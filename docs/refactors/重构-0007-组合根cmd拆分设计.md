## 重构目标

- `cmd/juhe-ai-gateway` 单包 47 个生产文件 / 26,898 行（2026-09-18 实测，含 `compose_account_test_local.go` 221 行；较评估报告 26,884 漂移 +14，为工作区演进），是评估文档 2.3 节第二大 god 包；顶层同包测试 67,303 行 + `acceptance/` 全链路测试套件（20 个文件，纯测试）。
- 本包是**组合根（composition root）**，与其他 god 包性质不同：`package main` 不可被 import、零外部消费方（实测 `internal/` 无任何生产文件 import 本包）。问题不是"包边界过宽"，而是**组合根职责与被误放进 cmd 的业务逻辑混装**——多个 chain_* 文件是完整的 Node 业务域移植（策略决策、协议变换、数据访问 seam、镜像管线），却装配在 main 包里积累耦合。
- 目标形态：区分"组合根职责本身"（runtimeConfig、compose、services 装配、端口适配、/v1 编排器）与"可下沉业务域"，把后者成批下沉到 `internal/` 子包；组合根留置装配与编排，业务改动半径移出 cmd。
- 关键约束（本设计最高优先级）：**组合根边界不可下沉**。`gatewayChain`/`v1DispatchLoop`（chain_v1.go）消费未导出的 `chainRuntimeServices` 装配态与 chain_ports.go 的约 90 个端口适配函数，下沉编排器会要求导出巨大 port 面、破坏"装配态只存在于 main"的既有边界。下沉对象限定为**自含业务域**（不引用 `composed`/`services` 装配态、或仅经构造函数参数收窄依赖的文件）。
- `chain_v1.go`（2,693 行）定位：它是 `/v1` 顶层编排器（`gatewayChain.ServeHTTP` + `v1DispatchLoop`：preflight → 调度循环 → 回退分组切换 → speed-first 切换 → 流式服务端重试），属组合根职责**留守**；其超 2000 行预警线问题由 R3 既有任务按大文件重构指南做**文件内拆分**（先纯函数/类型/常量，再副作用），本设计不改变该任务的归属与顺序。

### 共享类型归属

- **组合根独占（不下沉）**：`composition`、`runtimeConfig`、`chainRuntimeServices`、`chainRuntimeDeps`、`gatewayChain`、`v1DispatchLoop`、`gateGatewayChain`、`systemApiPrefix`、sqlite/PG 打开与迁移编排（storage_bootstrap*）、`Deps`/`Mount` 各家族装配函数。装配态（composed/services）只存在于 main——这是既有边界，下沉域不得反向引用。
- **下沉域自带**：各业务域的类型、常量、错误与中文文案随文件迁移（`chain_error_policy.go` 的规则注册表与匹配器、`chain_bridge_response.go` 的变换链、`chain_driver.go` 的协议常量投影、`chain_accounts_secret.go` 的 HMAC 指纹函数族等）；下沉文件对 `composed`/`services`/`cfg` 的引用点改为构造函数参数（db 句柄、secret、dialect 标志、缓存端口），由组合根装配注入。
- **共享常量收敛**：下沉文件间共用的小常量（如 `chainTimeLayout`、`gatewayPostgresPoolMaxOpen/MaxIdle`）随首个下沉域迁移或提升到组合根导出常量，逐符号核对（实施时 `rg` 该常量的全部引用点后决定方向），禁止每包复制一份。
- **外部包类型经窄面引用**：下沉域消费 `gatewayruntimecache`/`gatewaypreauth`/`gatewaydispatch`/`accounts`/`gatewaycodex` 的类型与端口保持既有 import 方向（internal 包 → internal 包，与现状一致）；`gatewayaccountseams` 实现的 `gatewayruntimecache.AccountsSelector`、`gatewayaccountseams` 实现的 `gatewaydispatch.AccountLocks`、`chatimaging`/`chatkeys`/`chatobservation` 实现的 `chat.*` 端口接口均在装配处由组合根接线——实现下沉不改变端口定义位置。

### 循环依赖检查（关键约束）

- **cmd → internal 单向，天然无环**：`cmd/juhe-ai-gateway` 是 `package main`，实测 `internal/` 无任何生产文件 import 本包（含测试文件仅在 `internal/business/accounts/w7a_extra_test.go` 等出现"juhe-ai-gateway"字符串，非 import）。下沉只会新增"main → 新 internal 包"单向边，结构上不可能成环。
- **唯一需要防守的反向边**：下沉域之间不得互相引用装配态。规则：`gatewayerrpolicy` 的效果窄桥（原 chain_error_policy_effects.go）需要写侧能力时，经构造函数注入的窄接口（在 errpolicy 包定义、组合根用 accounts/gatewayruntimecache 既有服务实现），不得直接 import 其他下沉域；`gatewayaccountseams` 不得 import `gatewayerrpolicy`（锁结算触发的错误策略调用走组合根接线）。每波验收用 `go list -deps ./internal/<新包>/...` 断言依赖闭包不含其他同批下沉域（波次 1 的 gatewayerrpolicy 与波次 3 的 gatewayaccountseams 分批交付即是为此）。
- **与 REFACTOR-0005/0006 的边界**：`chatimaging`/`chatobservation`/`chatkeys` 实现 `chat.*` 端口，方向是"新包 → chat 包"，与 chat 包自身拆分（0006 阶段 C 的 `chatassets`）不产生环；`gatewayaccountseams` 消费 `gatewaydispatch` 端口，方向同样是单向。两侧设计互不修改对方文件。

## 变更范围

- 受影响：`cmd/juhe-ai-gateway/` 11 个生产文件（约 11,152 行）成批下沉 + 顶层测试中对应主题文件随迁（w1_error_policy_*、w1_accounts_*、chain_accounts_*、chain_chat_images_* 等按被测对象归属；共享 stub 文件 `w1_stubs_test.go` 等按使用方复制或抽到各新包的 testhelper，随迁清单在每波实施前用 `rg -l` 逐符号核对）；新增约 8-9 个 internal 子包目录。
- 不动：`acceptance/` 全套件（黑盒级，经 HTTP 面/组合根入口测试）、`chain_v1.go` 的编排器职责（仅按既有 R3 任务做文件内拆分）、`compose.go` 装配矩阵、全部 internal 既有包（零改动——这是本设计与 0005/0006 的最大差异：外部消费面本来就是零）。
- 文档联动：本文件 + `docs/plans/` 计划状态 + `docs/refactors/README.md` 索引 + 评估文档 god 包表复测。

## 行为边界

- 保持不变：全部 HTTP 路由与方法面、/v1 链行为（降级端口的一次性日志语义、错误策略决策顺序、恢复时间计算）、错误中文文案、Redis 键名与命名空间（`gatewaycodexstate` 的字面量键逐字节保持）、审计事件、SQLite/PG 双模语义、`acceptance/` 全链路验收结果。
- 明确变化：仅代码归属（业务域从 main 包移入 internal 子包）+ 装配点改为构造函数注入；组合根对外的可观察行为（启动日志、fail-fast 报错文案）不变。
- `chain_v1.go` 文件内拆分（既有 R3 任务）在本框架中的定位：第一阶段先拆纯函数/类型/常量（`chainSchedulingPolicyValueOf`、`speedFirstReservationViewOf`、`streamServerRetryExhaustedInput` 等，实测该文件尾部约 500 行为自由函数与输入类型），再拆 `v1DispatchLoop` 的副作用族（speed-first 切换 / 流式服务端重试 / 回退分组切换），产物仍为 main 包内兄弟文件（chain_v1_speedfirst.go 等）；**不下沉、不接口化**，为未来"若编排器需要复用"保留唯一出口（导出编排函数 + services 窄面），当前不实施该出口。

## 风险与后续

- **测试随迁断裂（最高风险）**：顶层 67,303 行测试与 main 包未导出符号强绑定，且共享 stub 体系。缓解：每波实施前先出随迁清单（被测符号 `rg` 反查测试文件 + stub 依赖闭包）；波次 1 选最小域试跑随迁模式；stub 优先抽为各新包内 `export_test.go` 或 testhelper 文件，禁止把测试辅助下沉为生产代码。
- **装配态泄漏**：下沉文件残留对 `composed`/`services`/`cfg` 的引用是编译错误（天然拦截），但对包级函数/常量的隐性引用（`chainTimeLayout` 类）需逐符号核对；验收命令已含 `go vet` 与全量测试。
- **行为漂移**：错误策略决策、恢复时间抖动、Redis 键名是生产行为契约（Node 语义对齐），迁移必须逐字节保持文案与键名；波次 4 用字面量 diff 核对。
- **与并行波次的同文件冲突**：R4（时钟注入触及 gatewaycodexstate 相关退避）、0005（accounts 子域落地改变 compose 系归属）、0006（chat 阶段 C 与波次 5 共享 my-chat 链路）——三处均按"先到先得 + 后到 rebase 评估"协调，实施前在计划文档登记占用文件清单。
