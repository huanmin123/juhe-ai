# 重构案例库

- [REFACTOR-0004](重构-0004-管理接口场景DTO与字段级写入.md)：把 Node 管理列表、编辑、options、runtime、secret 和 mutation 从共享宽 Summary 拆为场景 DTO 与字段级写命令。

> 面向 AI 和维护者。
> 这里记录每次有复用价值的重构设计、拆分过程、验证结果和复盘，用来沉淀可参考的历史案例。
> 通用大文件重构流程见 [大文件重构指南](../architecture/大文件重构指南.md)。

## 1. 目录目标

- 记录重构为什么发生、怎么拆、拆完是否保持行为一致。
- 沉淀可复用的拆分边界、验证方式和踩坑经验。
- 为后续处理相似的大文件、职责膨胀和模块重构提供参考。

## 2. 什么时候建记录

- 出现跨文件、跨层、跨模块的职责拆分时。
- 重构后行为需要额外验证，且后续大概率还会复用同类做法时。
- 一个文件被拆成多个职责文件，且希望保留历史说明时。
- 需要在不同重构之间对比思路、结果或风险时。

## 3. 编号与命名

- 编号格式统一为 `REFACTOR-0001`、`REFACTOR-0002`、`REFACTOR-0003`……按创建顺序递增。
- 编号只增不改，不重复使用，不回收。
- 文件名建议：`重构-0001-简短标题.md`。

## 4. 推荐目录结构

```text
docs/refactors/
  README.md
  重构模板.md
  重构-0001-xxx.md
  重构-0002-xxx.md
```

## 5. 单个记录至少包含什么

- 基本信息：编号、状态、创建时间、关联计划、关联模块。
- 重构目标：为什么拆，期望达到什么边界。
- 重构前问题：原文件或原结构的职责混乱点。
- 拆分设计：新文件各自负责什么、不负责什么。
- 变更范围：涉及哪些文件、路由、组件、类型或脚本。
- 行为边界：哪些外部行为保持不变，哪些是明确变化。
- 验证记录：跑过哪些命令、做过哪些手动验证、结果如何。
- 风险与后续：剩余大文件、后续建议、可能的回归点。

## 6. 与计划的关系

- 如果重构对应一个明确需求，先看对应 `docs/plans/` 计划，再写重构记录。
- 计划负责需求推进，重构记录负责结构演进和复盘。
- 长期稳定结论仍应回写到架构、阶段计划或运行手册。

## 9. 写作注意事项

- 写事实和决策，不写空泛评价。
- 不要只写“已拆分”“更清晰了”，要写拆了什么、为什么拆、怎么验证。
- 不把敏感凭据、真实 token、用户隐私或完整错误快照写入记录。
- 如重构改变外部行为，必须明确说明保持不变的行为和变更边界。
