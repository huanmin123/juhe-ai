## 3. R1 迁移（shared/platform 收敛）

### 3.1 抽了什么

1. **schedulejitter.Window 全输入域等价**（对照 HEAD `gatewayaccounteffects/clock.go`、`accountkeystates/probe.go` 的 ms 域实现）：
   - ms 整除语义：新包装 `int64(schedulejitter.Window(time.Duration(ms)*time.Millisecond)/time.Millisecond)` 对任意 int64 ms 输入等于旧 `interval/2` 整除——`Duration(ms*1e6)/2` 恒精确（ms*1e6 为偶数），再除 1e6 截断即 `floor(ms/2)`，与旧 int64 整除逐点一致。
   - `interval<1` 钳制等价：旧 `max(1, interval)` 后取半得 0；新 `Window(≤0)=0`，结果一致（含负值）。
   - 删除的两处钳制经数学复核确为恒假：`interval<1min ⇒ interval/2 < 30s`（SubMinuteWindow 钳制恒不绑定）；各档常量窗口（30s/30min/1h/8h）在所属区间内恒 ≤ `interval/2`。删除有据（w12h 授权），行为不变。
   - 注入点保留：`gatewayaccounteffects` 的 `passiveScheduleOffsetWithinWindowMs(windowMs, random)` 原样保留可注入 random；`accountkeystates` 的 `passiveJitterOffsetMS` 与 HEAD 逐行一致；jobs 侧 `internal/schedulejitter` 为 platform 委托 shim。
2. **timefmt 与旧 parse 等价**：`timefmt/rfc3339.go` 与 HEAD 锚点 `jobs/internal/statsagg/rfc3339.go` 逐行一致（同一正则、TrimSpace、offset 必需、month/day/hour/minute/second 范围校验、`daysInMonth`、小数 >3 位截断毫秒、`FixedZone` offset、offsetMinute>59 拒绝）。三个消费方（gatewayquota/gatewayusage/usagewriter）均为薄委托包装，签名与错误文案前缀留在调用点。
3. **sanitize**：`rediscfg.SanitizeRedisName/SanitizeRedisNamespacePart/NamespacedKey` 与 HEAD 副本逐字符比对一致；`gatewayclientip.sanitizeRedisNamespacePart` 包装保留空值报错契约（`Redis namespace 不能为空`）；计划登记的 gatewayhotquality/gatewayobs 逐字符不折叠变体确实未收敛（差异保留）。
4. **bind**：`sqldialect.BindSQL` 与 HEAD `taskruns/store.go` bind 同算法（顺序 `?`→`$n`、SQLite 原样），taskruns 侧为委托。
5. **encodeJSON**：`jsonenc.EncodeJSON` 为"忽略错误返空串"语义，与 gatewaycircuit HEAD 原型一致——但 jobs circuitstore 原型是 panic 契约，见 P1-1。
6. **newID**：`idgen.RandomHex` 为 crypto/rand + 时间熵回退；authsys 包装 `prefix + "_" + idgen.RandomHex(12)` 保持 12 字节 hex 格式契约，错误路径语义变化见 P2-4。

- **P1-1 circuitstore encodeJSON 的 panic 契约被移除，与计划登记矛盾**：

## 4. 生产缺陷修复×2

### 4.1 jobs cmd J3a 停机死锁修复

- **抽了什么**：`backend-go/projects/jobs/cmd/juhe-ai-jobs/main.go:604-635`（J3a management API 组件）与 `shared/platform/supervisor/supervisor.go` 契约（"Close is called only after every Run invocation has stopped"，`group.Wait()` 后逆序 Close）。
- **死锁确认与修复形态**：HEAD 版 Close 内调 `managementServer.Shutdown`，而 `Serve` 只能被 Shutdown 解阻 ⇒ Run 等 Close、Close 等全部 Run，死锁成立。工作区版将 Shutdown 移到 Run 侧：goroutine 等 `runCtx.Done()` → 5s 上限 `Shutdown` → `Serve` 返回 `ErrServerClosed` → 等 `stopDone` 收尾后返回 nil；Close 收缩为只关 `j3ManagementPool`。形态正确。重复 Shutdown 已因 Close 不再触碰 server 而消除（且 `http.Server.Shutdown` 本身可重入）。正常停机路径 Run 返回 nil 时 `ctx.Err()!=nil`，不会触发 supervisor 的 `ErrComponentStopped` 重试。
- **发现的问题**：
  - **P2-3 Serve 持久报错时 stop goroutine 按次累积**：`Serve` 返回非 `ErrServerClosed` 错误时 Run 立即返回 err，而 stop goroutine 仍阻塞在 `runCtx.Done()`；supervisor 对该组件按重试边界重启 Run，每次重试新起一个 goroutine，旧 goroutine 直到进程级 ctx 取消才退出。仅在监听器持续故障的病态场景下缓慢累积（有界于组件循环存活期）。建议：将 stopDone goroutine 的生命周期与单次 Run 绑定（如 select Serve 返回即放弃等待）。不阻塞合入。

### 4.2 chat releaseRetryAt 60s 修复

- **抽了什么**：`backend-go/projects/gateway/internal/chat/asset_routes.go:412-420` 与 Node 归档 `migration-backup/node/final-archive/backend/src/modules/chat/chat.routes.ts:561`（`retryAt: new Date(nowMs + passiveScheduleDelayMs(60_000)).toISOString()`）。
- **修复确认**：HEAD 为 `.Add(60_000)`——Go time.Duration 域即 60µs，与 Node 毫秒域 60s 相差 1000 倍；工作区改为 `.Add(60 * time.Second)`，两个返回分支均已修正，注释载明了毫秒/纳秒域差异。单位修复正确。
- **发现的问题**：
  - **P2-2 注释声称 jitter is applied by the clock owner 与实现不符**：Node 语义是 `passiveScheduleDelayMs(60_000)` = 60s ± 最高 30s 抖动；Go 路径 `Now: nowValue` 为裸时间值，`assets.go` 的 `ReleaseAssetDeletionClaim` 将 retryAt 原样写库，全链无任何抖动施加点。实际行为是确定性 now+60s（较 Node 少 ±30s 抖动，非缺陷级差异），但该注释会误导后续维护者认为抖动已实现。建议改注释为未复刻 Node 抖动、固定 60s，或补齐抖动。不阻塞合入。
