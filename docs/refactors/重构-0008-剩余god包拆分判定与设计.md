## 2. openaicompat：值得拆（完整设计）

### 2.1 扇入构成与包内取证

- **扇入小且函数主导**：生产消费仅 5 文件（`cmd/juhe-ai-gateway/chain_bridge_response.go`、`chain_driver.go`、`chain_openaicompat.go`、`gatewayopenai/driver.go`、`gatewaydispatch/accountpreparation.go`），生产限定引用 132 处。构成：顶层函数调用为主（`PumpBridgeSseTransform`×10、`NormalizeEndpointFamily`×8、`BridgeJSONStringifyOf`×6、`ExtractJSONObject`×5、`Transform*`/`Process*`/`Complete*`/`Fail*` 族），端点族常量 `Family*`×31，类型词汇仅 `GatewayScope`×2、`BridgeGuidanceError`×3、选项结构体等少量。**复查-0001 的"词汇主导 → 不拆"条款不适用本包**，进入第 2 条判定。
- **纯叶子包**：直接 import 全部为标准库（`go list -f '{{.Imports}}'` 实证），是全工作区罕见的零内部依赖大包——拆分无任何 cycle 风险，也不新增任何跨包耦合边。
- **包内两个独立演化域**（生产代码 90 天 git 取证，11 次涉本包提交）：bridge 侧 26 次文件触碰、storage 侧 10 次，**生产代码 0 次同提交修改**（唯一一次同时触碰是覆盖扫描批次，且只动测试文件）。两侧是真独立的演化轨道：bridge 随协议对矩阵增长（每新增协议对需 request+response+stream 三类文件），storage 随 OpenAI 兼容 API 面增长（vectorstores/files 家族）。
- **交叉边极小且已量化**：bridge → storage 仅 `Config` 类型签名引用 2 处（`computeradapter.go:56`、`hostedtoolregistry.go`）+ `Deps` 依赖 7 处（全部在 `bridgeexecutors.go` 的 `FileResolverForScope`/`FileSearchExecutorForScope`，`scopeFileResolver{deps: d}`）；storage → bridge 仅 `BridgeRequestError`/`bridgeError` 7 处（全部在 `imagegeneration.go`）。双向边合计约 16 处生产引用——accountscore 式中立 core 可完全解掉。
- `bridge_request.go` 已拆为 7 个 `bridge_request_*.go` 文件（文件级治理完成）；本设计补的是**包级设计**。

### 2.5 消费方迁移策略（与 0005/0006 门面策略的差异点）

本包生产消费方仅 5 个文件、132 处限定引用，**推荐"消费方直接改 import"，不建永久函数转发层**：

- `chain_bridge_response.go` / `chain_driver.go` / `gatewayopenai/driver.go` / `gatewaydispatch/accountpreparation.go` → import `openaicompatbridge`（+ core 的错误/常量）；
- `chain_openaicompat.go` → import `openaicompatstorage`（`NewStore`/`Deps`/`Mount`/`Config`）；
- 根包 `internal/openaicompat` 缩薄为 doc.go + 装配聚合（可选保留 `Deps`/`Mount` 转发以稳住 `chain_openaicompat.go` 一处）。

理由：REFACTOR-0005/0006 选门面 + alias 是因为消费方 53/16 个生产文件 + 64 个测试文件，alias 是零改动收益最大解；本包函数主导的导出面做门面需要约 60 个一行转发函数（Go 函数不可 alias），永久重量大于 5 个文件的一次性机械改动。实施时以实测 diff 取小者为准。

### 2.6 循环依赖检查

1. `openaicompatcore` 不 import 任何兄弟包（只有标准库）——中立性由阶段 A-1 验收断言 `go list -deps` 保证。
2. `bridge → storage` 唯一潜在反向点是 `bridgeexecutors.go` 的 `FileResolverForScope`（Deps 方法）。解法：`FileResolver`/`FileSearchExecutor` 接口与输入输出类型留 bridge；`scopeFileResolver` 实现 + 两个 ForScope 方法（约 30 行）随 storage 包，storage 实现 bridge 声明的接口——与 0005 `AccountWriter` 窄接口同一模式。
3. `storage → bridge` 边：storage 消费 `FileResolver` 接口类型（import bridge）。bridge 对 storage 无任何引用（已实测交叉边清单，2.1 节）。验收：每阶段 `go vet ./...` + `go list -deps` 断言三个包无环。

**判定：不拆。** 证据：

## 4. gatewayresponse：不拆，维持现状

**判定：不拆。** 证据：

1. 位置形态是"末端响应子系统"：依赖 `gatewaydispatch`/`gatewaypreauth`/`gatewayruntimecache` 等 8 个内部包（方向单向向外），生产消费方仅 5 个文件且全部在 cmd（`chain_v1.go` 为主）。
2. 行为面极小且闭合：`HandleStreamUpstreamResponse`/`HandleNonStreamUpstreamResponse` 各 1 处（`chain_v1.go:431/433` 的流/非流分叉）、`NewSink` 1 处（`chain_compose.go:334`）、`NewReaderUpstreamBody`/`ShouldHandleOpenAIUpstreamResponseAsStream`/`ParseGatewayNonStreamJsonBody` 各 1 处；76 处限定引用以类型词汇为主（`UpstreamResponseHandlingResult`×9、`DownstreamCommitState`/`ModelCatalogEntry`/`DownstreamConnectionClosedMessage`/`AccountView` 各×4）。
3. 内部词汇链不可分：stream（sink/streamread/pipe/pipefinal/heartbeat）、non-stream（nonstream/nonstreamjson/nonstreaminspection）、finalize/audit（finalize/models/convert/failurestatus）共享 `UpstreamResponseHandlingResult`/`DownstreamCommitState`/`AttemptAuditCapture`/账户视图族词汇，且 `nonstream.go`（12 处）、`finalize.go` 直接消费 `gatewaydispatch` 词汇——按语义拆包等于把同一词汇链强行跨包化（复查-0002 §4.3 同款反事实）。
4. **热路径最高优先级约束**：本包承载 /v1 SSE 泵，R5 基线在册（`reports/perf-baseline-20260918/` 的 `response_sse_cpu.prof`/`response_sse_mem.prof` 与包内 `response_bench_test.go` 的 `BenchmarkResponsePipeUpstreamStreamOpenAIChatSSE` 可重放基准）。REFACTOR-0006 已确立"热路径文件禁止接口间接层"，而本包任何子域边界都必须穿过 pipe/sink 词汇链，拆分是纯高风险零 import 收益动作。
5. 文件级健康：最大 `nonstream.go` 1,145 行。

### 8.2 下潜设计

- **新平台包**：`shared/platform/circuitstate`（命名对齐现有 `sqldialect`/`schedulejitter` 单层小写风格；备选名 `accountcircuit`）。
- **内容**（每侧迁移约 1,650~1,750 行，净消重约 1.6k 行）：`lua.go` 全部 7 个脚本与 cjson 解析原语；`Scope`/`State`/`MutationResult`/`CapacityExhaustedState`/`Lease` 词汇与 `CloneState`/decode 原语；Redis key 构建与 namespaced key 原语；`ProbeSourceFence`/`encodeSourceFence`/fence 校验。
- **不迁移**（业务留在各自模块）：`CircuitService` 状态机编排、suppression/wait/probe 协调器、bridge 控制面（gateway 侧）；listavailability/controlplane/overlay/adapter（jobs 侧）。平台包只承载"共享运行态的权威迁移语义与词汇"，符合"shared 只放 contracts 与无业务 platform"边界——两进程写同一份 Redis 状态，脚本即契约。
- **实施步骤**：① 逐符号行为对账（漂移清单：`stringList.equal` 是否 jobs 侧必需、`sha256HexShort` 参数化或留守、注释语言统一为原文英文）——行为有差异的符号先甄别是漂移还是两侧各自需要，再决定下沉或留守；② 建包迁入 + 两侧改 import + 包内单行委托壳可免（两包均为内部包，无外部消费方，直接改 3+13 个消费文件中的引用符号即可，实际引用集中在包内）；③ 删除两侧重复定义。
- **正确性收益**：脚本从"两份手工同步的副本"变为"单一事实"，消除两侧脚本漂移导致共享熔断状态语义分叉的风险（这是比行数更重要的收益）。
- **验收**：两模块 `go build ./... && go test ./internal/gatewaycircuit/... ./internal/circuitstore/... -count=1` 全绿；两侧 Redis 集成/门控测试（脚本行为）不降；`diff` 断言平台包 lua.go 与两侧旧副本字节一致；评估文档 god 包表复测（预期 gatewaycircuit ≈9.5k、circuitstore ≈7.9k）。

## 10. 风险与后续

- **openaicompat 测试随迁断裂**：13,846 测试行 / 36 个测试文件与生产文件同包，跨界测试文件（wiring/coverage 族）需拆分或指定留守方；按 0005 已验证的"同前缀成批迁移"模式小批量先行。
