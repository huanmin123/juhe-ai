# 第一阶段计划：OpenAI 账户与 API Key

## 目标

做一个更轻量的管理后台。整体架构先覆盖供应商、账户、API Key、代理、使用记录、系统设置和分组，但第一阶段只落 OpenAI。

第一阶段的核心不是复制 `sub2api` 的全部能力，而是先把以下事情做好：

- OpenAI 供应商可管理
- OpenAI OAuth 账号可管理
- OpenAI API Key 账号可管理
- 分组可绑定 OpenAI 账号
- API Key 可绑定分组
- 透传、错误处理策略、并发、代理这些能力有清晰的字段和边界
- 前后端接口先稳定下来，后续再接中转逻辑

## 第一阶段范围

### 供应商管理

- 内置 OpenAI 供应商
- 展示供应商状态、支持的账户类型和默认基础配置
- 提供“查看模型”操作，展示该供应商的模型版本、上下文窗口和计费价格
- 暂不做供应商插件系统，但数据结构按可扩展方式设计

### 分组管理

- 分组列表
- 新增 / 编辑 / 删除
- 分组选择所属供应商，只绑定同一供应商下的多个账户
- 列表展示分组名称、供应商、账户可用数 / 总数、总并发、总用量、状态和操作，不展开账户名称
- 给 API Key 选择分组
- 第一阶段建议一个 API Key 绑定一个分组，后续再扩展多分组

### 账户管理

- 账户列表
- 新增 / 编辑 / 删除
- 启用 / 停用
- 备注、平台、账号类型等基础信息
- 统一“添加账户”入口：先选供应商，再显示该供应商支持的账户类型，最后显示具体配置
- OpenAI OAuth 创建方式
- OpenAI API Key 创建方式
- 代理绑定
- 并发上限
- 优先级
- 透传开关
- 错误处理策略引用：创建时使用系统默认策略，编辑弹窗可切换或清空为运行时默认
- 调度相关的基础标记位
- 账户测试动作
- 更多下拉动作：测试、停用/启用、暂停/恢复调度、OAuth 刷新、切换客户端等
- 账户列表不展示 `Access/API Key` 与 `Refresh Token`；这两个字段只在编辑弹窗中查看和修改

### API Key 管理

- API Key 列表
- 新增 / 编辑 / 删除
- 启用 / 停用
- 复制密钥
- 绑定分组
- 过期时间、备注、权限范围

### 代理管理

- 代理列表
- 新增 / 编辑 / 删除
- 支持 HTTP、HTTPS、SOCKS5 基础字段
- 账户可选择绑定代理

### 使用记录

- 记录 API Key、分组、账号、模型、状态码、耗时、错误摘要、token 和成本
- 从 OpenAI 响应解析 `usage.input_tokens`、`usage.output_tokens`、`usage.input_tokens_details.cached_tokens`
- 轻量计费按 OpenAI 官方价格表估算，未覆盖模型只记录 token 不强行猜价格

### 系统设置

- 基础系统信息
- 默认并发、默认错误策略、默认代理策略的配置占位
- 默认错误策略由 `defaultErrorPolicyId` 保存，新建账号默认带入
- 密钥显示：本地网关 API Key 完整展示并支持复制；账户密钥只在编辑弹窗里展示
- 流熔断与账号处理：支持流空闲超时、失败阈值和全局临时不可调用时长；达到阈值后一律临时不可调用

### 后端能力

- 提供账户和 API Key 的 REST 接口
- 提供供应商、分组、代理和系统设置 REST 接口
- 提供基础健康检查
- 提供前端需要的枚举、状态和配置字典
- 使用 SQLite 做默认存储，满足单人自用场景
- 数据访问先通过 repository 层封装，避免业务代码直接散落 SQL

### 前端页面

- 供应商管理页
- 账户管理页
- 分组管理页
- API Key 管理页
- 代理管理页
- 使用记录页
- 系统设置页
- 详情抽屉或弹窗编辑
- 搜索、筛选、分页
- 统一的状态标签和错误提示

## 参考 `sub2api` 的设计原则

### 透传

- 透传应该是账号能力的一部分，而不是临时页面配置。
- 需要保留账号级别的开关和对应的行为说明。

### 错误处理策略

- 错误处理不能只有“成功 / 失败”两种状态。
- 需要支持按状态码、关键词和匹配模式去做规则化处理。
- 需要区分“透传原始错误”和“返回自定义错误”。

### 并发

- 并发应该能区分“配置上限”和“当前占用”。
- 账号详情里最好能看到限制值和运行态。
- 后续网关层接入时，才真正按并发规则做调度。

### 代理

- 代理建议独立成一个配置实体，不要直接写死在账号请求里。
- 账号只负责绑定代理，实际请求时再解析代理地址。
- 这样后续更容易复用、切换和排查。

## 建议的数据对象

- `provider`：供应商定义
- `account`：上游账号主表
- `group`：账号分组，包含所属 `provider_code`
- `group_account`：分组与账号关联
- `api_key`：对外访问密钥
- `proxy_profile`：代理配置
- `usage_record`：使用记录
- `system_setting`：系统设置
- `error_passthrough_rule`：错误透传策略

## 建议里程碑

1. 建好前后端项目骨架和目录
2. 固化 OpenAI 供应商与账户类型定义
3. 实现分组、账户、API Key、代理基础 CRUD
4. 再补筛选、详情、状态切换和复制能力
5. 补齐透传、错误策略、并发和代理字段
6. 之后再接真正的中转和调度逻辑

## 第一阶段完成标准

- OpenAI OAuth 账号可以完整增删改查
- OpenAI API Key 账号可以完整增删改查
- 账户创建入口不写死成多个 OpenAI 按钮，可按供应商能力渐进展示类型与表单
- 分组可以绑定账户
- API Key 可以完整增删改查
- API Key 可以绑定分组
- 代理可以完整增删改查并绑定到账户
- 页面能展示基础状态和配置字段
- 后端接口有统一结构
- 文档能说明每个关键字段的作用
- 系统设置可配置默认错误策略、默认临时不可调用时长和流熔断阈值；未知异常和流式中断都会写入账号临时不可调用状态
