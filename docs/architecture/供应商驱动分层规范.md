# 供应商驱动分层规范

## 文档边界

本文定义供应商、协议、模型目录、计费和前端能力的长期隔离标准。它不记录某一次重构的任务进度；执行进度见 `docs/plans/计划-0050-供应商驱动化分层重构.md`。

本文适用于 `openai`、`gpt`、`anthropic` 以及后续 GLM、DeepSeek、Gemini 等供应商接入。新增供应商时必须先对齐本文接口边界，再落代码。

## 核心目标

- 通用网关只处理认证、分组、账号候选、调度运行态、审计和使用记录等共享能力。
- 协议差异下沉到 `ProtocolDriver`，例如 OpenAI v1、Anthropic Messages、Gemini native。
- 供应商账号差异下沉到 `ProviderDriver`，例如凭据、上游认证、默认 baseURL、endpoint mode、账号测试和模型映射。
- 模型目录、别名、价格和 usage 语义下沉到模型与计费驱动，避免统计和费用逻辑按 `providerCode` 散落特判。
- 前端页面通过 provider capability adapter 展示字段、校验和测试入口，不直接在页面组件里判断供应商。

## 标准接口

### ProtocolDriver

`ProtocolDriver` 表示协议形态，不表示账号池供应商。

职责：

- 识别请求路径、方法、endpoint family 和是否为本地模型列表请求。
- 构造协议级本地错误响应和流式失败事件。
- 解析 JSON / SSE 响应，抽取文本、错误、完成状态、usage 和语义帧。
- 渲染协议模型列表响应，例如 OpenAI `/v1/models` 或 Anthropic `/v1/models`。

禁止：

- 不读取账号凭据。
- 不决定 API Key 绑定分组。
- 不写账号状态、冷却或授权额度。
- 不包含 GPT / Claude Code 这类客户端画像专属策略。

### ProviderDriver

`ProviderDriver` 表示供应商协议档案下的账号运行能力，以 `provider_protocol_profile_id` 为注册边界。

职责：

- 标识支持的 `providerCode + protocolCode + protocolVersion + profileId`。
- 归一化账户凭据和 endpoint mode 默认值。
- 判断账号是否支持当前请求形态。
- 构造上游 URL、请求头和请求体。
- 执行账号测试请求构造与结果解释。
- 声明账户内 API Key 池策略、客户端兼容默认值和供应商局部模型映射。

禁止：

- 不做本地 API Key 认证。
- 不绕过分组、授权、模型限制和调度状态。
- 不在通用网关文件里新增 `if anthropic / if gpt / if openai-compatible` 分支。

### UsageSemantic / CostCalculator / ModelCatalogProvider

这三个接口共同处理“模型和账务语义”，不能继续揉进一个通用 service。

职责：

- `UsageSemantic`：把上游 usage 字段归一到当前明细和统计口径，定义 cache read/write/thinking tokens 等语义。
- `CostCalculator`：按供应商价格规则计算 input、output、cache read、cache write、thinking、image、audio 等成本。
- `ModelCatalogProvider`：提供内置模型、别名、下线过滤、release date、协议能力推断和供应商模型列表投影。

禁止：

- 不在 usage record 写入层直接 import OpenAI model mapping。
- 不在统计补算里绕过 catalog/custom model/system account 直接按 provider 固定估价。
- 不让前端自行用 `providerCode` 计算缓存命中率或计费展示口径。

### ClientProfile

`ClientProfile` 是客户端画像，不是供应商，也不是协议。

职责：

- 描述 Codex、Claude Code、普通 OpenAI SDK、普通 Anthropic SDK 等下游客户端的请求恢复、重试和失败事件偏好。
- 由入口、header、路径和请求上下文识别。

禁止：

- 不把 Codex 写进 OpenAI 协议通用层。
- 不把 Claude Code 写成 Anthropic 账号类型。
- 不把客户端画像作为用户创建账户时必须选择的供应商档案。

## 请求主链路

```text
客户端请求
  -> 本地 API Key 认证与额度快照
  -> 解析协议、endpoint family、客户端画像
  -> 通过模型路由或 API Key 分组确定 provider_protocol_profile_id
  -> 读取同档案候选账号
  -> ProviderDriver 判断请求能力和构造上游请求
  -> ProtocolDriver 解析响应和渲染下游协议
  -> UsageSemantic / CostCalculator 记录 usage 与成本
```

通用层只允许依赖 driver registry，不允许直接依赖具体供应商实现。具体供应商实现可以依赖通用工具，但不能反向污染通用层。

## 新供应商接入清单

新增供应商前必须明确：

- `providerCode`、`provider_protocol_profile_id`、`protocolCode`、`protocolVersion`。
- 账户类型、凭据字段、敏感字段、默认 baseURL 和账号测试模型。
- 支持的 endpoint family 与 endpoint mode。
- 上游认证方式、危险 header 过滤和请求体是否允许 raw passthrough。
- 模型目录、别名、下线规则、价格字段和 usage 语义。
- 前端表单字段、默认值、校验、测试入口和使用记录展示。
- 回归测试：账号创建、分组绑定、API Key 调度、请求能力过滤、账号测试、模型目录、usage/pricing 和前端类型检查。

## 迁移规则

- 先新增 registry / facade，再逐步把混写文件切到 driver，不做一次性大搬家。
- 旧 OpenAI 命名的类型可以短期保留别名，但新代码必须使用中性命名。
- 每切一个入口都要补回归，避免只完成文件移动而没有行为证明。
- 不为旧字段、旧表结构或旧接口保留运行时兼容分支；如果需要处理既有数据，只能作为离线同步或重建步骤记录。

## 边界检查

后续代码审查至少检查：

- `gateway/core`、`gateway/request`、`gateway/dispatch`、`gateway/response` 是否直接写了具体供应商分支。
- `storage` 通用 repository 是否出现 OpenAI 专属业务查询。
- `model-pricing` 是否把多个供应商价格和别名继续写在同一个 service。
- 前端页面组件是否直接判断 `providerCode === 'anthropic'`、`providerCode === 'gpt'` 或协议 profile。
