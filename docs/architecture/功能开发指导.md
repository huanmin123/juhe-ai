# 功能开发指导

> 面向 AI 与维护者。
> 适用于 `juhe-ai` 的前端、后端、存储、脚本和文档变更。
> 本文件只写通用开发方法和边界原则；当前业务事实以架构、functions 和运行手册为准，历史阶段计划只作为范围演进记录。

## 1. 文件定位

- 本文件位于 `docs/architecture/功能开发指导.md`，作为通用功能开发方法入口。
- 本文件回答这些问题：
  - 新功能开发前先判断什么
  - 代码应该落在哪一层
  - 新增字段、接口、页面时如何保持一致
  - 如何避免过早复杂化
  - 功能完成后如何验收和说明
- 具体模块范围以这些文档为准：
  - [架构总览.md](架构总览.md)
  - [功能文档目录](../functions/README.md)
  - [开发运行说明](../develop/运行说明.md)
  - [开发测试与验证说明](../develop/测试与验证说明.md)

## 2. 项目边界

- 当前项目定位是轻量管理与中转能力，不是重型系统的逐行重写。
- 技术栈：
  - 前端：`Vue 3 + TypeScript + Ant Design Vue`
  - 后端：`Node.js + TypeScript + Express`
  - 存储：`SQLite`
  - 包管理：`pnpm workspace`
- 默认原则：先做轻量闭环，再按实际需要扩展。
- 需求变化如果影响模块边界、数据关系或阶段范围，先更新设计文档，再开始大规模实现。

## 3. 开发前先判断

### 3.1 范围判断

- 先确认本次变更属于哪些范围：
  - 前端页面
  - API 请求层
  - 后端路由
  - 业务服务
  - 存储 schema
  - repository
  - 脚本
  - 配置
  - 文档
  - 验证流程
- 不清楚范围时，先查目录和设计文档，不要直接新增平行体系。

### 3.2 边界判断

- 判断是否改变：
  - 模块关系
  - 数据对象结构
  - API 入参或出参
  - 默认值
  - 敏感字段处理
  - 错误语义
  - 验证方式
- 只要影响边界，就应同步更新文档和类型。

### 3.3 复杂度判断

- 优先选择简单、直接、可验证的实现。
- 不为尚未落地的远期能力提前引入复杂抽象。
- 不为单个功能引入重型框架、全局状态或过度封装。
- 如果发现需求会显著扩大范围，应先向用户说明方案、收益和成本。

## 4. 分层落点

### 4.1 前端

- `frontend/src/views/`：页面组合、局部交互、页面级状态。
- `frontend/src/layouts/`：应用壳和通用布局。
- `frontend/src/router/`：路由定义。
- `frontend/src/api/`：后端请求封装。
- `frontend/src/types/`：前端领域类型。
- `frontend/src/styles/`：全局样式和跨页面样式。
- 页面不要直接复制后端业务规则；复杂规则应来自 API 返回或共享类型。

### 4.2 后端

- `backend/src/server.ts`：应用初始化、全局中间件、路由挂载。
- `backend/src/modules/`：模块路由和业务服务。
- `backend/src/domain/`：领域类型。
- `backend/src/storage/`：数据库连接、schema、repository、加解密等存储能力。
- `backend/src/scripts/maintenance/`：生产或上线可用的维护脚本，发布包统一通过 `backend/dist/scripts/maintenance/*.js` 调用。
- `backend/src/scripts/regression/`：本地开发回归脚本，只通过 `pnpm test:*` 调用，不作为生产运维入口。
- `backend/src/scripts/smoke/`：真实链路烟测脚本，只用于发布前验证。
- 可复用的本地演示 / 联调 / 测试造数统一扩展 `backend/src/scripts/maintenance/mockdata.ts` 或 `mockdata-fixtures.ts`；不要新增散落的 seed / demo 脚本。回归脚本内部的最小私有 fixture 只服务当前断言，一旦需要复用就移入 Mockdata。
- routes 负责 HTTP 边界，service 负责业务逻辑，repository 负责数据访问。

### 4.3 文档

- `docs/architecture/架构总览.md`：长期模块关系和架构决策。
- `docs/plans/`：历史阶段范围、具体需求计划、进度、验收、关联文档和注意事项。
- `docs/develop/运行说明.md`：启动项目、端口、环境变量和运行注意事项。
- `docs/develop/测试与验证说明.md`：类型检查、构建、接口检查、网关联通、账号测试和烟测。
- 规范类文档只写通用规则，不写具体业务流程。

## 5. 数据和字段策略

- 新增字段前必须明确：
  - 字段含义
  - 默认值
  - 是否可为空
  - 是否敏感
  - 展示策略
  - 数据清洗或重建方案
  - 是否影响现有 API
- 前端类型、后端类型、数据库字段、API payload 必须同步。
- 敏感字段应明确存储、传输、展示和编辑边界。
- 当前项目开发默认不做任何向下兼容；无论是否涉及代码、API、数据库字段、表结构、本地数据或历史部署，都只按当前最优解、最新模型和最新结构实现。
- 数据库结构可以直接调整到当前最优形态；如果影响本地 SQLite，直接修改 schema、类型、读写逻辑和测试种子，不在运行时代码里读取旧字段、双读双写、补旧表、自动迁移或保留旧数据兼容分支。
- 禁止在后端、前端、repository、网关主链路、启动路径或 worker 常规路径里保留一次性迁移、旧数据兼容、临时同步修复、迁移标记或历史字段兜底代码。
- 上线时由用户按当前 schema 做结构同步和数据迁移；AI 只在用户明确要求时提供一次性离线 SQL / 脚本，处理完成后不得把脚本挂入运行时代码。

## 6. 实现策略

### 6.1 单一事实来源

- 业务事实以后端和存储为准。
- 前端只做展示、输入和交互，不自行修正业务状态。
- 默认值应在后端或存储层收口，前端只负责呈现和提交。

### 6.2 副作用分离

- 外部请求、凭据处理、数据写入、后台任务、导入导出等副作用应集中在服务层或脚本中。
- 不要把复杂副作用塞进页面组件或路由回调。
- 副作用失败时要返回可读错误，避免吞掉根因。

### 6.3 大文件与频繁文件读取

- 日志文件、审计 payload、导入导出文件、运行记录和任何可能被定时任务或页面反复读取的文件，都必须按 offset / cursor / stream / 分块窗口读取。
- 禁止为了分页、搜索、追增量或截取尾部，先把完整文件读入内存再 `split`、过滤、反转或切片；需要按行处理时，必须只在完整行结束后推进 offset。
- 持续追新增内容的任务必须持久化文件游标和文件标识；worker 重启后从游标继续，遇到日志轮转、文件截断或文件标识变化时显式重置。
- 单次接口读取大 payload 时也只能返回有限窗口，并返回 offset、limit、total 和 nextOffset 等元数据，前端按需继续加载。
- 例外只限小配置文件、极小系统状态文件、测试 / 回归脚本、明确有大小上限的请求体 / 响应体捕获和加解密小 buffer；例外必须保持边界清晰，不能扩散到日志、审计、使用记录或业务明细的大文件路径。

### 6.4 列表稳定排序

- 所有底层列表查询必须使用稳定排序：业务排序字段之后追加不可漂移的唯一兜底字段，例如 `created_at + id`、`updated_at + id` 或关联表复合主键。
- 分页列表、下拉选项、后台批处理候选列表和聚合后返回的数组都应遵守同一原则，避免同一排序值的数据在更新无关字段后相对顺序变化。
- 前端可以提交排序条件，但不能依赖前端二次排序修正底层顺序；稳定性应在 repository 或聚合返回前完成。

### 6.5 统计聚合边界

- `usage_records` 是短期事实明细源，业务统计、额度、TopN、趋势、摘要卡片和授权消耗明细都必须由 background worker 或离线重建脚本写入预聚合表。
- API 路由、repository 请求路径、前端页面和下拉选项只能按主键、索引和筛选条件直读预聚合行；不得为了展示临时执行 `SUM`、`GROUP BY`，也不得用 `reduce` 把明细行或缓存桶再次合成为业务汇总。
- 前端可以在已返回的序列上做显示筛选、图表渲染和标签去重，但不能承担业务汇总口径；摘要数字必须来自后端预聚合字段。
- 分页明细的 `COUNT(*)`、日志搜索、表空间监控、队列字节估算和普通 UI 布局计算不属于业务用量统计，但不能借这些路径回扫 `usage_records` 生成用量。
- 如果新需求需要新的窗口、范围或组合维度，先新增 staged / window / summary 表，并由 worker 通过 `stats_job_state` 或等价游标增量写入；历史缓存可丢弃重建，不能为了兼容旧口径牺牲请求性能。

### 6.6 列表补数与缓存边界

- 列表接口的主查询必须尽量一次拿齐当前页所需事实字段；如果 DTO 组装阶段还需要按 ID 反查其他表补充展示、归属、授权来源、绑定关系、选项标签等数据，不能在 `map(row)` 中逐条查库，也不能为了补字段拉全量表。
- 低频业务资料使用正向按需缓存：账户、分组、API Key、系统账户、团队、名称、归属、低频绑定关系和授权来源等更新不频繁的数据，应在 repository / DAO lookup 层实现 `read-through`，调用方传当前页 ID，缓存命中直接返回，miss 才分批查库并写入缓存。
- 低频缓存必须有明确容量上限、TTL 和写路径失效；创建、更新、删除、绑定、授权、成员变化等会影响展示结果的写操作，要清理对应 ID 或对应缓存域。不能只依赖 TTL 等待自然过期。
- 高频业务资料使用反向主动缓存：当前并发、近期质量分、额度快照、实时运行状态、网关运行时校验、频繁变化的授权可用性等数据，如果列表需要展示，写入链路、网关副作用或后台 worker 应在事实变化时主动写入缓存或预聚合表；列表读取时先读缓存，缓存 miss 才按主键读库并回填缓存。
- 高频缓存的有效期必须跟对应后台刷新节奏对齐，不能随意设一个 TTL：例如用量统计跟随 `statsAggregationIntervalSeconds`，分组账户状态跟随 `groupAccountStatsRefreshIntervalSeconds`，账号质量跟随 `accountQualityRefreshIntervalSeconds`。后台定时任务刷新统计时，应同步补齐列表需要的缓存行、窗口行或轻量快照。
- worker 预热不能只写 worker 自己的进程内存：如果 API server、worker 和 DB service 分进程运行，worker 内存缓存不会自动被接口读取。跨进程需要共享的高频缓存，应落到紧凑的 SQLite 缓存 / 窗口表，或通过明确 IPC 让 API 进程预热；接口只读这些紧凑结果，不能因为缓存 miss 回扫大表。
- 高频数据如果无法可靠主动维护缓存，必须明确告知用户展示会有实时查询成本或统计滞后，并优先改成后台预聚合 / 窗口表 / 事件驱动缓存；不能为了赶页面在请求链路扫描明细表、现场聚合、全量反查或逐条补齐。
- 反向缓存的“全量失效”也必须是常量成本：使用哨兵、版本号或任务标记交给 worker 处理，禁止在写请求中先查询全量 ID 再逐条写脏队列。`group_account_stats_dirty` 的全量影响使用 `__all__` 哨兵作为参考实现。
- 敏感字段和易错字段不得进入通用 lookup 缓存：API Key 明文、OAuth token、代理密码、完整请求 / 响应 payload、审计正文、可导致越权的权限判定中间结果，都只能走受控读取路径；确需缓存也必须单独设计脱敏、作用域和失效策略。
- 新增列表、详情或下拉接口时，代码审查必须检查补数字段来源：哪些字段主查询已返回，哪些字段走低频正向缓存，哪些字段走高频反向缓存，哪些字段明确不缓存并说明原因。

### 6.7 校验一致

- 后端写接口必须有明确校验。
- 前端表单校验只改善体验，不能替代后端校验。
- 校验规则变化时，同步更新文档和类型。

### 6.8 复用优先

- 先查已有页面、服务、repository、工具函数和文档，再新增实现。
- 复用不代表硬套；如果已有实现不适合，应说明原因再新增。
- 不要为了“未来可扩展”提前堆抽象。

### 6.9 中文描述与协议字段边界

- 系统写死的错误返回、日志描述、脚本控制台输出、前端提示、空态、悬浮提示和说明文案默认使用中文。
- 只翻译面向人阅读的描述性内容，例如 `message`、`badRequest()` 文案、`throw new Error()` 文案、`logger.*()` 的消息文本、脚本 `console.*()` 输出和使用记录里的错误摘要。
- 不翻译机器可读或协议约定内容，例如枚举值、状态值、错误码、事件名、header、SQL 常量、缓存 key、路由路径、数据库字段值和 OpenAI / SSE 协议事件。
- 技术名词可以按语境保留原文，例如 `API Key`、`OAuth`、`Bearer Token`、`Refresh Token`、`access_token`、`HTTP`、`SSE` 和接口路径。
- 修改文案时只改描述，不顺手改协议结构、字段名、事件名、业务状态或调度语义。

## 7. 路径覆盖要求

- 功能实现不能只覆盖正向路径。
- 至少考虑：
  - 创建或提交成功
  - 参数缺失
  - 参数非法
  - 重复操作
  - 无数据
  - 依赖不可用
  - 保存失败
  - 刷新后状态恢复
  - 数据清洗或重建后的状态
- 具体业务路径如何验证，以运行手册和阶段文档为准。

## 8. 验收与验证

### 8.1 代码级验证

通用验证命令：

```powershell
pnpm typecheck
pnpm build
```

按变更范围可缩小到具体 workspace：

```powershell
pnpm --filter juhe-ai-frontend typecheck
pnpm --filter juhe-ai-backend typecheck
```

### 8.2 功能验证

- 前端变更：验证对应页面的加载、提交、错误提示和刷新。
- 后端变更：验证接口成功、失败和边界输入。
- 存储变更：验证按当前 schema 创建的新库能正常启动；旧库只做离线修复验证，不作为运行时兼容验收。
- 脚本变更：验证 dry run 或等价安全路径。
- 具体命令和样例以 [开发测试与验证说明](../develop/测试与验证说明.md) 为准。

## 9. 文档要求

- 需要跨多步推进或后续跟踪的需求：在 `docs/plans/` 新建或更新对应计划。
- 影响架构边界：更新 `docs/architecture/架构总览.md`。
- 影响阶段范围：更新 `docs/plans/` 下对应阶段计划或需求计划；当前功能事实还要同步到架构和 functions 文档。
- 影响运行或验证：按范围更新 `docs/develop/运行说明.md` 或 `docs/develop/测试与验证说明.md`。
- 影响存储：更新存储相关文档。
- 规范文档不记录某个具体需求的临时结论；临时结论应写入阶段记录或任务说明。

## 10. 无效开发信号

- 只改一层，其他类型、接口、文档不同步。
- 为简单需求引入复杂抽象。
- 新增字段没有默认值和数据处理策略。
- 错误处理只返回模糊失败。
- 依赖删除数据或手动清理才能运行。
- 具体业务流程被写进通用规范，导致规范越来越不可复用。

## 11. AI 输出要求

功能完成后建议输出：

```text
【功能范围】
- <实现了什么，不包含什么>

【主要落点】
- <前端 / 后端 / 存储 / 脚本 / 文档>

【关键设计】
- <分层、默认值、数据处理策略>

【验证情况】
- <已跑命令、手动验证、未验证项>

【风险与后续】
- <剩余限制、下一步建议>
```

禁止只说：

- “功能已完成”
- “页面已加好”
- “接口写好了”
- “后面再测”
