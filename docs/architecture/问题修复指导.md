# 问题修复指导

> 面向 AI 与维护者。
> 适用于 `juhe-ai` 的前端、后端、存储、脚本、配置和文档问题。
> 本文件只写通用排查和修复方法；具体业务问题的复现步骤、验证样例和临时结论应放在任务记录或运行手册中。

## 1. 文件定位

- 本文件位于 `docs/architecture/问题修复指导.md`，和 bug 记录目录配套使用。
- 本文件回答这些问题：
  - 修 bug 前如何定义问题
  - 如何区分表象和根因
  - 如何判断修复落点
  - 修复后如何检查影响面
  - AI 应如何交代修复结果

## 2. 核心原则

- 先复现或定位，再改代码。
- 先画触发链路，再判断落点。
- 能修根因，不修表象。
- 不用删除数据、强制刷新、延迟等待掩盖问题。
- 不把具体业务特例写入通用规范。
- 修复范围扩大时，先说明原因、风险和可选方案。

## 3. 排查流程

### 3.1 定义问题

- 先写清楚：
  - 现象是什么
  - 触发入口是什么
  - 影响范围是什么
  - 期望行为是什么
  - 实际行为是什么
  - 是否稳定复现
  - 是否影响运行或验证流程
- 如果用户提供的是结论，先还原成可验证现象。

### 3.2 查现有上下文

- 修复前优先查看：
  - 相关设计文档
  - 相关运行手册
  - 相关类型定义
  - 相关 API 和存储实现
  - 相邻模块的已有修法
- 如果文档和代码不一致，先判断是代码偏离设计，还是文档已经过期。

### 3.3 画触发链路

- 前端问题至少追到：页面、组件状态、API 请求、后端响应。
- 后端问题至少追到：路由、校验、服务、repository、存储或外部依赖。
- 存储问题至少追到：schema、默认值、迁移兼容、读写转换。
- 脚本问题至少追到：输入来源、执行环境、写入目标、失败处理。
- 文档问题至少追到：当前事实、过期内容、引用入口。

### 3.4 区分表象和根因

- 表象通常是页面显示异常、接口失败、数据缺失、状态不更新、脚本报错。
- 根因可能在字段不一致、默认值缺失、类型不同步、状态来源错误、旧数据不兼容、错误被吞掉等位置。
- 修复时要说明为什么改动落在根因层，而不是只处理表面现象。

## 4. 常见问题类别

### 4.1 前端

- 类型和接口字段不同步。
- 表单保存失败后状态丢失。
- 加载态、空态、错误态缺失。
- 筛选、刷新、弹窗、批量操作状态互相覆盖。
- 敏感字段展示边界不清。

### 4.2 后端

- 参数校验缺失或过宽。
- 错误响应不可读。
- 路由层承载过多业务逻辑。
- 副作用失败后没有回滚或没有记录。
- 外部依赖异常没有清楚分类。

### 4.3 存储

- 新字段不兼容旧数据。
- 布尔、JSON、时间、数字转换不一致。
- 敏感字段存取策略不一致。
- 删除或更新没有处理关联关系。
- 统计口径和展示口径不一致。

### 4.4 脚本与运行

- 环境变量不明确。
- dry run 和正式执行行为不一致。
- 重复执行不幂等。
- 失败后留下半完成状态。
- 日志不足以定位问题。

### 4.5 文档

- 文档写入了临时业务细节，导致规范不通用。
- 文档入口缺失或链接失效。
- 文档与当前代码事实不一致。
- 命令、路径、默认值过期。

## 5. 修改策略

### 5.1 修正确层级

- 展示问题修前端。
- 参数和响应问题修 API 边界。
- 业务规则问题修服务层。
- 数据事实问题修 repository 或 schema。
- 运行流程问题修脚本或 runbook。
- 文档问题修对应文档，不把临时结论写入通用规范。

### 5.2 不要补丁扩散

- 不要到处加条件分支来掩盖职责不清。
- 不要用重复请求、强制刷新、定时等待解决时序问题。
- 不要为单个数据样本写死特殊逻辑。
- 不要吞掉错误后只返回模糊失败。

### 5.3 允许止血，但要说明

- 如果只能临时止血，必须说明：
  - 为什么不能一次修根因
  - 哪些路径仍可能受影响
  - 后续更好的收口方案
  - 本次止血验证了哪些路径

## 6. 必查影响面

- 原问题路径。
- 同层相邻实现。
- 前后端类型和字段。
- 旧数据兼容。
- 加载、空、错、禁用状态。
- 敏感字段展示和存储。
- 脚本重复执行。
- 文档入口和运行命令。

## 7. 验证要求

### 7.1 代码级验证

- 普通修复至少运行：

```powershell
pnpm typecheck
```

- 影响构建、依赖或产物时补充：

```powershell
pnpm build
```

### 7.2 功能验证

- 前端修复：验证对应页面的加载、提交、失败和刷新。
- 后端修复：验证成功、失败和边界输入。
- 存储修复：验证新数据和旧数据兼容。
- 脚本修复：验证可重复执行和失败处理。
- 具体业务验证步骤以 [开发测试与验证说明](../develop/测试与验证说明.md) 为准。

## 8. 什么时候要明确告诉用户

- 根因是架构边界或阶段设计问题。
- 修复需要改变数据结构或历史数据。
- 修复会明显扩大范围。
- 当前只能止血，不能根治。
- 需要真实依赖或特定环境才能验证，但当前无法执行。
- 用户要求把具体业务特例写进通用规范。

## 9. 无效修复信号

- 问题消失了，但根因说不清。
- 只改一层，相关类型、字段、文档没同步。
- 删除本地数据后问题“好了”。
- 依赖强刷、延迟或重复操作才能稳定。
- 错误被隐藏，用户无法知道失败原因。
- 具体业务细节被写进规范，后续模块无法复用。

## 10. AI 输出要求

问题修复完成后建议输出：

```text
【问题定义】
- <现象、触发条件、影响范围>

【根因分析】
- <真正根因、为什么不是表面现象>

【修复落点】
- <文件或目录、为什么改这里>

【影响检查】
- <检查过的相邻路径、结论>

【验证情况】
- <typecheck/build/手动验证/未验证项>

【风险与建议】
- <剩余风险、止血说明、后续建议>
```

禁止只说：

- “问题已修复”
- “加了判断”
- “接口正常了”
- “应该没问题”
