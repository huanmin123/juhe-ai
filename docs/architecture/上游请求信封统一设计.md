# 上游探针请求信封统一设计（系统探针唯一构造源）v3

- **状态**：v3 修订稿，待审核；审核通过前不改代码。v2 复审意见及处理见 §0。
- **目标**：让系统发起的账户测试、模型检测、健康/恢复探针共用一条上游 HTTP 请求构造路径；探针内容仍由各探针族定义。
- **驱动事故（脱敏）**：一个 `profile_gpt_openai_v1` 账户在 `responses_sse` 模式下，模型检测首个 `protocol_basic` 请求收到输出预算低于上游最低值的 HTTP 400；同账户账户测试成功。具体生产账户、run 与 trace 标识留在私有运维记录，不进入架构文档。
- **范围边界**：本设计只定义系统生成的探针请求（F2–F5），不声称 `/v1` 用户请求也已使用同一构造源。若“全系统一份”要求还覆盖 `/v1`，须另行设计其透传与热路径边界；本稿不把该目标标记为已完成。

## 1. 现状事实与范围清单

| 面 | 触发场景 | 当前构造位置 | 当前预算事实 |
| --- | --- | --- | --- |
| F1 `/v1` 用户请求 | 客户端调用 | `gatewaydispatch` 请求准备；客户端 payload 原样透传并由网关准备上游目标 | 保留客户端字段。本设计不迁移，也不声称全仓请求构造已统一。 |
| F2 账户手动测试 | 用户在账户页执行测试 | `accountprobe.ManualDiagnostics` → `buildTestRequest` / `buildUpstreamURL`；执行器在 `manualtest` | 文本探针使用 `outputTokenLimit=1024`；Anthropic 使用 `max_tokens=1024`，无 `thinking` / `effort`。BUG-0201 将该形状用于 Anthropic 协议探针和手动测试。 |
| F3 模型检测探针 | 手动或定时 quick/full 检测 | `modelcheckprobe` 的协议 builder、探针族 builder 与 suite | 当前按协议和探针族不同：首个 Responses `protocol_basic` 是 `max_output_tokens=16`；Chat 有 64 下限、Gemini 有 128 下限；采样、身份、Token 完整性及 quiz 另有语义预算。不得把它们误写成一个现有值。 |
| F4 恢复与健康探针 | jobs 健康探针、gateway 恢复与冷却复测 | `exactkeyprobe` | 当前文本预算常量为 1024；需逐端点确认适用性。 |
| F5 Codex 适配器 | OAuth Codex 探针 | `modelcheckprobe` 与 `exactkeyprobe` 的 Codex 归一化 | Codex 适配会删除 `max_output_tokens` 等不接受的 tuning 字段；这是明确例外，不得强行补预算。 |

当前系统探针还覆盖以下端点及变体，不能只按四种 JSON 文本协议盘点：

| 端点 / 形态 | 已知模式或行为 | 请求体与预算边界 |
| --- | --- | --- |
| OpenAI Chat / Responses、Anthropic Messages、Gemini GenerateContent | JSON 与 SSE；SSE 路径可能带端点专属 query | JSON envelope 与协议必填字段按协议编码；预算字段名因协议而异。 |
| Gemini Interactions | `interactions_json`、`interactions_sse` | 独立 endpoint/body 语义；只有契约支持时才应用输出预算。 |
| 图片生成 | `images_json`，`POST /v1/images/generations` | 不是图片输入；按该端点自身请求字段构造，不套用文本输出预算。 |
| 音频生成与转录 | `audio_speech`、`audio_transcription_json` | 转录包含 multipart/form-data；共享构造需支持边界编码与二进制文件段。 |
| Codex Responses、Gemini Code Assist、GLM 与 gemini-openai 路径规约 | 适配器包装、路径/query、项目字段和身份头可能不同 | 作为显式端点/认证策略变体；适配器可声明能力和例外，不在调用方散落拼接。 |
| API Key、OAuth 与供应商专用认证 | 认证字段和附加头随适配器变化 | 信封构造统一应用认证策略；凭据选择仍属于账户/路由解析。 |

## 2. 事故证据链

- **生产记录所述**：账户配置为 `profile_gpt_openai_v1`、`protocol=openai_responses`、`endpointMode=responses_sse`。`protocol_basic` 三次尝试均收到 HTTP 400，错误原文为：`max_tokens=16 is below the minimum the model provider accepts (100); raise it to at least 100`。具体账户、run/trace ID 和原始日志属于私有生产记录。
- **源码可核对**：`suite.go` 为首个 `protocol_basic` 传入预算 16；Responses builder 将它编码为 `max_output_tokens=16`。同一 builder 的其他协议使用不同字段和下限。
- **尚未证实的解释**：错误文本使用 `max_tokens`，而出站 Responses 请求使用 `max_output_tokens`。这说明请求链中存在字段转换或错误规范化的可能，但不能据此断言是上游中转将 Responses 转成 Chat。内部转换路径需独立日志或可复现证据确认。
- **当前能成立的结论**：首个探针请求的输出预算小于该上游实际要求的 100，且 suite 在终止失败后跳过后续核心探针。Mock 应复现“Responses 预算不足返回同类 400、预算提高后请求可继续”的边界；真实供应商内部实现不作为该测试的前提。

## 3. 契约

1. **共享构造规则**：F2–F5 对相同的已解析目标、协议/适配器、`endpointMode` 与 body 编码使用同一请求构造实现。调用方不能另行拼接路径、标准头、认证头或协议 envelope 字段。
2. **探针内容独立**：提示词、schema、tools、图片/音频内容和采样意图由探针族提供；共享构造负责按端点契约编码它们。不同探针的 body 和预算可以不同。
3. **能力判断诚实**：共享构造只避免调用路径之间的请求形状分叉，不保证上游一定支持结构化输出、工具、特定模态或模型能力。未覆盖或上游拒绝时保留真实错误，不静默改写成成功。
4. **用户透传不变**：F1 客户端 body（包括其预算字段）继续原样透传。本设计不授权对 F1 做 body、header 或路由行为改动。
5. **范围声明准确**：实现完成后只能声称“系统生成的探针请求共用构造源”。只有另有设计并完成 `/v1` 迁移，才能声称全仓所有上游请求都只有一个构造源。

## 4. 设计

### 4.1 共享请求构造包

新增 `backend-go/shared/platform/upstreamenvelope`，由一个统一入口生成最终的 `http.Request`。调用方提供已解析的账户/供应商目标、协议 profile、`endpointMode`、认证策略及凭据引用、探针语义 body 和预算类别；不得从各自 probe 包传入已拼好的 URL、认证头或完整 envelope 来绕过共享入口。

共享包负责：

- 根据已解析 profile 与 endpoint catalog 生成 method、URL path/query、标准请求头和适用的认证头；覆盖 SSE、Code Assist、Codex、GLM/gemini-openai 等已登记变体。
- 根据 endpoint 定义验证 JSON、multipart 或音频 body 类型，序列化协议必填字段和预算字段。
- 根据 `endpointMode + probe family + adapter` 应用命名预算策略；不支持该字段的端点或适配器明确声明 `none`，不得用伪造字段兜底。
- 返回可供既有 transport/dispatcher 发送的请求对象；不持有重试、评分、结算、超时、账户选择或网络发送职责。

账户选择、凭据解密、目标供应商/profile 解析和协议转换仍由现有调用链负责。适配器只提供声明式端点、认证及能力描述；不能继续私有构造最终请求。探针族继续提供业务内容，但不得直接写 envelope 字段或序列化完整 HTTP 请求。

### 4.2 Endpoint catalog 与测试矩阵

实现前必须从当前 `accountprobe`、`exactkeyprobe`、`modelcheckprobe` 调用点形成完整 catalog。每个已支持条目至少列出 `protocol/profile`、`endpointMode`、HTTP method、path/query、body 编码、SSE/JSON 语义、认证策略、适用预算字段和明确例外。catalog 覆盖 §1 中列出的文本、Interactions、图片生成、音频、Codex、Code Assist 及供应商路径变体。

测试按 catalog 中真实支持的组合逐条覆盖，而非构造“四协议 × JSON/SSE”的虚假笛卡尔积。每个条目断言 method、最终 URL/query、认证和标准头、body 编码、协议必填字段及预算处理；对不支持组合断言明确失败。Multipart、音频响应和不支持预算的适配器各有独立契约测试。

### 4.3 输出预算策略

- **R1 用户请求**：F1 透传预算不进入本包，本设计不更改。
- **R2 系统探针**：使用共享、命名的 `BudgetPolicy`，以 `endpointMode + probe family + adapter` 决定预算字段和值。统一的是字段生成与合法性校验逻辑，不是所有探针请求必须具有相同输出上限。
- **本次故障修正目标**：Responses `protocol_basic` 使用有界预算 1024，避免当前值 16 低于已观测到的 100 下限。F2/F4 当前 1024 语义保持；其它探针族继续按其检测语义声明预算，尤其短采样/Token 统计不能被全局改成 1024。若某端点或适配器不支持预算字段，显式省略。
- **Codex 例外**：Codex 归一化会移除其不接受的 tuning 字段。策略必须表达“无预算字段”，不能要求 Codex 与普通 Responses 请求字面相同。
- **不得静默适配未知最低值**：当前 100 是该事故上游观测，不代表全供应商下限。若上游仍拒绝，保留原始状态与错误，不做无证据的重试改写或预算 fallback。

### 4.4 历史探针预算语义

各探针的输出预算是探针行为的一部分。迁移前需从 `docs/functions/模型检测设计.md` 和当前 builder 核实所有 family 的预算，包括 quick/full、身份、quiz、Token 完整性与 §17 采样统计。集中命名不等于把所有值统一为 1024。

若改变既有探针的预算并影响输出、成本、评分或证据可比性，必须同步更新对应检测契约、探针集版本和历史数据比较规则；不可只改 §1.2 的通用描述。短预算探针应保留其短预算意图，除非单独完成语义重设计和校准。

### 4.5 文档同步门禁

实现前先对照并修正各自领域的权威文档，不由本设计单方面宣布“冲突以本文为准”：

- `docs/functions/模型检测设计.md`：记录按探针族和端点划分的预算策略、quick/full 请求数量、probe set 版本，以及历史证据可比性。
- `docs/functions/Anthropic账号接入.md` 与 `docs/functions/ClaudeCode客户端画像兼容设计.md`：现有账户测试示例仍有 `max_tokens=32000`、`thinking` 或 `effort` 描述；需根据 BUG-0201 与当前 `accountprobe` 的 1024、无 reasoning enhancement 契约裁决并同步。不能仅把 32000 重新解释为“直连形态”。用户真实 Anthropic 请求的 raw passthrough 是另一条契约，需保留。
- `docs/architecture/功能开发指导.md`：新增检查项，要求系统探针使用共享构造入口并更新 endpoint catalog/契约测试。
- 其他 endpoint 专题文档：若矩阵调整其 path、header、body 或模态语义，一并同步。

## 5. 本次范围与非目标

本设计范围是 F2–F5 的系统生成探针构造。F1 `/v1` 客户端请求当前为独立透传链，本次不迁移；“不迁移”不等于永久排除，也不等于全仓已经实现单一构造源。若验收必须字面覆盖所有上游 HTTP 请求，需先补充 `/v1` 的性能边界、请求透传契约和迁移方案，再决定是否纳入代码阶段。

本设计不改模型检测评分、重试、超时、结算、调度、账户健康状态或用户 payload；不改变探针族检测内容，除 §4.3 明确的 Responses `protocol_basic` 预算修正及通过文档裁决的必要调整外，不顺带扩大行为变更。

## 7. 测试、成本与验收

1. **共享构造契约**：对 endpoint catalog 每个实际条目断言 method、URL/query、认证/标准头、body 编码、协议字段和预算策略；覆盖 Codex 无预算、multipart、SSE 与供应商路径变体。
2. **事故回归 Mock**：本地 Mock Responses 上游对输出预算低于 100 的请求返回与事故同类 400，对 1024 请求返回稳定成功。测试确认首个 `protocol_basic` 使用 `max_output_tokens=1024`，并确认请求失败仍保留真实错误；不依赖生产服务或其内部转换实现。
3. **请求数口径**：现有测试中 Responses JSON quick 基线为 11 个逻辑请求；SSE quick 因额外流式终态探针为 12 个。它们不是物理请求总数：HTTP/读取失败可触发最多三次尝试，可信对照会对另一账户执行套件，题库也会增加请求。测试按所选 profile、endpointMode、对照与题库分别断言逻辑请求数，并另测重试上限。
4. **成本口径**：不能用 `11 × 1024` 声称所有 quick run 的固定费用上限。文本预算成本按每个探针 family 的逻辑请求数、预算策略和最大尝试次数估算；图片/音频及无预算适配器单独核算。真实账单还受上游计费和实际输出影响。
5. **生产验证**：本设计不授权或要求本次访问生产。实现和 Mock 验收通过后，只有在另有明确生产操作授权与对应 runbook 时才执行限定 smoke；判据为原预算拒绝不再出现、手动账户测试行为保持、后续能力探针按真实结果评分，不要求两种测试评分相同或强行得到非零分数。
6. **回归范围**：相关 `modelcheckprobe`、`gatewaydispatch` 透传不变性、shared `accounttest` 三包及 jobs `accounthealth`。按项目测试指引运行最小充分集合并记录真实结果；不以文档审查替代实现测试。

## 8. 后续规则

1. 新增系统探针 endpoint 前先登记 endpoint catalog、请求编码、预算策略、认证变体与 Mock 契约；不得在调用方另建最终 HTTP 请求构造器。
2. Node 迁移历史不再作为当前实现 oracle。当前探针请求以本设计经领域文档裁决后的契约和实际 Go 实现为准；发生冲突时先核实证据并更新权威文档，不由单篇设计文档自动覆盖其它契约。
3. 本设计完成实施后，应与 `模型检测设计.md` 及相关账户测试/端点文档同步维护；若未来覆盖 F1，另行更新本节范围与 `/v1` 契约。
