# 功能开发指导

> 面向 AI 与维护者。
> 适用于 `sub2api-lite` 的前端、后端、存储、脚本和文档变更。
> 本文件只写通用开发方法和边界原则；具体业务阶段、模块细节和验证样例应放在阶段计划或运行手册中。

## 1. 文件定位

- 本文件回答这些问题：
  - 新功能开发前先判断什么
  - 代码应该落在哪一层
  - 新增字段、接口、页面时如何保持一致
  - 如何避免过早复杂化
  - 功能完成后如何验收和说明
- 具体模块范围以这些文档为准：
  - [architecture.md](architecture.md)
  - [phase-1-plan.md](phase-1-plan.md)
  - [dev-runbook.md](dev-runbook.md)

## 2. 项目边界

- 当前项目定位是轻量管理与中转能力，不是重型系统的逐行重写。
- 技术栈：
  - 前端：`Vue 3 + TypeScript + Ant Design Vue`
  - 后端：`Node.js + TypeScript + Express`
  - 存储：`SQLite`
  - 包管理：`pnpm workspace`
- 默认原则：先做轻量闭环，再按实际需要扩展。
- 需求变化如果影响模块边界、数据关系或阶段范围，先更新设计文档，再开始大规模实现。

## 3. 开发前先判断

### 3.1 范围判断

- 先确认本次变更属于哪些范围：
  - 前端页面
  - API 请求层
  - 后端路由
  - 业务服务
  - 存储 schema
  - repository
  - 脚本
  - 配置
  - 文档
  - 验证流程
- 不清楚范围时，先查目录和设计文档，不要直接新增平行体系。

### 3.2 边界判断

- 判断是否改变：
  - 模块关系
  - 数据对象结构
  - API 入参或出参
  - 默认值
  - 敏感字段处理
  - 错误语义
  - 验证方式
- 只要影响边界，就应同步更新文档和类型。

### 3.3 复杂度判断

- 优先选择简单、直接、可验证的实现。
- 不为尚未落地的远期能力提前引入复杂抽象。
- 不为单个功能引入重型框架、全局状态或过度封装。
- 如果发现需求会显著扩大范围，应先向用户说明方案、收益和成本。

## 4. 分层落点

### 4.1 前端

- `frontend/src/views/`：页面组合、局部交互、页面级状态。
- `frontend/src/layouts/`：应用壳和通用布局。
- `frontend/src/router/`：路由定义。
- `frontend/src/api/`：后端请求封装。
- `frontend/src/types/`：前端领域类型。
- `frontend/src/styles/`：全局样式和跨页面样式。
- 页面不要直接复制后端业务规则；复杂规则应来自 API 返回或共享类型。

### 4.2 后端

- `backend/src/server.ts`：应用初始化、全局中间件、路由挂载。
- `backend/src/modules/`：模块路由和业务服务。
- `backend/src/domain/`：领域类型。
- `backend/src/storage/`：数据库连接、schema、repository、加解密等存储能力。
- `backend/src/scripts/`：一次性脚本、导入导出、烟测等独立流程。
- routes 负责 HTTP 边界，service 负责业务逻辑，repository 负责数据访问。

### 4.3 文档

- `docs/architecture.md`：长期模块关系和架构决策。
- `docs/phase-*.md`：阶段范围和阶段完成标准。
- `docs/dev-runbook.md`：运行、验证和排障流程。
- 规范类文档只写通用规则，不写具体业务流程。

## 5. 数据和字段策略

- 新增字段前必须明确：
  - 字段含义
  - 默认值
  - 是否可为空
  - 是否敏感
  - 展示策略
  - 兼容旧数据的方式
  - 是否影响现有 API
- 前端类型、后端类型、数据库字段、API payload 必须同步。
- 敏感字段应明确存储、传输、展示和编辑边界。
- 不要通过删除本地数据来掩盖 schema 兼容问题。

## 6. 实现策略

### 6.1 单一事实来源

- 业务事实以后端和存储为准。
- 前端只做展示、输入和交互，不自行修正业务状态。
- 默认值应在后端或存储层收口，前端只负责呈现和提交。

### 6.2 副作用分离

- 外部请求、凭据处理、数据写入、后台任务、导入导出等副作用应集中在服务层或脚本中。
- 不要把复杂副作用塞进页面组件或路由回调。
- 副作用失败时要返回可读错误，避免吞掉根因。

### 6.3 校验一致

- 后端写接口必须有明确校验。
- 前端表单校验只改善体验，不能替代后端校验。
- 校验规则变化时，同步更新文档和类型。

### 6.4 复用优先

- 先查已有页面、服务、repository、工具函数和文档，再新增实现。
- 复用不代表硬套；如果已有实现不适合，应说明原因再新增。
- 不要为了“未来可扩展”提前堆抽象。

## 7. 路径覆盖要求

- 功能实现不能只覆盖正向路径。
- 至少考虑：
  - 创建或提交成功
  - 参数缺失
  - 参数非法
  - 重复操作
  - 无数据
  - 依赖不可用
  - 保存失败
  - 刷新后状态恢复
  - 旧数据兼容
- 具体业务路径如何验证，以运行手册和阶段文档为准。

## 8. 验收与验证

### 8.1 代码级验证

通用验证命令：

```powershell
cd F:\sub2api-lite
pnpm typecheck
pnpm build
```

按变更范围可缩小到具体 workspace：

```powershell
pnpm --filter sub2api-lite-frontend typecheck
pnpm --filter sub2api-lite-backend typecheck
```

### 8.2 功能验证

- 前端变更：验证对应页面的加载、提交、错误提示和刷新。
- 后端变更：验证接口成功、失败和边界输入。
- 存储变更：验证新库和旧库都能正常启动。
- 脚本变更：验证 dry run 或等价安全路径。
- 具体命令和样例以 [dev-runbook.md](dev-runbook.md) 为准。

## 9. 文档要求

- 影响架构边界：更新 `architecture.md`。
- 影响阶段范围：更新对应 `phase-*.md`。
- 影响运行或验证：更新 `dev-runbook.md`。
- 影响存储：更新存储相关文档。
- 规范文档不记录某个具体需求的临时结论；临时结论应写入阶段记录或任务说明。

## 10. 无效开发信号

- 只改一层，其他类型、接口、文档不同步。
- 为简单需求引入复杂抽象。
- 新增字段没有默认值和兼容策略。
- 错误处理只返回模糊失败。
- 依赖删除数据或手动清理才能运行。
- 具体业务流程被写进通用规范，导致规范越来越不可复用。

## 11. AI 输出要求

功能完成后建议输出：

```text
【功能范围】
- <实现了什么，不包含什么>

【主要落点】
- <前端 / 后端 / 存储 / 脚本 / 文档>

【关键设计】
- <分层、默认值、兼容策略>

【验证情况】
- <已跑命令、手动验证、未验证项>

【风险与后续】
- <剩余限制、下一步建议>
```

禁止只说：

- “功能已完成”
- “页面已加好”
- “接口写好了”
- “后面再测”
