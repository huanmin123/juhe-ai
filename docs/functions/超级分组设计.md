# 超级分组设计

> 状态：**已实施（2026-10-21）**。Go schema（`groups.group_kind` + `super_group_members`）、分组域成员接口（管理/个人/公开）、四模式写入口与 `merge` 拒绝、运行时超级分组展开、目标级失败分类与终态映射、merge→超级分组迁移命令、前端编辑器与帮助文案均已落地；§7 的 44 个 fixture 全部通过并有集合唯一性守卫（`internal/supergroupfixtures`）；旧 `merge` 运行链已按 §8 删除。2026-10-18 独立复审缺口已回填（2026-10-19）：§3.2 分组级/成员行级停用拆分口径与删除超级分组路径、§6 迁移 blocked 边界与绑定行映射、§4.2 目标分类聚合规则与成员跳过原因取值域、`priority` 后端归一口径、§7 fixture 由 32 行扩至 44 行。2026-10-22 契约变更：超级分组创建即可启用，成员数量不再作为启用或路由绑定的前置条件；`group_kind` 仍创建后固定。2026-10-24 方案B（用户裁决）：`route_rank` 语义修订——同族改名映射命中与直连命中同为 0，仅跨协议转换映射命中记 1（见 §4.2，与 [AI账户模型映射选择规则](AI账户模型映射选择规则.md) §2.4 同批交付）。
>
> 本文取代“合并路由”作为跨分组候选池的目标契约。路由策略只负责选择调度目标和调度顺序；超级分组属于分组域，负责把多个普通分组组合成一个可被路由绑定的分组目标。旧 `merge` 运行链已于 2026-10-21 删除，仅 `maintenance` 的迁移输入解析保留对存量 `mode=merge` 行的识别。

## 1. 裁决

1. 路由模式只保留 `normal`、`weighted`、`failover`、`round_robin` 四种；`merge` 从路由模式、API、前端菜单、runtime cache 和验收矩阵中退役。
2. 分组分为普通分组和超级分组。普通分组直接拥有账号；超级分组只拥有成员关系，不直接拥有账号。
3. `route_strategy_groups` 仍是路由策略到分组的唯一绑定表。路由可以绑定普通分组或超级分组，但一次路由解析只选择一个绑定目标；超级分组内部的成员展开不再表现为路由模式。
4. 超级分组只在分组域内合并成员候选。成员分组仍保留自己的授权、账号、模型能力、连接能力和成员级配额；超级分组不复制这些事实。
5. **本轮决策：第一版不支持跨 owner / 跨授权超级分组。** 超级分组与成员分组必须属于同一个 `system_account_id`，只允许组合该 owner 已有的普通分组；这满足跨普通分组候选池，但不宣称跨授权边界。要支持跨授权，必须另立显式授权引用、配额归属、撤权即时生效和审计设计，不能用成员表绕过授权门。

## 2. 概念和边界

| 对象 | 责任 | 禁止承担 |
| --- | --- | --- |
| 普通分组 | 账号成员、账号级调度、分组启停、授权和分组级调度参数 | 不保存供应商字段，不保存路由模式 |
| 超级分组 | 成员普通分组集合、成员顺序、成员启停和组合级展示身份 | 不直接绑定账号，不复制成员授权/配额/模型，不嵌套超级分组 |
| 路由策略 | 四种路由模式、路由绑定顺序、权重、主备和轮询状态 | 不把多个分组扁平合并成 `merge` 池 |
| API Key | 选择一条路由策略 | 不保存超级分组成员关系 |

路由和超级分组的关系固定为：

```text
API Key -> 路由策略 -> 普通分组/超级分组 -> 普通分组成员 -> AI 账户 -> 供应商/协议能力
```

超级分组只是一种分组目标。它不新增 API Key 字段，不新增路由模式，不改变 API Key 到路由策略的唯一入口。

## 3. 目标数据模型

### 3.1 `groups`

供应商重构删除 `groups.provider_code` 后，增加目标字段：

| 字段 | 约束 |
| --- | --- |
| `group_kind` | `standard` 或 `super`，非空；缺省为 `standard` |
| `group_type` | 继续表达 `personal` / `high_concurrency` 等调度类型；不承担组合身份 |
| `system_account_id` | 超级分组和其成员普通分组必须相同 |
| `is_default` | 只有普通分组可以为默认分组；超级分组禁止 `is_default=1` |

普通分组继续通过 `group_accounts` 绑定账号。超级分组不得存在任何 `group_accounts` 行（包含 disabled 行）；写入接口发现该行必须在同一事务中拒绝，不得静默把账号提升到超级分组。

### 3.2 `super_group_members`

```text
id                 TEXT PRIMARY KEY
super_group_id     TEXT NOT NULL REFERENCES groups(id)
member_group_id    TEXT NOT NULL REFERENCES groups(id)
priority           INTEGER NOT NULL CHECK(priority >= 0)
enabled            BOOLEAN/INTEGER NOT NULL
created_at         TEXT NOT NULL
updated_at         TEXT NOT NULL
UNIQUE(super_group_id, member_group_id)
UNIQUE(super_group_id, priority)
```

写入事务必须同时验证：

- `super_group_id != member_group_id`；
- 目标行的 `super_group_id` 是 `group_kind=super`，`member_group_id` 是 `group_kind=standard`；
- 两行的 `system_account_id` 相同；
- 任何超级分组允许 0..20 个成员行；成员行 enabled/disabled 都计数，成员数量不构成启用条件；
- `priority` 为**后端归一**字段（客户端契约钉死口径）：客户端可提交任意非负整数，允许重复、不要求连续；负数或非整数按 `400 super_group_member_invalid` 拒绝。后端在写入事务内按提交 `priority` 升序（同值时按 payload 数组顺序稳定排序）把成员归一为连续 `0..n-1` 保存，GET/PATCH 响应回显归一值；`0..19` 的实际取值范围由「最多 20 行」自然保证，存储层 `CHECK(priority >= 0)` 只兜底非负。归一化方向与旧 merge 基线「保存按行序归一化 priority」一致（见 [合并路由设计](合并路由设计.md) §B3，2026-09-27 口径），数值域以本文 `0..n-1` 为准；
- 不能重复成员、不能形成任何嵌套链、不能把已删除或无权访问的分组加入成员表；
- 成员增删、启停和顺序调整与超级分组更新在同一事务中全成全败。
- 成员增删、启停和顺序调整不改变超级分组自身 enabled 状态；未配置 enabled 成员时目标在运行期不可用。
- `group_kind` 创建后固定：普通 `PATCH` 和产品入口都不提供 `standard` ↔ `super` 互转。如需改变形态只能新建分组。
- `super_group_members.super_group_id/member_group_id` 使用 `ON DELETE RESTRICT`。
- **分组级停用/删除/改类型的引用冲突**：被超级分组引用为成员的普通分组，在分组级停用（`groups.enabled=0`）、删除或改类型（`group_kind` 创建后固定，当前没有可达写入口）前，必须先解除全部成员引用，否则写入口返回 `409 super_group_member_reference_conflict`。
- **成员行级停用不触发引用冲突**：超级分组成员绑定行自身的 `enabled=false` 不返回 `super_group_member_reference_conflict`，不要求先解除引用，运行期按 §4.2 跳过该成员（oracle 见 fixture `dispatch-member-skip`）。边界说明：「分组禁用」指 `groups.enabled=0`，作用于分组对象整体，影响该分组参与的一切路径；「成员行禁用」指 `super_group_members.enabled=false`，只作用于某一个超级分组内的一条成员绑定行。两者校验路径不同，不得混用。
- **删除超级分组自身**：其成员行在同一删除事务内先行清除（先删除该分组的全部 `super_group_members` 行，再删除 `groups` 行），不要求调用方先经 PATCH 清空成员；既有分组删除守卫（如路由绑定检查）先于成员行清除执行，数据库层 `ON DELETE RESTRICT` 仅拦截绕过应用事务的直接删除路径。

路由目标可用性固定为：`groups.enabled=1` 且 `group_kind=standard` 时至少存在一个 enabled 的 `group_accounts` 行；`group_kind=super` 时至少存在 1 个 enabled 的 `super_group_members` 行，0 个时目标不可用。超级分组目标不因成员暂时没有可承接账号而被写入禁用状态，运行时按 §4.2 返回目标不可用并交给外层模式处理。

超级分组可以被多个路由策略复用；成员普通分组也可以被多个超级分组复用。成员停用按上述拆分口径区分层级：分组级停用（`groups.enabled=0`）在被引用为成员时被 `409 super_group_member_reference_conflict` 拒绝，不存在“停用后自动跳过”；成员行级停用（`super_group_members.enabled=false`）不会自动删除超级分组、不触发引用冲突，只使该成员在运行时被跳过。删除成员分组必须先解除引用。若所有 enabled 成员都不可用，超级分组作为本次路由的不可用目标处理。

### 3.3 成员调度指纹

成员必须使用相同的调度类型和高并发调度策略指纹。指纹不是客户端字段，由后端从当前普通分组事实计算：

```text
group_dispatch_fingerprint = SHA256(canonical_json({
  "group_type": group.group_type,
  "scheduling_policy_json": group.scheduling_policy_json
}))
```

规范化固定为 UTF-8、对象 key 按字节序升序、数组保持业务顺序、无空白、数字使用 JSON 最短表示、非 ASCII 不转义；算法版本固定为 `group-dispatch-fingerprint:v1`，版本前缀作为哈希输入的第一段。现有数据模型没有独立的 `queue_policy_json` / `concurrency_policy_json` 列；队列与并发策略键（`maxQueueSize`、`maxQueueWaitMs`、`perApiKeyQueueLimit`、`defaultSoftConcurrency` 等）都位于 `scheduling_policy_json` 内，指纹按该列整体取值即覆盖，不新增列。成员写入时在同一事务内读取全部成员的指纹，任一不一致返回 `400 super_group_member_dispatch_policy_mismatch`。普通分组的上述字段发生变化时，必须重新校验所有引用它的超级分组；校验失败的更新返回 `409 super_group_member_dispatch_policy_conflict`，不允许留下不一致关系。

## 4. 运行语义

### 4.1 路由策略只选目标分组

四种路由模式的分组选择保持原职责：

- `normal` 只能绑定一个目标分组；该目标可以是普通分组或超级分组。
- `weighted`、`failover`、`round_robin` 可以绑定多个目标分组；每次请求先按路由模式选择一个目标分组，再进入该目标分组的账号调度。
- 路由模式之间不共享成员候选池；一个超级分组的成员展开不把另一个路由绑定目标的账号带入当前候选。
- 路由级会话亲和绑定目标 `group_id`。命中超级分组时，亲和边界是超级分组本身；成员分组不改变路由级黏性边界。

### 4.2 超级分组展开

路由选中超级分组后，分组解析器按 `priority ASC, member_group_id ASC` 读取 enabled 成员，逐成员执行现有分组访问、授权、账户状态、连接/协议能力、模型支持和映射过滤，再把可用账号交给现有 dispatch/session/health/capacity 管道。

- 只合并当前请求模型和 endpoint 能力可承接的账号；供应商不参与成员资格判定。
- 每个账号候选先计算 `route_rank`：直连模型命中与同族改名映射命中（映射行 source 与 target/upstream endpoint family 相同）为 `0`，跨协议转换映射命中（两族不同）为 `1`（2026-10-24 方案B：同族改名只是管理员声明的别名，调度不在其内部再降级）。同一账号重复出现时，保留最小 `(route_rank, member_priority, member_group_id)` 的出现，并用该出现的 `member_group_id` 记账；因此后面的 direct 命中可以胜过前面的 mapping 命中。
- 全局候选排序键唯一固定为：`route_rank ASC -> existing account dispatch comparator -> member_priority ASC -> member_group_id ASC -> account_id ASC`。成员顺序只在既有账号调度比较器完全相等时决胜，不形成路由主备偏置。
- 成员分组不可用时跳过该成员；仍有其他成员可用则继续。超级分组目标失败分类固定为：`no_candidate`（过滤后没有候选）、`capacity_exhausted`（候选存在但全部被配额/并发拒绝）、`upstream_exhausted`（候选存在但全部在语义提交前 transport/protocol 失败）或 `non_replayable`（已提交语义或不可安全重放）。前三类且请求仍可重放时，外层模式沿一次性目标快照继续下一个目标；`non_replayable` 立即结束，不得切换。
- 目标级分类按全体成员失败原因聚合，单目标判定顺序固定：任一候选已提交语义或不可安全重放 → `non_replayable`（立即结束）；否则未产生任何候选 → `no_candidate`；否则存在被配额/并发拒绝的候选 → `capacity_exhausted`（即使同时存在 transport 失败候选，capacity 优先，与外层终态“任一目标 capacity → 429”的优先级一致）；否则全部候选为语义提交前 transport/protocol 失败 → `upstream_exhausted`。
- 审计成员跳过原因取值域固定为四个值，逐成员写入：`member_disabled`（成员绑定行 `enabled=false`，未进入展开；定义归属 §3.2 成员行级停用口径）；`no_candidate`、`capacity_exhausted`、`upstream_exhausted`（定义归属本节目标级失败分类，成员级取同一语义的单成员投影，目标级分类即全体成员原因的聚合）。成员失败若构成 `non_replayable`，目标立即终止，不逐成员写跳过原因，按目标级分类记录。
- 外层终态固定为：所有目标 `no_candidate` 返回现有 `503 model_target_group_unavailable`；至少一次 `capacity_exhausted` 且无成功返回现有 `429 rate_limit_exceeded`；其余可重放候选耗尽返回 `503 upstream_candidates_exhausted`；`non_replayable` 保留当前协议/传输终态。`normal` 没有下一个目标，直接按同一分类返回。
- 超级分组不产生 `route_source=merged`、`merge` 或“无分组回退”专属字段；审计写入 `route_group_id=超级分组`、`member_group_id=实际成员分组` 和成员跳过原因。

### 4.3 配额、并发和记账

- 成员分组的授权门、组级配额、账号配额和账号并发门仍按实际成员分组执行；超级分组不新增聚合配额。
- 第一版超级分组不得混合不同 `group_type` 或不同高并发调度策略指纹的成员。写入时必须拒绝不一致成员，避免准入容量和队列语义无定义。
- 用量和尝试级审计按实际服务账号的成员分组记账；请求级审计同时保留超级分组 `route_group_id`，不得把超级分组伪装成实际成员分组。
- 速度优先运行态的路由作用域使用 `route_strategy_id + route_group_id`；账号健康和配额状态仍使用实际 `member_group_id`。不复用旧 merge 的窗口组概念。

## 5. API、权限和前端契约

- 路由策略 mode 只接受 `normal`、`weighted`、`failover`、`round_robin`；提交 `merge` 或任意 `merge*` 配置键统一返回 `400 {code:"unsupported_route_mode",message:"不支持的路由模式"}`，管理、个人、公开三套写入口完全一致。
- `POST /__aisys__/api/groups` 与 `POST /__aisys__/api/my-groups` 接受可选 `groupKind`（`standard` 或 `super`，缺省 `standard`）；`groupKind` 创建后不可经普通 `PATCH` 修改；超级分组禁止 `isDefault=1`，且不得直接持有 `group_accounts` 行。
- 所有路由策略 group options 的字段白名单统一为 `id`、`name`、`groupKind`、`enabled`；不返回或接受 `providerCode`。超级分组编辑器的成员 options 只返回 `id`、`name`、`groupKind=standard`、`enabled`，不返回账号、供应商或用量字段。
- 路由策略编辑器不展示“合并路由”。超级分组选项在普通分组候选中以一个目标分组显示，详情页另行展示成员数量和成员启停摘要。
- 管理面：`GET /__aisys__/api/groups/{id}/super-members`、`PATCH /__aisys__/api/groups/{id}/super-members`；个人面：`GET /__aisys__/api/my-groups/{id}/super-members`、`PATCH /__aisys__/api/my-groups/{id}/super-members`。GET 返回 `{data:{superGroupId,groupKind:"super",revision,members:[{memberGroupId,memberGroupName,priority,enabled,groupEnabled}]}}`；PATCH 严格只接受 `{expectedRevision,members:[{memberGroupId,priority,enabled}]}`，语义为完整替换成员集合，成功返回同一摘要和新 `revision`，no-op 不推进 revision。`revision` 是分组 `updated_at` 的单调毫秒时间戳（不透明字符串）；成员变更与分组更新共用同一版本基准。
- 管理面 GET/PATCH 需要 `super_group_members:read/write` 且管理员可指定 `systemAccountId`；个人面固定当前 owner，需要 `my_super_group_members:read/write`。两面都必须通过 owner、资源可见、成员可管理和同 `system_account_id` 校验；授权可见但无管理权的成员只能出现在读下拉中，不能写入。公开面 `POST /__aipublic__/group/super-members/update` 严格接受 `{targetUsername,superGroupId,expectedRevision,members:[{memberGroupId,priority,enabled}]}`，需要 scope `juhe_ai_public:group_super_members_update:write`，规则与管理面相同。
- 成员关系错误码固定：`group_kind_conflict`、`super_group_member_invalid`、`super_group_member_limit`、`super_group_member_owner_mismatch`、`super_group_member_unauthorized`、`super_group_member_nested`、`super_group_member_dispatch_policy_mismatch`、`super_group_member_dispatch_policy_conflict`、`super_group_member_reference_conflict`、`super_group_revision_conflict`。HTTP 映射为校验错误 `400`、权限 `403`、不存在 `404`、引用/CAS `409`；错误体固定 `{code,message}`。
- 超级分组编辑器提供成员添加、删除、启停和顺序调整；不提供账号直接添加、供应商筛选或跨所有者成员选择。成员更新与 revision CAS 在同一事务中全成全败。
- 分组列表的超级分组行操作按权限平铺展示「编辑 / 成员 / 删除」，不设「更多」菜单，成员入口不得在行内和菜单中重复出现；普通分组行操作同样按权限平铺展示「编辑 / 删除」。
- 使用记录和审计列表增加 `routeGroupId`、`memberGroupId`；不再新增或展示 `routeSource=merged`。

## 6. 迁移规则

旧 schema 中的 `route_strategies.mode='merge'` 不进入新运行时。迁移器必须为每条 merge 策略生成或复用一个**同一迁移批次内由本策略生成的**超级分组，并把该策略改写为一个绑定超级分组的 `normal` 策略；不得按名称或成员集合复用用户手工创建的超级分组：

1. 读取原策略全部 active/disabled 分组绑定并映射为 `super_group_members`：active 绑定行 → 成员行 `enabled=true`；disabled 绑定行 → 成员行 `enabled=false`（保留为草稿成员行，计入 20 行上限，不参与运行展开）。`priority` 按 §3.2 归一口径由迁移器按绑定行序归一为连续 `0..n-1`；
2. 绑定数量为 0、绑定数量为 1、映射后 `enabled=true` 成员数不足 2、绑定总行数超过 20、成员跨 `system_account_id`、成员本身是超级分组、成员授权/字段不一致或成员不存在时，写入 manifest 的 `blocked`，不得自动截断、拆分或降级；
3. 生成的超级分组保留原策略 owner，成员普通分组 ID 原样保留；
4. 将原 `route_strategy_groups` 替换为一条 `normal` 绑定，API Key 的 `route_strategy_id` 保持不变；
5. 迁移完成后，运行时和写入口都不得再识别 `merge`。未解决的 merge 行使迁移阻断计数，不允许带着旧模式上线。

迁移产物守卫（仅约束历史 merge 迁移器产物，不代表当前超级分组写入口契约）：迁移器禁止生成 `enabled=true` 成员数少于 2 却已启用或被路由绑定的超级分组，不得生成绑定 disabled 超级分组的 `normal` 策略。因此任一 merge 策略只要映射后 enabled 成员不足 2（含绑定 0 条、绑定 1 条，以及多绑定中 active 绑定不足 2 的情形），一律整体 `blocked`，由人工补足成员或改写策略后重跑；迁移器不得自行把此类策略降级为绑定单个普通分组的 `normal` 策略。blocked 判定只看映射后 `enabled=true` 的成员数，disabled 绑定行映射产生的 `enabled=false` 草稿行不参与该判定。

上述第 1-4 步与 manifest 的 `mapped` 记录必须在同一业务库事务内完成；任一成员、owner、指纹、唯一键或守卫校验失败，整笔事务回滚，不能出现策略已改写而成员表未写完的半迁移状态。SQLite/PG 的跨文件差异遵循供应商重构设计 §10，但同一业务文件内仍必须满足单事务。

生成超级分组的稳定名称和复用键固定为 `migration-super-group:<source_route_strategy_id>` 与 `(system_account_id, migration_batch_id, source_route_strategy_id)`；同一批次重复执行只允许命中同一生成行，发现同名但来源策略不同或字段不一致时计入 `groups_blocked`，不得覆盖或合并。

迁移 manifest 至少记录 `source_route_strategy_id`、`source_binding_ids[]`、`target_super_group_id`、`target_member_group_ids[]`、`target_route_mode=normal`、字段来源和阻断原因。迁移不得复制账号、授权、模型或配额事实。


迁移命令入口固定为 `juhe-ai-maintenance --migrate-merge-super-groups --migration-batch-id <id> --dry-run --manifest-out <path>`；去掉 `--dry-run` 时必须同时提交 `--node-stopped --go-stopped --backup-confirmed`，正式执行在单个业务事务内完成。存储形态与其它 maintenance 命令一致：`--driver postgres --dsn` 或 `--driver sqlite --paths "business=<业务库文件>"`（只强制 `business=` 键，其余键接受并忽略），两种方言共用同一迁移器与事务语义。
