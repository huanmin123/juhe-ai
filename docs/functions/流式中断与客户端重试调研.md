# 流式中断与客户端重试调研

> 记录时间：2026-05-05。
> 当前版本启用通用 `openai` 供应商和 `gpt` 子供应商；对外主要面向 OpenAI 兼容协议客户端，其中 GPT/Codex 是重点客户端策略。
> 2026-08-01 现行规则：通用 OpenAI / Anthropic / Gemini 客户端不解释上游状态、错误对象、错误类型、错误码、完成状态或正文；所有端点的完整非 `2xx`、未知 transport、timeout 和正文中断都在当前 attempt 终止并返回实际失败，资源/副作用请求不设例外。只有用户显式命中的 `retry_next` 策略才授权在未语义提交的安全边界内重放；Codex、Claude Code、Gemini CLI 精确画像只按协议声明的失败事件结构呈现当前失败。普通 `2xx` payload 和 generic SSE 事件透明；`semanticCommitted` 后禁止服务端自动重放或拼接第二响应，只能稳定结束或断流，由客户端的新请求重新选号。
> 2026-07-10 与 2026-06-29 的“通用客户端统一 503 / 流内失败都进入响应检查”口径已被 PLAN-0134 取代，仅保留为历史背景。
> 2026-06-29 补充：当前不保留旧 SSE 专项策略入口；管理端策略和账户级追加规则统一使用响应语义检查。

## 1. 背景

网关流式响应分两个阶段：

- 首段内容到达前：客户端还没有收到模型输出；真实上游 attempt 失败仍默认终止当前请求，不得据此切换账号。只有显式命中的 `retry_next` 策略可在对应 lane、安全重放和预算边界内切换候选。
- 首段内容到达后：客户端已经收到部分输出，且可能已经写入会话历史、UI 状态、turn state 或内部缓存。服务端不能安全换账号续写或拼接第二次上游请求，否则会产生重复内容、分叉上下文、响应 ID / usage 不一致等问题。

因此，“输出停顿上限”是每次流式 attempt 的 raw chunk 空闲阈值；文本 lane 默认 30 秒，图像 lane 默认 120 秒。SSE 注释、心跳、reasoning、tool call delta 和其他上游 chunk 都会刷新原始数据计时。网关自己的等待注释只设置 `transportCommitted`；真实协议事件或正文写出后才设置 `semanticCommitted`。所有请求的 transport、timeout 或读取失败都返回当前失败；仅显式 `retry_next` 策略能在语义提交前授权重放，语义提交后任何请求都不能静默拼接第二条上游流。

## 2. OpenAI / Codex 结论

当前客户端重试策略不把 Codex 行为外推给所有 OpenAI-compatible 客户端。客户端画像和下游协议只决定当前失败的最终呈现：Codex Responses、Claude Code Messages 和 Gemini CLI stream 使用对应协议事件；通用客户端在传输未提交时返回 HTTP 错误，已经提交 SSE 传输时直接断流。普通完整 `2xx` 和 generic payload 保持透明；建流前的完整非 `2xx`、未知 transport、timeout 和正文中断均终止当前 attempt，不按状态码或正文推断切换候选。图片、音频、文件、资源、后台任务和 hosted tool 同样不设隐式切换例外；只有精确命中的 `retry_next` 策略才可授权重放。

### 2.1 通用重试协调矩阵

| 客户端 / 下游协议 | 下游未提交 | 下游已提交 | 说明 |
| --- | --- | --- | --- |
| Codex / Responses SSE | 当前失败按 Responses 协议事件呈现 | `response.failed` 后结束 | 只有精确命中 `retry_next` 时才在语义提交前重放 |
| Claude Code / Messages SSE | 当前失败按 Anthropic 协议事件呈现 | Anthropic `event: error` 后结束 | 不透传或重写为候选耗尽语义 |
| Gemini CLI / Gemini SSE | 当前失败按 Gemini 协议事件呈现 | Gemini 协议错误事件后结束 | 不按上游错误字段推断切换 |
| 通用 OpenAI / Anthropic / Gemini 流式安全文本 | HTTP / transport 当前错误；generic SSE 事件原样转发 | 直接断流 | 未命中显式策略时不切换候选 |
| 非流式安全文本 | 当前 HTTP / transport 错误；普通 `2xx` 透明 | 正文已输出后直接断开 | 不能在半截 JSON 后拼接第二次响应 |
| 图片、音频、文件、资源、后台任务、hosted tool 与其他副作用请求 | 当前错误终止 | 已提交时结束或断流 | 不设隐式重放例外 |

请求级安全原地重试、候选切换与最终客户端信号是三个独立层次：

1. 未命中显式策略时，兄弟 Key、后续账号和后续分组都不能因失败自动尝试。
2. 精确命中账户错误处理策略 `retry_next` 后，才可在策略定义的安全边界内切换 Key、账号或分组。
3. 语义提交后，无论策略、端点或客户端画像如何都不能重放、续写或拼接第二响应。
4. 失败诊断可记录在审计和用量记录中，但不能把未验证的失败推断成共享账户状态或隐式切换资格。
5. 下游按客户端协议呈现当前失败；客户端是否新发请求由客户端决定，新请求重新按当时配置选路。

普通路由 `speed_first` 与本节无关：它只根据首字延迟样本确认慢请求，不因普通上游失败立即写状态，也不覆盖或重置整请求安全原地重试 token。

错误码策略：

> 以下为 2026-08-01 前的策略背景；现行规则以本文顶部和第 1、2 节为准。

- 服务端内部重试耗尽后统一使用稳定网关码 `upstream_retryable_error` 表达“服务端候选已耗尽，建议客户端重试”；精确客户端 profile 通过对应协议事件承载，普通客户端通过 HTTP `503` 承载。该码不承诺保留下游可见的原始上游错误语义，原始失败原因只保留在使用记录、审计和上游响应快照里。
- `upstream_stream_idle_timeout`、`upstream_stream_interrupted` 只保留为内部原因分类；精确客户端无论输出前后，只要网关仍能写入失败终态，都使用 `upstream_retryable_error` 作为下游稳定码。
- 当前不再维护终止类错误码白名单；可识别流式失败先按下游写出边界做服务端内部重试，耗尽后统一使用 `upstream_retryable_error`，不区分 `context_length_exceeded`、`insufficient_quota`、`usage_not_included`、`invalid_prompt`、`cyber_policy` 或其他上游错误码。
- `server_is_overloaded` / `slow_down` 说明了不能直接透传上游错误码：Codex 源码会把这两个原始码视为不可重试。网关因此只发送稳定网关码，但该原则适用于所有客户端的最终兜底，不构成 Codex 专属调度分支。

历史运行时落点（不适用于 2026-08-01 现行规则）：

- 如果上游已经返回 `2xx + SSE`，网关会立即把响应头和后续 SSE 事件转发给客户端，不再为了“首段上游内容”预读并阻塞下游。
- 首段上游内容到来前按最终 lane 使用首响应档位：文本 120 秒，图像 600 秒；语义尚未提交时，各类请求的 transport failure 都按同一边界切换后续候选。lane 只决定单次 attempt 的时限、整请求墙钟和并发，不决定切号准入。
- 首段上游内容到来后按 lane 使用 raw chunk 停顿档位：文本 30 秒，图像 120 秒。持续发送任意 chunk 会刷新计时；任意 lane 在语义提交前的失败都可服务端有界救回。图片 idle 超时终止当前候选 attempt，下游未提交且图片墙钟仍有余量时继续后备候选，已写出则结束或断流。
- 未提交单次 attempt 最大寿命按文本 1800 秒、图像 3600 秒设置；活跃且已提交语义的 SSE 不再因固定 1800 秒机械中断。
- `noAvailableAccountWaitTimeoutSeconds` 控制独立的 `ServerRetryBudget`，默认 270 秒，只累计零可派发、受控半开和 FIFO / 并发槽等待；真实上游 attempt 和活跃读取不消耗该累计等待预算。`GatewayRequestWallBudget` 从请求接收贯穿 Key、账户、分组、排队、attempt 和切换决策且不暂停：文本固定默认 270 秒，图片由 `imageRequestWallTimeoutSeconds` 控制且默认 3600 秒，二者都不能从等待预算派生。
- 流式转发 catch 分支按客户端画像和下游协议结束响应：精确客户端写对应协议失败事件，通用客户端在已提交后断开连接。
- 精确客户端正常 EOF 但没有协议终止事件时，任意 lane 在 `semanticCommitted = false` 且预算允许时都可按协议失败由服务端救回。通用客户端不解释缺少终止事件，按上游原始 EOF 收口。
- 精确客户端在语义提交前收到 `response.failed` 或对应协议 `event: error` 时，经过响应检查后可有界切换候选；通用客户端原样接收该事件，不改写为 `upstream_retryable_error`。协议事件结构只证明当前 attempt 失败，不授权共享状态。
- 上游在建流前返回完整 HTTP 非 `2xx` 时，所有通用请求只按 `response.ok=false` 做内容无关的请求级候选接管，不写共享状态；资源/副作用请求同样在下游未提交时继续候选，已提交时只能结束或断流。精确客户端画像还可以按协议声明处理结构失败，但用户显式状态策略不建立第二套切号规则。
- 该失败事件也加入响应快照 chunks，便于使用记录保留完整链路。
- `frontend/src/views/settings/SettingsView.vue` 中“输出停顿上限（秒）”只说明行为，不在说明文案里重复默认秒数。

## 3. OpenAI Responses 流式兜底方案

> 本节保留旧方案调研和客户端协议证据。凡提到“有界候选切换”“候选耗尽”或 `upstream_retryable_error` 的运行时描述，均已被顶部的“仅显式 `retry_next` 可重放”规则取代。

### 3.1 问题定义

2026-05-13 排查确认过一种特殊失败形态：上游返回 `200 + text/event-stream`，但 SSE 事件内出现 `error.code = server_is_overloaded` 或 `slow_down`。这类失败不是 HTTP 非 2xx，不能只靠账户错误处理策略识别。后续又确认过通用 `event: error`、缺少终止事件和上游读取中断等形态，本项目最终把处理边界收敛为“是否已经产生可见输出”，而不是围绕单个错误码或单个场景分别补偿。

Codex 对 `response.failed` 的处理有明确分支：如果 `data.type = "response.failed"` 且 `response.error.code` 是 `server_is_overloaded` 或 `slow_down`，会映射为 `ServerOverloaded`，客户端展示 `Selected model is at capacity. Please try a different model.`，并且 `is_retryable()` 为 `false`。所以如果网关把这两个原始错误码透传给下游，Codex 不会自动重试。

当前运行时采用“下游实际写出边界 + 客户端策略”兜底：不围绕单个 SSE 错误码维护特征规则，而是把所有可识别流式失败统一放到下游写出边界下处理。`response.failed` 事件格式由 `clientProfile = codex + downstreamProtocol = responses_sse` 决定；稳定网关码 `upstream_retryable_error` 也可以由其他精确协议事件或通用 HTTP `503` 承载。Codex profile 只接受普通 JSON 对象格式的 `x-codex-turn-metadata.turn_id`，不接受 `turnId`、URL 编码 JSON 或数组 JSON；未识别到 Codex 时不启用 turn 级避让，但仍执行通用候选扫描和客户端重试协调。

### 3.2 安全边界

项目内按输出边界区分服务端候选切换与客户端新请求：

- 语义提交前候选切换：`semanticCommitted = false` 且端点允许自动重放时，网关可在请求级去重、64-attempt、总墙钟和最终响应保留约束内切换后续 Key、账号或分组。已派发的图片、音频、文件、资源、后台任务、hosted tool 等副作用请求即使尚未输出也禁止隐式重放。
- 语义提交后终止：`semanticCommitted = true` 后，客户端已经看到模型输出、工具参数或执行状态变化；网关禁止自动继续、重新派发或拼接第二条上游流。精确客户端可在尚无终态时收到一个失败终态，其他情况稳定结束或断流；真正的重试必须形成新的 HTTP 请求。

客户端自动重试由客户端自己控制次数，网关只在可重放文本的服务端内部候选耗尽后，按对应客户端 profile 给出可重试的协议失败信号。服务端内部候选切换受当前候选账号、分组、整请求墙钟和 attempt 上限限制；图片和其他副作用请求派发后不进入该循环。如果服务端链路仍失败，返回给客户端的是按客户端能力生成的最终失败，而不是把中间账号失败逐个下发。

因此，流式自动重放安全边界不是“是否已经发过任意 SSE 事件”，而是“是否已经向下游提交可见输出或会改变客户端执行状态的 delta”，并且还必须先确认请求端点本身允许重放。所有 UI 文案、配置项、日志、审计字段、计划文档和后续实现都必须明确：语义提交前只能做有界候选切换，语义提交后禁止服务端自动重放。

下列事件不视为 `outputSeen`：

- `response.created`
- `response.in_progress`
- `response.metadata`
- 模型、限流、header 类元信息
- SSE 注释、心跳或其他不产生可见输出的事件

下列事件一旦写给下游，就必须视为 `outputSeen = true`：

- `response.output_text.delta`
- 工具调用参数 delta，例如 `response.custom_tool_call_input.delta`，以及后续新增客户端策略时可能出现的等价 tool/function argument delta
- `response.reasoning_summary_text.delta`
- `response.reasoning_text.delta`
- 任何携带可见 assistant 文本、工具调用参数或可执行状态变化的 `response.output_item.added` / `response.output_item.done`

只有服务端内部候选切换耗尽后，才允许把上游流式失败转换为客户端可重试信号。下游尚未语义提交时，即使解析器已在预提交缓冲中识别到可见输出，各类请求仍可在对应 lane 预算内丢弃缓冲并切换后续账号；已有真实协议内容写给下游后不再按错误码豁免、伪造整轮重试或自动继续。

### 3.3 策略兜底模型

此前讨论过的流式错误码特征规则已下线，不进入系统设置页，也不开放给管理员临时配置。经过 `server_is_overloaded`、`slow_down`、通用 `event: error`、缺少终止事件和上游读取中断等样本复盘后，当前运行时不再维护流式错误码特征白名单，也不保留空的流式规则接口或前端页签，而是按可见输出边界和客户端策略处理：

- transport 失败且 `semanticCommitted = false`：所有请求按对应 lane 有界预算切换后续账号 / 后续分组；安全原地重试 token 仅适用于文本主派发已开始、响应头前 transport failure。
- 精确客户端协议失败且 `semanticCommitted = false`：各类请求都可以按其策略由服务端切换候选；`generic_*` 不解释该语义并原样转发。
- `semanticCommitted = true`：不按错误码设置服务端重放例外，也不拼接第二条上游流。精确客户端在尚无协议终态且下游仍可写时允许追加一个脱敏失败终态并结束；通用客户端或失败终态不可写时断流。
- 可见输出判断由 `openAIStreamEventHasVisibleOutput()` 统一提供，流式解析器和兜底判断必须复用同一函数，避免账号副作用与下游改写边界不一致。
- 失败事件识别只在精确客户端画像下认协议声明的失败事件结构，例如 Responses 的 `response.failed` 或 Anthropic 的 `event: error`；generic 事件以及普通 payload 中的 `error`、`data.error`、`code`、`type` 或 `message` 始终透明，不触发失败兜底。
- 响应语义检查策略只在精确客户端画像下执行；新增规则类型、只读接口、前端展示或回归前，必须先证明现有边界无法覆盖。通用客户端不因任何响应字段进入该管线。
- 配置化流式策略把前端配置收敛为“数据处理、是否重试、账号避让、账户状态”四类意图，执行层继续受可见输出边界和客户端协议能力约束。

### 3.4 网关处理流程

流式转发不能只做原始字节级 `pipe` 后再字符串替换。要稳定执行可见输出前兜底，网关必须按 SSE 事件边界解析并在写下游前决策。

处理流程：

1. 上游返回 `2xx + text/event-stream` 后，网关进入 SSE 事件解析转发模式。
2. 每个完整 SSE 事件先解析 `event:`、`data:` 和 `data` JSON；解析失败或超限时按既有流式中断策略处理。
3. 写下游前更新 `outputSeen` 候选判断；只有会产生可见输出或工具状态变化的事件才置为 `true`。
4. 只有精确客户端画像下协议声明的失败事件结构才进入失败决策；generic 事件和仅携带 `error/code/type/message` 字段的普通 payload 原样转发。
5. 可见输出前失败时，禁止把原始事件继续写给下游，也禁止继续转发后续上游事件。
6. 中止当前上游读取并释放当前账号并发槽；只有可重放文本在仍未提交且满足安全条件时，才排除本请求失败候选并回到调度循环尝试后续账号 / 后续分组。图片和其他副作用请求不得进入该循环。
7. transport / timeout 导致服务端可承接账号全部耗尽后，才进入客户端最终兜底：Codex Responses、Claude Code Messages 和 Gemini CLI stream 分别写对应协议错误事件；通用客户端在传输未提交时返回 HTTP `503`，已经提交时断流；稳定网关码统一使用 `upstream_retryable_error`。
8. 写入协议失败事件后立即结束下游 SSE。Codex 会在流结束后把 `response.failed` 归类为 `CodexErr::Stream(...)` 并进入自身重试循环；其他客户端按各自协议或连接失败机制决定是否重试。
9. 已经提交可见语义后禁止重新发起上游请求；网关记录截断/失败终态并稳定结束或断流。客户端后续重试是全新的网关请求，重新计算候选。

推荐伪造事件格式：

```text
event: response.failed
data: {"type":"response.failed","response":{"status":"failed","error":{"code":"upstream_retryable_error","message":"Upstream returned a retryable stream failure before output. Please retry."},"usage":null}}
```

注意事项：

- 服务端重试耗尽后的最终可见失败统一使用 `upstream_retryable_error` 作为稳定网关码，不能使用 `server_is_overloaded`、`slow_down` 或其他上游错误码。
- 不维护终止白名单，也不把上游错误码作为下游可见重写码；精确客户端 profile 使用对应协议事件承载稳定网关码，通用客户端只有本地 transport / capacity 耗尽才通过 HTTP `503` 承载。
- 原始上游错误码只进入诊断记录，不参与账号切换、最终失败格式或客户端重试建议的判断。
- 如果伪造 `response.failed` 后不关闭下游流，Codex 可能会继续等待直到 idle timeout，重试不会及时发生。
- 如果已经向下游发出原始失败事件，再追加伪造事件无法可靠覆盖客户端已解析的错误；拦截必须发生在原事件写出之前。

### 3.5 审计与使用记录

服务端内部重试命中时，原始审计日志必须保留前序账号的上游原始事件、重试原因、被排除账号、后续账号响应和最终下游结果。所有服务端重试耗尽进入最终客户端兜底时，审计都需要同时解释“上游原始事件”和“下游协议事件 / HTTP `503` / 断流”的改写关系。实现上会写入 `gateway_metadata` 审计原文，用结构化 JSON 记录客户端策略、响应检查、服务端重试和最终改写关系，方便直接检索和排障。

`gateway_metadata` 中至少包含：

```text
responseInspectionIntercepted: true
intercept_rule_id
intercept_rule_name
intercept_action
upstream_event_type
upstream_error_code
rewrite_error_code
output_seen
stream_server_retry
account_policy
cooldown_minutes
```

使用记录建议以“客户端实际收到的可重试错误”为结果口径，同时通过响应快照、审计扩展字段和上游原始 payload 保留真实上游错误。这样客户端协议适配层可被审计还原，排障时仍能定位真实上游问题。

账号状态副作用不由可见输出或上游错误码授权。可见输出前后都不得根据 `server_is_overloaded`、`slow_down` 或其他 code/type/message 写账户、Key 或共享质量失败；只保留诊断事实，用户显式策略和独立 transport confirmation 仍按各自 provenance 执行。

### 3.6 验收口径

回归测试至少覆盖：

- Codex profile 请求下，上游 `200 + SSE` 返回 `response.created`、`response.in_progress` 后返回 `response.failed/server_is_overloaded`，且未出现 output delta：如果有后续可用账号，下游不能看到 `server_is_overloaded` 或 `upstream_retryable_error`，应看到后续账号成功流；如果所有账号耗尽，下游才能看到 `response.failed/upstream_retryable_error`，并且连接立即结束。
- 上游建流前返回任意完整非 `2xx`：所有通用请求只按 `response.ok=false` 在请求级有界切换，状态/正文互换不得改变共享状态动作；资源/副作用请求同样在下游未提交时继续候选，原始状态、响应头和错误体仅进入有界诊断；精确客户端按协议结构处理当前 attempt，用户显式策略只控制其声明的状态动作。
- Codex profile 请求在可见输出前返回通用 `event: error`、未知 `response.failed` 或缺少终止事件：有后续账号时服务端隐藏切号成功，账号耗尽时才返回 `upstream_retryable_error`，账号不进入流失败计数；副作用请求使用相同终态与候选切换规则。
- Claude Code / Gemini CLI 的同类协议失败可优先由服务端隐藏切号；图片等 lane 使用相同准入和各自时限。通用客户端不得解释失败事件，应原样透传。
- 服务端隐藏候选切换成功时不记录客户端可见 turn 失败；候选耗尽后才按精确客户端策略记录可见失败。该状态只作用于同一 Codex turn，不是账号健康处罚。
- 上游在 `response.output_text.delta` 后失败：网关不得自动重放或据此写账号共享状态；精确客户端在尚无终态且连接可写时收到一个 `response.failed/upstream_retryable_error`，通用客户端断流。
- 审计中保留原始上游错误、服务端重试调度、最终下游错误或成功结果、`output_seen` 和账号动作。
- 如果策略兜底误伤，发布修正版本调整可见输出或失败事件识别边界；运行时不会提供管理页开关。

### 3.7 后续阶段

“已输出后由服务端重放”是已否决方案，不属于后续阶段：它无法可靠处理响应 ID、turn state、工具调用副作用、重复输出、计费和审计一致性。任何未来设计都不得在 `semanticCommitted = true` 后自动重新派发；只能通过客户端发起新请求，并重新执行完整认证、额度、候选和状态判断。

## 4. Claude Code 结论

Claude Code 的重试机制没有使用 OpenAI 的 `response.failed` 协议。

可确认的公开资料：

- Claude Code 错误文档说明：Claude Code 会自动重试 transient failure，包括 server errors、overloaded responses、request timeouts、temporary 429 throttles、dropped connections，默认最多 10 次；可通过 `CLAUDE_CODE_MAX_RETRIES` 与 `API_TIMEOUT_MS` 调整。
- Claude Code programmatic 文档说明：API request 遇到 retryable error 时，Claude Code 会在重试前输出 `system/api_retry` 事件，字段包括 `attempt`、`max_retries`、`retry_delay_ms`、`error_status` 和 `error`。
- `anthropic/claude-agent-sdk-typescript` changelog 提到新增 `api_retry` system messages，用于暴露 transient API errors 的重试尝试。

边界说明：

- 本次没有从 Claude Code 核心可读源码中确认具体实现；npm 包是打包产物，不适合作为可维护源码依据。
- 已删除本地临时 Claude / Anthropic SDK 目录，避免保留无效源码。
- 如果未来需要接入 Claude Code 或 Anthropic 原生客户端，不能复用 OpenAI 的 `response.failed` 事件；应按 Claude / Anthropic 自己的事件、错误体和 SDK 行为单独适配。

## 5. 后续厂商接入规则

接入新厂商或新客户端前，先区分两个概念：

- 上游供应商协议：本服务如何请求 OpenAI、Anthropic、Gemini 等上游。
- 下游客户端协议：Codex、Claude Code、OpenAI SDK、Anthropic SDK 等客户端期望看到什么响应结构。

流式中断处理应遵循：

- 任意 lane 在首段内容前失败：服务端可以按账号调度策略和对应 lane 墙钟有界切换账号；只有文本真实主派发已开始且响应头前 transport failure 才可消费同凭据安全原地重试 token。
- 首段上游内容后但下游尚未语义提交失败：各类请求仍可丢弃未提交缓冲并切换候选；已经语义提交则不得重放。
- 已经写给下游后的失败：服务端只发送对应客户端协议的失败事件并结束流，不在同一响应里换账号拼接续写。
- 错误事件必须使用客户端能识别且语义正确的协议格式。
- 是否能自动重试由客户端决定；服务端只负责给出明确、可识别、可归类的失败信号。

## 7. 2026-05-17 客户端策略分层补充

本次复盘确认：当前项目有些流式兜底行为是从 Codex 源码和现场问题推导出来的，早期实现层曾经放在通用 OpenAI stream 流程里；当前已经收敛到 Codex profile。后续不能在通用层继续叠加客户端专属行为，否则会影响普通 OpenAI SDK、Cherry Studio、NextChat、Claude Code 或其他 OpenAI-compatible 厂家的客户端。

策略分层必须区分：

- `upstreamAdapter`：上游账号适配方式，例如 `openai_api_key`、`openai_oauth_codex`。
- `downstreamProtocol`：下游响应协议，例如 `responses_sse`、`chat_completions_sse`、`json`。
- `clientProfile`：下游客户端行为，例如 `codex`、`generic_openai`，未来可扩展其他客户端。
- `requestClientCompatibility`：当前请求需要的客户端兼容能力，例如 `codex_responses`、`openai_standard`、`anthropic_native`、`claude_code`。它用于候选账号筛选和上游请求准备。

Codex turn 级重试切号只允许在 `clientProfile = codex` 且 `downstreamProtocol = responses_sse` 时触发。Codex profile 的精确证据来自普通 JSON 对象格式的 `x-codex-turn-metadata`，其中必须有非空 snake_case `turn_id`。`turnId`、URL 编码 JSON、数组 JSON、`session_id`、`thread_id`、`x-client-request-id`、User-Agent、IP、请求体 hash 或模型名都不能单独兜底识别 Codex；它们最多作为审计字段或一致性校验字段。

响应检查策略可以配置 `clientProfiles` 作为适用范围维度。管理端规则可限定 `clientProfiles = codex`，用于约束 Codex 特有响应语义或 `response.failed` 事件格式；稳定网关码 `upstream_retryable_error` 本身不是 Codex 专属。该维度不是语义命中条件，策略仍必须由错误码、错误类型、错误文案、完成状态、JSON 路径、SSE 原文或输出文本触发。

Codex 对 Responses SSE `response.incomplete` 的处理与网关普通终止事件不同：客户端会把它视作可重试 stream error，而不是成功完成。因此 Codex profile 下 `response.incomplete` 需要通过响应检查在下游提交前拦截，优先服务端重试或切号；最终兜底仍使用 `response.failed/upstream_retryable_error` 并立即关闭流。

同一 Codex turn 的状态键建议使用：

```text
systemAccountId + apiKeyId + endpoint + codex.turn_id
```

这个键只能证明“同一本地 API Key 边界下的同一个 Codex turn”，不能证明真实自然人用户。`groupId` 和 `rawBodyHash` 不参与状态键，同一 API Key 下发生分组切换或 Codex 重建重试正文时仍应保留 turn 级失败账号避让连续性；正文 hash 只进入审计。若无法构造该键，网关不得启用 Codex turn 策略，但仍必须执行通用服务端候选扫描和客户端重试协调。

Codex turn 级避让的当前边界：

- 服务端隐藏候选切换优先。当前请求下游尚未语义提交、对应 lane 预算允许且还有可承接账号时，网关先救回当前请求，不向 Codex 客户端下发可重试失败，也不记录 turn 级失败账号；请求类型不改变该准入。
- 只有服务端可承接账号耗尽后，才向 Codex 返回 `response.failed/upstream_retryable_error` 并记录一次客户端可见 turn 失败；其他客户端按各自策略返回，不写 Codex turn 状态。
- 后续同一 turn 的客户端重试如果再次到达网关，turn 级避让只在 Codex profile、同一本地 API Key 和同一 `turn_id` 边界内避让已激活的失败账号；重试正文变化不切开状态。
- 无法精准识别 Codex turn 或状态丢失时，不启用 Codex turn 避让；请求仍走通用服务端候选扫描和客户端重试协调，不能因此跳过任何可用账号。
- turn 级避让不等于账号健康惩罚，不直接写 `temporary_unavailable`、`rate_limited` 或 `error`。

现有实现把可重放文本的有界候选切换作为通用稳定性策略；只有主派发已开始、响应头前 transport failure 可消费整请求安全原地重试 token。`response.failed` 格式和 turn 级避让只在 Codex profile 启用，Claude Code 与 Gemini CLI 使用各自协议事件；generic payload 保持透明。已提交语义后稳定结束或断流，禁止服务端自动重放。后续不能把 Codex 的 `turn_id`、上游错误码或正文写进通用调度。

## 8. 2026-07-27 Codex 流式中断修复设计

### 8.1 现场结论

生产样本同时存在两类失败，必须分开处理：

- 网关仍持有下游连接时，能够确认上游 idle、读取不完整或缺少协议终态。此时精确 Codex Responses 流可以补一个且仅一个 `response.failed`，稳定码统一为 `upstream_retryable_error`，随后立即结束。
- 下游连接关闭时，网关已经无法补协议事件。审计记录为 `downstream_closed`；它不计入账号失败。

Codex 当前实现会把普通 `response.failed` 以及传输层 stream/network 中断纳入自身重试路径；`upstream_retryable_error` 的价值是统一网关契约和审计，不是唯一能触发重试的字符串开关。直接断流仍是通用客户端或失败终态无法写入时的降级路径，但它不能替代网关可控的协议终态。

### 8.2 强弱证据模型

turn 局部状态按账号记录两类证据：

- `committed_retry_signal`：网关在已提交输出后确认当前流失败，并准备向 Codex 写入 `response.failed/upstream_retryable_error`。这是强证据，下一次同 turn 请求立即避开当前账号。
- `incomplete_downstream_abort`：下游在已有可见语义、没有成功或失败终态、解析器未跳过时提前关闭。这是弱证据；同账号、同 turn、60 秒窗口内两个不同请求才激活避让。

旧的服务端候选耗尽可见失败继续保留原有累计语义，不把“最后一个账号”直接推断为全部候选中的唯一坏账号。强证据只用于已经语义提交、服务端不能在当前响应内换号的场景。

每条证据携带有界 observation ID，重复收尾不得重复计数。状态按最后一次有效失败保留 30 分钟，读取不续期；弱证据另有 60 秒窗口。Redis 更新必须使用并发安全的合并，冲突耗尽时 fail-open。

### 8.3 候选顺序

激活的失败账号只在当前 `systemAccountId + apiKeyId + endpoint + codex.turn_id` 状态键内避让。状态键故意不包含请求体 hash，因为 Codex 重建同一 turn 的重试请求时正文可能变化；`rawBodyHash` 仅用于审计。

只要还有未激活账号，强证据激活的账号就移动到所有未激活账号之后，允许本 turn 临时跨越显式 priority、fallback 和 model rank 层。弱下游关闭证据仍只在相同调度层内后移；没有同层备用时保持原顺序，避免连续关闭把低优先级 fallback 抬成首选。它不能证明用户主动停止，也不修改持久路由策略；新 turn 仍按正常优先级重新选择。全部候选均激活或只有一个候选时恢复原顺序。

### 8.4 流式时序

提交后可控失败按以下顺序收尾：

1. 确认尚未写过成功/失败终态，并构造脱敏的 `response.failed/upstream_retryable_error`。
2. best-effort 写入强证据；Redis 或审计失败只告警，不能阻断协议终态。
3. 写入失败事件并立即结束 SSE；写事件失败则降级为断流。
4. 最终化记录复用同一 observation ID，不得重复累计。

下游关闭无法补事件。流处理只在强准入条件全部满足时回调记录弱证据，并继续抛出原始 abort；审计和使用记录统一使用 `downstream_closed`。弱证据不改变账户、Key、电路、质量、代理健康或会话外的调度状态。

这里的“追加失败终态”不是拼接第二条上游响应：它只在尚未出现任何协议终态时，为精确客户端关闭当前失败流。已经写出 `response.completed`、上游失败终态或其他协议终态后，不得再追加矛盾终态。

### 8.5 回归矩阵

- 输出后 idle/read incomplete/缺少终态：Codex 收到单个稳定可重试终态；generic 客户端断流。
- 强证据记录先于失败终态写出，同一 turn 的立即重试读取到新顺序。
- 一次弱 abort 不避让；同账号两个不同 observation 激活；不同账号各一次不互相累计；重复 observation 幂等。
- 无输出、仅 transport heartbeat、终态后关闭、parser skipped、缺 turn_id、generic client 和网关 forced close 不记录弱证据。
- 弱窗口过期、全部账号激活、单账号、跨 priority/fallback、同 turn body 变化、不同 turn/API Key 隔离均有断言。
- Memory / Redis 并发合并一致，CAS 耗尽 fail-open；所有场景断言共享账号状态和电路不变。
