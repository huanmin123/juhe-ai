> 记录时间：2026-05-05。
> 当前版本启用通用 `openai` 供应商和 `gpt` 子供应商；对外主要面向 OpenAI 兼容协议客户端，其中 GPT/Codex 是重点客户端策略。

> 2026-07-10 与 2026-06-29 的“通用客户端统一 503 / 流内失败都进入响应检查”口径已被 PLAN-0134 取代，仅保留为历史背景。
> 2026-06-29 补充：当前不保留旧 SSE 专项策略入口；管理端策略和账户级追加规则统一使用响应语义检查。
> 2026-06-12 补充（已由 2026-07-10 规则扩展）：当前运行时已改为“服务端内部重试优先”。只要下游尚未提交 SSE body，网关会先隐藏切换后续账号 / 后续分组；只有服务端可承接账号耗尽后，才按具体客户端 profile 下发协议事件，或向通用客户端返回 HTTP `503`。`upstream_retryable_error` 只表示网关已耗尽当前服务端候选并建议客户端重试，不是上游错误分类。

## 1. 背景

网关流式响应分两个阶段：

- 首段内容到达前：客户端还没有收到模型输出，服务端可以安全切换账号或重试上游请求。
- 首段内容到达后：客户端已经收到部分输出，且可能已经写入会话历史、UI 状态、turn state 或内部缓存。服务端不能安全换账号续写或拼接第二次上游请求，否则会产生重复内容、分叉上下文、响应 ID / usage 不一致等问题。

因此，“输出停顿上限”是每次流式 attempt 的 raw chunk 空闲阈值；文本 lane 默认 30 秒，图像 lane 默认 120 秒。SSE 注释、心跳、reasoning、tool call delta 和其他上游 chunk 都会刷新原始数据计时。网关自己的等待注释只设置 `transportCommitted`；真实协议事件或正文写出后才设置 `semanticCommitted`。transport 失败在语义提交前可服务端救回，语义提交后不能静默拼接第二条上游流。

## 2. OpenAI / Codex 结论

当前客户端重试策略不把 Codex 行为外推给所有 OpenAI-compatible 客户端。客户端画像和下游协议共同决定本地 transport 失败的最终机制：Codex Responses、Claude Code Messages 和 Gemini CLI stream 使用协议事件；通用客户端在传输未提交时返回 HTTP 错误，已经提交 SSE 传输时直接断流。完整上游响应对通用客户端始终透明，不会被改写成 503。

### 2.1 通用重试协调矩阵

| 客户端 / 下游协议 | 下游未提交 | 下游已提交 | 说明 |
| --- | --- | --- | --- |
| Codex / Responses SSE | `response.failed` + `upstream_retryable_error` | `response.failed` 后结束 | Codex 依据 Responses 事件进入自身重试 |
| Claude Code / Messages SSE | Anthropic `event: error`，类型为可重试服务错误 | Anthropic `event: error` 后结束 | 不透传具体上游错误分类 |
| Gemini CLI / Gemini SSE | Gemini 协议错误事件，状态为 `UNAVAILABLE` | Gemini 协议错误事件后结束 | 不按具体上游错误分类 |
| 通用 OpenAI / Anthropic / Gemini 流式客户端 | 本地 transport / capacity 耗尽时 HTTP 错误；完整上游事件原样转发 | 直接断流 | 不解释上游失败事件；已提交传输时交给传输层重试 |
| 非流式客户端 | transport / capacity 耗尽时 HTTP 错误；完整上游响应原样转发 | 正文已输出后直接断开 | 不能在半截 JSON 后拼接第二次响应 |

同账号失败确认与最终客户端信号是两个独立层次：

1. 第一次真实上游失败后，只要请求级共享确认预算仍有剩余，就在当前账号原地重试并消费一次预算，以吸收短时波动。
2. 预算耗尽或当前账号不能继续原地重试后切换账号；后续账号不会重新获得一套完整确认预算。
3. 服务端仍会扫描当前调度可承接账号和后续允许的分组，但不会再把配置重试次数乘以账号数。
4. 服务端承接能力耗尽后才发客户端可见重试信号。
5. 上述过程只判断尝试成功或失败，不按上游 HTTP 状态、错误码、错误类型或错误文案决定是否确认或如何切号。

普通路由 `speed_first` 与本节无关：它只根据首字延迟样本确认慢请求，不因普通上游失败立即切换，也不覆盖请求级失败确认预算。

错误码策略：

- 服务端内部重试耗尽后统一使用稳定网关码 `upstream_retryable_error` 表达“服务端候选已耗尽，建议客户端重试”；精确客户端 profile 通过对应协议事件承载，普通客户端通过 HTTP `503` 承载。该码不承诺保留下游可见的原始上游错误语义，原始失败原因只保留在使用记录、审计和上游响应快照里。
- `upstream_stream_idle_timeout`、`upstream_stream_interrupted` 可继续作为内部原因分类或已输出后错误码，但不再作为可见输出前发给客户端的兜底错误码。
- 当前不再维护终止类错误码白名单；可识别流式失败先按下游写出边界做服务端内部重试，耗尽后统一使用 `upstream_retryable_error`，不区分 `context_length_exceeded`、`insufficient_quota`、`usage_not_included`、`invalid_prompt`、`cyber_policy` 或其他上游错误码。
- `server_is_overloaded` / `slow_down` 说明了不能直接透传上游错误码：Codex 源码会把这两个原始码视为不可重试。网关因此只发送稳定网关码，但该原则适用于所有客户端的最终兜底，不构成 Codex 专属调度分支。

当前运行时落点：

- 如果上游已经返回 `2xx + SSE`，网关会立即把响应头和后续 SSE 事件转发给客户端，不再为了“首段上游内容”预读并阻塞下游。
- 首段上游内容到来前按最终 lane 使用首响应档位：文本 120 秒，图像 600 秒；语义尚未提交时的 transport 超时优先服务端切换后续账号 / 后续分组。
- 首段上游内容到来后按 lane 使用 raw chunk 停顿档位：文本 30 秒，图像 120 秒。持续发送任意 chunk 会刷新计时；超时发生在语义提交前可服务端救回，语义提交后只能按客户端能力收口。
- 未提交单次 attempt 最大寿命按文本 1800 秒、图像 3600 秒设置；活跃且已提交语义的 SSE 不再因固定 1800 秒机械中断。
- `noAvailableAccountWaitTimeoutSeconds` 默认 270 秒，只累计零可派发账号或并发槽等待阶段；真实上游 attempt、已有可派发账号扫描和活跃读取不消耗预算。
- 流式转发 catch 分支按客户端画像和下游协议结束响应：精确客户端写对应协议失败事件，通用客户端在已提交后断开连接。
- 精确客户端正常 EOF 但没有协议终止事件时，可按协议失败在语义提交前服务端救回；通用客户端不解释缺少终止事件，按上游原始 EOF 收口。
- 精确客户端在语义提交前收到 `response.failed` 或对应协议 `event: error` 时，经过响应检查后可服务端重试；通用客户端原样接收该事件，不改写为 `upstream_retryable_error`。
- 上游在建流前返回完整 HTTP 非 `2xx` 时，通用客户端原样接收状态和正文；只有精确客户端画像允许的策略才能在语义提交前处理。
- 该失败事件也加入响应快照 chunks，便于使用记录保留完整链路。
- `frontend/src/views/settings/SettingsView.vue` 中“输出停顿上限（秒）”只说明行为，不在说明文案里重复默认秒数。

## 3. OpenAI Responses 流式兜底方案

### 3.1 问题定义

2026-05-13 排查确认过一种特殊失败形态：上游返回 `200 + text/event-stream`，但 SSE 事件内出现 `error.code = server_is_overloaded` 或 `slow_down`。这类失败不是 HTTP 非 2xx，不能只靠账户错误处理策略识别。后续又确认过通用 `event: error`、缺少终止事件和上游读取中断等形态，本项目最终把处理边界收敛为“是否已经产生可见输出”，而不是围绕单个错误码或单个场景分别补偿。

Codex 对 `response.failed` 的处理有明确分支：如果 `data.type = "response.failed"` 且 `response.error.code` 是 `server_is_overloaded` 或 `slow_down`，会映射为 `ServerOverloaded`，客户端展示 `Selected model is at capacity. Please try a different model.`，并且 `is_retryable()` 为 `false`。所以如果网关把这两个原始错误码透传给下游，Codex 不会自动重试。

当前运行时采用“下游实际写出边界 + 客户端策略”兜底：不围绕单个 SSE 错误码维护特征规则，而是把所有可识别流式失败统一放到下游写出边界下处理。`response.failed` 事件格式由 `clientProfile = codex + downstreamProtocol = responses_sse` 决定；稳定网关码 `upstream_retryable_error` 也可以由其他精确协议事件或通用 HTTP `503` 承载。Codex profile 只接受普通 JSON 对象格式的 `x-codex-turn-metadata.turn_id`，不接受 `turnId`、URL 编码 JSON 或数组 JSON；未识别到 Codex 时不启用 turn 级避让，但仍执行通用候选扫描和客户端重试协调。

### 3.2 安全边界

项目内统一使用“重试”作为总称，并按输出边界分成两类：

- 未输出前重试：`outputSeen = false` 且下游尚未提交时，客户端尚未收到可见输出、工具参数或执行状态 delta，网关优先在服务端内部切换后续账号 / 后续分组。只有服务端可承接账号耗尽后，才允许按具体客户端 profile 把最终失败改写为客户端可重试错误。客户端重试次数不由网关限制。
- 已输出后重放：`outputSeen = true` 后，客户端已经看到部分输出或执行状态变化，此时自动继续必须由服务端按“重放”处理，也统一归入项目重试规范。重放的输入必须来自本次请求已捕获的原始请求、上下文、账号调度信息和审计链路，不能临时拼接用户可见文本。服务端重放必须遵守临时不可调用的策略重试机制；重放仍失败时，网关把最后一次上游失败原样返回给客户端。

客户端自动重试由客户端自己控制次数，网关只在服务端内部重试耗尽后，按对应客户端 profile 给出可重试的协议失败信号。服务端内部重试由网关主动发起，受当前候选账号、分组和重试预算限制，不能无限重放；如果服务端链路仍失败，返回给客户端的是按客户端能力生成的最终失败，而不是把中间账号失败逐个下发。

因此，流式重试安全边界不是“是否已经发过任意 SSE 事件”，而是“是否已经向下游发送过可见输出或会改变客户端执行状态的 delta”。所有 UI 文案、配置项、日志、审计字段、计划文档和后续实现都必须遵守这个术语：`重试 = 未输出前重试 + 已输出后重放`。

下列事件不视为 `outputSeen`：

- `response.created`
- `response.in_progress`
- `response.metadata`
- 模型、限流、header 类元信息
- SSE 注释、心跳或其他不产生可见输出的事件

下列事件一旦写给下游，就必须视为 `outputSeen = true`：

- `response.output_text.delta`
- 工具调用参数 delta，例如 `response.custom_tool_call_input.delta`，以及后续新增客户端策略时可能出现的等价 tool/function argument delta
- `response.reasoning_summary_text.delta`
- `response.reasoning_text.delta`
- 任何携带可见 assistant 文本、工具调用参数或可执行状态变化的 `response.output_item.added` / `response.output_item.done`

只有服务端内部重试耗尽后，才允许把上游流式失败转换为客户端可重试信号。下游实际写出字节数为零时，即使解析器已在预提交缓冲中识别到可见输出，也仍可切换后续账号；已有内容实际写给下游后不再按错误码豁免或伪造整轮重试。未来若要自动继续，必须走已输出后重放策略。

### 3.3 策略兜底模型

此前讨论过的流式错误码特征规则已下线，不进入系统设置页，也不开放给管理员临时配置。经过 `server_is_overloaded`、`slow_down`、通用 `event: error`、缺少终止事件和上游读取中断等样本复盘后，当前运行时不再维护流式错误码特征白名单，也不保留空的流式规则接口或前端页签，而是按可见输出边界和客户端策略处理：

- transport 失败且 `semanticCommitted = false`：先服务端内部重试，切换后续账号 / 后续分组；全部耗尽后按客户端画像写协议事件、HTTP 错误或断流。
- 精确客户端语义失败且 `semanticCommitted = false`：可以按其策略服务端重试；`generic_*` 不解释该语义并原样转发。
- `semanticCommitted = true`：不按错误码设置例外，不静默拼接第二条流，按客户端策略写协议错误事件或断流。
- 可见输出判断由 `openAIStreamEventHasVisibleOutput()` 统一提供，流式解析器和兜底判断必须复用同一函数，避免账号副作用与下游改写边界不一致。
- 失败事件识别只认明确失败形态：`response.failed`、通用 `event/type = error`、`response.error` 或 top-level `error` 对象；普通事件里的顶层 `code/message` 不单独触发失败兜底。
- 响应语义检查策略只在精确客户端画像下执行；新增规则类型、只读接口、前端展示或回归前，必须先证明现有边界无法覆盖。通用客户端不因任何响应字段进入该管线。
- 配置化流式策略把前端配置收敛为“数据处理、是否重试、账号避让、账户状态”四类意图，执行层继续受可见输出边界和客户端协议能力约束。

### 3.4 网关处理流程

流式转发不能只做原始字节级 `pipe` 后再字符串替换。要稳定执行可见输出前兜底，网关必须按 SSE 事件边界解析并在写下游前决策。

处理流程：

1. 上游返回 `2xx + text/event-stream` 后，网关进入 SSE 事件解析转发模式。
2. 每个完整 SSE 事件先解析 `event:`、`data:` 和 `data` JSON；解析失败或超限时按既有流式中断策略处理。
3. 写下游前更新 `outputSeen` 候选判断；只有会产生可见输出或工具状态变化的事件才置为 `true`。
4. 如果事件是 `response.failed`、通用 `event: error`，或携带可解析错误字段，则按 `outputSeen` 决定处理方式。
5. 可见输出前失败时，禁止把原始事件继续写给下游，也禁止继续转发后续上游事件。
6. 中止当前上游读取并释放当前账号并发槽；当前请求先排除该失败账号，回到调度循环尝试后续账号 / 后续分组。服务端隐藏重试成功时，客户端只看到成功账号的流。
7. transport / timeout 导致服务端可承接账号全部耗尽后，才进入客户端最终兜底：Codex Responses、Claude Code Messages 和 Gemini CLI stream 分别写对应协议错误事件；通用客户端在传输未提交时返回 HTTP `503`，已经提交时断流；稳定网关码统一使用 `upstream_retryable_error`。
8. 写入协议失败事件后立即结束下游 SSE。Codex 会在流结束后把 `response.failed` 归类为 `CodexErr::Stream(...)` 并进入自身重试循环；其他客户端按各自协议或连接失败机制决定是否重试。
9. 后续阶段若命中已输出后重放，网关使用本次请求的原始请求快照和调度上下文重新发起请求。重放必须进入独立审计尝试，保留原始失败事件、重放原因和后续上游响应；重放期间遵守临时不可调用策略重试机制，仍失败时按客户端能力返回最终失败，不把中间失败逐个下发。

推荐伪造事件格式：

```text
event: response.failed
data: {"type":"response.failed","response":{"status":"failed","error":{"code":"upstream_retryable_error","message":"Upstream returned a retryable stream failure before output. Please retry."},"usage":null}}
```

注意事项：

- 服务端重试耗尽后的最终可见失败统一使用 `upstream_retryable_error` 作为稳定网关码，不能使用 `server_is_overloaded`、`slow_down` 或其他上游错误码。
- 不维护终止白名单，也不把上游错误码作为下游可见重写码；精确客户端 profile 使用对应协议事件承载稳定网关码，通用客户端只有本地 transport / capacity 耗尽才通过 HTTP `503` 承载。
- 原始上游错误码只进入诊断记录，不参与账号切换、最终失败格式或客户端重试建议的判断。
- 如果伪造 `response.failed` 后不关闭下游流，Codex 可能会继续等待直到 idle timeout，重试不会及时发生。
- 如果已经向下游发出原始失败事件，再追加伪造事件无法可靠覆盖客户端已解析的错误；拦截必须发生在原事件写出之前。

### 3.5 审计与使用记录

服务端内部重试命中时，原始审计日志必须保留前序账号的上游原始事件、重试原因、被排除账号、后续账号响应和最终下游结果。所有服务端重试耗尽进入最终客户端兜底时，审计都需要同时解释“上游原始事件”和“下游协议事件 / HTTP `503` / 断流”的改写关系。实现上会写入 `gateway_metadata` 审计原文，用结构化 JSON 记录客户端策略、响应检查、服务端重试和最终改写关系，方便直接检索和排障。

`gateway_metadata` 中至少包含：

```text
responseInspectionIntercepted: true
intercept_rule_id
intercept_rule_name
intercept_action
upstream_event_type
upstream_error_code
rewrite_error_code
output_seen
stream_server_retry
account_policy
cooldown_minutes
```

使用记录建议以“客户端实际收到的可重试错误”为结果口径，同时通过响应快照、审计扩展字段和上游原始 payload 保留真实上游错误。这样客户端协议适配层可被审计还原，排障时仍能定位真实上游问题。

账号策略同样以可见输出边界为准。可见输出前失败不写账号流失败副作用；可见输出后失败不再按 `server_is_overloaded` / `slow_down` 等错误码豁免，统一进入流失败计数。

### 3.6 验收口径

回归测试至少覆盖：

- Codex profile 下，上游 `200 + SSE` 返回 `response.created`、`response.in_progress` 后返回 `response.failed/server_is_overloaded`，且未出现 output delta：如果有后续可用账号，下游不能看到 `server_is_overloaded` 或 `upstream_retryable_error`，应看到后续账号成功流；如果所有账号耗尽，下游才能看到 `response.failed/upstream_retryable_error`，并且连接立即结束。
- 上游建流前返回任意完整非 `2xx`：通用客户端应收到上游原始状态、响应头和错误体且只命中一个账号；精确客户端按各自策略决定是否服务端重试。
- Codex profile 下，上游 `200 + SSE` 在可见输出前返回通用 `event: error`、未知 `response.failed` 或缺少终止事件：有后续账号时服务端隐藏切号成功，账号耗尽时才返回 `upstream_retryable_error`，账号不进入流失败计数。
- Claude Code / Gemini CLI 的同类语义失败可优先服务端隐藏切号；通用客户端不得解释失败事件，应原样透传。
- 同样场景下，账号不进入流失败计数；这是通用可见输出边界，不依赖具体错误码规则。
- 上游在 `response.output_text.delta` 后再返回 `server_is_overloaded`：网关不得伪造客户端整轮重试错误，按通用流失败计数处理；如果后续开启已输出后重放，必须按服务端重放策略处理，并在审计中标记为 replay。
- 审计中保留原始上游错误、服务端重试调度、最终下游错误或成功结果、`output_seen` 和账号动作。
- 如果策略兜底误伤，发布修正版本调整可见输出或失败事件识别边界；运行时不会提供管理页开关。

### 3.7 后续阶段

第一阶段只做未输出前客户端自动重试型拦截，不做已输出后重放请求。

已输出后重放作为第二阶段评估：在 `outputSeen = true` 后命中特征时，网关基于原始请求快照重新发起请求，并把重放尝试作为同一次客户端请求下的后续上游尝试记录。重放必须复用临时不可调用的策略重试机制，不能无限重放；如果重放链路仍失败，网关把最后一次上游失败原样返回客户端。该方案可以减少用户手动发送“继续”的频率，但必须处理响应 ID、turn state、审计多次上游尝试、请求预算、工具调用副作用和重复输出边界，复杂度高于第一阶段。

## 4. Claude Code 结论

Claude Code 的重试机制没有使用 OpenAI 的 `response.failed` 协议。

可确认的公开资料：

- Claude Code 错误文档说明：Claude Code 会自动重试 transient failure，包括 server errors、overloaded responses、request timeouts、temporary 429 throttles、dropped connections，默认最多 10 次；可通过 `CLAUDE_CODE_MAX_RETRIES` 与 `API_TIMEOUT_MS` 调整。
- Claude Code programmatic 文档说明：API request 遇到 retryable error 时，Claude Code 会在重试前输出 `system/api_retry` 事件，字段包括 `attempt`、`max_retries`、`retry_delay_ms`、`error_status` 和 `error`。
- `anthropic/claude-agent-sdk-typescript` changelog 提到新增 `api_retry` system messages，用于暴露 transient API errors 的重试尝试。

边界说明：

- 本次没有从 Claude Code 核心可读源码中确认具体实现；npm 包是打包产物，不适合作为可维护源码依据。
- 已删除本地临时 Claude / Anthropic SDK 目录，避免保留无效源码。
- 如果未来需要接入 Claude Code 或 Anthropic 原生客户端，不能复用 OpenAI 的 `response.failed` 事件；应按 Claude / Anthropic 自己的事件、错误体和 SDK 行为单独适配。

## 5. 后续厂商接入规则

接入新厂商或新客户端前，先区分两个概念：

- 上游供应商协议：本服务如何请求 OpenAI、Anthropic、Gemini 等上游。
- 下游客户端协议：Codex、Claude Code、OpenAI SDK、Anthropic SDK 等客户端期望看到什么响应结构。

流式中断处理应遵循：

- 首段内容前失败：服务端可以按账号调度策略切换账号或重试。
- 首段内容后但下游尚未提交失败：服务端仍可按预提交缓冲边界切换账号或重试。
- 已经写给下游后的失败：服务端只发送对应客户端协议的失败事件并结束流，不在同一响应里换账号拼接续写。
- 错误事件必须使用客户端能识别且语义正确的协议格式。
- 是否能自动重试由客户端决定；服务端只负责给出明确、可识别、可归类的失败信号。

## 7. 2026-05-17 客户端策略分层补充

本次复盘确认：当前项目有些流式兜底行为是从 Codex 源码和现场问题推导出来的，早期实现层曾经放在通用 OpenAI stream 流程里；当前已经收敛到 Codex profile。后续不能在通用层继续叠加客户端专属行为，否则会影响普通 OpenAI SDK、Cherry Studio、NextChat、Claude Code 或其他 OpenAI-compatible 厂家的客户端。

策略分层必须区分：

- `upstreamAdapter`：上游账号适配方式，例如 `openai_api_key`、`openai_oauth_codex`。
- `downstreamProtocol`：下游响应协议，例如 `responses_sse`、`chat_completions_sse`、`json`。
- `clientProfile`：下游客户端行为，例如 `codex`、`generic_openai`，未来可扩展其他客户端。
- `requestClientCompatibility`：当前请求需要的客户端兼容能力，例如 `codex_responses`、`openai_standard`、`anthropic_native`、`claude_code`。它用于候选账号筛选和上游请求准备。

Codex turn 级重试切号只允许在 `clientProfile = codex` 且 `downstreamProtocol = responses_sse` 时触发。Codex profile 的精确证据来自普通 JSON 对象格式的 `x-codex-turn-metadata`，其中必须有非空 snake_case `turn_id`。`turnId`、URL 编码 JSON、数组 JSON、`session_id`、`thread_id`、`x-client-request-id`、User-Agent、IP、请求体 hash 或模型名都不能单独兜底识别 Codex；它们最多作为审计字段或一致性校验字段。

响应检查策略可以配置 `clientProfiles` 作为适用范围维度。管理端规则可限定 `clientProfiles = codex`，用于约束 Codex 特有响应语义或 `response.failed` 事件格式；稳定网关码 `upstream_retryable_error` 本身不是 Codex 专属。该维度不是语义命中条件，策略仍必须由错误码、错误类型、错误文案、完成状态、JSON 路径、SSE 原文或输出文本触发。

Codex 对 Responses SSE `response.incomplete` 的处理与网关普通终止事件不同：客户端会把它视作可重试 stream error，而不是成功完成。因此 Codex profile 下 `response.incomplete` 需要通过响应检查在下游提交前拦截，优先服务端重试或切号；最终兜底仍使用 `response.failed/upstream_retryable_error` 并立即关闭流。

同一 Codex turn 的状态键建议使用：

```text
systemAccountId + apiKeyId + endpoint + codex.turn_id + rawBodyHash
```

这个键只能证明“同一本地 API Key 边界下，同一个 Codex turn 的同一请求体”，不能证明真实自然人用户。`groupId` 不参与状态键，同一 API Key 下发生分组切换时仍应保留 turn 级失败账号避让连续性。若无法构造该键，网关不得启用 Codex turn 策略，但仍必须执行通用服务端候选扫描和客户端重试协调。

Codex turn 级避让的当前边界：

- 服务端隐藏重试优先。只要下游尚未提交并且还有可承接账号，网关先在服务端切号救回当前请求，不向 Codex 客户端下发可重试失败，也不记录 turn 级失败账号。
- 只有服务端可承接账号耗尽后，才向 Codex 返回 `response.failed/upstream_retryable_error` 并记录一次客户端可见 turn 失败；其他客户端按各自策略返回，不写 Codex turn 状态。
- 后续同一 turn 的客户端重试如果再次到达网关，turn 级避让只在 Codex profile、同一本地 API Key 和同一请求体哈希边界内避让已发生可见失败的账号。
- 无法精准识别 Codex turn 或状态丢失时，不启用 Codex turn 避让；请求仍走通用服务端候选扫描和客户端重试协调，不能因此跳过任何可用账号。
- turn 级避让不等于账号健康惩罚，不直接写 `temporary_unavailable`、`rate_limited` 或 `error`。

现有实现把 transport / timeout 服务端重试作为通用稳定性策略；`response.failed` 格式和 turn 级避让只在 Codex profile 启用，Claude Code 与 Gemini CLI 使用各自协议事件。generic 客户端对完整上游响应透明，只有本地 transport / capacity 耗尽时在未提交传输阶段返回 HTTP 错误，已提交传输时断流。后续不能把 Codex 的 `turn_id`、上游错误码或正文写进通用调度。
