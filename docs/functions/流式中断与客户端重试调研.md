# 流式中断与客户端重试调研

> 记录时间：2026-05-05。
> 当前版本只启用 OpenAI 供应商；对外主要面向 OpenAI 兼容客户端，其中重点客户端是 Codex。
> 2026-05-17 补充：Codex 的流式重试语义不能继续当作全部 OpenAI-compatible 客户端的通用行为。运行时已将可见输出前 `response.failed/upstream_retryable_error` 收敛到 Codex 客户端策略；新增或调整客户端自动重试、失败事件改写、turn 级切号时，必须先经过客户端策略分层。

## 1. 背景

网关流式响应分两个阶段：

- 首段内容到达前：客户端还没有收到模型输出，服务端可以安全切换账号或重试上游请求。
- 首段内容到达后：客户端已经收到部分输出，且可能已经写入会话历史、UI 状态、turn state 或内部缓存。服务端不能安全换账号续写或拼接第二次上游请求，否则会产生重复内容、分叉上下文、响应 ID / usage 不一致等问题。

因此，“输出停顿上限”是每次流式响应内部的计时阈值，表示本次响应收到首段上游内容后多久没有任何上游新数据；它不是跨请求共享的全局计时器。SSE 注释、心跳、reasoning、tool call delta 和其他上游 chunk 都会刷新原始数据计时。相同上限也用于处理上游持续吐原始字节但长期拼不出完整 SSE 事件的假活流。超时后网关应把失败明确告诉客户端并结束本次 SSE，而不是在服务端悄悄重试并继续拼接；是否重试、如何处理半截上下文，应交给客户端按自身协议和状态决定。

## 2. OpenAI / Codex 结论

历史上当前 OpenAI 兼容客户端按 Codex 优先兼容，因此流式失败改写优先验证了 Codex 行为。该结论不能外推成所有 OpenAI-compatible 客户端都支持同样的重试语义；当前策略以 `clientProfile` 为边界，Codex 专属行为只在识别到 Codex profile 后触发。

```text
event: response.failed

```

关于通用 `event: error`：

- Codex 的 SSE helper 只把 `data:` 内容传给后续解析，`event:` 名称本身没有进入 Responses 事件处理逻辑。源码位置：`F:\temp-project\agent\openai-codex-main\codex-rs\codex-client\src\sse.rs:20` 到 `F:\temp-project\agent\openai-codex-main\codex-rs\codex-client\src\sse.rs:22`。
- Codex 后续按 `data` JSON 的 `type` 字段分发事件。源码位置：`F:\temp-project\agent\openai-codex-main\codex-rs\codex-api\src\sse\responses.rs:245` 到 `F:\temp-project\agent\openai-codex-main\codex-rs\codex-api\src\sse\responses.rs:252`。
- `type: "response.failed"` 会被 Codex 识别并按错误类型决定是否重试；未知 `type` 只会被 trace 后忽略。源码位置：`F:\temp-project\agent\openai-codex-main\codex-rs\codex-api\src\sse\responses.rs:312` 到 `F:\temp-project\agent\openai-codex-main\codex-rs\codex-api\src\sse\responses.rs:340`。
- 所以不能把 `event: error` 当成跨客户端、跨供应商的统一失败协议；即使外层写 `event: error`，也必须保证 `data.type` 是目标客户端能识别的协议事件。对 Codex / OpenAI Responses 来说，可靠做法仍是发送 `type: "response.failed"`，并建议 `event:` 也保持 `response.failed`，便于日志、调试和其他严格 SSE 客户端识别。

错误码策略：

- 当前 Codex profile 在可见输出前失败时使用 `upstream_retryable_error` 给 Codex 触发客户端重试；失败原因仍保留在 message、使用记录、审计和上游响应快照里。该行为不是其他客户端能力的默认模板。
- `upstream_stream_idle_timeout`、`upstream_stream_interrupted` 可继续作为内部原因分类或已输出后错误码，但不再作为可见输出前发给客户端的兜底错误码。
- `context_length_exceeded`、`insufficient_quota`、`usage_not_included`、`invalid_prompt`、`cyber_policy` 这类 Codex 源码明确终止类错误必须原样返回，不改写成 `upstream_retryable_error`，也不参与 turn 级切号计数。
- `server_is_overloaded` / `slow_down` 是容量类专项兜底：Codex 源码会把原始码视为不可重试，所以当前 Codex profile 才在可见输出前改写为 `upstream_retryable_error`；该行为不能外扩到非 Codex。

当前运行时落点：

- 如果上游已经返回 `2xx + SSE`，网关会立即把响应头和后续 SSE 事件转发给客户端，不再为了“首段上游内容”预读并阻塞下游。
- 首段上游内容到来前有 `streamRequestTimeoutSeconds` 总时限；超过该时间没有收到任何上游 chunk，当前运行时会补发 `response.failed` 并结束本次 SSE；Codex profile 使用 `upstream_retryable_error`，非 Codex 保留普通流式错误码。
- 首段上游内容到来后，每次流式响应各自按 `streamIdleTimeoutSeconds` 对上游活动计时；上游持续发送 SSE 注释、心跳、reasoning、tool call delta 或其他任意 chunk 都会刷新原始数据计时。超时后当前运行时会补发 `response.failed` 并结束本次 SSE；Codex profile 使用 `upstream_retryable_error`，非 Codex 保留普通流式错误码。
- 同一个 `streamIdleTimeoutSeconds` 也限制完整 SSE 事件间隔；如果上游持续发送 raw chunk 但长期没有形成完整 SSE 事件，当前运行时会补发 `response.failed` 并结束本次 SSE，避免 Codex App 等客户端长时间停在无可展示状态；Codex profile 使用 `upstream_retryable_error`，非 Codex 保留普通流式错误码。若单行或单事件超过网关解析上限并触发解析跳过，后续不再使用完整 SSE 事件计时，只保留 raw chunk 活动计时并按原始流转发结果结束。
- `backend/src/modules/gateway/openai-gateway.routes.ts` 的 `pipeUpstreamStream()` 在 catch 分支写入 `response.failed` 后再结束响应。
- 如果上游正常 EOF 但没有收到 OpenAI 终止事件（`response.completed` / `response.done` / `response.failed` / `[DONE]`），也按流式中断处理并补发 `response.failed`。
- 如果上游在可见输出前已经发送 `response.failed` 或通用 `event: error`，只有命中 Codex profile 时，网关才会在原事件写给下游前改写为 `upstream_retryable_error` 的 `response.failed` 并结束；可见输出后不伪造整轮重试。
- 该失败事件也加入响应快照 chunks，便于使用记录保留完整链路。
- `frontend/src/views/settings/SettingsView.vue` 中“输出停顿上限（秒）”只说明行为，不在说明文案里重复默认秒数。

## 3. OpenAI Responses 流式兜底方案

### 3.1 问题定义

2026-05-13 排查确认过一种特殊失败形态：上游返回 `200 + text/event-stream`，但 SSE 事件内出现 `error.code = server_is_overloaded` 或 `slow_down`。这类失败不是 HTTP 非 2xx，不能只靠状态码错误策略识别。后续又确认过通用 `event: error`、缺少终止事件和上游读取中断等形态，本项目最终把处理边界收敛为“是否已经产生可见输出”，而不是围绕单个错误码或单个场景分别补偿。

Codex 对 `response.failed` 的处理有明确分支：如果 `data.type = "response.failed"` 且 `response.error.code` 是 `server_is_overloaded` 或 `slow_down`，会映射为 `ServerOverloaded`，客户端展示 `Selected model is at capacity. Please try a different model.`，并且 `is_retryable()` 为 `false`。所以如果网关把这两个原始错误码透传给下游，Codex 不会自动重试。

当前运行时采用“可见输出边界 + 客户端策略”兜底：不围绕单个 SSE 错误码维护特征规则，而是把所有可识别流式失败统一放到可见输出边界下处理。这里的 `upstream_retryable_error` + `response.failed` 已交给 `clientProfile = codex` 的策略层决定；Codex profile 只接受普通 JSON 对象格式的 `x-codex-turn-metadata.turn_id`，不接受 `turnId`、URL 编码 JSON 或数组 JSON；未识别到 Codex 时，网关按普通流式失败路径返回，不伪造 Codex 可重试码。

### 3.2 安全边界

项目内统一使用“重试”作为总称，并按输出边界分成两类：

- 未输出前重试：`outputSeen = false` 时，客户端尚未收到可见输出、工具参数或执行状态 delta，网关可以把命中特征的上游失败改写为客户端可重试错误，让客户端自动重试当前轮请求。客户端重试次数不由网关限制。
- 已输出后重放：`outputSeen = true` 后，客户端已经看到部分输出或执行状态变化，此时自动继续必须由服务端按“重放”处理，也统一归入项目重试规范。重放的输入必须来自本次请求已捕获的原始请求、上下文、账号调度信息和审计链路，不能临时拼接用户可见文本。服务端重放必须遵守临时不可调用的策略重试机制；重放仍失败时，网关把最后一次上游失败原样返回给客户端。

客户端自动重试由客户端自己控制次数，网关只负责在未输出前给出可重试的协议失败信号，不额外限制客户端重试。服务端重放由网关主动发起，必须复用临时不可调用的策略重试机制，不能无限重放；如果重放链路仍失败，返回给客户端的是最后一次上游失败原文，而不是再次改写后的 SSE。

因此，流式重试安全边界不是“是否已经发过任意 SSE 事件”，而是“是否已经向下游发送过可见输出或会改变客户端执行状态的 delta”。所有 UI 文案、配置项、日志、审计字段、计划文档和后续实现都必须遵守这个术语：`重试 = 未输出前重试 + 已输出后重放`。

下列事件不视为 `outputSeen`：

- `response.created`
- `response.in_progress`
- `response.metadata`
- 模型、限流、header 类元信息
- SSE 注释、心跳或其他不产生可见输出的事件

下列事件一旦写给下游，就必须视为 `outputSeen = true`：

- `response.output_text.delta`
- 工具调用参数 delta，例如 `response.custom_tool_call_input.delta`，以及后续兼容时可能出现的等价 tool/function argument delta
- `response.reasoning_summary_text.delta`
- `response.reasoning_text.delta`
- 任何携带可见 assistant 文本、工具调用参数或可执行状态变化的 `response.output_item.added` / `response.output_item.done`

只有 `outputSeen = false` 且命中对应客户端策略时，才允许把上游流式失败转换为客户端可重试错误。`outputSeen = true` 后不再按错误码豁免或伪造整轮重试；当前进入通用流失败计数，未来若要自动继续，必须走已输出后重放策略。

### 3.3 策略兜底模型

此前讨论过的流式错误码特征规则已下线，不进入系统设置页，也不开放给管理员临时配置。经过 `server_is_overloaded`、`slow_down`、通用 `event: error`、缺少终止事件和上游读取中断等样本复盘后，当前运行时不再维护流式错误码特征白名单，也不保留空的流式规则接口或前端页签，而是按可见输出边界和客户端策略处理：

- 可见输出前：命中 Codex profile 时，把可识别流式失败改写为 `upstream_retryable_error` 的 `response.failed`，结束下游 SSE，让 Codex 自行重试；未命中 Codex profile 时，不伪造 Codex 可重试码。
- 可见输出后：不改写、不按错误码豁免，进入通用流失败计数。
- 可见输出判断由 `openAIStreamEventHasVisibleOutput()` 统一提供，流式解析器和兜底判断必须复用同一函数，避免账号副作用与下游改写边界不一致。
- 失败事件识别只认明确失败形态：`response.failed`、通用 `event/type = error`、`response.error` 或 top-level `error` 对象；普通事件里的顶层 `code/message` 不单独触发失败兜底。
- 如果未来重新引入流式特征规则，必须证明当前可见输出边界和客户端策略无法覆盖，并补充比“是否有可见输出”更强的证据；届时再新增规则类型、只读接口、前端展示和回归，不提前保留空壳。历史规则模型只在 PLAN-0020 归档中保留，不放在现行功能文档里，避免维护时误以为仍有接口或规则表。

### 3.4 网关处理流程

流式转发不能只做原始字节级 `pipe` 后再字符串替换。要稳定执行可见输出前兜底，网关必须按 SSE 事件边界解析并在写下游前决策。

处理流程：

1. 上游返回 `2xx + text/event-stream` 后，网关进入 SSE 事件解析转发模式。
2. 每个完整 SSE 事件先解析 `event:`、`data:` 和 `data` JSON；解析失败或超限时按既有流式中断策略处理。
3. 写下游前更新 `outputSeen` 候选判断；只有会产生可见输出或工具状态变化的事件才置为 `true`。
4. 如果事件是 `response.failed`、通用 `event: error`，或携带可解析错误字段，则按 `outputSeen` 决定处理方式。
5. 可见输出前失败时，禁止把原始事件继续写给下游，也禁止继续转发后续上游事件。
6. 中止上游读取并释放当前账号并发槽；可见输出前失败不写账号流失败副作用。
7. 命中 Codex profile 时，向下游写入 OpenAI Responses `response.failed`，错误码统一使用 `upstream_retryable_error`；未命中时按普通流式失败返回。
8. 写入后立即结束下游 SSE。Codex 会在流结束后把该失败归类为 `CodexErr::Stream(...)` 并进入自身重试循环。
9. 后续阶段若命中已输出后重放，网关使用本次请求的原始请求快照和调度上下文重新发起请求。重放必须进入独立审计尝试，保留原始失败事件、重放原因和后续上游响应；重放期间遵守临时不可调用策略重试机制，仍失败时把最后一次上游失败原样返回客户端，不再改写 SSE。

推荐伪造事件格式：

```text
event: response.failed
data: {"type":"response.failed","response":{"status":"failed","error":{"code":"upstream_retryable_error","message":"Upstream returned a retryable stream failure before output. Please retry."},"usage":null}}
```

注意事项：

- Codex profile 可见输出前统一使用 `upstream_retryable_error` 作为 `rewriteErrorCode`，不能使用 `server_is_overloaded` 或 `slow_down`。
- 不能使用 `context_length_exceeded`、`insufficient_quota`、`usage_not_included`、`invalid_prompt`、`cyber_policy` 等 Codex 已特殊处理为终止类的错误码。
- 如果伪造 `response.failed` 后不关闭下游流，Codex 可能会继续等待直到 idle timeout，重试不会及时发生。
- 如果已经向下游发出原始失败事件，再追加伪造事件无法可靠覆盖客户端已解析的错误；拦截必须发生在原事件写出之前。

### 3.5 审计与使用记录

Codex 可见输出前失败兜底命中时，原始审计日志必须同时保留“上游原始事件”和“下游改写事件”，用于解释为什么客户端看到的是可重试错误，而上游真实返回是容量、降速或其他 SSE 内错误。实现上还会写入一段 `gateway_metadata` 审计原文，用结构化 JSON 记录客户端策略、拦截和改写关系，方便直接检索和排障。

`gateway_metadata` 中至少包含：

```text
stream_intercepted: true
intercept_rule_id
intercept_rule_name
intercept_action
upstream_event_type
upstream_error_code
rewrite_error_code
output_seen
account_policy
cooldown_minutes
```

使用记录建议以“客户端实际收到的可重试错误”为结果口径，同时通过响应快照、审计扩展字段和上游原始 payload 保留真实上游错误。这样客户端兼容层可被审计还原，排障时仍能定位真实上游问题。

账号策略同样以可见输出边界为准。可见输出前失败不写账号流失败副作用；可见输出后失败不再按 `server_is_overloaded` / `slow_down` 等错误码豁免，统一进入流失败计数。

### 3.6 验收口径

回归测试至少覆盖：

- Codex profile 下，上游 `200 + SSE` 返回 `response.created`、`response.in_progress` 后返回 `response.failed/server_is_overloaded`，且未出现 output delta：下游不能看到 `server_is_overloaded`，只能看到 `upstream_retryable_error`，并且连接立即结束。
- Codex profile 下，上游 `200 + SSE` 在可见输出前返回通用 `event: error` 或未知 `response.failed`：下游不能看到原始错误码，只能看到 `upstream_retryable_error`，账号不进入流失败计数。
- 非 Codex profile 下，同类可见输出前失败不得伪造 `upstream_retryable_error`。
- 同样场景下，账号不进入流失败计数；这是通用可见输出边界，不依赖具体错误码规则。
- 上游在 `response.output_text.delta` 后再返回 `server_is_overloaded`：网关不得伪造客户端整轮重试错误，按通用流失败计数处理；如果后续开启已输出后重放，必须按服务端重放策略处理，并在审计中标记为 replay。
- 审计中保留原始上游错误、改写后的下游错误、`output_seen` 和账号动作。
- 如果策略兜底误伤，回滚方式是调整可见输出或失败事件识别边界后发布；运行时不会提供管理页开关。

### 3.7 后续阶段

第一阶段只做未输出前客户端自动重试型拦截，不做已输出后重放请求。

已输出后重放作为第二阶段评估：在 `outputSeen = true` 后命中特征时，网关基于原始请求快照重新发起请求，并把重放尝试作为同一次客户端请求下的后续上游尝试记录。重放必须复用临时不可调用的策略重试机制，不能无限重放；如果重放链路仍失败，网关把最后一次上游失败原样返回客户端。该方案可以减少用户手动发送“继续”的频率，但必须处理响应 ID、turn state、审计多次上游尝试、请求预算、工具调用副作用和重复输出边界，复杂度高于第一阶段。

## 4. Claude Code 结论

Claude Code 的重试机制没有使用 OpenAI 的 `response.failed` 协议。

可确认的公开资料：

- Claude Code 错误文档说明：Claude Code 会自动重试 transient failure，包括 server errors、overloaded responses、request timeouts、temporary 429 throttles、dropped connections，默认最多 10 次；可通过 `CLAUDE_CODE_MAX_RETRIES` 与 `API_TIMEOUT_MS` 调整。
- Claude Code programmatic 文档说明：API request 遇到 retryable error 时，Claude Code 会在重试前输出 `system/api_retry` 事件，字段包括 `attempt`、`max_retries`、`retry_delay_ms`、`error_status` 和 `error`。
- `anthropic/claude-agent-sdk-typescript` changelog 提到新增 `api_retry` system messages，用于暴露 transient API errors 的重试尝试。

边界说明：

- 本次没有从 Claude Code 核心可读源码中确认具体实现；npm 包是打包产物，不适合作为可维护源码依据。
- 已删除本地临时 Claude / Anthropic SDK 目录，避免保留无效源码。
- 如果未来需要兼容 Claude Code 或 Anthropic 原生客户端，不能复用 OpenAI 的 `response.failed` 事件；应按 Claude / Anthropic 自己的事件、错误体和 SDK 行为单独适配。

## 5. 后续厂商接入规则

接入新厂商或新客户端前，先区分两个概念：

- 上游供应商协议：本服务如何请求 OpenAI、Anthropic、Gemini 等上游。
- 下游客户端协议：Codex、Claude Code、OpenAI SDK、Anthropic SDK 等客户端期望看到什么响应结构。

流式中断处理应遵循：

- 首段内容前失败：服务端可以按账号调度策略切换账号或重试。
- 首段内容后失败：服务端只发送对应客户端协议的失败事件并结束流，不在服务端换账号或重新请求上游续写。
- 错误事件必须使用客户端能识别且语义正确的协议格式。
- 是否能自动重试由客户端决定；服务端只负责给出明确、可识别、可归类的失败信号。

## 6. 开源中转项目对比

结论：没有看到可作为通用做法的“服务端续写重试”。主流处理大致分三类：

## 7. 2026-05-17 客户端策略分层补充

本次复盘确认：当前项目有些流式兜底行为是从 Codex 源码和现场问题推导出来的，早期实现层曾经放在通用 OpenAI stream 流程里；当前已经收敛到 Codex profile。后续不能在通用层继续叠加客户端专属行为，否则会影响普通 OpenAI SDK、Cherry Studio、NextChat、Claude Code 或其他 OpenAI-compatible 厂家的客户端。

策略分层必须区分：

- `upstreamAdapter`：上游账号适配方式，例如 `openai_api_key`、`openai_oauth_codex`。
- `downstreamProtocol`：下游响应协议，例如 `responses_sse`、`chat_completions_sse`、`json`。
- `clientProfile`：下游客户端行为，例如 `codex`、`generic_openai`，未来可扩展其他客户端。

Codex turn 级重试切号只允许在 `clientProfile = codex` 且 `downstreamProtocol = responses_sse` 时触发。Codex profile 的精确证据来自普通 JSON 对象格式的 `x-codex-turn-metadata`，其中必须有非空 snake_case `turn_id`。`turnId`、URL 编码 JSON、数组 JSON、`session_id`、`thread_id`、`x-client-request-id`、User-Agent、IP、请求体 hash 或模型名都不能单独兜底识别 Codex；它们最多作为审计字段或一致性校验字段。

同一 Codex turn 的状态键建议使用：

```text
systemAccountId + apiKeyId + groupId + endpoint + codex.turn_id + rawBodyHash
```

这个键只能证明“同一本地 API Key / 分组边界下，同一个 Codex turn 的同一请求体”，不能证明真实自然人用户。若无法构造该键，网关不得启用 Codex turn 策略，必须回到普通错误返回。

第 4 次切号的设计边界：

- 前 1 到 3 次可见输出前失败可以继续向 Codex 返回可重试失败，并记录 turn 级失败账号。
- 第 4 次及以后优先避让该 turn 已失败账号，尝试同分组其他可调度账号。
- 无法精准识别 Codex turn、没有可用备选账号或状态丢失时，不伪造更激进的重试事件，不扩大到全部客户端，按普通流式失败或上游错误返回。
- turn 级避让不等于账号健康惩罚，不直接写 `temporary_unavailable`、`rate_limited` 或 `error`。

现有实现已选择收紧路径：只在 Codex profile 下保留 `response.failed/upstream_retryable_error` 改写，generic OpenAI 客户端按普通失败返回。后续不能把 Codex 的 `turn_id`、重试次数和错误码策略写进通用 OpenAI gateway 层。
