# 流式中断与客户端重试调研

> 记录时间：2026-05-05。
> 当前阶段只有 OpenAI 供应商；对外主要面向 OpenAI 兼容客户端，其中重点客户端是 Codex。

## 1. 背景

网关流式响应分两个阶段：

- 首段内容到达前：客户端还没有收到模型输出，服务端可以安全切换账号或重试上游请求。
- 首段内容到达后：客户端已经收到部分输出，且可能已经写入会话历史、UI 状态、turn state 或内部缓存。服务端无法可靠续写不同客户端的上下文状态，不能安全换账号续写，否则会产生重复内容、分叉上下文、响应 ID / usage 不一致等问题。

因此，“输出停顿上限”只适合判断已开始输出后的流式响应是否中断。超时后网关应把失败明确告诉客户端并结束本次 SSE，而不是在服务端悄悄重试并继续拼接；是否重试、如何处理半截上下文，应交给客户端按自身协议和状态决定。

## 2. OpenAI / Codex 结论

当前 OpenAI 兼容客户端按 Codex 优先兼容。

Codex 可重试流式错误的关键源码证据来自本地参考源码：

- `F:\temp-project\openai-codex-main\codex-rs\core\src\session\turn.rs:1085`：先判断 `err.is_retryable()`，可重试才进入重试流程。
- `F:\temp-project\openai-codex-main\codex-rs\core\src\session\turn.rs:1090`：重试次数来自 provider 的 `stream_max_retries()`。
- `F:\temp-project\openai-codex-main\codex-rs\protocol\src\error.rs:193`：`CodexErr::Stream(..)` 属于 retryable。
- `F:\temp-project\openai-codex-main\codex-rs\codex-api\src\sse\responses.rs:346`：Codex 解析 OpenAI SSE 的 `response.failed`。
- `F:\temp-project\openai-codex-main\codex-rs\codex-api\src\sse\responses.rs:371`：`response.failed` 内未命中特殊致命错误的 error 会被映射为 `ApiError::Retryable`。

因此，OpenAI 兼容流式响应在已输出后中断时，网关应发送：

```text
event: response.failed
data: {"type":"response.failed","response":{"status":"failed","error":{"code":"upstream_stream_idle_timeout","message":"..."}}}
```

关于通用 `event: error`：

- Codex 的 SSE helper 只把 `data:` 内容传给后续解析，`event:` 名称本身没有进入 Responses 事件处理逻辑。源码位置：`F:\temp-project\openai-codex-main\codex-rs\codex-client\src\sse.rs:24` 到 `F:\temp-project\openai-codex-main\codex-rs\codex-client\src\sse.rs:25`。
- Codex 后续按 `data` JSON 的 `type` 字段分发事件。源码位置：`F:\temp-project\openai-codex-main\codex-rs\codex-api\src\sse\responses.rs:179` 到 `F:\temp-project\openai-codex-main\codex-rs\codex-api\src\sse\responses.rs:182`、`F:\temp-project\openai-codex-main\codex-rs\codex-api\src\sse\responses.rs:297` 到 `F:\temp-project\openai-codex-main\codex-rs\codex-api\src\sse\responses.rs:300`。
- `type: "response.failed"` 会被 Codex 识别并按错误类型决定是否重试；未知 `type` 只会被 trace 后忽略。源码位置：`F:\temp-project\openai-codex-main\codex-rs\codex-api\src\sse\responses.rs:346` 到 `F:\temp-project\openai-codex-main\codex-rs\codex-api\src\sse\responses.rs:374`、`F:\temp-project\openai-codex-main\codex-rs\codex-api\src\sse\responses.rs:425` 到 `F:\temp-project\openai-codex-main\codex-rs\codex-api\src\sse\responses.rs:430`。
- 所以不能把 `event: error` 当成跨客户端、跨供应商的统一失败协议；即使外层写 `event: error`，也必须保证 `data.type` 是目标客户端能识别的协议事件。对 Codex / OpenAI Responses 来说，可靠做法仍是发送 `type: "response.failed"`，并建议 `event:` 也保持 `response.failed`，便于日志、调试和其他严格 SSE 客户端识别。

错误码策略：

- `upstream_stream_idle_timeout`：已收到首段内容后，超过输出停顿上限没有新内容。
- `upstream_stream_interrupted`：已收到首段内容后，连接或读取过程异常中断。
- 不要伪造 `context_length_exceeded`、`insufficient_quota`、`invalid_prompt`、`server_is_overloaded` 等 Codex 已特殊处理的致命或非同类错误。

当前实现落点：

- `backend/src/modules/gateway/openai-gateway.routes.ts` 的 `pipeUpstreamStream()` 在 catch 分支写入 `response.failed` 后再结束响应。
- 如果上游正常 EOF 但没有收到 OpenAI 终止事件（`response.completed` / `response.done` / `response.failed` / `[DONE]`），也按流式中断处理并补发 `response.failed`。
- 如果上游已经发送 `response.failed`，网关不再重复补发失败事件，只记录失败并结束。
- 该失败事件也加入响应快照 chunks，便于使用记录保留完整链路。
- `frontend/src/views/settings/SettingsView.vue` 中“输出停顿上限（秒）”只说明行为，不在说明文案里重复默认秒数。

## 3. Claude Code 结论

Claude Code 的重试机制没有使用 OpenAI 的 `response.failed` 协议。

可确认的公开资料：

- Claude Code 错误文档说明：Claude Code 会自动重试 transient failure，包括 server errors、overloaded responses、request timeouts、temporary 429 throttles、dropped connections，默认最多 10 次；可通过 `CLAUDE_CODE_MAX_RETRIES` 与 `API_TIMEOUT_MS` 调整。
- Claude Code programmatic 文档说明：API request 遇到 retryable error 时，Claude Code 会在重试前输出 `system/api_retry` 事件，字段包括 `attempt`、`max_retries`、`retry_delay_ms`、`error_status` 和 `error`。
- `anthropic/claude-agent-sdk-typescript` changelog 提到新增 `api_retry` system messages，用于暴露 transient API errors 的重试尝试。

边界说明：

- 本次没有从 Claude Code 核心可读源码中确认具体实现；npm 包是打包产物，不适合作为可维护源码依据。
- 已删除本地临时 Claude / Anthropic SDK 目录，避免保留无效源码。
- 如果未来需要兼容 Claude Code 或 Anthropic 原生客户端，不能复用 OpenAI 的 `response.failed` 事件；应按 Claude / Anthropic 自己的事件、错误体和 SDK 行为单独适配。

## 4. 后续厂商接入规则

接入新厂商或新客户端前，先区分两个概念：

- 上游供应商协议：本服务如何请求 OpenAI、Anthropic、Gemini 等上游。
- 下游客户端协议：Codex、Claude Code、OpenAI SDK、Anthropic SDK 等客户端期望看到什么响应结构。

流式中断处理应遵循：

- 首段内容前失败：服务端可以按账号调度策略切换账号或重试。
- 首段内容后失败：服务端只发送对应客户端协议的失败事件并结束流，不在服务端续写。
- 错误事件必须使用客户端能识别且语义正确的协议格式。
- 是否能自动重试由客户端决定；服务端只负责给出明确、可识别、可归类的失败信号。

## 5. 开源中转项目对比

本地参考目录：`F:\temp-project`。调研重点是“首段内容已发给客户端后，服务端是否尝试重试并续写同一个流”。

结论：没有看到可作为通用做法的“服务端续写重试”。主流处理大致分三类：

- 首包前或 HTTP 状态级重试：请求还没真正向客户端输出时，可以换上游或重试。
- 流中断后记录 / 关闭：已输出后如果上游 EOF、读错误、客户端断开，通常只记录或结束。
- 发送协议内错误事件：少数项目会发通用 `event: error`，但不一定是 OpenAI / Codex 可识别的 `response.failed`。

具体项目观察：

- `new-api`：
  - `F:\temp-project\new-api\relay\helper\stream_scanner.go` 使用 scanner 转发 SSE，维护 timeout、client_gone、scanner_error、eof 等结束原因，并支持 ping。
  - `F:\temp-project\new-api\relay\common\stream_status.go` 把 `done`、`eof`、`handler_stop` 视为正常结束。
  - 没看到首段输出后重新请求并续写；也没看到针对 OpenAI Responses 的 `response.failed` 补发。
- `one-api`：
  - `F:\temp-project\one-api\relay\adaptor\openai\main.go` 逐行转发 OpenAI SSE；如果没收到 `[DONE]`，最后会主动 `render.Done(c)`。
  - 这能让很多普通 OpenAI Chat Completions 客户端收尾，但对 Codex / Responses API 的“失败可重试”语义不够明确。
- `LiteLLM`：
  - `F:\temp-project\litellm\litellm\a2a_protocol\main.py` 明确写了 `Only retry on first chunk, not mid-stream`。
  - `F:\temp-project\litellm\litellm\router.py` 有 `stream_timeout` 配置入口。
  - `responses` 类型里支持 `response.failed`，但本次没有看到把任意网关流中断统一转换成 `response.failed` 后让客户端重试的通用逻辑。
- `Helicone AI Gateway`：
  - `F:\temp-project\helicone-ai-gateway\ai-gateway\src\dispatcher\client.rs` 会先等待第一个 SSE event，用于在响应真正返回前传播错误。
  - `F:\temp-project\helicone-ai-gateway\ai-gateway\src\dispatcher\service.rs` 的 `dispatch_stream_with_retry` 只对 `StreamError::is_retryable()` 的建流阶段错误重试。
  - 流已经返回后，后台读取遇到错误会通过通道返回 stream error，没有看到服务端续写重试。
- `Portkey Gateway`：
  - `F:\temp-project\portkey-gateway\src\handlers\retryHandler.ts` 基于 HTTP status / timeout 做 request retry。
  - `F:\temp-project\portkey-gateway\src\handlers\streamHandler.ts` 负责读取和转换 ReadableStream。
  - 没看到流已输出后按 OpenAI `response.failed` 补错误并让 Codex 自动重试的逻辑。
- `proxify`：
  - `F:\temp-project\proxify\controller\proxy.go` 对流响应直接 copy，客户端断开或上游读错误就返回。
  - `F:\temp-project\proxify\infra\stream\smoothing.go` 主要做 SSE 平滑和客户端断开处理。
  - 没有服务端续写重试。
- `RelayPlane Proxy`：
  - `F:\temp-project\relayplane-proxy\src\streaming.ts` 上游非 2xx 或读取异常时会发通用 `event: error`，`close()` 会发送 `[DONE]`。
  - 这不是 OpenAI Responses 的 `response.failed`，Codex 未必会按可重试流错误处理。
- `Envoy AI Gateway` / `agentgateway`：
  - 主要是路由、超时、重试和协议 schema 层能力。能配置 request / stream idle / retry 等网关策略。
  - 没看到面向 Codex 的 OpenAI Responses 流中断 `response.failed` 合成逻辑。

对本项目的影响：

- 服务端不应在首段输出后尝试“续上”；这个结论和开源中转项目的常见做法一致。
- 当前项目面向 Codex，应比普通中转更明确：已输出后空闲/中断要发送 OpenAI Responses 协议内的 `response.failed`，这样客户端可以按自己的重试策略处理。
- 未来接入其他客户端时，不能简单复用 `response.failed`，应分别补对应客户端协议的失败事件。
