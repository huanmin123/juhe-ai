## 1. 结论与范围

### 1.1 要解决的问题

接收方确认治理把一次授权从「发起」到「可用」拉成了五段长链（所有者确认 → 团队审批 → 成员逐人接受 → 绑定/启用 → material change 重新确认），叠加快照、cooldown、限额、TTL 与通知面后，维护面远大于使用价值。2026-11-22 用户裁决：授权模型整体退回「使用权分享」的轻量形态——发送即达、成员各自领取、领取即生效；治理体系（审批/复核/快照/冷却/额度/TTL）随 revision 28 治理体系一并退役，不保留兼容开关。

### 1.2 目标

- **发送即达**：所有者发起、管理员代建一律直接发送，grant 创建即 `pending`；无所有者审批、无团队审批、无成员接受位；无 cooldown、无限额、无 pending TTL。
- **以成员为主**：个人授权产生 1 条待领取来源；团队授权按在册成员各产生 1 条 pending 来源，各自领取；新成员加入团队可再领取；成员移除级联撤销其来源。
- **领取即生效**：分组授权领取直接生效；账户授权领取一步完成「创建授权实例 + 绑定自己分组」。
- **状态词表收敛**：grants / sources / runtime 三层共用 7 值词表 `pending / active / paused / expired / revoked / returned / declined`；终态必填 `ended_at / ended_reason`。
- **调度实时跟随**：分组授权无快照，候选按 `group_accounts` 真实成员行实时解析；唯一可见性闸门是 `group_authorization_settings` 行存在性。
- **保留最小生命周期动作**：暂停/恢复、延长（可恢复到期）、回收、拒绝、归还、`expires_at` 有效期。

### 1.3 非目标

- 不改变 `/v1` 对外协议、网关路由层级（API Key → 路由策略 → 分组 → 账户）或供应商/协议面。
- 不改变授权消耗统计的「资源 × 用户」主维度；统计口径与 [系统团队与统一授权设计](系统团队与统一授权设计.md) 保持一致。
- 不重新引入任何已退役机制（cooldown、额度、快照、修订确认、TTL、通知、suspensions）；需要限制使用时用暂停/回收。
- 不提供旧授权模型（单方面即时生效，或 revision 28 审批链）的运行开关或双写。

### 1.4 与旧模型的差异总览

| 维度 | 旧模型（revision 28 治理，已废弃） | 本模型（revision 31） |
| --- | --- | --- |
| 发起 | offer + 所有者确认 + 团队审批 | 直接发送，grant=`pending` |
| 接收方动作 | accept（携带修订号）+ 绑定/启用 | 领取（accept）一步生效 |
| 分组授权范围 | 快照表 + refresh-scope + 逐账户 reconfirm | 无快照，实时跟随 `group_accounts` |
| 来源修订 | material change → `needs_review` 硬阻断 | 无修订闸门，来源事实实时读取 |
| 额度 | `limits_json` + quota 绑定 | 退役，无额度输入 |
| 重复防护 | cooldown + 限额 + pending TTL | 幂等返回 + `offer_already_active` |
| 通知/屏蔽/暂停发起 | 表 + 用户面 | 全部退役 |

## 2. 目标模型与核心原则

### 2.1 核心原则

1. **发送即达（Send, not ask）**：创建授权只产生 `pending` grant 与待领取来源，不产生运行时副作用；接收方在授权中心看到来源即可领取。管理员代建与所有者本人发起走同一状态机，不再区分审批位。
2. **领取即生效（Claim, then use）**：账户资源领取 = 同事务「创建/复用授权实例 + 写入接收方自己分组的 `group_accounts` 绑定」；分组资源领取 = upsert `group_authorization_settings` 行，生效条件即行存在。领取后无第二步。
3. **以成员为主（Members own their sources）**：团队授权只是分发渠道，团队 grant 不承载同意语义；每个成员对自己的来源独立领取/拒绝/归还，团队 grant 状态由来源聚合推导。
4. **持久退出（Durable exit）**：拒绝、归还持久有效；终态来源不复用、不复活；重新发起一律追加全新 `pending` grant，旧终态行保持归档。
5. **实时事实源（Live facts）**：网关不信任过期投影——调度时校验 runtime、有效来源、父 grant 三层在请求时刻一致；分组授权成员行按 `group_accounts` 实时解析，无快照缓冲。
6. **资源类型显式（Resource-type explicit）**：账户资源建授权实例，分组资源建 settings 行；两条分支在 accept、runtime 推导、网关预检、级联撤销中显式区分，不共用「创建实例」逻辑。

### 2.2 分层关系

```text
资源所有者发起（管理员代建同状态机）
        ↓ grant=pending；个人→1 条 manual 来源；团队→每在册成员 1 条 team 来源
接收方在授权中心领取（POST /my-authorization-sources/{id}/accept）
        ↓ 账户：实例 + group_accounts 绑定；分组：group_authorization_settings 行
        ↓ source=active，grant=active，runtime 按 §3.2 推导
网关按既有 API Key → 路由策略 → 分组 → 账户 链路调度（§8 活性谓词）
```

### 2.3 术语

| 术语 | 定义 |
| --- | --- |
| 授权方 | 发起授权的系统账户；管理员代建时 `created_by` 是管理员，资源归属人恒为 `resource_owner_system_account_id`。 |
| 资源所有者 | 拥有 AI 账户或分组的系统账户；始终可暂停、恢复、延长、缩短或回收自己资源的授权。 |
| 接收方 | 被授权系统账户；团队授权场景下是团队内每个在册成员。 |
| grant（业务记录） | `resource_authorization_grants`，表达「某资源拟授权给某用户或团队」；ID 前缀 `rauthgrant_`。 |
| 来源（source） | `resource_authorization_sources`，接收方维度的领取单元；`manual`（个人）/ `team`（团队）；ID 前缀 `rauthsrc_`。 |
| 运行时（runtime） | `resource_authorizations`，某资源对某系统账户的稳定投影；网关读取的唯一授权状态；ID 前缀 `rauth_`。 |
| 领取（claim/accept） | 接收方对 pending 来源执行 `POST /my-authorization-sources/{id}/accept`，一步完成生效。 |
| 授权实例 | `accounts` 表中 `authorization_instance_authorization_id` 非空的派生账户行；承载被授权侧本地状态。 |
| 调度偏好 | 接收方对授权实例的组内优先级/超级优先/降级备用标记（`group_accounts.local_*` 列）。 |

## 3. 状态机与推导规则

### 3.1 状态词表

三层共用 7 值词表（CHECK 同形）：

| 状态 | grants | sources | runtime | 含义 |
| --- | --- | --- | --- | --- |
| `pending` | 是 | 是 | 是 | 已发送，等待领取 |
| `active` | 是 | 是 | 是 | 已领取且生效 |
| `paused` | 是 | 否（来源不变） | 是（推导） | 授权方暂停；来源状态不变 |
| `expired` | 是 | 是 | 是 | `expires_at` 到期（`ended_reason='authorization_expired'`） |
| `revoked` | 是 | 是 | 是 | 回收/资源删除/成员移除/团队级联 |
| `returned` | 是 | 是 | 是 | 接收方归还 |
| `declined` | 是 | 是 | 是 | 接收方拒绝 |

退役状态（不得再写入，revision 31 存量收敛见 §9）：`pending_owner_approval`、`pending_team_approval`、`pending_member_acceptance`、`needs_review`、`dormant`、`superseded`、`acceptance_mode`。

约束：

- 终态（`expired` / `revoked` / `returned` / `declined`）必填 `ended_at` 与 `ended_reason`（grants / sources 两层 CHECK）。
- 终态不可逆，除 §5.3 的 extend 恢复（仅 `authorization_expired`）外不得复活。
- 所有状态迁移锁定目标 grant/source/runtime 行并使用带当前状态条件的 UPDATE；影响行数为 0 返回 `409 state_conflict` 或重读重试。锁顺序统一为 grant → runtime → source → settings。
- `source_type='manual'` 必须 `source_team_id IS NULL`，`team` 必须非空（建表 CHECK）。

### 3.2 runtime 推导（recomputeRuntime）

`resource_authorizations.status` 是物化投影；每次来源变化都在同事务内重算（锁定 runtime 与其全部来源、以及各来源父 grant）。推导顺序，每步命中即止：

1. **activeSource**：存在 `status='active'` 的来源且其父 grant `active` 且未过期（`expires_at` 为空或晚于当前时刻）→ runtime `active`。多条候选时取 `activated_at` 最早（并列取 `id` 最小）的一条作为有效来源，同步写 `effective_source_type` / `effective_source_team_id` 与 `expires_at`（跟随有效来源父 grant）。
2. **pendingParent**：存在 `status='pending'` 的来源且父 grant `pending` 或活跃 → runtime `pending`。
3. **pausedParent**：存在父 grant `paused` 的来源 → runtime `paused`。
4. **latestTerminal**：按最近终态来源（`ended_at DESC, id DESC`）取其状态作为 runtime 终态；更早的 `expired` 不覆盖更新的 `returned` / `revoked` / `declined`。
5. **兜底**：无任何来源 → runtime `revoked`（`no_sources` 语义；正常创建后至少有一条来源）。

补充规则：

- `grant_id` 为空的来源 fail closed：不参与推导、不可调度。
- 非终态投影的 `expires_at` 恒镜像有效来源父 grant（含清空）；只有终态且无来源到期值时保留旧值供审计。
- runtime 进入终态时同事务停用绑定（`group_accounts.enabled=0`）与授权实例（`status='disabled'`、`schedulable=0`），行保留供重新领取时复用；`group_authorization_settings` 行不动——分组授权可见性只由 runtime 状态表达。
- runtime `pending` / `paused` / 终态即使存在绑定，网关也必须阻断（§8）。

### 3.3 重复发起幂等

同一资源 + 同一接收方（个人按 `grantee_system_account_id`，团队按 `grantee_team_id`）已有**开放 grant**（`pending` / `active` / `paused`）时：

| 已有 grant 状态 | 行为 |
| --- | --- |
| `pending` | 幂等返回原 grant 与其 pending 来源（`created=false`），不重复创建、不追加来源 |
| `active` / `paused` | 返回 `409 offer_already_active`，不创建新记录 |
| 全部为终态（`expired` / `revoked` / `returned` / `declined`） | 一律 INSERT 全新 `pending` grant + 全新来源，不复用旧行、不清写旧终态字段 |

开放 grant 之外不设部分唯一索引之外的额外约束：`offer_already_active` 由应用层在创建事务内判定，而非数据库唯一索引。

### 3.4 团队聚合

团队 grant 不是成员级同意的主体；成员只能操作自己的来源。团队 grant 聚合规则：

1. 存在任一非终态来源 → 团队 grant 保持当前状态（首个成员领取后 `pending` → `active`）。
2. 当前周期存在至少一条来源且全部终态 → 团队 grant 按来源终态聚合（存在资源删除原因取 `revoked`；否则按最近终态/是否曾领取取 `declined` / `expired` / `returned` / `revoked`），写 `ended_at` / `ended_reason`。
3. 聚合前锁定团队 grant 行；「全部」分支必须先满足「当前周期至少一条来源」。
4. 个人 `manual` grant 归还/拒绝直接置同状态；来源被撤销而 runtime 有其他有效来源时，个人 grant 可保持 `active`，由来源聚合函数按非终态来源计数决定。

## 4. 授权实例使用面契约

被授权账户在接收方处**几乎等价自有账户使用**；业务数据（使用记录、统计、日志归属）完全隔离并按授权维度记账。

### 4.1 能做什么

- **调度标记**：可修改组内优先级、降级备用（`fallbackEnabled`）、超级优先（`superPriorityEnabled`）；写入 `group_accounts.local_*` 列，只影响接收方自己的分组绑定。
- **停用/启用**：可停用自己的授权实例（`status='disabled'`），只影响自己的实例；重新启用恢复。
- **限频下调**：实例的并发数 / RPM 限频可下调；**不能超过父**——来源账户限值 > 0 时，实例值超出来源限值直接拒绝（`validateInstanceLimitAgainstSource`）；来源限值为 0（不限制）时实例可自设。
- **实例限频经白名单通道**：`PATCH /my-accounts/{id}/authorized-dispatch`，字段白名单 `expectedConfigRevision` / `status` / `priority` / `superPriorityEnabled` / `fallbackEnabled` / `concurrencyLimit` / `rpmLimit` / `clearFailureState`。
- **清理失败态**：`clearFailureState` 清理实例自身的冷却/限流/异常运行态（来源账户运行态不受影响）。
- **使用侧编辑**：通用账户编辑路径对授权实例只接受使用侧字段（名称、备注、状态、标签、清失败态、本地分组绑定）；改绑自己的分组仅接收方本人可执行，管理员代绑定/解绑被拒绝（`authorization_binding_forbidden`）。前端编辑弹窗实际开放加入分组、标签与锁死配置，名称/状态在弹窗中禁用（状态走菜单停用/启用，优先级与限频走列表行内白名单通道）。

### 4.2 不能做什么

- **来源侧不可编辑、无克隆**：授权编辑弹窗对来源侧字段全部只读展示（凭据、Base URL、供应商/协议、模型映射、代理、连接、健康检查、时间计划、到期）；不提供克隆/导入/导出/转移；通用写路径对实例提交来源字段一律 `400`（`authorized_instance_source_field_rejected` 等既有错误码）。
- **不可二次授权**：授权实例不能作为授权资源再授权（资源解析阶段拒绝 `authorization_instance_authorization_id` 非空的账户）。
- **不能删除伪装归还**：通用删除/批量删除路径拒绝授权实例；删除来源账户走授权域级联撤销（§5.5）。
- **账户列表无授权操作入口**：账户列表与 `my-accounts` API 均无「归还授权」按钮/端点——`POST /my-accounts/{id}/return-authorization` 已退役（404）；归还统一在授权中心按来源执行。分组授权退订仍在分组列表：`POST /my-groups/{id}/return-authorization` 存活。
- **限频全局不隔离**：多个接收方共用同一源账户时，共享源账户的全局并发与每分钟请求数上限（实例级限频只是接收方侧的本地下调，不改变源账户全局预算）。

### 4.3 与来源账户的运行时关系

- 授权实例是独立 `accounts` 行（独立状态、冷却、调度标记、用量归属），但真实上游事实（凭据、连接、模型、代理、并发源限值）实时从来源账户读取；实例静态字段在领取/重新领取时从来源同步（`syncInstanceFromSource`）。
- 来源账户停用、异常、冷却、删除会通过 `effectiveAvailability` 阻断实例候选，但不回写实例行。

## 5. 核心流程

### 5.1 发起（CreateOffer）

输入：`resourceType`（`account` / `group`）、`resourceId`、`granteeType`（`system_account` / `team`）、精确 `granteeUsername`（或管理员 `granteeSystemAccountId`）、精确 `teamName`（或管理员 `teamId`）、可选 `remark` / `expiresAt`。

1. 校验 actor 是资源归属人；管理员必须通过 `systemAccountId` 指定资源归属人且该值必须等于资源实际归属。
2. 校验资源存在：账户未删除且非授权实例；分组必须 `group_kind=standard`（超级分组拒绝）。
3. 解析接收方：不存在/停用返回 `grantee_not_found` / `team_not_found`；接收方不能是资源所有者（`self_authorization_forbidden`）。
4. 幂等判定按 §3.3；通过后创建全新 `pending` grant（写入 `source_revision` 基线，仅展示/审计用途）。
5. 个人：复用或创建 runtime（非 pending 时重置为 pending 并清空撤销字段），追加 `manual` pending 来源（同 grant 已有 pending 来源时幂等复用该行）。
6. 团队：按在册活跃成员（排除资源所有者本人）逐成员复用/创建成员 runtime 并追加 `team` pending 来源；单成员已有该 grant 的 pending/active 来源时跳过。
7. 不创建实例、不写 `group_accounts`、不写 settings；提交后失效网关治理缓存。

管理员代建与所有者发起行为完全一致，仅 `created_by` 记录管理员。

### 5.2 领取（ClaimSource / accept）

`POST /my-authorization-sources/{sourceId}/accept`，请求体可选 `targetGroupId`（仅账户资源）。

1. 锁定 grant → runtime → source；校验 actor 是 runtime 的接收方；来源必须 `pending`、父 grant 非 `paused` 且 `pending` / `active`。
2. 团队来源额外校验：团队存在且活跃、逻辑删除标记为空、actor 仍是活跃在册成员（防止成员移除级联遗漏后残留领取入口）。
3. 校验资源仍归属原所有者且未被删除/未变为授权实例；不满足时撤销该来源（`ended_reason='resource_changed'`）并返回 `resource_changed`。
4. **账户资源**：创建或复用授权实例（`authorization_instance_authorization_id` = runtime ID），同步来源静态字段；`targetGroupId` 校验为接收方自己的启用普通分组，缺省回落接收方在源账户供应商下的默认分组（`defaultGroupIDForProvider`）；同事务写入 `group_accounts` 绑定（`account_authorization_id` = runtime ID，`enabled=1`）。实例已存在于其他分组时按既有换组语义移动，不产生多活跃绑定。
5. **分组资源**：upsert `group_authorization_settings` 行（`authorization_id` 主键、`system_account_id` = 接收方、`group_id` = 资源 ID、`group_type='personal'`）；行存在 + runtime `active` 即生效（§8 谓词），无启用开关、无快照。
6. 来源 `pending → active`（写 `accepted_at/by`、`activated_at`，清终态字段），个人/团队 grant 同事务 `pending/active → active`；重算 runtime；提交后失效缓存。
7. 返回 `{ sourceId, status: "active", instanceId?, bound }`。

领取即生效，无第二步绑定/启用；返回的 `bound=true` 表示账户授权绑定已完成。

### 5.3 暂停、恢复、延长、到期

- **暂停/恢复**：仅 `active` grant 可暂停（`state_conflict`）；`paused` 可恢复。父 grant 状态变化后重算其全部 runtime；来源状态不变。暂停期间领取请求返回 `state_conflict`（授权已暂停）。
- **延长（extend）**：`POST .../extend` 接受 `expiresAt`，必须晚于当前时刻（`active` 还要求晚于当前 `expires_at`）。`active` 直接更新到期时间并重算 runtime；`expired` 且 `ended_reason='authorization_expired'` 时恢复：来源按是否曾领取（`accepted_at` 非空）分别回到 `active` / `pending`，清终态字段，grant 恢复为 `active`（有已领取来源）或 `pending`；其他 `ended_reason` 的 expired 返回 `no_restorable_source`。`paused` 不能直接延长（先恢复）。
- **缩短**：`PATCH /my-authorizations/{id}/expire`（管理面 `/authorizations/{id}/expire`）只接受 `expectedUpdatedAt` + `expiresAt`，新值必须晚于当前时刻、早于现值（缩短语义）；完整 PATCH 只允许备注与缩短到期。
- **到期**：gateway 进程内 `authz-governance-sweep` 组件（每分钟一轮、单批 200）调用 `ExpireDueOffers`：把 `expires_at` 已过的非终态 grant/source 翻转为 `expired`（`ended_reason='authorization_expired'`），重算受影响 runtime。jobs 侧 `resource-authorization-expiry-sweep` 任务与 gateway `authz-expiry-runtime-sync` 组件（`ReconcileExpiredGrants` 幂等重放）作为到期面的另一路收敛，两条路径都只翻转 `expires_at` 已过的非终态行。**待领取不过期**：未设置 `expires_at` 的授权不参与扫描，`pending` 来源无限期等待领取。
- **回收（revoke）**：授权方/管理员 DELETE；非终态来源统一 `revoked`，终态来源保持原状；重算 runtime，runtime 终态时停用绑定与实例。重新发起创建全新 pending grant。

### 5.4 拒绝、归还、团队级联

- **拒绝（decline）**：来源 `pending → declined`（写 `declined_at/by`、`ended_at/ended_reason='declined'`）；个人 grant 同步终态；团队来源只改成员来源并按 §3.4 聚合。
- **归还（return）**：来源 `active → returned`；个人 grant 同步；团队按聚合。runtime 终态时停用绑定与实例；存在其他有效来源（如个人来源 + 团队来源并存）时 runtime 保持可用。重新发起后接收方重新领取，旧绑定不自动恢复（实例复用时重新绑定）。
- **成员移除（RevokeTeamSourcesForMemberTx）**：在团队成员移除事务内，撤销该成员在该团队全部 grant 上的非终态 team 来源（`ended_reason='member_removed'`）、重算其 runtime；终态来源保持原状。
- **团队停用**：撤销该团队全部非终态 team 来源与 grant（`ended_reason='team_disabled'`）。**团队重新启用不复活旧来源**；成员重新加入团队（未被移除级联命中或有全新 grant）时可再领取——新 pending 来源的创建不受成员 `declined` / `returned` 历史阻断。
- **新增成员**：团队授权在 `pending` / `active` 期间，管理员添加成员在同一事务内为该成员创建成员 runtime 与 pending 来源（与创建时同构）；无 TTL、无 reinvite 概念。

### 5.5 资源删除级联

- **来源账户删除**（`delete_resource`）：该账户的全部非终态来源 `revoked`（`ended_reason='account_deleted'`）、对应 grant 同步撤销、runtime 重算；授权实例随账户删除链路处置，接收方绑定停用。
- **分组删除**：`groups/store.go` 删除事务内撤销该分组全部非终态 grant / 来源（`ended_reason='group_deleted'`）、runtime 置 `revoked`，删除该分组的 `group_authorization_settings` 行（外键级联）。
- **归属人变化**：资源 `system_account_id` 被改写且资源自身是授权对象时，领取/调度路径检测到归属不一致即撤销来源（`resource_changed`），接收方需获得新归属人的新授权。
- 授权历史（grant/source/runtime 终态行）保留用于审计，不物理删除。

## 8. 网关与调度

### 8.1 分组授权活性谓词

分组授权生效条件（调度实时判定，无快照）：

1. **claim 行存在**：`group_authorization_settings` 中存在该 runtime 的行（SQL 层即 `authorization_id IS NOT NULL`，LEFT JOIN 后判 `gs.authorization_id IS NOT NULL`）；
2. **runtime / grant 活跃**：`resource_authorizations.status='active'` 且 `expires_at` 未过期，且有效来源 `status='active'` 且其父 grant `active` 且未过期（`runtimeSourceRevisionOK`——runtime、父 grant、有效来源三层在请求时刻一致，不信任滞后投影）；
3. **成员行实时**：候选账户按 `group_accounts` 真实成员行解析（`enabled=1`、账户当前归属人仍是分组归属人），叠加既有账户可用性闸（状态、调度、冷却、到期、凭据、连接、模型）。

落点：

- `gatewayruntimecache/sqlruntime.go`（运行时缓存授权臂）、`routestrategies/bindings.go`（策略路由绑定读校验）、`groups/store.go`（分组列表/删除级联）、`super_members.go`（超级分组成员展开）、`chain_accounts.go`（`runtimeSourceRevisionOK` / `groupSnapshotAllows` 请求时门）、`chain_media_video.go`（媒体链同款门）。
- 策略路由绑定写前校验 `ValidateGroupBinding` 同为活性校验：runtime `active` + settings 行存在 + 归属一致 + 未过期 + 有效来源在活跃 grant 之后。
- chat-pinned、媒体、realtime 等所有候选加载路径共用同一谓词；pinned 只能跳过健康可用性，不能跳过授权。

### 8.2 账户授权活性谓词

候选账户为授权实例时：实例 `status='active'`、`schedulable=1`、绑定 `group_accounts.enabled=1` 且 `account_authorization_id` 对应当前 runtime、runtime + 有效来源 + 父 grant 三层活跃未过期（同 `runtimeSourceRevisionOK`）、来源账户可用（`effectiveAvailability`）。

### 8.3 限频

- 实例限频（并发/RPM）只能 ≤ 来源限值：来源限值 > 0 时校验拒绝（`validateInstanceLimitAgainstSource`），来源不限（0）时实例自设。
- 多接收方共用源账户时共享源账户全局并发与每分钟请求数预算；无授权维度独立配额（额度已退役）。

### 8.4 缓存与失效

创建、领取、拒绝、归还、暂停、恢复、回收、到期、延长、资源删除级联、成员级联都必须在提交后失效相关网关治理缓存（`invalidateGovernance` + 既有 runtime 失效链）；缓存 TTL 仅兜底，不作为安全边界。

## 9. schema revision 31 与升级

### 9.1 升级步骤

- 步骤：`authz-claim-simplification`（revision 31，target primary）。
- 标记：`Destructive=true`、`RequiredBeforeStartup=true`——expand 相被引擎过滤，contract/all 相执行；不能用 `--phase=expand` 跳过。
- `Satisfied` / `Verify` 同源判据：四张退役表全部缺席 + grants status CHECK 不含旧审批词表 + 全部退役列缺席 + 授权来源 quota scope binding 行清零；fresh 库 ensure 即目标形状，Satisfied 即刻为真。
- **单事务**原子执行：
  1. `DROP TABLE` ×4（互不引用，任意序安全）；
  2. `DROP COLUMN` ×29（§7.2 清单；依赖退役列的索引/CHECK 由 PG 自动删除）；
  3. 显式 DROP 9 条退役 CHECK（含会挡收敛路径的 `pending_expiry` 等）；
  4. 存量状态收敛为 7 值词表：grants `pending_owner_approval` / `pending_team_approval` / `pending_member_acceptance` → `pending`；sources `dormant` / `needs_review` → `pending`、`superseded` → `returned`（补 `ended_at=COALESCE(ended_at, updated_at)`）；runtime `needs_review` → `pending`；
  5. 重建 3 个 7 值 status CHECK（收敛后数据必然满足，全量校验建立）；
  6. `DELETE` `request_quota_hourly_window_scope_bindings WHERE source_type='resource_authorization_grant'`（额度全链退役，授权绑定域随之退役；api_key 来源行不动）。
- 缺失对象是良性 no-op；DROP 不可回滚，执行前必须完成可恢复备份（发布 runbook 停写 + 备份门禁）。

### 9.2 发布基线

- `contracts.SchemaRevision=31`、`MinRequiredRevision=31`；`BusinessSchemaVersion` 保持 `business-postgres-gateway-v26`（无新增 gateway 契约列）。
- 发布基线为 **revision 27/28/29/30/31 合并批次**：revision 28（`authz-recipient-consent-governance`）、29（`capability-domain-vector-rerank`）、30（`capability-domain-declaration-retirement`）、31（`authz-claim-simplification`）四个数据/破坏步骤均 `RequiredBeforeStartup=true`，必须 `upgrade --phase=all` 停写窗口一次执行；revision 27 为纯 DDL 空号随基线同窗收敛。库在任何更低 revision（含 26/27/28/29/30）都必须按合并基线 `--phase=all` 执行，不存在 expand 中间窗口。
- 升级完成后 `schema_state.min_readable_binary_revision=31`，旧二进制被启动门禁拒绝；revision 31 DROP 后不存在「换回旧二进制」回滚路径，只能前向修复或恢复停写备份。gateway / jobs / frontend 必须同批发布。
- 部署命令、窗口序列与验收见 `docker/single-server/README.md`「升级门禁与 upgrade」与 [部署指南](../deploy/部署指南.md)；登记条目见 [升级兼容与迁移账本设计](升级兼容与迁移账本设计.md)。

## 10. 验收标准（可观察行为）

### 10.1 发送与幂等

1. 所有者发起个人/团队授权后，grant=`pending`、来源=`pending`；数据库零实例、零 `group_accounts` 写入、零 settings 写入；无任何审批位字段。
2. 重复发起同资源同接收方：已有 pending 幂等返回原 grant/source（`created=false`）；已有 active/paused 返回 `409 offer_already_active`；全部终态时新建全新 pending grant，旧终态行的 `ended_at` / `ended_reason` / 状态未被改写。
3. 管理员代建与所有者发起行为一致：无 `pending_owner_approval` 状态，接收方立即可见。
4. 团队授权按在册活跃成员逐一生成 pending 来源（排除资源所有者本人）；零成员团队创建后 grant 停留 `pending`，成员加入后获得来源。

### 10.2 领取与生效

5. 个人领取账户授权：同事务出现授权实例 + `group_accounts` 绑定（`enabled=1`），source/grant/runtime 逐层 `active`；响应 `bound=true`；网关候选立即可用。
6. 领取账户授权缺省 `targetGroupId` 时绑定接收方默认分组；显式 `targetGroupId` 指向他人分组/超级分组/停用分组时拒绝。
7. 领取分组授权：`group_authorization_settings` 出现对应行；接收方路由策略引用该分组后立即按实时成员行获得候选；分组归属人后续新增账户无需任何确认动作即可进入候选。
8. 团队成员各自领取互不影响；新成员加入团队后可领取（历史 `declined` / `returned` 不阻断）；成员移除后其来源 `revoked`（`member_removed`）、runtime 重算、候选消失。
9. `paused` grant 下领取请求返回 `state_conflict`；恢复后可继续领取。

### 10.3 生命周期与到期

10. 暂停后 runtime 推导为 `paused`（除非有其他有效来源）、网关阻断；恢复后按来源重推。
11. `expires_at` 到期由 `authz-governance-sweep`（每分钟）翻转为 `expired`（`ended_reason='authorization_expired'`）；延长后按「曾领取→active / 未领取→pending」恢复，grant 恢复 active/pending；非 `authorization_expired` 的 expired 不可延长（`no_restorable_source`）。
12. 拒绝/归还终态行带 `ended_at` / `ended_reason`；runtime 终态时绑定 `enabled=0`、实例 `disabled`；归还后重新发起、重新领取可用（实例复用并重新绑定）。
13. 来源账户删除 → 来源 `revoked`（`account_deleted`）；分组删除 → grant/source `revoked`（`group_deleted`）且 settings 行删除；归属变化 → 领取/调度路径撤销（`resource_changed`）。

### 10.4 网关与使用面

14. 分组授权候选 = settings 行存在 + runtime/grant/来源三层活跃未过期 + `group_accounts` 实时成员行；runtime 停滞投影（如来源已被撤销但投影未刷）时请求时谓词仍拒绝。
15. 授权实例限频下调生效、超过来源限值被拒（来源限值 > 0）；多接收方共享源账户全局并发/RPM 预算。
16. `PATCH /my-accounts/{id}/authorized-dispatch` 白名单外字段拒绝；账户列表无归还入口，`POST /my-accounts/{id}/return-authorization` 404；`POST /my-groups/{id}/return-authorization` 存活且退订后调度立即停止。
17. 策略路由绑定写前校验（`ValidateGroupBinding`）拒绝无 settings 行 / runtime 非 active / 已过期的分组授权绑定。
18. 三层状态词表 7 值 CHECK 生效：写入退役状态（`needs_review` / `dormant` / `pending_team_approval` 等）被数据库拒绝。

### 10.5 升级

19. revision 31 单事务执行：四表 DROP、29 列 DROP、存量状态收敛（含 `superseded` → `returned` 补 `ended_at`）、3 个 status CHECK 重建、quota scope binding 清零；重复执行零写入（no-op 报告）。
20. fresh 库 `--ensure-schema` 即目标形状，`Satisfied` 即真；`upgrade --dry-run` 在未升级库显示该步骤 pending 且 blocked 于 expand 相。
