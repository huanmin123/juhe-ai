# 核心功能设计

## 文档目标

本文承接原 `docs/architecture/架构总览.md` 中偏具体功能、字段、接口、页面行为和运行策略的内容。架构总览只保留模块边界和跨模块关系；具体实现要求统一以本文、[接口契约与权限矩阵](接口契约与权限矩阵.md)、[安全与日志策略](安全与日志策略.md)、[OpenAI 账号接入](OpenAI账号接入.md)、[SQLite 存储说明](SQLite存储说明.md) 和相关专题文档为准。

## 功能边界总览

- 当前只启用 OpenAI 供应商，账户类型支持 OpenAI OAuth 和 OpenAI API Key。
- 系统账户负责后台登录、角色权限、API Key 调用方和数据隔离。
- 系统团队把多个系统账户归纳在一起，用于承接团队级授权使用权。
- AI 账户保存上游凭据、调度状态、代理、并发、错误策略和可授权使用资源关系；透传不作为账号开关，由供应商网关策略统一决定。
- 分组汇总同供应商账户，是 API Key 的授权边界。
- API Key 只绑定分组，不直接绑定账户。
- 授权统一由授权管理菜单维护，支持 AI 账户、分组授权给系统账户或系统团队。
- 代理是服务器级全局运维资源，只允许管理员维护。
- 使用记录是请求计量事实源；统计缓存只服务高频列表和图表读取。
- 原始审计日志是独立的高权限排障模块，用于保存客户端请求、网关处理、上游请求、上游响应和最终返回的完整原文链路，不参与用量统计。
- 错误策略优先账号级内嵌规则；未命中的上游错误由网关兜底切换账号。

## 系统账户管理

系统账户是后台登录账号，负责权限控制和数据隔离。

建议字段：

- `id`
- `username`
- `display_name`
- `password_hash`
- `role`：当前仅 `admin` / `user`
- `status`：`active`、`disabled`
- `must_change_password`
- `last_login_at`
- `created_at` / `updated_at`

功能要求：

- 默认初始化一个 `admin/admin` 账号，登录成功后对初始密码状态做一次消息提醒。
- `admin` 可以查看、创建、编辑、停用、启用、重置密码和分配系统账户角色。
- 系统账户不提供硬删除；账户停用后禁止登录和继续作为有效调用方，但历史资源、使用记录、统计和审计日志继续保留原系统账户归属。
- 用户账户 `username` 和用户名称 `display_name` 都必须全局唯一；创建时同时校验，编辑时只允许修改用户名称、角色、状态和改密提醒，不允许修改用户账户。
- `user` 不能进入系统账户管理，也不能看到其他系统账户的数据归属维度。
- 所有业务数据都必须按 `system_account_id` 或明确 owner/grantee 字段隔离。
- 后端写入和查询以登录态为准，前端不传系统账户归属字段。
- 系统账户可以加入系统团队；团队只影响授权使用权，不改变该系统账户自己的数据归属和调用日志归属。

登录安全：

- 登录态建议使用服务端会话加 `HttpOnly Cookie`，便于后续封禁、改角色和强制下线。
- 登录验证码使用后端生成的短时挑战：前端先请求验证码图片和 `captchaId`，登录时提交 `captchaId` 与用户输入。
- 验证码后端无论校验成功或失败都消费该挑战，过期挑战自动失效。
- 验证码挑战当前使用单进程内存存储，不落 SQLite；后续多实例部署再替换为共享存储。
- 登录失败防护采用轻量滑动窗口：同一客户端 IP 在 10 分钟内登录失败 10 次会临时限制 15 分钟；同一用户名在 10 分钟内密码错误 5 次会临时锁定 15 分钟。
- 验证码错误不计入密码错误次数，但会消耗验证码；密码错误会同时计入 IP 和用户名维度；登录成功后清理该 IP 和用户名的失败记录。

## 供应商管理

供应商不是简单字符串，而是能力定义。不同供应商可以有不同的账户创建方式、字段 schema 和测试逻辑。当前供应商定义由系统内置，管理面只展示内置供应商和模型目录，不提供新增、编辑或删除。

建议字段：

- `id`：供应商 ID
- `code`：稳定编码，例如 `openai`
- `name`：展示名称
- `enabled`：是否启用
- `base_url`：供应商默认上游地址，例如 OpenAI 固定为 `https://api.openai.com/v1`，不放入系统设置
- `account_types`：支持的账户类型定义
- `capabilities`：支持的能力，例如 responses、chat、models、stream
- `created_at` / `updated_at`

当前内置：

- `openai`：支持 `oauth` 和 `api_key`

供应商模型目录：

- 模型价格应归属于供应商，而不是散落在网关代码里。
- 当前内置 OpenAI 模型价格快照，字段采用 LiteLLM / `model-price-repo` 的语义，token 单价以 USD/token 存储，接口展示时换算为 USD/1M tokens。
- 供应商页提供“查看模型”入口，展示模型版本、输入/输出/缓存读写/图片价格、上下文窗口和能力标签。
- 网关成本估算复用供应商模型目录；未命中模型时只记录 token，不猜测成本。

## AI 账户管理

AI 账户是上游凭据和调度配置的承载对象，归属某个系统账户。

建议字段：

- `id`
- `system_account_id`
- `provider_code`：供应商稳定编码，例如 `openai`
- `name`
- `type`：`oauth` 或 `api_key`
- `status`：`active`、`disabled`、`error`、`rate_limited`、`temporary_unavailable`
- `credentials`：加密后的凭据内容
- `credential_fingerprint`：上游凭据指纹；按凭据明文归一化后哈希，底层全局唯一
- `credential_mask`：兼容保留字段；列表不展示凭据，编辑弹窗可展示完整凭据
- `proxy_profile_id`
- `concurrency_limit`：创建账户时默认 `20`，可在账号表单中按账号调整
- `current_concurrency`：运行态字段，由主进程内网关请求生命周期实时计算；请求命中账号后占用，响应完成、流结束或失败退出时释放，不作为 SQLite 持久化主状态
- `passthrough_enabled`：内部派生字段，创建和更新账户时按供应商能力写入，不作为用户可配置项。
- `error_policy_id`
- `priority`
- `super_priority_enabled`：临时应急调度标记，只允许正常状态账号开启；账号变为停用、错误、限流中或临时不可调用时自动清除
- `schedulable`
- `account_expires_at`：本系统的账户套餐/购买到期时间；可为空，和 OAuth token 的 `credentials.expires_at` 分离
- `notes`
- `last_used_at`
- `cooldown_until`：账号临时冷却截止时间；未来时间内不参与调度
- `last_error_message`：最近一次熔断、临时不可调用或失败原因摘要
- `stream_failure_count`：流失败窗口内累计次数
- `stream_failure_window_started_at`：流失败统计窗口起始时间
- `created_at` / `updated_at`

列表和权限：

- 账户列表展示账户名称、来源、所有者摘要、账户类型、供应商、并发数、状态、用量情况、优先级、最近使用时间、账户到期时间和操作。
- 管理员视角额外展示系统账户列；用户视角自有账户不展示归属列，授权账户显示“来自授权”和所有者摘要。
- `Access/API Key` 与 `Refresh Token` 不在列表展示；只有账户所有者可在编辑弹窗里查看和修改，授权账户永不返回完整敏感凭据。
- 状态语义统一为正常、停用、错误、限流中、临时不可调用。
- 账号优先级按数字从小到大生效，`0` 优先于 `10`；同分组调度时先尝试优先级更高的账号。
- 账户所有者可在正常账号的“更多”菜单设置“超级优先”。超级优先用于应急人工提权，多个账号可同时开启；开启后状态列在“正常”旁展示“优先”。如果账号状态变为非正常，后端必须自动清除该临时标记。
- 账户所有者可在“更多”菜单执行“迁移流量”：选择同一系统账户、同一供应商、同一分组内的可调度目标账户，把当前进程内命中源账户的会话亲和绑定切到目标账户，并把源账户默认改为 `temporary_unavailable`；必要时可改为 `disabled`。该动作只影响后续请求，不主动中断已经建立的流式连接；当前正在输出的请求继续跑完。它不复制凭据、不修改 API Key 或分组绑定，只用于人工快速止血。

账号质量调度：

- `account_quality_scores` 保存账号最近质量缓存，默认来源是近 10 分钟真实请求；客户端请求时只读取缓存，不临时扫描 `usage_records`。
- 后台 `account-quality-refresh` 默认每 10 分钟运行一次，只刷新真实请求统计，不再保留任何主动探测能力或开关。
- 删除主动探测的原因是它不是恢复项，而是优化项；保留旧实现容易在后续维护中被重新接上，继续无业务价值地消耗上游请求。
- 调度只使用 24 小时内有真实样本更新过的质量分；更旧的质量缓存视为过期，不参与排序，客户回归后的第一次请求按“超级优先 > `priority` > 稳定兜底顺序”选择，随后由真实请求和下一轮 worker 恢复质量缓存。
- 网关调度顺序为：超级优先账号先于普通账号，账号 `priority` 小者优先；只有同层级候选数 `>= 2` 时，才按 `quality_score` 从小到大继续择优。层级内只有一个账号时不启用质量机制。

账户生命周期：

- `account_expires_at` 为空表示不设置本地套餐到期。
- 一旦到期，后端把账户改为 `disabled`、`schedulable = 0`、清空冷却时间并写入到期原因。
- 网关调度、真实响应头快照写入、成功/失败恢复逻辑都不能重新启用已到期账户。
- 只有用户清空或延后 `account_expires_at` 后才允许再次启用。

创建入口：

- 页面只提供“添加 AI 账户”。
- 弹窗内先选择供应商，再按供应商能力展示账户类型，最后渐进展开具体配置。
- OpenAI 支持 `oauth` 与 `api_key` 两种类型；后续供应商只扩展供应商定义和对应创建表单，不新增外部入口按钮。

OpenAI OAuth 建议凭据：

- `access_token`
- `refresh_token`
- `expires_at`：由 OAuth token 响应的 `expires_in` 计算，只表示 access token 到期时间
- `account_id`：从 OpenAI token 或账户信息解析出的系统元数据，不作为用户输入项
- `client_id`
- `email`
- `base_url`

OpenAI API Key 建议凭据：

- `api_key`
- `base_url`

## OAuth 额度快照

OpenAI OAuth 账户还有上游 Codex/ChatGPT 使用窗口限制，不能和 OpenAI API Key 的本地 token / 成本用量混为一类。

展示规则：

- 账户列表“用量情况”分成本地网关统计和 OAuth 专属额度进度两层。
- 本地网关统计从统计缓存读取，事实源仍是 `usage_records`；统计缓存只聚合有效消耗，用于有效请求、token 和成本。
- OAuth 专属额度进度来自上游返回的 Codex rate-limit 快照，用独立进度条展示 `5h` 与 `7d` 窗口百分比、预计恢复时间和快照更新时间。
- OAuth 额度进度只表示上游 OAuth 额度占用，不参与 API Key 计费口径。

存储建议：

- OAuth 额度快照单独存储为非敏感运行态，不写进 `credentials`。
- 当前采用 `account_usage_snapshots` 或等价 repository 对象。
- 按 `system_account_id + account_id + kind` 保存 `openai_codex` 快照。
- 建议保存原始 primary/secondary header、归一化后的 `codex_5h_*` / `codex_7d_*` 字段、`reset_at`、`window_minutes`、`updated_at`、`source`、`last_attempt_at`、`last_success_at`、`next_refresh_after`、`refresh_status` 和 `last_error_message`。
- 列表接口只返回可展示摘要，不返回 access token、refresh token 或完整请求内容。

更新规则：

- OAuth 额度快照只从真实网关请求和账户测试返回的 Codex rate-limit 响应头被动更新。
- OAuth 账户创建成功后不主动发模型请求获取额度；第一次真实调用或账户测试返回相关响应头后才出现快照。
- 后台 worker 不再注册 OAuth 额度快照主动刷新任务；保留 OAuth Access Token 预刷新，因为它只做凭据续期。
- 快照缺失或过期不触发列表页批量探测，页面显示“暂无快照”或“等待真实请求更新”。
- 收到 OAuth 429 时，网关仍可优先用 header 计算 reset 时间；header 不足时再解析响应体 `resets_at` / `resets_in_seconds`，并把账号标记为 `rate_limited` 到该时间。

## 系统团队管理

系统团队用于把多个系统账户归纳在一起，方便资源所有者一次性把 AI 账户或分组授权给团队成员共享使用。团队不是资源所有者，不改变团队成员自己的数据归属、API Key 归属和使用记录归属。

功能要求：

- 菜单名称为 `系统团队管理`，当前仅 `admin` 可见和维护。
- 管理员可以创建团队、编辑团队基础资料、启停团队、添加成员和移除成员。
- 普通用户不能进入团队管理页；普通用户菜单提供 `我的团队`，只读展示自己加入的团队和团队成员。
- 统一授权管理读取授权对象选项时，管理员可读取全部系统账户和团队摘要；普通用户只能读取最小用户摘要和自己加入的团队摘要，不能复用系统账户管理列表。
- 团队停用后，所有团队授权立即不可继续生效；历史授权和历史使用统计保留。
- 成员移除后，该成员不再通过团队授权获得资源使用权；网关每次调度都必须实时校验团队和成员状态。

建议字段见 [系统团队与统一授权设计](系统团队与统一授权设计.md)。

## 统一授权管理

统一授权管理用于把 AI 账户或分组的“使用权”授予某个系统账户或系统团队。授权不改变资源所有者，不复制凭据，也不产生新的上游账户或分组副本。

菜单与入口：

- 菜单名称为 `授权管理`。
- 该菜单对所有登录用户可见；普通用户只能查看自己授权出去或授权给自己的记录，管理员可以查看全部。
- 所有新增授权、授权列表、授权收回和授权用量详情都从该菜单进入。
- AI 账户页和分组页不再放资源自己的授权管理入口，只显示资源来源、所有者摘要和当前用户权限摘要。

语义规则：

- 当前只支持一种授权范围：`use`。
- 支持授权资源类型：`account`、`group`。
- 支持授权对象类型：`system_account`、`team`。
- 资源所有者可以新增授权、收回授权、查看授权消耗总量和按系统账户拆分的消耗明细。
- 授权给团队时，系统批量给团队内有效成员建立或合并用户级授权；团队成员新增、移除和团队停用应动态维护这些用户级授权来源。
- 同一系统账户同时通过个人来源和团队来源获得同一 AI 账户或分组时，最终只有一条用户级有效授权，列表只能展示一个资源行，不能出现重复 AI 账户或重复分组。
- 同一个 `account_id` 始终代表同一个物理上游账户，不因个人授权、团队授权或加入多个分组而复制；并发、冷却、限流、到期和真实总用量都共享同一账户状态。
- 被授权用户不能修改资源名称、凭据、代理、并发、优先级、调度开关、错误策略、备注和状态，不能删除资源，也不能继续转授权。
- 被授权用户不能查看完整敏感凭据，只能看到列表需要的基础摘要、状态、可用性和必要来源标识。
- 授权账户可加入被授权用户自己的同供应商分组参与调度；授权分组可被绑定到被授权用户自己的 API Key。
- 分组授权共享的是分组所有者自有账户集合；如果分组里包含其他用户授权来的账户，不能通过分组授权继续共享给第三方。

建议字段：

- `id`
- `resource_type`：`account`、`group`
- `resource_id`
- `resource_owner_system_account_id`
- `grantee_system_account_id`：最终被授权使用的系统账户
- `source_type`：`manual`、`team`
- `source_team_id`：团队来源 ID，手动个人授权为空
- `scope`：当前固定为 `use`
- `expires_at`：可选自动回收时间，命中后授权状态自动变为 `expired`
- `limits_json`：美元成本额度限制 JSON，内部 `limit` 表示美元金额，支持 n 小时额度、日额度、周额度、月额度和总额度；为空表示不限制。
- `model_policy_json`：预留字段，当前不启用，用于后续模型范围控制。
- `status`：`active`、`paused`、`expired`、`revoked`
- `remark`
- `created_by`
- `created_at`
- `revoked_by`
- `revoked_at`
- `updated_at`

约束与生命周期：

- 同一个 `resource_type + resource_id + grantee_system_account_id` 同一时间只能有一条有效授权。
- 不允许授权给资源所有者自己。
- 授权给团队时，如果资源所有者也在该团队内，资源所有者自己的调用仍按自用处理，不计入授权消耗。
- 不允许授权给已停用或不存在的系统账户、团队、账户或分组。
- 收回授权采用状态变更，不物理删除，历史请求和统计继续保留。
- 到期采用状态变更，不物理删除；独立 background worker 进程负责把过期授权改成 `expired`。
- 资源删除时级联清理授权关系；历史 `usage_records` 保留原始统一授权 ID、调用方和资源所有者字段用于追溯。
- 授权收回后，已有分组账户绑定或 API Key 分组绑定可以保留为失效状态，调度时必须重新校验有效授权。

列表与权限返回：

- `GET /api/accounts` 返回自有账户和授权账户的合集，并按 `account_id` 对当前用户去重；返回 `authorization_sources` 和用户级 `authorization_id`，但不能返回多条相同 AI 账户。
- `GET /api/groups` 返回自有分组和授权分组的合集，并按 `group_id` 对当前用户去重；返回 `authorization_sources` 和用户级 `authorization_id`，但不能返回多条相同分组。
- 每行建议返回 `access_type`：`owner`、`authorized` 或 `admin_view`；当同一资源同时拥有个人来源和团队来源时，仍只返回一行授权资源，来源摘要展示全部来源。
- 授权资源额外返回 `authorization_id`、`authorization_sources`、`grantee_system_account_id`、`owner_system_account_id`、`owner_display_name`、`authorization_status`。
- 每行建议返回 `permissions` 摘要，例如 `can_use`、`can_edit`、`can_delete`、`can_authorize`、`can_view_credentials`、`can_manage_members`、`can_bind_to_api_key`。
- 前端据 `permissions` 隐藏操作；后端仍必须在每个写接口重新校验。

授权管理页：

- 授权列表展示资源类型、资源名称、资源所有者、授权对象类型、授权对象、状态、授权时间、最近使用时间、今日授权消耗和操作。
- 新增授权时选择资源类型、自有资源、授权对象类型、系统账户或团队和备注。
- 用量详情的主维度是“资源 × 用户”：A 授权给 B 时，A 能看到 B 今日在该资源上的消耗，不再按个人来源或团队来源拆成多份。
- 团队授权详情展示团队成员用户级授权集合：团队今日总消耗是成员用户消耗的去重汇总，成员明细展示每个用户今日在该资源上的消耗。
- 如果 B 先有个人授权，后又因团队获得同一资源授权，B 的今日消耗合并到同一条“B 在该资源上的用量”里；团队详情也能按成员看到 B 的今日用量。
- 授权统计由独立 background worker 进程写入统计缓存，授权列表和详情接口只读缓存，不在页面请求时实时聚合原始 `usage_records`。
- 授权消耗统计不包含资源归属人自己的自用消耗；资源归属人的账户 / 分组用量情况仍展示全部总消耗。
- 新增授权和修改授权配置时可以设置美元成本额度；日额度每日 0 点重置，周额度每周一 0 点重置，月额度每月 1 号 0 点重置，总额度按累计 `total_cost_usd` 判断，n 小时额度按小时缓存窗口的 `total_cost_usd` 相加判断，例如 5 小时额度 $10 表示最近约 5 小时美元成本合计达到 10 后拦截。
- 授权额度判断读取后台统计缓存和短 TTL 网关内存缓存，不在请求内扫描 `usage_records` 或做强一致扣减；允许轻微超额，统计追平后下一次请求返回 `429` 和“额度已用完，请联系管理员提升额度”。
- 资源所有者只能查看授权聚合用量，不能查看被授权用户请求快照、响应快照、客户端 IP、API Key 明文或业务请求内容。

建议接口：

- `GET /api/authorizations`：查看授权列表和聚合摘要。
- `POST /api/authorizations`：新增授权，仅资源所有者或管理员可用。
- `DELETE /api/authorizations/:authorizationId`：收回授权，仅资源所有者或管理员可用；语义是改为 `revoked`。
- `GET /api/authorizations/:authorizationId/usage`：查看某条授权的聚合用量和按系统账户拆分明细。
- `GET /api/authorization-options/grantee-accounts`：获取可授权用户摘要；管理员返回全部系统账户摘要，普通用户返回最小字段的可选用户摘要，不能返回角色、改密状态、最后登录等管理字段。
- `GET /api/my-teams`：普通用户查看自己加入的团队和团队成员；系统团队管理列表仍使用管理员专用的 `GET /api/system-teams`。

## 分组

分组是调度和 API Key 授权边界。账户主动选择归属分组，API Key 绑定分组；分组使用权通过统一授权管理授权给系统账户或系统团队。

建议字段：

- `id`
- `system_account_id`
- `name`
- `provider_code`：分组所属供应商，默认 `openai`；只允许同一供应商的账户归入该分组
- `description`
- `enabled`
- `is_default`：是否为系统账户在该供应商下的默认分组；默认分组不允许修改或删除
- `account_count`
- `created_at` / `updated_at`

关系表：

- `group_account.group_id`
- `group_account.account_id`
- `group_account.weight`
- `group_account.enabled`

功能要求：

- 系统账户创建时后端自动创建一个 `默认 OpenAI 分组`，用于新用户开箱即用选择 OpenAI 账户和 API Key 的归属边界；名称已能表达默认含义，页面不再额外展示默认标签，默认分组说明保持为空。
- 一个账户必须归属到一个同供应商分组；创建时按供应商默认选中默认分组，编辑时可调整。
- 每个系统账户默认拥有一个 OpenAI 分组；本地未上线阶段可以通过重建库或离线清洗脚本补齐，不在源码保留旧数据补丁分支。
- 一个分组可以汇总多个同供应商账户。
- 一个分组只汇总同一 `provider_code` 下的账户，列表只展示数量与聚合状态，不展开账户名称。
- 一个 API Key 先绑定一个自有分组；统一授权完成后，也允许绑定授权给自己的分组。
- 调度顺序以账号 `super_priority_enabled`、`priority` 和账号质量缓存为主；`group_account.weight` 只作为初始读取的稳定辅助顺序，最终调度仍以账号级规则为准。
## API Key 管理

API Key 是对外访问入口，不直接绑定账户，而是绑定分组。

建议字段：

- `id`
- `system_account_id`
- `name`
- `key_hash`
- `key_prefix`
- `status`
- `group_id`
- `expires_at`
- `rate_limit`
- `quota_limit`
- `scopes`
- `last_used_at`
- `created_at` / `updated_at`

功能要求：

- 明文 API Key 只在创建时返回一次。
- 列表和详情直接展示完整密钥，便于单人自用场景复制和排查。
- API Key 可绑定自有分组；统一授权完成后，也可绑定授权给自己的分组，绑定时记录可选 `group_authorization_id` 以便调度实时校验。
- 请求进入后只能使用该 API Key 对应分组内当前可调度且授权仍有效的账户。

## 代理管理

代理独立于账户，账户只引用代理配置。代理是服务器级全局资源，不属于某个系统账户。

权限规则：

- 代理管理列表、创建、编辑、删除和手动检测只面向管理员开放。
- 普通用户不显示代理菜单，但可以在自有 AI 账户创建、编辑和 OpenAI OAuth 流程中选择已启用代理。
- 普通用户只获取代理选择项，不返回 Host、端口、用户名、出口 IP、检测摘要等运维字段。

建议字段：

- `id`
- `name`
- `type`：`http`、`https`、`socks5`、`socks5h`
- `host`
- `port`
- `username`
- `password_encrypted`
- `enabled`
- `test_status`
- `latency_ms`
- `outbound_ip`
- `outbound_region`
- `last_test_message`
- `last_tested_at`
- `created_at` / `updated_at`

代理质量检测以全部已启用供应商默认地址为测试目标；手动检测额外缓存出口 IP 和出口地区。最近检测状态、延迟、出口信息和摘要只作为运维参考缓存，不替代实际请求时的失败处理。

## 使用记录

使用记录用于排查、统计和后续计费。网关每次实际发起上游请求都写入一条记录，重试失败、切换账号失败和最终成功都会分别保留。

使用记录和原始审计日志必须分开：使用记录关注 token、成本、耗时、状态码、授权归属和统计聚合；原始审计日志关注完整请求过程和原始内容。使用记录失败快照仍遵循脱敏和截断策略，不因为原始审计日志存在而保存完整敏感原文。

建议字段：

- `id`
- `system_account_id`：实际调用方系统账户，决定普通用户使用记录隔离
- `account_owner_system_account_id`：命中账户所有者，自有账户时等于 `system_account_id`
- `group_owner_system_account_id`：命中分组所有者，自有分组时等于 `system_account_id`
- `account_access_type`：`owner`、`authorized`
- `group_access_type`：`owner`、`authorized`
- `account_authorization_id`：命中授权 AI 账户时记录用户级统一授权 ID，自有账户或仅通过授权分组访问时为空
- `group_authorization_id`：命中授权分组时记录用户级统一授权 ID，自有分组为空
- `authorization_source_summary`：可选快照，记录当时用户授权来自个人、团队或两者合并
- `trace_id`
- `api_key_id`
- `group_id`
- `account_id`
- `endpoint`
- `provider_id`
- `model`
- `stream`
- `status_code`
- `success`
- `client_ip`
- `first_token_ms`
- `duration_ms`
- `input_tokens`
- `output_tokens`
- `cache_read_tokens`
- `cost_usd`
- `error_code`
- `error_message`
- `request_snapshot_json`：失败请求的客户端请求快照
- `response_snapshot_json`：失败请求的网关返回与最后一次上游响应快照
- `created_at`

统计口径：

- 当前网关已写入请求记录，并从 OpenAI 响应里的 `usage.input_tokens`、`usage.output_tokens`、`usage.input_tokens_details.cached_tokens` 统计 token。
- OpenAI SSE 响应读取 `response.completed` / `response.done` / `response.failed` 事件里的 `response.usage`。
- 使用记录保存 `METHOD /v1/path` 形式的接口，便于区分 `/v1/models` 这类成功但没有模型和 token 用量的请求。
- 成本统计复用供应商模型目录里的 OpenAI 价格快照做轻量 1:1 估算；未覆盖的模型先只记录 token。
- 使用记录接口可派生输入成本、输出成本、输入单价、输出单价、缓存读取成本、账户计费和固定 1x 倍率，用于前端悬浮明细展示，不额外写入数据库。
- 管理员视角可按 `system_account_id` 查看全部记录并显示归属列，用户视角只看自己的记录且不显示归属列。
- 授权账户和授权分组调用都按调用方写入明细；统一授权管理只展示授权消耗聚合，不包含资源归属人自用消耗，也不向资源所有者展示被授权用户请求快照、响应快照、客户端 IP 或业务内容。
- 失败记录额外保存请求/响应快照，便于在使用记录页查看当时的请求体、响应体和最后一次上游错误。

## 原始审计日志

原始审计日志用于在客户端版本升级、请求头变化、上游校验规则变化或网关兼容问题出现时，还原一次请求从进入网关到最终返回的完整过程。具体字段、队列、采样、SSE 和安全边界见 [原始审计日志设计](原始审计日志设计.md)。

核心规则：

- 管理菜单名称为 `审计日志`，当前仅 `admin` 可见和查询。
- 完整成功请求默认按 `10%` 比例保存；非成功请求、客户端中断、流式中断、任一上游尝试失败后最终成功的请求，都必须全量保存。
- 审计内容保存完整原文，包括客户端请求头、请求体、上游请求头、上游请求体、上游响应头、响应体和最终返回客户端内容，不做脱敏、截断或字段移除。
- 原始 payload 建议加密存储；加密不等于脱敏，管理员按权限查看时应能还原原文。
- 网关请求链路禁止同步写审计表；请求处理中只维护内存捕获上下文。
- 只有请求结束、失败或客户端中断后，才能计算终态并按采样规则把完整审计对象放入内存队列。
- 审计队列由独立 background worker 进程定时或按批量阈值写入 SQLite；队列写库失败、系统重启或进程崩溃导致审计数据丢失是可接受边界。
- SSE 和其他流式响应不能按 chunk 实时写库，也不能在流未结束时入队；必须等自然结束、失败、超时或客户端断开后，以终态记录入队。
- 审计队列满或单请求捕获超过上限时，不能阻塞网关响应；允许丢弃审计记录并增加队列丢弃计数，供运维页面查看风险。

## 统计缓存与运维监控

统计层的目标是把“高频读、低频写”的指标提前聚合好，避免列表页和图表页每次都回扫 `usage_records`。`usage_records` 继续作为事实源，独立 background worker 进程按 `system_account_id` 分区和游标增量汇总到缓存表；列表和管理员统计概览只读缓存。

后台执行边界：

- Web/API/网关主进程不能注册统计聚合、系统采样、授权到期扫描、冷却账号复测、运行日志索引维护或审计清理定时任务。OAuth 额度快照不再有主动刷新定时任务。
- 调度框架只允许运行在独立 background worker 进程内；不能让 worker 只负责触发，再通过 IPC 回到主进程执行任务函数。
- 主进程只允许把请求链路产生的轻量事件或待写数据投递给 worker；批量聚合、批量写库、清理和外部探测都在 worker 内完成。
- Worker 任务必须支持不可重入、错误隔离和失败后下轮重试；单个任务失败不能影响 Web 请求主链路。

建议缓存分层：

- `usage_stats_totals`：按 `system_account_id + scope_type + scope_id` 存累计值，覆盖 `system_account`、`provider`、`group`、`account`、`account_authorization`、`group_authorization`、`api_key`、`model`、`endpoint`。
- `usage_stats_daily`：按 `system_account_id + scope_type + scope_id + stat_date` 存天级业务概览，用于列表和授权用量的自然日口径。
- `usage_stats_hourly`：按 `system_account_id + scope_type + scope_id + stat_hour` 存小时趋势，用于统计概览近一天、近三天、近一周和近一月监控窗口。
- `usage_model_daily`：按 `system_account_id + stat_date + model` 聚合请求数、token 和成本，用于自然日模型分布。
- `usage_model_hourly`：按 `system_account_id + stat_hour + model` 聚合小时级模型分布，用于统计概览监控窗口。
- `usage_error_daily`：按 `system_account_id + stat_date + error_group + error_code` 聚合错误，用于自然日错误情况。
- `usage_error_hourly`：按 `system_account_id + stat_hour + error_group + error_code` 聚合小时级错误，用于统计概览监控窗口。
- `group_account_stats`：按 `system_account_id + group_id` 缓存分组账户数量、可用数、状态数量和并发上限，分组列表只读该结果。
- `system_metrics_samples`：主机级运维采样，记录 CPU、内存、RSS、Heap、事件循环延迟、网络入站/出站吞吐、网卡累计收发、数据库大小和统计滞后，默认仅管理员可见。
- `system_metrics_hourly`：把主机采样值做小时级平均、最大值和最小值，供监控图长期查看。
- `stats_job_state`：按 `scope_type + scope_id + job_name` 记录任务游标、上次成功时间、上次错误和处理滞后；用户业务汇总使用 `scope_type = system_account`，主机监控使用 `scope_type = global`。
- 审计队列运行态指标：可在运维监控中展示队列长度、队列字节数、最近成功落库时间、最近错误和丢弃计数；这些指标只反映审计健康度，不参与用量统计。

隔离规则：

- 统计概览与运维监控属于管理员视角，只允许 `admin` 访问；普通用户没有统计概览菜单和统计 API 权限。
- 管理员按系统账户筛选时读取对应 `system_account_id` 的缓存；查看全局汇总时读取后台写入的 `global` 缓存行，不在概览接口里临时聚合多个系统账户缓存行，更不回扫 `usage_records`。
- 统一授权需要同时维护调用方口径、资源归属口径和授权消耗口径：调用方统计按 `usage_records.system_account_id` 聚合；账户真实总用量按 `account_owner_system_account_id + account_id` 聚合；分组真实总用量按 `group_owner_system_account_id + group_id` 聚合；授权管理按资源所有者和统一授权 ID 聚合，并过滤资源归属人自己的自用消耗。统一授权美元成本额度限制也读取这些 `account_authorization` / `group_authorization` 缓存维度，团队授权额度按成员用户授权的 `total_cost_usd` 缓存求和判断。
- 用量统计菜单面向账户维度读取缓存：列表展示近 1 天、近 3 天、近一周、近一月；授权用量弹窗展示授权用户和授权团队的近 1 天、近 3 天、近一周、近半月、近一月和总用量。多日统计由天级缓存行相加得到，总用量从累计缓存读取，不在页面请求时按 `n` 天实时汇总明细。
- 统计概览是监控窗口，不等同账户、分组、API Key 列表里的今日用量；默认近一天，并支持近三天、近一周和近一月。概览摘要、趋势、模型分布和错误 Top 10 均按小时级缓存窗口相加，不能从 0 点开始重置，也不能读取累计总量替代窗口数据。
- 请求时统计硬边界：列表、概览、授权详情、分组详情和元数据下拉只能读取缓存结果；只有独立 background worker、离线清洗脚本和使用记录分页明细允许直接读取事实表。
- 系统账户停用时，应停止对应后台任务和继续登录 / 调用；系统账户不提供硬删除，统计缓存、OAuth 额度快照和任务状态按历史归属保留或由保留期策略清理。
- 主机级 CPU、内存、数据库大小不属于用户业务数据，默认只在管理员运维视角展示。

常用指标：

- 监控窗口有效请求 = `request_count`
- 平均有效上游响应时间 = `duration_ms_sum / request_count`
- 平均首 token 时间 = `first_token_ms_sum / first_token_ms_count`
- 监控窗口 Token = `input_tokens + output_tokens + cache_read_tokens`
- 模型分布 = 按模型维度的请求数、Token 占比和成本占比
- 错误情况 = `error_rate`、`error_count`、`error_group`
- 统计滞后 = 当前时间与 `stats_job_state.last_success_at` 或游标对应记录时间的差值

## 错误处理策略

账号级错误处理通过 `credentials.error_handling_rules` 保存为账户内嵌规则；新建和编辑账户都在弹窗内维护规则列表。列表不额外展示规则明细，避免挤占状态、并发、用量和最近使用时间。

匹配规则：

- 匹配条件：`status_codes`、`error_codes`、`error_types`、`keywords`，配置多个字段时必须同时命中。
- 排序与开关：`enabled`、`priority`、`name`、`description`。
- 处理动作只保留三种：`rate_limited`（限流）、`temp_unschedulable`（临时不可调用）、`error_disabled`（错误）。
- 限流恢复：`reset_strategy` 支持 `duration`、`daily`、`weekly`，并保留 `duration_hours`、`daily_reset_hour`、`weekly_reset_day`、`weekly_reset_hour`；每日和每周恢复时间统一跟随服务器系统时间，不提供用户级时区配置。

动作语义：

- `rate_limited` 会把账号置为限流中并按恢复策略自动恢复。
- `temp_unschedulable` 会写入临时不可调用。
- 只有显式配置 `error_disabled` 才会把账号置为错误。
- 网关不会把未命中的上游错误透传给客户端；未命中账号规则时，当前账号会临时不可调用并切换到同分组内下一个可用账号。

## 系统设置

平台设置和系统运行设置分层管理。

全局设置：

- `global_settings` 只保存系统名称和系统图标路径。
- 登录页角标、副标题和视觉样式按 [产品与品牌边界](../architecture/frontend/产品与品牌边界.md) 固定。
- 全局设置未登录也需要读取，只允许 `admin` 修改。

系统运行设置：

- `system_settings` 当前用于保存网关运行策略、审计日志、后台任务和数据保留等系统级策略。
- 运行设置只允许管理员查看和修改；普通用户不显示系统设置菜单，也不能调用系统设置接口。
- 管理员的用户模式 / 管理模式菜单偏好属于浏览器本地前端习惯，默认第一次进入用户模式；不写入系统运行设置，也不影响后端权限。
- 如果后续需要个人偏好，应另起“我的偏好”接口和字段，避免和系统运行策略混用。

建议配置：

- 默认上游请求超时
- 默认临时不可调用时长
- 默认代理策略
- API Key 自动生成规则（内部固定，不在系统设置暴露）
- 自用后台完整密钥展示规则
- 使用记录、普通运行日志索引和原始审计日志的保留天数，表数据清理统一由后台 worker 执行
- 原始审计日志启停、成功采样率、队列上限、批量落库间隔和保留天数
- 统计 worker 间隔、系统采样间隔、聚合数据保留天数和统一清理批量上限
- OAuth Access Token 预刷新间隔、提前刷新窗口、批量大小和失败退避
- OAuth 额度快照被动更新口径；不再提供后台主动刷新间隔、过期探测和刷新并发配置
- 统计滞后告警阈值，用于运维概览提示缓存是否落后

## 流熔断与账号处理

轻量版流超时处理不引入复杂运行时调度器。当前实现完全基于 SQLite 字段和请求时判断。

默认参数：

- `defaultTemporaryUnschedulableMinutes`：默认 `5` 分钟。未知异常、策略冷却和流熔断都使用这个全局时长。
- `temporaryUnschedulableRetryIntervalSeconds`：默认 `3` 秒。进入临时不可调用前会按这个间隔短暂重试。
- `temporaryUnschedulableRetryAttempts`：默认 `3` 次。超过次数后才标记为临时不可调用。
- `streamCircuitBreakerEnabled`：默认 `true`。启用后累计流式空闲/中断失败。
- `streamRequestTimeoutSeconds`：默认 `180` 秒。流式请求在首个有效输出到来前超过该总时限会熔断；即使上游持续发送 `response.created`、SSE 注释或其他非输出事件，也不能无限延长首输出等待。
- `streamIdleTimeoutSeconds`：默认 `60` 秒。每次流式响应在首个有效输出后都会独立计时；当前响应超过该时间没有新的有效输出时判定为输出停顿。SSE 注释、心跳和其他非输出事件不能刷新该计时。超时后网关会向客户端发送失败事件并结束本次 SSE，不在服务端换账号或重新请求上游续写，同时记录一次失败。
- `streamFailureThresholdCount`：默认 `3` 次。
- `streamFailureThresholdWindowMinutes`：默认 `10` 分钟。
- `oauthAccessTokenRefreshIntervalSeconds`：默认 `60` 秒。后台 worker 定期扫描 OpenAI OAuth Access Token。
- `oauthAccessTokenRefreshLeadSeconds`：默认 `300` 秒。Access Token 距离过期小于该窗口时提前刷新。
- `oauthAccessTokenRefreshBatchSize`：默认 `20`。每轮最多预刷新多少个 OAuth 账户。
- `oauthAccessTokenRefreshRetryBackoffSeconds`：默认 `300` 秒。旧 Access Token 仍可用但预刷新失败时，同一账号下一次预刷新前的退避时间。
- `accountQualityRefreshIntervalSeconds`：默认 `600` 秒。账号质量缓存刷新间隔。
- `accountQualityWindowMinutes`：默认 `10` 分钟。真实网关请求首 token 质量统计窗口。
- `cooldownAccountRetestEnabled`：默认 `true`。冷却账号后台复测默认开启，但只用于冷却到期后的恢复性测试。
- `cooldownAccountRetestBatchSize`：默认 `10`。每轮最多恢复性复测多少个冷却到期账号。
- 账号质量主动探测相关系统项已删除，不允许通过配置重新开启。

处理方式：

- 流熔断达到阈值后会把非停用账户写入 `accounts.status = 'temporary_unavailable'` 并设置冷却截止时间；停用账户不受流熔断、错误策略或异步回写影响。
- 首包前请求熔断会按上游建连失败处理；已经收到 `2xx + SSE` 后，网关不再为了首输出预读而阻塞下游，而是立即透传上游事件，并在首个有效输出超过 `streamRequestTimeoutSeconds` 时补发 OpenAI Responses 协议内的 `response.failed` 后结束本次 SSE。冷却结束后后台默认会对冷却到期的 `temporary_unavailable`、`rate_limited` 做恢复性复测；复测成功恢复为正常，复测失败继续保持原状态。停用账户是人工硬边界，不会被测试、后台复测、OAuth 刷新成功或网关异步错误处理自动恢复或改成临时不可调用。账户所有者仍可在更多菜单手动“恢复正常”，用于人工清理冷却与最近错误并恢复调度。
- 未被账户错误处理策略截获的上游非成功响应，会立即把当前账号写入 `defaultTemporaryUnschedulableMinutes` 的临时不可调用状态，并切换到下一个可用账号重试。
- 未知请求异常会先按 `temporaryUnschedulableRetryIntervalSeconds` 与 `temporaryUnschedulableRetryAttempts` 做短暂重试，仍失败后才进入临时不可调用状态并切换账号。
- 命中错误策略里的 `rate_limited` 会标记为限流中；命中 `error_disabled` 才会显式标记为错误。
- 网关请求成功后会清理非停用账号的失败计数、冷却时间和最近错误，并恢复为正常。
- 账户列表展示五态状态、冷却截止时间和错误摘要；完整 token 仍只在编辑弹窗中查看。
- 手动“迁移流量”适用于上游返回 `200` 但内容已被中转或上游改写、自动错误策略无法识别的场景；它只迁移当前进程内已有会话亲和绑定，不主动断开当前流；后续新请求会因为源账户临时不可调用或停用而自然选择同分组其他可用账户。
- OpenAI OAuth Access Token 仍保留请求前懒刷新兜底；后台 worker 额外做专职预刷新，优先处理启用、可调度、有 `refresh_token` 且即将过期的账户。预刷新失败但旧 token 仍有效时只记录日志并按退避重试；旧 token 已过期或缺失时把账户写入临时不可调用，等待后续人工测试或后台复测恢复。

## 中转协议与流程

对外只暴露 OpenAI 兼容的 `/v1/*` 网关入口。开发环境默认 Base URL 是 `http://127.0.0.1:3000/v1`，常用路径包括 `/v1/models`、`/v1/responses` 和 `/v1/chat/completions`。后续新增提供方时，也优先把上游差异适配到 OpenAI 兼容格式，不在客户端侧暴露各厂商私有协议。

透传规则：

- 产品上不提供透传开关；所有账户按供应商 adapter 的内部策略透传。
- OpenAI API Key 账号按公开 OpenAI-compatible API 处理，请求体优先使用客户端 `rawBody` 原样转发，不做默认内容填充或无关重写。
- OpenAI API Key Header 透传必须过滤本地认证、HTTP hop-by-hop、代理链路、cookie、压缩、SDK / tracing / 部署平台噪声和 OAuth / Codex 专用头。
- OpenAI API Key 账号不默认透传客户端 `OpenAI-Organization` / `OpenAI-Project`，也不从账号凭据生成这两个头；组织 / 项目属于上游账号上下文，普通用户通常不知道也不应被要求填写。
- `OpenAI-Beta` 可保留客户端显式传入值；服务端不生成默认 Beta，也不做账号级覆盖。
- OpenAI OAuth 账号不复用 API Key raw passthrough，必须进入 `openai_oauth_codex` adapter，做 endpoint 限制、请求体归一化、Header 白名单和上游会话标识隔离。
- 更完整的源码对照和透传定位见 [中转透传机制调研与定位修正](中转透传机制调研与定位修正.md)、[OpenAI OAuth 透传细节统计与比较](OpenAI%20OAuth透传细节统计与比较.md) 和 [OpenAI API Key 透传细节统计与比较](OpenAI%20API%20Key透传细节统计与比较.md)。

后端网关职责：

- 校验本地 API Key。
- 按分组调度账号。
- 替换上游认证。
- 剔除协议安全头和明显代理链路头。
- 隔离会话标识。
- 稳定转发 SSE 流。
- 记录使用情况并按错误策略兜底切换。

当前轻量中转请求链路：

1. 创建原始审计内存捕获上下文，记录客户端原始请求入口信息。
2. 校验 API Key。
3. 找到 API Key 绑定的分组。
4. 获取分组内可调度账户，并过滤已到 `account_expires_at` 的账户。
5. 按状态、并发、代理、错误冷却等规则选账号。
6. 按供应商和账户类型构造上游请求，并把实际上游请求追加到审计上下文。
7. 根据账号错误策略处理上游响应；未命中则临时不可调用当前账号并切换账号。
8. 写入使用记录。
9. 请求结束、失败或客户端中断后，计算审计终态；命中保存规则时把完整审计对象放入内存队列，由后台批量落库。

使用记录和统计聚合使用同一事实源：`usage_records` 保留成功、失败、测试和后台检测记录；业务统计缓存聚合所有使用记录，失败记录没有 token / cost 时按 0 token、0 cost 计入请求和错误次数。

## OpenAI OAuth 授权设计

- OAuth 手动授权：生成 PKCE 授权链接，用户复制 localhost 回调 URL，后端校验 `state` 后换取 token；Client ID 和 Redirect URI 使用后端内置默认值，不作为用户输入项。
- Refresh Token 授权：用户粘贴 `refresh_token`，后端使用内置默认 Client ID 刷新后创建 OAuth 账户。
- OAuth 凭据字段：`access_token`、`refresh_token`、`expires_at`、`client_id`、`email`、`base_url`。
- OAuth token 的 `expires_in` 只用于计算 `credentials.expires_at`，不是账户套餐到期；本地套餐到期统一使用账户字段 `account_expires_at`。
- 网关调度：同一分组内可混合 API Key 账户和 OAuth 账户，OAuth 账户使用 `access_token` 透传到上游。
- 自动刷新：OAuth `expires_at` 接近过期时，用 `refresh_token` 刷新并写回 SQLite。
