## 功能边界总览

- 当前已启用 `profile_openai_openai_v1`、`profile_gpt_openai_v1`、`profile_anthropic_anthropic_v1`、`profile_gemini_native_v1beta`、`profile_gemini_openai_chat_v1beta`、`profile_deepseek_openai_v1`、`profile_deepseek_anthropic_v1`、`profile_glm_general_openai_v1`、`profile_glm_coding_openai_v1` 和 `profile_glm_coding_anthropic_v1`；OpenAI v1 档案承接 Chat / Responses 或 Chat-only 兼容面，Anthropic v1 档案承接 Messages / Models / countTokens 兼容面，Gemini v1beta 档案承接 generateContent / streamGenerateContent / countTokens / embedContent / models。`openai/v1`、`anthropic/v1` 和 `gemini/v1beta` 都是协议层；`providerCode=openai` 是通用 OpenAI-compatible 供应商层，也是 OpenAI v1 协议模型的聚合目录；`gpt` 是继承 `openai` 的 GPT 子供应商，只维护 GPT 自身模型目录；`anthropic` 是官方 Anthropic Claude 供应商，只维护自身 Claude 模型目录，不进入 `openai` 聚合目录；`gemini` 是 Google Gemini 供应商，Gemini native 与 Gemini OpenAI Chat compatibility 分属不同协议档案；`glm` 是独立智谱供应商，通用 GLM API、GLM Coding OpenAI Chat 与 GLM Coding Anthropic Messages 分属不同协议档案；`deepseek` 是独立供应商，DeepSeek OpenAI-compatible Chat 与 DeepSeek Anthropic-compatible Messages 分属不同协议档案。通用 `openai` 供应商支持 API Key，`gpt` 支持 GPT API Key 和 GPT OAuth，`anthropic` 当前只支持 API Key，Anthropic OAuth / Setup Token / Claude Code token 账号链路不纳入当前目标，Claude Code 仅作为下游客户端画像接入 Anthropic v1 Messages 档案，`gemini` 支持 Gemini native API Key 和 Gemini OpenAI Chat API Key，`glm` 支持通用 GLM API Key、GLM Coding OpenAI Chat Key 和 GLM Coding Anthropic Key，`deepseek` 支持 DeepSeek OpenAI API Key 和 DeepSeek Claude Code API Key。
- 系统账户负责后台登录、角色权限、API Key 调用方和数据隔离。
- 系统团队把多个系统账户归纳在一起，用于承接团队级授权使用权。
- AI 账户保存上游凭据、调度状态、代理、并发和可授权使用资源关系；透传不作为账号开关，由供应商网关策略统一决定。GPT 账户只额外允许受模型能力约束的服务等级与思考级别覆盖，不开放任意请求体改写。
- 分组汇总同一供应商下的账户，是策略路由可调度的号池边界；账户协议档案只属于账户真实上游能力。
- API Key 只选择一条路由策略，不直接绑定账户或分组；路由策略可以绑定一个或多个调用方可用分组，请求时按 `model` 优先路由到目标供应商分组，再按账户能力过滤。
- 授权统一由统一授权管理维护，支持 AI 账户、分组授权给系统账户或系统团队。
- 代理是服务器级全局运维资源，只允许管理员维护。
- 使用记录是请求计量事实源；统计缓存只服务高频列表和图表读取。
- 原始审计日志是独立的高权限排障模块，用于保存客户端请求、网关处理、上游请求、上游响应和最终返回的完整原文链路，不参与用量统计。
- 账户错误处理策略保存在 AI 账户 `credentials.error_handling_rules` 中，只在精确客户端画像允许解释上游语义时处理该账户响应；`generic_*` 客户端不执行该策略并原样接收完整上游响应。transport / timeout 失败由网关通用兜底切换账号。

## 系统账户管理

系统账户是后台登录账号，负责权限控制和数据隔离。

当前字段：

- `id`
- `username`
- `display_name`
- `password_hash`
- `role`：`super_admin`、`admin`、`user`
- `status`：`active`、`disabled`
- `must_change_password`
- `image_generation_enabled`：是否允许该系统账户通过 API Key 发起图像生成；默认关闭
- `last_login_at`
- `created_at` / `updated_at`

功能要求：

- 默认初始化一个 `admin/admin` 超级管理员账号，默认不创建普通管理员；管理员角色不触发强制修改密码，登录后可直接进入控制台。
- `super_admin` 可以查看、创建、编辑、停用、启用、重置密码和分配系统账户角色，并可以把普通用户升级为 `admin` 或调整回 `user`；系统账户管理页面和 API 不提供新增或升级其他 `super_admin` 的入口。
- `admin` 可以进入管理模式并查看系统账户列表和选项，但不能创建、编辑、停用、启用、重置密码或调整系统账户角色。
- 后端必须保护至少保留一个启用的 `super_admin`，避免误操作后无人能继续维护系统账户。
- 系统账户管理列表搜索框按用户名和用户名称做精确 / 前缀匹配；ID 和说明不参与搜索。
- 系统账户不提供硬删除；账户停用后禁止登录和继续作为有效调用方，但历史资源、使用记录、统计和审计日志继续保留原系统账户归属。
- 用户账户 `username` 和用户名称 `display_name` 都必须全局唯一；创建时同时校验，编辑时只允许修改用户名称、角色、状态、改密提醒和图像生成权限，不允许修改用户账户。改密提醒只对普通 `user` 生效，`super_admin` / `admin` 一律不强制修改密码。
- 用户账户、用户名称和登录密码都不能包含空白字符，包含首尾空格、中文 / 英文空格、换行和制表符。
- 系统账户图像生成权限默认关闭。网关识别到 Images API、GPT Image / DALL-E 模型或强制调用 Responses 图像生成工具时，如果调用方系统账户未开启图像生成，直接返回 `403 image_generation_disabled` 和“当前用户图像生成被禁用了，请联系管理员开启”，不进入额度校验、候选账号加载或上游调度；其中 Images API 这类路径可直接识别的请求在认证预解析阶段提前拒绝，不读取 raw body。Responses 请求仅在 `tools` 中以 `tool_choice: "auto"` / 未指定工具选择暴露 `image_generation` 时，视为可选工具声明；图像权限关闭时网关移除该工具并按文本请求继续转发，避免 Codex 等客户端默认携带可选图像工具导致普通文本请求被整体拒绝。
- `user` 不能进入系统账户管理，也不能看到其他系统账户的数据归属维度。
- 所有业务数据都必须按 `system_account_id` 或明确 owner/grantee 字段隔离。
- 后端写入和查询以登录态为准，前端不传系统账户归属字段。
- 系统账户可以加入系统团队；团队只影响授权使用权，不改变该系统账户自己的数据归属和调用日志归属。

登录安全：

- 登录态使用服务端会话加 `HttpOnly Cookie`，便于封禁、改角色和强制下线。
- 后台管理 API 使用凭据跨域时必须受 `JUHE_AI_ALLOWED_ORIGINS` 白名单约束；生产环境禁止反射任意 Origin。
- 会话 Cookie 的 `Secure` 和 `SameSite` 由运行时配置统一生成；生产环境默认 `Secure=true`，`SameSite=None` 必须同时启用 Secure。
- 登录验证码使用后端生成的短时挑战：前端先请求验证码能力，默认返回 PNG 验证码图片和 `captchaId`，登录时提交 `captchaId` 与用户输入；图片不能包含可直接解析的文本答案。开发、测试自动化或生产临时排障可显式设置 `JUHE_AI_AUTH_CAPTCHA_DISABLED=true`，此时能力接口返回 `required=false`，前端隐藏验证码且登录可省略验证码字段；该开关只跳验证码，不跳账号密码、登录限频、正式会话或权限，并在服务启动时输出 warn，排障后恢复 `false`。
- 验证码后端无论校验成功或失败都消费该挑战，过期挑战自动失效。
- 公开验证码生成接口按客户端 IP 做短窗口限频，超过阈值直接返回 429，不再生成 PNG 或新增 challenge，避免单一来源挤掉其他用户未提交的验证码。
- 验证码挑战和验证码生成限频当前使用单进程内存存储，不落 SQLite；过期清理只做节流后的固定小批量扫描，容量淘汰按最早插入条目删除，不在登录请求路径全量展开或排序；后续多实例部署再替换为共享存储。
- 登录失败防护采用轻量滑动窗口：同一客户端 IP 在 10 分钟内登录失败 10 次会临时限制 15 分钟；同一用户名在 10 分钟内密码错误 10 次会临时锁定 15 分钟。
- 登录失败防护状态当前使用单进程内存存储；每个 IP / 用户名只保留达到阈值所需的最近时间戳，过期维护按固定小批量轮转，不在登录检查或失败记录请求里全量扫描或排序。
- 验证码错误不计入密码错误次数，但会消耗验证码；密码错误会同时计入 IP 和用户名维度；登录成功后清理该 IP 和用户名的失败记录。
- 普通用户初始密码强制修改场景允许当前登录会话直接提交新密码并清除 `must_change_password`；管理员账户不进入强制改密场景。普通自助改密必须提交当前密码并校验通过。改密成功后只保留当前会话，撤销同账户其他会话。
- 登录用户可在头像下拉中修改自己的显示名称 `displayName`；用户名、角色、状态、图像生成权限和初始改密状态仍属于系统账户管理或改密流程，不开放普通自助修改。
- `GET /__aisys__/api/auth/me` 必须允许普通初始密码用户读取当前用户摘要并返回有效 `mustChangePassword=true`，前端据此进入强制改密流程；普通后台业务接口仍应返回 `403 must_change_password`。`PATCH /__aisys__/api/auth/me` 只允许当前用户修改自己的 `displayName`，普通初始密码用户继续返回 `403 must_change_password`，显示名大小写不敏感唯一，真实变更写 `auth.update_profile` 操作日志。`POST /__aisys__/api/auth/change-password` 允许普通初始密码用户只提交新密码，普通改密和管理员改密必须校验当前密码，成功后清除 `mustChangePassword` 并撤销同账号其他 session。`POST /__aisys__/api/auth/logout` 必须允许无有效登录态调用，有 `juhe_ai_session` 时只撤销当前 token hash 命中的 session，成功后清 Cookie，且清 Cookie 的 `Secure` / `SameSite` 与登录签发 Cookie 复用同一运行时配置。Go W3 opt-in 当前已覆盖 captcha、login / session 创建、current-user 只读、profile update、change-password、当前 session logout、已迁移管理写接口的 `last_seen_at` 60 秒节流 touch，以及系统账户 create / 完整 mixed PATCH；`GET /auth/me` 与 logout 不 touch，`PATCH /auth/me`、change-password 和已迁移管理写接口写鉴权 touch。完整会话管理生产接管、前端 smoke、生产切流和 Node 删除仍未完成。

## 协议与供应商管理

供应商不是简单字符串，而是模型目录、价格目录、账号池和账户创建能力的归属。协议是接口形态，描述客户端和上游适配如何表达请求、响应、SSE 事件和错误；同一个协议可以被多个供应商复用，不同协议也可能需要完全不同的网关 adapter。当前系统固定使用五层核心模型，客户端策略作为运行时附加层：

| 层级 | 存储 / 字段 | 当前值 | 说明 |
| --- | --- | --- | --- |
| 协议 | `protocols.code` | `openai`、`anthropic`、`gemini` | 表示接口协议族，不是账号池供应商。 |
| 协议版本 | `protocols.version` | `openai/v1`、`anthropic/v1`、`gemini/v1beta` | 表示协议版本。当前 OpenAI-compatible 网关使用 `openai/v1`，Anthropic 官方直连使用 `anthropic/v1`，Gemini native 使用 `gemini/v1beta`。 |
| 端点族 | `protocol_endpoint_families.family_code` | `chat_completions`、`responses`、`messages`、`models`、`message_token_counting`、`generate_content`、`stream_generate_content`、`count_tokens`、`embed_content` | 表示同一协议下的接口形态，用于路径能力、模型目录标签和测试策略。 |
| 供应商 | `providers.code` | 当前 `openai`、`gpt`、`anthropic`、`deepseek`、`glm`、`gemini` | 表示账号池、模型目录和价格目录归属；`openai` 是通用 OpenAI-compatible 供应商，`gpt.parent_code = openai`；`anthropic`、`deepseek`、`glm`、`gemini` 都是独立供应商。 |
| 供应商协议档案 | `provider_protocol_profiles.id` | 当前 `profile_openai_openai_v1`、`profile_gpt_openai_v1`、`profile_anthropic_anthropic_v1`、`profile_gemini_native_v1beta`、`profile_gemini_openai_chat_v1beta`、`profile_deepseek_openai_v1`、`profile_deepseek_anthropic_v1`、`profile_glm_general_openai_v1`、`profile_glm_coding_openai_v1`、`profile_glm_coding_anthropic_v1` | 把供应商和协议版本绑定成可创建账户、可测试和可调度的账户能力档案。 |

当前供应商、协议和协议档案均由系统内置，管理面只展示内置供应商、账户类型和模型目录，不提供新增、编辑或删除。供应商协议档案作为内部能力解析结果，用于接口返回、排障、测试和调度，不作为普通账户创建流程里的用户选择项。

当前内置能力：

- 协议：`openai/v1`、`anthropic/v1`、`gemini/v1beta`
- 端点族：OpenAI v1 为 `chat_completions`、`responses`；Anthropic v1 为 `messages`、`models`、`message_token_counting`；Gemini v1beta 为 `models`、`generate_content`、`stream_generate_content`、`count_tokens`、`embed_content`
- 供应商：当前 `openai`、`gpt`、`anthropic`、`deepseek`、`glm`、`gemini`
- 供应商协议档案：当前 `profile_openai_openai_v1`、`profile_gpt_openai_v1`、`profile_anthropic_anthropic_v1`、`profile_gemini_native_v1beta`、`profile_gemini_openai_chat_v1beta`、`profile_deepseek_openai_v1`、`profile_deepseek_anthropic_v1`、`profile_glm_general_openai_v1`、`profile_glm_coding_openai_v1`、`profile_glm_coding_anthropic_v1`
- 账户类型：通用 `openai` 支持 `api_key`；`gpt` 支持 `oauth`、`api_key`；`anthropic` 当前只支持 `api_key`；`gemini` 在页面分为“Google Gemini API Key”和“Google Gemini OpenAI Chat API Key”；`deepseek` 在页面分为“DeepSeek OpenAI API Key”和“DeepSeek Claude Code API Key”；`glm` 在页面分为“通用 GLM API Key”、“GLM Coding Plan Key”和“GLM Coding Anthropic Key”；这些第三方入口底层都保存为 `api_key`，通过协议档案区分。
- 默认上游地址：OpenAI v1 为 `https://api.openai.com/v1`；Anthropic 官方为 `https://api.anthropic.com/v1`；Gemini native 为 `https://generativelanguage.googleapis.com`，Gemini OpenAI Chat 为 `https://generativelanguage.googleapis.com/v1beta/openai`；DeepSeek OpenAI-compatible 为 `https://api.deepseek.com`，DeepSeek Claude Code 为 `https://api.deepseek.com/anthropic`；GLM 通用为 `https://open.bigmodel.cn/api/paas/v4/`，GLM Coding OpenAI Chat 为 `https://open.bigmodel.cn/api/coding/paas/v4`，GLM Coding Anthropic 为 `https://open.bigmodel.cn/api/anthropic`
- 协议档案内置默认检查模型：GPT 默认 `gpt-5.5`，Anthropic 默认使用内置 Claude 低成本检查模型，Gemini 默认 `gemini-3.5-flash`。新账户的检查模型按“当前系统账户个人默认 > 管理员维护的供应商系统默认 > 协议档案内置默认”初始化；账户保存后只读取自己的 `healthCheckModel`，后续默认值变化不改写已有账户。账户还必须保存精确 `healthCheckEndpointMode`：GPT 官方默认 `responses_sse`，OpenAI-compatible 默认 `chat_json`，Anthropic 默认 `messages_json`，Gemini Native 默认 `generate_content_json`；后台直接发送该请求形态，不再从协议族推导。所有供应商的 JSON / Streaming 生成形态均可作为检查协议，前提是账户上游接口能力已启用；工具、计数、嵌入、上传和下载接口不进入检查协议。混合供应商按所选 mode 构造诊断请求，再由模型映射决定实际上游协议和模型。

代码和数据库为了列表展示仍会在供应商摘要上带出默认协议档案的 `protocolCode`、`protocolVersion`、`baseUrl`、`defaultHealthCheckModel`、`accountTypes` 和 `capabilities`，但这些字段语义上属于默认供应商协议档案，不代表所有供应商都天然支持同一组 OpenAI v1、Anthropic v1 或 Gemini v1beta 端点。后续新增供应商时，必须先新增对应协议 / 供应商 / 协议档案定义，再让账户、检查和网关 driver 按档案接入；分组只按供应商接入。Anthropic 官方直连已经使用独立 `anthropic/v1` 档案；Gemini native 已使用独立 `gemini/v1beta` 档案；OAuth / Setup Token / Claude Code token 账号链路不纳入当前目标，Claude Code 客户端工具按 client profile 接入。智谱 GLM 是独立第三方供应商，通用 GLM API、GLM Coding OpenAI Chat 与 GLM Coding Anthropic Messages 必须拆成不同 GLM 协议档案；DeepSeek 也按 `profile_deepseek_openai_v1` 和 `profile_deepseek_anthropic_v1` 拆分 OpenAI-compatible Chat 与 Anthropic-compatible Messages；新增供应商只声明各自对应的协议档案，不混写到 OpenAI v1、官方 Anthropic 或 Gemini native 协议总层。

供应商模型目录：

- 模型价格应归属于供应商，而不是散落在网关代码里。
- 当前内置 GPT / OpenAI 官方模型价格快照归入 `gpt` 供应商自身目录；`openai` 通用供应商聚合自身和显式纳入聚合的 OpenAI-compatible 子供应商模型，不能自动包含所有 OpenAI v1 协议供应商。DeepSeek、Anthropic 等独立供应商归入自身目录，不进入 `openai` 聚合目录。字段采用 LiteLLM / `model-price-repo` 的语义，token 单价以 USD/token 存储，接口展示时换算为 USD/1M tokens。
- 所有模型目录返回顺序必须按 `releaseDate` 发布时间倒序；发布时间越新的模型越靠前，未填写发布时间的模型排在已填写发布时间的模型之后，再按模型 ID 稳定排序。
- 供应商页提供“查看模型”入口，展示模型版本、输入/输出/缓存读写/图片价格、上下文窗口和能力标签。
- GPT 模型目录使用 `supportedServiceTiers`、`supportedReasoningEfforts` 和 `defaultReasoningEffort` 精确描述 OpenAI API 请求能力，并使用独立 Codex 能力字段驱动 `/models`；自定义 GPT 模型也必须维护对应能力数组。账户请求覆盖不接受 `ultra`，Responses Multi-agent Beta 不在本期范围。
- 网关成本估算复用供应商模型目录；未命中模型时只记录 token，不猜测成本。

## AI 账户管理

AI 账户是上游凭据和调度配置的承载对象，归属某个系统账户。

当前字段：

- `id`
- `system_account_id`
- `provider_code`：供应商稳定编码，例如 `openai`、`gpt`、`anthropic`、`gemini`、`deepseek` 或 `glm`；该字段属于账号池 / 供应商层，不等同于 `protocol_code`
- `provider_protocol_profile_id`：供应商协议档案 ID，当前内置 `profile_openai_openai_v1`、`profile_gpt_openai_v1`、`profile_anthropic_anthropic_v1`、`profile_gemini_native_v1beta`、`profile_gemini_openai_chat_v1beta`、`profile_deepseek_openai_v1`、`profile_deepseek_anthropic_v1`、`profile_glm_general_openai_v1`、`profile_glm_coding_openai_v1` 和 `profile_glm_coding_anthropic_v1`；账户只能加入同供应商分组
- `protocol_code` / `protocol_version`：从协议档案冗余写入，用于运行时策略、审计和排障
- `name`
- `type`：`oauth` 或 `api_key`
- `status`：`active`、`pending_test`、`disabled`、`error`、`rate_limited`、`temporary_unavailable`
- `health_check_model`：账户必填检查模型，必须属于最终 `supported_models` 且满足协议最小检查能力；后台激活、周期健康、运行态恢复和 Key 恢复探针都严格使用该字段，不回退到其他模型
- `credentials`：加密后的凭据内容；GPT 账户可选保存 `service_tier_override` 和 `reasoning_effort_override`，空值表示保留客户端请求，已配置值在最终上游请求体生成前覆盖客户端值
- `credential_fingerprint`：上游凭据指纹；按凭据明文归一化后哈希，用于排查相同凭据，不做唯一约束
- `credential_mask`：凭据安全摘要字段；列表不展示凭据，编辑弹窗可展示完整凭据
- `proxy_profile_id`
- `concurrency_limit`：创建账户时默认 `20`，资源所有者可在账号表单中按账号调整；授权账户只读展示来源账号的硬并发上限，被授权用户不能修改该字段。
- `current_concurrency`：运行态字段，由主进程内网关请求生命周期实时计算；请求命中账号后占用，响应完成、流结束或失败退出时释放，不作为 SQLite 持久化主状态。授权实例和来源账号共享同一真实上游资源，硬并发槽与列表实时并发读数都按来源账号 ID 统计。
- 客户端画像由网关按请求路径、协议族、请求体结构和可信客户端特征内部识别，不作为 API Key、分组或普通 AI 账户的可配置字段保存。
- 账户不保存通用透传开关；GPT API Key 只有在请求侧识别为 Codex Responses 且路径为 Responses 时才启用 Codex 请求体和必要请求头补齐，其他请求仍保持 raw body 透传；OAuth 固定由 Codex adapter 内部处理。GLM / DeepSeek / Gemini OpenAI Chat 等 OpenAI v1 Chat-only 上游承接 Codex Responses / OpenAI Responses 时，由普通 AI 账户显式 `responses -> chat_completions` 模型别名声明，策略路由只负责选择路由模式、分组和目标模型；Anthropic Messages、Gemini native 等其他跨协议入口仍由混合供应商账户声明转换。
- `priority`：自有账户的全局排序配置；授权账户在当前分组内的排序读取 `group_accounts.local_priority`，不修改来源账户，也不影响其他被授权人或其他分组绑定。
- `super_priority_enabled`：自有账户的临时应急调度标记，只允许正常状态账号开启；授权账户开启超级优先时写入当前分组绑定的 `group_accounts.local_super_priority_enabled`，校验当前授权实例已绑定当前用户分组、授权有效、额度未耗尽、实例未到期且实例可调度。账号变为停用、异常、限流中或临时不可调用时保留用户配置但暂停生效，恢复正常后自动重新参与调度，只有用户手动取消时才清除。
- `fallback_enabled`：自有账户的降级备用标记，只允许正常状态账号开启；授权账户开启备用时写入当前分组绑定的 `group_accounts.local_fallback_enabled`，同样只校验授权实例可用性和当前用户分组绑定要求。仅在同分组非备用账号都不可用或请求失败后进入调度，账号变为停用、异常、限流中或临时不可调用时保留用户配置但暂停生效，恢复正常后自动重新参与调度，只有用户手动取消时才清除。
- `schedulable`
- `account_expires_at`：本系统的账户套餐/购买到期时间；可为空，和 OAuth token 的 `credentials.expires_at` 分离
- `notes`
- `last_used_at`
- `cooldown_until`：账号临时冷却截止时间；未来时间内不参与调度
- `last_error_code`：异常子类型编码；`status = error` 时用于区分 `oauth_token_refresh_failed`、`upstream_failure` 等具体异常来源
- `last_error_message`：最近一次熔断、临时不可调用或失败原因摘要
- `stream_failure_count`：流失败诊断窗口内累计次数
- `stream_failure_window_started_at`：流失败诊断窗口起始时间
- `created_at` / `updated_at`

列表和权限：

- 账户列表展示账户名称、来源、所有者摘要、账户类型、供应商、并发数、状态、用量情况、优先级、最近使用时间、到期时间和操作。到期时间列按“授权到期时间优先，其次账户到期时间”展示；自有账户没有授权到期时只展示账户套餐到期。
- 账户列表搜索框只按账户名称做精确 / 前缀 / 包含匹配；账户名称最长 128 个字符。包含匹配通过账户名 1/2/3 连续字符词项索引收敛候选账号 ID，并由规范化账户名文档做连续片段校验，不允许对 `accounts` 主表裸跑前导通配符扫描。分组使用独立下拉筛选，不把账户 ID、供应商编码、账户类型、Base URL 或备注放进通用搜索。管理侧查看全部系统账户时不展示跨用户分组下拉，需先选定系统账户后再筛分组。
- 管理员视角额外展示系统账户列；用户视角自有账户不展示归属列，授权账户显示“来自授权”和所有者摘要。
- `Access/API Key` 与 `Refresh Token` 不在列表展示；只有账户所有者可在编辑弹窗里查看和修改。授权账户永不返回完整敏感凭据，但详情可返回来源账户 `base_url`、公开 OAuth 元数据、模型、代理、并发、时间计划、账户追加流式规则和来源状态等非敏感配置用于只读展示。
- 底层账户状态语义统一为正常、待检查、停用、异常、限流中、临时不可调用；顶层异常统一使用 `status = error`，具体异常类型写入 `last_error_code`，可读说明写入 `last_error_message`。`precheck_pending`、`local_suppressed`、`half_open` 和 `precheck_failed` 是运行态可用性，不进入底层 `accounts.status` 枚举；列表可把它们归类展示为临时不可调用，但写库前仍要保留原账户状态。账户列表状态标签在底层状态外叠加展示层有效状态：授权到期显示“授权到期”，授权绑定失效显示“授权已失效”，账户套餐到期显示“账户到期”，授权额度耗尽显示“授权额度已用完”；这些展示层状态不新增底层 `accounts.status` 枚举，也不能把授权额度耗尽误写成物理账户 `rate_limited`。状态筛选不新增“授权额度已用完”选项，授权额度耗尽按不可调用的授权方额度限制归类到现有 `rate_limited` 筛选中。

账户状态筛选只允许使用页面现有 6 个状态，展示标签可以更细，但筛选枚举不能继续增加。所有派生状态必须按下表归类：

| 筛选状态 | 归类规则 |
| --- | --- |
| 正常 | 仅包含真实可用、可调度的账户；`active` 但授权到期、授权额度耗尽、来源不可用、冷却中或运行态拦截的账户不能归入正常。 |
| 待检查 | 自身 `pending_test`、授权实例待检查、来源账户待检查。 |
| 停用 | 自身停用、账户到期、授权到期、授权暂停、授权已失效、授权绑定失效、未绑定分组、来源删除、来源停用、来源到期、来源停调、授权实例停调。时间计划导致的时段外不新增派生状态，而是直接表现为账户或来源账户 `status=disabled`。 |
| 异常 | 自身异常、授权实例异常、来源账户异常；具体异常类型继续由 `last_error_code` 和错误摘要解释。 |
| 限流中 | 自身限流、授权实例限流、来源账户限流、授权额度已用完，以及明确属于额度 / 限频 / 限流的不可调用原因。 |
| 临时不可调用 | 自身临时不可调用、自身冷却、授权实例临时不可调用、授权实例冷却、来源临时不可调用、来源冷却、账户内 Key 全部不可用、网关短暂避让 / 待探针确认 / 半开探测 / 探针失败等临时恢复类运行态。 |

权限不足不是账户状态，不新增筛选值；权限层应直接限制可见性或操作能力。运行态原因只影响实际可用性和当前列表展示，不允许引入新的持久账户状态。

后端账户列表筛选以 `effectiveAvailability` 的 6 类归并结果为最终口径；服务端运行态快照可用时，列表接口必须在合并运行态后对“正常 / 临时不可调用”再做后置归类，避免短暂避让、待探针确认、半开探测或探针失败的账户继续落入正常。轻量 options 接口不返回完整 `effectiveAvailability`，也不主动请求 server runtime snapshot；但 options 的状态筛选必须覆盖授权额度、授权关系、来源账户、授权实例、账户内 Key 池这些存储侧可判断的派生状态，并落入同一组 6 个筛选入口。

- 授权账户视图必须隔离“实际可用性”“授权实例本地状态”“授权关系状态”和“来源资源事实”：返回给被授权用户或管理员代看被授权用户时，`effectiveAvailability` 是页面主状态和可操作性判断口径，按权限、本地绑定、最终用户授权、额度、来源账户可用性、授权实例本地状态和网关运行态计算；授权实例 `accounts.status / schedulable / cooldown_until / last_error_*` 是被授权侧本地运行态存储，不被来源账户覆盖或回写；`group_accounts.account_authorization_id` 只负责标识这条绑定对应哪条用户级授权；当前分组内 `priority`、`superPriorityEnabled` 和 `fallbackEnabled` 来自 `group_accounts.local_priority / local_super_priority_enabled / local_fallback_enabled`；`authorizationStatus`、`authorizationExpiresAt` 和 `authorizationSources` 只负责解释授权关系是否还有效。归属人原账户的停用、异常、冷却、关闭调度、套餐到期、删除或凭据缺失会阻断授权实例实际可用性，但不能覆盖或回写授权实例账户行；上游凭据、`base_url`、账号类型、支持模型、代理、并发、可用时段和账户追加流式规则从来源账户补齐。列表可额外返回 `authorizationInstanceSourceAccountStatus`、`authorizationInstanceSourceAccountSchedulable`、`authorizationInstanceSourceAccountExpiresAt`、`authorizationInstanceSourceAccountCooldownUntil` 和来源错误摘要用于解释来源侧阻断。手动测试可以作为诊断入口读取授权实例，但测试成功不自动代表当前可调度。
- 编辑弹窗只维护账户配置，不提供状态修改；编辑保存时不提交 `status`，避免覆盖后台检查、自动恢复、错误处理或网关冷却刚写入的状态。凭据、Base URL、协议档案或关键代理等连接配置变化后，后端把账户交给 `pending_test` 激活复检；检查模型变化立即投递后台健康检查，名称、标签、备注和优先级等非连接配置不改变状态。
- 账号优先级按数字从小到大生效，`0` 优先于 `10`；同分组调度时先尝试优先级更高的账号。
- 账户所有者可在正常账号的“更多”菜单设置“超级优先”。超级优先用于应急人工提权，多个账号可同时开启；开启后状态列在“正常”旁展示“超级优先”。如果账号状态变为非正常，系统保留用户设置但暂停生效，列表展示暂停提示；恢复正常并参与调度后自动重新生效。用户需要移除时可在“更多”菜单手动取消。
- 账户所有者可在正常账号的“更多”菜单设置“降级备用”。降级备用和超级优先不能同时开启；备用账号不参与首轮主池调度，只有同分组非备用账号全部不可用、额度不可用、并发已满或请求失败后才会继续尝试备用池；多个备用账号内部仍按账号优先级、质量分和稳定顺序排序。账号非正常时同样保留用户设置但暂停生效，恢复正常后自动重新生效。
- 账户所有者可在“更多”菜单执行“迁移流量”：选择同一系统账户、同一供应商协议档案、当前 API Key 路由候选范围内的可调度目标账户，把当前进程内命中源账户的会话亲和绑定切到目标账户。默认的 `unchanged` 不影响源账户状态，只迁移已有且当前命中源账户的客户端会话；必要时可把源账户改为 `temporary_unavailable` 或 `disabled`。迁移亲和绑定通过源账号、系统账户和可选 API Key 反向索引定位候选会话，不扫描全部亲和缓存；只有源账户被改为临时不可调用或停用时，才同时按本地系统账户和分组记录短期目标偏向，在源账户仍未回到候选池前，后续请求会优先尝试目标账户。迁移目标偏向是当前作用域内的短期最高排序覆盖，优先于会话亲和、超级优先、主池 / 备用池分层、账号优先级和质量分；但不绕过 API Key / 系统账户 / 分组 / 授权作用域 / 模型 / 状态 / 额度 / 硬并发等候选硬条件。该动作只影响后续请求，不主动中断已经建立的流式连接；当前正在输出的请求继续跑完。它不复制凭据、不修改 API Key、路由策略或账户分组绑定，只用于人工快速止血。
- 人工账户测试只做诊断。新增和编辑表单测试固定使用当前表单的 `healthCheckModel`，不提供临时模型下拉；列表单项测试打开时按需请求 `test-options`，模型候选来自账户供应商、协议档案和所有者作用域可见的启用文本模型目录，不受账户 `supportedModels` 限制，默认选中账户检查模型。人工测试成功或失败都不修改账户、授权实例、来源账户、账户内 Key、检查模型、支持模型、健康事实、冷却、错误、调度运行态、代理桶、客户端回避或会话亲和，只保留脱敏诊断结果、使用记录和审计，`traffic_source = manual_account_test`。
- 自有待检查账户复用操作菜单中的统一“恢复正常”入口。操作者必须明确确认账户当前可用；服务端只接受精确 `pending_test` 状态、拒绝授权实例和过期账户，按账户时间计划决定立即正常或计划停用，并清理待检查失败窗口。服务端继续用 `accounts.force_activate_pending` 记录该高风险状态转换的操作日志，但前端不再暴露独立的“人工恢复正常”菜单或处理分支；“重新检查”仍保持待检查并交给后台确认。
- 新建账户和导入请求中的 `active` 都先保存为 `pending_test`，事务完成后由后台激活检查使用账户检查模型确认，成功后才进入 `active`；明确创建为 `disabled` 时不投递激活检查。人工草稿测试结果不能作为创建、导入、编辑、激活或恢复凭证。多 API Key 人工测试可以返回逐 Key 诊断明细，但不能推进轮换或写入 Key 运行态；Key 初始化和恢复由后台 Key 探针负责。
- 手动账户测试有两类等待上限：`queued` 等待上限用于避免后台 `ops-worker` 未接收或队列堆积导致任务长期卡住，`running` 运行上限从后台任务进入 `running` 并写入 `started_at` 后开始计算，保持 `10s + 20s + 30s` 的 60 秒总诊断窗口。`queued` 期间必须持续记录 `queued_at`、最近投递 / 接收状态和等待时长；超过队列等待上限时，任务应收口为失败或取消，并给出“后台测试 worker 长时间未接收任务”类可排障消息。后端从数据库补充 runnable 测试任务时必须按固定窗口读取，不能一次性把全部 `queued` 任务灌入 worker 内存队列。
- 账户页面不提供多账户批量测试。每次单账户测试使用独立 `testSessionId`，账户 A 的运行任务不能阻止账户 B 启动测试；关闭弹窗只解除当前前端展示绑定，显式停止只取消当前会话，旧会话结果和延迟返回不能覆盖后来打开的弹窗。后台冷却复测不从用户真实请求快照里重放业务 prompt；恢复探活不进入业务统计或账户质量统计。
- 账户页加载分组元数据只使用轻量分组选项和 `accountIds` 映射，不读取分组统计、用量或并发快照；完整分组摘要只服务分组管理主列表。
- 异常账户和停用账户同属不可调度硬状态。异常账户在页面保留编辑、删除、测试、“异常恢复”、停用和取消既有调度标记入口；编辑可改名称、凭据、代理、策略等基础信息，但除停用外不能借编辑切到正常、限流中或临时不可调用。刷新 OAuth Token、重新授权、新增超级优先、新增降级备用、迁移流量和分组调整入口都隐藏。异常恢复会清理异常、健康检查和冷却字段，原子进入不可调度的 `pending_test` 并立即投递后台激活检查；只有检查成功后才能恢复正常。人工测试在异常、停用和其他状态下都只做诊断，不能恢复或改写状态。
- 修改凭据、Base URL 或检查协议后，旧配置版本的在途网关成功信号不得写回待检查账户，也不得把 `next_health_check_at` 推到正常 12 小时周期。Node 和 Go 在提交配置后立即投递 `configuration` 检查；周期扫描对所有 `pending_test` 忽略旧成功信号，但仍服从失败后固定一小时的 `next_health_check_at` 退避。停用账户只保存待检查计划，不立即请求上游。
- AI 账户批量编辑使用独立事务接口，只允许显式勾选白名单字段并直接覆盖；名称、分组、归属、供应商、协议档案、类型、凭据、Base URL、状态、健康事实和运行态均不可修改，授权实例不参与。模型和协议配置只在全部目标账户具有相同 `providerCode + providerProtocolProfileId + type` 时开放；后端按 `expectedVersions` 做乐观锁校验，在一个事务中完成全部权限、最终配置和关联表校验，任一账户失败或版本冲突时整批不写。
- 被授权用户获得授权实例账户时，新增授权必须已经绑定目标分组；后续可以像普通账户一样打开编辑弹窗，但只能修改自己的加入分组和分组内优先级，OpenAI API Key / OAuth Token 等敏感凭据不显示，名称、凭据、代理、并发、模型、账户追加流式规则和备注都不能修改；除敏感凭据外，来源账户的 `base_url`、公开 OAuth 元数据、模型、代理、并发、时间计划、账户追加流式规则和来源状态都应只读展示。授权账户的硬并发上限和当前并发槽按来源账号共享，普通更新接口必须拒绝被授权人提交 `concurrencyLimit`。授权账户“更多”菜单仍承载超级优先、降级备用、迁移流量和实例状态类操作。管理员在管理侧按某个系统账户查看授权账户时，也可以代该用户执行编辑分组 / 优先级、账户测试和使用侧调度操作。列表必须返回授权实例绑定所属的 `bindingSystemAccountId`，前端管理侧写接口必须优先携带该值；后端测试、迁移和调度写入也必须按该被代操作用户解析授权实例绑定。优先级、超级优先和降级备用只写当前 `group_accounts` 绑定；停用、恢复、异常、冷却和迁移流量这类运行态写授权实例自己的 `accounts` 行。所有这些操作只影响该用户自己的授权实例或当前分组绑定，不修改账户所有者原账户，也不影响其他被授权用户的授权实例和绑定。授权账户迁移流量可以把源授权实例设为临时不可调用或停用，并可迁移到同分组内当前用户可用的授权账户或自有账户。授权实例停用后，账户页和下拉选项都应显示“停用”，按“停用 / 不可调度”筛选能命中，按“正常 / 可调度”筛选不能命中；归属人的原账户仍保持自己的状态。
- 账户上游 `base_url` 保存和出站请求都必须经过 SSRF 防护：默认拒绝本机、内网、链路本地、保留地址和带用户名密码的 URL；历史旧数据或缓存绕过保存层时，网关最终出站前仍要做同样校验和 DNS 解析结果校验。全局开关 `JUHE_AI_ALLOW_PRIVATE_UPSTREAM_BASE_URLS` 只允许本地 mock 或回归测试使用，生产仍禁止；`JUHE_AI_UPSTREAM_BASE_URL_PRIVATE_ALLOWLIST` 默认留空，确有需要时只能由部署者显式配置精确 `scheme + IP + effective port` origin，发布包和生产示例不得自动预置。

账号质量调度：

- `account_quality_scores` 保存账号最近质量缓存，默认来源是近 10 分钟真实请求；客户端请求时只读取缓存，不临时扫描 `usage_records`。
- 主用量统计 worker 按 `(created_at, id)` 游标递增读取 `usage_records` 时，同步写入持久化的 `account_quality_minute_stats` 分钟桶；服务重启后不会丢失，升级补齐也通过独立 `stats_job_state` 游标线性回填。
- 后台 `account-quality-refresh` 默认每 10 分钟运行一次，只汇总 `account_quality_minute_stats` 的近窗口数据刷新质量分，不再按时间窗口回扫 `usage_records`，也不保留任何主动探测能力或开关。
- 删除主动探测的原因是它不是恢复项，而是优化项；当前系统只保留冷却到期后的恢复性确认，避免无业务价值地消耗上游请求。
- 调度只使用 24 小时内有真实样本更新过的质量分；更旧的质量缓存视为过期，不参与排序，客户回归后的第一次请求按“超级优先 > `priority` > 稳定兜底顺序 > 降级备用池”选择，随后由真实请求和下一轮 worker 恢复质量缓存。
- 网关调度顺序为：非备用池先于降级备用池；每个池内超级优先账号先于普通账号，账号 `priority` 小者优先；只有同层级候选数 `>= 2` 时，才按 `quality_score` 从小到大继续择优。层级内只有一个账号时不启用质量机制。

账户生命周期：

- `account_expires_at` 为空表示不设置本地套餐到期。
- 一旦到期，后端把账户改为 `disabled`、`schedulable = 0`、清空冷却时间并写入到期原因。
- 网关调度、真实响应头快照写入、成功/失败恢复逻辑都不能重新启用已到期账户。
- 只有用户清空或延后 `account_expires_at` 后才允许再次启用。

创建入口：

- 页面只提供“添加 AI 账户”。
- 弹窗内先选择供应商，再按该供应商当前默认协议档案能力展示账户类型，最后渐进展开具体配置；用户不选择 `providerProtocolProfileId`。
- 后端按供应商和当前启用能力解析默认 `provider_protocol_profile_id`，并把解析出的协议、协议版本、端点族和账户类型能力用于创建校验、测试和调度。
- `openai` 当前只有 `profile_openai_openai_v1` 一个协议档案，只支持 `api_key`；`gpt` 当前只有 `profile_gpt_openai_v1` 一个协议档案，支持 `oauth` 与 `api_key` 两种类型。后续同样使用 OpenAI v1 协议的供应商也必须新增独立供应商编码和协议档案，不复用 GPT 的账号池和模型目录。
- `glm` 目标提供三个页面接入类型：通用 GLM API Key、GLM Coding Plan Key 和 GLM Coding Anthropic Key。三者底层都是 `api_key`，但分别解析到 `profile_glm_general_openai_v1`、`profile_glm_coding_openai_v1` 和 `profile_glm_coding_anthropic_v1`；不能只靠用户手填 `base_url` 推断档案，也不能把 Coding Plan Key 或 Coding Anthropic Key 塞进通用 GLM 分组。
- `gemini` 提供两个页面接入类型：Google Gemini API Key 和 Google Gemini OpenAI Chat API Key。二者底层都是 `api_key`，但分别解析到 `profile_gemini_native_v1beta` 和 `profile_gemini_openai_chat_v1beta`；不能把 Gemini native 账户塞进 OpenAI Chat 档案。
- `deepseek` 提供两个页面接入类型：DeepSeek OpenAI API Key 和 DeepSeek Claude Code API Key。二者底层都是 `api_key`，但分别解析到 `profile_deepseek_openai_v1` 和 `profile_deepseek_anthropic_v1`；不能只靠用户手填 `base_url` 推断档案，也不能把 DeepSeek 账号塞进 GPT 或通用 OpenAI 账号池。

## OAuth 额度快照

GPT OAuth 账户还有上游 Codex/ChatGPT 使用窗口限制，不能和 API Key 账户的本地 token / 成本用量混为一类。

展示规则：

- 账户列表“用量情况”分成本地网关统计和 OAuth 专属额度进度两层。
- 本地网关统计从统计缓存读取，事实源仍是 `usage_records`；统计缓存聚合请求数、Token 消耗、成本、耗时和错误。
- OAuth 专属额度进度来自上游返回的 Codex rate-limit 快照，用独立进度条展示 `5h` 与 `7d` 窗口百分比、预计恢复时间和快照更新时间。
- OAuth 额度进度只表示上游 OAuth 额度占用，不参与 API Key 计费口径。
- OAuth 额度快照是非敏感运行态摘要；账户所有者和获得该 OAuth 账户使用权的被授权用户都可以在账户列表看到对应进度。

当前存储：

- OAuth 额度快照单独存储为非敏感运行态，不写进 `credentials`。
- 当前采用 `account_usage_snapshots` 或等价 repository 对象。
- 按 `system_account_id + account_id + kind` 保存 `openai_codex` 快照。
- 保存原始 primary/secondary header、归一化后的 `codex_5h_*` / `codex_7d_*` 字段、`reset_at`、`window_minutes`、`updated_at`、`source`、`last_attempt_at`、`last_success_at`、`next_refresh_after`、`refresh_status` 和 `last_error_message`。
- 列表接口只返回可展示摘要，不返回 access token、refresh token 或完整请求内容。

更新规则：

- OAuth 额度快照只从真实网关请求和账户测试返回的 Codex rate-limit 响应头被动更新。
- OAuth 账户创建成功后不主动发模型请求获取额度；第一次真实调用或账户测试返回相关响应头后才出现快照。
- 后台 worker 不再注册 OAuth 额度快照主动刷新任务；保留 OAuth Access Token 预刷新，因为它只做凭据续期。
- 快照缺失或过期不触发列表页批量探测，页面显示“暂无快照”或“等待真实请求更新”。
- 收到 OpenAI OAuth / Codex 额度响应头时，网关只更新额度快照和下次刷新参考时间；账号状态不再按 OAuth 429、`resets_at` 或 `resets_in_seconds` 写内置 `rate_limited`。命中上游账号后发生错误时，仍由统一请求错误处理链路先进入运行态确认；确认失败后才写当前账号状态，账户错误处理策略可以把目标状态改写为 `rate_limited`。

## 授权团队管理

授权团队用于把多个系统账户归纳在一起，方便资源所有者一次性把 AI 账户或分组授权给团队成员共享使用。团队不是资源所有者，不改变团队成员自己的数据归属、API Key 归属和使用记录归属；底层仍使用系统团队数据模型。

功能要求：

- 管理侧菜单名称为 `授权团队`，挂在 `统一授权管理` 下，当前仅 `super_admin` / `admin` 可见和维护。
- 授权团队列表搜索框只按团队名称做精确 / 前缀匹配；团队 ID 和说明不进入通用搜索。
- 管理员可以创建授权团队、编辑团队基础资料、启停团队、添加成员和移除成员。
- 普通用户不能进入授权团队管理页；普通用户菜单提供 `我的授权团队`，只读展示自己加入的团队和团队成员。
- 统一授权管理读取授权对象选项时，管理员和普通用户都可以读取全系统可授权用户 / 团队的最小摘要；这是授权候选目录的产品口径，不复用系统账户管理列表，也不返回角色、最后登录、团队成员明细或其他管理字段。
- 团队停用后，所有团队授权立即不可继续生效；历史授权和历史使用统计保留。
- 成员移除后，该成员不再通过团队授权获得资源使用权；团队授权变更必须同步维护最终用户授权及来源状态，网关调度只读取用户级授权、系统账户状态、授权实例或分组资源状态、绑定关系和额度缓存，不再把团队作为第二套运行时主体遍历判断。

当前字段见 [系统团队与统一授权设计](系统团队与统一授权设计.md)。

## 统一授权管理

统一授权管理用于把 AI 账户或分组的“使用权”授予某个系统账户或系统团队。授权不改变资源所有者，不复制敏感凭据，也不复制上游资源配置；AI 账户授权会创建被授权人的授权实例账户作为状态、绑定和用量载体，运行时上游资源事实仍从来源账户补齐。

菜单与入口：

- 用户侧为二级菜单 `我的授权`，包含 `授权操作`、`团队消耗明细`、`用户消耗明细` 和 `我的授权团队`；普通用户只能查看自己授权出去或授权给自己的记录。
- 管理侧为二级菜单 `统一授权管理`，包含 `统一授权`、`团队消耗明细`、`用户消耗明细` 和 `授权团队`。
- `统一授权` / `授权操作` 只负责授权关系管理，管理员可以在管理侧查看全部并执行新增授权、暂停、恢复、回收和修改授权配置，普通用户可以在用户侧管理自己授权出去的关系，也可以归还授权给自己的资源。
- 授权消耗不在 `统一授权` / `授权操作` 列表展示，统一进入对应菜单组下的 `团队消耗明细` 和 `用户消耗明细`。
- AI 账户页和分组页不再放资源自己的授权管理入口，只显示资源来源、所有者摘要和当前用户权限摘要。

语义规则：

- 当前只支持一种授权范围：`use`。
- 支持授权资源类型：`account`、`group`。
- 支持授权对象类型：`system_account`、`team`。
- 资源所有者可以新增授权、回收授权、查看授权消耗总量和按系统账户拆分的消耗明细。
- 授权给团队时，系统批量给团队内有效成员建立或合并用户级授权；团队成员新增、移除和团队停用应动态维护这些用户级授权来源。
- 同一系统账户同时通过个人来源和团队来源获得同一 AI 账户或分组时，最终只有一条用户级有效授权，列表只能展示一个资源行，不能出现重复 AI 账户或重复分组。
- AI 账户授权会创建被授权人的授权实例 `account_id`；来源账户 `account_id` 仍代表真实上游资源事实和来源可用性，授权实例 `account_id` 代表被授权侧状态、绑定、授权额度和用量口径。账号硬并发、当前并发槽、图像 / 文本 lane 并发和高并发分组容量判断统一按真实来源资源账号 ID 维护；授权实例命中上游时占用来源账号并发槽，避免来源账号页面长期为 `0` 或多个授权实例绕过同一来源账号硬并发上限。个人来源、团队来源或重新激活都复用同一最终用户授权和同一授权实例，不为同一被授权用户反复复制实例。授权实例实际可用性由 `effectiveAvailability` 统一表达，来源不可用时不改写实例本地状态但会阻断调度。
- 被授权用户不能修改资源名称、凭据、代理、并发上限、来源账户优先级、来源账户调度开关、账户追加流式规则和备注，不能删除授权方原资源，也不能继续转授权；账户编辑弹窗只允许调整自己的加入分组和分组内优先级，除敏感凭据外的来源资源配置只读展示。被授权用户不想继续使用个人直授权账户时，只能归还对应个人授权并隐藏自己的实例账户，不删除来源账户；团队来源授权账户不提供个人归还入口。
- 被授权用户不能查看完整敏感凭据，只能看到列表需要的基础摘要、状态、可用性、来源账号并发上限、来源资源当前并发和必要来源标识；当前并发只表示真实来源资源的瞬时 in-flight 占用，不包含请求内容、调用方或凭据信息。
- 个人 AI 账户授权生效时必须加入被授权用户自己的同供应商分组；新增授权表单默认选择目标用户在该供应商下的默认分组并提交 `targetGroupId`，后续只能在授权账户编辑弹窗里调整到被授权用户自己的其他同供应商分组参与调度；分组授权生效时，授权分组也可以直接作为被授权用户 API Key 的调度池。
- 分组授权共享的是分组所有者自有账户集合；如果分组里包含其他用户授权来的账户，不能通过分组授权继续共享给第三方。

当前字段：

- `id`
- `resource_type`：`account`、`group`
- `resource_id`
- `resource_owner_system_account_id`
- `grantee_system_account_id`：最终被授权使用的系统账户
- `source_type`：`manual`、`team`
- `source_team_id`：团队来源 ID，手动个人授权为空
- `scope`：当前固定为 `use`
- `expires_at`：可选自动回收时间，命中后授权状态自动变为 `expired`
- `limits_json`：美元成本额度限制 JSON，内部 `limit` 表示美元金额，支持 n 小时额度、日额度、周额度、月额度和总额度；为空表示不限制。
- `status`：`active`、`paused`、`expired`、`revoked`
- `remark`
- `created_by`
- `created_at`
- `revoked_by`
- `revoked_at`
- `updated_at`

约束与生命周期：

- 同一个 `resource_type + resource_id + grantee_system_account_id` 同一时间只能有一条有效授权。
- 不允许授权给资源所有者自己。
- 授权给团队时，如果资源所有者也在该团队内，资源所有者自己的调用仍按自用处理，不计入授权消耗。
- 不允许授权给已停用或不存在的系统账户、团队、账户或分组。
- 回收和归还授权都采用状态变更，不物理删除，历史请求和统计继续保留。
- 到期采用状态变更，不物理删除；独立 background worker 进程负责把过期授权改成 `expired`。
- 分组等非实例化资源删除时按对应资源生命周期处理授权关系；AI 账户删除采用两阶段。用户点击删除时只逻辑删除真实来源账户行并立即隐藏，不同步删除历史请求、审计、模型检测、质量快照、额度快照或统计缓存。删除来源账户时同步逻辑删除该来源下所有授权实例，并把对应授权操作记录和运行时授权标记为 `revoked`，避免授权页继续显示为“生效中”；授权实例账户不允许通过账户删除接口删除，被授权用户不想继续使用个人直授权时通过归还入口把授权状态标记为 `returned`。一个月后的后台物理清理任务再删除账户、分组绑定、授权、历史记录和统计缓存。历史 `usage_records` 在逻辑删除阶段保留原始统一授权 ID、调用方和资源所有者字段用于追溯。
- 授权回收或归还后，已有授权账户的本地分组绑定和路由策略中的授权分组绑定都可以保留为失效状态，调度时必须重新校验有效授权。

列表与权限返回：

- `GET /__aisys__/api/accounts` 返回自有账户和授权账户的合集，并按 `accountId` 对当前用户去重；返回 `authorizationSources` 和用户级 `authorizationId`，但不能返回多条相同 AI 账户。
- `GET /__aisys__/api/groups` 返回自有分组和授权分组的合集，并按 `groupId` 对当前用户去重；返回 `authorizationSources` 和用户级 `authorizationId`，但不能返回多条相同分组。有效授权分组可作为路由策略的可绑定分组，失效授权分组只保留可见性、授权关系和历史统计说明。
- 每行返回 `access_type`：`owner`、`authorized` 或 `admin_view`；当同一资源同时拥有个人来源和团队来源时，仍只返回一行授权资源，来源摘要展示全部来源。
- 授权资源额外返回 `authorizationId`、`authorizationSources`、`granteeSystemAccountId`、`ownerSystemAccountId`、`ownerDisplayName`、`authorizationStatus`。
- 每行返回 `permissions` 摘要，例如 `can_use`、`can_edit`、`can_delete`、`can_authorize`、`can_view_credentials`、`can_manage_members`、`can_bind_to_api_key`。
- 前端据 `permissions` 隐藏操作；后端仍必须在每个写接口重新校验。

授权管理页：

- `统一授权` 列表展示资源类型、资源名称、资源所有者、被授权的目标、当前生效来源、状态、授权时间、说明和操作；被授权的目标按来源直接展示团队名称或用户名称，来源标签保持个人 / 团队语义；不展示今日用量、范围用量、最后使用或额度摘要。
- 用户侧 `授权操作` 列表同样不展示今日用量、范围用量、最后使用或额度摘要，也不提供用量时间筛选；`授权给我` 只提供查看来源、关系和归还使用权，不提供暂停、回收或修改配置。
- 新增授权时，用户侧默认以当前登录用户作为授权人；管理侧必须先指定授权人 / 资源归属用户，再从该用户自己的 AI 账户或分组中选择授权内容，不能在“全部系统账户”范围下创建授权。
- 授权用量的主维度是“资源 × 用户”：A 授权给 B 时，A 能在用户消耗明细看到 B 在所选范围内在该资源上的消耗，不再按个人来源或团队来源拆成多份。
- 被授权人通过授权账户或授权分组产生的使用记录、我的用量、AI 性能、模型检测、账户测试和本地操作日志都归属被授权人的系统账户；资源归属人不能通过普通账户列表、普通分组统计、普通使用记录或我的操作日志把这些数据当成自己的数据管理，只能在授权消耗报表里按授权关系查看聚合消耗。
- `团队消耗明细` 按授权团队和资源名称展示所选日期范围内团队消耗，行操作可跳转 `用户消耗明细` 并带上团队筛选和日期范围。
- `用户消耗明细` 按最终被授权用户和资源名称展示所选日期范围内消耗，包含授权团队里的成员用户，可按日期范围、团队、用户、授权内容和授权资源筛选；管理侧可直接看到资源名称和资源归属人。
- 如果 B 先有个人授权，后又因团队获得同一资源授权，B 的范围消耗合并到同一条“B 在该资源上的用量”里；团队筛选也能按成员看到 B 的范围用量。
- 授权统计由独立 background worker 进程写入统计缓存，授权消耗明细只读缓存，不在页面请求时实时聚合原始 `usage_records`，也不允许前端拉取授权列表后自行汇总大量行。
- `团队消耗明细` / `用户消耗明细` 由后端接口按当前资源归属作用域和筛选条件直读授权范围窗口表并返回汇总结果；`GET /__aisys__/api/authorizations` / `GET /__aisys__/api/my-authorizations` 只服务关系列表，不作为消耗报表的数据源。
- 授权消耗统计不包含资源归属人自己的自用消耗；资源归属人的账户 / 分组用量情况仍展示全部总消耗。
- 新增授权和修改授权配置时可以设置美元成本额度；日额度每日 0 点重置，周额度每周一 0 点重置，月额度每月 1 号 0 点重置，总额度按累计 `total_cost_usd` 判断，n 小时额度按小时缓存窗口的 `total_cost_usd` 相加判断，例如 5 小时额度 $10 表示最近约 5 小时美元成本合计达到 10 后拦截。
- 授权额度判断读取后台统计缓存和短 TTL 网关内存缓存，不在请求内扫描 `usage_records` 或做强一致扣减；允许轻微超额，统计追平后下一次请求返回 `429` 和“额度已用完，请联系管理员提升额度”。
- 资源所有者只能查看授权聚合用量，不能查看被授权用户请求快照、响应快照、客户端 IP、API Key 明文或业务请求内容。

当前接口：

- `GET /__aisys__/api/authorizations`：查看授权关系列表；消耗统计不从该接口返回。
- `GET /__aisys__/api/authorizations/:id` / `GET /__aisys__/api/my-authorizations/:id`：查看授权关系详情；`:id` 为 `resource_authorization_grants.id` 授权业务记录 ID，返回授权关系、来源、额度和权限摘要；不作为授权消耗明细数据源。
- `POST /__aisys__/api/authorizations`：新增授权，仅资源所有者或管理员可用。个人 AI 账户授权必须提交 `targetGroupId`，用于授权成功后直接绑定到目标用户自己的同供应商分组；前端默认选中目标用户在该供应商下的默认分组，不允许清空后提交。
- `DELETE /__aisys__/api/authorizations/:id` / `DELETE /__aisys__/api/my-authorizations/:id`：回收授权，仅资源所有者或管理员可用；`:id` 为 `resource_authorization_grants.id` 授权业务记录 ID，语义是改为 `revoked`。
- `DELETE /__aisys__/api/my-authorizations/:id/return`：被授权人归还授权使用权；授权记录保留并进入 `returned` 状态。
- `GET /__aisys__/api/authorizations/:id/usage`：查看某条授权在指定日期范围内的聚合用量。
- `GET /__aisys__/api/authorizations/usage/team-details`：管理侧团队消耗明细，从授权范围窗口表分页读取团队行。
- `GET /__aisys__/api/authorizations/usage/user-details`：管理侧用户消耗明细，从授权范围窗口表分页读取用户行。
- `GET /__aisys__/api/my-authorizations/usage/team-details`：用户侧团队消耗明细，忽略 `systemAccountId`，只分页返回当前登录用户授权出去资源的团队范围窗口行。
- `GET /__aisys__/api/my-authorizations/usage/user-details`：用户侧用户消耗明细，忽略 `systemAccountId`，只分页返回当前登录用户授权出去资源的用户范围窗口行。
- `GET /__aisys__/api/system-accounts`：管理侧系统账户分页列表，只允许管理员访问，支持 `keyword` 用户名 / 显示名精确或前缀搜索、`page` 和 `pageSize=1..100`；响应为 `{ items, total, hasMore, page, pageSize }`，`total` 只作为当前窗口上界，不做全表精确 `COUNT(*)`；列表字段不包含 `password_hash`。Go W2 已覆盖该只读列表端点；Go W3 opt-in 已覆盖登录 / session 创建、自助改密、当前会话登出、系统账户创建和完整 mixed PATCH，但完整会话管理、前端 smoke、生产切流和 Node 删除仍未完成。
- `GET /__aisys__/api/system-accounts/options`：管理侧筛选和成员选择使用的系统账户最小摘要，只返回 `id`、`username`、`displayName`、`status`，支持 `ids` 回填、`keyword` 用户名 / 显示名精确或前缀搜索和 `limit=1..50`；不得读取 `password_hash`、角色、改密状态、最后登录、创建 / 更新时间等系统账户管理字段，不能复用系统账户管理列表查询。
- `GET /__aisys__/api/authorization-options/grantee-accounts`：管理侧获取可授权用户摘要；返回全部系统账户最小摘要，支持 `ids` / `keyword` / `limit`，不能返回角色、改密状态、最后登录等管理字段。Go W2 已覆盖该只读端点，普通用户只能走 `my-authorization-options/grantee-accounts`。
- `GET /__aisys__/api/authorization-options/grantee-teams`：管理侧获取可授权团队摘要；返回全部系统团队最小摘要，支持 `ids` / `keyword` / `limit`，不能返回团队成员明细。Go W2 已覆盖该只读端点，普通用户只能走 `my-authorization-options/grantee-teams`。
- `GET /__aisys__/api/my-authorization-options/grantee-accounts`：用户侧新增授权使用的全系统授权用户最小摘要，支持 `ids` / `keyword` / `limit`。Go W2 已覆盖该只读端点。
- `GET /__aisys__/api/my-authorization-options/grantee-teams`：用户侧新增授权使用的全系统授权团队最小摘要，支持 `ids` / `keyword` / `limit`。Go W2 已覆盖该只读端点。
- `GET /__aisys__/api/authorization-options/grantee-groups`、`GET /__aisys__/api/my-authorization-options/grantee-groups`：新增个人 AI 账户授权时用于选择目标用户同供应商启用分组，必须传 `granteeSystemAccountId`，支持 `ids`、`providerCode`、`keyword`、`preferDefault` 和 `limit=1..50`；只返回目标 active 用户自己的启用分组最小摘要，不返回分组成员、用量、并发、授权来源或 grant。Go W2 已覆盖该只读端点。
- `GET /__aisys__/api/my-teams`：普通用户分页查看自己加入的团队和团队成员，支持 `page`、`pageSize` 和 `keyword`；新增授权里的团队候选使用授权选项接口，不复用我的团队列表。

## 分组

分组是调度和路由策略号池边界。每个系统账户维护自己的同供应商本地分组，路由策略可以绑定调用方自己的分组，也可以绑定有效授权给调用方的分组；API Key 只选择一条路由策略。AI 账户通过 `group_accounts` 加入某个使用方的本地分组，授权账户加入分组时记录稳定的最终用户授权 ID。分组使用权通过统一授权管理授权给系统账户或系统团队，授权分组在有效期内与本地分组一样可作为路由策略号池。

分组模型必须区分三层关系：资源归属由 `accounts.system_account_id` 和 `groups.system_account_id` 决定；本地调度绑定由 `group_accounts.system_account_id + group_id + account_id` 决定；授权使用权由 `resource_authorizations.id` 决定。授权账户绑定到被授权用户分组时，`account_id` 指向被授权用户自己的授权实例账户，只新增或更新被授权用户作用域内的本地绑定，不改变授权方原账户的资源归属或所有者分组。

当前字段：

- `id`
- `system_account_id`
- `name`
- `provider_code`：分组所属供应商，例如 `openai`、`gpt`、`anthropic`、`gemini`、`deepseek` 或 `glm`
- `description`
- `enabled`
- `is_default`：是否为系统账户在该供应商下的默认分组；默认分组不允许修改或删除
- `group_type`：分组类型，取 `personal` 或 `high_concurrency`；默认分组使用 `personal`
- `scheduling_policy_json`：高并发分组调度策略配置；个人分组为空或按默认个人策略处理。当前可配置最大单账户排队阈值、最大等待时间、单 IP 并发限制和单 IP 超限模式；完整策略见 [高并发分组调度设计](高并发分组调度设计.md)
- `account_count`
- `created_at` / `updated_at`

关系表：

- `group_accounts.system_account_id`：本地绑定所属的使用方系统账户，不一定等于账户资源归属人。
- `group_accounts.group_id`
- `group_accounts.account_id`
- `group_accounts.account_authorization_id`：授权账户加入本地分组时记录的最终用户授权主记录；自有账户为空。
- `group_accounts.local_priority` / `local_super_priority_enabled` / `local_fallback_enabled`：当前使用方当前分组绑定的调度事实；授权账户的分组内排序、超级优先和降级备用读取这里，不读取来源账户，也不写授权实例全局账号字段。
- 授权实例持久状态以授权实例 `accounts` 行为准；冷却、最近错误和流失败诊断窗口不落在 `group_accounts` 本地绑定字段上。网关调度降级、事前确认和用户显式响应策略避让是易失运行态，standalone 保存在当前 Web 进程，performance 保存在 Redis state。
- `group_accounts.enabled`

功能要求：

- 系统账户创建时后端按当前启用的供应商自动创建默认分组，例如 OpenAI 兼容、GPT、Anthropic、Gemini、DeepSeek、GLM 和混合供应商。默认分组事实只认 `is_default = 1` 和对应 `provider_code`，名称只是当前种子展示名，不作为旧数据兜底判断。名称已能表达默认含义，页面不再额外展示默认标签，默认分组说明保持为空。默认普通路由和默认 API Key 只为非 hybrid 默认分组创建；hybrid 只创建默认分组，不创建默认普通路由或默认 API Key。
- 高并发分组将分组类型分为个人分组和高并发分组。个人分组保持当前轻量调度语义；高并发分组面向同一个 API Key 大量并发调用，启用软并发轮转、快速优先、慢请求分流、分组级短等待和可选单 IP 并发保护。完整设计见 [高并发分组调度设计](高并发分组调度设计.md)。
- 一个自有账户在所有者作用域内必须绑定到一个同供应商分组；创建时按供应商默认选中默认分组，编辑时可调整。被授权账户生效时必须绑定到授权创建时提交的目标用户同供应商分组，前端默认目标用户在该供应商下的默认分组；后续只能在被授权用户作用域内通过授权账户编辑弹窗调整分组和分组内优先级。绑定后统一按目标分组调度配置执行，同一 `account_id` 在同一 `system_account_id` 作用域内只保留一个有效分组绑定。
- 每个系统账户默认拥有每个启用供应商对应的默认分组；缺失默认分组属于数据异常，通过重建库或离线清洗脚本处理，不在源码保留旧数据补丁分支。
- 一个分组可以汇总多个同供应商账户；自有账户绑定自有 `accounts.id`，授权账户绑定被授权人自己的授权实例 `accounts.id`。授权来源变化不能让同一授权实例在同一使用方分组内重复出现。
- 一个分组只汇总同一 `provider_code` 下的账户，列表只展示数量与聚合状态，不展开账户名称。
- 一个 API Key 选择一条路由策略；路由策略可以绑定创建者 / 被管理用户自己的分组，也可以绑定有效授权给该用户的分组；绑定分组可以来自不同供应商。跨供应商混合由请求 `model` 先定位目标供应商，再只在该策略绑定的目标供应商分组内路由。授权账户仍需要先进入该用户自己的分组后参与自有分组调度；授权分组则直接使用授权方分组内可共享账户。个人分组和高并发分组可以混合绑定，选中后按各自分组类型调度。多分组路由、优先级、混合分组和故障切换规则见 [策略路由设计](策略路由设计.md)。
- 个人分组调度顺序以账号或绑定级 `fallback_enabled`、`super_priority_enabled`、`priority` 和账号质量缓存为主；授权实例的分组内排序、超级优先和降级备用读取当前 `group_accounts` 绑定。
- 高并发分组仍优先尊重账号配置，单账户排队阈值只来自目标分组配置并受账号硬并发上限约束。调度不默认依赖上游状态码判断账号健康，而以本地可观测的当前并发、分组排队、请求耗时、首段等待、近期超时和质量缓存作为新请求分流依据；慢请求分流默认只影响新请求排序，不直接写账号异常状态。
- 高并发分组实现必须把热路径性能作为硬边界：每次选号不得新增额外数据库往返，不得扫描使用记录或审计明细，不得引入跨分组全局排序；只能复用网关运行时快照和进程内轻量运行态做有界计算。
## API Key 管理

API Key 是对外访问入口，不直接绑定账户或分组，而是选择一条路由策略。路由策略负责绑定一个或多个调用方可用分组号池，包含自有分组和有效授权分组。当前网关先用请求 `model` 在当前路由策略可达的供应商集合内尝试唯一定位目标供应商，再在该供应商下的策略分组中选择可承接分组；账户侧协议档案、endpoint mode 和模型映射继续约束候选账户。无法明确定位时返回本地错误，不继续按默认分组路由候选顺序调度。

API Key 创建和编辑表单只通过策略路由 options 读取下拉摘要：管理侧使用 `/__aisys__/api/route-strategies/options`，用户侧使用 `/__aisys__/api/my-route-strategies/options`。这些接口只返回策略摘要和必要 owner 摘要，不返回完整策略配置、绑定分组或账号信息；编辑已有 API Key 时可通过 `ids` 追加当前已选策略，避免 inactive 或超出首屏 limit 的策略丢失。

当前字段：

- `id`
- `system_account_id`
- `name`
- `description`
- `key_hash`
- `key_prefix`
- `key_secret_encrypted`
- `status`
- `route_strategy_id`：API Key 绑定的策略路由 ID，是进入分组调度的唯一入口。
- `routeStrategyName` / `routeStrategyMode` / `routeStrategyStatus`：接口返回的策略路由摘要；分组绑定、权重、轮询、回退和混合智能配置只在策略路由接口中维护。
- `expires_at`
- `quota_limits_json`：美元成本额度限制 JSON，支持 n 小时、日、周、月和总额度。
- `availability_schedule_json`：API Key 时间计划 JSON；为空表示不设置计划。API Key 只有一个可用状态 `status`；创建或编辑计划时按当前时间初始化 `status`，之后由 background worker 在开始 / 结束边界继续写 `status`。人工启用 / 停用也只改 `status`。
- `last_used_at`
- `created_at` / `updated_at`

功能要求：

- 本地 API Key 密文存储，`key_secret_encrypted` 是当前必需字段；列表和更新响应只返回 `keyPrefix`、`keySuffix` 与空 `key`，避免后台页面批量暴露明文密钥。完整密钥在创建成功响应中返回，也可通过单条 `/:id/secret` 接口按资源权限读取。若数据缺字段或密文不可解，应离线修复或重建 API Key，不在前端或接口做历史降级展示。
- 创建成功弹窗展示完整密钥和 Base URL，方便立即接入客户端；列表仍只展示前8位和后8位识别 Key，复制按钮按单条记录读取并复制完整密钥。
- API Key 列表搜索框只按名称做精确 / 前缀匹配；Key 前缀、后缀和说明不进入通用搜索，也不维护多字段组合搜索索引；路由策略和状态使用独立筛选。需要按分组查找时，通过路由策略分组绑定命中对应 Key。
- API Key 和 AI 账户都可选配置时间计划。计划和人工操作共用同一个可用控制状态：API Key 写 `api_keys.status`，AI 账户写 `accounts.status`。窗口开始时写 `active`，窗口结束时按当前是否仍有其他允许窗口决定是否写 `disabled`。创建和编辑计划时按当前时间初始化 `active/disabled`；两个边界之间如果用户手动启用或停用，系统不持续纠偏，直到下一次计划边界再接管。AI 账户时间计划只自动切换 `active <-> disabled`，不能把 `pending_test`、`error`、`rate_limited`、`temporary_unavailable` 自动恢复为正常。网关只按落库后的状态、未过期、额度未耗尽和分组路由可用判断可调用性，不在请求热链路解析计划 JSON。
- 时间计划以分钟为粒度，按计划内 `timezone` 解释本地日期、星期和时间；默认使用系统统计时区。`windows` 支持多个允许时段，每个时段包含 `daysOfWeek`、`start` 和 `end`，星期取值为 `1` 到 `7`（周一到周日），`start/end` 使用 `HH:mm`。`start > end` 表示跨天时段，例如 `22:00-02:00`；`start = end` 非法。`dateRange` 约束窗口的开始日期，允许结束日期当天启动的跨天窗口延续到次日凌晨，但不允许开始日期前一晚的尾段在范围开始日凌晨误放行。`exceptions` 按例外日期替换当天启动的普通窗口，`deny` 表示该日期不启动任何窗口，`allow` 表示只按例外窗口启动；例外窗口同样支持跨天。多个窗口重叠时，只要当前仍命中任一允许窗口，边界同步就不能把统一状态错误关闭。
- API Key 选择的路由策略可以绑定调用方自己的一个或多个分组，也可以绑定有效授权给调用方的分组，策略绑定分组可以来自不同供应商；写入不再用同档案限制承接跨供应商边界，而是由运行时按请求 `model` 筛选目标供应商分组并按账户能力过滤。被授权账户通过 `group_accounts` 进入调用方自己的分组后参与自有分组调度，授权分组则直接按有效分组授权进入调度。
- 当前请求进入后先按请求 `model` 在当前路由策略可达供应商集合内定位目标供应商，再按主备、轮询或权重策略选择号池并依据账户协议档案、endpoint mode、模型和账号类型能力过滤。进入真实上游派发后，transport / timeout 失败可在语义提交前按账号和后续号池救回；通用客户端收到完整上游响应后立即透明转发，不按状态或正文切号。精确客户端语义失败只在该画像声明的边界内处理。独立后台探针真实失败后才建立 `precheck_pending` 软阻断，不能由普通请求直接屏蔽账户。
- 路由策略至少保留一个 active 分组绑定。停用、移除最后一个 active 号池或删除最后 active 号池对应分组时，后端必须拒绝并提示先调整路由策略绑定。
- API Key 生命周期分为停用、业务删除和记录物理清理。停用只改变状态并立即拒绝后续调用；业务删除同步移除业务库记录并让后续请求立即无法再使用该 Key；关联使用记录进入 usage shard 清理目标，原始审计日志、审计尝试、payload 引用和审计错误组进入数据集目录库清理目标，API Key 维度统计缓存、额度窗口、授权 / 账户 / 分组等聚合由统计结果库反向扣减。清理可能滞后于业务删除，普通请求路径不等待 usage shard、数据集目录库或统计结果库清理完成。
- AI 账户生命周期分为逻辑删除和过期物理清理。逻辑删除写入 `accounts.deleted_at / deleted_by`，同时置为停用且不可调度；所有列表、选项、授权使用、网关调度、账户测试、OAuth 后台刷新和冷却复测路径都排除逻辑删除账户。逻辑删除阶段保留历史记录和统计结果，避免删除动作阻塞请求或破坏近 31 天统计窗口；独立 background worker 每天扫描 `deleted_at` 已超过 1 个月的账户，先等统计安全游标覆盖并分批清理使用记录、审计、模型检测和统计缓存，再物理删除账户、绑定、支持模型、授权来源、授权主记录和授权 grant。

## 代理管理

代理独立于账户，账户只引用代理配置。代理是服务器级全局资源，不属于某个系统账户。

权限规则：

- 代理管理列表、创建、编辑、删除和手动检测只面向管理员开放。
- 代理管理列表使用后端分页和远程关键词搜索，关键词只按代理名称做精确 / 前缀匹配；代理 ID、地址、类型、用户名和说明不进入通用搜索，底层也不维护这些字段的组合搜索索引。前端不能为搜索一次性拉取完整代理列表。
- 删除代理前只读取最多 4 个绑定账户作为固定窗口预检，前 3 个账户名用于提示；读到第 4 个时错误文案按“至少 4 个账户”表达，不能为了显示精确数量对绑定账户做 `COUNT(*)`。
- 代理密码使用 `JUHE_AI_SECRET` 派生的 AES-256-GCM `v1` 密文存入 `password_encrypted`；列表、创建 / 更新响应和操作日志均不得返回明文。修改连接类型、主机、端口、用户名或密码时必须重置最近检测缓存，避免继续展示旧连接的检测结论。
- 创建、更新和删除成功后发布 gateway runtime cache 失效；代理写接口启用前必须配置不少于 32 字符的稳定 `JUHE_AI_SECRET`，不能回退到仅适用于本地测试的默认密钥。
- 普通用户不显示代理管理菜单，但可以在自有 AI 账户创建、编辑和 OpenAI OAuth 流程中读取全局已启用代理选择项。
- 普通用户读取全部已启用代理选项是当前产品口径，不按代理归属或系统账户做隔离，也不作为安全缺陷处理；接口支持远程关键词搜索，不返回 Host、端口、用户名、出口 IP、检测摘要等运维字段。

当前字段：

- `id`
- `name`
- `type`：`http`、`https`、`socks5`、`socks5h`
- `host`
- `port`
- `username`
- `password_encrypted`
- `enabled`
- `test_status`
- `latency_ms`
- `outbound_ip`
- `outbound_region`
- `last_test_message`
- `last_tested_at`
- `created_at` / `updated_at`

代理质量检测以全部已启用供应商默认地址为测试目标；后台刷新固定每 60 秒最多检测 20 个启用代理，不提供系统设置项调整。手动检测额外缓存出口 IP 和出口地区。最近检测状态、延迟、出口信息和摘要只作为运维参考缓存，不替代实际请求时的失败处理。同一次网关调度中，如果某个账号绑定的代理已经因配置不可用或请求链路异常失败，后续绑定同一个代理的账号直接跳过，不重复请求，也不把这些未实际尝试的账号逐个写入临时不可调用。

## 使用记录

使用记录用于排查、统计和后续计费。网关每次实际发起上游请求都写入一条记录，重试失败、切换账号失败和最终成功都会分别保留。

使用记录和原始审计日志必须分开：使用记录关注 token、成本、耗时、状态码、授权归属和统计聚合；原始审计日志关注完整请求过程和原始内容。使用记录失败快照按当前日志口径保留原文并受容量上限约束，不替代原始审计的完整链路保全。

当前字段：

- `id`
- `system_account_id`：实际调用方系统账户，决定普通用户使用记录隔离
- `account_owner_system_account_id`：命中账户所有者，自有账户时等于 `system_account_id`
- `group_owner_system_account_id`：命中分组所有者，自有分组时等于 `system_account_id`
- `account_access_type`：`owner`、`authorized`
- `group_access_type`：`owner`、`authorized`；API Key 所选路由策略可绑定调用方自有分组或有效授权分组，授权分组访问必须走当前显式授权校验路径。
- `account_authorization_id`：命中授权 AI 账户时记录用户级统一授权 ID，自有账户为空
- `authorization_instance_source_account_id`、`authorization_instance_authorization_id`、`authorization_instance_owner_system_account_id`：授权实例账户的来源账户、用户级授权和原资源归属人快照。
- `accounts.status`、`schedulable`、`cooldown_until`、`last_error_*`、`stream_failure_*`：授权实例账户自己的运行态，只影响该授权实例本身。
- `group_accounts.local_priority`、`local_super_priority_enabled`、`local_fallback_enabled`：授权实例在某个使用方分组内的调度态，只影响这一条分组绑定。

- `authorization_source_summary`：可选快照，记录当时用户授权来自个人、团队或两者合并

- `api_key_id`
- `group_id`

- `endpoint`

- `cost_breakdown_snapshot_json`：请求写入时锁定最终单价、成本小计、档位专用价 / 倍率来源和实际倍率

统计口径：

- 当前网关已写入请求记录，并按命中的 `provider_protocol_profile_id` 使用对应 usage parser 解析 OpenAI、Anthropic 或 Gemini native 用量。
- OpenAI SSE 响应读取 `response.completed` / `response.done` / `response.failed` 事件里的 `response.usage`；Anthropic / Gemini 入口按各自响应语义归一到统一 usage 字段。
- 使用记录保存 `METHOD /v1/path` 形式的接口，便于区分 `/v1/models` 这类成功但没有模型和 token 用量的请求。
- 成本统计复用供应商模型目录里的价格快照；未覆盖的模型先只记录 token。
- 使用记录落库时保存总成本、缓存读写、thinking、图像 / 音频 token、服务档位、请求 / 实际思考级别和不可变计价快照。使用记录列表的模型列展示实际计费档位与有效思考级别，延迟列合并首 token 和总耗时；成本明细只展示计价模型、非 Default 实际档位、计价来源、最终单价、小计和合计。
- 管理员视角可按 `system_account_id` 查看全部记录并显示归属列，用户视角只看自己的记录且不显示归属列。
- 使用记录明细支持按自然日时间范围、分组、结果和状态码筛选；前端提交 `startDate` / `endDate`，后端按系统用量时区转换为 `created_at` 半开区间分页查询，不在列表接口做统计聚合。管理 / 用户 API 未传日期范围时默认限制为今天，避免页面初次打开扫所有 usage shard；管理侧必须先指定系统账户，未指定时不返回 raw 明细。
- 使用记录列表的第一页、`created_at DESC`、每页不超过 50 条请求允许缓存最终响应：2 秒内直接命中，2 到 15 秒返回旧结果并单飞后台刷新，超过窗口或缓存不可用时回源 repository。缓存键必须按用户 / 管理员指定用户的访问作用域、视图类型、日期与全部筛选条件做 SHA-256 隔离；管理员未指定系统账户、深分页和非默认排序不进入缓存。Redis 模式使用短租约协调多 API 进程的同键回源；使用记录成功写入后仅推进缓存命名空间版本，不扫描缓存键，保证下一次读取不继续命中旧响应。缓存只优化明细读取，允许短时展示误差，不替代使用记录事实，也不改变落库、统计和额度口径。
- 使用记录的 AI 账户名称筛选必须先在业务库按精确 / 前缀匹配解析当前调用方可见的实际 `account_id`，再用 `usage_records.account_id IN (...)` 查询分片；不能在 `usage_records` 上做名称模糊扫描，也不能用账号 ID 前缀当作账户名搜索。解析范围包含调用方自有账户、授权实例账户名称、授权实例的来源账户名称，以及分组授权中来源分组内账户名称；返回结果仍只按 `usage_records.system_account_id` 展示调用方自己的明细。
- 授权账户和授权分组调用都按调用方写入明细；管理侧授权消耗只在团队消耗明细和用户消耗明细展示聚合，不包含资源归属人自用消耗，也不向资源所有者展示被授权用户请求快照、响应快照、客户端 IP 或业务内容。
- 失败记录额外保存请求/响应快照，便于在使用记录页查看当时的请求体、响应体和最后一次上游错误。

## 原始审计日志

原始审计日志用于在客户端版本升级、请求头变化、上游校验规则变化或网关兼容问题出现时，还原一次请求从进入网关到最终返回的完整过程。具体字段、队列、采样、SSE 和安全边界见 [原始审计日志设计](原始审计日志设计.md)。

核心规则：

- 管理菜单名称为 `审计日志`，当前仅 `super_admin` / `admin` 可见和查询。
- 完整成功请求默认先按最近 1 小时热窗口全量保存，超过热窗口后只保留 `10%` 稳定采样；非成功请求、客户端中断、流式中断、任一上游尝试失败后最终成功的请求，都必须全量保存。
- 审计内容保存完整原文，包括客户端请求头、请求体、上游请求头、上游请求体、上游响应头、响应体和最终返回客户端内容，不做脱敏、截断或字段移除。
- 原始 payload 按审计保全策略压缩、去重和保存；保全不等于脱敏，管理员按权限查看时应能还原可保留原文。
- 网关请求链路禁止同步写审计表；请求处理中只维护内存捕获上下文。
- 只有请求结束、失败或客户端中断后，才能计算终态并按采样规则把完整审计对象放入内存队列。
- 审计队列由 `ingest-worker` 定时或按批量阈值写入 SQLite；队列写库失败、系统重启或进程崩溃导致审计数据丢失是可接受边界。
- SSE 和其他流式响应不能按 chunk 实时写库，也不能在流未结束时入队；必须等自然结束、失败、超时或客户端断开后，以终态记录入队。
- 审计队列满或单请求捕获超过上限时，不能阻塞网关响应；允许丢弃审计记录并增加队列丢弃计数，供运维页面查看风险。

## 统计缓存与运维监控

统计层的目标是把“高频读、低频写”的指标提前聚合好，避免列表页和图表页每次都回扫 `usage_records`。`usage_records` 继续作为事实源，先由 `ingest-worker` 批量落入 usage shard，再由 `stats-worker` 按 `system_account_id` 分区和游标增量汇总到缓存表，并刷新 TopN、概览、范围和授权窗口；列表、用户统计概览和管理员统计概览只读缓存。

后台执行边界：

- Web/API/网关主进程不能注册统计聚合、系统采样、授权到期扫描、冷却账号复测、运行日志索引维护或审计清理定时任务。OAuth 额度快照不再有主动刷新定时任务。
- 调度框架只允许运行在独立 background worker 进程内；不能让 worker 只负责触发，再通过 IPC 回到主进程执行任务函数。
- 主进程只允许把请求链路产生的轻量事件或待写数据投递给 worker；批量聚合、批量写库、清理和外部探测都在对应 worker 内完成，其中使用记录、审计、操作日志、公开接口日志、运行日志索引和记录维护固定投递 `ingest-worker`，统计和窗口刷新固定在 `stats-worker`，账号测试、探测和轻运维任务固定投递 `ops-worker`。
- Worker 任务必须支持不可重入、错误隔离和失败后下轮重试；单个任务失败不能影响 Web 请求主链路。
- `usage-stats-aggregation` 每个 batch 只访问有界数量的 active usage shard，并通过轮转 offset 分摊历史 shard 检查；不能因为历史 shard 数量增长而在 5 秒级高频任务里对全部 shard 做同步 fan-out。

当前缓存分层：

- `usage_stats_totals`：按 `system_account_id + scope_type + scope_id` 存累计值，覆盖 `system_account`、`provider`、`group`、`account`、`caller_account`、`account_authorization`、`group_authorization`、`api_key`、`model`、`endpoint`。
- `usage_stats_daily`：按 `system_account_id + scope_type + scope_id + stat_date` 存天级业务概览，用于账户按日消耗趋势、列表今日口径和授权用量自然日口径。
- `usage_stats_hourly`：按 `system_account_id + scope_type + scope_id + stat_hour` 存小时趋势，用于 worker 刷新统计概览、额度、排行和 AI 性能窗口快照，也用于 `AI性能监控` 账户级首 token 和总耗时趋势；页面摘要和额度不在请求时聚合小时桶。
- `usage_model_daily`：按 `system_account_id + stat_date + model` 聚合请求数、token 和成本，用于自然日模型分布。
- `usage_model_hourly`：按 `system_account_id + stat_hour + model` 聚合小时级模型分布，由 worker 刷新统计概览模型排行窗口。
- `usage_error_daily`：按 `system_account_id + stat_date + error_group + error_code` 聚合错误，用于自然日错误情况。
- `usage_error_hourly`：按 `system_account_id + stat_hour + error_group + error_code` 聚合小时级错误，由 worker 刷新统计概览错误 Top 窗口。
- `group_account_stats`：按 `system_account_id + group_id` 缓存分组账户数量、可用数、状态数量和并发上限，分组列表只读该结果。
- `system_metrics_samples`：主机级运维采样，记录 CPU、内存、RSS、Heap、网络入站/出站吞吐、网卡累计收发、数据库大小和统计滞后；`event_loop_lag_ms` 保存采样进程本地事件循环值，默认仅管理员可见，多进程事件循环和进程内存细分以 `process_event_loop_samples` 为准。
- `system_metrics_hourly`：把主机采样值做小时级平均、最大值和最小值，供监控图长期查看。
- `process_event_loop_samples`、`process_event_loop_hourly`、`process_event_loop_trend_windows`：单独保存 `server`、`ingest-worker`、`stats-worker`、`ops-worker` 和 `db-service` 的事件循环延迟、RSS、Heap used / total、external 和 array buffers 采样、小时汇总和概览窗口趋势；管理侧事件循环趋势和进程内存占用趋势跟随统计页日期范围读取窗口缓存，用于看出卡顿尖峰和单进程内存爬升。
- 以上系统指标表述只描述当前 Node 过渡事实。Go 接管系统监控后，不能继续扩展或模拟 `event_loop_lag_ms`、`process_event_loop_*`、`processEventLoop*`、`db-service`、SQLite 文件体积或 usage shard 文件路径指标；必须按 [Go 迁移指标与观测规划](../migration/Go迁移指标与观测规划.md) 改为 Go runtime、goroutine、scheduler、GC、heap、RSS、PG pool、Redis、Asynq queue、worker lag、stats freshness 和网关 SLI，并同步更新前端系统监控契约。
- `stats_job_state`：按 `scope_type + scope_id + job_name` 记录任务游标、上次成功时间、上次错误和处理滞后；用户业务汇总使用 `scope_type = system_account`，主机监控使用 `scope_type = global`。
- 审计队列运行态指标：可在运维监控中展示队列长度、队列字节数、最近成功落库时间、最近错误和丢弃计数；这些指标只反映审计健康度，不参与用量统计。
- 后台队列运行状态的时间字段必须携带语义：调度类显示“下次运行”，写入类显示“最近写入成功”；禁止把 `nextRunAt` 与 `flushLastSuccessAt` 合并成无说明的“时间”。

隔离规则：

- 统计概览分为用户侧和管理侧：用户侧只读取当前登录系统账户的业务统计缓存；管理侧只允许 `super_admin` / `admin` 访问，默认查看全局汇总，也可以筛选指定系统账户。主机级系统监控仍属于管理员运维视角，只允许管理侧展示。
- 管理员按系统账户筛选时读取对应 `system_account_id` 的缓存；查看全局汇总时读取后台写入的 `global` 缓存行，不在概览接口里临时聚合多个系统账户缓存行，更不回扫 `usage_records`。
- 统一授权需要同时维护调用方口径、账户行口径和授权消耗口径：调用方统计按 `usage_records.system_account_id` 聚合；调用方在某个命中账户上的用量按 `usage_records.system_account_id + account_id` 写入 `caller_account`；账户行总用量按账户行所属系统账户和 `account_id` 聚合，授权实例账户与归属人原账户互不混入；自有分组总用量只统计分组所有者自己的调用，分组授权调用不写入资源归属人的普通 `group` / `account` 统计；授权管理按资源所有者和统一授权 ID 聚合，并过滤资源归属人自己的自用消耗。统一授权美元成本额度限制读取 `account_authorization` / `group_authorization` 缓存维度，团队授权额度直接读取 `account_authorization_team` / `group_authorization_team` 作用域缓存，不按成员用户授权现算求和。
- 用量统计菜单面向“我自己的调用”读取账户维度缓存：页面使用日期范围筛选，用户侧 `我的用量` 和管理侧 `用量统计管理` 都默认最近 31 天，最大最近 31 天；筛选区下方展示趋势账户列表，普通用户和管理员指定用户时默认从 `usage_rank_snapshots` 读取当前调用方 `caller_account + last7d + request_count` 的最近 7 天活跃前 10 个账户；管理员未指定用户查看全部用户时读取全局调用方账户快照；用户可通过“搜索并添加账户”临时追加更多当前响应内账户；未点选账户时，卡片、趋势图和账户统计明细沿用当前范围视图，点选账户后，卡片按已返回的账户范围窗口值汇总，趋势图和账户统计明细只展示所选账户，再次点击可取消，取消全部选择或重置后恢复全量分页视图；账户统计明细按 `page/pageSize` 分页读取当前范围窗口，支持关键词筛选，账号类型仅展示运行态参考，不作为统计筛选或分片；关键词筛选先解析账户名为当前调用方 `caller_account` 范围窗口中的实际 `account_id`，包含自有账户名、授权实例名、授权实例来源账户当前名和分组授权来源账户名，再读取范围窗口；`total` 仅为分页上界，是否还有更多以 `hasMore` 为准。范围累计值读取 `usage_scope_range_windows`，趋势图读取 `usage_stats_daily` 的逐日点；所有路径都不在页面请求时回扫 `usage_records`，也不把日行再次相加成摘要。授权用量和授权明细不在用量统计菜单提供入口，用户侧从 `我的授权` 查看，管理侧从 `统一授权管理` 下的团队 / 用户消耗明细查看。
- 统计概览是监控窗口，不等同账户、分组、API Key 列表里的今日用量；页面使用日期范围筛选，默认今天，最大最近 31 天。概览摘要、请求 / 失败 / Token / 平均总耗时趋势、模型分布和错误 Top 10 均读取 worker 预写的范围窗口快照，不能从累计总量替代范围数据，也不能在接口中临时聚合。用户侧统计概览展示自己的错误 Top 10；系统性能 / 网络吞吐趋势仍只在管理侧展示，并读取 `system_metrics_trend_windows`；当前 Node 过渡期的进程事件循环趋势和进程内存占用趋势读取 `process_event_loop_trend_windows`，跟随日期范围展示各进程卡顿峰值和 RSS / Heap 曲线，上方摘要取最近 24 小时窗口内各进程最大延迟。当前 Node 固定常驻角色为 `server`、`ingest-worker`、`stats-worker`、`ops-worker` 和 `db-service`；Go 接管后角色收敛为 `server`、`ingest-worker`、`stats-worker` 和 `ops-worker`，系统监控页面改读 Go runtime / queue / storage / stats freshness 窗口。后台任务按数据域注册到对应 worker，不是任务级临时进程；管理侧同时展示每个后台任务的所属 worker、最近耗时、最长耗时、失败和跳过次数。
- `AI性能监控` 是“调用方 × 可使用 AI 账户”的性能窗口，不等同主机级系统监控。用户侧读取当前系统账户自己的 `caller_account` 数据，包含自有账户、授权给自己的账号授权实例，以及授权分组内当前用户可调度的来源账户；授权方原账户的自用数据不会混入被授权人的调用。管理侧提供同名入口，可按系统账户筛选，未筛选时读取全局 `account` 统计缓存和全局排行快照。默认账户列表从 `usage_rank_snapshots` 读取当前调用方 `caller_account + last7d + request_count` 的最近 7 天活跃前 10，快照缺失时默认列表为空，不能在接口请求时临时聚合降级；授权实例账户和归属人原账户分别进入各自账户曲线，授权分组来源账户只展示当前调用方自己的小时数据。用户可通过“搜索并添加账户”把更多可见账户临时加入账户列表，不写数据库、不写系统设置，也不作为持久偏好；搜索关键词只按账户名、授权实例来源账户当前名和授权分组来源账户名做精确 / 前缀解析，显式选中账户只通过 `accountIds` 回填，不按账号 ID 前缀、供应商编码或系统账号名搜索。筛选区下方账户列表可点击控制图表视图：未点选时图表展示当前账户列表全部账户，点选后图表只展示点选账户，再次点击可取消，重置后恢复默认账户列表；页面顶部摘要读取 `ai_performance_summary_windows`，不随前端账户点选重算。页面使用日期范围筛选，默认最近 3 天，最大最近 31 天，图表按小时读取缓存；接口禁止实时回扫 `usage_records`。
- 请求时统计硬边界：列表、概览、授权详情、分组详情和元数据下拉只能读取缓存结果；只有独立 background worker、离线清洗脚本和使用记录分页明细允许直接读取事实表。
- 系统账户停用时，应停止对应后台任务和继续登录 / 调用；系统账户不提供硬删除，统计缓存、OAuth 额度快照和任务状态按历史归属保留或由保留期策略清理。
- 主机级 CPU、内存、数据库大小不属于用户业务数据，默认只在管理员运维视角展示。

常用指标：

- 监控窗口请求数 = `request_count`
- 平均总耗时 = `duration_ms_sum / duration_ms_count`
- 平均首 token 时间 = `first_token_ms_sum / first_token_ms_count`
- 监控窗口 Token 消耗 = `input_tokens + output_tokens`；`cache_read_tokens` 已包含在输入 token 中，只作为拆分指标和缓存折扣计费依据；缓存读取成本读取 `cache_read_cost_usd` 预聚合结果。
- 模型分布 = 按模型维度的请求数、Token 占比和成本占比
- 错误情况 = `error_rate`、`error_count`、`error_group`
- 统计滞后 = 当前时间与 `stats_job_state.last_success_at` 或游标对应记录时间的差值

`AI性能监控` 的完整页面、接口、默认账户池、搜索添加账户、点击筛选和性能边界见 [AI 性能监控设计](AI性能监控设计.md)。

## 错误处理策略

账户错误处理策略保存在账户 `credentials.error_handling_rules`，由 AI 账户编辑弹窗维护。运行时只有精确客户端画像允许解释上游响应语义时才执行；`generic_*` 客户端的完整响应不进入该策略。请求头、请求体和上下文改写仍由网关 adapter 与客户端策略内部处理。页面只开放 GPT 专属且由模型能力校验的 `service_tier_override`、`reasoning_effort_override`，不开放通用任意改写。

匹配规则：

- 匹配条件：`status_codes`、`error_codes`、`error_types`、`keywords`，配置多个字段时必须同时命中。
- 状态码禁止填写 `2xx` 成功状态码；`200 + SSE` 或 `200 + JSON` 协议内失败只在精确客户端画像下由响应检查策略和客户端策略处理。
- 策略字段：`enabled`、`priority`、`name`、`description`、匹配条件、`action` 和限流恢复字段。
- 处理动作只保留四种：`retry_next`（只切号）、`temp_unschedulable`（临时不可调用）、`rate_limited`（限流）、`error_disabled`（异常）。
- 限流恢复：`reset_strategy` 支持 `duration`、`daily`、`weekly`，并保留 `duration_hours`、`daily_reset_hour`、`weekly_reset_day`、`weekly_reset_hour`；每日和每周恢复时间统一跟随服务器系统时间，不提供用户级时区配置。

动作语义：

- `retry_next` 不直接改变持久账号状态，当前请求按排除失败账号和切号流程继续，并首次投递 `recovery_wait`；有效后台探针失败后才按通用失败写 `temporary_unavailable`。
- `temp_unschedulable` 命中后直接写入临时不可调用，并复用系统级快速 / 慢速恢复机制。
- `rate_limited` 命中后直接把账号置为限流中，并按恢复策略自动恢复。
- `error_disabled` 命中后直接把账号置为异常，等待人工执行异常恢复。
- 命中账户错误处理策略或响应拦截策略属于用户显式管理意图，可按配置直接执行，不等待系统自动探针二次确认；未命中策略的普通错误只首次投递 `recovery_wait`。
- 如果后续账号请求成功，本次请求救回，前序失败账号只进入 API Key / IP / 会话局部回避；如果所有候选账号都失败，返回网关统一 `service_unavailable`，不把最后一个上游错误原样返回客户端。
- 凡是决定放行给客户端的上游响应，都必须透传上游状态码、可透传响应头和原始响应体，不改写、不包装为网关自有错误格式；网关自有错误格式只用于鉴权、配额、无可用账号等网关本地生成的失败。

完整运行链路见 [网关错误处理完整链路](网关错误处理完整链路.md) 和 [网关异常重试与兜底策略](网关异常重试与兜底策略.md)。

## 系统设置

平台设置和系统运行设置分层管理。

全局设置：

- `global_settings` 只保存系统名称和系统图标路径。
- 登录页角标、副标题和视觉样式按 [产品与品牌边界](../architecture/frontend/产品与品牌边界.md) 固定。
- 全局设置未登录也需要读取，只允许 `super_admin` / `admin` 修改。

系统运行设置：

- `system_settings` 当前只保存白名单内的网关运行策略、后台管理 API 限流、后台任务、操作日志和数据保留等系统级策略；接口会拒绝白名单之外的字段。原始审计日志不进入系统设置，成功热窗口、成功采样、成功 / 问题保留期和正文上限只允许通过 `JUHE_AI_AUDIT_LOG_*` 部署环境变量配置，其余策略固定在后端。
- 运行设置只允许管理员查看和修改；普通用户不显示系统设置菜单，也不能调用系统设置接口。
- 管理员的用户模式 / 管理模式菜单偏好属于浏览器本地前端习惯，默认第一次进入用户模式；不写入系统运行设置，也不影响后端权限。
- 如果后续需要个人偏好，应另起“我的偏好”接口和字段，避免和系统运行策略混用。
- 流式 `200 + text/event-stream` 内的协议级失败只在精确客户端画像下解释：语义尚未提交时进入服务端内部重试，服务端耗尽后 Codex Responses、Claude Code Messages 和 Gemini CLI stream 分别使用各自协议错误事件。通用客户端原样接收上游 SSE 事件；只有本地 transport 失败耗尽才按 HTTP 错误或断流交给客户端重试。Codex turn 级避让仍只由 Codex 客户端策略决定。
- 上游非 `2xx`、`200 + error` 和任意错误正文在通用客户端路径均保持不透明，不按 `invalid_request_error` 等结构化字段短路、切号或写账号状态。精确客户端响应策略命中时按客户端能力和用户配置执行；独立后台探针仍只消费自己的完整成功 / 失败事实。

当前配置：

- 文本请求体业务上限，默认 `16MB`，由 `gatewayTextRawBodyLimitMegabytes` 在 `1..64` MB 内配置；只影响文本 lane，`/v1` 入口 hard limit 和图像生成 lane 仍为 `64MB`
- 后台管理 API 粗限流固定启用，作用于 `/__aisys__/api`：IP 级限流位于系统 API JSON body parser 之前，登录用户级限流位于 `requireAuth` 之后；`/__aisys__/api/health` 不受限流影响。阈值为 `0` 表示关闭对应限制项，但不提供关闭整套限流能力的系统设置；IP 管理白名单只放行后台管理 / 内部任务接口的 IP 和登录用户限流，不绕过认证、权限、网关 API Key 校验或封禁策略。
- 默认上游请求超时
- 默认临时不可调用最大暂停时间
- 默认代理策略
- API Key 自动生成规则（内部固定，不在系统设置暴露）
- 自用后台完整密钥展示规则
- 使用记录、业务统计缓存、系统监控、操作日志和普通运行日志索引的保留天数，表数据清理统一由后台 worker 执行；原始审计日志按部署环境变量和固定分层策略保留
- 原始审计日志能力固定启用，默认把成功请求最近 1 小时全量热保留，超过热窗口后保留 `10%` 稳定采样 3 天，问题链路全量保留 7 天；成功热窗口、成功采样、成功 / 问题保留期和成功 / 问题正文上限可由 `JUHE_AI_AUDIT_LOG_*` 配置，其中成功热窗口、采样率和保留期允许为 0，三项全 0 时不采集成功审计，问题链路仍至少保留 1 天。队列、批次、压缩、去重和问题采样策略固定，不提供系统设置项
- 统计 worker 间隔、统计聚合批量上限、分组账户统计刷新间隔、系统采样间隔、聚合数据保留天数和统一清理批量上限
- 操作日志固定启用，系统设置只开放操作日志保留天数和单条操作日志字段差异上限
- OAuth Access Token 预刷新间隔、提前刷新窗口、批量大小和失败退避
- OAuth 额度快照被动更新口径；不再提供后台主动刷新间隔、过期探测和刷新并发配置
- 统计滞后告警阈值，用于运维概览提示缓存是否落后

## 流式失败与账号处理

轻量版流超时处理不引入重型调度器。真实网关流式失败只处理当前请求、建立来源局部回避并首次投递 `recovery_wait`；运行态调度降级只能由后台探针按最小观察时间和真实失败结果确认。SQLite 中的流失败诊断窗口只保留诊断计数，不再作为处罚触发器。

默认参数：

- `gatewayTextRawBodyLimitMegabytes`：默认 `16`。表示认证预检通过后，文本 lane 请求体允许进入业务链路的最大 MB 数；可在系统设置中调整，合法范围 `1..64`。图像生成 lane 和 `/v1` 入口硬上限仍固定为 `64MB`，避免合法图像请求被文本上下文上限误伤。
- 后台管理 API 粗限流固定启用，不提供整体关闭开关。
- `systemApiRateLimitIpReadPerMinute`：默认 `600`。同一客户端 IP 的后台读请求每分钟上限，读请求包含 `GET`、`HEAD` 和 `OPTIONS`。
- `systemApiRateLimitIpReadBurstPer10Seconds`：默认 `120`。同一客户端 IP 的后台读请求 10 秒突发上限。
- `systemApiRateLimitIpWritePerMinute`：默认 `180`。同一客户端 IP 的后台写请求每分钟上限，写请求包含 `POST`、`PATCH`、`PUT` 和 `DELETE` 等非读方法。
- `systemApiRateLimitIpWriteBurstPer10Seconds`：默认 `40`。同一客户端 IP 的后台写请求 10 秒突发上限。
- `systemApiRateLimitUserReadPerMinute`：默认 `300`。同一登录系统账户的后台读请求每分钟上限。
- `systemApiRateLimitUserWritePerMinute`：默认 `120`。同一登录系统账户的后台写请求每分钟上限。
- `defaultTemporaryUnschedulableMinutes`：默认 `2` 分钟。表示临时不可调用恢复流程的最大单次暂停时间；账号先按 3 秒快速恢复，连续失败后翻倍，慢速恢复单次等待不超过该上限。
- `temporaryUnschedulableRetryIntervalSeconds`：默认 `3` 秒。transport / timeout 类上游尝试失败切号前，同账号原地确认重试之间的等待间隔；冷却恢复复测会显式覆盖为不做同账号重试。
- `temporaryUnschedulableRetryAttempts`：默认 `3` 次。transport / timeout 类失败在同一次网关请求中共享的同账号确认预算；预算不按账号、流式重新调度、后续分组或 compact 预处理重新发放。通用客户端收到完整上游响应后不消费该预算。冷却恢复复测会显式覆盖为不做同账号重试。
- 账户级后台核实：用户失败只能原子首次创建 `recovery_wait` 任务，后续同账户请求不得合并失败计数、替换 generation、提前或推迟探针、刷新 TTL，也不得形成账户级短暂避让；任务由统一后台探针调度器推进，standalone 使用 memory、performance 使用 Redis runtime state。真实网关流量中的代理 profile 已知不可用也只能投递后台核实，不直接写持久临时不可调用。`recovery_wait` 保持普通可调度且不展示账户异常；第一次有效独立后台探针失败后，`precheck_pending` 从普通候选池软阻断，但保留后台探针、主动健康检查和受控半开恢复出口。当前分组和后备均只剩软阻断账户时，同账户 / 同分组只允许一个 generation 租约半开，其余请求按分组、模型和候选 generation 进入有上限的 FIFO 等待。只有完整 JSON / SSE 协议成功才能 CAS 清理软阻断；失败和客户端中断只释放租约，不累计后台探针轮次。持久硬状态至少需要 5 分钟观察、3 个独立后台轮次且轮次至少间隔 2 分钟。后台探针成功后清理。
- 流式超时检测固定启用，不提供整体关闭开关；未命中用户显式策略的真实网关流式失败只切换当前请求并首次投递 `recovery_wait`。`recovery_wait` 阶段保持账户普通可调度；首次有效独立后台探针失败后进入 `precheck_pending` 并软阻断普通调度，最终确认失败且当前账号并发归零后才写持久账号状态。
- `textFirstResponseTimeoutSeconds`：默认 `120` 秒；文本 lane 上游首响应和非流式首字节等待上限。
- `textStreamIdleTimeoutSeconds`：默认 `30` 秒；文本 lane 收到首段上游内容后的 raw chunk 停顿上限。
- `textUncommittedAttemptMaxLifetimeSeconds`：默认 `1800` 秒；文本 lane 单次尚未提交语义的上游尝试最大寿命。活跃且已经提交语义的 SSE 不因该值到点机械中断。
- `imageFirstResponseTimeoutSeconds`：默认 `600` 秒；图像 lane 上游首响应和非流式首字节等待上限。
- `imageStreamIdleTimeoutSeconds`：默认 `120` 秒；图像 lane 收到首段上游内容后的 raw chunk 停顿上限。
- `imageUncommittedAttemptMaxLifetimeSeconds`：默认 `3600` 秒；图像 lane 单次尚未提交语义的上游尝试最大寿命。
- `noAvailableAccountWaitTimeoutSeconds`：默认 `270` 秒；只累计零可派发账号、并发槽或可恢复运行态的等待时间。真实上游 attempt、已有可派发账号的扫描和活跃响应读取不消耗该预算。SSE 等待期间可发送注释心跳，心跳只提交传输层。
- `JUHE_AI_GATEWAY_UPSTREAM_AGENT_MAX_SOCKETS` / `JUHE_AI_GATEWAY_UPSTREAM_AGENT_MAX_FREE_SOCKETS` / `JUHE_AI_GATEWAY_UPSTREAM_AGENT_MAX_TOTAL_SOCKETS`：默认分别为 `2048`、`512`、`8192`。这些值只控制网关到上游的 keep-alive socket 池容量，用来承接慢 SSE、长对话和多上游并发；它们不能替代账号并发、额度和系统资源保护，也不能改成无限连接。网关不因未知上游状态码、错误码或错误体结构扩大特征判断，只要当前路由范围还有可用账号且下游尚未提交，就优先在服务端继续切换账号 / 分组。
- `streamFailureThresholdCount`：默认 `3` 次。历史流失败诊断计数参数；真实网关流式失败不再依赖该阈值决定是否写状态。
- `streamFailureThresholdWindowMinutes`：默认 `5` 分钟。历史流失败诊断计数窗口参数；运行态调度降级由后台探针在观察窗口内确认，不由该诊断计数或普通用户请求直接触发，没有固定惩罚时长，由后台探针成功或手动恢复后清理。
- `statsAggregationIntervalSeconds`：默认 `60` 秒。统计缓存增量汇总间隔；常驻 stats-worker 的 usage 在线聚合有效间隔最多按 `60` 秒执行，即使系统设置被误配为更大值，也不能让新日用量可见性退化到小时级。
- `statsAggregationBatchSize`：默认 `2000`。统计 worker 配置层单批最多处理多少条使用记录；常驻 stats-worker 在线聚合会再把 usage 单批实际处理量限制为 1000 条，并给每轮调度设置 4.5 秒运行预算，避免压测或误配置把单批统计事务拉到多秒级卡顿。增量聚合在批内先按 scope、时间桶、模型、延迟桶和账号质量分钟桶预聚合，再写入 SQLite，避免高并发下对同一批记录逐条重复 upsert。更大的批量只适合作为离线重建或人工追赶历史积压时的独立脚本参数。持续写入时，统计游标保留 15 秒安全延迟，用来吸收 usage 队列落库、IPC 和 Redis Stream 传递的短暂延迟；stats-worker 不再简单要求 usage 队列或 Redis Stream backlog 完全为空，否则高吞吐场景会让统计长期饥饿。若 pending usage 或 Redis Stream backlog 中存在超过 15 秒仍未落库的记录，stats-worker 只会聚合早于该记录的安全窗口，避免游标越过未落库记录。
- `statsAggregationMaxBatchesPerRun`：默认 `5`。统计 worker 每轮最多处理多少批；连续批次之间必须让出事件循环，并在继续下一批前固定等待 25ms，避免长回填期间 worker 心跳、IPC 和系统指标采样被长时间延后。
- 每轮 usage 聚合处理到新数据或统计时区发生切日后，stats-worker 会通过 `usage_hot_window_refresh` 触发热用量窗口刷新，只发布 `today`、`yesterday`、`last7d`、`last31d` 和 `current_month` 等 `window_key` 窗口，并用 60 秒防抖、同一窗口刷新锁和 source watermark 跳过机制控制频率；`usage_scope_range_windows` 按 `window_key` 小事务删插，避免高频刷新整张窗口表。
- 常用 TopN、长周期概览窗口、额度窗口、按需范围窗口和授权范围窗口仍由独立 `usage-rank-snapshots-refresh` worker 任务兜底刷新，不绑在每轮 `usage-stats-aggregation` 尾部同步执行；生产 worker 按功能表分阶段短事务刷新，并在阶段之间让出事件循环。单阶段刷新命中已有水位时直接跳过；源表有新增聚合时，`usage-overview-windows-refresh` 和 `usage-scope-range-windows-refresh` 会根据上次成功水位后的最早变更日期，只重写受影响的热窗口或已登记按需窗口，避免常态下反复重建近 31 天全部范围组合。切日、首次运行、水位异常或无法定位变更日期时仍回退完整刷新。
- `groupAccountStatsRefreshIntervalSeconds`：默认 `60` 秒。分组账户统计缓存刷新间隔。
- `systemMetricsSampleIntervalSeconds`：默认 `30` 秒。系统监控采样间隔。
- `oauthAccessTokenRefreshIntervalSeconds`：默认 `60` 秒。后台 worker 定期扫描 OpenAI OAuth Access Token。
- `oauthAccessTokenRefreshLeadSeconds`：默认 `300` 秒。Access Token 距离过期小于该窗口时提前刷新。
- `oauthAccessTokenRefreshBatchSize`：默认 `20`。每轮最多预刷新多少个 OAuth 账户。
- `oauthAccessTokenRefreshRetryBackoffSeconds`：默认 `300` 秒。后台预刷新失败时，同一账号下一次预刷新前的退避时间。
- `accountQualityRefreshIntervalSeconds`：默认 `600` 秒。账号质量缓存刷新间隔。
- `accountQualityWindowMinutes`：默认 `10` 分钟。真实网关请求首 token 质量统计窗口。
- `accountTestTaskConcurrency`：默认 `100`。独立单账户人工测试任务的系统级并发上限，合法范围 `1..1000`；项目不提供多账户批量测试或用户级全局测试锁。
- `runtimeLogIndexRetentionDays`：默认 `14` 天，合法范围 `1..90`。普通运行日志索引用于运行日志页面检索和 facet 聚合，保留期到达后由后台清理。
- `publicApiLogRetentionDays`：默认 `30` 天，合法范围 `1..365`。公开接口日志用于排障，保留期到达后由统一数据保留任务清理。
- `usageRecordRetentionDays`：默认 `30` 天，合法范围 `1..180`。自动保留清理只删除已被统计安全游标覆盖的旧使用记录。
- 数据保留清理的调度间隔和批量吞吐是后台内部常量，不属于系统设置：固定每 10 分钟执行一次，单批 1000 行，单轮最多 20 批，每类数据每轮最多处理 2 万行。
- `cooldownAccountRetestMaxBackoffHours`：默认 `12` 小时。冷却账号后台复测固定启用，用于冷却到期后的恢复性测试；超过该快速恢复窗口后进入长期不可用阶段，固定每 1 小时复测，从观察起点满 7 天仍失败时转为 `error`。长期复测间隔不提供系统设置。
- `cooldownAccountRetestIntervalSeconds`：默认 `3` 秒。冷却账号恢复性复测扫描间隔，用于承接快速恢复通道。
- `cooldownAccountRetestBatchSize`：默认 `10`。每轮最多恢复性复测多少个冷却到期账号。
- 账号质量主动探测相关系统项已删除，不允许通过配置重新开启。

处理方式：

- 真实命中上游账号后的 transport / timeout、非流式正文中断和精确客户端语义失败，在未命中用户显式策略时不会改变账户级运行态或把当前账户行写为 `temporary_unavailable`；语义提交前当前请求可以切换后续账号并建立 API Key / IP / 会话局部回避，同时只在不存在后台事件时首次投递 `recovery_wait`。通用客户端收到完整上游响应后原样转发，不按状态、错误类型或正文进入这条失败流水线。独立后台探针真实失败后，才在 standalone memory / performance Redis runtime state 中建立 `precheck_pending` 软阻断；健康和后备优先，全池软阻断时同账户 / 同分组单飞半开，其余 FIFO 等待，并只累计最多 270 秒零可派发账号时间。账户错误处理策略与响应拦截策略只允许在明确客户端画像和显式管理边界内执行；账户授权实例只修改自己的实例账户行。
- 首响应前请求异常和非流式首字节前 transport 超时属于尚未向下游提交语义的安全切号窗口；非流式首字节已经写给下游后不再透明重放，正文中断记录 `upstream_body_interrupted` 并打断下游连接，让客户端重试。SSE 注释心跳只设置 `transportCommitted`，仍允许语义提交前的 transport 救回；真实协议事件或正文写出后设置 `semanticCommitted`，禁止拼接第二个账号。零可派发账号等待共享 `noAvailableAccountWaitTimeoutSeconds`，上游 attempt 和活跃读取不计入。独立后台探针连续失败且当前账号并发归零后，才允许写入持久临时不可调用；普通网关成功不能清理账户级运行态或 `rate_limited`。
- 对 `200 + SSE` 内的上游失败事件，只有精确命中的 Codex Responses、Claude Code Messages 和 Gemini CLI stream 才解释协议失败并在语义提交前服务端切号；通用客户端原样转发事件，不把 `server_is_overloaded`、`slow_down` 或任意未知错误码升级为网关判断。服务端 transport 失败耗尽后，已知客户端写对应协议错误事件，通用客户端按是否已提交传输选择 HTTP 错误或断流。
- 当前管理端响应检查策略只在精确客户端画像下执行；`generic_*` 请求不读取 `200 + SSE` / `200 + JSON` 的广告、错误对象或完成状态来决定调度。管理端仍可维护协议 / 供应商策略、账户可维护追加规则，但专属规则必须由运行时客户端能力门控，不能扩散成全局错误码或正文特征白名单。
- 下游写出边界拆为传输提交和语义提交：SSE 注释心跳只设置 `transportCommitted`；真实协议事件、正文或可见模型输出写出后设置 `semanticCommitted`。只有语义尚未提交时允许服务端 transport 救回；一旦语义提交就禁止拼接第二条响应。服务端重试耗尽后，`upstream_retryable_error` 只用于本地 transport / capacity 耗尽或精确客户端语义失败，不继承任意上游错误分类。
- 通用客户端对非 `2xx` 上游响应保持透明：不按状态或错误体原地确认、切号、轮换 Key、投递账号失败副作用或改写为统一错误。精确客户端只有在其声明的协议语义或显式响应检查策略命中时才允许语义提交前切号；纯 transport / timeout 失败仍走统一服务端救回。
- 请求异常会立即记录失败，并可在当前请求内按重试预算切换或跳过账号、按 API Key / IP / 会话做局部回避。未命中用户显式账户错误策略时，普通业务请求不得创建或续期账户级避让，不得改变账户全局调度资格或持久状态，只投递后台核实信号；实际命中 `credentials.error_handling_rules` 时，按用户选择的切号、临时不可调度、限流或异常动作直接执行。命中响应拦截 `avoid_account_ttl` 时同样直接执行配置的完整 TTL 运行态避让，不受系统自动短避让上限截断；该 TTL 只在到期或人工恢复时清理，后台健康成功只能清理自动探针层，不能提前解除用户显式策略。系统自动的 `recovery_wait` 不对外显示、不参与账户硬过滤。后台标准探针不维护状态码、错误码或错误类型白名单，只按是否得到完整成功、是否形成真实上游失败、是否未形成有效上游尝试推进：未知结论直接丢弃并释放观察；连续独立上游失败完成最终确认并等待当前账号并发归零后才写持久状态。账户授权实例进入这些持久状态路径时，写入的是当前命中的实例账户行，不写授权方原账户，也不写 `group_accounts.local_*`。
- 当前请求失败隔离、来源局部回避、后台核实、软阻断和流式失败处理流程见 [AI 账户运行态探针恢复设计](AI账户运行态探针恢复设计.md) 与 [网关异常重试与兜底策略](网关异常重试与兜底策略.md)；兜底层不维护状态码、错误码或错误类型白名单。
- 命中账户错误处理策略里的 `rate_limited` 会标记为限流中；命中 `error_disabled` 才会显式标记为错误。
- 未命中账户错误策略或响应拦截策略的普通网关请求无论成功失败都不改变账户级运行态、失败计数、冷却时间、最近错误或持久状态；命中用户显式策略时按配置执行，系统自动恢复与清理由后台标准探针或显式人工恢复完成。
- 账户列表展示六态状态、冷却截止时间、异常类型和错误摘要；完整 token 仍只在编辑弹窗中查看。
- 手动“迁移流量”适用于上游返回 `200` 但内容已被中转或上游改写、自动响应语义检查或账户错误处理策略无法识别的场景；它迁移当前进程内已有会话亲和绑定。选择“不影响原账户”时只迁移这些已识别客户端会话，不写源账户状态，也不影响没有会话亲和的新客户端调度；选择临时不可调用或停用时，会在源账户不可候选期间为当前系统账户和分组记录短期目标偏向，后续请求会先尝试目标账户，优先于会话亲和、超级优先、主池 / 备用池分层、账号优先级和质量分。目标不可用、被本地屏蔽、硬并发已满或不支持本次请求时再继续按原有候选顺序降级。该动作不主动断开当前流。
- OpenAI OAuth Access Token 仍保留请求前懒刷新兜底；同账号懒刷新在进程内串行，成功后用短 TTL 最近刷新缓存吸收同一波临期并发，避免每个排队请求都重复读写 DB service。后台 worker 额外做专职预刷新，扫描所有仍存在、未删除、有 `refresh_token` 且即将过期的 GPT OAuth 账户，不受 `active`、`disabled`、`error`、`rate_limited`、`temporary_unavailable` 或 `schedulable` 状态影响。后台预刷新只负责保活 token 并写回凭据，成功时不恢复普通冷却状态、不清理无关错误；失败时按退避重试并累计连续失败次数，连续 3 次失败后把非停用账户写入 `status = error` 和 `last_error_code = oauth_token_refresh_failed`，后续后台刷新成功会自动恢复该异常。手动停用账户不会被后台刷新失败覆盖成异常。

## 请求体解析错误边界

- 客户端上传未完成即断开、`Content-Length` 未完整到达，或解析器报告 `request.aborted` / `request.size.invalid` 时，返回 OpenAI 兼容 HTTP `408`、错误码 `request_timeout`，归因 `client_lifecycle`，允许客户端按标准重试策略重新发送完整请求。
- 完整上传但 JSON 语法非法时保持 HTTP `400` 本地请求错误；两类错误都发生在上游派发前，不执行账户错误策略、响应拦截、账户 Key 轮换、`recovery_wait` 或账户运行态副作用。

## 中转协议与流程

对外暴露 OpenAI 兼容的客户端网关入口，非 `/__aisys__/*` 请求都按客户端请求处理，兼容 `/*` 和 `/v1/*`。这里的兼容首先指客户端入口、鉴权方式和错误结构尽量贴近 OpenAI 协议；具体上游能力按账户类型区分，不能把 OAuth Codex adapter 等同于公开 OpenAI API Key 能力。开发环境可把 Base URL 配为 `http://127.0.0.1:3000` 或 `http://127.0.0.1:3000/v1`，常用路径包括 `/models`、`/responses`、`/chat/completions`、`/v1/models`、`/v1/responses` 和 `/v1/chat/completions`。GPT API Key 账户上游仍归一到 `/v1/*`；后续新增提供方时，也优先把上游差异适配到 OpenAI 兼容格式，不在客户端侧暴露各厂商私有协议。

透传规则：

- 产品上不提供透传开关；所有账户按供应商 adapter 的内部策略透传。
- GPT API Key 账号同时具备 OpenAI 标准和 Codex Responses 兼容能力；普通 OpenAI 请求体优先使用客户端 `rawBody` 原样转发，不做默认内容填充或无关重写。
- GPT API Key 账号仅在请求侧 `requestClientCompatibility = codex_responses` 且路径为 `POST /responses` / `POST /v1/responses` 时补齐 Codex Responses 协议：JSON 请求体中字符串 `input` 转为 Responses message 数组，数组内 `system` 角色归一为 `developer`，补 `instructions`、`tools=[]`、`tool_choice=auto`、`parallel_tool_calls=true`，强制 `stream=true`、`store=false`，确保 `include` 包含 `reasoning.encrypted_content`，将 `web_search_preview` / `web_search_preview_2025_03_11` 归一为 `web_search`，并移除 token 上限、采样字段、`context_management`、`truncation` 和 `user`；请求头强制 `Accept: text/event-stream` 与 `Content-Type: application/json`，缺省补 `originator`、`user-agent`、`version` 和 Responses `OpenAI-Beta`；其他路径继续透传。
- `/v1` raw body 当前入口硬上限为 `64mb`；认证预检和可提前识别的图像权限拒绝通过后才进入 `express.raw`。文本 lane 业务上限为 `16mb`，超过后返回 413；图像生成 lane 保留 `64mb` 上限，避免真实图像请求在本地被误拦截。API Key 账号上游请求体在上限内仍优先使用客户端 raw bytes 原样转发，不因本地解析改写。JSON body 小于等于 `256KB` 时可主线程内联解析；超过 `256KB` 且不超过入口硬上限时进入 worker thread 做顶层结构与元数据扫描，用于 `model`、`stream`、会话粘滞、图像工具权限、统计和审计字段，其中超过 `2MB` 会按大 JSON 请求记录预警；普通 API Key 大请求不在主线程完整构造 JSON 对象。只有 OAuth Codex 归一化、禁用图像权限下移除 optional `image_generation` 工具，或已选 GPT 账户配置了服务等级 / 思考级别覆盖等确实需要改写请求体的路径，才进入 worker thread 完整解析。GPT 覆盖在模型映射和协议桥接确定实际上游模型与 endpoint family 后、最终字段清洗和序列化前执行；大请求必须复用 JSON worker。使用记录请求快照只保存体积摘要，完整原始内容由原始审计按策略捕获。
- 这条限额是刻意保留的产品决策，不是遗留配置：入口 hard limit 不能简单改成统一文本 lane 上限。性能优化只能在认证预检、权限早拒绝、worker 元数据扫描、审计捕获上限或未来流式上传方案上收口；除非产品明确放弃大图像请求，否则不得用全局入口上限替代 lane 级限额。
- OpenAI API Key Header 透传必须过滤本地认证、HTTP hop-by-hop、代理链路、cookie、压缩、SDK / tracing / 部署平台噪声和 OAuth / Codex 专用头。
- GPT API Key 账号不默认透传客户端 `OpenAI-Organization` / `OpenAI-Project`，也不从账号凭据生成这两个头；组织 / 项目属于上游账号上下文，普通用户通常不知道也不应被要求填写。
- `OpenAI-Beta` 可保留客户端显式传入值；服务端不生成默认 Beta，也不做账号级覆盖。
- GPT OAuth 账号不复用 API Key raw passthrough，账号协议能力固定为 Codex Responses，并必须进入 `openai_oauth_codex` adapter，做 endpoint 限制、请求体归一化、Header 白名单和上游会话标识隔离；OAuth / Codex 请求体超过网关 JSON 预警阈值时继续保持连接，等 worker thread 异步解析完成后再归一化和转发，并写入 `openai_oauth_codex_large_body_parse` warning 日志，便于排查大请求导致的事件循环延迟。
- OAuth / API Key 账号类型只决定能力矩阵、转发方式、凭据刷新和账号运行态展示；会话亲和和 Codex prompt cache 隔离按本地系统账户、API Key 和客户端会话边界处理，不按分组或上游账号类型重分片。统计、额度和网关运行配置缓存仍按各自业务口径保留 API Key、分组、调用方和账户真实 ID 等维度。详细决策见 [账号类型统计缓存边界决策](../architecture/账号类型统计缓存边界决策.md)。
- 更完整的源码对照和透传定位见 [中转透传机制调研与定位修正](中转透传机制调研与定位修正.md)、[OpenAI OAuth 透传细节统计与比较](OpenAI%20OAuth透传细节统计与比较.md) 和 [OpenAI API Key 透传细节统计与比较](OpenAI%20API%20Key透传细节统计与比较.md)。

后端网关职责：

- 校验本地 API Key。
- 先按请求 `model` 尝试定位目标供应商，再在目标供应商的路由策略绑定分组内选择号池；账户侧协议档案、endpoint mode 和模型映射继续约束候选账户，无法明确定位时返回本地错误，不继续按默认分组调度账号。
- 替换上游认证。
- 剔除协议安全头和明显代理链路头。
- 隔离会话标识。
- 稳定转发 SSE 流；语义提交前的 transport 失败优先进入服务端内部重试，切换后续账号 / 后续分组。账号耗尽后按客户端策略返回最终失败：Codex Responses、Claude Code Messages 和 Gemini CLI stream 写各自协议错误事件，通用客户端在未提交传输时返回 HTTP `503/upstream_retryable_error`，已提交传输时断流。上游 SSE 自带的失败事件对通用客户端仍按原始事件透传。
- 通用客户端对完整非 2xx 上游响应原样转发，不进入失败流水线。只有本地 transport / timeout 或精确客户端画像允许的协议语义失败才可在语义提交前切换后续账号；账户错误处理策略和响应检查策略不得扩散到通用客户端。
- 记录使用情况并按账户错误处理策略和通用失败流程兜底切换。

当前轻量中转请求链路：

1. 创建原始审计内存捕获上下文，记录客户端原始请求入口信息。
2. 校验 API Key。
3. 读取 API Key 绑定的路由策略及其 active 分组绑定，按优先级准备候选号池；网关运行态里的 `apiKey.selected_group_id` 表示本次已经选中的实际分组，来源于当前路由策略绑定表。
4. 对每个候选分组校验归属、启用状态、供应商一致性和本地授权边界，获取分组内可调度账户，并按请求路径、客户端 profile、图像能力、账号类型能力和模型限制过滤候选，同时过滤已到 `account_expires_at` 的账户。
5. 按分组类型选择账号：个人分组按状态、并发、代理、错误冷却和既有账号排序选择；高并发分组在同样硬过滤后按分组级策略、账号优先级、软并发、分组排队、慢请求分流和快速优先选择，避免请求先绑定到单个账号后长时间排队。调度前如果当前分组没有正常可调度账号、能力不匹配或已明确不可承接，则按路由策略号池优先级尝试后续分组；真实上游派发开始后，普通上游失败不跨分组重放，写下游前的配置化响应检查在当前号池耗尽时可按策略绑定优先级切后备分组。
6. 按供应商和账户类型构造上游请求，并把实际上游请求追加到审计上下文。
7. 根据客户端画像、transport 生命周期和双提交状态处理上游结果：通用客户端收到完整响应后原样转发，不解释 HTTP 状态或正文；transport / timeout 失败在 `semanticCommitted = false` 时消费共享确认预算并切换后续账号。精确客户端允许按其协议语义和响应检查策略在语义提交前切号。非流式首字节或 SSE 真实协议事件写出后禁止拼接第二个账号；SSE 注释心跳只提交传输，仍可等待账号恢复。完整链路见 [网关错误处理完整链路](网关错误处理完整链路.md)。
8. 写入使用记录。
9. 请求结束、失败或客户端中断后，计算审计终态；命中保存规则时把完整审计对象放入内存队列，由后台批量落库。

当前跨供应商请求链路调整点：在读取 API Key 绑定路由策略及其 active 分组绑定后，解析请求体顶层 `model`，先用模型目录在当前策略可达供应商集合内唯一命中目标 `provider_code`，再把候选号池收窄到该供应商；模型无法明确路由时不猜测全局账号池，直接返回本地错误。账号支持模型、账户协议档案和模型映射用于账号过滤和上游模型改写；同一目标分组内候选账号按直接支持请求模型、模型映射命中且上游模型在支持模型内排序，未声明支持模型的账号视为不限模型并排在直接 / 映射命中之后作为兜底候选，层内继续按原有调度、并发、额度、冷却、错误避让和重试规则执行。后续模型路由索引增强完成后，应把这一步收敛为 O(1) 读取目标供应商。

使用记录和统计聚合使用同一事实源，但统计口径按 `traffic_source` 明确区分：`usage_records` 保留真实网关请求、手动账号测试和后台恢复探活明细；业务统计缓存只聚合 `gateway` 和 `manual_account_test`，`cooldown_retest` 只保留明细与审计，不进入业务统计或账户质量统计。失败记录没有 token / cost 时按 0 token、0 cost 计入对应口径的请求和错误次数。

## OpenAI OAuth 授权设计

- OAuth 手动授权：生成 PKCE 授权链接，用户复制 localhost 回调 URL，后端校验 `state` 后换取 token；Client ID 和 Redirect URI 使用后端内置默认值，不作为用户输入项。
- Refresh Token 授权：用户粘贴 `refresh_token`，后端使用内置默认 Client ID 刷新后创建 OAuth 账户。
- OAuth 凭据字段：`access_token`、`refresh_token`、`expires_at`、`client_id`、`email`、`base_url`。
- OAuth 创建允许通过客户端补丁写入账户本地错误处理规则。token、过期时间、Client ID 和上游地址始终由服务端 token 交换结果生成，不能被客户端补丁覆盖。
- OAuth token 的 `expires_in` 只用于计算 `credentials.expires_at`，不是账户套餐到期；本地套餐到期统一使用账户字段 `account_expires_at`。
- 网关调度：同一分组内可混合 API Key 账户和 OAuth 账户，OAuth 账户使用 `access_token` 透传到上游。
- 自动刷新：OAuth `expires_at` 接近过期时，用 `refresh_token` 刷新并写回 SQLite。
