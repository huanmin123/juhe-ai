# 账户模型限制设计

## 背景

网关的默认兜底策略是：上游账号真实失败后，可以按账户级错误处理策略进入临时不可调用、限流或异常状态。这是账号池自我保护能力，不能靠状态码、固定错误文案或某个客户端协议做被动拦截。

当客户端请求的模型和账号实际上游能力不匹配时，如果直接逐个账号打上游，可能把同一分组内多个账号连续打入临时不可调用。账户模型限制用于把这类“用户已知的模型能力边界”前置到本地调度，让用户自行决定是否启用安全约束。

## 核心语义

- 供应商维护模型目录，账户配置支持模型时只能从账号所有者可见的所属供应商模型目录选择；目录包含内置模型和账号所有者个人自定义模型，管理员创建的自定义模型也只归属管理员自己。当前目标供应商包含 `gpt` 和 `glm`，都可以使用 OpenAI v1 协议；支持模型不能按协议码 `openai` 混用不同供应商的模型目录。
- 账户模型映射现在是“账号模型别名”：左侧 `sourceModel` 和右侧 `upstreamModel` 都必须来自当前账号供应商模型目录，并且端点族只能是当前协议档案允许的同协议组合。OpenAI v1 普通账户额外允许显式配置 `responses -> chat_completions` bridge，用于 Chat-only 上游承接 Codex / Responses 入站；该 bridge 的左侧 `sourceModel` 可使用当前供应商目录内的 Chat-only 模型作为下游 Responses 别名，右侧 `upstreamModel` 仍必须支持 Chat Completions。其他跨供应商、跨协议或 Messages / Gemini native 桥接继续统一配置在混合供应商账户。
- `providerCode=glm` 的通用 GLM API 和 GLM Coding Plan 使用同一个 GLM 模型目录，并可以进入同一个 GLM 分组；如果某个 GLM 模型只适用于 Coding Plan 或只适用于通用 API，应通过模型目录能力字段和账号 `supportedModels`、账户接入类型与 endpoint mode 明确限制，不靠网关猜测。
- AI 账户必须配置支持模型列表；新建账户不再按供应商默认模型回填，用户可直接从本地目录选择并保存。账户表单不会自动同步上游目录，用户可手动刷新；上游目录不是隐式保存前置条件，但点击“测试”或“确认”时缺少支持模型或检查模型会被前端拦截，且不会自动同步。手动同步失败不影响已配置完整模型的保存、测试或调度。
- 检查模型必须由用户从支持模型中选择。手动目录同步成功后，后端可在“上游可见、当前协议兼容、本地可测试”的模型中按发布时间倒序推荐；当前推荐不可用时按发布时间严格回退。目录同步失败时保留现有手动选择；持久化账户始终保存一个最终有效检查模型，后台只读取账户保存值。
- 支持模型列表不能为空，未配置支持模型的账号不作为任意模型兜底候选。
- 下游请求模型精确命中列表中的某个模型时，该账号直接进入候选池。
- 请求模型未直接命中支持模型时，可以通过启用的模型映射命中 `sourceModel + sourceEndpointFamily` 保留候选，但映射右侧 `upstreamModel` 必须命中 `supportedModels`；`sourceModel` 不受 `supportedModels` 限制。
- 模型映射命中后只在选中账号后改写上游请求体；调度阶段使用账号运行时快照中的 `supportedModels` 和 `modelMappings` 判断是否保留候选账号。完整边界见 [自定义模型与模型映射设计](自定义模型与模型映射设计.md)。
- 因模型不匹配被跳过的账号不算失败，不进入账户错误处理策略，不写临时不可调用，不触发本地短期屏蔽。
- 请求缺少 `model` 时无法完成支持模型或映射匹配，网关直接返回本地错误，不请求上游。
- 如果分组内所有可用账号都因模型不匹配被过滤，网关直接返回本地错误，不请求上游。
- `GET /models` / `GET /v1/models` 继续由本地供应商模型目录返回，不参与账户模型限制过滤；所有本地模型目录入口必须携带有效 Gateway API Key。OpenAI-compatible 使用 `Authorization` 或 `x-api-key`，Anthropic native 使用 `x-api-key` 与其协议版本头，Gemini native 保留 `x-goog-api-key` 的协议认证入口。
- 账户表单不会自动同步上游模型目录；新增、编辑、字段变更和取消都不发起目录请求。用户只能通过刷新图标手动同步。后端按账户协议档案与草稿凭据请求上游，先以本地所有者可见、协议兼容的供应商目录过滤，再只返回当前 `supportedModels` 尚未包含的模型；前端只追加这些模型，绝不删除用户手动选择的模型或既有模型映射。点击“测试”或“确认”且支持模型或检查模型为空时只提示并中止，不触发同步。
- 列表单项人工测试是受控诊断例外：模型候选来自账户供应商、协议档案和所有者作用域可见的启用文本目录，不受 `supportedModels` 限制；测试固定命中当前账户且结果不修改支持模型、检查模型、健康、Key 或调度状态。新增 / 编辑表单测试仍固定使用表单 `healthCheckModel`。
- 账户请求覆盖的配置候选取支持模型 `supportedServiceTiers`、`supportedReasoningEfforts` 精确能力数组的并集；能力未知模型不清空其他模型贡献的候选。运行时按映射后的最终上游模型能力逐字段判断，不支持或能力未知时保留客户端字段，不做向下降级。`ultra` 只属于独立 Codex 能力，不是账户 reasoning wire 值；Responses Multi-agent Beta 不在本期账户覆盖范围。

## 性能设计

模型限制不能让每次客户请求都查询数据库。

- 账号支持模型使用业务库轻量关系表保存；正常账户必须至少有一行支持模型。
- 网关账号池缓存 miss 时，一次性读取分组内候选账号，并按账号 ID 批量读取支持模型列表。
- `OpenAIAccountSecret` 运行时快照带上 `supportedModels`，进入 `gatewayRuntimeCache` 和 `openAIAccountsCache`。
- 每次请求只在缓存账号数组上按下游请求 `model`、账号 `supportedModels` 和启用的 `modelMappings` 做内存过滤，再进入会话亲和、本地屏蔽、授权额度和上游尝试。
- 人工测试、周期健康检测和恢复探针直接执行账户保存的真实检查模型和请求形态，以协议成功结果判断。它们不以 `models_catalog` / `GET /v1/models` 的结果作为账户可用性结论；目录不可用、`404` 或格式不兼容不能阻断测试、激活、健康、恢复或调度。
- 账号创建、编辑、删除、分组绑定、授权变更等现有写路径已经清理网关 runtime cache；模型限制写入复用账号创建 / 编辑路径，避免额外维护一套失效机制。
- 后续如果单个分组账号池过大，再增加 `groupId + systemAccountId + model` 的派生候选缓存；第一版不引入，避免同时维护两套缓存失效链路。

## 存储

新增业务库表 `account_supported_models`：

| 字段 | 说明 |
| --- | --- |
| `account_id` | AI 账户 ID |
| `provider_code` | 供应商代码，冗余用于后续供应商模型目录约束和索引 |
| `model` | 模型 ID，精确匹配请求体中的 `model` |
| `created_at` | 创建时间 |

约束：

- 主键：`account_id + model`
- `account_id` 外键级联删除到 `accounts`
- 索引：`provider_code + model + account_id`
- 账号没有任何行视为数据异常或不可调度状态，新建和编辑路径必须拒绝保存空支持模型。

不把模型限制塞进 `credentials`，也不作为账户错误处理策略的一部分。凭据只保存上游认证材料，账户错误处理策略只处理上游失败后的账号副作用，模型限制是调度前的能力约束。

## 接口与页面

- 账户创建 / 编辑 payload 使用 `supportedModels: string[]` 与 `healthCheckModel: string`。
- 后端拒绝空数组；创建或编辑账户必须由表单提交非空值，更新时不提交该字段表示保持不变。
- 后端校验 `supportedModels` 必须存在于账号所有者可见的所属供应商模型目录。`glm` 账号的支持模型只能选择 GLM 目录模型，不能选择 `gpt` 模型或 `openai` 聚合目录里的跨供应商模型。
- 后端校验映射左侧 `sourceModel` 和右侧 `upstreamModel` 都必须存在于账号所有者可见的当前供应商模型目录，并且符合账号模型别名协议矩阵。OpenAI v1 `responses -> chat_completions` bridge 的左侧按当前供应商模型目录校验，不强制要求模型目录声明原生 `responses`。
- 后端还必须校验每条映射的 `upstreamModel` 命中 `supportedModels`，避免保存后运行时永远无法命中的映射；`sourceModel` 按对应协议模型池校验，OpenAI v1 Responses 到 Chat bridge 例外按当前供应商模型目录校验，不要求命中支持模型。
- 后端必须校验 `healthCheckModel` 命中最终 `supportedModels`；删除或批量覆盖支持模型时，如果现有检查模型不再命中且本次未同时覆盖检查模型，整次更新拒绝。
- 账户列表只返回模型摘要和版本控制所需字段，详情返回完整 `supportedModels`、`healthCheckModel` 和能力配置；授权账户可以只读查看这些非敏感约束，但不能编辑。
- 前端账户表单在 Base URL 下方分别展示“支持模型”和“检查模型”；新建账户不填充默认支持模型。新增和编辑账户不会自动尝试目录发现，用户点击刷新图标才会将上游目录与本地目录交集中的模型追加到待保存值，并按发布时间返回检查模型推荐。点击“测试”或“确认”时，支持模型或检查模型为空会提示并中止该操作。
- “支持模型”同行提供刷新图标；手动刷新使用同一通用目录能力，只追加新增模型，绝不删除用户手动选择的模型或既有模型映射。同步失败或上游返回不完整目录时，现有手动模型不变。
- 批量编辑模型区只在全部目标账户具有相同 `providerCode + providerProtocolProfileId + type` 时开放，并在一个事务内按每个账户最终快照校验支持模型、检查模型、映射、endpoint modes 和 GPT 请求覆盖；任一账户无权限、版本冲突或配置非法时整批不写，授权实例不参与。
- 空值文案表达为“请选择支持模型”；保存时必须提交非空数组。

## 网关过滤流程

1. 校验 API Key、分组授权和额度。
2. `GET /models` 直接返回本地模型目录。
3. 从 runtime cache / accounts cache 取得分组账号快照。
4. 读取请求 `model`，作为下游模型。
5. 对账号快照做内存过滤：
   - `supportedModels` 为空：跳过。
   - 请求 `model` 精确命中 `supportedModels`：保留。
   - 请求 `model` 未直接命中，但启用的模型映射命中 `sourceModel + sourceEndpointFamily`，且 `upstreamModel` 命中 `supportedModels`：保留。
   - 请求无 `model`、未命中直接模型且未命中有效映射：跳过。
6. 如果过滤后为空且过滤前有账号，返回本地模型不支持错误。
7. 继续执行会话亲和、本地屏蔽、Codex turn 避让、授权额度和上游转发；如果选中账号配置并命中模型映射，先改写上游请求体顶层 `model`。账户现有 `service_tier_override`、`reasoning_effort_override` 在映射和协议桥接确定实际上游模型与 endpoint family 后，由目标 provider driver 按模型能力精确应用。

## 非目标

- 不根据 HTTP 状态码、上游错误文案、客户端 UA 或路径硬编码判断模型不支持。
- 不把 Claude、OpenAI、Codex 等协议差异写成通用调度规则。
- 不在每次请求里查询模型表或供应商模型目录。
- 不在后台自动写回或删除账号支持模型；模型目录发现仅由用户在新增/编辑表单手动触发，模型限制仍以用户保存的配置为准。
