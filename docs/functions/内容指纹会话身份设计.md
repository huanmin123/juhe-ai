## 1. 背景与问题

现行会话身份链只认官方 Header（统一会话身份 §3）：Codex `session-id`（须先由合法 `x-codex-turn-metadata.turn_id` 建立画像）、Claude Code `x-claude-code-session-id`，外加显式 `x-juhe-client-profile` 自报兼容入口。Gemini CLI 经官方源码审查确认无会话 Header；Cherry Studio、LobeChat 及各类脚本等 generic OpenAI 客户端全部不发送这些 Header。

这些请求的官方 resolver 返回 `missing`，没有 `conversationKey`，由此产生三层空洞：

1. **三层会话亲和全部跳过**（组黏分组、账户黏账户、Key 黏指纹），全部流量按模式普通调度；策略路由的 round_robin / weighted 把同一逻辑会话的连续请求逐请求拆散，上游 prompt cache 命中率随之损失；
2. **审计会话串联不可用**：审计表 `session_id` 为 NULL，运维无法按会话精确串联一个逻辑对话的全部请求；
3. **来源身份退化为 IP 软桶**：统一来源标识阶梯（统一会话身份 §4）在官方会话与协议资源证据皆缺时回退 `ip_api_key_fallback`（`clientIp + apiKeyId`），现存消费方——来源级账号避让（传输失败面 `scheduleClientSourceAvoidanceFailure` 与流式换号面，含其探活 fence）——随之按 IP 维度共享状态；[请求级提前耗尽与负面缓存设计](请求级提前耗尽与负面缓存设计.md) §5 的 L2 负面缓存（待实施）同样预留了该回退。公司、校园等共享固定出口 IP 下，不同用户、不同会话的 generic 流量共用同一来源桶，互相连带误伤。

OpenAI 兼容协议是无状态的：客户端每轮重发全量上下文，`messages` 前缀是 append-only 的——system prompt 与首条 user 消息跨轮不变。这给出一个确定性派生面：对前缀锚点做哈希即可得到稳定的每会话键（与上游 prompt cache 的命中原理同构）。失效面恰好等于可接受面：压缩/截断改写前缀 → 指纹变更 → 视为新会话、亲和按既有语义重绑。

## 2. 目标与非目标

### 目标

1. 官方证据缺位的入站请求，当 body 呈现可锚定的 `messages` 对话序列时，派生内容指纹身份：审计串联自首个请求可用，三层亲和自第二请求起可用。
2. 同一会话在压缩/截断发生前跨请求同码；锚点缺失或改写时身份失效，按新会话语义走既有降级路径（普通调度 → 成功重绑），不产生错黏。
3. 同开场会话自确认档起分岔：同 S+U1 的会话由 A1（上游生成的首条回复）分岔；罐头/模板开场（A1 亦相同）由 U2（用户第二条消息）分岔——亲和绑定互不影响。
4. 恒定长度重放流量（批量脚本、冒烟测试）不建立、不消费亲和，行为与现状一致。
5. 来源标识阶梯新增 `content_fingerprint` 档：有内容锚点时来源身份定位到**会话级**，仅无锚点流量才回退 `ip_api_key_fallback`——现存来源级账号避让对有锚点流量升级为会话级作用域，共享出口 IP 不再因缺官方 Header 而在来源级状态上互相连带（§6）。
6. 官方身份路径逐字节不变：`resolved` / `invalid` / `conflict` / resolver 出错的行为与现状完全一致，指纹档只在官方证据缺位时存在。

### 非目标

1. 不改 Codex turn 避让子作用域与探活 fence 状态机的门控（仍由合法 `turn_id` 的 Codex 识别门控，指纹档不改变其入口，generic 会话不因持有指纹而进入 Codex turn/fence 专属状态机）；IP 级错误熔断与 IP 级账号回避（`gatewayclientip`，`clientIp` 直接入键）维持 IP 维度，不接入指纹档（§6.4）。指纹档不得进入 `gatewaysession.IdentityService.Resolve` 的官方裁决内部（该服务被 `codexSourceSessionAdapter` 共享），只在两个消费接缝以官方证据缺位后的后置档接入（§3）。
2. 不做模糊匹配，不设概率阈值：全程确定性等值判定，无 k-of-N、无置信度参数。
3. 不承诺压缩后身份延续；不承诺前缀逐字节相同的会话可区分（§8 精度上限）。
4. 不解析 body 中会话语义字段：`conversation`、`session_id`、`request.session_id`、`metadata.user_id` 等字段值仍不作身份来源（统一会话身份 §6 该条对字段值的排除不变）；本设计消费的是消息序列的内容锚点，不是字段值，锚点哈希不等于"请求 body 直接摘要"（§12 边界文档裁决句）。
5. v1 覆盖 `messages` 数组形态（OpenAI chat completions 为主；Anthropic messages 同形状同判据，但其顶层 `system` 字段 v1 不入锚，见 §4.1/§8）；Responses `input`、Gemini `contents` 形状不匹配判据，天然不激活，适配留待后续演进。
6. 不在身份接缝触发完整 body 物化、不依赖 JSONParser worker（§4.1）；不新增服务端会话存储、不新增 Redis 键空间、不改三层亲和键派生结构。唯一新增状态：进程内谱系 LRU 与请求级指纹记忆化（§4.3）。

## 3. 身份档位与来源阶梯

### 3.1 会话身份档位（preauth 会话身份接缝侧）

| 档位 | 激活条件 | SessionID（审计） | ConversationKey（亲和） |
| --- | --- | --- | --- |
| 官方身份 | resolver `resolved`（现状不变） | 原始 Header 值 | 现有派生 |
| **内容指纹档（本设计）** | `IdentityService.Resolve` 返回 `IdentityStatusMissing` 且锚点可用 | `cfp1-<临时指纹hex>`（首请求即有） | `cfp1c-<确认指纹hex>` 派生（过增长判别器才有） |
| `invalid` / `conflict` / resolver 出错 | 现状不变 | 无 | 无（fail-closed，不走指纹档；`Resolve` 返回 error 时与无身份同型折叠，不计算指纹） |

- 档位判定发生在官方 resolver 裁决**之后**：adapter 侧指纹档的唯一入口是 `IdentityStatusMissing`。`invalid` / `conflict` 仍整体终止身份，维持现行 fail-closed 纪律。
- **裁定词（fail-closed 的实现约束）**：指纹判定必须在 `sessionIdentityAdapter` 内部、`identity.Status` 与 `err` 仍在作用域处完成（`err == nil && Status == IdentityStatusMissing` 唯一分支）。禁止以「投影后的空 `SessionIdentity`」作为下游触发条件——投影（`ports.go` 的 `SessionIdentity{SessionID, ConversationKey}`）无法区分 missing / invalid / conflict / error，任何在该层面追加的指纹逻辑都会破坏 fail-closed。
- 接入点：`cmd/juhe-ai-gateway/chain_ports.go` 的 `sessionIdentityAdapter.ResolveGatewaySessionIdentity`。初始解析（`preflight.go:533`）与最终 profile 重解析（`preflight.go:729`，仅 profile 变化时发生）各自按当时的 profile 计算，最终身份以最后一次为准——与组亲和 §4.5「身份以最终 profile 为准」的既有语义同构，复用其补查机制，不新增规则。
- `resolveSessionIdentityFromStrategy` 的 `strategy.ClientSource.SessionIdentity` 冻结身份优先路径保持不变。生产装配下 `clientStrategyAdapter`（`chain_ports.go:1706`）不映射 ClientSource，该路径当前不可达，生产全部请求经 `sessionIdentityAdapter` 解析；若未来接线，冻结身份请求不进入指纹档。
- 锚点经**有界原始字节扫描器**直接从 `RawBody` 前向抽取（§4.1），不触发完整物化、不依赖 JSONParser worker、不接线 parser 依赖；扫描失败或无 `messages` → 无锚点，维持现状。

### 3.2 来源标识阶梯档位（公共来源标识层侧）

| 优先级 | sourceKind | 生成条件 |
| --- | --- | --- |
| 1 | `official_session` | 现状不变（画像适用官方会话且证据有效） |
| 2 | `protocol_resource` | Gemini 已存在 interaction resource（现状不变） |
| 3 | **`content_fingerprint`（本设计）** | 无前两档、非 `invalid` / `conflict`，且内容锚点可用。注意：generic 画像本就不适用官方会话（`profileMayUseOfficialSession` 为 false，阶梯内不调用官方 resolver），因此"非 invalid/conflict"涵盖「画像不适用官方会话」与「resolver missing」两种情形，无需为判定指纹档而新增 resolver 调用 |
| 4 | `ip_api_key_fallback` | 无任何锚点且已知 `clientIp`（现状不变，成为真正的最后手段） |

`invalid` / `conflict` 仍整体停发细粒度来源、不降级污染 IP 桶（现行纪律，对指纹档同样生效）。

## 4. 指纹算法定义

### 4.1 有界锚点扫描器（gatewaybody 新增）

背景：`Capture` 对 JSON 请求只保留 `RawBody`、`Body=nil` 待物化（`gatewaybody/middleware.go` Capture；`request.go` "nil after capture until materialization"）；完整物化经 `JSONParser.ParseRequestJSONBody` 在有界 worker 上按需发生，当前唯一生产调用点在 driver 阶段（`chain_driver.go`）。身份接缝（初始 strategy/source 与 preflight）位于物化之前——**身份接缝不得触发全量物化**（generic 流量在 preauth 强制全量解析与《网关 Body 解析性能治理设计》的治理方向冲突，且 plain passthrough 派发可能根本不需要全量对象）。

因此锚点抽取采用**有界原始字节扫描器**：

- **输入**：`RawBody`（Capture 已捕获的原始字节）。**不**物化、**不**依赖 worker、纯同步前向扫描。
- **行为**：基于 gatewaybody 既有 JSON tokenizer 原语（`jsonmetadata` 的 `skipJSONValue` / 字符串扫描族），前向扫描顶层 JSON object，定位 `messages` 数组后依序遍历元素：
  - 收集「前导连续 `system` / `developer` 元素」的原始字节（S 段，`developer` 视同 `system`）；
  - 第一、第二条 `role=user` 元素的原始字节（U1、U2；U2 允许间隔任意 assistant/tool 消息）；
  - 第一个 `role=assistant` 元素的原始字节（A1）；
  - 四锚齐备后停止内容检查，仅以 skip 级跳读走完 `messages` 数组尾部统计元素总数（谱系判别器输入）；成本为 O(`messages` 数组全长字节) 的单遍扫描，尾部消息内容不被读取；数组闭合后的 body 其余部分不校验（"截断"指 `messages` 数组未闭合，未闭合即失败）。
- **失败语义**：body 非 JSON object、无顶层 `messages` 数组、元素缺字符串 `role`、JSON 截断 / 畸形 → 无锚点（该请求无指纹身份，与现状一致）。畸形检查限于被消费前缀内的结构有效性，非完整 JSON 校验（与既有 ExtractJSONBodyMetadata 同源宽容性）。
- **U2 可用性**：U2 缺失（首请求、无新增提问的重发）时仅确认档不可计算——临时档与来源档照常产出，亲和无键（与首请求同型）；U2 一经出现即永久存在于上下文（append-only），确认档自该请求起可计算。
- **canonical**：直接使用元素**原始字节**，不重序列化、不解码——`hashS` = 各前导 system 元素字节以 `0x00` 分隔依序拼接后 sha256；`hashU1` / `hashA1` / `hashU2` = 各自元素字节 sha256。canonical 的要求只有两条：同一客户端同一会话跨轮重发逐字节稳定（同一序列化器输出，成立）；不同会话间由内容区分（逐字节哈希，成立）。不要求跨客户端/跨实现的位级规范型——`systemAccountID + apiKeyID + clientProfile` 已入指纹哈希做隔离，客户端间键序/空白差异不构成碰撞面。
- Anthropic messages 形状的顶层 `system` 字段 v1 **不读**（S 恒空）：同 U1 异 system 的会话在临时档/来源档同码概率上升，确认档有 A1/U2 兜底。该精度损失显式接受（§8.5）；纳入顶层 system 属后续演进的加法修订。

### 4.2 两档指纹

```text
临时指纹 provisionalHex = hex(sha256(
  "cfp1"  0x00  systemAccountID  0x00  apiKeyID  0x00  clientProfile  0x00
  hashS   0x00  hashU1 ))

确认指纹 confirmedHex  = hex(sha256(
  "cfp1c" 0x00  systemAccountID  0x00  apiKeyID  0x00  clientProfile  0x00
  hashS   0x00  hashU1   0x00  hashA1   0x00  hashU2 ))
```

- `systemAccountID + apiKeyID + clientProfile` 入哈希：不同系统账户、不同 API Key、不同检测画像的同内容会话互不可见（内部免 Key 直调路径 `apiKeyID` 为空，仍按 owner 系统账户隔离）。
- 锚点集**冻结规则**：确认指纹一经可计算（U2 存在时），锚点集即冻结为 {S, U1, A1, U2}；后续请求重算同一组锚点比对。不随消息数增长继续追加锚点（移动锚点会使码逐轮漂移，亲和必碎）；更深的锚点扩展属演进路径（§8.7）。
- 失效语义：任一冻结锚点缺失或 canonical 变更（压缩/截断/客户端改写）→ 该请求算出**不同的码**，等价于一个新会话；旧绑定不删除、不被错误消费，按各自 TTL 自然过期。身份"失效"不产生任何删除动作（三层亲和删除触发矩阵零新增）。

### 4.3 身份产出、记忆化与谱系判别器

- **请求级记忆化（契约）**：锚点扫描与两档指纹结果按 `clientProfile` 记忆化在 `GatewayRequest` 的请求级字段上（结构形如 `per-profile → {hashS, hashU1, hashA1, hashU2 可用性, provisionalHex, confirmedHex 可用性}`），会话身份接缝与来源标识阶梯共享同一份计算——每请求**每个 profile 至多执行一次**扫描与哈希（`ClientStrategy.Resolve` 每请求两次、adapter 再取 1-2 次、失败派发链失败时刻重解析，全部命中记忆化）。记忆化只缓存派生值，**不缓存谱系判定结果**：LRU 判定只在亲和确认档产出点（adapter 侧）发生；来源阶梯只消费记忆化的 `provisionalHex`，不接触 LRU——两接缝之间不存在首见资格竞争。
- **审计 `SessionID`** = `"cfp1-" + provisionalHex`。只要锚点可用即产出，与谱系判别无关——首个请求就具备审计串联。
- **亲和 `ConversationKey`** = `CreateGatewayConversationKey(scope, "content_fingerprint:v1", "cfp1c-" + confirmedHex)`（复用现有 canonicalizer 与 HMAC purpose，`scope` 携带 `systemAccountID + apiKeyID + secret`，与官方档同构）。产出受**谱系判别器**门控：
  - 进程内 LRU：键 = `confirmedHex`（已含账户/画像隔离），值 = `{lastMessageCount, everGrown, lastSeen}`；容量 10000 条、TTL 24h（与账户亲和 memory TTL 同量级），满员逐出最旧。
  - **产出规则**：首见 ∨ `messages 数长度 ≠ lastMessageCount`（增长或收缩均为谱系演化证据）∨（长度相等且 `everGrown`）。置位规则：长度 > 记录值时置 `everGrown`，其余情况保持。不满足 → 本次解析不产出确认档（按无键处理，走普通调度），不更新记录。
  - 判定与更新在 LRU 服务互斥锁内**原子**完成（check-and-update 单临界区）；并发同键首请求串行化后恰一个产出。
  - **可实现口径**：每次身份解析至多一次 LRU 判定与更新；profile 不变的请求全生命周期恰一次；profile 变化的请求对初始/最终两个不同指纹键各至多一次，且**最终身份键的判定结果是本请求亲和消费的唯一依据**（与 §3.1「最终 profile 为准」一致）。
- **判别语义与残余**：
  - 恒定长度重放（批量脚本，含带罐头 assistant 消息的多轮固定 payload）：永不演化 → 每个 LRU 记录生命周期内至多首见产出一次（TTL 24h 内未被逐出）；逐出/过期后再次首见、再次至多一次。候选池分布不受影响。
  - 已增长谱系的同长重放（轮内失败重试、重新生成、并发同轮）：`everGrown` 已置位 → 照常产出、照常黏住，**零拦截**。
  - 残余（接受并写入 §8.6）：谱系首个请求即失败、且重试长度不变的会话，其首轮全部尝试不产出确认档（首轮本无绑定可黏，损失仅为绑定创建推迟）；自首个长度变化请求起恢复正常。
  - 真实会话第二请求起长度必然变化（append-only 重发），判别器对增长中会话零拦截。

## 5. 与三层亲和及审计的衔接

- 三层亲和零结构改动：确认档 `ConversationKey` 注入 `preflight` 既有消费点（账户 `SessionAffinity.ResolveKey`、组 `GroupAffinity.DeriveGroupAffinityKeyParts`、Key 指纹写回），HMAC purpose、TTL、删除触发矩阵全部沿用。
- 审计：`bindAuditSessionIdentity` 按现状消费 `SessionID`；指纹会话的 `session_id` = `cfp1-…`（非空、可按完整值精确查询、跨全部请求稳定），`session_client_type` = 检测画像（如 `generic_openai`），不新增审计枚举。同一逻辑会话含未过判别器的请求在内全部可串联。
- sticky 语义：首请求通常无 A1/U2 → 无确认档 → 无亲和查询（与现状一致）；预填多轮历史且末位为 user 提问的首请求（few-shot、续写历史，U2 已在锚点集内）首见即产出确认档，允许一次亲和查询与绑定写回（§9.13 断言）。第二请求起判别器放行、绑定经最终协议成功写回，第三请求起黏住生效。
- 同开场双会话：临时档同码只影响审计串联与来源档（混流，§8 已接受）；亲和自确认档（A1 不同时）分岔，各自绑定互不影响。

## 6. 来源标识阶梯接入（`content_fingerprint` sourceKind）

### 6.1 现状与问题

统一客户端来源标识（统一会话身份 §4）的阶梯今天只有三档：`official_session`、`protocol_resource`、`ip_api_key_fallback`。generic 客户端（无官方 Header）全部落入 IP 软桶，来源级状态按 `clientIp + apiKeyId` 共享。

**消费面全景（2026-10-25 全仓核实：sourceKind 枚举值与 `src_v1_` 前缀全仓仅 `sourceidentity.go` 一处构造，生产契约单点）**：

1. **来源级账号避让——记录面（现存）**：传输失败面 `chain_ports.go` 的 `scheduleClientSourceAvoidanceFailure`（:857）与流式换号面（:966），共享核心 `scheduleStreamClientSourceAvoidance`（:898），经 `ClientSourceAvoidanceStateKey`（`turnretry.go:183`，根键为 clientSourceKey）记录，门控 `AllowClientSourceAccountAvoidance`（`strategy.go`，stateKey 非空即对所有画像允许）与 `ShouldRememberGatewayClientSourceFailure`（`gatewayresponse/retrydecision.go:171`）；
2. **来源级账号避让——调度序消费面（现存）**：`chainClientSourceAvoidance.OrderAsync`（`chain_dispatch.go:125`）→ dispatch engine `preparation.go:646-777`（避让排序、阈值排除候选）；
3. **Codex turn 避让与探活 fence（现存，Codex `turn_id` 门控）**：`turnretry.go` / `turnprobe.go`，stateKey = clientSourceKey + turn 子键；
4. **L2 负面缓存（待实施，T63）**：其设计 §5 已预留"完全无细粒度证据时才回退 `ip_api_key_fallback`"。

其中 1/2 即 generic 客户端现走 `ip_api_key_fallback` 作用域的来源级账号避让。共享固定出口 IP（公司、校园）下，不同用户不同会话因"没有更好的身份"共用同一来源桶：避让状态连带、负面缓存跨用户误伤（同模板客户端发同内容请求时 `requestFingerprint` 相同）。

### 6.2 接入定义

阶梯插入 `content_fingerprint` 档（§3.2 优先级 3），来源键**复用既有实现**（下式为示意，实现必须走 `gatewayClientSourceHMAC`：domain `source:v1`、JSON 数组载体、base64url 摘要、`src_v1_` 前缀，不得新造 HMAC 布局）：

```text
clientSourceKey = HMAC-SHA256(
  JUHE_AI_SECRET,
  systemAccountId + apiKeyId + "content_fingerprint" + semanticNamespace + stableValue )   // 示意
```

- `stableValue` = **临时指纹 `provisionalHex`**：首请求即可用（确认档要等 A1 出现）、全会话稳定、与审计 `session_id` 同源、已含账户/画像隔离。选临时而非确认指纹的理由：来源状态全部是短 TTL 软状态，同开场不同会话的过共享远窄于 IP 桶（不含 IP 维度，跨 NAT/出口天然隔离）；且 L2 缓存键还叠加 `requestFingerprint`（全量 body SHA-256），第二请求起 body 分岔即天然分键，实际粒度仍为会话级。
- `semanticNamespace` = `content_fingerprint:v1`，与亲和键 namespace 同值不同 purpose。
- 激活条件按 §3.2 阶梯口径（非 adapter 口径）；锚点来自 §4.1 扫描器并命中请求级记忆化，不重复扫描、不触发物化。来源阶梯不接触谱系 LRU（§4.3）。
- 门控与纪律沿用：`invalid` / `conflict` 整体停发（含指纹档）；无锚点且已知 `clientIp` → `ip_api_key_fallback` 照旧。原始值不进键：`provisionalHex` 已是派生哈希，满足"原始 Header、resource ID 和 IP 都不写入 key"的现行约束。
- 生成位置在公共来源标识层（`ResolveGatewayClientSourceIdentity` 的阶梯判定处，各 profile 共用同一输出契约），不在 `IdentityService.Resolve` 内部（§2 非目标 1）。

### 6.3 收益落点与作用域变化裁决

- **现存来源级账号避让（传输失败面 + 流式换号面，含其探活）对有锚点流量自动升级为会话级作用域**——这是本设计的显式裁决而非副作用：避让状态不再跨会话连带，NAT 下同模板同事互不牵连。代价有界：路径级故障下每个会话各"重新发现"一次故障账户（短 TTL 软避让，每会话每故障期至多多一次试错），而路径级共享语义由不受影响的两层承担（§6.4）。
- L2 负面缓存（待实施）对 generic 客户端自动升级为会话级作用域：同模板同事不再共用负面缓存条目。
- 未来任何来源级消费者默认获得会话级身份，`ip_api_key_fallback` 从"generic 客户端的常态"退为"body 不可解析流量的最后手段"。

### 6.4 明确不接入方

1. **IP 级错误熔断与 IP 级账号回避维持 IP 维度**：IP 熔断的触发类是"本地可确认失败"（认证前 token spray、认证后本地校验失败族）——这些请求要么没有可解析 body（无锚点，指纹天然不可得，正是 IP 兜底存在的原因），要么防护语义要求不可轮换维度（指纹可被攻击者逐请求免费轮换，会话级熔断可被绕过）。IP 级账号回避（`gatewayclientip`，`clientIp` 直接入键）承担传输失败的**网络路径共享**语义（同出口同路径），与 clientSource 侧避让的会话化形成分层：路径级故障由 IP 层共享避让 + 账户级健康机制（主探测/circuit）治理，会话级特有失败由会话层精确避让，两层互不替代。NAT 下熔断连带的残余风险由该设计既有手段治理（高阈值、短 TTL、成功恢复）；若未来误杀证据充分，另立"指纹优先、IP 升级"的阶梯设计，不在本文范围。
2. **Codex turn 避让与探活 fence**：门控与状态机零改动，仍由合法 `turn_id` 的 Codex 识别门控。

## 7. 隔离、安全与观测边界

1. **隔离维度**：指纹哈希输入含 `systemAccountID + apiKeyID + clientProfile`，跨系统账户、跨 Key、跨画像不同码——审计 `session_id`、谱系 LRU 键、来源 stableValue 全部随之天然隔离；`ConversationKey` 与 `clientSourceKey` 再经现有 HMAC（`JUHE_AI_SECRET`）派生，多实例部署沿用 `JUHE_AI_SECRET` 一致性既有约束。
2. **不可逆**：审计与 Redis/内存键只出现 sha256/HMAC 派生十六进制串；锚点原文、扫描字节、哈希中间值不进审计、日志或任何持久化。来源键本身也零承载于审计与用量记录（`gatewayusage` / `auditlog` 全仓无任何 sourceKey/sourceKind 承载点，2026-10-25 核实）——本设计对内管理面唯一的可见变化是审计 `session_id` 从 NULL 变为 `cfp1-…`（§5，前端核查已列 §12）。诊断日志（允许的诊断能力）只记锚点存在性、角色与字节数量级。
3. **伪造面**：客户端可故意构造相同前缀，但只能把自己 Key 内的请求黏到同一账户、共享自己的来源状态——软调度偏好 + 硬过滤照常，无跨租户面；伪造 `cfp1-…` 审计 id 不能伪造亲和键与来源键（HMAC secret 保护）。轮换前缀可轮换指纹，但换来的只是"放弃自己的黏性与缓存收益"，不受惩罚也不得利。
4. **撞码后果（语义碰撞，非哈希碰撞）**：同账户同 Key 同画像下临时档锚点（S+U1）或确认档锚点（S+U1+A1+U2）相同的会话在对应档同码——审计串联混流、来源档过共享、亲和共享绑定（§8 已接受）；sha256 全量哈希下哈希碰撞可忽略，不设碰撞处理逻辑。
5. **多实例边界**：谱系 LRU 是进程本地状态（与缓存驱动无关，Redis 驱动下同样进程本地）。当前生产形态为国内单机单实例（判别精确）；多实例下判别退化为每实例 best-effort（批量重放可能在每实例首见时各建一次绑定，同键 CAS 收敛，无正确性影响）。若未来多实例需要精确判别，另立设计，不在本文范围。

## 8. 精度上限（明确不做）

1. 冻结锚点逐字节相同的会话（同一会话的重放；含多轮罐头开场致 S+U1+A1+U2 全同的两个会话）在内容上不可区分——任何不依赖客户端 ID 的算法都分不开；共享亲和绑定、共享审计 id 与来源档过共享是**正确行为**（且共享上游 prompt cache 受益），不作为缺陷。同理，**不触及冻结锚点内容的变化**（锚点之后的消息重排、U1 与 A1 互相换位等）不改变指纹，同属本接受面。
2. 压缩 / 截断后身份必然更换；旧绑定靠 TTL 过期，不主动清理。
3. 滚动窗口客户端（丢弃最老消息）：被保留下来的最早消息成为新 U1/A1 → 新指纹、新会话（亲和重绑），并非"无身份"；仅当截断后 body 不再含可用 U1 时才无锚点，来源档此时回退 IP 软桶（与现状一致）。
4. 无概率阈值、无置信度参数；「识别为同一会话」只有确定性同码一种含义。
5. Anthropic 顶层 `system` 字段不入锚（§4.1）：异 system 同 U1 的 Anthropic 形状会话在临时档/来源档同码概率上升，确认档有 A1 兜底。
6. 谱系首请求即失败且重试长度不变的会话，其首轮全部尝试不产出确认档（首轮本无绑定可黏，损失仅为绑定创建推迟到首个长度变化请求）。
7. **深罐头演进路径（已设计、未启动）**：罐头轮数 ≥2 的预设开场可使 U2 亦为模板内容，冻结锚点无法分岔。后手方案为**锚点分批冻结 + 前驱指纹重算**——因客户端全量重发，上一环指纹可从本轮上下文确定性重算（链不需要客户端配合）；锚点分批扩展（如扩至前 5 轮），每次扩展以「前驱键查 LRU → 命中则迁移绑定键 → 写入新键」完成一次转移，之后永久冻结回归无状态。完整滚动接龙（每轮换键）被否决：有状态链在乱序到达 / LRU 逐出 / 多实例轮转下断链拆会话，绑定键逐轮重写违反「黏住命中零写入」纪律，转移状态机复杂度不成比例。触发条件：生产证据显示深罐头前缀造成实际调度伤害时另立修订。

## 9. 验收标准

1. 无 Header 多轮会话（chat completions，首请求不含 assistant 消息）：首请求亲和查询为零（与现状逐字节一致）；第二请求起产出确认档身份，最终协议成功写回绑定；第三请求起三层黏住生效（mock 上游按账户命中数为 oracle）。
2. 同 S+U1+A1 但 U2 不同的两个会话（含罐头开场预设）：确认档 `ConversationKey` 不同，各自绑定互不影响；并发交错下写回互不覆盖。
3. 审计：指纹会话全部请求（含未过判别器请求）`session_id` 相同且可按完整值精确查询串联；`session_client_type` 为检测画像。
4. 恒定长度重放 100 次：每个 LRU 记录生命周期内除首见外亲和查询与绑定写回为零，命中分布符合纯模式行为。
5. 改写 S 或 U1（模拟压缩）：身份更换，按模式重选并重绑；旧绑定不被新会话消费。
6. 官方身份三态回归：`resolved` / `invalid` / `conflict` 及 resolver 出错请求的指纹档调用次数为零，行为与现状逐字节一致；`x-juhe-client-profile` 自报 + 无会话 Header 的请求进入指纹档。
7. 扫描器与指纹固定测试向量 ≥2 组：原始字节 canonical（多条 system `0x00` 分隔、tool_calls 原样字节、tool_calls-only A1、U2 选取（间隔 assistant/tool）、嵌套 content 数组元素）与两档指纹对输入字段敏感（改 `systemAccountID` / `apiKeyID` / `clientProfile` / 任一锚点字节 → 码变）；畸形 JSON / 无 `messages` / 缺 role → 无锚点。
8. 判别器与记忆化矩阵：首见产出 / 增长产出（置 `everGrown`）/ 收缩产出 / 等长+已增长产出（重试、重新生成、并发同轮）/ 等长+未增长拦截 / 逐出后再首见 / 收缩后等长拦截；每次身份解析至多一次 LRU 判定更新（请求级记忆化 spy：每请求每 profile 扫描+哈希恰一次）；并发同键首请求恰一个产出（原子性）。
9. `IdentityService.Resolve` 内部与 Codex turn 避让、探活 fence 门控零改动断言（来源级状态机入口不受指纹档影响）；身份接缝零完整物化断言（`ParseRequestJSONBody` 调用次数为零）。
10. 来源阶梯矩阵：`official_session` / `protocol_resource` 存在时不生成 `content_fingerprint`；generic 画像 + 锚点可用 → 来源键 sourceKind 为 `content_fingerprint` 且输入不含 `clientIp`；无锚点 + 有 IP → `ip_api_key_fallback` 照旧；`invalid` / `conflict` → 无任何来源键。
11. NAT 隔离与避让分层断言：同 `clientIp + apiKeyId` 下两个不同锚点会话的 `clientSourceKey` 与来源避让状态键互不连带，同会话避让仍生效；跨系统账户同内容会话的审计 id 与 LRU 键互不相同；IP 级账号回避与 IP 错误熔断行为全量回归不变。
12. 预填确认档锚点的首请求（few-shot / 续写历史，末位为 user 提问、S/U1/A1/U2 齐备）：亲和查询恰一次，最终协议成功后绑定写回恰一次。
13. 同 S+U1+A1+U2（共享多轮罐头开场）的两个会话：确认档同码、亲和与审计共享（与 §8.1 一致的反向断言）。

## 10. 验证方式

- **单元测试（Mock 优先）**：扫描器（顶层 `messages` 定位、前导 system 收集、U1/A1 选取、提前终止、畸形/截断/无数组失败语义、大尾部不读取断言）、原始字节 canonical 固定向量、两档指纹向量、判别器 LRU（容量/TTL/逐出/`everGrown` 置位）、请求级记忆化（每请求每 profile 一次）、`sessionIdentityAdapter` 档位矩阵（官方三态 + 出错 × 锚点可用性 × 判别器结果）、来源阶梯矩阵（验收 10 全行）、审计绑定值形状。
- **集成**：fullchain 夹具 mock 无 Header 上游客户端，覆盖验收 1-6、11-13；复跑既有账户亲和、Key 黏性、组亲和、IP 熔断/IP 回避验收证明官方与 IP 路径零回归。
- **回归**：`gatewaysession`、`gatewaypreauth`、cmd 包既有会话身份/亲和测试全绿；`sessionIdentityAdapter` 在官方 `resolved` 路径的行为快照不变。

## 11. 风险与注意事项

- **锚点扫描与哈希成本**：扫描为 O(`messages` 数组全长字节) 的单遍字节前向——四锚齐备后停止内容检查，尾部消息仅以 skip 级跳读统计元素数，内容不被读取、不参与哈希；U1/A1 含大体积内容（如 base64 图）时为该元素字节的 sha256 量级（毫秒级，受既有入站 body 上限约束）。请求级记忆化保证每请求每 profile 至多一次（§4.3），热路径无新增解析、无 worker 依赖、零完整物化。不在扫描路径对锚点内容做任何截断（截断引入新的碰撞面且破坏确定性）。
- **扫描器正确性**：手写 tokenizer 前向扫描是本设计最大的新增实现面；以固定向量（§9.7）+ 畸形输入矩阵钉死行为，扫描失败一律无锚点（fail-closed 到"现状"），不存在半解析态。
- **profile 重解析抖动**：初始/最终 profile 不一致时指纹随 `clientProfile` 输入变化一次，与组亲和「最终 profile 为准、失配重查一次」的既有语义同构，复用其预算（每请求组亲和 GET ≤2 不变）。
- **来源避让会话化的试错成本**：路径级故障下有锚点会话各自多一次试错（§6.3）；由 IP 级账号回避 + 账户健康机制兜底，集成验收 11 断言两层分层成立。
- **`SessionID` 消费面核查**：实施时审计全部 `SessionIdentity.SessionID` 消费点，确认指纹档派生值在审计绑定之外无其他语义依赖（发现即回本设计补充契约）。
- **三值口径**：审计 `cfp1-…`、亲和 `cfp1c-…`、来源档 stableValue `provisionalHex`（无前缀裸哈希）是三个消费面的派生值，代码评审与排障时易混淆；固定向量测试与本文 §4.3/§6.2 为唯一口径。
- **来源档过共享**：临时指纹不含 A1，同开场会话在来源级短 TTL 软状态上过共享（L2 因叠加 `requestFingerprint` 实际分键）；相比 IP 桶（跨用户跨会话全共享）已是数量级收窄，进一步收窄无明确收益。
- **前缀统一模板客户端**：判别力主要来自 U1（及确认档 A1）；模板客户端是本设计收益最大群体，其残余撞码后果已由 §7.4 / §8 接受。
