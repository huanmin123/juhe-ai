# 内容指纹会话身份设计

> 设计状态：**已定稿，待实施（2026-10-25）**。本文是无官方会话 Header 客户端以内容锚点派生降级会话身份的行为契约权威来源。已含独立复审收口（1 blocker + 5 major + 7 minor 全部闭环，增量核验放行；复审裁决见 §6.3/§6.4/§4.3）。
>
> **实现归属。** 本文能力实现于 `backend-go/projects/gateway`；接入点为两处消费接缝：`/v1` 派发链 preflight 会话身份接缝（`gatewaypreauth/preflight.go` 的 `resolveSessionIdentityFromStrategy` 消费面与 `cmd/juhe-ai-gateway/chain_ports.go` 的 `sessionIdentityAdapter`），以及统一客户端来源标识公共层（`internal/gatewaycodex/sourceidentity.go` 的 `ResolveGatewayClientSourceIdentity` 阶梯）。
>
> **契约修订声明。** 本设计修订 [统一会话身份与审计串联设计](统一会话身份与审计串联设计.md) §1「内容特征都不作为会话来源」与 §6「不解析 body」两条边界：官方身份解析为 `missing` 时，允许按本文以上下文内容锚点派生降级身份。修订文字随实施同步落入该文档（§12）；本文与其冲突时以先合入的修订为准。

## 1. 背景与问题

现行会话身份链只认官方 Header（统一会话身份 §3）：Codex `session-id`（须先由合法 `x-codex-turn-metadata.turn_id` 建立画像）、Claude Code `x-claude-code-session-id`，外加显式 `x-juhe-client-profile` 自报兼容入口。Gemini CLI 经官方源码审查确认无会话 Header；Cherry Studio、LobeChat 及各类脚本等 generic OpenAI 客户端全部不发送这些 Header。

这些请求的官方 resolver 返回 `missing`，没有 `conversationKey`，由此产生三层空洞：

1. **三层会话亲和全部跳过**（组黏分组、账户黏账户、Key 黏指纹），全部流量按模式普通调度；策略路由的 round_robin / weighted 把同一逻辑会话的连续请求逐请求拆散，上游 prompt cache 命中率随之损失；
2. **审计会话串联不可用**：审计表 `session_id` 为 NULL，运维无法按会话精确串联一个逻辑对话的全部请求；
3. **来源身份退化为 IP 软桶**：统一来源标识阶梯（统一会话身份 §4）在官方会话与协议资源证据皆缺时回退 `ip_api_key_fallback`（`clientIp + apiKeyId`），现存消费方——来源级账号避让（传输失败面 `scheduleClientSourceAvoidanceFailure` 与流式换号面，含其探活 fence）——随之按 IP 维度共享状态；[请求级提前耗尽与负面缓存设计](请求级提前耗尽与负面缓存设计.md) §5 的 L2 负面缓存（待实施）同样预留了该回退。公司、校园等共享固定出口 IP 下，不同用户、不同会话的 generic 流量共用同一来源桶，互相连带误伤。

OpenAI 兼容协议是无状态的：客户端每轮重发全量上下文，`messages` 前缀是 append-only 的——system prompt 与首条 user 消息跨轮不变。这给出一个确定性派生面：对前缀锚点做哈希即可得到稳定的每会话键（与上游 prompt cache 的命中原理同构）。失效面恰好等于可接受面：压缩/截断改写前缀 → 指纹变更 → 视为新会话、亲和按既有语义重绑。

## 2. 目标与非目标

### 目标

1. 官方身份 `missing` 的入站请求，当 body 呈现可锚定的 `messages` 对话序列时，派生内容指纹身份：审计串联自首个请求可用，三层亲和自第二请求起可用。
2. 同一会话在压缩/截断发生前跨请求同码；锚点缺失或改写时身份失效，按新会话语义走既有降级路径（普通调度 → 成功重绑），不产生错黏。
3. 同开场（同 system + 同首条 user 消息）的不同会话自第二个请求起分岔（首条 assistant 回复作二次锚点），亲和绑定互不影响。
4. 恒定长度重放流量（批量脚本、冒烟测试）不建立、不消费亲和，行为与现状一致。
5. 来源标识阶梯新增 `content_fingerprint` 档：有内容锚点时来源身份定位到**会话级**，仅无锚点流量才回退 `ip_api_key_fallback`——现存来源级账号避让对有锚点流量升级为会话级作用域，共享出口 IP 不再因缺官方 Header 而在来源级状态上互相连带（§6）。
6. 官方身份路径逐字节不变：`resolved` / `invalid` / `conflict` 的行为与现状完全一致，指纹档只在官方证据缺位时存在。

### 非目标

1. 不改 Codex turn 避让子作用域与探活 fence 状态机的门控（仍由合法 `turn_id` 的 Codex 识别门控，指纹档不改变其入口，generic 会话不因持有指纹而进入 Codex turn/fence 专属状态机）；IP 级错误熔断与 IP 级账号回避（`gatewayclientip`，`clientIp` 直接入键）维持 IP 维度，不接入指纹档（§6.4）。指纹档不得进入 `gatewaysession.IdentityService.Resolve` 的官方裁决内部（该服务被 `codexSourceSessionAdapter` 共享），只在两个消费接缝以官方证据缺位后的后置档接入（§3）。
2. 不做模糊匹配，不设概率阈值：全程确定性等值判定，无 k-of-N、无置信度参数。
3. 不承诺压缩后身份延续；不承诺前缀逐字节相同的会话可区分（§8 精度上限）。
4. 不解析 body 中会话语义字段：`conversation`、`session_id`、`request.session_id`、`metadata.user_id` 等字段值仍不作身份来源（统一会话身份 §6 该条对字段值的排除不变）；本设计消费的是消息序列的内容锚点，不是字段值，锚点哈希不等于"请求 body 直接摘要"（§12 边界文档裁决句）。
5. v1 覆盖 `messages` 数组形态（OpenAI chat completions 为主；Anthropic messages 同形状同判据，但其顶层 `system` 字段 v1 不入锚，见 §4.1/§8）；Responses `input`、Gemini `contents` 形状不匹配判据，天然不激活，适配留待后续演进。
6. 不新增服务端会话存储、不新增 Redis 键空间、不改三层亲和键派生结构：指纹是无状态派生，唯一新增状态是进程内谱系 LRU 与请求级指纹记忆化（§4.3）。

## 3. 身份档位与来源阶梯

### 3.1 会话身份档位（preauth 会话身份接缝侧）

| 档位 | 激活条件 | SessionID（审计） | ConversationKey（亲和） |
| --- | --- | --- | --- |
| 官方身份 | resolver `resolved`（现状不变） | 原始 Header 值 | 现有派生 |
| **内容指纹档（本设计）** | `IdentityService.Resolve` 返回 `IdentityStatusMissing` 且锚点可用 | `cfp1-<临时指纹hex>`（首请求即有） | `cfp1c-<确认指纹hex>` 派生（过增长判别器才有） |
| `invalid` / `conflict` / resolver 出错 | 现状不变 | 无 | 无（fail-closed，不走指纹档；`Resolve` 返回 error 时与无身份同型折叠，不计算指纹） |

- 档位判定发生在官方 resolver 裁决**之后**：`IdentityStatusMissing` 是 adapter 侧指纹档的唯一入口。`invalid` / `conflict` 仍整体终止身份，维持现行 fail-closed 纪律。
- 接入点：`cmd/juhe-ai-gateway/chain_ports.go` 的 `sessionIdentityAdapter.ResolveGatewaySessionIdentity` 在 `Status == IdentityStatusMissing` 分支追加指纹档计算。初始解析（`preflight.go:533`）与最终 profile 重解析（`preflight.go:729`，仅 profile 变化时发生）各自按当时的 profile 计算，最终身份以最后一次为准——与组亲和 §4.5「身份以最终 profile 为准」的既有语义同构，复用其补查机制，不新增规则。
- `resolveSessionIdentityFromStrategy` 的 `strategy.ClientSource.SessionIdentity` 冻结身份优先路径保持不变。生产装配下 `clientStrategyAdapter`（`chain_ports.go:1706`）不映射 ClientSource，该路径当前不可达，生产全部请求经 `sessionIdentityAdapter` 解析；若未来接线，冻结身份请求不进入指纹档。
- 零额外解析：锚点抽取消费 `GatewayRequest.MaterializedParsedJSONObjectBody` 的已解析 JSON 对象（body 在 preflight 前已同步捕获解析，两次身份解析时点均可用）；body 非 JSON object、`messages` 非数组或元素无字符串 `role` 时无锚点，维持现状。

### 3.2 来源标识阶梯档位（公共来源标识层侧）

| 优先级 | sourceKind | 生成条件 |
| --- | --- | --- |
| 1 | `official_session` | 现状不变（画像适用官方会话且证据有效） |
| 2 | `protocol_resource` | Gemini 已存在 interaction resource（现状不变） |
| 3 | **`content_fingerprint`（本设计）** | 无前两档、非 `invalid` / `conflict`，且内容锚点可用。注意：generic 画像本就不适用官方会话（`profileMayUseOfficialSession` 为 false，阶梯内不调用官方 resolver），因此"非 invalid/conflict"涵盖「画像不适用官方会话」与「resolver missing」两种情形，无需为判定指纹档而新增 resolver 调用 |
| 4 | `ip_api_key_fallback` | 无任何锚点且已知 `clientIp`（现状不变，成为真正的最后手段） |

`invalid` / `conflict` 仍整体停发细粒度来源、不降级污染 IP 桶（现行纪律，对指纹档同样生效）。

## 4. 指纹算法定义

### 4.1 锚点抽取

对 `messages` 数组按顺序抽取三个锚点（角色词汇按 OpenAI chat completions；`developer` 视同 `system`）：

| 锚点 | 定义 |
| --- | --- |
| S | 前导连续 `system` / `developer` 消息（可 absent，取空；多条时逐条 canonical 后以 `0x00` 分隔依序拼接） |
| U1 | 第一条 `user` 消息 |
| A1 | 第一条 `assistant` 消息（含 `tool_calls`） |

- 锚点在数组中的**绝对位置**不参与判定，只看角色序：append-only 重发下其内容跨轮不变。
- 消息 canonical 化：`role + 0x00 + json.Marshal(content) + 0x00 + json.Marshal(tool_calls)`；消息无 `tool_calls` 字段时该段**整体省略**（不写 `null`）。`json.Marshal` 作用于解码后值（Go 编码 JSON 键序稳定），保证同一客户端跨轮重发逐字节同码。锚点哈希 `hashX = hex(sha256(canonicalX))`，对序列化字节增量写入，不额外物化全文。
- U1 不存在，或其 `content` 字段缺失 / 为 `null` / 序列化为空串 / 空数组：无指纹身份（维持现状）。S、A1 可缺省；A1 仅含 `tool_calls` 无文本 content 时照常参与 canonical（其 `tool_calls` 是会话分歧的强判别证据）。
- Anthropic messages 形状的顶层 `system` 字段 v1 **不读**（S 恒空）：同 U1 异 system 的会话在临时档/来源档同码概率上升，确认档有 A1 兜底。该精度损失显式接受（§8.5）；纳入顶层 system 属后续演进的加法修订。

### 4.2 两档指纹

```text
临时指纹 provisionalHex = hex(sha256(
  "cfp1"  0x00  apiKeyID  0x00  clientProfile  0x00
  hashS   0x00  hashU1 ))

确认指纹 confirmedHex  = hex(sha256(
  "cfp1c" 0x00  apiKeyID  0x00  clientProfile  0x00
  hashS   0x00  hashU1   0x00  hashA1 ))
```

- `apiKeyID` 与 `clientProfile` 入哈希：不同 API Key、不同检测画像的同内容会话互不可见。
- 锚点集**冻结规则**：确认指纹一经可计算，锚点集即冻结为 {S, U1, A1}；后续请求重算同一组锚点比对。不随消息数增长追加锚点（移动锚点会使码逐轮漂移，亲和必碎）。
- 失效语义：任一冻结锚点缺失、角色序错乱或 canonical 变更（压缩/截断/客户端改写）→ 该请求算出**不同的码**，等价于一个新会话；旧绑定不删除、不被错误消费，按各自 TTL 自然过期。身份"失效"不产生任何删除动作（三层亲和删除触发矩阵零新增）。

### 4.3 身份产出、记忆化与增长判别器

- **请求级记忆化（成本上界的关键规定）**：锚点抽取与两档指纹按 `clientProfile` 在请求内记忆化（挂在 `GatewayRequest` 的请求级缓存上），会话身份接缝与来源标识阶梯共享同一份计算。每请求**每个 profile 至多执行一次**锚点 canonical 化与哈希（`ClientStrategy.Resolve` 每请求执行两次、adapter 再取 1-2 次，均命中记忆化）。
- **审计 `SessionID`** = `"cfp1-" + provisionalHex`。只要锚点可用即产出，与增长判别无关——首个请求就具备审计串联。
- **亲和 `ConversationKey`** = `CreateGatewayConversationKey(scope, "content_fingerprint:v1", "cfp1c-" + confirmedHex)`（复用现有 canonicalizer 与 HMAC purpose，`scope` 携带 `systemAccountID + apiKeyID + secret`，与官方档同构）。产出受**谱系增长判别器**门控：
  - 进程内 LRU：键 = `confirmedHex`，值 = `{lastMessageCount, lastSeen}`；容量 10000 条、TTL 24h（与账户亲和 memory TTL 同量级），满员逐出最旧。
  - 判定：LRU 未命中（首见）或 `messages 数长度 > lastMessageCount`（严格增长）→ 产出确认档身份并更新记录；`长度 ≤ lastMessageCount` → 本次解析不产出确认档（按无键处理，走普通调度），不更新记录。
  - 更新口径（可实现表述）：每次身份解析（按 profile 记忆化后的产出点）至多产生一次 LRU 判定与更新；profile 不变的请求全生命周期恰一次；profile 变化的请求对初始/最终两个不同指纹键各至多一次，且**最终身份键的判定结果是本请求亲和消费的唯一依据**（与 §3.1「最终 profile 为准」一致）。
- 恒定长度重放（批量脚本，含带罐头 assistant 消息的多轮固定 payload）：长度永不严格增长 → 至多首见请求建立一次绑定、此后不消费亲和，候选池分布不受影响。
- 真实会话第二请求起长度必然严格增长（append-only 重发），判别器对正常会话零拦截。

## 5. 与三层亲和及审计的衔接

- 三层亲和零结构改动：确认档 `ConversationKey` 注入 `preflight` 既有消费点（账户 `SessionAffinity.ResolveKey`、组 `GroupAffinity.DeriveGroupAffinityKeyParts`、Key 指纹写回），HMAC purpose、TTL、删除触发矩阵全部沿用。
- 审计：`bindAuditSessionIdentity` 按现状消费 `SessionID`；指纹会话的 `session_id` = `cfp1-…`（非空、可按完整值精确查询、跨全部请求稳定），`session_client_type` = 检测画像（如 `generic_openai`），不新增审计枚举。同一逻辑会话含未过判别器的请求在内全部可串联。
- sticky 语义：首请求通常无 A1 → 无确认档 → 无亲和查询（与现状一致）；含预填 assistant 消息的首请求（few-shot、续写历史）首见即产出确认档，允许一次亲和查询与绑定写回（§9.12 断言）。第二请求起判别器放行、绑定经最终协议成功写回，第三请求起黏住生效。
- 同开场双会话：临时档同码只影响审计串联与来源档（混流，§8 已接受）；亲和在确认档分岔，各自绑定互不影响。

## 6. 来源标识阶梯接入（`content_fingerprint` sourceKind）

### 6.1 现状与问题

统一客户端来源标识（统一会话身份 §4）的阶梯今天只有三档：`official_session`、`protocol_resource`、`ip_api_key_fallback`。generic 客户端（无官方 Header）全部落入 IP 软桶，来源级状态按 `clientIp + apiKeyId` 共享。**现存消费方**：Codex turn 避让（Codex 门控）、可用性探活 fence、来源级账号避让（传输失败面 `chain_ports.go` 的 `scheduleClientSourceAvoidanceFailure` 与流式换号面 `scheduleStreamClientSourceAvoidance`，经 `ClientSourceAvoidanceStateKey` 以 clientSourceKey 为根键，generic 客户端现走 `ip_api_key_fallback` 作用域）。**待实施消费方**：L2 负面缓存（其 §5 已预留"完全无细粒度证据时才回退 `ip_api_key_fallback`"）。共享固定出口 IP（公司、校园）下，不同用户不同会话因"没有更好的身份"共用同一来源桶：避让状态连带、负面缓存跨用户误伤（同模板客户端发同内容请求时 `requestFingerprint` 相同）。

### 6.2 接入定义

阶梯插入 `content_fingerprint` 档（§3.2 优先级 3），来源键**复用既有实现**（下式为示意，实现必须走 `gatewayClientSourceHMAC`：domain `source:v1`、JSON 数组载体、base64url 摘要、`src_v1_` 前缀，不得新造 HMAC 布局）：

```text
clientSourceKey = HMAC-SHA256(
  JUHE_AI_SECRET,
  systemAccountId + apiKeyId + "content_fingerprint" + semanticNamespace + stableValue )   // 示意
```

- `stableValue` = **临时指纹 `provisionalHex`**：首请求即可用（确认档要等 A1 出现）、全会话稳定、与审计 `session_id` 同源。选临时而非确认指纹的理由：来源状态全部是短 TTL 软状态，同开场不同会话的过共享远窄于 IP 桶（不含 IP 维度，跨 NAT/出口天然隔离）；且 L2 缓存键还叠加 `requestFingerprint`（全量 body SHA-256），第二请求起 body 分岔即天然分键，实际粒度仍为会话级。
- `semanticNamespace` = `content_fingerprint:v1`，与亲和键 namespace 同值不同 purpose。
- 激活条件按 §3.2 阶梯口径（非 adapter 口径）；指纹计算消费 §4.3 的请求级记忆化，不重复哈希。
- 门控与纪律沿用：`invalid` / `conflict` 整体停发（含指纹档）；无锚点且已知 `clientIp` → `ip_api_key_fallback` 照旧。原始值不进键：`provisionalHex` 已是派生哈希，满足"原始 Header、resource ID 和 IP 都不写入 key"的现行约束。
- 生成位置在公共来源标识层（`ResolveGatewayClientSourceIdentity` 的阶梯判定处，各 profile 共用同一输出契约），不在 `IdentityService.Resolve` 内部（§2 非目标 1）。

### 6.3 收益落点与作用域变化裁决

- **现存来源级账号避让（传输失败面 + 流式换号面，含其探活）对有锚点流量自动升级为会话级作用域**——这是本设计的显式裁决而非副作用：避让状态不再跨会话连带，NAT 下同模板同事互不牵连。代价有界：路径级故障下每个会话各"重新发现"一次故障账户（短 TTL 软避让，每会话每故障期至多多一次试错），而路径级共享语义由不受影响的两层承担（§6.4）。
- L2 负面缓存（待实施）对 generic 客户端自动升级为会话级作用域：同模板同事不再共用负面缓存条目。
- 未来任何来源级消费者默认获得会话级身份，`ip_api_key_fallback` 从"generic 客户端的常态"退为"body 不可解析流量的最后手段"。

### 6.4 明确不接入方

1. **IP 级错误熔断与 IP 级账号回避维持 IP 维度**：IP 熔断的触发类是"本地可确认失败"（认证前 token spray、认证后本地校验失败族）——这些请求要么没有可解析 body（无锚点，指纹天然不可得，正是 IP 兜底存在的原因），要么防护语义要求不可轮换维度（指纹可被攻击者逐请求免费轮换，会话级熔断可被绕过）。IP 级账号回避（`gatewayclientip`，`clientIp` 直接入键）承担传输失败的**网络路径共享**语义（同出口同路径），与 clientSource 侧避让的会话化形成分层：路径级故障由 IP 层共享避让 + 账户级健康机制（主探测/circuit）治理，会话级特有失败由会话层精确避让，两层互不替代。NAT 下熔断连带的残余风险由该设计既有手段治理（高阈值、短 TTL、成功恢复）；若未来误杀证据充分，另立"指纹优先、IP 升级"的阶梯设计，不在本文范围。
2. **Codex turn 避让与探活 fence**：门控与状态机零改动，仍由合法 `turn_id` 的 Codex 识别门控。

## 7. 隔离、安全与观测边界

1. **隔离维度**：临时/确认指纹哈希输入含 `apiKeyID + clientProfile`，跨 Key、跨画像不同码；`ConversationKey` 与 `clientSourceKey` 再经现有 HMAC（`JUHE_AI_SECRET`）派生，多实例部署沿用 `JUHE_AI_SECRET` 一致性既有约束。
2. **不可逆**：审计与 Redis/内存键只出现 sha256/HMAC 派生十六进制串；锚点原文、canonical 字节、块哈希中间值不进审计、日志或任何持久化。诊断日志（允许的诊断能力）只记锚点存在性、角色与字节数量级。
3. **伪造面**：客户端可故意构造相同前缀，但只能把自己 Key 内的请求黏到同一账户、共享自己的来源状态——软调度偏好 + 硬过滤照常，无跨租户面；伪造 `cfp1-…` 审计 id 不能伪造亲和键与来源键（HMAC secret 保护）。轮换前缀可轮换指纹，但换来的只是"放弃自己的黏性与缓存收益"，不受惩罚也不得利。
4. **撞码后果（语义碰撞，非哈希碰撞）**：同 Key 同画像下 S+U1 相同的两个会话临时档同码——审计串联混流、来源档过共享（§8 已接受）；亲和自确认档（A1）起分岔，实际逐字节相同概率趋近于零。sha256 全量哈希下哈希碰撞可忽略，不设碰撞处理逻辑。
5. **多实例边界**：谱系 LRU 是进程本地状态（与缓存驱动无关，Redis 驱动下同样进程本地）。当前生产形态为国内单机单实例（判别精确）；多实例下判别退化为每实例 best-effort（批量重放可能在每实例首见时各建一次绑定，同键 CAS 收敛，无正确性影响）。若未来多实例需要精确判别，另立设计，不在本文范围。

## 8. 精度上限（明确不做）

1. 全锚点逐字节相同的两个会话（同一会话的重放）在内容上不可区分——任何不依赖客户端 ID 的算法都分不开；共享亲和绑定、共享审计 id 与来源档过共享是**正确行为**（且共享上游 prompt cache 受益），不作为缺陷。
2. 压缩 / 截断后身份必然更换；旧绑定靠 TTL 过期，不主动清理。
3. 滚动窗口客户端（丢弃最老消息）最终会丢掉锚点 → 身份消失，回退现状普通调度（来源档回退 IP 软桶，与现状一致）。
4. 无概率阈值、无置信度参数；「识别为同一会话」只有确定性同码一种含义。
5. Anthropic 顶层 `system` 字段不入锚（§4.1）：异 system 同 U1 的 Anthropic 形状会话在临时档/来源档同码概率上升，确认档有 A1 兜底。

## 9. 验收标准

1. 无 Header 多轮会话（chat completions，首请求不含 assistant 消息）：首请求亲和查询为零（与现状逐字节一致）；第二请求起产出确认档身份，最终协议成功写回绑定；第三请求起三层黏住生效（mock 上游按账户命中数为 oracle）。
2. 同 S+U1 的两个会话：确认档 `ConversationKey` 不同，各自绑定互不影响；并发交错下写回互不覆盖。
3. 审计：指纹会话全部请求（含未过判别器请求）`session_id` 相同且可按完整值精确查询串联；`session_client_type` 为检测画像。
4. 恒定长度重放 100 次：除首见外亲和查询与绑定写回为零，命中分布符合纯模式行为。
5. 改写 S 或 U1（模拟压缩）：身份更换，按模式重选并重绑；旧绑定不被新会话消费。
6. 官方身份三态回归：`resolved` / `invalid` / `conflict` 及 resolver 出错请求的指纹档调用次数为零，行为与现状逐字节一致；`x-juhe-client-profile` 自报 + 无会话 Header 的请求进入指纹档。
7. 固定测试向量 ≥2 组：锚点 canonical 化（含多条 system 分隔、tool_calls 省略段、tool_calls-only 消息）与两档指纹对输入字段敏感（改 `apiKeyID` / `clientProfile` / 任一锚点字节 → 码变）。
8. 判别器与记忆化矩阵：首见产出 / 严格增长产出 / 恒定拦截 / 缩减拦截；每次身份解析至多一次 LRU 判定更新，profile 不变的请求全生命周期恰一次（请求级记忆化 spy 断言：每请求每 profile 锚点哈希恰一次）。
9. `IdentityService.Resolve` 内部与 Codex turn 避让、探活 fence 门控零改动断言（来源级状态机入口不受指纹档影响）。
10. 来源阶梯矩阵：`official_session` / `protocol_resource` 存在时不生成 `content_fingerprint`；generic 画像 + 锚点可用 → 来源键 sourceKind 为 `content_fingerprint` 且输入不含 `clientIp`；无锚点 + 有 IP → `ip_api_key_fallback` 照旧；`invalid` / `conflict` → 无任何来源键。
11. NAT 隔离与避让分层断言：同 `clientIp + apiKeyId` 下两个不同锚点会话的 `clientSourceKey` 与来源避让状态键互不连带，同会话避让仍生效；IP 级账号回避与 IP 错误熔断行为全量回归不变。
12. 预填 A1 首请求（few-shot / 续写历史）：亲和查询恰一次，最终协议成功后绑定写回恰一次。

## 10. 验证方式

- **单元测试（Mock 优先）**：锚点抽取（角色序、developer 视同 system、多条 system 分隔、tool_calls canonical、空 content 边界、tool_calls-only A1、Anthropic 顶层 system 不读）、两档指纹固定向量、判别器 LRU（容量/TTL/逐出）、请求级记忆化（每请求每 profile 一次）、`sessionIdentityAdapter` 档位矩阵（官方三态 + 出错 × 锚点可用性 × 判别器结果）、来源阶梯矩阵（验收 10 全行）、审计绑定值形状。
- **集成**：fullchain 夹具 mock 无 Header 上游客户端，覆盖验收 1-6、11 与 12；复跑既有账户亲和、Key 黏性、组亲和、IP 熔断/IP 回避验收证明官方与 IP 路径零回归。
- **回归**：`gatewaysession`、`gatewaypreauth`、cmd 包既有会话身份/亲和测试全绿；`sessionIdentityAdapter` 在官方 `resolved` 路径的行为快照不变。

## 11. 风险与注意事项

- **锚点哈希成本**：U1 含大体积内容（如 base64 图）时为 sha256 量级（毫秒级，受既有入站 body 上限约束）；请求级记忆化保证**每请求每 profile 至多一次**锚点哈希（§4.3），不随链上解析点数量倍增。增量哈希不物化全文，热路径无新增解析；不在热路径对锚点内容做任何截断（截断引入新的碰撞面且破坏确定性）。
- **profile 重解析抖动**：初始/最终 profile 不一致时指纹随 `clientProfile` 输入变化一次，与组亲和「最终 profile 为准、失配重查一次」的既有语义同构，复用其预算（每请求组亲和 GET ≤2 不变）。
- **来源避让会话化的试错成本**：路径级故障下有锚点会话各自多一次试错（§6.3）；由 IP 级账号回避 + 账户健康机制兜底，集成验收 11 断言两层分层成立。
- **`SessionID` 消费面核查**：实施时审计全部 `SessionIdentity.SessionID` 消费点，确认指纹档派生值在审计绑定之外无其他语义依赖（发现即回本设计补充契约）。
- **三值口径**：审计 `cfp1-…`、亲和 `cfp1c-…`、来源档 stableValue `provisionalHex`（无前缀裸哈希）是三个消费面的派生值，代码评审与排障时易混淆；固定向量测试与本文 §4.3/§6.2 为唯一口径。
- **来源档过共享**：临时指纹不含 A1，同开场会话在来源级短 TTL 软状态上过共享（L2 因叠加 `requestFingerprint` 实际分键）；相比 IP 桶（跨用户跨会话全共享）已是数量级收窄，进一步收窄无明确收益。
- **前缀统一模板客户端**：判别力主要来自 U1（及确认档 A1）；模板客户端是本设计收益最大群体，其残余撞码后果已由 §7.4 / §8 接受。
