# 上游流式失败帧拦截设计

> 状态：已实施（2026-10-18）。修复生产事故 trace `40c59055-4f64-4dd0-9e23-0a5d9a2dc89b` 暴露的缺口：上游带内失败帧被当作正常内容透传给客户端后才中断。本文是网关流式失败帧识别规则的权威契约。

## 1. 背景与生产事故

2026-10-17 23:04，生产网关处理 `/v1/chat/completions`（trace `40c59055-4f64-4dd0-9e23-0a5d9a2dc89b`）：

1. 上游 `deepseek-v4.1-flash` 返回 HTTP 200 并正常流式输出，网关向客户端提交响应后转发 302 个 SSE 事件（66.7 KB，正处于 tool_call 参数流中段）。
2. 上游随后发送带内失败帧 `data: {"error":{"message":"upstream sent an error event","type":"upstream_error"}}`——**无 `event:` 行、JSON 无 `type` 字段，仅顶层挂 `error` 对象**。
3. 网关流式失败判定（`gatewayopenai.ClassifyStreamEvent`）不识别该形态，此帧被当作正常内容**透传给客户端**（下游审计 blob 尾部含该帧原文）。
4. 下一帧 `event: error`（`upstream_stream_truncated`）才触发失败判定，网关中断连接。客户端在已收到上游错误载荷的情况下收到连接中断，其自身重试/恢复机制无法将该失败归类为可恢复形态，回合直接终止（该 API key 直至 36 分钟后才有下一个请求）。

审计取证：`juhe_dataset.audit_log_attempts` 记录 `error_phase=stream`、`attempt_count=1`；上游响应 blob 完整保留事故帧。

## 2. 目标与非目标

### 目标

- 上游以带内帧表达的失败（顶层 `error` 对象形态），网关必须在**写入下游之前**识别并拦截：客户端永不收到上游错误载荷帧。
- 拦截后走既有失败路径，不新增机制：提交前 → 交回调度层服务端重试/换号；提交后 → 一律真·网络级断开（2026-10-23 契约收口：原「精确客户端补发脱敏失败终态」的 signaled 处置已删除，全部客户端与 generic 一致）。
- 三协议（OpenAI-compatible、Anthropic、Gemini）同规则修复。取证确认 Anthropic、Gemini 存在同形漏判，且顶层 `{"error":{...}}` 正是 Gemini streamGenerate 的标准流式错误形态。

### 非目标

- 不改变提交前失败收尾路径本身（pre-commit 缓冲重试维持现状）；提交后失败收尾自 2026-10-23 契约收口起统一为真·网络级断开（原 `signaled` 处置删除，`interrupted` 即 Hijack 底层 TCP 连接并直接 Close 的网络级断开）。
- 不改变 Codex `passthroughUpstreamFailure` 原样透传契约（该模式下 `interpretedProtocolFailure` 恒 false，失败帧按契约原样转发）。
- 不解决"提交后跨 transport chunk 拆分事件"的头部字节泄漏（见 §5.1，对现有命名 `event: error` 帧同样存在，非本设计引入）。
- 不做任何客户端定制：判定规则只描述上游协议事实，代码不出现任何客户端身份。

## 3. 失败判定规则契约

原则：**只放宽各协议流式检查器的失败判定条件，不改动被策略语义帧提取共用的提取函数**（`gatewayopenai.extractStreamEventError`、`gatewayanthropic.ExtractStreamEventError`、`gatewaygemini.ExtractStreamEventError` 均被拦截器语义帧提取共用，放宽会波及策略检查路径的观察行为）。

### 3.1 OpenAI-compatible（`gatewayopenai/sseparse.go` `ClassifyStreamEvent`）

`failed` 判定在现有六条件（`EventType`/`EventName` ∈ `response.failed`/`image_generation.failed`/`error`）基础上增加：

```go
failed := <现有六条件> ||
    (event.Data != nil && extractStreamEventError(event.Data) != nil)
```

- 与同包 `IsStreamFailureEvent` 的负载判定对齐，并保留 `ClassifyStreamEvent` 特有的 `image_generation.failed`。
- `extractStreamEventError` 的既有豁免（`type == "response.mcp_call.failed"` 返回 nil）随之继承。
- `ErrorCode`/`ErrorMessage` 仍仅在 `failed` 时从解析结果提取（现有逻辑不变）。
- 超大事件路径（`classifyOversizedStreamEvent`）不适用（事件超限不解析 JSON，属结构性限制，见 §5.2）。

### 3.2 Anthropic（`gatewayanthropic/streaminspection.go` 检查器失败判定）

现有判定 `failed := ExtractStreamEventError(data, eventType, eventName) != nil`，其门条件为 `eventType=="error" || eventName=="error" || data["type"]=="error"`。在该判定处增加一个独立条件：

```go
failed := ExtractStreamEventError(...) != nil || topLevelErrorObjectPresent(data)
```

其中 `topLevelErrorObjectPresent(data)` 表示 `data["error"]` 为 JSON 对象。共享的 `ExtractStreamEventError`（及依赖它的语义帧提取）不动。Anthropic 协议不涉及 `response.mcp_call.failed` 形态，不新增豁免。

### 3.3 Gemini（`gatewaygemini/streaminspection.go` 检查器失败判定）

与 3.2 同构：在检查器失败判定处增加 `data["error"]` 为 JSON 对象的独立条件，共享 `ExtractStreamEventError` 不动，取值优先级（`interaction.error` > `data["error"]` > 整体）维持现状。

### 3.4 语义锁定

| 输入形态 | 判定 |
| --- | --- |
| `data: {"error":{"code":...,"message":...}}`（无 event 名、无 type） | **失败**（本次修复目标，DeepSeek 事故形态） |
| `data: {"error":{}}`（空对象） | 失败（空错误对象仍是上游失败信号） |
| `data: {"error":null}` / `data: {"error":"string"}` | 非失败（仅对象形态命中） |
| `data: {"type":"response.mcp_call.failed","error":{...}}` | 非失败（既有豁免维持） |
| `event: error` / `data: {"type":"error",...}` | 失败（现有行为不变） |
| 正常 chat chunk（含 `choices`，无 `error` 键） | 非失败（不受影响） |
| 非法 JSON（DataParseError） | 非失败（现有行为不变） |
| 判定失败的帧按各协议既有失败帧语义收尾（OpenAI 视为 terminal，summary `CanEndStream=true`；Anthropic/Gemini 与各自命名 error 帧行为一致） | 与命名失败帧行为一致 |

## 4. 拦截后的管道行为（现状确认，不新增机制）

- 判定时序：拦截器挂载时完整 SSE 事件经事件重组后才进入主循环；inspector 在事件完成（空行）时分类；主循环在写下游之前检查 `interpretedProtocolFailure`（`gatewayresponse/pipe.go:309` 先于 `:315`）。事件粒度上分类恒先于写入。
- 提交前失败：`TakeStreamPreCommitChunks` 丢弃缓冲，结果交回调度层决定服务端重试/换号，日志 `gateway_stream_failure_before_downstream_commit`。
- 提交后失败：全部客户端（精确与 generic 一致）`interrupted` = 真·网络级断开——网关 Hijack 底层 TCP 连接并直接 Close（无 chunked 终止帧），不发任何错误载荷，客户端 HTTP 栈感知为网络层中断（unexpected EOF），由客户端以自身网络错误重试机制重发；2026-10-23 契约收口删除原精确客户端 `signaled`（补发脱敏失败终态）处置。日志相应为 `gateway_stream_failure_after_downstream_commit_*`。
- `passthroughUpstreamFailure`（Codex cyber_policy）：透传语义不变。
- 账户健康语义不变：`FailedReceived` 置位提前一帧，账户失败资格仍经同一 `HandleStreamFailure` 回调。

### 桥接转换流覆盖（终审补充）

检查器按**上游账户协议**选择、管道消费的是**转换后客户端协议形态**字节（`gatewaydispatch/upstreamattempts.go` → `chain_bridge_response.go`），因此本设计对桥接流的效果是方向性的：

- **Anthropic/Gemini 上游 → chat 客户端**：转换层把上游错误改写为 chat 形态顶层 `{"error":{...}}` 帧 + `[DONE]`（`FailAnthropicChatStream` / `ProcessAnthropicEventAsChat` / gemini 分支）。修复前该转换后错误载荷会透传给客户端并以 `[DONE]` 按成功收尾；修复后由本设计新增判定拦截——这是本设计额外收敛的一个真实桥接泄漏面，失败归因仍为上游账户。
- **chat 上游 → anthropic/gemini/responses 客户端**：三个转换器的错误门只认命名 `event: error`/`type:"error"`，DeepSeek 形态（无名无 type）不命中，帧被状态机吞掉、EOF 时补发合成命名错误事件——修复前后行为完全相同，事故形态到不了检查器。该方向客户端拿不到真实失败原因是既有行为，超出本契约范围。

### W7 桥接转换层边界（2026-10-23 契约收口补充）

chat 上游 → 其他协议客户端方向的桥接转换层（`chain_bridge_response.go`）在 EOF 时补发合成错误事件、在目标协议内收尾的机制**不属于本契约**，也不受提交后「真·网络级断开」收口影响：协议桥接必须在目标协议内收尾，该机制保留。提交后网络级断开的契约只适用于非桥接的原生协议流管道。

## 5. 边界与已知限制

1. **提交后跨 chunk 拆分**：提交后管道无缓冲，若失败事件的字节被上游拆在多个 transport chunk 中，前半部分字节会先于事件级分类写下游。该边界对现有命名 `event: error` 帧同样存在，本设计不扩大提交后转发时序去解决；单事件完整到达（普遍情况）完全覆盖。
2. **超大事件**：事件超过 inspector 解析上限被跳过解析（`Skipped`）时不做逐事件分类，按原样转发收尾（现状）。
3. **非流式路径**不变：`gatewayopenai.InspectResponse` 等缓冲响应判定与本设计无关。
4. **网关自产帧**（如 `juhe_ai.keepalive`）无 `error` 键，不受影响。
5. **成功终态后的 error 对象帧**（行为变化点，与命名帧先例一致）：`[DONE]` 等成功终态已写出后又到达顶层 error 对象帧的，修复后按 `gateway_stream_failed_after_terminal` 失败收尾（修复前该帧会被当内容转发后按成功收尾）。与既有命名 `event: error` 帧在同位置的语义一致。
6. **生产消费方全景封闭**（终审核验）：`ClassifyStreamEvent` 唯一生产消费方是 `gatewayopenai/inspector.go`；modelcheckprobe/accountprobe/chat/gatewayobs/媒体链路均不消费该分类器，无契约外行为变化。error 对象帧的事件类型名仍计为 `"message"`（`EventType`/`EventName` 均空），全仓无"Failed 帧必为 error 类型名"的依赖。

## 6. 验收标准

1. 判定单测：OpenAI 覆盖 §3.4 语义锁定的全部形态；Anthropic/Gemini 覆盖本次新增的顶层 error 对象命中形态与各自标准错误形态回归（三处为同一惯用法实现，边界形态由 OpenAI 侧锚定）。测试绿。
2. `gatewayopenai`、`gatewayanthropic`、`gatewaygemini`、`gatewayresponse` 包测试绿。
3. `cmd/juhe-ai-gateway` acceptance 全链测试绿。
4. 独立复审无 blocker。
5. 生产行为可观察验证口径：同类上游故障发生时，网关日志为 `gateway_stream_failure_*` 且 attempt 记录 `error_phase=stream`；下游响应审计 blob 不再含上游错误原文帧。
6. 提交后失败收口验证（2026-10-23 契约收口）：拦截命中且已越过提交边界时，全部客户端（精确与 generic 一致）收到网络级断开（Hijack + Close，无 chunked 终止帧、无补发失败终态）；提交前拦截仍走缓冲丢弃 + 服务端重试/换号。
