# 响应语义检查管线设计

> 设计状态：OpenAI v1 Chat / Responses 与 Anthropic native Messages 核心链路已落地；后续其他 native 协议继续按本文扩展。
> 本文定义返回侧统一响应语义检查能力，覆盖 OpenAI v1 Chat / Responses、Anthropic native Messages、SSE / JSON。当前不保留旧 SSE 拦截器、旧策略表或旧账户字段，不做运行时兼容，也不迁移历史配置。账户专属规则使用账户凭据内新的 `response_inspection_rules` 字段配置。

## 1. 背景

仅按 SSE 事件处理的旧式返回检查不能覆盖这些 OpenAI v1 场景：

- 客户端请求非流式，上游按 `application/json` 返回完整 Chat Completions 响应。
- 客户端请求非流式，网关即使尝试让上游流式，上游仍强制返回 JSON。
- 客户端请求流式，但上游异常返回 JSON 成功体或 JSON 错误体。
- 同一类污染内容在 OpenAI v1 Chat JSON、Chat SSE、Responses JSON、Responses SSE 中以不同字段出现。

上游 HTTP 非 `2xx` 不是响应检查策略的配置入口；它仍归账户错误处理、同账号确认和切号流水线处理。所有候选账号都失败后，如果当前请求命中 Codex Responses SSE profile，网关可在最终下游渲染阶段写 `response.failed/upstream_retryable_error` SSE，防止 Codex 客户端断开；这属于客户端最终兜底，不替代响应语义检查规则。

因此，问题不应被定义为“是否强制客户端或上游使用流式”。真正需要稳定处理的是：上游响应表达了什么语义、是否出现可见输出污染、协议失败或异常完成状态。

## 2. 目标

- 不要求客户端必须开启 `stream`。OpenAI v1 客户端可以继续请求 Chat JSON、Chat SSE、Responses JSON 或 Responses SSE。
- 不把“强制上游流式”作为唯一拦截手段。它只能是优化传输策略，不能作为检查能力边界。
- 将上游返回解析为统一响应语义帧，再执行策略匹配和处置。
- 同一条策略尽量同时覆盖同一协议内不同传输形态的同类输出文本、错误码和完成状态；当前已覆盖 OpenAI v1 Chat / Responses 与 Anthropic native Messages 的 SSE / JSON。
- 在尚未向下游写出任何内容时，命中可重试策略可以服务端换账号重试。
- 已经向下游写出可见内容后，仍禁止服务端静默拼接第二条上游响应；只能按客户端能力返回失败、结束连接或让客户端自行重试。
- 保持轻量边界：先覆盖文本类对话响应和结构化错误，不提前实现全协议、全模态、全字段重写器。

## 3. 非目标

- 不实现通用 WAF，不扫描任意 HTTP 响应、二进制文件、图片、音频、视频或未知协议正文。
- 不为规则匹配缓存无限完整响应体，不在热路径做全量正文搜索。
- 不把 Codex 专用 `upstream_retryable_error` 语义扩散给普通 OpenAI-compatible 客户端。
- 不把请求客户端、供应商能力和账户运行态混成同一个判断。请求客户端只作为策略适用范围维度；语义命中仍必须来自输出文本、错误码、错误类型、错误文案、完成状态、JSON 路径或 SSE 原文等响应字段。
- 不把“删除广告文本并拼回一个看似正常的回答”作为默认策略；对完整回答污染优先按失败或重试处理，避免伪造模型输出。
- 不兼容旧 `stream_intercept_policies`、旧账户 `stream_intercept_rules` 或旧前端 SSE 专项配置；当前以管理端响应检查策略和账户级 `response_inspection_rules` 作为配置入口。

## 4. 三层解耦

响应语义检查必须把三个维度拆开：

| 维度 | 示例 | 职责 |
| --- | --- | --- |
| 客户端协议 | OpenAI v1 Chat JSON、Chat SSE、Responses JSON、Responses SSE；后续其他协议自己的 native 形态 | 决定最终返回给客户端的格式和错误形态 |
| 上游传输 | 上游 JSON、上游 SSE、上游被强制流式、上游忽略流式要求 | 决定如何读取和解析上游响应 |
| 响应语义 | 可见文本、错误、完成状态、usage、工具调用摘要 | 决定策略是否命中以及能否重试 |

响应检查策略还可以带一个运行时适用范围维度：

| 维度 | 示例 | 职责 |
| --- | --- | --- |
| `clientProfiles` | `codex`、`generic_openai`、`generic_anthropic`、`claude_code`、`gemini_cli` | 描述当前下游请求客户端如何解释失败事件和错误码；协议错误事件必须由精确客户端画像和下游协议共同决定，`upstream_retryable_error` 只是候选耗尽后的稳定网关码，不是 Codex 专属上游错误分类 |

这个维度不能单独构成命中条件。创建或更新策略时仍必须填写至少一个响应语义正向条件，避免一条只选择“Codex”的规则拦截所有 Codex 响应。

目标流水线：

```text
上游响应
  -> 传输解码器
  -> 协议适配器
  -> 统一响应语义帧
  -> 响应检查策略
  -> 下游渲染器
  -> 客户端原协议
```

传输解码器负责把上游 `content-encoding: gzip` / `br` / `deflate` 响应体先解码成协议原文，再交给 JSON 或 SSE 适配器；下游 header 复制必须过滤 `content-encoding`、`content-length` 和 `transfer-encoding`。压缩体损坏或解码失败属于上游读取异常，未写下游时走服务端重试 / 切号，账号耗尽后再按客户端画像返回统一兜底错误。

请求侧仍按 [请求处理分层设计](请求处理分层设计.md) 维护；本文只描述上游返回后的响应侧处理。

## 5. 协议与供应商分层

`Chat JSON`、`Chat SSE`、`Responses JSON` 和 `Responses SSE` 是 OpenAI v1 协议下的端点族和传输形态，不是所有供应商天然支持的通用协议。响应语义检查的“通用”只存在于语义帧和策略执行核心，不存在于具体上游字段路径。

分层规则：

| 层级 | 归属 | 示例 | 响应检查职责 |
| --- | --- | --- | --- |
| 语义核心 | 跨协议 | `output_text_delta`、`error`、`usage`、`completed` | 定义统一帧、策略匹配、动作展开、审计字段 |
| 协议适配器 | 协议层 | `openai/v1`、后续 `anthropic`、`gemini` 等 | 把该协议自己的 JSON / SSE / stream 事件解析为统一语义帧 |
| 端点族 | 协议层 | OpenAI v1 `chat_completions`、`responses`；Anthropic native `messages` | 决定哪些字段能抽取输出文本、错误、完成状态和 usage |
| 供应商协议档案 | 供应商 + 协议版本 | `profile_gpt_openai_v1`、后续某供应商的 OpenAI-compatible 档案或 native 档案 | 决定某个供应商账号实际走哪个协议适配器 |
| 供应商策略 | 供应商层 | GPT、DeepSeek、GLM、Kimi 等局部中转文案或私有错误码 | 只表达该供应商在所选协议档案下的局部差异 |

供应商不能直接决定协议语义。DeepSeek、GLM、Kimi 或其他供应商如果通过 OpenAI-compatible `/v1/chat/completions` 接入，就应使用 OpenAI v1 协议适配器，并在供应商层补局部规则；如果未来接入它们的原生协议，则必须新增对应协议适配器和端点族，不能复用 OpenAI v1 的 Chat / Responses 字段路径。Claude / Anthropic native 这类非 OpenAI v1 协议同理，应通过自己的协议适配器映射到统一语义帧；只有在某个上游明确提供 OpenAI-compatible 包装入口时，才落到 OpenAI v1 档案。

DeepSeek 当前只接入 `profile_deepseek_openai_v1`，响应侧按 OpenAI v1 Chat Completions 适配器解析，再由 DeepSeek 供应商层补 `reasoning_content`、`prompt_cache_hit_tokens` / `prompt_cache_miss_tokens`、`finish_reason = insufficient_system_resource`、SSE keep-alive comment 和非流式空行保活等差异。DeepSeek 不新增 Anthropic Messages 适配器，也不把 Anthropic-compatible surface 作为当前目标。

## 6. 统一响应语义帧

当前只抽象足够支撑污染检查、失败识别、usage 统计和安全重试的轻量帧：

| 语义帧 | 典型来源 | 用途 |
| --- | --- | --- |
| `output_text_delta` | Chat SSE `choices[].delta.content`、Responses SSE `response.output_text.delta`、Anthropic SSE `content_block_delta.delta.text` | 流式可见文本增量检查 |
| `output_text_done` | Chat JSON `choices[].message.content`、Responses JSON `output_text` / `output[].content[].text`、Responses SSE done/completed、Anthropic JSON `content[].text` | 非流式完整文本检查和最终输出摘要 |
| `error` | SSE `response.failed` / `event:error` / `data.error`、JSON `error`、Responses `response.error`、Anthropic JSON `{type:"error"}` 或 SSE `event:error` | 统一错误码、错误类型和错误文案检查 |
| `completed` | Chat `finish_reason`、Responses `status` / completed event、Anthropic `stop_reason` / `message_stop` | 判断正常完成、异常完成和可结束流 |
| `usage` | JSON `usage`、SSE usage event 或 completed event、Anthropic `usage` / `message_delta.usage` | 使用记录和成本统计 |
| `raw_json_path` | 原始协议 JSON 或 SSE data JSON；OpenAI v1 第一阶段是 Chat / Responses JSON | 保留少量结构化兜底匹配，不替代语义字段 |

工具调用、图片、音频、文件等复杂输出第一阶段只保留轻量结构摘要和完成状态，不做关键词扫描。后续确需处理工具调用污染时，应新增专门语义帧，不能把工具参数当普通文本全文扫描。

DeepSeek 的 `choices[].message.reasoning_content` / `choices[].delta.reasoning_content` 可以进入推理内容摘要或审计扩展帧，但不能拼进普通 `output_text_delta` / `output_text_done`。`finish_reason = insufficient_system_resource` 应映射为异常完成状态或供应商诊断字段，由策略决定观察、重试或告警；它不是 HTTP 非 `2xx` 错误，也不能直接写账号持久状态。

## 7. 协议适配器

第一阶段适配器范围只覆盖 OpenAI v1 对话类端点。这里的 Chat / Responses 是 OpenAI v1 端点族；其他原生协议必须另建适配器。

| 上游响应 | 适配器责任 |
| --- | --- |
| `/v1/chat/completions` + JSON | 读取有界 JSON，抽取 `choices[].message.content`、`choices[].finish_reason`、`usage` 和顶层错误 |
| `/v1/chat/completions` + SSE | 按完整 SSE event 增量解析，抽取 `choices[].delta.content`、`finish_reason`、usage 和错误事件 |
| `/v1/responses` + JSON | 读取有界 JSON，抽取 `output_text`、`output[].content[].text`、`status`、`usage` 和 `error` |
| `/v1/responses` + SSE | 按完整 SSE event 增量解析，抽取 `response.output_text.delta`、`response.completed`、`response.failed`、usage 和错误 |
| `/v1/messages` + JSON | 读取有界 JSON，抽取 Anthropic `content[].text`、`content[].tool_use`、`content[].thinking`、`stop_reason`、`usage` 和顶层错误 |
| `/v1/messages` + SSE | 按完整 SSE event 增量解析，抽取 Anthropic `message_start`、`content_block_*`、`message_delta.usage`、`message_stop`、`ping` 和 `error` |

适配器只负责把协议差异转换为语义帧，不决定是否切号、不写账号状态、不判断客户端是否支持专用重试码。

DeepSeek OpenAI-compatible Chat Completions 复用上表 Chat 适配器，但必须满足：

- SSE comment / keep-alive 事件只刷新传输活跃时间，不产生文本、错误、完成或 usage 帧。
- 非流式 JSON 聚合容忍响应体中的空行保活，最终仍按有界 JSON 解析。
- `choices[].delta.reasoning_content` 和 `choices[].message.reasoning_content` 进入 DeepSeek 供应商扩展帧或审计摘要，不进入普通可见文本匹配。
- `usage.prompt_cache_hit_tokens` 和 `usage.prompt_cache_miss_tokens` 进入 DeepSeek usage 扩展解析，不作为所有 OpenAI-compatible 供应商的通用字段。
- `finish_reason = insufficient_system_resource` 进入完成状态帧和供应商诊断，是否重试由策略和下游写出边界决定。

Anthropic Messages 适配器还必须遵守：

- `message_delta.usage` 是累计值，不能按 delta 累加。
- `text_delta`、`input_json_delta`、`thinking_delta` 和 `signature_delta` 都是有状态输出，是否可见由下游渲染器和安全策略决定；适配器只产出语义帧和审计摘要。
- `event:error`、缺少 `message_stop`、上游 EOF 或流式中断只表示本次上游 attempt 失败，后续账号状态仍交给统一错误流水线确认。
- HTTP 状态码、Anthropic `error.type` 和错误文案只进入语义帧、审计和账户错误处理策略输入，不能在适配器里硬编码账号状态。

后续新增协议适配器时必须先定义：

- 协议代码和协议版本。
- 端点族，例如 native messages、generateContent 或其他协议自己的对话端点。
- JSON 与流式传输中可抽取的输出文本、错误、完成状态和 usage 字段。
- 是否存在可安全丢弃的独立事件；如果不存在，不能复用 `drop_event`。
- 与客户端协议的渲染关系：是否能原样返回、是否需要聚合、是否支持客户端重试事件。

## 8. 策略模型

新版本只保留“响应检查策略”。策略按协议层和供应商层合并：

- 协议层：某个协议的通用语义，例如 OpenAI v1 的 `response.failed`、JSON `error`、异常完成状态，或 Anthropic native 的 JSON `error` / SSE `event:error`；其他协议不得直接复用 OpenAI v1 字段规则。
- 供应商层：GPT、Anthropic、DeepSeek 或其他供应商在所选协议档案下的局部污染文案和私有错误码。
- 账户层：AI 账户编辑页保存当前账号专属 `response_inspection_rules`，用于处理单个账号或中转的广告污染、私有错误码和异常响应形态；运行时按账户规则、管理端供应商 / 协议规则、系统默认规则的顺序执行。

匹配条件直接使用下表这些字段。页面配置时优先填写错误码、错误消息、完成状态、输出文本或 JSON 路径，少用原始文本：

| 匹配条件 | 含义 |
| --- | --- |
| `clientProfiles` | 请求客户端适用范围，例如只匹配 `codex`；不算正向语义条件 |
| `outputTextIncludes` | 可见输出文本包含关键词；对 SSE 是单个或滚动窗口文本，对 JSON 是抽取后的文本字段 |
| `outputTextExcludes` | 可见输出文本排除关键词，降低误杀 |
| `errorCodes` | 统一错误码，例如 `cyber_policy`、`upstream_retryable_error` |
| `errorTypes` | 统一错误类型 |
| `errorMessageIncludes` | 错误文案包含关键词 |
| `finishReasons` | Chat `finish_reason` 或 Responses 完成状态映射 |
| `jsonPathsExists` | 原始 JSON 或 SSE data JSON 中存在指定路径，支持点路径和数组下标，例如 `response.error`、`choices.0.message.content` |
| `rawTextIncludes` | SSE 事件原文包含；只检查当前这一条 SSE 事件原文，包含 `event:` 行和 `data:` 行，不拼接整条响应流 |

`rawTextIncludes` 不是 `data` 里的业务字段，也不是单独的事件类型。SSE 原文通常长这样：`event: response.failed` 一行，后面跟 `data: {"type":"response.failed", ...}` 一行。`rawTextIncludes` 会在这两行合起来的原文里找关键词。能用 `errorCodes`、`errorTypes`、`errorMessageIncludes`、`finishReasons` 或 `jsonPathsExists` 表达时，应优先使用这些字段；只有上游返回格式不稳定、广告污染或中转私有文本不好拆字段时，才用 `rawTextIncludes` 先观察。

`errorCodes` 只能在策略明确声明 `clientProfiles` 时参与运行时命中。没有客户端画像门槛的通用规则不能仅靠上游错误码触发账号切换、账号避让或客户端失败，因为不同上游会复用、乱填或重定义这些字段；通用兜底应使用结构性 `jsonPathsExists`、协议 `errorTypes`、已写前协议失败、空响应或本地传输失败等服务端可验证信号。

`clientProfiles` 是运行时适用范围，不参与语义字段命中。`outputTextExcludes` 只作为已命中输出文本条件后的负向排除条件，不能单独构成一条可触发策略的正向 matcher。创建或更新策略时至少需要填写 `outputTextIncludes`、错误字段、完成状态、JSON 路径或 SSE 事件原文中的一个正向条件。

Codex 兼容规则必须由运行时 `clientProfiles = codex` 门控，不能仅凭账号能力、供应商或端点族把普通 OpenAI-compatible 客户端改写成 Codex 语义。

Codex Remote Compaction V2 另有一个系统默认契约规则：当请求被识别为 Codex compact 期望，包括 `/responses/compact` 或带 `compaction_trigger` 的 Codex `/responses`，响应检查器会在 `response.completed` 前暂存有限 SSE 事件窗口，并统计 `response.output_item.done` 中 Codex 可反序列化的 compact item 数量。合法 compact item 必须是 `type = "compaction"` 或 Codex 别名 `type = "compaction_summary"`，且 `encrypted_content` 为字符串。Codex compact SSE 的 `response.completed.response.id` 也必须是字符串；非流式 compact JSON 只按 `output` 数组校验。完成时数量不是 1 或 completed 结构不可被 Codex 解析时生成 `codex_compaction_contract_mismatch` 错误帧，命中 `default_codex_compaction_contract`，在下游未写出时允许服务端换号重试。这个规则只在 `clientProfiles = codex` 且当前账号实际 Responses 能力满足 Codex compact 检查条件时生效，不扩散给普通 OpenAI-compatible 客户端。

处置模板沿用当前可理解的动作语义，但作为新响应检查策略字段重新定义：

| action | 语义 |
| --- | --- |
| `observe` | 只记录命中，不改变下游响应 |
| `drop_event` | 只适用于可安全删除的流式独立事件；非流式完整 JSON 默认不使用该动作 |
| `retry_no_avoidance` | 当前结果不可接受，服务端可行时重试但不避让账号；前端新建策略默认使用该动作 |
| `retry_next_account` | 本次服务端重试避开当前账号 |
| `avoid_account_ttl` | 写入当前账号通用临时不可调用并触发可行重试 |
| `avoid_upstream_bucket_ttl` | 短 TTL 避让上游桶并触发可行重试 |

第一版不建议新增“替换文本”类动作。替换会让网关伪造模型输出，难以审计，也容易破坏工具调用和 JSON 结构。

## 9. 执行模式

### 9.1 下游流式

下游是 SSE 时，网关按增量语义帧检查：

- 尚未写出任何下游 body：命中可重试策略时可关闭当前上游并服务端重试。
- 已写出 metadata、心跳或不可见事件但未写可见输出：仍必须谨慎判断是否可重试；是否已写下游 body是更强约束，不能静默拼接第二条上游流。
- 已写出可见输出：禁止服务端透明重试，只能写失败事件、结束连接或依赖客户端重试能力。

### 9.2 下游非流式

下游是 JSON 时，网关应在写出客户端响应前完成检查：

- 上游返回 JSON：在有界响应体内解析语义帧，命中后可服务端重试；未命中再原样或规范化返回 JSON。
- 上游返回 SSE：可选执行“上游流式、下游 JSON 聚合”，语义帧增量检查，最终渲染回客户端请求的 JSON 形态。
- 命中重试策略时，由于下游尚未写出，服务端重试空间最大；最终只返回最后一次成功或统一失败 JSON。

非流式 JSON 聚合必须设置响应体、文本抽取和语义帧数量上限。超限时不能继续堆内存；应记录 `inspection_omitted` 诊断并按当前安全策略决定继续返回、返回本地错误或要求客户端改用流式。第一版默认不引入会大量误伤的全局 fail-closed。

### 9.3 上游强制流式

“客户端未开流时，网关对上游强制 `stream=true`”只能作为执行策略之一：

- 适用范围应限制在 `/v1/chat/completions` 和 `/v1/responses` 文本类请求。
- 下游仍按客户端原始协议返回，不能把流式要求传染给客户端。
- 上游如果尊重流式，网关可以更早发现污染并在写下游前重试。
- 上游如果忽略流式并返回 JSON，仍由 JSON 适配器进入同一响应检查管线。
- 该策略不得成为唯一防线；可靠边界是语义检查，而不是上游是否流式。

## 10. 性能与安全边界

- 响应检查运行在网关热路径，必须按协议适配器输出的语义帧增量处理。
- SSE 文本匹配只扫描当前事件或受控滚动窗口，不拼接无限完整流。
- JSON 成功响应检查必须有响应体上限和文本字段抽取上限；超限时记录省略原因。
- 图像、音频、视频、文件、base64 大字段和未知二进制响应不做关键词扫描。
- 策略读取仍必须在 API Key 校验、分组选择和账号候选确定后进行，只加载当前 `protocol_code + provider_code` 相关规则。
- 规则数量、关键词数量、单个关键词长度、JSON path 数量和命中摘要长度都必须有上限。
- 命中审计只记录规则 ID、来源、命中字段、命中值和短摘要，不保存完整污染正文。
- 不能为了响应检查在 API 路由或 repository 请求链路扫描使用记录、审计正文或统计缓存。

## 11. 审计、使用记录和诊断

响应检查命中时，应写入统一 gateway metadata：

- 策略 ID、名称、来源、协议、供应商和优先级。
- 命中的语义帧类型、字段、关键词或 JSON path。
- 当前客户端协议、上游传输类型和是否做过上游强制流式。
- 当前 `clientProfile`，用于解释策略适用范围。
- 命中时下游写入状态：未写出、已写出不可见事件、已写出可见输出。
- 执行动作、是否触发服务端重试、是否避让账号或上游桶。
- 如果因为响应过大、图像流或解析上限跳过检查，必须记录 `inspection_omitted` 原因。

使用记录需要避免把客户端协议和上游传输混淆。落地时应至少在快照或元信息中区分：

- `clientStream`：客户端原始请求是否要求流式。
- `upstreamStream`：实际发给上游或上游实际返回是否按流式处理。
- `responseInspection`：是否启用、是否命中、是否省略检查。

现有 `stream` 字段如果继续表示客户端请求语义，就不能拿它推断上游一定是 SSE。

## 12. 旧字段边界

当前响应语义检查直接作为返回侧唯一策略入口：

- 不保留旧 SSE 拦截器作为独立运行组件。
- 不迁移 `stream_intercept_policies` 表里的历史规则；直接使用新的响应检查策略表和字段结构。
- 不迁移旧账户级 `stream_intercept_rules`；账户专属配置使用新的 `response_inspection_rules` 字段，不做旧字段兼容或自动转换。
- 不在运行时代码里做旧字段兼容、双读、双写或自动转换。
- 前端菜单直接改为“响应检查策略”，用户在新入口重新配置协议层和供应商层规则。
- 旧文档只用于解释旧版本为什么只能覆盖 `200 + SSE`，不再作为新实现的约束来源。

## 13. 验证场景

目标实现至少需要覆盖：

- Chat JSON 成功响应里 `choices[].message.content` 命中污染关键词，网关未写下游前切号重试。
- Chat SSE 首个可见文本事件命中污染关键词，未写下游前可切号重试。
- Responses JSON 成功响应里 `output_text` 或 `output[].content[].text` 命中污染关键词，未写下游前可切号重试。
- Responses SSE `response.output_text.delta` 命中污染关键词，仍遵守已写下游后不能静默拼接的限制。
- Codex compact 期望请求返回 `response.completed` 但没有恰好 1 个 `compaction` output item 时，网关在写下游前拦截并服务端切号重试，坏 output item 不得先透传给客户端。
- 畸形 Responses SSE 关键事件，例如 `response.failed` / `response.completed` 的 `data` 不是 JSON，或 `data:` 到 EOF 仍未闭合时，未写下游前必须按缺少可解析终止事件失败收口，并交给调度层服务端重试，不得把畸形事件先写给客户端。
- 客户端非流式、上游被强制流式成功时，最终返回客户端非流式 JSON。
- 客户端非流式、上游忽略流式并返回 JSON 时，仍走 JSON 语义检查。
- 上游 JSON 错误、SSE `response.failed` 和 SSE `event:error` 都能统一归一为 `error` 帧。
- 大响应、图像流、base64 输出和未知二进制响应触发检查省略，不导致内存无界增长。
- 普通 OpenAI-compatible 客户端不接收 Codex 专用可重试错误码。
- 审计 metadata 能区分客户端协议、上游传输、命中规则、重试动作和检查省略原因。
