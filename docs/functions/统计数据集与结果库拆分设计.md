# 统计数据集与结果库拆分设计

## 文档目标

本文记录统计相关存储按统计数据集域和统计结果库拆分的设计。域拆分原则与存储形态无关（历史口径曾表述为「在 Go standalone（SQLite）与 performance（PostgreSQL + Redis）双模式下同样成立」；SQLite 模式已于 2026-10-25 退役，现行唯一形态为 PostgreSQL + Redis 单库 schema 域拆分），本文的独立库路径与 env 清单描述的是已退役的 standalone 模式拓扑。本文回答这些问题：

- 为什么要把事实数据和统计结果拆开。
- 拆分后各类表、repository、worker 和查询路径如何归属。
- 如何避免统计数据集域高频写入影响统计结果查询和网关额度判断。
- 如何在 standalone 模式下不引入重型外部依赖的前提下保证统计增量、重建、清理和观测可维护。

> **历史状态（2026-10-25 更新）。** 本文的域拆分原则（业务 / 数据集 / 使用记录 / 统计结果 / 运行日志 / 操作日志 / chat 各域独立、事实域高频写入与结果域查询隔离）仍是现行契约；库拓扑、env 清单、DB service 入口函数、worker 与切流叙述为 Node / SQLite 时代截面。2026-10-24/25 存储收口后 SQLite 与 memory 本地模式已物理退役，**现行唯一形态是单库 `juhe_ai` 内的 PostgreSQL schema 域拆分**（`juhe_business` / `juhe_dataset` / `juhe_usage` / `juhe_stats` / `juhe_codex_context` / `juhe_chat` / `juhe_jobs` / `juhe_j3b`），现行事实以 [PostgreSQL 与 Redis 高性能模式设计](PostgreSQL与Redis高性能模式设计.md)（含「PostgreSQL 存储形态」schema 映射表）、[架构总览](../architecture/架构总览.md) 数据访问隔离节与 `backend-go/projects/{jobs,maintenance}` 实现为准。原 Node 转 Go 迁移计划 `计划-20260706T071505000Z-Node转Go渐进减法迁移` 已删除（git 历史可溯）。

## 背景与问题

当前模型先把可恢复业务事实与高增长事实、统计结果分离：

- 业务库保存系统账户、AI 账户、分组、API Key、授权、设置、公告等可恢复业务事实。
- 统计数据集域保存使用记录、usage shard 目录、审计、公开接口日志、模型检测明细和清理目标；运行日志索引已拆到 Go F1 专用运行日志库，操作日志已拆到 Go F4 专用事实库。
- 统计结果库保存统计缓存、额度窗口和后台游标（原系统监控与表监控结果已随 2026-10-14 监控改造退役）。

拆分目标是避免高频追加事实和面向查询的统计结果互相拖慢：

- 高频追加的数据集：`usage_records`、`audit_logs`、`public_api_logs`、审计 payload、模型检测记录等；`runtime_logs` 由 Go F1 写入专用运行日志库，操作日志由 Go F4 写入专用事实库。
- 面向查询的统计结果：`usage_stats_*`、`usage_model_*`、`usage_error_*`、`usage_latency_*`、额度窗口、范围窗口、排行快照、概览窗口、AI 性能窗口等（原系统监控采样和趋势已随 2026-10-14 监控改造退役）。

随着使用记录和审计增长，事实数据集会出现更频繁的 WAL 写入、索引维护、清理、checkpoint 和 freelist 增长。即使页面统计只读预聚合表，也不应受到高频写入和维护任务影响。当前边界让“事实数据集高频写入”不再拖住“统计结果稳定查询”。

## 核心结论

数据集与统计职责固定拆分为统计数据集域和统计结果库：

| 库 | 建议默认路径 | 职责 | 写入特征 | 查询入口 |
| --- | --- | --- | --- | --- |
| 统计数据集域 | 数据集目录库 `backend/data/juhe-ai-dataset.sqlite3` + 使用记录目录库 `backend/data/juhe-ai-usage-catalog.sqlite3` + usage shard 文件 | 保存高增长事实、排障明细、文件游标、usage shard 元数据和筛选目录 | 高频追加、分批清理、可按保留期丢弃 | 明细页、排障页、worker 增量读取 |
| 统计结果库 | `backend/data/juhe-ai-stats.sqlite3` | 保存预聚合统计、额度窗口、范围窗口、排行、运行快照和后台水位 | worker 小批量 upsert、低频刷新、可重建 | 统计页、列表用量、网关额度、监控窗口 |

（上表「建议默认路径」为退役的 standalone SQLite 拓扑历史截面；现行唯一形态为单 PG 库 `juhe_ai` 内 schema 域拆分——统计数据集域落 `juhe_dataset` / `juhe_usage`，统计结果域落 `juhe_stats`，映射见 [PostgreSQL 与 Redis 高性能模式设计](PostgreSQL与Redis高性能模式设计.md)「PostgreSQL 存储形态」。）

原则：

- 业务库不参与本次拆分，继续只承载可恢复核心业务事实。
- 网关额度判断、统计概览、账户 / 分组 / API Key 列表用量、授权消耗、AI 性能摘要只读统计结果域（现行 `juhe_stats` schema）。
- 使用记录列表先读 `juhe_usage` 的逻辑 shard 目录（catalog），再按命中窗口读取 `usage_records` 日分区明细；页面不提供使用记录按 ID 详情，具体日志只从审计、公开接口、运行日志或操作日志管理页面读取。内部维护与验证如需按 ID 定位逻辑 shard，仍不得作为页面或 HTTP 详情能力暴露。
- jobs 后台任务（usage writer 与统计任务族）按统计安全游标读取 `juhe_usage.usage_records` 事实，向 `juhe_stats` 写入派生结果（历史口径「按 per-shard 游标读 usage shard」已随逐分片游标废弃调整，见下文 Worker 增量流程）。
- 运行路径不做跨 schema 的隐式耦合查询。需要展示的业务名称仍通过业务库按 ID 批量补齐或缓存，不在事实域与结果域之间 join。
- 现行唯一形态为 PostgreSQL + Redis 单机 Docker：单库 `juhe_ai` 多 schema 承载全部域拆分，启动必填 `JUHE_AI_POSTGRES_URL` / `JUHE_AI_REDIS_CACHE_URL` / `JUHE_AI_REDIS_STATE_URL`；原「standalone SQLite 多库 + usage shard 文件拓扑」与「显式 performance 模式」的双模式叙述已随 2026-10-25 存储收口退役，PG 侧数据域映射见 [PostgreSQL 与 Redis 高性能模式设计](PostgreSQL与Redis高性能模式设计.md)。

高频写入优化的现行形态：最热的 `usage_records` 是 `juhe_usage` 内按 `created_at` 的日 range 分区父表（历史 SQLite shard 文件方案见 [数据集库分片写入设计](数据集库分片写入设计.md)，已退役；逻辑 shard 目录四表仍保留用于列表窗口与清理定位）。统计结果域和业务库职责不变。

## 命名与配置（历史截面：standalone SQLite 拓扑，已退役）

> 本节 env 清单属 SQLite 模式历史截面：`JUHE_AI_DATABASE_PATH` / `JUHE_AI_CHAT_DATABASE_PATH` / `JUHE_AI_DATASET_DATABASE_PATH` / `JUHE_AI_USAGE_CATALOG_DATABASE_PATH` / `JUHE_AI_STATS_DATABASE_PATH` / `JUHE_AI_USAGE_SHARD_ROOT` / `JUHE_AI_USAGE_SHARD_COUNT` 与 F1 运行日志、余额刷新等 `*_DATABASE_PATH` 专库 env 已随 2026-10-25 存储收口全部退役，代码不再读取、残留值无效。现行配置契约是 `JUHE_AI_POSTGRES_URL` / `JUHE_AI_REDIS_CACHE_URL` / `JUHE_AI_REDIS_STATE_URL` 三个必填连接串加 `JUHE_AI_DATA_DIR` 文件目录派生，见 [PostgreSQL 与 Redis 高性能模式设计](PostgreSQL与Redis高性能模式设计.md) 配置模型节与 `docker/single-server/README.md`。以下清单保留为当时拓扑记录。


另有 F1 运行日志专库 `JUHE_AI_RUNTIME_LOG_DATABASE_PATH` 与余额刷新专库 `JUHE_AI_ACCOUNT_BALANCE_DATABASE_PATH`，在 standalone 模式下各自独立成库，未配置时按 `backend-go` datadir 约定落到数据目录默认文件名（原 F2 表监控专库 `JUHE_AI_TABLE_MONITOR_DATABASE_PATH` 已随 2026-10-14 监控改造删除）。

强制边界：

- 运行时只打开业务库、chat 库、数据集目录库、运行日志库、使用记录目录库、余额刷新专库、usage shard 和统计结果库这些明确入口。
- 未配置 `JUHE_AI_DATASET_DATABASE_PATH`、`JUHE_AI_USAGE_CATALOG_DATABASE_PATH` 或 `JUHE_AI_STATS_DATABASE_PATH` 时，使用默认 `backend/data/juhe-ai-dataset.sqlite3`、`backend/data/juhe-ai-usage-catalog.sqlite3` 和 `backend/data/juhe-ai-stats.sqlite3`。
- 业务库、chat 库、统计数据集目录库、使用记录目录库和统计结果库必须互不相同；F1 运行日志库与余额刷新专库各自独立成文件；usage shard 根目录必须与这些 SQLite 文件路径区分，避免把 shard 写入单库文件路径。
- 运行时代码只读取当前数据入口，不做跨体系双读。需要查看既有明细时，只能停服务后由用户自行用一次性离线脚本处理，处理逻辑不进入运行时代码。既有 usage 可以放弃，从新请求重新累计。
- 新部署由 `juhe-ai-maintenance --ensure-schema` 直接创建数据集目录库、使用记录目录库、usage shard 目录、统计结果库和各专库。

## 表归属

> 本节表清单以 [PostgreSQL 与 Redis 高性能模式设计](PostgreSQL与Redis高性能模式设计.md) 与 `backend-go/projects/maintenance/internal/schema/` 当前 DDL 为准。

### 统计数据集域

统计数据集域保存事实、明细、原始样本和清理目标（现行全部落在单库 `juhe_ai` 的 `juhe_dataset` / `juhe_usage` 等 schema；下文「××库」为历史 SQLite 库拓扑口径，现行对应关系见表内与 [PostgreSQL 与 Redis 高性能模式设计](PostgreSQL与Redis高性能模式设计.md)「PostgreSQL 存储形态」）。数据集域保存审计、公开接口日志、模型检测和清理目标；Go F1 索引器唯一写入运行日志索引；Go F4 owner 写入操作日志四表；`juhe_usage` 保存逻辑 shard 目录、使用记录筛选目录、scope catalog 与 `usage_records` 日分区事实（历史口径「新写入的 usage_records 保存到 usage shard 文件」已退役）。页面只能按分页、游标、offset 或明确索引窗口读取。

| 表 | 归属原因 |
| --- | --- |
| `usage_record_shards`、`usage_record_shard_entries`、`usage_record_account_shards`、`usage_record_api_key_shards` | 逻辑 shard 目录（现行 `juhe_usage` schema；历史口径为使用记录目录库），承载列表筛选窗口、shard 去重定位和清理定位，不承载物理 shard 文件 |
| `usage_records` | 网关请求事实源，高频追加；现行保存于 `juhe_usage.usage_records` 日分区父表（历史口径为 usage shard 文件），是统计任务的主输入 |
| `audit_logs`、`audit_log_attempts`、`audit_payload_blobs`、`audit_payload_refs`、`audit_error_groups` | 原始审计和 payload 明细，高增长排障数据 |
| `operation_logs`、`operation_log_targets`、`operation_log_viewers`、`operation_log_summary_search_terms` | Go F4 专用事实库中的业务操作追溯数据；不属于数据集目录库，也不由统计任务读取或清理 |
| `runtime_logs`、`runtime_log_file_cursors`、`runtime_log_facet_summary`、`runtime_log_level_facets`、`runtime_log_event_facets` | Go F1 专用运行日志库中的索引、游标和 facets，来源是日志文件追增量 |
| `model_check_runs`、`model_check_items` | 模型检测历史和诊断明细 |
| `api_key_record_cleanup_targets` | API Key 删除后的记录清理目标和重试状态 |

说明：

- 统计数据集域中的数据是统计结果和排障详情的事实来源，但不是页面汇总来源。
- 使用记录保留清理必须保护统计安全游标（现行双聚合 global 游标放行门；per-shard 游标已废）；不能删除统计尚未处理到的 `usage_records` 分区。
- 大字段和 payload 继续按保全策略分块、压缩、去重和窗口读取。

### 统计结果库

统计结果库保存紧凑结果、窗口、排行和可被网关或页面直接读取的运行快照。它允许 worker 刷新，但不能承接大 payload 或高频明细追加。

| --- | --- |
| `usage_stats_minute`、`usage_stats_hourly`、`usage_stats_daily`、`usage_stats_weekly`、`usage_stats_monthly`、`usage_stats_totals` | 通用用量聚合桶，页面和额度直读 |
| `usage_model_minute`、`usage_model_hourly`、`usage_model_daily`、`usage_model_weekly`、`usage_model_monthly` | 模型维度聚合结果 |
| `usage_error_minute`、`usage_error_hourly`、`usage_error_daily`、`usage_error_weekly`、`usage_error_monthly` | 错误维度聚合结果 |
| `usage_latency_minute`、`usage_latency_hourly`、`usage_latency_daily`、`usage_latency_weekly`、`usage_latency_monthly` | 首 token 和总耗时直方图结果 |
| `usage_quota_hourly_windows`、`usage_scope_range_windows` | 额度窗口和日期范围结果 |
| `usage_rank_snapshots`、`usage_overview_summary_windows`、`usage_overview_trend_windows`、`usage_model_rank_windows`、`usage_error_rank_windows`、`ai_performance_summary_windows` | 页面范围摘要、趋势和 TopN 结果 |
| `authorization_team_usage_summary_daily`、`authorization_user_usage_summary_daily` | 授权消耗日摘要；范围窗口两表 `authorization_team_usage_range_windows` / `authorization_user_usage_range_windows` 已退役（B09） |
| `account_quality_minute_stats`、`account_quality_scores` | 账号质量派生结果和调度辅助缓存 |
| `group_account_stats` | 分组绑定统计结果 |
| `account_usage_snapshots` | OAuth 额度快照和账户运行摘要，列表直读 |
| `stats_job_state` | 统计结果库自己的派生水位、窗口刷新水位和重建状态 |

（原表中的 `system_metrics_samples` / `system_metrics_hourly` / `system_metrics_trend_windows`、`process_event_loop_samples` / `process_event_loop_hourly` / `process_event_loop_trend_windows` 与 `database_storage_snapshots` / `table_storage_snapshots` 三行已随 2026-10-14 监控改造删除：退役表经 maintenance `--drop-retired-monitoring-tables` 清退，应用进程监控与容量观测改由 Prometheus / postgres_exporter 承担，见 [Prometheus 指标暴露设计](Prometheus指标暴露设计.md)。）

- `stats_job_state` 放在统计结果库，因为它描述“统计结果已经处理到哪里”。统计结果写入和游标推进必须在同一个统计结果库事务里提交。
- `group_account_stats_dirty` 是业务库里的结果刷新队列；它服务的是分组统计结果刷新，写入量受业务变更控制，但不能因为统计结果库长写事务而影响业务写路径。
- （原"表监控历史"与 `process_event_loop_*` / `go_runtime_metrics_*` 说明已随 2026-10-14 监控改造删除：系统监控与表监控窗口表整体退役，不再存在"Node event loop、V8 heap、`db-service` 或 SQLite 文件体积"类 Go 统计结果；监控走 Prometheus。）

## 访问边界

Node 时代的 `getBusinessDatabase()` / `getDatasetDatabase()` / `getUsageCatalogDatabase()` / `getStatsDatabase()` DB service 入口已随 Node 后端归档退役。Go 现行访问边界（证据：[架构总览](../architecture/架构总览.md) 数据访问隔离节；[Go 三项目架构基线](../architecture/Go三项目架构基线.md) §3）：

- 业务库写入由 `juhe-ai-gateway` 单进程唯一写者持有（短事务、连接池与锁超时控制写等待；历史口径的 WAL / `busy_timeout` 为 SQLite 时代细节）。
- 数据集域各事实写入归唯一 owner 包：审计 / 操作日志归 gateway F3 / F4 owner，运行日志索引归 jobs F1 索引器，usage 写入归 jobs `usagewriter` 唯一 owner（历史口径 usage shard owner writer；现行写 `juhe_usage` 日分区），统计聚合只读事实，不把派生估算字段回写原始明细。
- 统计结果域写入由 `juhe-ai-jobs` 对应任务串行提交；统计结果写入和 `stats_job_state` 游标推进在同一事务内完成。
- repository 边界保持：
  - 明细类 store 只依赖统计数据集域；使用记录经 `juhe_usage` 逻辑 shard 目录与日分区访问层读取，其他明细经各自事实 schema 读取。
  - 统计类 store、额度检查、窗口读取和列表用量补数只依赖统计结果域。
  - 业务 store 需要补统计字段时，只批量读取统计结果域，不读取统计数据集域。

## Worker 增量流程

主统计流程由 `juhe-ai-jobs` 的统计任务族执行（实现：`backend-go/projects/jobs/internal/usagewriter/`、`backend-go/projects/jobs/internal/statsagg/`；任务注册以 `backend-go/projects/jobs/internal/jobregistry/registry.go` 为准）：

```text
juhe_usage.usage_records（日分区父表，历史口径为 usage shard usage_records）
  -> 统计任务按统计安全游标（stats_job_state）有界批量读取事实（历史口径：按有界 shard 窗口轮转 + 每 shard (created_at, id) 游标；per-shard 游标已废）
  -> 内存生成 scope、模型、错误、耗时、授权、窗口刷新输入
  -> juhe_stats 事务中 upsert 统计桶和窗口
  -> 同一个事务中推进 stats_job_state
```

一致性规则：

- 统计任务读取统计数据集域不需要跨域事务；读取批次只以稳定游标和批量上限确定。
- （历史口径：主用量统计聚合曾在单个 batch 内只打开固定上限数量的 active usage shard，历史 shard 很多时按轮转窗口逐批检查；per-shard 游标已废，现行按统计安全游标有界批量读取。）
- 统计结果写入和 `stats_job_state` 游标推进必须在同一个事务内完成。
- 如果统计写入失败，不推进游标，下一轮重复读取同一批数据。
- 如果事务提交成功，统计结果和游标同时生效，不会因为进程崩溃导致重复累加。
- 使用记录保留清理必须读取统计安全游标（现行双聚合 global 游标放行门；历史口径为 per-shard 游标）；清理候选先从 `juhe_usage.usage_record_shard_entries` 按 `created_at + usage_id` 窗口读取，再按 `(created_at, id)` 命中日分区小批删除，不能在管理 API 预览或后台批次里做无界候选排序。
- 重建统计结果域时，先停 gateway 与 jobs 两进程，清空统计结果表和 `stats_job_state`，再从 `usage_records` 逐批重放聚合；离线重建也可直接使用 `juhe-ai-maintenance --rebuild-usage-stats`（见下文清理与重建）。

## API 与查询路径

拆分后查询路径固定如下：

| 场景 | 读取域 | 说明 |
| --- | --- | --- |
| 网关 API Key 额度 | 统计结果域 `juhe_stats` | 只读额度窗口、自然日 / 周 / 月 / 累计统计 |
| 统计概览、我的用量、AI 性能监控 | 统计结果域 `juhe_stats` | 只读范围窗口、排行、趋势、聚合桶 |
| 账户 / 分组 / API Key 列表用量 | 统计结果域 `juhe_stats` | 只读累计、今日和必要窗口 |
| 授权团队 / 用户消耗 | 统计结果域 `juhe_stats` | 只读授权专用摘要和范围窗口 |
| 使用记录列表 | `juhe_usage` 逻辑 shard 目录 + `usage_records` 日分区 | 按 catalog 窗口筛选后读命中分区明细（历史口径为「使用记录目录库 + usage shard」），不提供按 ID 页面或 HTTP 详情 |
| 原始审计 | `juhe_dataset` + payload blob 专用目录 | 审计表保存在 `juhe_dataset`（历史口径为数据集目录库），大 payload blob 由 `JUHE_AI_AUDIT_LOG_BLOB_DIRECTORY` 指向的专用目录保存；按游标、分页和受控窗口读取 |
| 操作日志 | `juhe_dataset`（Go F4 owner 四表） | 由 Go F4 owner 读取（历史口径为 F4 专库） |
| 运行日志 | `juhe_dataset`（Go F1 索引器唯一写入） | 按游标、分页和受控窗口读取（历史口径为 F1 专库） |

（原"表监控 → 统计结果库"查询路径已随 2026-10-14 监控改造删除；容量观测由 postgres_exporter 承担。）

禁止路径：

- 页面接口不得对 `usage_records` 或逻辑 shard 目录做临时 `SUM/GROUP BY` 明细聚合。
- 页面接口不得把统计结果域多行桶再次 `reduce` 成业务摘要。
- 运行时不得做跨 schema 的隐式耦合查询或事实域 / 结果域 join（历史口径为 SQLite `ATTACH` 跨库 join）。
- 网关请求路径不得读取统计数据集域。

## 清理与重建

统计数据集域清理由 `juhe-ai-jobs` 的 cleanup / retention 任务族执行：

- `usage_records` 清理必须同时满足保留期和统计安全游标安全位置（现行双聚合 global 游标放行门，历史口径为 per-shard 游标）；为了避免请求链路 fan-out，首批预览和候选选择只读 catalog 窗口，实际删除按 `(created_at, id)` 命中日分区小批执行（历史口径为「打开命中候选的 shard 删除」）。
- 审计、运行日志、操作日志和模型检测历史按各自 owner 的保留策略清理；F3 / F4 事实明确不进入通用 hard cleanup。
- 清理批次必须有限，不做全表删除和全表 `COUNT(*)`。

统计结果库清理：

- 分钟、小时、日、周、月、排行、窗口按现有保留策略分批清理（原监控趋势窗口已随 2026-10-14 监控改造退役）。
- 统计结果库损坏时优先从 usage shard 和仍保留的数据集目录库事实重建；离线重建另有 `juhe-ai-maintenance --rebuild-usage-stats`（复用 jobs statsagg 聚合口径，BUG-0182；要求 gateway/jobs 停机，业务库与 `usage_records` 只读）。
- 如果统计数据集域已清理掉所需历史事实，则只能从仍保留的事实重新累计，不能伪造历史统计。

AI 账户 / API Key 删除：

- 业务库删除 AI 账户或 API Key 后立即让新请求不可用，请求链路只登记清理目标，不同步清历史明细。
- usage shard 负责清理相关使用记录，数据集目录库负责清理模型检测和排障明细；F3/F4 专库分别由 Go retention owner 清理。
- 统计结果域负责清理或反向扣减账号 / API Key 维度统计、额度窗口、范围窗口、排行、账号质量和账号外部用量快照。
- 删除清理必须按域边界拆成短事务，并通过 dataset 清理目标记录重试状态；不能依赖单个跨域事务。
- （历史口径：SQLite 时代统计结果库或 usage shard 出现 `database is locked` 时，清理目标应标记 blocked 并等待 worker 后续重试；现行 PG 形态下可恢复锁竞争与写入失败同样按清理目标 blocked + 后续重试处理，不抛成删除失败。）

## 当前模型切换（历史截面：SQLite 模式库拓扑，已退役）

> 本节描述的「新建数据集目录库 / 使用记录目录库 / usage shard 目录 / 统计结果库」切换路径属 SQLite 模式库拓扑，已随 2026-10-25 存储收口退役，不可执行；保留为当时发布 / 回滚语义记录。现行形态下不存在存储模式切换：唯一形态为 PostgreSQL + Redis，发布只执行当前 schema 的 `--ensure-schema` 幂等初始化与 verify-release 验证。

预上线阶段推荐停机切换，不做运行时双写和双读。默认策略是“业务库必保，统计相关域可丢弃”：统计数据集目录库、使用记录目录库、usage shard 和统计结果库可以直接新建空库，统计从新请求重新累计；如果仍保留 usage shard 里的 `usage_records`，也可以按需重建统计结果。

切换路径：

1. 停止 gateway 和 jobs 两个进程（`juhe-ai-gateway`、`juhe-ai-jobs`）。
2. 必须备份业务库和 `backend/.env`；统计数据集目录库、使用记录目录库、usage shard 和统计结果库默认不纳入必备份范围。
3. 创建新的数据集目录库、使用记录目录库、usage shard 目录和统计结果库；允许它们为空启动。
4. 统计结果库可以清空后从新请求累计；既有统计默认放弃。
5. 按上文「命名与配置」中的 env 清单更新 `.env`。
6. 启动服务并执行统计、列表和网关额度验证。
7. 验证通过后只保留当前业务库、统计数据集目录库、使用记录目录库、usage shard 目录、统计结果库和 `backend/.env`。

统计结果库按当前 schema 清空重建；如果统计数据集域不保留，既有统计明确放弃，从新请求重新累计。

## 方案复查评审

> 本节为 Node 时代实施前的方案验收记录，整体保留作历史对照，不构成现行验收标准；现行事实以 [PostgreSQL 与 Redis 高性能模式设计](PostgreSQL与Redis高性能模式设计.md)、架构总览数据访问隔离节与 `backend-go` 实现和测试为准。

评审结论：方案可进入实施，但需要按以下约束验收。

| 检查项 | 结论 | 要求 |
| --- | --- | --- |
| 是否符合轻量部署 | 通过 | 仍使用本地 SQLite，不引入外部依赖 |
| 是否减少写入对查询影响 | 通过 | 高频 usage 进入 shard，大 payload 进入数据集目录库，统计页面和网关只读结果库 |
| 是否避免跨库强事务 | 通过 | 统计结果写入和游标推进在结果库内同事务，统计数据集域只作为输入 |
| 是否支持重建 | 通过 | 统计结果库可从 usage shard 和仍保留的数据集目录库事实重建，历史事实缺失时明确放弃不可恢复区间 |
| 是否保护请求路径性能 | 通过 | 网关不读统计数据集域，页面不临时聚合明细 |
| 是否影响部署和备份 | 需要同步 | 部署文档、运行说明和备份策略需要增加四个主 SQLite 路径、`JUHE_AI_USAGE_SHARD_ROOT`、`JUHE_AI_USAGE_SHARD_COUNT` 以及对应备份 / 重建边界 |
| 是否影响表监控 | 需要同步 | 表监控要展示 `business`、`dataset`、`usage-catalog`、`stats` 四类库（本项已随 2026-10-14 监控改造作废：表监控页与快照表整体删除） |
| 是否影响测试 | 需要补齐 | 启动、mockdata、统计重建、额度、清理和查询 guard 都要覆盖四个主库 |

实施前需要重点复查：

- 源码中不应出现记录域短名入口、历史配置入口或隐式跨库访问。
- 所有统计接口是否只读统计结果库。
- 所有明细接口是否没有误读统计结果库。
- `stats_job_state` 是否只存在于统计结果库，并能保护 usage shard 和数据集目录库清理。
- （原"表监控是否能看到业务库、数据集目录库、使用记录目录库、统计结果库文件大小、WAL、freelist 和表级采样"复查项已随 2026-10-14 监控改造作废。）
- 部署恢复时是否明确“默认只备份业务库，数据集目录库、使用记录目录库、usage shard 和统计结果库可选备份或重建”。
