# 统计数据集与结果库拆分设计

## 文档目标

本文用于记录统计相关存储按统计数据集域和统计结果库拆分后的当前方案，回答这些问题：

- 为什么要把事实数据和统计结果拆开。
- 拆分后各类表、repository、worker 和查询路径如何归属。
- 如何避免统计数据集域高频写入影响统计结果查询和网关额度判断。
- 如何在不引入重型外部依赖的前提下保证统计增量、重建、清理和观测可维护。

本文是方案设计和评审依据。当前实现已经按统计数据集域 / 统计结果库拆分核心运行路径；统计数据集域当前由数据集目录库和 usage shard 文件组成。后续真实上线必须保护业务库和 `backend/.env`；统计数据集域和统计结果库都可以丢弃、清空或重建，历史统计不能重建时从新请求重新累计。

## 背景与问题

当前模型先把可恢复业务事实与高增长事实、统计结果分离：

- 业务库保存系统账户、AI 账户、分组、API Key、授权、设置、公告等可恢复业务事实。
- 统计数据集域保存使用记录、审计、操作日志、公开接口日志、运行日志索引、模型检测明细和清理目标。
- 统计结果库保存统计缓存、额度窗口、系统监控、表监控和后台游标。

拆分目标是避免高频追加事实和面向查询的统计结果互相拖慢：

- 高频追加的数据集：`usage_records`、`audit_logs`、`public_api_logs`、`runtime_logs`、审计 payload、操作日志、模型检测记录等。
- 面向查询的统计结果：`usage_stats_*`、`usage_model_*`、`usage_error_*`、`usage_latency_*`、额度窗口、范围窗口、排行快照、概览窗口、AI 性能窗口、系统监控采样和趋势等。

随着使用记录和审计增长，事实数据集会出现更频繁的 WAL 写入、索引维护、清理、checkpoint 和 freelist 增长。即使页面统计只读预聚合表，也不应受到高频写入和维护任务影响。当前边界让“事实数据集高频写入”不再拖住“统计结果稳定查询”。

## 核心结论

数据集与统计职责固定拆分为统计数据集域和统计结果库：

| 库 | 建议默认路径 | 职责 | 写入特征 | 查询入口 |
| --- | --- | --- | --- | --- |
| 统计数据集域 | 数据集目录库 `backend/data/juhe-ai-dataset.sqlite3` + usage shard 文件 | 保存高增长事实、排障明细、文件游标和 shard 元数据 | 高频追加、分批清理、可按保留期丢弃 | 明细页、排障页、worker 增量读取 |
| 统计结果库 | `backend/data/juhe-ai-stats.sqlite3` | 保存预聚合统计、额度窗口、范围窗口、排行、系统监控采样、运行快照和后台水位 | worker 小批量 upsert、低频刷新、可重建 | 统计页、列表用量、网关额度、监控窗口 |

原则：

- 业务库不参与本次拆分，继续只承载可恢复核心业务事实。
- 网关额度判断、统计概览、账户 / 分组 / API Key 列表用量、授权消耗、AI 性能摘要只读统计结果库。
- 使用记录只读 usage shard；审计日志、公开接口日志、运行日志、操作日志、模型检测详情只读统计数据集目录库。
- 后台 worker 从 usage shard 按 per-shard 游标读取使用记录，从数据集目录库读取其他事实，向统计结果库写入派生结果。
- 运行路径不使用 `ATTACH` 做跨库 join。需要展示的业务名称仍通过业务库按 ID 批量补齐或缓存，不在统计库之间 join。
- 不引入 Redis、ClickHouse、PostgreSQL 或分布式队列。拆分仍保持单机轻量 SQLite 部署。

高频写入优化已经先把最热的 `usage_records` 拆为多个本地 SQLite shard 文件；统计结果库和业务库职责不变。具体方案见 [数据集库分片写入设计](数据集库分片写入设计.md)。

## 命名与配置

当前运行配置：

```dotenv
JUHE_AI_DATABASE_PATH=./data/juhe-ai.sqlite3
JUHE_AI_DATASET_DATABASE_PATH=./data/juhe-ai-dataset.sqlite3
JUHE_AI_STATS_DATABASE_PATH=./data/juhe-ai-stats.sqlite3
JUHE_AI_USAGE_SHARD_ROOT=./data/usage-shards
JUHE_AI_USAGE_SHARD_COUNT=16
```

强制边界：

- 运行时只打开业务库、统计数据集目录库、usage shard 和统计结果库这些明确入口。
- 未配置 `JUHE_AI_DATASET_DATABASE_PATH` 或 `JUHE_AI_STATS_DATABASE_PATH` 时，使用默认 `backend/data/juhe-ai-dataset.sqlite3` 和 `backend/data/juhe-ai-stats.sqlite3`。
- 业务库、统计数据集目录库和统计结果库必须指向三个不同 SQLite 文件；usage shard 根目录必须与这些 SQLite 文件路径区分，避免把 shard 写入单库文件路径。
- 运行时代码只读取当前数据入口，不做跨体系双读。需要查看既有明细时，只能停服务后由用户自行用一次性离线脚本处理，处理逻辑不进入运行时代码。既有 usage 可以放弃，从新请求重新累计。
- 新部署直接创建数据集目录库、usage shard 目录和统计结果库。

## 表归属

### 统计数据集域

统计数据集域保存事实、明细、原始样本和清理目标。数据集目录库保存审计、操作日志、公开接口日志、运行日志、模型检测和 shard 元数据；新写入的 `usage_records` 保存到 usage shard 文件。它可以被频繁写入，但页面只能按分页、游标、offset 或明确索引窗口读取。

| 表 | 归属原因 |
| --- | --- |
| `usage_records` | 网关请求事实源，高频追加，保存于 usage shard 文件，是统计 worker 的主输入 |
| `audit_logs`、`audit_log_attempts`、`audit_payload_blobs`、`audit_payload_refs`、`audit_error_groups` | 原始审计和 payload 明细，高增长排障数据 |
| `operation_logs`、`operation_log_targets`、`operation_log_viewers` | 业务操作追溯事实，追加型历史数据 |
| `runtime_logs`、`runtime_log_file_cursors`、`runtime_log_facet_summary`、`runtime_log_level_facets`、`runtime_log_event_facets` | 运行日志索引和文件读取游标，来源是日志文件追增量 |
| `model_check_runs`、`model_check_items` | 模型检测历史和诊断明细 |
| `api_key_record_cleanup_targets` | API Key 删除后的记录清理目标和重试状态 |

说明：

- 统计数据集域中的数据是统计结果和排障详情的事实来源，但不是页面汇总来源。
- usage shard 清理必须保护统计结果库中的 per-shard 统计游标；不能删除统计 worker 尚未处理到的 `usage_records`。
- 大字段和 payload 继续按保全策略分块、压缩、去重和窗口读取。

### 统计结果库

统计结果库保存紧凑结果、窗口、排行和可被网关或页面直接读取的运行快照。它允许 worker 刷新，但不能承接大 payload 或高频明细追加。

| 表 | 归属原因 |
| --- | --- |
| `usage_stats_minute`、`usage_stats_hourly`、`usage_stats_daily`、`usage_stats_weekly`、`usage_stats_monthly`、`usage_stats_totals` | 通用用量聚合桶，页面和额度直读 |
| `usage_model_minute`、`usage_model_hourly`、`usage_model_daily`、`usage_model_weekly`、`usage_model_monthly` | 模型维度聚合结果 |
| `usage_error_minute`、`usage_error_hourly`、`usage_error_daily`、`usage_error_weekly`、`usage_error_monthly` | 错误维度聚合结果 |
| `usage_latency_minute`、`usage_latency_hourly`、`usage_latency_daily`、`usage_latency_weekly`、`usage_latency_monthly` | 首 token 和总耗时直方图结果 |
| `usage_quota_hourly_windows`、`usage_scope_range_windows` | 额度窗口和日期范围结果 |
| `usage_rank_snapshots`、`usage_overview_summary_windows`、`usage_overview_trend_windows`、`usage_model_rank_windows`、`usage_error_rank_windows`、`ai_performance_summary_windows` | 页面范围摘要、趋势和 TopN 结果 |
| `authorization_team_usage_summary_daily`、`authorization_team_usage_range_windows`、`authorization_user_usage_summary_daily`、`authorization_user_usage_range_windows` | 授权消耗日摘要和范围窗口 |
| `account_quality_minute_stats`、`account_quality_scores` | 账号质量派生结果和调度辅助缓存 |
| `group_account_stats` | 分组绑定统计结果 |
| `account_usage_snapshots` | OAuth 额度快照和账户运行摘要，列表直读 |
| `system_metrics_samples`、`system_metrics_hourly`、`system_metrics_trend_windows` | 系统监控采样、小时聚合和趋势结果，写入频率低且供管理监控直读 |
| `process_event_loop_samples`、`process_event_loop_hourly`、`process_event_loop_trend_windows` | 进程事件循环采样、小时聚合和趋势结果，供管理监控直读 |
| `database_storage_snapshots`、`table_storage_snapshots` | 管理端表监控结果，低频写入，用于观察业务库、数据集目录库和统计结果库 |
| `stats_job_state` | 统计结果库自己的派生水位、窗口刷新水位和重建状态 |

说明：

- `stats_job_state` 放在统计结果库，因为它描述“统计结果已经处理到哪里”。统计结果写入和游标推进必须在同一个统计结果库事务里提交。
- `group_account_stats_dirty` 是业务库里的结果刷新队列；它服务的是分组统计结果刷新，写入量受业务变更控制，但不能因为统计结果库长写事务而影响业务写路径。
- 表监控历史用于稳定展示三库容量和增长趋势，低频写入，不应跟随高频统计数据集域一起被清理或影响统计页面。

## 访问边界

代码层新增明确数据库入口：

```text
getBusinessDatabase()
getDatasetDatabase()
getStatsDatabase()
```

设计要求：

- 当前代码统一使用 `getBusinessDatabase()` 表达业务库职责；新增代码不再引入业务库短名入口。
- 任何数据集或统计访问都必须明确选择 `getDatasetDatabase()`、usage shard 访问层或 `getStatsDatabase()`。
- schema 拆分为 `dataset-schema.ts` 和 `stats-schema.ts`。
- repository 按职责引用对应数据库：
  - 明细类 repository 只依赖统计数据集域；使用记录经 usage shard 访问层读取，其他明细经数据集目录库读取。
  - 统计类 repository、额度检查、窗口读取和列表用量补数只依赖统计结果库。
  - 业务 repository 需要补统计字段时，只批量读取统计结果库，不读取统计数据集域。

## Worker 增量流程

主统计流程：

```text
usage shard usage_records
  -> worker 按有界 shard 窗口轮转，并按每个 shard 的 (created_at, id) 游标读取一批事实
  -> 内存生成 scope、模型、错误、耗时、授权、窗口刷新输入
  -> 统计结果库事务中 upsert 统计桶和窗口
  -> 同一个统计结果库事务中推进 stats_job_state
```

一致性规则：

- worker 读取统计数据集域不需要跨库事务；读取批次只以稳定游标和批量上限确定。
- 主用量统计聚合在单个 batch 内只打开固定上限数量的 active usage shard；历史 shard 很多时按轮转窗口逐批检查，避免高频任务每轮打开全部 shard。
- 统计结果写入和 `stats_job_state` 游标推进必须在同一个统计结果库事务内完成。
- 如果统计结果库写入失败，不推进游标，下一轮重复读取同一批数据。
- 如果统计结果库事务提交成功，统计结果和游标同时生效，不会因为进程崩溃导致重复累加。
- usage shard 保留清理必须读取统计结果库 per-shard 游标；清理候选先从数据集目录库 `usage_record_shard_entries` 按 `created_at + usage_id` 窗口读取，再按 shard 分组删除明细，不能在管理 API 预览或后台批次里打开全部 active shard 做候选排序。
- 重建统计结果库时，先停 worker，清空统计结果表和 `stats_job_state`，再按 usage shard `usage_records` 游标重放。

## API 与查询路径

拆分后查询路径固定如下：

| 场景 | 读取库 | 说明 |
| --- | --- | --- |
| 网关 API Key 额度 | 统计结果库 | 只读额度窗口、自然日 / 周 / 月 / 累计统计 |
| 统计概览、我的用量、AI 性能监控 | 统计结果库 | 只读范围窗口、排行、趋势、聚合桶 |
| 账户 / 分组 / API Key 列表用量 | 统计结果库 | 只读累计、今日和必要窗口 |
| 授权团队 / 用户消耗 | 统计结果库 | 只读授权专用摘要和范围窗口 |
| 使用记录列表与详情 | usage shard | 按索引分页，不做业务汇总 |
| 原始审计、操作日志、运行日志 | 统计数据集目录库 | 按游标、分页和受控窗口读取 |
| 表监控 | 统计结果库 | 展示业务库、数据集目录库和统计结果库三种 `database_role` |

禁止路径：

- 页面接口不得从 usage shard 临时 `SUM/GROUP BY usage_records`。
- 页面接口不得把统计结果库多行桶再次 `reduce` 成业务摘要。
- 运行时不得 `ATTACH` 统计数据集域和统计结果库做跨库 join。
- 网关请求路径不得读取统计数据集域。

## 清理与重建

统计数据集域清理：

- `usage_records` 清理必须同时满足保留期和统计结果库 per-shard 游标安全位置；为了避免请求链路 fan-out，首批预览和候选选择只读 catalog 窗口，实际删除时才打开命中候选的 shard。
- 审计、运行日志、操作日志和模型检测历史按各自保留策略清理。
- 清理批次必须有限，不做全表删除和全表 `COUNT(*)`。

统计结果库清理：

- 分钟、小时、日、周、月、排行、窗口、监控趋势按现有保留策略分批清理。
- 统计结果库损坏时优先从 usage shard 和仍保留的数据集目录库事实重建。
- 如果统计数据集域已清理掉所需历史事实，则只能从仍保留的事实重新累计，不能伪造历史统计。

AI 账户 / API Key 删除：

- 业务库删除 AI 账户或 API Key 后立即让新请求不可用，请求链路只登记清理目标，不同步清历史明细。
- usage shard 负责清理相关使用记录，数据集目录库负责清理审计、模型检测和排障明细。
- 统计结果库负责清理或反向扣减账号 / API Key 维度统计、额度窗口、范围窗口、排行、账号质量和账号外部用量快照。
- 删除清理必须按库边界拆成短事务，并通过 dataset 清理目标记录重试状态；不能依赖单个跨库事务。
- 统计结果库或 usage shard 出现 `database is locked` 时，清理目标应标记 blocked 并等待 worker 后续重试，不应把可恢复锁竞争抛成删除失败。

## 当前模型切换

预上线阶段推荐停机切换，不做运行时双写和双读。默认策略是“业务库必保，统计相关域可丢弃”：统计数据集目录库、usage shard 和统计结果库可以直接新建空库，统计从新请求重新累计；如果仍保留 usage shard 里的 `usage_records`，也可以按需重建统计结果。

切换路径：

1. 停止 Web、DB service 和 background worker。
2. 必须备份业务库和 `backend/.env`；统计数据集目录库、usage shard 和统计结果库默认不纳入必备份范围。
3. 创建新的数据集目录库、usage shard 目录和统计结果库；允许它们为空启动。
4. 统计结果库可以清空后从新请求累计；既有统计默认放弃。
5. 更新 `.env` 为 `JUHE_AI_DATABASE_PATH`、`JUHE_AI_DATASET_DATABASE_PATH`、`JUHE_AI_STATS_DATABASE_PATH`、`JUHE_AI_USAGE_SHARD_ROOT` 和 `JUHE_AI_USAGE_SHARD_COUNT`。
6. 启动服务并执行统计、列表、网关额度和表监控验证。
7. 验证通过后只保留当前业务库、统计数据集目录库、usage shard 目录、统计结果库和 `backend/.env`。

统计结果库按当前 schema 清空重建；如果统计数据集域不保留，既有统计明确放弃，从新请求重新累计。

## 方案复查评审

评审结论：方案可进入实施，但需要按以下约束验收。

| 检查项 | 结论 | 要求 |
| --- | --- | --- |
| 是否符合轻量部署 | 通过 | 仍使用本地 SQLite，不引入外部依赖 |
| 是否减少写入对查询影响 | 通过 | 高频 usage 进入 shard，大 payload 进入数据集目录库，统计页面和网关只读结果库 |
| 是否避免跨库强事务 | 通过 | 统计结果写入和游标推进在结果库内同事务，统计数据集域只作为输入 |
| 是否支持重建 | 通过 | 统计结果库可从 usage shard 和仍保留的数据集目录库事实重建，历史事实缺失时明确放弃不可恢复区间 |
| 是否保护请求路径性能 | 通过 | 网关不读统计数据集域，页面不临时聚合明细 |
| 是否影响部署和备份 | 需要同步 | 部署文档、运行说明和备份策略需要增加三个 SQLite 路径、`JUHE_AI_USAGE_SHARD_ROOT`、`JUHE_AI_USAGE_SHARD_COUNT` 以及对应备份 / 重建边界 |
| 是否影响表监控 | 需要同步 | 表监控要展示 `business`、`dataset`、`stats` 三类库 |
| 是否影响测试 | 需要补齐 | 启动、mockdata、统计重建、额度、清理和查询 guard 都要覆盖三库 |

实施前需要重点复查：

- 源码中不应出现记录域短名入口、历史配置入口或隐式跨库访问。
- 所有统计接口是否只读统计结果库。
- 所有明细接口是否没有误读统计结果库。
- `stats_job_state` 是否只存在于统计结果库，并能保护 usage shard 和数据集目录库清理。
- 表监控是否能看到三库文件大小、WAL、freelist 和表级采样。
- 部署恢复时是否明确“默认只备份业务库，数据集目录库、usage shard 和统计结果库可选备份或重建”。
