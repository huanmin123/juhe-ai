# AI 账户模型映射选择规则

> 状态：当前规则。
> 更新时间：2026-07-27。
> 本文统一 AI 账户单个编辑、批量编辑、导入保存和网关运行时的模型映射语义。协议转换方向仍以 [协议桥接框架设计](协议桥接框架设计.md) 为准；模型目录与价格事实仍以 [自定义模型与模型映射设计](自定义模型与模型映射设计.md) 为准。

## 1. 问题定义

模型映射描述一条精确的一跳规则：

```text
客户端请求协议 + 客户端模型名
  -> 真实上游协议 + 真实上游模型
```

现有实现曾同时存在以下不同口径：

- 单账户编辑左侧加载协议级全局模型池，普通账户保存时却按当前供应商目录校验。
- `Responses -> Chat Completions` 通过右侧协议反向扩大左侧模型候选。
- 批量编辑没有完整复用单账户编辑的模型与协议过滤。
- 网关先按 `supportedModels` 标记直接匹配，再识别当前账户已显式配置的精确映射，导致候选排序分类与最终驱动实际执行的映射不一致。

这些差异会让页面展示可选但保存失败的模型，也会让用户难以区分客户端别名和真实上游能力。

## 2. 核心语义

### 2.1 左侧是客户端匹配键

`sourceModel` 是客户端请求体里的模型名，不代表当前账户真实支持该模型，也不代表上游具备该模型的协议能力。

- 普通供应商账户只允许选择当前供应商模型目录内的模型名，表达当前供应商内的客户端别名。
- 混合供应商账户允许按左侧来源协议从全局协议模型池选择模型名，表达跨供应商、跨协议入口。
- 左侧候选只由账户类型、当前供应商和左侧来源协议决定，不读取右侧目标协议或右侧目标模型。

普通账户不按左侧协议过滤当前供应商模型名。原因是 OpenAI v1 普通账户必须能显式表达 `Responses -> Chat Completions`；DeepSeek、GLM、Gemini OpenAI Chat 等真实上游模型通常只声明 Chat 能力，但仍可作为 Responses 客户端别名的来源模型。左侧协议由映射行显式保存，不需要再让模型目录协议字段重复决定。

### 2.2 右侧是真实上游能力

`upstreamModel` 是最终发送给当前账户真实 Base URL 的模型名。

右侧模型候选固定为：

```text
账户 supportedModels ∩ 支持右侧 upstreamEndpointFamily 的模型
```

后端保存必须再次执行相同校验。右侧模型不能通过自由输入绕过模型目录和账户支持模型边界。

### 2.3 协议矩阵只约束协议

来源协议和目标协议的组合由普通账户矩阵或混合供应商矩阵决定。协议矩阵可以：

- 限制来源协议下拉。
- 限制目标协议下拉。
- 根据右侧目标协议检查账户上游接口能力。

协议矩阵不得改变左侧或右侧另一端的模型目录范围。

### 2.4 显式映射优先识别

对于单个账户，如果请求精确命中启用的 `sourceModel + sourceEndpointFamily` 映射，即使 `sourceModel` 同时存在于该账户 `supportedModels`，该账户仍应按“映射匹配”分类，最终执行该映射。

不同账户之间仍保持：

```text
真正无映射的直接支持账户
  优先于
需要模型映射的账户
```

这样既保留直接账户优先级，也不会把同模型名、仅协议变化的显式桥接误分类成直接命中。

## 3. 供应商规则

| 供应商 / 档案 | 左侧模型范围 | 允许的协议方向 |
| --- | --- | --- |
| GPT、通用 OpenAI-compatible、xAI OpenAI v1 | 当前供应商目录 | Chat -> Chat；Responses -> Responses；Responses -> Chat，具体目标还需账户上游能力 |
| DeepSeek OpenAI v1 | DeepSeek 目录 | Chat -> Chat；Responses -> Chat |
| GLM OpenAI Chat | GLM 目录 | Chat -> Chat；Responses -> Chat |
| Gemini OpenAI Chat | Gemini 目录 | Chat -> Chat；Responses -> Chat；目标只能是 Chat |
| Anthropic、DeepSeek Anthropic、GLM Anthropic | 当前供应商目录 | Messages -> Messages |
| Gemini native | Gemini 目录 | GenerateContent -> GenerateContent；StreamGenerateContent -> GenerateContent |
| Hybrid | 左侧协议对应的全局协议模型池 | 按混合供应商白名单转到 Chat、Messages 或 GenerateContent；不合成 Responses 上游 |

通用 `openai` 供应商的“当前供应商目录”本身是 OpenAI-compatible 聚合目录，因此它仍可覆盖未深度接入但兼容 OpenAI v1 的模型；专用供应商不能引用其他供应商目录模型。

## 4. 页面规则

### 4.1 单账户编辑

- 区域名称继续使用“账号模型别名”。
- 左侧字段文案使用“客户端协议”“客户端模型”。
- 右侧字段文案使用“上游协议”“上游模型”。
- 普通账户左侧读取当前供应商完整模型目录，不随左右协议切换重新过滤。
- Hybrid 左侧按客户端协议加载 OpenAI、Anthropic 或 Gemini 全局协议模型池。
- 右侧只显示账户支持模型中支持所选上游协议的模型。
- 改变上游协议不得清空或改变左侧模型；异步目录刷新也不得静默清空已选值。
- 模型目录中不存在的历史值允许保留显示，但保存时由后端按当前完整模型拒绝。

### 4.2 批量编辑

- 只允许同供应商、同协议档案账户批量修改模型映射。
- 普通账户和 Hybrid 使用与单账户编辑相同的左侧模型策略。
- 右侧使用批量最终支持模型交集，并按上游协议过滤。
- 不维护第二套独立选择规则。

## 5. 保存与运行时校验

保存时固定校验：

1. `sourceModel`、`sourceEndpointFamily`、`upstreamModel`、`upstreamEndpointFamily` 非空。
2. 同一 `sourceModel + sourceEndpointFamily` 只能存在一条映射。
3. 协议方向命中当前账户类型的白名单。
4. 启用映射的右侧协议具备对应账户上游接口能力；停用映射可以保留。
5. 普通账户左侧模型存在于当前供应商目录；Hybrid 左侧模型存在于来源协议全局模型池。
6. 右侧模型存在于目标协议模型池、当前供应商目录或 Hybrid 目标协议池。
7. 右侧模型存在于账户最终 `supportedModels`。
8. 右侧模型声明支持目标上游协议。

运行时固定顺序：

1. 对每个账户先检查精确启用映射。
2. 映射存在且右侧模型仍属于账户支持模型时，将该账户分类为映射匹配。
3. 没有映射时再检查请求模型是否由账户直接支持。
4. 候选汇总时直接匹配账户排在映射匹配账户之前。
5. 驱动按同一精确映射改写模型和上游协议。

## 6. 非目标

- 不允许普通供应商账户跨供应商选择左侧模型。
- 不把模型映射迁移到 API Key、路由策略或分组。
- 不允许映射右侧自由输入未入模型目录的真实上游模型。
- 不新增自动猜测协议或相似模型回退。
- 不改变当前协议桥接白名单。
- 不新增数据库字段或历史运行时兼容分支。

## 7. 验收标准

- 普通 DeepSeek OpenAI 账户左侧只展示 DeepSeek 模型，不展示 GPT、GLM 或 Gemini 模型。
- DeepSeek / GLM / Gemini OpenAI Chat 账户仍可配置 `Responses -> Chat Completions`。
- 修改右侧上游协议不会改变左侧模型候选。
- Hybrid 切换客户端协议时按对应全局协议池切换左侧模型。
- 右侧模型始终来自账户支持模型并符合目标协议。
- 单账户编辑、批量编辑、前端保存和后端保存使用同一规则。
- 同模型名的 `Responses -> Chat Completions` 显式映射在网关候选分类和最终驱动中都按映射处理。
