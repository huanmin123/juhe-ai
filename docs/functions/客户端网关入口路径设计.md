# 客户端网关入口路径设计

> 状态：已实现，2026-05 路径边界改造落地。
> 关联文档：[中转透传机制调研与定位修正](中转透传机制调研与定位修正.md)、[OpenAI 账号接入](OpenAI账号接入.md)、[接口契约与权限矩阵](接口契约与权限矩阵.md)

## 1. 背景

`juhe-ai` 的客户端网关入口同时支持 `/v1/*` 和无 `/v1` 的同类 OpenAI 路径。后台管理、健康检查、静态资源和系统 API 统一挂在 `/__aisys__/*`，其余请求进入客户端网关，由本地 API Key 决定分组、供应商和账号池。

目标是让客户端请求路径是否显式带 `/v1` 不再决定能否进入网关。客户端路径只表达“要访问的上游资源”；本地 API Key 才决定使用哪个分组、供应商和账号池。

## 2. 设计目标

- 客户端 Base URL 可以填写服务根地址，也可以填写 `/v1` 地址。
- `/v1/*` 和无 `/v1` 的同类 OpenAI 路径在网关内部归一到同一语义。
- 本地 API Key 解析后，按绑定分组定位供应商和账号池，再交给供应商适配器处理。
- OpenAI API Key 账号保持公开 OpenAI API 的 raw body 透传优势。
- OpenAI OAuth / Codex 账号继续走专用适配器，不承诺支持公开 OpenAI API 的全部路径。
- 系统后台和管理 API 必须让出根路径，避免与客户端网关入口冲突。

不做的事情：

- 不把系统后台、管理 API、静态资源继续长期挂在根路径下。
- 不把所有供应商都强行转换为 OpenAI 协议。
- 不把上游不支持的路径伪装成网关支持；上游能力由供应商适配器和目标服务决定。
- 不透传本地认证头、代理链路头、危险协议头或系统内部头。

## 3. 路径边界

当前路径分层：

| 路径 | 归属 | 说明 |
| --- | --- | --- |
| `/__aisys__/*` | 系统后台 | 管理前端、管理 API、健康检查、静态资源和系统配置 |
| `/v1/*` | 客户端网关 | 标准 OpenAI-compatible 入口 |
| `/*` | 客户端网关 | 排除系统前缀后进入网关 |

系统前缀使用 `/__aisys__`，原因是它不像通用业务路径，和未来 OpenAI / 其他供应商新增 API 路径冲突的概率更低。

当前路径边界只保留上述三类入口：系统请求必须使用 `/__aisys__/*`，客户端请求使用 `/v1/*` 或根路径 OpenAI 资源路径。非系统前缀请求会进入客户端网关；没有本地 API Key 时返回网关认证错误。

## 4. 请求处理流程

目标主链路：

```text
HTTP 请求进入服务
-> 如果路径匹配 /__aisys__/*，走系统后台路由
-> 否则进入客户端网关
-> 提取 Authorization: Bearer <本地 API Key>
-> 校验 API Key 状态、额度、授权和分组绑定
-> 根据分组定位 provider
-> 从分组账号池选择可调度账号
-> 供应商适配器归一化路径、Header、Body 和上游认证
-> 请求账号配置的 Base URL
-> 流式或非流式返回客户端
-> 写入使用记录和原始审计
```

这个流程里，客户端路径不决定“能否进入系统”；它只作为供应商适配器构造上游请求的输入。

## 5. OpenAI 路径归一化

OpenAI 官方 API 的 base URL 是 `https://api.openai.com/v1`。因此对 OpenAI API Key 账号，网关应保证上游最终路径有且只有一个 `/v1` 版本前缀。

### 5.1 下游路径归一化

客户端请求路径：

| 客户端请求 | 归一化语义 |
| --- | --- |
| `/v1/models` | `/v1/models` |
| `/models` | `/v1/models` |
| `/v1/chat/completions` | `/v1/chat/completions` |
| `/chat/completions` | `/v1/chat/completions` |
| `/v1/responses` | `/v1/responses` |
| `/responses` | `/v1/responses` |
| `/v1/images/generations` | `/v1/images/generations` |
| `/images/generations` | `/v1/images/generations` |

查询字符串必须保留，例如 `/responses?stream=true` 归一化后仍保留 `?stream=true`。

### 5.2 Base URL 拼接规则

对 OpenAI API Key 账号，账号 `base_url` 可以是官方根地址、官方 `/v1` 地址，或带自定义前缀的中转地址。拼接时必须避免重复 `/v1`，也不能漏掉 `/v1`。

| 账号 Base URL | 客户端路径 | 上游 URL |
| --- | --- | --- |
| `https://api.openai.com` | `/responses` | `https://api.openai.com/v1/responses` |
| `https://api.openai.com` | `/v1/responses` | `https://api.openai.com/v1/responses` |
| `https://api.openai.com/v1` | `/responses` | `https://api.openai.com/v1/responses` |
| `https://api.openai.com/v1` | `/v1/responses` | `https://api.openai.com/v1/responses` |
| `https://example.com/openai/v1` | `/responses` | `https://example.com/openai/v1/responses` |
| `https://example.com/openai/v1` | `/v1/responses` | `https://example.com/openai/v1/responses` |

错误结果示例：

| 错误 URL | 问题 |
| --- | --- |
| `https://api.openai.com/v1/v1/responses` | 重复 `/v1` |
| `https://api.openai.com/responses` | 漏掉 OpenAI API 版本前缀 |
| `https://example.com/v1/responses` | 丢失账号 Base URL 中的自定义前缀 |

## 6. 供应商适配边界

### 6.1 OpenAI API Key 账号

- 入口路径可宽松，最终上游路径按公开 OpenAI `/v1` API 归一化。
- 请求体优先使用客户端原始 `rawBody` 透传。
- Header 以客户端语义头为基础，过滤本地认证、代理链路、危险协议头、SDK / tracing 噪声和 OpenAI 组织 / 项目上下文头。
- 上游认证统一替换为被调度账号的 OpenAI API Key。
- 目标上游不支持某个 OpenAI 路径时，由上游返回错误，网关按现有错误策略记录和返回。

### 6.2 OpenAI OAuth / Codex 账号

- 客户端入口仍可走 `/v1/*` 或无 `/v1` 的等价路径。
- 实际上游不是公开 `api.openai.com/v1`，而是 ChatGPT / Codex backend。
- 适配器只承诺自身支持的 Codex 路径和请求体形态，例如 `/responses` 与 `/responses/compact`。
- 对不支持的路径，应返回清晰的网关错误或上游适配错误，不能伪装成通用 OpenAI API Key 透传。

### 6.3 后续供应商

其他供应商接入时，应遵守同一分层：

- 入口层只负责系统路径排除、API Key 鉴权和请求交给网关。
- 分组 / 供应商决定使用哪个 adapter。
- adapter 决定路径归一化、上游 URL、认证头和请求体转换策略。

## 7. 实施策略

### 7.1 一次性边界改造

本设计不采用“先别名、再迁移、再 catch-all”的过渡期方案，而是在一次功能改造中完成路径边界切换：

- 系统后台、管理 API、健康检查和静态资源迁移到 `/__aisys__/*`。
- `/v1/*` 保持为标准客户端网关入口。
- 非 `/__aisys__/*` 的其他请求全部进入客户端网关。
- OpenAI API Key 账号的上游路径统一归一化为有且只有一个 `/v1`。
- 前端路由、前端 API base、API Key 页面展示的网关 Base URL、开发代理、部署反向代理、烟测脚本和文档在同一批变更中同步更新。

### 7.2 系统前缀迁移

将系统能力迁移到 `/__aisys__`：

- 管理 API：`/__aisys__/api/*`
- 后台前端：`/__aisys__/`
- 静态资源：确认构建产物和品牌图标在 `/__aisys__/*` 下可访问
- 健康检查：`/__aisys__/health`
- 前端路由 base：切到 `/__aisys__/`
- 前端 API base：切到 `/__aisys__/api`
- 开发代理和部署反向代理同步更新

### 7.3 根路径网关 catch-all

系统前缀迁移完成后，启用根路径网关入口：

```text
非 /__aisys__/* 请求 -> 客户端网关
```

客户端可以把 Base URL 填为：

```text
http://host:port
http://host:port/v1
```

并获得一致的 OpenAI API Key 账号转发行为。

### 7.4 首批必须覆盖的客户端路径

根路径 catch-all 启用后，以下路径不再作为白名单限制，而是作为首批回归重点：

- `GET /models`
- `GET /models/:model`
- `POST /chat/completions`
- `POST /responses`
- `POST /responses/*`
- `GET /responses`
- `POST /images/generations`
- `POST /images/edits`
- `POST /embeddings`
- `POST /audio/transcriptions`
- `POST /audio/translations`
- `POST /audio/speech`

## 8. 验证清单

OpenAI API Key 账号至少验证：

| 请求 | 预期 |
| --- | --- |
| `GET /models` | 与 `GET /v1/models` 一致 |
| `POST /chat/completions` | 与 `POST /v1/chat/completions` 一致 |
| `POST /responses` | 与 `POST /v1/responses` 一致 |
| `POST /images/generations` | 与 `POST /v1/images/generations` 一致 |
| Base URL 为 `https://api.openai.com` | 自动补 `/v1` |
| Base URL 为 `https://api.openai.com/v1` | 不重复 `/v1` |
| Base URL 为 `https://example.com/openai/v1` | 保留 `/openai` 前缀 |

OpenAI OAuth / Codex 账号至少验证：

| 请求 | 预期 |
| --- | --- |
| `POST /responses` | 能进入 Codex adapter |
| `POST /v1/responses` | 与无 `/v1` 一致 |
| `POST /chat/completions` | 返回清晰的不支持错误或适配错误 |

系统路径至少验证：

| 请求 | 预期 |
| --- | --- |
| `/__aisys__/` | 打开后台 |
| `/__aisys__/api/settings/public` | 返回公开设置 |
| `/__aisys__/health` | 返回健康状态 |
| `/api/*` | 不再命中系统管理 API；按客户端网关路径处理 |
| `/` | 不再返回后台页面；按客户端网关路径处理 |
| 非系统路径无 API Key | 返回网关认证错误，不返回前端 HTML |

## 9. 风险与约束

- 根路径 catch-all 启用前，系统后台必须先迁移到独立前缀，否则前端页面和网关入口会互相抢路径。
- OpenAI `/v1` 是上游协议版本前缀；客户端可以不写，但网关最终发往 OpenAI API Key 上游时必须补齐。
- 不能把 OAuth / Codex 账号等同于 OpenAI API Key 账号；它们的上游协议和支持路径不同。
- 管理 API 固定使用 `/__aisys__/api/*`，健康检查固定使用 `/__aisys__/health`；实现时必须同步更新前端、脚本、部署文档和运维检查地址，避免系统内部调用访问错误路径。
- 文档、部署反向代理、烟测脚本、回归脚本和前端复制的网关 Base URL 需要随阶段同步更新。
