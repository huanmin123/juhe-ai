# 账号健康检测设计

> 本文记录当前账户哨兵健康机制。多模型账户的完整目标以 [AI 账户多模型能力健康与精确隔离设计](AI账户多模型能力健康与精确隔离设计.md) 为准：周期检查模型失败只更新该哨兵能力，真实请求失败按精确模型能力触发独立探针，部分能力失败不得直接写整号 `temporary_unavailable`。

账户哨兵 Route 由 `healthCheckModel + healthCheckEndpointMode` 共同定义。`healthCheckEndpointMode` 保存 JSON / Streaming 精确请求形态；首次激活和 active 周期哨兵使用该 Route。请求失败确认、精确能力恢复和 `protocol_model` 恢复必须使用真实 Attempt 持久化的 ProbeRecipe；账号冷却和 Key 恢复只消费各自匹配 provenance，不得回退到账户哨兵。GPT 新账户默认 `responses_sse`，其他协议档案默认对应 JSON mode；人工诊断可显式选择其他已启用 mode。

## 1. 背景与目标

账号列表中长期处于 `active` 的账户，可能因为上游凭据失效、代理异常、套餐变化、上游封禁或账户内 API Key 全部不可用而实际无法调用。只依赖真实流量失败或用户主动诊断，会导致“看起来正常，实际死号”的账户长期留在可调度池里。

本设计目标是增加一套轻量后台健康检测：

- 正常且可调度的 AI 账户默认约每 1 小时获得一次哨兵 Route 观察；稳定抖动后最长为 1 小时 10 分钟。该观察不代表整个账户或全部模型已经确认可用。
- 最近已有与哨兵完整 Route 相同的真实成功请求时不额外探测；其他模型、endpoint、转换路径或 Key 的成功不能顺延哨兵。
- 探测使用共享的账户最小请求执行器；active 哨兵严格读取 `healthCheckModel + healthCheckEndpointMode`，pending_test 使用 Catalog 冻结的多 Route activation selection。pending_test 由激活策略管理账户状态，active 账户只更新哨兵健康和精确模型能力。
- 完整 HTTP / SSE 但协议未成功对 transport 电路保持中性；对 active 的 execution 哨兵能力形成通用 unavailable，只阻断该精确能力，不按状态码或正文解释具体错误语义。
- 前端账号列表能看到最近检测时间、下次检测时间、连续失败次数和失败原因。
- 周期健康检查是基础机制，所有未停用账户都按自身状态进入对应系统检查，不提供账户级关闭开关。

## 2. 范围边界

本次纳入：

- `accounts` 增加健康检测事实字段。
- `ops-worker` 增加正常账户周期探测任务。
- 后台任务按到期窗口分批读取账户，不全量扫描后在内存过滤。
- `active` 周期 tick 只创建哨兵 admission trigger；accepted 后由统一 logical intent / physical execution 调用纯结果 `executeAccountProbe()`，再由 intent owner 应用允许的健康事实副作用。tick 不直接请求上游。
- 管理侧和用户侧账户列表展示健康检测信息。
- 人工“测试”保留为零生产状态副作用的诊断工具，不作为健康检测或恢复入口。

本次不纳入：

- 不再新增一套“账户健康专用”分布式状态机；完整目标复用 capability v2 的 PostgreSQL durable admission / due、Redis 派生投影和 Go Asynq physical worker，外部 cron 只可唤醒 control scheduler，不能直接执行探针。
- 新账户首次激活、连接配置变更和普通周期复检共用统一 physical probe 预算。首次激活优先级最高并保留执行容量，但仍受每物理账户 running=1、自动 physical start 5 分钟门禁和 global budget，不能通过旧 ops-worker 直调扩大并发。
- 不用同一个周期候选查询处理停用、待检查、异常或冷却账户；`pending_test` 进入激活检查，`temporary_unavailable / rate_limited` 进入冷却恢复，`error` 只进入明确可自动恢复的对应后台任务，`disabled` 尊重人工停用。
- 激活检查成功只确认上游连接健康；账户从 `pending_test` 退出时仍需按当前时间计划决定进入 `active` 还是 `disabled`，不能因健康成功绕过时间计划。
- 不把健康检测作为新的 `accounts.status` 枚举；物理状态仍只使用现有 `active / pending_test / disabled / error / rate_limited / temporary_unavailable / quality_isolated`。
- 不为旧数据库结构写运行时兼容迁移；上线或本地数据同步由用户按当前 schema 离线处理。

## 3. 数据字段

账户检查配置：

| 字段 | 默认值 | 含义 |
| --- | --- | --- |
| `health_check_model` | 必填 | 账户固定哨兵模型，必须属于最终 `supportedModels`，且能按账户协议档案发起最小文本检查请求。只供激活、周期哨兵和真正账户全局 owner 使用；请求派生及模型能力恢复探针使用持久 `ProbeRecipe`。 |

`accounts` 健康事实字段：

| 字段 | 默认值 | 含义 |
| --- | --- | --- |
| `last_health_check_at` | `NULL` | 最近一次后台健康检测完成时间。手动测试不写该字段。 |
| `next_health_check_at` | `NULL` | 下次后台健康检测计划时间。为空时由候选查询按创建 / 更新时间补计划。 |
| `health_check_schedule_reason` | `NULL` | `regular_sentinel / infrastructure_retry / config_recheck / activation_retry`；只解释账户哨兵时钟，不承载 capability recovery due。 |
| `health_check_schedule_attempt` | `0` | 仅基础设施重排的有界级别；完整上游失败不增加，正常完成或配置 revision 接管时清零。 |
| `last_health_success_at` | `NULL` | 最近一次哨兵 Route 成功时间。后台检查和与当前哨兵 Route 匹配的真实网关成功都可刷新。 |
| `last_health_success_route_scope_id` | `NULL` | 成功所对应的不可逆 `routeScopeId`；不含具体 Key，但包含最终模型、endpoint、lane、adapter route 和账户运行身份。 |
| `last_health_success_dispatch_revision` | `NULL` | 成功时的 `effectiveDispatchRevision`，用于阻止连接、凭据或转换目标变化后复用旧成功。 |
| `last_health_success_universe_revision` | `NULL` | 成功时的 `capabilityUniverseRevision`，用于阻止模型目录、endpoint、映射或 Key 集合变化后复用旧成功。 |
| `health_check_failure_count` | `0` | 兼容的 `pending_test` 诊断计数，只描述当前 activation selection 已完成的失败 Attempt；不能形成整号阈值，精确事实仍在 capability ledger。task failure / stale / unknown 不增加，active 周期哨兵不得使用。 |
| `health_check_failure_started_at` | `NULL` | 当前 activation selection 首个精确失败的诊断时间；success、重建 selection 或关键连接配置重置时清空。它不授权 24 小时后写整号 error。 |
| `last_health_check_status_code` | `NULL` | 最近一次后台健康检测收到的 HTTP 状态码，仅用于诊断，不授权状态变化。 |
| `last_health_check_error_code` | `NULL` | 最近一次后台健康检测错误码，仅用于有界诊断。 |
| `last_health_check_error_message` | `NULL` | 最近一次后台健康检测摘要，不作为自动状态语义来源。 |

字段定位：

- `last_health_success_at` 必须与三个成功身份字段作为一个原子水位读写；任一字段缺失或与当前解析出的哨兵 Route / revision 不匹配，都不能跳过本轮检查。
- `routeScopeId` 是 Route 级身份，不含具体 Key；Key 级 execution incident 仍使用含 `credentialScopeKey` 的精确 `scopeId`，两者不能互换。
- `health_check_model` 是账户配置，不是最近成功模型，也不由人工测试结果回写。
- `last_used_at` 仍表示真实业务流量最近使用时间，不被后台探测更新。
- `cooldown_retest_*` 仍只表示临时不可调用 / 限流账户的恢复复测，不和正常账户健康检测混用。
- `account_quality` 仍表示近期真实流量质量，不能替代长期空闲账户探活。
- 每个精确 Attempt capability ledger 另有单调递增的 `positiveObservationVersion`。独立探针 claim 必须保存 `claimedPositiveObservationVersion`；这两个版本不属于 `accounts` 哨兵字段，不能用账户级成功时间代替。

## 4. 调度策略

默认设置：

- 基础间隔：1 小时。
- 抖动窗口：0 到 10 分钟，按账户 ID 稳定计算；同一账户跨轮次和进程重启保持固定偏移，避免整点集中探测。
- 单轮批量：默认 20 个，受系统设置上限保护。
- 全局 physical probe 默认并发最多 10；首次激活和连接配置变更属于高优先级，普通周期复检最多占用 7 个槽位，为用户可见的新账户激活保留 3 个槽位。它还要与 capability 统一 global budget 对账，不能形成第二套 10 槽池。
- 同一账户等待期间重复 trigger 只更新 durable admission / schedule；已有 intent 或 physical execution 时返回 covered，检查已经运行时不追加第二次上游调用。配置变化由新 definition revision 的 selection / trigger 接管，旧任务 stale。
- owner 角色：control scheduler 负责到期扫描与 admission，Go Asynq worker 只执行已持久 claim 的 physical execution；legacy `ops-worker -> executeAccountProbe()` 直调在 capability v2 激活前必须下线。
- 调度频率：沿用账号探测类后台任务的短周期 tick，每次只捞取到期窗口。

active 周期候选条件：

- `status = active`。
- `schedulable = 1`。
- 未删除。
- 未过期。
- 当前不在冷却期。
- 可用时段允许。
- `next_health_check_at <= now`，或者 `next_health_check_at IS NULL` 且缺少近期成功健康信号。
- 与当前哨兵 `routeScopeId + effectiveDispatchRevision + capabilityUniverseRevision` 完全一致的成功水位在最近 1 小时内存在时，跳过主动探测并顺延；账户级 `last_used_at`、其他能力成功和旧 revision 成功不作为判断。

排序：

- `next_health_check_at ASC NULLS FIRST`。
- `last_health_check_at ASC`。
- `created_at ASC`。
- `id ASC`。

后台不得一次性拉取全部账号再过滤；必须在 SQL 中按状态、时间和 limit 取候选。

候选被捞取只表示“应尝试建立哨兵 observation”，不代表允许物理发送。control scheduler 必须先走统一 durable admission：`already_running / OPEN_not_due / HALF_OPEN / RECOVERING / automatic_5m_cooling / saturated` 分别闭合为 covered、cooling 或有界 retry，并在同一账户计划 CAS 中推进下一次哨兵时钟；只有 accepted -> group claim ledger committed 后，Asynq worker 才能调用上游。账户 1 小时哨兵时钟与 capability 的 5 分钟恢复 due / 每物理账户 5 分钟启动门禁是三条不同语义的时钟，不能互相消费或重复派发。

## 5. 探测行为

健康检测在统一 admission accepted 后复用共享系统探针执行器：

- 通过 `findAccountForTest` 读取账户。
- active 周期哨兵严格使用账户保存的 `healthCheckModel + healthCheckEndpointMode`；缺失、不可见、不属于 `supportedModels` 或无法按协议完成对应探针时，记录“检查模型配置异常”并按配置重排停止本轮，不回退个人默认、管理员默认、协议档案默认或支持模型首项。
- pending_test 不再把单一 healthCheckModel 当整号准入。配置 owner 先生成 ready Catalog / credential baseline，再冻结一个 activation selection：只包含无需额外成本的 execution Attempt，优先 healthCheckModel，随后按 Route / credential 稳定排序；单轮最多物化 8 项。每个失败只进入自己的 capability ledger，后续候选仍按每物理账户 5 分钟启动门禁轮转；任一当前 definition / binding 的 complete_success 即可完成激活。
- worker 使用 `executeAccountProbe()` 执行真实网关链路诊断，底层执行器只返回诊断结果；scheduler / tick 不得调用它。
- 使用账户绑定代理。
- OAuth 账户按网关准备逻辑刷新 token。
- API Key 账户复用账户测试的最小请求构造，但生产探针走独立 intent / audit owner。普通生成模型按冻结 Attempt 的 endpoint mode 执行，不从最近真实请求反推。OpenAI v1 纯图像模型目录检查仍只得到 catalog 可见性，不能完成 pending 激活或形成 execution 成功；周期任务不得执行付费生图。
- 流量来源固定标记为 `account_health_check`，不伪装成真实网关流量、人工测试或 `cooldown_retest`，不计入常规质量统计。
- 候选入队时携带 route / attempt definition revisions、membership incarnations、binding 权限版本与账户 publication provenance；执行前和结果落库时再次校验。只有 scope definition / incarnation / binding 真正变化才 stale；无关账户 revision 变化 carry-forward，不能让所有模型结果一起作废。

结果处理统一使用：`complete_success`、`framing_complete_neutral`、仅代表 `transport_incomplete` 的 `upstream_failure`，以及 `probe_task_failure/stale/unknown`。结果名称描述传输事实；固定模型、固定协议的账户可用性检查还会把 `framing_complete_neutral` 作为通用可用性失败，不能把它误当成传输电路失败。

- `complete_success`：
  - `last_health_check_at = now`。
  - 原子写入 `last_health_success_at = now`、当前 `last_health_success_route_scope_id`、`last_health_success_dispatch_revision` 和 `last_health_success_universe_revision`。
  - `next_health_check_at = now + 1h + jitter`，`health_check_schedule_reason=regular_sentinel`，基础设施 schedule attempt 清零。
  - `pending_test` 只有在结果属于当前 activation selection / definition / binding 时，才清空激活失败计数、首次失败时间和最近健康检测错误字段，并按时间计划进入 `active` 或 `disabled`；不要求 healthCheckModel 必须是成功项。
  - `active` 只向当前精确 Route / Attempt 提交正向 execution 观察并更新哨兵计划，不清理或恢复任何账户硬状态。
- `transport_incomplete` 或账户可用性检查中的 `framing_complete_neutral`：
  - `last_health_check_at = now`。
  - 写入最近状态码、错误码和失败摘要。
  - `pending_test` 只对当前 activation selection 的该 Attempt 执行诊断计数，并把 unavailable 提交给精确 capability；若 selection 尚有合法候选，则计划时间取 `max(next automatic physical probe gate, candidate due)`，否则写 `activation_unconfirmed / owner_action_required` 并按 1 小时 + jitter 重建 selection。超过 24 小时只升级提示和运维告警，不写整号 error。只有本地证明确实覆盖全部 Route / credential 的共用配置错误，才由 account-global configuration owner 独立写 error。
  - 普通 `active` 周期检查只把 execution 结果提交给当前精确 Route / Attempt 的 `model_capability` scope 并记录哨兵观察；同时原子写 `next_health_check_at = now + 1h + jitter`、`schedule_reason=regular_sentinel`，不增加账户失败计数，不按次数写整号 `temporary_unavailable`。对应 capability blocked 的首次恢复 due 由 capability outcome 事务另行写 5 分钟时钟。
  - 只复用现有 transport 冷却 / 事前确认策略；不得从状态码、错误码、错误类型或正文推断账号级业务故障。
  - 只有本地目录 / 能力可以验证的检查模型缺失、检查模型不属于支持模型、没有可执行 endpoint mode 或最小请求模板构造错误才记录配置异常并走 `probe_task_failure/unknown`。上游 status/body 声称的 `model_not_found`、未授权或 `unsupported_endpoint` 不派生具体语义；framing 完整时仍是 `framing_complete_neutral`，但受控账户可用性检查可以把“协议未成功”作为通用失败。
  - PostgreSQL 的 pending 激活计数必须在行锁事务内读取和递增，并校验任务的 Route、revision 与当前配置一致，禁止“先读后覆盖”造成丢失更新。active capability intent 建立后，真实业务成功生成确定性 observationId，并由 control owner 在 PostgreSQL scope 串行化事务内原子插入 committed observation、递增精确 Attempt 的 `positiveObservationVersion` 和写连续 outbox；不能直接终结 intent，未提交事务的成功诊断也不能充当 fence。
- `framing_complete_neutral`：对 transport 电路、账号冷却恢复和 Key 恢复保持中性并最多关闭同来源 transport 怀疑；对 pending_test 激活计入哨兵失败，对 active execution 哨兵只形成精确能力 unavailable。请求失败确认不再进入账户哨兵服务。
- `probe_task_failure` / `unknown`：不增加健康或能力失败计数、不改变 phase；同一账户哨兵 schedule 用独立基础设施退避 5、15、30、60 分钟（此后保持 60 分钟并加稳定 jitter）CAS 写 `next_health_check_at / schedule_reason=infrastructure_retry / schedule_attempt`。它不创建 capability recovery due，也不得保留已过期时间形成 tick 热循环。
- `stale`：旧任务只终结自身，不写 last result、failure count 或旧 revision 的 next time；配置事务 / 新 revision owner 原子建立至多一条 `config_recheck` 计划，默认立即到 5 分钟内且仍受 physical 5 分钟门禁。若新 revision 已有更晚计划，旧结果不能回拨。

PostgreSQL 各类结果写回的可选 CAS 条件只在参数存在时动态追加；禁止使用无类型上下文的 `$n IS NULL` 守卫。除 stale 由新 revision owner 接管外，accepted / covered / cooling / saturated / complete success / complete failure / task failure / unknown 的每个终态分支都必须以当前 schedule fencing 在同一事务 CAS `next_health_check_at + schedule_reason + schedule_attempt`，不得留下 overdue 行。周期候选优先处理 `pending_test`；`pending_test` 且从未完成后台检查时忽略遗留的未来复检时间和普通成功信号，人工诊断或真实流量成功不能替代后台 activation selection，即时投递失效时新账户仍能被分钟级任务尽快兜底。

普通 `active` 周期失败策略：

- 每次结果继续写 v1 哨兵小时事实和最近检查摘要。
- execution 探针失败按精确 model + endpoint + lane + adapter route + credential scope 进入能力状态机。
- catalog_only 只写目录可见性，不改变 execution 能力。
- 无论连续多少次，都不写整号 temporary_unavailable；后续由精确能力 half-open / recovering 自动恢复。
- 真实请求失败由请求终态 CapabilityFailureCollector 处理，并先写 release 外 gateway durable capability handoff 后再提交精确 admission；控制面短时失败由同 handoffId 重放，不复用本周期队列、账户阈值或 healthCheckModel，也不等待下一次用户失败补触发。
- active 周期检查不消费 `accountHealthCheckFailureThreshold`；该旧设置不得再授权任何账户状态转换。

## 6. 与真实流量的关系

真实网关请求成功是最可靠的健康信号：

- 只有与当前哨兵 `routeScopeId + effectiveDispatchRevision + capabilityUniverseRevision` 相同的成功请求可以原子刷新完整哨兵成功水位，并把 `next_health_check_at` 顺延到 `successAt + 1h + jitter`；同 Route 的任一当前可执行 Key 成功都可证明本轮账户哨兵，Key 级阻断仍由精确 capability scope 独立保存。
- 迁移前既有 Node adapter 必须保持系统间隔、稳定账户 jitter 和半窗口写入节流语义一致；完整目标只保留 PostgreSQL 权威写入，不能只更新成功时间而漏写 Route、revision 或下一次复核计划。
- 成功请求刷新健康信号按检测窗口节流；离下次检测还很远时不反复写 `accounts`，快到期、计划缺失、设置缩短或存在健康失败状态时再顺延。
- 普通网关失败仍由现有请求级错误处理和 transport 运行态负责，不直接写健康检测失败次数；完整 HTTP/协议结果不写共享业务状态。
- 失败请求不会刷新健康成功信号，也不会因为更新 `last_used_at` 而跳过后台健康检测。
- 同一哨兵 Route 的真实成功和后台失败并发时，v1 水位按事务完成时间记录观察，v2 capability 按 active generation / ledger CAS 收敛。业务成功不能直接终结 active intent；存在 active intent 时必须通过 committed observation + version + outbox 的 PostgreSQL 原子事务递增该精确 Attempt 的 `positiveObservationVersion`，不得因普通 15 分钟正向写节流而跳过。physical claim 保存 `claimedPositiveObservationVersion`；claim 之后出现更高版本成功时，迟到的负向 outcome 标记为 `superseded_by_newer_success`，不得转 OPEN；当前 logical intent 终态并写 durable due，调度器使用新 generation / physicalExecutionId 验证。其他 Route 成功仍不能刷新该哨兵水位。

这样可以减少后台探测量：活跃账户由真实流量自然证明可用，长期空闲但显示正常的账户才需要探测。

## 7. 前端展示

当前账户状态卡片只消费统一 `availabilityPresentation`：状态、最近检查、下次实际检查、原因和最近检查 `traceId`。健康检查、冷却复测、来源账户探针、Key 复测和运行态探针都映射为同一组 observation/schedule 字段，不能把历史健康成功、旧计划或内部任务时间拼到当前状态上。数据库状态、进程缓存、失败计数、来源统计、探针轮次和质量算法说明不属于用户卡片。

账号列表状态 tooltip 按“当前状态 + 最近检查事实 + 下一步检查计划”展示：

- 最近一次实际检查时间与结果。
- 仍有真实任务时显示下次检查；正在执行显示“正在检查”，任务不存在显示“暂无计划”。
- 当前原因和最近一次失败的状态码、错误码、摘要与 `traceId`。
- 仅在用户显式策略存在时显示策略释放边界。

展示原则：

- 不新增醒目的硬状态标签覆盖 `active`，避免和近期质量、冷却、授权实例状态混淆。
- `pending_test` 在尚未完成任一 activation Attempt 时显示“激活待确认”；有精确失败但 selection 仍有候选时显示“正在验证其他能力”，全部免费候选尚无成功时显示“需要账户所有者处理”。24 小时只升级告警，不把某个模型的失败显示成整号 error。
- “重新检查”先原子重建当前 Catalog / activation selection，并按统一 admission 尝试首项，不能清理已有精确 blocked 或直接改 active。`error` 的“异常恢复”同样只进入干净的 `pending_test` 并创建 selection，不能直接写为 `active`。
- 后台复测节奏和终止条件属于运维日志与详情排障信息，不在列表状态 tooltip 展示。
- 手动“测试”只展示诊断结果；成功或失败都不写健康事实、不恢复账户状态，也不改变下次后台检测计划。

## 8. 设置与默认值

建议新增系统设置白名单：

| 设置项 | 默认值 | 范围 | 说明 |
| --- | --- | --- | --- |
| `accountHealthCheckIntervalHours` | `1` | `1..168` | 正常账户健康检测基础间隔。 |
| `accountHealthCheckJitterMinutes` | `10` | `0..1440` | 下次检测按账户 ID 计算的稳定错峰窗口。 |
| `accountHealthCheckBatchSize` | `20` | `1..100` | 单轮到期账户候选批量。 |

如暂不增加设置页面，后端可先使用默认值和 settings helper 读取，缺省时回落到上述值。遗留 `accountHealthCheckFailureThreshold` 不再属于本机制的有效设置，active 周期检查和 pending 激活终态都不得消费它；pending 超过 24 小时仍未取得任何合法 activation success 时只升级 owner_action_required 告警，不产生账户状态转换。

## 9. 验证项

- 新库 schema 能创建健康检测字段。
- 到期候选 SQL 按八种 JSON / Streaming 生成 `healthCheckEndpointMode` 返回待检查，或正常、可调度、未过期、未冷却且到期的账户；覆盖 OpenAI Chat / Responses、Anthropic Messages 和 Gemini GenerateContent，工具类接口不进入候选。
- 候选查询不存在 `health_check_enabled` 条件，账户接口和页面不存在周期检查关闭开关。
- 最近 1 小时只有与当前哨兵 routeScopeId 和两个 revision 都匹配的真实成功信号会顺延计划；其他 Route 或旧 revision 成功不跳过探测。
- active 周期哨兵严格使用账户 `healthCheckModel + healthCheckEndpointMode`，非法时不回退；pending_test 只使用 ready Catalog activation selection 中冻结的合法免费 execution Attempt，不能回退目录默认或单一哨兵整号判死。
- `pending_test` 的 `complete_success` 会清空激活失败计数和首次失败时间，并写入下次计划；`active` 的 `complete_success` 只更新精确 Route / Attempt 的正向观察和哨兵计划。
- `pending_test` 的每个独立探针未通过协议可用性校验时，只增加当前 selection 的诊断计数、保留首次失败时间并安排下一合法候选 / 1 小时重建；任一候选成功即可激活。满 24 小时仍无成功只产生 owner_action_required，任务故障、stale 和 unknown 不推进该告警窗口。
- 配置版本变化会使旧探测结果 stale；业务成功不直接终结 active intent，但 claim 后递增的 `positiveObservationVersion` 会使迟到负向 outcome superseded，并通过 durable due 触发新 generation 独立验证。
- active 连续哨兵失败只更新精确模型能力，账户不得进入通用临时不可调用；transport 电路仍只接受真实传输失败。
- active tick 在 scope 已有 intent、OPEN 未 due、HALF_OPEN / RECOVERING、账户自动 physical 5 分钟门禁未到和预算饱和时均不会直接调用上游；每个分支仍推进账户哨兵计划。active 完整失败写 1 小时 + jitter，task failure / unknown 写 5/15/30/60 分钟基础设施重排，stale 由新 revision 唯一计划接管，不存在 overdue 热循环。
- 多 scheduler / 重启下 activation selection 的 cursor、page claim 和 item disposition 单调推进；模型 B 失败后模型 A 成功可以激活，B 仍保持精确 blocked。删除后原样重加的 Route / credential 使用新 membership incarnation，旧结果不能污染新 selection。
- 冷却复测候选按 `healthCheckEndpointMode` 的八种生成请求形态筛选，覆盖 OpenAI Chat / Responses、Anthropic Messages 和 Gemini GenerateContent 的 JSON / Streaming；模型列表、计数 Token 等非生成工具接口不进入候选。
- “重新检查”和“异常恢复”都只重置到不可调度的 `pending_test` 并立即投递后台检查；自有账户的 `pending_test`、`error` 等所有非停用状态均可人工停用。
- 人工测试成功或失败后账户、授权实例、Key、健康事实和运行态均不变化。
- 前端账户列表能展示健康检测时间和失败原因。
- `pnpm --filter juhe-ai-backend typecheck` 和 `pnpm --filter juhe-ai-frontend typecheck` 通过。
