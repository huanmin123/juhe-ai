# 账号健康检测设计

账户健康事实由 `healthCheckModel + healthCheckEndpointMode` 共同定义。`healthCheckEndpointMode` 保存 JSON / Streaming 精确请求形态；首次激活、周期复检、冷却恢复和运行态恢复都直接使用该值，不再从协议族推导或自动切换。GPT 新账户默认 `responses_sse`，其他协议档案默认对应 JSON mode；人工诊断可显式选择其他已启用 mode。

## 1. 背景与目标

账号列表中长期处于 `active` 的账户，可能因为上游凭据失效、代理异常、套餐变化、上游封禁或账户内 API Key 全部不可用而实际无法调用。只依赖真实流量失败或用户主动诊断，会导致“看起来正常，实际死号”的账户长期留在可调度池里。

本设计目标是增加一套轻量后台健康检测：

- 正常且可调度的 AI 账户默认每 1 小时至少获得一次可用性确认。
- 最近已有真实成功请求的账户不额外探测，避免重复消耗上游和代理资源。
- 探测使用共享的账户最小请求执行器，严格读取账户 `healthCheckModel`，并由周期健康检查策略决定健康事实和账户状态副作用。
- 完整 HTTP / SSE 但协议未成功对 transport 电路保持中性，但作为固定模型、固定协议的独立账户可用性探针失败会累计健康阈值；任意结果都不按状态码或正文解释具体错误语义。
- 前端账号列表能看到最近检测时间、下次检测时间、连续失败次数和失败原因。
- 周期健康检查是基础机制，所有未停用账户都按自身状态进入对应系统检查，不提供账户级关闭开关。

## 2. 范围边界

本次纳入：

- `accounts` 增加健康检测事实字段。
- `ops-worker` 增加正常账户周期探测任务。
- 后台任务按到期窗口分批读取账户，不全量扫描后在内存过滤。
- 健康探测复用纯诊断的 `executeAccountProbe()`，并由 `runScheduledHealthCheck()` 应用允许的健康事实副作用。
- 管理侧和用户侧账户列表展示健康检测信息。
- 人工“测试”保留为诊断工具，不作为健康检测或激活入口；仅已保存自有账户的列表测试在模型和精确请求形态都等于保存检查配置、协议成功且持久不可调度时，允许受版本 CAS 保护地恢复调度资格。

本次不纳入：

- 不新增独立分布式队列、Redis、外部 cron 或多实例协调。
- 新账户首次激活、连接配置变更和普通周期复检共用 ops-worker 内的受控优先队列；首次激活优先级最高，并保留执行容量，不能通过绕过队列扩大总并发。
- 不用同一个周期候选查询处理停用、待检查、异常或冷却账户；`pending_test` 进入激活检查，`temporary_unavailable / rate_limited` 进入冷却恢复，`error` 只进入明确可自动恢复的对应后台任务，`disabled` 尊重人工停用。
- 激活检查成功只确认上游连接健康；账户从 `pending_test` 退出时仍需按当前时间计划决定进入 `active` 还是 `disabled`，不能因健康成功绕过时间计划。
- 不把健康检测作为新的 `accounts.status` 枚举；物理状态仍只使用现有 `active / pending_test / disabled / error / rate_limited / temporary_unavailable`。
- 不为旧数据库结构写运行时兼容迁移；上线或本地数据同步由用户按当前 schema 离线处理。

## 3. 数据字段

账户检查配置：

| 字段 | 默认值 | 含义 |
| --- | --- | --- |
| `health_check_model` | 必填 | 账户固定检查模型，必须属于最终 `supportedModels`，且能按账户协议档案发起最小文本检查请求。所有系统检查只读该字段。 |

`accounts` 健康事实字段：

| 字段 | 默认值 | 含义 |
| --- | --- | --- |
| `last_health_check_at` | `NULL` | 最近一次后台健康检测完成时间。手动测试不写该字段。 |
| `next_health_check_at` | `NULL` | 下次后台健康检测计划时间。为空时由候选查询按创建 / 更新时间补计划。 |
| `last_health_success_at` | `NULL` | 最近一次后台健康检测成功时间。真实网关成功请求也可刷新这个字段，表示近期已有成功信号。 |
| `health_check_failure_count` | `0` | 后台健康检测连续、独立 `transport_incomplete` 次数；`complete_success` 后清零，中性 / unknown 不增加。 |
| `health_check_failure_started_at` | `NULL` | 当前连续独立 `transport_incomplete` 窗口的首次失败时间；成功、重新检查、异常恢复或关键连接配置重置时清空。 |
| `last_health_check_status_code` | `NULL` | 最近一次后台健康检测收到的 HTTP 状态码，仅用于诊断，不授权状态变化。 |
| `last_health_check_error_code` | `NULL` | 最近一次后台健康检测错误码，仅用于有界诊断。 |
| `last_health_check_error_message` | `NULL` | 最近一次后台健康检测摘要，不作为自动状态语义来源。 |

字段定位：

- `last_health_success_at` 是健康事实，不是用量统计口径。
- `health_check_model` 是账户配置，不是最近成功模型，也不由人工测试结果回写。
- `last_used_at` 仍表示真实业务流量最近使用时间，不被后台探测更新。
- `cooldown_retest_*` 仍只表示临时不可调用 / 限流账户的恢复复测，不和正常账户健康检测混用。
- `account_quality` 仍表示近期真实流量质量，不能替代长期空闲账户探活。

## 4. 调度策略

默认设置：

- 基础间隔：1 小时。
- 抖动窗口：0 到 10 分钟，按账户 ID 稳定计算；同一账户跨轮次和进程重启保持固定偏移，避免整点集中探测。
- 单轮批量：默认 20 个，受系统设置上限保护。
- 健康检查队列固定并发 3；候选批量只限制一次读取量，不得据此扩大诊断并发。首次激活和连接配置变更属于高优先级，并保留其中 2 个入口位。
- `scheduled` 和 `request_failure` 属于例行健康检查，在获取全局完整诊断槽前必须先经过并发 1 的例行 lane；因此慢速例行任务最多占用 1 个全局诊断槽，激活和配置检查仍可进入其余容量。
- 同一账户等待期间重复投递时更新为最新配置并提升优先级；检查已经运行时，当前检查完成后只追加一次最新任务，避免并发重复探测和丢失配置变更。
- worker 角色：`ops-worker`。
- 调度频率：沿用账号探测类后台任务的短周期 tick，每次只捞取到期窗口。

候选条件：

- `status = active`。
- `schedulable = 1`。
- 未删除。
- 未过期。
- 当前不在冷却期。
- 可用时段允许。
- `next_health_check_at <= now`，或者 `next_health_check_at IS NULL` 且缺少近期成功健康信号。
- `last_health_success_at` 在最近 1 小时内存在时，跳过主动探测，并把下次检测时间顺延；`last_used_at` 只表示近期使用过，不作为成功判断。

排序：

- `next_health_check_at ASC NULLS FIRST`。
- `last_health_check_at ASC`。
- `created_at ASC`。
- `id ASC`。

后台不得一次性拉取全部账号再过滤；必须在 SQL 中按状态、时间和 limit 取候选。

## 5. 探测行为

健康检测复用共享系统探针执行器：

- 通过 `findAccountForTest` 读取账户。
- 严格使用账户保存的 `healthCheckModel`；缺失、不可见、不属于 `supportedModels` 或无法按协议完成对应探针时，记录“检查模型配置异常”并停止本轮，不回退个人默认、管理员默认、协议档案默认或支持模型首项。
- 使用 `executeAccountProbe()` 执行真实网关链路诊断，底层执行器只返回诊断结果。
- 使用账户绑定代理。
- OAuth 账户按网关准备逻辑刷新 token。
- API Key 账户复用账户测试链路。普通生成模型按账号 `credentials.supported_endpoint_modes` 中可用于连接测试的 endpoint mode 选择；不会从最近真实请求或客户端兼容口径反推 endpoint。OpenAI v1 纯图像模型固定向所选账户上游发送 `GET /v1/models`，只有标准模型列表精确包含检查模型才成功；不得调用 `/v1/responses`，也不得由周期任务执行付费生图。
- 多 API Key 账户按固定 Key 串行探测，跳过已停用 Key，并在首个成功后结束。每个账户的整轮健康检查共享固定 `30s` deadline；模型目录和生成诊断都继承同一取消信号，deadline 到达时立即中止在途请求，且不再开始后续 Key。
- 若 deadline 前未完成整个 Key 池，结果归为 `probe_task_failure/unknown`：不增加健康失败次数、不把账户标记为临时不可调用，只安排下一次复检。进程内游标至少保留两小时，覆盖待激活账户的一小时复检间隔；它记录最后尝试的 Key，下一轮从其后一把继续。worker 重启或游标过期时按账户 ID 的稳定哈希选择起点，避免长期只扫描池首。
- 流量来源固定标记为 `account_health_check`，不伪装成真实网关流量、人工测试或 `cooldown_retest`，不计入常规质量统计。
- 候选入队时携带账户 `config_revision`；执行前和结果落库时再次校验。配置在探测期间变化时，旧探测结果作废，由新配置的下一轮任务重新确认。

结果处理统一使用：`complete_success`、`framing_complete_neutral`、仅代表 `transport_incomplete` 的 `upstream_failure`，以及 `probe_task_failure/stale/unknown`。结果名称描述传输事实；固定模型、固定协议的账户可用性检查还会把 `framing_complete_neutral` 作为通用可用性失败，不能把它误当成传输电路失败。

- 成功：
  - `last_health_check_at = now`。
  - `last_health_success_at = now`。
  - `next_health_check_at = now + 1h + jitter`。
  - `health_check_failure_count = 0`。
  - 清空首次失败时间和最近健康检测错误字段。
- `transport_incomplete` 或账户可用性检查中的 `framing_complete_neutral`：
  - `last_health_check_at = now`。
  - `health_check_failure_count += 1`。
  - 写入最近状态码、错误码和失败摘要。
  - `pending_test` 首次独立可用性失败时原子写入 `health_check_failure_started_at`，后续独立、同来源失败保留最早值；未满 24 小时固定写 `next_health_check_at = now + 1h`，满 24 小时后的再次独立失败才由同一条状态 CAS 更新为 `error`、`schedulable = 0`、清空下次检查时间，并写入 `account_activation_check_timeout` 和明确错误摘要。
  - 普通 `active` 周期检查仍使用短退避并按配置阈值抗抖；真实请求失败触发的独立二次确认使用阈值 1，确认失败后立即进入通用临时不可调用 / 冷却恢复链路。
  - 只复用现有 transport 冷却 / 事前确认策略；不得从状态码、错误码、错误类型或正文推断账号级业务故障。
  - 只有本地目录 / 能力可以验证的检查模型缺失、检查模型不属于支持模型、没有可执行 endpoint mode 或最小请求模板构造错误才记录配置异常并走 `probe_task_failure/unknown`。上游 status/body 声称的 `model_not_found`、未授权或 `unsupported_endpoint` 不派生具体语义；framing 完整时仍是 `framing_complete_neutral`，但受控账户可用性检查可以把“协议未成功”作为通用失败。
  - PostgreSQL transport 失败计数必须在行锁事务内读取和递增，并校验探测开始时间之后没有更新的真实协议成功信号，禁止“先读后覆盖”造成丢失更新。
- `framing_complete_neutral`：对 transport 电路、账号冷却恢复和 Key 恢复保持中性并最多关闭同来源 transport 怀疑；对激活、周期健康、请求失败二次确认和质量确认这类账户可用性检查则累计对应健康失败事实。
- `probe_task_failure` / `stale` / `unknown`：不增加失败计数、不改变状态，只记录任务诊断并有界重排。

PostgreSQL 各类结果写回的可选 CAS 条件只在参数存在时动态追加；禁止使用无类型上下文的 `$n IS NULL` 守卫。周期候选优先处理 `pending_test`；`pending_test` 且从未完成后台检查时忽略遗留的未来复检时间和普通成功信号，人工诊断或真实流量成功不能替代后台激活检查，即时投递失效时新账户仍能被分钟级任务尽快兜底。

普通 `active` 周期账户可用性失败策略：

- 第 1 次失败：只记录健康失败，短间隔复检。
- 第 2 次独立失败：继续短间隔复检，并在前端提示“后台检测失败”。
- 第 3 次独立失败：账户仍为正常可调度时，进入现有通用临时不可调用 / 冷却复测链路。
- 真实请求失败已经提供第一重业务证据，因此其专用独立二次确认不复用上述三次阈值；确认失败即临时退出调度。

## 6. 与真实流量的关系

真实网关请求成功是最可靠的健康信号：

- 成功请求可以刷新 `last_health_success_at`，并把 `next_health_check_at` 顺延到 `successAt + 1h + jitter`。
- SQLite 与 PostgreSQL 必须使用同一套系统间隔、稳定账户 jitter 和半窗口写入节流语义；PostgreSQL 使用记录批量写入的业务副作用不能只更新成功时间而漏写下一次复核计划。
- 成功请求刷新健康信号按检测窗口节流；离下次检测还很远时不反复写 `accounts`，快到期、计划缺失、设置缩短或存在健康失败状态时再顺延。
- 普通网关失败仍由现有请求级错误处理和 transport 运行态负责，不直接写健康检测失败次数；完整 HTTP/协议结果不写共享业务状态。
- 失败请求不会刷新健康成功信号，也不会因为更新 `last_used_at` 而跳过后台健康检测。
- 真实成功和后台失败并发时按账户行串行化；如果真实成功时间晚于本次探测开始时间，本次失败结果丢弃，不得重新写回失败计数。

这样可以减少后台探测量：活跃账户由真实流量自然证明可用，长期空闲但显示正常的账户才需要探测。

## 7. 前端展示

当前账户状态卡片只消费统一 `availabilityPresentation`：状态、最近检查、下次实际检查、原因和最近检查 `traceId`。健康检查、冷却复测、来源账户探针、Key 复测和运行态探针都映射为同一组 observation/schedule 字段，不能把历史健康成功、旧计划或内部任务时间拼到当前状态上。数据库状态、进程缓存、失败计数、来源统计、探针轮次和质量算法说明不属于用户卡片。

账号列表状态 tooltip 按“当前状态 + 最近检查事实 + 下一步检查计划”展示：

- 最近一次实际检查时间与结果。
- 仍有真实任务时显示下次检查；正在执行显示“正在检查”，任务不存在显示“暂无计划”。
- 当前原因和最近一次失败的状态码、错误码、摘要与 `traceId`。
- 仅在用户显式策略存在时显示策略释放边界。

展示原则：

- 不新增醒目的硬状态标签覆盖 `active`，避免和近期质量、冷却、授权实例状态混淆。
- `pending_test` 在尚未完成首次检查时显示“待检查”；已有后台检查失败事实时派生显示红色“检查失败”，未满 24 小时时固定每 1 小时复检。
- 待检查失败时显示“重新检查”；该操作先原子清空本轮失败窗口，再立即投递后台激活检查。`error` 的“异常恢复”同样只进入干净的 `pending_test` 并立即检查，不能直接写为 `active`。
- 后台复测节奏和终止条件属于运维日志与详情排障信息，不在列表状态 tooltip 展示。
- 手动“测试”默认只展示诊断结果；成功或失败都不写健康事实、不恢复账户状态，也不改变下次后台检测计划。唯一例外是已保存自有账户的列表任务精确匹配保存的检查模型和请求形态、协议成功且持久不可调度时：它清理已有不可用运行态并恢复调度，不写新的健康检查成功事实；草稿、授权实例、停用、质量隔离或任一配置不匹配时均无状态副作用。

## 8. 设置与默认值

建议新增系统设置白名单：

| 设置项 | 默认值 | 范围 | 说明 |
| --- | --- | --- | --- |
| `accountHealthCheckIntervalHours` | `1` | `1..168` | 正常账户健康检测基础间隔。 |
| `accountHealthCheckJitterMinutes` | `10` | `0..1440` | 下次检测按账户 ID 计算的稳定错峰窗口。 |
| `accountHealthCheckBatchSize` | `20` | `1..100` | 单轮到期账户候选批量。 |
| `accountHealthCheckFailureThreshold` | `3` | `1..10` | 连续失败达到该值后允许进入临时不可调用处理。 |

如暂不增加设置页面，后端可先使用默认值和 settings helper 读取，缺省时回落到上述值。

## 9. 验证项

- 新库 schema 能创建健康检测字段。
- 到期候选 SQL 按八种 JSON / Streaming 生成 `healthCheckEndpointMode` 返回待检查，或正常、可调度、未过期、未冷却且到期的账户；覆盖 OpenAI Chat / Responses、Anthropic Messages 和 Gemini GenerateContent，工具类接口不进入候选。
- 候选查询不存在 `health_check_enabled` 条件，账户接口和页面不存在周期检查关闭开关。
- 最近 1 小时已有真实成功信号的账户会顺延计划，不被探测。
- 所有系统检查严格使用账户 `healthCheckModel`，非法时不回退其他模型。
- 探测成功会清空失败计数、首次失败时间并写入下次计划。
- `pending_test` 的独立探针只要未通过协议可用性校验就增加失败计数、保留首次失败时间并精确安排 1 小时后复检，首次失败满 24 小时后的再次独立失败才会原子转为 `error`；任务故障、stale 和 unknown 不推进窗口。
- 配置版本变化或更新的真实成功信号会使旧探测结果失效。
- 连续独立账户可用性失败达到阈值后，账户进入通用临时不可调用 / 冷却复测链路；transport 电路仍只接受真实传输失败。
- 冷却复测候选按 `healthCheckEndpointMode` 的八种生成请求形态筛选，覆盖 OpenAI Chat / Responses、Anthropic Messages 和 Gemini GenerateContent 的 JSON / Streaming；模型列表、计数 Token 等非生成工具接口不进入候选。
- “重新检查”和“异常恢复”都只重置到不可调度的 `pending_test` 并立即投递后台检查；自有账户的 `pending_test`、`error` 等所有非停用状态均可人工停用。
- 除精确匹配保存检查模型和请求形态的已保存自有不可调度账户可在协议成功后恢复调度外，人工测试成功或失败后账户、授权实例、Key、健康事实和运行态均不变化；模型或请求形态不匹配必须保持原状态。
- 前端账户列表能展示健康检测时间和失败原因。
- `pnpm --filter juhe-ai-backend typecheck` 和 `pnpm --filter juhe-ai-frontend typecheck` 通过。
