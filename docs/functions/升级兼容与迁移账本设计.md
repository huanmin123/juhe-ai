## 1. 问题与证据

项目已从「单一维护者自行部署」转为开源项目，升级动作将由不特定使用者执行。[功能开发指导](../architecture/功能开发指导.md) §5.1 规定「不做向下兼容」，其真实含义是**运行时代码不得保留旧结构载体**（禁止双列读、回落、迁移期开关）——这条正确且应保留。但它目前被延伸成了「升级过程由文档清单驱动」，这对第三方使用者不成立。

七个可核对的事实：

1. **没有发布版本**。`git tag` 为空；`juhe-ai-maintenance --version` 输出的是契约代际 `contract=go-projects-v1`（`backend-go/shared/contracts/project.go:5`），不是发布版本。用户无法表达「我在哪个版本」，项目无法承诺「支持从哪个版本升级」。
2. **没有迁移账本**。`backend-go/projects/maintenance/cmd/juhe-ai-maintenance/main.go` 注册了 14 个一次性迁移/清理命令（原 15 个；`--migrate-provider-connection-model` 已于 2026-10-30 退役）；完成状态只有两处散落的 `global_settings` key（`account_capability_domain_migration`、`scheduling_preferences_migration`），其余条目靠人记忆。
3. **升级流程按日期组织**。`docs/deploy/部署指南.md` §4 是自 2026-10-02 起的变更流水账；跨 5 个版本升级等于读 5 段日期条目并自行求并集、排顺序。
4. **漏跑不报错**。`--apply-j3b-model-check-postgres` 未执行时，首个 `schedule_now` run 插入被三值 CHECK 拒绝，用户侧表现为「已发起」后静默无记录（`docker/single-server/README.md:144`）。同类「漏跑无感知」是系统性风险：现有启动期门禁各管一段（盘点见 §11.2）：两类迁移记录门禁只覆盖各自的迁移，结构/就绪门禁只看形状——**各自覆盖面之外的迁移漏跑（如 j3b 表 CHECK、base_url 数据回填）无任何感知**。
5. **回滚口径冲突**。「回滚 = 上传上一版 `build/` 重新 build+up」这句话同时存在于 `docs/deploy/部署指南.md:53` 与 `docker/single-server/README.md`「更新发布」节的手动流程段；而同文件 `README.md:195/:207` 又写了正确顺序「先回代码、再回 schema，备份是唯一回滚载体」——README 内部即自相矛盾。2026-10-23 起的收列批之后，按冲突句操作的旧二进制读写已删列必然报错。
6. **配置面无诊断**。`JUHE_AI_*` 变量共 214 个（gateway 123 / jobs 102 / maintenance 16，按去重变量名口径、排除测试文件）。删除或改名的变量会被 `os.Getenv` 静默忽略；旧名别名机制只有 `JUHE_AI_USAGE_SPOOL_DIR` 一个特例（`backend-go/projects/gateway/cmd/juhe-ai-gateway/runtime.go:533`），且没有弃用提示。
7. **门禁是点状的**。现有门禁只覆盖两类迁移记录与两处结构就绪；其余迁移未完成时进程照常启动，把问题推迟到运行期或用户发现数据不对。

## 2. 目标与非目标

### 2.1 目标

1. **任意已发布版本 → 最新版本，一条命令**：`juhe-ai-maintenance upgrade --dsn ... --backup-confirmed --stop-write-confirmed`。跨 1 个版本与跨 6 个版本是同一操作。
2. **可预演、可重入、失败即停**：`--dry-run` 只读输出计划；任一步骤失败立即停止且不推进后续步骤；中断后重跑同一条命令即续跑。
3. **版本可识别**：二进制、镜像、健康响应、日志都带同一个版本号；进程能判断「库比二进制旧 / 比二进制新」并给出可执行提示。
4. **配置变更可诊断**：未知变量、废弃别名、缺失必填项在启动期和独立检查命令下都有明确输出。
5. **承诺由测试背书**：最近 3 个发布版本 → HEAD 的升级路径真实执行（先以本地脚本形态交付，CI 化见 §20.6），而不是文档承诺。

### 2.2 非目标

1. **不引入运行时兼容层**。不双读旧列、不做 fallback、不加迁移期开关（维持 §5.1）。
2. **不做在线迁移**。单机自托管接受停写窗口；实际时长随 pending 步骤数而定，`--dry-run` 给出步骤数与超时上界估算（§9.3），不承诺固定「分钟级」。
3. **不引入 goose / golang-migrate 等迁移框架**。现有 `--ensure-schema` 全量幂等 DDL 具备「自愈收敛」能力，框架的版本化 DDL 会与之形成双轨。账本只记录一次性数据步骤，不接管结构定义。
4. **不支持数据库降级**。回滚 = 恢复备份（§14）；不提供 down migration。
5. **不做自动升级**。升级只由用户显式执行 `upgrade` 命令触发（`deploy.sh upgrade` 是同一命令的脚本封装，同样用户手动调用）；拉取代码、重建镜像、`docker compose up`、进程重启均**不得**触发任何结构收敛、数据迁移或 seed。启动门禁（§11）只做只读检查——库未升级时 fail-fast 并给出命令，由用户自行决定何时执行；对比 Grafana 式「启动即自动迁移」是刻意相反的选择（自动迁移会把破坏性 DDL 藏进用户无感知的启动路径，绕过停写与备份确认）。

## 3. 术语

| 术语 | 定义 |
| --- | --- |
| 结构收敛 | `--ensure-schema` 重放全量当前 DDL，把任意形状的旧库补到当前形状；每句自带幂等守卫 |
| 迁移步骤（step） | 一次性的数据/约束变更，有唯一递增 `revision`，有序执行 |
| 账本（ledger） | 记录「哪些 step 已在哪个库上应用」的持久化表 |
| 破坏性动作 | 删除列/表，或覆盖既有数据；执行后旧二进制可能无法运行，回滚只能靠备份（来源可以是破坏相 DDL，也可以是步骤自身的破坏性动作） |
| 停写窗口 | gateway 与 jobs 均停止、无写者的时段 |

## 5. 总体设计

```
构建期：版本号 + SchemaRevision 常量（§6）
   │
运行期：maintenance upgrade
   ├── 1-6. 前置：解析/连接/锁/读账本/方向校验/算计划
   ├── 7. --dry-run 输出计划并退出（只读）
   ├── 8. 确认门禁（缺 secret 同步拦截）；9. 已最新则短路为只读核验
   ├── 10. ensure-schema 加法相（建表/补列/补种）
   ├── 11. seed（幂等补种内置行，需 secret）
   ├── 12. 逐 step：Satisfied? → adopt : (running → apply → verify → applied)
   ├── 13. ensure-schema 破坏相（删列/删表）
   ├── 14. postflight：分相语句计数 + 各 step Verify + 模块级 verify
   └── 15. 写 schema_state，输出 JSON 报告（存在性口径见 §9.3：第 1 步用法错误无 JSON；连接不可达无报告、stderr 摘要）
   │
启动期：gateway / jobs 读 schema_state 与账本，与自身 SchemaRevision 比对，不符 fail-fast
```

两条不可交换的顺序：**加法结构 → seed → 数据步骤 → 破坏结构**。理由见 §7.3。

## 6. 版本标识

### 6.1 发布版本

- **v2 口径（2026-10-30，用户裁决「不可能记得打 tag」）**：版本号 = **CalVer 日历 tag `vYYYY.MM.DD`（同日多发布追加 `-2/-3`）**，由 `deploy.sh` 在**干净树的生产部署**时自动打（发布即版本，维护者零记忆负担；`JUHE_AI_DISABLE_AUTO_TAG=1` 可关闭；不 push 仅本地留存）。无 tag 构建自动降级 `dev-<sha>`（提交级唯一可追溯），脏树恒为 `dev-<sha>-dirty` 永不打 tag（§9.6 自改口径）。镜像 tag 对应关系见 §6.5。
- 终端用户**不需要关注版本号**：升级时机由启动门禁告知（拉代码启动即提示），版本号仅用于日志辨识与支持排查。
- 节律锚点：本设计各处原稿的「MINOR」表述读作「**发布批次**」（一次干净树生产部署 = 一个批次）；破坏性变更（DROP）延后「一个批次」执行的裁决（§20.2 选 A）不变，`Breaking` 事实以 `CHANGELOG` 的 Breaking 节声明为准。
- 兼容承诺写入 `CHANGELOG.md`（新建）：一个发布批次内**用户可见结构**（列/表/API 契约）只增不删；存储收敛的破坏性 DDL（退役列 DROP，§13 规则 2）不算违约，但必须在当版 `Upgrade notes` 如实披露——「删」的两种口径以本句为准。

### 6.4 SchemaRevision

`backend-go/shared/contracts` 新增：

```go
// SchemaRevision 是本二进制认识的最高结构/步骤版本号，与迁移步骤的 revision
// 共用同一个递增序号空间：一次交付新增或修改了步骤 / DDL 语句清单，即取本次
// 分配的最高 revision 作为新的 SchemaRevision。首个实施交付注册 12 个步骤
// （revision 1..12），故 SchemaRevision 初值为 12。
const SchemaRevision int64 = 12
```

规则：

- 递增触发条件是「DDL 语句清单**或**步骤注册表的任何变化」（新增、删除、修改既有语句文本均算）；纯代码不变更不递增。
- `revision` 全局单调：新步骤取 `max(已注册 revision)+1`；已发布步骤的实现语义变化时不改原步骤，注册更高 revision 的补偿步骤（检测机制见 §7.4 ImplVersion）；**纯 DDL 变更（无新步骤）同样占用一个新 revision 空号**（不入账本），`SchemaRevision` 取该值。
- golden 测试（§7.4）同时钉住「DDL 语句清单 digest」与「(revision, step_id, implVersion) 有序对」，两类变化都会被拦下。

- 版本**可核验性**以二进制 `--version` 与 `/health` 为准，镜像 tag 是发布物标注而非唯一凭证。

## 7. 迁移账本

### 7.1 表结构

账本 DDL 放在**独立文件** `maintenance/internal/schema/upgrade_ledger.go`（自研 DDL，不进 Node 生成清单），由 `EnsurePostgres` 在六个 schema 组之后追加执行 `ensureUpgradeLedger`：

```sql
CREATE TABLE IF NOT EXISTS juhe_business.schema_state (
  id              smallint PRIMARY KEY DEFAULT 1 CHECK (id = 1),
  schema_revision bigint NOT NULL,
  schema_digest   text   NOT NULL,
  app_version     text   NOT NULL,
  converged_at    text   NOT NULL
);

CREATE TABLE IF NOT EXISTS juhe_business.schema_migrations (
  revision     bigint PRIMARY KEY,
  step_id      text     NOT NULL UNIQUE,
  title        text     NOT NULL,
  target       text     NOT NULL CHECK (target IN ('primary','j3a','j3b','account_balance')),
  destructive  boolean  NOT NULL DEFAULT false,
  status       text     NOT NULL CHECK (status IN ('running','applied')),
  checksum     text     NOT NULL,
  impl_version integer  NOT NULL DEFAULT 1,
  adopted      boolean  NOT NULL DEFAULT false,
  started_at   text,
  applied_at   text,
  duration_ms  integer,
  app_version  text,
  detail_json  text
);
```

放置与选型理由：

- **不进 `pg_schema_business_tables.go`**：该文件头声明「从 Node 源逐字移植、不得手改 SQL 常量」，golden（693 语句/per-schema 计数）钉死 Node 输出——账本表进去会破坏 623/624 事故的核对基准。独立文件 + 专属 golden（钉账本 DDL 文本）两不误。
- 单机部署是**单库 `juhe_ai` + 8 个 schema**（`docker/single-server/compose.yml:6`），主 `--dsn` 可达全部业务 schema；账本放 `juhe_business` 不需要额外连接。
- 时间列用 `text`（ISO-8601 UTC 毫秒），跟随 `juhe_business` 主流时间列惯例（业务表 `*_at` 均为 text；timestamptz 仅 jobs 运行态表有先例），保证同一套运维读面口径一致。
- 不用 `global_settings`：需要 `revision` 主键、`status` 状态机和 append-only 校验，key-value 无法表达。

### 7.2 状态机

```
（无行） --apply--> running --verify 通过--> applied
                      │
                      └── 失败/进程中断：保持 running，detail_json 覆盖写最近一次错误
```

- 重跑时遇到 `running` 行：直接重跑该 step（步骤契约要求幂等，§8.4）。
- `detail_json` 每次**覆盖写**（保留最近一次失败），成功后清空；历史诊断靠 `--report-out` 落盘，不进账本。
- 不存在 `failed` 终态——失败永远是「可重试的中间态」，避免需要人工改状态。
- `impl_version`（§7.4）高于账本行的步骤视为待求值：先跑 `Satisfied`，满足则 adopt 并更新 impl_version，不满足则重跑 Apply。

### 7.3 结构收敛的分相执行

`EnsurePostgres` 增加过滤模式，按语句分类拆两相：

```
EnsureAdditive    // DROP TABLE / DROP COLUMN 以外的全部语句
EnsureDestructive // 仅 DROP TABLE / DROP COLUMN
EnsureAll         // 现有行为：加法相 + 破坏相，单次执行（--ensure-schema CLI 保持）
```

`upgrade` 使用 `Additive → steps → Destructive`，`--ensure-schema` 保持 `All`。

好处有三：

1. **ensure 自身的破坏性 DDL 缩到最后**。数据步骤失败时，若破坏相未执行，旧列未删、旧二进制仍可运行，回滚可以选择「换回旧二进制」而不必恢复备份。
2. 破坏性窗口缩小到最后一步，停写时长可预期。
3. 与 expand–contract 的「读切换完成后再删」顺序同构。

**边界必须如实声明**：部分步骤自带破坏性动作（`--migrate-chat-account-only-binding` 删三列、`--apply-studio-retirement` 删表删列、`--drop-retired-monitoring-tables` 删表），它们在数据步相执行，同样会使旧二进制失效——「破坏相之前可换回旧二进制」只对「尚未执行任何破坏性动作」的窗口成立，报告的 `rollback` 字段按实际已发生的破坏性写判定（§9.3/§14）。

**分相顺序契约**：各相内部保持 Node 清单相对顺序不变；跨相重排的合法性由静态测试钉住——「破坏相语句的目标对象与加法相语句的目标对象不相交」，新增或移动破坏性语句时必须运行该测试。

分类规则（构建期计算，不手写清单）：语句文本命中 `DROP TABLE|DROP COLUMN` 判为破坏性；`CREATE OR REPLACE FUNCTION`、`DROP TRIGGER IF EXISTS + CREATE TRIGGER`、`DROP INDEX`、DO 块内的 `DROP CONSTRAINT` + 重建判为非破坏性。**2026-10-30 B09 后当前全量 DDL 破坏性语句为 2 条**（`juhe_stats` 2 条 `DROP TABLE IF EXISTS`——`authorization_team_usage_range_windows` / `authorization_user_usage_range_windows`，B09 授权范围窗口退役，由 ensure-schema 破坏相执行；B08 曾撤除原 12 条 `DROP COLUMN IF EXISTS`：`juhe_codex_context` 3 条、`juhe_business` 9 条，生产只读预检确认目标旧列均不存在，破坏相一度清零）。

### 7.4 append-only、checksum 与 ImplVersion

- `revision` 只增不改；已发布步骤的实现语义变化时，注册更高 revision 的补偿步骤，不改原步骤。
- `checksum = sha256(step_id + "|" + revision + "|" + target + "|" + title + "|" + destructive)`。用于发现「同 revision 被改名/改目标」的意外改动。
- **ImplVersion 检测实现漂移**：每个 step 声明 `ImplVersion int`（初值 1）。账本行记录 apply 时的 ImplVersion；注册表的 ImplVersion 高于账本行 → 该步骤重新求值（Satisfied 满足则 adopt 并更新，否则重跑幂等 Apply）。这与 `schedprefdomain`/`capabilitydomain` 的 ruleVersion「不符即拒绝」先例同构，堵住「checksum 钉不住函数体」的缺口。
- golden 测试（P1 交付项）固定三样：DDL 语句清单 digest（含分相归类）、`(revision, step_id, implVersion)` 有序对、账本 DDL 文本。新增或修改即测试失败，必须显式更新 golden 并在同批递增 `SchemaRevision`。

## 8. 步骤注册表

### 8.1 契约

```go
type Target string // primary | j3a | j3b | account_balance

type Step struct {
    Revision    int64
    ID          string  // 稳定标识，例 "2026-10-12-scheduling-preferences-p2"
    Title       string  // 面向使用者的中文标题
    Target      Target
    Destructive bool
    ImplVersion int     // 实现语义版本，语义变化必须递增并联动新 revision（§7.4）
    // Satisfied 独立于账本求值：只看库内事实，与 Apply 的达成判据严格同源
    // （优先复用各迁移包现有 Verify 的只读探测函数）。返回 true 表示目标状态
    // 已达成，upgrade 记账为 adopted=true，不执行 Apply。
    Satisfied func(ctx context.Context, env *Env) (bool, error)
    // Apply 必须幂等：重复执行要么零写入，要么写等值结果；中断后可从头重跑。
    Apply  func(ctx context.Context, env *Env) (Detail, error)
    // Verify 必须在 Apply 之后通过；不通过则 upgrade 停止，退出码 3。
    Verify func(ctx context.Context, env *Env) error
}
```

`revision` 是账本与启动门禁的唯一序号空间：只有**升级路径上必须有**的步骤才进入注册表并占用 revision。一次性割接/修复工具（`--import-legacy-business`、`--rebuild-usage-stats`）不是升级路径的一部分，保留为独立命令，不入账本、不参与门禁（割接/修复工具不属于升级路径）。

### 8.2 两类条目

| 分类 | 判定 | upgrade 行为 |
| --- | --- | --- |
| 升级步骤 | 进入注册表、占用 revision | `Satisfied` 满足则记账 adopt；不满足则 apply→verify |
| 独立命令 | 割接/修复工具，不进入注册表 | 不执行、不计账、不参与启动门禁；文档与帮助文本标注适用场景 |

### 8.3 目标 DSN 解析

`upgrade` 按 `target` 解析连接串：

| target | schema | 取值顺序 |
| --- | --- | --- |
| `primary` | 全部业务 schema | `--dsn` |
| `j3a` | `juhe_jobs` | `JUHE_AI_MAINTENANCE_J3A_POSTGRES_URL`，缺失回落 `--dsn` |
| `j3b` | `juhe_j3b` | `JUHE_AI_MAINTENANCE_J3B_POSTGRES_URL`，缺失回落 `--dsn` |
| `account_balance` | `juhe_jobs` | `JUHE_AI_MAINTENANCE_ACCOUNT_BALANCE_POSTGRES_URL`，缺失回落 `--dsn` |

回落是现有部署事实（三者通常同库）。解析发生在 preflight（§9.4 第 2 步）：注册表含某 target 的步骤而该 target 的连接串不可用时，`--dry-run` 与正式执行都在计划阶段 exit 2 并在 stderr 指出缺失的环境变量名——加法相之前即拦截。这正是把「漏跑 j3b 静默失败」变成显式失败的关键。

对 `j3a` / `j3b` / `account_balance` 三个目标，步骤 `Apply` 前统一执行 `CREATE SCHEMA IF NOT EXISTS <映射表中的 schema>`（已存在时 no-op，不改 owner），使全新库无需再手工 `CREATE SCHEMA AUTHORIZATION`。这一条与 §20.3 是同一决策的两面：若裁决不采纳，则本段删除，`upgrade` 在目标 schema 缺失时 exit 2 并提示手工建 schema。

### 8.4 幂等契约

每个 step 必须满足：

1. 重复执行零写入或写等值结果（现有命令多数已满足，`--apply-success-cost-backfill` 的游标、`--migrate-scheduling-preferences` 的 NULL 判定是范例）。
2. 中断后从头重跑安全；不依赖上一次运行的进程内状态。
3. 只依赖库内事实，不依赖「上一步是否刚跑过」；不允许低序步骤依赖高序步骤产物（违反即注册错误，实施评审拦截）。
4. 单步有界超时：步骤 Apply/Verify/seed 用 `--step-timeout`（钳制 1m..4h，默认 30m）；结构两相与 postflight 用独立默认上界（60m/30m），超时按失败处理——`estimate` 按两类上界分别累加。

## 9. 命令契约

### 9.1 旗标与调用形态

```
juhe-ai-maintenance upgrade [flags]

  --dsn string                 主库连接串（必填）
  --dry-run                    只读：输出计划（pending / adopt / 破坏性语句披露 / 回滚代价 / 步骤数估算）后退出
  --stop-write-confirmed       操作者确认 gateway 与 jobs 均已停止
  --backup-confirmed           操作者确认已存在可恢复备份
  --secret string              种子加密密钥（回落 JUHE_AI_SECRET；seed 与凭据类步骤必需）
  --report-out string          额外把 JSON 报告写入文件（落盘失败仅 stderr WARN，不翻转退出码——stdout 报告是权威载体）
  --step-timeout duration      步骤（Apply/Verify/seed）单步超时，钳制 1m..4h（默认 30m；结构两相与 postflight 各用独立默认上界 60m/30m）
```

**argv 解析策略**：现有 maintenance CLI 是单层 `flag.FlagSet`（Go flag 在首个非 flag 参数处停止解析，`upgrade --dsn x` 会把 `--dsn` 吞进位置参数）。`upgrade`/`check-config` 以**显式子命令分发**实现：`os.Args[1]` 命中子命令白名单即剥离后交独立 FlagSet，其余走既有单层 FlagSet——两套入口互不干扰；子命令各自的 `--dry-run` 与既有 backfill 等一次性迁移命令的同名旗标无归属冲突。

**确认门禁规则**：

- 存在待执行（Apply，非 adopt）步骤、或 `dbRevision < SchemaRevision` 时，`--stop-write-confirmed` 与 `--backup-confirmed` 均必填（缺一 exit 2）。
- 全部已最新且走短路分支（§9.4-9）时，两个确认都可不填，命令只做只读核验并 exit 0。
- `destructiveDDLStatements`（=12）是清单常量披露值，**不参与**确认判定；是否实际生效以执行结果为准。

### 9.2 退出码

| 码 | 含义 |
| --- | --- |
| 0 | 已最新（短路），或升级完成且 postflight 全通过 |
| 1 | 执行失败：连接不可达（第 2 步试连，含 primary 与全部 target）、Apply 失败、结构 DDL 失败、锁获取失败、账本写入失败 |
| 2 | 用法/旗标解析错误（无报告）、确认缺失、env 缺失、`--secret` 缺失 |
| 3 | 需要人工判断：Verify 失败、postflight 未就绪、库 revision 高于二进制、账本含超出本二进制注册表的 revision、账本/state 反向不一致、secret 与库内密文不一致（KCV，§9.4-11） |

### 9.3 报告

stdout 单行 JSON + stderr 单行摘要。**报告存在性**：第 1 步旗标解析/用法错误 → 无 JSON（字段无从产生），stderr 单行 + exit 2；第 2 步起（连接失败、锁失败、方向不符、确认缺失、执行失败、完成）→ 均输出报告，未到达的阶段字段缺席。字段存在性矩阵：

| 场景 | driver/binary | database | plan | estimate | executed | postflight | rollback | result |
| --- | --- | --- | --- | --- | --- | --- | --- |
| `--dry-run` | ✓ | ✓ | ✓ | ✓ | — | — | ✓（若继续将达到的等级） | `planned` / `blocked` |
| 前置失败（第 2-9 步：连接/锁/方向/确认/secret） | ✓（database 连接失败子场景缺位） | 方向校验后才有 | — | — | — | — | `blocked` / `failed` |
| 已最新（短路） | ✓ | ✓ | ✓（空 pending） | ✓ | — | ✓（只读核验） | — | `up-to-date` |
| 升级完成 | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | `upgraded` |
| 执行失败（第 10-14 步） | ✓ | ✓ | ✓ | ✓ | ✓（含失败行） | 到达时才有 | ✓ | `failed` |

示例（自洽口径：上次升级完成于 revision 36；本次二进制 SR=40；37/39/40 待 Apply，38 的 Satisfied 在本库为真；执行成功）：

```json
{
  "driver": "postgres",
  "binary": {"version": "v1.4.0", "commit": "1e136a9e1", "schemaRevision": 40},
  "database": {"schemaRevision": 36, "appliedSteps": 36},
  "plan": {
    "pending": [
      {"revision": 37, "stepId": "…", "title": "…", "target": "primary", "destructive": false, "status": "absent"},
      {"revision": 39, "stepId": "…", "title": "…", "target": "primary", "destructive": false, "status": "absent"},
      {"revision": 40, "stepId": "…", "title": "…", "target": "primary", "destructive": true, "status": "absent"}
    ],
    "adopt":   [{"revision": 38, "stepId": "…", "reason": "satisfied"}],
    "destructiveDDLStatements": 12
  },
  "estimate": {"applySteps": 3, "applyUpperBoundMinutes": 90, "structuralUpperBoundMinutes": 90, "totalUpperBoundMinutes": 180},
  "executed": [
    {"revision": 37, "status": "applied", "durationMs": 310},
    {"revision": 39, "status": "applied", "durationMs": 402},
    {"revision": 40, "status": "applied", "durationMs": 812}
  ],
  "postflight": {"ok": true, "checks": [{"name": "capability-domain", "ok": true}]},
  "rollback": "backup-required",
  "result": "upgraded"
}
```

`status` 取值 `absent`（无账本行）/ `running`（上次运行残留，重跑即续）。中断场景下会出现 `running` 行且低序步骤已 applied——两者按各自账本事实呈现，不组合出「39 absent 而 40 running」的矛盾形态。

`result` 与退出码映射：`upgraded`/`up-to-date`/`planned`→0，`blocked`→3，`failed`→1 或 3（与 §9.2 对应）。`rollback` 取值规则（**语句级**）：本次运行已成功执行任一破坏性动作（破坏性步骤的写、或破坏相中任一条 DROP）→ `backup-required`；否则 → `binary-only`——破坏相部分执行后失败同样取 `backup-required`。`estimate` 分列：步骤数 × `--step-timeout` 上界、结构两相 + postflight 的独立默认上界（60m/30m，不受该旗标影响）、合计——供停写窗口排期，两类上界口径不同不合并。

### 9.4 执行序列

1. 子命令分发与旗标解析。
2. 解析并**试连**全部将用到的 DSN（primary + 注册表含步骤的 target，§8.3）：env 缺失 → exit 2；连接不可达 → exit 1（环境故障与配置缺失分流，两类都不再重试）。
3. 取 advisory lock（§9.5）；拿不到即 exit 1。
4. 读 `schema_state` 与 `schema_migrations`（表或行缺失按 revision 0 处理）。
5. 方向校验：`dbRevision > SchemaRevision` → 报告 `result=blocked`、exit 3（`--dry-run` 同样执行本校验，用于自查「落后/超前多少」）。
6. 计算计划（**只读求值，不写账本**）：pending（含 running 行的呈现，§9.3）、adopt（Satisfied 求值结果）、estimate；重算结构 digest 与 `schema_state.schema_digest` 比对，不一致 → WARN「上次升级后库结构被外部改动（自改或手工 DDL），升级将按当前形态收敛，请确认改动是否需保留」（§9.6）。
7. `--dry-run` → 输出报告并退出（0；方向不符时 3）。全程不写任何表，在显式 `READ ONLY` 事务内执行求值（§18-7 的断言依据）。
8. 确认门禁检查（§9.1）；secret 三态在此一并处理（均先于任何写入）：缺失且存在待执行步骤 → exit 2；存量库取任一现有密文（如 system account 凭据）试解密作 KCV，失败 → exit 3「secret 与库内密文不一致」；存量库无可试解密载体（无密文行）→ 与 fresh 同口径跳过 KCV，报告披露 `secretVerified: false`（错误 secret 在该形态下无法前置发现，由 §20.5 备份保障兜底）。
9. **已最新短路**：无待执行步骤、`dbRevision == SchemaRevision` 且 `stepMax <= dbRevision` → 只读一致性核验（账本/state 一致 + `CheckBusinessPostgresSchema`）→ `result=up-to-date`、exit 0。跳过第 10-14 步。
10. 执行 `EnsureAdditive`。
11. 执行 seed（`SeedPostgresDefaults` 幂等补种内置题库/模型目录/默认资源），使用第 8 步已校验的 secret（AES-256-GCM 无密钥校验值，正确性校验前置到第 8 步——KCV 为只读操作，前移不产生写入）。
12. 按 revision 升序遍历：Satisfied 为真的步骤**在此写入** `adopted` 行（写入前重跑一次 Satisfied 确认仍真）；其余写 `running` → `Apply` → `Verify` → 记 `applied`。Apply 失败：`detail_json` 覆盖写、exit 1，不执行后续步骤与破坏相；Verify 失败：同记录、exit 3，同样停。
13. 执行 `EnsureDestructive`。
14. postflight：两相语句计数 vs 内置分相期望（执行侧完整性，防语句清单版本错配）、全部步骤 `Verify` 重跑、三个模块级 verify（capability domain、scheduling preferences、upstream base URL）、`CheckBusinessPostgresSchema`（仅覆盖 `juhe_business`；chat/j3b 由各 step Verify 与 bootstrap 自检承担）。
15. 写 `schema_state`（revision=SchemaRevision、digest、app version、时间），输出报告，exit 0。

### 9.5 并发

- `shared/platform/advisorylock` 新增升级编排键 `UpgradeOrchestration`（新值，避开既有 `AccountListDirty=7001001` 与 J3a/J3b 的 `…015/…016`；键值一经发布不可变更）。`upgrade` 全程持会话级锁，取锁有界等待（对齐 `ListDirtyLockWaitTimeout` 的 2s 快失败口径）。
- `--ensure-schema` 与 `--seed` 接入**同一把锁**——这是对既有命令的行为改造（当前它们不取任何 advisory lock），纳入 P1 交付与测试；未接入前 `upgrade` 报告提示并发风险。
- 操作纪律：upgrade 运行期间禁止并行执行任何旧 flag 迁移命令（锁不覆盖它们）；该纪律写入升级指南与报告提示。强制互斥需改造 14 个旧命令，随实施另行评估。

### 9.6 用户自改（fork / 手工 DDL）的检测边界

开源用户可能自改代码或手工改库。检查分三类，原则是「发现并兜住意外，不拦有意扩展」：

- **改坏官方结构（删列/改类型）**：加法相幂等 DDL 自动补回（自愈收敛）；收敛不掉的由启动形状契约与 step Verify fail-fast，不静默。
- **迁移前提被改坏**：各 step 的 Satisfied/preflight/Verify 只看库内事实，坏前提 → 失败清单非空零写入 exit 3，报告列明坏数据。
- **外部改动检测（WARN，不阻断）**：preflight 重算 digest 与 `schema_state.schema_digest` 比对（§9.4-6）；digest 只能告警——无法区分有意私有扩展与漂移，不做硬拦截。
- **刻意不检**：用户私加的表/列/索引原样保留（前向兼容面）。已知边界：私加对象与未来官方对象同名时，`ADD COLUMN IF NOT EXISTS` 会接管同名列，类型不符在运行期才暴露——升级指南要求自改用户的私加对象使用自有前缀。
- **代码自改**：无法检测也不检测；账本与 `schema_state.app_version` 记 `dev-<sha>` 留痕（§6.2），版本来源靠 `--version`/`/health` 辨识。

## 11. 启动门禁

### 11.1 契约

gateway 与 jobs 启动时执行一次只读检查，按固定顺序求值：

```
dbRevision = schema_state.schema_revision        // 缺失视为 0
stepMax    = max(schema_migrations.revision)      // 缺失视为 0
```

| 顺序 | 条件 | 行为 |
| --- | --- | --- |
| 1 | `stepMax > dbRevision` | fail-fast：升级中断在途——「上次升级未完成，请使用 schemaRevision ≥ stepMax 的版本重跑 upgrade」（账本已写入而 state 未推进） |
| 2 | `dbRevision > SchemaRevision` | fail-fast：「二进制版本低于数据库结构，请升级二进制」（完成态的库领先于本二进制） |
| 3 | `dbRevision < SchemaRevision` | fail-fast：引导 `juhe-ai-maintenance upgrade --dry-run` 预演（门禁只读库、拿不到步骤注册表，无法枚举未入账本的等待步骤，等待清单以 dry-run 计划为准）；若 `stepMax == 0` 且 `dbRevision > 0`（纯 DDL 空号 + 结构相/破坏相中断形态），文案改为「结构未收敛完成，请直接重跑 `upgrade` 续跑」 |
| 4 | `dbRevision > 0` 且 `stepMax == 0` | fail-fast：账本缺失或被清空（state 与账本反向不一致）——恢复备份，或重跑 `upgrade` 重建账本并重新求值全部步骤。**按账本行数判定**（`max(revision)`，表存在但被 TRUNCATE 清空同样命中）；顺序 3 先于顺序 4，故本行只承接「state 声称已完成但账本为空」的完成态不一致 |
| 5 | 其余（`dbRevision == SchemaRevision` 且 `stepMax <= dbRevision`） | 通过 |

场景代数验证：fresh 未升级 0/0/12 → 顺序 3；正常完成 12/12/12 → 顺序 5；升级中断（state=36、账本至 40、SR=40）→ 顺序 1；中断后换旧二进制（SR=36 看 stepMax=40）→ 顺序 1；完成态库领先（state=50、stepMax=50、SR=40）→ 顺序 2；手工 DROP 账本（state=12、stepMax=0）→ 顺序 4。

`schema_state` 只在 `upgrade` 完整跑完 postflight 后写入（§9.4-15），`--ensure-schema` 不写。「账本有步骤但 state 未更新」必然落在顺序 1 或 2，被识别为中断的升级，而不是误判为已完成。（2026-10-30 二轮复审修正：行 4 原实现按「账本表是否存在」判定，TRUNCATE 清空可绕过，已改按行数判定并与本表对齐；行 3 的空号分支同步实现。）

### 11.2 与既有门禁的关系

现有启动期检查共四族，全部保留：capability domain 与 scheduling preferences 的迁移记录/形状门禁（gateway/jobs 各一份镜像）、J3b 运行态索引就绪门禁（`CheckReady`，Redis 索引缺失时 `/v1` fail-closed）、codex_context schema 启动探针。它们校验的是**形状 + 记录 + 就绪**，比 revision 更具体，但各管一段、合起来仍不覆盖「注册表之外的迁移漏跑」；revision 门禁只回答「库是否被这一版 CLI 收敛过」，两者互补不重复。

### 11.3 发布与全新安装序列

**存量库升级（本设计首版发布起，每次含结构变更的发布都走同一序列）**：

```
停写（stop gateway/jobs）→ 备份 → maintenance upgrade → 启动新版 gateway/jobs
```

**全新安装**：

```
--ensure-schema --seed → upgrade --stop-write-confirmed --backup-confirmed
  （seed 已封存的步骤 adopt；backfill 等无数据可回填的步骤会执行空跑，秒级零写入。
   fresh 库两确认的实际含义：确认无写者、确认空库无需备份；门禁不设 fresh 豁免口）
→ docker compose run --rm gateway -init-account-circuit-runtime-index
  （J3b 运行态索引，新库必需，gateway 启动前置）
→ 启动
```

**deploy.sh 承载**：`deploy.sh` 新增 `upgrade` 模式（`compose build maintenance` → 停写 → 提示/校验备份 → `docker compose --profile tool run --rm maintenance upgrade --stop-write-confirmed --backup-confirmed --dsn "$JUHE_AI_POSTGRES_URL"`，secret 经容器 env 注入 `JUHE_AI_SECRET`）。**发布前核验不适用于 upgrade 模式**：其唯一工作场景就是库落后/升级中断，dry-run 必然 blocked/3，硬性核验会让 `./deploy.sh upgrade` 在入口处自我死锁（提示去执行的正是当前命令——2026-10-30 二轮复审实锤）；核验仅约束常规发布（all/gateway/jobs）。

**upgrade 非零退出的脚本分支（固定）**：脚本立即中止且**不执行 `up -d`**（gateway/jobs 保持停止）；stderr 输出二选一指引——「重跑同命令前向续跑（账本断点，推荐）」或「恢复升级前备份」；`set -e` 语义下人工介入后重入，停写窗口不悬挂、不自动拉起半升级库。`all` 模式在 `up -d` 之前插入同一段，且插入点的顺序固定为 **build 全部镜像 → 停写（stop gateway/jobs）→ 脚本校验备份 → upgrade（代填两确认，语义 = 脚本已完成停写与备份校验）→ `up -d`**——不得在写者存活时执行 upgrade，确认旗标由脚本代填的前提是前两步真实发生；命令一律带 `--profile tool`（maintenance 在该 profile 下，缺失即 `no such service`）；发布前核验的 `upgrade --dry-run` 必须用**新版 maintenance 镜像**（先 build maintenance 再核验，否则旧镜像看不见新 revision 步骤）。这替代现有脚本里写死的两条 verify 判断。

## 12. 配置兼容

### 12.1 声明式注册表

新增 `backend-go/shared/platform/configregistry`：

```go
type Entry struct {
    Name       string   // 主名
    Aliases    []string // 旧名，按顺序回落
    Process    []string // gateway | jobs | maintenance
    Required   bool
    Kind       string   // string|int|bool|duration|url|path|enum
    Default    string
    Range      string   // 例 "1..1000"
    Deprecated string   // 弃用起始版本
    RemovedIn  string   // 计划移除版本
    Sensitive  bool     // 日志脱敏
}
```

三项目接入方式：gateway `loadRuntimeConfig` 与 jobs `loadWorkerConfig` 是现成的注入式 `getenv` 闭包，直接替换取值来源；maintenance 现状是散点 `os.Getenv`（无装载函数），P3 先为其建立等价装载边界再接入注册表（登记为 P3 前置小项）。`strings.TrimSpace(getenv("JUHE_AI_..."))` 逐步替换为 `registry.String("JUHE_AI_...")`，读取语义与默认值保持逐字节不变（DIRECTORY/DIR 双名先例进入 `Aliases`）。

### 12.2 启动诊断

| 情况 | 行为 |
| --- | --- |
| 环境里存在 `JUHE_AI_*` 但不在注册表 | 单条 WARN，列出全部未识别变量名，输出到启动日志与 stderr（不 fail：手工 shell 里的历史变量不应阻断启动；值校验语义本阶段不变） |
| 使用了 alias 且主名未设置 | WARN：`JUHE_AI_X 已弃用，请改用 JUHE_AI_Y；将在 <RemovedIn> 移除` |
| 主名与 alias 同时设置 | 主名生效，WARN 提示 alias 被忽略 |
| 必填缺失 | 保持现有 fail-fast 文案（`runtime.go:308-314` 的三连接串是范例） |

### 12.3 `check-config` 命令

```
juhe-ai-maintenance check-config --env-file /opt/juhe-ai/.env --process all
```

只解析不连接、不启动；输出每个变量的 `name / source(default|env|alias) / valid / message`，exit 0（合法）或 2（缺失/非法）。附加模式：`check-config --list [--format markdown]` 生成 env 契约表（§12.4 文档生成的来源，exit 0）；`--process` 取值校验（`gateway|jobs|maintenance|all` 之外 exit 2）。三个子命令与默认入口各自注册同款 `--version`（§6.3）。用于升级前的「配置是否还合法」自检。

### 12.4 漂移测试

单元测试双向比对（三项目全部 `getenv` 装载函数为对象，排除测试文件）：

- 代码中出现、注册表缺失的 `JUHE_AI_*` 字面量 → 测试失败；
- 注册表条目在声明的 Process 中无任何真实读取 → 测试失败；
- 标记 `RemovedIn` 的变量被重新读取 → 测试失败；
- `docs` 中 env 契约表与 `check-config --list --format markdown` 生成物**逐行内容**（name/aliases/default/deprecated/process 等）比对，不一致 → 测试失败（只比行数会漏同行数的内容漂移；生成物随注册表变更同批提交，人工只审不改）。

### 12.5 API 面不在本文范围

- `/v1` 是 OpenAI 兼容面，其跨版本兼容由协议契约保证，不属于本文定义的「需要外部调整的输入」。
- 管理面 API 与前端产物同批发布，由现有前端 buildId 门禁保证版本一致，不做跨版本兼容，也不引入 API 版本协商。
- 因此本文不设计 HTTP API 的 deprecation/versioning 机制；若未来开放管理面 API 给第三方集成，需另立设计。

## 13. 破坏性变更的正确姿势

当前允许「新增列 + 删旧列」同批发布（2026-10-23 收列批即如此）。对单一维护者可行，对开源用户不可行，因为它同时取消了「换回旧二进制」这条回滚路径。

建议新增规则（待裁决，§20.2）：

1. **新增或切换读写字段的版本不删旧列**。旧列至少保留一个发布批次（§6.1 v2：CalVer，原稿「MINOR」读作发布批次），期间新代码只读写新列（不双读），旧代码仍能运行。
2. **删列放在后续版本的破坏相**，由 `upgrade` 的 `EnsureDestructive` 执行，强制备份确认。
3. 例外：安全原因必须立即删除的列/表，需在设计文档写明理由与不可回滚声明，并在 `CHANGELOG` 的 `Upgrade notes` 标注。

这条规则不改变 §5.1 的「运行时不双载体」——因为保留旧列不等于读取旧列；与 §5.1 条文本身的冲突消解方式见 §20.1/§20.2。

## 14. 回滚

| 阶段 | 回滚方式 |
| --- | --- |
| 破坏性动作发生前失败（含加法相、非破坏性步骤） | 换回旧二进制即可（旧列未删、旧结构兼容） |
| 任一破坏性动作成功执行后失败（chat 绑定/studio/监控表清理或破坏相） | 恢复备份；或重跑同版本 `upgrade` 前向续跑（破坏性动作幂等，账本断点续跑——本表只列回滚轴，续跑契约见 §2.1-2/§18-3） |
| 升级成功后因业务问题恢复旧备份再重升 | 重跑 `upgrade`（账本随备份回退，步骤按幂等契约重放）；**注意**：迁移后的人工数据修正（如 upstream base URL v2 迁移的 7 行人工等价修正）不会随重放复现，需按当时报告重做 |

`rollback` 字段按「本次运行是否已发生破坏性写」取值（§9.3），执行前由 `--dry-run` 给出「若继续将达到的等级」。

## 15. 升级测试矩阵

### 15.1 夹具

每个发布版本发布时生成并入库（`backend-go/testdata/upgrade-fixtures/vX.Y.Z/`）：

- **v2 口径（2026-10-30 实施修订）**：夹具 = 该版本二进制本身，从 `git archive <tag>` 临时构建（§15.1 原稿的 pg_dump 方案在 D14 复审中被否——schemasnapshot 只能导出 digest 化 JSON 无法还原 DDL，且 pg_dump 引入额外依赖）。旧版二进制对 pgtestkit 隔离空库执行 `--ensure-schema --seed [--mockdata]` 即得该版本真实形态，随后直接运行 HEAD 的 `upgrade`——不需要落盘 SQL 文件。
- 夹具形态随 tag 天然同源（归档即夹具）；无落盘、无生成流水线。

### 15.2 执行形态

对最近 3 个 tag 各跑一遍（P4 已交付本地形态：`JUHE_AI_TEST_EXTERNAL=1 ./scripts/upgrade-matrix.sh vN...`，CI 化另裁决 §20.6）：

```
归档构建 vN 版 maintenance 二进制（git archive → 临时目录）
→ pgtestkit 隔离空库执行 vN 版 --ensure-schema --seed [--mockdata]
→ HEAD upgrade --dry-run（断言 blocked/3 与 pending 计划）
→ HEAD upgrade --stop-write-confirmed --backup-confirmed（断言 upgraded/0）
→ 重跑断言 up-to-date/0 → 断言账本 12 行 applied 且 schema_revision == HEAD 的 SchemaRevision
```

启动门禁/冒烟边界：gateway/jobs 以升级后的库启动由启动门禁（§11）与部署后 `verify-release.sh` 覆盖；登录/建 Key/`/v1/chat` 冒烟由既有验收链覆盖，不进入矩阵。

任一条失败即阻止发布。

### 15.3 覆盖的失效模式

| 失效模式 | 由谁覆盖 |
| --- | --- |
| 跨版本漏跑迁移 | 夹具从 vN 起升级，pending 由账本计算 |
| 步骤顺序错误 | 同一夹具按 revision 顺序执行，乱序即失败 |
| 旧二进制读新库 | 反向用例：升级后启动 vN 门禁版二进制，断言 fail-fast 文本 |
| 配置改名 | `check-config` 对 vN 的 `.env` 夹具运行，断言 alias 告警与必填通过 |

## 16. 发布契约

1. 每次发布打 tag；`CHANGELOG.md` 固定结构：
   - `## vX.Y.Z`
   - `### Breaking`（无则写「无」）
   - `### Upgrade notes`：是否需要停写、是否需要备份、`upgrade` 会自动执行哪些步骤、是否有必须手工执行的独立命令
   - `### Rollback`：`binary-only` 或 `backup-required`
   - `### Pre-1.0 behavior notes`：pre-tag 历史批次的可见行为变更与核验 SQL 迁入于此（部署指南 §4 收敛后的去向，避免披露丢失）
2. `docs/deploy/部署指南.md` §4 收敛为**一页升级指南**：只保留「如何升级」与版本兼容矩阵；历史披露迁入 CHANGELOG（上一条）。
3. 支持策略：**任意已发布版本 → 最新**，由 §15 的最近 3 个版本矩阵背书；超出 3 个版本的升级仍允许，但不承诺回归覆盖。冷启动口径：矩阵自**首个同时具备账本与夹具流水线的 tag** 起生效（v1.0.0 若先于 P4 交付，其升级路径由 P1-P3 验收测试覆盖）；tag 不足 3 个时对现有 tag 全量执行。

## 18. 验收标准

1. 在 vN-3 夹具上执行单条 `upgrade` 命令，gateway/jobs 正常启动，冒烟通过。
2. 同一命令重复执行：`result=up-to-date`，除 `schema_state` 时间戳/版本字段外零写入（表行内容对比），耗时 < 3 秒（短路分支生效）。
3. 中断（kill -9）后重跑：从断点步骤继续，最终 `result=upgraded`；失败路径输出 JSON 报告 + stderr 摘要。
4. 库 revision 高于二进制时：gateway/jobs fail-fast 文案含「升级二进制」；`upgrade --dry-run` exit 3 且 `result=blocked`。
5. 库 revision 低于二进制时：fail-fast 文案列出待执行步骤标题；账本含超出注册表的 revision 时文案指明最低可用版本。
6. 删除一个环境变量（必填）→ 启动失败文案不变；新增一个未知 `JUHE_AI_*` → 启动成功且 WARN 可见。
7. `--dry-run` 零写入：求值在显式 `READ ONLY` 事务内执行，且关键业务表与账本行数前后一致。
8. 破坏性动作发生后失败/完成，报告 `rollback=backup-required`；其前失败，报告 `rollback=binary-only`。
9. 报告字段存在性符合 §9.3 矩阵（dry-run/已最新/升级完成/中途失败四场景）。

## 20. 开放问题（需裁决）

### 20.1 §5.1「不做向下兼容」的边界澄清

建议在 `功能开发指导.md` §5.1 增加边界声明。注意 §5.1 原文「无论是否涉及代码、API、数据库字段、表结构……都不做向下兼容」在 **schema 层**与 §13「旧列保留一个发布批次（§6.1 v2 CalVer）」直接冲突，仅追加「运行时代码」限定句豁免不了 schema 保留——**若 §20.2 选 A，须同步改写 §5.1 条文本身**（把「结构收敛两版走」写成显式例外），而非两句并存。

### 20.2 破坏性变更是否延后一个版本

§13 建议「新增/切换读写的版本不删旧列，删列留到下一个发布批次（§6.1 v2 CalVer）」。这会放慢存储收敛速度，但换来「换回旧二进制即可回滚」。

- 选项 A（推荐）：采纳。存储变更两版完成，回滚成本低，适合开源用户。
- 选项 B：维持现状。删列与代码同批，接受「回滚只能恢复备份」。

### 20.3 是否把 `juhe_jobs` / `juhe_j3b` schema 创建并入步骤 Apply

现状：两个 schema 需手工 `CREATE SCHEMA AUTHORIZATION`，再由 `--apply-*` 建表（`docker/single-server/README.md:31`）。对开源用户是额外的失败点。

建议：按 §8.3 在步骤 `Apply` 前执行 `CREATE SCHEMA IF NOT EXISTS`（不改既有 schema 的 owner），`--apply-*` 保留为幂等补表。若裁决不采纳，§8.3 末段删除。

### 20.4 账本是否记录「一次升级运行」的历史

本文只记步骤级结果。若要支持「这台机器上个月升级到哪个版本」的排查，需要额外 `schema_upgrade_runs` 表。建议先不做，靠 stdout 报告落盘（`--report-out`）。

### 20.5 升级前的备份最低保障与备份维度

`--backup-confirmed` 是纯人工声明；对从未配置备份的第三方用户，破坏性动作后数据安全完全押在自觉上。候选：① `upgrade` 内置 pg_dump + 按影响自动定维度（推荐，见下）；② 仅输出提示命令；③ 维持现状。属产品取舍，随 P1 裁决。

方案 ① 的**备份维度**（避免「数据量大了升级几小时」）：

- 存储分层决定备份分层：`juhe_business`/`juhe_chat`/`juhe_codex_context` 小而关键，每次升级必备；`juhe_usage`/`juhe_dataset` 大头只在当版破坏性 DDL 或迁移触及时才备；`juhe_stats` 由 `--rebuild-usage-stats` 可从 usage_records 重建、`juhe_jobs`/`juhe_j3b` 为可重放运行态，均不入升级备份；审计 blob/chat 资产等在文件系统，不在 pg_dump 范围且升级不触及。
- 触达清单由**步骤注册表自动推导**：每个 step 与分相 DDL 声明其触达的 schema，`upgrade` 取并集生成 dump 清单——默认清单通常只有 business/chat/codex_context（分钟级）；备份在停写窗口内、破坏性动作之前执行。
- 超大表破坏性变更不走 dump：沿用项目既有「迁移前自动建备份表 + 报告 rollbackSql」先例（`chat_conversations_bind_legacy_backup`、`audit_logs_in_progress_bak_20261023`），只拷受影响列/行。
- 灾备（整机/全量）与升级备份分离：前者由部署方的日常备份机制（如既有 203 主动拉取）承担，`upgrade` 只保证「破坏性动作前受影响数据可恢复」。
- 自动 dump 失败（磁盘不足/权限）→ 破坏性步骤拒绝执行，exit 2 指明原因。

### 20.6 CI 载体

仓库当前无任何 CI 配置；§15 矩阵先以本地脚本交付，是否引入 CI（GitHub Actions / 自托管 runner）与「发布流水线」形态属独立基建决策，不阻塞 P0-P3。
