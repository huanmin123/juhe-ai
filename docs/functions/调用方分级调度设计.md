# 调用方分级调度设计（压力自适应四级优先）

> 状态：设计提案 v1，待用户裁决开放项后分期实施。2026-10-17 由用户提出方向：「别让坏的把路都堵死了，先让好的通过；坏的你随便折腾都行，但是需要让路、减少资源占用；系统空闲没有分级，资源紧张才分流；纯系统层面，不能影响业务」。

## 1. 目标与非目标

**目标**

- 系统层面的调用方（API Key）四级优先级，行为劣化者让路、降资源占用，优质者优先通过。
- 压力自适应：空闲时全部层级完全同权（无任何差异化），拥塞时分级才产生资源效果。
- 业务零影响：模型、计费、API 形态、正常成功请求的响应语义对任何层级完全一致；分级只作用于排队/等待/唤醒顺序等**资源调度**维度。
- 全自动升降级，无人工配置入口（与「客户端画像由网关内部自动识别、不作用户配置项」的项目边界同构）。

**非目标**

- 不做上游 AI 账户的分级——上游侧已有 J3b 熔断 + J1 健康（账户逐渐降级为长期不可用/异常），本设计只补**调用方侧**。
- 不新增限流/配额维度（额度体系独立，本设计与 429 数值无关）。
- 不永久封禁任何 Key（T4 也只是让路，用户原话：「老赖偶尔花点小钱」——花钱的权利永远保留，只是拥挤时排后面）。
- 不引入 feature flag（压力门控是内在行为，不是开关）。

## 2. 分级对象与四级定义

分级对象 = API Key（调用方），系统内维度，管理员只读可见、不可手改。

| 层级 | 名称 | 含义 |
| --- | --- | --- |
| T1 | 优质 | 长期干净记录 earned（默认不是 T1，信用要赚） |
| T2 | 正常 | **默认档**，所有新 Key 出生即 T2 |
| T3 | 观察 | 行为劣化信号持续，降资源优先序 |
| T4 | 受限 | 持续劣化或硬信号命中（老赖），拥塞时让路 |

## 3. 信号源（怎么分）——只采集「调用方可控行为」

关键原则：**区分责任方**。上游账户故障、系统侧资源饱和造成的失败不是调用方的错，计入会让无辜用户降级。只采调用方自己造成/可控制的信号：

1. 429 撞击频率：反复打满配额仍高频重试（复用 quota 记录面）。
2. 4xx 参数错误率：持续发非法请求（复用错误分类面）。
3. 主动取消/超时弃单率：客户端异常 abort 风暴（复用请求终止观测）。
4. 队列重入率：拥塞下反复超时重进（复用 high_concurrency_dispatch_queue 埋点的 waitedMs/reason）。
5. 并发超限频率：反复撞 perKey 并发上限。
6. 硬信号（直接 T4）：确认的滥用模式（枚举自现有审计/安全信号，实施期定清单，见开放裁决项 2）。

所有信号已有数据源（审计日志、quota、dispatch metadata），零新埋点。

## 4. 升降级规则（怎么涨怎么降）

- **滚动窗口计分**：24h 滑动窗口统计各信号强度（Redis 滚动计数）。
- **降快升慢（迟滞）**：
  - T2→T3：窗口内劣化信号连续超阈（如 15 分钟）；
  - T3→T4：持续超阈（如 1 小时）或硬信号命中（立即）；
  - T4→T3：连续 24h 零劣化信号（老赖要慢慢赚回信用）；
  - T3→T2：信号半衰自动回落（约 1h 无新增）；
  - T2→T1：连续 N 天（建议 7 天）干净且量达标（ earned，防冷启动 Key 冒充）。
- 全部阈值为内部常量（与项目「功能不设开关」纪律一致），首版取值偏保守（宁可少降级，不允许误伤优质客户），上线观察后调。

## 5. 压力门控（空闲不分级）与资源杠杆（让路怎么让）

分级状态**始终**在后台维护（打分不停），但资源效果**仅在压力下生效**。压力定义：分组队列非空、并发饱和、或请求进入等待预算消耗——三者任一即视为拥塞。

| 杠杆 | 空闲时 | 拥塞时 | 插入点 |
| --- | --- | --- | --- |
| 唤醒顺序 | FIFO（同级内也 FIFO，完全同权） | 容量释放按层级唤醒：T1→T2→T3→T4，同级内保持 FIFO | `HighConcurrencyGroupQueue.findQueueWakeCandidate` |
| 等待上限 | 全额 `maxQueueWaitMs` | T3 ×0.5、T4 ×0.25 打折——老赖更早超时让路（晕倒的人拖到路边，不用等他醒） | `WaitForCapacity` 的 MaxWaitMs 入参 |
| 队列准入 | 正常 | 队列满时先拒 T4/T3（T1/T2 仍可入队） | 既有 perAPIKeyQueueLimit 机制加层级维度 |
| 并发槽竞争 | 无差别 | 槽位竞争排序按层级 | dispatch 段内排序扩展 |

分期交付（每期独立可验收）：

- **M1（观测期，先行）**：状态存储 + 信号采集 + 自动升降级，**无任何资源效果**——先跑真实流量，用分级结果与人工直觉对拍，验证分级质量（分级错误的代价是伤优质客户，必须先证伪）。
- **M2（核心让路）**：唤醒顺序 + 等待打折两项杠杆上线。
- **M3（视观察）**：队列准入/并发槽维度，仅当 M2 观察显示仍堵才加。

## 6. 复用与存储

- 状态存储复用 `gatewaycircuit` 双驱动模式：Redis 权威（key `juhe-ai:caller-tiers:<apiKeyHash>`，滚动计数+层级+状态机时间戳），memory 形态进程内（本地单机形态单进程，语义不变）。
- 队列杠杆全部落在既有 `HighConcurrencyGroupQueue` 与 dispatch 预算层，不改队列数据结构（层级作为 item 字段参与排序/上限计算）。
- 分级对管理页只读展示（后续期次，非本期）。

## 7. 风险

1. **误伤优质客户是本设计最大风险**——对策：信号只取调用方可控行为 + M1 观测期先行 + 首版阈值保守。
2. Redis 不可用时降级为 memory 形态（与电路恢复同先例），单机形态无差异；Redis 分片场景下分级按实例独立（可接受，层级是软状态）。
3. T4 让路对其用户体验可见（等待变长、更早超时）——这是设计的本意（资源公平），但需在文档明示：T4 收到的仍是标准 queue timeout 语义，无新增错误码。

## 8. 验收标准

1. 空闲注入：T4 与 T1 请求行为逐项一致（无差异化路径触达）。
2. 拥塞注入：同组持续容量竞争下，T1 平均等待 < T4，T4 更早收到标准 queue timeout。
3. 升降级：注入劣化信号 → 按迟滞曲线降级；信号停止 → 按迟滞曲线恢复；硬信号 → 立即 T4。
4. 业务不变：任意层级成功请求的模型/计费/响应完全一致；空闲时 T4 无任何额外路径。
5. 双形态：memory 与 Redis 运行态行为一致（单机 memory 形态语义不变）。

## 9. 开放裁决项（需用户确认后实施）

1. **四级保留 T1？** 推荐保留（长期信用奖励成本低），备选三级（T2/T3/T4）更简单。
2. **T4 硬信号清单**：直接降 T4 的确认滥用模式需要枚举（从现有审计/安全信号选），推荐首版宁缺勿滥、只放最确定的 1-2 种。
3. **让路力度**：等待打折 0.5/0.25 首版是否够，还是直接上准入拒绝——推荐首版只做唤醒顺序+等待打折。
4. **实施启动**：M1 观测期是否随下一发布单元走，还是等批次 0/1 发布核验后再排。
