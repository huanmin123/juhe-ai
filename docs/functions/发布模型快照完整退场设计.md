# 发布模型快照完整退场设计

## 1. 背景

客户端 `/models`、`/v1/models` 和 AI 问答已经统一使用按 API Key 路由供应商合集动态聚合的模型目录。Node 旧 `gateway_model_catalog_snapshots` 最终响应快照没有运行时消费者，但其生产、预热、dirty rebuild、内部 HTTP bridge 和 DB service 读取操作仍在执行，形成空转链路和过期契约。Go runtime 不属于本次关注范围。

## 2. 退场边界

- 删除 Node 发布快照 service、reconcile service、内部 rebuild router、维护脚本及启动预热/扫描逻辑。
- 删除系统账户和供应商模型写入后的发布快照重建调用。
- 删除 DB service 的快照查询 operation 与 storage repository 导出。
- SQLite 启动时删除废弃快照表。PostgreSQL 表暂留给不在本次范围内的 Go runtime；Node 不再读取、写入或检查这些表。
- 历史 migration 保持不可变，只作为数据库演进记录；当前代码、测试和权威文档不得继续把快照当作运行时能力。

## 3. 保留能力

- 供应商级模型目录及其进程内 / Redis 缓存继续保留。
- 公开模型目录、认证模型目录和 AI 问答均继续调用动态目录服务。
- 模型管理写入后现有供应商目录缓存失效逻辑继续保留。
- AI 问答前端所有 `/my-chat` 请求必须有同方法、同路径的后端路由；模型列表和能力详情必须纳入接口对照回归。

## 4. 数据迁移

- SQLite 快照表只保存可重建派生数据，不属于业务事实，允许直接删除。
- PostgreSQL 不执行删表 migration，避免影响仍依赖该机制的 Go runtime。

## 5. 验收

- 非历史 migration、历史 bug/计划归档之外，不再存在 `chat_list:*`、`chat_model:*`、发布快照 service 或 rebuild bridge 的生产引用。
- Node 启动不再预热、扫描或检查发布快照表权限。
- Node 模型写入不再产生发布快照重建副作用。
- 前端 Chat API 与后端 Chat router 方法/路径全部匹配。
- 类型检查、构建、Node 回归和 schema gate 验证通过。
