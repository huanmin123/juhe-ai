# 供应商订阅认证接入安全设计

> 状态：调研完成，尚未开放任何新认证方式。

## 结论

CLIProxyAPI 的认证能力不能按“供应商有 OAuth”直接复制到本项目。它同时包含官方 API Key、用户订阅 OAuth、设备授权、服务账号 JSON 和外部 WebSocket relay；这些凭据的授权主体、上游契约、条款和安全边界不同。

当前项目只应将已验证、允许服务端代理且有明确凭据生命周期的方式设计成一等账户类型。任何依赖非公开客户端 ID、模拟 CLI 请求、反检测 TLS 指纹或把个人订阅账号组成代理池的方式，必须先完成供应商条款与真实授权核验；在完成前不得显示为可用账户类型。

## 不可直接复用的实现

- Claude 订阅 OAuth 使用固定第三方 client ID、Claude Code scopes，并以 Bearer token 转发推理请求；不能等同于 Anthropic 官方 API OAuth。
- 其 Claude 链路使用 uTLS 模拟浏览器 TLS 指纹以绕过 bot detection；本项目禁止实现或移植该行为。
- 默认凭据存储为明文 JSON，且部分后端可同步到 Git / 对象存储；本项目必须继续使用账户凭据应用层加密，列表、操作日志和普通运行日志不得输出 secret。
- 本地 OAuth callback 不能监听所有网卡；必须只绑定 loopback、使用一次性 state/PKCE、严格过期与取消、并防止并发会话覆盖。

## 统一落地前提

每一种候选认证方式均须先满足以下条件：

1. 供应商公开文档或书面许可明确允许该认证类型在本项目的服务端代理场景使用。
2. 凭据来源、授权范围、刷新端点、撤销语义和最小 scopes 可验证；不得复用未获授权的第三方 client ID 或 client secret。
3. 账户类型、协议档案和上游请求认证方式独立建模，不把订阅 token 伪装成 API Key。
4. 凭据应用层加密保存；刷新并发按账户去重。远端 token endpoint 的状态码、错误码和正文不自动触发重放、冷却或账号切换，只有安全重放规则与用户显式策略 / 匹配来源证据同时满足时才执行对应动作。
5. 至少具备 mock 回归、刷新并发回归、撤销 / 过期回归与用户自有真实账户 E2E；真实验证不记录 token。

## 建议实施顺序

1. 补齐现有 GPT OAuth 的设备码可行性与真实验证，不改变 OAuth 主体或凭据安全模型。
2. 对 Kimi、xAI、Antigravity、Vertex 服务账号分别完成官方协议与条款调研；每项独立建立供应商、账户类型和测试矩阵。
3. Claude.ai / Claude Code 订阅 OAuth 仅在取得明确可代理依据后再立项；否则保持 Anthropic API Key-only。

## 本地联调替代路径

如果目标只是本地复用 CLIProxyAPI 已完成的 OAuth 认证，而不是在 juhe-ai 内直接复制其认证内核，当前推荐把 CLIProxyAPI 作为 loopback sidecar 运行，再把 juhe-ai 的普通上游账户指向 sidecar 暴露的 `/v1` 或 `/v1beta` 入口。具体接法见 [CLIProxyAPI 本地 Sidecar 接入](CLIProxyAPI本地Sidecar接入.md)。
