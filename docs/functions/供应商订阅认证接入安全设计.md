# 供应商订阅认证接入安全设计

> 状态：持续维护。Anthropic、Gemini 与 Grok 的已验证 OAuth 路径已经在 Node 后端落地，其余候选认证方式仍按本文安全前提单独评估。

## 结论

CLIProxyAPI 等参考项目同时包含官方 API Key、用户订阅 OAuth、设备授权、服务账号 JSON 和外部 WebSocket relay；这些凭据的授权主体、上游契约和安全边界不同。本项目可以复用已经确认的协议常量与交互顺序，但必须落入本项目的账户类型、凭据加密、日志脱敏、代理和运行时能力边界。

当前已作为一等账户类型落地的新增路径包括 Anthropic 浏览器 PKCE / Refresh Token / Access Token、Gemini `code_assist|google_one|ai_studio` OAuth，以及 Grok 浏览器 PKCE / Refresh Token / Access Token / SSO Cookie 转 device flow。固定客户端、scope、token 端点和上游 runtime 只能在对应供应商适配器内使用，不得泛化成可跨供应商复用的 OAuth 模板。

## 不可直接复用的实现

- Claude 订阅 OAuth 使用固定 client ID、Claude Code scopes，并以 Bearer token 转发推理请求；它是独立的 Anthropic OAuth 账户类型，不能伪装成 Anthropic API Key。
- 其 Claude 链路使用 uTLS 模拟浏览器 TLS 指纹以绕过 bot detection；本项目禁止实现或移植该行为。
- 默认凭据存储为明文 JSON，且部分后端可同步到 Git / 对象存储；本项目必须继续使用账户凭据应用层加密，列表、操作日志和普通运行日志不得输出 secret。
- 本地 OAuth callback 不能监听所有网卡；必须只绑定 loopback、使用一次性 state/PKCE、严格过期与取消、并防止并发会话覆盖。

## 统一落地前提

每一种候选认证方式均须先满足以下条件：

1. 凭据来源、授权主体、授权范围、刷新端点、过期语义和最小 scopes 必须可验证。
2. 固定 client ID、client secret、scope 和产品专用上游只能封装在对应供应商与账户模式中；前端不得允许用户把内置客户端切换到不兼容的 runtime。
3. 账户类型、协议档案和上游请求认证方式独立建模，不把订阅 token 伪装成 API Key。
4. 凭据应用层加密保存；刷新并发按账户去重。远端 token endpoint 的状态码、错误码和正文不自动触发重放、冷却或账号切换，只有安全重放规则与用户显式策略 / 匹配来源证据同时满足时才执行对应动作。
5. 至少具备 mock 回归、刷新并发回归、撤销 / 过期回归与用户自有真实账户 E2E；真实验证不记录 token。

## 当前落地顺序

1. Anthropic、Gemini 和 Grok OAuth 已按独立 ProviderDriver、账户能力与运行时完成 Node 实现和 mock 契约回归。
2. Gemini Code Assist / Google One 只开放 GenerateContent JSON / SSE；Grok OAuth 只开放 Responses JSON / SSE，不能因 API Key 账户能力更宽而放松。
3. Kimi、Antigravity、Vertex 服务账号等其余认证方式继续独立调研；未建档前不得复用当前 OAuth 端点或账户类型。

## 本地联调替代路径

CLIProxyAPI loopback sidecar 仍可用于参考实现对照或未纳入本项目的认证方式，但 Anthropic、Gemini 和 Grok OAuth 已由 juhe-ai 自己管理，不再依赖 sidecar。sidecar 的普通上游接法见 [CLIProxyAPI 本地 Sidecar 接入](CLIProxyAPI本地Sidecar接入.md)。
