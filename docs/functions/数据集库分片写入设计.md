# 数据集库分片写入设计

## 文档目标

本文用于记录统计数据集域从单 SQLite 文件演进为数据集目录库加 usage shard 的当前方案，重点解决这些问题：

- 为什么三库拆分后仍会遇到数据集目录库写锁瓶颈。
- 哪些表需要分片，哪些表暂时保持单库。
- `usage_records` 如何按多个 SQLite 文件并行写入。
- 分片后统计、明细查询、API Key 删除清理、数据保留和统计重建如何保持原有语义。
- 如何在不引入 Redis、Kafka、PostgreSQL、ClickHouse 等外部依赖的前提下提升写入速度。

本文是方案设计和实施依据。当前运行实现以业务库、统计数据集域和统计结果库为主；统计数据集域已经从“一个数据集 SQLite 文件”扩展为“数据集目录 + 数据集目录库 + 使用记录分片 SQLite 文件”的轻量本地存储形态。

当前数据保护等级：

- 业务主库是必须保护的恢复事实，账号、分组、API Key、授权、配置等业务数据不能因为统计重建或分片迁移被破坏。
- 统计数据集目录库、usage shard 和统计结果库都属于可再生统计域，可以在停机维护、模型切换或统计口径重建时删除后重建。
- 不为分片前的 `usage_records` 做复杂历史适配、长期模型迁移或双模型维护；历史 usage 明细和历史统计可以明确放弃，优先采用当前分片模型。

## 背景与问题

项目先完成三库拆分：

- 业务库保存可恢复业务事实。
- 数据集目录库当时保存使用记录、审计、操作日志、公开接口日志、运行日志索引、模型检测等高增长事实。
- 统计结果库保存统计缓存、额度窗口、排行、范围窗口、账号质量和监控结果。

这一步已经把业务写入、数据集写入和统计查询隔离开，是正确方向。但 SQLite 的写锁边界仍然是单个数据库文件；如果 `usage_records`、`audit_logs`、`operation_logs`、`runtime_logs` 等高频事实都写入同一个数据集目录库文件，高峰期仍会出现单文件单 writer 排队。

最热路径是网关每次请求终态写入的 `usage_records`。它不仅频率最高，还要支撑统计游标、使用记录列表、账号质量、额度缓存、授权消耗和排障详情。继续只在一个数据集目录库文件内“分表”，不能解决 SQLite 单文件写锁；必须把最热事实拆到多个 SQLite 文件，形成多把独立写锁。

## 核心结论

- 分片优先解决 `usage_records`，不先改审计、操作日志、运行日志和模型检测。
- 分片单位是 SQLite 文件，不是在同一个 SQLite 文件里建多张同构表。
- 分片键采用 `bucket_date + shard_id`：日期控制保留和归档，hash shard 控制同一天写入并行度。
- 每个 shard 文件按短事务串行写入；当前第一阶段由 background worker 按 shard 分组写入，独立 child process / worker thread writer pool 是后续性能增强。
- 统计结果库不分片，额度判断、统计页面、列表用量仍只读统计结果库。
- 统计 worker 从“单游标扫描 `usage_records`”改为“按 shard 独立游标公平推进”，统计口径不变。
- 明细列表通过 shard 路由层跨 shard 合并分页；详情通过 usage id 中的 shard 信息直接定位。
- API Key 删除、数据保留和统计重建都必须按 shard 维度执行，不能回退为全库扫描或跨库强事务。
- 业务主库必须保护；数据集目录库、usage shard 文件和统计结果库都可以删除重建。
- 第一阶段不做复杂历史适配或模型迁移；分片前 usage 历史可放弃，新模型从启用时间重新累计。
- 默认仍保持单机轻量部署，不引入外部队列或外部数据库；后续多实例另行设计。

## 当前落地状态

本轮代码已经完成第一阶段主链路：

- 新增 `JUHE_AI_USAGE_SHARD_ROOT` 和 `JUHE_AI_USAGE_SHARD_COUNT` 配置，默认跟随数据集目录库所在目录创建 `usage-shards`。
- 新 usage 不再写入数据集目录库中的旧 `usage_records` 单表，而是按 `createdAt + stable hash(id)` 写入多个 shard SQLite 文件。
- 使用记录列表、详情、最近请求形态、统计聚合、API Key 删除清理和保留期清理都已切换到 shard 访问层。
- 统计结果库使用 `scope_type = 'usage_shard'` 的 per-shard 游标推进，统计结果仍保持原表结构和原 API 口径。
- 账号 `last_used_at` 从 usage shard 写事务中拆出，使用短事务和 30 秒内存节流，避免每条 usage 都拖回业务主库写锁。
- 本地回归已覆盖 shard 路由、重复投递幂等、列表合并、详情读取、统计聚合、API Key 清理、保留清理、作用域、额度快速路径、模型检测和性能脚本。

当前实现先复用现有 background worker usage 队列，在 worker 内按 shard 分组并对每个 shard 执行短事务。独立 child process / worker thread writer pool 是下一步性能增强，不阻塞第一阶段从“单数据集目录库热表”切到“多 SQLite shard 文件”的落地。

## 范围边界

### 第一阶段只分片 `usage_records`

`usage_records` 是网关请求事实源，也是当前最可能放大写锁的表。第一阶段只拆它，原因是：

- 每次上游尝试都会产生记录，写入频率远高于管理操作和模型检测。
- 统计、额度、账号质量和授权消耗都以它为输入，收益最大。
- 它不依赖跨库外键，天然适合拆到多个 SQLite 文件。
- 先拆单表能把风险集中在一条事实链路，避免一次性改动审计 payload、运行日志索引和操作日志可见性。

### 暂不分片的表

这些表第一阶段仍保存在统计数据集目录库，也就是当前 `JUHE_AI_DATASET_DATABASE_PATH` 指向的 SQLite 文件：

| 表 | 第一阶段策略 | 原因 |
| --- | --- | --- |
| `audit_logs`、`audit_log_attempts`、`audit_payload_refs`、`audit_payload_blobs`、`audit_error_groups` | 暂不分片 | 审计成功采样率低于 usage，且涉及 payload 去重和错误组 upsert，先保持现有保全策略 |
| `operation_logs`、`operation_log_targets`、`operation_log_viewers` | 暂不分片 | 管理操作频率低，且用户可见范围预计算需要保持简单 |
| `runtime_logs`、`runtime_log_file_cursors`、facets | 暂不分片 | 运行日志索引已有文件游标和短保留期，先保留单库短事务 |
| `model_check_runs`、`model_check_items` | 暂不分片 | 模型检测是显式诊断动作，不是请求高频写入 |
| `api_key_record_cleanup_targets` | 暂不分片 | 作为清理任务登记入口，数据量小 |

如果后续真实压测显示审计或运行日志索引也成为写锁瓶颈，再按同一模式独立设计 shard，不和 usage 分片混在一起。

## 存储形态

三库口径保持不变，但统计数据集域已经从单文件扩展为数据集目录库加 usage shard 文件：

```text
backend/data/
  juhe-ai.sqlite3
  juhe-ai-dataset.sqlite3
  juhe-ai-stats.sqlite3
  usage-shards/
    2026/
      05/
        24/
          usage-20260524-s00.sqlite3
          usage-20260524-s01.sqlite3
          ...
          usage-20260524-s15.sqlite3
```

默认配置建议：

```dotenv
JUHE_AI_DATABASE_PATH=./data/juhe-ai.sqlite3
JUHE_AI_DATASET_DATABASE_PATH=./data/juhe-ai-dataset.sqlite3
JUHE_AI_STATS_DATABASE_PATH=./data/juhe-ai-stats.sqlite3
JUHE_AI_USAGE_SHARD_ROOT=./data/usage-shards
JUHE_AI_USAGE_SHARD_COUNT=16
```

配置规则：

- `JUHE_AI_DATASET_DATABASE_PATH` 继续存在，作为数据集目录库，保存未分片数据集表和分片 catalog。
- `JUHE_AI_USAGE_SHARD_ROOT` 未配置或留空时跟随 `JUHE_AI_DATASET_DATABASE_PATH` 所在目录生成 `usage-shards`；显式相对路径按 `backend/` 目录解析，示例配置使用 `./data/usage-shards`。
- `JUHE_AI_USAGE_SHARD_COUNT` 初始建议为 `16`。该值一旦生产启用，不能直接改小；扩容需要独立 rebalance 计划。
- shard 文件同样使用 WAL，并设置 `busy_timeout`。是否把 `synchronous` 调整为 `NORMAL` 必须作为明确配置和验证项，不能隐式改变持久性口径。

## 分片路由

每条使用记录在入队前必须拥有稳定的 `id` 和 `createdAt`。路由算法：

```text
bucket_date = YYYYMMDD(createdAt)
shard_id = stable_hash(id) % JUHE_AI_USAGE_SHARD_COUNT
shard_key = bucket_date + ':s' + shard_id
```

usage id 建议带上日期和 shard 信息：

```text
usage_20260524_s03_1780000000000_abcd1234
```

这样详情查询可以从 id 直接定位 shard；不含 shard 信息的 id 不作为可查范围。

当前运行时只保证 shard 记录可查；不含 shard 信息的 id 可按不存在处理，详情和列表不扫描其他库，也不提供双模型查询入口。

约束：

- shard id 必须由稳定 hash 计算，不能用递增计数轮询，否则进程重启或并发顺序变化会让同一记录无法稳定定位。
- hash 输入优先使用 usage id；如果调用点还未生成 id，必须先补 id 再路由。
- 日期来自记录创建时间，不来自当前系统时间；迟到记录写入其自身 `createdAt` 对应日期 shard。
- shard 文件路径由日期和 shard id 确定，不能由用户输入拼接。

## Shard Catalog

数据集目录库新增轻量 catalog，用于记录 shard 文件状态和运维观测。当前已落地表：

```text
usage_record_shards
```

当前已落地字段：

| 字段 | 含义 |
| --- | --- |
| `shard_key` | 主键，例如 `20260524:s03` |
| `bucket_date` | 日期桶，例如 `2026-05-24` |
| `shard_id` | 数字 shard 编号 |
| `file_path` | 相对 `backend/` 的 shard 文件路径 |
| `schema_version` | shard schema 版本 |
| `status` | `active`、`sealed`、`archived`、`deleted`、`error` |
| `first_seen_at` / `last_write_at` | 首次发现和最近写入时间 |
| `last_error_message` | 最近打开、写入、采样或清理错误 |
| `created_at` / `updated_at` | 元数据时间 |

后续如果需要更强运维观测，可以通过显式 schema 变更补充这些可选字段；它们不是当前 schema，也不能作为当前实现依赖：

| 字段 | 含义 |
| --- | --- |
| `min_created_at` / `max_created_at` | 已知时间范围 |
| `min_id` / `max_id` | 已知 id 范围 |
| `row_estimate` | 估算行数，不要求强实时精确 |
| `database_bytes` / `wal_bytes` | 最近采样文件大小 |
| `sealed_at` / `deleted_at` | 封存和删除时间 |

catalog 只用于定位、观测和维护，不参与统计强一致判断。统计是否处理完成以统计结果库里的 per-shard 游标为准。catalog 损坏时可以扫描 `JUHE_AI_USAGE_SHARD_ROOT` 重建。

## 写入链路

当前第一阶段写入链路：

```text
网关终态
  -> normalize usage input(id, createdAt, snapshot 上限)
  -> server IPC / worker 本地入口
  -> usage shard router
  -> worker 内按 shard 分组
  -> shard SQLite 短事务批量 INSERT
  -> writer runtime snapshot
```

写入规则：

- server 角色不直接打开 usage shard 写库。
- worker 接收到 usage 后在本地队列批量 flush，按 shard 分组后逐个 shard 执行短事务。
- 当前第一阶段没有独立 per-shard writer 进程；同一 shard 写入由 SQLite 连接和短事务串行化。
- writer 以短事务批量写入，初始单批可沿用 `200`，再按目标机器压测调整到 `500` 或 `1000`。
- 每个批次只写一个 shard 文件，不能在同一事务里跨 shard 写入。
- `ON CONFLICT(id) DO NOTHING` 保留，用于重试或重复投递幂等。
- 账号 `last_used_at` 不应跟随每条 usage 同步写业务库；必须改为按账号节流合并队列，例如每个账号 30 到 60 秒最多刷新一次。
- 后续如果引入 writer pool，每个 writer 应独占自己的 SQLite 连接、prepared statements 和待写队列。

### Writer Pool

推荐新增本地 writer pool，而不是让通用 background worker 一个进程顺序写所有 shard：

```text
background worker
  -> usage shard writer 0: owns s00-s03
  -> usage shard writer 1: owns s04-s07
  -> usage shard writer 2: owns s08-s11
  -> usage shard writer 3: owns s12-s15
```

实现可以使用 child process 或 worker thread。优先 child process，原因是：

- `DatabaseSync` 阻塞不会拖慢通用 background worker 的统计、清理和审计任务。
- 单个 writer 崩溃时 supervisor 可以只重启对应 writer。
- 每个进程的队列、事件循环延迟和内存都能单独观测。

writer 数量不一定等于 shard 数。建议 `writerCount = min(4, shardCount)` 起步，每个 writer 拥有一组 shard，避免一次性创建过多 Node 子进程。

## 持久性与降级

当前记录队列是 best-effort，统计数据集域事实丢失不会回滚业务请求。分片落地后必须把策略显式化：

| 模式 | 行为 | 适用场景 |
| --- | --- | --- |
| `best_effort` | IPC 或 writer 队列满时允许丢弃 usage，并记录 dropped 计数 | 个人轻量部署、追求请求不中断 |
| `durable_spool` | usage 先写本地 append-only spool，再由 writer 刷入 SQLite，刷入成功后推进 spool offset | 更重视计量完整性 |
| `strict` | durable spool 不可写或 writer 长时间不可用时，后续请求可以进入本地保护或快速失败 | 明确把本地计量完整性放在可用性之前 |

第一阶段默认仍建议 `best_effort`，保持当前项目轻量边界；但设计必须预留 `durable_spool`，否则后续无法回答“计费级 usage 是否会丢”。

spool 规则：

- spool 也是按 `bucket_date + shard_id` 拆分的 JSONL 或 length-prefixed 本地文件。
- spool 必须记录 offset，只在 SQLite 批量写入并确认后推进。
- spool 读取按 offset / chunk 进行，不能一次读完整文件。
- spool 文件与 shard 文件使用同一保留水位；已确认落库且超过保留期后删除。

## 查询链路

### 详情查询

详情优先通过 usage id 定位 shard：

```text
usage_20260524_s03_xxx -> usage/2026/05/24/usage-20260524-s03.sqlite3
```

如果 id 不含 shard 信息，默认返回不存在，不为了补查单条记录扫描其他库或全库。如果确实需要核查既有数据，只允许停机后用临时离线脚本或直接 SQL 处理；处理结果不进入正常 API、repository 或启动路径。

### 列表查询

使用记录列表响应结构不变，但请求路径不再逐 shard 拉取候选再做 JS 合并排序：

1. 写入 usage shard 时，同步在数据集目录库 `usage_record_shard_entries` 记录 `usage_id`、`shard_key`、归属、API Key、常用筛选字段和排序字段；同时维护 `usage_record_account_shards`、`usage_record_api_key_shards` 两张去重 shard 目录，供删除清理按账号 / API Key 精确定位仍有记录的 shard。
2. 列表先从 `usage_record_shard_entries` 读取固定候选窗口，窗口上限为 `pageSize + 1` 叠加最大页码后的 1001 行，不按 shard 数量放大。
3. 只对当前页命中的 `usage_id` 按 `shard_key` 分组回到 usage shard 批量补取明细字段。
4. 返回 `pageSize + 1` 判断 `hasMore`，`total` 继续保持分页上界，不做精确全量 COUNT。

限制：

- 无筛选深翻页只在固定 catalog 窗口内翻页；超过窗口的历史明细必须通过日期、账号、分组、模型或结果筛选重新收敛，不允许请求链路线性越过窗口。
- 排序字段只支持已有索引可支撑的字段；新增排序必须先评估每个 shard 上的索引写放大。
- 列表补名仍通过业务库按当前页 ID 批量补齐，不跨 shard join。
- 已删除 AI 账户 / API Key 的关联清理不从明细目录临时 `GROUP BY shard_key`，只读取去重 shard 目录里的固定窗口，再回具体 usage shard 按统计安全游标分批扣减和删除。

### 最近请求形态学习

账号恢复探活、模型检测辅助、账号质量诊断等需要读取最近真实请求形态时，按最近日期 shard 倒序查找，默认只看最近 7 天，找到第一条满足条件的记录即停止。禁止为了学习请求形态扫描全保留期所有 shard。

## 统计聚合

统计结果库不分片。变化只在统计输入侧：

```text
usage shard 20260524:s00
usage shard 20260524:s01
...
  -> aggregate batch
  -> stats database transaction
  -> upsert usage_stats_* / authorization_* / account_quality_*
  -> advance stats_job_state(job_name, source_type=usage_shard, source_id=20260524:sNN)
```

游标规则：

- 每个 shard 对每个统计 job 都有独立游标。
- 游标仍使用 `(created_at, id)`，写在统计结果库。
- 统计结果 upsert 和游标推进必须在同一个统计结果库事务中完成。
- 如果统计结果库事务失败，不推进该 shard 游标，下一轮重复读取同一批。
- 如果 shard writer 仍在写入当天 shard，统计 worker 可以同时读 WAL 快照，但只处理已提交记录。
- 每轮聚合必须公平调度多个 shard，不能一个大 shard 长时间阻塞其他 shard。

统计延迟指标改为：

- `usage_stats_lag_max_seconds`：所有 active shard 中最大的统计延迟。
- `usage_stats_lag_p95_seconds`：active shard 延迟分布。
- `usage_stats_oldest_unprocessed_shard`：最旧未处理 shard。
- `usage_stats_shard_cursor_count`：当前需要维护的 shard 游标数量。

额度判断仍只读统计结果库，因此语义不变：允许短暂统计延迟和轻微超额，统计追平后拦截。

## API Key 删除与记录清理

API Key 业务删除仍同步移除业务库记录，让后续请求立即不可用。关联记录清理改为 shard 任务：

```text
register cleanup target(apiKeyId)
  -> enumerate retained usage shards
  -> enqueue per-shard cleanup job
  -> DELETE FROM usage_records WHERE api_key_id = ? LIMIT window
  -> stats result deduction / cleanup remains in stats database
  -> mark shard cleanup progress
```

约束：

- 不新增中心化 `api_key_id -> usage_id` 明细索引表，否则会重新制造单点高频写入。
- 清理任务只能按 shard 分批执行，不能在 API 请求内同步扫 shard。
- 统计结果库反向扣减或清理仍以已聚合结果为准，不依赖统计数据集域清理和统计结果清理的跨库事务。
- 每条 usage 的统计反向扣减必须通过统计结果库内的 `usage_record_cleanup_deductions` 账本幂等保护：统计扣减和账本标记同事务提交，shard 删除失败后重试只补删；shard 已删但后续收尾失败时也不能重复扣减。
- 如果某个 shard 已归档或删除，清理任务记录跳过原因；不因为关联明细已不存在而阻塞 API Key 删除完成。

## 数据保留与归档

分片后 `usage_records` 清理优先按 shard 文件处理，而不是在大表里批量 DELETE：

1. 找到超过保留期的 shard。
2. 确认所有统计 job 对该 shard 的游标已经处理到 shard 最大 `(created_at, id)`。
3. 确认 API Key 删除等维护任务没有未完成的必要处理。
4. 将 shard 标记为 `sealed`。
5. 按配置删除、压缩归档或移动到离线目录。

好处：

- 删除旧数据可以直接删除文件，避免 SQLite 大量 freelist 和长时间 VACUUM。
- WAL 和主文件大小按日期自然收敛。
- 表监控可以直接看到单个 shard 文件异常增长。

当天 active shard 和最近保护窗口不做整文件删除。需要提前释放空间时，只允许 worker 对已安全的旧 shard 做受控批次清理。

## 统计重建

统计重建只以 shard 输入为准，统计结果库可删除后从当前可用数据重新生成。默认不读取分片前 usage，也不恢复切换前统计。

| 来源 | 处理方式 |
| --- | --- |
| usage shard 文件 | 按日期和 shard id 稳定顺序扫描 |
| 已归档 shard | 默认不读取；显式传入归档目录时才读取 |

重建流程：

1. 停止 Web、DB service 和 background worker。
2. 备份业务库和 `backend/.env`；数据集目录和统计结果库按需备份，不作为必须保护对象。
3. 删除或清空统计结果库中的统计缓存和 `stats_job_state`。
4. 扫描 shard 输入源，按批写入统计结果库；不扫描旧单表 usage。
5. 记录每个 source 的重建游标和结果。
6. 启动服务，让新请求从新 shard 继续累计。

如果数据集 shard 已删除，历史统计明确放弃，从新请求重新累计。

## 表监控与运行态观测

表监控后续需要从“三个 SQLite 文件”扩展为“四类观测对象”：

- 业务库文件。
- 数据集目录库文件。
- usage shard 文件集合。
- 统计结果库文件。

usage shard 观测至少包含：

| 指标 | 用途 |
| --- | --- |
| shard 总数、active shard 数 | 判断文件数量和活跃窗口 |
| 最大 shard 主文件大小、最大 WAL 大小 | 发现单 shard 写入倾斜 |
| 当天每个 shard row 估算 | 判断 hash 是否均匀 |
| writer 队列长度、队列字节数 | 判断写入是否跟得上请求 |
| writer 最近 flush 成功时间、失败次数 | 判断落库健康 |
| shard 统计延迟 | 判断统计 worker 是否落后 |
| spool 待刷字节数 | durable 模式下判断积压 |
| dropped / rejected 计数 | best-effort 模式下判断数据丢弃 |

管理页面不能为了展示精确总行数扫描所有 shard；只能展示 catalog 估算、最近采样和有限窗口。

## 索引策略

分片会降低单文件写锁竞争，但每条 INSERT 仍会维护该 shard 内所有索引。第一阶段需要复查 `usage_records` 索引：

必须保留：

- 主键 `id`
- 统计游标索引 `(created_at, id)`
- 默认列表索引 `(system_account_id, created_at, id)`
- 常用筛选索引，例如 `api_key_id + created_at + id`、`group_id + created_at + id`、`account_id + created_at + id`

需要重新评估：

- 多个排序字段组合索引，例如 `first_token_ms`、`duration_ms`、`cost_usd` 的全局和系统账户组合索引。
- 模型维度明细索引是否仍需要直接服务列表，还是改为统计结果库排行和筛选。
- 仅用于低频诊断的索引是否可以按需延后创建或只在归档分析脚本中使用。

原则：热写 shard 上的索引只服务当前明细页和统计 worker。TopN、趋势、摘要和业务报表一律走统计结果库，不能靠给 shard 明细表不断加索引硬扛。

## 当前模型切换

第一阶段推荐停机切换，不做长期双写，也不做复杂历史适配。业务主库必须备份并保护；数据集目录库、usage shard 文件和统计结果库可以按当前模型重建。

1. 停止 Web、DB service、background worker。
2. 备份业务库和 `backend/.env`；如需要留档，可额外备份当前数据集目录库、usage shard 和统计结果库。
3. 创建 usage shard root。
4. 删除或清空统计结果库，让统计从当前 shard 模型重新累计。
5. 可清空数据集目录库中的分片前 `usage_records`，或直接更换为新的数据集目录库；历史明细默认放弃。
6. 启动服务，后续新请求写入 shard，并由 per-shard 统计游标推进统计结果。
7. 验证写入、列表、统计、额度和表监控。

如果未来某个部署需要处理历史用量或审计，只能另做一次性离线修复 / 导出方案；当前计划不为该场景内置运行时适配、双读或双写。

## 当前模型与发布异常恢复

当前模型策略：

- 新 usage 写 shard。
- 分片前 usage 详情和列表默认不保证可查；历史 usage 可以放弃。
- 不保留分片前模型兜底、历史模型重建、历史 usage 拆分或双模型查询入口。
- 统计重建默认读取 shard；统计结果库可删除后重建。
- API 响应结构不变。

发布异常恢复策略：

- 如果分片写入异常，停止服务后恢复到同一数据契约下的已验证构建和配置，并使用已备份的业务库 / `.env`。
- 数据集目录库、usage shard 文件和统计结果库可丢弃或重建；业务库必须保留。
- 如果已经有部分新 usage 写入 shard，恢复时默认可以放弃这段明细和统计，从恢复后的新请求重新累计；不要求离线合并回分片前 `usage_records`。

## 实施顺序

推荐拆成这些阶段：

1. 文档与计划：固定分片边界、运行配置、统计游标和验收标准。
2. 存储抽象：新增 usage shard locator、catalog repository、shard schema 初始化和配置解析。
3. 写入链路：新增 writer pool、per-shard 队列、批量写入和运行态快照。
4. 明细读取：改造详情、列表、最近请求形态学习；分片前 usage 不进入运行时范围。
5. 统计聚合：改造 per-shard 游标、聚合调度、统计延迟指标和基于 shard 的重建脚本。
6. 清理维护：改造 API Key 删除清理、保留期清理、shard seal / archive / delete。
7. 表监控与运维：展示 shard 文件、writer 队列、统计延迟和 dropped / spool 指标。
8. 切换验证：压测、重建演练、页面烟测、发布异常恢复演练。

## 验收标准

- 高并发请求下 usage writer 队列不长期增长，统计延迟可观测且可恢复。
- `usage_records` 写入不再被单个数据集目录库 SQLite 写锁限制。
- 使用记录列表、详情、统计页面、API Key 额度、统一授权额度和 AI 性能监控响应结构不变；分片前 usage 不作为必须可查范围。
- 统计结果库聚合口径与分片前一致，不漏、不重。
- API Key 删除和使用记录清理不在请求链路同步扫 shard。
- 数据保留可以按 shard 文件删除旧数据，不再依赖大表批量 DELETE 作为主要释放空间方式。
- 表监控可以定位具体异常 shard、writer 队列和统计滞后。
- 业务主库有明确保护和发布异常恢复路径；数据集目录库、usage shard 文件和统计结果库有明确删除重建路径。
