# 客户端兼容与模型映射重设计草案

> 状态：一期已按本文规则落地，仍可继续产品复核和迭代。
> 创建时间：2026-06-23。
> 本文用于复盘前序沟通并重新定义最新设计边界；2026-06-23 已完成首轮前后端、网关和回归验证落地。
> 2026-06-24 补充：PLAN-0058 在本文之后新增 OpenAI Chat / Responses 到 Anthropic Messages 的显式桥接设计；该能力不是本文的 OpenAI `responses -> chat_completions` bridge，需参考 [OpenAI 到 Anthropic Messages 协议桥接设计](OpenAI到Anthropic协议桥接设计.md)。

## 1. 背景

当前账户高级设置里把几件不同性质的事情混在一起：

- 客户端兼容：下游客户端或工具如何请求、如何解释错误、如何处理 SSE。
- 上游协议能力：账号真实支持 Chat、Responses、Messages、JSON 或 SSE。
- 模型映射：下游请求模型 A 转成上游模型 B。
- 协议转换：下游协议和上游协议不一致时，网关在中间做桥接。
- 上游返回处理：上游响应回来后如何做 SSE 解析、错误分类、usage 提取、审计、统计、账号恢复和客户端输出兼容。
- 供应商定位：定制供应商和通用 OpenAI 兼容供应商的职责边界。

这些概念混用后，用户会不清楚：

- 我到底应该选 GPT、DeepSeek、GLM，还是 OpenAI 兼容供应商？
- 客户端兼容开关是不是等于协议转换？
- 上游能力应该填真实能力，还是填本地 bridge 后看起来支持的能力？
- 模型映射到底是换模型名，还是换协议，还是换供应商？
- 上游返回到底是原样透传，还是还会经过本地拦截、统计、兼容和错误处理？

这块需要先用产品语义重新定清楚，再考虑落地代码。

## 2. 前序沟通复盘

### 2.1 已经达成的共识

- 客户端兼容不能继续承担所有语义，它只应该服务下游客户端工具体验。
- 上游真实能力必须独立表达，不能因为本地能桥接就伪造上游原生能力。
- 模型映射需要能表达下游模型、上游模型，以及下游 / 上游协议族。
- 当前只考虑 `responses -> chat_completions`，不支持 `chat_completions -> responses`。
- 不做历史兼容分支，正式落地时按当前最优字段和 UI 重整。

### 2.2 之前不清楚的地方

之前曾把规则理解成：

- 只有 `openai` 通用 OpenAI-compatible 供应商支持 `responses -> chat_completions`。
- DeepSeek、GLM、GPT 这些定制供应商不做协议转换。

这个理解现在需要修正。

### 2.3 最新修正

最新设计应按“协议支持”而不是按“是否通用 OpenAI 兼容供应商”来决定协议转换能力：

- 凡是供应商协议档案支持 OpenAI 协议，都可以支持 `responses -> chat_completions`。
- 包括 GPT、DeepSeek、GLM、通用 OpenAI 兼容供应商。
- 通用 OpenAI 兼容供应商的定位不是“唯一桥接供应商”，而是“尚未深度接入供应商的临时通用入口”。
- GPT、DeepSeek、GLM 这类定制供应商的价值是深度集成、参数优化、官网能力适配、模型目录和价格口径更准确。

## 3. 最新推荐模型

一句话规则：

> 客户端兼容只管下游工具体验；上游能力只管真实协议能力；凡是 OpenAI 协议供应商都可以通过模型映射显式启用 `Responses -> Chat`；定制供应商负责深度优化，通用 OpenAI 兼容供应商负责兜底接入未适配厂商。

这套模型最符合当前项目：

- 项目定位是轻量 OpenAI 兼容中转与账号管理，不应该把所有能力塞进一个客户端兼容开关。
- GPT、DeepSeek、GLM 都是已接入供应商，应作为定制供应商做深度适配。
- 国内外其他支持 OpenAI 协议但尚未单独接入的厂商，先用通用 OpenAI 兼容供应商接入，避免用不了。
- `Responses -> Chat` 是 OpenAI 协议族内部的桥接能力，不应该只属于通用 OpenAI 兼容供应商。
- 模型映射挂在当前上游账号 / 当前供应商下。
- 模型映射左侧是客户端请求模型，可以从全局客户端可见模型目录选择，例如 GPT / Codex / DeepSeek / GLM / 通用 OpenAI-compatible / 自定义模型。
- 模型映射右侧是实际发给上游的模型，必须来自当前供应商 / 当前账号真实可用模型列表，这是强制规则。
- 通用 OpenAI 兼容账号是例外：它的左右两侧都可以放宽到 OpenAI 协议模型池，但不能选择 Anthropic / Messages 等非 OpenAI 协议模型。
- “GPT 转发给 DS”在产品语义上应该理解为“DeepSeek 账号允许接收客户端传入的 GPT / Codex 模型名，然后显式映射到 DeepSeek 上游模型”，不是把 GPT 官方账号伪装成 DeepSeek 账号。

客观审查后的关键修正：

- “当前供应商”在账号高级设置里就是当前上游供应商，不是客户端模型来源。
- 右侧上游模型必须固定到当前供应商模型列表，因为它关系到账号测试、账号支持模型、价格、错误处理和真实上游调用。
- 左侧下游模型是客户端传来的 `model`，只作为匹配键；它可以来自全局客户端模型目录，不应该被当前上游供应商限制。
- 如果要支持 `Codex -> DeepSeek`，DeepSeek 账号的模型映射左侧应允许选择 GPT / Codex 模型名，右侧强制选择 DeepSeek 模型。
- 通用 OpenAI 兼容账号用于接入未深度适配的 OpenAI-compatible 上游，所以它的右侧模型列表应放宽到所有支持 OpenAI 协议的供应商模型，以及用户在通用 OpenAI 兼容供应商下创建的自定义模型；最终仍由 Base URL、账号测试和真实请求验证可用性。
- 因此模型映射不需要额外保存 source / target 供应商字段；当前账号就是上游边界。真正需要保存的是 `sourceModel + sourceEndpointFamily -> upstreamModel + upstreamEndpointFamily`。

## 4. 供应商定位

| 供应商类型 | 代表 | 定位 | 是否可支持 `Responses -> Chat` | 关键差异 |
| --- | --- | --- | --- | --- |
| GPT 定制供应商 | `gpt` | OpenAI 官方深度接入 | 可以，只要使用 OpenAI 协议档案并显式配置映射 | 官方 OAuth / API Key、官方参数、Responses 原生能力、Codex 请求策略优化 |
| DeepSeek 定制供应商 | `deepseek` | DeepSeek 深度接入 | 可以，只要使用 OpenAI 协议档案并显式配置映射 | DeepSeek 模型目录、参数、错误语义、价格和测试优化 |
| GLM 定制供应商 | `glm` | 智谱 GLM 深度接入 | 可以，只要使用 OpenAI 协议档案并显式配置映射 | GLM 通用 / Coding / Anthropic 档案、模型目录、参数和测试优化 |
| 通用 OpenAI 兼容供应商 | `openai` | 未接入 OpenAI-compatible 厂商的兜底入口 | 可以，只要使用 OpenAI 协议档案并显式配置映射 | 不做厂商深度优化；左右模型选择放宽到 OpenAI 协议模型池 |
| Anthropic 定制供应商 | `anthropic` | Anthropic / Claude Code / Messages 深度接入 | 不参与 OpenAI `Responses -> Chat`；可按 PLAN-0058 参与 OpenAI -> Anthropic Messages 显式桥接 | 走 Anthropic Messages 协议，不和 OpenAI 协议内部 bridge 混用 |

## 5. 用户应该怎么选供应商

### 5.1 用 OpenAI 官方

选择 GPT 定制供应商。

适合：

- OpenAI API Key。
- OpenAI OAuth。
- 需要官方 Responses 原生能力。
- 需要 Codex Responses 官方链路优化。

可配置：

- Chat 原生透传。
- Responses 原生透传。
- 如果确实要把下游 Responses 请求转到某个 OpenAI Chat 模型，也可以通过模型映射显式配置 `responses -> chat_completions`。

不适合：

- 用 GPT 供应商去接 DeepSeek / GLM Base URL。
- 用 GPT 定制供应商代表其他 OpenAI-compatible 厂商。

### 5.2 用 DeepSeek

选择 DeepSeek 定制供应商。

适合：

- DeepSeek 官方 OpenAI-compatible API。
- DeepSeek 模型目录和价格口径。
- DeepSeek 参数、错误语义和账号测试优化。

可配置：

- Chat 原生透传。
- 下游 Responses 请求通过显式模型映射转到 DeepSeek Chat。
- 左侧下游模型可以选择客户端会发送的 GPT / Codex 模型名，例如 `gpt-5.3-codex`。
- 右侧上游模型必须是当前 DeepSeek 账号实际可用模型，例如 `deepseek-v4-flash`。

如果用户希望客户端继续请求 GPT / Codex 模型名，但实际打到 DeepSeek，就在 DeepSeek 账号的模型映射里配置 `gpt-5.3-codex -> deepseek-v4-flash`，不要把 DeepSeek 账号伪装成 GPT 账号。

### 5.3 用 GLM

选择 GLM 定制供应商。

适合：

- GLM 官方 OpenAI-compatible API。
- GLM Coding Plan。
- GLM Anthropic / Claude Code 兼容档案。
- GLM 模型目录、参数和价格口径。

可配置：

- OpenAI 协议档案下支持 Chat 原生透传。
- OpenAI 协议档案下支持下游 Responses 通过显式模型映射转到 GLM Chat。
- Anthropic / Claude Code 档案不参与 OpenAI `Responses -> Chat`；如果 OpenAI 下游请求需要命中 Anthropic Messages 上游，走 PLAN-0058 定义的 OpenAI -> Anthropic Messages 显式桥接。

### 5.4 用未接入厂商

选择通用 OpenAI 兼容供应商。

适合：

- 国内其他模型厂商。
- 国外其他 OpenAI-compatible 聚合平台。
- 暂时没有单独供应商驱动，但支持 OpenAI Chat Completions 的上游。

可配置：

- Chat 原生透传。
- 下游 Responses 通过显式模型映射转到该上游 Chat。

限制：

- 只做 OpenAI-compatible 通用能力。
- 不保证厂商私有参数、错误码、模型目录、价格、测试流程完全优化。
- 后续如果某厂商使用量变大，可以升级为定制供应商。

## 6. 用户配置示例

### 6.1 Codex Responses 打到 DeepSeek Chat

选择：

- 当前供应商：DeepSeek 定制供应商。
- 当前账号协议档案：DeepSeek OpenAI v1。
- 左侧下游模型：从全局客户端模型目录选择 `gpt-5.3-codex`，不能在映射表里临时手写。
- 右侧上游模型：从当前 DeepSeek 账号可用模型列表选择 `deepseek-v4-flash`。
- Base URL：DeepSeek 官方 OpenAI-compatible URL。
- 上游真实能力：`chat_json`、`chat_sse`。
- 模型映射：

```json
{
  "sourceModel": "gpt-5.3-codex",
  "sourceEndpointFamily": "responses",
  "upstreamModel": "deepseek-v4-flash",
  "upstreamEndpointFamily": "chat_completions",
  "enabled": true
}
```

结果：

- 下游客户端请求 `gpt-5.3-codex` 的 Responses。
- 当前 API Key 必须绑定 DeepSeek 分组，网关只在已授权的 DeepSeek 账号池内选择账号。
- 网关在 DeepSeek 账号上匹配 `gpt-5.3-codex + responses` 模型映射。
- 网关执行 `Responses -> Chat`。
- 上游 DeepSeek 收到 Chat Completions 请求，模型为 `deepseek-v4-flash`。
- 下游收到 Responses 兼容响应。

这里的关键点是：`gpt-5.3-codex` 是客户端传来的模型名，只需要存在于全局客户端可见模型目录；`deepseek-v4-flash` 才是当前 DeepSeek 账号实际发给上游的模型，必须来自 DeepSeek 模型列表。用户可以用 GPT / Codex 模型名服务本地 Codex 客户端，同时把实际请求落到 DS Chat。

### 6.2 Codex Responses 打到 GLM Chat

选择：

- 当前供应商：GLM 定制供应商。
- 当前账号协议档案：GLM OpenAI v1 或 GLM Coding OpenAI v1。
- 左侧下游模型：从全局客户端模型目录选择 `gpt-5.3-codex`，不能在映射表里临时手写。
- 右侧上游模型：从当前 GLM 账号可用模型列表选择 `glm-5.2`。
- 上游真实能力：`chat_json`、`chat_sse`。
- 模型映射：

```json
{
  "sourceModel": "gpt-5.3-codex",
  "sourceEndpointFamily": "responses",
  "upstreamModel": "glm-5.2",
  "upstreamEndpointFamily": "chat_completions",
  "enabled": true
}
```

### 6.3 Codex Responses 打到未接入 OpenAI-compatible 厂商

选择：

- 当前供应商：通用 OpenAI 兼容供应商。
- 左侧下游模型：从 OpenAI 协议模型池选择 Codex / GPT / DeepSeek / GLM / 自定义 OpenAI-compatible 模型名。
- 右侧上游模型：同样从 OpenAI 协议模型池选择，但保存 / 测试时必须证明当前 Base URL 能调用该模型。
- Base URL：该厂商提供的 OpenAI-compatible URL。
- 上游真实能力：`chat_json`、`chat_sse`。
- 模型映射同样配置 `responses -> chat_completions`。

区别：

- 可以快速接入。
- 但没有该厂商专属参数、错误处理、模型目录和价格优化。
- 模型选择只放宽到 OpenAI 协议模型池，不包括 Anthropic / Messages 模型。

### 6.4 普通 Chat 转发

如果下游就是 Chat Completions：

- 不需要协议转换。
- 可以没有模型映射，直接透传。
- 也可以做同协议模型映射，例如 `client-model -> deepseek-v4-flash`，但协议仍是 `chat_completions -> chat_completions`。

### 6.5 左侧全局客户端模型，右侧当前供应商模型

当前账号做模型映射时，左右两侧规则不同：

- 左侧“下游模型”从全局客户端可见模型目录选择，用来匹配客户端传入的 `model`。
- 右侧“上游模型”强制从当前供应商 / 当前账号可用模型列表选择，用来真实发给上游。
- 通用 OpenAI 兼容账号的左右两侧都放宽到 OpenAI 协议模型池，因为它代表未深度接入的 OpenAI-compatible 上游。

允许的产品语义：

- DeepSeek 账号：左侧可选择 `gpt-5.3-codex`，右侧只能选择 DeepSeek 可用模型，例如 `deepseek-v4-flash`。
- GLM 账号：左侧可选择 `gpt-5.3-codex`，右侧只能选择 GLM 可用模型，例如 `glm-5.2`。
- 通用 OpenAI 兼容账号：左侧和右侧都可以从 OpenAI 协议模型池选择；该模型池包含支持 OpenAI 协议的供应商模型，以及用户在通用 OpenAI 兼容供应商下创建的自定义模型。
- GPT 官方账号：左侧可选择其他客户端模型名，右侧只能选择 OpenAI 官方账号真实可用模型。

也就是说，定制供应商不是左右都开放：左侧是客户端匹配模型，右侧才是当前账号真实上游模型。通用 OpenAI 兼容供应商可以更宽，但也只宽到 OpenAI 协议模型池。保存和测试必须围绕“当前账号能否调用右侧模型”校验。

## 7. 高级设置页面应该怎么改

高级设置必须让用户一眼看清“这块配置解决什么问题”。建议拆成五个区域。

### 7.1 上游连接

回答：

> 这个账号实际连到哪里？

字段：

- 供应商。
- 协议档案。
- Base URL。
- API Key / OAuth。
- 代理。

### 7.2 上游真实能力

回答：

> 这个上游真实支持什么协议和传输形态？

字段：

- Chat JSON。
- Chat Streaming。
- Responses JSON。
- Responses Streaming。
- Messages JSON。
- Messages Streaming。
- Count Tokens。

说明：

> 这里只填写上游真实能力。本地协议转换不会改变上游真实能力。

例如 DeepSeek Chat-only 账号即使能通过本地 bridge 承接 Codex Responses，也仍然只勾选 `chat_json`、`chat_sse`。

### 7.3 客户端请求策略

回答：

> 下游工具按哪种客户端体验来请求和解释响应？

字段：

- OpenAI 标准。
- Codex Responses。
- Claude Code。
- Anthropic native。

说明：

> 该配置只影响客户端请求补齐、错误语义和工具体验，不启用模型映射或协议转换。

### 7.4 模型映射与协议转换

回答：

> 下游请求的模型和协议，应该转成哪个上游模型和协议？

表格列：

- 下游模型。
- 下游协议族。
- 上游模型。
- 上游协议族。
- 启用状态。

UI 规则：

- 下游模型列表来自全局客户端可见模型目录，不能在映射表里手写临时别名；确实需要新别名时先维护到模型目录。
- 上游模型列表必须来自当前供应商 / 当前账号可用模型列表，强制校验。
- 通用 OpenAI 兼容账号的下游模型和上游模型列表都使用 OpenAI 协议模型池。
- OpenAI 协议模型池只包含支持 OpenAI 协议的供应商模型，以及用户在通用 OpenAI 兼容供应商下创建的自定义模型；不包含 Anthropic / Messages 等非 OpenAI 协议模型。
- 当前账号协议档案支持 OpenAI 协议时，允许 `responses -> chat_completions`。
- 右侧上游协议选择 `responses` 时必须是原生直连：左侧协议也必须是 `responses`，并且当前账号 `supported_endpoint_modes` 必须包含 `responses_json` 或 `responses_sse`。
- 所有供应商都禁止 `chat_completions -> responses`。
- Anthropic / Messages 协议档案不显示 OpenAI `responses -> chat_completions`。
- 如果当前账号配置了支持模型列表，保存时必须校验上游模型在该账号可用模型内；没有配置时，至少通过账号测试或后续真实请求验证。
- 下游模型不必等同于上游模型归属，它只是客户端请求匹配键。

### 7.5 错误、响应与运维策略

回答：

> 失败后怎么处理？响应怎么检查？账号怎么恢复？

字段：

- 账号错误处理。
- 响应语义检查策略。
- 错误分类与恢复策略。
- usage / 成本解析策略。
- 审计与原始响应保留策略。
- 冷却恢复。
- 账号测试策略。

这块不参与协议转换，也不改变模型映射。它只决定上游返回后如何被诊断、记录、统计和恢复。

## 8. 核心概念重新定义

### 8.1 客户端兼容

客户端兼容只描述“下游客户端如何和本系统交互”。

它可以影响：

- 请求体补齐。
- 请求头补齐。
- SSE 事件语义。
- 错误码和可重试语义。
- 特定客户端工具的稳定性体验。

它不应该影响：

- 上游账号真实支持哪些 endpoint。
- 是否自动启用协议转换。
- 是否把 Chat-only 上游伪装成原生 Responses 上游。

建议将页面文案从“客户端兼容”改成“客户端请求策略”或“客户端工具兼容”，避免用户误以为它是上游协议兼容。

### 8.2 上游协议能力

上游协议能力只描述账号真实支持什么。

OpenAI v1 可表达：

- `chat_json`
- `chat_sse`
- `responses_json`
- `responses_sse`

Anthropic v1 可表达：

- `messages_json`
- `messages_sse`
- `message_token_counting`

本地 bridge 不改变上游真实能力。

### 8.3 模型映射

模型映射描述“客户端请求模型 A 和协议 X，转发为当前账号上游模型 B 和协议 Y”。

模型映射行建议包含：

- 下游模型。
- 下游协议族。
- 上游模型。
- 上游协议族。
- 是否启用。

模型映射不是客户端兼容开关。只有请求模型、请求协议族和启用状态都匹配时才生效。

左侧下游模型是客户端匹配键：

- 可以从全局客户端可见模型目录选择。
- 保存、导入和运行前校验都必须验证 `sourceModel` 是当前账号所有者可见、启用且可请求的模型。
- 如果需要新增对外暴露的模型名，应先进入模型目录维护，再被模型映射引用。
- 不允许在模型映射行直接创建临时别名。

右侧上游模型是强约束：

- 必须来自当前供应商 / 当前账号可用模型列表。
- 通用 OpenAI 兼容账号可以来自 OpenAI 协议模型池，但仍需要当前 Base URL / 账号测试证明可调用。
- 运行时只能在当前 API Key 已授权的当前账号所属分组里选择账号。
- 当前账号必须真实支持 `upstreamEndpointFamily` 和 `upstreamModel`。
- 不能只根据客户端模型名猜上游模型。

### 8.4 协议转换

当前只定义一种 OpenAI 协议族内部转换：

- `responses -> chat_completions`

同协议 `responses -> responses` 不是 bridge，只有当前账号真实接口能力包含 `responses_json` 或 `responses_sse` 时才能配置为上游协议；DeepSeek、GLM Coding、Anthropic Messages 等非原生 Responses 上游不能通过模型映射右侧选择 `responses`。

当前明确不支持：

- `chat_completions -> responses`
- Anthropic Messages 转 OpenAI Chat / Responses

本文原范围不定义 OpenAI Responses 转 Anthropic Messages。2026-06-24 起该方向改由 [OpenAI 到 Anthropic Messages 协议桥接设计](OpenAI到Anthropic协议桥接设计.md) 单独定义，且目标扩展为 Chat JSON、Chat SSE、Responses JSON、Responses SSE 四类入口。

## 9. 规则矩阵

| 场景 | 是否允许 | 说明 |
| --- | --- | --- |
| GPT OpenAI 协议档案 `responses -> chat_completions` | 允许 | 显式模型映射触发，可用于转到 OpenAI Chat 模型 |
| GPT / OpenAI 原生账号 `responses -> responses` | 允许 | 账号真实接口能力必须包含 `responses_json` 或 `responses_sse`，这是原生转发，不是协议桥接 |
| DeepSeek OpenAI 协议档案 `responses -> chat_completions` | 允许 | 定制供应商深度集成 DeepSeek，bridge 仍按 OpenAI 协议族处理 |
| GLM OpenAI 协议档案 `responses -> chat_completions` | 允许 | 仅限 GLM OpenAI 协议档案，不含 Anthropic / Claude Code 档案 |
| 通用 OpenAI 兼容供应商 `responses -> chat_completions` | 允许 | 用于未接入厂商的 OpenAI-compatible 临时接入 |
| 下游 GPT / Codex 模型名映射到 DeepSeek / GLM 上游模型 | 允许 | 配置在 DeepSeek / GLM 当前账号下，左侧选择 GPT / Codex 客户端模型名，右侧选择当前账号真实可用模型 |
| 通用 OpenAI 兼容账号左右模型选择 OpenAI 协议模型池 | 允许 | 仅限支持 OpenAI 协议的供应商模型，以及用户在通用 OpenAI 兼容供应商下创建的自定义模型 |
| 下游模型不在全局客户端模型目录 | 禁止 | `sourceModel` 不能在映射行临时创建，必须先进入模型目录 |
| 上游模型不在当前供应商 / 当前账号可用模型列表 | 禁止 | `upstreamModel` 是真实上游调用模型，必须强校验 |
| 通用 OpenAI 兼容账号选择 Anthropic / Messages 模型 | 禁止 | 通用 OpenAI 兼容账号只处理 OpenAI 协议模型池 |
| API Key 未绑定当前账号所在分组但请求命中该账号映射 | 禁止 | 映射不能扩大授权范围，只能在已授权分组内生效 |
| 只按模型目录供应商路由，忽略账号映射 | 禁止 | Codex 的 GPT 模型名会被固定路由到 GPT，DeepSeek 账号无法承接 |
| 模型映射左侧展示全局客户端模型目录 | 允许 | 左侧只是客户端请求匹配键，不代表当前上游供应商 |
| OpenAI Chat / Responses 转 Anthropic Messages | 允许 | 必须按 PLAN-0058 显式桥接，目标账号真实 endpoint family 仍是 `messages` |
| Chat-only 或 Messages 上游选择 `responses` | 禁止 | 右侧 Responses 只代表上游原生 Responses，不代表本地桥接输出形态 |
| 任意供应商 `chat_completions -> responses` | 禁止 | 当前不支持 |
| Anthropic Messages 转 OpenAI Chat / Responses | 禁止 | 协议族不同，不在本轮设计 |
| 通过客户端请求策略启用 bridge | 禁止 | 必须通过模型映射显式声明 |
| Chat-only 上游勾选 Responses 上游真实能力 | 禁止 | 上游能力必须真实 |

- `当前协议档案不支持 OpenAI Responses 转 Chat Completions`
- `暂不支持 Chat Completions 转 Responses`
- `客户端请求策略不负责协议转换，请在模型映射中配置协议转换`
- `下游模型必须先维护到全局客户端模型目录`
- `上游模型必须从当前供应商模型列表选择`
- `通用 OpenAI 兼容账号只能选择 OpenAI 协议模型池中的模型`
- `当前 API Key 未绑定可承接该映射的账号分组`
- `上游真实能力必须与账号实际支持的接口一致`
- `上游模型必须是当前账号真实可调用的模型`

## 10. 网关运行规则

### 10.1 请求进入

网关先识别：

- 请求 endpoint family：Chat Completions、Responses、Messages。
- 请求模型。
- 请求客户端画像。

这三者分开记录，不互相推导。

### 10.2 候选账号筛选

筛选顺序建议：

1. API Key 找到绑定分组。
2. 识别请求 endpoint family、请求模型和客户端画像。
3. 校验请求模型存在于全局客户端可见模型目录；如果不存在，返回模型不可用或模型未维护。
4. 在 API Key 已绑定分组内枚举可用账号，不能跳出授权分组。
5. 对每个账号先查是否存在 `sourceModel + sourceEndpointFamily` 的启用映射。
6. 有映射时，校验该账号协议档案、上游真实能力和右侧 `upstreamModel` 是否可用；可用则该账号进入候选。
7. 无映射时，按普通透传规则校验请求模型是否可被该账号直接承接。
8. 完成会话亲和、IP 回避、本地屏蔽、授权额度和账号排序。
9. 选中账号后应用映射：同协议族只改写模型；`responses -> chat_completions` 进入 bridge。
10. 有 `responses -> chat_completions` 映射时，要求当前账号协议档案支持 OpenAI 协议，且上游真实能力包含 Chat Streaming。

这个顺序是客观必要条件：不能只按客户端模型所属供应商路由。Codex 请求 GPT 模型名时，DeepSeek 分组里的账号必须能通过账号映射成为候选，否则就无法实现 Codex 访问 DeepSeek。

### 10.3 上游请求构造

如果无协议转换：

- 尽量保持 raw passthrough。
- 只做必要的认证头、代理、审计和模型名改写。

如果是 `responses -> chat_completions`：

- 把 Responses input 转为 Chat messages。
- 把 Responses stream 语义映射为 Chat SSE 请求。
- 把 Chat SSE 上游响应转回 Responses SSE。
- 只支持桥接能力清单中明确覆盖的 Responses 字段，不承诺完整等同原生 Responses。

### 10.4 上游响应返回

如果无协议转换：

- 下游可见响应尽量保持上游原样返回。
- 原样返回不代表跳过本地响应管线；审计、usage 提取、错误分类、账号状态、SSE 保活和统计事件仍然要走通用处理。
- 网关只做必要的安全 / 协议守卫，例如头部清理、连接中断诊断、非法 JSON / 非法 SSE 的受控错误，不做业务字段重写。

如果有 bridge：

- Chat 响应必须转回 Responses 兼容事件。
- bridge 产生的本地错误必须明确标记为协议转换错误，不能伪装成上游原生 Responses 错误。

### 10.5 上游返回处理管线

上游返回必须进入统一响应管线，不能散落在各供应商 driver 里各写一套。

建议顺序：

1. 传输接收：记录 HTTP 状态、响应头、首包耗时、总耗时、连接中断和超时。
2. 通用协议守卫：按 JSON / SSE / stream 类型做有界解析、空响应检查、SSE comment / keep-alive 处理、`[DONE]` 识别和背压控制。
3. 供应商语义解析：由供应商适配器提取错误类型、限流 / 余额 / 权限语义、`finish_reason`、usage 扩展字段和供应商私有字段。
4. 协议转换输出：只有显式 bridge 时才把上游协议事件转为下游协议事件，例如 Chat SSE 转 Responses SSE。
5. 客户端输出适配：按客户端请求策略调整下游可见错误格式、SSE 事件名、终止事件和必要 header。
6. 副作用投递：写使用记录、原始审计引用、运行日志、账号命中、错误分类和统计增量事件。

这条管线里只有第 4 步会改变协议族。第 5 步只做客户端体验适配，不能把 Chat-only 上游包装成原生 Responses 能力。

### 10.6 响应拦截能力边界

可以通用化的拦截能力：

- HTTP 状态和响应头采集。
- JSON / SSE 结构守卫。
- SSE comment / keep-alive 忽略。
- 流式首包、空闲、总耗时诊断。
- usage 提取接口。
- 错误分类接口。
- 账号错误策略、冷却、半开恢复和复测触发。
- 原始审计截断、脱敏、blob 引用和保留期。
- 使用记录 append-only 写入和后台统计事件投递。
- 响应语义检查，例如空输出、异常 `finish_reason`、缺失终止事件。

供应商只补差异：

- DeepSeek 的 `reasoning_content`、cache hit / miss usage、`insufficient_system_resource` 和 keep-alive 细节。
- GLM 的厂商私有错误码、模型族参数和特殊 usage 字段。
- GPT 官方 Responses / Chat 原生字段、官方错误码和 headers。
- 通用 OpenAI 兼容供应商只按 OpenAI-compatible 基础语义解析，不承诺识别所有厂商私有字段。

### 10.7 透传、守卫和兼容的关系

需要把三个词分开：

- 透传：成功响应的下游可见 body / event 尽量不改写。
- 守卫：发现上游返回不符合当前协议时，转成受控网关错误，避免客户端收到半截坏结构或服务端崩溃。
- 兼容：按客户端请求策略微调错误形态、SSE 终止事件和必要 header，让特定客户端更稳定。

因此“上游返回什么，下游就收到什么”只适用于可见业务内容，不适用于本地观测、副作用和协议守卫。

## 11. 分层与通用能力复用

为了避免 GPT、DeepSeek、GLM、通用 OpenAI 兼容供应商重复实现，应按层拆分。

### 11.1 网关核心层

负责所有供应商共享能力：

- API Key 鉴权、分组、账号调度。
- 模型映射匹配。
- 代理、超时、取消、背压。
- 审计、运行日志、使用记录事件投递。
- 账号错误策略、冷却、恢复和复测状态机。
- 统一响应管线编排。

网关核心层不写死某个供应商模型、错误码或私有字段。

### 11.2 账号候选与模型映射层

负责在授权账号池内判断哪些账号能承接当前请求：

- 根据 API Key 绑定分组得到候选账号池。
- 校验请求 `sourceModel` 属于全局客户端可见模型目录。
- 对每个账号匹配 `sourceModel + sourceEndpointFamily` 模型映射。
- 有映射时，校验 `upstreamModel` 属于当前账号供应商模型列表和账号支持模型。
- 无映射时，按普通透传规则校验当前账号是否能直接承接请求模型和协议。
- 输出网关核心层可以调度的账号候选集。

这一层必须在账号选择之前运行，但不需要额外保存 source / target 供应商字段：当前账号就是上游边界。这样 DeepSeek 账号可以凭 `gpt-5.3-codex -> deepseek-v4-flash` 映射承接 Codex 请求。

### 11.3 协议适配层

负责协议族的通用语义：

- OpenAI Chat Completions 请求 / 响应 / SSE 解析。
- OpenAI Responses 请求 / 响应 / SSE 解析。
- Anthropic Messages 请求 / 响应 / SSE 解析。
- `responses -> chat_completions` bridge。

协议适配层可以被 GPT、DeepSeek、GLM、通用 OpenAI 兼容供应商共享。

### 11.4 供应商适配层

负责定制供应商差异：

- 默认 Base URL。
- 协议档案。
- 模型目录、价格、上下文和能力标签。
- 参数白名单、别名和厂商扩展字段。
- 错误码、错误文案和恢复建议。
- usage 扩展字段和成本拆分。
- 账号测试和模型检测策略。

通用 OpenAI 兼容供应商的供应商适配层应保持薄，只声明基础 OpenAI-compatible 能力；GLM、DS、GPT 定制供应商可以做深度优化。

### 11.5 客户端请求策略层

负责下游客户端体验：

- Codex Responses 请求补齐、SSE 事件期待和错误形态。
- OpenAI 标准 SDK 的默认行为。
- Claude Code / Anthropic native 的客户端侧差异。

这一层不能决定上游真实能力，不能隐式启用协议转换，也不能绕过模型映射规则。

### 11.6 响应语义插件

建议把响应语义检查做成可组合插件，而不是写进单个供应商 driver：

- `usageExtractor`：提取 token、cache、reasoning 等统计字段。
- `errorClassifier`：把 HTTP / JSON / SSE 错误归类成认证、限流、余额、模型不可用、上游协议错误等。
- `semanticGuard`：判断空输出、异常结束、缺失 usage、缺失 done、异常 `finish_reason`。
- `auditProjector`：决定哪些字段进入摘要、哪些只进原始审计引用。
- `clientOutputAdapter`：按客户端策略输出可见错误和 SSE 终止形态。

供应商定制只注册插件和规则，通用管线负责调用顺序和副作用投递。

### 11.7 运行时副作用边界

响应管线产生的副作用不能直接在请求热路径里做重统计：

- 使用记录只追加明细或投递 append-only 事件。
- 统计、额度、趋势、TopN 和账号质量由后台 worker 按游标增量聚合。
- 原始审计 payload 只按现有容量、截断、脱敏和保留期策略保存引用。
- 路由和 repository 不能为了响应兼容实时扫描明细表或缓存桶汇总。

## 12. 模型目录与模型选择

建议把模型选择分成两个视图：

- 下游模型视图：全局客户端可见模型目录，表示客户端可能传入的模型名。
- 上游模型视图：当前供应商 / 当前账号实际可发给上游的模型名。

下游模型池：

- 模型映射左侧可以从全局客户端可见模型目录选择。
- 全局客户端模型目录包含 GPT、DeepSeek、GLM、通用 OpenAI-compatible 和用户自定义模型。
- UI 必须显示模型来源，例如 `GPT`、`DeepSeek`、`GLM`、`自定义`，避免用户误以为左侧模型一定属于当前上游账号。

定制供应商：

- 上游模型只能来自当前供应商模型目录和当前账号支持模型。
- 可附带厂商参数、价格、上下文、工具能力等深度信息。
- 不允许在右侧选择其他供应商模型名，除非该模型已经作为当前供应商账号的自定义上游模型维护。

通用 OpenAI 兼容供应商：

- 左侧和右侧模型都来自 OpenAI 协议模型池。
- OpenAI 协议模型池包含 GPT、DeepSeek、GLM、通用 OpenAI-compatible 等支持 OpenAI 协议的供应商模型。
- OpenAI 协议模型池还包含用户在通用 OpenAI 兼容供应商下创建的自定义模型。
- OpenAI 协议模型池不包含 Anthropic / Messages、Claude Code native 或其他非 OpenAI 协议模型。
- 可以快速接入未适配厂商。
- 不保证深度参数和价格完整。
- 右侧模型虽然可以从 OpenAI 协议模型池选择，但当前 Base URL 是否真实支持仍必须通过保存校验、账号测试或真实请求验证。

下游模型：

- 必须来自全局客户端可见模型目录。
- 可以是为了兼容客户端工具而暴露的模型名，但这个模型名必须先被维护到模型目录。
- 自定义模型名也必须先归入模型目录，不能只存在于映射表。
- 不必表示真实上游供应商归属。
- 典型场景是下游暴露 `gpt-5.3-codex`，右侧实际映射到 `deepseek-v4-flash` 或 `glm-5.2`。

上游模型：

- 必须来自当前供应商 / 当前账号可用模型列表。
- 通用 OpenAI 兼容账号例外：可以来自 OpenAI 协议模型池，但不能超出该池。
- 是真实发给上游的 `model`。
- 决定账号测试、错误处理、价格和 usage 成本口径。

## 13. 导入导出协议建议

导入导出时应保持同样语义：

- 客户端请求策略只表示下游工具体验。
- `supportedEndpointModes` 只表示上游真实能力。
- `modelMappings` 显式表达模型和协议族映射。
- `modelMappings.sourceModel` 必须属于全局客户端可见模型目录，导入时不满足应直接报错。
- `modelMappings.upstreamModel` 必须属于当前供应商 / 当前账号可用模型列表，导入时不满足应直接报错。
- 通用 OpenAI 兼容账号导入时，`sourceModel` 和 `upstreamModel` 必须属于 OpenAI 协议模型池。
- `responses -> chat_completions` 是否允许，由当前账号协议档案是否支持 OpenAI 协议决定。
- 导入后的模型映射不能扩大 API Key 授权范围，只能在该账号所属分组被授权时生效。
- 导入时发现 Anthropic / Messages 档案配置 OpenAI `responses -> chat_completions`，应直接报错。

## 14. 不做的事情

本轮设计不做：

- 不做历史字段兼容分支。
- 不做 Chat 转 Responses。
- 本文不做 Anthropic Messages 和 OpenAI Responses 的互转；OpenAI Chat / Responses 到 Anthropic Messages 的单向显式桥接由 PLAN-0058 负责，Anthropic Messages 到 OpenAI Chat / Responses 的反向转换仍不做。
- 不让客户端兼容开关隐式启用协议转换。
- 不在没有模型映射的情况下自动把 Responses 请求转成 Chat。
- 不把通用 OpenAI 兼容供应商做成所有厂商深度优化入口。
- 不把供应商私有返回处理复制到每个网关分支里；应通过统一响应管线和插件扩展。
- 不在映射行里保存 source / target 供应商；当前账号就是上游边界。
- 不允许 API Key 未授权当前账号分组时通过映射访问该账号。

## 15. 建议落地顺序

### 15.1 先确认产品语义

- 是否将页面文案从“客户端兼容”改成“客户端请求策略”。
- 是否确认“协议转换按协议档案支持判断，不按供应商 code 判断”。
- 是否确认“通用 OpenAI 兼容供应商是未接入厂商兜底入口，不是唯一 bridge 容器”。
- 是否确认“透传只表示下游可见响应不改写，不表示跳过本地响应管线”。
- 是否确认“模型映射属于当前上游账号配置，右侧上游模型强制当前供应商模型列表”。
- 是否确认“通用 OpenAI 兼容账号左右两侧都放宽到 OpenAI 协议模型池”。

### 15.2 再确认数据契约

- 账户如何保存客户端请求策略。
- 账户如何保存上游真实 endpoint modes。
- 模型映射如何保存 `sourceModel`、`sourceEndpointFamily`、`upstreamModel`、`upstreamEndpointFamily`。
- `sourceModel` 如何引用全局客户端可见模型目录。
- `upstreamModel` 如何强制引用当前供应商 / 当前账号可用模型列表。
- 通用 OpenAI 兼容账号如何计算 OpenAI 协议模型池。
- API Key / 分组授权如何约束模型映射只在已授权账号池内生效。
- 协议档案如何声明是否支持 `responses -> chat_completions` bridge。
- 响应语义插件如何声明 usage、错误分类、审计摘要和客户端输出适配。
- 现有《自定义模型与模型映射设计》里的模型路由说明需要同步：账号级模型映射可以承接客户端传入的其他供应商模型名，但右侧上游模型必须是当前账号供应商模型。

### 15.3 调整前端高级设置

- 按五块重新分区。
- 在模型映射里显示下游协议族和上游协议族。
- 下游模型选择器读取全局客户端可见模型目录。
- 上游模型选择器只读取当前供应商 / 当前账号可用模型列表。
- 根据协议档案禁用不支持的转换。
- 把错误提示写成用户能理解的配置原因。
- 在高级设置说明里区分“上游真实能力”“客户端请求策略”“响应语义检查”。

### 15.4 调整后端校验

- 保存账号时校验 endpoint modes。
- 保存模型映射时校验 `sourceModel` 属于全局客户端可见模型目录。
- 保存模型映射时校验 `upstreamModel` 属于当前供应商 / 当前账号可用模型列表。
- 通用 OpenAI 兼容账号保存模型映射时校验左右两侧都属于 OpenAI 协议模型池。
- 保存模型映射时校验当前账号协议档案能力。
- 导入时复用同一套校验。
- 不写旧结构兼容分支。

### 15.5 调整网关

- 候选筛选识别请求 endpoint family。
- 在 API Key 已授权账号池内按 `sourceModel + sourceEndpointFamily` 匹配账号映射。
- 命中映射后校验当前账号可调用 `upstreamModel`，再进入账号排序。
- 只有当前账号协议档案支持 OpenAI 协议且映射为 `responses -> chat_completions` 时进入 bridge。
- 其他情况保持下游可见响应透传，但仍经过统一响应管线。
- 建立通用响应管线，统一处理传输守卫、usage 提取、错误分类、审计、统计事件和客户端输出适配。
- 将 DeepSeek / GLM / GPT 私有返回语义收敛为供应商插件，不复制网关主流程。

### 15.6 验证

必须覆盖：

- GPT 官方 Chat 透传。
- GPT 官方 Responses 透传。
- GPT 官方 `responses -> chat_completions` 映射。
- DeepSeek 定制供应商 `responses -> chat_completions` 映射。
- GLM OpenAI 档案 `responses -> chat_completions` 映射。
- 通用 OpenAI 兼容供应商 `responses -> chat_completions` 映射。
- Anthropic / Messages 档案配置 OpenAI bridge 报错。
- `chat_completions -> responses` 全局报错。
- 客户端请求策略不会单独启用协议转换。
- DeepSeek 账号映射 `gpt-5.3-codex -> deepseek-v4-flash` 时，如果 API Key 未绑定 DeepSeek 分组必须报错。
- Codex 请求 GPT 模型名时，DeepSeek 账号可以凭账号映射进入候选。
- 通用 OpenAI 兼容账号左右两侧可选 OpenAI 协议模型池，但选择 Anthropic / Messages 模型必须报错。
- 非 bridge 透传请求仍记录 usage、审计、错误分类和账号命中。
- 上游非法 JSON / 非法 SSE 被转成受控 `upstream_protocol_error`。
- DeepSeek keep-alive、cache usage、reasoning 和异常 `finish_reason` 只作为供应商插件处理。

## 16. 当前推荐结论

推荐采用以下最终边界：

- 客户端兼容只处理下游客户端工具体验，不承担上游协议转换。
- 上游协议能力只表示账号真实能力，不因 bridge 伪造。
- 模型映射负责模型名映射，并显式携带下游 / 上游协议族。
- 模型映射左侧下游模型来自全局客户端可见模型目录，用于匹配客户端传入的 `model`。
- 模型映射右侧上游模型必须来自当前供应商 / 当前账号可用模型列表，这是强制边界。
- 通用 OpenAI 兼容账号是模型选择例外：左右两侧都放宽到 OpenAI 协议模型池，但不能超出该池。
- OpenAI 协议模型映射可以让 DeepSeek / GLM / 通用 OpenAI 兼容账号接收 GPT / Codex 客户端模型名，但真实上游模型必须由当前账号能力兜底校验。
- `responses -> chat_completions` 是 OpenAI 协议供应商的通用 bridge 能力，GPT、DeepSeek、GLM、通用 OpenAI 兼容供应商都可以支持。
- 上游返回必须进入统一响应管线；透传只是不改下游可见业务内容，不代表跳过拦截、统计、审计、错误处理和客户端输出兼容。
- 使用记录必须同时保存客户端请求模型、实际上游模型、计价模型、当前账号协议档案和是否命中映射；成本按实际上游模型或其计价模型计算。
- 通用能力放在网关核心层和协议适配层，供应商只注册模型、参数、错误、usage 和响应语义差异。
- 通用 OpenAI 兼容供应商用于接入尚未定制的 OpenAI-compatible 厂商。
- GPT、DeepSeek、GLM 作为定制供应商，应提供更深的官网参数、能力、模型目录、价格和测试优化。

这个方案比“只有 OpenAI 兼容供应商能转换”更符合项目长期演进：既能让定制供应商做深度体验，也能让未接入厂商先通过通用 OpenAI-compatible 入口可用，同时不会再让客户端兼容开关承担模糊职责。
