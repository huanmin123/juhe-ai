# 上游额度不足继承错误策略设计

> 状态：已实施（2026-08-24，Node API Key/OAuth quota recovery policy）。本文件同时记录设计结论与当前 Node/Vue 实现事实；未修改数据库、生产环境或 `backend-go`。

## 当前评审结论

1. 当前账户错误处理规则只从 `account.credentials.error_handling_rules` 读取，运行时落点为 `backend/src/modules/gateway/policy/account-error-policy.service.ts:228-275`。现有合法动作只有 `retry_next`、`temp_unschedulable`、`rate_limited`、`error_disabled`。
2. 额度不足应作为系统内置规则继承到账户错误策略页面，而不是复制进每个账户的 `credentials`，也不应增加全局策略页面或“查看全局规则”入口。
3. 系统规则与账户自定义规则在同一列表中使用相同卡片样式，系统规则只增加“继承” Tag；系统规则不可修改、删除、启停或排序。
4. 系统额度保护规则在同一请求上先于账户自定义规则。账户通用规则不能作为低优先级兜底绕过额度保护；例外授权另立需求，本期不做。
5. 当前系统额度规则复用 `rate_limited`。支持该语义的 API Key 供应商若提供 `reset_at` / `Retry-After` / reset header，则严格遵守该显式时间；没有可靠信号时按默认 60 分钟，并由账户/Key recovery seed 在恢复间隔的全局窗口内稳定派生正向错峰。OAuth / Google OAuth 不消费 API Key 的 reset 字段，默认按 UTC 每日 00:00，并可通过独立的 `quota_recovery_policy` 配置 duration/daily/weekly 模式和时间。供应商显式 reset 的优先级只适用于支持该语义的 API Key 路径。多 Key API Key 只写失败 fingerprint；通用额度连续确认 30 天后该 Key 进入 `error`，只允许人工重新验证恢复；明确 reset 的 API Key 不进入 30 天终局。

## 目标

- 在账户错误策略页面可观察系统默认的“上游额度不足”规则，并明确它来自系统继承。
- 使用稳定的额度语义匹配保护账户，避免把普通权限、内容策略或任意 `403` 误判为余额不足。
- 将系统规则、账户规则、优先级、动作、状态恢复和健康探测竞态落实为可测试的契约。
- 保持现有账户策略接口、现有动作和账户凭据脱敏边界；通过有效展示 DTO 与写入拒绝保护实现。

## 非目标

- 不修改数据库、依赖、`system_settings`、生产环境或 `backend-go`。
- 不建立全局规则管理页面、全局规则查询入口、全局策略 API 或数据库表。
- 不把系统规则复制到每个账户，不把源 `credentials` 返回给授权实例。
- 不把任意 `403`、泛化 `quota`、权限限制、内容安全拦截或新错误类型归为余额不足。
- 不在未确定状态机契约前新增或声称已实现 `quota_blocked`。
- 不用小请求或人工测试证明真实大上下文额度恢复。

## 已核验的当前实现事实

- `account-error-policy.service.ts` 先匹配系统额度规则，再匹配账户自己的 `credentials.error_handling_rules`；动作集合仍为 `retry_next`、`temp_unschedulable`、`rate_limited`、`error_disabled`。
- `AccountErrorPolicyCard.vue` 将系统继承规则与本地 `rules` 同列表展示；本地数组仍是唯一可保存数据源。
- `account-error-policy-validation.ts` 明确拒绝写入带 `source: 'system'`、`inherited: true` 或 `editable: false` 的规则，系统规则不得进入 `credentials.error_handling_rules`。
- `account-advanced-detail.repository.ts` 返回顶层 `effectiveErrorHandlingRules` 与非敏感 `effectiveQuotaRecoveryPolicy`；授权实例不返回源 `credentials`。
- 响应检查策略已有 `defaultRule`、`editable`、`source` 这类展示模式，可作为 DTO 形状参考，但不能直接复用其运行时匹配逻辑。
- 普通完整非 2xx 仍会触发 `request_failure` 健康检查；系统额度规则命中会跳过该低上下文探针，避免其与明确 `rate_limited` 状态竞争。
- 多 Key API Key 的系统额度命中在网关层直接写入当前 Key 运行态，并允许当前请求切换兄弟 Key；不会把账户整体写成 `rate_limited`。
- API Key 运行态的 `error` 不再进入自动复测候选；账户菜单中的“重新验证 Key 池”会把它们置为 `unverified` 并重置通用 30 天观察窗口。

## 后端静态规则 registry

后端以进程内静态 registry 维护系统规则 `system.upstream_insufficient_quota`。registry 只包含规则 ID、展示文案、固定顺序、匹配条件、动作和来源元数据：

- 不写入 `system_settings`。
- 不建数据库表，不增加数据库字段。
- 不复制到 `credentials`，不参与账户规则保存。
- 不提供全局管理 API；通过账户现有错误策略读取接口组装有效展示 DTO。
- registry 的规则顺序是代码固定顺序，不能由账户用户排序。

系统规则首批匹配证据码为：

`insufficient_user_quota`、`insufficient_balance`、`insufficient_quota`、`quota_exceeded`、`quota_exhausted`、`WALLET_BALANCE_EXHAUSTED`、`pre_consume_token_quota_failed`。

实现已对错误码做 lowercase、空白及连字符规范化后比较；原始错误继续在既有脱敏诊断链路中保留。

## 账户规则与系统规则分层

有效规则由两层组成：

1. 系统层：由静态 registry 生成，`source: 'system'`、`inherited: true`、`editable: false`，固定启用、固定顺序、固定动作。
2. 账户层：来自 `credentials.error_handling_rules`，`source: 'account'`、`inherited: false`、`editable: true`（再受页面权限和账户只读态约束），继续使用现有 `priority`。

系统层不是账户层的低优先级兜底。对同一请求先执行系统额度保护匹配；只有系统规则未命中时，才按现有账户规则 `priority` 处理。账户规则不能覆盖、禁用、删除或重新排序系统规则。未来如需管理员授权例外，必须另立授权契约和计划。

## 匹配语义

额度不足系统规则必须同时满足：

- HTTP 状态为 `403`；并且
- 命中稳定错误码，或命中高置信度的余额/额度文本；
- `billing_error` 只有在同时出现余额不足关键词时才命中，单独出现 `billing_error` 不足以判定。

推荐的高置信文本需要表达余额耗尽、用户额度不足、预扣 token 额度失败或钱包余额耗尽等明确语义；应先做大小写无关的规范化，并保留供应商原始字段的脱敏诊断。

以下情况必须排除：

- 裸 `403`，无稳定错误码且无高置信额度语义。
- 仅有泛化 `quota`，无法确认是余额、用户额度或预扣额度不足。
- `client_restricted`。
- `new_api_error` 只是 NewAPI 的通用错误包装 `type`，不是否决证据；同一 `403` 仍须同时具有稳定额度 `code` 或高置信余额文本才命中。
- `content_policy_violation`、`prompt_guard_blocked` 或其他权限/内容策略拒绝。
- 仅有认证、权限、地域、组织或模型访问限制的 `403`。

证据不足时保留原始错误和 `request_failure` 诊断，不触发额度规则；未知不得静默降级成余额不足。

## 优先级与冲突

- 系统规则先判定，命中后直接使用系统规则动作，不再让账户通用规则改写本次额度语义。
- 多条系统规则内部按 registry 固定顺序，稳定错误码优先于文本兜底；同一证据只产生一次系统动作。
- 系统未命中时，账户规则仍按现有 `priority` 和既有冲突处理。
- 同一账户多个来源实例都必须使用相同系统 registry，不以账户保存数组中是否存在系统规则决定保护是否生效。
- 对支持 reset 提示的 API Key，已校验的供应商显式 reset 是该账户/Key 的硬恢复边界；OAuth / Google OAuth 忽略 API Key reset 字段，按有效账户策略计算恢复时间。

## 动作与现有状态复用

第一期只复用现有动作：

| 场景 | 推荐动作 | 选择条件 | 恢复边界 |
| --- | --- | --- | --- |
| 官方 OAuth 余额/额度耗尽 | `rate_limited` | 证据明确；默认 OAuth UTC daily，账户可在受限策略内调整 | 写入账户 `rate_limited`，按账户有效策略复测 |
| API Key 有明确恢复时间 | `rate_limited` | 证据明确且供应商给出 `reset_at`、`Retry-After` 或 reset header | 写入当前 Key `rate_limited`，严格使用该时间；不进入 30 天 `error` |
| API Key 无明确恢复时间 | `rate_limited` | 证据明确但没有可靠恢复信号 | 当前 Key 默认 60 分钟，并由账户/Key recovery seed 在全局窗口内稳定错峰复测；连续确认 30 天后 Key 进入 `error`，人工恢复 |
| 产品明确要求短期避让 | `temp_unschedulable` | 已有明确 TTL、CAS、重试和恢复契约，且能证明不会被中性探测覆盖 | 仅按既有临时不可调度状态机恢复 |

`retry_next` 只表示请求级换号，不足以保护后续调度。新增 `quota_blocked` 只有在另一个计划中完成状态持久化、恢复、展示、迁移和并发契约后才可讨论。

## 请求失败健康探测竞态

当前完整非 2xx 会触发 `request_failure` 健康检查。未来额度规则写入状态时必须携带来源、规则版本和账户/凭据代次，避免以下迟到结果覆盖：

- 请求失败已确认余额不足后，后来的小探测成功不能在对应 `cooldown_until` 到期前清理 `rate_limited`；Key `error` 更不能被自动成功清理。
- 探测返回 `403 neutral` 或权限拒绝时，不能当作额度恢复，也不能把额度保护改写成普通可用。
- 普通成功请求、人工测试成功、后台最小探针成功都不能在没有匹配来源且未到 `cooldown_until` 时清除额度限流；30 天 `error` 只能由人工“重新验证 Key 池”打开探测入口。
- 健康探测失败或队列重试只能保留诊断，不得把未确认的 `403` 直接升级为额度状态。
- 状态写回必须使用现有 CAS、generation 或等价代次门禁，旧请求不得覆盖用户手动恢复或新配置。

人工/后台探测是小请求，不能证明真实大上下文额度；实现必须显式区分“协议/连接可达”和“额度可用”。

## 恢复边界

系统额度命中写入 `rate_limited`，`cooldown_until` 是实际下一次复测/恢复边界，不是展示用的估算时间。API Key 运行态候选扫描仍可高频发现到期项；无 reset 信号时默认间隔为 60 分钟，错峰由账户/Key canonical seed 在恢复间隔的全局窗口内稳定派生。同一恢复周期的重复观察不会重算 deadline，gateway 与 worker 使用同一 seed 得到同一结果。明确 reset 时严格使用供应商时间，不被策略提前。OAuth 不走这套 Key 30 天终局，而继续使用每日策略。

单 Key API Key 和 OAuth 落到账户级 `rate_limited` 时，系统额度写回使用独立 provenance：未来的 `system_quota_explicit_reset`（并兼容旧显式 provenance）不能被迟到的 `system_quota_generic_cooldown` 覆盖；显式写入仍可替换通用冷却。多 Key 隔离池继续使用 Key runtime 自身的状态、claim 和配置版本 CAS。

## 额度恢复策略配置

`credentials.quota_recovery_policy` 是独立的非敏感配置对象，不属于 `error_handling_rules`，也不复制静态 system rule。对象按账户类型分为 `api_key`、`oauth`、`google_oauth` 三个可选项，每项支持：

- `reset_strategy: duration | daily | weekly`；
- `duration_minutes`（30–10080 分钟）；
- `daily_reset_hour` 或 `weekly_reset_day` + `weekly_reset_hour`；
- IANA `timezone`（默认 `UTC`）；
- `jitter_minutes` 固定为 15，仅保留为兼容字段；运行时错峰由 recovery seed 在恢复间隔的全局窗口内稳定派生，账户不能关闭或修改。

前端在“额度不足恢复策略”卡片中显示当前账户类型的有效策略；OAuth 的每日策略明确展示并可改为其他受限模式。新建或克隆账户未编辑该卡片时不持久化 `quota_recovery_policy`，运行时继续使用默认策略；用户编辑后才写入。保存时服务端再次校验范围。对支持该语义的 API Key，供应商返回的显式 reset 是最高优先级，不能被账户配置缩短；OAuth / Google OAuth 不把 API Key reset 字段当作恢复提示。系统规则仍优先于账户 `error_handling_rules`。授权实例只读显示有效策略，不暴露源凭据。

若未来调整 `temp_unschedulable`，必须先固定 TTL、最大重试、半开并发、恢复成功证据和迟到写回条件；任何一个契约未定，都不能扩大系统额度规则范围。

## 权限和授权实例

- 账户自有实例继续遵守现有高级凭据脱敏和权限校验。
- `account-advanced-detail.repository.ts` 不得为展示系统规则而暴露源 `credentials`。
- 授权实例展示相同的无敏感系统规则；不合并或返回源账户自定义规则。
- 授权实例只返回规则展示 DTO 和来源账户的非敏感 `effectiveQuotaRecoveryPolicy` 只读投影，不返回源凭据、token、完整上游错误正文或 system registry 内部未授权字段。

## 接口 DTO 与写入契约

有效展示 DTO 应至少包含：

```ts
type EffectiveAccountErrorRule = {
  id: string
  action: 'retry_next' | 'temp_unschedulable' | 'rate_limited' | 'error_disabled'
  priority: number
  enabled: boolean
  source: 'system' | 'account'
  inherited: boolean
  editable: boolean
}
```

系统 DTO 使用 `source: 'system'`、`inherited: true`、`editable: false`；账户 DTO 使用 `source: 'account'`、`inherited: false`、`editable: true`，页面仍叠加账户整体只读态。字段名与动作值已由当前接口类型落实。

读取复用账户高级详情接口，由服务层合成系统规则与账户规则；不新增全局规则读取入口。写接口拒绝系统来源或继承/只读标记的规则，不能依赖前端保护数据。

## 前端混排与保存过滤

- `AccountErrorPolicyCard.vue` 继续使用单列表混排；系统规则和账户规则保持同样的视觉结构。
- 系统规则仅显示“继承” Tag，不增加全局设置入口或跳转。
- 系统规则的编辑、删除、启停、排序控件必须逐规则只读/隐藏；账户卡片整体只读时继续受现有 `readonly` 约束。
- 保存模型只保存本地规则；系统规则独立于 `credentials.error_handling_rules`，账户规则为空时继续复用现有删除语义。
- 刷新后页面应由后端有效 DTO 重建混排列表，不能依赖前端把系统规则持久化后再补回。
- 新建和克隆窗口尚未有账户高级详情 DTO 时，前端只展示同 ID 的只读系统规则预览；创建完成后必须改由后端有效 DTO 重建，预览同样不得进入保存 payload。

## 已知边界

- 当前首批错误码与高置信文本是静态白名单；新增供应商语义必须先补回归，不得以泛化 `quota` 扩大匹配。
- OAuth `rate_limited` 的恢复继续使用既有 cooldown retest 入口；API Key 多 Key 使用 Key runtime cooldown retest，`error` 只由现有“重新验证 Key 池”人工入口恢复；本次不新增恢复 API，也不新增 `quota_blocked`。
- `temp_unschedulable` 仍不是额度默认动作；若未来采用，TTL、半开和恢复证据需另立方案。
