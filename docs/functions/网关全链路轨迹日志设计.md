# 网关与 jobs 全链路轨迹日志设计

> 2026-09-24。定位：`/v1` 网关链与 jobs 调度器的可观测性契约——每个请求从进入网关到返回客户端的完整轨迹、每次调度决策的"为什么选它 / 为什么不选它 / 为什么重试"，以及 jobs 每轮任务的结局。性能边界：决策摘要为纯内存切片组装（O(n)），审计写入沿用既有 fire-and-forget producer；决策日志每请求（含每次重派）至多一条。

## 背景

此前排查断裂的四个精确缺口（均已修复）：

1. **双 trace 断裂**：响应头 `X-Trace-Id` 是 kernel UUID，而审计库 / 用量记录里的 traceId 是链内另造的 `trace_<UnixNano>`——拿响应头查审计永远查不到。
2. **调度决策零解释**：`gatewaydispatch` / `gatewayrouting` / `gatewayproxyhealth` 三个引擎包零日志；能力 / 模型过滤只输出聚合计数（`skippedCount`），不输出"哪个账户因什么被跳过"。
3. **`gateway.request.timing_summary` 恒 0**：`attemptCount` 硬编码 0、`stages` 恒空数组。
4. **jobsched 零日志**：任务开始 / 成功 / 失败 / 超时 / 退避只写内存快照（仅 `/health` 可见），失败不可归因（BUG-0183 的"可发现但不可定位"）。

## 能力一：trace 统一与请求耗时汇总

- `/v1` 链级 traceId 改为与 kernel 同源（`kernel.Context(r).TraceID`，即响应头 `X-Trace-Id` 的值），回落保留 `CreateTraceID()`。审计（`audit_logs.trace_id`）、用量记录、全部阶段日志与客户端拿到的响应头同源可查。
- `gateway.request.timing_summary` 输出真实 `attemptCount`（两个累积器取较大值：索引折算 `RecordUpstreamAttempt` 与逐次计数 `RecordGatewayAttempt`）、真实 `stageCount`；失败 / 中断请求携带完整 `stages` 数组（上限 64 条 + `droppedStageSummaries`），成功请求保持空列表降噪（对齐《运行日志降噪与终态语义设计》）。
- 新增阶段埋点：`upstream.fetch_headers`（每次上游尝试一条，带 `accountId` / `attemptIndex` / `auditAttemptIndex` / `statusCode`）、`upstream.dispatch.failed`（调度耗尽点）。
- 实现：`internal/kernel/ctx.go`（RequestContext 阶段 / 尝试累积器）、`ctxobservability.go`（summary 发射）、`cmd/juhe-ai-gateway/chain_v1.go`（traceId 解析 + fetch_headers 埋点）、`chain_ports.go`（进程级 stage recorder 注册表，按 traceId 键、defer 注销）。

## 能力二：调度决策明细

每请求（含每次重派）一条 info 日志 `gateway_dispatch_decision`，自含完整选择解释：

```text
gateway_dispatch_decision candidateTotal=1 eligibleCount=1 selectedAccountId=acc_xxx
  preFilterSkippedCount=1 preFilterSkipped="[{id:acc_yyy reason:capability_mismatch}]"
  groupId=... apiKeyId=... traceId=...
```

字段含义：

| 字段 | 含义 |
| --- | --- |
| `candidateTotal` / `eligibleCount` / `selectedAccountId` | 进入候选准备的窗口总量 / 准备完成可派发数 / 首选账户 |
| `preFilterSkippedCount` / `preFilterSkipped` | **窗口之前**能力 / 模型过滤的逐账户跳过明细（reason 稳定常量：`capability_mismatch`、`unsupported_model_constraint`、`unsupported_model_mapping`、`model_not_matched`） |
| `skippedTop` / `skippedCount` | 窗口内的跳过明细（`quota_denied`、`model_unsupported`）。注意两组 reason 值域不重叠：`preFilterSkipped` 是过滤层（`capability_mismatch` + 模型三分支），`skippedTop` 是准备窗口内（`quota_denied` / `model_unsupported`）——看日志时先看账户出现在哪一组即知它死在哪一层 |
| `busyAccountIds` / `suppressedAccountIds` / `degradedAccountIds` / `avoidedAccountIds` | 容量忙 / 本地抑制 / 运行时降级 / 回避的账户 ID |

- 各列表截断 20 条 + 对应 `*Truncated` 置位；审计侧同内容写入 `gateway_dispatch_candidates` 标签（受既有审计开关门控），预过滤层明细同时保留在既有 `account_request_capability_filter` / `account_model_filter` 标签。
- 透传链：`gatewaydispatch.candidatefilter`（过滤出口带 `PreFilterSkipped`）→ `gatewaypreauth` 端口（`CandidateFilterResult` / `DispatchPreparationInput` 的 `AccountSkipDetail`）→ `preparation` 决策摘要 → 进程级观察槽 → `cmd/juhe-ai-gateway/chain_dispatch_decision.go` 日志。观察回调 panic-safe。
- 逐账户上游失败 / 重试 / 切号已有既有日志与审计（`gateway_upstream_response_failed`、`same_account_retry_dispatch`、审计 attempts 行等），本轮不重复实现。

## 能力三：jobsched 逐轮结局日志

| 事件 | 级别 | 触发点 | 关键字段 |
| --- | --- | --- | --- |
| `jobsched_run_failed` | WARN | 任务闭包返回 error | `job`、`error` 原文、`durationMs`、`consecFail`、`backoffMs` |
| `jobsched_run_timeout` | WARN | 单轮超时 | `job`、`durationMs`、`consecFail`、`nextRetryAt` |
| `jobsched_run_partial` | WARN | OutcomePartial | `job`、`warning` |
| `jobsched_run_skipped` / `run_stopped` | DEBUG | 任务自报 skipped / 停机 | `job`、`skipReason` |
| `jobsched_run_success` | DEBUG | 成功 | `job`、`durationMs` |
| `jobsched_run_backoff_skip` | DEBUG | 退避期静默轮 | `job` |
| `jobsched_lane_busy` | DEBUG | lane 占用跳过 | `job`、`lane` |

- 成功不打 info（防止 1s 级任务刷屏）；退避跳过打 DEBUG（失败本体已有 WARN，避免 3s 任务 × 5min 退避 = 100 条 WARN）。
- 全部锁外输出；`Options.Logger` nil 时零行为变化。装配：`worker_assembly.go` 注入进程 logger。

## 排查工作流

1. 客户报障提供响应头 `X-Trace-Id`；
2. `GET /__aisys__/api/audit-logs?traceId=<id>`：请求面 / 结果面 / 每次上游尝试（attempts 行含上游 URL、状态码、错误原文）；
3. 日志文件 grep 该 traceId：`gateway_dispatch_decision`（当时怎么选的、谁被跳过及原因）→ `upstream.fetch_headers` / `gateway_upstream_response_failed`（每次上游返回）→ `timing_summary`（全貌：几次尝试、哪个阶段慢 / 失败）；
4. jobs 侧：grep `jobsched_run_failed` / `run_timeout` 直接得到任务名、错误原文与连续失败计数。

## 边界与已知限制

- 能力过滤的 `capability_mismatch` 为统一粒度（driver 端口 `AccountSupportsGatewayRequest` 仅布尔）；细分需改端口，暂不做。
- 熔断 `circuit_transition` 观测事件无生产发出点（J3b 控制面仅 TransitionID 落库 / Redis）；本地抑制路径已有 `gateway_account_local_suppressed` WARN。
- Key 轮转选择、策略 skipped（空绑定 / 缺模型 / 单供应商）仍无逐条记录（仅 RouteAction.Reason）。
- 客户端并发重放相同 `X-Trace-Id` 时 stage recorder 注册表后者覆盖前者（仅影响 timing_summary 的 stages 明细，正常 UUID 下不触发）。
- 相同语义的高频 debug 阶段单行日志受既有采样门控，`timing_summary.stages`（失败请求）是权威阶段序列。

## 验证

- 单测：`internal/kernel`、`internal/gatewaydispatch`（W1b 族）、`internal/jobsched`（W2 族）、`cmd/juhe-ai-gateway`（Trace / StageRecorder / TimingSummary / DispatchDecision 族）全绿，含 `-race`。
- 真实 e2e（隔离 SQLite 实例 + 真实上游）：成功路径（非流式 + 流式 HTTP 200）、上游 500×3 → 网关 503 重试路径、多账户能力过滤路径，逐项核对日志与审计记录；响应头 traceId == 审计 traceId 实测一致。
