# 系统团队与统一授权设计

> **状态：2026-11-22 同步「直发 + 领取」模型（schema revision 31）。** 本文保留 `system_teams` / `system_team_members` 的团队管理契约、授权统计口径、页面与团队接口。授权生命周期、发送/领取流程、状态词表、调度活性谓词与存储设计，以 [授权发送与领取设计](授权发送与领取设计.md) 为权威；本文不再保留「offer 审批链」「接收方确认」「团队审批」「来源优先级 dormant」「额度 limits_json」等已退役语义（随 revision 28 治理体系废弃，见新设计 §1）。

## 文档定位

本文定义 `juhe-ai` 的授权团队（底层为系统团队）和统一授权中心的团队侧契约。授权相关入口、统计和来源说明收敛到管理侧 `统一授权管理` 和用户侧 `我的授权` 菜单，不沿用「账户页里管账户授权、分组页里管分组授权」的分散入口。

命名边界：代码、存储和接口实体仍称 `系统团队`；前端菜单在授权场景中显示为 `授权团队` / `我的授权团队`。两者指向同一套 `system_teams` / `system_team_members` 模型，不代表两套团队体系。

## 目标

- 管理侧 `统一授权管理` 下提供 `授权团队` 菜单，用团队把多个系统账户归纳在一起。
- 资源所有者可以把 AI 账户或分组直接授权给某个系统账户，也可以向某个系统团队发起团队授权。
- 团队只是批量分发渠道，不是运行时最终授权主体；最终有效授权只绑定到具体系统账户的授权实例。
- 授权统计唯一主维度统一为「资源 × 用户」，授权方只关心「这个用户在这个资源上消耗了多少」。
- 团队来源与个人来源可以并存：多条来源同时有效时 runtime 取最早激活的有效来源；来源终态按 [授权发送与领取设计](授权发送与领取设计.md) §3.2 推导。
- 授权只代表使用权，不代表编辑权、删除权、凭据查看权、成员管理权或二次授权权。

## 核心结论

- 最终可用资源始终绑定到 `grantee_system_account_id`，不绑定团队。
- 同一 `resource_type + resource_id + grantee_system_account_id` 全生命周期只保留一条稳定的最终用户授权主记录。
- 授权发送即达：发起后 grant=`pending`，团队授权按在册成员各生成一条 pending 来源；成员各自领取，领取即生效（账户授权一步创建实例并绑定自己分组，分组授权 settings 行存在即生效）。
- 资源所有者不能把自己的 AI 账户或分组授权给自己；团队展开时也不为资源归属人成员生成来源。
- 团队停用、团队逻辑删除或成员移除时，撤销对应的非终态团队来源；重新启用团队不复活旧来源；成员重新加入团队可再领取（不受历史 `declined` / `returned` 阻断）。
- 网关调度只读取最终用户授权主记录、有效来源与父 grant 的实时状态、`group_authorization_settings` 行存在性和 `group_accounts` 真实成员行；团队成员变化在业务写入阶段维护来源和运行时状态。
- 历史使用记录以稳定的用户授权聚合，来源变化、团队变化和重新领取不会拆散同一用户在同一资源上的历史消耗。

## 核心术语

| 术语 | 含义 |
| --- | --- |
| 系统账户 | 后台登录账号，是 API Key、调用日志和业务数据的默认隔离边界。 |
| 授权团队 | 多个系统账户的集合，用于批量承接授权使用权。底层仍使用系统团队数据模型；在授权对象、筛选和统计列语境中可显示为「被授权团队」。 |
| 资源 | 可被授权使用的对象，当前支持 `AI 账户` 和 `分组`。 |
| 最终用户授权 | 某个资源授权给某个系统账户的稳定运行时关系，是运行时唯一看的授权主体。 |
| 授权来源 | 最终用户授权为什么成立。当前支持 `manual`（个人）和 `team`（团队）。 |
| 成员来源 | 团队授权展开后，为团队成员创建的 pending 来源；成员只能处理自己的来源。 |
| 调用方 | 实际发起网关请求的 API Key 所属系统账户。 |
| 资源归属人 | AI 账户或分组的真实所有者。 |
| 授权消耗 | 调用方不是资源归属人时，通过授权产生的请求、Token 和成本。 |

## 授权团队管理

### 菜单与权限

- 管理侧菜单名称为 `授权团队`，挂在 `统一授权管理` 下。
- 当前菜单仅 `super_admin` / `admin` 可见，用于创建授权团队、编辑团队资料、启停团队和维护成员。
- 普通 `user` 不进入管理侧授权团队页；用户侧可在 `我的授权团队` 只读查看自己加入的团队和成员。

### 团队字段

- `id`
- `name`：团队名称，页面主展示字段，活跃团队全局唯一。
- `description`
- `status`：`active`、`disabled`；逻辑删除时写 `deleted_at` 并置 `deleted`，历史行保留。
- `created_by`：团队创建人（仅审计与展示；团队授权无审批角色）。
- `created_at` / `updated_at`
- `deleted_at`：逻辑删除时间；非空团队不参与列表、精确名匹配和成员维护。

### 成员字段

- `id`
- `team_id`
- `system_account_id`
- `member_role`：当前固定为 `member`，后续可扩展 `manager`。
- `status`：`active`、`removed`
- `joined_at`
- `removed_at`
- `created_by`
- `created_at` / `updated_at`

### 团队与成员规则

- 同一团队内同一系统账户同一时间只能有一条有效成员关系。
- 同一系统账户允许同时属于多个团队。
- 单团队有效成员上限 20；单次添加成员上限 20；团队名称 1-100 字符，说明最多 200 字符。
- 团队名称搜索只按名称精确 / 前缀匹配，不搜索 ID 或说明。
- 团队列表、基础详情、成员页和历史成员页分开按需读取；列表不预取成员数组。
- 团队字段、成员添加和成员移除都使用 `expectedUpdatedAt` CAS；冲突返回 `409`，no-op 不推进版本。
- 系统账户被停用后，即使仍在团队中，也不能通过团队授权继续调用。

### 团队生命周期与授权级联

- 团队停用：撤销该团队全部非终态 team 来源，并把对应团队 grant 置 `revoked`（`ended_reason=team_disabled`）；已终态来源和 grant 保持原状。
- 团队重新启用：只恢复团队本身可用状态，**不复活**已撤销的团队来源；需要资源所有者重新发起团队授权。
- 团队成员移除：在成员移除事务内撤销该成员在该团队下所有非终态 team 来源（`ended_reason=member_removed`，`RevokeTeamSourcesForMemberTx`），重算 runtime；其他成员和团队 grant 不受影响。
- 团队新增成员：团队授权处于 `pending` / `active` 时，为该成员创建成员 runtime 与 pending 来源，不创建实例或绑定；成员领取后生效。成员重新加入团队（历史只有 `member_removed` / `expired` 或从未有过来源）按新增成员同样获得来源；历史 `declined` / `returned` 不阻断新来源创建。
- 团队逻辑删除：先撤销全部非终态 team 来源和团队 grant，再写 `deleted_at`；成员行保留为历史，不物理删除授权来源或统计。当前管理端仅提供启停，删除入口未暴露；删除契约保留给后续管理动作。

## 统一授权中心

> 完整状态机、接口、存储与验收标准见 [授权发送与领取设计](授权发送与领取设计.md)。本节只保留与团队和统计相关的现行口径。

### 信息架构

- 用户侧 `我的授权`：`授权中心`（页签：收到的授权、我发出的授权、我的资源授权）、`团队消耗明细`、`用户消耗明细`、`我的授权团队`。
- 管理侧 `统一授权管理`：`授权中心`（管理态：全部业务记录）、`团队消耗明细`、`用户消耗明细`、`授权团队`。
- `授权中心` 只负责授权关系和来源状态，不展示消耗统计列；消耗进入同组的团队 / 用户消耗明细。
- AI 账户页和分组页不放「授权管理」弹窗；账户列表无授权归还入口（归还已退役，见下），分组列表保留分组授权退订入口。

### 模型分层

统一授权拆成三层：

1. `resource_authorization_grants`：授权业务主表，表达「某资源拟授权给哪个业务目标」，目标可以是系统账户或团队。
2. `resource_authorizations`：最终用户授权运行时表，表达「某资源最终授权给某系统账户」；同一资源同一用户全生命周期一条。
3. `resource_authorization_sources`：来源表，表达这条运行时授权当前或历史上因何成立，以及成员是否已领取。

授权操作列表、新增、暂停、恢复、延长、回收和到期修改以 `resource_authorization_grants` 为准；运行时、资源列表、分组绑定、API Key 绑定和授权统计以 `resource_authorizations` 为准；来源领取状态以 `resource_authorization_sources` 为准。三层共用 7 值状态词表 `pending / active / paused / expired / revoked / returned / declined`。

### 来源有效性与推导

- 同一 runtime 可以同时存在 `manual` 和 `team` 来源；多条有效来源并存时，runtime 取「最早激活且父 grant 活跃」的来源作为有效来源，其余有效来源共同维持运行时可用。
- 来源进入终态（`revoked` / `returned` / `declined` / `expired`）后由剩余有效来源接管；无剩余有效来源时 runtime 按最近终态推导（推导链见 [授权发送与领取设计](授权发送与领取设计.md) §3.2）。
- 来源切换不拆散历史统计：同一 runtime 的历史消耗继续归并到「资源 × 用户」。

### 发起、领取与回收

- 个人授权：资源所有者按精确用户名发起，发送即达，接收方在授权中心看到待领取来源。
- 团队授权：资源所有者按精确团队名发起，发送即达，按在册成员逐人生成 pending 来源；无团队审批环节。
- 成员领取后账户授权立即创建实例并绑定自己分组（缺省回落默认分组），分组授权立即生效；无第二步绑定/启用。
- 资源所有者可以暂停、恢复、延长、缩短或回收非终态授权；暂停期间不能领取。
- 接收方可以拒绝或归还来源；团队授权的归还/拒绝是成员自己的成员来源，不影响其他成员。管理员收回访问用回收。
- 到期由 gateway `authz-governance-sweep`（每分钟）把 `expires_at` 已过的非终态授权翻转为 `expired`；延长可把 `authorization_expired` 的授权恢复（曾领取的来源回 `active`，未领取的回 `pending`）。
- 无额度输入、无 cooldown、无 reinvite、无审批；重复发起的幂等与 `offer_already_active` 规则见 [授权发送与领取设计](授权发送与领取设计.md) §3.3。

### 使用权生效

- 领取即生效：账户授权领取 = 实例 + 绑定一步完成；分组授权领取 = settings 行写入，路由策略引用后按实时成员行调度。
- 授权账户和授权分组只能绑定到接收方自己的分组和路由策略；通用账户、分组和路由策略写路径重复校验 runtime 活性与 settings 行存在（`ValidateGroupBinding`）。
- 授权实例使用面契约（可改限频下调/优先级/调度标记、不可编辑来源字段、无克隆、账户列表无归还入口、限频 ≤ 父）见 [授权发送与领取设计](授权发送与领取设计.md) §4。
- 归还、拒绝、回收或团队来源撤销只有在 runtime 进入终态时才关闭绑定；runtime 仍有其他有效来源时保留绑定。

## 授权统计口径

### 使用记录事实字段

`usage_records` 同时记录调用方、资源归属和最终用户授权路径：

- `system_account_id`：实际调用方系统账户，即 API Key 所属系统账户。
- `account_owner_system_account_id`：实际命中 AI 账户的归属人。
- `group_owner_system_account_id`：请求使用的分组归属人。
- `account_access_type`：`owner`、`authorized`
- `group_access_type`：`owner`、`authorized`
- `account_authorization_id`：命中授权 AI 账户时写入最终用户授权主记录 ID。
- `group_authorization_id`：命中授权分组时写入最终用户授权主记录 ID。
- `account_authorization_source_type` / `account_authorization_source_team_id`：命中授权 AI 账户时的来源类型和团队。
- `group_authorization_source_type` / `group_authorization_source_team_id`：命中授权分组时的来源类型和团队。

使用记录保留成功、失败和排障记录；授权消耗统计按进入网关使用记录的请求聚合，失败记录按 0 token、0 cost 计入请求和错误次数。资源归属人自己的自用调用仍按自用处理，不进入授权 ID 维度。

### 展示口径

- 资源归属人的 AI 账户 / 分组「用量情况」展示资源全部总消耗，包含归属人自用和所有被授权用户使用。
- `授权中心` 列表不展示今日用量、范围用量、最后使用或额度摘要，避免把关系管理和消耗报表混在一起（授权额度已退役，不存在额度摘要）。
- 管理侧授权消耗统一进入 `团队消耗明细` 和 `用户消耗明细`；时间筛选按日范围，默认最近 31 天，均不包含归属人自己的自用消耗。
- 用户侧 `我的授权` 下同样把 `授权中心` 和消耗明细分开；授权消耗进入同组的 `团队消耗明细` 和 `用户消耗明细`。
- 授权统计主维度是「资源 × 用户」，后台统计 worker 按稳定的 `authorization_id`、调用方、来源快照和资源筛选组合增量写入专用日摘要表（约 60 秒节拍）。
- 授权消耗明细接口按日范围直接聚合 `authorization_team_usage_summary_daily` 和 `authorization_user_usage_summary_daily`，31 天窗口内任意自定义日期区间均可出数；不在页面查询时临时扫描 `usage_records`。
- `团队消耗明细` 和 `用户消耗明细` 必须调用后端明细接口；接口按日范围、授权人、团队、被授权用户和资源筛选现场聚合报表日摘要行。
- A 授权给 B 时，A 在用户消耗明细看「B 在所选日期范围内在该资源上用了多少」，不区分这部分用量在历史上来自个人来源还是团队来源。
- A 授权给团队时，团队详情本质是该团队曾激活过的成员用户授权集合；展示仍以成员用户为主，不以来源为主。
- 如果 B 先有个人来源，后又有团队来源，B 在该资源上的范围消耗继续合并到同一条用户授权中；团队筛选只看使用记录写入时来源快照属于该团队的消耗。
- 如果 B 后续被移出团队，已经写入团队日摘要的历史消耗保留；后续请求不再写入该团队来源。
- 资源归属人只能看授权维度的聚合统计，不直接查看被授权人的请求快照、响应快照、客户端 IP、API Key 明文或业务请求内容。
- 调用方仍可在自己的使用记录里看到自己 API Key 产生的明细，包括使用授权资源产生的请求；结果仍限制在调用方自己的 `usage_records.system_account_id`。

### 重叠授权统计示例

场景：A 把 `001` 账户先直接授权给 B，随后又把 `001` 账户授权给 B 所在的 `XX` 团队。

- B 的 AI 账户列表只出现一个 `001`（同一 runtime 复用同一授权实例）。
- B 在 `001` 上对应的始终是同一条最终用户授权主记录。
- 团队来源与个人来源并存时 runtime 取最早激活的有效来源；一条来源归还后另一条继续维持可用。
- B 发起请求时，每次实际上游请求 / 上游尝试写入一条 `usage_records`，授权 ID 始终是 `001 × B` 这条主记录。
- A 在用户消耗明细筛选日期范围时，可以看到 B 在该范围内对 `001` 的消耗。
- A 在用户消耗明细按 `XX` 团队筛选时，看到的是使用记录写入时来源快照属于 `XX` 团队的范围消耗。团队消耗明细只展示 `XX` 团队的汇总总量，行操作可跳转到用户消耗明细并自动带上团队筛选和日期范围。

## 页面设计

### 授权团队页

- 团队列表：团队名称、状态、成员数、描述、创建时间、操作。
- 团队基础详情和成员集合分开按需读取；列表与基础详情不携带成员数组，只有打开成员弹窗时才读取当前有效成员的 `id`、系统账户、展示名称和加入时间。
- 创建 / 编辑团队：名称、描述、状态；团队名称必须唯一，不让用户感知团队编码。
- 成员维护：添加系统账户、移除成员、查看成员状态；系统账户下拉只展示启用或可管理的账号。
- 团队成员变化会影响既有授权覆盖范围（移除即撤销该成员来源），团队详情必须给管理员展示影响提示。

### 授权中心页

- 用户侧页签：收到的授权、我发出的授权、我的资源授权；管理侧管理态页签：全部业务记录。
- 收到的授权按来源行展示资源、来源账户/团队、状态、到期、领取状态和可执行动作（待领取：领取/拒绝；已生效：归还）。
- 领取弹窗：账户资源展示目标分组下拉（可选 `targetGroupId`，缺省默认分组）；分组资源直接确认生效。
- 发起授权：用户侧直接输入精确用户名或精确团队名；管理侧先选择资源所有者，再从该所有者自己的资源中选择；无额度输入、无目标分组字段、无全量用户/团队下拉。
- 我发出的授权展示来源领取计数（已领取 / 待领取）与生命周期动作（暂停、恢复、延长、缩短、回收）。
- 归还入口只在授权中心按来源提供；账户列表无归还按钮，分组列表保留分组授权退订。

### 团队消耗明细页

- 顶部筛选：用量日期范围、被授权团队、资源类型、资源名称；日期范围最大 31 天。
- 列表维度：按被授权团队和资源名称展示，不在该页展开成员。
- 主要列：被授权团队、资源名称、资源归属人、范围消耗、最后使用、操作。
- 行操作 `查询用户明细` 跳转到 `用户消耗明细` 并带上团队筛选、日期范围和资源类型筛选。
- 数据来源：管理侧并行调用 `GET /__aisys__/api/authorizations/usage/team-details` 与 `team-summary`，用户侧调用对应 `my-authorizations` 接口；rows 只读分页明细窗口，summary 精确读取一条汇总窗口，互不阻塞。

### 用户消耗明细页

- 顶部筛选：用量日期范围、被授权团队、被授权用户、授权内容、授权资源；日期范围最大 31 天。
- 列表维度：按最终被授权用户和资源名称展示，包含个人直接授权和被授权团队展开后的成员用户。
- 主要列：被授权用户、资源名称、资源归属人、范围消耗、最后使用。
- 数据来源：管理侧并行调用 `GET /__aisys__/api/authorizations/usage/user-details` 与 `user-summary`，用户侧调用对应 `my-authorizations` 接口；rows 只读分页明细窗口，summary 精确读取一条汇总窗口，互不阻塞。

## 当前接口

团队管理：

- `GET /__aisys__/api/system-teams` / `GET /__aisys__/api/my-teams`：分页返回当前页面渲染字段和 `updatedAt`，不返回成员数组；管理侧读取全部可管理团队，用户侧只读当前用户加入的团队。
- `GET /__aisys__/api/system-teams/:id` / `GET /__aisys__/api/my-teams/:id`：返回团队基础详情、成员数和版本，不返回成员数组。
- `GET /__aisys__/api/system-teams/:id/members` / `GET /__aisys__/api/my-teams/:id/members`：按需返回 `{ id, memberCount, updatedAt, items }`。
- `GET /__aisys__/api/system-teams/:id/members/history` / `GET /__aisys__/api/my-teams/:id/members/history`：按需分页读取已移除成员，默认和上限均为 20 条。
- `POST /__aisys__/api/system-teams`：创建团队，仅管理员；返回可合并到列表的轻量行。
- `PATCH /__aisys__/api/system-teams/:id`：编辑团队，仅管理员；只提交变化字段和 `expectedUpdatedAt`，只返回 `{ id, changedFields, rowPatch, updatedAt }`。
- `POST /__aisys__/api/system-teams/:id/members`：添加成员，仅管理员；提交目标用户 ID 与 `expectedUpdatedAt`；团队授权活跃时同事务为新成员创建 pending 来源。
- `DELETE /__aisys__/api/system-teams/:id/members/:memberId`：移除成员，仅管理员；请求体提交 `expectedUpdatedAt`，同事务级联撤销该成员全部非终态 team 来源。
- 团队字段和成员写入都使用作用域内 CAS；冲突返回 `409`，只有实际变更才推进版本、写操作日志、展开或撤销授权并失效相关缓存。

授权中心接口（保留 + 移除清单）见 [授权发送与领取设计](授权发送与领取设计.md) §6 与 [接口契约与权限矩阵](接口契约与权限矩阵.md)；团队审批接口（`my-teams/{teamId}/authorization-offers` 及 approve/decline）已随审批位退役删除。

消耗明细：

- `GET /__aisys__/api/authorizations/usage/team-details` / `user-details`
- `GET /__aisys__/api/authorizations/usage/team-summary` / `user-summary`
- `GET /__aisys__/api/my-authorizations/usage/team-details` / `user-details`
- `GET /__aisys__/api/my-authorizations/usage/team-summary` / `user-summary`

## 存储与实现原则

- 团队使用 `system_teams` + `system_team_members`；逻辑删除列 `deleted_at` 保留（活跃名称部分唯一索引随之有效）。
- 授权统一使用 `resource_authorization_grants` + `resource_authorizations` + `resource_authorization_sources`；三层 7 值状态词表与终态 `ended_at` / `ended_reason` 约束见 [授权发送与领取设计](授权发送与领取设计.md) §7。
- 授权账户通过 `group_accounts.account_authorization_id` 记录绑定命中的最终用户授权；授权分组通过 `group_authorization_settings` 行存在性表达生效（7 列，无 enabled/快照）。
- 无授权额度存储（`limits_json` 已随 revision 31 退役）；无 cooldown、通知、suspensions、范围快照表。
- 授权创建、领取、团队停用、成员变更、回收和归还都必须在事务内完成主记录、来源和 runtime 更新（锁顺序 grant → runtime → source → settings）。
- 对 `resource_type + resource_id + grantee_system_account_id`、`authorization_id + source_team_id`、`team_id + system_account_id` 建立唯一索引或唯一有效性约束，防止重复授权和重复成员。
- 团队、账户、来源和 runtime 的授权域外键使用 `RESTRICT`；团队/账户逻辑删除不得级联删除授权历史。

## 边界条件清单

| 场景 | 处理规则 |
| --- | --- |
| 先个人后团队 | 复用同一条最终用户授权；两条来源并存时 runtime 取最早激活的有效来源，历史用量不拆分。 |
| 先团队后个人 | 个人来源可以单独领取；团队来源仍有效时按来源推导决定有效来源，不把个人来源永久取消。 |
| 多个团队来源 | 允许多条团队来源同时有效；runtime 只保留一条主记录和一个有效来源。 |
| 团队授权无成员 | 发送后 grant 停留 `pending`；成员加入后获得来源并可领取，不因空集终态。 |
| 成员拒绝或归还 | 只影响该成员的团队来源；其他成员不受影响；该成员历史退出不阻断未来团队授权的来源创建。 |
| 团队成员被移除 | 该成员团队来源撤销（`member_removed`）并重算 runtime；历史消耗保留。 |
| 团队被停用 | 撤销全部非终态团队来源；重新启用不复活旧来源。 |
| 系统账户被停用 | runtime 可保留，但网关调度拦截该账户。 |
| 授权方原账户被停用或删除 | 来源进入不可用/撤销路径（删除即 `account_deleted`），接收方不再调度；历史授权和统计保留。 |
| 分组包含他人授权来的账户 | 该账户不能通过分组授权继续下发，防止授权穿透。 |
| 同一次上游尝试命中多个来源 | 只认最终用户授权主记录，只写一条使用记录。 |
| 归还或拒绝后重新授权 | 发起方创建全新 pending grant，接收方重新领取；旧绑定不自动复活。 |
| 重复发起同资源同接收方 | pending 幂等返回；active/paused 返回 `offer_already_active`；终态一律新建全新 grant。 |

## 当前能力清单

- 管理员可以创建、编辑、启停团队，并维护团队成员和成员状态。
- 资源所有者可以直接发起个人或团队授权（发送即达）、暂停/恢复/延长/缩短/回收授权、查看来源领取计数和聚合消耗。
- 成员可以逐人领取、拒绝或归还自己的来源；领取账户授权一步完成实例创建与绑定，领取分组授权立即生效。
- 同一资源同一用户全生命周期只存在一条稳定的最终用户授权主记录；同一用户同时命中多个来源时只出现一个有效资源。
- 被授权用户不能修改来源凭据、`base_url`、供应商/协议、模型映射或代理；只能通过 `authorized-dispatch` 白名单修改授权实例的本地限频（≤ 父）与调度标记，可停用/启用自己的实例。
- 团队成员新增、移除、团队停用、系统账户停用和授权回收 / 归还都能实时影响网关调度。
- 团队消耗明细展示每个被授权团队总消耗；行操作可跳转用户消耗明细并带上团队筛选。
- 用户消耗明细按「资源 × 用户」统计到最终用户，并能按被授权团队筛选成员用户消耗，且不包含资源归属人自用消耗。
- AI 账户授权实例的账户用量按被授权实例所属系统账户聚合；授权方查看对外授权消耗时使用团队 / 用户消耗明细。
- 使用记录页只展示调用方自己的明细，资源所有者不能查看被授权人的请求快照和业务内容。
