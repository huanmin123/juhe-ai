# 系统团队与统一授权设计

## 文档定位

本文定义 `juhe-ai` 当前的系统团队与统一授权中心。授权相关入口、统计、回收和来源说明统一收敛到管理侧 `统一授权管理` 和用户侧 `我的授权` 菜单，不再沿用“账户页里管账户授权、分组页里管分组授权”的分散入口。

当前项目未正式上线，本地 SQLite 数据可以备份后直接重建或清洗，因此本方案按完整授权模型设计，统一使用当前表结构。

源码规则：后端启动、repository、routes 和前端页面都不能挂载一次性数据处理、临时同步修复或迁移标记代码；本地数据结构问题通过直接操作数据库、临时离线脚本或重建库解决。

命名边界：代码、存储和接口实体仍称 `系统团队`；前端菜单在授权场景中显示为 `授权团队` / `我的授权团队`。两者指向同一套 `system_teams` / `system_team_members` 模型，不代表两套团队体系。

## 目标

- 管理侧 `统一授权管理` 下提供 `授权团队` 菜单，用团队把多个系统账户归纳在一起。
- 资源所有者可以把 AI 账户或分组授权给某个系统账户，也可以直接授权给某个系统团队。
- 团队只是批量授权来源，不是运行时最终授权主体；最终有效授权只绑定到具体系统账户。
- 授权统计唯一主维度统一为“资源 × 用户”，授权方只关心“这个用户在这个资源上消耗了多少”。
- 同一用户在同一资源上同时出现个人来源和团队来源时，以团队来源为准；个人来源取消，但历史用量继续合并到同一条最终用户授权。
- 授权只代表使用权，不代表编辑权、删除权、凭据查看权、成员管理权或二次授权权。

## 核心结论

- 最终可用资源始终绑定到 `grantee_system_account_id`，不绑定团队。
- 同一 `resource_type + resource_id + grantee_system_account_id` 全生命周期只保留一条稳定的最终用户授权主记录。
- 团队授权进入系统后，作用是“创建或激活用户授权来源”，而不是在网关运行时再参与一层团队判断。
- 资源所有者不能把自己的 AI 账户或分组授权给自己；团队授权展开时也不能为资源归属人成员生成最终用户授权。
- 网关调度只读取最终用户授权主记录及其可用性快照，并结合调用方系统账户、资源、绑定关系和额度缓存判断；团队成员变化、团队停用和团队授权回收必须在业务写入或后台同步阶段维护来源和最终用户授权状态。
- 团队来源优先级高于个人来源；当团队来源覆盖个人来源时，系统切换同一条用户授权的生效来源，不新建第二条最终授权。
- 历史使用记录以稳定的 `user authorization` 聚合，因此来源变化、团队变化和重新激活不会拆散同一用户在同一资源上的历史消耗。

## 核心术语

| 术语 | 含义 |
| --- | --- |
| 系统账户 | 后台登录账号，是 API Key、调用日志和业务数据的默认隔离边界。 |
| 授权团队 | 多个系统账户的集合，用于批量承接授权使用权。底层仍使用系统团队数据模型；在授权对象、筛选和统计列语境中可显示为“被授权团队”，强调它是资源使用权的接收方。 |
| 资源 | 可被授权使用的对象，当前支持 `AI 账户` 和 `分组`。 |
| 最终用户授权 | 某个资源授权给某个系统账户的最终有效关系，是运行时唯一看的授权主体。 |
| 授权来源 | 最终用户授权为什么成立。当前支持 `个人来源` 和 `团队来源`。 |
| 调用方 | 实际发起网关请求的 API Key 所属系统账户。 |
| 资源归属人 | AI 账户或分组的真实所有者。 |
| 授权消耗 | 调用方不是资源归属人时，通过授权产生的请求、Token 和成本。 |

## 授权团队管理

### 菜单与权限

- 管理侧菜单名称为 `授权团队`，挂在 `统一授权管理` 下。
- 当前菜单仅 `super_admin` / `admin` 可见，用于创建授权团队、编辑团队资料、启停团队和维护成员。
- 普通 `user` 不进入管理侧授权团队页；用户侧可在 `我的授权团队` 只读查看自己加入的团队和成员，并且在我的授权新增授权时可以读取可选团队摘要、选择有效团队作为授权对象。
- 管理员可以查看所有团队和成员；资源所有者在授权详情里只能看到与自己授权相关的团队及成员消耗明细。

### 团队字段

- `id`
- `name`：团队名称，页面主展示字段，全局唯一。
- `description`
- `status`：`active`、`disabled`
- `created_by`
- `created_at` / `updated_at`

### 成员字段

- `id`
- `team_id`
- `system_account_id`
- `member_role`：当前固定为 `member`，后续可扩展 `manager`。
- `status`：`active`、`removed`
- `joined_at`
- `removed_at`
- `created_by`
- `created_at` / `updated_at`

### 团队与成员规则

- 同一团队内同一系统账户同一时间只能有一条有效成员关系。
- 同一系统账户允许同时属于多个团队。
- 团队和成员默认采用软状态管理；有历史授权或历史消耗时不做硬删除。
- 停用团队后，该团队不能再作为新增授权对象；该团队现有团队来源立即失效，但历史授权和历史统计保留。
- 移除成员后，该成员不再通过该团队来源获得资源使用权；已有 API Key 或分组绑定会因为最终用户授权状态或来源状态已更新而被网关拦截。
- 新增成员后，如果团队仍有有效团队授权来源，系统应为该成员补齐对应最终用户授权或重新激活已有授权。
- 系统账户被停用后，即使仍在团队中，也不能通过团队授权继续调用。
- 团队详情必须展示当前成员状态，并保留历史已移除成员标记，便于解释历史授权消耗。

## 统一授权中心

### 菜单定位

- 管理侧使用二级菜单：`统一授权管理`。
- `统一授权` 只负责授权关系管理：新增、查看、暂停、恢复、回收、修改到期时间和额度配置，不展示消耗统计列。
- `团队消耗明细` 按被授权团队查看所选日期范围内的预聚合总消耗。
- `用户消耗明细` 按最终被授权用户查看所选日期范围内的预聚合消耗，包含被授权团队里的成员用户。
- `授权团队` 维护可被授权的团队和成员。
- 用户侧同样使用二级菜单：`我的授权`，包含 `授权操作`、`团队消耗明细`、`用户消耗明细` 和 `我的授权团队`。
- 用户侧 `授权操作` 只负责当前登录用户授权出去或授权给自己的关系查看与操作，不展示消耗统计列，也不提供用量时间筛选；授权出去的关系可暂停、恢复、回收和修改配置，授权给自己的个人直授权只提供归还动作。团队授权记录代表团队业务授权，个人成员不能在该列表直接归还团队记录，避免把个人意愿误操作成团队授权变化；如果后续要支持成员不使用团队授权，应单独设计个人退出 / 屏蔽状态，不复用团队授权回收或个人直授权归还。
- 用户侧 `团队消耗明细` / `用户消耗明细` 只读取当前登录用户作为资源归属人的授权范围窗口表，不展示或汇总别人授权给自己的资源消耗。
- AI 账户页和分组页不再放“授权管理”弹窗，只展示资源来源、所有者摘要和当前登录用户的权限摘要。

### 模型分层

统一授权拆成两层：

1. `resource_authorization_grants`：授权操作业务主表，只表达“某资源被授权给哪个业务目标”，目标可以是系统账户或团队。
2. `resource_authorizations`：最终用户授权运行时表，只表达“某资源最终授权给某系统账户”。
3. `resource_authorization_sources`：授权来源表，只表达“这条最终用户授权当前或历史上是因为什么来源成立”。

授权操作列表、新增、暂停、恢复、回收和配置修改都只以 `resource_authorization_grants` 为准，不能从成员展开后的 `resource_authorizations` 反推业务操作。运行时、资源列表、分组绑定、API Key 绑定和授权统计仍以 `resource_authorizations` 为准；`resource_authorization_sources` 只负责来源说明、优先级切换、历史追踪和批量重算。

### 授权操作业务主表

`resource_authorization_grants` 是统一授权业务主表，字段如下：

- `id`
- `resource_type`：`account`、`group`
- `resource_id`
- `resource_owner_system_account_id`
- `grantee_type`：`system_account`、`team`
- `grantee_system_account_id`：`grantee_type = system_account` 时必填
- `grantee_team_id`：`grantee_type = team` 时必填
- `scope`：当前固定为 `use`
- `status`：`active`、`paused`、`expired`、`revoked`、`returned`
- `remark`
- `expires_at`
- `limits_json`
- `created_by`
- `created_at`
- `revoked_by`
- `revoked_at`
- `updated_at`

约束与原则：

- 有效人员授权唯一键为 `resource_type + resource_id + grantee_system_account_id WHERE status = active AND grantee_type = system_account`。
- 有效团队授权唯一键为 `resource_type + resource_id + grantee_team_id WHERE status = active AND grantee_type = team`。
- 同一资源同一业务目标不能重复创建有效授权；数据库唯一索引负责兜底拦截，服务层负责返回中文错误。已回收、已归还或已过期的授权再次授权时复用原业务记录并恢复为 `active`，不新建重复授权。
- 授权记录不提供普通物理删除动作；回收、归还和到期都通过状态保留历史。AI 账户删除采用两阶段：删除操作只允许删除真实来源账户，逻辑删除 `accounts` 行并立即从列表、选项、测试、调度和后台刷新路径隐藏；删除来源账户时同步逻辑删除所有被授权实例，并把该资源对应的授权操作记录和运行时授权标记为 `revoked`。授权实例账户不能通过账户删除接口删除；被授权人不想继续使用个人直授权时，必须走授权归还入口，授权操作记录和运行时授权标记为 `returned`，来源账户不受影响。
- 团队授权创建后会展开到团队成员的 `resource_authorizations` 运行时记录，但授权操作列表只展示团队这一条业务记录。
- 人员直授权即使被团队来源覆盖，也仍然是业务主表中的一条人员授权操作，不和团队授权混在同一展开结果里。

### 最终用户授权主表

`resource_authorizations` 是当前最终授权主表，字段如下：

- `id`
- `resource_type`：`account`、`group`
- `resource_id`
- `resource_owner_system_account_id`
- `grantee_system_account_id`
- `scope`：当前固定为 `use`
- `status`：`active`、`paused`、`expired`、`revoked`、`returned`
- `effective_source_type`：`manual`、`team`、`null`
- `effective_source_team_id`：当前生效来源是团队时记录团队 ID，否则为空
- `expires_at`：可选自动回收时间，命中后状态自动切换为 `expired`
- `limits_json`：美元成本额度限制 JSON，内部 `limit` 表示美元金额，支持 n 小时、日、周、月和累计总额度；为空表示不限制。
- `activated_at`
- `last_source_changed_at`
- `revoked_at`
- `revoked_reason`：例如 `manual_revoked`、`team_revoked`、`member_removed`、`team_disabled`、`grantee_returned`、`resource_disabled`
- `remark`
- `created_by`
- `created_at`
- `updated_at`

约束与原则：

- 唯一键固定为 `resource_type + resource_id + grantee_system_account_id`。
- 同一资源同一用户全生命周期只维护这一条主记录；来源变化、停用后重启、回收或归还后重授都优先复用这条记录，不新建第二条最终授权。
- `status = active` 表示被授权人可见且可用；`paused` 表示授权方暂停，被授权人仍可见但不可用；`expired` 表示到期，被授权人仍可见但不可用，调整为未过期后可恢复可用；`revoked` 表示授权方回收，被授权人不可见也不可用；`returned` 表示被授权人归还，被授权人不可见也不可用。
- 实际可调用仍要结合调用方系统账户状态、最终用户授权状态、授权实例账户状态、本地绑定状态、额度缓存和来源账户可用性做校验；团队状态通过授权来源同步影响最终用户授权，不作为网关运行时额外遍历的主体。对 AI 账户授权来说，授权生效后会创建被授权人自己的账户实例，归属人原账户的停用、异常、限流 / 临时不可调用、冷却未结束、关闭调度、套餐到期、删除或凭据缺失不会覆盖或回写授权实例账户行，但会作为来源侧阻断进入 `effectiveAvailability` 并阻止实际调度、账户测试和迁移目标选择。来源账户仍提供真实上游资源事实，凭据、模型、代理、并发、可用时段和账户追加流式规则缺失或变更会影响授权实例运行时；来源账户被逻辑删除后，来源账户和所有授权实例都会立即隐藏且不可调度，授权关系统一转为回收状态。需要暂停、恢复、回收、归还或限制授权关系时，必须通过授权列表修改授权关系或额度；需要调整被授权侧本地运行态时，只能修改对应授权实例。

### 授权来源表

`resource_authorization_sources` 是当前授权来源表，字段如下：

- `id`
- `authorization_id`
- `source_type`：`manual`、`team`
- `source_team_id`：`source_type = team` 时必填
- `status`：`active`、`superseded`、`revoked`
- `activated_at`
- `ended_at`
- `ended_reason`：例如 `covered_by_team`、`team_revoked`、`member_removed`、`team_disabled`
- `created_by`
- `created_at`
- `updated_at`

约束与原则：

- 同一 `authorization_id` 最多只允许一条 `manual` 来源记录处于 `active` 或 `superseded`。
- 同一 `authorization_id + source_team_id` 同一时间只能有一条有效团队来源。
- 来源表用于说明“为什么有权限”，不是运行时主键，不单独承载统计口径。
- 到期不会删除主记录，只会把主记录切换为 `expired`，并保留来源历史和使用统计。

### 来源优先级与合并规则

- 优先级固定为：`team > manual`。
- 同一资源同一用户原本已有个人来源时，如果后来又被某个团队覆盖：
  - 不创建新的最终用户授权主记录；
  - 原主记录切换为团队来源生效；
  - 原个人来源改为 `superseded`；
  - 历史用量继续挂在同一条 `resource_authorizations.id` 下。
- 如果团队来源已经存在，再创建同一资源同一用户的个人来源：
  - 不让个人来源成为生效来源；
  - 可写入一条 `superseded` 的来源记录或直接返回“已被团队覆盖”的幂等成功；
  - 不保留个人来源作为未来自动回退来源。
- 如果同一资源同一用户同时被多个团队覆盖：
  - 允许存在多条 `active` 团队来源；
  - `effective_source_team_id` 仅保存当前主展示团队，按“最早生效且仍有效”的团队确定；
  - 只要任一团队来源仍有效，最终用户授权继续保持 `active`。
- 当最后一个有效团队来源失效时：
  - 若只剩 `superseded` 个人来源，最终用户授权直接转为 `revoked`；
  - 不自动恢复个人来源，符合“个人源取消”的规则。
- 重新授权同一资源同一用户时，优先重新激活原主记录，并新增新的来源记录。

### 创建、切换与回收流程

#### 个人授权给系统账户

- 若不存在最终用户授权主记录：创建主记录，`effective_source_type = manual`。
- 若存在主记录且当前无有效团队来源：
  - 若已有手动来源且仍有效，按幂等成功处理；
  - 若主记录已回收或已归还，则重新激活同一主记录并恢复手动来源。
- 若存在有效团队来源：不创建新的生效授权，个人来源只能作为被团队覆盖的非生效记录或直接 no-op。

#### 团队授权给系统团队

- 对团队内每个 `active` 成员逐个处理。
- 成员不存在最终授权时：创建主记录和团队来源。
- 成员已有手动来源时：复用主记录，切换 `effective_source_type = team`，手动来源转为 `superseded`。
- 成员已有其他团队来源时：新增当前团队来源；主记录继续保持 `active`。
- 批量生效逻辑必须使用事务，避免同一个团队授权中出现部分成员已生效、部分成员未生效。

#### 回收团队授权或团队成员失效

- 团队授权被回收、团队被停用、成员被移除时，相关团队来源统一改为 `revoked`。
- 如果该用户在该资源上仍有其他 `active` 团队来源，主记录继续 `active`，并切换主展示团队。
- 如果没有任何 `active` 来源剩余，主记录改为 `revoked`。
- 主记录被回收时不删除历史使用记录、来源历史和绑定关系。

#### 重新激活

- 同一资源同一用户后续再次被授权时，优先复用原 `resource_authorizations.id`，并把 `revoked` / `returned` / `expired` 记录恢复为 `active`。
- 已有分组绑定或 API Key 绑定不自动删除；重新激活后可继续复用，未激活期间网关仍必须拦截请求。

### 使用权生效

- 自有资源：调用方是资源归属人时天然可用，不需要授权记录。
- 用户授权：调用方匹配有效 `resource_type + resource_id + grantee_system_account_id` 主记录时可用。
- 团队授权：团队只负责生成或维持用户授权；网关不按团队再判断一次资源权限。
- 有效资源列表必须按 `resource_type + resource_id` 去重；同一资源不因个人来源、多个团队来源或来源切换而重复显示。
- 单行授权 AI 账户只暴露一个稳定的 `authorization_id` 和一个被授权侧实例账户 ID，用于加入被授权用户自己的本地分组并参与网关调度；API Key 可绑定调用方自己的分组，也可绑定有效授权给调用方的分组。
- 绑定关系保存 `authorization_instance_account_id + authorization_id`；来源变化、团队切换和重新激活不改变绑定对象。
- 同一次上游尝试只能写入一条使用记录，不能因为同一用户存在多个来源而写多条记录。
- 上游 AI 账户授权后不再共享同一个运行态 `account_id`：系统会为每个最终被授权用户创建独立授权实例账户。实例拥有自己的 `accounts.status / schedulable / cooldown_until / last_error_* / stream_failure_*`、分组绑定、授权 ID、调度用量和授权用量；凭据、`base_url`、账号类型、模型能力、代理、并发、可用时段和账户追加流式规则从来源账户读取。归属人原账户后续停用、异常、冷却、关闭调度、套餐到期、测试失败或分组变化都不能覆盖或回写该实例；来源账户资源配置变化会同步影响实例运行时，来源账户可用性变化会通过 `effectiveAvailability` 阻断或恢复授权实例的实际可用性。
- 个人 AI 账户授权创建时必须指定目标用户自己的同协议档案启用分组，前端默认选择目标用户在该 `provider_protocol_profile_id` 下的默认分组；授权实例创建后立即加入该目标分组并可调度使用。这只是使用方本地绑定，不改变授权方原账户的分组绑定。被授权人后续通过账户编辑弹窗调整加入分组和分组内优先级；除 OpenAI API Key / OAuth Token 等敏感凭据外，来源账户的 `base_url`、公开 OAuth 元数据、模型、代理、并发、时间计划、账户追加流式规则和来源状态都只读展示。`group_accounts.local_priority / local_super_priority_enabled / local_fallback_enabled` 是当前分组绑定的调度事实，被授权人调整排序、超级优先或降级备用时只影响自己的这条绑定；授权实例的可调度状态、冷却、最近错误和流失败窗口以该实例自己的 `accounts.status / schedulable / cooldown_until / last_error_* / stream_failure_*` 为准。
- 新增个人 AI 账户授权时必须提交目标用户自己的同协议档案启用分组；新增授权表单默认选择目标用户在该协议档案下的默认分组，不能清空后提交。团队 AI 账户授权展开到成员时只使用成员当前已存在且启用的同协议档案默认分组。目标用户缺少对应协议档案默认分组属于当前数据异常，只能按当前 schema 离线修复或重建该用户默认数据，表单、options 和授权写入路径都不自动补建分组。
- 分组授权允许被授权人获得分组使用权；有效授权分组可直接作为被授权人 API Key 的号池。授权暂停、过期、回收、归还或额度不可用时，已有 API Key 绑定配置保留但运行态不可用。
- 授权分组不物化新的分组行；被授权人的本地使用配置由 `group_authorization_settings` 保存，包含本地启用状态、分组类型和高并发调度策略。被授权人从分组页编辑授权分组时只更新该表，网关按 `group_id + 调用方系统账户` 读取本地覆盖后的 `enabled / group_type / scheduling_policy_json`；授权方原 `groups` 行的名称、供应商、说明、启用状态、分组类型和调度策略不被覆盖。
- 分组授权共享的是分组归属人自有账户集合；如果分组里包含其他用户授权来的账户，不能通过分组授权继续传递给第三方。
- 账户页对授权 AI 账户提供普通“编辑”入口；弹窗中只能选择被授权人自己的同协议档案分组并调整分组内优先级，不能修改授权方原账户名称、凭据、代理、并发、模型、账户追加流式规则或备注。后端绑定时必须重新校验用户级授权、分组归属和供应商协议档案一致性。

### 绑定与列表展示

- `授权给我的` 资源列表只展示当前有效资源，不展示被 `superseded` 的个人来源。
- 来源文案展示当前生效来源；需要解释历史时，通过详情页展示来源变更记录。
- 若个人来源被团队覆盖，列表中只显示 `团队授权`，不显示“个人 + 团队”双标签。
- AI 账户列表中的到期时间列对授权账户优先展示最终用户授权的 `expires_at`；授权未设置到期时再展示授权实例自己的 `account_expires_at`。状态标签主口径使用 `effectiveAvailability`：授权到期 / 授权绑定失效显示为授权有效性问题，授权额度耗尽显示“授权额度已用完”；实例被停用、异常、限流或冷却显示实例自己的状态；来源账户停用、异常、冷却、关闭调度、套餐到期、删除或凭据缺失显示为来源侧实际阻断。归属人原账户状态可以影响授权实例实际可用性，但不能覆盖或回写实例 `accounts.status`；授权额度耗尽不能写入任何 `accounts.status`。
- `group_accounts.account_authorization_id` 指向稳定的最终用户授权主记录；API Key 分组绑定仍只保存 `group_id`，该分组可以是调用方自有分组，也可以是有效授权给调用方的分组；运行态按 `group_id + API Key 所属系统账户` 重新校验分组归属或有效授权。
- 当主记录被完全回收或归还时，绑定关系保留但标记为不可用；主记录再次激活后，绑定可恢复可用。

## 授权统计口径

### 使用记录事实字段

`usage_records` 需要同时记录调用方、资源归属和最终用户授权路径：

- `system_account_id`：实际调用方系统账户，即 API Key 所属系统账户。
- `account_owner_system_account_id`：实际命中 AI 账户的归属人。
- `group_owner_system_account_id`：请求使用的分组归属人。
- `account_access_type`：`owner`、`authorized`
- `group_access_type`：`owner`、`authorized`
- `account_authorization_id`：命中授权 AI 账户时写入最终用户授权主记录 ID。
- `group_authorization_id`：命中授权分组时写入最终用户授权主记录 ID。
- `account_authorization_source_type` / `account_authorization_source_team_id`：命中授权 AI 账户时的来源类型和团队快照。
- `group_authorization_source_type` / `group_authorization_source_team_id`：命中授权分组时的来源类型和团队快照。

使用记录保留成功、失败和排障记录；授权消耗统计按进入网关使用记录的请求聚合，失败记录按 0 token、0 cost 计入请求和错误次数。资源归属人自己的自用调用仍按自用处理，不进入授权 ID 维度。

### 展示口径

- 资源归属人的 AI 账户 / 分组“用量情况”展示资源全部总消耗，包含归属人自用和所有被授权用户使用。
- `统一授权` 列表不展示今日用量、范围用量、最后使用或额度摘要，避免把关系管理和消耗报表混在一起。
- 管理侧授权消耗统一进入 `团队消耗明细` 和 `用户消耗明细`；时间筛选按日范围，默认最近 31 天，均不包含归属人自己的自用消耗。
- 用户侧 `我的授权` 下也必须把 `授权操作` 和消耗明细分开；授权操作页不展示今日用量、范围用量、最后使用或额度摘要，授权消耗统一进入同组的 `团队消耗明细` 和 `用户消耗明细`。
- 授权统计主维度是“资源 × 用户”，后台统计 worker 按稳定的 `authorization_id`、调用方、团队来源快照和资源筛选组合增量写入专用日摘要表，并刷新最近 31 天范围窗口。
- 授权消耗明细只读取 `authorization_team_usage_range_windows` 和 `authorization_user_usage_range_windows`，不在页面查询时临时扫描 `usage_records`，也不允许读取缓存后再在接口内二次汇总。
- `团队消耗明细` 和 `用户消耗明细` 必须调用后端明细接口；接口按日范围、授权人、团队、被授权用户和资源筛选直接读取报表窗口行。
- A 授权给 B 时，A 在用户消耗明细看“B 在所选日期范围内在该资源上用了多少”，不区分这部分用量在历史上来自个人来源还是团队来源。
- A 授权给团队时，团队详情本质是该团队曾激活过的成员用户授权集合；展示仍以成员用户为主，不以来源为主。
- 如果 B 先有个人来源，后又被团队覆盖，则 B 在该资源上的范围用户消耗继续合并到同一条用户授权中；团队筛选只看使用记录写入时来源快照属于该团队的消耗。
- 如果 B 后续被移出团队，已经写入团队日摘要 / 范围窗口的历史消耗保留；后续请求不再写入该团队来源。
- 资源归属人只能看授权维度的聚合统计，不直接查看被授权人的请求快照、响应快照、客户端 IP、API Key 明文或业务请求内容。
- 调用方仍可在自己的使用记录里看到自己 API Key 产生的明细，包括使用授权资源产生的请求。使用记录按 AI 账户名称筛选时，授权实例可用来源账户名称命中，分组授权记录可用来源分组内账户名称命中，但结果仍限制在调用方自己的 `usage_records.system_account_id`。

### 重叠授权统计示例

场景：A 把 `001` 账户先直接授权给 B，随后又把 `001` 账户授权给 B 所在的 `XX` 团队。

- B 的 AI 账户列表只出现一个 `001`。
- B 在 `001` 上对应的始终是同一条最终用户授权主记录。
- 团队来源生效后，个人来源被标记为 `superseded`，不再作为生效来源展示。
- B 发起请求时，每次实际上游请求 / 上游尝试写入一条 `usage_records`，授权 ID 始终是 `001 × B` 这条主记录。
- A 在用户消耗明细筛选日期范围时，可以看到 B 在该范围内对 `001` 的消耗。
- A 在用户消耗明细按 `XX` 团队筛选时，看到的是使用记录写入时来源快照属于 `XX` 团队的范围消耗。团队消耗明细只展示 `XX` 团队的汇总总量，行操作可跳转到用户消耗明细并自动带上团队筛选和日期范围。

## 页面设计

### 授权团队页

- 团队列表：团队名称、状态、成员数、描述、创建时间、操作。
- 团队详情：基础信息、成员列表、成员状态、加入时间、移除时间、历史成员标记。
- 创建 / 编辑团队：名称、描述、状态；团队名称必须唯一，不再让用户感知团队编码。
- 成员维护：添加系统账户、移除成员、查看成员状态；系统账户下拉只展示启用或可管理的账号。
- 团队成员变化会影响既有授权覆盖范围，团队详情必须给管理员展示影响提示。
- 系统团队的成员总量、单次添加数量和可展开的有效团队授权数量都固定受限，避免团队越大时管理页、授权展开和成员维护在请求路径上同步线性增长。

### 统一授权页

- 顶部只保留一个搜索框，支持按资源名称、资源 ID、资源归属人、被授权用户、被授权团队和备注前缀检索；授权内容、授权资源、被授权团队、被授权用户、状态等条件统一放入“更多”筛选。
- 授权列表：资源类型、资源名称、资源归属人、被授权的目标、当前生效来源、授权状态、授权时间、说明和操作；目标为团队授权时展示团队名称，为个人授权时展示用户名称，来源标签保持原有个人 / 团队语义。
- 新增授权：用户侧默认以当前登录用户作为授权人；管理侧必须先选择授权人 / 资源归属用户，再从该用户自己的 AI 账户或分组中选择授权内容。之后选择授权对象类型、系统账户或团队、填写备注；选择团队时按成员批量生成或切换用户授权。
- 授权内容和授权对象必须分开表达：`AI 账户 / 分组` 表示授权出去的资源，`个人 / 团队` 表示授权给谁。分组授权表示把整个分组账号池的使用权授权给个人或团队，不代表授权给某个分组。
- 额度限制：新增授权和修改授权配置时可设置 n 小时、日、周、月和总美元成本额度；额度为空表示不限制。
- 暂停授权：二次确认后改为 `paused`，被授权人仍可见但不可用。
- 回收授权：二次确认后把授权业务记录改为 `revoked`，被授权人不可见也不可用，不删除历史行。
- 归还授权：被授权人在授权操作页或授权账户操作里主动归还个人直授权后改为 `returned`，资源归属人仍能在授权列表中看到并重新授权；归还只改变授权关系，不删除授权方原账户，也不作为账户删除的一种形式。授权操作页和账户操作只对个人直授权展示归还，团队授权行或团队来源授权账户不展示个人归还入口。
- `统一授权` / `授权操作` 页不承载用量筛选；管理端和用户端消耗查看都进入各自菜单组下的 `团队消耗明细` 和 `用户消耗明细`。
- 来源详情：展示该用户授权当前来源、历史来源、来源切换时间和原因。
- `授权给我的` 视图：展示当前用户可使用的 AI 账户和分组，以及当前生效来源，便于排查为什么某个资源可见；该视图不提供暂停、回收或修改配置，只对个人直授权提供归还使用权。

### 团队消耗明细页

- 顶部筛选：用量日期范围、被授权团队、资源类型、资源名称；日期范围最大 31 天。
- 列表维度：按被授权团队和资源名称展示，不在该页展开成员。
- 主要列：被授权团队、资源名称、资源归属人、范围消耗、最后使用、操作。
- 行操作 `查询用户明细` 跳转到 `用户消耗明细` 并带上团队筛选、日期范围和资源类型筛选。
- 数据来源：管理侧只调用 `GET /__aisys__/api/authorizations/usage/team-details`，用户侧只调用 `GET /__aisys__/api/my-authorizations/usage/team-details`，由后端按 `page/pageSize` 和筛选条件直读团队范围窗口行和摘要行；页面不再用授权列表结果做本地汇总，不再一次性渲染全量明细，后端接口也不再现场汇总缓存。

### 用户消耗明细页

- 顶部筛选：用量日期范围、被授权团队、被授权用户、授权内容、授权资源；日期范围最大 31 天。
- 列表维度：按最终被授权用户和资源名称展示，包含个人直接授权和被授权团队展开后的成员用户。
- 主要列：被授权用户、资源名称、资源归属人、范围消耗、最后使用。
- 数据来源：管理侧只调用 `GET /__aisys__/api/authorizations/usage/user-details`，用户侧只调用 `GET /__aisys__/api/my-authorizations/usage/user-details`，由后端按 `page/pageSize` 和筛选条件直读用户范围窗口行和摘要行；页面不再用授权列表结果做本地汇总，不再一次性渲染全量明细，后端接口也不再现场汇总缓存。

## 当前接口

- `GET /__aisys__/api/system-teams`：团队摘要列表，仅管理员可读取，用于授权团队管理。
- `GET /__aisys__/api/my-teams`：当前登录用户加入的团队和成员，只读，用于普通用户 `我的授权团队`。
- `POST /__aisys__/api/system-teams`：创建团队，仅管理员。
- `PATCH /__aisys__/api/system-teams/:id`：编辑团队，仅管理员。
- `POST /__aisys__/api/system-teams/:id/members`：添加成员，仅管理员。
- `DELETE /__aisys__/api/system-teams/:id/members/:memberId`：移除成员，仅管理员。
- `GET /__aisys__/api/authorizations`：授权列表，普通用户默认查看自己授权出去或授权给自己的记录，管理员可筛选全部；参数支持 `keyword`、`resourceType`、`resourceId`、`resourceOwnerSystemAccountId`、`granteeSystemAccountId`、`teamId`、`status`、`sourceType`、`page` 和 `pageSize`。
- `GET /__aisys__/api/authorizations/usage/team-details`：管理侧团队消耗明细，参数支持 `startDate=YYYY-MM-DD`、`endDate=YYYY-MM-DD`、`page` 和 `pageSize`，只读团队范围窗口表并分页返回团队行。
- `GET /__aisys__/api/authorizations/usage/user-details`：管理侧用户消耗明细，参数支持 `startDate=YYYY-MM-DD`、`endDate=YYYY-MM-DD`、`page` 和 `pageSize`，只读用户范围窗口表并分页返回用户行。
- `GET /__aisys__/api/my-authorizations/usage/team-details`：用户侧团队消耗明细，忽略 `systemAccountId`，按当前登录用户作为资源归属人分页读取团队范围窗口表。
- `GET /__aisys__/api/my-authorizations/usage/user-details`：用户侧用户消耗明细，忽略 `systemAccountId`，按当前登录用户作为资源归属人分页读取用户范围窗口表。
- `POST /__aisys__/api/authorizations`：新增授权，资源归属人或管理员。管理员管理侧创建时必须通过 `systemAccountId` 明确授权人 / 资源归属用户，不能在“全部系统账户”的模糊范围下创建授权。个人 AI 账户授权必须提交 `targetGroupId`，只能指向被授权用户自己的同协议档案启用分组；新增授权表单默认选择目标用户在该协议档案下的默认分组，不能清空后提交。
- `PATCH /__aisys__/api/authorizations/:id`：修改授权状态、到期时间和额度限制，资源归属人或管理员。
- `DELETE /__aisys__/api/authorizations/:id`：回收授权业务记录，资源归属人或管理员；`:id` 为 `resource_authorization_grants.id`，不接受额外回收来源参数。
- `DELETE /__aisys__/api/my-authorizations/:id/return`：被授权人归还授权使用权；`:id` 为个人直授权业务记录 ID，团队授权业务记录 ID 不作为个人归还入口。授权记录保留并进入 `returned` 状态。
- `POST /__aisys__/api/my-accounts/:id/return-authorization`：被授权人从 AI 账户列表归还个人直授权账户；`:id` 为被授权人自己的授权实例账户 ID。归还后授权实例从被授权人的账户列表、选项和调度路径隐藏，不影响授权方原账户。
- `POST /__aisys__/api/accounts/:id/return-authorization`：管理员按被授权人系统账户作用域代归还个人直授权账户；必须通过 `systemAccountId` 指定被授权人作用域。普通 `DELETE /accounts/:id` 不接受授权实例账户，授权实例账户请使用归还操作。
- `PATCH /__aisys__/api/my-groups/:id`：被授权人编辑授权分组时只允许提交本地 `enabled`、`groupType` 和 `schedulingPolicy`。该操作只影响被授权人自己的授权分组使用配置，不影响授权方原分组；管理员同源接口为 `PATCH /__aisys__/api/groups/:id?systemAccountId=被授权人ID`。
- `POST /__aisys__/api/my-groups/:id/return-authorization`：被授权人从分组列表归还个人直授权分组；`:id` 为授权方原分组 ID。归还后授权分组从被授权人的分组列表、选项、API Key 可绑定号池和调度路径隐藏，不影响授权方原分组。管理员同源代归还接口为 `POST /__aisys__/api/groups/:id/return-authorization?systemAccountId=被授权人ID`。
- `POST /__aisys__/api/accounts/:id/group`：将自有或授权 AI 账户绑定到当前调用方可管理的同协议档案分组；授权账户绑定时记录稳定用户级授权 ID。
- `GET /__aisys__/api/authorizations/:id/usage`：查看某个最终用户授权的聚合用量。
- `GET /__aisys__/api/authorization-options/grantee-accounts`：返回可选择的授权用户最小摘要，不返回系统账户管理字段。
- `GET /__aisys__/api/authorization-options/grantee-teams`：返回可选择的授权团队最小摘要，不返回团队成员明细。
- `GET /__aisys__/api/authorization-options/grantee-groups`：返回指定被授权用户可作为授权账户绑定目标的同协议档案启用分组最小摘要，参数包含 `granteeSystemAccountId`、`providerCode`、`providerProtocolProfileId`、`keyword`、`ids`、`limit` 和 `preferDefault`；用户侧同源接口为 `GET /__aisys__/api/my-authorization-options/grantee-groups`。

## 存储与实现原则

- 授权统一使用 `resource_authorization_grants` + `resource_authorizations` + `resource_authorization_sources`。
- 新增 `system_teams` 和 `system_team_members`。
- `group_accounts` 对授权账户增加可选的 `account_authorization_id`，用于记录加入分组时命中的最终用户授权。
- 当前 API Key 模型不需要额外授权分组绑定字段；新建和编辑 API Key 可以绑定调用方自己的一个或多个分组号池，也可以绑定有效授权给调用方的分组号池。
- `resource_authorization_grants.limits_json` 保存授权操作美元成本额度，人员授权和团队授权通过 `grantee_type` 区分；团队授权来源额度在成员展开或成员后续加入时同步到对应用户级授权。
- 授权创建、团队成员变更、团队停用、授权回收和归还都必须在事务内完成主记录和来源记录更新。
- 对 `resource_type + resource_id + grantee_system_account_id`、`authorization_id + source_team_id`、`team_id + system_account_id` 建立唯一索引或唯一有效性约束，防止重复授权和重复成员。
- 本地库可通过备份后直接 SQL、临时离线脚本或重建库完成调整，运行路径只维护当前表结构。

## 边界条件清单

| 场景 | 处理规则 |
| --- | --- |
| 先个人后团队 | 复用同一条最终用户授权，切换生效来源到团队，个人来源改为 `superseded`，历史用量不拆分。 |
| 先团队后个人 | 个人来源不能成为生效来源；可记为 `superseded` 或幂等成功，不作为自动回退来源。 |
| 多个团队覆盖同一用户 | 允许多条团队来源同时有效；最终用户授权只保留一条主记录。 |
| 回收其中一个团队来源 | 只移除该团队来源；若仍有其他团队来源，授权继续有效。 |
| 最后一个团队来源失效 | 最终用户授权直接回收；不会自动恢复被覆盖的个人来源。 |
| 团队成员被移除 | 当前调用立即失效；历史消耗保留，团队详情中成员标记为已移除。 |
| 团队被停用 | 等价于回收该团队的全部团队来源；不删除历史统计。 |
| 系统账户被停用 | 最终用户授权主记录可保留 `active`，但运行时必须拦截。 |
| 授权方原 AI 账户被停用或删除 | 停用、异常、冷却、关闭调度和测试失败不改变也不回写已创建的授权实例账户本地状态，但会通过 `effectiveAvailability` 阻断实际调度、账户测试和迁移目标选择；来源账户被删除时只先逻辑删除来源账户和所有授权实例，立即隐藏并阻断调度，同时把该资源对应的授权操作记录和运行时授权标记为已回收，不能继续显示为“生效中”。一个月后的物理清理任务再删除账户、授权、绑定、历史记录和统计缓存。 |
| 分组包含他人授权来的账户 | 该账户不能通过分组授权继续下发，防止授权穿透。 |
| 同一次上游尝试命中多个来源 | 只认最终用户授权主记录，只写一条使用记录。 |
| 回收或归还后重新授权 | 优先复用原最终用户授权 ID，已有绑定可恢复使用。 |
| 授权额度命中 | 网关返回 429 和“额度已用完，请联系管理员提升额度”；额度判断读取统计缓存，允许统计延迟导致轻微超额。 |
| 团队授权额度 | 直接读取 worker 写入的 `account_authorization_team` / `group_authorization_team` 作用域缓存判断团队总美元成本额度；账号授权团队 scope 使用授权实例账户 ID，成员用户级授权仍保留各自额度限制，网关请求路径不枚举成员求和。 |

## 当前能力清单

- 管理员可以创建、编辑、启停团队，并维护团队成员和成员状态。
- 同一资源同一用户全生命周期只存在一条稳定的最终用户授权主记录。
- 资源所有者可以在统一授权里把自有 AI 账户或分组授权给系统账户或系统团队。
- 团队授权进入后，同一资源同一用户若已有个人来源，系统切换为团队来源生效，个人来源取消但历史用量继续合并。
- 同一用户同时命中多个团队来源时，前端列表、接口结果和网关调度都只出现一个有效资源。
- 被授权系统账户或团队成员只能使用资源，不能编辑来源资源、删除授权方原资源、查看敏感凭据或继续转授权；授权 AI 账户实例不能被删除，不想继续使用个人直授权时只能走归还授权入口。
- 团队成员新增、移除、团队停用、系统账户停用和授权回收 / 归还都能实时影响网关调度。
- 绑定到授权账户的本地分组关系在来源切换后仍保持稳定，不要求重复绑定；新增个人 AI 账户授权可直接指定目标用户分组，默认使用目标用户默认分组；API Key 入口同时接受调用方自有分组和有效授权给调用方的分组。
- 团队消耗明细展示每个被授权团队总消耗；行操作可跳转用户消耗明细并带上团队筛选。
- 用户消耗明细按“资源 × 用户”统计到最终用户，并能按被授权团队筛选成员用户消耗，且不包含资源归属人自用消耗。
- 授权管理新增和修改配置时可设置美元成本额度；网关命中用户级或团队级授权额度后返回“额度已用完，请联系管理员提升额度”。
- AI 账户授权实例的账户用量和授权额度按被授权实例所属系统账户聚合；授权方查看对外授权消耗时使用团队 / 用户消耗明细。
- 使用记录页只展示调用方自己的明细，资源所有者不能查看被授权人的请求快照和业务内容。
