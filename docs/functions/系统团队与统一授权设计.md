# 系统团队与统一授权设计

> **状态：2026-11-21 本地同步，待统一上线验证。** 本文保留 `system_teams` / `system_team_members` 的团队管理契约、授权统计口径、页面与团队接口。授权生命周期、接收方确认、所有者确认、目标分组绑定、团队成员级 offer、来源 material change 与来源优先级，以 [授权接收方确认与来源治理设计](授权接收方确认与来源治理设计.md) 为权威；本文不再保留“单方面即时生效”“自动加入目标分组”“团队来源永久覆盖个人”等旧语义。

## 文档定位

本文定义 `juhe-ai` 的授权团队（底层为系统团队）和统一授权中心的团队侧契约。授权相关入口、统计和来源说明收敛到管理侧 `统一授权管理` 和用户侧 `我的授权` 菜单，不再沿用“账户页里管账户授权、分组页里管分组授权”的分散入口。

命名边界：代码、存储和接口实体仍称 `系统团队`；前端菜单在授权场景中显示为 `授权团队` / `我的授权团队`。两者指向同一套 `system_teams` / `system_team_members` 模型，不代表两套团队体系。

## 目标

- 管理侧 `统一授权管理` 下提供 `授权团队` 菜单，用团队把多个系统账户归纳在一起。
- 资源所有者可以把 AI 账户或分组授权给某个系统账户，也可以向某个系统团队发起团队 offer。
- 团队只是批量授权来源，不是运行时最终授权主体；最终有效授权只绑定到具体系统账户。
- 授权统计唯一主维度统一为“资源 × 用户”，授权方只关心“这个用户在这个资源上消耗了多少”。
- 团队来源与个人来源可以并存：团队生效时个人来源进入 `dormant`，团队结束后按接收方接受时的选择回退；不再永久取消个人来源。
- 授权只代表使用权，不代表编辑权、删除权、凭据查看权、成员管理权或二次授权权。

## 核心结论

- 最终可用资源始终绑定到 `grantee_system_account_id`，不绑定团队。
- 同一 `resource_type + resource_id + grantee_system_account_id` 全生命周期只保留一条稳定的最终用户授权主记录。
- 团队 offer 必须经团队审批人同意后，才展开为成员级 pending 来源；成员逐人接受后才创建实例或分组快照，**不会自动加入任何成员的分组**。
- 资源所有者不能把自己的 AI 账户或分组授权给自己；团队展开时也不能为资源归属人成员生成最终用户授权。
- 团队停用、团队逻辑删除或成员移除时，撤销对应的非终态团队来源；重新启用团队不复活旧同意，必须重新发起并重新接受。
- 网关调度只读取最终用户授权主记录、来源状态、授权范围快照、绑定关系和额度缓存；团队成员变化在业务写入阶段维护来源和运行时状态。
- 历史使用记录以稳定的用户授权聚合，来源变化、团队变化和重新接受不会拆散同一用户在同一资源上的历史消耗。

## 核心术语

| 术语 | 含义 |
| --- | --- |
| 系统账户 | 后台登录账号，是 API Key、调用日志和业务数据的默认隔离边界。 |
| 授权团队 | 多个系统账户的集合，用于批量承接授权使用权。底层仍使用系统团队数据模型；在授权对象、筛选和统计列语境中可显示为“被授权团队”。 |
| 资源 | 可被授权使用的对象，当前支持 `AI 账户` 和 `分组`。 |
| 最终用户授权 | 某个资源授权给某个系统账户的稳定运行时关系，是运行时唯一看的授权主体。 |
| 授权来源 | 最终用户授权为什么成立。当前支持 `manual`（个人）和 `team`（团队）。 |
| 团队审批人 | `system_teams.created_by`；失效、缺失或与授权方为同一账户时，由 `super_admin` / `admin` 代行。 |
| 成员 offer | 团队审批通过后，为团队成员创建的 pending 来源；成员只能处理自己的成员 offer。 |
| 调用方 | 实际发起网关请求的 API Key 所属系统账户。 |
| 资源归属人 | AI 账户或分组的真实所有者。 |
| 授权消耗 | 调用方不是资源归属人时，通过授权产生的请求、Token 和成本。 |

## 授权团队管理

### 菜单与权限

- 管理侧菜单名称为 `授权团队`，挂在 `统一授权管理` 下。
- 当前菜单仅 `super_admin` / `admin` 可见，用于创建授权团队、编辑团队资料、启停团队和维护成员。
- 普通 `user` 不进入管理侧授权团队页；用户侧可在 `我的授权团队` 只读查看自己加入的团队和成员。
- 团队审批人可以在 `授权中心 -> 团队审批` 查看和处理自己团队的 pending offer；普通成员只能看到自己的成员 offer，不能审批团队 offer。
- 管理员可以在 `统一授权 -> 团队审批` 查看全部团队 offer，但只能在审批人失效、缺失或与授权方为同一账户时代行审批；代行写操作日志并通知团队审批人。

### 团队字段

- `id`
- `name`：团队名称，页面主展示字段，活跃团队全局唯一。
- `description`
- `status`：`active`、`disabled`；逻辑删除时写 `deleted_at` 并置 `deleted`，历史行保留。
- `created_by`：团队审批人。
- `created_at` / `updated_at`
- `deleted_at`：逻辑删除时间；非空团队不参与列表、精确名匹配、审批和成员维护。

### 成员字段

- `id`
- `team_id`
- `system_account_id`
- `member_role`：当前固定为 `member`，后续可扩展 `manager`。
- `status`：`active`、`removed`
- `joined_at`
- `removed_at`
- `created_by`
- `created_at` / `updated_at`

### 团队与成员规则

- 同一团队内同一系统账户同一时间只能有一条有效成员关系。
- 同一系统账户允许同时属于多个团队。
- 单团队有效成员上限 20；单次添加成员上限 20；团队名称 1-100 字符，说明最多 200 字符。
- 团队名称搜索只按名称精确 / 前缀匹配，不搜索 ID 或说明。
- 团队列表、基础详情、成员页和历史成员页分开按需读取；列表不预取成员数组。
- 团队字段、成员添加和成员移除都使用 `expectedUpdatedAt` CAS；冲突返回 `409`，no-op 不推进版本。
- 系统账户被停用后，即使仍在团队中，也不能通过团队授权继续调用。

### 团队生命周期与授权级联

- 团队停用：撤销该团队全部非终态 team 来源，并把对应 team grant 置 `revoked`（`ended_reason=team_disabled`）；已终态来源和 grant 保持原状。
- 团队重新启用：只恢复团队本身的可审批状态，**不复活**已撤销的团队来源或成员同意；需要资源所有者重新发起团队 offer。
- 团队成员移除：撤销该成员在该团队下所有非终态 team 来源（`ended_reason=member_removed`），按来源回退规则重算 runtime；其他成员和团队 grant 不受影响。
- 团队新增成员：只为仍处于 `pending_member_acceptance` / `active` / `paused` 的团队 grant 创建 pending 成员来源，不创建实例、快照或绑定；成员接受后自行绑定。
- 团队逻辑删除：先撤销全部非终态 team 来源和团队 grant，再写 `deleted_at`；成员行保留为历史，不物理删除授权来源、快照或统计。当前管理端仅提供启停，删除入口未暴露；删除契约保留给后续管理动作。
- 团队审批人失效、缺失或与授权方为同一账户时，管理员可代行团队审批；团队审批人有效时管理员不得越权代行。

## 统一授权中心

> 完整状态机、接口、权限矩阵、迁移和验收标准见 [授权接收方确认与来源治理设计](授权接收方确认与来源治理设计.md)。本节只保留与团队和统计相关的现行口径。

### 信息架构

- 用户侧 `我的授权`：`授权中心`（收到的授权、我发出的授权、我的资源授权、待我确认、团队审批、屏蔽列表、通知）、`团队消耗明细`、`用户消耗明细`、`我的授权团队`。
- 管理侧 `统一授权管理`：`统一授权`（全部业务记录、团队审批、屏蔽记录）、`团队消耗明细`、`用户消耗明细`、`授权团队`。
- `授权中心` / `统一授权` 只负责授权关系和来源状态，不展示消耗统计列；消耗进入同组的团队 / 用户消耗明细。
- AI 账户页和分组页不再放“授权管理”弹窗，只展示资源来源、所有者摘要和当前登录用户的权限摘要。

### 模型分层

统一授权拆成三层：

1. `resource_authorization_grants`：授权业务主表，表达“某资源拟授权给哪个业务目标”，目标可以是系统账户或团队。
2. `resource_authorizations`：最终用户授权运行时表，表达“某资源最终授权给某系统账户”；同一资源同一用户全生命周期一条。
3. `resource_authorization_sources`：来源表，表达这条运行时授权当前或历史上因何成立，以及接收方是否已接受当前来源修订。

授权操作列表、新增、暂停、恢复、回收和配置修改以 `resource_authorization_grants` 为准；运行时、资源列表、分组绑定、API Key 绑定和授权统计以 `resource_authorizations` 为准；来源状态与来源修订以 `resource_authorization_sources` 为准。

### 来源优先级与合并规则

- 同一 runtime 可以同时存在 `manual` 和 `team` 来源；团队来源生效时，保留的个人来源进入 `dormant`，不是永久删除。
- 团队来源结束后，若接收方在成员 offer 接受时选择保留个人回退，且个人来源仍有效，则个人来源恢复为生效来源；否则 runtime 按最近终态进入 `returned` / `declined` / `expired` / `revoked`。
- 接收方显式选择“不保留个人回退”时，团队来源结束后不得静默恢复个人来源。
- 多个团队来源同时有效时，runtime 选择生效团队来源；具体排序与终态推导以新设计 §4.4 为准。
- 来源切换不拆散历史统计：同一 runtime 的历史消耗继续归并到“资源 × 用户”。

### 创建、审批、接受与回收

- 个人 offer：资源所有者按精确用户名发起，接收方 `pending`；管理员代资源所有者发起时进入 `pending_owner_approval`，所有者确认后才对接收方可见。
- 团队 offer：资源所有者按精确团队名发起，进入 `pending_team_approval`；团队审批人同意后进入 `pending_member_acceptance`，并为每个符合条件成员创建 pending 来源。
- 成员接受成员 offer 后才创建授权实例或分组快照；接受不自动绑定分组，分组授权还需要接收方显式启用。
- 团队审批通过但没有可发送成员时，grant 保持 `pending_member_acceptance` 直到 `TeamMemberlessTTL` 或到期，不因空集立即终态。
- 资源所有者可以暂停、恢复、延长、缩短、修改额度或回收非终态 grant；暂停期间不得重新邀请或延长。
- 接收方可以拒绝、归还或屏蔽来源；团队来源的归还是成员自己的成员 offer，不是团队业务记录。管理员不能用“归还”代替接收方表达同意，只能回收。
- 来源账户发生 material change 时，账户来源进入 `needs_review`，网关硬阻断；接收方携带 `expectedRevision` 重新确认后才恢复。分组资源新增账户不自动进入已接受快照，必须显式刷新范围并逐账户确认修订变化。

### 使用权生效与绑定

- 接收方接受账户来源后，授权实例存在但 `group_accounts` 仍为空；接收方需要在自己的账户页把实例加入自己的分组后才参与调度。
- 接收方接受分组来源后，分组快照存在但 `group_authorization_settings.enabled=0`；接收方需要在授权中心启用授权分组，再在自己的路由策略中引用。
- 授权方和管理员都不能代替接收方绑定账户或启用/停用授权分组。
- 授权账户和授权分组只能绑定到接收方自己的分组和路由策略；所有通用账户、分组和路由策略写入路径都重复校验 runtime active、来源修订和绑定归属。
- 归还、拒绝、屏蔽或团队来源撤销只有在 runtime 进入终态时才关闭绑定；runtime 仍有其他有效来源时保留绑定，由网关按当前有效来源重算。

## 授权统计口径

### 使用记录事实字段

`usage_records` 同时记录调用方、资源归属和最终用户授权路径：

- `system_account_id`：实际调用方系统账户，即 API Key 所属系统账户。
- `account_owner_system_account_id`：实际命中 AI 账户的归属人。
- `group_owner_system_account_id`：请求使用的分组归属人。
- `account_access_type`：`owner`、`authorized`
- `group_access_type`：`owner`、`authorized`
- `account_authorization_id`：命中授权 AI 账户时写入最终用户授权主记录 ID。
- `group_authorization_id`：命中授权分组时写入最终用户授权主记录 ID。
- `account_authorization_source_type` / `account_authorization_source_team_id`：命中授权 AI 账户时的来源类型和团队快照。
- `group_authorization_source_type` / `group_authorization_source_team_id`：命中授权分组时的来源类型和团队快照。

使用记录保留成功、失败和排障记录；授权消耗统计按进入网关使用记录的请求聚合，失败记录按 0 token、0 cost 计入请求和错误次数。资源归属人自己的自用调用仍按自用处理，不进入授权 ID 维度。

### 展示口径

- 资源归属人的 AI 账户 / 分组“用量情况”展示资源全部总消耗，包含归属人自用和所有被授权用户使用。
- `授权中心` / `统一授权` 列表不展示今日用量、范围用量、最后使用或额度摘要，避免把关系管理和消耗报表混在一起。
- 管理侧授权消耗统一进入 `团队消耗明细` 和 `用户消耗明细`；时间筛选按日范围，默认最近 31 天，均不包含归属人自己的自用消耗。
- 用户侧 `我的授权` 下同样把 `授权中心` 和消耗明细分开；授权消耗进入同组的 `团队消耗明细` 和 `用户消耗明细`。
- 授权统计主维度是“资源 × 用户”，后台统计 worker 按稳定的 `authorization_id`、调用方、来源快照和资源筛选组合增量写入专用日摘要表（约 60 秒节拍）。
- 授权消耗明细接口按日范围直接聚合 `authorization_team_usage_summary_daily` 和 `authorization_user_usage_summary_daily`，31 天窗口内任意自定义日期区间均可出数；不在页面查询时临时扫描 `usage_records`。
- `团队消耗明细` 和 `用户消耗明细` 必须调用后端明细接口；接口按日范围、授权人、团队、被授权用户和资源筛选现场聚合报表日摘要行。
- A 授权给 B 时，A 在用户消耗明细看“B 在所选日期范围内在该资源上用了多少”，不区分这部分用量在历史上来自个人来源还是团队来源。
- A 授权给团队时，团队详情本质是该团队曾激活过的成员用户授权集合；展示仍以成员用户为主，不以来源为主。
- 如果 B 先有个人来源，后又被团队覆盖，B 在该资源上的范围消耗继续合并到同一条用户授权中；团队筛选只看使用记录写入时来源快照属于该团队的消耗。
- 如果 B 后续被移出团队，已经写入团队日摘要的历史消耗保留；后续请求不再写入该团队来源。
- 资源归属人只能看授权维度的聚合统计，不直接查看被授权人的请求快照、响应快照、客户端 IP、API Key 明文或业务请求内容。
- 调用方仍可在自己的使用记录里看到自己 API Key 产生的明细，包括使用授权资源产生的请求；结果仍限制在调用方自己的 `usage_records.system_account_id`。

### 重叠授权统计示例

场景：A 把 `001` 账户先直接授权给 B，随后又把 `001` 账户授权给 B 所在的 `XX` 团队。

- B 的 AI 账户列表只出现一个 `001`。
- B 在 `001` 上对应的始终是同一条最终用户授权主记录。
- 团队来源生效后，个人来源进入 `dormant`；团队来源结束后，按 B 接受时是否保留个人回退决定是否恢复。
- B 发起请求时，每次实际上游请求 / 上游尝试写入一条 `usage_records`，授权 ID 始终是 `001 × B` 这条主记录。
- A 在用户消耗明细筛选日期范围时，可以看到 B 在该范围内对 `001` 的消耗。
- A 在用户消耗明细按 `XX` 团队筛选时，看到的是使用记录写入时来源快照属于 `XX` 团队的范围消耗。团队消耗明细只展示 `XX` 团队的汇总总量，行操作可跳转到用户消耗明细并自动带上团队筛选和日期范围。

## 页面设计

### 授权团队页

- 团队列表：团队名称、状态、成员数、描述、创建时间、操作。
- 团队基础详情和成员集合分开按需读取；列表与基础详情不携带成员数组，只有打开成员弹窗时才读取当前有效成员的 `id`、系统账户、展示名称和加入时间。
- 创建 / 编辑团队：名称、描述、状态；团队名称必须唯一，不让用户感知团队编码。
- 成员维护：添加系统账户、移除成员、查看成员状态；系统账户下拉只展示启用或可管理的账号。
- 团队成员变化会影响既有授权覆盖范围，团队详情必须给管理员展示影响提示。
- 团队审批信息展示 `created_by`；管理员可在这里查看团队的待审批 offer 并跳转授权中心处理。

### 授权中心页

- 用户侧页签：收到的授权、我发出的授权、我的资源授权、待我确认、团队审批、屏蔽列表；顶部显示待确认、需复核、待审批和所有者待确认计数。
- 管理侧页签：全部业务记录、团队审批、屏蔽记录；不展示接收方分组。
- 收到的授权按来源行展示资源、来源账户/团队、状态、endpoint host、代理摘要、模型数、到期、绑定/启用状态和可执行动作。
- 待确认来源提供“查看并接受 / 拒绝 / 屏蔽”；需复核来源展示字段级变更摘要和“重新接受”；账户来源未绑定时提供“去绑定分组”，分组来源提供“启用/停用分组”和“查看范围”。
- 发起授权：用户侧直接输入精确用户名或精确团队名；管理侧先选择资源所有者，再从该所有者自己的资源中选择；不再显示目标分组，也不再加载全量用户/团队下拉。
- 所有者确认：`待我确认` 展示管理员代建 offer，所有者为自己的资源提供“同意以我名义授权 / 拒绝”。
- 团队审批：审批人看到资源、来源账户、供应商、endpoint host、额度、成员数和接受/拒绝聚合；看不到成员个人分组或个体拒绝原因。
- 通知：顶部通知入口展示未读数和通知列表，支持标记已读；通知不替代来源状态和待办计数。
- 屏蔽记录：用户可解除自己的屏蔽；管理员可在管理侧查看屏蔽记录用于滥用调查，不展示给团队审批人。
- 系统账户页：管理员可查看和切换“暂停发起授权/解除暂停”，并显示暂停时间与原因。

### 团队消耗明细页

- 顶部筛选：用量日期范围、被授权团队、资源类型、资源名称；日期范围最大 31 天。
- 列表维度：按被授权团队和资源名称展示，不在该页展开成员。
- 主要列：被授权团队、资源名称、资源归属人、范围消耗、最后使用、操作。
- 行操作 `查询用户明细` 跳转到 `用户消耗明细` 并带上团队筛选、日期范围和资源类型筛选。
- 数据来源：管理侧并行调用 `GET /__aisys__/api/authorizations/usage/team-details` 与 `team-summary`，用户侧调用对应 `my-authorizations` 接口；rows 只读分页明细窗口，summary 精确读取一条汇总窗口，互不阻塞。

### 用户消耗明细页

- 顶部筛选：用量日期范围、被授权团队、被授权用户、授权内容、授权资源；日期范围最大 31 天。
- 列表维度：按最终被授权用户和资源名称展示，包含个人直接授权和被授权团队展开后的成员用户。
- 主要列：被授权用户、资源名称、资源归属人、范围消耗、最后使用。
- 数据来源：管理侧并行调用 `GET /__aisys__/api/authorizations/usage/user-details` 与 `user-summary`，用户侧调用对应 `my-authorizations` 接口；rows 只读分页明细窗口，summary 精确读取一条汇总窗口，互不阻塞。

## 当前接口

团队管理：

- `GET /__aisys__/api/system-teams` / `GET /__aisys__/api/my-teams`：分页返回当前页面渲染字段和 `updatedAt`，不返回成员数组；管理侧读取全部可管理团队，用户侧只读当前用户加入的团队。
- `GET /__aisys__/api/system-teams/:id` / `GET /__aisys__/api/my-teams/:id`：返回团队基础详情、成员数和版本，不返回成员数组。
- `GET /__aisys__/api/system-teams/:id/members` / `GET /__aisys__/api/my-teams/:id/members`：按需返回 `{ id, memberCount, updatedAt, items }`。
- `GET /__aisys__/api/system-teams/:id/members/history` / `GET /__aisys__/api/my-teams/:id/members/history`：按需分页读取已移除成员，默认和上限均为 20 条。
- `POST /__aisys__/api/system-teams`：创建团队，仅管理员；返回可合并到列表的轻量行。
- `PATCH /__aisys__/api/system-teams/:id`：编辑团队，仅管理员；只提交变化字段和 `expectedUpdatedAt`，只返回 `{ id, changedFields, rowPatch, updatedAt }`。
- `POST /__aisys__/api/system-teams/:id/members`：添加成员，仅管理员；提交目标用户 ID 与 `expectedUpdatedAt`，只返回 `{ id, memberCount, updatedAt, addedMembers }`。
- `DELETE /__aisys__/api/system-teams/:id/members/:memberId`：移除成员，仅管理员；请求体提交 `expectedUpdatedAt`，只返回 `{ id, memberCount, updatedAt, removedMemberId }`。
- 团队字段和成员写入都使用作用域内 CAS；冲突返回 `409`，只有实际变更才推进版本、写操作日志、展开或撤销授权并失效相关缓存。

团队审批与授权治理：

- `GET /__aisys__/api/my-teams/:teamId/authorization-offers`
- `POST /__aisys__/api/my-teams/:teamId/authorization-offers/:grantId/approve`
- `POST /__aisys__/api/my-teams/:teamId/authorization-offers/:grantId/decline`
- 管理侧同源端点：`GET /__aisys__/api/system-teams/:teamId/authorization-offers` 及 approve/decline。
- 完整授权中心、来源、绑定、范围、屏蔽、通知、暂停/延长/回收、所有者确认和字段可见性接口见 [授权接收方确认与来源治理设计](授权接收方确认与来源治理设计.md) §6 与 [接口契约与权限矩阵](接口契约与权限矩阵.md)。

消耗明细：

- `GET /__aisys__/api/authorizations/usage/team-details` / `user-details`
- `GET /__aisys__/api/authorizations/usage/team-summary` / `user-summary`
- `GET /__aisys__/api/my-authorizations/usage/team-details` / `user-details`
- `GET /__aisys__/api/my-authorizations/usage/team-summary` / `user-summary`

## 存储与实现原则

- 团队使用 `system_teams` + `system_team_members`；逻辑删除列 `deleted_at` 由 schema revision 28 增加。
- 授权统一使用 `resource_authorization_grants` + `resource_authorizations` + `resource_authorization_sources`。
- 授权账户通过 `group_accounts.account_authorization_id` 记录加入绑定时命中的最终用户授权；授权分组通过 `resource_authorization_group_accounts` 记录范围快照，通过 `group_authorization_settings.enabled` 控制启用。
- `resource_authorization_grants.limits_json` 保存授权美元成本额度；额度随来源和 runtime 同步到成员用户，不从团队成员列表现算。
- 授权创建、审批、接受、来源变更、团队停用、成员变更、回收和归还都必须在事务内完成主记录、来源和 runtime 更新。
- 对 `resource_type + resource_id + grantee_system_account_id`、`authorization_id + source_team_id`、`team_id + system_account_id` 建立唯一索引或唯一有效性约束，防止重复授权和重复成员。
- 团队、账户、来源和 runtime 的授权域外键使用 `RESTRICT`；团队/账户逻辑删除不得级联删除授权历史。

## 边界条件清单

| 场景 | 处理规则 |
| --- | --- |
| 先个人后团队 | 复用同一条最终用户授权；团队来源生效时个人来源进入 `dormant`，历史用量不拆分。 |
| 先团队后个人 | 个人来源可以单独接受；团队来源仍有效时按来源优先级决定生效来源，不把个人来源永久取消。 |
| 多个团队来源 | 允许多条团队来源同时有效；runtime 只保留一条主记录和一个生效来源。 |
| 团队审批通过但无成员 | grant 保持 `pending_member_acceptance`，直到 `TeamMemberlessTTL` 或到期，不立即终态。 |
| 成员拒绝或归还 | 只影响该成员的团队来源；其他成员和团队 grant 不受影响。 |
| 团队成员被移除 | 该成员团队来源撤销并重算 runtime；历史消耗保留。 |
| 团队被停用 | 撤销全部非终态团队来源；重新启用不复活旧同意。 |
| 系统账户被停用 | runtime 可保留，但网关和团队审批必须拦截该账户。 |
| 授权方原账户被停用或删除 | 来源进入不可用/撤销路径，接收方不再调度；历史授权、快照和统计保留。 |
| 分组包含他人授权来的账户 | 该账户不能通过分组授权继续下发，防止授权穿透。 |
| 同一次上游尝试命中多个来源 | 只认最终用户授权主记录，只写一条使用记录。 |
| 归还或拒绝后重新授权 | 重新发起新的来源，接收方重新接受后仍需自行绑定/启用；旧绑定不自动复活。 |
| 授权额度命中 | 网关返回 429 和“额度已用完，请联系管理员提升额度”；额度判断读取统计缓存，允许轻微超额。 |

## 当前能力清单

- 管理员可以创建、编辑、启停团队，并维护团队成员和成员状态。
- 团队审批人可以查看并审批团队 offer；团队成员可以逐人接受、拒绝、归还或屏蔽自己的成员 offer。
- 资源所有者可以发起个人或团队 offer、确认管理员代建 offer、暂停/恢复/延长/回收授权、查看来源接受计数和聚合消耗。
- 接收方可以接受或重新确认来源、查看来源详情、绑定账户分组、启用/停用授权分组、刷新分组范围和逐账户确认修订变化。
- 同一资源同一用户全生命周期只存在一条稳定的最终用户授权主记录；同一用户同时命中多个团队来源时只出现一个有效资源。
- 被授权用户不能修改来源凭据、`base_url`、供应商/协议、模型映射或代理；只能修改授权实例的本地调度与绑定字段。
- 团队成员新增、移除、团队停用、系统账户停用、来源 material change 和授权回收 / 归还都能实时影响网关调度。
- 团队消耗明细展示每个被授权团队总消耗；行操作可跳转用户消耗明细并带上团队筛选。
- 用户消耗明细按“资源 × 用户”统计到最终用户，并能按被授权团队筛选成员用户消耗，且不包含资源归属人自用消耗。
- AI 账户授权实例的账户用量和授权额度按被授权实例所属系统账户聚合；授权方查看对外授权消耗时使用团队 / 用户消耗明细。
- 使用记录页只展示调用方自己的明细，资源所有者不能查看被授权人的请求快照和业务内容。
