# 系统团队与统一授权设计

## 文档定位

本文定义 `juhe-ai` 新版系统团队与统一授权中心。后续不再沿用“账户页里管账户授权、分组页里管分组授权”的分散入口；授权相关入口、统计、撤销和来源说明统一收敛到授权管理菜单。

当前项目未正式上线，本地 SQLite 数据可以备份后直接重建或清洗，因此本方案按新版完整模型设计，统一使用当前表结构，不保留旧 `account_authorizations` / `group_authorizations` 分支。

源码规则：后端启动、repository、routes 和前端页面都不能长期保留一次性迁移、旧数据兼容、临时同步修复或迁移标记代码；本地旧库问题通过直接操作数据库、临时离线脚本或重建库解决。

## 目标

- 新增 `系统团队管理` 菜单，用团队把多个系统账户归纳在一起。
- 资源所有者可以把 AI 账户或分组授权给某个系统账户，也可以直接授权给某个系统团队。
- 团队只是批量授权来源，不是运行时最终授权主体；最终有效授权只绑定到具体系统账户。
- 授权统计唯一主维度统一为“资源 × 用户”，授权方只关心“这个用户在这个资源上消耗了多少”。
- 同一用户在同一资源上同时出现个人来源和团队来源时，以团队来源为准；个人来源取消，但历史用量继续合并到同一条最终用户授权。
- 授权只代表使用权，不代表编辑权、删除权、凭据查看权、成员管理权或二次授权权。

## 核心结论

- 最终可用资源始终绑定到 `grantee_system_account_id`，不绑定团队。
- 同一 `resource_type + resource_id + grantee_system_account_id` 全生命周期只保留一条稳定的最终用户授权主记录。
- 团队授权进入系统后，作用是“创建或激活用户授权来源”，而不是在网关运行时再参与一层团队判断。
- 团队来源优先级高于个人来源；当团队来源覆盖个人来源时，系统切换同一条用户授权的生效来源，不新建第二条最终授权。
- 历史使用记录以稳定的 `user authorization` 聚合，因此来源变化、团队变化和重新激活不会拆散同一用户在同一资源上的历史消耗。

## 核心术语

| 术语 | 含义 |
| --- | --- |
| 系统账户 | 后台登录账号，是 API Key、调用日志和业务数据的默认隔离边界。 |
| 系统团队 | 多个系统账户的集合，用于批量承接授权使用权。 |
| 资源 | 可被授权使用的对象，第一阶段支持 `AI 账户` 和 `分组`。 |
| 最终用户授权 | 某个资源授权给某个系统账户的最终有效关系，是运行时唯一看的授权主体。 |
| 授权来源 | 最终用户授权为什么成立。第一阶段支持 `个人来源` 和 `团队来源`。 |
| 调用方 | 实际发起网关请求的 API Key 所属系统账户。 |
| 资源归属人 | AI 账户或分组的真实所有者。 |
| 授权消耗 | 调用方不是资源归属人时，通过授权产生的请求、Token 和成本。 |

## 系统团队管理

### 菜单与权限

- 新增菜单：`系统团队管理`。
- 第一阶段菜单仅 `admin` 可见，用于创建团队、编辑团队资料、启停团队和维护成员。
- 普通 `user` 不进入团队管理页，但在统一授权管理里可以读取团队摘要并选择有效团队作为授权对象。
- 管理员可以查看所有团队和成员；资源所有者在授权详情里只能看到与自己授权相关的团队及成员消耗明细。

### 团队字段

- `id`
- `name`：团队名称，页面主展示字段，全局唯一。
- `description`
- `status`：`active`、`disabled`
- `created_by`
- `created_at` / `updated_at`

### 成员字段

- `id`
- `team_id`
- `system_account_id`
- `member_role`：第一阶段固定为 `member`，后续可扩展 `manager`。
- `status`：`active`、`removed`
- `joined_at`
- `removed_at`
- `created_by`
- `created_at` / `updated_at`

### 团队与成员规则

- 同一团队内同一系统账户同一时间只能有一条有效成员关系。
- 同一系统账户允许同时属于多个团队。
- 团队和成员默认采用软状态管理；有历史授权或历史消耗时不做硬删除。
- 停用团队后，该团队不能再作为新增授权对象；该团队现有团队来源立即失效，但历史授权和历史统计保留。
- 移除成员后，该成员不再通过该团队来源获得资源使用权；已有 API Key 或分组绑定在网关调度时应被实时拦截。
- 新增成员后，如果团队仍有有效团队授权来源，系统应为该成员补齐对应最终用户授权或重新激活已有授权。
- 系统账户被停用后，即使仍在团队中，也不能通过团队授权继续调用。
- 团队详情必须展示当前成员状态，并保留历史已移除成员标记，便于解释历史授权消耗。

## 统一授权中心

### 菜单定位

- 新增菜单：`授权管理`。
- 所有授权新增、查看、撤销、统计入口都从该菜单进入。
- AI 账户页和分组页不再放“授权管理”弹窗，只展示资源来源、所有者摘要和当前登录用户的权限摘要。

### 模型分层

统一授权拆成两层：

1. `resource_authorizations`：最终用户授权主表，只表达“某资源最终授权给某系统账户”。
2. `resource_authorization_sources`：授权来源表，只表达“这条最终用户授权当前或历史上是因为什么来源成立”。

运行时、资源列表、分组绑定、API Key 绑定和授权统计都只以 `resource_authorizations` 为准；`resource_authorization_sources` 只负责来源说明、优先级切换、历史追踪和批量重算。

### 最终用户授权主表

建议保留 `resource_authorizations` 作为最终授权主表，字段如下：

- `id`
- `resource_type`：`account`、`group`
- `resource_id`
- `resource_owner_system_account_id`
- `grantee_system_account_id`
- `scope`：第一阶段固定为 `use`
- `status`：`active`、`paused`、`expired`、`revoked`
- `effective_source_type`：`manual`、`team`、`null`
- `effective_source_team_id`：当前生效来源是团队时记录团队 ID，否则为空
- `expires_at`：可选自动回收时间，命中后状态自动切换为 `expired`
- `limits_json`：美元成本额度限制 JSON，内部 `limit` 表示美元金额，支持 n 小时、日、周、月和累计总额度；为空表示不限制。
- `activated_at`
- `last_source_changed_at`
- `revoked_at`
- `revoked_reason`：例如 `manual_revoked`、`team_revoked`、`member_removed`、`team_disabled`、`resource_disabled`
- `remark`
- `created_by`
- `created_at`
- `updated_at`

约束与原则：

- 唯一键固定为 `resource_type + resource_id + grantee_system_account_id`。
- 同一资源同一用户全生命周期只维护这一条主记录；来源变化、停用后重启、撤销后重授都优先复用这条记录，不新建第二条最终授权。
- `status = active` 表示授权语义有效；`paused` 表示人工暂停但保留记录；`expired` 表示到期自动回收；`revoked` 表示主动收回。
- 实际可调用仍要结合系统账户状态、团队状态、资源状态和绑定状态做实时校验。

### 授权来源表

建议新增 `resource_authorization_sources`，字段如下：

- `id`
- `authorization_id`
- `source_type`：`manual`、`team`
- `source_team_id`：`source_type = team` 时必填
- `status`：`active`、`superseded`、`revoked`
- `activated_at`
- `ended_at`
- `ended_reason`：例如 `covered_by_team`、`team_revoked`、`member_removed`、`team_disabled`
- `created_by`
- `created_at`
- `updated_at`

约束与原则：

- 同一 `authorization_id` 最多只允许一条 `manual` 来源记录处于 `active` 或 `superseded`。
- 同一 `authorization_id + source_team_id` 同一时间只能有一条有效团队来源。
- 来源表用于说明“为什么有权限”，不是运行时主键，不单独承载统计口径。
- 到期不会删除主记录，只会把主记录切换为 `expired`，并保留来源历史和使用统计。

### 来源优先级与合并规则

- 优先级固定为：`team > manual`。
- 同一资源同一用户原本已有个人来源时，如果后来又被某个团队覆盖：
  - 不创建新的最终用户授权主记录；
  - 原主记录切换为团队来源生效；
  - 原个人来源改为 `superseded`；
  - 历史用量继续挂在同一条 `resource_authorizations.id` 下。
- 如果团队来源已经存在，再创建同一资源同一用户的个人来源：
  - 不让个人来源成为生效来源；
  - 可写入一条 `superseded` 的来源记录或直接返回“已被团队覆盖”的幂等成功；
  - 不保留个人来源作为未来自动回退来源。
- 如果同一资源同一用户同时被多个团队覆盖：
  - 允许存在多条 `active` 团队来源；
  - `effective_source_team_id` 仅保存当前主展示团队，按“最早生效且仍有效”的团队确定；
  - 只要任一团队来源仍有效，最终用户授权继续保持 `active`。
- 当最后一个有效团队来源失效时：
  - 若只剩 `superseded` 个人来源，最终用户授权直接转为 `revoked`；
  - 不自动恢复个人来源，符合“个人源取消”的规则。
- 重新授权同一资源同一用户时，优先重新激活原主记录，并新增新的来源记录。

### 创建、切换与撤销流程

#### 个人授权给系统账户

- 若不存在最终用户授权主记录：创建主记录，`effective_source_type = manual`。
- 若存在主记录且当前无有效团队来源：
  - 若已有手动来源且仍有效，按幂等成功处理；
  - 若主记录已撤销，则重新激活同一主记录并恢复手动来源。
- 若存在有效团队来源：不创建新的生效授权，个人来源只能作为被团队覆盖的非生效记录或直接 no-op。

#### 团队授权给系统团队

- 对团队内每个 `active` 成员逐个处理。
- 成员不存在最终授权时：创建主记录和团队来源。
- 成员已有手动来源时：复用主记录，切换 `effective_source_type = team`，手动来源转为 `superseded`。
- 成员已有其他团队来源时：新增当前团队来源；主记录继续保持 `active`。
- 批量生效逻辑必须使用事务，避免同一个团队授权中出现部分成员已生效、部分成员未生效。

#### 撤销团队授权或团队成员失效

- 团队授权被收回、团队被停用、成员被移除时，相关团队来源统一改为 `revoked`。
- 如果该用户在该资源上仍有其他 `active` 团队来源，主记录继续 `active`，并切换主展示团队。
- 如果没有任何 `active` 来源剩余，主记录改为 `revoked`。
- 主记录被撤销时不删除历史使用记录、来源历史和绑定关系。

#### 重新激活

- 同一资源同一用户后续再次被授权时，优先复用原 `resource_authorizations.id`。
- 已有分组绑定或 API Key 绑定不自动删除；重新激活后可继续复用，未激活期间网关仍必须拦截请求。

### 使用权生效

- 自有资源：调用方是资源归属人时天然可用，不需要授权记录。
- 用户授权：调用方匹配有效 `resource_type + resource_id + grantee_system_account_id` 主记录时可用。
- 团队授权：团队只负责生成或维持用户授权；网关不按团队再判断一次资源权限。
- 有效资源列表必须按 `resource_type + resource_id` 去重；同一资源不因个人来源、多个团队来源或来源切换而重复显示。
- 单行资源只暴露一个稳定的 `authorization_id`，用于加入分组、绑定 API Key 和网关调度。
- 绑定关系保存 `resource_id + authorization_id`；来源变化、团队切换和重新激活不改变绑定对象。
- 同一次上游尝试只能写入一条使用记录，不能因为同一用户存在多个来源而写多条记录。
- 上游 AI 账户始终是一个物理资源：同一个 `account_id` 不会因为授权来源不同而复制出多个账户实例；并发、冷却、到期、限流和真实总用量都共享同一个账户状态。
- AI 账户授权允许被授权人把该账户加入自己的同供应商分组并调度使用。
- 分组授权允许被授权人把自己的 API Key 绑定到该授权分组并调度使用。
- 分组授权共享的是分组归属人自有账户集合；如果分组里包含其他用户授权来的账户，不能通过分组授权继续传递给第三方。
- 账户页对授权 AI 账户提供“绑定分组 / 调整分组”入口，只能选择被授权人自己的同供应商分组；后端绑定时必须重新校验用户级授权、分组归属和供应商一致性。

### 绑定与列表展示

- `授权给我的` 资源列表只展示当前有效资源，不展示被 `superseded` 的个人来源。
- 来源文案展示当前生效来源；需要解释历史时，通过详情页展示来源变更记录。
- 若个人来源被团队覆盖，列表中只显示 `团队授权`，不显示“个人 + 团队”双标签。
- 现有 `group_accounts.account_authorization_id` 和 `api_keys.group_authorization_id` 均应指向稳定的最终用户授权主记录。
- 当主记录被完全撤销时，绑定关系保留但标记为不可用；主记录再次激活后，绑定可恢复可用。

## 授权统计口径

### 使用记录事实字段

`usage_records` 需要同时记录调用方、资源归属和最终用户授权路径：

- `system_account_id`：实际调用方系统账户，即 API Key 所属系统账户。
- `account_owner_system_account_id`：实际命中 AI 账户的归属人。
- `group_owner_system_account_id`：请求使用的分组归属人。
- `account_access_type`：`owner`、`authorized`
- `group_access_type`：`owner`、`authorized`
- `account_authorization_id`：命中授权 AI 账户时写入最终用户授权主记录 ID。
- `group_authorization_id`：命中授权分组时写入最终用户授权主记录 ID。
- `effective_source_type_snapshot`：调用当时的生效来源类型快照。
- `effective_source_team_id_snapshot`：调用当时生效团队快照，非团队来源为空。

使用记录保留成功、失败和排障记录；授权消耗统计按进入网关使用记录的请求聚合，失败记录按 0 token、0 cost 计入请求和错误次数。资源归属人自己的自用调用仍按自用处理，不进入授权 ID 维度。

### 展示口径

- 资源归属人的 AI 账户 / 分组“用量情况”展示资源全部总消耗，包含归属人自用和所有被授权用户使用。
- 授权管理里的默认用量展示为今日 0 点开始的授权消耗，不包含归属人自己的自用消耗。
- 授权统计唯一主维度是“资源 × 用户”，后台统计 worker 按稳定的 `authorization_id` 聚合到统计缓存。
- 授权列表和用量详情只读取统计缓存，不在页面查询时临时扫描 `usage_records` 做实时聚合。
- A 授权给 B 时，A 只看“B 今日在该资源上用了多少”，不区分这部分用量在历史上来自个人来源还是团队来源。
- A 授权给团队时，团队详情本质是该团队曾激活过的成员用户授权集合；展示仍以成员用户为主，不以来源为主。
- 如果 B 先有个人来源，后又被团队覆盖，则 B 在该资源上的今日消耗继续合并到同一条用户授权中；团队详情中看到的是合并后的 B 今日消耗。
- 如果 B 后续被移出团队，团队详情仍保留 B 今日已产生的消耗，但成员状态标记为“已移除”。
- 资源归属人只能看授权维度的聚合统计，不直接查看被授权人的请求快照、响应快照、客户端 IP、API Key 明文或业务请求内容。
- 调用方仍可在自己的使用记录里看到自己 API Key 产生的明细，包括使用授权资源产生的请求。

### 重叠授权统计示例

场景：A 把 `001` 账户先直接授权给 B，随后又把 `001` 账户授权给 B 所在的 `XX` 团队。

- B 的 AI 账户列表只出现一个 `001`。
- B 在 `001` 上对应的始终是同一条最终用户授权主记录。
- 团队来源生效后，个人来源被标记为 `superseded`，不再作为生效来源展示。
- B 发起请求时，每次实际上游请求 / 上游尝试写入一条 `usage_records`，授权 ID 始终是 `001 × B` 这条主记录。
- A 查看 B 在 `001` 上的授权详情时，看到的是 B 今日在该资源上的消耗。
- A 查看 `XX` 团队授权详情时，看到的也是 B 今日在 `001` 上的消耗，而不是只看团队生效后的局部区间。

## 页面设计

### 系统团队管理页

- 团队列表：团队名称、状态、成员数、描述、创建时间、更新时间、操作。
- 团队详情：基础信息、成员列表、成员状态、加入时间、移除时间、历史成员标记。
- 创建 / 编辑团队：名称、描述、状态；团队名称必须唯一，不再让用户感知团队编码。
- 成员维护：添加系统账户、移除成员、查看成员状态；系统账户下拉只展示启用或可管理的账号。
- 团队成员变化会影响既有授权覆盖范围，团队详情必须给管理员展示影响提示。

### 授权管理页

- 顶部筛选：资源类型、授权对象类型、授权对象、状态、资源名称、时间范围。
- 授权列表：资源类型、资源名称、资源归属人、被授权用户、当前生效来源、授权状态、授权时间、最近使用时间、用户今日消耗、操作。
- 新增授权：选择资源类型、选择自有资源、选择授权对象类型、选择系统账户或团队、填写备注；选择团队时按成员批量生成或切换用户授权。
- 额度限制：新增授权和修改授权配置时可设置 n 小时、日、周、月和总美元成本额度；额度为空表示不限制。
- 撤销授权：二次确认后改为 `revoked` 或撤销对应来源，不删除历史行。
- 用量详情：展示授权用户今日总量和明细；团队筛选下展示团队成员用户的今日去重汇总和成员明细。
- 来源详情：展示该用户授权当前来源、历史来源、来源切换时间和原因。
- `授权给我的` 视图：展示当前用户可使用的 AI 账户和分组，以及当前生效来源，便于排查为什么某个资源可见。

## 接口草案

- `GET /api/system-teams`：团队摘要列表，仅管理员可读取，用于系统团队管理。
- `GET /api/my-teams`：当前登录用户加入的团队和成员，只读，用于普通用户 `我的团队`。
- `POST /api/system-teams`：创建团队，仅管理员。
- `PATCH /api/system-teams/:id`：编辑团队，仅管理员。
- `POST /api/system-teams/:id/members`：添加成员，仅管理员。
- `DELETE /api/system-teams/:id/members/:memberId`：移除成员，仅管理员。
- `GET /api/authorizations`：授权列表，普通用户默认查看自己授权出去或授权给自己的记录，管理员可筛选全部。
- `POST /api/authorizations`：新增授权，资源归属人或管理员。
- `PATCH /api/authorizations/:id`：修改授权状态、到期时间和额度限制，资源归属人或管理员。
- `DELETE /api/authorizations/:id`：撤销最终用户授权或当前来源，资源归属人或管理员；语义由参数区分“撤销个人来源 / 撤销团队来源 / 撤销整条授权”。
- `POST /api/accounts/:id/group`：将自有或授权 AI 账户绑定到当前调用方可管理的同供应商分组；授权账户绑定时记录稳定用户级授权 ID。
- `GET /api/authorizations/:id/usage`：查看某个最终用户授权的聚合用量。
- `GET /api/authorizations/:id/sources`：查看当前和历史来源。
- `GET /api/authorization-options/grantee-accounts`：返回可选择的授权用户最小摘要，不返回系统账户管理字段。

## 存储与实现原则

- 删除旧的账户授权表和分组授权表设计，统一使用 `resource_authorizations` + `resource_authorization_sources`。
- 新增 `system_teams` 和 `system_team_members`。
- `group_accounts` 对授权账户增加可选的 `account_authorization_id`，用于记录加入分组时命中的最终用户授权。
- `api_keys` 对授权分组增加可选的 `group_authorization_id`，用于记录绑定授权分组时命中的最终用户授权。
- `resource_authorizations.limits_json` 保存用户级授权美元成本额度；`team_resource_authorization_grants.limits_json` 保存团队授权来源美元成本额度，并在成员展开或成员后续加入时同步到对应用户级授权。
- 授权创建、团队成员变更、团队停用、授权撤销都必须在事务内完成主记录和来源记录更新。
- 对 `resource_type + resource_id + grantee_system_account_id`、`authorization_id + source_team_id`、`team_id + system_account_id` 建立唯一索引或唯一有效性约束，防止重复授权和重复成员。
- 本地库可通过备份后直接 SQL、临时离线脚本或重建库完成调整，不做旧表字段补丁分支。

## 边界条件清单

| 场景 | 处理规则 |
| --- | --- |
| 先个人后团队 | 复用同一条最终用户授权，切换生效来源到团队，个人来源改为 `superseded`，历史用量不拆分。 |
| 先团队后个人 | 个人来源不能成为生效来源；可记为 `superseded` 或幂等成功，不作为自动回退来源。 |
| 多个团队覆盖同一用户 | 允许多条团队来源同时有效；最终用户授权只保留一条主记录。 |
| 撤销其中一个团队来源 | 只移除该团队来源；若仍有其他团队来源，授权继续有效。 |
| 最后一个团队来源失效 | 最终用户授权直接撤销；不会自动恢复被覆盖的个人来源。 |
| 团队成员被移除 | 当前调用立即失效；历史消耗保留，团队详情中成员标记为已移除。 |
| 团队被停用 | 等价于撤销该团队的全部团队来源；不删除历史统计。 |
| 系统账户被停用 | 最终用户授权主记录可保留 `active`，但运行时必须拦截。 |
| 资源被停用或删除 | 对应最终用户授权改为不可用并记录原因；历史记录保留。 |
| 分组包含他人授权来的账户 | 该账户不能通过分组授权继续下发，防止授权穿透。 |
| 同一次上游尝试命中多个来源 | 只认最终用户授权主记录，只写一条使用记录。 |
| 撤销后重新授权 | 优先复用原最终用户授权 ID，已有绑定可恢复使用。 |
| 授权额度命中 | 网关返回 429 和“额度已用完，请联系管理员提升额度”；额度判断读取统计缓存，允许统计延迟导致轻微超额。 |
| 团队授权额度 | 按团队成员用户级授权的 `total_cost_usd` 缓存求和判断团队总美元成本额度，同时成员用户级授权仍保留同一份额度限制。 |

## 验收标准

- [ ] 管理员可以创建、编辑、启停团队，并维护团队成员和成员状态。
- [ ] 同一资源同一用户全生命周期只存在一条稳定的最终用户授权主记录。
- [ ] 资源所有者可以在授权管理里把自有 AI 账户或分组授权给系统账户或系统团队。
- [ ] 团队授权进入后，同一资源同一用户若已有个人来源，系统切换为团队来源生效，个人来源取消但历史用量继续合并。
- [ ] 同一用户同时命中多个团队来源时，前端列表、接口结果和网关调度都只出现一个有效资源。
- [ ] 被授权系统账户或团队成员只能使用资源，不能编辑、删除、查看敏感凭据或继续转授权。
- [ ] 团队成员新增、移除、团队停用、系统账户停用和授权收回都能实时影响网关调度。
- [ ] 绑定到授权账户或授权分组的既有关系在来源切换后仍保持稳定，不要求重复绑定。
- [ ] 授权管理能按“资源 × 用户”展示每个被授权用户消耗；团队筛选展示成员用户聚合结果，且不包含资源归属人自用消耗。
- [ ] 授权管理新增和修改配置时能设置美元成本额度；网关命中用户级或团队级授权额度后返回“额度已用完，请联系管理员提升额度”。
- [ ] AI 账户 / 分组用量情况能展示资源全部总消耗，包含自用和所有授权使用。
- [ ] 使用记录页仍只展示调用方自己的明细，资源所有者不能查看被授权人的请求快照和业务内容。
