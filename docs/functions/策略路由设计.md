# 策略路由设计

> 状态：当前目标设计。
> 创建时间：2026-06-27。
> 本文固定 API Key、策略路由、分组、AI 账户和供应商的层级关系，替代早期把分组路由规则挂在 API Key 上的设计。

## 1. 核心结论

当前路由层级固定为：

```text
API Key -> 路由策略 -> 分组 -> AI 账户 -> 供应商 / 协议能力
```

API Key 仍然是用户调用入口，但不再直接保存分组绑定、权重、故障回退、轮询或混合智能路由规则。API Key 页面可以提供“配置路由规则”的产品入口，但保存时必须落到独立的路由策略实体；`api_keys` 只保存当前使用的 `route_strategy_id`。

分组统一绑定到路由策略里，不再绑定到 API Key 里。这样可以避免 API Key 页面长期膨胀成策略中心，也能让普通路由、混合智能路由、权重、故障回退和轮询共享同一套边界。

## 2. 职责边界

| 层级 | 职责 | 不负责 |
| --- | --- | --- |
| API Key | 用户入口、鉴权、额度、状态、过期、时间计划、使用记录归属；选择一个路由策略 | 不保存分组绑定；不保存模型档位、权重、回退、轮询或混合智能路由细节；不配置客户端画像或跨协议桥接 |
| 路由策略 | 保存路由模式、分组绑定、分组优先级 / 权重、混合智能路由规则和路由运行参数 | 不管理真实上游凭据；不修改账户能力；不做跨协议转换 |
| 分组 | 账号池容器，负责协调 AI 账户和分组内调度 | 不承载供应商、模型或协议语义；不保存路由模式 |
| AI 账户 | 管理真实上游账号、凭据、Base URL、代理、并发、时间计划、模型限制、错误策略和真实上游能力 | 不代表调用入口；不管理 API Key 额度；不管理其他账户或分组 |
| 供应商 | 对 AI 账户分类，提供协议驱动、模型目录、价格口径、账号测试和专项优化 | 不承接 API Key 入口或路由策略 |

两个容易混淆的点必须固定：

- 客户端画像由网关内部自动识别，不在 API Key、路由策略、分组或普通账户页面展示。
- 混合智能路由只负责“按评分和规则选择目标模型 / 分组”；跨协议转换属于混合供应商账户能力。

## 3. 路由模式

当前目标包含 5 个路由模式：

| 模式 | 代码建议 | 分组数量 | 是否可配置策略 | 用途 |
| --- | --- | --- | --- | --- |
| 普通路由 | `normal` | 只能绑定 1 个分组 | 仅开放调度偏好 | 默认入口，按唯一分组进入分组内调度，可在成本优先和速度优先之间选择 |
| 混合智能路由 | `hybrid_smart` | 1 个或多个分组 | 可配置 | 先评分请求难度，再按等级选择目标模型和可承接分组 |
| 权重调度路由 | `weighted` | 2 个或多个分组 | 可配置 | 按权重比例把请求分配到不同分组 |
| 故障回退路由 | `failover` | 1 个主用分组 + 1 个或多个备用分组 | 可配置 | 优先使用主用分组；主用不可承接时按备用顺序尝试，主用恢复后继续回到主用 |
| 轮询路由 | `round_robin` | 2 个或多个分组 | 可配置 | 多个分组等权轮询，当前分组不可承接时尝试后续分组 |

普通路由是最轻量的显式路由模式，系统会为每个非混合供应商的内置默认分组自动创建一条 `normal` 默认路由策略，并且该策略只能有一个 active 分组绑定。API Key 表单只选择已有策略路由，不直接展示或保存分组绑定。

普通路由支持两种调度偏好：

- 成本优先：默认偏好，尽量尊重会话亲和、账号亲和、缓存命中和现有分组内排序；不创建路由首字截止，只受 lane hard timeout、整请求预算和真实 transport 失败约束，适合长会话、上下文缓存敏感和成本敏感场景。
- 速度优先：仅对可重放文本请求观察首字耗时；当同一运行态键在配置窗口内连续慢到达触发条件后，把账号临时降级到当前普通路由号池后部，并且只在确认慢、下游尚未写出可见内容且仍有可承接候选时允许中止慢上游后切换同分组其他账号。图片及其他副作用请求不创建慢样本、`latency_degraded` 或速度切号，适合对首字等待敏感的文本场景。

成本优先和速度优先都属于 `normal` 模式内部的调度偏好，不新增第 6 种路由模式。只有速度优先的可重放文本使用 `normalRoutingConfig.firstByteDeadlineMs` 中性首字事件，用于累计慢样本并按确认状态裁决切号；成本优先、图片及其他副作用请求不创建该事件。该事件不得推进账户电路、Key 失败、共享可靠性或恢复任务；只有连接 / 读取失败和 lane hard timeout 保留 transport failure 语义。速度优先只影响当前普通路由唯一分组内的账号排序、慢样本观察和确认慢后的可安全切号；它不跨分组借号，不把多个分组混排，不改变账户能力、凭据、状态、并发、模型限制或账户错误处理策略。

普通路由调度遵循三层裁决：硬约束最高，路由策略目标其次，账户配置偏好最后。账户的超级优先、优先级、备用标记、质量分、会话亲和和缓存亲和是默认秩序；只有当账号违反当前路由目标时，路由策略才临时接管。以速度优先为例，账号进入 `latency_degraded` 后，路由可以临时覆盖该账号的超级优先、优先级和备用分层，让同分组内其他未降级且可承接账号先接单；一旦后台探针、真实达标请求或 TTL 清理了 `latency_degraded`，后续请求必须回到分组内账户配置排序，不能因为之前切到某个替补账号就长期粘在替补账号上。

系统会自动创建内置默认分组，并为除“默认混合供应商分组”以外的每个默认分组创建一条默认普通路由和一个默认 API Key。混合供应商路由属于高级路由，不作为默认入口；用户需要跨供应商或跨协议调度时，在策略路由和混合供应商账户中显式配置。

混合智能路由、权重调度路由、故障回退路由和轮询路由都在“策略路由”菜单里新增、编辑和启停。API Key 只选择使用哪条路由策略。

## 4. 产品入口

### 4.1 API Key 页面

API Key 页面只保留入口相关字段：

- 名称、状态、过期时间、说明。
- 额度、限流、时间计划。
- 策略路由选择。

API Key 页面选择已有路由策略，或跳转到“策略路由”菜单创建。若后续提供快捷新建策略，也必须写入 `route_strategies` 和 `route_strategy_groups`，不能把规则字段写回 `api_keys`。

API Key 列表筛选也必须保持这一层级：可以按策略路由筛选，不能把分组筛选作为 API Key 页面的一等筛选项。分组筛选属于策略路由、分组、账户或使用记录等更下游视图。

API Key 表单读取策略路由下拉时只使用轻量 options：管理侧调用 `GET /__aisys__/api/route-strategies/options`，可按 `systemAccountId` 收窄或全局查看；用户侧调用 `GET /__aisys__/api/my-route-strategies/options`，后端强制当前登录用户作用域。options 只返回 `id`、`name`、`mode`、`status` 和 `isDefault` 等摘要，管理侧额外带 owner 摘要；不得为了表单下拉读取完整 `config_json`、分组绑定、API Key 数量或账号信息。

策略路由表单的分组下拉使用专用轻量接口：管理侧调用 `GET /__aisys__/api/groups/route-strategy-options`，用户侧调用 `GET /__aisys__/api/my-groups/route-strategy-options`。该接口只返回 `id`、`name`、`providerCode`、`enabled`，候选范围包含调用方自有分组和当前授权可见的分组；不得复用账户表单的宽分组选项 DTO。新增弹窗首开不请求候选，只有用户展开或搜索分组下拉后才加载；混合智能的模型候选继续等到用户展开模型下拉时，再按已选分组的 `providerCode` 请求。

### 4.2 策略路由菜单

新增菜单建议命名为“策略路由”。该菜单管理可配置路由策略：

- 混合智能路由。
- 权重调度路由。
- 故障回退路由。
- 轮询路由。

普通路由只开放单分组绑定和调度偏好。若列表展示普通路由，应明确它是“普通路由 / 单分组 / 成本优先或速度优先”，避免用户误以为普通路由也能配置多分组、权重、回退或混合智能规则。

路由策略可以被多个 API Key 复用。编辑被多个 API Key 复用的策略时，页面必须提示影响范围；如果用户只想改一个 API Key，应复制一条新策略再绑定。

策略路由页面必须按路由模式展示结构化配置，不把底层 JSON 配置直接暴露给用户：

- 普通路由只展示一个分组绑定和调度偏好；选择速度优先后才展示首字截止、触发次数、窗口期、恢复次数和探针间隔等轻量参数，不展示权重、回退或混合智能配置。首字截止默认 30 秒，按 `10..60` 秒录入，保存时转换为 `normalRoutingConfig.firstByteDeadlineMs`；成本优先不提交该字段。
- 权重调度路由展示分组权重。
- 故障回退路由展示 1 个主用分组和多个备用分组；不暴露优先级输入，所有分组行都可通过拖拽调整顺序，备用分组拖到第一行即可晋升为主用分组。
- 轮询路由不暴露顺序输入，通过拖拽调整稳定轮询顺序。
- 混合智能路由展示评分模型、质量偏好、等级模型、质量检查、缓存和模型亲和等表单项；保存时再组装为 `route_strategies.config_json` 中的 `hybridRoutingConfig`。

#### 4.2.1 列表与详情读取契约

策略路由菜单使用管理 / 个人双作用域的完整列表和详情 GET：

- `GET /__aisys__/api/route-strategies`
- `GET /__aisys__/api/my-route-strategies`
- `GET /__aisys__/api/route-strategies/{id}`
- `GET /__aisys__/api/my-route-strategies/{id}`

管理侧未指定 `systemAccountId` 或使用 `all` 时读取全局 owner 视图，指定具体 ID 时收窄到该 owner；个人侧始终强制当前登录账户，即使调用者是管理员也不能通过用户侧接口读取全局。

列表契约保持当前页有界：

- `page` 默认 `1`、最小 `1`、无最大页；`pageSize` 默认 `50`、范围 `1..200`。
- 使用 `pageSize + 1` 判断 `hasMore`，`total` 只返回渐进上界，不执行精确总数查询。
- `keyword` 只做大小写敏感的名称字面前缀匹配，不搜索说明；非法 `mode/status` 忽略。
- 排序固定为 `updated_at DESC, created_at DESC, id DESC`。
- 列表返回静态字段和管理侧 owner 摘要；`normal` 列表项返回规范化 `normalRoutingConfig`，便于直接展示成本优先 / 速度优先。
- 同一响应包含 `generatedAt`，每项包含精确 `bindingCount`、精确 `apiKeyCount` 与最多 3 条 `groupBindingPreview`；真实无绑定或无 API Key 时返回 `0`。
- `bindingCount` 统计全部绑定；`apiKeyCount` 统计 owner 匹配的全部状态 API Key。预览保持 active 优先，再按 priority、createdAt、id 稳定排序，并返回 `id/groupId/groupName/providerCode/status/groupEnabled`。
- 计数和预览使用当前页 ID 的有界批量查询，不增加逐行查询、物化表、后台预聚合或长 TTL 缓存；`generatedAt` 只表示生成时间，不承诺跨查询事务快照。
- 页面只请求列表；翻页、筛选、切换 owner、刷新或卸载后的迟到列表响应必须按请求代次和 owner scope 丢弃。

详情契约用于编辑回填，必须返回完整 `groupBindings`、`apiKeyCount` 和当前模式完整配置：`normal` 返回规范化 `normalRoutingConfig`，`hybrid_smart` 返回规范化 `hybridRoutingConfig`。详情不能复用列表 preview，也不能在配置损坏时静默伪造 hybrid 默认值。

### 4.3 分组页面

分组页面只维护账号池关系、分组内排序、启停、分组类型和分组内调度策略。分组可以展示成员账户派生出的供应商 / 协议摘要，但这些摘要只用于理解号池内容，不代表分组拥有供应商、模型或协议语义。

### 4.4 AI 账户和供应商页面

AI 账户页面维护真实上游账号配置。供应商页面维护供应商分类、协议驱动、模型目录、价格口径和专项优化。

混合供应商账户仍然是 AI 账户，保存自己的真实上游凭据、Base URL、真实上游协议和下游到上游模型映射。它不指向其他账户或分组，也不属于策略路由规则。

## 5. 数据模型

目标存储关系：

```text
api_keys
  id
  system_account_id
  route_strategy_id
  quota_config
  availability_schedule
  status

route_strategies
  id
  system_account_id
  name
  mode
  status
  is_default
  config_json
  created_at
  updated_at

route_strategy_groups
  id
  route_strategy_id
  group_id
  priority
  weight
  enabled
  created_at
  updated_at
```

`api_keys.route_strategy_id` 是 API Key 到路由策略的唯一入口。旧的 `api_key_group_bindings` 语义应收敛到 `route_strategy_groups`；旧的 API Key 级 `routeMode`、`hybridRoutingConfig`、权重和分组回退字段应收敛到 `route_strategies.config_json` 或后续独立策略表。

`route_strategies.is_default` 标识系统默认策略路由。启动种子、系统账户创建和带账户作用域的策略路由列表读取会为非混合供应商默认分组补齐默认普通路由；带有 `is_default = 1` 的默认路由不允许删除或修改名称，避免默认入口身份被破坏，但仍允许编辑说明、状态、调度配置和分组绑定；用户显式创建的新路由默认写入 `is_default = 0`。

默认 API Key 同样不允许修改名称；AI 对话专用 API Key 以 `purpose = chat` 识别，也纳入名称保护。前端禁用对应名称输入只是交互提示，最终约束由后端 repository 更新入口统一执行。

`route_strategies.mode` 建议使用：

```ts
type RouteStrategyMode =
  | 'normal'
  | 'hybrid_smart'
  | 'weighted'
  | 'failover'
  | 'round_robin'
```

普通路由配置示意：

```ts
type NormalRouteConfig = {
  schedulingPreference: 'cost_first' | 'speed_first'
  firstByteDeadlineMs: number
  speedFirstConfig?: {
    slowTriggerCount: number
    slowWindowSeconds: number
    recoverySuccessCount: number
    probeIntervalSeconds: number
    degradedTtlSeconds: number
    maxFirstByteRetriesPerRequest: number
  }
}
```

普通路由配置保存在 `route_strategies.config_json.normalRoutingConfig`。缺省配置等价于：

```json
{
  "normalRoutingConfig": {
    "schedulingPreference": "cost_first",
    "firstByteDeadlineMs": 10000
  }
}
```

速度优先首字截止与专属默认值：

| 字段 | 默认值 | 建议范围 | 含义 |
| --- | --- | --- | --- |
| `firstByteDeadlineMs` | `30000` | `10000..60000` | 仅速度优先可重放文本使用的中性路由首字截止。每个请求开始时只解析一次，同请求后续业务 attempt 复用；流式按首个可见语义 chunk、非流式按首个 body 字节计算。成本优先、图片及其他副作用请求不创建该 timer。它不替代 lane hard timeout，也不作为 circuit confirmation 失败证据。旧 `speedFirstConfig.firstByteThresholdMs` 只作为读取兼容别名；规范化响应和持久化只写当前字段，新旧同时提交直接拒绝。 |
| `slowTriggerCount` | `3` | `2..10` | 同一运行态键在窗口内连续慢样本达到该值后进入速度降级。 |
| `slowWindowSeconds` | `120` | `60..600` | 慢样本观察窗口；超过窗口的样本不参与当前连续触发判断。 |
| `recoverySuccessCount` | `3` | `3..10` | 真实用户请求连续达标达到该值后恢复正常排序；其计数与后台恢复探针完全隔离。 |
| `probeIntervalSeconds` | `30` | `10..300` | 真实请求恢复成功但尚未达到 `recoverySuccessCount` 时的后续检查间隔；后台恢复探针固定约 5 秒一次。 |
| `degradedTtlSeconds` | `300` | `60..3600` | 速度降级运行态租约时长；确认慢触发时创建。后台探针仅在同一两次窗口均失败时续到至少 `now + degradedTtlSeconds`，且不缩短既有截止。 |
| `maxFirstByteRetriesPerRequest` | `2` | `1..3` | 单次请求在账号已确认首字慢后允许的额外换号次数；默认最多救两次，避免单个已确认慢账号长期拖住当前请求。 |

确认慢后的当前请求首字慢切号是速度优先的内部机制，不作为用户可关闭的配置项；未达到慢样本触发条件前，速度优先在专属截止事件上只记录观察，不因慢样本机制立即切号。成本优先不创建该事件；速度优先也不能把该配置事件上报为 transport failure。

混合智能路由配置示意：

```ts
type HybridSmartRouteConfig = {
  scoringModel: string
  scoringContextMode: 'full_request'
  qualityPreference: 'cost_first' | 'balanced' | 'quality_first'
  scoringTimeoutMs: number
  scoringFallbackMaxLevel: number
  scoringCacheTtlSeconds: number
  cacheAffinityTtlSeconds: number
  switchMinLevelDelta: number
  levelRoutes: Array<{
    minLevel: number
    maxLevel: number
    targetModel: string
    enabled: boolean
  }>
}
```

权重、故障回退和轮询优先使用 `route_strategy_groups.priority`、`route_strategy_groups.weight` 和策略运行态，不额外复制分组绑定结构。

## 6. 校验规则

通用校验：

- 每个 API Key 必须绑定一条可用路由策略。
- 路由策略的 `system_account_id` 必须与 API Key 所属系统账户一致。
- 路由策略绑定的分组必须对该系统账户可用，可以是自有分组，也可以是有效授权分组。
- 同一条路由策略下不能重复绑定同一个分组。
- 至少存在一个 enabled 分组绑定。
- disabled 分组绑定只作为配置保留和列表展示，不参与运行时路由。
- 删除分组、停用自有分组、停用授权分组设置或让分组对某个系统账户不可用时，必须先检查受影响的策略路由；如果该分组仍是某条策略路由唯一可用的 active 分组，写入必须被阻断。
- 这类跨聚合不变量由策略路由可用性守卫统一处理，分组写入只负责调用守卫，不直接散落维护策略路由可用性规则。

各模式校验：

- `normal`：只能有一个 enabled 分组；只接收 `normalRoutingConfig`；不接收权重、回退、轮询或混合智能配置。
- `normalRoutingConfig.schedulingPreference` 缺省为 `cost_first`，只允许 `cost_first` 或 `speed_first`。
- `speed_first` 必须按上表范围校验专属首字截止、慢触发次数、窗口期、恢复次数、探针间隔、降级 TTL 和单请求首字慢重试次数；确认慢后的当前请求切号为内部机制，不开放关闭开关。
- `cost_first` 保存时不写入无效的速度优先参数；从速度优先切回成本优先时，应清理该路由策略相关速度降级运行态，避免旧运行态继续影响普通调度。
- `hybrid_smart`：至少一个 enabled 分组；必须有评分模型和连续覆盖 `1-10` 的等级路由规则；目标模型必须来自调用方可见模型目录。
- `weighted`：至少一个 enabled 分组；每个分组权重范围为 `1-100`。当前创建接口不强制至少两个分组，也不校验权重总和；运行时按已保存权重归一化选择。
- `failover`：必须有且只有 1 个启用主用分组，并至少有 1 个启用备用分组；备用分组可以有多个，通过行顺序写入隐藏优先级。
- `round_robin`：至少一个 enabled 分组；enabled 分组按页面拖拽顺序写入隐藏优先级，并形成稳定轮询环。当前创建接口允许先保存单分组配置。

如果 `weighted` 或 `round_robin` 暂时只配置了一个可用分组，前端可以提示用户普通路由更轻量，但不能把提示升级为后端额外校验。

## 7. 运行链路

目标请求链路：

```text
请求进入网关
  -> 校验 API Key、系统账户状态、额度、过期和时间计划
  -> 读取 API Key 绑定的路由策略
  -> 路由策略按 mode 和 route_strategy_groups 选择候选分组
  -> 分组内调度选择可承接 AI 账户
  -> 普通账户按真实协议直连上游
  -> 混合供应商账户按账户内协议桥接配置请求自己的真实上游
  -> 返回侧按下游协议和客户端画像渲染响应
```

运行时职责边界：

- 网关 runtime cache 只负责读取、缓存、失效和后台刷新 API Key、分组访问、账号候选和响应检查策略。
- 路由解析器负责按路由策略模式、分组绑定顺序、分组可用性和账号候选情况选择本次请求的目标分组。
- DB service 与 server runtime cache 如果都需要执行动态路由解析，应复用同一套解析语义，不能在两条链路长期各自复制分组选择规则。

普通路由：

- 只读取唯一分组。
- 该分组不可用或没有可承接账号时，返回本地可读错误。
- 不自动尝试其他分组。

普通路由的成本优先：

- 成本优先是默认调度偏好。
- 分组内调度优先尊重会话亲和、账号亲和、缓存命中、模型匹配、账号优先级、超级优先、备用标记、质量缓存和现有运行态避让。
- 如果首选账号没有进入账号故障屏蔽、运行态降级或持久冷却，系统应尽量继续使用该账号，减少上游上下文缓存被打散。
- 成本优先仍然沿用通用上游失败切号链路；账号失败、响应检查命中、流式可见输出前失败等可安全重放场景，仍按候选账号继续尝试。

普通路由的速度优先：

- 速度优先只改变当前 `normal` 路由唯一分组内的账号候选排序、首字慢样本观察和确认慢后的可安全切号行为。
- 速度优先只对文本推理做首字观察、慢样本和确认慢切号。图片、音频、文件 / 资源、后台任务、hosted tool 及其他副作用请求不创建该 timer、不记录慢样本、不进入 `latency_degraded`，因此不会仅因速度策略超阈值中止当前 attempt；它们的实际失败仍按统一候选规则切号。长耗时或特殊文本协议请求不会因为单次超阈值立即切号，只有连续慢样本确认账号进入 `latency_degraded`，并且仍有未尝试的硬可承接候选、下游未写出可见内容和单请求重试上限时，才允许当前请求因速度策略切换账号。
- 首字时间以用户实际感知为准。可重放文本流式请求按首个可见语义输出计算，SSE comment、空心跳、尚未形成完整语义的 raw chunk 不算达标首字；非流式请求按上游 `2xx` 后首个 body 字节计算。副作用 lane 不参与该观察。
- 首字慢样本按运行态键聚合，建议键为 `systemAccountId + routeStrategyId + groupId + accountRuntimeKey`。自有账户的 `accountRuntimeKey` 使用 `accountId`；授权实例使用 `accountId + 使用方系统账户 + 本地分组 + 授权 ID`，与账号运行态探针的隔离口径保持一致。
- 启用速度优先的可重放文本请求在 `normalRoutingConfig.firstByteDeadlineMs` 截止时仍无首字则记录慢样本。慢样本只记录非客户端取消、非本地认证 / 额度 / 授权 / 模型过滤、非本地请求体非法、非账号并发满或分组队列满的上游等待。同一个上游 attempt 只能记录一次慢样本；副作用 lane 始终不记录。
- 窗口内连续慢样本达到 `slowTriggerCount` 后，该运行态键进入 `latency_degraded`。快样本会清理当前连续慢计数；超过 `slowWindowSeconds` 的旧慢样本不参与触发。
- `latency_degraded` 是短 TTL 易失运行态，不写 `accounts.status`、不写 `cooldown_until`、不修改 `schedulable`，也不计入账号健康检测连续失败。它只表示“在当前普通路由的速度优先偏好下，这个账号近期首字慢，应暂时后置”。
- 候选排序时先执行硬过滤：账户状态、授权、可用时段、模型能力、协议能力、分组可用性、账户错误处理策略、本地短暂屏蔽、账号硬并发和分组队列仍然优先。`latency_degraded` 账号不被移出候选，只在未降级候选之后兜底。
- `latency_degraded` 是路由策略覆盖层，而不是账户配置重写。只要当前普通路由仍是速度优先，已确认慢的账号可以被同分组内其他未降级且硬可承接账号越过，即使该慢账号开启了超级优先、拥有更高账户优先级、处于主池或有会话 / 缓存亲和。未降级候选之间、降级候选之间仍保留原始分组内账户排序。
- 速度优先下，会话亲和和缓存亲和只在亲和账号未处于 `latency_degraded` 时优先；亲和账号已速度降级时，本次请求优先尝试同分组其他未降级账号。速度优先切号命中的替补账号不能形成比账户配置和速度恢复状态更强的长期偏向；慢账号恢复后，后续请求应重新按超级优先、优先级、备用标记、质量分和稳定顺序选择。
- 如果所有可承接候选都处于 `latency_degraded`，系统应旁路速度降级排序，回到原始分组内候选顺序，避免因为保护机制把号池筛空或长期只返回失败。
- 速度优先可重放文本的当前上游达到 `firstByteDeadlineMs` 仍没有可见输出时，网关先记录软慢样本；如果本次样本尚未使账号达到 `latency_degraded`，当前上游继续等待，不立即切号。真正的 lane hard timeout、建连失败或读取中断仍走统一传输电路。成本优先和副作用 lane 不进入本段软截止流程。
- 只有账号已经处于 `latency_degraded`，或本次软慢样本使账号达到 `latency_degraded`，且下游尚未提交任何可见内容、仍有未尝试的硬可承接候选、未超过客户端总等待上限时，网关才可以主动中止当前上游请求，把当前账号加入本次请求排除集合，并切换同分组下一个账号。这里的“硬可承接”不要求同超级优先或同账户优先级，只要求不违反路由分组范围、模型 / 协议能力、授权、状态、额度、并发和请求能力等硬约束。
- 单次请求确认慢后触发的切号次数受 `maxFirstByteRetriesPerRequest` 限制。默认允许 2 次，避免单个已确认慢账号拖住当前请求，同时保留上限防止上游抖动时把成本、连接数和代理压力放大。
- 如果下游已经写出可见内容，无论流式还是非流式，都不在同一个响应中透明切号；只记录首字慢和后续质量样本，交给后续请求排序和后台探针恢复。
- 速度优先默认不做并发抢跑。也就是不会同时向两个上游账号发送同一请求后取最快结果；后续如要引入抢跑，必须作为独立高成本能力设计，明确额外计费、取消语义、审计和并发保护。

速度降级恢复：

- 进入 `latency_degraded` 后，应提交运行态探针意图，由统一运行态探针调度器约 5 秒后执行首字恢复探针；调度扫描也保持 5 秒。
- 探针复用账号测试健康探针的最小请求，不复用用户失败请求的 model、endpoint、stream、payload 或正文内容；探针只验证当前账号在通用健康请求下首字能否回到阈值以内。
- 后台恢复探针以严格的两次窗口判定：`SS` 清理 `latency_degraded` 和慢样本窗口；`FF` 将 `degradedUntil` 延长到至少 `now + degradedTtlSeconds`（不得缩短既有截止）并开启新窗口；`SF` 或 `FS` 不续期并开启新窗口。两次探针约间隔 5 秒。
- `neutral` / incomplete 探针结果不视为失败续期证据：它会作废当前窗口并开始新窗口，不能与前后结果拼成 `FF`。每个 candidate 都携带降级事件、当前两次窗口计数、下一次到期时间和截止时间围栏；success、failure、defer、discard 均须完整匹配才可变更，拒绝重复、迟到或跨进程重放。
- 真实用户请求成功仍只累加自己的 `recoverySuccessCount`，连续达到该值后清理；后台探针的窗口计数不会读写该计数。清理后该账号不再受速度优先覆盖层后置，下一次请求按当前分组内账户配置重新排序，防止恢复账号被长期饿死。
- 真实请求完整成功但首字仍超过阈值，只能说明账号可用但慢，不清理速度降级；真实请求失败仍进入现有账号失败状态机，不由速度优先直接写持久账号状态。
- 切换路由策略配置、关闭速度优先、删除或停用路由策略、移除分组绑定、账户从分组解绑或授权失效时，应清理对应 `latency_degraded` 运行态。

故障回退路由：

- 当前顺序的第 1 个分组作为主用分组；后续分组都是备用分组，所有分组都可拖拽重排，备用分组拖到第 1 位后即成为主用分组。
- 每次请求都先尝试主用分组；主用分组恢复可承接后，不继续粘在备用分组。
- 主用分组授权失效、无可调度账号、模型 / 请求能力不匹配或写下游前账号耗尽时，按备用拖拽顺序尝试后续分组。
- 已经写出下游响应后，不做服务端透明跨分组重放。

轮询路由：

- 多个 enabled 分组按拖拽顺序等权组成环。
- 每次请求从下一个分组开始尝试。
- 当前分组不可承接时，按本轮候选顺序继续尝试。

权重调度路由：

- 使用平滑加权轮询或等价算法生成候选起点；单个分组权重为 `1-100`，所有分组权重合计不能超过 `100`。
- 大量请求下命中比例接近配置权重。
- 当前分组不可承接时，按本次候选顺序继续尝试。

混合智能路由：

- 先调用评分模型判断请求等级。
- 按等级规则选择目标模型。
- 只在本路由策略绑定的分组里筛选可承接目标模型和当前请求协议的账户。
- 如果命中普通账户，按普通账户真实能力直连。
- 如果命中混合供应商账户，才进入该账户自己的跨协议转换配置。

## 8. 审计、统计和缓存

使用记录和原始审计应记录路由摘要：

- `route_strategy_id`
- `route_strategy_mode`
- 尝试过的 `group_id` 列表
- 最终命中的 `group_id`
- 最终命中的 `account_id`
- 本地跳过原因，例如分组停用、授权不可用、模型不匹配、账户耗尽、请求能力不匹配
- 普通路由调度偏好，例如 `normal_scheduling_preference`
- 速度优先相关摘要，例如 `first_byte_ms`、`first_byte_threshold_ms`、`first_byte_slow_observed`、`first_byte_confirmed_cutover`、`latency_degraded_account_ids` 和 `latency_degraded_recovered`
- 混合智能路由的评分等级、目标模型和评分摘要

API Key 统计仍按 API Key 聚合；分组统计按实际命中的分组聚合；AI 账户统计按实际命中的账户聚合。路由策略可以新增独立统计维度，但必须由后台 worker 增量聚合，不能在请求链路或前端页面实时扫描使用记录。

速度优先只依赖请求链路已经产生的首字时间和后台探针结果。实时路由不能为了判断账号慢而扫描使用记录、统计缓存或审计日志；需要展示趋势、TopN 或分位数时，必须使用 `usage_latency_*` 或账号质量这类后台预聚合结果。

运行态缓存必须以 `apiKeyId + routeStrategyId + routeStrategyUpdatedAt` 或等价版本摘要作为失效条件。修改路由策略、普通路由调度偏好、速度优先参数、分组绑定、分组启停、分组成员、授权状态、账户能力和模型限制时，都要清理相关网关 runtime cache。速度降级运行态属于短 TTL 调度态，standalone 模式可以保存在进程内；performance 模式必须进入 Redis runtime state，并带 TTL、generation 和 due 索引，不能写入业务库或统计结果库作为持久事实。

## 9. 迁移边界

本项目默认不做运行时向下兼容。落地策略路由时，代码和 schema 应直接按当前目标模型推进：

- `api_keys` 不再保存分组绑定和复杂路由规则。
- `route_strategies` 保存路由模式和模式配置。
- `route_strategy_groups` 保存路由策略到分组的绑定。
- 已有数据需要处理时，只允许在代码库外离线重建或按当前 schema 一次性整理，不把双读、双写、历史字段兜底或历史结构补丁写进运行时链路。

W5 管理端策略路由列表 / 详情的 Go 实现当前只允许作为 opt-in 迁移路径存在。真实 PostgreSQL / HTTP、前端真实 Go 后端 smoke、反向代理单 owner 切流、回滚和 Node 删除证据完成前，Node 仍是生产 owner，不能把契约对齐或单元测试通过描述为生产接管。

当前路由实现和后续改造只以本文为准；不要再把分组路由规则直接挂在 API Key 上作为背景入口或产品依据。
