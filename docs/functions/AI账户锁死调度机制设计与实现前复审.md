>
> 更新时间：2026-08-30
>
> 需求来源：用户需求调研
>
> 本文固化当前链路事实、已确定的锁死方案、冲突审查和实现约束；锁死已完成首版实现，本文同时作为实现边界与复审记录。

## 1. 需求概述

“锁死”是比“超级优先”更强的账号调度策略：用户在“我的 AI 账户”操作中执行“锁死”后，只要该账号尚未被判定为彻底不可用，网关就不应在请求恢复、速度切换或分组回退时切换到其他账号，而应继续使用该账号和现有的账号内重试机制。用户可以在账号高级配置中设置死亡判定窗口，默认 5 分钟。

本次复审确定以下产品与调度规则：

- “锁死 / 解除锁死”是列表操作，也是锁死状态的唯一启停入口；不增加、不展示单独的 `lockEnabled` 高级配置开关。
- 死亡窗口和重试间隔是当前使用方账户实例的持久调度配置，不是凭据字段，也不是某个请求的临时参数。自有账号写入自有账号作用域；授权账号写入当前被授权人的授权实例作用域。授权用户对锁死拥有与自有账号一致的使用侧操作权限。
- 运行态锁定可以跨客户端重试请求保留；但单个 HTTP 请求仍必须服从现有 270 秒请求墙钟。
- “5 分钟内全死”表示从一次真实业务流量形成锁定失败窗口开始，窗口内没有任何一次完整、协议有效的成功；没有流量不能证明账号死亡。
- 一次有效成功只要属于同一账号实例且通过候选能力过滤，就证明该账号实例在当前窗口仍然存活；协议、模型和 lane 不再拆出另一份“未锁死”状态。

## 2. 当前实现事实

### 2.1 请求主链路

当前网关主链路为：

```text
请求入口
-> 认证、额度和策略路由预检
-> 路由选定分组与模型目标
-> 候选账号能力、模型、状态和可调度性过滤
-> 账号优先级 / fallback / super priority 排序
-> 运行态抑制、电路、代理、并发槽和 Key 准备
-> 单个上游 attempt
-> 响应协议检查与下游提交
-> 成功、当前候选失败、同账号重试、切号、切组或客户端交接
```

代码证据：

- 请求预检建立 `ServerRetryBudget`、`GatewayRequestWallBudget` 和请求尝试跟踪器：[backend/src/modules/gateway/request/preflight.ts](../../backend/src/modules/gateway/request/preflight.ts:399)。
- 主循环先检查墙钟，再构造当前轮次账号集合；无候选时才考虑后备分组：[backend/src/modules/gateway/routes.ts](../../backend/src/modules/gateway/routes.ts:765)。
- 每轮调用 `fetchFirstAvailableUpstream`，并传递同一请求的墙钟、等待预算、尝试去重和语义重试上下文：[backend/src/modules/gateway/routes.ts](../../backend/src/modules/gateway/routes.ts:1005)。
- 单候选 attempt 前依次执行账号电路、运行态抑制、代理和并发槽检查：[backend/src/modules/gateway/dispatch/upstream-dispatch.ts](../../backend/src/modules/gateway/dispatch/upstream-dispatch.ts:449)。

### 2.2 当前的超级优先不是锁死

超级优先目前只是候选排序层级。它通常让账号先进入主候选层，但以下机制仍可以越过它：

- `speed_first` 已确认首字过慢时的路由救援；
- 单账号排队或分组容量达到软阈值；
- 账号电路、运行态抑制、代理不可用或硬并发限制；
- 当前账号失败后的同分组候选和后备分组处理。

因此仅增加一个更高的 `priority` 或把 `super_priority_enabled` 改成更大数值，不能实现用户要求的“只要没死就不切号”。锁死必须是切号决策处的额外否决条件。

### 2.3 当前重试和切号边界

- 同账号已有有界瞬态重试，当前实现最多额外两次，并受剩余请求墙钟和最终响应预留约束；不能改成无限循环。
- 账户内多 Key 已有独立的请求内故障隔离：完整响应可按当前 Key 池规则尝试同账户后续 Key，瞬态 `408/425/429/5xx` 先复用既有同 Key 有界重试；显式账户策略 `retry_next` 仍保留其额外的兄弟 Key 授权语义。锁死不应改变这些账户内 Key 规则，只禁止跨账号 / 跨分组切换。
- 完整非 `2xx` 在未命中显式账户错误策略时按 opaque 上游失败处理，通常排除当前候选并继续调度；不能仅凭状态码、错误码或正文把账号写成死亡。
- 传输失败在下游未提交时可继续候选；真实 JSON、SSE 事件或模型输出已经提交后，不能拼接第二账号响应。

参考：[docs/functions/网关异常重试与兜底策略.md](网关异常重试与兜底策略.md)、[docs/functions/AI账户错误语义与状态变更边界.md](AI账户错误语义与状态变更边界.md)。

### 2.4 两个 270 秒预算不能混用

| 预算 | 当前含义 | 锁死约束 |
| --- | --- | --- |
| `GatewayRequestWallBudget` | 文本整请求默认 270 秒，贯穿账号、Key、分组和切换决策 | 绝不能因锁死延长、暂停或重置；到期必须交接客户端 |
| `ServerRetryBudget` | 默认 270 秒，只累计零可派发、并发槽、FIFO 或受控半开等待 | 继续由原机制消费；活动上游读取不因为锁死改变计时口径 |

锁死的默认死亡窗口为 300 秒，大于单个文本请求的 270 秒。因此“锁死 5 分钟”主要表现为：当前请求最多坚持到 270 秒，随后客户端重新发起请求；新的请求仍可依据活动锁定运行态继续选择该账号。服务端不能在 270 秒后继续替客户端等待。

## 3. 候选设计

### 3.1 配置和运行态分离

增加以下持久配置字段。锁死状态本身由列表操作切换，不作为高级配置开关：

| 字段 | 类型 | 默认值 | 作用 |
| --- | --- | --- | --- |
| `lockDeathTimeoutSeconds` | integer | `300` | 没有有效成功后允许继续坚持的窗口，必须有最小值、最大值和整数校验 |
| `lockRetryIntervalSeconds` | integer | `5` | 锁死运行态下两次业务重试之间的基准等待时间，配置范围 `5..30` 秒；实际等待按已确认的抖动规则计算 |

列表操作的持久动作固定为 `lock` / `unlock`，而不是让前端先保存一个布尔开关再等待调度读取。操作必须经过现有账号更新权限、配置版本和操作日志链路；`lock` 成功后当前使用方的账号实例进入锁死状态，`unlock` 成功后只解除该实例的锁死策略，不自动清除其他来源创建的状态。授权实例的操作不得回写授权方原账户，也不得影响其他被授权人的授权实例。授权用户对自己的授权实例拥有与自有账号相同的锁死 / 解锁使用侧操作权。

增加以下运行态信息，但不写入业务账号表的热路径字段：

- `lockIncidentId`、`generation`、`dispatchRevision`；
- 运行态记录维度：以账号实例身份为主键；协议档案、请求 lane、模型桶和分组仅作为能力过滤、重试诊断和失败证据维度，不参与锁死状态隔离；
- `startedAt`、`lastAttemptAt`、`lastSuccessAt`、`deathDeadlineAt`；
- 最近一次失败类型，仅记录可观察结果，不从 HTTP 文案推断具体业务原因；
- 当前租约、CAS 版本和结算状态。

锁死必须定义独立的规范实例键：自有账号使用 `account.id`，授权实例使用该实例的 `account.id`，不得把 `route strategy`、`groupId`、协议、模型桶或 lane 拼进锁死键。`account_lock_states` 是锁死事故、死期和发送租约的跨实例权威账本；其条件更新使用账号实例、事故代次和 `incidentId` 围栏。当前 `gatewayAccountRuntimeKey` 为授权实例附加 `groupId`，只能继续用于既有电路、抑制和质量状态；若直接复用它，授权账户换分组后可能绕过锁死。

### 3.2 确定的状态模型

```text
UNLOCKED
  账号未被操作锁死，或已执行 unlock；不启动锁死死亡倒计时
  |
  | 列表操作 lock 成功
  v
LOCKED_IDLE
  已锁死，但尚无真实业务流量；不启动锁死死亡倒计时
  |
  | 账号被选中并出现未成功的真实 attempt
  v
ENGAGED
  锁死生效，当前失败窗口开始，切号决策被锁死门阻止
  |\
  | \ 有效协议成功
  |  v
  |  HEALTHY（关闭当前失败窗口，账号继续作为锁死账号使用）
  |
  | deathDeadlineAt 到达且窗口内没有有效成功
  v
DEAD_CONFIRMED
  通过带 provenance / generation 的 CAS 转入现有 temporary_unavailable
```

说明：`HEALTHY` 不代表执行了 unlock，只表示当前失败窗口被有效成功结算；账号仍保持列表操作设置的锁死状态。后续再次出现真实失败时应建立新的 `ENGAGED` 窗口。`DEAD_CONFIRMED` 进入既有冷却复测和恢复流程；恢复后列表中的锁死状态仍可保留，下一次真实失败重新建立窗口。只有 `unlock` 操作才解除锁死状态。

`deathDeadlineAt` 在第一次真实失败后单调向前计算；失败窗口已经进入 `ENGAGED` 后，即使中间暂时没有新请求，也不能把死期重置或延后。只有从未发生真实 attempt 的 `LOCKED_IDLE` 才不启动死亡计时。

### 3.3 “有效成功”的口径

锁死窗口只接受 `complete_success` 作为正向证据：

- 协议结构验证通过；
- 上游 framing 完整；
- 对流式响应，必须有真实协议事件或模型输出，并正常完成可识别终态。

下列结果不能清除死亡窗口：

- 完整非 `2xx`；
- 只有 SSE 注释心跳；
- 客户端取消、读取未知或任务失败；
- 仅收到响应头但协议正文未完成；
- 不属于同一账号实例，或未通过当前请求能力过滤的结果；不同协议 / 模型 / lane 只要实际命中同一账号实例且协议成功，均可作为该实例存活证据。

### 3.4 锁死门的位置

锁死门应位于“当前账号失败后是否允许切换候选”的决策点，而不是修改候选排序算法本身：

1. 正常路由先确定分组、模型目标和初始账号。
2. 当前账号进入锁死窗口后，继续调用现有同账号 attempt / Key / 电路 / 并发机制。
3. 在未达到 `deathDeadlineAt` 且未触发硬不可用条件时，禁止当前请求切换到其他账号或后备分组。
4. 270 秒墙钟到达时，仍按原 `client_handoff` 交给客户端；不得抛出一个“服务端无限重试成功”的假象。
5. 窗口内没有有效成功且达到死期时，才允许释放锁并按现有账号状态与后备机制继续。

该门只表达“不要主动换号”，不重写路由策略、候选过滤、Key 选择、重试预算或上游协议转换。锁死门是否存在由列表 `lock` / `unlock` 操作后的账号状态决定，不由高级配置里的重复开关决定。

### 3.5 锁死重试频率和随机抖动

锁死不能把“继续使用该账号”实现成失败后立即再次发送。每次锁死业务重试都必须经过同一账号运行态的共享重试闸门，至少满足以下规则：

1. 初次派发不等待；只有当前 attempt 结束并且锁死仍然有效时，下一次进入同一锁死作用域才等待。
2. `lockRetryIntervalSeconds` 是用户配置的基准值，持久范围为 `5..30` 秒，默认基准值为 `5` 秒；不存在独立的“默认延迟”配置。
3. 抖动范围只由基准值决定：基准值 `5..10` 秒时使用 `±2` 秒，基准值 `>10..30` 秒时使用 `±5` 秒。实际延迟按毫秒级均匀随机取值，并做边界裁剪：

   ```text
   jitter = base <= 10 ? 2 : 5
   minDelay = max(2, base - jitter)
   maxDelay = min(30, base + jitter)
   delay = random(minDelay, maxDelay)
   ```

   例如：基准 `5` 秒得到 `3..7` 秒；基准 `10` 秒得到 `8..12` 秒；基准 `20` 秒得到 `15..25` 秒；基准 `30` 秒得到 `25..30` 秒。
4. “默认随机 `2..7` 秒”和“用户配置 `5` 秒上下浮动 `2` 秒”统一解释为同一条抖动规则，不再单列默认延迟口径，也不保留 `2..7` 秒特殊窗口。按统一公式，默认基准 `5` 秒的实际范围是 `3..7` 秒；`2` 秒只是全局下界裁剪值。
5. 抖动只改变下一次尝试的等待长度，不改变现有同账号重试次数、Key 轮换授权、账号电路、响应语义或候选去重。
6. 已有全局 `temporaryUnschedulableRetryIntervalSeconds` 仍然有效。锁死重试的实际等待不应小于现有全局等待，采用以下规则：

   ```text
   effectiveDelay = max(globalRetryDelay, sampledLockDelay)
   ```

   这样不会因为开启锁死而加速既有重试路径；锁死只是额外增加最小间隔。未开启锁死时，现有同账号重试的次数和固定等待完全不变；锁死开启后同一次 retry 只等待一次，不得先睡全局间隔再额外睡一段锁死间隔。
7. 每个锁死运行态作用域必须维护一个共享的 `nextRetryAt` 和短时发送租约。并发请求到达时只有持有租约的请求可以在该时间点发起上游 attempt，其余请求等待同一个时间点或按原有候选失败 / handoff 处理，不能各自随机等待后同时发送。
8. 随机值应在预约重试时生成并随租约保存，不能在每个进程、每个 waiter 的本地内存中独立生成。多实例以 `account_lock_states` 的条件更新作为共享权威，避免重启或多副本造成同一时间的重试波峰。
9. 等待从上一次 attempt 完成或释放发送租约后开始计算，不能只按 attempt 开始时间计算。这样慢请求不会和下一次锁死重试重叠，降低对上游的并发冲击。
10. 锁死间隔等待继续受现有 `GatewayRequestWallBudget`、请求取消信号、最终响应预留和 `routeCoordinationBudget` 约束；不得为了等满 5 分钟而暂停或重置 270 秒墙钟。锁死等待默认不计入 `ServerRetryBudget` 的“零可派发账号”累计，除非该次等待本来就属于现有无可派发 / 并发队列路径；不能通过改写预算口径延长服务端等待。

该闸门的作用是限制锁死造成的新增业务请求频率，不应套用到后台健康探针、人工账户测试或 OAuth token 刷新；这些路径继续使用各自已有的退避和租约规则。

## 4. 机制兼容规则

| 现有机制 | 锁死下的处理 | 不能做的事 |
| --- | --- | --- |
| 策略路由和分组绑定 | 仍由路由层选择初始分组；锁死只在账号派发和切号决策处生效 | 不把锁死账号跨路由策略强行注入 |
| 普通候选排序 | 正常使用模型匹配、fallback、super、priority 和运行态排序选出首账号 | 不新增一个伪造的无限优先级层 |
| `speed_first` | 锁死窗口内，已确认慢也不能执行跨账号切换，否则锁死弱于超级优先；首字计时本身仍按原规则执行 | 不把速度截止改成账号死亡证据，不暂停墙钟 |
| 同账号重试 | 复用现有有界重试、`retry_next`、Key 轮换和电路确认 | 不扩大为无限重试，不自动授权兄弟 Key |
| 锁死重试频率 | 每次锁死重试经过共享 `nextRetryAt` / 发送租约，基准值按 `lockRetryIntervalSeconds` 加随机抖动 | 不让每个请求独立 sleep 后同时撞击上游，不改全局重试次数 |
| 账号电路 | `OPEN`、硬阻断、过期、凭据不可装配、模型不支持等仍是硬门；锁死不能绕过 | 不为了“全力尝试”跳过熔断或半开租约 |
| 并发和队列 | 继续受账号并发上限、组容量和 `ServerRetryBudget` 控制 | 不因锁死让容量超限或无限排队 |
| 后备分组 | 健康锁死窗口内禁止因当前账号失败而主动切组；锁释放或账号硬死后恢复原 fallback | 不改变分组权重、轮询和混合路由语义 |
| 完整非 `2xx` | 仍遵循 opaque 错误边界；除非命中显式账户策略，否则不能直接持久化死亡 | 不按 400/401/429/5xx 或正文关键词自动锁死 |
| 流式提交 | semantic commit 前可继续同账号处理；提交真实事件后不能拼接其他账号 | 不在流中途换号拼接 |
| IP 回避和热质量 | 保留为各自作用域的排序/避让事实；锁死只作为切号否决门 | 不把锁死失败扩散成 IP、代理或其他账号状态 |
| 后台探针 | 继续负责既有恢复和账户健康确认；可作为独立恢复证据 | 不把人工测试或普通业务流量假装成探针成功 |
| 客户端重试 | 270 秒交接后客户端发起新请求，按当前运行态重新判定 | 不让服务端吞掉客户端重试责任 |

### 4.1 `speed_first` 边界（本轮审核结论）

- 锁死窗口内，`speed_first` 的首字计时、慢样本记录和可观测性继续运行；首字超时或确认变慢只产生调度信号，不能把当前账号从候选中排除，也不能触发跨账号或跨分组切换。
- 锁死门必须位于 `speed_first` 的切号 / cutover 决策点之前；同一账号实例仍继续使用现有 attempt、账号内重试、Key、电路、代理和并发机制。不得通过“速度优先”路径绕过锁死。
- 当前 attempt 仍服从原有 lane hard timeout、语义提交边界和请求取消；锁死不取消已建立连接，也不把首字计时改成新的服务端等待预算。
- `GatewayRequestWallBudget` 到达 270 秒时照常交接客户端；客户端重新请求后继续读取同一账号实例的锁死运行态。只有锁死死期到达、账号进入明确不可调度终态（包括硬不可用、`rate_limited`、`temporary_unavailable`）或用户执行 `unlock` 后，才恢复原有速度切号与后备分组语义。

## 5. 状态写入和错误语义边界

现行最高约束要求：普通网关请求的未知上游错误不能直接写 `accounts.status`、Key 状态、代理健康、模型能力或账户持久状态。锁死在 5 分钟后写入 `temporary_unavailable`，只作为用户通过账号列表 `lock` 操作明确开启的策略结算，并且满足以下条件：

1. 只接受“真实流量窗口内无 `complete_success`”这一明确判定，不接受状态码或错误文案分类。
2. 写入时携带来源，例如 `lock_policy`，并带 `incidentId + generation + dispatchRevision + observedAt`。来源、事故代次、死期、原状态和结算结果应放在独立锁死状态 / 事故元数据中，不能只依赖 `last_error_code` 或 `last_error_message`。
3. 使用 CAS / fencing，迟到的成功、失败、探针或旧配置不能覆盖新代次。成功在 `DEAD_CONFIRMED` CAS 之前结算则取消死亡；CAS 之后到达的成功不得清除已写入的持久状态，只能作为既有探针的候选证据。
4. 当前仍有在途请求时，不能仅因计时器到期就破坏并发中的有效请求；应遵循现有提交和并发释放边界。计时器不取消连接、不截断响应。
5. **已确定的 A 方案**：仅当当前实例状态仍是 `active` 且没有更强 / 外部状态时，才把 `accounts.status` 以 CAS 改为现有 `temporary_unavailable`，并标注 `lock_policy` provenance；已有 `disabled`、`error`、`quality_isolated`、过期、来源不可用、`rate_limited` 或外部 `temporary_unavailable` 时不覆盖，只结束锁死事故并恢复原调度语义。
6. 写入 `temporary_unavailable` 后，复用既有冷却、探针和恢复语义，不新造另一套恢复状态机。探针恢复账户状态时保留列表上的锁死策略，状态回到 `LOCKED_IDLE`，下一次真实失败再开启新事故。
7. 用户关闭锁死只清理锁死策略运行态；不能顺便清除由其他来源创建的 `temporary_unavailable`、`rate_limited` 或 `error`。即使 `temporary_unavailable` 是锁死写入的，也不因 `unlock` 直接“复活”账号，仍由既有探针 / 人工恢复流程解除不可调度状态。

特别注意：A 方案只适用于“锁死操作已明确开启且事故达到死期”的结算，不改变普通网关未知错误的状态边界；B 已确定不采用，实现不得自行切换为 B。

本轮复审确定采用 **A：写入现有 `temporary_unavailable`**。理由是用户原始目标明确包含“死期内无一次成功后进入临时不可调度”，而列表 `lock` 操作本身可以作为用户对该状态策略的显式授权；这不同于普通请求根据未知 HTTP 错误自行猜测账户状态。A 不是新增账户状态值，也不是把普通网关失败改成持久写入，而是锁死事故达到死期后的唯一结算动作。实现新增 `account_lock_states` 账号锁死状态 / 事故元数据表，主键为账号实例 `account_id`，记录 `lockState`、`incidentId`、`generation`、死期、原状态和终态来源；`accounts.status` 只作为现有调度过滤可识别的 `temporary_unavailable` 投影。实现必须使用该元数据、原状态快照、`lock_policy` provenance、CAS fencing、在途请求保护和既有恢复探针；`unlock` 不得误清其他来源状态。

## 6. 管理端和存储影响

### 6.1 账号操作和高级配置

- “我的 AI 账户”操作菜单增加“锁死 / 解除锁死”，菜单动作就是锁死状态切换，必须使用现有账号更新权限、配置版本和操作日志链路。
- 高级配置只增加“锁死死亡窗口”和“锁死重试间隔”：死亡窗口使用整数秒，默认 `300` 秒，范围固定为 `30..3600` 秒；重试间隔默认基准 `5` 秒，范围固定为 `5..30` 秒；不增加 `lockEnabled` 开关。死亡窗口在当前 `ENGAGED` 事故中使用事故开始时的快照，配置修改从下一次事故生效；重试间隔修改立即使旧的待发租约失效，并按新基准重新预约，均不重置 270 秒请求墙钟。
- 账号列表、详情和编辑回显应区分：列表操作设置的锁死状态、当前运行态是否正在锁定、是否已经进入 `temporary_unavailable`。不能再显示一个与“锁死”操作重复的启用开关。
- 自有账号和授权账号都可以在“我的 AI 账户”中执行“锁死 / 解除锁死”。授权使用方对自己的授权实例应按现有使用侧调度权限修改死亡窗口和重试间隔；这些写入只作用于当前授权实例，不回写授权方原账户，也不影响其他被授权人的实例。凭据、来源账户归属、继续转授权、删除授权实例等敏感内容仍不可修改。

权限边界固定为：

| 使用对象 | 锁死 / 解锁作用域 | 可修改内容 | 不可修改内容 |
| --- | --- | --- | --- |
| 自有账号所有者 | 自有账号实例 | 锁死状态、死亡窗口、重试间隔及既有自有账号使用侧调度项 | 受系统权限和账号类型限制的敏感凭据规则 |
| 被授权用户 | 当前用户自己的授权实例 | 锁死状态、死亡窗口、重试间隔及既有授权实例使用侧调度项 | 来源凭据、来源账户归属、授权关系、继续转授权、删除来源资源 |
| 管理员代用户操作 | 请求中明确指定的用户 / 授权实例作用域 | 在管理权限内代用户执行同等使用侧锁死操作 | 不得省略 `systemAccountId` 作用域，不得把代操作写成资源所有者自用状态 |

这里的“授权用户可操作”不等于“授权用户可以改授权方原账户”：授权模型仍保持实例隔离。一个用户锁死自己的授权实例，只影响该用户通过该实例发起的调度；授权方自用账号和其他被授权人的实例不受影响。

## 7. 并发、作用域和竞态要求

以下规则是实现前的硬门槛：

- 同一账号多个并发请求只能共享同一个匹配运行态 incident，不能各自启动独立 5 分钟计时器。
- 同一账号多个并发请求也必须共享重试闸门；同一作用域同一时刻最多一个业务重试发送租约，不能因随机数不同形成并发波峰。
- `nextRetryAt` 必须在发送租约释放、请求取消、锁死关闭、账号硬死和配置版本变化时有明确结算；不能留下永久等待或失效租约。
- 重试间隔的随机值必须记录在受控运行态或审计元数据中，至少可解释“为什么本次等待了这个时长”；不能把随机值写成用户配置或持久账号健康事实。
- 配置变更推进 `configRevision`；旧请求和旧 worker 不能覆盖新配置。
- 多实例部署以 Redis 作为共享运行态权威；memory 仅作单进程适配，不得让不同实例各自认为锁已释放。
- 锁死状态的主作用域是当前使用方的账号实例身份：自有账号使用所有者账号实例身份，授权账号使用被授权人的授权实例身份。它在该账号实例内跨协议、模型和 lane 生效；协议、模型和 lane 只能用于能力过滤、重试诊断和失败证据，不能生成另一份“未锁死”状态。相同物理来源账号的不同授权实例必须使用不同的锁死运行态作用域，避免一个人的锁死影响其他人。
- 一个作用域的成功只能清理同一 generation 的锁定窗口；迟到成功不能清除新一轮死亡窗口。
- 账号进入 `temporary_unavailable`、`disabled`、过期或硬错误后，锁死运行态必须以明确终态结束，不能继续阻塞其他可用账号。
- 没有真实 attempt 的账号不计入“全死”；只有排队、没有候选、客户端取消和探针 unknown 不能单独推进死亡计时。

## 8. 已确认决策

以下决策已确定，实施时不得自行改成其他语义：

1. **作用范围（已确认）**：锁死按当前使用方的账号实例全局生效，跨协议、模型和 lane；协议、模型和 lane 只保留为能力过滤、诊断和失败证据维度。自有账号和每个授权实例分别拥有自己的锁死状态；不允许通过切换协议、模型或 lane 绕过锁死，也不允许跨用户共享锁死状态。
2. **跨请求是否继续（已确认）**：继续。否则 270 秒后客户端一重试就立即正常切号，锁死无法达到“全力使用这个账户”的目的。
3. **死亡窗口起点（已确认）**：从第一次真实失败 attempt 起算，不从执行 lock 操作或没有流量的时间起算。
4. **成功定义（已确认）**：只认 `complete_success`，不认完整非 2xx、心跳、取消和 unknown。
5. **并发成功范围（已确认）**：以同一账号实例和 generation 为范围；任一通过候选能力过滤的协议 / 模型 / lane 成功都可清理该账号实例当前窗口，但不能跨授权实例或跨用户清理。
6. **硬电路是否可绕过（已确认）**：不可绕过。锁死不能破坏既有熔断、凭据保护和容量保护。
7. **死期到达后的持久状态（已确认采用 A）**：
   - A：以 `lock_policy` provenance 写入现有 `temporary_unavailable`，交给既有恢复探针；只允许从 `active` 且无更强 / 外部状态的实例通过 CAS 转入，不覆盖 `disabled`、`error`、`quality_isolated`、过期、来源不可用、`rate_limited` 或外部 `temporary_unavailable`；
   - B：只释放锁死并允许原调度切号。本轮不采用，因为不能满足“死期后进入临时不可调度”，仅作为产品反向选择时的替代方案。
8. **授权账号权限（已确认）**：授权使用方应和自有账号一样拥有使用侧调度操作权，可以在自己的授权实例上 `lock` / `unlock`，并修改死亡窗口、重试间隔等非敏感调度参数；不得修改凭据、来源归属、授权关系或继续转授权。授权方原账户和其他被授权人的实例不受影响。管理员代用户操作时必须锁定明确的被授权人作用域。
9. **锁死与 `speed_first`（已确认）**：锁死窗口内否决速度切号；仍保留首字计时、270 秒墙钟和客户端交接。`speed_first` 只能记录变慢和等待，不能借速度 cutover 绕过锁死；死期或硬不可用终态后恢复原有速度切号语义。
10. **解除动作（已确认）**：列表“解除锁死”是锁死状态的正式关闭入口，只解除锁死策略及其运行态；现有 `temporary_unavailable` 等其他来源状态仍按原恢复动作处理。不再另设 `lockEnabled` 开关。
11. **重试间隔与抖动（已确认）**：`lockRetryIntervalSeconds` 保存用户配置的基准值，范围 `5..30` 秒，默认基准 `5` 秒；基准 `<=10` 使用 `±2` 秒，基准 `>10` 使用 `±5` 秒，结果统一裁剪到 `2..30` 秒。不存在独立默认延迟口径，也不保留默认值专用 `2..7` 秒窗口。
12. **共享重试闸门（已确认）**：同一账号运行态使用一个 `nextRetryAt + lease`，并发请求排队到同一闸门；不采用仅在请求内随机 `sleep`。
13. **与全局间隔的关系（已确认）**：锁死实际等待取 `max(temporaryUnschedulableRetryIntervalSeconds, sampledLockDelay)`，保证新机制不会缩短既有全局保护间隔。

## 9. 实施验收场景

实施时必须将以下场景加入测试设计；本轮尚未执行：

| 场景 | 预期 |
| --- | --- |
| 锁死账号传输失败，另一个账号健康 | 锁死窗口内不切换；只复用现有同账号重试 / 电路 / Key 规则 |
| 基准间隔为 5 秒 | 抖动后的实际等待落在已确认的范围内，即 `3..7` 秒 |
| 基准间隔为 10 秒 | 使用低档抖动，实际范围为 `8..12` 秒 |
| 基准间隔为 11 或 20 秒 | 使用高档抖动，实际范围分别为 `6..16` 秒、`15..25` 秒 |
| 基准间隔为 30 秒 | 实际等待不超过 30 秒，范围为 `25..30` 秒 |
| 同账号 64 路并发失败 | 共享一个 `nextRetryAt` 和发送租约，不出现 64 次同刻上游请求 |
| 多个网关实例同时重试 | Redis runtime state 只允许一个匹配租约持有者发起该次重试 |
| 授权用户锁死授权实例 | 该用户自己的授权实例跨协议、模型和 lane 生效；授权方原账户和其他被授权人的实例不受影响 |
| 授权方修改或停用来源账号 | 授权实例仍受 `effectiveAvailability` 和来源硬门禁约束；授权用户的本地锁死不能绕过来源不可用 |
| 当前 attempt 本身耗时 20 秒 | 下一次等待从 attempt 结束后开始，不与在途请求重叠 |
| `speed_first` 下锁死账号首字慢 | 不执行跨账号切换；首字计时和 270 秒墙钟仍生效 |
| 显式 `retry_next` | 仍按原规则处理同账号兄弟 Key；锁死不扩大授权范围 |
| 270 秒将耗尽 | 返回原 `client_handoff`，不延长到 300 秒，不写成“服务端成功” |
| 客户端在 270 秒后重试 | 新请求重新走网关，但活动锁定仍可使其继续选择该账号 |
| 窗口内出现有效 JSON / SSE 成功 | 关闭当前失败窗口，账号继续可用 |
| 只有 SSE 心跳、完整非 2xx 或 unknown | 不清除窗口，不直接写死亡状态 |
| 无流量经过 5 分钟 | 不判死，不写 `temporary_unavailable` |
| 死期到达且窗口内始终无成功 | 按 A 结算：锁死专用 CAS 写入带 provenance 的 `temporary_unavailable`；若 CAS 发现更强 / 外部状态，保留原状态并结束锁死事故 |
| 已提交流式输出后读取中断 | 不拼接第二账号，客户端收到断流 / 失败并自行重试 |
| 账号过期、禁用、模型不支持或电路硬阻断 | 锁死不能绕过，按原硬门和恢复规则处理 |
| 两个网关实例并发结算 | 只有一个 incident / generation 结算成功；迟到结果被 fencing 拒绝 |
| 关闭锁死后存在其他来源状态 | 只清理锁死策略运行态，不误清除其他来源状态 |

| 锁死启停入口 | 管理侧和授权侧列表均提供 `lock` / `unlock` 动作；配置接口携带 `expectedConfigRevision` 并进入操作日志链路 | 需继续覆盖并发配置编辑和授权实例隔离回归 | 保持独立 `lock` / `unlock` 命令，不增加重复的 `lockEnabled` 高级开关 |
| 候选能力和模型过滤 | `candidate-filter.ts` 先做请求能力过滤，再做模型 / 映射过滤；无候选时按既有规则请求路由回退 | 锁死不能改变“能不能承接请求”的硬条件，否则会把不支持协议 / 模型的账号强行送到上游 | 锁死门只能作用于已通过能力、模型、授权、状态和可调度性检查的账号 |
| 普通排序和超级优先 | 候选窗口按 fallback、super priority、priority、创建时间等排序，运行态还会重新排序 | 提高 priority 不能阻止后续切号，无法表达“比超级优先更强” | 锁死必须是切号决策上的否决门，不新增伪造的无限优先级 |
| `speed_first` 首字切号 | 路由仍记录慢样本并保留首字计时，但锁死窗口内拒绝 cutover；死期或硬门后才恢复原切换 | 需覆盖首字慢、预占失败和客户端 handoff 回归 | 锁死窗口内继续当前账号，保留计时、观测、取消、lane hard timeout 和墙钟 |
| 同账号重试与账户内 Key | 既有同账号重试和账户内 Key 规则保持不变；锁死重试在其外层增加共享 `nextRetryAt + lease` 与抖动 | 共享租约覆盖主循环和路由级 pending 重试，需继续做多实例时序回归 | 锁死不得改成无限重试，不改变账户内 Key 池规则或 `retry_next` 语义 |
| 锁死重试防突发 | 已实现共享数据库租约、采样等待和 `nextRetryAt`；base `5..30`，`<=10` 为 `±2`、`>10` 为 `±5`，结果裁剪到 `2..30` | 需持续做多实例并发时序回归 | 共享 `nextRetryAt + lease` 串行化锁死业务重试 |
| 270 秒请求墙钟 | `GatewayRequestWallBudget` 在每轮派发前检查最终响应预留和最小有效 attempt；耗尽后发送 `client_handoff`。文本默认 270 秒，图片使用独立更长墙钟 | 锁死窗口默认 300 秒不能让单请求越过 270 秒，也不能把 270 秒改成锁死等待预算 | 锁死等待服从既有 wall budget、取消和最终响应预留；客户端重试仍是新请求 |
| `ServerRetryBudget` | `ServerRetryBudget` 只累计零可派发、并发 / FIFO / 半开等待；活动上游读取和正常 attempt 不按该口径累计 | 若把锁死等待错误计入或暂停错误，会改变现有全局重试语义 | 保持现有预算口径；锁死共享闸门等待同时受 wall budget 和 route coordination 约束 |
| 熔断、硬门和并发 | 单候选 attempt 前先经过账号电路、运行态抑制、代理、并发槽和 Key / 模型 admission；blocked 或硬不可用会跳过 | “全力使用”不能解释成绕过熔断、来源不可用、过期、模型不支持或并发上限 | 锁死只禁止主动切号，不绕过任何硬门；硬门成立时按原机制结束、恢复或交接 |
| 响应提交边界 | 下游 `transportCommitted` / `semanticCommitted` 分离；未提交的可验证 transport failure 可继续候选，真实 JSON / SSE / 模型输出提交后不能透明拼接 | 锁死不能为了坚持账号而在已提交流中重放或拼接第二账号 | 仍以现有提交状态为最高边界；客户端负责已提交后的重试 |
| 完整非 `2xx` | generic 路径保留 opaque 响应；先按账户内多 Key 隔离规则尝试后续 Key，Key 池耗尽后排除当前账户并继续后续候选；只有显式账户错误策略或独立后台探针才能推进共享状态 | 不能按 400、401、429、5xx 或正文关键词直接判定锁死死亡 | “全死”只能由锁死窗口内无 `complete_success` 的明确证据结算；错误语义继续遵守现有边界 |
| 精确协议响应检查 | 当前代码另有系统默认 / 显式 `retry_next_account`、账户避让和 `retry_no_avoidance` 分支；是否排除当前账号取决于规则、客户端画像、下游提交和端点重放门禁 | 不能把账户错误策略 `retry_next`（兄弟 Key）误当成账号切换授权，也不能让锁死窗口被 `retry_next_account` 或速度 cutover 绕过 | 锁死门必须覆盖所有跨账号 / 跨组重放出口；保留原规则的协议呈现、预算和同账户 Key 语义 |
| 现行文档一致性 | 当前代码和回归测试要求未命中策略的完整非 `2xx` 先按账户内 Key 隔离规则处理，Key 池耗尽后再扫描后续候选；本轮已同步架构总览、backend README、流式调研和网关错误链路中的旧描述，并补充系统默认 / 显式响应检查重放分支 | 若实现者按旧文档改锁死，会把普通候选切换、账户内 Key 轮换、响应检查重放和锁死否决门混成一个权限 | 以当前代码和回归为现行事实：账户内 Key 轮换和同 Key 有界重试按既有规则保留，账户 / 分组切换按统一未提交边界进行，精确协议切号由适用响应检查规则授权，`retry_next` 只额外授权其声明的兄弟 Key 行为；锁死需覆盖所有跨账号 / 跨组出口 |
| 运行态作用域 | 现有授权账户运行键会区分当前用户、分组和授权关系；`speed_first` latency state 还按 system account、route strategy、group 隔离 | 直接复用 route / model / lane latency key 会把锁死错误隔离，导致换协议、换模型或换 lane 绕过 | 锁死主键必须是当前使用方的账号实例；协议、模型、lane 只作能力 / 诊断维度 |
| 授权账户写入 | 当前授权调度 repository / route 支持实例级状态、优先级、超级优先、备用和恢复，但不接受锁死字段 | 文档已经规定授权用户拥有使用侧锁死权，代码尚未提供 payload、校验、审计和运行态写入 | 新接口必须携带当前被授权人作用域和 `expectedConfigRevision`；只写授权实例，不回写来源账户或其他实例 |
| 后台探针和持久状态 | 现有探针、冷却、`temporary_unavailable` 和健康投影有自己的 revision / generation / CAS 约束；普通请求未知失败不直接写共享状态 | 若死期到达要写 `temporary_unavailable`，必须与既有状态来源、恢复探针和迟到结果竞争；通用冷却写入会覆盖部分已有冷却状态，不能直接复用 | 按 A 使用锁死专用 CAS 和独立 provenance / 事故元数据；普通请求仍不得直接写共享状态，锁死事故死期到达后才自动结算 |

### 10.2 已验证的机制关系

以下关系已经由代码和现行专题文档交叉核对，可以作为实现的不可变约束：

1. **入口到 attempt**：预检创建并复用 `ServerRetryBudget`、`GatewayRequestWallBudget`、`RouteCoordinationBudget` 和 `GatewayRequestAttemptTracker`；主循环先判断墙钟，再构造候选并调用 `fetchFirstAvailableUpstream`。
2. **候选到切组**：能力 / 模型过滤和候选耗尽处理都可能触发既有 fallback group；锁死不能把一个不匹配模型或无授权的账号重新注入候选，也不能跨路由策略强行注入账号。
3. **首字慢路径**：当前 `speed_first` 代码确实存在“记录慢 -> 预占目标槽 -> 抛出 cutover error -> 排除当前账号 -> 下轮只试目标账号”的路径；未来锁死门必须覆盖这个完整路径，而不是只在普通失败分支加判断。
4. **跨请求边界**：当前客户端新请求默认重新按当时优先级、质量、速度、可用状态和轮换游标选号；锁死若要跨请求持续，必须新增共享运行态读取点，同时明确在 `unlock`、死期、硬终态和配置版本变化时如何失效。
5. **授权实例边界**：现有 `gatewayAccountRuntimeKey` 已为授权实例附加当前用户 / 分组 / 授权关系，适合既有分组绑定态；锁死不得直接沿用这个含 `groupId` 的键，否则授权实例改绑分组后可能形成第二个锁死窗口。锁死应使用当前使用方拥有的规范账号实例键（授权实例 `accounts.id` 已独立时以其为主，必要时附授权关系 / 租户），并明确不含 route strategy、group、协议、模型或 lane。
6. **持久化边界**：锁死配置与事故元数据由 `account_lock_states` 保存，列表与高级详情投影其状态；普通 `accounts` 表仍不增加新的账户状态枚举。

### 10.3 当前文档的冲突点和处理方式

- [架构总览](../architecture/架构总览.md) 和 [AI 账户短窗口热质量与精准切号设计](AI账户短窗口热质量与精准切号设计.md) 仍把普通 `speed_first` 描述为可越过账户偏好的速度目标；本文定义的锁死窗口例外已在网关切换入口落地。
- 当前代码、[核心功能设计](核心功能设计.md)、[网关错误处理完整链路](网关错误处理完整链路.md) 和回归测试已经把完整非 `2xx` 的现行行为固定为“先按账户内 Key 隔离规则处理，Key 池耗尽后排除当前候选并继续扫描”；部分架构和流式文档残留的“只有 `retry_next` 才允许切候选”属于旧口径。本轮按实际代码修正文档，保留账户内 Key 池、同 Key 有界重试、响应检查重放和账户错误 `retry_next` 各自的边界。
- [网关异常重试与兜底策略](网关异常重试与兜底策略.md) 仍规定 generic 完整非 `2xx` 排除当前候选并继续后备；精确协议的系统默认 / 显式响应检查规则另有受限重放分支。本文保留这些既有错误语义，只增加“已锁死且仍未到死期时，所有跨账号 / 跨组切号动作由锁死门否决”的现行调度约束。
- [高并发分组调度设计](高并发分组调度设计.md) 仍允许达到阈值后打破会话亲和；锁死不等同于会话亲和，已在账号锁死门处阻止跨账号选择，同时继续执行并发硬上限和客户端 handoff。不能通过改写高并发的全局“打破亲和”规则来实现锁死。
- 本方案采用 A：死期结算时以锁死专用 CAS 将当前实例写入现有 `temporary_unavailable`，并交给既有恢复探针；这不是普通网关错误的持久化。长期文档只应引用本文的已落地边界，不得将其扩展为普通网关错误分类。

### 10.4 已确定方案的实施验收硬门

以下内容不是待确认的产品选择，而是进入代码实施时必须落成并通过的验收硬门：

1. 按已确定的 A 方案实施，并在实现合同中固定与既有 `temporary_unavailable` / `rate_limited` / `error` 来源的合并、优先级、解锁和探针恢复规则。
2. 固定锁死运行态的序列化主键、`generation`、租约失效、Redis 丢失 / 重启恢复和多实例 fencing 规则。
3. 明确 `complete_success` 的协议终态判定，尤其是 SSE 真实事件、正常终态、客户端取消和未知读取结果。
4. 为 `speed_first` 补充“锁死窗口内不 cutover、到期 / 硬门后恢复 cutover”的分支测试，并覆盖普通失败、首字慢、后备分组和 270 秒交接。
5. 为授权实例补充 owner / authorized 两套作用域的列表动作、详情回显、更新校验、操作日志和来源账户隔离测试。
6. 为抖动补充边界测试：base `5` 为 `3..7`、base `10` 为 `8..12`、base `11` 为 `6..16`、base `30` 为 `25..30`；并验证高并发下只有一个共享发送租约。

### 10.5 二次边界复审与冲突关闭结论

本轮针对“锁死是否会绕过现有机制、或被现有机制绕过”再次逐项复核，以下结论作为后续实现的硬边界：

| 边界 | 关闭结论 |
| --- | --- |
| 锁死作用域 | 以当前使用方的账号实例为全局作用域，跨协议、模型、lane、route strategy 和 group；不按 `account + protocol + model bucket + lane` 分片。协议 / 模型能力过滤仍是前置硬门，锁死不能把不支持的请求强行送上游。 |
| 授权实例 | 授权用户的实例状态与授权方原账户、其他被授权人隔离。现有含 `groupId` 的 `gatewayAccountRuntimeKey` 不可直接作为锁死主键；换分组、换路由或换 lane 不能开启第二个锁死窗口。 |
| 普通失败与死亡结算 | 普通网关失败继续沿用 Key 池、同 Key 有界重试、账户 / 分组候选和 opaque 错误规则；只有锁死事故达到死期且窗口内没有 `complete_success`，才触发 A 方案的持久状态 CAS。 |
| 账号内 Key | 锁死只否决跨账号 / 跨组切换，不否决现有账户内 Key 轮换和同账号重试；账户错误策略 `retry_next` 仍只代表其已有的兄弟 Key 语义，不扩大为跨账号授权。 |
| 所有跨账号出口 | 锁死门必须覆盖普通失败后的候选切换、`switchToFallbackGroup`、响应检查 `retry_next_account`、`speed_first` cutover、混合质量切换和会话亲和打破等出口；不能只拦一个 `NormalRouteFirstByteCutoverError` 分支。 |
| `speed_first` | 锁死窗口内可以继续计首字、记录慢样本和等待，但不得预占其他账号并切换；死期、硬不可用或 `unlock` 后才恢复原 cutover。 |
| 硬门 | 熔断 `OPEN`、半开确认、代理失败、并发容量、账号 / 来源过期、凭据不可装配、授权失效、模型不支持和显式停用优先于锁死。锁死不能为了“全力使用”绕过这些门；硬门成立时应按原机制结束、恢复或交接。 |
| 提交边界 | `semanticCommitted` 之后不拼接第二账号；锁死不增加副作用请求的透明重放能力。只有现有未提交 transport / 协议重试规则允许的路径才可继续。 |
| 请求墙钟 | 死亡窗口是跨请求的账号运行态，不是请求预算。`GatewayRequestWallBudget` 仍约 270 秒，到期照常 `client_handoff`；客户端重试读取同一锁死运行态，服务端不得把 270 秒延长为 300 秒。 |
| 重试节流 | 只对锁死事故后的再次业务 attempt 施加共享 `nextRetryAt + lease`；首次派发和健康并发请求不等待。已有全局重试等待与锁死采样等待同一次只等待一次，实际取 `max(globalRetryDelay, sampledLockDelay)`，不能双重 sleep 或因每个 waiter 本地抖动形成波峰。 |
| 计时与竞态 | 死期从第一次真实失败 attempt 开始；无流量、排队、候选为空、取消或 unknown 不推进。死期到达不取消在途请求；在 `DEAD_CONFIRMED` CAS 前完成的成功赢得结算，之后的迟到结果不能清除持久状态。 |
| A 方案持久状态 | `accounts.status` 仍使用现有 `temporary_unavailable`，但来源、事故代次、原状态、死期和恢复资格必须存于独立锁死元数据；禁止只写 `last_error_*`，也禁止把 `lock_policy` 增加为普通账户状态值。仅从 `active` 且无更强 / 外部状态的实例写入；外部状态已存在时不覆盖。 |
| 探针与恢复 | A 写入后复用既有冷却 / 探针状态机。探针恢复 `temporary_unavailable` 时保留列表上的锁死策略并回到 `LOCKED_IDLE`；锁死事故结束不等于自动解除锁死。 |
| `unlock` | `unlock` 使后续请求立即不再受锁死门约束，且不取消在途 attempt；不清除外部 `disabled` / `error` / `rate_limited` / `temporary_unavailable`，也不因解锁直接复活锁死造成的临时不可用，后者仍走现有探针 / 人工恢复。 |
| 配置和版本 | 修改死亡窗口、重试间隔或锁死动作时递增 `configRevision` / 事故 generation；旧租约、旧死期和旧 CAS 结果全部失效。配置变更不重置 270 秒墙钟，也不把已提交响应变成可重放。 |
| 后台与副作用 | 后台探针、人工测试、OAuth 刷新和账户迁移继续使用各自退避 / 租约，不计入锁死“全死”成功证据，也不共享锁死重试节流；锁死不扩散到来源账户、代理、IP 或其他账号。 |

因此，当前方案不存在需要另造“超级锁死调度器”的理由：实现只需增加账号实例级锁死策略 / 共享闸门、死期结算 CAS 和管理端操作，并在既有跨账号决策点接入一个否决门。任何试图通过提高优先级、复制 `latency_degraded` 键、改写全局重试次数或绕过硬门来实现锁死的方案均视为范围漂移。

本轮深度复审未修改业务代码、数据库 schema 或 API；只同步方案已确定的设计文档。工作区内其他未提交改动保持不变。
