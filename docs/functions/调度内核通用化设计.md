## 1. 结论

1. 生产请求 7bdf2099 暴露的事故形态（高优账号被 turn 避让后整体剔除出候选、低优账号跨层上位、约 199 秒后才由 last-resort 翻回）根因是**画像语义进入了调度内核**：内核无法从通用调度语义解释"为什么跳过了用户显式配置的高优先级账号"。
2. 修复方式不是给该画像分支打补丁，而是把内核内全部画像/供应商语义残留（第 3 节清单）通用化：排除语义收敛为**通用调度排除集**（分派段状态机：段内让位、动态翻回、per-account 资格、不绕过硬门、保持速度优先健康分段，见 5.1 节），超时豁免收敛为**参数化布尔/枚举**（含大输入 extended 档维度），具名适配器错误收敛为**通用错误契约接口**（三处消费语义全保留），历史清理门收敛为**三维历史准备策略参数**。
3. 通用化之后，内核对"你是哪个客户端/画像/供应商"零感知；turn 避让退化为排除集的一个来源（由准备层之前的 gatewaycodex 服务产出），未来下线或新增排除来源都不需要改内核。
4. 本文当前状态为文档契约有界通过，代码实施未开始；按第 6 节批次进入代码实施前仍须完成对应 Mock、隔离集成和桥接 oracle 验收。第 7 节为实施验收标准；第 8 节记录已裁决事项与实施前取证项。

## 2. 背景与动机

### 2.1 触发事故

生产请求 7bdf2099（2026-10-09 02:37:47 UTC）累计约 199 秒。根因链逐段如下（每段均可在代码中定位）：

1. 同一 Codex turn 内，aotera 账号（超级优先层、优先级 0）此前发生客户端可见失败，turn 避让激活。激活阈值与 TTL 为：`committed≥1`，或 `retryable≥2`，或 60 秒窗口内 `incomplete abort≥2`；状态 TTL 30 分钟。证据：`backend-go/projects/gateway/internal/gatewaycodex/turnretry.go:39-46`（常量 `codexTurnRetryTtlMs = 30 * 60_000`、`codexTurnAccountAvoidanceFailureThreshold = 2`、`codexTurnIncompleteAbortWindowMs = 60_000`）、`backend-go/projects/gateway/internal/gatewaycodex/turnretry.go:912-940`（`codexTurnAccountAvoidanceActivated` = 强避让 `committed > 0 || retryable >= 2` 或弱避让 60 秒窗口 `aborts >= 2`）。
2. 预调度排序正确：tier 保持，aotera 仍排第一，`selectedAccountId=aotera`。即准备层的排序语义没有问题。
3. 但调度引擎内核把被避让账号从候选列表**整体剔除**（不分层）：`backend-go/projects/gateway/internal/gatewaydispatch/upstreamdispatch.go:553-574`（`filterCodexTurnAvoidedAccounts(dispatchAccounts, codexTurnAvoided, false)` 对整个 dispatch 列表过滤）。
4. 低优先级账号（优先级 10）上位先打，连续 3 次约 60 秒首响应超时耗尽。
5. last-resort 兜底回头用 aotera：`upstreamdispatch.go:1216-1236`（`codexTurnAvoidanceActive && !codexTurnReversalFired` 时取未耗尽的被避让账号重进候选），跳转标签 `goto codexTurnReversalPass` 位于 `upstreamdispatch.go:843`。aotera 随后 12.8 秒成功。
6. 净效果：跨层降级**越过了用户显式配置的优先级边界**——用户配置 aotera 为超级优先层，系统却先打了 180 秒注定失败的低优账号。

### 2.2 架构判定

调度主流程必须只有一套通用逻辑；客户端画像与供应商差异只允许存在于协议适配层与用户显式配置。调度内核（候选选择、排序、过滤、重试、超时）只接受通用参数：优先级、熔断状态、超时预算、重试预算、通用排除集。内核不得感知"你是哪个客户端/画像"。

### 2.3 排查性理由

画像分支进入内核后，故障排查者无法从通用调度语义推断实际选号行为——本次事故即是：排序日志显示 aotera 第一，实际内核却先打了低优账号，两套语义叠加后行为不可推理。同时画像分支使内核状态组合按客户端种类膨胀，隐藏 bug 难以被通用行为测试覆盖。

## 5. 目标契约

### 5.1 通用调度排除集（替代 CodexTurn 两字段 + 内核两段）

**内核入参新形状**（最终命名实施时定，语义如下）：

```text
SchedulingExclusions {
    ExcludedAccountIDs []string
}
```

- **产出位置**：准备管线（`preparation.go`）。来源避让（turn / client-source）与任何未来来源级排除统一在准备层算出最终排除集合；画像语义（阈值、TTL、状态键、开关）全部留在准备层之前的 `gatewaycodex` 服务，内核不 import。
- **tier 与分派段定义（不得简化）**：tier 沿用引擎既有四元组（`backend-go/projects/gateway/internal/gatewaycircuit/suppression.go:1028-1047`：`modelRank:fallbackRank:superRank:priority`），不得折算为 `account.Priority` 数值。准备层在最终候选顺序确定后，沿该序列生成**连续 run**，并显式传入有序分派段列表；每段至少包含以下元数据：
  ```text
  DispatchSegment {
      OpaqueSegmentID string
      Tier { ModelRank, FallbackRank, SuperRank, Priority }
      Accounts []AccountCandidate // 保持最终候选原顺序
  }
  ```
  `OpaqueSegmentID` 只用于关联同一次准备结果和审计，不参与排序。段边界由准备层最终顺序中的**外层调度段与四元 tier 的联合连续 run**决定：健康/降级、人工迁移、热质量重排、并发等待后的 reload 等既有外层段界必须切断 run，即使相邻账户的四元 tier 完全相同也不得合并；反之，仅四元 tier 相同且处于同一外层段时才允许归入同一 run。不重排候选、不跨段合并后来再次出现的相同 tier、不按四元组数值重新排序。所有入口、重排和重试路径都必须携带这组段元数据；等待或 reload 得到的新顺序必须重新生成外层段边界和 `OpaqueSegmentID`，不得复用旧段。
- **准备阶段的副作用边界**：分派段生成只投影准备层已经得到的候选顺序、四元 tier 和分段元数据，不预先调用 `CanAttemptAccount`、熔断确认、并发租约或其他会改变状态的硬门，也不得先取得 lease 再在真实尝试路径重复取得。账户资格以既有真实尝试路径的硬门结果为准。段内去重必须保留合法的预约上下文；`SameAccountRetry`、`KeyRotation`、有效锁租约或其他现有预约不能仅因账户 ID 已出现、已释放或已尝试而被错误去重。
- **排除与释放状态**：`ExcludedAccountIDs` 在本次引擎调用入口由准备层固化；引擎内部维护 `releasedAccountIDs`，初始为空，在段之间、外层等待和同一次调用内的 reload/reorder 中持续保留，新的引擎调用重新开始。`releasedAccountIDs` 只表示解除软排除，不代表绕过硬门或增加尝试预算。
- **内核语义（目标行为，含事故修复）——逐段状态机**：
  - 引擎按分派段顺序推进，对每段先按原顺序处理非排除候选。每个候选的可调度性只由真实尝试路径中的既有硬门决定（熔断确认窗口、账户准入注册 `CanAttemptAccount`、并发、去重及其他准入检查）；排除集只提供软排除。
  - **翻回触发**：当该段的普通候选已真实耗尽或被硬门逐个跳过，且该段仍有尚未进入 `releasedAccountIDs` 的排除集账号时，解除该段这些账号的软排除并按原顺序尝试。段入口即没有普通候选时同样触发；中途普通候选腾空时不得先进入下一段。解除之后按既有尝试、失败和等待规则继续。
  - **反例的固定尝试序列**：候选 `[B 健康 T0，C 健康 T1，A 降级 T0]` 且仅 B 在排除集时，准备层必须形成三个连续段。T0 健康段无普通候选，先释放并尝试 B；若 B 按既有规则成功则立即结束，若 B 耗尽或被硬门终止则进入 C 所在的健康段；若 C 成功则立即结束，若 C 也按既有规则耗尽，则进入降级段并按原顺序尝试 A（A 不在本例排除集）。失败/硬阻路径的尝试序列为 `B → B 耗尽/硬阻 → C → C 耗尽 → A`；不得把降级 A 提前，也不得静默跳过被排除的 B。
  - **硬门边界**：释放只解除软排除，不绕过熔断确认、准入注册、并发和其他硬门。临时硬阻按原有等待/重试规则处理；硬终止、失败去重或已结算的终态不因释放而复活。若释放后的账号暂时不可调度，`releasedAccountIDs` 仍保留，等待恢复后沿原规则继续，不再次消耗翻回资格。
  - **失败与预算**：普通候选真实耗尽后才释放尚未释放的软排除；释放资格本身每个账号每次引擎调用最多一次。`SameAccountRetry`、`KeyRotation` 和合法预约不增加翻回预算，也不因排除集再次扣除其既有重试预算；钉住目标按既有钉住规则执行。
  - **多段组合**：每段独立维护其未释放排除账号，但共享本次调用的 `releasedAccountIDs` 和既有失败/去重结算。高段释放失败后，低段仍按自身顺序释放其尚未释放的排除账号；进入下一段或外层等待前，上一段尚未释放且应解除的软排除必须先结算，不能把未释放状态带成跨层静默跳过。
  - **审计**：现有 `last-resort` 一次性兜底（`upstreamdispatch.go:1216-1236` + `:843`）由上述确定性状态机取代。内核只记录通用事件 `gateway_dispatch_exclusion_release`，字段至少包含 `opaqueSegmentId`、四元 `tier`、`candidateAccountIds`、`releasedAccountIds` 和释放原因；旧事件名 `client_source_avoided_accounts_last_resort` 如需兼容历史查询，只能在内核外的审计投影层提供别名，不能继续作为内核语义分支。
- **理由**：跨层降级使"优先级"这一用户显式配置被隐式行为推翻；同层让位保留了"同层内避免重复踩同一失败账号"的价值；动态翻回消除了本次 199 秒事故形态及其入口快照变体。
- **熔断确认路径豁免**：排除集不影响熔断确认路径的既有语义（现状条件 `AccountCircuitConfirmation == nil`，见 `upstreamdispatch.go:561`），保留。

### 5.2 超时豁免参数化

- `RequestCoordinationContext.TimeoutPolicy`（字符串枚举）→ `TimeoutsDisabled bool`；总时间档位 → `TotalTimeLane normal|extended`（或等价枚举）。
- **TotalTimeLane 的判定输入必须保留大输入维度（复审补齐）**：现行选档是双条件——`compactionLane = CompactionTimeoutsDisabled || EstimatedInputTokens >= routestrategies.SpeedFirstLargeInputTokenThreshold`（`dispatchsingle.go:1044-1067`，选档与常量 `:1008-1011`）。即**非压缩大输入同样走 extended 档**。参数化后 lane 判定输入（超时豁免布尔 + 估算输入 token 与阈值）由链面完整传入，行为不变；不得把 lane 归因于压缩单一维度。
- 请求形状判定（`/responses/compact` 路径或 body 含 `compaction_trigger`，`circuitfacade.go:17-55`）从内核移出，与 preflight 既有判定（`preflight.go:270` → `backend-go/projects/gateway/internal/gatewaycodex/compactioncontract.go:22-31`，wall budget `Unbounded`）和链面镜像门（`cmd/juhe-ai-gateway/chain_v1_speedfirst.go:592-601`）**三轨合一**为准备/preflight 层单点计算，链面与引擎消费同一结果；产生点 `chain_v1_loop.go:174-176` 的重导出通道与零消费死拷贝 `gatewayresponse/codexcontract.go:43-53` 随批次 2 一并删除。
- **行为不变约束**：豁免面维持现状口径——wall 整体预算、首响应等待、首字截止、attempt 生命周期、响应层 read plan 豁免；总时间软观察保留（extended 档阈值 300s）；重试 backoff、`NoAvailableAccountWait` 不豁免（豁免面的权威表述以 `preflight.go:903-910` 的 `codex_compaction_timeouts_disabled` 审计口径为准）。

### 5.4 账户准备历史清理门契约化

- **现状事实与边界**：当前清理由请求兼容性、endpoint family、账户适配路径共同决定。`BuildPreparedUpstreamRequestParts` 先执行前置清理，OAuth 适配器可在构造出站 body 时清理并通过 `MarkGatewayCodexHistorySanitized` 写入已处理标记，构造完成后还会执行后置清理并先检查 `IsGatewayCodexHistorySanitized`。`chain_driver.go:544-556` 的 OpenAI OAuth 分支当前无条件传入 `SanitizeCodexHistory: true`；因此 SDK→OAuth 也会经过适配器清理。三处不能合并成单一账户协议判断，也不能把已处理标记丢掉。
- **目标形状**：由协议适配层根据账户协议形态、请求 `RequestClientCompatibility`、endpoint family、是否桥接/压缩恢复等输入，计算单一通用 `HistoryPrepPolicy` 传入准备链。策略表达三个执行阶段和去重规则，不暴露具体供应商或适配器名称：
  ```text
  HistoryPrepPolicy {
      Front          preserve | sanitize_inline
      Adapter        preserve | sanitize
      Post           preserve | sanitize
      SkipIfProcessed bool
  }
  ```
  `Front` 是 driver 之前对请求上下文的处理，`Adapter` 是适配器自己的出站 body 处理，`Post` 是 driver 返回 body 后的处理；`SkipIfProcessed` 使用现有序列化 body 标记，已标记时后续阶段必须跳过重复清理。保留当前前置+后置两阶段顺序；把 OAuth worker 的延迟步骤表达为通用 `Adapter=sanitize`，不新增清理次数、不改变 Store/持久化参数。
- **已知形态矩阵（先锁定源码事实，再实施）**：下表是实施前必须逐项取证的最小矩阵；“当前可证”只记录已从源码读到的条件，尚未确认的阶段必须由 Mock/集成取证补齐。
  表中“SDK/Codex”是请求来源分类，必须在测试夹具中映射到实际 `RequestClientCompatibility` 和 endpoint family；被能力门拒绝的组合也要记录为拒绝 oracle，不能把它们写成“无清理”。

  | 形态 | 当前可证的入口条件 | 前置 Front | 适配器 Adapter | 后置 Post / 标记 |
  |---|---|---|---|---|
  | SDK → API Key | `requestClientCompatibility` 通常不是 `codex_responses`；API Key driver 不走 OAuth normalizer | 保留 | 保留 | 保留；验证兼容性 body 是否携带已处理标记 |
  | SDK → OAuth | 先经过 OAuth 能力门；当前**非空且不为** `codex_responses` 的兼容形态会在 `chain_driver.go:780-782` 被淘汰，能进入 OpenAI OAuth 分支的请求仍传 `SanitizeCodexHistory: true`（`:544-556`） | 按实际兼容性与 endpoint 条件取证 | 清理 | 清理后标记；后置遇到标记必须跳过 |
  | Codex → API Key | `codex_responses` 且 endpoint family 为 `responses` 时前置 guard 命中 | 清理 | 保留 | 未带标记时按现有后置逻辑清理；带标记时跳过 |
  | Codex → OAuth | `defersCodexResponsesHistorySanitizationToOpenAIOAuthWorker` 条件命中 | 延迟 | 清理 | 适配器写标记；后置跳过 |
  | Chat bridge | bridge 可能恢复/合并历史后再进入 API Key 或 OAuth driver | 不预设 `none`；按组合取证 | 按目标账户 adapter 取证 | 标记必须跨 bridge→driver→post 保留或明确失效原因 |

- **桥接组合验收（不得用笼统 `none` 代替）**：至少分别覆盖以下组合，并记录每一阶段的输入、输出、清理调用次数、`SkipIfProcessed` 命中情况及 `input`/`previous_response_id` 变化：
  1. Responses 新会话 → Chat bridge → API Key；
  2. Responses 携带 `previous_response_id` → Chat bridge → API Key；
  3. Responses 新会话 → Chat bridge → OAuth；
  4. Responses 携带 `previous_response_id` → Chat bridge → OAuth；
  5. `/responses/compact` 恢复已有 bridge snapshot → API Key；
  6. `/responses/compact` 恢复已有 bridge snapshot → OAuth；
  7. bridge 恢复失败/无快照后继续普通请求（API Key、OAuth 各一例）。
  每个组合都要以真实 bridge preflight/restore 结果作为 oracle，确认前置清理、适配器清理、后置清理和已处理标记的行为等价；无法从现有源码证明的组合标记为待实现取证，不得写成“无需清理”。
- **行为等价约束**：策略只改变参数承载位置，不改变当前两阶段调用顺序、清理器输入、`Store=false` 与 `TargetPersistenceScope="none"` 等现有参数；普通 SDK、Codex Responses、OAuth 适配器和 bridge 状态恢复的异常都必须保留原始错误。矩阵验收以阶段级调用记录和序列化 body 标记为准，不能只断言最终 body 相同。
