# API Key 多分组路由设计

> 本文定义一个 API Key 绑定多个分组号池后的路由策略、故障切换、存储、接口和前端规则。
> 目标是让调用方继续只使用一个本地 API Key，并可按主备、轮询或权重在多个分组号池之间分配入口流量，而不是让用户手动切换 Key 或 Base URL。

## 背景

早期 API Key 只能绑定一个分组；当前实现已经支持一个 API Key 绑定一个或多个调用方自有分组号池。这个能力要解决两个问题：

- 一个分组就是一个号池；首选号池暂时不可用、全部账号繁忙、模型不匹配或授权账户失效时，调用方可以在真实派发前自动尝试备用号池。已经进入某个号池真实派发后，如果该号池账号全部尝试失败且尚未向客户端写出响应，也可以回到 API Key 的分组候选顺序重新分配分组；重新分配会排除本次请求已经失败过的账号，只继续使用当前仍正常可承接的账号。
- 用户需要把多个号池挂到同一个 Key 下，并选择“主备优先”“轮询分配”或“权重分配”来表达不同流量策略。

新增能力应保持现有边界：

- API Key 仍是客户端入口、调用方身份和额度边界。
- 分组仍是账号池和分组内调度边界。
- 多分组能力只解决“本次请求先选择哪个分组号池”，不把多个分组里的账号打散成一个全局大池。

## 概念定义

| 概念 | 定义 |
| --- | --- |
| API Key | 对外访问凭据，决定调用方系统账户、Key 状态、Key 额度和审计归属 |
| 号池 | 一个分组内的账户集合，包含自有账户和已经加入该用户本地分组的授权账户 |
| 分组路由绑定 | API Key 与某个本地分组之间的候选关系，包含优先级、权重和启停状态 |
| 分组路由策略 | API Key 级策略，决定本次请求的分组候选顺序，支持主备优先、轮询分配和权重分配 |
| 分组路由 | 网关在调度前按 API Key 路由策略选择一个当前可承接请求的分组 |
| 分组内调度 | 选定分组后，继续使用个人分组或高并发分组已有账号调度逻辑 |

当前支持三种 API Key 级分组路由策略：

- `priority_failover` / 主备优先：默认策略，按绑定优先级从小到大尝试；前一个号池不可承接时再进入后一个号池。
- `round_robin` / 轮询分配：启用分组等权组成环，每次请求从下一个分组开始尝试；若当前分组不可承接，则按本轮候选顺序继续尝试后续分组。
- `weighted_round_robin` / 权重分配：按绑定权重使用平滑加权轮询生成候选起点；大量请求下命中比例接近权重比例，不可承接时仍按本次候选顺序继续尝试后续分组。

这些策略只做入口级分组选择：

- 允许跨分组做请求级分流。
- 不把 A 分组和 B 分组账号混排。
- 不共享不同分组的队列、等待状态、账号并发槽或账号亲和运行态。
- 只有当前策略候选中的分组无法承接本次请求时，才尝试候选顺序里的下一个分组；真实上游账号耗尽后允许在同一个有界候选环内继续寻找未失败且当前可承接的账号。

## 分组隔离底线

分组和分组之间必须保持容器隔离。一个分组就是一个号池容器，API Key 多分组路由只允许在真实派发前按 API Key 路由策略选择“本次请求先进入哪个容器”，不能演进成跨分组协同调度。

产品心智模型可以这样理解：**API Key 像域名，分组像 IP / 容器**。多个分组绑定同一个 API Key 后，等价于这个 Key 背后有多个按策略排列的号池容器；区别只是先尝试哪个容器，不是把账户能力、账户状态或会话亲和按分组重新拆一套。

必须固定两个维度：**分组是调控维度，账户是资源维度**。分组只决定 API Key 背后怎么分配号池、哪个容器先承接、哪个容器后备；它不改变账户本身，也不制造新的账户语义。账户的能力、类型、凭据、代理、状态、冷却、并发、质量、错误策略和亲和都属于账户资源维度，不能被分组维度打乱。

- 允许的跨分组行为包括按 API Key 路由策略切换候选号池、写下游前当前号池账号耗尽后回到 Key 层重新分配分组、写下游前配置化流式拦截耗尽当前号池后的后续号池切换，以及记录安全诊断摘要，例如尝试过哪些分组、失败 reason code 和最终命中分组。
- 不允许跨分组账号混排、跨分组借号、跨分组共享队列或跨分组共享分组级等待状态；已经写下游输出后的失败不得跨分组透明重放。
- 不允许把多个分组的队列、分组容量、分组等待状态或分组内部策略合并成热路径调度依据；需要展示总览时只能走统计缓存或诊断摘要，不能反向影响分组内调度。
- 账户不关心分组。账户能力、支持模型、账号类型、凭据、代理、物理状态、冷却、短期屏蔽、并发占用、质量分、错误策略和会话亲和都是账户级事实，不能因为账户出现在不同分组里就被拆成多份或重做一套。
- 切换只能发生在写下游输出前。选中分组并开始上游请求后，失败、冷却、账号切换、队列等待和恢复探活优先在当前请求已选容器内完成；如果当前容器内账号全部尝试失败且尚未写下游输出，才回到本 API Key 的候选分组顺序继续寻找未失败且当前可承接的账号。其中账户级副作用按真实命中的账户行生效，授权账户命中的是被授权人的实例账户行。
- 个人分组和高并发分组可以作为同一个 Key 的候选号池混合绑定，但这只是路由候选混合；选中后继续使用该分组自己的内部策略，不能让高并发策略扩散成跨分组调度器。
- 高并发分组的短队列、单 IP 并发保护、每 Key 队列上限和分组等待状态必须以 `systemAccountId + apiKeyId + groupId` 或更细维度隔离，避免不同分组互相污染容器级运行态；账户并发和会话亲和仍按账户级规则处理。
- 审计和日志可以记录跨分组切换过程，但这些记录只用于排障和追溯，不能变成跨分组共享运行态。

## 核心规则

- 一个 API Key 可以绑定一个或多个调用方自己的本地分组。
- 绑定的分组必须全部属于 API Key 所属系统账户；管理员代某个用户维护 Key 时，也只能绑定该被管理用户自己的分组。
- 授权方的分组不能直接作为被授权方 API Key 的号池；被授权账户必须先进入调用方自己的本地分组，再由该本地分组参与 Key 路由。
- 第一版要求同一个 API Key 下所有绑定分组的 `provider_code` 一致。当前只有 OpenAI 供应商，但先把规则固定下来，避免未来多供应商时同一个 Key 的 `/models`、路径能力和错误语义变得含糊。
- 至少保留一个 `active` 绑定。前端和后端都要阻止移除或停用最后一个 active 号池。
- 优先级数字越小越靠前，主备优先策略下建议 UI 展示为“主号池、备 1、备 2”；轮询和权重策略下优先级作为环顺序、兜底顺序和稳定排序依据。同一个 API Key 下 active 绑定的优先级必须唯一；保存时后端可以归一化为 `1, 2, 3...`。
- 权重只在 `weighted_round_robin` 下生效，取值范围 `1-100`，默认 `1`；轮询和主备优先策略保留权重字段但不参与路由。
- disabled 绑定只作为配置保留和列表展示，不参与网关路由。
- API Key 的美元成本额度在所有绑定号池之间共享，不因绑定多个分组而拆成多份额度。
- `groups.enabled` 只表示人工启停开关，不承载“当前是否可用”的运行态；分组是否可承接由分组内当前正常可调度账号派生。
- 多分组切换主要发生在分组选择 / 调度预检阶段：如果当前策略选中的 A 号池没有正常可调度账号，或本次请求在 A 号池内没有账号能通过路径能力 / 客户端 profile / 模型预检，才按本次候选顺序尝试 B 号池。一旦进入某个分组内真实上游派发，普通上游失败先在该分组内按账号切换、短期屏蔽、错误策略和恢复探活处理；如果 A 号池账号已经耗尽且尚未写下游响应，可以回到 API Key 的候选顺序重新分配分组。重新分配时跳过本次请求已经失败过的账号，因此 A -> B -> C 后如果 A 出现未失败且当前可承接账号，可以继续由 A 承接；如果所有候选账号都失败或不可承接，则结束本次请求。配置化流式拦截在写下游前命中、允许服务端重试且 A 号池账号耗尽时，也可以按同样规则尝试后续号池。

## 分组运行可用状态

分组需要把“人工开关”和“运行可用状态”分开，否则账号自动恢复时很容易把分组状态做乱。

| 状态层 | 存储 / 来源 | 含义 | 写入方式 |
| --- | --- | --- | --- |
| 人工开关 | `groups.enabled` | 管理员或用户显式启用 / 停用分组 | 只由分组编辑、删除、恢复等人工操作改写 |
| 绑定开关 | `api_key_group_bindings.status` | 某个 API Key 是否启用该号池 | 只由 API Key 号池配置改写 |
| 运行可用状态 | 由分组内账号和授权状态派生 | 分组当前是否有正常可调度账号、是否空池、是否全部不可用 | 由账号 / 授权 / 绑定变更即时重算，后台 job 定期兜底 |

派生状态建议使用展示字段或缓存字段承载，不直接覆盖 `groups.enabled`：

| 派生状态 | 口径 |
| --- | --- |
| `normal` / 正常 | 分组启用，且至少有一个正常可调度账号 |
| `empty` / 空池 | 分组启用，但没有绑定任何账号 |
| `no_schedulable_accounts` / 无可调度账号 | 分组启用，存在账号，但全部因账户停用、异常、冷却、过期、授权关系不可用、绑定未启用、代理不可用或凭据不可用被过滤；授权实例不再读取 `group_accounts.local_*` 作为运行态事实 |
| `disabled` / 已停用 | `groups.enabled = 0`，人工硬停用 |
| `authorization_unavailable` / 授权不可用 | 当前用户访问的是授权分组或授权账号，授权暂停、过期、回收、归还或额度不可用导致无法调度 |

运行态更新采用“事件触发 + 后台巡检”：

- 账号创建、编辑、启停、恢复正常、进入 / 退出冷却、套餐到期变更、代理绑定变更、分组绑定变更、授权暂停 / 恢复 / 回收 / 归还时，立即标记相关分组运行态需要重算，并清理网关 runtime cache。
- 当前后台 worker 通过 `group-account-stats-refresh` 刷新分组账户统计缓存，运行时最终仍以本次 DB service 读取到的分组候选账号、授权状态、额度缓存和账号硬状态为准。后续如果要增加独立 `group-runtime-health` 派生状态 job，必须先补 schema / runtime snapshot / 回归验证，不能把它当作当前事实。
- 网关调度不能只信缓存的派生状态，最终仍以本次 `listOpenAIAccountsForGroup` 得到的正常可调度账号列表为准；派生状态主要服务列表展示、筛选、诊断和提前跳过明显不可用号池。
- 账号从异常 / 冷却恢复为正常时，应优先触发所在分组即时重算；后台 job 只是兜底，不作为用户等待恢复的唯一通道。

## 混合分组专项规则

这里的“混合”必须拆开判断，不能笼统允许或禁止。

| 混合类型 | 第一版规则 | 处理方式 |
| --- | --- | --- |
| 跨供应商混合 | 禁止 | 同一个 API Key 下不能同时绑定 OpenAI、Claude 等不同 `provider_code` 分组。未来如果要支持，需要先设计跨供应商模型目录、路径能力和错误语义，不在本轮做隐式兼容 |
| 分组类型混合 | 允许 | 同一个 Key 可以同时绑定个人分组和高并发分组，例如主号池是个人分组、备号池是高并发分组。路由层只决定选哪个分组，选中后使用该分组自己的调度策略 |
| 账号类型混合 | 允许 | 同一个 OpenAI 分组里可以同时有 OpenAI API Key 账户和 OpenAI OAuth 账户。请求进入后先按路径、模型和账号类型能力过滤候选账号，不支持该请求的账号直接跳过 |
| 自有 / 授权账户混合 | 允许 | 一个本地分组可同时包含自有账户和授权实例账户。授权实例只在最终用户授权、授权额度、实例账户状态和本地绑定都可用时进入候选 |
| 绑定状态混合 | 允许 | active 绑定参与路由，disabled 绑定只展示和保留配置，不参与运行时 |

### 跨供应商混合

跨供应商混合先禁止，原因不是数据库做不到，而是网关语义会变得不清楚：

- `/models` 应该返回哪个供应商目录不明确。
- 同名模型在不同供应商可能不是同一能力。
- 路径、请求体、响应体和错误结构可能需要不同 adapter。
- Key 额度虽然可以共享，但授权额度、价格目录和审计解释会变复杂。

因此第一版写接口必须校验所有绑定分组 `provider_code` 一致。运行时如果发现脏数据导致 provider 不一致，应跳过该绑定并记录 `provider_mismatch`，同时建议在管理列表给出修复提示。

### 分组类型混合

个人分组和高并发分组可以混合绑定，但跨分组路由优先级高于分组内排队：

- 如果 A 是高并发分组且当前没有立即可派发账号，路由层应先看 B、C 是否能立即承接，而不是直接让请求在 A 队列里等待；这只是调度前改选分组，不共享 A、B、C 的队列或并发槽。
- 如果所有 active 号池都不能立即承接，再选择本次候选顺序里最靠前且允许排队的分组进入有界短等待。
- 如果 A 是个人分组且账号都被硬过滤、硬并发已满或本地屏蔽，直接尝试 B。
- 分组类型不参与跨分组评分；`priority = 1` 的个人分组仍优先于 `priority = 2` 的高并发分组，除非个人分组无法承接。

这样可以避免“主号池排队很久，备号池明明空闲却不用”的体验问题，也避免把高并发策略扩散成跨分组全局调度器。

### OpenAI 账号类型混合

OpenAI 分组内允许混合 OAuth 账户和 API Key 账户，但每个账号类型的上游能力不同：

- OpenAI API Key 账户按公开 OpenAI-compatible `/v1` 能力透传。
- OpenAI OAuth 账户走 Codex adapter，只支持该 adapter 明确列出的 Responses / Codex 路径。
- `/models` 这类本地目录接口不应为了某个账号类型额外发上游请求，仍按本地供应商模型目录返回。

运行时需要在分组内账号硬过滤前增加“请求能力过滤”。当前落地顺序是：运行时快照先选出有正常候选账号的主号池；请求预检阶段再按当前路径、客户端 profile 和模型过滤账号。如果当前号池的候选账号全部被能力或模型过滤掉，并且该 API Key 还有更低优先级的 active 绑定，则在真实上游派发前继续尝试后备号池。

| 请求类型 | 候选账号处理 |
| --- | --- |
| 公开 `/chat/completions` | OAuth 账号不参与，API Key 账号可参与 |
| 公开 `/responses` | API Key 账号可按公开 API 透传；OAuth 账号只有在命中 Codex adapter 支持范围时参与 |
| Codex 专属 Responses / compact | 只允许支持 Codex adapter 的 OAuth 账号或后续显式支持该 profile 的账号参与 |
| Images API / 图像工具 | Images API、GPT Image / DALL-E 模型和强制 Responses 图像工具先校验系统账户图像生成权限，再只保留支持对应图像能力的账号；仅 auto 暴露的 Responses `image_generation` 工具在权限关闭时会被移除并按文本请求继续 |
| 不支持路径 | 当前分组内没有可支持账号时，按 `request_capability_mismatch` 记录并尝试下一号池 |

如果 A 分组只有 OAuth 账号，而当前请求是 OAuth 不支持的公开路径，A 不算“可承接”，应尝试 B 分组。如果 B 分组里有 API Key 账号，则由 B 承接。这个切换优先在上游请求发出前完成；一旦已经进入 A 分组真实派发，普通上游失败先消耗 A 分组内可用账号，只有当前分组账号耗尽且尚未写下游输出时，才回到 API Key 的候选分组继续寻找未失败且当前可承接的账号。这样混合账号类型不会把请求打到明知不支持的上游，也不会因为 A 号池账号多但能力不匹配而阻断后续号池。

### 自有与授权账户混合

自有账户和授权账户可以混在同一个本地分组里。有效候选按账户逐个判断：

- 自有账户只看调用方自己的账户状态、套餐到期、调度开关、代理、模型和并发等条件。
- 授权账户在被授权侧是独立账户实例，候选过滤只看最终用户授权状态、授权额度、团队成员状态、实例账户自己的 `accounts.status / schedulable / cooldown_until / last_error_* / stream_failure_*` 和本地分组绑定。
- 归属人原账户的状态、冷却、调度开关、代理、分组绑定和删除不参与授权实例调度；需要暂停或回收授权实例时，只能通过授权列表修改授权关系。
- 如果授权账户失效，但同组自有账户可用，当前分组仍可承接。
- 如果同组所有账户都因授权关系、实例状态、绑定状态或额度被过滤，当前分组不可承接，路由尝试下一号池。
- 授权额度检查属于真实上游派发前的候选过滤；如果主号池剩余候选全部因授权额度耗尽被过滤，并且后备号池存在可承接账号，应切到后备号池，而不是直接返回授权额度耗尽。

这条规则能覆盖“主号池里授权账号被回收了，但还有自有账号”“主号池全部是授权账号且授权暂停了，切到备号池”两类实际场景。

## 路由触发矩阵

### 会切到下一个号池

| 场景 | 说明 |
| --- | --- |
| 绑定被停用 | `api_key_group_bindings.status = disabled`，直接跳过 |
| 分组不可用 | 分组不存在、已删除、被停用或归属不匹配 |
| 供应商不匹配 | 分组 `provider_code` 和本 Key 其他绑定不一致，应在写入时阻止；运行时发现则跳过并记诊断 |
| 请求能力不匹配 | 当前请求路径、客户端 profile、图像能力或账号类型能力在该分组内没有可承接账号 |
| 模型不匹配 | 当前分组内没有任何可调度账号支持请求模型 |
| 授权或绑定失效 | 分组内授权实例暂停、过期、回收、归还、额度耗尽、实例账户不可用或本地绑定不可用，导致无候选账号 |
| 账号池无可用账号 | 硬过滤后没有候选账号，例如账号停用、异常、限流、冷却、套餐到期、凭据不可用、代理不可用 |
| 分组运行态无正常账号 | 分组启用但派生状态不是正常，或本次读取不到正常可调度账号 |
| 本地容量不可承接 | 个人分组在调度前确认当前号池账号硬并发全满时，先尝试后续号池；高并发分组没有立即可派发账号时也先尝试后续号池；没有可立即承接后备时，再回到本次候选顺序里最靠前且允许排队的分组进入有界短等待或返回繁忙 |
| 本地短期屏蔽全量命中 | 当前号池候选账号全部处于 Web 进程本地短期屏蔽时，先尝试后续号池；没有可承接后备时，才在当前号池等待屏蔽释放 |

### 不会切到下一个号池

| 场景 | 说明 |
| --- | --- |
| API Key 无效 | Key 不存在、停用、删除、过期或系统账户不可用，直接拒绝 |
| API Key 额度耗尽 | Key 额度是入口级共享边界，命中后不尝试任何号池 |
| 请求本身无效 | JSON 解析失败、路径不支持、缺少必要字段或客户端协议错误，不进入号池路由 |
| 图像生成权限关闭 | 调用方系统账户未开启图像生成权限时，确定图像生成请求直接返回权限错误；仅 auto 暴露的 Responses `image_generation` 工具不切号，移除工具后按文本请求继续 |
| 已进入真实上游派发 | 选定分组后，普通上游请求失败先在该分组内账号切换和错误策略处理；当前分组账号耗尽且尚未写下游输出时，回到 API Key 候选分组继续寻找未失败且当前可承接的账号；已写下游输出后的流式中断不透明切到其他号池重放 |
| 已有可见流式输出 | 一旦已经向客户端写出可见 assistant 内容、reasoning 或工具参数，更不能服务端透明切到其他号池重放 |
| 非幂等或客户端续写敏感 | 可能造成重复副作用、重复工具调用或破坏客户端 turn 状态的场景，不做跨号池重试 |

## 调度流程

```mermaid
flowchart TD
  A["客户端请求"] --> B["校验本地 API Key"]
  B --> C["校验系统账户和 API Key 额度"]
  C --> D["读取 active 分组路由绑定"]
  D --> E["按 API Key 路由策略生成候选号池顺序"]
  E --> F["校验分组归属、启用状态和 provider"]
  F --> G["读取该分组候选账号快照"]
  G --> H["模型、授权、额度、实例状态和绑定硬过滤"]
  H --> I["请求能力和模型预检"]
  I --> J{"当前分组是否可立即承接"}
  J -- "否" --> K["记录安全失败原因"]
  K --> E
  J -- "是" --> L["进入分组内调度"]
  L --> M["分组内账号切换、错误策略和上游派发"]
  M --> N["写使用记录和审计，记录实际命中 groupId"]
  E --> O{"所有号池都不可用"}
  O -- "是" --> P["返回 OpenAI 兼容错误"]
```

高并发分组需要额外注意队列语义：多号池路由不能让请求在 A 分组长时间排队，同时 B 分组有空闲账号。建议第一轮按本次策略候选顺序尝试“立即承接”；如果所有绑定号池都没有立即承接能力，再进入本次候选顺序里最靠前且允许排队分组的短等待。等待期间释放、取消、超时和客户端断开仍复用高并发分组的队列边界。

这里的短等待只属于最终选中的单个分组，不能把多个分组排成一个共享等待队列；等待期间如果需要重新评估，也只能重新回到路由层选择一个分组，而不是在多个分组内同时占位或抢占账号。

## 运行缓存边界

主备优先策略可以继续缓存“本地 API Key + 当前命中分组 + 分组账号快照”的运行时结果，因为同一个 Key 在短 TTL 内反复命中同一个主号池符合预期。

轮询和权重策略不能缓存最终命中的 `group_id`，否则第一次选中某个分组后会在缓存 TTL 内持续命中同一分组，破坏分流比例。动态策略下：

- API Key 校验结果、分组绑定静态信息、分组账号列表和分组授权元数据仍可按现有短 TTL 缓存。
- “本次请求从哪个分组开始尝试”必须每次请求重新计算。
- 轮询游标和权重当前值属于单节点进程内易失运行态，服务重启后从初始顺序重新开始；它不参与账务、权限或统计事实。
- 动态策略只影响候选分组起点和 fallback 顺序，不改变分组内账号排序、账号亲和、账号并发和错误策略。

## 存储设计

新增业务库表 `api_key_group_bindings`：

```sql
CREATE TABLE api_key_group_bindings (
  id TEXT PRIMARY KEY,
  api_key_id TEXT NOT NULL,
  system_account_id TEXT NOT NULL,
  group_id TEXT NOT NULL,
  priority INTEGER NOT NULL,
  weight INTEGER NOT NULL DEFAULT 1,
  status TEXT NOT NULL DEFAULT 'active',
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL
);
```

建议约束和索引：

```sql
CREATE UNIQUE INDEX idx_api_key_group_bindings_unique
  ON api_key_group_bindings(api_key_id, group_id);

CREATE UNIQUE INDEX idx_api_key_group_bindings_priority
  ON api_key_group_bindings(api_key_id, priority)
  WHERE status = 'active';

CREATE INDEX idx_api_key_group_bindings_gateway_route
  ON api_key_group_bindings(api_key_id, system_account_id, priority, created_at, id)
  WHERE status = 'active';

CREATE INDEX idx_api_key_group_bindings_group
  ON api_key_group_bindings(group_id);

CREATE INDEX idx_api_key_group_bindings_owner
  ON api_key_group_bindings(system_account_id, api_key_id);

CREATE INDEX idx_api_key_group_bindings_owner_group_key
  ON api_key_group_bindings(system_account_id, group_id, api_key_id);
```

字段说明：

| 字段 | 说明 |
| --- | --- |
| `api_key_id` | 所属 API Key |
| `system_account_id` | 冗余 Key 所属系统账户，用于隔离、列表筛选和越权校验 |
| `group_id` | 候选号池分组，只能是该系统账户自己的本地分组 |
| `priority` | 路由优先级，小值优先 |
| `weight` | 权重分配策略下的分流权重，默认 `1`，范围 `1-100` |
| `status` | `active` / `disabled`，disabled 不参与路由 |

`api_keys` 增加 `group_route_strategy TEXT NOT NULL DEFAULT 'priority_failover'`：

| 值 | 说明 |
| --- | --- |
| `priority_failover` | 主备优先 |
| `round_robin` | 启用号池等权轮询 |
| `weighted_round_robin` | 启用号池按绑定权重平滑轮询 |

`api_keys` 不再保存单独的主号池字段。API Key 到分组的唯一事实来源是 `api_key_group_bindings`；列表、详情、筛选和网关运行态都从绑定表读取。网关运行态里的 `apiKey.selected_group_id` 表示本次已经选中的实际分组，避免把运行态选路结果伪装成 `api_keys` 表字段。

分组删除规则：

- 默认分组仍不允许删除。
- 删除非默认分组前，如果该分组是某个 API Key 的最后一个 active 绑定，后端应拒绝并提示先调整该 Key 的号池。
- 删除分组前只读取最多 101 条受影响 API Key 绑定作为固定窗口预检；如果受影响 API Key 超过 100 个，后端拒绝本次删除，要求先分批解除绑定后再删除分组，避免管理请求在业务库内全量枚举和大事务删除。
- 如果该分组不是最后一个 active 绑定，删除分组时在同一业务库事务内同步删除相关绑定，刷新 Key 校验缓存并写操作日志。操作日志记录受影响的 API Key 路由摘要，并把受影响 API Key 作为 affected target，方便追溯绑定移除。

API Key 删除规则：

- 业务删除 API Key 时同步删除 `api_key_group_bindings`。
- 历史使用记录、审计、统计扣减和记录物理清理仍按现有 API Key 删除流程投递后台 worker。

## API 契约

创建和更新 API Key 使用绑定数组表达号池：

```ts
type ApiKeyGroupBindingInput = {
  groupId: string
  priority: number
  weight?: number
  status?: 'active' | 'disabled'
}

type ApiKeyCreateOrUpdateInput = {
  name: string
  description?: string
  groupRouteStrategy?: 'priority_failover' | 'round_robin' | 'weighted_round_robin'
  groupBindings: ApiKeyGroupBindingInput[]
  expiresAt?: string | null
  quotaLimits?: Record<string, unknown> | null
}
```

写入规则：

- 创建 API Key 必须显式提交 `groupBindings`，不能由数据层隐式绑定默认分组；这样前端、接口和存储层都能统一拦截“未选择号池”的配置。
- 更新 API Key 未提交 `groupBindings` 时保留现有绑定；提交时按数组整体替换。
- 未提交 `groupRouteStrategy` 时默认 `priority_failover`。
- 后端校验重复分组、active 绑定数量、优先级唯一、权重范围、分组归属、分组启用状态和 provider 一致性。
- 后端允许个人分组和高并发分组混合绑定；分组类型不影响写入校验，只影响运行时选中该分组后的内部调度。

列表和详情返回：

```ts
type ApiKeyGroupBindingSummary = {
  id: string
  groupId: string
  groupName: string
  providerCode: string
  priority: number
  weight: number
  status: 'active' | 'disabled'
  groupEnabled: boolean
}

type ApiKeySummary = {
  id: string
  name: string
  groupRouteStrategy: 'priority_failover' | 'round_robin' | 'weighted_round_robin'
  groupBindings: ApiKeyGroupBindingSummary[]
}
```

筛选规则：

- `keyword` 仍只按 API Key 名称精确 / 前缀匹配。
- `status` 仍筛选 API Key 自身状态。
- `groupId` 匹配任意绑定关系；返回结果中带出绑定状态，让用户能看出该组是 active 还是 disabled。

操作日志：

- 创建、移除、停用、启用、调整优先级和整体替换绑定都应写操作日志。
- 操作日志不需要变成授权流水表；它只记录谁改了 API Key 的号池配置、改了哪些分组、优先级和状态。

## 前端设计

API Key 表单新增“绑定号池”配置区：

- 默认至少一行，选择当前用户自己的分组。
- 新增“分组路由策略”选择，支持“主备优先”“轮询分配”“权重分配”；未选择时默认“主备优先”。
- 主备优先下第一行展示为“主号池”，后续展示“备 1”“备 2”；轮询下展示“轮询 1”“轮询 2”；权重下展示“权重 1”“权重 2”。
- 权重分配下展示权重输入框，范围 `1-100`，默认 `1`；主备优先和轮询不展示权重输入，但后端仍保留默认权重字段。
- 支持添加号池、移除号池、上移、下移和启停。
- 分组选项只返回当前作用域自有分组；授权分组不出现在 API Key 绑定选项里。
- 分组选项不能因为某个分组已经被其他 API Key 绑定就隐藏；同一个分组允许被多个 API Key 复用。去重只发生在当前 API Key 当前绑定列表内：当前表单已选的其他行不再出现在本行下拉中，避免同一个 Key 重复绑定同一个分组。
- 选中第一个分组后，后续选项按相同 `provider_code` 过滤。
- 分组选项需要展示分组类型，允许个人分组和高并发分组混排；用户通过优先级决定谁是主号池、谁是备号池。
- 同一个 Key 内不能重复选择同一个分组。
- 至少保留一个 active 号池；禁用或移除最后一个 active 行时前端直接提示。

API Key 列表建议：

- “绑定分组”列改为展示多个标签：主备优先展示 `主号池：A`、`备 1：B`；轮询展示 `轮询 1：A`、`轮询 2：B`；权重展示 `权重 1：A 权重 3`、`权重 2：B 权重 1`。
- disabled 绑定用灰色标签展示“已停用”，但不参与调用。
- 如果主号池分组已停用或异常，列表给出轻量提示，避免用户以为 Key 会优先命中它。
- 分组筛选命中任意绑定关系，筛选后仍展示完整绑定列表。

错误提示建议：

- 所有绑定号池都不可用：`所有绑定号池均不可用，请检查分组账号、授权状态或号池优先级。`
- 最后一个 active 号池不能停用：`至少需要保留一个启用的号池。`
- 分组归属不匹配：`只能绑定该 API Key 所属用户自己的分组。`
- provider 不一致：`同一个 API Key 的绑定号池必须属于同一供应商。`

## 网关运行态与缓存

DB service 的 API Key 运行时快照应一次性带出：

- API Key 基础状态、系统账户状态和图像生成权限。
- API Key 额度缓存。
- active 分组绑定列表，主备优先按 `priority` 升序，轮询和权重按本次请求策略生成的候选顺序。
- 当前选中分组的基础状态、provider、分组类型、调度策略和候选账号。

热路径要求：

- 运行时先由 DB service 按 API Key 路由策略生成候选顺序，再选出第一个有正常候选账号的 active 分组，并把本次候选顺序随 API Key 一起返回；只有该分组在请求能力、模型、授权额度、本地屏蔽或本地容量预检中无法承接时，才按本次候选顺序做缓存化按需读取。
- 后备分组读取必须走 DB service 和网关 runtime cache，不能在 Web 进程同步读库；遍历上限由单个 API Key 的绑定数量控制，当前后端上限为 20 个分组。
- 单分组账号快照也必须有界：DB service 只按分组绑定优先级读取当前硬可调度账号窗口，当前最多返回 `256` 个候选账号；冷却中、停用、不可调度、过期和来源类型不支持的账号在 SQL 窗口前过滤。带账户自动启停计划的账号单独读取固定窗口，并在内存中按当前时段过滤后再与普通账号合并排序，避免计划账号因为普通账号数量过多被误漏。
- 主备优先下如果运行时快照命中的不是最高优先级 active 分组，说明当前处于临时后备路由状态；这类快照应使用短 TTL，避免主号池恢复后长时间仍停留在后备号池。
- 轮询和权重策略不能缓存最终选中的 `group_id` 运行时快照；每次请求都需要重新计算候选起点，否则会破坏分流比例。
- 路由计算只在本 Key 的绑定分组数量和对应分组候选账号集合内做有界遍历，不能扫描全局账号、全局分组、使用明细或审计明细。
- 请求能力 / 模型预检只遍历本 Key 已绑定号池及其候选账号；后备号池递进优先在真实上游派发前完成。已经派发上游后，只有当前号池账号耗尽且尚未写下游输出，或写下游前配置化流式拦截耗尽当前号池时，才可以回到 API Key 候选列表重新分配分组；重新分配仍只遍历本 Key 已绑定的有界号池列表，并排除本次请求已经失败过的账号。
- API Key 额度和授权额度判定必须先查当前进程本地短 TTL 决策缓存；决策缓存 miss 只能读取 background worker 被动推送到 server 内存的额度快照，不能为了本次请求主动通过 DB service 查询授权主表、团队授权表或统计额度窗口。worker 推送给 server 的额度快照必须有固定窗口，当前 API Key 成本快照最多 5000 条、授权决策快照最多 5000 条，server 接收端也要二次截断，避免一次 IPC 刷新阻塞主进程事件循环。
- API Key 校验缓存必须把绑定表版本或 `updated_at` 摘要纳入失效条件。
- 创建、更新、移除绑定、调整优先级、分组启停、分组删除、分组账号变化和授权状态变化都要清理相关网关 runtime cache。

客户端请求全链路缓存边界：

- 认证前来源保护只用内存滑动窗口和短 TTL 熔断，缺少 Bearer 或无效 Key 的高频请求不能放大成重复数据库读取。
- 认证通过后，运行时快照是请求链路的唯一业务事实入口：API Key、系统账户、active 分组绑定、当前命中分组、分组访问元数据、候选账号和设置都来自 runtime cache 或 DB service。同一个无效 Bearer token 的运行时读取也要短 TTL 负缓存，重复失败只累计来源保护，不重复请求 DB service。
- 分组回退只能复用 `apiKey.group_bindings` 中的有界候选列表；后备分组的访问元数据和账号快照按需读缓存，缓存 miss 再走 DB service，不能在 Web 进程按 `apiKeyId`、`groupId` 或 `accountId` 补查业务库。
- 请求能力、模型、本地屏蔽、高并发即时容量、会话亲和、客户端 IP 并发和来源级回避都只在内存候选列表上计算；不能为了更优排序扫描全局账户、全局分组、使用记录或审计明细。
- API Key 额度、授权额度和团队授权额度只使用短 TTL 决策缓存及 worker 被动推送的有界额度快照；快照缺失、超出当前固定窗口或尚未包含某个新授权组合时，网关短时放行并等待下一轮 worker 刷新追平，不能在请求链路主动查询授权主表、团队授权表或统计窗口。
- OAuth Access Token 懒刷新只服务已选 OAuth 账户的凭据正确性。后台预刷新应覆盖常态请求；请求前兜底刷新在同账号内串行，并用最近成功刷新缓存吸收同一波临期并发，避免重复读取 OAuth 账户、重复解析代理或重复写回凭据。
- 上游请求成功、失败、流式中断或客户端断开后的使用记录和审计只终态入队；账号冷却、失败计数、OAuth 额度快照和 Codex header 持久化是异步副作用，不允许阻塞响应返回。
- 管理端列表、分组状态、统计图和消耗明细如果需要展示这次请求后的结果，只能等 worker 聚合或运行态缓存刷新；不能把展示需求反推到客户端请求链路里现场汇总。

会话亲和：

- 会话亲和是账户级事实，不按分组重新分片。亲和键应包含 `systemAccountId + apiKeyId + 客户端会话标识`，绑定值是实际命中的账户 ID；不能因为同一个 API Key 切到另一个分组，就为同一个客户端会话另起一套亲和。
- API Key 路由策略仍先于亲和跨组跳转。路由层按本次策略候选顺序选出当前可承接容器后，如果该容器候选账号里包含历史亲和账户，分组内调度可以优先复用；如果历史亲和账户不在当前可承接容器内，不能为了亲和直接绕过策略选中的可承接分组。
- 如果当前候选分组不可承接而切到后续分组，同一个 API Key / 客户端会话的亲和仍应沿用同一个账户级绑定；当后续分组包含该账户且账户可用时，可以继续命中同一账户。
- 不能为了亲和绕过 Key 状态、分组绑定、授权、模型、额度或账号硬状态。

## 使用记录、统计与审计

- `usage_records.group_id` 继续写实际命中的分组 ID。
- API Key 维度统计不新增 scope，仍按 `scope_type = api_key` 聚合该 Key 的所有号池调用。
- 分组维度统计按实际命中的 `group_id` 聚合；A 调度前不可承接后命中 B，本次成功和用量属于 B 分组。
- 授权账户消耗仍按实际命中的授权账户和最终用户授权 ID 写入。
- 原始审计和使用记录元数据可以记录安全摘要，例如尝试过的分组 ID、最终选中分组、每个分组的本地失败 reason code；不要保存完整请求体或敏感凭据。
- 列表统计、额度判断和趋势仍读取后台 worker 预聚合结果，不因为多号池路由在请求链路现场汇总明细。

建议 reason code：

| code | 含义 |
| --- | --- |
| `binding_disabled` | 绑定停用 |
| `group_unavailable` | 分组不存在、停用或已删除 |
| `provider_mismatch` | 供应商不一致 |
| `request_capability_mismatch` | 请求路径、客户端 profile、图像能力或账号类型能力不匹配 |
| `model_not_supported` | 当前分组账号均不支持请求模型 |
| `no_schedulable_accounts` | 硬过滤后没有可调度账号 |
| `authorization_unavailable` | 授权、团队成员或授权额度不可用 |
| `authorization_quota_exceeded` | 当前号池候选账号全部被授权额度过滤 |
| `upstream_accounts_exhausted` | 当前号池真实上游尝试后账号耗尽，且尚未写下游输出，需要回到 API Key 候选列表继续寻找可承接账号 |
| `group_runtime_unavailable` | 分组派生运行态不可承接 |
| `local_capacity_unavailable` | 并发、队列或本地屏蔽在调度前已明确无法承接 |

## 权限与安全

- 用户侧接口完全忽略前端传入的 `systemAccountId`，只允许维护当前登录用户自己的 Key 和分组绑定。
- 管理侧接口如果代某个系统账户创建或编辑 Key，`api_keys.system_account_id`、`api_key_group_bindings.system_account_id` 和所有绑定分组的 `groups.system_account_id` 必须一致。
- 分组选项接口可以用于 API Key 表单，但必须支持 `manageableOnly` 或等价参数，确保只返回可绑定的自有分组。
- 绑定关系不授予额外资源使用权；它只引用已经属于调用方本地分组的号池。
- 完整 API Key 明文展示规则不变；多号池信息不包含敏感凭据。

## 验收清单

- API Key 只有一个绑定时按单号池路由。
- 创建 API Key 时可以绑定 A、B、C 三个同供应商自有分组，并按 `1, 2, 3` 保存优先级；未设置策略时默认主备优先。
- 可以选择轮询策略，连续请求在多个启用号池之间按稳定顺序轮转。
- 可以选择权重策略，连续请求在多个启用号池之间按绑定权重接近比例分配。
- 不能绑定其他用户分组，也不能绑定授权方分组。
- 同一个 API Key 内不能提交重复分组、混合 provider 或没有 active 号池的配置；不同 API Key 可以绑定同一个分组。
- 可以提交个人分组和高并发分组混合的绑定配置，运行时按 API Key 路由策略选择候选号池，选中后使用各自分组内调度策略。
- A 分组只有 OAuth 账号且不支持当前公开路径时，应跳过 A 并尝试包含 API Key 账号的 B 分组。
- A 分组内授权实例失效但自有账户可用时，仍可由 A 分组承接；如果 A 分组所有账户都被授权关系、实例状态或绑定状态过滤，则尝试 B 分组。
- A 分组停用、无正常可调度账号、模型不匹配、授权账户失效或调度前已明确不可承接时，会尝试 B 分组。
- API Key 停用、过期或额度耗尽时，不尝试任何分组。
- 真实上游派发开始后，分组内账户会按既有恢复、冷却和切号策略优先在 A 号池内处理；如果 A 号池账号耗尽且尚未写下游输出，或写下游前配置化流式拦截耗尽 A 号池，可以回到 API Key 候选列表继续寻找未失败且当前可承接的账号，并在审计 metadata 中记录切换原因。
- A 调度前不可承接后最终命中 B，使用记录里的 `group_id` 是 B，API Key 统计仍归属同一个 Key；A 恢复正常可调度账号后，后续请求应优先回到 A。
- 分组筛选能查到绑定了该分组的 Key，并展示完整 `groupBindings`。
- 调整绑定优先级、停用绑定、删除分组和删除 API Key 都会清理网关缓存并写操作日志。
- 高并发分组作为 A 不可立即承接时，优先尝试 B；所有号池都不可立即承接时，才进入有界短等待或返回本地容量错误。
- 主备优先下同一 API Key、命中分组和授权组合在缓存 TTL 内的第二次请求，不应再次读取运行时、分组授权元数据、账号列表、授权主表、团队授权表或统计额度窗口；轮询和权重策略下不得缓存最终选中分组，但仍可复用静态校验、授权元数据、账号列表和额度快照缓存。
