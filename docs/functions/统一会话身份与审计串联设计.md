# 统一会话 Header 与审计串联设计

## 1. 最终范围

当前范围只识别请求头中直接表达的稳定会话 ID。请求体不参与会话识别；`thread-id`、`turn-id`、`agent-id`、`x-client-request-id`、response / interaction ID、缓存键和内容特征都不作为会话来源。

各客户端 adapter 的统一输出是请求内的 `sessionId`。审计主表直接记录原始 `session_id` 和 `session_client_type` 以支持按客户端会话 ID 精确查询；亲和存储仍只使用带客户端 namespace 的 HMAC `affinityKey`。入站 Header 不改写。

## 2. 官方客户端结论

| 官方客户端 / API | 会话请求头 | 本项目结论 |
| --- | --- | --- |
| OpenAI Codex | `session-id` | 请求已识别为 Codex 画像后支持，映射为内部 `sessionId`；该 Header 本身不建立画像 |
| Anthropic Claude Code | `x-claude-code-session-id` | 支持，映射为内部 `sessionId` |
| Google Gemini CLI | 未发现用于模型请求的官方会话 Header | 不支持会话识别，正常无粘黏降级 |
| OpenAI 通用 API | 没有跨 API 通用的会话 Header 标准 | 不识别会话，不因同名 Header 建立亲和 |
| xAI、DeepSeek、GLM 等通用 API | 未发现官方稳定会话 Header | 不猜测，不建立会话亲和 |

`x-openclaw-session-id` 属于第三方客户端扩展，不属于模型厂商官方客户端基线，当前范围不接入。`mcp-session-id` 是 MCP 传输会话，不等于模型对话会话，也不接入。

官方与源码证据：

- [Codex 官方源码](https://github.com/openai/codex/blob/main/codex-rs/codex-api/src/requests/headers.rs)在 `build_session_headers` 中设置 `session-id`，`/responses`、`/responses/compact` 与 WebSocket 测试均验证该 Header。
- [Claude Code 官方网关协议](https://code.claude.com/docs/en/llm-gateway-protocol#request-headers)定义 `x-claude-code-session-id`，并明确它用于聚合同一 Claude Code 会话的全部请求。
- [Gemini CLI 官方源码](https://github.com/google-gemini/gemini-cli)内部有 session 概念；本次源码审查未发现模型请求对应的会话 Header。这是基于当前官方源码的审查结论，按“只读 Header”边界不接入。

因此不存在所有模型厂商客户端共同遵循的行业标准 Header。本项目不定义“任意客户端通吃”的会话 Header；只让已确认的客户端 adapter 把自己的官方 Header 投影到统一审计字段。

### 2.1 为什么其他中转维护很多 ID Header

中转项目经常把协议透传、路由、追踪、缓存、限流和不同传输协议的动态 Header 集中维护，因此名单很长，但不表示这些字段都是模型会话 ID：

| 标识类别 | 常见用途 | 本项目处理 |
| --- | --- | --- |
| 厂商客户端 session ID | 跨多次模型请求的会话串联和账号粘黏 | 仅由对应客户端 resolver 接入 |
| request / trace ID | 单次请求追踪、日志关联、幂等 | 保持请求级语义，不映射 `session_id` |
| thread / turn / agent / parent ID | 对话子层级、单轮、子代理或父子关系 | 不提升为会话 |
| response / interaction ID | 上游资源续接或取回 | 不提升为会话，本阶段也不接 continuation |
| cache key | 响应缓存、prompt cache、计费优化 | 不提升为会话 |
| `mcp-session-id` / `Last-Event-Id` | MCP 有状态传输与 SSE 续传 | 与模型会话隔离 |
| 供应商运行时 session ID | Bedrock AgentCore、SageMaker 等特定运行时粘黏 | 只属于对应 provider/runtime namespace |

有些中转为了提高兼容命中率，会按优先级把 `session-id`、`x-client-request-id`、body metadata 等不同语义的值合并成一个 affinity ID；另一些只是原样透传整组官方客户端 Header。前者是 best-effort 工程折中，后者是协议保真，两者都不能作为“这些字段具有相同会话语义”的证据。本项目不得从其他中转的透传名单或敏感动态 Header 名单直接生成会话 resolver。

### 2.2 动态 Header 与协议边界

动态 Header、会话 Header 和协议专属 Header 可以重叠，但不是同一个概念。`backend/src/modules/gateway/upstream/header-policy.ts` 只登记协议专属 Header，用于跨协议重建时清理来源协议字段；它不参与会话 resolver，也不参与审计或使用记录保存。

| 类别 | 当前名单 / 规则 | 原生同协议请求 | 跨协议重建请求 |
| --- | --- | --- | --- |
| Codex 会话与请求层级身份 | `session-id`、`thread-id`、`x-client-request-id`、`x-codex-turn-metadata`、`x-codex-window-id`、`x-codex-installation-id`、`x-codex-parent-thread-id` | 原生 Codex Responses 保留 | Responses 重建为 Chat / Anthropic / Gemini 时剔除 |
| Codex 不透明状态 | `x-codex-turn-state` | 原生 Responses 请求 / 响应往返保留 | 剔除 |
| Codex 能力与客户端标记 | `x-codex-*` 其余字段、`openai-beta`、`originator`、`version`、`x-openai-subagent`、`x-openai-memgen-request`、`x-responsesapi-include-timing-metrics`、`x-openai-internal-codex-responses-lite` | 按现有 Codex 兼容规则保留或生成 | 剔除；`x-codex-*` 前缀 fail-closed，避免新字段漏清理 |
| Claude Code 身份 | `x-claude-code-session-id`、`x-claude-code-agent-id` | 原生 Anthropic Messages 保留或按兼容规则补齐 | Anthropic 重建为 Chat / Gemini 时剔除；OpenAI 转 Anthropic 后可由 Claude Code adapter 重新生成目标协议字段；`x-claude-code-*` 前缀 fail-closed |
| Anthropic 能力与 SDK 标记 | `anthropic-beta`、`anthropic-version`、`anthropic-dangerous-direct-browser-access`、`x-app`、`x-stainless-*` | 能力头按 Anthropic adapter 规则处理 | 离开 Anthropic Messages 时剔除 |
| Gemini CLI 安装身份 | `x-gemini-api-privileged-user-id` | 原生 Gemini 请求保留 | Gemini 重建为 Chat / Anthropic 时剔除 |
| Gemini / Vertex 能力与 SDK 标记 | `x-goog-api-client`、`x-vertex-ai-llm-request-type`、`x-vertex-ai-llm-shared-request-type` | 原生 Gemini / Vertex 请求按 adapter 处理 | 离开 Gemini GenerateContent 时剔除；`x-gemini-*`、`x-goog-*`、`x-vertex-ai-*` 前缀 fail-closed |

厂商内部客户端 Header 的显式上游放行白名单只允许 OAuth / 官方订阅账号使用。API Key 账号不套用该白名单，继续走公开 API 的通用安全过滤和语义透传规则。`x-oai-attestation` 只有 OAuth Codex 原生请求允许向上游透传，API Key 与跨协议请求均剔除。

实现统一收敛到 `copyOfficialOAuthClientRequestHeaders`，但策略仍按 `openai_codex`、`anthropic_claude_code`、`gemini_cli`、`xai_grok` 四个 profile 分开登记；这个复制器只统一执行机制，不合并厂商字段语义。客户端传入的 Authorization、API Key、代理链、转发链和任意 `x-custom-*` 不进入 OAuth 上游，真实认证及账号身份只能由命中账户重新写入。API Key 路径继续使用 `copySafeUpstreamRequestHeaders`，保留通过通用安全过滤后的自定义业务 Header。

Gemini CLI 的 `x-gemini-api-privileged-user-id` 是稳定安装身份，不是模型会话 ID，因此不新增 Gemini session resolver。原始审计和使用记录快照按实际捕获值保存全部 Header 与 Body，包括凭据、attestation、会话、turn 和 installation 字段；不做敏感字段判断、替换或排除。

本项目账户层不开放任意静态 Header override，所以不存在“管理员把动态会话头固定写死”的入口。以后若开放类似能力，必须另加逐跳头和凭据头禁止规则。OAuth Header allowlist 也不得下沉为 API Key 通用 allowlist：API Key 使用公开协议，OAuth 才需要对厂商内部客户端契约做显式放行。

对比其他中转的结论：可借鉴其“集中登记、按协议透传 / 清理”的组织方式，但不能复制把 session、thread、request、cache、trace 全部当 affinity key 的语义。`new-api` 的长名单主要用于透传和可配置亲和；`sub2api_source` 的禁止覆盖名单主要防止管理员静态值造成跨请求串话。本项目最佳做法是客户端专属会话 resolver、原生协议保真、跨协议来源清理和原始审计分别承担单一职责，不共用一份含混的敏感 Header 名单。

## 3. Resolver 规则

当前注册表只有两个 resolver：

```text
clientProfile=codex      + session-id                    -> sessionId
clientProfile=claude_code + x-claude-code-session-id     -> sessionId
```

`session-id` 不是 Codex 画像识别信号。官方 Codex 主流程需要先由合法的 `x-codex-turn-metadata.turn_id` 建立 Codex 画像；项目显式画像 Header 也可进入同一 resolver。仅发送 `session-id` 的通用 OpenAI 请求保持 `generic_openai`，不会生成 `sessionId`、`conversationKey` 或会话亲和。这样可避免其他客户端碰巧使用同名 Header 时被错误归类。

解析器收集同一 Header 的全部物理值后再裁决：

- 空值、控制字符或 UTF-8 超过 512 bytes：`invalid`。
- 重复 Header 值不同，或两个同级会话 Header 同时给出不同身份：`conflict`。
- `invalid` / `conflict` 请求可以继续普通调度，但没有 `conversationKey`，不建立亲和。
- 没有支持的 Header：`missing`，不使用 IP、API Key、User-Agent、正文哈希或时间桶伪造会话。

generic 客户端即使发送同名 Header 也不会触发会话识别或亲和。新增厂商时只增加该客户端专属 resolver，声明客户端画像、Header 名和 semantic namespace；不得在路由、审计、普通/混合调度中各自维护字段数组。

## 4. Key、亲和与隔离

```text
conversationKey = HMAC-SHA256(
  JUHE_AI_SECRET,
  systemAccountId + apiKeyId + semanticNamespace + rawSessionId
)

affinityKey = HMAC-SHA256(
  JUHE_AI_SECRET,
  conversationKey + routeStrategyId + groupId + providerProfilePool
)
```

`affinityKey` 用于账号粘黏，客户端 semantic namespace 是其隔离输入之一。普通路由与混合路由只消费已经由客户端 adapter 确认的 identity，首次并发通过 memory 原子 claim 或 Redis Lua CAS 保证 first-writer-wins。

亲和是软约束：绑定账号仍必须通过分组、模型、协议、权限、健康和并发硬校验。账号不可用时按条件删除旧绑定并重新选择，旧请求不能覆盖新绑定。

没有会话 Header 时无法保证跨请求会话粘黏，系统执行普通调度。这是明确降级，不做不可靠猜测。

### 统一客户端来源标识

网关额外统一输出内部 `clientSourceKey`，供来源级短期避让、可用性探活 fence 和后续客户端专属状态复用。它不是“所有供应商共用一个外部 Header”，也不会替代 `conversationKey`：每个协议 adapter 只提供自身已经验证的稳定证据，再由公共层生成带 namespace 的 HMAC。

```text
clientSourceKey = HMAC-SHA256(
  JUHE_AI_SECRET,
  systemAccountId + apiKeyId + sourceKind + semanticNamespace + stableValue
)
```

| `sourceKind` | 当前来源 | 用途与限制 |
| --- | --- | --- |
| `official_session` | 已通过可靠客户端画像门控的 Codex `session-id`、Claude Code `x-claude-code-session-id` | 可作为来源级运行态的最细粒度证据；其底层会话解析也可生成 `conversationKey` / `affinityKey`。 |
| `protocol_resource` | Gemini Interactions 的已存在 interaction resource | 只表达同一协议资源续接，不声明自然会话，也不替代 Gemini interaction affinity。 |
| `ip_api_key_fallback` | 已规范化的 `clientIp + apiKeyId` | 只能用于短 TTL 来源保护；共享 NAT、可信代理配置错误或 IP 缺失时均不能当作会话亲和。 |

官方会话解析为 `invalid` 或 `conflict` 时，公共层停止生成细粒度来源，不降级污染 IP 桶。完全 `missing` 才允许使用 IP 软桶。来源状态键会再纳入客户端画像、endpoint 和下游协议；会话亲和才额外纳入路由策略、分组和供应商协议档案。这样同一 API Key 的同一来源在路由切组时仍能保留短期失败经验，而会话粘黏不会跨越路由/分组边界。显式 `x-juhe-client-profile` 仍是现有会话亲和兼容入口，但只是调用方自报，不能单独把 Header 升级为来源级运行态。原始 Header、resource ID 和 IP 都不写入 Redis / memory key。当前 Codex 已消费该统一来源；Claude Code、Gemini 和后续供应商也复用同一输出契约，而不是各自重建 HMAC、降级和隔离逻辑。

### Codex turn 避让子作用域

Codex turn 级候选避让不是会话亲和，也不以 `x-codex-turn-metadata.session_id` 或 `thread_id` 建立身份。只有已被合法 `turn_id` 识别为 Codex 的 Responses SSE 或 compact 请求可启用该状态；它以公共 `clientSourceKey` 派生调度作用域后，再加 `turnId` 子键。实际 retry/CAS 持久键仍以账户身份 HMAC 分片，因此同一 turn 可保留多个账户避让而不会发生跨账户清理。

- `session-id` resolver 返回 `resolved/official` 时，公共层生成 `official_session` 来源；原始 Header 不进入 Redis key。
- resolver 返回 `missing` 时，且仅在已知 `clientIp` 的前提下，公共层生成 `ip_api_key_fallback` 短 TTL 软桶。
- `invalid`、`conflict` 或无 IP 时不创建持久 turn/source 状态。不能用 API Key 单独兜底。
- metadata 的 session/thread、body 与 body hash、User-Agent、显式 client profile、request/trace ID 都只是协议或请求字段，不能提升为共享避让来源。

这与会话亲和的“无官方 Header 就普通调度”并不冲突：IP 软桶只限制同一合法 Codex turn 的短期避让状态，不生成 `conversationKey`、不建立会话粘黏，也不改变账户健康或 circuit。

首次达到避让阈值时，状态记录会返回该来源账户的 `sourceGeneration`。这个 generation 与 HMAC 来源键一起写入共享探活 fence；并发来源只加入同一个 probe generation，不追加真实上游探活。来源 handoff 同时携带 `stateKey + accountId + sourceGeneration + runtimeKey + probeGeneration + configRevision`，且这些字段都不含原始 Header。Redis 环境由共享 runtime state 统一 owner；standalone memory 环境中 gateway 与 ops-worker 各有独立内存，因此 worker 必须通过 IPC 收到 fence，并把 settlement 回传 gateway 进程执行精确清理，不能读取或假设共享 Map。

来源 owner 只投递既有后台健康检查并释放有截止时间的执行 handoff；control 拒绝、control 网络失败或 worker 未能入队时，必须按原始 fence 立即结算为 `unknown`，不能遗留 `dispatchPending`。过期而未回传的 handoff 可由新 owner 接管。已结算 success 后的另一次 activation 必须原子建立新 generation，晚到 fence 不得加入或消费旧结果。后台成功按每个 fence 的完整 `stateKey + accountId + sourceGeneration + sourceFenceId` 精确清理；任务失败、取消、未知、过期或不匹配的结果保留短避让，不能清空账户 circuit 或提前恢复 `temporary_unavailable`。当 fence 只是附着到已经运行的普通 scheduled/quality/request-failure 健康任务时，该任务仍照常进行账户健康结算；source fence 仅获得自己的窄清理或保留结果。

## 5. 审计串联

`traceId` 继续表示单次请求；`session_id + session_client_type` 表示客户端会话。每次请求保留独立轻量 audit envelope，因此同一会话的 N 次请求可以按原始 `session_id` 精确查询，同时保留 N 个不同的 `traceId`。

审计主字段：

- `session_id`
- `session_client_type`
- `conversation_key`（内部 HMAC 诊断字段，不作为用户主搜索入口）

历史记录保持 `NULL`，不做无证据回填。成功采样只控制 payload / attempts；热保留期结束只裁剪正文，父 audit envelope 在长期保留期结束时才删除。

审计明细不能对 `session_id` 建唯一索引，因为同一会话必须保存多条请求。查询索引采用非唯一复合索引：

```text
(session_id, created_at, id, session_client_type)
```

`session_id` 放在首列以服务管理端“只输入完整会话 ID”的主查询；`created_at, id` 紧随其后以直接完成稳定分页排序。该索引仍是非唯一索引，同一会话可以保存任意数量的请求审计。

普通审计宽查询保留 1001 行窗口保护；完整 `session_id` 精确查询使用该索引继续分页，不受普通窗口截断，因此长会话可以读取全部历史请求。

原始审计 Header 与 Body 按捕获到的值保存，不做字段名匹配、JSON / SSE 二次解析或 `[redacted]` 替换。风险由管理员权限、捕获范围、容量上限、采样和保留期控制。

## 6. 明确不做

- 不解析 body 的 `conversation`、`session_id`、`request.session_id` 或 `metadata.user_id`。
- 不把 `thread-id`、`x-client-request-id`、request ID 或 trace ID 当会话 ID。
- 不接 response / interaction continuation edge。
- 不支持没有官方会话 Header 的客户端粘黏承诺。
- 不允许 `session-id` 单独建立 Codex 画像；画像必须先由 Codex 的独立可靠证据建立。
- 不把第三方 Header 冒充模型厂商标准。

## 7. 验收

- 同一客户端的合法会话 Header 在同一租户/API Key 下生成相同内部亲和键。
- 不同租户、API Key、namespace、路由、分组或 provider profile pool 互相隔离。
- body-only session、非会话 Header、冲突 Header 都不能生成 `conversationKey`。
- 统一 `clientSourceKey` 回归覆盖 Codex / Claude Code 的官方会话、Gemini interaction resource、`IP + API Key` 软桶、跨 API Key 隔离，以及 invalid / conflict / 无 IP 不生成来源级持久状态。
- 同会话并发只 claim 一个合法账号；失败解绑不覆盖新绑定。
- 审计可按原始 `session_id` 精确查询全部轻量父记录；相同 `session_id` 允许存在多行。
- 跨层回归必须覆盖“Codex / Claude Code 官方 Header -> 客户端画像 -> resolver -> AuditCapture -> 队列 -> DB -> 管理查询”，并验证不同 `traceId` 可由同一 `session_id` 串联。
- 原始审计和使用记录快照保留捕获到的 Header 与 Body，不写入脱敏占位。
- 原生 Codex、Claude Code、Gemini 请求的协议 Header 不被误删；重建为其他协议时来源协议专属 Header 不得泄漏。
- 新增 `x-codex-*` 时跨协议边界默认剔除；新增其他厂商字段时必须显式登记分类和测试。
