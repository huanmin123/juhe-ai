# 表数据监控设计

## 目标

表数据监控用于让管理员看到当前运行模式下事实库和统计库的容量变化，尽早发现日志、审计、usage catalog、统计结果、Responses 桥接状态索引异常增长，辅助扩容、清理、VACUUM 或后续分区判断。standalone 模式监控 SQLite 业务库、数据集目录库、使用记录目录库、统计结果库和可轮询的 usage shard 文件集合；performance 模式监控 PostgreSQL `juhe_business`、`juhe_dataset`、`juhe_usage`、`juhe_stats` 和 `juhe_codex_context` schema，不再读取或展示 SQLite 文件路径。

## 存储边界

- F2 监控历史写入当前模式的 Go owner 输出：standalone 写入 `JUHE_AI_TABLE_MONITOR_DATABASE_PATH` 专用 SQLite，performance 写入 PostgreSQL `juhe_stats` schema；不再写入 Node 统计结果库路径。
- 同一运行实例只采一套存储：`JUHE_AI_DATABASE_DRIVER=sqlite` 时采 SQLite 多库，`JUHE_AI_DATABASE_DRIVER=postgres` 时采 PostgreSQL schema，不做 SQLite 与 PostgreSQL 双采样、双展示或回退读取。
- 采样表：
  - `database_storage_snapshots`：保存当前模式下被监控存储角色的主库 / schema 估算大小、页大小、页数、空闲页、已用空间、空闲空间、表数量和索引数量；SQLite 同步读取可选 WAL / SHM 文件大小，PostgreSQL 下无等价字段时保持未知。若 PostgreSQL catalog 超过本轮表预算，schema 总容量、页数和已用空间保持未知，不以局部 relation 伪造总值。
  - `table_storage_snapshots`：保存每张表的可选行数、表大小、索引大小、总大小、页数、索引数、分区 / 归档状态，以及 1 小时 / 24 小时增长；Go SQLite 采样按目录枚举并执行受控精确 `COUNT(*)`，可选 `dbstat` 提供大小/页数且不可用时保持未知；PostgreSQL 使用 `pg_class` / `pg_stat_user_tables` 目录统计和 relation size 函数。
- performance 模式下监控角色映射为 PostgreSQL schema：`business -> juhe_business`、`dataset -> juhe_dataset`、`usage-catalog -> juhe_usage`、`stats -> juhe_stats`、`codex-context-state -> juhe_codex_context`；容量来自 PostgreSQL catalog 函数与统计视图，`database_path` 使用 `postgres:<schema>` 口径。不存在的预留 schema 不能作为固定占位项展示。
- usage shard 文件属于统计数据集存储域的一部分。当前表监控主路径不直接采样 shard 文件集合；后续接入时可以把 shard 文件汇总为独立的 `usage_shards` 逻辑角色，同时保留单个异常 shard 的明细观测，且不能为了精确总行数扫描所有 shard。
- 监控历史默认保留最近一月；这些数据是运维记录，不纳入默认业务备份。

## 采样策略

- `juhe-ai-go-sidecar` 内的 F2 每 1 分钟采样一次，sidecar 启动后立即执行首轮；每轮在独立 goroutine 中并发读取各 SQLite 源库或 PostgreSQL schema，上一轮未完成时由 owner lease 和写事务边界拒绝重入。
- 采样只在 Go 进程内执行，Web/API 主进程和 Node worker 不注册 F2 定时器。
- SQLite 表目录按稳定名称枚举并受 `JUHE_AI_TABLE_MONITOR_MAX_TABLES` 限制，表行数使用受控精确 `COUNT(*)`。Codex shard 超过本轮 source 并发表预算时按采样时间槽循环选择，不扫描全部 shard；本轮未覆盖全部 shard 时不写伪造的 database 汇总快照。
- PostgreSQL 表目录读取 `pg_class` / `pg_stat_user_tables`，仅对目录返回的 relation 调用 `pg_relation_size`、`pg_total_relation_size` 和索引计数；不执行实时 `COUNT(*)`，不伪造 schema 占位项。
- SQLite 使用只读连接读取 page / freelist / 表目录；采样不写入源库。PostgreSQL 采样读取系统 catalog / 统计视图，快照写入 `juhe_stats`。
- 每轮采样成功提交后由同一 Go owner 按 `JUHE_AI_TABLE_MONITOR_RETENTION_DAYS` 批量删除过期 F2 快照；不存在中央 Node retention、队列或 fallback。
- usage shard 仅按已配置 Codex Context shard 路径枚举并并发读取；不为了精确总行数扫描所有 shard。

## 管理页面

管理员菜单新增 `表监控`：

- 汇总展示当前模式监控角色的主库 / schema 估算大小、可用 WAL 大小、空闲空间和表数量；常规采样不为 WAL / SHM 做同步文件系统读取，缺失时按未知展示。
- 汇总统计展示在表格列表上方，standalone 固定为业务库、数据集目录库、使用记录目录库和统计结果库四类，performance 额外展示 Responses 桥接状态索引库；某一类暂无采样时仍保留位置并显示占位。
- 趋势统计按监控角色展示为独立视图；点击某个库 / schema 的表只更新对应趋势图。
- 表格展示每张表在所选时间范围内的最近一次表级快照；不同源库的采样完成时间允许不同，页面直接展示已提交的最新值。概览查询只读取 `database_storage_snapshots` 和 `table_storage_snapshots` 各自的最新窗口，不通过关联查询拼接过期采样值。
- 管理端默认概览仅缓存首页（`page=1`、`pageSize=10`、无关键词）：默认 10 分钟内直接复用，最长允许 1 小时旧值并后台刷新；可用 `JUHE_AI_TABLE_MONITOR_OVERVIEW_FRESH_MS` 和 `JUHE_AI_TABLE_MONITOR_OVERVIEW_STALE_MS` 在进程启动时调整，但 stale 始终硬上限为 1 小时、不会短于 fresh，非法/小于 1 毫秒的值回退默认值或归一为 1 毫秒。缓存年龄按快照 `sampledAt` 计算，重复读取同一旧快照不会延长事实年龄。手动刷新使用 `refresh=true` 绕过缓存并回写缓存。缓存为各 db-service 进程内单 key，多实例各自预热，实例间允许最终一致但单实例不会超过 1 小时；后台刷新失败或刚完成后的 30 秒内退避，避免故障或停采样时重复打库。搜索、翻页和趋势历史保持原有读取语义，不纳入该缓存。
- 概览接口通过 `X-Table-Monitor-Cache`（`bounded-swr`、`bypass` 或 `none`）和 `X-Table-Monitor-Duration-Ms` 暴露缓存策略与耗时；后台刷新/预热失败写结构化日志，统一 HTTP Prometheus 管理接口指标继续记录请求量和耗时。
- db-service ready 后异步预热概览；预热失败不阻塞服务就绪，且冷启动没有旧值时不会抑制首个正常请求，后续请求失败才按 30 秒退避。
- 表监控路由显式启用 `KeepAlive` 以避免菜单往返重复首屏查询；页面回访时会按 `sampledAt` 检查一小时上限，超过上限自动重新请求概览，首次加载和手动刷新不因该保活策略重复发起无谓请求。
- 页面时间范围默认最近一月，选择粒度精确到日；查询时开始日期按当天 00:00:00、结束日期按当天 23:59:59 覆盖，并同时约束摘要、表格和趋势图。
- 表格展示库类型、表名、行数、表大小、索引大小、总大小、1 小时增长、24 小时增长和采样时间；SQLite 行数来自 Go 采样的精确 `COUNT(*)`，PostgreSQL 行数来自目录统计，列表直接展示当前快照值，不关联过期快照补值，也不在请求时实时扫描。
- 表格默认每页显示 10 行，允许管理员切换到更大的分页数量。
- 支持表名搜索；不提供固定库类型筛选，库类型直接保留在表格列和摘要卡片中。
- 点击表行查看该表在所选时间范围内的总大小与可用行数趋势；业务库、数据集目录库、使用记录目录库和统计结果库趋势统计各自独立，时间范围默认最近一月。
- 页面不提供 `立即采样`，采样只由 Go sidecar 内的 F2 自动执行。
- 页面提供非业务数据硬清理入口，管理员选择截止时间后，后端只校验截止时间不能晚于当前时间，不再强制保留最近 1 天。
- 后端把任务投递给 `recordMaintenanceQueue`，由 worker 按批次清理早于截止时间的数据集目录库、使用记录目录库、统计结果库、usage shard 和审计 payload 外部文件；performance 模式清理 `juhe_dataset`、`juhe_usage` 和 `juhe_stats` 内的同类非业务数据。业务库不参与清理，`juhe_codex_context` 继续由 Responses 桥接状态过期清理任务维护。数据集目录库、使用记录目录库和统计结果库的普通表按 schema 动态枚举，只要表内存在可识别时间列就纳入清理；Go F3/F4 专库及其 payload/blob 不属于该枚举，分别由各自 retention owner 管理。
- 硬清理是管理员应急释放入口，不替代常规保留策略。常规过期治理中，standalone 下 usage 超期数据优先 seal / archive / delete shard 文件；performance 下 `usage_records` 在统计安全游标追平后按整日分区 `DETACH / DROP`，不保留同库冷归档副本。硬清理不等待统计安全游标，也不按业务关联反向扣减统计；确需删除明细行时只能小批次按可识别时间列推进，PG usage 明细必须使用 `(created_at, id)` 命中分区。
- 硬清理覆盖数据集目录库、使用记录目录库和统计结果库内具备时间字段的非业务表，包括模型检测、公开接口日志、usage shard 目录、统计缓存、额度窗口、排行 / 范围窗口、系统监控、IP 统计和后台游标 / 扣减账本；F1/F2/F3/F4 专库均明确排除，分别由 Go owner retention 清理。新增非业务表只要使用标准时间列命名，也会被该入口自动覆盖，但不得覆盖这些 Go 专库。
- 审计 payload 外部文件按 `audit_payload_blobs.created_at < cutoffAt` 删除本地 blob 文件和元数据，不为保留期内数据做关联保护。
- API Key 删除后的记录和统计清理由 API Key 删除流程自动登记并交给后台 worker 重试处理；表监控页面不展示 API Key 删除清理队列，也不提供单独查看或操作入口。
- 后续把 usage shard 文件集合接入表监控后，页面再额外展示 shard 总数、active shard 数、最大 shard 主文件大小、最大 WAL 大小、当天 shard 分布、writer 队列长度、最近 flush 时间和统计延迟；手动清理优先提交 shard seal / delete 任务，而不是在请求链路同步删除明细行。

## F2 Go 完整接管边界

- `cmd/juhe-ai-go-sidecar` 内的 `internal/tablemonitor` 是 F2 的唯一采样、快照写入和表监控历史保留 owner。该接管是完整功能接管，不是 opt-in、灰度、Node/Go 双写或 owner switch；Node scheduler、stats writer 和 Node retention 路径已退出。
- Go 直接异步并发采样 SQLite 业务库、数据集目录库、使用记录目录库、统计结果库和 Codex Context shard，以及 PostgreSQL `juhe_business`、`juhe_dataset`、`juhe_usage`、`juhe_stats`、`juhe_codex_context` schema；不使用 queue、Redis、Asynq、Node IPC 或 fallback。单次采样失败保留原始错误并结束本轮，不伪造空快照。
- SQLite 模式的输出库由 `JUHE_AI_TABLE_MONITOR_DATABASE_PATH` 指定，是 F2 专用 SQLite 文件且由 Go 唯一写入；它不得与业务、数据集、usage catalog、stats 或 Codex Context shard 共用。Node 表监控 HTTP 读取只使用该专用文件，不读取源库或回退到旧 Node writer。
- PostgreSQL 模式的快照与保留清理写入 `juhe_stats.database_storage_snapshots` 和 `juhe_stats.table_storage_snapshots`；Go 启动时检查连接、schema 和 `JUHE_AI_TABLE_MONITOR_OWNER_LEASE`（默认 5m）owner lease，同一事实库第二个 Go 实例拒绝启动，失去 lease 后采样/清理拒写，写入使用短事务。该 lease 不是 Node/Go 开关或队列。经用户授权创建一次性隔离测试库后，真实 PostgreSQL adapter、lease takeover、relation-size 快照、五个 schema 的 `RunOnce` 采样和 retention 清理 smoke 已通过；这不等同生产部署验收。
- 必填/关键配置为 `JUHE_AI_TABLE_MONITOR_INSTANCE_ID`、`JUHE_AI_TABLE_MONITOR_STORE`（必须显式设置）、`JUHE_AI_TABLE_MONITOR_DATABASE_PATH`（SQLite）、`JUHE_AI_TABLE_MONITOR_POSTGRES_URL`（PostgreSQL）、各源库路径、`JUHE_AI_CODEX_CONTEXT_STATE_SHARD_ROOT`、`JUHE_AI_TABLE_MONITOR_INTERVAL`、`JUHE_AI_TABLE_MONITOR_RUN_TIMEOUT`（默认 `45s`）、`JUHE_AI_TABLE_MONITOR_RETENTION_DAYS` 和 `JUHE_AI_TABLE_MONITOR_MAX_TABLES`。采样并发与 retention 上限由 `JUHE_AI_TABLE_MONITOR_MAX_CONCURRENT_SOURCES`（默认 512，范围 1..5096）、`JUHE_AI_TABLE_MONITOR_RETENTION_BATCH_SIZE`（默认 512，范围 1..5096）和 `JUHE_AI_TABLE_MONITOR_RETENTION_MAX_BATCHES`（默认 512，范围 1..5096）控制。启动缺配置、路径复用、源库不可读、deadline 到期或 owner lease 丢失必须显式失败。
- 默认采样间隔为 1 分钟、历史保留 30 天、单库最多 256 张表；保留清理由同一 Go owner 在采样提交后按批次执行，达到批次数上限仍有过期数据时显式失败，Node 不再承担表监控历史 retention。页面仍只提供读取和非业务数据清理入口，不能触发表监控采样。

## 口径说明

- `fileBytes` 是 SQLite `page_size * page_count` 估算的主库大小，不含 WAL 和 SHM；为避免后台 worker 阻塞事件循环，常规采样不同步 `stat` WAL / SHM 文件，相关字段允许为空。
- `freeBytes` 来自 `freelist_count * page_size`，表示 SQLite 文件内部可复用但尚未归还给文件系统的空闲页。
- performance 模式下 `fileBytes` 表示对应 PostgreSQL schema 内普通表 / 分区表 / 物化视图的 `pg_total_relation_size` 汇总，`pageSize` 来自 PostgreSQL `block_size`，`pageCount` 为总大小按 block size 估算；表级快照通过 `pg_inherits` 标记分区父表 / 子表，不再采样同库冷归档 schema；`freelistCount`、`freeBytes`、WAL / SHM 字段没有 SQLite 等价口径，保持未知。
- standalone 删除大量数据后，`freeBytes` 会升高，但 SQLite 主文件不会自动变小；需要停机后执行 `VACUUM INTO` 并替换文件，才能释放磁盘空间。performance 下空间回收遵循 PostgreSQL autovacuum / VACUUM 与表膨胀口径，表监控只展示 relation size 变化，不把 `freeBytes` 伪造成 SQLite 等价字段。usage shard 和审计 payload 外部文件被物理删除后会直接归还对应文件占用。
- 数据集目录库中的明细事实可丢失或按保留期清理；使用记录目录库中的 usage shard 定位关系可重建；统计结果库中的统计缓存和监控历史可重建；F3/F4 专库按各自保留契约处理；业务恢复默认只依赖业务库和 `backend/.env`。
- 日志搜索不维护额外回填型搜索影子表；操作日志摘要词项由 Go F4 同步生成并由 F4 retention 清理，不属于 Node dataset。数据集目录库、使用记录目录库和统计结果库新增表必须是表监控可观测、统一保留期可清理的普通表，长期保留表需要在存储文档中说明理由。
- usage shard 的 `freeBytes` 只解释单个 shard 文件内部可复用空间；超过保留期且统计游标安全的 shard 应优先整文件删除或归档，不把大规模 `DELETE + VACUUM` 作为常规释放空间路径。
