# 合并路由设计（merge 模式）

## 1. 概述与定位

合并路由（`merge`）是策略路由的第 6 种路由模式，与普通路由、混合智能路由、权重调度、故障回退、轮询平级。

一句话语义：**绑定 2 个及以上分组，把所有绑定分组中能服务当前请求模型的账号合并成一个大池统一调度，不区分分组**。

与故障回退的本质区别：故障回退以分组为单位、带主备偏置（主分组可用时一直用主分组，保证同类型分组的服务质量）；合并路由以账号为单位、无分组偏置（每次请求在全池按账号级调度因子选最优账号，分组合并即"号合并"）。

典型场景：glm 分组（原生 glm 账号）与 openai 兼容分组（内含 glm→deepseek/grok 模型映射的账号）合并后，一个 API Key 即可服务全部模型；glm 原生账号不可用时，请求自动落到兼容分组经映射的账号，无需人工切换密钥。

权威模式对照表见 [策略路由设计](策略路由设计.md)；本文细化 merge 模式专属语义，与该文冲突时以该文为准（本文落地时同步更新该文）。

## 2. 目标与非目标

### 目标

1. 一个 API Key 通过合并路由使用所有绑定分组的模型能力，无需按供应商切换密钥。
2. 每次请求在全池按现有账号级调度因子统一排序选最优：并发忙闲、代理健康分层、客户端 IP 回避、速度优先降级后置（配置速度优先时）。
3. 调度偏好（成本优先 / 速度优先）对 merge 照常适用，与普通 / 权重 / 故障回退 / 轮询四种模式一致。
4. 用量与审计按实际服务账号所属分组记账，分组统计不失真。
5. 池内账号失败 / 耗尽直接用池内下一账号；全池耗尽按现有耗尽契约终局。

### 非目标（后续迭代）

1. 分组级权重 / 容量配比（V1 为纯账号级统一竞争，绑定权重字段被忽略）。
2. 跨路由模式的质量信号共享（热质量成本优先信号作用域跟窗口首组，见 T2）。
3. 全池会话亲和（亲和请求 V1 钉在首绑定组，见 T3）。
4. 合并池专属的分组级配额切分。

## 3. 核心语义

### 3.1 全池统一调度

请求解析（路由层 merge 分支）：

1. 取 API Key 全部绑定（按 priority 升序，现有排序），**过滤 `status=active` 且 `GroupEnabled=1` 的绑定**（注意：现有路由层 `activeGatewayAPIKeyGroupBindings` 只过滤 status，GroupEnabled 过滤在 dispatch ordering 路径；merge 解析层必须自行补齐 GroupEnabled 过滤）。
2. 逐绑定分组：读取组访问元数据（缺失或授权失效 → 跳过该组，与现有 targetgroupselector 语义一致）→ `ListCachedOpenAIAccountsForGroupAsync(请求模型, endpoint family)`（SQL 层完成模型 rank 匹配：直接支持 / 模型映射 / 默认）→ `FilterAccountsByRequestedModel` 模型过滤 → 得到该组的账号片段。
3. 片段内为空 → 跳过该组；所有片段为空 → 沿用现有失败语义（`model_target_group_not_bound` / `model_target_group_unavailable`）。
4. 跨组重复账号（同一账号属于多个绑定分组）：按绑定优先级去重，首次出现（优先级高）的组胜出。模型映射是账号属性（`account_model_mappings` 挂在账号上），与所在组无关，去重不影响账号行为；胜出组的 GroupID 记为该账号的 BoundGroupID。
5. 扁平合并全部片段（绑定序 → 组内序），形成合并池。调度排序由 dispatch 层现有账号级管道执行，分组先后不构成偏置。

耗尽语义：合并池已包含全部分组的账号，**不存在分组回退**。池内账号逐个尝试，全部耗尽后按现有耗尽契约终局渲染（无 `switchToFallbackGroup` 跳转）。

### 3.2 跨组模型映射

请求模型 → 上游模型的映射解析发生在 dispatch/driver 层（逐账号 `ResolveAccountModelMapping`，请求体改写与响应反向映射均按账号），与分组无关。合并池中的账号自带各自映射（如兼容分组账号的 glm→ds 映射），合并后天然生效，路由层不做任何映射改写。

### 3.3 调度偏好

merge 加入 `ModeSupportsSchedulingPreference`：

- 成本优先（默认）：`normalRoutingConfig` 不落盘（config_json 为 NULL）。
- 速度优先：照常落盘 `normalRoutingConfig`（firstByteDeadlineMs + speedFirstConfig），首字截止、慢样本观察、确认慢切号、恢复探针全链路照常工作；状态键作用域见 3.5 与 B23。
- 模式切换 feed-forward：normal(speed_first) ↔ merge 等四种调度模式之间切换保留调度配置，切到 hybrid_smart 丢弃（现有 `normalInput` 语义，merge 加入谓词后自动成立）。

### 3.4 窗口身份与分组作用域

合并请求运行于**单一 DispatchContext**（扁平池一个列表），但组维度机制需要单一作用域，定义如下：

- **窗口身份 = 第一个（最高优先级）启用绑定分组**：请求级审计上下文、`UsageContext.GroupID`、`SelectedGroupID`、`SessionAffinityScope`、高并发窗口判定（`GroupType` / `SchedulingPolicy`）均取首绑定组的访问元数据（原样传递，不改写）。
- 高并发窗口语义跟随首组：首组为 `high_concurrency` 时全池启用 IP 并发槽 / 排队准入（容量 = 全池账号并发上限求和）；首组为普通组时这些窗口级机制不激活，账号级并发上限照常生效。
- 图片 lane 的 lane limit 推导使用首组 SchedulingPolicy；图片账号按能力过滤照常。

### 3.5 按账号所属组记账

- **尝试级**用量记录与审计尝试行：merge 上下文下 group_id 取**所服务账号的 `BoundGroupID`**（账号按组加载时自带，`OpenAIAccountSecret.BoundGroupID` 已存在）。失败路与完成路两条记录路径都要覆盖。
- **请求级**审计上下文保持首绑定组（请求身份）。
- 统计聚合（jobs statsagg 按 usage 行 GroupID 聚合）：合并路由的用量分别计入各真实分组，与故障回退"切到哪组记哪组"的既有口径一致。
- usage records 成套性校验：自有组（owner，无授权字段）与授权组（authorized，GroupOwner / GroupAuthorizationID 等来自账号自带 UsageAccess）在按账号组记账下均成套。

### 3.6 速度优先状态键作用域

慢样本 / 降级 / 探针状态键 `version:systemAccount:routeStrategy:group:runtimeKey` 的 **group 分量改为优先取账号 BoundGroupID**（为空回落 scope 原值），读（降级后置排序）、写（慢 / 恢复观察）、清理三处同源：

- 存量模式（normal / weighted / failover / round_robin）账号的 BoundGroupID 恒等于窗口组 → 键形不变，零回归。
- merge 账号按各自所属组记键 → jobs 恢复探针（按"策略×组"三元组全等找候选、按组解析凭据）**无需任何改动**即闭环。

## 4. 边界清单

### 4.1 配置面（routestrategies）

| # | 边界 | 设计 |
| --- | --- | --- |
| B1 | 绑定数量 | merge 至少 2 个启用分组（`validateModeBindings` 新分支，仿 failover 强度）。单绑定策略直接切 merge 报错，需先补绑定（与切 failover 同模式）。 |
| B2 | 权重 | merge 不使用权重；从 weighted 切来的存量行 weight 残留被忽略、不清洗。前端隐藏权重列。 |
| B3 | priority / 拖拽 | 保留语义 = 基础顺序：调度平局的稳定序 + 窗口身份（首绑定）依据。缺省 priority=index+1（现有归一化）。 |
| B4 | 调度偏好 | merge ∈ `ModeSupportsSchedulingPreference`；`normalRoutingConfig` 复用（历史命名），cost_first 不落盘、speed_first 落盘；模式切换 feed-forward。 |
| B5 | 三入口同源 | 管理面 / 公开面（aipublic）/ 委托面（delegated）共用 Store 校验，自动生效；aipublic mock 投影谓词（`ModeSupportsSchedulingPreference`）同步覆盖 merge。 |
| B6 | 列表与摘要 | `normalConfigForMode`、`isSpeedFirstRouteStrategy`（列表速度优先时延摘要 + 运行态抽屉端点）按谓词自动覆盖 merge。 |
| B7 | 缓存失效 | 现有 `gatewayRuntimeChanged` 字段集已含 mode / normalRoutingConfig / groupBindings，merge 修改触发同等失效，无新增。 |

| B9 | 绑定过滤 | 解析层自行过滤 `GroupEnabled=0`（现有路由层只看 status）+ 组访问元数据缺失跳过。 |

## 5. 数据模型与配置

1. 模式常量：`ModeMerge = "merge"`，三处注册（`routestrategies/config.go`、`gatewayrouting/types.go`、`gatewayruntimecache/types.go`）+ `IsRouteStrategyMode` / `ModeSupportsSchedulingPreference` 白名单。
2. 配置存储：复用 config_json 的 `normalRoutingConfig` 键（历史命名，第五个共享模式），零 schema 迁移；cost_first 不落盘，speed_first 整体落盘。
3. 绑定表：`route_strategy_groups` 照常（priority = 基础顺序，weight 忽略），上限 20 个绑定沿用。
4. 数据库无 CHECK 约束，无迁移。

## 7. 实现核实项

设计阶段已核实的代码事实：

1. `CompletedAttemptInput.Account` 为 `AccountView` 接口（无 BoundGroupID），具体适配 `OpenAIAccountView` 包装完整 `OpenAIAccountSecret` —— 按账号记账可行，需小幅扩展接口或在具体类型取值。
2. 排序管道账号类型 `AccountCandidate = OpenAIAccountSecret` —— 状态键按账号组解析直接可行。
3. `ClearNormalRouteLatencyDegradationForAccount` 按账号匹配、组无关 —— 清理覆盖确认。
4. 热质量成本优先模式存在且排序要求非空 GroupID —— 窗口首组满足。
5. 亲和命中跳过路由解析（preflight.go:463）—— T3 成立。

实现时需复核：

1. gatewayusage 失败 / 完成两路拿到的账号形态与最小改动点。
2. `ClearNormalRouteLatencyDegradationForAccountBinding` 调用方传入的组集合来源（是否为账号全部绑定组）。
3. merge 分支与目录路由（catalog provider route）解耦的具体切点与错误分类路径。
4. RoutePlanSnapshot 对 merge 的构造点（单目标或不构造）与审计字段兼容。
