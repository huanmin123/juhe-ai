# 合并路由设计（merge 模式）

> 状态：设计已通过两轮独立代码对照复审（2026-09-19），复审发现已全部回填。可进入实现。
> 2026-09-20 口径更新（hybrid 移除后）：原第 6 种评分分级路由模式（hybrid 评分路由）已彻底移除，存量 hybrid 策略行由 maintenance `--migrate-hybrid-smart-strategies` 一次性迁移；合并路由是五种路由模式（普通 / 权重 / 故障回退 / 轮询 / 合并）之一，五种模式全部支持调度偏好（成本优先 / 速度优先）；本文原按“第 6 种模式”表述的内容已同步收敛。

## 1. 概述与定位

合并路由（`merge`）是策略路由的 5 种路由模式之一，与普通路由、权重调度、故障回退、轮询平级。

一句话语义：**绑定 2 个及以上分组，把所有绑定分组中能服务当前请求模型的账号合并成一个大池统一调度，不区分分组**。

与故障回退的本质区别：故障回退以分组为单位、带主备偏置（主分组可用时一直用主分组，保证同类型分组的服务质量）；合并路由以账号为单位、无分组偏置（每次请求在全池按账号级调度因子选最优账号，分组合并即"号合并"）。

典型场景：glm 分组（原生 glm 账号）与 openai 兼容分组（内含 glm→deepseek/grok 模型映射的账号）合并后，一个 API Key 即可服务全部模型；glm 原生账号不可用时，请求自动落到兼容分组经映射的账号，无需人工切换密钥。

权威模式对照表见 [策略路由设计](策略路由设计.md)；本文细化 merge 模式专属语义，实现落地时同步更新该文。

## 2. 目标与非目标

### 目标

1. 一个 API Key 通过合并路由使用所有绑定分组的模型能力，无需按供应商切换密钥。
2. 每次请求在全池按现有账号级调度因子统一排序选最优：并发忙闲、代理健康分层、客户端 IP 回避、速度优先降级后置（配置速度优先时）。
3. 调度偏好（成本优先 / 速度优先）对 merge 照常适用，与普通 / 权重 / 故障回退 / 轮询四种模式一致。
4. 用量与审计按实际服务账号所属分组记账（组 ID 与访问五元组随账号走），分组统计不失真。
5. 池内账号失败 / 耗尽直接用池内下一账号；全池耗尽按现有耗尽契约终局。

### 非目标（后续迭代）

1. 分组级权重 / 容量配比（V1 为纯账号级统一竞争，绑定权重字段被忽略）。
2. 跨路由模式的热质量信号共享（成本优先热质量信号作用域跟窗口首组，见 T2）。
3. 合并池专属的分组级配额切分。

## 3. 核心语义

### 3.1 全池统一调度

请求解析的 merge 分支：

1. 取 API Key 全部绑定（priority 升序），过滤 `status=active` 且 `GroupEnabled=1`。说明：runtime cache SQL 加载已按 `status='active' AND groups.enabled=1` 过滤（sqlruntime.go:296-305），到达路由层的绑定恒满足；解析层再过滤属防御性断言，不承载正确性。
2. 逐绑定分组：组访问元数据缺失或授权失效 → 跳过该组（与 targetgroupselector 语义一致）→ 逐组走 `ListCachedOpenAIAccountsForGroupAsync(请求模型, endpoint family)` → 能力过滤（当前 pass-through，保持链路一致）→ `FilterAccountsByRequestedModel` 模型过滤 → 得到该组账号片段。**实现建议：复用 `SelectGatewayModelTargetGroup` 的逐组骨架（候选收集改为全部片段），不平行实现第二套链路。**
3. 组内片段为空 → 跳过该组；所有片段为空 → 沿用现有失败语义（`model_target_group_not_bound` / `model_target_group_unavailable`，错误分类可借助目录路由结果）。
4. **组标（stamp）**：合并池内全部账号（不限于去重场景、不限于授权账号）显式写入 `BoundGroupID = 所在片段组`。这是记账（3.5）与状态键（3.6）的统一前提——现有赋值点仅覆盖 account_authorized 账号（chain_accounts_secret.go:202-205），owner 与 group_authorized 账号恒为 nil，不能依赖"按组加载时自带"。
5. 跨组重复账号（同一账号属于多个绑定分组）：按绑定优先级去重，首次出现（优先级高）的组胜出。模型映射与支持模型是账号属性（`account_model_mappings` / `account_supported_models` 挂在账号上），与所在组无关，去重不影响账号行为；dispatch 层会按全池重跑统一 rank（candidatefilter.go:138），无需合并各片段 rank。同一账号按胜出组的本地优先级参与排序（rank tiebreaker 含 `local_priority`）。
6. 扁平合并全部片段（绑定序 → 组内序）。调度排序由 dispatch 层现有账号级管道执行，分组先后不构成偏置。

耗尽语义：合并池已包含全部分组的账号，**不存在分组回退**。池内账号逐个尝试，全部耗尽后按现有耗尽契约终局渲染。实现：RoutePlanSnapshot 的 `OrderedAllowedTargets` 截断为单目标 `[窗口组]`（见 3.4）——单目标下 `canAttemptAPIKeyGroupFallback` 的 `cursor < len-1` 恒假，回退链路（switchToFallbackGroup / resolveRouteAction）自然短路，无需为其新增 merge 分支（可选防御）。

### 3.2 跨组模型映射

请求模型 → 上游模型的映射解析发生在 dispatch/driver 层（逐账号 `ResolveAccountModelMapping`，请求体改写与响应反向映射均按账号），与分组无关。合并池中的账号自带各自映射（如兼容分组账号的 glm→ds 映射），合并后天然生效，路由层不做任何映射改写。

### 3.3 调度偏好

merge 加入 `ModeSupportsSchedulingPreference`：

- 成本优先（默认）：`normalRoutingConfig` 不落盘（config_json 为 NULL）。
- 速度优先：照常落盘 `normalRoutingConfig`（firstByteDeadlineMs + speedFirstConfig），首字截止、慢样本观察、确认慢切号、恢复探针全链路照常工作；状态键作用域见 3.6 与 B24。
- 模式切换 feed-forward：五种调度模式之间切换保留调度配置（merge 加入谓词后自动成立）。

### 3.4 窗口身份与分组作用域

合并请求运行于**单一 DispatchContext**（扁平池一个列表），组维度机制需要单一作用域：

- **窗口身份 = 第一个产生非空片段的启用绑定分组**（即首个"实际贡献账号"的组）。请求级审计上下文、`UsageContext.GroupID`、`SelectedGroupID`、`SessionAffinityScope`、高并发窗口判定（`GroupType` / `SchedulingPolicy`）、RoutePlanSnapshot 单目标均取该组，定义唯一，不区分"首绑定组"与"首片段组"两套口径。
- 高并发窗口语义跟随窗口组：窗口组为 `high_concurrency` 时全池启用 IP 并发槽 / 排队准入；为普通组时这些窗口级机制不激活，账号级并发上限照常。
- **速度优先 body admission 时序取舍**：准入在 preflight 之前的中间件层执行（chain_preflight.go:241-267），此时 merge 解析尚未发生，`runtime.Accounts` 只有窗口组账号 → **V1 准入容量 = 窗口组账号并发上限求和**（非全池），适用性判定（GroupType）同样取窗口组。见 T1。
- 图片 lane 的 lane limit 推导使用窗口组 SchedulingPolicy；图片账号按能力过滤照常。
- **候选重解析扇出**：模型感知重载（candidateLoader，preflight.go:1606-1615）与"全池临时不可用等待恢复"（recoverableLoader，preflight.go:1619-1626 → preflighthelpers.go:536-609）默认按单一 groupID 重读账号，merge 下会把扁平池静默收窄回窗口组。merge 上下文中这两个 loader 必须按绑定分组扇出重建扁平池（保留组标）；recoverableLoader 的等待 scopeKey 取窗口组。

### 3.5 按账号所属组记账

- **组标前提**：合并池全量账号在解析/rehydrate 时显式 stamp `BoundGroupID`（3.1 第 4 条），不依赖现有赋值点。
- **尝试级用量与审计**：merge 上下文下，尝试记录的 group_id 与**访问五元组（GroupOwnerSystemAccountID / GroupAccessType / GroupAuthorizationID / SourceType / SourceTeamID）整体取所服务账号 secret 自带的组元组**（账号按组加载时由该组 groupAccess 填充，chain_accounts_secret.go:156-168）——不是只覆盖 group_id。原因：现有完成/失败记录的五元组优先取 UsageContext（窗口组，chain_usage.go:328-332 + applyUsageAccountScope:369-373），若不整体替换，会出现"组 ID 属账号组、五元组属窗口组"的混合记录：虽能通过 records.go:179-221 成套性校验，但把授权组用量记成 owner 访问（或反之），统计口径失真。
- **请求级**审计上下文保持窗口组（请求身份）。
- **改动点位清单**（实现必须全覆盖）：
  1. 完成路生产实现是组合根 `chain_usage.go:307-349`（chainFinalizationUsage），不是 `gatewayusage/service.go` 完成路——五元组整体替换在此处；失败记录路 `chain_usage.go:392-424` 同。
  2. engine 失败路 choke point `chain_ports.go:105-109`（触达 service.go 失败路）。
  3. 审计尝试行两处：`audit_capture.go:663` StartAttempt 与 `:805` RecordFailedDispatchAttempt——在 `StartAttemptInput` / `RecordFailedDispatchAttemptInput` 上**加显式 GroupID 字段**，不得通过临时改写共享 gatewayContext 快照实现（in-progress 审计与 finalize 都读该快照）。
  4. 账号组值获取：优先在具体类型上取值（`OpenAIAccountView.Account.BoundGroupID` 类型断言，仿 applyUsageAccountScope 模式），避免扩 `AccountView` 接口。
- 统计聚合（jobs statsagg 按 usage 行 group_id）：合并路由用量分别计入各真实分组，与故障回退"切到哪组记哪组"口径一致。
- 已知口径：`AccountAPIKeySuccessRecorder` 当前未接线（nil 守卫跳过），无 group 写点；失败诊断日志 `fields.Set("groupId")`（service.go:363）保持窗口组口径（诊断字段，非统计事实）。

### 3.6 速度优先状态键作用域

**硬约束：状态键与存储的 `latencyState.Scope.GroupID` 必须同源**（同一解析值）。jobs 探针不用键枚举——`ListProbeCandidates` 直接读共享 Redis 运行态，用**存储 Scope** 重建 StateKey（speedfirstrepo stateKeyFor(s.Scope, s.RuntimeKey)）并按 `Scope.GroupID` 找账号凭据（FindCandidateAccount）；只改键不改存储 Scope 会让 claim/discard/RecordSuccess 全部落错键、凭据查找失败即 Discard，恢复闭环整体断裂。

设计：

1. **服务边界逐账号解析**：`gatewayproxyhealth/latencydegradation.go` 服务入口（OrderAsync 排序读、RecordFirstByteSlow/Success 写、checked 变体）对每个账号把组分量解析为 `账号 BoundGroupID`（空回落入参 scope.GroupID），**键与存储 Scope 用同一解析值**。排序管道账号类型即 `OpenAIAccountSecret`（AccountCandidate 别名），BoundGroupID 全程可用（含 stamp 后的 merge 账号）。
2. 存量模式账号 BoundGroupID 原为 nil（键回落窗口组，键形与现状一致，零回归）；stamp 后 owner/授权账号也带组——**存量模式路由不受影响**：单组路由的窗口组即账号加载组，解析值与原 scope.GroupID 相同，键形不变（回归测试锁定）。
3. jobs 侧零改动闭环：存储 Scope.GroupID = 账号组 → 探针按账号组重建键、按账号组找凭据，天然命中；`DegradedRuntimeItem.ScopeGroupID` 展示随之正确。
4. 探针成功回写（jobs RecordSuccess）与 gateway 观察期成功回写两端自动同值（同一存储 Scope）。
5. 清理路径：生产清理入口 `ClearNormalRouteLatencyDegradationForAccount`（compose_accounts_reset.go:168）按账号匹配、组无关（latencydegradation.go:1173-1176）→ 天然覆盖；`ForAccountBinding` 变体（按存储 Scope.GroupID 匹配）当前无生产调用方，若未来接线应传账号胜出组集合；`ForRouteStrategy` 按策略全清不受影响。

| B24 | 排队等待 | 高并发排队等待期间账号列表不重解析（等待后仅刷新并发 overlay + 重排序，preparation.go:668-675），与现有单组路径行为一致，扁平池无额外处理。 |

### 4.4 运行态与 jobs 面

| # | 边界 | 设计 |
| --- | --- | --- |
| B25 | 慢样本状态键 | 键与存储 Scope 同源、服务边界逐账号解析（详见 3.6，含存量零回归与 jobs 闭环论证）。 |

### 4.5 已知取舍

| # | 取舍 | 说明 |
| --- | --- | --- |
| T1 | 高并发准入跟随窗口组 + 容量时序 | 准入适用性（GroupType）与容量求和都发生在 merge 解析前的中间件层 → 容量为窗口组账号并发和（非全池）；GroupType 取窗口组。后移准入需重构中间件时序，V1 不做。（准入发生在路由解析前的中间件时点，分组口径取 SelectedGroupID 指向的加载组） |
| T2 | 热质量 / IP 避让信号命名空间 | 均跟窗口组，与单组路由信号隔离；短期信号，可接受。 |
| T3 | 权重忽略 | merge 不支持分组权重；需要配比时拆成多条合并路由或用权重路由。 |
| T4 | 配额窗口门跳过 | merge 依赖解析期逐片段批查为权威门（B14）；窗口门跳过是有意行为，测试锁定。 |

## 7. 实现核实项（已全部核实）

1. `CompletedAttemptInput.Account` 为 `AccountView` 接口；生产链唯一实现 `OpenAIAccountView` 包装完整账号；**生产完成路是组合根 chainFinalizationUsage（chain_usage.go:307-349）而非 gatewayusage/service.go 完成路**——记账改动按 3.5 点位清单执行。
2. 排序管道账号类型 `AccountCandidate = OpenAIAccountSecret`（含 BoundGroupID）——状态键逐账号解析直接可行。
3. 生产清理入口 `ClearNormalRouteLatencyDegradationForAccount` 按账号匹配、组无关——清理覆盖确认；`ForAccountBinding` 无生产调用方。
4. 热质量成本优先模式存在且排序要求非空 GroupID——窗口组满足。
5. 交互亲和命中跳过路由解析（preflight.go:463）；亲和记录组为首次创建时的组（preflight.go:415）。
6. **`BoundGroupID` 仅对 account_authorized 账号赋值（chain_accounts_secret.go:202-205），owner / group_authorized 恒 nil**——合并池必须全量显式 stamp（3.1 第 4 条）。
7. jobs 探针枚举直接读共享 Redis 运行态（无按策略×组枚举），用存储 Scope 重建键并按 Scope.GroupID 找凭据——键与存储 Scope 同源是硬约束（3.6）。
8. speed_first body admission 在 preflight 前中间件层执行，容量时序取舍见 T1。
