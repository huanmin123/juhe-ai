# 分布式部署与用户分片设计

## 文档目标

本文用于固定 `juhe-ai` 从单机轻量部署演进到多节点部署的设计边界，重点回答这些问题：

- 分布式模式如何通过配置启用，节点如何发现彼此。
- 多节点如何选出控制平面主节点，如何避免脑裂。
- 用户数据如何按系统账户归属到固定节点。
- API Key 请求、管理 API、后台 worker、统计和审计如何按用户 home node 路由。
- 节点故障、主节点故障、网络分区和后续副本能力分别怎么处理。
- 哪些能力放在第一阶段，哪些能力必须等后续阶段单独设计。

本文是后续实现和评审依据。第一阶段目标是“无副本用户分片 + 安全选主 + 自动路由”，不是一次性实现完整分布式数据库。

## 核心结论

- 默认部署仍是单机；只有显式开启 `distributed.enabled` 后才进入分布式模式。
- 分布式至少需要 2 个数据节点才有意义，但安全自动选主需要 3 个投票成员；2 个数据节点建议增加 1 个 witness 见证节点。
- 主节点只负责控制平面：节点状态、任期、分片归属、路由表、全局配置、后台任务归属和集群观测，不承载所有业务流量。
- 数据平面按系统账户分片。每个系统账户有且只有一个 `home_node_id`，该用户的 AI 账户、分组、API Key、使用记录、统计、审计和操作日志都写入 home node。
- API Key 请求没有登录态，必须通过全局复制的 `api_key_hash -> owner_system_account_id -> home_node_id` 路由索引找到 home node。
- 第一阶段 `replicationFactor = 1`。用户 home node 故障时，该节点用户不可用；不自动把用户数据切到其他节点。
- 第一阶段不做自动数据迁移、不做自动副本接管、不做跨节点资源授权实例，不引入 Redis、Kafka、PostgreSQL、ClickHouse 或外部分布式队列。
- 后续副本、手动迁移、节点 drain、跨节点授权和自动故障接管必须分别进入独立计划，不能混入第一阶段运行路径。

## 术语

| 术语 | 含义 |
| --- | --- |
| control plane | 控制平面，负责集群元数据、选主、节点状态、分片归属和任务归属 |
| data plane | 数据平面，负责用户业务数据、网关请求、统计、审计和本地 worker |
| leader | 当前任期内的控制平面主节点 |
| follower | 非主投票节点，接收 leader 心跳和元数据日志 |
| witness | 只参与投票和元数据日志确认，不承载用户业务数据的见证节点 |
| home node | 某个系统账户的唯一业务数据归属节点 |
| route table | 系统账户、API Key hash、节点地址和元数据版本组成的路由表 |
| term | 选主任期。term 越大，控制命令越新 |
| metadata version | 集群元数据递增版本，用于拒绝旧 leader 和旧路由写入 |

## 部署拓扑

### 推荐拓扑

```text
node-a  data + voter
node-b  data + voter
node-c  data + voter
```

3 个投票成员可以容忍 1 个节点故障并自动选主。任意 2 个节点形成多数派后，才能选出或维持 leader。

### 两数据节点拓扑

```text
node-a  data + voter
node-b  data + voter
node-w  witness + voter
```

如果只有 `node-a` 和 `node-b` 两台数据机器，必须额外增加 witness 才建议开启自动故障选主。witness 可以是轻量进程，不保存业务库、数据集库、usage shard 或统计结果库，只保存集群元数据和投票状态。

### 不推荐拓扑

```text
node-a  data + voter
node-b  data + voter
```

2 个投票成员没有多数派容错空间。任一节点不可达时，另一节点无法区分“对方宕机”和“网络分区”，自动选主会有脑裂风险。

该拓扑可以作为分布式路由开发 / 测试模式，但生产只能使用以下策略之一：

- 固定 leader，故障后人工切换。
- 禁用自动选主，只保留节点间转发。
- 显式开启不安全模式，并在页面和日志中持续提示脑裂风险。

## 配置模型

分布式配置属于启动配置，不放到普通系统设置里动态修改。所有节点的 `clusterName`、共享密钥和投票成员列表必须一致。

推荐配置形态：

```ts
distributed: {
  enabled: true,
  clusterName: "juhe-ai-prod",
  nodeId: "node-a",
  nodeRole: "data",
  advertiseUrl: "http://10.0.0.1:3000",
  bindUrl: "http://0.0.0.0:3000",
  peers: [
    { nodeId: "node-a", url: "http://10.0.0.1:3000", role: "data", voter: true },
    { nodeId: "node-b", url: "http://10.0.0.2:3000", role: "data", voter: true },
    { nodeId: "node-c", url: "http://10.0.0.3:3000", role: "data", voter: true }
  ],
  election: {
    heartbeatMs: 1000,
    electionTimeoutMinMs: 3000,
    electionTimeoutMaxMs: 6000,
    leaderLeaseMs: 8000
  },
  sharding: {
    strategy: "system-account-home-node",
    replicationFactor: 1,
    allowCrossNodeAuthorization: false
  },
  routing: {
    forwardTimeoutMs: 30000,
    maxForwardBodyBytes: "follow-system-settings-gatewayTextRawBodyLimitMegabytes",
    staleRouteMaxAgeMs: 30000
  },
  security: {
    sharedSecretEnv: "JUHE_AI_CLUSTER_SECRET",
    requireHttps: true,
    clockSkewMs: 5000
  }
}
```

环境变量建议：

```dotenv
JUHE_AI_DISTRIBUTED_ENABLED=true
JUHE_AI_CLUSTER_NAME=juhe-ai-prod
JUHE_AI_CLUSTER_NODE_ID=node-a
JUHE_AI_CLUSTER_NODE_ROLE=data
JUHE_AI_CLUSTER_ADVERTISE_URL=http://10.0.0.1:3000
JUHE_AI_CLUSTER_PEERS=http://10.0.0.1:3000,http://10.0.0.2:3000,http://10.0.0.3:3000
JUHE_AI_CLUSTER_VOTERS=node-a,node-b,node-c
JUHE_AI_CLUSTER_SECRET=change-me
JUHE_AI_CLUSTER_REPLICATION_FACTOR=1
```

启动校验：

- `distributed.enabled = false` 时保持现有单机行为。
- `distributed.enabled = true` 时必须配置 `clusterName`、`nodeId`、`advertiseUrl`、`peers` 和集群共享密钥。
- `peers` 中必须包含当前 `nodeId`。
- 数据节点数量少于 2 时拒绝启动分布式模式。
- 投票成员少于 3 时，自动选主默认关闭；除非显式配置开发 / 不安全模式。
- `replicationFactor = 1` 是第一阶段唯一支持值；其他值启动时报错。

## 控制平面

控制平面不处理所有业务请求，只维护少量集群元数据。leader 的职责：

- 接收节点心跳，维护节点健康状态。
- 维护当前 term、leader lease 和元数据版本。
- 为新系统账户分配 home node。
- 维护 `system_account_id -> home_node_id` 和 `api_key_hash -> home_node_id` 路由索引。
- 下发全局设置、供应商目录、模型目录和分布式运行参数。
- 决定后台 worker 的集群级任务归属。
- 汇总节点级统计快照，生成集群概览。
- 记录选主、节点离线、路由变更、分片分配和维护事件。

leader 不负责：

- 代理所有 `/v1` 网关请求。
- 读取或写入其他节点的用户业务库。
- 在请求链路实时聚合所有节点明细。
- 在第一阶段自动搬迁用户数据。
- 在第一阶段自动提升副本。

## 选主设计

第一阶段采用 Raft 风格的最小控制面选主，不实现通用分布式数据库，只复制集群元数据日志。

节点状态：

```text
follower -> candidate -> leader
leader -> follower
candidate -> follower
```

基本规则：

- 每个投票节点本地持久化 `current_term`、`voted_for` 和已提交的 metadata log index。
- follower 在 `electionTimeoutMinMs ~ electionTimeoutMaxMs` 内收不到 leader 心跳后进入 candidate。
- candidate 增加 term，向投票成员请求投票。
- candidate 获得多数票后成为 leader。
- leader 按 `heartbeatMs` 发送心跳，并携带当前 `term`、`leaderId`、`commitIndex` 和 `metadataVersion`。
- 任一节点看到更高 term，必须立即降级为 follower。
- 所有控制平面写命令都必须带 `term`、`leaderId` 和 `metadataVersion`。
- follower 只接受当前 leader 的元数据日志；旧 leader 的写入必须被 term fencing 拒绝。

多数派规则：

```text
quorum = floor(voterCount / 2) + 1
```

示例：

| 投票成员 | 多数派 | 可容忍故障 | 说明 |
| --- | --- | --- | --- |
| 2 | 2 | 0 | 不适合自动故障选主 |
| 3 | 2 | 1 | 推荐最小生产拓扑 |
| 5 | 3 | 2 | 后续大集群可选 |

脑裂约束：

- 没有多数派的分区不能选出 leader。
- 没有 leader 或 leader lease 过期时，集群元数据写入暂停。
- 少数派节点可以继续服务自己 home node 上已知 API Key 的本地网关请求，但不能创建系统账户、创建 / 轮换 / 删除 API Key、变更全局设置、变更授权关系或分配新分片。

## 元数据日志

控制平面变更通过轻量 metadata log 复制，不直接依赖所有节点同时写业务库。

日志事件类型：

| 事件 | 含义 |
| --- | --- |
| `node_joined` | 节点加入或重新注册 |
| `node_health_changed` | 节点健康状态变化 |
| `leader_elected` | 新 leader 当选 |
| `system_account_assigned` | 系统账户分配 home node |
| `api_key_route_upserted` | API Key 路由索引新增或更新 |
| `api_key_route_removed` | API Key 路由索引移除 |
| `global_setting_changed` | 全局设置变更 |
| `worker_lease_changed` | 集群级后台任务归属变化 |
| `node_draining` | 节点进入 drain，后续不再分配新用户 |
| `node_reactivated` | 节点恢复可分配 |

提交规则：

- leader 写入本地 pending log。
- leader 将 log entry 发送到投票成员。
- 获得多数派确认后标记 committed。
- leader 和 follower 都只应用 committed log 到本地路由表和元数据缓存。
- 应用 log 必须幂等，按 `term + index` 保证顺序。

## 分片模型

分片键是系统账户，不是 API Key、分组、AI 账户或使用记录。

```text
system_account_id -> home_node_id
```

选择系统账户作为分片键的原因：

- 系统账户已经是登录、调用方和数据隔离边界。
- 用户自有 AI 账户、分组、API Key、使用记录、统计和审计天然围绕系统账户闭合。
- 用户维度能避免跨节点实时聚合明细。
- API Key 可通过 owner 反查 home node。

新用户分配：

1. 创建系统账户请求进入任意节点。
2. 非 leader 节点将请求转发给 leader。
3. leader 根据节点健康、权重、已有用户数、最近写入压力和 drain 状态选择 home node。
4. leader 提交 `system_account_assigned` 元数据日志。
5. home node 在自己的业务库创建用户业务事实。
6. 所有节点应用路由表更新。

默认分配策略：

```text
candidate nodes = healthy data nodes excluding draining nodes
score = activeUsersWeight + recentRequestWeight + storagePressureWeight + manualWeight
pick lowest score
```

分配后固定，不因新增节点自动变化。后续 re-balance 必须通过显式用户迁移计划执行。

## 数据归属

第一阶段按以下规则划分数据：

| 数据 | 归属 |
| --- | --- |
| 系统账户登录身份、角色、状态、密码哈希、会话 epoch | 控制平面元数据，复制到所有节点 |
| 系统账户 home node 映射 | 控制平面元数据，复制到所有节点 |
| 用户自有 AI 账户、凭据引用、状态 | home node |
| 分组、分组账号绑定、API Key、API Key 多分组绑定 | home node |
| API Key hash 路由索引 | 控制平面元数据，复制到所有节点 |
| 使用记录、usage shard、原始审计、操作日志、运行日志索引 | home node |
| 用户级统计缓存、额度窗口、AI 性能、账号质量 | home node |
| 集群级统计概览 | leader 周期性汇总节点预聚合快照 |
| 全局设置、供应商目录、模型目录、系统公告 | 控制平面元数据，复制到所有节点 |
| 代理配置 | 第一阶段按节点本地运维资源处理，账号只能绑定 home node 可用代理 |

原则：

- 用户业务数据只在 home node 的 SQLite 文件内写入。
- 非 home node 不能直接打开或远程写 home node 的 SQLite 文件。
- 全局元数据只允许 leader 修改，通过 metadata log 复制。
- 页面查询不能为了全局视图实时扫描所有节点明细；只能读取每个节点 worker 预聚合后的摘要。

## 路由链路

### 登录态管理 API

```text
浏览器请求任意节点
  -> 节点校验登录 token
  -> 根据 system_account_id 查 home node
  -> 如果当前节点是 home node：本地处理
  -> 如果不是 home node：内部转发到 home node
  -> home node 返回结果
```

管理员全局页面：

- 系统账户、节点状态、集群设置等控制面页面走 leader。
- 用户资源详情页按目标用户 home node 转发。
- 跨节点列表只读取每个节点预聚合 / 固定窗口结果，不能在 API 请求里实时回扫明细。

### API Key 网关请求

```text
客户端请求任意节点 /v1/*
  -> 当前节点解析 Bearer token hash
  -> 查本地复制的 api_key_route_index
  -> 如果 route miss：返回本地 401/404 风格错误
  -> 如果当前节点是 home node：执行现有网关调度
  -> 如果不是 home node：内部流式转发到 home node
  -> home node 校验 API Key 当前状态、额度、分组和账号
  -> home node 转发上游并写本地 usage / audit / stats
```

转发要求：

- 文本请求体仍受系统设置 `gatewayTextRawBodyLimitMegabytes` 约束；入口 hard limit 和图像 lane 上限保持 `64MB`。
- 流式请求必须流式转发，不能缓存完整上游响应。
- 转发节点只做认证前路由，不写 usage、audit 或账号状态。
- home node 是唯一事实写入方。
- 如果 route table 版本过旧，home node 返回 `route_version_conflict`，转发节点刷新路由后重试一次。

### 内部转发 Header

内部请求必须携带：

```text
X-Juhe-Cluster-Name
X-Juhe-Cluster-Node-Id
X-Juhe-Cluster-Term
X-Juhe-Cluster-Metadata-Version
X-Juhe-Cluster-Timestamp
X-Juhe-Cluster-Nonce
X-Juhe-Cluster-Signature
```

签名输入至少包含：

```text
method + path + timestamp + nonce + bodyHash + sourceNodeId + targetNodeId + metadataVersion
```

安全要求：

- 生产必须使用 HTTPS 或内网 mTLS。
- 所有内部请求用共享密钥 HMAC 签名。
- timestamp 超过 `clockSkewMs` 拒绝。
- nonce 在短 TTL 内去重，防止重放。
- 内部 API 不接受公网客户端直接调用。

## 后台 worker 归属

单机模式下 worker 只服务本机。分布式模式下 worker 分为两类：

| 类型 | 归属 | 示例 |
| --- | --- | --- |
| 用户本地任务 | 每个 data node 自己执行，只处理本机 home users | usage 写入、审计落库、账号质量、用户统计、额度窗口、数据保留 |
| 集群控制任务 | leader 持有 lease 后执行 | 节点健康汇总、集群概览刷新、分片分配、drain 调度 |

worker 规则：

- home node worker 只扫描本机业务库、数据集目录库、使用记录目录库、usage shard 和统计结果库。
- leader 不能直接扫描其他节点 usage shard。
- 集群概览由各节点定期发布本地预聚合摘要，leader 合并摘要后写入集群级 summary。
- leader 切换时，集群级任务必须依赖 `worker_lease` 和 term fencing，旧 leader 不能继续刷新集群级结果。

## 会话与身份

分布式模式下，登录身份需要能在任意节点校验，但用户业务数据仍回 home node。

第一阶段建议：

- `system_accounts` 的身份字段作为控制平面元数据复制：用户名、角色、状态、密码哈希、`mustChangePassword`、`session_epoch`。
- 登录 token 使用集群共享签名密钥签发，包含 `system_account_id`、`session_id`、`session_epoch` 和过期时间。
- 任意节点可用本地身份元数据校验 token。
- 强制退出、重置密码、停用用户时，由 leader 增加 `session_epoch` 并复制到所有节点。
- 普通 session 行可以保留节点本地，用于审计最近登录；不能作为跨节点唯一鉴权事实。

这样可以避免为登录态单独引入外部 session store。

## 统一授权与团队边界

第一阶段先限制跨节点授权，避免把用户分片刚落地时就引入跨节点资源事实读取。

规则：

- 同一 home node 内的用户授权、团队授权和授权实例账户按现有模型工作。
- 资源所有者和被授权目标不在同一 home node 时，第一阶段返回明确错误：`跨节点授权暂未开放，请先迁移用户到同一节点或等待后续版本`。
- 系统团队如果包含多个 home node 的成员，第一阶段不能创建跨节点资源授权。
- 授权消耗统计仍由 home node worker 预聚合，不做跨节点明细扫描。

后续跨节点授权需要单独设计两种方案之一：

- 资源代理：被授权用户请求仍在自己的 home node，实际上游资源由来源 home node 代理执行。
- 授权实例复制：在被授权用户 home node 创建可调度实例，并安全复制必要的凭据引用和可用性状态。

这两种都会影响安全、审计、额度和账号状态，不能作为第一阶段附带实现。

## 故障语义

### leader 故障

- follower 超时后发起选举。
- 获得多数派的 candidate 成为新 leader。
- 新 leader 继续处理控制平面写入。
- 已有用户的 home node 网关请求可以继续按最后 committed 路由表执行。
- 选主期间，系统账户创建、API Key 创建 / 删除、全局设置、节点 drain 等控制面写入暂停。

### home node 故障

第一阶段 `replicationFactor = 1`：

- 属于该 home node 的用户不可用。
- 打到其他节点的该用户 API Key 请求返回明确 `home_node_unavailable`。
- 管理页面标记这些用户和资源为“所属节点不可用”。
- leader 不自动改写这些用户的 `home_node_id`。
- 恢复后该节点继续承接原用户。

### 非 home 转发节点故障

- 客户端可切到其他节点入口。
- 如果入口前有负载均衡，健康检查摘除故障节点即可。
- 因为业务事实写在 home node，非 home 转发节点故障不影响已转发完成的请求事实。

### 网络分区

- 有多数派的一侧可以选出 leader 并处理控制面写入。
- 没有多数派的一侧不能选 leader，不能处理控制面写入。
- 少数派 data node 可以按最后 committed 路由表继续服务本机 home users 的已知 API Key 请求，但页面必须展示“集群控制面不可用 / 本节点处于降级模式”。
- 降级模式不允许创建 / 删除 API Key、修改用户身份、修改全局设置、创建跨节点关系或执行迁移。

## 数据迁移与重平衡

第一阶段不做自动迁移，但设计保留手动迁移入口。

迁移状态：

```text
planned -> exporting -> importing -> verifying -> switching -> completed
planned -> cancelled
* -> failed
```

手动迁移流程：

1. leader 将用户标记为 `migrating`，暂停该用户控制面写入。
2. source home node 停止接收该用户新的 API Key 网关请求，或进入短暂维护窗口。
3. source 按用户维度导出业务库数据、统计数据和必要审计索引。
4. target 导入数据并完成 schema 校验。
5. target 执行一致性校验：核心资源数量、API Key hash、分组绑定、账号状态、最近统计窗口。
6. leader 提交 `system_account_home_node_changed` 元数据日志。
7. 所有节点刷新路由表。
8. source 保留短期只读副本，超过确认窗口后按离线维护删除。

迁移不进入普通请求路径，不写运行时自动兼容或双写逻辑。

## 副本与自动接管后续方向

后续如果要做到 home node 故障后用户仍可用，需要 `replicationFactor >= 2`。这不是第一阶段。

副本能力至少需要：

- 每个用户有 `primary_node_id` 和 `replica_node_ids`。
- primary 将业务变更、usage、审计、统计输入按用户维度复制到 replica。
- 复制日志有 offset、校验和、重放幂等和落后指标。
- leader 只在 replica 追平到安全水位后允许提升。
- 旧 primary 恢复后必须先降级为 follower replica，不能继续写旧 primary 身份。
- 对凭据、OAuth token、代理绑定和账号运行态要有单独冲突策略。

在没有副本日志和安全提升规则前，不能把 `home_node_id` 自动切到其他节点。

## 第一阶段实施顺序

1. 配置与启动校验：新增分布式配置解析、节点 ID、peer 列表、生产拓扑校验和单机默认行为。
2. 内部通信与安全：新增节点签名、心跳接口、节点健康状态和内部请求鉴权。
3. 控制面选主：实现 term、vote、heartbeat、leader lease 和多数派判断。
4. 元数据日志：实现 committed metadata log、路由表复制和 metadata version。
5. 用户分片：新增系统账户 home node 分配；新用户由 leader 分配，旧单机数据按当前节点作为 home node。
6. API Key 路由：维护 API Key hash 全局索引，网关入口按路由转发到 home node。
7. 管理 API 路由：登录态校验后按用户 home node 转发 my-* 和资源详情；控制面 API 走 leader。
8. worker 归属：本地 worker 只处理 home users，leader worker 处理集群级摘要和 lease。
9. 前端集群状态：展示 leader、节点、路由、用户分布和风险。
10. 验证与演练：覆盖 leader 故障、home node 故障、route table 滞后、2 节点不安全拓扑和单机回归。

## 验收标准

- 单机模式默认行为不变。
- 3 个投票节点可以自动选主，leader 故障后能在超时时间内选出新 leader。
- 2 个无 witness 投票节点不会默认开启安全自动选主。
- 新系统账户会被分配唯一 home node，并写入 committed 路由表。
- API Key 请求打到任意节点都能路由到 home node，usage、audit、账号状态和统计只写 home node。
- home node 故障时，该节点用户明确不可用，不自动漂移到其他节点。
- leader 故障期间已有本地用户网关请求可继续，控制面写入暂停到新 leader 产生。
- 网络分区时少数派不能选主，不能处理控制面写入。
- 页面能展示 leader、term、节点健康、用户分布、路由版本和风险提示。
- 所有全局概览读取预聚合摘要，不在请求链路扫描所有节点明细。

## 待确认

- 生产首期是否接受 `replicationFactor = 1` 下 home node 故障用户不可用。
- 是否必须支持 2 数据节点 + witness 作为推荐最小生产形态。
- 跨节点统一授权是否第一阶段直接禁用，还是提前设计资源代理。
- 管理后台入口是否由负载均衡打到任意节点，还是固定打 leader。
- 节点间通信是否要求 mTLS，还是内网 HTTPS + HMAC 先满足首期。
- 旧单机数据进入分布式时，是否统一把全部已有用户归属到当前节点，再由后续手动迁移分散。
