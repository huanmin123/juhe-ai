# 可靠统计与读写资源隔离设计

> 面向 PostgreSQL + Redis 高性能模式下的统计准确性、读写资源隔离、上线清理和压测验收。
> 高性能模式总体边界见 [PostgreSQL 与 Redis 高性能模式设计](PostgreSQL与Redis高性能模式设计.md)，执行计划见 [PLAN-20260705T092619000Z 可靠统计与读写资源隔离](../plans/计划-20260705T092619000Z-可靠统计与读写资源隔离.md)。

## 背景

生产排障已确认：管理列表、策略详情和下拉接口的慢，不是 PostgreSQL 表级全局锁，也不是 MVCC 读写互斥。真正风险来自这些资源竞争：

- `stats-worker` 高频刷新 `usage_scope_range_windows` 这类重窗口，产生大量 `DELETE / INSERT / UPSERT`、autovacuum 和 I/O 压力。
- record maintenance 曾在审计 payload blob 上做全局 orphan 证明式扫描，数据量大时会占用 PG 和 Node 事件循环。
- DB service、stats-worker、ingest-worker、ops-worker 都可能连接同一个 PgBouncer / PostgreSQL，PG 没有全局锁不代表 CPU、I/O、连接池和 autovacuum 不会被抢满。
- 前端弹窗会触发详情 + options 等 fanout 请求；如果后端同时被重统计占满，轻量读也会在端到端耗时上变慢。

因此本设计把“统计准确性”和“统计实时性”拆开：事实先可靠落 PostgreSQL，统计窗口允许分钟级到半小时级滞后，但不能丢事实，也不能让派生窗口刷新影响前台读。

## 目标

- 前台管理读和网关关键读不被后台统计、维护清理和长查询无意义拖慢。
- 使用记录、审计、操作日志等事实先落 PostgreSQL；统计结果通过游标可重放生成。
- 统计结果允许滞后，不追求实时；但是事实不丢，统计可重建，游标可校验。
- Redis 只保存可清理缓存、短 TTL 运行态和待落库队列；上线时不备份 Redis，但清理前必须确认未落库队列已经 drain。
- Redis key 必须带部署 namespace；多套环境共用 Redis 实例时不允许共享同一个 namespace。
- 压测必须同时看接口延迟、PG 活跃查询、连接池等待、Redis Stream pending/lag 和 worker 事件循环。

## 非目标

- 不引入 ClickHouse、Kafka、RabbitMQ 或新的分布式调度系统。
- 不把前台接口改成返回空统计、空列表或少字段来掩盖慢查询。
- 不为了旧 schema 写运行时兼容、双读双写或启动迁移逻辑。
- 不要求统计卡片、TopN、范围窗口和授权窗口秒级实时。

## 事实与派生

| 数据类别 | 事实源 | 是否必须备份 | 清理 / 重建策略 |
| --- | --- | --- | --- |
| 系统账户、AI 账户、分组、API Key、授权、代理、设置、公告 | `juhe_business` | 是 | 按当前 schema 备份和离线导入 |
| 使用记录事实 | `juhe_usage.usage_records` 与列表目录 | 按业务要求保留；常规上线不作为业务库备份 | 按保留期清理；统计可从保留期内事实重放 |
| 审计、操作日志、公开接口日志 | `juhe_dataset` | 常规上线不备份 | 排障数据，按保留期和容量清理 |
| 运行日志索引、cursor、facet | Go F1 专用运行日志库 | 常规上线不备份 | Go 唯一 writer，按 F1 保留期和容量清理，Node 只读 |
| 统计桶、范围窗口、TopN、额度窗口、系统指标 | `juhe_stats` | 不作为业务库备份 | 可由事实和重建脚本生成，允许清空重建 |
| Redis cache / state | Redis | 不备份 | 停服务后可清空，启动后自动回填 |
| Redis Streams 队列 | Redis queue / state | 不做长期备份 | 清空前必须停服务并确认 pending/lag 为 0，否则未落库消息会丢 |

准确性规则：

- 网关完成一次请求后，使用记录先进入 ingest 队列并落到 PostgreSQL 事实表。
- 统计聚合只读取已经安全落库的事实；如果 ingest 队列不可观测、写入失败或 Redis Stream 有更早 pending，则统计聚合跳过本轮。
- 统计结果和统计游标必须在同一个 PostgreSQL 事务提交；不能先推进游标再写结果。
- 窗口表、TopN 和趋势只作为读优化，不是账务事实源；窗口刷新失败只导致展示滞后，不代表事实丢失。

## Worker 与资源边界

| 角色 | 主要职责 | 资源策略 |
| --- | --- | --- |
| `db-service` | 管理 API、登录态、管理读写和网关关键 DB 读 | 前台读优先；纯读不进入 SQLite 写队列；PG 下通过 `application_name=juhe-ai:db-service` 可观测 |
| `ingest-worker` | 使用记录、审计、操作日志、公开接口日志和 record maintenance | append-only 事实写优先；维护清理小批次、低优先级 |
| Go F1 indexer | 运行日志索引、cursor、facet 和索引保留 | 独立直接异步并发；不使用 Node IPC、Redis 或任务队列 |
| `stats-worker` | 使用记录增量聚合、IP 聚合、重窗口、TopN、系统指标和表监控 | 可滞后；重窗口低频；慢 SQL 不得无限占用连接 |
| `ops-worker` | 账号测试、健康检测、冷却复测、OAuth 保活、授权到期和删除协调 | 外部 I/O 受控并发；业务写回走 DB service / typed operation |

PostgreSQL 连接规则：

- 所有 PG 连接必须通过 `storage/postgres-client.ts` 创建，设置角色化 `application_name`，便于在 `pg_stat_activity` 中区分慢源。
- 默认设置 `statement_timeout`、`lock_timeout` 和 `idle_in_transaction_session_timeout`，避免长查询或异常事务无限占用连接。普通 SQL 使用数据库或应用 role 默认值，显式事务再通过 `SET LOCAL` 收紧；不使用 URL startup parameter，避免 PgBouncer 兼容与跨事务污染问题。
- PgBouncer pool、`JUHE_AI_DB_POOL_MAX`、worker 并发和 System API in-flight 必须一起压测；不能只加连接数。
- 发现前台慢时，先按 `application_name` 看是否是 `stats-worker`、`ingest-worker` 或 `db-service` 占用，再看 SQL 文本、等待事件和 rows。

管理读路径规则：

- `GET /accounts`、`GET /route-strategies`、`GET /api-keys`、`/options` 和详情接口只读当前快照，禁止为了“保证默认项存在”在 GET 链路创建默认分组、策略或 API Key。
- 需要种子数据时只能在初始化、显式维护命令或 POST/PATCH 写路径完成，不能藏在列表、下拉和弹窗详情读取中。
- API Key secret reveal 属于读接口；操作日志异步记录，不能占用写 admission 后再返回密钥。

## 统计刷新分层

| 层级 | 示例 | 默认实时性 | 请求路径是否允许现场聚合 |
| --- | --- | --- | --- |
| 原始事实 | `usage_records` | 请求结束后尽快落库 | 不允许扫明细汇总 |
| 在线桶聚合 | minute / hour / day / totals | 1 到 5 分钟内推进，受 ingest 安全水位约束 | 不允许 |
| 轻量热窗口 | `usage_overview_windows` 今日概览 | 约 10 分钟，允许配置 | 不允许 |
| 重派生窗口 | `usage_scope_range_windows`、授权范围窗口、TopN、AI 性能 summary | 10 到 30 分钟或更低频 | 不允许 |
| 离线重建 | 统计口径升级、窗口损坏、上线后校验 | 停服务显式执行 | 不适用 |

热窗口拆分规则：

- `usage_hot_window_refresh` 只刷新轻量统计首页窗口，不再在每次用量聚合后刷新 `usage_scope_range_windows`。
- `usage_scope_range_windows` 保留独立定时任务，使用 source watermark 跳过无变化轮次。
- 用户不要求实时统计时，生产可把热窗口间隔调到 `600` 秒以上，把重窗口保持在 `30` 分钟级别。

## 维护清理边界

- 审计 payload blob 清理不能在每轮保留期清理后做全局 orphan 扫描；只清理本轮删除 refs 涉及的 candidate blob IDs。
- 账号 / API Key 关联明细清理必须等统计安全游标追平后小批删除，不能越过未聚合事实。
- 非业务数据硬清理使用小批次、索引条件和明确 cutoff；禁止在热路径上证明“全库没有 orphan”。
- 清理任务失败只影响容量回收，不能阻塞前台读或网关响应。

## 上线清理与备份口径

- 常规上线只备份业务库 / 业务 schema：系统账户、AI 账户、分组、API Key、授权、代理、设置、公告和必要业务关系。
- PostgreSQL 高性能模式不做全库业务外备份；`juhe_dataset`、`juhe_usage`、`juhe_stats` 按保留、取证或专项迁移需要单独处理。
- Redis 不做备份；上线可清空 Redis cache / state / queue，但必须先停服务并确认 Redis Streams pending 和 lag 都为 0。
- Redis namespace 是逻辑环境隔离边界，但不能替代物理角色隔离。生产显式设置稳定 namespace，压测 / 回归使用独立 namespace；高性能模式强制 cache/state/queue 使用三个不同 `host:port`，没有共享许可。
- 如果 Redis Stream 仍有未 ACK 消息，先启动 ingest-worker drain 或导出待处理消息；直接 `FLUSHALL` 会丢未落库事实。
- 统计库可清空后重建；清空前要确认这不会影响正在进行的额度判断窗口，必要时先停服务并跑离线重建。

## 观测与压测

上线前压测至少记录：

- System API 管理读：`my-accounts`、`my-route-strategies`、`groups/options`、详情接口 p50/p95/p99。
- 读写混合压测必须对每个 GET 操作设置单独 p95 / p99 门槛，不能只看整体 p95；整体平均值可能掩盖某个弹窗详情或 options 接口秒级慢。
- 网关：成功率、p95/p99、usage/audit/operation/public/runtime log 队列 pending 与 lag。
- PostgreSQL：`pg_stat_activity` 按 `application_name` 分组的 active、wait_event、最长 query、最长事务；`pg_stat_statements` 的 mean/max 和 calls。
- Redis：cache/state/queue 的 `used_memory`、`evicted_keys`、Stream length、pending、consumer lag。
- Node：server、db-service、ingest-worker、stats-worker、ops-worker 事件循环 lag 和 RSS。

压测通过口径：

- 前台管理读在后台统计开启时不进入秒级稳定慢。
- PG lock wait 为 0 或可解释短等待，active query 不长期堆积。
- Redis Stream 本轮 positive pending / lag 不持续增长。
- usage 事实落库数量与压测请求数对得上；统计滞后可接受并最终追平。
