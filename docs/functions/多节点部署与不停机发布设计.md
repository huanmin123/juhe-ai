# 多节点部署与不停机发布设计

> 状态：**dev 验证完毕、作为多机打底保留；生产不落地（2026-11-07 用户最终裁决）**。P0 文档、P1 门禁/账本/在线 DDL、P2 gateway 无状态、P3 jobs 单活/共享文件/前端拆出/LB/发布脚本均已实施，并在 dev 双机（203 + Mac）完成真实流量、滚动、故障与恢复演练（§8.7 dev 证据）。部署物与单机完全隔离在多机目录 [`docker/cluster/`](../../docker/cluster/README.md)（按角色 compose + 独立入口/前端 + 构建/滚动/自检脚本），`docker/single-server/` 保持现行生产形态不变。现行生产维持单机 Docker（无服务器资源），本设计成果留待未来具备多机资源时切换；切换前需用户重新确认，并按 §8.7 补齐需外部资源的演练（PG/Redis 主备、生产量级大表锁等）。已确认方向：多机 Docker、暂不使用 K8s、不做跨历史版本兼容（只保留发布窗口内 N/N-1 共存）。

## 1. 裁决摘要

1. **部署载体**：多台服务器各自运行 Docker Compose，前面挂云 LB 或自建 Nginx；不引入 K8s、Docker Swarm 或服务网格。K8s 作为未来编排升级路径，应用契约保持不变（§10）。
2. **版本策略**：只支持最新版。不维护跨历史版本升级矩阵，不做旧库自动升级，不保留跨发布批次的旧列。旧部署升级失败由维护者按当次发布说明处理，不属于本设计承诺。
3. **发布窗口兼容**：同一次滚动发布内，允许 N 与 N-1 两个二进制同时连接同一数据库。这是滚动更新的物理前提，不属于“历史版本兼容”；窗口结束、旧实例全部下线后，旧版本不再受支持。
4. **迁移分相**：结构变更拆成 **expand**（加新结构 + 双写/回填，旧二进制可运行）和 **contract**（删旧结构，旧二进制被拒绝）。expand 可在写者存活时执行；contract 要求旧实例全部下线 + 备份 + 锁超时，只有不可逆数据清退才强制停写；contract 本身通常是秒级元数据操作。
5. **应用形态**：gateway 多副本无状态；jobs 单活（PG leader lease），standby 只保留健康面且任务返回 skipped；前端从 gateway 镜像拆出独立托管（拆出时机 §12 待确认）。
6. **共享文件**：usage spool 与运行日志必须跨机可见。短期用 NFS/云 NAS 维持同源目录契约，长期改对象存储；具体方案 §12 待裁决。
7. **数据库**：PostgreSQL 使用云 RDS 主备或等效高可用，Redis 使用主从/Cluster（代码已支持 `single|cluster` 两种模式）；数据库不随应用容器部署在多台业务机上（具体形态 §12 待确认）。
8. **回滚**：expand 完成后回退二进制即可；contract 完成后只能恢复备份或前向修复，不提供降级迁移。

## 2. 目标与非目标

### 2.1 目标

- gateway 可水平扩展到 ≥2 台，单实例故障由 LB 摘除，不影响整体服务。
- 无 schema 变更的发布：逐台滚动，`/v1` 请求不中断；管理面允许短暂 502，旧页面刷新即可。
- 有 schema 变更的发布：expand 在线执行，滚动期间旧实例继续服务；新增/切换读写的版本不删旧列。
- 大改变更（改类型、改名、拆表/合表、改约束）在灰度窗口内完成：旧实例继续读写旧结构，不因结构变化报错；新代码通过双写/回填/读切换接管。
- jobs 任意时刻只有一个实例执行同一任务；发布时 leader 交接，中断秒级。
- 每次结构变更执行前可判定“是否在线安全”；不可在线项强制走窗口，不允许静默执行。
- 全部运维动作可用 Docker、云 LB 和脚本完成，不依赖 K8s。

### 2.2 非目标

- 不维护从任意历史版本升级到最新的路径；不为旧版本保留运行时兼容层。
- 不做双库蓝绿、逻辑复制切换或按版本切换数据库。
- 不做按系统账户的 home node 分片、跨节点路由或控制面选主；分片是另一套架构，不在本次范围。
- 不做 K8s、Swarm、服务网格或自动扩缩容；这些属于后续编排升级。
- 不改变业务 API、调度语义、计费口径、审计与权限契约。
- 不做跨发布批次的旧列保留；旧列最多保留一个发布批次（§6）。

## 3. 改造前现状与差距（2026-11-05 基线）

> 本节是 P1 改造前的取证基线，用于说明动机；当前实现已按 §5/§6 落地，门禁/账本/在线 DDL 的能力以 §5/§6 与代码为准。行号会漂移，本节只引用路径与符号。

### 3.1 部署与发布现状

- 生产形态是国内单台云服务器 + Docker Compose，`docker/single-server/compose.yml` 定义 `postgres`、`redis`、`gateway`、`jobs`、`maintenance`、`caddy` 六个服务，每服务单容器。
- `docker/single-server/Caddyfile` 的 upstream 是固定容器 IP `172.18.0.10:3000`，没有多实例池、权重或动态摘流。
- `docker/single-server/Dockerfile.runtime` 把 `build/frontend-dist` 烤进 gateway 镜像（`COPY build/frontend-dist /app/frontend/dist`），前端与后端生命周期绑定。
- `docker/single-server/deploy.sh` 绑定单台服务器：构建 → 上传 → md5 校验 → `docker compose build` → `up -d` → 健康检查 → `verify-release.sh`；`upgrade` 模式固定执行 `停 gateway/jobs → 备份 → upgrade → 拉起`。
- `docker/single-server/verify-release.sh` 强制断言 gateway 容器 env 含 `GOMEMLIMIT` 且 `mem_limit` 非 0（BUG-0313）；usage spool 同源与 jobs drain 断言随 2026-11-09 T188（网关直投 PG）删除。
- 运行日志由 gateway 的 FileSink 写节点本地 JSONL 并自行轮转/清理；jobs 的 F1 PG 索引器已下架，集中检索由 ELK/Loki 等外部抓取承担。

### 3.2 schema 门禁与迁移现状

- `backend-go/shared/platform/schemagate/schemagate.go` 的 `Evaluate` 按固定顺序求值：`stepMax > dbRevision` 视为升级中断；`dbRevision > binary SchemaRevision` 判定“二进制过旧”；`dbRevision < binary SchemaRevision` 判定“库待升级”；两者都 fail-fast。**因此 N 与 N-1 二进制不可能同时通过启动门禁。**
- `docs/functions/升级兼容与迁移账本设计.md` §2.2 明确非目标：“不做在线迁移。单机自托管接受停写窗口”；`upgrade` 必须带 `--stop-write-confirmed`。
- `backend-go/projects/maintenance/internal/schema` 的 `EnsurePostgres` 逐条 `ExecContext` 执行全量幂等 DDL，没有长事务，但全部 `CREATE INDEX` 是阻塞式，没有 `CONCURRENTLY`；`EnsurePostgresFiltered` 只分 Additive/Destructive 两相，尚未按“在线安全”区分。
- 迁移账本 `schema_state`/`schema_migrations` 只记录 revision，没有“最低可读二进制版本”字段。
- schema 账本与门禁覆盖不是全部：`schema_state` 位于 `juhe_business`，`EnsurePostgres` 覆盖 `business/dataset/usage/stats`（`codex_context` 已随 2026-11-07 Chat bridge 退役于 revision 20 drop，不再由 ensure 创建）；J3a `juhe_jobs`、J3b `juhe_j3b`、J2 account-balance 的 bootstrap 已于 2026-11-07 作为 revision 1/2/3 并入 `upgrade`（见 §8.3），`--apply-*` 仅保留为修复工具；运行时仍由各 Store 的独立 `CheckSchema` 守门。

## 4. 目标拓扑

```text
                         ┌──────────────────────────┐
        HTTPS ──────────▶│ 云 LB / 自建 Nginx        │
                         │ 健康检查 + 摘流 + 权重    │
                         └───────────┬──────────────┘
              ┌──────────────────────┼──────────────────────┐
              ▼                      ▼                      ▼
        gateway-1               gateway-2               gateway-3
        Docker Compose          Docker Compose          Docker Compose
        （无状态，可水平扩展）  （无状态）              （无状态）
              └──────────────────────┼──────────────────────┘
                                     ▼
                 ┌─────────────────────────────────────┐
                 │ 云 RDS PostgreSQL 主备（跨 AZ）      │
                 │ Redis 主从 / Cluster                │
                 └──────────────────┬──────────────────┘
                                    ▲
                         jobs-1（active）+ jobs-2（standby）
                         PG leader lease，standby 任务 skipped
```

- 每台 gateway 一个 compose 文件，只跑 gateway 容器；`.env` 由同一模板生成，`*_INSTANCE_ID` 必须唯一。
- jobs 独立一台或两台主备；`background_job_leases` 全局 leader 已于 2026-11-07 实施（§7.2），第二副本自动 standby。
- 前端静态资源独立容器或对象存储 + CDN，不再由 gateway 镜像提供。
- maintenance 是一次性容器，从发布流水线在任意一台执行；`advisorylock.UpgradeOrchestration` 已能防并发。
- 数据库不随业务机部署；备份、主备切换、连接池由云服务或独立数据库机承担。
- 连接数必须按副本预算：`gateway 副本数 × pool_size + jobs + maintenance < PG max_connections`，预留 ≥20%；超限用 PgBouncer。
- **部署形态隔离（2026-11-07 落地）**：单机形态继续使用 `docker/single-server/`（生产现役，行为不变）；
  本设计对应的多机形态全部隔离在 `docker/cluster/`（`compose.gateway.yml` / `compose.jobs.yml` /
  `compose.edge.yml`、独立 Caddyfile、`build-images.sh`、`rolling-release.sh`、`verify-cluster.sh`），
  同一套二进制两种形态兼容。操作口径见 `docker/cluster/README.md`；本目录是打底模板，
  未在现生产启用。

## 5. 版本与兼容模型

### 5.1 版本标识

- 发布版本继续使用 CalVer tag（现有契约），镜像 tag 与二进制 `--version` 同源。
- 二进制内嵌两个 schema 版本：
  - `SchemaRevision`：本二进制写入的结构版本。
  - `MinRequiredRevision`：本二进制正常运行所需的最低库结构版本，等于**本二进制所属发布批次的 `SchemaRevision`**。库低于该值必须拒绝启动，先执行 expand。
- 数据库 `schema_state` 增加两个字段：
  - `schema_revision`：当前库结构版本（沿用）。
  - `min_readable_binary_revision`：当前库结构仍允许的最旧二进制 `SchemaRevision`。

### 5.2 启动门禁

启动时读取 `dbRevision`、`dbMinReadableBinary`、`stepMax`，按以下顺序判定：

| 顺序 | 条件 | 行为 |
| --- | --- | --- |
| 1 | `stepMax > dbRevision`，且未完成步骤含 contract/破坏性步骤 | fail-fast：升级中断在途；旧二进制也不得启动，提示恢复备份或重跑 contract |
| 1a | `stepMax > dbRevision`，且未完成步骤仅为在线安全 expand | 旧二进制允许启动并 WARN“expand 中断，库结构仍兼容”；新二进制按顺序 3 拒绝；提示重跑 `upgrade --phase=expand` 续跑 |
| 2 | `binary.SchemaRevision < dbMinReadableBinary` | fail-fast：库结构已要求更新二进制 |
| 3 | `dbRevision < binary.MinRequiredRevision` | fail-fast：库太旧，提示先执行本批 `upgrade --phase=expand` 再启动新二进制 |
| 4 | `dbRevision > 0` 且 `stepMax == 0` | fail-fast：账本缺失/被清空 |
| 5 | 其余 | 通过 |

顺序 1/1a 的区分必须读账本 `schema_migrations.phase/destructive`，不能只看 `stepMax`；`schema_state.expand_completed` 只用于提示文案（expand 中断 vs 记账后 state 未推进）。在线 expand 期间旧实例可能因 OOM/节点故障重启，若一律按“中断”拒绝，会导致发布窗口内容量下降。

与现有实现的关键差异：**不再因为 `dbRevision > binary.SchemaRevision` 无条件拒绝旧二进制**。旧二进制能否运行由库侧的 `min_readable_binary_revision` 决定；expand 相把它保持在旧值，contract 相推进到新值。新二进制则由自己的 `MinRequiredRevision` 要求库至少达到本批结构，避免在新结构尚未 expand 时提前启动并运行时失败。这样 N 与 N-1 可以在发布窗口内共存，contract 后旧二进制自然被拒绝。

### 5.3 发布批次规则

- 每个发布批次只承诺与**上一个发布批次**的兼容窗口，不承诺跨多个批次。
- 有结构变更的批次必须拆两部分：
  1. **expand**：加表、加可空列、加常量默认列、加索引、加约束（`NOT VALID`）。完成后 `schema_revision` 推进，`min_readable_binary_revision` 保持上一批值，旧二进制仍可启动。
  2. **contract**：删旧列/旧表、收紧约束、删除过渡对象。要求旧实例全部下线、先备份、设置 `lock_timeout`；只有不可逆数据清退才要求停写。完成后 `min_readable_binary_revision` 推进到本批。
- 没有 contract 需求的批次一批完成；有 contract 需求的批次，contract 可以延后到下一个发布窗口。
- 不允许同一批次内既新增/切换读写字段又删除旧字段。
- 每批 expand 开始时把 `min_readable_binary_revision` 收窄到**上一批的 `SchemaRevision`**；即使上一批没有执行 contract，也不再允许更旧的二进制。这样兼容窗口始终只有一版。

发布窗口时序示例（假设上一批已完成 contract）：

| 阶段 | `schema_revision` | `min_readable_binary_revision` | 可启动的二进制 |
| --- | --- | --- | --- |
| 发布前 | N-1 | N-1 | N-1 |
| expand 完成、滚动中 | N | N-1 | N-1 与 N |
| contract 完成 | N | N | 仅 N |
| 下一批 N+1 expand | N+1 | N | N 与 N+1 |

- §2.2 非目标“不做在线迁移”改为“支持 expand/contract 分相；contract 仍要求停写与备份”。

## 6. 迁移设计

### 6.1 两相模型

```text
expand 相（在线）
  加表 / 加可空列 / 加常量默认列 / CREATE INDEX CONCURRENTLY
  ADD CONSTRAINT ... NOT VALID
  数据回填（分批、幂等、可暂停）
  → 写 schema_revision；min_readable_binary_revision 不变
  → 旧二进制仍可启动、继续服务

contract 相（窗口）
  DROP COLUMN / DROP TABLE / VALIDATE 后收紧约束
  → 写 min_readable_binary_revision = 当前 SchemaRevision
  → 旧二进制启动被拒绝
```

顺序不可交换：expand 必须先于新二进制滚动；contract 必须晚于所有旧实例下线。

### 6.2 命令契约

在现有 `maintenance upgrade` 上增加：

```text
juhe-ai-maintenance upgrade --phase=expand --online \
  --dsn "$JUHE_AI_POSTGRES_URL" --secret "$JUHE_AI_SECRET"

juhe-ai-maintenance upgrade --phase=contract \
  --dsn "$JUHE_AI_POSTGRES_URL" --secret "$JUHE_AI_SECRET" \
  --old-writers-drained --backup-confirmed
```

- `--phase=expand` 默认仍要求 `--online` 才允许写者存活；没有 `--online` 时维持现有停写确认语义，防止误用。
- `--phase=contract` 要求 `--old-writers-drained --backup-confirmed`；`--old-writers-drained` 声明旧二进制实例已全部下线。只有步骤自身声明 `destructiveData`（不可逆清退）时才额外要求 `--stop-write-confirmed`，不要求全局停写。
- `--old-writers-drained` 不能只靠人工声明：`deploy.sh contract` 必须先查询按 version 维度的请求指标，确认旧 gateway 与旧 jobs 请求=0 持续 ≥30min，并把查询结果写入报告附件；脚本校验失败时拒绝执行 contract。
- `--phase=all` 保持现有单机停写语义，作为 fallback。
- `--dry-run` 报告必须新增字段：`phase`、`onlineSafe`、`destructive`、`compatibleBinaryRange`、`estimatedLockRisk`。
- 报告与退出码沿用现有契约；`blocked` 仍表示库版本高于二进制或升级中断。

### 6.3 在线 DDL 规则

| 变更 | 规则 |
| --- | --- |
| 加表 | `CREATE TABLE IF NOT EXISTS`；不引用新表的外键可同批，否则下一批 |
| 加列 | 可空列，或常量默认值（PG 11+ 不重写表）；禁止 volatile 默认值 |
| 加索引（普通表） | `CREATE INDEX CONCURRENTLY IF NOT EXISTS`；逐条执行，不能放在事务/DO 块 |
| 加索引（分区表） | PostgreSQL 不支持在分区父表上直接 `CONCURRENTLY`：先 `CREATE INDEX ... ON ONLY parent` 建无效父索引（不递归锁全部分区），再逐分区 `CREATE INDEX CONCURRENTLY`，最后 `ALTER INDEX ... ATTACH PARTITION`；全部 attach 后父索引转 valid。当前实现只支持一级分区，遇到二级分区显式报错，不静默降级为阻塞式全表索引 |
| 加 CHECK/FK | 先 `NOT VALID`，后续 `VALIDATE CONSTRAINT`（只取 SHARE UPDATE EXCLUSIVE） |
| 改列类型 | 拆成“加新列 → 回填 → 切换读写 → contract 删旧列” |
| 重命名 | 不用 `RENAME` 做在线切换；用新列 + 双读过渡（如需）或直接 contract 窗口 |
| 删列/删表 | 只在 contract 相；设置 `lock_timeout`，低峰执行 |
| 大表回填 | 分批 + 断点 + 幂等；复用 `backfill_progress` 模式；单批有上限 |
| 全局约束 | 必须声明 `lock_timeout`（建议 2s）与重试策略；锁等待超时不得推进账本 |
| 索引并发失败 | `CREATE INDEX CONCURRENTLY` 失败会留下 invalid index；重跑前检测 `pg_index.indisvalid=false`，先 `DROP INDEX CONCURRENTLY` 再重建；失败不推进账本 |
| 长事务/复制槽 | contract 前检查 `pg_stat_activity` 长事务与复制槽延迟；`lock_timeout` 超时重试，不强制终止业务会话 |
| 连接池 | 迁移/contract 必须直连主库，不能经过 PgBouncer transaction mode（会话级 advisory lock、`search_path`、`CONCURRENTLY` 会失效） |
| WAL/磁盘 | 大表回填与索引创建前确认磁盘余量；监控 WAL 生成速率、主备复制延迟与磁盘水位；回填限速避免打满 WAL |

`schema` 包需要增加“语句级在线安全性”标记，`EnsurePostgresFiltered` 的 Additive 相在 `--online` 模式下只允许标记为在线安全的语句；遇到阻塞式索引或表重写直接拒绝执行并报错，不静默降级。

### 6.4 账本字段

| 对象 | 变更 | 说明 |
| --- | --- | --- |
| `juhe_business.schema_state` | 新增 `min_readable_binary_revision bigint NOT NULL DEFAULT 0` | contract 完成时推进；expand 保持旧值 |
| `juhe_business.schema_migrations` | 新增 `phase text NOT NULL DEFAULT 'expand'` | `expand` / `contract`；用于断点续跑与报告 |
| `juhe_business.schema_migrations` | 新增 `online_safe boolean NOT NULL DEFAULT false` | 执行前判定，执行后作为证据 |
| `juhe_business.schema_state` | 新增 `expand_completed boolean NOT NULL DEFAULT true` | 账本补列时为兼容已收敛的旧库默认 `true`；upgrade 完成 postflight 后写 `true`，失败不写（保留上一次值）。门禁的中断判定以 `schema_migrations.phase/destructive` 为准，本字段只作报告与排障，不单独作为放行/拒绝条件 |
| `juhe_business.schema_state` | 新增 `last_phase text` | 记录最近完成的相，便于排障 |

账本仍只记录一次性步骤与相状态；结构定义继续由 `EnsurePostgres` 全量幂等 DDL 收敛，不引入 goose/golang-migrate 双轨。

### 6.5 失败与续跑

- expand 失败：账本不推进 `schema_revision`，已成功的语句保留；重跑同命令从断点继续。允许在线重试，但每次重试前重新检查锁等待与语句安全性。expand 中断期间旧二进制仍可启动（门禁顺序 1a），避免在线扩容时旧实例重启被拒。
- contract 失败：进入 `backup-required` 状态，停止后续步骤；只能重跑同版本命令前向续跑，或恢复备份。
- 中断识别沿用 `stepMax > dbRevision`，但必须按账本 `phase` 区分：
  - expand 中断：旧二进制放行并 WARN；新二进制按 `MinRequiredRevision` 拒绝；重跑 expand 续跑。
  - contract 中断：旧结构可能已部分删除，所有二进制拒绝；只能重跑 contract 或恢复备份。
- `schema_state.expand_completed` 记录 upgrade 是否完整跑完 postflight：成功写 `true`，失败保留上一次值；中断相由 `schema_migrations.phase/destructive` 判定，不能只靠本字段。
- 任何 contract 步骤执行后，`min_readable_binary_revision` 不得回退；回滚只能恢复备份。

### 6.6 数据回填

- 回填是 expand 相的一部分，但必须独立可暂停、可重入、有批次上限。
- 回填期间新旧代码都能运行：旧代码不读新列，新代码读新列但允许空值回退到旧列（仅限发布窗口，不跨批次）。
- 回填完成后才能切换读路径；切换读路径属于 expand 批次内的代码发布，不单独做 contract。
- 回填进度、行数、批次耗时写入现有报告；失败不推进账本。

### 6.7 大改变更专项

> “大改”指无法用单条 `ADD COLUMN` 表达的变更：改列类型、改列名、拆表/合表、改主键、改分区、收紧约束、改枚举语义、删列/删表。无感的核心不是 DDL 技巧，而是**旧实例下线前保留旧结构可读写**；旧代码报错的根因永远是它访问的结构被改、被删或被收紧。

#### 6.7.1 三段发布模型

| 阶段 | 数据库 | 代码 | 旧实例 | 回滚 |
| --- | --- | --- | --- | --- |
| expand | 加新列/新表/触发器，回填历史数据 | 新代码双写；读新列，空值回退旧列 | 继续读写旧结构 | 回退新代码，旧结构仍在 |
| switch | 不改结构，最多补索引 | 新代码只读新结构；双写保留 | 灰度中，新旧并存 | 回退旧代码；双写保证旧结构是最新的 |
| contract | 删旧列/旧表/触发器，收紧约束 | 只依赖新结构 | 必须已全部下线 | 只能恢复备份或前向修复 |

#### 6.7.2 分类矩阵

| 变更 | expand | switch | contract | 主要风险 |
| --- | --- | --- | --- | --- |
| 改列类型 | 加新类型列；转换触发器或应用双写；分批回填 | 新代码读新列 | 删旧列；新列设 NOT NULL/默认值 | 有损转换、非法值行需先 dry-run 统计 |
| 改列名 | 加新列 + 双写；或基表改名 + 旧名视图 | 新代码读新列 | 删旧列/旧视图 | 视图可更新性有限；旧代码连接需独立 `search_path`/数据库角色，不能改连接配置时改用新列 + 双写 |
| 拆表 | 建新表；新代码双写；旧→新触发器；回填 | 新代码读新表 | 删旧表 | 反向同步遗漏会导致旧代码读到旧数据 |
| 合表 | 建新表；双写；回填 | 新代码读新表 | 删旧表 | 主键/唯一键冲突需先合并规则 |
| 改 CHECK/FK/NOT NULL | 先加宽松约束（新旧值都允许） | 代码只写新值 | 收紧约束并 VALIDATE | `NOT VALID` 只跳过存量行，新写入仍校验；旧代码写旧值必须仍被接受 |
| 改枚举/状态语义 | 新列或新值域，新旧值并存 | 应用映射到新值 | 收紧值域/CHECK | 旧代码写旧值必须仍能通过 |
| 改主键 | 新表 + 双写 + 外键重建；或双库蓝绿 | 新代码用新主键 | 切换后删旧表 | 外键多、不可在线概率高 |
| 改分区 | 新分区表 + 双写 + 回填 | 新代码读写新表 | 切换后删旧表 | 大表回填耗时长，需要限速 |
| 删列/删表 | 不做 | 不做 | 只在此阶段执行 | 旧实例未下线即执行会立即报错 |
| 大表类型重写 | 新列/新表 + 回填 | 新代码读新列 | 删旧列 | 禁止在线 `ALTER TYPE`（表重写 + 排他锁） |

#### 6.7.3 旧代码为什么不会报错

- 旧列、旧表、旧约束在 contract 前**不删、不改类型、不收紧**。
- 旧代码写旧列时，由触发器或应用双写同步到新列；新代码写新列时，双写旧列。两个方向至少覆盖一个，读路径才能一致。
- 新代码读新列，空值回退旧列，直到回填完成并切换读路径。
- 新约束必须接受旧代码写入的旧值：要么约束本身允许新旧值并存，要么触发器把旧值映射成新值。
- 禁止在旧实例存活期间直接 `RENAME COLUMN`、`ALTER COLUMN TYPE`、加严格 `CHECK`、`SET NOT NULL`、`DROP COLUMN/TABLE`。这是“旧的一直报错”的唯一根因。
- 唯一例外：已确认旧实例 100% 下线，且进入 contract 阶段。

#### 6.7.4 双写与同步实现

- **首选：单写 + 触发器双向同步**。新代码只写新列，旧代码只写旧列；触发器在任一列发生变化时用同一转换函数同步另一列。触发器必须同时满足：
  - `pg_trigger_depth() = 1` 防递归；
  - 只同步真正变化的列（`NEW.col IS DISTINCT FROM OLD.col`），避免新代码双写时重复覆盖。
- **备选：新代码双写 + 旧→新单向触发器**。所有写路径必须覆盖，漏一条就会产生新旧不一致；触发器加 `IS DISTINCT FROM` 条件，避免把新代码写入的值再覆盖一次。
- 禁止无条件双向触发器；禁止在触发器里调用可能抛错且无兜底的复杂转换（转换失败会让旧代码写入失败，直接违反“旧代码不报错”）。
- 运行时代码禁止 `SELECT *`（列集变化会让 scan 失败）；发布前扫描新增/修改的查询。
- 回填按主键范围或 `SKIP LOCKED` 分批，每批有上限并可限速；热点表先评估触发器写放大，必要时改用应用双写 + 异步校验。
- 一致性校验用分块/抽样，不要对大表做全表 `count(*)`；contract 前在低峰做一次分块精确校验。
- 回填与触发器必须使用同一个转换函数，避免两套转换口径。

#### 6.7.5 灰度与 contract 门禁

灰度按 LB 权重、用户或 API Key 分流；新旧版本同时写同一库，靠双写/触发器保持一致。观测项：新旧版本错误率、写入分布、回填进度、约束冲突、同步差异。

进入 contract 必须同时满足：

1. 旧版本实例数 = 0（LB 后端、日志版本号、实例心跳/版本上报均可作为证据）。
2. 双写/触发器至少经过一个观察窗（建议 24h），同步差异为 0。
3. 回填完成，行数/抽样/checksum 校验通过。
4. 可恢复备份完成并验证可读。
5. contract 步骤均为在线安全；如包含不可逆数据清退，必须停写并单独确认。

任一条件不满足就继续灰度，不允许“先删了再说”。

#### 6.7.6 不可在线的大改

改主键值、改分区键、跨表合并、PG 大版本/扩展升级属于高风险项，按以下顺序选择：

1. **拆批**：把一次大改拆成多个 expand-contract；能拆则拆，拆不动的进入双库/短窗口评估。
2. **双库蓝绿**：新库新结构 + 逻辑复制/CDC + 双写 + 追平校验 + 短暂只读切换；成本高，回滚靠切回旧库。
3. **短停写窗口**（30s–几分钟）：只用于不可拆且双库成本不划算的变更。

不接受“直接 `ALTER` 锁表几分钟”作为常规路径。

#### 6.7.7 预防性 schema 约束

减少大改比优化大改更有效：

- 主键用不可变 ID（UUID/ULID），不用业务字段。
- 枚举用 text + 应用层校验，不用 PG enum（改 enum 需要 DDL）。
- 时间用 `timestamptz`，金额用 `numeric`，避免后期类型迁移。
- 分区键提前设计（如按时间），避免后期改分区策略。
- 新需求优先加列/加表，不改旧列。
- 复杂扩展字段用 JSONB 仅限查询/约束要求低的场景。

## 7. 应用多副本设计

### 7.1 gateway 无状态清单

| 状态 | 现状 | 目标 | 处理 |
| --- | --- | --- | --- |
| 会话/组亲和、账户锁、Key 轮换、turn retry | Redis | 保持 | 无需改造 |
| RPM 并发/限流 | Redis `RedisAccountConcurrency`（2026-11-07 起） | 跨实例共享 | 已接线；`jobs` overlay v2 键空间待 P3 切换 |
| OAuth session store | Redis（2026-11-07 起） | 保持 | 已闭合；跨节点发起/回调共享，Redis 故障显式失败 |
| singleflight、负面缓存、进程内 LRU | 进程内 | 保留 | 声明为可丢失、仅性能优化 |
| J3b scheduler | PG 租约 + fence | 多实例安全 | 多实例演练验证 `JUHE_AI_J3B_INSTANCE_ID` 唯一 |
| F4 操作日志 owner | 写入 lease 每实例独立（`f4-operation-log-persistence:<instanceID>`）；retention 独立 store + 全局键 | 每实例可写；retention 单 owner | 已实施（2026-11-07）；真实 PG 双实例租约测试通过 |
| F3 审计写入 | 写入 lease 每实例独立（`f3-audit-log-persistence:<instanceID>`）；retention 独立 store + 全局键 | 每实例可写；retention 单 owner | 已实施（2026-11-07）；与旧全局键滚动互斥 |
| 验证码/登录限频（主面） | 已走 Redis（`NewRedisCaptchaService` / `NewRedisLoginGuard`） | 跨实例共享 | 无需改造；验证跨实例一致 |
| 验证码（J3b `/auth`） | Redis（`authsys.NewRedisCaptchaService`） | 共享 | 无需改造；验证跨实例一致 |
| 管理面 IP/用户限流 | `ratelimit.RedisStore`（生产 chain 路径） | 共享 | 已接（2026-10-24）；验证 namespace 一致与 Redis HA |
| API Key 额度在途预留 | Redis 单 HASH + expiry ZSET（2026-11-07 起） | 共享 | 已接；Lua 原子多 scope，Redis 故障 fail-closed |
| Realtime WS 连接计数 | Redis（2026-11-07 起，10min TTL + 20s ping 续租） | 共享 | 已接；Redis 故障 fail-closed 503；崩溃泄漏 ≤10min |

Realtime 计数的残余边界：若 Redis 连续不可用超过 10min，活跃连接的续租会失效，计数过期；Redis 恢复后新 acquire 只按当前可见计数判定，可能在旧连接自然结束前短暂超过每 Key 上限。故障期间 acquire 仍 fail-closed，不会因为计数过期而放行新连接；该边界由 P4 故障演练量化。

表中标“硬 blocker”的项未闭合，不得进入 L2。对应验收：

- RPM：N 个 gateway 对同一账户并发 N 次，Redis 计数 = N，无超卖、无重复释放。
- OAuth session：实例 A 发起的授权流程在实例 B 可完成（已 Redis 化）；Redis 故障时授权/回调显式失败，不允许静默回退进程内。
- 验证码/登录限频：实例 A 消耗后在实例 B 看到一致状态；失败时 fail-closed，不回落进程内存。
- F3/F4：两个 gateway 实例同时写入审计/操作日志均成功；retention 仍只有一个 owner；实例故障后 lease 可接管。

### 7.2 jobs 单活（2026-11-07 已实施）

第一版采用**全局 leader**：

- 启动时用 `background_job_leases` 的全局 lease（`scheduled:jobs-global-leader:global`，30s TTL、10s 续租）竞争 leader；owner ID 由实例 ID + 进程随机 token 组成，同名 `JUHE_AI_INSTANCE_ID` 的两个副本不会互相续租。
- leader 执行全部任务；standby 启动时只做幂等 bootstrap（schema ensure / 基线播种），随后只保留健康端点：scheduler 已装配但每轮任务在 leader 门禁处返回 `skipped`（`jobs_standby_no_leader`），不写业务表；J1/J2/J3a 与 worker writer/溢出回放组件的 `Run` 阻塞在 leader gate。
- leader 失租或续租失败且接近到期时，gate 取消组件 ctx 并返回 `ErrLeaderLost`，supervisor 收口后进程退出，由容器编排重启为候选；不在进程内重新竞选，避免旧 leader 携带过期状态继续写。
- 发布时先让旧 leader 优雅退出（释放租约），再启动新 leader；中断秒级。
- 现有 `withLease` 任务租约保留，作为 leader 内部或未来 active-active 的第二层保护；standby 的 scheduler 不获取 per-job lease。
- `/health` 新增 `leader` 与 `leaderStatus`（leaseKey/ownerId/leaseUntil）；`ready` 现在同时要求本进程为 leader、各组件就绪与 worker 运行。
- 若后续吞吐需要 active-active，按 `SingleOwner` / `Shardable` 逐任务开放，并核对进程内状态；不在第一版承诺。

### 7.3 共享文件（现状：默认不需要）

2026-11-09 T188 起，用量记录由 gateway 直投 PG（共享 `usagewriter`），`usage-record-spool`、jobs drain 与跨节点共享数据目录的硬依赖一并删除。运行日志由 gateway FileSink 写节点本地 JSONL，集中检索走 ELK/Loki 外部抓取；只有部署方要求集中留存文件时才把 `logs/` 挂到共享存储。

| 文件 | 写者 | 读者 | 跨机方案 |
| --- | --- | --- | --- |
| `logs/juhe-ai.<instance>.log` | gateway FileSink | 运维 / 外部采集 | 默认节点本地；集中留存时挂 NFS/云 NAS，或用 ELK/Loki 抓取 |

历史（2026-11-07 方案 A NFS 实测）：双机写同一 NFS 导出时按实例日志双向可见；`processlog.FileSink` 是常驻 fd，断连恢复后不会自动重开文件，写面恢复需重启进程或触发轮转（改进项保留）；跨机共享目录需统一节点 UID/GID，否则另一 UID 读 `0600` 文件会 `Permission denied`。该实测中的 usage spool 部分已随 T188 退役，不再作为现行方案。

- 采用 NFS/云 NAS 前必须完成：① rename/append 原子性测试；② 锁语义与延迟测试；③ 断开时写入失败行为（不得静默丢日志）；④ 恢复后追平；⑤ 单点故障演练。未通过不得进入 L2。
- 每台 gateway 必须写独立文件名（含 `instance_id`）；不得让多实例写同一文件。
- 无论哪种方案，`verify-release.sh` 的同源断言要改成多机版本：检查每台 gateway 的 spool 目录与 jobs 可见的共享目录一致，并检查 spool 追平。

### 7.4 前端

- 前端从 gateway 镜像拆出：独立 Nginx 容器或对象存储 + CDN。
- 已落地（2026-11-07，集群目录）：`docker/cluster/frontend/nginx.conf` 独立静态站，
  dist 经 `frontend_dist` 命名卷挂到 `/usr/share/nginx/html/__aisys__`（vite `base=/__aisys__/`，
  发布时 assets 先写、`index.html` 最后切换，nginx 不重启）；入口 Caddy 只把网关路由面
  （`/v1`、`/__aisys__/api`、`/__aisys__/health`、`/__aipublic__`）反代 gateway，SPA 与
  `dist/help` 走 frontend。单机形态仍由 gateway 内嵌 dist 承接（生产不变）。
- `index.html` 不缓存，assets 带内容 hash；发布时先上传新 assets，再切换 index。
- 管理面 API 只保证“当前前端 + 当前后端”同版本；滚动期间旧页面可能短暂不兼容，刷新即可。不引入跨版本 API 协商。
- 如果暂不拆出，至少要求滚动时新旧 gateway 镜像的前端 buildId 一致，或接受管理面短暂不可用。
- 前端若独立域名，必须配置 CORS（携带 cookie 的 origin 白名单）与 cookie 的 `Domain`/`SameSite`/`Secure`；否则登录态跨域失效。同域部署优先，避免引入 CORS。

### 7.5 会话、缓存与 LB 粘性

**结论：默认不需要 LB 粘性。** 登录态和调度会话亲和都在共享存储，请求落到任意节点都能恢复同一会话；只有少数仍留在进程内的状态需要先迁 Redis，或在过渡期对特定路径开粘性兜底。

| 状态 | 存储 | 跨节点 | 影响 | 多副本动作 |
| --- | --- | --- | --- | --- |
| 登录会话 `system_sessions` | PostgreSQL | 共享 | 无 | 无 |
| 调度会话亲和（账户/组） | Redis（生产装配 `CacheDriverRedis`；本地 ttlCache 在 Redis 模式下不可读） | 共享 | 无 | 无 |
| 账户内 API Key 亲和 | Redis（同一 `AffinityService`） | 共享 | 无 | 无 |
| 运行时配置/账户缓存 | Redis shared cache（`NewRedisSharedCacheFactory`）；Redis 模式下进程缓存为 no-op | 共享 | 无 | 无 |
| 缓存失效总线 | Redis 版本号（`inval.RedisSharedStore`） | 跨实例可见 | 无 | 无 |
| 验证码 / 登录限频（主面） | Redis（`NewRedisCaptchaService` / `NewRedisLoginGuard`） | 共享 | 无 | 无 |
| 验证码（J3b `/auth`） | Redis（`authsys.NewRedisCaptchaService`） | 共享 | 无 | 无 |
| OAuth 授权 session | Redis（30min TTL，2026-11-07 起） | 共享 | 无 | 无需 sticky；Redis 故障时授权/回调显式失败 |
| RPM / 账户并发计数 | Redis（2026-11-07 起，`DomainConcurrency`） | 共享 | 无 | 已接；Redis 故障 acquire 显式失败 |
| 请求级负面缓存 | 进程内 | 不共享 | 只影响同会话重试命中率 | 可接受 |
| singleflight | 进程内 | 不共享 | 只影响并发合并 | 可接受 |
| 手动账户测试队列 | 进程内单持有者 | 不共享 | 任务不跨节点接管，实例故障可能丢任务 | 单节点执行或迁共享队列 |
| 管理面 IP/用户限流 | `ratelimit.RedisStore`（生产 chain 路径） | 共享 | 无 | 已接；验证 namespace 一致与 Redis HA |
| API Key 额度在途预留 | Redis 单 HASH + expiry ZSET（2026-11-07 起） | 共享 | 无 | 已接；Lua 多 scope 原子，Redis 故障 fail-closed |
| Realtime WS 连接计数 | Redis（2026-11-07 起，10min TTL + 20s ping 续租） | 共享 | 无 | 已接；Redis 故障 fail-closed 503；崩溃泄漏 ≤10min |

LB 策略：

- 默认 round-robin / least-conn，不启用 cookie sticky。
- OAuth session 已于 2026-11-07 迁 Redis，J3b 验证码也已在 Redis，默认不启用 cookie sticky；只有出现未纳入本表的进程内状态时才评估路径级 sticky，且禁止 IP sticky（NAT/移动网络会变）。
- 状态迁 Redis 后立即关闭 sticky，避免把粘性变成长期依赖。
- 会话亲和的读写在 Redis 侧有 CAS/失败告警；Redis 不可用时按既有保守策略处理，不回落进程内存。

SSE：

- 连接本身固定在单节点；断流后重连可到任意节点，会话亲和键在 Redis，不依赖原节点。
- 滚动发布断流由客户端重试（既有契约）；图片/视频异步任务不受连接影响。

验收：同一会话先在节点 A 发起、再到节点 B 继续，必须命中同一账户/分组/账户内 Key；登录 cookie 在 A 建立后 B 可用；J3b 验证码跨节点签发/校验一致。

## 8. 流量与发布

### 8.1 LB 契约

- 健康检查：`GET /__aisys__/health`，使用 gateway 的 3306 健康端口（已绑全接口）。F3/F4 的 `auditLogReady`/`operationLogReady` 表示本实例写入组件存活；**未持有全局 retention lease 的实例也会 ready**，ready 不代表本实例在跑 retention。
- 上游：至少两台 gateway，权重相同；后续可按权重做金丝雀。
- Nginx 必须 `proxy_next_upstream off`，防止网关真实崩溃时把非幂等 POST 重放到另一实例；云 LB 同样必须关闭对非幂等请求的自动重试。
- SSE：`proxy_buffering off`，idle timeout 大于最长流；网关已发送 `X-Accel-Buffering: no`。
- **WebSocket（`/v1/realtime`）**：LB 必须支持 HTTP/1.1 Upgrade；idle timeout 大于 Realtime 会话空闲上限；连接固定在某节点，重连可到任意节点（会话亲和键在 Redis）。滚动发布会断开 WS，客户端按协议重连。
- 客户端 IP 透传：LB 必须设置 `X-Forwarded-For`，gateway 的 `JUHE_AI_TRUST_PROXY` 必须按实际代理层数配置；否则 IP 限流、审计和 IP 封禁会错。
- 管理面与 `/v1` 可以共用入口；如需隔离，管理面单独 upstream，便于灰度。

### 8.2 摘流与排空

- 发布一台前先调用 LB API 摘除该实例，等待连接排空（建议 preStop 15–30s）。
- 容器收到 SIGTERM 后：
  - 停止接受新请求；
  - 等待在途请求完成（现有主端口 10s 预算，需按最长请求调整）；
  - 释放 owner/租约；
  - 退出。
- SSE 是 Hijack 连接，不受 `Shutdown` 等待；第一版接受“滚动时断流 + 客户端重试”（现有契约），第二版增加活跃流计数与可配置排空预算。
- jobs 没有用户请求，直接停旧起新即可；确保 leader 释放后再启动新实例。

### 8.3 发布 runbook

**每次发布前置（所有类型共用）**

- 容量：滚动期间至少 N-1 台承载峰值；N=2 且余量不足时先扩到 3 台。
- 时间：避开每日备份窗口（当前 04:00–07:00）。
- 配置：每台 `maintenance check-config` 通过，配置与模板无 diff。
- 镜像：tag 不可变，记录发布 tag 与 schema revision。
- schema 覆盖：`upgrade` 的 EnsureAll 覆盖 `business/dataset/usage/stats`（`codex_context` 已随 2026-11-07 Chat bridge 退役于 revision 20 drop）；J3a（`juhe_jobs`）、J3b（`juhe_j3b`）和 J2 account-balance 已作为 revision 1/2/3 并入 `upgrade`（`EnsureTargetSchema` + bootstrap Apply + Verify），无需发布脚本另跑 `--apply-*`；三个 `--apply-*` 仅保留为幂等修复/补表工具。运行时仍由各 Store 的独立 `CheckSchema` 守门。

**常规发布（无 schema 变更）**

```text
0. CI 构建镜像，tag = git sha，推送镜像仓库
1. 更新一台 gateway：LB 摘流 → docker compose pull gateway → up -d → /health ready → LB 接回
2. 对其余 gateway 重复
3. 更新 jobs：停旧 leader → 起新 → leader 接管 → 健康检查
4. 验证 /v1 错误率、P99、SSE 断流率、jobs 滞后
```

**带 schema 变更（expand）**

```text
0. 新版 maintenance 镜像先就绪；J3a/J3b/J2 的 bootstrap 已含在 upgrade 的 revision 1/2/3，无需另跑 --apply-*（仅独立修复/补表时使用）
1. 运行 upgrade --phase=expand --online（单实例，advisory lock 防并发）
2. 核对报告：onlineSafe、compatibleBinaryRange、pending 步骤
3. 滚动 gateway（逐台摘流/健康/接回）
4. 更新 jobs（先停旧 leader，再起新）
5. 验证；旧二进制仍可启动，作为回滚路径
6. contract 延后到下一阶段：确认旧实例全部下线 → 备份 → upgrade --phase=contract --old-writers-drained --backup-confirmed（旧实例=0、无长事务、lock_timeout 生效时可在线）
```

**带 contract 的发布（不需要常规停写）**

```text
1. 确认旧实例全部下线：灰度 100%、旧 gateway 与旧 jobs 请求数均为 0、旧版本心跳/版本上报消失
2. 备份并验证可恢复
3. 在线执行 upgrade --phase=contract --old-writers-drained --backup-confirmed
   （设置 lock_timeout；删列/删表通常是秒级元数据操作）
   只有不可逆数据清退才停写并追加 --stop-write-confirmed
4. 验证结构、约束与业务读写；旧备份是本阶段唯一回滚载体
```

  - `build-images.sh`：本地交叉编译三二进制 + 前端 buildId 门禁 + 构建/推送

    spool、Caddy 上游池与入口全链路；
  - compose 按角色拆成 `compose.gateway.yml` / `compose.jobs.yml` / `compose.edge.yml`，
    各角色 `.env` 互不要求，避免单文件 profile 的全局插值耦合。

### 8.5 灰度门禁与发布观测

- **版本指标契约**：gateway/jobs 必须暴露 `build_info{version,schema_revision,instance_id}`；请求量、5xx、P99 指标带 `version` 维度。没有按版本维度的指标，就无法证明“旧实例=0”，不能灰度，也不能执行 contract。
  - 已实施（2026-11-07）：gateway/jobs 均暴露 `juhe_ai_build_info`（标签 `service`/`version`/`commit`/`schema_revision`/`instance_id`，值 1）；gateway HTTP `juhe_ai_http_requests_total`、`juhe_ai_http_request_duration_seconds`、`juhe_ai_http_requests_in_flight` 增加 `version` 标签。`instance_id` 取显式 `JUHE_AI_INSTANCE_ID`；未配置时 gateway 用 hostname、jobs 用实例 ID@hostname。
- 灰度阶段（初始目标，首次多机演练校准；未校准前不得当作已达成证据）：

| 阶段 | 流量 | 最短观察 | 晋级条件 | 回滚条件 |
| --- | --- | --- | --- | --- |
| 1 | 10% | 15min | 新版本 5xx ≤ 旧版本 +0.1pp；P99 ≤ 旧版本 +10%；双写差异=0；无迁移/约束错误 | 5xx > 旧版本 +0.5pp 持续 5min；或双写差异 >0；或关键错误日志 |
| 2 | 50% | 30min | 同阶段 1 | 同阶段 1 |
| 3 | 100% | 24h | 同阶段 1；旧版本请求数=0 | 同阶段 1 |
| contract | — | 旧版本请求数=0 持续 30min | 回填完成 + 校验通过 + 备份完成 | 任一条件失败不执行 |

- 基线：0.1pp / 10% / 0.5pp 是初始目标，基线由首次多机演练实测；校准后回填本节与 §11，未校准前只能作为目标，不能作为验收通过证据。
- 回滚动作：LB 权重回 0 → 确认旧版本恢复 → 保留双写与旧结构；contract 之后只能恢复备份。
- 镜像仓库与不可变 tag：多机发布必须从镜像仓库拉取，不允许上传 `build/` 到每台；tag 使用 git sha 或 CalVer，回滚使用上一 tag。
- 连接池预算：`gateway 副本数 × pool_size + jobs + maintenance < PG max_connections`，预留 ≥20%；超限用 PgBouncer 或降低 pool。
- 长流策略：文本 SSE 接受“断流 + 客户端重试”；图片/视频异步任务不受连接影响；管理面长请求必须摘流等待或返回明确失败，不允许静默截断；Realtime WebSocket 连接随节点退出断开，客户端按协议重连，不在服务端迁移连接。

### 8.6 部署级一致性契约

多节点不是把镜像起多份；以下配置必须全节点一致，否则会出现“部分节点正常、部分节点报错”：

| 项 | 要求 | 不一致的后果 |
| --- | --- | --- |
| `JUHE_AI_SECRET` | 所有 gateway/jobs 同值，生产 ≥32 字符 | API Key/凭据解密失败、会话亲和 HMAC 不匹配、J3b 身份签名不一致 |
| Redis URL / namespace | 全节点同一逻辑库与 namespace | 亲和/限流/缓存各写各的，等于没有共享 |
| PostgreSQL DSN | 全节点指向同一主库或同一 VIP | 数据分叉 |
| 时钟 | NTP 同步，偏差 ≤1s | 租约误判、JWT/cookie/TTL/限频窗口漂移 |
| `JUHE_AI_TRUST_PROXY` | 按 LB 层数一致配置 | IP 限流、审计和 IP 封禁错误 |
| 实例 ID | `JUHE_AI_RUNTIME_LOG_INSTANCE_ID`、`JUHE_AI_J3B_INSTANCE_ID`、owner ID 全节点唯一 | 日志 fencing 冲突、J3b owner 抢占 |
| 镜像 tag | 同一次发布全节点同 tag | 新旧混跑超出兼容窗口 |
| 配置 | 同一模板生成；发布前每台跑 `maintenance check-config` | 配置漂移导致部分节点启动失败 |
| 健康/指标端口 | 3306/3305 只在内网或 LB 探针网段可达，不公网暴露 | 健康端点与指标泄露 |
| 备份窗口 | 迁移/contract 避开每日备份窗口（当前 04:00–07:00） | 备份锁与 DDL 锁互相阻塞 |
| 日志 | 多节点日志集中采集（Loki/ELK/云日志）；本地 JSONL 只作 spool | 故障排查只能逐台 SSH，日志丢失 |
| 发布记录 | 记录 tag、schema revision、操作人、时间、灰度结果 | 无法追溯哪个版本、谁发布 |
| 发布互斥 | 发布脚本单入口或加锁（CI/运维平台），禁止两人同时滚动 | 两次发布交叉执行，镜像/schema 混用 |

- Secret 轮换必须全节点同批，不能单台滚动；轮换前确认旧 secret 仍可解密，否则先做数据重加密设计。
- 配置漂移检测：发布前对每台执行 `check-config`，并与模板 diff；不一致拒绝发布。

### 8.7 故障演练清单（L2 上线前必须完成）

| 演练 | 操作 | 通过标准 |
| --- | --- | --- |
| PG 主备切换 | 云 RDS 控制台触发切换，观察 gateway/jobs 重连与事务失败 | 连接池自动重连；失败请求可安全重试；无数据分叉 |
| Redis 主备/节点故障 | 切换或杀掉主节点 | 亲和按未命中降级；验证码/登录限流 fail-closed；不回落进程内存 |
| NFS/对象存储断连 | 断开共享目录 | gateway spool 写入失败可见，不静默丢；恢复后 jobs 追平 |
| 节点宕机 | 直接停一台 gateway | LB 摘除；其余节点承载；无登录/亲和丢失 |
| 滚动中断 | expand 中重启旧实例 | 旧实例按门禁 1a 启动；expand 续跑成功 |
| 备份恢复 | 从最近备份恢复到临时库 | 数据完整；RTO 记录 |
| 网络分区 | 节点与 PG/Redis 断连 | fail-fast/降级符合契约；恢复后自动恢复 |
| 长流/WS | 滚动时保持 SSE/WS | 客户端重连成功；无重复计费/重复请求 |

dev 跨机演练证据（2026-11-07，非生产量级；拓扑：dev 203（gw-a 容器 + jobs 容器 + Nginx LB 容器）+ Mac 156（gw-b 原生进程），PG/PgBouncer/Redis 用 dev 共享实例 + 独立临时库 `juhe_ai_sub2api_dev_multinode`（revision 21）+ 独立 Redis namespace `dev:multinode` + NFS 导出 `/srv/k8s/nfs/juhe-ai-rehearsal`）：

- 节点宕机（部分通过）：SIGKILL gw-b 后 LB passive failover 生效——`proxy_connect_timeout 2s` 下每个 fail_timeout 窗口最多 2 次 504（各 2.0s），其余请求全落健康节点（access log upstream 归属 + 耗时证据）；gw-b 重启后 fail_timeout 过期自动接回，轮询恢复（8 请求 4/4）。限制：Mac pf 对关闭端口丢包黑洞（非 RST），放大了被动检查窗口；生产 LB 必须配主动健康检查（§8.1 已要求），本项待生产 LB 形态复验。
- 摘流/排空（通过）：Nginx upstream 移除后端 + reload，摘流期间 6/6 请求全落 gw-a，gw-b 零流量；接回后恢复轮询。逐台滚动的前半段（摘流→更新→健康→接回）可直接复用本证据。
- jobs 单活跨机接管（通过）：Mac jobs-2 以 standby 加入（`leader=false`，任务 skipped）；杀 203 jobs-1 后 25s 内 jobs-2 接管（30s TTL 语义内）；jobs-1 回归后保持 standby 不抢锁；jobs-2 停止后 jobs-1 重新接管。
- NFS 断连（部分通过）：force 断连下 gw-b 存活（health ready、API 经 LB 401 正常）；恢复后 spool 语义自动安全（每写新开文件）、运行日志写面需进程重启恢复（FileSink 常驻 fd，改进项已登记 §7.3）；"spool 写失败可见、恢复后 jobs 追平"需带真实 API key 流量的补充演练。
- 双实例观测（通过）：gw-a/gw-b `juhe_ai_build_info{instance_id}` 各自暴露、schema_revision=21；`juhe-ai.gw-a.log`/`juhe-ai.gw-b.log` 在共享 NFS 目录双向可见。按 version 灰度观测需两个不同 version 的镜像，属滚动发布演练项。
- 真实流量跨机 spool 交接（通过，2026-11-07 晚；含一次错误结论修正）：首次演练时 gw-b 的 `data` 目录因 setup 脚本 `mkdir -p data` 后再 `ln -sfn` 变成 `data/data` 链接，spool 实际写本地，jobs 未消费——当时"跨机 spool 闭环"判断有误。修复（data 恢复为指向 NFS 的符号链接、spool 目录 0777、统一文件权限）后重测：gw-b 新请求的 spool 落 NFS（uid 501 可见于 203），6 个积压文件被 203 jobs 全量消费（目录清零），`usage_records` 6→12；演练库 deepseek 账户 + API Key 经 LB 4 次 `/v1/chat/completions` 全 200、upstream 分布 gw-a/gw-b 各 2 次、两实例 `juhe_ai_http_requests_total{version="dev"}` 37/2 与分布一致。**契约结论：跨机共享 spool 要求所有节点统一 UID/GID（生产 compose 的 app uid 1000 满足）；异构 UID 读端会 Permission denied。**
- 灰度观测（通过，2026-11-07 晚）：构造两个 version 镜像（`rev21-gray-a`/`rev21-gray-b`）分别跑 gw-b/gw-a，经 LB 6 次请求 200、upstream 4/2；两实例 `build_info{version}` 各自正确，`juhe_ai_http_requests_total{version=...}` 分别 4/2 与分布一致——按 version 观测能力可用。
- 网络分区（部分通过）：断 gw-b→PG/Redis 隧道后，运行期请求在缓存窗口内仍 200（进程内 apiKeyRuntime 等缓存命中，未构造 Redis 协调路径）；断连下**重启**进程挂起等待依赖（25s 未退出、health 不就绪），发布编排靠健康门禁超时回滚；恢复隧道后 10s 内 healthy、请求 200。
- 备份恢复（通过）：演练库 `pg_dump -Fc`（1.8MB）→ 新临时库 `pg_restore` 3s，191 张表、usage 20 行、schema_revision=21 与源一致；恢复库已删除。
- WS 握手（LB 层通过）：Upgrade 请求完整穿透 LB 到 gateway 业务校验（缺 model 时返回 gateway 的 `missing_model` 400，非 404/502）；实 101 握手受账户无 realtime endpointMode 限制未完成。
- 前端生产实施（完成）：`Dockerfile.runtime` 移除前端 COPY（镜像验证无 `/app/frontend`）、compose 新增 `frontend` 服务（img/healthcheck/只读卷）、Caddy 路由 `/v1`+`/__aisys__`→gateway、其余→frontend、`deploy.sh` 前端探针与发布后闭环改到 frontend 容器；Caddyfile/nginx/compose 分项校验通过。
- 未覆盖（需外部资源）：PG/Redis 主备切换（需云 RDS 或自建主备）、滚动中断的旧 revision 二进制启动（需构造旧门禁镜像）、生产量级大表锁/WAL、真实 realtime 上游握手；gw-b 原生进程形态为 Mac Local Network 隐私门禁限制（容器化会因 VZ NAT 不通 LAN 无法挂 NFS）。

## 9. 回滚矩阵

| 阶段 | 回滚方式 | 数据库处理 | 可观察结果 |
| --- | --- | --- | --- |
| expand 执行前失败 | 无 | 无 | 旧实例继续服务 |
| expand 成功后、新二进制未上线 | 无（无需回滚） | 无 | 旧二进制仍可启动 |
| 新二进制已滚动、contract 未执行 | 回退镜像到旧版 | 无（旧列未删、双写仍在） | 旧二进制通过门禁 |
| contract 执行前失败 | 旧结构仍在，回退镜像或重跑 contract | 无 | 旧二进制仍可启动 |
| contract 执行中失败 | 重跑同版本 contract 前向续跑，或恢复备份 | 备份恢复 | 依赖备份完整性 |
| contract 成功后 | 只能恢复备份或前向修复 | 恢复备份 | 旧二进制被门禁拒绝 |
| 数据回填后回滚代码 | 回退镜像 | 新列保留，旧代码忽略 | 回填数据仍在，不丢 |

## 10. K8s 演化映射

现在按以下契约实现，未来换 K8s 只改部署描述，不改应用代码：

| 当前（Docker） | 未来（K8s） | 现在必须满足的契约 |

| MND/NFR-006 | 定量 | SHOULD | 灰度 10%→50%→100% | 每阶段满足晋级条件；不满足时回滚 | 指标：5xx 率、P99、双写差异；阈值：5xx ≤ 旧版本+0.1pp、P99 ≤ 旧版本+10%、差异=0（初始目标）；回滚：5xx > 旧版本+0.5pp 持续 5min；基线：首次演练；测量：按 version 指标 |
