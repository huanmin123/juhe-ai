# 模型检测设计

> 面向 AI 与维护者。
> 本文定义模型检测功能的产品口径、权限边界、检测方法、结果分级和后续深度调研方向。

## 1. 文档目标

- 固定“模型检测”不是绝对真伪证明，而是当前账号真实网关链路下的模型可信度检测。
- 为后续独立菜单、接口、存储和页面实现提供统一边界。
- 当前已落地检测按供应商协议 profile 支持 GPT / OpenAI-compatible、Anthropic、GLM、DeepSeek 和 Gemini 首批完整模型 ID；后续模型扩展必须先补模型目录、协议专属探针集和评分基线。
- 模型检测入口、历史、报告、筛选、证据摘要和终端日志都必须使用完整模型 ID，不做简称展示。例如 Anthropic 只显示和提交 `claude-opus-4-8`、`claude-opus-4-7`，不显示 `opus-4-8`、`opus-4-7`；GLM 只显示和提交 `glm-5.2`、`glm-5.1`。
- 把后续深度调研拆成可验证问题，避免只靠单个提示词或模型自报身份判断。
- 当前产品目标按“强诊断、准确率优先”处理：模型检测不以成本、等待时间、请求次数或 token 消耗为约束，相关成本由发起用户承担；设计上优先压低误判和漏判概率。

## 2. 功能定位

模型检测用于帮助管理员和用户检查当前可用链路是否“像目标模型”：

- 目标模型是否符合当前账户供应商协议 profile 与账户支持模型配置，由发起检测前的本地校验负责；这不是可信度证据。
- 请求目标模型后，上游响应对象是否声明使用同一模型。
- Responses API、流式、结构化输出和工具调用等协议能力是否符合目标模型预期。
- 一组隐藏探针的输出是否接近目标模型的行为基线。

黑盒 API 无法在软件层 100% 证明上游物理模型身份。模型 ID、`/v1/models` 返回值、响应体里的 `model` 字段和模型自报身份都可能被上游代理伪造。因此页面和接口统一使用“可信度”“疑似不符”“不确定”等表述，不使用“已证明为真模型”作为结论。

## 3. 用户场景

### 3.1 管理员

- 在管理侧独立菜单 `模型检测` 中检测任意系统账户可管理或可见的 AI 账户。
- 管理侧默认按全部系统账户查看和搜索检测目标、可信对比账户与历史记录；选择具体系统账户后，账户下拉、发起检测、历史筛选和详情读取都收窄到该系统账户作用域。
- 可以筛选系统账户、AI 账户、目标模型和检测等级。
- 可以查看完整诊断摘要，包括 traceId、命中账号、绑定分组、请求接口、响应模型字段、协议能力结果、探针得分和耗时。
- 不能在页面展示上游 API Key、OAuth token、代理密码或完整敏感请求头。

### 3.2 普通用户

- 在用户侧独立菜单 `模型检测` 中检测 `我的 AI 账户` 中的 AI 账户。
- 可以检测被授权给自己的账户，但只获得脱敏检测结论。
- 授权资源检测属于一次真实使用动作，必须按当前用户计入使用记录、额度和授权消耗。
- 用户侧不能看到上游地址、完整响应头、完整请求体、代理信息、凭据或所有者内部诊断。

### 3.3 群成员自行检测

如果对外希望“大家自行检测”，推荐让用户登录本系统后在 `我的 AI 账户` 里选择自己的 AI 账户检测，不推荐跳转第三方检测网站粘贴密钥。

第三方检测网站无法避免 API Key 泄露、请求内容泄露、检测题泄露和结果不可追溯问题。系统内检测可以复用本地权限、审计、用量和脱敏边界。

## 4. 支持范围

当前已落地版本按供应商和协议档案分流检测，不自动复用 GPT 检测探针。首批目标模型必须全部使用完整模型 ID：

| 供应商 | 协议档案 / 检测协议 | 首批目标模型 | 说明 |
| --- | --- | --- | --- |
| GPT / OpenAI-compatible | OpenAI Responses | `gpt-5.5`、`gpt-5.4` | 沿用当前强诊断 Responses profile |
| Anthropic | Anthropic Messages | `claude-opus-4-8`、`claude-opus-4-7` | 不使用 `opus-4-8`、`opus-4-7` 简称；检测 `/v1/messages`、`/v1/messages/count_tokens` 和 `/v1/models` |
| GLM | OpenAI Chat Completions | `glm-5.2`、`glm-5.1` | 通用 GLM API 和 GLM Coding Plan 分别按自己的 `provider_protocol_profile_id` 判断，不混用额度语义 |
| DeepSeek | OpenAI Chat Completions | `deepseek-v4-flash`、`deepseek-v4-pro` | 只检测 DeepSeek 自身 Chat Completions 能力，不复用 GPT Responses 探针 |
| Gemini | Gemini native | `gemini-3.5-flash`、`gemini-3.1-pro-preview` | 检测 `generateContent`、`streamGenerateContent`、`countTokens` 和 `models` |

智谱 GLM 接入模型检测时不自动复用 GPT 检测探针。GLM 模型检测使用 GLM 模型目录、Chat Completions 协议一致性基线、行为探针和评分阈值；GLM Coding Plan 还需要额外标记套餐资源消耗提示。

DeepSeek 第一阶段支持 `profile_deepseek_openai_v1` 的 Chat Completions JSON / SSE，不能复用 GPT Responses 检测探针。DeepSeek 模型检测使用 DeepSeek 模型目录、Chat Completions 响应字段、SSE 一致性、usage 形态、`reasoning_content` 和 cache usage 口径，不发送 `/responses`、FIM、Chat Prefix beta、Anthropic Messages 或 GPT / Codex 专属检测项。默认检测模型使用 `deepseek-v4-flash` 和 `deepseek-v4-pro`，旧别名 `deepseek-chat`、`deepseek-reasoner` 不作为新检测默认项。

Anthropic 模型检测必须使用 Anthropic 原生 Messages 协议，不把 OpenAI Chat / Responses 请求桥接过去后再按 GPT 规则判分。Anthropic 目标模型、辅助模型、可信对比模型和报告模型字段都使用完整 Claude 模型 ID，例如 `claude-opus-4-8`、`claude-opus-4-7`。Claude Code 的 `opus`、`sonnet`、`haiku` 这类客户端配置别名只能作为账号模型目录或计价别名，不进入模型检测目标下拉，也不作为检测报告展示值。

Gemini 模型检测必须使用 Gemini native 协议，不把 OpenAI Chat / Anthropic Messages 桥接响应当成 Gemini 原生检测证据。`models/` 前缀只作为 Gemini API 原生返回形态参与解析；前端目标模型统一展示本地目录里的完整模型 ID，例如 `gemini-3.5-flash`，不在页面混用 `models/gemini-3.5-flash` 和 `gemini-3.5-flash` 两种写法。

检测目标只支持 AI 账户：复用账号测试的单账号命中能力，适合用户自行检查 `我的 AI 账户` 中某个具体上游账号是否可疑。模型检测不提供 API Key 或分组目标，避免用户误以为是在检查某个网关 Key 或分组调度策略。

GPT API Key 账号可以按公开 OpenAI-compatible API 检测；GPT OAuth 账号经过 Codex adapter，能力和公开 OpenAI API 不完全一致，第一版对 OAuth 账号只给出“链路与能力检测”结论，不把缺少公开 API 能力直接等同于模型不真实。

### 4.1 多供应商检测 profile

多供应商模型检测采用检测 profile 注册表，不再把模型检测写成全局 GPT 常量。每个检测 profile 至少包含：

- `providerCode` 与允许的 `providerProtocolProfileId`。
- 完整目标模型 ID 列表、默认模型和同供应商辅助对照模型。
- 真实探针请求路径和 payload builder。
- JSON / SSE 响应解析器，包括模型字段、可见输出、错误消息、usage、流式终态和工具调用结构。
- 协议能力探针和行为探针评分规则。
- 可信对比账户过滤规则。
- 当前探针版本号。

首批 profile：

| profile | 适用账户 | 主要探针 |
| --- | --- | --- |
| `openai_responses_strong` | `profile_gpt_openai_v1`、`profile_openai_openai_v1` 且账户支持 Responses | `/v1/responses` JSON / SSE、结构化输出、工具调用、usage、行为指纹、长上下文、稳定性、辅助模型对照 |
| `openai_chat_strong` | `profile_deepseek_openai_v1`、`profile_glm_general_openai_v1`、`profile_glm_coding_openai_v1`、`profile_gemini_openai_chat_v1beta` 等 Chat-only 档案 | `/v1/chat/completions` JSON / SSE、JSON 输出、tool calls、usage、行为指纹、长上下文、稳定性、辅助模型对照 |
| `anthropic_messages_strong` | `profile_anthropic_anthropic_v1`、后续明确支持 Messages 的供应商档案 | `/v1/messages` JSON / SSE、`/v1/messages/count_tokens`、tool_use、usage、行为指纹、长上下文、稳定性、辅助模型对照 |
| `gemini_native_strong` | `profile_gemini_native_v1beta` | `generateContent`、`streamGenerateContent`、`countTokens`、function calling、usageMetadata、行为指纹、长上下文、稳定性、辅助模型对照 |

可信对比默认只允许同供应商、同协议 profile、同目标模型的账户。跨供应商或跨协议的对比只能作为后续人工诊断项，不进入当前自动评分，避免把协议差异误判成模型差异。

### 4.2 官方资料校准与可行性结论

截至 2026-06-30 重新核对官方资料和真实兼容上游 smoke 后，当前识别路线可行，但只能定位为“可信度诊断”，不能表述为“物理模型身份已证明”。官方 API 能给出的强证据是：目标协议实际请求成功、响应里的模型字段与完整模型 ID 匹配、可见输出可解析、usage / token 字段形态正确、结构化输出 / 工具调用 / 流式事件符合该协议。`/models` 或等价模型目录只能证明目录可见，不进入当前可信度检测项和自动评分；模型自报身份不作为证据。

| 供应商 / 协议 | 官方资料可支持的检测信号 | 本项目结论 |
| --- | --- | --- |
| OpenAI Responses | Responses API 请求 `model`、`input`、`max_output_tokens`，响应输出 `output_text` / `output`，并支持工具和结构化输出能力 | 可继续作为 GPT / OpenAI-compatible 强诊断主 profile；仍需认为响应 `model` 可被兼容代理伪造 |
| OpenAI Chat-compatible | Chat Completions 响应的 `choices[].message`、`tool_calls`、`usage` 和 `model` 字段 | 适合 GLM、DeepSeek、Gemini OpenAI compatibility 等 Chat-only 账户做中高可信诊断；不复用 Responses 字段 |
| Anthropic Messages | Messages 返回 `content[]`、`model`、`stop_reason`、`usage`，工具调用使用 `tool_use` block | 可行；`claude-opus-4-8`、`claude-opus-4-7` 这类 Opus 4.7+ 检测请求不发送通用 `temperature` / `top_p` / `top_k` 采样字段，避免参数约束导致 400 |
| GLM OpenAI-compatible | Z.AI HTTP / OpenAI SDK 兼容资料展示 `glm-5.2` 通过 `/chat/completions` 请求，返回按 Chat Completions 读取 | 可行；资源不足、无 channel 或套餐限制只判定为不可检测 / 跳过，不判定模型不符 |
| DeepSeek OpenAI-compatible | DeepSeek 官方资料说明可用 OpenAI 兼容格式，并公开 V4-Pro / V4-Flash 通过 Chat Completions 接入 | 可行；检测 `deepseek-v4-flash`、`deepseek-v4-pro` 的 Chat JSON / SSE、usage、tool calls 和行为探针 |
| Gemini native | `generateContent` / `streamGenerateContent` 使用 `models/{model}` 路径，响应包含 `candidates[]`、`usageMetadata`、`modelVersion` | 可行但必须专门处理；短 `maxOutputTokens` 可能被 thinking tokens 挤占导致没有可见输出，因此 native 探针使用更高输出 token 下限，不全局强制 `thinkingBudget=0` |

Gemini 不能按 OpenAI Chat 或 Anthropic Messages 的字段直接判分。原生响应必须优先解析 `candidates[].content.parts[].text`、`modelVersion`、`usageMetadata` 和函数调用结构；如果走 Gemini OpenAI compatibility，则按 `openai_chat_strong` profile 单独判定，不把兼容响应当 Gemini native 证据。

当前最可靠的自动增强项仍是同供应商、同协议 profile、同完整模型 ID 的可信对比账户。跨供应商比较、跨协议桥接比较和 `/models` 目录命中只能辅助排查，不能进入自动高可信结论的核心证据。

本节参考官方资料入口：OpenAI [Responses](https://platform.openai.com/docs/api-reference/responses/create) / [Chat Completions](https://platform.openai.com/docs/api-reference/chat/create)、Anthropic [Messages](https://docs.anthropic.com/en/api/messages) / [prompt validation](https://docs.anthropic.com/en/api/prompt-validation)、DeepSeek [API Docs](https://api-docs.deepseek.com/)、Z.AI [Docs](https://docs.z.ai/)、Gemini [GenerateContent API](https://ai.google.dev/api/generate-content)。

## 5. 检测分层

### 5.1 模型选择与目录边界

模型检测发起前会校验目标模型是否适用于当前账户供应商协议 profile，并确认账户支持模型配置允许该完整模型 ID。该校验属于请求入口约束，不属于模型可信度证据。

注意：本项目当前 `/v1/models`、Anthropic `/v1/models` 和 Gemini `models` 响应都可能由本地模型目录生成，不依赖某个具体上游账号是否可调度。因此模型检测执行器不再调用 `/models` 或等价目录接口作为检测项，也不把本地目录命中或缺失写入报告评分。当前 GPT / OpenAI-compatible 模型检测的上游真实可用性以 `/v1/responses` 实际请求结果为准；DeepSeek / GLM Chat-only 检测以 `/v1/chat/completions` 实际请求结果为准；Anthropic 检测以 `/v1/messages` 实际请求结果为准；Gemini native 检测以 `generateContent` 实际请求结果为准。

限制：

- OpenAI-compatible 代理可以伪造模型列表。
- 本项目本地网关模型列表可能来自本地目录，而不是上游账号实时列表。
- OAuth / Codex adapter 未必支持完整公开 `/models` 语义。

### 5.2 响应对象检测

GPT / OpenAI-compatible 检测调用 `/v1/responses`，固定指定目标模型，检查响应结构。DeepSeek、GLM Chat-only、Anthropic Messages 和 Gemini native 不进入 Responses 检测，而是按各自 profile 使用协议专属响应对象规则。

可验证信号：

- HTTP 状态为成功。
- 响应对象包含 `object = response`。
- `status = completed`。
- 响应体 `model` 与请求目标模型一致。
- 模型字段匹配必须按目标模型本体判断：允许 `gpt-5.4` 或 `gpt-5.4-YYYY-MM-DD` 这类日期快照，不允许把 `gpt-5.4-mini`、`gpt-5.4-nano` 等变体当成 `gpt-5.4` 通过。
- 响应包含可解析 `output_text` 或 `output` 文本。
- 响应包含 `usage`，且 token 字段结构符合预期。

限制：

- `model` 字段同样可被上游伪造。
- 只测一次可能受临时错误、限流、代理和调度切换影响。

### 5.3 协议能力检测

用多类请求检查目标模型能力和当前协议 profile 的兼容形态。当前功能按准确率优先设计，不把低成本作为首要目标。GPT / OpenAI-compatible Responses 检测使用 Responses 能力项；Chat / Anthropic / Gemini profile 使用各自协议能力项，不能把 OpenAI Responses 的 `text.format`、Responses 工具调用或 `output_text` 字段直接套到 Anthropic、GLM、DeepSeek 或 Gemini。

建议第一版能力项：

| 能力项 | 目的 | 结论用途 |
| --- | --- | --- |
| Responses 基础文本 | 确认 `/v1/responses` 可用 | 必选 |
| 流式 SSE | 确认流事件、终态事件和首 token 可观测 | 推荐 |
| 结构化输出 | 确认 JSON schema / strict 输出能力 | 推荐 |
| 函数调用 | 确认工具调用对象结构 | 推荐 |
| 用量字段 | 确认 token 统计字段可解析 | 必选 |

协议能力不用于证明模型身份，只用于识别“明显不像 OpenAI GPT-5 系列公开 API 行为”的链路。

多供应商扩展的协议能力基线：

| profile | 必选能力 | 推荐能力 |
| --- | --- | --- |
| `openai_chat_strong` | Chat Completions JSON、usage、响应模型字段、可见文本 | SSE、tool calls、严格 JSON 输出 |
| `anthropic_messages_strong` | Messages JSON、usage、响应模型字段、可见文本 | Messages SSE、Count Tokens、tool_use |
| `gemini_native_strong` | GenerateContent JSON、usageMetadata、可见文本 | streamGenerateContent、countTokens、function calling |

### 5.4 行为指纹检测

行为指纹通过一组隐藏探针题做概率判断。探针题不在前端展示完整内容，避免被上游针对性适配。

探针原则：

- 不问“你是什么模型”，不依赖模型自报身份。
- 使用低温度、低输出 token、明确输出格式，降低随机性。
- 覆盖中文指令遵循、严格 JSON、短推理、代码理解、拒绝不合理要求、上下文保持和格式稳定。
- 每次从题库中随机抽取一部分，保留探针版本号和随机种子。
- 探针答案不要求逐字一致，优先采用可程序化校验的结构、关键词、约束满足率和错误类型。

行为指纹只能提升或降低可信度，不能单独给出“真实”结论。

### 5.5 强诊断增强检测

当不以成本、耗时和请求次数为约束时，默认启用强诊断完整检测：

- 多轮采样：关键协议检测、稳定性检测和可信对比探针执行多轮采样，降低偶发网络、限流、随机采样和单次幻觉带来的误判。
- 探针级暴力重试：单个探针只要本轮网关响应未成功，就不区分具体错误类型，在同一个被测账号上按 `10s -> 20s -> 30s` 最多尝试 3 次，单探针总等待不超过 60 秒；仍失败才判定该探针失败。重试不会切换到同分组其他账号，也不会对“响应成功但行为约束未通过”的判分失败做重试。
- 探针池扩大：完整检测使用强诊断探针集，覆盖中文指令、严格 JSON、函数调用、复杂约束、代码理解、拒答边界、指令优先级、格式稳定和知识 / 能力边界。
- 行为指纹聚合：行为探针不再依赖单题命中，而是按多题成功率、模型字段匹配率和约束满足率聚合评分；行为指纹大面积异常会显著降低可信度。
- 辅助模型对照：同一检测目标在目标模型之外，再请求同供应商、同协议 profile 下另一个完整模型 ID，例如目标为 `gpt-5.5` 时辅助请求 `gpt-5.4`，目标为 `claude-opus-4-8` 时辅助请求 `claude-opus-4-7`，目标为 `glm-5.2` 时辅助请求 `glm-5.1`。检测检查两个请求在行为、usage、结构和响应字段上的差异是否符合预期；如果两个模型表现完全同质且长期稳定一致，应降低可信度。当前完整 profile 已内置轻量辅助模型对照项。辅助模型响应字段不符只作为该对照项失败和扣分依据，不直接等同于“当前目标模型字段不符”；只有目标模型自身探针返回的模型字段不匹配，才触发硬性“疑似不符”结论。
- 长上下文探针：完整检测默认加入多窗口 needle-in-haystack，当前固定为 `8k / 20k / 60k` 三档输入 token 目标，用于识别“短上下文走真模型、长上下文切低质模型”的中转伪装。三档 prompt 按项目统一 token 估算器生成到目标长度，并在报告摘要记录窗口 key、目标输入 token 和上游返回的实际 input usage；长上下文聚合项全部通过才视为通过，部分窗口通过时总览最高只能到 `uncertain`，全部失败或明显异常时进入 `suspicious`。
- 可信对比：默认关闭。只有用户在发起检测时选择一个自己信任的同供应商、同协议 profile、同目标模型账户，才用该账户跑同一探针集，并把目标链路结果与可信对比链路做差异比较。后端不按账户类型、名称或 base URL 猜测“官网账户”；未选择、不可访问、不可调度、未绑定可用分组或与目标账户相同时，检测请求必须返回中文提示并失败，不能静默降级为无对比检测。
- 分布相似度对照：可信对比开启时额外执行隐藏分布探针。目标账户和可信对比账户使用同一批隐藏 prompt、多次采样，比较成功率、约束满足率、输出长度、usage 形态和输出文本相似度。当前强诊断 profile 使用更多隐藏题和更多采样轮次；该项只保存 prompt key、统计摘要和少量输出预览，不保存完整题面。分布相似度显著异常时降低可信度；如果目标模型自身字段仍匹配，则不直接覆盖为“响应模型字段不一致”。
- 反适配策略：探针题面、抽样顺序、随机种子和评分权重不在前端暴露；对可公开协议项和隐藏行为项分开计分，避免中转站只适配公开题。
- 置信度输出：报告展示“证据充分度”和“异常一致性”，例如多轮均通过、多轮部分波动、多轮稳定异常。稳定异常比单次失败更能支持“疑似不符”。

### 5.6 探针共享与专属实现策略

随着模型和协议 profile 增加，模型检测按“共享检测意图 + 专属协议适配”维护，避免每接一个模型复制一整套检测代码。

共享层统一收敛这些内容：

- 探针定义：行为题、分布题、长上下文窗口、稳定性题和判分所需的 prompt key。
- 判分器：模型字段严格匹配、JSON / 关键词 / 格式约束、长上下文 marker 命中、稳定性通过率、分布相似度和总览等级封顶规则。
- 报告结构：`itemType`、`status`、`score`、`traceId`、摘要证据、脱敏和保留期。
- 运行约束：固定命中被测账号、同账号重试、禁用会话亲和、不静默切号、按真实网关链路计费和审计。

协议 / 供应商专属层只实现这些差异：

- 请求入口和 payload：OpenAI Responses、OpenAI Chat Completions、Anthropic Messages、Gemini native 的路径、字段和工具调用格式。
- 响应解析：各协议的文本、模型字段、usage、流式终态、工具调用和错误字段。
- 能力基线：某协议不支持或语义不同的能力项必须在 profile 中单独定义，不把 OpenAI Responses 字段套到其他协议。
- 模型清单和辅助对照：同供应商、同协议 profile 的完整模型 ID、默认模型和 paired model。

新增模型时优先复用现有 profile 的共享探针和判分器；只有当协议字段、能力语义、模型基线或上下文窗口目标不同，才新增 profile 专属实现。新增 profile 必须同时补回归，至少覆盖协议 payload / parser、完整 profile、长上下文窗口、模型字段严格匹配、不可用边界和可信对比可用性。

## 6. 结果分级

建议返回稳定枚举和中文展示文案：

| 等级 | 枚举 | 判定口径 |
| --- | --- | --- |
| 高可信 | `high_confidence` | 响应模型字段、核心协议能力、多行为指纹、长上下文、三轮稳定性和可信对比 / 辅助模型对照均符合目标模型预期 |
| 较可信 | `likely` | 关键字段和大多数能力通过，少量非关键探针不稳定；长上下文聚合项必须通过 |
| 不确定 | `uncertain` | 链路可用但证据不足、长上下文仅部分窗口通过，或 OAuth / adapter 能力边界导致不能直接比较 |
| 疑似不符 | `suspicious` | 响应模型字段不匹配、核心能力缺失、行为探针大面积异常或长上下文聚合项失败 |
| 不可检测 | `unavailable` | 账号、绑定分组、代理、权限或上游不可用，未形成有效模型证据 |

准确优先评分维度：

- 响应对象：20 分。
- 协议能力：25 分。
- 行为指纹：35 分。
- 长上下文：15 分。
- 多轮稳定性：15 分。
- 可信对比 / 辅助模型对照：10 分。
- 分布相似度对照：15 分，仅在开启可信对比时加入总分。

最终分值只作为排序和解释辅助，前端主要展示等级、关键证据和风险提示。

## 7. 接口

管理侧：

- `POST /__aisys__/api/model-checks/run`
- `GET /__aisys__/api/model-checks/runs`
- `GET /__aisys__/api/model-checks/runs/:id`
- `GET /__aisys__/api/model-checks/options`

管理侧接口通过查询参数 `systemAccountId` 指定本次查看或检测的用户作用域。未传 `systemAccountId` 时，管理员按全局管理作用域读取模型检测历史、详情和 AI 账户 options，并可直接选择任意可管理或可见的 AI 账户发起检测；传入具体系统账户时，读写作用域必须收窄到该系统账户，不能落回当前管理员自己的默认作用域。

用户侧：

- `POST /__aisys__/api/my-model-checks/run`
- `GET /__aisys__/api/my-model-checks/runs`
- `GET /__aisys__/api/my-model-checks/runs/:id`
- `GET /__aisys__/api/my-model-checks/options`

运行请求。当前接口接受完整模型 ID，提交后由后端按目标账户 provider profile 校验；示例：

```json
{
  "targetType": "account",
  "targetId": "acc_xxx",
  "model": "claude-opus-4-8",
  "profile": "full",
  "trustedComparison": true,
  "trustedComparisonAccountId": "acc_trusted_xxx"
}
```

`targetType` 是后端检测目标类型字段，当前固定为 `account`，含义就是“检测 AI 账户”。`model` 必须是完整模型 ID，不能提交或展示简称。`profile` 是后端内部检测档位字段，当前固定为 `full`，含义是强诊断完整检测。前端不展示目标类型和检测档位选择，也不支持 API Key 或分组作为检测目标。

`trustedComparison` 默认 `false`。当用户选择 `trustedComparisonAccountId` 或显式传 `trustedComparison=true` 时，后端必须校验该可信对比账户是否为当前用户有权访问、可调度、已绑定可用分组，且和目标账户属于同供应商、同协议 profile、同目标模型的账户。未选择对比账户时返回“请选择可信对比账户后再开启可信对比检测”，本次检测不创建成功报告；对比账户不能和检测目标相同。

`GET /options` 响应应包含可信对比状态摘要：

```json
{
  "trustedComparison": {
    "enabledByDefault": false,
    "available": true,
    "message": "可信对比默认关闭；选择一个同供应商同协议且你信任的可用账户后，会额外消耗该账户额度"
  }
}
```

前端通过账户 options 接口提供可信对比账户下拉，不在页面内猜测哪个账户是“官网账户”。真正发起检测时后端仍要重新校验所选账户可用性。

返回摘要：

```json
{
  "id": "mcr_xxx",
  "targetType": "account",
  "targetId": "acc_xxx",
  "model": "claude-opus-4-8",
  "level": "likely",
  "score": 82,
  "message": "目标模型链路较可信，仍建议结合多次检测结果观察",
  "startedAt": "2026-05-20T10:00:00.000Z",
  "finishedAt": "2026-05-20T10:00:08.000Z",
  "durationMs": 8000,
  "checks": []
}
```

## 8. 存储

模型检测记录属于诊断记录，不属于核心业务配置。当前写入数据集目录库，并只保存有界摘要。

建议表：

- `model_check_runs`
- `model_check_items`

`model_check_runs` 保存检测目标、模型、等级、总分、状态、调用方、系统账户作用域、traceId、开始和结束时间。`model` 字段保存完整模型 ID；前后端类型、路由校验和 repository 查询都按字符串模型 ID 处理，不写死 `gpt-5.5 | gpt-5.4` 两值枚举。

`model_check_items` 保存每个检测项的结果、得分、耗时、错误摘要和脱敏证据。

模型检测历史默认按 `modelCheckRetentionDays = 30` 保留，后台 `data-retention-cleanup` 会批量删除过期的 `model_check_runs` 和对应 `model_check_items`，避免诊断明细在数据集目录库长期增长。

禁止保存：

- 上游 API Key、OAuth token、代理密码。
- 完整敏感请求头。
- 大体积完整响应体。
- 探针题库完整内容。

写入数据集目录库前，检测报告摘要需要同时执行两层脱敏：按字段名屏蔽 `authorization`、`api_key`、`access_token`、`refresh_token`、`password`、`secret`、`rawBody`、`fullResponse` 等敏感字段；按字符串形态识别并替换 `sk-*`、Bearer / Basic 凭据和带密码的代理 URL。顶层 `message`、`errorMessage` 与 JSON 摘要都必须走同一套规则。

如果需要排障，可通过 traceId 跳转使用记录、审计日志和运行日志；审计日志仍按既有保全策略控制。

## 9. 网关与统计边界

- 检测请求必须复用本地网关链路，不能在模型检测服务中另写一套直连上游逻辑。
- 检测 AI 账户时可以复用现有账号测试的单账号候选能力，确保不会静默切到同分组其他账号。
- 检测 AI 账户时必须按真实调用方计入使用记录、额度和授权消耗。
- 模型检测页面自身不做用量统计聚合；检测产生的 token、成本和错误继续进入既有 usage / stats 流程。
- DeepSeek、GLM、Anthropic 和 Gemini 进入各自协议 profile 的模型检测，必须固定命中待检测账户和对应 `provider_protocol_profile_id`，不能因为同分组或同 API Key 有其他供应商账户而切号完成检测。测试、批量测试和恢复探活同理必须走账号绑定代理和真实网关链路。
- 检测历史列表只查询检测记录摘要，不扫描使用记录或审计 payload 生成统计。

## 10. 前端页面

页面名称：

- 用户侧：`模型检测`
- 管理侧：`模型检测`

页面区域：

- 检测目标选择：仅 AI 账户。
- 检测目标应优先提供可搜索选择，避免让普通用户手工复制资源 ID；管理侧默认使用全部系统账户作用域，选择具体系统账户后把 `systemAccountId` 传给后续账户 options 和模型检测接口；用户侧调用当前用户作用域接口。
- 目标模型选择：按当前已选 AI 账户的供应商和协议 profile 动态加载；所有选项使用完整模型 ID，例如 `claude-opus-4-8`、`claude-opus-4-7`、`glm-5.2`、`glm-5.1`，不显示简称。
- 检测档位不对外展示；后端固定使用强诊断完整检测。
- 当前检测进度：响应对象、协议能力、行为指纹、长上下文、稳定性；开启可信对比时额外输出分布相似度对照进度。
- 可信对比账户：可选；用户自己选择一个同供应商、同协议 profile、同目标模型的可信账户作为对比链路，选择后会额外消耗该账户额度；页面不根据账户类型、名称或 base URL 自动判断。
- 结果总览：可信等级、分数、风险提示、耗时、traceId。
- 证据列表：每项检测的通过 / 告警 / 失败状态和脱敏说明。
- 历史记录：最近检测结果，支持按模型、目标和等级筛选。

所有页面文案、空态、提示和错误说明必须使用中文。

## 11. 风险与限制

- 黑盒模型检测天然只能给出概率判断，不能作为法律、账务或官方认证依据。
- 第三方中转可以专门适配公开探针，因此探针题库不能完全暴露。
- 模型版本会更新，行为基线需要随官方模型变化重新校准。
- 准确优先检测可以覆盖更多长上下文、复杂约束和多轮稳定性，但仍不能对抗所有自适应伪装。
- OAuth / Codex adapter 与 OpenAI API Key 公开 API 行为不同，必须单独标注检测边界。
- 检测会消耗 token 和额度，当前按用户自行承担成本处理；页面仍需明确展示预估成本、检测次数和预计耗时，避免误操作。

## 14. 深度调研结论

调研日期：2026-05-20。

### 14.1 官方信号边界

- OpenAI Models API 的 `listModels` 只承诺列出当前账号可用模型及基础 owner / availability 信息，不适合作为真伪证明。
- 本项目模型检测必须复用本地网关链路，而本地 `/v1/models` 当前由模型目录返回，所以实现时不能把本地模型目录命中解释成“上游账号可见目标模型”。当前检测执行器不再生成模型目录检测项。
- OpenAI RBAC 文档把 `List models` 和 `Model capabilities` 分成不同权限：前者是读取可见模型列表，后者是发起模型请求。模型检测需要同时处理“能列出模型但不能调用”和“能调用但模型列表不可用”的边界。
- Responses API 响应对象包含 `model`、`output`、`usage`、流式事件和工具调用结构，适合做协议一致性检测。它仍然是上游返回的数据，代理可以伪造字段，所以只能作为可信度证据。
- 官方 GPT-5.5 指南明确 `gpt-5.5` 支持 `gpt-5.4` 已有的 API 特性。因此第一版 `gpt-5.5` / `gpt-5.4` 可以共用协议能力检测集，但行为探针基线必须按模型分开版本化。

工程结论：

- 第一版必须至少检查 `/v1/responses` 非流式、Responses 流式、usage 字段、结构化输出和函数调用。
- 模型字段匹配只能加分，不能单独给出“高可信”。
- 响应 `model` 字段如果稳定返回目标模型的 mini / nano / 其他变体，必须作为硬失败证据，整体结论最高只能到 `suspicious`。
- 对 OAuth / Codex adapter 的检测要单独标注“adapter 能力边界”，不能和 GPT API Key 账号直接等价。

| --- | --- | --- |
| OpenAI Evals | eval 任务、样例、评分组织方式成熟，适合参考探针版本化和结果记录 | 框架偏评测平台，直接嵌入会过重 |
| promptfoo | provider、assertion、CI 回归和 deterministic assertion 思路适合轻量探针 | 它是通用测试工具，不负责本项目权限、审计和网关调度 |
| lm-evaluation-harness | 标准 benchmark 组织成熟，可参考任务抽象和多 provider 适配 | 运行时间偏长、依赖偏重，不适合作为本系统运行时依赖；可抽取少量思想到隐藏探针 |
| HELM | 多场景、多指标、透明报告适合参考报告结构 | 面向研究级评测，过重 |
| Veridrop | 与本需求高度相似：给定 `base_url + api_key + model` 后做协议、能力、行为和 usage 检测；OpenAI 检测覆盖基础请求、model 一致性、function calling、structured output、SSE、usage 后端指纹和 token 异常 | 第三方站点仍要求提交 API Key；其 OpenAI 检测主要基于 Chat Completions，而本项目目标模型优先走 Responses API |
| openai_key_checker | 说明社区里已有“检查 key 是否支持某模型”的简单需求 | 只查 `/models` 太弱，不能识别模型替换 |
| LLMmap | 用行为轨迹做低查询量模型指纹，证明“行为指纹”方向可行 | 需要训练模板和目标模型基线；GPT-5.5 / GPT-5.4 闭源模型难以构建强参考分布 |

工程结论：

- 不引入外部 eval 框架作为运行依赖。
- 内部实现一个轻量 `probe runner + deterministic checker`，借鉴 promptfoo 的断言思想。
- 报告结构参考 Veridrop 的“字段级证据”和 quick / standard / full 三档模式，但必须放在本系统权限和脱敏边界里。
- OpenAI 侧不能复刻 Claude thinking signature 这类加密级验证；报告必须明确标注“协议级 / 行为级可信度”。

### 14.3 学术与安全研究结论

- LLM API Audit 调研了分类器、身份提示、模型等价测试、benchmark 和 logprobs 等方法，结论是纯输出文本方法面对细微替换、随机替换或自适应攻击时能力有限；logprobs 更强但通常不可用；可证明完整性需要 TEE 等硬件或服务端机制。
- Model Equality Testing 把黑盒 API 与参考分布的差异检测形式化为双样本检验。这个方法适合有参考分布、可重复采样、可接受统计成本的场景；本项目准确优先模式应借鉴“多探针、多次采样、统计置信度”，但不照搬研究级完整检验。
- Rank-Based Uniformity Test 进一步强调 API 黑盒和缺少 logits 时的困难，并尝试在有限查询预算内做更稳健审计。它仍要求更强的参考条件，不适合第一版工程落地。
- LLMmap 说明“主动行为指纹”可以识别模型，但需要训练或维护目标模型模板；模型快速迭代时基线维护成本高。

工程结论：

- 第一版只承诺“可信度检测”，不承诺“证明真模型”。
- 检测报告必须展示证据来源和限制，不输出法律式确定结论。
- 不做 logprobs、TEE、可验证计算或完整模型指纹分类器；这些放入后续研究项。

### 14.4 外部检测网站结论

存在面向中转站检测的网站和开源项目，例如 Veridrop；也存在只检测 API Key 是否支持某模型的简单 checker。它们对调研有价值，但不建议把用户引导到第三方站点粘贴密钥。

原因：

- OpenAI Help Center 明确提醒不要分享 API Key。
- 第三方检测站点需要 `base_url + api_key + model` 才能跑真实检测，用户必须信任站点不会记录、转卖或滥用密钥。
- 即便开源，也只有自托管部署才能把密钥留在用户控制的网络内。
- 本项目已经具备登录态、账号、分组绑定、审计和脱敏边界，内置检测比外跳网站更安全、可追溯。

工程结论：

- 页面可以写“系统内检测，不需要把密钥交给第三方网站”作为安全价值。
- 不在产品里推荐外部检测站点作为常规入口；可以在文档中作为研究参考。

### 14.5 第一版检测 profile 建议

以下 profile 仅作为内部研究分层，不作为第一版页面选择项。

快速检测：

- `/v1/responses` 非流式最小请求。
- 1 个结构化输出或函数调用轻探针。
- 只用于临时连通性确认，不作为默认可信度判断。

标准检测：

- 快速检测全部项目。
- Responses 流式 SSE 检测。
- 结构化输出和函数调用都检测。
- 6-10 个隐藏行为探针。
- 用于普通排障研究，不作为当前页面按钮。

强诊断完整检测：

- 标准检测全部项目。
- 使用强诊断隐藏行为探针集，覆盖严格 JSON、代码理解、复杂约束、拒答边界、指令优先级、格式稳定和中文约束。
- 默认加入更长上下文 needle-in-haystack，并执行三轮稳定性探针。
- 单个网关探针只要未成功，同账号按 `10s -> 20s -> 30s` 最多尝试 3 次，报告记录每次尝试的 traceId、HTTP 状态和摘要错误。
- 对 `gpt-5.5` 和 `gpt-5.4` 做辅助模型对照；可信对比默认不开启，只有用户显式选择可信对比账户时，才做同探针集 live 对照和隐藏分布相似度对照。
- 当前作为唯一实际运行 profile，优先保证判断质量。

### 14.6 第一版探针策略

探针题库建议拆成公开规则和隐藏题面：

- 公开规则：会检测协议、结构化输出、函数调用、流式一致性和少量行为指纹。
- 隐藏题面：具体 prompt、期望结构、判分器、权重和随机抽样策略不在前端暴露。
- 探针版本：`probeSetVersion` 写入检测报告，后续模型基线变化时可比较新旧版本。
- 判分方式：优先 deterministic checker，例如 JSON schema、字段存在、事件顺序、正则、关键词、拒答边界、长度范围和数值关系；减少 LLM-as-judge。
- 共享优先：行为题、长上下文窗口、稳定性题、分布题和等级封顶逻辑先沉到共享探针层；协议 profile 只补请求 payload、响应 parser、能力差异和模型清单。
- 长上下文反降级：长上下文不只保留一个固定窗口，应使用 `8k / 20k / 60k` 三档目标输入 token 窗口；低档通过而高档失败时，视为疑似“按上下文长度切换模型”的风险信号，不能输出高可信或较可信结论。

不建议第一版使用的问题：

- “你是什么模型？”：只能作为非核心参考，不作为核心证据。
- 大型公开 benchmark：容易被针对，运行依赖重，不适合作为系统运行时依赖；可抽取少量不可公开的轻量变体。
- 只看速度或价格：延迟和成本受代理、地区、负载、并发和缓存影响，不能证明模型身份。

### 14.7 推荐落地方案

第一版推荐做成内置自托管检测，不推荐把用户引导到第三方网站：

1. 默认入口只检测 AI 账户，也就是用户在 `我的 AI 账户` 中配置或绑定的账户。
2. 后端固定使用“强诊断完整检测”，前端不展示检测档位；当前目标优先保证检测准度，不以节省成本、请求次数或时间为约束。
3. 检测执行器分为 `responses_basic`、`responses_stream`、`structured_output`、`function_calling`、`usage_shape`、`behavior_probe`、`long_context`、`stability` 和 `cross_model` 九类检测项；显式选择可信对比账户时额外生成 `trusted_comparison` 和 `distribution_similarity` 检测项。`long_context` 内部由 `8k / 20k / 60k` 三档子探针聚合，报告只保存窗口 key、目标输入 token、上游 input usage、通过率、摘要输出和 traceId，不保存完整上下文题面。
4. 每个检测项只保存 `status`、`score`、`durationMs`、`evidenceSummary`、`traceId`、`errorCode`、`errorMessage` 和脱敏字段，不保存完整请求体、完整响应体或隐藏题面。
5. `high_confidence` 需要响应对象、协议能力和行为探针都通过；本地模型目录不进入可信度评分。
6. `suspicious` 触发条件应包含硬失败：响应 `model` 明显不匹配、核心 Responses 字段缺失、工具调用结构明显不是 OpenAI 形态、usage 出现异源字段痕迹或隐藏探针大面积失败。
7. `unavailable` 用于权限、额度、账号不可用、代理失败、账户未绑定可用分组、请求超时等未形成模型证据的情况，不能误判成假模型。
8. 强诊断模式下，`high_confidence` 必须要求行为指纹、长上下文和三轮稳定性通过；单轮协议通过最多只能给到 `likely`。长上下文仅部分通过时最高为 `uncertain`，长上下文聚合失败时进入 `suspicious`。
9. 可信对比是用户显式选择的增强项，默认不开启；开启时若未选择可用可信对比账户，接口必须失败并提示，不允许自动退回普通检测。
10. 未成功的探针按探针粒度在同一账号上暴力重试，连续多次仍失败才落失败证据；报告保存尝试次数、状态码和 traceId，便于排查网络、限流、权限、协议或上游错误。

实现优先级：

1. 后端只保留 `account` 目标和完整 profile，复用网关真实请求链路，打通数据集目录库摘要保存。
2. `account` 目标复用现有账户测试的单账号候选能力，探针重试也固定使用同一个候选账号，防止静默切号。
3. 前端交付一个中文独立菜单，只展示 AI 账户选择、模型、可信对比账户、结果等级、证据列表和历史记录。
