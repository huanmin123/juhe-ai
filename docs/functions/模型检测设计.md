# 模型检测设计

> 面向 AI 与维护者。
> 本文定义模型检测功能的产品口径、权限边界、检测方法、模型指纹、Token 用量可信度、结果分级和后续深度调研方向。

## 1. 文档目标

- 固定“模型检测”不是绝对真伪证明，而是当前账号真实网关链路下的模型可信度检测。
- 为后续独立菜单、接口、存储和页面实现提供统一边界。
- 当前已落地检测按供应商协议 profile 支持 GPT / OpenAI-compatible、Anthropic、GLM、DeepSeek 和 Gemini 首批完整模型 ID；后续模型扩展必须先补模型目录、协议专属探针集和评分基线。
- 模型检测入口、历史、报告、筛选、证据摘要和终端日志都必须使用完整模型 ID，不做简称展示。例如 Anthropic 只显示和提交 `claude-opus-4-8`、`claude-opus-4-7`，不显示 `opus-4-8`、`opus-4-7`；GLM 只显示和提交 `glm-5.2`、`glm-5.1`。
- 把后续深度调研拆成可验证问题，避免只靠单个提示词或模型自报身份判断。
- 当前产品默认执行快速检测，用 2 个轻量探针在短时间内给出初步可信度判断；用户显式开启“深度检测”后才执行原有强诊断完整 profile。快速检测优先减少等待和请求数，深度检测继续优先压低误判和漏判概率，相关成本均由发起用户承担。
- 本次 quick/full 落地以本节为准：`profile` 只有 `quick` 和 `full` 两个值，省略时使用 `quick`。`quick` 是默认关闭深度检测开关后的执行路径，`full` 是开启开关后的原有强诊断路径。
- GPT-5.6 检测必须把“模型身份可信度”“显式模型映射”“Token 用量可信度”和“证据充分度”拆开输出，不能用一个总分掩盖不同风险。

### 1.1 Quick / Full 执行契约

| 项目 | `quick` 快速检测 | `full` 深度检测 |
| --- | --- | --- |
| 默认值 | 是 | 否 |
| 请求预算 | 每个参与账户最多 2 个串行请求：基础非流式 + 1 个确定性行为题；每个探针最多 1 次尝试。选择可信对比账户时，目标与对比账户分别执行这一轻量探针集 | 沿用完整强诊断探针集；单个探针最多 3 次尝试，失败重试等待沿用现有退避策略 |
| 检测内容 | 响应模型字段、基础协议可用性、一个轻量行为约束；可选可信对比执行相同轻量探针集；目标基础请求失败或模型字段不符立即结束 | 流式、结构化输出、工具调用、usage、多个行为题、长上下文、三轮稳定性、辅助模型和可选可信对比 |
| 结果上限 | 成功且无硬异常时最高为 `likely`，文案必须标记“初步判断” | 按现有评分规则，可得到 `high_confidence` |
| 可信对比 | 可选；仅运行基础非流式和轻量行为探针，不执行分布相似度、长上下文等深度项目 | 可选；运行完整对比探针与分布相似度项目 |
| 统计影响 | 不写入新的行为观察或用量观察，不把历史最新统计合并进本次报告 | 沿用现有观察写入和最新统计合并规则 |

快速检测不是准确率保证，也不是深度检测的别名；它只回答“当前链路是否大致像目标模型”，适合快速筛查。页面、历史列表、详情和进度事件都必须展示实际 `profile`，避免把初步结论误读成强诊断结论。

## 2. 功能定位

模型检测用于帮助管理员和用户检查当前可用链路是否“像目标模型”：

- 目标模型是否符合当前账户供应商协议 profile 与账户支持模型配置，由发起检测前的本地校验负责；这不是可信度证据。
- 请求目标模型后，上游响应对象是否声明使用同一模型。
- Responses API、流式、结构化输出和工具调用等协议能力是否符合目标模型预期。
- 一组隐藏探针的输出是否接近目标模型的行为基线。
- 上游返回的 usage 是否与受控差分 Token 探针一致，是否存在固定灌水、按比例灌水或分桶取整异常。

黑盒 API 无法在软件层 100% 证明上游物理模型身份。模型 ID、`/v1/models` 返回值、响应体里的 `model` 字段和模型自报身份都可能被上游代理伪造。因此页面和接口统一使用“可信度”“疑似不符”“不确定”等表述，不使用“已证明为真模型”作为结论。

## 3. 用户场景

### 3.1 管理员

- 在管理侧独立菜单 `模型检测` 中检测任意系统账户可管理或可见的 AI 账户。
- 管理侧默认按全部系统账户查看和搜索检测目标、可信对比账户与历史记录；选择具体系统账户后，账户下拉、发起检测、历史筛选和详情读取都收窄到该系统账户作用域。
- 可以筛选系统账户、AI 账户、目标模型和检测等级。
- 可以查看完整诊断摘要，包括 traceId、命中账号、绑定分组、请求接口、响应模型字段、协议能力结果、探针得分和耗时。
- 不能在页面展示上游 API Key、OAuth token、代理密码或完整敏感请求头。

### 3.2 普通用户

- 在用户侧独立菜单 `模型检测` 中检测 `我的 AI 账户` 中的 AI 账户。
- 可以检测被授权给自己的账户，但只获得脱敏检测结论。
- 授权资源检测属于一次真实使用动作，必须按当前用户计入使用记录、额度和授权消耗。
- 用户侧不能看到上游地址、完整响应头、完整请求体、代理信息、凭据或所有者内部诊断。

### 3.3 群成员自行检测

如果对外希望“大家自行检测”，推荐让用户登录本系统后在 `我的 AI 账户` 里选择自己的 AI 账户检测，不推荐跳转第三方检测网站粘贴密钥。

第三方检测网站无法避免 API Key 泄露、请求内容泄露、检测题泄露和结果不可追溯问题。系统内检测可以复用本地权限、审计、用量和脱敏边界。

## 4. 支持范围

当前已落地版本按供应商和协议档案分流检测，不自动复用 GPT 检测探针。首批目标模型必须全部使用完整模型 ID：

| 供应商 | 协议档案 / 检测协议 | 首批目标模型 | 说明 |
| --- | --- | --- | --- |
| GPT / OpenAI-compatible | OpenAI Responses | `gpt-5.6-sol`、`gpt-5.6-terra`、`gpt-5.6-luna`、`gpt-5.5`、`gpt-5.4` | 沿用当前强诊断 Responses profile |
| Anthropic | Anthropic Messages | `claude-opus-4-8`、`claude-opus-4-7` | 不使用 `opus-4-8`、`opus-4-7` 简称；检测 `/v1/messages`、`/v1/messages/count_tokens` 和 `/v1/models` |
| GLM | OpenAI Chat Completions | `glm-5.2`、`glm-5.1` | 通用 GLM API 和 GLM Coding Plan 分别按自己的 `provider_protocol_profile_id` 判断，不混用额度语义 |
| DeepSeek | OpenAI Chat Completions | `deepseek-v4-flash`、`deepseek-v4-pro` | 只检测 DeepSeek 自身 Chat Completions 能力，不复用 GPT Responses 探针 |
| Gemini | Gemini native | `gemini-3.5-flash`、`gemini-3.1-pro-preview` | 检测 `generateContent`、`streamGenerateContent`、`countTokens` 和 `models` |

智谱 GLM 接入模型检测时不自动复用 GPT 检测探针。GLM 模型检测使用 GLM 模型目录、Chat Completions 协议一致性基线、行为探针和评分阈值；GLM Coding Plan 还需要额外标记套餐资源消耗提示。

DeepSeek 第一阶段支持 `profile_deepseek_openai_v1` 的 Chat Completions JSON / SSE，不能复用 GPT Responses 检测探针。DeepSeek 模型检测使用 DeepSeek 模型目录、Chat Completions 响应字段、SSE 一致性、usage 形态、`reasoning_content` 和 cache usage 口径，不发送 `/responses`、FIM、Chat Prefix beta、Anthropic Messages 或 GPT / Codex 专属检测项。默认检测模型使用 `deepseek-v4-flash` 和 `deepseek-v4-pro`，旧别名 `deepseek-chat`、`deepseek-reasoner` 不作为新检测默认项。

Anthropic 模型检测必须使用 Anthropic 原生 Messages 协议，不把 OpenAI Chat / Responses 请求桥接过去后再按 GPT 规则判分。Anthropic 目标模型、辅助模型、可信对比模型和报告模型字段都使用完整 Claude 模型 ID，例如 `claude-opus-4-8`、`claude-opus-4-7`。Claude Code 的 `opus`、`sonnet`、`haiku` 这类客户端配置别名只能作为账号模型目录或计价别名，不进入模型检测目标下拉，也不作为检测报告展示值。

Gemini 模型检测必须使用 Gemini native 协议，不把 OpenAI Chat / Anthropic Messages 桥接响应当成 Gemini 原生检测证据。`models/` 前缀只作为 Gemini API 原生返回形态参与解析；前端目标模型统一展示本地目录里的完整模型 ID，例如 `gemini-3.5-flash`，不在页面混用 `models/gemini-3.5-flash` 和 `gemini-3.5-flash` 两种写法。

检测目标只支持 AI 账户：复用账号测试的单账号命中能力，适合用户自行检查 `我的 AI 账户` 中某个具体上游账号是否可疑。模型检测不提供 API Key 或分组目标，避免用户误以为是在检查某个网关 Key 或分组调度策略。

GPT API Key 账号可以按公开 OpenAI-compatible API 检测；GPT OAuth 账号经过 Codex adapter，能力和公开 OpenAI API 不完全一致，第一版对 OAuth 账号只给出“链路与能力检测”结论，不把缺少公开 API 能力直接等同于模型不真实。

GPT-5.6 预览模型按官方完整 API 模型 ID 注册为 `gpt-5.6-sol`、`gpt-5.6-terra`、`gpt-5.6-luna`。Sol / Terra / Luna 同属 GPT-5.6 系列，协议能力可能高度接近，模型检测不能把“能返回目标模型名”当作真伪证明；必须结合响应 `model` 字段、Responses 对象结构、usage 形态、工具 / 结构化输出、隐藏行为探针、长上下文探针、稳定性和辅助模型对照综合给出可信度。

### 4.1 多供应商检测 profile

多供应商模型检测采用检测 profile 注册表，不再把模型检测写成全局 GPT 常量。每个检测 profile 至少包含：

- `providerCode` 与允许的 `providerProtocolProfileId`。
- 完整目标模型 ID 列表、默认模型和同供应商辅助对照模型。
- 真实探针请求路径和 payload builder。
- JSON / SSE 响应解析器，包括模型字段、可见输出、错误消息、usage、流式终态和工具调用结构。
- 协议能力探针和行为探针评分规则。
- 可信对比账户过滤规则。
- 当前探针版本号。

首批 profile：

| profile | 适用账户 | 主要探针 |
| --- | --- | --- |
| `openai_responses_strong` | `profile_gpt_openai_v1`、`profile_openai_openai_v1` 且账户支持 Responses | `/v1/responses` JSON / SSE、结构化输出、工具调用、usage、行为指纹、长上下文、稳定性、辅助模型对照 |
| `openai_chat_strong` | `profile_deepseek_openai_v1`、`profile_glm_general_openai_v1`、`profile_glm_coding_openai_v1`、`profile_gemini_openai_chat_v1beta` 等 Chat-only 档案 | `/v1/chat/completions` JSON / SSE、JSON 输出、tool calls、usage、行为指纹、长上下文、稳定性、辅助模型对照 |
| `anthropic_messages_strong` | `profile_anthropic_anthropic_v1`、后续明确支持 Messages 的供应商档案 | `/v1/messages` JSON / SSE、`/v1/messages/count_tokens`、tool_use、usage、行为指纹、长上下文、稳定性、辅助模型对照 |
| `gemini_native_strong` | `profile_gemini_native_v1beta` | `generateContent`、`streamGenerateContent`、`countTokens`、function calling、usageMetadata、行为指纹、长上下文、稳定性、辅助模型对照 |

可信对比默认只允许同供应商、同协议 profile、同目标模型的账户。跨供应商或跨协议的对比只能作为后续人工诊断项，不进入当前自动评分，避免把协议差异误判成模型差异。

### 4.2 官方资料校准与可行性结论

截至 2026-06-30 重新核对官方资料和真实兼容上游 smoke 后，当前识别路线可行，但只能定位为“可信度诊断”，不能表述为“物理模型身份已证明”。官方 API 能给出的强证据是：目标协议实际请求成功、响应里的模型字段与完整模型 ID 匹配、可见输出可解析、usage / token 字段形态正确、结构化输出 / 工具调用 / 流式事件符合该协议。`/models` 或等价模型目录只能证明目录可见，不进入当前可信度检测项和自动评分；模型自报身份不作为证据。

| 供应商 / 协议 | 官方资料可支持的检测信号 | 本项目结论 |
| --- | --- | --- |
| OpenAI Responses | Responses API 请求 `model`、`input`、`max_output_tokens`，响应输出 `output_text` / `output`，并支持工具和结构化输出能力 | 可继续作为 GPT / OpenAI-compatible 强诊断主 profile；仍需认为响应 `model` 可被兼容代理伪造 |
| OpenAI Chat-compatible | Chat Completions 响应的 `choices[].message`、`tool_calls`、`usage` 和 `model` 字段 | 适合 GLM、DeepSeek、Gemini OpenAI compatibility 等 Chat-only 账户做中高可信诊断；不复用 Responses 字段 |
| Anthropic Messages | Messages 返回 `content[]`、`model`、`stop_reason`、`usage`，工具调用使用 `tool_use` block | 可行；`claude-opus-4-8`、`claude-opus-4-7` 这类 Opus 4.7+ 检测请求不发送通用 `temperature` / `top_p` / `top_k` 采样字段，避免参数约束导致 400 |
| GLM OpenAI-compatible | Z.AI HTTP / OpenAI SDK 兼容资料展示 `glm-5.2` 通过 `/chat/completions` 请求，返回按 Chat Completions 读取 | 可行；资源不足、无 channel 或套餐限制只判定为不可检测 / 跳过，不判定模型不符 |
| DeepSeek OpenAI-compatible | DeepSeek 官方资料说明可用 OpenAI 兼容格式，并公开 V4-Pro / V4-Flash 通过 Chat Completions 接入 | 可行；检测 `deepseek-v4-flash`、`deepseek-v4-pro` 的 Chat JSON / SSE、usage、tool calls 和行为探针 |
| Gemini native | `generateContent` / `streamGenerateContent` 使用 `models/{model}` 路径，响应包含 `candidates[]`、`usageMetadata`、`modelVersion` | 可行但必须专门处理；短 `maxOutputTokens` 可能被 thinking tokens 挤占导致没有可见输出，因此 native 探针使用更高输出 token 下限，不全局强制 `thinkingBudget=0` |

Gemini 不能按 OpenAI Chat 或 Anthropic Messages 的字段直接判分。原生响应必须优先解析 `candidates[].content.parts[].text`、`modelVersion`、`usageMetadata` 和函数调用结构；如果走 Gemini OpenAI compatibility，则按 `openai_chat_strong` profile 单独判定，不把兼容响应当 Gemini native 证据。

当前最可靠的自动增强项仍是同供应商、同协议 profile、同完整模型 ID 的可信对比账户。跨供应商比较、跨协议桥接比较和 `/models` 目录命中只能辅助排查，不能进入自动高可信结论的核心证据。

本节参考官方资料入口：OpenAI [Responses](https://platform.openai.com/docs/api-reference/responses/create) / [Chat Completions](https://platform.openai.com/docs/api-reference/chat/create)、Anthropic [Messages](https://docs.anthropic.com/en/api/messages) / [prompt validation](https://docs.anthropic.com/en/api/prompt-validation)、DeepSeek [API Docs](https://api-docs.deepseek.com/)、Z.AI [Docs](https://docs.z.ai/)、Gemini [GenerateContent API](https://ai.google.dev/api/generate-content)。

## 5. 检测分层

### 5.1 模型选择与目录边界

模型检测发起前会校验目标模型是否适用于当前账户供应商协议 profile，并确认账户支持模型配置允许该完整模型 ID。该校验属于请求入口约束，不属于模型可信度证据。

注意：本项目当前 `/v1/models`、Anthropic `/v1/models` 和 Gemini `models` 响应都可能由本地模型目录生成，不依赖某个具体上游账号是否可调度。因此模型检测执行器不再调用 `/models` 或等价目录接口作为检测项，也不把本地目录命中或缺失写入报告评分。当前 GPT / OpenAI-compatible 模型检测的上游真实可用性以 `/v1/responses` 实际请求结果为准；DeepSeek / GLM Chat-only 检测以 `/v1/chat/completions` 实际请求结果为准；Anthropic 检测以 `/v1/messages` 实际请求结果为准；Gemini native 检测以 `generateContent` 实际请求结果为准。

限制：

- OpenAI-compatible 代理可以伪造模型列表。
- 本项目本地网关模型列表可能来自本地目录，而不是上游账号实时列表。
- OAuth / Codex adapter 未必支持完整公开 `/models` 语义。

### 5.2 响应对象检测

GPT / OpenAI-compatible 检测调用 `/v1/responses`，固定指定目标模型，检查响应结构。DeepSeek、GLM Chat-only、Anthropic Messages 和 Gemini native 不进入 Responses 检测，而是按各自 profile 使用协议专属响应对象规则。

可验证信号：

- HTTP 状态为成功。
- 响应对象包含 `object = response`。
- `status = completed`。
- 响应体 `model` 与请求目标模型一致。
- 模型字段匹配必须按目标模型本体判断：允许 `gpt-5.6-sol` 或 `gpt-5.6-sol-YYYY-MM-DD` 这类日期快照，不允许把 `gpt-5.6-terra`、`gpt-5.6-luna`、`gpt-5.4-mini`、`gpt-5.4-nano` 等其他模型或变体当成目标模型通过。
- 响应包含可解析 `output_text` 或 `output` 文本。
- 响应包含 `usage`，且 token 字段结构符合预期。

限制：

- `model` 字段同样可被上游伪造。
- 只测一次可能受临时错误、限流、代理和调度切换影响。

### 5.3 协议能力检测

用多类请求检查目标模型能力和当前协议 profile 的兼容形态。`full` 功能按准确率优先设计，不把低成本作为首要目标；`quick` 仅保留基础协议能力和一个确定性行为题。GPT / OpenAI-compatible Responses 检测使用 Responses 能力项；Chat / Anthropic / Gemini profile 使用各自协议能力项，不能把 OpenAI Responses 的 `text.format`、Responses 工具调用或 `output_text` 字段直接套到 Anthropic、GLM、DeepSeek 或 Gemini。

建议第一版能力项：

| 能力项 | 目的 | 结论用途 |
| --- | --- | --- |
| Responses 基础文本 | 确认 `/v1/responses` 可用 | 必选 |
| 流式 SSE | 确认流事件、终态事件和首 token 可观测 | 推荐 |
| 结构化输出 | 确认 JSON schema / strict 输出能力 | 推荐 |
| 函数调用 | 确认工具调用对象结构 | 推荐 |
| 用量字段 | 确认 token 统计字段可解析 | 必选 |

协议能力不用于证明模型身份，只用于识别“明显不像 OpenAI GPT-5 系列公开 API 行为”的链路。

多供应商扩展的协议能力基线：

| profile | 必选能力 | 推荐能力 |
| --- | --- | --- |
| `openai_chat_strong` | Chat Completions JSON、usage、响应模型字段、可见文本 | SSE、tool calls、严格 JSON 输出 |
| `anthropic_messages_strong` | Messages JSON、usage、响应模型字段、可见文本 | Messages SSE、Count Tokens、tool_use |
| `gemini_native_strong` | GenerateContent JSON、usageMetadata、可见文本 | streamGenerateContent、countTokens、function calling |

### 5.4 行为指纹检测

行为指纹通过一组隐藏探针题做概率判断。探针题不在前端展示完整内容，避免被上游针对性适配。

探针原则：

- 不问“你是什么模型”，不依赖模型自报身份。
- 使用低温度、低输出 token、明确输出格式，降低随机性。
- 覆盖中文指令遵循、严格 JSON、短推理、代码理解、拒绝不合理要求、上下文保持和格式稳定。
- 每次从题库中随机抽取一部分，保留探针版本号和随机种子。
- 探针答案不要求逐字一致，优先采用可程序化校验的结构、关键词、约束满足率和错误类型。

行为指纹只能提升或降低可信度，不能单独给出“真实”结论。

### 5.5 强诊断增强检测

在准确率优先且允许较长等待时间时，用户可以显式开启深度检测，执行 `full` 强诊断完整 profile：

- 多轮采样：深度检测的关键协议、稳定性和可信对比探针执行多轮采样，降低偶发网络、限流、随机采样和单次幻觉带来的误判；快速检测仍保持单次轻量请求。
- 探针级延迟重试：仅深度检测使用。单个探针只要本轮网关响应未成功，就在同一个被测账号上最多尝试 3 次，单次请求超时仍沿用 `10s -> 20s -> 30s`；每次重试前必须等待默认 `65s`，不依赖上游状态码或错误类型判断是否进入长退避，若上游返回更长的 `Retry-After` 则按更长时间等待。正常探针不做人为并发限制，避免拖慢大多数不限制并发的上游；失败后再通过分钟级等待保护上游 RPM。仍失败时记为请求失败 / 未计分，只作为链路可检测性证据，不进入模型可信度评分分母、异常计数或“疑似不符”判定。基础链路连续失败时整体结论为 `unavailable`；非基础探针请求失败只降低证据完整度，成功响应后的模型字段、能力和行为判分仍按原规则执行。重试不会切换到同分组其他账号，也不会对“响应成功但行为约束未通过”的判分失败做重试。
- 探针池扩大：完整检测使用强诊断探针集，覆盖中文指令、严格 JSON、函数调用、复杂约束、代码理解、拒答边界、指令优先级、格式稳定和知识 / 能力边界。
- 行为指纹聚合：行为探针不再依赖单题命中，而是按多题成功率、模型字段匹配率和约束满足率聚合评分；行为指纹大面积异常会显著降低可信度。
- 辅助模型对照：同一检测目标在目标模型之外，再请求同供应商、同协议 profile 下另一个完整模型 ID，例如目标为 `gpt-5.6-sol` 时辅助请求 `gpt-5.6-terra`，目标为 `gpt-5.6-luna` 时辅助请求 `gpt-5.6-terra`，目标为 `gpt-5.5` 时辅助请求 `gpt-5.4`，目标为 `claude-opus-4-8` 时辅助请求 `claude-opus-4-7`，目标为 `glm-5.2` 时辅助请求 `glm-5.1`。检测检查两个请求在行为、usage、结构和响应字段上的差异是否符合预期；如果两个模型表现完全同质且长期稳定一致，应降低可信度。当前完整 profile 已内置轻量辅助模型对照项。辅助模型响应字段不符只作为该对照项失败和扣分依据，不直接等同于“当前目标模型字段不符”；只有目标模型自身探针返回的模型字段不匹配，才触发硬性“疑似不符”结论。
- 长上下文探针：完整检测默认加入多窗口 needle-in-haystack，当前固定为 `8k / 20k / 60k` 三档输入 token 目标，用于识别“短上下文走真模型、长上下文切低质模型”的中转伪装。三档 prompt 按项目统一 token 估算器生成到目标长度，并在报告摘要记录窗口 key、目标输入 token 和上游返回的实际 input usage；长上下文聚合项全部通过才视为通过，部分窗口通过时总览最高只能到 `uncertain`，全部失败或明显异常时进入 `suspicious`。
- 可信对比：快速检测和深度检测均可选且默认关闭。用户选择一个自己信任的同供应商、同协议 profile、同目标模型账户后，快速检测对两个账户分别执行基础非流式和轻量行为探针，深度检测执行完整同探针集与分布相似度比较。后端不按账户类型、名称或 base URL 猜测“官网账户”；未选择、不可访问、不可调度、未绑定可用分组或选择了检测目标自身时，请求必须返回中文提示并失败，不能静默降级。
- 分布相似度对照：深度检测开启可信对比时额外执行隐藏分布探针。目标账户和可信对比账户使用同一批隐藏 prompt、多次采样，比较成功率、约束满足率、输出长度、usage 形态和输出文本相似度。快速检测不执行本项。该项只保存 prompt key、统计摘要和少量输出预览，不保存完整题面。分布相似度显著异常时降低可信度；如果目标模型自身字段仍匹配，则不直接覆盖为“响应模型字段不一致”。
- 反适配策略：探针题面、抽样顺序、随机种子和评分权重不在前端暴露；对可公开协议项和隐藏行为项分开计分，避免中转站只适配公开题。
- 置信度输出：报告展示“证据充分度”和“异常一致性”，例如多轮均通过、多轮部分波动、多轮稳定异常。稳定异常比单次失败更能支持“疑似不符”。

### 5.6 探针共享与专属实现策略

随着模型和协议 profile 增加，模型检测按“共享检测意图 + 专属协议适配”维护，避免每接一个模型复制一整套检测代码。

共享层统一收敛这些内容：

- 探针定义：行为题、分布题、长上下文窗口、稳定性题和判分所需的 prompt key。
- 判分器：模型字段严格匹配、JSON / 关键词 / 格式约束、长上下文 marker 命中、稳定性通过率、分布相似度和总览等级封顶规则。
- 报告结构：`itemType`、`status`、`score`、`traceId`、摘要证据、脱敏和保留期。
- 运行约束：固定命中被测账号、同账号重试、禁用会话亲和、不静默切号、按真实网关链路计费和审计。

协议 / 供应商专属层只实现这些差异：

- 请求入口和 payload：OpenAI Responses、OpenAI Chat Completions、Anthropic Messages、Gemini native 的路径、字段和工具调用格式。
- 响应解析：各协议的文本、模型字段、usage、流式终态、工具调用和错误字段。
- 能力基线：某协议不支持或语义不同的能力项必须在 profile 中单独定义，不把 OpenAI Responses 字段套到其他协议。
- 模型清单和辅助对照：同供应商、同协议 profile 的完整模型 ID、默认模型和 paired model。

新增模型时优先复用现有 profile 的共享探针和判分器；只有当协议字段、能力语义、模型基线或上下文窗口目标不同，才新增 profile 专属实现。新增 profile 必须同时补回归，至少覆盖协议 payload / parser、完整 profile、长上下文窗口、模型字段严格匹配、不可用边界和可信对比可用性。

## 6. 结果分级

建议返回稳定枚举和中文展示文案：

| 等级 | 枚举 | 判定口径 |
| --- | --- | --- |
| 高可信 | `high_confidence` | 响应模型字段、核心协议能力、多行为指纹、长上下文、三轮稳定性和可信对比 / 辅助模型对照均符合目标模型预期 |
| 较可信 | `likely` | 关键字段和大多数能力通过，少量非关键探针不稳定；长上下文聚合项必须通过 |
| 不确定 | `uncertain` | 链路可用但证据不足、长上下文仅部分窗口通过，或 OAuth / adapter 能力边界导致不能直接比较 |
| 疑似不符 | `suspicious` | 响应模型字段不匹配、核心能力缺失、行为探针大面积异常或长上下文聚合项失败 |
| 不可检测 | `unavailable` | 账号、绑定分组、代理、权限或上游不可用，未形成有效模型证据 |

准确优先评分维度：

- 响应对象：20 分。
- 协议能力：25 分。
- 行为指纹：35 分。
- 长上下文：15 分。
- 多轮稳定性：15 分。
- 可信对比 / 辅助模型对照：10 分。
- 分布相似度对照：15 分，仅在开启可信对比时加入总分。

最终分值只作为排序和解释辅助，前端主要展示等级、关键证据和风险提示。请求失败、超时、代理不可用或上游不可用的探针不参与该分值计算；报告保留重试次数、状态码、traceId 和错误摘要用于排障，并单独输出“证据完整度”表示本次检测有多少探针形成了有效模型证据。只有成功响应后出现模型字段不匹配、协议结构异常或行为约束未通过，才作为模型可信度异常进入评分与等级判定。

## 7. 接口

管理侧：

- `POST /__aisys__/api/model-checks/run`
- `GET /__aisys__/api/model-checks/runs`
- `GET /__aisys__/api/model-checks/runs/:id`
- `GET /__aisys__/api/model-checks/options`

管理侧接口通过查询参数 `systemAccountId` 指定本次查看或检测的用户作用域。未传 `systemAccountId` 时，管理员按全局管理作用域读取模型检测历史、详情和 AI 账户 options，并可直接选择任意可管理或可见的 AI 账户发起检测；传入具体系统账户时，读写作用域必须收窄到该系统账户，不能落回当前管理员自己的默认作用域。

用户侧：

- `POST /__aisys__/api/my-model-checks/run`
- `GET /__aisys__/api/my-model-checks/runs`
- `GET /__aisys__/api/my-model-checks/runs/:id`
- `GET /__aisys__/api/my-model-checks/options`

运行请求。当前接口接受完整模型 ID，提交后由后端按目标账户 provider profile 校验；示例：

```json
{
  "targetType": "account",
  "targetId": "acc_xxx",
  "model": "claude-opus-4-8",
  "profile": "quick",
  "trustedComparison": false
}
```

`targetType` 是后端检测目标类型字段，当前固定为 `account`，含义就是“检测 AI 账户”。`model` 必须是完整模型 ID，不能提交或展示简称。`profile` 支持 `quick | full`，省略时默认 `quick`；前端把它映射为“深度检测”开关，关闭提交 `quick`，开启提交 `full`，不额外展示档位下拉。页面不支持 API Key 或分组作为检测目标。

`trustedComparison` 默认 `false`，可与 `profile=quick` 或 `profile=full` 一起使用。选择 `trustedComparisonAccountId` 或显式传 `trustedComparison=true` 时，后端必须校验该可信对比账户是否为当前用户有权访问、可调度、已绑定可用分组，且和目标账户属于同供应商、同协议 profile、同目标模型的账户。未选择对比账户时返回“请选择可信对比账户后再开启可信对比检测”，本次检测不创建成功报告；对比账户不能和检测目标相同。快速检测只运行轻量对比探针，深度检测才运行完整对比与分布相似度探针。

`GET /options` 响应应包含可信对比状态摘要：

```json
{
  "trustedComparison": {
    "enabledByDefault": false,
    "available": true,
    "message": "可信对比默认关闭；选择一个同供应商同协议且你信任的可用账户后，会额外消耗该账户额度"
  }
}
```

前端通过账户 options 接口提供可信对比账户下拉，不在页面内猜测哪个账户是“官网账户”。真正发起检测时后端仍要重新校验所选账户可用性。

返回摘要：

```json
{
  "id": "mcr_xxx",
  "targetType": "account",
  "targetId": "acc_xxx",
  "model": "claude-opus-4-8",
  "level": "likely",
  "score": 82,
  "message": "目标模型链路较可信，仍建议结合多次检测结果观察",
  "startedAt": "2026-05-20T10:00:00.000Z",
  "finishedAt": "2026-05-20T10:00:08.000Z",
  "durationMs": 8000,
  "checks": []
}
```

## 8. 存储

模型检测记录属于诊断记录，不属于核心业务配置。当前写入数据集目录库，并只保存有界摘要。

建议表：

- `model_check_runs`
- `model_check_items`

`model_check_runs` 保存检测目标、模型、等级、总分、状态、调用方、系统账户作用域、traceId、开始和结束时间。`model` 字段保存完整模型 ID；前后端类型、路由校验和 repository 查询都按字符串模型 ID 处理，不写死某几个 GPT 模型的固定枚举。

`model_check_items` 保存每个检测项的结果、得分、耗时、错误摘要和脱敏证据。

模型检测历史默认按 `modelCheckRetentionDays = 30` 保留，后台 `data-retention-cleanup` 会批量删除过期的 `model_check_runs` 和对应 `model_check_items`，避免诊断明细在数据集目录库长期增长。

禁止保存：

- 上游 API Key、OAuth token、代理密码。
- 完整敏感请求头。
- 大体积完整响应体。
- 探针题库完整内容。

写入数据集目录库前，检测报告摘要需要同时执行两层脱敏：按字段名屏蔽 `authorization`、`api_key`、`access_token`、`refresh_token`、`password`、`secret`、`rawBody`、`fullResponse` 等敏感字段；按字符串形态识别并替换 `sk-*`、Bearer / Basic 凭据和带密码的代理 URL。顶层 `message`、`errorMessage` 与 JSON 摘要都必须走同一套规则。

如果需要排障，可通过 traceId 跳转使用记录、审计日志和运行日志；审计日志仍按既有保全策略控制。

## 9. 网关与统计边界

- 检测请求必须复用本地网关链路，不能在模型检测服务中另写一套直连上游逻辑。
- 检测 AI 账户时可以复用现有账号测试的单账号候选能力，确保不会静默切到同分组其他账号。
- 检测 AI 账户时必须按真实调用方计入使用记录、额度和授权消耗。
- 模型检测页面自身不做用量统计聚合；检测产生的 token、成本和错误继续进入既有 usage / stats 流程。
- DeepSeek、GLM、Anthropic 和 Gemini 进入各自协议 profile 的模型检测，必须固定命中待检测账户和对应 `provider_protocol_profile_id`，不能因为同分组或同 API Key 有其他供应商账户而切号完成检测。人工单账户测试和后台检查同理必须走账号绑定代理和真实网关链路；账户页面不提供多账户批量测试。
- 检测历史列表只查询检测记录摘要，不扫描使用记录或审计 payload 生成统计。

## 10. 前端页面

页面名称：

- 用户侧：`模型检测`
- 管理侧：`模型检测`

页面区域：

- 检测目标选择：仅 AI 账户。
- 检测目标应优先提供可搜索选择，避免让普通用户手工复制资源 ID；管理侧默认使用全部系统账户作用域，选择具体系统账户后把 `systemAccountId` 传给后续账户 options 和模型检测接口；用户侧调用当前用户作用域接口。
- 目标模型选择：按当前已选 AI 账户的供应商和协议 profile 动态加载；所有选项使用完整模型 ID，例如 `claude-opus-4-8`、`claude-opus-4-7`、`glm-5.2`、`glm-5.1`，不显示简称。
- 深度检测开关：默认关闭。关闭时执行快速检测，开启时执行原有强诊断完整检测；页面不提供第三种档位或 profile 下拉。
- 当前检测进度：快速检测只输出基础响应和轻量行为探针；深度检测输出响应对象、协议能力、行为指纹、长上下文、稳定性、Token / 身份探针和辅助模型对照，开启可信对比时再输出分布相似度对照进度。
- 可信对比账户：快速检测和深度检测均可选；用户自己选择一个同供应商、同协议 profile、同目标模型的可信账户作为对比链路，选择后会额外消耗该账户额度；页面不根据账户类型、名称或 base URL 自动判断。
- 结果总览：可信等级、分数、风险提示、耗时、traceId。
- 证据列表：每项检测的通过 / 告警 / 失败状态和脱敏说明。
- 历史记录：最近检测结果，支持按模型、目标和等级筛选。

运行任务与终端日志：

- 同一登录用户同一时间只允许一个模型检测任务运行；已有任务未结束时再次发起会返回“当前用户已有模型检测正在运行”，用户必须等待完成或手动停止后再开始下一次检测。
- 手动停止通过模型检测停止接口中断当前运行中的检测任务，检测报告状态按 `canceled` 结束；停止不是开始新任务的隐式前置动作，前端不能在用户点击“开始检测”时静默取消旧任务。
- 页面切换、菜单切换和组件卸载不能主动停止运行中的模型检测；同一个浏览器标签页内的前端运行会话应保留当前 SSE 连接并继续追加进度事件，用户回到页面后继续看到同一段终端输出。
- 终端日志只保存在前端 `sessionStorage` 和运行会话中，用于展示本次浏览器会话收到的进度事件；默认过期时间为 12 小时。关闭浏览器会话或超过过期时间后，终端日志可以丢失。
- 浏览器刷新后前端只恢复 `sessionStorage` 中已有的终端内容，不要求后端回放旧进度流；刷新导致旧 SSE 连接断开时，后端检测任务仍继续运行，完成后用户通过历史记录列表查看报告。
- 后端不保存终端逐行日志，也不提供终端日志回放接口。
- 终端内容在检测完成、页面切换、刷新历史或重置表单时不清理；只有用户下一次成功开始新的模型检测时，前端才覆盖上一轮终端内容。
- 检测历史和报告仍以后端 `model_check_runs` / `model_check_items` 为准；终端日志只作为前端实时观测，不作为审计事实源。

所有页面文案、空态、提示和错误说明必须使用中文。

## 11. 风险与限制

- 黑盒模型检测天然只能给出概率判断，不能作为法律、账务或官方认证依据。
- 第三方中转可以专门适配公开探针，因此探针题库不能完全暴露。
- 模型版本会更新，行为基线需要随官方模型变化重新校准。
- 准确优先检测可以覆盖更多长上下文、复杂约束和多轮稳定性，但仍不能对抗所有自适应伪装。
- OAuth / Codex adapter 与 OpenAI API Key 公开 API 行为不同，必须单独标注检测边界。
- 检测会消耗 token 和额度，当前按用户自行承担成本处理；页面仍需明确展示预估成本、检测次数和预计耗时，避免误操作。

## 14. 深度调研结论

调研日期：2026-07-09。

### 14.1 官方信号边界

- OpenAI Models API 的 `listModels` 只承诺列出当前账号可用模型及基础 owner / availability 信息，不适合作为真伪证明。
- 本项目模型检测必须复用本地网关链路，而本地 `/v1/models` 当前由模型目录返回，所以实现时不能把本地模型目录命中解释成“上游账号可见目标模型”。当前检测执行器不再生成模型目录检测项。
- OpenAI RBAC 文档把 `List models` 和 `Model capabilities` 分成不同权限：前者是读取可见模型列表，后者是发起模型请求。模型检测需要同时处理“能列出模型但不能调用”和“能调用但模型列表不可用”的边界。
- Responses API 响应对象包含 `model`、`output`、`usage`、流式事件和工具调用结构，适合做协议一致性检测。它仍然是上游返回的数据，代理可以伪造字段，所以只能作为可信度证据。
- 官方 GPT-5.6 预览资料公开了 `gpt-5.6-sol`、`gpt-5.6-terra`、`gpt-5.6-luna` 三个完整 API 模型 ID，并标注这些模型可通过 OpenAI API 使用。因此第一版 GPT-5.6 / GPT-5.5 / GPT-5.4 可以共用 Responses 协议能力检测集，但行为探针基线和辅助模型对照必须按具体模型 ID 分开版本化。

工程结论：

- 第一版必须至少检查 `/v1/responses` 非流式、Responses 流式、usage 字段、结构化输出和函数调用。
- 模型字段匹配只能加分，不能单独给出“高可信”。
- 响应 `model` 字段如果稳定返回目标模型的 mini / nano / 其他变体，必须作为硬失败证据，整体结论最高只能到 `suspicious`。
- 对 OAuth / Codex adapter 的检测要单独标注“adapter 能力边界”，不能和 GPT API Key 账号直接等价。

### 14.2 开源项目调研

| 项目 | 可借鉴点 | 不直接采用原因 |
| --- | --- | --- |
| OpenAI Evals | eval 任务、样例、评分组织方式成熟，适合参考探针版本化和结果记录 | 框架偏评测平台，直接嵌入会过重 |
| promptfoo | provider、assertion、CI 回归和 deterministic assertion 思路适合轻量探针 | 它是通用测试工具，不负责本项目权限、审计和网关调度 |
| lm-evaluation-harness | 标准 benchmark 组织成熟，可参考任务抽象和多 provider 适配 | 运行时间偏长、依赖偏重，不适合作为本系统运行时依赖；可抽取少量思想到隐藏探针 |
| HELM | 多场景、多指标、透明报告适合参考报告结构 | 面向研究级评测，过重 |
| Veridrop | 与本需求高度相似：给定 `base_url + api_key + model` 后做协议、能力、行为和 usage 检测；OpenAI 检测覆盖基础请求、model 一致性、function calling、structured output、SSE、usage 后端指纹和 token 异常 | 第三方站点仍要求提交 API Key；其 OpenAI 检测主要基于 Chat Completions，而本项目目标模型优先走 Responses API |
| openai_key_checker | 说明社区里已有“检查 key 是否支持某模型”的简单需求 | 只查 `/models` 太弱，不能识别模型替换 |
| LLMmap | 用行为轨迹做低查询量模型指纹，证明“行为指纹”方向可行 | 需要训练模板和目标模型基线；GPT-5.5 / GPT-5.4 闭源模型难以构建强参考分布 |

工程结论：

- 不引入外部 eval 框架作为运行依赖。
- 内部实现一个轻量 `probe runner + deterministic checker`，借鉴 promptfoo 的断言思想。
- 报告结构参考 Veridrop 的“字段级证据”和 quick / standard / full 三档模式，但必须放在本系统权限和脱敏边界里。
- OpenAI 侧不能复刻 Claude thinking signature 这类加密级验证；报告必须明确标注“协议级 / 行为级可信度”。

### 14.3 学术与安全研究结论

- LLM API Audit 调研了分类器、身份提示、模型等价测试、benchmark 和 logprobs 等方法，结论是纯输出文本方法面对细微替换、随机替换或自适应攻击时能力有限；logprobs 更强但通常不可用；可证明完整性需要 TEE 等硬件或服务端机制。
- Model Equality Testing 把黑盒 API 与参考分布的差异检测形式化为双样本检验。这个方法适合有参考分布、可重复采样、可接受统计成本的场景；本项目准确优先模式应借鉴“多探针、多次采样、统计置信度”，但不照搬研究级完整检验。
- Rank-Based Uniformity Test 进一步强调 API 黑盒和缺少 logits 时的困难，并尝试在有限查询预算内做更稳健审计。它仍要求更强的参考条件，不适合第一版工程落地。
- LLMmap 说明“主动行为指纹”可以识别模型，但需要训练或维护目标模型模板；模型快速迭代时基线维护成本高。

工程结论：

- 第一版只承诺“可信度检测”，不承诺“证明真模型”。
- 检测报告必须展示证据来源和限制，不输出法律式确定结论。
- 不做 logprobs、TEE、可验证计算或完整模型指纹分类器；这些放入后续研究项。

### 14.4 外部检测网站结论

存在面向中转站检测的网站和开源项目，例如 Veridrop；也存在只检测 API Key 是否支持某模型的简单 checker。它们对调研有价值，但不建议把用户引导到第三方站点粘贴密钥。

原因：

- OpenAI Help Center 明确提醒不要分享 API Key。
- 第三方检测站点需要 `base_url + api_key + model` 才能跑真实检测，用户必须信任站点不会记录、转卖或滥用密钥。
- 即便开源，也只有自托管部署才能把密钥留在用户控制的网络内。
- 本项目已经具备登录态、账号、分组绑定、审计和脱敏边界，内置检测比外跳网站更安全、可追溯。

工程结论：

- 页面可以写“系统内检测，不需要把密钥交给第三方网站”作为安全价值。
- 不在产品里推荐外部检测站点作为常规入口；可以在文档中作为研究参考。

### 14.5 当前检测 profile

快速检测（`quick`，默认）：

- 按账户供应商协议执行 1 个非流式最小请求，检查真实链路、响应模型字段、可见文本和 usage 形态。
- 再执行 1 个普通协议请求承载的确定性轻量行为探针，不依赖某个供应商可选的 strict JSON 或工具调用能力。
- 每个探针只尝试 1 次，沿用首档 10 秒单次超时；基础请求失败或响应模型字段硬冲突时立即结束，不进入分钟级重试。
- 不执行流式、结构化输出、工具调用、长上下文、三轮稳定性、Token 差分、身份 observation、辅助模型或分布相似度；选择可信对比账户时，仅对对比账户执行相同的基础非流式和轻量行为探针。
- 全部通过最高只能输出 `likely`，结论文案必须说明是快速初筛；模型字段硬冲突仍可输出 `suspicious`，链路失败输出 `unavailable`。

深度检测（`full`，显式开启）：

- 标准检测全部项目。
- 使用强诊断隐藏行为探针集，覆盖严格 JSON、代码理解、复杂约束、拒答边界、指令优先级、格式稳定和中文约束。
- 默认加入更长上下文 needle-in-haystack，并执行三轮稳定性探针。
- 单个网关探针只要未成功，同账号最多尝试 3 次，单次超时按 `10s -> 20s -> 30s` 递进；每次失败后按分钟级间隔重试，`Retry-After` 只用于拉长等待时间，不依赖上游状态码或错误类型选择重试策略。报告记录每次尝试的 traceId、网关 HTTP 状态、上游 HTTP 状态和摘要错误。
- 对 `gpt-5.6-sol`、`gpt-5.6-terra`、`gpt-5.6-luna`、`gpt-5.5` 和 `gpt-5.4` 做辅助模型对照；可信对比默认不开启，只有用户显式选择可信对比账户时，才做同探针集 live 对照和隐藏分布相似度对照。
- 保留原有强诊断完整行为，优先保证判断质量；只有该档位可以输出 `high_confidence`、写入 Token / 身份 observation 或执行可信对比分布相似度项目。

历史“标准检测”仅保留为研究分层，不进入当前 API 和页面。

### 14.6 第一版探针策略

探针题库建议拆成公开规则和隐藏题面：

- 公开规则：会检测协议、结构化输出、函数调用、流式一致性和少量行为指纹。
- 隐藏题面：具体 prompt、期望结构、判分器、权重和随机抽样策略不在前端暴露。
- 探针版本：`probeSetVersion` 写入检测报告，后续模型基线变化时可比较新旧版本。
- 判分方式：优先 deterministic checker，例如 JSON schema、字段存在、事件顺序、正则、关键词、拒答边界、长度范围和数值关系；减少 LLM-as-judge。
- 共享优先：行为题、长上下文窗口、稳定性题、分布题和等级封顶逻辑先沉到共享探针层；协议 profile 只补请求 payload、响应 parser、能力差异和模型清单。
- 长上下文反降级：长上下文不只保留一个固定窗口，应使用 `8k / 20k / 60k` 三档目标输入 token 窗口；低档通过而高档失败时，视为疑似“按上下文长度切换模型”的风险信号，不能输出高可信或较可信结论。

不建议第一版使用的问题：

- “你是什么模型？”：只能作为非核心参考，不作为核心证据。
- 大型公开 benchmark：容易被针对，运行依赖重，不适合作为系统运行时依赖；可抽取少量不可公开的轻量变体。
- 只看速度或价格：延迟和成本受代理、地区、负载、并发和缓存影响，不能证明模型身份。

### 14.7 推荐落地方案

第一版推荐做成内置自托管检测，不推荐把用户引导到第三方网站：

1. 默认入口只检测 AI 账户，也就是用户在 `我的 AI 账户` 中配置或绑定的账户。
2. 后端默认使用 `quick`，前端“深度检测”开关默认关闭；用户显式开启后提交 `full`。快速档对每个参与账户只执行 2 次单轮轻量请求，深度档继续执行强诊断完整探针并在失败后按分钟级间隔重试。
3. 快速档为目标账户生成基础协议、usage 和单题行为检测项；选择可信对比账户时，对比账户生成相同轻量检测项并增加 `trusted_comparison` 汇总项。深度档继续生成 `responses_basic` / `protocol_basic`、流式、结构化输出、工具调用、`usage_shape`、`behavior_probe`、`long_context`、`stability`、Token / 身份和 `cross_model` 检测项，显式选择可信对比账户时再生成完整 `trusted_comparison` 和 `distribution_similarity`。`long_context` 内部由低 / 中 / 高三档子探针聚合，报告只保存窗口 key、目标输入 token、上游 input usage、通过率、摘要输出和 traceId，不保存完整上下文题面。
4. 每个检测项只保存 `status`、`score`、`durationMs`、`evidenceSummary`、`traceId`、`errorCode`、`errorMessage` 和脱敏字段，不保存完整请求体、完整响应体或隐藏题面。
5. `high_confidence` 需要响应对象、协议能力和行为探针都通过；本地模型目录不进入可信度评分。
6. `suspicious` 触发条件应包含硬失败：响应 `model` 明显不匹配、核心 Responses 字段缺失、工具调用结构明显不是 OpenAI 形态、usage 出现异源字段痕迹或隐藏探针大面积失败。
7. `unavailable` 用于权限、额度、账号不可用、代理失败、账户未绑定可用分组、请求超时等未形成模型证据的情况，不能误判成假模型。
8. `high_confidence` 只允许深度检测输出，并必须要求行为指纹、长上下文和三轮稳定性通过；快速检测全部通过最多给到 `likely`。长上下文仅部分通过时最高为 `uncertain`，长上下文聚合失败时进入 `suspicious`。
9. 可信对比是快速和深度检测的显式增强项，默认不开启；快速检测使用轻量同探针集，深度检测使用完整同探针集和分布相似度项目；开启可信对比但未选择可用账户时必须失败并提示，不允许自动降级。
10. 只有深度检测对未成功探针在同一账号上最多尝试 3 次，并保存尝试次数、状态码和 traceId；快速检测每个探针只尝试 1 次，避免分钟级等待。

实现优先级：

1. 后端只保留 `account` 目标和完整 profile，复用网关真实请求链路，打通数据集目录库摘要保存。
2. `account` 目标复用现有账户测试的单账号候选能力，探针重试也固定使用同一个候选账号，防止静默切号。
3. 前端交付一个中文独立菜单，只展示 AI 账户选择、模型、可信对比账户、结果等级、证据列表和历史记录。

## 15. GPT-5.6 模型指纹与 Token 用量可信度增强设计

设计日期：2026-07-13。

### 15.1 当前能力审计结论

当前模型检测已经具备完整网关链路、协议对象、流式、结构化输出、函数调用、通用行为题、长上下文、稳定性、辅助模型对照和可选可信账户对照，但还不能把这些能力等同为完整的模型指纹分类器。

当前明确缺口如下：

- `gpt-5.6-sol`、`gpt-5.6-terra`、`gpt-5.6-luna`、`gpt-5.5` 和 `gpt-5.4` 目前共用大部分通用行为题，缺少按模型版本维护的统计特征基线。
- 当前辅助模型对照能够发现响应字段或通用行为明显不一致，但不能可靠识别“上游把多个模型名稳定映射到同一个模型，同时把响应 `model` 字段伪装正确”的情况。
- 当前 `usage_shape` 只验证 usage 数字字段是否存在和形态是否合法，没有把上游报告 Token 与精确本地 Token 增量比较，因此没有实现 Token padding 检测。
- 当前长上下文固定为 `8k / 20k / 60k`，可以发现一部分短上下文正常、长上下文失败的降级链路，但不足以覆盖 GPT-5.6 公布的大上下文边界。
- 当前没有解析或保存 `system_fingerprint`。后续即使补充，该字段也只能用来观察同一链路的后端版本变化，不能作为物理模型身份证明。
- 生产自然流量很多，但普通用户请求受到提示词、工具、缓存、参数、客户端和路由影响，不能直接作为带标签的模型指纹训练集。

因此当前回答是：项目已经使用“协议探针 + 通用行为指纹”的相似思路，但还没有使用足以识别 GPT-5.6 子版本替换的模型专属统计指纹，也没有使用差分 Token 探针检测灌水。

### 15.2 目标与非目标

本次增强目标：

- 在没有官方直连对照账户时，提高发现 `Sol -> Luna`、`Terra -> Sol`、`5.5 -> 5.4` 等未声明替换的概率。
- 对同一个上游把多个模型名都映射到一个模型的情况，输出“疑似同源 / 疑似模型塌缩”证据。
- 对上游 usage 的固定增加、比例放大和分桶取整异常做可重复、可校准的诊断。
- 保留显式模型映射的透明语义：配置里已经声明的映射是路由事实，不等于欺诈；报告必须同时显示下游请求模型和实际上游模型。
- 让检测结论可解释、可复算、可按探针版本和基线版本回看。

本次不承诺：

- 不承诺仅靠黑盒输出 100% 证明物理模型身份。
- 不使用 TEE、远程证明、logits、官方签名或上游账单对账等当前拿不到的强证明。
- 不把 Pro、Max、Ultra、service tier、思考档位、多智能体、网页搜索或其他账户权益能力当作模型身份指纹。这些能力受套餐、组织权限、客户端和灰度影响，缺失时不能推导模型为假。
- 不把知识截止日期单题当作强证据。模型可能拒答、记错、通过系统提示获得补充知识或被上游注入检索结果；知识时间窗只允许作为低权重统计特征。
- 第一阶段只诊断 Token 用量异常，不自动改写 usage、成本、额度或账单，不因单次异常自动停用账户。

### 15.3 结果维度必须拆分

单一 `score` 不足以表达真实风险。增强后报告至少拆分以下维度：

| 维度 | 推荐字段 | 解决的问题 |
| --- | --- | --- |
| 模型身份可信度 | `identityStatus` / `identityConfidence` | 当前链路行为是否与目标模型群体一致，是否疑似被替换或多个模型塌缩到同一来源 |
| 映射透明度 | `mappingStatus` | 请求模型与配置后的实际上游模型是否一致，是否存在已声明映射或未声明字段冲突 |
| Token 用量可信度 | `usageIntegrityStatus` / `usageIntegrityConfidence` | usage 是否存在固定、比例或分桶灌水迹象 |
| 协议一致性 | `protocolStatus` | 响应对象、流式、工具、结构化输出、usage 字段是否满足协议预期 |
| 证据充分度 | `evidenceStatus` / `evidenceCoverage` | 当前是否有足够独立来源、样本轮次、可比较探针和稳定基线形成判断 |

推荐稳定枚举：

- 模型身份：`consistent`、`suspected_downgrade`、`suspected_same_source`、`population_outlier`、`insufficient_evidence`。
- 映射透明度：`direct`、`configured_mapping`、`undeclared_mismatch`、`unknown`。
- Token 用量：`consistent`、`warning`、`suspected_padding`、`unsupported`、`insufficient_evidence`。
- 证据充分度：`stable`、`candidate`、`bootstrap`、`insufficient`。

现有总览等级可以保留用于列表排序，但详情页必须展示上述分项，且 `usageIntegrityStatus` 不得直接改写 `identityStatus`。

当前运行闭环在模型检测报告 `resultSummary.trustReport` 中输出五个分项，并由中文详情页展示。只有深度检测执行和写入模型指纹 / Token observation；快速检测不写 observation，也不把历史预聚合结果合并成当前快速报告证据。输入 Token 差分使用锁定的 `js-tiktoken@1.0.21:o200k_base`，每次深度检测执行 P0 / P1 / P2 三轮受控探针。身份侧使用 `identity-features-v2-seven-categories`，把约束、代码、推理、错误恢复、多语言、工具 schema 和知识时间窗分别写入确定性有界维度，第八维只保存归一化输出规模；题面和回答正文不落 observation。observation 经 dataset-writer 投递 ingest-worker，stats-worker 按 `(created_at, id)` 游标增量刷新 Token 窗口、固定 intercept cohort 版本、按独立上游桶塌缩的身份特征、LOO median / MAD / 分位基线、paired 距离和账号 latest。深度检测详情 API 只合并 latest，不扫描 observation。

### 15.4 显式映射与未声明替换

检测执行顺序仍然是先解析账号模型映射，再固定命中当前账号请求实际上游模型。报告必须同时保存：

- `requestedModel`：用户发起检测的下游模型。
- `mappedUpstreamModel`：账号模型映射解析后的实际上游模型。
- `observedModel`：响应对象声明的模型。
- `mappingApplied` 和脱敏后的 `mappingRuleId`。

命中显式映射后，响应 `model` 匹配 `requestedModel` 或 `mappedUpstreamModel` 都视为协议层合法。部分兼容上游接受私有映射目标，但响应仍回显公开请求模型名；这不能单独构成未声明替换。响应为二者之外的第三个模型时仍是 `undeclared_mismatch`，身份 cohort 继续按映射目标评估。

典型判定：

| 场景 | 映射结论 | 身份结论 |
| --- | --- | --- |
| 请求 Sol，配置明确映射到 Luna，响应 Luna | `configured_mapping` | 对 Luna 做身份检测；页面明确说明本次并未实际调用 Sol |
| 请求 Sol，配置明确映射到私有 Luna 别名，响应仍回显 Sol | `configured_mapping` | 视为兼容上游回显公开请求名，仍按映射目标 cohort 检测 |
| 请求 Sol，无配置映射，响应 Luna | `undeclared_mismatch` | 硬冲突，最高只能为疑似降级 |
| 请求 5.5，配置明确映射到 5.4，响应 5.4 | `configured_mapping` | 对 5.4 做身份检测，不把它描述成 5.5 真模型 |
| 请求 Sol，响应字段仍写 Sol，但行为长期贴近 Luna | `direct` | 统计层输出 `suspected_downgrade`，不能声称已证明是 Luna |
| 请求 Sol / Terra / Luna，响应字段各自正确，但三者跨模型特征异常同质 | `direct` | 输出 `suspected_same_source` |

### 15.5 可比较队列与干扰变量

只有相同 cohort 的样本才允许进入同一基线。建议 cohort key 至少包含：

```text
provider_code
+ provider_protocol_profile_id
+ endpoint_mode
+ credential_type
+ mapped_upstream_model
+ probe_set_version
+ probe_family
```

其中：

- OpenAI API Key / OpenAI-compatible Responses 作为 GPT-5.6 模型指纹的首个高可比 cohort。
- OpenAI OAuth / Codex adapter、Chat bridge、Anthropic bridge 和其他跨协议转换必须进入独立 cohort；证据不足时只输出协议 / 链路结果，不与 API Key cohort 强行比较。
- `service_tier`、reasoning 档位、客户端画像、地区、代理、缓存状态和请求参数作为干扰变量记录；它们可以用于分层或排除样本，但不能成为身份判据。
- 自定义上游地址按规范化 origin 生成 HMAC 上游桶 ID。明文 Base URL 不进入基线表或前端报告。
- 同一上游桶下即使有很多账号，也必须限制总体权重，避免单个供应商通过大量账号控制群体基线。

### 15.6 GPT-5.6 指纹探针体系

指纹探针拆为四层，按证据强度分别计分。

#### 15.6.1 硬协议与边界探针

- 请求 / 响应协议、模型字段、usage、流式终态、结构化输出和工具调用继续作为基础层。
- 长上下文使用模型目录 `max_input_tokens` 动态阶梯：大上下文模型通常得到低档 `8k`、中档 `60k`、高档约 `25% max_input_tokens`；较小模型会按比例收缩并保持低 / 中 / 高递增。不再执行接近模型输入上限的极限档，避免单次检测成本和运行时间过高。
- 每个窗口使用多个随机 marker，检查开头、中部、尾部和干扰区，避免上游只保留首尾文本也能通过。

硬协议层能发现明显模型名替换、上下文截断和协议伪装，但三种 GPT-5.6 子版本公开硬能力接近，不能只靠这一层区分 Sol、Terra、Luna。

#### 15.6.2 模型专属统计探针

为每个目标模型维护版本化的隐藏 probe catalog，题面不进入前端：

- 多约束满足：嵌套格式、禁止词、字符预算、跨段一致性和冲突指令消解。
- 代码变换：小范围补丁、错误定位、测试推断、严格保持无关代码不变。
- 复杂推理：可程序化判分的组合逻辑、反事实、排序和边界条件，不使用公开 benchmark 原题。
- 错误恢复：给出带诱导错误的中间结论，检测模型是否盲从或主动校正。
- 多语言稳定性：同一语义用中文和英文变体表达，比较约束满足和答案一致性。
- 工具与 schema：复杂参数嵌套、必填 / 枚举 / 互斥字段和工具选择稳定性。
- 生成式 canary：题面由固定模板、运行时种子和随机数据生成，降低上游对公开固定题的适配价值。
- 知识时间窗：仅使用不可调用工具、不可联网的封闭题，并作为低权重特征；单题失败或成功都不能触发身份结论。

每个探针保存 deterministic feature，而不是只保存 pass / fail，例如约束满足位图、错误类型、输出 Token、结构深度、修复覆盖率和多轮方差。只有这些结构化特征才能形成可校准指纹。

#### 15.6.3 同账号跨模型塌缩检测

对同一账号按随机顺序请求目标模型和 paired model：

- Sol 与 Terra、Luna 与 Terra、5.5 与 5.4 继续作为第一批配对；后续可增加 Sol 与 Luna 的三角对照。
- 同一批生成式 canary 必须共享语义和判分器，但加入不同 nonce，避免响应缓存直接制造文本一致。
- 比较的不是逐字文本，而是约束满足向量、错误类别、代码补丁结构、工具选择、输出长度分布、Token 斜率和多轮方差。
- 单次相似不算异常；只有跨多题、多轮、多个时间窗口持续比群体内正常配对更同质，才输出 `suspected_same_source`。
- 响应成功但探针行为失败不重试；网络、限流和不可用样本退出模型评分分母。

#### 15.6.4 后端版本变化辅助信号

如果上游返回 `system_fingerprint`，本地只保存 HMAC 后的稳定摘要，并记录它与模型、上游桶、时间窗口的共同变化：

- 同一账号指纹变化可以解释行为基线突然漂移，触发重新收集而不是立即判假。
- 多个模型长期返回完全相同指纹只能作为“可能共享后端”的弱证据。
- 字段缺失、可伪造或相同都不能单独证明模型替换。

### 15.7 无官方对照账户时的群体基线

没有官方直连账户时，不训练“真 / 假”二分类器，而是维护抗污染的群体分布并输出偏离程度。

基线只允许使用本系统主动发起的受控探针事实，禁止直接读取普通用户请求正文或任意自然流量输出作为训练样本。自然流量仅用于发现哪些模型值得优先安排探针，不进入身份标签。

基线构建规则：

1. `ingest-worker` 把有界探针 observation 写入数据集目录库，不在模型检测 API 请求里同步聚合。
2. `stats-worker` 按游标增量读取 observation，按 cohort、模型、探针版本、probe key 和时间窗写入统计结果库。
3. 每个上游桶对同一窗口的贡献设上限；同一上游的多个账号不能被当作多个独立来源。
4. 候选账号评分使用 leave-one-upstream-out 基线，不能把自己的数据计入对照分布。
5. 有模型字段硬冲突、协议硬冲突或明显 usage 灌水的样本不进入稳定身份基线。
6. 使用 median、MAD、分位数、截尾均值和 bootstrap 置信区间，避免均值被少量极端样本拉偏。
7. 模型快照、probe set 或 `system_fingerprint` 群体性变化时创建新 baseline version，不把旧分布直接覆盖。

群体基线只能发现“相对于当前独立来源群体的异常”。如果多数独立上游桶都把同一个低版本伪装成目标模型，群体基线也可能把错误分布当成正常；没有官方对照、硬件证明或可靠账单侧证据时，系统不能消除这一盲区。第一版更可靠的是发现跨模型塌缩和离群，不应在基线尚未证明模型间可分时点名“实际就是 Luna / 5.4”。

第一版建议门槛是校准前默认值，不是最终产品承诺：

| 基线阶段 | 独立上游桶 | 有效配对 observation | 时间跨度 | 可输出结论 |
| --- | ---: | ---: | ---: | --- |
| 不足 | `< 3` | `< 30` | 任意 | 只能输出 `insufficient_evidence` |
| 启动 | `>= 3` | `>= 30` | `>= 3` 天 | 只展示偏离趋势，不下疑似替换结论 |
| 候选 | `>= 5` | `>= 100` | `>= 7` 天 | 可输出低置信 warning |
| 稳定 | `>= 10` | `>= 300` | `>= 14` 天 | 可输出经过重复确认的统计异常 |

如果样本长期达不到门槛，系统必须诚实显示证据不足，不能为了页面有结论而降低独立来源要求。

### 15.8 Token 灌水的差分探针

单次比较“上游 usage - 本地估算”不可靠，因为服务端消息模板、工具 schema、隐藏 reasoning、多模态和 tokenizer 版本都可能引入正常差异。第一版使用同链路差分实验消除固定开销。

#### 15.8.1 输入 Token 差分

为同一个账号、模型和请求形态构造三组请求：

```text
P0 = 固定基础请求 + 随机 nonce
P1 = P0 语义等价结构 + 精确 512-token 填充块
P2 = P0 语义等价结构 + 精确 2048-token 填充块
```

实现要求：

- 填充块必须由项目选定并版本锁定的精确 tokenizer 生成与复核，不能使用当前 ASCII `/4`、CJK `/1` 的粗略估算器。
- 当前 P2 的 2048 Token 是填充硬上限；填充使用线性构造并在有界单 worker 任务池中完成，服务主事件循环不执行随目标长度增长的同步 tokenizer 循环。
- 三组请求不使用图片、音频、文件、工具、`previous_response_id` 或外部检索；输出要求保持短且固定。
- 每轮随机打乱 P0 / P1 / P2 顺序并更换 nonce，至少执行 3 轮；上游失败样本不进入回归。
- 记录总 input tokens 和 cached tokens。缓存命中不改变总 input tokens 的语义，但如果某个兼容上游只返回“未缓存输入”，该差异会在协议检查中单独标记。
- 对每轮计算 `deltaReported = reported(Pn) - reported(P0)`、`deltaLocal = local(Pn) - local(P0)` 和 `ratio = deltaReported / deltaLocal`。
- 多轮拟合 `reported = intercept + slope * local`。`slope` 持续大于 1 更像比例灌水；候选账号 `intercept` 显著高于同 cohort 更像固定灌水。

#### 15.8.2 输出 Token 差分

输出 Token 只有在“可见输出可精确复算”且“usage 能区分隐藏 reasoning”时才允许形成结论：

- 使用严格 JSON / 固定字符串长度探针，分别要求两个可程序化验证的输出长度。
- 如果 usage 明确给出 reasoning tokens，则从总输出中分离后比较可见输出增量。
- 如果模型可能产生隐藏 reasoning 但上游不提供 breakdown，输出灌水状态必须为 `unsupported` 或 `insufficient_evidence`，不能把隐藏 reasoning 误判成灌水。
- 不依赖 Pro / Max 才开放的思考档位，也不把是否能关闭 reasoning 作为模型身份或 Token 诚信证据。

#### 15.8.3 异常模式和初始阈值

第一版识别三类模式：

- 比例灌水：多轮 `slope` 稳定高于 1。
- 固定灌水：`slope` 接近 1，但 leave-one-upstream-out cohort 中的 `intercept` 持续异常。
- 分桶 / 取整灌水：reported usage 大量落在固定倍数，且增量呈阶梯跳变。

校准前建议阈值：

- `abs(slope - 1) <= 3%`：不形成灌水异常，但仍展示置信区间。
- `3% < abs(slope - 1) <= 5%`：warning，需要更多轮次。
- `abs(slope - 1) > 5%` 且至少 3 个独立轮次、置信区间不跨 1：可进入 `suspected_padding` 候选。
- 固定 intercept 不使用全局常数阈值，必须和同 cohort、同 endpoint、同 tokenizer version 的群体基线比较。

这些阈值必须通过诚实 mock、5% / 10% 比例灌水、固定增加、分桶取整和真实兼容上游样本校准后才能转为产品阈值。页面不能在校准前宣称“可稳定检测 5% 灌水”。

### 15.9 数据结构与 worker 边界

受控探针需要追加 observation 事实，而不是在 API 内扫描检测历史或 usage 明细临时聚合。

建议新增数据集事实 `model_check_observations`，每行保存有界字段：

- 归属：`run_id`、`check_item_id`、`account_id`、`upstream_bucket_hmac`、`system_account_id`。
- cohort：`provider_code`、`protocol_profile_id`、`endpoint_mode`、`credential_type`。
- 模型：`requested_model`、`mapped_upstream_model`、`observed_model`、`mapping_applied`。
- 探针：`probe_set_version`、`probe_key_hmac`、`probe_family`、`round_index`、`randomization_group`。
- 结构化特征：有界 `feature_summary_json`、`deterministic_score`、`status`、`duration_ms`。
- Token 事实：`tokenizer_version`、`local_input_tokens`、`local_visible_output_tokens`、上游归一化 usage、delta、ratio。
- 辅助信号：HMAC 后的 `system_fingerprint`、traceId、时间戳和脱敏错误码。

不得保存完整隐藏题面、完整响应、明文 Base URL、凭据、Authorization、用户自然流量正文或无上限 payload。

统计结果库建议新增：

- `model_fingerprint_baseline_windows`：按 cohort / model / probe version / probe key / 时间窗保存来源桶数、样本数、中位数、MAD、分位数和 baseline version。
- `model_pair_similarity_windows`：保存模型配对的正常相似度区间和塌缩阈值。
- `model_usage_integrity_windows`：保存 Token slope、intercept、置信区间、轮次数和异常模式。
- `model_account_trust_results`：保存账号最新四维结论、基线版本、证据覆盖度、原因码和刷新时间，供 API 直接读取。

所有窗口由 `stats-worker` 按已确认游标增量构建；API、repository 查询和前端页面只读最新预聚合结果，禁止实时扫描 observation、模型检测明细、审计日志或 usage shard 聚合。

当前实现表为：dataset 的 `model_check_observations`；stats 的 `model_token_integrity_windows`、`model_token_integrity_rounds`、`model_token_intercept_baseline_versions`、`model_trust_window_sources`、`model_identity_source_features`、`model_identity_baseline_versions`、`model_paired_similarity_windows` 和 `model_account_trust_results`。observation 不含 prompt、响应正文、Base URL 或普通用户流量正文，只含 HMAC 桶、模型映射事实、Token 数值、8 维有界特征、轮次、版本和状态。只有请求成功、存在 `observed_model` 且 observation 状态为 `observed` 的样本可进入身份窗口；Token 窗口还必须存在有效 reported input usage。`undeclared_mismatch`、`protocol_status = failed` 等硬冲突 observation 继续保存在 dataset，并可刷新 latest 的映射 / 协议诊断事实，但不得进入 Token source / window、身份 source / baseline、独立来源数或证据覆盖率。`model_token_integrity_rounds` 按 run 和 round 保存 P0 / P1 / P2 有效掩码，三档齐全才增加完整轮次。`request_failed`、`model_missing` 和 `usage_missing` 只保留事实，不增加来源数、有效样本、轮次、时间跨度、覆盖率或 bootstrap / candidate / stable 阶段。

身份来源向量按同一来源、模型和 probe 的 `sum_feature_n / sample_count` 累计均值聚合，再按 HMAC 上游桶合并同源账号；约束维度以 `constraint_pass_count / sample_count` 通过率为准，`latest_feature_n` 只保留最近事实，不能替代累计来源签名。候选账号继续使用 leave-one-upstream-out，MAD 极端样本退出稳定分布。群体共同漂移创建 `drift_protected` 候选并暂停强结论；候选状态只依据 observation 时间推进：群体回到 active 分布时记为 `recovered`，验证窗内继续失稳时记为 `rejected`，证据不足且超过 7 天时记为 `expired`，只有至少连续 3 天稳定且证据充分才切换为 active。`recovered`、`rejected`、`expired` 都是历史候选状态，不再优先于当前 active 基线。

固定 intercept 由 stats-worker 按 cohort / model / tokenizer / probe set 聚合到 `model_token_intercept_baseline_versions`。每个上游桶先折叠为一个 intercept 中位数，再生成 `calibration_pending` 版本；账号 latest 使用排除自身上游桶后的 LOO median / MAD。待校准版本的 `strong_gate_enabled` 固定为 `0`，无论 mock 偏离多大都不能输出固定灌水强结论。只有独立来源和时间跨度达到 stable、人工记录真实样本阈值与校准说明后，离线校准入口才能把版本切为 `active` 并开启强判；API 与前端只读取 `model_account_trust_results` 中的预聚合结果和版本状态。

`model_trust_window_sources` 的 cohort 独立来源计数固定使用 `idx_model_trust_window_sources_cohort(cohort_key_hmac, upstream_bucket_hmac)`；等值筛选列必须作为前导列，来源桶列用于覆盖 `COUNT(DISTINCT upstream_bucket_hmac)`，SQLite 当前 schema 与生成的 PostgreSQL schema 必须保持一致。

### 15.10 判定优先级

判定顺序固定为：

1. 请求是否成功形成可判分响应；失败、限流、权限和代理问题优先落 `unavailable` / 证据不足。
   全部请求失败或没有任何 response model 时，身份必须为 `insufficient_evidence`、映射为 `unknown`、协议为 `insufficient_evidence`，且当前不可用报告不得被历史 latest 统计覆盖。
2. 是否存在未声明模型字段冲突、协议硬冲突或上下文硬失败。
3. 是否存在显式模型映射；有映射时按实际上游模型评估，并单独展示映射透明度。
4. 当前 cohort 是否有足够稳定基线。
5. 模型专属特征是否持续偏离目标模型且更接近 paired model。
6. 同账号跨模型是否出现超过群体正常范围的长期同质化。
7. Token 差分是否形成可重复异常。

硬冲突可以直接封顶；统计异常必须经过多探针、多轮和时间窗口确认。模型刚升级、群体指纹共同漂移或 baseline version 变化时，先降为 `candidate` / `insufficient_evidence`，不能批量把全部账号判成假模型。

### 15.11 安全、抗适配与误判控制

- 题库只公开探针类别，不公开完整题面、随机种子、权重和阈值组合。
- probe key、上游桶和 `system_fingerprint` 使用服务端 HMAC；前端只看稳定摘要和中文原因。
- 生成式 canary、题面变体、随机顺序和轮换版本降低中转站针对固定题适配的收益。
- 每个上游桶限权、候选 leave-one-out、异常样本退出稳定基线，降低基线投毒风险。
- 对照样本必须匹配 cohort；OAuth / Codex、API Key、跨协议 bridge 不混算。
- 网络失败、限流、无额度、权限不足、模型暂不可用只降低证据覆盖度，不进入“假模型”分母。
- 速度、价格、输出文风和单次知识题不能触发硬结论。
- Token 诚信诊断与实际计费分离；第一阶段只告警和留证，不自动扣回费用或修改账单。

### 15.12 验证矩阵

实现前必须先恢复现有模型检测全链路回归。当前共享 mock fixture 创建账号时传入 `active`，但账户创建规则会把非 disabled 新账号统一置为 `pending_test`，导致多个回归在真正执行探针前因无可调度账号失败。该问题属于 Phase 0 门禁，不能在回归失效的基础上继续叠加指纹实现。

后续至少覆盖：

| 场景 | 预期 |
| --- | --- |
| Sol 无映射、响应 Luna | `undeclared_mismatch` + 身份硬冲突 |
| Sol 显式映射 Luna、响应 Luna | `configured_mapping`，按 Luna 评估，不报隐藏替换 |
| 5.5 显式映射 5.4 | 页面明确实际上游模型，不描述成 5.5 真模型 |
| Sol / Terra / Luna 全部由同一 mock 行为返回 | 多轮跨模型塌缩检测命中 |
| 三个模型有可控但相近的正常分布 | 不因单题相似误报同源 |
| 诚实 usage，存在固定协议开销 | Token slope 接近 1，不误报固定开销 |
| input usage 按 1.05 / 1.10 放大 | 5% 进入校准边界，10% 稳定命中比例灌水 |
| 每次固定增加 20 tokens | cohort intercept 异常命中 |
| usage 向 64 的倍数取整 | 分桶 / 阶梯异常命中 |
| usage 缺失或输出 reasoning 无 breakdown | `unsupported` / 证据不足，不判灌水 |
| 单个上游创建大量账号 | 上游桶限权，不能控制群体基线 |
| 模型群体同时升级漂移 | 新建 baseline version，暂停强结论 |
| OAuth / Codex 与 API Key 样本混入 | cohort 门禁拒绝混算 |

### 15.13 分阶段落地顺序

1. Phase 0：修复并恢复现有模型检测回归，冻结当前行为基线。
2. Phase 1：扩展报告契约，拆出身份、映射、usage 诚信和证据充分度；补 `system_fingerprint` 辅助采集。
3. Phase 2：引入版本锁定的精确 tokenizer 和输入 Token 差分探针，先用 mock 完成灌水校准。
4. Phase 3：建设 GPT-5.6 版本化 probe catalog、生成式 canary 和跨模型塌缩 observation。
5. Phase 4：通过 ingest / stats worker 建立独立上游桶群体基线、配对窗口和账号最新可信结果。
6. Phase 5：前端展示四维结论、证据覆盖度、映射事实、异常原因和校准边界。
7. Phase 6：在测试环境和生产只读 / 小流量探针中校准阈值，确认误报率后再开放强诊断结论。
