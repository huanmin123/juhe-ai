# 时间计划闸门与账户状态解耦设计

> 状态：已实施（2026-11-03，schema revision 15；gateway + jobs + 前端同批）。
> 裁决来源：2026-11-03 用户裁决方案 A——「人工停用持久，时间计划只维护闸门」。账户与 API Key 在时段外仍然是正常状态，只是被时间计划限制，不表现为停用。

## 1. 问题

当前时间计划与可用状态共用同一列 `status`：

- 账户：`jobs` 的 `account-availability-schedule-status-sync` 在窗口开始写 `accounts.status='active'`、窗口结束写 `'disabled'`（`backend-go/projects/jobs/internal/oauthrefresh/availability.go`）。
- API Key：`api-key-availability-schedule-status-sync` 同样直接写 `api_keys.status`。

后果：

1. 时段外的账户在管理页显示「账户停用，当前不可用」，与真正的人工停用无法区分。
2. 时段外的 API Key 在客户端返回 401「API Key 无效」，把「当前不在可用时段」表达成「密钥无效」，误导排查。
3. 导出、公开 API、统计桶、筛选条件全部按停用计。
4. 计划边界会覆盖人工停用（下一个窗口开始自动启用），用户无法通过人工停用持久关闭账户。

## 2. 目标与非目标

### 2.1 目标

- `status` 只表达账户/Key 自身的管理与健康事实，**时间计划不再写 `status`**。
- 新增独立派生列表达「此刻是否落在允许时段内」，作为调度准入的第二个门。
- 时段外表现为「正常状态 + 非时间段」，属于正常状态的子集，不进入停用统计与停用筛选。
- 人工停用持久生效，不再被计划边界自动复活。
- 时段外的 API Key 返回可区分的提示，不再报「API Key 无效」。

### 2.2 非目标

- 不改时间计划的配置模型（`availability_schedule_json`、窗口、例外、时区、跨天语义全部不变）。
- ~~不改计划的边界计算与补偿逻辑（T91-7 的 Key 补偿、账户边界事件语义保持）~~——**实施期修正**：闸门改为每轮按当前时刻重算并与现值比较，错过边界由下一轮天然纠正，T91-7 的事件键补偿分支与 `catchUpScheduleEvent` 随之退役；`schedule.go` 的 `DueScheduleEvent` / `CatchUpScheduleEvent` 公共函数保留但同步路径不再使用。
- 不引入账户级「计划停用」新状态词。
- 不改授权实例的计划来源语义（授权实例不复制来源计划，继续按来源账户判定）。

## 3. 数据模型

### 3.1 新增列

`accounts` 与 `api_keys` 各新增一列：

```
availability_schedule_gate integer NULL
```

取值与语义：

| 值 | 语义 |
| --- | --- |
| `NULL` | 未配置时间计划（或计划已清除），闸门恒开 |
| `1` | 当前落在允许时段内 |
| `0` | 当前不在允许时段内 |

约束：不设 CHECK（三态由写侧保证），不设默认值（存量行保持 `NULL`，等价于现状「无计划」）。

### 3.2 与既有列的关系

- `availability_schedule_json`：计划文档，不变。
- `availability_schedule_next_check_at`：下次边界检查时间，不变。
- `availability_schedule_gate`：由计划同步任务与各写入口维护的**派生事实**，不参与乐观锁 revision。
- `status`：不再被计划写入。

### 3.3 事件表

`account_schedule_status_events` / `api_key_schedule_status_events` 保留，语义从「status 变更事件」修改为「闸门翻转审计」；`status` 列继续存 `active` / `disabled`，读作闸门开/关。**事件不再承担去重职责**：是否写闸门由「目标值与现值比较」决定，事件插入为 `ON CONFLICT DO NOTHING` 的审计写；事件键改为 `id:active:<UTC 分钟>` / `id:disabled:<UTC 分钟>`，与历史边界键（`dateKey:minute:action:windows`）不冲突。

### 3.4 升级

- `contracts.SchemaRevision` 由 14 提到 15（纯 DDL 空号，不写 `schema_migrations`，沿用 revision 14 的加法列先例）。
- DDL 加法相在 `maintenance` 的 `--ensure-schema` 与 `upgrade` 的加法相自动补列（`ALTER TABLE ... ADD COLUMN IF NOT EXISTS`）。
- 存量「计划造成的 disabled」不设独立数据步骤，改由同步任务内建自愈（见 §7）。

## 4. 写入语义

### 4.1 计划同步（jobs）

`SyncAccountScheduleStatuses` / `SyncApiKeyScheduleStatuses`：

- 不再写 `status`，改写 `availability_schedule_gate` 与 `availability_schedule_next_check_at`。
- 闸门与 `status` 正交：**任何 `status` 的行都维护闸门**（不再有「仅 active/disabled 可变」与「质量处罚 disable 跳过」守卫——闸门不改 `status`，这些守卫已无意义）。
- 只在「目标值与行内现值不同」时写入；相同时只推进 `availability_schedule_next_check_at`。
- 计划文档解析失败按 fail-closed 关闸（`gate=0`），但**不改 `status`**；同时把 `next_check_at` 写到 1 小时后而不是 NULL/空串——候选条件含 `IS NULL OR <= now`，写 NULL 会让坏行永久 due 并占满批次。PATCH 修正计划会立即重算，不必等重试。Key 侧旧计划非法时列表/详情降级为“无计划”，PATCH 允许直接清空或替换，不得因旧值不可解析而拒绝修复。
- Key：小时额度窗口绑定重建跟随**闸门打开**（`gate` 由 0/NULL 变 1），不再跟随 status 翻转。
- 激活副作用（`ActivationHook` / `APIKeyActivationHook`）的触发条件改为「闸门由关到开」。
  - 账户 dispatch revision 家族推进继续 best-effort。
  - Key 小时额度窗口绑定重建继续强一致（失败回滚整笔同步）。

### 4.2 账户创建与编辑（gateway）

- 创建：写入计划时按当前时间计算 `gate`；无计划写 `NULL`。`status` 只按用户选择与健康状态机派生，不再被计划覆盖。
- PATCH：计划变化时重算 `gate`；`status` 不再因计划变化被覆盖。
- 批量编辑、克隆、导入、公开 API：同口径——计划入参重算 `gate`，`status` 不因计划改写。
- 「恢复正常」（`ForceActivatePending`）：`status` 由人工确认决定，`gate` 保持计划事实。时段外恢复为 `active` 后依然 `gate=0`，展示「正常 · 非时间段」，不参与调度。
- API Key 创建与 PATCH：同口径，`status` 只由用户启停决定。

### 4.3 账户投影激活臂（jobs accounthealth）

`activationPlanForProjection` 的 `activation_success` / `cooldown_success` 分支：

- `status` 恒为 `active`（健康事实恢复），不再因计划落 `disabled`。
- 同事务写入计划的当前 `gate` 与 `next_check_at`。
- `restoresDispatch` 改为按 `status == active && gate != 0` 判定（`gate NULL` 视为开）。

## 5. 读取语义

### 5.1 调度准入

网关账户候选 SQL（`chain_accounts.go` 的 `chainCandidateWhere`）：

```
AND accounts.status IN ({statusSet})
AND accounts.schedulable = 1
AND (accounts.availability_schedule_gate IS NULL OR accounts.availability_schedule_gate = 1)
```

授权实例来源账户臂同样追加 gate 条件。

媒体准入臂（`video_create`）同样追加 gate 条件。

#### 跨进程可见性（jobs → gateway）

闸门由 jobs 同步任务写入，不能只等 gateway `runtimeCache` 的 60 秒 TTL 过期（最坏情况下旧 gate 仍可派发一分钟）。写入方在 PG 事务提交后按变更 ID bump 共享状态序号：

- 账户：`juhe-ai:{<namespace>:oauth}:version:state:account:<account_id>`；
- API Key：`juhe-ai:{<namespace>:oauth}:version:state:apikey:<api_key_id>`。

`gatewayruntimecache` 每次命中 runtime 缓存时以一次 MGET 读取凭据版本与本次派发涉及的账户/API Key 序号；任一变化即重载 PG 快照，gate 过滤仍由上述候选 SQL 完成。序号键缺失按 0 处理，只增不减（`INCR` + TTL），不依赖时钟；Redis 不可用时回退 60 秒 TTL，不阻塞请求。正常路径下一次请求即看到新闸门；若状态写入与快照装载并发，该次变化最坏仍受既有 60 秒窗口约束（不比改造前更差）。写入方不得在提交前 bump。

### 5.2 API Key 鉴权

`gatewayruntimecache` 的 Key 装载器：

- `status != 'active'` 继续视为不可用。
- 新增：`gate = 0` 视为**当前不在可用时段**，返回可区分的错误（`api_key_outside_schedule`），对外文案「API Key 当前不在可用时段」，HTTP 401、`type=invalid_request_error`。
- `gate NULL` 或 `1` 正常放行。
- `GatewayAPIKeyRow` 增加 `ScheduleGate` 字段，`isGatewayAPIKeyRuntimeUsableAt` 同步判定。

### 5.3 探测与后台任务候选

以下候选 SQL 追加 gate 条件，避免时段外白跑上游：

- jobs `accounthealth/direct_input_reader.go`（周期健康检查、冷却复测）。
- gateway `accountkeystates/probe.go`、`revalidate.go`。
- shared `accountbalance/direct_input_reader.go`（余额查询）。
- `exactkeyprobe/direct_input.go`。

时段外的账户继续保留计划同步与探针冷却状态机，但不投递新的真实上游请求。

### 5.4 列表与统计

账户列表：

- 主状态取 `status`；`status='active'` 且 `gate=0` 时，`effectiveAvailability` 产出新分支：
  - `Status = "schedule_out_of_window"`
  - `Label = "非时间段"`
  - `Color = "blue"`（非告警色）
  - `BlockerScope = "schedule"`
  - `Action = "none"`
  - `Reason = "当前不在可用时段，到达下一个时间计划边界后自动恢复"`
  - `RetryAt` 取 `availability_schedule_next_check_at`
- `blockerScope` 枚举新增 `schedule`。
- `statusBoundary.kind` 新增 `schedule_window_open`。

筛选归组：

- 「正常 / 可调度」筛选：`status='active' AND schedulable=1 AND (gate IS NULL OR gate=1)`（不含非时间段）。
- 新增「非时间段」筛选值，等价条件 `status='active' AND gate=0`。
- 「停用 / 不可调度」筛选继续只命中真正停用，**不再命中非时间段**。

API Key 列表：状态列在 `active + gate=0` 时显示「非时间段」（替代「启用」显示）；筛选项新增「非时间段」，并**下沉为服务端虚拟筛选值** `status=out_of_window`（等价 `status='active' AND gate=0`），避免只过滤当前页造成跨页假阴性。

统计与导出：`ExportAccountStatus` 继续以 `status` 为准，非时间段账户导出为 `active`；`SchedulableBucket` 对非时间段返回 `disabled`（不可调度）但 `effectiveStatus` 保持 `active`，供上层区分。

## 6. 前端

- 账户状态标签：`active + gate=0` 显示「非时间段」（蓝色），tooltip 显示「当前不在可用时段，到达下一个时间计划边界后自动恢复，不影响账户健康」并在有边界时间时补充具体时间；不显示为「停用」。
- 状态筛选新增「非时间段」，并修正「正常」不含非时间段、「停用」不含非时间段。
- 超优先 / 降级备用徽章：`dispatchFlagActive` 继续按 `effectiveAvailability.available` 判定，非时间段为 false。
- API Key 列表与编辑弹窗：状态列在 `active + gate=0` 时整体显示「非时间段」（蓝色）——它替代「启用」显示，因为此时 Key 实际不可调用；编辑弹窗 tooltip 文案为「时间计划只切换可用时段（非时间段），不改写运行状态；人工停用不会被计划自动恢复」。
- 时间计划区块文案：说明「时段外账户仍为正常状态，仅暂停调度」。

## 7. 存量迁移（实施期定稿）

### 7.1 口径与后果

升级**不猜历史 `status`**：一条 `status='disabled'` 的行，无法可靠区分「计划造成」与「人工停用」——事件表最后一条 `disabled` + `executed_at=updated_at` 只能证明「最后一次写入是计划」，不能证明此前没有人工意图。因此：

- **只补闸门，不改 `status`**：同步任务在候选扫描中把 `availability_schedule_gate IS NULL` 的行按当前时刻求值补齐（`gate IS NULL` 已加入候选条件）。
- **存量「计划造成的 disabled」行升级后仍是 `disabled`，需要人工启用一次**；启用后闸门按当前计划重算，此后行为与新语义一致。

这是本改造唯一需要人工介入的升级动作，已在 `docs/待办与阻塞事项.md` T112 的已知边界与发布说明中登记。

### 7.2 执行方式

由同步任务内建自愈，无需停写窗口或一次性数据步骤：

- `listScheduleRows` 的候选条件为 `availability_schedule_json IS NOT NULL AND (next_check_at IS NULL OR next_check_at <= now OR availability_schedule_gate IS NULL)`；升级后第一轮同步（10 秒）即为所有存量行补齐闸门。
- 计划被清除的行（`availability_schedule_json` 置 NULL）不受候选条件命中，但其写入口（PATCH / 批量 / 公开 API）在同一次事务内会把 `gate` 写成 NULL，不依赖同步补齐。

### 7.3 风险与回滚

- 补齐 `gate=0` 不会改变任何 `status`，调度与展示在 `status='disabled'` 时不变（闸门只在 `status='active'` 时才有意义）；补齐 `gate=1` 同理。
- 回滚：`gate` 列可保留不用（回退版本忽略该列）；`status` 未被改写，回滚后行为即恢复旧语义（计划重新写 `status`）。

## 8. 验收

1. 配置计划且当前在时段外：账户列表显示「正常 / 非时间段」，不显示停用；「停用」筛选不命中，「非时间段」筛选命中。
2. 该账户不参与调度；时段边界到达后自动可调度，`status` 全程保持 `active`。
3. 人工在时段外停用：`status='disabled'` 持久；下一个窗口开始时**不**自动启用。
4. 时段外人工启用：`status='active'` 但 `gate=0`，仍不调度，展示非时间段。
5. API Key 时段外调用：返回「API Key 当前不在可用时段」，不再返回「API Key 无效」。
6. Key 小时额度窗口绑定只在闸门打开时重建，闸门关闭不改写绑定。
7. 存量：升级后第一轮同步为存量行补齐闸门且不改写任何 `status`；原本由计划停用（`status=disabled` + `gate=0`）的行需人工启用一次后进入新语义（已在 T112 登记）。
8. 既有计划语义回归全绿：跨天窗口、多窗口重叠、例外日期、闸门每轮重算（原 T91-7 边界补偿分支已退役，其纯函数保留）。
