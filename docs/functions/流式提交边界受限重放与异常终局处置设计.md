# 流式提交边界受限重放与异常终局处置设计

> 状态：设计评审 v2.2（2026-10-24 用户立项裁决「需要做这个机制」；两轮独立复审 + 一轮外部静态审核，全部发现已修订闭环，放行实施；实现后回填状态为已实施）。本文是该机制的权威契约。
> 起因：2026-10-24 生产事故（待办 W22，trace `a61a7882`）——上游 whiteapi-ds 断流吐出「半截 chunk + 错误帧粘连」的非法 SSE 载荷，网关在语义提交后透传给客户端（客户端 `JSON.parse` 报 `Bad control character`，turn 失败），网关自身却按既有 generic EOF 收敛记为 success（估算 usage 4189 tokens 以成功口径入账，熔断面反被喂入「帧完成」治愈证据）。[上游流式失败帧拦截设计](上游流式失败帧拦截设计.md) §5.1 登记的字节级边界首次生产命中，且暴露出「假成功记账 + 零可观测」的伴生缺口。

## 1. 目标与非目标

### 目标

1. **流早期断流客户端无感**：上游在「首个语义事件之后、受限窗口之内」异常断流时，网关在窗口内保持服务端重放资格，按既有提交前失败路径丢弃缓冲并换号重放，客户端零字节、无感知（候选耗尽时按 §5.4 给出失败终态）。
2. **流中/尾异常断流不再假成功**：上游以异常终局收尾（EOF 前存在无法解析的非法 JSON 事件）时，generic 客户端不再无条件收敛 success——按失败结算：审计 failure、usage 以失败口径估算入账、账户失败归因正确（修正熔断「治愈证据」倒挂）、客户端按 2026-10-23 收口契约收到真·网络级断开并触发其自身重试。**前提是坏事件字节不再透传**（§3.2.0 隔离）：W22 实证客户端在收到粘连载荷的瞬间即解析失败终止，等不到 EOF 终局——若坏字节照旧透传，「网络级断开触发重试」对这类客户端不可达。隔离后客户端全程只见过合法 SSE 事件，EOF 断开即网络级中断，重试承诺成立。
3. **非法 SSE 事件可观测且不透传**：原生 OpenAI 直通管道对无法 JSON 解析的事件（含粘连载荷）建立计数与日志，**字节级隔离（不写下游）**，终结「透传且零留痕」。

### 非目标

1. **不做语义提交后的服务端重放/拼接**。[流式中断与客户端重试调研](流式中断与客户端重试调研.md) §3.7 已否决「已输出后由服务端重放」；本设计的窗口机制本质是**推迟语义提交点的置位**，窗口内提交从未发生，重放仍发生在提交前（该做法的直接契约依据是调研文档 L141：「下游尚未语义提交时，即使解析器已在预提交缓冲中识别到可见输出，各类请求仍可丢弃缓冲并切换后续账号」）。
2. **不改 2026-10-23 收口契约**：提交后失败对全部客户端一律真·网络级断开（Hijack+Close，无补发终态）。
3. **不改 Codex `passthroughUpstreamFailure` 例外与 W7 桥接转换层例外**（两者契约原文见 [上游流式失败帧拦截设计](上游流式失败帧拦截设计.md) §4）；**桥接流不启用窗口**（§3.1 窗口资格）。
4. **首版只覆盖原生 OpenAI 直通管道**：`gatewayopenai` inspector 驱动的 chat/responses 流（本次事故形态所在面）。Anthropic / Gemini native 流的 parse-error 已有各自 summary 机制（`gatewayanthropic/streaminspection.go`、`gatewaygemini/streaminspection.go`），其终局判定同覆盖列为后续批次，本文不裁决。
5. 不新增任何配置项/开关；窗口参数为编译期常量（调参走代码评审）。
6. 不解决「上游静默挂流不 EOF」——既有 idle/首字超时已覆盖该形态，窗口机制在其之上工作。

## 2. 现状机制与空白（2026-10-24 取证结论，复审核对）

- **提交点即首个语义事件**：pre-commit 缓冲（`gatewayresponse/precommit.go`）仅在「下游零字节且未见语义输出」时工作，上限 256KB；`RetryBeforeDownstreamWriteUntilOutput` 生产恒 `true`（`finalize.go:312`），但首个语义事件分类完成即 `OutputReceived=true` → 立即 flush + `MarkSemanticCommitted`（`pipe.go:289-308`），此后 `CanRetryUpstream()=false` 永久失去重放资格（`commitstate.go:35`）。
- **generic EOF 收敛**：`finalizeAfterLoop`（`pipefinal.go:368-379`）对非精确画像（`interpretProtocolFailures=false`）在「干净 EOF + 见过任一 data 事件」时无条件收敛 `completed=true "已完成"`——裁定出自 2026-07-23 `1452df2be`（diff 原文已复核：「Generic clients keep opaque upstream SSE semantics: a clean transport EOF is sufficient…」），`992bf2a6b` 收紧排除纯心跳空流，测试锚定 `TestW13CFinalizeAfterLoopGenericEOF`。精确画像 EOF 无终止走 `finalizeMissingTerminal` 失败路径（提交前可救回/提交后中断）。
- **非法 JSON 事件在原生 OpenAI 直通管道零观测**：`DataParseError` 只进该 inspector 内部 summary（`gatewayopenai/inspector.go:206-214`），管道与结算面无消费方——无日志、无审计、无计数；字节透传是唯一处置。桥接层（`openaicompatbridge/bridge_gemini_response.go` 等 5 处）已各自消费 parse-error，不在本设计范围内（§1 非目标 4）。失败帧拦截（[上游流式失败帧拦截设计](上游流式失败帧拦截设计.md) §3.4）对非法 JSON 单帧明确「非失败，现有行为不变」。
- **健康记账倒挂**：以 `StreamPipeResult` 正常返回的**提交后语义失败族**（missing-terminal、协议失败终态、矛盾失败、拦截命中）`TransportFailure` 恒 nil（真实读取中断/超时经 `handlePipeError` 置位，不属此族）→ `classifyPostVerdictOutcome` 不产 transportFailure → circuit 结算落入 `ReportFramingComplete`（`chain_v1_loop.go:2051-2060`）——断流被记为熔断「治愈证据」；且 success 收敛形态根本不触发 `HandleStreamFailure` 失败回调。本次事故因此零失败痕迹。
- **usage 估算入账**：估算本身有文档依据（[模型价格与用量统计口径](模型价格与用量统计口径.md) L12/L28）；估算只在结算点消费（`finalize.go:390-400`），窗口缓冲不会提前触发。缺口在**成败归类**——异常 EOF 的估算值随 `Success=true` 入账且无字段区分。

## 3. 机制设计

### 3.1 受限重放窗口（推迟语义提交点）

在既有 pre-commit 缓冲之上增加「窗口阶段」。时间线：

```
上游请求 ──► 首个语义事件到达 ──► [窗口：继续缓冲，不写下游] ──► 窗口关闭条件任一命中 ──► 一次性 flush + MarkSemanticCommitted ──► 现状行为
                                       │
                                       └─ 窗口内任一失败信号 ──► 既有提交前失败路径：丢弃缓冲 + 换号重放（客户端零字节，无感）
```

**窗口关闭条件**（先到先关）：

1. **收到协议终止事件或失败帧**（`TerminalReceived` / `FailedReceived` 置位）——终态语义事件**不入窗口缓冲**，先关闭窗口并按既有语义处置（终止→flush 成功路径；失败帧→既有失败路径），见 §3.1.2 不变量；
2. **窗口缓冲字节达上限 `B`**——超限判定在**追加该 chunk 之前**进行：达到 B 时该 chunk 不入缓冲、直接随 flush 写出（确定性规则，测试可断言缓冲内容与首写字节）；
3. **窗口时长超 `T`——真实截止**：窗口启动 `time.Timer`（T 到点回调强制关窗 flush；窗口因其他条件关闭或管道结束时 `Stop` 释放，防泄漏）。不采用「后续 chunk 到达时惰性检查」：上游静默或慢滴流时惰性检查使实际上限漂移到 idle timeout（30s）或单个 chunk 间隔，违反「最多 +T」承诺；真实截止下静默超 T 的流在 T 到点即把已缓冲内容下发、后续 chunk 直接透传，行为与承诺一致；
4. 上游 EOF / 失败信号——进入 §3.2 终局判定或既有失败路径。

**参数（编译期常量，初值）**：`B = 8KB`，`T = 2000ms`。

- 取值依据（2026-10-24 生产数据）：流式首字延迟 p50 6.4s（deepseek-v4.1-flash）～15.6s（gpt 系），p99 26s+。`T=2000ms` 的常态代价仅落在「上游迟迟不发终止事件」的流（reasoning 长流为主），首字延迟最多 +2s；正常流终止事件紧随内容，flush 提前，延迟增量趋近 0。`B=8KB` 对几十字节粒度的 delta chunk 约合数百个事件，实际由 T 主导，B 只是防单流内存占用的护栏；图像流等 base64 大 chunk 会在首 chunk 即触 B 关窗，窗口近似 no-op（行为与现状一致）。
- **诚实边界**：窗口只覆盖「首语义事件后 T 秒内」的断流（秒断/早期断型）。本次事故断在流 35 秒处，**窗口救不了**——中/尾断由 §3.2 处置。T 取更大值可扩大覆盖但线性增加全体流式请求的首字延迟，不做。

**窗口资格（不启用窗口的流，保持现状「首个语义事件即提交」）**：

- **媒体域请求**（图片/音频/视频任务流）；
- **桥接流**（chat 上游 → anthropic/gemini/responses 客户端方向）：桥接管道有自己的 EOF 合成收尾契约（W7），窗口会改变其时序前提，排除；
- **hosted tool 本地 runtime 模式**及其他副作用请求（调研文档 L123 硬禁令：图片、音频、文件、资源、后台任务、hosted tool 等副作用请求即使尚未输出也禁止隐式重放）。媒体域判定复用 `dispatchDomainStatelessMediaOf`（与 `settleResponseStreamServerRetry` 媒体域切断同源）；hosted tool 子调用（AI 问答 web_search 经 `/v1/responses` 回环、身份头 `x-juhe-ai-purpose: chat_web_search`，见 `chat/generation_websearch.go`）在调度层无既有排除标记——S2 将该 purpose 头投影进流式窗口资格（读既有头、传布尔，加法式接线），显式排除窗口，避免搜索子调用被换号重放重复执行副作用。

窗口资格由调度层在发起流式请求时随选项传入（扩展 `StreamPipeOptions`），缺省**启用**（文本主路径），显式排除面关闭。

**与现有代码的关系**：

- `PreCommitBufferState` 增加窗口阶段字段（windowing/windowStartMs/windowBytes）；`CanKeepPreCommitChunk` 在窗口内放行语义 chunk；
- 现有「已见 data 证据但未语义提交时缓冲超限抛 `StreamPreCommitBufferExceededError`」的处置**变更为「flush 提交并继续」**（窗口满不再是失败）——该错误码保留给「纯非语义帧（注释/心跳）堆积超 256KB」的既有保护场景；
- `writeDownstreamChunk` 的 `semantic` 判定（`DataPayloadStarted` 即提交）在窗口期不再触发写下游，仅窗口关闭 flush 时置位。

#### 3.1.1 提交边界引用（全文）

架构总览原文：「提交边界 = 网关向客户端写出的首个真实字节（含 SSE 心跳 / 保活帧）」。窗口期零字节写出（等待期心跳仅由派发等待驱动，attempt 活跃读取期不产心跳），边界未越过；本设计不改该定义。

#### 3.1.2 窗口缓冲不变量

1. 窗口缓冲**永不包含** `TerminalReceived` / `FailedReceived` 置位后的 chunk——终态语义事件到达即先关窗、按既有语义处置；
2. 窗口关闭 flush 复用既有写路径，`terminalEventWritten` / `MarkSuccessfulProtocolTerminalReceived` 置位次序与现状一致（终止语义先于任何矛盾失败判定，`finishTerminalSuccess` 矛盾臂不被误触——测试锚点 `TestW11BFinishTerminalSuccessContradictoryFailureAlwaysInterrupts` 继续绿 + 新增窗口版用例）；
3. 失败帧字节不经窗口 flush 透传（「失败帧不透传」契约保持）。

### 3.2 异常终局判定（收紧 generic EOF 收敛）

#### 3.2.0 ParseError 事件隔离（坏字节不透传）

inspector 将事件分类为解析失败（`DataParseError`）时，该事件的字节**不写下游**（与既有失败帧拦截同一时序保证：事件级分类先于写入，[上游流式失败帧拦截设计](上游流式失败帧拦截设计.md) §4），计入 `ParseErrorEventCount` 并打 WARN `gateway_stream_event_parse_error`（带 trace/account、事件序号、原始字节摘要），此后只累加计数。效果：客户端全程只见过合法 SSE 事件——流继续则看到内容小缺口（丢弃的是无法解析的残片，如 W22 的「上级」增量），流异常终局则收到干净网络级断开；两种路径都不再向客户端投递非法字节。Codex `passthroughUpstreamFailure` 模式例外照旧（该模式下失败帧原样透传契约不变，ParseError 隔离不改变其分支）。

#### 3.2.1 EOF 终局判定伪码（互斥，按序判定；`completed` 以干净 EOF 为前提，读错误/超时仍走既有 `handlePipeError`，不在本伪码内）

```
1. completed && TerminalReceived（且无失败帧证据）                                  → success（流健康收尾；ParseError WARN 已留痕，混入 ParseError 不改判；「终止+失败帧同到」不落入此行，按既有矛盾失败契约在判定 2/拦截设计 §5.5 处置）
2. completed && FailedReceived（可解析失败帧）                                      → 既有失败路径（拦截设计契约，不在本设计改动面）
3. completed && !TerminalReceived && ParseErrorEventCount > 0
   && !interpretProtocolFailures                                                    → 流异常终局 → 失败结算（§3.2.2，仅 generic）
4. completed && !TerminalReceived && ParseErrorEventCount == 0
   && DataEventObserved && !interpretProtocolFailures                               → success（现状 generic 收敛，1452df2be 主体语义保留）
5. 其余精确画像形态（EOF 无终止 → finalizeMissingTerminal；终止+失败帧 → finalizeIncompleteOrFailed 等）→ 现状不变（error_code、探针、归因全部维持 missing-terminal 现行行为，ParseError 不改变精确画像任何路径）
```

优先级即行序：判定 1 优先于判定 3（终止事件已到 = 上游自愈完成，仍 success）；判定 3 限定 generic 且优先于既有 `finalizeParserSkipped` 分支（先 ParseError 后 Skipped 的流归因 abnormal_eof，失败归因更准）；判定 4 保留 `1452df2be` 主体——大量真实上游（含杂牌中转）不发终止事件即干净 EOF，避免大面积假失败。**精确画像路径完全不动**（判定 3/4 均限定 `!interpretProtocolFailures`，精确画像的 ParseError 形态维持现状归因与探针行为）。

#### 3.2.2 异常终局失败结算

- 复用 `finalizeMissingTerminal` 的提交前/提交后两分支骨架（提交前→缓冲丢弃换号；提交后→`signalCommittedStreamFailure` 网络级断开），新增日志事件族 `gateway_stream_abnormal_eof_before_downstream_commit` / `gateway_stream_abnormal_eof_interrupted`（对齐收口后命名）；
- error_code 常量 `upstream_stream_abnormal_eof` 定义在 `gatewayresponse` 包（S0）；
- **失败归因三面**（修正倒挂，对齐 BUG-0289 注释口径「不得落入 transportFailure==nil 的 ReportFramingComplete 臂」）：
  - circuit：`ReportUnknown`（中性臂，BUG-0289 先例 `chain_v1_loop.go:2042-2050` 同款）——**不进** `ReportTransportFailure`（干净 EOF 非 transport 失败，传输/opaque 分离契约保持）、**不进** `ReportFramingComplete`（不再是治愈证据）；circuit API 无「上游不完整」专用方法，中性臂为既有语义最近落点，不新增状态机方法；
  - 账户锁：`RecordFailureAsync('upstream_stream_abnormal_eof')` 计入失败统计（不直接熔断，阈值由既有机制管）；接线位置 = `classifyPostVerdictOutcome` 新增按 `handling.ErrorCode == upstream_stream_abnormal_eof` 的分支（该 code 经 `finalizeStreamFailure` 可达 handling）；
  - 热质量终态：`upstream_response_failure / source=upstream_response`；keyModel 面：默认臂 `ReportUpstreamNotComplete`（现状同款，ProtocolValidatedSuccess=false 即落此臂）；
- **探针不派发**：`availabilityProbeEligible=false`（与 missing-terminal 现行 `true` 的差异点显式化：低质量渠道高频断流时避免探针风暴；失败统计已由账户锁承担，探针留给既有调度失败路径）；
- usage 仍按可见输出估算入账（口径文档 L28 对失败流的既有规则）但 `Success=false`、`error_code=upstream_stream_abnormal_eof`；审计 outcome=stream_failed。

### 3.3 观测面

- `gateway_stream_event_parse_error` WARN（每请求首个）+ 结算日志新增 `parseErrorEventCount` 字段（成功/失败结算均带）；
- **窗口延迟独立观测**：现有 `first_token_ms` 在识别到上游语义输出时记录（`markFirstSemanticOutput`），不含窗口停留时间，观测不到窗口机制引入的延迟——新增结算日志字段 `windowDurationMs`（窗口开启到关闭的时长；未开窗流省略）与 `downstreamFirstWriteMs`（首个下游字节写出时刻 − 请求开始，客户端可感知首字延迟的真口径）；§5.1 的上线观察以这两项对比，`first_token_ms` 仅作上游侧参考；
- 审计不加新列：异常终局失败经既有 `error_phase/error_code/error_message` 表达；
- W22 完成判定与本设计生产验证联动：同类事件生产表现应为「网关 failure 日志 + 客户端网络级中断自动重试」，替代现状「客户端 JSON 解析炸 + 网关 success」。

## 4. 既有契约的遵守与修订

| 契约 | 本设计关系 |
| --- | --- |

## 5. 风险与权衡

1. **首字延迟 +T**：仅「上游不早发终止事件」的流承担，最多 2000ms（真实截止 timer 保证，含静默流）；生产 p50 TTFB 6.4s+，占比温和。上线后以 `downstreamFirstWriteMs`/`windowDurationMs` 分布对比上线前后 p50/p90（`first_token_ms` 不含窗口停留，仅作上游侧参考，见 §3.3）。
2. **异常终局误伤**：上游发过非法 JSON 事件但客户端本可容错解析成功的流，将被判失败并断开——客户端触发重试（本就大概率需要的动作），代价可控；但「无重试能力的哑客户端」会从「收到部分内容」变成「明确失败」。观察期跟踪 `upstream_stream_abnormal_eof` 的账户/渠道分布，若某渠道高频误伤再评估按渠道收敛（属后续裁决）。
3. **健康探针连锁已排除**：abnormal_eof 不派发可用性探针（§3.2.1），低质量渠道高频断流不会引发探针风暴；账户锁失败统计的调度影响与既有失败记账同强度。
4. **候选耗尽终态**：窗口内失败且候选/预算耗尽 → 既有 `sendStreamServerRetryExhaustedResponse` 503（或既有失败终态），客户端零业务字节——从「收到部分内容后失败」变为「未收到内容即明确失败」，配合客户端重试语义不变。
5. **窗口缓冲内存**：8KB/流上限，并发放大可忽略（对比现有 256KB 语义前缓冲）；图像大 chunk 立即触 B 关窗，无额外驻留。
6. **假成功存量行为消失的下游影响**：看板/对账中「success 但客户端报错」的口径消失；低质量渠道失败率上升属数据变真，非回归，运维侧需知晓（同步运维手册口径）。

## 6. 验收标准与测试锚点

1. 窗口内断流（首个语义事件后、T/B 内上游断/错误帧）→ 换号重放成功、客户端零字节、审计恰一成功尝试 + N 次失败尝试（镜像 `TestW31StreamTopLevelErrorFrameBeforeCommitSwitchesCandidate` 形态新增窗口版用例）；
1b. **ParseError 事件隔离**：流中混入解析失败事件但流继续正常完成 → 客户端字节流不含坏事件原文、内容小缺口可接受、流 success + WARN + 计数（新增用例，客户端回放验证下游可见字节全为合法 SSE 事件）；
2. 窗口内收到终止事件 → 立即 flush，流正常完成，`first_token` 语义不受损；
3. 窗口超 B（追加前判定，该 chunk 随 flush 写出）/ 超 T → flush 提交，其后失败按提交后契约断开（`TestWdCommittedFailureAlwaysInterrupts` 族回归）；
4. 粘连载荷 + 干净 EOF（generic）→ failure 结算：`error_code=upstream_stream_abnormal_eof`、usage 估算入账且 `Success=false`、客户端 `io.ErrUnexpectedEOF`、**下游字节流不含坏事件原文（隔离断言）**、circuit=`ReportUnknown` + keyModel=`ReportUpstreamNotComplete`（两面分别断言）+ 账户锁失败记录 + 热质量 `upstream_response_failure`、探针零派发（新增用例，镜像 W22 事故形态）；
4b. **窗口期静默行为**：首个语义事件后上游静默 >T → timer 到点强制 flush（客户端在 T 收到已缓冲内容）；静默后 EOF → 终局判定按 §3.2.1；静默后读错误 → 既有 handlePipeError 失败路径；
5. 终止事件 + 混入 ParseError → success + WARN（新增用例，判定 1 优先于 3）；
6. 干净 EOF 无终止无 ParseError（generic）→ success 回归不变（`TestW13CFinalizeAfterLoopGenericEOF` 继续绿）；
7. 纯心跳空流 EOF → 提交前可救回回归不变；Codex passthrough / 桥接流（不启用窗口，EOF 合成收尾不变）/ 精确画像 missing-terminal 全部回归绿；
8. **精确画像 × 窗口**：窗口内失败换号（无感）成功用例 + 窗口外 missing-terminal 行为不变用例；
9. **窗口内失败 × 副作用排除面**：媒体域/hosted tool 请求不启用窗口（首个语义事件即提交，现状行为），回归锚定；
10. **窗口内失败候选耗尽** → 503/失败终态、客户端零业务字节、审计 N 次失败尝试；
11. **窗口内多账户连环失败**（候选 1、2 均窗口内断，候选 3 成功）→ 客户端零字节、最终成功、审计 2 失败 + 1 成功；
12. 先 ParseError 后 Skipped 的流 → 归因 abnormal_eof（判定 3 优先于 Skipped 分支）；
13. gateway 包全量 + cmd 定向 + 三项目 build 全绿。
