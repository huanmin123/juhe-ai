# 缓存率感知调度与用量缓存率展示设计

> 状态：设计稿（2026-10-07），未实施。本文是该功能的唯一契约入口；实施交付时必须按第 13 节清单同步各权威文档，本文随实施状态更新。
>
> 动机：上游计价对缓存命中高度敏感——缓存率越低，实际输入单价越高（部分上游缓存率每降低约 10 个百分点，实际价格约提升 4 倍）。倍率低的账户若缓存差，换算后的真实成本反而更高。当前调度在同层只比较可靠性与首字速度，完全不感知缓存命中；本设计把"缓存率"作为同层速度平局时的决胜维度，并在账户列表展示今日缓存率。

## 1. 现状事实（2026-10-07 代码基线，均已核实）

以下事实是本设计的出发点，实施时如代码已演化，以代码为准并回填本文。

1. **同层排序的权威位置**：`/v1` 候选的最终同层排序在热质量层 `backend-go/projects/gateway/internal/gatewayhotquality/selection.go` 的 `compareWithinTier`（约 585 行）。层（tier）由 `模型秩 | fallback | super | priority` 四元组构成（`GatewayAccountConfigurationTierKey`），"同优先级"在代码上就是同层。当前层内维度顺序：
   1. 可靠性等级（`reliabilityLevel`）；
   2. 有效可靠性数值（`effectiveReliability`）；
   3. 首字速度（双方均有样本时：`FirstByteEwma5m`，其次 `FirstByteP95Bucket10m`）；
   4. `StableBindingOrder`（稳定绑定序）；
   5. 账户 ID / 原始下标（确定性兜底）。
2. **速度比较对所有调度偏好生效**：`cost_first`（普通模式）下 `compareWithinTier` 同样比较速度 EWMA，不同账户速度平局罕见——若把缓存率简单排在速度之后，它在普通模式下几乎永远不生效。因此缓存率维度必须与速度做"死区联合裁决"（第 5 节），不能简单追加。
3. **调度偏好机制**：`cost_first | speed_first`（`routestrategies/config.go`；普通/权重/故障回退/轮询路由共用，默认 `cost_first`）。快速模式的完整机制（首字截止 → 滑窗慢样本 → `latency_degraded` 降级 → 限次切号 → 恢复探针）已内置且权威文档为《普通路由速度优先延迟切换设计》。
4. **热质量层对所有组类型执行**（`preparation.go` `applyHotQualityOrder`，媒体 lane 豁免）；快速模式下降级账户整体后移发生在层间分段（`DecideHotQualityCandidate`），与层内比较正交。
5. **缓存数据链已全通**：上游解析（`gatewayopenai/gatewayanthropic/gatewaygemini` usage）→ `usage_records` 明细（`cache_read_tokens` 等列）→ jobs `usage-stats-aggregation` 每 60s 聚合 → 统计库 `usage_stats_hourly` / `usage_stats_daily`，两张表均已有 `cache_read_tokens / cache_write_tokens / cache_write_1h_tokens` 列（`maintenance/internal/schema/sqlite_schema_stats.go`、`pg_schema_stats.go`）。**本设计不需要任何 schema 变更。**
6. **hourly 保留期**：`usageStatsHourlyRetentionDays` 默认 60 天（seed 与 jobs 设置一致），远大于滚动 24h 窗口需求。
7. **时区**：聚合日/小时键按系统设置 `usageStatsTimezone`（默认 `Asia/Shanghai`）生成；gateway 读侧已有同键读取先例（`accounts/list_usage.go`）。
8. **列表投影缺口**：`accounts/list.go` `UsageSummary` 只有 `requestCount / totalTokens / totalCost` 三字段，`list_usage.go` 的 SELECT 只投影 `request_count、input+output、success_cost_usd`——列表展示缓存率需要扩展这条投影。
9. **前端现成口径**：`frontend/src/views/usage-stats/usageStatsHelpers.ts` 已有 `cacheReadRate()`（OpenAI 口径分母为 `inputTokens`，即上游语义已含缓存命中部分）；`UsageSummaryTags.vue` 是"用量(日)"列的 tag 渲染组件；回归脚本 `account-list-inline-dynamic-regression.ts` 覆盖该组件。
10. **调度消费现状**：网关任何调度路径（dispatch/quota/routing/hotquality）目前不读取任何缓存指标。

## 2. 目标与非目标

### 2.1 目标

1. 同层、候选均健康时：首字速度差距在模式阈值内，由缓存率决胜，缓存率高者优先；差距超过阈值，仍由速度裁决。**速度是第一裁决维度，缓存率是速度接近时的决胜维度。**
2. 阈值分模式：普通模式（`cost_first`）10s；快速模式（`speed_first`）5s——快速模式速度权重更高，只给缓存率更小的上位窗口。
3. 调度结果必须稳定：不因阈值边缘震荡或数据小幅波动出现同层账户间频繁切换（第 6 节）。
4. 账户列表"用量(日)"列新增今日缓存率 tag（第 9 节）。
5. 快速模式触发阈值后的既有行为（降级账户后移、限次切号、恢复探针）保持完全不变。

### 2.2 非目标

- 不改层级次序（模型秩、备用、超级优先、优先级）与分组层调度（轮询、权重、故障回退）。
- 不改会话粘性、同层探索、账户电路、慢样本状态机、媒体 lane 豁免。
- 不做实时/精确缓存率统计：读现成 60s 聚合 + 网关侧 60s TTL 快照，允许约 1~2 分钟滞后（用户已明确接受延迟）。
- 不新增 schema、不新增配置项或开关：全部参数为内置常量（第 10 节），调整通过文档修订 + 代码同改完成。
- `cache_write`（Anthropic 显式缓存写）不参与口径：当前供应商形态为 OpenAI 自动缓存，无显式写；未来接入时按第 12 节扩展。

## 3. 术语与口径

| 术语 | 定义 |
| --- | --- |
| 缓存率 | `cache_read_tokens ÷ input_tokens`（OpenAI 口径：上游 `input_tokens` 已含缓存命中部分）。与前端 usage-stats「缓存读占比」同口径 |
| 有效缓存数据 | 滚动窗口内该账户 `input_tokens ≥ CacheMinSampleInputTokens`（10 万 token）。低于样本门视为"无缓存数据"，不参与缓存率裁决 |
| 调度窗口 | 滚动 24 小时：统计库 `usage_stats_hourly` 按 `stat_hour ≥ cutoff` 求和，cutoff 按使用时区回溯 24h。不用自然日——凌晨"今日"数据过少会产生噪声决策 |
| 展示窗口 | 自然日：`usage_stats_daily` 当日行，与"用量(日)"列语义一致。展示值与调度值允许不一致 |
| 数据行 | `system_account_id='global' AND scope_type='account'`（global 视角，避免跨租户串数），`scope_id` = 账户 ID |

## 4. 总体规则（一句话）

> 同层候选在可靠性与有效可靠性分出高下之后：先比首字速度，速度差超过模式阈值 → 快者胜；速度差在阈值内（含任一方无速度样本）→ 转入缓存率裁决，有效缓存率差距 ≥ 死区 → 高者胜；仍分不出 → 落回 `StableBindingOrder` 稳定序（现行为）。

## 5. 调度比较规则（核心契约）

### 5.1 修改点

仅修改 `gatewayhotquality` 层内比较器 `compareWithinTier` 的"速度"一步，替换为下述"速度-缓存率联合裁决"；其余维度（可靠性等级、有效可靠性、`StableBindingOrder`、确定性兜底）与调用链全部不变。模式阈值在决策入口（`DecideHotQualityCandidate`，已有 `Mode` 输入）解析后传入比较器，比较器保持纯函数、无状态。

### 5.2 联合裁决伪代码

```text
输入：left, right（同层两候选）；mode（cost_first | speed_first）

threshold = (mode == speed_first) ? 5_000ms : 10_000ms

# 第一步：速度评估（取值顺序与现有 compareSpeed 一致）
v(候选) = FirstByteEwma5m，缺省则 FirstByteP95Bucket10m，均缺则 速度未知

若 双方速度已知 且 |vA - vB| > threshold：
    速度快的候选胜出（现行为，结束）
否则（速度接近，或任一方速度未知）：
    # 第二步：缓存率裁决
    若 双方均有有效缓存数据 且 |rA - rB| >= CacheRateDeadband(10pp)：
        缓存率高的候选胜出（结束）
    否则：
        落回 StableBindingOrder → 账户 ID → 原始下标（现行为）
```

### 5.3 输入组合裁决表

| 速度样本 | 缓存数据 | 裁决 |
| --- | --- | --- |
| 双方已知，差 > 阈值 | 任意 | 速度胜（现行为） |
| 双方已知，差 ≤ 阈值 | 双方有效且差 ≥ 10pp | 缓存率高者胜 |
| 双方已知，差 ≤ 阈值 | 缓存差 < 10pp 或任一方无有效数据 | 稳定序（现行为） |
| 任一方速度未知 | 双方有效且差 ≥ 10pp | 缓存率高者胜 |
| 任一方速度未知 | 缓存不可裁决 | 稳定序（现行为，与现有"cold 中性"语义一致） |

### 5.4 决策可观测

`gateway_dispatch_decision` 决策日志（轨迹日志设计的"为什么选它"明细）在候选明细中补充两个候选级字段：`cacheHitRate`（窗口值，无数据省略）与裁决中实际生效的维度标记（`speed_dominate / cache_rate_dominate / neutral`），供线上核对调度行为。

## 6. 稳定性与防抖设计

用户硬约束：不能频繁切换，要有策划地稳定。本设计不引入任何有状态滞回（第一版），依赖以下五层无状态机制达成稳定：

1. **双重死区**：速度阈值（10s/5s）与缓存率死区（10pp）都是滞回带——边缘小幅波动不改变胜负关系；比较器是确定性纯函数，同样输入恒得同样排序。
2. **慢变量输入**：速度用 5 分钟 EWMA（已平滑），缓存率用滚动 24h 窗口（日内相对稳定）；快照以 60s TTL 批量刷新，排序输入的变化频率被物理限制在分钟级。
3. **会话粘性不受影响**：已建立会话的请求由既有 affinity claim 钉住原账户（排序之后的提升机制），缓存率裁决只决定新会话/无绑定请求的首选。
4. **同层探索托底**：既有探索机制（credit + cursor，目标冷却 60s）继续给同层其他账户固定流量份额——低缓存率/新账户不会饿死，其缓存率数据也能持续积累，胜负关系才能真实演化。
5. **正反馈自稳定 + 既有兜底**：胜出账户获得流量 → 缓存命中维持 → 缓存率保持；若其被限速/出错，可靠性等级与账户电路（既有机制）立即把它降下去，流量自然回流。

**留观项（不实施，仅观察）**：上线后若线上仍观测到同层账户间高频切换（以 `gateway_dispatch_decision` 首选账户切换频率为准），再评估"在位账户滞回"（incumbent bias：现任账户仅在挑战者明确更优时让位）。该机制需要跨请求状态，收益与复杂度都待实测数据支撑。

## 7. 与既有机制的边界

| 机制 | 关系 | 说明 |
| --- | --- | --- |
| 快速模式降级/切号 | 正交，零修改 | 降级账户后移是层间分段（先于层内比较）；触发阈值、限次切号、恢复探针全部照旧。切号目标 = 剩余候选顺序第一个有空槽者，该顺序已含缓存率裁决——即快速模式切号会在"速度接近"的健康候选中偏好缓存率高者，符合速度优先语义 |
| 会话粘性 | 不变 | 见第 6 节第 3 条 |
| 同层探索 | 不变 | 探索目标选择与配额不受缓存率影响；探索产生的流量会自然更新账户缓存率 |
| 高并发分组 | 生效，路径待实施核实 | 高并发组在亲和排序阶段有独立的负载/并发维度（先于热质量层）；热质量层随后对所有组类型执行层内重排。实施时确认高并发组最终排序路径，若其存在独立的层内比较器，按同规则复用 |
| 媒体 lane | 天然豁免 | 热质量层对媒体 lane 豁免，缓存率维度随之不作用于音频/视频请求 |
| 数据缺失 | 中性跳过 | 快照加载失败或账户无数据时，缓存率维度整体跳过，排序回退现行为；不阻塞调度、不报错、不静默改变其他维度语义 |

## 8. 数据链与加载器契约

### 8.1 快照加载器（新增，gateway 进程内）

- **端口**：`CacheRateSnapshotSource`，返回 `map[账户ID]{CacheReadTokens, InputTokens}`；由组合根（`compose.go`）装配 adapter，读**统计库**句柄。
- **查询**（单条聚合 SQL，每刷新周期一次）：

```sql
SELECT scope_id,
       SUM(cache_read_tokens) AS cache_read_tokens,
       SUM(input_tokens)      AS input_tokens
FROM usage_stats_hourly
WHERE system_account_id = 'global'
  AND scope_type = 'account'
  AND stat_hour >= ?            -- cutoff：按 usageStatsTimezone 回溯 24h 的小时键
GROUP BY scope_id;
```

- **刷新**：singleflight + TTL 60s（`CacheRateSnapshotTTL`）；到点后台刷新，请求路径只读内存 map，**零每请求 I/O**。
- **失败语义**：刷新失败保留上一快照并在日志 WARN（限频）；从未成功过则缓存率维度整体跳过（第 7 节）。时区设置读取失败时按聚合侧同源逻辑处理，不自行猜测。
- **注入**：`HotQualitySelectionSnapshot` 增加 `CacheHitRate *float64` 与 `CacheWindowInputTokens int64`；快照装配处按账户 ID 从内存 map 注入（无数据保持 nil/0，即"无缓存数据"）。

### 8.2 待实施核实（第一实施步骤）

1. 授权来源账户（source_accounts）流量在统计聚合中落 `global/account` 行的 `scope_id` 语义：缓存率必须按**实际承载流量的物理账户**匹配；若授权流量落在 `account_authorization` 行，加载器需按授权实例归并到物理账户后再注入。
2. 高并发分组最终排序路径中热质量层的覆盖关系（第 7 节）。

## 11. 测试与验收

### 11.1 调度侧

- 比较器单测（`gatewayhotquality` 包级）：5.3 节裁决表逐行断言；阈值两侧（10s/5s 各一组）；缓存率死区两侧；样本门上下；双方 cold 中性；mode → 阈值映射。
- 加载器单测：TTL 内不重复查询、到点刷新、失败保留旧快照、cutoff 小时键按使用时区、scope 行过滤（global/account）。
- 注入与装配测试：候选快照带/不带缓存数据两种形态。
- 回归：既有 w1/w2/chain 排序与速度优先用例全绿（证明降级切号、探索、粘性零回归）；`gateway_dispatch_decision` 新字段断言。

### 11.2 展示侧

- 后端：列表投影回归（SQLite/PG 双 dialect，现有投影测试扩展）。
- 前端：`vue-tsc` 通过；`account-list-inline-dynamic-regression.ts` 更新并绿；无数据不渲染 tag 断言。

### 11.3 端到端验收标准

1. 同层、双账户健康、EWMA 差 ≤ 阈值、缓存率差 ≥ 10pp → 首选为缓存率高者。
2. 同层、EWMA 差 > 阈值 → 首选为速度快者（两种模式）。
3. 快速模式触发首字截止 → 降级后移、限次切号行为与现状逐字节一致（既有回归护航）。
4. 无缓存数据账户的排序位置与改造前一致（不因缓存率垫底）。
5. `/accounts` 列表"用量(日)"出现缓存率 tag，数值与 usage-stats 页同账户"缓存读占比"口径一致（自然日）。
6. 停掉统计库读路径（mock 故障）→ 网关正常调度，决策日志显示缓存率维度跳过。

## 12. 风险与留观

| 风险 | 评估 | 缓解/预案 |
| --- | --- | --- |
| 流量向高缓存率账户集中，触发上游限速 | 设计意图内的倾斜；单账户过载有既有可靠性等级、账户电路与限速语义兜底，流量自动回流 | 观测 `gateway_dispatch_decision` 首选分布与上游 429 率；必要时调大 `CacheRateDeadband` |
| 授权账户 scope 归属与预期不符 | 第 8.2 节核实项 | 实施第一步做数据核实后再写注入逻辑 |
| 高并发组路径覆盖不全 | 第 8.2 节核实项 | 若存在独立比较器，同规则复用并补测试 |

| 同层切换频率异常 | 第 6 节留观项 | 触发标准：首选账户切换频率显著高于改造前基线；届时再评估在位滞回 |
