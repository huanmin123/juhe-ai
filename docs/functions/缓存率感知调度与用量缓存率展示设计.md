> 状态：设计稿 v2（2026-10-08），未实施。本文是该功能的唯一契约入口；实施交付时必须按第 13 节清单同步各权威文档，本文随实施状态更新。
>
> 修订记录：
> - v1（2026-10-07）：初稿。
> - v2（2026-10-08）：吸纳外部复审意见重构——①层内排序由两两死区比较改为满足严格弱序的全局排序键（速度合格集 + 缓存率量化档），消除循环胜负与输入序依赖（P0）；②速度信号改为 EWMA 毫秒单信号，P95 恢复其现状语义（桶索引次级比较），禁止毫秒与桶索引互算（P1）；③缓存率 scope 由"待核实"升级为粒度裁决：物理账户级混合缓存率，语义与局限明示（P1）；④快照增加最大陈旧时间与失效语义（P1）；⑤展示口径前提、公共组件边界、列表 DTO 契约、小时桶近似窗口、异常数据规则、组件测试清单逐项补齐。
>
> 动机：上游计价对缓存命中高度敏感——缓存率越低，实际输入单价越高（部分上游缓存率每降低约 10 个百分点，实际价格约提升 4 倍）。倍率低的账户若缓存差，换算后的真实成本反而更高。当前调度在同层只比较可靠性与首字速度，完全不感知缓存命中；本设计把"缓存率"作为同层速度接近时的决胜维度，并在账户列表展示今日缓存率。

## 1. 现状事实（代码基线，均已核实）

以下事实是本设计的出发点，实施时如代码已演化，以代码为准并回填本文。

1. **同层排序的权威位置**：`/v1` 候选的最终同层排序在热质量层 `backend-go/projects/gateway/internal/gatewayhotquality/selection.go` 的 `compareWithinTier`（约 585 行），调用方对候选做 `sort.SliceStable` 排序。层（tier）由 `模型秩 | fallback | super | priority` 四元组构成，"同优先级"在代码上就是同层。当前层内维度顺序：
   1. 可靠性等级（`reliabilityLevel`）；
   2. 有效可靠性数值（`effectiveReliability`）；
   3. 首字速度（双方均有样本时：`FirstByteEwma5m`，EWMA 平局时 `FirstByteP95Bucket10m`）；
   4. `StableBindingOrder`（稳定绑定序）；
   5. 账户 ID / 原始下标（确定性兜底）。
2. **速度信号的两个量纲**：`FirstByteEwma5m` 是毫秒浮点（`snapshot.go` `firstByteEwma`，由一分钟桶 `FirstByteSumMs / FirstByteSampleCount` 平滑而来）；`FirstByteP95Bucket10m` 是**直方图桶索引**（`snapshot.go` `p95HistogramBucket` 返回 `int64(index)`，桶界 `HotQualityFirstByteBucketUpperBoundsMS` 为 ≤1s/≤2s/≤5s/≤10s/≤20s/≤30s/≤60s/>60s 共 8 档）。现有 `compareSpeed` 中 P95 只在 EWMA 平局后做"桶索引对桶索引"的次级比较，两种量纲从不互算。**任何新逻辑不得把 P95 桶索引与毫秒阈值相减或比较。**
3. **层内排序必须满足严格弱序**：`sort.SliceStable` 的正确性以比较器的传递性为前提。任何"两两死区"式规则（如"A 与 B 速度接近则比缓存率"逐对生效）可产生 A<B、B<C、C<A 的循环，使排序结果依赖输入顺序——这是排序类改造的硬约束。
4. **速度比较对所有调度偏好生效**：`cost_first`（普通模式）下 `compareWithinTier` 同样比较速度 EWMA，不同账户速度平局罕见——若把缓存率简单排在速度之后，它在普通模式下几乎永远不生效。因此缓存率必须与速度联合裁决（第 5 节），不能简单追加。
5. **调度偏好机制**：`cost_first | speed_first`（`routestrategies/config.go`；普通/权重/故障回退/轮询路由共用，默认 `cost_first`）。快速模式的完整机制（首字截止 → 滑窗慢样本 → `latency_degraded` 降级 → 限次切号 → 恢复探针）已内置，权威文档为《普通路由速度优先延迟切换设计》。
6. **热质量层对所有组类型执行**（`preparation.go` `applyHotQualityOrder`，媒体 lane 豁免）；快速模式下降级账户整体后移发生在层间分段（`DecideHotQualityCandidate`），与层内比较正交。
7. **缓存数据链已全通**：上游解析 → `usage_records` 明细（`cache_read_tokens` 等列）→ jobs `usage-stats-aggregation` 每 60s 聚合 → 统计库 `usage_stats_hourly` / `usage_stats_daily`，两表均已有 `cache_read_tokens / cache_write_tokens / cache_write_1h_tokens` 列。**本设计不需要任何 schema 变更。**
8. **hourly 保留期**：`usageStatsHourlyRetentionDays` 默认 60 天，远大于滚动窗口需求。
9. **时区与小时桶**：聚合小时键 `stat_hour` 是**本地时区（`usageStatsTimezone`，默认 `Asia/Shanghai`）的 `YYYY-MM-DDTHH` 字符串桶**。按 `stat_hour >= cutoff` 回溯 24h 实际覆盖 24~25 个小时桶，是"小时桶近似滚动窗口"（第 3 节），不做小时内的边界精修。
10. **global/account 聚合行的语义**：`jobs/internal/statsagg/record.go` 对**每条**用量记录无条件追加一行 `{system_account_id='global', scope_type='account', scope_id=账户ID}`（record.go:66-68）。该行是该物理账户**全部流量**的混合总账——不区分调用方租户（owner / 授权调用方）、授权实例、模型、协议 profile、request lane。另有 owner 视角 `account` 行（带 `accountStatsSystemAccountID` 条件）与 `account_authorization` 行（授权调用方场景），可用于未来更细粒度升级。
11. **聚合的异常边界**：聚合侧对 input/cache 各 token 列只做**独立非负钳位**，不保证 `cache_read_tokens <= input_tokens`。异常上游可能产生缓存率 > 100% 的行，调度与展示必须各自定义处理（第 3、8、9 节）。
12. **列表投影缺口**：`accounts/list.go` `UsageSummary` 只有 `requestCount / totalTokens / totalCost` 三字段；SELECT 只投影 `request_count、input+output、success_cost_usd`。**列表 DTO 契约**：回归脚本 `frontend/src/scripts/regression/account-list-inline-dynamic-regression.ts` 明确断言列表 DTO 不得暴露完整用量对象（`usage`），展示缓存率的扩展必须只经 `todayUsage` 承载（第 9 节）。
13. **前端现成口径与公共组件**：`usageStatsHelpers.ts` 已有 `cacheReadRate()`，其分母是 **provider 感知**的（anthropic 或 `cacheReadTokens > inputTokens` 时分母为 `input+cacheRead+cacheWrite`，否则为 `inputTokens`）；`UsageSummaryTags.vue` 是被账户、分组、API Key、授权用户等页面共用的公共 tag 组件。当前供应商形态为 OpenAI 系（input 已含缓存命中），缓存率口径与 provider 感知分母的关系见第 3 节前提。
14. **调度消费现状**：网关任何调度路径目前不读取任何缓存指标。

## 2. 目标与非目标

### 2.1 目标

1. 同层、候选均健康时：与层内最快账户的首字速度差距在模式阈值内的候选构成"速度合格集"，集合内由缓存率分档决胜，缓存率高者优先；差距超过阈值的候选仍按速度排序。**速度是第一裁决维度，缓存率是速度接近时的决胜维度。**
2. 阈值分模式：普通模式（`cost_first`）10s；快速模式（`speed_first`）5s——快速模式速度权重更高，只给缓存率更小的上位窗口。
3. 层内排序必须满足严格弱序：结果与候选输入顺序无关、可复现。
4. 调度结果必须稳定：不因阈值边缘震荡、数据小幅波动或输入顺序出现同层账户间频繁切换（第 6 节）。
5. 账户列表"用量(日)"列新增今日缓存率 tag（第 9 节）。
6. 快速模式触发阈值后的既有行为（降级账户后移、限次切号、恢复探针）保持完全不变。

### 2.2 非目标

- 不改层级次序（模型秩、备用、超级优先、优先级）与分组层调度（轮询、权重、故障回退）。
- 不改会话粘性、同层探索、账户电路、慢样本状态机、媒体 lane 豁免。
- 不做实时/精确缓存率统计：读现成 60s 聚合 + 网关侧 60s TTL 快照，允许分钟级滞后（用户已明确接受延迟，但滞后有上限，见第 8 节 stale 语义）。
- 不新增 schema、不新增配置项或开关：全部参数为内置常量（第 10 节），调整通过文档修订 + 代码同改完成。
- 缓存率不做授权实例/模型/协议级分桶（粒度裁决见第 8.2 节）。
- `cache_write`（Anthropic 显式缓存写）不参与当前口径；未来接入 Anthropic 系供应商时按第 12 节扩展。

## 3. 术语与口径

| 术语 | 定义 |
| --- | --- |
| 缓存率 | `cache_read_tokens ÷ input_tokens`。**前提**：当前供应商形态为 OpenAI 系，上游 `input_tokens` 已含缓存命中部分，该口径与前端 usage-stats 的 provider 感知分母在 OpenAI 形态下一致。未来接入 Anthropic 系账户时，分母必须改为 `input + cache_read + cache_write`（与 `cacheReadRateDenominator` 对齐），且调度读侧需按 provider 分别聚合——在此之前本设计仅适用于 OpenAI 系候选 |
| 有效缓存数据 | 同时满足：滚动窗口内该账户 `input_tokens ≥ CacheMinSampleInputTokens`（10 万 token），且 `cache_read_tokens ≤ input_tokens`（异常数据判定，见下）。任一不满足视为"无有效缓存数据"，不参与缓存率裁决 |
| 异常数据 | 窗口聚合结果 `cache_read_tokens > input_tokens`（上游多报/聚合口径异常）。调度侧：该账户本周期数据作废、按无数据处理，加载器限频 WARN；不做截断、不改分母。展示侧：维持 usage-stats 页现状行为（provider 感知分母下可能 >100%），不在本设计内改变 |
| 调度窗口 | **小时桶近似滚动 24h**：统计库 `usage_stats_hourly` 按 `stat_hour ≥ cutoff` 求和，cutoff 按使用时区回溯 24h 的小时键。实际覆盖 24~25 个小时桶，属有意近似，不做小时级精修；`Asia/Shanghai` 无 DST，窗口稳定。不做自然日窗口——凌晨"今日"数据过少会产生噪声决策 |
| 展示窗口 | 自然日：`usage_stats_daily` 当日行，与"用量(日)"列语义一致。展示值与调度值允许不一致 |
| 数据行（调度） | `system_account_id='global' AND scope_type='account'`，`scope_id` = 物理账户 ID；粒度裁决与局限见第 8.2 节 |
| 缓存率档位 | 有效缓存率 `r` 的量化：`q = floor(r ÷ 0.10)`，取值 0..10；无有效数据 `q = -1`。档位粒度即原"10 个百分点死区"，量化是实现严格弱序的手段（第 5.3 节取舍说明） |

## 4. 总体规则（一句话）

> 同层候选在可靠性与有效可靠性分出高下之后：以层内最快 EWMA 为基准，与其速度差在模式阈值内的候选（含速度未知者）构成速度合格集，排在合格集之前；合格集内按缓存率档位（10pp 一档）降序，不合格集内按 EWMA 升序；仍平局落回 `StableBindingOrder` 稳定序（现行为）。

## 5. 调度排序规则（核心契约）

### 5.1 设计约束与算法选型

层内排序消费方是 `sort.SliceStable`，比较器必须满足严格弱序（反对称 + 传递）。逐对生效的速度死区（"两候选速度差 ≤ 阈值则比缓存率"）会产生循环胜负（例：A 1s/0%、B 7s/20%、C 13s/40%，10s 阈值下 B胜A、C胜B、A胜C），排序结果依赖输入顺序——**禁止**。本设计将"速度接近"从两两关系提升为**与层内基准的全局关系**，将缓存率死区从两两差值提升为**全局量化档位**，使每个候选获得一组全序标量排序键。

### 5.2 排序键序列（同层内依次比较）

| 键 | 比较方向 | 定义 |
| --- | --- | --- |
| 1 | 等级升序（healthy 优先） | `reliabilityLevel`（不变） |
| 2 | 数值降序 | `effectiveReliability`（不变） |
| 3 | 组别降序（合格集在前） | 速度合格集成员 = 1，否则 = 0。定义见 5.3 |
| 4a | 缓存率档位降序（合格集内） | `q = floor(r ÷ 0.10)`，无有效数据 `q = -1` |
| 4b | EWMA 升序（不合格集内） | 不合格集成员必有 EWMA（见 5.3），快者在前 |
| 5 | 升序 | `StableBindingOrder`（不变） |
| 6 | 升序 | 账户 ID → 原始下标（确定性兜底，不变） |

每个键都是全序标量/枚举，字典序复合严格弱序；`sort.SliceStable` 仅对全键相等的元素保持输入序，而全键相等已被键 5/6 唯一化，因此**结果与候选输入顺序无关**。

### 5.3 速度合格集定义

- 基准 `vBase` = 层内所有 EWMA 已知候选中的最小 EWMA（最快者）；层内无任何 EWMA 时全员合格。
- 候选 EWMA 已知：`(v − vBase) ≤ threshold` → 合格；`> threshold` → 不合格。
- 候选 EWMA 未知（无 5 分钟样本）：**恒合格**——速度冷账号保持中性，不因缺数据受速度惩罚（与现有 cold 语义一致）。
- 不合格集成员必为 EWMA 已知者，键 4b 恒可比较。
- **P95 的角色**：仅当参与比较的两候选 EWMA 均未知（同处合格集、`q` 同档落到键 5 之前无速度信息）时不引入新比较——本设计不再消费 P95 参与层内排序。现有 `compareSpeed` 的 P95 桶次级比较被缓存率档位与稳定序替代；这是行为变化点，在期二回归中显式验证（原"P95 平局裁决"场景改由 StableBindingOrder 决定）。

### 5.4 阈值与裁决示例

`threshold`：`cost_first` 10_000ms；`speed_first` 5_000ms（决策入口按 `Mode` 解析后传入）。

以 `cost_first`（10s）为例，层内三候选：A（EWMA 1s，缓存率 0%）、B（7s，20%）、C（13s，40%）：

- `vBase = 1s`；A 差 0s 合格（q=0）；B 差 6s 合格（q=2）；C 差 12s **不合格**。
- 排序结果：**B → A → C**。B 与基准速度接近且缓存率高于 A，胜出；C 虽缓存率最高但速度超出阈值，垫底。结果确定，与输入顺序无关。

### 5.5 量化档位的取舍说明

以 `floor(r ÷ 0.10)` 量化替代两两"差 ≥ 10pp 才分胜负"的死区：语义从"任意两候选差值比较"变为"全局 10pp 粒度分档"。边界效应：缓存率 9% 与 11% 分属 0、1 两档（差仅 2pp 也分出胜负）。这是满足严格弱序的必要代价；档位翻转只发生在缓存率跨越 10pp 整数边界时，而缓存率是 24h 慢变量，翻转频率天然低（第 6 节）。

### 5.6 决策可观测

`gateway_dispatch_decision` 决策日志在候选明细中补充候选级字段：`cacheHitRate`（窗口值，无有效数据省略）、`cacheQuantum`（档位，无数据为 -1）、`speedQualified`（是否合格集）；决策级字段补充 `speedBaseEwmaMs`（基准）与生效阈值。供线上核对排序行为与第 6 节留观指标的统计口径。

## 6. 稳定性与防抖设计

用户硬约束：不能频繁切换，要有策划地稳定。本设计不引入跨请求状态（第一版），依赖以下机制：

1. **算法确定性**：全局排序键（5.2 节）保证同快照输入恒得同序，与候选输入顺序无关——P0 级稳定性由算法本身保证。
2. **双重慢变量 + 量化**：速度基准与合格集判定基于 5 分钟 EWMA（已平滑）；缓存率档位基于滚动 24h 慢变量且量化到 10pp——档位翻转只发生在慢变量跨越档界时。快照以 60s TTL 刷新，排序输入变化频率被物理限制在分钟级。
3. **基准的唯一敏感点与自愈**：`vBase` 随层内最快账户变化，EWMA 平滑使其低频漂移；基准账户劣化时可靠性键（键 1/2）先于速度键介入，整体行为仍由既有机制兜底。
4. **会话粘性不受影响**：已建立会话由既有 affinity claim 钉住原账户（排序之后的提升机制），本排序只决定新会话/无绑定请求的首选。
5. **同层探索托底**：既有探索机制（credit + cursor，目标冷却 60s）继续给同层其他账户固定流量份额——低缓存率/新账户不会饿死，其缓存率数据持续积累。
6. **正反馈自稳定 + 既有兜底**：胜出账户获得流量 → 缓存命中维持 → 缓存率保持；若其被限速/出错，可靠性等级与账户电路（既有机制）立即把它降下去，流量自然回流。

**留观项（不实施，仅观察）**：上线后以 `gateway_dispatch_decision` 首选账户切换频率对照改造前基线；若仍观测到同层高频切换，再评估"在位账户滞回"（incumbent bias：现任账户仅在挑战者明确更优时让位，需跨请求状态）。触发条件、评估与实施另行修订本文。

## 7. 与既有机制的边界

| 机制 | 关系 | 说明 |
| --- | --- | --- |
| 快速模式降级/切号 | 正交，零修改 | 降级账户后移是层间分段（先于层内比较）；触发阈值、限次切号、恢复探针全部照旧。切号目标 = 剩余候选顺序第一个有空槽者，该顺序已含新排序——快速模式切号会在合格集中偏好缓存率高者，符合速度优先语义 |
| 会话粘性 | 不变 | 见第 6 节第 4 条 |
| 同层探索 | 不变 | 探索目标选择与配额不受缓存率影响；探索流量自然更新账户缓存率 |
| 高并发分组 | 生效，路径待实施核实 | 高并发组在亲和排序阶段有独立负载/并发维度（先于热质量层）；热质量层随后对所有组类型执行层内重排。实施时确认高并发组最终排序路径；若存在独立层内比较器，按同规则复用并补测试 |
| 媒体 lane | 天然豁免 | 热质量层对媒体 lane 豁免，缓存率维度不作用于音频/视频请求 |
| 数据缺失/失效 | 中性跳过 | 快照加载失败、快照超龄（第 8.1 节）、账户无有效数据时，缓存率相关键退化为中性（`q=-1` 或全员合格），排序回退现行为；不阻塞调度、不报错、不改变其他维度语义 |

## 8. 数据链与加载器契约

### 8.1 快照加载器（新增，gateway 进程内）

- **端口**：`CacheRateSnapshotSource`，返回 `{LoadedAt time.Time, Rates map[账户ID]{CacheReadTokens, InputTokens}}`；由组合根（`compose.go`）装配 adapter，读**统计库**句柄。
- **查询**（单条聚合 SQL，每刷新周期一次）：

```sql
SELECT scope_id,
       SUM(cache_read_tokens) AS cache_read_tokens,
       SUM(input_tokens)      AS input_tokens
FROM usage_stats_hourly
WHERE system_account_id = 'global'
  AND scope_type = 'account'
  AND stat_hour >= ?            -- cutoff：按 usageStatsTimezone 回溯 24h 的小时键
GROUP BY scope_id;
```

- **刷新**：singleflight + TTL 60s（`CacheRateSnapshotTTL`）；到点后台刷新，请求路径只读内存快照，零每请求 I/O。
- **陈旧上限（stale）**：快照带 `LoadedAt`；距最近一次成功刷新超过 `CacheRateSnapshotMaxStale`（10 分钟）即视为失效——缓存率维度整体退化为中性（第 7 节），不再参与排序，决策日志标记 `cacheRateStale=true` 并限频 WARN。连续失败不允许无限沿用旧数据。
- **失败语义**：刷新失败保留旧快照直至超龄；时区设置读取失败按聚合侧同源逻辑处理，不自行猜测。
- **注入**：`HotQualitySelectionSnapshot` 增加 `CacheHitRate *float64` 与 `CacheWindowInputTokens int64`（无有效数据保持 nil/0）；快照装配处按物理账户 ID 从内存快照注入。

### 8.2 缓存率粒度裁决（原"待核实"项，本版裁决）

- **裁决：第一版按物理账户粒度**，即消费 `global/account` 行。该行语义是该物理账户全部流量（跨调用方租户、授权实例、模型、协议 profile、lane）的混合缓存率（第 1.10 节）。
- **理由**：本功能的调度目标是"账户间上游缓存服务质量"比较（哪些账户/上游缓存能力差、真实成本高），物理账户正是调度候选与计费主体；用户已明确接受延迟与不精确。按授权实例/模型分桶需要跨行归并与 provider 上下文匹配，复杂度与收益不成比例，且热质量快照注入点以物理账户 ID 为键，天然对齐。
- **明示局限**：同一物理账户下多个授权实例（不同上游凭据）或差异极大的模型组合会互相稀释缓存率。**升级路径**：聚合已产出 owner 视角 `account` 行与 `account_authorization` 行（record.go:63-72），若实测同账户不同授权实例缓存率差异显著（以 `gateway_dispatch_decision` 与 usage 明细对照为准），再按授权实例粒度升级注入——届时先修订本文再改代码。
- **保留核实项**：①授权实例候选（runtime key 含授权上下文）注入时按候选行的物理账户 ID 匹配快照，实施时在装配代码中以测试固定该映射；②高并发组排序路径（第 7 节）。

## 11. 测试与验收

### 11.1 调度侧

- **严格弱序性质测试（P0）**：以第 5.4 节循环样本及其变体断言全序一致；随机生成候选集，断言任意输入排列产出相同排序（洗牌不变性）；断言比较器不自反为零除全等外无矛盾。
- 排序键单测（`gatewayhotquality` 包级）：5.2 节键序列逐键断言；阈值两模式（10s/5s）；EWMA 未知候选恒合格；`q=-1` 中性；档位边界（9%/11% 分档）；样本门上下；`cache_read > input` 数据作废。
- **P95 行为变化回归**：原"P95 平局裁决"场景改由 StableBindingOrder 决定的显式断言（第 5.3 节）。
- 加载器单测：TTL 内不重复查询、到点刷新、失败保留旧快照、**超龄失效**（stale 后维度中性 + 日志 + 决策标记）、cutoff 小时键按使用时区、scope 行过滤（global/account）。
- 注入与装配测试：候选快照带/不带缓存数据两种形态；授权实例候选按物理账户 ID 匹配（第 8.2 节核实项固定为测试）。
- 回归：既有 w1/w2/chain 排序与速度优先用例全绿（降级切号、探索、粘性零回归）；`gateway_dispatch_decision` 新字段断言。

### 11.2 展示侧

- 后端：列表投影回归（SQLite/PG 双 dialect）；DTO 拆分后 `usage` 三字段形状不变断言。
- 前端：`vue-tsc` 通过；第 9.3 节新增纯函数与组件测试全绿；回归脚本保持绿。

### 11.3 端到端验收标准

1. 同层、双账户健康、与基准速度差 ≤ 阈值、缓存率不同档 → 首选为缓存率档位高者。
2. 同层、与基准速度差 > 阈值 → 首选为速度快者（两种模式）；缓存率最高的慢账户不越位。
3. 任意候选输入顺序下排序结果一致（洗牌不变性）。
4. 快速模式触发首字截止 → 降级后移、限次切号行为与现状一致（既有回归护航）。
5. 无有效缓存数据账户的排序位置与改造前一致（不因缓存率垫底）。
6. `/accounts` 列表"用量(日)"出现缓存率 tag，数值与 usage-stats 页同账户"缓存读占比"（自然日）一致；无流量不渲染。
7. 快照超龄或统计库读故障（mock）→ 网关正常调度，决策日志标记 `cacheRateStale=true`，排序回退现行为。

## 12. 风险与留观

| 风险 | 评估 | 缓解/预案 |
| --- | --- | --- |
