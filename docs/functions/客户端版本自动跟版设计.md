# 客户端版本自动跟版设计

- 状态：已定稿（2026-10-08），PLAN-20261007T164058012Z 第一期行为契约权威来源
- 关联：[计划-20261007T164058012Z](../plans/计划-20261007T164058012Z-客户端版本自动跟版与请求特征加固.md)、[上游客户端身份版本覆盖](上游客户端身份版本覆盖.md)（手动键既有契约）

## 1. 目标与非目标

**目标**：客户端家族（codex/claudeCode/geminiCLI/zcode/grokCLI 五族）的伪装版本由 jobs 周期任务自动跟官方发布源，消除手写常量过期失效模式；版本事实收敛为单点，全部出站身份注入点消费生效值。

**非目标**：Grok 426 反应式跟版（证据闭合后第二期）；UA 格式改造（第二期，本设计只记录核实结论）；TLS 指纹、WebSocket 传输、版本滞后档位（留观）；不新增 env、不改 compose/部署面、不改管理端可写表单。

**硬约束（用户裁决）**：保全现有功能与用户体验——手动键契约、管理页行为、现有出站身份格式全部不变；自动值只影响"版本号"这一个变量。

## 3. 存储模型（两键三层）

| 键 | 所有权 | 契约 |
| --- | --- | --- |
| `upstreamClientVersionOverrides` | 管理页（人工） | **完全不变**：非空即生效、可升可降、清空回下一层（自动层该族有值则回自动，否则回内置；见《上游客户端身份版本覆盖》） |
| `upstreamClientVersionAutoOverrides` | jobs 跟版任务（自动） | 新增。同结构（键 ⊆ 五家族、值 `^\d+\.\d+\.\d+$`）、默认 `{}`；由任务独占写入，管理端 v1 不可写 |

**合并优先级**：手动 > 自动 > 内置，插入点 `identity.go` 的 `EffectiveClientVersion`（当前唯一合并点，全部版本/UA getter 与各消费点均经此生效）。

**新增 API（identity.go）**：
- `SetClientVersionAutoOverrides(map[string]string)`：同手动键的过滤语义（未知家族与非 semver 忽略），nil/空 = 清空自动层。
- `BuiltInClientVersion(family string) string`：导出内置常量（任务侧单调检查用；未知家族返回空串）。

**写者侧规则（任务内实现，非 storage 层）**：
1. 新值 < 该族当前自动值 → 拒绝该族、保留旧值、结构化日志（发布源回滚信号）。
2. 新值 < 该族内置值 → 拒绝该族、保留旧值、结构化日志（内置视为人工核实基线；人工跟版后自动层可再上升）。
3. 拒绝按族隔离，不影响其他族更新。
4. 无任何变化时跳过写库（不制造无谓 `updated_at` 变更）。
5. 单写者：任务经 jobregistry PG 租约串行；管理端不写该键，不存在读-改-写竞争。
6. 版本比较用任务包内三段整数比较；parser 已保证输入形状。

## 6. 任务契约

- 任务名：`upstream-client-version-refresh`（kebab-case，对齐注册表命名）。
- 调度参数（jobregistry）：Interval 24h；InitialDelay 37min（避让现有 31min 档内时隙）；PassiveJitter true（DayWindow 档 ±1h，每轮重随机）；Lane `external-account-maintenance`；Timeout 3min；BackoffBase 30min；BackoffMax 6h；LeaseTTL 2min；OverlapCoalesce true。
- 单轮：串行拉五源 → 逐源 parse/校验 → 汇总写者侧规则 →（有变化时）幂等 upsert 自动键 → 结构化日志事件 `upstream_client_version_refresh_completed`（逐源：结果/原始版本字段/解析值/动作/耗时）。
- 失败语义：单源失败仅该族跳过（保留旧值）；全部源失败 → 返回 error 交调度退避；部分成功 → 任务成功。
- 观测：v1 不新增表/键；逐源结果进结构化日志 + 任务运行历史（`background_task_runs`，框架自带）。per-family 上次成功时间持久化留第二期。

## 7. 管理面可见性（v1 决策）

自动键加入 settings 白名单与 `compatibleSystemSettingDefaults` 后，settings GET 自然返回该键值（接口可见、只读语义）；**不加入管理端可写目录/设置表单**（避免与自动写者竞争及 UX 变化）；前端展示留第二期（若做，只读字段）。此为本期工作量与风险控制的有意收敛（计划裁决 ④ 的降级条款）。

## 8. UA 身份核实结论（阶段 B 证据闭合）

**判定：混合身份（非任何官方 surface 的准确复刻）。**

证据链（openai/codex 开源源码，main 与 rust-v0.159.3 一致）：
- 官方机制：`initialize` 中 `originator = clientInfo.name`，UA 后缀 `({name}; {version})`，两者同源同值（`codex-rs/app-server/.../initialize_processor.rs`、`codex-rs/login/src/auth/default_client.rs`）。
- 官方两个真实 surface：`codex exec` → originator/前缀 `codex_exec/{v}` + 后缀 `(codex_exec; {v})`；Codex Desktop → `Codex Desktop/{core_v} (…) (Codex Desktop; {desktop_version})`（后缀是桌面版本号如 `26.901.x`）。
- juhe-ai 现状 `Codex Desktop/0.159.3 (Windows 10.0.22621; x86_64) unknown (codex_exec; 0.159.3)`：Desktop 前缀 + exec 后缀，开源可核实范围内无对应组合。
- 官方客户端**不发送独立 `version` 请求头**（版本只在 UA 内）；juhe-ai 现状一致，无需添加。
- 保留可能性（无证据）：Desktop 派生 `codex exec` 子进程且环境变量占用 originator 时可产生该组合。

第二期改造选项（待立项裁决）：
- A. 完整复刻 `codex exec` surface：originator 与前缀改 `codex_exec`，单版本号，无新版本源需求——**推荐**（成本最低，且 exec 是终端场景真实 surface）。
- B. 完整复刻 Desktop surface：需引入独立 desktop_version 跟踪（appcast 制品核验级工程）——成本高，除非有证据表明 Desktop surface 待遇更优。

**裁决（2026-10-08，用户）：A/B 均不采用，改为"源码锚定"——不追 Desktop，直接遵守开源 codex 源码的身份契约，并确立通用原则：身份画像一律优先以开源客户端源码为事实源**（codex=openai/codex ✓、grok-build=xai-org/grok-build ✓、ZCode=zai-org/ZCode ✓、gemini-cli=google-gemini/gemini-cli ✓；claude code 闭源，维持 npm 跟版）。

### 8.1 源码锚定的 exec surface 契约（本地 openai/codex 源码取证）

| 事实 | 源码证据（本地 `F:\temp-project\agent\openai-codex-main`） |

- 会话协议头（session-id/turn-metadata/beta-features 等）为 core 层协议头非 surface 身份，保持现状，登记观察项。

## 8.3 Grok 机制重构（第二期，采纳用户裁决：426 文案不作为数据源）

- **主机制 = 主动跟版**：与其余四族同型，从可行源拉官方最新版写 auto 键（版本自然 ≥ 服务端门槛，426 不应发生）。
- **426 降级为触发器，零解析**：白名单路径命中 426 → ①立即触发一次版本源刷新；②记录有界原始响应 + 人工告警；③刷新后版本无变化且持续 → 告警升级。上游文案变化只影响告警可读性，不影响行为。原 `minimumRequiredVersion` 字段方案作废。
- **主动源已定位（2026-10-08 实测）**：`https://raw.githubusercontent.com/xai-org/grok-build/main/crates/codegen/xai-grok-shell/Cargo.toml` 的 `version` 字段（CLI 主 crate，main 当前 1.0.45，紧贴最新发布 1.0.46；仓内 `changelogs/` 按版本存档可交叉核对）。GitHub 路径国内可达，与其余四源同路，**无需代理扩展**；`install.sh` 走代理方案降为备选。注意 `xai-org/grok-build` 不发 GitHub Release/tag，不能用 `releases/latest` 惯用接口。

**已实施（2026-10-08 第二期收尾）**：

- **第五源 grokCLI** 已加入 `versiontracking.Sources()`（家族键 `grokCLI`，五族末位，请求带 GitHub 标识 UA）。提取规则为**只取 `[package]` section 内的 `version` 键**：从 `[package]` 行起、到下一个行首 `[` section 头止；`[dependencies]` 等段的依赖版本行与 `[package.metadata]` 子表一律忽略，且不作"全文第一个 version 行"假设——文件布局可变，`[patch.crates-io]`/`[workspace]` 可出现在 `[package]` 之前（section 头去行尾注释后须精确等于 `[package]`）。校验 `^\d+\.\d+\.\d+$`，缺失/非法返回带原因 error。单调规则经既有 `decideAction` 自动生效（`BuiltInClientVersion("grokCLI")` 已存在），`refresh.go` 无逻辑改动。
- **426 触发器** 已落在 jobs xai worker（`worker_xai_grok_usage.go`）。判定点为 `fetchXAIGrokJSON` 非 2xx 分支（状态码与响应体均可得的最小侵入点），命中 HTTP 426 时：①记结构化告警日志 `grok_version_gate_426_observed`（`status_code` + ≤300 字节响应体原文摘录 `response_excerpt` + 当前生效 grokCLI 版本 `grok_cli_version`，零解析文案，每次 426 均记）；②经装配字段 `workerAssembly.upstreamClientVersionRefresh`（`wireVersionTrackingFamily` 赋值、登记 disabled 时保持 nil，消费侧 nil 安全）即时异步触发一次版本刷新，冷却 ≥10 分钟（`atomic.Int64` UnixNano 时间戳 CompareAndSwap 去重，防 426 风暴；冷却内 426 日志照记但不重触发）；刷新失败仅记 `grok_version_gate_426_refresh_failed`，不改变原请求错误返回与快照落库语义。本步未实施 §8.3 的"③刷新后版本无变化且持续 → 告警升级"（留待 426 运行证据闭合后立项）。

## 9. 抖动审计结论（阶段 D）
