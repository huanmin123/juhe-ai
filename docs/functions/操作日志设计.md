# 操作日志设计

> 面向后端、前端、存储和 AI 维护者。
> 本文定义 `juhe-ai` 的业务操作日志能力，用于追溯系统内资源被谁新增、修改、删除、绑定、授权或配置变更。操作日志不同于原始审计日志、普通运行日志和使用记录，只记录已经提交成功的业务状态变更。

## 文档目标

- 明确操作日志的产品边界：记录真实业务变更，不记录查询。
- 固定用户和管理员的可见范围，满足“凡是和我有关的操作我可以看到，管理员可以看全部”。
- 给后端提供统一接入方案，避免在每个前端按钮或每个路由里散落手写日志。
- 固定操作日志的存储字段、脱敏规则、接口和页面入口。
- 区分操作日志、原始审计日志、普通运行日志和使用记录，避免不同日志能力互相污染。

## 模块定位

操作日志回答这些问题：

- 谁在什么时候改了系统里的什么资源？
- 是用户自己操作，还是管理员在管理范围内操作了某个用户的资源？
- 操作前后哪些安全可展示字段发生了变化？
- 这个操作影响了哪些系统账户，为什么这些账户可以看到它？
- 后续排查“谁改错了配置或删错了资源”时，能否还原关键上下文？

操作日志不回答这些问题：

- 某次网关请求原始 headers、body、上游响应是什么。这个属于 [原始审计日志设计](原始审计日志设计.md)。
- 某次模型调用消耗多少 token、成本是多少。这个属于使用记录和统计缓存。
- 某个后端异常堆栈、任务执行详情或 debug 信息是什么。这个属于普通运行日志和日志搜索。
- 用户看过哪些页面、查过哪些列表、打开过哪些详情。查询不属于操作日志。

## 日志分类边界

主流实践上，操作日志应放在应用层统一生成，而不是依赖前端按钮或基础设施日志。OWASP Logging Cheat Sheet 强调应用日志应保持一致，记录每个事件的 when / where / who / what，并避免把访问令牌、密码、密钥等敏感数据直接写入日志。NIST SP 800-92 则把日志管理视为生成、传输、存储、访问和处置的完整流程，用于支撑安全事件调查、运维问题定位和保留周期要求。本设计按这些原则落地为“后端统一记录、状态变更才记录、敏感数据只存摘要、按影响用户控制可见范围”。

| 能力 | 主要目的 | 记录内容 | 可见范围 |
| --- | --- | --- | --- |
| 操作日志 | 业务变更追溯 | 增删改、启停、绑定、授权、配置变更等状态变化 | 用户看与自己有关；管理员看全部 |
| 原始审计日志 | 网关链路排障 | 客户端请求、上游请求、上游响应、最终返回原文 | 仅管理员 |
| 普通运行日志 | 运行排障 | 结构化事件、错误摘要、后台任务状态 | 仅管理员 |
| 使用记录 | 调用明细与统计事实源 | 模型请求、用量、成本、账号命中、错误摘要 | 调用方和管理员按权限查看 |

## 记录边界

### 必须记录

只记录已经提交成功、会改变业务状态的操作：

- `create`：新增系统账户、AI 账户、分组、API Key、代理、团队、公告等。
- `update`：修改名称、状态、额度、到期时间、绑定关系、策略和说明等。
- `delete`：删除 AI 账户、分组、API Key、代理、公告等允许删除的资源。
- `enable` / `disable`：启用、停用资源或系统账户。
- `bind` / `unbind`：账户绑定分组、API Key 绑定分组、授权账户加入自有分组等。
- `authorize` / `revoke_authorization` / `return_authorization`：创建、修改、暂停、恢复、回收或归还统一授权。
- `add_member` / `remove_member`：团队成员变化。
- `publish` / `unpublish`：公告发布、下线。
- `change_password` / `reset_password`：用户修改自己密码、管理员重置系统账户密码。
- `update_settings`：全局品牌设置、系统运行设置、统计保留策略等配置变更；原始审计日志策略固定，不属于系统设置变更。
- `test` / `detect`：只有当测试或检测会写入状态、检测结果、最近检测时间、快照或错误状态时才记录。
- `migrate`：手动迁移账户流量、批量移动资源等有持久化副作用的操作。

### 禁止记录

查询不属于操作日志：

- `GET` 请求一律不写操作日志。
- 列表查询、分页、筛选、搜索、详情查看、下拉选项读取不写操作日志。
- 查看原始审计详情、查看运行日志、查看使用记录不写操作日志。
- 前端页面打开、菜单切换、表格排序、弹窗打开不写操作日志。
- 只生成临时内容且不落库的动作不写操作日志，例如生成 OAuth 授权链接。

如果后续需要追踪敏感读取行为，应另建“安全访问日志”，不能把查询行为混入操作日志。

### 失败操作

操作日志默认只记录已经提交成功的变更。参数校验失败、权限失败、资源不存在、唯一约束冲突等未改变业务状态的请求不进入操作日志。接入防重复提交后，被内存缓存拦截的重复提交也不进入操作日志。

如果某个操作包含多步业务变更，应把业务表变更放在同一个业务库事务内提交。当前后端通过 `runLoggedOperation()` 包装核心同步写操作：先提交业务库事务，提交成功后再把操作日志投递给 background worker 队列，由 worker 批量写入统计数据集库的 `operation_logs` / `operation_log_targets` / `operation_log_viewers`。操作日志属于追溯数据，入队或落库失败不能反向回滚已经提交成功的业务数据；外部网络调用类操作先完成外部调用，再同步提交本地业务变更，最后投递操作日志。

## 可见范围

### 管理员

管理员可以查看全部操作日志，包括：

- 所有用户自己的操作。
- 管理员在管理侧操作任意用户资源。
- 系统级配置、公告、代理、供应商、运行策略等全局资源变更。

管理员列表支持按操作人、影响用户、资源类型、模块、动作、时间、关键词和 trace ID 筛选。

### 普通用户

普通用户只能看到与自己有关的操作日志：

- 自己发起的操作。
- 管理员在管理侧操作自己名下资源，例如管理员修改了自己的 AI 账户、分组、API Key 或授权。
- 自己拥有的资源被授权、回收授权、加入分组、解绑或删除。
- 授权给自己的资源发生影响使用权的变化，例如授权被暂停、恢复、回收、归还、到期时间或额度被修改。
- 自己授权出去的资源发生授权关系变化。
- 自己所在团队的成员关系或团队授权发生变化。
- 影响全员的系统设置、全局品牌设置和已发布公告变化。
- 影响自己资源使用的全局运维资源变化，例如管理员修改了自己 AI 账户正在使用的代理配置。

普通用户看到的日志必须按可见等级脱敏。对于系统设置、代理、错误策略等管理员资源，用户只能看到安全摘要，不能看到不可见配置明细。后端接口必须执行裁剪，不能只依赖前端隐藏；`summary` 级日志不返回字段差异、影响对象、可见用户、请求路径、客户端 IP 或 User-Agent。

### 可见原因

当前可见原因使用稳定枚举：

- `actor_self`：本人发起。
- `resource_owner`：本人是资源所有者。
- `admin_managed_my_resource`：管理员操作了本人资源。
- `authorization_owner`：本人授权出去的资源发生授权变化。
- `authorization_grantee`：授权给本人的资源发生变化。
- `team_member`：本人所在团队成员关系变化。
- `team_authorization`：本人所在团队的资源授权变化。
- `global_affected`：全局设置、全员公告或全局策略影响所有登录用户。
- `bound_resource_affected`：本人资源绑定的全局运维资源发生变化。

## 操作语义

操作日志必须使用稳定的机器枚举和中文展示文案分离：

| 字段 | 示例 | 说明 |
| --- | --- | --- |
| `module` | `accounts`、`groups`、`api_keys`、`settings` | 模块枚举，机器可读 |
| `action` | `create`、`update`、`delete`、`authorize` | 动作枚举，机器可读 |
| `operationKey` | `accounts.update` | 模块和动作组合，便于查询和排查 |
| `resourceType` | `account`、`group`、`api_key` | 主要资源类型 |
| `resourceId` | `acct_xxx` | 主要资源 ID |
| `resourceName` | `OpenAI 主账号` | 安全可展示名称快照 |
| `summary` | `管理员修改了用户 张三 的 AI 账户：OpenAI 主账号` | 中文摘要 |

当前覆盖这些模块：

| 模块 | 典型动作 | 主要资源 | 影响用户 |
| --- | --- | --- | --- |
| 系统账户 | 创建、编辑、启停、重置密码 | 系统账户 | 被操作账户本人、管理员 |
| AI 账户 | 创建、编辑、删除、绑定分组、测试状态写入、流量迁移 | AI 账户 | 账户所有者、授权使用者 |
| 分组 | 创建、编辑、删除、绑定账户 | 分组 | 分组所有者、授权使用者 |
| API Key | 创建、编辑、删除、启停、额度修改 | API Key | API Key 所有者 |
| 统一授权 | 创建、修改、暂停、恢复、回收、归还 | 授权记录 | 资源所有者、被授权用户、团队成员 |
| 系统团队 | 创建、编辑、启停、成员变化 | 团队、团队成员 | 团队成员 |
| 代理 | 创建、编辑、删除、检测结果写入 | 代理 | 管理员；绑定该代理的账户所有者看安全摘要 |
| 系统设置 | 修改全局设置、系统设置 | 设置项 | 全员或管理员，按设置类型决定 |
| 公告中心 | 创建、编辑、发布、下线、删除 | 公告 | 已发布或下线公告影响全员；草稿变更仅管理员 |

## 变更内容

操作日志应记录字段级安全差异，但不保存完整请求体。

当前 `changesJson` 结构：

```json
[
  {
    "field": "status",
    "label": "状态",
    "before": "active",
    "after": "disabled",
    "sensitive": false
  },
  {
    "field": "credentials",
    "label": "账户凭据",
    "before": "未变更",
    "after": "已变更",
    "sensitive": true
  }
]
```

规则：

- 只记录业务字段，不记录完整请求体。
- 字段名使用稳定枚举或后端字段路径，展示标签使用中文。
- 未变化字段不记录。
- 敏感字段只记录“已变更”“已清空”“已设置”“尾号变更”等摘要。
- 删除操作可以保存资源的安全快照，例如名称、状态、归属、绑定关系和创建时间，但不能保存凭据、token、代理密码或完整 API Key。
- 系统设置变化只保存允许展示的设置项和摘要；普通用户可见时进一步降级为“系统运行设置已变更”等安全摘要。

## 脱敏规则

以下内容禁止进入操作日志：

- 上游 API Key、OAuth access token、OAuth refresh token、代理密码、会话 token、验证码、登录密码。
- 本地 API Key 完整明文；只能记录资源 ID、名称、前缀、尾号或“密钥已重新生成”。
- 原始请求体、原始响应体、完整 headers、Cookie、Authorization。
- 使用记录里的模型输入输出内容。
- 原始审计日志 payload。

敏感字段差异统一由后端脱敏工具处理，不能由前端决定。新增字段时必须先判断敏感级别，再注册差异展示策略。

## 统一接入方案

操作日志不在前端按钮里写。当前后端通过请求上下文、写操作结构化日志参数和统一操作日志服务三层能力接入。

### 请求上下文

复用现有请求上下文和登录态：

- `traceId`
- `actorSystemAccountId`
- `actorUsername`
- `actorDisplayName`
- `actorRole`
- `sessionId`
- `clientIp`
- `userAgent`
- `method`
- `path`

管理员通过管理侧接口操作某个用户资源时，必须同时保存：

- `actorSystemAccountId`：真实登录管理员。
- `operationScopeSystemAccountId`：本次业务操作作用域，例如 `systemAccountId` 查询参数指定的用户，或资源真实 owner。
- `actorRole`：真实角色。
- `mode`：`admin` 或 `self`，用于区分管理员在管理侧操作和管理员在用户模式操作自己资源。

### 写操作结构化日志参数

每个业务模块在成功写操作附近传入结构化日志参数，而不是在前端按钮里写日志。参数包含：

- `operationKey`
- `module`
- `action`
- `resourceType`
- `resourceId`
- `resourceName`
- `summary`
- `changes`
- `targets`
- `viewers`
- `visibilityScope`
- `detailLevel`
- `recordCondition`

`recordCondition` 由业务代码在调用 `runLoggedOperation()` 或 `recordOperationLog()` 前判断。例如 `POST /__aisys__/api/openai-oauth/auth-url` 生成临时授权链接，不记录；账户测试只有在写入状态、检测结果、快照或错误状态时才记录。

### 操作日志服务

后端提供统一服务，例如 `recordOperationLog()` 或 `runLoggedOperation()`：

1. 从请求上下文读取操作人、traceId、IP。
2. 读取变更前安全快照。
3. 执行业务变更。
4. 读取变更后安全快照。
5. 计算安全 diff、资源摘要和影响用户。
6. 业务库提交成功后，把操作日志、目标资源和可见用户投递给 background worker 队列。
7. 返回业务响应。

当前落地约定：

- 核心同步写操作优先使用 `runLoggedOperation()`，包括系统账户、AI 账户、分组、API Key、统一授权、系统团队、代理、系统设置和公告中心的新增、修改、删除、绑定、发布等动作；`runLoggedOperation()` 只保证业务库同步提交，操作日志在提交后异步入队。
- 需要防重复提交的写接口由 [幂等与唯一约束设计](幂等与唯一约束设计.md) 统一约束；后端先用内存短 TTL 缓存拦截同一用户、同一接口、同一资源指纹的重复提交，只有真实业务变更进入 `runLoggedOperation()`。
- `afterCommit` 只放运行时缓存清理、会话亲和迁移等非数据库副作用，避免事务回滚后缓存已经被提前改变；操作日志入队也发生在业务提交之后，提交后副作用失败只写普通运行日志，不反向影响已经提交成功的业务响应。
- 外部调用类接口不把网络请求放进数据库事务；拿到外部成功结果后，再同步提交本地业务写入，最后投递操作日志。
- 查询接口、详情接口、筛选和分页不调用操作日志服务。

不使用数据库触发器记录操作日志。触发器能看到表变化，但不知道业务动作、登录用户、管理员作用域、影响用户和中文摘要。

## 存储设计

### `operation_logs`

主表保存一条业务操作事件。

当前字段：

- `id`
- `trace_id`
- `actor_system_account_id`
- `actor_username`
- `actor_display_name`
- `actor_role`
- `operation_scope_system_account_id`
- `mode`：`self`、`admin`
- `module`
- `action`
- `operation_key`
- `resource_type`
- `resource_id`
- `resource_name`
- `summary`
- `detail_level`：`full`、`summary`
- `visibility_scope`：`targeted`、`all_users`、`admin_only`
- `changes_json`
- `metadata_json`
- `method`
- `path`
- `status_code`
- `client_ip`
- `user_agent`
- `created_at`

### `operation_log_targets`

记录本次操作涉及的资源，便于按资源反查。

当前字段：

- `id`
- `operation_log_id`
- `target_type`
- `target_id`
- `target_name`
- `target_owner_system_account_id`
- `relation`：`primary`、`affected`、`created`、`deleted`、`owner`、`grantee`、`team_member`、`bound_resource`
- `created_at`

### `operation_log_viewers`

预计算普通用户可见性，确保资源删除、授权回收 / 归还或团队成员变化后，历史日志仍按当时关系可见。

当前字段：

- `operation_log_id`
- `system_account_id`
- `visibility_reason`
- `detail_level`
- `created_at`

全员可见的安全摘要日志可使用 `operation_logs.visibility_scope = 'all_users'`，不必给每个用户展开一行，也不写入 `operation_log_viewers`；用户侧查询时合并 `all_users` 和 `operation_log_viewers` 命中的日志。普通用户接口必须把 `all_users` 强制降级为摘要级，避免未来误配置为完整详情时泄露系统配置明细。

### 当前索引

- `operation_logs(created_at, id)`：默认分页。
- `operation_logs(actor_system_account_id, created_at, id)`：按操作人筛选。
- `operation_logs(operation_scope_system_account_id, created_at, id)`：按业务作用域筛选。
- `operation_logs(module, action, created_at, id)`：按模块和动作筛选。
- `operation_logs(resource_type, resource_id, created_at, id)`：按主资源追溯。
- `operation_logs(resource_id, created_at, id)`：按主资源 ID 直接定位。
- `operation_logs(visibility_scope, created_at, id)`：用户侧合并全员摘要日志。
- `operation_logs(trace_id)`：按链路 ID 关联运行日志。
- `operation_logs(trace_id, created_at, id)`：按 trace ID 前缀定位时保持稳定分页。
- 操作日志关键词搜索不维护单独搜索影子表；`keyword` 直接对 `operation_logs` 的摘要、资源名、资源 ID、操作人、操作键、模块和动作等字段做普通 SQL 模糊匹配。
- `operation_log_targets(target_type, target_id, created_at)`：按任意受影响资源反查。
- `operation_log_viewers(system_account_id, created_at, operation_log_id)`：用户侧按可见集合读取。
- `operation_log_viewers(system_account_id, operation_log_id)`：用户侧当前页详情级别裁剪。
- `operation_log_viewers(operation_log_id, system_account_id)`：详情权限校验。

用户侧列表优先由 `operation_log_viewers.system_account_id` 命中的可见集合驱动，再与 `visibility_scope = 'all_users'` 的全员摘要集合合并；避免日志总表增长后普通用户列表只能从 `operation_logs` 主表按时间扫描。列表接口只返回摘要字段，不解析 `changes_json` / `metadata_json`，详情接口再按权限读取字段差异和影响对象。

## 接口设计

操作日志查询接口本身属于查询行为，不写操作日志。

用户侧：

- `GET /__aisys__/api/my-operation-logs`：当前用户查看与自己有关的操作日志。
- `GET /__aisys__/api/my-operation-logs/:id`：当前用户查看自己可见的操作日志详情。

管理侧：

- `GET /__aisys__/api/operation-logs`：管理员查看全部操作日志。
- `GET /__aisys__/api/operation-logs/:id`：管理员查看任意操作日志详情。

当前查询参数：

- `page`
- `pageSize`
- `keyword`
- `module`
- `action`
- `resourceType`
- `resourceId`
- `actorSystemAccountId`
- `affectedSystemAccountId`
- `operationScopeSystemAccountId`
- `startAt`
- `endAt`
- `traceId`

普通用户接口必须忽略或禁止跨用户筛选参数。管理员接口可以筛选操作人、影响用户和业务作用域。

管理员列表可以返回摘要和安全 diff；普通用户列表和详情必须按 `detailLevel` 以及当前 viewer 的 `detail_level` 裁剪。用户侧 `summary` 级只返回时间、模块、动作、操作人、资源摘要、中文摘要和 trace ID 等安全摘要；用户侧 `full` 级可以返回完整安全 diff 和相关目标资源，但仍不返回可见用户列表、客户端 IP 或 User-Agent。管理侧详情可以返回完整安全 diff、目标资源列表和可见原因，但仍不能返回敏感字段。

## 前端页面

当前入口：

- 用户侧：`我的操作日志`
- 管理侧：`操作日志管理`

用户侧展示：

- 操作时间
- 操作人
- 模块
- 动作
- 操作摘要
- 与我有关的原因
- 关键变更摘要

管理侧额外展示：

- 操作人账号
- 业务作用域用户
- 影响用户
- trace ID
- IP 和 User-Agent 摘要

列表不展示 `operationKey`、HTTP 方法、请求路径、资源类型和资源 ID 等技术字段；这些字段只在详情中作为追溯元数据展示。资源名称在列表中不作为独立列重复展示，优先由中文摘要承载，避免“资源”和“摘要”重复。

页面文案、空态、筛选项、表格列和详情抽屉必须保持中文。查询和翻页不产生操作日志。

## 数据保留

操作日志体积远小于原始审计日志，且用于长期追溯，默认保留周期应长于使用记录和原始审计日志。

当前默认值：

| 配置 | 默认值 | 说明 |
| --- | --- | --- |
| `operationLogEnabled` | `true` | 是否启用操作日志 |
| `operationLogRetentionDays` | `365` | 操作日志默认保留 365 天 |
| `operationLogMaxChangesPerRecord` | `100` | 单条日志最多保存的字段差异数量，超过后折叠摘要 |

清理任务统一接入 `data-retention-cleanup`，只按时间清理操作日志，不按资源删除历史日志。删除资源不应删除历史操作日志。

## 当前能力清单

- `GET` 请求不写操作日志。
- 普通查询、列表、筛选、详情查看、日志查看不写操作日志。
- 已接入的成功状态变更会在业务库提交后投递操作日志队列，并由 worker 写入统计数据集库。
- 失败且未提交的操作不写操作日志。
- 管理员可以查看全部操作日志。
- 普通用户只能查看自己发起、自己资源、授权关系、团队关系或全局影响相关的日志。
- 管理员操作某个用户资源时，日志同时保留真实管理员和被影响用户。
- 系统设置和全局运维资源对普通用户只展示安全摘要。
- 敏感字段不会进入 `changes_json`、`metadata_json`、摘要或运行日志。
- 删除资源后，历史操作日志仍可按当时资源名称、资源 ID 和影响用户追溯。
- 操作日志详情可通过 `traceId` 关联普通运行日志，但不暴露原始审计 payload。
- 数据保留清理只按时间清理操作日志，不因资源删除而级联删除历史记录。
