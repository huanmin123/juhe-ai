# 上游模型漂移防护与加密上下文失效治理设计

> 状态：2026-10-09 详细契约修订并通过 A/B 有界独立复审（无文档实施 blocker）。观测证据、状态机、参数、版本隔离与展示边界已明确；代码实施未开始，真实 Redis 原子性、接口装配与回归须在实施时验收。上下文承接过滤（批次 C）**维持冻结**，不随 A/B 契约收口解禁。
>
> 本文只解决一个问题：上游把请求模型交给其他模型应答（"偷换模型"）时，其响应携带的加密上下文等上游 opaque 状态可能与请求模型域不匹配，调度切到其他上游继续同一会话即被拒绝。本文建立**模型声明异常观测与漂移登记**，使这类失效可观测、可解释；**上下文承接过滤**（凭指纹隔离候选）因兼容性依据不足暂被冻结（见 2.3 节）。上游偷换模型本身是上游侧行为，网关无法阻止其发生（边界见 1.3 节）。
>
> 关联文档：调度引擎内核通用化（通用排除集、同层让位 + 翻回）见 [调度内核通用化设计](调度内核通用化设计.md)。观测能力的现有契约见 [上游响应模型不一致审计](上游响应模型不一致审计.md)，本文的归一化比较**仅用于漂移判定与登记计数，不改变该审计的展示比较口径**（2.1 节）。

## 0. 复审修订记录（2026-10-09）

外部三路复审否决了初版的两条核心推理，本文据此修订：

1. **"模型名一致 ⇒ 加密上下文兼容"不成立**（已从设计中移除）。归一化模型名是上游自报字符串：两个独立上游可都自报 `gpt-*` 而使用不同加密/状态域；偷换模型的上游也可以继续自报请求模型原名，完全绕过基于模型名的检测。官方协议资料（OpenAI reasoning 文档）说明 encrypted reasoning 可传给后续调用，但**未提供"同模型名即可跨账户解密"的保证**。
2. **"密文绑定真身模型"目前是工作假设，未经运行时证据确证**。现有证据（0289 档案的"encrypted_content 只有生成它的上游账户能解密"）支持"跨上游上下文被拒"的观察，但绑定机制的精确形态（密钥域、模型域、账户域）无本地可证结论。
3. 初版"承接门第四门"存在准入旁路（SwitchTarget 未冻结即放行、冻结源同账户无条件保留，见 2.3 节冻结理由），且以会话亲和当前绑定充当密文来源凭证（亲和绑定可迁移，见 1.2 节）。

因此本文将能力拆为两部分：**响应声明异常观测**（详细契约见 2.1/2.2 节）与**上下文承接过滤**（冻结，待证据）。任何把"指纹一致"当作放行依据的表述一律不成立；本期登记只说明响应声明与实际发送模型是否相符，不证明真实模型身份或上下文兼容性。

## 1. 背景与根因

### 1.1 问题形态

用户观察与代码证实结合：部分上游会将请求模型交给其他模型应答（如 gpt 请求由 grok 等 Responses 兼容模型服务，"偷换模型"）。其响应中的 `encrypted_content` 等上游 opaque 状态与请求模型域不匹配的风险随之存在；`docs/bug/问题-0289-Codex加密上下文流内失败漏给客户端致死重试.md` 已确认"encrypted_content 只有生成它的上游账户能解密"。当调度切到其他上游（或另一真身上游）继续同一会话时，历史上下文可能被上游拒绝（`encrypted_context_invalid` 等），触发 0289 恢复臂或直接失败。

**假设边界（重要）**：以上"绑定真身模型"的机制描述是工作假设。本设计的观测部分不依赖该假设成立（观测的是"声明与应答不一致"这一客观事实）；承接过滤部分依赖它，因此在证据补齐前冻结。

### 1.2 现状能力与缺口（全部已取证）

- **观测已有但不等于终态模型**：`UpstreamResponseModelSlot`（`backend-go/projects/gateway/internal/gatewaydispatch/upstreamdispatch.go:77-141`）记录上游响应模型；观测器取值语义为 `terminalModel ?? firstModel`（`backend-go/projects/gateway/internal/gatewayobs/upstreamresponsemodel.go:73-79`），**提前关闭、失败、不完整终态同样发布样本**（断流时的首个 model 声明也会成为返回值）。dispatch 侧挂载 `backend-go/projects/gateway/internal/gatewaydispatch/dispatchsingle.go:849-869`；组合根装配 `chain_compose.go:551-556` 与 `:802-823`。读取侧展示比对 `upstreamModelMismatch`（`backend-go/projects/gateway/internal/statreads/usagerecords.go:831-836`，TrimSpace 后精确 `!=`，存在别名噪声）。
- **裁决缺失**：观测值从不与请求模型比对产生调度/状态联动；全仓无 requested-vs-observed 校验点、无按账户的模型指纹登记。
- **事后止血**：0289 恢复臂每账户一次清理重放（`backend-go/projects/gateway/internal/gatewayresponse/encryptedrecovery.go:29-93` + `chain_v1_loop.go:570-600`、`:200-224`），信号白名单四码（`backend-go/projects/gateway/internal/gatewaycodex/encryptedcontent.go:27-36`）；未知错误形状依赖 BUG-0298 同签名即停止损。**注意：恢复臂的清理可能删除整个加密 compaction item，历史完整性不被保证**——本设计不承诺"历史完整"或"上下文失效已被彻底消除"。
- **事前约束与它们不是来源凭证的事实**：SwitchTarget 三门（`backend-go/projects/gateway/internal/gatewaydispatch/switchtarget.go:85-90`）只保证**配置层面**一致性，且未冻结时直接放行（`:310-311`）、冻结后对源账户无条件保留（`:322`）；外部 `previous_response_id` 只发原生 Responses 账号（`chatbridgestate.go:778`）；会话亲和是软排序，且**绑定可被整体迁移**（`backend-go/projects/gateway/internal/gatewaysession/affinity.go:495-517` 把绑定账户直接改为迁移目标）——**亲和当前绑定 ≠ 历史密文的生成账户**。

### 1.3 治理边界（重要）

上游偷换模型是上游侧行为，网关无法阻止其发生；加密上下文兼容性在本地没有可判定的充分条件。本设计的可达目标是：

1. **可观测**：把"声明与应答不一致"从纯展示升级为带接纳条件的状态化观测；
2. **可解释**：漂移登记使"上下文被拒"类故障在排查时有据可查；
3. **（冻结中）已知异常源隔离**：承接过滤仅在被冻结的四项前置条件补齐后才可能解禁（2.3 节）。

本文**不承诺**：消除全部上下文失效；历史完整性；"指纹一致即可安全承接"。

## 2. 目标设计

### 2.1 响应声明异常判定（通用观测，不参与路由）

#### 2.1.1 结构化证据与接纳规则

保留现有 `terminalModel ?? firstModel` 字符串槽位及所有使用记录消费者；新增旁路证据结果供本设计使用，不把旧槽位返回值强制改成终态模型。每个真实上游 attempt 独立记录：

- `observationId`：网关进程实例标识 + 请求标识 + 单次真实发送的 attempt 标识。Key 轮换、重试、不同 URL 均为不同 attempt；同一次发送的重复 verdict 使用同一标识。
- `expectedModel`：该 attempt 构造完成、实际发送 Body 的模型，不能用入口请求模型、其他尝试的映射或最终成功账户的模型代替。
- `protocol` / `endpointMode`，原始首声明与终态声明，声明所在事件类型；成功终态、干净 EOF、提前关闭、上游失败和响应层完整性裁决分别记录，不能把 EOF 直接认作业务成功。
- 原始声明冲突标志、解析错误/超限/覆盖不全标志。原有 observer 的 `completed` 仅表示解析 Finish，不能充当业务成功终态证据。
- 发送前捕获的账户调度 revision、归一化 revision、登记 epoch；结束时记录样本时间和最终接纳/剔除原因。

**本期协议范围固定为原生 OpenAI Responses JSON、Responses SSE 与 `/responses/compact` JSON。** Chat、Anthropic、Gemini 以及协议转换后的合成帧仍沿用旧展示观测，不参加本期连续计数。范围不靠开关控制；以后扩展须先补对应协议的接纳矩阵。

| 实际响应形态 | 成功结束证据 | 可计数的声明来源 |
| --- | --- | --- |
| Responses SSE | 原始上游 `response.completed`（或既有兼容 `response.done`），响应层确认完整成功，无后续失败/取消/断流；观察器看到完整终态事件 | 该成功终态 `response.model` 或其同语义顶层 `model`，两处同时存在须一致 |
| Responses JSON | 完整解析原始 JSON，`status=completed`，响应层成功且无 error | 该完整响应的顶层 `model` |
| compact JSON | 完整解析原生 compact 结果，具有合法 compaction 输出，既有响应层判定成功且无 error | 同一 compact 结果顶层 `model`；缺失则不接纳，不从请求模型补齐 |

以上均要求实际发送模型非空、声明非空、原始声明无冲突、模型观测所需帧解析完整。终态无模型但 `created` 有 X 时，只展示 X，计数剔除原因为 `model_without_terminal_evidence`。超限、解析失败、无法证明终态、失败、不完整、提前关闭均不接纳；多个不同原始声明按 `conflict` 单列，不因归一化后相等隐去原始冲突。注释帧/保活帧不构成解析失败。帧被现有大小上限跳过时必须暴露不完整原因，禁止增大无限缓存以实现该功能。

证据收集保持字节透传与现有时序；在 response verdict 和观察结束证据均就绪后结算一次。下游中断导致无法完成取证时只记剔除，不继续读完整上游来补样本。探针、账户人工测试及内部辅助派发只记录自身审计，不更新本登记，避免违反既有诊断无副作用契约。

#### 2.1.2 归一化、参数与状态机

归一化 revision 初始为 `1`：仅 `TrimSpace` 与大小写折叠，**初始别名表为空**。不自动删除日期后缀、不按模型家族归并、不把模型映射 LHS 当别名。这样无需猜测供应商别名契约；以后添加精确别名对必须附供应商依据与回放样本、先修本文，再更新 revision 并隔离旧状态。旧使用记录精确比较口径不变。

固定实现参数（常量，不新增配置项或功能开关）：异常登记 N=2、解除异常 M=2；两类连续序列的窗口均为 5 分钟；登记状态自最后接纳样本起保留 30 分钟。窗口从本轮序列首个样本提交起计算，严格大于 5 分钟先重置再处理当前样本，等于窗口可累加。时效在原子提交时检查 `storeNow - sentAt`，严格大于 30 分钟只展示/审计并剔除为 `observation_expired`，等于 30 分钟仍可接纳；包括及时完成但延迟回调的旧样本，不只检查响应耗时。sentAt 由发送前捕获的同一运行态权威时钟提供（memory 可注入时钟、Redis 服务时钟）；完成回调不能自报新的 sentAt。该限制不改变上游等待或超时。

状态只有 `unknown`（当前无接纳证据）、`observing`（已接纳但未确认异常）和 `declared_mismatch`（异常已登记）。字段包括异常序列计数/首时间、恢复序列计数/首时间、该异常周期的声明集合、首末接纳时间、最后声明、接纳/剔除统计。声明集合最多保留 8 个归一化名称，按提交顺序收集；第 9 个及之后设置 `modelsTruncated=true`，保持 mixed 事实，不把最后一个名称当唯一服务模型。恢复解除或 epoch 重建后集合清空。

| 当前状态与事件 | 确定转移和输出 |
| --- | --- |
| unknown / observing + 接纳的不一致 | 恢复序列归零；异常序列在 5 分钟内累加，否则当前样本起算 1；达到 2 进入 declared_mismatch，未达时为 observing |
| declared_mismatch + 接纳的不一致 | 保持异常，恢复序列归零；更新异常周期声明集合与最后样本，不必重新达到 N |
| unknown / observing + 接纳的一致 | 状态 observing，异常序列和待确认集合清空；登记最后接纳声明，不称“已证明健康” |
| declared_mismatch + 接纳的一致 | 异常序列归零；恢复序列按 5 分钟窗口累加；达到 2 切为 observing 并清空异常周期集合，未达保持异常 |
| 原始声明 conflict，且版本/epoch 有效 | 只增加 conflict 剔除计数，两个连续序列归零；已登记异常保持，不能当成一致恢复证据 |
| 失败/关闭/不完整/无声明/解析超限/超时效/不支持协议 | 仅剔除统计和审计；不接纳、不推进、不打断序列；不续状态 TTL，下一接纳样本仍受原窗口约束 |
| 连续不一致 X → Y | 达 N 后登记 mixed，集合含 X/Y；登记的是“连续不一致”而非“稳定的单一真实模型” |
| 同一 observationId 重复结算 | 不改变状态、计数、窗口或 TTL；仅一次有效结算 |
| TTL 到期 / 手动清除 / 调度 revision 或归一化 revision 变化 | 新 epoch，状态 unknown、序列/集合归零；旧 epoch 的在途结果不接纳、不重建旧登记 |
| 缓存丢失 / memory 重启 | 读为 unknown 并建立新 epoch；缺失 epoch 不由完成回调重建，必须由新的发送前捕获建立 |
| 并发乱序完成 | 按同维度原子提交的线性顺序计数；不声称发送顺序连续，也不等待较早请求完成；首次提交赋单调 sampleSequence |

单次不一致只留下当次事实与 observing 计数；N/M 仅是登记与解除门槛，第一次异常密文不受保护。不一致不改变当次响应、计费、失败分类、健康熔断或普通路由。

### 2.2 声明异常登记、原子更新与管理边界

**精确维度**固定为当前逻辑账户的 owner 作用域 + 账户运行态标识 + 路由策略 ID + 候选实际所属分组 ID + 供应商协议档案 + 精确 endpoint mode + 实际发送的上游模型 + 实际选中物理 Key 指纹（OAuth 使用运行态已有凭据身份）。不按入口模型猜测，不跨模型、Key、授权实例或路由维度合并计数；缺少必要维度则仅审计剔除。指纹使用既有内部脱敏身份，不保存原始凭据。

每次发送前捕获账户级 `accountEpoch` 和该维度的 `(dispatchRevision, normalizationRevision, dimensionEpoch)`；epoch 均为不可复用随机标识。读取时校验当前账户调度 revision；改配置后完成的旧尝试必须因 revision 不符被拒绝。账户清除、配置 revision 变化、控制记录丢失/重建旋转 accountEpoch；维度 TTL 到期仅旋转 dimensionEpoch，不清其他维度。归一化 revision 不同的 gateway 不混写同一序列，部署过渡期仅接受当前登记 revision 的样本。读/写失败记录原始错误和登记不可用诊断，响应转发继续；不可用不显示为“无异常”。

memory 采用账户级锁，Redis 原子脚本或等价 CAS 共同校验账户控制记录与维度记录（同账户使用同一 Redis hash slot）；**校验 revision/accountEpoch/dimensionEpoch、提交时效、observationId 去重、分配 sampleSequence、窗口/TTL、计数与集合更新**为同一原子操作。账户清除在同一屏障下校验版本并旋转 accountEpoch，不靠逐维度删除实现一致性；旧维度逻辑失效，物理清理可异步，新维度也不能逃过账户 fence。

三类期限各自明确：状态 TTL 自最后接纳提交起 30 分钟（达到期限视为过期）；账户/维度控制记录自发送前捕获或有效结算/清除起保留 60 分钟；去重记录自首次结算起 60 分钟。旧回调不续控制 TTL，不存在控制记录时只剔除，只有新发送前捕获可以重建。剔除统计不续异常 TTL，重复/版本失效/超时效回调不改变状态。持续有效流量可续控制记录，但超过 30 分钟的旧提交仍被时效门拒绝，故 60 分钟去重过期后不再复算；不能把 sentAt 改为再次回调时间。存储调用次数与清理需实施量测；这里只增加运行态，不新增数据库表。

管理面能力限定为管理员账户诊断，所有者/普通角色和授权使用者本期没有新增读写入口。先走现有管理员身份与账户管理 owner 作用域检查；无权限不得通过账户 ID 查询来源账户或其他授权实例的状态。原始 Key 指纹、runtime key、epoch 和内部状态键不出现在 UI、日志明文或 API DTO 中。

- 只读接口计划为 `GET /__aisys__/api/accounts/:id/model-declaration-runtime`，返回 `{accountId, generatedAt, dispatchRevision, runtimeVersion, runtimeAvailable, items, nextCursor}`；每页最多 50 维度。dispatchRevision 与 opaque runtimeVersion 是整个逻辑账户的版本，非某页/某维度版本；runtimeVersion 包含账户 epoch、控制 revision 及登记变更序号的校验摘要，原子清除校验读取后的任何有效登记变更，变化返回 409。cursor 绑定同一版本，跨页改变返回 409 后由客户端重读，不承诺跨页静态快照。不可用时两个版本字段为空，不能清除。items 展示路由/分组、协议档案、endpoint mode、发送模型、脱敏 Key 标签、state、声明集合及截断标志、最近接纳/异常时间、expiresAt、序列计数。`runtimeAvailable=false` 不表示零异常，页面展示“登记暂不可读”。
- 清除接口计划为 `POST /__aisys__/api/accounts/:id/model-declaration-runtime/clear`；body 仅接受 `expectedDispatchRevision` 与读取接口提供的 opaque `runtimeVersion`。动作清除本逻辑账户当前登记，不涉及来源账户或兄弟实例，不恢复健康状态。revision/version 不符返回 `409`，无权限返回 `403`，运行态不可读写返回明确服务错误；成功返回 `{accountId, changed, generatedAt}` 并写既有操作日志。version 是控制记录摘要，不是内部 epoch 明文；原子清除旋转 epoch，所有清除前开始的 attempt 均不能重新登记。
- 页面明确标“当前响应声明登记”，附 generatedAt/最近样本时间，不称真实模型识别或历史快照。当次结算的 stateBefore/stateAfter、归一化 revision、sampleSequence 和剔除原因写入该 attempt 的审计，历史追溯走审计已有权限。
- **不新增使用记录详情关联展示。** [使用记录详情退场设计](使用记录详情退场设计.md) 已明确列表-only，本设计不得恢复详情接口/抽屉、行操作或日志跳转。使用记录列表原 `upstreamModelMismatch` 与字段保持原状；不得把当前登记拼入过去使用记录伪装成当次事实。

以上 API 为待实施契约，本轮只交付文档，不声称路由已经存在。实施批次 B 必须同步权限矩阵、账户前端入口与操作日志文档，Mock 验证越权、分页、版本冲突、状态不可用和清除 fence，再以隔离实例验证端口真实装配。

### 2.3 上下文承接过滤（原"承接门第四门"）——设计冻结，禁止实施

初版设计承诺"携带上游 opaque 上下文的请求不路由到漂移指纹与来源账户指纹不一致的账户"。外部复审证明该承诺在以下四点未补齐前不可安全实施，**本文将其冻结**：

1. **兼容依据缺失（P1）**：指纹一致不构成兼容放行依据（第 0 节）。需要先取得密文绑定机制的运行时证据（如：失败/成功账户对的观测研究、上游加密域行为证据），定义"可承接"的充分条件。在此之前，任何过滤都只能是"排除已知异常"，而初版把它表述为安全承接，语义过度。
2. **准入旁路（P1）**：初版把过滤挂在 SwitchTarget 承接门上，但 `switchtarget.go:310-311` 未冻结时直接放行原候选列表、`:322` 对冻结源同账户无条件保留。反例：上一轮账户 A 生成密文，下一轮该请求首选账户 B——B 在过滤生效前已成为候选/冻结源，仍会收到 A 的密文；同账户 Key 轮换也存在绕过路径。**兼容检查必须从首次发送前对所有候选生效**，覆盖首选、重试、Key 轮换、切号、分组回退与 compact 全路径，不能以追加切号门实现。
3. **来源凭证缺失（P1）**：初版以会话亲和当前绑定充当密文生成账户，但亲和绑定可迁移，且存在混合来源、网关外部 response ID、亲和过期。过滤需要每个产物生成时不可变的来源及**兼容域证据**；账户 + 声明模型快照仍不是充分条件。Unknown/混合/过期来源的放行或拒绝须另行裁决。已经安全物化的内部桥历史不得被当成未解密的上游 opaque 状态。
4. **观测与准入语义分离（P1）**：2.1 节只解决声明异常取证，不能提供上下文准入 oracle。连续 N 次门槛不是首份产物的防护；未来过滤需另定义生成时兼容证据与准入状态，不得复用本期异常标签直接决定承接。

**解禁条件**：以上四项各自形成可验证的设计补充（运行时证据、全路径准入设计、产物来源快照与 Unknown 决策、两级过滤输入语义），合并入本文并重新通过独立复审后，方可解禁实施。解禁前，任何批次不得实现按指纹的候选过滤。

### 2.4 止血保留
