# 调度慢失败直切、来源避让记账与墙钟收尾修复设计

> 状态：设计定稿（2026-10-23），实施依据 [PLAN-20261022T171949672Z](../plans/计划-20261022T171949672Z-调用方维度真实流量质量反馈与慢失败快速换号.md) v5 三刀。修复全部落在默认（cost_first）调度路径，不引入模式切换、不新增状态机。

## 1. 背景与目标

2026-10-22 生产事件：上游渠道对 `deepseek-v4.1-flash` 流式慢失败（504/TLS/120s 首字超时，单次 60~120s），网关同账户重试把 3 次尝试全部烧在同一账户（~5 分钟），客户端超时断开；来源避让因记账侧缺失从未生效。设计第一原理：**一切调度必须在客户端耐心窗口（~270s 墙钟预算）内交付结果或给出确定性终态，宁可主动收尾，不可吊死到客户端超时。**

三刀：A 慢失败直切（同账户重试耗时门槛）、B 来源避让记账与确认时机补全、C 墙钟收尾修复（裁剪缺口查修 + 新尝试启动门槛）。

## 2. 改动 A：同账户重试快速失败门槛

- 位置：`internal/gatewaydispatch/attemptoutcomes.go` 两个同账户重试预留点——`:332`（`upstream_http_response`，上下文 `upstreamAttemptResponseContext`）与 `:571`（`upstream_transport_failure`，上下文 `upstreamAttemptErrorContext`）。
- 耗时来源：两上下文均有 `attemptStartedAt`（`dispatchsingle.go:1104/:1149`，源于 `dispatchsingle.go:575` 每尝试 `gatewayupstream.NowMs()`）；耗时 = `gatewayupstream.NowMs() - c.attemptStartedAt`（与 `gateway_upstream_attempt_failed` 日志 `durationMs` 同源口径）。
- 契约：`耗时 ≥ settings.SameAccountRetryFastFailMaxMs（默认 10000）` → 不调用 `reserveSameAccountRetry`，直接走轮换；输出审计 metadata `same_account_retry_skipped_slow_failure`（含 elapsedMs、thresholdMs、retryReason）。`< 阈值` 行为不变。预算上限 `min(2, temporaryUnschedulableRetryAttempts)` 不动。
- 不改变：同账户重试的既有预算语义（`preparationpaths_test.go:568/664` 墙钟窗用例保持通过）。

## 3. 改动 B：来源避让记账与确认时机补全

**现状缺口（取证实证）**：`RememberPendingFailure`（`avoidance.go:288-308`）全仓零生产调用——tracker 的 `PendingFailures` 从未被填充，`ConfirmAfterFinalFailureAsync` 生产空转。机制本体（计数+1、读侧阈值 ≥2、TTL、排序保层、全避让旁路、清空幂等）完好。

- **B1 记账侧接线**：引擎失败结算点对**上游归因失败**调用记账，范围界定（独立复审界定，与实现的引擎结算面一致）：覆盖 `upstream_request`（传输/拨号/首字超时）与 `upstream_response`（2xx 后失败响应判定、非 2xx 透传）两臂；`stream` 相位（首字后正文中断）与 speed_first 首字截止臂不经引擎结算点、不记账——前者由流式 precommit/直传语义承接，后者由速度优先自身的切号与热质量承接。纯 `downstream_closed` 无上游失败不记。接线方式：`FetchFirstAvailableUpstreamArgs` 增加可选回调 `RememberUpstreamAttemptFailure func(accountID string, failure gatewayclientip.AccountFailure)`，由 chain 层从 `DispatchContext.ClientIPAccountAvoidance` tracker 构造闭包注入；nil = 不记账（测试/内部派发）。
- **B2 成功确认**：`chain_v1_loop.go` 最终成功臂（`:594-602`，`!handling.RetryUpstream` 分支，`settleHotQualityTerminal` 之后、`confirmProtocolSuccessSideEffects` 相邻）新增 `confirmClientIPAccountAvoidanceAfterSuccess`：与既有失败确认（`:2164`）同构——`IsAccountDiagnosticTrafficSource` 过滤、`ConfirmAfterFinalFailureAsync` 调用、审计 metadata `client_ip_account_avoidance_update`。**不受 `ProtocolValidatedSuccess` 门限制**（2xx 透传亦算交付）。
- 语义：请求内任一上游归因失败进 PendingFailures（同账户去重覆盖）；结算（成功或失败）确认一次 → 每个 entry FailureCount+1 → 读侧 ≥2 生效、沉底 TTL 5 分钟（上限 10 分钟）→ 无流量后 TTL 过期，下一请求真实试探自愈。**沉底作用域（重要界定）**：避让排序保优先级层（`PreserveGatewayAccountDispatchPriorityTiers`）——沉底只在**同层内**生效；跨层的高优先级坏号（如今晚 kid1412=0 独占顶层）仍会被每请求先尝试一次，由改动 A 保证该次失败后立即换号、改动 C 保证预算内收尾。若需跨层避让效果，运营上是把可互换账户放同层（同层=等价可轮换的语义）；跨层旁路属调度语义变更，未含在本设计内。探针/诊断流量不记账不确认。
- 既有行为恢复说明：B1 落地后，既有「最终失败确认」路径（`chain_v1_loop.go:2164`）同时从空转转为生效——这是恢复 Node 镜像的设计行为，不是新行为。

## 4. 改动 C：墙钟收尾修复

**缺口定位（取证实证）**：precommit 截止已装配到流式读取（`chain_v1.go:692-694` → `finalize.go:318` → `streamread.go`），但 (a) upstream_request 相位（等响应头/首字）不受墙钟约束，仅由 120s 单尝试首字超时管，晚启动的尝试可越过 270s 预算；(b) `streamread.go:94-97` 首个语义输出后墙钟免疫——此为 precommit 设计语义（已提交内容不剪），**保留**。

- **C1 启动门槛**：唯一咽喉点 `dispatchsingle.go:548-554` → `assertGatewayRequestWallBudgetAvailableForAttempt`（`enginehelpers.go:343-365`）→ `HandoffRequired`（`routecoordination.go:331-347`）。将 `GatewayRequestWallBudgetDecision.MinimumMeaningfulAttemptMs` 从缺省 0 提升为 `settings.GatewayAttemptStartMinWindowMs（默认 30000）`：`剩余 − 2s 渲染保留 ≤ 30s`（承载机制 HandoffRequired 原生边界为 ≤）→ 不启动任何新尝试（首轮/轮换/Key 轮换/URL 循环全覆盖，断言位于尝试循环头），返回既有 `GatewayRequestWallBudgetExhaustedError` → 既有渲染（`chain_v1_loop.go:896-935` wall kind → 503 `gateway_request_wall_budget_exhausted`）。
- **C2 尝试截止裁剪**：普通路径单尝试首字截止按墙钟预提交线裁剪——`effectiveDeadline = min(now + firstResponseTimeout, wallBudget.DeadlineAtMs − DefaultGatewayFinalResponseReserveMs)`，插入点在每尝试截止解析处（`dispatchsingle.go:582-598` 一带，speed_first 的 `ResolveNormalRouteAttemptFirstByteDeadline` 已有同型 limiting-factor 裁剪 `gatewayrouting/firstbytedeadline.go:71-85` 可参照）；Unbounded（压缩）与 image lane 豁免不变。裁剪后尝试到点按既有超时路径失败结算，不再越过墙钟。
- 时间账自洽：预算内最多 2 次完整尝试（2×120s=240s < 270s）；A 保证第 1 次失败即换号；C2 保证晚启动尝试不越线；C1 保证无本钱不开局。

## 5. 设置项（2 个新字段，全链路接线）

| 字段 | 默认 | 范围 | 语义 |
| --- | --- | --- | --- |
| `sameAccountRetryFastFailMaxMs` | 10000 | 0~60000 | ≥此耗时的失败不做同账户重试；0 = 全部直切 |
| `gatewayAttemptStartMinWindowMs` | 30000 | 0~60000 | 启动新尝试所需最小剩余预算；0 = 仅保留 2s 渲染保留（旧行为） |

接线清单（逐处显式，非动态）：`gatewayruntimecache/types.go` GatewaySettings 字段；`sqlmodels.go` projectGatewaySettings `numberSetting` clamp（min/max 与下同源）；`maintenance` seed（`pg_schema.go:756+`）；`settings/store.go` SystemSettingKeys 白名单 + systemSettingSpecs 校验；`settings/settings_test.go` 期望 map；`gatewayruntimecache/sqlmodels_test.go` 投影断言；前端 `types/domain/settings.ts`、`views/settings/settingsForm.ts`（字段声明/默认值/integerValue 校验，中文标签与相邻超时字段同风格）、`settingsDisplay.ts` 核对登记。

## 6. 时间与协调约束（验收硬项）

1. 机制顺序：失败 → A 门槛 → 轮换（过 C1 门槛）→ 结算 → B 确认；墙钟到点 → C2 裁剪/C1 拒启 → 终态只渲染一次。
2. 避让只在下一请求排序时读取（`OrderAccountsByClientIPAccountAvoidanceAsync`），请求中途不改排序。
3. 探针/诊断流量（`IsAccountDiagnosticTrafficSource`）不记账、不确认。
4. 正常号零扰动：无失败尝试的请求不产生避让记录、排序不变、行为与现状逐字节一致。
5. 既有测试锚点全保持：`TestDispatchResponsePrecommitDeadlinePopulated`、`TestAssertGatewayRequestWallBudgetAvailableForAttempt`、`TestFetchFirstAvailableUpstreamWallBudgetAssertion`、`TestV1DispatchLoopWallBudgetKinds`、`TestResponsePrecommitDeadlineAfterFirstByte`、same-account retry 墙钟窗用例、precommit 竞速各臂。
