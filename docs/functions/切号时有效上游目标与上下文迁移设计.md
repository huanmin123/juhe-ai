# 切号时有效上游目标与上下文迁移设计

> 2026-09-08 复查定稿草案：本文只定义“切号发生后”的候选约束和请求重建边界。初始路由、客户端画像识别以及显式 `Responses -> Chat` mapping 是否允许，分别由对应专题文档负责，不在本文重新定义。

## 1. 定稿结论

切号时必须同时固定两件事：

1. **有效上游目标（`SwitchTarget`）**：当前账号经过模型映射、协议 bridge 和上游 request builder 后，实际上要发送到哪个供应商、哪个模型、哪个协议族和哪个精确接口形态。
2. **已转换上下文（`ConvertedContext`）**：已经完成状态恢复和协议转换、可以被下一个候选账号重新序列化的上下文。它不是客户端原始请求，也不是上一个账号专属的最终 body。

因此，`Responses -> Chat` 不是“把路径从 `/responses` 改成 `/chat/completions`”就完成了切号准备。只有在 `Responses` 状态已经由网关消费，输入、历史、工具调用和必要的 reasoning 已转换成可迁移的 Chat / canonical 上下文，并且实际 Chat 上游请求已经成功构造时，才可以按 Chat 目标切号。

切号的核心规则是：

```text
客户端 source 协议
    -> 初始路由和账号 mapping（这里才使用 source）
    -> 状态恢复 / 协议转换 / 上游请求构造
    -> 冻结 ConvertedContext + SwitchTarget
    -> 未提交失败时，只按 SwitchTarget 筛选并重新序列化
    -> 返回侧继续按客户端 source 协议渲染
```

客户端原始协议只负责入口识别和返回格式；冻结后不再作为切号候选的协议依据。

## 2. 两个必须分开的对象

### 2.1 `SwitchTarget`

`SwitchTarget` 是请求级、不可变的上游目标快照，至少包含：

```text
providerCode                  # 当前实际上游供应商
providerProtocolProfileID     # 当前上游适配档案；非 Chat 目标用于同档案约束
upstreamModel                 # 实际发送模型，比较时大小写不敏感，转发保留规范拼写
upstreamEndpointFamily        # chat_completions / responses / messages / ...
upstreamEndpointMode          # 精确 JSON / SSE 形态，如 chat_sse、responses_json
contextContract               # 上下文形态，如 chat_messages_v1、native_responses_v1
```

`upstreamPathAndQuery`、供应商序列化器和 bridge 执行计划属于请求构造所需的附加元数据；它们必须随目标计划传递，但不应被当成候选身份的替代字段。候选资格最终仍要由目标协议族、精确 mode、模型和供应商规则共同决定。

`upstreamModel` 的逻辑比较使用与模型限制相同的大小写不敏感规则；候选账号可以使用自己的规范拼写发送，只要逻辑模型相同。不能只比较模型名而忽略协议族或 mode。

### 2.2 `ConvertedContext`

`ConvertedContext` 是账号无关、凭据无关的可迁移上下文，至少应能表达：

- 已恢复的历史消息、工具调用和工具结果；
- 本轮 instructions、输入和必要的 reasoning；
- 目标协议可表达的工具、采样和响应格式字段；
- 仍未转换或不可保真的能力标记。

它不得包含账号凭据、Base URL、代理、API Key、上一个账号的 Authorization，或只能由特定上游服务器解开的 opaque 状态。每个候选账号都必须从同一份 `ConvertedContext` 重新生成自己的上游 body、路径、Header 和 mode；不能把上一账号已经序列化的最终 body 原样投递给下一账号。

## 3. 冻结时点和失败边界

### 3.1 冻结时点

第一次候选账号完成以下步骤后，在第一次真实网络发送前冻结 `SwitchTarget + ConvertedContext`：

1. 解析当前账号的有效模型 mapping；
2. 恢复或验证 Responses / Codex 状态；
3. 执行协议 bridge 或原生请求整理；
4. 由 provider driver 生成最终的上游 path、model、endpoint mode 和可发送 body。

冻结必须发生在“能完整描述实际上游请求”之后，不能在只知道客户端 `/responses` 或请求 `model` 时提前冻结。

账号准备阶段失败且尚未发送真实上游请求时，该账号可以按账户级失败继续尝试初始候选；但每个候选都必须独立完成自己的准备。不得把前一个账号的部分改写 body 当成下一个候选的输入。第一个完整形成目标和上下文的候选成为冻结源；所有候选都无法形成时，返回既有本地错误，不得按客户端协议猜测一个目标继续发送。

一旦任何真实上游 attempt 已开始，`SwitchTarget` 必须存在。之后发现目标缺失属于实现不变量错误，不能进入“放宽筛选”的降级路径。

### 3.2 切号时的请求重建

当前 attempt 在下游语义尚未提交时发生允许切号的失败，执行顺序固定为：

1. 使用冻结的 `SwitchTarget` 过滤同一分组或路由策略允许的候选；
2. 检查候选的真实接口能力和别名 RHS；
3. 使用冻结的 `ConvertedContext` 和目标执行计划重新构造候选请求；
4. 只把候选自己的凭据、Base URL、Header 和序列化结果交给上游。

候选请求构造不得重新调用只接受 `sourceModel + sourceEndpointFamily` 的初始 mapping resolver，也不得从原始客户端路径重新推导切号协议。

## 4. 切号候选硬约束

切号过滤必须新增独立的 target-aware 规则，不能直接复用初始请求的模型 / source 协议过滤器。候选账号必须同时满足：

1. `supported_endpoint_modes` 包含冻结的精确 `upstreamEndpointMode`；
2. `supportedModels` 直接命中冻结的 `upstreamModel`，或存在启用且仍有效的账号模型别名，其 RHS 同时命中：
   - `upstreamModel`；
   - `upstreamEndpointFamily`；
3. 供应商规则满足下表；
4. 候选 provider driver 能把冻结的 `contextContract` 序列化为该目标，而不是只能处理原始客户端 source。

别名左侧 `SourceModel`、`SourceEndpointFamily`、客户端画像和本次客户端请求路径均不参与切号资格判断。映射 RHS 只用于证明候选能够到达冻结的真实目标；RHS 不同、映射停用或 RHS 协议族不同都必须拒绝。

| 冻结的 `upstreamEndpointFamily` | 供应商规则 | 仍需满足 |
| --- | --- | --- |
| `chat_completions` | 允许跨供应商 | 同一 `upstreamModel`、同一 Chat 协议族、同一精确 JSON / SSE mode、上下文可序列化 |
| `responses` | 不允许跨供应商 | 同一 `providerCode`、兼容的 `providerProtocolProfileID`、同一模型、同一协议族和同一 mode |
| 其他非 Chat 协议 | 不允许跨供应商 | 同一 `providerCode`、同一协议族 / mode、同一模型和可迁移上下文 |
| 空值、未知值或无法证明的目标 | 不允许放宽 | 停止跨账号切换，走既有最终失败 / 客户端交接 |

当前架构把 `provider_code` 作为分组硬过滤条件，因此 Chat 跨供应商只能通过路由策略绑定多个供应商分组并执行 group fallback；本规则不把不同供应商混入同一个分组号池。

## 5. `Responses -> Chat` 的特殊边界

### 5.1 何时切号上下文属于 Chat

当首个账号的显式 mapping RHS 是 `chat_completions`，并且 bridge 已经完成状态恢复和请求转换时，本次请求的切号目标是：

```text
upstreamEndpointFamily = chat_completions
contextContract         = chat_messages_v1（或等价 canonical Chat 上下文）
```

此时下一个账号只需要支持该 Chat 模型和精确 Chat mode；它不需要支持客户端 `Responses`，也不需要配置同一条 `Responses -> Chat` 左侧 mapping。它可以是原生 Chat 账号，也可以是别名 RHS 指向同一 Chat 目标的账号。

但是，候选请求构造必须消费已经转换的 Chat / canonical 上下文。不能因为候选账号没有匹配客户端 `Responses` 左侧 mapping，就把原始 `Responses` body 重新交给它；也不能因为候选有另一条 `Responses -> Chat` mapping，就再次从客户端 source 进行不同转换。

### 5.2 当前 bridge 的精确 mode

当前设计中的 `Responses -> Chat` bridge 使用上游 Chat SSE 作为桥接载体：

- 下游 `stream=true` 时，Chat SSE 事件转换为 Responses SSE；
- 下游非流式请求如果未来开放，也必须先在 bridge 中聚合，再渲染为 Responses JSON；不能把 Chat SSE 原样交给非流式客户端；
- 当前 bridge 的已落地启用条件仍以流式 `/v1/responses` 和 `chat_sse` 为准。

所以 `SwitchTarget.upstreamEndpointMode` 必须记录实际上游 mode。当前 bridge 请求不能仅因为下游是非流式就自动改成 `chat_json`；只有 provider driver 明确选择并验证了 `chat_json`，才可以形成 `chat_json` target。`chat_json` 与 `chat_sse` 不是同一能力，不能在切号时互换。

### 5.3 `previous_response_id`、`encrypted_content` 和状态链

Responses 的客户端 source 与上游状态不是同一层：

- **内部 bridge `previous_response_id` 或 `juhecmp` 引用**：由网关状态层校验边界、TTL 和 digest，恢复为可迁移的历史 / Chat summary；发送 Chat 前删除 `previous_response_id` 和网关私有 envelope。
- **外部原生 `previous_response_id`**：如果网关不能在本地物化其历史，就只能交给原生 Responses 账号；该请求不能切到 Chat。
- **原生上游 `encrypted_content`**：属于上游 opaque 状态，网关不解码、不伪造。只要它仍是继续请求所必需的状态，就必须保持同供应商、兼容协议档案和 Responses mode；不能把它带给 Chat 或其他供应商。
- **已物化的 Chat 上下文**：只有在所有继续请求所需的 Responses 状态都已经被网关消费、历史和工具链完整恢复后，才允许按 Chat 目标跨供应商切号。

删除一个字段不等于完成转换。工具调用顺序、reasoning、图片 / 文件引用、响应格式和不可保真能力都必须经过 bridge 的既有能力矩阵；无法安全转换时返回 guidance 或账号作用域的受控失败，不得靠丢字段后继续切号。

本规则只放宽“同一请求内、已物化上下文”的 Chat 跨供应商切号。它不自动放宽 `previous_response_id` 后续请求的持久状态边界；后续请求仍按 Chat-only bridge 的状态存储规则校验 API Key、分组和 provider profile。若未来要允许状态续链跨供应商，必须另行修改状态边界、摘要归属和审计契约。

## 6. 各类切号入口的统一行为

| 切号入口 | 目标处理 |
| --- | --- |
| 同一账户 API Key 轮换 | `SwitchTarget` 和 `ConvertedContext` 不变，只更换物理凭据；不重新按客户端 source 选协议 |
| 同分组账户切换 | 使用 target-aware 候选过滤和候选自己的序列化器 |
| 路由策略 group fallback | 保留同一 target；只在策略允许的后续分组内继续筛选，Chat 跨供应商仍受分组 provider 硬过滤约束 |
| Codex turn / stream retry / speed-first cutover | 只要下游未语义提交，继续消费同一 target；不重置目标、预算或已转换上下文 |
| 下游已写出真实协议事件、正文或可见输出 | 沿用现有“禁止拼接第二账号结果”规则，不因 target 规则重新播放 |
| 客户端主动重试形成的新 HTTP 请求 | 重新执行初始路由和 mapping，生成新的 target；不继承上一请求的 target |
| target 或 context 无法解析 | 记录有界的 `switch_target_unresolved` 诊断，停止跨账号扩散，不退回客户端 source 协议 |

同一请求的 attempt、账户、Key、分组和 compact 阶段共享既有预算与物理凭据去重；切号规则不能通过重置预算来扩大尝试范围。

## 7. 当前 Go 实现复查状态

2026-09-19 起本节描述已落地的 Go 实现（`SwitchTarget` 冻结 + target-aware 切号过滤）；`ConvertedContext` 独立结构化与 `contextContract` 字段仍为暂缓项（见 7.1）。

已落地事实：

- **类型与过滤纯函数**：`internal/gatewaydispatch/switchtarget.go` 定义 `SwitchTarget`（`ProviderCode` / `ProviderProtocolProfileID` / `UpstreamModel` / `UpstreamEndpointFamily` / `UpstreamEndpointMode`，暂不实现 `contextContract`）与 `FilterAccountsForSwitchTarget`。候选保留需同时满足三条门：精确 mode 门（候选声明了 `SupportedEndpointModes` 时必须包含冻结 mode；候选空 modes = 不受限，保持既有 D-155 语义；目标 mode 为空 = 本次请求形状无闸门 mode，同样不过滤）、供应商门（非 `chat_completions` 目标锁定冻结供应商，Chat 目标允许跨供应商；本次不做额外 profile 兼容判定）、承接门（复用初始路由同款 `resolveAccountModelMapping` 解析候选别名：命中别名时 RHS 模型 EqualFold 相等且 RHS 协议族一致；无别名直连时仅当冻结目标为原生形态——目标族等于构造侧客户端族——且候选直持该模型 EqualFold 时保留）。
- **冻结时点与捕获**：`cmd/juhe-ai-gateway/chain_switchtarget.go` 在 `chainProviderDriver.BuildGatewayUpstreamRequestParts`（`chain_driver.go` 构造实现的外层包装）成功返回后、首次真实发送前冻结本请求目标：有 mapping 时取 RHS（`mapping.UpstreamModel` / `mapping.UpstreamEndpointFamily`）+ `requiredSupportedEndpointMode` 推导的精确 mode（覆盖 D-99 codex_responses 强制 SSE 与跨协议桥的 mode 重映射，如 Responses→Chat 桥恒为 `chat_sse`）；无 mapping（原生）时取 (客户端模型, 构造侧客户端族, 客户端精确 mode)。**冻结与过滤同源**：冻结时把构造侧 mapping 解析实际使用的 `ClientRequestedModel` 与 `requestMappingSourceFamilyOf` 协议族一并记录进载体，全部消费点的过滤输入一律取自冻结快照（不按请求路径重新推导），保证同一请求内冻结与过滤用同一族词表——`/v1/responses/compact` 等两侧推导分歧形态不再过度收窄候选池，`countTokens` 等未闸门形态不再产生空 family 误诊（构造侧族词表恒非空）。载体是请求级 `gatewaydispatch.SwitchTargetCapture`，由 `/v1` handler（`chain_v1.go`）注入请求 ctx；每请求只冻结一次，不随后续尝试、同账户 Key 轮换或分组切换重置。构造前失败（URL 构建错误、候选门拒绝）不触发冻结，后续候选仍走既有初始筛选。
- **构造包装调用方边界**：唯一允许冻结的调用方是主请求账户派发（engine `dispatchSingleAccount` → `BuildPreparedUpstreamRequestParts` → driver 包装）；内部合成 / 辅助 / 打分类派发共享请求 ctx 时必须经 `gatewaydispatch.WithoutSwitchTargetCapture(ctx)` 剥离载体——当前接入点是混合智能路由打分 `chainHybridAuxiliaryDispatcher.DispatchHybridAuxiliaryChatCompletion`（`chain_compose.go`，preflight 混合智能路由在主请求任何账户构造之前同步打分，其打分账户构造不得抢先冻结主请求目标），并有回归测试断言打分派发到达构造阶段后主请求载体仍未冻结。
- **消费点接线**（统一经 `SwitchTargetGate`：与冻结源同账户的候选不是切换点，无条件保留；其余候选过三门；过滤输入取自冻结快照）：
  1. 引擎侧账户推进：`internal/gatewaydispatch/upstreamdispatch.go` `FetchFirstAvailableUpstream` 候选 for-of 循环顶部，推进到不同账户前逐候选过滤；
  2. cmd 重派窗口（覆盖流式未提交重试、速度优先切换收窄、调度错误重派、组回退后的全部重派）：`cmd/juhe-ai-gateway/chain_v1_loop.go` `run()` 在 `streamRetryDispatchAccounts` 与 speed-first 收窄之后、重派之前调用 `filterAccountsForFrozenSwitchTarget`；
  3. 分组 fallback：`internal/gatewaydispatch/fallbackcandidate.go` `ResolveNextGroupFallbackCandidateForArgs` 在候选投入配额/排序前按冻结目标后置过滤，过滤后为空跳过该分组继续下一个候选分组；
  4. 候选窗口与模型感知 reload：`internal/gatewaydispatch/candidatefilter.go` `FilterOpenAIGatewayRequestCandidateAccounts` 在模型过滤与模型感知 reload 结果定稿后按冻结目标后置过滤。
  初始候选筛选完全不变：冻结目标不存在时（首个账户选择、首次 preflight）过滤函数根本不参与。同账户 API Key 轮换（`dispatchsingle.go` 轮换循环）不是切换点，不重筛。
- **fail-closed 诊断**：已发生完成构造但冻结目标不可解析（空 family/model 等不变量违规）时，各消费点停止跨账户切号（仅保留冻结源账户），走既有最终失败/兜底路径，不回退客户端协议筛选；诊断关键字 `switch_target_unresolved` 每请求至多输出一次（载体级 once 标记），各消费点字段如下：引擎账户推进（`AuditCapture.AddGatewayMetadata`：`accountId` / `sourceAccountId` / `traceId` / `apiKeyId` / `groupId` / `reason`）、候选过滤（`reason` / `sourceAccountId` / `stage=candidate_filter`）、分组回退候选加载（`reason` / `sourceAccountId` / `stage=group_fallback_candidate`，经 `GroupFallbackCandidateInput.AuditCapture` 传入）、cmd 重派窗口（audit 同名字段外另经 `observability.Logger().Warn` 输出 `event` / `endpoint` / `apiKeyId` / `groupId` / `traceId` / `sourceAccountId`）。过滤后候选为空同样走既有最终失败/兜底路径，不得放宽。

### 7.1 暂缓项

以下条目本次明确不做，保留为暂缓：

- 第 8 行 RHS-only 候选加载一般化（切号时不经客户端 LHS、直接按 RHS 目标加载候选的独立加载路径）；
- `ConvertedContext` 独立结构化（账号无关、可迁移上下文的完整对象化）；
- `SwitchTarget.contextContract` 字段（上下文形态，如 `chat_messages_v1` / `native_responses_v1`）。

## 8. 影响、边界和非目标

预期影响：

- 混合协议或模型配置不完整的号池，切号候选会减少，最终失败或客户端交接可能增加；这是保护上游状态和加密上下文的必要成本。
- 不需要把 target 或完整上下文写入业务库；target 是请求内易失状态，完整 bridge 状态沿用现有受控状态存储，凭据和 opaque payload 不进入 target metadata。
- Chat 跨供应商只在“上下文已经物化为 Chat / canonical 形态”后生效；原生 Responses、外部 `previous_response_id` 和不可解密的 `encrypted_content` 不获得该例外。

明确不改变：

- 初始路由、模型目录和显式 `Responses -> Chat` mapping 的允许矩阵；
- 客户端画像作为请求整理、状态恢复、响应检查和审计的职责；它不是切号候选硬门槛；
- 配额、并发、熔断、质量排序、预算、物理凭据去重和已提交响应后的禁止切换边界；
- 当前分组的供应商硬过滤，不把跨供应商账号混入同一分组；
- 新 HTTP 请求的重新选路，不跨请求继承 target。

## 9. 验收矩阵

| 场景 | 预期 |
| --- | --- |
| GPT Responses 原生 → 同 GPT Responses | 允许，模型 / profile / family / mode 一致 |
| GPT Responses 原生 → GLM Responses | 拒绝 |
| GPT Responses 原生 → GPT Chat | 拒绝；候选有 bridge 也不能改变已冻结的 Responses target |
| Responses 初始 mapping 到 Chat → GLM Chat | 允许，前提是上下文已物化、RHS / 模型 / Chat mode 匹配 |
| Responses 初始 mapping 到 Chat → 仅支持 Responses 的账号 | 拒绝 |
| Chat target → 其他供应商 Chat | 允许，前提是策略绑定了目标供应商分组且上下文可序列化 |
| Chat target → 其他供应商 Responses | 拒绝 |
| mapping 左侧与当前客户端 source 不同，但 RHS 相同 | 允许；候选请求必须使用冻结的 Chat / canonical context |
| mapping RHS 模型或协议族不同 | 拒绝 |
| `chat_json` ↔ `chat_sse` 或 `responses_json` ↔ `responses_sse` | 未显式桥接时拒绝 |
| 外部 `previous_response_id` / 必需 opaque `encrypted_content` → Chat | 拒绝，不请求 Chat 上游 |
| 内部 bridge 状态已物化 → Chat | 允许按 Chat target 切号 |
| 同账户 API Key 轮换 | 允许，target 和 context 不变 |
| 分组 fallback / Codex retry / speed-first cutover | 全链路使用同一 target |
| target 缺失、未知或构造计划不完整 | 不放宽，不跨账号发送 |
| 下游已语义提交 | 不切号、不拼接第二账号响应 |
