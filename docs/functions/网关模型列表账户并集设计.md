> 动机：客户端通过 `GET /v1/models` 发现可用模型。当前实现返回的是**供应商模型目录**（`provider_model_catalog` + `custom_provider_models`），与调度实际使用的账户支持模型（`account_supported_models`）完全不同源——目录里"有价目但没有任何账户支持"的模型会被列出，目录不可见/无价的模型即使账户支持也不出现。本设计把 `/v1/models` 的成员资格改为**该 API Key 可达账户 supportedModels 的并集（配置能力并集）**，并以"读时聚合 + 双层缓存"实现：请求路径零 DB 成本、不新增 schema、不引入冗余存储表、不新增第二条失效链。

## 1. 背景与问题定性

### 1.1 问题现象

客户端（Cline、Roo、Cherry Studio 等按 `/v1/models` 渲染模型选择器的工具）拿到的模型列表与实际能调通的模型不一致：

- 列表里有的模型调不通：目录收录了模型并定价，但没有账户把它配置进 supportedModels（或支持它的账户全部不可调度/不可授权）。
- 列表里没有的模型能调通：账户把某个模型加入 supportedModels，但目录行 `catalog_visible=false`、无可见价格，或被音视频/realtime 模式过滤剔除。

### 1.2 根因

项目里存在**两套"模型集合"事实**，而 `/v1/models` 用了错误的一套：

| 事实 | 存储 | 消费方 |
| --- | --- | --- |
| 供应商模型目录（能卖什么、什么价） | `provider_model_catalog` + `custom_provider_models` | 计费、管理面、模型检测推荐、**当前 `/v1/models`** |
| 账户支持模型（这个账户能调什么） | `account_supported_models`（每模型一行）+ `account_model_mappings`（映射源） | 调度候选过滤、模型检测候选项 |

`/v1/models` 的成员资格应由第二套决定。这是**契约变更**：现行权威文档《账户模型限制设计》明文规定「`GET /models` / `GET /v1/models` 继续由本地供应商模型目录返回，不参与账户模型限制过滤」，实施本设计时必须先翻转该条契约（第 10 节同步清单）。

### 1.3 性能担忧的定性

需求方的直觉约束是"不能每次请求实时算一遍并集"。这个担忧成立的前提是把并集理解为"装载分组内全部账户 + 内存归并"。实际不是：

- 并集是**一组索引聚合 SQL**，输入是 Key 激活绑定已携带的分组 ID 集（零额外装载），数据面是几张小表的主键/二级索引前缀扫描，单次成本目标为毫秒级（第 5.4 节，实测校准前均为目标值）；
- 项目已有成熟的请求路径缓存形态（供应商目录缓存的进程内 + Redis 共享 + singleflight，`gatewayruntimecache/catalog.go`），照搬其结构即可让 DB 聚合只在缓存未命中时发生。

因此"避免每次请求实时并集"不需要物化表，只需要"一组便宜的 SQL + 一层现成的缓存"。

## 2. 现状事实（代码基线，均已核实）

以下事实是本设计的出发点；行号基于 2026-10-09 工作区快照，实施时如代码已演化，以代码为准并回填本文。

1. **本地响应链路**：外部 HTTP 的 `/v1/models` 恒走本地目录响应，不转发上游（转发开关 `ForwardModelsRequestToUpstream` 在 `/v1` 入口恒 false）。链路：preauth 判定 models 请求（`gatewaypreauth/preauth.go:60-64`）→ preflight 的 before-required-auth 分支（`gatewaypreauth/preflight.go:166-179` → `handleGatewayModelsRequestBeforeRequiredAuth` :1314-1358）→ API Key 校验 + models 端点专用限流 → `gatewayresponse/sink.go:294-335` `sendModelsGatewayResponsePayload` → 端口 `ModelCatalogLoader.ListClientModelCatalog`（`gatewayresponse/ports.go:226-229`）→ 实现 `cmd/juhe-ai-gateway/chain_compose.go:908-935` `chainClientModelCatalog`。
2. **provider codes 的来源**：`gatewayModelsProviderCodes`（`preflight.go:1271-1286`）遍历 `GatewayAPIKeyRow.GroupBindings` 取 `Status=="active"` 绑定的去重 `ProviderCode`。
3. **Key 记录已携带分组 ID**：`GatewayAPIKeyGroupBindingRow` 含 `GroupID/Status/ProviderCode/GroupEnabled`（`gatewayruntimecache/types.go:146-159`）。取分组集合与取 provider codes 是同一次遍历，零额外查询。
4. **当前成员过滤**：`selectClientCatalogItems`（`chain_compose.go:955-989`）按 `status=active`、built_in 行 `catalog_visible`、有可见价格过滤并按 model 去重；目录 SQL 取自 `provider_model_catalog`（内置行）与 `custom_provider_models`（global/personal 作用域）（`chain_catalog.go:170-228`），另有音视频/realtime 模式过滤（`chainIsSupportedCatalogModel`）。
5. **账户支持模型存储**：`account_supported_models(account_id, provider_code, model, created_at)`，PK `(account_id, model)`（`pg_schema_business_tables.go:970-979`）；管理面强制非空、上限 64（`accounts/write.go:274-309`）。写路径收敛于 `Store.replaceAccountSupportedModels`（`accounts/write.go:1006-1018`）：管理面建户/编辑、OAuth 建户、导入、批量编辑；模型检测只读不写；jobs 仅在账户物理清理时删行（`cleanuprepo/deleteaccount.go:483`）。
6. **调度侧的"可调用集合"语义**：候选账户静态门为 `chainCandidateWhere`（`chain_accounts.go:244-266`）：`group_accounts.system_account_id = 分组属主/GroupOwnerSystemAccountID`、`group_accounts.enabled=1`、`accounts.deleted_at IS NULL`、`accounts.status IN (statusSet)`、`accounts.schedulable=1`、未过期（`account_expires_at`）、可选 `cooldown_until` 门、授权实例账户追加来源账户同门；调用方只在授权行的 `grantee_system_account_id` 与访问臂上校验。模型匹配为"请求模型 ∈ supportedModels，或启用映射 `source_model` 命中且映射右侧 `upstream_model` ∈ supportedModels"（`chain_accounts.go:574-600` 的 SQL 与 `gatewayrouting/modelfilter.go:51-119` 内存过滤同语义）。`statusSet` 两档：默认 `'active'`，`includeUnavailable` 时放宽为 `'active','rate_limited','temporary_unavailable'`（`chain_accounts.go:493-497`）。
7. **模型事实主体与资格主体分离（调度实态）**：模型匹配按 `model_resource_account_id` 读取——`COALESCE(source_accounts.id, accounts.id)`，provider 同取 `COALESCE(source_accounts.provider_code, accounts.provider_code)`（`chainCandidateModelTail`，`chain_accounts.go:236-241`；模型匹配 SQL :574-600 按该列关联 `account_supported_models` / `account_model_mappings`）。`source_accounts` 是 `LEFT JOIN accounts ON source_accounts.id = accounts.authorization_instance_source_account_id`（:272）。即**授权实例账户的支持模型与映射事实挂在来源账户上**，实例行可以没有自己的模型行。
8. **映射行的完整匹配条件（调度 SQL 实态）**：`account_model_mappings` 命中要求 `account_id = 模型事实主体` **且 `provider_code = 模型事实主体 provider`**（:581）**且 `source_model = 请求模型` 且 `source_endpoint_family = 请求端点族` 且 `enabled = 1`**，并要求**跨改写**（`upstream_model <> source_model OR upstream_endpoint_family <> source_endpoint_family`，:587-589）。
9. **映射行存在 ≠ 映射有效（代码侧判定）**：`ResolveAccountModelMapping`（`gatewayopenai/mapping.go:68-116`）在 DB 行之上还有四道与请求无关的静态判定：①源端点族在可接受集（`isAccountModelMappingSourceEndpointFamily`）；②协议档案排除（`GeminiOpenAIChatProfileID` 账户不接受 anthropic messages 源族）；③恒等改写拒绝（upstream 与 source 的模型、族全同 → 不视为映射）；④运行时转换矩阵（`isOpenAIModelMappingRuntimeConversionSupported`：同族放行、gemini stream→generateContent 放行、responses→chat_completions 仅 OpenAI 协议档案，其余按矩阵）。这些判定只依赖映射行 + 账户协议档案，可静态执行。
10. **授权门（调度实态）**：候选 SQL 之后还有授权判定（`chain_accounts.go:320-336`）：
    - 有效性谓词（三个查询共用）：`resource_authorizations` 行须 `status = 'active'` 且 `(expires_at IS NULL OR expires_at > now)` 且 `grantee_system_account_id = 调用方`（`activeResourceAuthorization*`，:909-982；表 DDL `pg_schema_business_tables.go:588-607`）。
    - 分组访问形态 `resolveGroupAccess`（:811-893）：分组 `enabled != 1` → 无访问；属主 → owner 臂；否则须组级授权行有效（active + 未过期 + grantee），再查 `group_authorization_settings`（按 `authorization_id + grantee + group_id`）：**不存在 → 放行**（沿用组默认 type/policy）、**存在且 `enabled=0` → 拒绝**、**存在且 `enabled≠0` → 放行**（本地 type/policy 覆写只影响调度形态，不影响成员资格）。
    - 访问臂判定 `resolveChainAccountAccess`（:1037-1092），**顺序即语义**：**实例臂最优先**（`authorization_instance_authorization_id` 非空的账户只走本臂：调用方 ≠ `accounts.system_account_id` → 直接拒绝，不落入后续臂；授权行按 ID 查有效 + 绑定级 `ga.account_authorization_id` **必须非空且与授权行 id 精确一致**）；属主臂（直连账户属主 == 调用方）放行；授权分组臂（组访问形态 = authorized）要求**直连账户**属主 == 分组属主（免授权行）；owner 域授权臂要求按 `resource_type='account'` + `resource_id=账户ID`（或绑定授权 ID）查到有效授权行，绑定 ID 一致。
    - `canScheduleChainAuthorizedAccount`（:1094-1110）：owner / 授权分组臂放行；账户授权臂要求授权行在有效集合中。授权额度（`limits_json`）是请求期逻辑，不属于候选门。
11. **实例供应不变式**：实例账户的 `group_accounts.account_authorization_id` 由供应器 UPSERT 时**恒以运行时授权 ID 写入**（`authz/instance_provision.go:355-367`），良构数据中实例绑定授权恒非空；完整调度最终门仍要求该列**非空且与运行时授权 ID 精确一致**，历史/不完整绑定必须拒绝。
12. **`group_accounts` 的租户列**：PK `(group_id, account_id)` 不含 `system_account_id`，该列表达绑定所属的**分组属主域**，而不是请求调用方。候选查询应使用 `ga.system_account_id = g.system_account_id`（等价于调度装载时的 `GroupOwnerSystemAccountID`）；调用方通过组级/账户级授权行的 `grantee_system_account_id` 及访问臂完成授权校验。实例供应写入的 grantee 值属于实例绑定的授权域语义，不能推广为所有普通分组绑定的租户门。
13. **空 `supportedModels` 的现存矛盾**：调度模型窗口 SQL 中"模型事实主体无任何 supportedModels 行"→ `model_rank = 2`，`model_rank < 3` 放行——即调度把空集合当"匹配任意模型"（`chain_accounts.go:589-600`）；`chain_driver.go:798-801` 内存过滤同语义（"No constraint configured: the account accepts every model"）。这与《账户模型限制设计》「未配置支持模型的账号不作为任意模型兜底候选」的现行契约**相悖**。管理写路径（创建/编辑/导入/批量）强制非空，空集合只可能是历史/直写脏数据。该矛盾属调度侧现存问题，登记为后续独立修复项（第 9 节），本设计的列表语义按契约裁决（第 4.3 节）。
14. **映射表结构**：`account_model_mappings(account_id, provider_code, source_model, source_endpoint_family, upstream_model, upstream_endpoint_family, enabled, created_at, updated_at)`，PK `(account_id, source_model, source_endpoint_family)`；二级索引 `idx_account_model_mappings_source (provider_code, source_model, source_endpoint_family, account_id)` 与 `idx_account_model_mappings_upstream (provider_code, upstream_model, upstream_endpoint_family, account_id)`（`pg_schema_business_indexes.go:617,622`）。同一 `source_model` 可有多行（跨端点族）。
15. **缓存现状**：供应商目录缓存 = 进程内 entryCache（24h TTL，容量 1000）+ Redis 共享缓存（redis runtime 模式）+ singleflight 防击穿 + generation 守卫（`gatewayruntimecache/catalog.go:23-120`、`service.go:27,319-325`）。**读路径实态**：redis 模式下先读共享缓存（共享命中回填进程内），memory 模式只读进程内；**共享缓存读写失败不失败请求**——读失败按未命中继续、写失败记 WARN（`getSharedCatalog`/`setCatalogCacheEntry` 的既有容错）。**并发窗口（已观察事实）**：后台装载的 generation 检查（`isCatalogGenerationCurrent`）与缓存写入（`setCatalogCacheEntry`）是两次独立加锁，失效若插在两步之间，旧装载仍会回填两层缓存——本期新缓存不得复制该缺陷；目录缓存自身的该窗口修复不在本期范围（第 9 节）。
16. **失效机制现状**：失效由管理面写路径触发 `InvalidateGatewayRuntime(reason)` → `ClearGatewayRuntimeCache(reason)`（`invalidate.go:14-23`）。reason 判别只用于**可选**缓存：`ShouldInvalidateProviderModelCatalog` 白名单仅含 `custom_provider_model_saved / custom_provider_model_deleted / provider_model_configuration_updated` 三个目录事件（`service.go:58-65`）；核心运行时缓存（runtimeCache / identityCache / groupCache / accountsCache 等）在 `ClearGatewayRuntimeCacheLocal` 中**不区分 reason 一律清空**并推进 generation（`invalidate.go:27-45`）。实测 reason 全集（写路径 → reason）：账户编辑 `account_management_patch`、账户创建 `account_created`、账户删除 `account_deleted`（`accounts/invalidation.go:68-73,146,196,264`）；批量编辑 `account_batch_updated`（`accountstransfer/batch_effects.go:324`）；策略路由 `route_strategy_created/updated/deleted`（`routestrategies/mutations.go:143,420,563`）；API Key `api_key_updated` / `api_key_quota_updated`（`apikeys/patch.go:34-37`）；分组 `group_created/updated/deleted`（`groups/store.go:1395,1733,1877`）。**注意：账户模型变更走 `account_management_patch`，不在目录白名单内**。
17. **端口无错误语义（现状缺陷形态）**：`ListClientModelCatalog` 签名无 error 返回；实现里 `ListCachedProviderModelCatalogAsync` 出错时 `return nil`（`chain_compose.go:921-928`）——上游装载失败会被渲染成**200 空列表**。本设计的装载失败语义必须改变这一点（第 4.6 节）。
18. **Codex 形态的默认值实态**：`buildCodexModelInfo`（`gatewayresponse/models.go:139-215`）对**每个**条目填充默认：`Slug=DisplayName=model`、`ShellType="shell_command"`、`Visibility="list"`、`SupportedInAPI=true`、`Priority=索引`、`BaseInstructions="You are Codex, a coding agent."`、`DefaultReasoningSummary="auto"`、`WebSearchToolType="text"`、`TruncationPolicy={bytes,10000}`、`EffectiveContextWindowPercent=95`；`ContextWindow=MaxContextWindow` 取目录 `ContextWindowTokens`，**缺省回退 272000**；`InputModalities` 取目录真实模态，**缺省回退 `["text","image"]`**；`Description` 取目录备注三选一，无则 nil；reasoning levels / service tiers / multi-agent 仅在目录有数据时填充。
19. **响应形态**：四种协议形态共用同一份载荷（`gatewayresponse/models.go`）：OpenAI `{object:list,data:[{id,object,created,owned_by}]}`（:36-46）、Codex 富字段 `{models:[...]}`（:55-92 + :134-215）、Anthropic 分页形态（:303-328）、Gemini 形态（:331-345）。`owned_by` 规则：built_in 行 → `"openai"`，其余 → `"juhe-ai"`（:127-132）；`created` 取目录 `release_date/created_at` 的 Unix 秒（:253-268）。
20. **无单模型查询路由**：OpenAI 面精确匹配 `/models`（`gatewayopenai/endpoint.go:100`），`/v1/models/{id}` 返回 404；根形态 `/models` 注册仅服务 Gemini native `:action` 族。本设计不新增路由。契约覆盖端点全集：根形态 `/models`（适配进 `/v1` 链）、`/v1/models`（OpenAI-compatible 响应；同一路径按 Codex / Anthropic 客户端信号切换形态）、`/v1beta/models` 与明确 Gemini 客户端信号的 models 族（Gemini native 响应）。
21. **本地错误载荷与协议适配（既有能力）**：`GatewayErrorPayload{error:{message,type,code?}}`（`gatewaypreauth/responses.go:22-99`）、`GatewayErrorPayloadOf(message, type, code...)`、`GatewayErrorPayloadForProtocol`（openai / anthropic / gemini 三形态适配）、`LocalizedGatewayErrorPayload`（按状态码本地化消息）、`sendGatewayErrorResponseForSink(res, statusCode, payload, options)`（`gatewayresponse/sink.go:404`）。models 链审计惯例：`auditCapture.AddGatewayMetadata(key, fields)`（如 `"authenticated_models_rate_limit"`，`preflight.go:1390`）与错误 code（`authenticated_models_rate_limited`，:1376）。
22. **现行契约**：《账户模型限制设计》明文「`GET /models` / `GET /v1/models` 继续由本地供应商模型目录返回，不参与账户模型限制过滤」；`docs/functions/README.md`「客户端模型目录规则」段同口径（「只保留启用、可见、可计价模型」）。同文档性能设计节已有派生缓存的反向决策：「后续如果单个分组账号池过大，再增加 `groupId + systemAccountId + model` 的派生候选缓存；**第一版不引入，避免同时维护两套缓存失效链路**」。
23. **账户侧无效化已覆盖 supportedModels**：账户 patch 的副作用联动显式含 `supportedModels` 字段（`accounts/invalidation.go`），并以 `account_management_patch` reason 触发网关运行时失效——本设计搭既有车（但按第 6.3 节的无条件清空关系，而非目录白名单）。

## 3. 目标与非目标

### 3.1 目标

1. `/v1/models`（含第 2 节事实 20 枚举的全部端点与形态）的成员资格 = 该 API Key 激活绑定分组集合上、通过静态门与授权门的**资格主体**的**模型事实主体** supportedModels 并集，**加上**有效映射（第 4.2 节完整定义）的 `source_model`，并集语义为**配置能力并集**（不声称严格等于瞬时可调用集合）。
2. 请求路径零 DB 成本：聚合 SQL 只在缓存未命中时执行；缓存形态复用现有 runtime cache 模式（进程内 + Redis 共享 + singleflight + generation 守卫）。
3. 装载失败可观察：数据面装载失败返回确定的本地错误契约（第 4.6 节），禁止渲染成 200 空列表；缓存面失败按既有容错降级。
4. 四种协议响应形态、鉴权、models 端点限流、缓存响应头全部不回归。
5. 无 schema 变更、无 jobs 变更、无 maintenance CLI 变更、无部署文档变更。

### 3.2 非目标

- 不改调度本身的模型过滤逻辑（`modelfilter.go` / `chainCandidateWhere` / `resolveChainAccountAccess` / 映射解析与转换矩阵不动）。
- 不修复调度侧"空 supportedModels 匹配任意模型"与契约的现存矛盾（第 2 节事实 13，登记为后续独立修复项）。
- 不改供应商模型目录的存在与运营语义：价格、可见性、模式过滤继续服务计费与管理面，只是**不再参与 `/v1/models` 成员资格**（目录降级为元数据字典，第 4.5 节）。
- 不改管理面 AI 问答的动态模型目录（已有"目录 ∩ account_supported_models"逻辑，本期不动；后续可复用本设计的聚合）。
- 不新增 `/v1/models/{model}` 路由，不新增配置项或开关。
- 列表不反映冷却、熔断、健康、限流额度等运行态（第 4.4 节，契约明示）。
- 不修复现有目录缓存的 generation 检查/写入非原子窗口（已记录为观察事实，第 9 节；本期只保证新缓存不复制该缺陷）。
- 不提供多 gateway 实例下的跨进程缓存一致性（当前唯一部署形态为单实例；升级前置条件见第 6.3 节）。
- 不引入任何冗余存储表、不新增第二条缓存失效链（第 5 节论证）。

## 4. 语义定义（新契约）

### 4.1 成员资格公式

**两个主体必须区分**（对齐第 2 节事实 7 的调度实态）：

- **资格主体**：`group_accounts` 绑定的 `accounts` 行（直连账户或授权实例账户）。静态门与授权门都判在它身上。
- **模型事实主体**：`COALESCE(source_accounts.id, accounts.id)`（直连账户即自身；授权实例账户即其来源账户）。`account_supported_models` 与 `account_model_mappings` 都按它读取；provider 归属取 `COALESCE(source_accounts.provider_code, accounts.provider_code)`。

以下是成员集合的逻辑示意，不是可直接执行的完整 SQL。实际装载结果须保留资格主体/模型事实主体 ID、协议档案、授权依赖和到期时间，完成授权门与代码侧映射判定后再按模型名去重，不能提前只取 `DISTINCT model` 而丢失这些判定依据。

```
成员 = 直接支持模型 ∪ 有效映射源模型（第 4.2 节定义"有效"）

FROM group_accounts ga
JOIN groups g  ON g.id = ga.group_id
JOIN accounts a ON a.id = ga.account_id
LEFT JOIN accounts src ON src.id = a.authorization_instance_source_account_id

静态门（WHERE，全部判在资格主体，实例时对齐 chainCandidateWhere 的 source_accounts 分支）：
  ga.group_id IN ({Key 激活绑定的分组 ID 集})
  AND ga.system_account_id = g.system_account_id              -- 分组属主域（对齐 GroupOwnerSystemAccountID）；调用方只用于授权门
  AND ga.enabled = 1
  AND g.enabled  = 1
  AND a.provider_code = g.provider_code
  AND a.deleted_at IS NULL
  AND a.schedulable = 1
  AND a.status IN ('active', 'rate_limited', 'temporary_unavailable')
  AND (a.account_expires_at IS NULL OR a.account_expires_at > {now})
  AND (a.authorization_instance_authorization_id IS NULL AND a.type IN ('api_key','oauth','google_oauth')
       OR（实例臂）：a.authorization_instance_authorization_id IS NOT NULL
         AND src.deleted_at IS NULL AND src.provider_code = g.provider_code
         AND src.type IN ('api_key','oauth','google_oauth')
         AND src.status IN ({同上状态集}) AND src.schedulable = 1
         AND (src.account_expires_at IS NULL OR src.account_expires_at > {now})
         AND (src.last_error_code IS NULL OR src.last_error_code <> 'account_expired'))

直接支持模型（模型事实主体无 supportedModels 行的账户不产出任何行，见第 4.3 节裁决）：
  JOIN account_supported_models asm
    ON asm.account_id = COALESCE(src.id, a.id)               -- 模型事实主体
   AND asm.provider_code = COALESCE(src.provider_code, a.provider_code)
  SELECT DISTINCT asm.model

有效映射源模型（DB 层条件；代码侧四道判定见第 4.2 节，在装载器内过滤）：
  JOIN account_model_mappings m
    ON m.account_id = COALESCE(src.id, a.id)                 -- 模型事实主体
   AND m.provider_code = COALESCE(src.provider_code, a.provider_code)   -- 供应商门（对齐调度 :581）
   AND m.enabled = 1
  WHERE EXISTS (SELECT 1 FROM account_supported_models asm2
                WHERE asm2.account_id = COALESCE(src.id, a.id)
                  AND asm2.provider_code = COALESCE(src.provider_code, a.provider_code)
                  AND asm2.model = m.upstream_model)
  SELECT DISTINCT m.source_model
```

分组 ID 集 = `GatewayAPIKeyRow.GroupBindings` 中 `Status=="active"` 的绑定（与现行 `gatewayModelsProviderCodes` 同一遍历），SQL 内的 `g.enabled=1` 是权威复核（绑定行上的 `GroupEnabled` 只是缓存快照）。`调用方` = API Key 属主 `system_account_id`，仅用于授权门；`分组属主` = `g.system_account_id`，用于 `group_accounts` 候选域过滤并与 `GroupOwnerSystemAccountID` 对齐。

### 4.1.1 授权门（配置态子集，对齐 `resolveGroupAccess` + `resolveChainAccountAccess` + `canScheduleChainAuthorizedAccount`）

静态门之上，必须先按调用方执行分组访问判定 `resolveGroupAccess`：无访问资格则整组不贡献模型，不能因为某个账户归调用方所有而绕过组级授权。分组访问有效后，资格主体再通过**按调度实态顺序**执行的访问臂；调用方 = API Key 属主。授权行有效性的配置态谓词（与调度三查询同款）：`status = 'active'` 且 `(expires_at IS NULL OR expires_at > now)` 且 `grantee_system_account_id = 调用方`。

**臂判定顺序是规范的一部分（对齐 `resolveChainAccountAccess` 的分支顺序）**：

1. **实例臂（最优先且互斥）**：`a.authorization_instance_authorization_id IS NOT NULL` 的账户**只**适用本臂——
   - `a.system_account_id ≠ 调用方` → **直接拒绝**，不得落入授权分组臂（否则"含 A 实例账户的分组再授权给 C"时 C 会越权看到 A 的实例模型，见验收第 16 条）；
   - 按 `a.authorization_instance_authorization_id` 查到有效授权行；
   - 绑定级 `ga.account_authorization_id` **必须非空且与该授权行 id 精确一致**（调度最终门；供应不变式保证正常写入恒非空——事实 11）。
2. **属主臂**：直连账户（无实例授权 ID）且 `a.system_account_id = 调用方` → 放行。
3. **授权分组臂**：仅适用于**直连账户**。分组访问形态为 authorized（`resolveGroupAccess` 全链：分组 `enabled=1` + 组级授权行对调用方有效 + **`group_authorization_settings` 三态**——不存在 → 放行（沿用组默认）；存在且 `enabled=0` → **拒绝**；存在且 `enabled≠0` → 放行），且 `a.system_account_id = 分组属主`（免账户级授权行）。
4. **owner 域账户授权臂**：直连账户、账户归他人所有、分组为 owner 域：存在有效授权行（未绑定限定时按 `resource_type='account' AND resource_id=a.id` 解析；绑定限定时按 `ra.id = ga.account_authorization_id` 解析），且绑定 ID 一致性按调度实态判定。

**属于配置态、进授权门的**：授权行 `status`（撤销/暂停即失效）、授权行 `expires_at`、grantee 归属、绑定授权 ID 一致性、分组授权形态与本地 settings 三态。**不进授权门的**：授权额度 `limits_json`（请求期逻辑）、调用方的配额与限流（请求期）。授权状态属于配置态的理由：撤销/暂停/过期是管理动作或确定性时点，语义上等同"该授权关系不再存在"，与"分组禁用踢出成员"同层。

实现要求：聚合 SQL 的授权臂分支必须与 `resolveGroupAccess` / `resolveChainAccountAccess` 及 `ListOpenAIAccountsForGroupResult` 的后置绑定门（`chain_accounts.go:348-355`）逐条对照并加注释互引；不能只复刻前置访问臂而漏掉 authorized 账户的绑定 ID 必填门。臂顺序必须与调度一致（实例臂互斥不得被分组臂吸收）；授权分组形态判定与授权行装载在装载器内与聚合同批执行（第 6.2 节），不依赖请求期上下文。

### 4.2 决策：映射源并入，语义为"配置能力并集"；"有效映射"的完整定义

**并入的理由**：调度语义（现行契约明文）是"`sourceModel` 不受 `supportedModels` 限制"但映射命中可直接调用。若列表只含 supportedModels，客户端按列表配置会漏掉实际可用的映射源模型。

**"有效映射"= DB 条件（第 4.1 节 SQL）+ 四道代码侧判定（第 2 节事实 9）**：源端点族在可接受集、协议档案排除、恒等改写拒绝、运行时转换矩阵支持。理由：只按"启用 + upstream 在 supportedModels"筛选会把**存在于库但运行时不可执行的映射**（矩阵不支持族对、恒等行、档案排除）列进列表——恰是"配置能力并集"最需要避免的"列出实际完全不能调用的模型"。装载器必须用**模型事实主体**的协议档案和 provider code 调用 `gatewayopenai` 的同一判定函数源（授权实例不得用包装账户的档案），禁止在聚合 SQL 或新代码里复刻第二份矩阵；矩阵演化时两侧自动同步（第 6.2 节）。

**语义边界**：本设计的列表是**配置能力并集**，不是"瞬时可调用集合"的严格等价物。剩余偏差来源有二，均为已接受取舍：

1. **端点族合并**：`account_model_mappings` 的 PK 是 `(account_id, source_model, source_endpoint_family)`（事实 14），同一 `source_model` 可在不同端点族各有一行。列表是扁平模型名，跨端点族去重后单条目呈现。客户端在列表看到某模型，只代表"存在至少一个端点族上的有效映射或直接支持"；该模型在特定端点是否可调仍由调度判定，列表不承诺。
2. **运行态偏差**：冷却、熔断、Key-模型短屏蔽不反映（第 4.4 节）。

**对齐细节**：只并入 `upstream_model ∈ 模型事实主体 supportedModels` 的有效映射源，与调度 SQL（`chain_accounts.go:574-600`）的接受条件一致；`source_endpoint_family` 不参与列表成员资格（只造成上述去重合并）。

转换矩阵的当前取证基线如下（`gatewayopenai/mapping.go:118-154`）；先执行源族可接受集与档案排除，再应用此表，表外族对拒绝。实现和测试仍以同一判定函数源为准，不按此表新建第二份代码矩阵。

| 模型事实主体条件 | source → upstream 允许族对 |
| --- | --- |
| 所有档案 | 同族模型名改写；`stream_generate_content → generate_content` |
| OpenAI 协议档案（ProtocolCode/ProtocolVersion 判定） | `responses → chat_completions` |
| `provider_code=hybrid` | `responses/messages/generate_content/stream_generate_content → chat_completions`；`chat_completions/responses/generate_content/stream_generate_content → messages`；`chat_completions/responses/messages → generate_content` |
| 媒体源族 `video_generation`、`tts` | 仅同族模型名改写；不接受媒体与文本族之间或两个媒体族之间的转换 |

源族可接受集为 `chat_completions`、`responses`、`messages`、`generate_content`、`stream_generate_content`、`video_generation`、`tts`；`GeminiOpenAIChatProfileID` 的 `messages` 源族即使族对符合表格，也被前置档案门排除。模型名与族全同的恒等行始终不是映射。

### 4.3 决策：空 `supportedModels` 的裁决

**裁决：空集合 = 非法/历史脏数据，聚合剔除，贡献零模型；不允许展开为"全部模型"。**

理由：

1. 契约权威《账户模型限制设计》明文「未配置支持模型的账号不作为任意模型兜底候选」——按契约，空集合账户本就不该对任意模型成为候选；
2. "匹配任意模型"无法转换为有限列表——`/v1/models` 的成员资格必须是可枚举集合，展开语义在实现上不存在；
3. 管理写路径（创建 `write.go:504`、编辑 `patch.go:587`、导入、批量、OAuth 建户默认回填）全部强制非空，空集合只可能是历史数据、直写数据或迁移数据——按"非法数据不产生可见能力"处理，而不是给它发明展示语义。

**如实记录的现存矛盾**：调度 SQL 实态把空集合当 rank-2"匹配任意模型"（第 2 节事实 13），与上述契约相悖。本设计不改调度（非目标）；该矛盾登记为后续独立修复项（第 9 节）。列表与调度的这一偏差只在脏数据场景出现，修复调度侧后自然消失。

### 4.4 决策：列表反映配置态，不反映运行态

**门条件取 `chainCandidateWhere` 静态子集 + 第 4.1.1 节授权门配置态子集**。**明确排除**：

- `cooldown_until`（分钟级自愈态；调度里它还受 `includeUnavailable` 开关翻转）；
- 熔断 / 健康投影 / Key-模型短屏蔽（Redis 运行态）；
- 授权额度与请求期限流。

**为什么排除**：

1. 列表的消费者是客户端的**静态配置**（用户照着列表配模型）。运行态是自愈的、分钟级翻转的，把它折进列表只会造成列表抖动；客户端可能长期缓存列表，抖动会被放大成"模型忽有忽无"的体验事故。
2. 现行 `/v1/models` 完全不看账户，新语义取静态门已经完成"从目录语义到账户语义"的收敛；把"此刻可调度"做成列表语义是无上限的追认成本（任何运行态变化都要进失效链）。
3. `status` 白名单取放宽档 `'active','rate_limited','temporary_unavailable'`：这三档是调度在 `includeUnavailable` 下会使用的全部状态，排除它们（只留 `'active'`）会让限流中的账户模型从列表消失，同样制造抖动。`pending_test` 不在白名单——与调度一致，未测活的账户不对外展示能力。

### 4.5 决策：目录过滤退役出成员资格

`catalog_visible`、可见价格、音视频/realtime 模式过滤不再影响 `/v1/models` 列出什么。**为什么**：这三者回答"目录里什么值得卖/展示"，是计费与运营语义；用户对本功能的诉求是"这个 Key 背后的账户能提供什么"，是能力语义。成员资格只由第 4.1/4.1.1 节的账户门与授权门决定。目录自身（管理面、计费、模型检测推荐）不受影响。

### 4.6 失败语义（具体契约）

现状缺陷形态：`ListClientModelCatalog` 无 error 返回，装载失败 `return nil` → **200 空列表**（第 2 节事实 17）。新契约：

1. 新端口方法 `ListGatewayKeyModels(ctx context.Context, systemAccountID string, bindings []GatewayModelBinding) (GatewayKeyModelList, error)`，内含模型条目与 `validUntil`（第 6.3 节）。`ModelsResponseInput` 新增请求 `Context`，由 preflight 的 `ctx` 传入，贯穿缓存等待和数据面装载；不以 `context.Background()` 代替请求取消。singleflight 的共享后台装载可按既有缓存模式使用独立有界 context，但单个等待者取消不能取消其他等待者，取消者须及时退出。
2. **数据面失败**（聚合 SQL 错误、授权行/分组设置装载错误、目录字典 loader 错误）→ 装载器返回错误，不吞错、不回退目录、不静默空列表。
3. **错误响应契约**：
   - HTTP 状态码：`500`；
   - 内部标准载荷的 `type=internal_error`、`code=models_list_unavailable`；message 走 `LocalizedGatewayErrorPayload` 本地化。经 `GatewayErrorPayloadForProtocol` 转换后，OpenAI/Codex 输出 `error.type=internal_error`，Anthropic 输出外层 `type=error` 与 `error.type=api_error`，Gemini 输出 `error.status=INTERNAL`；三者均保留相同的 message 与 `error.code=models_list_unavailable`。外部协议的字段与类型值不要求字面相同。
4. **发送与错误传递责任**：`sendModelsGatewayResponsePayload` 改为 `(any, error)`，`sendModelsGatewayResponse` 与 `ResponseSink` 四个 models sender（Authenticated/OpenAI/Anthropic/Gemini）均改为返回 `error`。装载失败时 sender 不写 HTTP、不 finalize、不记成功用量。preflight 的 before-auth 与 Identity 注入两处调用点必须检查错误，共用包内 helper：输入请求/响应、audit、usage、startedAt、**已经判定的 models 协议**和原始错误，构造 500 标准载荷并调用 `Responses.SendGatewayFailureResponse` 一次。为此 `FailureResponseInput` 增加 `Protocol GatewayErrorProtocol`：非空时 sink 使用显式协议，为空时其他既有调用保持当前路径推断；由既有失败 sink 完成回包、失败审计与失败用量，helper 只补 `authenticated_models_list_load_failed` 元数据。before-auth 返回已完成 `(true, nil)`，Identity 返回已完成的零 `PreflightResult, nil`，禁止裸 error 落到外层 generic 500、重复写响应或进入上游派发。头部指定 Anthropic/Gemini 的 `/v1/models` 与 `/v1beta/models` 均按显式 models 协议输出。`gatewayresponse` 私有的 `sendGatewayErrorResponseForSink` 不作为 preflight 调用接口。
5. **缓存面失败不失败请求**：Redis 读失败按未命中继续，写入/清理失败记 WARN；数据面仍必须成功装载才可返回 200。失效通过第 6.3 节的启动 token 与 generation 使旧 Redis 键逻辑不可达，清理失败不得重新引入陈旧集合；TTL 只负责残留旧键的空间回收。
6. **审计**：失败时 `auditCapture.AddGatewayMetadata("authenticated_models_list_load_failed", {reason, traceID, …})`（命名对齐同链路 `"authenticated_models_rate_limit"` 惯例），并保留现行失败审计终态。
7. 空列表只允许来自"聚合成功且结果为空"（第 4.7 节），不允许来自错误。

### 4.7 空态

Key 无激活绑定、绑定分组全部禁用、分组无在册可调度账户 → 返回各协议形态的**空列表**（HTTP 200，OpenAI 形态 `{"object":"list","data":[]}`）。不报错、不回退到目录。

### 4.8 不变项清单

- 鉴权：仍要求有效 Gateway API Key（Bearer/`x-api-key`/`x-goog-api-key` 按协议），无 Key 仍走现行的 before-required-auth 本地拒绝路径。
- models 端点专用限流：不变。
- 响应协议判定（explicit gemini/anthropic 客户头优先，否则按请求路径协议）、Codex 客户端识别（originator/user-agent/`x-codex-client`/`client_version`）：不变。
- 转发开关恒 false（不转发上游）：不变。
- 响应缓存头（`Cache-Control`/`Vary`）：不变。

### 4.9 元数据：目录降级为字典

四种协议形态的响应结构不变，元数据来源调整：

1. **字典装载**：按绑定的去重 provider codes 复用现有 `ListCachedProviderModelCatalogAsync`（缓存与失效原样不动），在 active 行内按现有 scope 优先级（personal > global > built_in）取每模型最优行，构建 `map[模型名]目录条目`。
2. **命中**：模型在字典中 → 沿用现有条目全字段（`created`、`owned_by`、Codex 富字段按目录数据填充），`owned_by` 规则不变（built_in → `"openai"`，其余 → `"juhe-ai"`）。
3. **未命中（合成条目）**：模型不在字典 → 构造空目录条目（仅 `Model` 字段）进入**现有 builder 原样加工**。因此合成条目继承 `buildCodexModelInfo` 的现行默认值（第 2 节事实 18），明确契约如下：`Slug=DisplayName=模型名`、`ShellType="shell_command"`、`Visibility="list"`、`SupportedInAPI=true`、`BaseInstructions` 为 Codex 固定串、`ContextWindow=MaxContextWindow=272000`（回退值）、`InputModalities=["text","image"]`（回退值）、`EffectiveContextWindowPercent=95`、`TruncationPolicy={bytes,10000}`、`DefaultReasoningSummary="auto"`、`WebSearchToolType="text"`、`Description=nil`、无 reasoning levels / service tiers / multi-agent；OpenAI 形态 `created=0`、`owned_by="juhe-ai"`。**即：合成条目允许返回这些默认能力字段**——这是现行 builder 对无数据条目的一致行为，不为合成条目另造一套默认值，也不把 272000/`["text","image"]` 解读为对模型能力的承诺（与音频设计 §4.3 的目录回退语义一致）。
4. **排序**：按模型名字典序升序，稳定确定性（替代现行目录运营排序 `clientCatalogCompareItems`；客户端对模型列表顺序无契约依赖）。
5. **去重**：UNION 天然去重；列表为扁平模型名数组。

## 5. 方案对比与选型理由

### 5.1 三个候选

| | C：API Key 维度冗余表（原始提案） | A：分组维度冗余表 | **B：读时聚合 + 双层缓存（选定）** |
| --- | --- | --- | --- |
| 存储形态 | `api_key_models(api_key_id, model)` 物化 | `group_models(group_id, model)` 物化 | 无新表，一组聚合 SQL |
| 读路径 | 单 Key 主键范围扫，最快 | `WHERE group_id IN (…)` | 同 A 的查询语义，外加双层缓存 |
| 维护触发 | **扇出到 Key 级**：一个账户改模型/换组，所有可达 Key 的行都要重算；账户编辑、分组绑定、策略绑定、Key 换绑、启停、映射变更……全部写路径（10+ 处）都要挂更新钩子 | 扇出收敛到分组级，但同样要挂全套写路径 | 无物化重算钩子；沿用运行时失效入口，遗漏的写路径触发点仍须补齐 |
| Schema 代价 | 新表 + 7 处 schema 文件（PG 表/索引、SQLite 镜像、contracts 白名单、dataset manifest、golden 计数测试）+ seed | 同左 | **无** |
| 漂移风险 | 有：任何遗漏的写路径都会造成永久漂移，需要重建工具与巡检兜底 | 有 | **无** |
| 状态/授权/映射有效性条件纳入成本 | 每纳入一个条件（账户启停、授权撤销、到期、转换矩阵演化）就多一批触发钩子 | 同左 | 一个 WHERE 条件 / 一次复用函数的内存过滤 / 一项 validUntil 计算 |
| 与项目既有决策 | 相悖 | 相悖 | 一致 |

### 5.2 为什么否决"API Key 维度冗余表"（原始提案）

提案的动机——避免每次请求实时并集——是真实约束，方案 B 已满足（第 5.4 节）。但 Key 维度物化本身有两个结构性问题：

1. **扇出方向错误**。链条是 Key → 策略 → 分组 → 账户。一次账户 supportedModels 编辑影响的 Key 数 = 所有链路可达它的 Key，这是系统里扇出最大的一端；而分组数远小于 Key 数。同一调用方、同一策略绑定分组集下的所有 Key 并集结果相同，Key 维度物化等于把同一份数据复制 N 份，没有信息增量，只有一致性负担；不同调用方仍须分别校验授权，不能跨调用方共享结果。
2. **写路径挂钩无法收敛**。第 2 节事实 5、16 取证的影响写路径超过 10 处（账户编辑/建/删、批量编辑、分组绑定、策略绑定、Key 换绑、启停、导入、OAuth 建户、jobs 清理、授权实例供应/回收）。每处都必须在事务内正确更新冗余表，任何一处遗漏就是静默漂移；授权行撤销/暂停/到期这类**不经过账户写路径**的状态变化（授权独立模块、自然到期）、以及**映射有效性矩阵演化**（代码变更即语义变化）在 Key 维度表下还需要额外的扫描、触发或重算机制。配合 SQLite 镜像（jobs 侧 FK 不生效，需显式 DELETE）与 golden 计数测试同步，维护面远超功能本身。

### 5.3 为什么否决"分组维度物化表"

A 修复了扇出方向（账户变化只影响其所在分组的行），但保留了 C 的全部固定成本：schema 七件套、写路径挂钩、漂移兜底；授权归属是 **(调用方, 账户)** 二维事实，分组维度的行仍要按调用方再展开或读时过滤，物化收益进一步稀释。它相对 B 的唯一收益是"缓存未命中时少算一组毫秒级 SQL"——在单机 Docker 单 gateway 实例、Key 与分组规模有限的当前形态下，这个收益没有可观测价值。若未来出现多实例 + 大规模 Key 的形态，B 的聚合 SQL 就是 A 的回填语句，升级路径无冲突（第 9 节）。

### 5.4 为什么 B 满足"不能每次请求实时并集"

- **读路径（按实现实态描述）**：redis runtime 模式下，请求先读 Redis 共享缓存（亚毫秒），命中即返回（共享命中时回填进程内条目）；memory 模式下读进程内 entryCache。未命中进入 singleflight 合并的后台装载：执行聚合 SQL + 授权臂判定 + 映射有效性过滤，写回两层缓存。并发未命中只算一次。
- 聚合的输入（分组 ID 集）来自 Key 记录缓存里已有的绑定行，**不新增任何装载**。
- 性能预期（**实测见下，热命中为缓存单元测试保证的零 SQL**）：按分组绑定、模型事实主体的 supportedModels 与映射行总数扫描，单次目标毫秒级。管理写路径的每账户 ≤64 只约束 supportedModels，映射表没有统一可依赖的表级行数上限，不能把总成本也写成每账户 ≤64。可用索引为 `group_accounts` PK 分组前缀、`account_supported_models` PK 账户前缀、映射表 PK/两个二级索引及授权查询索引；是否采用索引、是否产生全表扫描，须用实际聚合 SQL 的 PostgreSQL `EXPLAIN (ANALYZE, BUFFERS)` 与代表性数据验证，不能由索引存在直接推定。
- 实测记录（2026-10-10，dev 临时子库 `juhe_ai_sub2api_dev_unionperf`，已用后删除；harness 为 `backend-go/projects/gateway/cmd/juhe-ai-gateway/chain_gatewaykeymodels_perf_test.go`，`JUHE_AI_UNION_PERF_DSN` 门控手动运行）：
  - 规模：3 分组 × 100 个 active 直连账户 = 300 账户，supportedModels 19200 行（每账户 64，相邻账户 50% 重叠），映射 3000 行（每账户 10 行：8 行可通过 `IsAdmissibleModelMapping`、2 行恒等行被排除）；映射加压场景把映射加到每账户 64 行 = 19200 行（全部可接受）。
  - 每轮 SQL 次数恒为 12（3 组 × 4 条：分组访问、候选、supportedModels 批量、映射批量），其中授权查询 0 次（调用方=分组属主，owner 臂与批量预取空参短路均不产生授权查询）。20 轮采样计数无波动。
  - 冷调用耗时（装载器全量 SQL 路径，含 dev 网络往返，20 次采样）：映射 3000 行场景 p50 195ms / p95 214ms / max 216ms / 均值 196ms，首次预热（含计划编译）284ms；映射 19200 行场景 p50 408ms / p95 450ms / max 629ms / 均值 423ms。耗时主体是 12 条顺序查询的网络往返，服务端执行合计为数十毫秒量级；热命中不执行任何并集 SQL。
  - EXPLAIN (ANALYZE, BUFFERS)（seed 后 ANALYZE，映射表 19200 行）：候选 SQL 在夹具规模（accounts/group_accounts 各 300 行）被规划器选为顺序扫描，execution ≈2.7ms——小表上顺序扫描即最优，且同 SQL 在陈旧统计下曾选中 `idx_group_accounts_group_enabled` / `idx_accounts_provider_status` / `accounts_pkey` 索引路径，索引可用、组内占全表比例随规模下降后会重新生效；supportedModels 批量 IN(100) 取 6400/19200 行（33% 选择率）顺序扫描 execution ≈17.9ms；映射批量 IN(100) 取 6400 行顺序扫描 execution ≈52.8ms（含排序）。批量查询在该选择率下顺序扫描为规划器最优选择，未出现劣化计划。
  - 结果 sanity：映射 3000 行场景并集去重 6496 个模型、19200 行场景 22696 个，均与夹具推演的期望去重数一致。
- 实施交付记录冷缓存 SQL/授权查询次数、冷热耗时，以及分组数、账户数、supportedModels/映射行数。至少覆盖当前规模与映射行较多的场景；热命中验收为新增并集 SQL 执行次数为零（实测记录见上）。

### 5.5 与项目既有决策的一致性

《账户模型限制设计》性能设计节已裁决：「后续如果单个分组账号池过大，再增加 `groupId + systemAccountId + model` 的派生候选缓存；第一版不引入，**避免同时维护两套缓存失效链路**」。方案 B 严格遵守该裁决：唯一新增的缓存挂在既有 `InvalidateGatewayRuntime` 失效总线上（第 6.3 节），不发明第二条失效链。引入物化表（A/C）则同时违背"两套失效链"约束与"最小改动"原则。

## 6. 详细设计

### 6.1 读取链路（改造前后）

```
改造前：
preauth(models 判定) → preflight before-auth 分支
  → ResolveGatewayAPIKeyForModelsAsync（Key 校验 + 记录缓存）
  → gatewayModelsProviderCodes(record) → []providerCode
  → 限流 → sink.sendModelsGatewayResponsePayload
  → ports.ModelCatalogLoader.ListClientModelCatalog(systemAccountID, providerCodes)（无 error，失败静默空）
  → selectClientCatalogItems 过滤 → 四协议形态输出

改造后（变化点加 ★）：
preauth(models 判定) → preflight before-auth 分支
  → ResolveGatewayAPIKeyForModelsAsync（不变）
  ★ gatewayModelsBindings(record) → []{groupID, providerCode}（同一遍历，多取 GroupID）
  → 限流（不变）→ ★ models sender / sendModelsGatewayResponsePayload（增加 error 返回）
  ★ ports.ModelCatalogLoader.ListGatewayKeyModels(ctx, systemAccountID, bindings) (GatewayKeyModelList, error)
      内部：
      a. groupModelUnion 缓存（第 6.3 节）→ {[]model, validUntil}
      b. 缓存未命中：聚合 SQL（静态门 + 模型事实主体 COALESCE + 映射 provider 门）
         + 授权臂判定（4.1.1，含 settings 三态，与聚合同批）
         + 映射有效性过滤（4.2，复用 gatewayopenai 判定函数）
         + 空集合剔除（4.3）+ validUntil 计算
      c. 目录字典：按去重 providerCode 复用现有 ListCachedProviderModelCatalogAsync（不变）
      d. 合并：成员 ∪ 字典元数据 / 合成条目（第 4.9 节）→ 条目列表
      e. 任一数据面装载失败 → 返回 error（第 4.6 节；缓存面失败按既有容错降级）
  ★ 四协议形态输出（结构不变，数据源切换）
  ★ 装载错误 → sender 返回 error 且不写响应、不记成功副作用
    → before-auth / Identity 两处调用点检查 error
    → 显式 models 协议 + SendGatewayFailureResponse → 500 + 失败审计/用量 → 终止请求
```

### 6.2 聚合 SQL、授权臂与映射有效性装载

语义见第 4.1/4.1.1/4.2 节。实现要点：

- 静态门 SQL 与 `chainCandidateWhere`、授权臂分支与 `resolveGroupAccess` / `resolveChainAccountAccess` **逐臂逐条对照并注释互引**（臂顺序含在内），防止两边语义漂移；
- 授权分组形态判定（组级授权行 + settings 三态）与账户级授权行查询在装载器内**同批执行**（有界次数的小查询：每组一次组级判定 + 每批一次授权行批量查询），全部发生在缓存未命中路径上；
- **映射有效性过滤在 Go 侧执行**：SQL 只负责取回候选映射行（含 source/upstream 端点族与**模型事实主体**的账户协议档案列；授权实例不得误用包装实例账户档案），装载器逐行调用 `gatewayopenai` 导出的单条映射可接受性判定（源族集合、档案排除、恒等拒绝、转换矩阵——与 `ResolveAccountModelMapping` 同一函数源）过滤后并入；**禁止在 SQL 或新代码里复刻矩阵**；
- 空 `supportedModels`（模型事实主体无行）账户不产出任何模型（第 4.3 节裁决，无需特判——UNION 天然不产出）；
- `now` 统一取装载时刻，`validUntil` 与聚合同批计算（第 6.3 节）。

### 6.3 缓存设计

- **缓存对象**：`{models []string, validUntil time.Time}`——模型集合 + 有效期界，与元数据解耦（元数据字典已有自己的缓存）。
- **业务键**：`callerSystemAccountID + ":" + sha256(去重、排序后分组 ID 集的确定性编码)`（这里的 `callerSystemAccountID` 是 API Key 属主，用于区分授权结果；SQL 内的 `group_accounts.system_account_id` 仍按每个分组的属主过滤；分组集相同且调用方相同的不同 Key 共享条目）。
- **版本键**：新并集缓存专用的 `processStartToken`（每次进程启动唯一）+ `unionGeneration` + 业务键，作为 Redis、本地缓存与 singleflight 的键。Redis 可直接复用 `SharedCacheFactory.Cache("gateway:group-model-union:" + token + ":" + generation)`，桶内使用业务键；这样既有 `SharedCache.Clear` 清理的是旧版本桶，不需扩大通用共享缓存接口。`unionGeneration` 在既有运行时失效入口无条件递增；这是该失效链内的版本守卫，不新增失效通道。启动 token 防止重启后命中旧条目；generation 防止 Redis 删除失败或旧 loader 回写时恢复旧集合。同进程、同一代的不同 Key 仍按业务键共享结果；当前不提供跨进程缓存复用。
- **两层（按实现实态）**：redis runtime 模式先读共享桶 `gateway:group-model-union`（命中回填进程内），写入进程内与 Redis 两层；memory 模式只读写进程内 entryCache。singleflight 合并并发未命中。Redis 读写失败按既有容错降级（读=未命中、写=WARN，第 4.6 节），不失败请求。
- **TTL 与到期一致性**：基础 `groupModelUnionBaseTTL = 1h`。条目有效期 `validUntil = min(装载时刻 + 1h, 最近未来到期点)`——最近未来到期点 = 贡献该并集的全部行中**未来的** `accounts.account_expires_at`（含实例的来源账户）与访问链依赖的有效授权行 `resource_authorizations.expires_at`（包括组级授权和账户级/实例授权）的最小值；全部无未来到期点时取基础 TTL。命中后或 loader 返回前若 `now >= validUntil`，视为未命中重算；Redis 物理 TTL 不得超过发布时剩余有效期，回填不能重新起算 1h。账户/来源账户/授权自然到期后，下一次读取必须重算。`api_keys.expires_at` 不在 validUntil 内——Key 自身过期由更早的 Key 校验层处理。
- **失效关系**：**不使用目录 reason 白名单**（第 2 节事实 16）。并集缓存随 `ClearGatewayRuntimeCacheLocal` 无条件推进 `unionGeneration`、清空本地与 pending，使旧版本键**立即逻辑不可达**；Redis 旧键删除只用于尽力回收空间，失败记 WARN，不影响下一次请求读取新代事实。清理不得删除已发布的新代键（限定旧 token/generation 的键范围，不能异步清空整个桶）。理由：并集的账户、分组、绑定、映射、授权依赖属于核心运行时事实，沿用唯一运行时失效入口。
- **写路径 → 失效覆盖依据（契约要求）**：实施交付必须包含一张覆盖表并配契约测试，核对下列已核实路径均触发 `InvalidateGatewayRuntime`（即无条件清空并集缓存）：账户编辑 `account_management_patch` / 创建 `account_created` / 删除 `account_deleted`（`accounts/invalidation.go:68-73,146,196,264`）、批量编辑 `account_batch_updated`（`batch_effects.go:324`）、策略路由 `route_strategy_created/updated/deleted`（`mutations.go:143,420,563`）、API Key `api_key_updated`/`api_key_quota_updated`（`apikeys/patch.go:34-37`）、分组 `group_created/updated/deleted`（`groups/store.go:1395,1733,1877`）。**范围内核查义务**：模型映射编辑、授权行撤销/暂停、分组授权形态与 settings 变更、授权实例供应/回收（`authz/instance_provision.go`）等路径若未触发运行时失效，属于**必须在本交付内补齐触发的缺陷**（补触发，而不是给并集另立失效通道）；仅 `expires_at` 类自然到期不依赖写路径，由 validUntil 覆盖。
- **并发规则与保证范围**：**保证范围 = 单 gateway 进程**（当前唯一部署形态）。新缓存使用专用 `unionPublicationMu`；本地发布的 generation 检查与写入、失效的 generation 推进与本地/pending 清空，必须在同一临界区串行，不能复制目录缓存的检查/写入分离窗口。Redis GET 与 loader 可在锁外执行，但捕获的版本键不可变；命中提升/返回及 loader 发布前必须在该锁下复核 generation 与 `validUntil`。旧代结果不得回填本地或直接交给等待者，须重新加入当前代读取/装载；请求取消则返回原始取消错误，不无限等待。Redis SET 始终使用捕获的版本键，即使完成在失效之后，也只产生不可达旧键。禁止持有全局 `Service.mu` 跨 Redis I/O；若需嵌套锁，固定先专用锁后短时 `Service.mu`，不得反向获取。**多实例前置条件**：启动 token 只隔离本进程旧缓存，不能替代跨实例失效传播；未来多 gateway 须先补齐跨进程通知/共享版本与 fencing 测试，才能宣称管理写在全部实例即时生效，当前不提供此保证。

## 8. 验收标准（可观察行为）

以绑定分组 G（owner 域，含直连账户 a1：支持 m1、m2，映射 m5→m1 启用；a2：支持 m2、m3）为例：

1. Key 绑定 G：`/v1/models` 恰好返回 m1、m2、m3、m5（字典序输出）。
2. 目录新增 m4（有价、可见）但无账户支持 → 不出现。
3. m1 的 active 目录行置 `catalog_visible=false`、移除可见价格或标记音视频/realtime 模式 → m1 仍出现且沿用该目录行元数据；仅当字典无 active 条目时才合成（owned_by=juhe-ai、Codex 默认值按第 4.9 节）。
4. a1 `schedulable=0` → m1、m5 消失（m2、m3 由 a2 维持）；a1 恢复 → 重新出现。
5. G 禁用或绑定禁用 → 空列表（200）。
6. Codex / Anthropic / Gemini 形态的模型 id 集与 OpenAI 形态完全一致。
7. 缓存命中期间重复请求无聚合 SQL 执行；账户模型编辑后（运行时失效联动）下一次请求反映新集合。
8. 无效 Key、限流超限的现行错误形态与状态码不回归。
9. **授权实例**：来源账户支持 m7、实例账户无自有模型行 → 授权实例所在分组的 Key 列表含 m7（模型事实主体 COALESCE）。
10. **授权门**：撤销/暂停账户授权行、或授权行过期 → 该授权贡献的模型消失；实例授权同理；实例绑定授权 ID 为空或不一致 → 不出现，非空且一致才放行。
11. **自然到期**：不写任何库，仅推进时钟越过账户/来源账户/授权行的未来到期点 → 下一次请求模型消失（validUntil 生效）。
12. **失败可观察**：注入聚合 SQL/授权/settings/字典装载错误 → 客户端收到 HTTP 500 + `code=models_list_unavailable`（按已解析的 models 协议适配，含显式协议头与 `/v1beta/models`），而非 200 空列表；失败审计/用量只记录一次，无成功终态、成功用量或上游请求。
13. **并发与缓存故障**：GET/旧 loader 与失效交错，或 Redis DEL 失败后 GET 恢复 → 旧版本结果不返回、不回填，下一次请求反映新集合；重启后仍有旧 Redis 键也不能命中。允许旧物理键存活至 TTL，禁止其参与当前代读取（mock 时序验收）。
14. **跨端点族**：同一 `source_model` 在两个端点族各有一行启用映射 → 列表单条目。
15. **settings 三态**：授权分组无 settings → 模型可见；settings `enabled=0` → 该组模型消失；恢复后重新出现。
16. **实例臂互斥**：A 的实例账户所在分组再授权给 C → C 的列表不含该实例贡献的模型（实例归属不匹配，不落入授权分组臂）。
17. **映射有效性**：恒等改写行、转换矩阵不支持的族对、Gemini 档案的 anthropic messages 源族行 → 均不进入列表；矩阵支持的有效映射源 → 进入。
18. **空集合**：模型事实主体无 supportedModels 行的账户（脏数据）→ 不贡献任何模型，不展开"全部模型"。
19. **租户门**：分组属主为 A、调用方为已获组级授权的 B 时，`ga.system_account_id=A` 的绑定可参与并集；查询必须按 `ga.system_account_id=g.system_account_id`，不能按调用方 B 过滤。另用不同分组属主域的绑定验证不会被错误并入；不构造违反 PK `(group_id, account_id)` 的重复行。
