> 动机：客户端通过 `GET /v1/models` 发现可用模型。当前实现返回的是**供应商模型目录**（`provider_model_catalog` + `custom_provider_models`），与调度实际使用的账户支持模型（`account_supported_models`）完全不同源——目录里"有价目但没有任何账户支持"的模型会被列出，目录不可见/无价的模型即使账户支持也不出现。本设计把 `/v1/models` 的成员资格改为**该 API Key 可达账户 supportedModels 的并集（配置能力并集）**，并以"读时聚合 + 双层缓存"实现：请求路径零 DB 成本、不新增 schema、不引入冗余存储表、不新增第二条失效链。

## 1. 背景与问题定性

### 1.1 问题现象

客户端（Cline、Roo、Cherry Studio 等按 `/v1/models` 渲染模型选择器的工具）拿到的模型列表与实际能调通的模型不一致：

- 列表里有的模型调不通：目录收录了模型并定价，但没有账户把它配置进 supportedModels（或支持它的账户全部不可调度/不可授权）。
- 列表里没有的模型能调通：账户把某个模型加入 supportedModels，但目录行 `catalog_visible=false`、无可见价格，或被音视频/realtime 模式过滤剔除。

### 1.2 根因

项目里存在**两套"模型集合"事实**，而 `/v1/models` 用了错误的一套：

| 事实 | 存储 | 消费方 |
| --- | --- | --- |
| 供应商模型目录（能卖什么、什么价） | `provider_model_catalog` + `custom_provider_models` | 计费、管理面、模型检测推荐、**当前 `/v1/models`** |
| 账户支持模型（这个账户能调什么） | `account_supported_models`（每模型一行）+ `account_model_mappings`（映射源） | 调度候选过滤、模型检测候选项 |

`/v1/models` 的成员资格应由第二套决定。这是**契约变更**：现行权威文档《账户模型限制设计》明文规定「`GET /models` / `GET /v1/models` 继续由本地供应商模型目录返回，不参与账户模型限制过滤」，实施本设计时必须先翻转该条契约（第 10 节同步清单）。

### 1.3 性能担忧的定性

需求方的直觉约束是"不能每次请求实时算一遍并集"。这个担忧成立的前提是把并集理解为"装载分组内全部账户 + 内存归并"。实际不是：

- 并集是**一组索引聚合 SQL**，输入是 Key 激活绑定已携带的分组 ID 集（零额外装载），数据面是几张小表的主键前缀扫描，单次成本目标为毫秒级（第 5.4 节，实测校准前均为目标值）；
- 项目已有成熟的请求路径缓存形态（供应商目录缓存的进程内 + Redis 共享 + singleflight，`gatewayruntimecache/catalog.go`），照搬其结构即可让 DB 聚合只在缓存未命中时发生。

因此"避免每次请求实时并集"不需要物化表，只需要"一组便宜的 SQL + 一层现成的缓存"。

## 2. 现状事实（代码基线，均已核实）

以下事实是本设计的出发点；行号基于 2026-10-09 工作区快照，实施时如代码已演化，以代码为准并回填本文。

1. **本地响应链路**：外部 HTTP 的 `/v1/models` 恒走本地目录响应，不转发上游（转发开关 `ForwardModelsRequestToUpstream` 在 `/v1` 入口恒 false）。链路：preauth 判定 models 请求（`gatewaypreauth/preauth.go:60-64`）→ preflight 的 before-required-auth 分支（`gatewaypreauth/preflight.go:166-179` → `handleGatewayModelsRequestBeforeRequiredAuth` :1314-1358）→ API Key 校验 + models 端点专用限流 → `gatewayresponse/sink.go:294-335` `sendModelsGatewayResponsePayload` → 端口 `ModelCatalogLoader.ListClientModelCatalog`（`gatewayresponse/ports.go:226-229`）→ 实现 `cmd/juhe-ai-gateway/chain_compose.go:908-935` `chainClientModelCatalog`。
2. **provider codes 的来源**：`gatewayModelsProviderCodes`（`preflight.go:1271-1286`）遍历 `GatewayAPIKeyRow.GroupBindings` 取 `Status=="active"` 绑定的去重 `ProviderCode`。
3. **Key 记录已携带分组 ID**：`GatewayAPIKeyGroupBindingRow` 含 `GroupID/Status/ProviderCode/GroupEnabled`（`gatewayruntimecache/types.go:146-159`）。取分组集合与取 provider codes 是同一次遍历，零额外查询。
4. **当前成员过滤**：`selectClientCatalogItems`（`chain_compose.go:955-989`）按 `status=active`、built_in 行 `catalog_visible`、有可见价格过滤并按 model 去重；目录 SQL 取自 `provider_model_catalog`（内置行）与 `custom_provider_models`（global/personal 作用域）（`chain_catalog.go:170-228`），另有音视频/realtime 模式过滤（`chainIsSupportedCatalogModel`）。
5. **账户支持模型存储**：`account_supported_models(account_id, provider_code, model, created_at)`，PK `(account_id, model)`（`pg_schema_business_tables.go:970-979`）；管理面强制非空、上限 64（`accounts/write.go:274-309`）。写路径收敛于 `Store.replaceAccountSupportedModels`（`accounts/write.go:1006-1018`）：管理面建户/编辑、OAuth 建户、导入、批量编辑；模型检测只读不写；jobs 仅在账户物理清理时删行（`cleanuprepo/deleteaccount.go:483`）。
6. **调度侧的"可调用集合"语义**：候选账户静态门为 `chainCandidateWhere`（`chain_accounts.go:244-266`）：`group_accounts.enabled=1`、`accounts.deleted_at IS NULL`、`accounts.status IN (statusSet)`、`accounts.schedulable=1`、未过期（`account_expires_at`）、可选 `cooldown_until` 门、授权实例账户追加源账户同门；模型匹配为"请求模型 ∈ supportedModels，或启用映射 `source_model` 命中且映射右侧 `upstream_model` ∈ supportedModels"（`chain_accounts.go:574-600` 的 SQL 与 `gatewayrouting/modelfilter.go:51-119` 内存过滤同语义）。`statusSet` 两档：默认 `'active'`，`includeUnavailable` 时放宽为 `'active','rate_limited','temporary_unavailable'`（`chain_accounts.go:493-497`）。
7. **模型事实主体与资格主体分离（调度实态）**：模型匹配按 `model_resource_account_id` 读取——`COALESCE(source_accounts.id, accounts.id)`，provider 同取 `COALESCE(source_accounts.provider_code, accounts.provider_code)`（`chainCandidateModelTail`，`chain_accounts.go:236-241`；模型匹配 SQL :574-600 按该列关联 `account_supported_models` / `account_model_mappings`）。`source_accounts` 是 `LEFT JOIN accounts ON source_accounts.id = accounts.authorization_instance_source_account_id`（:272）。即**授权实例账户的支持模型与映射事实挂在来源账户上**，实例行可以没有自己的模型行。
8. **授权门（调度实态）**：候选 SQL 之后还有授权判定（`chain_accounts.go:320-336`）：
   - 有效性谓词（三个查询共用）：`resource_authorizations` 行须 `status = 'active'` 且 `(expires_at IS NULL OR expires_at > now)` 且 `grantee_system_account_id = 调用方`（`activeResourceAuthorization*`，:909-982；表 DDL `pg_schema_business_tables.go:588-607`：`status` 默认 `'active'`、`expires_at`、`grantee_system_account_id`、`resource_owner_system_account_id`）。
   - 访问臂判定 `resolveChainAccountAccess`（:1037-1092）：实例臂（`authorization_instance_authorization_id` 非空）要求调用方 == 实例属主、按 ID 查到有效授权行、绑定授权 ID 一致；属主臂（直连账户属主 == 调用方）直接放行；授权分组臂（`groupAccess.GroupAccessType == authorized`）要求账户属主 == 分组属主（免授权行，组级有效性由 `activeResourceAuthorization(ctx,"group",groupID,…)` :847 + `group_authorization_settings` 决定）；owner 域授权臂要求按 `resource_type='account'` + `resource_id=账户ID`（或绑定授权 ID）查到有效授权行，绑定 `account_authorization_id` 一致。
   - `canScheduleChainAuthorizedAccount`（:1094-1110）：owner / 授权分组臂放行；账户授权臂要求授权行在有效集合中。授权额度（`limits_json`）是请求期逻辑，不属于候选门。
9. **映射表结构**：`account_model_mappings(account_id, provider_code, source_model, source_endpoint_family, upstream_model, upstream_endpoint_family, enabled, created_at, updated_at)`，PK `(account_id, source_model, source_endpoint_family)`（`pg_schema_business_tables.go:983-995`）。同一 `source_model` 可有多行（跨端点族）。
10. **缓存现状**：供应商目录缓存 = 进程内 entryCache（24h TTL，容量 1000）+ Redis 共享缓存（redis runtime 模式）+ singleflight 防击穿 + generation 守卫（`gatewayruntimecache/catalog.go:23-120`、`service.go:27,319-325`）。**读路径实态**：redis 模式下先读共享缓存（共享命中回填进程内），memory 模式只读进程内——并非"先进程内再 Redis"（:28-43）。**并发窗口（已观察事实）**：后台装载的 generation 检查（`isCatalogGenerationCurrent`）与缓存写入（`setCatalogCacheEntry`）是两次独立加锁，失效若插在两步之间，旧装载仍会回填进程内与共享缓存——本期新缓存不得复制该缺陷；目录缓存自身的该窗口修复不在本期范围（第 9 节）。
11. **失效机制现状**：失效由管理面写路径触发 `InvalidateGatewayRuntime(reason)` → `ClearGatewayRuntimeCache(reason)`（`invalidate.go:14-23`）。reason 判别只用于**可选**缓存：`ShouldInvalidateProviderModelCatalog` 白名单仅含 `custom_provider_model_saved / custom_provider_model_deleted / provider_model_configuration_updated` 三个目录事件（`service.go:58-65`，`gatewayresponse/failclass.go:155-161` 同源）；核心运行时缓存（runtimeCache / identityCache / groupCache / accountsCache 等）在 `ClearGatewayRuntimeCacheLocal` 中**不区分 reason 一律清空**并推进 generation（`invalidate.go:27-45`）。实测 reason 全集（写路径 → reason）：账户编辑 `account_management_patch`、账户创建 `account_created`、账户删除 `account_deleted`（`accounts/invalidation.go:68-73`）；批量编辑 `account_batch_updated`（`accountstransfer/batch_effects.go:324`）；策略路由 `route_strategy_created/updated/deleted`（`routestrategies/mutations.go:143,420,563`）；API Key `api_key_updated` / `api_key_quota_updated`（`apikeys/patch.go:34-37`）；分组 `group_created/updated/deleted`（`groups/store.go:1395,1733,1877`，经 RuntimeInvalidator K5 端口 :42-44）。**注意：账户模型变更走 `account_management_patch`，不在目录白名单内**。
12. **端口无错误语义（现状缺陷形态）**：`ListClientModelCatalog` 签名无 error 返回；实现里 `ListCachedProviderModelCatalogAsync` 出错时 `return nil`（`chain_compose.go:921-928`）——上游装载失败会被渲染成**200 空列表**。本设计的装载失败语义必须改变这一点（第 4.7 节）。
13. **Codex 形态的默认值实态**：`buildCodexModelInfo`（`gatewayresponse/models.go:139-215`）对**每个**条目填充默认：`Slug=DisplayName=model`、`ShellType="shell_command"`、`Visibility="list"`、`SupportedInAPI=true`、`Priority=索引`、`BaseInstructions="You are Codex, a coding agent."`、`DefaultReasoningSummary="auto"`、`WebSearchToolType="text"`、`TruncationPolicy={bytes,10000}`、`EffectiveContextWindowPercent=95`；`ContextWindow=MaxContextWindow` 取目录 `ContextWindowTokens`，**缺省回退 272000**；`InputModalities` 取目录真实模态，**缺省回退 `["text","image"]`**；`Description` 取目录备注三选一，无则 nil；reasoning levels / service tiers / multi-agent 仅在目录有数据时填充。
14. **响应形态**：四种协议形态共用同一份载荷（`gatewayresponse/models.go`）：OpenAI `{object:list,data:[{id,object,created,owned_by}]}`（:36-46）、Codex 富字段 `{models:[...]}`（:55-92 + :134-215）、Anthropic 分页形态（:303-328）、Gemini 形态（:331-345）。`owned_by` 规则：built_in 行 → `"openai"`，其余 → `"juhe-ai"`（:127-132）；`created` 取目录 `release_date/created_at` 的 Unix 秒（:253-268）。
15. **无单模型查询路由**：OpenAI 面精确匹配 `/models`（`gatewayopenai/endpoint.go:100`），`/v1/models/{id}` 返回 404；根形态 `/models` 注册仅服务 Gemini native `:action` 族。本设计不新增路由。契约覆盖端点全集：根形态 `/models`（适配进 `/v1` 链）、`/v1/models`（OpenAI-compatible 响应；同一路径按 Codex / Anthropic 客户端信号切换形态）、`/v1beta/models` 与明确 Gemini 客户端信号的 models 族（Gemini native 响应）。
16. **现行契约**：《账户模型限制设计》明文「`GET /models` / `GET /v1/models` 继续由本地供应商模型目录返回，不参与账户模型限制过滤」；`docs/functions/README.md`「客户端模型目录规则」段同口径（「只保留启用、可见、可计价模型」）。同文档性能设计节已有派生缓存的反向决策：「后续如果单个分组账号池过大，再增加 `groupId + systemAccountId + model` 的派生候选缓存；**第一版不引入，避免同时维护两套缓存失效链路**」。
17. **账户侧无效化已覆盖 supportedModels**：账户 patch 的副作用联动显式含 `supportedModels` 字段（`accounts/invalidation.go`），并以 `account_management_patch` reason 触发网关运行时失效——本设计搭既有车（但按第 6.3 节的无条件清空关系，而非目录白名单）。

## 3. 目标与非目标

### 3.1 目标

1. `/v1/models`（含第 2 节事实 15 枚举的全部端点与形态）的成员资格 = 该 API Key 激活绑定分组集合上、通过静态门与授权门的**资格主体**的**模型事实主体** supportedModels 并集，**加上**有效模型映射的 `source_model`（第 4.2 节），并集语义为**配置能力并集**（第 4.2 节，不声称严格等于瞬时可调用集合）。
2. 请求路径零 DB 成本：聚合 SQL 只在缓存未命中时执行；缓存形态复用现有 runtime cache 模式（进程内 + Redis 共享 + singleflight + generation 守卫）。
3. 装载失败可观察：聚合或字典装载失败时返回可传播的本地错误响应，禁止渲染成 200 空列表（第 4.7 节）。
4. 四种协议响应形态、鉴权、models 端点限流、缓存响应头全部不回归。
5. 无 schema 变更、无 jobs 变更、无 maintenance CLI 变更、无部署文档变更。

### 3.2 非目标

- 不改调度本身的模型过滤逻辑（`modelfilter.go` / `chainCandidateWhere` / 授权三函数不动）。
- 不改供应商模型目录的存在与运营语义：价格、可见性、模式过滤继续服务计费与管理面，只是**不再参与 `/v1/models` 成员资格**（目录降级为元数据字典，第 4.5 节）。
- 不改管理面 AI 问答的动态模型目录（已有"目录 ∩ account_supported_models"逻辑，本期不动；后续可复用本设计的聚合）。
- 不新增 `/v1/models/{model}` 路由，不新增配置项或开关。
- 列表不反映冷却、熔断、健康、限流额度等运行态（第 4.3 节，契约明示）。
- 不修复现有目录缓存的 generation 检查/写入非原子窗口（已记录为观察事实，第 9 节；本期只保证新缓存不复制该缺陷）。
- 不引入任何冗余存储表、不新增第二条缓存失效链（第 5 节论证）。

## 4. 语义定义（新契约）

### 4.1 成员资格公式

**两个主体必须区分**（对齐第 2 节事实 7 的调度实态）：

- **资格主体**：`group_accounts` 绑定的 `accounts` 行（直连账户或授权实例账户）。静态门与授权门都判在它身上。
- **模型事实主体**：`COALESCE(source_accounts.id, accounts.id)`（直连账户即自身；授权实例账户即其来源账户）。`account_supported_models` 与 `account_model_mappings` 都按它读取；provider 归属取 `COALESCE(source_accounts.provider_code, accounts.provider_code)`。

```
成员 = 直接支持模型 ∪ 有效映射源模型（两分支的 FROM/门条件完全一致）

FROM group_accounts ga
JOIN groups g  ON g.id = ga.group_id
JOIN accounts a ON a.id = ga.account_id
LEFT JOIN accounts src ON src.id = a.authorization_instance_source_account_id

静态门（WHERE，全部判在资格主体，实例时对齐 chainCandidateWhere 的 source_accounts 分支）：
  ga.group_id IN ({Key 激活绑定的分组 ID 集})
  AND ga.enabled = 1
  AND g.enabled  = 1
  AND a.provider_code = g.provider_code
  AND a.deleted_at IS NULL
  AND a.schedulable = 1
  AND a.status IN ('active', 'rate_limited', 'temporary_unavailable')
  AND (a.account_expires_at IS NULL OR a.account_expires_at > {now})
  AND a.authorization_instance_authorization_id IS NULL AND a.type IN ('api_key','oauth','google_oauth')
      -- 或（实例臂）：a.authorization_instance_authorization_id IS NOT NULL
      --   AND src.deleted_at IS NULL AND src.provider_code = g.provider_code
      --   AND src.type IN ('api_key','oauth','google_oauth')
      --   AND src.status IN ({同上状态集}) AND src.schedulable = 1
      --   AND (src.account_expires_at IS NULL OR src.account_expires_at > {now})
      --   AND (src.last_error_code IS NULL OR src.last_error_code <> 'account_expired')

直接支持模型：
  JOIN account_supported_models asm
    ON asm.account_id = COALESCE(src.id, a.id)          -- 模型事实主体
   AND asm.provider_code = COALESCE(src.provider_code, a.provider_code)
  SELECT DISTINCT asm.model

有效映射源模型：
  JOIN account_model_mappings m
    ON m.account_id = COALESCE(src.id, a.id)            -- 模型事实主体
   AND m.enabled = 1
  WHERE EXISTS (SELECT 1 FROM account_supported_models asm2
                WHERE asm2.account_id = COALESCE(src.id, a.id)
                  AND asm2.provider_code = COALESCE(src.provider_code, a.provider_code)
                  AND asm2.model = m.upstream_model)
  SELECT DISTINCT m.source_model
```

分组 ID 集 = `GatewayAPIKeyRow.GroupBindings` 中 `Status=="active"` 的绑定（与现行 `gatewayModelsProviderCodes` 同一遍历），SQL 内的 `g.enabled=1` 是权威复核（绑定行上的 `GroupEnabled` 只是缓存快照）。

### 4.1.1 授权门（配置态子集，对齐 `resolveChainAccountAccess` + `canScheduleChainAuthorizedAccount`）

静态门之上，资格主体还须通过与其归属形态对应的**授权臂**；调用方 = API Key 的属主 `system_account_id`。授权行有效性的配置态谓词（与调度三查询同款）：`status = 'active'` 且 `(expires_at IS NULL OR expires_at > now)` 且 `grantee_system_account_id = 调用方`。

| 归属形态 | 进列表条件（对齐调度访问臂） |
| --- | --- |
| 直连账户属主臂 | `a.system_account_id = 调用方` 且非实例账户 |
| 授权实例臂 | `a.system_account_id = 调用方`（实例恒归调用方所有），且按 `a.authorization_instance_authorization_id` 查到有效授权行；绑定级 `ga.account_authorization_id` 非空时须与该授权行 id 一致 |
| 授权分组臂 | 分组处于授权分组形态（组级授权行对调用方有效 + `group_authorization_settings` 在册），且 `a.system_account_id = 分组属主`（免账户级授权行） |
| owner 域账户授权臂 | 账户归他人所有且分组为 owner 域：存在有效授权行（未绑定限定时按 `resource_type='account' AND resource_id=a.id` 解析；绑定限定时按 `ra.id = ga.account_authorization_id` 解析） |

**属于配置态、进授权门的**：授权行 `status`（撤销/暂停即失效）、授权行 `expires_at`、grantee 归属、绑定授权 ID 一致性、分组授权形态。**不进授权门的**：授权额度 `limits_json`（请求期逻辑）、调用方的配额与限流（请求期）。授权状态属于配置态的理由：撤销/暂停/过期是管理动作或确定性时点，语义上等同"该授权关系不再存在"，与"分组禁用踢出成员"同层。

实现要求：聚合 SQL 的授权臂分支必须与 `resolveChainAccountAccess` 三臂逐条对照并加注释互引；授权分组形态判定（组级授权行 + settings）在装载器内与聚合同批执行（第 6.2 节），不依赖请求期上下文。

### 4.2 决策：映射源并入，语义为"配置能力并集"

**并入的理由**：调度语义（现行契约明文）是"`sourceModel` 不受 `supportedModels` 限制"但映射命中可直接调用。若列表只含 supportedModels，客户端按列表配置会漏掉实际可用的映射源模型。

**语义边界（v2 收紧）**：本设计的列表是**配置能力并集**，不是"瞬时可调用集合"的严格等价物。偏差来源有二，均为已接受取舍：

1. **端点族合并**：`account_model_mappings` 的 PK 是 `(account_id, source_model, source_endpoint_family)`（第 2 节事实 9），同一 `source_model` 可在不同端点族各有一行。列表是扁平模型名，跨端点族去重后单条目呈现。客户端在列表看到某模型，只代表"存在至少一个端点族上的可用映射或直接支持"；该模型在特定端点（如 `/v1/completions` vs `/v1/responses`）是否可调仍由调度判定，列表不承诺。
2. **运行态偏差**：冷却、熔断、Key-模型短屏蔽不反映（第 4.3 节）。

**对齐细节**：只并入 `upstream_model ∈ 模型事实主体 supportedModels` 的启用映射源，与调度 SQL（`chain_accounts.go:574-600`）的接受条件完全一致；`source_endpoint_family` 不参与列表成员资格（只造成上述去重合并）。

### 4.3 决策：列表反映配置态，不反映运行态

**门条件取 `chainCandidateWhere` 静态子集 + 第 4.1.1 节授权门配置态子集**。**明确排除**：

- `cooldown_until`（分钟级自愈态；调度里它还受 `includeUnavailable` 开关翻转）；
- 熔断 / 健康投影 / Key-模型短屏蔽（Redis 运行态）；
- 授权额度与请求期限流。

**为什么排除**：

1. 列表的消费者是客户端的**静态配置**（用户照着列表配模型）。运行态是自愈的、分钟级翻转的，把它折进列表只会造成列表抖动；客户端可能长期缓存列表，抖动会被放大成"模型忽有忽无"的体验事故。
2. 现行 `/v1/models` 完全不看账户，新语义取静态门已经完成"从目录语义到账户语义"的收敛；把"此刻可调度"做成列表语义是无上限的追认成本（任何运行态变化都要进失效链）。
3. `status` 白名单取放宽档 `'active','rate_limited','temporary_unavailable'`：这三档是调度在 `includeUnavailable` 下会使用的全部状态，排除它们（只留 `'active'`）会让限流中的账户模型从列表消失，同样制造抖动。`pending_test` 不在白名单——与调度一致，未测活的账户不对外展示能力。

### 4.4 决策：目录过滤退役出成员资格

`catalog_visible`、可见价格、音视频/realtime 模式过滤不再影响 `/v1/models` 列出什么。**为什么**：这三者回答"目录里什么值得卖/展示"，是计费与运营语义；用户对本功能的诉求是"这个 Key 背后的账户能提供什么"，是能力语义。成员资格只由第 4.1/4.1.1 节的账户门与授权门决定。目录自身（管理面、计费、模型检测推荐）不受影响。

### 4.5 元数据：目录降级为字典

四种协议形态的响应结构不变，元数据来源调整：

1. **字典装载**：按绑定的去重 provider codes 复用现有 `ListCachedProviderModelCatalogAsync`（缓存与失效原样不动），在 active 行内按现有 scope 优先级（personal > global > built_in）取每模型最优行，构建 `map[模型名]目录条目`。
2. **命中**：模型在字典中 → 沿用现有条目全字段（`created`、`owned_by`、Codex 富字段按目录数据填充），`owned_by` 规则不变（built_in → `"openai"`，其余 → `"juhe-ai"`）。
3. **未命中（合成条目）**：模型不在字典 → 构造空目录条目（仅 `Model` 字段）进入**现有 builder 原样加工**。因此合成条目继承 `buildCodexModelInfo` 的现行默认值（第 2 节事实 13），明确契约如下：`Slug=DisplayName=模型名`、`ShellType="shell_command"`、`Visibility="list"`、`SupportedInAPI=true`、`BaseInstructions` 为 Codex 固定串、`ContextWindow=MaxContextWindow=272000`（回退值）、`InputModalities=["text","image"]`（回退值）、`EffectiveContextWindowPercent=95`、`TruncationPolicy={bytes,10000}`、`DefaultReasoningSummary="auto"`、`WebSearchToolType="text"`、`Description=nil`、无 reasoning levels / service tiers / multi-agent；OpenAI 形态 `created=0`、`owned_by="juhe-ai"`。**即：合成条目允许返回这些默认能力字段**——这是现行 builder 对无数据条目的一致行为，不为合成条目另造一套默认值，也不把 272000/`["text","image"]` 解读为对模型能力的承诺（与音频设计 §4.3 的目录回退语义一致）。
4. **排序**：按模型名字典序升序，稳定确定性（替代现行目录运营排序 `clientCatalogCompareItems`；客户端对模型列表顺序无契约依赖）。
5. **去重**：UNION 天然去重；列表为扁平模型名数组。

### 4.6 空态

Key 无激活绑定、绑定分组全部禁用、分组无在册可调度账户 → 返回各协议形态的**空列表**（HTTP 200，OpenAI 形态 `{"object":"list","data":[]}`）。不报错、不回退到目录。

### 4.7 失败语义（新增，v1 缺口）

现状缺陷形态：`ListClientModelCatalog` 无 error 返回，装载失败 `return nil` → **200 空列表**（第 2 节事实 12）。新契约：

1. 新端口方法签名带 error：`(GatewayKeyModelList, error)`，内含模型集合与 `validUntil`（第 6.3 节）。
2. 聚合 SQL 失败、字典装载失败、授权臂装载失败 → 装载器**返回错误**，不吞错、不回退目录、不静默空列表。
3. 错误升级路径：before-auth models 分支（`handleGatewayModelsRequestBeforeRequiredAuth`）收到装载错误时，放弃本次本地 models 响应，按网关本地错误语义返回（内部错误形态，走既有 `GatewayErrorPayloadOf` 错误构造与审计捕获），不继续链路；Identity 注入路径（preflight 完整分支）同样向上传播错误。
4. 空列表只允许来自"聚合成功且结果为空"（第 4.6 节），不允许来自错误。

### 4.8 不变项清单

- 鉴权：仍要求有效 Gateway API Key（Bearer/`x-api-key`/`x-goog-api-key` 按协议），无 Key 仍走现行的 before-required-auth 本地拒绝路径。
- models 端点专用限流：不变。
- 响应协议判定（explicit gemini/anthropic 客户头优先，否则按请求路径协议）、Codex 客户端识别（originator/user-agent/`x-codex-client`/`client_version`）：不变。
- 转发开关恒 false（不转发上游）：不变。
- 响应缓存头（`Cache-Control`/`Vary`）：不变。

## 5. 方案对比与选型理由

### 5.1 三个候选

| | C：API Key 维度冗余表（原始提案） | A：分组维度冗余表 | **B：读时聚合 + 双层缓存（选定）** |
| --- | --- | --- | --- |
| 存储形态 | `api_key_models(api_key_id, model)` 物化 | `group_models(group_id, model)` 物化 | 无新表，一组聚合 SQL |
| 读路径 | 单 Key 主键范围扫，最快 | `WHERE group_id IN (…)` | 同 A 的查询语义，外加双层缓存 |
| 维护触发 | **扇出到 Key 级**：一个账户改模型/换组，所有可达 Key 的行都要重算；账户编辑、分组绑定、策略绑定、Key 换绑、启停、映射变更……全部写路径（10+ 处）都要挂更新钩子 | 扇出收敛到分组级，但同样要挂全套写路径 | **零挂钩**：任何时刻查询的都是当时的事实 |
| Schema 代价 | 新表 + 7 处 schema 文件（PG 表/索引、SQLite 镜像、contracts 白名单、dataset manifest、golden 计数测试）+ seed | 同左 | **无** |
| 漂移风险 | 有：任何遗漏的写路径都会造成永久漂移，需要重建工具与巡检兜底 | 有 | **无** |
| 状态/授权条件纳入成本 | 每纳入一个条件（账户启停、授权撤销、到期）就多一批触发钩子 | 同左 | 一个 WHERE 条件 / 一项 validUntil 计算 |
| 与项目既有决策 | 相悖 | 相悖 | 一致 |

### 5.2 为什么否决"API Key 维度冗余表"（原始提案）

提案的动机——避免每次请求实时并集——是真实约束，方案 B 已满足（第 5.4 节）。但 Key 维度物化本身有两个结构性问题：

1. **扇出方向错误**。链条是 Key → 策略 → 分组 → 账户。一次账户 supportedModels 编辑影响的 Key 数 = 所有链路可达它的 Key，这是系统里扇出最大的一端；而分组数远小于 Key 数，且同一策略下的所有 Key 并集结果完全相同。Key 维度物化等于把同一份数据复制 N 份，没有信息增量，只有一致性负担。
2. **写路径挂钩无法收敛**。第 2 节事实 5、11 取证的影响写路径超过 10 处（账户编辑/建/删、批量编辑、分组绑定、策略绑定、Key 换绑、启停、导入、OAuth 建户、jobs 清理、授权实例供应/回收）。每处都必须在事务内正确更新冗余表，任何一处遗漏就是静默漂移；授权行撤销/暂停/到期这类**不经过账户写路径**的状态变化（授权独立模块、自然到期）在 Key 维度表下还需要额外的扫描或触发机制。配合 SQLite 镜像（jobs 侧 FK 不生效，需显式 DELETE）与 golden 计数测试同步，维护面远超功能本身。

### 5.3 为什么否决"分组维度物化表"

A 修复了扇出方向（账户变化只影响其所在分组的行），但保留了 C 的全部固定成本：schema 七件套、写路径挂钩、漂移兜底；授权归属是 **(调用方, 账户)** 二维事实，分组维度的行仍要按调用方再展开或读时过滤，物化收益进一步稀释。它相对 B 的唯一收益是"缓存未命中时少算一组毫秒级 SQL"——在单机 Docker 单 gateway 实例、Key 与分组规模有限的当前形态下，这个收益没有可观测价值。若未来出现多实例 + 大规模 Key 的形态，B 的聚合 SQL 就是 A 的回填语句，升级路径无冲突（第 9 节）。

### 5.4 为什么 B 满足"不能每次请求实时并集"

- **读路径（按实现实态描述）**：redis runtime 模式下，请求先读 Redis 共享缓存（亚毫秒），命中即返回（共享命中时回填进程内条目）；memory 模式下读进程内 entryCache。未命中进入 singleflight 合并的后台装载：执行聚合 SQL + 授权臂判定，写回两层缓存。并发未命中只算一次。
- 聚合的输入（分组 ID 集）来自 Key 记录缓存里已有的绑定行，**不新增任何装载**。
- 性能预期（**目标值，实施后实测校准**，本节数字不作为验收依据）：聚合 SQL 数据面 = 分组数 × 组内账户数 × 每账户 ≤64 模型行的主键前缀索引探测，单次毫秒级；`resource_authorizations` 按 `grantee + status` 与 PK 查询。索引论证：`group_accounts` PK `(group_id, account_id)` 前缀、`account_supported_models` PK `(account_id, model)` 前缀、`account_model_mappings` PK `(account_id, source_model, source_endpoint_family)` 前缀、`resource_authorizations` 按 grantee/status 条件与主键。无全表扫描。

### 5.5 与项目既有决策的一致性

《账户模型限制设计》性能设计节已裁决：「后续如果单个分组账号池过大，再增加 `groupId + systemAccountId + model` 的派生候选缓存；第一版不引入，**避免同时维护两套缓存失效链路**」。方案 B 严格遵守该裁决：唯一新增的缓存挂在既有 `InvalidateGatewayRuntime` 失效总线上（第 6.3 节），不发明第二条失效链。引入物化表（A/C）则同时违背"两套失效链"约束与"最小改动"原则。

## 6. 详细设计

### 6.1 读取链路（改造前后）

```
改造前：
preauth(models 判定) → preflight before-auth 分支
  → ResolveGatewayAPIKeyForModelsAsync（Key 校验 + 记录缓存）
  → gatewayModelsProviderCodes(record) → []providerCode
  → 限流 → sink.sendModelsGatewayResponsePayload
  → ports.ModelCatalogLoader.ListClientModelCatalog(systemAccountID, providerCodes)（无 error，失败静默空）
  → selectClientCatalogItems 过滤 → 四协议形态输出

改造后（变化点加 ★）：
preauth(models 判定) → preflight before-auth 分支
  → ResolveGatewayAPIKeyForModelsAsync（不变）
  ★ gatewayModelsBindings(record) → []{groupID, providerCode}（同一遍历，多取 GroupID）
  → 限流（不变）→ sink.sendModelsGatewayResponsePayload（不变）
  ★ ports.ModelCatalogLoader.ListGatewayKeyModels(systemAccountID, bindings) (GatewayKeyModelList, error)
      内部：
      a. groupModelUnion 缓存（第 6.3 节）→ {[]model, validUntil}
      b. 缓存未命中：聚合 SQL（静态门 + 模型事实主体 COALESCE + 映射分支）
         + 授权臂判定（4.1.1，与聚合同批）+ validUntil 计算
      c. 目录字典：按去重 providerCode 复用现有 ListCachedProviderModelCatalogAsync（不变）
      d. 合并：成员 ∪ 字典元数据 / 合成条目（第 4.5 节）→ 条目列表
      e. 任一装载失败 → 返回 error（第 4.7 节）
  ★ 四协议形态输出（结构不变，数据源切换）
  ★ 装载错误 → 本地错误响应（before-auth 分支放弃响应；Identity 注入分支向上传播）
```

### 6.2 聚合 SQL 与授权臂装载

语义见第 4.1/4.1.1 节。实现要点：

- 静态门 SQL 与 `chainCandidateWhere`、授权臂分支与 `resolveChainAccountAccess` 三臂**逐条对照并注释互引**，防止两边语义漂移；
- 授权分组形态判定（组级授权行有效性 + `group_authorization_settings`）与账户级授权行查询在装载器内**同批执行**（有界次数的小查询：每组一次组级判定 + 每批一次授权行批量查询），全部发生在缓存未命中路径上；
- `now` 统一取装载时刻，`validUntil` 与聚合同批计算（第 6.3 节）。

### 6.3 缓存设计

- **缓存对象**：`{models []string, validUntil time.Time}`——模型集合 + 有效期界，与元数据解耦（元数据字典已有自己的缓存）。
- **键**：`systemAccountID + ":" + sha256(排序后分组 ID 集)`（分组集相同的不同 Key 共享条目）。
- **两层（按实现实态）**：redis runtime 模式读共享桶 `gateway:group-model-union` 优先（命中回填进程内），memory 模式只读进程内 entryCache；写入双层。singleflight 合并并发未命中。
- **TTL 与到期一致性**：基础 `groupModelUnionBaseTTL = 1h`。条目有效期 `validUntil = min(装载时刻 + 1h, 最近未来到期点)`——最近未来到期点 = 贡献该并集的全部行中**未来的** `accounts.account_expires_at`（含实例的来源账户）与有效授权行 `resource_authorizations.expires_at` 的最小值；全部无未来到期点时取基础 TTL。到期读取侧判定：共享/进程内命中后若 `now >= validUntil` 视为未命中重算。**这消除了"排除过期账户却缓存 1h"的矛盾**：账户或来源账户或授权自然到期（无写事件）后，至多到期点即刻即被重算，独占模型不会滞留到基础 TTL 结束。`api_keys.expires_at`（Key 自身过期）不在 validUntil 计算内——它在 Key 记录校验层处理，先于 models 响应。
- **失效关系（v2 重定）**：**不使用目录 reason 白名单**（第 2 节事实 11：白名单仅 3 个目录事件，覆盖不了 `account_management_patch` 等）。并集缓存随 `ClearGatewayRuntimeCacheLocal` **无条件清空**（generation 推进 + 进程内清空 + 共享桶清空），与 runtimeCache / groupCache / accountsCache 等核心运行时缓存同待遇。理由：并集的依赖面（账户、分组、绑定、映射、授权）正是运行时缓存族服务的核心事实，任何触发运行时失效的管理写都可能与并集相关；reason 判别在本项目里只为"可选缓存"（settings、目录）存在，并集不是可选缓存。
- **写路径 → 失效覆盖依据（契约要求）**：实施交付必须包含一张覆盖表并配契约测试，核对下列已核实路径均触发 `InvalidateGatewayRuntime`（即无条件清空并集缓存）：账户编辑 `account_management_patch` / 创建 `account_created` / 删除 `account_deleted`（`accounts/invalidation.go:68-73,146,196,264`）、批量编辑 `account_batch_updated`（`batch_effects.go:324`）、策略路由 `route_strategy_created/updated/deleted`（`mutations.go:143,420,563`）、API Key `api_key_updated`/`api_key_quota_updated`（`apikeys/patch.go:34-37`）、分组 `group_created/updated/deleted`（`groups/store.go:1395,1733,1877`）。**范围内核查义务**：模型映射编辑、授权行撤销/暂停、分组授权形态变更、授权实例供应/回收（`authz/instance_provision.go`）等路径若未触发运行时失效，属于**必须在本交付内补齐触发的缺陷**（补触发，而不是给并集另立失效通道）；仅 `expires_at` 类自然到期不依赖写路径，由 validUntil 覆盖。
- **并发规则（v2 钉死）**：并集缓存的**发布**（generation 检查 + 进程内写入 + 共享写入）与**失效**（generation 推进 + 双层清空）必须在同一互斥量的临界区内串行，二者的先后序两种结局都正确：失效先入临界区 → 后续发布的 generation 检查失败、放弃回填；发布先入临界区 → 后续失效擦除其产物（双层都擦）。**禁止**复制现有 `catalog.go` 的"检查与写入分两次加锁"形态（第 2 节事实 10）。要求一条时序测试：注入"检查通过 → 失效介入 → 发布执行"的顺序，断言两层缓存无陈旧条目（白盒 seam 或时间窗控制）。

## 8. 验收标准（可观察行为）

以绑定分组 G（owner 域，含直连账户 a1：支持 m1、m2，映射 m5→m1 启用；a2：支持 m2、m3）为例：

1. Key 绑定 G：`/v1/models` 恰好返回 m1、m2、m3、m5（字典序输出）。
2. 目录新增 m4（有价、可见）但无账户支持 → 不出现。
3. m1 目录行置 `catalog_visible=false` → m1 仍出现（元数据走合成条目，owned_by=juhe-ai、Codex 默认值按第 4.5 节）。
4. a1 `schedulable=0` → m1、m5 消失（m2、m3 由 a2 维持）；a1 恢复 → 重新出现。
5. G 禁用或绑定禁用 → 空列表（200）。
6. Codex / Anthropic / Gemini 形态的模型 id 集与 OpenAI 形态完全一致。
7. 缓存命中期间重复请求无聚合 SQL 执行；账户模型编辑后（运行时失效联动）下一次请求反映新集合。
8. 无效 Key、限流超限的现行错误形态与状态码不回归。
9. **授权实例**：来源账户支持 m7、实例账户无自有模型行 → 授权实例所在分组的 Key 列表含 m7（模型事实主体 COALESCE）。
10. **授权门**：撤销/暂停账户授权行、或授权行过期 → 该授权贡献的模型消失；实例授权同理；绑定授权 ID 不一致 → 不出现。
11. **自然到期**：不写任何库，仅推进时钟越过账户/来源账户/授权行的未来到期点 → 下一次请求模型消失（validUntil 生效）。
12. **失败可观察**：注入聚合 SQL 失败 → 客户端收到网关本地错误响应，而非 200 空列表；审计有记录。
13. **并发时序**：发布检查通过后注入失效 → 两层缓存无陈旧条目（测试用例，非线上观察）。
14. **跨端点族**：同一 `source_model` 在两个端点族各有一行启用映射 → 列表单条目。
