# 原始审计日志设计

> 面向网关、后端、前端和 AI 维护者。
> 本文定义 `juhe-ai` 的原始审计日志能力，用于在客户端、网关、上游供应商行为变化时还原完整请求链路。原始审计日志不同于使用记录，不服务计费和统计，重点服务故障定位、协议兼容排查和上游行为复盘。

## 文档目标

- 明确原始审计日志和 `usage_records` 的职责边界。
- 固定“成功 10% 采样、非成功全量保存”的判定规则。
- 固定“不脱敏、不裁剪、不改写原文”的保存边界。
- 固定“不在请求链路同步写库、终态入队、后台批量落库”的性能边界。
- 固定 SSE、重试、客户端中断、队列溢出、进程重启等关键场景的处理方式。

## 模块定位

原始审计日志回答这些问题：

- 客户端实际发来了哪些请求头、查询参数和请求体？
- 网关在鉴权、调度、替换上游认证、剔除或补充协议头后，实际向上游发送了什么？
- 每一次上游尝试命中了哪个账号、代理、URL、状态码和响应内容？
- 网关最终返回给客户端的状态码、响应头、响应体或 SSE 事件是什么？
- 客户端是否中断、上游是否中断、流式响应是否完整结束？

原始审计日志不回答这些问题：

- 本次请求消耗了多少 token、成本是多少、平均耗时是多少。
- 账户、分组、API Key 的累计用量趋势。
- 授权资源的聚合消耗。

这些仍由 `usage_records` 和统计缓存负责。

## 与使用记录的边界

| 能力 | 使用记录 | 原始审计日志 |
| --- | --- | --- |
| 主要目的 | 计量、统计、调用明细和错误摘要 | 完整链路复盘和协议排查 |
| 写入粒度 | 每次上游尝试写入一条 | 每次客户端请求写入一条主记录，下面挂多次上游尝试 |
| 成功请求 | 每次都写结构化指标 | 默认只保存 10% 完整原文 |
| 非成功请求 | 每次都写结构化指标和有限快照 | 100% 保存完整原文 |
| 请求 / 响应内容 | 失败快照脱敏、截断 | 不脱敏、不截断、不改写 |
| 写入方式 | 可由现有队列或服务写入 | 只允许终态入队，后台批量写库 |
| 前端页面 | 调用方明细、统计相关 | 管理员排障检索和原文查看 |
| 权限边界 | 管理员看全部，用户看自己调用明细 | 当前仅管理员可见 |

## 保存范围

一条原始审计日志应能还原一次客户端请求从进入网关到最终结束的完整过程。

必须保存：

- 客户端原始请求：method、path、query、headers、raw body、客户端 IP、请求开始时间。
- 网关解析结果：API Key ID、调用方系统账户、分组、供应商、模型、stream 标记、trace ID。
- 调度结果：候选账号、最终尝试账号、代理、上游 URL、尝试顺序。
- 上游请求：实际发给上游的 method、URL、headers、raw body。
- 上游响应：状态码、headers、raw body；SSE 保存完整事件或原始 chunk 序列。
- 网关返回：最终返回给客户端的状态码、headers、raw body 或 SSE 事件。
- 结束状态：成功、失败、客户端中断、上游中断、网关异常、队列采样原因、总耗时。

不得保存“伪完整”内容：

- 不能只保存脱敏后的 header 或 body。
- 不能保存被截断但没有明确标记的 payload。
- 不能把普通运行日志或 `usage_records` 快照当成原始审计日志。
- 如果资源保护策略导致本次原文无法完整进入审计队列，应丢弃本条审计记录并记录队列丢弃计数，不写入一条看起来完整但实际缺内容的记录。

## 成功与非成功判定

`audit_outcome` 建议使用这些值：

- `success`：最终返回客户端的是成功响应，且没有上游尝试失败、网关异常、流式中断或客户端中断。
- `success_after_retry`：最终成功，但中间至少一次上游尝试失败或被错误策略切换。
- `gateway_failed`：网关本地鉴权、调度、请求构造、响应处理或未知异常失败。
- `upstream_failed`：最终上游失败，包括 4xx、5xx、网络错误、代理错误、超时和账号错误策略命中。
- `stream_failed`：SSE 或其他流式响应未完整结束，包含上游流中断、空闲超时、解析失败。
- `client_aborted`：客户端在请求体上传、普通响应或流式响应过程中主动断开。

采样规则：

- `success` 按默认 `10%` 保存。
- `success_after_retry`、`gateway_failed`、`upstream_failed`、`stream_failed`、`client_aborted` 全量保存。
- 如果请求最终没有进入上游，例如 API Key 无效、无可用账号、分组失效，也属于非成功，必须保存。
- 如果最终成功但任一上游尝试失败，不能按成功 10% 采样，必须全量保存，因为这类记录对定位账号和供应商行为最有价值。

成功采样建议使用稳定桶：

- 每个请求生成 `audit_sample_bucket`，范围 `0` 到 `9999`。
- 固定成功采样率为 `0.1` 时，`bucket < 1000` 进入保存。
- 采样率后续调整不影响历史记录的 `sample_reason`。

## 异步写入原则

原始审计日志不能影响正常请求链路。网关请求处理过程中禁止同步写 `audit_logs` 表。

必须遵守：

- 请求开始时只创建内存态 `AuditCaptureContext`。
- 请求处理中只向当前上下文追加原始片段和结构化元数据，不执行数据库写入。
- 请求完成、失败或客户端中断后，先计算终态，再按采样规则决定是否入队。
- 入队对象必须是终态快照，包含主记录、尝试记录和 payload 记录。
- 队列后台 worker 每隔一段时间或达到批量阈值后，用事务批量写入 SQLite。
- 队列写入失败不能影响已经返回给客户端的响应；失败批次可留在内存中等待下一轮重试。
- 系统重启、进程崩溃或强制退出时，允许丢失内存中的活跃捕获、待写队列和失败重试批次。

固定策略参数：

| 参数 | 固定值 | 说明 |
| --- | --- | --- |
| `enabled` | `true` | 原始审计日志固定启用，不提供系统设置开关 |
| `successSampleRate` | `0.1` | 完全成功请求固定采样比例 |
| `flushIntervalSeconds` | `5` | 后台批量落库间隔 |
| `batchSize` | `50` | 单批最多写入审计请求数 |
| `queueMaxItems` | `1000` | 待写队列最大请求数 |
| `queueMaxBytes` | `256MB` | 待写队列近似最大原文体积 |
| `activeCaptureMaxBytes` | `64MB` | 单个请求活跃捕获上限 |
| `retentionDays` | `7` | 原始审计日志固定保留天数 |

这些参数写死在后端审计日志模块中，不进入 `system_settings`，也不在系统设置页面暴露。保留期清理由统一 `data-retention-cleanup` 后台任务每天自动运行一次，不提供页面手动清理入口。

## 队列策略

队列是内存队列，不是可靠消息队列。

核心要求：

- 只存放已完成的审计记录，不能存放半程请求。
- 后台批量写库使用单事务，成功后从队列移除。
- 写库失败时保留批次并在下一轮重试；如果持续失败导致队列超过上限，优先丢弃成功采样记录。
- 非成功记录优先级高于成功采样记录；成功采样记录不能挤掉非成功记录。
- 如果队列已满且无法释放空间，允许丢弃新来的审计记录，但必须增加内存计数，供管理员在运维页面看到审计丢弃风险。
- 不为了审计日志等待队列空位，不阻塞客户端请求完成。

建议维护这些运行态指标：

- `auditQueueLength`
- `auditQueueBytes`
- `auditFlushLastSuccessAt`
- `auditFlushLastError`
- `auditDroppedSuccessCount`
- `auditDroppedFailureCount`
- `auditDroppedOverflowCount`
- `auditActiveCaptureCount`

这些指标可以进入运维监控，不需要写入每条业务记录。

## SSE 与流式响应

SSE 和其他流式响应必须按“终态入队”处理。

规则：

- 流开始时创建捕获上下文，但不入队、不写库。
- 上游每个 SSE chunk 或事件可以追加到内存上下文，转发客户端不能等待审计处理完成。
- 网关向客户端写出的事件也要追加到上下文，便于区分“上游原始流”和“实际返回客户端的流”。
- 只有流自然结束、上游失败、流超时、解析失败或客户端断开后，才计算终态并尝试入队。
- SSE 过程中不能按 chunk 实时写库，不能生成多条未完成审计记录。
- 如果 SSE 完整结束并最终成功，按成功 10% 采样。
- 如果 SSE 中断、超时、客户端断开或上游返回失败事件，按非成功全量保存。

对 OpenAI Responses SSE，建议额外记录：

- 是否收到 `response.completed`。
- 是否收到 `response.failed`。
- 最后一个事件类型。
- 完成事件中的 usage 摘要。
- 流关闭原因：`completed`、`upstream_error`、`client_aborted`、`idle_timeout`、`parse_error`。

- `attempt_index`
- `account_id`

- `error_phase`
- `error_code`
- `error_message`
- `started_at`
- `ended_at`
- `duration_ms`

### `audit_log_payloads`

保存原始请求、上游请求、上游响应和最终网关响应。

建议字段：

- `id`
- `audit_log_id`
- `attempt_id`
- `part_type`：`client_request`、`upstream_request`、`upstream_response`、`gateway_response`、`gateway_error`
- `sequence_index`
- `content_type`
- `content_encoding`
- `headers_encrypted`
- `body_encrypted`
- `body_sha256`
- `size_bytes`
- `created_at`

字段说明：

- `headers_encrypted` 保存完整 header JSON，不脱敏。
- `body_encrypted` 保存原始 body 或 SSE chunk 序列，不脱敏。
- 原始内容建议使用 `JUHE_AI_SECRET` 做应用层加密；加密不是脱敏，页面按管理员权限解密展示原文。
- 详情接口会按完整 headers JSON 计算 `headersSha256`，用于快速比较客户端请求和上游请求的头部差异。
- `body_sha256` 只针对 body 原文字节计算，用于确认 body 完整性和后续导出校验。
- 如果内容是二进制或压缩数据，按原始字节保存，同时记录 `content_type` 和 `content_encoding`。

## 管理 API 建议

当前只提供管理员接口。

- `GET /api/audit-logs`：分页查询审计日志元数据。
- `GET /api/audit-logs/:id`：读取审计日志详情、上游尝试和 payload 摘要。
- `GET /api/audit-logs/:id/payloads/:payloadId`：读取某段原始 payload，后端解密后返回。
- `DELETE /api/audit-logs/:id`：可选，管理员删除单条审计日志。
- `GET /api/audit-logs/runtime`：可选，查看队列长度、最近落库时间、丢弃计数、错误摘要和当前审计设置。

查询条件建议：

- 时间范围
- 成功 / 非成功 / outcome
- 状态码
- path
- model
- API Key
- 分组
- AI 账户
- 系统账户
- 供应商
- trace ID
- 客户端 IP
- 错误阶段

## 前端页面建议

菜单名称：

- `审计日志`

权限：

- 当前仅 `admin` 可见。
- 普通用户不展示菜单，不提供接口访问。

列表只展示元数据：

- 请求时间
- 调用方
- API Key 摘要
- 接口
- 模型
- 分组
- 命中账号
- 结果
- 状态码
- 耗时
- 采样原因

详情使用抽屉或详情页，按 tab 展示：

- `链路概览`
- `客户端请求`
- `上游尝试`
- `上游请求`
- `上游响应`
- `返回客户端`
- `队列与采样`

展示规则：

- 默认折叠完整 header 和 body，用户主动展开后再加载 payload。
- 文案必须明确“原始审计日志包含完整凭据、请求和响应内容，仅用于排障”。
- 原始内容摘要分别展示 `Headers SHA256` 和 `Body SHA256`；内容按文本展示，无法安全解码的二进制内容展示大小、hash 和十六进制预览。
- 不在列表中直接展示完整凭据、token 或大段业务内容，避免误触暴露。

## 安全边界

原始审计日志是安全策略里的高权限例外：

- 不脱敏、不截断、不改写。
- 必须限制为管理员可见。
- 原始 payload 建议应用层加密存储。
- 普通运行日志、错误日志、`usage_records` 快照仍然按安全策略脱敏和截断。
- 对外分享数据库、日志、截图或 bug 文档前，必须移除原始审计日志数据。
- 删除 API Key、账号、分组或系统账户时，不自动删除历史审计日志；历史保留按审计日志保留策略处理。

## 保留与清理

原始审计日志体积会远大于使用记录，必须有独立保留策略。

- 固定保留 `7` 天，不提供系统设置项调整。
- 支持按时间清理 `audit_logs`、`audit_log_attempts`、`audit_log_payloads`。
- 清理任务统一接入 `data-retention-cleanup`，只在后台 worker 运行，不在列表请求中触发大批量删除。
- 清理失败只记录运维错误，不影响网关请求。
- 统计缓存不依赖审计日志，删除审计日志不会影响用量统计。

## 实现落点建议

后端：

- `backend/src/modules/audit-logs/`：管理接口、队列服务、批量落库服务。
- `backend/src/modules/gateway/`：只负责创建捕获上下文、追加原始片段、终态入队，不直接写库。
- `backend/src/storage/`：新增审计日志 repository 和 schema。
- `backend/src/modules/background/`：如后续统一后台任务调度，可挂载审计 flush 和清理任务。

前端：

- `frontend/src/views/audit-logs/`：审计日志列表和详情。
- `frontend/src/api/`：新增审计日志 API 请求封装。
- `frontend/src/types/`：新增审计日志类型。

## 验收标准

- [ ] 完全成功请求只按默认 10% 采样保存。
- [ ] 非成功请求、客户端中断、流式中断、重试后成功请求都能 100% 保存。
- [ ] 网关请求路径不直接写 `audit_logs`，审计日志只通过内存队列后台批量落库。
- [ ] SSE 请求只在流结束、失败或断开后入队，队列中不存在半程记录。
- [ ] 审计队列满或数据库异常时不阻塞正常请求，并能记录丢弃计数。
- [ ] 管理员能在页面检索审计记录并查看完整原始请求、上游请求、上游响应和最终返回。
- [ ] 普通用户不能访问审计日志页面和接口。
- [ ] 普通运行日志和使用记录快照仍遵循脱敏策略，不被原始审计日志需求污染。
