# 原始审计日志设计

> 面向网关、后端、前端和 AI 维护者。
> 本文定义 `juhe-ai` 的原始审计日志能力，用于在客户端、网关、上游供应商行为变化时还原完整请求链路。原始审计日志不同于使用记录，不服务计费和统计，重点服务故障定位、协议兼容排查和上游行为复盘。

## 文档目标

- 明确原始审计日志和 `usage_records` 的职责边界。
- 默认“最近 1 小时完全成功请求全量热保留，超过热窗口后保留全部事件元数据，仅为 10% 稳定采样保留长期 payload”；热窗口、成功采样和保留期可通过受控环境变量调整，问题链路始终必须保留。
- 固定“headers、queryString 和 body 不脱敏、不改写原文；未完整保留时必须明确标记”的保存边界。
- 固定“不在请求链路同步写库、终态入队、后台批量落库”的性能边界。
- 固定 SSE、重试、客户端中断、队列溢出、进程重启等关键场景的处理方式。

容量治理、成功采样、压缩、去重、错误聚合和清理策略见 [审计日志保全策略设计](审计日志保全策略设计.md)。本文侧重捕获语义和链路边界；涉及存储形态和保留策略时，以保全策略文档为当前口径。

## 模块定位

原始审计日志回答这些问题：

- 客户端实际发来了哪些请求头、查询参数和请求体？
- 网关在鉴权、调度、替换上游认证、剔除或补充协议头后，实际向上游发送了什么？
- 每一次上游尝试命中了哪个账号、代理、URL、状态码和响应内容？
- 网关最终返回给客户端的状态码、响应头、响应体或 SSE 事件是什么？
- 客户端是否中断、上游是否中断、流式响应是否完整结束？

原始审计日志不回答这些问题：

- 本次请求消耗了多少 token、成本是多少、平均耗时是多少。
- 账户、分组、API Key 的累计用量趋势。
- 授权资源的聚合消耗。

这些仍由 `usage_records` 和统计缓存负责。

## 与使用记录的边界

| 能力 | 使用记录 | 原始审计日志 |
| --- | --- | --- |
| 主要目的 | 计量、统计、调用明细和错误摘要 | 完整链路复盘和协议排查 |
| 写入粒度 | 每次上游尝试写入一条 | 每次客户端请求写入一条主记录，下面挂多次上游尝试 |
| 成功请求 | 每次都写结构化指标 | 最近 1 小时全量进入原始审计，超过热窗口后保留事件元数据，只有 10% 稳定采样继续保留 payload |
| 非成功请求 | 每次都写结构化指标和有限快照 | 100% 进入原始审计；body 不超过 `2MB` 时完整保全，超过后转为摘要并参与错误聚合 |
| 请求 / 响应内容 | 失败快照按原文保存并受容量上限约束 | headers、queryString 和 body 不脱敏、不改写；未完整保留时必须标记 `summary_only`、`hash_only` 或 `expired` |
| 写入方式 | 可由现有队列或服务写入 | 只允许终态入队，后台批量写库 |
| 前端页面 | 调用方明细、统计相关 | 管理员排障检索和原文查看 |
| 权限边界 | 管理员看全部，用户看自己调用明细 | 当前仅管理员可见 |

## 保存范围

一条原始审计日志应能还原一次客户端请求从进入网关到最终结束的完整过程。

必须保存：

- 客户端原始请求：method、path、query、headers、raw body、客户端 IP、请求开始时间；headers 和 query 按原文保存。
- 网关解析结果：API Key ID、调用方系统账户、分组、供应商、模型、stream 标记、trace ID。
- 调度结果：候选账号、最终尝试账号、代理、上游 URL、尝试顺序。
- 上游请求：实际发给上游的 method、URL、headers、raw body；headers 按原文保存。
- 上游响应：状态码、headers、raw body；headers 按原文保存；SSE 保存完整事件或原始 chunk 序列。
- 网关返回：最终返回给客户端的状态码、headers、raw body 或 SSE 事件；headers 按原文保存。
- 结束状态：成功、失败、客户端中断、上游中断、网关异常、队列采样原因、HTTP 客户端完成时间与审计完成耗时。

上述范围说明进入原始审计后的捕获阶段。完全成功请求会先进入最近 1 小时热保留窗口，超过热窗口后由后台清理按稳定采样桶裁剪未命中记录的 attempts 和 payload 引用，并把主记录降为 `metadata_only`；主记录及 `session_id` 等结构化身份继续保留。每次请求发生过的计量事实仍由 `usage_records` 保留。进入原始审计后，正文是否长期完整落盘由审计保全策略决定，事件元数据、原始内容哈希、大小、采样原因和保留状态必须可查。

DeepSeek OpenAI-compatible 响应中的 `choices[].message.reasoning_content`、`choices[].delta.reasoning_content`、`usage.prompt_cache_hit_tokens`、`usage.prompt_cache_miss_tokens` 和 `finish_reason = insufficient_system_resource` 属于上游原始响应事实。进入原始审计后应按原文或结构摘要保留，不能因为通用 OpenAI `content` 字段不存在或为空就丢弃这些扩展字段；但列表页、使用记录摘要和普通统计页面不默认展开完整 reasoning 内容。

不得保存“伪完整”内容：

- 不能只保存脱敏后的 body 或 headers；进入审计的 headers、queryString 和 body 应保持原值。
- 不能保存被截断但没有明确标记的 payload。
- 不能把普通运行日志或 `usage_records` 快照当成原始审计日志。
- 如果过期或资源保护策略导致已进入原始审计的正文未完整保留，事件仍然可以写入或保留，但必须把 payload 标记为 `metadata_only`、`summary_only`、`hash_only`、`expired`、`overflow` 或 `dropped`，不能写入一条看起来完整但实际缺内容的记录。

## 成功与非成功判定

`audit_outcome` 当前使用这些值：

- `success`：最终返回客户端的是成功响应，且没有上游尝试失败、网关异常、流式中断或客户端中断。
- `success_after_retry`：最终成功，但中间至少一次上游尝试失败或被账户错误处理策略切换。
- `gateway_failed`：网关本地鉴权、调度、请求构造、响应处理或未知异常失败。
- `upstream_failed`：最终上游失败，包括 4xx、5xx、网络错误、代理错误、超时和账户错误处理策略命中。
- `stream_failed`：SSE 或其他流式响应未完整结束，包含上游流中断、空闲超时、解析失败。
- `downstream_closed`：下游连接提前关闭，但 Node 的 `aborted/close` 事件不能证明由客户端主动操作触发；记录 `error_phase=downstream`、`error_code=downstream_connection_closed`，并在网关元信息中保存 `trigger=unknown_unproven`。
- `client_aborted`：历史兼容值；管理页面必须按“下游连接关闭（历史记录）”中性展示，不得把它当作主动客户端操作的证据。

当前采样规则：

- `success` 默认先全量进入最近 `1` 小时热保留窗口；超过热窗口后，默认 `10%` 稳定采样命中的记录继续保留 payload，未命中采样的成功审计删除 attempts 和 payload 引用并降为 `metadata_only`，不删除主记录。
- `success_after_retry`、`gateway_failed`、`upstream_failed`、`stream_failed`、`downstream_closed`、`client_aborted` 默认进入原始审计；body 不超过 `2MB` 时完整保留，超过后保留原始 hash、大小、content type、头尾窗口和文本预览，不解析原始 JSON Body。
- 如果请求最终没有进入上游，例如 API Key 无效、无可用账号、分组失效，也属于非成功，必须保存原始审计事件，并按问题链路 body 保全档位保存可捕获正文。
- 如果最终成功但任一上游尝试失败，事件不能按普通成功处理；失败尝试按问题链路保全，最终成功响应可按策略保留。

成功采样当前使用稳定桶：

- 每个请求生成 `audit_sample_bucket`，范围 `0` 到 `9999`。
- 成功原始审计长期采样率为 `0.1` 时，`bucket < 1000` 的成功记录超过热窗口后继续保留 payload；`bucket >= 1000` 的普通成功记录超过热窗口后裁剪 payload 并降为 `metadata_only`。
- `sample_reason` 当前记录为 `success_hot_full_retention`、`success_sample_<rate>` 或 `full_capture`，历史记录不随采样率调整而改写；长期保留判断以 `sample_bucket` 为准，不依赖 `sample_reason` 文本。

## 异步写入原则

原始审计日志不能影响正常请求链路。网关请求处理过程中禁止同步写 `audit_logs` 表。

必须遵守：

- 请求开始时只创建内存态 `AuditCaptureContext`。
- 请求处理中只向当前上下文追加原始片段和结构化元数据，不执行数据库写入。
- 请求完成、失败或客户端中断后，先计算终态；普通成功请求和问题链路都以终态快照入队，长期成功采样由后台清理阶段执行。
- HTTP `finish/close` 是返回客户端、请求体在途 lease 和账户并发槽的共同释放边界；审计 `ended_at` 只表示后台收尾后的审计固化时间，二者不得混用。
- 入队对象必须是终态快照，包含主记录、尝试记录和 payload 记录。
- 队列后台 worker 每隔一段时间或达到批量阈值后，用事务批量写入 SQLite。
- 队列写入失败不能影响已经返回给客户端的响应；失败批次可留在内存中等待下一轮重试。
- 系统重启、进程崩溃或强制退出时，允许丢失内存中的活跃捕获、待写队列和失败重试批次。
- 正常 `SIGINT/SIGTERM` 必须先停止接流量，再有限等待活动捕获、server transport、投递队列和 ingest 审计队列；超过时限可以退出，但必须记录未排空计数。

server 只允许对小审计做内联编码。估算超过 `256KB` 的终态快照进入有界 transport worker，正文哈希、摘要、base64 和 Redis JSON 编码都在 worker 内完成；队列采用 FIFO，不能让持续小任务饿死队首大任务。transport 当前最多 2 个 worker，单条输入上限 `64MB`、总预算 `128MB`、活跃预算 `72MB`、单任务超时 `60s`，最终 codec 字符串的实际 UTF-8 输出严格受 `4MiB` 消息预算约束。单正文或聚合正文触发预算收敛时仍按保全契约写入 `summary_only`，不能为缩小消息退化为只有 hash。

基础队列参数：

| 参数 | 默认值 | 说明 |
| --- | --- | --- |
| `enabled` | `true` | 默认启用；仅部署环境变量 `JUHE_AI_AUDIT_LOG_ENABLED` 可临时整体关闭，不提供系统设置开关 |
| `flushIntervalSeconds` | `5` | 后台批量落库间隔 |
| `batchSize` | `500` | 单批最多写入审计请求数；后台定时 flush 遇到积压时每轮最多连续处理 20 批，批间短暂让出事件循环 |
| `queueMaxItems` | `50000` | 待写队列最多保留 50000 条审计请求，超过后优先丢弃成功采样记录；该容量用于承接 50 并发真实网关流量下的短期写入波峰 |
| `queueMaxBytes` | `256MB` | 待写队列最多保留约 256MB 审计快照，超过后按队列策略丢弃；该值按轻量 SQLite 部署控制上限，避免写库积压时审计队列把进程拖入长时间 GC 或 OOM |
| `activeCaptureMaxBytes` | `64MB` | 单个请求活跃捕获上限 |
| `successHotRetentionHours` | `1` | 普通成功请求全量热保留窗口，超过后按稳定桶只长期保留 10% |
| `successSampleRate` | `0.1` | 普通成功请求超过热窗口后的稳定采样率 |
| `successRetentionDays` | `3` | 命中稳定采样的成功链路长期保留天数 |
| `problemRetentionDays` | `7` | 问题链路、问题 payload 与错误聚合组统一保留天数 |
| `successFullBodyLimitBytes` | `512KB` | 成功正文完整保留上限；设为 0 时为 `hash_only` |
| `problemFullBodyLimitBytes` | `2MB` | 问题正文完整保留上限；设为 0 时为 `hash_only` |

以上配置通过 `JUHE_AI_AUDIT_LOG_*` 环境变量读取，非法值会让进程启动失败。`JUHE_AI_AUDIT_LOG_ENABLED=false` 时所有成功、失败、早期拒绝、transport、队列和落库都停止，但功能代码、schema 与历史查询保留；该开关不影响 `usage_records`。成功热窗口、采样率和保留期允许为 0，采样率和成功保留期必须同时为 0 或同时大于 0，启用长期采样时成功保留期必须覆盖热窗口。热窗口可单独启用；三项全 0 只表示不采集成功审计，问题链路仍按问题保留期采集。失败采样、错误聚合窗口、压缩、去重、队列和批次参数不开放。

## 队列策略

队列是内存队列，不是可靠消息队列。

核心要求：

- 只存放已完成的审计记录，不能存放半程请求。
- 后台批量写库使用单事务，成功后从队列移除。
- 写库失败时保留批次并在下一轮重试；如果持续失败导致队列超过上限，优先丢弃成功采样记录。
- 非成功记录优先级高于成功采样记录；成功采样记录不能挤掉非成功记录。
- 如果队列已满且无法释放空间，允许丢弃新来的审计记录，但必须增加内存计数，供管理员在运维页面看到审计丢弃风险。
- 不为了审计日志等待队列空位，不阻塞客户端请求完成。

当前运行态指标：

- `auditQueueLength`
- `auditQueueBytes`
- `auditFlushLastSuccessAt`
- `auditFlushLastError`
- `auditDroppedSuccessCount`
- `auditDroppedFailureCount`
- `auditDroppedOverflowCount`
- `auditActiveCaptureCount`
- `auditTransportQueuedJobs` / `auditTransportQueuedBytes`
- `auditTransportActiveJobs` / `auditTransportActiveBytes`
- `auditTransportCompletedCount` / `auditTransportFailedCount` / `auditTransportRejectedCount`
- `auditTransportPendingDispatchCount`

这些指标可以进入运维监控，不需要写入每条业务记录。

## SSE 与流式响应

SSE 和其他流式响应必须按“终态入队”处理。

规则：

- 流开始时创建捕获上下文，但不入队、不写库。
- 上游每个 SSE chunk 或事件可以追加到内存上下文，转发客户端不能等待审计处理完成。
- 网关向客户端写出的事件也要追加到上下文，便于区分“上游原始流”和“实际返回客户端的流”。
- 只有流自然结束、上游失败、流超时、解析失败或客户端断开后，才计算终态并尝试入队。
- SSE 过程中不能按 chunk 实时写库，不能生成多条未完成审计记录。
- 如果 SSE 完整结束并最终成功，默认先进入最近 1 小时热保留窗口；超过热窗口后保留主记录，仅为 10% 稳定采样继续保留 payload。
- 如果 SSE 中断、超时、客户端断开或上游返回失败事件，必须进入原始审计，正文按问题链路保全档位保存并参与错误聚合。

对 OpenAI Responses SSE，当前重点保留这些语义：

- 是否收到 `response.completed`。
- 是否收到 `response.failed`。
- 最后一个事件类型。
- 完成事件中的 usage 摘要。
- 流关闭原因：`completed`、`upstream_error`、`downstream_closed`、`idle_timeout`、`parse_error`；历史 `client_aborted` 仅表示旧记录，不能推断主动客户端取消。

对 DeepSeek Chat Completions SSE，当前重点额外保留这些语义：

- 是否出现 `choices[].delta.reasoning_content`，以及受控摘要 / 字节数。
- 是否出现 `usage.prompt_cache_hit_tokens`、`usage.prompt_cache_miss_tokens`。
- 是否出现 `finish_reason = insufficient_system_resource`。
- 是否收到 SSE comment / keep-alive；comment 只作为传输保活诊断，不作为可见输出、错误事件或完成事件。
- 流关闭原因仍按统一值记录，不为 DeepSeek 单独新增审计 outcome。

### `audit_payload_refs`

容量保全目标方案应将大字段拆成 `audit_payload_refs` 和 `audit_payload_blobs`：事件表只保存引用、hash、大小和保留状态，正文 blob 在后台压缩并按内容哈希去重后保存。

当前字段：

- `id`
- `audit_log_id`
- `attempt_id`
- `part_type`：`client_request`、`upstream_request`、`upstream_response`、`gateway_response`、`gateway_error`、`gateway_metadata`
- `sequence_index`
- `content_type`
- `content_encoding`
- `headers_blob_id`
- `body_blob_id`
- `headers_sha256`
- `body_sha256`
- `raw_size_bytes`
- `compressed_size_bytes`
- `capture_status`：`complete`、`summary_only`、`hash_only`、`expired`、`dropped`
- `created_at`

字段说明：

- payload blob 保存 header JSON、原始 body 或 SSE chunk 序列；headers 和 body 按原始审计保全策略保存。
- 详情接口会按入库后的 headers JSON 计算 `headersSha256`，用于快速比较客户端请求和上游请求的头部差异；凭据类 headers 的原值参与入库和 hash。
- `body_sha256` 只针对 body 原文字节计算，用于确认 body 完整性和后续导出校验。
- 如果内容是二进制或压缩数据，按原始字节保存，同时记录 `content_type` 和 `content_encoding`。
- 采用保全策略后，`body_sha256` 必须基于压缩前的原始字节计算；相同正文通过 blob 引用复用，不在每条事件里重复存储。

### 当前索引

- `audit_logs(created_at, id)`：保留清理和短窗口默认分页。
- `audit_logs(system_account_id, created_at, id)`：用户维度日期窗口列表；管理员默认全局最新列表使用 `created_at + id` 索引，也可以按用户缩小范围。
- `audit_logs(system_account_id, trace_id, created_at, id)`：用户维度 trace 精确 / 前缀定位；管理员排障允许不指定用户直接按 trace ID 查询。
- `audit_logs(system_account_id, api_key_id, created_at, id)`、`audit_logs(system_account_id, group_id, created_at, id)`、`audit_logs(system_account_id, account_id, created_at, id)`：用户范围内资源定位。
- `audit_logs(system_account_id, client_ip, created_at, id)`：用户范围内客户端 IP 短窗口排障。
- `audit_logs(audit_outcome, created_at, id)`：审计保全策略和错误态排障的例外索引。

不默认建立全局 `final_status_code/path/model/upstream_model/client_ip/trace_id` 索引。全局默认列表只读取最新分页窗口，管理员按 trace ID 排障允许使用现有复合索引；低频 path、model、status、client_ip 筛选只能在用户 + 日期窗口内过滤，或走诊断 / 离线导出；新增全局筛选索引必须登记为例外并说明保留期和容量影响。
- `audit_log_attempts(audit_log_id, attempt_index)`
- `audit_payload_refs(audit_log_id, part_type, sequence_index)`
- `audit_payload_refs(audit_log_id, sequence_index)`：审计详情按真实捕获顺序展示 payload 引用。
- `audit_payload_blobs(sha256, raw_size_bytes, content_type)`：按原始内容 hash 做精确去重。
- `audit_error_groups(fingerprint, window_started_at)`：重复错误聚合定位。

## 当前管理 API

当前只提供管理员接口。

- `GET /__aisys__/api/audit-logs`：分页查询审计日志元数据。
- `GET /__aisys__/api/audit-logs/:id`：用户点击列表行后读取详情补充 DTO，只返回列表行缺失的链路字段、上游尝试摘要和 payload 元数据；前端与触发抽屉的列表行合并渲染。主表、attempt 和 payload 查询均使用显式展示字段投影，不重复读取列表列；错误聚合只作为后台索引元数据，不在详情页默认展示。
- `GET /__aisys__/api/audit-logs/:id/payloads/:payloadId`：在单个响应中返回某段当前已捕获的完整 payload，不接受 `offset + limit` 窗口参数。后端底层仍通过文件 stream 或解压流读取，并返回 `bodyOffset`、`bodyLimit`、`bodyTotalBytes`、`bodyNextOffset` 和 `bodyTruncated` 完整性元数据；超过内部窗口上限的正文默认保持 plain，避免解压路径额外放大读取成本。
- `GET /__aisys__/api/audit-logs/runtime`：查看队列长度、最近落库时间、丢弃计数、transport 活跃/排队字节、完成/失败/拒绝/待投递计数、ingest worker 状态和当前审计设置；响应通过 `runtimeAvailable`、`workerSnapshotAvailable`、`auditLogQueueAvailable` 和 `activeCaptureAvailable` 表达运行态是否可观测，不可观测数字返回 `null` 而不是默认 `0`。
- `GET /__aisys__/api/audit-logs/error-groups`：分页查看错误聚合组。
- `GET /__aisys__/api/audit-logs/error-groups/:id/events`：查看某个错误聚合组下的审计事件。

当前查询条件：

- 成功 / 非成功 / outcome
- 状态码
- path
- model
- upstream model
- model mapping applied
- API Key
- 分组
- AI 账户
- 系统账户
- 供应商
- trace ID
- 客户端 IP
- 错误阶段

查询语义：

- `path` 和 `model` 按结构化精确匹配；需要排查接口族时应选择具体接口路径或后续新增专门维度，不在主表做包含匹配。
- `model` 记录客户端请求模型；发生账号模型映射时，`upstream_model` 记录最终给上游的模型，`pricing_model` 记录本次计价模型，`model_mapping_applied` / `model_mapping_source` 用于排查映射来源。
- `trace ID` 和客户端 IP 支持右侧前缀定位，不使用前导通配符扫描。

## 查看边界

原始审计日志是独立排障数据：

- headers、queryString 和 body 不脱敏、不截断、不改写。
- 必须限制为管理员可见。
- 原始 payload 可以压缩后存储。
- 普通运行日志、错误日志、`usage_records` 快照同样不做敏感字段脱敏；各自仍按捕获范围和容量上限处理。
- 对外分享数据库、日志、截图或 bug 文档前，必须移除原始审计日志数据。
- 删除 API Key 是产品级例外：为满足密钥删除后相关信息全部删除的策略，后台数据集目录库维护任务会分批清理该 Key 关联的历史审计事件、上游尝试、payload 引用和审计错误组，并通过异步文件接口清理不再被引用的正文 blob。删除账号、分组或停用系统账户时仍不自动删除历史审计日志，历史保留按审计日志保留策略处理。

## 保留与清理

原始审计日志体积会远大于使用记录，必须有独立保留策略。

- 成功样本、错误 / 异常事件、错误正文和错误聚合组采用分层保留，当前默认值见 [审计日志保全策略设计](审计日志保全策略设计.md)。
- 支持按时间清理事件、尝试、payload 引用、payload blob 和错误聚合组。
- payload 先清理引用，再删除无引用 blob，不能因为正文过期而删除仍在保留期内的审计事件。
- 清理任务统一接入 `data-retention-cleanup`，只在后台 worker 运行，不在列表请求中触发大批量删除。
- 清理失败只记录运维错误，不影响网关请求。
- 统计缓存不依赖审计日志，删除审计日志不会影响用量统计。

前端：

## 当前能力清单

- 完全成功请求先按最近 1 小时热窗口全量进入原始审计；超过热窗口后，后台清理保留全部主记录，仅为默认 10% 稳定采样命中的成功记录继续保留 payload。
- 每次请求的结构化事实仍由 `usage_records` 保留。
- 非成功请求、客户端中断、流式中断、重试后成功请求默认进入原始审计；body 不超过 `2MB` 时保存完整正文，超过后保存 `summary_only` 摘要。
- 成功样本 body 不超过 `512KB` 时保存完整正文，超过后保存 `summary_only` 摘要。
- 最近 1 小时审计内容搜索通过未压缩 NDJSON 热搜索镜像使用 rg 匹配关键字，命中后按 `auditLogId` 回表展示审计行；搜索镜像随热窗口清理，不替代长期压缩 blob。
- 网关请求路径不直接写 `audit_logs`，审计日志只通过内存队列后台批量落库。
- SSE 请求只在流结束、失败或断开后入队，队列中不存在半程记录。
- 审计队列满或数据库异常时不阻塞正常请求，并记录丢弃计数。
- 管理员能在页面检索审计记录并查看原始请求、上游请求、上游响应和最终返回。
- 未完整保留正文的事件展示 `hash_only`、`summary_only`、`expired`、`overflow` 或 `dropped` 等状态，不伪装成完整原文。
- 重复错误按错误组聚合，并可通过接口追溯组内审计事件。
- 普通用户不能打开审计日志页面和接口。
- 普通运行日志和使用记录快照同样遵循原文日志策略；原始审计日志的差异在于完整链路、采样和保全状态。
