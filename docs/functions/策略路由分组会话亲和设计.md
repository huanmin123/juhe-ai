# 策略路由分组会话亲和设计

> 设计状态：**已实施（2026-10-17）**。本文是分组级会话黏性的行为契约权威来源；实施落点与阻断项关闭记录见 §11/§12。

## 1. 背景与问题

路由层级固定为 `API Key -> 路由策略 -> 分组 -> AI 账户 -> 供应商 / 协议能力`。账户维度的会话亲和（黏账户）与账户内 Key 维度的会话亲和（黏 Key，[账户内 API Key 会话亲和设计](账户内APIKey会话亲和设计.md)）已交付，二者共同语义是：**候选健康时尽可能黏住，策略只在黏不住（故障/不可用）时决策**。

但路由层（分组级）目前不是这个语义。策略路由的分组绑定派发序由 [routeselector.go](../../backend-go/projects/gateway/internal/gatewayrouting/routeselector.go) 按模式产出：

| 模式 | 每请求分组选择 | 会话视角的问题 |
| --- | --- | --- |
| normal | 单分组 | 无（黏性天然完整） |
| failover | 优先序稳定，取第一个 viable 分组 | 基本黏住主组；会话切到备组并成功后，主组恢复也**不回切** |
| round_robin | **每请求**按策略级共享计数器轮转绑定序 | 同一会话连续请求被拆到不同分组，分组内各自黏各自的账户/Key |
| weighted | 平滑加权，选中组按权重逐请求变化 | 同轮询 |
| 超级分组目标 | 路由先选一个超级分组，再由分组域按成员顺序展开 | 组级亲和绑定超级分组目标；成员选择不新增路由级亲和 |

分组级 `round_robin` / `weighted` 把「负载分布」放在了「会话连续性」之上：同一会话的请求随全局计数器在分组间漂移。用户契约应当与账户/Key 两级一致——**轮询与权重只在会话没有可黏分组（首次）或黏不住（故障）时决策，而不是每个请求都重新掷骰子**。

现行契约（[统一会话身份与审计串联设计](统一会话身份与审计串联设计.md)）明确「会话粘黏不会跨越路由/分组边界」。本设计将该契约修订为**三层黏性**：策略内黏分组 → 分组内黏账户 → 账户内黏 Key；黏住关系仍不跨路由策略边界。

## 2. 目标与非目标

### 目标

1. 同一会话（有 conversationKey）在同一策略路由内，首个协议成功请求按模式选择分组并绑定；后续请求只要该分组仍在策略活跃绑定中且通过既有硬过滤（分组启用、账户能力、模型、健康），一律直接路由到该分组。
2. 黏住分组不可用时（绑定缺失/组被移出/组内无 viable 账户），按现行模式选择（轮转/加权/优先序）重选，并在协议成功后重绑新分组；不自动回切旧分组。
3. 黏住命中不消费轮转/加权状态（与 Key 级「黏住不消费计数器」一致）；无会话键流量与其他会话的模式行为完全不变。
4. 写回只认最终协议成功（`ProtocolValidatedSuccess=true` 且不再重试上游），成功者赢；2xx 响应头不写。

### 非目标

1. 不改路由策略的配置面（模式、绑定、权重、优先级的用户配置语义不变）；路由拓扑配置仍是会话盲的，组级黏性是网关在策略拓扑之内的软调度偏好，与账户亲和同级。
2. 不做跨策略黏住：换绑路由策略即失配重绑。
3. 不改 normal 行为；超级分组的成员展开属于分组域，组级亲和只绑定路由选中的超级分组目标。
4. 不做组级流量迁移（账户级 `trafficMigrationPreferred` 语义不外推到分组）。
5. 无会话键请求（无法生成 conversationKey）不参与，行为与现状逐字节一致。

## 3. 绑定与键

### 3.1 组亲和键

- `groupAffinityKey = HMAC-SHA256(JUHE_AI_SECRET, conversationKey + systemAccountID + apiKeyID + routeStrategyID)`。
- 与账户亲和键（含 GroupID）不同源不同名：分组选择发生在分组解析**之前**，键不能含分组。使用独立的 HMAC purpose/domain（固定字符串 `group-affinity:v1`）和独立 canonicalizer；不得以现有 `DeriveGatewaySessionAffinityKey` 省略 `GroupID` 的方式复用，避免与账户亲和键发生语义碰撞。Redis 键前缀独立（如 `juhe-ai:session-affinity:group-binding:`），与账户绑定键空间隔离。
- 身份来源与账户亲和一致（统一会话身份解析链：官方会话 Header / 显式 `x-juhe-client-profile` 兼容入口）。
- canonicalizer 的输入顺序固定为 `purpose, systemAccountID, apiKeyID, routeStrategyID, conversationKey`，每段使用长度前缀编码；实现必须提供至少 2 组固定测试向量，并验证改变任一字段都会改变结果。

### 3.2 绑定记录

- `GroupSessionBinding { RouteStrategyID string; GroupID string }`，按 `groupAffinityKey` 一会话一策略一条。
- 组绑定使用独立记录类型、独立 Redis key/index 命名和独立 memory map，不复用账户 `SessionBinding` 的 owner/index 结构。记录只包含 `RouteStrategyID`、`GroupID` 和版本/时间字段，不包含账户 ID、Key 指纹或迁移字段。Redis（TTL 1h，读不刷 TTL）+ 进程内 memory（TTL 24h）；写走既有 CAS 脚本模式（整 rawValue 比较，≤2 轮，冲突保留现值并告警）。组绑定不创建账户绑定索引，也不参与账户迁移。
- 多实例要求 `JUHE_AI_SECRET` 实例间一致（同 Key 指纹绑定的部署约束，部署文档已覆盖）。

### 3.3 与既有两层黏性的关系

- 分组黏住后，会话稳定落在同一分组，账户亲和（含 Key 指纹）继续在 `(策略, 分组)` 命名空间内工作，语义不变。
- 会话重绑新分组后，新分组命名空间内的账户/Key 绑定从零开始（首个协议成功写回）；旧分组的账户/Key 绑定按 TTL 自然过期，不主动清理（与账户级跨组失败经验保留语义一致）。
- 三层删除不通过扩大现有账户 `ForgetAsync` 的入参实现。新增 `ForgetSessionAffinityLayers(ctx, AffinityContext, FailureClass)`，其中 `AffinityContext` 同时携带 `GroupAffinityKey`、账户 `SessionAffinityKey`、当前账户 ID 和策略 ID；只有明确列入 §5.2 的触发类才删除组绑定。缺少组键（尚未完成身份解析或无会话键）时只执行原有账户删除，不猜测或派生空键。

## 4. 选择管线

在动态路由选择之前插入黏性查询，命中则重排绑定派发序。当前 Go 组合根中 `ReadCachedGatewayRuntimeAsync` 会在 `preflight` 之前调用动态排序器（`gatewaypreauth/preauth.go:159`，`gatewayruntimecache/runtime.go:362-368`），因此不能只在 `ResolveNormalGatewayModelRoute` 内追加一次查询；实施必须把当前单阶段 runtime read 拆成“静态身份快照 → 身份解析 → 动态分组派发快照”三步，并保证旧的缓存/鉴权错误语义不变：

1. `ReadCachedGatewayRuntimeIdentityAsync(ctx, gatewayAPIKey)` 只读取并校验 API Key、策略、绑定和 settings，不调用 `OrderAPIKeyGroupBindings*`，不读取分组账户，不消费任何 RR/weighted 状态。
2. preflight 依据该静态快照解析 `conversationKey`、最终 client profile 和 `GroupAffinityInput`；无会话键或范围外模式直接走原有单分组/静态路径。
3. `SelectDynamicGatewayRuntimeForDispatch(ctx, identitySnapshot, GroupAffinityInput)` 才允许读取组绑定、应用 sticky/peek 或推进一次模式状态，并加载候选组账户。该函数返回一次性的 `OrderedGroupIDs` 快照，后续 normal route、account dispatch 和跨组 fallback 只消费这份快照。

实现可以把三个步骤封装在一个新 service 方法内，但行为上必须保持上述边界；不得让兼容包装方法在身份未知时偷偷调用旧的动态 `Orderer`。

```
解析 API Key 与请求身份（可在 preflight 得到；动态 runtime route 不得先消费模式状态）
→ 组亲和键可计算 且 模式 ∈ {round_robin, weighted, failover} 且 活跃绑定 ≥ 2
   → 查组绑定
      → 命中且绑定组在活跃绑定中：跳过轮转/加权状态消费，
        绑定序 = [绑定组] + 其余按模式派发序；走既有「第一个 viable 分组」walk
         → 绑定组 viable：直接使用（黏住命中）
         → 绑定组不可用：本请求将其加入 excludedGroupIDs，沿同一份候选快照继续 walk；不得重新读取亲和并把已失败组放回队首
      → 未命中 / 绑定组已被移出绑定：完全现行模式行为
→ 无会话键 / normal / 单活跃绑定：按各自现行目标语义执行并跳过路由级亲和查询；超级分组目标本身不改变判定，weighted/failover/round_robin + super 且活跃绑定 ≥2 时仍查询并绑定超级分组
```

关键点：

1. **黏性优先级高于模式序，但低于硬过滤**：绑定组只有在通过分组启用、模型、协议、权限、健康、并发和账户能力过滤后才可命中；通过硬过滤后，`CandidatePriority` 不得把另一个组排到黏性组之前。只有黏性组无候选时，才按本请求的模式候选序选择其他组。
2. **候选快照只生成一次**：同一请求第一次选择后固定 `OrderedGroupIDs` 和 `excludedGroupIDs`；跨组回退只推进该快照的 cursor，不再次调用组亲和查询或模式状态推进。最终成功组写回组绑定，失败请求保留原组绑定。
3. **不消费模式状态**：黏性命中路径不得调用会推进状态的 `OrderAPIKeyGroupBindingsForDispatch(Async)`。`round_robin` 必须提供纯函数 `peek` 生成当前序列；`weighted` 必须提供不修改本地 debt、也不调用 Redis counter 的 `peek` 生成剩余序列。只有无绑定、绑定失配或同请求进入策略重选时，才允许恰好推进一次对应状态。
4. **动态 runtime route seam 是硬前置**：实现必须落成上面的三阶段契约（可以由一个编排方法内部实现），并以测试证明身份快照阶段不会调用状态推进器。不得保留“runtime 已按模式选组，之后再尝试组 sticky”的双重选择。runtime 阶段的 `hasDispatchableCachedGatewayAccount` 只能作为候选组的粗粒度可用性提示；最终模型、协议、能力、并发硬过滤仍由 normal route 的候选解析完成，不能把粗粒度命中当成 sticky 已确认。
5. **身份以最终 profile 为准**：初始/最终 client profile 重解析不一致时，丢弃初始 lookup 结果，使用最终 `conversationKey` 再查一次；同一请求最多 2 次组亲和 GET，且不得推进模式状态两次。无法得到最终身份时不建立、不更新组绑定。
6. **生效边界判定**在键计算处一次完成：无 conversationKey / 模式不在范围 / 活跃绑定少于 2，直接跳过查询（零额外开销路径）。

## 5. 写回契约

- 唯一写回点：`confirmProtocolSuccessSideEffects`（`!RetryUpstream` 最终协议成功分支），与账户级 `RememberAsync`、Key 指纹写回并列消费。
- 写回内容：最终成功派发的路由目标分组；若目标为超级分组，另由分组域记录实际成员分组，不改变路由级组绑定。
- 成功者赢：写入即建即更（组绑定无账户级 claim 前置，首个协议成功负责创建；会话在该策略下至多一条绑定），CAS ≤2 轮，冲突保留现值并告警。
- 失败/取消/重试/2xx 头不写；协议失败的删除范围按下表执行，不得把所有现有 `ForgetAsync` 调用无条件扩大为组删除。
- 不回切：绑定随**最终协议成功**移动。黏住分组故障重绑到备组后，即使原主组恢复，会话仍黏备组；同一请求所有分组均失败时保留原组绑定，避免一次失败把会话绑定清空。

### 5.1 结算上下文

`DispatchContext`/`UpstreamDispatchResult` 必须携带 `GroupAffinityKey`、`GroupAffinityRouteStrategyID` 和本请求初始组 ID；`confirmProtocolSuccessSideEffects` 只从最终成功 attempt 的 `SelectedGroupID` 取写回组。组、账户、Key 三个写回互相独立，任一层失败只告警，不回滚其他层；三层写回互相独立、互不改写语义：账户层绑定在引擎 2xx 响应头时点落定（既有行为），组层与 Key 指纹层在最终协议成功结算块内按组 → Key 顺序消费；层间顺序不改变成功者赢的 CAS 语义，也无原子性要求（§10）。

### 5.2 删除触发矩阵

| 触发 | 组绑定 | 账户/Key 绑定 | 说明 |
| --- | --- | --- | --- |
| 显式 `ForgetSessionAffinity` | 删除 | 删除 | 三层同删，需携带 `AffinityContext` |
| 非流式 2xx 协议校验失败、正文中断等既有响应失败 forget | 删除 | 删除 | 与账户内 API Key 设计 §8.5 一致 |
| 请求内上游重试、同账户换 Key、跨组回退中间失败 | 保留 | 按既有 attempt 语义 | 不得提前清空，最终成功者负责写回 |
| 客户端取消、首字超时、传输失败 | 保留 | 按现有账户失败链路 | 组亲和是策略级路由偏好，不因单个传输失败删除 |
| 本请求所有候选最终失败 | 保留原绑定 | 按现有账户失败链路 | 下次请求仍会验证硬过滤后再决定是否失配 |

## 6. 生效边界与兼容

| 场景 | 行为 |
| --- | --- |
| 无会话键请求 | 完全现行行为（零改动路径） |
| normal 模式 | 完全现行行为 |
| 超级分组目标 | 路由级只绑定超级分组；成员展开、成员内账号亲和和成员记账由分组域处理 |
| 单活跃绑定 | 完全现行行为（绑定即必选） |
| round_robin / weighted / failover + 会话键 | 本设计生效 |
| 绑定组被移出策略绑定 / 组禁用 | 视同未命中，按模式重选，成功后重绑 |
| 组内全部账户不可用（模型/能力/健康过滤后为空） | walk 落到下一组（请求级组回退），成功后重绑 |
| 跨组回退（同一请求内） | 消费本请求一次性候选快照：排除已失败分组、不重查组亲和、不推进模式状态（§4 关键点 2）；账户级亲和键随最终落组自然重建（既有语义），最终成功分组负责写回组绑定 |
| 旧版本读新记录 | 组绑定是独立键空间的新记录，旧版本不读不写，无兼容问题 |

## 7. 验收标准

1. `round_robin` 双分组策略 + 一个会话键：首请求按轮转落组 A 并绑定；随后连续 20 个协议成功请求全部落组 A（mock 上游按分组账户命中数为 oracle）；期间无会话请求继续正常轮转两个分组，且轮转计数器不受会话黏住影响（另一无会话会话的命中序列符合纯轮转）。
2. 同策略两个会话键：各自首绑后分别黏住自己分组（可强制首轮错开），互不影响；删除/重绑 A 不改变 B；并发 32 个请求交错执行，B 的绑定不能被 A 的写回覆盖。
3. `weighted` 双分组（权重 2:1）：会话首绑后连续 30 个请求全部黏住首绑分组；另执行无会话 300 个成功请求，命中数必须为 200:100（Redis counter 与 memory debt 两驱动分别执行，允许最大绝对偏差 2 个请求），并断言 sticky hit 不产生 counter/debt 写操作。
4. `failover` 双分组：会话黏主组；主组全部账户脚本失败后请求组回退落备组，协议成功重绑备组；主组恢复（脚本还原）后连续 20 个成功请求仍黏备组，不回切。若主备同一请求均失败，随后主组恢复时下一请求仍允许主组重新成为候选，但不得因失败请求提前改写组绑定。
5. 黏住分组的全部账户被移出/禁用（管理面操作）：下一请求按模式重选其他分组并重绑，不再命中旧分组。
6. 协议失败（2xx 坏载荷）：组绑定随既有响应失败 forget 一并删除，下一请求按模式重新选择并重绑。
7. 黏住命中不消费轮转/加权状态：执行 1 个 sticky 会话 100 次、无会话 100 次、另一个 sticky 会话 100 次交错请求；去除 sticky 请求后，无会话请求的 RR 序列与“只执行无会话 100 次”的基线逐项一致，weighted counter/debt 写次数为 0。
8. normal（无论目标是普通还是超级分组）、单活跃绑定和无会话键：验证路由级亲和查询为零；weighted/failover/round_robin + 超级分组且活跃绑定 ≥2 时验证仍查询并黏住超级分组目标，成员展开不产生旧 `merge` 专属字段（回归断言）。
9. 显式 `ForgetAsync` 后分组、账户、Key 三层绑定一并消失，下一请求全新选择。
10. Redis 与 memory 双驱动分别验证组绑定读/写/CAS/TTL 语义；Redis TTL 1h、memory TTL 24h，sticky read 不刷新 TTL；每个请求组亲和 GET ≤2，sticky hit 的 RR/weighted state write = 0，最终成功组写回 CAS ≤2 轮。
11. 多实例部署要求 `JUHE_AI_SECRET` 一致（复用既有部署检查表述，不新增机制）。

## 8. 验证方式

- **单元测试（Mock 优先）**：
  - `gatewayrouting`：黏住重排（命中置首、未命中原序、绑定组不在活跃绑定中视同未命中）、模式范围边界（无会话键、normal、单绑定跳过；多目标 super 仍查询）、`peek` 不推进 RR/weighted 状态、硬过滤后 sticky 优先于 `CandidatePriority`、同请求 excluded group 不回队首。
  - `gatewaysession`：独立组绑定编解码、独立 key/index、双驱动读写、HMAC purpose 与固定向量、CAS ≤2 轮与冲突放弃、TTL 不刷新；三层删除按 §5.2 矩阵验证。
  - `gatewaypreauth`/`gatewayruntimecache`：身份解析前不得调用会推进模式状态的排序器；sticky hit/miss 各自最多一次模式状态推进，最终 profile 重解析最多一次补查。
  - `gatewaydispatch`/`chain`：`DispatchContext` 携带组键、写回时点（仅 `protocolValidatedSuccess`）、写回分组取值、同请求 fallback 不重复查 sticky、重绑后旧分组不再命中。
- **回归**：既有账户亲和、Key 黏性、组回退、轮转计数相关测试全量通过；旧 merge 测试已于 2026-10-21 随 merge 运行链删除，不计入目标设计通过证据。

## 10. 风险与注意事项

- **会话长尾集中**：黏住会把长会话钉在单个分组上，分组间负载由「新会话按模式分布」承担——与 Key 级「黏住不消费计数器」同一取舍，属预期行为。
- **首绑采样偏差**：rr 下会话黏住的是「首次轮转到」的分组，长会话分布可能偏离均匀（会话数不等于请求数）。可接受；若未来需要均匀性，可在绑定缺失时改用加权选组，属后续演进。
- **组绑定与账户绑定的双重写回顺序**：确认结算块内三层写回的顺序（组 → 账户 → Key）须原子性无要求但不得互相改写语义；失败任一层不回滚其他层（与现有账户/Key 解耦一致）。
- **身份重解析边界**：初始/最终 client profile 不一致时组黏性失配一次，按模式重选并重绑，最终身份一致后恢复黏住（优雅降级，不新增机制）。

## 11. 复审裁决（2026-10-17）

本设计**有条件通过**，但在以下四项完成前不得进入 Work/实施阶段：

1. **时序阻断项**：必须采用 §4「动态 runtime route seam 是硬前置」的三阶段契约（静态身份快照 → 身份解析 → 动态分组派发快照），并证明组亲和读取发生在动态 RR/weighted 状态消费之前；仅在 `ResolveNormalGatewayModelRoute` 里重排绑定不合格。
2. **状态阻断项**：必须实现并测试纯 `peek`；sticky hit 的 RR Redis `NextRouteCounterIndex` 调用次数为 0，weighted 本地 debt map 和 Redis counter 均为 0 次写入。不能通过“先正常排序再把 sticky 组挪到首位”规避。
3. **数据面阻断项**：组绑定必须使用独立 type/key/index/port；`DispatchContext`、失败派发和响应效果必须携带 `GroupAffinityKey`，按 §5.2 选择性删除，不能把组删除隐式塞进现有账户 `ForgetAsync`。
4. **路由语义阻断项**：sticky 只在硬过滤通过后取得最高组优先级；同请求 fallback 使用一次候选快照并排除已失败组，不能重新命中旧 sticky 组。

以下取舍由本复审直接裁决：

- 继续采用 `round_robin`、`weighted`、`failover`、`normal` 四种模式；单活跃绑定保持零额外查询，超级分组成员展开不新增路由级模式。
- 采用 failover 不回切；只有最终协议成功才移动绑定，全候选失败保留旧绑定。
- 采用独立 `group-affinity:v1` HMAC purpose 和独立组绑定记录，不复用账户绑定记录的空 `GroupID` 变体。
- 组亲和只表示路由偏好；模型、协议、能力、健康、并发等硬条件始终优先，传输失败/取消/首字超时不自动删除组绑定。

### 12.3 与 §4/§5 契约的两点精确化（行为裁定，不改变验收语义）

1. **Gemini interaction 亲和请求不再消费 RR/weighted 状态**：interaction 亲和自带分组/账号锚定，策略轮转从未治理其派发。静态化后补全块对 `interactionResourceAffinity != nil` 的请求整体跳过（§4 关键点 3「策略选择未治理派发时不推进」的严格化）；与旧行为（中间件完整读每请求消耗一次轮转刻度）相比，rr/weighted 计数器对这类请求不再推进。
2. **第 3 步完成前失败路径的组归因漂移**：无效 JSON、客户端 IP 错误熔断、Key 不可用等在补全块之前收口的失败，其 usage/审计 `group_id` 与 IP 错误熔断桶键取静态存储序首位，而旧完整读下是轮转后的动态首位。三阶段接缝的固有代价，属诊断归因口径变化，不影响派发与记账正确性。
3. **最终 profile 重解析的推进预算**：初始阶段已推进（miss）时，最终身份命中走 peek 重选、未命中保持既有派发序（`AdvanceOnStickyMiss=false`）；初始阶段零推进（hit）时，最终 miss 补一次推进。任意请求全生命周期模式状态推进 ≤1 次、组亲和 GET ≤2 次（单测 7 行矩阵覆盖）。
