# 网关兼容策略与请求恢复设计

## 文档目标

本文固定网关在多客户端、多供应商、多协议工具场景下的兼容策略边界，重点解决这些问题：

- 不把某个客户端、供应商或错误码特例散落到主调度流程。
- `openai_standard` 首轮保持 raw passthrough，不因为识别到 Codex Desktop、某个 User-Agent 或某个供应商就提前改写请求体。
- 上游明确返回协议兼容失败时，由独立策略决定是否生成一次受控的请求体变体重试。
- 新客户端、新供应商、新工具能力只扩展画像和策略，不反复改派发、失败处理和上游请求准备主流程。

## 核心原则

- **首轮原样优先**：API Key `openai_standard` 账号首轮请求继续使用客户端 raw body。兼容恢复只在上游已经给出明确失败信号后触发。
- **决策和执行分离**：策略层只输出动作，body/header transform 只执行 patch，不在 transform 里判断客户端或供应商。
- **请求级恢复不等于账号健康**：`thinking_signature_invalid`、`invalid_encrypted_content` 这类错误可触发请求体恢复，但不能直接把账号写成异常；账号状态仍按网关异常重试与兜底策略确认。
- **一次恢复有上限**：同一请求、同一账号、同一上游 URL 对同一种恢复策略最多执行一次，避免用变体重试制造新风暴。
- **不做用户侧任意规则**：兼容策略是系统内置能力，不开放任意 header/body 脚本或账户级自由 patch。
- **可观测不泄露密文**：诊断只记录是否存在 `reasoning.encrypted_content`、`previous_response_id`、reasoning item 数量和清洗动作，不记录 encrypted content 原文。

## 分层模型

```text
client-profile
  识别下游客户端和协议期望，例如 codex、generic_openai。

provider-capability
  描述账号 / 供应商 / 上游 URL 的协议能力，例如是否稳定支持 encrypted reasoning。

request-feature
  从请求中提取受控特征，例如 endpoint family、stream、encrypted reasoning、previous_response_id、function_call_output。

error-classifier
  把上游错误归一成协议兼容信号，例如 encrypted_reasoning_invalid、previous_response_not_found。

compatibility-policy
  输入画像、能力、请求特征和错误信号，输出下一步动作。

body/header-transform
  根据动作生成请求体或请求头变体，不修改原始 req.rawBody。
```

主调度层只消费策略输出，不理解具体协议细节。新增供应商或客户端时，优先补画像和策略，不在 `openai-gateway-upstream-dispatch.ts` 堆积供应商特例。

## 策略输入

| 输入 | 来源 | 用途 |
| --- | --- | --- |
| `clientProfile` | `openai-gateway-client-strategy.ts` | 判断客户端是否有专属重试语义；不能仅靠 User-Agent 升级为专属策略 |
| `account` / `providerCode` / `baseUrl` | 调度命中的账号 | 判断供应商能力和上游 URL 范围 |
| `requestFeatures` | 请求体保护 / 请求特征检查 | 判断是否包含可恢复的协议状态 |
| `upstreamErrorSignal` | 非 `2xx` 响应体解析或流式失败解析 | 判断是否属于兼容恢复，而不是普通临时上游失败 |
| `attemptState` | 当前请求内存态 | 控制同一恢复策略最多执行一次 |

## 请求特征

第一阶段只需要覆盖 Responses encrypted reasoning：

| 特征 | 含义 | 诊断字段 |
| --- | --- | --- |
| `endpointFamily=responses` | `POST /responses` 或 `POST /v1/responses` | `endpointFamily` |
| `stream=true` | 下游请求流式响应 | `stream` |
| `hasEncryptedReasoning` | `input` 中存在 reasoning item 的 `encrypted_content` | `hasEncryptedReasoning` |
| `encryptedReasoningItemCount` | 带 `encrypted_content` 的 reasoning item 数量 | `encryptedReasoningItemCount` |
| `hasPreviousResponseId` | 顶层存在 `previous_response_id` | `hasPreviousResponseId` |
| `hasFunctionCallOutput` | `input` 中存在 `function_call_output` | `hasFunctionCallOutput` |

大 JSON 请求如果已经超过内联解析阈值，恢复策略必须在触发后通过 JSON worker 或其他受控解析生成变体；不能为了普通首轮透传提前完整解析所有大请求，也不能在请求主线程同步解析大 body。

## 错误信号

第一阶段内置这些兼容信号：

| 错误码 / 文案 | 归一信号 | 说明 |
| --- | --- | --- |
| `thinking_signature_invalid` | `encrypted_reasoning_invalid` | 上游无法验证 reasoning encrypted content |
| `invalid_encrypted_content` | `encrypted_reasoning_invalid` | 上游拒绝 encrypted content |
| 文案包含 `encrypted content` 且包含 `could not be decrypted` / `could not be verified` | `encrypted_reasoning_invalid` | 兼容部分中转包裹错误码或丢失 code 的响应 |

错误信号只用于请求级兼容恢复和诊断。是否进入账号运行态屏障、是否本地屏蔽、是否确认持久账号状态，仍由 [网关异常重试与兜底策略](网关异常重试与兜底策略.md) 决定。

## 恢复动作

| 动作 | 含义 | 使用条件 |
| --- | --- | --- |
| `continue_default` | 继续现有同账号重试 / 切号逻辑 | 未命中兼容恢复策略 |
| `retry_cleaned_body_once` | 使用清洗后的请求体在当前账号当前上游 URL 重试一次 | 命中 encrypted reasoning invalid，且请求体包含可清洗 encrypted reasoning |

`retry_cleaned_body_once` 不修改 `req.rawBody`，只作为当前 attempt 的 body override。审计中应能区分原始 attempt 和 recovery attempt，并记录清洗动作摘要。
如果上游返回了 encrypted reasoning 类错误，但当前请求没有可恢复的 `reasoning.encrypted_content`，策略必须返回 `continue_default`，继续现有同账号确认、账号错误处理和 fallback 流程，不能因为错误文案相似就提前跳号。

## Responses encrypted reasoning 恢复规则

当同时满足以下条件时触发：

- 请求是 `POST /responses` 或 `POST /v1/responses`。
- 原始或当前 body 是 JSON 对象。
- `input` 中存在 reasoning item 的 `encrypted_content`。
- 上游非 `2xx` 错误归一为 `encrypted_reasoning_invalid`。
- 当前请求当前账号当前上游 URL 尚未执行过该恢复策略。

清洗方式：

- 删除 `input` 中所有 reasoning item 的 `encrypted_content` 字段。
- 如果 reasoning item 删除 `encrypted_content` 后没有保留价值，且不会破坏工具输出顺序，可以删除空 reasoning item。
- 如果存在 `previous_response_id` 且本轮不是 `function_call_output` 场景，可以删除 `previous_response_id`。
- 如果存在 `function_call_output`，默认保留 `previous_response_id`，避免破坏工具结果提交链路。

恢复后：

- 立即用清洗 body 重试当前账号当前上游 URL 一次。
- 如果恢复重试仍失败，进入默认失败流水线并尝试后续账号。
- 不再对同一个恢复策略重复生成第二个清洗体。

## 与现有能力关系

- `clientCompatibility=codex_responses` 仍负责 API Key 账号显式 Codex Responses 请求体 / header 补齐。
- `clientStrategy` 仍负责客户端画像和 Codex turn 级避让。
- `sessionAffinity` 继续负责成功后的账号粘性，不承担 encrypted reasoning 清洗。
- `streamInterceptPolicy` 处理 `200 + SSE` 事件污染或失败，不替代非 `2xx` 请求级恢复。
- 账户错误处理策略仍只决定确认失败后的目标状态，不承载请求 body 变体生成。

## 验证要求

新增或调整兼容策略时，至少覆盖：

- 首轮 `openai_standard` raw passthrough 不变。
- mock 上游首次返回 `thinking_signature_invalid` 时，网关使用清洗 body 对同账号重试并成功；至少包含一次超过内联解析阈值的大请求，确认恢复解析走受控路径。
- 清洗 body 删除 `reasoning.encrypted_content`，非 `function_call_output` 场景删除 `previous_response_id`。
- `function_call_output` 场景清洗 encrypted content 但保留 `previous_response_id`。
- 请求不含 encrypted reasoning 时不触发清洗，仍走默认失败流程。
- 清洗重试失败后不重复清洗循环，并能 fallback 到后续账号。
- 审计 / 日志只记录清洗摘要，不记录 encrypted content 原文。
