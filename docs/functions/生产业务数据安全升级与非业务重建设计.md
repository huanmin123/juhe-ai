# 生产业务数据安全升级与非业务重建设计

## 背景与目标

本设计用于 Node 高性能同机多进程生产发布。发布范围只包含 Node 应用、当前 Node PostgreSQL schema、Control / Gateway / DB service / worker 拓扑和 Redis 三角色；Go 仍处于独立迁移阶段，不进入本次打包、启动、验证或切流范围。

本次数据策略固定为：

- `juhe_business` 是唯一必须保留的历史事实域，在 fresh 候选数据库中恢复并升级到发布包声明的当前 Node schema。
- `juhe_chat`、`juhe_dataset`、`juhe_usage`、`juhe_stats`、`juhe_codex_context` 不导入历史数据，由当前 Node schema 重建为空结构。
- temporary 槽使用候选数据库和独立 Redis namespace；请求、数据库、队列、全部 worker、慢 SSE 和管理面全部通过前不切流。
- 不创建完整生产数据库快照，不保留旧整库或旧应用版本回滚点。失败采用前向修复：修复代码或离线 schema、重新构建不可变包、重新启动 temporary 并重跑全部门禁。

## 数据分类

| 数据域 | 主要内容 | 本次策略 | 验收方式 |
| --- | --- | --- | --- |
| `juhe_business` | 系统账户、AI 账户、凭据、分组、路由策略、API Key、授权、供应商与系统设置 | 必须保留；恢复到 fresh 候选库后运行当前 Node schema 和默认数据入口 | 全表列契约、逐行主键对账、已批准默认资源新增、凭据可解密性和管理 CRUD |
| `juhe_chat` | AI 问答会话、消息、幂等和存储窗口 | 不导入历史数据，重建空结构 | 表、约束和索引存在，新会话读写正常 |
| `juhe_dataset` | 审计、操作日志、公开接口日志、运行日志索引、模型检查等 | 不导入历史数据，重建空结构 | 新请求的日志与审计可落库 |
| `juhe_usage` | 使用记录事实、分区和 scope catalog | 不导入历史数据，重建空结构 | 新请求与 usage 行精确对账，分区和唯一约束正常 |
| `juhe_stats` | 统计窗口、排行、质量、系统与进程指标 | 不导入历史数据，重建空结构 | worker 从新 usage / metrics 开始聚合，游标和结果正常推进 |
| `juhe_codex_context` | Codex 上下文状态 | 不导入历史数据，重建空结构 | 新上下文可写入、读取和清理 |
| Redis cache | 可丢失缓存 | 新 namespace 冷启动 | 缓存 miss 可有界回填 |
| Redis state | 短 TTL 运行态 | 新 namespace 冷启动 | 原子计数、TTL 和探针状态正常收敛 |
| Redis queue | 未 ACK 的可靠队列事实 | 旧 namespace 先 fence 并排空；新 namespace 空启动 | 5 条 Stream 的 pending 和 lag 连续两个窗口为 0 |

不导入聊天、usage、日志、统计和上下文是用户明确选择，这些历史数据在旧整库删除后不可恢复。由于这些非业务域占据绝大部分空间，本次风险控制依赖小体量业务专用备份、隔离候选库、逐行对账和严格 temporary 门禁，不依赖完整数据库快照。

## 候选数据库构建

1. 从源库只读导出 `juhe_business` custom dump、业务 schema SQL、业务表清单与 SHA256；不导出其他 schema 历史数据。
2. 新建空候选数据库，只恢复 `juhe_business`。目标数据库必须是显式候选名，不允许原地改造源库。
3. 使用候选包内 `pnpm run ops:postgres-upgrade-node-schema` 建立当前六个 schema、补齐既有业务表结构并写入当前默认资源；连续执行两次，第二次必须保持幂等。
4. 使用候选包内 `pnpm run ops:verify-business-preservation` 对源业务副本与候选库逐表、逐主键、逐列对账。通过 `JUHE_AI_BUSINESS_VERIFY_ALLOWED_NEW_TABLES` 显式批准当前 schema 新增业务表，通过 `JUHE_AI_BUSINESS_VERIFY_ALLOWED_ADDITION_TABLES` 批准当前默认资源新增行；缺失行、修改行、未知新增或未知类型变化均阻断。
5. 运行外键检查、sequence / identity 检查和 `ANALYZE`，再启动完整 temporary 多进程槽。其他 schema 必须只有当前空结构和 temporary 验证期间新产生的数据。

Node schema 入口是显式离线运维命令，不接入服务启动或正常请求路径。业务类型升级只接受已验证的 `proxy_profiles.enabled` 整数 `0/1` 到 boolean，以及三列 ISO 时间文本到 `timestamptz`；遇到非法旧值立即失败，不做猜测或吞错。

## 运维入口护栏

- 源业务副本与候选数据库必须使用两个不同连接串；校验器只开启 `REPEATABLE READ READ ONLY` 快照。
- 候选数据库必须新建，验收成功前不得删除或修改源数据库。
- `juhe_business` dump、业务 schema SQL、manifest 和 SHA256 任一缺失或回读失败即停止。
- 允许新增表、允许新增默认行和明确舍弃的源表必须显式配置；配置指向不存在的舍弃表同样阻断。
- 本次已验证的新增业务表白名单固定为 `account_circuit_incidents,account_circuit_outbox,account_quality_enforcements,model_quality_policies,model_quality_schedules,request_quota_hourly_window_scope_bindings`；代码继续变化导致名单不符时必须重新审计，不能自动放宽。
- 不自动清理旧 Redis queue；只有 fence 后 pending、lag 和 backlog 连续收敛为 0 才能切换 namespace。
- 输出只记录数据库标识、schema、表名、行数、摘要、耗时和哈希，不输出 DSN、凭据值或业务行内容。

## Temporary 门禁

temporary 槽必须在候选数据库和独立 Redis namespace 上完成：

- 1 Control、3 Gateway、4 DB service、2 Usage、2 Log、1 Stats、1 Ops 全部存活，角色和端口身份与预期一致。
- Control / Gateway 健康检查连续成功；Control 报告 6 个 ready worker，Gateway 不托管后台 worker。
- 管理登录、系统账户、AI 账户、分组、路由策略、API Key、授权、代理和系统设置读取正常；隔离验证写入必须清理。
- 普通请求、大响应、慢 SSE、首输出超时、流提交后失败和协议契约回归全部通过。
- 新 usage / audit 记录落入候选库，5 条 Redis Stream 在收敛后 pending 和 lag 均为 0。
- `JUHE_AI_AUDIT_LOG_ENABLED=true` 与 `JUHE_AI_RUNTIME_LOG_INDEX_ENABLED=true` 必须由生产启动脚本显式固定；真实请求后审计日志可查询，角色 JSONL 被 ingest worker 导入后可通过 Log 搜索检索。
- PostgreSQL 无 SQL 类型错误、deadlock、未知 lock waiter、长事务、悬空外键或未批准 schema 漂移。
- 真实停止一组 Usage / Log worker 后，Supervisor 必须自动拉起，队列继续收敛且无重复写入。
- temporary 停止或门禁失败时不切流；修复后重新构建候选包、重建候选槽并从第一项重跑。

## 生产顺序

1. 候选包、提交、SHA256、包内容和本地证据全部固定后，获取部署计划锁；此前生产保持零写入。
2. 执行生产只读预检并创建 `juhe_business` custom dump、业务 schema SQL、manifest 和 SHA256；不创建完整数据库快照。
3. 新建生产候选数据库，恢复业务数据，连续执行两次 Node schema 入口和业务对账，再以独立端口、launchd label 与 Redis namespace 启动 temporary。
4. temporary 完成与本地同级的进程、请求、慢 SSE、管理面、数据库、Redis、队列和 worker 故障门禁；失败只前向修复，不切流。
5. 进入最终写冻结：拒绝管理写，停止旧业务 writer，fence 并排空旧 Gateway / Redis queue，生成最终业务 dump。
6. 用最终业务 dump 重新构建候选数据库，重新运行 schema、逐行对账和 temporary 稳定门禁；在此之前 Nginx 不得切换。
7. 原子切换 Nginx 到新 Gateway 池，旧槽只用于已进入请求和长连接排空，不再接收新流量。确认旧流排空后停止旧槽并删除不保留的数据域。
8. 切流后若发现问题，停止继续放量或进入维护态，完成前向修复并通过新的 temporary 全门禁后再次切换；不切回旧 release 或旧整库。

## 阻断条件

- release commit、archive SHA256、包内 `RELEASE_SOURCE_COMMIT` 或运维入口不一致。
- `juhe_business` 任一保留表、列、主键、行值、默认资源或凭据可用性对账失败。
- 业务 dump、业务 schema SQL、manifest 或 SHA256 验证失败。
- 候选数据库不是新建隔离目标，或非业务 schema 混入未批准历史数据。
- Redis queue 未排空，或 worker / DB service 数量、角色、健康身份不符合目标拓扑。
- temporary 任一健康、管理接口、请求、慢流、队列、数据库、worker 自愈或前向修复复验失败。
