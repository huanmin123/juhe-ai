# 客户端画像与混合路由设计

> 状态：目标设计，待产品复核和实现。
> 创建时间：2026-06-27。
> 本文用于重新收敛“客户端兼容、账号模型映射、跨供应商模型映射和协议桥接”的产品边界。当前代码仍以既有账号模型映射实现为准；后续实施时按本文调整，不做旧结构运行时兼容。

## 1. 背景

当前账号表单把几类不同职责放在同一处：

- 账号真实上游是什么供应商、什么协议。
- 下游客户端是 Codex、OpenAI SDK、Claude Code 还是 Gemini CLI。
- 模型名是否只是同供应商别名。
- 请求是否需要跨供应商或跨协议桥接。
- 上游响应是否需要按特定客户端形态重新渲染。

这会造成典型误解：用户创建 GPT 账号时还能在模型映射里选择 Anthropic / Gemini 模型，容易以为 GPT 供应商本身可以直接变成任意上游；`客户端兼容` 又和模型映射同时出现，用户不清楚它到底是下游工具体验、上游协议要求，还是协议转换开关。

目标是把这些概念拆开：

- 普通账号只描述真实上游账号。
- 普通账号模型映射只做当前供应商内模型别名。
- 下游客户端画像独立管理，不再作为账号普通字段。
- 跨供应商 / 跨协议能力统一进入“混合路由”。
- 协议转换只能由混合路由显式触发，并受协议桥接矩阵约束。

## 2. 核心结论

1. 供应商账号不再承担跨供应商映射。GPT 账号只能选择 GPT / OpenAI 官方目录内模型；Anthropic 账号只能选择 Anthropic 目录；DeepSeek、GLM、Gemini 账号同理。
2. `OpenAI-compatible` 只表示 OpenAI v1 兼容协议上游，不能包含 Anthropic Messages、Claude Code 原生、Gemini native 等非 OpenAI 协议入口。
3. 账号表单不再展示泛化的“客户端兼容”下拉。账号只展示“上游接入契约”和真实 endpoint modes。
4. 下游客户端画像改为 API Key / 路由规则层的高级策略，默认 `auto` 自动识别。
5. 跨供应商、跨协议和“客户端发 A 模型、实际上游用 B 模型”的能力进入混合路由规则。
6. 混合路由不是一个真实供应商，不保存凭据，不持有账号池；它是调度规则层，引用 API Key 已授权的目标分组或账号。
7. 直连和桥接分开：直连只允许同协议或上游原生兼容；桥接必须匹配协议转换矩阵和 adapter。

## 3. 名词定义

| 名词 | 含义 |
| --- | --- |
| 供应商 | 账号池、模型目录、价格目录和供应商差异归属，例如 `gpt`、`anthropic`、`deepseek`、`glm`、`gemini`、`openai`。 |
| 供应商协议档案 | 供应商与协议版本的绑定，例如 GPT OpenAI v1、DeepSeek OpenAI v1、DeepSeek Anthropic v1、Gemini native v1beta。 |
| 上游接入契约 | 当前账号真实要求的上游请求形态，由供应商协议档案和账号类型决定，例如 OpenAI Chat、OpenAI Responses、Anthropic Messages、Gemini GenerateContent、GPT OAuth Codex Responses。 |
| 下游客户端画像 | 调用本系统的客户端工具画像，例如 `auto`、`openai_compatible`、`codex_responses`、`claude_code`、`gemini_cli`。它只影响本地入站归一化、错误形态、SSE 细节和客户端体验。 |
| 账号模型别名 | 普通账号内的同供应商模型名映射，只解决当前供应商目录内模型别名或部署名差异。 |
| 混合路由 | 独立路由规则：按下游协议、模型和客户端画像选择目标分组 / 账号、上游协议和上游模型。 |
| 直连规则 | 混合路由的一种执行模式：不做协议转换，只替换认证、baseURL、必要 header 和模型名。 |
| 桥接规则 | 混合路由的一种执行模式：下游协议和上游协议不一致，必须通过共享 adapter 转换请求和响应。 |

## 4. 普通账号边界

普通账号表单只回答一个问题：

> 这个账号真实能怎么调用上游？

账号表单保留：

- 供应商。
- 接入类型 / 上游接入契约。
- Base URL。
- 凭据。
- 代理。
- 真实 endpoint modes。
- 支持模型。
- 账号模型别名。
- 错误处理、响应检查、并发、时间计划等运维策略。

账号表单不再直接承接：

- 跨供应商模型映射。
- 跨协议模型映射。
- 下游客户端画像选择。
- “把非 Codex 客户端伪装成 Codex 上游”的隐式转换。

### 4.1 账号模型别名

账号模型别名只在当前供应商 / 当前协议档案内生效。

示例：

- GPT 账号：`gpt-5-mini-alias -> gpt-5-mini`。
- DeepSeek 账号：`deepseek-chat -> deepseek-v4-flash`。
- Anthropic 账号：`claude-sonnet -> claude-sonnet-4-5`。
- Gemini native 账号：`gemini-pro -> gemini-2.5-pro`。

不允许：

- GPT 账号里配置 `gpt-5-mini -> claude-sonnet`。
- Anthropic 账号里配置 `claude-sonnet -> gpt-5-mini`。
- Gemini native 账号里配置 `gemini-pro -> deepseek-v4-flash`。

如果确实需要这些跨供应商关系，进入混合路由。

### 4.2 OpenAI-compatible 边界

`openai` 通用兼容供应商只用于“上游暴露 OpenAI v1 兼容接口，但本项目尚未做深度供应商适配”的场景。

允许进入 OpenAI-compatible 语义的上游：

- 通用 OpenAI v1 Chat / Responses 兼容服务。
- DeepSeek OpenAI-compatible。
- GLM OpenAI Chat 档案。
- Gemini OpenAI Chat compatibility 档案。
- 其他只暴露 OpenAI v1 的第三方聚合服务。

不允许混入 OpenAI-compatible 的上游：

- Anthropic Messages。
- DeepSeek / GLM 的 Anthropic-compatible Messages 档案。
- Gemini native GenerateContent。
- Claude Code 原生客户端画像。
- Gemini CLI 原生请求。

如果一个供应商同时提供 OpenAI-compatible 和 Anthropic-compatible 两套入口，必须拆成不同 `provider_protocol_profile_id`，不能在同一个账号或同一个分组里混用。

## 5. 下游客户端画像

下游客户端画像描述“谁在调用本系统”，不是“上游账号应该用什么协议”。

建议支持：

| 画像 | 来源 | 作用 |
| --- | --- | --- |
| `auto` | 默认值 | 从路径、header、请求体和已知客户端特征自动识别。 |
| `openai_compatible` | API Key / 路由规则可显式指定 | 按普通 OpenAI-compatible SDK 处理错误、JSON 和 SSE。 |
| `codex_responses` | API Key / 路由规则可显式指定，也可自动识别 | 处理 Codex Responses 的 SSE、上下文恢复、compact、工具兼容和客户端重试语义。 |
| `claude_code` | API Key / 路由规则可显式指定，也可自动识别 | 处理 Claude Code 下游画像，不改变 Anthropic API Key 上游认证。 |
| `gemini_cli` | API Key / 路由规则可显式指定，也可自动识别 | 处理 Gemini native 下游请求和错误输出体验。 |

存放位置：

- API Key 高级设置：默认客户端画像，默认 `auto`。
- 混合路由规则：可选匹配条件，例如只匹配 `codex_responses`。
- 请求级显式 header：仅作为本地入站识别信号，不透传上游。

不放在普通账号表单里。

## 6. 上游要求 Codex 来源的场景

有些上游并不是“普通 OpenAI Chat”或“普通 Responses”，而是要求 Codex 形态、Codex 特定 header、Responses 状态链或特殊 body。这个需求不能用“下游客户端画像”直接解决。

规则：

1. 上游需要什么请求形态，由账号的上游接入契约声明。
2. 下游实际发来的协议，由请求路径和 body 决定。
3. 如果下游协议和上游接入契约不同，必须存在显式桥接 adapter。
4. 没有 adapter 时，本地拒绝或跳过该账号，不能因为账号“需要 Codex”就静默改写 Chat 请求。

例如用户请求是 Chat，但目标上游要求 Codex Responses：

- 如果没有 `chat_completions -> codex_responses` adapter，则混合路由规则不能保存或不能运行。
- 前端提示：当前上游要求 Codex Responses，请让客户端使用 `/v1/responses`，或等待实现 Chat 到 Codex Responses 桥接。
- 如果未来实现该 adapter，也必须配置在混合路由中，不能作为账号字段隐式启用。

如果上游只是同协议请求里要求增加某些 Codex 风格 header 或 query，这属于上游接入契约的 request decorator，仍由供应商 driver 明确声明和构造；它不等于把任意下游客户端画像改成 Codex。

## 7. 混合路由

混合路由回答：

> 下游用什么协议和模型进来，最终应该打到哪个已授权上游账号 / 分组、什么协议和模型？

它是虚拟调度层，不是供应商：

- 不保存 API Key、OAuth token 或上游凭据。
- 不直接拥有模型目录和价格目录。
- 不绕过 API Key 已绑定分组。
- 不把请求路由到当前 API Key 未授权的账号池。

### 7.1 规则字段

建议规则结构：

| 字段 | 说明 |
| --- | --- |
| `id` | 规则 ID。 |
| `name` | 中文名称。 |
| `enabled` | 是否启用。 |
| `priority` | 同时命中时的优先级，数值越小越优先。 |
| `scope` | 作用域，可为系统默认、某 API Key、某系统账户或某分组策略。第一版建议从 API Key 级开始。 |
| `source_client_profile` | 可选，下游客户端画像；为空表示不限。 |
| `source_endpoint_family` | 下游协议族，如 `chat_completions`、`responses`、`messages`、`generate_content`、`stream_generate_content`。 |
| `source_model` | 下游请求模型，必须来自对应协议的客户端可见模型池。 |
| `target_group_id` | 目标分组；必须在当前 API Key active 绑定内。 |
| `target_account_id` | 可选，强制目标账号；为空表示按目标分组调度。 |
| `target_provider_protocol_profile_id` | 目标供应商协议档案，用于校验分组和 adapter。 |
| `upstream_endpoint_family` | 上游协议族。 |
| `upstream_model` | 上游实际模型，必须来自目标供应商 / 目标协议档案模型目录，或目标账号支持模型。 |
| `adapter_mode` | `direct` 或 `bridge`。 |
| `notes` | 维护备注。 |

### 7.2 直连规则

直连规则只允许同协议或目标上游原生兼容的请求。

示例：

- `chat_completions + glm-alias -> GLM OpenAI Chat + chat_completions + glm-5.2`。
- `messages + claude-alias -> Anthropic Messages + messages + claude-sonnet-4-5`。
- `generate_content + gemini-alias -> Gemini native + generate_content + gemini-2.5-pro`。

直连仍会经过：

- 本地认证。
- 授权额度。
- 候选账号筛选。
- 代理。
- 响应语义检查。
- usage、审计、错误分类和账号副作用。

直连不做协议结构转换。

### 7.3 桥接规则

桥接规则用于协议不一致的场景，必须匹配协议桥接矩阵。

允许方向以 [协议桥接框架设计](协议桥接框架设计.md) 为准。当前目标设计继续沿用白名单原则：

| 下游 | 上游 | 处理 |
| --- | --- | --- |
| `responses` | `chat_completions` | 允许，Responses 到 Chat bridge。 |
| `chat_completions` / `responses` | `messages` | 允许，OpenAI 到 Anthropic Messages bridge。 |
| `messages` | `chat_completions` | 允许，Anthropic Messages 到 Chat bridge。 |
| `generate_content` / `stream_generate_content` | `chat_completions` | 允许，Gemini native 到 Chat bridge。 |
| `generate_content` / `stream_generate_content` | `messages` | 允许，Gemini native 到 Anthropic Messages bridge。 |
| `chat_completions` / `responses` / `messages` | `generate_content` | 允许，OpenAI / Anthropic 到 Gemini native bridge。 |
| 非 `responses` 来源 | `responses` | 禁止，不合成 Responses 状态机。 |
| 未列出的方向 | 禁止，不能靠供应商或客户端画像猜测。 |

示例：

- `responses + gpt-5-mini -> Anthropic 分组 + messages + claude-sonnet-4-5`。
- `chat_completions + gpt-4o -> Gemini native 分组 + generate_content + gemini-2.5-pro`。
- `generate_content + gemini-pro -> GPT 分组 + chat_completions + gpt-5-mini`。

## 8. 路由优先级

请求进入网关后按以下顺序处理：

1. 认证 API Key，得到当前系统账户和 active 分组绑定。
2. 识别请求协议族、请求模型、流式形态和下游客户端画像。
3. 查找当前 API Key 作用域内启用的混合路由规则。
4. 规则必须同时匹配 `source_endpoint_family`、`source_model` 和可选 `source_client_profile`。
5. 命中混合路由后，校验目标分组仍在当前 API Key active 绑定内。
6. 校验目标分组的 `provider_protocol_profile_id` 与规则目标一致。
7. 校验 `upstream_model` 属于目标供应商 / 目标账号可用模型。
8. 如果是 `direct`，只允许同协议或目标原生兼容请求。
9. 如果是 `bridge`，校验协议桥接矩阵、目标 endpoint modes 和 adapter 能力。
10. 进入目标分组内账号调度。
11. 如果没有混合路由命中，回到普通模型目录路由：按请求模型唯一定位供应商协议档案，再在当前 API Key 绑定分组内调度。

混合路由优先于普通模型目录路由。原因是 `gpt-*` 这类模型名默认可能路由到 GPT 官方分组，但用户可能明确希望某个 API Key 把该模型路由到 Anthropic、DeepSeek 或 Gemini。没有显式混合路由时，系统仍按普通模型目录规则，不猜测跨供应商目标。

## 9. 模型池规则

### 9.1 普通供应商账号

普通账号支持模型和账号模型别名只使用当前供应商模型目录。

| 账号供应商 / 档案 | 可选模型池 |
| --- | --- |
| GPT / OpenAI 官方 | GPT / OpenAI 官方模型目录。 |
| Anthropic 官方 | Anthropic 官方模型目录。 |
| DeepSeek OpenAI Chat | DeepSeek 模型目录。 |
| DeepSeek Anthropic Messages | DeepSeek Anthropic-compatible 模型目录。 |
| GLM OpenAI Chat | GLM OpenAI Chat 模型目录。 |
| GLM Anthropic Messages | GLM Anthropic-compatible 模型目录。 |
| Gemini native | Gemini native 模型目录。 |
| Gemini OpenAI Chat | Gemini OpenAI Chat 模型目录。 |

### 9.2 通用 OpenAI-compatible

通用 `openai` 兼容供应商使用 OpenAI 协议模型池：

- GPT / OpenAI v1 模型。
- DeepSeek OpenAI-compatible 模型。
- GLM OpenAI Chat 模型。
- Gemini OpenAI Chat 模型。
- 用户在通用 `openai` 兼容供应商下维护的自定义模型。

该池不包含：

- Anthropic Messages 模型。
- DeepSeek / GLM Anthropic-compatible 模型。
- Gemini native 模型。
- Claude Code / Gemini CLI 仅客户端画像模型。

### 9.3 混合路由

混合路由的左侧模型池按下游协议族选择：

- OpenAI Chat / Responses 来源：OpenAI 协议客户端模型池。
- Anthropic Messages 来源：Anthropic 协议客户端模型池。
- Gemini native 来源：Gemini native 客户端模型池。

右侧模型池按目标供应商协议档案选择。跨供应商只在混合路由规则里发生。

## 10. 页面设计

### 10.1 账号表单

账号表单建议分区：

- 上游连接：供应商、接入类型、Base URL、凭据、代理。
- 上游真实能力：endpoint modes，只描述真实上游能力。
- 模型能力：支持模型、账号模型别名。
- 调度策略：优先级、并发、时间计划、错误恢复。
- 响应策略：响应语义检查、审计、日志和使用记录。

页面不显示“客户端兼容”下拉。可显示只读徽标：

- 上游接入契约：OpenAI Chat、OpenAI Responses、Anthropic Messages、Gemini native、GPT OAuth Codex Responses。
- 可被哪些混合路由目标引用。

### 10.2 API Key 设置

API Key 高级设置可提供：

- 默认客户端画像：`auto`、`openai_compatible`、`codex_responses`、`claude_code`、`gemini_cli`。
- 是否允许混合路由。
- 绑定分组列表。
- 该 Key 下的混合路由规则入口。

默认客户端画像只影响下游体验，不改变账号可调度范围。

### 10.3 混合路由页面

混合路由页面用于高级用户，建议字段：

- 规则名称。
- 匹配条件：客户端画像、下游协议、下游模型。
- 目标：分组、可选账号、上游协议、上游模型。
- 模式：直连 / 桥接。
- 能力检查结果：可保存、需要 endpoint mode、不可保真 guidance、禁止方向。
- 优先级和启用状态。
- 测试按钮：使用规则构造最小请求，验证目标账号是否可用。

页面文案必须明确：

- 混合路由不会扩大 API Key 授权范围。
- 桥接不是原生能力，部分工具 / 状态 / 响应字段可能走 guidance-first。
- 目标上游模型决定成本和 usage 口径。

## 11. 数据契约建议

### 11.1 账号

账号保留或派生：

- `provider_code`
- `provider_protocol_profile_id`
- `connection_type`
- `credentials`
- `supported_endpoint_modes`
- `supported_models`
- `model_aliases`

不再使用账号级 `client_compatibility` 作为普通配置字段。实现时可直接移除或替换，不做运行时旧字段兼容。

### 11.2 账号模型别名

建议替代当前跨协议账号模型映射语义：

```ts
type AccountModelAlias = {
  accountId: string
  sourceModel: string
  upstreamModel: string
  endpointFamily: 'chat_completions' | 'responses' | 'messages' | 'generate_content'
  enabled: boolean
}
```

约束：

- `sourceModel` 和 `upstreamModel` 必须在当前供应商 / 当前协议档案模型池内。
- 不允许跨供应商。
- 不允许跨协议族；需要跨协议进入混合路由。
- 如果 `sourceModel === upstreamModel`，不保存别名。

### 11.3 混合路由规则

建议新增独立表或配置对象，不复用账号模型别名：

```ts
type HybridRouteRule = {
  id: string
  name: string
  enabled: boolean
  priority: number
  scopeType: 'api_key' | 'system_account'
  scopeId: string
  sourceClientProfile?: 'openai_compatible' | 'codex_responses' | 'claude_code' | 'gemini_cli'
  sourceEndpointFamily: 'chat_completions' | 'responses' | 'messages' | 'generate_content' | 'stream_generate_content'
  sourceModel: string
  targetGroupId: string
  targetAccountId?: string
  targetProviderProtocolProfileId: string
  upstreamEndpointFamily: 'chat_completions' | 'responses' | 'messages' | 'generate_content'
  upstreamModel: string
  adapterMode: 'direct' | 'bridge'
}
```

第一版建议只做 API Key 作用域，避免系统默认路由影响所有调用方。

## 12. 导入导出

账号导入导出：

- 只包含账号真实接入、真实 endpoint modes、支持模型和账号模型别名。
- 不包含跨供应商 / 跨协议混合路由。
- 不包含账号级客户端兼容。

混合路由导入导出：

- 独立导入。
- 必须校验目标分组存在且当前系统账户有权引用。
- 必须校验目标模型、目标协议和 adapter 矩阵。
- 导入失败必须指向具体规则。

## 13. 使用记录与审计

使用记录需要区分：

- 下游请求模型。
- 下游协议族。
- 下游客户端画像。
- 是否命中混合路由。
- 混合路由规则 ID。
- 目标供应商 / 协议档案。
- 上游协议族。
- 上游模型。
- 是否发生协议桥接。
- 计价模型。

成本按上游模型或其 `pricingModel` 计算。统计模型维度默认按下游请求模型聚合，详情页展示上游模型和混合路由命中信息。

## 14. 非目标

- 不通过账号字段隐式启用跨协议转换。
- 不把 `OpenAI-compatible` 扩展成任意协议兼容。
- 不在 GPT / Anthropic / DeepSeek / GLM / Gemini 普通账号里选择其他供应商模型。
- 不用客户端画像猜测上游目标。
- 不让混合路由绕过 API Key 分组授权。
- 不做 `chat_completions -> responses`、`messages -> responses` 或 Gemini native 到 Responses 的合成桥接。
- 不把直连规则理解为跳过审计、usage、错误分类或响应语义检查。
- 不做运行时旧字段兼容；需要实施时由维护者按当前 schema 做离线数据处理。

## 15. 落地顺序

1. 产品确认本文边界，尤其“账号模型别名”和“混合路由”拆分。
2. 新增混合路由计划文档，明确分阶段实施范围。
3. 调整模型目录服务：普通账号只返回当前供应商模型池，通用 OpenAI-compatible 只返回 OpenAI 协议池。
4. 调整账号表单：移除普通客户端兼容下拉，新增上游接入契约只读展示。
5. 新增账号模型别名数据结构和校验，替换当前账号级跨协议模型映射语义。
6. 新增混合路由数据结构、接口、页面和导入导出。
7. 网关请求链路先匹配混合路由，再回退普通模型目录路由。
8. 将现有跨协议 adapter 绑定到混合路由规则。
9. 同步使用记录、审计、Mockdata 和测试文档。

## 16. 验证清单

- GPT 账号表单模型别名只能选择 GPT / OpenAI 模型。
- Anthropic 账号表单模型别名只能选择 Anthropic 模型。
- DeepSeek OpenAI Chat 账号不能在账号别名里选择 GPT 或 Claude 模型。
- 通用 OpenAI-compatible 账号只能选择 OpenAI 协议模型池，不能选择 Anthropic Messages 或 Gemini native。
- API Key 默认客户端画像为 `auto`，不影响普通账号可用性。
- `responses + gpt-* -> Anthropic messages + claude-*` 只能通过混合路由保存。
- API Key 未绑定目标 Anthropic 分组时，上述混合路由不能运行。
- `chat_completions -> responses` 混合路由保存失败。
- 用户请求 Chat、目标上游要求 Codex Responses 且无 adapter 时，规则保存失败或运行前返回明确错误。
- 混合路由命中后，使用记录展示下游模型、上游模型、规则 ID 和桥接标记。
- 直连规则仍写 usage、审计、错误分类和账号命中。
