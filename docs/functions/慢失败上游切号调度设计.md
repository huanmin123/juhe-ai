# 慢失败上游切号调度设计（W17 观察项②设计预案）

> 状态：**设计预案，待维护者裁决，未授权实施**。来源：[待办与阻塞事项](../待办与阻塞事项.md) W17（2026-10-22 生产排查）。本文只提供裁决材料与实施蓝图，不含任何代码改动。
>
> 取证基线说明：当前工作区含大量未提交改动。本文区分两个基线——**生产基线**（HEAD 已发布形态，生产容器实际运行版本对应哪个 commit 未验证，按 W17 生产行为与 HEAD 代码一致取证）与**工作区基线**（未提交、未发布）。行号以工作区文件为准；与 W17 条目引用的 HEAD 行号差异处单独标注。

## 1. 背景与目标

2026-10-22 生产事件：上游渠道 `napi.kid1412.qzz.io` 对 `deepseek-v4.1-flash` 流式慢失败（Cloudflare 504 页面 ~115s、TLS bad record MAC 18~110s、网关 120s 首字超时、偶发 429）。网关按生产基线行为先把同账户重试预算烧完：3 次尝试耗时 4~6 分钟全部落在同一账户，而客户端约 5 分钟即断开（当晚 25 条 `downstream_connection_closed`），切号实际来不及发生。切号机制本身正常：trace `91179cb8` attempt1-3 全在 kid1412-ds（504×115.9s / TLS×66s / 下游关闭×117s），同批唯一到 attempt4 的 trace 切到 workbuddy-ds 即成功进入流式。

目标：给出「慢失败上游不再拖死切号」的用户可裁决方案，写清各方案与既有调度机制的交互、验收标准、验证方式与回滚形态。

成功标准（裁决实施后）：上游单账户慢失败（单次尝试耗时达到时间阈值）时，请求在有限时间内切换到下一优先级候选或给出确定性终态，同账户不再消耗多次慢尝试；正常账户与快失败行为不受扰动。

## 2. 非目标

- 不改账户健康判定、探针三态语义与自动状态变更边界（W17 当晚账户 active/可调度/无冷却、探针 78/91 通过，健康面无缺陷）。
- 不改路由拓扑、分组会话亲和、速度优先 `latency_degraded` 软慢样本与激活/恢复语义。
- 不引入新配置面：参数只以既有 DB `system_settings` 键（或其取值语义扩展）形式存在，不新增 feature flag（功能不设开关）。
- 不处理 W17 下一步①运营动作（调低 kid1412-ds 优先级或暂停调度，控制台即改即生效）。
- 不处理 W11（同渠道 `deepseek-v4.1-flash` 非流式空 choices，外部上游缺陷）。

## 3. 现状机制取证

### 3.1 生产基线：同账户重试预算先行，无时间维度

- 预算上限：`maxSameAccountRetries = min(2, settings.TemporaryUnschedulableRetryAttempts)`（`backend-go/projects/gateway/internal/gatewaydispatch/upstreamdispatch.go:661`；HEAD 同代码在 `:654`，即 W17 条目引用处，行号漂移来自未提交批）。生产 `temporaryUnschedulableRetryAttempts=2`（种子默认，`backend-go/projects/maintenance/internal/schema/pg_schema.go:758`）。
- 消费点两处，均位于 `internal/gatewaydispatch/attemptoutcomes.go`：
  - **响应失败臂**（重试原因 `upstream_http_response`）：非 2xx 且状态码属瞬态集合 `408/425/429/5xx`（`upstreamdispatch.go:1722-1725` `isTransientSameAccountHttpStatus`）且非显式策略失败时预留同账户重试（工作区 `:358-383`；HEAD 同点无耗时门槛）。W17 的 504 Cloudflare 页面走此臂。
  - **传输失败臂**（重试原因 `upstream_transport_failure`）：`provenStartedTransportFailure`（已连上上游的传输失败，含 TLS bad record MAC、lane hard timeout，按[网关异常重试与兜底策略](网关异常重试与兜底策略.md)「`textFirstResponseTimeoutSeconds` 等 lane hard timeout 按 transport failure 处理」口径）时预留（工作区 `:616-640`；HEAD 同点无耗时门槛）。W17 的 TLS ×66s、120s 首字超时走此臂。
- 重试间隔与账户锁：间隔 `temporaryUnschedulableRetryIntervalSeconds`（默认 3s，`pg_schema.go:757`）经账户锁 retry lease 排程（`upstreamdispatch.go:662-709`）；传输失败同账户重试还向锁面记失败证据（`:743-747`）。
- 请求级既有守卫（生产已生效）：预留前检查墙钟剩余窗——剩余减 2s 渲染保留不足一个配置间隔即放弃重试，审计 `same_account_retry_exhausted` / `gateway_request_wall_budget_exhausted`（`upstreamdispatch.go:713-721`；HEAD `:706-711`）。该守卫只防「预算不够再等一轮间隔」，不约束单次尝试耗时：W17 场景每次 60~120s 的尝试都能起跳，守卫不触发。
- 时间账（W17 复盘）：2 次重试 × 单次 60~120s + 2×3s 间隔 ≈ 4~6 分钟全部落在同一账户；请求墙钟预算默认 270s（`internal/gatewayrouting/routecoordination.go:16`），客户端耐心更短——切号前请求已被下游终止。

### 3.2 工作区基线：三刀修复已实现、未提交、未发布

工作区已含设计定稿（2026-10-23）与实现：[调度慢失败直切与来源避让记账及墙钟收尾修复设计](调度慢失败直切与来源避让记账及墙钟收尾修复设计.md)（实施依据 [PLAN-20261022T171949672Z](../plans/计划-20261022T171949672Z-调用方维度真实流量质量反馈与慢失败快速换号.md) v5）。代码在工作区未提交（`git status`：`attemptoutcomes.go`、`upstreamdispatch.go`、`enginehelpers.go`、`dispatchsingle.go` 等已修改，设计文档未跟踪）。与本文相关的三刀：

- **A 同账户重试时间闸**：两个预留点增加耗时门槛——单次失败耗时 ≥ `sameAccountRetryFastFailMaxMs`（默认 10000ms，范围 0~60000）即不预留同账户重试、直接轮换下一候选，输出审计 `same_account_retry_skipped_slow_failure`（含 elapsedMs/thresholdMs/retryReason）（`attemptoutcomes.go:366`、`:620`）；< 阈值行为不变；预算上限 `min(2, temporaryUnschedulableRetryAttempts)` 不动。
- **C1 尝试启动门槛**：剩余墙钟扣 2s 渲染保留后不足 `gatewayAttemptStartMinWindowMs`（默认 30000ms）不启动任何新尝试，返回既有 503 `gateway_request_wall_budget_exhausted`（`internal/gatewaydispatch/enginehelpers.go:341-372`、`internal/gatewaydispatch/dispatchsingle.go:551-554`）。
- **C2 尝试截止裁剪**：普通路径单尝试首字截止按墙钟预提交线裁剪，晚启动尝试不再越过墙钟（`dispatchsingle.go:626-636`；速度优先路径同型裁剪既有，`internal/gatewayrouting/firstbytedeadline.go:66-90`）。
- **B 来源避让记账**（与切号互补，不在本文裁决面）：上游归因失败记入 PendingFailures、结算确认后同层沉底（`attemptoutcomes.go:56-77` 记账回调接线）。

对 W17 场景的效果：attempt1 504×115.9s ≥ 10s → 不预留同账户重试，直接切下一优先级账户；同账户慢失败停留从 4~6 分钟收敛为「1 次尝试 + 1 次切号」。**该修复发布前，生产仍在 3.1 行为下运行。** 本任务复跑其差分测试 5 例（慢响应失败/慢传输失败直切、快失败保留、启动门槛、截止裁剪）全绿（`internal/gatewaydispatch/dispatchfastfail_test.go`；工作区验证，2026-10-23）。

### 3.3 chain 层既有切号与兜底（生产已生效）

- **首字截止切号**：路由配置首字截止到期产生 `NormalRouteFirstByteCutoverError`（`attemptoutcomes.go:486-525`，类型定义 `internal/gatewaydispatch/errors.go:76-90`），对账户电路、Key 运行态保持中性；链面收窄到保留目标重派（`cmd/juhe-ai-gateway/chain_v1_loop.go:879-885` `settleSpeedFirstCutoverError`）。
- **总时间兜底截止切号**：`NormalRouteTotalTimeTimeoutError` 由传输层总时间 timer 到点决策确认后产生（`internal/gatewaydispatch/gatewayupstream/transport.go:161-176`），沿引擎错误通路原样上抛，链面凭决策载荷槽构造 cutover 消费（`chain_v1_loop.go:866-876` `settleTotalTimeCutoverError`）；与首字维度共享切号链与上限。
- **墙钟预算兜底**：`GatewayRequestWallBudgetExhaustedError` → 固定 503 `gateway_request_wall_budget_exhausted`（`chain_v1_loop.go:903-942`）。
- **会话亲和交互**：同账户重试钉住原账户候选（`upstreamdispatch.go:572-574`）；传输失败臂与首字截止臂执行 `Affinity.ForgetAsync`（`attemptoutcomes.go:465`、`:501`），切号后账户/组/Key 亲和按最终成功自然写回新账户——切号与亲和语义已解耦，无需新增处理。
- **健康/熔断交互**：响应失败臂 `ReportUnknown`（`attemptoutcomes.go:335-337`）、传输失败臂 `ReportTransportFailure`（`:612-615`）都在同账户重试决策点之前结算——是否重试不影响熔断取证与失败证据记账。

## 4. 方案选项与取舍

对比基线是「发布三刀之后」的残余缺口，而非生产基线——任何方案都不应在三刀未发布的状态上叠加裁决，否则归因不了收益。

### 方案 a：同账户重试按错误类别收紧

内容：5xx/超时/TLS 类对同账户降为 0~1 次重试；429 维持 2 次（瞬态限流语义，短间隔重试常能自愈）。

- 实现面：预留点按失败类别（响应臂 5xx 与 429；传输臂 Timeout 与 Connection，分类已有 `TransportFailureKind`，`attemptoutcomes.go:604-611`）差异化重试预算，需给 `TryReserveSameAccountRetry` 预约接口增加类别入参（`internal/gatewayrouting` 域接口扩展）。
- 与既有机制交互：熔断取证不变（结算先于决策）；429 的 `DeferAutomaticSameAccountKeyRotation` 路径（`attemptoutcomes.go:218-221`）须保持不受收紧影响；速度优先首字截止与总时间兜底两个切号臂不经过该预算，不受影响。
- 收益（三刀发布后）：只剩「<10s 的快 5xx/快传输失败」仍会重试满 2 次，总代价 ≈ 3×秒级 + 2×3s，时延有界且小；收紧主要减少对病号上游的重复敲打，切号时延收益边际。
- 风险/成本：新增「错误类别 × 重试预算」二维行为面，组合与测试面扩大；快 5xx 同账户重试常是正确行为（上游抖动自愈），收紧可能降低单账户抖动自愈率；与最小化改动相悖。

### 方案 b：同账户重试加时间预算上限

- **b1 单次尝试时间闸（已实现，即三刀 A）**：单次失败耗时 ≥ `sameAccountRetryFastFailMaxMs` 即直切。同账户停留上界：慢失败场景 = 1×阈值；快失败场景 = 3×阈值 + 2×间隔 ≈ 36s。
- **b2 累计时间预算**：同账户累计耗时超过首字超时的 N 倍即切号，时间维度取代次数维度。
- 与既有机制交互：b1 与次数预算正交叠加（先时间闸、后次数预算），与既有墙钟剩余窗守卫（`upstreamdispatch.go:713-721`）、三刀 C1/C2 构成四层递进；b2 需在预留决策引入累计耗时 plumbing，而其上界已被 b1+次数预算间接有界化（≤36s），独立参数收益有限，且引入第二时间维度的口径与归因成本。
- 配置兼容：`sameAccountRetryFastFailMaxMs` 是既有瞬态重试语义的时间维度扩展（同错误处理域的取值语义，0=全部直切与 `temporaryUnschedulableRetryAttempts=0` 关闭能力同为该键家族既有风格），非开关。

### 方案 c：请求级全局切号 deadline

内容：请求总耗超过 X 即不再同账户重试，直接下一候选。

- 与既有机制交互：该语义已被三层既有机制覆盖——墙钟预算 270s 总兜底（`routecoordination.go:16`）、同账户重试预留前的剩余窗检查（`upstreamdispatch.go:713-721`）、三刀 C1 拒启 + C2 截止裁剪（尝试不越过墙钟）。独立 X 与墙钟预算构成双总时参数：X > 270s 永不先触发；X < 270s 与 C1 门槛竞争裁决，语义重叠、漂移风险高。
- 收益：不存在三刀覆盖不到的残余场景（尝试能否启动、单尝试多长都已被约束）。
- 风险/成本：新增配置键 + 双截止源归因歧义；违背「优先复用既有机制」。

### 交互总表

| 既有机制 | 方案 a | 方案 b1（推荐） | 方案 c |
| --- | --- | --- | --- |
| 速度优先首字截止切号 | 不相交 | 不相交（不同截止源） | 共享切号链，需消歧 |
| 总时间兜底截止切号 | 不相交 | 不相交 | 与墙钟语义重叠 |

| 会话亲和 | 中性 | 中性（失败臂既有 forget） | 中性 |
| 账户健康/熔断 | 中性（结算先于决策） | 中性（同左） | 中性 |
| 配置契约 | 预约接口加类别入参 | 复用已接线新键 | 新增键，双截止源 |

### 推荐

**推荐方案 b，且以已实现的三刀 A（b1 形态）为落地主体：先行发布并按 §6.2 观察口径验证；b2、方案 a、方案 c 不叠加实施。**

理由：

1. W17 根因是「同账户重试只有次数预算、没有时间维度」，b1 正是该维度，且已定稿、已实现、已有差分测试（§3.2）——发布即根治，无新增设计面。
2. b1 发布后，方案 a 的适用面收窄到「快失败重复重试」（时延秒级且有界），方案 c 的适用面为零（墙钟 + C1/C2 已闭合时间账）；两者当前都属「为未证实的残余风险新增机制」，按「保持正常语义」规范不实施。
3. 若发布后观察出现残余缺口（§6.2 口径 5），按 §8 触发条件复议对应方案，届时有生产数据支撑参数取值。

## 6. 验收标准与验证方式

### 6.1 Mock 层（gatewaydispatch 单测，mock 上游）

1. 慢失败直切差分：可配延迟的假上游（响应臂 5xx、传输臂失败各一例，延迟 ≥ 阈值）+ 两个候选账户 → 断言 attempt1 失败后 attempt2 落在第二账户、无同账户重试预留、审计含 `same_account_retry_skipped_slow_failure`（elapsedMs/thresholdMs/retryReason）。
2. 快失败保留：延迟 < 阈值的同型失败 → 同账户重试预算保留（min(2, N)），行为与现状一致。
3. 切号时延上限断言：慢失败 + 两账户候选场景，请求总时长 ≤ attempt1 耗时 + 第二账户尝试截止；同账户停留满足 §4 方案 b1 的上界分支（慢失败 1×阈值 / 快失败 3×阈值 + 2×间隔）。
4. 墙钟边界：剩余窗不足时 `same_account_retry_exhausted`（既有）；剩余 < `gatewayAttemptStartMinWindowMs` 拒启返回 503（三刀 C1 既有用例）。
5. 回归面：`gatewaydispatch` / `gatewayrouting` / `gatewayclientip` 全量 + `cmd` 定向回归（既有锚点清单见[三刀设计 §6](调度慢失败直切与来源避让记账及墙钟收尾修复设计.md)）。

现状：1/2/4/5 的三刀侧用例已存在且本任务复跑全绿（§3.2）；3 作为发布验收项随全量回归确认。

### 6.2 生产观察口径

以 trace 尝试链（audit attempts，同 W17 排查口径）为单位，发布后观察 3~7 天：

1. 同账户尝试序数分布：attempt1 失败后即切下一账户的比例显著上升；「同账户 attempt≥3 且单次 ≥10s」形态应归零。
2. `same_account_retry_skipped_slow_failure` 触发率与 elapsedMs 分布：验证阈值合理性；若触发集中在 10~15s 且对应上游常快速恢复，评估上调阈值。
3. `downstream_connection_closed` × 请求总时长联合分布：W17 形态（总时长 >4 分钟后下游断开）应消失。
4. 跨账户切换成功率对照 W17 基线（当晚 13 个 trace 成功跨账户切换、58 个重试后成功），不回退。
5. 误伤监控：快失败上游（秒级失败）渠道的重试成功率不下降——确认 b1 未吞掉抖动自愈。若此口径恶化，即为复议方案 a（错误类别收紧）的触发条件。

## 7. 迁移与回滚

- 发布形态：gateway 单进程镜像替换（compose recreate 滚动，无停机窗口要求），发布序列含 maintenance `--ensure-schema --seed`——两个新设置键为增量 INSERT；存量库缺行由 `compatibleSystemSettingDefaults` 兜底、行为一致；无 schema 变更。
- 回滚：回退 gateway 镜像即可。设置行是普通数据行，旧二进制不读取新键、无兼容问题；无状态残留（来源避让 entry TTL ≤10 分钟自然过期，与三刀设计 §8 同口径）。
- 与运营动作解耦：发布前可用控制台即时调整渠道优先级/暂停调度（W17 下一步①）缓解，与本设计互不依赖。
