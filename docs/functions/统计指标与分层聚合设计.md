# 统计指标与分层聚合设计

## 文档目标

本文用于统一当前统计实现口径和后续扩展边界。重点回答三件事：

- 当前系统有哪些统计维度，分别服务哪些页面、接口和权限口径。
- 当前和近期需要沉淀哪些指标，哪些属于消耗，哪些属于性能。
- 分钟、小时、日、周、月、累计聚合表如何承载统计，避免页面、额度判断和监控接口实时汇总明细表。

本文是统计口径与读取边界文档，不替代具体接口字段、页面交互或计划验收记录；新增统计维度仍应先在这里确认事实源、聚合层级、保留期和请求路径读取方式。

## 核心结论

- `usage_records` 仍是事实明细源，用于短期排障、审计关联和统计缓存重建；页面统计、列表统计、额度判断和监控趋势不能实时 `GROUP BY usage_records`。
- 业务统计统一走持久化聚合表，不使用内存缓存承载关键统计。服务重启后依赖 SQLite 聚合表和 `stats_job_state` 游标继续推进。
- 聚合维度统一使用 `system_account_id + scope_type + scope_id` 表达，账户、分组、API Key、授权、模型、接口等维度都归入同一套指标口径。
- OpenAI OAuth / API Key 账户类型只影响上游能力、转发方式和账号运行态展示；默认统计、额度、会话亲和和缓存连续性不按账户类型切分。同一个本地 API Key 路由下命中 OAuth 账号或 API Key 账号时，`api_key` 与 `group` 统计必须合并到同一条本地口径。
- 指标先分为两大类：消耗指标和性能指标。消耗指标用于用量、费用、额度和排序；性能指标用于 AI 性能监控、账号质量和慢请求趋势。
- 分层聚合表确定形成 `minute / hourly / daily / weekly / monthly / totals` 六层；页面固定窗口、TopN、n 小时额度和范围摘要还需要单独快照表承接，避免接口把多行缓存再次相加。
- IP 维度因高基数单独使用 `client_ip_stats_daily` 和 `client_ip_usage_range_windows`，不接入通用六层 `usage_stats_*` scope，避免写放大和索引膨胀；IP 管理只展示 IP 行维度列表，不维护 IP 累计总表或范围总聚合表。
- 任意日期范围如果要展示范围总量，必须先由 worker 写入范围快照；趋势图需要每日点时仍可读取日桶，因为图本身需要逐日数据，但摘要不能由请求路径把日桶相加得到。
- 当前最重要的设计边界是：所有统计表只做增量累加、增量扣减或 worker 内刷新快照，不能在页面请求时回扫明细，也不能在请求路径临时聚合统计缓存。
- 统计体系以长期干净为优先级。运行时只按当前 schema 和当前统计口径工作；既有数据如需保留，由用户停机后离线整理，否则直接清空统计缓存并从新请求重新累计。
- 当前统计桶已覆盖通用分钟、小时、日、周、月和累计层，并同步覆盖模型、错误和耗时桶；`account_quality_minute_stats` 继续保留为调度专用派生表，不承担通用用量查询。
- 周表统一使用自然周周一作为 `stat_week`，月表统一使用 `YYYY-MM` 作为 `stat_month`。
- 月表默认保留 24 个月，避免当前月、上月、自然月账单、年度追溯和报表被短保留策略卡住。
- 性能指标不只保留平均值，还保留最大值和耗时直方图桶，用于 P95 / P99 / 慢请求分布，避免尾延迟监控重新改统计主链路。

## 当前统计维度

统一维度模型：

```text
system_account_id + scope_type + scope_id
```

`system_account_id` 表示统计归属，不一定等于发起调用的人。比如账户真实总量归属账户所有者；我的用量归属调用方；授权用量归属资源所有者。

| `scope_type` | `scope_id` | 统计归属 | 当前用途 | 说明 |
| --- | --- | --- | --- | --- |
| `system_account` | 系统账户 ID | 调用方系统账户 | 用户统计概览 | 表示某个系统账户自身全部调用消耗 |
| `system_account` + 全局行 | `global` | 全局虚拟统计账户 | 管理员全局概览 | 由后台增量写入，不在接口临时汇总多个用户 |
| `provider` | 供应商编码 | 调用方系统账户 | 供应商维度统计 | 用于按 OpenAI 等供应商查看消耗和性能 |
| `group` | 分组 ID | 分组所有者 | 分组列表、分组总量 | 被授权用户使用分组时，也计入分组所有者的真实分组总量 |
| `caller_account` | AI 账户 ID | 调用方系统账户 | 我的用量 | 表示“我自己对某个账户的调用消耗”，即使账户是别人授权给我的，也只统计我的调用 |
| `account` | AI 账户 ID | 账户行所属系统账户 | AI 性能监控、账户真实总量 | 表示当前账户行的整体使用情况；授权实例账户与归属人原账户互不混入 |
| `account_authorization` | 授权 ID | 账户所有者 | 账户授权明细、授权额度 | 只统计授权关系产生的消耗；所有者自用不进入该维度 |
| `group_authorization` | 授权 ID | 分组所有者 | 分组授权明细、授权额度 | 只统计授权关系产生的消耗；所有者自用不进入该维度 |
| `account_authorization_team` | `账户ID:团队ID` | 账户所有者 | 团队来源账户授权额度 | 只统计团队来源产生的合计消耗，网关额度判断直读 |
| `group_authorization_team` | `分组ID:团队ID` | 分组所有者 | 团队来源分组授权额度 | 只统计团队来源产生的合计消耗，网关额度判断直读 |
| `api_key` | API Key ID | API Key 所有者 / 调用方 | API Key 列表、API Key 额度 | 表示对外访问密钥产生的消耗 |
| `model` | 模型名 | 调用方系统账户 | 模型维度统计 | 当前模型分布主要依赖专用 `usage_model_*` 表，通用 scope 用于模型级额度或筛选 |
| `endpoint` | 网关接口路径 | 调用方系统账户 | 接口维度统计 | 用于区分 `/v1/responses`、`/v1/chat/completions` 等接口消耗 |

需要明确的概念边界：

- `caller_account` 和 `account` 不能混用。前者回答“我用了哪些账户、花了多少”，后者回答“这个 AI 账户整体被用了多少、性能如何”。
- 授权统计必须挂在授权 ID 上，而不是只挂被授权人 ID 上。这样授权回收、归还、恢复、团队来源切换后，历史消耗仍能落在同一授权关系下。
- 分组和账户都存在“真实资源总量”和“授权关系消耗”两种口径，页面文案和接口字段需要保持清晰。
- 全局统计必须由后台增量写入全局缓存行，不能由管理员接口临时汇总所有系统账户。
- 账号类型可以作为账户列表、账号运行态、能力矩阵或后续筛选条件展示，但不能新增 `oauth`、`api_key`、`account_type` 这类默认统计 scope；否则同一个本地 API Key 路由在上游账号切换后会出现统计、额度、缓存和会话连续性割裂。
- `group_account_stats` 由 worker 写入；分组列表请求只读取预聚合结果。缓存缺失或已标脏时先展示旧值或空值，等待 worker 刷新，避免列表页因为账户数展示阻塞写事务或扫描绑定关系。

## 指标清单

### 消耗指标

所有业务统计维度都应支持以下消耗指标：

| 指标 | 存储字段 | 计算方式 | 用途 |
| --- | --- | --- | --- |
| 请求数 | `request_count` | 每条有效使用记录 +1 | 活跃排序、趋势、额度辅助 |
| 成功数 | `success_count` | 成功记录 +1 | 成功率、质量、概览 |
| 失败数 | `error_count` | 失败记录 +1 | 失败趋势、错误率、告警 |
| 输入 Token | `input_tokens` | OpenAI usage 输入 token | 用量展示、成本拆分 |
| 输出 Token | `output_tokens` | OpenAI usage 输出 token | 用量展示、成本拆分 |
| 缓存读取 Token | `cache_read_tokens` | OpenAI cached tokens | 缓存拆分展示、成本折扣依据 |
| 缓存成本 | `cache_read_cost_usd` | 缓存读取 token 按模型缓存输入单价估算 | 缓存率卡片、成本拆分 |
| 总 Token | 不落表 | `input_tokens + output_tokens` | 页面展示；缓存读取已包含在输入 Token 中 |
| 成本 | `total_cost_usd` | 按模型价格估算美元成本 | 额度、排序、账务口径 |
| 最近使用时间 | `last_used_at` | 当前桶内最大 `created_at` | 列表排序、最近使用展示 |
| 最近错误时间 | `last_error_at` | 当前桶内最大失败 `created_at` | 错误状态辅助 |

注意：

- `total_tokens` 不应按 `input + output + cache_read` 计算，缓存读取 Token 已包含在输入 Token 中。
- 失败请求没有 token 或成本时，仍应计入请求数和失败数，token / 成本按 0 处理。
- `cache_read_cost_usd` 在写入 `usage_records` 时按同一份模型价格快照计算，再由 worker 增量汇总进各级统计缓存；页面不能按 token 临时估算。
- 成本用美元小数保存；额度 JSON 内的 `limit` 也表示美元金额。

### 性能指标

当前已沉淀的性能指标：

| 指标 | 存储字段 | 计算方式 | 用途 |
| --- | --- | --- | --- |
| 总耗时样本和 | `duration_ms_sum` | 有总耗时样本时累加 | 平均总耗时 |
| 总耗时样本数 | `duration_ms_count` | 有总耗时样本时 +1 | 平均总耗时分母 |
| 平均总耗时 | 不落表 | `duration_ms_sum / duration_ms_count` | 统计概览、AI 性能监控 |
| 最大总耗时 | `duration_ms_max` | 当前桶内最大总耗时样本 | AI 性能监控、慢请求排查 |
| 首 token 样本和 | `first_token_ms_sum` | 有首 token 样本时累加 | 平均首 token |
| 首 token 样本数 | `first_token_ms_count` | 有首 token 样本时 +1 | 平均首 token 分母 |
| 平均首 token | 不落表 | `first_token_ms_sum / first_token_ms_count` | AI 性能监控、账号质量 |
| 最大首 token | `first_token_ms_max` | 当前桶内最大首 token 样本 | AI 性能监控、慢首 token 排查 |

尾延迟指标继续保留分层能力：

- `duration_latency_bucket`：总耗时直方图桶。
- `first_token_latency_bucket`：首 token 直方图桶。

直方图桶边界固定为毫秒：

```text
100, 250, 500, 1000, 2000, 5000, 10000, 30000, 60000, +Inf
```

说明：

- P95 / P99 不能从 `sum/count` 准确恢复，所以当前统计体系保留直方图统计。
- 当前 AI 性能监控页面展示平均值和最大值；P95 / P99 仍需从直方图近似计算后再进入接口和页面。
- P95 / P99 由直方图近似计算，响应中需要标记为估算值，不能伪装成精确样本分位数。

### 模型分布指标

模型维度需要包含：

| 维度 | 指标 |
| --- | --- |
| `system_account_id + provider_code + model + 时间桶` | 请求数、成功数、失败数、输入 Token、输出 Token、缓存读取 Token、成本 |

说明：

- 模型分布更适合保留专用聚合表，因为它天然是 `provider_code + model` 的组合维度。
- 普通 `scope_type = model` 可以作为通用维度保留，但页面模型分布、Top 模型和全局模型统计应优先读专用模型聚合表。

### 错误分布指标

错误维度需要包含：

| 维度 | 指标 |
| --- | --- |
| `system_account_id + error_group + provider_code + error_code + status_code + 时间桶` | 请求数、错误数、最近错误消息 |

说明：

- 错误消息只作为最近样本或代表样本展示，不用于精确分组。
- 错误 Top 10 不能回扫明细，应读取错误聚合桶。

### 账号质量指标

账号质量属于调度辅助指标，不应和页面用量统计混成一个概念：

| 维度 | 指标 | 用途 |
| --- | --- | --- |
| `account_id + stat_minute` | 请求数、成功数、失败数、首 token 样本和、首 token 样本数、最近错误 | 刷新 `account_quality_scores`，影响调度排序 |

账号质量可以由统一统计 worker 同步写入，但质量分本身是派生缓存，不作为账务或用量事实。

## 分层聚合表设计

### 通用业务统计桶

确定形成以下通用表：

| 表 | 粒度 | 主键 | 用途 |
| --- | --- | --- | --- |
| `usage_stats_minute` | 自然分钟 | `system_account_id, scope_type, scope_id, stat_minute` | 精细短窗口、分钟级额度、分钟趋势、统一账号质量派生来源 |
| `usage_stats_hourly` | 自然小时 | `system_account_id, scope_type, scope_id, stat_hour` | AI 性能逐小时趋势，以及 worker 刷新概览、排行和额度窗口的来源 |
| `usage_stats_daily` | 自然日 | `system_account_id, scope_type, scope_id, stat_date` | 我的用量每日趋势、今日用量、日额度 |
| `usage_stats_weekly` | 自然周 | `system_account_id, scope_type, scope_id, stat_week` | 周额度和周报类趋势的预聚合基础 |
| `usage_stats_monthly` | 自然月 | `system_account_id, scope_type, scope_id, stat_month` | 月额度和月度消耗趋势的预聚合基础 |
| `usage_stats_totals` | 累计 | `system_account_id, scope_type, scope_id` | 累计用量、总额度、列表累计值 |
| `usage_scope_range_windows` | 固定日期范围快照 | `system_account_id, scope_type, scope_id, start_date, end_date` | 范围摘要和详情汇总，接口按范围 key 直读 |
| `client_ip_stats_daily` | IP 自然日 | `ip_hash, stat_date` | IP 统计 daily 事实，后台 `client-ip-stats-aggregation` 写入 |
| `client_ip_usage_range_windows` | IP 固定日期范围快照 | `ip_hash, start_date, end_date` | 系统运维 / IP管理 列表和后续外部 IP 聚合接口直读 |
| `usage_quota_hourly_windows` | n 小时窗口快照 | `system_account_id, scope_type, scope_id, window_hours` | n 小时额度判断，网关直读 |
| `usage_overview_summary_windows` | 概览范围摘要 | `system_account_id, window_key, start_date, end_date` | 统计概览摘要卡片 |
| `usage_overview_trend_windows` | 概览范围趋势 | `system_account_id, window_key, start_date, end_date, bucket_key` | 统计概览趋势图 |
| `usage_model_rank_windows` | 概览模型 TopN | `system_account_id, window_key, start_date, end_date, rank` | 模型分布排名 |
| `usage_error_rank_windows` | 概览错误 TopN | `system_account_id, window_key, start_date, end_date, rank` | 错误排名 |
| `ai_performance_summary_windows` | AI 性能范围摘要 | `system_account_id, window_key, start_date, end_date` | AI 性能监控摘要卡片 |
| `system_metrics_trend_windows` | 系统指标范围趋势 | `window_key, start_date, end_date, bucket_key` | 系统性能 / 网络吞吐趋势 |
| `process_event_loop_trend_windows` | 进程事件循环范围趋势 | `window_key, start_date, end_date, bucket_key, process_role` | 主进程、后台 worker、DB service 事件循环趋势 |

通用表字段保持一致：

```text
request_count
success_count
error_count
input_tokens
output_tokens
cache_read_tokens
cache_read_cost_usd
total_cost_usd
duration_ms_sum
duration_ms_count
first_token_ms_sum
first_token_ms_count
last_used_at
last_error_at
updated_at
```

时间 key 规则：

- `stat_minute`：`YYYY-MM-DDTHH:mm`
- `stat_hour`：`YYYY-MM-DDTHH`
- `stat_date`：`YYYY-MM-DD`
- `stat_week`：自然周周一日期，格式 `YYYY-MM-DD`
- `stat_month`：`YYYY-MM`
- 当前系统设置包含 `usageStatsTimezone`，默认使用部署时区；所有桶都按该固定时区生成。设置一旦产生统计数据就不能直接修改；需要改时区时必须先重建统计缓存，避免自然日、自然周和自然月错位。

### 性能直方图桶

当前性能直方图聚合表和通用统计桶同粒度：

```text
usage_latency_minute
usage_latency_hourly
usage_latency_daily
usage_latency_weekly
usage_latency_monthly
```

主键：

```text
system_account_id + scope_type + scope_id + metric_type + 时间桶 + bucket_upper_bound_ms
```

字段：

```text
sample_count
updated_at
```

规则：

- `metric_type` 取 `duration_ms` 或 `first_token_ms`。
- `bucket_upper_bound_ms` 使用固定边界，`+Inf` 用 `-1` 表示。
- 只有存在对应耗时样本时才写直方图。
- 通用性能页面的平均值继续从通用统计表单行内的 sum/count 派生；P95/P99 从直方图读取。IP 管理因高基数需要，平均首 token / 平均总耗时由 worker 写入 IP 窗口表，接口只读当前页 IP 行上已落表平均值。
- 直方图不参与成本和额度判断，只服务性能监控、账号质量分析和慢请求排查。

### 账号质量与通用分钟表

当前保留 `account_quality_minute_stats`，但明确它是调度派生表：

- 通用页面、额度和报表读取 `usage_stats_minute/hourly/daily/weekly/monthly/totals`。
- 账号质量刷新可以继续读取 `account_quality_minute_stats`，避免把调度字段污染到通用统计表。
- 通用分钟表和账号质量分钟表都由同一条主统计游标增量写入，保证服务重启后可恢复。
- 账号质量刷新读取派生表，通用统计读取通用分钟表，两个用途明确分开；保留派生表是为了避免把调度口径和页面统计口径绑死。

## 增量写入策略

当前项目保持轻量统计模型：后台统计 worker 按 usage shard 独立维护 `(created_at, id)` 游标并公平轮询 `usage_records`，每条记录只处理一次，然后把同一个增量写入所有需要的桶。统计结果库表、统计口径和页面读取方式不变，具体见 [数据集库分片写入设计](数据集库分片写入设计.md)。

处理流程：

```text
usage shard usage_records
  -> 统计 worker 按每个 shard 的 (created_at, id) 游标读取一批
  -> 生成多个 scope 维度条目
  -> 对每个 scope 同步累加 minute / hourly / daily / weekly / monthly / totals
  -> 同步累加 model 和 error 专用桶
  -> 更新 stats_job_state 游标
```

这样做的原因：

- 当前统计 worker 已经在后台运行，不在用户请求路径内。
- 单条明细在处理时已经具备全部上下文，直接写周表、月表比事后再从日表汇总更简单，也更不容易出现多层游标漏算。
- 这是线性增量，不是全量汇总。数据量增长时，成本随新增记录线性增长，不随历史总量重复增长。

当前不采用逐级 rollup 作为主路径，原因是多层 rollup 会引入每层水位、未封口桶和重复扣减问题。先用“单条明细一次性写入所有桶”的方式保证口径最稳。

若写放大达到需要改为逐级 rollup 的阈值，仍必须满足本文约束：

- 每层 rollup 都有独立 `stats_job_state`，例如 `usage_stats_hourly_rollup`、`usage_stats_daily_rollup`、`usage_stats_weekly_rollup`、`usage_stats_monthly_rollup`。
- rollup 只处理新增或变更过的低层桶，不能每次扫描整张低层表。
- 当前未封口的分钟、小时、日、周、月需要有明确策略：要么允许实时更新当前桶，要么页面显示统计滞后。
- 删除 `usage_records` 前必须确认新统计主聚合和正在执行的一次性迁移 / rollup 的 per-shard 游标都已经处理到安全位置。

### 写入放大控制

当前一条明细会写入多类桶，必须控制写放大的边界：

- 通用统计只为已经明确使用的 scope 写桶，不为无用维度生成空行。
- `model` 和 `endpoint` 通用 scope 保留，但模型分布优先使用专用 `usage_model_*` 表；实现时需要用基准测试评估写入成本，不能凭感觉删维度。
- `last_used_at`、`last_error_at` 只做最大值更新，不做复杂重算。
- 批处理继续放在后台 worker，单次批量大小由设置控制，避免网关请求同步等待统计聚合。
- 统计落库失败时不推进 `stats_job_state` 主游标，下一轮继续从原位置处理，避免漏算。

### 扣减与删除

可预见的删除场景必须同步处理。设计上优先改为软删除，物理删除只作为维护动作；API Key 是产品级例外，业务删除会先让 Key 立即失效，再把关联明细交给数据集与统计维护队列分批清理，并在统计结果库反向扣减 API Key 维度统计：

- 账户、分组、授权默认软删除或停用，历史统计保留，避免破坏历史账务和排行。
- API Key 业务删除同步移除业务库记录并让后续请求立即不可用；其关联使用记录、原始审计、API Key 维度统计缓存、额度窗口、排行 / 范围窗口进入 worker 分批清理和反向扣减，不要求删除接口内强一致完成。
- 物理删除 API Key 时，已经聚合过的关联记录需要按 `(created_at, id)` 分批读取并反向扣减所有相关桶，包括分钟、小时、日、周、月、累计、模型桶、错误桶、直方图桶和账号质量分钟桶。
- 反向扣减必须使用 `MAX(0, 原值 - 增量)` 防止负数，同时在计数和成本都归零后删除空桶。
- 反向扣减无法准确恢复被删桶的 `last_used_at` / `last_error_at`，删除维护路径允许将对应字段置空或保留旧最大值；页面不能把维护路径后的最近时间作为强一致账务依据。
- 普通用户操作不提供高频物理删除历史统计的入口；需要物理删除时走管理员维护动作，并在操作日志中记录影响。

### 统计重建与修复

统计重建和修复统一使用当前 schema 与当前统计口径：

- 如果 `usage_records` 仍完整覆盖需要重建的时间段，维护脚本按 `(created_at, id)` 分批重建当前统计桶。
- 如果 `usage_records` 已被清理或字段不完整，维护脚本直接清空统计缓存和统计游标，从新请求开始累计。
- 查询层只读取当前统计体系，不做跨体系双读，也不从低层缓存临时补数。
- 执行维护脚本前必须先备份 SQLite 数据库，然后执行“清空统计缓存 -> 重置统计游标 -> 启动统计 worker”的流程。
- 数据保留清理只需要保护当前统计体系的主游标；不为一次性修复状态保留运行时明细。
- 重建脚本必须清空并重建全部当前统计桶，包含分钟、小时、日、周、月、累计、模型、错误、直方图、排行快照和账号质量派生表。

## 查询策略

### 基本规则

- 页面和额度判断只读聚合表。
- 列表累计值读 `usage_stats_totals`。
- 今日读 `usage_stats_daily`。
- 本周读 `usage_stats_weekly`。
- 本月读 `usage_stats_monthly`。
- 滚动 n 小时额度读 `usage_quota_hourly_windows`，不在网关请求时组合小时桶。
- 固定范围摘要读 `usage_scope_range_windows`，不在页面请求时组合日 / 周 / 月桶。
- 概览窗口摘要、趋势、模型分布和错误 Top 读 `usage_overview_*_windows`、`usage_model_rank_windows` 和 `usage_error_rank_windows`。
- AI 性能摘要读 `ai_performance_summary_windows`；用户侧和管理侧指定用户读取对应系统账户窗口，管理侧全部用户读取全局窗口；AI 性能趋势因图表需要逐小时点，直接读 `usage_stats_hourly` 的账户维度小时行。
- 每日趋势必须读日桶，因为图表需要每一天的点。
- 每小时趋势必须读小时桶，因为图表需要每小时的点。
- 查询层不得把多行缓存再 `SUM` / `reduce` 成业务摘要；如果一个页面需要新的窗口或组合维度，先新增 worker 快照表。

### 任意日期范围汇总

任意自然日范围不能由页面接口临时拆月 / 拆周 / 拆日后相加。需要展示范围总量时，后台 worker 必须提前写入 `usage_scope_range_windows`：

- 主键为 `system_account_id + scope_type + scope_id + start_date + end_date`。
- 当前用量统计页面固定支持最近 31 天内的日期范围，worker 预生成该窗口内常用范围快照。
- 页面摘要、账户明细范围累计和管理员全局范围累计都按完整范围 key 直读。
- 趋势图如果需要逐日点，可以读取 `usage_stats_daily` 返回序列；趋势序列不能被前端或接口再次折算为摘要。
- 如果后续要支持更长范围或新的任意范围能力，先扩展快照生成规则或新增范围表，不能让请求路径临时回退到缓存行相加。

### 滚动窗口

滚动窗口和自然周 / 自然月不是同一个概念：

- `近 24 小时`、`近 3 天`、`近 7 天` 这类滚动窗口由 worker 读取小时桶或日桶刷新成窗口快照；页面和网关只读快照。
- `本周`、`上周`、`本月`、`上月` 这类自然窗口可以直接读周桶或月桶。
- 页面做“滚动 7 天 Top 10”时，读取排行快照，不能在页面请求时临时聚合降级，更不能回扫 `usage_records`。
- 网关滚动 n 小时额度必须读 `usage_quota_hourly_windows`，由 worker 在统计推进后刷新。

### 排行和 Top N

排行榜类查询也需要遵守聚合表原则：

- 常用窗口 Top N 统一读 `usage_rank_snapshots`、`usage_model_rank_windows` 或 `usage_error_rank_windows`。当前已落地受保护的 IP 维度公开读取接口和 IP TopN 便利视图，但没有公益站用户维度排行榜快照表；如后续要生成公益站用户榜或公开展示快照，需要先补 schema、worker 快照和接口契约，再写入本文。
- 请求路径不能为了排行榜临时读取小时 / 日 / 周 / 月桶并排序聚合。
- 新增排行榜需求时，先定义窗口 key、指标和刷新任务，再接页面。

当前排行快照：

| 表 | 主键 | 用途 |
| --- | --- | --- |
| `usage_rank_snapshots` | `system_account_id, scope_type, window_key, metric, snapshot_at, rank, scope_id` | 保存常用窗口的 Top N 结果 |

当前至少刷新：

- `account + last7d + request_count`：AI 性能监控默认账户池。
- `caller_account + last7d + request_count`：我的用量默认活跃账户池。
- `api_key + current_month + total_cost_usd`：API Key 月度高消耗排查。
- `account_authorization / group_authorization + current_month + total_cost_usd`：授权月度高消耗排查。

刷新规则：

- 由后台低频任务读取周 / 日 / 月桶生成，不读取 `usage_records`。
- 页面读取最新快照；快照不存在或过期时默认池为空，不能在页面请求时临时聚合降级。
- 快照是默认 Top N 事实源；用量事实仍是分层聚合桶。

## 额度读取规则

额度判断必须从预聚合结果读取，不允许扫明细，也不允许在网关请求时把多个缓存桶相加。

| 额度类型 | 读取方式 |
| --- | --- |
| 小时额度 | `usage_quota_hourly_windows`，按 `window_hours` 直读 |
| 日额度 | 当天 `usage_stats_daily` |
| 周额度 | 当前自然周 `usage_stats_weekly` |
| 月额度 | 当前自然月 `usage_stats_monthly` |
| 总额度 | `usage_stats_totals` |

细节规则：

- 当前已有 `hourly / daily / weekly / monthly / total` 成本额度，统一读取 `total_cost_usd`。
- 周额度按自然周周一到周日，不按滚动 7 天。
- 月额度按自然月，不按滚动 30 天。
- 滚动窗口额度只能读取 worker 生成的窗口快照，不能复用自然周 / 月桶，也不能由网关临时组合小时桶。
- 额度读取发生在网关请求前，必须只读少量索引命中的聚合行；团队授权额度直接读团队授权作用域缓存，不能枚举成员后求和。

## 权限与隔离规则

- 所有聚合表都必须包含 `system_account_id`，并在查询入口按权限决定可读范围。
- 普通用户接口强制当前登录用户作用域，不接受前端传入的 `systemAccountId` 扩权。
- 管理员全局统计读取全局缓存行；指定用户统计读取指定用户缓存行。
- `我的用量` 展示可使用账户，但统计维度必须是当前用户的 `caller_account`。
- `AI性能监控` 用户侧只允许查看当前登录用户名下账户行的 `account` 统计；别人授权给当前用户使用的账户以授权实例账户身份进入用户侧页面，归属人的原账户不进入。管理侧允许管理员读取全部用户全局缓存或指定系统账户的 `account` 统计。
- 授权统计必须归属于资源所有者，调用方只通过“我的用量”看到自己使用授权资源产生的消耗。
- API Key 统计归属于 API Key 所有者，不因为命中别人的授权资源而改变 API Key 统计归属。

## 数据保留与重建

- 聚合表是业务统计缓存，但必须持久化保存，不能只放内存。
- `stats_job_state` 长期保留，记录主聚合和 rollup 的游标。
- `usage_records` 可以短期保留；自动保留任务按统计游标安全清理，表监控手动清理只强制保护最近 1 天。
- 统计缓存损坏时，只能从仍保留的 `usage_records` 重建；超过明细保留期的数据无法凭空恢复。
- 当前策略允许放弃既有统计：如果无法从现有 `usage_records` 可靠重建，直接清空统计缓存，从新请求重新累计。
- 分钟表默认保留 48 小时，用于精细短窗口和问题排查。
- 小时表默认保留 60 天，覆盖近 30 天趋势和边界回查。
- 日表默认保留 400 天，覆盖一年内自然日查询和月表重建。
- 周表默认保留 104 周，覆盖两年周报和周额度历史。
- 月表默认保留 24 个月，覆盖年度账单、同比和追溯。
- 累计表长期保留。
- 模型和错误聚合表使用同级别保留策略；存储压力大时，优先缩短分钟 / 小时模型错误桶，不缩短业务总量桶。

## 一致性与校验

为避免统计漂移，当前统计体系保留这些校验要求：

- 后台定期抽样校验高层桶与低层桶是否一致，例如随机选择若干 `system_account_id + scope_type + scope_id + stat_date`，用小时桶求和对比日桶。
- 校验只读聚合桶，不读 `usage_records`。
- 校验发现差异时记录运行日志和操作日志可见事件，不自动全量重建。
- 管理员可以手动运行统计重建脚本，但执行前必须备份 SQLite 数据库。
- 用量统计、AI 性能和授权消耗等统计接口响应继续带 `statsLagSeconds`，用于说明统计游标滞后；IP 管理列表不展示范围总统计或统计滞后卡片。

## 可预见问题与设计处理

| 问题 | 风险 | 当前处理 |
| --- | --- | --- |
| 服务重启导致缓存丢失 | 统计缺失 | 所有统计桶和游标都持久化在 SQLite |
| 页面按日期范围汇总太重 | 账户多时接口变慢 | worker 预写 `usage_scope_range_windows`，接口按范围 key 直读 |
| Top N 排序成为热点 | 每次请求聚合大量账户 | 增加排行快照表，页面优先读快照 |
| 周 / 月口径混乱 | 额度和报表不一致 | 周固定自然周周一，月固定自然月 |
| 我的用量和 AI 性能监控概念混淆 | 用户看到不一致 | `caller_account` 与 `account` 强隔离 |
| 授权统计重复或漏算 | 授权额度不准 | 授权只按授权 ID 聚合，所有者自用不进授权维度 |
| OAuth / API Key 账号类型被当成统计分片 | 切换上游账号后 API Key / 分组统计和缓存连续性割裂 | 账户类型只用于能力和转发；本地统计按 API Key、分组、调用方、授权和账户真实 ID 聚合 |
| 统计缓存无法可靠重建 | 页面显示断层 | 清空统计缓存，从新请求重新累计 |
| 删除 API Key 后统计残留 | 列表和额度异常 | 删除维护路径反向扣减全部桶 |
| `last_used_at` 扣减后不准 | 最近使用时间漂移 | 明确维护路径下最近时间为弱一致；强一致需软删除 |
| 明细已按保留策略清理 | 既有统计无法补齐 | 清空统计缓存，从新请求重新累计 |
| 写入放大过高 | 后台 worker 压力增加 | 批量处理、只写有效 scope、保留设置控制批量大小 |
| 分位数需求 | 平均值不能反映尾延迟 | 保留性能直方图桶，P95/P99 从直方图估算 |
| 时区变化 | 自然日 / 周 / 月错位 | 固定 `usageStatsTimezone`，修改时区必须重建统计 |
| 模型 / 错误维度爆炸 | 聚合表过大 | 错误消息不参与主键；模型按 provider + model 聚合 |

## 当前设计结论

当前统计设计不再保留关键待确认项，实施和后续维护按以下结论推进：

- 新增通用 `usage_stats_minute`，并补齐 `usage_stats_weekly`、`usage_stats_monthly`。
- 模型和错误聚合也补齐分钟、周、月。
- 新增性能直方图桶，支持 P95/P99 和慢请求分布。
- 周表使用自然周周一作为 key。
- 月表使用 `YYYY-MM`，月级聚合至少保留 24 个月。
- 新增固定统计时区设置 `usageStatsTimezone`，有数据后修改必须重建统计。
- 保留 `account_quality_minute_stats` 作为账号质量派生表，不删除。
- 账户、分组和授权优先软删除 / 停用，物理删除属于维护动作；API Key 业务删除是例外，会立即失效并由数据集与统计维护队列分批清理关联记录，同时在统计结果库反向扣减 API Key 维度统计。
- 查询层只允许读取 worker 预写的范围快照；不再实现请求时范围拆桶汇总。
- 额度判断读取自然日 / 周 / 月 / 总量单行和 n 小时窗口快照，不在网关请求时求和多个桶。
- 增加常用 Top N 排行快照设计，AI 性能监控和我的用量默认池优先使用快照。
- 新增表必须配套重建脚本、数据保留清理和一致性校验。
- 既有数据修复只做离线一次性处理；无法可靠处理时清空统计缓存，从新请求重新累计。
