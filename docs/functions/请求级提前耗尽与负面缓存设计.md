# 请求级提前耗尽与负面缓存设计

> **实现归属。** 本文能力实现于 `backend-go/projects/gateway`；插入点为 `/v1` 网关链统一调度与耗尽出口（`chain_v1_loop.go` 的 dispatch 循环与 `renderDispatchExhausted`）。
>
> **强约束声明。** 本文遵守 [AI 账户错误语义与状态变更边界](AI账户错误语义与状态变更边界.md)。本机制不写任何账户 / Key / 供应商状态，不改变账户级候选切换的既有语义（§6）；P1 实施时在边界文档登记一条定位说明。

## 1. 背景与动机

调用方发送内容有问题的请求（上下文超限、内容策略拒绝、模型不支持等）时，请求本身合法通过网关本地校验，只有上游拒绝。现有链路下该请求会横扫候选池：完整非 `2xx` 逐个排除候选继续调度（统一请求级行为），受 64 attempt 安全截断、瞬态重试预算与 `noAvailableAccountWaitTimeoutSeconds`（默认 270 秒）约束。由此产生两个问题：

1. **撞号放大**：同一坏请求在候选池内反复撞号（配合调用方本地重试 N 次，撞号次数 = 全池候选 × N），持续消耗上游调用、审计与日志成本，构成可持续的滥用面；
2. **体验劣化**：调用方要等全池扫描 + 270 秒级预算耗尽才拿到失败结论，本地重试 10 次意味着极长的等待才知道"这个请求注定无法被服务"。

而这两类失败构成高概率确定性事实：同一请求被 ≥3 只同桶账户一致地以完整非 `2xx` 拒绝（状态码可各不相同，不做语义区分），根因大概率在请求侧——继续换账户大概率也不会成功。本机制把这一事实转化为更早的失败出口。

与已否决的"错误签名自动杀号"方案的本质区别：本机制的判定对象是**请求内容**（精确 hash，无语义歧义），结论作用于**单个调用方的单个请求**（不影响账户池），不需要也不尝试从错误码推断账户或供应商状态。

## 2. 与既有机制的分层

| 机制 | 判定对象 | 事实来源 | 动作 |
| --- | --- | --- | --- |
| [IP 级错误熔断](IP级错误熔断与恶意请求保护设计.md) | 来源（`systemAccountId + apiKeyId + clientIp`） | 网关本地可确认失败（认证失败、本地校验失败） | 短 TTL 本地 429 短路 |
| **本机制 L1** | **单次请求（dispatch 循环）** | **上游对 ≥3 只同桶（上游派发模型）账户的完整非 2xx 拒绝** | **提前进入既有耗尽出口** |
| **本机制 L2** | **来源会话 + 请求内容（跨请求）** | **L1 已确认的提前耗尽记录** | **短 TTL 内同会话重试直接秒级返回** |
| 账户错误策略（`credentials.error_handling_rules`） | 单个 AI 账户 | 用户显式配置 | 账户侧状态副作用 |
| 请求内统一切号 | — | — | 不变：本机制不改变切号语义，只让"候选池事实性耗尽"更早到达既有出口 |

四层互不替代：IP 熔断管"来源持续制造本地可确认坏请求"，本机制管"单个请求被上游多账户一致拒绝"，账户策略管账号侧，统一切号是所有完整非 `2xx` 的既有基线行为。

## 3. 目标与非目标

**目标**

1. 坏请求的候选扫描从"横扫全池"收窄到有界上界：单桶最多 3 只不同账户；计入瞬态重试预算后最坏约 3 + 2×2 = 7 次完整非 `2xx`（3 账户各 1 次主失败 + 最多 2 账户各 2 次瞬态预算重试），每次重试的撞号成本封顶；
2. 调用方在"3 账户 5 次拒绝"事实成立后立即拿到失败结论（而不是等全池 + 270 秒预算）；本地重试在第 2 次起秒级返回；
3. 成功请求零新增开销：指纹计算与缓存查询只发生在失败路径。

**非目标**

1. 不写任何账户 / Key / 代理 / 供应商状态，不产生账户冷却、禁用或调度回避；
2. 不改变切号准入：不按错误语义决定"是否允许切号"，只是在同请求重复被拒的事实上提前到达既有统一耗尽出口；
3. 不跨会话共享：坏请求判定以来源会话为最小隔离单位，一个会话的坏请求不熔断其他会话的相同内容；无会话证据时按既有分层回退（IP + API Key 软桶）；来源键缺失、`invalid` 或 `conflict` 时不写不查缓存；
4. 不替代 IP 级错误熔断、不新增数据库表、不做多实例共享运行态（与 IP 熔断同边界：单机进程内有界状态）；
5. 不做管理页面：可观测走既有审计错误分组视图（§8）；
6. 不按状态码或错误码做任何语义分类：上游不可信、可能不遵守 HTTP 错误码规范，计数只消费"完整 HTTP 非 `2xx`"这一结构事实。

## 4. L1：请求内提前耗尽

**"同一请求"由 dispatch 循环边界定义，无需识别**：计数器挂在单次客户端调用的 dispatch 循环上下文上，循环从头到尾处理同一次调用（同一逻辑请求在候选账户间轮转投递），请求结束计数器随之销毁。纯循环内内存计数，零缓存、零 TTL、零 hash。

**计数规则**（不依赖任何状态码或错误码语义——不可信上游原则：上游可能不遵守 HTTP 错误码规范，可用任意状态码表达任意故障）：

1. **计入**：完整 HTTP 非 `2xx` 的候选拒绝——这是网关本地可观察的结构事实（响应完整到达且 `response.ok = false`），不解释该状态码是限流、凭据失效还是请求错误，不维护状态码 / 错误码白名单或黑名单；
2. **不计入**（均为结构性排除，与错误语义无关）：传输类失败（连接、超时、读取中断——账户 / 网络侧问题，换账户可能成功）、语义提交后的失败（不是候选拒绝）、路由配置截止取消（`firstByteDeadlineMs` 等到期推进候选，边界文档已定义其为中性事实）；
3. 计数单位是**候选账户**：同账户内多 Key 轮换（`retry_next` 显式授权的兄弟 Key 重试）不虚增账户计数；瞬态重试预算（同账户对瞬态结果的既有额外重试，每账户上限 2 次）同样只计一次账户、按 attempt 合计次数；
4. **计数桶键 = attempt 的上游派发模型**（`upstream_model`，与 usage 写库同源信息）：同桶内计数并判阈值，映射到不同上游模型的候选分桶独立计数。这样"跨模型候选不被烧断"落在上游模型层面——直连 `X` 的账户与映射 `X→Y` 的账户各自成桶，8k 窗口的 `Y` 全拒不影响 128k 的 `X` 继续承接。**不使用** circuit 域的 `modelBucket`（那是传输电路作用域概念，dispatch 链路不可得）；
5. 达到阈值（≥3 只不同账户、合计 ≥5 次，同一计数桶内）→ 立即停止继续扫描该桶剩余候选，进入**既有统一耗尽出口**，不新建出口、不改墙钟与 attempt 预算语义、不改出口响应契约（不加错误摘要——详细诊断仍在审计面）；
6. **速度优先交互**：速度优先 cutover 窗口内的完整非 `2xx` 同样计入（计数输入与调度模式无关）；L1 触发时统一走既有耗尽出口，不借用速度优先的固定 503 契约出口。

不做错误码过滤后，"正常账户"的保证弱化为统计性保证：限流等异常账户的失败同样计数；已知异常账户会被既有调度排序（冷却、质量、优先级）排后，未知异常账户只有恰好连续占据同桶候选前 3 位才参与误判——概率被调度压低，残余风险见 §12。

## 5. L2：跨请求负面缓存

调用方本地重试是新的 HTTP 调用，需要内容级识别把重试与首次失败关联：

- **缓存键**：`clientSourceKey + requestFingerprint`，作用域最小取**会话级**。来源身份复用既有 `clientSourceKey` 分层（边界文档来源键体系）：Codex / Claude Code 官方会话为 `official_session`，Gemini interaction resource 为 `protocol_resource`，完全无细粒度证据时才回退 `ip_api_key_fallback`（IP + API Key 软桶，比裸 IP 窄：还要求同 Key）——"先会话、不行再扩大回退"与既有来源避让是同一分层；
- **为什么最小取会话**：上游存在与会话状态相关的拒绝（会话级限流、上下文缓存损坏），同内容换会话可能成功——会话级隔离排除这类误伤；粒度变细损失的缓存命中由 L1 兜底（每请求最多 3 账户 5 次），细粒度不会放大任何伤害；
- **来源键约束沿用**：来源键缺失、`invalid` 或 `conflict` 时不写不查 L2（对齐既有来源避让边界），该请求仅由 L1 兜底；
- `requestFingerprint` **复用既有审计指纹**（`auditlog/store.go:1531`：`method + path + model + stream + bodySha256` 聚合 hash，`bodySha256` 为全量 body SHA-256）——不自造 hash 体系，与审计错误分组键天然可对照排障；
- **写入时机**：仅当 L1 提前耗尽事实成立时写入（懒写入）；TTL 内同一键的后续请求命中即秒级进入既有耗尽出口（本次调用最多撞 1 只账户——懒查询策略见 §7）；
- **懒计算与取值点**：入口不计算指纹。请求发生第一次候选拒绝（完整非 `2xx`）后才计算指纹（本请求内续用）；后续重试请求同样在第一次候选拒绝后才查缓存。成功请求从入口到完成零 hash、零缓存操作。`bodySha256` 取值点：优先读审计捕获已算出的 `payload.BodySha256`（`gatewayusage` 审计路径同请求已在算），缺失时由 L2 自算全量 SHA-256；
- **复用形态**：指纹聚合构造从 `auditlog` 包私有 `hashNodeValue` 抽出为导出的公共构造函数（聚合构成不变：`method + path + model + stream + bodySha256`），L2 与审计共用同一实现，保证键值一致；L2 自算 body 摘要用同款 SHA-256 实现；
- **大 body 上限**：对齐审计既有上限 `auditInlineSha256MaxBytes = 1MB`（`gatewayusage/audit_capture.go:22`），**判定依据为原始 body 字节数**——超过 1MB 的 body 不参与 L2（不读缓存不写缓存），L1 不受影响（L1 不需要指纹）；
- **TTL 与续期**：TTL 固定不续期；命中递增命中计数（仅观测用）；命中路径同样落 `request_level_fast_exhausted` 审计标记；
- **存储**：进程内有界 TTL map（与 IP 熔断运行态同风格），容量上限与超限策略见 §7。

## 6. 边界合规

1. 零状态写入：不写 `accounts.status`、Key 运行态、共享质量、传输电路、代理健康、IP 避让或供应商状态；
2. 不改切号准入：切号仍是完整非 `2xx` 的统一无条件行为；本机制只在"同请求已被多只同桶账户拒绝"的事实上更早到达既有耗尽出口，不按错误语义禁止任何切号；
3. 计数输入只有"完整 HTTP 非 `2xx`"这一结构事实，不解释状态码语义、不维护状态码或错误码白名单 / 黑名单（对齐不可信上游原则与"通用客户端默认不解析上游错误对象"的既有口径）；
4. 账户错误策略命中的失败同样计入 L1 计数（计数语义是"请求被多少只账户拒绝"，与账户侧副作用正交）；
5. P1 实施时在边界文档登记定位："请求级提前耗尽与负面缓存是既有耗尽出口的快速到达，不构成账户 / Key / 供应商健康事实"。

## 7. 定量参数

| 参数 | 值 | 说明 |
| --- | --- | --- |
| L1 账户数阈值 | ≥ **3** 只不同账户 | 初值，settings 常量可调（不做开关） |
| L1 失败次数阈值 | 合计 ≥ **5** 次 | 与账户数阈值同时满足 |
| L1 作用域 | 计数桶键 = attempt 上游派发模型（`upstream_model`，usage 写库同源） | 直连与映射到不同上游模型的候选天然分桶；不使用 circuit 域 `modelBucket`（dispatch 不可得） |
| L1 阈值边界 | 次数达 5 但不同账户 <3 时不触发，继续扫描后续候选 | 阈值为合取条件；计入瞬态预算后最坏约 7 次上界 |
| 计数输入 | 完整 HTTP 非 `2xx` 的候选拒绝，不解析状态码与错误码语义 | 不可信上游原则；结构性排除项仅三类：传输类失败、语义提交后失败、配置截止取消；速度优先窗口内的失败同样计入 |
| L2 缓存键 | `clientSourceKey + requestFingerprint`（会话级最小作用域） | 来源身份复用既有 clientSourceKey 分层（official_session / protocol_resource / 无证据时回退 ip_api_key_fallback）；指纹复用 `auditlog/store.go:1531` 既有构成 |
| L2 指纹构成 | `method + path + model + stream + bodySha256`（全量 SHA-256） | 复用审计实现 `sha256Hex` |
| L2 body 上限 | ≤ **1MB**（对齐 `auditInlineSha256MaxBytes`） | 超限 body 不参与 L2，L1 不受影响 |
| L2 TTL | **10 分钟**（可调 5~15） | 上游行为漂移（模型升级、政策调整）的自愈窗口 |
| L2 容量上限 | **10000** 条，达上限拒绝新写入并递增 Prometheus 计数器 | 有界运行态，最坏 10000 × ~200B ≈ 2MB 内存 |
| L2 查询时机 | 懒查询：本请求第一次候选拒绝（完整非 `2xx`）后 | 重试请求最多多撞 1 只账户（一次上游 RTT），成功请求零开销 |
| hash 成本 | ≤ 1MB body ≈ 0.5~2ms（硬件加速 ~1.5GB/s） | 仅失败路径执行；审计路径已在算同款全量摘要 |
| 提前耗尽响应 | 既有统一耗尽出口原样（响应契约不变、不加错误摘要）+ 审计标记 `request_level_fast_exhausted` | 实施方式：走 `AddGatewayMetadata` 免 schema 变更；详细诊断仍在审计 / 日志面 |

## 8. 可观测

零新增管理页面、零新增 schema。提前耗尽事件带 `request_level_fast_exhausted` 审计标记（`AddGatewayMetadata`），审计事件落库后含 `request_fingerprint` 列——运维按该列筛选即可看到"同请求 × 多账户"的拒绝事实（注意：`audit_error_groups` 的分组唯一键是复合 `fingerprint`（含 accountId / statusCode / errorCode 等），同一坏请求被 3 只账户拒绝会形成 3 个分组，不是单一聚合视图；按 `request_fingerprint` 列筛选才是正确口径）。Prometheus `/__aisys__/metrics` 增加提前耗尽、缓存命中、缓存容量拒绝三个计数器。

## 9. 验收标准

### 9.1 定性

1. 未触发路径与现状逐字节一致：失败次数不足阈值时，调度、切号、耗尽行为与现网无差异；
2. 成功请求零新增开销：L2 自身逻辑在成功路径零 hash 计算、零缓存读写（断言对象为 L2 模块自身的调用计数；审计路径的既有摘要计算不在断言范围）；
3. 边界测试（按边界文档 §6 框架）：传输失败、语义提交后失败、配置截止取消的夹具不推进计数；任意状态码组合（`400 / 429 / 503 / 401` 混合）按同一计数规则处理，不产生任何状态码相关分支；映射到不同上游模型的候选分桶独立、互不烧断；跨会话同内容请求互不影响；来源键缺失 / `invalid` / `conflict` 时 L2 不写不查（仅 L1 兜底）；兄弟 Key 轮换不虚增账户计数；速度优先窗口内失败计入、触发时走统一耗尽出口；
4. 响应不泄漏上游地址与账户身份。

### 9.2 定量

| 用例 | 预期 |
| --- | --- |
| 同请求 3 只不同账户、合计 5 次完整非 `2xx`（任意状态码） | 第 5 次失败后立即耗尽，同桶剩余候选不被扫描 |
| 混合状态码（`400`+`429`+`503` 等，≥3 账户 ≥5 次） | 同样触发——状态码不参与判定，无任何状态码分支 |
| 失败次数达 5 但不同账户仅 2 只（含瞬态预算凑满） | 不触发，继续扫描后续候选直到账户数达 3 或池尽 |
| 直连桶 3 账户 5 次拒绝、映射桶未达阈值 | 仅直连桶耗尽，映射桶候选继续承接 |
| 传输失败 / 语义提交后失败 / 配置截止取消 | 不计数（仅有的三类结构性排除） |
| 同账户瞬态额外重试 2 次均失败 | 账户计数 +1、失败次数 +3（不虚增账户数） |
| L2 命中后的重试 | 上游调用次数 ≤ 1，响应耗时 ≈ 单次上游 RTT |
| L2 TTL 过期后 | 恢复完整 L1 流程 |
| L1 提前耗尽后写缓存 / 未达阈值不写 | 断言精确 |
| 性能 | L1/L2 新增逻辑在失败路径的开销 ≤ 5ms（含 ≤1MB hash）；L2 运行态内存 ≤ 2MB |

## 10. 分期

| 阶段 | 交付物 | 说明 |
| --- | --- | --- |
| P1 | L1 请求内提前耗尽 + 审计标记 + 边界文档登记 | 纯循环内状态，风险最低，收益已覆盖"撞号封顶 + 单请求快速失败" |
| P2 | L2 负面缓存（复用 `requestFingerprint`） | 解决本地重试体验（第 2 次起秒级返回）；依赖 P1 的写入时机 |

每阶段独立交付、独立回退（L1 关闭 = 计数逻辑不达阈值自然不触发；L2 回退 = 清空运行态 map）。

## 11. 实施时的文档同步清单

## 12. 开放问题

1. 阈值（3 账户 / 5 次）为初值，按上线后审计数据复核；
2. **无错误码过滤的残余误伤**：同桶内连续 ≥3 只未知异常账户（如未知限流）会对健康请求提前耗尽，L2 进一步把误伤放大到 TTL 窗口（10 分钟）。当前缓解全部为非语义手段：调度排序把已知异常账户排后（概率压制）+ TTL 有限自愈；若生产观察到此类误伤，候选缓解是提高账户数阈值或为 L2 写入增加独立的非语义条件，届时再评估；
3. 账户错误策略命中的失败计入 L1 计数（§6.4）——若实际运行中管理员规则覆盖导致计数语义混乱，再评估排除规则命中样本；
4. L2 命中次数展示：Prometheus 计数器已覆盖（§8），暂不做独立管理视图；
5. generic 客户端（无会话证据）回退到 `ip_api_key_fallback` 的粒度：同一公司 / 校园出口 + 同 API Key 的不同终端用户会互相命中负面缓存——该层是既有来源避让体系的既有回退粒度，先沿用；若生产观察到 NAT 出口互伤，再评估为 generic 客户端引入请求内派生会话键（须保持无状态、不可逆 HMAC，不引入新的持久身份）。
