# 用户维度热数据分区与归档治理设计

## 文档目标

本文定义当前 Node 阶段高增长表的治理方案，用于统一 `standalone` / SQLite 单机模式和 `performance` / PostgreSQL 快速模式下的索引、分区、查询、归档和清理边界。

本设计解决这些问题：

- 大量表为低频全局筛选建立过多索引，导致写入放大和索引体积远大于数据体积。
- 使用记录、日志、审计、统计窗口和监控采样随时间增长，默认在线范围过大。
- 管理员具备查看全部用户的权限，但多数页面实际应先选择用户，再查看该用户的数据。
- PG 快速模式不能继续复制 SQLite usage catalog 模型；SQLite 单机模式也不能把所有历史数据放在一个热查询面里。
- 历史明细需要可归档、可导出、可手动删除，但不应长期挤占热表和热索引。

本文是当前 Node 阶段改造 `usage_records`、`usage_record_shard_entries`、`usage_scope_range_windows`、日志 / 审计 / 统计 / 表监控等高增长表的依据。执行计划见 [PLAN-0080 用户维度热数据分区与归档治理](../plans/计划-0080-用户维度热数据分区与归档治理.md)。

## 核心结论

- 高增长明细表的查询入口必须先限定 `system_account_id` 和日期窗口；管理员全局入口也必须先选择用户，不能默认扫全部用户明细。
- 管理员全局概览只读预聚合 summary / snapshot，不读 raw 明细表。
- 默认热查询窗口是今天；最近 7 天是在线明细窗口上限。超过在线窗口的数据进入归档层，不参与常规页面查询。
- 列表分页使用 cursor，不使用深 `OFFSET` 跨天翻页，不返回精确全量 `COUNT(*)`。
- 大表索引采用白名单，不为每个可选筛选项建立全局索引。索引必须以用户维度开头，除非该表没有用户语义。
- PostgreSQL 模式下高增长事实表按时间分区；过期数据优先 `DROP / DETACH PARTITION`，不靠热表大批 `DELETE`。
- SQLite 模式下高增长事实进入按日期组织的 shard / segment 文件；过期数据优先 seal / archive / delete 文件，不在热库里长期批量删除。
- `usage_scope_range_windows` 不再预生成 31 天内所有任意范围；只物化热窗口和用户明确请求的范围窗口。
- 不为旧结构保留运行时双读、双写或兼容兜底。上线窗口按当前 schema 离线重建或归档旧数据。

## 当前落地状态（2026-07-06）

- `usage_records`：
  - SQLite 单机模式继续按日期 shard 写入和读取，列表默认今天，管理员未选择用户时不查 raw。
  - PostgreSQL 快速模式将 `juhe_usage.usage_records` 改为 `created_at` 日分区父表，主键改为 `(created_at, id)`，写入前按记录时间自动创建日分区。
  - PG 详情读取可从 `usage_YYYYMMDD_...` 形态的 id 推导日期分区裁剪条件。

  - SQLite 只保留 shard 定位和清理所需索引。

  - 后台默认只刷新 `today`、`yesterday`、`last7d`、`last31d`、`current_month`。
  - 自定义范围先登记 `usage_range_window_requests`，由 stats worker 按批生成，接口请求链路不现场聚合。
- 日志和统计表：
  - `audit_logs` 停止创建全局 trace / model / path / status / client_ip 等低频索引，保留清理时间索引和用户范围 trace / client_ip / API Key / 分组 / 账号索引。

  - 客户端 IP 范围窗口只保留窗口请求量默认排序、到期清理和必要定位索引，不再为每个可选排序指标建一套大索引。
- 表监控：
  - PG 表监控增加 `archive` 逻辑库，采样 `juhe_archive`。
  - 表级快照增加 `table_kind`、`parent_table_name`、`is_partition`、`is_archive`，前端展示分区 / 归档状态和索引体积比例。
  - 已通过 PostgreSQL table monitor smoke，覆盖 `juhe_archive` 采样、分区 / 归档状态和索引体积比例字段。
- 压测：
  - 已通过 `test:usage-hot-data-pressure` 合成高增长极限压测：50 万 hot usage、10 万 archive usage、25 万 range window、64 并发查询、PG 分区归档和表监控采样均无错误、无死锁、无 Seq Scan。

## 数据分层

| 层级 | 默认范围 | 存储职责 | 查询入口 |
| --- | --- | --- | --- |
| 今日热层 | 今天 | 默认列表、排障、近实时统计输入 | 页面默认查询，只查当前用户 |
| 近期在线层 | 最近 7 天 | 可分页查看近期明细，支持常用筛选 | 需要日期 cursor，仍必须指定用户 |
| 归档层 | 超过 7 天 | 历史取证、导出、手动恢复或手动清空 | 不进入常规页面；通过归档任务 / 导出入口处理 |
| 长期摘要层 | 按设置保留 | daily / weekly / monthly 统计、容量趋势、额度和报表 | 常规统计页面和全局概览 |

默认值可以通过系统设置调整，但上限必须受控。建议目标设置：

| 设置 | 默认值 | 合法范围 | 说明 |
| --- | --- | --- | --- |
| `usageRecordOnlineRetentionDays` | `7` | `1..31` | raw 使用记录在线明细保留天数 |
| `usageRecordArchiveRetentionDays` | `90` | `7..365`，`0` 表示只手动删除 | raw 使用记录归档保留天数 |
| `recordListDefaultDateWindow` | `today` | `today` / `last_24h` | 使用记录、审计、日志页面默认窗口 |
| `statsHotWindowDays` | `31` | `7..31` | 统计窗口允许选择的最大天数，不表示全范围预物化 |
| `tableMonitorSnapshotRetentionDays` | `30` | `7..90` | 表监控采样历史保留 |

现有 `usageRecordRetentionDays` 后续应被拆成在线保留和归档保留两个语义；运行时代码只维护新语义，既有数据由离线流程处理。

## 查询契约

### 用户维度强制规则

这些页面和接口必须指定用户：

- 使用记录列表和详情旁路检索。
- 原始审计日志列表、公开接口日志、操作日志、运行日志索引中可归属用户的列表。
- AI 账户用量、API Key 用量、分组用量、授权消耗、客户端 IP 用量等明细 / 排行页面。
- 管理员查看普通用户数据时，先在用户选择器中确定 `systemAccountId`。

允许不指定用户的入口只能返回聚合结果：

- 全局今日请求量、成本、错误数、活跃用户数。
- Top 用户排行，来源必须是预聚合表。
- 表容量总览，来源必须是 `database_storage_snapshots` / `table_storage_snapshots`。
- 后台队列和 worker 运行态。

### 日期窗口强制规则

- 默认查询今天，不默认查询最近 30 天。
- 用户选择历史时，先按日期范围缩小，再按 cursor 翻页。
- 明细列表最多在线查询最近 7 天；超过范围只展示归档入口。
- 不允许无日期窗口的 `LIKE`、排序、`COUNT(*)` 或跨分区扫描。

### 分页规则

高增长表统一使用稳定 cursor：

```text
cursor = {
  systemAccountId,
  date,
  createdAt,
  id,
  direction
}
```

翻页顺序：

1. 默认读取当前用户今天的数据。
2. 今天没有更多后，cursor 指向前一天。
3. 前端继续加载时再读取昨天的数据。
4. 超过在线窗口后返回 `archiveAvailable`，不继续扫热表。

返回值只提供 `hasMore`、`nextCursor` 和当前页数量，不提供精确全量 `total`。需要总量时由统计摘要表给出估算或预聚合数字。

## 索引白名单

### 默认大表索引

有用户归属的大表只默认保留：

```sql
(system_account_id, created_at DESC, id DESC)
```

按真实高频功能补充：

```sql
(system_account_id, trace_id, created_at DESC, id DESC)
(system_account_id, api_key_id, created_at DESC, id DESC)
(system_account_id, account_id, created_at DESC, id DESC)
(system_account_id, group_id, created_at DESC, id DESC)
```

PostgreSQL 文本前缀查询必须使用稳定 collation 的局部索引，例如：

```sql
(system_account_id, (trace_id COLLATE "C"), created_at DESC, id DESC)
```

### 不再默认建立的索引

这些索引不应在 raw 明细表中默认存在：

- 全局 `created_at` 排序索引，除清理游标必需外不服务页面。
- 全局 `trace_id`、`model`、`client_ip`、`status_code`、`success` 索引。
- `duration_ms`、`first_token_ms`、`cost_usd` 这类诊断排序索引。
- 同一字段的“全局版本 + 用户版本”双套索引。
- 为低频管理员全局筛选准备的复合索引。

这些能力的替代方式：

- 今天或最近 7 天内的小窗口可以使用用户 + 日期主索引回表过滤。
- TopN、错误率、成本排行、耗时排行进入统计摘要 / 诊断快照。
- 深度取证通过归档导出或离线分析执行，不挤占热写路径。

### 例外登记

新增大表索引必须在对应功能文档中说明：

- 服务哪个接口或后台任务。
- 是否以 `system_account_id` 开头。
- 是否限定日期窗口。
- `EXPLAIN` 预期命中的索引。
- 写入放大成本和移除条件。

## 分区与归档模型

### SQLite 单机模式

SQLite 仍保持轻量单机，不引入外部数据库。高增长事实使用日期 segment：

```text
data/
  usage-shards/
    2026/07/05/usage-20260705-s000.sqlite3
    2026/07/05/usage-20260705-s001.sqlite3
  archives/
    usage-records/2026/06/usage-20260628.tar.zst
```

规则：

- `usage_records` 继续按 `bucket_date + shard_id` 写入多个 SQLite shard 文件。
- 默认列表只打开当前日期 shard；需要历史时按 cursor 打开上一日期 shard。
- shard 内索引收敛为用户 + 时间、用户 + API Key、用户 +账号、用户 + 分组、用户 + trace。
- `usage_record_shard_entries` 不再承载所有筛选字段和排序索引；它只保留 shard 定位、日期、用户、少量清理定位字段。
- 超过在线保留期的 shard 先确认统计游标追平，再 seal 并移动到 archive。
- archive 只保留可离线读取的压缩包和 manifest，常规 API 不打开 archive。
- 手动清空 archive 只删除 archive 文件和 manifest，不影响业务库。

低频日志表可以暂时继续在数据集目录库中使用用户 + 时间索引；当增长达到阈值时迁移到同样的日期 segment 模型。阈值建议：

- 单表 24 小时增长超过 `500MB`。
- 单表索引大小持续超过表大小 `3` 倍。
- 维护清理连续 3 轮无法追平新增速度。

### PostgreSQL 快速模式

PostgreSQL 高增长事实表统一按时间分区：

```text
juhe_usage.usage_records
  usage_records_20260705
  usage_records_20260706

juhe_dataset.audit_logs
  audit_logs_20260705
  audit_logs_20260706
```

规则：

- `usage_records` 按 `created_at` 日分区；请求量较低时可按月分区，但默认目标是日分区。
- 每个分区建立局部索引，索引以 `system_account_id` 开头。
- `id` 已包含日期时，详情查询可先从 id 推导分区；无法推导时必须带 `created_at` 或从轻量定位表查一次，不扫描全部分区。
- `usage_record_shard_entries` 在 PG 下不再作为实体列表 catalog；PG 列表直接读分区后的 `usage_records`。
- 过期数据优先 `DETACH PARTITION` 到 archive schema 或导出后 `DROP PARTITION`。
- 保留期清理不得在热分区上执行无界 `DELETE`；小批 `DELETE` 只作为未分区表过渡期或异常修复手段。

## 范围窗口治理

`usage_scope_range_windows` 当前会为 31 天内任意 `start_date/end_date` 组合生成 496 个范围。目标模型改为热窗口 + 按需窗口。

### 热窗口

默认后台只刷新这些窗口：

| 窗口 | 用途 |
| --- | --- |
| `today` | 默认页面、额度近实时、今日概览 |
| `yesterday` | 昨日对比 |
| `last_7d` | 近期运营查看 |
| `last_30d` / `last_31d` | 月内近似趋势 |
| `current_month` | 月度费用和额度 |

热窗口表建议增加 `window_key`，避免仅用任意 `start_date/end_date` 表达所有窗口。

### 按需窗口

用户选择自定义范围时：

1. API 先检查窗口缓存是否存在。
2. 不存在则登记 `usage_range_window_requests`。
3. stats-worker 按用户和范围生成缓存。
4. 页面返回“窗口生成中”，不在请求链路现场聚合。
5. 生成后的自定义窗口可设置 TTL，例如 24 小时或 7 天。

### 索引收敛

范围窗口只保留：

```sql
PRIMARY KEY (system_account_id, scope_type, scope_id, window_key)
(system_account_id, scope_type, window_key, request_count DESC, total_cost_usd DESC, scope_id)
(end_date)
```

如果仍需要 `start_date/end_date`，也必须以用户和窗口维度收口：

```sql
(system_account_id, scope_type, start_date, end_date, scope_id)
```

不再为 `success_count`、`error_count`、`error_rate`、`total_tokens`、`active_days`、`last_used_at` 分别建立默认排序索引。相关排行进入独立排行快照或按需诊断窗口。

## 表级治理矩阵

| 表 / 表族 | 数据类型 | 查询前提 | 分区 / segment | 默认在线 | 归档策略 | 索引策略 |
| --- | --- | --- | --- | --- | --- | --- |
| `usage_records` | 使用记录 raw 明细 | 必须指定用户和日期 cursor | SQLite 日期 hash shard；PG 日分区 | 7 天 | seal / detach 后压缩归档 | 用户 + 时间，用户 + API Key / 账号 / 分组 / trace |
| `usage_record_shard_entries` | SQLite usage 定位 catalog | 仅定位在线 shard 和清理候选 | SQLite 保留轻 catalog；PG 移除实体表 | 跟随 usage 在线期 | 可从 shard 重建，不长期归档 | 只保留定位和清理索引 |
| `usage_record_account_shards` / `usage_record_api_key_shards` | 删除清理定位 | 后台维护任务 | SQLite catalog；PG 由分区 usage 查询替代 | 跟随 usage 在线期 | 可重建 | 账号 / API Key + 日期 / shard |
| `audit_logs` / `audit_log_attempts` | 原始审计元数据 | 指定用户和日期；trace 排障可精确查 | PG 日分区；SQLite 阈值触发日期 segment | 成功热窗口 + 失败保留 | payload refs / blobs 跟随归档或清理 | 用户 + 时间，用户 + trace |
| `audit_payload_refs` / `audit_payload_blobs` | 审计正文引用和 blob | 只能由审计详情按 id 读取 | 外部 payload 文件优先 | 跟随审计策略 | 文件级归档 / 删除 | 不做内容搜索索引 |
| `operation_logs` | 管理操作记录 | 指定用户或目标对象 | 可继续普通表；PG 可月分区 | 365 天 | 默认不归档或按需导出 | 用户 + 时间，目标对象低频索引 |
| `public_api_logs` | 公开接口调用记录 | 来源系统 + 日期 | PG 后续可按日 / 月分区；SQLite 保留短期或 segment | 30 天 | 按来源导出 | 来源 + 时间；不默认建全局 trace / client_ip |
| `runtime_logs` | 运行日志索引 | 时间窗口必填，默认今天 / 最近 1 小时 | 原日志文件 + 有界索引 | 7 到 14 天 | 不默认归档 | 时间 + 角色 / 级别，trace 例外 |

| `usage_stats_hourly` / `usage_latency_hourly` | 小时统计桶 | 用户 + 范围 | PG 月分区 | 60 天 | 可重建，不归档 | 用户 / scope + 时间 |
| `usage_stats_daily` / weekly / monthly | 长期摘要 | 用户 + 范围 | PG 年 / 月分区 | 长期 | 可离线备份 | 用户 / scope + 日期 |
| `usage_scope_range_windows` | 账号 / API Key / 分组范围窗口 | 用户 + 热窗口或按需窗口 | 普通缓存表，按 `window_key` 管理 | 热窗口长期滚动 | 自定义窗口 TTL 删除 | 用户 + scope + window_key |
| `authorization_*_usage_range_windows` | 授权范围窗口 | 用户 / 团队 + 热窗口或按需窗口 | 同范围窗口模型 | 热窗口 | 自定义 TTL | 授权作用域 + window_key |
| `client_ip_registry` / `client_ip_stats_daily` | IP 统计 | 用户 + 日期 / IP | registry 保留；daily 可分区 | 30 到 90 天 | 可按用户导出 | 用户 + bucket / IP + 日期 |
| `client_ip*_range_windows` | IP 范围窗口 | 用户 + 热窗口 | 热窗口 + 按需 | 热窗口 | TTL 删除 | 用户 + window_key |

| `system_metrics_samples` / `process_event_loop_samples` | 系统原始采样 | 时间窗口 | 短保留 | 7 天 | 不归档 | 时间 + 进程角色 |
| `system_metrics_trend_windows` / `process_event_loop_trend_windows` | 系统趋势窗口 | 热窗口 | 热窗口 | 30 天 | 不归档 | window_key + 时间 |
| `database_storage_snapshots` / `table_storage_snapshots` | 表监控采样 | 时间窗口 | 普通表；PG 可月分区 | 30 天 | 可导出 | 时间 + 表名 / 库角色 |
| `model_check_runs` / `model_check_items` | 显式诊断结果 | 用户 / run id | 普通表 | 30 天 | 不默认归档 | 用户 + 时间，run id |
| `usage_record_cleanup_deductions` | 清理扣减账本 | 后台幂等 | 普通表短保留 | 30 天 | 不归档 | usage id / updated_at |

## 页面与接口调整

### 管理员视角

- 高增长明细页面打开后先展示用户选择器和今日全局摘要。
- 未选择用户时，不加载 raw 列表。
- 选择用户后，默认加载该用户今天数据。
- “全部用户”只允许在预聚合页面使用，不允许进入 raw 使用记录 / raw 审计 / raw 日志列表。

### 普通用户视角

- 默认打开今天。
- 日期范围默认最多 7 天。
- 最近一周外展示归档提示，不直接查热库。

### API 契约

高增长列表接口新增或收敛为：

```text
GET /records?systemAccountId=...&date=2026-07-05&cursor=...
```

响应：

```json
{
  "items": [],
  "hasMore": true,
  "nextCursor": {
    "date": "2026-07-05",
    "createdAt": "2026-07-05T12:00:00.000Z",
    "id": "usage_20260705_s000_xxx"
  },
  "archiveAvailable": false
}
```

不再承诺：

- 精确全量 `total`。
- 无用户条件的全局 raw 列表。
- 任意历史范围实时聚合。
- 任意字段排序都走索引。

## 归档与恢复

### 归档 manifest

每个归档包保存 manifest：

```json
{
  "domain": "usage_records",
  "systemAccountIds": ["sys_admin"],
  "startDate": "2026-06-01",
  "endDate": "2026-06-07",
  "recordCountEstimate": 123456,
  "source": "sqlite_usage_shard",
  "schemaVersion": 1,
  "createdAt": "2026-07-05T00:00:00.000Z"
}
```

manifest 进入轻量归档目录表，便于页面显示“有归档数据”。归档目录不保存完整正文，不参与常规查询。

### 恢复边界

- 恢复归档必须是显式维护动作，不在页面请求中自动恢复。
- 恢复可以导入到临时分析库或离线导出文件，不默认回写热表。
- 如果需要把归档恢复为在线数据，必须停机或进入维护模式，并按当前 schema 重建相关统计。
- 2026-07-06 已完成 PG 分区归档恢复演练：从 `juhe_archive` 和 `data_archive_manifests` 校验归档，再显式移回热库并 `ATTACH PARTITION` 验证父表可读；该路径不依赖运行时代码双读或页面自动恢复。

### 手动清空

管理员可按归档域、用户和日期删除 archive。删除 archive 不回滚统计摘要；统计摘要是长期聚合事实，可以单独保留。

## 表监控与告警

表监控需要新增这些判断：

- 索引 / 表大小比超过 `3`：提示索引写放大。
- 24 小时增长超过在线保留预期：提示清理或分区未追平。
- PG 未分区大表超过阈值：提示需要迁移为分区表。
- SQLite usage shard 单日分布倾斜：提示 shard hash 或热点用户异常。
- archive 目录增长超过阈值：提示手动清理或外部备份。

表监控不得为了这些指标扫描 raw 表；PG 使用 catalog / stats view，SQLite 使用文件大小、dbstat 和已记录采样。

## 实施顺序

1. 查询契约收敛：高增长页面和 API 强制用户 + 日期窗口，默认今天，cursor 分页。
2. 索引白名单落地：删除全局和低频排序索引，补用户 + 日期核心索引。
3. SQLite usage catalog 瘦身：`usage_record_shard_entries` 改为定位和清理目录，不再承担所有筛选排序。
4. PG usage 分区：`usage_records` 改为日分区，列表直接读分区表，移除 PG 实体 `usage_record_shard_entries` 依赖。
5. 范围窗口重构：从 496 全范围物化改为热窗口 + 按需窗口。
6. 归档任务：实现 seal / detach / archive / manifest / 手动清空。
7. 表监控增强：展示分区、索引放大、归档增长和清理追平状态。
8. 压测与回归：分别验证 SQLite 单机和 PG 快速模式。

## 风险与边界

- 删除索引会让部分低频筛选从“立即返回”变为“限定日期窗口内过滤”或“后台诊断生成”。这是有意取舍。
- PG 分区会改变主键 / 唯一约束设计；usage id 已包含日期，写入幂等应按当前分区和当前 schema 处理，不做旧结构兼容。
- 归档数据不参与在线统计实时重建；长期统计摘要应在归档前由 stats-worker 追平。
- 管理员全局 raw 明细能力会被收紧；需要全局排障时走预聚合摘要、trace 精确查找或离线导出。
- 本设计不引入 ClickHouse、Kafka 或重型 OLAP。PG 快速模式只用 PostgreSQL 分区和 Redis 队列，SQLite 单机模式只用本地 shard / archive。
