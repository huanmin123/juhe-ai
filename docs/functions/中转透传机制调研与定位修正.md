# 中转透传机制调研与定位修正

本文用于沉淀 `sub2api_source` 与其他开源 AI 中转 / 网关项目的源码对照结论，并修正 `juhe-ai` 的透传产品定位。

OpenAI OAuth / Codex backend 的二次细节复查、项目对比、风险排序和后续打磨建议见 [OpenAI OAuth 透传细节统计与比较](OpenAI%20OAuth透传细节统计与比较.md)。

## 一句话结论

`juhe-ai` 的用户侧不应该出现多套透传选项，也不应该出现“是否开启透传”的账号或系统开关。透传是中转网关的默认行为：所有账户都按所属供应商的透传策略转发。服务端仍然保留必要的网关职责，例如本地鉴权、上游凭据替换、协议安全头剔除、流式转发、错误兜底、账号调度和会话隔离，但这些都属于供应商适配器的内部实现细节，不暴露给用户选择。

透传的目标不是让用户理解复杂网关策略，而是让客户端长期固定使用本服务 `/v1` 和本地 API Key，同时让上游看到尽量接近真实客户端的请求语义，减少“中间代理实现细节”泄露给上游。

## 产品定位依据

`README.md` 对 `juhe-ai` 的定位非常明确：

- 客户端只保留一个本地 OpenAI 兼容入口，不再在多个中转、账号和服务商之间来回改 Base URL / API Key。
- 服务商、账户、代理、错误切换和使用记录由后台统一管理。
- 授权模型是“分组绑定账号、API Key 绑定一个或多个可用分组路由”，可用分组包含调用方自有分组和有效授权分组；客户端只需要使用本服务 `/v1` 和后台生成的本地 API Key。
- 项目目标是减少配置混乱、会话割裂和手动切换成本，而不是把底层转发策略暴露成用户需要理解的配置项。

因此，透传能力应该服务于这个产品目标：用户只知道请求会由本服务按供应商策略稳定转发，不需要知道内部如何清洗头、替换认证、处理流或兜底切换。

## `sub2api_source` 当前做法

参考源码位置：`F:\temp-project\sub2api_source`。

### 核心入口

- 网关按供应商策略启用 OpenAI 透传，账户上的布尔值只作为内部派生状态，不作为用户开关。
- GPT 供应商进入 OpenAI v1 协议透传转发链路，用户不需要选择是否启用，也不需要选择更多细分策略。
- 透传链路仍然会读取必要字段，例如模型、流式标识、reasoning effort、compact 路径和错误处理所需上下文。

### 请求头处理

- `sub2api_source` 没有把所有入站头无条件抛给上游，而是通过透传允许列表控制低风险头。
- 会保留客户端语义相关头，例如 `accept`、`accept-language`、`content-type`、`user-agent`、`openai-beta`、`originator`、`session_id`、`conversation_id`、`x-codex-turn-state`、`x-codex-turn-metadata`。
- 会删除客户端侧残留认证头，例如本地 `authorization`、`x-api-key`、`x-goog-api-key`，再写入上游账号对应的真实凭据。
- `X-Forwarded-For`、`X-Real-IP` 只用于诊断日志白名单，不参与上游透传；这点很关键，因为主动发送代理链路头反而更容易暴露“我是中转”。
- OAuth 到 ChatGPT internal API 时会补必要协议头、设置 `Host`、处理 `chatgpt-account-id`，并对 `session_id` / `conversation_id` 做隔离，避免不同本地 API Key 的会话互相碰撞。

### Body 处理

- 透传链路不是重型改写，但也不是完全不读 body；它会为了账号选择、模型映射、流式处理、请求错误策略和统计读取必要字段。
- 对 OAuth / Codex 相关请求，会做少量必要 normalize，例如 compact 请求路径和必需字段检查。
- 其他项目里的转换型链路通常更偏向协议整理，例如默认内容、工具字段或模型参数的适配；`juhe-ai` 当前不把这类整理作为 API Key 账号的运行路径。

### 响应与错误处理

- 透传响应会尽量保持上游原始流式数据和错误响应。
- 对容量类错误、临时不可用或账号失败，服务端仍会按账号调度策略做兜底和切换。
- 流式响应会边转发边做必要的结束事件、usage 和断流处理，避免客户端体验和统计完全失控。

## 为什么 `sub2api_source` 要这样做

`sub2api_source` 的设计目标不是“所有字节无条件原样反代”，而是在账号调度、多用户隔离和 OpenAI OAuth 兼容场景下尽量保留客户端真实语义。

关键原因：

- **保护上游账号**：不能把本地网关的认证头、内部头、代理链路头、错误噪声或框架默认头传给上游。
- **减少中转痕迹**：保留真实客户端的 `user-agent`、语言、Codex 相关头和会话语义，同时避免发送 `X-Forwarded-For` 这类明显代理头。
- **保持会话隔离**：多个本地 API Key 可能复用同一上游账号，必须隔离 `session_id` / `conversation_id`，否则会话可能串线。
- **保证可用性**：中转的核心价值包含账号选择、错误切换、流式稳定和使用记录，完全 raw proxy 会削弱这些能力。
- **降低用户心智负担**：用户只关心“这个账号是否尽量按客户端请求走”，不应该学习底层转发策略。

## 其他开源项目对照结论

| 项目 | 对请求头的做法 | 对 body 的做法 | 对 `juhe-ai` 的启发 |
| --- | --- | --- | --- |
| `one-api` | 默认最小头，按供应商重新写认证 | 通过渠道适配 OpenAI 格式 | 简单稳定，但不适合承诺全量客户端语义透传 |
| `new-api` | 支持显式头转发规则，但会跳过协议头、认证头、长度头和压缩头 | 按供应商做参数与响应适配 | 适合借鉴“先跳过危险头，再转发客户端语义头”的内部实现 |
| `LiteLLM` | 默认清洗请求头，不转发上游认证；只转发少数追踪头 | 会注入路由、团队、metadata 等网关信息 | 适合作为企业网关参考，但不符合我们“尽量少改客户端请求”的透传诉求 |
| `Portkey` | 常规路径按供应商重写；代理入口可复制多数请求头并跳过危险头 | 提供供应商转换、重试、缓存和 hooks | 可借鉴“常规网关能力”和“代理式转发能力”分层，但不要暴露给用户 |
| `Proxify` | 接近直接复制客户端请求头 | 默认 body 原样流向上游 | 原样反代思路可参考，但缺少账号调度、多租户隔离和上游凭据替换 |
| `RelayPlane` | 常规路径重写认证，部分场景强调客户端指纹头 | 会读取 body 做策略、成本和降级 | 成本与预算可参考，透传语义不适合作为主线 |

综合来看，成熟网关很少无条件全量转发。越是有账号池、授权、统计、错误切换和多用户隔离的中转系统，越需要在服务端保留必要边界；但这些边界不应该变成用户可见的复杂选项。

## `juhe-ai` 推荐落地方式

### 用户侧语义

- 账号表单、账号列表和系统设置都不展示透传开关。
- 不展示头策略、body 策略、会话策略、代理策略等内部细分选项。
- 帮助文案只说明：请求按供应商策略默认透传，不做默认内容填充或额外内容追加。
- 用户不需要知道某个账号能否关闭透传；当前产品结论是所有账户都必须透传。

### 后端内部语义

- 透传策略挂到供应商适配器，当前 GPT 供应商能力包含 `passthrough`，因此所有 GPT API Key 账户按 OpenAI v1 协议强制透传。
- `accounts` 不保存透传开关或派生标记；透传由供应商 adapter 的当前实现直接决定。
- 透传请求 body 默认不填充、不追加、不注入默认内容；只允许为上游协议必需、安全边界或账号调度做最小处理。
- 透传请求头应以客户端头快照为来源，尽量转发 end-to-end 客户端语义头，同时剔除必须剔除的协议头、本地认证头、网关内部头和明显代理链路头。
- 响应头也需要做同类安全边界过滤；除固定 hop-by-hop、`Connection` 声明的动态 hop-by-hop、压缩、cookie 等协议头外，应剔除常见中转网关指纹头，例如 LiteLLM、Portkey、Helicone、Cloudflare AI Gateway、Kong 等前缀，避免把上游或中间层实现泄露给客户端。
- OAuth 账户的真实转发不走官方 `api.openai.com/v1` 兼容链路，而走 ChatGPT / Codex backend 专用链路；该链路只作为 GPT 供应商适配器内部细节，用户侧仍然只看到本服务 `/v1`。
- 对带 `session_id`、`conversation_id`、`prompt_cache_key` 或相关 `metadata` 的请求，网关可以使用短期内存会话亲和优先调度到上次成功账号；该策略只改变同一调度层级内的排序，不跳过授权、分组、状态、冷却、到期、并发和错误处理。绑定账号并发满时只在本请求内做很短的同账号等待和重查，尽量保住上游会话 / 缓存；短等后仍满才继续后续候选。
- 响应体和 SSE 流尽量原样转发；统计、usage、错误切换可以旁路解析，但不要影响客户端收到的数据语义。

### 请求头建议

推荐内部实现从“客户端头快照 + 必要剔除列表”出发，而不是在业务代码里散落手动 `Set` / `Del`：

- 必须替换：`authorization`、上游 API Key 类认证头。
- 必须由 HTTP 客户端重新计算或禁止转发：`host`、`content-length`、`transfer-encoding`、`connection`、`upgrade`、`keep-alive`、`te`、`trailer`、`proxy-authorization`、`proxy-authenticate`。
- 默认不转发：`x-forwarded-for`、`x-real-ip`、`forwarded`、`via`、本服务内部调试头、本地管理端 cookie。
- 谨慎处理：`accept-encoding`，避免上游压缩导致流式转发、usage 旁路解析和错误处理不稳定。
- 优先保留：`user-agent`、`accept`、`accept-language`、`content-type`、`openai-beta`、`originator`、`session_id`、`conversation_id`、Codex 相关客户端头。

这样既更接近“客户端怎么请求，上游就看到什么语义”，又不会把本地网关身份、代理链路和本地鉴权暴露给上游。

### 关于客户端 IP

从服务端中转的网络原理看，上游 TCP 连接的源 IP 一定是 `juhe-ai` 服务所在机器或账号绑定代理的出口 IP，不可能仅靠转发请求头变成真实客户端公网 IP。

因此，`juhe-ai` 不应默认把 `X-Forwarded-For` / `X-Real-IP` 发给上游。这样做不仅不能改变 TCP 源 IP，还会明确告诉上游“这里有代理链路”，反而违背中转稳定目标。

如果业务确实要求上游按不同客户看到不同出口，应通过账号绑定代理、客户专属代理出口或分组级代理策略解决，而不是通过伪造或透传代理链路头解决。服务端可以在本地使用记录中保存客户端 IP 供审计和排查，但不默认向上游暴露。

## 最终决策

1. `juhe-ai` 产品不提供透传开关；所有账户都按供应商策略默认透传。
2. 透传时，服务端不做 body 填充、默认内容追加或无关改写。
3. 透传时，服务端尽量保留客户端请求头和请求语义，但必须剔除会泄露本地网关、破坏协议或暴露代理链路的头。
4. 上游认证必须由本地 API Key 替换为被调度账号的真实上游凭据。
5. 客户端 IP 不通过 `X-Forwarded-For` 透给上游；需要不同出口 IP 时通过账号 / 分组绑定代理解决。
6. 调研到的头处理、body 旁路解析、流式转发、错误切换和会话隔离都作为供应商适配器内部实现，不让用户选择。
