# 自定义模型与模型映射设计

> 面向 AI 和维护者。
> 本文记录手动添加模型、自定义价格和账号模型映射的长期设计。官方模型目录清洗见 [厂商模型目录更新与清洗指南](厂商模型目录更新与清洗指南.md)，usage 字段与成本公式见 [模型价格与用量统计口径](模型价格与用量统计口径.md)。

> 设计同步提示：`2026-06-23` 起，客户端兼容、`responses -> chat_completions` 协议转换和模型映射高级设置的最新草案见 [客户端兼容与模型映射重设计草案](客户端兼容与模型映射重设计草案.md)。新草案收敛为账号级模型映射：左侧 `sourceModel` 选择全局客户端可见模型，右侧 `upstreamModel` 强制选择当前供应商 / 当前账号可用模型；Codex 请求 GPT 模型名但实际打到 DeepSeek 时，应配置在 DeepSeek 账号映射中。`2026-06-24` 起，OpenAI Chat / Responses 到 Anthropic Messages 的显式桥接按 [OpenAI 到 Anthropic Messages 协议桥接设计](OpenAI到Anthropic协议桥接设计.md) 扩展模型映射目标族。`2026-06-25` 起，Anthropic Messages 到 OpenAI Chat Completions 的显式桥接按 [Anthropic Messages 转 Chat Completions 协议转换设计](AnthropicMessages转Chat协议转换设计.md) 扩展模型映射来源族。

## 1. 背景

`/v1/models` 当前来自本地模型目录，不直接请求上游。这个设计能保证客户端初始化稳定，但上游 OpenAI-compatible 服务经常存在非官方、私有部署、别名、灰度版本或特殊模型名，例如客户端继续请求 `gpt-5.5`，实际需要把某个账号的上游请求转成 `gpt-5.5-pro`、`gpt-5.5pro` 或其他私有模型名。

模型映射不能只改请求体，还必须先有可维护的本地模型事实：

- 模型必须能手动添加，否则账号表单无法选择映射源和映射目标。
- 模型必须能配置价格，否则 usage 返回 token 后无法稳定计算美元成本和额度消耗。
- 管理员添加的是全局模型，面向所有系统账户可见。
- 用户自己添加的是个人模型，只服务自己的账号、API Key 和模型映射配置。
- 后续账号模型映射只允许选择已经存在于本地模型目录的模型，避免随手输入上游模型名导致价格、审计和调度口径断裂。
- 后续 API Key 支持跨供应商分组后，客户端请求模型会成为供应商路由键；因此模型名不能再依赖覆盖式去重，必须先保证全系统客户端模型名唯一。

## 2. 名词

| 名词 | 含义 |
| --- | --- |
| 内置模型 | 代码内置的官方厂商模型目录和官方价格，当前主要是 GPT / OpenAI 官方模型目录。 |
| 全局自定义模型 | 管理员手动添加的模型，作为平台级事实，所有用户可见。 |
| 个人自定义模型 | 普通用户或管理员以某个系统账户身份添加的模型，只在该系统账户作用域可见。 |
| 下游模型 / 请求模型 | 客户端请求体里的 `model`，也是用户在 `/v1/models` 中看到并发起调用的模型 ID。 |
| 上游模型 / 实际模型 | 网关选中某个 AI 账户后，最终发给上游账号的 `model`。 |
| 路由模型 | 用于网关先确定供应商协议档案的客户端模型名。当前与下游模型同名，必须全系统唯一。 |
| 模型映射 | 针对某个 AI 账户，把下游模型精确映射到上游模型，例如 `gpt-5.5 -> gpt-5.5-pro`。 |
| 计价模型 / 基准计价模型 | 后端成本估算使用的模型。发生映射后先定位上游模型；如果该模型配置了 `pricingModel`，再使用 `pricingModel` 指向模型的价格。当前手动维护表单里的“价格模板”不是该字段，只用于回填价格。 |

## 3. 总体原则

- 本地模型目录是 `/v1/models`、账号支持模型、账号测试模型、模型检测候选、使用记录筛选和模型映射下拉的共同来源。
- 模型事实必须显式区分目录模型名、上游实际模型名和计价模型名：`model` 用于下游可见目录，`upstream_model` 用于转发改写，`pricingModel` 只用于成本和能力解释。
- `model` 也是后续跨供应商 API Key 的路由键，必须在全系统维度唯一；唯一性不按供应商、scope 或系统账户放宽。
- 模型映射是账号级能力，不是全局自动改写。不同上游账号可以把同一个下游模型映射到不同上游模型。
- 模型映射只做精确匹配，不做模糊匹配、前缀匹配或自动猜测。
- 账号支持模型是当前账号供应商的下游请求能力边界。调度时先用用户请求的下游模型尝试直接命中支持模型；如果未直接命中，则跳过该账号，不再靠模型映射保留候选账号。账号模型映射只在选中账号后把已允许的 `sourceModel` 改写为 `upstreamModel`。
- 自定义模型如果要进入调度、映射或 `/v1/models` 展示，必须有明确价格口径；未配置价格的草稿模型不能作为可调度模型发布。
- 使用记录必须同时保留下游模型和上游模型，避免排障时只看到被改写后的模型或只看到用户请求模型。
- API Key 和统一授权美元额度按实际计价模型消耗计算；发生模型映射时优先看上游模型是否有 `pricingModel`，否则按上游模型价格计算，未映射时同理回退到下游模型。
- 不把模型映射和自动降级、成本优化、跨供应商 fallback 混在一起；这些属于后续独立能力。

## 4. 模型目录来源与作用域

模型目录按供应商视角聚合三类来源；`providerCode=openai` 是通用 OpenAI-compatible 聚合目录，只读取自身和显式纳入聚合的供应商模型，`providerCode=gpt` 只读取 GPT 自身模型，`providerCode=anthropic` 只读取 Anthropic 自身模型，`providerCode=glm` 只读取智谱 GLM 自身模型，`providerCode=deepseek` 只读取 DeepSeek 自身模型，`providerCode=gemini` 只读取 Gemini 自身模型。DeepSeek 不进入 `openai` 聚合目录；Gemini 模型只归属 `providerCode=gemini`，其中 `profile_gemini_native_v1beta` 使用 Gemini 原生协议，`profile_gemini_openai_chat_v1beta` 使用 OpenAI Chat 兼容协议，文本模型可声明 `chat_completions` 以便 OpenAI Responses / Codex 显式映射到 Gemini OpenAI Chat：

1. 内置模型：所有系统账户可见，来源于代码内置官方目录。
2. 全局自定义模型：管理员添加，所有系统账户可见。
3. 个人自定义模型：当前系统账户添加，只对该系统账户可见。

模型 ID 必须在全系统维度唯一。模型 ID 冲突时不能按个人、全局或内置优先级覆盖，也不能在 `/v1/models` 或选项接口里悄悄去重。具体规则：

- 内置模型之间不能重名；新增或清洗厂商目录时必须先处理冲突。
- 全局自定义模型不能和内置模型、已有全局自定义模型、任何用户的个人自定义模型重名。管理员后添加全局模型时，如果已有用户个人模型同名，必须拒绝保存，不能让全局模型把个人模型挤掉。
- 个人自定义模型不能和内置模型、全局自定义模型、任何用户的个人自定义模型重名。这里不按用户维度放宽，避免未来把模型名作为 API Key 路由键时出现歧义。
- 重复判断使用规范化模型键，至少包含 `trim + lower-case`；后续如增加 `model_key` 字段或表达式唯一索引，也必须使用同一规范化口径。
- `/v1/models` 只输出已确认唯一、启用且可计价的模型；如果运行时发现重名脏数据，应把它视为数据异常并通过离线清洗或重建处理，不在请求链路兜底覆盖。
- `openai` 聚合目录里来自 GPT、GLM、DeepSeek 或其他 OpenAI v1 子供应商的自定义模型会直接出现在聚合页；Anthropic 原生模型不进入 `openai` 聚合目录。可见的自定义模型允许在聚合页发起编辑 / 删除，但后端请求必须按模型自身的来源供应商编码路由，内置模型仍只读。
- 所有目录按 `releaseDate` 发布时间倒序展示，最新模型在前；未填写发布时间的模型排在已填写发布时间的模型之后。
- 自定义模型不再区分“公开目录”和“仅映射目标”；只要在当前作用域内、状态为 `active` 且可解析价格，就进入 `/v1/models`、账号支持模型和账号模型映射下拉。

个人自定义模型不会因为 AI 账户授权自动共享给被授权用户。授权账户如果需要让多个用户稳定使用某个非官方模型，优先由管理员添加为全局自定义模型；如果只能由各用户自行维护，则每个用户都必须使用全系统唯一的客户端模型名，再通过账号级模型映射指向各自上游真实模型。

## 5. 手动添加模型

模型新增 / 编辑表单包含：

| 字段 | 说明 |
| --- | --- |
| `providerCode` | 供应商代码，当前内置 `openai`、`gpt`、`anthropic`、`glm`、`deepseek` 和目标 `gemini`；`openai` 在模型目录维度表示通用 OpenAI-compatible 聚合供应商，协议维度另由 `protocolCode` 表达。 |
| `model` | 模型 ID，必须按上游真实要求精确填写；创建后不可修改。 |
| `scope` | `global` 或 `personal`；管理员创建全局模型，用户创建个人模型。 |
| `status` | `draft`、`active` 或 `disabled`；只有 `active` 且可解析价格的模型进入可用目录。 |
| `mode` | 模型用途，固定对齐页面分类：`text`、`image`、`audio`。 |
| `supportedApiProtocols` | 支持的接口协议，例如 `responses`、`chat_completions`、`messages`、`message_token_counting`、`images`。 |
| `contextWindowTokens` | 可选，上下文窗口 token 数，用于页面提示、账号测试和后续模型检测。 |
| `maxOutputTokens` | 可选，最大输出 token 数，用于页面提示和请求前校验。 |
| `releaseDate` | 可选发布时间，用于排序。 |
| `shutdownDate` | 可选停用日期，到期后不再进入可调度目录。 |
| 价格模板 | 前端临时选择项，选择同用途模型后只回填价格输入框，不保存为模型字段。 |

当前维护表单只展示会影响目录、映射、协议、上下文和计费的字段。模型展示名不单独维护，页面、`/v1/models` 和 Codex `/models` 都直接使用模型 ID。`capabilityNotes`、`notes`、`pricingNotes` 这类备注字段不在模型列表展示，也不作为新增 / 编辑表单填写项；后端和数据库可以保留历史字段，但前端编辑隐藏字段时不提交它们，避免把旧备注误清空。

手动表单里的“价格模板”是前端临时选择项，不落库、不保存为 `pricingModel`，也不代表后续成本直接引用该模型。用户选择模板后，只把同用途模型的直接价格字段回填到当前表单，保存时仍保存为当前模型自己的直接价格。

手动添加的自定义模型默认就是当前作用域内的可见模型；不再提供只用于账号模型映射、但不进入 `/v1/models` 的分类。账号模型映射的上游模型也必须先作为普通自定义模型维护并具备价格。

当前页面入口：

- 管理员后台 `供应商` 页面维护全局模型，也可维护管理员自己账号下的个人模型。
- 用户侧 `模型目录` 页面维护当前登录用户自己的个人模型。
- 账号创建 / 编辑里的 `支持模型` 下拉读取已发布且可公开请求的模型目录；维护弹窗读取时额外包含当前用户可维护的草稿、停用和未定价个人模型。

后端 `pricingModel` 字段用于历史数据、导入数据或后续高级入口，解决 Azure deployment、自定义部署名、日期版本模型或上游私有模型名与真实价格模型不一致的问题。它只参与价格和上下文解释，不参与 `/v1/models` 输出、不参与调度改写，也不能改变上游实际收到的 `model`。

后端 `pricingModel` 校验规则：

- 必须指向同供应商内已经存在且有直接价格的模型；第一版只解析一跳，不允许 `pricingModel -> pricingModel` 递归。
- 全局自定义模型只能指向内置模型或全局自定义模型；个人自定义模型可以指向自己可见的内置、全局或个人模型。
- 目标模型必须是当前作用域内可见、启用且可解析直接价格的模型，不能是停用、草稿或价格缺失模型。
- 第一版不允许同一模型同时使用直接价格和 `pricingModel` 代理；如果需要特殊套餐价或倍率，直接填写最终价格。
- 不允许把 `pricingModel` 指向明显更便宜但不等价的模型来绕过额度；价格来源、套餐或部署依据如果需要留档，应记录在外部变更说明或功能文档中，不放入当前模型维护表单。
- 当前手动表单保存时提交直接价格，并把 `pricingModel` 提交为 `null`；如果原模型历史上使用 `pricingModel`，编辑时会尝试按该目标模型回填价格模板，保存后转为当前模型自己的直接价格。备注类隐藏字段不随页面编辑提交。

自定义模型保存后应进入模型目录缓存。创建、更新、停用、删除或价格变化都必须失效：

- 供应商模型列表缓存。
- `/v1/models` 响应缓存。
- 前端账号表单模型选项缓存，避免用户新建或编辑个人模型后，新增账户弹窗继续展示旧下拉。
- 模型映射下拉选项缓存。
- 成本估算价格缓存。

## 6. 自定义价格

自定义模型发布前必须能解析到价格口径。当前手动维护以直接保存价格字段为准，用户可以选择“价格模板”回填同用途模型价格，但最终保存的是当前模型自己的直接价格。直接价格字段与现有 OpenAI 价格结构保持同一语义：

| 字段 | 说明 |
| --- | --- |
| `inputUsdPer1M` | 每 100 万输入 token 美元价格。 |
| `outputUsdPer1M` | 每 100 万输出 token 美元价格。 |
| `cachedInputUsdPer1M` | 每 100 万缓存命中输入 token 价格，可为空，空值默认按输入价格。 |
| `cacheWriteUsdPer1M` | 缓存写入价格，可为空。 |
| `imageInputUsdPer1M` | 图片输入 token 价格，可为空。 |
| `imageOutputUsdPer1M` | 图片输出 token 价格，可为空。 |
| `audioInputUsdPer1M` | 音频输入 token 价格，可为空。 |
| `audioOutputUsdPer1M` | 音频输出 token 价格，可为空。 |
| `outputUsdPerImage` | 按张计费的图片输出价格，可为空。 |
| `currency` | 第一版固定为 `USD`。 |

维护页面按模型用途只展示实际需要填写、且会在列表中展示的价格项：

| 用途 | 表单展示价格项 | 列表展示 |
| --- | --- | --- |
| `text` 对话 / 编码 | 输入价格、输出价格、缓存读取价格、缓存写入价格 | `计费`、`缓存写入` |
| `image` 图像 | 图片输入价格、图片输出价格、每张图片价格 | `图片 token 价格`、`每张价格` |
| `audio` 音频 | 音频输入价格、音频输出价格 | `音频 token 价格` |

选择“价格模板”时，直接价格字段仍然展示；模板只把同用途的直接价格复制到输入框，用户可以继续修改。保存只提交当前用途对应价格，非当前用途价格提交为 `null`，并把 `pricingModel` 清空，避免旧引用或旧用途价格继续参与计费。

第一版不引入 one-api / new-api 那类复杂倍率体系，也不引入按用户组、渠道类型、倍率表达式、tiered expression 自动计算。模型价格或 `pricingModel` 指向价格就是美元成本估算的直接来源；如果上游返回 usage 但本地没有可用价格，使用记录仍写 token，但成本字段为空，并在审计和运行日志中标记为 `model_price_missing`。

为了保障额度判断，账号模型映射选择的上游模型必须能解析到可用价格；否则后端拒绝保存映射。手动维护的普通自定义模型如果未填写直接价格，只能保存为草稿，不进入 `/v1/models`，也不能被账号支持模型或模型映射选择；后端高级 `pricingModel` 只作为历史、导入或后续高级入口的计价解析能力。

## 7. `/v1/models` 展示口径

`GET /models` 和 `GET /v1/models` 继续由本地模型目录返回，不请求上游账号。

OpenAI v1 档案下的对外响应必须符合 OpenAI List models 标准格式，只暴露兼容字段。契约以 [OpenAI OpenAPI `GET /models`](https://api.openai.com/v1/models) / 官方 API Reference 的 List models 响应为准：

```json
{
  "object": "list",
  "data": [
    {
      "id": "gpt-5.5",
      "object": "model",
      "created": 1776902400,
      "owned_by": "openai"
    }
  ]
}
```

字段约束：

- 顶层 `object` 固定为 `list`。
- 顶层 `data` 固定为数组。
- 每个模型项只输出 `id`、`object`、`created`、`owned_by`。
- 模型项 `object` 固定为 `model`。
- `created` 使用 Unix 秒整数；内置模型优先使用发布日期，自定义模型优先使用 `releaseDate`，否则使用创建时间，无法确认时为 `0`。
- 内置 OpenAI / GPT 模型 `owned_by = openai`；内置 GLM 模型使用本地目录约定的独立归属值，但不影响路由判断；全局和个人自定义模型 `owned_by = juhe-ai`。
- 不向 `/v1/models` 暴露 `model`、价格字段、`scope`、`pricingModel`、能力说明、备注或个人归属信息。

Anthropic native 档案下的 `/v1/models` 使用 Anthropic 模型列表形态，顶层为 `data`，并可包含 `has_more`、`first_id`、`last_id`。模型项保留 Anthropic native 字段，不改写成 OpenAI `object=list` 响应；OpenAI v1 分组不能通过 `/v1/messages` 获取 Anthropic 模型列表。

响应目录按 API Key 调用方的系统账户作用域生成：

- 包含内置模型。
- 包含管理员发布的全局自定义模型。
- 包含调用方自己的个人自定义模型。
- 不包含其他用户的个人自定义模型。
- 不包含 `draft`、`disabled` 或价格不可解析的模型。
- 不按账号支持模型过滤，保持客户端初始化稳定。

模型路由落地后，`/v1/models` 返回调用方可见且全系统唯一的公开模型目录，不按 API Key 当前绑定分组逐个过滤。API Key 是否能实际调用某个模型，由网关在请求时用模型路由结果和该 Key 绑定的目标供应商分组共同判断。

## 8. 模型路由与 API Key 跨供应商号池

跨供应商 API Key 的目标是让调用方继续只持有一个本地 Key，但能按请求 `model` 自动进入 GPT、Anthropic、GLM、CC 等不同供应商分组。路由事实只来自模型目录和请求端点能力，不从客户端 `User-Agent`、账号列表或上游 base URL 猜测供应商。

GLM 有两个 OpenAI v1 档案：`profile_glm_general_openai_v1` 和 `profile_glm_coding_openai_v1`。模型目录必须能把公开模型路由到明确档案；如果同一个模型 ID 同时存在于通用 GLM API 和 GLM Coding Plan，产品层需要选择默认路由档案，或者通过两个全系统唯一的客户端模型别名分别路由，不能让同一个 `model` 同时命中两个 `provider_protocol_profile_id`。

DeepSeek 当前只有一个 OpenAI v1 档案：`profile_deepseek_openai_v1`。DeepSeek 模型只声明 `chat_completions` 能力，不声明 Responses、Anthropic Messages、FIM 或 Chat Prefix beta 默认能力。旧别名 `deepseek-chat` 和 `deepseek-reasoner` 如果进入目录，只能作为历史兼容别名并标注退役日期；新建账户、账户测试和模型检测默认使用 `deepseek-v4-flash` 或后续官方推荐模型。

Gemini 当前有两个档案：`profile_gemini_native_v1beta` 和 `profile_gemini_openai_chat_v1beta`。前者使用 Gemini 原生 `generateContent` / `streamGenerateContent` / `countTokens`，不参与 OpenAI / Anthropic 协议互转；后者使用 Gemini 官方 OpenAI Chat compatibility，默认 Base URL 为 `https://generativelanguage.googleapis.com/v1beta/openai`，只承接 `chat_completions` 直连和 `responses -> chat_completions` 显式映射。Codex 使用 Gemini 时走 `responses -> chat_completions` 到 Gemini OpenAI Chat；不支持 Anthropic Messages 到 Gemini，也不支持 OpenAI Chat / Responses 转 Gemini native。

Anthropic 使用独立 `profile_anthropic_anthropic_v1`，模型路由不能把 Claude 模型无声明地路由到 OpenAI v1 Chat / Responses 分组，也不能让 OpenAI v1 模型无声明地承接 Anthropic `/v1/messages`。OpenAI Chat / Responses 下游请求如果要命中 Anthropic Messages 分组，必须通过目标模型或账号模型映射明确进入 `chat_completions|responses -> messages` 桥接；Anthropic Messages 下游请求如果要命中 OpenAI Chat-only 分组，必须通过账号模型映射明确进入 `messages -> chat_completions` 桥接。请求路径、模型路由结果和桥接能力必须共同收敛到同一个 `provider_protocol_profile_id`。

模型路由索引建议在网关运行时保存为紧凑 Map：

```ts
type ModelRouteIndex = {
  exact: Map<string, ModelRouteTarget>
}

type ModelRouteTarget = {
  providerCode: string
  providerProtocolProfileId: string
  upstreamModel: string
}
```

请求热路径：

1. 解析请求体顶层 `model`。
2. 规范化模型名，使用 `exact.get(modelKey)` 做 O(1) 查找。
3. 命中后得到目标 `providerProtocolProfileId`。
4. 从当前 API Key 的 active 分组绑定中筛出同 `providerProtocolProfileId` 的分组。
5. 在筛选后的分组内继续执行主备、轮询或权重策略。
6. 选中账号后再应用账号级模型映射，把下游模型改写为该账号的上游模型。

错误语义：

- 模型不存在、停用、未定价或不在调用方可见目录中：返回本地模型不可用错误，不进入账号调度。
- 模型可路由，但当前 API Key 没有绑定目标供应商分组：返回本地号池未绑定错误，提示为该供应商配置分组。
- 请求缺少 `model`，且无法从路径或请求体安全提取模型：按当前模型过滤错误处理，不猜供应商。

模型路由索引不能在每次请求里遍历全部供应商模型构建。它应随模型目录、供应商档案或自定义模型变更失效并重建；API Key 绑定变化只影响候选分组，不需要重建模型索引。

## 9. 账号模型映射

账号模型映射配置在 AI 账户上，属于上游资源事实。建议存储为：

| 字段 | 说明 |
| --- | --- |
| `account_id` | AI 账户 ID。 |
| `source_model` | 客户端请求模型，必须存在于账号所有者可见的对应协议客户端模型池；OpenAI Chat / Responses 来源使用 OpenAI 协议模型池，Anthropic Messages 来源使用 Anthropic 协议模型池。 |
| `source_endpoint_family` | 客户端请求协议族，当前为 `chat_completions`、`responses` 或 `messages`。 |
| `upstream_model` | 上游实际模型；专用 OpenAI 协议供应商必须存在于当前供应商模型目录，通用 OpenAI-compatible 账号可来自 OpenAI 协议模型池。 |
| `upstream_endpoint_family` | 上游协议族，当前为 `chat_completions`、`responses` 或 `messages`。 |
| `enabled` | 是否启用。 |
| `created_at` / `updated_at` | 维护时间。 |

约束：

- 主键建议为 `account_id + source_model + source_endpoint_family`。
- 同一账号中同一个 `source_model + source_endpoint_family` 只能映射到一个上游模型和上游协议。
- `source_model` 可以是 GPT/Codex 等客户端可见模型名，也可以是 DeepSeek、GLM 或用户自定义 OpenAI-compatible 模型名；它只表达客户端请求，不表达当前账号所属供应商。
- `upstream_model` 代表真实上游账号会收到的模型名。DeepSeek、GLM、GPT 等专用供应商必须选择当前供应商模型目录；通用 `openai` 兼容账号可选择 OpenAI 协议模型池。
- 如果账号配置了 `supportedModels`，每条映射的 `upstream_model` 必须命中 `supportedModels`；`source_model` 不受 `supportedModels` 限制。
- 允许白名单式协议转换：OpenAI 协议档案内的 `responses -> chat_completions`、真实 Responses 上游的 `chat_completions -> responses`、PLAN-0058 定义的 `chat_completions|responses -> messages`，以及 PLAN-0064 定义的 `messages -> chat_completions`。`upstream_endpoint_family = responses` 只允许账号真实接口能力包含 `responses_json` 或 `responses_sse` 的 OpenAI/GPT 原生上游；其中 `responses -> responses` 是原生直连，`chat_completions -> responses` 是本地桥接后还原 Chat 响应形态。Chat-only、Messages 或未知兼容上游不能选择右侧 Responses；Anthropic Messages 到 OpenAI 只允许显式 `messages -> chat_completions`，不支持 `messages -> responses`；Gemini OpenAI Chat 档案是例外收口，只允许 Chat 直连或 `responses -> chat_completions`，禁止 `messages -> chat_completions`。
- 模型映射只表达“请求应发往哪个上游模型 / 协议族”，不代表 hosted/native 工具能力自动可用。上游供应商或当前模型不支持的能力必须走通用 agent guidance，不伪造执行结果，不把能力缺口返回成 500；请求非法、权限越界、状态链损坏或 schema 校验失败才走本地协议错误。
- 映射链不做递归解析，`source_model -> upstream_model` 一跳结束，避免循环和排障复杂度。
- 如果 `source_model === upstream_model` 且 `source_endpoint_family === upstream_endpoint_family`，不保存映射行。

协议互转矩阵：

| 下游协议族 | 上游协议族 | 状态 | 说明 |
| --- | --- | --- | --- |
| `chat_completions` | `chat_completions` | 支持 | OpenAI-compatible 原生 Chat 或同协议模型映射。 |
| `responses` | `responses` | 仅原生支持 | 账号 `supported_endpoint_modes` 必须包含 `responses_json` 或 `responses_sse`，用于 GPT / OpenAI 原生或明确支持 Responses 的上游。 |
| `responses` | `chat_completions` | 支持 | Responses 客户端请求转 Chat-only 上游，由本地 bridge 承接。 |
| `chat_completions` | `responses` | 支持范围内 | 仅允许真实支持 Responses 的 OpenAI/GPT 原生上游；本地桥接把 Chat 请求转为 Responses，并把 Responses 输出还原成 Chat Completion。Chat-only、Messages 或未知兼容上游仍禁止。 |
| `chat_completions` | `messages` | 支持 | OpenAI Chat 请求显式桥接到 Anthropic Messages。 |
| `responses` | `messages` | 支持 | OpenAI Responses 请求显式桥接到 Anthropic Messages。 |
| `messages` | `chat_completions` | 支持范围内 | Anthropic Messages 请求显式桥接到 OpenAI Chat Completions；只允许真实 Chat 上游，不伪造 server tool / MCP / thinking 等能力。 |
| `messages` | `responses` | 禁止 | Anthropic Messages 不合成 OpenAI Responses；需要 Responses 能力时必须使用真实 Responses 上游或客户端 agent 自行切换。 |

Gemini 额外限制：`profile_gemini_native_v1beta` 不进入上表互转；它只承接 Gemini 原生请求。`profile_gemini_openai_chat_v1beta` 虽然是 OpenAI v1 档案，但只允许 OpenAI Chat 直连和 `responses -> chat_completions`，不允许 Anthropic Messages 来源映射。

示例：

```text
账号 A：
- 支持模型：gpt-5.5
- 模型映射：gpt-5.5 -> gpt-5.5-pro

客户端请求：
- model = gpt-5.5

网关行为：
- 调度阶段先按 `gpt-5.5` 判断账号 A 是否支持；只有请求模型命中支持模型或账号不限制模型时，账号才进入候选。
- 选中账号 A 后，把上游请求体顶层 model 改为 gpt-5.5-pro。
- 使用记录保存 requestedModel = gpt-5.5，upstreamModel = gpt-5.5-pro。
- 成本按 gpt-5.5-pro 的价格计算；如果 gpt-5.5-pro 配置了 pricingModel，则按其指向模型价格计算。
```

## 10. 网关链路

模型路由和模型映射后的主链路固定为：

1. 读取 API Key，确定调用方系统账户和候选分组。
2. 解析请求体顶层 `model`，得到下游模型。
3. 通过模型路由索引定位目标供应商协议档案，并筛选当前 API Key 绑定的同档案分组。
4. 在目标分组集合内按 API Key 路由策略选择候选号池。
5. 按请求路径、账号类型、客户端能力和账号支持模型过滤候选账号；支持模型非空时，请求模型必须直接命中 `supportedModels`，模型映射不参与候选保留。
6. 完成会话亲和、IP 回避、本地屏蔽、授权额度和账号排序。
7. 选中具体 AI 账户。
8. 在账号运行时快照里查 `source_model` 对应的 `upstream_model`。
9. 如果未命中映射，保持原始 `model`。
10. 如果命中映射，只改写 JSON 请求体顶层 `model`，不重构整个请求对象，不删除未知字段。
11. 上游响应默认透传，不默认把响应体中的模型名改回下游模型。
12. 使用记录和审计同时记录下游模型、上游模型、模型路由目标、是否命中映射和账号 ID。

如果请求体不是 JSON、JSON 非法、缺少 `model` 或请求体过大导致无法安全改写：

- 账号支持模型过滤只按下游请求模型是否直接命中处理；模型映射不参与候选保留。
- 命中需要改写的映射时，网关返回本地请求错误，不把无法改写的请求继续发给上游，避免用户以为已经映射但实际上游收到原模型。
- 未命中映射时继续按原透传规则处理。

## 11. 使用记录与审计

使用记录建议新增或明确这些字段：

| 字段 | 说明 |
| --- | --- |
| `model` | 保留当前语义，记录下游请求模型，兼容现有筛选和统计。 |
| `upstream_model` | 发生映射后记录实际上游模型；未映射时可为空或等于 `model`。 |
| `pricing_model` | 本次实际用于价格查找的模型；等于 `upstream_model`、`upstream_model.pricingModel`、`model` 或 `model.pricingModel`。 |
| `model_route_provider_code` | 可选，本次模型路由命中的供应商代码，用于排障跨供应商 API Key。 |
| `model_route_profile_id` | 可选，本次模型路由命中的供应商协议档案。 |
| `model_mapping_applied` | 是否命中账号模型映射。 |
| `model_mapping_source` | 映射来源，第一版固定为 `account`。 |

成本估算优先级：

1. 如果发生映射且 `upstream_model` 对应模型配置了 `pricingModel`，按该 `pricingModel` 指向模型计算。
2. 如果发生映射且 `upstream_model` 有直接价格，按 `upstream_model` 计算。
3. 未映射时，如果 `model` 对应模型配置了 `pricingModel`，按该 `pricingModel` 指向模型计算。
4. 未映射且 `model` 有直接价格时，按 `model` 计算。
5. 如果价格缺失，token 照常写入，成本为空，并记录 `model_price_missing`。

授权账户或授权分组发生账号模型映射时，价格目录按资源账号所有者作用域解析，而不是按调用方个人目录解析。资源所有者的个人上游模型只能在所有者作用域内维护和解析，不会自动进入被授权调用方的 `/v1/models`。

前端使用记录默认展示下游模型，详情中展示上游模型和映射标记。统计聚合的模型维度默认仍按下游模型聚合，成本按每条使用记录已计算的美元成本累加，避免同一个下游模型映射到不同上游模型时丢失真实成本。

## 12. 页面与接口

### 管理员全局模型

管理员后台 `供应商` 页面用于维护全局自定义模型：

- 列表：查看内置模型、全局自定义模型和当前目标用户可见的个人模型；默认目标用户为当前管理员自己，可切换到其他系统账户查看该用户拥有的个人模型。
- 新增：添加全局自定义模型和价格。
- 编辑：调整全局自定义模型状态、协议、上下文和价格。
- 停用：从 `/v1/models` 和账号表单选项中移除，但保留历史使用记录可解析价格。
- 删除：只允许删除未被 AI 账户支持模型、账号映射、检测任务或历史记录引用的自定义模型；否则必须先解除绑定或停用。

### 用户个人模型

用户侧 `模型目录` 页面用于维护个人自定义模型：

- 只能影响自己的模型目录、账号表单、账号映射和 API Key `/v1/models`。
- 用户对自己创建的个人自定义模型有新增、编辑和删除权限；模型 ID 创建后不能修改，需要更名时应新建模型并停用或删除旧模型。
- 不能覆盖、删除或创建同名全局自定义模型。
- 如果个人模型已被未删除 AI 账户的支持模型或账号模型映射引用，不能删除，必须先从账户配置中解除绑定。
- 如果模型 ID 与内置、全局或任意个人模型冲突，后端必须拒绝保存并返回中文冲突提示。
- 普通用户维护视图只能额外看到自己的草稿、停用和未定价个人模型；管理员的全局草稿、停用和未定价模型不向普通用户暴露。

### 管理 API

`GET /__aisys__/api/providers/:code/models` 默认返回当前登录用户可见、启用且可计价的可请求目录。管理员可传 `systemAccountId` 按目标系统账户生成目录；未传时按管理员自己的系统账户生成，普通用户传入该参数会被忽略。维护页面使用：

- `includeInactive=true`：额外返回可维护的 `draft` 和 `disabled` 模型。
- `includeUnpriced=true`：额外返回可维护的未定价草稿或未发布模型。

权限边界：

- `POST /__aisys__/api/providers/:code/models` 创建自定义模型；普通用户只能创建 `personal`，管理员可以创建 `global`。
- `PATCH /__aisys__/api/providers/:code/models/:id` 更新自定义模型；全局模型只允许管理员更新，个人模型只允许所有者更新；只允许更新状态、协议、上下文和价格等可变字段，提交不同模型 ID 时返回 `400`。
- `DELETE /__aisys__/api/providers/:code/models/:id` 删除自定义模型；权限同更新；如果模型已被未删除 AI 账户的支持模型、账号模型映射下游模型或上游模型引用，返回 `409`，必须先解除账户绑定。
- 内置模型只读，不能通过这些接口修改或删除。

### 账号表单

账号表单需要两个模型相关区域：

- 支持模型：选择该账号真实上游可承接的模型边界；选项来自当前账号供应商下、账号所有者可见且可公开请求的模型目录。
- 模型映射：配置客户端模型与协议到上游模型与协议的一跳映射。左侧模型选项根据下游协议族切换：`chat_completions` / `responses` 使用 OpenAI 协议模型池，`messages` 使用 Anthropic 协议模型池；右侧模型选项在专用供应商中来自当前供应商模型目录，在通用 `openai` 兼容账号中来自 OpenAI 协议模型池。

保存账号时，后端必须校验：

- `supportedModels` 中的模型存在于当前账号供应商下、账号所有者可见模型目录。
- 每条映射的 `source_model` 存在于账号所有者可见的对应协议模型池；`chat_completions` / `responses` 来源使用 OpenAI 协议模型池，`messages` 来源使用 Anthropic 协议模型池。
- 每条映射的 `upstream_model` 在专用供应商中存在于当前供应商模型目录，在通用 `openai` 兼容账号中存在于 OpenAI 协议模型池。
- `supportedModels` 非空时，每条映射的 `upstream_model` 必须命中 `supportedModels`。
- 如果账号支持模型为空表示不限制，则允许映射上游模型不在支持模型列表里。运行时调度先在 API Key 已授权账号池内匹配 `source_model + source_endpoint_family`，命中账号后再把请求改写为 `upstream_model + upstream_endpoint_family`。

## 13. 非目标

- 不自动从上游 `/models` 同步模型。
- 不用模糊匹配、模型族匹配或前缀匹配把未知模型映射到相近模型。
- 不做模型自动降级、预算降级或智能选便宜模型。
- 不做基于质量阈值、成本阈值、prompt 分类或用户画像的自动模型路由。
- 不做无声明的跨协议转换型 router；跨供应商 API Key 只在模型已经能唯一定位供应商协议档案，且请求可被原生能力或白名单式显式桥接能力承接时生效。
- 不做复杂倍率、渠道倍率、用户组倍率或表达式计费。
- 不把个人自定义模型自动共享给被授权用户。
- 不默认改写上游响应体中的 `model` 字段。

| [Portkey conditional routing](https://portkey.ai/docs/product/ai-gateway/conditional-routing) | 可按请求参数里的 `model` 做别名路由，并用 `override_params.model` 覆盖目标模型；这是比静态映射更重的路由能力。 | 第一版只做精确一跳映射，不引入条件路由、用户画像路由或多策略配置。 |

如果后续要做智能模型路由、自动降级或成本优化路由，必须先补独立设计并满足这些前置条件：

- 有离线评测集、线上抽样数据和成本-质量指标，不能只按模型名或价格排序。
- 支持灰度、回滚、每用户或每 API Key 显式开关，不能默认替换用户请求模型。
- 使用记录必须记录路由策略、候选模型、最终模型、质量阈值、成本阈值和是否触发升级 / 降级。
- 计费仍按最终实际上游模型或其 `pricingModel` 计算，不能按用户请求的便宜别名结算。

## 15. 自审清单

落地实现前后都要检查：

- `/v1/models` 是否能返回当前 API Key 调用方可见的内置、全局和个人模型。
- 模型 ID 是否在全系统维度唯一，且不再通过个人 / 全局 / 内置优先级覆盖解决冲突。
- 模型路由索引是否能按规范化模型名 O(1) 查到供应商协议档案。
- `/v1/models` 是否只返回 OpenAI 标准字段：顶层 `object/data`，模型项 `id/object/created/owned_by`。
- 账号支持模型是否仍只按下游请求模型过滤；启用的账号模型映射只在选中账号后改写请求体，不作为候选保留规则。
- 账号映射是否只在选中账号后应用，避免映射影响候选账号选择。
- 请求体改写是否只改顶层 `model`，没有重构未知字段。
- 映射上游模型是否必须有价格，避免额度和成本为空。
- `pricingModel` 是否只用于价格和上下文解释，没有影响上游请求体。
- 使用记录是否同时保存下游模型、上游模型和实际计价模型。
- 成本是否按 `upstream_model.pricingModel -> upstream_model -> model.pricingModel -> model` 的顺序解析。
- 自定义模型停用后是否不影响历史使用记录查看和成本解释。
- 个人自定义模型是否不会泄露到其他用户的 `/v1/models`。
- 管理员全局模型和用户个人模型的重名冲突是否在保存时被后端拒绝。
