# 使用记录延迟健康分档与输出吞吐展示设计

## 背景与目标

使用记录列表的「延迟」列如果只渲染灰度纯文本，「用量」列只渲染纯文本数字，逐行扫视时无法快速分辨哪些请求慢、哪些请求吞吐异常。本设计为列表补三组纯前端呈现能力：

1. 延迟健康度分档：首字与总耗时各自独立分档，文字按档位着色，行首竖向渐变色条同时编码两个档位，支持纵向扫视；
2. 输出吞吐（t/s）：每条记录直接给出「输出 Token ÷ 总耗时」的每秒吞吐，替代人工心算；
3. 压缩请求识别与标记：Codex 压缩请求天然长耗时（上传超大上下文、输出极短），按普通阈值分档会全部染红失真；列表识别显式压缩请求、打「压缩」标记并切换到压缩专用分档。

## 可见行为契约

### 延迟列（管理侧与我的使用记录共用）

单元格为「色条 + 三行两列标签值」结构：

| 行 | 标签 | 值 | 着色 |
| --- | --- | --- | --- |
| 1 | 首字 | `firstTokenMs` 经共享时长格式化 | 普通记录按首字档着色；压缩记录中性色不看档；缺失时 `-`（灰） |
| 2 | 总耗时 | `durationMs` 经共享时长格式化 | 按总耗时档着色（压缩记录用压缩档阈值） |
| 3 | TPS | 见下节口径 | 中性色，不参与健康度着色 |

分档阈值（毫秒，达到即归档；低于 warn 为 good）：

| 档位 | 首字（TTFT） | 总耗时（普通） | 总耗时（压缩） |
| --- | --- | --- | --- |
| good（`--juhe-latency-good`/`-good-text`） | < 10s | < 30s | < 2min |
| warn（`--juhe-latency-warn`/`-warn-text`） | ≥ 10s | ≥ 30s | ≥ 2min |
| slow（`--juhe-latency-slow`/`-slow-text`） | ≥ 30s | ≥ 60s | ≥ 4min |
| critical（`--juhe-latency-critical`/`-critical-text`） | ≥ 60s | ≥ 120s | ≥ 6min |

分档色为 sub2api 同款明亮色阶（色条 500 系、文字 600 系，2026-10-23 用户裁决引入，登记于前端样式规范 §6.1 令牌表与例外清单）；不使用主题低饱和语义色（`--juhe-ok` 系偏暗，扫视对比不足）。

取舍说明：

- 普通记录总耗时阈值收紧到 30/60/120s（大于 30s 即偏慢），判定失真由同格展示的输出 TPS 兜底区分——「慢但 t/s 正常」是长输出的健康慢，「慢且 t/s 低」才是真慢；
- 压缩记录首字不参与分档与着色：压缩需先对超大上下文做预填充，首字天然长，看了只会误判；只按总耗时（2/4/6min 档）判读，色条退化为总耗时档纯色。

**渐变色条**：宽约 4px 的竖向圆角条，40%–60% 高度区间做线性过渡。普通记录有首字数据时，上端纯色为首字档颜色、下端纯色为总耗时档颜色（`linear-gradient(to bottom, from色 0 40%, to色 60% 100%)`）；无首字数据时上下同色，退化为总耗时档纯色条；**压缩记录上端固定浅紫、下端为压缩总耗时档紫**（时间越久紫越深），紫色即压缩身份。色条纯装饰（`aria-hidden`）。

**输出 TPS 口径**（列表标签为 `TPS`）：`outputTokens × 1000 ÷ durationMs`，固定一位小数，后缀 ` t/s`；分母是含首字等待的完整耗时（输出可能含推理 Token，该口径偏保守且与 AI 性能监控的完整耗时口径一致）。以下情况显示 `—`：媒体计量记录、`outputTokens` 缺失或 ≤ 0、`durationMs` 缺失或 ≤ 0。

### 压缩请求识别

- **识别口径（权威）**：用量记录携带后端字段 `compactionExpected`——请求进入网关时由单点判定 `CodexCompactionExpectedForRequest`（gatewaycodex/compactioncontract.go：`/responses/compact` 路径，或 `/responses` 请求体含内联压缩触发器）冻结进请求级上下文，随用量记录链（gateway `UsageRecordInput` → spool JSON → jobs `usagewriter` 落列 `compaction_expected` → 列表 API `compactionExpected`）透传；内联压缩触发器形态自此可识别。
- **历史行回退**：字段上线前写入的存量记录无该列值（默认 0），前端识别保留 endpoint 推断（`POST` + 路径以 `/responses/compact` 结尾）作为存量行回退，不做数据回填。
- **标记（2026-10-23 用户裁决）**：压缩识别由**紫色渐变色条**承担，不再使用模型列 tag——压缩记录色条为「固定浅紫顶（`--juhe-latency-compaction-light`）→ 压缩总耗时档紫底」的渐变，紫色即身份、紫的深浅即耗时档（< 2min `#c084fc`、≥ 2min `#a855f7`、≥ 4min `#9333ea`、≥ 6min `#7e22ce`）；首字数值保持中性色。

### 用量列（对话记录）

对话记录改为三行图标行，每行一个维度、行首彩色图标（图标取自 sub2api 同款 heroicons 线稿）：

- 第 1 行：下箭头（`--juhe-ok-strong` 图标重点绿）+ 输入 Token 千分位；
- 第 2 行：上箭头（`--juhe-violet-strong` 图标重点紫）+ 输出 Token 千分位；
- 第 3 行（仅 `cacheReadTokens > 0` 时）：档案盒图标（`--juhe-accent-strong` 图标重点青）+ 缓存读缩写（≥1M 显示 `X.XM`、≥1K 显示 `X.XK`、其余千分位）。

图标重点色（`--juhe-ok-strong` / `--juhe-accent-strong` / `--juhe-violet-strong`）是主题令牌的加饱和档（同色相、小面积图标级强调专用，登记于前端样式规范 §6.1），数字保持墨色主文字不变色。

媒体计量记录（音频 token / TTS 字符 / 音秒 / 视频秒任一非零）保持现有文本行展示，不套图标。

### 移动端卡片

「更多字段」展开区的「延迟」摘要为三行：首字、总耗时、TPS（TPS 不可用时省略该行），复用与表格同一组格式化函数；标签行追加「压缩」tag。

## 非目标

- 不做缓存写入 5m/1h 明细徽标（列表类型未返回 `cacheWriteTokens`，成本明细浮层已有该拆解）;
- 不做 Token / 成本悬停明细浮层（成本明细浮层已存在，行为不变）；
- 不调整延迟列排序与筛选能力（该列本就不参与排序）；
- 不回填存量记录的压缩标记（存量行由前端 endpoint 推断回退覆盖）；
- 网关桥接合成的压缩摘要上游调用不是独立请求记录，其耗时并入主请求，不单独归因。

## 实现落点

前端：
- `frontend/src/views/usage-records/usageRecordLatencyHealth.ts`：普通 / 压缩两套总耗时阈值与分类函数、档位 → 主题 CSS 变量映射、色条渐变 CSS 变量（感知压缩）；
- `frontend/src/views/usage-records/usageRecordFormatters.ts`：新增缓存读缩写 `formatCacheTokens`、压缩识别 `usageRecordIsCompaction`（`compactionExpected` 字段为主、endpoint 推断回退存量行）与 TPS 格式化 `formatUsageOutputTps`（媒体计量判断复用本文件既有函数，避免与健康度模块互相依赖）；`usageRecordLatencySummaryParts` 输出「首字 / 总耗时 / TPS」三行；
- `frontend/src/views/usage-records/UsageRecordsTable.vue`：延迟列与用量列模板及配套样式、模型列「压缩」tag；
- `frontend/src/views/usage-records/UsageRecordMobileCard.vue`：延迟摘要与「压缩」tag；
- `frontend/src/types/domain/usage-records.ts`：`UsageRecordSummary` / `UsageRecordListItem` 增加 `compactionExpected`。

后端（压缩标记透传链）：
- gateway 请求侧：压缩判定在 preflight 早期以原始谓词 `CodexCompactionExpectedForRequest` 单点求值并冻结进请求级用量上下文（早于 strategy 解析；主环、engine 失败分支、response 层失败与 RouteAction 失败全部同源。strategy Opaque 上的 `CodexCompactionExpected` 带 `codexTurn != nil` 门，只作 keepalive/超时豁免口径，不作识别口径），主环 `chainFinalizationUsage` 与失败用量上下文把该值注入 `gatewayusage.UsageRecordInput.CompactionExpected`（models / media / realtime 流量天然 false）；
- spool 交接：字段加在 gateway `gatewayusage/records.go` 与 jobs `usagewriter/records.go` 两份镜像结构（同名 json tag），经 spool JSON 往返自动穿透；
- 落库：jobs `usagewriter` `UsageRecordColumns` / INSERT 参数同位加 `compaction_expected`（integer NOT NULL DEFAULT 0，SQLite/PG 同名同型），存量 SQLite 分片由 `openShardDB` PRAGMA 守卫幂等补列；
- schema：jobs `UsageShardBaseSchemaSQL` 与 maintenance `sqlite_usage_shard.go`（逐字镜像 + golden 67→68）、`pg_schema_usage.go`（`ADD COLUMN IF NOT EXISTS compaction_expected integer NOT NULL DEFAULT 0`，生产随发版 `--ensure-schema` 生效）、mockdata `usageRecordColumns` 镜像同位加列；
- 列表 API：gateway `statreads/usagerecords.go` SELECT 列、行映射与响应 DTO 透出 `compactionExpected`。
