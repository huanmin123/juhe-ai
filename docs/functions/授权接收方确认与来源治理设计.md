# 授权接收方确认与来源治理设计

> **状态：本地实现完成（2026-11-21），待统一上线验证；生产尚未发布。**
>
> 本文定义统一授权生命周期、接收方确认、所有者确认、目标分组绑定、团队展开、来源治理和分组授权范围快照的现行契约。代码、schema revision 28、前端授权中心和帮助文档已按本文在本地落地；真实 PostgreSQL 升级、生产存量盘点和 §13 全量验收尚未执行，执行窗口与上线后事项登记在 [待办与阻塞事项](../待办与阻塞事项.md) T215。
>
> 本文的“必须 / 不得 / 只能”是实现与验收口径。2026-11-20 复审已修正暂停推导、pending/needs_review 接受、多来源回退、团队聚合、团队+分组组合、通用接口代绑定、`source_revision` 覆盖、迁移回滚和若干事实错误；2026-11-21 本地实现复核又补齐了发起授权入口、管理员团队审批入口、通知阅读和授权发起暂停 UI。

## 1. 结论与范围

### 1.1 要解决的问题

改造前的授权是资源所有者单方面发起并立即生效：授权方在创建个人授权时替接收方选择目标分组，后端立即在接收方名下创建 active 授权实例并写入 `group_accounts`；团队授权则自动为每个成员创建实例并放入成员默认分组。接收方没有事前同意、没有事后有效退出，授权方在授权后仍可通过修改来源账户的 `base_url`、模型、代理、映射和凭据持续控制接收方的实际上游。

这曾使授权从“使用权分享”变成“授权方向接收方调度域单方面写入一个由自己持续控制的执行入口”，可被用于强制注入、流量劫持、批量骚扰和授权方事后换源。本文的实施目标就是消除这条路径。

### 1.2 目标

- 授权创建只产生**待接收方确认的 offer**，不创建 active 运行时、不创建授权实例、不写 `group_accounts`、不进入调度候选。
- 接收方接受后才创建/激活授权实例；**目标分组绑定由接收方在自己的账户/分组页面完成**，授权方不再提交 `targetGroupId`，也不再能查询接收方的分组。
- 管理员代资源所有者创建 offer 必须经**资源所有者确认**；管理员不能代替资源所有者或接收方表达同意。
- 团队授权必须先经**团队审批人**同意，再向每个成员发**成员级 offer**；成员逐人接受后才创建实例或快照，新成员只收 pending offer，不自动继承既有团队授权。
- 来源账户发生 material change 时，相关授权进入 `needs_review`，暂停实际调度，接收方重新确认后才恢复；重新确认必须携带接收方看到的修订号，禁止“接受时是正常账户、接受后换成恶意上游”。
- 归还、拒绝、屏蔽是持久状态；归还按 runtime 是否进入终态停用绑定，重新授权必须重新接受，不能复用旧绑定自动复活。
- 来源优先级从“团队覆盖并永久取消个人”改为“团队生效、个人 dormant、团队结束后可回退”；接收方也可以显式选择不保留个人来源。
- 普通用户不能批量枚举全部用户、全部团队或他人的分组；授权对象改用精确用户名/精确团队名 + 团队审批，取消全量候选下拉。
- 增加 per-grantor 全局限额、per-grantee 上限、offer 速率限制、pending TTL、屏蔽名单和管理员滥用暂停能力，防止批量注入和骚扰。
- 团队+分组资源组合必须保留并完成定义：团队审批、成员逐人接受、每成员快照、成员移除撤销，不得因本次重构丢失现有能力。
- 所有候选加载路径（常规、chat-pinned、媒体、realtime 等）共用同一授权范围、快照和来源修订闸门；不得存在绕过路径。

### 1.3 非目标

- 不改变 `/v1` 对外协议、网关路由层级（API Key -> 路由策略 -> 分组 -> 账户）或供应商/协议面。
- 不改变授权消耗统计的“资源 × 用户”主维度、额度读取口径和价格口径；只调整授权生效前后的关系与可见性。
- 不在本期引入团队自服务成员管理或团队 owner 角色；团队审批人使用 `system_teams.created_by`，失效时由全局管理员代行。成员增删仍由管理员执行。
- 不重新引入分组 `provider_code` 维度。分组在现行架构中无供应商维度；本文只要求纠正“同供应商分组”的错误表述，并在接收方绑定时给出跨供应商提示，不把供应商一致性做成硬约束。
- 不提供“管理员代替接收方接受或绑定”的能力；管理员可以回收、暂停和封禁，但不能代替接收方表达同意，也不能通过通用账户/分组/路由策略接口代绑定。
- 不提供旧授权模型的运行开关或双写；新契约同批替换旧路径。

## 2. 术语与信任边界

| 术语 | 定义 |
| --- | --- |
| 授权方 | 发起 offer 的系统账户；普通场景即资源所有者，管理员代建时是管理员（`created_by`）。 |
| 资源所有者 | 拥有 AI 账户或分组的系统账户；无论 offer 由谁发起，始终可暂停、恢复、延长、缩短或回收自己资源的授权。 |
| 接收方 | 被授权系统账户；团队授权场景下是团队内每个成员。 |
| offer | 授权业务记录 `resource_authorization_grants`，表达“某资源拟授权给某个用户或团队”。offer 未接受前不产生可用授权。 |
| 所有者确认 | 管理员代资源所有者创建 offer 时，资源所有者对“以自己名义发出 offer”的确认；不是接收方同意。 |
| 成员 offer | 团队授权展开后，某个成员对应的来源记录 `resource_authorization_sources`；成员只能处理自己的成员 offer，不能处理团队业务记录。 |
| 最终用户授权 | `resource_authorizations`，某资源对某系统账户的稳定运行时记录；同一资源同一用户全生命周期一条。 |
| 来源 | `resource_authorization_sources`，记录某条最终用户授权当前/历史因为什么成立（`manual` 或 `team`）。 |
| 接受 | 接收方对某个来源明确表达同意；接受只让资源进入接收方可用集合，不自动绑定分组。 |
| 重新确认 | 来源 material change 后，接收方对**新的来源修订**再次表达同意；与首次接受走同一端点，但必须携带 `expectedRevision`。 |
| 绑定（账户） | 接收方在自己的账户/分组页面把授权实例加入自己的普通分组；写入 `group_accounts`。 |
| 绑定（分组） | 接收方把授权分组显式启用（`group_authorization_settings.enabled=1`），再在自己的路由策略中引用该分组。 |
| 接受修订 | `accepted_source_revision`，接收方最后一次明确同意的来源指纹；material change 不得覆盖。 |
| 观察修订 | `observed_source_revision`，系统最近一次计算出的当前来源指纹；material change 时写入。 |
| material change | 会影响流量去向、上游身份或信任边界的变更：`base_url`（含查询串）、供应商/驱动/协议档案、连接 preset/端点模式、代理绑定及代理池成员、支持模型集合、账户入口映射、OAuth 主体标识、API Key 身份指纹等。 |
| 快照修订 | 分组授权当前范围（账户 ID + 各账户接受修订）的稳定哈希；用于刷新范围的 CAS 校验。 |
| 屏蔽 | 接收方对某个授权方或某个资源设置持久拒绝，后续 offer 不再创建。 |
| 团队审批人 | `system_teams.created_by`；其账户不存在、已停用或与授权方为同一账户时，由 `super_admin` / `admin` 代行。 |
| 授权周期 | 同一 grant 下从一次 offer 创建到该来源进入终态的过程；重新发起创建新的来源行，不复用旧终态行。 |
| 范围快照 | 分组授权接受时记录的账户集合及各账户来源修订；新增账户不自动进入已接受范围。 |

信任边界：

- 来源账户的真实上游由授权方控制；接收方必须知道这一点，并在接受前看到来源账户、供应商、当前上游 host、额度和风险提示。
- 接收方拥有自己的分组和调度拓扑；授权方不得直接写入。授权只能让资源进入接收方的“可用授权资源集合”，由接收方决定是否绑定、绑定到哪个分组。
- 团队审批人只决定“团队是否接受这个 offer 进入成员确认流程”，不能代替成员接受；成员保留个人拒绝权。
- 全局管理员是治理角色，不是同意主体；不得代替接收方接受或绑定，也不得绕过资源所有者确认以所有者名义发 offer。
- 精确用户名/团队名仍可能被逐字探测；本文通过全局限额、统一错误、审计和限速提高成本，但不把“完全不可探测”作为安全承诺。更强的邀请码/邀请链接机制可在不改变状态机的前提下后续增加。
- API Key 身份指纹变化属于 material change；OAuth token 刷新但主体标识不变不属于 material change。若某类账户无法取得稳定主体标识，禁止在原账户上更换凭据主体，必须新建账户。

## 3. 目标模型总览

### 3.1 核心原则

1. **Offer, not push**：创建授权只产生 pending offer，不产生任何运行时副作用。
2. **Accept, then bind**：接受与绑定分离；接受不建绑定，绑定不改变授权关系。
3. **Owner consent for admin-created offers**：管理员不能以资源所有者名义单方面发 offer；必须经所有者确认。
4. **Re-consent on material change**：来源 material change 必须重新确认；未确认前不调度；重新确认绑定到接收方看到的修订。
5. **Team is a distribution list, not an auto-provisioner**：团队只负责分发成员 offer；成员逐人接受。
6. **Durable exit**：拒绝、归还、屏蔽持久有效；重新授权不得自动复活旧绑定或旧接受状态。
7. **No cross-tenant enumeration**：普通用户不能批量枚举全量用户/团队/他人分组；精确名探测受全局限额和审计约束。
8. **No admin consent substitution**：管理员不能代替接收方接受或绑定，也不能通过通用账户/分组/路由策略写接口绕过。
9. **One gate for all loaders**：常规、chat-pinned、媒体、realtime 等所有候选加载路径共用同一授权范围、快照和修订闸门；pinned 只能跳过健康可用性，不能跳过授权。
10. **Resource-type explicit**：账户资源和分组资源在 accept、bind、runtime 推导、网关预检、迁移中必须显式分支；不得用同一套“创建实例”逻辑处理分组资源。

### 3.2 分层关系

```text
资源所有者创建 offer（管理员代建时先经所有者确认）
        ↓
接收方接受（来源 active / dormant）；账户资源建实例，分组资源建快照
        ↓
接收方显式绑定（账户实例加入自己的分组；分组授权启用再进路由策略）
        ↓
网关按既有 API Key -> 路由策略 -> 分组 -> 账户 链路调度
```

授权域不直接修改接收方的 `group_accounts`，不把资源塞进接收方的默认分组，也不改变接收方的路由策略。网关仍然只认最终用户授权运行时、授权实例本地状态、分组绑定/分组授权开关和来源账户可用性。

### 3.3 状态分层

| 层 | 表 | 状态 | 作用 |
| --- | --- | --- | --- |
| 业务 offer | `resource_authorization_grants` | `pending_owner_approval` / `pending` / `pending_team_approval` / `pending_member_acceptance` / `active` / `paused` / `expired` / `revoked` / `returned` / `declined` | 授权方/所有者/团队审批人视角的业务生命周期；不直接决定网关可用性。 |
| 接收方来源 | `resource_authorization_sources` | `pending` / `active` / `dormant` / `needs_review` / `revoked` / `returned` / `declined` / `expired` | 每个接收方对某条来源的同意状态；优先级和回退在这一层计算。 |
| 最终用户运行时 | `resource_authorizations` | `pending` / `active` / `needs_review` / `paused` / `expired` / `revoked` / `returned` / `declined` | 网关唯一读取的最终授权状态；由来源和父 offer 状态推导并物化。 |

`resource_authorization_grants.status` 与 `resource_authorizations.status` 不是同一个概念：前者是业务记录，后者是运行时投影。`needs_review` 只出现在来源和运行时层，不作为业务 offer 状态。

### 3.4 资源类型与接收方矩阵

| 资源类型 \ 接收方 | 个人 | 团队 |
| --- | --- | --- |
| AI 账户 | 个人接受后创建授权实例；接收方绑定到自己的分组。 | 团队审批 → 成员逐人接受 → 为接受成员创建授权实例；成员各自绑定。 |
| 分组 | 个人接受后建立范围快照；接收方显式启用后再加入自己的路由策略。 | 团队审批 → 成员逐人接受 → 为接受成员建立各自的范围快照；成员各自启用并加入路由策略。 |

**通用规则：**

- 分组资源只支持普通分组（`group_kind=standard`）；超级分组不是授权资源，创建/接受/迁移均拒绝 `group_kind_conflict`，不得按超级分组成员展开为多个普通分组授权（与 [超级分组设计](超级分组设计.md) “不宣称跨授权边界”一致）。接收方如需使用成员分组，必须分别获得对应普通分组授权。
- 分组资源永远不创建授权实例；账户资源接受后创建授权实例。
- 团队+分组组合是正式支持路径，不得拒绝新写入；团队展开按成员生成来源，每个成员独立快照、独立启用、独立撤销。
- 同一 runtime 可以有多个来源（个人 `manual` + 多个团队 `team`）；授权实例/分组快照只在接受时创建一次，后续来源变化只重算 runtime，不重复创建。

## 4. 状态机与推导规则

### 4.1 个人授权状态机

| 当前状态 | 动作 | 执行者 | 目标状态 | 副作用 |
| --- | --- | --- | --- | --- |
| — | 创建 offer（所有者本人） | 授权方 | `pending` | 创建/复用 runtime；创建 `manual` 来源 `pending`；不建实例、不建绑定 |
| — | 创建 offer（管理员代建） | 管理员 | `pending_owner_approval` | 创建/复用 runtime；创建 `manual` 来源 `pending`；接收方不可见；通知资源所有者 |
| `pending_owner_approval` | 所有者同意 | 资源所有者 | `pending` | 通知接收方；其他副作用不变 |
| `pending_owner_approval` | 所有者拒绝 | 资源所有者 | `declined` | 来源 `declined`（`ended_reason=owner_declined`）；通知管理员；接收方从未看到该 offer |
| `pending` | 接受 | 接收方 | `active` | 来源 `pending -> active` 或 `dormant`；创建/激活授权实例（账户资源）或快照（分组资源）；不建绑定；失效网关缓存；通知授权方 |
| `pending` | 拒绝 | 接收方 | `declined` | 来源 `declined`；无实例/绑定；通知授权方 |
| `pending` | 回收 | 授权方 | `revoked` | 来源 `revoked`；撤回 offer；通知接收方 |
| `pending` | 到期（TTL/expires_at） | 系统 | `expired` | 来源 `expired`；runtime 按 §4.4 重算（可能因其他来源仍 active）；通知双方 |
| `active` | 归还 | 接收方 | `returned` | 来源 `returned`；按 §4.4 重算 runtime；runtime 终态时才停用绑定/隐藏实例；通知授权方 |
| `active` | 回收 | 授权方 | `revoked` | 来源 `revoked`；按 §4.4 重算 runtime；runtime 终态时才停用绑定/隐藏实例；通知接收方 |
| `active` | 暂停 | 授权方 | `paused` | 父 offer 暂停；来源状态不变；runtime 按 §4.4 推导；绑定保留但网关阻断；通知接收方 |
| `paused` | 恢复 | 授权方 | `active` | 父 offer 恢复；runtime 按来源重新推导；通知接收方 |
| `paused` | 归还 | 接收方 | `returned` | 来源 `returned`；按 §4.4 重算；runtime 终态时才停用绑定；通知授权方 |
| `paused` | 回收 | 授权方 | `revoked` | 来源 `revoked`；按 §4.4 重算；通知接收方 |
| `active` / `paused` | 到期 | 系统 | `expired` | 父 offer 与**非终态**来源到期；runtime 按 §4.4 重算（可能仍 active）；通知双方 |
| `expired` | 延长有效期 | 授权方 | `active` / `pending` / `paused` | 只恢复本次到期周期写为 `expired` 的来源；若 grant 到期前为 `paused`，恢复为 `paused`，不得自动解除暂停；否则任一已接受来源恢复时 grant=`active`，只有未接受来源时 grant=`pending`；本次恢复不自动恢复被停用的绑定，其他有效来源的绑定不受影响；通知接收方 |
| `declined` / `returned` / `revoked` / `expired` | 重新发起 | 授权方 | `pending` 或 `pending_owner_approval` | 复用同一 grant/runtime；**追加新的 `manual` 来源行**；本次重发不自动恢复旧绑定，其他有效来源的绑定不受影响；接收方必须重新接受并重新绑定 |
| `pending` / `active` / `paused` | 屏蔽 | 接收方 | `declined` 或保持 | pending 来源撤回为 `declined`（`ended_reason=blocked`）；已接受来源按 `return_existing` 决定是否 `returned` |

规则：

- 个人授权创建时**不得**提交 `targetGroupId`。后端收到 `targetGroupId` 返回 400，避免旧客户端静默写入。
- 个人授权接受后，账户资源创建授权实例但**没有** `group_accounts` 行；分组资源建立快照但 `group_authorization_settings.enabled=0`。接收方必须显式绑定后才能调度。
- 暂停只允许作用于 `active` offer；`pending` offer 不能暂停，只能回收或等待 TTL。
- 到期延长不要求重新接受，但必须重新绑定：到期时只有 runtime 进入终态才停用绑定；延长恢复本次周期来源后，被停用的绑定不自动恢复，其他有效来源的绑定不受影响。
- 延长必须按 `expiry_cycle` 选择本次到期周期来源，并按 `expired_from_status` 恢复：`active` / `dormant` / `needs_review` / `pending` 分别恢复到对应状态；若恢复前计算出的当前指纹与 `accepted_source_revision` 不一致，恢复为 `needs_review`，不得直接恢复 active。`returned` / `declined` / `revoked` 永不恢复。
- 没有本次到期周期可恢复来源时（零成员团队 `no_member_offer`、legacy expired 分组授权、全部来源已终态），不得 extend；返回 409 `no_restorable_source`，必须重新发起。不得把空来源父 grant 恢复为 active/pending。
- `pending_owner_approval` 到期后不允许 extend（所有者确认 TTL 已过），必须由管理员重新发起并重新等待所有者确认；不得恢复为 `pending` 绕过所有者确认。
- grant 到期时必须记录 `expired_from_status`（`active` / `paused` / `pending` / `pending_member_acceptance` 等）；extend 时按该字段恢复父 grant。`paused` 到期后延长恢复为 `paused`，需显式 resume 才可用。
- 重新发起必须检查屏蔽名单、24 小时 cooldown、per-grantee/per-grantor 限额和全局限额；命中时返回 `offer_suppressed`，不创建 offer。
- pending offer 有默认 TTL（见 §8.5）；到期后来源和 grant 进入 `expired`，不再占用 pending 限额；`pending_owner_approval` 也有独立 TTL。
- 父 offer 进入终态时，只处理非终态来源；已 `returned` / `declined` / `revoked` / `expired` 的来源保持原终态和 `ended_at`，不得被批量覆盖。
- `active` / `paused` 个人 grant 没有任何 source 属于异常数据；巡检/维护应置 `revoked`（`ended_reason=no_sources`）并告警，不得保留无来源的可用业务记录。
- 通用迁移规则：所有状态迁移必须锁定目标 grant/source/runtime 行并使用带当前状态条件的 UPDATE；影响行数为 0 时返回 409 `state_conflict` 或重读后重试，不得无条件覆盖并发结果。终态不可逆，除 §5.5 明确列出的 extend 恢复外不得复活。涉及多表写入时统一锁顺序为 grant → runtime → source → settings/snapshot，批量按 ID 排序，避免死锁。

### 4.2 团队授权状态机

| 当前状态 | 动作 | 执行者 | 目标状态 | 副作用 |
| --- | --- | --- | --- | --- |
| — | 创建团队 offer（所有者本人） | 授权方 | `pending_team_approval` | 不创建任何成员来源；通知团队审批人 |
| — | 创建团队 offer（管理员代建） | 管理员 | `pending_owner_approval` | 不创建成员来源；通知资源所有者 |
| `pending_owner_approval` | 所有者同意 | 资源所有者 | `pending_team_approval` | 通知团队审批人；其他副作用不变 |
| `pending_owner_approval` | 所有者拒绝 | 资源所有者 | `declined` | `ended_reason=owner_declined`；通知管理员 |
| `pending_team_approval` | 同意 | 团队审批人 | `pending_member_acceptance` | 为每个 eligible 成员创建/复用成员 runtime 和 `team` 来源 `pending`；不建实例/快照/绑定；通知成员。若零成员来源，仍保持 `pending_member_acceptance`，通知授权方可 re-invite |
| `pending_team_approval` | 拒绝 | 团队审批人 | `declined` | 不创建成员来源；通知授权方 |
| `pending_team_approval` | 到期（TTL） | 系统 | `expired` | 无成员来源；通知授权方/审批人 |
| `pending_member_acceptance` | 首个成员接受 | 成员 | `active` | 该成员来源 `active` 或 `dormant`；复用审批时为该成员创建的 runtime；账户资源建实例、分组资源建快照；不建绑定；通知授权方/审批人 |
| `active` | 成员逐人接受/拒绝/归还 | 成员 | `active` | 成员来源独立变化；团队业务记录保持 active，直到所有来源终态 |
| `active` | 暂停 | 授权方 | `paused` | 父 offer 暂停；所有成员 runtime 按 §4.4 推导；绑定保留但网关阻断 |
| `paused` | 恢复 | 授权方 | `active` | 父 offer 恢复；成员 runtime 按来源重新推导 |
| `active` / `paused` | 到期 | 系统 | `expired` | 父 offer 与**非终态**成员来源到期；runtime 按 §4.4 重算；绑定仅在 runtime 终态时停用 |
| `expired` | 延长有效期 | 授权方 | `active` / `pending_member_acceptance` / `paused` | 只恢复本次到期周期的来源；若 grant 到期前为 `paused`，恢复为 `paused`，不得自动解除暂停；否则任一已接受成员来源恢复时 grant=`active`，无已接受来源时 `pending_member_acceptance`；按 `expired_from_status` 恢复，指纹不符转 `needs_review`；`returned` / `declined` / `revoked` 不复活；本次恢复不自动恢复被停用的绑定，其他有效来源的绑定不受影响 |
| 任意非终态 | 回收 | 授权方 | `revoked` | **非终态**成员来源 `revoked`；按 §4.4 重算；runtime 终态时才停用绑定 |
| 任意非终态 | 团队停用 | 管理员/系统 | `revoked` | `ended_reason=team_disabled`；**非终态**成员来源 `revoked`；按来源回退 |
| 任意非终态 | 团队删除 | 管理员 | `revoked` | `ended_reason=team_deleted`；**非终态**成员来源 `revoked`；按来源回退 |
| `active` / `paused` / `pending_member_acceptance`（当前周期已有成员来源） | 全部成员来源终态 | 系统 | `declined` 或 `expired` | 按 §4.2 聚合规则写 `ended_reason`；通知授权方。零成员来源不命中本行，按 `TeamMemberlessTTL` 保持 |
| `declined` / `revoked` / `expired` | 重新发起 | 授权方 | `pending_team_approval` 或 `pending_owner_approval` | 复用同一团队 grant；团队审批人必须重新同意；此前该团队+资源的 team 来源有 `declined`/`returned` 历史的成员不自动重发，需显式 re-invite |

规则：

- 团队业务记录不是成员级同意的主体；成员只能操作自己的成员 offer（`resource_authorization_sources.id`），不能归还/回收团队业务记录。
- 团队审批人只审批团队 offer，不能接受成员 offer；成员接受与否由成员自己决定。
- 团队审批人默认是 `system_teams.created_by`（该列 NOT NULL）。其账户不存在、已停用或与授权方为同一账户时，任一 `super_admin` / `admin` 可代行；管理员代行必须写操作日志并通知团队。存在独立且有效的审批人时，管理员不得绕过。
- **禁止自审批**：授权方不得审批自己发起的团队 offer；若 `created_by` 就是授权方，必须由管理员代行，且管理员不得同时是授权方。自审批判断按资源归属人（grantor）计算；管理员代建时若团队审批人就是资源归属人，仍需另一名管理员代行，不能以“创建者是管理员”规避。
- 团队审批人的权限仅限授权 offer 审批，不自动获得团队成员管理或其他管理权限；团队管理仍由管理员执行。
- 团队新增成员时，只为**当前周期没有非终态来源且该团队+资源没有 team 来源持久退出记录**的成员创建 pending 来源；该团队+资源的 team 来源此前 `declined` / `returned` 的成员不自动重发，需团队授权方显式 re-invite（仍受 blocklist/cooldown/上限约束）。
- 成员被移出团队：该成员在该团队所有 grant 上的**非终态**来源改为 `revoked`（`ended_reason=member_removed`）；不是 `returned`，因为不是成员主动归还。终态来源保持原状。重新加入团队时，若该成员历史上只有 `member_removed` / `expired` 记录，按新增成员自动创建 pending；若该团队来源曾有 `declined` / `returned`，不自动重发，需显式 re-invite。
- 持久退出判定只看该成员在该**团队+资源**的 `team` 来源历史；个人 `manual` 来源的 `returned`（含 `fallback_declined`）不阻止未来团队成员 offer，也不自动恢复个人来源。
- 团队停用/删除等价于回收该团队全部非终态 team 来源；不是删除业务记录。
- 资源归属人本人作为团队成员时不生成成员 offer（不能给自己授权）；团队 grant 仍对其他成员生效。
- `resource_authorization_grants.status=returned` 仅用于个人直授权；团队成员归还不把团队业务记录改为 `returned`，全部成员终态时用 `declined` + `ended_reason` 表达。
- 零 eligible 成员时，审批后保持 `pending_member_acceptance`，不得立即 `declined`；授权方可以 re-invite 或等待 TTL。`no_eligible_member` 只作为通知/统计原因，不作为即时终态。
- 团队 grant 到期时记录 `expired_from_status`；`paused` 到期后 extend 恢复 `paused`，需显式 resume，不得自动解除暂停。`pending_owner_approval` / `pending_team_approval` 到期不允许 extend，必须重新发起并重新审批。

**团队聚合规则**（在 `pending_member_acceptance` / `active` / `paused` 下统一执行；聚合前锁定团队 grant 行，避免并发成员接受/拒绝基于旧来源集合写终态）：

1. 若存在任一 `pending` / `active` / `dormant` / `needs_review` 成员来源，团队 grant 保持当前状态（`pending_member_acceptance` 或 `active`；`paused` 仅在暂停期间保持）。
2. 若当前周期存在至少一条成员来源，且全部来源均为终态：
   - 存在任一 `revoked` 且 `ended_reason=source_deleted` / `group_deleted` → 团队 grant `revoked`，`ended_reason` 取对应资源删除原因（资源已不存在，优先于成员原因）；
   - 全部为 `revoked` 且原因均为 `member_removed` → `declined`，`ended_reason=all_members_removed`；
   - 至少一个来源曾接受且当前全部为 `returned` / `declined` → `declined`，`ended_reason=all_members_ended`；
   - 全部为 `declined` 且从未接受 → `declined`，`ended_reason=all_members_declined`；
   - 全部为 `expired`（含成员 offer TTL）→ `expired`，`ended_reason=all_member_offers_expired`；
   - 混合终态 → 按“是否曾接受”选择 `declined`（`all_members_ended`）或 `declined`（`all_members_declined`）；若全部是 `expired` 则 `expired`。
3. 若当前周期没有任何成员来源（零 eligible 或全部被抑制）：
   - `pending_member_acceptance` 在 `TeamMemberlessTTL` 内保持，不得因空集命中“全部 declined/expired”；
   - `TeamMemberlessTTL` 到期 → `expired`，`ended_reason=no_member_offer`；
   - `active` / `paused` 下零来源属于异常数据，置 `revoked`（`ended_reason=no_sources`）并告警，不得停留 active/paused。
4. `paused` 下所有来源终态时，同样按上述规则进入终态，不得停在 `paused`。
5. 聚合只读取当前周期来源和其 `ended_reason`；终态来源不得被后续批量操作改写；“全部”分支必须先满足“当前周期至少一条来源”，空集不得按全称命题处理。

### 4.3 来源状态与优先级

来源状态：

| 状态 | 含义 | 可作为有效来源 |
| --- | --- | --- |
| `pending` | 已发 offer，等待接收方确认 | 否 |
| `active` | 接收方已接受，未被更高优先级来源覆盖 | 是 |
| `dormant` | 接收方已接受，但当前被更高优先级的 team 来源覆盖；保留回退 | 仅当没有 active team 来源时提升为有效 |
| `needs_review` | 来源 material change，等待接收方重新确认 | 否 |
| `revoked` | 授权方回收、团队停用/删除、成员移除或资源删除 | 否 |
| `returned` | 接收方主动归还 | 否 |
| `declined` | 接收方拒绝或被屏蔽撤回 | 否 |
| `expired` | 到期 | 否 |

规则：

- 优先级固定为 `team > manual`；多个 team 来源之间按“最早生效且仍有效”确定 `effective_source_team_id`，其余 team 来源保持 `active`，共同维持运行时可用。
- `manual` 来源被 team 来源覆盖时，状态从 `active` 改为 `dormant`，不改为 `superseded`；`dormant` 可在最后一个 team 来源失效时自动恢复为 `active`（前提：manual 父 offer 仍 `active`、来源未过期、未归还/拒绝、未被 `return_existing=true` 的屏蔽撤回）。
- 屏蔽使用 `return_existing=false`（仅屏蔽未来）时，已存在的 active/dormant/needs_review 来源保持原状，dormant 仍可在团队结束后提升；解除屏蔽不改变这些来源。只有 `return_existing=true` 时来源才被 `returned`，之后不自动恢复。
- 旧 `superseded` 数据迁移时按 `source_type` 和 `ended_reason` 分支：`manual` + `covered_by_team` 转 `dormant` 并清除终态字段；`team` + `covered_by_team` 转 `active`（新模型允许多个 team 来源共存），父 grant 已终态时按父状态转 `expired` / `returned` / `revoked`；`authorization_expired` / `authorization_returned` / `authorization_revoked` 分别转 `expired` / `returned` / `revoked`；无法判定时阻断升级并输出清单。
- 接收方接受 team 来源时，前端必须提示“团队来源将优先；你的个人来源会保留为回退”。接收方可以显式选择“不保留个人回退”，此时该 runtime **已接受**的对应 `manual` 来源（`active` / `dormant` / `needs_review`）改为 `returned`（`ended_reason=fallback_declined`），其父个人 grant 同步 `returned`；`pending` manual offer 保持 pending，由接收方单独接受/拒绝，不自动撤回；不允许接收方把来源写成 `revoked`。
- 来源 material change 只把**非终态**来源改为 `needs_review`，不改变父 offer 状态；接收方重新接受后恢复 `active` / `dormant`（按优先级）。
- `needs_review` 来源在计算有效来源时被跳过；如果存在其他 active/dormant 来源，运行时可以继续 active，并回退到其他来源。只有没有任何可用来源且存在 `needs_review` 时，运行时才显示 `needs_review`。
- 同一 runtime 的多个来源状态变化必须在同一事务内重算 runtime 状态，并失效网关运行时缓存。重算前必须锁定 runtime 行（`SELECT ... FOR UPDATE` 或等效串行化机制），防止两个来源并发 accept/return 各自基于旧状态计算并互相覆盖；来源状态更新也要带旧状态条件，影响行数为 0 时重读重试或返回冲突。
- 同一 runtime + 来源类型的非终态唯一性由部分唯一索引保证；重新发起追加新来源行，旧终态行保留。重复创建 pending offer 时幂等返回同一 pending 行，不追加。

### 4.4 运行时状态推导

`resource_authorizations.status` 是物化投影，按以下顺序推导（每一步命中即停止）：

1. 定义：
   - `active_parent_sources`：父 grant 状态为 `active` 的来源；
   - `paused_parent_sources`：父 grant 状态为 `paused` 的来源；
   - 终态来源：`revoked` / `returned` / `declined` / `expired`；
   - 有效来源只在 `active_parent_sources` 中选择；`paused_parent_sources` 不参与 active 判定。
2. 若 `active_parent_sources` 中存在 `active` 的 team 来源：runtime `active`；`active_parent_sources` 中所有 `active` 的 manual 来源转为 `dormant`。
3. 否则若 `active_parent_sources` 中存在 `active` 的 manual 来源：runtime `active`。
4. 否则若 `active_parent_sources` 中存在 `dormant` 的 manual 来源：把该 manual 来源提升为 `active`，runtime `active`。这是团队来源失效、待确认、暂停或被 `needs_review` 时的个人回退路径。
5. 否则若存在 `needs_review` 来源且其父 grant 为 `active` / `pending` / `pending_owner_approval` / `pending_member_acceptance`：runtime `needs_review`。
6. 否则若存在 `pending` 来源且其父 grant 为 `active` / `pending` / `pending_owner_approval` / `pending_member_acceptance`：runtime `pending`。
7. 否则若 `paused_parent_sources` 中存在 `pending` / `active` / `dormant` / `needs_review` 来源：runtime `paused`。
8. 否则按最近一次来源终态（`ended_at DESC NULLS LAST, id DESC`）取 `revoked` / `returned` / `declined` / `expired` 作为 runtime 终态；不得因为存在一条更早的 `expired` 来源就覆盖更新的 `returned` / `revoked` / `declined`；终态来源的 `ended_at` 由迁移回填，终态后不再更新。
9. 否则 runtime `revoked`（防御性兜底；正常创建 offer 时至少有一条来源）。

补充规则：

- runtime `active` 不代表可调度；账户资源必须同时满足授权实例 `status=active`、`schedulable=1`、`group_accounts.enabled=1`、来源账户可用、接受修订匹配；分组资源必须满足快照、`group_authorization_settings.enabled=1`、来源账户可用、接受修订匹配。
- 每次重算必须同步 runtime 的 `effective_source_type` / `effective_source_team_id`：team 有效来源写 `team` + 团队 ID，manual 写 `manual` + NULL，无有效来源置空；不得保留旧来源。
- runtime `pending` / `needs_review` / `paused` / 终态即使存在绑定，网关也必须阻断。
- runtime `dormant` 不对外展示；`dormant` 是来源状态，runtime 只展示 active/pending/needs_review/paused/终态。
- 来源从 `dormant` 提升为 `active` 或从 `active` 转为 `dormant` 时，不创建实例/快照、不修改绑定；只重算 runtime 和失效缓存。
- 暂停只阻断被暂停 grant 的来源；同一 runtime 的其他 active/dormant 来源仍可按上述顺序维持可用。若授权方希望整体不可用，必须暂停所有相关 grant 或回收。
- 父 grant `pending_owner_approval` 时，runtime 仍按 pending 推导，但接收方 API 必须隐藏该 offer；网关不可能有绑定候选。

### 4.5 来源修订与 material change

来源修订（`source_revision`）是稳定指纹，必须覆盖：

- `connection_driver_code`、`vendor_code`、`protocol_code` / `protocol_version`、`capability_domain`、连接 `connection_preset_code`；当前 schema 已无 `provider_protocol_profile_id` 列，不得引用；协议档案由连接 preset 派生。
- 所有 enabled 的 `account_connections`（`connection_preset_code`、`protocol_surface_code`、规范化 `base_url`、`enabled`）及其 endpoint modes；新增、删除、停用或修改任一连接都属于 material change，不得只对运行时临时选中的单条连接计算指纹。
- 上述每条 enabled 连接的 `base_url`：规范化后的完整 URL（scheme + host + port + path + query），使用服务端 HMAC 哈希后存储；不得把含敏感 token 的明文写入修订字段或展示。查询串任何变化都视为 material change，防止用 `?tenant=` 切换上游租户；
- 启用的 endpoint modes / 协议能力集合；
- 代理绑定：`proxy_profile_id` / `proxy_pool_id`，以及代理档案 revision（host/port/type/username 变更）、代理池有效成员集合及每个成员的 `enabled` / `priority` / `weight` / profile revision、代理池 `strategy`；任一影响实际出口的变化都必须标记直接引用该档案或通过池引用该成员的来源；
- 支持模型集合（排序后的 `model_id` / `public_model` 集合）；
- 账户入口映射 `account_entry_mappings` 全行（source model、source endpoint family、target connection、target model、target endpoint family、enabled）；
- 账户类型 / 能力域（不可变字段，但纳入指纹保证一致性）；
- OAuth 主体标识：`sub`、`account_id`、`chatgpt_account_id`、`organization_id`、`email`（展示时脱敏）；主体指纹从解密后的凭据载荷提取并 HMAC，凭据无法解密时 fail closed，不得静默跳过。
- API Key 身份指纹：解密凭据中的**完整 API Key 池**（池内每个 Key 按凭据顺序完整参与 HMAC；单 Key 账户等价于该 Key 的 HMAC）。任一 Key 增删/替换属于 material change；`credential_fingerprint` 列不参与修订：OAuth 账户该列是 refresh token 的哈希，token 轮换不得误触发 `needs_review`，只有主体标识变化才触发。实现位于 `shared/platform/authzrevision`，迁移与网关共用同一算法。
- 若某类账户无法取得稳定主体标识，禁止在原账户上更换凭据主体，必须新建账户。
- 指纹 HMAC 密钥必须持久化并跨发布稳定；轮换密钥视为 `revision_version` 升级，必须走 maintenance 步骤并通知接收方，不得直接换密钥造成全量静默阻断。

不纳入修订、只做可用性通知的字段：

- `status` / `schedulable` / `cooldown_until` / `last_error_*` / `stream_failure_*`；
- `concurrency_limit` / `rpm_limit` / 可用时段 / `account_expires_at`；
- 账户名称、备注、健康检查模型、探测开关；
- OAuth access/refresh token 刷新但 `sub` / `account_id` 等主体标识不变（token 轮换本身不触发）；若主体标识变化，必须触发。

**两个修订字段：**

- `accepted_source_revision`：接收方最后一次明确同意的修订；只有 accept/reconfirm 成功时写入，material change 不得覆盖。
- `observed_source_revision`：系统最近一次计算出的当前修订；material change 时写入。
- grant 上的 `source_revision` 只表示 offer 创建时的基线，用于展示和审计，不参与接受比较。
- 每条来源增加 `revision_version`；指纹算法升级时递增。升级必须由 maintenance 具名步骤把所有非终态来源置 `needs_review` 并重算 runtime，不能只让网关静默阻断；否则 `active` 来源没有重新确认入口。

material change 处理：

1. 授权方修改来源账户的 material 字段并保存成功后，在同一事务/同一批失效中找出所有引用该来源账户的**非终态账户资源** `manual` 来源和 `team` 来源（包括团队成员来源）；终态来源不得改写。分组资源的账户级变化不走本步骤，见第 3 条。
2. 将这些来源的 `observed_source_revision` 更新为当前指纹，状态置为 `needs_review`，记录 `needs_review_reason`、`needs_review_detail_json`（变更字段与脱敏后的旧/新值）和 `needs_review_at`；重算受影响 runtime；失效网关缓存。更新必须带 `status IN ('pending','active','dormant','needs_review')` 和旧 `observed`/`revision_version` 条件，避免覆盖并发 accept。
3. 对分组授权，不把整个 group grant/来源置为 needs_review，而是按账户粒度处理：对应快照行的 `source_revision` 与当前不一致时，该账户从该接收方的分组授权候选中排除；接收方通过 `scope-diff` 查看并逐账户 reconfirm 后重新纳入。分组来源自身的 `needs_review` 只用于分组身份/归属/删除等分组级变化。
4. 通知每个受影响接收方：“来源账户配置已变更，需重新确认后才能继续使用”，并展示变更字段；通知授权方“N 条授权待接收方重新确认”。
5. 接收方重新确认时携带 `expectedRevision`（即 UI 展示的 `observed_source_revision`）和 `expectedRevisionVersion`；服务端 `SELECT ... FOR UPDATE` 锁定来源并重新计算当前指纹，使用条件更新 `WHERE id=? AND status IN ('pending','needs_review') AND observed_source_revision=? AND revision_version=?`；成功后写入 `accepted_source_revision`、`accepted_source_revision_version`，来源恢复 `active` / `dormant`。影响行数为 0 或 `expectedRevision != observed != current` 时返回 409 `offer_stale_source_changed`，刷新 `observed`，要求重新查看；不得用先读后写的非原子检查。
6. 接收方拒绝重新确认或归还时，来源进入 `declined` / `returned`；按来源回退规则处理。

禁止：

- 不得在 material change 后自动沿用旧接受记录继续调度。
- 不得把 `needs_review` 当作“可用但降权”；必须是硬阻断。
- 不得因为来源状态变化自动修改接收方的 `group_accounts` 绑定或分组授权开关；绑定只由接收方动作创建/停用/移动。
- 不得只监听单账户 PATCH；批量更新、凭据更新、OAuth reauth、账户导入/转移、连接替换、代理档案/池变更、模型映射变更都必须在同一批失效中触发 material change 检测。
- 资源归属人变化（`accounts.system_account_id` / `groups.system_account_id` 被改写）不属于可重新确认的 material change：资源自身作为授权对象时，必须撤销该资源全部非终态 manual/team 来源并回收 grant，接收方需获得新归属人的新授权，不得用 reconfirm 继续使用。账户归属人变化但该账户只是他人分组快照成员时，只移除该账户快照行/从候选中排除并重算 `snapshot_revision`，不撤销分组来源或分组 grant；分组归属人变化则撤销该分组全部来源/grant。`owner-approve`、`accept`、团队审批、`bind`、`extend`、逐账户 reconfirm 都必须在事务内重新校验资源当前归属与 grant 的 `resource_owner_system_account_id` 一致；不一致时拒绝动作并触发撤销，不能只信任创建时的快照。

### 4.6 分组授权的范围快照与绑定开关

分组授权不创建授权实例，接收方获得的是分组内账户的使用权。为防止授权方在接受后往分组里加入新账户，分组授权按接收方维度保存范围快照，并用 `group_authorization_settings.enabled` 作为显式绑定开关。

表 `resource_authorization_group_accounts`：

- `authorization_id`：最终用户授权 ID；
- `account_id`：快照时分组内属于分组归属人的账户 ID；
- `source_revision`：该账户纳入快照时的接受修订；
- `accepted_at` / `updated_at`：纳入/最近确认时间；
- 主键 `(authorization_id, account_id)`；索引 `account_id`。

表 `group_authorization_settings` 增量：

- `enabled`：分组授权绑定开关；首次创建 settings 行（该 runtime 尚无已接受 group 来源）时写 0；同一 runtime 后续来源 accept/reconfirm 保留原值，不得重置；接收方显式 bind 后写 1，显式 unbind 写 0；runtime 进入终态或分组删除时写 0；暂停/needs_review/分组停用保留原值但网关阻断；
- `snapshot_revision`：当前快照的稳定哈希（排序后的账户 ID + `source_revision` + `revision_version`，逐段以 NUL 分隔后 HMAC；零账户快照写入空集合 HMAC，不得留 NULL）；
- `snapshot_mode`：`normal` / `legacy_oversized`；
- `scheduling_policy_json` 保持现有语义，不被授权流程覆盖。
- `enabled` 是 runtime 级开关，不是 source 级：同一 runtime 的 team + manual 来源共享；从任一来源执行 unbind 都会停用该分组授权，UI 必须提示影响所有来源。

规则：

- **首次接受**分组授权（该 runtime 当前没有任何非终态 group 来源）或历史终态后重新接受且快照不存在时，对当前分组内 `group_accounts.enabled=1` 且账户归属人为分组归属人的账户建立快照；带 `authorization_instance_authorization_id` 的他人授权实例不进入快照（沿用现行防穿透规则）。同时创建 `group_authorization_settings.enabled=0` 和 `snapshot_revision`。
- **同一 runtime 的后续来源接受/重新确认**只校验该来源的分组身份修订，不得重建快照、不得扩大/缩小快照、不得重置 `enabled`；分组范围变化只能走 `scope-diff` + `refresh-scope`（新增/移除）或逐账户 reconfirm（修订变化）。
- 分组来源的 `accepted_source_revision` / `observed_source_revision` 只覆盖分组身份和分组级元数据（group id + owner + 删除等），**不覆盖账户级 material change，也不把分组临时停用/启用当作修订变化**；分组停用是可用性状态，保持来源 active、`settings.enabled` 不变，重新启用后直接恢复，不要求 reconfirm。账户级 `base_url`、模型、代理、映射、凭据变化只影响该账户的快照行，不把整个分组来源置 `needs_review`。
- 接收方显式调用 `POST /my-authorization-sources/{sourceId}/bind` 后，`enabled=1`；之后才能在自己的路由策略中引用该分组。路由策略绑定必须再次校验 runtime active、settings enabled=1、分组属于资源归属人且未删除。
- 网关选择分组授权账户时，必须同时满足：账户在快照中、当前仍是该分组有效成员（`group_accounts.enabled=1`）、账户当前归属人仍是分组归属人（`accounts.system_account_id = groups.system_account_id`）、快照 `source_revision` 与当前账户指纹一致且 `revision_version` 一致、分组/授权可用、`group_authorization_settings.enabled=1`，并叠加现有账户可用性（状态、调度、冷却、过期、凭据、连接）。
- 分组归属人后续新增账户：不自动进入已接受的快照；接收方看到“新增 N 个账户可纳入”，通过 `scope-diff` 查看逐账户修订，再调用 `refresh-scope` 显式纳入。新增账户不改变已接受范围。
- 分组归属人移除账户：实时成员过滤会排除；快照行可以在下一次 refresh 时清理，不要求即时删除。
- 账户 material change：该账户从该接收方的分组候选中排除，其他账户不受影响；接收方通过 `scope-diff` 查看变更，调用逐账户 `reconfirm`（携带该账户 `expectedRevision` / `expectedRevisionVersion`）后恢复，不得用一次 refresh 批量接受所有修订变化。
- `refresh-scope` 只处理新增账户和移除账户，必须携带 `expectedSnapshotRevision` 和接收方已审阅的新增账户 ID/修订/版本；服务端发现快照已变化或某账户修订/版本不匹配时返回 409 `scope_stale`，要求重新展示 diff；不得按请求时全量集合静默纳入。已有账户的修订变化必须走 `POST .../accounts/{accountId}/reconfirm`。
- `snapshot_revision` 必须在首次建快照、`refresh-scope` 和逐账户 `reconfirm` 成功后重算；`refresh-scope` 的 CAS 与快照行更新在同一事务完成，避免并发刷新覆盖。逐账户 reconfirm 必须锁定该 runtime 的 `group_authorization_settings`（或等效串行化锁）后重算 hash，不能两个账户并发更新后各自写入基于旧快照的 `snapshot_revision`。
- 快照缺失但存在已接受且非终态 group 来源时，`scope-diff` 返回空 `snapshotRevision`、当前分组账户全量 diff 和 `snapshot_missing=true`；接收方审阅后调用 `refresh-scope` 并显式 `rebuildMissingSnapshot=true` 重建快照，重建后 `settings.enabled=0`，必须重新启用后才能调度。该路径只用于修复缺失，不得用于绕过正常 refresh 的 CAS。
- 快照账户数上限见 §8.4；新接受/新增账户超过上限时拒绝新增，不得静默截断；`legacy_oversized` 快照只允许迁移存量，后续 refresh 只能减少或保持，不得继续扩大。
- 现有生产分组授权在迁移时为每个 `active` / `paused` 授权建立当前账户快照，保持迁移前可用范围；`legacy_oversized` 允许超过新上限，但必须标记并通知接收方。
- 团队+分组：团队审批后为每个成员创建成员来源；成员接受时为该成员建立独立快照和独立的 `group_authorization_settings` 行（`authorization_id` 是该成员的 runtime），成员各自 enable、各自 refresh、各自归还；成员移除时只撤销该成员 runtime/来源，不影响其他成员。
- 分组停用/删除：停用时来源/运行时不可用但保留关系，`settings.enabled` 保持不变（网关因分组停用阻断，重新启用后恢复，不要求重新绑定）；删除时来源 `revoked`（`ended_reason=group_deleted`）、个人 grant `revoked`（`group_deleted`）、团队 grant 按 §4.2 聚合置 `revoked`、runtime 重算、绑定开关 0；通知接收方。资源删除不依赖来源聚合：该分组的所有非终态 grant（含零成员来源的 `pending_owner_approval` / `pending_team_approval` / `pending_member_acceptance`）必须直接置 `revoked`（`ended_reason=group_deleted`），不得因空集聚合停留在 pending。不得让接收方继续看到已删除分组或继续调度其账户。删除路径必须在删除 group 前撤销来源并更新 grant，**不得沿用现行“物理删除 resource_authorization_sources / resource_authorizations”的级联清理**；授权 grant/source/runtime/快照历史必须保留用于审计，`group_accounts` / `settings` 行可随 group 外键删除。
- 网关读取 `group_authorization_settings` 时，非 legacy runtime 缺失行必须视为 `enabled=0`（fail closed），不得沿用 `COALESCE(...,1)`；只有迁移步骤为存量 active/paused runtime 补行时才可按旧语义写 1，并必须同时建立快照。新接受/新 runtime 缺失 settings 视为异常并阻断。
- 防止授权穿透：带 `authorization_instance_authorization_id` 的他人授权实例不进入快照；分组归属人后续把授权实例加入分组，也不会进入快照。

### 4.7 屏蔽规则

表 `resource_authorization_blocks`：

- `id`；
- `blocker_system_account_id`：接收方；
- `blocked_system_account_id`：被屏蔽的授权方；按资源屏蔽时必填资源归属人；
- `blocked_resource_type` / `blocked_resource_id`：按资源屏蔽时填写；按授权方屏蔽时为空；
- `reason`；
- `created_at` / `updated_at`；
- 约束：`blocked_resource_type` 与 `blocked_resource_id` 必须同时为空或同时非空；资源屏蔽时 `blocked_system_account_id` 必填；
- 唯一性：
  - `(blocker_system_account_id, blocked_system_account_id) WHERE blocked_resource_type IS NULL`；
  - `(blocker_system_account_id, blocked_resource_type, blocked_resource_id) WHERE blocked_resource_type IS NOT NULL`。

语义：

- 屏蔽授权方：该授权方未来对当前接收方的个人 offer、以及该授权方作为资源归属人的团队授权成员 offer 一律不创建；已存在的 pending 来源撤回为 `declined`（`ended_reason=blocked`）；`return_existing=true` 时同时归还原有 active/dormant/needs_review 来源。管理员代建不改变授权主体：屏蔽匹配按资源归属人判断，阻止该归属人的资源通过管理员代建绕过；管理员自身滥用由管理员治理与审计处理，不进入接收方的授权方屏蔽列表。
- 屏蔽资源：该资源未来对当前接收方的 offer 不创建；已存在 pending 来源撤回；`return_existing=true` 时归还原有来源。
- 默认 `return_existing=true`；前端提供“仅屏蔽未来”选项。`return_existing=false` 时只抑制未来 offer，不改变现有来源和绑定；解除屏蔽后这些来源仍按原状态和优先级工作。
- 授权方侧只收到中性错误 `offer_suppressed`，不暴露是否被屏蔽、被谁屏蔽；cooldown、上限、屏蔽使用同一外部错误码，真实原因只写服务端审计与指标。
- 团队审批人不能查看成员的个体屏蔽记录；全局管理员可以查看（用于滥用调查），查看行为写操作日志。
- 接收方可以解除屏蔽；解除后未来 offer 恢复，历史 `returned` / `declined` 来源不自动恢复。
- 屏蔽只抑制新 offer 相关通知；已保留来源的 `source_needs_review`、到期、暂停、凭据轮换等安全通知仍发送给接收方，不因屏蔽被抑制。被屏蔽授权方的新 offer 尝试只得到中性 `offer_suppressed`，不暴露屏蔽事实。

### 4.8 管理员滥用暂停

表 `system_account_authorization_suspensions`：

- `id`、`system_account_id`、`suspended_by`、`reason`、`suspended_at`、`lifted_at`、`lifted_by`。
- 生效条件：`lifted_at IS NULL`。
- 唯一约束：`(system_account_id) WHERE lifted_at IS NULL`，同一账户最多一条生效暂停。

规则：

- 管理员可以对一个系统账户设置“暂停发起授权”；生效期间该用户不能创建个人或团队 offer，也不能延长、re-invite、恢复已暂停的 offer、增加额度；只能缩短、暂停或回收。暂停按资源归属人（`resource_owner_system_account_id`）判断，管理员代建 offer 不得绕过归属人的暂停；被暂停期间也不能确认 `pending_owner_approval`（owner-approve），避免先由管理员建单再绕过暂停。管理员自身若被暂停，也不能作为 `created_by` 发起。
- 暂停不是账户状态，不写 `system_accounts.status`，不影响登录、API Key 和正常调用。
- 管理员可以回收该用户作为资源归属人的在途/生效授权；回收必须写操作日志并通知接收方。不得用暂停代替接收方同意，也不得代接收方接受/绑定。
- 解除暂停后恢复发起能力；历史屏蔽/拒绝记录仍有效。
- 管理员可以查询当前暂停状态；解除暂停写操作日志。

## 5. 核心流程

### 5.1 个人授权创建

输入：资源类型、资源 ID、接收方精确用户名（或精确 ID，仅管理员可用）、备注、可选到期时间、可选额度。

步骤：

1. 校验 actor 是资源归属人或管理员；管理员必须通过 `systemAccountId` 指定资源归属人，且该值必须等于资源实际 `system_account_id`，不能以任意账户名义创建 offer。
2. 校验资源存在、未被删除、未被授权（授权实例不能再次授权）；资源为分组时必须 `group_kind=standard`，超级分组返回 `group_kind_conflict`。
3. 校验接收方存在且 `active`；接收方不能是资源归属人（无论 actor 是本人还是管理员代建），返回 `self_authorization_forbidden`；接收方不存在/停用返回 `grantee_not_found`；精确名查询必须限速、写审计。
4. 同一资源+接收方已有非终态 offer 时：`pending` / `pending_owner_approval` 幂等返回原 offer，不重复创建、不重复通知；已有 `active` offer 时返回 `409 offer_already_active`（或明确提示已生效），不创建新记录。
5. 校验 actor 未被管理员暂停发起授权；校验 per-grantor 全局限额、per-grantor→grantee 24 小时 offer 数、per-grantee pending 上限。
6. 校验 blocklist：若接收方屏蔽了 actor 或该资源，返回 `offer_suppressed`，不创建 offer；cooldown/上限同样返回 `offer_suppressed`，真实原因写审计。
7. 若 actor 是管理员且不是资源归属人：校验资源归属人账户存在且 `active`；全部校验通过后创建 grant 状态 `pending_owner_approval`，通知资源所有者；接收方不可见。所有者同意后转 `pending`，拒绝后 `declined`。管理员不得代所有者同意。若 actor 是资源归属人，直接创建 `pending`。
8. 复用或创建 `resource_authorizations` runtime；**追加新的 `manual` 来源行**（状态 `pending`，写入 `observed_source_revision` 当前指纹、`expiry_cycle=grant.expiry_cycle`；`accepted_source_revision` 为空）。仅同一 grant 已存在非终态 pending 来源时幂等复用该行。
9. **不创建** `accounts` 授权实例，**不写** `group_accounts`，**不写**分组快照/绑定开关；pending offer 不出现在接收方账户列表，只出现在授权中心收件箱（`pending_owner_approval` 连收件箱也不出现）。
10. 写操作日志/通知接收方（所有者确认后）；提交。pending TTL 按 §8.5。
11. 返回 `{ grantId, sourceId, status, sourceRevision, ownerApprovalRequired, ... }`。

明确禁止：请求体中的 `targetGroupId` 一律 400；不得因为接收方有默认分组就自动绑定；不得因为资源是分组就创建授权实例。

### 5.2 接受与重新确认

输入：`sourceId`、`expectedRevision`（必填，值为接收方在详情页看到的 `observed_source_revision`）、`expectedRevisionVersion`、`retainFallback`（团队来源首次接受可选，默认 `true`；`false` 时按 §4.3 把该 runtime 已接受的 manual 来源置 `returned`，`ended_reason=fallback_declined`，其父个人 grant 同步 `returned`；pending manual 不自动撤回。`needs_review` 重新确认不得改变回退选择，携带 `false` 时拒绝或忽略并提示）。

步骤：

1. 校验 actor 是 runtime 的 `grantee_system_account_id`；团队来源只能由团队成员处理；管理员不能代接受。校验资源仍存在、未删除、未变为授权实例，且当前归属人等于 grant 的 `resource_owner_system_account_id`；不满足时拒绝并触发撤销。
2. 校验来源状态为 `pending` 或 `needs_review`；个人场景父 offer 为 `pending` / `active`；团队场景父 offer 为 `pending_member_acceptance` / `active`。父 offer `paused` 时拒绝并提示先恢复；`pending_owner_approval` 时接收方不可见，不得接受（所有者同意后父状态已转 `pending`）。接受门禁只取决于来源状态与父 offer：同一 runtime 已因其他来源处于 `active` 时，本来源仍可接受；列表/详情返回的 `canAccept` 必须与本节一致，不得要求 runtime 为 `pending` 或 `needs_review`。
3. 服务端锁定 grant/runtime/source 行；重新计算当前指纹时读取已提交的账户配置，不持有账户行锁。要求 `expectedRevision == observed_source_revision == current_revision` 且 `expectedRevisionVersion == revision_version`；`needs_review` 场景还要求来源当前状态为 `needs_review`。使用条件更新 `WHERE id=? AND status IN ('pending','needs_review') AND observed_source_revision=? AND revision_version=?`；影响行数为 0 或任一不匹配时返回 409 `offer_stale_source_changed`，更新 `observed_source_revision`，要求接收方重新查看；不得先读后写、不得静默接受新修订。账户写路径在账户更新提交后按条件把引用来源置 `needs_review`，即使与 accept 并发也不会留下“接受旧配置仍 active”的状态。
4. 校验 blocklist、per-grantee active/pending 上限、实例/快照上限；命中返回 `offer_suppressed`。
5. 来源 `pending/needs_review -> active` 或 `dormant`（按当前 team 来源优先级）；写入 `accepted_source_revision=observed_source_revision`、`accepted_source_revision_version=revision_version`、`accepted_at/by`；个人场景同步 grant 的 `acceptance_mode='recipient'`、`accepted_at/by`，**即使来源因 team 覆盖为 dormant，个人父 grant 也置 active**（否则 dormant 无法在团队结束后回退）；团队场景首个成员接受置团队 grant active，runtime `acceptance_mode='recipient'`；runtime 按 §4.4 重算。
6. 按资源类型分支：
   - **账户资源**：创建或激活授权实例（`authorization_instance_authorization_id` = runtime ID，`system_account_id` = 接收方，`status=active`，`schedulable=1`）；**不创建** `group_accounts`。接受/重新确认成功后，必须同步实例从来源继承的静态字段（vendor/driver/protocol/account type/capability/health 配置等）或保证网关读取来源当前值，不得让实例保留旧协议/旧能力配置；同步失败则本次接受失败，来源保持 `needs_review`。
   - **分组资源**：不创建实例。若该 runtime 当前没有已接受且非终态的 group 来源且快照不存在，建立首次快照并创建 `group_authorization_settings.enabled=0`、`snapshot_revision`、`snapshot_mode=normal`；若同一 runtime 已有快照，则只更新来源状态，**不得重建快照、不得重置 `enabled`**；快照存在但 settings 行缺失时补建 `enabled=0` 并写 `snapshot_revision`，不得因为缺失行让来源无法接受；若当前存在已接受且非终态的 group 来源但快照缺失，返回 409 `snapshot_missing_requires_review`，要求先走 `scope-diff` + `refresh-scope` 重建；若只有历史终态来源（如 legacy expired 后重新发起且快照缺失），按首次快照规则建立新快照和 `settings.enabled=0`，不得因历史来源拒绝接受。不写路由策略。
7. 失效网关运行时缓存；写操作日志；通知授权方/团队审批人。
8. 返回 `{ sourceId, status: "active"|"dormant", instanceId?, snapshotRevision?, bound: false }`。

接受后，接收方在“授权给我的”里看到资源；账户资源显示“未绑定分组”，分组资源显示“未启用”。绑定前网关没有候选。

### 5.3 接收方绑定

**账户资源：**

1. 校验 actor 是实例所属系统账户；实例必须是授权实例且对应 runtime 存在。
2. 校验 runtime `active`；若 `needs_review` / `paused` / 终态，拒绝并提示先处理授权状态。
3. 校验目标分组属于 actor、`enabled=1`、`group_kind=standard`；超级分组不能直接绑定账户。
4. 校验分组账户数/实例数上限（沿用账户加入分组的现有约束）。
5. 若已存在该实例的有效绑定：同一分组幂等成功；不同分组按现有账户换组语义移动，不产生多活跃绑定；授权域不改变现有换组的历史保留行为。
6. 写入 `group_accounts`，`account_authorization_id` = runtime ID，`enabled=1`；写操作日志；失效网关缓存。
7. 返回 `{ instanceId, groupId, groupName }`。

授权实例是 runtime 级资源，manual 与 team 来源共享同一个实例；接收方停用实例、解绑分组会影响该 runtime 的所有来源，UI 必须提示。来源归还只撤销对应来源，不直接删除/转移实例。

**分组资源：**

1. 校验 actor 是 runtime 的 `grantee_system_account_id`；runtime 必须 `active`。
2. 校验快照存在、`group_authorization_settings` 存在且分组仍属于资源归属人、未删除。
3. 调用 `POST /my-authorization-sources/{sourceId}/bind` 把 `settings.enabled` 置 1；接收方可调用 `POST .../unbind` 置 0，不改变 source/runtime，仅停止该 runtime 的分组调度；重新启用必须再次 bind。
4. 接收方再通过现有路由策略接口把该分组加入自己的策略；路由策略写入必须校验 runtime active、settings enabled=1、分组归属关系。
5. 返回 `{ sourceId, groupId, enabled: true }`。

**通用约束：**

- 绑定只能由接收方发起；管理员接口不得提供“代绑定”。
- 授权实例（`authorization_instance_authorization_id` 非空）不得通过通用账户删除、批量删除、导入/导出、克隆或转移接口删除、复制或改归属；接收方只能归还来源，授权方只能回收，源账户逻辑删除由授权域统一撤销。通用删除路径必须识别授权实例并拒绝，不得留下 runtime/source 与实例脱节。`authorization_instance_authorization_id` 和 `group_accounts.account_authorization_id` 是授权域内部字段，通用创建/导入/更新接口不得写入或清空（接收方绑定授权实例走专用校验路径），防止伪造授权归属或绕过来源闸门。
- 接收方对授权实例只能修改本地调度字段：启用/停用、`schedulable`、分组绑定、组内优先级/超级优先/降级备用、冷却/测试等使用侧设置；不得修改凭据、`base_url`、供应商/协议档案、模型/映射、代理、连接等来源字段。通用 PATCH/批量接口必须按实例类型收窄，尝试修改来源字段返回 403；来源字段变更只能由资源归属人操作并触发 material change。
- 所有可能写 `group_accounts` 的通用路径（`PATCH /accounts/{id}`、`POST /accounts/{id}/group`、创建/导入/克隆账户等）必须对 `authorization_instance_authorization_id` 非空的账户拒绝非所属接收方的写入；管理员也不能绕过。
- 通用账户删除/批量删除路径必须区分授权实例和来源账户：授权实例拒绝删除；作为授权来源的账户删除时，在同一事务调用授权域撤销非终态来源、移除分组快照行、重算 runtime 并失效缓存，不得只删账户留下悬空 source/快照。系统账户删除路径同理走逻辑删除。
- 所有可能把他人分组写入路由策略的路径必须校验：分组属于当前用户，或存在当前用户的有效分组授权且 `settings.enabled=1`；管理员不能替他人绑定授权分组。路由策略执行时仍需按 §8.1 校验 runtime/source/修订，写入时校验不能替代运行时闸门。
- 管理员可以帮助排查，但不能代替接收方做出同意或绑定动作。

### 5.4 拒绝、归还、屏蔽

**拒绝（pending / needs_review）**

- 来源 `pending/needs_review -> declined`；个人场景父 offer -> `declined`；团队场景只改成员来源，团队业务记录按 §4.2 聚合。
- 不创建实例/快照、不写绑定；通知授权方/团队审批人。
- 写 cooldown：同一资源+接收方 24 小时内不能再收到同一授权方的新 offer（授权方侧收到 `offer_suppressed`）。

**归还（active / dormant / needs_review，或父 offer paused 下的来源）**

- 来源 -> `returned`；个人场景父 offer -> `returned`；团队场景只改成员来源并按 §4.2 聚合。
- 先按 §4.4 重算 runtime：
  - runtime 进入终态（`returned` / `revoked` / `expired` / `declined`）时，停用该 runtime 的账户绑定（`group_accounts.enabled=0`，保留历史行）或分组绑定开关（`settings.enabled=0`），并隐藏/停用无其他来源的实例；
  - runtime 仍为 `active` / `paused` / `needs_review` / `pending` 时，保留绑定；另一来源可继续服务，不得因归还一条来源误停整个 runtime 的绑定。
- 如果存在其他来源，runtime 重算并回退（例如 team 归还后 manual dormant 恢复 active）；实例和绑定保留。
- 实例停用使用授权实例自身的 `status='disabled'` + `schedulable=0`，保留 `authorization_instance_authorization_id` 关联，不物理删除；重新接受时恢复 `active` / `schedulable=1` 并同步来源字段。runtime 仍 active 时不得停用实例。
- 通知授权方；写 cooldown；接收方可以随后屏蔽。

**屏蔽**

- 写入 blocklist；`return_existing=true` 时归还原有 active/dormant/needs_review 来源，按 §4.4 重算 runtime，只有 runtime 终态时才停用绑定；**pending 来源在两种模式下都一律撤回**为 `declined`（`ended_reason=blocked`）。
- 个人父 grant 状态回写：撤回 pending 后没有其他非终态个人来源 → `declined`（`ended_reason=blocked`）；归还有效来源后没有其他非终态个人来源 → `returned`（`ended_reason=blocked`）；团队来源仍有效时，个人 grant 可为 `returned`，但 runtime 继续 active，绑定不停用。
- `return_existing=false` 时只抑制未来 offer，保留已接受来源和绑定；pending 来源仍撤回；解除屏蔽后保留来源按原状态继续，历史 `returned` / `declined` 不恢复。
- 不通知被屏蔽的授权方具体原因；后续 offer 统一返回 `offer_suppressed`。屏蔽只抑制新 offer/`offer_suppressed` 通知，不得抑制被保留来源的 `source_needs_review` 等安全通知。
- 团队场景：成员屏蔽授权方时，只影响该成员的成员 offer；团队其他成员不受影响；不再向该成员发送该授权方的新 offer 通知；已保留来源的安全通知仍发送。

**归还与重新授权**

- 归还后，授权方可以发起新 offer，但必须重新走 `pending -> accept`；不得复用旧接受状态。
- 归还时停用的绑定不会自动恢复；接收方重新接受后必须显式重新绑定。
- 重新授权命中 cooldown/block/限额时返回 `offer_suppressed`；接收方解除屏蔽后未来 offer 恢复，历史来源不自动恢复。

### 5.5 暂停、到期、回收、延长

**暂停**

- 仅 `active` offer 可暂停；父 offer `paused`；来源状态不变；runtime 按 §4.4 推导；绑定保留但网关阻断。
- 若同一 runtime 存在其他 active/dormant 来源，runtime 可继续 active 或回退；暂停只影响被暂停 grant 的来源。
- 恢复时父 offer `active`；runtime 重新推导；如果期间发生 material change，来源仍为 `needs_review`，恢复后仍不可用，直到重新确认。
- 暂停期间不接受新的成员接受、re-invite、延长或增加额度；可以归还/回收。暂停不冻结 pending source 的 TTL：成员 offer 到期后按 §4.2 聚合/`expired` 处理，恢复后不自动复活，需要显式 re-invite。

**到期**

- 父 offer 与所有**非终态**来源 `expired`；终态来源保持原终态。grant `expiry_cycle` 递增一次，grant 写 `expired_from_status=到期前 grant 状态`；每个来源写 `expiry_cycle` 和 `expired_from_status`（到期前来源状态）。
- 先按 §4.4 重算 runtime；只有 runtime 进入终态时才停用绑定/隐藏实例；若其他来源仍有效，runtime 可继续 active。
- 通知双方；到期扫描沿用现有 worker，并扩展 pending/team 审批/成员 offer TTL（§8.5）。

**延长**

- 授权方可以延长 `active` 或 `expired` offer 的 `expires_at`：`active` 只更新到期时间，不改变来源状态；`expired` 父 offer 恢复到 `active` / `pending`（团队为 `active` / `pending_member_acceptance`）；若 grant `expired_from_status='paused'`，恢复为 `paused`，不得自动解除暂停。
- 只恢复**本次到期周期**写为 `expired` 的来源：`expiry_cycle` 必须等于 grant 当前的 `expiry_cycle`，且 `ended_reason=offer_expired`；历史周期的过期来源不复活。`expiry_cycle` 只由 grant 到期事件推进：grant 到期时仍非终态的 source 写入新的周期；更早因 `MemberOfferTTL` 过期的 source 保留原 `expiry_cycle`，不因 grant 后续到期被提升到新周期，grant extend 不得复活这些成员 offer，必须显式 re-invite。每来源按 `expired_from_status` 恢复（`active` / `dormant` / `needs_review` / `pending`），恢复前重新计算指纹：与 `accepted_source_revision` 不一致时恢复为 `needs_review`，不得直接 active/dormant；`returned` / `declined` / `revoked` 永不恢复。
- `extend` 只处理由 grant 自身到期产生的 `expired`（`ended_reason=offer_expired`，含个人 pending TTL）。团队因全部成员 offer 过期聚合出的 `expired`（`all_member_offers_expired`）、`no_member_offer`、`team_approval_timeout`、`owner_approval_timeout` 不允许 extend，必须重新发起并重新审批/接受；不得用 extend 复活已过期的成员 offer。迁移前已 `expired` 的 legacy grant（`acceptance_mode='legacy'`）是例外：其 `ended_reason` 可能为 `authorization_expired`，extend 按迁移回填的 `expired_from_status` 恢复，但终态 legacy source 未回填 `accepted_source_revision`，必须恢复为 `needs_review`；legacy expired 分组授权仍禁止 extend。
- 父 grant 状态：若 `expired_from_status='paused'` → `paused`（优先，需 resume 才可用）；否则任一恢复来源曾接受（`accepted_source_revision` 非空或 `expired_from_status` 为 active/dormant/needs_review）→ `active`；只有未接受来源恢复 → `pending` / `pending_member_acceptance`。不得把已接受来源恢复在 `pending` 父 grant 下，否则 §4.4 会把它推成终态。
- 本次恢复不自动恢复被停用的绑定；其他有效来源维持的绑定不得被触碰。分组授权 `settings.enabled` 保持原值（若原为 0 则仍为 0），接收方需显式重新绑定/启用。
- 没有本次周期可恢复来源的 `expired` offer 不允许 extend（含零成员团队 `no_member_offer`、legacy expired 分组授权），返回 409 `no_restorable_source`，必须重新发起；legacy expired 分组授权没有快照，延长后无法绑定，不得例外。`legacy_expiry_unknown` 的 expired grant 必须由管理员显式提交 `confirmExpiredFromStatus`（`active` / `paused`）才能延长，默认拒绝，避免静默解除暂停。
- 通知接收方“授权已延长，请重新绑定/启用分组”。
- 新增显式 `POST /my-authorizations/{grantId}/extend`；不得只靠 PATCH 改到期时间。当前状态 `paused` 不能直接延长（先恢复）；`expired` 且 `expired_from_status='paused'` 可以延长，但只恢复为 `paused`；`returned` / `declined` / `revoked` 不能延长；`pending_owner_approval` 到期不能延长。
- 缩短到期时间允许通过 PATCH 设置更早的 `expiresAt` 或立即回收；新值必须晚于当前时间（过去时间用回收）；`expiresAt` 设为 null（变为永不过期）或晚于当前值视为延长，拒绝；当前为 null 时设置具体时间属于缩短，允许。缩短后重新计算到期时间，不恢复已停用绑定。

**回收**

- 授权方回收父 offer；所有**非终态**来源 `revoked`；终态来源保持原状；按 §4.4 重算；runtime 终态时才停用绑定/隐藏实例；通知接收方。
- 回收不删除历史使用记录、来源历史、绑定历史；只改状态。
- 重新发起必须重新接受；旧绑定不自动恢复。
- 来源账户逻辑删除时，所有引用该来源的**非终态账户资源** `manual` / `team` 来源统一 `revoked`（`ended_reason=source_deleted`），按 §4.4 重算；个人父 grant 同步 `revoked`；团队 grant 在无非终态来源且存在 `source_deleted` 时按 §4.2 置 `revoked`（`ended_reason=source_deleted`）；该账户资源的所有非终态 grant（含零成员来源的 `pending_owner_approval` / `pending_team_approval` / `pending_member_acceptance`）必须直接置 `revoked`，不得因空集聚合停留 pending。分组授权不因某个成员账户删除而撤销：只移除该账户的快照行/从候选中排除，分组来源和团队 grant 保持，快照 `snapshot_revision` 重算并失效缓存。
- 资源归属人系统账户被停用时，不自动删除授权数据，但管理员应暂停或回收其未完成 offer；接收方侧仍可归还/屏蔽，网关按来源账户可用性阻断。
- 系统账户删除必须逻辑删除；存在授权 grant/source/runtime/授权实例时禁止物理删除，避免 `grant_id` RESTRICT 与既有 CASCADE 冲突、授权历史丢失或统计断链。
- 团队删除（逻辑删除）时，团队 grant 仅在自身非终态时置 `revoked`；所有非终态 team 来源 `revoked`（`ended_reason=team_deleted`）；已终态 grant/来源保持原状，不得覆盖 `ended_reason`。

### 5.6 重新发起、cooldown 与限额

- 个人：同一资源+接收方在 `declined` / `returned` 后 24 小时内，授权方不能创建新 offer；返回 `offer_suppressed`，不创建记录。
- 团队：团队审批人拒绝后 24 小时内，授权方不能对同一团队重新发起（团队级 cooldown）；成员归还/拒绝后，团队重新发起不自动给该成员发 offer，需显式 re-invite，且该成员 24 小时内不能被 re-invite（成员级 cooldown）。成员级 cooldown 只阻止向该成员 re-invite，不阻止向团队其他成员 re-invite，也不阻止新建团队 offer；团队级 cooldown 只由团队审批拒绝或团队级屏蔽触发。
- 屏蔽优先于 cooldown：被屏蔽时直接 `offer_suppressed`，不等待 cooldown；cooldown、上限、屏蔽使用同一外部错误码。
- 管理员滥用暂停优先于一切：被暂停的发起来源直接拒绝创建、延长、re-invite、恢复和增加额度。
- 全局限额（§8.4）在解析目标前检查，避免用大量精确名探测绕过 per-pair 限额。
- 重新发起追加新来源行，不复用旧终态行；本次重发不自动恢复旧绑定，其他有效来源的绑定不受影响。
- `fallback_declined`（接受团队来源时选择不保留个人回退）不是拒绝团队授权，不写 cooldown、不计入团队成员持久退出；对应个人来源及其父 grant 进入 returned。
- 复用 grant 重新发起时必须重置上一轮批准/同意字段：清空 `accepted_at/by`、`team_approved_at/by`、`owner_approved_at/by`、`ended_at/ended_reason`、`expired_from_status`、`legacy_basis`、`legacy_review_deadline`（含 `legacy_expiry_unknown` 标记），`acceptance_mode='recipient'`，runtime `acceptance_mode='recipient'`，并写入新的 `source_revision` 基线和按新 TTL 计算的 `pending_expires_at`；上一轮来源保持终态不可改写。个人重新发起必须重新接受，团队重新发起必须重新审批；不得用旧字段跳过流程。
- 重新发起时重新校验资源归属并同步 grant/runtime 的 `resource_owner_system_account_id`；资源归属已变化的，先按 §4.5 撤销旧来源，再由新归属人发起，不得沿用旧归属人的 grant 继续授权。

### 5.7 团队授权创建与审批

1. 授权方创建团队 offer：资源归属校验同个人；接收方类型 `team`；团队必须 `active`；团队审批人必须存在（`created_by` 或管理员回退）；资源为分组时同样适用。
2. 管理员代资源所有者创建时，先进入 `pending_owner_approval`；所有者同意后才进入 `pending_team_approval`。
3. 校验授权方未被暂停、per-grantor 全局限额、per-grantor→team 24 小时 offer 数、团队 pending offer 上限。团队层面不检查个人 blocklist；成员级 blocklist 在成员 offer 阶段检查。
4. 创建 team grant，状态 `pending_team_approval`；不创建成员来源、不创建实例/快照、不写绑定。
5. 通知团队审批人；审批人查看 offer 详情（资源、来源账户、供应商、endpoint host、额度、成员数、风险提示）。
6. 审批人同意：状态 `pending_member_acceptance`；为每个 eligible 成员创建/复用成员 runtime 和 `team` 来源 `pending`（写入 `expiry_cycle=grant.expiry_cycle` 和各自的 `pending_expires_at`；跳过 blocklist、上限、已有非终态来源、该团队+资源的 team 来源曾有 `declined`/`returned` 持久退出的成员）；runtime 保持 `pending`，不创建实例/快照/绑定；通知成员。有成员来源时 grant `pending_expires_at` 置空，由成员 offer TTL 驱动；零成员来源时保持 `pending_member_acceptance`，grant `pending_expires_at=now+TeamMemberlessTTL`，通知授权方可 re-invite 或等待 TTL。
7. 审批人拒绝：状态 `declined`；不创建成员来源；通知授权方。
8. 成员接受：按 §5.2 处理；父 offer 在首个成员接受后变 `active`；账户资源创建成员实例，分组资源创建成员快照；均不绑定。
9. 成员拒绝/归还/屏蔽：只改成员来源；团队业务记录按 §4.2 聚合。
10. 团队停用/删除/成员移除：按 §4.2 批量撤销非终态来源；成员来源按回退规则处理。
11. 自审批禁止：授权方不得审批自己发起的团队 offer；审批人账户失效或与授权方同一时，由管理员代行并审计。

### 5.8 团队成员变更

- 新增成员（管理员）：在团队添加成员事务内，为该团队所有 `active` / `pending_member_acceptance` / `paused` 团队 grant 创建/复用成员 runtime 和 pending 成员来源；runtime 保持 `pending`，不创建实例/快照/绑定；不自动激活；对每个成员执行 blocklist/上限/历史退出检查。若原 grant 是零成员 `pending_member_acceptance`，成功创建首个成员来源后清空 grant `pending_expires_at`，改由成员 offer TTL 驱动。成员 offer 创建被抑制时记录 `suppressed` 统计，不回滚团队成员加入，也不阻塞团队操作，因为 offer 本身不创建实例；这与现行“全员展开失败整体回滚”不同，目的是避免“一个成员缺默认分组导致整个团队授权/加成员失败”的旧缺陷。团队加入成功后，成员在授权中心看到待确认；若因上限或历史拒绝被抑制，系统向该成员发送 `offer_suppressed` 通知（不创建来源行），说明“待确认授权过多”或“此前已拒绝”，不暴露其他成员信息；若因该成员屏蔽了授权方/资源而抑制，则不发送通知，遵守 §4.7 的屏蔽隐私。
- 移除成员（管理员）：该成员在该团队所有 grant 上的**非终态**来源 -> `revoked`（`ended_reason=member_removed`）；终态来源保留；重算 runtime；只有 runtime 终态时才停用绑定；通知成员和授权方。
- 成员重新加入：若该成员对该团队+资源从未有过来源，或历史只有 `member_removed` / `expired`，按新增成员自动创建 pending；若曾有 `declined` / `returned`，不自动重发，需授权方显式 re-invite。
- 团队审批人变更：`system_teams.created_by` 的变更仍由管理员执行并写操作日志；旧审批人的 pending 审批不自动转移，但新审批人/管理员可处理。
- re-invite：只允许在团队 grant `pending_member_acceptance` / `active` 下，对指定 active 成员创建 pending 来源；不得在 `pending_team_approval`（未审批）或 `paused`（暂停期间）下创建；已有该成员+团队的非终态 team 来源时幂等返回原来源，不重复创建；受 blocklist/cooldown/上限约束。团队审批人不能 re-invite，只能审批；需要时由授权方操作。
- 暂停期间新增成员：可以创建 pending 来源（记录待确认），但成员不能接受，直到恢复；恢复后按来源重算。不得因为暂停漏掉成员，恢复时也不需要补发逻辑。

### 5.9 来源 material change 流程

1. 授权方保存来源账户 material 字段（`base_url`、供应商/协议档案、连接 preset/端点模式、代理、支持模型集合、模型映射、OAuth 主体、API Key 指纹等）。
2. 账户写路径在同一事务/同一批失效中标记引用该来源账户的所有**非终态**来源 `needs_review`，写入 `observed_source_revision`、原因和变更详情；终态来源不改写。
3. 对分组授权，按快照账户粒度排除；不把整个 group grant 置为 needs_review。
4. 失效网关缓存；写操作日志；通知接收方，展示变更字段和脱敏后的旧/新值。
5. 接收方在授权中心看到“来源已变更，需重新确认”，可查看新的供应商/endpoint host/模型集合/代理摘要；携带 `expectedRevision` 重新接受后恢复，拒绝/归还则按来源回退。
6. 如果接收方在重新确认前发起绑定/调度，网关必须返回授权不可用；前端应隐藏/禁用绑定入口。
7. 批量更新、凭据更新、OAuth reauth、账户导入/转移、连接替换、代理档案/池变更、模型映射变更都走同一检测；不得只覆盖单账户 PATCH。

### 5.10 分组授权接受、绑定与刷新范围

1. 授权方创建 group offer：资源为普通分组（`group_kind=standard`；超级分组拒绝 `group_kind_conflict`）；校验分组归属 actor、未被删除；接收方为精确用户或团队；创建 pending（管理员代建先经所有者确认）。
2. 接收方接受：建立范围快照（当前分组内归属人账户 + 各账户接受修订）；runtime `active`；upsert `group_authorization_settings.enabled=0`、`snapshot_revision`；不创建实例。
3. 接收方显式 bind：`settings.enabled=1`；然后才能在自己的路由策略中引用该分组；路由策略写入校验 runtime active、settings enabled=1、分组归属关系。
4. 分组新增账户：不自动进入快照；接收方通过 `scope-diff` 看到新增账户及修订，调用 `refresh-scope`（携带 `expectedSnapshotRevision` 和新增账户 ID/修订/版本）显式纳入；刷新只处理新增/移除，不处理已有账户的修订变化；快照变化返回 409。快照缺失时 `scope-diff` 返回空 revision + 全量 diff + `snapshot_missing=true`，接收方显式 `rebuildMissingSnapshot=true` 重建，重建后 `enabled=0` 并要求重新启用。
5. 账户 material change：该账户被排除；接收方通过 `scope-diff` 查看，调用 `POST .../accounts/{accountId}/reconfirm` 逐账户确认（携带 `expectedRevision` / `expectedRevisionVersion`），条件更新快照行的 `source_revision` 和 `revision_version`；不得用一次 refresh 批量接受所有修订变化。
6. 分组停用/删除：停用时来源/运行时不可用但保留关系，`settings.enabled` 保持不变（分组重新启用后恢复，不要求重新绑定）；删除时来源 `revoked`（`ended_reason=group_deleted`）、个人/团队 grant 按 §4.2 置 `revoked`、runtime 重算、绑定开关 0；通知接收方。不得让接收方继续看到已删除分组或继续调度其账户，也不得物理删除授权历史。
7. 防止授权穿透：带 `authorization_instance_authorization_id` 的他人授权实例不进入快照；分组归属人后续把授权实例加入分组，也不会进入快照。
8. 团队+分组：按 §4.6 为每个成员建立独立快照和 settings；成员移除只撤销该成员，不影响其他成员。
9. 所有加载路径（常规、chat-pinned、媒体、realtime）都必须应用快照、接受修订和 settings 开关；chat-pinned 只能跳过健康可用性，不能跳过授权范围。

### 6.1 授权方与资源所有者接口

| 方法 | 路径 | 作用 | 关键约束 |
| --- | --- | --- | --- |
| `POST` | `/__aisys__/api/my-authorizations` | 创建个人/团队 offer | 不再接受 `targetGroupId`；接收方使用精确 `granteeUsername` 或管理员 `granteeSystemAccountId`；团队使用 `teamId` 或精确 `teamName`；管理员代建返回 `pending_owner_approval` |
| `GET` | `/__aisys__/api/my-authorizations?direction=outbound` | 我发出的授权 | 返回业务 grant 状态、来源接受计数、待审批/待接受计数；不返回接收方分组 |

| `GET` | `/__aisys__/api/my-authorizations?direction=owner_pending` | 资源所有者待确认的管理员代建 offer | 仅资源所有者；返回 `pending_owner_approval` 列表和最小详情；接收方不可见 |

| `POST` | `/__aisys__/api/my-authorizations/{grantId}/pause` | 暂停 | 仅 active |
| `POST` | `/__aisys__/api/my-authorizations/{grantId}/resume` | 恢复 | 仅 paused；暂停期间不得 re-invite/延长 |
| `POST` | `/__aisys__/api/my-authorizations/{grantId}/extend` | 延长到期时间 | `active` / `expired`；当前 `paused` 先恢复；`expired_from_status='paused'` 只恢复为 `paused`；`pending_owner_approval` 到期不可延长；`legacy_expiry_unknown` 必须由管理员显式提交 `confirmExpiredFromStatus`；只恢复本次 `expiry_cycle` 且由 grant 自身到期产生（`ended_reason=offer_expired`）的来源；`all_member_offers_expired` / `no_member_offer` / `team_approval_timeout` / `owner_approval_timeout` 不可延长；终态不复活；本次恢复不自动恢复旧绑定 |
| `DELETE` | `/__aisys__/api/my-authorizations/{grantId}` | 回收 | 非终态来源 revoked；终态保留；不删除历史 |
| `POST` | `/__aisys__/api/my-authorizations/{grantId}/reinvite` | 团队场景显式重发成员 offer | 仅团队 grant 的 `pending_member_acceptance` / `active`；对指定成员创建 pending；受 blocklist/cooldown/上限约束 |
| `POST` | `/__aisys__/api/my-authorizations/{grantId}/owner-approve` | 资源所有者确认管理员代建 offer | 仅 `pending_owner_approval`；仅资源所有者；所有者不得处于暂停发起状态；管理员不得代操作 |
| `POST` | `/__aisys__/api/my-authorizations/{grantId}/owner-decline` | 资源所有者拒绝管理员代建 offer | 仅 `pending_owner_approval`；仅资源所有者 |

控制类端点（`PATCH` / `pause` / `resume` / `extend` / `DELETE`）由资源所有者（`resource_owner_system_account_id`）调用；只有 `created_by == resource_owner_system_account_id`（所有者本人创建）时，`created_by` 才等同所有者。管理员代建的 grant，创建者管理员不能通过 owner 端点暂停、恢复、延长、缩短或回收来覆盖所有者的决定，只能走 §6.4 管理员治理并留审计；资源所有者始终可以控制自己的资源。管理员治理动作不得代接收方接受或绑定；所有者对管理员代建 grant 的控制动作必须通知创建者管理员并写审计。

### 6.4 管理接口

- `POST /__aisys__/api/authorizations`：管理员可指定资源归属人创建 offer，但必须进入 `pending_owner_approval`，经资源所有者确认后才对接收方可见；必须写操作日志、通知资源所有者；仍不建实例/快照/绑定。管理员不得代所有者确认，也不得代接收方接受或绑定。
- `GET /__aisys__/api/authorizations`：管理员全量查询；支持 pending_owner_approval/pending/needs_review/team approval 状态筛选。
- `DELETE /__aisys__/api/authorizations/{grantId}`：管理员回收；只改非终态来源。
- `POST /__aisys__/api/authorizations/{grantId}/pause` / `resume` / `extend`：管理员治理动作，受暂停发起授权和审计约束。`pause` / `resume` 只处理非终态 grant；`extend` 只恢复本次 `expiry_cycle` 写为 `expired` 的来源，`returned` / `declined` / `revoked` 不恢复；`legacy_expiry_unknown` 的 grant 必须显式提交 `confirmExpiredFromStatus`（`active` / `paused`）才允许 extend，默认拒绝。
- `POST /__aisys__/api/system-accounts/{id}/authorization-suspension` / `DELETE ...`：暂停/解除发起授权能力；`GET .../authorization-suspension` 查询当前状态。
- `GET /__aisys__/api/authorizations/blocks`：管理员查看屏蔽记录（用于滥用调查）；不返回给团队审批人；查看写操作日志。

管理员没有“强制归还”单独接口；需要移除访问时使用回收（DELETE），其效果是撤回非终态来源，不伪装成接收方同意。管理员也不能通过通用账户/分组/路由策略接口代绑定。

### 6.5 移除/收窄的接口

| 接口 | 处理 |
| --- | --- |
| `POST /authorizations` 的 `targetGroupId` | 移除；传了返回 400，不静默忽略 |
| `GET /authorization-options/grantee-accounts` | 仅管理员可用；普通用户不得全量枚举 |
| `GET /my-authorization-options/grantee-accounts` | 移除全量列表；改为精确用户名校验或由创建接口内部解析 |
| `GET /authorization-options/grantee-teams` / `my-.../grantee-teams` | 仅管理员可全量；普通用户使用精确团队名 + 团队审批 |
| `GET /authorization-options/grantee-groups` / `my-.../grantee-groups` | 从授权方侧移除；接收方绑定使用自己的 `/my-groups` |
| `POST /my-accounts/{id}/return-authorization` | 保留但收窄：仅当该实例只有一条非终态来源时等价于归还该来源；存在多条来源时返回 409，要求去授权中心按来源归还 |
| `POST /my-groups/{id}/return-authorization` | 保留但收窄：仅当该授权分组只有一条非终态来源时等价于归还该来源；存在多条来源时返回 409 |
| `POST /accounts/{id}/return-authorization`（管理面） | 移除；管理员不得代接收方归还，需要移除访问时使用回收 |

| 团队 grant 的个人归还入口 | 不提供；成员归还的是成员 offer（来源），不是团队业务记录 |

精确用户名/团队名仍可能被逐字探测；接口必须全局限速、写审计，并且只返回最小结果（不返回角色、状态、分组等额外信息）。屏蔽、cooldown、限额统一返回 `offer_suppressed`；目标不存在/停用返回 `grantee_not_found` / `team_not_found`，并通过限速和审计降低探测价值。

### 6.6 字段可见性

- 接收方必须能看到：授权方展示名、来源账户名、供应商、所有 enabled 连接的 endpoint host（去重，不含敏感查询串）、代理类型/区域摘要（不含代理凭据）、额度限制、到期时间、当前状态、绑定/启用状态、风险提示、material change 的变更字段和脱敏旧/新值。
- 接收方**不能**看到：来源凭据、完整代理配置、授权方原账户的敏感管理字段、其他成员的个人接受/拒绝记录。
- 授权方可以看到：自己创建的 offer、来源接受计数、团队审批状态、聚合消耗；不能看到接收方的分组列表，也不展示绑定分组名称；只展示“已绑定/已启用”布尔值。
- 资源所有者可以看到：管理员代自己创建、待自己确认的 offer；确认前接收方不可见。
- 团队审批人可以看到：团队 offer 的资源、来源账户、供应商、endpoint host、额度、成员数、接受/拒绝聚合计数；不能看到成员个人分组和个体拒绝原因。
- 管理员可以看到全量授权关系、状态、审计和屏蔽记录，但不得在授权域展示来源凭据明文、代理凭据或接收方分组给授权方；管理员查看敏感管理字段沿用账户管理权限。

## 7. 存储设计

### 7.1 `resource_authorization_grants` 变更

新增/调整：

- `status`：扩展为 `pending_owner_approval`、`pending`、`pending_team_approval`、`pending_member_acceptance`、`active`、`paused`、`expired`、`revoked`、`returned`、`declined`。
- `acceptance_mode`：`recipient`（新契约）、`legacy`（迁移存量）；默认 `legacy`，新代码写 `recipient`。
- `accepted_at` / `accepted_by`：接收方接受时间/人（个人）；团队 grant 的成员接受在来源层。legacy 行 `accepted_by` 为空，另写 `legacy_basis`。
- `team_approved_at` / `team_approved_by`：团队审批时间/人；legacy 行 `team_approved_by` 为空，另写 `legacy_basis`。
- `owner_approved_at` / `owner_approved_by`：管理员代建时的所有者确认。
- `source_revision`：offer 创建时的来源基线修订，仅展示/审计，不参与接受比较。
- `expiry_cycle`：到期周期编号；每次到期递增，延长只恢复同一 `expiry_cycle` 的来源。
- `pending_expires_at`：当前 pending 阶段（`pending_owner_approval` / 个人 `pending` / `pending_team_approval` / 零成员 `pending_member_acceptance`）的绝对 TTL 截止；创建、重发、owner approve、team approve、零成员状态变化时按对应 TTL 重算；进入 active/terminal 或不再 pending 时置空。TTL worker 只按此字段，不得用 `created_at` 或 `updated_at` 推算，避免复用 grant 后立即过期。CHECK：`status NOT IN ('pending_owner_approval','pending','pending_team_approval') OR pending_expires_at IS NOT NULL`；`pending_member_acceptance` 有成员来源时可为空。
- `expired_from_status`：grant 到期前状态（`active` / `paused` / `pending` / `pending_member_acceptance` 等）；延长时据此恢复父 grant，保留暂停语义。
- `ended_at` / `ended_reason`：业务记录终态原因；终态 grant 必须有 `ended_at`（CHECK：`status NOT IN ('expired','revoked','returned','declined') OR ended_at IS NOT NULL`），迁移回填历史终态。
- `legacy_basis`：迁移来源说明；`legacy_review_deadline`：存量授权复核截止时间（默认迁移后 30 天）。
- `target_group_id` 不存在于当前表，也不新增；原自动绑定目标仅存在于 `group_accounts.account_authorization_id` 绑定行，迁移按该行盘点。
- `grantee_team_id` 外键必须从 `ON DELETE CASCADE` 改为 `ON DELETE RESTRICT`；`grantee_system_account_id` 外键同样改为 `RESTRICT`，系统账户删除改为逻辑删除 + 撤销授权，不得物理级联删除授权历史。`resource_owner_system_account_id` 当前无外键，迁移盘点无孤儿后由应用层保证不物理删除所有者账户；不新增级联删除。
- 唯一约束：用部分唯一索引表达“同一资源同一接收方/团队最多一条非终态业务记录”：
  - 个人：`(resource_type, resource_id, grantee_system_account_id) WHERE grantee_type='system_account' AND status IN ('pending_owner_approval','pending','active','paused')`；
  - 团队：`(resource_type, resource_id, grantee_team_id) WHERE grantee_type='team' AND status IN ('pending_owner_approval','pending_team_approval','pending_member_acceptance','active','paused')`。
- 旧 `active` 唯一索引必须显式 DROP 后重建；`CREATE UNIQUE INDEX IF NOT EXISTS` 不会替换同名旧索引。

### 7.2 `resource_authorizations` 变更

- `status`：扩展 `pending`、`active`、`needs_review`、`paused`、`expired`、`revoked`、`returned`、`declined`。
- `status_reason` / `status_changed_at`：最近一次状态变化原因。
- `effective_source_type` / `effective_source_team_id`：按 §4.3/§4.4 的当前有效来源同步；无 active/dormant 有效来源时置空；不得保留已终态或 needs_review 的旧值。
- `expires_at`：按当前有效来源父 grant 的 `expires_at` 投影；多来源时取有效来源，无有效来源的终态保留最后值用于审计；grant extend/缩短/到期后必须同步重算，不得让 runtime 到期时间与父 grant 脱节。
- `acceptance_mode`：`recipient` / `legacy`；默认 `legacy`，但新代码创建的 runtime 必须显式写 `recipient`，只有迁移存量写 `legacy`。
- `last_source_changed_at`：保留/复用。
- 唯一键 `resource_type + resource_id + grantee_system_account_id` 不变。
- `grantee_system_account_id` 外键从 `ON DELETE CASCADE` 改为 `ON DELETE RESTRICT`；系统账户删除必须逻辑化，不得物理删除带走 runtime/统计历史。
- runtime 不保存来源修订；修订在来源/快照层。

### 7.3 `resource_authorization_sources` 变更

- `grant_id`：父业务 grant ID；expand 相新增 nullable 并回填；`SET NOT NULL` 放到 contract 相（旧二进制全部退出后），避免回滚窗口内旧代码插入 source 时因 NOT NULL 失败；FK `ON DELETE RESTRICT`；必须有索引。`grant_id IS NULL` 的 source 视为未迁移数据，新 gateway/jobs 必须 fail closed（不调度、不自动绑定）并告警，不能当作有效来源。
- `status`：扩展 `pending`、`active`、`dormant`、`needs_review`、`revoked`、`returned`、`declined`、`expired`；`superseded` 仅迁移存量，迁移后不再写入。新增 CHECK：`source_type='manual' OR status <> 'dormant'`，团队来源不得处于 dormant。
- `source_type` / `source_team_id`：`manual` 必须 `source_team_id IS NULL`，`team` 必须非空；新增 CHECK，迁移前先核对历史异常行。
- `acceptance_mode`：`recipient` / `legacy`；默认 `legacy`，但新代码创建的 source（含 pending）必须显式写 `recipient`，只有迁移存量写 `legacy`。
- `accepted_at` / `accepted_by`、`declined_at` / `declined_by`、`returned_at` / `returned_by`、`needs_review_at` / `needs_review_reason`、`needs_review_detail_json`。
- `accepted_source_revision`：接收方最后一次同意的修订；`observed_source_revision`：当前观察修订；`accepted_source_revision_version`：接收方同意时的指纹算法版本；`revision_version`：当前指纹算法版本，accept 必须匹配。accepted revision 与 accepted version 必须成对写入；版本不一致时不得仅比较 HMAC。CHECK：`status NOT IN ('active','dormant') OR (accepted_source_revision IS NOT NULL AND accepted_source_revision_version IS NOT NULL)`。
- `expiry_cycle` / `expired_from_status`：到期周期和到期前状态；延长按这两个字段恢复，`needs_review` 可恢复为 `needs_review`，不会丢失复核状态。新 source 插入时 `expiry_cycle` 必须写父 grant 当前周期（迁移存量除外），不得默认 0 导致跨周期恢复。
- `pending_expires_at`：成员 pending offer 的绝对 TTL 截止；创建、re-invite、extend 恢复为 `pending` 时按 `MemberOfferTTL` 与 grant `expires_at` 重算；离开 `pending` 时置空。worker 只按此字段，不得用 source `created_at` 推算。CHECK：`status <> 'pending' OR pending_expires_at IS NOT NULL`。
- `ended_at` / `ended_reason`。终态来源必须有 `ended_at`（CHECK：`status NOT IN ('revoked','returned','declined','expired') OR ended_at IS NOT NULL`）；迁移回填历史终态的 `ended_at`。
- `source_team_id` 外键必须从 `ON DELETE CASCADE` 改为 `ON DELETE RESTRICT`；团队删除不得级联删除来源历史。
- `authorization_id` 外键必须从 `ON DELETE CASCADE` 改为 `ON DELETE RESTRICT`；runtime 删除前必须先撤销来源并保留历史，不得级联删除 source。
- 唯一约束：用两个部分唯一索引表达非终态唯一，保留历史行：
  - manual：`(authorization_id) WHERE source_type='manual' AND status IN ('pending','active','dormant','needs_review')`；
  - team：`(authorization_id, source_team_id) WHERE source_type='team' AND status IN ('pending','active','dormant','needs_review')`。
- 旧 `active` 唯一索引必须显式 DROP 后重建；`source_team_id` 对 manual 为 NULL，不得依赖普通唯一索引的 NULLS DISTINCT 表达唯一性。

### 7.4 新表/变更表

**`resource_authorization_group_accounts`**

- `authorization_id`、`account_id`、`source_revision`、`revision_version`、`accepted_at`、`updated_at`。
- 主键 `(authorization_id, account_id)`；索引 `account_id`。
- `authorization_id` / `account_id` 外键使用 `ON DELETE RESTRICT`；快照历史不随 runtime/账户删除级联。账户使用逻辑删除，存在快照引用时物理删除必须拒绝，保证审计链不断裂。

**`resource_authorization_blocks`**

- 字段见 §4.7；索引：
  - `(blocker_system_account_id, blocked_system_account_id) WHERE blocked_resource_type IS NULL`；
  - `(blocker_system_account_id, blocked_resource_type, blocked_resource_id) WHERE blocked_resource_type IS NOT NULL`。

**`authorization_notifications`**

- `id`、`system_account_id`、`type`、`grant_id`、`source_id`、`payload_json`、`dedupe_key`、`read_at`、`created_at`。
- `dedupe_key` NOT NULL 且唯一；索引 `(system_account_id, read_at, created_at)`。

**`system_account_authorization_suspensions`**

- 字段见 §4.8；索引 `(system_account_id, lifted_at)`；部分唯一索引 `(system_account_id) WHERE lifted_at IS NULL`。

**`system_accounts` / `system_teams` 逻辑删除**

- `system_accounts` 与 `system_teams` 新增 `deleted_at`；删除写 `deleted_at` 并将 `status` 置 `deleted`，不物理删除。登录、精确用户名/团队名查询、团队列表、团队成员、团队审批都必须排除 `deleted_at IS NOT NULL`。
- 唯一约束调整：`system_accounts.username` 与 `system_teams.name` 的旧全局唯一索引改为 `WHERE deleted_at IS NULL` 的部分唯一索引，允许已删除名称复用；迁移前检查同名活跃行冲突。若产品要求名称永不复用，可保留旧索引，但必须在文档中明确；本设计默认允许复用。
- 团队删除顺序：先按 §4.2 撤销非终态 team 来源/团队 grant，再写 `deleted_at`；成员行保留为历史，不再参与审批/分配。团队物理删除被 `RESTRICT` 外键拒绝。
- 系统账户删除：存在以其为 grantee（`grantee_system_account_id`）、资源归属人（`resource_owner_system_account_id`）、创建者（`created_by`）或其他引用字段的非终态 grant/source/runtime 时拒绝删除（含逻辑删除），要求先回收/暂停；只有历史终态数据时可逻辑删除。不得以删除系统账户绕过接收方归还/屏蔽或清除审计。
- 逻辑删除的账户/团队不得再创建 offer、审批、接受或绑定；历史 grant/source/runtime/快照仍按原 ID 可查询审计。逻辑删除必须复用现有账户/团队停用路径失效会话与访问入口，不能只写 `deleted_at` 而让旧会话继续有效。

**`resource_authorization_offer_cooldowns`**

- `id`、`grantor_system_account_id`、`grantee_type`、`grantee_system_account_id`、`grantee_team_id`、`member_system_account_id`、`resource_type`、`resource_id`、`until_at`、`reason`、`created_at`。
- `grantee_type`：`system_account`（个人/成员级）、`team`（团队审批级）、`team_member`（团队成员级 re-invite）。
- CHECK：`system_account` 必须有 `grantee_system_account_id` 且团队/成员字段为空；`team` 必须有 `grantee_team_id` 且成员/个人字段为空；`team_member` 必须同时有 `grantee_team_id` 和 `member_system_account_id`，个人字段为空。
- 部分唯一索引：
  - 个人：`(grantor_system_account_id, grantee_system_account_id, resource_type, resource_id) WHERE grantee_type='system_account'`；
  - 团队：`(grantor_system_account_id, grantee_team_id, resource_type, resource_id) WHERE grantee_type='team'`；
  - 团队成员：`(grantor_system_account_id, grantee_team_id, member_system_account_id, resource_type, resource_id) WHERE grantee_type='team_member'`。
- 拒绝/归还/屏蔽时按对象 upsert `until_at = now + 24h`：个人来源写 `system_account`；团队审批拒绝写 `team`；团队成员拒绝/归还/被屏蔽写 `team_member`。`grantor_system_account_id` 使用资源归属人（不是管理员 `created_by`），管理员代建不改变 cooldown 键，避免换管理员绕过。创建个人 offer、团队 offer、re-invite 前分别检查对应键；到期后不再阻止。

**`group_authorization_settings` 增量**

- `enabled`、`snapshot_revision`、`snapshot_mode`；不覆盖现有 `scheduling_policy_json`。
- `enabled` 是 runtime 级绑定开关：首次接受建行写 0；同一 runtime 后续来源接受/重新确认保留原值；接收方显式 bind 写 1、unbind 写 0；runtime 终态或分组删除写 0。

- `resource_authorization_grants`：`(grantee_system_account_id, status)`、`(grantee_team_id, status)`、`(resource_owner_system_account_id, status)`、`(status, expires_at)`、`(status, pending_expires_at)`。
- `resource_authorizations`：`(grantee_system_account_id, status)`、`(resource_type, resource_id, status)`。
- `resource_authorization_sources`：`(grant_id)`、`(authorization_id, status)`、`(source_team_id, status)`、`(status, pending_expires_at)`。

### 7.6 迁移与回填

Schema revision：以实施时 `contracts.SchemaRevision` 实际值为准；当前代码为 28（本批已分配并落地 28）；`BusinessSchemaVersion` 同步升至 `business-postgres-gateway-v26`（`system_accounts.deleted_at` 纳入 gateway 契约列，username 唯一性改用 `deleted_at IS NULL` 部分唯一索引），并同步 `MinRequiredRevision`、DDL/步骤 golden 和部署文档。

回填：

> **执行顺序**：存量 `active` / `dormant` / `pending` 来源的 `accepted_source_revision` 回填必须先于 `grant_id` 的 UPDATE。expand 相添加的 `resource_authorization_sources_accepted_revision_check` 虽为 `NOT VALID`，PostgreSQL 仍会对被 UPDATE 的行执行校验；若先写 `grant_id` 而接受修订仍为空，迁移会在停写窗口内直接失败。

1. **`grant_id`**：manual 按 `source.authorization_id -> runtime` 的 `resource_type` + `resource_id` + `grantee_system_account_id` 匹配 `grantee_type='system_account'` 的 grant；team 按 `source.source_team_id = grant.grantee_team_id` 且 `grant.grantee_type='team'` 匹配，runtime 只提供 resource/member，**不得使用不存在的 `runtime.grantee_team_id`**。用 `source.created_at` 落在 grant 生命周期内或审计批次确定唯一父 grant；多候选无法唯一匹配的阻断升级并输出清单，不得按状态猜一条。expand 相保持 nullable；`SET NOT NULL` 放到 contract 相。
2. 存量 `active` / `paused` / `expired` 个人 grant：`acceptance_mode='legacy'`，`accepted_at=created_at`，`accepted_by=NULL`，`legacy_basis='migration'`，`source_revision` 按当前来源账户计算；同时为该 grant 下所有**非终态** manual source 回填 `accepted_source_revision=observed_source_revision=当前指纹`、`revision_version=1`、`accepted_source_revision_version=1`、`accepted_at=created_at`、`accepted_by=NULL`。终态 `expired` source 不背填 `accepted_source_revision`；后续 extend 恢复时按 `needs_review` 处理，接收方重新确认后才可调度。前端/文档不得把 `accepted_by=NULL` 展示为“接收方已接受”。
3. 存量团队 grant：`acceptance_mode='legacy'`，`team_approved_at=created_at`，`team_approved_by=NULL`，`legacy_basis='migration'`；所有**非终态**成员来源 `acceptance_mode='legacy'`，`accepted_at=created_at`，`accepted_by=NULL`，并回填 `accepted_source_revision=observed_source_revision=当前指纹`、`revision_version=1`、`accepted_source_revision_version=1`；终态 `expired` 成员来源同样不背填 accepted，extend 时按 `needs_review` 恢复。存量 `pending_member_acceptance` 且零成员来源的 grant，`TeamMemberlessTTL` 从迁移时间起算，由 worker 到期置 `no_member_offer`，不得永久停留。
4. 旧 source 状态/原因迁移：
   - 父 grant 已 `expired` 且 source 为非终态（`active` / `superseded` 等）-> `expired`；父 grant 已 `returned` / `revoked` 且 source 为非终态 -> 分别转 `returned` / `revoked`；
   - `superseded` + `covered_by_team` + `manual` -> `dormant`，清除 `ended_at/ended_reason/revoked_at/revoked_by`，回填 `expired_from_status` 为空；
   - `superseded` + `covered_by_team` + `team` -> `active`（新模型允许多 team 来源），清除 `ended_at/ended_reason/revoked_at/revoked_by`；父 grant 终态时按父状态处理；
   - `revoked` + `grantee_returned` -> `returned`；
   - `revoked` + `account_deleted` / `team_revoked` -> `revoked`；
   - 其他 `superseded`：`authorization_expired` -> `expired`，`authorization_returned` -> `returned`，`authorization_revoked` -> `revoked`；
   - 未知/空原因阻断升级并输出清单。所有终态回填 `ended_at`（缺失时用 `updated_at`/`created_at`）；仅 `expired` 来源回填 `expired_from_status`（迁移前状态），其他终态保持为空。若前置步骤已给 `superseded` 回填 `accepted_source_revision`，最终映射为 `expired` 的 source 必须清空 `accepted_source_revision` / `accepted_source_revision_version`，保证终态 expired source 没有“已接受修订”，extend 时只能恢复为 `needs_review`；映射为 `returned` / `revoked` / `declined` 的可保留 accepted 仅作审计，不得用于恢复。
5. 存量 group 授权：为每个 `active` / `paused` runtime 建立 `resource_authorization_group_accounts` 快照（当前分组内归属人账户 + 当前来源修订和 `revision_version`）；超过 500 的存量快照标记 `snapshot_mode='legacy_oversized'`，保持可用范围，后续 refresh 只能减少/保持；新接受/新增账户执行 500 上限。`expired` 的 legacy group grant 不允许 extend（没有快照，恢复后无法绑定），必须重新发起/接受；不提供“延长时间时重建快照”的例外。若发现资源为超级分组的存量 grant，阻断升级并输出清单，由产品确认回收或改为普通分组授权，不得按成员组静默展开。
6. 存量 `group_accounts` 绑定：保留；通过 `account_authorization_id` 识别 legacy 绑定；不新增 `target_group_id`（该列不存在）。
7. 存量 `group_authorization_settings`：仅 `active` / `paused` runtime 保留 `enabled` 原值；缺失行按现有 `COALESCE(...,1)` 语义视为已绑定，迁移时补行并标记 legacy。终态 runtime 的 `enabled` 必须写 0；缺失行补 0 或保持无行，不得补成 1，避免已归还/撤销的授权分组仍被路由策略启用。同一 runtime 首次接受建行写 0，后续 source accept/reconfirm 保留原值，显式 bind 才写 1。
8. 团队审批人：使用 `system_teams.created_by`（NOT NULL）；若该账户不存在或非 active，管理员回退；不强制回填。
9. 一次性通知：通过 maintenance 具名 upgrade step 或受控 jobs 任务向所有有 inbound active 授权的接收方发送“请复核你收到的授权”通知，**团队授权必须覆盖每个已接受成员来源的成员接收方**（通知类型 `legacy_review_required`，dedupe key 按接收方+grant/source 稳定生成），提供归还/屏蔽入口；通知表使用 `dedupe_key` 唯一键，重复执行不重复插入；不在 gateway 启动时执行一次性数据处理。
10. 存量授权复核截止：legacy grant 写入 `legacy_review_deadline = 迁移时间 + 30 天`（可配置）。截止后仍未重新确认的 legacy 来源转为 `needs_review`，网关阻断，直到接收方重新确认或归还/屏蔽；通知双方。
11. 状态 CHECK：为 grants/sources/runtime 的 status、source_type、grantee_type 增加 CHECK，按 `NOT VALID -> 回填 -> VALIDATE CONSTRAINT` 落地；不得直接假设历史值全部合法。source status CHECK 在 expand 相必须保留 `superseded` 词表（旧二进制回滚窗口仍可能写入），contract 相删除 `superseded` 时再替换 CHECK。同时增加 `source_type`/`source_team_id` 互斥 CHECK；历史异常行阻断升级并输出清单。
12. 唯一索引：显式 `DROP INDEX IF EXISTS` 旧索引 `idx_resource_authorization_grants_active_user_unique`、`idx_resource_authorization_grants_active_team_unique`、`idx_resource_authorization_sources_active_manual_unique`、`idx_resource_authorization_sources_active_team_unique`，再按 §7.1/§7.3 建立新的部分唯一索引；`CREATE UNIQUE INDEX IF NOT EXISTS` 不会替换同名旧索引，必须显式重建。迁移前按新键去重，冲突行阻断升级并输出清单。
13. 终态可排序性：所有终态 source 必须回填 `ended_at`；`resource_authorizations` 终态选择按 `ended_at DESC NULLS LAST, id DESC` 排序；终态 source 不得再更新 `updated_at`。新增 CHECK：非终态允许 `ended_at` 为空，终态必须非空。
14. `revision_version` 升级：指纹算法版本变化时，maintenance 具名步骤把所有非终态 source 置 `needs_review`、写 `observed_source_revision` 和新版本、重算 runtime、发通知；分组快照行保留旧 `revision_version`，网关因版本不一致排除，接收方先重新确认分组来源恢复 source `active` / `dormant`，再逐账户 reconfirm 后才恢复；不得把旧快照批量重写为新版本。升级步骤幂等，按版本号只跑一次。
15. 外键：`resource_authorization_grants.grantee_team_id` / `grantee_system_account_id`、`resource_authorization_sources.source_team_id` / `authorization_id`、`resource_authorizations.grantee_system_account_id` 从 `ON DELETE CASCADE` 改为 `ON DELETE RESTRICT`；团队/系统账户删除统一走逻辑删除 + 撤销来源，禁止物理删除带走授权历史。迁移前先盘点是否存在已物理删除团队/账户导致的孤儿行，孤儿行保留并标记 `legacy_orphan_team` / `legacy_orphan_account`，不静默删除；存在孤儿行时阻断 FK 收紧并输出清单。
16. `expiry_cycle` / `expired_from_status`：迁移时对所有 grant/source 置 `expiry_cycle=0`；对终态 `expired` grant/source 置 `expired_from_status`（grant 按迁移前状态推断 active/paused/pending 等；source 按迁移前状态推断 active/dormant/pending/needs_review；无法推断时置 `pending` 并标记待复核）。后续到期由 worker 递增 grant `expiry_cycle` 并写入 grant/source 的 `expiry_cycle` 和 `expired_from_status`。legacy expired grant 无法可靠判断是否曾 paused 时，`expired_from_status` 置 `active` 并标记 `legacy_expiry_unknown`，extend 前要求管理员确认；不得静默解除暂停。
17. `pending_expires_at`：迁移时对当前处于 pending 状态的 grant/source 按迁移时间重新起算对应 TTL（个人/owner approval/team approval/member offer/team memberless），保证 legacy pending 不会因旧 `created_at` 立即过期；`pending_member_acceptance` 只有零成员来源时设置 grant TTL，已有成员来源时置空；active/terminal 置空。写入后由 worker 只按该字段扫描。
18. `system_accounts` / `system_teams` 逻辑删除：新增 `deleted_at`；显式 DROP 旧的 `system_accounts.username` / `system_teams.name` 全局唯一索引，按 `WHERE deleted_at IS NULL` 重建部分唯一索引；迁移前检查同名行，全部现有行 `deleted_at IS NULL`，不会冲突。旧索引名与 `CREATE UNIQUE INDEX IF NOT EXISTS` 行为必须按 §7.6 第 12 条同样处理，不能只改索引定义；同时检查注册/团队创建等 `ON CONFLICT` 推断是否需要带部分索引谓词，避免升级后插入报错。
19. 资源孤儿：若 grant 的 `resource_type/resource_id` 指向的账户/分组已不存在或已逻辑删除，所有非终态 source/grant 置 `revoked`（`ended_reason=resource_deleted`），runtime 重算为终态并清空有效来源；同时停用接收方 `group_accounts.enabled=0`、`group_authorization_settings.enabled=0`，账户资源派生实例置 `status=disabled` / `schedulable=0`，确保网关与页面在下一轮对账前也不能继续使用已删除资源。不得把孤儿资源继续作为 legacy active 保留，也不得因快照为空而留下 active runtime。孤儿行保留审计并在 dry-run 清单中列明。
20. 迁移幂等：升级步骤中途失败后必须可安全重跑；已回填的 `accepted_source_revision` / `accepted_source_revision_version` / `accepted_at`、`pending_expires_at`、快照行与 `group_authorization_settings.snapshot_revision` 在重跑时不得被覆盖或重置，重复执行只补缺失项。`snapshot_revision` 使用统一 canonical HMAC（排序后的账户 ID + `source_revision` + `revision_version`，逐段 NUL 分隔），迁移、refresh-scope 与逐账户 reconfirm 共用同一算法；零账户快照也必须写入空集合 HMAC，不得留 NULL。

发布顺序（同一发布批，不做旧/新双写）：

1. 备份生产库；确认 maintenance `upgrade` 可用。
2. maintenance upgrade 执行 expand + 回填（停写窗口）；先 dry-run 输出盘点与冲突清单。
3. 部署 gateway/jobs/frontend；新代码只写新状态，不再接受 `targetGroupId`，不再自动建实例/绑定。
4. 执行存量授权复核通知与 legacy 截止任务。
5. postflight：核对 active grant/runtime/source/instance/binding 数量与迁移前一致；抽查 legacy 授权可调度；新 pending offer 零实例/零绑定；chat-pinned 路径受快照/修订约束。
6. contract 相在后续版本删除旧 `superseded` 词表；旧 active-only 索引已在 expand 相替换，不重复删除；不删除 `target_group_id`（不存在）。

回滚：

- expand 相之前可以正常回滚。
- revision 28 步骤为 `RequiredBeforeStartup=true` 且 `Destructive=true`，必须用 `--phase=all` 完成；完成后 `schema_state.min_readable_binary_revision=28`，旧二进制（schemaRevision=27）会被启动门禁拒绝，数据步骤也已写入 legacy 回填、runtime 撤销、快照与复核通知。因此升级后不存在“换回旧二进制”的回滚路径，只能前向修复或恢复停写备份。旧 binary 创建的 source 不写 `grant_id` 的兼容假设只在升级前旧库或恢复备份后的窗口成立；再次升级必须幂等补跑回填。
- 一旦产生 `pending` / `needs_review` / `dormant` / `declined` 等新状态写入，**禁止回滚到旧二进制**：旧 gateway 会在 grant 非 active 时 revive 为 active 并自动写 `group_accounts`，旧 jobs 不识别新状态，等于重新打开单方面注入路径。此时只能前向修复，或用备份恢复并接受数据回退。
- 回滚窗口内不得重新启用 `targetGroupId` 自动绑定；不得只回滚前端而保留新 API 行为。

## 8. 网关与调度

### 8.1 预检

网关授权预检必须同时满足（按资源类型分支）：

**账户资源：**

- runtime `resource_authorizations.status = 'active'`，且其有效来源的父 grant 为 `active`；
- 来源 `status = 'active'`（或 runtime 已按 §4.4 从 `dormant` 提升为 active）；
- `accepted_source_revision` 与当前来源账户指纹一致，且 `revision_version` 一致；
- 授权实例 `status=active`、`schedulable=1`、未删除；
- `group_accounts.enabled=1` 且绑定 `account_authorization_id` 对应当前 runtime；
- 来源账户可用（沿用现行 `effectiveAvailability`：状态、调度、冷却、过期、凭据、连接等）。

**分组资源：**

- runtime `status = 'active'`，且其有效来源的父 grant 为 `active`；
- 来源 `status = 'active'`；
- `group_authorization_settings.enabled=1`；
- 账户在 `resource_authorization_group_accounts` 快照中；
- 账户当前仍是分组有效成员；
- 账户当前归属人仍是分组归属人（`accounts.system_account_id = groups.system_account_id`）；
- 账户当前接受修订与快照一致，且 `revision_version` 一致；
- 分组存在、属于资源归属人、未删除/停用；
- 叠加账户可用性（状态、调度、冷却、过期、凭据、连接、模型）。

**通用：**

- 不得把 `needs_review` 当作可用但降权；必须硬阻断。
- 父 grant `paused` 的来源不得被当作有效 active 来源；暂停必须真实阻断。
- 预检不得只信任 runtime 状态；必须校验父 grant、来源状态和接受修订，防止投影滞后。

### 8.2 分组授权候选

- 只使用 `resource_authorization_group_accounts` 中存在的账户；
- 账户当前仍是分组有效成员（`group_accounts.enabled=1`）；
- 账户当前归属人仍是分组归属人；
- 账户当前接受修订与快照一致，且 `revision_version` 一致；
- `group_authorization_settings.enabled=1`；
- 带 `authorization_instance_authorization_id` 的他人授权实例不进入候选（沿用现行防穿透）；
- 叠加现有账户可用性闸（`status` / `schedulable` / 时间计划 / 冷却 / `account_expires_at` / 凭据 / 连接）；
- 新增账户未刷新范围前不可用；刷新后失效缓存；
- chat-pinned、媒体、realtime 等所有加载路径复用同一过滤，不得绕过快照/修订/开关。

### 8.3 缓存与失效

- 接受、重新确认、逐账户 reconfirm、拒绝、归还、屏蔽、暂停、恢复、回收、到期、延长、来源 material change、范围刷新、绑定/启用/停用（unbind）都必须在提交后失效相关网关运行时缓存；沿用现有 `InvalidateGatewayRuntime` 或等价按账户/授权定向失效。
- 缓存 TTL 仍可作为兜底，但不得依赖 TTL 作为安全边界；关键状态变化必须主动失效。
- 网关不得把 `needs_review` 当作可用但降权。
- chat-pinned 专用直取路径必须共享授权范围/快照/修订闸门；只能跳过健康可用性（禁用/冷却/过期/禁调度），不能跳过授权状态。

### 8.5 TTL、到期 worker 与 cooldown

TTL 规则：pending 类对象（`pending_owner_approval`、个人 `pending`、团队 `pending_team_approval`、成员 pending 来源、零成员 `pending_member_acceptance`）使用默认 TTL；若同时设置了 `expires_at`，取 `min(expires_at, now+TTL)`，显式时间不能把 pending 延长到默认 TTL 之后。已接受 grant 只使用 `expires_at`（未设置则永不过期），不再叠加 pending TTL。grant 与 source 的 `pending_expires_at` 在进入对应 pending 状态、重发、owner approve、re-invite、extend 恢复时重算，worker 以它为准；不得用 `created_at` 导致复用 grant 立即过期。`pending_owner_approval` 下的个人 source 不独立按 `PendingOfferTTL` 先到期，其 `pending_expires_at` 跟随 grant 的 `OwnerApprovalTTL`；owner approve 后从批准时刻重置为接收方接受窗口。

| 对象 | 默认 TTL | 到期后 |
| --- | --- | --- |
| `pending_owner_approval` grant | `OwnerApprovalTTL` 7d | grant `expired`（`owner_approval_timeout`）；个人 offer 的 source `expired`，团队 offer 无成员来源；通知管理员/所有者 |
| 个人 `pending` grant | `PendingOfferTTL` 7d | grant `expired`（`offer_expired`）；source `expired`；runtime 按 §4.4 重算 |
| 团队 `pending_team_approval` | `TeamApprovalTTL` 14d | grant `expired`（`team_approval_timeout`）；无成员来源；通知授权方/审批人 |
| 团队零成员 `pending_member_acceptance` | `TeamMemberlessTTL` 14d | grant `expired`（`no_member_offer`）；不按空集聚合为 declined |
| 团队成员 `pending` source | `MemberOfferTTL` 7d | source `expired`（`offer_expired`）；团队 grant 按 §4.2 聚合 |
| 已接受 grant 的 `expires_at` | 用户设置 | grant 与非终态 source `expired`；grant 写 `expiry_cycle`/`expired_from_status`（到期前 grant 状态），source 写各自 `expiry_cycle`/`expired_from_status`；runtime 按 §4.4 重算 |

worker 规则：

- 到期扫描按状态索引分批执行，幂等；同一 grant 的 `expiry_cycle` 只递增一次，同一 source 只写一次 `expired`。`pending_member_acceptance` 的 grant `pending_expires_at` 只对零成员来源生效；已有成员来源时必须为重算为 NULL 或忽略，不得用 `TeamMemberlessTTL` 提前终止有成员待确认的团队。同一批内先处理 grant 自身到期（含个人 pending TTL、团队成员来源所属 grant 的 `expires_at`），再处理 `MemberOfferTTL`/`OwnerApprovalTTL`/`TeamApprovalTTL`/`TeamMemberlessTTL`，避免同一来源被错误归因为成员 offer 过期而无法随 grant extend 恢复。`expiry_cycle` 只由 grant 到期事件推进：仅 grant 到期时仍非终态的 source 写入新周期；更早由 `MemberOfferTTL` 过期的成员来源保留原周期，不得被后续 grant 到期提升，grant extend 不得复活，必须显式 re-invite。
- 到期只处理非终态 source；终态 source 保持原状；不得把旧 `expired` 覆盖更新的 `returned` / `revoked` / `declined`。
- 到期后按 §4.4 重算 runtime；只有 runtime 终态才停用绑定/分组开关；其他有效来源继续服务。
- 到期通知双方；被屏蔽的接收方按 §4.7 抑制该授权方的新 offer 通知；已保留来源的安全通知仍发送。
- cooldown 使用 `resource_authorization_offer_cooldowns` 表（§7.4），按授权方 + 个人接收方/团队/团队成员 + 资源键分别 upsert `until_at=now+24h`；创建个人 offer、团队 offer、re-invite 前检查对应键，到期后不再阻止。成员级 cooldown 不得扩大为团队级，团队级 cooldown 也不得阻止向未命中的成员 re-invite。不得只依赖内存或日志推导。

## 9. 前端设计

### 9.1 信息架构

`我的授权` 菜单组：

`统一授权管理`：

- `统一授权`：管理全量业务记录，增加 pending_owner_approval/pending/team approval/needs_review/declined 筛选；不展示接收方分组。
- `授权团队`：团队列表/成员维护保持管理员权限；团队审批信息展示 `created_by`；管理员可查看待审批团队 offer。
- `团队消耗明细` / `用户消耗明细`：保持。

### 9.2 授权创建

- 资源选择后，接收方输入改为“精确用户名”或“精确团队名”，不再加载全量用户/团队下拉。
- 个人授权不再显示“目标分组”；提交后提示“已发送待确认，接收方接受后需自行绑定分组”。

- 授权列表显示 pending_owner_approval/审批中/已接受/已拒绝/需重新确认；不再显示“目标分组”。

### 9.3 接收方授权中心

- 待确认：显示授权方、资源、来源账户、供应商、endpoint host、代理摘要、额度、到期、风险提示；按钮“接受 / 拒绝 / 屏蔽”。
- 已生效：显示状态、绑定/启用状态、额度、到期；按钮“绑定分组 / 更换分组 / 启用分组 / 归还 / 屏蔽”。
- 需重新确认：显示变更内容（字段级 diff，例如“上游地址 host 已变更”“代理池成员已变更”）；按钮“查看并重新接受 / 归还 / 屏蔽”。
- 分组授权：显示“未启用/已启用”；未启用时提供“启用授权分组”，启用后引导加入路由策略；已启用时提供“停用授权分组”；提供“查看范围差异”“刷新范围”并逐账户展示新增/修订变化。
- 已拒绝/已归还：只读历史；可以查看并解除屏蔽。
- 团队来源：显示“来自团队 X 的授权”，成员只能归还/拒绝自己的成员 offer；不显示“归还团队授权”按钮；接受时提示团队来源优先，并提供“保留/不保留个人回退”选择。
- 待绑定状态：账户列表/授权中心显示“未绑定分组，尚未参与调度”，提供“去绑定”入口。
- 通知徽标：待确认、需重新确认、团队待审批、所有者待确认。
- 资源所有者：显示管理员代建、待自己确认的 offer，按钮“同意以我名义授权 / 拒绝”。

### 9.4 团队审批人

- 团队页面显示“待审批授权”列表；详情展示资源、来源账户、供应商、endpoint host、额度、成员数、风险提示。

- 自审批请求不出现审批按钮；提示由管理员代行。

## 11. 统计、审计与通知

- 统计口径不变：只有实际产生的请求进入 usage；pending/declined 不产生消耗；接受但未绑定/未启用不产生调度，因此不产生授权消耗（账户测试等显式动作按现有测试口径处理）。

## 12. 迁移与发布

### 12.1 存量盘点（实施前）

只读盘点生产：

- active/paused/expired personal/team/group 授权数量；
- 每个授权方→接收方/团队的分布，识别单方大量授权；
- 授权实例数量、`group_accounts` 中 `account_authorization_id` 非空绑定数量；
- `resource_authorization_sources` 中 `superseded` 数量及 `ended_reason` 分布；
- 是否存在 `grant_id` 回填无法唯一匹配的 source；
- 授权 grant 的 `resource_id` 是否仍存在（账户/分组孤儿），以及孤儿对应的 source/runtime/实例；
- 团队 `created_by` 账户不存在/非 active 的数量；
- 分组账户数分布（最大值、超过 500 的分组数）；
- 按 `group_kind` 统计分组授权，识别超级分组存量授权；
- 来源账户 `base_url`/模型映射/代理在授权后是否变更过（如审计/操作日志可查）；
- 现有授权是否已有异常/滥用迹象；
- chat-pinned/realtime/媒体等加载路径的实际使用面，确认新闸门覆盖。

盘点需要生产只读权限，按 `.local/project-resources/prod/` 的运维手册执行；不在本文写具体连接信息。

### 12.2 迁移步骤

账户来源修订按账户授权记录引用的资源计算。接收方实例由原授权关联管理，其占位凭据不参与来源修订。分组范围快照中的账户按实际成员补算修订。

1. 备份生产库；确认 maintenance `upgrade` 可用。
2. expand schema：新增列/表/状态词表/索引/CHECK；不删除旧列；显式 DROP 旧 active-only 唯一索引后重建。`authz-recipient-consent-governance` 注册为 `Destructive=true` / `RequiredBeforeStartup=true`，必须使用 `upgrade --phase=all`（停写 + 可恢复备份）执行，不得用 `--phase=expand` 跳过；`--secret` 必填，且与来源修订 HMAC 使用同一密钥。升级管线在 expand 相检测到该步骤未 applied 且 `Satisfied=false`，或账本残留 `running`/`outdated-impl` 时直接 blocked。
3. 回填 §7.6 的 legacy 接受状态、`grant_id`、dormant 来源、group 快照、group settings、团队审批人。
4. 部署 gateway/jobs/frontend（同一发布批）；新代码只走新契约。
5. 执行存量授权复核通知和 legacy 截止任务。
6. postflight 核对数量与抽样调度；检查 pending 零实例/零绑定、group settings=0、chat-pinned 受快照约束。
7. 观察期：pending 创建是否零实例/零绑定；legacy 授权是否正常；needs_review/屏蔽/归还路径是否符合预期；收件箱/通知是否可用。
8. contract 相：确认无旧二进制读取后，删除 `superseded` 词表；旧 active-only 索引已在 expand 相替换，不重复删除；更新旧设计文档和帮助文档。

### 12.3 回滚

- schema 保持向前兼容；但旧二进制只对新状态安全“不可用”，并不安全——旧 gateway 会在 grant 非 active 时 revive 并自动绑定。
- expand 相之前可正常回滚；expand 相之后、未产生新状态写入时可回滚二进制，且必须 gateway/jobs/frontend 同批；`grant_id` 在 expand 相保持 nullable，旧 binary 写入的 source 可以为空，再次升级必须幂等补跑回填。
- 产生 `pending` / `needs_review` / `dormant` / `declined` 等新状态写入后，禁止回滚到旧二进制；只能前向修复，或用备份恢复并接受数据回退。`min_readable_binary_revision` 在 contract 相推进后旧 binary 会被 schemagate 拒绝；contract 相执行 `grant_id SET NOT NULL` 后不再允许旧二进制写入。
- 回滚后不得恢复 `targetGroupId` 自动绑定路径；不得只回滚前端而保留新 API 行为；不得混合旧 jobs。

## 13. 验收标准

### 13.1 安全验收（必须全过）

1. 任意用户创建个人/团队 offer 后，数据库新增 `accounts` 授权实例数 = 0，新增 `group_accounts` 数 = 0，新增分组快照仅在接收方接受后出现；该新来源的网关候选数 = 0（同一 runtime 已有其他有效来源时，其候选不受影响）。
2. 接收方首次接受（无其他有效来源）后：账户资源授权实例存在但 `group_accounts` 仍为 0；分组资源快照存在但 `settings.enabled=0`；网关候选数 = 0。
3. 只有接收方本人可以把授权实例绑定到自己的分组、把授权分组启用/停用并加入自己的路由策略；管理员接口、授权方接口和通用账户/分组/路由策略接口都不能代绑定/代启用/代停用。
4. 归还/拒绝/屏蔽后，只有 runtime 进入终态时才写绑定 `enabled=0` 或 `settings.enabled=0`；runtime 仍 active/paused/needs_review/pending 时保留绑定；重新发起 offer 后，未接受前该来源无候选（其他有效来源不受影响）；接受后仍需重新绑定/启用才有候选。
5. 团队 offer 未经团队审批人同意不产生成员来源；成员未接受不产生实例/快照；新成员加入只产生 pending 来源，不产生实例/快照；零 eligible 成员时保持 `pending_member_acceptance`，不得立即终态。
6. 账户资源的来源 `base_url`（含查询串）/代理（含池策略/权重/优先级/成员开关）/协议档案/连接 preset/端点模式/支持模型/模型映射/OAuth 主体/API Key 指纹变更后，受影响非终态来源进入 `needs_review`，网关硬阻断；接收方携带 `expectedRevision` 重新确认后才恢复；终态来源不被改写。分组资源的账户级变化只排除对应快照行，不把分组来源整体置 needs_review。
7. 分组授权新增账户不进入已接受快照；未显式 refresh 前不参与调度；refresh 必须携带 `expectedSnapshotRevision`，集合变化返回 409，不能静默纳入未审阅账户。
8. 普通用户无法通过 API 获取全量用户/团队列表或他人分组列表；精确用户名/团队名 + 团队审批可用；屏蔽/cooldown/限额统一返回 `offer_suppressed`。
9. per-grantee/per-grantor/全局限额、cooldown、pending TTL、屏蔽名单生效；单授权方对大量不同目标也受限；被屏蔽授权方后续 offer 被拒绝。
10. 管理员不能代接受/代绑定/代所有者确认；可以回收、暂停发起授权。管理员代资源所有者创建 offer 时必须进入 `pending_owner_approval`，所有者确认后才对接收方可见。
11. 团队审批禁止自审批（包括管理员代建时审批人就是资源归属人的情况）；管理员代行仅限审批人失效/缺失/与授权方同一；团队成员接受不受影响。
12. 暂停父 grant 后，该来源不得继续被当作 active；runtime 按 §4.4 推导为 paused，除非存在其他 active/dormant 来源可回退；网关硬阻断被暂停来源。
13. 新建个人 pending offer 的 runtime 不得被推导为 revoked；pending/needs_review 下的接受入口可用且修订校验正确。
14. chat-pinned、媒体、realtime 等所有加载路径在来源 needs_review、账户被移出快照、`settings.enabled=0` 或 settings 行缺失（非 legacy 按 0 处理）时不得返回候选；pinned 只能跳过健康可用性。
15. 管理员暂停发起授权后，被暂停的资源归属人不能创建、延长、re-invite、恢复、确认管理员代建 offer 或增加额度；只能缩短/暂停/回收；管理员代建 offer 不得绕过归属人的暂停，被暂停管理员也不能作为创建者发起。
16. legacy 复核截止后未重新确认的存量来源进入 `needs_review`，网关阻断；重新确认后恢复。
17. 团队审批通过但零成员来源时，不得因“全部来源 declined/expired”的空集全称命题立即终态；保持 `pending_member_acceptance` 直到 `TeamMemberlessTTL` 或 `expires_at`。
18. 延长恢复已接受来源且 `expired_from_status` 非 `paused` 时 grant 必须为 `active`；不得把已接受来源恢复在 `pending` / `pending_member_acceptance` 父下导致 runtime 落成终态；`expired_from_status='paused'` 只能恢复为 `paused`；指纹不一致时恢复为 `needs_review`；当前状态 `paused` 不得直接 extend；`returned`/`declined`/`revoked` 不复活；团队因 `all_member_offers_expired` / `no_member_offer` / `team_approval_timeout` / `owner_approval_timeout` 结束的 `expired` 不可 extend，早期 `MemberOfferTTL` 过期来源不因 grant 后续到期被恢复。
19. 分组资源首次接受才创建快照和 `settings.enabled=0`；同一 runtime 第二次来源 accept/reconfirm 不重建快照、不重置 enabled；已启用绑定不得因 accept 被关闭。
20. 分组范围变化按逐账户 `reconfirm` 接受修订；`refresh-scope` 只处理新增/移除并携带 `expectedSnapshotRevision`；二者冲突返回 409，不得用一次 refresh 批量接受修订变化。
21. 存量非终态来源回填 `accepted_source_revision` / `accepted_source_revision_version` / `observed_source_revision` / `revision_version` 后，legacy 授权仍可调度；`grant_id` 在 expand 相保持 nullable，contract 相才 `SET NOT NULL`；旧二进制回滚窗口插入 source 不因 NOT NULL 失败，新代码遇到 `grant_id IS NULL` fail closed 并告警。
22. 管理面 `POST /accounts/{id}/return-authorization`、`POST /groups/{id}/return-authorization` 已移除（404，不保留 410 兼容）；管理员不能以“归还”名义代替接收方。
23. 资源所有者可通过 `direction=owner_pending` 列出待确认的管理员代建 offer；接收方在所有者确认前无法通过 source 详情/操作端点看到该 offer（404）。
24. `resource_authorization_offer_cooldowns` 生效：拒绝/归还/屏蔽后 24h 内同一授权方+个人接收方/团队/团队成员+资源不能按对应层级新建 offer 或 re-invite；成员级 cooldown 不阻止团队其他成员 re-invite，也不阻止新建团队 offer；团队级 cooldown 不阻止向未命中成员 re-invite；屏蔽只抑制新 offer/`offer_suppressed` 通知，不抑制已保留来源的安全通知。
25. 终态来源的 `ended_at` 已回填，runtime 终态按 `ended_at DESC NULLS LAST, id DESC` 选最近终态；旧 `expired` 不覆盖新 `returned`/`revoked`/`declined`。
26. 指纹算法 `revision_version` 升级时，maintenance 步骤把所有非终态来源置 `needs_review` 并提供重新确认入口；不得只让网关永久阻断 active 来源。
27. 复用 grant 重新发起后，旧 `accepted_at/by`、`team_approved_at/by`、`owner_approved_at/by`、`ended_at/ended_reason`、`expired_from_status`、`legacy_basis`、`legacy_review_deadline` 已清空，`pending_expires_at` 已按新 TTL 重算；个人必须重新接受、团队必须重新审批，旧来源保持终态不可改写。
28. 分组授权只接受 `group_kind=standard`；超级分组创建/接受/迁移均返回 `group_kind_conflict`，不会按超级分组成员展开为普通分组授权。
29. 通用账户删除、批量删除、导入/导出、克隆和转移接口不得删除、复制授权实例或改变其归属；通用创建/导入/更新接口不得写入或清空 `authorization_instance_authorization_id` / `account_authorization_id`，不能伪造授权归属；接收方只能归还来源，授权方只能回收。
30. 接收方不能通过通用账户接口修改授权实例的凭据、`base_url`、供应商/协议、模型/映射、代理或连接；只能修改本地调度与绑定字段，来源字段变更只能由资源归属人触发并走 material change。
31. legacy expired 分组授权重新发起后，接受时快照不存在且只有历史终态来源，必须建立新快照和 `settings.enabled=0`，不得返回 `snapshot_missing_requires_review` 造成无法接受。
32. 已接受非终态分组来源的快照缺失时，`scope-diff` 返回 `snapshot_missing=true` 和全量 diff；`refresh-scope` 显式 `rebuildMissingSnapshot=true` 可重建且 `settings.enabled=0`，正常 refresh 不得用该参数绕过 CAS。
33. 资源归属人变化（账户/分组 `system_account_id` 改写）且资源自身是授权对象时，全部非终态来源和 grant 被撤销；reconfirm 不能把旧授权继续用于新归属人的资源。账户仅是他人分组快照成员时只移除该快照行，不撤销分组授权。
34. `paused` grant 到期后 extend 必须恢复为 `paused`，不得自动解除暂停；`pending_owner_approval` 到期不允许 extend，必须重新发起并重新获得所有者确认。
35. 管理员代资源所有者创建的 offer，资源所有者可通过 `direction=owned` 查看并仍可暂停、恢复、延长、缩短或回收；owner 控制端点按 `resource_owner_system_account_id` 授权，不因 `created_by` 是管理员而让创建者获得覆盖所有者决定的 owner 控制权；管理员治理动作走 §6.4 并审计。
36. `revision_version` 升级后，分组来源先重新确认恢复 `active` / `dormant`，分组快照行旧版本仍被网关排除；接收方逐账户 reconfirm 后才恢复，不得批量重写快照版本绕过复核。
37. legacy expired grant 的终态 expired source 未背填 `accepted_source_revision`；extend 恢复时转 `needs_review`，接收方重新确认后才可调度，不得静默恢复 active。
38. 账户授权重新确认成功后，实例继承字段与来源当前协议/能力一致；同步失败时接受失败且来源保持 `needs_review`，不得让实例继续使用旧协议配置。
39. 存在以其为 grantee/资源归属人/创建者的非终态授权 grant/source/runtime/授权实例的系统账户拒绝删除（含逻辑删除），必须先回收；仅有历史终态数据时只能逻辑删除。被授权来源或分组快照引用的账户只能逻辑删除，物理删除被拒绝，不因 FK RESTRICT/CASCADE 冲突丢失历史或统计断链。
40. 分组删除前必须先把非终态 group 来源置 revoked、个人 grant/团队 grant（含零来源 pending）置 revoked 并重算 runtime；不得物理删除授权 source/runtime/grant 历史；接收方不再看到或调度已删除分组。

### 13.2 功能验收

- 个人账户授权：创建 -> 所有者确认（如管理员代建）-> 接收方接受 -> 未绑定不可调度 -> 绑定 -> 可调度 -> 归还 -> 不可调度 -> 重新发起 -> 重新接受 -> 重新绑定 -> 可调度。
- 个人分组授权：创建 -> 接受 -> 快照 + settings=0 -> 启用 -> 加入路由策略 -> 可调度 -> 归还 -> 不可调度 -> 重新接受 -> 重新启用 -> 可调度。
- 团队账户授权：创建 -> 审批 -> 成员接受/拒绝 -> 实例/绑定 -> 暂停/恢复/到期/回收 -> 成员回退；新成员只收 pending；自审批被拒绝；零 eligible 保持 pending_member_acceptance。
- 团队分组授权：创建 -> 审批 -> 成员逐人接受 -> 每成员快照/settings -> 成员启用并加入路由策略 -> 成员归还/移除只影响本人 -> 新成员只收 pending。
- 来源优先级：个人 active -> 团队 active（个人 dormant）-> 团队结束（个人恢复 active）；接收方选择不保留回退时个人不恢复；屏蔽 `return_existing=false` 时现有来源保持。
- 多来源：team 归还/回收/到期时 manual dormant 回退，绑定保持；personal 归还时 team 仍 active，绑定保持；只有 runtime 终态才停绑定。
- 额度：接收方能在 offer 详情看到额度；额度命中返回现有 429 文案；额度变更通知。
- 通知/操作日志/审计：所有状态变化有记录，viewer 正确；所有者确认、重新确认、解除屏蔽、范围刷新、管理员代行均有审计。
- 前端：授权中心、待确认、待绑定/待启用、范围差异、团队审批、屏蔽、暂停状态、错误/空态/移动端。

### 13.3 迁移验收

- 迁移前后 active grant/runtime/source/instance/binding 数量对得上（允许快照表新增、superseded 状态映射）。
- 每条存量 source 的 `grant_id` 在回填后指向正确父 grant；无匹配行阻断升级；expand 相允许 NULL，contract 相才 NOT NULL。
- 存量 legacy 授权仍可调度（除非超过 legacy 复核截止）；非终态 manual/team source 的 `accepted_source_revision` / `observed_source_revision` / `revision_version` 已回填；存量 group 授权快照覆盖 active/paused 当前可用账户。
- 分组快照 `snapshot_revision` 与 canonical HMAC 一致：排序后的 `account_id` + `source_revision` + `revision_version` 逐段 NUL 分隔后 HMAC；零账户快照写入空集合 HMAC 且 `settings.enabled=1`；快照行的 `source_revision`/`revision_version` 与账户当前修订一致。
- 父 grant 已终态时，仍为非终态的 legacy source 正确映射为 `expired` / `returned` / `revoked`，终态 `ended_at` 有值；映射为 `expired` 的来源清空接受修订并记录迁移前 `expired_from_status`，后续 extend 只能恢复为 `needs_review`。
- 孤儿账户/分组 grant 的所有非终态 source/runtime 置 `revoked`（`resource_deleted`），接收方 `group_accounts.enabled=0`、`group_authorization_settings.enabled=0`，账户资源派生实例 `status=disabled` / `schedulable=0`。
- 二次 `Apply` 幂等：不重复建快照/通知，不覆盖已回填的接受修订、`accepted_at`、`pending_expires_at` 或非空 `snapshot_revision`；失败重跑只补缺失项。
- `superseded` 按 `source_type` + `ended_reason` 正确映射：`manual` + `covered_by_team` 转 dormant 后可回退；`team` + `covered_by_team` 转 active；`grantee_returned` 转 returned；`account_deleted`/`team_revoked` 转 revoked；expired/returned/revoked 不被错误复活；终态 `ended_at` 已回填。
- 新部分唯一索引生效，四个旧 active-only 索引已显式删除；状态 CHECK 校验通过；团队外键改为 RESTRICT，无物理级联删除。
- legacy 复核通知只发一次（dedupe_key），已读状态正确；截止任务幂等；零成员团队 grant 不会被空集聚合误判。
- `expired` 的 legacy group grant 不允许 extend，必须重新发起/接受，不会出现 active 但无快照/无法绑定的状态；不提供“延长时重建快照并走 scope 审阅”的替代路径。
- 回滚演练明确：expand 相可回滚且 `grant_id` 可空；产生新状态或 contract 相后不得回滚旧二进制；备份恢复流程可用。

## 14. 风险与取舍

| 风险 | 说明 | 缓解 |
| --- | --- | --- |
| 接受/绑定增加操作步骤 | 接收方需要多步操作，可能降低授权使用率 | 清晰待办、通知；不提供批量接受（违背逐条同意）；提供“接受后去绑定/启用”引导 |
| 来源 material change 频繁 | 授权方维护 `base_url`/模型/映射/API Key 会触发重新确认 | 只对 material 字段触发；状态/并发/额度变更只通知；提供字段级 diff 和一键重新确认；API Key 轮换按 material 处理，运营需提前通知接收方 |
| 团队审批人瓶颈 | 团队 offer 需审批人同意 | 审批人=创建者，管理员在失效/缺失/自审批时代行；待审批通知/积压指标；成员仍可拒绝 |
| 分组快照过期 | 新增账户不自动纳入 | 明确“查看范围差异/刷新范围”入口和通知；逐账户审阅；不静默扩大 |
| 存量授权治理 | 历史授权可能是恶意/不需要的 | legacy accepted + 一次性复核通知 + 30 天复核截止 + 归还/屏蔽；必要时管理员批量回收 |
| 限额误伤 | 大批量合法授权被限额 | 默认值按生产盘点调整；明确 `offer_suppressed` 和审计；管理员可暂停/解除；不做静默丢弃 |
| 旧客户端/API | `targetGroupId` 移除是破坏性变更 | 前端同批发布；旧请求 400 明确提示；管理面 API 为内部契约，不保留静默兼容 |
| 回滚受限 | 新状态写入后旧二进制会复活/自动绑定 | 只允许 expand 相前回滚；之后前向修复或备份恢复；部署文档写明 |
| 团队+分组复杂度 | 成员级快照/settings/refresh 状态多 | 统一按 runtime 维度建快照和 settings；复用个人分组流程；验收覆盖成员移除/回退 |
| legacy 复核截止 | 接收方未及时确认会短暂不可用 | 提前 30 天通知、多次提醒、截止前 7 天再次通知；可配置延长 |
| 精确名探测 | 无法完全阻止逐字探测 | 全局限额、统一错误、审计、限速；邀请码作为后续增强 |

## 15. 被否决的方案

1. **保留自动绑定，增加接收方事后确认**：资源已经写入接收方分组/调度池，确认前已暴露；且存在竞态。否决。
2. **只加“归还”按钮/通知**：不能阻止首次注入；归还不清绑定、重授权可复活。否决。
3. **用功能开关在旧/新授权模型间切换**：同一契约双语义，旧路径永远不安全；项目规范不接受以开关规避缺陷。否决。
4. **团队审批人直接代表成员同意**：仍是单方面；成员无法拒绝。否决。
5. **只信任团队、不给成员拒绝权**：任意用户可向任意团队发起，成员被批量注入。否决。
6. **完全冻结来源账户配置**：破坏正常维护（换域名、模型更新）；不能解决所有信任问题。改为 material change 重新确认。否决。
7. **重新给分组加 provider 维度**：与现行“分组无供应商维度”架构冲突，影响面过大；改为纠正文档表述 + 绑定提示 + 模型/端点过滤。否决。
8. **仅靠邀请码，不做精确用户名**：邀请码是可选增强，不是安全必需；精确用户名/团队名 + 无全量列表 + 审批 + 限额已降低枚举/批量注入。邀请码可在不改变状态机的前提下后续增加。否决。
9. **管理员代资源所有者创建 offer 只需审计+通知**：所有者未同意即以其名义授权，窗口内可被接收方接受并消耗额度。改为 `pending_owner_approval`。否决。
10. **把 `needs_review` 当“可用但降权”**：来源已被换过，降权仍会发送流量。否决。
11. **复用旧来源行表示重新发起**：覆盖终态历史，无法审计，且会让“归还后不自动复活”检查失效。改为追加新来源行。否决。
12. **依赖 `group_accounts` 表示分组授权绑定**：分组授权本来不创建实例，`group_accounts` 无对应行；归还无法停用。改为 `group_authorization_settings.enabled`。否决。

## 18. 设计裁决记录

| 裁决 | 结论 | 理由 |
| --- | --- | --- |
| 授权创建是否立即生效 | 否，必须接收方接受 | 单方面写入接收方调度域是根因 |
| 目标分组由谁选择 | 接收方，接受后自己绑定 | 分组是接收方本地配置，不是授权参数 |
| 团队授权是否自动展开 | 否；团队审批 + 成员逐人接受 | 任意用户可向任意团队发起，自动展开会批量注入 |
| 团队审批人 | `system_teams.created_by`，失效/缺失/自审批时管理员回退 | 不引入新团队角色，闭合任意用户向任意团队发起 offer 的路径 |
| 管理员代资源所有者创建 | 必须 `pending_owner_approval` | 不能以他人名义单方面授权 |
| 来源 material change | 重新确认，未确认硬阻断；双修订字段 | 防止接受后换源，且能证明接收方看到的是哪一版 |
| 个人来源被团队覆盖 | dormant + 可回退，不永久 superseded | 团队变化不应永久剥夺个人授权 |
| 归还后重新授权 | 必须重新接受 + 重新绑定 | 防止归还失效/重授权复活 |
| 分组授权范围 | 接收方快照 + 显式 refresh + 快照 CAS | 防止授权方事后加账户动态扩大，防止刷新窗口注入 |
| 分组授权绑定 | `group_authorization_settings.enabled` 显式开关 | 分组授权没有账户实例，`group_accounts` 不适用 |
| 普通用户枚举 | 禁止全量用户/团队/他人分组；精确名 + 审批 + 全局限额 | 防止批量枚举和骚扰；精确探测接受残余风险 |
| 管理员代接受/代绑定 | 禁止；通用接口同样禁止 | 同意必须由接收方表达 |
| 旧单方面写入路径 | 同批删除，不做开关/双写 | 根治，不留安全缺口 |
| 存量授权 | legacy accepted + 一次性复核 + 30 天复核截止 + 可归还/屏蔽 | 避免生产中断，同时给补救入口 |
| 团队+分组 | 正式支持，成员级快照/settings | 现行已支持，不得因重构丢失 |
| 重新发起来源 | 追加新来源行，不复用终态行 | 保留历史，保证 durable exit 可判定 |
| 回滚 | 新状态写入后禁止旧二进制回滚 | 旧 gateway 会 revive 并自动绑定 |
| chat-pinned | 只跳过健康可用性，不跳过授权/快照/修订 | 防止 pinned 路径绕过新闸门 |
| 团队聚合 | 当前周期已有成员来源且全部终态时按结束原因终态化，含 paused；零成员来源按 `TeamMemberlessTTL` 保持 | 防止死状态和错误 ended_reason，也防止空集全称命题误判 |

## 19. 待实施前确认项

以下不改状态机，但实施前需要数据/运维输入：

1. 生产存量授权、实例、`group_accounts` 授权绑定、`superseded` 分布、`grant_id` 映射冲突数、分组账户数分布（最大值/超 500 组数）的只读盘点结果。
2. 限额默认值、pending TTL、团队审批 TTL 是否按生产分布调整；调整只改常量，不改状态机。
3. legacy 复核截止是否采用默认 30 天，是否需要在截止前延长/分批；截止后统一转 `needs_review`。
4. 一次性复核通知的发送范围（全部 inbound active 授权，或仅跨用户授权）；建议全部。
5. `legacy_oversized` 分组快照的处置策略：保留可用还是要求拆组；新接受/新增账户仍执行 500 上限。
6. 现有帮助文档中旧授权文案的替换清单；实施时按 §17 同步。
7. `TeamMemberlessTTL` 默认 14 天是否按生产团队/成员分布调整；到期 `no_member_offer` 后，授权方重新发起复用同一团队 grant 并重新走团队审批，已有成员的重新邀请仍需显式操作；确认该口径不改为“到期自动重发”。
8. legacy 已 `expired` 的分组授权不允许 extend（无快照，恢复后无法绑定），必须由授权方重新发起、接收方重新接受并建立新快照；本批不支持“延长时重建快照”的替代方案，若未来需要，按新设计另行评审。
9. 旧管理面 `POST /accounts/{id}/return-authorization`、`POST /groups/{id}/return-authorization` 的下线方式：建议直接移除路由（404），同批删除前端入口、帮助文档和运营脚本引用，不保留 410 兼容层；实施前确认没有内部自动化依赖这两个端点。
10. 所有者确认与逐账户 reconfirm 的运维口径：`pending_owner_approval` 不进入接收方收件箱，需确认所有者通知渠道（站内通知 + 管理侧待办徽标）和 `OwnerApprovalTTL` 到期后的管理员告警；逐账户 reconfirm 前端可提供多选，但后端必须逐账户携带 `expectedRevision` / `expectedRevisionVersion` 独立 CAS，不提供无修订条件的批量接受接口。
11. 逻辑删除后的名称复用：本设计默认 `system_accounts.username` / `system_teams.name` 在 `deleted_at` 后可复用（部分唯一索引）；若产品要求名称永不复用，需在实施前确认并保留全局唯一索引，但查询仍必须排除已删除行。
