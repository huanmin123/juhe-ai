# 普通分组可选调度策略设计（高并发分组收敛）

> 设计状态：**已裁决并实施（2026-11-09）**。本文是“移除 `high_concurrency` 分组类型、把两个可选策略并入普通分组”的唯一目标契约；代码、前端、迁移命令与 revision 22 已落地，本文描述现行运行事实，[高并发分组调度设计](高并发分组调度设计.md) 只保留为退役实现记录。生产迁移须在发布窗按 §5.3 执行 `maintenance upgrade`（revision 22）并跑 postflight。
>
> 关联裁决：2026-11-09 用户确认高并发分组不是主力，去掉该类型；普通分组保留「最大单账户排队阈值」和「单 IP 并发限制」两个可选策略，最大等待时间统一继承全局 `noAvailableAccountWaitTimeoutSeconds`（默认 270 秒）。

## 1. 背景与决策

现行分组类型分为 `personal`（普通/个人）和 `high_concurrency`（高并发）。高并发分组为“同一 API Key 大量并发”提供了一整套独立机制：快速优先评分、分组短队列、备用账号排队接管、慢请求降权、每 Key 队列上限、图片 lane 上限、单 IP 闸口和 16 个策略字段。

用户实际需要的只有两件事：

1. 需要分流时，设置「最大单账户排队阈值」，让账户使用更平均；
2. 防止某些用户过度使用占用资源，设置「单 IP 并发限制」。

因此不再保留第二种分组类型。普通分组增加两个**可选**策略，默认关闭；其余高并发机制全部退役。这样只有一套分组调度语义，减少组合状态、迁移遗留和维护成本。

### 目标

1. 分组类型只剩 `personal`；`group_kind`（普通/超级）不变。
2. 普通分组可选 `defaultSoftConcurrency`（最大单账户排队阈值）与 `clientIpConcurrencyLimit`（单 IP 并发限制）。
3. 默认行为不因本设计新增任何限制：阈值 `-1`、IP 限制 `0` 时，除既有账户亲和 latch 外与当前普通分组一致。
4. 阈值只影响排序、账户亲和让位与后继选择，不作为硬拒绝；硬并发/RPM 仍由 `TryAcquire` 原子判定。
5. 最大等待时间不再有分组级配置，统一由全局 `noAvailableAccountWaitTimeoutSeconds`（默认 270 秒）承担；不保留分组短队列。
6. 单 IP 并发限制超限固定返回 429，不提供排队模式。

### 非目标

1. 不做分组级短队列、每 API Key 队列上限、`maxQueueSize`、`maxQueueWaitMs`。
2. 不做 fastFirst 评分、fallbackOnQueue、慢请求/首字慢统计、图片 lane 独立上限。
3. 不新增功能开关；功能交付即默认生效，两个策略字段是业务配置而非开关。
4. 不改组级会话亲和、账户内 API Key 亲和、RPM/硬并发判定、错误语义、熔断/冷却/探针规则。
5. 不建模上游缓存共享域；跨账户切换按可能丢缓存处理（见 [账户亲和同层单向粘性与会话名额设计](账户亲和同层单向粘性与会话名额设计.md)）。

## 2. 分组模型与字段契约

### 2.1 分组类型

- 唯一类型：`personal`。`high_concurrency` 在迁移后从 API 写入面拒绝（400「分组类型无效」），存量行迁移为 `personal`。
- `group_kind` 继续区分 `standard` / `super`；超级分组成员展开、记账与路由目标语义不变。
- `is_default`、启用状态、名称唯一性等既有约束不变。
- 存储列 `groups.group_type` **保留**（`text NOT NULL DEFAULT 'personal'`），不删除、不新增 CHECK，避免把本次收敛扩大为破坏性 DDL；迁移把所有行写成 `personal`。API 响应继续带 `groupType: "personal"` 作为兼容字段，前端类型收窄为 `'personal'`。
- 读路径把旧 `high_concurrency` 行归一为 `personal`，策略按 §5.2 映射后返回；未知 `group_type` 仍是读取错误（500），不静默归为 `personal`；空串/NULL 同样按非法数据处理（列 `NOT NULL DEFAULT 'personal'`，正常路径不可产生）。
- `group_authorization_settings.group_type` / `scheduling_policy_json` 同步退役：运行时与管理读路径不再用授权设置覆盖分组类型或策略；迁移把两列清为 `personal` / `NULL`（列保留，避免破坏性 DDL）。

### 2.2 `scheduling_policy_json`

普通分组的策略列保持可选：`NULL` 等价于两个字段都取默认值。非空时只允许以下两个键：

| 键 | 类型 | 默认 | 合法范围 | 语义 |
| --- | --- | --- | --- | --- |
| `defaultSoftConcurrency` | 整数 | `-1` | `-1` 或 `1..1000000` | 最大单账户排队阈值；`-1` 关闭；生效阈值 = `min(值, 账户硬并发上限)` |
| `clientIpConcurrencyLimit` | 整数 | `0` | `0..1000000` | 单 IP 并发上限；`0` 关闭；超限立即 429 |

规则：

1. `0` 不是 `defaultSoftConcurrency` 的合法值；关闭只能用 `-1`，避免“0 是关闭还是零阈值”的二义。
2. 非空策略必须同时包含两个键；缺键、未知键、越界或非整数一律 400，不做静默补默认。
3. 阈值是分组级配置，不支持按账户绑定或 `group_authorization_settings` 覆盖；账户硬并发上限始终是最终上限（`min` 收口）。
4. `clientIpConcurrencyLimit` 的作用域为 `(system_account_id, group_id, api_key_id, client_ip)`，与现有 `gatewayclientip` 单 IP 闸口同源。
5. 不再接受 `clientIpConcurrencyOverflowMode`；超限行为固定为拒绝。

写入与响应语义：

6. 创建：缺省或显式 `null` → 存 `NULL`；传对象 → 必须两键齐全，两项都为默认值（`-1`/`0`）时也存 `NULL`。
7. PATCH：缺省 → 策略不变；显式 `null` → 清空为 `NULL`；传对象 → **整对象替换**，不做键级合并；两项都为默认值时存 `NULL`。
8. 响应：非空策略返回规范化两键对象，`NULL` 返回 `null`；列表、详情、编辑详情、options 返回同一策略值。列表项新增可选 `schedulingPolicy`，避免前端为摘要逐行拉详情。
9. 旧 16 键行读兼容：新二进制读路径只取 `defaultSoftConcurrency` / `clientIpConcurrencyLimit` 并按 §5.2 映射，忽略其余旧键；迁移完成后出现非两键的非空策略视为数据错误（500），不静默修复。

### 2.3 API 与前端

- 创建/编辑分组：`group_type` 只接受 `personal`；前端删除“高并发”类型选项、紫色类型标签和相关策略表单。响应继续返回 `groupType: "personal"` 兼容字段。
- 普通分组列表行携带 `schedulingPolicy`，编辑可直接使用列表行，不强制逐行调用 `edit-basic`；Create/Update 响应返回最终策略（PATCH 的 `changedFields` 含 `schedulingPolicy` 时），便于前端即时刷新摘要。
- 普通分组编辑页新增“调度策略（可选）”区块，只有两个字段：
  - 最大单账户排队阈值：默认 `-1`，帮助文案“-1 表示不启用；设置后达到阈值的账户在新请求排序中让位，让账户使用更平均”。
  - 单 IP 并发限制：默认 `0`，帮助文案“0 表示不限制；设置后同一 IP 超过并发立即返回 429”。
- 分组列表/详情摘要：
  - 两项都默认：显示“未启用可选调度策略”。
  - 阈值启用：显示“单账户排队阈值 N”。
  - IP 限制启用：显示“单 IP 并发 N（超限拒绝）”。
- 旧字段 `maxQueueWaitMs`、`maxQueueSize`、`perApiKeyQueueLimit`、`fastFirstEnabled`、`fallbackOnQueueEnabled`、`breakAffinityOnSoftLimit`、`breakAffinityOnQueueWaitMs`、`slowRequestThresholdMs`、`firstOutputSlowThresholdMs`、`recentTimeoutWindowSeconds`、`recentTimeoutPenaltyThreshold`、`mode`、`clientIpConcurrencyOverflowMode`、`imageLaneMaxConcurrency` 全部从表单、类型和摘要中移除。

## 3. 调度行为契约

### 3.1 软阈值

定义（账户维度）：

```
hardLimit = account.concurrency_limit（<1 按 1）
softLimit = defaultSoftConcurrency > 0 ? min(defaultSoftConcurrency, hardLimit) : 0
softBusy  = softLimit > 0 && currentConcurrency >= softLimit
hardBusy  = currentConcurrency >= hardLimit（图片 lane 仍按既有 lane 上限判定）
```

- `softBusy` **不是**容量失败，不触发 `TryAcquire` 拒绝，也不改变 RPM/并发槽计数。
- 并发读数取本次请求冻结的候选快照 `CurrentConcurrency`，与 `TryAcquire` / 容量排序同源；不为软阈值新增实时 tracker、Redis 调用或数据库往返。
- 选号排序：`hardBusy` 账户在同层内永远最后；文本/对话主链的热质量排序再把 `hardBusy` 候选整体追加到最终尾部。先按既有四元调度层/模型优先级保持层序，层内 `softBusy` 排在非 `softBusy` 之后；同层内沿用现有负载、质量与稳定顺序。`softBusy` 只在本层内降权，不跨层抢占更高优先级层。媒体 lane 不做热质量排序，`hardBusy` 沿用既有层内后置，`softBusy` 由容量排序在同层降权。
- 准备期热质量排序（成本优先/速度优先）与上述排序同源：`hardBusy` 候选不进入热质量比较、排序后整体追加尾部；层内热质量重排以 `softBusy` 为第一顺位键。同层探索（same-tier exploration）也不得把 `softBusy` 目标置顶，软忙目标不进入探索候选。质量统计与探索因此都不会把软忙/硬忙账户提回健康 peer 之前。
- 会话亲和：普通分组的 owner latch 按 [账户亲和同层单向粘性与会话名额设计](账户亲和同层单向粘性与会话名额设计.md) 执行；owner 达到 `softBusy` 时视为 `softBroken`，本次请求允许让位给同层后继。`softBroken` 随准备期 owner 状态传递到最终结算：后继最终协议成功且同层时，按容量失败同款 CAS 重绑，审计 reason 记 `soft_threshold`（与 `capacity` 区分），指标沿用 `rebind_total`；旧 owner 恢复空闲不主动回切。只有让位成功而不重绑会让每次请求重新落回 owner，阈值无法真正分流。会话名额规划的 preferred owner 在 `hardBusy` 或 `softBusy` 时不得被提回候选首位；只有名额回退到其他账户时才前移。
- 如果同层所有非硬忙候选都 `softBusy`：仍按负载/质量/稳定顺序正常选择，不排队、不拒绝；`softBusy` 只是排序降权。
- 阈值关闭（`-1`）时 `softBusy` 恒 false，latch 只在 `hardBusy`/运行态排除时让位。
- 跨层不 latch：owner 所在层无可用后继时按既有四元层顺序走跨层候选；跨层成功不重绑 owner。

### 3.2 单 IP 并发

- `clientIpConcurrencyLimit = 0`：完全不启用，零额外开销。
- `> 0`：在 L0 硬过滤后、账号准入/派发前，按 `(system_account_id, group_id, api_key_id, client_ip)` 获取一个 IP 槽；达到上限立即返回 429（错误码沿用既有 IP 并发拒绝契约），不占账号并发、不进入任何等待队列。
- IP 槽在响应结束（成功/失败/流中断/取消）释放；客户端断开同样释放。
- IP 闸口不替代账户硬并发、RPM、白名单/黑名单或 IP 级账号回避；它们相互独立。
- 路由计划还有后续分组时，按既有跨组回退先尝试其他分组；全部穷尽后才渲染本组 IP 并发 429。跨组回退本身不变。
- realtime WS 长连接不经过本闸门：媒体 lane 的既有超时、无会话调度与 lane 隔离不变，WS 连接仍受 `realtimeMaxConnectionsPerApiKey` 约束。
- 不再有 `queue` 溢出模式；如果存量高并发分组使用过 `queue`，迁移报告必须列出并说明行为变为拒绝。

### 3.3 等待预算

- 分组级最大等待参数全部删除；`maxQueueWaitMs`、`maxQueueSize`、`perApiKeyQueueLimit` 不再存在。
- 所有账户硬忙/无可用账号时，沿用普通分组既有整池等待：由 `noAvailableAccountWaitTimeoutSeconds`（默认 270 秒）约束，期间按既有退避重新选号；预算耗尽后按既有 503/429 终态收口。
- owner latch 的有界等待按账户亲和设计执行（共享 1-2s：200ms × 5-10 次；RPM reset 在预算内才等待），不新增分组级等待参数。
- 本设计不引入任何新的“等待到某个分组队列位置”的语义。

### 3.4 与高并发旧机制的关系

实施完成后删除：

| 旧机制 | 处置 |
| --- | --- |
| `high_concurrency` 分组类型 | 迁移为 `personal`，写面拒绝 |
| 分组短队列 / `HighConcurrencyQueue` | 删除；走 270 秒整池等待 |
| 队列等待后的 `ReorderOnly` 纯排序 | 删除；普通分组只保留准备期一次热质量/亲和排序 |
| `fastFirstEnabled` | 删除；排序只保留硬忙/软忙/负载/质量/稳定序 |
| `fallbackOnQueueEnabled` | 删除；fallback 仍由四元调度层 `fallbackRank` 表达 |
| `breakAffinityOnSoftLimit` / `breakAffinityOnQueueWaitMs` | 删除；软阈值启用即按 §3.1 让位 |
| `slowRequestThresholdMs` / `firstOutputSlowThresholdMs` / 近期超时字段 | 删除；不移植慢请求统计 |
| `maxQueueWaitMs` / `maxQueueSize` / `perApiKeyQueueLimit` | 删除；等待统一 270 秒 |
| `imageLaneMaxConcurrency` | 删除；图片请求按账户硬并发与既有 lane 超时处理 |
| `clientIpConcurrencyOverflowMode` | 删除；固定拒绝 |
| `mode=balanced_fast` | 删除；不再有分组调度模式 |

账户亲和的后继排序仍需要“硬忙 → 软忙 → 负载/并发 → 质量 → 稳定序”的比较器；实施时保留该比较器的**纯排序部分**（不含队列、fastFirst、慢请求统计），作为普通分组候选/后继排序。它不再依赖 `GroupTypeHighConcurrency`。

实施顺序硬约束：`upstreamdispatch.go` 的整池短队列当前以 `GroupSchedulingPolicy != nil` 为入口，而不是 `group_type`。必须在普通分组策略生效的同一批删除该分支及 `HighConcurrencyQueue`，禁止出现“普通分组带策略但短队列仍存在”的中间态；否则普通分组整池容量失败会误入高并发队列并按旧 `maxQueueWaitMs` 等待。

## 4. 与既有契约的关系

- **账户亲和**：本设计只新增“软阈值让位”这一 L3 运行态条件，owner latch、同层谓词、有界等待、同层重绑和 30 分钟 lease 均以 [账户亲和同层单向粘性与会话名额设计](账户亲和同层单向粘性与会话名额设计.md) 为准。该文 §5.2 中“软阈值默认收口到硬并发（globalMax）”仅适用于退役前的高并发分组；迁移后普通分组默认 `-1`（关闭）。软阈值让位属于 P0 重绑条件，不是 P1；该文“软阈值路径重绑留 P1”的旧表述按本契约回正。
- **超级分组**：成员继续要求 `group_type` + `scheduling_policy_json` 指纹完全一致，迁移后指纹按两键策略计算；成员策略不一致仍返回 `super_group_member_dispatch_policy_mismatch` / `super_group_member_dispatch_policy_conflict`。迁移必须把超级分组自身行的 `group_type`/策略按首成员重算，否则后续成员保存会把旧值写回。若未来要允许成员各自不同阈值，另立设计，不在本次范围。
- **授权设置**：`group_authorization_settings` 的 `group_type`/`scheduling_policy_json` 覆盖退役；授权用户看到并运行来源分组的两个策略，不再有 per-grantee 覆盖；迁移把两列清为 `personal`/`NULL`。
- **组级会话亲和**：不变；组绑定成功者赢、不回切。
- **策略路由**：分组仍是号池容器；跨组回退、路由模式、超级分组展开不变。本设计不改变 `API Key -> 路由策略 -> 分组 -> 账户` 层级。
- **RPM**：不变；RPM 满仍是容量失败，纯 RPM 拒绝不短等；软阈值不替代 RPM。
- **媒体 lane**：图片/音频/视频/realTime 的既有超时、无会话调度、lane 隔离不变；图片不再有分组级独立并发上限，按账户硬并发执行。
- **调用方分级调度**：层级排序仍在其既有位置生效；软阈值只在本分组候选内降权，不改变调用方层级。

## 5. 迁移

### 5.1 前置盘点

迁移前必须只读盘点，且盘点范围不止 `groups`：

```sql
SELECT group_type, count(*) FROM juhe_business.groups GROUP BY group_type;
SELECT id, system_account_id, name, group_kind, group_type, scheduling_policy_json
FROM juhe_business.groups
WHERE group_type <> 'personal' OR group_kind = 'super';
SELECT count(*) FROM juhe_business.group_authorization_settings
WHERE group_type <> 'personal' OR scheduling_policy_json IS NOT NULL;
SELECT id, group_id, group_type, scheduling_policy_json
FROM juhe_business.group_authorization_settings
WHERE group_type <> 'personal' OR scheduling_policy_json IS NOT NULL;
```

报告至少列出：`groups` 与 `group_authorization_settings` 的 `high_concurrency` 行数、未知 `group_type` 行、超级分组行、`defaultSoftConcurrency` 分布、`clientIpConcurrencyLimit` 分布、`clientIpConcurrencyOverflowMode='queue'` 行、`imageLaneMaxConcurrency>0` 行、`defaultSoftConcurrency` 非默认值的行，以及 JSON 损坏/非对象/缺键/未知键的 `needs_review` 行。

### 5.2 映射规则

`globalMax` 指旧高并发策略注入的进程配置 `JUHE_AI_CONCURRENCY_GLOBAL_MAX`（默认 5000）；迁移命令必须提供 `--global-max`（默认 5000，范围同源），并在报告中回显，不把默认值硬编码为业务常量。

| 旧值/字段 | 新值 |
| --- | --- |
| `group_type='high_concurrency'`（`groups` 与 `group_authorization_settings`） | `personal` |
| `defaultSoftConcurrency` ∈ `[1, min(1000000, globalMax))` | 保留原值（明确设置的阈值） |
| `defaultSoftConcurrency` 缺失、`<=0` 或 `>=globalMax` | `-1`（旧默认 globalMax 等价于硬上限，不迁移为阈值） |
| `clientIpConcurrencyLimit` | 保留（0..1000000） |
| `clientIpConcurrencyOverflowMode` | 删除；`queue` 行在报告中标注“行为变为拒绝” |
| `imageLaneMaxConcurrency` | 删除；`>0` 行在报告中标注“图片 lane 改为账户硬并发” |
| 其它旧字段 | 删除 |
| 两项都默认 | `scheduling_policy_json = NULL` |
| `group_authorization_settings` 的策略列 | 清为 `NULL`（覆盖退役，不再参与运行） |
| 超级分组自身行 | 按首成员的 `group_type`/映射后策略重算，保持指纹一致 |
| 空超级分组自身行 | 收敛为 `personal` + `NULL`；运行期成员清空时同一事务立即回写，不留待迁移 |

示例：旧 `{"defaultSoftConcurrency":5,"clientIpConcurrencyLimit":5,"maxQueueWaitMs":60000,...}` → 新 `{"defaultSoftConcurrency":5,"clientIpConcurrencyLimit":5}`；旧 `{"defaultSoftConcurrency":5000,...}` → `{"defaultSoftConcurrency":-1,...}`（或 NULL，如 IP 也为 0）。

JSON 损坏、非对象、缺键、未知键或未知 `group_type` 一律进入 `needs_review`，独立 `migrate-group-policy` apply 阶段以退出码 3 阻断（upgrade 步骤以 exit 1 停账本于 running），不静默补默认或猜测修复；由人工确认后再迁移。行数少时单事务写入，事务前 `SET LOCAL lock_timeout='2s'`；不更新 `updated_at`（避免触发前端乐观锁/版本 churn 与运行态失效），由发布流程重启进程刷新运行时缓存。

`--check=postflight` 必须先确认目标库存在 `juhe_business.groups` 表；缺表直接报错，不把错库/全新库按 0 行误报 Ready。upgrade 步骤的 fresh 库语义由 `Satisfied` 的 `tableExists` 守卫承担，不受此门禁影响。

### 5.3 兼容与回滚

- 新二进制在迁移前可读取旧 `high_concurrency` 行：读路径归一为 `personal`，只取两个键并按 §5.2 映射后运行/返回；写面从新二进制启动起拒绝 `high_concurrency`。这样滚动发布窗口内不会因未迁移数据而 500。
- 迁移完成后 `scheduling_policy_json` 严格只接受两个键；旧键不再读取；`personal + 16 键旧策略` 视为数据错误（500），不静默修复。
- 迁移承载在 **maintenance 子命令 + upgrade 步骤**，不是 `--ensure-schema`：子命令提供 dry-run/manifest、逐行报告、幂等重跑、`--global-max`、停写/备份确认；upgrade 步骤取当前 `SchemaRevision` 的下一个号（当前 21 → 22），标记 `Destructive`，只能在停写窗口执行；同批提升 `contracts.SchemaRevision` 并更新 upgrade 注册表 golden。禁止把数据迁移塞进 ensure-schema。
- 迁移命令必须支持 dry-run、逐行报告、幂等重跑；执行前备份 `groups` 与 `group_authorization_settings`。postflight 校验两张表无 `high_concurrency` 行、策略列只含两键或 `NULL`。
- 部署文档同批更新：`docs/deploy/部署指南.md` 增加升级步骤与窗口命令，`docker/single-server/README.md` 同步升级/回滚口径。
- 回滚限制：旧二进制无法把已迁移的 `personal` 行恢复成 `high_concurrency` 语义；回滚后这些分组按旧普通分组运行（无软阈值/IP 限制）。这是本设计的已知代价，回滚前保留数据库备份。
- 不新增功能开关；滚动发布窗口内新旧二进制对 `high_concurrency` 的读写行为按“新读旧、新拒写”执行。

## 7. 验收标准

1. **默认无策略**：`scheduling_policy_json=NULL` 的普通分组，候选顺序、latch、等待、错误终态与实施前一致（除既有 P0 亲和变更外）。
2. **软阈值排序**：阈值 3、账户 current 3/5 → `softBusy`；非软忙账户排前；全部软忙时仍返回可用账户，不排队、不 429；媒体 lane 由容量排序同层降权，同层探索不选择软忙目标。
3. **latch 让位/重绑**：owner 达到软阈值 → 本次让位同层后继；名额规划的 preferred owner 不得把软忙 owner 提回首位；后继协议成功 → `soft_threshold` CAS 重绑；owner 恢复空闲后连续请求不回切；跨层成功不重绑。
4. **硬并发优先**：软阈值不影响 `TryAcquire`；硬满账户仍由硬并发拒绝并跳过。
5. **IP 限制**：0 关闭零开销；>0 超限 429、不占账号并发；作用域隔离（不同 Key/IP 不共享）；响应结束释放；取消/断流释放；不再有 queue 模式。
6. **等待**：无分组队列；带非空策略的普通分组整池硬忙时仍走 270 秒预算内整池重试，不进入 `HighConcurrencyQueue`；耗尽后既有终态；无 `maxQueueWaitMs` 可配。
7. **迁移**：dry-run 覆盖 `groups`/`group_authorization_settings`、旧默认/显式阈值/IP/queue/image lane/超级分组行；畸形行进入 `needs_review` 并阻断 apply；迁移幂等；旧行可读、写面拒绝；迁移后严格两键。
8. **前端**：类型只剩“个人/普通”；两个字段默认与校验正确；列表/详情摘要正确；旧字段不可见；普通分组编辑不再依赖高并发条件拉详情。
9. **API 兼容**：`groupType` 响应仍为 `personal`；创建/编辑 `high_concurrency` 返回 400「分组类型无效」；PATCH `schedulingPolicy:null` 清空、缺省不变、对象整替换；列表项带 `schedulingPolicy`。
10. **授权与超级分组**：授权用户与 owner 看到/运行同一分组策略（授权覆盖失效）；超级分组成员策略不一致仍按既有错误码拒绝；迁移后超级分组自身行与首成员一致。
11. **删除**：生产代码除一个只读 legacy 字符串常量（迁移前旧行归一）外零 `high_concurrency` 类型/队列引用；`rg "high_concurrency" backend-go frontend` 仅命中该常量、历史测试夹具或文档（测试夹具在实施完成后清零）。

## 8. 风险与待确认

1. **存量行**：必须先盘点；若存在正在使用的高并发分组，迁移会改变排队/备用/图片 lane 行为，需要按报告逐组确认。
2. **队列依赖**：使用 `clientIpConcurrencyOverflowMode='queue'` 的分组，迁移后超限从排队变为 429；需在报告中确认可接受。
3. **图片 lane**：使用 `imageLaneMaxConcurrency>0` 的分组，迁移后图片请求按账户硬并发；需确认可接受，否则另立“普通分组图片 lane 可选限制”设计。
4. **旧客户端**：仍发送 `group_type=high_concurrency` 的客户端在迁移后收到 400；需要确认无外部自动化依赖。
5. **回滚限制**：旧二进制无法恢复高并发语义，回滚前必须保留备份并接受普通分组行为。
6. **latch 交互**：软阈值会让位并重绑，可能增加跨账户切换；按亲和设计的指标观察切换率与缓存率，不承诺缓存命中。
7. **阈值配置错误**：`0`/负数/超上限在 API 层拒绝；前端做同样校验，避免写入非法策略。
8. **短队列误入**：`upstreamdispatch.go` 以策略非空进入高并发短队列；若先让普通分组带策略、后删队列，会造成生产误排队。必须同批删除（§3.4），验收第 6 条覆盖。
9. **超级分组策略一致性**：迁移后成员仍须两键策略完全一致；若存量超级分组成员策略不一致（旧数据手工写入），迁移进入 `needs_review`，不能自动选一个覆盖。迁移需按首成员重算超级分组自身行。
10. **授权覆盖残留**：`group_authorization_settings` 停止读取后，旧行若不清空会成为死数据；迁移必须清为 `personal`/`NULL`，postflight 覆盖两表。
11. **revision 取号**：新数据步骤必须取 `SchemaRevision` 下一个号（21 → 22）并提升 `SchemaRevision`，否则 `upgrade --dry-run` 不 blocked、`deploy.sh` 会放行未迁移库。
12. **列保留**：`group_type` 列保留且不加 CHECK，避免破坏性 DDL；写面拒绝与读归一由应用层保证。若未来要删列，另立破坏性迁移。
13. **时间戳**：迁移不更新 `groups.updated_at`，避免前端乐观锁/版本 churn；发布流程必须重启 gateway/jobs 刷新运行时缓存。
14. **畸形数据**：损坏 JSON/未知键/未知类型不做自动修复，`needs_review` + 独立 CLI apply 退出码 3 阻断（upgrade 步骤 exit 1 停账本）；人工确认后再迁移，避免静默改变行为。
