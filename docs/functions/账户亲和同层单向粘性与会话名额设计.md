# 账户亲和同层单向粘性与会话名额设计

> 设计状态：**P0 + P1 已实施（2026-11-10）**。P0（同层单向粘性、有界等待、并发重绑、30 分钟 lease、D-94 修复）与 P1（会话名额表）已落地并有单测/fullchain 验收；质量优先后继、稳定随机分散仍待后续评估；P2（粘性优先队列、跨层驻留）仅登记。
>
> **缓存共享限制（2026-11-09 用户裁决）**：上游是否跨账户/跨服务共享缓存不可知（自建、官网、开源模型混用），本设计**不建模缓存域**。唯一可靠的缓存单元是**账户**；任何跨账户切换都按“可能丢缓存”处理。latch 的目标是减少切换次数，不承诺跨账户缓存命中。

## 1. 背景与问题

自营模型可能由不同上游服务承接，缓存是否互通无法确认。高并发下账户容量满时，同一会话会在 A/B 账户之间反复切换，导致上游缓存持续失效；切换越频繁，缓存命中率越低。

当前实现放大了这个问题：

1. 账户亲和绑定是 `first-binder-wins`：首次绑定的账户成为 owner，后续成功不会改绑（`gatewaysession/affinity.go:313-315`、`420-476`）。
2. 准备期 claim 后，若 claim 返回的 owner 与首候选不同，会重新按亲和排序，把 owner 提升到同层首位（`gatewaydispatch/preparation.go:705-713`）；容量繁忙降位被覆盖。
3. 普通分组的下一个候选在并发满时先做请求级短等，默认预算约 1200ms（`gatewaydispatch/engine.go:73-75`、`enginehelpers.go:89-138`）。
4. 切到 B 成功后，`RememberAsync` 仍是 claim 语义，不把绑定改到 B；下一次请求又先把 A 排到首位。
5. 高并发分组里 `affinityAllowed` 只是最后一个 tiebreaker（`gatewaysession/affinityorder.go:515`），与普通分组的强亲和语义相反。
6. 普通分组“容量忙”判定是 any（有一个账户满就认为整组忙），与 Node 原语义 every 不一致，已登记 D-94（`docs/bug/问题-0175-二次伪迁移首轮核对缺陷清单.md:147`），多分组路由会过早回退下一组。**working tree 已按 every 修复并有三处回归测试（`capacity.go`；2026-11-09 复核通过），本文按已修复口径描述。**

结果：A 持续满时，会话每请求先撞 A、失败后用 B；A 一空又回 A。既掉 A 的缓存，也掉 B 的缓存，还增加尾延迟。缓存共享不可知，所以唯一能做的是**减少切换**，而不是“切到缓存互通的账户”。

## 2. 目标与非目标

### 目标

1. **同层单向粘性（latch）**：同层内 owner 健康时优先 owner；owner 因容量/运行态不可用而切到新账户并最终协议成功后，绑定迁移到新账户；旧 owner 恢复空闲也不主动回切。
2. **减少跨账户切换**：latch 只减少切换次数；跨账户切换按可能丢缓存处理，不假设共享。
3. **有界等待**：仅对并发类容量失败与名额回退做短等待（200ms × 5-10 次 = 1-2s 共享预算）；RPM 满在 reset 不落在预算内时立即切换，不等待分钟级窗口。
4. **同层谓词可执行、可测试**：用统一四层模型（硬门 → 四元调度层 → 质量带 → 运行态/显式覆盖）取代当前散落在 `canSessionAffinityPromoteOver`、`anySuperPriority`、缓存率/热质量排序里的多头判定。
5. **可观测、可验收**：重绑、回切阻止、跨账户切换、租约命中/过期、名额驱逐、等待时长、会话-账户命中率可查；先有基线和目标，再判定收益。
6. **边界清晰**：并发槽是请求级资源，不按会话保留；会话名额是软 claim，不占并发、不占 RPM、不作为拒绝依据。

### 非目标

1. 不按会话保留并发槽；不允许空闲会话占用并发容量。
2. 不建模缓存域、不假设跨账户缓存共享；跨账户切换的缓存损失接受。
3. 不做跨层禁止回切；跨层仍由四元调度层顺序决定（跨层最短驻留见 P2）。
4. 不新增功能开关或用户配置项；内部常量先固化，观测后再决定是否升为系统设置。
5. 不改组级会话亲和（成功组绑定、不回切）和账户内 API Key 亲和。
6. 不改上游错误语义、重试预算、熔断/冷却/探针规则；纯单次上游协议错误默认不触发 latch。
7. 不做真实上游缓存命中率压测；用 usage 缓存率与新增指标观测。
8. P1 名额表已由用户裁决实施；质量优先后继与稳定随机分散仍不是必做项，按发布后指标另行评估。

## 3. 术语与资源边界

| 术语 | 定义 |
| --- | --- |
| owner | 会话当前绑定的账户（`SessionBinding.AccountID`） |
| 调度层 | `GatewayAccountDispatchPriorityTier` 四元组 `modelRank:fallbackRank:superRank:priority`（`gatewayproxyhealth/dispatchpriority.go`、`gatewaydispatch/dispatchsegments.go`） |
| 同层 | 四元调度层相等 |
| 质量带 | `QualityScore`（毫秒量纲：首字 EWMA + 状态/年龄罚分；未知=1,000,000）按 `qualityBandWidthMs` 量化后的档位；只用于层内排序与后继选择 |
| latch | 同层内单向粘性：owner 不可用切到新账户后，绑定迁移；旧 owner 恢复不主动回切 |
| lease | 会话对 owner 的优先占位；默认 30 分钟滑动；过期后占位可回收 |
| slot | 每账户的会话占位数软上限；只做分配与 LRU 治理 |
| hardBusy | 并发总量达到硬上限、image lane 达到账户硬并发（无分组级 lane 上限）、或 RPM 已用达到上限 |
| runtimeExcluded | 冷却、熔断、软阻断、屏蔽、延迟降级、调度排除等运行态不可用 |

资源边界：

- **并发槽**：请求级，响应结束释放（`cmd/juhe-ai-gateway/chain_v1_loop.go 成功结算释放点`）。会话空闲时本来就不占并发，不能为粘性保留。
- **RPM**：账户级自然分钟窗口；纯 RPM 拒绝不做逐账户短等（`AI账户每分钟请求上限设计` §5.1）。
- **绑定**：Redis 存储，TTL 1h（`gatewaysession/affinity.go:18`）；排序读刷新 TTL（`affinityredis.go:26-40`）。
- **lease**：控制“优先权”，不控制存储；过期后绑定可保留，但排序不再提升、claim 可重写。
- **slot**：控制“每账户记住多少会话”，软上限，不参与准入。
- **缓存**：共享边界不可知；唯一可靠单元是账户。跨账户切换即可能丢缓存。

### 4.2 根因与“同层谓词”现状问题

不是“没有粘性”，而是“粘性太硬且不迁移”：

- owner 被重排到首位，即使它已硬满；
- 每次先为 owner 付 1.2s 短等；
- 切到新账户成功后绑定不改；
- 下一次又回到 owner。

现有“同层”判定不统一，至少四套口径并存：

1. `canSessionAffinityPromoteOver`：model priority + super priority + fallback + priority + quality rank（严格不差）。
2. `canSessionAffinityRotateWithinSameTier`：上述谓词双向成立（质量必须相等）。
3. `anySuperPriority`：组内存在超级优先账户时，整个个人分组亲和排序直接关闭。
4. 高并发比较器：`SuperPriorityEnabled`、`Priority`、`loadRatio`、`affinityAllowed` 各自是独立键；`affinityAllowed` 最后。
5. 四元调度层：modelRank/fallbackRank/superRank/priority，已被引擎分段/熔断使用。

这些口径互相重叠且不一致：super/fallback/priority 已经在四元组里，却又在 `canSessionAffinityPromoteOver` 里重复；`anySuperPriority` 又额外把整个亲和关闭；质量既不在四元组里，又在 `canSessionAffinityRotateWithinSameTier` 里被当成同层条件。结果就是“同层”没有单一权威定义，实施 latch 时无法判断谁和谁可比。

## 5. 行为契约

### 5.1 同层谓词（权威定义）

调度判定固定为四层，顺序如下：

| 层 | 内容 | 作用 |
| --- | --- | --- |
| L0 硬门 | 配置启用、配额、模型/协议、权限、健康、屏蔽、熔断、调度排除 | 不通过即不可用，不参与后续比较 |
| L1 调度层 | `GatewayAccountDispatchPriorityTier` 四元组 `modelRank:fallbackRank:superRank:priority` | **唯一“同层”定义**；层序由引擎既有 tier 排序决定 |
| L2 质量带 | `QualityScore` 按 `qualityBandWidthMs` 量化 | 层内排序/后继选择；不改变同层定义，不主动破 owner latch |
| L3 运行态/显式覆盖 | `latency_degraded`、软阈值、traffic migration、账户锁死 | 可破 latch 或覆盖 latch；不是“层” |

**四元组已包含 super/fallback/priority**：`superRank`（超级优先 0/1）、`fallbackRank`（备用 0/1）、`priority`、`modelRank` 都参与层相等判定。因此：

- 不再需要单独的“super priority 覆盖 latch”规则；超级优先账户天然是更高层。
- 不再需要 `canSessionAffinityPromoteOver` 里重复比较 super/fallback/priority。
- **`anySuperPriority` 短路已删除（2026-11-09，W3）**：它会在组内存在超级优先账户时关闭整个个人分组亲和，和“超级优先是更高层”不一致；删除后 affinity 在普通层内仍生效，超级优先层仍按层序优先。行为变更测试已补。
- `canSessionAffinityPromoteOver` 的质量阻断已移除（W3）：质量只影响层内排序/后继，不再阻止健康 owner 在其层内保持首位。
- `fallback` 账户天然是更低层；跨层不 latch，绑定不迁移到 fallback。

**质量带定义**：

```
qualityBand(a) = unknown ? WORST : floor(QualityScore(a) / qualityBandWidthMs)
qualityBandWidthMs = 2000（建议起点，W3 用生产分布校准）
WORST = 哨兵（未知/缺失质量分）
```

- `QualityScore` 是毫秒量纲：首字 EWMA + 状态/年龄罚分；`UnknownQualityScore=1_000_000`。
- 2 秒档宽能把“首字差 1-2 秒”与“failed +60s / stale +5s”分开；具体值在 W3 用生产分布校准。
- 质量带只用于**层内后继选择**（优先更小档位；未知最差），不用于主动抢占健康 owner。

**谓词**：

```
eligible(a)        := 通过 L0 所有硬门
layer(a)           := GatewayAccountDispatchPriorityTier(a, modelPriority)
sameLayer(a,b)     := layer(a) == layer(b)
qualityBand(a)     := 见上
ownerUsable(o)     := eligible(o) && !hardBusy(o) && !runtimeExcluded(o) && !softBroken(o)
latchAllowed(o,c)  := ownerUsable(o) && sameLayer(o,c) && !trafficMigrationOverride && !accountLocked
successorEligible(o,c) := eligible(c) && sameLayer(o,c) && !hardBusy(c) && !runtimeExcluded(c)
successorOrder     := qualityBand asc -> load/occupancy asc -> stable order   // 设计目标
P0 successorOrder  := 层键 -> affinityAllowed -> softBusy -> loadRatio -> currentConcurrency -> qualityBand -> 稳定序（慢请求统计已退役）
```

规则：

1. **owner 可用**：owner 在其层内优先；不因同层 peer 的质量带/缓存率/负载更好而让位。更高层可用时仍按层序优先（跨层不 latch）。
2. **owner 不可用**：先做有界等待（仅并发，200ms 固定轮询 × 5-10 次 = 1-2s；RPM 仅在 reset 落在剩余预算内等待），仍不可用则选同层后继；同层无后继才走跨层正常 tier walk。
3. **重绑只允许同层**：`sameLayer(expectedOwner, newOwner)` 为真才 CAS 改绑；跨层成功不重绑（绑定留在原 owner）。
4. **跨层后果**：跨层服务可能每次请求都先尝试原 owner（有界等待）再落低层；这是层优先级的代价，跨层最短驻留/`avoidUntil` 留 P2，不在 P0 扩大范围。
5. **质量带不破 latch**：同层 peer 质量带更好也不抢占；只有 `latency_degraded`/持续慢样本可破。
6. **显式覆盖**：traffic migration 高于 latch；账户锁死门优先，锁死不跨账户；软阈值按普通分组 `defaultSoftConcurrency` 让位。

### 5.2 owner 健康判定

owner 在本次请求中视为“可用”需同时满足：

1. 在最终候选集中（通过 L0 硬门）；
2. 未 `hardBusy`：
   - 账户总并发 `< concurrency_limit`；
   - image lane 请求的 lane 并发 `< EffectiveImageLaneConcurrencyLimit`；
   - RPM 已用 `< rpm_limit`（`rpm_limit=0` 不限制）。
3. 未被运行态排除：冷却、熔断、软阻断、屏蔽、调度排除、`latency_degraded` 等。

软阈值：`breakAffinityOnSoftLimit=true` 且 owner 达到软阈值时，owner 在排序中让位（现有高并发策略）；这不是 `hardBusy`，但会触发迁移。软阈值默认收口到硬并发（`defaultSoftConcurrency=globalMax=5000`，effective=`min(阈值, 硬上限)`），所以默认在硬满时才让位。

> 2026-11-09 已实施：高并发分组移除后，普通分组的软阈值字段为 `defaultSoftConcurrency`，默认 `-1`（关闭），启用即让位，不再有 `breakAffinityOnSoftLimit` 开关；本节“默认收口到硬并发”只描述退役前高并发分组。目标契约见 [普通分组可选调度策略设计](普通分组可选调度策略设计.md)。

### 5.3 选择管线

```
L0 硬过滤（配额/模型/协议/权限/健康/屏蔽/熔断/调度排除）
→ 读取 binding + lease（无会话键/无绑定直接走现行路径）
→ owner 可用？
   ├── 是：owner 在其层内优先；不因同层 load/quality/cache 让位
   └── 否：有界优先等待（仅并发类，200ms × 5-10 次；RPM 仅在 reset 落在预算内等待）
            → 仍不可用：按后继规则选择同层候选
→ 准备期 claim（首候选建立/刷新绑定）
→ 名额规划（owner 有名额/未满 → owner；满 → 有界等待 → 空闲名额账户）
→ 逐候选 TryAcquire（并发+RPM 原子）
→ 最终协议成功：CAS 重绑 owner → 成功账户（同层；slot_fallback 允许跨层）
```

要点：

1. **owner 优先只在其四元层内**：更高层账户可用时仍按层序优先；跨层不 latch（跨层最短驻留见 P2）。名额回退到其他层的空闲账户时，最终成功按 `slot_fallback` 跨层重绑，属于名额表的显式例外。
2. **owner 优先发生在硬过滤之后**：owner 必须仍通过所有硬门；硬门优先于亲和。
3. **等待预算是共享的 1-2s**：名额等待与 owner 并发等待共用 `SessionAffinityOwnerWaitBudgetMs`（默认 2000ms），固定 200ms 轮询，即 5-10 次探测；准备期名额等待消耗后把剩余额度传给派发阶段，两段等待不叠加；owner 等待使用独立请求级额度，不被通用 1.2s 并发预算提前截断，并同时受 `ServerRetryBudget`/墙钟约束。RPM 满不等待（reset 落在剩余预算内才等）。链面跨 attempt/回退组复用同一请求级剩余额度指针，只减不增，避免每个 attempt 重新获得完整 2s。
4. **准备期 claim/名额规划不得把硬满/软阈值让位 owner 重新提到首位**：claim 后的重排与 `PlanSessionSlot` 的首选前移都携带容量繁忙与软阈值状态，owner 硬满或 `softBusy` 时不把 owner 提回首位（名额回退到其他账户仍可前移）。同时必须把“owner 准备期硬满”传给最终成功结算：容量排序可能让请求直接成功在其他同层账户上，完全不经过 owner，此时没有派发期容量失败记录；不携带该标志就不会重绑，下一次 owner 空闲时仍会回切（2026-11-09 W8 实测缺口，已补 `SessionAffinityOwnerBusy`）；软阈值让位同理由 `SessionAffinityOwnerSoftBusy` 驱动 `soft_threshold` 重绑。
5. **同请求内跨组回退不变**：`RoutePlanSnapshot`/候选快照只生成一次；跨组回退不重新查账户亲和。

### 5.4 后继选择（successor preference）

**设计目标**（后继选择器后续完整实施）：owner 不可用时，按以下顺序选择后继：

1. **同层**：只在 `sameLayer(owner, candidate)` 的候选中选；同层无可用候选才走跨层正常 tier walk。
2. **质量带**：同层候选中优先质量带更小（更好）者；不选明显更差的账户，除非没有更好的。
3. **负载/占用分散**：同质量带内按当前并发、最近分配时间、稳定随机/轮转分散，避免 A 满后大量会话同时涌向同一个 B（herd）。
4. **稳定顺序**：最后落回稳定序（账户 ID/输入索引），保证可回放。

**P0 实际口径（2026-11-09）**：后继仍使用现有高并发比较器，键序为
`hardBusy -> modelPriority -> trafficMigration -> fallbackRank -> superRank -> priority -> affinityAllowed -> softBusy -> loadRatio -> currentConcurrency -> qualityBand -> 稳定 index`。
即层键（model/fallback/super/priority）先于 `softBusy`，`softBusy` 只在本层内降权、不跨层抢占；慢请求/首字慢统计已随高并发分组退役删除，质量带只作为负载相同后的档位键，不再作为全局第一排序键。

P0 不做“质量带优先的后继选择器”，原因：

- **冷启动饥饿**：`QualityScore` 只来自近 24h 统计；新账户/无流量账户为未知，按“未知最差”会被质量优先排序永久后置，形成“无流量→无质量分→无流量”的死循环。
- **行为面过大**：把质量带提到负载之前会同时改变普通分组的全局分流语义（从负载分散变为质量集中），影响所有请求，而不是只影响 owner 失效后的后继；这超出 P0“减少切换”的范围，需要独立压测与容量评估。
- **质量带只作同负载档位键**：P0 层内排序按 loadRatio → currentConcurrency → qualityBand → 稳定序；慢请求/首字慢/最老在途统计已随高并发分组退役删除，质量带用于区分“同负载下质量差一档”的候选。

herd 分散同样只保留现有 `loadRatio`/`currentConcurrency` 维度：快照相同的并发请求可能仍同选一个账户。稳定随机/轮转键与质量优先后继一起放到 P1，由 W12 指标（迁移目标分布、跨账户切换率）决定是否实施。

不建模缓存域：跨账户切换即可能丢缓存；后继选择只保证“同层 + 不主动扰乱健康 owner + 负载分散”，不承诺缓存命中。跨账户切换次数单独计数（审计与 Prometheus 均已接）。

实现落点：

- `compareSoftConcurrencyCandidates` 中 `affinityAllowed = boundToSession && !hardBusy && !softBusy` 位于 `superRank/priority` 之后、`loadRatio` 之前，保证健康 owner 在同层内不被更空闲 peer 抢占；软阈值通过 `affinityAllowed=false` 让位，紧随其后的独立 `softBusy` 键用于同层非 owner 排序。
- `orderOpenAIPersonalAccountsBySessionBinding` 把绑定账户提升到其四元层首位，保留同层 peer 相对顺序（不做轮转）；过期 lease 不提升。
- `gatewaydispatch/preparation.go` 的 claim 块在 owner 容量忙时跳过重排，避免把硬满 owner 提回首位。
- 质量带函数位于 `concurrencyidentity.go`（`qualityBandWidthMs=2000`），当前只作为比较器末段档位键。

### 5.5 写回与重绑

- **2xx 头时点**：现有 `RememberAsync`（claim 语义）保持；它只刷新/保持 owner，不改变 owner。
- **最终协议成功**：新增 `RebindAsync(expectedOwner, newOwner, scope) bool`，CAS 把绑定从 `expectedOwner` 改到 `newOwner`；返回值表示 CAS 是否应用（false = 并发改绑/绑定删除/Redis 失败）。reason 由调用方按成功/容量场景写入审计与指标，不进入存储接口。
  - 触发条件：本请求最终协议成功（`ProtocolValidatedSuccess=true` 且不再重试上游）；`newOwner` 是最终成功账户；`expectedOwner` 是本请求准备期 claim 的 owner；`expectedOwner` 在本请求被容量拒绝/运行态排除（含 `latency_degraded`），**或准备期已硬并发繁忙（请求可能被容量排序直接绕过 owner）**；`newOwner != expectedOwner`。单次首字超时 cutover 只影响本请求，不触发 rebind；只有进入 `latency_degraded` 或持续慢样本才重绑，避免一次抖动永久迁移。
  - 只允许同层重绑（`sameLayer(expectedOwner, newOwner)`）；P0 要求 `expectedOwner` 在本请求候选集内（owner 被硬过滤时是否 latch 见 §11），否则不重绑。
  - CAS 失败（并发请求已改绑/绑定被删/Redis 失败）只告警，不影响请求结果。
  - 重绑后清除旧 owner 的 Key 指纹（新 owner 没有旧 Key 指纹）；保留 scope；刷新 lease/lastActiveAt。
- **并发请求**：同会话多个在途请求可能分别落 A/B/C；每个请求以自己看到的 `expectedOwner` 做 CAS。最后成功的 CAS 赢；失败方 no-op。允许短暂请求级分裂；下一次请求以最终 owner 为准。不得无条件覆盖（避免反复改绑）。
- **失败/取消/重试**：沿用现有删除矩阵；容量失败、单次上游失败不删除绑定；协议失败按既有 `ForgetSessionAffinity` 删除。
- **不回切**：重绑后旧 owner 恢复空闲也不主动提升；只有新 owner 也 hardBusy/runtimeExcluded 时才再次迁移。

### 5.6 lease

- 每次**最终协议成功**刷新 `leaseUntilMs = now + leaseTtlMs`（默认 30 分钟）和 `lastActiveAtMs = now`。
- lease 有效期内：排序提升 owner；claim 对 owner 刷新 TTL；不迁移。
- lease 过期（`leaseUntilMs>0` 且 `<=now`）：
  - 排序不再提升 owner；
  - claim 允许用新 proposed 账户 CAS 重写 owner（视为新分配）；
  - 旧绑定记录可保留到 TTL 1h，也可以按 slot 策略删除；不得让过期 lease 继续阻止新分配。
- lease 只控制优先权，不控制存储 TTL；绑定 TTL 仍 1h。
- 不同上游缓存 TTL 不同且不可知；2026-11-09 用户裁决 lease 空闲保留 **30 分钟**（常见上游缓存 TTL 为 5/30 分钟，取上限）；`leaseTtlMs` 先全局 30 分钟，P1 观测后按 vendor 校准。

### 5.7 会话名额（P1，已实施）

**定位**：soft claim / 分配目标，不是容量预留；名额满永远不拒绝请求。

- 每账户一个 slot 表（Redis ZSET），member = `sessionAffinityKey`，score = `leaseUntilMs`（每次最终成功刷新，因此 ZSET 顺序即“最久空闲在前”）。
- 名额上限 `slotCap`（内部常量，不做用户配置）：

  ```
  concurrencyBound = C × 4
  rpmBound         = R > 0 ? floor(R / 2) : +∞
  slotCap          = clamp(min(concurrencyBound, rpmBound), 32, 10000)
  ```

  其中 C=账户硬并发上限，R=RPM 上限；4 = 每个并发位最多记住 4 个会话，2 = 活跃会话平均每分钟请求数。`C<1` 按 1 计算。示例：C=10/R=60 → min(40,30) → 32；C=10/R=600 → 40；C=100/R=600 → 300；C=100/R=0 → 400。
- 分配（准备期 `PlanSessionSlot`，claim 结果附带“claim 前是否存在正 lease 的活跃绑定”）：
  - owner 已持有本会话名额 → 直接首选 owner（名额是 soft claim，已占用的会话不会因表满被挤出，不需要等待）；
  - owner 未持有名额但账户未满 → 首选 owner；
  - owner 未持有名额且是既有会话（claim 前已有正 lease 活跃绑定，名额过期/被驱逐）→ **200ms 轮询、最多 5-10 次（1-2s）** 等待名额释放，释放则仍选 owner；等待耗尽按候选顺序选第一个空闲名额账户；
  - owner 未持有名额且是新会话/零 lease 占位（claim 前无正 lease）→ 不为占位等待，直接选第一个空闲名额账户，避免高优先级账户先被新会话占满；
  - 候选顺序由调用方把 owner 同层账户排在其他层之前；全池都满时保留原 owner（新会话取第一候选），成功结算时再做 LRU 驱逐。
- 结算（最终协议成功 `ConfirmSessionSlot`）：
  - 先读 binding：只有最终成功账户已是当前 binding owner 时才写入/迁移名额；跨层成功未重绑、rebind CAS 冲突或 binding 缺失时保留原 owner 名额，不在成功账户上积累 stale 名额；
  - 向新 owner 的 slot ZSET 写入/刷新 member；名额已满时 `ZPOPMIN` 驱逐 score 最小（最久未成功）的会话；
  - owner 变化时释放旧 owner 的 member；驱逐成员异步清理其 binding（校验账户归属 + best-effort，失败只告警）；
  - slot 写入失败只告警，不回滚请求；binding CAS 仍是正确性边界。
- 回退语义：准备期名额首选不是原 owner 时，最终成功按 `slot_fallback` CAS 重绑；该 reason **允许跨层**（名额表可把会话分配到其他层的空闲账户），与 P0“容量/软阈值只允许同层”不同。
- 名额只控制“账户记住多少会话”，不占并发、不占 RPM；owner 并发/RPM 满时仍由派发阶段 1-2s 共享等待与候选切换处理。
- 驱逐保护：请求开始且 owner 名额 active 时刷新该 member 的 score/TTL（LRU 按“最近请求”而非仅“最近成功”排序），使有在途请求的旧会话不会因上次成功久远被优先驱逐；slot 服务仍不维护逐请求在途计数，极端并发下仍以 score 顺序近似。

### 5.8 多分组与“满”

- 普通分组容量忙判定改为 **every**：组内所有候选都通过既有 lane 容量 busy 谓词（硬并发 + image lane）才算该组满（D-94）；RPM 仍由派发阶段 `TryAcquire`/整池等待处理，不并入该谓词。两个调用点一起改：
  - `gatewaydispatch/preparation.go 当前组回退调用点`（当前组回退）；
  - `gatewaydispatch/fallbackcandidate.go:202`（回退目标组跳组）。
- 多分组：按 `RoutePlanSnapshot.OrderedAllowedTargets` 顺序走；当前组满 → 下一目标；所有目标都不可用才是终态（429/503 由现有终态分类决定）。不得按“哪个组有空”挑组，破坏 failover/rr/weighted 语义。
- 组级亲和保持不变：成功组绑定、不回切。容量把会话推到另一组会触发组亲和重绑（一次性换组），账户 latch 在组内生效；组切换后新组的账户绑定从零开始。
- slot 按账户共享，跨分组不重复计。

### 5.9 与既有机制的交互

| 机制 | 交互 |
| --- | --- |
| super priority | `superRank` 已在四元层内，天然是更高层；按层序优先，latch 只在同层生效 |
| fallback | `fallbackRank` 已在四元层内，天然是更低层；跨层不 latch |
| traffic migration | 高于 latch；人工迁移目标可用时不被 latch 拉回；跨层边界按四元层序 |
| soft threshold | 普通分组 `defaultSoftConcurrency` 启用时，owner 达到 `softBusy` 视为 `softBroken` 并让位；**属于 P0 重绑条件**：同层后继协议成功后按 CAS 重绑，审计 reason=`soft_threshold`；旧 owner 恢复空闲不主动回切 |
| speed-first / latency_degraded | owner 被判 `latency_degraded` 且仍进入候选时，按运行态排序让位；P0 只有同时命中容量类失败/准备期硬满才重绑。owner 被硬过滤时 P0 不 latch（§11.4）；运行态排除自动重绑留 P1 |
| 热质量/缓存率 | 影响新会话选择和同层排序；owner 健康时不让位；后继选择中作为质量带/排序键 |
| Key 亲和 | 不变；owner 变更时清除旧 Key 指纹；Key 级 sticky 仍按现 owner 读取 |
| 组级亲和 | 不变；组切换后账户 latch 在新组重新建立 |
| switch target | 请求内切号仍受冻结上游目标过滤；rebind 只认最终成功账户 |
| 配额/健康/屏蔽 | 硬过滤；P0 只在 owner 仍在候选集且容量/运行态不可用时 latch；owner 被硬过滤时是否 latch 见 §11 |
| 媒体 lane | 沿用 lane 容量语义；latch 对所有 lane 生效，image lane 按账户硬并发判 hardBusy（`imageLaneMaxConcurrency` 已退役） |
| 账户锁死 | 锁死门仍优先；锁死窗口内不跨账户，latch 不绕过 |

### 6.1 绑定记录（Redis JSON，加法）

现有 `SessionBinding` 增加：

```json
{
  "accountId": "...",
  "scope": { "systemAccountId": "...", "apiKeyId": "...", "groupId": "..." },
  "upstreamApiKeyFingerprint": "...",
  "leaseUntilMs": 1760000000000,
  "lastActiveAtMs": 1760000000000
}
```

- 旧记录缺字段：`leaseUntilMs=0` 按 **legacy active** 处理（不降级既有亲和）；首次成功请求补写 lease；只有 `leaseUntilMs>0` 且已过期才视为失活。
- 不批量清洗；不新增 PG 列。
- 绑定 TTL 仍 1h；排序读刷新 TTL；lease 只由成功请求刷新。

### 6.2 slot 索引（P1，Redis ZSET）

- key：`juhe-ai:{<namespace>}:session-affinity:slot:<accountId>`（`RedisNamespacedKey` 生成的实例命名空间前缀）。
- member = `sessionAffinityKey`；score = `leaseUntilMs`（毫秒）。
- 维护：
  - 最终成功：先校验当前 binding owner 等于成功账户，再执行 Lua“清理过期 → 已存在则刷新 score → 满则 ZPOPMIN → ZADD → PEXPIRE”；过期清理条件为 `score <= now`，TTL 为绑定 TTL + 索引 padding。
  - 等待探测：同一 Lua 批量清理过期、返回每个候选的 ZCARD 与当前会话是否在表中。
  - 重绑/驱逐：`ZREM` 旧 owner member；被驱逐 member 异步清理 binding。
- 原子性：slot ZSET 与 binding 写入分开；slot 是 advisory，binding CAS 是权威。Lua 只负责“清理过期 + 计数 + 取最老成员”，不负责完整 binding JSON 构造。

### 6.3 账号索引现状

现有 `juhe-ai:session-affinity:index:account:*`、`:account-system:*`、`:account-system-api-key:*` ZSET（`affinityredis.go:390-406`）用于按账户枚举绑定（traffic migration）。slot 使用独立 key 空间，不复用这些索引，避免语义混用。

## 9. 失败、降级、兼容与回滚

- **Redis 读失败**：排序降级为无亲和（现有行为），不影响请求；告警。
- **Rebind CAS 失败**：保留现值，告警；请求结果不变；下一次请求按现值继续。
- **lease/slot 写失败**：slot advisory，告警；binding 写入成功则以 binding 为准。
- **旧二进制**：新增 JSON 字段被 `encoding/json` 忽略；新 Redis key 按 TTL 过期；无 PG DDL；回退只换二进制。
- **多实例**：lease/slot/CAS 全部 Redis；进程内 fallback 只用于测试/降级，生产不依赖本地 map。
- **无 feature flag**：行为默认生效；通过发布批次和 dev 观察控制风险，不引入 2^N 配置组合。

## 10. 验收标准与测试

### 10.1 验收标准

1. 同层 A 硬满 → B 成功 → owner=B；A 恢复空闲后连续 20 次请求全部落 B，无回切。
2. 同层后继仍按现有比较器（层键 → affinityAllowed → softBusy → loadRatio → currentConcurrency → qualityBand → 稳定序）；质量带不主动抢占健康 owner；负载分散，不集中到同一账户。质量优先的后继选择器与稳定随机分散留后续评估。
3. 同会话并发 A→B / A→C：只有一个 CAS 成功，最终 owner 稳定；Redis 失败不影响请求。
4. 并发满只做 200ms 固定轮询、最多 5-10 次（1-2s）的有界等待；名额等待与 owner 并发等待共享同一预算；RPM 满在 reset 不落在剩余预算内时立即切换；无每请求 1.2s 固定等待。
5. 软阈值、`latency_degraded`、super priority、fallback、traffic migration 行为符合 §5.9；P0 容量类与软阈值重绑已验收，运行态排除自动重绑为 P1。
6. D-94 修复后，普通分组只有整组所有候选项 lane 容量忙（硬并发 + image lane）才回退下一组；两个调用点均回归；多分组终态为所有目标耗尽。
7. 既有账户亲和、Key 亲和、组级亲和、高并发队列、媒体 lane 回归全绿。
8. P0 前后基线对照：会话-账户命中率提升、跨账户切换下降、缓存率不降、p95/429 不显著恶化（目标值基线后回填）。
9. P1 已实施：slot 容量公式、名额规划（owner 有名额/未满、满等待、同层→其他层回退、全满保留 owner）、成功结算写入/释放/LRU 驱逐、请求开始 touch 保护在途会话、`slot_fallback` 跨层重绑、Redis 适配器与 Prometheus 指标均有单测；名额满不拒绝请求。

## 11. 开放决策

> 2026-11-09 用户裁决“按建议来”：质量带 2000ms、删除 `anySuperPriority`、P1 名额表最初由 P0 指标决定、owner 硬过滤 P0 不扩展、LRU 在途保护留 P1；2026-11-10 用户裁决提前实施 P1 名额表。以下保留仍未定的实施决策。

1. **质量带档宽校准**：`qualityBandWidthMs=2000` 已作为 P0 起点；W12 用 dev/生产 `QualityScore` 分布校准，若分布集中在同一档导致该键无效，再调整档宽。质量不升为层；“质量优先于粘性”是独立产品决策，必须升层而不是调档宽。
2. **质量优先后继与稳定随机分散（P1）**：P0 只把质量带作为同负载档位键。是否把质量带提到负载之前、是否加 `hash(sessionKey)` 稳定随机键，由 W12 的迁移目标分布/冷启动账户流量/跨账户切换率决定；未获数据前不实施。
3. **P1 名额表是否实施**：2026-11-10 用户裁决实施；容量公式、1-2s 共享等待、同层优先回退、LRU、跨层 `slot_fallback` 已落地。后续只需观察名额命中/回退/驱逐指标，不再以“是否实施”为开放问题。
4. **owner 被硬过滤（禁用/冷却/配额）时是否 latch**：P0 只处理 owner 仍在候选集的情况；若要扩展到硬过滤，绑定需存层快照，P1 再评估。
5. **LRU 在途保护**：已实施请求开始 touch active slot，LRU 按最近请求排序，降低在途会话被驱逐概率；不维护逐请求在途计数，若生产仍观察驱逐后切换率反弹，再评估调用方显式保护标记。
