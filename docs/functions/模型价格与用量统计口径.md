# 模型价格与用量统计口径

> 面向 AI 和维护者。
> 本文记录不同厂商模型价格、usage 字段和本地统计成本的核对方法。模型是否存在和是否废弃看 [厂商模型目录更新与清洗指南](厂商模型目录更新与清洗指南.md)；本文专注“请求回来以后 token 和成本怎么算”。
> 管理员全局模型、用户个人模型、自定义价格和账号模型映射的目录事实见 [自定义模型与模型映射设计](自定义模型与模型映射设计.md)。

## 1. 通用原则

- 厂商官方价格页和官方 API usage 字段是最终来源。
- 第三方中转只能作为实现参考，不能替代官方价格。
- 先确认 usage 原始字段，再确认本地归一化字段，最后确认成本公式。
- 成本估算优先按上游实际返回的 usage 结算；流式请求已经产生文本、reasoning、工具参数等可见输出但没有返回 usage 时，按请求体和已解析输出做本地估算，避免真实已收费链路记成 0。
- 发生账号模型映射时，成本只按最终实际上游供应商与上游模型目录行的直接价格计算；模型映射不能引用另一模型价格，也不能按相似名称回退。
- 发生 API Key 级混合智能路由时，成本必须拆成评分模型成本、最终目标模型成本、失败 / 兜底尝试成本和缓存命中收益；不能只用最终目标模型价格描述本次请求成本。
- 自定义模型价格与内置官方价格使用同一字段语义；价格查找优先级为个人自定义模型、全局自定义模型、内置模型。
- 只要已经真实请求上游 AI 账户，就必须写入 `usage_records`，不因它是账户测试、后台 job、质量探测或内部调用而跳过。
- 同一厂商不同端点可能使用不同 usage 字段，不要只按一种响应格式写死。
- 不同厂商缓存、图片、音频、批处理、service tier、长上下文阶梯价的语义不同，必须按厂商单独补充。

## 2. 统计归属规则

使用记录是事实源，按“实际上游尝试”记账：

- 客户从客户端网关 `/*` 或 `/v1/*` 发起的模型请求，成功、失败、流式中断、上游 4xx/5xx 都写入使用记录；OpenAI API Key 上游仍归一到 `/v1/*`。
- 账户测试，以及后台冷却复测，只要通过模型接口请求了上游账户，都写入使用记录。OpenAI OAuth 额度快照不再主动发模型请求获取，只从真实网关请求或账户测试响应头被动更新。
- 同一次客户请求如果因为账户错误处理策略或临时重试实际请求了多个上游账户，每一次上游尝试各写一条；最终成功不会抵消前面的失败尝试。
- 失败请求如果上游返回了 usage，则按 usage 解析 token 和成本；如果是已经产生可见输出的流式失败但没有 usage，则估算输入 / 输出 token 和成本；没有可见输出也没有 usage 时仍记录请求、账号、状态、耗时和错误，token / cost 按 0。
- 客户端中途取消时，只要请求已经发到上游账户，也要记录一条失败使用记录；如果取消发生在认证、限额、调度前，没有真实上游请求，则不按模型消耗记账。
- 本地生成的 `/v1/models` 可记录为 0 token / 0 cost 的网关请求，用于排障和客户端初始化追踪；它不是上游模型消耗。
- 本地容量或本地策略失败如果已经定位到账号，可以保留账号上下文和错误原因用于排障，但必须通过 `failure_attribution` 标记归因；只有 `account_upstream` 和 `account_dependency` 这类账号调用链路失败才能进入账号质量，`gateway_capacity`、`gateway_policy` 和 `client_lifecycle` 不应影响 AI 账户近期质量和后台频繁失败预检。
- OAuth token refresh、授权 URL、token 交换、代理连通性检测、系统指标采样不是模型请求，不计入模型 token / cost。
- `usage_records` 保留事实明细；统计缓存和前端图表必须从该事实源聚合，不能过滤掉测试或后台 job 的真实上游调用。

混合智能路由的统计归属规则：

- 评分模型调用是真实上游模型请求，必须单独写入使用记录，建议标记 `traffic_source = hybrid_scoring`。
- 最终目标模型调用继续按真实命中的分组、账户、模型写入使用记录，并在审计 metadata 中保留评分等级、目标模型、缓存亲和和切换原因。
- API Key 美元额度按评分请求和最终请求的实际成本合计判断。
- 混合路由节省额只能由后台 worker 按 usage 明细增量聚合，不能在网关请求链路或前端页面扫描明细临时计算。
- 跨模型、跨供应商或跨账号会降低上游 KV / prompt cache 命中，节省估算必须把 `cache_read_tokens`、缓存读取成本和模型切换导致的缓存损失作为独立维度。

### 2.1 使用记录展示边界

使用记录页面是排障和扫表入口，不承担完整价格解释：

- `Token 用量` 列和移动端卡片只展示 `输入`、`输出`、`缓存读` 三项。
- `模型` 列在模型名后展示实际 `billed_service_tier` 和最终上游请求的 `effective_reasoning_effort`；`default` / 空档位不显示无信息标签。
- `首 token` 和 `总耗时` 在桌面表格与移动卡片统一合并为 `延迟`，两项仍分别取 `first_token_ms`、`duration_ms`，不改变统计口径。
- 成本明细只解释计价事实：计价模型、非 Default 的实际服务档位、档位专用价 / 基础价倍率来源、请求时锁定的最终单价、各项小计和合计；不重复展示请求模型、实际上游模型、映射来源、协议映射或“模型口径”。
- `cost_breakdown_snapshot_json` 在记录写入时固化最终单价、小计、实际倍率和档位计价来源。新记录即使目录未命中，也必须写入 `unknown` 快照并保留当时已有的总成本 / 缓存成本事实，禁止用未来目录价格重新解释；该字段上线前的旧空快照只展示已落库总成本 / 缓存成本并标记来源未知，不重建单价或小计。
- 前端不得自行重算成本；`ProviderCostBreakdown` 由后端生成，页面只负责中文展示。

### 2.3 Token 用量可信度与计费边界

上游返回的 usage 是当前成本和额度计算的事实输入，但“上游报告了数字”不等于已经证明该数字没有灌水。Token 用量可信度诊断按 [模型检测设计](模型检测设计.md) 的受控差分探针执行，与实际计费链路保持分离：

- 当前 `usage_shape` 只检查字段存在和数字形态，不具备 Token padding 检测能力。
- 独立的 `token_integrity` 受控探针使用锁定的 `js-tiktoken@1.0.21:o200k_base` 执行三轮 P0 / P1 / P2 输入差分；结论由 stats-worker 预聚合，不改变 `usage_shape` 和计费事实语义。
- 普通流式 usage 缺失时使用的本地估算器是防止已产生消耗却记成 0 的兜底，不是精确 tokenizer，也不能拿它和单次上游 usage 差值直接判定灌水。
- Token 诚信探针必须使用版本锁定的精确 tokenizer、P0 / P1 / P2 已知增量和多轮随机顺序，优先比较 reported / local 的差分斜率；服务端消息模板等固定开销由 intercept 和同 cohort 基线吸收。
- input 比例灌水、固定增加和分桶取整分别输出诊断原因；输出 Token 存在隐藏 reasoning 且没有 breakdown 时必须标记为不支持或证据不足。
- Token 诚信结果只读取受控探针 observation，不扫描普通用户正文，不用自然流量输出训练真假标签。
- 模型身份 observation 与 Token 诚信共用 dataset 游标，但分别写入身份来源特征 / paired 基线和 Token 窗口；身份侧只保存受控回答即时提取的有界数值特征，不保存回答正文，也不改变 usage、成本、额度和账单事实。
- 第一阶段即使诊断为 `suspected_padding`，也不回写 `usage_records`，不自动修改成本、额度、账单或账号状态。是否引入对账、赔付或计费修正必须另立需求，并以真实上游账单和误报校准为前提。

### 3.2 价格公式

文本模型基础公式：

```text
uncached_input_tokens = input_tokens - cached_tokens - separately_priced_input_tokens
text_output_tokens = output_tokens - separately_priced_output_tokens

cost =
  uncached_input_tokens * input_cost_per_token
  + cached_tokens * cache_read_input_token_cost
  + text_output_tokens * output_cost_per_token
  + separately_priced_tokens * corresponding_special_price
```

OpenAI prompt caching 的 `cached_tokens` 仍包含在总输入 token 里，但要按 cached input 价格单独计费，所以本地公式必须先从普通 input tokens 中扣掉缓存命中 token。

GPT-5.6 预览系列新增明确的 cache write 计费口径：缓存写入按普通 input 价格的 1.25 倍计费，缓存读取按普通 input 价格 90% 折扣计费。本地价格目录将其映射为 `cache_creation_input_token_cost` 和 `cache_read_input_token_cost`；实际请求是否产生 cache write token 仍以上游返回的 usage 字段为准，不在解析层自行推断。

OpenAI 官方 Responses / Chat Completions usage 当前标准字段主要提供 `input_tokens_details.cached_tokens` / `prompt_tokens_details.cached_tokens`，用于缓存读取或 cached input 计费。OpenAI-compatible 上游如果额外返回明确的 `cache_write_tokens`、`cache_write_input_tokens`、`cache_creation_tokens`、`cache_creation_input_tokens`、`cache_creation.ephemeral_5m_input_tokens`、`cache_creation.ephemeral_1h_input_tokens`，或兼容桥字段 `claude_cache_creation_5_m_tokens` / `claude_cache_creation_1_h_tokens`，本地会映射为 `cache_write_tokens` / `cache_write_1h_tokens` 并进入成本明细；`prompt_cache_miss_tokens` 只代表 DeepSeek 等上游的缓存未命中事实，不能当作 OpenAI-compatible 通用 cache write。

`image_tokens` 和 `audio_tokens` 是 usage 细分字段，不等于一定有独立图片或音频单价。只有模型价格表明确提供 `input_cost_per_image_token`、`output_cost_per_image_token`、`input_cost_per_audio_token` 或 `output_cost_per_audio_token` 时，才从普通输入 / 输出 token 中拆出对应成本；例如 GPT Image 模型会展示图片输入 / 输出成本，而 `gpt-5.5` 这类按普通 input / output token 计费的模型不再展示重复的图片单价。自定义模型如果只配置音频价格且没有文本价格，成本估算会把总输入 / 输出 token 作为音频 token 兜底计费；按张图片价格只在已知图片张数时计入，不自动猜测张数。

OpenAI-compatible 可见模型目录以官方最新模型和可确认发布时间倒序维护。`2026-07-09` 复核时，OpenAI Help Center 发布 `GPT-5.6` 预览系列，API model ID 为 `gpt-5.6-sol`、`gpt-5.6-terra` 和 `gpt-5.6-luna`；本地 `gpt` / `openai` 目录首屏固定为 `gpt-5.6-sol`、`gpt-5.6-terra`、`gpt-5.6-luna`、`gpt-5.5`、`gpt-5.5-2026-04-23`、`gpt-5.5-pro`、`gpt-5.5-pro-2026-04-23`、`gpt-image-2`。

2026-07-14 已按官方模型页把 GPT-5.6 Sol / Terra / Luna 目录统一为 `context_window = 1050000`、`max_input = 922000` 和 `max_output = 128000`，并由模型目录回归锁定三个字段。该目录事实只描述能力边界，不作为 Sol / Terra / Luna 子版本身份判据。

GPT-5.6 预览系列标准 API 价格如下；Batch 和 Flex 按相同 token 维度 50% 折扣，cache write/cache read 仍按上述倍率从标准 input 价换算：

| --- | ---: | ---: | ---: | ---: |
| `gpt-5.6-sol` | 5.00 USD | 6.25 USD | 0.50 USD | 30.00 USD |
| `gpt-5.6-terra` | 2.50 USD | 3.125 USD | 0.25 USD | 15.00 USD |

Responses usage 常见字段：

```json
{
  "usage": {
    "input_tokens": 1000,
    "output_tokens": 200,
    "input_tokens_details": {
      "cached_tokens": 300,
      "image_tokens": 25,
      "audio_tokens": 30
    },
    "output_tokens_details": {
      "image_tokens": 1000,
      "audio_tokens": 40
    },
    "output_image_count": 2
  }
}
```

Chat Completions usage 常见字段：

```json
{
  "usage": {
    "prompt_tokens": 1000,
    "completion_tokens": 200,
    "prompt_tokens_details": {
      "cached_tokens": 300
    },
    "completion_tokens_details": {
      "image_tokens": 1000,
      "audio_tokens": 40
    }
  }
}
```

流式 Chat Completions 只有请求启用 `stream_options.include_usage` 时，最后的 chunk 才会带总 usage；Responses 流式通常在 `response.completed` 的 `response.usage` 中给总 usage。为保留 API Key 账号 raw body 透传，本项目不默认改写请求体注入 `stream_options.include_usage`；使用记录以旁路解析到的上游 usage 为准，缺失时只对已产生可见输出的流式请求做估算兜底。

本地估算不是 OpenAI 官方账单算法，不能替代上游 `usage`。官方公开可用的是响应里的 `usage`、Tokenizer 工具和 `tiktoken` 文本 tokenizer；多模态图片 / 音频、隐藏 reasoning、服务端消息模板、工具 schema 包装、缓存命中等最终仍以上游返回的 usage 为准。估算只用于“已经转发可见输出但 final usage 丢失”的失败兜底：输入优先递归统计已解析 JSON 中的文本字段，跳过 `model`、`stream`、`stream_options`、`metadata`、`user` 和裸 base64 数据；输出统计 SSE delta、Chat choices、工具调用参数，以及仅在没有 delta 计数时补看 Responses 的 `output_item.done` / `response.completed.output`。如果只收到心跳、`response.created`、空 `output_item.added` 或其他 metadata，不按输出 token 估算。

### 3.4 本次调研结论

本次调研日期：`2026-07-09`。

- 原解析只读 Responses 字段，漏掉 Chat Completions 的 `prompt_tokens`、`completion_tokens`、`prompt_tokens_details.cached_tokens`。

- 自定义音频模型如果只配置音频输入 / 输出价格，现已能按 `audio_tokens` 或纯音频模型的总输入 / 输出 token 计算成本；按张图片价格现已能在已知 `output_image_count` / `output_images` / `image_count` 时计入成本拆解。

- 部分统计图表曾把 `cache_read_tokens` 再加到总 token 中；OpenAI 的 cached tokens 已包含在 input tokens 中，所以总 token 应为 `input_tokens + output_tokens`，缓存命中只作为拆分指标和成本折扣依据。

- 流式请求如果在可见输出后失败且上游没有返回 usage，网关会按请求体和已解析输出做轻量估算并写入 `usage_records`；首包前失败、只有 `response.created` / 心跳 / metadata 这类不可见输出的中断仍按 0 token / 0 cost 记录。
- 流式本地估算已补充大 JSON / base64 防误算和 Responses `output_item.done` 兜底：大请求已成功解析 JSON 时不再直接按 raw body 字节数除以 4 估算，避免把 data URL / 音频块按文本收费；空 `output_item.added` 不算可见输出；只有 `output_item.done` 或 `response.completed.output` 携带完整内容且没有前序 delta 时，才补算输出 token。
- 账户测试复用 `testOpenAIAccount()`，而 `testOpenAIAccount()` 会构造内部 `/v1/responses` 请求并调用 `handleOpenAIGatewayRequest()`，不会绕过使用记录。后台冷却复测固定启用，但只对冷却到期的 `temporary_unavailable` 做恢复性测试；`rate_limited` 等其他状态不主动复测、不做自愈恢复。账号质量主动探测代码已删除，避免后续在没有业务收益的情况下恢复上游测速请求。OpenAI OAuth 额度快照已改为被动读取真实网关响应头，不再通过 `testOpenAIAccount()` 主动刷新。

- 统计聚合的 `request_count` 以 `usage_records` 明细为事实源；失败无 usage 且无可见输出时按 0 token / 0 cost 纳入请求数和错误数，失败流已经产生可见输出时按使用记录里的估算 token / cost 聚合，避免漏掉真实消耗链路。

- Context Caching：[Context Caching](https://api-docs.deepseek.com/guides/kv_cache)
- 价格：[Pricing](https://api-docs.deepseek.com/quick_start/pricing)
- 余额查询：[Get User Balance](https://api-docs.deepseek.com/api/get-user-balance)

价格只采信 DeepSeek 官方价格页、官方模型页或官方 API 文档。DeepSeek 开源权重、第三方中转价格、社区表格和其他平台部署价只能作为线索，不能作为 DeepSeek hosted API 的价格事实。

### 9.2 usage 解析

DeepSeek OpenAI-compatible Chat Completions 响应优先复用 OpenAI v1 Chat usage 解析，并补充 DeepSeek 扩展字段：

- 输入 token：优先读取 `usage.prompt_tokens`。
- 输出 token：优先读取 `usage.completion_tokens`。
- 总 token：优先读取 `usage.total_tokens`；没有时用输入和输出相加。
- 缓存命中：读取 `usage.prompt_cache_hit_tokens`，映射为 DeepSeek 扩展 cache hit 统计和成本拆分来源。
- 缓存未命中：读取 `usage.prompt_cache_miss_tokens`，映射为 DeepSeek 扩展 cache miss 统计和成本拆分来源。
- reasoning 内容：`reasoning_content` 是响应内容字段，不等同于独立计价字段；如果官方后续返回 reasoning token 细分，再按字段进入供应商扩展 usage，不从文本自行推断。

Context Caching 默认开启，不需要请求参数。缓存命中和未命中 token 仍属于输入 token 语义，统计总 token 不能把 `prompt_cache_hit_tokens` 再额外加一遍。成本拆分应按 DeepSeek 官方价格页的 cache hit / miss 或 cached input 口径计算；如果官方价格口径没有明确拆分，先保留 token 事实并按普通输入价格估算，不臆造折扣。

流式请求仍按现有原则：上游提供最终 usage 时以 usage 为准；没有 usage 且已经产生可见输出时做本地估算兜底；首包前失败、只有 keep-alive comment / 空行 / metadata 时按 0 token / 0 cost 记录。

### 9.3 成本与额度边界

- DeepSeek API Key 直连按官方 token 价格估算美元成本，进入本地 API Key 和统一授权美元额度统计。
- DeepSeek hosted API 是 API-key-only，不存在 OpenAI OAuth 额度快照或 Codex quota header。
- DeepSeek Balance 接口可作为后续账户页人工诊断信息，但不参与本地 API Key 额度、系统团队授权额度或统一授权额度判断。
- 本地额度消耗以真实 `usage_records` 和后台预聚合结果为准，不在网关请求链路调用 Balance 接口。
- `finish_reason = insufficient_system_resource` 属于上游完成语义和诊断输入，不因为单次出现直接改写 token 或成本；如果已有 usage，仍按 usage 入账。

### 9.4 本地映射

```text
providerCode = deepseek
providerProtocolProfileId = profile_deepseek_openai_v1
supportedApiProtocols = chat_completions
usage 字段按 OpenAI Chat Completions + DeepSeek cache 扩展解析
成本按 DeepSeek 官方价格估算
```

初始价格目录必须单独放在 DeepSeek 供应商数据文件中，不要混入 GPT / OpenAI 价格目录。旧别名 `deepseek-chat` 和 `deepseek-reasoner` 如果保留用于历史兼容，应明确标注 shutdown date 和计价来源，不作为新默认模型。

### 9.5 验证要求

DeepSeek usage / pricing 落地后至少覆盖：

- JSON Chat Completions usage 能解析 `prompt_tokens`、`completion_tokens`、`total_tokens`。
- DeepSeek cache usage 能解析 `prompt_cache_hit_tokens` 和 `prompt_cache_miss_tokens`，且总 token 不重复相加。
- 成本估算按 `providerCode = deepseek` 查找 DeepSeek 模型价格，不回落到 GPT / OpenAI 同名或相似模型。
- 流式 keep-alive comment / 非流式空行不会产生 output token 估算。
- Balance 接口不参与请求链路额度判断。
- `pnpm --filter juhe-ai-backend test:usage-pricing` 覆盖 DeepSeek usage 和成本拆分。
