# 模型价格与用量统计口径

> 面向 AI 和维护者。
> 本文记录不同厂商模型价格、usage 字段和本地统计成本的核对方法。模型是否存在和是否废弃看 [厂商模型目录更新与清洗指南](厂商模型目录更新与清洗指南.md)；本文专注“请求回来以后 token 和成本怎么算”。

## 1. 通用原则

- 厂商官方价格页和官方 API usage 字段是最终来源。
- 第三方中转只能作为实现参考，不能替代官方价格。
- 先确认 usage 原始字段，再确认本地归一化字段，最后确认成本公式。
- 成本估算只按上游实际返回的 usage 结算；失败请求没有 token 和 cost 时按 0 计入请求数和错误数。
- 只要已经真实请求上游 AI 账户，就必须写入 `usage_records`，不因它是账户测试、后台 job、质量探测或内部调用而跳过。
- 同一厂商不同端点可能使用不同 usage 字段，不要只按一种响应格式写死。
- 不同厂商缓存、图片、音频、批处理、service tier、长上下文阶梯价的语义不同，必须按厂商单独补充。

## 2. 统计归属规则

使用记录是事实源，按“实际上游尝试”记账：

- 客户从 `/v1/*` 发起的模型请求，成功、失败、流式中断、上游 4xx/5xx 都写入使用记录。
- 账户测试、后台冷却复测、账户质量主动探测、OpenAI OAuth 创建后的首次用量快照、OpenAI OAuth 后台额度快照，只要通过模型接口请求了上游账户，都写入使用记录。
- 同一次客户请求如果因为错误策略或临时重试实际请求了多个上游账户，每一次上游尝试各写一条；最终成功不会抵消前面的失败尝试。
- 失败请求如果上游返回了 usage，则按 usage 解析 token 和成本；没有 usage 时仍记录请求、账号、状态、耗时和错误，token / cost 按 0。
- 客户端中途取消时，只要请求已经发到上游账户，也要记录一条失败使用记录；如果取消发生在认证、限额、调度前，没有真实上游请求，则不按模型消耗记账。
- 本地生成的 `/v1/models` 可记录为 0 token / 0 cost 的网关请求，用于排障和客户端初始化追踪；它不是上游模型消耗。
- OAuth token refresh、授权 URL、token 交换、代理连通性检测、系统指标采样不是模型请求，不计入模型 token / cost。
- `usage_records` 保留事实明细；统计缓存和前端图表必须从该事实源聚合，不能过滤掉测试或后台 job 的真实上游调用。

## 3. OpenAI 口径

### 3.1 官方来源

OpenAI 价格和 usage 审计优先使用这些官方页面：

- 价格目录：[OpenAI Pricing](https://developers.openai.com/api/docs/pricing)
- Prompt Caching：[Prompt caching](https://developers.openai.com/api/docs/guides/prompt-caching)
- Responses API reference：[Responses](https://developers.openai.com/api/reference/responses)
- Chat Completions API reference：[Chat Completions](https://developers.openai.com/api/reference/chat)
- Images API reference：[Images](https://developers.openai.com/api/reference/images)

如果 `openai-docs` 技能可用，先用 OpenAI developer docs MCP；如果 MCP 不可用或当前会话没有工具，回退到官方域名网页检索，范围只限 `developers.openai.com` 和 `platform.openai.com`。

### 3.2 价格公式

文本模型基础公式：

```text
uncached_input_tokens = input_tokens - cached_tokens - separately_priced_input_tokens
text_output_tokens = output_tokens - separately_priced_output_tokens

cost =
  uncached_input_tokens * input_cost_per_token
  + cached_tokens * cache_read_input_token_cost
  + text_output_tokens * output_cost_per_token
  + separately_priced_tokens * corresponding_special_price
```

OpenAI prompt caching 的 `cached_tokens` 仍包含在总输入 token 里，但要按 cached input 价格单独计费，所以本地公式必须先从普通 input tokens 中扣掉缓存命中 token。

Responses usage 常见字段：

```json
{
  "usage": {
    "input_tokens": 1000,
    "output_tokens": 200,
    "input_tokens_details": {
      "cached_tokens": 300,
      "image_tokens": 25
    },
    "output_tokens_details": {
      "image_tokens": 1000
    }
  }
}
```

Chat Completions usage 常见字段：

```json
{
  "usage": {
    "prompt_tokens": 1000,
    "completion_tokens": 200,
    "prompt_tokens_details": {
      "cached_tokens": 300
    },
    "completion_tokens_details": {
      "image_tokens": 1000
    }
  }
}
```

流式 Chat Completions 只有请求启用 `stream_options.include_usage` 时，最后的 chunk 才会带总 usage；Responses 流式通常在 `response.completed` 的 `response.usage` 中给总 usage。

### 3.4 本次调研结论

本次调研日期：`2026-05-08`。

采用的方法：

- 使用 `openai-docs` 技能规则确认 OpenAI 资料必须以官方文档为准。
- 访问 OpenAI 官方价格页、Prompt Caching 指南和 API reference，确认 input / cached input / output 的计费单位与 usage 字段。当前会话没有 OpenAI Docs MCP 工具，所以回退到官方网页；实际核对到的页面包括 [OpenAI API Pricing](https://openai.com/api/pricing/)、[Prompt caching](https://platform.openai.com/docs/guides/prompt-caching)、[Responses API reference](https://platform.openai.com/docs/api-reference/responses) 和 [Image Streaming API reference](https://platform.openai.com/docs/api-reference/images-streaming?api-mode=responses)。
- 用 `rg` 检查本项目 usage 解析、成本估算、使用记录落库和统计聚合链路。
- 对比 `F:\temp-project` 里的 LiteLLM、new-api、one-api。
- 增加 `pnpm --filter juhe-ai-backend test:usage-pricing` 回归脚本，覆盖 Responses、Chat Completions、Responses SSE、Chat SSE include_usage、缓存折扣和图片 token 价格。

对比结果：

- LiteLLM 会从 `prompt_tokens_details.cached_tokens` 中取缓存命中 token，并从普通 prompt tokens 里扣掉后再按缓存读取价格计费，和本项目修正后的口径一致。
- new-api 同时兼容 OpenAI Responses 的 `input_tokens/output_tokens/input_tokens_details` 和 Chat Completions 的 `prompt_tokens/completion_tokens/prompt_tokens_details`，并支持缓存、图片、音频变量归一化。
- one-api 主要使用模型倍率、分组倍率和 completion ratio 做内部 quota 扣费，不适合作为官方美元成本的真值来源。

本次发现并修正：

- 原解析只读 Responses 字段，漏掉 Chat Completions 的 `prompt_tokens`、`completion_tokens`、`prompt_tokens_details.cached_tokens`。
- 原流式解析只在 `response.completed/response.done/response.failed` 中采集 usage，漏掉 Chat Completions 最终 usage chunk。
- GPT Image 类模型存在图片 token 专用单价，原成本估算会把输出图片 token 按普通输出 token 价格计算，导致成本偏低；现已支持图片输入 / 输出 token 专用价格，且在没有输出细分但模型是 `image_generation` 时，把 `output_tokens` 作为图片输出 token 结算。
- 使用记录新增保存 `input_image_tokens` 和 `output_image_tokens`，避免详情页后续重算成本明细时丢失图片 token 拆分。
- 部分统计图表曾把 `cache_read_tokens` 再加到总 token 中；OpenAI 的 cached tokens 已包含在 input tokens 中，所以总 token 应为 `input_tokens + output_tokens`，缓存命中只作为拆分指标和成本折扣依据。
- 账户测试、后台冷却复测、账户质量主动探测和 OpenAI OAuth 用量快照已确认复用 `testOpenAIAccount()`，而 `testOpenAIAccount()` 会构造内部 `/v1/responses` 请求并调用 `handleOpenAIGatewayRequest()`，不会绕过使用记录。
- 网关成功、上游 4xx/5xx、请求异常、流式首包前失败、流式中断、上游流式空响应体、客户端已发起上游后的取消，均会按实际上游尝试写入使用记录。
- 统计聚合的 `request_count` 以 `usage_records` 明细为事实源，失败无 usage 时按 0 token / 0 cost 纳入请求数和错误数，避免漏掉真实消耗链路。
