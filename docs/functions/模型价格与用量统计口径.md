# 模型价格与用量统计口径

> 面向 AI 和维护者。
> 本文记录不同厂商模型价格、usage 字段和本地统计成本的核对方法。模型是否存在和是否废弃看 [厂商模型目录更新与清洗指南](厂商模型目录更新与清洗指南.md)；本文专注“请求回来以后 token 和成本怎么算”。
> 管理员全局模型、用户个人模型、自定义价格和账号模型映射的目录事实见 [自定义模型与模型映射设计](自定义模型与模型映射设计.md)。

## 1. 通用原则

- 厂商官方价格页和官方 API usage 字段是最终来源。
- 第三方中转只能作为实现参考，不能替代官方价格。
- 先确认 usage 原始字段，再确认本地归一化字段，最后确认成本公式。
- 成本估算优先按上游实际返回的 usage 结算；流式请求已经产生文本、reasoning、工具参数等可见输出但没有返回 usage 时，按请求体和已解析输出做本地估算，避免真实已收费链路记成 0。
- 发生账号模型映射时，成本估算优先使用实际上游模型的 `pricingModel` 指向价格，其次使用实际上游模型直接价格；未映射时按下游请求模型同样顺序解析。
- 发生 API Key 级混合智能路由时，成本必须拆成评分模型成本、最终目标模型成本、失败 / 兜底尝试成本和缓存命中收益；不能只用最终目标模型价格描述本次请求成本。
- 自定义模型价格与内置官方价格使用同一字段语义；价格查找优先级为个人自定义模型、全局自定义模型、内置模型。
- 只要已经真实请求上游 AI 账户，就必须写入 `usage_records`，不因它是账户测试、后台 job、质量探测或内部调用而跳过。
- 同一厂商不同端点可能使用不同 usage 字段，不要只按一种响应格式写死。
- 不同厂商缓存、图片、音频、批处理、service tier、长上下文阶梯价的语义不同，必须按厂商单独补充。

## 2. 统计归属规则

使用记录是事实源，按“实际上游尝试”记账：

- 客户从客户端网关 `/*` 或 `/v1/*` 发起的模型请求，成功、失败、流式中断、上游 4xx/5xx 都写入使用记录；OpenAI API Key 上游仍归一到 `/v1/*`。
- 账户测试，以及后台冷却复测，只要通过模型接口请求了上游账户，都写入使用记录。OpenAI OAuth 额度快照不再主动发模型请求获取，只从真实网关请求或账户测试响应头被动更新。
- 同一次客户请求如果因为账户错误处理策略或临时重试实际请求了多个上游账户，每一次上游尝试各写一条；最终成功不会抵消前面的失败尝试。
- 失败请求如果上游返回了 usage，则按 usage 解析 token 和成本；如果是已经产生可见输出的流式失败但没有 usage，则估算输入 / 输出 token 和成本；没有可见输出也没有 usage 时仍记录请求、账号、状态、耗时和错误，token / cost 按 0。
- 客户端中途取消时，只要请求已经发到上游账户，也要记录一条失败使用记录；如果取消发生在认证、限额、调度前，没有真实上游请求，则不按模型消耗记账。
- 本地生成的 `/v1/models` 可记录为 0 token / 0 cost 的网关请求，用于排障和客户端初始化追踪；它不是上游模型消耗。
- 本地容量或本地策略失败如果已经定位到账号，可以保留账号上下文和错误原因用于排障，但必须通过 `failure_attribution` 标记归因；只有 `account_upstream` 和 `account_dependency` 这类账号调用链路失败才能进入账号质量，`gateway_capacity`、`gateway_policy` 和 `client_lifecycle` 不应影响 AI 账户近期质量和后台频繁失败预检。
- OAuth token refresh、授权 URL、token 交换、代理连通性检测、系统指标采样不是模型请求，不计入模型 token / cost。
- `usage_records` 保留事实明细；统计缓存和前端图表必须从该事实源聚合，不能过滤掉测试或后台 job 的真实上游调用。

混合智能路由的统计归属规则：

- 评分模型调用是真实上游模型请求，必须单独写入使用记录，建议标记 `traffic_source = hybrid_scoring`。
- 最终目标模型调用继续按真实命中的分组、账户、模型写入使用记录，并在审计 metadata 中保留评分等级、目标模型、缓存亲和和切换原因。
- API Key 美元额度按评分请求和最终请求的实际成本合计判断。
- 混合路由节省额只能由后台 worker 按 usage 明细增量聚合，不能在网关请求链路或前端页面扫描明细临时计算。
- 跨模型、跨供应商或跨账号会降低上游 KV / prompt cache 命中，节省估算必须把 `cache_read_tokens`、缓存读取成本和模型切换导致的缓存损失作为独立维度。

### 2.1 使用记录展示边界

使用记录页面是排障和扫表入口，不承担完整价格解释：

- `Token 用量` 列和移动端卡片只展示 `输入`、`输出`、`缓存读` 三项。
- `缓存写入`、`1h 缓存写入`、`思考 / 推理 Tokens`、图片 token、音频 token、按张图片成本和各类单价，只在成本明细浮层里按需展示。
- 成本明细必须按供应商或 usage 语义展示中文标签：Anthropic 使用 `5m 缓存写入` / `1h 缓存写入`，OpenAI-compatible / DeepSeek / GLM 的 reasoning 类字段展示为 `推理 Tokens`，Gemini 展示为 `思考 Tokens`。
- “按需展示”指字段缺失或数值为 0 时不占用列表空间；如果某个维度有 token 或成本，即使成本为 0，也可以在成本明细里展示，避免免费价、套餐价或特殊价被误认为没有发生。
- 前端不得用展示层简化反推成本。成本估算继续使用后端 `ProviderCostBreakdown`，列表只是把明细折叠到浮层。

### 2.2 供应商计费维度速查

| 供应商 | 主要 usage / 计费维度 | 本地展示与估算要求 |
| --- | --- | --- |
| OpenAI / GPT / OpenAI-compatible | 输入、cached input、输出；图片 / 音频 / Realtime / Image 模型可能有独立 token 或按张图片价 | 文本模型列表只展示输入 / 输出 / 缓存读；图片、音频和按张成本进入成本明细。 |
| Anthropic | 输入、输出、缓存读取、缓存写入 5m、缓存写入 1h；部分模型返回 thinking 细分 | 不能把成本压成输入 / 输出 / 缓存读三项，缓存写入和 1h 缓存写入必须进入成本估算和成本明细。 |
| Gemini | 输入、输出、cached content 命中、思考 token；显式 cached content 还有存储时长费用 | 单次请求成本只按响应 usage 可确认字段估算；上下文缓存存储费需要后续单独资源 / 时间窗口字段承接，不能塞进单条请求临时估算。 |
| DeepSeek | 输入、输出、cache hit / miss；reasoning 内容是响应内容，是否有独立 token 以官方 usage 为准 | 复用 OpenAI-compatible usage 解析并补 DeepSeek cache 字段；成本必须查 DeepSeek 价格目录，不回落 GPT / OpenAI。 |
| GLM | 通用 API 复用 OpenAI-compatible token 语义；Coding Plan 是套餐权益 | 本地美元成本只用于系统额度控制，不代表 Coding Plan 官方剩余额度。 |

### 3.2 价格公式

文本模型基础公式：

```text
uncached_input_tokens = input_tokens - cached_tokens - separately_priced_input_tokens
text_output_tokens = output_tokens - separately_priced_output_tokens

cost =
  uncached_input_tokens * input_cost_per_token
  + cached_tokens * cache_read_input_token_cost
  + text_output_tokens * output_cost_per_token
  + separately_priced_tokens * corresponding_special_price
```

OpenAI prompt caching 的 `cached_tokens` 仍包含在总输入 token 里，但要按 cached input 价格单独计费，所以本地公式必须先从普通 input tokens 中扣掉缓存命中 token。

`image_tokens` 和 `audio_tokens` 是 usage 细分字段，不等于一定有独立图片或音频单价。只有模型价格表明确提供 `input_cost_per_image_token`、`output_cost_per_image_token`、`input_cost_per_audio_token` 或 `output_cost_per_audio_token` 时，才从普通输入 / 输出 token 中拆出对应成本；例如 GPT Image 模型会展示图片输入 / 输出成本，而 `gpt-5.5` 这类按普通 input / output token 计费的模型不再展示重复的图片单价。自定义模型如果只配置音频价格且没有文本价格，成本估算会把总输入 / 输出 token 作为音频 token 兜底计费；按张图片价格只在已知图片张数时计入，不自动猜测张数。

OpenAI-compatible 可见模型目录以官方最新模型和可确认发布时间倒序维护。`2026-06-22` 复核时，OpenAI developer docs `latest-model.md` 指向 `gpt-5.5`，因此本地 `gpt` / `openai` 目录首屏固定为 `gpt-5.5`、`gpt-5.5-2026-04-23`、`gpt-5.5-pro`、`gpt-5.5-pro-2026-04-23`、`gpt-image-2`、`gpt-image-2-2026-04-21`、`gpt-5.4-mini`、`gpt-5.4-mini-2026-03-17`。

Responses usage 常见字段：

```json
{
  "usage": {
    "input_tokens": 1000,
    "output_tokens": 200,
    "input_tokens_details": {
      "cached_tokens": 300,
      "image_tokens": 25,
      "audio_tokens": 30
    },
    "output_tokens_details": {
      "image_tokens": 1000,
      "audio_tokens": 40
    },
    "output_image_count": 2
  }
}
```

Chat Completions usage 常见字段：

```json
{
  "usage": {
    "prompt_tokens": 1000,
    "completion_tokens": 200,
    "prompt_tokens_details": {
      "cached_tokens": 300
    },
    "completion_tokens_details": {
      "image_tokens": 1000,
      "audio_tokens": 40
    }
  }
}
```

流式 Chat Completions 只有请求启用 `stream_options.include_usage` 时，最后的 chunk 才会带总 usage；Responses 流式通常在 `response.completed` 的 `response.usage` 中给总 usage。为保留 API Key 账号 raw body 透传，本项目不默认改写请求体注入 `stream_options.include_usage`；使用记录以旁路解析到的上游 usage 为准，缺失时只对已产生可见输出的流式请求做估算兜底。

本地估算不是 OpenAI 官方账单算法，不能替代上游 `usage`。官方公开可用的是响应里的 `usage`、Tokenizer 工具和 `tiktoken` 文本 tokenizer；多模态图片 / 音频、隐藏 reasoning、服务端消息模板、工具 schema 包装、缓存命中等最终仍以上游返回的 usage 为准。估算只用于“已经转发可见输出但 final usage 丢失”的失败兜底：输入优先递归统计已解析 JSON 中的文本字段，跳过 `model`、`stream`、`stream_options`、`metadata`、`user` 和裸 base64 数据；输出统计 SSE delta、Chat choices、工具调用参数，以及仅在没有 delta 计数时补看 Responses 的 `output_item.done` / `response.completed.output`。如果只收到心跳、`response.created`、空 `output_item.added` 或其他 metadata，不按输出 token 估算。

### 3.4 本次调研结论

本次调研日期：`2026-05-08`。

采用的方法：

- 使用 `openai-docs` 技能规则确认 OpenAI 资料必须以官方文档为准。
- 访问 OpenAI 官方价格页、Prompt Caching 指南和 API reference，确认 input / cached input / output 的计费单位与 usage 字段。当前会话没有 OpenAI Docs MCP 工具，所以回退到官方网页；实际核对到的页面包括 [OpenAI API Pricing](https://openai.com/api/pricing/)、[Prompt caching](https://platform.openai.com/docs/guides/prompt-caching)、[Responses API reference](https://platform.openai.com/docs/api-reference/responses) 和 [Image Streaming API reference](https://platform.openai.com/docs/api-reference/images-streaming?api-mode=responses)。
- 用 `rg` 检查本项目 usage 解析、成本估算、使用记录落库和统计聚合链路。
- 对比 `F:\temp-project` 里的 LiteLLM、new-api、one-api。
- 增加 `pnpm --filter juhe-ai-backend test:usage-pricing` 回归脚本，覆盖 Responses、Chat Completions、Responses SSE、Chat SSE include_usage、缓存折扣、图片 token、音频 token 和按张图片价格。

对比结果：

- LiteLLM 会从 `prompt_tokens_details.cached_tokens` 中取缓存命中 token，并从普通 prompt tokens 里扣掉后再按缓存读取价格计费，和本项目修正后的口径一致。
- new-api 同时兼容 OpenAI Responses 的 `input_tokens/output_tokens/input_tokens_details` 和 Chat Completions 的 `prompt_tokens/completion_tokens/prompt_tokens_details`，并支持缓存、图片、音频变量归一化。
- one-api 主要使用模型倍率、分组倍率和 completion ratio 做内部 quota 扣费，不适合作为官方美元成本的真值来源。

本次发现并修正：

- 原解析只读 Responses 字段，漏掉 Chat Completions 的 `prompt_tokens`、`completion_tokens`、`prompt_tokens_details.cached_tokens`。
- 原流式解析只在 `response.completed/response.done/response.failed` 中采集 usage，漏掉 Chat Completions 最终 usage chunk。
- GPT Image 类模型存在图片 token 专用单价，原成本估算会把输出图片 token 按普通输出 token 价格计算，导致成本偏低；现已支持图片输入 / 输出 token 专用价格，且在没有输出细分但模型是 `image_generation` 时，把 `output_tokens` 作为图片输出 token 结算。
- 自定义音频模型如果只配置音频输入 / 输出价格，现已能按 `audio_tokens` 或纯音频模型的总输入 / 输出 token 计算成本；按张图片价格现已能在已知 `output_image_count` / `output_images` / `image_count` 时计入成本拆解。
- 使用记录新增保存 `input_image_tokens` 和 `output_image_tokens`，避免详情页后续重算成本明细时丢失图片 token 拆分。
- 部分统计图表曾把 `cache_read_tokens` 再加到总 token 中；OpenAI 的 cached tokens 已包含在 input tokens 中，所以总 token 应为 `input_tokens + output_tokens`，缓存命中只作为拆分指标和成本折扣依据。
- 流式请求如果在可见输出后失败且上游没有返回 usage，网关会按请求体和已解析输出做轻量估算并写入 `usage_records`；首包前失败、只有 `response.created` / 心跳 / metadata 这类不可见输出的中断仍按 0 token / 0 cost 记录。
- 流式本地估算已补充大 JSON / base64 防误算和 Responses `output_item.done` 兜底：大请求已成功解析 JSON 时不再直接按 raw body 字节数除以 4 估算，避免把 data URL / 音频块按文本收费；空 `output_item.added` 不算可见输出；只有 `output_item.done` 或 `response.completed.output` 携带完整内容且没有前序 delta 时，才补算输出 token。
- 账户测试复用 `testOpenAIAccount()`，而 `testOpenAIAccount()` 会构造内部 `/v1/responses` 请求并调用 `handleOpenAIGatewayRequest()`，不会绕过使用记录。后台冷却复测固定启用，但只对冷却到期的 `temporary_unavailable` 做恢复性测试；`rate_limited` 等其他状态不主动复测、不做自愈恢复。账号质量主动探测代码已删除，避免后续在没有业务收益的情况下恢复上游测速请求。OpenAI OAuth 额度快照已改为被动读取真实网关响应头，不再通过 `testOpenAIAccount()` 主动刷新。
- 网关成功、上游 4xx/5xx、请求异常、流式首包前失败、流式中断、上游流式空响应体、客户端已发起上游后的取消，均会按实际上游尝试写入使用记录。
- 统计聚合的 `request_count` 以 `usage_records` 明细为事实源；失败无 usage 且无可见输出时按 0 token / 0 cost 纳入请求数和错误数，失败流已经产生可见输出时按使用记录里的估算 token / cost 聚合，避免漏掉真实消耗链路。
