# 请求处理分层设计

## 文档边界

本文只描述客户端请求进入本地网关后，到系统发起上游请求前的代码职责分层和维护边界。它不设计页面，但会定义账户受控请求覆盖的运行时落点；不描述上游返回后的响应处理。

以下内容不属于本文范围：

- 上游响应头复制、非流式响应转发和响应正文捕获。
- `200 + SSE` / `200 + JSON` 响应语义检查、事件丢弃 / 替换 / 客户端重试事件。
- 上游失败后的响应侧账号状态确认、流式失败副作用、usage 从响应中解析。
- 管理端策略配置页面和可视化页面。

后续如果新增“请求进入上游前”的处理能力，必须先判断它属于本文哪一层；如果找不到合适层级，先更新本文和架构总览，再写代码。

## 核心原则

- 请求处理是系统兼容能力，不是用户自定义脚本能力。请求头改写、正文归一化、模型映射、OAuth 会话、客户端兼容和上游 URL 选择都由系统代码维护；账户只允许现有 `service_tier_override` 和 `reasoning_effort_override` 两项固定覆盖，不开放通用 request policy 或任意 header/body patch。
- 请求侧和返回侧必须分离。请求侧只负责入口保护、鉴权授权、请求体元数据、候选账号、调度运行态、上游请求准备；返回侧负责响应转发、响应语义检查、usage 解析和响应后副作用。返回侧不能在失败后生成请求体变体或改写原始请求对象。
- 协议、供应商、客户端画像和账户运行态不能混写。`openai/v1` 是协议语义，`gpt`、`glm` 是供应商语义，Codex 和 Claude Code 是客户端 / 上游适配语义，账户承载凭据、代理、并发、运行状态和少量明确登记的供应商请求覆盖。
- 通用层只写通用规则，特化逻辑只能下沉。OpenAI 协议通用处理不能写 GPT / Codex、GLM 或 DeepSeek 专属判断；GPT / Codex 专属判断不能反向污染通用 OpenAI-compatible 账号，GLM 和 DeepSeek 的 Chat Completions 兼容差异也不能写进全局 OpenAI v1 协议层。
- 请求链路不能同步扫描统计明细、审计正文、usage shard 或日志文件；额度、授权、账号候选和设置必须来自运行时缓存、DB service 或后台预聚合结果。
- 服务等级和思考级别是不能被静默过滤的两类请求字段。API Key、OAuth、客户端画像、模型映射和 bridge 只需把对应供应商 wire 字段加入现有白名单或映射器，不新增捕获、重放或发送前校验机制。

## 请求处理流水线

```mermaid
flowchart LR
  Entry["入口挂载"] --> PreAuth["认证前运行态"]
  PreAuth --> Body["请求体保护与元数据"]
  Body --> Context["请求上下文"]
  Context --> Auth["授权与额度"]
  Auth --> Profile["协议 / 客户端画像"]
  Profile --> Compat["兼容策略"]
  Compat --> Candidate["候选账号筛选"]
  Candidate --> Runtime["调度运行态"]
  Runtime --> Dispatch["账号派发保护"]
  Dispatch --> Prepare["上游请求准备 / 协议改写"]
  Prepare --> Overrides["目标 provider driver 字段处理与两项覆盖"]
  Overrides --> Upstream["发起上游请求"]
```

这条链路的终点是发起上游请求。上游返回后的所有处理都从本文切出。

## 目录分层约定

`backend/src/modules/gateway/` 目录按运行职责和协议边界拆分，不再把通用网关能力统一命名为 `openai-gateway-*`：

| 目录 | 边界 |
| --- | --- |
| `request/` | 入口认证前运行态、请求体保护、本地校验和请求侧预检 |
| `dispatch/` | 候选账号筛选、派发准备、账号准备、并发保护和上游 attempt 调度 |
| `runtime/` | 进程内短 TTL 调度态、账号副作用队列、会话亲和、代理健康和 IP 级保护 |
| `upstream/` | 上游 HTTP 请求构造、上游响应体读取和上游错误诊断辅助 |
| `response/` | 下游响应渲染、失败响应、流式管道、响应最终化和响应检查执行 |
| `protocols/openai-v1/` | OpenAI v1 协议层路径、endpoint family、模型字段、SSE 事件和协议 usage 解析 |
| `protocols/anthropic-v1/` | Anthropic Messages 协议层路径、endpoint family、模型字段、SSE 事件、thinking / cache / tool_use 语义和 usage 解析 |
| `adapters/gpt-codex/` | GPT / Codex 上游 adapter、OAuth 归一化、Codex headers、GPT 服务等级 / 思考级别最终覆盖和 Codex usage 快照 |
| `providers/drivers/glm/` | 智谱 GLM 供应商局部兼容、通用 GLM API 与 GLM Coding Plan 的 Chat Completions 档案差异、GLM 专属字段白名单和测试默认值 |
| `providers/drivers/deepseek/` | DeepSeek 供应商局部兼容、OpenAI-compatible Chat Completions 档案差异、DeepSeek `user_id` 透传边界、thinking / reasoning / cache usage / keep-alive / beta 能力边界处理 |
| `providers/drivers/anthropic/` | 官方 Anthropic API Key 上游 driver、`x-api-key` 替换、`anthropic-version` / `anthropic-beta` 处理、官方直连诊断、Messages 上游请求准备，以及显式 OpenAI -> Anthropic bridge 的供应商启用点 |
| `providers/drivers/gemini/` | Gemini native 与 Gemini OpenAI Chat compatibility driver、`x-goog-api-key` 处理、Gemini endpoint family、Gemini CLI 画像和 usage 解析 |
| `client-profiles/` | Codex、Claude Code、Gemini CLI 等客户端画像和客户端重试策略 |
| `usage/`、`audit/`、`quota/`、`policy/`、`routing/` | 使用记录、审计捕获、额度快照、账户错误策略和策略路由分组调度等横切能力 |

只有确实表达 OpenAI v1 协议字段、Anthropic native 协议字段、OpenAI-compatible 透传、GPT/Codex OAuth adapter 或具体供应商 driver 时，文件才应放在 `protocols/openai-v1/`、`protocols/anthropic-v1/`、`adapters/gpt-codex/` 或 `providers/drivers/*`。通用请求、调度、运行态、响应和审计能力必须留在对应通用目录，避免后续新增 native 协议或其他供应商时误以为只能服务 OpenAI。

## 分层归属细则

### 全局网关层

- 系统账户请求次数限制位于 API Key 认证成功之后、候选账号筛选之前：运行时快照提供全局设置和用户覆盖，Node 热路径只做同步本地 Map 计数与最多四个窗口比较；Redis 仅由后台协调器批量同步，不能进入请求 await 链。
- 用户覆盖到期按 `usageStatsTimezone` 的本地日期判断，所选日期当天有效、次日继承全局；模型目录请求不计数，超限在账号调度前返回 `429 user_request_limit_exceeded` 并写丢弃请求审计。

全局网关层只处理所有协议入口都成立的系统保护和本地身份逻辑：

- 系统后台路径与客户端网关路径隔离。
- 请求体硬上限、lane 上限和在途 body 总量保护。
- Bearer Token 缺失 / 无效的本地错误。
- 来源 IP 封禁和认证前短 TTL 熔断。
- traceId、clientIp、请求终止和审计上下文初始化。
- `clientIp` 必须来自 Express `trust proxy` 后的 `req.ip` 或 socket 回退，不直接读取公网客户端自带的 `X-Forwarded-For` / `X-Real-IP`；部署层负责只信任 Caddy、edge 或隧道等可信反代。

这一层不应该知道 GPT、Codex、某个模型或某个上游账号的专属语义。

### OpenAI 协议层

OpenAI 协议层处理 `openai/v1` 共有语义：

- `/v1` 路径归一化。
- `/models` 本地模型列表响应。
- Codex `/models` 响应从独立模型能力字段读取默认 reasoning、支持级别、服务等级和多代理版本，不按统一模板伪造；OpenAI API wire reasoning 与 Codex `ultra` 分开建模。
- `/responses`、`/chat/completions`、`images` 等 endpoint family 和 request lane。
- `model`、`stream`、Responses `tools/tool_choice` 的轻量元数据。
- OpenAI-compatible API Key 账号的上游 URL 拼接、危险请求头过滤和 raw body 透传。

如果一个规则只对 OpenAI v1 成立，应落在 OpenAI 协议层；如果未来 Anthropic 或 Gemini 不能复用，就不能写进全局网关层。

### Anthropic 协议层

Anthropic 协议层处理 `anthropic/v1` 共有语义：

- `/v1/messages`、`/v1/messages/count_tokens` 和 `/v1/models` 的路径归一化。
- Anthropic Messages JSON / SSE 的输出文本、工具调用、thinking、cache、completion 和 error 事件抽取。
- `anthropic-version`、`anthropic-beta`、Messages 语义和本地 Anthropic Models API 形态。
- Anthropic Models API 形态和本地模型目录渲染。

如果一个规则只对 Anthropic Messages 成立，应落在 Anthropic 协议层；不能复用 OpenAI v1 的 `choices` / `response.*` 字段路径，也不能把第三方 Anthropic-compatible surface 直接提升为官方直连协议层。

`x-api-key` 或 `Authorization: Bearer` 的上游认证替换属于 `adapters/anthropic/` 的供应商账号类型分支，不属于协议层。协议层只知道 Anthropic Messages 怎么解析；当前已验证的是 API Key 和 Bearer Token 导入型 OAuth，未验证的仍是订阅网页登录、Setup Token、Cookie / sessionKey 等私有链路。

### 供应商层

供应商层表达账号池和上游能力归属，当前主要是 `openai` 通用供应商、`gpt` 子供应商、`glm` 供应商和 `deepseek` 供应商：

- `openai` 供应商承载通用 OpenAI-compatible API Key 透传。
- `gpt` 供应商继承 OpenAI v1 协议，并追加 GPT / ChatGPT / Codex 上游特化能力，以及受精确模型能力约束的服务等级和思考级别账户覆盖。
- `glm` 供应商包含通用 GLM OpenAI Chat、GLM Coding OpenAI Chat 和 GLM Coding Anthropic Messages 三个 `provider_protocol_profile_id`；OpenAI Chat 档案不声明 OpenAI Responses，也不继承 GPT / Codex 客户端策略。Codex / OpenAI Responses -> Chat bridge 由普通 GLM OpenAI v1 账户显式 `responses -> chat_completions` 模型别名声明；Anthropic Messages 或 Gemini native 等其他跨协议方向仍由混合供应商账户声明。GLM 的上游 Base URL 是 `/api/paas/v4`、`/api/coding/paas/v4` 和 `/api/anthropic`，URL 拼接必须落在 GLM / Anthropic provider driver / adapter 中，不能复用会给非 `/v1` 地址自动追加 `/v1` 的通用 OpenAI helper。
- `deepseek` 供应商包含 `profile_deepseek_openai_v1` 和 `profile_deepseek_anthropic_v1`；前者复用 OpenAI v1 Chat Completions，并在 DeepSeek 供应商层处理 `user_id` 透传边界、`thinking`、`reasoning_effort`、`reasoning_content`、cache usage、keep-alive 和 beta 能力边界；后者复用 Anthropic v1 Messages，面向 Claude Code / Anthropic SDK 兼容入口，使用 DeepSeek 独立账号池、默认分组、模型目录和 usage 归属，不和官方 Anthropic 档案混用。
- `anthropic` 供应商处理官方 Anthropic Claude Messages 语义，只能使用 `protocols/anthropic-v1/` 和 `adapters/anthropic/`；当前允许 API Key 与 Bearer Token 导入型 `oauth` 账号类型，但订阅网页登录、Setup Token、Cookie / sessionKey 等链路仍不纳入当前目标。
- 供应商专属能力必须通过 `provider_code`、`provider_protocol_profile_id` 或账户来源判断隔离。

供应商层可以决定上游能力差异，但不能绕过 API Key、分组、授权、模型限制和账号硬状态。

### 客户端画像层

客户端画像层只描述下游客户端期望，不是供应商，也不是账户类型：

- 普通 OpenAI-compatible 客户端默认是 `generic_openai`。
- `generic_openai`、`generic_anthropic`、`generic_gemini` 对上游状态、错误对象、错误码、错误类型、完成状态和正文保持不透明：完整 `2xx` 和普通 payload 原样转发；所有端点仅按布尔 `response.ok=false` 做内容无关的请求级 Key/账号接管，但不执行系统默认语义检查，也不据此写共享 Key/IP/质量/账户状态。副作用 POST 与普通文本共用未交付结果时的候选切换；已提交真实协议事件、正文或可见输出时结束或断流，不能把供应商原始错误当客户端重试指令。
- 候选切换机制可以复用，但 lane 策略必须隔离：普通路由快速模式和首字切换只适用于可安全重放的文本 lane；图像不记录该类慢样本，也不因文本墙钟或首字阈值自动跨账户重放，并继续使用独立首响应、空闲、未提交 attempt 生命周期超时与图像并发限制。
- 精确命中 `/responses` SSE 和 `x-codex-turn-metadata.turn_id` 时才进入 Codex profile。
- Codex turn 级避让、Codex 可重试语义和 Codex 请求体归一化必须留在客户端画像或对应上游 adapter 下。
- 普通 Anthropic native / Anthropic SDK 类客户端默认是 `generic_anthropic`。
- 显式命中 Anthropic Messages 协议和 `x-juhe-client-profile: claude_code`，或官方 Claude Code 多信号命中时，才进入 Claude Code profile。多信号至少包含 `claude-cli/` User-Agent、`anthropic-beta` 中的 `claude-code-*`、`x-claude-code-session-id` / `x-claude-code-agent-id`、`?beta=true` 中的两个，单个信号不升级画像。
- Claude Code profile 只表达下游客户端工具画像；当前不注入 Claude Code OAuth，不生成 Claude Code system prompt / tool schema / thinking body。上游请求准备层只在 `claude_code` 画像下按真实 CLI 抓包补齐缺失或非 Claude Code 的 `User-Agent`、缺失的 `anthropic-beta` 项和缺失的 `?beta=true`。
- 普通 Gemini native / Gemini SDK 类客户端默认是 `generic_gemini`。
- 显式命中 Gemini native 协议和 `x-juhe-client-profile: gemini_cli`，或 `GeminiCLI` / `proxy_client=geminicli` User-Agent 加 Gemini 本地认证信号命中时，才进入 Gemini CLI profile；`x-goog-api-client` 只是 SDK 信号，不能用于升级 CLI 画像。
- Gemini CLI profile 只表达下游客户端工具画像；默认专属响应策略只在该画像下按 Google canonical `error.status` 处理已知可重试错误，普通 Gemini 客户端不继承。
- 运行时策略还会派生 `requestClientCompatibility`：普通 OpenAI 请求为 `openai_standard`，Codex 请求为 `codex_responses`，普通 Anthropic 请求为 `anthropic_native`，Claude Code 请求为 `claude_code`。候选账号筛选和上游请求准备都读取该值，不能仅凭账号保存字段决定是否启用专属适配。

新增客户端 profile 时，必须先定义识别条件、作用端点、请求侧影响和返回侧影响；不能通过上游错误码或模型名临时推断。

### 账户运行层

账户运行层只处理命中具体候选账号后才知道的事情：

- 凭据读取和上游 Authorization 替换。
- OAuth access token 请求前刷新。
- 代理绑定和代理失败跳过。
- 账号当前并发、图像 lane 并发、半开探测租约。
- 账户支持模型和账户模型映射。
- AI 账户可选的 `service_tier_override`、`reasoning_effort_override`，只在模型映射与 endpoint family 已确定后参与最终请求准备。
- 账户选择器的运行时投影白名单必须保留 `service_tier_override`、`reasoning_effort_override`；两者和 API Key / OAuth 密钥字段继续分层处理，不能因补覆盖字段而放宽其他敏感凭据投影。
- 使用记录从客户端请求体提取 requested 服务档位 / 思考级别，并从模型映射、协议 bridge、OAuth 归一化和账户覆盖全部完成后的最终上游 JSON 提取 effective 事实；`/responses/compact` 等特化路径也不能静默删除已识别字段，无法可靠映射时返回该路径现有的明确 `400`。
- 当前 GPT 两项覆盖在统一目标中只泛化字段名称和值域，继续复用账户现有保存流程和配置版本，不增加独立请求策略字段、动态 control 或独立策略版本。

账户层不提供任意请求级处理配置。账户可以保存模型映射、支持模型、代理、错误处理规则、流式追加规则和已登记的服务等级 / 思考级别请求覆盖；配置值必须来自支持模型精确能力数组的并集。运行时由最终上游模型对应的 provider driver 逐字段判断，不支持或能力未知时保留客户端字段，不做向下降级；请求头补充、正文替换、上下文拼接和协议适配仍由系统 adapter 负责。

## 新增请求处理能力落点

| 新能力类型 | 应落层级 | 示例 | 备注 |
| --- | --- | --- | --- |
| 入口保护 | 全局网关层 | body 上限、认证前熔断 | 必须协议无关 |
| 新 OpenAI endpoint family | OpenAI 协议层 | 新增 `/v1/realtime` 识别 | 同步协议档案和模型能力 |
| 新供应商兼容差异 | 供应商层 | 某供应商要求固定 header；DeepSeek 要求保留 `user_id`、`thinking`、`reasoning_effort`、`reasoning_content`、keep-alive 和 cache usage 扩展字段 | 只能影响该供应商账号 |
| 新客户端兼容能力 | 客户端画像层 + 候选账号筛选层 | 某客户端要求特殊 request body | 必须有明确识别条件，并定义可承接账号能力 |
| Codex `previous_response_id` 状态恢复 | 客户端画像层 + 上游请求准备前的 bridge 状态层 | Chat-only bridge 根据 response id 恢复完整 Responses / Chat 历史，再转为 Chat messages | 只能在同 API Key、同分组、同供应商边界内恢复；找不到状态时受控失败，不进入上游派发 |
| Chat-only gateway summary compact | 候选账号筛选层 + 受控内部 Chat Completions 请求 | 在当前分组和当前供应商内通过 Chat Completions 摘要模型生成网关自有 compact snapshot | 内部摘要请求必须禁止递归 compact，不能跨分组、跨供应商或绕过统计审计，不能向 Chat 上游发送 `/responses/compact` |
| OpenAI -> Anthropic Messages bridge | 候选账号筛选层 + 共享 bridge 层 + Anthropic provider driver + 返回侧协议渲染 | OpenAI Chat / Responses JSON/SSE 在显式映射或目标模型命中时转为 Anthropic `/v1/messages`，再按下游 OpenAI 协议渲染 | 只覆盖设计文档列出的字段；账号真实 endpoint modes 仍是 `messages_json/messages_sse`；不支持字段必须受控拒绝或明确降级 |
| 模型路由 | 候选账号筛选层 | 请求 `model` 通过现有 `modelKey -> providerCode[]` 缓存唯一确定供应商后，筛当前路由策略绑定分组 | 零命中或多供应商命中时本地失败；协议档案和 endpoint mode 留在账户候选过滤，不在请求链路遍历供应商模型目录 |
| 新模型选择规则 | 候选账号筛选层 | endpoint family 与支持模型共同过滤 | 不在派发层临时跳过 |
| 普通路由速度优先重放安全门 | 调度运行态层 + 协议 endpoint family helper | 只为最终 `requestReplaySafeText = true` 的文本推理请求创建软首字 timer、慢样本和可选 cutover | 图片、音频、文件/资源、后台任务、hosted tool、其他副作用和未知重放语义端点不创建 timer、慢样本或 `latency_degraded`；该门禁不能跳过认证、授权、模型过滤、各 lane hard timeout 或响应检查 |
| lane timeout profile | 请求上下文层 + policy 层 + 上游读取层 | `text` 使用 `120/30/1800` 秒，`image` 使用 `600/120/3600` 秒；图片使用独立长时限，但切号准入与文本一致 | 图像 lane 不复用文本快速模式首字阈值；图片超时或断尾且下游未语义提交时继续 Key / 账户 / 分组，已写出只结束或断流；活跃且已提交语义的 SSE 不受未提交 attempt 寿命机械中断 |
| SSE 等待心跳与双提交 | 调度运行态层 + 返回侧 | 零可派发账号等待时发送 SSE 注释，标记传输提交但不标记语义提交；账号恢复后继续同一连接 | 不发送伪造模型事件；心跳后不能再返回 HTTP 状态；上游改为非流式时写协议可重试事件或断流，不能拼接 JSON |
| 新账号凭据处理 | 账户运行层 | token 临期刷新、会话标识隔离 | 必须命中账号后才发生 |
| 服务等级 / 思考级别账户覆盖 | 账户运行层 + 上游请求准备层 | `service_tier_override`、`reasoning_effort_override` | 先完成模型映射和 bridge，再由目标 provider driver 按模型能力逐字段应用；大 JSON 复用 worker；不支持或未知时保留客户端字段，仅 bridge 无法安全映射受保护字段时返回既有 `400` |
| 跨供应商服务等级 / 思考级别字段保护 | 上游请求准备层 + provider driver / bridge | `service_tier`、`speed`、`reasoning.effort`、`reasoning_effort`、`thinking`、`thinkingConfig`、`budget_tokens` | 目标契约见 [统一模型能力与计费抽象设计](统一模型能力与计费抽象设计.md)；`speed`、thinking budget 等首版只做字段保护，不增加账户控件；无法映射时显式拒绝 |
| 新响应事件处理 | 返回侧文档 | SSE 事件替换、usage 解析 | 不写入本文请求层 |

## 禁止扩散的实现

- 禁止把 GPT / Codex 专属 header、body、错误码和 session 逻辑写入通用 OpenAI API Key 透传路径。
- 禁止把官方 Anthropic Messages、`anthropic-version`、`anthropic-beta`、`x-api-key` 或 SSE 事件解析写入 OpenAI v1 适配器。
- 禁止把尚未真实验证的 Anthropic OAuth Bearer token、Claude Code OAuth 伪装 header 或 token 刷新逻辑写进 Anthropic API Key 账户路径；本地 `x-juhe-client-profile` 画像声明只能用于网关识别并必须过滤出上游请求，官方 Claude Code 多信号只能作为客户端画像识别输入，不能改变上游认证方式。
- 禁止把 GLM 的 Chat Completions 字段兼容、Coding Plan base URL 或套餐语义写入 GPT、通用 OpenAI-compatible 或全局 OpenAI v1 路径。
- DeepSeek Anthropic-compatible Messages 只能存在于已声明的 DeepSeek Anthropic profile 和对应 driver，不能写进 DeepSeek OpenAI profile或全局 OpenAI v1；同理，`user_id`、thinking 参数和 beta base URL 只能落在相应供应商 / profile 层，不能跨 profile 注入。
- 禁止在失败后静默改写请求 body/header 重新派发；需要协议转换时必须发生在明确的供应商 adapter 或客户端 bridge 边界内。
- 只有实际会重建对应供应商请求体的 OAuth normalizer、客户端画像、模型映射或 bridge，才把该供应商的 tier、speed、reasoning、thinking、budget 字段加入现有白名单或映射器；同协议保留，跨协议无法映射时返回目标路径现有的 `400` 请求错误，不能静默删除。
- 禁止把响应侧的 `SSE` 事件、响应语义检查或 usage 解析写进请求 preflight。
- 禁止在 `generic_*` 客户端路径读取具体上游状态码、错误对象或正文语义来决定共享状态、质量、响应改写或动作类型。所有端点只允许使用布尔 `response.ok` 进入内容无关的 opaque 请求级 Key/账号切换；精确客户端画像才能额外解释其声明的协议结构，用户显式策略才能按配置执行语义副作用。显式策略只控制状态动作，不建立第二套切号准入。
- 禁止在账户 credentials 中新增“任意请求处理脚本 / 任意 header 改写 / 任意 body patch”。
- 禁止为了某个页面或临时排障，把请求链路中间结果写成长期业务字段。
- 禁止在请求链路扫描 `usage_records`、usage shard、审计表、运行日志或统计缓存桶做实时汇总。
- 禁止在 server 角色回退同步 SQLite repository；缓存 miss 只能走 DB service 或已有运行时缓存加载通道。
