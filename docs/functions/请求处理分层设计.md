# 请求处理分层设计

## 文档边界

本文只描述客户端请求进入本地网关后，到系统发起上游请求前的代码职责分层和维护边界。它不设计页面，不开放用户配置，也不描述上游返回后的响应处理。

以下内容不属于本文范围：

- 上游响应头复制、非流式响应转发和响应正文捕获。
- `200 + SSE` 流式事件解析、流式拦截策略、事件丢弃 / 替换 / 客户端重试事件。
- 上游失败后的响应侧账号状态确认、流式失败副作用、usage 从响应中解析。
- 管理端策略配置页面和可视化页面。

后续如果新增“请求进入上游前”的处理能力，必须先判断它属于本文哪一层；如果找不到合适层级，先更新本文和架构总览，再写代码。

## 核心原则

- 请求处理是系统兼容能力，不是用户自定义能力。请求头改写、正文归一化、模型映射、OAuth 会话、Codex 兼容和上游 URL 选择都由系统代码维护，不开放为账户级任意请求处理配置。
- 请求侧和返回侧必须分离。请求侧只负责入口保护、鉴权授权、请求体元数据、候选账号、调度运行态、上游请求准备；返回侧负责响应转发、流式拦截、usage 解析和响应后副作用。上游失败触发的请求体恢复属于跨边界兼容策略：错误信号来自返回侧，策略动作只生成下一次 attempt 的受控请求变体，不改写原始请求对象。
- 协议、供应商、客户端画像和账户运行态不能混写。`openai/v1` 是协议语义，`gpt`、`glm` 是供应商语义，Codex 是客户端 / 上游适配语义，账户只承载凭据、代理、并发和运行状态。
- 通用层只写通用规则，特化逻辑只能下沉。OpenAI 协议通用处理不能写 GPT / Codex 或 GLM 专属判断；GPT / Codex 专属判断不能反向污染通用 OpenAI-compatible 账号，GLM 的 Chat Completions 兼容差异也不能写进全局 OpenAI v1 协议层。
- 请求链路不能同步扫描统计明细、审计正文、usage shard 或日志文件；额度、授权、账号候选和设置必须来自运行时缓存、DB service 或后台预聚合结果。

## 请求处理流水线

```mermaid
flowchart LR
  Entry["入口挂载"] --> PreAuth["认证前运行态"]
  PreAuth --> Body["请求体保护与元数据"]
  Body --> Context["请求上下文"]
  Context --> Auth["授权与额度"]
  Auth --> Profile["协议 / 客户端画像"]
  Profile --> Compat["兼容策略"]
  Compat --> Candidate["候选账号筛选"]
  Candidate --> Runtime["调度运行态"]
  Runtime --> Dispatch["账号派发保护"]
  Dispatch --> Prepare["上游请求准备"]
  Prepare --> Upstream["发起上游请求"]
```

这条链路的终点是发起上游请求。上游返回后的所有处理都从本文切出。

## 目录分层约定

`backend/src/modules/gateway/` 目录按运行职责和协议边界拆分，不再把通用网关能力统一命名为 `openai-gateway-*`：

| 目录 | 边界 |
| --- | --- |
| `request/` | 入口认证前运行态、请求体保护、本地校验、请求恢复和请求侧预检 |
| `dispatch/` | 候选账号筛选、派发准备、账号准备、并发保护和上游 attempt 调度 |
| `runtime/` | 进程内短 TTL 调度态、账号副作用队列、会话亲和、代理健康和 IP 级保护 |
| `upstream/` | 上游 HTTP 请求构造、上游响应体读取和上游错误诊断辅助 |
| `response/` | 下游响应渲染、失败响应、流式管道、响应最终化和响应检查执行 |
| `protocols/openai-v1/` | OpenAI v1 协议层路径、endpoint family、模型字段、SSE 事件和协议 usage 解析 |
| `protocols/anthropic-v1/` | Anthropic Messages 协议层路径、endpoint family、模型字段、SSE 事件、thinking / cache / tool_use 语义和 usage 解析 |
| `adapters/gpt-codex/` | GPT / Codex 上游 adapter、OAuth 归一化、Codex headers 和 Codex usage 快照 |
| `adapters/glm/` | 智谱 GLM 供应商局部兼容、通用 GLM API 与 GLM Coding Plan 的 Chat Completions 档案差异、GLM 专属字段白名单和测试默认值 |
| `adapters/deepseek/` | DeepSeek 供应商局部兼容、OpenAI-compatible Chat Completions 档案差异、Anthropic-compatible Messages 档案准备和 DeepSeek 专属字段处理 |
| `adapters/anthropic/` | 官方 Anthropic API Key / OAuth 上游 adapter、`x-api-key` 或 `Authorization: Bearer` 替换、OAuth token 准备、`anthropic-version` / `anthropic-beta` 处理、官方直连诊断和 Messages 上游请求准备 |
| `client-profiles/` | Codex 等客户端画像、客户端重试策略和兼容恢复策略 |
| `usage/`、`audit/`、`quota/`、`policy/`、`routing/` | 使用记录、审计捕获、额度快照、账户错误策略和 API Key 分组路由等横切能力 |

只有确实表达 OpenAI v1 协议字段、Anthropic native 协议字段、OpenAI-compatible 透传或 GPT/Codex、GLM、DeepSeek、Anthropic 上游适配时，文件才应放在 `protocols/openai-v1/`、`protocols/anthropic-v1/`、`adapters/gpt-codex/`、`adapters/glm/`、`adapters/deepseek/` 或 `adapters/anthropic/`。通用请求、调度、运行态、响应和审计能力必须留在对应通用目录，避免后续新增 native 协议或其他供应商时误以为只能服务 OpenAI。

## 分层归属细则

### 全局网关层

全局网关层只处理所有协议入口都成立的系统保护和本地身份逻辑：

- 系统后台路径与客户端网关路径隔离。
- 请求体硬上限、lane 上限和在途 body 总量保护。
- Bearer Token 缺失 / 无效的本地错误。
- 来源 IP 封禁和认证前短 TTL 熔断。
- traceId、clientIp、请求终止和审计上下文初始化。

这一层不应该知道 GPT、Codex、某个模型或某个上游账号的专属语义。

### OpenAI 协议层

OpenAI 协议层处理 `openai/v1` 共有语义：

- `/v1` 路径归一化。
- `/models` 本地模型列表响应。
- `/responses`、`/chat/completions`、`images` 等 endpoint family 和 request lane。
- `model`、`stream`、Responses `tools/tool_choice` 的轻量元数据。
- OpenAI-compatible API Key 账号的上游 URL 拼接、危险请求头过滤和 raw body 透传。

如果一个规则只对 OpenAI v1 成立，应落在 OpenAI 协议层；如果未来 Anthropic 或 Gemini 不能复用，就不能写进全局网关层。

### Anthropic 协议层

Anthropic 协议层处理 `anthropic/v1` 共有语义：

- `/v1/messages`、`/v1/messages/count_tokens` 和 `/v1/models` 的路径归一化。
- Anthropic Messages JSON / SSE 的输出文本、工具调用、thinking、cache、completion 和 error 事件抽取。
- `anthropic-version`、`anthropic-beta`、Messages 语义和本地 Anthropic Models API 形态。
- Anthropic Models API 形态和本地模型目录渲染。

如果一个规则只对 Anthropic Messages 成立，应落在 Anthropic 协议层；不能复用 OpenAI v1 的 `choices` / `response.*` 字段路径，也不能把第三方 Anthropic-compatible surface 直接提升为官方直连协议层。

`x-api-key`、`Authorization: Bearer <access_token>`、OAuth token 刷新和 OAuth 必要 beta/header 合并属于 `adapters/anthropic/` 的供应商账号类型分支，不属于协议层。协议层只知道 Anthropic Messages 怎么解析，不能假设所有 Anthropic 请求都使用 API Key 或 OAuth。

### 供应商层

供应商层表达账号池和上游能力归属，当前主要是 `openai` 通用供应商、`gpt` 子供应商、目标 `glm` 供应商和目标 `deepseek` 供应商：

- `openai` 供应商承载通用 OpenAI-compatible API Key 透传。
- `gpt` 供应商继承 OpenAI v1 协议，并追加 GPT / ChatGPT / Codex 上游特化能力。
- `glm` 供应商继承 OpenAI v1 Chat Completions 语义，分为通用 GLM API 和 GLM Coding Plan 两个 `provider_protocol_profile_id`；第一阶段不声明 OpenAI Responses，也不继承 GPT / Codex 客户端策略。
- `deepseek` 供应商分为 OpenAI-compatible 和 Anthropic-compatible 两个 `provider_protocol_profile_id`；OpenAI 面可复用 OpenAI v1 Chat Completions，Anthropic 面必须新增 Anthropic Messages adapter 后再开放。
- `anthropic` 供应商处理官方 Anthropic Claude Messages 语义，只能使用 `protocols/anthropic-v1/` 和 `adapters/anthropic/`；同一档案下允许 API Key 与 OAuth 两种账号类型，但上游认证和 token 生命周期必须分支处理；它不和 `deepseek` 的 Anthropic-compatible surface 共用账号池、价格目录或错误策略。
- 供应商专属能力必须通过 `provider_code`、`provider_protocol_profile_id` 或账户来源判断隔离。

供应商层可以决定上游能力差异，但不能绕过 API Key、分组、授权、模型限制和账号硬状态。

### 客户端画像层

客户端画像层只描述下游客户端期望，不是供应商，也不是账户类型：

- 普通 OpenAI-compatible 客户端默认是 `generic_openai`。
- 精确命中 `/responses` SSE 和 `x-codex-turn-metadata.turn_id` 时才进入 Codex profile。
- Codex turn 级避让、Codex 可重试语义和 Codex 请求体归一化必须留在客户端画像或对应上游 adapter 下。

新增客户端 profile 时，必须先定义识别条件、作用端点、请求侧影响和返回侧影响；不能通过上游错误码或模型名临时推断。

### 兼容策略与请求恢复层

兼容策略层处理“首轮原样转发后，上游明确返回协议兼容失败，是否需要构造下一次 attempt 的受控请求变体”。

- 策略输入包含客户端画像、供应商 / 账号能力、请求特征、上游错误信号和当前 attempt 状态。
- 策略输出只能是继续默认失败流程，或使用受控 body/header 变体重试一次。
- body/header transform 只执行策略给出的 patch，不自行判断 `Codex`、供应商、模型或错误码。
- 请求恢复不改变原始 `req.rawBody`，不影响审计中的原始请求边界；恢复 attempt 应记录清洗摘要。
- 请求恢复不是账号健康判断，不直接写账号状态，也不替代账户错误处理策略。

具体设计见 [网关兼容策略与请求恢复设计](网关兼容策略与请求恢复设计.md)。

### 账户运行层

账户运行层只处理命中具体候选账号后才知道的事情：

- 凭据读取和上游 Authorization 替换。
- OAuth access token 请求前刷新。
- 代理绑定和代理失败跳过。
- 账号当前并发、图像 lane 并发、半开探测租约。
- 账户支持模型和账户模型映射。

账户层不提供任意请求级处理配置。账户可以保存模型映射、支持模型、代理、错误处理规则和流式追加规则这类受控字段，但请求头补充、正文替换、上下文拼接和协议适配必须由系统 adapter 负责。

## 新增请求处理能力落点

| 新能力类型 | 应落层级 | 示例 | 备注 |
| --- | --- | --- | --- |
| 入口保护 | 全局网关层 | body 上限、认证前熔断 | 必须协议无关 |
| 新 OpenAI endpoint family | OpenAI 协议层 | 新增 `/v1/realtime` 识别 | 同步协议档案和模型能力 |
| 新供应商兼容差异 | 供应商层 | 某供应商要求固定 header；DeepSeek Anthropic 面要求 `x-api-key` 和 Anthropic Messages 路径 | 只能影响该供应商账号 |
| 新客户端兼容模式 | 客户端画像层 | 某客户端要求特殊 request body | 必须有明确识别条件 |
| 上游兼容失败后的请求恢复 | 兼容策略与请求恢复层 | `encrypted_reasoning` 被上游拒绝后清洗 body 重试一次 | 首轮保持 raw passthrough；只由明确错误信号触发 |
| 模型路由 | 候选账号筛选层 | 请求 `model` 解析到目标 `provider_protocol_profile_id` 后筛 API Key 绑定分组 | 必须读取已构建索引，不在请求链路遍历供应商模型目录 |
| 新模型选择规则 | 候选账号筛选层 | endpoint family 与支持模型共同过滤 | 不在派发层临时跳过 |
| 新账号凭据处理 | 账户运行层 | token 临期刷新、会话标识隔离 | 必须命中账号后才发生 |
| 新响应事件处理 | 返回侧文档 | SSE 事件替换、usage 解析 | 不写入本文请求层 |

## 禁止扩散的实现

- 禁止把 GPT / Codex 专属 header、body、错误码和 session 逻辑写入通用 OpenAI API Key 透传路径。
- 禁止把官方 Anthropic Messages、`anthropic-version`、`anthropic-beta`、`x-api-key`、OAuth Bearer token 或 SSE 事件解析写入 OpenAI v1 适配器。
- 禁止把 Anthropic OAuth 必要 beta、Claude Code header 或 token 刷新逻辑写进 Anthropic API Key 账户路径。
- 禁止把 GLM 的 Chat Completions 字段兼容、Coding Plan base URL 或套餐语义写入 GPT、通用 OpenAI-compatible 或全局 OpenAI v1 路径。
- 禁止把 DeepSeek 的 Anthropic-compatible Messages 请求、`x-api-key` 头、Anthropic 版本头或 Messages SSE 解析写进 OpenAI v1 适配器；DeepSeek OpenAI 面的局部差异也只能落在供应商层。
- 禁止把请求恢复策略硬编码到主调度循环、账户错误处理策略或供应商 URL 判断中；必须通过兼容策略层输出动作。
- 禁止把响应侧的 `SSE` 事件、流式拦截或 usage 解析写进请求 preflight。
- 禁止在账户 credentials 中新增“任意请求处理脚本 / 任意 header 改写 / 任意 body patch”。
- 禁止为了某个页面或临时排障，把请求链路中间结果写成长期业务字段。
- 禁止在请求链路扫描 `usage_records`、usage shard、审计表、运行日志或统计缓存桶做实时汇总。
- 禁止在 server 角色回退同步 SQLite repository；缓存 miss 只能走 DB service 或已有运行时缓存加载通道。
