# 协议桥接框架设计

> 面向 AI 和维护者。
> 本文定义 OpenAI、Anthropic、Gemini native 以及后续独立协议之间的长期桥接框架。具体供应商账号接入仍看各自账号文档；模型映射 UI 和保存校验看 [自定义模型与模型映射设计](自定义模型与模型映射设计.md)。

## 1. 背景

当前已经存在多个协议桥接方向：

- OpenAI Responses 到 OpenAI Chat Completions。
- OpenAI Responses 到真实 OpenAI Responses 上游原生直连。
- OpenAI Chat / Responses 到 Anthropic Messages。
- Anthropic Messages 到 OpenAI Chat Completions。
- Gemini native GenerateContent / StreamGenerateContent 到 OpenAI Chat Completions。
- Gemini native GenerateContent / StreamGenerateContent 到 Anthropic Messages。

如果后续每接入一个独立协议，都按“新协议到已有协议逐个写一遍、已有协议再到新协议逐个写一遍”的方式推进，协议数量从 3 个增长到 6 个时，点对点桥接数量会快速变成维护灾难。长期方案必须把协议转换抽成框架，而不是把转换逻辑散落在各个 provider driver 里。

## 2. 目标

- 新增一个独立协议时，只需要实现该协议的入站解析、出站渲染、上游请求构造、上游响应解析和能力声明。
- 协议互转默认走统一中间表示，而不是每两个协议之间都写一套私有转换。
- 模型映射只表达 `sourceModel + sourceEndpointFamily -> upstreamModel + upstreamEndpointFamily`，不承载转换细节。
- 前端、后端、导入、账号测试和 mockai 使用同一份协议互转矩阵，避免 UI 允许但后端拒绝，或后端允许但运行时不可用。
- 上游不支持的能力优先走 guidance-first，不静默丢字段，不伪造成成功；只有协议不合法、状态链损坏、权限越界或无法安全转换时才返回本地错误。

## 3. 非目标

- 不把所有协议强行伪造成 OpenAI Responses。Responses 有状态、工具、compact、previous response 和 hosted tools 语义，不能作为所有协议的默认中间层。
- 不做无模型映射的自动跨协议猜测。模型名、客户端画像或供应商名称都不能替代显式模型映射。
- 不为旧数据、旧字段或历史档案保留运行时兼容分支。
- 不把不可保真的能力静默删除后继续上游请求。

## 4. 分层模型

协议桥接框架分为五层：

| 层级 | 职责 | 代码归属建议 |
| --- | --- | --- |
| 协议识别层 | 从路径、方法、请求体和 header 中识别 source endpoint family、模型、流式形态和客户端画像 | `protocols/*` |
| 中间表示层 | 把不同协议的生成请求和响应事件抽象成统一语义帧 | `drivers/_shared/protocol-bridge/*` |
| 能力矩阵层 | 判断源协议能力、目标协议能力、目标模型能力和本地运行时能力是否能保真 | `storage/account-model-mapping-protocol-matrix.ts` 与共享能力定义 |
| 上游适配层 | 把中间表示渲染为目标上游协议请求，并把目标上游响应解析回统一事件 | `ProviderDriver` 内按协议 profile 接入 |
| 下游渲染层 | 把统一事件渲染回客户端原协议 JSON / SSE / error shape | 协议 bridge renderer |

Provider driver 负责账号认证、Base URL、endpoint mode、模型映射命中和上游请求发送；协议 bridge 负责请求 / 响应语义转换。二者不能互相吞职责。

## 5. 统一中间表示

第一阶段只抽生成类请求，不把 files、batch、live、embeddings 混入同一个中间表示。

```ts
type BridgeEndpointFamily =
  | 'chat_completions'
  | 'responses'
  | 'messages'
  | 'generate_content'
  | 'stream_generate_content'

type CanonicalGenerateRequest = {
  sourceFamily: BridgeEndpointFamily
  targetFamily: BridgeEndpointFamily
  sourceModel: string
  upstreamModel: string
  stream: boolean
  system: CanonicalContentBlock[]
  turns: CanonicalTurn[]
  tools: CanonicalTool[]
  toolChoice: CanonicalToolChoice
  responseFormat: CanonicalResponseFormat
  sampling: CanonicalSampling
  reasoning: CanonicalReasoningRequest
  unsupported: CanonicalUnsupportedCapability[]
  metadata: Record<string, unknown>
}
```

响应侧使用事件流，而不是一次性对象：

```ts
type CanonicalGenerateEvent =
  | { type: 'message_start'; id: string; model: string }
  | { type: 'text_delta'; text: string; index: number }
  | { type: 'tool_call_delta'; callId: string; name?: string; inputDelta?: string }
  | { type: 'tool_call_done'; callId: string; name: string; input: unknown }
  | { type: 'reasoning_delta'; text: string }
  | { type: 'usage'; inputTokens?: number; outputTokens?: number; cacheReadTokens?: number; cacheWriteTokens?: number }
  | { type: 'message_stop'; stopReason: string }
  | { type: 'guidance'; message: string; details?: unknown }
  | { type: 'error'; status: number; code: string; message: string }
```

每个协议 adapter 只需要实现：

- `fromDownstreamRequest()`：下游请求转中间表示。
- `toUpstreamRequest()`：中间表示转目标上游请求。
- `fromUpstreamResponse()`：目标上游响应转事件流。
- `toDownstreamResponse()`：事件流渲染回下游协议。
- `renderGuidance()`：按下游协议返回 guidance-first。
- `renderError()`：按下游协议返回本地错误。

## 6. 能力矩阵

每个桥接方向必须先声明能力，不允许边写边猜。

| 能力 | OpenAI Chat | OpenAI Responses | Anthropic Messages | Gemini native GenerateContent | 处理原则 |
| --- | --- | --- | --- | --- | --- |
| 文本输入输出 | 支持 | 支持 | 支持 | 支持 | 必须保真 |
| SSE 流式文本 | 支持 | 支持 | 支持 | 支持 | 必须保真到下游协议事件 |
| 图片输入 | 支持范围内 | 支持范围内 | 支持范围内 | 支持范围内 | URL / base64 / file reference 按目标协议能力转换，不支持则 guidance |
| 函数工具 | 支持 | 支持 | 支持 | 支持 | tool name、arguments、tool result 必须保真 |
| JSON object / schema | 支持范围内 | 支持范围内 | 支持范围内 | 支持范围内 | 目标协议可表达时转换，否则 guidance |
| 音频输入 / 输出 | 支持范围内 | 支持范围内 | 异构 | 支持范围内 | 目标协议不能承载时 guidance，不伪造成文本或空结果 |
| reasoning / thinking | 异构 | 支持范围内 | 支持范围内 | 异构 | 不强行伪造；可表达才映射 |
| prompt cache / cache_control | 异构 | 异构 | 支持范围内 | cachedContent 异构 | 不跨协议伪造缓存命中 |
| hosted tools / server tools | 协议差异大 | 协议差异大 | 协议差异大 | 协议差异大 | 本地运行时可承接才执行，否则 guidance |
| context / compact / previous response | Responses 专属 | 支持 | 不同构 | 不同构 | 不能强行合成 |
| safety settings | 不同构 | 不同构 | 不同构 | Gemini 原生 | 不静默丢弃；目标不支持则 guidance |

能力判断结果只有四类：

- `passthrough`：原生同协议或目标协议天然支持。
- `bridge`：可通过中间表示保真转换。
- `guidance`：上游不支持或不可保真，但请求本身不是非法。
- `reject`：请求无法安全解析、协议状态非法、映射非法或目标账号不具备 endpoint mode。

`guidance` 与 `reject` 的边界必须稳定：

- 配置期非法矩阵必须 `reject`，例如 `chat_completions -> responses`、`messages -> responses`、`generate_content -> responses`，不能在运行时伪装成可用。
- 请求体不是合法 JSON、必填字段缺失、工具历史破损、跨 API Key 状态链、未知本地状态、权限越界、文件引用不可解析或安全策略命中时必须 `reject`。
- 请求本身合法，但目标上游协议不能保真承载某个能力时必须 `guidance`，例如目标不支持 hosted tool、server tool、thinking、cache、非目标协议的状态链、JSON schema 与工具组合、目标协议无等价 include / logprobs / audio / 多候选等能力。
- `guidance` 必须按下游协议渲染为客户端可消费的 JSON / SSE 成功响应，并明确告诉 agent 后续应切换支持能力的上游、移除该能力、或配置本地 MCP / runtime；正文应包含稳定能力代码，便于客户端、日志和 mockai 断言定位；不能返回裸 400 导致客户端会话直接中断。
- 运行时 `guidance` 默认是账号 / 目标协议作用域，不是全局请求终止。调度器必须先跳过当前账号并继续尝试同分组后续账号和 API Key 后续可承接分组；只有所有候选都无法承载时，才把最后的 guidance 按下游协议返回给客户端。
- 只有请求本身与具体目标账号无关地非法或不安全时，才允许全局 `reject` 或全局 guidance，例如坏 JSON、跨 API Key 状态链、权限越界、无法解释的工具历史或安全策略命中。目标协议能力缺口不能写成全局终止，也不能写入账号健康状态。

## 7. 当前互转策略

| 下游来源 | 上游目标 | 策略 |
| --- | --- | --- |
| OpenAI Chat | OpenAI Chat | 同协议直连或模型改写 |
| OpenAI Responses | OpenAI Responses | 仅真实 Responses 原生 |
| OpenAI Responses | OpenAI Chat | 已落地桥接 |
| OpenAI Chat | OpenAI Responses | 禁止；不能合成 Responses 服务端状态 |
| OpenAI Chat / Responses | Anthropic Messages | 已落地桥接 |
| Anthropic Messages | OpenAI Chat | 已落地桥接 |
| Gemini native GenerateContent / StreamGenerateContent | OpenAI Chat | 已落地桥接 |
| Gemini native GenerateContent / StreamGenerateContent | Anthropic Messages | 已落地桥接 |
| OpenAI Chat / Responses | Gemini native GenerateContent | PLAN-0069 落地，右侧 `generate_content` 动态选择 JSON / SSE |
| Anthropic Messages | Gemini native GenerateContent | PLAN-0069 落地，右侧 `generate_content` 动态选择 JSON / SSE |

继续禁止：

- `messages -> responses`。
- `chat_completions -> responses`。
- `generate_content|stream_generate_content -> responses`。
- `count_tokens`、`embed_content`、files、cached contents、batch、live 参与生成类桥接。
- 未配置账号模型映射的自动跨协议转换。

`responses -> chat_completions` 当前使用上游 Chat SSE 作为桥接载体：下游 `stream:true` 时渲染回 Responses SSE；下游非流式请求必须聚合为 Responses JSON，不能把 Chat SSE 原样返回给 Responses 客户端。

## 8. Gemini native 作为右侧目标

Gemini native 目标只开放 `upstreamEndpointFamily = generate_content`。它代表“Gemini 生成类上游”，不是固定非流式端点。

- 下游非流式请求命中 `generate_content` 目标时，上游调用 `:generateContent`。
- 下游流式请求命中 `generate_content` 目标时，上游调用 `:streamGenerateContent?alt=sse`。
- UI 不单独提供右侧 `stream_generate_content`，避免用户为同一模型维护两条映射。
- 上游账号必须是 `profile_gemini_native_v1beta`，且真实 endpoint modes 必须包含对应 JSON 或 SSE 能力。

本方向支持：

- `chat_completions -> generate_content`。
- `responses -> generate_content`。
- `messages -> generate_content`。

本方向不承诺 Gemini 原生独有能力反向完整表达给 OpenAI / Anthropic 客户端。下游协议能表达的文本、图片、函数工具、JSON 输出、usage 和 finish reason 必须尽量保真；不能保真的 safety settings、cachedContent、Gemini 原生搜索 / 代码执行等只在 Gemini native 下游侧原生可用，不从 OpenAI / Anthropic 请求中伪造。

## 9. 模型映射与 UI 约束

前端和后端必须共用同一矩阵语义：

- 右侧 `responses` 只允许 `responses -> responses` 原生直连，账号必须真实支持 Responses endpoint mode；任何非 Responses 来源都不能桥接到 Responses。
- 右侧 `messages` 只允许 Anthropic 协议档案账号。
- 右侧 `generate_content` 只允许 Gemini native 协议档案账号。
- `profile_gemini_openai_chat_v1beta` 是 OpenAI Chat compatibility 档案，右侧仍是 `chat_completions`，不是 `generate_content`。
- 选择右侧 `generate_content` 时，右侧模型池来自 Gemini 供应商模型目录；左侧模型池按 source family 分别来自 OpenAI、Anthropic 或 Gemini 客户端模型池。

保存、导入、测试任务和运行时调度必须复用后端矩阵校验；前端只负责减少误选，不作为唯一安全边界。

## 10. 测试策略

所有桥接先用 mockai 全量回归，再做真实账户代表抽样。

mockai 必须覆盖：

- 协议矩阵：所有允许方向可保存、可运行；所有禁止方向保存失败或运行前受控拒绝。
- JSON / SSE：每个允许方向都覆盖非流式和流式。
- 文本：普通多轮输入输出。
- 工具：工具声明、工具调用、工具结果、流式工具参数增量。
- 图片：base64、URL 或 file reference 的可表达子集。
- JSON 输出：JSON object、schema 或目标协议等价能力。
- reasoning / thinking：可表达时转换，不可表达时 guidance。
- 目标不支持能力 guidance：至少覆盖 hosted/server tool、strict JSON schema + 用户工具、include / logprobs、多候选、音频输入 / 输出、请求级控制、状态控制和本地 runtime 未配置。
- cache / compact / previous response：不能保真时 guidance 或受控拒绝。
- usage：输入、输出、cache token 字段映射。
- 错误：上游非 2xx、坏 SSE chunk、空候选、无可用账号、endpoint mode 不匹配。

复杂协议矩阵的固定回归入口是：

```powershell
pnpm --filter juhe-ai-backend test:protocol-cross-matrix-mock-ai
```

该命令用于横向验证 OpenAI Chat / Responses、Anthropic Messages、Gemini native 三类生成协议的允许方向、禁止 Responses 目标方向、JSON / SSE、图片、函数工具、工具结果、JSON schema / response schema、usage，以及不可保真组合的 guidance-first 行为。它不能替代各桥接专项 mock，但每次新增独立协议、调整协议矩阵或修改共享桥接层后都必须运行。

真实账户只做抽样验证：

- 每个协议目标至少一条 JSON 成功路径。
- 每个协议目标至少一条 SSE 成功路径。
- 工具和图片按模型真实能力抽样。
- 真实账户错误、额度、模型不可用只记录结论，不替代 mockai 验收。

## 11. 后续接入新协议的模板

新增独立协议时，必须按下面顺序推进：

1. 新增协议档案、endpoint family 和 endpoint mode。
2. 定义该协议到中间表示的入站 adapter。
3. 定义中间表示到该协议的出站 adapter。
4. 声明协议能力矩阵和 guidance 边界。
5. 更新模型映射矩阵，前后端共用同一规则。
6. 增加 mockai 供应商，覆盖新协议作为下游来源和上游目标的正反方向。
7. mockai 全通过后再做真实账户抽样。

这个模板是后续接入 Kimi、Qwen、Vertex AI、Claude 新 surface 或其他独立协议的默认入口。任何新增点对点桥接都必须解释为什么不能复用中间表示。
