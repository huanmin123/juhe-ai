# 客户端稳定性竞品对比

## 文档目标

本文用于固定 `juhe-ai` 和 Sub2API、CLIProxyAPI、New API 的定位差异，重点回答一个问题：如果目标是让 Codex、OpenAI SDK、Cherry Studio、NextChat 等客户端长期固定一个入口并尽量稳定不断，`juhe-ai` 的优势在哪里。

本文不是功能数量清单，也不用于贬低其他项目。Sub2API、CLIProxyAPI 和 New API 都有更宽的生态能力；`juhe-ai` 当前的核心取舍是把 GPT 账号池后面的波动吸收在 OpenAI-compatible 网关和后台里，让前面的客户端尽量少改配置、少断流、少遇到误伤账号导致的可用池缩小。

## 总体结论

`juhe-ai` 的优势不是“供应商最多”“协议转换最多”或“商业化组件最完整”，而是：

> 客户端固定连接一个本地 `/v1` 入口，后端用账号池调度、异常兜底、流式保护、后台恢复和审计追踪吸收上游波动，尽量保证客户端稳定不断。

换句话说，`juhe-ai` 更像一个面向个人、小团队和工作室的 GPT 账号稳定层。用户只把本地 API Key 发给客户端，上游 OpenAI OAuth Token、OpenAI-compatible API Key、代理、分组、授权、账户错误处理策略和恢复动作都留在后台处理。

## 稳定机制优势

### 1. 客户端入口稳定

客户端只需要配置本服务根地址或 `/v1` 地址，并使用本地 API Key。后端负责根据 API Key 找到路由策略，再由路由策略选择分组并从分组内选择可用账号。

这带来三个直接收益：

- 客户端不用频繁更换 Base URL 或上游密钥。
- 上游账号更换、限流、冷却、停用、重新授权都不要求客户端侧同步修改。
- 不同用户、团队和业务通过本地 API Key、路由策略和分组授权隔离，不把上游凭据散落到客户端。

### 2. 账号池不是简单轮询

`juhe-ai` 的调度会同时考虑账号状态、分组、授权、并发、冷却、到期时间、优先级、超级优先、降级备用、质量缓存和会话亲和。

关键区别是：系统不是“拿下一个账号试一下”这么简单，而是尽量在不破坏会话体验的前提下选择当前更可用的账号。

- `disabled` 是手动硬边界，不被后台复测或旧失败异步改写误恢复；显式硬异常不被普通网关成功误恢复。
- 系统自动 transport `temporary_unavailable` 会进入带来源 fencing 的后台复测自愈；用户显式 `temporary_unavailable / rate_limited` 只按 TTL、匹配恢复或人工动作清理。OAuth 远端刷新失败只做诊断和退避，不写账户业务状态。
- 降级备用账号只在主池不可用或请求失败后进入调度，适合保留应急容量。
- 会话亲和只影响排序，不绕过 API Key、路由策略、分组授权、状态、冷却、并发和优先级。
- 被授权账户可以在被授权人自己的授权实例上设置超级优先、降级备用和迁移流量，不影响授权方原账户和其他被授权人的实例。

### 3. 未知失败先吸收波动

上游失败不一定代表账号坏了。网络抖动、上游瞬时错误、代理短暂异常和公共请求错误都可能产生失败。

`juhe-ai` 对未知失败的处理顺序是：

1. 单个账号发生本地 transport / timeout 失败时，只把对应 transport source 加入本请求排除并进入受控传输确认；通用安全文本请求收到完整非 `2xx` 时只按 `response.ok=false` 做请求级 opaque 接管。opaque HTTP 和协议失败都不能建立 Key、IP、账户或其他跨请求状态。
2. 所有请求在下游未语义提交且仍满足对应 lane 墙钟、候选和 attempt 上限时切换后续账号，不按错误码、错误类型、上游文案或请求类型做通用分支；图片接受有界 at-least-once 的重复生成/计费风险。
3. 账户错误处理策略命中时才额外按策略写入限流、临时不可调用或异常状态。
4. 只有同一请求的后续候选形成完整 framing，证明前序本地 transport source 可绕开时，才允许建立针对该 transport source 的有界来源级抑制；opaque HTTP、协议失败和仅有响应头都不能提供该证据，也不能写跨请求共享状态。
5. 任意请求的所有候选账号都失败时，返回稳定网关错误，不把最后一个上游错误、状态码、正文或私有响应头原样交给客户端；不再为图片建立独立的 `upstream_outcome_unknown` 终态。
6. 后续请求如果发现当前分组所有候选账号都被本地屏蔽，先尝试路由策略后续可承接分组；没有后续分组时快速返回 `503` 和 `Retry-After`，避免继续打刚失败的账号。

这套机制的价值是避免账号池被误伤，同时避免刚失败的账号继续承接高并发请求。一个坏请求不应该让多个可用账号被轮流冷却，单个坏账号也不应该在短时间内把上游错误扩散给大量客户端。

### 4. 流式响应按可见输出边界兜底

Codex / OpenAI Responses 这类客户端最怕流式响应卡住、半截中断或服务端把两次上游回答拼在一起。`juhe-ai` 没有把 SSE 当普通字节流简单转发，而是按事件边界增量解析，并用“是否已有可见输出”决定兜底策略。

- 可见输出前失败：所有请求在精确协议失败或普通文本允许重试的 transport / timeout / 正文中断边界下做服务端有界候选切换；generic `event: error` 和普通 payload 不解释，图片及其他副作用请求不设切号例外。服务端可承接候选耗尽后，Codex Responses、Claude Code Messages 和 Gemini CLI stream 使用各自协议错误事件，通用客户端在下游未提交时返回 HTTP `503/upstream_retryable_error`，已提交时断流。
- 可见输出后失败：已经写给下游后不伪造整轮重试，不拼接第二个账号的回答，不制造重复工具调用或上下文分叉；只记录诊断，除本地可验证 transport 事实或用户显式策略外不写共享运行态。
- `response.created`、`response.in_progress`、metadata、心跳和 header 类事件不算可见输出，不会误触发账号流失败计数。
- 文本 delta、reasoning delta、工具调用参数 delta 和会改变 assistant 内容或工具状态的 output item 才算可见输出。

这个设计的核心不是“失败就无限重试”，而是“未交付结果时做有界候选切换，已经交付后绝不拼接第二份结果”。文本、图片、音频、文件、资源、后台任务和 hosted tool 都使用同一准入，差异只在 lane 时限、协议解析和显式资源边界。是否把最终失败交给客户端安全重试取决于 `clientProfile` 和 `downstreamProtocol`；已输出后保守结束并记录问题。

### 5. 慢客户端和客户端断开不会拖垮账号池

流式转发必须尊重 `res.write()` backpressure。慢客户端读取时，网关会等待 drain 并记录背压日志，不把下游慢读误判为上游账号故障。

客户端主动断开时，网关记录 `client_aborted`，释放账号并发槽，不写账号失败状态。这避免用户取消、网络断开或客户端重启把可用账号错误冷却。

### 6. 后台恢复把“坏一次”变成“可恢复”

稳定不是只靠请求当下切账号，还需要后台把可恢复账号带回池子。

当前后台 worker 覆盖：

- OpenAI OAuth Access Token 预刷新：不受账号当前调度状态影响，只做 token 保活；远端非 `2xx`、畸形响应、超时、代理或读取异常只做诊断和有界退避，不写账户 `error`，也不覆盖手动停用或用户显式状态。只有独立可验证的本地配置 / 解密 / 装配异常进入带 provenance 的维护路径。
- 请求前懒刷新：真实请求命中 OAuth 账号且 access token 即将过期时，优先刷新后再转发。
- 冷却账号复测：固定启用，处理系统自动 transport 冷却和用户显式冷却的各自恢复通道；只有匹配来源的 `complete_success` 才恢复业务状态，失败继续退避，neutral / unknown 不计数。
- 使用记录、统计、运行日志和审计落库异步处理，减少对网关主链路的干扰。

这让账号池具备“自动止血”和“自动恢复”的闭环，而不是只靠人工频繁启停账号。

### 7. 完整审计支撑稳定性排障

稳定机制必须可解释，否则出了问题只能猜。

`juhe-ai` 把使用记录和原始审计日志分开：

- 使用记录关注请求、模型、token、成本、耗时、错误摘要和命中账号。
- 原始审计日志关注客户端请求、网关处理、上游请求、上游响应和最终返回。
- 完全成功请求默认稳定采样；非成功、客户端中断、流式中断、上游失败、网关失败以及中间失败后最终成功链路全量保存。
- 流式改写会在审计中同时保留上游原始失败和下游改写后的 `response.failed`，能解释客户端看到的错误和上游真实事件为什么不同。

这对维护客户端兼容、排查上游规则变化、定位代理问题和证明账号是否被误伤都很重要。

## 逐项对比

### 对 Sub2API

Sub2API 更像完整的 AI API 网关平台，重点能力包括订阅配额分发、Token 级计费、支付系统、用户级和账号级并发、速率限制、智能调度和粘性会话。它适合要做平台、做配额售卖或服务更多用户的场景。

`juhe-ai` 不把支付、充值和公开运营作为第一目标，因此当前 Node 阶段部署和维护边界更轻，默认 SQLite，不要求 PostgreSQL + Redis。自 [PLAN-20260706T071505000Z Node 转 Go 渐进减法迁移](../plans/计划-20260706T071505000Z-Node转Go渐进减法迁移.md) 起，后端长期目标改为 Go + PostgreSQL + Redis 单模式；项目取舍仍然围绕 GPT 账号池稳定调度、统一授权、统计审计和排障闭环展开。

如果目标是“平台运营能力”，Sub2API 更完整；如果目标是“少依赖、少配置、让自己或小团队的客户端尽量不断”，`juhe-ai` 的取舍更直接。

### 对 CLIProxyAPI

CLIProxyAPI 的强项是 CLI 生态和多协议接入。它支持 OpenAI/Gemini/Claude/Codex 兼容端点、OpenAI Codex OAuth、Claude Code OAuth、多账户轮询、WebSocket、SDK 和很多衍生工具。

`juhe-ai` 不追求覆盖这么多客户端协议，而是把 OpenAI 兼容入口后的管理闭环做完整：系统账户、系统团队、统一授权、账号分组、API Key、代理、账户错误处理策略、用量统计、AI 性能、原始审计和后台恢复都在同一个后台里。

CLIProxyAPI 更适合“一个代理吃多种 CLI OAuth”；`juhe-ai` 更适合“有多个 OpenAI 上游账号，要给客户端一个稳定入口并能在后台看清楚、管得住、查得明白”。

### 对 New API

New API 是更宽的大模型网关与 AI 资产管理系统，优势在多模型、多渠道、格式转换、Responses、Realtime、Claude Messages、Gemini、充值额度、权限管理和可视化看板。

`juhe-ai` 目前故意不走全供应商、全协议、全商业化平台路线。它把复杂度压到 GPT 账号接入、OpenAI 兼容网关、GPT OAuth / API Key 调度和 Codex / Responses 流式稳定上。

因此 New API 更适合多模型资产治理；`juhe-ai` 更适合单机轻量部署下的 GPT 账号池稳定层。功能面更窄，但出问题时链路更短、排障更集中、账号状态副作用更容易被维护者理解。

## 对外表达建议

推荐把项目优势表述为：

> `juhe-ai` 是一个轻量 OpenAI 兼容中转与账号稳定调度后台。它让 Codex、OpenAI SDK 和常见 OpenAI 兼容客户端长期固定连接一个本地 `/v1` 入口，由后台吸收账号限流、上游失败、OAuth 过期、流式中断和代理波动，减少用户频繁切换 Base URL、API Key 或账号的成本。

不建议把项目表述为：

- “替代 New API 的全模型网关”。
- “替代 Sub2API 的支付计费平台”。
- “替代 CLIProxyAPI 的全 CLI OAuth 代理”。

更准确的定位是：

- 比通用代理更可管理。
- 比大型平台更轻量。
- 比简单轮询更稳。
- 比单纯转发更懂 OpenAI / Codex 流式失败边界。

## 后续可强化方向

- 已输出后服务端重放：明确禁止，不作为后续能力评估；客户端只能发起新请求，由网关重新执行认证、额度、候选和状态判断。
- 真实上游长时间稳定性验证：在真实 OpenAI、真实代理、真实客户端和长流式场景下补充持续压测与异常注入。
- 稳定性看板：把本地账号屏蔽次数、屏蔽等待、切号救回、全部候选失败、流式改写、流失败计数、冷却复测恢复率做成管理员可读指标。
- 客户端兼容矩阵：继续记录 Codex、OpenAI SDK、Cherry Studio、NextChat 等客户端对 `response.failed`、断流和重试行为的实际表现。
