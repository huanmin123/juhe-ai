## 1. 裁决摘要

1. 代理域新增 `proxy_pools`、`proxy_pool_members`、`account_proxy_leases` 三张表；代理池是服务器级全局资源，由管理员维护，单层、不嵌套。
2. 账户代理绑定升级为“单代理 或 代理池”二选一，共用同一个下拉；存量 `accounts.proxy_profile_id` 语义和行为不变。
3. 账户绑池后按**账户级粘性租约**固定一个成员；轮询/权重只决定新绑定和失效重分配，不按请求换 IP。
4. 池成员的启停和健康决定运行时代理可用性；**池逻辑不得写入账户持久调度或健康字段**。池耗尽时，账户按现有代理可用性与路由规则暂不可派发；实际请求或账户探测收到的上游错误继续执行现有账户错误策略，可能改变账户状态（C2 裁决 A，§7.6）。
5. 池内无可用成员时不发起上游请求、不静默直连；成员恢复后，已有可用租约的账户随现有缓存和候选刷新重新可用，无租约/失效租约的账户在下一次请求解析时补租约。池不可用沿用现有代理不可用 attempt/终态（`proxy_unavailable`/`proxy:configured`），池原因只作内部诊断 `pool_reason=proxy_pool_unavailable`；不新增池专用 URL、`ProxyPoolUnavailable` 字段或用户可见池码。
6. 直接代理（`proxy_profile_id`）的校验、行为、错误语义完全不变；新增的 `pool_health_status` 只对池成员分配生效，`test_status` 仍是直接代理的运维参考，不改变直接代理的调度语义。
7. 代理池全局可见（C6 A）：管理员维护，普通用户在账户下拉只看到 enabled 池的摘要，不按 owner 过滤；不等待 T117d 的 owner 隔离裁决。本设计仍不改变 `proxy_profiles` 的全局可见性和 `system_account_id` 写入归属；T117d 对代理名称作用域的裁决不受本文预占。
8. 池不按 vendor 限制，任何账户可用；池健康只判断“代理是否可用”，不按 vendor 逐个探测；1-2 次可用性探测失败为 `degraded`，仍可分配（用户裁决）。
9. `dead` 采用**连续 3 次可用性探测失败**阈值；一次成功即恢复；3 次阈值降低误杀，但不消除本机网络长期故障导致集中下架的风险（用户裁决）。
10. 租约失效只在 gateway 请求解析时修复；**不新增后台扫描，不主动预修复空闲账户**。账户粘住成员直到该成员不可分配，下一次请求排除坏成员并按池策略选新成员（用户裁决）。
11. C7-R：jobs 每次可用性探测完成后写 PG `pool_health_*` 和 Redis 成员健康键（`juhe-ai:{<namespace>}:proxy-pool:member-health:<profile_id>`，TTL 5min）；gateway 对池绑定账户在请求解析时批量 `MGET`，`dead` 即排除并重分配租约；Redis 缺失/失败回退 PG，两者都不可用 fail-closed。池绑定账户的代理 URL 可来自 60s 运行时缓存，但健康门每请求读 Redis；`dead` 时请求内重分配并覆盖缓存 URL。直接代理保持 60s。不新增 jobs→gateway 事件/RPC；Redis key 是共享领域契约，不是 gateway `inval` 内部键。

## 2. 目标与非目标

### 2.1 目标

- 支持大量账户共享一组代理，按权重或轮询把账户分散到不同出口。
- 账户出口 IP 稳定：同一账户固定一个池成员，不因请求、进程重启或权重调整漂移。
- 成员不可用时停止新分配，受影响账户在 gateway 下一次请求解析时恢复租约；池逻辑不修改账户调度状态。
- 把现有全链路账户代理解析收口到同一契约，任何账户出站路径都不得绕过代理池直连。
- 管理员可观测：每个池成员的租约数、健康状态、最近池健康检测；账户列表显示池名和当前成员。

### 2.2 非目标

- 不做每请求轮换，不做按请求在池内选成员。
- 不做后台租约修复扫描，也不为无请求流量的空闲账户预分配成员；首次请求负责修复（§6.6）。
- 不做池套池、跨 owner/跨授权池、池级配额、池级并发上限。
- 不做自动重平衡：改权重、增删成员不主动打散存量租约。
- 不做跨成员复测归因或上游封禁识别；不把单次上游 HTTP 失败直接判为代理坏（C2 A：实际出站错误仍按现有账户策略处理）。
- 不改变账户调度算法、路由策略、分组绑定、会话亲和、IP 回避和代理桶语义；池可用性按现有代理可用性规则影响本次候选是否可派发。
- 第一版不做导入时自动创建代理池，只引用已存在的池（见 §8.4）。
- 不改 `proxy_profiles` 的 owner 可见性，不解决 T117d 的历史归属问题。

## 3. 现状事实与差距

> 行号取自 2026-11-05 当前工作区（有未提交改动）；代码变动后以函数/结构名为准。复审已抽查关键引用在当前工作区仍可定位。

### 3.1 单代理绑定事实

- `proxy_profiles` 是单代理档案：`id/system_account_id/name/type/host/port/username/password_encrypted/enabled/test_status/latency_ms/outbound_ip/outbound_region/last_test_*/created_at/updated_at`，没有分组、成员、权重或租约结构（`backend-go/projects/maintenance/internal/schema/pg_schema_business_tables.go:208-227`）。
- `accounts.proxy_profile_id` 是单值外键，一个账户最多绑一个代理（同文件 `:609,660`）；`idx_accounts_proxy_profile` 支撑 `(proxy_profile_id, id)`（`pg_schema_business_indexes.go:275`）。
- 账户创建、编辑、批量编辑和导入都按“目标代理必须存在且 enabled”校验；批量编辑额外带 owner 作用域，其余路径不带（`accounts/write.go:821-832`、`patch.go:737-769`、`accountstransfer/batch.go:857-884`、`accountstransfer/import.go:1571-1621`）。
- 账户列表和授权实例详情通过 `LEFT JOIN proxy_profiles` 返回 `proxyProfileId/Name/Type/Enabled/Unavailable/ErrorMessage`；`proxyProfileUnavailable` 的判定是“未解析或 enabled 非 true”（`accounts/list.go:660-695,741-753,1214-1261`、`m11_reads.go:413,424`）。
- 网关运行时按批收集有效代理 ID，单条 SQL 读取代理行并解密 URL，再写入候选账户的 `ProxyProfileID/ProxyURL`；`socks5` 与 `socks5h` 统一渲染为 `socks5h://`（`cmd/juhe-ai-gateway/chain_accounts.go:531-540,1846-1932`、`chain_accounts_secret.go:578-595`）。
- 运行时缓存把解密后的 `ProxyURL` 明文保存 60s revalidate / 2min retain（`internal/gatewayruntimecache/service.go:24-33`、`types.go:359-362`）；账户改绑会失效运行时缓存，代理档案 PATCH/DELETE 目前不会（`internal/accounts/invalidation.go:44-67,149`；`internal/proxyprofiles` 包没有 invalidator 引用）。

### 3.2 代理健康与探测事实

- jobs 的 J3a 是当前周期代理诊断：`enabled` 代理 × 已启用供应商默认地址，默认 `interval=5s`、每轮最多 `batch=512`，按“从未测试 → 最久未测”滚动覆盖（`jobs/internal/proxylatency/config.go:14-31`、`direct_input_reader.go:366-386`、`runner.go:873-883`）。池健康不消费该 vendor 矩阵，另走“代理是否可用”的可用性探测（§7.2）。
- 投影只写 `test_status/latency_ms/last_test_message/last_tested_at`；手动检测额外写 `outbound_ip/outbound_region`（`result_projector.go:541-575`、`:348-394`）。
- `test_status` 当前是运维参考，**不是派单门**：直接代理只要 `enabled` 就会被使用（`核心功能设计.md:533`、`docs/deploy/proxy/sing-box网络代理部署指南.md` §9.6、`AI账户错误语义与状态变更边界.md:46/145`）。
- J3a 的 `OverallStatus` 是跨全部已启用 vendor 目标的聚合：任一 target `failed` 即整体 `failed`，全部 passed 才 passed（`proxylatency/types.go:141-164`）。因此单个 vendor 端点不可达就会把整个代理标 failed，池若直接用整体状态排除会过度保守。
- `test_status` 变化不会触发 gateway 运行时缓存失效；J3a 在 jobs 进程，gateway 外层运行时缓存采用 60s revalidate / 2min last-good retain（`gatewayruntimecache/service.go:24-33`）。这是缓存策略，不保证数据库持续故障时两分钟内获得新状态。
- `gatewayproxyhealth` 的按代理桶键**已接线**：`gatewaydispatch/preparation.go:610` 调 `ProxyHealth.OrderAsync`，`cmd/juhe-ai-gateway/chain_wiring_w2c.go:684-699` 装配；桶键为 `proxy:profile:<id>` / `proxy:url:<sha256>`（`gatewayproxyhealth/proxyhealth.go:306-351`），参与上游桶排序/避让。池绑定时有效成员会成为桶键，本设计必须显式处理该交互。
- 代理写入不会触发运行时缓存失效，与 `核心功能设计.md:511`“创建、更新和删除成功后发布 gateway runtime cache 失效”的现行文档表述不一致；实施时必须裁决并回正文档或代码。
- `核心功能设计.md:533` 写“后台刷新固定每 60 秒最多检测 20 个启用代理”，与当前 Go J3a 的 5s/512 不一致；实施时一并回正。
- 账户可用性投影 **确实包含代理展示字段**：`jobs/internal/circuitstore/listavailability_rows.go:140-200,551-566` 选取并写入 `proxyProfile*`，而 `proxy_profiles` 的 dirty 触发器已于 2026-10-17 移除（`pg_schema_business_tables.go:2167-2172`）。池/成员/租约变化若只改 live join，会让该投影消费者看到陈旧代理信息；本设计必须补投影 dirty 口径（§8.5）。

### 3.4 现存不一致（实施时必须一并收口）

1. **静默直连**：余额手动刷新在代理档案不存在时返回 `(nil,nil)`，会直连；共享直读在 `proxyRequired` 为真且无绑定/停用时会报错，仅在未要求代理时允许直连（`compose_account_balance_refresh.go:163-165`、`accountbalance/direct_input_reader.go:222-231`）。余额手动/周期查询均未检查 `proxy_profiles.enabled`（`compose_account_balance_refresh.go:150-160`、`worker_balance_detect.go:750-758`），停用代理仍会被使用。池绑定必须始终视为 proxyRequired：租约缺失/成员不可用一律失败，不得直连。
2. **媒体任务不读实例 source 覆盖**：`chain_media_video.go:910-940` 只读账户本行 `proxy_profile_id`；授权实例行该字段为 NULL，媒体任务会直连。现有契约已承认该差异（`接口契约与权限矩阵.md:739`），但池绑定会让“同一账户不同入口出口不同”更明显。C10 裁决 A：本期修正，媒体任务统一走有效目标解析，消除实例 source 覆盖差异。
3. **代理写入不失效运行时缓存**：与 `核心功能设计.md:511` 的现行表述冲突；池成员/池启停变更如果不失效，缓存可能继续使用旧成员，具体边界见 §7.4。
4. **新增池健康投影参与分配**：本设计新增 `pool_health_status` 供池成员分配消费（见 §7.2），不改变直接代理只看 `enabled`、`test_status` 仅作运维参考的既有语义。实施时必须同步 §14 文档。
5. **审计代理 URL 含凭据**：`audit_log_attempts.proxy_url` 与读路径只 trim，含 `user:password`（`gatewayusage/audit_capture.go:705,858`、`gatewayusage/snapshots.go:283-287`、`logreads/audit_reads.go:320-343`）。本设计不改变该既有契约，但新增池/成员字段时不得扩大敏感面。
6. **可用性投影含代理字段且 dirty 触发器已删**：`listavailability_rows.go:140-200,551-566` 的 payload 含 `proxyProfile*`，`proxy_profiles` dirty 触发器已于 2026-10-17 移除；池/成员/租约变化若不补 dirty 口径，投影消费者会长期显示旧成员。§8.5 给出处理方案。
7. **代理桶已接线**：`preparation.go:610` + `chain_wiring_w2c.go:684-699` 已启用按代理/上游桶的健康排序与避让，桶键包含 `proxy:profile:<id>`/`proxy:url:<hash>`。池绑定把 `ProxyProfileID` 映射为有效成员后会自然进入该桶；这是既有机制，不是本设计新增，但必须纳入验收（§10.2/§12.1）。
8. **schemaReady/启动检查未含池**：`shared/contracts/business_schema.go:92,105-106` 的 `BusinessSchemaVersion` 仍为 v22，`accounts` 必填列无 `proxy_pool_id`、必填表无池表；`jobs/cmd/juhe-ai-jobs/worker_business_db.go:116` 同样。池 DDL 必须同步升 `BusinessSchemaVersion`（建议 v23）并加入检查，否则旧库可能通过启动门后才在查询时报错。
9. **余额身份摘要多处直读**：除 `accountbalance/input_digest.go`/`models.go` 外，`accountsbalance/balance.go:80-110`、`accounts/patch.go:2496-2518`、`shared/platform/accountbalance/multi_key.go:45-49` 都只把 `proxy_profile_id` 纳入摘要；池绑定若不改这些点，租约迁移后旧余额快照仍会被当成当前（§10.3）。
10. **失效总线是 gateway 进程内组件**：`inval.Bus`（`backend-go/projects/gateway/internal/inval/inval.go`）只在 gateway 内使用；`Invalidate` 清本地缓存并把版本号写 Redis 共享键（`<namespace>:inval:topic-version:<topic>`），gateway 缓存读前 `SyncFromShared` 拉取版本，没有 Redis pub/sub 推送到 gateway。jobs 不导入该包，也不应写 `topic:gateway_runtime_cache` 共享键。池健康若让 jobs 发布 gateway 失效，会把 jobs 耦合到 gateway 缓存实现，违反“jobs 与 gateway 隔离”约束；§7.4 因此采用独立的 Redis 成员健康键（领域契约，不是 gateway inval 键），gateway 请求时直接读取。

### 3.5 差距结论

代理池不是“代理管理页多一个列表”，而是**出站解析契约 + 数据模型 + 粘性租约 + 成员健康 + 全链路收口**。只做管理页和主派发链会导致余额、OAuth、探针、媒体、模型目录等路径绕过池，出口身份不确定。

## 4. 目标数据模型

### 4.1 `proxy_pools`

```text
id                 TEXT PRIMARY KEY
system_account_id  TEXT NOT NULL              -- 写归属，沿用 proxy_profiles 口径；读取面仍为全局
name               TEXT NOT NULL
description        TEXT
strategy           TEXT NOT NULL              -- 'round_robin' | 'weighted'
                   CHECK (strategy IN ('round_robin','weighted'))
enabled            BOOLEAN NOT NULL DEFAULT true
created_at         TIMESTAMPTZ NOT NULL
updated_at         TIMESTAMPTZ NOT NULL
```

- 名称全局唯一，沿用 `proxy_profiles` 的 `name` 唯一口径（`pg_schema_business_indexes.go:977`）；T117d 若改为租户内唯一，池同步改。
- `strategy` 首版只允许 `round_robin` 和 `weighted`；不做 `failover`。
- 池创建后 `strategy` 可改，但改策略不重排存量租约（§6.5）。

### 4.2 `proxy_pool_members`

```text
pool_id             TEXT NOT NULL REFERENCES proxy_pools(id) ON DELETE RESTRICT
proxy_profile_id    TEXT NOT NULL REFERENCES proxy_profiles(id) ON DELETE RESTRICT
priority            INTEGER NOT NULL CHECK(priority >= 0)
weight              INTEGER NOT NULL CHECK(weight BETWEEN 1 AND 100) DEFAULT 1
enabled             BOOLEAN NOT NULL DEFAULT true
created_at          TIMESTAMPTZ NOT NULL
updated_at          TIMESTAMPTZ NOT NULL
PRIMARY KEY (pool_id, proxy_profile_id)
UNIQUE (pool_id, priority)
```

- 单池成员数上限 50（应用层校验，DB 只兜底非负优先级）。
- `priority` 由后端归一：客户端提交数组顺序即优先级，后端在事务内归一为连续 `0..n-1`；客户端不能提交重复优先级。归一方向与超级分组一致。
- `weight` 缺省 1，范围 1..100；`round_robin` 下权重仍保存但不参与选择（或按 1 处理），避免切换策略时丢配置。
- 同一代理可加入多个池；同一池不能重复同一代理。
- 成员行 `enabled=false` 是“从本池下架”，不等于代理档案停用；代理档案 `enabled=false` 是所有池都不可用。

### 4.3 `account_proxy_leases`

```text
account_id          TEXT PRIMARY KEY          -- 有效绑定所有者：普通账户=自身；授权实例=source account
                    REFERENCES accounts(id) ON DELETE CASCADE
pool_id             TEXT NOT NULL REFERENCES proxy_pools(id) ON DELETE RESTRICT
proxy_profile_id    TEXT NOT NULL REFERENCES proxy_profiles(id) ON DELETE RESTRICT
generation          BIGINT NOT NULL DEFAULT nextval('juhe_business.account_proxy_lease_generation_seq')
                                               -- 单调递增，删除重插不复位
assignment_reason   TEXT NOT NULL              -- 'initial' | 'member_unavailable' | 'member_removed' | 'pool_reassigned'
                    CHECK (assignment_reason IN ('initial','member_unavailable','member_removed','pool_reassigned'))
assigned_at         TIMESTAMPTZ NOT NULL
updated_at          TIMESTAMPTZ NOT NULL
FOREIGN KEY (pool_id, proxy_profile_id)
  REFERENCES proxy_pool_members(pool_id, proxy_profile_id) ON DELETE RESTRICT
```

- 租约按**有效绑定所有者**存储，不按授权实例行存储：同一上游账户的所有授权实例共享一个出口，避免同一凭证同时出现在多个 IP。
- 租约为空表示“配置上绑了池，但尚无有效租约”，可能正在等待修复，也可能没有可分配成员；不是直连信号。
- 租约与账户配置的 `pool_id` 必须一致：写入前锁定账户行（`SELECT ... FOR UPDATE`）并校验 `accounts.proxy_pool_id = pool_id`，不能只靠应用层先读后写；池成员变更同时锁池行。
- `generation` 使用同一个数据库序列：每次 INSERT 和改变成员的 UPDATE 均显式取 `nextval`，禁止自行 `+1`；删除/重插后不复用。CAS 条件固定为 `account_id + generation + proxy_profile_id`，并在账户行锁内校验当前池绑定，避免 ABA 和跨池写入。
- `assigned_at` 表示当前成员的分配时间，换成员时一并更新；`updated_at` 表示行更新时间。两者在 INSERT 时相同，后续可因非换成员的行更新分离。
- `assignment_reason` 取值：`initial`（首次分配）、`member_unavailable`（已有租约成员不可分配）、`member_removed`（成员删除后重新分配）、`pool_reassigned`（账户改绑池）。成员恢复导致的首次补租约按 `initial` 记录。
- 复合外键保证租约成员一定在池内；成员删除/池删除必须在同一事务先删租约，否则 FK 阻塞。
- 账户删除（逻辑删除后物理清理）级联删除租约；池删除前必须先没有绑定账户（§4.5）。

### 4.4 `accounts.proxy_pool_id`

```text
proxy_pool_id TEXT NULL REFERENCES proxy_pools(id) ON DELETE RESTRICT
CHECK (proxy_profile_id IS NULL OR proxy_pool_id IS NULL)  -- 至多一个非空
```

- 新增 `idx_accounts_proxy_pool (proxy_pool_id, id)`。
- 账户行变更脏触发器目前比较列集包含 `proxy_profile_id`（`pg_schema_business_tables.go:1798,1851`）；新增 `proxy_pool_id` 必须同时加入 new/old 列集，否则改绑池不会标脏。若可用性投影构建 SQL 不消费该列，按“只改一半禁止”的既定教训处理：要么同步纳入构建 SQL，要么明确不依赖该列并保留账户行变更语义。
- 软删除账户仍保留 `proxy_pool_id` 和租约，直到物理清理；删除池的绑定守卫忽略软删除账户，但同一事务清空其 `proxy_pool_id` 并删除租约（例外，避免 FK 阻塞，见 §4.5）。

### 4.5 约束与删除规则

| 操作 | 规则 |
| --- | --- |
| 删除池 | 存在未删除账户绑定（`proxy_pool_id=pool_id AND deleted_at IS NULL`）返回 `409 proxy_pool_bound_accounts`；删除前预览最多 4 个账户名，沿用代理删除的固定窗口口径；同一事务先把软删除账户的 `proxy_pool_id` 清为 NULL（避免 FK 阻塞），再删租约、成员行，最后删池 |
| 删除成员 | 同一事务删除该成员的租约、删除成员行并把剩余成员 priority 重新归一为连续 `0..n-1`；受影响账户由 gateway 按 §6.6 修复，不阻塞成员删除 |
| 停用成员 | `proxy_pool_members.enabled=false`；不删除租约；视为不可分配并由 gateway 按 §6.6 迁移 |
| 停用池 | `proxy_pools.enabled=false`；保留租约；所有绑定账户运行期 `proxy_pool_unavailable`；重新启用后若成员仍可分配则恢复原租约 |
| 删除代理档案 | 若被任何池引用，返回 `409 proxy_pool_member_reference_conflict`，不能删除；先解除成员关系 |
| 停用代理档案 | 允许；所有引用它的池成员视为不可分配；绑定账户按 §6.6 迁移 |
| 删除账户 | 逻辑删除保留租约；物理清理级联删除租约 |

可用性投影的 dirty 口径（与 §8.5 联动）：账户行 `proxy_pool_id` 变更纳入既有账户 update 触发器列集；`account_proxy_leases` INSERT/UPDATE/DELETE 按 account_id 标脏；`proxy_pools` 的 `name/enabled/strategy` 变更和 `proxy_pool_members` 的增删改按 pool 绑定账户标脏；`proxy_profiles` 的 `name/type/enabled` 变更按直接代理或池引用标脏，`pool_health_status` 仅进入或离开 `dead` 时按所有引用该代理的池的绑定账户标脏，包括当前无租约的账户。不要按 `test_status/latency/last_tested_at/pool_health_checked_at` 标脏，避免恢复高频纯 churn。所有触发器与投影构建 SQL 必须同批修改，禁止只改一半。

### 4.6 schema revision 与迁移

- 当前工作区 `SchemaRevision=17`（`backend-go/shared/contracts/project.go` 注释与常量；2026-11-05 九家真实厂商收口已占用 17）。本设计新增纯 DDL，revision 升到 **18**；不得复用 17。若发布顺序上厂商收口先上线，池批次顺延；若两者同窗口，必须明确合并后的 revision 与 golden，不允许两个分支各自声明 17。
- 同步升 `BusinessSchemaVersion`（当前 v22，`shared/contracts/business_schema.go:92`）到 **v23**，把 `accounts.proxy_pool_id`、`proxy_pools`、`proxy_pool_members`、`account_proxy_leases` 以及 `proxy_profiles.pool_health_status/pool_health_failure_streak/pool_health_checked_at` 纳入 gateway schemaReady 与 jobs `worker_business_db.go` 的必填表/列检查；`modelcheckowner/business_source.go` 的代理查询同步。
- 新增语句插入 `pg_schema_business_tables.go` 与 `pg_schema_business_indexes.go` 的正确顺序；新增 `accounts.proxy_pool_id` 用 `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` 形态并入加法相。
- 池健康字段：`proxy_profiles` 增加 `pool_health_status`（`healthy|degraded|dead|unknown`，nullable）、`pool_health_failure_streak` 和 `pool_health_checked_at`（最近一次可用性探测完成时间，驱动每代理 60 秒调度；探测完成且结果成功投影时更新，任务取消/无结果/投影失败不更新），由可用性探测结果投影（§7.2）；直接代理不消费，J3a vendor 矩阵也不消费。
- 同步 `pg_schema_test.go` 的语句总数/golden（池批 +16 到 641；后续跨协议退役批回落到 637，当前基线以 `goldenPostgresSchemaStatementCount` 为准）、`schema_state` digest、`validate-test-rehearsal.mjs` 的复制/清空清单（池与成员为配置复制；租约为运行态清空）。
- 不做存量数据迁移：现有账户仍为直接代理或无代理；代理池是新增可选绑定。

## 5. 绑定与解析语义

### 5.1 配置绑定与有效目标分离

| 概念 | 存储 | 含义 |
| --- | --- | --- |
| 配置绑定 | `accounts.proxy_profile_id` 或 `accounts.proxy_pool_id` | 用户/管理员选择的单代理或池 |
| 租约 | `account_proxy_leases` | 池绑定当前固化的成员 |
| 有效目标 | 运行时解析结果 | 直接代理=配置代理；池=租约成员；无配置=直连 |
| 展示字段 | 列表/详情 API | 必须同时暴露配置绑定和有效成员，不能把成员写回配置字段 |

### 5.2 授权实例覆盖

- 授权实例的上游凭据、模型能力、代理等从来源账户补齐（`架构总览.md:254`）。解析顺序：
  1. 实例有 source account：若 source 有 `proxy_pool_id` → 用 source 的池；否则若 source 有 `proxy_profile_id` → 用 source 的代理；否则回落到实例自身既有的直接代理绑定（无绑定则直连）；实例自身的池绑定不参与解析。source 已有任一绑定时，实例自身两列即使是双绑定损坏态也不参与、不阻断 source 解析。
  2. 普通账户：使用自身 `proxy_pool_id` 或 `proxy_profile_id`。
- **两列同时非空是数据损坏**：普通账户或 source 行双列同时非空时解析器返回 `proxy_target_conflict` 并记录诊断，绝不静默按池优先选边；授权实例在 source 无绑定、回落到实例自身 direct profile 时，若实例行双列同时非空同样返回 conflict。写入路径用 `CHECK` + 应用校验保证至多一列。现有历史数据如有双列，必须先修复数据再上线。
- 池租约键固定为 source account ID；实例行即使误写 `proxy_pool_id` 也不参与解析。
- 实例详情只读展示 source 的池名/当前成员；实例自身不能改池。

### 5.3 统一解析契约

新增共享解析器（建议 `backend-go/shared/platform/proxyresolve`，允许注入解密函数以保持依赖方向）：

```text
Target {
  Kind:              "direct" | "profile" | "pool_member"
  ProfileID:         string   // direct/profile 时为配置档案；pool_member 时为成员档案
  PoolID:            string   // pool_member 时非空
  MemberProfileID:   string   // pool_member 时等于 ProfileID
  URL:               string   // 已解密并归一为 socks5h:// 等；direct 时为空
  UnavailableCode:   string   // 空表示可用
  UnavailableMessage:string
}

ResolveAccount(accountRef) (Target, error)
ResolveAccountsBatch(accountRefs) (map[accountKey]Target, error)
```

解析器以接口注入 DB、解密函数、Redis 成员健康读取器和时钟，便于单元测试与 Mock；批量接口是网关热路径的唯一入口，单账户接口供 jobs/OAuth/余额等使用。健康读取器批量 `MGET`，缺失/失败回退 PG。

解析规则固定：

1. 按 §5.2 确定有效绑定和租约键；池不按 vendor 限制，任何账户可用；池健康只做“代理是否可用”的可用性探测，不按 vendor 逐个探测（用户裁决）。
2. 无绑定 → `Kind=direct`，URL 为空；**不**读取环境代理（沿用 `upstreamhttp` 直连语义）。
3. 直接代理 → 档案必须存在、`enabled=true`、密码可解密；否则 `UnavailableCode=proxy_unavailable`，**不得直连**。
4. 池 → 池必须存在且 `enabled=true`；租约必须存在且成员在池内、成员行 enabled、代理档案 enabled；健康先读 Redis 成员健康键，存在时以其为准；缺失/失败回退 PG `pool_health_status`；`dead` 即不可分配；否则 `UnavailableCode=proxy_pool_unavailable`，**不得直连**。
5. 池租约为空但成员可分配时，只有 gateway 在**请求解析路径**按 §6.6 补租约；只读进程（jobs/shared reader）返回 `proxy_pool_unavailable`，不自行选择成员。没有请求流量时允许保持无租约，不新增后台扫描。
6. 两列同时非空 → `proxy_target_conflict`，不选边。
7. 任何解密失败、host/port 非法、协议不支持都返回明确的不可用，不返回空 URL 伪装直连。

### 5.4 失败语义

| 场景 | 结果 | 是否直连 |
| --- | --- | --- |
| 无代理绑定 | `direct` | 是（合法直连） |
| 直接代理不存在/停用/解密失败 | `proxy_unavailable` | 否 |
| 池不存在/停用 | `proxy_pool_unavailable` | 否 |
| 池无 enabled 成员 | `proxy_pool_unavailable` | 否 |
| 池有成员但全部健康不可分配 | `proxy_pool_unavailable` | 否 |
| Redis 健康键缺失/读取失败 | 回退 PG `pool_health_status`；PG 也不可用则 `proxy_pool_unavailable` | 否 |
| 租约为空且池有可分配成员 | gateway 在请求解析时补租约；只读进程返回 `proxy_pool_unavailable` | 否 |
| 租约成员被移除/停用 | gateway 在下一次请求解析时修复租约；修复前只读进程返回 `proxy_pool_unavailable` | 否 |
| 池成员代理解密失败 | 该成员不可分配；无其他成员则 `proxy_pool_unavailable` | 否 |

### 5.5 运行时字段映射

为避免改动传输层和审计的既有消费面，运行时候选做如下映射：

- `ProxyProfileID` = 有效成员档案 ID（直接代理时为配置档案；池绑定时为租约成员）。
- `ProxyURL` = 有效成员的解密 URL。
- 新增 `ProxyPoolID`、`ProxyMemberProfileID`，用于派发键、诊断和列表。
- 复用 `ProxyProfileUnavailable` 作为“有效代理目标不可用”的通用标记（字段名为历史兼容）；解析器内部用结构化原因区分 `proxy_unavailable` 和 `proxy_pool_unavailable`，用户可见 attempt 仍复用 `proxy_unavailable`，不得从消息文本判断。
- 既有 `gatewayproxyhealth` 会按 `ProxyProfileID` 生成 `proxy:profile:<member>` 桶键并参与上游桶排序/避让；池绑定时成员级桶避让仍然生效，这是既有行为。
- 普通上游 transport/HTTP/协议失败沿用对应入口既有错误策略和代理桶行为，不得新增成员下线或池级排除；成员下线只由健康投影/手动下架触发。

### 5.6 请求内代理错误处理

- 池解析出的成员沿用现有代理身份、重试与代理错误处理；不新增池级失败记忆、去重键或跨请求熔断。
- 池不可用、租约缺失或失效沿用现有代理不可用 attempt/终态（`proxy_unavailable`/`proxy:configured`）；池原因写内部诊断 `pool_reason=proxy_pool_unavailable`，不新增 `proxy:pool` URL、`ProxyPoolUnavailable` 字段或用户可见池专用 code。候选阶段被过滤时不产生 attempt；进入派发的按现有代理不可用路径处理，不据此推断整个池不可用，也不回退直连。
- 实际上游 transport/HTTP/协议错误仍按现有账户错误策略处理，可能影响账户状态（C2 A）；这些错误不更新池健康。池健康只由代理可用性探测结果投影及人工成员下架改变。

## 6. 租约与分配策略

### 6.1 租约创建时机

| 场景 | 处理 |
| --- | --- |
| 账户创建绑池 | 账户 INSERT 与租约 INSERT 同一事务；无健康成员时允许创建但无租约（池结构必须至少有一个 enabled 成员，否则 400 `proxy_pool_empty`） |
| 账户 PATCH 改绑池 | 账户 UPDATE 与租约替换同一事务；旧租约删除 |
| 批量编辑绑池 | 逐账户在同一批事务内分配；每个账户独立租约 |
| 克隆 | 复制池绑定，不复制租约；新账户按策略重新分配（C9 A 已确认，见 §15） |
| 导入绑池 | 第一版只引用已存在池；每个账户创建时分配租约 |
| OAuth 建号 | 建号前用池做一次**临时分配**（不落租约），同次授权交换固定使用该成员；账户落库时重新校验成员仍可分配，并把同一成员固化为租约（`assignment_reason='initial'`），校验失败则明确失败，不静默换出口。并发建号在落库前不占租约，可能临时集中同一成员；第一版接受该限制，不引入预留表 |
| OAuth 自动刷新/重新授权/jobs 保活 | 使用账户已固化租约成员；租约不可用时失败，不在 token 刷新中途换 IP、不直连；jobs `oauthrefresh` 的 `refresh/keepalive/store` 全部走统一解析器 |
| 草稿测试 | 临时分配，不固化；保存时重新分配。草稿测试是诊断，不承诺与保存后出口一致 |
| 重分配 | gateway 请求解析发现租约不可分配时，按统一锁序重新分配并 CAS 更新（§6.6）；不新增后台扫描 |

### 6.2 可分配成员

成员可分配必须同时满足：

1. `proxy_pools.enabled = true`；
2. `proxy_pool_members.enabled = true`；
3. `proxy_profiles.enabled = true`；
4. 代理档案密码可解密、host/port/scheme 合法；
5. 健康状态不是 `dead`：先读 Redis 成员健康键，存在时以其为准；缺失/读取失败回退 PG `pool_health_status`；`dead` 即不可分配；NULL 按 `unknown` 处理，SQL 必须显式包含 NULL。
6. `pool_health_failure_streak` 未达到 3；连续 3 次可用性探测失败后才进入 `dead`（§7.2）。

`pool_health_status` 由池可用性探测投影（§7.2）；字段为 NULL 的存量行视为 `unknown`，不得用旧整体 `test_status` 推断 `dead`；`pool_health_failure_streak` 默认 0。

代理 PATCH 命中现有 `connectionChanged` 检测字段重置分支时，也把 `pool_health_status` 重置为 `unknown`、`pool_health_failure_streak` 重置为 0、`pool_health_checked_at` 重置为 NULL，并删除 Redis 成员健康键（best-effort，失败靠 TTL/下次探测兜底）；旧连接的检测结果不得继续决定新连接的分配状态。

- `healthy/degraded/unknown` 均平等参与分配；只用租约数、权重和成员顺序决定选择，不增加健康等级平票或检测过期计时规则。池不按 vendor 限制，`degraded` 的可分配性是接受的粗粒度取舍：可用性探测成功只证明代理链路可用，不代表特定 vendor 可达或未被封禁；需要精确隔离时另立 per-vendor 健康设计。
- `dead` 在连续 3 次可用性探测失败后进入，**始终不可分配**，直到一次有效成功；不因时间过期自动降级为 unknown（避免坏节点回流）。
- 从未检测的成员为 `unknown`，可分配；无探测结果或无可判定结果时保持原状态，健康结果陈旧不自动推断新状态。

### 6.3 `round_robin` 语义

对可分配成员计算当前池内租约数 `leases(member)`，选择：

```text
min leases(member)
tie: priority ASC, proxy_profile_id ASC
```

这是“按账户数轮转”，不是按请求游标；它天然抗并发、抗成员增删，且存量租约不动。举例：3 个成员、5 个账户依次绑定 → 2/2/1。

### 6.4 `weighted` 语义

选择：

```text
min leases(member) / weight(member)
tie: priority ASC, proxy_profile_id ASC
```

比较用整数交叉相乘（`leases_a * weight_b` vs `leases_b * weight_a`），避免浮点误差。权重 1:2:1、8 个账户的期望分布是 2/4/2；实际以逐次最小比值分配为准。

### 6.5 粘性、不重排与重平衡

- 已存在的租约在成员可分配时永不因以下事件改变：新账户加入、权重调整、池策略切换、成员新增、其他成员恢复。
- 只有以下事件触发重分配：租约成员被删除、被停用（成员行或代理档案）、健康不可分配、池被删除（池删除前必须无绑定账户，实际不会发生）、账户改绑/解绑。
- “改权重后立即重平衡”是非目标；需要时另立显式管理操作，且必须审计。第一版不提供。
- 账户解绑或物理删除时删除租约；逻辑删除保留至物理清理（§4.5）。重新绑定时重新分配，不保证回到原成员。

### 6.6 失效重分配

- gateway **只在请求解析路径**处理池绑定账户的租约，不运行独立后台扫描：
  1. 读取租约；成员可分配时直接使用，账户继续粘住该成员。
  2. 租约缺失或成员不可分配时，按 §6.2/§6.3/§6.4 从当前可分配成员中选新成员；已有租约时在账户行锁内校验绑定，再执行 `UPDATE account_proxy_leases SET proxy_profile_id=?, generation=nextval('juhe_business.account_proxy_lease_generation_seq'), assignment_reason=?, assigned_at=?, updated_at=? WHERE account_id=? AND generation=? AND proxy_profile_id=?`；缺失时在同一锁内校验绑定并 INSERT，generation 同样取该序列；
  3. CAS 或唯一约束冲突时重读并重新校验最新绑定和租约，不能直接使用未经校验的结果；
  4. 解析和重分配在本次请求内完成，然后使用新成员发起上游请求；同一账户的并发请求遵守账户行锁与 CAS，只有一个请求写入新租约。
- 用户口径“只要不坏就访问同一个，坏了就访问下一个”对应上述行为：租约成员可分配时不换；不可分配时下一次请求排除坏成员并按池策略选新成员。`round_robin` 的“下一个”由 §6.3 的租约数最少者决定，不保证严格 priority 相邻，但保证不会继续使用坏成员。请求路径的“知道坏了”来自解析时读取的成员状态；成员状态由 60 秒可用性探测或人工下架更新。单次请求的代理连接失败不会立即改租约或下架成员（C1/C2），连续 3 次探测失败进入 `dead` 后，后续请求解析才会换成员。成员状态更新后由 gateway 在请求解析时读取 Redis/PG 健康；C7-R 下 jobs 标记 `dead` 后下一次请求即可排除，不依赖运行时缓存窗口。
- 没有可分配成员时保留已有租约，解析仍返回 `proxy_pool_unavailable`；若成员被删除则必须删除其租约（FK 不允许悬空）。
- 只读进程不重分配；它们读取到的不可用租约直接失败，等待 gateway 下一次请求解析。无请求流量的空闲账户可以暂时保留失效租约，不影响账户调度状态；首次请求会先修复再派发，不为空闲账户做主动扫描。

### 6.7 并发与 CAS

- 租约分配在 gateway 内串行化到池级，锁池行并锁账户行；创建、改绑、成员更新和请求解析重分配必须使用同一锁序。跨池改绑按池 ID 固定顺序锁相关池，再锁账户，事务内重新验证绑定与成员；具体批处理锁序在实施计划中展开并以并发测试验证。
- 租约更新带 `generation` CAS；并发请求解析/管理写入不会互相覆盖。
- 分配只统计 `account_proxy_leases` 中该池的当前行；软删除账户的租约在物理清理前仍计数，避免短期分配倾斜；如需精确可加 `JOIN accounts deleted_at IS NULL`，第一版按全量租约计数，口径写入验收。

### 6.8 示例

池 P：成员 A(weight=1, priority=0)、B(weight=2, priority=1)、C(weight=1, priority=2)，全部 healthy。

- `round_robin` 依次绑定 6 个账户：A,B,C,A,B,C。
- `weighted` 前 6 次绑定的选中顺序：A、B、C、B、A、B；前 8 次后分布收敛为 A=2、B=4、C=2（比例 1:2:1）。计算方式是每一次选 `leases/weight` 最小的成员，平票按 priority。

## 7. 健康与失效

### 7.1 可用性公式

```text
pool_available   = pool.enabled
member_assignable = member.enabled
                    && proxy.enabled
                    && proxy 可解密/协议合法
                    && coalesce(proxy.pool_health_status, 'unknown') != 'dead'
assignable_members = 全部 member_assignable
pool_dispatchable = pool_available && assignable_members > 0
```

### 7.2 池可用性探测

- 池健康**不消费 J3a 的 vendor 矩阵**，只判断“代理是否可用”。探测复用现有代理解密、transport 和 jobs 任务生命周期，但目标固定为一个高额度 204 端点，不按 vendor 逐个探测，也不读取出口 IP/地区。
- 端点：首选 `https://cp.cloudflare.com/generate_204`（高额度、无响应体）。实施前必须从部署环境经一个已知可用代理验证该端点可达；若不可达，替换为经同样验证的等价 204 端点（例如 `https://connectivitycheck.gstatic.com/generate_204`），仍不新增 env。探测要求 HTTP 204；3xx/4xx/5xx、代理握手/认证失败、TLS/DNS/连接失败、超时均算失败。端点固定，不做多端点顺序兜底。
- 调度：新增独立 jobs 任务 `proxy_pool_health`（包名建议 `poolhealth`），复用 jobregistry 的任务 owner lease，不占用 J3a 的 vendor 矩阵预算。任务按 `pool_health_checked_at` 到期顺序分批扫描“至少被一个 enabled 池的 enabled 成员引用的 enabled 代理档案”，每代理目标间隔 60 秒；单次探测超时 5 秒；批次上限 128、并发 8，批次/并发不足时顺延到下一轮，单轮未完成不并发启动下一轮，不承诺固定完成时刻；owner lease 需覆盖单轮最坏时长（128/8×5s≈80s，建议 ≥120s）。调度依据 `pool_health_checked_at`：探测完成且结果成功投影时更新，任务取消/无结果/投影失败不更新；新代理或被重新启用/连接配置变更的代理可立即到期。
- 新增投影字段 `proxy_profiles.pool_health_status`、`pool_health_failure_streak`、`pool_health_checked_at`，由一次完成且成功投影的可用性结果计算：
  - `healthy`：最近一次可用性探测成功。
  - `degraded`：连续 1-2 次可用性探测失败，未达到 `dead` 阈值；可分配。
  - `dead`：连续 3 次可用性探测失败；第 3 次进入，成功一次恢复。
  - `unknown`：尚无有效结果（初始/存量 NULL）。
- 探测结果投影 PG 成功后，同步写 Redis 成员健康键（§7.4）；Redis 写失败不回滚 PG、不改变 streak，记录告警，并 best-effort 删除旧键让 gateway 回退 PG。删除也失败时旧键最多保留到下一次探测覆盖；期间按旧键处理，Redis 整体不可读时 gateway 回退 PG。
- `pool_health_failure_streak`：可用性探测失败 +1，成功清零；无结果、取消、任务失败、数据库/投影失败不递增也不重置；连接配置变更时 `pool_health_status='unknown'`、streak=0、`pool_health_checked_at=NULL`，并删除 Redis 成员健康键（§6.2）。
- 探测成功/失败只指“代理链路是否可用”：成功证明代理能完成一次 204 请求；失败指连接、超时、TLS/代理握手、认证或响应读取失败。任务取消、目标配置错误、无结果不算失败，不改变状态和 streak。
- `test_status` 保持现有 J3a vendor 矩阵诊断语义不变；直接代理仍只看 `enabled`，不消费 `pool_health_status`。J3a vendor 矩阵继续服务代理管理页，不参与池健康；其 9-target 预算问题属于独立诊断问题，不再是池健康 P0 阻塞。
- 池可用性探测只写 `pool_health_status/pool_health_failure_streak/pool_health_checked_at`，不写 `test_status/latency_ms/last_test_message/last_tested_at/outbound_ip/outbound_region`；J3a 的 vendor 矩阵调度和手动检测结果不受影响。
- 周期可用性探测改变池健康；手动代理检测只做展示（仍用现有 6 端点获取出口 IP/地区），不改变 `pool_health_status` 和 streak（避免一次手动单目标测试触发下架）。如后续要求手动探测参与，另立规则。
- `dead` 保持不可分配直到一次成功；`degraded` 可分配。池不按 vendor 限制，`healthy/degraded` 只代表代理链路可用性，不代表某个上游 vendor 可达或未被封禁；上游封禁无法由可用性探测识别，仍可能需要人工下架。
- 自动状态不修改 `proxy_profiles.enabled` 或 `proxy_pool_members.enabled`；`dead` 代理继续参与周期探测，成功一次恢复。人工停用代理档案后不探测，需人工重新启用；池成员人工停用不会被探测结果自动打开。
- 时间口径：每代理 60 秒一次，连续 3 次失败约 3 分钟进入 `dead`；实际受批次、并发、探测排队、投影和 gateway 缓存刷新影响，验收不断言固定秒数上界。恢复同样需要一次成功探测加投影/缓存刷新；旧快照与在途请求边界见 §7.4。
- 健康字段属于代理档案，同一代理加入多个池共享结果；页面分别显示“自动检测异常”和“手动停用”、连续失败次数、最近池健康检测时间及结果，不把自动异常写成手动关闭。

### 7.3 手动下架与恢复

- 管理员在池成员表上直接切换 `enabled`：下架停止新分配；已绑定账户由 gateway 在下一次请求解析时迁移。缓存失效和在途请求的边界见 §7.4。
- 下架不写账户状态、不触发账户冷却、不改 `accounts.schedulable`。
- 人工重新启用后还须满足代理启用和健康不是 `dead` 等条件，才重新进入可分配集合；不回迁已迁移账户。
- 代理档案的 `enabled` 切换是全局下架；语义同上，影响所有引用它的池。

### 7.4 传播时延

- 池/成员管理写入成功后发布 `TopicGatewayRuntime` 失效；同批补上代理档案写入失效。失效后新的读取重新装配，已在途请求不回收；失效传播或数据库故障不保证即时生效。
- 池可用性探测每代理 60 秒一次，结果写 PG `pool_health_*`（事实源）和 Redis 成员健康键（快速投影）：`juhe-ai:{<namespace>}:proxy-pool:member-health:<profile_id>`，值为 `healthy|degraded|dead`，TTL 5min，每次完成探测都刷新。jobs 不导入 gateway `inval`，不写 `topic:gateway_runtime_cache`；这是独立的 Redis 领域键，不是 gateway 缓存内部键。成员/池删除时 best-effort 删除相关键；失败靠 TTL 过期，gateway 只读当前成员键。
- 探测结果投影前在同一行锁内比对探测快照的连接配置（`host/port/username/password_encrypted`）与 `enabled`：探测在途期间发生连接变更或停用，则丢弃该结果，不覆盖重置后的 `unknown/streak`，也不写 Redis 旧状态；§6.2 的“连接变更重置”因此不会被在途旧结果回写。
- gateway 对池绑定账户在请求解析时批量 `MGET` 健康键：正常路径只读当前租约成员；当前成员 `dead` 时才读取池成员集合并对重分配候选批量 `MGET`。Redis 键存在时以其为准，`dead` 即排除；缺失/读取失败回退 PG `pool_health_status`（fresh 读取）；Redis 与 PG 都不可用则 fail-closed（`proxy_pool_unavailable`，不直连）。`degraded` 仍可分配。
- Redis `MGET` 使用短超时（建议 100ms）；超时/错误按缺失处理并回退 PG，不得让健康读取阻塞请求超过现有代理解析预算。
- 池绑定账户的代理 URL 可来自 60s 运行时缓存，但**健康不依赖缓存**：请求解析每请求对当前成员批量 `MGET` Redis 健康键；healthy/degraded 用缓存 URL，dead 时读 PG 租约/成员并在本次请求内 CAS 重分配，覆盖为新成员 URL。直接代理保持现有 60s 缓存和语义。这样 jobs 把节点标记为 `dead` 后，下一次请求即可见，不需要 jobs→gateway 事件。
- 代价：池绑定账户每请求增加一次 Redis `MGET`（当前成员，按 source account 批处理）；只有 `dead` 或 Redis 缺失/失败时才读 PG（health/lease），正常路径不增加 PG 查询；直接代理/非池账户不变。
- 当前单机规模下一次批量 `MGET` 可忽略；若后续 QPS 增大，可在进程内对健康键加 1s 本地缓存，或并入 `gatewayproxyhealth` 的桶读取批量；不改变 Redis 契约，1s 窗口需明确接受。
- 手动下架继续通过池/成员写入失效，且请求解析读取 PG 成员状态，下一请求即可见；C7-R 主要解决自动探测 `dead/恢复` 的传播。jobs 侧 `proxy_pool_health` 仍是唯一健康来源，gateway 不做独立健康轮询。

### 7.5 账户持久调度状态不变（硬约束）

- 池逻辑不得写 `accounts.status`、`cooldown_until`、`schedulable`、`priority`、`last_error_*`、健康检查失败计数等任何账户持久调度/健康字段。
- 账户恢复策略（冷却/探活/恢复/可调度）与租约修复是两层：租约修复只改 `account_proxy_leases`，不写账户状态；账户恢复策略仍按原逻辑运行。
- 池耗尽使账户在现有代理可用性判断中暂不可派发；恢复后按现有候选刷新重新可用。它不改变账户分组、路由配置、会话亲和或调度排序规则，也不将临时不可派发写成账户永久状态。
- 若请求路径实际调用解析器并得到 `proxy_pool_unavailable`，沿用现有代理不可用 attempt/终态（`proxy_unavailable`/`proxy:configured`）；池原因只写内部诊断 `pool_reason=proxy_pool_unavailable`。候选阶段被过滤时不产生 attempt；进入派发的按现有代理不可用路径处理。不新增池专用 URL、`ProxyPoolUnavailable` 字段或用户可见池码。
- 账户健康探针、余额、OAuth 等后台任务遇到解析阶段确认的池不可用时，应保留明确错误，不直连、不把该本地错误当作上游账户失败写入账户状态；各任务保留原有可重试机制，避免将池不可用计入 OAuth 终态停刷。实际出站后收到的上游错误仍遵循原策略（§7.6）。
- 只读后台任务（余额、OAuth 刷新/保活、探针、模型目录、xAI 用量）不会替空闲账户补租约；租约失效时按各自重试机制失败，待 gateway 请求解析修复后再恢复。这是“请求时修复、不后台扫描”的直接取舍。

### 7.6 上游错误与归因边界（C2 已裁决）

- 用户裁决 C2 A：实际请求失败通常无法可靠区分账户、代理出口与上游原因；跨成员复测成功或失败都不能证明责任归属。本期不做自动跨成员复测归因，不增加成员隔离信号或延迟账户处罚机制。接受“实际出站错误仍可能触发现有账户处罚”这一后果。
- 本地解析阶段已确定的池停用、无成员、租约缺失等 `proxy_pool_unavailable` 由池处理，按 §7.5 不作为账户失败。代理连接阶段若现有链路能明确识别代理准备或握手错误，沿用既有代理错误分类与请求内避让；本设计不扩大可归因范围，不据单次请求失败更新池健康或立即改租约。
- 请求或账户探测实际出站后的 HTTP、transport 和协议错误，沿用对应入口当前账户错误策略和代理桶行为；不因绑定池而豁免或新增账户处罚，也不据单次失败自动下架成员。现有规则可能冷却或禁用账户。
- 池可用性探测只证明代理链路可用，不能识别上游按 IP 封禁；`dead` 仅表达连续 3 次可用性探测失败，不证明代理为上游封禁的根因。管理员可按诊断信息手动下架成员。
- 验收必须分别覆盖本地池不可用不写账户状态，以及真实上游错误仍按既有策略生效；不承诺“所有由代理间接引起的失败都不影响账户”。

### 7.7 全部成员不可用

- 解析器遇到池停用、无成员、全部不可分配或租约不可用时返回 `proxy_pool_unavailable`，不得直连。
- 网关沿用现有代理不可用 attempt/终态：进入派发的账户产生与直接代理不可用一致的 attempt（`proxy_unavailable`/`proxy:configured`），池原因写内部 `pool_reason=proxy_pool_unavailable`；候选阶段被过滤时不产生 attempt。不新增 `proxy:pool` URL、`ProxyPoolUnavailable` 字段或用户可见池专用 code。
- 该本地不可用状态不会写账户冷却或禁用；其他候选与最终响应按当前路由类型处理。
- 池与成员恢复后，原租约仍可用时随缓存刷新恢复；租约缺失或失效时由 gateway 在下一次请求解析时按 §6.6 修复。修复和缓存刷新完成前请求仍可能失败，不需要人工重置账户。

## 8. API、权限与绑定写入

### 8.1 管理面代理池 CRUD

| 方法 | 路径 | 语义 |
| --- | --- | --- |
| `GET` | `/__aisys__/api/proxy-pools` | 分页 `page/pageSize/keyword`，关键词只按池名精确/前缀；返回 `id/name/description/strategy/enabled/memberCount/assignableMemberCount/leaseCount/updatedAt` |
| `GET` | `/__aisys__/api/proxy-pools/{id}` | 详情：池字段 + 成员（`proxyProfileId/name/type/enabled/testStatus/lastTestedAt/latencyMs/poolHealthStatus/poolHealthFailureStreak/poolHealthCheckedAt/priority/weight/memberEnabled/leaseCount/assignable`） |
| `POST` | `/__aisys__/api/proxy-pools` | 创建；`name/description/strategy/enabled/members`；严格白名单；`MutationGuard` key `proxy-pools.create` |
| `PATCH` | `/__aisys__/api/proxy-pools/{id}` | 局部更新；必须带 `expectedUpdatedAt`；`members` 出现即完整替换成员集合；成员增删/改权重/改启停与池更新同一事务 |
| `DELETE` | `/__aisys__/api/proxy-pools/{id}` | 删除；有未删除账户绑定返回 409；同一事务删租约/成员/池 |
| `GET` | `/__aisys__/api/proxy-pools/member-options` | 管理员成员选择器：`keyword/limit/selectedIds`，返回 `id/name/type/enabled/testStatus`，不返回 host/port/用户名/密码 |

- 池成员写入校验：池存在；成员代理存在；成员不重复；成员数 ≤50；`weight` 1..100；`priority` 归一；不能把池自身或不存在对象作为成员（成员只能是单代理）。
- 成员集合完整替换时，保留交集成员行并原地更新属性，只对差集执行增删，保留成员的租约不变。priority 采用两阶段更新（先整体移到不冲突的临时值再写新值），避免 `UNIQUE(pool_id, priority)` 的瞬时冲突；删除成员后剩余 priority 归一为连续 `0..n-1`。
- `member-options` 必须在 `/{id}` 之前注册或使用不与其冲突的路径；否则会被 `{id}` 捕获成池 ID。
- 池更新 CAS 失败返回 409 `proxy_pool_revision_conflict`；`updated_at` 用文本时间戳，沿用代理/分组的实现口径。
- 池写操作日志记录池名、策略、成员变更摘要（不记录代理密码/host 等敏感细节）。

### 8.2 账户下拉（同一个下拉）

扩展现有 `GET /__aisys__/api/proxies/options`：

- 新增 `kinds` 查询，缺省 `profile`（保持现有调用方行为）；账户表单传 `kinds=profile,pool`。
- 新增 `selectedPoolIds`（裸重复键或 bracket 数组键），与 `selectedIds` 分开；`selectedIds` 只匹配代理档案，`selectedPoolIds` 只匹配池，均最多 20 个、排序去重规则一致。
- 响应项新增 `kind`：`profile` 或 `pool`。`profile` 项保持 `id/name/type/enabled`；`pool` 项返回 `id/name/kind/enabled/memberCount/assignableMemberCount`，不返回成员、host、端口、用户名、密码、出口 IP 或检测明细。
- `type` 对 `pool` 项不返回（或返回空），前端用 `kind` 分组和标签；不要用 `type='pool'` 混入代理协议值域。
- 现有只传 `keyword/limit/selectedIds` 的调用方行为不变；池选项只在显式请求 `kinds=pool` 时返回。

### 8.3 账户写入

- `POST /accounts`、`PATCH /accounts/{id}` 新增 `proxyPoolId`（string 或 null），与 `proxyProfileId` 互斥：
  - 两者同时非空 → 400 `proxy_target_conflict`；
  - 创建：缺省 = 无代理；`null` = 无代理；
  - PATCH：缺省 = 不修改；`null` = 清除该目标；同时 `proxyProfileId:null, proxyPoolId:null` = 解除绑定；
  - `proxyPoolId` 非空：池必须存在、enabled、至少有一个 `member.enabled && proxy.enabled` 成员，否则 400 `proxy_pool_empty`/`proxy_pool_disabled`；健康不可分配不阻止绑定。
- 写入同一事务：账户行 + 租约（创建/改绑）；解绑时删除租约。
- 账户详情/高级详情：返回配置绑定 `proxyProfileId` 和 `proxyPoolId`，以及 `proxyPoolName/strategy/memberCount` 和有效成员摘要；编辑表单必须回填配置绑定，不能回填有效成员（否则保存会把池改成直接代理）。
- 账户列表：见 §8.5 字段契约；`proxyProfileId` 保持“配置的直接代理”，池绑定时为 null；新增 `proxyPoolId/proxyPoolName/proxyTargetType/proxyMemberProfileId/proxyMemberProfileName`。
- 克隆：复制 `proxyPoolId`（或 `proxyProfileId`），不复制租约；新账户按策略分配（C9 A）。克隆上下文返回池名供前端展示。
- 授权实例：来源账户池覆盖；实例自身不可写池；实例详情只读展示。
- 手工测试草稿：草稿加密 payload 增加 `proxyPoolId`；执行时临时分配一个成员，不固化；本地解析不可用按 `proxy_pool_unavailable` 归类，不写账户状态。实际出站错误按该测试入口既有语义处理。
- OAuth 建号：`allowedKeys` 增加 `proxyPoolId`；建号前临时分配成员用于 token 交换；账户创建时固化同一成员为租约。重新授权/轮换/自动刷新/jobs 保活使用账户已固化租约成员；租约不可用时失败，不在 token 刷新中途换 IP、不直连。
- OAuth 自动刷新路径（`oauthmgmt/auto_refresh.go:81-84`）和 jobs 刷新/保活（`oauthrefresh/refresh.go:637`、`keepalive.go:292`、`store.go:105-107`）当前直读 `current.ProxyProfileID`；必须改为有效目标解析，否则池绑定账户会 400 或直连。OAuth 建号写路径 `oauthmgmt/store.go` 也要接受并固化池租约。

### 8.4 批量编辑、导入与导出

- 批量编辑：`proxyPoolId` 加入可批量字段白名单；与 `proxyProfileId` 互斥；三态（不勾选/勾选 null/勾选值）与现有代理字段一致；每个目标账户独立分配租约。批量接口仍需 owner/权限校验，不能绕过单账户规则。
- 导入：
  - 新增顶层 `proxyPools`（可选，第一版只读引用，不创建）与账户字段 `proxyPoolRef`/`proxyPoolId`；
  - `proxyRef`/`proxyProfileId` 与 `proxyPoolRef`/`proxyPoolId` 互斥；
  - 普通用户只能引用已存在且 enabled 的池；管理员同样不自动建池（第一版）；
  - 引用不存在/停用池 → 该账户导入失败并给出明确原因，不静默丢绑、不直连。
- 导出：
  - 账户绑池时写 `proxyPoolRef: "proxy-pool-<id>"`，并在顶层 `proxyPools` 写池名/策略/成员引用（成员用 `proxyRef` 或 `proxyProfileId`），不重复导出成员密码；`proxyPools` 段用于文档可读性和一致性校验，第一版导入不据此创建池，目标环境缺失即拒绝；
  - 第一版导入支持 `proxyPools` 的“已存在则复用、缺失则拒绝”，不做自动创建；如果审核要求完整 round-trip，再升级为管理员可创建（§15 C3）。
- 现有 `proxies` 自动创建逻辑不变；池成员引用的代理如果由导入自动创建，必须在池解析前完成，顺序固定为 proxies → proxyPools → accounts。

### 8.5 账户列表字段契约

| 字段 | direct | pool |
| --- | --- | --- |
| `proxyTargetType` | `"profile"` | `"pool"` |
| `proxyProfileId/Name/Type/Enabled` | 配置代理 | null |
| `proxyPoolId/Name/Enabled` | null | 配置池 |
| `proxyMemberProfileId/Name/Type/Enabled` | null | 当前租约成员（无租约时 null） |
| `proxyPoolAssignableMemberCount` | null | 池当前可分配成员数；用于区分“待分配/待切换/无可用成员” |
| `proxyProfileUnavailable` | 现有语义 | 有效目标不可用（池停用/无成员/租约不可用） |
| `proxyProfileErrorMessage` | 现有语义 | 池级原因（含池名） |

- 字段名 `proxyProfileUnavailable` 保留是为了兼容现有前端/消费方；语义在池绑定下扩展为“有效代理目标不可用”，在 §14 文档中写明。新增 `proxyTargetType` 作为判别字段。
- 无租约但池存在可分配成员时，`proxyProfileUnavailable=false`，列表显示“待分配”，`proxyProfileErrorMessage` 为空；只有池停用、无任何可分配成员或已有租约成员不可用时才为 true。这样“待分配”和“无可用成员”不会共用同一个标红状态。
- `proxyPoolAssignableMemberCount` 必须随账户列表/详情返回，并进入可用性投影 payload；前端用它区分“待分配”（无租约且计数>0）、“待切换”（有租约但成员不可用且计数>0）和“无可用成员”（计数=0 或池停用）。不要只靠 `proxyProfileUnavailable` 布尔值推断。
- `proxyProfileErrorMessage` 必须区分“当前成员不可用、仍有其他可分配成员”和“池无可用成员”：前者提示下次请求会重新分配，后者提示池级不可用；不能把两种情况都写成“无可用成员”。
- **可用性投影确实包含代理字段**：`circuitstore/listavailability_rows.go` 的 payload 含 `proxyProfile*`，`proxy_profiles` dirty 触发器已在 2026-10-17 移除。因此不能只改 live join：必须把 `proxyTargetType/proxyPoolId/proxyPoolName/proxyPoolAssignableMemberCount/proxyMember*` 加入投影构建 SQL 与 payload，并按 §4.5 对池、成员、租约和代理展示列标脏；健康状态只在进入或离开 `dead` 时标脏相关池的所有绑定账户，不对 `test_status/latency/last_tested_at/pool_health_checked_at` 标脏。
- 账户列表 API 仍以 live 读取为准；投影是 jobs 侧可用性消费，两者必须同口径。验收含“改池名/换成员/下架成员后投影 payload 在下一轮刷新变为新值”。

## 10. 运行态、缓存与可观测性

### 10.1 网关运行时装配

1. 候选查询同时取 `accounts.proxy_profile_id/proxy_pool_id` 和 source 侧同名列。
2. 对池绑定候选按当前成员批量 `MGET` Redis 成员健康键（§7.4）：`healthy/degraded` 使用缓存中的有效成员/URL；`dead` 进入重分配；缺失/读取失败时 fresh 读取 PG `pool_health_status`，PG `healthy/degraded/unknown` 使用缓存 URL，PG `dead` 进入重分配，PG 不可用则 `proxy_pool_unavailable`。
3. Redis `dead`、Redis 缺失且 PG `dead`、或租约缺失时，批量读取 `account_proxy_leases`（按 source account），按 §6.6 在本次请求内重分配并 CAS。
4. 新成员 URL 批量解密（或使用由成员变更驱动的短期 URL 缓存）；直接代理沿用现有 60s 缓存。
5. 写入候选：`ProxyProfileID`=有效成员、`ProxyURL`、`ProxyPoolID`、`ProxyMemberProfileID`、`ProxyProfileUnavailable`。
6. 直连/单代理路径保持原有分支和错误语义。
7. 池绑定候选在 dispatch 准备阶段执行最终覆盖，写回本次请求的 `ProxyProfileID/ProxyURL/ProxyPoolID/ProxyMemberProfileID`；运行时缓存不是池绑定健康的权威来源。

上述装配由请求路径触发；池绑定账户的健康按请求读取 Redis（URL 可来自缓存，`dead` 时覆盖并重分配），直接代理仍按现有缓存生命周期装配。不新增对空闲账户的批量预修复；不得为了补租约遍历与本次请求无关的账户。

### 10.2 缓存失效

- 池/成员/池启停写入：`InvalidateGatewayRuntime("proxy_pool_updated")`。
- 代理档案写入：同批补上 `InvalidateGatewayRuntime("proxy_profile_updated")`，修正文档与代码不一致。
- 账户绑定/解绑：沿用现有账户写失效。
- 请求内租约重分配成功后，更新/失效本进程该 API key 的运行时缓存条目（本地操作，不跨进程）；后续请求不再用旧成员 URL。多实例下其他 gateway 由现有账户/租约写失效或下一次 PG 读取收敛，v1 单实例不额外处理。
- 池可用性探测健康：jobs 写 PG + Redis 成员健康键；gateway 请求解析时批量 `MGET`（C7-R），`dead` 即排除并重分配。池绑定账户的 URL 可缓存，但健康门每请求读 Redis、`dead` 时覆盖缓存 URL；直接代理保持 60s。手动下架继续通过池/成员写入失效；在途请求不回收，见 §7.4。
- 可用性投影：池/成员/租约/代理展示列及健康跨 `dead` 边界的变更按 §4.5 标脏，不对检测时间或延迟的高频变化标脏。
- 代理桶：有效成员 `ProxyProfileID` 会进入既有 `gatewayproxyhealth` 桶键与避让；池不可用沿用现有账户可用性和路由处理。
- 不新增 Redis 健康缓存；租约与健康均从 PG 读取（批量、低频）。

### 10.3 余额身份

- 余额查询身份摘要当前包含 `proxyProfileId`，且调用点不止一处：`accountbalance/input_digest.go:45-52`、`models.go:45,54-55,78`、`accountsbalance/balance.go:80-110`（`COALESCE(proxy_profile_id,'')`，含 `LoadBalanceInputDigests`）、`accounts/patch.go:2496-2518`（`balanceIdentityValue`）、`shared/platform/accountbalance/multi_key.go:45-49`，以及 gateway `accounts/balance_subdomain_bridge.go` 的余额读桥接。
- 池绑定账户的身份摘要改为包含 `proxyPoolId` + **有效成员档案 ID**；租约迁移视为不同输入，重置刷新代次。上述所有读写执行调用点必须同批改，不能只改摘要函数。
- 无租约/池不可用时余额查询失败并记录原因，不直连、不用旧成员结果写回。

### 10.4 审计与日志

- `audit_log_attempts.proxy_url` 继续沿用现有 attempt 记录语义；若既有路由路径产生池解析失败 attempt，`error_code`/`proxy_url` 与直接代理不可用一致（`proxy_unavailable`/`proxy:configured`），池原因写入内部 `pool_reason=proxy_pool_unavailable`；不新增 `proxy:pool` URL、用户可见池码或 audit 列。
- 第一版不扩展 `audit_log_attempts` schema；实际出站仍通过现有 `proxy_url` 记录解析后的成员代理。
- 现有 `proxy_url` 含凭据的既有契约不变。
- 操作日志记录池 CRUD/成员变更；不记录代理密码、host、端口。

### 10.5 可观测性

- 池详情/列表展示成员租约数、可分配数、池健康状态、连续失败次数、最近池健康检测时间；不新增 Prometheus 指标为第一版要求。
- 请求解析触发的租约重分配和池不可用写结构化日志：账户 ID、池 ID、旧/新成员、`assignment_reason`、generation、`pool_reason`、`health_source`（redis/pg）；Redis 健康读取失败/回退 PG 也记录。attempt 消息沿用现有 `proxy_unavailable`，不新增审计 schema。
- 账户列表 tooltip 展示池级原因，便于用户判断是池空还是成员不可用。
- 验收 SQL 包括：池成员租约分布、租约与配置一致性、无“池绑定但直连”的审计行。

### 12.2 静态扫描门

- 非测试 Go 代码中，除共享解析器、账户写入/列表/导入、代理管理、J3a 探测、池可用性探测外，不得新增 `proxy_profile_id`/`proxy_profiles` 直读；现有 15 个入口逐一改为调用解析器。
- 禁止“池绑定但 `ProxyURL` 为空”的直连路径：静态检查关键入口在 `proxy_pool_id` 非空时必须返回不可用或解析成员。
- schema golden/语句计数/digest 与 rehearsal 清单必须同改。
- 前端不得把 `profile:`/`pool:` 复合值直接提交给账户 API；回归脚本断言 payload 只含裸 id。
- 账户列表字段契约由前端类型 + 后端 golden 响应共同钉住。

### 12.3 测试层次

- 单元：分配算法（轮询/权重/平票/权重 1..100/无成员）、健康状态边界、错误码映射、URL 归一。
- PG 集成：schema/约束/CAS/删除守卫/租约一致性/触发器列集。
- 网关：候选装配、直接代理不变、池解析、请求时租约修复、实例覆盖、池不可用沿用现有路由语义、本地池不可用不写账户状态，以及真实出站错误沿用现有策略。
- jobs/shared：余额、探针、OAuth、xAI、modelcheckowner、J3a 对池的 fail-closed；新增 `proxy_pool_health` 任务的 204 成功/超时/取消/投影失败、60s 调度与 streak 边界。
- 前端：类型检查、ProxySelect/标签缓存、账户表单/批量/导入、列表展示、回归脚本。
- 端到端：真实 dev PG/Redis，池 CRUD → 账户绑池 → 派发 → 成员下架 → 下次请求迁移；按 `AGENTS.md` 本地管理页测试规则执行。

### 12.4 人工验收

- 代理管理页创建池、加成员、调权重、下架成员、删除守卫。
- 账户创建/编辑/批量/克隆/导入选择池；列表显示池+成员；移动端一致。
- 成员停用/代理停用/池停用导致账户暂不可派发时，不因该本地不可用写账户持久状态；实际出站错误仍按既有策略处理。
- 余额、OAuth 刷新、账户测试、媒体任务、模型目录刷新均走同一成员；池不可用时全部 fail-closed。

## 13. 实施分期

P0、P1 是开发顺序，构成同一个发布批次；在所有入口收口和对应验收完成前不得对外启用池绑定。

### 13.1 P0：数据与核心解析

- schema revision 18、三表 + 序列、`accounts.proxy_pool_id`、`pool_health_status`、索引、投影/dirty 触发器、golden/演练清单、`BusinessSchemaVersion` v23。
- 共享解析器与 15 个入口收口；直接代理行为不变；池绑定 fail-closed；两列冲突显式失败。
- 代理池 CRUD/成员 API（含 CAS、成员完整替换、删除守卫）。
- 租约分配、请求解析时失效重分配、并发 CAS、池/成员/账户写入锁序。
- 实现池可用性探测与 3 次失败下架/成功恢复；新增 `pool_health_status`/`pool_health_failure_streak`/`pool_health_checked_at`；NULL 按 unknown，不从旧 `test_status` 推断 dead；池不可用沿用现有代理不可用 attempt/终态（A）。
- 可用性探测使用固定 204 端点、单次 5s 超时、每代理 60s 一次，由独立 jobs 任务执行；实施前必须从部署环境经一个已知可用代理预检端点可达，不可达则替换为等价 204 端点并记录证据；不按 vendor 矩阵、不需要调整 J3a 预算。
- 实现 C7-R：jobs 探测后写 PG + Redis 成员健康键（TTL 5min）；gateway 请求解析批量 `MGET`，`dead` 即重分配，Redis 缺失/失败回退 PG；池绑定账户健康门每请求读 Redis、`dead` 时覆盖缓存 URL，直接代理保持 60s。
- 账户创建/编辑/批量/克隆/导入导出的池字段与互斥校验；账户列表/详情字段契约。
- 按已裁决范围接线：C5 成员上限 50/权重 1..100；C8 OAuth 建号支持池；C10 媒体任务修正实例 source 覆盖；C3 导入只引用已存在池。
- 验收核心数据、分配、锁序、请求时恢复和本地错误分类；全入口与界面验收在 P1 完成后共同作为发布门。

### 13.2 P1：管理页与发布验收

- 代理池管理页标签页、成员选择器、账户表单/批量/列表/移动端。
- 统一 options、OAuth 建号及管理页面接线；核验 P0 的自动刷新、账户测试、余额、媒体、探针、模型目录、xAI 等全入口收口。
- 池成员健康投影消费、手动下架、池停用/恢复、池写失效、代理写失效修正、Redis 健康键与请求时重分配生效（无 jobs→gateway 失效接线）、池绑定账户健康门每请求读 Redis/`dead` 时覆盖缓存 URL、投影 dirty 生效。
- Mockdata 池种子与前端回归脚本。
- 发布验收：§12 全部适用 fixture，包括全入口 fail-closed、本地池错误与真实上游错误边界、投影和前端回归；按最终裁决调整对应 fixture。

### 13.3 后续可能的增强

- 本版 C7-R 使用 Redis 成员健康键 + 请求时读取；若未来要减少每请求 Redis/PG 读取，可评估本地短缓存或批量聚合，不改变“不直接 jobs→gateway 事件”的边界。
- 可用性探测端点/超时可配置化、导入自动创建池、显式重平衡操作。

### 13.4 停止条件与回滚

- 任一 P0 入口仍存在“池绑定可直连”路径 → 停止，不得发布。
- schema 升级 dry-run blocked、golden 不一致、演练清单缺失 → 停止。
- 回滚按 §11.4：先处理并核验全部池绑定，再按经演练的兼容路径回退镜像或恢复备份。

推荐值不是既定结论。C1（连续 3 次可用性探测失败下架、一次成功恢复）、C2（A）、池不按 vendor 限制、池不可用 attempt（A）、C3（只引用已存在池）、C5（50/1..100）、C6（A 全局可见）、C7（C7-R Redis 健康键、gateway 请求时读取）、C8（OAuth 支持池）、C9（A 不复制租约成员）、C10（本期修正媒体实例覆盖）已由用户裁决；另已裁决：租约失效修复只在 gateway 请求解析时发生，不新增后台扫描。全部 C 项已裁决。

| 编号 | 问题 | 选项 | 推荐 | 影响 |
| --- | --- | --- | --- | --- |
| C1 | 池成员分配是否消费健康投影 `pool_health_status`？ | 已裁决：连续 3 次可用性探测失败下架；一次成功恢复；不由业务请求失败驱动 | 已确认 | 池健康只测代理是否可用，不按 vendor 矩阵；固定 204 端点、单次 5s 超时、每代理 60s 一次，3 次约 3 分钟 + 排队，见 §7.2 |
| C2 | 实际出站失败是否按跨成员复测归因？ | 已裁决 A：不做跨成员归因；本地池不可用不写账户状态；实际出站错误按现有账户策略，可能处罚 | 已确认 | 不承诺识别代理或上游封禁；封禁可能先冷却账户 |
