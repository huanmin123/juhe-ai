> 术语边界：本文“代理池”指**应用层上游代理成员池**，成员是 `proxy_profiles` 单代理档案；不是 [公开接口独立进程设计](公开接口独立进程设计.md) 中已退役的反向代理连接池，也不是 `docs/deploy/proxy/` 的外部 sing-box 节点池。

## 1. 裁决摘要

1. 代理域新增 `proxy_pools`、`proxy_pool_members`、`account_proxy_leases` 三张表；代理池是服务器级全局资源，由管理员维护，单层、不嵌套。
2. 账户代理绑定升级为“单代理 或 代理池”二选一，共用同一个下拉；存量 `accounts.proxy_profile_id` 语义和行为不变。
3. 账户绑池后按**账户级粘性租约**固定一个成员；轮询/权重只决定新绑定和失效重分配，不按请求换 IP。
4. 池成员的启停、健康和下架仅决定出口选择；**池逻辑不得写入账户调度或健康字段，不改变分组和路由候选**。实际请求或账户探测收到的上游错误继续执行现有账户错误策略，可能改变账户状态（§7.6）。
5. 池内无可用成员时，请求按代理不可用失败（attempt 级），账户仍留在调度候选；不静默直连。
6. 直接代理（`proxy_profile_id`）的校验、行为、错误语义完全不变；新增的 `pool_health_status` 只对池成员分配生效，`test_status` 仍是直接代理的运维参考，不改变直接代理的调度语义。
7. 本设计不改变 `proxy_profiles` 的全局可见性和 `system_account_id` 写入归属；T117d 对代理名称作用域的裁决不受本文预占，代理池跟随其最终口径。

## 2. 目标与非目标

### 2.1 目标

- 支持大量账户共享一组代理，按权重或轮询把账户分散到不同出口。
- 账户出口 IP 稳定：同一账户固定一个池成员，不因请求、进程重启或权重调整漂移。
- 成员不可用时停止新分配，受影响账户由 gateway 恢复租约；池逻辑不修改账户调度状态。
- 把现有全链路账户代理解析收口到同一契约，任何账户出站路径都不得绕过代理池直连。
- 管理员可观测：每个池成员的租约数、健康状态、最近检测；账户列表显示池名和当前成员。

### 2.2 非目标

- 不做每请求轮换，不做按请求在池内选成员。
- 不做池套池、跨 owner/跨授权池、池级配额、池级并发上限。
- 不做自动重平衡：改权重、增删成员不主动打散存量租约。
- 不做跨成员复测归因或上游封禁识别；不把单次上游 HTTP 失败直接判为代理坏。
- 不改变账户调度、路由策略、分组、会话亲和、IP 回避和代理桶语义。
- 第一版不做导入时自动创建代理池，只引用已存在的池（见 §8.4）。
- 不改 `proxy_profiles` 的 owner 可见性，不解决 T117d 的历史归属问题。

## 3. 现状事实与差距

> 行号取自 2026-11-05 当前工作区（有未提交改动）；代码变动后以函数/结构名为准。复审已抽查关键引用在当前工作区仍可定位。

### 3.1 单代理绑定事实

- `proxy_profiles` 是单代理档案：`id/system_account_id/name/type/host/port/username/password_encrypted/enabled/test_status/latency_ms/outbound_ip/outbound_region/last_test_*/created_at/updated_at`，没有分组、成员、权重或租约结构（`backend-go/projects/maintenance/internal/schema/pg_schema_business_tables.go:208-227`）。
- `accounts.proxy_profile_id` 是单值外键，一个账户最多绑一个代理（同文件 `:609,660`）；`idx_accounts_proxy_profile` 支撑 `(proxy_profile_id, id)`（`pg_schema_business_indexes.go:275`）。
- 账户创建、编辑、批量编辑和导入都按“目标代理必须存在且 enabled”校验；批量编辑额外带 owner 作用域，其余路径不带（`accounts/write.go:821-832`、`patch.go:737-769`、`accountstransfer/batch.go:857-884`、`accountstransfer/import.go:1571-1621`）。
- 账户列表和授权实例详情通过 `LEFT JOIN proxy_profiles` 返回 `proxyProfileId/Name/Type/Enabled/Unavailable/ErrorMessage`；`proxyProfileUnavailable` 的判定是“未解析或 enabled 非 true”（`accounts/list.go:660-695,741-753,1214-1261`、`m11_reads.go:413,424`）。
- 网关运行时按批收集有效代理 ID，单条 SQL 读取代理行并解密 URL，再写入候选账户的 `ProxyProfileID/ProxyURL`；`socks5` 与 `socks5h` 统一渲染为 `socks5h://`（`cmd/juhe-ai-gateway/chain_accounts.go:531-540,1846-1932`、`chain_accounts_secret.go:578-595`）。
- 运行时缓存把解密后的 `ProxyURL` 明文保存 60s revalidate / 2min retain（`internal/gatewayruntimecache/service.go:24-33`、`types.go:359-362`）；账户改绑会失效运行时缓存，代理档案 PATCH/DELETE 目前不会（`internal/accounts/invalidation.go:44-67,149`；`internal/proxyprofiles` 包没有 invalidator 引用）。

### 3.2 代理健康与探测事实

- jobs 的 J3a 是当前唯一的周期代理探测：`enabled` 代理 × 已启用供应商默认地址，默认 `interval=5s`、每轮最多 `batch=512`，按“从未测试 → 最久未测”滚动覆盖（`jobs/internal/proxylatency/config.go:14-31`、`direct_input_reader.go:366-386`、`runner.go:873-883`）。
- 投影只写 `test_status/latency_ms/last_test_message/last_tested_at`；手动检测额外写 `outbound_ip/outbound_region`（`result_projector.go:541-575`、`:348-394`）。
- `test_status` 当前是运维参考，**不是派单门**：直接代理只要 `enabled` 就会被使用（`核心功能设计.md:533`、`docs/deploy/proxy/sing-box网络代理部署指南.md` §9.6、`AI账户错误语义与状态变更边界.md:46/145`）。
- J3a 的 `OverallStatus` 是跨全部已启用 vendor 目标的聚合：任一 target `failed` 即整体 `failed`，全部 passed 才 passed（`proxylatency/types.go:141-164`）。因此单个 vendor 端点不可达就会把整个代理标 failed，池若直接用整体状态排除会过度保守。
- `test_status` 变化不会触发 gateway 运行时缓存失效；J3a 在 jobs 进程，gateway 外层运行时缓存采用 60s revalidate / 2min last-good retain（`gatewayruntimecache/service.go:24-33`）。这是缓存策略，不保证数据库持续故障时两分钟内获得新状态。
- `gatewayproxyhealth` 的按代理桶键**已接线**：`gatewaydispatch/preparation.go:610` 调 `ProxyHealth.OrderAsync`，`cmd/juhe-ai-gateway/chain_wiring_w2c.go:684-699` 装配；桶键为 `proxy:profile:<id>` / `proxy:url:<sha256>`（`gatewayproxyhealth/proxyhealth.go:306-351`），参与上游桶排序/避让。池绑定时有效成员会成为桶键，本设计必须显式处理该交互。
- 代理写入不会触发运行时缓存失效，与 `核心功能设计.md:511`“创建、更新和删除成功后发布 gateway runtime cache 失效”的现行文档表述不一致；实施时必须裁决并回正文档或代码。
- `核心功能设计.md:533` 写“后台刷新固定每 60 秒最多检测 20 个启用代理”，与当前 Go J3a 的 5s/512 不一致；实施时一并回正。
- 账户可用性投影 **确实包含代理展示字段**：`jobs/internal/circuitstore/listavailability_rows.go:140-200,551-566` 选取并写入 `proxyProfile*`，而 `proxy_profiles` 的 dirty 触发器已于 2026-10-17 移除（`pg_schema_business_tables.go:2167-2172`）。池/成员/租约变化若只改 live join，会让该投影消费者看到陈旧代理信息；本设计必须补投影 dirty 口径（§8.5）。

### 3.4 现存不一致（实施时必须一并收口）

1. **静默直连**：余额手动刷新在代理档案不存在时返回 `(nil,nil)`，会直连；共享直读在 `proxyRequired` 为真且无绑定/停用时会报错，仅在未要求代理时允许直连（`compose_account_balance_refresh.go:163-165`、`accountbalance/direct_input_reader.go:222-231`）。余额手动/周期查询均未检查 `proxy_profiles.enabled`（`compose_account_balance_refresh.go:150-160`、`worker_balance_detect.go:750-758`），停用代理仍会被使用。池绑定必须始终视为 proxyRequired：租约缺失/成员不可用一律失败，不得直连。
2. **媒体任务不读实例 source 覆盖**：`chain_media_video.go:910-940` 只读账户本行 `proxy_profile_id`；授权实例行该字段为 NULL，媒体任务会直连。现有契约已承认该差异（`接口契约与权限矩阵.md:739`），但池绑定会让“同一账户不同入口出口不同”更明显。本设计要求统一到有效目标解析，媒体任务的现有差异必须显式修正或保留并写入验收。
3. **代理写入不失效运行时缓存**：与 `核心功能设计.md:511` 的现行表述冲突；池成员/池启停变更如果不失效，缓存可能继续使用旧成员，具体边界见 §7.4。
4. **`test_status` 语义扩大**：本设计要求池成员分配消费健康投影（见 §7.2），这是对“检测状态只是运维参考、不是派单门”的局部改写；直接代理不消费。实施时必须同步 §14 文档。
5. **审计代理 URL 含凭据**：`audit_log_attempts.proxy_url` 与读路径只 trim，含 `user:password`（`gatewayusage/audit_capture.go:705,858`、`gatewayusage/snapshots.go:283-287`、`logreads/audit_reads.go:320-343`）。本设计不改变该既有契约，但新增池/成员字段时不得扩大敏感面。
6. **可用性投影含代理字段且 dirty 触发器已删**：`listavailability_rows.go:140-200,551-566` 的 payload 含 `proxyProfile*`，`proxy_profiles` dirty 触发器已于 2026-10-17 移除；池/成员/租约变化若不补 dirty 口径，投影消费者会长期显示旧成员。§8.5 给出处理方案。
7. **代理桶已接线**：`preparation.go:610` + `chain_wiring_w2c.go:684-699` 已启用按代理/上游桶的健康排序与避让，桶键包含 `proxy:profile:<id>`/`proxy:url:<hash>`。池绑定把 `ProxyProfileID` 映射为有效成员后会自然进入该桶；这是既有机制，不是本设计新增，但必须纳入验收（§10.2/§12.1）。
8. **schemaReady/启动检查未含池**：`shared/contracts/business_schema.go:92,105-106` 的 `BusinessSchemaVersion` 仍为 v22，`accounts` 必填列无 `proxy_pool_id`、必填表无池表；`jobs/cmd/juhe-ai-jobs/worker_business_db.go:116` 同样。池 DDL 必须同步升 `BusinessSchemaVersion`（建议 v23）并加入检查，否则旧库可能通过启动门后才在查询时报错。
9. **余额身份摘要多处直读**：除 `accountbalance/input_digest.go`/`models.go` 外，`accountsbalance/balance.go:80-110`、`accounts/patch.go:2496-2518`、`shared/platform/accountbalance/multi_key.go:45-49` 都只把 `proxy_profile_id` 纳入摘要；池绑定若不改这些点，租约迁移后旧余额快照仍会被当成当前（§10.3）。

### 3.5 差距结论

代理池不是“代理管理页多一个列表”，而是**出站解析契约 + 数据模型 + 粘性租约 + 成员健康 + 全链路收口**。只做管理页和主派发链会导致余额、OAuth、探针、媒体、模型目录等路径绕过池，出口身份不确定。

## 4. 目标数据模型

### 4.1 `proxy_pools`

```text
id                 TEXT PRIMARY KEY
system_account_id  TEXT NOT NULL              -- 写归属，沿用 proxy_profiles 口径；读取面仍为全局
name               TEXT NOT NULL
description        TEXT
strategy           TEXT NOT NULL              -- 'round_robin' | 'weighted'
enabled            BOOLEAN NOT NULL DEFAULT true
created_at         TIMESTAMPTZ NOT NULL
updated_at         TIMESTAMPTZ NOT NULL
```

- 名称全局唯一，沿用 `proxy_profiles` 的 `name` 唯一口径（`pg_schema_business_indexes.go:977`）；T117d 若改为租户内唯一，池同步改。
- `strategy` 首版只允许 `round_robin` 和 `weighted`；不做 `failover`。
- 池创建后 `strategy` 可改，但改策略不重排存量租约（§6.5）。

### 4.2 `proxy_pool_members`

```text
pool_id             TEXT NOT NULL REFERENCES proxy_pools(id) ON DELETE RESTRICT
proxy_profile_id    TEXT NOT NULL REFERENCES proxy_profiles(id) ON DELETE RESTRICT
priority            INTEGER NOT NULL CHECK(priority >= 0)
weight              INTEGER NOT NULL CHECK(weight BETWEEN 1 AND 100) DEFAULT 1
enabled             BOOLEAN NOT NULL DEFAULT true
created_at          TIMESTAMPTZ NOT NULL
updated_at          TIMESTAMPTZ NOT NULL
PRIMARY KEY (pool_id, proxy_profile_id)
UNIQUE (pool_id, priority)
```

- 单池成员数上限 50（应用层校验，DB 只兜底非负优先级）。
- `priority` 由后端归一：客户端提交数组顺序即优先级，后端在事务内归一为连续 `0..n-1`；客户端不能提交重复优先级。归一方向与超级分组一致。
- `weight` 缺省 1，范围 1..100；`round_robin` 下权重仍保存但不参与选择（或按 1 处理），避免切换策略时丢配置。
- 同一代理可加入多个池；同一池不能重复同一代理。
- 成员行 `enabled=false` 是“从本池下架”，不等于代理档案停用；代理档案 `enabled=false` 是所有池都不可用。

### 4.3 `account_proxy_leases`

```text
account_id          TEXT PRIMARY KEY          -- 有效绑定所有者：普通账户=自身；授权实例=source account
                    REFERENCES accounts(id) ON DELETE CASCADE
pool_id             TEXT NOT NULL REFERENCES proxy_pools(id) ON DELETE RESTRICT
proxy_profile_id    TEXT NOT NULL REFERENCES proxy_profiles(id) ON DELETE RESTRICT
generation          BIGINT NOT NULL DEFAULT nextval('juhe_business.account_proxy_lease_generation_seq')
                                               -- 单调递增，删除重插不复位
assignment_reason   TEXT NOT NULL              -- 'initial' | 'member_unavailable' | 'member_removed' | 'pool_reassigned'
assigned_at         TIMESTAMPTZ NOT NULL
updated_at          TIMESTAMPTZ NOT NULL
FOREIGN KEY (pool_id, proxy_profile_id)
  REFERENCES proxy_pool_members(pool_id, proxy_profile_id) ON DELETE RESTRICT
```

- 租约按**有效绑定所有者**存储，不按授权实例行存储：同一上游账户的所有授权实例共享一个出口，避免同一凭证同时出现在多个 IP。
- 租约为空表示“配置上绑了池，但尚无有效租约”，可能正在等待修复，也可能没有可分配成员；不是直连信号。
- 租约与账户配置的 `pool_id` 必须一致：写入前锁定账户行（`SELECT ... FOR UPDATE`）并校验 `accounts.proxy_pool_id = pool_id`，不能只靠应用层先读后写；池成员变更同时锁池行。
- `generation` 使用同一个数据库序列：每次 INSERT 和改变成员的 UPDATE 均显式取 `nextval`，禁止自行 `+1`；删除/重插后不复用。CAS 条件固定为 `account_id + generation + proxy_profile_id`，并在账户行锁内校验当前池绑定，避免 ABA 和跨池写入。
- 复合外键保证租约成员一定在池内；成员删除/池删除必须在同一事务先删租约，否则 FK 阻塞。
- 账户删除（逻辑删除后物理清理）级联删除租约；池删除前必须先没有绑定账户（§4.5）。

### 4.4 `accounts.proxy_pool_id`

```text
proxy_pool_id TEXT NULL REFERENCES proxy_pools(id) ON DELETE RESTRICT
CHECK (proxy_profile_id IS NULL OR proxy_pool_id IS NULL)  -- 至多一个非空
```

- 新增 `idx_accounts_proxy_pool (proxy_pool_id, id)`。
- 账户行变更脏触发器目前比较列集包含 `proxy_profile_id`（`pg_schema_business_tables.go:1798,1851`）；新增 `proxy_pool_id` 必须同时加入 new/old 列集，否则改绑池不会标脏。若可用性投影构建 SQL 不消费该列，按“只改一半禁止”的既定教训处理：要么同步纳入构建 SQL，要么明确不依赖该列并保留账户行变更语义。
- 软删除账户仍保留 `proxy_pool_id` 和租约，直到物理清理；删除池的绑定守卫忽略软删除账户，但同一事务清空其 `proxy_pool_id` 并删除租约（例外，避免 FK 阻塞，见 §4.5）。

### 4.5 约束与删除规则

| 操作 | 规则 |
| --- | --- |
| 删除池 | 存在未删除账户绑定（`proxy_pool_id=pool_id AND deleted_at IS NULL`）返回 `409 proxy_pool_bound_accounts`；删除前预览最多 4 个账户名，沿用代理删除的固定窗口口径；同一事务先把软删除账户的 `proxy_pool_id` 清为 NULL（避免 FK 阻塞），再删租约、成员行，最后删池 |
| 删除成员 | 同一事务删除该成员的租约、删除成员行并把剩余成员 priority 重新归一为连续 `0..n-1`；受影响账户由 gateway 按 §6.6 修复，不阻塞成员删除 |
| 停用成员 | `proxy_pool_members.enabled=false`；不删除租约；视为不可分配并由 gateway 按 §6.6 迁移 |
| 停用池 | `proxy_pools.enabled=false`；保留租约；所有绑定账户运行期 `proxy_pool_unavailable`；重新启用后若成员仍可分配则恢复原租约 |
| 删除代理档案 | 若被任何池引用，返回 `409 proxy_pool_member_reference_conflict`，不能删除；先解除成员关系 |
| 停用代理档案 | 允许；所有引用它的池成员视为不可分配；绑定账户按 §6.6 迁移 |
| 删除账户 | 逻辑删除保留租约；物理清理级联删除租约 |

可用性投影的 dirty 口径（与 §8.5 联动）：账户行 `proxy_pool_id` 变更纳入既有账户 update 触发器列集；`account_proxy_leases` INSERT/UPDATE/DELETE 按 account_id 标脏；`proxy_pools` 的 `name/enabled/strategy` 变更和 `proxy_pool_members` 的增删改按 pool 绑定账户标脏；`proxy_profiles` 的 `name/type/enabled` 变更按直接代理或池引用标脏，`pool_health_status` 仅进入或离开 `dead` 时按所有引用该代理的池的绑定账户标脏，包括当前无租约的账户。不要按 `test_status/latency/last_tested_at` 标脏，避免恢复高频纯 churn。所有触发器与投影构建 SQL 必须同批修改，禁止只改一半。

## 5. 绑定与解析语义

### 5.1 配置绑定与有效目标分离

| 概念 | 存储 | 含义 |
| --- | --- | --- |
| 配置绑定 | `accounts.proxy_profile_id` 或 `accounts.proxy_pool_id` | 用户/管理员选择的单代理或池 |
| 租约 | `account_proxy_leases` | 池绑定当前固化的成员 |
| 有效目标 | 运行时解析结果 | 直接代理=配置代理；池=租约成员；无配置=直连 |
| 展示字段 | 列表/详情 API | 必须同时暴露配置绑定和有效成员，不能把成员写回配置字段 |

### 5.2 授权实例覆盖

- 授权实例的上游凭据、模型能力、代理等从来源账户补齐（`架构总览.md:254`）。解析顺序：
  1. 实例有 source account：若 source 有 `proxy_pool_id` → 用 source 的池；否则若 source 有 `proxy_profile_id` → 用 source 的代理；否则回落到实例自身既有的直接代理绑定（无绑定则直连）；实例自身的池绑定不参与解析。
  2. 普通账户：使用自身 `proxy_pool_id` 或 `proxy_profile_id`。
- **两列同时非空是数据损坏**：解析器返回 `proxy_target_conflict` 并记录诊断，绝不静默按池优先选边；写入路径用 `CHECK` + 应用校验保证至多一列。现有历史数据如有双列，必须先修复数据再上线。
- 池租约键固定为 source account ID；实例行即使误写 `proxy_pool_id` 也不参与解析。
- 实例详情只读展示 source 的池名/当前成员；实例自身不能改池。

### 5.3 统一解析契约

新增共享解析器（建议 `backend-go/shared/platform/proxyresolve`，允许注入解密函数以保持依赖方向）：

```text
Target {
  Kind:              "direct" | "profile" | "pool_member"
  ProfileID:         string   // direct/profile 时为配置档案；pool_member 时为成员档案
  PoolID:            string   // pool_member 时非空
  MemberProfileID:   string   // pool_member 时等于 ProfileID
  URL:               string   // 已解密并归一为 socks5h:// 等；direct 时为空
  UnavailableCode:   string   // 空表示可用
  UnavailableMessage:string
}

ResolveAccount(accountRef) (Target, error)
ResolveAccountsBatch(accountRefs) (map[accountKey]Target, error)
```

解析器以接口注入 DB、解密函数和时钟，便于单元测试与 Mock；批量接口是网关热路径的唯一入口，单账户接口供 jobs/OAuth/余额等使用。

解析规则固定：

1. 按 §5.2 确定有效绑定和租约键；第一版池健康为代理级，不按 vendor 细分。
2. 无绑定 → `Kind=direct`，URL 为空；**不**读取环境代理（沿用 `upstreamhttp` 直连语义）。
3. 直接代理 → 档案必须存在、`enabled=true`、密码可解密；否则 `UnavailableCode=proxy_unavailable`，**不得直连**。
4. 池 → 池必须存在且 `enabled=true`；租约必须存在且成员在池内、成员行 enabled、代理档案 enabled、健康不是 `dead`；否则 `UnavailableCode=proxy_pool_unavailable`，**不得直连**。
5. 池租约为空但成员可分配时，只有 gateway 按 §6.6 补租约；只读进程（jobs/shared reader）返回 `proxy_pool_unavailable`，不自行选择成员，恢复不依赖请求流量。
6. 两列同时非空 → `proxy_target_conflict`，不选边。
7. 任何解密失败、host/port 非法、协议不支持都返回明确的不可用，不返回空 URL 伪装直连。

### 5.4 失败语义

| 场景 | 结果 | 是否直连 |
| --- | --- | --- |
| 无代理绑定 | `direct` | 是（合法直连） |
| 直接代理不存在/停用/解密失败 | `proxy_unavailable` | 否 |
| 池不存在/停用 | `proxy_pool_unavailable` | 否 |
| 池无 enabled 成员 | `proxy_pool_unavailable` | 否 |
| 池有成员但全部健康不可分配 | `proxy_pool_unavailable` | 否 |
| 租约成员被移除/停用 | gateway 修复租约；修复前只读进程返回 `proxy_pool_unavailable` | 否 |
| 池成员代理解密失败 | 该成员不可分配；无其他成员则 `proxy_pool_unavailable` | 否 |

### 5.5 运行时字段映射

为避免改动传输层和审计的既有消费面，运行时候选做如下映射：

- `ProxyProfileID` = 有效成员档案 ID（直接代理时为配置档案；池绑定时为租约成员）。
- `ProxyURL` = 有效成员的解密 URL。
- 新增 `ProxyPoolID`、`ProxyMemberProfileID`，用于派发键、诊断和列表。
- 复用 `ProxyProfileUnavailable` 作为“有效代理目标不可用”的通用标记（字段名为历史兼容），错误消息区分 `proxy_unavailable` 和 `proxy_pool_unavailable`。
- 新增 `ProxyPoolUnavailable` 布尔值仅用于区分池级不可用，避免消费方从消息文本判断。
- 既有 `gatewayproxyhealth` 会按 `ProxyProfileID` 生成 `proxy:profile:<member>` 桶键并参与上游桶排序/避让；池绑定时成员级桶避让仍然生效，这是期望的补充机制。池级不可用另用 `pool:<id>` 去重键，不替换成员桶。
- 普通上游 transport/HTTP/协议失败只进入既有上游桶，不得升级为成员下线或池级排除；成员下线只由健康投影/手动下架触发。

### 5.6 请求内去重键

- 直接代理：`profile:<profileID>`（沿用）。
- 池成员：`profile:<memberProfileID>`；仅在现有代理错误分类允许请求内避让时排除该成员，不扩大到整个池。
- 池停用、池不存在或确认全池无可分配成员：使用 `pool:<poolID>`；同一请求内后续绑定同池的账户跳过。单账户租约缺失、失效或修复失败不能证明其他账户不可用，不得写池级去重键；按该账户失败继续尝试其他账户。
- 这些键只在单次请求内有效，不写账户状态、不写跨请求熔断（`upstreamdispatch.go:563,1317-1319,1378-1381` 的现有生命周期不变）。
- 普通上游 transport/HTTP/protocol 失败不得升级为池成员级排除；只有代理准备/握手/本地 proxy transport 事实才允许排除（沿用 `接口契约与权限矩阵.md:560`）。

## 6. 租约与分配策略

### 6.1 租约创建时机

| 场景 | 处理 |
| --- | --- |
| 账户创建绑池 | 账户 INSERT 与租约 INSERT 同一事务；无健康成员时允许创建但无租约（池结构必须至少有一个 enabled 成员，否则 400 `proxy_pool_empty`） |
| 账户 PATCH 改绑池 | 账户 UPDATE 与租约替换同一事务；旧租约删除 |
| 批量编辑绑池 | 逐账户在同一批事务内分配；每个账户独立租约 |
| 克隆 | 复制池绑定，不复制租约；新账户按策略重新分配（显式取舍，见 §15） |
| 导入绑池 | 第一版只引用已存在池；每个账户创建时分配租约 |
| OAuth 建号 | 建号前用池做一次**临时分配**（不落租约），同次授权交换固定使用该成员；账户落库时重新校验成员仍可分配，并把同一成员固化为租约（`assignment_reason='initial'`），校验失败则明确失败，不静默换出口。并发建号在落库前不占租约，可能临时集中同一成员；第一版接受该限制，不引入预留表 |
| OAuth 自动刷新/重新授权/jobs 保活 | 使用账户已固化租约成员；租约不可用时失败，不在 token 刷新中途换 IP、不直连；jobs `oauthrefresh` 的 `refresh/keepalive/store` 全部走统一解析器 |
| 草稿测试 | 临时分配，不固化；保存时重新分配。草稿测试是诊断，不承诺与保存后出口一致 |
| 重分配 | gateway 装配或不依赖请求流量的后台修复发现租约不可分配时，按统一锁序重新分配并 CAS 更新（§6.6） |

### 6.2 可分配成员

成员可分配必须同时满足：

1. `proxy_pools.enabled = true`；
2. `proxy_pool_members.enabled = true`；
3. `proxy_profiles.enabled = true`；
4. 代理档案密码可解密、host/port/scheme 合法；
5. 健康投影不是 `dead`；NULL 按 `unknown` 处理，SQL 必须显式包含 NULL。

`pool_health_status` 由 J3a 的 item 结果投影（§7.2）；字段为 NULL 的存量行视为 `unknown`，不得用旧整体 `test_status` 推断 `dead`。

- `healthy/degraded/unknown` 均平等参与分配；只用租约数、权重和成员顺序决定选择，不增加健康等级平票或检测过期计时规则。
- `dead` 在 J3a 成功复测并投影为新状态前**始终不可分配**，不因时间过期自动降级为 unknown（避免坏节点回流）。
- 从未检测、无 vendor target 或无可判定探测结果的成员为 `unknown`，可分配；健康结果陈旧不自动推断新状态。

### 6.3 `round_robin` 语义

对可分配成员计算当前池内租约数 `leases(member)`，选择：

```text
min leases(member)
tie: priority ASC, proxy_profile_id ASC
```

这是“按账户数轮转”，不是按请求游标；它天然抗并发、抗成员增删，且存量租约不动。举例：3 个成员、5 个账户依次绑定 → 2/2/1。

### 6.4 `weighted` 语义

选择：

```text
min leases(member) / weight(member)
tie: priority ASC, proxy_profile_id ASC
```

比较用整数交叉相乘（`leases_a * weight_b` vs `leases_b * weight_a`），避免浮点误差。权重 1:2:1、8 个账户的期望分布是 2/4/2；实际以逐次最小比值分配为准。

### 6.5 粘性、不重排与重平衡

- 已存在的租约在成员可分配时永不因以下事件改变：新账户加入、权重调整、池策略切换、成员新增、其他成员恢复。
- 只有以下事件触发重分配：租约成员被删除、被停用（成员行或代理档案）、健康不可分配、池被删除（池删除前必须无绑定账户，实际不会发生）、账户改绑/解绑。
- “改权重后立即重平衡”是非目标；需要时另立显式管理操作，且必须审计。第一版不提供。
- 账户解绑或物理删除时删除租约；逻辑删除保留至物理清理（§4.5）。重新绑定时重新分配，不保证回到原成员。

### 6.6 失效重分配

- gateway 运行时装配或后台修复时，对池绑定账户读取租约；若租约缺失或成员不可分配：
  1. 按 §6.2/§6.3/§6.4 选新成员；
  2. 已有租约时在锁内校验绑定，再执行 `UPDATE account_proxy_leases SET proxy_profile_id=?, generation=nextval('juhe_business.account_proxy_lease_generation_seq'), assignment_reason=?, updated_at=? WHERE account_id=? AND generation=? AND proxy_profile_id=?`；缺失时在同一锁内校验绑定并 INSERT，generation 同样取该序列；
  3. CAS 或唯一约束冲突时重读并重新校验最新绑定和租约，不能直接使用未经校验的结果。
- 没有可分配成员时保留已有租约，解析仍返回 `proxy_pool_unavailable`；若成员被删除则必须删除其租约（FK 不允许悬空）。
- 只读进程不重分配；它们读取到的不可用租约直接失败。gateway 作为唯一租约写者，在已有 gateway 进程内执行有界、可重试的后台修复扫描：覆盖缺失租约、租约成员不可分配的池绑定账户，包含成员新增/恢复后此前无租约的账户；扫描可分页并重复执行，不新增队列或跨进程 RPC。管理写入和运行时装配可提前触发同一修复逻辑，但不得成为唯一触发方式。无可分配成员时保留现状并等待后续扫描，数据库错误须记录并重试，不保证故障期间恢复时限。

### 6.7 并发与 CAS

- 租约分配在 gateway 内串行化到池级，锁池行并锁账户行；创建、改绑、成员更新、装配和后台扫描必须使用同一锁序。跨池改绑按池 ID 固定顺序锁相关池，再锁账户，事务内重新验证绑定与成员；具体批处理锁序在实施计划中展开并以并发测试验证。
- 租约更新带 `generation` CAS；并发装配/管理写入不会互相覆盖。
- 分配只统计 `account_proxy_leases` 中该池的当前行；软删除账户的租约在物理清理前仍计数，避免短期分配倾斜；如需精确可加 `JOIN accounts deleted_at IS NULL`，第一版按全量租约计数，口径写入验收。

### 6.8 示例

池 P：成员 A(weight=1, priority=0)、B(weight=2, priority=1)、C(weight=1, priority=2)，全部 healthy。

- `round_robin` 依次绑定 6 个账户：A,B,C,A,B,C。
- `weighted` 前 6 次绑定的选中顺序：A、B、C、B、A、B；前 8 次后分布收敛为 A=2、B=4、C=2（比例 1:2:1）。计算方式是每一次选 `leases/weight` 最小的成员，平票按 priority。

## 7. 健康与失效

### 7.1 可用性公式

```text
pool_available   = pool.enabled
member_assignable = member.enabled
                    && proxy.enabled
                    && proxy 可解密/协议合法
                    && coalesce(proxy.pool_health_status, 'unknown') != 'dead'
assignable_members = 全部 member_assignable
pool_dispatchable = pool_available && assignable_members > 0
```

### 7.2 J3a 复用

- 复用现有 J3a，不新增探测任务：成员是 `proxy_profiles` 行，已被 J3a 覆盖。
- 新增投影字段 `proxy_profiles.pool_health_status`，由 J3a 投影器按 outcome 的 items 计算，供池成员分配使用（统计时排除非 vendor 的“基础连通性”汇总项；以 outcome item schema 为准）：
  - `dead`：至少一个 item 有结果且没有任何 item passed（全部实际探测失败）；
  - `degraded`：部分 item failed、部分 passed；
  - `healthy`：全部 item passed；
  - `unknown`：无 item、无真实探测或其它无法判定。
- `test_status` 保持现有整体诊断语义不变；直接代理仍只看 `enabled`，不消费 `pool_health_status`。
- J3a 整体 `OverallStatus` 是“任一 target failed → failed”，不能直接用于池排除；池只看上面的 `pool_health_status`，避免单个 vendor 不可达就下掉整个代理。
- `dead` 在成功复测并投影为新状态前保持不可分配；其他状态均可分配，检测时间不增加额外的分配等级。
- 检测恢复为 `healthy/degraded` 后，成员自动回到可分配集合；存量租约不自动迁回，新分配可再次选中它。
- 上游按 IP 封禁可能返回完整 HTTP 403，J3a 仍记为 passed，因此 `pool_health_status` **不能识别上游封禁**。所有目标失败也只是探测结果，不证明代理本身必然故障；自动排除是 C1 推荐方案的取舍，可能受到共同上游或网络故障影响。
- J3a 的探测目标、批次、lease、CAS、迟到写回契约不变；本设计只增加投影字段与计算规则。

### 7.3 手动下架与恢复

- 管理员在池成员表上直接切换 `enabled`：下架停止新分配；已绑定账户由 gateway 装配或后台修复迁移。缓存失效和在途请求的边界见 §7.4。
- 下架不写账户状态、不触发账户冷却、不改 `accounts.schedulable`。
- 恢复后成员重新进入可分配集合；不回迁已迁移账户。
- 代理档案的 `enabled` 切换是全局下架；语义同上，影响所有引用它的池。

### 7.4 传播时延

- 池/成员管理写入成功后发布 `TopicGatewayRuntime` 失效；同批补上代理档案写入失效。失效后新的读取重新装配，已在途请求不回收；失效传播或数据库故障不保证即时生效。
- J3a 写健康状态不经过 gateway 失效总线；外层运行时缓存使用 60s revalidate / 2min last-good retain。健康变化在刷新成功后可见，2min 只是旧快照保留策略，不是故障期间成功传播的时限承诺；此期间旧成员可能仍被使用。
- 第一版不新增 jobs→gateway 健康失效事件或独立健康轮询；是否接受这一传播策略仍由 C7 裁决。

### 7.5 账户调度不变（硬约束）

- 池逻辑不得写 `accounts.status`、`cooldown_until`、`schedulable`、`priority`、`last_error_*`、健康检查失败计数等任何账户调度/健康字段。
- 池成员不可用只影响“该账户本次请求能否解析到出口”；账户仍留在分组、路由、会话亲和和健康候选集。
- 池级不可用只产生 attempt 级 `proxy_pool_unavailable`，沿用现有“代理不可用不突变量账户状态”的边界（`accountpreparation.go:83-145` 的注释与实现）。
- 账户健康探针、余额、OAuth 等后台任务遇到解析阶段确认的池不可用时，应保留明确错误，不直连、不把该本地错误当作上游账户失败写入账户状态；各任务保留原有可重试机制，避免将池不可用计入 OAuth 终态停刷。实际出站后收到的上游错误仍遵循原策略（§7.6）。

### 7.6 上游错误与归因边界（C2 已裁决）

- 用户确认：实际请求失败通常无法可靠区分账户、代理出口与上游原因；跨成员复测成功或失败都不能证明责任归属。本期不做自动跨成员复测归因，不增加成员隔离信号或延迟账户处罚机制。
- 本地解析阶段已确定的池停用、无成员、租约缺失等 `proxy_pool_unavailable` 由池处理，按 §7.5 不作为账户失败。代理连接阶段若现有链路能明确识别代理准备或握手错误，沿用既有代理错误分类与请求内避让；本设计不扩大可归因范围。
- 请求或账户探测实际出站后的 HTTP、transport 和协议错误，沿用对应入口当前账户错误策略和代理桶行为；不因绑定池而豁免或新增账户处罚，也不据单次失败自动下架成员。现有规则可能冷却或禁用账户。
- J3a 把完整 HTTP 响应（含 403）视为 reachable，不能识别上游 IP 封禁；`dead` 仅表达全部实际探测失败，不证明代理为根因。管理员可按诊断信息手动下架成员。
- 验收必须分别覆盖本地池不可用不写账户状态，以及真实上游错误仍按既有策略生效；不承诺“所有由代理间接引起的失败都不影响账户”。

### 7.7 全部成员不可用

- 解析返回 `proxy_pool_unavailable`，消息包含池名和原因（池停用/无成员/全部不可分配/租约成员不可用）。
- 请求按代理失败处理：attempt 记录 `proxy:pool` 类 URL、`error_code=proxy_pool_unavailable`；账户不冷却、不禁用。
- 用量/审计保留账户和失败原因；不写 IP 级熔断、不写代理桶的账户级状态。
- 池与成员恢复后，原租约仍可用时随缓存刷新恢复；租约缺失或失效时由 gateway 按 §6.6 修复。修复和缓存刷新完成前请求仍可能失败，不需要人工重置账户。

## 8. API、权限与绑定写入

### 8.1 管理面代理池 CRUD

| 方法 | 路径 | 语义 |
| --- | --- | --- |
| `GET` | `/__aisys__/api/proxy-pools` | 分页 `page/pageSize/keyword`，关键词只按池名精确/前缀；返回 `id/name/description/strategy/enabled/memberCount/assignableMemberCount/leaseCount/updatedAt` |
| `GET` | `/__aisys__/api/proxy-pools/{id}` | 详情：池字段 + 成员（`proxyProfileId/name/type/enabled/testStatus/latencyMs/priority/weight/memberEnabled/leaseCount/assignable`） |
| `POST` | `/__aisys__/api/proxy-pools` | 创建；`name/description/strategy/enabled/members`；严格白名单；`MutationGuard` key `proxy-pools.create` |
| `PATCH` | `/__aisys__/api/proxy-pools/{id}` | 局部更新；必须带 `expectedUpdatedAt`；`members` 出现即完整替换成员集合；成员增删/改权重/改启停与池更新同一事务 |
| `DELETE` | `/__aisys__/api/proxy-pools/{id}` | 删除；有未删除账户绑定返回 409；同一事务删租约/成员/池 |
| `GET` | `/__aisys__/api/proxy-pools/member-options` | 管理员成员选择器：`keyword/limit/selectedIds`，返回 `id/name/type/enabled/testStatus`，不返回 host/port/用户名/密码 |

- 池成员写入校验：池存在；成员代理存在；成员不重复；成员数 ≤50；`weight` 1..100；`priority` 归一；不能把池自身或不存在对象作为成员（成员只能是单代理）。
- 成员集合完整替换时，保留交集成员行并原地更新属性，只对差集执行增删，保留成员的租约不变。priority 采用两阶段更新（先整体移到不冲突的临时值再写新值），避免 `UNIQUE(pool_id, priority)` 的瞬时冲突；删除成员后剩余 priority 归一为连续 `0..n-1`。
- `member-options` 必须在 `/{id}` 之前注册或使用不与其冲突的路径；否则会被 `{id}` 捕获成池 ID。
- 池更新 CAS 失败返回 409 `proxy_pool_revision_conflict`；`updated_at` 用文本时间戳，沿用代理/分组的实现口径。
- 池写操作日志记录池名、策略、成员变更摘要（不记录代理密码/host 等敏感细节）。

### 8.2 账户下拉（同一个下拉）

扩展现有 `GET /__aisys__/api/proxies/options`：

- 新增 `kinds` 查询，缺省 `profile`（保持现有调用方行为）；账户表单传 `kinds=profile,pool`。
- 新增 `selectedPoolIds`（裸重复键或 bracket 数组键），与 `selectedIds` 分开；`selectedIds` 只匹配代理档案，`selectedPoolIds` 只匹配池，均最多 20 个、排序去重规则一致。
- 响应项新增 `kind`：`profile` 或 `pool`。`profile` 项保持 `id/name/type/enabled`；`pool` 项返回 `id/name/kind/enabled/memberCount/assignableMemberCount`，不返回成员、host、端口、用户名、密码、出口 IP 或检测明细。
- `type` 对 `pool` 项不返回（或返回空），前端用 `kind` 分组和标签；不要用 `type='pool'` 混入代理协议值域。
- 现有只传 `keyword/limit/selectedIds` 的调用方行为不变；池选项只在显式请求 `kinds=pool` 时返回。

### 8.3 账户写入

- `POST /accounts`、`PATCH /accounts/{id}` 新增 `proxyPoolId`（string 或 null），与 `proxyProfileId` 互斥：
  - 两者同时非空 → 400 `proxy_target_conflict`；
  - 创建：缺省 = 无代理；`null` = 无代理；
  - PATCH：缺省 = 不修改；`null` = 清除该目标；同时 `proxyProfileId:null, proxyPoolId:null` = 解除绑定；
  - `proxyPoolId` 非空：池必须存在、enabled、至少有一个 `member.enabled && proxy.enabled` 成员，否则 400 `proxy_pool_empty`/`proxy_pool_disabled`；健康不可分配不阻止绑定。
- 写入同一事务：账户行 + 租约（创建/改绑）；解绑时删除租约。
- 账户详情/高级详情：返回配置绑定 `proxyProfileId` 和 `proxyPoolId`，以及 `proxyPoolName/strategy/memberCount` 和有效成员摘要；编辑表单必须回填配置绑定，不能回填有效成员（否则保存会把池改成直接代理）。
- 账户列表：见 §8.5 字段契约；`proxyProfileId` 保持“配置的直接代理”，池绑定时为 null；新增 `proxyPoolId/proxyPoolName/proxyTargetType/proxyMemberProfileId/proxyMemberProfileName`。
- 克隆：复制 `proxyPoolId`（或 `proxyProfileId`），不复制租约；新账户按策略分配。克隆上下文返回池名供前端展示。
- 授权实例：来源账户池覆盖；实例自身不可写池；实例详情只读展示。
- 手工测试草稿：草稿加密 payload 增加 `proxyPoolId`；执行时临时分配一个成员，不固化；本地解析不可用按 `proxy_pool_unavailable` 归类，不写账户状态。实际出站错误按该测试入口既有语义处理。
- OAuth 建号：`allowedKeys` 增加 `proxyPoolId`；建号前临时分配成员用于 token 交换；账户创建时固化同一成员为租约。重新授权/轮换/自动刷新/jobs 保活使用账户已固化租约成员；租约不可用时失败，不在 token 刷新中途换 IP、不直连。
- OAuth 自动刷新路径（`oauthmgmt/auto_refresh.go:81-84`）和 jobs 刷新/保活（`oauthrefresh/refresh.go:637`、`keepalive.go:292`、`store.go:105-107`）当前直读 `current.ProxyProfileID`；必须改为有效目标解析，否则池绑定账户会 400 或直连。OAuth 建号写路径 `oauthmgmt/store.go` 也要接受并固化池租约。

### 8.4 批量编辑、导入与导出

- 批量编辑：`proxyPoolId` 加入可批量字段白名单；与 `proxyProfileId` 互斥；三态（不勾选/勾选 null/勾选值）与现有代理字段一致；每个目标账户独立分配租约。批量接口仍需 owner/权限校验，不能绕过单账户规则。
- 导入：
  - 新增顶层 `proxyPools`（可选，第一版只读引用，不创建）与账户字段 `proxyPoolRef`/`proxyPoolId`；
  - `proxyRef`/`proxyProfileId` 与 `proxyPoolRef`/`proxyPoolId` 互斥；
  - 普通用户只能引用已存在且 enabled 的池；管理员同样不自动建池（第一版）；
  - 引用不存在/停用池 → 该账户导入失败并给出明确原因，不静默丢绑、不直连。
- 导出：
  - 账户绑池时写 `proxyPoolRef: "proxy-pool-<id>"`，并在顶层 `proxyPools` 写池名/策略/成员引用（成员用 `proxyRef` 或 `proxyProfileId`），不重复导出成员密码；`proxyPools` 段用于文档可读性和一致性校验，第一版导入不据此创建池，目标环境缺失即拒绝；
  - 第一版导入支持 `proxyPools` 的“已存在则复用、缺失则拒绝”，不做自动创建；如果审核要求完整 round-trip，再升级为管理员可创建（§15 C3）。
- 现有 `proxies` 自动创建逻辑不变；池成员引用的代理如果由导入自动创建，必须在池解析前完成，顺序固定为 proxies → proxyPools → accounts。

## 10. 运行态、缓存与可观测性

### 10.1 网关运行时装配

1. 候选查询同时取 `accounts.proxy_profile_id/proxy_pool_id` 和 source 侧同名列。
2. 对池绑定账户批量读取 `account_proxy_leases`；按 §5.2 确定租约键。
3. 校验租约成员可分配；不可分配时按 §6.6 重分配并 CAS。
4. 收集直接档案 ID + 有效成员档案 ID，沿用 `resolveProxyURLsForProfiles` 批量解密。
5. 写入候选：`ProxyProfileID`=有效成员、`ProxyURL`、`ProxyPoolID`、`ProxyMemberProfileID`、`ProxyProfileUnavailable`/`ProxyPoolUnavailable`。
6. 直连/单代理路径保持原有分支和错误语义。

### 10.2 缓存失效

- 池/成员/池启停写入：`InvalidateGatewayRuntime("proxy_pool_updated")`。
- 代理档案写入：同批补上 `InvalidateGatewayRuntime("proxy_profile_updated")`，修正文档与代码不一致。
- 账户绑定/解绑：沿用现有账户写失效。
- J3a 健康：不跨进程失效，刷新成功后可见；60s revalidate / 2min last-good retain 不构成故障期间的传播上界。手动下架通过失效传播影响后续读取，不中断在途请求，见 §7.4。
- 可用性投影：池/成员/租约/代理展示列及健康跨 `dead` 边界的变更按 §4.5 标脏，不对检测时间或延迟的高频变化标脏。
- 代理桶：有效成员 `ProxyProfileID` 会进入既有 `gatewayproxyhealth` 桶键与避让；这是既有机制，池级不可用另用 `pool:<id>` 键，二者不互相替代。
- 不新增 Redis 健康缓存；租约与健康均从 PG 读取（批量、低频）。

### 10.3 余额身份

- 余额查询身份摘要当前包含 `proxyProfileId`，且调用点不止一处：`accountbalance/input_digest.go:45-52`、`models.go:45,54-55,78`、`accountsbalance/balance.go:80-110`（`COALESCE(proxy_profile_id,'')`）、`accounts/patch.go:2496-2518`（`balanceIdentityValue`）、`shared/platform/accountbalance/multi_key.go:45-49`。
- 池绑定账户的身份摘要改为包含 `proxyPoolId` + **有效成员档案 ID**；租约迁移视为不同输入，重置刷新代次。上述所有读写执行调用点必须同批改，不能只改摘要函数。
- 无租约/池不可用时余额查询失败并记录原因，不直连、不用旧成员结果写回。

### 10.4 审计与日志

- `audit_log_attempts.proxy_url` 继续记录解析后的成员 URL；池级不可用时记录 `proxy:pool` 类标记，`error_code=proxy_pool_unavailable`。
- 建议 P1 在 `audit_log_attempts` 增加 `proxy_pool_id`、`proxy_member_profile_id` 两列（nullable），便于历史排障；如果不加，至少在使用记录错误映射中保留池名/成员名。该加法与 §4.6 同批 schema。
- 现有 `proxy_url` 含凭据的既有契约不变；新增字段不得复制密码或完整 URL 到非审计面。
- 操作日志记录池 CRUD/成员变更；不记录代理密码、host、端口。

### 10.5 可观测性

- 池详情/列表展示成员租约数、可分配数、最近检测；不新增 Prometheus 指标为第一版要求。
- 账户列表 tooltip 展示池级原因，便于用户判断是池空还是成员不可用。
- 验收 SQL 包括：池成员租约分布、租约与配置一致性、无“池绑定但直连”的审计行。

### 12.2 静态扫描门

- 非测试 Go 代码中，除共享解析器、账户写入/列表/导入、代理管理、J3a 探测外，不得新增 `proxy_profile_id`/`proxy_profiles` 直读；现有 15 个入口逐一改为调用解析器。
- 禁止“池绑定但 `ProxyURL` 为空”的直连路径：静态检查关键入口在 `proxy_pool_id` 非空时必须返回不可用或解析成员。
- schema golden/语句计数/digest 与 rehearsal 清单必须同改。
- 前端不得把 `profile:`/`pool:` 复合值直接提交给账户 API；回归脚本断言 payload 只含裸 id。
- 账户列表字段契约由前端类型 + 后端 golden 响应共同钉住。

### 12.3 测试层次

- 单元：分配算法（轮询/权重/平票/权重 1..100/无成员）、健康状态边界、错误码映射、URL 归一。
- PG 集成：schema/约束/CAS/删除守卫/租约一致性/触发器列集。
- 网关：候选装配、直接代理不变、池解析、实例覆盖、池级不可用、请求内去重键、本地池不可用不写账户状态，以及真实出站错误沿用现有策略。
- jobs/shared：余额、探针、OAuth、xAI、modelcheckowner、J3a 对池的 fail-closed。
- 前端：类型检查、ProxySelect/标签缓存、账户表单/批量/导入、列表展示、回归脚本。
- 端到端：真实 dev PG/Redis，池 CRUD → 账户绑池 → 派发 → 成员下架 → 迁移;按 `AGENTS.md` 本地管理页测试规则执行。

### 12.4 人工验收

- 代理管理页创建池、加成员、调权重、下架成员、删除守卫。
- 账户创建/编辑/批量/克隆/导入选择池；列表显示池+成员；移动端一致。
- 成员停用/代理停用/池停用导致本地解析不可用时，不因该本地错误冷却或禁用账户；请求按 `proxy_pool_unavailable` 失败或迁移。实际出站错误仍按既有策略处理。
- 余额、OAuth 刷新、账户测试、媒体任务、模型目录刷新均走同一成员；池不可用时全部 fail-closed。

## 13. 实施分期

P0、P1 是开发顺序，构成同一个发布批次；在所有入口收口和对应验收完成前不得对外启用池绑定。

### 13.1 P0：数据与核心解析

- schema revision 18、三表 + 序列、`accounts.proxy_pool_id`、`pool_health_status`、索引、投影/dirty 触发器、golden/演练清单、`BusinessSchemaVersion` v23。
- 共享解析器与 15 个入口收口；直接代理行为不变；池绑定 fail-closed；两列冲突显式失败。
- 代理池 CRUD/成员 API（含 CAS、成员完整替换、删除守卫）。
- 租约分配、gateway 后台修复、并发 CAS、池/成员/账户写入锁序。
- 按 C1 裁决实现健康投影；NULL 按 unknown，不从旧 `test_status` 推断 dead；池级不可用在 dispatch 的 `proxy:pool`/`proxy_pool_unavailable` 分支。
- 账户创建/编辑/批量/克隆/导入导出的池字段与互斥校验；账户列表/详情字段契约。
- 验收核心数据、分配、锁序、后台恢复和本地错误分类；全入口与界面验收在 P1 完成后共同作为发布门。

### 13.2 P1：管理页与发布验收

- 代理池管理页标签页、成员选择器、账户表单/批量/列表/移动端。
- 统一 options、OAuth 建号及管理页面接线；核验 P0 的自动刷新、账户测试、余额、媒体、探针、模型目录、xAI 等全入口收口。
- 池成员健康投影消费、手动下架、池停用/恢复、池写失效、代理写失效修正、投影 dirty 生效。
- Mockdata 池种子与前端回归脚本。
- 发布验收：§12 全部适用 fixture，包括全入口 fail-closed、本地池错误与真实上游错误边界、投影和前端回归；按最终裁决调整对应 fixture。

### 13.3 后续可能的增强

- 审计 `proxy_pool_id`/`proxy_member_profile_id` 列由 C4 决定；若同批加入则随 schema 发布。
- jobs→gateway 健康失效事件由 C7 决定；不能据此承诺故障期间的传播上界。
- 池健康按 vendor 细分、导入自动创建池、显式重平衡操作。

### 13.4 停止条件与回滚

- 任一 P0 入口仍存在“池绑定可直连”路径 → 停止，不得发布。
- schema 升级 dry-run blocked、golden 不一致、演练清单缺失 → 停止。
- 回滚按 §11.4：先处理并核验全部池绑定，再按经演练的兼容路径回退镜像或恢复备份。
