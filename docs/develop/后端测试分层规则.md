# 后端测试分层规则

> 面向 AI 与维护者。本文件是后端测试的强制规则：开发与测试都必须按此分层执行，测试文档、测试命名和 CI 选择以此为唯一依据。操作层面的验证入口见[开发测试与验证说明](测试与验证说明.md)。

## 1. 目标与优先级

1. **后端代码覆盖率优先**：后端是长期运行的代码，问题潜伏期长、人工很难看出来；覆盖率是保证"代码本身没有问题"的第一道防线。**硬门槛：所有 Go 包语句覆盖率 ≥95%**（`go test -cover`，`go tool cover -func` 口径），无默认豁免包。
2. **核心原则：凡是无法测试的都是设计有问题**。遇到覆盖率墙时第一反应不是"登记豁免"，而是当作设计缺陷信号去改设计——抽依赖注入点、拆可测函数、建 fixture。实测证据（2026-09 战役）：两个真实生产缺陷（J3a 停机死锁、releaseRetryAt 单位错误）恰恰都是在"本以为不可测"的 boot/冷路径里被补测试挖出来的。
3. **业务正确性其次**：流程是否正确需要在使用和业务测试中发现，不指望单元测试替业务兜底。
4. **前端按前端规则执行**：前端逻辑代码域（api/shared/composables/lib/utils/config/directives）的自动化覆盖与契约打通要求见[前端测试分层规则](前端测试分层规则.md)；页面交互不做自动化覆盖要求。

## 2. 测试分层

| 层 | 目的 | 依赖 | 时长预算 | 是否随单元测试运行 |
| --- | --- | --- | --- | --- |
| 单元测试 | 纯代码覆盖：把流程拆成最小可测元素，用参数伪造输入与依赖 | 无真实外部依赖；外部依赖一律 Mock/Stub 注入 | 秒级到分钟内；理想情况下百万级用例也应是秒级 | 是（默认层） |
| 业务测试（流程测试） | 验证完整业务流程 | 真实 mock AI 上游服务器、真实数据库（仅授权外部链路，见 §3.6）、隔离实例 | 周期大（分钟级以上） | 否，单独触发 |
| 压测/并发测试 | 竞争、吞吐、等待类行为 | 专用环境 | 专项周期 | 否，专项触发 |

### 2.1 单元测试硬规则

1. **参数伪造**：不启动进程、不连真实服务；把一个流程里的代码以最小化可测试元素逐个用参数方式调试测试。结构体字段、函数闭包、接口桩、内存 map 都是合法注入面。
2. **确定性**：禁止 `time.Sleep`/轮询等待/墙钟断言/随机值；时间用注入时钟，异步结果用 channel 同步收口。
3. **禁止并发+等待类用例**：多线程竞争、等待超时、吞吐类行为不进单元测试，归压测和并发测试。单元测试里允许出现并发原语本身（如 `sync.Once`、channel 收发），但断言不得依赖时序等待。
4. **秒级预算**：新增用例不得显著拖慢单元测试包；需要真实数据库、真实网络、子进程、健康轮询的用例放业务层，不放单元层。
5. **有意义的断言**：断言状态码、响应体、副作用或错误原文；禁止只调用不断言的凑数用例。
6. **表驱动 + `t.Run`**；helper 必须 `t.Helper()`；资源用 `t.Cleanup` 释放；断言消息用中文。
7. **外部依赖可 Mock**：涉及外部依赖的功能必须具备可 Mock 的依赖边界，优先以 Mock 隔离被测逻辑，并覆盖正常、异常与边界路径。
8. **cmd 包设计模式**：入口程序必须采用 `main() { os.Exit(run(args, stdout, stderr) int) }` 形态——错误出口返回退出码而非 `os.Exit`（全部可断言），boot 装配/停机序列抽为依赖可注入的函数（pgtestkit 隔离 PG 库、`net.Listen` 假 listener、坏 DSN 均为合法 fixture；原「临时 SQLite」fixture 已随 2026-10-25 存储收口退役）。`main.go` 出现只能靠启动真进程才能执行的语句，即视为设计缺陷。

### 2.2 业务测试（流程测试）规则

1. 需要真实 mock AI 上游服务器与隔离实例（隔离后端 + 隔离数据库 + 隔离端口），按 `AGENTS.md` 本地管理页面测试的隔离约定执行。
2. 周期大，**不随单元测试一起跑**；单独命令触发，或以环境变量门控（未设置时 `t.Skipf` 跳过）。
3. 进程级路径（`main()`、信号处理、启动装配、监听生命周期）的覆盖属于业务层：以 `go build -cover` 构建真进程 + `GOCOVERDIR` + 健康检查 + 优雅退出 + `go tool covdata textfmt` 收割，再与单元 profile 合并统计。此类用例同样遵守隔离与无人工介入规则。

### 2.3 压测与并发规则

竞争、吞吐、锁压力、超时边界统一放压测/并发测试；报告产物按 `docs/reports/README.md` 归档。

### 2.4 组合根接线与数据守护规则

> 本节由 2026-09-20 模型目录接线缺陷专项审计固化。**历史截面（SQLite 模式，已于 2026-10-25 退役）**：下文引言中的「生产 SQLite 业务池 `SetMaxOpenConns(1)`、测试环境 `memory&cache=shared`、pragma（`foreign_keys` / WAL / `busy_timeout`）复刻」等叙述是当时 SQLite 模式的事实，保留为事故复盘；现行存储测试统一经 `backend-go/shared/platform/pgtestkit` 在真实 PostgreSQL 上执行，属授权外部链路（唯一开关 `JUHE_AI_TEST_EXTERNAL=1`，未授权默认 SKIP、授权后行为不变，SKIP 不作验证通过证据；旧「PG 不可达显式失败而非 skip」口径已随 2026-10-27 测试链路治理废止，见 §3.6），第 3 条的复刻要求按 PostgreSQL 等价口径执行。根因结论「nil 端口静默 no-op + 无守卫」与全部守则条款继续有效。专项审计背景：`accounts.Store.SetModelCatalogReader` 注释宣称 composition-root handover，但组合根从未调用，真实实例上模型目录校验整体空转，而单测因注入假端口全部通过；接线后真实隔离实例又暴露第二层——“写事务内经端口回查同池”的自锁只有生产能暴露。专项审计另确认 6 个同类未接线端口、一整族观测暗区，以及无守护的种子数据不变量；本节按该根因逐条设防。

1. **组合根接线守则**：凡注释宣称 composition-root handover / 组合根接线 / compose handover 的端口或依赖注入点，必须同时满足：
   - (a) 组合根（cmd 层装配函数）存在真实装配调用点；
   - (b) cmd 层组合装配测试断言该端口非 nil——参照 `backend-go/projects/gateway/cmd/juhe-ai-gateway/compose_assembly_test.go` 的真 `composeSystemAPI` 模式（测试走真实装配函数产出依赖图，不重新手拼一套）；
   - (c) 新增端口时，端口定义、组合根装配、非 nil 守卫断言三件事在同一改动内交付，缺任何一件即视为改动未完成。
   **“单测注入假端口全绿”不构成接线完成的证据**：假端口只能证明消费侧逻辑正确，不能证明组合根真的把生产实现交了出去。
2. **nil 端口 no-op 约定的登记要求**：允许 nil 静默 no-op 的可选端口，包内注释必须写明影响面——哪些用户可见路径会降级或空转；且该包需维护（或跟随全局清单登记）可选端口清单。组合根守卫测试（上一条 b）是防漏接的第一道闸；注释登记是可读性要求，不能替代守卫断言。
3. **测试环境基础设施复刻要求**：测试 DB 构造必须复刻生产连接池关键配置中与被测行为相关的子集（现行 PostgreSQL 单形态经 `pgtestkit` 在真实 PG 上执行——授权外部链路口径，`JUHE_AI_TEST_EXTERNAL=1`，见 §3.6；复刻 `MaxOpenConns` 上限、事务 / 语句超时等生产池配置；原 SQLite 时代的 `busy_timeout` / `foreign_keys` / WAL pragma 复刻清单已随 2026-10-25 存储收口退役）。特别地，“写事务内回调端口 / 回调查询同一连接池”的代码路径必须在 `MaxOpenConns(1)` 约束下测试；若该端口在设计上使用独立连接，须在包内注明依据。新增 store 测试构造应沉淀并复用共享 helper（现行即 `backend-go/shared/platform/pgtestkit`），禁止各用例裸写 DSN——连接配置分叉正是测试环境与生产池配置漂移的源头。
4. **种子/配置数据不变量守护**：种子数据之间的不变量必须有测试锁定，包括但不限于：provider 默认支持模型 ⊆ 模型目录种子、设置键默认值与运行时回退常量一致。改种子而未同步交付（或未通过）对应守护测试，视为改动未完成。schema/seed 门禁执行入口见[开发测试与验证说明](测试与验证说明.md)。

组合级改动（接线、装配顺序、端口注入）的验收执行标准——隔离实例真实验证与副作用链验证——见[开发测试与验证说明](测试与验证说明.md) 2.3 / 2.4。

## 3. 开发期的测试执行规则

1. **不做默认全量测试**：开发过程中只运行与本次功能/修复边界相关的最小充分测试集（`go test -run '...' -count=1` 选择性运行），避免全量跑包。分区选择按本节末的「测试分区速查与耗时基线」执行；改动面属哪条测试链路、是否需要授权开关，按 §3.6「测试链路与授权」判断。
2. **边界全面覆盖**：功能涉及的边界（正常 / 异常 / 空 / 越界 / 幂等 / 竞争面收敛到单元层可测部分）必须全面覆盖后再交付。
3. 交付前核对：改动包 `go build`/`go vet` 干净；新增测试文件 `gofmt` 干净；改动面相关测试全部通过。
4. 发现疑似生产缺陷时：不修改生产代码，按现状断言并加 `// 行为存疑：<现象>` 注释，另行走问题记录（`docs/bug/`）。

### 3.5 测试分区速查与耗时基线

按「改动域 → 测试入口」选择最小充分测试集；耗时为 2026-10-03 单机实测基线，只用于数量级判断（机器不同会漂移），且均含真实 PG 臂——按授权链路口径理解（§3.6）：未授权的日常链路下，经 pgtestkit 的真实 PG 臂一律 SKIP；日常链路自身基线为 216.8s（2026-10-27 实测，见 §3.6.1）。跨模块 / 跨包执行遵守 §5.4：分模块串行（`-p 1`）、带 `-timeout`，不并行起多个 `go test` 进程。

| 改动域 | 最小充分测试入口（在模块根 `projects/<proj>` 下运行） | 参考耗时 |
| --- | --- | --- |
| gateway `internal/<pkg>`（如 gatewaycodex / gatewaydispatch / settings / gatewayanthropic） | `go test ./internal/<pkg>/... -run '<被测族>' -count=1`，包内全量通常可接受 | 单包秒级～分钟级 |
| gateway `cmd/juhe-ai-gateway`（组合根 / 装配 / 链行为；授权链路，§3.6） | 定向族：`go test ./cmd/juhe-ai-gateway/ -run '<改动族关键字如 AccountLocks|ComposeWires|Dispatch>' -count=1`；组合根 Compose 族较重 | 定向族 5–10s；Compose 族约 190s |
| jobs `internal/<pkg>`（usagewriter / statsagg / runtimelog 等） | `go test ./internal/<pkg>/... -count=1` | 单包秒级～分钟级 |
| jobs `cmd/juhe-ai-jobs`（worker 装配 / main 出口臂；授权链路，§3.6） | `go test ./cmd/juhe-ai-jobs/ -run '<改动族关键字>' -count=1`；该包全量尚可接受 | 包全量约 115s（343 测试函数） |
| maintenance（schema / seed / mockdata；`internal/schema` 属授权链路，§3.6） | `go test ./internal/schema/ -run '<被测族>' -count=1` | 包全量约 115s |
| `shared/platform/<pkg>`（accountbalance / openaicompatcore / prommetrics 等） | 按引用方拆两侧：`go test ./<pkg>/... -count=1` + 受影响项目内定向族 | 单包秒级～分钟级 |
| 跨包公共契约（shared 接口 / gatewaydispatch 端口签名） | 各受影响项目的定向族串行相加，而不是任一项目全量 | 依影响面 |

**全量测试的触发条件（默认不跑，满足其一才跑）**：发布 / verify-release 前的整模块回归；大范围重构或清理批次收尾（如开关移除、god 包拆分）；定向族无法覆盖的组合根共享状态改动。即使此时也按模块串行执行，禁止全仓 `go test ./...` 轰炸（§5.4）。

**已知全量基线与陷阱**：gateway `cmd/juhe-ai-gateway` 包全量约 **691s**，超过 `go test` 默认 10 分钟超时——跑该包全量必须显式 `-timeout 15m` 以上，否则超时 panic 会被误报为测试失败（2026-10-03 实测，panic 栈指向无关 goroutine 属超时表现，不是缺陷；该包属授权链路，§3.6）。

### 3.6 测试链路与授权

> 2026-10-27 测试链路治理裁决固化。测试分两条链路，链路归属与授权开关是强制口径；旧口径「存储测试统一真实 PG、PG 不可达显式失败」自本节起废止，由两链路口径取代。

1. **日常回归链路（默认）**：纯 mock、进程内（内存桩、httptest、miniredis），**禁止任何外部连接**——真实 PG、真实上游、真实后端一律不得进入该链路。入口 `pnpm test:daily`（`node scripts/test-daily-regression.mjs`），范围与脚本一致（按 §3.6.1 裁剪规则移出超时包）：gateway / jobs / maintenance 各自 `./internal/...`（带 `-short`）+ 前端 `test:unit`；总时长预算 **300 秒硬上限**，带 `-short` 与显式 `-timeout` 运行。未覆盖的包 / 场景一律不许私自带入日常链路。
2. **授权外部链路（独立，不属于日常回归）**：真实 PG（pgtestkit）、组合根 / acceptance 子进程网关、真实上游与真实后端 smoke 在此链路执行。唯一授权开关 `JUHE_AI_TEST_EXTERNAL=1`；未授权时这些测试一律 SKIP，**SKIP 不作验证通过证据**（沿用既有 opt-in smoke 的门控范式）。每条真实环境命令必须显式带该开关，且属于单次授权的执行，不进日常回归。
3. **语义变更（对旧规则的裁决）**：pgtestkit 由「无 PG 显式失败（`Fatalf`）」改为「未授权默认 SKIP、授权后行为不变」。真实 PG 仍是存储层验证的权威手段，但只在授权链路执行。本裁决覆盖在途计划 [PLAN-20261024T051925945Z](../plans/PLAN-20261024T051925945Z-SQLite与内存模式彻底退役.md)（SQLite 退役）中与之冲突的执行口径，该计划的存储验收在授权链路进行。
4. **慢测试归属**：gateway cmd 包（基线 691s）、jobs cmd 包（115s）、maintenance `internal/schema`（115s）、acceptance 包等组合根 / 慢面默认不在日常链路，按需在授权链路以显式 `-timeout` 运行。
5. **日常链路耗时基线**：2026-10-27 验收实测总耗时 **216.8s**（未授权、warm 缓存、全绿、退出码 0）；范围裁剪、分阶段明细与扩展 mock 回归见 §3.6.1。

## 4. 覆盖率审计规则

1. **硬门槛**：所有 Go 包语句覆盖率 ≥95%；未达标必须处置，不得仅登记了事。jobs cmd 83% 事件（2026-09）的教训：先登记上限、后补做可测试化重构的做法已被用户标准否决——上限登记只在重构尝试完成后对残余部分成立。
2. **覆盖率墙的处置阶梯（按序升级，跳步需说明）**：
   a. **设计重构**：为不可测代码改设计——`run()` 抽取、boot 函数化、依赖注入点、`sync.Once` 化重试监听等（J3a 死锁修复即此先例）；
   b. **fixture 注入**：pgtestkit 隔离 PG 库、miniredis、PG 门禁（w1cover）、假 listener、坏 DSN/坏路径（NUL 字节、缺失盘符）驱动错误臂（原「临时 SQLite」fixture 已随 2026-10-25 存储收口退役）；
   c. **死臂删除**：证据确凿的恒不可达防御臂（如平面数据的 `json.Marshal` 恒不失败、非 DriverContext 驱动的 `sql.Open` 恒成功）按 w12f/w12h 先例删除，原位留一行证据注释；
   d. **上限登记**：仅当 a-c 完成后仍有残余，且残余逐条具备"已尝试重构"的书面证据时，才可登记实测上限 + 缺口逐条清单，并须经用户确认。
3. **"不好测"不是豁免理由**：先拆最小可测元素；`main()`/exec 语义路径要么按 §2.2.3 收割业务层覆盖，要么按 §2.1.8 重构为可进程内测试的形态。
4. **未测代码视同隐患**：覆盖率缺口不是中性状态——J3a 死锁、releaseRetryAt 均在缺口区被挖出。审计报告必须把缺口按"可驱动 / 需真实依赖 / 防御臂"三类逐条列出，可驱动类限期补齐。
5. **跨层传导契约测试（语句覆盖的盲区补充，2026-10 BUG-0266/0267 固化）**：语句覆盖率只证明代码执行过，不证明"值的来源正确"。该两案实证：13 处 Node→Go 迁移传导断线全部处于 ≥95% 语句覆盖之下（断线代码每请求都执行，如 `timeoutProfileOf(..., false)` 硬编码的 `false`、coordination 恒空字段），且被兜底冗余掩盖后行为测试全绿。对"A 层生成运行态 → B 层消费"的关键传导值（timeout profile / 请求级预算实例 / timeoutPolicy / 客户端策略视图等），必须补两类断言：
   a. **来源断言**：消费端拿到的值必须逐指针/逐字段来自生产端结果（如响应层 profile 必须就是 dispatch 生成的那个，而非 settings 重建的另一个）；
   b. **组合矩阵断言**：关键请求形态（客户端画像 × 压缩/普通 × 流式/非流式 × 快/慢/半途死上游）的组合路径至少各有一条端到端用例——"普通×快"一个格子喂不出的缺陷，恰恰集中在压缩×慢这类组合（端到端测试的 mock 上游必须包含首输出超预算的慢流形态，参见 `chain_v1_compaction_timeout_test.go` 的先例）。

## 5. 测试进程纪律（硬性）

> 本节由 2026-09-19 maintenance fork 炸弹事故固化为硬性规则：`wm_main_exit_branches_test.go` 当时以“子进程重执行测试二进制”方式测 `main()` 的 `os.Exit` 分支，哨兵环境变量一次失配即自复制 658 个进程、单进程内存 1.8GB，几乎压死开发机。违反本节即测试缺陷；**不允许“加了护栏的子进程测试”作为折中**。

1. **一次 `go test` 运行 = 恰好一个测试进程**。测试代码禁止 `exec.Command` 孵化任何子进程，包括：重执行测试二进制（`os.Executable` / `os.Args[0]` + 哨兵环境变量）、`go build` / `go run`、启动被测服务的独立进程。线程 / goroutine / `t.Parallel()` 不受限——单进程内的并发不是本纪律的对象。
2. **需要覆盖 `main()` / `os.Exit` 出口分支时**：把 main 主体抽成 `runX(argv []string) int` 进程内直调——所有 `os.Exit(N)` 改 `return N`，flag 集必须用每次调用新建的 `flag.ContinueOnError` FlagSet（`ExitOnError` 会在解析错误时直接 `os.Exit` 终止测试进程），CLI 对外行为（参数、退出码、stdout/stderr 文本）逐分支保持不变。`backend-go/projects/maintenance/cmd/juhe-ai-maintenance/main.go`（`runMaintenance` + `wm_main_exit_branches_test.go`）是 2026-09-19 之后的范例；出口码断言用进程内替换 `os.Stdout` / `os.Stderr` 捕获输出。
3. **需要验证“编译产物 + 真实启动”时**：走 acceptance/ 冒烟体系——单独脚本运行、单实例、带超时与清理，不得塞进 `go test`。进程级路径的覆盖率收割仍按 §2.2.3 的 `go build -cover` + `GOCOVERDIR` 流程执行，同样由脚本而非 go test 发起。
4. **同一时刻只允许一个 go test 进程**：模块级扫描用 `go test -p 1 ./...` 串行化，且必须带 `-timeout`；禁止多任务对同一包并发跑测试（端口 / 临时库 / 编译态冲突会产生假 FAIL）；禁止 `go test ./...` 式全仓全模块轰炸，跨模块回归分模块串行执行。
5. **自动守卫**：`node scripts/test-process-isolation-regression.mjs` 扫描 `backend-go` 全部 `*_test.go`，任何非例外文件命中子进程模式即失败；例外文件命中数只允许减少（防止例外被滥用扩大）。例外文件基线只允许减少，历史遗漏的追认调整必须在此登记留痕——2026-10-08 追认一次：提交 `9ef312ce9`（模型检测零配置自动认领）为 acceptance harness 新增 `maintenance --apply-j3b-model-check-postgres` 验收子进程调用点时漏更基线，`acceptance/harness_test.go` 基线 2→3（该提交漏更后守卫红态至本次追认，详见 `scripts/test-process-isolation-regression.mjs` 内注释）。

## 7. Windows 全量测试已知环境问题（2026-10-13 登记）

> **历史截面（SQLite 模式，已于 2026-10-25 退役）。** 本节挂死根因是 modernc SQLite 驱动的 WAL 文件写入被 Windows 实时扫描 / 索引进程间歇独占；该驱动与组合根 `ensureGatewaySQLiteStoragePreflight` 均已随 2026-10-25 存储收口物理删除，上述机理不再存在。本节保留为环境问题事故复盘；现行存储测试统一经 pgtestkit 在真实 PG 上执行（授权外部链路口径：`JUHE_AI_TEST_EXTERNAL=1`，未授权默认 SKIP，见 §3.6），分片运行等规避口径是否仍需按现行实测判断，不作为当前强制规则。

`gateway` 模块 `cmd/juhe-ai-gateway` 包的全量运行（2400+ 测试）在 Windows 上存在**偶发挂死**，根因已定位为环境级而非代码缺陷：

- **证据链**：超时 dump 显示挂起 goroutine 停在 modernc SQLite WAL 提交的 `walFrames`（把页写入 `-wal` 文件的 OS write 调用）；挂点测试每次不同（组合根/chain/W 族均出现过）；同一测试单独或分片运行全部通过；HEAD 基线（改动前）同样复现。
- **机理**：Windows 实时扫描/索引类外部进程对 `TempDir` 新建的 `.sqlite3` / `.sqlite3-wal` 文件间歇持有独占句柄，OS 层 `write` 阻塞不响应 SQLite `busy_timeout` 与 `context` 取消，表现为该次全量在随机位置无限等待。
- **处置**：
  1. 全量验收使用分片运行（等价覆盖）：`go test -run 'TestChain'` + `-run 'TestW1[A-L]'` / `TestW1[M-Z]'` + `-run 'TestComp|TestGateway|TestLoad|TestW14|TestW11'` 三片，全绿即视同全量通过；或单包重跑一次。
  2. 组合根启动 preflight 已做有界化（`ensureGatewaySQLiteStoragePreflight` 120s 上限，显式启动失败可重试；历史截面：该 preflight 已随 SQLite 模式退役删除），生产同路径受益。
  3. 根治需把 Go/TempDir 目录加入 Windows Defender 排除列表（机器操作，非代码项），由维护者按需执行。
