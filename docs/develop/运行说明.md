# 开发运行说明

> **F1 运行说明（2026-08-09）。** 运行日志索引与保留必须由 Go 的 juhe-ai-runtime-log-indexer 启动；不再设置 Node 侧运行日志索引开关，也不由 Node worker 导入或保留。Node 只写 JSONL，管理端只读 Go 产物。

> 面向 AI 与维护者。
> 本文件只说明如何把项目跑起来以及运行时注意事项；测试步骤、接口样例和烟测细节请放到 [开发测试与验证说明](测试与验证说明.md)。

## 1. 运行前提

- 先完成 [开发环境安装说明](安装指南.md)，确保依赖已安装。
- 后端和前端默认读取项目内 `.env` 文件；后端还会自动读取 `backend/.env.capacity`，专门承载并发、批次、队列和容量参数。优先级为进程环境变量、`JUHE_AI_ENV_FILE` 覆盖文件、`.env.capacity`、`.env`；模板为 `backend/.env.capacity.example`。
- Node.js 需要使用官方 LTS，并通过后端运行时预检；预检会验证 `node:sqlite` 可用。
- 根 `pnpm dev` 还需要 `go` 可从 `PATH` 调用。它会在 Node 后端就绪后启动 F1 的 Go 运行日志索引器；只执行 `pnpm --filter juhe-ai-backend dev` 时不会自动启动该索引器。
- 默认端口 `3000` 和 `5173` 不应被其他进程占用。
- 复用当前业务库时，`backend/.env` 里的 `JUHE_AI_SECRET` 必须保持稳定；开发环境可留空使用内置开发密钥，`NODE_ENV=production` 时必须配置至少 32 位稳定随机密钥；当前 schema 之外的结构问题按当前 schema 离线修复，不进运行时代码。
- 开发、测试自动化或生产临时排障需要简化登录时，可显式设置 `JUHE_AI_AUTH_CAPTCHA_DISABLED=true`；此开关只关闭验证码，账号密码、登录限频、会话 Cookie 和权限边界保持不变。默认值为 `false`，所有环境开启时都会输出 `auth_captcha_disabled` warn 日志；排障结束后改回 `false` 并重启服务即可恢复验证码。

## 2. 启动项目

在项目根目录同时启动前后端：

```powershell
pnpm dev
```

根启动脚本会先启动后端，等待 `VITE_JUHE_AI_BACKEND_TARGET` 对应的 `/__aisys__/api/health` 可用后启动独立的 Go `juhe-ai-runtime-log-indexer`，再启动前端，避免前端首屏初始化请求在后端和 DB service 未就绪时触发 Vite 代理 `ECONNREFUSED`。索引器继承当前进程、`backend/.env` 与 `JUHE_AI_ENV_FILE` 覆盖文件中的 SQLite / PostgreSQL 配置和日志目录；相对路径按 `backend/` 解析，默认实例 ID 为 `dev-runtime-log-indexer`，并且根脚本会移除 `JUHE_AI_RUNTIME_LOG_ONCE`，使它保持常驻。任一受根脚本看护的子进程退出或根脚本收到退出信号时，根脚本会停止前端、Go 索引器和 Node 后端。

未显式设置 `VITE_JUHE_AI_BACKEND_TARGET` 时，根启动脚本会从当前进程、`backend/.env` 及 `JUHE_AI_ENV_FILE` 覆盖文件读取 `JUHE_AI_HOST` / `JUHE_AI_PORT`，推导后端目标并传给前端；监听地址为 `0.0.0.0` 或 `::` 时使用 `127.0.0.1` 建立本机连接。调整后端开发端口不再需要重复配置前端代理地址；显式设置的 `VITE_JUHE_AI_BACKEND_TARGET` 仍具有最高优先级。

根启动脚本不默认启用免登录，普通 `pnpm dev` 保持正常账号、密码和验证码流程。只有 AI 测试需要跳过登录时，才在当前 PowerShell 会话中显式设置开发身份后启动：

```powershell
$env:JUHE_AI_DEV_AUTO_LOGIN_USERNAME = 'admin'
pnpm dev
```

浏览器测试必须使用独立后端和前端端口。启动前检查实时监听端口；默认端口被占用时改用新的空闲端口，并将 `VITE_JUHE_AI_BACKEND_TARGET` 指向新后端，不能复用或停止已有开发进程。打开浏览器前先检查新后端的 `/__aisys__/api/auth/me` 已返回自动登录账户，以及 `/__aisys__/api/auth/captcha` 返回 `required: false`；预检失败时停止，不进入登录页手工操作。

测试结束后运行 `Remove-Item Env:JUHE_AI_DEV_AUTO_LOGIN_USERNAME`，避免后续普通开发继续继承测试身份。该通道不会创建或修改数据库会话，只为当前请求装配开发身份；非生产环境不会因为监听地址触发安全启动拦截，生产环境仍禁止启用。开发环境如果监听 `0.0.0.0`，Vite 和免登录可能被局域网访问，只应在可信网络使用。

只启动后端：

```powershell
pnpm --filter juhe-ai-backend dev
```

Node 后端开发模式需要同时关注五个常驻运行单元：

- Web/网关主进程：监听 `/__aisys__/*` 系统后台静态资源、健康检查和系统 API 反向代理，并承接根路径和 `/v1` 客户端网关入口。
- standalone 的 ingest-worker 承载使用记录、审计日志、操作日志、公开接口日志等 append-only 写入；performance 改由可扩容的 Usage / Log worker 分担这些记录职责。
- stats-worker 进程：承载系统采样写入、用量增量聚合、IP 聚合、分组账号统计缓存、TopN、概览、范围窗口、授权窗口、系统趋势窗口、账号质量刷新和统计保留期清理；表监控采样、快照写入与快照保留已由独立 Go F2 owner 接管，不属于 stats-worker。standalone 模式避免多个 Node worker 抢写同一个 stats SQLite 文件；PG 高性能模式使用 PostgreSQL async repository 写入 `juhe_stats`，SQLite shard 专属维护协议只在 standalone 下执行。
- ops-worker 进程：承载代理检测、账号健康检查、账号质量失败预检、OAuth token 保活、手动账号测试、账号级冷却复测、账户内 Key 级冷却复测、授权到期扫描、可用性时间计划同步和过期逻辑删除账号清理等运维任务。
- DB service 进程：承接系统管理 API、登录态校验、管理面 CRUD、网关高频 SQLite 读写、公开设置读取、运行日志索引查询和账号运行态副作用，降低 Web/网关主进程被同步 SQL 短暂阻塞的风险。

通过根 `pnpm dev` 启动时，以上 Node 进程之外还会有独立的 Go `juhe-ai-runtime-log-indexer` 和 `juhe-ai-table-monitor`。F1 直接读取 Node 写入的 JSONL、写入索引和 cursor、执行自己的保留清理；F2 直接并发采样 SQLite 源库或 PostgreSQL schema，并向专用 F2 SQLite 文件或 `juhe_stats` 写入快照和执行快照保留。两者均不属于 Node worker，不使用 Node bridge 或任务队列。Node 后端必须先就绪，Go sidecar 才能启动。

`usage_records_cleanup`、`non_business_data_cleanup`、API Key / AI 账户关联记录清理等维护任务现在由 ingest-worker 本地队列执行 usage shard / dataset 部分，stats 部分投递 stats-worker，不再 fork 临时维护 worker 写 usage shard 或 stats。

`pnpm --filter juhe-ai-backend dev` 的 standalone 拓扑仍由 Web/网关主进程 fork 并看护 ingest-worker、stats-worker、ops-worker 和 DB service。performance control 默认看护 2 个 Usage、2 个 Log、1 个 Stats、1 个 Ops worker；3 个 gateway 各自只看护 DB service，不重复启动 consumer。DB service 短时不可用时，已缓存且仍在硬保留窗口内的网关鉴权/路由快照继续服务并后台刷新；首次未命中的请求仍需要 DB service。系统管理 API 不使用陈旧写事实。

高性能模式 `JUHE_AI_RUNTIME_MODE=performance` 下，缓存、运行态和队列的跨进程事实源固定为 Redis / Redis Streams：`JUHE_AI_CACHE_DRIVER=redis`、`JUHE_AI_RUNTIME_STATE_DRIVER=redis`、`JUHE_AI_QUEUE_DRIVER=redis_stream`。进程内 `memory` / LRU 只允许作为 standalone driver 或 performance 下的本地 L1 / 连接对象 / 请求内观测缓存，随进程丢失也不能改变跨进程事实；登录限流、验证码、账号并发槽、网关缓存失效版本、API Key / 授权额度缓存、模型目录 / 路由索引、客户端 IP 策略单 IP shared cache、混合路由评分共享缓存和记录类队列不能把进程内 memory 当事实来源。

Codex Responses 只在请求发送上游前执行历史上下文修复：恢复可验证的 `previous_response_id` 状态，并清理不属于目标账户、不可持久化或前缀不匹配的历史 item ID。该修复没有账户级开关或 `JUHE_AI_CODEX_PROTOCOL_GUARD_MODE` 环境变量。上游 Responses SSE / JSON 不做质量校验、响应改写、拦截或由此触发的切号；正常的通用响应检查策略仍由其独立配置控制。

### 2.1 W1b Go 公开接口过渡运行

`JUHE_AI_PUBLIC_API_ENABLED=true` 时，Go 公开账户仅在新增结果为 `pending_test` 后投递 `activation`，或更新的 API Key / Base URL 实际变化、显式提交 `supportedModels` 后投递 `configuration`；投递通过 loopback Node internal bridge best-effort 触发既有健康任务。普通字段更新、删除和非 `pending_test` 新增不投递。过渡期 Node Web 与其看护的 `ops-worker` 仍需运行；Node 应先就绪、Go 后启动。仅开启 public API 时，Go 启动仍不探测 Node 存活；开启完整 management API 时按下述模型目录 bridge readiness 门禁 fail-fast。

- `JUHE_AI_NODE_INTERNAL_BASE_URL` 无默认且 Go public API 或完整 management API 开启时必填，只接受 `http` loopback IP literal 与显式端口，例如 `http://127.0.0.1:<Node端口>`。
- `JUHE_AI_NODE_INTERNAL_REQUEST_TIMEOUT` 默认 `2s`，范围 `100ms..10s`。
- Node 与 Go 必须使用 trim 后完全一致的 `JUHE_AI_SECRET`。
- 当前仅支持同主机、同网络命名空间；分容器无法直接使用 loopback，当前不支持。
- `POST /__aiinternal__/v1/account-health-check/dispatch` 不得反代公网。dispatch 失败只记日志，不回滚已提交写入，也不提供可靠重试。
- Go 管理端模型 CRUD 现直接依赖 PostgreSQL 模型事实和 Go-native dynamic catalog/cache invalidation，不再调用已从 Node 删除的 published catalog rebuild bridge；历史 snapshot 表和 migration 暂留为兼容窗口，不是运行时 owner。`JUHE_AI_NODE_INTERNAL_BASE_URL` 仍只服务账户健康 / account-test 过渡 dispatch，不代表模型目录依赖 Node。

只启动前端：

```powershell
pnpm --filter juhe-ai-frontend dev
```

## 3. 默认访问地址

- 前端管理后台：`http://127.0.0.1:5173/__aisys__/`
- 后端系统 API：`http://127.0.0.1:3000/__aisys__/api`
- 后端健康检查：`http://127.0.0.1:3000/__aisys__/health`
- OpenAI 兼容中转入口：`http://127.0.0.1:3000` 或 `http://127.0.0.1:3000/v1`

开发模式下，前端会把 `/__aisys__/api` 和 `/v1` 转发到 `frontend/.env` 中的 `VITE_JUHE_AI_BACKEND_TARGET`。根路径和其他非 `/__aisys__/*` 请求属于客户端网关入口，生产部署时不要再把管理后台挂到 `/`。

## 4. 运行注意事项

- 本地运行可以保持 `JUHE_AI_HOST=127.0.0.1`；需要局域网联调时可改成 `0.0.0.0`。非生产安全策略冲突不会阻止启动，但功能性配置错误仍会 fail-fast。
- `JUHE_AI_DEV_AUTO_LOGIN_USERNAME` 只用于需要免登录的 AI 测试，普通开发不要设置，也不能写入开发 / 生产 `.env`、发布包或部署脚本。开发自动登录不改变业务权限边界，但通过局域网暴露仍会让配置账户可被访问。
- DB service 内部系统 API 默认监听 `JUHE_AI_DB_SERVICE_HTTP_HOST=127.0.0.1` 和随机空闲端口 `JUHE_AI_DB_SERVICE_HTTP_PORT=0`；通常不要暴露到公网，也不要固定端口，除非本机排障需要。
- 分离部署或公网访问时，再按实际地址设置 `VITE_JUHE_AI_GATEWAY_BASE_URL`。
- SQLite 默认数据目录是 `backend/data/`，默认包含业务库 `juhe-ai.sqlite3`、统计数据集目录库 `juhe-ai-dataset.sqlite3`、使用记录目录库 `juhe-ai-usage-catalog.sqlite3`、统计结果库 `juhe-ai-stats.sqlite3` 和 usage shard 文件目录。需要查看当前 schema 之外的历史明细时只能停服务后离线处理，不写进源码主路径。
- AI 问答默认保留 `3` 天、每用户最多 `50` 个会话、每个会话最多接受 `50` 个用户轮次；可分别通过 `JUHE_AI_CHAT_RETENTION_DAYS`（`1..365`）、`JUHE_AI_CHAT_MAX_CONVERSATIONS_PER_USER`（`1..1000`）和 `JUHE_AI_CHAT_MAX_TURNS_PER_CONVERSATION`（`1..1000`）调整。上游 Responses 与 Chat Completions SSE 共享 `JUHE_AI_CHAT_UPSTREAM_SSE_MAX_EVENTS` 事件预算，默认 `65536`，允许 `2048..262144`；提高该值会增加单轮解析 CPU 预算，但不会取消 `64 KiB` 单事件、`192 KiB` 内容/辅助数据和常量内存边界。`JUHE_AI_CHAT_DIAGNOSTIC_TOOL_ENABLED` 默认 `false`，只供 development/test 验证 `diagnostic_echo`，生产即使误开也不暴露。以上配置都必须使用合法类型，非法值会在启动时直接报错。
- AI 问答当前图像模型注册表只启用 `gpt-image-2`。用户可在当前会话输入 `/image-model` 打开设置弹窗；生成使用 `/v1/images/generations`，基于既有图片编辑使用 `/v1/images/edits`。编辑源图必须来自当前会话有效 `assetId`，最多 5 张且处理后总大小不超过 48 MiB；这不是上传接口上限，也不能通过提高网关 64 MiB image lane 上限绕过。
- 网关按最终 request lane 使用独立超时：文本默认首响应 / 停顿 / 未提交 attempt 为 `120/30/1800` 秒，图像为 `600/120/3600` 秒；无可用账号等待默认 `270` 秒且只累计零可派发账号阶段。SSE 等待时会发送注释心跳保活，已写真实协议事件后不再透明拼接其他账号。普通路由 `speed_first` 只处理文本 lane，图像 lane 不记录慢样本或执行软阈值切号。
- `generate_image` 在系统账户图片权限已开，且会话 API Key 的分组存在可调度 `gpt-image-2` API Key 账户时注入支持函数调用的文本模型。会话详情会按当前最近模型、用户权限和实际路由展示网页搜索与图片生成的可用状态及不可用原因。跨协议图片生成也携带当前请求授权回到本机 `/v1/images/generations`，由同一套 API Key、策略路由、分组和账户能力决定是否可用；项目不再提供 `JUHE_AI_IMAGE_GENERATION_PROVIDER_*` 环境变量。生产反向代理的响应头 / 空闲超时必须大于对应图像档位，否则请求会先在代理层被截断。
- 需要给本地 admin 生成完整演示 / 测试数据时，先停止正在写库的本地服务，再执行 `pnpm mockdata`；脚本会清理上一批 `造数-` / `mockdata_` 数据并重建近 31 天统计缓存，详细范围见 [Mockdata 造数设计](../functions/Mockdata造数设计.md)。后续新增可复用造数能力统一扩展 Mockdata，不新增散落的 seed / demo 脚本。
- OAuth token 换取、刷新和账号测试优先使用账号绑定代理；`JUHE_AI_OAUTH_PROXY_URL` 只是兜底代理。
- 如果要复用本地 CLIProxyAPI 已完成的 Claude / Codex / Gemini 等认证，当前推荐把它作为 loopback sidecar 运行，再在 juhe-ai 创建普通 `api_key` 账户：OpenAI / Anthropic 兼容入口填 `http://127.0.0.1:<port>/v1`，Gemini native 填 `http://127.0.0.1:<port>/v1beta`，`API Key` 填 CLIProxyAPI access key；同时在后端显式配置 `JUHE_AI_UPSTREAM_BASE_URL_PRIVATE_ALLOWLIST=http://127.0.0.1:<port>`。
- 模型检测本地服务默认不限制正常探针并发；任意失败重试默认等待 `65s`，若上游返回更长的 `Retry-After` 则按更长时间等待；回归脚本会把等待压低，避免测试套件被真实等待拖慢。
- 后端普通运行日志默认写入 `backend/logs/juhe-ai.log`；本地直接运行时也会输出到终端。发布包 `start.sh` 在生产模式下默认设置 `JUHE_AI_LOG_CONSOLE_ENABLED=false`，避免 launchd / systemd / PM2 再额外收集一份高频 JSONL 日志；如需临时观察 stdout，可在启动前显式设置为 `true`。每条请求日志都会带 `traceId`，响应头也会返回 `x-trace-id`。
- 默认 `info` 只保留每个网关请求的一条 `gateway.request.timing_summary`、耗时达到 `1000ms` 的慢阶段和问题阶段。standalone 保留全部有界阶段详情；performance 默认按 trace 稳定采样 50/1000，未采样的正常成功汇总只保留标量诊断，日志压力下暂停正常阶段详情。DB service 请求开始与小于 `50ms` 的成功完成也只写 `debug`，慢完成和失败继续保留。
- F1 运行日志索引在 standalone 与 performance 均由独立 Go `juhe-ai-runtime-log-indexer` 持续执行，必须保持 `JUHE_AI_LOG_FILE_ENABLED=true`，让每个 gateway / worker 写入独立实例 JSONL。`JUHE_AI_RUNTIME_LOG_INDEX_ENABLED` 不再控制 F1，也不能作为 Node importer 的回退开关；文件轮转清理由 Go owner 执行，`grep` 仍只读日志文件。
- Web/网关主进程启动时不直接打开业务库、数据集目录库、使用记录目录库、usage shard 或统计结果库，也不直接挂载管理 API repository；系统 API 或客户请求链路如果遇到 DB service 未就绪、队列满、请求超时或内部 HTTP 不可用，应按不可用错误排查 DB service supervisor、子进程日志、内部 HTTP 端口和 IPC 队列，不能临时恢复主进程同步读取 SQLite。
- 高性能模式排障时优先检查 Redis cache / state / queue 三类连接和 Redis Stream consumer lag；不能为了绕过 Redis 故障临时把 `JUHE_AI_CACHE_DRIVER`、`JUHE_AI_RUNTIME_STATE_DRIVER` 或 `JUHE_AI_QUEUE_DRIVER` 改成 `memory` 后继续按高性能模式运行。
- 后台定时任务和手动账号测试不应在 Web/API 主进程事件循环里执行；统计聚合、系统采样写入、窗口刷新、账号质量和统计保留期清理应在 stats-worker，F2 表监控采样、快照写入和 retention 应在独立 Go `juhe-ai-table-monitor`；OAuth Access Token 保活 / 手动账号测试 / 账号复测 / 授权到期扫描 / 可用性时间计划同步应在 ops-worker，记录维护和数据集保留期清理应在 ingest-worker。任一职责出现在错误进程时需要先修正角色隔离。OAuth Access Token 保活会扫描所有仍存在且快过期的 GPT OAuth 账户；上游 HTTP、畸形响应、超时、断连、代理或数据库异常只记录诊断并执行有界退避，只有连续 3 次结构化本地配置错误才写入可恢复的 `oauth_token_refresh_local_configuration_invalid`。OAuth 额度快照只由真实网关请求或账户测试响应头被动更新，不再有后台主动刷新任务。
- 普通日志默认 `100MB` 滚动，保留 `30` 天、最多 `500` 个历史文件，约束总量约 `50GB`；可通过 `JUHE_AI_LOG_LEVEL`、`JUHE_AI_LOG_DIR`、`JUHE_AI_LOG_MAX_FILE_MB`、`JUHE_AI_LOG_RETENTION_DAYS`、`JUHE_AI_LOG_MAX_FILES` 调整，后端会把保留天数和文件数限制在默认上限内。
- 网关写下游响应时仍尊重 `res.write()` backpressure；短暂 drain 默认只保留 debug 级运行日志，只有等待超过 50ms 时才写 warn，避免把 0 到 1ms 的正常瞬态当成生产告警。
- 管理后台“日志搜索”的索引查询模式只检索最近 3 天写入 SQLite 索引的普通运行日志，支持按索引日志时间范围筛选；超过 3 天的日志即使日志文件仍保留也不会被索引查询搜到。
- Go 运行日志索引器会在专用 `JUHE_AI_RUNTIME_LOG_DATABASE_PATH` 中持久化文件游标，追踪当前普通日志文件，只读取上次游标之后新增的完整行；首次看到已有日志文件时从文件末尾开始追新内容，避免本地开发重启时反复全量扫描大日志。该专用库不得和 Node dataset 库共用。
- 管理后台“表监控”只对管理员开放。Go F2 `juhe-ai-table-monitor` 默认每 1 分钟采样一次当前运行模式的存储增长：standalone 只读采样业务库、数据集目录库、使用记录目录库、统计结果库和 Codex Context shard，并写入专用 `JUHE_AI_TABLE_MONITOR_DATABASE_PATH`；performance 采样 `juhe_business`、`juhe_dataset`、`juhe_usage`、`juhe_stats` 和 `juhe_codex_context` schema，并把快照写入 `juhe_stats`。SQLite 在受控预算内执行精确 `COUNT(*)`，`dbstat` 不可用时大小指标保持未知；缺少源库或 PostgreSQL schema 时本轮显式失败，不写零值占位快照。F2 历史默认保留 30 天，由同一 Go owner 清理；Node stats-worker、Node retention 和硬清理均不再写入或删除 F2 快照。
- 管理后台“日志搜索”的 `grep 模式` 会由后端调用 `rg --json`，在日志目录中按任意关键字搜索当前保留的 `.log` 文件；多关键字按同一行同时命中处理。时间范围只用于筛选参与扫描的日志文件，不读取文件内容判断行时间；默认按文件时间搜索最近 3 天，单次文件时间范围最多 7 天，同一 Go 后端进程一次只允许 1 个 grep 搜索，整次多批 `rg` 搜索共用 15 秒 deadline，避免一次扫描过大拖垮服务。Go 开发命令未配置 `JUHE_AI_LOG_DIR` 时默认读取 `../backend/logs`；生产接管必须把 `JUHE_AI_LOG_DIR` 显式配置为 Node/Go 共用日志目录的绝对路径。Go 原生路径优先使用 `JUHE_AI_RG_PATH` 指定的二进制，留空时通过进程 `PATH` 查找 `rg`；缺失或执行失败时只返回中文不可用提示，不回退到 Go 文件逐行扫描，也不回显日志目录、二进制路径或命令错误。Node 路径在删除前继续使用生产依赖 `@vscode/ripgrep`。
- 前端面向中文用户，页面应通过全局 `a-config-provider` 使用中文 locale，避免 Ant Design Vue 默认英文文案出现在界面。
- 启动后先看终端日志里的监听地址和报错信息，不要把具体接口测试矩阵写进本文件。
