# 开发运行说明

> **F1/F2/F3/F4 运行说明（2026-08-14，历史截面）。** 以下为 Node/Go 共存期的迁移中间状态描述，仅作过程溯源：其中"Node 只写 F1 JSONL……网关、账户、主 API 等仍由 Node owner"已过时——Node 后端已于 2026-09-05 全量清零（归档移出仓库，git 历史可溯），JSONL 运行日志由 gateway 自身 FileSink 产生，全部对外 API、网关链与后台任务由 Go 三项目唯一承担。现行 go-only 开发拓扑见本文 §2（根 `pnpm dev` 直接拉起 Vite 前端、Go gateway 与 Go jobs 三进程）。四个功能的独立 Store、schema、owner lease 与直接执行（不使用队列）约束继续生效。

> 面向 AI 与维护者。
> 本文件只说明如何把项目跑起来以及运行时注意事项；测试步骤、接口样例和烟测细节请放到 [开发测试与验证说明](测试与验证说明.md)。

## 1. 运行前提

- 先完成 [开发环境安装说明](安装指南.md)，确保依赖已安装。
- 环境变量按形态区分：开发形态下 dev 启动器读取仓库根 `.env`（文件不存在时 Go 进程按零配置默认派生 `./data`、`./logs`）；发布形态下 `start.sh` / `start.ps1` 读取发布包内 `backend/.env`，并叠加 `backend/.env.capacity`（承载并发、批次、队列和容量参数）与 `JUHE_AI_ENV_FILE` 覆盖文件，优先级为进程环境变量、覆盖文件、`.env.capacity`、`.env`。
- Node.js 需要使用官方 LTS；Node 后端已归档，它在开发机上只用于 dev 启动器、前端构建与校验脚本，不存在后端运行时预检（`check:runtime` / `node:sqlite` 校验已随 Node 退场）。
- 根 `pnpm dev` 还需要 `go`（当前构建基线为 1.26.x）可从 `PATH` 调用。dev 启动器为 go-only：直接拉起 Vite 前端、Go gateway 与 Go jobs 三个进程，不存在 Node 后端。
- 默认端口 `3000` 和 `5173` 不应被其他进程占用。
- 复用当前业务库时，`JUHE_AI_SECRET` 必须保持稳定；开发环境可留空使用内置开发密钥，生产环境必须配置至少 32 位稳定随机密钥；当前 schema 之外的结构问题按当前 schema 离线修复，不进运行时代码。
- F3/F4 的 loopback input secret 机制已随 go-only 收口移除：审计与操作日志由 gateway 进程内 producer 独占写入，旧监听器（3303/3304）不存在，残留的 loopback input 环境变量会被 dev 启动器与发布启动脚本剥离忽略，不得恢复。
- 开发、测试自动化或生产临时排障需要简化登录时，可显式设置 `JUHE_AI_AUTH_CAPTCHA_DISABLED=true`；此开关只关闭验证码，账号密码、登录限频、会话 Cookie 和权限边界保持不变。默认值为 `false`，所有环境开启时都会输出 `auth_captcha_disabled` warn 日志；排障结束后改回 `false` 并重启服务即可恢复验证码。

## 2. 启动项目

在项目根目录同时启动前后端：

```powershell
pnpm dev
```

根启动脚本（`scripts/dev.mjs`）是 go-only 启动器：直接启动 Go gateway 与 Go jobs，等待 `/__aisys__/api/health` 可用后再启动前端，避免前端首屏初始化请求在后端未就绪时触发 Vite 代理 `ECONNREFUSED`。两个 Go 项目继承当前进程与仓库根 `.env` 中的 SQLite / PostgreSQL 配置和日志目录；相对路径以仓库根为基准解析，dev 专属数据与日志 fallback 统一落在 gitignored 的 `.local/dev/` 下。只有根脚本收到退出信号或任一 Go 项目启动预检失败才会停止全部子进程。

未显式设置 `VITE_JUHE_AI_BACKEND_TARGET` 时，根启动脚本会从当前进程与仓库根 `.env` 读取 `JUHE_AI_HOST` / `JUHE_AI_PORT`，推导后端目标并传给前端；监听地址为 `0.0.0.0` 或 `::` 时使用 `127.0.0.1` 建立本机连接。调整后端开发端口不再需要重复配置前端代理地址；显式设置的 `VITE_JUHE_AI_BACKEND_TARGET` 仍具有最高优先级。

根启动脚本不默认启用免登录，普通 `pnpm dev` 保持正常账号、密码和验证码流程。只有 AI 测试需要跳过登录时，才在当前 PowerShell 会话中显式设置开发身份后启动：

```powershell
$env:JUHE_AI_DEV_AUTO_LOGIN_USERNAME = 'admin'
pnpm dev
```

浏览器测试必须使用独立后端和前端端口。启动前检查实时监听端口；默认端口被占用时改用新的空闲端口，并将 `VITE_JUHE_AI_BACKEND_TARGET` 指向新后端，不能复用或停止已有开发进程。打开浏览器前先检查新后端的 `/__aisys__/api/auth/me` 已返回自动登录账户，以及 `/__aisys__/api/auth/captcha` 返回 `required: false`；预检失败时停止，不进入登录页手工操作。

测试结束后运行 `Remove-Item Env:JUHE_AI_DEV_AUTO_LOGIN_USERNAME`，避免后续普通开发继续继承测试身份。该通道不会创建或修改数据库会话，只为当前请求装配开发身份；非生产环境不会因为监听地址触发安全启动拦截，生产环境仍禁止启用。开发环境如果监听 `0.0.0.0`，Vite 和免登录可能被局域网访问，只应在可信网络使用。

只启动后端的某个 Go 项目（例如联调 jobs 任务族）：

```powershell
cd backend-go/projects/gateway && go run ./cmd/juhe-ai-gateway
cd backend-go/projects/jobs && go run ./cmd/juhe-ai-jobs
```

> **历史截面。** 下述"五个常驻运行单元"（Web/网关主进程、ingest/stats/ops-worker、DB service）是 Node 后端时代的开发拓扑，Node 后端已于 2026-09-05 归档清零，这些进程不再存在，保留此处仅为阅读旧设计文档时对照。现行 go-only 开发拓扑只有三个单元：

- **Vite 前端**：本地 `5173`，通过 `VITE_JUHE_AI_BACKEND_TARGET` 指向 Go gateway。
- **Go gateway**：监听 `/__aisys__/*` 管理面、公开面与 `/v1` 客户端网关入口（端口 `3000`）；进程内承载原 F3 审计、F4 操作日志的 producer 与读写面，以及 AI 问答等业务链。
- **Go jobs**：承载原 F1 运行日志索引与保留、F2 表监控采样及账号健康、余额刷新等全部后台任务族（jobregistry 统一调度）。

F1 读取 gateway 写入的 JSONL 文件日志并维护索引与 cursor；F2 并发采样 SQLite 源库或 PostgreSQL schema 并写入专用快照库；F3/F4 由 gateway 进程内 owner 包直接写入各自事实库并执行 retention，没有跨进程 RPC。

SQLite 下各库路径为 2026-09-19 零配置语义：未显式配置路径类 env 时，业务、dataset、usage catalog、stats、usage shard 与 F1/F2/F3/F4 专用库/目录自动落 `JUHE_AI_DATA_DIR`（缺省 `./data`，相对 `backend/` 解析），显式配置仍可覆盖；多进程（或容器）共享存储时必须使用同一 `JUHE_AI_DATA_DIR`，或显式配置互不重叠的路径。各 owner 的 `*_INSTANCE_ID` 未配置时缺省主机名，共享同一数据存储的多实例部署应显式配置稳定唯一值。J1 账户健康的 `JUHE_AI_ACCOUNT_HEALTH_INPUT_SOURCE` 自 2026-09 起缺省跟随 store 模式（PG store→postgres、sqlite store→sqlite 直读业务/统计库），`files`（签名文件目录）保留为显式后备，零配置下导入的 pending_test 账户可被直接探活。各 Go 专用输出库强制 `WAL` 与 `busy_timeout=5000`。F3 已在启动时递归校验其审计 SQLite 专库不会与 usage shard root 或 shard 文件发生物理重叠；F4 启动时校验其事实库不与 business/dataset/runtime-log/table-monitor/audit/usage/stats 路径重叠；F1/F2 输出与 usage shard root 的整体隔离仍需在 SQLite 部署/联调前人工确认，这也是未来 usage 迁移前需补齐的启动门禁。

`JUHE_AI_GATEWAY_SYSTEM_API_ENABLED` 与 `JUHE_AI_GATEWAY_CHAIN_ENABLED` 自 2026-09-21 起整体移除：系统 API 与 `/v1` 网关链是 gateway 的常驻能力，不再提供环境变量开关（残留配置值会被启动器剥离并忽略）。

Go runtime 指标监控自 2026-09-27 起出厂默认开启（跟随主存储）：`JUHE_AI_GO_RUNTIME_METRICS_STORE` 未配置/空时跟随 `JUHE_AI_DATABASE_DRIVER`（`postgres` → postgres，`sqlite`、空或未知值 → sqlite 零配置默认），跟随派生与显式取值同样启用采样；唯一关闭方式是显式 `JUHE_AI_GO_RUNTIME_METRICS_STORE=disabled`，此时读接口返回 `samplingEnabled=false`。显式 `sqlite|postgres` 仍有效且优先于 driver 跟随。`JUHE_AI_GO_RUNTIME_METRICS_POSTGRES_URL` 可省略：省略时自动回退复用 `JUHE_AI_POSTGRES_URL`，写入仍严格限定 `juhe_stats.go_runtime_metrics_samples`、`go_runtime_metrics_hourly`、`go_runtime_metrics_trend_windows` 三表；两个 URL 都为空才启动报错。`JUHE_AI_GO_RUNTIME_METRICS_ROLE` 已删除：role 由进程身份固定（gateway/gateway、jobs/jobs），不再接受配置，共享转发也不再造成角色错位。采样周期 `JUHE_AI_GO_RUNTIME_METRICS_INTERVAL`（默认 `15s`，下限 `1s`）、保留天数 `JUHE_AI_GO_RUNTIME_METRICS_RETENTION_DAYS`（默认 `30`，1..3650）与服务名 `JUHE_AI_GO_RUNTIME_METRICS_SERVICE`（默认 `juhe-ai`）不变。SQLite 模式使用独立指标文件（`JUHE_AI_GO_RUNTIME_METRICS_DATABASE_PATH`，未配置时按 `JUHE_AI_DATA_DIR`（缺省 `./data`）派生为 `<数据根>/go-runtime-metrics.sqlite3`）。gateway 与 jobs 各自进程内采样并以 role 维度写入同一 Store；`GET /__aisys__/api/stats/system-metrics/go-runtime-trend`（管理员）由 gateway 进程内直查共享 Store 聚合，按 `roles`（gateway 在前、jobs 在后）返回分组小时窗口并携带 `samplingEnabled`，趋势窗口上限 90 天；浏览器不直连 jobs loopback，也不存在 Node 管理 API 同源转发。建表语义按存储分派：sqlite 模式（零配置默认派生 `./data/go-runtime-metrics.sqlite3`）在 gateway/jobs 启动时自举建表（`CREATE TABLE IF NOT EXISTS` 幂等，连接带 `busy_timeout=5000ms` 与 WAL，双进程并发安全），新库开箱即用、无需预处理；postgres 模式的 DDL 仍由 maintenance 显式执行（`--apply-go-runtime-metrics` 仅支持 PostgreSQL URL），gateway/jobs 启动只做只读 schema 校验、缺表即 fail-fast（容器形态表现为循环重启），因此 PG 环境的新装/新库首次启动 gateway/jobs 前，必须先用 `juhe-ai-maintenance --check-go-runtime-metrics` 检查、按开发数据库生命周期完成预演/备份后用 `--apply-go-runtime-metrics --node-stopped --go-stopped --backup-confirmed` 显式建表。之后再启动/重启 gateway 与 jobs。页面三层契约与空态规则见 [系统指标统计设计](../functions/系统指标统计设计.md)。

> **开发闭环证据（2026-08-10）。** 已在隔离开发资源中通过 Go `go test ./...`、`go test -race ./...`、`go vet ./...`；Linux 固定 release 直接启动验证了 F1/F2/F3 与 Node 读链路；Docker standalone（SQLite）和 performance（PostgreSQL/PgBouncer/三 Redis）均启动成功，Node → F3 → Node 审计读回、F3 health `204`、错误 HMAC `401`、F1/F2 实际快照均通过。临时数据库、Redis namespace、容器、卷、进程和测试目录均已清理。此证据仅覆盖开发环境，不证明 Docker 生产常驻、macOS launchd、生产发布或生产数据新鲜度已验证。

`usage_records_cleanup`、`non_business_data_cleanup`、API Key / AI 账户关联记录清理等维护任务现在由 Go jobs 的后台任务族统一调度执行，不存在临时维护 worker 进程。


高性能模式 `JUHE_AI_RUNTIME_MODE=performance` 下，缓存、运行态和队列的跨进程事实源固定为 Redis / Redis Streams：`JUHE_AI_CACHE_DRIVER=redis`、`JUHE_AI_RUNTIME_STATE_DRIVER=redis`、`JUHE_AI_QUEUE_DRIVER=redis_stream`。进程内 `memory` / LRU 只允许作为 standalone driver 或 performance 下的本地 L1 / 连接对象 / 请求内观测缓存，随进程丢失也不能改变跨进程事实；登录限流、验证码、账号并发槽、网关缓存失效版本、API Key / 授权额度缓存、模型目录 / 路由索引、客户端 IP 策略单 IP shared cache 和记录类队列不能把进程内 memory 当事实来源。

Codex Responses 只在请求发送上游前执行历史上下文修复：恢复可验证的 `previous_response_id` 状态，并清理不属于目标账户、不可持久化或前缀不匹配的历史 item ID。该修复没有账户级开关或 `JUHE_AI_CODEX_PROTOCOL_GUARD_MODE` 环境变量。上游 Responses SSE / JSON 不做质量校验、响应改写、拦截或由此触发的切号；正常的通用响应检查策略仍由其独立配置控制。

## 4. 运行注意事项

- 本地运行可以保持 `JUHE_AI_HOST=127.0.0.1`；需要局域网联调时可改成 `0.0.0.0`。非生产安全策略冲突不会阻止启动，但功能性配置错误仍会 fail-fast。
- `JUHE_AI_DEV_AUTO_LOGIN_USERNAME` 只用于需要免登录的 AI 测试，普通开发不要设置，也不能写入开发 / 生产 `.env`、发布包或部署脚本。开发自动登录不改变业务权限边界，但通过局域网暴露仍会让配置账户可被访问。
- 分离部署或公网访问时，再按实际地址设置 `VITE_JUHE_AI_GATEWAY_BASE_URL`。
- SQLite 默认数据目录是 `backend/data/`，默认包含业务库 `juhe-ai.sqlite3`、统计数据集目录库 `juhe-ai-dataset.sqlite3`、使用记录目录库 `juhe-ai-usage-catalog.sqlite3`、统计结果库 `juhe-ai-stats.sqlite3` 和 usage shard 文件目录。需要查看当前 schema 之外的历史明细时只能停服务后离线处理，不写进源码主路径。
- AI 问答默认保留 `3` 天、每用户最多 `50` 个会话、每个会话最多接受 `50` 个用户轮次；可分别通过 `JUHE_AI_CHAT_RETENTION_DAYS`（`1..365`）、`JUHE_AI_CHAT_MAX_CONVERSATIONS_PER_USER`（`1..1000`）和 `JUHE_AI_CHAT_MAX_TURNS_PER_CONVERSATION`（`1..1000`）调整。上游 Responses 与 Chat Completions SSE 共享 `JUHE_AI_CHAT_UPSTREAM_SSE_MAX_EVENTS` 事件预算，默认 `65536`，允许 `2048..262144`；提高该值会增加单轮解析 CPU 预算，但不会取消 `64 KiB` 单事件、`192 KiB` 内容/辅助数据和常量内存边界。`JUHE_AI_CHAT_DIAGNOSTIC_TOOL_ENABLED` 自 2026-09-21 起移除：`diagnostic_echo` 诊断工具为常驻能力（原默认 false 仅限 development/test 验证）。以上配置都必须使用合法类型，非法值会在启动时直接报错。
- AI 问答当前图像模型注册表只启用 `gpt-image-2`。用户可在当前会话输入 `/image-model` 打开设置弹窗；生成使用 `/v1/images/generations`，基于既有图片编辑使用 `/v1/images/edits`。编辑源图必须来自当前会话有效 `assetId`，最多 5 张且处理后总大小不超过 48 MiB；这不是上传接口上限，也不能通过提高网关 64 MiB image lane 上限绕过。
- 网关按最终 request lane 使用独立超时：文本默认首响应 / 停顿 / 未提交 attempt 为 `120/30/1800` 秒，图像为 `600/120/3600` 秒；无可用账号等待默认 `270` 秒且只累计零可派发账号阶段。SSE 等待时会发送注释心跳保活，已写真实协议事件后不再透明拼接其他账号。普通路由 `speed_first` 只处理文本 lane，图像 lane 不记录慢样本或执行软阈值切号。
- `generate_image` 在系统账户图片权限已开，且会话 API Key 的分组存在可调度 `gpt-image-2` API Key 账户时注入支持函数调用的文本模型。会话详情会按当前最近模型、用户权限和实际路由展示网页搜索与图片生成的可用状态及不可用原因。跨协议图片生成也携带当前请求授权回到本机 `/v1/images/generations`，由同一套 API Key、策略路由、分组和账户能力决定是否可用；项目不再提供 `JUHE_AI_IMAGE_GENERATION_PROVIDER_*` 环境变量。生产反向代理的响应头 / 空闲超时必须大于对应图像档位，否则请求会先在代理层被截断。
- 需要给本地 admin 生成完整演示 / 测试数据时，先停止本地常驻 gateway/jobs（常驻聚合器与造数的一次性派生重建并发会重复累计同一批用量游标），再执行 `pnpm mockdata`，完成后重启服务。脚本可重复执行，会先清理上一批 `造数-` / `mockdata_` 数据再重建；参数（`--days`、`--daily-requests`、`--data-dir` 等）与造数范围、已知边界见 [Mockdata 造数设计](../functions/Mockdata造数设计.md)。后续新增可复用造数能力统一扩展 Go maintenance 的 mockdata 域，不新增散落的 seed / demo 脚本。
- OAuth token 换取、刷新和账号测试优先使用账号绑定代理；`JUHE_AI_OAUTH_PROXY_URL` 只是兜底代理。
- 如果要复用本地 CLIProxyAPI 已完成的 Claude / Codex / Gemini 等认证，当前推荐把它作为 loopback sidecar 运行，再在 juhe-ai 创建普通 `api_key` 账户：OpenAI / Anthropic 兼容入口填 `http://127.0.0.1:<port>/v1`，Gemini native 填 `http://127.0.0.1:<port>/v1beta`，`API Key` 填 CLIProxyAPI access key；同时在后端显式配置 `JUHE_AI_UPSTREAM_BASE_URL_PRIVATE_ALLOWLIST=http://127.0.0.1:<port>`。
- 模型检测本地服务默认不限制正常探针并发；任意失败重试默认等待 `65s`，若上游返回更长的 `Retry-After` 则按更长时间等待；回归脚本会把等待压低，避免测试套件被真实等待拖慢。
- 后端普通运行日志：go-only 形态下 gateway 的 slog 同时写 stdout 与 `JUHE_AI_LOG_DIR` 下的 `juhe-ai.log`（BUG-0195 修复，2026-09-28 起）；未配置 `JUHE_AI_LOG_DIR` 时仅 stdout，文件日志写侧与 grep 面禁用（启动事件会注明）。`slog.Default()` 由同一多路 logger 接管，HTTP 访问日志（`http_request_started/completed` 等）自此为 JSON 且同步进文件。每条请求日志都会带 `traceId`，响应头也会返回 `x-trace-id`。
- 默认 `info` 只保留每个网关请求的一条 `gateway.request.timing_summary`、耗时达到 `1000ms` 的慢阶段和问题阶段（`unexpected_failure` / `expected_failure` / `aborted` 问题阶段分别升为 `error` / `warn` / `warn`）。Go 网关不再按 standalone/performance 采样阶段详情：成功请求的汇总恒只保留标量诊断（尝试次数、阶段计数、总耗时，`stageDetailsSampled=false`），失败与中断请求的汇总带完整有界阶段列表，不受采样影响。健康检查路径（`/__aisys__/health`、`/__aisys__/api/health`）的成功完成只写 `debug`，避免探针刷运行日志；失败的完成按正常级别保留。
- F1 运行日志索引与其索引保留在 standalone 与 performance 均由 Go jobs 持续执行；`JUHE_AI_LOG_FILE_ENABLED` 自 2026-09-21 起移除（文件日志恒开），gateway 写独立实例 JSONL，jobs 进程自身日志当前仅 stdout（写侧接入为后续项）。`JUHE_AI_RUNTIME_LOG_INDEX_ENABLED` 不再控制 F1，也不能作为 Node importer 的回退开关；轮转文件保留清理由 jobs 索引器承担（只删已完整索引且无 cursor 错误的 rotated 文件），`grep` 仍只读日志文件。
- go-only 形态下 gateway 进程内直接打开业务库并挂载管理 API repository（standalone SQLite 下是业务库唯一写者，WAL、短事务、`busy_timeout` 控制写锁等待）；数据集目录库、使用记录目录库、usage shard 与统计结果库的写入各归唯一 owner（usage shard 由 jobs 的 usage writer 异步写入，统计结果库由 jobs 对应统计任务串行提交）。不存在独立 DB 进程或 IPC 队列可排查：请求链路遇到数据库故障时返回可读错误并短暂快速失败，不静默降级为无数据成功；排障入口是 gateway / jobs 各自进程日志、数据库连接配置（`JUHE_AI_DATABASE_*` / `JUHE_AI_POSTGRES_URL`）与数据库实例本身——SQLite 写锁冲突按单写者边界与 `busy_timeout` 排查，PostgreSQL 按连接池与事务范围排查。
- 高性能模式排障时优先检查 Redis cache / state / queue 三类连接和 Redis Stream consumer lag；不能为了绕过 Redis 故障临时把 `JUHE_AI_CACHE_DRIVER`、`JUHE_AI_RUNTIME_STATE_DRIVER` 或 `JUHE_AI_QUEUE_DRIVER` 改成 `memory` 后继续按高性能模式运行。
- 进程职责边界：gateway 不在请求链路内执行周期后台任务，jobs 不承接在线请求（只保留 loopback 健康端点）。统计聚合与各类窗口刷新、账号质量和统计保留期清理在 jobs 的统计与 retention 任务族；F2 表监控采样、快照写入和 retention 在 jobs；OAuth Access Token 保活、授权到期扫描和可用性时间计划同步在 jobs 的 oauthrefresh 任务族（`openai-oauth-access-token-refresh`、`oauth-keepalive-token-refresh`、`resource-authorization-expiry-sweep`、`api-key-availability-schedule-status-sync` / `account-availability-schedule-status-sync`）；账号周期健康检测与冷却复测在 jobs 的 J1 与探针任务族；记录维护和数据集保留期清理在 jobs 的 cleanup 任务族。手动账号测试是唯一例外：执行队列（含 sweep）已随去跨进程战役收归 gateway 进程内单持有者异步执行，jobs 不再运行该队列，且同样不允许在请求链路内同步执行。任一职责出现在错误进程时需要先修正角色隔离。
- OAuth Access Token 保活扫描仍存在且快过期的 OAuth 账户：OpenAI 族按 `oauth_access_token_expires_at` 为空或进入提前量窗口（默认 `300s`）触发刷新，anthropic / gemini / grok 由 keepalive 计划按各自窗口保活；上游 HTTP、畸形响应、超时、断连、代理或数据库异常只记录诊断并执行有界退避（默认 `300s`，受账户 `config_revision` 保护，账户变更时丢弃退避状态），只有连续 3 次结构化本地配置错误才写入可恢复的 `oauth_token_refresh_local_configuration_invalid`（刷新成功后自动恢复）。OpenAI OAuth 额度快照只由真实网关响应头被动写入，不作为后台主动刷新任务。
- 普通日志默认 `100MB` 滚动，保留 `30` 天、最多 `500` 个历史文件，约束总量约 `50GB`；可通过 `JUHE_AI_LOG_LEVEL`、`JUHE_AI_LOG_DIR`、`JUHE_AI_LOG_MAX_FILE_MB`、`JUHE_AI_LOG_RETENTION_DAYS`、`JUHE_AI_LOG_MAX_FILES` 调整，后端会把保留天数和文件数限制在默认上限内。gateway 文件日志写侧自 2026-09-28（BUG-0195 修复）实现 `JUHE_AI_LOG_MAX_FILE_MB` 大小轮转：默认 `100`，合法 `1..1024`，越界启动失败。
- 网关写下游响应时仍尊重 `res.write()` backpressure；短暂 drain 默认只保留 debug 级运行日志，只有等待超过 50ms 时才写 warn，避免把 0 到 1ms 的正常瞬态当成生产告警。
- 管理后台“日志搜索”的索引查询模式只检索最近 3 天写入 SQLite 索引的普通运行日志，支持按索引日志时间范围筛选；超过 3 天的日志即使日志文件仍保留也不会被索引查询搜到。
- Go 运行日志索引器会在专用 `JUHE_AI_RUNTIME_LOG_DATABASE_PATH` 中持久化文件游标，追踪当前普通日志文件，只读取上次游标之后新增的完整行；首次看到已有日志文件时从文件末尾开始追新内容，避免本地开发重启时反复全量扫描大日志。该专用库不得和业务、数据集目录、usage catalog、stats、Codex Context shard 或 F2 表监控库共用；即使路径不同但通过 hard link/symlink 指向同一物理文件也会拒绝启动。
- 管理后台“表监控”只对管理员开放。Go jobs 内的 F2 默认每 1 分钟采样一次当前运行模式的存储增长：standalone 只读采样业务库、数据集目录库、使用记录目录库、统计结果库和 Codex Context shard，并写入专用 `JUHE_AI_TABLE_MONITOR_DATABASE_PATH`；performance 采样 `juhe_business`、`juhe_dataset`、`juhe_usage`、`juhe_stats` 和 `juhe_codex_context` schema，并把快照写入 `juhe_stats`。SQLite 在受控预算内执行精确 `COUNT(*)`，`dbstat` 不可用时大小指标保持未知；缺少源库或 PostgreSQL schema 时本轮显式失败，不写零值占位快照。F2 历史默认保留 30 天，由同一 Go owner 清理；Node stats-worker、Node retention 和硬清理均不再写入或删除 F2 快照。
- 管理后台“日志搜索”的 `grep 模式` 由 Go 后端在 `JUHE_AI_LOG_DIR` 目录内对保留的 `.log` 文件直接逐行扫描（不依赖 `rg`），多关键字按同一行同时命中处理。时间范围只用于筛选参与扫描的日志文件（默认窗口由墙钟计算最近 3 天、单次最多 7 天；文件按 mtime 不早于窗口起点即参与扫描），不读取文件内容判断行时间；同一 Go 后端进程一次只允许 1 个 grep 搜索，整次搜索共用 15 秒 deadline，命中上限 2000 条。未配置 `JUHE_AI_LOG_DIR` 时 grep 面返回「文件日志未启用」降级，不回显日志目录或内部错误。
- 前端面向中文用户，页面应通过全局 `a-config-provider` 使用中文 locale，避免 Ant Design Vue 默认英文文案出现在界面。
- 启动后先看终端日志里的监听地址和报错信息，不要把具体接口测试矩阵写进本文件。
