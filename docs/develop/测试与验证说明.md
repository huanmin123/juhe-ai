# 开发测试与验证说明

> 面向 AI 与维护者。
> 本文件承接代码级检查、接口验证、网关联通、账号测试和自动烟测；启动方式和运行注意事项见 [开发运行说明](运行说明.md)。

## 1. 适用场景

- 需要确认代码改动没有破坏类型、构建或关键路径。
- 需要验证后端接口、管理面页面、账号测试、网关转发或使用记录。
- 需要执行自动烟测、回归验证或问题修复后的复现检查。

## 2. 代码级验证

在项目根目录执行：

```powershell
pnpm typecheck
pnpm build
```

如果只改了某一端，也可以先跑对应 workspace 的命令，再按需要补全全量验证。

高性能模式中间件已启动后，PostgreSQL 初始化验证使用：

```powershell
pnpm --filter juhe-ai-backend postgres:init-schema-only
pnpm --filter juhe-ai-backend postgres:init-schema
```

`postgres:init-schema-only` 只验证当前版本 DDL；`postgres:init-schema` 会继续写入默认管理员、内置供应商 / 协议 / 协议档案 / 分组和系统设置。默认内置分组只绑定 provider，不引用 provider protocol profile；该契约必须由 `test:postgres-seed-defaults` 固定，避免 PostgreSQL seed 缺项导致创建系统账户时触发 `groups_provider_code_fkey`。完整初始化后必须在开放公网前轮换默认管理员密码。宿主机运行时如果 `JUHE_AI_POSTGRES_URL` / Redis URL 来自 Docker Compose 内部 DNS，需要临时改为宿主机发布端口，具体见 `../deploy/高性能模式部署指南.md`。

PostgreSQL 验证只支持当前 schema 初始化。已有历史测试库不要沿用原结构；需要保留数据时由运维在代码库外离线重建为当前 schema，再运行 `pnpm --filter juhe-ai-backend test:postgres-schema-sql` 固定当前 DDL 边界。

从宿主机或开发机验证 Docker 栈时，不要直接复用应用容器内 URL。容器内可用 `pgbouncer:5432`、`redis-cache:6379`、`redis-state:6379`、`redis-queue:6379`；宿主机需要使用测试主机 IP 和发布端口，例如 `<测试主机IP>:6432`、`<测试主机IP>:6379`、`<测试主机IP>:6380`、`<测试主机IP>:6381`。其中 redis-state / redis-queue 容器内端口仍是 `6379`，但默认宿主机发布端口分别是 `6380` / `6381`。

如果 `redis-cache` 可连接但 `redis-state` 宿主机发布端口超时，登录保护、运行态锁和账号并发 Redis Lua 等路径会卡在 runtime state 连接，`test:performance-system-api-smoke` 可能在登录阶段超时。此时先恢复 redis-state 发布端口或容器，再复跑真实 state 验证；只为验证业务代码路径时，可以临时让 smoke 的 cache/state URL 指向同一个可达 Redis 实例，但报告里必须记录这个 caveat。

Redis 密码包含 `@`、`:`、`/`、`#` 等特殊字符时，写入 `JUHE_AI_REDIS_CACHE_URL`、`JUHE_AI_REDIS_STATE_URL`、`JUHE_AI_REDIS_QUEUE_URL` 或各测试脚本专用 Redis URL 前必须 URL 编码，否则 Node URL 解析会把密码切断，表现为健康检查失败或子进程连错地址。

真实 Redis cache / runtime state driver 回归使用：

```powershell
$env:JUHE_AI_REDIS_CACHE_URL = "redis://:<Redis缓存密码URL编码>@<测试主机IP>:6379/0"
$env:JUHE_AI_REDIS_STATE_URL = "redis://:<Redis运行态密码URL编码>@<测试主机IP>:6380/0"
pnpm --filter juhe-ai-backend test:runtime-state-cache-redis
Remove-Item Env:\JUHE_AI_REDIS_CACHE_URL, Env:\JUHE_AI_REDIS_STATE_URL -ErrorAction SilentlyContinue
```

该命令覆盖 `SharedJsonCache` 的 TTL / delete / clear 版本失效、`RuntimeStateStore` 的 JSON 读写 / `incr` 上限 / lock token 释放、登录失败锁定和账号并发 Redis Lua 原子占用；脚本只写入带 `regression_*` 后缀的临时 key，并在结束时按 pattern 清理。

客户端 IP 策略单 IP Redis shared cache 回归使用：

```powershell
$env:JUHE_CLIENT_IP_POLICY_SHARED_CACHE_REDIS_URL = "redis://:<Redis缓存密码URL编码>@<测试主机IP>:6379/0"
$env:JUHE_AI_ALLOW_CLIENT_IP_POLICY_SHARED_CACHE_CLEANUP = "1" # 仅确认该 Redis 是测试实例时设置
pnpm --filter juhe-ai-backend test:client-ip-policy-shared-cache-redis
Remove-Item Env:\JUHE_CLIENT_IP_POLICY_SHARED_CACHE_REDIS_URL, Env:\JUHE_AI_ALLOW_CLIENT_IP_POLICY_SHARED_CACHE_CLEANUP -ErrorAction SilentlyContinue
```

该命令在临时统计库创建 active policy，通过普通判定按 `ip_hash` 从数据库索引回源并写入单 IP Redis shared cache，随后验证 `cacheOnly` 能命中该单 IP 条目；禁用策略后先确认未失效的旧单 IP 条目仍会被 `cacheOnly` 命中，再通过绕过 shared cache 的重载清理旧条目；清理 shared cache 后，`cacheOnly` 不应回源数据库，普通判定应再次回源并重建单 IP 条目。该脚本会切换 / 清理固定 cache namespace；非本机 Redis 必须显式设置 `JUHE_AI_ALLOW_CLIENT_IP_POLICY_SHARED_CACHE_CLEANUP=1`，且只允许指向测试 Redis 或维护窗口内实例，不能直接打正在承载生产网关的 Redis。它同时固定 Redis cache driver 下 IP 策略判定不加载全量 active 策略快照的边界。

## 4. 本地网关验证

客户端接入时使用 OpenAI 兼容协议：

- Base URL：`http://127.0.0.1:3000` 或 `http://127.0.0.1:3000/v1`
- API Key：`API Key 管理` 或 `我的 API Key` 页面生成的本地网关密钥
- 通用入口：`/models`、`/responses`；`/chat/completions` 只在当前 API Key 绑定的路由策略分组能选到 OpenAI API Key / OpenAI-compatible 上游账号时验证。
- OAuth / Codex 边界：GPT OAuth 账号只覆盖 `POST /responses` 和 `POST /responses/compact`（含 `/v1` 前缀），不会把 `/chat/completions` 自动翻译到 Responses。

`$LiteKey` 使用 API Key 页面新建后返回的明文密钥，或同步脚本首次输出的 `sync.apiKey`。

本机 `backend/data/juhe-ai.sqlite3`（或 `JUHE_AI_DATABASE_PATH` 指向的业务库）可能已经保存真实 GPT 账户、本地网关 API Key 和分组绑定；`JUHE_AI_DATASET_DATABASE_PATH` 指向的数据集目录库保存审计、日志索引、操作日志、公开接口日志和模型检测事实；`JUHE_AI_USAGE_CATALOG_DATABASE_PATH` 指向的使用记录目录库保存 usage shard 注册表和筛选目录；`JUHE_AI_USAGE_SHARD_ROOT` 指向的目录保存新写入的使用记录；`JUHE_AI_STATS_DATABASE_PATH` 指向的统计结果库保存统计缓存、额度窗口和监控历史。四个主 SQLite 文件路径必须互不相同，usage shard 根目录也必须与这些文件路径区分。需要真实联通验证或烟测时，可以优先复用本地业务库里的数据，不必重复创建；但不要把真实密钥写入文档、提交记录、Issue、截图或聊天内容，只在本机命令会话里临时赋值。

本地网关 API Key 的列表和更新响应只返回前缀、掩码或空 key，不从管理面列表接口批量取回完整密钥；新建成功响应、页面弹窗和单条复制接口可按资源权限返回完整密钥。需要手工验证时，使用刚创建后保存到当前 PowerShell 会话的 `$LiteKey`、在 API Key 列表复制完整密钥，或使用 `pnpm test:smoke` 自动创建并清理临时本地网关 API Key：

```powershell

```

真实上游账户只用于本地联通验证；优先通过账户测试接口、网关请求或 `pnpm test:smoke` 验证可用性，不要直接导出或打印上游账户凭据。账户测试和后台复测必须走本地 OpenAI 网关处理链路，不能在测试服务里单独直连上游；测试产生的请求、token、成本、错误和账号命中记录必须和客户请求一样进入使用记录、审计和必要统计，不隐藏成本、不丢弃账户配置。统计、质量和授权消耗口径通过 `traffic_source` 区分普通 `gateway`、手动 `manual_account_test` 和恢复探活 `cooldown_retest`；未产生 token / cost 的失败按 0 token、0 cost 计入请求和错误次数。人工测试产生使用记录和审计事实，但不得修改账户状态、账户内 API Key 状态、健康检查信号、冷却字段、最近错误或调度可用性。

```powershell
$LiteKey = "你的本地网关 API Key"

Invoke-RestMethod http://127.0.0.1:3000/v1/models `

  input = "只输出 OK"
  max_output_tokens = 16
  stream = $false
} | ConvertTo-Json -Compress

Invoke-RestMethod -Method Post `
  -Uri "http://127.0.0.1:3000/v1/responses" `
  -Headers @{ Authorization = "Bearer $LiteKey" } `

```

## 5. GPT OAuth 账户验证

前端路径：

```text
http://127.0.0.1:5173/__aisys__/accounts
```

新增 GPT OAuth 账户时，可选两种 OpenAI OAuth 授权方式：

- `手动授权`：生成授权链接，登录完成后复制浏览器地址栏里的 `http://localhost:1455/auth/callback?code=...&state=...` 回调 URL，粘贴回弹窗创建账户。
- `Refresh Token`：直接粘贴已有 OpenAI `refresh_token`，后端刷新成功后创建 OAuth 账户。

已有 GPT OAuth 账户在账户列表“更多”菜单中提供两个排障入口：

- `刷新令牌`：强制使用当前账户保存的 Refresh Token 换取一次 Access Token；成功后账户会刷新凭据，限流中、临时不可调用等软失败状态会恢复可调度，停用和异常不会被这个入口恢复。异常账户前端隐藏刷新入口，后端也会拒绝直接刷新，需要先走“恢复异常”或通过编辑修正凭据。失败会直接显示 OAuth 或代理错误。如果遇到 OpenAI 返回 `refresh_token_reused` 或 “Refresh Token 已被使用”一类提示，但账户仍能继续调用，通常表示另一个请求或后台任务已经先完成刷新并写入了新凭据；后端会在锁内重读账户并优先采用最新凭据。
- `重新授权`：打开独立弹窗复用新增账户的授权流程，可通过授权回调 URL 或新的 Refresh Token 覆盖当前账户 OAuth 凭据；名称、分组、代理和并发不随重新授权修改。异常账户前端隐藏重新授权入口，后端也会拒绝直接重新授权。

后端授权链接接口可用以下命令做冒烟检查：

```powershell
$AdminCookie = "juhe_ai_session=..."

Invoke-RestMethod -Method Post `
  -Uri "http://127.0.0.1:3000/__aisys__/api/openai-oauth/auth-url" `
  -Headers @{ Cookie = $AdminCookie } `
  -ContentType "application/json" `
  -Body "{}"
```

OAuth token 交换、刷新、重新授权和账户测试会使用账户绑定代理；网关真实转发也会使用账号绑定代理。OAuth token 交换、刷新和重新授权属于授权协议请求，不计入模型使用统计；账户测试会通过同一套网关模型请求链路计入使用记录。后台 Access Token 预刷新只做授权保活，会扫描所有仍存在、未删除、有 `refresh_token` 且快过期的 GPT OAuth 账户，不因停用、异常、限流或临时不可调用状态跳过；预刷新成功只写回凭据，不自动恢复普通账户状态；连续 3 次预刷新失败会把账户标记为 `status = error`，异常类型为 `oauth_token_refresh_failed`，后续后台刷新成功只自动恢复这一类刷新异常。真实网关请求只在 Access Token 缺失、过期、过期时间无效或距离过期不超过 5 秒时阻塞刷新；距离过期小于 60 秒但仍超过 5 秒时只触发账号级后台预热并继续当前请求。后台冷却复测固定启用，但只会复测冷却时间到期的 `temporary_unavailable` 和 `rate_limited` 账号；临时状态下的 `cooldown_until` 表示下次后台复测计划时间，不作为账户套餐到期时间展示。账号质量主动测速能力已删除；真实质量样本触发的频繁失败后台确认仍保留，确认探针使用 `traffic_source = cooldown_retest`，不进入账号质量统计。OAuth 额度快照不再主动探测，只从真实网关请求响应头被动更新；人工测试不得更新额度快照。

## 6. 账户与管理面验证

账户列表“更多”菜单里的“测试”会调用后端 `POST /__aisys__/api/accounts/:id/test`；用户侧 `我的 AI 账户` 调用 `POST /__aisys__/api/my-accounts/:id/test`，固定使用当前登录用户作用域。创建 / 编辑账户弹窗底部的“测试”使用当前表单快照，并固定以表单中的 `healthCheckModel` 执行，不开放临时模型选择；新增自有账户调用 `POST /__aisys__/api/accounts/test-draft` 或 `POST /__aisys__/api/my-accounts/test-draft`，编辑已保存自有账户把未保存表单快照提交到单账户测试接口。保存新增或导入账户时，即使请求状态为 `active`，也必须先落为 `pending_test`，由后台激活检查成功后改为 `active`；关键连接字段编辑保存后同样交后台复检，不以人工测试结果激活或恢复账户。授权账户仍按已保存账户测试。管理员在管理侧可通过 `systemAccountId` 代某个用户作用域测试其可见账户。

测试内部按协议档案构造最小本地网关请求并复用正常网关链路验证账户是否可用；OpenAI v1 API Key 账户的请求形态只由本次测试提交的 `clientCompatibility` 决定：`openai_standard` 使用 `/v1/chat/completions` 最小 Chat Completions 请求，`codex_responses` 使用 `/v1/responses` SSE 最小 Responses 请求；GPT OAuth 账户会在网关准备上游账号时按正常请求规则刷新 token，并固定使用 Codex Responses 测试路径。人工测试、后台激活检查、周期健康检查、冷却复测和事前确认探针都不根据历史流量切换 endpoint / stream；测试不过即表示该账户不能承接本次测试形态。Anthropic API Key 账户使用 `/v1/messages`，不会绕过使用记录。系统探针必须严格使用账户 `health_check_model`；账户创建时按“当前所有者供应商个人默认 > 管理员系统默认 > 协议档案默认”初始化一次，后续默认变化不回写已有账户，也不回退到账户支持模型首项。账户列表测试先按需调用 `GET /__aisys__/api/accounts/:id/test-options` 或 `GET /__aisys__/api/my-accounts/:id/test-options`，可选择该账户供应商、协议档案与所有者作用域内可见且启用的文本目录模型，不受 `supportedModels` 限制；所选模型只用于本次诊断，不保存到账户。诊断重试的所有 attempt 使用同一轮开始时确定的模型。OpenAI API Key 账户的 Responses 测试按当前契约不发送 `max_output_tokens`。账户测试和后台复测结果携带本地 `traceId`，上游错误文本中的 `request id` 必须保留；排障时本地链路用 `traceId` 查询运行日志、使用记录和审计日志，上游链路用 `request id` 查询供应商日志。OAuth 账户固定显示 Codex Responses。测试输入由后端使用默认探活输入生成。测试只允许命中当前被测账户，不会静默切到同分组其他账号。

手动账户测试的真实请求等待策略为 `10s + 20s + 30s`。产品不提供多账户批量测试；后端账号测试 worker 只异步消费用户显式发起的单账户测试任务，并按系统设置 `accountTestTaskConcurrency` 控制全站并发。单个任务的 60s 运行超时只从后台任务进入 `running` 并写入 `startedAt` 后开始计算；`queued` / 等待后台接收的任务也必须记录 `queuedAt`、等待时长和最近投递 / 接收状态，超过队列等待上限后自动收口为失败或取消，避免后台异常时长期卡住并持续堆积。worker 从数据库补充 runnable 测试任务时必须按固定窗口读取，不能一次性把所有 queued 任务灌入内存队列。每次单账户测试创建独立 `testSessionId`，同一用户的 A/B 两次测试互不阻塞、互不覆盖、互不取消；“停止测试”只取消当前会话。关闭弹窗、切换菜单、刷新页面或浏览器会话丢失只中断当前前端接收，后端任务继续执行。前端用 `sessionStorage` 保存 12 小时终端快照，重新进入页面后按对应 `testSessionId` 恢复接收；若浏览器会话已丢失，则通过后端任务列表和检测结果查看最终结果。

模型检测和代理检测仍共享 DB service 诊断任务 in-flight 上限；超过上限会快速返回 `503` 和 `Retry-After`，不会在 DB service 事件循环内排队等待外部探测。账户测试和模型检测展示用响应体只保留 `256KB` 有界预览，异常大响应会标记 `responseTruncated` 并追加截断提示，避免管理接口因为上游异常响应占用过多内存或同步解析大文本。自有账户包含停用和异常状态都可以手动测试，但成功或失败都只形成诊断结果，不得清理或写入 `pending_test`、`temporary_unavailable`、`rate_limited`、`error`、冷却、最近错误、健康检查信号、账户内 API Key 运行态或调度状态。只有后台激活检查、周期健康检查、冷却复测和事前确认探针可以按各自策略推进运行态。授权账户测试额外要求已绑定到当前用户分组、授权仍有效、额度未耗尽、账户未到期；授权用户只看到脱敏后的测试结果，完整上游响应头、响应体、上游地址、代理、请求体和无状态码内部异常文本等诊断字段仅所有者或管理员可见。授权实例不提供批量编辑；显式异常账户仍通过专用恢复动作或后台策略处理，不能借人工测试恢复调度。

## 7. 性能综合测试

需要评估本机模拟链路的 QPS、延迟、错误率和资源占用时，可以运行：


该命令会启动临时 SQLite 业务库、统计数据集目录库、使用记录目录库、usage shard 目录和统计结果库、本机模拟 OpenAI 上游和临时网关实例，并通过 Mockdata 共享夹具自动创建压测 GPT 分组、GPT API Key 类型账户和本地网关 API Key；测试结束后删除临时数据目录，不消耗真实 OpenAI 额度，也不污染 `backend/data/`。

验证 fresh PostgreSQL migration 时，应显式设置部署 IANA 时区：

```powershell
Set-Location backend-go

goose -dir db/migrations postgres $env:JUHE_AI_POSTGRES_URL up
```

`Asia/Shanghai` 只是示例，必须替换为实际部署 IANA 时区。migration `000024` 优先使用 `JUHE_AI_USAGE_STATS_TIMEZONE`，未设置时回退 PostgreSQL `TimeZone`，再回退 `UTC`；Node / Go 共存期必须与 Node `Intl` 实际部署时区一致。PostgreSQL 在线 PATCH 禁止修改 `usageStatsTimezone`。当前真实依赖 smoke 仍受本机无 Docker 阻塞，不能把 integration `SKIP` 写成通过。

system API 六项限流设置的当前默认值依次为：IP read 每分钟 `600`、IP read 每 10 秒 burst `120`、IP write 每分钟 `180`、IP write 每 10 秒 burst `40`、用户 read 每分钟 `300`、用户 write 每分钟 `120`。Go 读取这些设置后缓存 60 秒；验证配置热更新时应等待缓存刷新或构造可控时钟，不能把 60 秒内继续使用旧值误判为设置未生效。

当前系统不提供“特征规则”菜单、只读接口或运行时规则表；协议内错误和污染内容通过响应检查策略和客户端能力门控处理。非 2xx 上游错误响应统一进入账户错误处理策略和兜底确认流程：未命中账户错误处理规则时先同账号短重试，再尝试后续账号；后续账号成功则本次请求救回。所有候选账号都失败时返回网关统一 `service_unavailable` 错误，不再透传最后一个上游错误，也不再维护请求级上游错误签名缓存。

检查点：系统不存在特征规则管理接口；前端菜单不出现“特征规则”入口。上游 `invalid_request_error` 类错误不应首账号直接短路，应由回归覆盖“切号成功”“第三账号救回”“全部账号失败统一兜底”和“本地屏蔽耗尽快速失败”路径。

检查点：系统设置页能保存并回显；流式异常达到阈值后账号列表会显示临时不可调用、限流中、长期不可用或异常摘要；临时不可调用与限流状态可以通过账户列表“更多”菜单的专用恢复动作清理冷却与最近错误并恢复调度，不能通过人工测试恢复。冷却到期后的后台复测会自动处理 `temporary_unavailable` 和 `rate_limited`；复测连续失败会按指数退避，单次暂停不超过最大暂停时间，超过 `cooldownAccountRetestMaxBackoffHours` 表达的长期不可用观察阈值后保持原状态并继续低频复测，`last_error_code` 变为 `cooldown_retest_long_term_unavailable`。`cooldownAccountRetestLongTermIntervalHours` 控制长期不可用后的低频自动复测间隔。“启用账户”只用于真正停用的账户，不用于清理临时状态。账户测试只提供人工诊断，停用、异常、待检查、临时不可调用和限流账户的测试成功或失败都不得改写运行态、健康信号、账户内 API Key 或调度状态。后台激活检查、周期健康检查、冷却复测、OAuth 刷新和网关异步错误处理必须遵守各自状态边界，不能绕过停用硬边界或普通显式异常硬状态。

账户健康检查优先队列回归执行 `pnpm --filter juhe-ai-backend test:retry-queue-priority` 和 `pnpm --filter juhe-ai-backend test:account-health-check-dispatch`。必须验证首次激活优先于普通周期复检、普通任务不能占满全部并发槽、等待中的重复任务升级为最新内容、运行中的重复任务完成后只追加一次，以及普通新增、导入、OAuth 和外部推送入口都携带首次激活原因即时投递。
