# 后台任务迁移总设计与路线图

> 状态：2026-08-21 已更新 J3 L1 语义冻结；本文件不授权启动新 owner、停止 Node worker、修改生产路由或迁移对外网关。J1/J2 的“已生产 Go-owner”状态来自用户提供的生产事实，不由本地源码推断；仍须按各自契约保留回滚与证据。

## 1. 目标与非目标

目标是把周期性、可恢复、可独立验收的后台功能迁入 `backend-go/projects/jobs`，使它可以独立构建、部署、重启和观测。每个任务完成后只有一个 scheduler、一个状态 writer 和一条恢复路径。

本阶段不迁移 Node 对外网关、管理 API、AI 请求代理、路由策略、候选选择、用户鉴权、配额、流式响应、G2/G3 网关运行态或 F3/F4 的 gateway 数据 owner。Node 继续是这些主业务的唯一 owner，不能因为 jobs 需要账户信息而把网关调用链搬进 jobs。

## 2. 不可违反的边界

1. Go `jobs` 不调用 Node，也不调用 Go `gateway`。禁止 `JUHE_AI_NODE_INTERNAL_*`、gateway URL、Node IPC、Redis Stream、Node DB service 和任何隐式 fallback。
2. jobs 的账户探活、余额刷新、复制校验与模型检测直接请求账户配置的真实上游。它们是最小诊断协议，不是网关请求的缩小复制品。
3. PostgreSQL 下，jobs 只经冻结的数据库契约读取候选和写入已接管的任务事实；SQLite 下，同一业务 SQLite 文件只能有一个 writer，jobs 不得成为 Node/gateway 文件的第二 writer。
4. SQLite 需要账户输入时，由当前业务 owner 单向推送经签名、版本化的诊断快照到 jobs 自己的 Store；jobs 的结果由 Node 通过只读稳定协议消费。Go jobs 绝不反向轮询或调用 Node。
5. 任务只有在 Node scheduler、queue/IPC、写入分支、部署入口和回退分支清零后才算接管；一个“Go 可以运行”的影子任务不是完成。

### 2.1 范围升级与停止规则

Node 现有实现只用于行为取证，不能自动成为 Go 的依赖设计。若任一后台任务要闭环而需要调用 Node、Go `gateway`、网关运行态、未接管业务 writer、额外凭据权限、共享 SQLite 文件、对外 API 或不在当前迁移契约中的 owner，实施立即停在取证/契约阶段。

停止报告必须列明：已验证的 Node 行为、最小依赖环、影响的 owner/数据/接口、为什么当前范围不能独立 handover、可选拆分或重设计方案、生产与回滚影响。只有用户明确选择扩大范围、改变设计、拆为独立功能或暂缓后，才可修改实现；禁止自行新增 bridge、fallback、双写或“先同时跑”的临时路径。

## 3. 直接上游诊断契约

### 3.1 输入与资格

每次任务从稳定候选事实取得：账户与授权来源 ID、`configRevision` / `dispatchRevision`、provider、protocol、profile、账户类型、endpoint mode、health model、base URL、代理引用、凭据引用、可调度状态、cooldown、到期时间和授权绑定。读取后、发起上游前必须再次校验资格与 revision；发生漂移时记为 stale，不发请求。

凭据只能使用已经过审计的共享秘密管理或可独立解析的加密引用。Node 当前凭据格式、代理、URL 白名单、授权实例来源和协议字段必须在每个 provider 切片中逐项冻结并用兼容 fixture 验证。没有稳定的 jobs 凭据读取路径时，该 credential-requiring task 不能迁移。

### 3.2 请求行为

- 每个诊断只发一次直接上游请求；默认不跟随重定向、不经网关、不做路由或账号 fallback。
- 使用账户自身 base URL、代理、TLS、协议和 endpoint mode。URL/DNS/private-address 策略、代理启用状态、超时、body 上限和取消必须显式校验。
- OpenAI、Anthropic、Gemini 及 OAuth/API key 的探测请求按各自 provider native 语义构造；不得套用对外网关的 body bridge、用户 token 或模型重写。
- 图片账户优先使用不产生付费生成的 models-catalog 证据；多 API key pool、Codex 专有刷新或跨协议诊断不在首个直接探测切片中，必须另立契约，不能静默选第一个 key。

### 3.3 结果分类与写入

使用冻结的四类结果：`complete_success`、`framing_complete_neutral`、`upstream_failure`、`probe_task_failure`。完整 HTTP framing 但诊断业务失败是 neutral；只有已证明的上游 timeout/connection/read-incomplete 才是 `upstream_failure`；本地 URL/凭据/取消/执行器错误不得伪装为账户故障。

健康成功、failure threshold、temporary unavailable、cooldown、余额快照和模型质量是不同的状态机。每个 writer 都必须使用 account/config/dispatch/generation/观察时间等 fence、稳定幂等键和 owner lease；`Changed=false`、neutral、task failure、取消或旧 revision 不得产生自动恢复或账户状态变更。

## 4. 数据模式

| 模式 | 候选输入 | 任务事实写入 | 禁止事项 |
| --- | --- | --- | --- |
| PostgreSQL | 冻结的 `juhe_business`/授权/代理契约，只读候选窗口 | 已 handover 的任务表在短事务内 CAS；统计写各自 owner 表 | 调 gateway/Node；未 handover 前写账户业务事实；共享无界 queue |
| SQLite | jobs-owned snapshot Store，由当前业务 owner 单向签名输入 | jobs-owned outcomes、cursor、统计或结果 Store；Node 仅只读结果 | 打开或写 Node/gateway business SQLite；双 writer；Go->Node RPC |

> 方案 A 例外：J3b 不使用上述 `jobs` 输入/结果模式。J3b 的管理入口、直接执行、scheduler、结果与质量/health 投影均在 `gateway` 同进程完成；`jobs` 对 J3b 启用配置硬失败，`maintenance` 仅执行显式离线 schema/backfill/审计。该例外不放宽唯一 writer、三库回填、切换/回滚或 Node active-path-zero 门禁。

SQLite 结果协议、snapshot 版本、签名 domain、重放保护、凭据引用、结果读模型和切换顺序是每个 credential-requiring task 的 L1 门禁；没有这些内容不得启用 scheduler。

## 6. 历史归档与未来批次

### 6.1 历史归档：J1/J2 实施步骤

以下内容保留为 J1/J2 的历史实施记录，不构成未来路线，也不授权重新执行或切换 J1/J2 owner。两项当前状态以用户提供的“已生产 Go-owner”事实为准；未来仅保留生产证据、回滚与审计职责。

1. **部署基线（历史）。** F1/F2/F3/F4 的独立构建、SQLite、可销毁 PostgreSQL/PgBouncer、Node→Go RPC、启动器和 Docker 验证。
2. **J1 冻结与 direct-probe（历史）。** Node scheduler、queue、IPC、DB service、候选 SQL、credential/proxy、四类结果、CAS/fence、冷却复测和管理读模型的冻结与实现。
3. **J1 双模式与 handover（历史）。** SQLite 单 writer/snapshot-result 协议、PG fixture/CAS/lease/recovery、candidate 和 Node scheduler/queue/IPC/writer drain。
4. **J2（历史）。** 其冻结、实现和 handover 证据仍以 J2 完整迁移契约为准；不得把旧“J2–J6 顺序”当作未实施路线。

### 6.2 未来顺序：从 J3 开始

1. J3a 已完成 Go 独占实现与本地质量门；后续只推进隔离开发环境的 PostgreSQL/PgBouncer/Redis smoke、真实 Node→Go manual 联调、active-path-zero、owner handoff、重启/回滚与 L4 验收，不再设计 Node projector 或双 writer。
2. J3a 完整 handover 后，J3b/J3c 仍分别维护各自 owner 与契约；共享 writer/数据的实际切换必须串行。J3b 按方案 A 在 Gateway 单进程处理模型检测、直接上游 probe、SSE heartbeat、探针级失败隔离和结果状态；不得复用 J3a 的代理结果表，也不得引入 DB-service/Node/跨进程 proxy。
3. J3c 先拆统计刷新、失败前置确认、模型质量三种 writer，再分别建立契约；不得把质量检查写成模型检测的别名。
4. 账号复制保持排除，等待产品/历史路线图澄清后另立任务。J4–J6 也仅在 J3 的相应完整 handover 和独立契约后重新排序，不继承历史顺序。

## 7. 每个批次的验收门

- Node→Go 字段、资格、URL/代理、凭据、失败和状态机对照完整。
- jobs 的单元、race、取消/超时、单条失败隔离、重复/旧 revision、owner lease 和恢复测试通过。
- SQLite 证明不存在第二 writer；PostgreSQL/PgBouncer/Redis 使用可销毁资源证明事务、锁、连接和 namespace 隔离。
- direct upstream smoke 覆盖成功、neutral、timeout/connection/read-incomplete、错误凭据/代理、取消和无重试 fallback。
- candidate 部署验证 health、任务 freshness、结果 readback、日志/指标、停止 drain 与回滚；生产切换前保存旧 owner 的运行证据和恢复路径。
- Node 活跃扫描、启动器、Docker、systemd/launchd、package script、worker/IPC/queue/schema owner 与 manifest 全部归零后，才归档 Node 专属源码。

## 8. 明确禁止的捷径

- 为了“先跑起来”让 jobs 调 Node/internal API 或 Go gateway。
- 在 SQLite 上让 jobs 与 Node 同时写业务文件，或以 retry/queue 掩盖锁冲突。
- 用网关 HTTP 状态、用户流量、audit/usage 或 G2/G3 状态替代诊断结果。
- 把所有后台功能塞进一个全局队列、一个无限重试 worker 或一个无版本 payload。
- 以开发 PG smoke、health 200 或 Go 二进制存在宣称生产已接管。
