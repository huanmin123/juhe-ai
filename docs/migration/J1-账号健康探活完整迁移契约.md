# J1：账号健康探活与冷却复测完整迁移契约

> 状态：L4 本地代码归档完成，2026-08-17。Go `jobs` 是唯一 J1 task owner，Node 旧 scheduler/RetryQueue/Gateway diagnostic/IPC/loopback bridge 已移除并归档；本文仍不授权生产切换。

## 1. 结论

J1 接管的是完整的“账号健康探活与冷却复测状态机”，不是仅周期扫描。Go `jobs` 将成为唯一的候选调度、直接上游探活、结果/状态/Key 池游标 writer、冷却复测和结果保留 owner。Node 保留账号 CRUD、Gateway 请求生命周期及 OAuth provider writer；它只可作为 J1 稳定输入的生产者，以及由业务 SQLite 单写者执行的**通用结果投影者**。投影者不执行探活决策、调度、重试或上游请求。

Go `jobs` 不调用 Node、Go `gateway`、Node IPC、Redis Stream 或 Gateway HTTP。Gateway request-failure 触发通过稳定数据协议投递 probe request；Gateway 只按同一 source fence 读取 Go outcome 并结算自身运行态。

## 2. Node 旧行为冻结（归档依据）

- primary `ops-worker` 每分钟调度 `account-health-check`，经 DB-service 读取候选并投入 Node `RetryQueue`；入口见 `backend/src/modules/background/background-jobs.ts`、`account-probe-jobs.ts` 与 `account-health-check.service.ts`。
- 当前执行复用 `account-test.service.ts` 的 `handleOpenAIGatewayRequest`，因此会进入 Gateway 上游准备、side effect flush 和 usage record queue；这不是 Go 的可复用依赖。
- 当前成功/失败由 DB-service 写 `accounts.last_health_*`、状态、冷却、group stats、cache invalidation 与 API Key pool cursor。SQLite 业务库 writer 是 Node DB-service。
- 触发来源包括周期、创建/激活、连接配置更新、导入、OAuth 建账、外部推送、Gateway request failure 和 Codex source avoidance。现有 loopback bridge、worker IPC、DB-service IPC 和 shared availability coordinator 均属于待下线 J1 Node owner。

## 3. 功能范围和非目标

J1 包含：候选资格、API Key pool、按冻结协议 profile 分派的直接探活（OpenAI-compatible、Anthropic Messages、Gemini GenerateContent/Interactions，以及显式模型映射的 Hybrid）、`pending_test` 激活检查、`active` 周期检查、request-failure 二次确认、冷却复测、四类结果、账户/Key 健康状态、source-fence outcome、租约、取消、重试、保留、读模型、Node owner drain 和归档。

J1 不包含：公共 Gateway、请求路由、用户鉴权、用量 writer、Redis Stream、Circuit/G2/G3 运行态、OAuth token/provider writer、余额刷新和模型质量检查。`account-api-key-cooldown-retest` 维护的是 API Key runtime-state，不写 J1 account health/cooldown 事实，也不属于本次账户级 J1 owner；它在 Node 保持独立 owner，不能在 J1 归档时被误删。OAuth access token 过期、缺失或未通过 J1 输入验证时，J1 记录 `probe_task_failure`，不刷新、不轮换、不写任何 OAuth 凭据；后续 J4 OAuth owner 负责令牌保活。

J1 输入必须冻结 `provider_protocol_profile_id`、协议代码/版本、账户类型、endpoint mode、模型和认证所需的附加字段；Go 不得仅凭物理 `provider_code` 猜测协议。当前已接入的 profile 覆盖 OpenAI/GPT、xAI、DeepSeek、GLM、Anthropic、Gemini 原生/Google OAuth，以及显式 `account_model_mappings` 解析后的 Hybrid。Gemini `generate_content_sse` 的 mapping 源族固定为 `stream_generate_content`；identity mapping 不构成有效转换。OAuth 只使用 Node 已发布且未过期的 access token，J1 不刷新或轮换凭据。输入中出现未冻结 provider/profile/type/mode/mapping 时必须成为可观察的 `probe_task_failure`，不得调用 Gateway、猜测协议或回退 Node；新增供应商/协议要先扩展本契约并完成对应实现后才可进入候选。

## 4. 唯一 owner 与数据协议

| 事实 | PostgreSQL | SQLite | 唯一 writer |
| --- | --- | --- | --- |
| 账号配置、授权绑定、代理定义、配置 revision | `juhe_business` 既有业务表 | Node business SQLite | Node 主业务 |
| J1 输入 snapshot/request | `juhe_jobs.account_health_inputs`、`account_health_probe_requests` | Node 原子发布的签名 versioned input 文件 | Node 输入生产者 |
| J1 outcome、current state、Key pool cursor、lease | `juhe_jobs.account_health_*` | `JUHE_AI_ACCOUNT_HEALTH_DATABASE_PATH` 专用库 | Go `jobs` |
| J1 outcome 到 `accounts` 的业务投影 receipt | business DB 的 `account_health_projection_receipts` | Node business SQLite 的同名表 | Node DB-service（仅通用 projector） |
| Gateway source fence 运行态 | Gateway 自身 runtime/Redis（只读消费 outcome） | Gateway 自身进程运行态（只读消费 outcome） | Node Gateway |
| 管理页健康展示 | 只读 J1 state/outcome DTO | 只读 J1 专用库 DTO | Go `jobs` 写、Node 读 |

Node 不写 J1 result/state/cursor/lease，Go 不写 Node business SQLite、usage shard 或 Gateway runtime。Node 的唯一写回行为是消费已完成且未投影的 Go outcome，并在一笔业务库事务内按结果中声明的目标账户、输入/配置/调度/复测 fence 更新允许的账号健康投影字段、写 receipt、刷新既有 group stats/cache 失效标记；CAS 拒绝仅记 receipt 为 `stale`，绝不重放或改写 Go outcome。该 projector 必须是 DB-service 内的通用稳定协议实现，而不是账号探活 scheduler、队列或 Gateway 适配。

上述 owner 边界约束常驻运行路径，不阻止一次性生产数据库维护。经当前任务明确授权并遵守 `.local/project-resources/prod/runbooks/生产数据库维护.md` 时，可以通过本地 PostgreSQL 连接对指定账户执行受控数据修复、回填或向前兼容的加法式 schema 变更；该操作必须是显式 allowlist、可审计、幂等且不覆盖未知或同 epoch fence，不得演变为第二个常驻 writer。应用代码和 Kubernetes 变更仍按 GitOps 发布。

PostgreSQL 的 `juhe_jobs` schema 必须由外部 bootstrap 预创建并归 jobs output role 所有；jobs 启动时只验证该 owner 并在 schema 内创建或升级自己的表，不得为“首次启动方便”取得业务数据库级 `CREATE` 权限。启用 PG direct-input 时，jobs 还必须在获取 J1 lease 前以零行只读查询验证冻结业务/统计表、`SELECT` 授权和关键设置；缺表或授权不完整必须启动失败，不能在运行后重复报错或由 jobs 修复 Node business schema。Node outcome reader 只能被授予该 schema 的 `USAGE`/`SELECT`。

因此，`accounts.status`、`schedulable`、`cooldown_until`、`last_error_*`、`last_health_*` 与 `cooldown_retest_*` 的业务投影 writer 在 SQLite 始终是 Node DB-service；J1 的决策事实和唯一任务 owner 始终是 Go。PG 也采用同一投影路径，避免按数据库类型产生双语义。Node 业务配置每次影响探活资格、凭据、代理、授权绑定、模型或 endpoint mode 时，必须发布新的不可变输入版本；Go 只接受当前版本。初始全量输入只能由显式 maintenance/backfill 命令生成，不能在常驻路径中隐式迁移历史数据。

初始全量 bootstrap 的维护入口为 `pnpm maintenance:backfill-account-health-jobs-input [--execute] [--limit N]`（在 `backend/` 执行）。默认是 dry-run；只有 `--execute` 才为当前符合 J1 input producer 资格且不存在 `account_health_jobs_input_versions` 行的账户写入 `snapshot` durable outbox intent。脚本复用现有 eligibility read adapter，并在写入事务中重新检查 input version；重复或并发运行不会为已有 epoch 再推进版本。它不直接发布 input 文件、不调用 Go、不启动常驻扫描；发布文件仍由受控 Node input publisher 消费 outbox。输出只包含脱敏统计和 account ID，`--limit` 默认 `1000`、最大 `100000`。若经生产数据库维护手册明确授权直接 SQL 回填，也必须等价保持上述 outbox、签名、revision 单调性和幂等约束，不得借“修数据”绕过 J1 输入契约。

### 4.1 输入契约

每个输入具有稳定 `account_id`、独立且单调递增的 `input_version`、`config_revision`、`dispatch_revision`、签发时间、过期时间和 HMAC/signature key ID。`input_version` 来自 Node business DB 的 `account_health_jobs_input_versions.current_version`，不能从 config/dispatch revision 算术推导；资格变化、禁用、删除、授权撤销、代理停用和 tombstone 必须先保留新 epoch，再发布替代 snapshot。它包含：

- provider/type/protocol profile/endpoint mode、health model、base URL；候选资格读取阶段另外校验 supported models/modes、绑定、授权和 proxy 事实；
- 授权来源账户的 config revision、授权/分组绑定、有效期与 quota eligibility 由 Node eligibility 和 `source_config_revision` fence 共同约束；未满足资格不发布 snapshot；
- API Key pool 的 key-set fingerprint、顺序、每 Key 的加密 credential envelope；
- OAuth 的 access-token envelope、expires-at、可选 `chatgpt_account_id` / `oauth_account_id`、Google quota project、OAuth type 与 project ID；J1 不接收 refresh token 或 client secret；
- 受限的 proxy envelope、connect/read deadline、最大响应大小和 TLS/URL policy version。

PostgreSQL 直接读取冻结的业务列时，Go 使用共享、版本化的 `v1:<iv>:<tag>:<ciphertext>` AES-256-GCM 凭据格式和已有 `JUHE_AI_SECRET` key derivation 解封；这是稳定数据协议，不调用 Node。SQLite snapshot 携带相同 cipher text 以及 input signature，Go 只接受已验签的 current revision。Go 不读取 Node IPC，不产生明文日志，也不把凭据、token、代理密码或完整 URL 写入 outcome、指标、错误或测试产物。

输入发布和失效规则固定如下：Node 先在业务写事务保留新的 snapshot epoch，再发布完整 immutable input；读取端只承认同一 `account_id` 的最大、未过期 `input_version`，projector 也只接受当前保留 epoch。删除、禁用、授权撤销和 proxy 停用发布 tombstone input；运行态进入冷却或因套餐过期停用时，账户状态写入与其 snapshot/tombstone intent 必须在同一业务事务完成，并同步 fan-out 到以它为物理 source 的授权实例。Go 在发请求前、每次 API Key pool 尝试前和提交 outcome 前重验 input fence；任一失配中止未开始请求并记 `stale`。SQLite 文件以临时文件、fsync、原子 rename 发布；envelope 使用 `hmac-sha256-v1`，签名覆盖 `algorithm + "\\n" + key_id + "\\n" + payload` 的精确 UTF-8 bytes，payload 以 base64url 封装原始 input JSON。旧签名、未知 key 或重新序列化后的 payload 一律拒绝。

即时 request 也是签名事实；Go 仅在 request ID 对应 outcome 已幂等提交后删除其自身已消费的 request 文件。崩溃或删除失败时保留文件，下一轮先检查 outcome 再清理；Node 不回收 request，也不因重复文件重复探活。

### 4.2 候选与冷却语义

Go 只从 current input 决定候选，不能重新扫描 Node SQLite 或向 Node 查询。周期健康候选必须同时满足：未删除；`type` 是 `api_key`、`oauth` 或 `google_oauth`；mode 属于已冻结的 `chat_json`、`chat_sse`、`responses_json`、`responses_sse`、`images_json`、`messages_json`、`messages_sse`、`generate_content_json`、`generate_content_sse`、`interactions_json`、`interactions_sse`；状态为 `active` 或 `pending_test`；`active` 必须可调度；不在冷却且未到期；存在 enabled group binding。为避免图片生成成本，`active + images_json` 账户不因 `next_health_check_at` 到期进入周期候选；`pending_test` 的首次激活检查、明确账户加载以及 `temporary_unavailable` / `rate_limited` 的冷却恢复不受此排除。授权实例还必须有有效、已绑定、未超额度的 authorization 与可调度、未到期、未冷却且未标记 `account_expired` 的物理 source account。排序为 `pending_test` 优先，然后按上次/下次检查、创建时间和账号 ID 的稳定序；最新真实成功会推进下次检查以避免无意义重探。

冷却复测候选仅接受 `temporary_unavailable` 或 `rate_limited`、可调度、冷却已到期且具备完整 observation/generation fence 的 current input；授权实例额外重新验证 source、授权、绑定和额度。冷却结果为 `success`、`defer` 或 failure，并由 Go 生成带五元 fence 的投影；Node projector 只在输入 revision 与所有观察代次仍匹配时改动业务状态。未满足候选条件、输入过期或授权撤销都不是“探测失败”，而是 `stale` / `probe_task_failure`，不得进入失败阈值。

### 周期探活时间偏离

周期 `next_due_at` 以及后续被动失败/冷却重试必须由 Go jobs 使用全局被动偏离策略生成：小于 1 分钟 ±30 秒（窗口不超过周期一半）、1 分钟至小于 1 小时 ±30 秒、1 小时至小于 1 天 ±30 分钟、1 天至小于 1 周 ±1 小时、1 周及以上 ±8 小时。偏移每轮重新抽取并持久化到 outcome/current state；Node 的 `health_jitter_ms` 只保留协议兼容性，不得将 Go owner 降级为固定准点或稳定单向偏移。Node input publisher、outcome projector 和 source-fence consumer 的空闲外层轮询同样使用这一策略，但已领取消息/outcome 的 ACK、fence/CAS 与投影立即完成。首次激活、显式 request-failure、租约续期和其它事件驱动控制路径保持原有即时语义；首轮激活仍立即执行，不以随机延迟阻塞用户可见的建账结果。

> API Key 多 Key 额度恢复是独立的 Key runtime 契约：网关收到明确的 `403` 额度不足时只写当前 `key_fingerprint`；供应商提供 `reset_at` / `Retry-After` / reset header 时必须原样作为该 Key 的 `cooldown_until`，但 `next_probe_at` 必须在该截止之后按全局偏离策略重新随机安排。没有可靠时间时同样按账户 `quota_recovery_policy` 的 duration 加全局随机偏移复测。通用模式连续确认 30 天后该 Key 写入 `error`，从自动候选移除，只有人工重新验证才能回到 `unverified`；明确 reset 模式不得进入该 30 天终局。当前 Node 已实现这组 Key runtime 规则；`backend-go` 后续接管时必须把 recovery mode、recovery start、manual-terminal 和 per-fingerprint fence 纳入 Go/Node 迁移输入输出，不能按账户级每日额度猜测。

### 4.3 source-fence 契约

Gateway 发生可确认的 request failure 时写入 `source_probe_request`，字段至少为 `request_id`、`account_id`、`config_revision`、`source_generation`、`source_fence_id`、`runtime_key`、`probe_generation`、原因和 deadline。Go 以 `request_id` 幂等执行，结果写入同一 request 的 `source_probe_outcome`。

Node Gateway 仅按 account/revision/fence 精确读取结果并结算自己的避让状态；`complete_success` 可以结算成功，其他结果保持或按 Gateway 自身既有运行态规则结算。若 Node 在 Go-owner 模式下连签名 request 事实也无法发布，只能由 Gateway 内部同一 CAS helper 结算该 fence 为 `unknown`；不得绕回旧 worker IPC。Go 不清理任何 Gateway runtime key，也不依赖 Redis/IPC/HTTP 回传。

## 5. 直接上游探活契约

每次执行只使用输入 snapshot，先校验签名、时效、provider/mode、资格和 revision；任一失败均不发上游请求。Go 使用独立 `http.Client`/Transport、账户代理、禁止重定向、请求/响应大小上限、context deadline 与取消；按账户和真实资源有界 fan-out，不使用 Node RetryQueue 或全局迁移并发阈值。

- API Key：按冻结顺序和持久 cursor 诊断 Key pool；首个成功停止未开始请求，结果记录 winner fingerprint/index。cursor 绑定 account、purpose、key-set fingerprint 与 config revision。
- OAuth：仅使用有效的 input access token；到期或接近到期即失败为 task failure，不能调用 refresh endpoint 或写 token。
- `chat_json`：`POST {base_url}/v1/chat/completions`，body 固定为 `model`、单条用户消息“只能回复：juhe”、`max_tokens: 256`、`stream: false`；成功必须得到非空 assistant 文本且包含精确挑战值 `juhe`。
- API Key `responses_json`：`POST {base_url}/v1/responses`，body 固定为 `model`、单条 `input_text` 挑战、`instructions`、`max_output_tokens: 256`、`stream: false`；成功必须取得完整响应并验证精确挑战值 `juhe`。
- OAuth `responses_json`：`POST https://chatgpt.com/backend-api/codex/responses`，同一固定 body 并强制 `store:false`，加 `openai-beta: responses=experimental`、`chatgpt-account-id`（输入存在时）和 OAuth Bearer token；不得复用 API Key base URL、客户端会话、attestation 或 refresh 路径。
- `images_json`：`POST {base_url}/v1/images/generations`，使用低质量、单张最小诊断请求，并要求响应包含 `data[].b64_json` 或 `data[].url`；该请求只用于首次激活或图片账户已进入不可用/限流后的恢复探活，正常 `active` 图片账户不做周期生成。
- `chat_sse` / `responses_sse`：分别使用对应 OpenAI-compatible SSE 完成事件和 `juhe` 输出；GPT OAuth `responses_sse` 与 JSON 共用 Codex `/responses` 路径。
- Anthropic `messages_json` / `messages_sse`：`POST {base_url}/v1/messages`，API Key 使用 `x-api-key`，OAuth/GLM Coding 使用 Bearer，并验证 `message_stop` / `stop_reason` 与 `juhe`。
- Gemini `generate_content_json` / `generate_content_sse`：使用 `:generateContent` / `:streamGenerateContent?alt=sse`；API Key 使用 `x-goog-api-key`，Google OAuth 使用 Bearer。`interactions_json` / `interactions_sse` 使用 `/v1beta/interactions` 和 `api-revision` 完成事件；Code Assist/Google One OAuth 仅允许 GenerateContent 探活。

各协议使用其冻结的认证头和 `Accept`（JSON 或 SSE）；不跟随重定向，`base_url` 必须为 HTTPS 的绝对 URL（明确允许的本地开发地址由输入 TLS/URL policy 标识）。协议/状态码/JSON 验证失败形成 `framing_complete_neutral`；仅已发送 HTTP(S) 请求后的 timeout、连接或不完整读取形成 `upstream_failure`。凭据、代理、输入、取消、deadline、JSON 本地解析或不允许 URL 的失败为 `probe_task_failure`。

结果严格为：

| 结果 | 含义 | 账户健康状态写入 |
| --- | --- | --- |
| `complete_success` | 已完成直接上游请求且诊断成功 | 成功 state、清失败、安排下次 |
| `framing_complete_neutral` | HTTP framing 完整但诊断语义未成功 | 对账户检查按冻结规则计为可用性失败；对 transport/circuit 保持中性 |
| `upstream_failure` | 已证明真实 HTTP(S) transport timeout/connection/read-incomplete | 写适用失败 state；request-failure 二次确认可进入冷却 |
| `probe_task_failure` | 输入、资格、凭据、代理、取消、deadline、解析或本地执行失败 | 仅 outcome/指标，绝不改变账户可用性 |

所有状态写入都校验 account/input/config/dispatch/retest generation fence、owner lease 和幂等 request ID。旧输入、取消、失租和 CAS 拒绝为 `stale`，不得覆盖新状态。

## 6. 状态、读模型与 Node 适配

J1 current state 覆盖当前 Node 的健康事实：最近检查/成功、下次检查、失败窗口/次数、状态码、错误摘要、trace/request ID、冷却观察 generation 和 API Key pool winner。它不复制 Gateway circuit 或用户请求运行态。每一个可投影 outcome 都带 `projection`：`target_account_id`、`input_version`、`config_revision`、`dispatch_revision`、可选 `source_config_revision`、必填 `expected_account_status`、可选 `expected_cooldown_fence`、输出 `cooldown_fence`、`transition_kind` 与只含允许字段的值；它不是可执行 SQL。Node projector 只接受白名单 transition，例如 activation success、health success、health failure、temporary unavailable、cooldown success/defer/failure，并以同一事务写 `account_health_projection_receipts(outcome_id, applied_at, disposition, account_id, input_version)`。任何缺失期望状态或把输出 fence 当作期望 fence 的投影都必须拒绝，不能以“当前状态相近”放宽 CAS。

Node 管理读 repository、账户列表投影和 Gateway account selection 必须从投影后的业务状态和只读 J1 DTO 读取；Node 业务写路径不再直接更新 `last_health_*`、health failure/cooldown re-test 的 J1 字段。真实请求成功是否生成新的 J1 health input/outcome 必须通过显式稳定 request 事实实现，不能直接跨 owner 更新 Go state。

既有 `account_health_hourly` 仍是 usage 聚合读模型，不得作为 J1 outcome/state writer 或回退来源。AI 健康监控页面在 Go-owner 模式下按当前页账户、时间窗只读 jobs-owned outcome，并同已有小时表历史合并；它不写 usage record、小时表或 J1 store。J1 自己的 outcome/state 形成可审计事实后，J3 再迁移其统计聚合。

### 6.1 投影字段白名单

projector 只能使用 Go outcome 的 `observed_at`、`next_due_at`、`status_code`、错误摘要、失败窗口/次数和 projection fence，写入下列固定字段；任何未列出的 `projection.values` 键直接 `rejected`，不允许把 payload 当 SQL 或通用 patch。

| transition | 必需前置 | 固定写入 |
| --- | --- | --- |
| `activation_success` | `pending_test` | `active`、`schedulable=1`、清 cooldown/error/retest，写 health success 与下次 due |
| `health_success` | `active` | 写 health success、清 health failure；不覆盖当前业务 `schedulable` |
| `health_failure` | `active` 或 `pending_test` | 只写 health failure/window/next due，不重新计算阈值或 backoff |
| `activation_error` | `pending_test` | `error`、`schedulable=0`、清 cooldown/retest，写 terminal error 与 health failure |
| `temporary_unavailable` | `active` | `temporary_unavailable`、`schedulable=1`、写 output cooldown fence/due/error 与 health failure |
| `cooldown_success` | cooling status + expected cooldown fence | `active`、`schedulable=1`、清 cooldown/error/retest，写 health success 与下次 due |
| `cooldown_defer` | cooling status + expected cooldown fence | 仅按 Go output fence/due 更新 cooldown/retest 和 health observation |
| `cooldown_failure` | cooling status + expected cooldown fence | 仅按 Go output fence/due/error 更新 cooldown/retest 和 health failure |

每次 `UPDATE` 同时比较 `id`、未删除、input epoch、config revision、dispatch revision、expected status，以及授权来源 revision 或完整 cooldown fence。更新 0 行必须写 `stale` receipt；已存在 receipt 原样返回且不得产生再次写入、group stats 标脏或 cache 失效。状态/可调度性发生变化时，group stats dirty 与 receipt 位于同一业务事务，cache 和 Gateway 本地 cache 仅在提交后失效。
