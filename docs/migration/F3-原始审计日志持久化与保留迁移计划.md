# F3 原始审计日志持久化与保留迁移计划

> 建立日期：2026-08-09。
> 状态：实施中；本文冻结 F3 的范围、契约、完成条件和后续工作，不把设计或历史 Node 行为写成已经接管。

## 1. 决策与范围

F3 是继 F1“运行日志索引与保留”、F2“表存储监控采样与保留”之后的下一个完整 Go 接管功能：**原始审计日志持久化与保留**。

Go 最终是以下事实的唯一 owner：审计记录、流式 `in_progress -> finalized` 更新、attempt、payload 引用与 blob、错误分组、热搜索索引、审计保留清理、相关 schema、启动/停机生命周期和运行指标。

本期不迁移网关请求调度、账户管理、模型检测、操作日志、公开接口日志、usage records、通用数据保留或审计只读页面。Node 网关仍负责在请求生命周期内收集审计字段；Node 管理端可在过渡后的 F3 专用事实库上保留只读查询，不能再写入、调度、清理或回退到 Node 审计 writer。

操作日志与公开接口日志都是独立的完整功能，后续分别作为 F4、F5 冻结和接管；不得为了共用“日志”名义把它们混进 F3。

## 2. 当前 Node 基线与保留契约

当前 Node 审计捕获由 gateway audit capture 形成 `AuditLogInput`，包含稳定 ID、trace/session、账号/模型/结果、attempt、payload、采样和生命周期信息。流式请求会先形成 `in_progress`，终态使用同一 ID 提交 `finalized`。早期 body、鉴权与权限拒绝也会形成相应的 dropped capture。

Node 当前通过 Redis Stream、IPC、本地队列和 transport worker 将数据送入 dataset writer；这些均为 F3 要退出的运行机制，不是可在 Go 接管后保留的兼容层。审计还包含 payload blob 文件、引用计数、错误分组和 hot-search 文件，不能只迁 `audit_logs` 主表。

原始审计当前是非阻塞、best-effort 记录：业务响应不等待审计落库；容量满、超大输入、传输失败或进程异常可能丢弃可丢记录，但必须保留原因、数量和日志。F3 保持此可观察语义，不承诺在没有 durable outbox/spool 的条件下“进程崩溃后绝不丢失尚未提交的审计”。若未来要求该保证，必须另行冻结 durable outbox/spool 完整功能，不能把内存 goroutine 伪装成可靠队列。

## 3. Go 直接异步模型

F3 不引入 Redis Stream、Asynq、Node IPC 审计队列、Go 通用 task queue、常驻 worker pool 或 Node/Go owner 开关。

Node capture 在请求结束后异步向本机 Go F3 sidecar 发送已归一化的审计输入；该调用不阻塞已经可返回的客户端响应。Go sidecar 收到输入后由当前请求 goroutine 直接执行校验、幂等写入与必要的 payload/blob 处理。Node 的职责止于输入生产和失败计数；它不缓存、不重试成队列、不落库，也不改由旧 Node writer 接手。

这不是无限并发承诺：

- SQLite：F3 使用独立审计事实文件，启用并回读验证 `journal_mode=WAL`、`busy_timeout=5000`；同一物理文件只有 Go F3 单 writer。并发请求直接等待该 writer 的事务完成，禁止每个 goroutine 另开写连接规避单写者。
- PostgreSQL：请求可直接并发写入，但受连接池、事务/语句超时、唯一 ID、行锁和 payload 文件 I/O 的真实资源边界约束；这些是正确性和资源边界，不是业务限速或迁移队列。
- 任一配置、连接、schema、owner lease、写入或 payload 失败必须留下原始错误和可观测计数；禁止静默 fallback 到 Node、另一种存储或伪造成功。

Go F3 使用 owner lease 与单调 fence token 排除失租旧实例提交。稳定审计 ID 保持幂等；同一流式审计的终态必须按现行语义更新同一记录，而不是新增重复记录。

## 4. 双模式存储边界

### SQLite

`JUHE_AI_AUDIT_LOG_DATABASE_PATH` 是 F3 专用事实库。它不得与业务库、dataset、usage catalog、stats、usage shard、Codex Context shard、F1 运行日志库或 F2 表监控库指向同一个物理文件，包括 hard link 和 symlink 情形。

Go 是该文件唯一 writer；Node 审计查询只读打开它。现有 dataset SQLite 中的 audit 表、payload 元数据与相关索引必须在切换前停止 Node/Go 后通过 F3 的明确离线迁移命令复制并逐表校验。常驻 F3 进程不得附加旧 dataset、自动复制或回退读取旧表。

### PostgreSQL

F3 Go 直接拥有 `juhe_dataset` 中 F3 审计表的 schema 与 DML owner；Node 仅保留读查询。Go schema 必须独立初始化 F3 对象，fresh PostgreSQL 验收不得先依赖 Node audit schema 初始化制造通过。

## 5. 完整接管项

完成 F3 前必须同时具备：

1. Go `cmd/juhe-ai-audit-log-writer`、配置、监听/停机、SQLite/PG Store、owner lease/fence、schema、blob 文件 owner、hot-search、retention 和观测；
2. Node gateway audit capture 到 Go sidecar 的直接输入契约，覆盖普通、流式、请求中止、早期拒绝、采样过滤、payload 大小与生命周期；
3. 记录、attempt、payload refs/blobs、error groups、热搜索与读取 DTO 的字段、权限、分页和 payload 读取契约；
4. F3 的 hot/full/failure/error-group retention 与 payload/blob 无引用清理，不再由 Node `data-retention-cleanup`、`audit-hot-retention-cleanup` 或 record-maintenance 处理；
5. Node audit queue、Redis consumer、IPC message、transport worker、server shutdown audit drain、scheduler、runtime health、schema writer 和写回归全部退出活跃路径；共享文件先拆出 F3 专属模块，不能删除仍服务 operation/public/usage 的共享代码；
6. Node 专属文件、专属脚本和测试按完整文件集归档至 `migration-backup/node/audit-log-write-retention/`，manifest 固定 SHA-256、Go 实现位置、停用入口、双模式验证和回滚提交；
7. SQLite、PostgreSQL、并发、重复 ID、流式终态、取消、停机、重启、lease 丢失、payload/blob、错误分组、hot-search、保留清理、Node 只读 API 与隔离开发环境端到端验证均通过。

## 6. 明确非目标和阻断规则

- 不迁 Node 网关主流程：只替换其审计输出目标，不把账户选择、上游 dispatch、响应转发或业务副作用移入 Go。
- 不复用或新增审计任务队列；不保留 Node audit writer、Redis Stream、IPC transport、worker thread 或长期双 owner。
- 不迁 operation/public/usage writer；它们仍在 Node 的 dataset/usage owner 边界内。
- `dataset-schema.ts`、`server.ts`、`worker.ts`、`background-jobs.ts`、通用 retention 与 runtime 配置均是共享文件；必须先拆分 F3 专属文件并回归，不能仅删除其中若干行后声称完整归档。
- 任何无法证明重启、失败或存储隔离语义的实现只能标记为“实现中”，不能切 Go owner 或归档 Node。

## 7. 实施顺序与提交边界

1. 本文和 Node -> Go 证据矩阵：固定现行字段、表、调用方、读取、保留和共享耦合。
2. 先做不改变 Node 行为的 F3 专属拆分，并用 Node 回归固定捕获与持久化契约。
3. 实现 Go F3 双模式 owner、直接输入协议、离线 SQLite 数据迁移和 Go 测试。
4. 在隔离开发资源完成 Node capture -> Go F3 -> SQLite/PG -> Node 只读 API 闭环；失败路径、重启/停机和压力证据必须单独记录。
5. 一次性切 Go 唯一 owner，清零 Node F3 活跃路径，归档完整 Node 文件集，更新启动/部署/Mockdata 文档，最后独立总审。

每一步按完整可审计功能提交 Git；不得把账户、网关主流程、模型检测或其他维护者的工作混入 F3 提交。

- 已完成：Node capture、queue/transport、writer、读取、保留、schema、调用方和测试盘点；该条是 F3 接线前的历史基线，当前活跃路径已改为 Node capture -> Go 一次性输入，Go 负责持久化与保留。
- 已完成：F1/F2 的独立 SQLite owner、WAL/busy timeout、lease/fence、Go 直接异步和 Node 归档模式可作为结构参考，但不能机械复制其表模型或本机时钟 lease 细节。
- 已完成 foundation 验证：Go F3 的独立 DTO、schema、Store、lease/fence、blob 原子发布与 PostgreSQL smoke 已具备基础实现。2026-08-10 在可销毁的 `juhe_ai_sub2api_dev_f3_smoke_20260810` 上，以 PgBouncer 应用连接执行真实 PostgreSQL smoke，通过后已强制删除并复核库不存在；该证据只覆盖 foundation，不能替代完整 F3 闭环或生产验证。
- 已完成开发实现：Go 已实现 F3 独立 schema/store、lease/fence、payload/blob、错误分组、hot-search、hot/full/failure/error-group retention，以及显式离线 SQLite 迁移 CLI；迁移工具要求 Node/Go 双停机确认、源表/blob 完整性和复制后逐表核验，常驻进程不会自动调用。Go loopback HMAC 输入 server 的 `POST /__aiinternal__/v1/audit-captures` 仅接受 4 MiB 以内、签名正确的本机 JSON 输入，事务和 blob 均完成后返回 `204`；Node capture（包括普通、流式和早期拒绝）已改为对应的一次性输入客户端，无本地队列、重试或 fallback，并在发送前按成功/问题正文窗口执行 4 MiB JSON 收敛：普通摘要不伪标为丢弃，必须裁剪结构时使用 `transport_budget` tombstone，超大 payload 列表直接收敛为范围 tombstone，避免单条输入占用无界 CPU。Node 管理路由已切到显式 F3 专库只读适配器（SQLite `readOnly`/`query_only`，PostgreSQL `BEGIN READ ONLY`，schema 缺失显式失败）；旧 Node audit queue、Redis consumer、IPC、transport、writer、retention、schema 和 db-service/read-worker 专属入口已退出活跃路径。
- 已完成隔离开发端到端验证（2026-08-10）：管理员仅经 `5432` 创建和清理一次性库，应用仅经 PgBouncer `6432` 连接。真实 `dispatchAuditLogToGo` 发送 `in_progress` 后，Go health 与输入均返回 `204`，Node F3 只读适配器读回同 ID/trace 的 `in_progress`、`metadata_only`、0 attempt、0 payload；停止 writer 后 health 不可达。以同一稳定 instance ID、最小允许 owner lease `5s` 等待 `5.5s` 到期后，新 PID 成功接管并返回 health `204`；发送 `finalized` 后 Node 读回同 ID/trace 的 `finalized`、1 attempt 和 1 payload，headers/body storage 均为 `available`。无效 HMAC 返回 `401`。测试结束后 writer PID、临时 profile/log/控制脚本和目标库会话均为 0，目标库已删除并复核不存在；主库、Redis、`shared.env` 和生产环境未触碰。
- foundation 放行硬条件：blob 必须先在同目录临时文件完整写入并原子发布；未获 lease、事务回滚、提交结果不确定或失租时不得删除可能已被其他提交引用的 blob。`OpenStore` 或尚未获得 lease 的进程不得创建 blob 目录或清理其他实例的临时文件。复用已有 blob 时必须读取其真实 ID、压缩方式和尺寸，不能假定新 ID；不得把 Go gzip 字节等同性当作 Node gzip 的兼容条件。attempt/payload、hash-only 与截断 body 的原始 hash/尺寸、空 headers、headers 标量/数组、gzip、非负压缩节省、emoji 错误摘要与错误分组的乱序 first/last 语义必须与 Node 基线逐项对齐。同一稳定 ID 的并发终态竞争中，只有实际插入或从 `in_progress` 更新成功者可以写 attempt、payload ref 或增加错误分组，失败者不得产生子表副作用。PostgreSQL lease/fence 必须使用数据库的实时钟，并在不把所有审计请求串行化的前提下防止失租事务提交；PG 的 blob 引用事实以 refs 为准，不在热路径为共享 blob 更新 `ref_count`。PG retention 与 Persist 对同一审计记录必须先取得同一 audit-ID 生命周期锁，再按 blob ID 取得 blob 生命周期锁；retention 在锁后复核候选条件，先提交可重试 GC 意图。物理删除失败必须保留元数据和 GC locator，提交后出现新引用时必须取消 GC 而不得删除其文件。SQLite 隔离还必须递归覆盖 `JUHE_AI_USAGE_SHARD_ROOT` 的真实分层 shard、路径、hard link 与 symlink。F3 fresh schema 必须具备 Node 只读查询和 F3 保留所需的 F3 专属索引。
- PostgreSQL smoke 放行硬条件：真实 smoke 仅可连接经显式配置、可销毁且开始时 F3 表为空的专用数据库；不满足即失败、不得写入。开发环境测试库必须遵守 `juhe_ai_sub2api_dev_f3_smoke_<name>` 命名，禁止使用长期开发主库。每次使用唯一测试标记，测试结束必须清理其审计行、blob 文件和 lease 并复核零残留；不能让 `t.TempDir()` 删除仍被数据库引用的 blob。smoke 必须覆盖同 ID 并发赢家/输家、“旧写事务完成初始 fence、租约到期被接管、提交前 fence 拒绝整个事务”，以及 pending blob GC 与同内容新引用交错、物理删除失败后保留可重试 locator。fresh PostgreSQL schema 还须含 Node 前缀查询所需的 `COLLATE "C"` 索引。Codex Context shard 与 usage shard 一样必须做实际文件的物理 identity 检查，而不是只检查 F3 文件是否位于根目录下。
- 已完成归档：`migration-backup/node/audit-log-write-retention/manifest.json` 固定 59 个归档文件的 SHA-256、停用 Node 入口、Go 实现位置、回滚提交和部分验证边界；归档不假定单一源提交，必须以每项路径和 SHA-256 复核。归档只能按 manifest 的整体回滚规则处理。
- 待完成：对当前固定工作区进行独立总审；随后再单独验证发布包、Docker/Mac 常驻生命周期、生产 listener、回滚和切流。开发闭环不得写成生产部署通过。
