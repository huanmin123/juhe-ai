## 1. 范围与非目标

F4 的完整功能边界是管理操作日志：Node 管理路由生产一条已归一化的操作日志输入，Go `gateway` 项目负责认证接收、校验、幂等写入、读取、保留、SQLite/PostgreSQL schema 和运行生命周期；Node 管理路由在切换后只保留生产输入和调用 Go 读 API 的适配，不再拥有操作日志写入、队列、保留或存储 schema。

F4 不迁移或改造以下范围：

- F3 原始审计日志及其主链路、owner、表、读写协议和保留策略；F3 主链路明确不改。
- F1 运行日志、F2 表存储监控、F5 公开接口日志、F6 usage records/统计，及网关请求调度、账号选择、上游 dispatch、响应转发。
- Node 业务资源自身的事务、鉴权模型、管理路由业务语义和前端页面功能；F4 只替换操作日志这一提交与读取所有者。
- durable outbox、长期双写、Node fallback、Redis Stream/IPC 兼容层或新的通用任务队列。

F4 完成后，Go 是操作日志的唯一持久化、读取和保留 owner；Node 不得保留第二个 writer、第二个保留任务或另一套可回退查询源。

## 3. 输入、默认值、脱敏与幂等

### 3.1 输入契约

Go loopback RPC 接收的操作日志输入至少保留当前 `OperationLogInput` 的全部字段和含义：

- 标识和请求：`id`、`traceId`、`createdAt`、`method`、`path`、`statusCode`、`clientIp`、`userAgent`。
- actor 与作用域：`actorSystemAccountId`（必填）、`actorUsername`、`actorDisplayName`、`actorRole`（必填）、`operationScopeSystemAccountId`、`mode`。
- 业务操作：`module`、`action`、`operationKey`、`resourceType`、`resourceId`、`resourceName`、`summary`；其中 `module`、`action`、`operationKey`、`resourceType`、`summary` 均必填。
- 细节与可见性：`detailLevel`、`visibilityScope`、`changes`、`metadata`、`targets`、`viewers`。
- 子对象字段：change 的 `field`、`label`、`before`、`after`、`sensitive`；target 的 `targetType`、`targetId`、`targetName`、`targetOwnerSystemAccountId`、`relation`；viewer 的 `systemAccountId`、`visibilityReason`、`detailLevel`。

传输协议必须为仅 loopback 可达、带时限、带请求体上限的签名 RPC。签名校验、时间/重放边界、JSON 校验或存储不可用时必须拒绝该条输入并记录原始错误与受影响 ID；不得改投 Node writer、另一个存储模式或队列。业务级单条输入失败不得退出 HTTP listener 或整个 Go gateway 服务。

### 3.2 固定默认值与归一化

- 缺少 `id` 时，在 Node 发送前生成稳定 ID；Go 只接受并以该 ID 执行幂等。缺少 `createdAt` 时同样在 Node 发送前固定，禁止重试时改写时间。兼容切换前已有 producer 的输入缺项只能通过一次明确的边界归一化补齐，不得让存储层生成不稳定重试 ID。
- `mode` 默认 `self`，`detailLevel` 默认 `full`，`visibilityScope` 默认 `targeted`，`changes` 默认 `[]`，`metadata` 默认 `{}`。
- 若 `resourceId` 或 `resourceName` 存在且没有 `relation=primary` 的 target，添加 primary target：type 为 `resourceType`，owner 为 `operationScopeSystemAccountId`。
- 除 `admin_only`、`all_users` 外，targeted 记录自动增加 actor 的 `actor_self` viewer；scope 与 actor 不同则增加 scope viewer，admin actor 的原因为 `admin_managed_my_resource`，否则为 `resource_owner`。viewer 按 `systemAccountId:visibilityReason:detailLevel` 去重，空账号不写入。
- target relation、visibility reason、mode、detail level、visibility scope 必须维持当前枚举域；未知值不得静默降级。

### 3.3 脱敏与稳定 ID 幂等

`changes` 在进入 RPC 前沿用当前 `safeChange`/`sanitizeOperationChanges` 语义：凭据、token、key、secret、password 及现有同义字段只记录“未设置/已设置/已变更”，不写入原文；非敏感字符串最大 200 字符，其他可 JSON 化值最大 500 字符；超过 `operationLogMaxChangesPerRecord`（有效范围 1..500）的 change 以 `__truncated__` 记录余量。Go 不得重新暴露被 Node 脱敏的信息，也不得因序列化失败丢弃整条记录；`changes`/`metadata` 不可 JSON 化时分别固定为 `[]`/`{}`。

同一稳定 `id` 的首次成功提交创建主记录及所有子记录；后续同 ID 提交必须为幂等成功，不创建重复主记录、targets、viewers 或 search terms，也不得覆盖首次已提交字段。主记录、子表和搜索词必须在同一 SQLite 单写事务或 PostgreSQL 事务内原子完成。

## 4. 业务提交与失败语义

业务资源变更先按现有业务事务成功提交，再提交操作日志。同步 `runLoggedOperation` 在业务事务返回后记录；异步 `runLoggedOperationAsync` 在业务操作成功后记录。操作日志输入、签名发送、RPC、校验或存储失败只写运行日志/失败计数，并不回滚已经成功的业务事务、不改变原业务 HTTP 成功响应，也不补做资源修改。

Node 只负责一次直接提交已归一化输入；不得建立内存重试、持久队列、Redis Stream、IPC worker、长期双写或 Node 存储 fallback。Go 可在单请求内执行受限的存储操作，但不能将该语义改写成新通用队列。失败必须可观察：至少包含 operation log ID（存在时）、producer、module/action、错误类别和原始错误；敏感内容继续脱敏。

## 5. 双模式存储、schema 与历史迁移

### 5.1 SQLite

F4 SQLite 使用 Go 操作日志专用事实库；该物理文件不得与业务库、dataset 其他未接管功能、F1/F2/F3 专库或 usage/statistics 文件共用，包括 hard link/symlink。Go `gateway` 是唯一 writer，启用并验证 WAL 与明确的 busy timeout；SQLite 写入必须经单 writer 串行化，不能以每请求新写连接绕开文件级单写不变量。Node 读 API 仅通过 Go RPC，不得直连写或保留旧 SQLite reader 作为 fallback。

### 5.2 PostgreSQL

Go 在 `juhe_dataset` 拥有 `operation_logs`、`operation_log_targets`、`operation_log_viewers`、`operation_log_summary_search_terms` 及其约束和索引的 schema/DML owner。写入使用连接池和单个 PostgreSQL 事务；稳定 ID 为主键冲突边界，子表只对本事务实际新插入的主记录写入。fresh PostgreSQL 验收必须由 Go schema catalog 独立完成，不得先运行 Node schema 初始化。`gateway` 即使连接 URL 回退到共享 `JUHE_AI_POSTGRES_URL`，也必须在 `CREATE TABLE IF NOT EXISTS` 后校验五张 F4 表的关键列类型、主键、级联外键和必需索引；任一旧 Node 表不兼容都 fail-closed，提示先离线迁移，绝不静默接管。

### 5.3 Schema、索引与归档

主表至少保存 actor、scope、operation/resource、summary、detail/visibility、`changes_json`、`metadata_json`、request fields 和 `created_at`；三个子表分别保存 target、viewer、summary search term。保留当前按 `created_at,id` 的时间排序/游标语义，以及 actor、scope、module/action、resource、visibility、trace、target、viewer、search term 所需索引。详情关联主表时必须保留外键级联删除。

切换前旧 Node dataset 中的操作日志只能在 Node 与 Go writer 均停止后，由明确、可重跑的离线迁移命令处理；常驻 gateway 不得自动附加旧库、后台复制或读旧表回退。SQLite 使用 `juhe-ai-gateway --migrate-operation-log-legacy-sqlite --operation-log-source-db <旧 Node dataset SQLite> --node-stopped --go-stopped --backup-confirmed`，只读源库并复制到配置的 F4 专库，保留稳定 ID，重建派生 search terms；源/目标同一物理文件会拒绝。PostgreSQL 的旧 Node/F4 表都位于 `juhe_dataset` 且同名，不允许复制到运行中的第二个 owner；仅在完整备份和双停机确认后使用 `juhe-ai-gateway --migrate-operation-log-legacy-postgres --node-stopped --go-stopped --backup-confirmed` 在事务、advisory lock 内将旧 viewer 三列主键升级为 Go 的四列主键，并按批重建 F4 search terms 和所需索引，再由严格 catalog 校验确认。两种迁移都要求固定版本、主/target/viewer 行数核验、按 `created_at,id` 首尾抽样的完整主记录、原始 JSON、target/viewer 字段核验；SQLite 重跑时相同稳定 ID 必须逐字段一致，否则 fail-closed。失败不得切 owner、不得删除或改写 SQLite 源数据。历史数据迁移完成不等于允许长期双写。

## 6. 读 API、权限与投影

Go `gateway` 提供由 Node 管理路由转发的等价读 API，保持如下外部路由语义：

- `GET {systemApiPrefix}/operation-logs` 与 `GET {systemApiPrefix}/operation-logs/:id`：仅管理员；无权限按现有鉴权拒绝，详情不存在返回现有“操作日志不存在”语义。`systemApiPrefix` 由部署配置决定，当前挂载入口见 `system-api-app.ts`。
- `GET {systemApiPrefix}/my-operation-logs` 与 `GET {systemApiPrefix}/my-operation-logs/:id`：已登录用户；只可见 `all_users`，或 `targeted` 且其账号在 viewer 表中存在的记录；个人详情必须按有效 viewer detail level 裁剪。
- 列表保留 `page`、`pageSize`、`summaryKeyword`、`module`、`action`、`resourceType`、`resourceId`、`traceId`、`startAt`、`endAt`；管理端额外保留 `actorSystemAccountId`、`affectedSystemAccountId`、`operationScopeSystemAccountId`。列表响应继续为 `items`、`total`、`hasMore`、`page`、`pageSize`，排序稳定为 `created_at,id`。
- 管理列表在没有精确 UUID `traceId` 且未指定时间范围时，默认最近 31 个自然日；输入的 start/end 逆序时交换；精确 trace 查询不强加该默认窗口。
- 详情为“列表行 + supplement”模型：列表保持轻量字段；详情才返回 operation/resource、visibility、changes、method/path/client IP、targets/viewers。个人详情不得因 ID 可猜测而看到未授权记录，也不得通过 summary search、target 或 viewer 查询泄露不可见记录。

## 7. 保留

保留设置继续使用 `operationLogRetentionDays`，默认 365 日，允许范围 1..3650 日。每个 Go retention tick 都在删除前刷新该设置：SQLite 通过只读 `JUHE_AI_OPERATION_LOG_BUSINESS_SETTINGS_PATH` 读取业务库 `system_settings`，PostgreSQL 通过 `juhe_business.system_settings` 读取；仅缺失该键时回退 365。非法值或读取失败必须记录原始错误并跳过本轮删除，不能由环境变量覆盖或静默降级。Go 是唯一的操作日志 retention owner，按截止 `created_at` 分批删除主记录；依赖外键级联删除 targets、viewers、search terms，并记录实际删除数、截止时间、存储模式和失败原始错误。保留失败不得停止 `gateway` 或业务 listener，不得由 Node cleanup 接管。

## 8. 切换与 Node L4 归档

L4 只能在 SQLite、PostgreSQL 和 Node->Go->Node 端到端验收均通过后执行：

1. 先部署且健康检查 Go `gateway` 的签名 loopback 输入与读 API，验证目标 schema、SQLite 单 writer/PG pool、权限和 retention 但不启用 Node 写切换。
2. 原子切换 Node producer 的唯一输出目标到 Go；不启用 Node fallback 或双写。确认全部 L1 producer 活跃路径均已改为 Node->Go RPC，旧 queue 运行时指标不再增长。
3. 清零并删除活跃 Node 操作日志 queue、Redis Stream producer/consumer、IPC message/worker role、local queue、shutdown drain、Node writer、Node schema writer、Node retention、相关 runtime health/metrics 和专属回归入口；共享代码先拆分，不能伤及 F3 或其他未迁移日志。
4. 将完整 Node 专属文件集归档至 `migration-backup/node/operation-log-write-retention/`，以 manifest 固定原路径、SHA-256、停用入口、Go 实现位置、双模式验证、切换提交和回滚提交。归档不是删除证据，也不是恢复 Node owner 的授权。
5. 回滚只能在已验证 owner manifest、drain/停机顺序和可审计提交的前提下完成；不得在运行中的两个 writer 间临时切换或用 Git 还原替代运行时 owner 回滚。

## 10. 已知风险与明确未验证项

- 当前代码实现使用独立 F4 RPC path `/__aiinternal__/v1/operation-logs`、HMAC domain `juhe-ai/operation-log-input/v1`、timestamp/nonce 重放窗口、4 MiB 请求上限和独立 owner lease。SQLite 本地定向测试已覆盖稳定 ID、子表原子性、viewer 权限与个人详情脱敏、签名/过期/重放拒绝后继续处理、系统设置 retention、NFKC 搜索子串、1001 行窗口、SQLite 路径隔离与旧 Node SQLite 离线复制；真实 Node->Go->Node smoke 已覆盖 Node 适配器写入、Go 持久化、列表搜索和个人详情读取。`JUHE_AI_OPERATION_LOG_SYSTEM_API_SMOKE=1 go test ./internal/operationlog -run '^TestNodeGoNodeSystemAPIProducerSmoke$' -count=1 -v` 启动临时 SQLite Node System API，覆盖 26 个一般管理/外部 API producer；`JUHE_AI_OPERATION_LOG_OAUTH_SMOKE=1 go test ./internal/operationlog -run '^TestNodeGoNodeOAuthProducerSmoke$' -count=1 -v` 复用项目 OAuth 本地受控上游，覆盖四个 OAuth 创建路由；`JUHE_AI_OPERATION_LOG_WORKER_SMOKE=1 go test ./internal/operationlog -run '^TestNodeGoNodeWorkerProducerSmoke$' -count=1 -v` 则以最小合法 stats registry fixture 走 `ip-stats` 的真实 stats writer 成功路径与 `table-monitor` 的真实 maintenance 投递成功路径。三组 smoke 均经 Go F4 与 Node 管理 API 读回，且不访问外部供应商或已有开发数据。后台多进程拓扑由独立 `pnpm --filter juhe-ai-backend test:background-worker-topology-smoke` 验证；它不替代 F4 producer 验收。最新隔离 PostgreSQL/PgBouncer smoke 已覆盖 fresh schema 的实际 catalog 输出、连接池 `application_name`、事务 `SET LOCAL` 超时、lease、幂等写入、viewer/search、个人详情裁剪、锁等待超时、retention 和外键索引；另有旧 Node viewer 主键升级的隔离 smoke，均在 finally 删除隔离数据库。实际历史库迁移以及生产切换仍未执行或验证。
- performance producer 回归使用真实开发 PostgreSQL 与三组 Redis 配置读取 settings，再以被阻塞的本地 `fetch` 验证 `runLoggedOperationAsync` 不等待 F4 RPC、仍在一次异步 settings 读取后发出唯一签名请求。命令为 `pnpm --filter juhe-ai-backend test:operation-log-performance-producer`；它要求通过当前进程显式传入 `JUHE_AI_OPERATION_LOG_PRODUCER_POSTGRES_URL`、`JUHE_AI_OPERATION_LOG_PRODUCER_REDIS_CACHE_URL`、`JUHE_AI_OPERATION_LOG_PRODUCER_REDIS_STATE_URL` 和 `JUHE_AI_OPERATION_LOG_PRODUCER_REDIS_QUEUE_URL`，不得将真实连接写入仓库或文档。环境不可达时应报告为真实依赖未验证，不能以 mock 替代。
- 当前 producer 扫描结果是 32 个管理路由文件的类别清单；每次主线漂移后必须重新扫描 import 与调用路径，新增 producer 必须先纳入本契约或停止 F4 实施。
- Node 现有 queue 具有本地缓冲、Redis pending/retry 与 shutdown drain 行为；F4 已从活跃路径退出这些机制，因此切换后仍是“业务成功、日志 best-effort”，对进程在 RPC 完成前崩溃导致的单条日志丢失不作 durable-outbox 承诺。
- 历史 SQLite/PG 数据规模、实际跨模式数据迁移耗时、生产索引成本、管理查询峰值和 retention 批大小尚未验证；不得据此假设可在线复制或无停机迁移。
- 读 API 已由 Node route adapter 调用 Go F4 signed HTTP list/detail，沿用既有 `systemApiPrefix`、状态码和前端 DTO；后续调整必须用现有路由测试与调用方逐项固定，不得降低权限、扩大详情字段或改变默认 31 日管理窗口。
