# 双模式存储与被动任务优先迁移方案

> 决策日期：2026-08-08。
> 本文是 Go 迁移的双模式存储规则。完整功能接管、Node 退出运行路径和源码归档规则以 [完整功能接管与 Node 归档迁移规则](完整功能接管与Node归档迁移规则.md) 为准，它取代本文早期“按 job / writer 小切片接管、长期影子”的现行优先级。旧计划、M/W 波次记录中的相反描述只保留为历史快照，不表示已完成或仍应执行。

## 1. 已决定的边界

- **SQLite 与 PostgreSQL/Redis 均为保留的正式部署模式。** 部署模式只决定采用的存储和运行态 adapter，不决定 Go 是否可运行。Go 新模块必须同时声明 SQLite 和 PostgreSQL/Redis 支持及测试矩阵；当前工作区已有受版本控制的 `backend-go/go.mod` 和 F1/F2/F3 实现，后续功能继续复用并逐项验收该基线。
- **未选择的功能继续由 Node owner。** 每次只迁移一个完整功能；该功能完成接管后，Node 的完整文件集退出活跃路径并进入 `migration-backup/`，不保留 Node fallback。SQLite、DB service、配置和 schema 是否仍存在只由尚未接管的完整功能决定。
- **功能边界先于候选类型。** operation log、public API log、统计、探针或其他功能都可以作为候选，但不能只接管其中一个 writer / scheduler / route。会改写账户、运行态或路由的功能必须把全部副作用、调用方和 Node 文件一起纳入完整接管。
- **双模式不是双写。** 每个 job、队列 consumer、SQLite 文件、派生表和外部副作用在任一时刻都只能有一个正式 owner；影子结果只能写入隔离存储，不能写共享业务表。

## 2. 双模式 adapter 边界

| 部署模式 | 事实与写入边界 | 运行态与队列边界 | Go 共存要求 |
| --- | --- | --- | --- |
| SQLite | 延续当前按文件单 writer：业务库归 DB service；数据集 / usage 路径归 ingest writer；统计库归 stats writer。非 owner 只能 query-only。 | Redis 不是前置条件。未接管 Node 功能仍可维持既有 IPC / 运行态；Go 新功能使用直接异步，不新增本地队列。 | 共存期 Go 不得直接并行写 Node 正在拥有的 SQLite 文件；L3 前必须完成冻结、drain 与独占 owner。若无法隔离完整 owner，则该功能不能接管；具体 SQLite driver 在 B0 定案。 |
| PostgreSQL/Redis | 使用数据库事务、连接池、锁 / lease、幂等键和表级 / 功能级单 owner。 | Node 现状是 Redis Streams；新 Go 完整功能默认直接异步执行，不把 Redis Streams、Asynq 或通用队列作为前提。 | writer 与外部副作用按完整功能单 owner；切换前后以事务、幂等与 drain 保障无重叠。 |

所有 Store Port 必须收口 SQLite 与 PostgreSQL 的 schema、SQL 方言和事务差异；业务规则不得因 driver 分叉。新接管功能默认直接异步，不引入通用 Queue Port；若功能自身需要重启恢复，必须从持久事实直接重放，不能用临时内存队列伪装可靠性。启动时 driver、异步执行方式与 owner 配置不匹配必须 fail-fast 并暴露原始错误，禁止静默 fallback 或因缺 Redis 自动禁用 Go。

## 3. 基线与完整功能接管

| 阶段 | 目标 | owner / 约束 |
| --- | --- | --- |
| B0 | Go 双模式基线：SQLite + PostgreSQL Store adapter、直接异步执行、启动校验和双模式测试矩阵。 | F1/F2/F3 已使用；后续功能仍须逐项验证，不得从已有功能外推。 |
| L1 | 选择一个完整功能，冻结其全部 Node 文件、入口、调用方和副作用。 | 不选择 route/job 小区域；共享文件先做行为不变的 Node 文件拆分。 |
| L2 | 在 Go 完成该完整功能，并直接异步实现其并发与重启恢复语义。 | SQLite 继续单 writer；PostgreSQL 受连接池和事务约束；无 Node / Go 正式双 owner。 |
| L3 | 以 Go 作为唯一 owner 做完整功能验证。 | 包含两种模式、调用方、失败、取消、重启和并发验证。 |
| L4 | 停止 Node 完整功能，并把全部专属 Node 文件移入 `migration-backup/node/<feature-id>/`。 | 移除活跃 import、route、scheduler、consumer、部署和测试入口；归档不参与构建。 |

功能批次 F1“运行日志索引与保留”是首个完成 L1-L4 的功能；其现行边界和后续功能规则见[完整功能接管与 Node 归档迁移规则](完整功能接管与Node归档迁移规则.md)。不得预先把任何 job 或 writer 的一部分视为可接管。

## 4. 每条接管链路的切换与恢复

接管不是只修改 owner manifest。每个完整功能必须有冻结的契约、完整文件清单、Node drain、Go readiness、唯一 owner 观察和回滚演练。切换失败或指标异常时，以明确提交恢复整个功能的 Node 文件与 owner；不得从归档取一段代码回填，也不得让两个 owner 同时运行。

每个新增 Go 功能至少验证：两种存储模式的 Store Port 契约、直接异步并发、启动错配 fail-fast、取消 / 失败 / 重启恢复、Node 活跃路径清零和归档清单。真实 PostgreSQL/Redis 与 SQLite 验证缺任一项时，只能标为未接管。

## 5. 非目标

- 本文不声明 Go 已实现、可运行或已接管任何路径。
- 不把 Redis 设为 SQLite 模式使用 Go 的隐式前提。
- 不以通用队列、业务限速或无界 goroutine 代替完整功能的恢复与正确性契约。
