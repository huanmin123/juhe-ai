## 2. 开发环境目标

迁移完成后的本地开发依赖：

- 迁移时重新确认的最新稳定 Go 版本。
- pnpm 继续用于前端 Vue 3 构建和类型检查。
- SQLite 与 PostgreSQL/Redis 都是正式部署模式。SQLite 沿用数据库文件单 writer、DB service / typed command 边界，不要求 Redis；PostgreSQL/Redis 使用连接池、事务和独立的 Redis cache / state adapter。新 Go 功能默认直接异步执行，不以队列为运行前提。
- 在 PostgreSQL/Redis 模式下，Redis cache / state 的物理隔离、容量与持久化按完整功能的实际契约配置；不得将当前 Node Redis Streams 与 Go 直接异步执行混称。
- PowerShell 7 作为 Windows 默认命令示例。

目标命令示例：

```powershell
Set-Location backend-go
go version
go test ./...
go test ./... -race
$env:JUHE_AI_REQUIRE_INTEGRATION = '1'
try {
  go test -tags=integration ./...
} finally {
  Remove-Item Env:\JUHE_AI_REQUIRE_INTEGRATION -ErrorAction SilentlyContinue
}
goose -dir db/migrations postgres $env:JUHE_AI_POSTGRES_URL up
go run ./cmd/juhe-ai server
go run ./cmd/juhe-ai-worker stats
go build -o .\dist\juhe-ai.exe .\cmd\juhe-ai
go run ./cmd/juhe-ai-maintenance w0-smoke
go run ./cmd/juhe-ai-maintenance w1a-public-settings-smoke
go run ./cmd/juhe-ai-maintenance w1b-public-api-smoke
go run ./cmd/juhe-ai-maintenance w2-operation-logs-smoke
go run ./cmd/juhe-ai-maintenance stats-schema-contract-preflight
Set-Location ..
pnpm --filter juhe-ai-frontend build
```

`backend-go/go.work` 用于本地同时开发全部 Go 模块，不作为发布依赖。当前常驻命令是 `projects/jobs/cmd/juhe-ai-jobs`（F1/F2）与 `projects/gateway/cmd/juhe-ai-gateway`（F3/F4）；它们各自保留 Store、schema、owner lease、健康端点和服务管理器重启边界。正式开发/发布入口由根 `pnpm dev`、release `start.*` 与 Compose 静态装配调用；`maintenance` 只执行显式的一次性命令，不常驻。

`JUHE_AI_REQUIRE_INTEGRATION=1` 是切流 / CI gate 模式：integration 包会在任何测试运行前检查 testcontainers provider，Docker 不可用时直接失败；未设置时仍允许开发机按现有规则输出 `SKIP`。生产接管证据必须使用 gate 模式，不能只依据未设置该变量时的 `go test` 退出码。

生产 owner 启动必须同时满足 owner lock 和 Goose schema 精确门禁。Node owner 启动与 Go server / Go worker 只在 owner lock 显式开启时检查数据库，且必须在开始监听和启动业务运行时之前只读确认当前 Goose schema 精确等于代码 catalog 的当前版本 `92`；同一版本的最新 rollback 记录按未应用处理。版本偏低、偏高、记录损坏或查询失败都必须终止启动，不允许自动迁移、兼容旧 schema 或降级放行。`JUHE_AI_OWNER_LOCK_ENABLED` 仅接受忽略大小写后的精确 `true`，其他值均视为关闭。启用时 `JUHE_AI_OWNER_LOCK_PATH` 必须显式设置为 release 目录之外的绝对共享路径，主/临时环境使用不同锁域；路径门禁解析 `current` 等符号链接和尚不存在的尾部目录，不能用 release 内的物理路径绕过。Node 只在 metadata 同时包含包装器与子进程 PID 且二者均确认不存在时原子隔离并回收 stale lock，无法验证的锁一律 fail-closed；子进程启动后的任一包装器异常必须先终止并等待子进程，再释放锁。

Go mutating worker 还必须设置 `JUHE_AI_GO_WORKER_EXCLUSIVE_OWNER=true`、`JUHE_AI_LEGACY_NODE_WORKER_DRAINED=true` 和绝对 `JUHE_AI_OWNER_MANIFEST_PATH`。schema v3 优先解析当前 CLI job 的 `workerAllowlist` 项，未列出时回退 `routeOwners.worker`；schema v2 继续使用全局 worker owner。解析后的当前 job 必须为 Go，且 deployment epoch、Go release 与 Goose schema `92` 同当前二进制完全一致。两个布尔值是当前 job 的发布证据，每个独立 Go job 进程还必须使用独立的 release 外绝对 lock path。当前生产 manifest 的全局 worker 为 Node 且 `workerAllowlist=[]`，因此所有 mutating Go worker 仍必须拒绝启动。`gateway-quota-snapshot-build` 不带 `--publish-runtime-state` 时是只读本地 smoke，不进入 worker owner gate；开启发布后必须满足完整门禁。

owner manifest schema v3 继续以 `routeOwners` 保存 management / public / gateway / worker 四大域默认归属；`routeAllowlist` 声明 method + path template 精确路由 owner，`workerAllowlist` 声明精确 job owner。当前两类 allowlist 为空且四域全 Node，因此没有改变实际启动或代理分发。Node ops-worker 在 owner lock 开启时用同一 manifest/epoch 决定是否注册 cooldown scheduler，任何无效配置对该 job fail-closed；owner lock 关闭时保持现有 Node 默认行为。格式、回滚和切换门禁以 [精确路由 Owner 清单设计](精确路由Owner清单设计.md) 为准；声明变化本身不构成 drain、进程互斥或生产切流证据。

> **历史 PG/Redis 灰度记录。** 下列 W1-W7 命令、开关、manifest 和 schema 叙述来自 2026-08-08 前的 Go 规划。它们不描述当前 F1/F2/F3 以外的 Go 功能、发布包或接线，也不改变 F1/F2/F3 双模式完整功能接管的事实。

历史记录中的生产切流前提是先停写并离线升级目标 PostgreSQL，再执行 schema 门禁；它不适用于 SQLite profile 的开发闭环。当前可确认的 Go owner 仅限功能批次 F1/F2/F3，其他功能仍为 Node；任何未来 handoff 仍须按双模式契约完成。

历史冷却复测灰度记录中的 `juhe-ai-worker cooldown-account-retest`、API Key/OAuth Probe、PostgreSQL outcome adapter 和 manifest 仅说明当时的设计输入；当前不声明其已接入或可启动。账户健康、冷却复测、余额、OAuth、代理和模型质量均不属于 B0 / L1-L4 已接管范围。

历史 W1a Go server 方案依赖 `JUHE_AI_POSTGRES_URL` 和 `JUHE_AI_REDIS_STATE_URL`：PostgreSQL 承载公开设置和系统设置，Redis state 承载系统 API IP 读限流。该记录不适用于 B0 SQLite profile，也不构成当前 Go 可启动证据。

历史 W1b `/__aipublic__` 灰度挂载曾由 `JUHE_AI_PUBLIC_API_ENABLED` 控制，默认必须保持 `false`。显式设置为 `true` 时，当时方案要求 Go 主 server 注册 `/__aipublic__` 和 `/__aipublic__/*` 并依赖 PG/Redis/Asynq；这只是历史灰度，不等于 W1b 正式接管，也不构成现行完整功能或 SQLite 模式的实现前提。

历史公开账户健康灰度曾让 Go 通过 `JUHE_AI_NODE_INTERNAL_BASE_URL` 调用 Node/ops-worker；这类 Node bridge 不属于现行完整功能接管，不能作为 F2/F3 依赖，也不构成当前已接线事实。

历史 W2 管理端辅助路径和 W3 auth / system account opt-in 路径曾描述为已完成 Go schema / 既有表复用、Redis state、store / service / handler 与会话鉴权基线；该段只保存旧灰度范围。`JUHE_AI_MANAGEMENT_API_ENABLED` 的旧开关不等于 W2/W3 正式接管，也不构成 B0 或 L1-L4 实施前提；主流程接口在被选为完整功能前仍由 Node owner。

历史完整管理端 Go opt-in 下曾将 Redis cache、state 和 queue 作为启动依赖；这不是新 Go 完整功能的队列要求。登录会话列表 / 按 ID 撤销专用开关已删除，不得恢复。历史记录中业务 PATCH 成功后的 operation log 行为也不构成本轮接管边界。

历史 W3 `POST /__aisys__/api/auth/login` 和 `PATCH /__aisys__/api/system-accounts/{id}` 仅记录旧 Go opt-in 灰度；其 PostgreSQL + Redis cache/state/queue 依赖不允许推导为 Go 仅支持 PG/Redis，亦不允许推导为这些 Node 主流程已接管。前端登录页 / 系统账户管理页、生产切流和 Node `/auth` / `/system-accounts` 删除均不属于本轮。

历史 W1b 真实依赖灰度验证入口曾为 `go run ./cmd/juhe-ai-maintenance w1b-public-api-smoke`，并依赖 PostgreSQL、Redis 与 `juhe-ai-worker ingest`。该命令和其 public API log 队列只保留为历史资料，不存在于当前工作区，也不能作为现行 F1 候选或实现前提。

历史 W2 operation log 读路径灰度验证入口曾为 `go run ./cmd/juhe-ai-maintenance w2-operation-logs-smoke`，并依赖 PostgreSQL 与 Redis queue。该命令只说明旧 opt-in 设计，不存在于当前工作区，不能作为现行完整功能接管证据。

历史 W6 Node stats writer 与 Go reader 共存门禁曾为 `go run ./cmd/juhe-ai-maintenance stats-schema-contract-preflight`。它只说明旧 PostgreSQL reader 灰度设计，不存在于当前工作区；现行 F1 不得以只读路由或 `writerOwner=node` 取代完整功能接管。

如部署在 Caddy / Nginx / 隧道之后，必须显式配置 `JUHE_AI_TRUST_PROXY`；未启用时 IP 限流按 Go server 直连 socket 地址计数，可能只看到反代出口。开启后 diagnostics 的 loopback 判断也使用解析后的客户端 IP，避免公网请求经本机反代误入 metrics / pprof。

历史 W1a 真实依赖验证入口曾为 `go run ./cmd/juhe-ai-maintenance w1a-public-settings-smoke`。该命令只保留为旧 PG/Redis 规划资料，不构成当前 Go 可运行或完整功能已接管证据。

未来 Go 健康检查即使返回 HTTP 200，JSON 仍可能是 `status=degraded`。届时部署 smoke、反向代理健康检查和 watchdog 不能只看 HTTP 状态码，必须解析 `success`、`status` 和 `dependencies`。`/__aisys__/metrics` 与 `/__debug/pprof` 只属于受控诊断入口，默认由 loopback / 反代规则保护，不能作为公网 API 暴露。

PowerShell 健康检查示例：

```powershell
$h = Invoke-RestMethod http://127.0.0.1:3000/__aisys__/health
if (-not $h.success -or $h.status -ne 'ok') { throw ($h | ConvertTo-Json -Depth 8) }

$api = Invoke-RestMethod http://127.0.0.1:3000/__aisys__/api/health
if (-not $api.success -or $api.status -ne 'ok') { throw ($api | ConvertTo-Json -Depth 8) }
```

系统指标迁移的部署边界见 [Go 迁移指标与观测规划](Go迁移指标与观测规划.md)：完整功能迁移后系统监控必须改用 Go runtime、PG/Redis、直接异步执行和统计新鲜度指标，不再用 Node `eventLoopLagMs`、`db-service` 或 SQLite 文件体积判断 Go 服务健康。

## 3. 过渡运行方式

渐进迁移需要一段过渡期，但必须保持单 owner：

- 按路径或模块分流时，同一路径只允许 Node 或 Go 其中一个处理。
- Go 接管某个路径后，Node 对应 route/service 必须删除。
- 过渡入口可以是本地开发代理、测试环境反向代理或 Go edge server，但不能成为长期双后端架构。
- 生产切换前，每个已迁移模块必须有独立 smoke 和删除证据。
- W1b `JUHE_AI_PUBLIC_API_ENABLED=true` 只允许用于显式灰度；同一公网 `/__aipublic__/*` 不能同时由 Node 和 Go 作为正式 owner。
- W1b `w1b-public-api-smoke` 只作为本地 httptest + 真实依赖灰度验证，不能替代真实监听端口、反向代理切流、生产流量观测和 Node 删除证据。
- W2 `w2-operation-logs-smoke` 只作为本地 httptest + 真实 PG / Redis 依赖灰度验证，不能替代真实监听端口、反向代理切流、生产流量观测和 Node 删除证据。
- W2/W3 `JUHE_AI_MANAGEMENT_API_ENABLED=true` 只允许用于显式灰度；同一公网后台路径不能同时由 Node 和 Go 作为正式 owner。除 captcha / login / logout 的特殊登录态边界外，Go 入口必须保留管理端会话鉴权，已迁移管理写接口必须保留 60 秒节流 touch，change-password 必须使用允许初始密码用户进入的 current-user 写鉴权分支。系统账户列表读和 options 只覆盖当前 W2 只读范围；W3 已覆盖 captcha、login、current-user、profile update、change-password、当前 token logout、system account create 和完整 mixed PATCH，但仍不覆盖前端 auth / 系统账户页 smoke、生产单 owner 切流或 Node `/auth` / `/system-accounts` 删除；登录会话列表 / 按 ID 撤销已撤销，不属于接管缺口。

现行 B0 / L1-L4 过渡顺序（功能批次 F1/F2/F3 已完成唯一 owner 接管；下列规则对后续功能继续适用）：

1. B0 建设并验证 SQLite 与 PostgreSQL/Redis 双模式 Store、Runtime、直接异步执行和错配 fail-fast；存储模式不决定 Go 是否可运行。
2. L1 冻结一个完整功能的 Node 入口、调用链、存储写入、后台触发、配置、测试和运行副作用，形成归档清单；不得按 job、单个 queue consumer 或共享文件的一部分接管。
3. L2 在 Go 中一次实现该完整功能的双模式行为，默认以直接异步 goroutine 完成并发工作；SQLite 必须形成该完整功能的唯一 file owner，PostgreSQL 仍受连接池和事务约束。owner bridge 只能留在 B0 或未迁 Node 功能，不能成为 L3 依赖。
4. L3 让 Go 成为该完整功能唯一运行 owner，删除 Node 的所有活跃入口、调度、调用与部署引用；不保留 Node bridge、双消费者、双写或运行时 fallback。
5. L4 将 Node 的完整专属文件集移入 `migration-backup/node/<feature-id>/` 并写入可校验 manifest。网关、账户管理和主要 HTTP 接口在被单独选为完整功能前继续由 Node owner；SQLite 与 DB service 不是本批次删除对象。

## 4. B0 / L1-L4 构建目标

F1/F2/F3 当前发布包已能按明确 profile 选择 SQLite 或 PostgreSQL adapter；后续完整功能继续遵循同一双模式目标：

```text
release/
  backend/dist/                         # Node 主服务
  backend-go/juhe-ai-gateway(.exe)     # 当前 F3/F4，未来管理/API/AI gateway
  backend-go/juhe-ai-jobs(.exe)        # 当前 F1/F2，后续全部 Go 定时任务
  backend-go/juhe-ai-maintenance(.exe) # 一次性 maintenance 项目
  frontend/dist/
  backend/.env.example
  start.sh / start.ps1
```

构建规则：

- 前端继续用 Vite 构建静态资源。
- F1/F2/F3/F4 分别由 `projects/jobs` 与 `projects/gateway` 独立构建；`projects/maintenance` 构建为一次性命令。Node 主服务仍保留 Node 构建与 engine 约束。
- Go SQLite driver 的选择、CGO / 纯 Go 构建差异和 owner bridge 在 B0 后固定；F1/F2/F3 已完成各自隔离 PostgreSQL smoke，但这不能替代后续 candidate/handover 发布验收。
- 当前发布与开发仍保留 Node 运行产物和 Node engine 约束；每个完整功能完成 L3 后才移除其 Node 活跃文件与引用，并按 L4 归档，不能由阶段名称推导整体退出 Node。

## 5. Docker profile

当前 Docker Compose 已静态装配 Node、`go-jobs` 和 `go-gateway`；两个 profile 的现行边界为：

1. SQLite profile：保留 SQLite volume、DB service / typed command 边界；Go 功能若运行，只能通过 SQLite Store 的唯一写 owner 或 owner bridge 直接提交，不要求 Redis。
2. PostgreSQL/Redis profile：使用 PostgreSQL Store、Redis Runtime；完整功能的异步工作默认由 Go goroutine 直接执行，Redis 只在该功能已有 cache/state/持久任务事实时按契约使用。
3. 两个 profile 都必须在启动时校验 driver、执行边界与 owner 是否一致，错配失败而不 fallback。

Docker 运行验证仍需确认：

- SQLite 数据卷、单 writer、DB service / bridge 与恢复边界。
- PostgreSQL 数据卷、初始化、备份和恢复，以及 PostgreSQL/Redis profile 的 cache、state 和直接异步执行的连接/内存边界。
- 健康检查路径。
- 代理访问宿主机的方式。
- 日志输出和文件保留策略。

当前不指定唯一默认 Docker profile，也不删除 SQLite volume、Node entrypoint 或 `check-node-sqlite`。F1/F2/F3 SQLite 输出必须与所有源库和 usage shard root 物理隔离，Go 输出库强制 `WAL`、`busy_timeout=5000`；未来 usage 迁移仍须独立验证 shard root 隔离门禁。未来是否调整默认 profile 或退出 Node / SQLite 只能通过单独决策，并以双模式迁移完成后的独立验收为前提。

## 6. 常驻运行目标

服务化必须编排当前 Node 主服务、`gateway` 与 `jobs`，`maintenance` 只按需执行。生产事实以当前部署文档和状态页为准：

- Linux：systemd/启动脚本先启动 Node，确认 DB-ready API health 后分别启动 `gateway` 与 `jobs`，配置各自 PID、日志和健康检查。
- Windows：PowerShell 启动脚本或 Windows Service 按同样顺序运行 Node、`gateway.exe` 和 `jobs.exe`，保留各自数据目录和日志目录。
- macOS：launchd 为 Node 槽、gateway 和 jobs 分别保留工作目录、环境变量、日志与失败联动；maintenance 不常驻。零停机发布必须使用独立 candidate slot 和 handover controller；同一完整功能不得出现两个 owner。
- watchdog：按项目 health JSON 分别判断和重启；普通单条/单轮错误只记录并交给下一轮，租约丢失或进程级致命退出才由服务管理器重启所属项目。

服务化文档必须按最终进程拓扑分别覆盖 `gateway`、`jobs` 和 `maintenance` 命令，说明健康检查、重启退避、shutdown drain、job lag 和一次性报告；不得把 Node 的 `ingest-worker`、`stats-worker`、`ops-worker` 当作 Go 项目边界，也不得由 gateway 看护 jobs 子进程作为部署前提。

watchdog 的 Go 目标规则：

- 连续失败阈值基于 health JSON，而不是 HTTP 200。
- 只在本地服务整体不可用或关键依赖持续不可用时重启 juhe-ai；公网域名、证书、上游模型、单个账号或队列积压不能直接触发整栈重启。
- CPU 高、GC 抖动、直接异步任务积压或统计滞后优先告警和记录指标，不自动重启。
- watchdog 日志必须记录 health JSON 摘要、失败次数、冷却时间、PID 和重启结果。

## 7. 配置与数据

- 产品级环境变量名称尽量保持稳定，例如端口、PostgreSQL、Redis、代理和密钥相关配置。
- Node 专用环境变量、Node 版本预检、`node:sqlite` 预检和 `tsx` 开发命令继续保留，除非未来单独批准退出 Node。
- SQLite 路径、usage shard、DB service 与模式选择配置继续保留；B0 只定义 Go adapter 需要识别的配置和 owner 校验，不删除现有 SQLite 配置。
- 本地数据仍按当前 schema 处理；迁移期间如果 schema 调整，源码只保留当前 schema，既有数据由离线脚本或人工方案处理。
- 数据备份、恢复和迁移说明必须覆盖 SQLite profile 的文件 / 单 writer 恢复，以及 PostgreSQL/Redis profile 的事实库、运行态和直接异步恢复边界；仍未迁移 Node 功能的队列另按 Node 当前契约维护。SQLite 不是仅供一次性导出的旧数据域。

环境变量删除矩阵：

| 类型 | 最终状态 |
| --- | --- |
| 端口、host、secret、cookie、安全和代理配置 | 保留或按 Go 命名收敛 |
| `JUHE_AI_POSTGRES_URL`、Redis cache/state URL、`JUHE_AI_REDIS_NAMESPACE` | PostgreSQL/Redis profile 的候选配置；具体 Redis 隔离要求在 B0 后按完整功能契约确定，不能套用于 SQLite profile；不新增 Go queue URL |
| `JUHE_AI_PUBLIC_API_ENABLED`、`JUHE_AI_MANAGEMENT_API_ENABLED`、`JUHE_AI_COOLDOWN_ACCOUNT_RETEST_WORKER_ENABLED` | 历史 W1-W7 Go 灰度开关；不是 B0/L1-L4 配置，也不得恢复为局部接管方式 |
| `JUHE_AI_SECRET` | 保留为敏感数据加密和签名密钥；具体 Go 功能使用前按该完整功能契约校验，不能以历史 W1b 开关推导当前需求 |
| `JUHE_AI_NODE_INTERNAL_BASE_URL`、`JUHE_AI_NODE_INTERNAL_REQUEST_TIMEOUT` | 历史 Node bridge 配置；已接管的完整 Go 功能不得依赖它们，不能作为新功能配置 |
| `JUHE_AI_DATABASE_PATH`、dataset / stats / usage catalog 路径、usage shard root | SQLite profile 的正式配置。Go SQLite adapter 必须显式支持并校验它们；完成 L3 的功能应有自己的 file owner，而非 owner bridge |
| `JUHE_AI_RUNTIME_MODE`、`JUHE_AI_DATABASE_DRIVER`、`JUHE_AI_CACHE_DRIVER`、`JUHE_AI_RUNTIME_STATE_DRIVER` | B0 定义明确的双模式 adapter 选择与 owner 校验；SQLite 与 PostgreSQL/Redis 都是正式模式，错配必须 fail-fast |
| `JUHE_AI_QUEUE_DRIVER` | 未迁 Node 功能的现有配置；新 Go 功能不得读取它或以它决定是否可运行 |
| `JUHE_AI_DB_SERVICE_*`、`JUHE_AI_PROCESS_ROLE`、Node preflight 相关变量 | SQLite / Node 当前运行边界，在未完成对应完整功能的 L3/L4 前保留；未来是否删除需另立决策 |

## 8. 回滚边界

减法迁移不保留同一模块的长期双实现，因此回滚应以发布包和数据备份为单位：

- 模块生产切换前，保留上一版可运行发布包和数据备份。
- 切换失败时，停止当前版本，恢复同一数据契约下的上一版发布包和配置。
- 如果 schema 已按当前最优方案调整，不能依赖运行时代码自动回滚旧 schema；必须有明确的离线恢复或重新初始化方案。
- 网关迁移阶段必须有单独的灰度、压测、真实上游 smoke 和快速停止方案。
