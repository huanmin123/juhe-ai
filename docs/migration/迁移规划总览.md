# Node 转 Go 迁移规划总览

## 1. 背景与目标

当前后端是 Node.js + TypeScript。项目为了避免事件循环阻塞、同步 SQLite 占用、慢管理接口拖住前台、网关副作用反压和大 JSON 解析阻塞，已经引入 DB service、worker role、IPC 队列、读写隔离、运行态缓存和多种队列保护。

最新迁移目标（2026-08-08）是双模式完整功能接管：SQLite 与 PostgreSQL/Redis 都是 Go 的正式部署目标，模式只选择 Store、Runtime 与直接异步执行方式，绝不决定 Go 是否可用。每次只接管一个完整功能，接管完成后 Node 的整个功能文件集退出活跃路径并归档到 `migration-backup/`。当前工作区还没有受版本控制的 Go 源码或 `go.mod`，因此这是待建设要求；详细阶段、owner、归档和回滚见 [完整功能接管与 Node 归档迁移规则](完整功能接管与Node归档迁移规则.md)。

迁移到 Go 的核心目标不是逐行翻译，而是减少这些由 Node 运行时特性带来的复杂度：

- 每个 HTTP 请求天然在独立 goroutine 中处理，不再围绕单事件循环设计大量避让机制。
- 上游 I/O、SSE 透传、后台任务和管理接口可以用 `context.Context`、连接池、mutex、atomic 和按资源维度的直接 goroutine fan-out 表达。
- 移除 Node 专用的 `tsx`、worker thread、DB service 事件循环隔离、IPC pending 防护和一部分本地队列胶水。
- 保留 SQLite 模式所需的单写者、usage shard、多库和 DB service 边界；Go 在共存期通过 typed command / owner bridge 或完成 handoff 后独占目标文件，不能直接并行写入。
- 保留真实业务边界：API Key、路由策略、分组、AI 账户、供应商、协议能力、使用记录、审计、统计和系统设置不因语言迁移丢失。

## 2. 迁移总原则

- 渐进式：一次迁移一个完整功能，不要求一次性重写全部后端，也不允许按 route、job、writer 或文件片段接管。
- 减法迁移：一个完整功能由 Go 接管并通过验收后，将对应 Node 的完整文件集移至 `migration-backup/node/<feature-id>/`，并移除活跃 Node route、service、repository、脚本、部署和测试入口，避免长期双实现。
- 单 owner：同一完整功能及其接口、后台任务、数据写入和外部副作用同一时间只能有一个正式实现。
- 网关后置、Chat 最终：真实中转协议网关必须在公开接口、后台接口、存储边界、worker 和测试体系成熟后迁移；Go 网关稳定后再迁移 AI Chat，最后进入 W11 Node 减法。
- 测试先行：迁移前先固定当前行为契约，迁移后用 Go 测试和现有回归测试证明行为等价。
- Go 优先：遇到 Go 中更简单、稳定、可验证的表达方式时，优先使用 Go 原生方式，不照搬 Node 时代的补丁结构。
- 缺陷不兼容：契约测试冻结业务意图和可观察语义，不把已确认的 Node 缺陷固定成兼容要求。发现 Node 缺陷时，Go 必须采用 Go 原生方式修复，并在迁移记录中写明 Node 原行为、缺陷证据、Go 修复、差异原因、测试和回滚影响；未经证据确认的差异不得擅自改写。
- 持续漂移审计：共享主目录固定在 `master`，迁移只在独立 worktree 中进行；每批任务分配前、代码完成后、长时间真实依赖测试后、中心集成前和推送前都先只读 `fetch origin master`，再记录本地 `master`、`origin/master`、迁移 HEAD 和 merge-base。在迁移 worktree 中将待发布的本地 `master` 与最新 `origin/master` 普通 merge 到迁移分支，不使用 rebase 或 force-push，不在共享主目录切换分支。审计覆盖已迁移、预迁移和本批依赖模块；Node 的业务调整要同步到 Go，纯 Node runtime 机制不机械复制。完整同步、范围审计、合回与回滚规则以 [迁移目录入口](README.md#21-共享主目录与迁移-worktree-强制规则) 为准。
- 存储双模式：Go 必须通过 Store Port 支持 SQLite 与 PostgreSQL/Redis；每个完整功能必须列出两种模式的 adapter 和测试矩阵，driver / 直接异步执行方式 / owner 错配必须 fail-fast，不能静默 fallback。
- 指标重建：系统指标统计必须按 Go runtime、PostgreSQL、Redis、直接异步执行、cursor / freshness 和网关 SLI 重建；执行时按 [Go 系统指标字段迁移清单](Go系统指标字段迁移清单.md) 逐项删除 Node 字段、替换前端契约和记录验证证据；不能为了前端短期兼容继续模拟 Node `eventLoopLagMs`、DB service 或 SQLite 文件体积指标。
- 当前最优：不为旧代码、旧 API 内部结构、旧数据库结构或历史部署保留运行时兼容分支；需要处理旧数据时只做离线方案。
- 不隐藏数据问题：Go 迁移不默认复刻 Node 里的补偿逻辑、宽松 fallback、旧字段兜底或“脏数据自动修正”。数据不满足当前 schema / 当前契约时，运行路径应明确报错并暴露问题；需要修数据时使用离线 SQL / 离线脚本 / 重建流程处理，不能把长期兜底写进 route、repository、worker 或网关热路径。
- Go 抽象优先但不过度：泛型、反射、接口组合、代码生成和常见设计模式可以用于减少重复和固定边界；只有在能降低长期维护成本、保持类型安全或集中校验规则时使用，不能为了炫技让业务路径难以审查、难以测试或隐藏错误。

## 3. 现行迁移阶段（B0、F1-F4）

| 阶段 | 目标 | 主要交付 | 删除重点 | 网关风险 |
| --- | --- | --- | --- | --- |
| B0 双模式 Go 基线 | 建设 Go module、双 Store Port、直接异步执行、启动校验与双模式 smoke | 待建设目录、SQLite / PG adapter PoC、无 owner 切换 | 无业务删除 | 无 |
| F1 完整功能冻结 | 选择一个完整功能，列全 Node 文件、入口、调用方、数据和副作用 | 功能清单、归档计划、共享文件拆分证据 | 无 | 低 |
| F2 Go 完整实现 | 在 Go 中实现整个功能及其双模式、直接异步、取消和重启恢复语义 | Go 功能文件、双模式测试、调用方验证 | 无 | 中 |
| F3 唯一 owner 验收 | Go 完整功能成为唯一 owner | Node drain、失败/取消/重启/并发验证、回滚提交 | Node 不再运行该功能 | 中 |
| F4 Node 归档与清零 | 将完整 Node 文件集放入 `migration-backup/` 并移除所有活跃入口 | 归档 manifest、静态搜索、构建/部署验证 | 仅该完整功能的 Node 活跃路径 | 中 |

网关、账户管理和主要 HTTP 接口不是禁止迁移对象；但它们必须以完整功能而非单 route / 小区域接管，且每次只迁一个完整功能。

首个已冻结的 F1 候选是 [运行日志索引与保留](F1-运行日志索引与保留功能冻结.md)。它只迁移日志文件到索引 / cursor / facet / retention 的被动持久化功能；Node 日志浏览读页面仍是下游消费者，不属于本批 owner 切换。

## 4. 减法规则

模块迁移完成必须同时满足：

- Go 已拥有该完整功能的正式 route、service、store、job、脚本和调用方入口。
- 当前模块所有必要测试已迁移或补齐，至少覆盖成功路径、权限、非法输入、空数据和相邻回归。
- 文档已说明 Go 目标实现范围、正式接管门禁、删除范围和未迁移例外。
- `rg` 能证明 Node 旧入口、旧脚本、旧测试命令、旧 import 和旧引用已经从活跃路径删除，只保留 `migration-backup/` 与历史文档引用。
- Node 完整功能文件已归档到 `migration-backup/node/<feature-id>/`，并有原始路径 / SHA-256 / Go 文件 / 回滚提交的 manifest。
- 发布/开发命令不再暴露已删除模块的 Node 测试入口。

允许短期存在的东西：

- 测试环境的 Node vs Go 契约对比脚本。
- 按路径分流的本地或测试环境过渡入口。
- 为删除旧代码准备的临时清单。

不允许长期存在的东西：

- 同一路径 Node 与 Go 同时可处理。
- Go 调 Node 业务 service，或 Node 调 Go 业务 service 后还保留两份事实逻辑。
- 为迁移期保留的旧 schema 自动探测、双读双写、启动迁移、兼容字段兜底。
- 因为“还没确认有没有用”而保留不可达 Node 模块。

## 5. 当前优先级

1. B0 先建立 SQLite 与 PostgreSQL/Redis 双模式 Store、直接异步执行、配置错配失败和测试矩阵。
2. F1 从可完整隔离的功能开始，先完成 Node 文件与调用链清单，再开始 Go 实现。
3. F2/F3 在一个完整功能通过两种模式、并发、取消、重启和调用方验证后立即切换唯一 Go owner。
4. F4 当批归档完整 Node 文件并清零活跃入口；不积压“以后再删除”的 Node 功能债务。

## 6. B0、F1-F4 成功标准

- B0 的 SQLite 与 PostgreSQL/Redis Store Port、直接异步执行、driver / owner 配置 fail-fast 和双模式测试矩阵均有可核验 PoC；缺任一模式只标为未完成。
- F1 有完整功能、完整 Node 文件、所有调用方和副作用的清单；共享 Node 文件已先拆分为完整功能文件。
- F2/F3 的 Go 功能覆盖完整外部契约、两种存储模式、直接异步并发、取消、失败、重启和回滚；SQLite 验证文件单 writer，PostgreSQL/Redis 验证事务、连接池与幂等。
- F4 的 Node 文件、route、scheduler、consumer、部署和测试入口均已从活跃路径移除；归档 manifest 完整，归档不参与构建或运行。
