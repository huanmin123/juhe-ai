# Node 转 Go 迁移规划总览

## 1. 背景与目标

当前后端是 Node.js + TypeScript。项目为了避免事件循环阻塞、同步 SQLite 占用、慢管理接口拖住前台、网关副作用反压和大 JSON 解析阻塞，已经引入 DB service、worker role、IPC 队列、读写隔离、运行态缓存和多种队列保护。

最新迁移目标已经明确：Go 后端不再保留 SQLite standalone / PostgreSQL performance 两套存储模式。迁移完成后的唯一正式存储目标是 PostgreSQL + Redis；SQLite 只作为当前 Node 旧实现和一次性离线导出来源存在，不能进入 Go 运行路径。

迁移到 Go 的核心目标不是逐行翻译，而是减少这些由 Node 运行时特性带来的复杂度：

- 每个 HTTP 请求天然在独立 goroutine 中处理，不再围绕单事件循环设计大量避让机制。
- 上游 I/O、SSE 透传、后台任务和管理接口可以用 `context.Context`、连接池、channel、mutex、atomic 和 bounded worker pool 表达。
- 移除 Node 专用的 `tsx`、worker thread、DB service 事件循环隔离、IPC pending 防护和一部分本地队列胶水。
- 移除 SQLite 单写者治理、usage shard 文件写入、SQLite 多库拆分和 standalone / performance 模式分支。
- 保留真实业务边界：API Key、路由策略、分组、AI 账户、供应商、协议能力、使用记录、审计、统计和系统设置不因语言迁移丢失。

## 2. 迁移总原则

- 渐进式：按模块迁移，不要求一次性重写全部后端。
- 减法迁移：一个模块由 Go 接管并通过验收后，删除对应 Node route、service、repository、脚本入口和测试入口，避免长期双实现。
- 单 owner：同一接口路径、后台任务或数据写入 owner 同一时间只能有一个正式实现。
- 网关后置、Chat 最终：真实中转协议网关必须在公开接口、后台接口、存储边界、worker 和测试体系成熟后迁移；Go 网关稳定后再迁移 AI Chat，最后进入 W11 Node 减法。
- 测试先行：迁移前先固定当前行为契约，迁移后用 Go 测试和现有回归测试证明行为等价。
- Go 优先：遇到 Go 中更简单、稳定、可验证的表达方式时，优先使用 Go 原生方式，不照搬 Node 时代的补丁结构。
- 缺陷不兼容：契约测试冻结业务意图和可观察语义，不把已确认的 Node 缺陷固定成兼容要求。发现 Node 缺陷时，Go 必须采用 Go 原生方式修复，并在迁移记录中写明 Node 原行为、缺陷证据、Go 修复、差异原因、测试和回滚影响；未经证据确认的差异不得擅自改写。
- 持续漂移审计：每批任务分配前、中心集成前和推送前都要 fetch / rebase 最新 `master` 并记录基线。审计覆盖已迁移、预迁移和本批依赖模块；Node 的业务调整要同步到 Go，纯 Node runtime 机制不机械复制。
- 存储单模式：Go 目标只支持 PostgreSQL + Redis，不新增 SQLite adapter，不保留 SQLite 配置入口，不维护两套 schema / repository / 测试矩阵。
- 指标重建：系统指标统计必须按 Go runtime、PostgreSQL、Redis、Asynq、worker lag 和网关 SLI 重建；执行时按 [Go 系统指标字段迁移清单](Go系统指标字段迁移清单.md) 逐项删除 Node 字段、替换前端契约和记录验证证据；不能为了前端短期兼容继续模拟 Node `eventLoopLagMs`、DB service 或 SQLite 文件体积指标。
- 当前最优：不为旧代码、旧 API 内部结构、旧数据库结构或历史部署保留运行时兼容分支；需要处理旧数据时只做离线方案。
- 不隐藏数据问题：Go 迁移不默认复刻 Node 里的补偿逻辑、宽松 fallback、旧字段兜底或“脏数据自动修正”。数据不满足当前 schema / 当前契约时，运行路径应明确报错并暴露问题；需要修数据时使用离线 SQL / 离线脚本 / 重建流程处理，不能把长期兜底写进 route、repository、worker 或网关热路径。
- Go 抽象优先但不过度：泛型、反射、接口组合、代码生成和常见设计模式可以用于减少重复和固定边界；只有在能降低长期维护成本、保持类型安全或集中校验规则时使用，不能为了炫技让业务路径难以审查、难以测试或隐藏错误。

## 4. 减法规则

模块迁移完成必须同时满足：

- Go 已拥有该模块的正式 route、service、store、job 或脚本入口。
- 当前模块所有必要测试已迁移或补齐，至少覆盖成功路径、权限、非法输入、空数据和相邻回归。
- 文档已说明 Go 目标实现范围、正式接管门禁、删除范围和未迁移例外。
- `rg` 能证明 Node 旧入口、旧脚本、旧测试命令和旧引用已经删除或只剩历史文档引用。
- 发布/开发命令不再暴露已删除模块的 Node 测试入口。

允许短期存在的东西：

- 测试环境的 Node vs Go 契约对比脚本。
- 按路径分流的本地或测试环境过渡入口。
- 为删除旧代码准备的临时清单。

不允许长期存在的东西：

- 同一路径 Node 与 Go 同时可处理。
- Go 调 Node 业务 service，或 Node 调 Go 业务 service 后还保留两份事实逻辑。
- 为迁移期保留的旧 schema 自动探测、双读双写、启动迁移、兼容字段兜底。
- 因为“还没确认有没有用”而保留不可达 Node 模块。

## 5. 当前优先级

1. 先搭 Go 工程基线、PostgreSQL schema / seed / store port、Redis cache / state、Asynq queue 和契约测试方式。
2. 先迁移公开接口，因为路径少、业务副作用少、风险低；W1b 可使用 `JUHE_AI_PUBLIC_API_ENABLED=false` 默认关闭、显式开启的 opt-in guard 做测试环境灰度，但同一公网 `/__aipublic__/*` 仍必须保持单 owner。
3. 再迁移后台管理接口，因为多数是 CRUD、权限和分页契约。
4. 再迁移 worker，并在 PG/Redis 基线上删除 Node storage / DB service / SQLite 旧路径，因为它们决定统计、审计和维护任务的长期稳定性。
5. 在 W6-W8 同步替换系统指标统计和前端系统监控契约，确认 Go runtime、PG/Redis、Asynq、worker lag 和统计新鲜度可观测后，再删除 Node event loop、DB service 和 SQLite 文件指标。
6. 完成 Go 网关灰度接管和稳定性验证后，最后迁移仍在持续改造的 AI Chat；AI Chat 单 owner 切流和回滚演练后，再把 Chat 内部客户端切到 Go gateway 并重验真实生成、恢复和 usage / audit，之后才删除 Node gateway 回滚入口并进入 W11 最终减法。

## 6. 成功标准

- 后端最终由 Go 承载，Node 只保留前端构建链路需要的工具依赖。
- 当前公开接口、后台接口和网关主契约没有功能缺失。
- Node 专用的 DB service 事件循环隔离、worker thread 解析、大量 IPC 防阻塞逻辑被删除或转化为更小的 Go 生命周期/队列边界。
- Node 专用系统指标已经按 [Go 系统指标字段迁移清单](Go系统指标字段迁移清单.md) 删除或替换：不再暴露 `eventLoopLagMs`、`process_event_loop_*`、`db-service` 运行角色、SQLite 文件体积和 usage shard 文件指标；Go 系统监控改为 runtime、goroutine、scheduler、GC、heap、RSS、PG pool、Redis、Asynq、worker lag 和网关 SLI。
- 迁移完成时，PostgreSQL + Redis、日志、审计、统计、部署和备份都必须有 Go 版本验证记录；满足前不得删除对应 Node / SQLite 正式路径。SQLite 不再作为 Go 运行模式验收。
- 网关迁移完成前，每个阶段都有可回溯测试证据；网关迁移完成后，有独立性能和稳定性报告。
