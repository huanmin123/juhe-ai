# Node 到 Go 迁移状态与后续批次

> 更新时间：2026-08-12
> 本文是后续迁移的权威状态入口。旧日期的迁移状态和 W/M 记录仅作历史证据，不能覆盖本文。

## 当前结论

项目仍是 Node 主业务加 Go sidecar 的混合架构，不是“整个后端已经迁到 Go”。当前完整接管到 Go 的只有 F1、F2、F3：

| 批次 | Go 唯一 owner | Node 保留边界 | 生产状态 |
| --- | --- | --- | --- |
| F1 运行日志索引与保留 | JSONL 发现、解析、cursor、索引、facet、retention | 继续产生 JSONL，管理接口只读 | 已随正式 Mac 拓扑运行 |
| F2 表存储监控采样与保留 | 多源采样、快照、lease/fence、retention | 管理接口只读 | 已随正式 Mac 拓扑运行 |
| F3 原始审计日志持久化与保留 | 审计主记录、attempt、payload/blob、error group、hot-search、retention | 网关 capture 归一化并经 loopback HMAC 一次性直投；管理接口只读 | 已完成正式接线与真实生产读回，继续观察 |

F3 的旧 Node writer、queue、Redis Stream、transport、retention、schema 和 read-worker 路径已退出活跃代码并归档。Node 不保留 F3 fallback；Go 输入不可用时该条 best-effort 审计明确失败并计数，不回退旧 writer。

2026-08-12 首次 F3 正式上线发生过硬停机，并暴露前端构建把 `/__aisys__/api` 转换成 Windows 磁盘路径的问题。该事故来自发布与验收流程，不表示恢复 Node F3 owner。生产前端已通过正确根相对 API base 前向修复，并以真实浏览器登录态业务页验证恢复。零停机 candidate/handover 流程尚待下一次正式发布完整证明，因此后续迁移暂不立刻切新 owner。

## 仍由 Node 负责

- 网关请求调度、上游协议执行、provider/OAuth、账户、API Key、分组、权限和主业务 HTTP API；
- 操作日志及其全部 producer、权限读和 retention；
- 公开接口日志的 HTTP capture、快照、写入、读取和 retention；
- usage records、pricing freeze、usage shard、统计游标和可靠投递；
- model-check、账号健康、后台探针、stats、ops 和其余 Node worker。

这些功能不得因为 Go 已存在相邻 DTO、read route、schema 或实验代码就写成“已迁移”。只有完整功能 owner 切换、Node 活跃路径清零、归档 manifest 和运行证据同时成立，才算完成。

## 后续顺序

1. **发布稳定窗口**：按 [生产发布快速流程](../deploy/生产发布快速流程.md) 把构建、依赖、candidate 启动和完整业务验证移到旧槽承流期间；随后完成一次带时效/文件指纹凭证的 `preflight -> takeover` 正式演练。成功后 journal 必须为 `committed`；需要正常回切时重新执行反向 `preflight`，再执行 `switchback`。`recover` 只用于尚未 committed 的中断 journal，`stable` 是控制器内部瞬时状态而不是命令。该门禁通过前不切 F4 生产 owner。
2. **F4 操作日志**：完整覆盖所有 `recordOperationLog*` producer、提交后异步语义、actor/viewer/targets/search terms、admin/self 权限读、稳定 ID、幂等写和默认 365 天 retention。业务事务不能因为操作日志失败而回滚。
3. **F5 公开接口日志**：完整覆盖 middleware 顺序、finish/close/aborted exactly-once、`499`、bounded request/response snapshot、capture status、敏感 header 过滤、管理读和默认 30 天 retention。
4. **F6 使用记录与统计**：最后迁移 pricing freeze、usage shard、写入事实、统计游标和恢复。现行 Redis Stream/ACK 提供可恢复事实；若改成 Go 直投，必须先冻结新的可靠性契约，不能把它替换成无恢复源的裸 goroutine。

原始审计以外的“各种日志”不能合并成一个模糊批次。操作日志、公开接口日志和 usage 有不同的数据模型、失败语义、权限和恢复要求，必须分别完成。

## 每批完成门禁

每一批都必须按以下顺序完成，任何一步失败都不能进入下一步：

1. 冻结完整 Node producer、capture、transport、writer、schema、reader、retention、配置、启动/停机、指标和测试清单。
2. Go 同时实现 SQLite/PostgreSQL Store、稳定 ID/幂等、owner lease/fence、直接异步生命周期、retention、只读契约和错误可见性。
3. SQLite 保持单 writer、WAL 和 `busy_timeout`；PostgreSQL 保持连接池、事务/锁超时、批次和文件/内存边界。Go 不新增 Redis/Asynq/通用业务队列，但“无队列”绝不等于无限 goroutine 或无限连接。
4. 在隔离开发环境完成 mock/golden、race/vet/typecheck、真实 PostgreSQL smoke 和 Node -> Go -> Node 端到端；失败时禁止跨存储或回退 Node。
5. 切换唯一 owner 后，把旧 Node 完整文件移动到 `migration-backup/node/<feature>/`，生成逐文件 SHA-256 manifest，并清零活跃 import、scheduler、consumer、schema、部署和测试入口。
6. 发布包、Docker standalone/performance 与目标 Mac 都必须包含新 owner。Mac 先以不可变 independent candidate 槽完成进程、数据读回、重启、停机和稳定观察。
7. 高性能生产只通过 `performance-handover-controller.sh` 原子切流。切流前验证前端 bundle API base、真实浏览器登录态业务页、Node 双 health、gateway、F1/F2/F3 或新 owner 数据读回；旧槽保留到稳定窗口结束。
8. 新 owner 的总审、回滚 manifest、生产观察和文档全部通过后，才开始下一功能。

## 下次会话操作方向

- 先完成发布 candidate/handover 的生产级演练和事故门禁验证。
