# W7 模型检测写入与任务契约迁移记录

## 当前状态

状态：`契约固定 + 账户状态传播 + durable control-plane / health-sync adapter 扩展`。Node 继续拥有 POST run、stop、SSE、真实上游探针、dataset writer、retention 和模型质量 worker。Go 已固定 writer/job 与纯质量决策契约，补齐 `accounts.quality_isolated`、控制面 schema、policy CAS、schedule 配置/claim/complete、enforcement apply、recovery claim/complete、quality-health hourly writer，以及 failed health-sync 的 token/epoch claim、同库原子完成与 release seam；不注册运行路由，不启动 worker，不接生产 owner。

## 已固定契约

- Asynq task type：`model-check:run`，payload version `1`。
- payload 只携带稳定业务 ID、目标 / 可信对比 config revision、model/profile、`probeSetVersion`、可信对比选择、trace ID 和 requestedAt；queue 为 `model-check` 并由 ops worker role 消费，基础设施失败最多 retry 3 次，总 deadline 按 `probe-plan-budget-v1` 从实际 probe plan 推导。
- public run status：`running/completed/failed/canceled`。
- terminal transition：只允许 running 进入一个终态，相同终态重放幂等，不同终态不可覆盖。
- worker claim 使用单调 `claim_epoch` fencing；续租和所有写阶段都校验 epoch，旧 lease owner 失效后不能继续写。
- run 与 enqueue outbox 同一 PostgreSQL 事务提交，outbox 保存 canonical payload bytes / SHA-256 / task type / version，dispatcher 使用 `UniqueKey(payload)` 作为 Asynq `TaskID` 原样幂等投递；不保留 DB / Asynq 双写窗口。
- worker 的三种终态都要求有效 claim 和未过期 lease，completed / failed 还要求没有 stop intent；用户 stop 独立原子写取消意图并执行不要求 worker claim 的 canceled CAS。
- task payload 使用最大 `8 KiB` 的严格 codec；producer 先 canonicalize，consumer 拒绝未知字段、重复字段、非 canonical 标识字段和尾随 JSON。
- write stages：`create_run/checkpoint_probe_attempts/upsert_items/append_observations/finish_run`；checkpoint 是内部恢复事实，不暴露 partial report。
- SSE disconnect 不取消 durable run；stop 是显式共享取消入口。
- Go 不迁移 Node active `Map`、SQLite writer IPC 或 Token child process pool。

实现和原因见 [模型检测写入与任务契约 Go 迁移设计](../superpowers/specs/2026-07-22-模型检测写入与任务契约Go迁移设计.md)。

## 2026-07-26 模型质量纯决策契约批次

- 新增 `internal/modelquality`，以无 I/O 的 Go 类型收敛 Node 当前质量判定：仅 `completed` 且非 `unavailable` 的 run 可触发处罚；`suspicious`、未声明映射冲突和协议失败属于硬失败，其他低于阈值的完成 run 也失败；`unavailable` 只形成质量健康事实，不触发处罚。默认策略保持 quick、手工处罚开启、阈值 70、fallback 和 10 分钟恢复周期。
- 策略/账户/计划 revision 与处罚 generation 采用不同 Go 类型，处罚仅允许自有物理账户且 policy/account `system_account_id` 一致；source-status 矩阵与 Node 相同：fallback 仅 active，disable 可为 active 或 quality-isolated，quality-isolate 仅 active。手工处罚仍须显式开关；quality-recovery 只能走恢复计划，不能误复用普通处罚入口。
- 恢复计划只认可同一 active quality-isolate enforcement token 与 policy revision；通过时依可用时间表事实恢复 active 或 disabled，失败/策略变更时保留隔离并请求重排。租约、实际时间、数据库 CAS、健康小时写入、缓存失效、worker 和 listener 均不在此包内。
- Node 最新恢复任务会在 claim 时刷新账户 `config_revision`；Go `ClaimRecovery` 也只在 policy/enforcement generation、账户 scope、active isolation 状态均匹配时，才把该次 claim 的当前 revision 写入 enforcement state。隔离后、claim 前的配置修改会成为新检查基线；claim 后的修改则由 recovery request、claim snapshot 与当前账户的三方比较判为 stale，保持 `quality_isolated` 并请求重新调度，连“检测未通过”的结果也不能覆盖较新的账户配置。

## 2026-07-26 schedule PostgreSQL CAS adapter 批次

- `modelqualityschedule` 已实现 schedule upsert/delete、到期 claim 和 run complete。配置写入先锁定自有物理账户，再锁 `(system_account_id,account_id)` 唯一 schedule；创建使用独立 `mqs_*` ID，更新原子推进 revision、重算 `next_run_at` 并清空旧 owner/token/until，显式 expected revision 冲突返回当前事实而不覆盖。
- claim 保持 Node 的默认批次 3、最大 20、默认 5 分钟和 1–30 分钟 lease，但使用 Go 原生 opaque token。候选只对 active、自有、未删除账户按 `(next_run_at,id)` 排序，并以 `FOR UPDATE OF mqs SKIP LOCKED` 锁 schedule；lease UPDATE 再以账户 `config_revision`、active/owned/deleted facts 做 EXISTS CAS。账户在选择后发生变化时仅跳过该候选，不回滚已安全处理的其他候选。
- claim 有意不锁账户行：账户编辑/删除通常先锁账户再处理子事实，同时锁 schedule+account 会形成相反锁序和死锁环。当前方案只持有最多 20 个 schedule 行锁，账户随后变化由 claim revision snapshot 和 worker/enforcement revision fence 判 stale，既不扩大热点锁，也不牺牲状态安全。
- complete 必须同一 SQL 同时匹配 schedule revision、durable interval、owner、token、精确 lease-until、未过期 lease 和不早于 claim 的完成时间；成功后一次写入 last-run facts、下一执行时间并清空完整 lease。相同进程重新 claim、配置编辑、租约过期或迟到回调均不能完成旧代次。
- adapter 只使用请求局部切片和最大 20 条候选/policy cache，没有后台 goroutine 或全局可变状态；rows 在后续查询前显式关闭，事务提交失败不返回 claim，rollback 使用独立 5 秒有界 context。持久 ID/token 使用返回 error 的加密随机 UUID，熵源失败会回滚而不是触发 `uuid.Must` 类 panic。定向 escape analysis 只保留 pgx `Scan`/variadic SQL 参数和返回可选时间/lease 指针的预期逃逸，均受 20 条批次和小字段上限约束，不持有 body、credential 或跨请求缓存。targeted race、vet 和 transaction stub 回归已通过；真实 PostgreSQL 双连接 `SKIP LOCKED` / stale CAS smoke 仍待后续集中验证。
- Node 与 Go schedule worker 不能同时运行。可空 token 列仅支持 schema 共存和未来切流，不提供 Node 旧 completion 对 Go token 的互操作；生产启用 Go worker 前仍必须完成 Node drain、single-owner 和回滚门禁。

## 2026-07-26 recovery PostgreSQL CAS adapter 批次

- `modelqualityrecovery` 已实现到期 recovery claim 和 complete。claim 保持 Node 默认 2、最大 10、默认 6 分钟与 1–30 分钟 lease，但每次生成 error-returning 随机 opaque token；候选按 `(recovery_due_at,account_id)` 稳定排序并只锁 enforcement 行，账户状态、scope、ownership、当前 config revision 和当前有效 policy revision 在 lease UPDATE 中再次 CAS。enforcement 上的 policy revision 继续保留为处罚创建时的审计事实，不用于永久钉住后续恢复；策略或账户在候选读取后变化时只跳过该项，不启动陈旧探针。
- Go 有意不照搬 Node 的 owner-only lease。completion 必须同时匹配 enforcement ID、generation、owner、token、精确 lease-until、未过期 lease、policy revision、claim 捕获 revision 和当前 account revision；同一进程的新 claim、迟到回调、claim 后账户编辑或策略修改均不能清除当前隔离。检测失败也遵守三方 account revision fence，不能用旧失败结果延长较新配置的恢复周期。
- completion 采用固定的 `account -> enforcement` 加锁顺序：先无锁读取 scope，再锁账户并重新锁/复核完整 enforcement lease。claim 只持 enforcement 锁且以 EXISTS 读取账户，不获取账户行锁，因而不会与账户编辑或处罚写入的 account-first 路径组成反向锁环。恢复账户的 status/schedulable/error/config_revision 修改和 enforcement clear 在同一事务内；clear 的最终 CAS 失败会回滚先前账户修改，不留下半恢复状态。
- 通过检查时复用 `apikeyschedule` 的 Go 时间表领域实现决定恢复 `active` 或 `disabled`，没有复制一套 JSON/时区算法。持久 JSON 在 decode 前限制为 256 KiB，windows/exceptions 继续沿用既有 32/128 上限；失败探针或已确定的 policy/config drift 不解析无关时间表。adapter 仅分配最大 10 条候选和同批 system-account policy cache，无 goroutine、channel、ticker、全局可变状态或跨请求引用。
- 本批 targeted race、vet、事务回滚与 SQL fence 回归通过。尚未执行真实 PostgreSQL 双连接 lock/CAS smoke；quality-health writer 已由后续独立批次补齐，cache invalidation、worker/Asynq、Node drain 和生产 single-owner 仍未完成，因此不能把 recovery adapter 存在解释为恢复任务已接管。

## 2026-07-26 enforcement PostgreSQL CAS adapter 批次

- `modelqualityenforcement` 已把纯 `PlanEnforcement` 接入 PostgreSQL。事务固定先锁 account、再锁该 account 唯一 enforcement；policy、manual-enforcement 开关、action、account scope/ownership/status/config revision 在账户 mutation 和最终 enforcement write 中再次 CAS。首次写使用 `ON CONFLICT DO NOTHING` fail-closed，替换已有事实必须匹配旧 enforcement ID 与 generation；任一最终 CAS 丢失都会回滚先前账户修改。
- generation 只通过 `modelquality.NextGeneration` 推进并在 PostgreSQL INTEGER 上限前拒绝，ID 使用 error-returning 随机 UUID。disable/quality-isolate 原子写 `schedulable=false`；fallback 原子启用 fallback、清 super priority；真实账户 mutation 同时写有界质量错误并递增 config revision。`last_error_trace_id` 会清空，避免把此前无关请求 trace 错绑到模型质量处罚。
- Go 主动修复 Node 的两类重放/租约问题：同一 `trigger_run_id` 一旦已有 enforcement 事实，即使该事实后来 cleared，也只返回幂等 no-op，旧 durable job 不会在恢复后重新复活处罚；新 generation 会清空旧 recovery owner/token/until、last-run 和 cleared facts，避免继承旧代次租约而延迟新恢复。不同 action 复用同一 run ID 则返回 stale，不静默改写历史含义。
- 处罚创建时持久 `account_config_revision` 保留本次 pre-mutation 快照；后续 recovery claim 再按当前账户 revision 刷新，文档和 port 注释已区分两个阶段。错误消息输入最大 64 KiB，持久化最多 1000 个完整 Unicode scalar，并拒绝 PostgreSQL 不支持的 NUL；截断不构造完整 rune slice。adapter 无 goroutine、channel、ticker 或跨请求缓存，cache invalidation 继续由未来应用层在 `applied` 后负责。
- 本批 targeted race、vet、generation/rollback/idempotency/UTF-8 回归通过；尚未执行真实 PostgreSQL 并发 Node/Go writer smoke。生产启用前仍须完成 single-owner、Node drain、应用层 cache invalidation、worker/Asynq 与回滚门禁。

## 2026-07-26 quality-health PostgreSQL writer 批次

- 新增细粒度 `ModelQualityHealthFailureWriter` port 和 PostgreSQL adapter，复用现有 `usageStatsTimezone` reader 与 `timezonecompat`，按 Node-compatible `YYYY-MM-DDTHH` 本地小时生成 `stat_hour`。秋季 DST 重复小时仍合并为同一小时事实，由 UTC `observed_at` 决定较新观测；这是共享表和现有读契约的兼容边界，不在共存期擅自改成带 offset 的新 key。
- 单条 `INSERT ... ON CONFLICT` 以 `(account_id,stat_hour)` 幂等写入，只允许更大的 canonical UTC millisecond `observed_at` 覆盖；相同时仅更大的 `model_check_run_id` 胜出。`updated_at` 只是审计元数据，不参与新旧裁决。旧/迟到重放返回 `Applied=false`，不额外读行、不刷新旧事实，也不存在读后写竞态。

- adapter 不持有全局缓存、goroutine、channel、ticker、事务或行锁；每次调用只有一次设置读取和一次单行 UPSERT，所有临时字符串与参数均受明确上限。它只写独立 retained statistics fact，不查询账户 FK，也不拥有 dataset decision；账户或 run 后续保留清理不会追溯抹除已发生的质量不可用事实。

## 2026-07-26 quality-health durable retry adapter 批次

- Goose `000085_w7_model_quality_health_sync_retry.sql` 将当前 Node `juhe_dataset.model_check_runs` 的完整 TEXT/INTEGER 物理事实纳入 fresh Goose 数据库，并以加法列补充 health-sync owner、opaque token、单调 epoch、lease-until、next-attempt、attempt count、错误摘要和独立同步更新时间。共存期不添加 owner/token/until 三元 CHECK，避免仍在运行的 Node writer 因不了解 Go token 而写入失败；Down 保持 forward-only `SELECT 1`。
- Go 没有把纯 `(updatedAt,id)` cursor 当作生产所有权。PostgreSQL adapter 在单事务内按 due time、`updated_at`、ID 有界选择最多 100 条失败 run，使用 `FOR UPDATE SKIP LOCKED`，再以 owner/逐 run token/epoch/until 原子 claim。所有随机 token 在加锁前生成且熵源失败返回 error；lease 到期、claim due、release retry-at 均由 PostgreSQL `clock_timestamp()` 生成 canonical UTC millisecond TEXT，调用方只传 duration，主机时钟漂移或锁等待跨过到期点不能延长所有权；epoch/attempt 到 PostgreSQL bigint 上限后 fail-closed，不发生整数回绕。
- durable decision JSON 只读取最多 64 KiB，必须是无重复顶层字段的对象，严格验证 `threshold`、`healthSyncResult=failed`、`message` 和 `decidedAt`，未知字段继续保留以允许 Node 前向扩展。单条坏数据被写入有界错误摘要并延后一小时，不再使整页回滚或长期饿死后续有效任务；返回 claim 的错误消息已提前收缩到最终 1000 Unicode scalar，避免批量重复持有大文本。
- completion 固定 `account -> quality-health hourly row -> dataset run` 锁序，并在同一 PostgreSQL 短事务中先写 retained hourly fact，再以 run ID、account/system scope、原始 decision JSON、原始 `updated_at`、owner/token/epoch/精确 lease-until 和未过期 lease 做 decision CAS。hourly UPSERT 的 `RowsAffected=0` 代表已有更新观测胜出，仍允许标记 applied；decision CAS 丢失则事务整体回滚，消除 Node 现有“统计已写、decision 未写”的可避免双写窗口。
- release 只允许当前 token/epoch/lease，写入显式 retry-at 与有界错误分类/摘要；迟到或被替换的 worker 返回 false，不覆盖新 owner。adapter 没有 goroutine、ticker、channel、全局缓存或事务内二次借连接，候选/JSON/错误均有上限，pgx rows 在任何写入前关闭，rollback 使用独立 5 秒 context。
- 本批只迁移 durable seam，不注册 scheduler/worker。Node 与 Go health-sync retry 仍必须单 owner；当前 Node retention 会删除任意非 running run，尚未排除 `quality_health_sync_status='failed'`，因此生产切换前必须先补 retention 门禁并完成真实 PostgreSQL 双连接 claim/CAS、账户删除并发、commit-unknown 和 Node/Go 共存 smoke。该缺口被明确记录，不能用 adapter 单测替代接管证据。
