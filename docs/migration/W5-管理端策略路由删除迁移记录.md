# W5 管理端策略路由删除迁移记录

> 本文记录管理端与个人端策略路由删除接口的 Node 当前契约、Go opt-in 实现和删除门禁。Go service、HTTP、前端请求捕获和 PostgreSQL integration smoke 代码已完成；本机 Windows Docker provider 不可用，目标 smoke 输出 `SKIP`。这不表示真实 PostgreSQL 已通过、生产流量已切到 Go，或 Node 路由与 repository 可以删除。

## 基本信息

- 接口：
  - `DELETE /__aisys__/api/route-strategies/{id}`
  - `DELETE /__aisys__/api/my-route-strategies/{id}`
- 当前 Node owner：`backend/src/modules/route-strategies/route-strategies.routes.ts`、`backend/src/storage/route-strategy.repository.ts`
- 目标 Go owner：`backend-go/internal/modules/managementroutestrategies/`、`backend-go/internal/httpapi/`、`backend-go/internal/store/postgres/`
- 当前状态：Go opt-in 已实现，真实依赖待复跑，未生产接管
- 关联计划：`../plans/计划-0081-Node转Go渐进减法迁移.md`

## 权限与传输

- 管理端只允许 `admin` / `super_admin`。未指定 `systemAccountId` 或使用 `all` 时按全局 ID 删除；指定具体 ID 时收窄到该 owner。
- 个人端强制使用当前 session 的系统账户 ID，并忽略 query 中伪造、空白或重复的 `systemAccountId`。
- 不存在、owner 不匹配和个人端跨 owner 删除统一返回 `404 { "message": "策略路由不存在" }`。
- 两条路由都受 `JUHE_AI_MANAGEMENT_API_ENABLED` opt-in 保护，默认不注册。
- DELETE 不读取请求体，不挂 JSON body parser，也不挂进程内 mutation guard。
- 中间件顺序固定为鉴权前 IP write limiter、写鉴权与 session touch、已认证用户 write limiter；管理路由随后执行 admin 校验，再进入 handler。
- 成功响应固定为 `204`、空 body 和 `Cache-Control: no-store`。

## 删除保护与错误语义

- 默认策略路由不允许删除，返回 `400 { "message": "默认策略路由不允许删除" }`。
- 已被 API Key 使用的策略路由不允许删除，返回 `400 { "message": "策略路由已被 N 个 API Key 使用，请先解绑" }`。
- 上述两类业务冲突按当前 Node 管理接口契约使用 `400`，不改成 `409`。
- 数据库、事务提交和其他内部错误统一返回 `500 { "message": "服务器内部错误" }`，不回显内部错误文本。

## 事务与并发

- 删除复用 public route strategy PostgreSQL transaction/store，并通过事务 callback store 读取目标策略。
- production transaction store 的 `FindPublicRouteStrategyByID` 必须调用锁读 helper；源码门禁同时固定 helper 的 `forUpdate=true` 和 `FindPublicRouteStrategyByIDForUpdate` 命名 SQL section 中独立的 `FOR UPDATE`。
- 默认保护、owner 收窄、API Key 引用计数和硬删除都在同一事务内基于锁定快照执行。
- 主表删除依赖 fresh schema 的外键级联清理 `route_strategy_groups`；binding 删除触发失败或 commit 失败时，策略主表和 binding 都必须保留。
- 事务失败返回零结果，不发布运行态失效，也不写成功操作日志。

## 写后副作用

事务提交后使用脱离客户端取消、最长 5 秒的 context best-effort 发布网关运行态失效，reason 固定为：

```text
route_strategy_deleted
```

失效失败只记录结构化 warning，不回滚已经提交的删除。

操作日志固定为：

- module：`route_strategies`
- action：`delete`
- key：`route_strategies.delete`
- summary：`删除策略路由：<name>`
- changes：仅记录 `deleted: false -> true`
- visibility：`targeted`
- viewer：目标 owner

删除前摘要严格只包含 `id/name/mode/status`。说明、配置、分组绑定、API Key 信息和内部数据库字段不进入 operation-log payload。管理端日志 mode 为 `admin`，个人端为 `self`；operation log 入队失败不覆盖业务成功。

## 前端契约证据

`frontend/scripts/regression/route-strategy-create-api-regression.ts` 同时固定创建、更新和删除请求契约，其中删除部分覆盖：

- 管理端全局删除不发送 owner query。
- 管理端显式 owner 删除发送 `systemAccountId`。
- 个人端使用 `/my-route-strategies/{id}`，忽略外部传入的 owner。
- scoped delegation 保持正确管理路径和 owner query。
- 所有 DELETE 请求都不发送 body。

## 删除门禁

以下条件全部满足前，不能删除 Node 删除接口：

1. 健康 Docker/testcontainers 或独立环境中真实 PostgreSQL smoke 通过。
2. Node 与 Go 发布 `route_strategy_deleted` 后，真实 Redis 双 runtime 失效和 speed-first 状态清理观测通过。
3. 前端策略路由页面连接真实 Go 后端完成管理 / 个人删除 smoke，并验证默认策略和 API Key 引用错误。
4. 反向代理按两条 DELETE 路径切到 Go 单 owner，并完成回滚演练。
5. 生产观测确认错误率、延迟、连接池、行锁等待、失效失败和 operation log 入队告警正常。
6. 删除对应 Node route/store/test 后提供 `rg` 静态证据。

## 当前结论

管理端策略路由删除已经形成 Go service、HTTP、router/app、事务锁读、硬删除、前端 request-capture 和 integration smoke 代码。真实 PostgreSQL、真实 Redis 互操作、前端真实 Go 后端联调、生产切流、回滚和 Node 删除仍未完成，因此状态保持 Go opt-in。
