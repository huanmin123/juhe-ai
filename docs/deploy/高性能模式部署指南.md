# 高性能模式部署指南

> `performance = PostgreSQL + PgBouncer + Redis cache + Redis state + Redis queue`。
> 默认轻量部署看 [Docker 部署指南](Docker部署指南.md)。

## 1. 适用边界

适合 SQLite + 进程内缓存已经不够的部署。家庭宽带入口默认不选高性能模式。

当前边界：

- 核心 PostgreSQL repository、DB service、Redis cache/state/stream、网关事实写入、System API 高频管理链路和主要统计窗口已通过远端 PG/Redis smoke、readiness 和压测验证。
- 未覆盖或未启用的低频入口、复杂筛选和长周期运维任务在 PostgreSQL 模式下必须 fail-fast，不允许静默回退 SQLite。
- 关键共享缓存已接 Redis `SharedJsonCache` 并有门禁；剩余本地 LRU 是已登记的本进程快照或热路径保留项，不代表全量 Redis 化。
- 高性能模式上线前必须在目标机器跑一次本机验证和业务回归。

压测和容量结论只放 [reports 目录](../reports/README.md)，不写进部署 runbook。

## 2. 组件

| 组件 | 默认镜像 | 边界 |
| --- | --- | --- |
| PostgreSQL | `postgres:18-bookworm` | 事实数据、统计结果、日志索引 |
| PgBouncer | `edoburu/pgbouncer:v1.25.2-p0` | 应用只连 PgBouncer |
| Redis cache | `redis:8.2.7-bookworm` | 可丢弃缓存，`allkeys-lru` |
| Redis state | `redis:8.2.7-bookworm` | 短 TTL 运行态、原子计数，`noeviction` |
| Redis queue | `redis:8.2.7-bookworm` | Redis Streams 未落库消息队列，`noeviction`，必须监控 pending + lag |
| juhe-ai | `node:22-bookworm-slim` | 同机 control、gateway、worker 与各自 DB service 子进程 |

不要使用 `latest` 镜像。Redis 8 授权如果不接受，需要单独评估替代方案。

## 3. 部署文件

```text
docker/
  compose.performance.yml
  .env.performance.example
  postgres/init/001-extensions.sql
```

默认生产入口是宿主机 Caddy HTTPS：

```text
公网 80/443 -> Caddy -> 127.0.0.1:3000 juhe-ai
```

高并发网关和管理后台共用同一域名时，macOS 裸机部署使用同机多进程拓扑：

```text
公网 80/443 -> Caddy -> 127.0.0.1:3000 Nginx
  /__aisys__/*、/__aipublic__/* -> control:3200
  其他 AI 路径                  -> least_conn(gateway:3101..3103)

control: 1 server + Usage Worker 2 + Log Worker 2 + Stats Worker 1 + Ops Worker 1
gateway: 3 个独立 Node 事件循环，各自只处理客户端请求
```

所有 Node 端口只绑定 `127.0.0.1`。gateway 与 control 各自看护 DB service 子进程并使用动态本机端口，DB service 不对 Nginx 或公网暴露。Redis cache/state/queue 与 PostgreSQL 是同一套共享事实源；Usage、审计、操作日志和公开接口日志通过 Redis Stream consumer group 分工，禁止每个完整 server 重复启动一套 consumer。

拓扑权威边界见 [高性能模式同机多进程拓扑设计](../functions/高性能模式同机多进程拓扑设计.md)。Go 迁移完成后，正式部署应按 [Go 迁移开发构建部署调整](../migration/开发构建部署调整.md) 改为 Go server / worker、PostgreSQL、Redis / Asynq、health、Prometheus metrics、pprof 和 worker lag 口径；不得继续把 `db-service`、Node event loop 或 SQLite 文件体积作为 Go 服务健康和容量判断依据。

Compose 默认端口边界：

- 应用：`JUHE_AI_PUBLIC_BIND=127.0.0.1`
- 中间件：`JUHE_AI_MIDDLEWARE_BIND=127.0.0.1`
- 公网只开放 Caddy `80/443`

规则：

- `.env.performance.example` 的密钥和连接串保持空值，未填写时 Compose 必须失败。
- 改数据库或 Redis 密码时，同步改对应 URL；密码和 URL 不能漂移。
- URL 里的密码必须百分号编码；避免直接 `source .env.performance` 后拼接原始密码。
- `JUHE_AI_TRUST_PROXY=true` 只在应用端口被 Caddy、负载均衡或可信内网入口保护时使用。
- 同机多进程模式由每个 server 自动分配 DB service 本机端口；Nginx 不直连 DB service。管理流量进入 control，AI 流量只进入 gateway 池。每个 gateway 必须把 `JUHE_AI_ACCOUNT_HEALTH_CHECK_DISPATCH_URL` 指向实际 control loopback 端口，使真实请求失败触发能经 HMAC 内部通道到达 ops-worker；该地址不得指向公网入口，缺失或非法时 gateway 会拒绝启动。
- macOS performance 滚动安装固定按 Gateway 逐个重启、逐个 HTTP 健康并确认 `gateway:<id>` 与 `db-service:<id>` 已进入 Redis 进程指标索引，最后才重启 control 及其 worker；control 健康后还必须确认完整拓扑角色都已注册，才能切换 Nginx。指标 publisher 对在线请求保持 fail-open，但部署 gate 对注册失败 fail-closed 并触发安装回滚，防止新 reader 在旧 publisher 仍存续时提前上线。
- `JUHE_AI_USAGE_SPOOL_DIR` 必须位于 release 目录之外并由 control 与所有 gateway 进程共同可读写；每个 gateway 只写自己的实例子目录，Usage worker 副本 0 扫描全部实例目录并在 Redis 恢复后重放。
- capability v2 另要求每台 gateway host 配置 release 外持久卷上的 `JUHE_AI_CAPABILITY_HANDOFF_SPOOL_DIR` 与独立 `JUHE_AI_CAPABILITY_HANDOFF_QUARANTINE_DIR`。目录必须由 gateway / replay 专用身份读写并禁止其他用户访问，启动时验证 append / fdatasync / rename、record / checksum contract version、24 小时峰值容量和告警 / 摘流阈值；不能放在容器临时层或发布解压目录。host-local 持久卷只覆盖进程 / release 崩溃，不覆盖主机或磁盘永久丢失；发生后 producer 必须转 lost 并激活 global barrier。要求 RPO=0 的环境还必须把 durable record / sealed segment 在 ACK 前同步复制到第二故障域；异步镜像需在 manifest 声明最大 RPO。当前变量、spool / replay owner、复制 policy 和 preflight 尚未实现，因此 capability v2 保持禁用，不能只创建目录后宣称满足门禁。
- performance 默认只保留 50/1000 的正常网关阶段详情；失败、中断、慢阶段和每请求终态摘要仍保留。日志 publisher 待写字节达到压力阈值时，正常阶段详情暂停，不能反向阻塞 AI 流。
- `JUHE_AI_GATEWAY_UPSTREAM_AGENT_MAX_*` 控制网关到上游的 Node keep-alive 连接池。慢 SSE 或长对话并发较高时优先加大这些上限，并同步确认系统 `nofile` / launchd / systemd 文件句柄上限；不要改成无限连接。
- 公网 Edge、WireGuard、Caddy/Nginx、Linux/macOS 系统参数和入口容量门禁由 [反向代理与高并发隧道部署指南](反向代理与高并发隧道部署指南.md) 维护；本指南只负责应用与数据层高性能模式。
- `JUHE_AI_REDIS_NAMESPACE` 是同一套部署的 Redis key 前缀，生产建议显式设置并保持稳定；多套环境共用 Redis 实例时必须使用不同 namespace。
- 高性能模式要求 `JUHE_AI_REDIS_CACHE_URL`、`JUHE_AI_REDIS_STATE_URL`、`JUHE_AI_REDIS_QUEUE_URL` 指向三个不同的物理 `host:port`；同一进程不同 DB 不算隔离，也不存在共享绕过开关。Redis URL host 不接受 `localhost` 或 `::1`，同机部署统一使用 canonical `127.0.0.1`。
- 普通 PostgreSQL SQL 直接通过 pool / PgBouncer 执行，`statement_timeout`、`lock_timeout` 和 `idle_in_transaction_session_timeout` 必须配置为目标数据库或应用 role 默认值；部署迁移后要通过 PgBouncer 新连接执行 `SHOW` 精确验证。显式多语句事务仍由应用按上述环境变量执行 `SET LOCAL` 覆盖。不要在 URL 里拼 startup parameter，避免 PgBouncer 拒绝或跨事务污染。
- 当前 Docker 模板的 `POSTGRES_USER=juhe_ai` 是 PostgreSQL 初始化账号，按官方镜像语义具备较高权限；生产必须把 PostgreSQL / PgBouncer 端口限制在本机、WireGuard 私网或安全组白名单内。独立 admin/app 账号改造需要同步 PgBouncer、初始化脚本和回归验证。

PowerShell 生成 URL 编码密码：

```powershell
[uri]::EscapeDataString('替换为强密码')
```

Node 生成 URL 编码密码：

```bash
node -e "console.log(encodeURIComponent(process.argv[1]))" '替换为强密码'
```

## 5. 启动

macOS 裸机先确保 Nginx 主配置已经 include 一个专用绝对路径，再用默认 dry-run 审核拓扑：

```bash
bash docs/deploy/macos/operations/install-performance-topology.sh --dry-run \
  --scope user \
  --base-dir "$HOME/juhe-ai-lite" \
  --label-prefix com.example.juhe-ai.performance \
  --control-port 3200 \
  --gateway-base-port 3101 \
  --gateway-count 3 \
  --usage-workers 2 \
  --log-workers 2 \
  --ingress-port 3000 \
  --nginx-config /opt/homebrew/etc/nginx/servers/juhe-ai-performance.conf
```

确认路径、端口、旧入口和回滚目标后才把 `--dry-run` 改成 `--apply`。脚本先启动并连续验证所有 Node health，再执行 `nginx -t` 和 reload；任一步失败都恢复先前 plist、run script 和 Nginx include。该脚本只把新拓扑准备到 `127.0.0.1:<ingress-port>`，不会修改 Caddy 或公网入口；未启用 capability v2 时，必须在新入口业务探针通过后再使用既有 temporary cutover 流程切换，旧服务保留到稳定观察完成。capability v2 启用后禁止使用纯入口 temporary cutover，必须改走 deployment epoch 协调器、ingress / finalizer drain 和新 epoch 回滚。单机 `standalone` 不使用此脚本，继续只启动一个 `server`。

项目根目录先构建：

```bash
pnpm install
pnpm build
```

启动：

```bash
cd docker
docker compose --env-file .env.performance -f compose.performance.yml config --quiet
docker compose --env-file .env.performance -f compose.performance.yml up -d --build
docker compose --env-file .env.performance -f compose.performance.yml ps
```

看日志：

```bash

docker compose --env-file .env.performance -f compose.performance.yml logs --tail=100 pgbouncer
```

`postgres`、`pgbouncer`、`redis-cache`、`redis-state`、`redis-queue` 应为 healthy。`juhe-ai` 如果因未覆盖入口 fail-fast，先按第 7 节定位具体入口和回归范围，不要让配置回退 SQLite。

## 6. PostgreSQL 初始化

以下命令在 Linux / bash Docker 宿主机执行。Docker 宿主机验证要把 URL 改成宿主机发布端口：

```bash
export JUHE_AI_RUNTIME_MODE=performance
export JUHE_AI_DATABASE_DRIVER=postgres
export JUHE_AI_CACHE_DRIVER=redis
export JUHE_AI_RUNTIME_STATE_DRIVER=redis
export JUHE_AI_QUEUE_DRIVER=redis_stream
export JUHE_AI_POSTGRES_URL='postgres://juhe_ai:<PostgreSQL密码URL编码>@127.0.0.1:6432/juhe_ai'
export JUHE_AI_REDIS_CACHE_URL='redis://:<Redis缓存密码URL编码>@127.0.0.1:6379/0'
export JUHE_AI_REDIS_STATE_URL='redis://:<Redis运行态密码URL编码>@127.0.0.1:6380/0'
export JUHE_AI_REDIS_QUEUE_URL='redis://:<Redis队列密码URL编码>@127.0.0.1:6381/0'
export JUHE_AI_REDIS_NAMESPACE='prod'
```

空库、首次部署或测试库重建执行完整初始化：

```bash
pnpm --filter juhe-ai-backend postgres:init-schema
```

已有当前版本库只需要复查 DDL 时，才执行 schema-only：

```bash
pnpm --filter juhe-ai-backend postgres:init-schema-only
```

`postgres:init-schema` 面向空 PostgreSQL 库或明确要重建的测试库，会创建当前版本 schema 并写入默认系统账号、供应商、协议档案、默认分组和系统设置种子；只跑 `schema-only` 会导致创建分组 / 账号时缺默认供应商数据。`postgres:init-schema-only` 只用于当前版本库的 DDL 复查，不作为旧库结构迁移方案。生产执行前先完成临时库预演、项目备份和业务备份，执行后跑第 7 节 readiness。完整初始化会写入默认管理员，开放公网前必须先在内网登录后台轮换默认管理员密码，未完成改密禁止放通 Caddy / Nginx / 防火墙公网入口。

抽样检查：

```bash
docker compose --env-file .env.performance -f compose.performance.yml exec -T postgres \
  sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -c "SELECT count(*) FROM juhe_business.system_accounts;"'
```

### 6.1 数据切换边界

项目代码库不提供 SQLite -> PostgreSQL 数据迁移脚本、旧 PostgreSQL 结构迁移脚本、启动期自动迁移、双读双写或旧 schema 兼容。高性能模式部署只负责“当前版本 PostgreSQL schema 初始化 + 当前代码路径验证”。历史数据是否保留、如何导入、如何对齐旧结构，由运维在代码库外按当次上线窗口单独处理；处理结果必须落到当前 schema，应用代码不承担旧结构成本。

切换到高性能模式后至少执行：

```bash
pnpm --filter juhe-ai-backend postgres:init-schema
export JUHE_PERFORMANCE_SYSTEM_API_POSTGRES_URL="$JUHE_AI_POSTGRES_URL"
export JUHE_PERFORMANCE_SYSTEM_API_REDIS_CACHE_URL="$JUHE_AI_REDIS_CACHE_URL"
export JUHE_PERFORMANCE_SYSTEM_API_REDIS_STATE_URL="$JUHE_AI_REDIS_STATE_URL"
export JUHE_PERFORMANCE_SYSTEM_API_REDIS_QUEUE_URL="$JUHE_AI_REDIS_QUEUE_URL"
pnpm --filter juhe-ai-backend test:performance-system-api-smoke
pnpm --filter juhe-ai-backend test:performance-gateway-persistence-readiness
pnpm --filter juhe-ai-backend test:performance-boundary
```

## 8. 项目备份、业务备份与运行数据边界

高性能模式每次上线生成两类备份并分别只保留最近 3 次。若 `juhe_rollback_compat` 非空，必须把同一次 barrier 的业务备份、项目 release、owner manifest、Goose catalog、rollback adapter contract 及其 WAL/PITR 恢复范围作为一个 pin set 保留到 compat cleaner 证明 manifest 清空；该 pin set 不参与三份轮换，普通新备份仍继续各自轮换，不能因 compat 长期存在而无限积累全部 business 备份：

- `project-时间戳`：升级前当前运行 release 的干净压缩包、清单和校验值；一次性迁移脚本仅作附加证据，不含 `.env`、数据、日志、数据库、`node_modules` 或链接。
- `business-时间戳`：使用一个 coordinator barrier 下的单个 PostgreSQL exported snapshot 覆盖 `public.goose_db_version + juhe_business + juhe_stats`；`juhe_rollback_compat` schema 存在时也加入同一 snapshot。备份还包含恢复所需的 `backend.env` / `.env.performance`、owner manifest / deployment epoch before-image、task / budget 清单、Asynq retry / dead / in-flight、sealed producer set / watermark、quarantine / hold 内容寻址 artifact manifest 和校验值；它与同 stamp 的项目备份组成升级前恢复证据。v2 的 Redis 是可重建派生数据，不替代 PostgreSQL 事实备份。

业务备份示例：

```bash
set -euo pipefail
umask 077

STAMP=$(date +%Y%m%d-%H%M%S)
BACKUP_ROOT=backups
STAGE="$BACKUP_ROOT/.business-$STAMP.tmp-$$"
FINAL="$BACKUP_ROOT/business-$STAMP"
test ! -e "$FINAL"
mkdir -p "$STAGE/pg"
trap 'rm -rf -- "$STAGE"' EXIT

cp .env.performance "$STAGE/backend.env"
chmod 600 "$STAGE/backend.env"

EPOCH_TABLE_EXISTS=$(
  docker compose --env-file .env.performance -f compose.performance.yml exec -T postgres \
    sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -Atqc "SELECT to_regclass('\''juhe_business.deployment_contract_epochs'\'') IS NOT NULL"'
)
case "$EPOCH_TABLE_EXISTS" in
  t)
    ACTIVE_CAPABILITY_CONTRACT_VERSION=$(
      docker compose --env-file .env.performance -f compose.performance.yml exec -T postgres \

    )
    ;;
  f) ACTIVE_CAPABILITY_CONTRACT_VERSION=1 ;;
  *)
    printf 'cannot determine active deployment contract state: %s\n' "$EPOCH_TABLE_EXISTS" >&2
    exit 1
    ;;
esac
case "$ACTIVE_CAPABILITY_CONTRACT_VERSION" in
  1) ;;
  2)
    printf 'capability v2 requires the sealed-producer backup coordinator; this legacy sample refuses\n' >&2
    exit 1
    ;;
  *)
    printf 'unsupported or missing capability contract version: %s\n' "$ACTIVE_CAPABILITY_CONTRACT_VERSION" >&2
    exit 1
    ;;
esac

EVIDENCE_FILES=()
SCHEMA_ARGS=(--schema=public --schema=juhe_business --schema=juhe_stats)
SCHEMA_NAMES=public,juhe_business,juhe_stats
COMPAT_SCHEMA_EXISTS=$(
  docker compose --env-file .env.performance -f compose.performance.yml exec -T postgres \
    sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -Atqc "SELECT to_regnamespace('\''juhe_rollback_compat'\'') IS NOT NULL"'
)
case "$COMPAT_SCHEMA_EXISTS" in
  t)
    SCHEMA_ARGS+=(--schema=juhe_rollback_compat)
    SCHEMA_NAMES=$SCHEMA_NAMES,juhe_rollback_compat
    ;;
  f) ;;
  *)
    printf 'cannot determine rollback compat schema state: %s\n' "$COMPAT_SCHEMA_EXISTS" >&2
    exit 1
    ;;

if [ "$COMPAT_SCHEMA_EXISTS" = t ]; then
  printf 'rollback compat requires the coordinator and a pinned release/database/WAL set; this legacy sample refuses\n' >&2
  exit 1
fi

docker compose --env-file .env.performance -f compose.performance.yml exec -T postgres \
  sh -c 'exec pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB" --format=custom --no-owner --no-acl "$@"' \
  sh "${SCHEMA_ARGS[@]}" > "$STAGE/pg/business-snapshot.dump"
pg_restore --schema-only --no-owner --no-acl \
  --file="$STAGE/pg/business-snapshot-schema.sql" "$STAGE/pg/business-snapshot.dump"
pg_restore --list "$STAGE/pg/business-snapshot.dump" > "$STAGE/pg/business-snapshot.manifest"
pg_restore --file=/dev/null --no-owner --no-acl "$STAGE/pg/business-snapshot.dump"
{
  printf 'created_at=%s\n' "$(date -u +%Y-%m-%dT%H:%M:%SZ)"
  printf 'schemas=%s\n' "$SCHEMA_NAMES"
  printf 'format=custom\n'
  printf 'capability_contract_version=%s\n' "$ACTIVE_CAPABILITY_CONTRACT_VERSION"
} > "$STAGE/manifest.txt"
CHECKSUM_FILES=(
  backend.env
  pg/business-snapshot.dump
  pg/business-snapshot-schema.sql
  pg/business-snapshot.manifest
  manifest.txt
  "${EVIDENCE_FILES[@]}"
)
(
  cd "$STAGE"
  shasum -a 256 "${CHECKSUM_FILES[@]}" > SHA256SUMS
  shasum -a 256 -c SHA256SUMS
)
chmod -R go-rwx "$STAGE"
mv "$STAGE" "$FINAL"
trap - EXIT

retain_latest_three() {
  local prefix="$1" item index
  local -a backups=()
  while IFS= read -r item; do
    [ -d "$item" ] && [ ! -L "$item" ] && backups+=("$item")
  done < <(printf '%s\n' "$BACKUP_ROOT"/"$prefix"-* | LC_ALL=C sort -r)
  for ((index = 3; index < ${#backups[@]}; index += 1)); do
    rm -rf -- "${backups[$index]}"
  done
}

retain_latest_three project
retain_latest_three business
```

上面的 Shell 片段是**legacy-only 示例**。它从数据库 active deployment contract 自动判定，发现 capability v2、未知 contract 或 rollback compat 即 fail-closed；操作者没有布尔变量可以把它强行切成 v2。capability v2 必须使用实现后的 deployment / backup coordinator：冻结 ingress、finalizer 和 capability mutation；冻结 expected producer inventory revision；将每个 producer `draining -> sealed` 并 fsync finalSequence；证明 `control_resolved_through = producer_ack_through = finalSequence`、unacked=0、无 lost / gap / unknown tail / active global barrier；随后在数据库写 immutable backup barrier，绑定 barrierOutboxSeq、snapshot LSN、producerSetDigest、policyDigest、release / manifest / Goose digest。任一未 ACK record 都可能是唯一副本，常规 v2 备份不允许只保存水位或把未封口 spool 留在主机上。coordinator / semantic validator 未实现时，v2 备份保持阻断，不能用非空 JSON、手工空 archive 或 `test -s` 冒充。

legacy 示例中的单次 `pg_dump` 为所选 schema 建立一个 snapshot；schema SQL 从同一个 custom dump 派生，不能再执行第二次数据 dump 冒充同一快照。v2 coordinator 必须显式导出一个 PostgreSQL snapshot，保持 coordinator fence 到所有 schema dump 和外部 artifact manifest 完成，并让 dump 内 backup barrier 行的 snapshot identity / LSN 与外部根 manifest相互引用；仅“导出时间接近”不算同一 barrier。`pg_restore --list`、完整读取、schema / Goose version、逐表 count / digest、外键 / retained reference、producer set、水位和 artifact digest 全部由 semantic validator 重算；通过证明写入根 manifest并签名后才可原子发布。生产脚本还应清理上次异常退出遗留的 `.project-*.tmp-*` / `.business-*.tmp-*`，但不得把暂存目录计入最近 3 次。

示例把 `public` schema 纳入 dump 是为了保存 `public.goose_db_version`；发布前 restore-manifest validator 必须使用项目版本化 allowlist 证明 public 中只有 Goose ledger 与明确允许的基础对象。发现未知业务表即拒绝，不能为“只要有 Goose”而悄悄扩大恢复面。v2 coordinator 也使用相同 allowlist 与 Goose catalog digest。

`juhe_rollback_compat` schema 只要存在就由 coordinator 加入同一 snapshot，空 schema 的额外备份是允许的；它非空时，数据库还必须启用 physical base backup / managed snapshot 与连续 WAL 归档，记录 system identifier、timeline、base backup start / stop LSN、restore point 和保留范围。每个 compat manifest 固定 pin 一个“business backup + project release + current / rollback artifact + owner manifest + Goose catalog + artifact archive + WAL range”集合；compat cleaner 清空前不得删除该 pin set或截断覆盖窗口，但普通未 pin 的 project / business 备份仍分别只保留最近三份。定期恢复到隔离实例验证 compat manifest、task 查询、幂等重放、retired-epoch tombstone、deny-only gate 和 artifact 引用闭合。digest manifest 只能校验内容，不能替代数据副本；灾备恢复先落隔离库，禁止用旧整库覆盖生产中的新业务写入。

quarantine archive 使用内容寻址根 manifest；每个 retained quarantine / hold / receipt 引用必须映射到 `sha256 + byteLength + mediaType + schemaVersion + immutableLocation`。恢复到新主机时先把 artifact 复制到新受限持久卷，生成 signed location-remap manifest，再逐行回读 digest；任何 artifact 缺失、digest 不符、account / scope hold 投影未重建、producer watermark 不闭合都使 capability readiness false。恢复验收固定使用非空 fixture：至少包含一个 pending delivery、一个 terminal duplicate handoff、一个 quarantined sequence + active scope hold + artifact、一个 terminal tombstone，以及一个跨 schema backup barrier；验证只重放一次、ACK 连续、hold 持续过滤并按 fresh evidence / adjudication 正确解除。

`juhe_dataset`、`juhe_usage`、`juhe_codex_context`、Redis、Compose 数据 volume、`data/`、日志和审计 payload 都不进入项目备份或业务备份；`juhe_stats` 在 capability v2 启用后必须进入业务快照，不能继续套用旧排除规则。

临时接管需要复制生产 `juhe_business` 时，使用管道直接恢复到临时库，不持久化 dump：

```bash
docker compose --env-file .env.performance -f compose.performance.yml exec -T postgres \
  sh -c 'pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB" --schema=juhe_business --format=custom' \
  | pg_restore --dbname="$TEMP_POSTGRES_URL" --no-owner --no-acl
```

临时验证完成后删除临时数据库。跨主机数据转移必须作为单独授权的迁移操作处理，不得把非业务历史混入常规备份。

Redis：

- `redis-cache` 使用 `appendonly no`、`save ""`、`allkeys-lru`，不做备份。
- `redis-state` 是可重建的短 TTL 运行态，使用 `appendonly no`、`save ""`、`noeviction`；关闭持久化是为了避免 AOF rewrite 拖慢租约、限频和调度状态，不表示允许随机淘汰。
- `redis-queue` 是 Redis Streams 可靠队列事实源，使用 `appendonly yes`、`appendfsync everysec`、`save ""`、`noeviction`；入队不使用 `MAXLEN` 静默裁剪未确认消息，消费成功 `XACK` 后同步 `XDEL`。未 ACK 消息在落 PostgreSQL 前不能按缓存丢弃。
- 上线需要清理 Redis 时，先停应用并确认所有 Redis Streams 的 pending 和 lag 为 0；确认后只按 `JUHE_AI_REDIS_NAMESPACE` 使用 `SCAN/DEL` 删除本项目 key，不做 Redis 备份。共享 Redis 禁止 `FLUSHDB` / `FLUSHALL`；未确认 drain 前清理会丢未落库队列消息。

Redis Stream drain 检查示例：

```bash
docker compose --env-file .env.performance -f compose.performance.yml exec -T redis-queue \
  sh -c 'redis-cli -a "$REDIS_QUEUE_PASSWORD" XINFO GROUPS "juhe-ai:prod:queue:usage-records"'

docker compose --env-file .env.performance -f compose.performance.yml exec -T redis-queue \
  sh -c 'redis-cli -a "$REDIS_QUEUE_PASSWORD" XPENDING "juhe-ai:prod:queue:usage-records" "juhe-ai:prod:usage-record-writers"'
```

同样检查 `audit-logs`、`operation-logs`、`public-api-logs` 和 `record-maintenance`。正式切换使用 `backend/dist/scripts/operations/drain-redis-streams.js`：先用 token 建立 queue fence，再由独立 one-shot 进程只启动五类 consumer；只有五个目标 group 均存在、所有 Stream `XLEN=0`、全部 group `pending=0/lag=0`，并且连续两个窗口 `XADD` 计数不增长才成功。错误 token、缺组、检查失败或超时都保留 fence 和现场。普通运行日志不参与 Redis drain；必须另行确认各角色 JSONL 文件的 `pendingFileCount=0`、`pendingBytes=0`，并且 ingest-worker 的 `lastCommitAt` 持续推进后再切换。

`lag`、`pending` 或 Redis 返回字段为 `null` / 缺失 / 非法值时按 unknown 阻断，不得折算为 0。one-shot 在启动任何 consumer 之前先确认五个既有目标 group，避免错误 namespace 被启动过程自动创建空 Stream/group 后误通过。无法解码的 Stream 消息保留 pending 并阻断排空，禁止自动 XACK/XDEL 删除唯一现场。

应用 volume：

- `juhe-ai-data` 仍可能保存审计 blob、上下文文件、自动生成文件和临时数据，不进入项目备份或业务备份。
- `juhe-ai-logs` 保存日志，不进入项目备份或业务备份。

## 9. 调优基线

起步值：

```text
PostgreSQL max_connections=300
PgBouncer default_pool_size=50
JUHE_AI_DB_POOL_MAX=150
JUHE_AI_SYSTEM_API_DB_SERVICE_MAX_IN_FLIGHT=256
JUHE_AI_DB_WRITE_MAX_CONCURRENCY=100
Redis cache/state maxmemory=512mb
```

调优顺序：

- 先看 PgBouncer 等待、PostgreSQL active session、慢 SQL、锁等待和 Redis Stream backlog（pending + consumer group lag）。
- 不直接通过加大连接数解决慢查询或热点行冲突。
- `redis-cache` 可淘汰；`redis-state` 和 `redis-queue` 不允许随机淘汰。
- Redis Streams 是 at-least-once 写入队列，不是最终事实表；但未 ACK 条目代表尚未落库的队列事实，不能按缓存丢弃。

## 10. 非 Docker 边界

非 Docker 只要部署出等价边界即可：

```text
PostgreSQL 18
PgBouncer 6432
Redis cache 6379
Redis state 6380
Redis queue 6381
```

三个端口必须由三个不同 PID 持有。macOS 使用 `docs/deploy/macos/operations/install-redis-role-services.sh` 以 dry-run/apply 方式安装或替换 system LaunchDaemon，并使用 `verify-redis-role-isolation.sh` 验证 URL、PID、launchd、PING、策略与持久化；任何角色切换失败都恢复原 plist/config/loaded 状态。完成后仍使用本文第 4、6、7 节的 env、初始化和回归命令。

硬性要求：

- PgBouncer 和 Redis 默认绑定 `127.0.0.1`。
- 跨机器访问只走内网 IP、WireGuard 私网或安全组白名单；业务回源只允许 WireGuard。
- `pg_hba.conf` 用真实可信 CIDR 占位，不写死示例私网。
- 应用和 worker 连接 PgBouncer，不直连 PostgreSQL。

## 11. 停止和清理

legacy / capability v1 停止：

```bash
docker compose --env-file .env.performance -f compose.performance.yml down
```

active contract 为 capability v2 时，普通 `docker compose down` 必须由包装脚本拒绝。停止只能调用 deployment coordinator：先 ingress fence，冻结 expected producer inventory revision，drain 请求 / finalizer，逐 producer seal 并等待 `control_resolved_through = producer_ack_through = finalSequence`、unacked=0、无 unknown tail / lost producer / global barrier，再按 gateway writer -> capability mutation owner / Asynq -> replay / quarantine -> control / stats -> PostgreSQL 的证明顺序停机。replay 必须在 ingress 停止后继续运行到 drain certificate 已签发；不能和 gateway 一起被 compose 直接杀死。

删除 volume：

```bash
docker compose --env-file .env.performance -f compose.performance.yml down -v
```

`down -v` 会删除 PostgreSQL、Redis、应用数据和日志，只能用于临时测试环境；capability v2 生产 manifest 必须明确禁止该命令，不能用备份存在作为删除 volume 的授权。
