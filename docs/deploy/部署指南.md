# 部署指南（国内单机 Docker，唯一生产形态）

> 本文是**从零部署到日常升级的主流程**：一台国内云服务器 + Docker Compose（PostgreSQL + Redis + gateway/jobs/maintenance + Caddy），按顺序执行即可。组件安装与配置参考拆到独立文档，正文只保留流程、门禁和容易出错的细节。
>
> 配置契约的权威来源是仓库 [`docker/single-server/README.md`](../../docker/single-server/README.md)。服务器 IP、域名解析值、密钥等实例事实只在私有目录 `.local/project-resources/prod/` 留档，本文使用占位符。
>
> 已退役、不要使用的形态：K3s/K8s、Harbor/Jenkins 发布链、家庭宽带反向代理、Edge/WireGuard 回源、macOS/Windows 本机部署、SQLite/内存存储模式、Node 后端。

## 0. 从零部署顺序（速查）

1. 服务器：按[主机初始化](host/README.md)执行 `host-init.sh`、安装 Docker、放行 80/443、配好域名 A 记录。
2. 本地：§6 编译三个 Go 二进制 + 前端 `dist`；按[配置参考](config/README.md)填 `.env`；按 §5.2 改 `Caddyfile`（或改用 [Nginx](nginx/README.md)）。
3. 服务器：§7.1 上传 → §5.3 权限 → §7.2 `--profile tool build` → §7.3 起 PG/Redis → §7.4 PG 初始化 → §7.5 `maintenance upgrade` → §7.6 chown + J3b 索引 → §7.7 `up -d`。
4. §8 验证（容器 healthy、公网健康、登录、一次真实 `/v1` 调用）；需要监控时按[监控接入](monitoring/README.md)接入。
5. 日常发布与升级按 §9；备份按[备份与恢复](backup/README.md)。

## 1. 部署形态

```
公网 :80 / :443 / :443/udp
        │
        ▼
   Caddy（juhe-ai-caddy，自动 HTTPS/ACME，80 → 443）
     ├─ /              → 301 /__aisys__/
     ├─ /v1/*          → gateway:3000（OpenAI 兼容入口，SSE 不缓冲）
     └─ 其余            → gateway:3000（管理 SPA + /__aisys__/api）
        │
   gateway（juhe-ai-go-gateway，固定容器 IP 172.18.0.10）
     ├─ postgres:5432（juhe-ai-postgres，单库 juhe_ai，多 schema）
     └─ redis:6379（juhe-ai-redis，DB0；cache/state/J3b 等按 {namespace:域} 键空间隔离）
   jobs（juhe-ai-go-jobs）─ 同 PG/Redis
   maintenance（一次性 CLI，compose profile=tool）
```

- 五个常驻容器：`postgres`、`redis`、`gateway`、`jobs`、`caddy`；`maintenance` 只在执行维护命令时临时启动。
- 对外只有 80/443/443udp；PostgreSQL 与 Redis 不发布宿主端口。
- 健康/指标监听只发布到宿主回环：gateway `127.0.0.1:3306`、jobs `127.0.0.1:3305`，不加入公网反代。
- 管理后台路径 `/__aisys__/`；后台 API `/__aisys__/api/*`；OpenAI 兼容入口 `/v1/*`。
- 不用内置 Caddy 时，用 [Nginx](nginx/README.md) 替代；入口同一时间只能有一个监听 80/443。

## 2. 前置条件

- 服务器 4 核 8G 起步，系统盘 ≥ 60G；Debian 12/13 或 Ubuntu 22.04+，x86_64。详细要求与 Docker 安装见[主机初始化](host/README.md)。
- 公网 IP，安全组放行 `22`、`80`、`443`（TCP），可选 `443/udp`。
- 一个域名（示例 `<domain>`），A 记录指向服务器公网 IP。
- 本地构建机有 Go（版本以 `backend-go/go.work` / 各 `go.mod` 为准）、Node.js + pnpm；**严禁在服务器上编译 Go 或构建前端**。
- AI 上游需要出海时，先在服务器准备出站代理，见 [proxy/](proxy/README.md)；上游可直连时跳过。

## 3. 主机初始化

```sh
# 仓库根目录执行：上传脚本后以 root 运行（幂等；新机必做）
scp docker/single-server/host-init.sh <user>@<server>:/tmp/host-init.sh
ssh <user>@<server> 'sudo bash /tmp/host-init.sh'   # 已是 root 可去掉 sudo
```

脚本完成三项主机层治理：4G swap、防内存冻结 sysctl、journald 日志上限 500M。`deploy.sh` 每次发布都会自动自检（单项失败只告警，不阻塞发布）。

```sh
swapon --show
sysctl vm.min_free_kbytes vm.watermark_scale_factor vm.overcommit_memory
journalctl --disk-usage
```

完整说明、Docker 安装与防火墙配置见[主机初始化](host/README.md)。

## 5. 配置

### 5.1 `.env`

`.env` 由 compose `env_file` 注入 gateway/jobs/maintenance，同时提供 compose 变量插值。文件权限 `600`，只放在服务器与本地发布机的 `docker/single-server/.env`（gitignore），不要提交。

必填项（完整语义、建议项、已删除变量与模板见[配置参考](config/README.md)）：

| 变量 | 说明 |
| --- | --- |
| `POSTGRES_PASSWORD` / `REDIS_PASSWORD` | 中间件密码；进程启动时映射为 `PGPASSWORD` / 自动注入 Redis 客户端 |
| `JUHE_AI_POSTGRES_URL` | 主库连接串，全部子系统共用 |
| `JUHE_AI_REDIS_URL` / `JUHE_AI_REDIS_MODE` | 单节点或 Cluster 连接串 + 模式（`single`/`cluster`） |
| `JUHE_AI_REDIS_NAMESPACE` | 键空间根，生产固定 `prod` |
| `JUHE_AI_SECRET` | ≥32 位强随机；有加密数据后不可更换 |
| `JUHE_AI_ACCOUNT_HEALTH_INPUT_POSTGRES_URL` | J1 必须显式，不回退主库；运行日志索引连接串已随 2026-11-09 F1 下架删除 |
| `JUHE_AI_ALLOWED_ORIGINS` | 后台访问 Origin；生产为空或 `*` 会启动失败 |
| `JUHE_AI_ALLOW_PRIVATE_UPSTREAM_BASE_URLS` | 生产必须 `false`（SSRF 防线）：禁止账户 `base_url` 指向本机/内网/链路本地/CGNAT/保留地址；确需私网上游时用 `JUHE_AI_UPSTREAM_BASE_URL_PRIVATE_ALLOWLIST` 按 `scheme+IP+port` 精确放行 origin |
| `JUHE_AI_TRUST_PROXY` | `true`；否则来源 IP 全部变成反代容器地址 |
| `JUHE_AI_PROXY_IP_A` / `JUHE_AI_PROXY_IP_B` | 旧出海隧道 IP 钉死；compose `:?required` 引用，过渡保留 |
| `JUHE_AI_AUDIT_LOG_ENABLED` | 可选，默认 `true`；`false` 停写全部审计并隐藏管理菜单（retention 继续清理存量），集群无共享 `data/` 时必须为 `false` |

compose 对 gateway/jobs/maintenance 三服务固定 `NODE_ENV=production`。maintenance 消费 secret 的命令（`--migrate-account-capability-domain`、`--verify-account-capability-domain`、`--seed`）在 production 缺 `--secret`/`JUHE_AI_SECRET` 时 exit 2，不回落开发默认密钥；维护窗口命令仍应显式传 `--secret "$JUHE_AI_SECRET"`。

模板与完整说明见[配置参考 §4](config/README.md)。修改后先自检：

```sh
cd /opt/juhe-ai
docker compose --profile tool run --rm maintenance check-config --process all
```

### 5.1.1 Redis Cluster

Cluster 已支持：`JUHE_AI_REDIS_MODE=cluster`，`JUHE_AI_REDIS_URL` 用重复 `addr` 参数列节点，只支持 DB0。键形态固定 `juhe-ai:{<namespace>:<域>}:<key>`，域内多键操作同 slot。

部署要点、从旧三 URL 配置迁移的停写窗口、`FLUSHALL` 在 Cluster 下的语义，见[配置参考 §5](config/README.md)。

### 5.1.2 Cluster 模式的实际影响

- 客户端开销与单节点基本一致；随机键吞吐随 master 数扩展。
- `circuit`、`keymodel`、`hotquality` 三个热点域固定单 slot，无法随节点数拆分，需按节点监控并垂直扩容。
- 有 replica 时故障可自动恢复，但 Redis 复制是异步的，不能当持久事实库；`/health` 的 Ping 也不代表所有 slot 可用。

完整实测与运维边界见[配置参考 §5.3](config/README.md)。

### 5.2 Caddyfile

默认入口由 compose 内置 Caddy 提供；完整模板、换域名注意事项与外部 Caddy 见[配置参考 §6](config/README.md) 和 [HTTPS / 反向代理](https/README.md)。主流程只需确认：

- Caddy 自动 ACME 签发/续期，80 常驻 308 升级 HTTPS。
- `/v1/*` 必须保留 `flush_interval -1`（SSE 不缓冲）。
- 站点返回 `Strict-Transport-Security: max-age=31536000`（2026-11-06 安全基线）；刻意不加 `includeSubDomains`，避免影响同域其他未全程 HTTPS 的子域。换域名或改用外部入口时保留等价 HSTS 配置。
- 上游固定 `172.18.0.10:3000`，保持 HTTP/1.1；不要改成容器名或 h2c。
- 换域名时同步改 `Caddyfile` 与 `compose.yml` 中 caddy healthcheck 的 URL，否则 caddy 会一直 unhealthy。
- 需要 Nginx 时见 [Nginx 部署](nginx/README.md)；同一时间只能有一个入口占用 80/443。

### 5.3 权限

以下命令在 §7.1 上传完成后、启动容器前执行：

```sh
chmod 600 /opt/juhe-ai/.env
mkdir -p /opt/juhe-ai/data/app
chown -R 1000:1000 /opt/juhe-ai/data/app   # 容器以 UID/GID 1000 的 app 用户运行
```

`data/app` 的 chown 必须在旧容器停止后执行（首次部署无旧容器，直接执行即可）；否则 app 用户无权写 logs / audit-blob。

容器安全基线（2026-11-06，随 `compose.yml` 固化）：

- gateway/jobs/maintenance：非 root `app` 用户 + `read_only: true` + `cap_drop: [ALL]`；可写面只有 `data/app/{data,logs}` 与 `/tmp` tmpfs。
- caddy：`read_only: true` + `cap_drop: [ALL]` + `cap_add: [NET_BIND_SERVICE]`；可写面仅 `caddy_data` / `caddy_config` 卷与 `/tmp`。
- postgres/redis：只加 `no-new-privileges`，不裁剪 capability、不设只读根（官方镜像入口需要 root 修正数据目录属主后降权）。
- 请求体：`/v1/images/edits`、`/v1/audio/transcriptions|translations`（含裸形态）64 MiB 车道；管理面 JSON 256 KiB。gateway 主监听默认 `ReadTimeout` 10 分钟，上述大请求体路由在监听层延长到 30 分钟，最多 8 个并发（超出 503 + `Retry-After`）；低于约 36 KiB/s（64 MiB）的极慢上传仍会超时。原 `/v1/files` 512 MiB 车道随 2026-11-09 openai-compatible files 本地运行时退役删除。
- 镜像 digest 已固定（2026-11-06）：postgres/redis/caddy 与构建基础 alpine 均使用 `tag@sha256:…`；升级镜像必须同步改 tag 与 digest，并在发布窗口验证 pull 与健康检查，见 `docker/single-server/README.md` 安全基线节。

## 6. 本地构建

在仓库根目录（本地发布机）执行：

```sh
VERSION=$(git describe --tags --exact-match 2>/dev/null || echo dev-$(git rev-parse --short HEAD))
COMMIT=$(git rev-parse --short HEAD)
BUILD_TIME=$(date -u +%Y-%m-%dT%H:%M:%SZ)
mkdir -p docker/single-server/build/bin

for p in gateway jobs maintenance; do
  (cd backend-go/projects/$p && CGO_ENABLED=0 GOOS=linux GOARCH=amd64 \
    go build -trimpath \
    -ldflags "-s -w \
      -X github.com/huanminabc/juhe-ai/backend-go-platform/version.Version=$VERSION \
      -X github.com/huanminabc/juhe-ai/backend-go-platform/version.Commit=$COMMIT \
      -X github.com/huanminabc/juhe-ai/backend-go-platform/version.BuildTime=$BUILD_TIME" \
    -o ../../../docker/single-server/build/bin/juhe-ai-$p ./cmd/juhe-ai-$p)
done

(cd frontend && pnpm install --frozen-lockfile && pnpm build)
rm -rf docker/single-server/build/frontend-dist
cp -r frontend/dist docker/single-server/build/frontend-dist
```

校验（构建机可能不是 Linux，不要直接执行 linux/amd64 二进制）：

```sh
ls -l docker/single-server/build/bin/
ls docker/single-server/build/frontend-dist/index.html
# 上传后在服务器上可执行：/opt/juhe-ai/build/bin/juhe-ai-gateway --version
```

> 生产发布脚本 `deploy.sh` 会无条件重新编译并做 md5 三点校验；手工构建时必须保证工作树干净、前端产物与后端同批，避免旧前端被烤进新镜像。需要独立发布包（含 `start.sh`/`start.ps1` 直跑）时见[构建指南](构建指南.md)。

## 7. 首次部署（手动，逐条执行）

### 7.1 上传

```sh
# 在仓库根目录执行；<user>@<server> 替换为服务器 SSH 目标
ssh <user>@<server> 'mkdir -p /opt/juhe-ai/backup'
tar czf - -C docker/single-server \
  compose.yml Caddyfile Dockerfile.runtime verify-release.sh host-init.sh .env build \
  | ssh <user>@<server> 'tar xzf - -C /opt/juhe-ai && chmod 0755 /opt/juhe-ai/build/bin/* /opt/juhe-ai/verify-release.sh /opt/juhe-ai/host-init.sh'
```

首次部署前按[配置参考](config/README.md)填好 `.env`；`build/` 来自 §6。

> 后续更新只上传 `build/`（以及确需变更的 compose/Caddyfile），**不要再次覆盖服务器 `.env`**：服务器上的 `.env` 是运行事实，本地副本可能已过期。

### 7.2 组装镜像

```sh
cd /opt/juhe-ai
chmod 600 .env
docker compose --profile tool build    # 必须带 --profile tool，否则不会构建 maintenance 镜像
```

服务器只做镜像组装，不编译。国内网络下 `compose.yml` 的 `BASE_IMAGE` 已指向 `docker.m.daocloud.io` 并固定 digest；若 BuildKit 解析基础镜像 HEAD 502，先 `docker pull docker.m.daocloud.io/library/alpine:3.20@sha256:d9e853e87e55526f6b2917df91a2115c36dd7c696a35be12163d44e6e2a4b6bc` 预热再重试。

### 7.3 启动中间件

```sh
docker compose up -d postgres redis
docker compose ps          # 两者 healthy 后再继续
```

### 7.4 PostgreSQL 初始化

```sh
docker compose exec -T postgres psql -U juhe_ai -d juhe_ai \
  -c 'CREATE EXTENSION IF NOT EXISTS pg_stat_statements;' \
  -c "ALTER SYSTEM SET log_min_duration_statement='500ms';" \
  -c "ALTER SYSTEM SET log_line_prefix='%m [%p] app=%a ';" \
  -c "ALTER SYSTEM SET log_connections='on';" \
  -c "ALTER SYSTEM SET log_lock_waits='on';" \
  -c 'SELECT pg_reload_conf();' </dev/null
```

`shared_buffers=2GB`、`effective_cache_size=4GB`、`shared_preload_libraries=pg_stat_statements` 已在 compose `command` 中固化，不要删除。

### 7.5 初始化 schema / seed / 升级账本

全新空库也走 `upgrade`（它会执行 ensure-schema、seed 与全部迁移步骤，并把账本推进到当前 revision）：

```sh
cd /opt/juhe-ai
set -a && . ./.env && set +a
docker compose --profile tool run --rm maintenance upgrade \
  --dsn "$JUHE_AI_POSTGRES_URL" \
  --secret "$JUHE_AI_SECRET" \
  --stop-write-confirmed \
  --backup-confirmed </dev/null
```

- `--stop-write-confirmed` / `--backup-confirmed` 对全新库同样必填（语义：确认无写者、确认空库无需备份）。
- 执行完成后 stdout 会给出步骤报告与 postflight 结果；失败时退出码非 0，按报告修复后重跑（账本断点续跑）。
- 当前二进制 schema revision 为 `23`；`gateway/jobs` 启动时只读校验库 revision，落后会 fail-fast 并提示 `upgrade`。revision 18 为代理池加法批次（`proxy_pools`/`proxy_pool_members`/`account_proxy_leases`、`accounts.proxy_pool_id`、`proxy_profiles.pool_health_*`）；revision 19 为 API Key 安全策略批（`juhe_business.security_policies` 新表 + `api_keys.security_policy_id` 列 + `juhe_usage.usage_records` 的 `security_policy_applied`/`pii_hits_json` 两列；纯 DDL 空号，`maintenance upgrade` 加法相幂等执行，无数据步骤、无新增/变更 env，`--ensure-schema` 同批补种内置「默认安全策略」行）；revision 20 为 2026-11-07 跨协议映射退役批（单个 Destructive 步骤含三阶段：归一/删除非合规映射行、`DROP SCHEMA juhe_codex_context CASCADE`；因 `schema_migrations.revision` 主键不能同 revision 注册多条目），删除映射行与 schema 不可逆，升级窗口见 §9.4；revision 21 为安全策略防护次数写后缓存批（`security_policies.protection_count` 加法列，纯 DDL 空号，无新 env 与数据步骤）；revision 22 为 2026-11-09 高并发分组退役批（`retire-high-concurrency-groups`，Destructive：`groups` 全部行迁为 `personal`、16 键旧策略按 `JUHE_AI_CONCURRENCY_GLOBAL_MAX` 映射为两键、`group_authorization_settings` 覆盖列清为 `personal`/NULL、超级分组自身行按首成员重算；畸形行 `needs_review` 阻断，迁移窗口与盘点命令见 §9.4）；revision 23 为 2026-11-10 usage shard 目录退役批（`retire-usage-shard-catalog`，Destructive：按 FK 依赖顺序 `DROP TABLE` `juhe_usage.usage_record_shard_entries` / `usage_record_account_shards` / `usage_record_api_key_shards` / `usage_record_shards`；生产写入链路只写 `usage_records`，列表与清理直接读日分区，DROP 不可逆，执行前必须停写+可恢复备份）。
- `--ensure-schema --seed` 仍可单独跑（幂等加法），但它不推进升级账本；不要用它替代 `upgrade`。

## 9. 日常更新与升级

### 9.1 推荐：发布脚本

```sh
# 常规发布（无 schema/迁移变更）：构建 → 上传 → md5 校验 → build+up → healthy → 公网健康检查 → verify-release
bash docker/single-server/deploy.sh all

# 只发某个服务（仅限发布说明明确只影响单侧时）
bash docker/single-server/deploy.sh gateway
bash docker/single-server/deploy.sh jobs
bash docker/single-server/deploy.sh maintenance   # 只重建 CLI 镜像，不启动常驻进程
```

> `deploy.sh` 绑定**当前生产实例**：ssh 目标取 `docker/single-server/.env` 的 `JUHE_AI_DEPLOY_SERVER`，私钥路径 `.local/project-resources/prod/assets/ssh/...`、公网健康检查 `HEALTH_URL` 都写死在脚本里。部署到其他服务器时，先改这三处，或直接按 §9.3 / §9.4 手工执行。

`deploy.sh all` 内置：

- 服务器 compose 配置预检：`docker compose config -q` 用生产 Compose 版本校验 compose.yml/.env 插值（含 `extra_hosts` 映射形式），失败即中止且不改动容器；
- 无条件全量重编译（不信任旧 `build/`）；
- 前端漏发门禁（前端相对线上版本有变化时自动构建上传）；
- compose.yml / Caddyfile / Dockerfile.runtime 与远端 md5 同步；
- 发布前用新版 maintenance 跑 `upgrade --dry-run`，库落后/升级中断则中止并提示 `deploy.sh upgrade`；
- 发布后逐容器等 healthy、公网健康检查、`verify-release.sh`。

### 9.2 带 schema / 迁移的升级（停写窗口）

二进制与数据库 revision 不一致时必须先升级库，否则新版 gateway/jobs 启动 fail-fast：

```sh
# 本机执行；脚本会 build → 停 gateway/jobs → 要求输入 YES 确认已备份 → 容器内 upgrade → 拉起
bash docker/single-server/deploy.sh upgrade
```

窗口纪律：

- 备份必须在停写之后、升级之前完成并验证可读（见[备份与恢复](backup/README.md)）。
- 脚本的备份确认是交互式的；无人值守环境请先备份，再手动执行窗口步骤（§9.4）。
- 备份通常在每日 04:10（当前核心范围约 20–30s），发版只需避开该时刻前后几分钟；历史上整库 `pg_dump` 持表锁约 2 小时的限制已随 2026-11-05 备份范围收敛消失。
- 失败时 gateway/jobs 保持停止：修复后重跑 `deploy.sh upgrade`（账本断点续跑），或恢复备份后重试。
- 回滚注意：库 revision 高于旧二进制认识的值时，旧二进制会被启动门禁拒绝（当前 revision 23；revision 17 的 accounts vendor/driver CHECK 与清退不可逆，revision 18 的代理池表为加法变更，revision 19 的安全策略表列为加法变更且旧代码不读，revision 20 删除非合规映射行与 `juhe_codex_context` schema 不可逆，revision 21 的防护计数列为加法变更，revision 22 将 `groups` 行迁为 `personal` 并清空授权覆盖、不可逆，revision 23 删除 usage shard 目录四表、不可逆；回滚只能恢复升级前备份）。核心范围备份保留完整 schema 与账户/授权/配置，但不含升级前 usage/统计/日志历史，回滚后这些数据从零累积。
- 与版本升级解耦的一次性运维批次（数据回填、废弃索引/表清退、人工核对等）不在本文重复，按 `docs/待办与阻塞事项.md` 中当前发布窗口条目执行；执行前同样先停写并完成可恢复备份。

### 9.4 手工升级窗口（有 schema/迁移变更）

```sh
cd /opt/juhe-ai
set -a && . ./.env && set +a

# 0) 本机构建并上传新 build/（§6）；只传 build/ 与确需变更的配置，不要覆盖服务器 .env
docker compose --profile tool build    # 含新版 maintenance，升级必须用新镜像

docker exec juhe-ai-postgres pg_dump -U juhe_ai -Fc juhe_ai > "$DUMP"
docker exec -i juhe-ai-postgres pg_restore -l >/dev/null < "$DUMP" && echo backup-ok

# 3) 一次性清退 openai/hybrid/generic_http 账户（revision 17 之前的强制步骤）
#    dry-run 只读并冻结 manifest；人工核对 JSON 中的每表行数、日期范围与 ID 哈希后再 apply。
docker compose --profile tool run --rm maintenance \
  purge-unsupported-vendor-accounts --dry-run \
  --manifest-out /app/backend/data/purge-unsupported-vendors-$(date +%Y%m%d-%H%M).json \

  purge-unsupported-vendor-accounts \

  --dsn "$JUHE_AI_POSTGRES_URL" </dev/null
#    清退会删除目标账户及其连接/映射/授权实例/历史 usage/audit/stats；不可逆。

# 3.5) revision 22 分组策略迁移盘点（只读；dry-run 只写 manifest）
#      --global-max 必须与旧 gateway 实际运行的 JUHE_AI_CONCURRENCY_GLOBAL_MAX（1-50000）一致；
#      未覆盖时用默认 5000。upgrade 步骤自身读取同一 env（缺失/非法/越界回落 5000）。
docker compose --profile tool run --rm maintenance \
  migrate-group-policy --dry-run \
  --manifest-out /app/backend/data/group-policy-$(date +%Y%m%d-%H%M).json \
  --global-max "${JUHE_AI_CONCURRENCY_GLOBAL_MAX:-5000}" \
  --dsn "$JUHE_AI_POSTGRES_URL" </dev/null
#    人工核对 manifest 的 groups / groupAuthorizationSettings / highConcurrency* /
#    superGroups / needsReview / queueOverflow / imageLane。needsReview>0 必须先人工
#    修正（独立 migrate-group-policy apply 以退出码 3 零写入阻断；upgrade 步骤
#    以 exit 1 停账本于 running）；queueOverflow 行迁移后由排队变为 429，
#    imageLane 行迁移后图片按账户硬并发。空超级分组会自动收敛为 personal + NULL，
#    不进入 needsReview。

# 3.6) revision 23 usage shard 目录四表退役（停写窗口内执行；DROP 不可逆）
#     upgrade 的 retire-usage-shard-catalog 步骤会按 FK 依赖顺序删除
#     juhe_usage.usage_record_shard_entries / usage_record_account_shards /
#     usage_record_api_key_shards / usage_record_shards。生产写入链路只写
#     usage_records，四表预期为空或仅有历史造数残留；执行前用 psql 记录四表
#     count(*) 到发布记录，并确认已完成可恢复备份。回滚只能从备份整体恢复。

# 4) 只读预演：落后库（dbRevision < 二进制）返回 blocked/3 属预期，

  --dsn "$JUHE_AI_POSTGRES_URL" --secret "$JUHE_AI_SECRET" \

  drop-retired-account-name-search-index \
  --dsn "$JUHE_AI_POSTGRES_URL" --stop-write-confirmed --backup-confirmed </dev/null

#    存量库上不要在 `up -d` 之后执行 `--ensure-schema`：EnsureAll 仍含破坏性

```

### 9.5 发布顺序约束

- gateway 与 jobs 必须同批发布（共享 schema 读取面与 usage 定价目录契约），除非发布说明明确只影响单侧。
- **并发槽 ZSET 模型（2026-11-13，BUG-0361）**：gateway 写/读 Redis `:slots` ZSET，jobs 投影读同一 ZSET；两侧必须同批发布、同批回滚，禁止新旧二进制混跑（旧 gateway 只读旧 HASH `total`，新代码不维护；混跑会各自少计并发）。回滚窗口内并发计数从头累积，短期可能放宽硬并发，属已知边界。
- 涉及 schema 的改动：先升级库（`upgrade`）再启动新版进程；顺序颠倒会让新版进程 fail-fast 重启循环。
- 2026-11-05 退役批次顺序固定：停写 → 核心范围备份并验证 → purge dry-run/核对 manifest → purge apply → `upgrade` 到 revision 17 → T119 名称搜索派生层退役 → 启动新版 gateway/jobs → `verify-release.sh`。若 purge 未完成而先 `upgrade`，CHECK 会因遗留空 vendor/generic 账户失败。
- T119 退役命令必须在 `upgrade` 之后、`docker compose up -d gateway jobs` 之前执行：新版 gateway/jobs 已不再读写派生表，先拉起会让旧表与新二进制并存并放大「表已删、进程仍写」的误判。DROP 后回滚只能恢复窗口备份 + 回退旧镜像，只换二进制不可行。
- 维护命令一律加 `</dev/null`（避免吞脚本 stdin）；管道接维护命令时用 `set -o pipefail`（否则退出码被 `tail`/`grep` 掩盖）。

### 9.6 AI 账户名称搜索去索引化（T119 / BUG-0349）

账户名称搜索自 2026-11-03 起改为作用域内直读 `accounts.name`，不再维护派生词项层；本命令只清退生产存量对象，新库由 `--ensure-schema` 直接建出无索引层形态，无需执行。

- 清退对象：`juhe_business.account_name_search_terms`、`account_name_search_documents`、`account_list_availability_projection_search_terms` 三张表；`account_list_availability_projection_index.search_index_complete` 列；残留触发器函数 `account_list_availability_name_search_dirty_trigger()`。
- 执行方式：单事务、默认 RESTRICT（不级联）、`lock_timeout=2s`、幂等可重跑；正式执行强制 `--stop-write-confirmed` + `--backup-confirmed`（缺一 exit 2，不开库）。`--dry-run` 只读，输出目标库与各对象存在状态，不要求两个确认。
- 窗口内顺序：必须在 §9.4 第 6 步完成（停写窗口内、`upgrade` 之后、拉起 gateway/jobs 之前）；第 2 步的备份是本操作的回滚恢复点（核心范围，保留账户/授权/配置；不含升级前 usage/统计历史）。
- 验证：拉起后管理面对话账户列表搜 `k40`（前缀）、`林`（中段）、`GROK`（ASCII 大小写）、`%`/`_`/`\`（字面）均符合预期；再跑一次 `--dry-run` 应全部为 absent 且重跑幂等。

## 10. 备份与恢复

- 当前生产由备份机每日 04:10 定时拉取 `pg_dump`，保留最近 7 份；只备份**核心业务数据**（账户、授权、API Key、分组、路由、供应商/模型/系统配置），用量/统计/日志/测试/运行态表仅保留 DDL。
- 核心范围备份实测约 2.2MB、20–30s，发版只需避开 04:10 前后几分钟；备份后必须 `pg_restore -l` 验证可读，并定期做隔离恢复演练。
- 恢复在停写窗口内执行：停 gateway/jobs → 重建库 → `pg_restore` → 重建电路索引 → 拉起 → 按 §8 验证；恢复后历史用量/统计为空属预期。

完整策略、手工命令、不备份内容与迁移关系见[备份与恢复](backup/README.md)。

| 有容器 unhealthy | `docker compose logs <service> --tail=200` | 按日志根因；gateway 首次启动等租约约 1 分钟属正常 |
| 公网 502 | 反代日志、gateway 状态、上游地址 | 恢复 gateway；Caddy 固定 `172.18.0.10:3000`，Nginx 见 [Nginx 部署](nginx/README.md) |
| health 返回 503 | `curl 127.0.0.1:3306/health`、PG/Redis 连接 | 连接串、密码、中间件 healthy |
| 统计/用量恒 0 | gateway 日志是否有 `usage_record_delivery_failed` / `usage_record_delivery_unavailable`、PG `juhe_usage.usage_records` 是否有新行 | 检查 PG 连接与 gateway 启动日志；用量自 2026-11-09 T188 起直投 PG，不再有 spool 目录 |
| 新版启动提示「尚未升级/升级未完成」 | `maintenance upgrade --dry-run` | 走 §9.2 升级 |
| 后台登录 401/跨域失败 | `ALLOWED_ORIGINS`、`COOKIE_SECURE`、`TRUST_PROXY` | 改成实际访问 Origin；HTTPS 下 cookie secure |

完整排障表（入口、容器、PG/Redis、业务链路、监控）见[排障速查](troubleshooting/README.md)。

## 13. 迁移到新服务器

- 搬：`/opt/juhe-ai/{compose.yml,Caddyfile,Dockerfile.runtime,verify-release.sh,host-init.sh,.env}` + `/opt/juhe-ai/data/` 全部。
- 不搬：`build/`、Docker 镜像、Caddy 命名卷。
- 整体搬 `data/` 时无需重跑 schema；只恢复 PG dump 时按 §7 完整初始化，并在 gateway 首次启动前重建电路索引。
- DNS 切流放在最后；旧机保留一个观察期。

完整步骤、验证与回退见[迁移到新服务器](migration/README.md)。

## 14. 安全清单

- `.env` 权限 600，只在服务器与本地发布机；不提交、不粘贴到聊天/文档/日志。
- `JUHE_AI_SECRET` ≥32 位随机并离线多处留档；有加密数据后不可更换。
- 生产保持验证码开启（不要保留 `JUHE_AI_AUTH_CAPTCHA_DISABLED`）。
- PG/Redis 不发布宿主端口；metrics/pprof 仅回环。
- `JUHE_AI_ALLOWED_ORIGINS` 禁止 `*`；`COOKIE_SECURE=true`。
- 建议 SSH 仅密钥登录并启用 fail2ban。
- 发布脚本使用的 `docker/single-server/.env`（本地）含 `JUHE_AI_DEPLOY_SERVER`；首次部署时会同时填入生产密钥用于上传，因此本地副本同样按 600 保管、永不提交。日常发布可只保留部署变量，但不得把服务器 `.env` 复制到其他位置。

## 附录：当前运行契约速查

- 进程工作目录：gateway/jobs/maintenance 容器必须 `working_dir: /app/backend`；`data/`、`logs/` 相对 cwd 解析，否则写入容器临时层，容器重建即丢。
- 用量投递：gateway 直投 PG `juhe_usage.usage_records`（共享 `usagewriter`，有界异步 + 定价冻结）；无文件 spool 交接，gateway 与 jobs 的 `data/` 无需同源。
- 非 root：容器以 UID/GID 1000 `app` 运行，`data/app` 属主必须匹配。
- 客户端交接：非终态失败（锁死 hold、预算耗尽、临时隔离等）先提交 200 传输头再断开，客户端按网络错误重试；Caddy/Nginx 需保持 HTTP/1.1 upstream、SSE 不缓冲。
- schema 门禁：`gateway/jobs` 启动比对库 revision，落后 fail-fast；升级只走 `maintenance upgrade` / `deploy.sh upgrade`。
- 当前 schema revision：`23`（以 `backend-go/shared/contracts` 常量为准；revision 18 代理池加法、19 安全策略 DDL 空号、20 跨协议映射退役、21 安全策略防护计数 DDL 空号、22 高并发分组退役、23 usage shard 目录四表退役——升级后删除非合规映射行与 `juhe_codex_context` schema，并 DROP usage shard 目录四表；旧 `.env` 中 `JUHE_AI_CODEX_CONTEXT_ROOT` 必须同批删除，`check-config` 对未知变量 exit 2）。
