# 部署指南（国内单机 Docker，唯一生产形态）

> 本文是当前唯一生产形态的完整手动部署手册：一台国内云服务器 + Docker Compose（PostgreSQL + Redis + gateway/jobs/maintenance + Caddy），可直接照做。
>
> 配置契约的权威来源是仓库 [`docker/single-server/README.md`](../../docker/single-server/README.md)（compose / Caddyfile / `.env` / 构建与发布细节）；本文是面向部署者的操作手册，已包含从零部署所需的全部当前步骤，遇到该 README 中的历史迁移记录时以本文与 `docs/待办与阻塞事项.md` 为准。服务器 IP、域名解析值、密钥等实例事实只在私有目录 `.local/project-resources/prod/` 留档，本文使用占位符。
>
> 已退役、不要使用的形态：K3s/K8s、Harbor/Jenkins 发布链、家庭宽带反向代理、Edge/WireGuard 回源、macOS/Windows 本机部署、SQLite/内存存储模式、Node 后端。仓库内不再保留这些形态的部署文档。

## 0. 从零部署顺序（速查）

1. 服务器：执行 §3 `host-init.sh`，安装 Docker、放行 80/443、配好域名 A 记录。
2. 本地：§6 编译三个 Go 二进制 + 前端 `dist`；§5.1 填 `.env`；§5.2 按域名改 `Caddyfile`（并改 compose 的 caddy healthcheck）。
3. 服务器：§7.1 上传 → §5.3 权限 → §7.2 `--profile tool build` → §7.3 起 PG/Redis → §7.4 PG 初始化 → §7.5 `maintenance upgrade` → §7.6 chown + J3b 索引 → §7.7 `up -d`。
4. §8 验证（容器 healthy、公网健康、登录、一次真实 `/v1` 调用）。
5. 日常发布与升级按 §9；备份按 §10。

## 1. 部署形态

```
公网 :80 / :443 / :443/udp
        │
        ▼
   Caddy（juhe-ai-caddy，自动 HTTPS/ACME，80 → 443）
     ├─ /              → 301 /__aisys__/
     ├─ /v1/*          → gateway:3000（OpenAI 兼容入口，SSE 不缓冲）
     └─ 其余            → gateway:3000（管理 SPA + /__aisys__/api）
        │
   gateway（juhe-ai-go-gateway，固定容器 IP 172.18.0.10）
     ├─ postgres:5432（juhe-ai-postgres，单库 juhe_ai，多 schema）
     └─ redis:6379（juhe-ai-redis，DB0；cache/state/J3b 等按 {namespace:域} 键空间隔离）
   jobs（juhe-ai-go-jobs）─ 同 PG/Redis
   maintenance（一次性 CLI，compose profile=tool）
```

- 五个常驻容器：`postgres`、`redis`、`gateway`、`jobs`、`caddy`；`maintenance` 只在执行维护命令时临时启动。
- 对外只有 80/443/443udp；PostgreSQL 与 Redis 不发布宿主端口。
- 健康/指标监听只发布到宿主回环：gateway `127.0.0.1:3306`、jobs `127.0.0.1:3305`，不加入公网反代。
- 管理后台路径 `/__aisys__/`；后台 API `/__aisys__/api/*`；OpenAI 兼容入口 `/v1/*`。

## 2. 前置条件

服务器：

- 4 核 8G 起步（本项目生产实测规格），系统盘建议 ≥ 60G（PG 数据 + 备份 + 日志）。
- Debian 12/13 或 Ubuntu 22.04+，x86_64。
- 公网 IP，安全组/防火墙放行：`22`（SSH）、`80`、`443`（TCP）、`443/udp`（HTTP/3，可选但建议）。
- 已安装 Docker Engine 24+ 与 Docker Compose v2（`docker compose version` 可用）。未安装时 Debian/Ubuntu 可用官方脚本 `curl -fsSL https://get.docker.com | sh && systemctl enable --now docker`；国内网络拉取失败时改用云厂商镜像源或 Docker 官方 apt 仓库。
- 能访问 Docker Hub；国内网络需配镜像加速（否则 `postgres:18-alpine` / `redis:7.4-alpine` / `caddy:2-alpine` 拉取会超时）。

域名与 DNS：

- 一个域名（示例 `<domain>`），A 记录指向服务器公网 IP；Caddy 自动申请/续期证书。
- 首次验证可先用服务器 IP + 仅 80 端口（需要单独改 Caddyfile 与 compose 的 caddy healthcheck，不属于本文标准流程）；正式入口必须 HTTPS，标准流程按域名配置。

本地构建机：

- Go（版本以 `backend-go/go.work` / 各 `go.mod` 为准）、Node.js + pnpm。
- 可在 Windows / macOS / Linux；**严禁在服务器上编译 Go 或构建前端**（4C8G 机器会被构建拖死）。

上游网络：

- AI 上游需要出海时，先在服务器准备出站代理（sing-box 或常驻隧道），见 [proxy/](proxy/README.md)。没有代理且上游可直连时可跳过。

## 3. 主机初始化

```sh
# 在仓库根目录执行：上传脚本后以 root 运行（幂等；新机必做）
scp docker/single-server/host-init.sh <user>@<server>:/tmp/host-init.sh
ssh <user>@<server> 'sudo bash /tmp/host-init.sh'   # 已是 root 可去掉 sudo
```

脚本完成三项主机层治理：

1. 4G swap（`/swapfile`，fstab 持久，`vm.swappiness=10`）；
2. 防内存冻结 sysctl：`vm.min_free_kbytes=262144`、`vm.watermark_scale_factor=125`、`vm.overcommit_memory=1`，写入 `/etc/sysctl.d/99-juhe-ai.conf`；
3. journald 日志上限 500M。

每次 `deploy.sh` 发布都会自动自检这三项（单项失败只告警，不阻塞发布）。新机可手工核对：

```sh
swapon --show
sysctl vm.min_free_kbytes vm.watermark_scale_factor vm.overcommit_memory
journalctl --disk-usage
```

## 5. 配置

### 5.1 `.env`

`.env` 由 compose `env_file` 注入 gateway/jobs/maintenance，同时提供 compose 变量插值。文件权限 `600`，只放在服务器与本地发布机的 `docker/single-server/.env`（gitignore），不要提交。

必填（缺失会在 `docker compose config` 或进程启动时失败）：

| 变量 | 说明 |
| --- | --- |
| `POSTGRES_PASSWORD` | PG `juhe_ai` 用户密码；进程启动时映射为 `PGPASSWORD`，连接串可不再重复写密码 |
| `REDIS_PASSWORD` | Redis 密码；Redis 客户端自动注入，连接串可不再重复写密码 |
| `JUHE_AI_POSTGRES_URL` | `postgres://juhe_ai@postgres:5432/juhe_ai`；gateway/jobs/maintenance 及全部子系统共用这一个主库连接串 |
| `JUHE_AI_REDIS_URL` | 单节点 `redis://redis:6379`；Cluster 用 `redis://<node1>:6379?addr=<node2>:6379&addr=<node3>:6379` |
| `JUHE_AI_REDIS_MODE` | `single`（缺省）或 `cluster` |
| `JUHE_AI_REDIS_NAMESPACE` | 键空间根，生产固定 `prod`，必填非空 |
| `JUHE_AI_SECRET` | ≥32 位强随机；凭据/内建 Key 加密封套，有数据后不可更换 |
| `JUHE_AI_RUNTIME_LOG_POSTGRES_URL` | 运行日志索引连接串；**必须显式，不回退主库**（保留独立库隔离能力） |
| `JUHE_AI_ACCOUNT_HEALTH_INPUT_POSTGRES_URL` | jobs 的 J1 账户健康 PG 输入；**必须显式，不回退主库** |
| `JUHE_AI_ALLOWED_ORIGINS` | 后台访问 Origin，逗号分隔，如 `https://<domain>`；生产环境为空或 `*` 都会启动失败 |
| `JUHE_AI_TRUST_PROXY` | `true`；缺失时默认 false，所有请求的来源 IP 都会变成 Caddy 容器地址，来源限流/封禁/调度避让全部失真 |
| `JUHE_AI_PROXY_IP_A` / `JUHE_AI_PROXY_IP_B` | 旧出海隧道域名 `data./egress.aijh.huanmin.top` 的 IP 钉死；**过渡保留**，生产 `proxy_profiles.host` 核对完成后再删除 |

建议显式配置：

| 变量 | 说明 |
| --- | --- |
| `JUHE_AI_COOKIE_SECURE` | 生产默认即为 `true`；显式写出便于审计，也避免日后直跑时遗漏 |
| `JUHE_AI_ACCOUNT_BALANCE_JOBS_HTTP_SECRET` | J2 手动触发端点密钥，≥32 字符；`JUHE_AI_SECRET` 已 ≥32 时可省略 |
| `JUHE_AI_LOG_MAX_FILE_MB` / `JUHE_AI_LOG_MAX_FILES` / `JUHE_AI_LOG_RETENTION_DAYS` | 文件日志轮转（默认 100MB / 500 个 / 30 天） |
| `JUHE_AI_AUDIT_LOG_SUCCESS_HOT_RETENTION_HOURS` | 成功正文热保留窗口（默认 1 小时）；成功正文长期保留 3 天且恒全量采样 |

注意：

- **一个 Redis 就够**：cache/state/J3b/限流/会话等域通过 `juhe-ai:{<namespace>:<域>}:...` 键前缀隔离，不再需要多逻辑库。单节点只支持 DB0；配置 DB1/DB2 会启动失败。
- **Cluster 已支持**：`JUHE_AI_REDIS_MODE=cluster` + `JUHE_AI_REDIS_URL` 用重复 `addr` 参数列节点。Cluster 只支持 DB0；每个域一个 hash tag，域内多键 Lua/批量读同 slot，域间分布到不同 slot。
- **已知容量边界**：`circuit`（账户电路）、`keymodel`（Key 模型运行态）、`hotquality`（短窗口热质量）三个热点域内部有全局索引/多键原子脚本，只能落单个 slot，无法再拆；其他域按域分布。热点域压力靠垂直扩容，不是集群能解决的。
- PG 子系统 URL 已收口：审计/操作日志/J3b/J2/J3a/账户健康 store 等不再有独立连接串，统一主库。需要独立库隔离的只有 `RUNTIME_LOG` 与 `ACCOUNT_HEALTH_INPUT`，两者必须显式配置且不回退。
- `application_name` 不再写进连接串：三个进程启动时由 `pgcfg.PrepareProcessEnv` 设置 `PGAPPNAME`，慢 SQL 与 `pg_stat_activity` 仍可区分来源。
- maintenance 的 `--apply-j3a-proxy-latency-postgres` / `--apply-j3b-model-check-postgres` / `--apply-account-balance-postgres` / `--postgres-schema-snapshot` 全部改用 `--dsn "$JUHE_AI_POSTGRES_URL"`，不再读取 `JUHE_AI_MAINTENANCE_*` / `JUHE_AI_SCHEMA_SNAPSHOT_POSTGRES_URL`。
- SQLite/内存模式已退役：`JUHE_AI_RUNTIME_MODE`、`JUHE_AI_DATABASE_DRIVER`、`JUHE_AI_CACHE_DRIVER`、`JUHE_AI_RUNTIME_STATE_DRIVER`、全部 `*_DATABASE_PATH`、`JUHE_AI_USAGE_SHARD_*`、`JUHE_AI_CODEX_CONTEXT_STATE_SHARD_*`、`*_STORE` 等都不要再写；残留只会产生未知变量 WARN。
- 本次硬切删除的配置（不得回填）：`JUHE_AI_REDIS_CACHE_URL`、`JUHE_AI_REDIS_STATE_URL`、`JUHE_AI_J3B_CIRCUIT_REDIS_URL`、`JUHE_AI_J3B_CIRCUIT_REDIS_NAMESPACE`、`JUHE_AI_BUSINESS_POSTGRES_URL`、`JUHE_AI_AUDIT_LOG_POSTGRES_URL`、`JUHE_AI_OPERATION_LOG_POSTGRES_URL`、`JUHE_AI_J3B_POSTGRES_URL`、`JUHE_AI_ACCOUNT_HEALTH_POSTGRES_URL`、`JUHE_AI_ACCOUNT_BALANCE_POSTGRES_URL`、`JUHE_AI_PROXY_LATENCY_POSTGRES_URL`、`JUHE_AI_MAINTENANCE_*_POSTGRES_URL`、`JUHE_AI_SCHEMA_SNAPSHOT_POSTGRES_URL`、`JUHE_AI_ACCOUNT_HEALTH_JOBS_OUTCOME_POSTGRES_URL`、`JUHE_AI_USAGE_SPOOL_DIR`（旧名）、`JUHE_AI_COOKIE_SAME_SITE`、`JUHE_AI_BUSINESS_OWNER`、`JUHE_AI_PROCESS_ROLE`、`JUHE_AI_J3B_OWNER`、`JUHE_AI_MODEL_CHECK_ENABLED`、`JUHE_AI_ACCOUNT_BALANCE_STORE`、`JUHE_AI_PROXY_LATENCY_STORE`、`JUHE_AI_ACCOUNT_HEALTH_INPUT_SOURCE`、`JUHE_AI_GATEWAY_TIMING_DETAIL_SAMPLE_PERMILLE`、`JUHE_AI_AUDIT_LOG_SUCCESS_SAMPLE_RATE`。
- 系统指标/表监控已下线：`JUHE_AI_GO_RUNTIME_METRICS_*`、`JUHE_AI_TABLE_MONITOR_*`、gateway 侧 `JUHE_AI_JOBS_HEALTH_LISTEN_ADDRESS` 不要再写。
- AI 问答已退役：`JUHE_AI_CHAT_*` 不要再写。
- 配置自检：`docker compose --profile tool run --rm maintenance check-config --process all`（`.env` 已由 compose 注入容器，容器内没有 `.env` 文件，不要传 `--env-file`；发版前核对必填/别名/未知变量）。

`.env` 模板（把 `<...>` 替换为真实值；完整模板见 `docker/single-server/.env.example`）：


### 5.1.1 Redis Cluster 与本次键空间迁移

Cluster 部署要点：

- 三个（或更多）master，建议 3 master + 3 replica；客户端经 `JUHE_AI_REDIS_URL` 的重复 `addr` 参数发现拓扑，故障转移由 Redis Cluster 负责。
- `JUHE_AI_REDIS_MODE=cluster`，URL 不能带 DB 路径（只支持 DB0）。
- 键形态固定 `juhe-ai:{<namespace>:<域>}:<key>`；同一域内多键操作同 slot。域清单：`circuit`、`j3b`、`keymodel`、`hotquality`、`clientip`、`session`、`runtimecache`、`ratelimit`、`callertier`、`quota`、`obs`、`routestate`、`proxyhealth`、`inval`、`realtime`、`speedfirst`、`oauth`、`authstate`。
- 不支持把同一份数据同时跑在 single 与 cluster 之间热切：键布局与 DB0 假设不同，必须停写迁移。

从旧三 URL 配置迁移（一次性停写窗口）：

1. 停 gateway/jobs；备份 PG 并确认可恢复。
2. 核对代理档案 `proxy_profiles.host` 是否引用旧隧道域名（只读）。
3. 清空旧 Redis（管理员会话、限流窗口、client-ip、会话亲和、Key 模型瞬态、电路运行态都会清零）：single 用 `FLUSHALL`；cluster 必须用 `redis-cli --cluster call <seed>:<port> FLUSHALL` 对每个 master 执行（单节点 FLUSHALL 只清当前节点），并逐个复核 `DBSIZE=0`。
4. 按新契约改 `.env`（删除 3 个 Redis URL、J3b namespace 与全部已删 PG URL）。
5. 发布新二进制；`docker compose --profile tool run --rm maintenance --ensure-schema --dsn "$JUHE_AI_POSTGRES_URL"`（本次无 schema 变更）。
6. 重建电路索引（gateway 一次性 flag）：`docker compose run --rm --entrypoint /app/backend/juhe-ai-gateway gateway -init-account-circuit-runtime-index`；由 PG 中的权威派发版本回填 Redis 索引，完成后进程自行退出。
7. 启动 gateway/jobs，验证 `/health`、`/v1` 流式请求与 `usage_records` 增长。

回滚只能使用旧二进制 + 旧配置并重新初始化旧键空间；不存在单/集群双读兼容路径。

本地/联调验证可用 Docker 起三主集群（无密码，仅供测试）：

```sh
for p in 7001 7002 7003; do
  docker run -d --name juhe-ai-redis-cluster-$p -p $p:$p -p 1$p:1$p \
    redis:7.4-alpine redis-server --port $p --cluster-enabled yes \
    --cluster-config-file nodes.conf --cluster-node-timeout 5000 \
    --cluster-announce-ip <宿主机IP> --cluster-announce-port $p --cluster-announce-bus-port 1$p \
    --appendonly no --save "" --dir /data
done
docker exec juhe-ai-redis-cluster-7001 redis-cli --cluster create   <宿主机IP>:7001 <宿主机IP>:7002 <宿主机IP>:7003 --cluster-yes
```

真实集群回归：`JUHE_AI_TEST_REDIS_CLUSTER_ADDRS=<host>:7001,<host>:7002,<host>:7003 go test ./rediscfg -run TestRealClusterRoundTrip`；节点启用密码时另设 `JUHE_AI_TEST_REDIS_CLUSTER_PASSWORD`（显式 opt-in，未设置则 SKIP；SKIP 不作验证证据）。

### 5.1.2 Cluster 模式对业务的实际影响（2026-11 dev 实测）

功能面：

- 所有键都带 `{<namespace>:<域>}` hash tag，域内多键 Lua/MGET/SCAN 同 slot；dev 用 3 master + 3 replica、`requirepass` 集群跑通 gateway/jobs 全链路、管理面接口与 `/v1` SSE。
- 单节点与集群的客户端开销基本一致（本机到 dev 的 SET+GET 基准：single 4.7–5.0ms/op，cluster 4.8–4.9ms/op，差异在噪声内）；随机键吞吐集群可随 master 数横向扩展（dev 3 master `redis-benchmark SET`：43.6k → 79.7k ops/s）。
- **热点域不随节点数扩展**：`circuit`、`keymodel`、`hotquality` 必须单 slot，吞吐/内存上限就是单个 master。按生产 namespace `prod` + 3 master 默认区间计算：`keymodel` 落 master1，`hotquality` 与 `circuit` 同时落 master2，`ratelimit/authstate/quota` 等落 master3。master2 是明确的热点节点，需单独监控与垂直扩容；若要重新分布，只能在迁移前更换 namespace（键全部重建），不能在线改。
- 连接串只列一个可达 seed 也能发现拓扑；但把不可达节点排在第一位会让首次连接多等约 5s（dev 实测），生产按“先列当前存活节点”的顺序写 `addr`。

故障与运维：

- 有 replica 时，master 故障后该 master 负责的 slot 会短暂报连接错误，随后 replica 提升、客户端自动刷新拓扑恢复。工厂已把 Cluster 拨号收紧为 1s、读写 2s、最多 1 次重试（默认 go-redis 是 5s×3 次）：dev 实测单客户端首错从默认 12s 提前到 4s、总错误窗口从 22s 缩到 11s，应用层只出现 1 个 500 后恢复 200。没有 replica 时这些 slot 直到节点恢复都不可用，且无数据副本。
- Redis 复制是异步的：故障瞬间未复制的写入可能丢失，不能把 Redis 当持久事实库（与现有设计一致）。
- **`FLUSHALL` 在 Cluster 下只清当前节点**（dev 实测：本地 FLUSHALL 后仅该节点 DBSIZE 归零，其余 master 不变）。迁移清库必须用 `redis-cli --cluster call <seed>:<port> FLUSHALL`（带认证时加 `-a`），并对每个 master 复核 `DBSIZE=0`。
- 每个 master 独立 `maxmemory`：集群总容量是各节点之和，但热点域只能吃到单节点上限；`noeviction` 下热点节点先写失败。
- `/health` 的 Redis Ping 只证明“至少一个节点可达”，不代表所有 slot 可用；生产监控必须按节点抓取（redis_exporter cluster 模式）并告警单节点下线/槽位缺失。
- 新增多键命令/脚本必须继续使用 `rediscfg` 的域命名空间与 hash tag；跨域多键操作在 Cluster 下会直接 CROSSSLOT，代码评审需拦截。

### 5.2 Caddyfile

仓库 `docker/single-server/Caddyfile` 模板：

```caddy
<domain> {
	encode zstd gzip
	redir / /__aisys__/ permanent

	reverse_proxy /v1/* 172.18.0.10:3000 {
		flush_interval -1
	}
	reverse_proxy 172.18.0.10:3000
}
```

- `<domain>` 替换为你的域名；Caddy 自动 ACME 签发/续期，80 常驻 308 升级 HTTPS。
- `/v1/*` 必须保留 `flush_interval -1`（SSE 不缓冲）。
- 上游固定 `172.18.0.10:3000`（compose 固定 IP），不要改成容器名，避免 Docker DNS 偶发失败导致 502。
- 若同机还有其他站点（共享 Caddyfile），保留其 server 块；本项目生产 Caddyfile 含同机公益站块，部署纯本项目时可删除。
- **换域名时必须同步改两处**：`Caddyfile` 的站点地址，以及 `compose.yml` 中 caddy healthcheck 的 URL（当前模板写死 `https://aijh.huanmin.top/__aisys__/health`）。healthcheck 不随 Caddyfile 变化，漏改会让 caddy 一直 unhealthy（流量仍正常）。
- **Caddy → gateway 必须保持 HTTP/1.1 upstream**（默认即是）：客户端交接依赖 Hijack 先提交 200 头再断开；不要给 gateway 配 `transport http { versions h2c }`，否则交接退化为 503。

## 9. 日常更新与升级

### 9.1 推荐：发布脚本

```sh

bash docker/single-server/deploy.sh all

# 只发某个服务（仅限发布说明明确只影响单侧时）
bash docker/single-server/deploy.sh gateway
bash docker/single-server/deploy.sh jobs
bash docker/single-server/deploy.sh maintenance   # 只重建 CLI 镜像，不启动常驻进程
```

> `deploy.sh` 绑定**当前生产实例**：ssh 目标取 `docker/single-server/.env` 的 `JUHE_AI_DEPLOY_SERVER`，私钥路径 `.local/project-resources/prod/assets/ssh/...`、公网健康检查 `HEALTH_URL=https://aijh.huanmin.top/__aisys__/health` 都写死在脚本里。部署到其他服务器时，先改这三处，或直接按 §9.3 / §9.4 手工执行。

`deploy.sh all` 内置：

- 无条件全量重编译（不信任旧 `build/`）；
- 前端漏发门禁（前端相对线上版本有变化时自动构建上传）；
- compose.yml / Caddyfile / Dockerfile.runtime 与远端 md5 同步；
- 发布前用新版 maintenance 跑 `upgrade --dry-run`，库落后/升级中断则中止并提示 `deploy.sh upgrade`；
- 发布后逐容器等 healthy、公网健康检查、`verify-release.sh`。

### 9.2 带 schema / 迁移的升级（停写窗口）

二进制与数据库 revision 不一致时必须先升级库，否则新版 gateway/jobs 启动 fail-fast：

```sh
# 本机执行；脚本会 build → 停 gateway/jobs → 要求输入 YES 确认已备份 → 容器内 upgrade → 拉起
bash docker/single-server/deploy.sh upgrade
```

窗口纪律：

- 备份必须在停写之后、升级之前完成并验证可读（见 §10）。
- 脚本的备份确认是交互式的；无人值守环境请先备份，再手动执行窗口步骤（§9.4）。
- 避开每日 04:00–07:00 的自动备份窗口发版/重启容器（PG 整库读快照会持表锁约 2 小时）。
- 失败时 gateway/jobs 保持停止：修复后重跑 `deploy.sh upgrade`（账本断点续跑），或恢复备份后重试。
- 回滚注意：库 revision 高于旧二进制认识的值时，旧二进制会被启动门禁拒绝（当前 revision 17；本次 revision 增加 accounts vendor/driver 一致性 CHECK 且清退不可逆，回滚只能恢复升级前整库备份）。
- 与版本升级解耦的一次性运维批次（数据回填、废弃索引/表清退、人工核对等）不在本文重复，按 `docs/待办与阻塞事项.md` 中当前发布窗口条目执行；执行前同样先停写并完成可恢复备份。

### 9.4 手工升级窗口（有 schema/迁移变更）

```sh
cd /opt/juhe-ai
set -a && . ./.env && set +a

# 0) 本机构建并上传新 build/（§6）；只传 build/ 与确需变更的配置，不要覆盖服务器 .env
docker compose --profile tool build    # 含新版 maintenance，升级必须用新镜像

# 1) 停写
docker compose stop gateway jobs

# 2) 备份并验证（见 §10）
DUMP=backup/juhe_ai-pre-upgrade-$(date +%Y%m%d-%H%M).dump
docker exec juhe-ai-postgres pg_dump -U juhe_ai -Fc juhe_ai > "$DUMP"
docker exec -i juhe-ai-postgres pg_restore -l >/dev/null < "$DUMP" && echo backup-ok

# 3) 一次性清退 openai/hybrid/generic_http 账户（revision 17 之前的强制步骤）
#    dry-run 只读并冻结 manifest；人工核对 JSON 中的每表行数、日期范围与 ID 哈希后再 apply。
docker compose --profile tool run --rm -v "$PWD/backup:/backup" maintenance \
  purge-unsupported-vendor-accounts --dry-run \
  --manifest-out /backup/purge-unsupported-vendors-$(date +%Y%m%d-%H%M).json \
  --dsn "$JUHE_AI_POSTGRES_URL" </dev/null
docker compose --profile tool run --rm -v "$PWD/backup:/backup" maintenance \
  purge-unsupported-vendor-accounts \
  --manifest-out /backup/purge-unsupported-vendors-<上一步文件名>.json \
  --stop-write-confirmed --backup-confirmed \
  --dsn "$JUHE_AI_POSTGRES_URL" </dev/null
#    清退会删除目标账户及其连接/映射/授权实例/历史 usage/audit/stats；不可逆。

# 4) 只读预演（确认没有 blocked）
docker compose --profile tool run --rm maintenance upgrade --dry-run --dsn "$JUHE_AI_POSTGRES_URL" </dev/null

# 5) 正式升级（revision 17 会添加 accounts vendor/driver CHECK）
docker compose --profile tool run --rm maintenance upgrade \
  --dsn "$JUHE_AI_POSTGRES_URL" --secret "$JUHE_AI_SECRET" \
  --stop-write-confirmed --backup-confirmed </dev/null

# 6) T119 退役账户名称搜索派生层（必须在拉起新版 gateway/jobs 之前，见 §9.6）
docker compose --profile tool run --rm maintenance \
  drop-retired-account-name-search-index --dry-run --dsn "$JUHE_AI_POSTGRES_URL" </dev/null
docker compose --profile tool run --rm maintenance \
  drop-retired-account-name-search-index \
  --dsn "$JUHE_AI_POSTGRES_URL" --stop-write-confirmed --backup-confirmed </dev/null

# 7) 拉起并验证
docker compose up -d gateway jobs
docker compose ps
bash verify-release.sh

# 8) 幂等补种/校验（可选；不推进账本）
docker compose --profile tool run --rm maintenance --ensure-schema --seed \
  --dsn "$JUHE_AI_POSTGRES_URL" --secret "$JUHE_AI_SECRET" </dev/null
```

### 9.5 发布顺序约束

- gateway 与 jobs 必须同批发布（共享 usage spool 契约与 schema 读取面），除非发布说明明确只影响单侧。
- 涉及 schema 的改动：先升级库（`upgrade`）再启动新版进程；顺序颠倒会让新版进程 fail-fast 重启循环。
- 2026-11-05 退役批次顺序固定：停写 → 整库备份并验证 → purge dry-run/核对 manifest → purge apply → `upgrade` 到 revision 17 → T119 名称搜索派生层退役 → 启动新版 gateway/jobs → `verify-release.sh`。若 purge 未完成而先 `upgrade`，CHECK 会因遗留空 vendor/generic 账户失败。
- T119 退役命令必须在 `upgrade` 之后、`docker compose up -d gateway jobs` 之前执行：新版 gateway/jobs 已不再读写派生表，先拉起会让旧表与新二进制并存并放大「表已删、进程仍写」的误判。DROP 后回滚只能恢复窗口备份 + 回退旧镜像，只换二进制不可行。
- 维护命令一律加 `</dev/null`（避免吞脚本 stdin）；管道接维护命令时用 `set -o pipefail`（否则退出码被 `tail`/`grep` 掩盖）。

### 9.6 AI 账户名称搜索去索引化（T119 / BUG-0349）

账户名称搜索自 2026-11-03 起改为作用域内直读 `accounts.name`，不再维护派生词项层；本命令只清退生产存量对象，新库由 `--ensure-schema` 直接建出无索引层形态，无需执行。

- 清退对象：`juhe_business.account_name_search_terms`、`account_name_search_documents`、`account_list_availability_projection_search_terms` 三张表；`account_list_availability_projection_index.search_index_complete` 列；残留触发器函数 `account_list_availability_name_search_dirty_trigger()`。
- 执行方式：单事务、默认 RESTRICT（不级联）、`lock_timeout=2s`、幂等可重跑；正式执行强制 `--stop-write-confirmed` + `--backup-confirmed`（缺一 exit 2，不开库）。`--dry-run` 只读，输出目标库与各对象存在状态，不要求两个确认。
- 窗口内顺序：必须在 §9.4 第 6 步完成（停写窗口内、`upgrade` 之后、拉起 gateway/jobs 之前）；第 2 步的整库备份是本操作唯一的回滚恢复点。
- 验证：拉起后管理面对话账户列表搜 `k40`（前缀）、`林`（中段）、`GROK`（ASCII 大小写）、`%`/`_`/`\`（字面）均符合预期；再跑一次 `--dry-run` 应全部为 absent 且重跑幂等。

## 10. 备份与恢复

备份策略（按实际环境二选一或并用）：

- 备份机每日定时拉取（当前生产采用）：备份机通过 SSH 到服务器，在 PG 容器内执行 `pg_dump`，流式落盘，保留最近 7 份；不改服务器本地磁盘。当前生产只备份业务数据：日志/审计/遥测域仅排除表数据（`--exclude-table-data`，DDL 仍保留在 dump 内），`data/app` 文件域整体不备份。
- 服务器本地 cron：每日低峰执行 `pg_dump -Fc` 到 `/opt/juhe-ai/backup/`，定期同步到异机并清理过期文件。整库 dump 会包含日志/审计数据、体积大；磁盘有限时按与生产相同的排除清单裁剪。

窗口纪律：自动备份通常安排在凌晨（当前生产为 04:10）；发版/重启容器避开备份窗口（整库读快照会持表锁，窗口约 1–2 小时）。备份后必须用 `pg_restore -l` 验证可读，不能只看文件大小。

手工备份：

```sh
cd /opt/juhe-ai
DUMP=backup/juhe_ai-$(date +%Y%m%d-%H%M).dump
docker exec juhe-ai-postgres pg_dump -U juhe_ai -Fc juhe_ai > "$DUMP"
docker exec -i juhe-ai-postgres pg_restore -l >/dev/null < "$DUMP" && echo backup-ok
```

恢复（示例，停写窗口内）：

```sh
docker compose stop gateway jobs
docker exec -i juhe-ai-postgres psql -U juhe_ai -d postgres -c 'DROP DATABASE IF EXISTS juhe_ai;'
docker exec -i juhe-ai-postgres psql -U juhe_ai -d postgres -c 'CREATE DATABASE juhe_ai OWNER juhe_ai;'
docker exec -i juhe-ai-postgres pg_restore -U juhe_ai -d juhe_ai --no-owner < backup/<dump>
docker compose up -d
```

按当前生产口径不备份：Redis（运行态可重建）、`juhe_dataset` 与 `juhe_jobs`/`juhe_stats` 遥测表的**表数据**（结构仍在 dump 内），以及 `data/app` 内的审计 blob/热缓存/瞬态队列（边界与重建步骤见私有备份说明）。升级回滚只依赖业务数据；审计/日志域不承担恢复点职责。

## 11. 监控

- gateway 指标：`127.0.0.1:3306/__aisys__/metrics`；jobs：`127.0.0.1:3305/__aisys__/metrics`。只发布宿主回环，禁止公网反代。
- 抓取可选用独立 Prometheus：经 SSH 隧道或同机 agent 访问上述回环端口，`scrape_interval: 60s`。当前生产由监控机经既有 SSH 隧道抓取；抓取配置片段、postgres_exporter 查询与 Grafana 面板 JSON 在 `docker/single-server/monitoring/`。
- pprof 诊断：`127.0.0.1:3306/debug/pprof/`（只读、仅回环；抓取产物不入仓库）。
- 文件日志：`/opt/juhe-ai/data/app/logs/juhe-ai.log`（按大小轮转，保留 500 个 × 30 天；索引行保留另由 `JUHE_AI_RUNTIME_LOG_RETENTION_DAYS` 控制）。

## 12. 排障速查

| 症状 | 先查 | 处理 |
| --- | --- | --- |
| `docker compose ps` 有容器 unhealthy | `docker compose logs <service> --tail=200` | 按日志根因；gateway 首次启动等租约约 1 分钟属正常 |
| 公网 502 | Caddy 日志、gateway 容器状态、固定 IP 是否 172.18.0.10 | 恢复 gateway；确认 Caddyfile upstream 未被改成容器名/HTTP2 |
| `docker compose up` 报 `Pool overlaps` / 网段冲突 | `docker network ls`、`ip route` | 修改 compose 的 `ipam.subnet`，并同步修改 Caddyfile 的固定 IP |
| health 返回 503 | `curl 127.0.0.1:3306/health`、PG/Redis 连接 | 连接串、密码、PG/Redis healthy |
| 统计/用量恒 0 | 两容器 `data` 挂载是否同源、`usage-record-spool` 是否存在 | 恢复 `working_dir: /app/backend` 与 `./data/app/data` 挂载；`bash verify-release.sh` |
| 新版启动提示「尚未升级/升级未完成」 | `maintenance upgrade --dry-run` | 走 §9.2 升级 |
| 文件日志不增长 | `JUHE_AI_LOG_DIR` 与 `data/app/logs` 挂载 | 修正挂载；`disabled` 字面量会关闭写侧 |
| Caddy 容器 exec 全败/不健康但流量正常 | caddy zombie/子进程 | `docker compose force-recreate caddy`（入口闪断数秒） |
| 内存压力/整机卡死 | `free -h`、`docker stats`、GOMEMLIMIT/mem_limit | 保持 compose 双限；新机确认 `host-init.sh` 已执行 |
| 后台登录 401/跨域失败 | `.env` 的 `ALLOWED_ORIGINS`、`COOKIE_SECURE`、`TRUST_PROXY` | 改成实际访问 Origin；HTTPS 下 cookie secure |
| `/v1` 401 | 是否带 Bearer Key | 正常鉴权行为；用后台 Key 重试 |

## 13. 迁移到新服务器

1. 搬：`/opt/juhe-ai/{compose.yml,Caddyfile,.env}` + `/opt/juhe-ai/data/` 全部（PG/Redis 数据 + app 文件）。
2. 不搬：`build/`（本地重编译上传）、Docker 镜像（重新 build）、Caddy 命名卷（新机自动重签证书）。
3. 新机执行 `host-init.sh`，安装 Docker，重建 `data/app` 属主。`data/` 整体搬走时 Redis AOF/RDB 与 PG 数据都在，本机按 §6 重新构建并上传 `build/` 后 `docker compose --profile tool build && docker compose up -d` 即可，无需重跑 schema；只恢复 PG dump 时按 §7 完整初始化。
4. 若 Redis 数据未搬迁，必须在 gateway 首次启动前跑 `docker compose run --rm gateway -init-account-circuit-runtime-index`；gateway 已启动时先 `docker compose stop gateway`，跑完再 `start`（一次性容器会占用固定 IP）。
5. 出海代理（sing-box/隧道）按 [proxy/](proxy/README.md) 在新机重装，确认 `JUHE_AI_PROXY_IP_A/B` 与代理监听一致；DNS A 记录切新机。
6. 验证按 §8 全量执行。

## 14. 安全清单

- `.env` 权限 600，只在服务器与本地发布机；不提交、不粘贴到聊天/文档/日志。
- `JUHE_AI_SECRET` ≥32 位随机并离线多处留档；有加密数据后不可更换。
- 生产保持验证码开启（不要保留 `JUHE_AI_AUTH_CAPTCHA_DISABLED`）。
- PG/Redis 不发布宿主端口；metrics/pprof 仅回环。
- `JUHE_AI_ALLOWED_ORIGINS` 禁止 `*`；`COOKIE_SECURE=true`。
- 建议 SSH 仅密钥登录并启用 fail2ban。
- 发布脚本使用的 `docker/single-server/.env`（本地）含 `JUHE_AI_DEPLOY_SERVER`；首次部署时会同时填入生产密钥用于上传，因此本地副本同样按 600 保管、永不提交。日常发布可只保留部署变量，但不得把服务器 `.env` 复制到其他位置。

## 附录：当前运行契约速查

- 进程工作目录：gateway/jobs/maintenance 容器必须 `working_dir: /app/backend`；`data/`、`logs/` 相对 cwd 解析，否则写入容器临时层，容器重建即丢。
- 用量交接：gateway 写 `data/usage-record-spool`，jobs drain 后写 PG；两侧必须同一挂载（`./data/app/data`）。
- 非 root：容器以 UID/GID 1000 `app` 运行，`data/app` 属主必须匹配。
- 客户端交接：非终态失败（锁死 hold、预算耗尽、临时隔离等）先提交 200 传输头再断开，客户端按网络错误重试；Caddy/Nginx 需保持 HTTP/1.1 upstream、SSE 不缓冲。
- schema 门禁：`gateway/jobs` 启动比对库 revision，落后 fail-fast；升级只走 `maintenance upgrade` / `deploy.sh upgrade`。
- 当前 schema revision：`16`（以 `backend-go/shared/contracts` 常量为准）。
