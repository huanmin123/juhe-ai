# 跨平台部署基线

> 本文只说明发布包在 Windows、macOS、Linux 上的通用启动、配置、验证、常驻、项目备份和业务备份基线。如何构建发布包见 `docs/deploy/构建指南.md`。
>
> 如果你还没确定部署场景，不要从本文开始。先看 [服务器部署方案](scenarios/服务器部署方案.md) 或 [家庭宽带反向代理方案](scenarios/家庭宽带反向代理方案.md)，再按场景跳回本文或平台文档。
>
> 如果你要用 Docker 部署，请直接先看 `docs/deploy/Docker部署指南.md`，再参考 `docker/README.md`、`docker/compose.yml`、`docker/.env.example`、`docker/Dockerfile` 和 `docker/entrypoint.sh`。如果要部署 PostgreSQL + Redis 高性能模式，先看 `docs/deploy/高性能模式部署指南.md`，并使用 `docker/compose.performance.yml` 与 `docker/.env.performance.example`。
>
> 平台差异不要继续堆进本文：Linux 看 [Linux 部署指南](linux/Linux部署指南.md)，Windows 看 [Windows 部署指南](windows/Windows部署指南.md)，macOS 看 [macOS 部署指南](macos/macOS部署指南.md)。公网 HTTPS 入口默认看 [Caddy 自动 HTTPS 部署指南](https/Caddy自动HTTPS部署指南.md)。如果上游 API 需要网络代理，先看 [sing-box 网络代理部署指南](proxy/sing-box网络代理部署指南.md)。

## 1. 部署兼容矩阵

同一个发布包可以部署到三类目标机器：

| 部署目标 | 推荐压缩包 | 启动脚本 | 常驻运行建议 |
| --- | --- | --- | --- |
| Windows | `juhe-ai-release.zip` | `pwsh ./start.ps1` | NSSM / PM2 / 任务计划程序 |
| macOS | `juhe-ai-release.tar.gz` | `bash ./start.sh` | launchd / PM2 |
| Linux | `juhe-ai-release.tar.gz` | `bash ./start.sh` | systemd / PM2 |

不要跨系统复制 `node_modules`。日志搜索 `grep 模式` 只使用后端生产依赖 `@vscode/ripgrep` 安装的 `rg`，不读取服务器 PATH 中的系统 `rg`，也不回退到 Node 文件扫描。Windows、macOS、Linux 的 x64 / arm64 等平台差异由目标机器执行 `pnpm install --prod` 时自动处理。

## 2. 部署前必须检测

### Windows 目标

```powershell
$PSVersionTable.PSVersion
Get-Location
node -v
node -p "process.version + ' LTS=' + (process.release.lts || '非LTS')"
corepack --version
pnpm -v
netstat -ano | Select-String ':3000'
```

### macOS 目标

```bash
pwd
sw_vers
uname -a
df -h .
node -v
node -p "process.version + ' LTS=' + (process.release.lts || '非LTS')"
corepack --version || true
pnpm -v || true
lsof -iTCP:3000 -sTCP:LISTEN || true
```

### Linux 目标

```bash
pwd
uname -a
df -h .
node -v
node -p "process.version + ' LTS=' + (process.release.lts || '非LTS')"
corepack --version || true
pnpm -v || true
ss -lntp | grep ':3000 ' || true
curl -I https://registry.npmjs.org/ || true
```

必须确认：

- Node.js 是官方 LTS，当前支持 22.x LTS（>=22.13.0）或 24.x LTS（>=24.11.0）；启动脚本会进一步验证 `node:sqlite` 可用。
- pnpm 可用，或 corepack 可用且能启用 pnpm。
- 首次启动能访问 npm registry，或已配置可用代理/缓存。
- 如果目标上游 API 无法直连，先准备服务器可用的网络代理；账号级上游代理配置见 [sing-box 网络代理部署指南](proxy/sing-box网络代理部署指南.md)。
- 公网域名访问建议优先准备 HTTPS 反向代理；免费证书和自动续期配置见 [Caddy 自动 HTTPS 部署指南](https/Caddy自动HTTPS部署指南.md)。
- 默认端口 `3000` 未被占用；占用时修改 `backend/.env` 的 `JUHE_AI_PORT`。
- 当前部署目录有写入权限和足够磁盘空间。
- 如果 `grep 模式` 报找不到 `rg`，确认目标机器的后端生产依赖安装成功，尤其是 `@vscode/ripgrep` 及其当前平台 optional dependency 没有被跳过。

## 4. 配置 `backend/.env`

发布包默认带 `backend/.env.example`。如果没有手动创建 `backend/.env`，`start.ps1` / `start.sh` 首次启动会自动复制 example，并为新部署生成稳定的 `JUHE_AI_SECRET` 写回 `backend/.env`，同时填入本机默认 `JUHE_AI_ALLOWED_ORIGINS`，避免首次启动卡在空配置上。后续迁移或公网部署时，仍应按实际环境修改并放在稳定的共享配置位置；项目备份不得复制真实 `backend/.env`，业务备份必须包含它以保留 `JUHE_AI_SECRET`。

### 创建配置文件

Windows：

```powershell
Copy-Item .\backend\.env.example .\backend\.env -ErrorAction SilentlyContinue
notepad .\backend\.env
```

macOS / Linux：

```bash
cp -n backend/.env.example backend/.env
nano backend/.env
```

### 最低配置

```env
JUHE_AI_HOST=127.0.0.1
JUHE_AI_PORT=3000
JUHE_AI_DB_SERVICE_HTTP_HOST=127.0.0.1
JUHE_AI_DB_SERVICE_HTTP_PORT=0
JUHE_AI_DATABASE_PATH=./data/juhe-ai.sqlite3
JUHE_AI_DATASET_DATABASE_PATH=./data/juhe-ai-dataset.sqlite3
JUHE_AI_STATS_DATABASE_PATH=./data/juhe-ai-stats.sqlite3
JUHE_AI_USAGE_SHARD_ROOT=./data/usage-shards
JUHE_AI_USAGE_SHARD_COUNT=16
JUHE_AI_SECRET=换成一串足够长且固定保存的随机密钥
JUHE_AI_ALLOWED_ORIGINS=https://你的后台访问域名
JUHE_AI_COOKIE_SECURE=true
JUHE_AI_COOKIE_SAME_SITE=lax
JUHE_AI_TRUST_PROXY=false
JUHE_AI_ALLOW_PRIVATE_UPSTREAM_BASE_URLS=false
JUHE_AI_UPSTREAM_BASE_URL_PRIVATE_ALLOWLIST=
JUHE_AI_OAUTH_PROXY_URL=
JUHE_AI_MODEL_CHECK_PROBE_RETRY_DELAY_MS=65000
```

配置规则：

- 反向代理或本机访问：`JUHE_AI_HOST=127.0.0.1`。
- 局域网/公网直连访问：`JUHE_AI_HOST=0.0.0.0`，并开放系统防火墙或云安全组端口。
- DB service 内部系统 API 默认绑定 `127.0.0.1` 并自动选择空闲端口，由主进程代理 `/__aisys__/api/*`；不要把 `JUHE_AI_DB_SERVICE_HTTP_HOST` 暴露到公网。
- 新部署如果通过启动脚本首次生成 `backend/.env`，脚本会写入随机 `JUHE_AI_SECRET`；也可以手动改成自己保存的强随机值。不要把它改回空值、示例值或短密钥，`NODE_ENV=production` 时默认开发密钥或短于 32 位的密钥会直接拒绝启动。
- `NODE_ENV=production` 时必须配置 `JUHE_AI_ALLOWED_ORIGINS`，只填写后台前端的完整 Origin，多个用英文逗号分隔；不要配置 `*`。启动脚本默认只写入 `localhost/127.0.0.1` 本机访问 Origin，公网 IP、域名或反向代理部署需要改成实际访问地址。
- 生产环境登录态 Cookie 默认启用 `Secure`，建议前端入口走 HTTPS；只有临时 HTTP 内网验证才显式设为 `JUHE_AI_COOKIE_SECURE=false`。
- `JUHE_AI_COOKIE_SAME_SITE` 默认 `lax`；如果前后端确实跨站部署并配置为 `none`，必须同时保持 `JUHE_AI_COOKIE_SECURE=true`。
- HTTPS 反向代理后如需后台记录真实客户端 IP，把 `JUHE_AI_TRUST_PROXY` 设置为 `true` 或实际代理跳数；后端端口必须只允许本机 Caddy、可信内网或可信 edge 访问。公网直连后端时保持 `false`，避免客户端伪造 `X-Forwarded-For`。
- 上游账户 `Base URL` 默认拒绝本机、内网、链路本地和保留地址；`NODE_ENV=production` 时仍禁止启用全局开关 `JUHE_AI_ALLOW_PRIVATE_UPSTREAM_BASE_URLS`。`JUHE_AI_UPSTREAM_BASE_URL_PRIVATE_ALLOWLIST` 默认必须留空，只有明确需要连接私网上游时才由部署人员显式填写精确 IP Origin，例如 `http://192.168.40.199:8317`；按 `scheme + IP + effective port` 匹配，不接受域名或路径，也不会自动跟随上游重定向。发布包和生产示例不得预置该白名单。
- 复用当前业务库必须沿用原 `JUHE_AI_SECRET`。
- `JUHE_AI_SECRET` 改错会导致 OAuth token、上游 API Key、代理密码等敏感字段无法解密。
- `JUHE_AI_OAUTH_PROXY_URL` 只用于 OpenAI OAuth token 换取 / 刷新的兜底代理；普通上游模型请求应在后台“代理管理”创建 `http` / `https` / `socks5` / `socks5h` 代理并绑定到 AI 账户。
- 模型检测正常探针不做人为并发限制；`JUHE_AI_MODEL_CHECK_PROBE_RETRY_DELAY_MS` 是所有探针失败后的重试间隔，默认 65 秒。后端不依赖上游状态码或错误类型判断是否长退避，避免同一分钟窗口里贴着重打。若上游返回 `Retry-After` 且更长，会按更长时间等待。
- `JUHE_AI_DATABASE_PATH` 只保存系统账户、AI 账户、分组、API Key、授权、设置和公告等业务数据。
- `JUHE_AI_DATASET_DATABASE_PATH` 保存审计、操作日志、运行日志索引、模型检测和清理目标。
- `JUHE_AI_USAGE_CATALOG_DATABASE_PATH` 保存 usage shard 注册表、列表筛选目录和账号 / API Key scope catalog。
- `JUHE_AI_STATS_DATABASE_PATH` 保存统计缓存、额度窗口、账号质量、系统监控、表监控历史和 `stats_job_state`。
- `JUHE_AI_USAGE_SHARD_ROOT` 保存使用记录 shard 文件；未配置或留空时默认跟随数据集目录库生成同级 `usage-shards`，也可以显式配置到独立目录。
- `JUHE_AI_USAGE_SHARD_COUNT` 默认 `16`；生产启用后不要直接改小。
- 原始审计正文捕获固定开启，不再通过环境变量关闭。
- 四个 SQLite 路径必须指向不同文件；当前存储入口使用业务库、数据集目录库、使用记录目录库、usage shard 目录和统计结果库。

### 高性能模式配置

高性能模式使用 PostgreSQL + Redis。配置、密码 URL 编码、PgBouncer、Redis cache / state、初始化、项目/业务备份和验证只维护在 [高性能模式部署指南](高性能模式部署指南.md)。不要在通用发布包基线里复制高性能 env。

## 5. 启动

### Windows

```powershell
pwsh .\start.ps1
```

### macOS / Linux

```bash
bash ./start.sh
```

启动脚本会：

- 检查 Node.js LTS 和 `node:sqlite` 可用性。
- 尝试通过 corepack 启用 pnpm。
- 缺少 `backend/.env` 时自动从 example 创建，并补齐首次启动可用的随机 `JUHE_AI_SECRET` 和本机默认 `JUHE_AI_ALLOWED_ORIGINS`。
- 创建 `backend/data`。
- 首次安装目标平台生产依赖，并随依赖安装 `@vscode/ripgrep` 对应平台的 `rg` 二进制。
- 主进程会 fork 并看护 worker 组和 DB service；不要把子进程单独注册成系统服务。

后台任务运行边界：

- HTTP 主服务、worker 组和 DB service 是一个发布包拓扑；外部守护只守护主进程。
- 部署验证不能只看 `/__aisys__/health`，还要看 `/__aisys__/api/health` 和启动日志里的 worker / DB service 记录。

## 6. 验证

### Windows

```powershell
Invoke-WebRequest http://127.0.0.1:3000/__aisys__/health
Invoke-WebRequest http://127.0.0.1:3000/__aisys__/api/health
Invoke-WebRequest http://127.0.0.1:3000/__aisys__/
```

### macOS / Linux

```bash
curl -i http://127.0.0.1:3000/__aisys__/health
curl -i http://127.0.0.1:3000/__aisys__/api/health
curl -I http://127.0.0.1:3000/__aisys__/
```

期望：

- `/__aisys__/health` 返回 `200` 和 `status: ok`。
- `/__aisys__/api/health` 返回 `200` 和 `status: ok`。
- `/__aisys__/` 返回前端页面。
- `/__aisys__/` 和登录路径返回 `Content-Security-Policy`、`X-Frame-Options: DENY`、`X-Content-Type-Options: nosniff` 与 `Referrer-Policy: strict-origin-when-cross-origin`，且不返回 `X-Powered-By`。
- CSP 的 `script-src` 只允许 `'self'`，不得包含 `unsafe-eval`；`/v1` 不返回管理面 CSP。

响应头验证示例：

```bash
curl -sS -D - -o /dev/null http://127.0.0.1:3000/__aisys__/
curl -sS -D - -o /dev/null 'http://127.0.0.1:3000/__aisys__/login?redirect=/'
curl -sS -D - -o /dev/null http://127.0.0.1:3000/v1/models
```

公网 Edge 场景使用实际域名并通过 `curl --resolve 域名:443:EdgeIP` 逐个验证；六个入口应返回相同管理面 CSP、静态资源版本和正确 JS/CSS MIME 类型。此项只验收主应用响应，不要求修改 DNS、WireGuard、Caddy/Nginx 或 Edge 配置。

浏览器访问：

```text
http://127.0.0.1:3000/__aisys__/
```

如果使用公网或域名，按实际地址访问。

## 7. 常驻运行

重要：下面 PM2 示例直接启动 `backend/dist/server.js`，只适合已经先运行过 `pwsh ./start.ps1` 或 `bash ./start.sh`，并确认运行时预检、`backend/.env`、生产依赖和 `@vscode/ripgrep` 安装都已完成的发布包。首次部署或依赖变化后，仍应先执行启动脚本；如果绕过启动脚本，必须自行设置完整环境变量并执行 `pnpm install --prod --frozen-lockfile --filter juhe-ai-backend...`。`start.sh` 默认设置 `JUHE_AI_LOG_CONSOLE_ENABLED=false`，Windows `start.ps1` 则保留 `.env` / 外部环境里的日志设置。

### Windows

推荐：

- NSSM 注册 Windows Service。
- PM2 Windows 服务化方案。
- 任务计划程序开机启动 `pwsh -File start.ps1`。
- 常驻运行只需要守护 Web/API/网关主进程；主进程会 fork 并看护 `ingest-worker`、`stats-worker`、`ops-worker` 和 DB service。不要把 `worker.js`、DB service 或 `temporary-maintenance-worker.js` 当成独立服务长期手动启动；当前运行时 usage / dataset / stats 维护任务不再依赖临时维护 worker。

PM2 示例：

```powershell
npm install -g pm2
pm2 start .\backend\dist\server.js --name juhe-ai --cwd (Get-Location).Path
pm2 save
```

### macOS

推荐：

- launchd。
- PM2。
- Caddy/Nginx 反向代理。
- launchd / PM2 只需要守护 Web/API/网关主进程；主进程会 fork 并看护 `ingest-worker`、`stats-worker`、`ops-worker` 和 DB service。`temporary-maintenance-worker` 不是常驻服务，当前运行时维护写入不再通过它执行，不写入 launchd / PM2 常驻配置。
- 发布包 `start.sh` 默认 `JUHE_AI_LOG_CONSOLE_ENABLED=false`，普通运行日志写入 `backend/logs/` 滚动文件；launchd stdout 只保留启动脚本和极少量进程级输出。如需临时排障 stdout，可在守护配置里显式覆盖该环境变量。

PM2 示例：

```bash
npm install -g pm2
cd /你的路径/juhe-ai-release
pm2 start backend/dist/server.js --name juhe-ai --cwd /你的路径/juhe-ai-release
pm2 save
```

### Linux

推荐：

- systemd。
- PM2。
- Nginx/Caddy 反向代理和 HTTPS。
- systemd / PM2 只需要守护 Web/API/网关主进程；主进程会 fork 并看护 `ingest-worker`、`stats-worker`、`ops-worker` 和 DB service。

PM2 示例：

```bash
npm install -g pm2
cd /你的路径/juhe-ai-release
pm2 start backend/dist/server.js --name juhe-ai --cwd /你的路径/juhe-ai-release
pm2 save
pm2 startup
```

Linux `systemd` 不在通用基线重复维护；使用 [Linux 部署指南](linux/Linux部署指南.md) 的 `/opt/juhe-ai-lite/current` 固定入口。

## 9. 项目备份、业务备份和数据迁移

常规备份固定分成两类，并分别只保留最近 3 次：

| 类型 | 目录前缀 | 必须包含 | 明确排除 |
| --- | --- | --- | --- |
| 项目备份 | `project-时间戳` | 升级前当前运行 release 的干净压缩包、清单、校验值；目标迁移脚本仅作附加证据 | `.env`、`data/`、日志、数据库、`node_modules`、所有链接 |
| 业务备份 | `business-时间戳` | SQLite 业务库或 PostgreSQL `juhe_business`、恢复所需的 `backend.env`、schema / 清单、校验值 | dataset、usage、stats、Codex context、审计 payload、日志、Redis |

同一时间戳的项目备份与业务备份必须在迁移前生成：项目归档当前运行 release，业务备份捕获同一时刻的业务库和有效 env，形成一对可配套恢复的升级前恢复点。不得把待上线新包当成这份项目快照；目标迁移文件可以作为附加证据写入项目目录。两类都完成完整性校验并原子发布后，立即分别删除同类第 4 份及更早备份。不要直接压缩整个部署根目录，也不要跟随 `current`、`backend/data` 或其他共享目录软链接。业务备份中的 `backend.env` 必须保存当前有效的 `JUHE_AI_SECRET` 并限制文件权限；Docker 自动生成密钥时也要把有效密钥单独导出到业务备份，否则加密凭据无法恢复。

Windows 项目备份示例：

下面的 `juhe-ai-release.zip` 必须由升级前当前运行 release 生成；`migrate-*.sql` 只是目标变更证据。

```powershell
$ErrorActionPreference = 'Stop'
$Stamp = Get-Date -Format yyyyMMdd-HHmmss
$BackupRoot = (New-Item -ItemType Directory -Force .\backups).FullName
$Stage = Join-Path $BackupRoot ".project-$Stamp.tmp-$PID"
$Final = Join-Path $BackupRoot "project-$Stamp"
if (Test-Path -LiteralPath $Final) { throw "备份已存在：$Final" }
New-Item -ItemType Directory -Path $Stage | Out-Null

try {
  Copy-Item -LiteralPath .\juhe-ai-release.zip -Destination $Stage
  Copy-Item .\migrate-*.sql -Destination $Stage -ErrorAction SilentlyContinue
  Get-ChildItem -LiteralPath $Stage -File | Get-FileHash -Algorithm SHA256 | ForEach-Object {
    "$($_.Hash.ToLowerInvariant()) *$([IO.Path]::GetFileName($_.Path))"
  } | Set-Content -LiteralPath (Join-Path $Stage 'SHA256SUMS') -Encoding ascii

  Get-Content -LiteralPath (Join-Path $Stage 'SHA256SUMS') | ForEach-Object {
    if ($_ -notmatch '^([0-9a-f]{64}) \*(.+)$') { throw "非法校验行：$_" }
    $Expected = $Matches[1]
    $Name = $Matches[2]
    $Actual = (Get-FileHash -LiteralPath (Join-Path $Stage $Name) -Algorithm SHA256).Hash.ToLowerInvariant()
    if ($Actual -ne $Expected) { throw "校验失败：$Name" }
  }
  Move-Item -LiteralPath $Stage -Destination $Final
} finally {
  if (Test-Path -LiteralPath $Stage) { Remove-Item -LiteralPath $Stage -Recurse -Force }
}

foreach ($Prefix in @('project', 'business')) {
  Get-ChildItem -LiteralPath $BackupRoot -Directory -Filter "$Prefix-*" |
    Sort-Object Name -Descending |
    Select-Object -Skip 3 |
    Remove-Item -Recurse -Force
}
```

macOS / Linux 项目备份示例：

下面的 `juhe-ai-release.tar.gz` 必须由升级前当前运行 release 生成；`migrate-*.sql` 只是目标变更证据。

```bash
set -euo pipefail

STAMP=$(date +%Y%m%d-%H%M%S)
BACKUP_ROOT=backups
STAGE="$BACKUP_ROOT/.project-$STAMP.tmp-$$"
FINAL="$BACKUP_ROOT/project-$STAMP"
test ! -e "$FINAL"
mkdir -p "$STAGE"
trap 'rm -rf -- "$STAGE"' EXIT

cp juhe-ai-release.tar.gz "$STAGE/"
for migration in migrate-*.sql; do
  [ -e "$migration" ] || continue
  cp "$migration" "$STAGE/"
done
(
  cd "$STAGE"
  : > SHA256SUMS
  for file in ./*; do
    [ -f "$file" ] || continue
    [ "$file" = ./SHA256SUMS ] && continue
    shasum -a 256 "$file" >> SHA256SUMS
  done
  shasum -a 256 -c SHA256SUMS
)
mv "$STAGE" "$FINAL"
trap - EXIT

retain_latest_three() {
  local prefix="$1" item index
  local -a backups=()
  while IFS= read -r item; do
    [ -d "$item" ] && [ ! -L "$item" ] && backups+=("$item")
  done < <(printf '%s\n' "$BACKUP_ROOT"/"$prefix"-* | LC_ALL=C sort -r)
  for ((index = 3; index < ${#backups[@]}; index += 1)); do
    rm -rf -- "${backups[$index]}"
  done
}

retain_latest_three project
retain_latest_three business
```

业务备份也必须先写入同一 `backups/` 下的 `.business-时间戳.tmp-*`，完成数据库完整性检查、`SHA256SUMS` 落盘和回读验证后，再原子改名为 `business-时间戳`。示例按时间戳目录名分别轮转 `project-*` 与 `business-*`，每类跳过最近 3 个，只删除其余目录；生产脚本和手工备份都不得绕过。

SQLite 模式在停服务后把 `backend/.env` 和 `backend/data/juhe-ai.sqlite3` 写入 `business-时间戳`，执行 `PRAGMA integrity_check` 并生成校验值；不得复制整个 `backend/data/`。PostgreSQL 模式按 [高性能模式部署指南](高性能模式部署指南.md) 只导出 `juhe_business`，同时保存恢复所需的 `backend.env`。

同机升级继续复用稳定的共享配置和数据目录，不为上线额外复制非业务数据。临时 PostgreSQL 验证库如需生产业务结构，只允许 `pg_dump | pg_restore` 管道直传，完成后删除临时库，不在备份目录持久化临时 dump。跨主机数据迁移必须作为一次单独授权的迁移操作执行，不属于常规备份。

SQLite 业务库明显膨胀时，停服务后用 `VACUUM INTO` 生成 compact 业务库并替换原文件；只有核心业务库进入业务备份。数据集目录库、使用记录目录库、usage shard 和统计结果库按当前模型重建，不进入备份。

当前版本固定使用业务库 / 数据集目录库 / 使用记录目录库 / usage shard / 统计结果库模式。新部署建议显式配置 `JUHE_AI_DATABASE_PATH`、`JUHE_AI_DATASET_DATABASE_PATH`、`JUHE_AI_USAGE_CATALOG_DATABASE_PATH`、`JUHE_AI_STATS_DATABASE_PATH`、`JUHE_AI_USAGE_SHARD_ROOT` 和 `JUHE_AI_USAGE_SHARD_COUNT`，并确保四个 SQLite 文件路径互不相同。复用业务库时必须让库结构符合当前 schema；不符合时停服务离线修复或重建。数据集目录库、使用记录目录库、usage shard 目录和统计结果库可以新建或清空。

统计口径升级或统计缓存损坏时，必须停服务后显式执行统计重建。发布包和源码构建后都统一使用编译产物入口：

Windows：

```powershell
node .\backend\dist\scripts\maintenance\rebuild-usage-stats.js --confirm-offline
```

macOS / Linux：

```bash
node ./backend/dist/scripts/maintenance/rebuild-usage-stats.js --confirm-offline
```

统计重建只在统计表、统计口径、授权消耗规则或额度窗口规则变化时执行。执行前停服务，确认 `backend/.env` 指向目标生产库，并传 `--confirm-offline` 或设置 `JUHE_AI_CONFIRM_USAGE_STATS_REBUILD=1`。

切换部署时：

1. 解压新发布包。
2. 核对 archive SHA256，并确认包内 `RELEASE_SOURCE_COMMIT` 与上线计划冻结的完整 release SHA 完全一致；缺失或不一致时禁止继续。
3. 复制当前 `backend/.env` 到新发布包的 `backend/.env`，或按当前配置重新填写。
4. 业务库必须符合当前 schema；如不符合，停服务后用一次性离线 SQL / 脚本修复，或把当前业务表数据整理后导入新业务库。数据集目录库、使用记录目录库和 usage shard 目录按需要复制或丢弃，统计结果库可以直接清空或通过重建脚本再生成。
5. 如果当前部署需要按最新统计口径重建统计结果，先运行统计重建脚本。
6. 在同一主机、另一端口并行启动候选服务前，确认旧外部 watchdog 已持久禁用且未加载；禁止依赖 PPID 扫描清理候选或生产子进程。
7. 启动新服务。
8. 验证登录、账户、API Key、网关和管理员“表监控”页面。
9. 候选只用于离线预验时，成功或失败后都必须显式结束并清理其子进程；候选正在承担临时接管流量时，必须保留到主服务完成固定 PID、正确 release、双 health、完整 `1 server + 1 db-service + 3 worker` 拓扑和稳定观察，确认可以回切后再清理。部署脚本应使用 `finally` / `trap` 保证最终清理，不得恢复旧 watchdog。

health 成功只表示 server / DB service 已能响应，不代表所有后台 worker 已完成 spawn。临时和生产验证必须在 health 成功后继续轮询完整 `1 server + 1 db-service + 3 worker` 拓扑，建议最多等待 30 秒；不能只读取一次进程树。启用 `set -e` 时，`grep -c` 暂时没有命中会返回退出码 `1`，计数命令必须用 `|| true` 接受 `0`，再由显式数量判断继续等待或超时失败。

macOS `launchctl kickstart -k`、Linux `systemctl restart` 或其他服务管理器切换 release 时，旧进程退出与新进程接管存在短暂重叠。验证器不能在首次看到 `running` 后固定使用当时的 PID；每轮都要重新读取服务管理器的当前 PID，并在同一轮确认该 PID 的 cwd / 可执行路径属于目标 release、该 PID 持有目标监听端口，三项同时成立后才能继续 health、前端哈希和稳定观察。否则旧 PID 会造成误回滚，新 PID 也可能被错误漏检。

仅前后端代码或前端资源变化、schema 与统计口径未变化时，生产切换只做项目备份和业务备份、依赖安装、`schema-only` 校验、release 原子切换和稳定观察；禁止无条件删除或重建数据集、使用记录、统计、Codex context schema，也不做无依据的全量 Redis 清空。只有当前 schema、统计口径或缓存契约明确要求时，才执行对应离线迁移、重建或定向缓存失效。

生产升级脚本的“重建非业务库”和“清理 Redis namespace”必须是两个独立、默认关闭的显式开关。普通发布两者都传 `0`；只有对应迁移计划明确要求、完成项目备份、业务备份和临时环境验证后才允许传 `1`。即使需要重建非业务 schema，也不能自动推导为允许清空 Redis queue/state。

## 10. 常见排障

- Node.js / `node:sqlite` 预检失败：切换到官方 Node.js LTS，当前支持 22.x LTS（>=22.13.0）或 24.x LTS（>=24.11.0）。
- `pnpm install` 失败：检查 npm registry 网络或代理配置。
- `grep 模式` 报找不到 `rg`：重新执行 `pnpm install --prod --frozen-lockfile --filter juhe-ai-backend...`，确认没有使用 `--ignore-optional` 或禁用 optional dependency。
- 页面能开但 API 失败：检查 `/__aisys__/api` 是否到同一后端。
- `/v1` 或根路径网关流式断开：反向代理关闭 buffering，并增大超时。
- 敏感字段无法解密：找回旧 `JUHE_AI_SECRET`。
- 端口外部访问失败：直连用 `JUHE_AI_HOST=0.0.0.0`，并开放防火墙/安全组端口。

### 发布失败恢复与源阻断

临时数据库初始复制完成后，正式切到 temporary 前必须从主库同一个只读一致性快照导出当前有效的 `system_sessions` 和这些 session 引用的账户安全字段，再在临时库事务内原子替换；同步失败或超时保持 main 承流，并在切流前再次复验临时进程身份。前端只有明确 401 才清除登录态；503、超时或网络瞬断保留已有用户与当前路由。冷启动认证瞬断只做有上限的退避重试，仍失败则显示“服务正在恢复”并允许手动重连，不得跳登录或无限轮询。该机制不开放临时窗口的新登录或其他认证写操作。

生产发布不是把所有接口一刀切停用的理由：临时服务只接管发布期间明确需要的入口，读取、登录会话和普通客户端操作必须由临时接管方案按健康检查验证后持续可用。任一发布阶段失败时，先停止写操作并登记失败源、问题单和客户影响；通过固定 PID、应用/DB 双 health 与最小业务 smoke 证明 main 健康才回 main，否则保持健康的 temporary，状态未知禁止盲切。

部署计划锁只保护未完成的生产现场，不承担失败源永久占用。客户端恢复后按 `rolled-back` 或 `cancelled` 释放锁；释放必须绑定本次锁创建后的精确恢复证据。失败源由 `release-source-blocker.ps1` 独立登记，后续同类应用发布在修复 commit、归档和验证证据完成 `fix-ready` 前不得继续，基础设施/运维变更按 `ChangeKind` 独立判断。

## 11. 给 AI 的部署摘要

临时接管候选环境必须显式设置 `JUHE_AI_SYSTEM_API_READ_ONLY=true`。该开关只在 DB service 的 System/Public API 入口按 HTTP 方法生效：`GET`、`HEAD`、`OPTIONS` 继续读取，其他方法返回 `503`、`Retry-After: 60` 和 `code=system_api_read_only`；客户端 `/v1` 网关不经过此门禁。正式环境必须未设置或显式为 `false`，切回正式服务前先验证。

1. 先判断部署场景：服务器部署看 `docs/deploy/scenarios/服务器部署方案.md`，家庭宽带反代看 `docs/deploy/scenarios/家庭宽带反向代理方案.md`。
2. 再判断目标系统：Windows、macOS、Linux 或 Docker。
3. 检查 Node.js LTS、运行时预检、pnpm/corepack、端口、网络、磁盘和权限。
4. 按目标系统解压 zip 或 tar.gz。
5. 检查 `start.sh`、`start.ps1`、`backend/dist/server.js`、`frontend/dist/index.html`。
6. 创建并审阅 `backend/.env`。
7. 根据访问方式设置 `JUHE_AI_HOST`，根据入口域名设置 `JUHE_AI_ALLOWED_ORIGINS`。
8. 确认 `JUHE_AI_SECRET`：新部署生成至少 32 位强随机值；复用当前业务库时沿用原值。
9. Windows 执行 `pwsh ./start.ps1`；macOS/Linux 执行 `bash ./start.sh`。
10. 验证 `/__aisys__/health`、`/__aisys__/api/health`、`/__aisys__/`。
11. 按场景配置 HTTPS 入口；上游无法直连时再配置 sing-box 账号代理。
12. 配置状态检测和自动恢复，必须有连续失败阈值、启动宽限、冷却时间和窗口限频。
13. 配置目标平台常驻运行。
14. 生成项目备份和业务备份并分别轮转到最近 3 次；除业务库与恢复所需 `backend.env` 外，不备份 `data/`、日志、审计、usage、统计或 Redis。
15. 如果目标是 Docker 部署，改看 `docs/deploy/Docker部署指南.md`，并按 `docker/README.md`、`docker/compose.yml`、`docker/.env.example`、`docker/Dockerfile` 和 `docker/entrypoint.sh` 的说明执行。
