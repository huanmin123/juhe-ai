# 跨平台部署文档

> 本文只说明如何把发布包部署到 Windows、macOS、Linux。如何构建发布包见 `docs/deploy/构建指南.md`。
>
> 如果你要用 Docker 部署，请直接先看 `docs/deploy/Docker部署指南.md`，再参考 `docker/README.md`、`docker/compose.yml`、`docker/.env.example`、`docker/Dockerfile` 和 `docker/entrypoint.sh`。

## 1. 部署兼容矩阵

同一个发布包可以部署到三类目标机器：

| 部署目标 | 推荐压缩包 | 启动脚本 | 常驻运行建议 |
| --- | --- | --- | --- |
| Windows | `juhe-ai-release.zip` | `pwsh ./start.ps1` | NSSM / PM2 / 任务计划程序 |
| macOS | `juhe-ai-release.tar.gz` | `bash ./start.sh` | launchd / PM2 |
| Linux | `juhe-ai-release.tar.gz` | `bash ./start.sh` | systemd / PM2 |

不要跨系统复制 `node_modules`。日志搜索 `grep 模式` 只使用后端生产依赖 `@vscode/ripgrep` 安装的 `rg`，不读取服务器 PATH 中的系统 `rg`，也不回退到 Node 文件扫描。Windows、macOS、Linux 的 x64 / arm64 等平台差异由目标机器执行 `pnpm install --prod` 时自动处理。

## 2. 部署前必须检测

### Windows 目标

```powershell
$PSVersionTable.PSVersion
Get-Location
node -v
node -p "process.version + ' LTS=' + (process.release.lts || '非LTS')"
corepack --version
pnpm -v
netstat -ano | Select-String ':3000'
```

### macOS 目标

```bash
pwd
sw_vers
uname -a
df -h .
node -v
node -p "process.version + ' LTS=' + (process.release.lts || '非LTS')"
corepack --version || true
pnpm -v || true
lsof -iTCP:3000 -sTCP:LISTEN || true
```

### Linux 目标

```bash
pwd
uname -a
df -h .
node -v
node -p "process.version + ' LTS=' + (process.release.lts || '非LTS')"
corepack --version || true
pnpm -v || true
ss -lntp | grep ':3000 ' || true
curl -I https://registry.npmjs.org/ || true
```

必须确认：

- Node.js 是官方 LTS，当前支持 22.x LTS（>=22.13.0）或 24.x LTS（>=24.11.0）；启动脚本会进一步验证 `node:sqlite` 可用。
- pnpm 可用，或 corepack 可用且能启用 pnpm。
- 首次启动能访问 npm registry，或已配置可用代理/缓存。
- 默认端口 `3000` 未被占用；占用时修改 `backend/.env` 的 `JUHE_AI_PORT`。
- 当前部署目录有写入权限和足够磁盘空间。
- 如果 `grep 模式` 报找不到 `rg`，确认目标机器的后端生产依赖安装成功，尤其是 `@vscode/ripgrep` 及其当前平台 optional dependency 没有被跳过。

## 4. 配置 `backend/.env`

### 创建配置文件

Windows：

```powershell
Copy-Item .\backend\.env.example .\backend\.env -ErrorAction SilentlyContinue
notepad .\backend\.env
```

macOS / Linux：

```bash
cp -n backend/.env.example backend/.env
nano backend/.env
```

### 最低配置

```env
JUHE_AI_HOST=127.0.0.1
JUHE_AI_PORT=3000
JUHE_AI_DB_SERVICE_HTTP_HOST=127.0.0.1
JUHE_AI_DB_SERVICE_HTTP_PORT=0
JUHE_AI_DATABASE_PATH=./data/juhe-ai.sqlite3
JUHE_AI_DATASET_DATABASE_PATH=./data/juhe-ai-dataset.sqlite3
JUHE_AI_STATS_DATABASE_PATH=./data/juhe-ai-stats.sqlite3
JUHE_AI_USAGE_SHARD_ROOT=./data/usage-shards
JUHE_AI_USAGE_SHARD_COUNT=16
JUHE_AI_SECRET=换成一串足够长且固定保存的随机密钥
JUHE_AI_ALLOWED_ORIGINS=https://你的后台访问域名
JUHE_AI_COOKIE_SECURE=true
JUHE_AI_COOKIE_SAME_SITE=lax
JUHE_AI_TRUST_PROXY=false
JUHE_AI_ALLOW_PRIVATE_UPSTREAM_BASE_URLS=false
JUHE_AI_UPSTREAM_BASE_URL_PRIVATE_ALLOWLIST=
JUHE_AI_OAUTH_PROXY_URL=
JUHE_AI_AUDIT_FULL_BODY_CAPTURE_ENABLED=false
```

配置规则：

- 反向代理或本机访问：`JUHE_AI_HOST=127.0.0.1`。
- 局域网/公网直连访问：`JUHE_AI_HOST=0.0.0.0`，并开放系统防火墙或云安全组端口。
- DB service 内部系统 API 默认绑定 `127.0.0.1` 并自动选择空闲端口，由主进程代理 `/__aisys__/api/*`；不要把 `JUHE_AI_DB_SERVICE_HTTP_HOST` 暴露到公网。
- 新部署必须修改 `JUHE_AI_SECRET`，不要使用示例值；`NODE_ENV=production` 时默认开发密钥或短于 32 位的密钥会直接拒绝启动。
- `NODE_ENV=production` 时必须配置 `JUHE_AI_ALLOWED_ORIGINS`，只填写后台前端的完整 Origin，多个用英文逗号分隔；不要配置 `*`。
- 生产环境登录态 Cookie 默认启用 `Secure`，建议前端入口走 HTTPS；只有临时 HTTP 内网验证才显式设为 `JUHE_AI_COOKIE_SECURE=false`。
- `JUHE_AI_COOKIE_SAME_SITE` 默认 `lax`；如果前后端确实跨站部署并配置为 `none`，必须同时保持 `JUHE_AI_COOKIE_SECURE=true`。
- HTTPS 反向代理后如需 Express 识别代理协议，可把 `JUHE_AI_TRUST_PROXY` 设置为 `true` 或实际代理跳数；无反向代理时保持 `false`。
- 上游账户 `Base URL` 默认拒绝本机、内网、链路本地和保留地址；`NODE_ENV=production` 时不能启用 `JUHE_AI_ALLOW_PRIVATE_UPSTREAM_BASE_URLS`，也不能配置 `JUHE_AI_UPSTREAM_BASE_URL_PRIVATE_ALLOWLIST`。
- 复用当前业务库必须沿用原 `JUHE_AI_SECRET`。
- `JUHE_AI_SECRET` 改错会导致 OAuth token、上游 API Key、代理密码等敏感字段无法解密。
- `JUHE_AI_DATABASE_PATH` 只保存系统账户、AI 账户、分组、API Key、授权、设置和公告等业务数据。
- `JUHE_AI_DATASET_DATABASE_PATH` 保存审计、操作日志、运行日志索引、模型检测、清理目标和 usage shard 元数据；新写入的 `usage_records` 保存到 usage shard 文件。
- `JUHE_AI_STATS_DATABASE_PATH` 保存统计缓存、额度窗口、账号质量、系统监控、表监控历史和 `stats_job_state`。
- `JUHE_AI_USAGE_SHARD_ROOT` 保存使用记录 shard 文件；未配置或留空时默认跟随数据集目录库生成同级 `usage-shards`，也可以显式配置到独立目录。
- `JUHE_AI_USAGE_SHARD_COUNT` 默认 `16`；生产启用后不要直接改小。
- `JUHE_AI_AUDIT_FULL_BODY_CAPTURE_ENABLED` 默认 `false`，只决定服务启动后的全局 body 全量保全默认状态，不会把普通 `200 success` 改成 100% 审计；运行中优先在审计日志页面使用“临时全量捕获”弹窗短时定向配置，可选择指定 AI 账户、是否包含普通成功请求和有效期。默认仍按成功样本 `512KB`、问题链路 `2MB` 做 `summary_only` 摘要；命中临时捕获配置后原始审计 body 不做摘要化或流式正文省略，但凭据类 headers 仍脱敏保留，并继续受 blob 压缩去重、窗口读取和 `64MB` 活跃捕获硬上限约束。排查结束必须关闭页面配置，并确认环境变量不是 `true` / `1`。
- 三个 SQLite 路径必须指向不同文件；当前存储入口只使用业务库、数据集目录库、usage shard 目录和统计结果库。

## 5. 启动

### Windows

```powershell
pwsh .\start.ps1
```

### macOS / Linux

```bash
bash ./start.sh
```

启动脚本会：

- 检查 Node.js LTS 和 `node:sqlite` 可用性。
- 尝试通过 corepack 启用 pnpm。
- 缺少 `backend/.env` 时自动创建。
- 创建 `backend/data`。
- 首次安装目标平台生产依赖，并随依赖安装 `@vscode/ripgrep` 对应平台的 `rg` 二进制。
- Web/API/网关主进程会自动 fork 并看护独立 background worker 进程和 DB service 进程；后台任务在 worker 内完成，系统管理 API 与高频 SQLite 读写由 DB service 承接。

后台任务运行边界：

- Web/API/网关主进程只处理 HTTP 请求和必要的 worker 看护。
- 统计聚合、系统采样、运行日志索引维护、审计日志批量落库和清理任务必须在独立 background worker 进程内运行。系统管理 API、管理面 CRUD、公开设置读取、运行日志索引查询和网关数据库副作用必须经 DB service 执行。OpenAI OAuth 额度快照由真实网关响应头被动更新，不再依赖后台主动刷新任务。
- 部署验证不能只看 `/__aisys__/health`，还要确认 background worker 和 DB service 已启动并持续存活；否则管理 API、统计、日志索引和清理会受影响。

## 7. 常驻运行

重要：下面 PM2 示例直接启动 `backend/dist/server.js`，只适合已经先运行过 `pwsh ./start.ps1` 或 `bash ./start.sh`，并确认运行时预检、`backend/.env`、生产依赖和 `@vscode/ripgrep` 安装都已完成的发布包。首次部署或依赖变化后，仍应先执行启动脚本；如果绕过启动脚本，必须自行设置完整环境变量并执行 `pnpm install --prod --frozen-lockfile --filter juhe-ai-backend...`。`start.sh` 默认设置 `JUHE_AI_LOG_CONSOLE_ENABLED=false`，Windows `start.ps1` 则保留 `.env` / 外部环境里的日志设置。

### Windows

推荐：

- NSSM 注册 Windows Service。
- PM2 Windows 服务化方案。
- 任务计划程序开机启动 `pwsh -File start.ps1`。
- 常驻运行只需要守护 Web/API/网关主进程；主进程会 fork 并看护 background worker 和 DB service。不要把 `worker.js` 或 DB service 当成独立服务长期手动启动。

PM2 示例：

```powershell
npm install -g pm2
pm2 start .\backend\dist\server.js --name juhe-ai --cwd (Get-Location).Path
pm2 save
```

### macOS

推荐：

- launchd。
- PM2。
- Caddy/Nginx 反向代理。
- launchd / PM2 只需要守护 Web/API/网关主进程；主进程会 fork 并看护 background worker 和 DB service。
- 发布包 `start.sh` 默认 `JUHE_AI_LOG_CONSOLE_ENABLED=false`，普通运行日志写入 `backend/logs/` 滚动文件；launchd stdout 只保留启动脚本和极少量进程级输出。如需临时排障 stdout，可在守护配置里显式覆盖该环境变量。

PM2 示例：

```bash
npm install -g pm2
cd /你的路径/juhe-ai-release
pm2 start backend/dist/server.js --name juhe-ai --cwd /你的路径/juhe-ai-release
pm2 save
```

### Linux

推荐：

- systemd。
- PM2。
- Nginx/Caddy 反向代理和 HTTPS。
- systemd / PM2 只需要守护 Web/API/网关主进程；主进程会 fork 并看护 background worker 和 DB service。

PM2 示例：

```bash
npm install -g pm2
cd /你的路径/juhe-ai-release
pm2 start backend/dist/server.js --name juhe-ai --cwd /你的路径/juhe-ai-release
pm2 save
pm2 startup
```

systemd 示例：

```ini
[Unit]
Description=Juhe AI
After=network.target

[Service]
Type=simple
WorkingDirectory=/opt/juhe-ai-release
ExecStart=/usr/bin/env bash /opt/juhe-ai-release/start.sh
Restart=always
RestartSec=5
User=你的Linux用户
Environment=NODE_ENV=production

[Install]
WantedBy=multi-user.target
```

## 9. 数据备份和迁移

默认数据库：

```text
业务库：backend/data/juhe-ai.sqlite3
数据集目录库：backend/data/juhe-ai-dataset.sqlite3
统计结果库：backend/data/juhe-ai-stats.sqlite3
使用记录分片：backend/data/usage-shards/ 或 JUHE_AI_USAGE_SHARD_ROOT 指向的目录
审计 payload 文件：backend/data/audit/blobs/，短期排障数据，不纳入常规备份
```

必须备份：

```text
backend/.env
核心业务表数据
```

生产环境默认不做整库 SQLite 备份，避免把短期日志、审计 payload、用量明细、统计缓存、系统监控和运行索引一起带走，导致备份过大或长时间占用数据库锁。默认备份口径只包含可恢复业务配置和资源关系：

```text
system_accounts
global_settings
providers
proxy_profiles
accounts
system_teams
system_team_members
resource_authorizations
resource_authorization_sources
resource_authorization_grants
groups
group_accounts
api_keys
system_settings
announcements
announcement_reads
```

默认不备份这些可重建、可过期或排障类数据：usage shard 文件里的 `usage_records`、`audit_*`、`operation_log*`、`runtime_logs`、`usage_*` 统计缓存、`stats_job_state`、`group_account_stats`、`account_quality_*`、`system_metrics_*`、`account_usage_snapshots`、`database_storage_snapshots`、`table_storage_snapshots` 和 `backend/data/audit/blobs/`。`system_sessions` 虽然在业务库里，但属于短期登录态，常规备份也不需要单独导出；恢复时重新登录即可。数据集目录库、usage shard 目录、统计结果库和审计 payload 文件都可以丢弃、清空或重建；历史备份不保留审计原文。

审计详情里的 Headers / Body 原文不直接保存在 `audit_payload_refs` 行内，而是由数据集目录库中的 `audit_payload_blobs.storage_key` 指向 `backend/data/audit/blobs/` 下的外部文件。历史数据或常规备份里没有这些文件时，详情页只能看到 hash、大小和 blob 引用，这是预期结果。只有正在排查当前现场、且明确需要查看仍在保留期内的审计原文时，才临时复制同一时点的数据集目录库和 `audit/blobs` 目录作为一次性排障材料；这不属于备份流程，排查完成后按排障数据处理。

SQLite 删除记录后只把页放回 freelist，可复用但不会自动归还给文件系统；因此数据库文件变大后，即使数据保留任务已经清理完成，文件大小也可能不会立刻下降。如果业务库出现明显膨胀，应先停服务，再使用 `VACUUM INTO` 生成 compact 业务库并替换原文件。数据集目录库、usage shard 和统计结果库属于可重建数据域，优先按当前模型清空或重建，不在部署流程里执行历史表升级。

Windows 备份：

```powershell
New-Item -ItemType Directory -Force backups | Out-Null
Copy-Item .\backend\.env ".\backups\backend.env.$(Get-Date -Format yyyyMMddHHmmss)"
sqlite3 .\backend\data\juhe-ai.sqlite3 ".dump system_accounts global_settings providers proxy_profiles accounts system_teams system_team_members resource_authorization_grants resource_authorizations resource_authorization_sources groups group_accounts api_keys system_settings announcements announcement_reads" | Out-File -Encoding utf8 ".\backups\business-tables.$(Get-Date -Format yyyyMMddHHmmss).sql"
```

macOS / Linux 备份：

```bash
mkdir -p backups
cp backend/.env backups/backend.env.$(date +%Y%m%d%H%M%S)
sqlite3 backend/data/juhe-ai.sqlite3 ".dump system_accounts global_settings providers proxy_profiles accounts system_teams system_team_members resource_authorization_grants resource_authorizations resource_authorization_sources groups group_accounts api_keys system_settings announcements announcement_reads" > backups/business-tables.$(date +%Y%m%d%H%M%S).sql
```

当前版本固定使用业务库 / 数据集目录库 / usage shard / 统计结果库模式。新部署建议显式配置 `JUHE_AI_DATABASE_PATH`、`JUHE_AI_DATASET_DATABASE_PATH`、`JUHE_AI_STATS_DATABASE_PATH`、`JUHE_AI_USAGE_SHARD_ROOT` 和 `JUHE_AI_USAGE_SHARD_COUNT`，并确保三个 SQLite 文件路径互不相同。复用业务库时必须让库结构符合当前 schema；不符合时停服务离线修复或重建。数据集目录库、usage shard 目录和统计结果库可以新建或清空。

统计口径升级或统计缓存损坏时，必须停服务后显式执行统计重建。发布包和源码构建后都统一使用编译产物入口：

Windows：

```powershell
node .\backend\dist\scripts\maintenance\rebuild-usage-stats.js
```

macOS / Linux：

```bash
node ./backend/dist/scripts/maintenance/rebuild-usage-stats.js
```

说明：

1. 统计重建不是每次上线必跑，只在统计表、统计口径、授权消耗规则或额度窗口规则变化时执行。
2. 该脚本会清空并重建统计缓存、授权消耗报表和统计窗口快照，不删除系统账户、AI 账户、分组、API Key、授权关系或 usage shard 里的 `usage_records`。
3. 重建只能基于当前 usage shard 中仍保留的 `usage_records`；已经被丢弃或被保留策略清理掉的历史明细不能凭空恢复，统计会从后续新请求继续累计。
4. 执行前必须确认 `backend/.env` 里的数据库路径指向目标生产库，并先停掉 Web 和 background worker，避免重建期间继续写入统计游标。

切换部署时：

1. 解压新发布包。
2. 复制当前 `backend/.env` 到新发布包的 `backend/.env`，或按当前配置重新填写。
3. 业务库必须符合当前 schema；如不符合，停服务后用一次性离线 SQL / 脚本修复，或把当前业务表数据整理后导入新业务库。数据集目录库和 usage shard 目录按需要复制或丢弃，统计结果库可以直接清空或通过重建脚本再生成。
4. 如果当前部署需要按最新统计口径重建统计结果，先运行统计重建脚本。
5. 启动新服务。
6. 验证登录、账户、API Key、网关和管理员“表监控”页面。

## 10. 常见排障

- Node.js / `node:sqlite` 预检失败：切换到官方 Node.js LTS，当前支持 22.x LTS（>=22.13.0）或 24.x LTS（>=24.11.0）。
- `pnpm install` 失败：检查 npm registry 网络或代理配置。
- `grep 模式` 报找不到 `rg`：重新执行 `pnpm install --prod --frozen-lockfile --filter juhe-ai-backend...`，确认没有使用 `--ignore-optional` 或禁用 optional dependency。
- 页面能开但 API 失败：检查 `/__aisys__/api` 是否到同一后端。
- `/v1` 或根路径网关流式断开：反向代理关闭 buffering，并增大超时。
- 敏感字段无法解密：找回旧 `JUHE_AI_SECRET`。
- 端口外部访问失败：直连用 `JUHE_AI_HOST=0.0.0.0`，并开放防火墙/安全组端口。

## 11. 给 AI 的部署摘要

1. 先判断目标系统：Windows、macOS 或 Linux。
2. 检查 Node.js LTS、运行时预检、pnpm/corepack、端口、网络、磁盘和权限。
3. 按目标系统解压 zip 或 tar.gz。
4. 检查 `start.sh`、`start.ps1`、`backend/dist/server.js`、`frontend/dist/index.html`。
5. 创建并审阅 `backend/.env`。
6. 根据访问方式设置 `JUHE_AI_HOST`。
7. 确认 `JUHE_AI_SECRET`：新部署生成至少 32 位强随机值；复用当前业务库时沿用原值。
8. Windows 执行 `pwsh ./start.ps1`；macOS/Linux 执行 `bash ./start.sh`。
9. 验证 `/__aisys__/health`、`/__aisys__/api/health`、`/__aisys__/`。
10. 配置目标平台常驻运行。
11. 备份 `.env` 和核心业务表导出；数据集目录库、usage shard 目录和统计结果库按取证或迁移需要另行停服务备份。
12. 如果目标是 Docker 部署，改看 `docs/deploy/Docker部署指南.md`，并按 `docker/README.md`、`docker/compose.yml`、`docker/.env.example`、`docker/Dockerfile` 和 `docker/entrypoint.sh` 的说明执行。
