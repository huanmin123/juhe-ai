# 高性能模式压测报告

> 记录 `PostgreSQL + Redis` 高性能模式在 `192.168.1.203` 测试栈上的 System API 压测结果。本文不记录任何真实连接串或密码。

## 测试范围

- 被测链路：管理端 System API 的登录后读写链路，覆盖设置公开读取、当前用户、供应商、分组、AI 账户、API Key secret 和账号 PATCH。
- 存储模式：`JUHE_AI_RUNTIME_MODE=performance`、`JUHE_AI_DATABASE_DRIVER=postgres`、`JUHE_AI_CACHE_DRIVER=redis`、`JUHE_AI_RUNTIME_STATE_DRIVER=redis`、`JUHE_AI_QUEUE_DRIVER=redis_stream`。
- 中间件：远端 Docker PostgreSQL / PgBouncer / Redis cache / Redis state。
- 压测脚本：`pnpm --filter juhe-ai-backend test:performance-system-api-load`。

## 正式结果（相同模型配置校验短路后）

执行时间：2026-06-26 21:31:54 至 21:32:38（Asia/Shanghai）。

本轮优化：

- 账号 PATCH 请求里 `groupId` 与当前绑定分组一致时，不再重复执行分组校验和分组重绑。
- 网关运行时缓存失效携带 `reason`；`account_updated` 只清网关运行时缓存，不再误清 `system_settings` 仓储缓存。
- `settings_updated` 和无 `reason` 的兼容清理仍会清 `system_settings` 仓储缓存，避免设置更新后读到旧值。
- 账号 PATCH 提交的 `supportedModels` / `modelMappings` 归一化后与当前值完全一致时，直接复用当前配置，不再重复查询 provider catalog / 跨协议模型池。

## 被压测否决的优化

尝试过“账号 UPDATE 按 payload 动态省略凭据列”。该方案在类型检查和功能回归上可通过，但压测变差，已回滚：

结论：这类动态 SQL 形态可能破坏 PostgreSQL statement 复用和执行稳定性，实际收益不成立。后续账号主表写入优化必须继续以压测结果为准，不能只按“少写字段”直觉推进。

## 探索性风险

### 查询 / 搜索 / 筛选索引边界

2026-06-26 已补做一轮列表、搜索、筛选、分页窗口和统计 fan-out 守护检查。通过项：

- API Key 列表：搜索只按名称精确 / 前缀匹配，列表不返回完整密钥。
- AI 账户列表：搜索只按账户名称精确 / 前缀 / 词项索引候选包含匹配，不裸扫 `accounts` 主表；分组使用独立筛选。
- 使用记录列表：`model` 精确匹配，`clientIp` 前缀范围匹配；候选窗口先读 usage catalog 固定窗口，再按当前页 ID 回 usage shard 补详情。
- 审计 / 操作 / 运行日志：结构化过滤避免前导通配符，操作日志摘要搜索走倒排词项索引；深翻页 offset / 合并窗口限制在 1000 行级别。
- 基础管理列表：API Key、账户、分组、用户、代理、公告、外部来源、团队、统一授权和授权用量详情 offset 均限制在 1000 行内。
- 授权候选项、账号用量、授权用量：候选项支持精确 / 前缀搜索和 limit；账号用量先解析账号 ID，窗口查询不接收前导通配符；授权用量按窗口分页。
- 统计聚合：基础统计 upsert statement 在 batch 内复用；usage stats / client IP stats 单次聚合只访问有界 shard 窗口并轮转推进。
- 数据维护：删除清理、详情读取和过期清理查询使用目标索引并避免临时排序；网关 API Key 路由绑定读取固定 20 条窗口并命中路由索引。

### 管理端在途请求阈值

探索压测中 `systemApiDbServiceMaxInFlight=64` 时，`100` 并发多账号压测出现 `system_api_busy` 503，错误率约 39.62%。这不是 PostgreSQL 死锁，而是应用层管理端入口保护提前拒绝。

已改为环境变量 `JUHE_AI_SYSTEM_API_DB_SERVICE_MAX_IN_FLIGHT`，standalone 默认 `64`，performance 默认 `256`。生产高性能模式仍需配合 `JUHE_AI_DB_POOL_MAX`、PgBouncer pool 和机器资源压测后再调整。

### 单热点账号写入

探索压测中把 15% 写请求全部打到同一个账号时，出现明显行锁排队：HTTP 503 错误率约 69.29%，最大事务时长约 21.52s，最大 active query 时长约 21.51s，最大 lock waiters 48。

这说明 PostgreSQL 消除了 SQLite 文件级写锁，但不能消除热点行竞争。生产队列和管理操作应避免大量并发写同一账号；如果后续确实存在同一资源高频状态写入，需要按资源维度串行、合并写入或拆分轻量运行态字段。
