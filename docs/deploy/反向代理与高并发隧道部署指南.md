# 反向代理与高并发隧道部署指南

> 本文是公网 Edge、家庭 / 内网回源、高并发长连接、WireGuard、Caddy / Nginx 和系统参数的权威部署入口。具体生产 IP、域名、密钥、端口清单和容量结果必须保存在私有运维记录中，不写入仓库。

## 1. 推荐结论

高并发、长连接、SSE 流式转发且应用位于家庭宽带或内网时，推荐固定为：

```text
客户端
  -> 公网 Edge：Caddy layer4，监听 80/443，TCP/TLS 透传，HTTPS 发送 PROXY v2
  -> WireGuard 点对点隧道
  -> macOS / 内网入口：Caddy，在 8081/8443 终止 HTTP/TLS 并接收 PROXY v2
  -> Nginx 流式反代
  -> juhe-ai
```

这条链路的边界是：

- 公网 Edge 不终止业务 TLS，只做四层转发；证书和域名路由由回源节点 Caddy 管理。
- WireGuard 是唯一允许的公网回源数据面；不得配置其他回源协议或单 TCP 回源方案。
- HTTPS 入口通过 PROXY v2 传递客户端源地址；回源 Caddy 只信任精确的 Edge WireGuard `/32`。
- systemd / launchd 负责进程常驻。默认不部署会自动重启应用的外部 watchdog；外部探针默认只告警，避免与发布和受控重启冲突。
- 本文参数是已验证的保守起步值，不是容量承诺。是否继续调大，由分档压测和指标增量决定。

如果应用和公网入口在同一台服务器，直接使用 `Caddy HTTPS -> 127.0.0.1:3000`，不需要 WireGuard、layer4 或 PROXY protocol。

## 2. 两种入口模式不能混用

| 模式 | TLS 终止位置 | Edge 配置 | 适用场景 |
| --- | --- | --- | --- |
| HTTP 反向代理 | 公网 Edge | 标准 Caddy `reverse_proxy` | 应用与 Edge 同机，或已有可信 HTTP 回源 |
| L4 TLS 透传 | 家庭 / 内网 Caddy | Caddy layer4 TCP proxy，HTTPS 发送 PROXY v2 | 公网 Edge + WireGuard 回源，高并发长连接 |

同一个 `443` 入口只能选择一种模式。不要一边让 Edge 终止 TLS 并写 `reverse_proxy`，一边又要求回源 Caddy 接收原始 TLS 和 PROXY v2。本文后续配置均按 L4 TLS 透传模式说明。

## 3. 组件与信任边界

| 层级 | 职责 | 不负责 |
| --- | --- | --- |
| 公网 Edge Caddy | 接收公网 TCP、发送 PROXY v2、转发到 WireGuard peer | 不解密业务 TLS，不伪造健康成功 |
| WireGuard | 提供独立 UDP 加密数据面 | 不提供 HTTP 健康语义，不替代应用压测 |
| 回源 Caddy | 接收 PROXY v2、终止 TLS、维护证书、转发 HTTP/SSE | 不信任宽泛来源网段 |
| Nginx | 现有入口下的长连接、上传和流式转发 | 不缓存 `/v1` 流式响应 |
| juhe-ai | 鉴权、路由、网关和后台业务 | 不直接暴露公网监听端口 |

公网只开放 Edge 的 `80/tcp`、`443/tcp` 和 WireGuard UDP 端口。回源节点的 Caddy、Nginx 和 juhe-ai 端口只绑定 loopback 或精确 WireGuard 地址。

## 4. WireGuard 基线

### 4.1 地址和 peer

- 每条点对点隧道使用独立小网段；接口地址可用 `/30`。
- peer 的 `AllowedIPs` 只写对端隧道 IP `/32`，不要使用 `0.0.0.0/0` 或接管系统默认路由。
- MTU 从 `1380` 起步，并通过长响应、上传和不同网络路径验证；出现分片或特定尺寸卡顿时再向下调整。
- NAT 后的家庭 / 内网 peer 设置 `PersistentKeepalive = 25`。
- 私钥只在目标机器生成，权限设为 `0600`；仓库、工单、聊天和日志都不得保存私钥。

Edge 示例结构：

```ini
[Interface]
Address = <EDGE_WG_IP>/30
ListenPort = <WG_UDP_PORT>
PrivateKey = <EDGE_PRIVATE_KEY>
MTU = 1380

[Peer]
PublicKey = <HOME_PUBLIC_KEY>
AllowedIPs = <HOME_WG_IP>/32
```

家庭 / 内网节点示例结构：

```ini
[Interface]
Address = <HOME_WG_IP>/30
PrivateKey = <HOME_PRIVATE_KEY>
MTU = 1380

[Peer]
PublicKey = <EDGE_PUBLIC_KEY>
Endpoint = <EDGE_PUBLIC_IP>:<WG_UDP_PORT>
AllowedIPs = <EDGE_WG_IP>/32
PersistentKeepalive = 25
```

尖括号字段都是占位符，不得原样执行。

### 4.2 生命周期

Linux Edge 使用 `wg-quick@<接口名>.service` 交给 systemd 管理。验证不只看 unit 状态，还要检查接口、路由、最近握手和收发计数。

macOS 使用 wireguard-go / wg-quick 时，逻辑接口名可能映射为真实 `utun`。运维脚本应读取 `/var/run/wireguard/<逻辑名>.name` 获取实际接口，停止时执行 `wg-quick down` 并确认 utun、路由、socket 和映射文件已清理，再重新 bootstrap。不要只用逻辑名判断 `wg show`。

旧 Linux 内核无法加载 WireGuard 内核模块时，只允许使用从 WireGuard 官方源码固定提交构建并记录 SHA-256 的 `wireguard-go`。不得下载来源不明的预编译二进制；systemd 必须继续托管 `wg-quick@<interface>`，并通过真实握手、传输计数和 HTTP/TLS 请求确认用户态实现可用。

每次重建至少验证：

1. Edge 与回源节点能互 ping 隧道地址。
2. `wg show` 的 latest handshake 持续更新，传输计数随请求增长。
3. Edge 能访问对应 WireGuard listener 的 HTTP/TLS 端口。
4. 停止并重新启动服务后，旧接口和旧路由没有残留。
5. 重启主机后，接口、路由、握手和监听均恢复。

### 4.3 五 Edge 正式拓扑

生产环境固定按五个 Edge 节点建设，五个节点均使用同一套 WireGuard/Caddy 正式配置规范；不保留临时节点、临时入口或协议兼容节点。每个 Edge 必须独立分配以下资源：

| 资源 | Edge-01 | Edge-02 | Edge-03 | Edge-04 | Edge-05 |
| --- | --- | --- | --- | --- | --- |
| WireGuard 网段 | 独立 `/30` | 独立 `/30` | 独立 `/30` | 独立 `/30` | 独立 `/30` |
| 公网 UDP 端口 | 独立端口 | 独立端口 | 独立端口 | 独立端口 | 独立端口 |
| Edge peer 地址 | 唯一 `/32` | 唯一 `/32` | 唯一 `/32` | 唯一 `/32` | 唯一 `/32` |
| 回源 listener | 独立地址 | 独立地址 | 独立地址 | 独立地址 | 独立地址 |

回源节点上的每个 WireGuard 地址都必须声明独立的 Caddy HTTP/TLS listener，并只允许对应 Edge peer `/32`；禁止把多个 Edge 合并到通配 listener 或共享一个 peer。正式发布前逐个验证五个握手、传输计数、HTTP/TLS、SSE 和真实客户端地址，任一 Edge 未通过都不得宣称集群完成。

## 5. Caddy 模块和配置边界

标准 Caddy 安装包通常只覆盖 HTTP 反向代理。本文的 Edge layer4 和回源 `listener_wrappers.proxy_protocol` 需要相应模块；安装前先确认实际二进制：

```bash
/path/to/caddy version
/path/to/caddy list-modules --packages --versions | grep -E 'layer4|proxy_protocol'
```

缺少模块时，使用项目认可的自定义 Caddy 构建和固定版本。不要把标准软件源安装步骤当成已经包含 layer4 / proxy_protocol。验证、adapt、reload 和 systemd / launchd 必须引用同一个绝对路径的 Caddy binary：

```bash
/path/to/caddy list-modules --packages --versions
/path/to/caddy adapt --config /path/to/Caddyfile --pretty
/path/to/caddy validate --config /path/to/Caddyfile
```

caddy-l4 上游明确提示仍可能有破坏性变化，因此生产应固定已经验证的 Caddy binary、模块版本和校验值，不自动跟随最新构建；升级先验证候选配置和回滚门禁。

### 5.1 Edge layer4

Edge 的目标行为是：

```text
:80  TCP -> <HOME_WG_IP>:8081
:443 TCP + PROXY v2 -> <HOME_WG_IP>:8443
```

具体 Caddyfile 语法以锁定的 layer4 模块版本为准。写入服务前必须用运行中的同一 binary 完成 `adapt` 和 `validate`，再在对应 WireGuard listener 抓取一次连接验证 `443` 确实发送 PROXY v2。不要把 HTTP `reverse_proxy` 配置复制到这一层。

### 5.2 回源 Caddy

回源 HTTPS listener 只绑定精确 WireGuard 地址。PROXY wrapper 必须在 `tls` 之前，并且只允许 Edge peer `/32`：

```caddyfile
{
    admin off
    default_bind <HOME_WG_IP>
    http_port 8081
    https_port 8443

    servers <HOME_WG_IP>:8443 {
        listener_wrappers {
            proxy_protocol {
                timeout 5s
                allow <EDGE_WG_IP>/32
                fallback_policy require
            }
            tls
        }
    }
}

http://ai.example.com {
    redir https://ai.example.com{uri} 308
}

https://ai.example.com {
    reverse_proxy 127.0.0.1:3099 {
        flush_interval -1
    }
}
```

关键约束：

- `allow` 不得写 `0.0.0.0/0`、整个家庭局域网或整个隧道地址段。
- `fallback_policy require` 防止没有 PROXY v2 时静默记录成 Edge / 隧道地址。
- 普通公网请求不得绕过 Edge 直连这个 listener。
- 不建立其他协议的回退 listener；入口回滚只恢复已验证的上一版 WireGuard/Caddy 配置。
- DNS 指向公网 Edge，`80` 和 `443` 都必须透传到回源，才能维持自动 HTTPS 的完整链路。
- 多个 Edge 使用多个 WireGuard 地址时，为每个 `<HOME_WG_IP>:8443` 单独声明 `servers` listener 和对应 `<EDGE_WG_IP>/32`；不要把多个来源合并成 `servers :8443` 通配配置。

## 6. Nginx 与流式转发基线

已有 Nginx 运维层时，使用下面的长连接基线；没有 Nginx 需求时，回源 Caddy 可以直接转发 juhe-ai，避免无必要的代理层。

主配置起步值：

```nginx
worker_processes auto;
worker_rlimit_nofile 65536;

events {
    worker_connections 16384;
}
```

站点配置：

```nginx
location / {
    proxy_pass http://127.0.0.1:3000;
    proxy_http_version 1.1;
    proxy_set_header Connection "";
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;

    proxy_buffering off;
    proxy_request_buffering off;
    proxy_cache off;
    proxy_socket_keepalive on;
    proxy_read_timeout 3600s;
    proxy_send_timeout 3600s;
}
```

Nginx 服务本身也要有至少 `65536` 的文件句柄上限，否则 `worker_rlimit_nofile` 单独配置不会生效。不要无证据开启 `multi_accept on`；它不是长连接容量门禁，并可能放大瞬时 accept 抢占。

## 7. Linux Edge 系统基线

保守起步值：

```sysctl
net.core.somaxconn = 4096
net.ipv4.tcp_max_syn_backlog = 4096
```

写入独立的 `/etc/sysctl.d/` 文件后执行 `sysctl --system`，并用 `sysctl net.core.somaxconn net.ipv4.tcp_max_syn_backlog` 复核实际值。

Caddy systemd override：

```ini
[Service]
LimitNOFILE=1048576
```

执行 daemon-reload 和受控重启后，用实际 Caddy PID 的 `/proc/<PID>/limits` 验证，而不是只看 unit 文件。

BBR + fq 只在当前内核明确支持时启用。先检查可用 congestion control 和 qdisc；旧内核不支持时保留现有 cubic / pfifo_fast，不得把“未启用 BBR”当成发布失败。

以下参数不做全节点无条件统一：

- UDP `rmem_max` / `wmem_max`：只在 WireGuard 压测期间 UDP buffer error 增长时调整。
- `netdev_max_backlog`、softnet budget、IRQ/RPS：只在区间采样出现 drop、time_squeeze 或单核 softirq 持续打满时调整。
- conntrack：先确认链路确实经过 conntrack，并观察使用量接近上限后再调整。

## 8. macOS 回源节点基线

内核起步值：

```text
kern.ipc.somaxconn=4096
kern.maxfiles=524288
kern.maxfilesperproc=131072
```

macOS 重启后不保证自动保留这些值。使用 root LaunchDaemon 在开机时设置，并在每次重启后执行 `sysctl` 复核。launchd 没有严格依赖排序，因此还要继续检查 Caddy、Nginx、Node 和 WireGuard 是否在参数生效后正常监听。

每个 Caddy、Nginx、Node 和 WireGuard LaunchDaemon / LaunchAgent 都显式设置：

```xml
<key>SoftResourceLimits</key>
<dict>
  <key>NumberOfFiles</key>
  <integer>65536</integer>
</dict>
<key>HardResourceLimits</key>
<dict>
  <key>NumberOfFiles</key>
  <integer>131072</integer>
</dict>
```

plist 只影响新进程。修改后必须受控重启服务，并检查 live PID 的实际 limits；不能看到 plist 已更新就判定生效。

macOS Application Firewall 保持启用。自定义或 xcaddy 构建的 Caddy binary 如果未签名，可能出现 TCP 三次握手成功、收到首个应用数据包后立即 RST；应先备份 binary，执行本机 ad-hoc 签名，再把同一个绝对路径加入防火墙允许列表并重启 Caddy。签名或替换 binary 后必须重新验证版本、模块、SHA-256、HTTP、TLS 和 PROXY v2。

### 8.1 launchd 受控替换

Caddy 的长连接优雅退出可能长时间等待。如果执行 `launchctl bootout` 的 SSH 会话或发布脚本中断，后续 bootstrap 可能永远没有执行，应用会留在停止状态。

生产替换顺序：

1. 先验证新 plist、Caddyfile / Nginx 配置和 binary，保存旧 plist 与当前服务状态。
2. 在 `bootout` 前启动一次性、有超时和日志的恢复助手；它只负责发现目标 job 已退出后 bootstrap 已验证的 plist。
3. 执行 `bootout`，有界等待旧 job 和监听退出，再 bootstrap 新 job。
4. 验证 health、监听、实际资源上限、WireGuard 握手和请求链路。
5. 任一步失败时恢复旧 plist 并重新 bootstrap，验证旧链路恢复。
6. 成功后清理一次性助手、PID 和临时日志。

恢复助手不是长期 watchdog，不循环探测或反复重启应用。发布脚本也不能无限等待 Caddy 的长连接优雅退出。

## 9. 上线与回滚

### 9.1 上线前

- 备份 Caddyfile、Nginx 配置、systemd override、launchd plist、WireGuard 配置和 sysctl 文件。
- 对所有配置执行静态验证；私钥和敏感配置不进入备份仓库。
- 先在未承载公网流量的正式 WireGuard listener 上完成候选配置验证，公网 `80/443` 保持当前正式配置。
- 分层验证每个 Edge listener、WireGuard 握手、回源 listener、TLS、PROXY v2、Nginx 和 juhe-ai health。

### 9.2 业务验证

至少覆盖：

- 后台页面与 health。
- OpenAI 兼容短请求。
- SSE 首字、持续输出、60 秒以上长连接和客户端取消。
- 请求体上传与大响应。
- 两个不同公网来源的真实客户端 IP。
- 强制命中每一个 Edge IP 的请求；只测 DNS 默认命中不代表所有节点可用。

### 9.3 公网切换

所有正式 Edge 独立验证通过后再确认公网切换。切换后至少观察 30 分钟。回滚只恢复已验证的上一版 WireGuard/Caddy 配置。

## 10. 高并发容量门禁

突发和渐进是两种不同测试：

- 瞬时突发：验证 accept、队列、文件句柄和短时 CPU 峰值。
- 渐进加压：验证稳态连接数、SSE、重传、延迟和资源增长。

建议从低档开始逐级验证短请求与长连接，再按业务目标扩到 `500 -> 1000` 或更高。某一档最终全部返回，不等于该档达到业务容量；成功率、首字延迟、p95 / p99 和业务 SLO 必须同时达标。

每档比较压测前后增量：

- WireGuard handshake、收发字节和 UDP buffer errors。
- TCP listen overflow / drop、重传、持续 Send-Q。
- softnet drop / time_squeeze 和单核 softirq。
- Caddy / Nginx / Node 的 FD，门禁建议低于实际上限的 70%。
- CPU、RSS、事件循环延迟、应用错误和基础设施断连。

出现基础设施断连、listen overflow、UDP buffer error、持续重传、FD 超门禁或延迟超过 SLO 时，不得切公网。具体压测结果与容量结论写入 `docs/reports/`，本文只维护方法和边界。

## 11. 日常排障顺序

按层检查，避免“客户端访问不了”就重启应用：

1. DNS 是否命中预期 Edge IP，Edge `80/443` 是否监听。
2. Caddy layer4 是否加载正确模块，连接是否到达目标 peer。
3. WireGuard 是否有新握手和流量增量，路由与 MTU 是否正常。
4. 回源 Caddy 是否收到 PROXY v2，证书与 TLS 是否正常。
5. Nginx 是否监听、是否有 upstream timeout / reset。
6. juhe-ai health、进程拓扑、文件句柄和事件循环是否正常。
7. 最后才判断是否需要由 systemd / launchd 受控重启对应服务。

“进程存在、端口监听、ping 可通”都不等于数据面可用。WireGuard 必须结合 handshake、流量增量和真实 HTTP/TLS/SSE 请求验证。
