# 集群上线与开发兼容指南

> 状态：2026-11-06 随 [PLAN-20261106T163123672Z](../plans/计划-20261106T163123672Z-多节点发布基建改造.md) 建立；2026-11-07 dev 双机演练验收，部署物完全隔离在 [`docker/cluster/`](../../docker/cluster/README.md)。当前生产仍是单机 Docker；本文的滚动 / contract 步骤在集群形态可用，生产切换前需用户重新确认。命令以 `docker/cluster/README.md` 与 `maintenance upgrade` 现行契约为准，不再使用不存在的 `deploy.sh rolling|contract`。
>
> 目标契约见 [多节点部署与不停机发布设计](../functions/多节点部署与不停机发布设计.md)；本文只回答两件事：**集群上线怎么做**、**开发需求阶段必须评估什么**。

## 1. 先决策：这次发布能不能停

```text
是单机部署吗？
├─ 是 → 允许停写 → 走单机窗口（§3）
│        不需要新旧结构并存，但仍禁止运行时代码双载体。
└─ 否（集群）
   ├─ 能接受一次停写窗口吗？
   │  ├─ 能 → 走停写窗口（§3 的等价集群流程）
   │  └─ 不能 → 必须无感 → expand / switch / contract（§2）
   └─ 变更是不是大改（改类型/改名/删字段/删表/拆表/改主键）？
      ├─ 允许停机 → 优先停写窗口，不要为了大改硬做滚动灰度
      └─ 必须无感 → §2.6 的大改流程，成本最高
```

判断原则：

- **小改**（加可空列、加表、加索引、加约束）→ 常规 expand，成本低。
- **大改**（改类型、改名、删列、删表、拆表、改主键、改分区）→ 滚动灰度需要双写/回填/两段发布，成本远高于一次停写窗口；**条件允许停机时优先停写**。
- 只有“业务不能停”且“变更必须上”同时成立时，才走大改的无感流程。

## 2. 集群上线

### 2.1 发布前检查（所有类型）

| 检查 | 要求 |
| --- | --- |
| 版本 | 镜像 tag 不可变（git sha/CalVer）；记录发布 tag 与 schema revision |
| 配置 | 每台 `maintenance check-config` 通过，与模板无 diff |
| 部署级一致性 | `JUHE_AI_SECRET` 同值；Redis namespace/URL 同源；DSN 同主库或同 VIP；`JUHE_AI_TRUST_PROXY` 按 LB 层数；时钟 NTP 同步；实例 ID 唯一 |
| 容量 | 滚动期间至少 N-1 台承载峰值；N=2 且余量不足时先扩到 3 台 |
| 时间 | 避开每日备份窗口（当前 04:00–07:00） |
| 备份 | 有本次发布可恢复的整库备份，`pg_restore -l` 校验可读 |
| 观测 | 已有按 `version` 维度的请求量/5xx/P99；无指标不允许灰度 |
| 回滚 | 上一 tag 镜像可取；回滚命令已确认 |

### 2.2 常规发布（无 schema 变更）

```text
1. CI 构建镜像，推送镜像仓库（tag = git sha）
2. 逐台 gateway：LB 摘流 → docker compose pull gateway → up -d
   → /health ready → LB 接回
3. jobs：停旧 leader → 起新 → leader 接管 → 健康检查
4. 验证：/v1 错误率、P99、SSE/WS 断流、jobs 滞后
```

约束：

- 一次只动一台 gateway；不要同时摘两台。
- jobs 与 gateway 必须同批发布；spool JSON 契约在一个窗口内向后兼容（只加字段、不删字段），否则先停旧 jobs 再起新 jobs。
- 管理面允许短暂 502；`/v1` 只允许既有错误语义（上游失败、长流断流重试）。

jobs 全局 leader（2026-11-07 起）：

- 两副本可同时启动；仅持有 `background_job_leases` 全局租约的副本执行任务，另一副本 `/health` 返回 `leader=false`、`ready=false` 且任务记录为 `skipped`，这是正常 standby。
- 确认 leader：`/health` 的 `leader`、`leaderStatus.ownerId`/`leaseUntil`；租约 TTL 30s、每 10s 续租。
- 旧 leader 失租/续租失败会主动退出进程；compose 必须配置 `restart: unless-stopped`（或等效），新 leader 在 ≤30s 内接管。
- 发布 jobs 时先停旧 leader，再启动新副本；不要在旧 leader 仍持租约时强制启动另一个并期待立即接管。

### 2.3 带 schema 变更：expand（在线）

```text
0. 新版 maintenance 镜像就绪；J3a/J3b/J2 bootstrap 已含在 upgrade 的 revision 1/2/3，无需另跑 --apply-*（仅独立修复/补表时使用）
1. maintenance upgrade --phase=expand --online --dsn "$JUHE_AI_POSTGRES_URL" --secret "$JUHE_AI_SECRET"
2. 核对报告：onlineSafe / compatibleBinaryRange / pending 步骤 / lock 风险
3. 逐台滚动 gateway（同 §2.2）
4. 更新 jobs（先停旧 leader）
5. 灰度 10% → 50% → 100%，观察错误率、双写差异、回填进度
6. 旧二进制仍可启动，作为回滚路径
```

expand 期间允许写者存活，但必须满足：

- 只做在线安全 DDL：可空列/常量默认列、`CREATE INDEX CONCURRENTLY`、`ADD CONSTRAINT ... NOT VALID`；
- 分区表索引不能直接 `CONCURRENTLY`：maintenance 会先 `CREATE INDEX ... ON ONLY parent`，再逐分区并发建索引并 `ATTACH PARTITION`；当前只支持一级分区，二级分区会显式报错，需在上线前拆分或停写处理；
- 回填分批、幂等、可暂停，有批次上限和限速；
- 锁等待超时（`lock_timeout`）不推进账本，重试或回退；
- 旧实例在 expand 中断时允许重启（门禁 1a），但新实例要求 expand 完成。

### 2.4 switch（切换读路径）

switch 不是数据库命令，是**新代码只读新结构**的发布：

```text
1. 新代码只读新列/新表；双写/触发器继续保留
2. 灰度 10% → 50% → 100%
3. 确认旧版本请求数 = 0、旧实例心跳消失
4. 此时才允许进入 contract
```

双写必须保留到 contract 完成；提前关双写会让旧实例写入的数据丢失在新结构里。

### 2.5 contract（删旧结构）

前置条件（全部满足）：

1. 旧 gateway 与旧 jobs 请求数 = 0，持续 ≥30min；
2. 双写/触发器观察窗（建议 24h）差异 = 0；
3. 回填完成，行数/抽样/checksum 校验通过；
4. 可恢复备份完成并验证；
5. 无长事务、复制槽延迟正常、磁盘/WAL 余量足够。

```text
1. deploy.sh contract（自动校验旧版本请求=0）
2. 备份 + pg_restore -l 校验
3. maintenance upgrade --phase=contract --old-writers-drained --backup-confirmed
   （设置 lock_timeout；删列/删表通常是秒级元数据操作）
4. 只有不可逆数据清退才停写并追加 --stop-write-confirmed
5. 验证结构、约束、业务读写；旧备份是本阶段唯一回滚载体
```

contract 后旧二进制会被门禁拒绝；回滚只能恢复备份或前向修复。

### 2.6 大改专项

| 变更 | 允许停机（推荐） | 必须无感 |
| --- | --- | --- |
| 改字段类型 | 停写窗口一次改完；先备份 | 新列 + 双写/触发器 + 回填 + 切读 + contract |
| 改字段名 | 停写窗口 `RENAME` | 新列 + 双写；或基表改名 + 旧名视图（旧连接需独立 `search_path`） |
| 删字段 | 停写窗口 `DROP COLUMN` | 只能 contract：旧实例=0 + 备份 + 低峰 |
| 删表 | 停写窗口 `DROP TABLE`；先查外键/视图依赖 | 只能 contract：旧实例=0 + 备份 + 依赖清理 |
| 拆表/合表 | 停写窗口重建 | 新表 + 双写 + 回填 + 切读 + contract |
| 改主键 | 停写窗口重建 | 极高风险，通常改走双库蓝绿或短窗口 |

大改的通用纪律：

- 旧实例仍存活时，禁止 `RENAME COLUMN`、`ALTER COLUMN TYPE`、`DROP COLUMN/TABLE`、加严格约束。
- `NOT VALID` 只跳过存量行，新写入仍校验；旧代码写旧值时，新约束必须允许旧值，或触发器把旧值映射成新值。
- 删除/改名必须等旧实例全部下线；没有“先删了，旧实例会自己好”这回事。

### 2.7 回滚

| 阶段 | 回滚方式 |
| --- | --- |
| expand 后、新二进制未上线 | 无需回滚；旧二进制仍可启动 |
| 新二进制已滚动、contract 未执行 | 回退镜像到旧 tag；旧结构仍在、双写仍在 |
| contract 执行前失败 | 旧结构仍在，回退镜像或重跑 contract |
| contract 成功后 | 只能恢复备份或前向修复 |

### 2.8 发布后验证

- 按 `version` 维度的 5xx/P99 回到基线；`juhe_ai_build_info` 能列出各实例的 `version`/`schema_revision`/`instance_id`，HTTP 请求量/耗时/在途指标带 `version` 标签；
- 旧版本请求数持续为 0（进入 contract 后）；
- spool 追平，无 `usage_record_spool_drain_unwired`；
- jobs leader 唯一，任务滞后正常；
- 审计/操作日志双实例写入正常；
- 双写差异 = 0（如处于双写期）。

## 3. 单机上线窗口

单机允许停机，**不需要**新旧结构并存，也不需要为旧实例保留兼容。

```sh
docker compose stop gateway jobs
DUMP=backup/juhe_ai-pre-upgrade-$(date +%Y%m%d-%H%M).dump
docker exec juhe-ai-postgres pg_dump -U juhe_ai -Fc juhe_ai > "$DUMP"
docker exec -i juhe-ai-postgres pg_restore -l >/dev/null < "$DUMP" && echo backup-ok
docker compose --profile tool run --rm maintenance upgrade \
  --phase=all --stop-write-confirmed --backup-confirmed \
  --dsn "$JUHE_AI_POSTGRES_URL" --secret "$JUHE_AI_SECRET" </dev/null
docker compose up -d gateway jobs
docker compose ps && bash verify-release.sh
```

单机注意：

- 备份必须在 DDL 之前完成并验证可读；
- 大改可以直接改结构，但**代码与结构同批切换**；运行时代码仍禁止“双列读/旧列回落”；
- 回滚 = 恢复备份 + 回退镜像；contract/删除类变更不可逆。

## 4. 开发阶段评估（需求评审必填）

任何需求进入开发前，必须回答下表。没有评估结论的需求不得进入实现。

### 4.1 需求评估表

| 维度 | 必答问题 | 结论/动作 |
| --- | --- | --- |
| 部署形态 | 单机、集群，还是两者都要支持？ | 决定走停写窗口还是 expand/contract |
| 表结构 | 加列/加表/改类型/改名/删列/删表/加约束/加索引/改分区？ | 列出变更类型与兼容策略 |
| 旧实例 | 发布窗口内旧代码是否还会读写这些表/列？ | 会 → 旧结构必须保留到旧实例下线 |
| 数据回填 | 数据量、批次、转换失败行、幂等、限速、WAL/磁盘 | 设计回填与校验 |
| 缓存/会话 | 新增状态放哪里？Redis/PG/进程内？多节点是否共享？TTL、失效？ | 集群必须共享；进程内只能可丢失的性能缓存 |
| 后台任务 | 是否新增 jobs 任务？单活/租约/重复执行/积压？ | 集群必须 leader 或租约 |
| 共享文件 | spool/日志/上传是否跨机？ | 集群必须 NFS/对象存储 |
| API/前端 | 管理面 API 是否变化？前端资源版本？ | 同批发布或兼容一个窗口 |
| 配置 | 新增 env、默认值、必填、每实例唯一？secret？ | 更新 check-config 与部署文档 |
| 观测 | 版本指标、错误率、回填进度、双写差异？ | 发布门禁需要 |
| 回滚 | 旧二进制能否运行？是否需要备份？ | 写入回滚矩阵 |
| 发布方式 | 停写窗口还是滚动灰度？谁执行？窗口？ | 写入计划 |

### 4.2 单机 vs 集群

| 能力/变更 | 单机（允许停写） | 集群（无感） |
| --- | --- | --- |
| 加列/加表 | 直接加，停写窗口 | expand，旧结构可运行 |
| 改类型 | 停写窗口直接改 | 新列 + 双写 + 回填 + contract |
| 改字段名 | 停写窗口 `RENAME` | 新列 + 双写；或旧名视图 |
| 删字段/删表 | 停写窗口直接删 | contract：旧实例=0 + 备份 |
| 缓存/会话 | 进程内可接受 | 必须 Redis/PG，跨节点共享 |
| 额度/限流 | 进程内可接受 | 必须 Redis 原子计数 |
| 后台任务 | 单实例 | jobs 单活/租约 |
| spool/日志 | 同宿目录 | NFS/对象存储 |
| 前端 | 跟随后端同批 | 独立托管/版本化 |

### 4.3 需求文档必须写清

1. 变更类型（表/缓存/会话/任务/文件/API/配置）。
2. 发布方式：单机停写，还是集群 expand/switch/contract。
3. 旧实例在窗口内是否可运行；需要保留哪些旧结构。
4. 回填/双写/校验方案与失败处理。
5. 回滚方式与不可逆点。
6. 验证证据（指标、SQL、演练）。

### 4.4 禁止项

- 旧实例存活时直接 `RENAME COLUMN` / `ALTER COLUMN TYPE` / `DROP COLUMN/TABLE` / 加严格约束。
- 依赖 `NOT VALID` 让旧代码写旧值通过。
- 用进程内 map 承载跨节点会话、额度、限流、验证码、WS 连接计数。
- 双写只覆盖部分写路径，且没有差异校验。
- 未备份就执行 contract；先 DDL 后备份。
- 在备份窗口（04:00–07:00）执行迁移/contract。
- 两人同时执行发布脚本。

## 5. 集群命令与检查 SQL（dev 验收完成）

```sh
# expand（在线）
maintenance upgrade --phase=expand --online --dsn "$JUHE_AI_POSTGRES_URL" --secret "$JUHE_AI_SECRET"

# 逐台滚动（在 docker/cluster/ 下，每台 gateway/jobs 节点执行；digest 引用来自 build/images.txt）
./rolling-release.sh \
  --image <registry>/juhe-ai@sha256:<digest> \
  --apply-cmd 'JUHE_AI_GATEWAY_IMAGE=%IMAGE% docker compose -f compose.gateway.yml up -d --no-deps --force-recreate gateway' \
  --health-url http://127.0.0.1:3306/health \
  --container juhe-ai-gateway

# 旧实例全部下线后执行 contract（先确认旧版本请求=0 且备份可恢复）
maintenance upgrade --phase=contract --old-writers-drained --backup-confirmed \
  --dsn "$JUHE_AI_POSTGRES_URL" --secret "$JUHE_AI_SECRET"
```

> `deploy.sh rolling|contract` 从未实现，集群发布统一用 `docker/cluster/rolling-release.sh`
> + `maintenance upgrade`；单机停写窗口仍用 `docker/single-server/deploy.sh upgrade`。

检查 SQL：

```sql
-- 当前结构版本
SELECT schema_revision, min_readable_binary_revision, expand_completed
FROM juhe_business.schema_state WHERE id = 1;

-- 升级中断
SELECT revision, step_id, phase, status, destructive
FROM juhe_business.schema_migrations
WHERE status = 'running' OR revision > (
  SELECT schema_revision FROM juhe_business.schema_state WHERE id = 1
);

-- 长事务（contract 前）
SELECT pid, state, now() - xact_start AS age, query
FROM pg_stat_activity
WHERE xact_start IS NOT NULL AND now() - xact_start > interval '5 minutes';

-- 复制槽延迟
SELECT slot_name, active, restart_lsn, confirmed_flush_lsn FROM pg_replication_slots;
```

## 6. 评审清单

### 需求评审 10 问

1. 单机还是集群？能不能停写？
2. 表结构变了什么？旧实例还能跑吗？
3. 需要回填吗？数据量、失败行、限速？
4. 新状态放哪？多节点共享吗？
5. 有没有新增后台任务？单活/租约？
6. 有没有文件跨机？
7. API/前端是否兼容？
8. 配置是否新增/改名？每实例唯一吗？
9. 发布观测看什么？回滚怎么回？
10. 文档和待办是否同批更新？

### 代码评审 10 问

1. 有没有双列读/旧列回落/迁移期开关？（禁止）
2. 有没有进程内状态承载跨节点事实？
3. 写路径是否全部覆盖双写？有差异校验吗？
4. 新约束是否允许旧代码写入？
5. 回填是否分批、幂等、可暂停？
6. 失败是否 fail-closed？是否静默降级？
7. 迁移失败是否推进账本？（禁止）
8. 旧实例重启是否会被门禁误拒？
9. 日志/指标是否带 version/instance？
10. 回滚后旧结构是否仍然可用？

### 发布前 10 项

1. 备份完成并验证；
2. 配置一致（secret/namespace/DSN/trust proxy/时钟/实例 ID）；
3. 容量 N-1；
4. 旧版本请求=0（contract 前）；
5. 长事务/复制槽正常；
6. 按版本指标已就绪；
7. 回滚 tag 可取；
8. 发布窗口避开备份；
9. 发布互斥（无并发发布）；
10. 发布记录（tag/schema revision/操作人/时间）。
