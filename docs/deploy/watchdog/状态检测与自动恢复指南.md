# 状态检测与自动恢复指南

## 1. 推荐结论

无论是服务器部署还是家庭宽带部署，都建议配置外部状态检测：

```text
watchdog -> 检查 juhe-ai health -> 连续失败 -> 重启主服务 -> 等待恢复 -> 记录日志
```

当前 juhe-ai 内部已经由主进程看护 DB service 和后台 worker：DB service / worker 异常退出会自动退避重启，不需要外部 watchdog 单独管理这些子进程。外部 watchdog 的职责是发现“主服务整体不可用、卡死或 health 长时间失败”，然后重启主服务。

## 2. 检查哪些状态

最低检查：

```text
GET http://127.0.0.1:3000/__aisys__/health
GET http://127.0.0.1:3000/__aisys__/api/health
```

公网入口还要额外检查：

```text
GET https://ai.example.com/__aisys__/health
```

推荐分层：

| 层级 | 检查目标 | 失败含义 |
| --- | --- | --- |
| 本机主服务 | `127.0.0.1:端口/__aisys__/health` | Node 主服务不可用或卡死 |
| 系统 API / DB service | `127.0.0.1:端口/__aisys__/api/health` | 管理 API 或 DB service 链路不可用 |
| 公网入口 | `https://域名/__aisys__/health` | Caddy / Nginx / 隧道 / DNS / 证书 / 主服务任一层异常 |

自动重启主服务时，优先以本机主服务和系统 API health 为准。公网入口失败可能只是 DNS、宽带、证书、隧道或上游 edge 问题，不一定应该直接重启 juhe-ai。

## 3. 防止重启风暴

watchdog 必须具备这些保护：

| 保护 | 建议值 | 目的 |
| --- | --- | --- |
| 单次请求超时 | `5s` | 不让 curl 卡住 |
| 检查间隔 | `15s` 到 `60s` | 避免高频探测 |
| 连续失败阈值 | `2` 到 `3` 次 | 避免一次抖动就重启 |
| 启动宽限期 | `60s` | 服务刚启动时允许依赖初始化 |
| 重启后冷却 | `60s` 到 `180s` | 给服务恢复和日志落盘时间 |
| 窗口限频 | 例如 `10min` 内最多 `3` 次 | 避免配置错误导致无限重启 |
| CPU-only 策略 | 默认只记录 | CPU 高但 health 正常时不要贸然杀进程 |

满足以下条件才自动重启：

- 本机 `/__aisys__/health` 和 `/__aisys__/api/health` 连续失败。
- 当前不在启动宽限期或重启冷却期。
- 最近窗口内重启次数未超过上限。

不建议自动重启：

- 只有公网域名 health 失败，但本机 health 正常。
- 只有上游模型 API 失败。
- 只有 CPU 高，但 health 正常。
- 只有某个账号或代理测试失败。

## 4. 平台职责

| 平台 | 推荐守护 | watchdog 职责 |
| --- | --- | --- |
| macOS | `launchd` + watchdog 脚本 | watchdog 终止主 server，launchd `KeepAlive` 拉起 |
| Linux | `systemd` + timer/service 或独立脚本 | systemd 管主服务，watchdog 按阈值 `systemctl restart` |
| Docker | Compose restart policy + 外部 watchdog | healthcheck 只报告状态，不保证自动重启 unhealthy 容器 |
| Windows | NSSM / 任务计划程序 + PowerShell watchdog | 连续失败后重启 Windows Service 或进程 |

平台重启目标示例：

| 平台 | 发布包重启目标 | Docker 重启目标 |
| --- | --- | --- |
| Linux | `sudo systemctl restart juhe-ai` | `docker compose restart juhe-ai` |
| Windows | `Restart-Service JuheAI` 或 `nssm restart JuheAI` | `docker compose restart juhe-ai` |
| macOS | `launchctl kickstart -k "gui/$UID/com.juhe-ai"` | `docker compose restart juhe-ai` |

高性能 Docker 只重启应用容器：

```bash
docker compose --env-file .env.performance -f compose.performance.yml restart juhe-ai
```

不要把 PostgreSQL、PgBouncer、Redis cache、Redis state、sing-box、Caddy 和 juhe-ai 混成同一个“失败就全量重启”的动作。外部入口失败但本机 health 正常时，查 Caddy / Nginx / DNS / 证书 / 隧道；上游 API 失败时，查账号代理或 sing-box；中间件失败时，按中间件自身日志处理。

## 5. 与旧 worker / DB service 残留的关系

当前新版本已经把 DB service 和 worker 纳入主进程 supervisor：

- DB service 异常退出后会自动退避重启。
- 后台 worker 异常退出后会自动退避重启。
- 运行时不再把临时维护 worker 作为长期写库路径。

因此，旧版本那种“正常重启后旧 worker/db-service 长期残留并抢 SQLite 写锁”的问题不应作为当前常规风险描述。

仍建议保留一个兜底排查项：如果发生强杀、系统崩溃、手工误杀、launchd/systemd 异常或 SQLite 持续 `database is locked`，再检查是否有旧子进程脱离当前 server。

macOS / Linux 示例：

```bash
CURRENT=$(pgrep -f 'backend/dist/server.js' | head -n 1)
ps -axo pid,ppid,command \
  | awk -v current="$CURRENT" '/backend\/dist\/(db-service|worker)\.js/ && $2 != current {print}'
```

只有确认是旧进程，且不是当前 server 的子进程，才手动结束。

## 6. 日志要求

watchdog 每次动作至少记录：

- 检查时间。
- health HTTP 状态码。
- 当前主服务 PID。
- 失败计数。
- 是否处于冷却期。
- 是否触发重启。
- 重启后的恢复结果。

出现频繁重启时，应先禁用自动重启或提高冷却窗口，再看应用日志、Caddy / Nginx 日志、系统日志和数据库状态。
