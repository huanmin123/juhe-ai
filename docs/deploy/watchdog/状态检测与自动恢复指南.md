# 状态检测与自动恢复指南

## 1. 当前恢复模型

juhe-ai 的恢复边界按组件隔离：

| 组件 | 恢复责任 | 判据 |
| --- | --- | --- |
| 主进程 | launchd / systemd / Windows Service / 容器 restart policy | 进程明确退出 |
| DB service | 主进程 supervisor | 子进程退出；或本机 DB health 持续失败达到内部门槛 |
| ingest / stats / ops worker | 主进程 supervisor | 对应子进程明确退出 |
| 公网入口 | 只读监控和告警 | 不触发应用重启、代理切换或回滚 |
| 上游代理 | 独立代理策略 | 不由应用 health 或公网域名状态驱动 |

外部 HTTP watchdog 已退役。任何发布包、plist、service、timer、计划任务或上线脚本都不得重新启用它。

## 2. 子进程退避

DB service 和每个 worker 分别维护退避状态，互不连带：

```text
1s -> 5s -> 15s -> 30s -> 1m -> 2m -> 5m -> 10m
```

- 到达 10 分钟后保持上限，不无限增长。
- 收到 ready 只表示启动完成，不能立即清零失败历史。
- 只有同一子进程连续稳定运行 10 分钟，下一次退出才从 1 秒重新开始。
- 一个 worker 异常不能重启 DB service、其他 worker 或主进程。
- stdout、stderr 或 IPC 接收端关闭时，按组件断开处理，不能用 `EPIPE` 拖垮主进程。

## 3. DB service health

DB service 的“进程退出”和“进程存活但 health 异常”是两条路径：

- 明确退出：直接进入该 DB service 的退避重启。
- health 异常：启动宽限后必须持续失败 5 分钟，并以当前本机探测作为最终复核；随后才受冷却和窗口预算保护，只终止当次核对过 PID 的 DB service 子进程。
- 公网 health、Caddy、Nginx、证书、隧道或上游账号失败都不能作为 DB service 恢复判据。

## 4. 公网观察

公网域名可以用于监控完整链路，但结果只分为 `healthy / failed / unknown` 并记录告警：

- `failed` 不自动杀主进程。
- `unknown` 不等同于失败，也不累计恢复动作门槛。
- 本机 health 正常而公网失败时，按入口链路独立排障。
- 发布验证可以因公网失败而阻断切流，但不能据此自动回滚或切代理。

## 5. 发布门禁

发布前后都应确认：

1. 旧外部 watchdog 为 disabled / not loaded，且没有旧脚本进程。
2. 服务管理器只守护主进程；DB service / worker 不注册为独立系统服务。
3. 候选服务和生产服务按 PID、cwd、端口与版本身份分别验证。
4. 临时服务清理由发布脚本显式完成，不由旧 watchdog 的 PPID 扫描代办。
5. 验证失败时保持临时接管或停止发布，等待人工决定回滚，不执行自动全组件恢复。

## 6. 记录要求

恢复与观察日志至少包含组件、PID、版本/cwd、信号来源、状态 `healthy / failed / unknown`、连续时间、退避档位、最终复核结果和实际动作。日志不得包含密码、Token、API Key、Cookie 或完整请求体。
