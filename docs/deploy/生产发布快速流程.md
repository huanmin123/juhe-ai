# 生产发布快速流程

> 面向生产维护者和 AI 执行者。本文定义高性能 Mac 拓扑的唯一快速发布路径；真实地址、账号、端口、凭据和当前槽位以受限私有 runbook 为准。

## 1. 目标与时间边界

生产发布分为“在线准备”和“原子切流”两个阶段。构建、上传、依赖安装、候选启动、数据准备、F1/F2/F3 验证和真实浏览器检查都在旧槽继续承流时完成，不计入不可用窗口。

| 阶段 | 用户流量 | 目标时间 | 允许动作 |
| --- | --- | --- | --- |
| 构建冻结 | 旧槽承流 | 窗口前完成 | 固定 commit、构建一次、校验 bundle/归档/三项 Go 二进制 |
| candidate 准备 | 旧槽承流 | 可持续数分钟，但不得影响用户 | 上传、解包、离线依赖、独立 runtime/label/端口/实例、启动与完整业务验证 |
| handover preflight | 旧槽承流 | 默认 60 秒 | 同时观察两槽、入口身份和 access log，生成 5 分钟有效的带指纹凭证 |
| takeover | 原子切流 | 目标 60–120 秒完成稳定证明 | 校验凭证时效与文件指纹、一次身份复核、替换 route、Nginx test/reload、一轮并行稳定观察 |
| 观察 | 新槽承流，旧槽保留 | 按发布风险决定 | 业务错误率、F1/F2/F3、浏览器页面和日志观察；禁止清理旧槽 |
| retire | 新槽稳定承流 | 观察后执行 | 更新 current、归档证据、按精确 allowlist 清理旧槽 |

候选失败不得影响用户；切流失败必须自动恢复原 route 并保留两槽。任何发布如果需要先停止 active 槽才能继续，必须停止操作，不能把它归类为本流程。

## 2. 窗口前必须完成

1. 工作树干净，固定完整 commit SHA；同一窗口只构建一次不可变 release。
2. `pnpm test:release-package`、`pnpm test:release-source-preflight`、`pnpm test:release-go-sidecar-launchers`、`pnpm test:macos-operations` 全部通过。
3. 最终 bundle 只能包含合法 API base；静态页面和 health `200` 不构成前端验收。
4. release 上传后校验 commit、archive SHA-256、文件权限、Node LTS、生产依赖和 F1/F2/F3 二进制。
5. candidate 使用独立 release、runtime、label、端口、Nginx slot、upstream suffix、instance ID 和 Redis 身份；业务槽连接同一份权威业务库。
6. candidate 完成 Node 双 health、三个 gateway、worker/PID、F1/F2 freshness、F3 Node -> Go -> Node 读回、网关认证性探针和真实浏览器登录态业务页。
7. 生产连接快照、当前 route、旧槽回切目标和私有 plan 均与现场一致。快照不一致时先更新事实，禁止用旧值试错。

## 3. 切流命令

完整候选验证通过后，在预计切流前五分钟内执行：

```bash
sudo bash ./performance-handover-controller.sh --apply \
  --action preflight \
  --plan-dir '<私有plan绝对路径>' \
  --stability-seconds 60 \
  --preflight-max-age-seconds 300
```

`PREFLIGHT_OK` 会写入当前 route、main/temporary fragment、plan 和 Nginx main config 的 SHA-256。凭证时效在生成时冻结，后续命令只能缩短、不能延长；任一文件变化、凭证超过时效、进程身份变化或槽位不健康都会拒绝切流。

随后执行：

```bash
sudo bash ./performance-handover-controller.sh --apply \
  --action takeover \
  --plan-dir '<私有plan绝对路径>' \
  --stability-seconds 60 \
  --preflight-max-age-seconds 300
```

`takeover` 不再重复完整的切流前稳定窗口；控制器先复制自己的 rollback/target 快照并校验快照哈希，实时身份复核后紧邻 route 变更再次校验凭证时效和全部文件指纹，只把已验证快照原子替换为 active route。切换后把入口与两槽状态放在同一个稳定循环中验证。成功条件是 journal 为 `committed` 且输出 `HANDOVER_OK`。

## 4. 快速回切

新槽已 committed 后出现业务错误，不得执行 `recover`。保持两槽运行，立即对旧槽执行反向预检，再回切：

```bash
sudo bash ./performance-handover-controller.sh --apply --action preflight --plan-dir '<私有plan绝对路径>'
sudo bash ./performance-handover-controller.sh --apply --action switchback --plan-dir '<私有plan绝对路径>'
```

如果新槽已经宕机，普通反向 preflight 会按设计拒绝。此时使用显式降级源模式；它只允许从 committed journal 进入，要求当前 route 字节仍指向故障新槽，并连续证明旧槽回切目标健康，不要求故障源恢复：

```bash
sudo bash ./performance-handover-controller.sh --apply --action preflight --degraded-source --plan-dir '<私有plan绝对路径>'
sudo bash ./performance-handover-controller.sh --apply --action switchback --plan-dir '<私有plan绝对路径>'
```

旧槽不健康或 route 已被手工修改时，降级源预检同样拒绝。切流尚未 committed 时不使用此选项，由控制器自动恢复经过快照校验的旧 route，并只验证恢复后的旧槽与入口，不会要求故障 candidate 健康。

只有未 committed 的中断 journal 才使用 `recover`。未知状态先执行 `status`，不得杀进程、改 route 文件或原地重新安装。

## 5. 禁止事项

- 禁止对 active 槽执行同端口、同 label 的原地 `--apply` 并宣称无感。
- 禁止在切流窗口中构建、在线安装依赖、修复 env、迁移 schema、清理 Redis/日志或删除旧 release。
- 禁止重复构建多个“临时修复包”；失败后修复源码、重新冻结新 commit，并重新完成 candidate。
- 禁止以单个 HTTP `200`、F3 `204`、launchd loaded 或静态首页替代真实业务验证。
- 禁止在观察完成前停止旧槽、更新回滚指针或执行生产残留清理。
- 禁止为赶时间绕过 Node/Go owner、F1/F2/F3 数据读回、bundle 扫描、浏览器业务页或 journal 状态。

## 6. 发布完成记录

每次发布只记录一份窗口证据：release commit 与 archive SHA-256、candidate 身份、四项发布回归、F1/F2/F3 结果、浏览器业务页、preflight/takeover journal、切流与回切耗时、观察结论和旧槽处理。失败重试继续使用同一窗口记录；不得靠重复备份、重复审查或散落终端输出堆叠证据。
