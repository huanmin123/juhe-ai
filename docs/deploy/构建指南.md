# 跨平台构建文档

> 本文只说明如何在 Windows、macOS、Linux 任一平台构建发布包。部署到目标机器的步骤见 `docs/deploy/部署指南.md`。

## 1. 兼容目标

当前发布体系支持任意构建平台生成同一类发布包：

| 构建平台 | 推荐命令 | 支持的部署目标 |
| --- | --- | --- |
| Windows | `pnpm package:release:windows` | Windows / macOS / Linux |
| macOS | `pnpm package:release:mac` | Windows / macOS / Linux |
| Linux | `pnpm package:release:linux` | Windows / macOS / Linux |

发布包是平台无关的构建产物，不包含当前机器的 `node_modules`。日志搜索 `grep 模式` 依赖后端生产依赖 `@vscode/ripgrep`，部署时由目标机器执行 `pnpm install --prod` 自动安装对应平台和架构的 `rg`。

## 2. 构建前必须检测

### Windows 构建机

```powershell
$PSVersionTable.PSVersion
node -v
node -p "process.version + ' LTS=' + (process.release.lts || '非LTS')"
corepack --version
pnpm -v
pnpm install --frozen-lockfile
pnpm --filter juhe-ai-backend check:runtime
tar --version
Test-Path package.json
Test-Path backend/package.json
Test-Path frontend/package.json
```

### macOS 构建机

```bash
pwd
sw_vers
uname -a
node -v
node -p "process.version + ' LTS=' + (process.release.lts || '非LTS')"
corepack --version || true
pnpm -v || true
pnpm install --frozen-lockfile
pnpm --filter juhe-ai-backend check:runtime
tar --version || bsdtar --version || true
test -f package.json
test -f backend/package.json
test -f frontend/package.json
```

### Linux 构建机

```bash
pwd
uname -a
node -v
node -p "process.version + ' LTS=' + (process.release.lts || '非LTS')"
corepack --version || true
pnpm -v || true
pnpm install --frozen-lockfile
pnpm --filter juhe-ai-backend check:runtime
tar --version
test -f package.json
test -f backend/package.json
test -f frontend/package.json
```

必须确认：

- 当前目录是项目根目录。
- 发布包只能从固定提交的干净 Git worktree 构建；tracked、untracked 任一变更都会在构建前被拒绝。需要保留本地开发改动时，另建指向固定 release SHA 的干净 worktree，禁止用忽略参数绕过。
- Node.js 是官方 LTS，当前支持 22.x LTS（>=22.13.0）或 24.x LTS（>=24.11.0），且通过后端运行时预检。
- pnpm 可用；不可用时先执行 `corepack enable`。首次签出、切换分支或 `pnpm-lock.yaml` 变化后，先执行 `pnpm install --frozen-lockfile`，再运行后端运行时预检。
- 不要把构建机的 `node_modules` 放进发布包。
- 不要把真实 `.env`、`backend/data/`、任何 `data/`、`logs/`、SQLite 文件、数据库 dump、审计 payload、Redis 持久化文件或链接放进发布包。项目备份沿用相同内容边界，但正式升级恢复点必须归档升级前当前运行的 release，不能用待上线新包与升级前业务库配对。
- 不要把构建机的 `rg` 二进制放进发布包；目标机器安装后端生产依赖时会自动安装对应平台的 `@vscode/ripgrep` 二进制。
- 前端配置是构建时注入的，修改域名或网关展示地址后必须重新打包。
- 后端生产构建只包含运行入口、业务模块、预检和必要维护脚本；回归、压测和 smoke 脚本不进入发布包。

## 3. 推荐构建命令

### Windows

```powershell
pnpm package:release:windows
```

等价显式命令：

```powershell
pwsh ./scripts/package-release.ps1
```

### macOS

```bash
pnpm package:release:mac
```

等价显式命令：

```bash
bash ./scripts/package-release.sh
```

### Linux

```bash
pnpm package:release:linux
```

等价显式命令：

```bash
bash ./scripts/package-release.sh
```

## 4. 产物说明

默认生成：

```text
release/juhe-ai-release.tar.gz
release/juhe-ai-release.zip
```

推荐选择：

| 部署目标 | 推荐上传 |
| --- | --- |
| Windows | `juhe-ai-release.zip` |
| macOS | `juhe-ai-release.tar.gz` |
| Linux | `juhe-ai-release.tar.gz` |

发布包目录包含：

```text
juhe-ai-release/
  RELEASE_SOURCE_COMMIT
  backend/dist/
  backend/.env.example
  frontend/dist/
  docs/deploy/
  package.json
  pnpm-lock.yaml
  pnpm-workspace.yaml
  start.sh
  start.ps1
  README.md
```

## 5. 常用构建参数

### 锁定发布提交

打包脚本始终检查工作树是否干净。正式发布还应显式传入计划中冻结的完整 40 位 commit SHA；当前 HEAD 不一致时立即失败：

Windows：

```powershell
pwsh ./scripts/package-release.ps1 -ExpectedCommit '<完整 release SHA>'
```

macOS / Linux：

```bash
bash ./scripts/package-release.sh --expected-commit '<完整 release SHA>'
```

生成目录和压缩包内的 `RELEASE_SOURCE_COMMIT` 必须与该 SHA 完全一致。部署侧校验 archive hash 时同时核对这个文件，不能只根据文件名推断版本。

### 固定公网网关地址

Windows：

```powershell
pwsh ./scripts/package-release.ps1 -FrontendGatewayBaseUrl "https://你的域名/v1"
```

macOS / Linux：

```bash
bash ./scripts/package-release.sh --frontend-gateway-base-url "https://你的域名/v1"
```

默认不传时：

```env
VITE_JUHE_AI_API_BASE_URL=/__aisys__/api
VITE_JUHE_AI_GATEWAY_BASE_URL=
```

含义：

- 管理后台请求同源 `/__aisys__/api`。
- API Key 页面按浏览器访问地址自动推断网关根地址；客户端也可以继续填写 `/v1` 地址。

### 只生成一种压缩格式

Windows：

```powershell
pwsh ./scripts/package-release.ps1 -ArchiveFormat zip
pwsh ./scripts/package-release.ps1 -ArchiveFormat tar.gz
```

macOS / Linux：

```bash
bash ./scripts/package-release.sh --archive-format zip
bash ./scripts/package-release.sh --archive-format tar.gz
```

Linux 构建机如果没有 `zip` 命令，可以只生成 `tar.gz`。

### 真实配置禁止进入发布包

构建脚本不提供携带本地 `.env` 的参数。真实 `backend/.env` / `frontend/.env` 不得进入 release 或项目备份；生产恢复所需的 `backend.env` 只放在受限权限的 `business-*` 业务备份中。

## 6. 构建后检查

Windows：

```powershell
Test-Path release/juhe-ai-release.tar.gz
Test-Path release/juhe-ai-release.zip
tar -tzf release/juhe-ai-release.tar.gz | Select-Object -First 50
```

macOS / Linux：

```bash
test -f release/juhe-ai-release.tar.gz
tar -tzf release/juhe-ai-release.tar.gz | head -50
```

必须看到：

- `juhe-ai-release/start.sh`
- `juhe-ai-release/start.ps1`
- `juhe-ai-release/README.md`
- `juhe-ai-release/RELEASE_SOURCE_COMMIT`
- `juhe-ai-release/backend/dist/server.js`
- `juhe-ai-release/backend/dist/worker.js`
- `juhe-ai-release/frontend/dist/index.html`
- `juhe-ai-release/pnpm-lock.yaml`

后端只通过生产依赖 `@vscode/ripgrep` 读取当前平台安装的 `rg`，不读取服务器 PATH 里的系统 `rg`，也不回退到 Node 文件扫描。发布包不内置 `rg` 二进制；Windows、macOS、Linux 的 x64 / arm64 等平台差异由目标机器安装依赖时自动处理。

## 7. 给 AI 的构建摘要

1. 先判断构建机系统：Windows、macOS 或 Linux。
2. 检查 Node.js LTS、后端运行时预检、pnpm、tar 和项目根目录。
3. 使用对应 `package:release:*` 命令构建。
4. 不要打包 `node_modules`。
5. 检查发布包同时包含 `start.sh` 和 `start.ps1`。
6. 按目标系统转到 `docs/deploy/部署指南.md`。
