# 跨平台构建文档

> 本文只说明如何在 Windows、macOS、Linux 任一平台构建发布包。部署到目标机器的步骤见 `docs/deploy/部署指南.md`。

## 1. 兼容目标

当前发布体系支持任意构建平台生成同一类发布包：

| 构建平台 | 推荐命令 | 支持的部署目标 |
| --- | --- | --- |
| Windows | `pnpm package:release:windows` | Windows / macOS / Linux |
| macOS | `pnpm package:release:mac` | macOS / Linux（以 `--goos` / `--goarch` 匹配目标） |
| Linux | `pnpm package:release:linux` | macOS / Linux（以 `--goos` / `--goarch` 匹配目标） |

发布包不包含当前机器的 `node_modules`。Node 部分仍由目标机器执行 `pnpm install --prod`，自动安装与目标平台、架构匹配的 `@vscode/ripgrep`。发布包还会包含已交叉编译的 Go F1 `juhe-ai-runtime-log-indexer`、F2 `juhe-ai-table-monitor` 和 F3 `juhe-ai-audit-log-writer`，因此压缩包必须与部署目标的 `GOOS/GOARCH` 完全匹配；不要把 Linux 二进制部署到 macOS，或把 `amd64` 二进制部署到 `arm64` 主机。Go 原生日志搜索路径不复用 `node_modules`，目标主机仍须另行提供 `rg`，并通过 `JUHE_AI_RG_PATH` 固定路径或放入 Go 进程 `PATH`。macOS system `launchd` 部署应在依赖安装完成后把 release 固定为“服务用户可读/可执行、不可写”；不要把 `node_modules` 或整个 release 递归交给服务用户写入。

## 2. 构建前必须检测

### Windows 构建机

```powershell
$PSVersionTable.PSVersion
node -v
node -p "process.version + ' LTS=' + (process.release.lts || '非LTS')"
corepack --version
pnpm -v
pnpm install --frozen-lockfile
pnpm --filter juhe-ai-backend check:runtime
tar --version
Test-Path package.json
Test-Path backend/package.json
Test-Path frontend/package.json
```

### macOS 构建机

```bash
pwd
sw_vers
uname -a
node -v
node -p "process.version + ' LTS=' + (process.release.lts || '非LTS')"
corepack --version || true
pnpm -v || true
pnpm install --frozen-lockfile
pnpm --filter juhe-ai-backend check:runtime
go version
go -C backend-go env GOOS GOARCH
tar --version || bsdtar --version || true
test -f package.json
test -f backend/package.json
test -f frontend/package.json
```

### Linux 构建机

```bash
pwd
uname -a
node -v
node -p "process.version + ' LTS=' + (process.release.lts || '非LTS')"
corepack --version || true
pnpm -v || true
pnpm install --frozen-lockfile
pnpm --filter juhe-ai-backend check:runtime
go version
go -C backend-go env GOOS GOARCH
tar --version
test -f package.json
test -f backend/package.json
test -f frontend/package.json
```

必须确认：

- 当前目录是项目根目录。
- 发布包只能从固定提交的干净 Git worktree 构建；tracked、untracked 任一变更都会在构建前被拒绝。需要保留本地开发改动时，另建指向固定 release SHA 的干净 worktree，禁止用忽略参数绕过。
- Node.js 是官方 LTS，当前支持 22.x LTS（>=22.13.0）或 24.x LTS（>=24.11.0），且通过后端运行时预检。
- 发布构建机需要 Go `1.26.x`；脚本使用 `CGO_ENABLED=0` 交叉编译 F1 索引器、F2 表监控器和 F3 原始审计 writer，部署目标不需要安装 Go。
- Unix 构建 `tar.gz` 需要 GNU tar 的 append/mode 能力，或 macOS BSD tar 的 `-r` 能力；脚本会按可用实现选择对应命令。BusyBox tar 不具备这两种完整能力时必须失败，不能手工拼接一个未经权限校验的归档。2026-08-11 已在目标 Intel Mac 以 BSD tar 生成并解包校验 F1/F2/F3 发布归档。
- pnpm 可用；不可用时先执行 `corepack enable`。首次签出、切换分支或 `pnpm-lock.yaml` 变化后，先执行 `pnpm install --frozen-lockfile`，再运行后端运行时预检。
- 不要把构建机的 `node_modules` 放进发布包。
- 不要把真实 `.env`、`backend/data/`、任何 `data/`、`logs/`、SQLite 文件、数据库 dump、审计 payload、Redis 持久化文件或链接放进发布包。项目备份沿用相同内容边界，但正式升级恢复点必须归档升级前当前运行的 release，不能用待上线新包与升级前业务库配对。
- 不要把构建机的 `rg` 二进制跨平台放进发布包；Node 路径由目标机器安装对应平台的 `@vscode/ripgrep`，Go 原生路径由目标主机安装系统 `rg` 或配置目标平台的 `JUHE_AI_RG_PATH`。
- 前端配置是构建时注入的，修改域名或网关展示地址后必须重新打包。
- `VITE_JUHE_AI_API_BASE_URL` 必须是严格的 `http://` 或 `https://` URL，或唯一允许的根相对值 `/__aisys__/api`；不接受其它根相对路径。HTTP(S) URL 必须有明确的非空 authority，且 path 以 `/__aisys__/api` 结尾，总长度不超过 2048 字符、path 不超过 1024 字符；不得包含 query、fragment、userinfo、无效端口、空白、反斜杠、authority percent escape 或畸形 percent escape。禁止传入盘符路径、UNC 路径或协议相对 URL。Windows 上从 Git Bash/MSYS 调用 PowerShell 打包器时，`/__aisys__/api` 可能被 shell 转换成磁盘路径；正式打包应直接从 PowerShell 调用，或省略该默认参数。两个打包器都会在修改输出目录前拒绝文件系统路径。
- 后端生产构建只包含运行入口、业务模块、预检和必要维护脚本；回归、压测和 smoke 脚本不进入发布包。

## 3. 推荐构建命令

### Windows

```powershell
pnpm package:release:windows
```

等价显式命令：

```powershell
pwsh ./scripts/package-release.ps1
```

### macOS

```bash
pnpm package:release:mac
```

等价显式命令：

```bash
bash ./scripts/package-release.sh
```

### Linux

```bash
pnpm package:release:linux
```

等价显式命令：

```bash
bash ./scripts/package-release.sh
```

Unix 脚本默认将 F1/F2/F3 Go sidecar 编译为当前 macOS/Linux 主机的 `GOOS/GOARCH`。交叉构建时必须显式传入部署目标，例如：

```bash
# Linux x86_64
bash ./scripts/package-release.sh --goos linux --goarch amd64

# Apple Silicon macOS
bash ./scripts/package-release.sh --goos darwin --goarch arm64
```

Unix 脚本只生成 macOS 或 Linux 的 F1/F2/F3 二进制；Windows 发布包使用 PowerShell 发布入口。

## 4. 产物说明

默认生成：

```text
release/juhe-ai-release.tar.gz
release/juhe-ai-release.zip
```

推荐选择：

| 部署目标 | 推荐上传 |
| --- | --- |
| Windows | `juhe-ai-release.zip` |
| macOS | `juhe-ai-release.tar.gz` |
| Linux | `juhe-ai-release.tar.gz` |

发布包目录包含：

## 5. 常用构建参数

### 锁定发布提交

打包脚本始终检查工作树是否干净。正式发布还应显式传入计划中冻结的完整 40 位 commit SHA；当前 HEAD 不一致时立即失败：

Windows：

```powershell
pwsh ./scripts/package-release.ps1 -ExpectedCommit '<完整 release SHA>'
```

macOS / Linux：

```bash
bash ./scripts/package-release.sh --expected-commit '<完整 release SHA>'
```

生成目录和压缩包内的 `RELEASE_SOURCE_COMMIT` 必须与该 SHA 完全一致。部署侧校验 archive hash 时同时核对这个文件，不能只根据文件名推断版本。

打包脚本还会把同一个完整 SHA 作为 `VITE_JUHE_AI_BUILD_ID` 注入前端构建，并生成 `frontend/dist/build-info.json`。该变量属于发布脚本内部契约，不得由维护者手工填写、缩短或改成时间戳；否则当前页面与服务器版本的比较将失去可信来源。

### 固定公网网关地址

Windows：

```powershell
pwsh ./scripts/package-release.ps1 -FrontendGatewayBaseUrl "https://你的域名/v1"
```

macOS / Linux：

```bash
bash ./scripts/package-release.sh --frontend-gateway-base-url "https://你的域名/v1"
```

默认不传时：

```env
VITE_JUHE_AI_API_BASE_URL=/__aisys__/api
VITE_JUHE_AI_GATEWAY_BASE_URL=
```

含义：

- 管理后台请求同源 `/__aisys__/api`。
- API Key 页面按浏览器访问地址自动推断网关根地址；客户端也可以继续填写 `/v1` 地址。

不要从 Git Bash/MSYS 将 `-FrontendApiBaseUrl '/__aisys__/api'` 传给 PowerShell 脚本；路径转换可能把它改写为 Windows 盘符路径。需要显式传值时在 PowerShell 中执行：

```powershell
pwsh ./scripts/package-release.ps1 -FrontendApiBaseUrl '/__aisys__/api'
```

### 只生成一种压缩格式

Windows：

```powershell
pwsh ./scripts/package-release.ps1 -ArchiveFormat zip
pwsh ./scripts/package-release.ps1 -ArchiveFormat tar.gz
```

macOS / Linux：

```bash
bash ./scripts/package-release.sh --archive-format zip
bash ./scripts/package-release.sh --archive-format tar.gz
```

Linux 构建机如果没有 `zip` 命令，可以只生成 `tar.gz`。

### 真实配置禁止进入发布包

构建脚本不提供携带本地 `.env` 的参数。真实 `backend/.env` / `frontend/.env` 不得进入 release 或项目备份；生产恢复所需的 `backend.env` 只放在受限权限的 `business-*` 业务备份中。

## 6. 构建后检查

Windows：

```powershell
Test-Path release/juhe-ai-release.tar.gz
Test-Path release/juhe-ai-release.zip
tar -tzf release/juhe-ai-release.tar.gz | Select-Object -First 50
```

macOS / Linux：

```bash
test -f release/juhe-ai-release.tar.gz
tar -tzf release/juhe-ai-release.tar.gz | head -50
```

必须看到：

- `juhe-ai-release/start.sh`
- `juhe-ai-release/start.ps1`
- `juhe-ai-release/README.md`
- `juhe-ai-release/RELEASE_SOURCE_COMMIT`
- `juhe-ai-release/backend/dist/server.js`
- `juhe-ai-release/backend/dist/worker.js`
- `juhe-ai-release/backend-go/juhe-ai-runtime-log-indexer`
- `juhe-ai-release/backend-go/juhe-ai-table-monitor`
- `juhe-ai-release/backend-go/juhe-ai-audit-log-writer`
- `juhe-ai-release/frontend/dist/index.html`
- `juhe-ai-release/frontend/dist/build-info.json`
- `juhe-ai-release/pnpm-lock.yaml`

`frontend/dist/build-info.json` 的 `buildId` 必须与 `RELEASE_SOURCE_COMMIT` 完全一致。后端以 `no-cache` 提供该清单，供前端只在动态资源加载失败时判断是否确有版本变化；它不是服务启停记录，也不触发后台轮询。

打包器会在归档前调用 `scripts/validate-release-package.mjs` 自动扫描最终前端产物。校验器要求 bundle 包含 `/__aisys__/api`，并拒绝 Windows 盘符、UNC、Unix 文件路径、协议相对 URL、非 HTTP(S) scheme 和畸形 HTTP URL。也可以手工复核：

```powershell
rg -l -F '/__aisys__/api' release/juhe-ai-release/frontend/dist/assets
rg -n '[A-Za-z]:[\\/].*__aisys__[\\/]api' release/juhe-ai-release/frontend/dist
```

第一条必须至少命中当前主 bundle；第二条必须没有输出。Unix 使用同一 `rg` 表达式。自动校验或手工扫描失败时打包必须终止，不得生成可上传归档。静态 `index.html`、health `200` 和 `build-info.json` 都不能证明 Axios 使用了正确 base，部署后仍须执行登录态浏览器业务页验证。

Node 后端只通过生产依赖 `@vscode/ripgrep` 读取当前平台安装的 `rg`。Go 原生后端优先读取 `JUHE_AI_RG_PATH`，留空时通过进程 `PATH` 查找 `rg`；两条路径都不回退到应用层文件逐行扫描。发布包不跨平台内置 `rg` 二进制，目标机器必须按实际 owner 安装对应平台依赖。

## 7. 给 AI 的构建摘要

1. 先判断构建机系统：Windows、macOS 或 Linux。
2. 检查 Node.js LTS、后端运行时预检、pnpm、tar 和项目根目录。
3. 使用对应 `package:release:*` 命令构建。
4. 不要打包 `node_modules`。
5. 检查发布包同时包含 `start.sh`、`start.ps1` 和与部署目标匹配的 `backend-go/juhe-ai-runtime-log-indexer`、`backend-go/juhe-ai-table-monitor`、`backend-go/juhe-ai-audit-log-writer`。
6. 确认打包器的最终 bundle 内容校验通过；手工 `rg` 只用于复核，不是唯一门禁。
7. 按目标系统转到 [AI 部署执行清单](AI部署执行清单.md)，再进入 `docs/deploy/部署指南.md`。
