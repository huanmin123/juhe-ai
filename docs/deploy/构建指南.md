# 跨平台构建文档

> 本文只说明如何在 Windows、macOS、Linux 任一平台构建发布包。部署到目标机器的步骤见 `docs/deploy/部署指南.md`。
>
> 发布物自 X02（2026-09-04）起为 go-only 形态：Node 后端已归档清零，发布包只含 Go 三项目二进制、前端静态产物与运行脚本；仓库根的 `Jenkinsfile*` 是已废弃 K3s/Harbor 发布链的文件残留，不构成现行构建流程（见 [README](README.md) 已废弃清单）。

## 1. 兼容目标

当前发布体系按目标平台使用原生构建环境，不跨 MSYS/Windows POSIX 兼容层生成正式包：

| 构建平台 | 推荐命令 | 支持的部署目标 |
| --- | --- | --- |
| Windows | `pnpm package:release:windows` | Windows |
| macOS | `pnpm package:release:mac` | macOS；生产 Mac 包必须在目标 Mac 或受控原生 macOS 构建机生成 |
| Linux | `pnpm package:release:linux` | Linux |

发布包不包含当前机器的 `node_modules`，也不包含 Node 后端（Node 已于 2026-09-05 归档清零，历史 hybrid 包在目标机器执行 `pnpm install --prod` 安装 `@vscode/ripgrep` 的步骤随之退场）。发布包包含三个已交叉编译的 Go 项目：`juhe-ai-jobs` 承载 F1/F2，`juhe-ai-gateway` 承载 F3/F4，`juhe-ai-maintenance` 仅执行一次性维护命令；压缩包必须与部署目标的 `GOOS/GOARCH` 完全匹配。不要把 Linux 二进制部署到 macOS，或把 `amd64` 二进制部署到 `arm64` 主机。Go 原生日志搜索在进程内逐行扫描，不复用 `node_modules`，也不依赖 `rg`，目标主机无需安装任何额外二进制。macOS system `launchd` 部署应把 release 固定为“服务用户可读/可执行、不可写”；不要把 `node_modules` 或整个 release 递归交给服务用户写入。

## 2. 构建前必须检测

### Windows 构建机

```powershell
$PSVersionTable.PSVersion
node -v
node -p "process.version + ' LTS=' + (process.release.lts || '非LTS')"
corepack --version
pnpm -v
pnpm install --frozen-lockfile
tar --version
Test-Path package.json
Test-Path frontend/package.json
Test-Path backend-go/projects/gateway/go.mod
Test-Path backend-go/projects/jobs/go.mod
Test-Path backend-go/projects/maintenance/go.mod
```

### macOS 构建机

```bash
pwd
sw_vers
uname -a
node -v
node -p "process.version + ' LTS=' + (process.release.lts || '非LTS')"
corepack --version || true
pnpm -v || true
pnpm install --frozen-lockfile
go version
go -C backend-go env GOOS GOARCH
tar --version || bsdtar --version || true
test -f package.json
test -f frontend/package.json
test -f backend-go/projects/gateway/go.mod
test -f backend-go/projects/jobs/go.mod
test -f backend-go/projects/maintenance/go.mod
```

### Linux 构建机

```bash
pwd
uname -a
node -v
node -p "process.version + ' LTS=' + (process.release.lts || '非LTS')"
corepack --version || true
pnpm -v || true
pnpm install --frozen-lockfile
go version
go -C backend-go env GOOS GOARCH
tar --version
test -f package.json
test -f frontend/package.json
test -f backend-go/projects/gateway/go.mod
test -f backend-go/projects/jobs/go.mod
test -f backend-go/projects/maintenance/go.mod
```

必须确认：

- 当前目录是项目根目录。
- 发布包只能从固定提交的干净 Git worktree 构建；tracked、untracked 任一变更都会在构建前被拒绝。需要保留本地开发改动时，另建指向固定 release SHA 的干净 worktree，禁止用忽略参数绕过。
- Node.js 是官方 LTS，当前支持 22.x LTS（>=22.13.0）或 24.x LTS（>=24.11.0）；Node 后端已归档，构建机上的 Node.js 只用于前端构建与打包校验器（`validate-release-package.mjs` 等），不再有后端运行时预检。
- 发布构建机需要 Go `1.26.x`；脚本使用 `CGO_ENABLED=0` 交叉编译 `gateway`、`jobs`、`maintenance` 三个 Go 项目，部署目标不需要安装 Go。
- Unix 构建 `tar.gz` 需要 GNU tar 的 append/mode 能力，或 macOS BSD tar 的 `-r` 能力；脚本会按可用实现选择对应命令。BusyBox tar 不具备这两种完整能力时必须失败，不能手工拼接一个未经权限校验的归档。2026-08-11 已在目标 Intel Mac 以 BSD tar 生成并解包校验 F1/F2/F3 发布归档。
- pnpm 可用；不可用时先执行 `corepack enable`。首次签出、切换分支或 `pnpm-lock.yaml` 变化后，先执行 `pnpm install --frozen-lockfile`。
- 不要把构建机的 `node_modules` 放进发布包。
- 不要把真实 `.env`、任何 `data/`、`logs/`、SQLite 文件、数据库 dump、审计 payload、Redis 持久化文件或链接放进发布包。项目备份沿用相同内容边界，但正式升级恢复点必须归档升级前当前运行的 release，不能用待上线新包与升级前业务库配对。
- 不要把构建机的 `rg` 二进制跨平台放进发布包；Go 后端日志搜索为进程内逐行扫描，发布包与目标主机都不需要 `rg`（Node `@vscode/ripgrep` 路径已随 Node 归档退场）。
- 前端配置是构建时注入的，修改域名或网关展示地址后必须重新打包。
- `VITE_JUHE_AI_API_BASE_URL` 必须是严格的 `http://` 或 `https://` URL，或唯一允许的根相对值 `/__aisys__/api`；不接受其它根相对路径。HTTP(S) URL 必须有明确的非空 authority，且 path 以 `/__aisys__/api` 结尾，总长度不超过 2048 字符、path 不超过 1024 字符；不得包含 query、fragment、userinfo、无效端口、空白、反斜杠、authority percent escape 或畸形 percent escape。禁止传入盘符路径、UNC 路径或协议相对 URL。两个原生打包器都会在修改输出目录前拒绝非法配置。
- Windows 只允许从 PowerShell 运行 `package-release.ps1`。`package-release.sh` 在任何 Windows Bash（包括 `MINGW/MSYS/CYGWIN` 和 w64devkit）中都会立即失败；不得通过 `MSYS2_ARG_CONV_EXCL`、`MSYS2_ENV_CONV_EXCL` 或 `MSYS_NO_PATHCONV` 绕过。生产 Mac 包在原生 macOS 环境构建。
- 发布包只复制运行必需文件（Go 三项目二进制、`start.sh`/`start.ps1`、owner-manifest 与运行锁脚本、前端静态产物、`docs/deploy`）；回归、压测和 smoke 脚本不进入发布包。

## 3. 推荐构建命令

### Windows

```powershell
pnpm package:release:windows
```

等价显式命令：

```powershell
pwsh ./scripts/package-release.ps1
```

### macOS

```bash
pnpm package:release:mac
```

等价显式命令：

```bash
bash ./scripts/package-release.sh
```

### Linux

```bash
pnpm package:release:linux
```

等价显式命令：

```bash
bash ./scripts/package-release.sh
```

Unix 脚本默认将 `jobs`、`gateway` 与 `maintenance` 三个 Go 项目编译为当前 macOS/Linux 主机的 `GOOS/GOARCH`。开发场景可以显式选择目标，但生产发布使用与部署目标一致的原生构建机：

```bash
# Linux x86_64
bash ./scripts/package-release.sh --goos linux --goarch amd64

# Apple Silicon macOS
bash ./scripts/package-release.sh --goos darwin --goarch arm64
```

Unix 脚本只生成 macOS 或 Linux 的三个 Go 项目二进制；Windows 发布包使用 PowerShell 发布入口。

## 5. 常用构建参数

### 锁定发布提交

打包脚本始终检查工作树是否干净。正式发布还应显式传入计划中冻结的完整 40 位 commit SHA；当前 HEAD 不一致时立即失败：

Windows：

```powershell
pwsh ./scripts/package-release.ps1 -ExpectedCommit '<完整 release SHA>'
```

macOS / Linux：

```bash
bash ./scripts/package-release.sh --expected-commit '<完整 release SHA>'
```

生成目录和压缩包内的 `RELEASE_SOURCE_COMMIT` 必须与该 SHA 完全一致。部署侧校验 archive hash 时同时核对这个文件，不能只根据文件名推断版本。

打包脚本还会把同一个完整 SHA 作为 `VITE_JUHE_AI_BUILD_ID` 注入前端构建，并生成 `frontend/dist/build-info.json`。该变量属于发布脚本内部契约，不得由维护者手工填写、缩短或改成时间戳；否则当前页面与服务器版本的比较将失去可信来源。

### 固定公网网关地址

Windows：

```powershell
pwsh ./scripts/package-release.ps1 -FrontendGatewayBaseUrl "https://你的域名/v1"
```

macOS / Linux：

```bash
bash ./scripts/package-release.sh --frontend-gateway-base-url "https://你的域名/v1"
```

默认不传时：

```env
VITE_JUHE_AI_API_BASE_URL=/__aisys__/api
VITE_JUHE_AI_GATEWAY_BASE_URL=
```

含义：

- 管理后台请求同源 `/__aisys__/api`。
- API Key 页面按浏览器访问地址自动推断网关根地址；客户端也可以继续填写 `/v1` 地址。

不要从 Git Bash/MSYS 调用任何正式打包入口。需要显式传值时在 PowerShell 中执行：

```powershell
pwsh ./scripts/package-release.ps1 -FrontendApiBaseUrl '/__aisys__/api'
```

### 只生成一种压缩格式

Windows：

```powershell
pwsh ./scripts/package-release.ps1 -ArchiveFormat zip
pwsh ./scripts/package-release.ps1 -ArchiveFormat tar.gz
```

macOS / Linux：

```bash
bash ./scripts/package-release.sh --archive-format zip
bash ./scripts/package-release.sh --archive-format tar.gz
```

Linux 构建机如果没有 `zip` 命令，可以只生成 `tar.gz`。

### 真实配置禁止进入发布包

构建脚本不提供携带本地 `.env` 的参数。真实 `frontend/.env` 不得进入 release 或项目备份；生产恢复所需的环境文件只放在受限权限的 `business-*` 业务备份中。

## 6. 构建后检查

Windows：

```powershell
Test-Path release/juhe-ai-release.tar.gz
Test-Path release/juhe-ai-release.zip
tar -tzf release/juhe-ai-release.tar.gz | Select-Object -First 50
```

macOS / Linux：

```bash
test -f release/juhe-ai-release.tar.gz
tar -tzf release/juhe-ai-release.tar.gz | head -50
```

必须看到：

- `juhe-ai-release/start.sh`
- `juhe-ai-release/start.ps1`
- `juhe-ai-release/README.md`
- `juhe-ai-release/RELEASE_SOURCE_COMMIT`
- `juhe-ai-release/backend-go/juhe-ai-jobs`
- `juhe-ai-release/backend-go/juhe-ai-gateway`
- `juhe-ai-release/backend-go/juhe-ai-maintenance`
- `juhe-ai-release/frontend/dist/index.html`
- `juhe-ai-release/frontend/dist/build-info.json`
- `juhe-ai-release/deploy/owner-manifest.json`
- `juhe-ai-release/scripts/run-with-owner-lock.mjs`
- `juhe-ai-release/pnpm-lock.yaml`

`frontend/dist/build-info.json` 的 `buildId` 必须与 `RELEASE_SOURCE_COMMIT` 完全一致。后端以 `no-cache` 提供该清单，供前端只在动态资源加载失败时判断是否确有版本变化；它不是服务启停记录，也不触发后台轮询。

打包器在构建开始前校验 API base 输入，在归档前调用 `scripts/validate-release-package.mjs` 检查发布包结构、链接、真实环境文件、日志和持久化数据。它不解析压缩后的 JavaScript bundle，也不从产物反推构建配置。

构建完成后可用以下命令做事故形态的诊断复核，但它不是语义解析器，也不能替代 candidate 浏览器验证：

```powershell
rg -l -F '/__aisys__/api' release/juhe-ai-release/frontend/dist/assets
rg -n '[A-Za-z]:[\\/].*__aisys__[\\/]api' release/juhe-ai-release/frontend/dist
```

第二条必须没有输出；第一条只用于快速定位构建结果，不作为对压缩 bundle 的完整语义证明。静态 `index.html`、health `200` 和 `build-info.json` 都不能证明 Axios 请求可用，candidate 部署后必须使用登录态浏览器打开真实业务页并观察 API 请求成功。

Go 后端的日志搜索在进程内逐行扫描保留的 `.log` 文件，不依赖 `rg` 或任何外部二进制（Node 的 `@vscode/ripgrep` 路径已随 Node 归档退场）。发布包不跨平台内置 `rg` 二进制，目标机器也无需安装。

## 7. 给 AI 的构建摘要

1. 先判断构建机系统：Windows、macOS 或 Linux。
2. 检查 Node.js LTS、Go 工具链、pnpm、tar 和项目根目录。
3. 使用对应 `package:release:*` 命令构建。
4. 不要打包 `node_modules`。
5. 检查发布包同时包含 `start.sh`、`start.ps1` 以及与部署目标匹配的 `backend-go/juhe-ai-jobs`、`backend-go/juhe-ai-gateway`、`backend-go/juhe-ai-maintenance`。
6. Windows 只用 PowerShell，macOS/Linux 只用原生 Unix 环境；生产 Mac 包在原生 macOS 构建。
7. candidate 必须完成真实登录业务页验证；不得用 bundle 文本扫描或单个 `200` 替代。
8. 按目标系统进入 `docs/deploy/部署指南.md`（国内单机 Docker，唯一生产形态）；Linux 发布包直跑差异见 `docs/deploy/linux/`。
