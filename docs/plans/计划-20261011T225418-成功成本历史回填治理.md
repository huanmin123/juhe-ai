# 计划：成功成本历史回填治理（ensure-schema 重复全表扫根治）

- **状态**：已实施（2026-10-12 复审修订后当日完成代码交付，独立复审无 blocker）：三处回填卸载、marker 表 DDL、`--apply-success-cost-backfill` 子命令、双路径扣减 CASE 补正、测试与部署文档同步均已落地；待办：生产维护窗口按 §4 执行、PG 隔离 scratch 批时长实测。修订记录见 §7。
- **日期**：2026-10-11（2026-10-12 复审修订并实施）
- **来源**：[信封差异与慢查询处置复核报告](../reports/信封差异与慢查询处置复核报告-2026-10-11.md) §4；BUG-0307 观察项 2。
- **裁决记录**（用户已拍板，2026-10-11）：首次回填与聚合写者的协调采用**受控维护窗口**；迟到补正采用**扣减事务内补正**（根治，部分索引过渡方案否决）；总原则为彻底根治、不做临时方案。

## 1. 背景与根因

`UPDATE usage_stats_minute SET success_cost_usd = total_cost_usd WHERE error_count = 0 AND success_cost_usd <> total_cost_usd` 及同款共 **6 条**（totals/minute/hourly/daily/weekly/monthly，`pg_schema_stats.go:2182-2207`）作为 schema statements 在**每次** `EnsurePostgres` 遍历执行；SQLite `ensureSQLiteStatsSuccessCostColumns`（`sqlite_schema.go:520`）每次执行同谓词回填。没有任何完成标记——"数据已相等时重复执行不改值"成立，但"重复执行无扫描成本"不成立：`usage_stats_minute` 24 万行全扫 UPDATE 生产实测 max 234s。

同根源第二个缺陷：删失败记录会把历史混合行从 `(error_count=1, total=10, success=0)` 扣成 `(0, 8, 0)`；此后回填谓词命中会补成 `(0, 8, 8)`（现状的迟到补正），但若只加完成标记删掉回填，这行会永远停在 0。**所以一次性迁移与运行中补正必须一起交付**，不能单独加标记了事。

## 2. 目标与非目标

**目标**：
1. `ensure-schema` 不再对六表执行回填扫描——结构保证与数据迁移职责分离（BUG-0307 教训：schema 保证收敛到显式运维动作）。
2. 历史回填一次性、可恢复、可重跑；中断不丢行、不重复改值。
3. 删失败记录后迟到符合谓词的行，在**扣减事务提交时**即得到补正，不依赖任何后续全表扫描。
4. 新库、存量库、中断库、已回填无标记库（生产现状）四形态全部明确承接，无需用户手工宣告。

**非目标**：不改聚合写入口径（upsert 的 success_cost 参数本就按记录 success 标志给出）；不改分钟/分层聚合调度；不做部分索引；不新增 feature flag。

## 3. 设计

### 3.1 完成标记：新专用表（PG + SQLite 同构）

```sql
CREATE TABLE IF NOT EXISTS backfill_progress (
  table_name   text PRIMARY KEY,
  status       text NOT NULL,        -- running / done
  cursor_json  text NOT NULL DEFAULT '{}',  -- 各表主键 tuple 游标
  updated_at   text NOT NULL
);
```

- 建表 DDL 加入 PG/SQLite schema statements（幂等轻量，保留在 ensure 内）。
- 不复用 `stats_job_state`：其 cursor 语义与 jobs 状态机耦合，回填完成态混进 jobs 运行态会污染 lag/心跳语义。

### 3.2 回填执行者：maintenance 新一次性子命令

`juhe-ai-maintenance --apply-success-cost-backfill [--dry-run]`：

1. 对六表逐表检查 `backfill_progress`：`done` → 跳过（只查一行主键，零事实表触碰）。
2. 无记录/`running` → 按主键 tuple 游标分批回填：`WHERE (pk...) > (cursor...) ORDER BY pk... LIMIT 5000`，批内语句为 `UPDATE ... SET success_cost_usd = total_cost_usd WHERE pk 范围 AND error_count = 0 AND success_cost_usd <> total_cost_usd`（谓词在行锁后的当前值上重判，不用批前读取值写回），**cursor 推进与批修改同一事务提交**；失败保留原始错误，重跑从持久化 cursor 继续。
3. 全表扫完 → `status='done'`，清 cursor。
4. `--dry-run` 只统计各表待回填行数，不修改。

**四形态承接规则**（统一为"无 marker 就从头分批跑"，无需区分）：

| 形态 | 行为 |
| --- | --- |
| 新库 | 表为空，0 批即 done（秒级） |
| 存量库未回填 | 分批迁移，分钟级 |
| 存量库已回填无 marker（生产现状） | 分批扫过，批 UPDATE 命中 0 行，自然收敛到 done（有界核对） |
| 中断库 | 从持久化 cursor 续跑 |

**回填扫描点共三处，全部卸载**（2026-10-12 复审修订：原稿漏计 jobs 侧第三处）：

| 位置 | 现状 | 处置 |
| --- | --- | --- |
| `maintenance` PG `EnsurePostgres`（`pg_schema_stats.go:2182-2207` 六条 UPDATE statements） | 每次 ensure 全表扫六表 | statements 从列表删除 |
| `maintenance` SQLite `ensureSQLiteStatsSuccessCostColumns`（`sqlite_schema.go:520`） | 每次 ensure 全表扫六表 | 只保留 ADD COLUMN 守卫，删除回填循环 |
| `jobs` `statsverify.ensureStatsSuccessCostBackfill`（`statsverify/store.go:552`，`store.go:178` 在 SQLite 模式 `EnsureSchema` 内调用） | 每次建/校验 statsverify stats 库对 `usage_stats_daily`/`usage_stats_hourly` 全表扫 | 删除调用与函数；该面与生产 stats SQLite 同文件时由同一次子命令覆盖（marker 同库生效），独立测试库由各自实例跑子命令收敛 |

`statsverify` PG 模式现状只校验 schema 不回填（fail-closed），保持不变。

ensure 遇到 `running`/缺失 marker 时不自动迁移，仅在结果摘要输出提示"存在待回填表，请在维护窗口执行 --apply-success-cost-backfill"。回填职责唯一收敛到 `--apply-success-cost-backfill` 子命令，除此之外代码中不得再有同谓词全表 UPDATE（验收含 `rg "SET success_cost_usd = total_cost_usd"` 仅命中子命令与测试夹具）。

### 3.3 受控维护窗口（用户裁决）

runbook 步骤（写入国内单机运维手册与部署指南初始化序列；命令形态对齐现行维护序列——`docker/single-server/README.md` 与运维手册 `--ensure-schema --seed --driver postgres --dsn "$JUHE_AI_POSTGRES_URL"` 同源，DSN/secret 从宿主 `.env` 读取，compose run 直接传参）：

```bash
# 0) 前置：发布含子命令的新版三二进制（deploy.sh all）
# 1) 建 marker 表（幂等；本批新增 backfill_progress DDL 随 schema statements 生效）
docker compose run --rm maintenance --ensure-schema --driver postgres --dsn "$JUHE_AI_POSTGRES_URL"
# 2) 停全部聚合/扣减/清理写者
docker compose stop jobs
# 3) 预检：只读统计各表待回填行数（期望生产为 0，因旧回填随最近一次 ensure 已收敛；非 0 属历史遗留错口径行）
docker compose run --rm maintenance --apply-success-cost-backfill --dry-run --driver postgres --dsn "$JUHE_AI_POSTGRES_URL"
# 4) 一次性回填（输出六表批数/命中行数；重复执行零批秒完）
docker compose run --rm maintenance --apply-success-cost-backfill --driver postgres --dsn "$JUHE_AI_POSTGRES_URL"
# 5) 恢复写者（聚合游标增量消费）
docker compose start jobs
# 6) 复核：backfill_progress 六行全 done；jobs 启动后 spool 积压消费归零
```

SQLite 形态（单机直跑/开发）同构：`--driver sqlite --paths "stats=<stats 库文件>,..."`（paths 键集见 maintenance CLI 契约），同样先 `--ensure-schema` 再子命令。

**停摆安全性依据（2026-10-12 复审修订：补齐 gateway 异步链路证据）**：

- jobs 侧：`AggregateUsageStatsBatch` 是持久游标增量消费（`stats_job_state` cursor + 安全延迟），jobs 重启后从上次位置继续；`stop jobs` 前已进入 writer/spool 的记录由 ingest gate 保护，不丢。
- gateway 侧（原稿"gateway 不写六表、无需停"表述不精确，修正）：gateway 不直接写六表，但经**异步 buffer → spool → jobs 消费**间接写：`spooledUsageRecorder` 入队先进进程内有界 buffer（`chain_usage.go:74`，默认 4096），由后台 drain goroutine 交付 spool/Redis。窗口内 **不停 gateway**：spool 是持久文件，已入 buffer 的记录会被 drain 落盘，jobs 恢复后由 usagespooldrain 照常消费聚合——**零丢失，统计可见性延迟至 jobs 追平**。gateway 优雅停机（发布重启）已先 drain buffer 再退出（`Close()`，`chain_usage.go:216`），不因停机丢记录；仅 gateway 进程崩溃可能丢进程内未落盘记录——这是常态运行固有风险，不因本窗口引入或放大，不在本 runbook 处置范围。
- 回填与恢复后增量无冲突：回填只改历史错口径行（批内谓词在行锁后当前值重判），恢复后的聚合写入本就按记录 success 标志给出正确口径（§2 非目标），两者无行级竞争。
- 回放验收：窗口结束 jobs 启动后，spool 目录积压文件数回落到 0（或稳态水位），六表行数/增量恢复——写入运维手册验证步骤。

发布版内嵌该子命令后，**发布到窗口执行之间**迟到补正暂时缺席（旧回填已卸载）——runbook 规定发布同窗口内立即执行子命令，间隔压缩到分钟级；扣减补正 CASE（3.4）随代码上线，在该间隔内删失败记录产生的 `(0,8,0)` 行由窗口回填兜住（谓词在批内重判）。发布窗口纪律沿用现状：避开 04:00-07:00 备份窗口（BUG-0254）。

### 3.4 扣减事务内补正（用户裁决，根治；2026-10-12 复审修订：SQLite/PG 双路径分别落）

**路径事实**：扣减写路径按存储分两套——SQLite 走 `statssubtract.go` 的 `subtractUsageStatsRecord → subtractStatsTotalsAndBuckets`（列表达式由 `statsSubtractSetExpr` 生成，`statssubtract.go:358`）；生产 PostgreSQL 走独立家族 `subtractPostgresUsageStatsRows → subtractPostgresUsageStatsTotals`（`statssubtractpostgres.go:683`）与 `subtractPostgresUsageStatsTimeBucket`（`statssubtractpostgres.go:744`），其 `success_cost_usd` 现为裸 `GREATEST(0, success_cost_usd - ?)`（`statssubtractpostgres.go:706`）。**只改 `statsSubtractSetExpr` 覆盖不到生产 PG**——两套必须分别落，语义保持一致。

补正语义（两路径同一）：`success_cost_usd` 的赋值从裸下限保护改为按**扣减后的值**重判谓词——删除失败记录使该行 `error_count` 扣减后归零、且成功成本与总成本扣减后不一致时，成功成本直接取扣减后的总成本；混合行（扣减后 `error_count` 仍 >0）与其他情形维持原扣减结果。

**SQLite 表达式**（`statsSubtractSetExpr`，`MAX` 形式；totals 与 5 个时间桶共用一次改动生效）：

```sql
success_cost_usd = CASE
  WHEN MAX(0, error_count - ?) = 0
       AND MAX(0, total_cost_usd - ?) <> MAX(0, success_cost_usd - ?)
  THEN MAX(0, total_cost_usd - ?)
  ELSE MAX(0, success_cost_usd - ?)
END
```

**PostgreSQL 表达式**（`subtractPostgresUsageStatsTotals` 与 `subtractPostgresUsageStatsTimeBucket` 两处 SET 中的 `success_cost_usd` 行，`GREATEST` 形式）：

```sql
success_cost_usd = CASE
  WHEN GREATEST(0, error_count - ?) = 0
       AND GREATEST(0, total_cost_usd - ?) <> GREATEST(0, success_cost_usd - ?)
  THEN GREATEST(0, total_cost_usd - ?)
  ELSE GREATEST(0, success_cost_usd - ?)
END
```

- 参数绑定：CASE 新增占位符复制同行既有扣减参数（error_count/total_cost_usd/success_cost_usd 的同一扣减值），绑定顺序与各路径 SET 列表参数序一致；不引入新参数语义。
- 事务边界：两路径的补正都在**既有扣减事务内**（调用方 `tx`），与同事务其他列扣减同提交同回滚，无新增事务；谓词在行锁后的当前值上重判（UPDATE 内联表达式），单行原子。
- 全零行条件 DELETE 不变（补正后 `(0,8,8)` 非零，不会被误删）；PG 侧 `deleteEmptyPostgresUsageStatsTotal`（`statssubtractpostgres.go:729`）同断言回归。
- 可见时点变化：补正从"下次 ensure-schema"提前到"扣减事务提交时"——同步《统计指标与分层聚合设计.md》success_cost_usd 语义节（本轮复审修订已补齐，见 §6）。

### 3.5 并发边界

- 维护窗口内六表唯一写者是回填子命令 → 首次迁移无写者竞争（用户裁决路径，报告中"写路径协调"方案否决）。
- 窗口外的迟到补正只发生在扣减事务内（行锁后当前值重判，单行原子）——不存在跨事务竞争窗口。
- 双 maintenance runner 同时跑子命令：`backfill_progress` 行级 `UPDATE ... WHERE status='running' AND cursor_json=期望值` 做 cursor CAS，后进者从持久 cursor 续跑或因批幂等（谓词重判）无害重做；文档明确"窗口内只跑一个实例"为运维约定，CAS 为防御而非依赖。
