# 计划：成功成本历史回填治理（ensure-schema 重复全表扫根治）

- **状态**：待用户审核；审核通过前不改代码。
- **日期**：2026-10-11
- **来源**：[信封差异与慢查询处置复核报告](../reports/信封差异与慢查询处置复核报告-2026-10-11.md) §4；BUG-0307 观察项 2。
- **裁决记录**（用户已拍板，2026-10-11）：首次回填与聚合写者的协调采用**受控维护窗口**；迟到补正采用**扣减事务内补正**（根治，部分索引过渡方案否决）；总原则为彻底根治、不做临时方案。

## 1. 背景与根因

`UPDATE usage_stats_minute SET success_cost_usd = total_cost_usd WHERE error_count = 0 AND success_cost_usd <> total_cost_usd` 及同款共 **6 条**（totals/minute/hourly/daily/weekly/monthly，`pg_schema_stats.go:2182-2207`）作为 schema statements 在**每次** `EnsurePostgres` 遍历执行；SQLite `ensureSQLiteStatsSuccessCostColumns`（`sqlite_schema.go:520`）每次执行同谓词回填。没有任何完成标记——"数据已相等时重复执行不改值"成立，但"重复执行无扫描成本"不成立：`usage_stats_minute` 24 万行全扫 UPDATE 生产实测 max 234s。

同根源第二个缺陷：删失败记录会把历史混合行从 `(error_count=1, total=10, success=0)` 扣成 `(0, 8, 0)`；此后回填谓词命中会补成 `(0, 8, 8)`（现状的迟到补正），但若只加完成标记删掉回填，这行会永远停在 0。**所以一次性迁移与运行中补正必须一起交付**，不能单独加标记了事。

## 2. 目标与非目标

**目标**：
1. `ensure-schema` 不再对六表执行回填扫描——结构保证与数据迁移职责分离（BUG-0307 教训：schema 保证收敛到显式运维动作）。
2. 历史回填一次性、可恢复、可重跑；中断不丢行、不重复改值。
3. 删失败记录后迟到符合谓词的行，在**扣减事务提交时**即得到补正，不依赖任何后续全表扫描。
4. 新库、存量库、中断库、已回填无标记库（生产现状）四形态全部明确承接，无需用户手工宣告。

**非目标**：不改聚合写入口径（upsert 的 success_cost 参数本就按记录 success 标志给出）；不改分钟/分层聚合调度；不做部分索引；不新增 feature flag。

## 3. 设计

### 3.1 完成标记：新专用表（PG + SQLite 同构）

```sql
CREATE TABLE IF NOT EXISTS backfill_progress (
  table_name   text PRIMARY KEY,
  status       text NOT NULL,        -- running / done
  cursor_json  text NOT NULL DEFAULT '{}',  -- 各表主键 tuple 游标
  updated_at   text NOT NULL
);
```

- 建表 DDL 加入 PG/SQLite schema statements（幂等轻量，保留在 ensure 内）。
- 不复用 `stats_job_state`：其 cursor 语义与 jobs 状态机耦合，回填完成态混进 jobs 运行态会污染 lag/心跳语义。

### 3.2 回填执行者：maintenance 新一次性子命令

`juhe-ai-maintenance --apply-success-cost-backfill [--dry-run]`：

1. 对六表逐表检查 `backfill_progress`：`done` → 跳过（只查一行主键，零事实表触碰）。
2. 无记录/`running` → 按主键 tuple 游标分批回填：`WHERE (pk...) > (cursor...) ORDER BY pk... LIMIT 5000`，批内语句为 `UPDATE ... SET success_cost_usd = total_cost_usd WHERE pk 范围 AND error_count = 0 AND success_cost_usd <> total_cost_usd`（谓词在行锁后的当前值上重判，不用批前读取值写回），**cursor 推进与批修改同一事务提交**；失败保留原始错误，重跑从持久化 cursor 继续。
3. 全表扫完 → `status='done'`，清 cursor。
4. `--dry-run` 只统计各表待回填行数，不修改。

**四形态承接规则**（统一为"无 marker 就从头分批跑"，无需区分）：

| 形态 | 行为 |
| --- | --- |
| 新库 | 表为空，0 批即 done（秒级） |
| 存量库未回填 | 分批迁移，分钟级 |
| 存量库已回填无 marker（生产现状） | 分批扫过，批 UPDATE 命中 0 行，自然收敛到 done（有界核对） |
| 中断库 | 从持久化 cursor 续跑 |

`EnsurePostgres`/`ensureSQLiteStats` **彻底卸载回填职责**：六条 UPDATE statements 从列表删除；SQLite `ensureSQLiteStatsSuccessCostColumns` 只保留 ADD COLUMN 守卫、删除回填循环。ensure 遇到 `running`/缺失 marker 时不自动迁移，仅在结果摘要输出提示"存在待回填表，请在维护窗口执行 --apply-success-cost-backfill"。

### 3.3 受控维护窗口（用户裁决）

runbook 步骤（写入国内单机运维手册与部署指南初始化序列）：

```bash
docker compose stop jobs        # 聚合/扣减/清理写者全部停止
docker compose run --rm maintenance --apply-success-cost-backfill
docker compose start jobs       # 聚合游标增量消费，停摆窗口零丢失
```

停摆安全性依据：`AggregateUsageStatsBatch` 是持久游标增量消费（`stats_job_state` cursor + 安全延迟），jobs 重启后从上次位置继续，窗口内的 usage 记录照常聚合，无窗口丢数。gateway 不写六表（只读查询），无需停。

发布版内嵌该子命令后，**发布到窗口执行之间**迟到补正暂时缺席（旧回填已卸载）——runbook 规定发布同窗口内立即执行子命令，间隔压缩到分钟级；扣减补正 CASE（3.4）随代码上线，在该间隔内删失败记录产生的 `(0,8,0)` 行由窗口回填兜住（谓词在批内重判）。

### 3.4 扣减事务内补正（用户裁决，根治）

`cleanuprepo/statssubtract.go` 的 `statsSubtractSetExpr` 中 `success_cost_usd` 的赋值从裸 `MAX(0, success_cost_usd - ?)` 改为按**扣减后的值**重判谓词：

```sql
success_cost_usd = CASE
  WHEN MAX(0, error_count - ?) = 0
       AND MAX(0, total_cost_usd - ?) <> MAX(0, success_cost_usd - ?)
  THEN MAX(0, total_cost_usd - ?)
  ELSE MAX(0, success_cost_usd - ?)
END
```

- 该表达式被 totals 与 5 个时间桶共用，一次改动六表生效。
- 语义：删除失败记录使某行 `error_count` 归零且成功成本与总成本不一致时，成功成本直接取扣减后的总成本；混合行（error_count 仍 >0）与其他情形维持原扣减结果。
- 全零行条件 DELETE 不变（补正后 `(0,8,8)` 非零，不会被误删）。
- 可见时点变化：补正从"下次 ensure-schema"提前到"扣减事务提交时"——需同步《统计指标与分层聚合设计.md》的 success_cost_usd 语义节。

### 3.5 并发边界

- 维护窗口内六表唯一写者是回填子命令 → 首次迁移无写者竞争（用户裁决路径，报告中"写路径协调"方案否决）。
- 窗口外的迟到补正只发生在扣减事务内（行锁后当前值重判，单行原子）——不存在跨事务竞争窗口。
- 双 maintenance runner 同时跑子命令：`backfill_progress` 行级 `UPDATE ... WHERE status='running' AND cursor_json=期望值` 做 cursor CAS，后进者从持久 cursor 续跑或因批幂等（谓词重判）无害重做；文档明确"窗口内只跑一个实例"为运维约定，CAS 为防御而非依赖。

## 4. 上线顺序

1. 发布代码（含：marker 表 DDL、ensure 卸载回填、扣减 CASE 补正、新子命令）——gateway/jobs/maintenance 三二进制同版。
2. 同窗口执行：`stop jobs` → `--apply-success-cost-backfill` → `start jobs`。
3. 复核：子命令输出六表批数/命中行数；`backfill_progress` 六行全 `done`；二次执行应零批秒完。

## 5. 验收清单

- [ ] 新库：ensure 建表含 marker；子命令 0 批 done；ensure 二次执行 StatementCount 不含六条回填。
- [ ] 旧库等价：预置 `(0,8,8)` 不变、`(1,10,0)` 不动（混合行不臆算）、`(0,10,0)→(0,10,10)`、`(0,10,10)` 无改动；marker 收敛 done。
- [ ] 中断恢复：批 N 后杀进程，重跑从 cursor 续跑，行不丢不重改。
- [ ] 扣减补正：删失败记录 `(1,10,0)→(0,8,8)`；删成功记录混合行 `(1,10,6)` 扣减后仍混合不补正；重试扣减幂等；全零行 DELETE 不回归。
- [ ] PG/SQLite 双模确定性测试全绿；PG 侧隔离 scratch 实测批时长与锁持有（验收线：单批 < 1s、无长事务告警）。
- [ ] 生产执行后 `pg_stat_statements` 中六表回填 UPDATE 归零（marker 短路）。
