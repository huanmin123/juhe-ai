## 需求目标

- 背景：部分上游不希望账户被系统后台自动探测。现有机制没有账户级总开关，`temporaryUnavailableContinuousProbeEnabled`（持续恢复探活）只控制 `temporary_unavailable` 在 10 分钟有界确认后是否继续长期低频恢复，不能覆盖周期健康检查、首次激活、请求失败二次确认、运行态/电路恢复、定时模型检测等后台探测。
- 目标：新增账户级「后台自动探测」总开关。关闭后，系统不再对该账户发起任何后台自动探测请求；真实用户请求和用户主动触发的手动测试/刷新/检测不受影响。关闭总开关的账户健康状态收敛为「正常 / 异常」二态，不出现待检查、冷却、限流、质量隔离、恢复中等过程状态。
- 交付物：账户字段与 API、后台探针调度门禁、运行态清理与状态归一化、前端开关与二态状态展示、文档更新、Mock/回归测试与验证记录。

## 口径与术语

- **口径对齐**：用户所说的「禁止被动」= 关闭系统后台自动探测；「不禁止主动」= 用户显式点击的手动测试/刷新/检测保持可用。
- **后台自动探测**：由系统定时、状态机、队列或后台任务自动发起、无需用户当次操作的上游请求。本开关只控制这一类。
- **主动操作**：用户在页面显式点击的「测试」「刷新余额」「立即检测」「同步上游模型」等。**不在本开关范围，不禁止、不拦截**。
- **余额刷新**：属于余额查询功能自己的开关与调度范围，**本计划不修改、不暂停、不纳入总开关**。
- **真实用户请求**：`/v1` 等业务流量，始终不受本开关影响；请求级切号、重试、候选排除、IP/传输局部回避和请求预算保持现状。
- **二态健康状态**：关闭后台自动探测的账户只有「正常 / 异常」两种健康状态，不展示或建立 `pending_test`、`temporary_unavailable`、`rate_limited`、`quality_isolated`、`precheck_pending`、`runtime_degraded` 等账户健康过程态；`latency_degraded` 仍属请求级速度排序状态，可由真实流量建立，但不作为账户健康状态展示；`disabled` 是人工停用操作，单独展示，不计入健康状态。
- **凭据生命周期**：OAuth token 刷新 / keepalive 不属于探测，保持现状。

## 方案概述

### 数据变化

- `accounts` 新增：
  - `background_probe_enabled integer NOT NULL DEFAULT 1 CHECK (background_probe_enabled IN (0,1))`
- 语义：`1` = 允许后台自动探测（默认）；`0` = 禁止后台自动探测。
- 存量账户默认 `1`，行为零变化。
- 该字段属于账户配置，变更时 `config_revision + 1`；在途探针结果因版本/代次不匹配自动丢弃。

### 接口变化

- 账户创建 / 更新 / PATCH / 详情 / 列表 / 克隆 / 导入导出 / OAuth 托管创建 / 授权实例 provision 增加 `backgroundProbeEnabled`。
- 列表与健康监控响应增加 `backgroundProbeEnabled`，供前端展示「手动」标记。
- 授权实例只读继承来源账户值，不接受实例侧单独修改。
- 关闭/开启写审计事件：`account_background_probe_disabled` / `account_background_probe_enabled`，记录清理的运行态与待处理任务数量。

### 后端变化

- **候选筛选**：所有后台探针候选查询增加 `background_probe_enabled = 1`；授权实例同时检查 `source.background_probe_enabled = 1`。
- **派发前守卫**：后台探针在真正构造上游请求前重读账户 `config_revision + background_probe_enabled`；关闭则返回 `probe_skipped_disabled`，不发请求、不写健康事实、不写 usage、不推进状态。
- **手动操作例外**：手动测试、手动刷新、手动检测走显式 `trigger=manual` 路径，不经过后台探针门禁；共享执行器如被复用，必须显式区分 `background` / `manual`，禁止误伤手动操作。
- **关闭清理**：新增 `DisableBackgroundProbe(accountID)` 服务，同一事务改字段、清 DB 运行态、取消 pending outbox，并推进 dispatch fence 入队 `dispatch_revision_changed` 关闭事件；Redis 运行态与 circuit incident 经既有链路异步收敛（jobs 控制面投影关 incident；提交后运行时重置链路端口清 latency 降级 / Key 运行态池 / 运行时缓存投影，端口缺席降级为仅 DB 清理并审计注明）；`config_revision` 递增作为最终围栏。
- **开启恢复**：状态为 `active` 时设置 `next_health_check_at = now` 并投递一次健康检查；`error` / `disabled` 不自动探测，按人工处理路径恢复。关闭期间不允许出现 `pending_test`，因此不存在「重新开启后补激活检查」的语义。

### 前端变化

- 账户高级配置「稳定性与锁死」卡片顶部新增「后台自动探测」总开关，默认开启。
- 总开关关闭时：
  - 「持续恢复探活」子开关置灰，提示「仅在后台自动探测开启时生效」；
  - 显示后台自动探测关闭提示：系统不会自动检查/恢复本账户，手动测试和真实请求不受影响；
  - 账户健康状态只显示「正常 / 异常」：`active` → 正常，`error` → 异常；`disabled` 单独显示「停用」，不计入健康状态；
  - 不显示 `待检查`、`临时不可调用`、`限流中`、`质量隔离`、`待探针确认`、`调度降级`、`恢复中` 等过程态标签；
  - 账户列表状态标签组增加「手动」灰色标签；
  - 健康监控页账户卡片状态只显示「正常 / 异常」，增加「手动」标签，最近/下次独立检查显示「不适用」；
  - 不提供「重新检查」入口；「异常恢复」只做人工状态处理，不投递后台检查；
  - 表单状态选项只提供「正常 / 停用」；「异常」为系统只读状态，不作为可提交选项。
  - 特供、锁死等依赖自动恢复的功能按「手动模式功能可用性」矩阵置灰；切换为手动模式时自动取消特供、解除锁死并清理运行态。
- 关闭确认弹窗必须列出将被清除的过程态：待检查、冷却/临时不可调用、限流、运行态降级、待探针确认；质量隔离说明为「保留为异常，需人工解除」。
- 余额查询卡片**不改**：余额刷新不纳入本开关。

## 状态模型：关闭后健康状态只有「正常 / 异常」两态（停用为人工操作）

关闭后台自动探测的账户不使用现有探测过程态，健康状态只有：

| 健康状态 | 存储状态 | 调度 |
| --- | --- | --- |
| 正常 | `active` | 参与正常调度 |
| 异常 | `error` | 不参与调度，等待人工处理 |
| （人工停用） | `disabled` | 不参与调度；属于人工操作，不视为探测过程态 |

- 这类账户不允许 `pending_test`、`temporary_unavailable`、`rate_limited`、`quality_isolated` 作为健康状态；创建/编辑时提交这些状态应返回 400。
- `error`（异常）只由人工操作、本地可验证硬错误或已有 `quality_isolated` 转换写入；真实请求失败不自动写异常，避免无后台探测时进入无法自动恢复的死状态。
- 关闭账户的「异常恢复」直接写 `active`（正常），不经过 `pending_test`，不投递后台检查；恢复后由真实流量验收。
- 关闭总开关时，同一事务内：
  - `pending_test` → `active`，不执行首次激活检查；真实流量就是验收；
  - `temporary_unavailable` / `rate_limited` 一律 → `error`（2026-10-30 复审修订：显式策略 / 系统额度冷却与探针冷却共用同一 `cooldown_retest_generation` fence，来源标记不可靠，全部转异常保留人工恢复，不覆盖用户显式策略意图），清空冷却列族；
  - `quality_isolated` → `error`（异常），保留质量处罚，不自动解除；质量隔离恢复探针不再运行；
  - 同请求显式 `status` 输入优先，不被归一化覆盖；
  - `error` 保持 `error`，不自动恢复；
  - `disabled` 保持 `disabled`。
- 关闭确认弹窗必须明确提示「将清除待检查 / 冷却 / 限流状态；质量隔离保留为异常；如账户实际不可用，真实请求会失败并切号，可手动停用」。
- 关闭时的清理范围：
  - `recovery_wait` / `failure_observed` / `precheck_pending` / `runtime_degraded`：清理，取消 due 任务与半开租约；已有 `latency_degraded` 一并清理，后续仅由真实流量建立；
  - circuit `SUSPECT` / `OPEN` / `HALF_OPEN` / `RECOVERING`：关闭该账户相关 incident，写审计原因；
  - Key 冷却 / key-model memory 状态：清理探针派生状态；
  - `last_health_check_*` / `health_check_failure_count` / `next_health_check_at`：停止更新并清空计划与失败计数；历史检查时间可保留展示为「关闭前」。
- `latency_degraded` 仍可由真实流量建立，只影响速度优先排序，不作为账户健康状态展示；后台恢复探针不运行，按 TTL 或真实流量恢复。
- 显式用户策略（如响应拦截 TTL、`local_suppressed`）仍按配置执行请求级动作，但不再写持久冷却/限流/质量隔离过程态；这类策略不改变二态健康状态，只影响请求级避让。

## 手动模式功能可用性

关闭后台自动探测后，账户进入「手动模式」。依赖后台探测或自动恢复的功能不开放：

| 功能 | 手动模式处理 |
| --- | --- |
| 特供恢复 | 不可用；进入手动模式时自动取消并释放特供名额；列表操作置灰 |
| 账户锁死 | 不可用；进入手动模式时自动解除锁死并清理 lock 运行态；列表操作置灰，死期/重试间隔字段隐藏或只读 |
| 持续恢复探活 | 子开关置灰，不生效 |
| 自动激活 / 待检查 | 不执行；账户直接正常 |
| 冷却 / 限流自动恢复 | 不执行；已有过程态按二态规则归一化 |
| Key 冷却 / Key-model 自动恢复 | 不执行；已有状态清理；不建立后台探测派生的 Key 运行态 |
| 质量隔离自动恢复 | 不执行；已有 `quality_isolated` 转异常 |
| 速度优先首字恢复探针 | 不执行；`latency_degraded` 仍可请求级建立，不作为健康状态 |
| 定时模型检测 | 暂停 |
| 手动模型检测 | 完整保留（含 `quality_isolate` / `disable` 处罚）；处罚产生的状态无自动恢复，人工解除 |
| 账户错误策略（`retry_next` / `temp_unschedulable` / `rate_limited` / `error_disabled`） | 完整保留，属于账户所有者显式配置；策略产生的冷却 / 限流无自动恢复，人工「恢复正常」 |
| 响应拦截策略（含 `avoid_account_ttl`） | 完整保留，属于账户所有者显式配置；TTL 避让按自身到期或人工恢复 |
| 迁移流量 | 完整保留全部选项 |
| 系统额度规则 | 保留现状；产生的 `rate_limited` 无自动恢复，人工「恢复正常」 |
| 账户电路 / 运行态建立 | 不建立；真实流量只做请求级排除，不写账户级 circuit / 运行态 |
| 时间计划 / 超级优先 / 降级备用 / 会话亲和 / 并发 / 代理 | 保留 |
| 余额查询 / 刷新 | 不纳入本开关，保持现状 |
| OAuth token 刷新 / keepalive | 保留 |

- 特供、锁死、持续恢复探活、自动激活、冷却/限流/质量隔离恢复都属于“依赖被动恢复”的功能；手动模式不开放。
- 账户错误策略、响应拦截、迁移流量、手动模型检测是账户所有者的显式配置，不属于被动探测；手动模式完整保留。注意：这类配置产生的冷却 / 限流 / 质量隔离状态在手动模式下只能人工恢复（对应的自动恢复探针已关闭）。
- 超级优先、降级备用、时间计划、会话亲和、并发、代理、模型映射、余额查询不依赖被动恢复，保持可用。
- `latency_degraded` 是请求级速度排序，不是账户健康状态；手动模式保留其真实流量行为，但不运行后台恢复探针。

## 真实请求切号 / 重试边界

- 本开关只影响后台自动探测，不改变真实请求链路：
  - 上游失败仍按现有候选规则排除当前账户并切换后续候选；
  - `retry_next`、同账户兄弟 Key 重放、多分组后备、`ServerRetryBudget`、请求墙钟与 attempt 上限保持现状；
  - 本地 IP / transport 局部回避保持现状；
  - 请求级审计、使用记录、错误语义保持现状。
- 真实请求失败不会写账户级冷却、限流、质量隔离或二态之外的状态；后台探测关闭时，账户保持「正常」，由请求级切号承担失败隔离。
- 本开关不改变正常请求的候选排序逻辑；`latency_degraded` 仍按真实流量建立，只是没有后台恢复探针，状态按 TTL 或真实流量恢复，且不作为健康状态展示。

## 与「持续恢复探活」及「特供」的关系

- 新增「后台自动探测」为父开关；「持续恢复探活」为子开关。
- 父开关关闭时：
  - 子开关有效值强制为 `false`，前端置灰；
  - 已保存的子开关值保留，重新开启父开关后恢复原值；
  - 10 分钟有界恢复窗口也不再执行，因为不存在任何后台探测。
- 特供恢复（`expeditedRecoveryEnabled`）属于后台恢复加速：
  - 父开关关闭时自动取消并释放特供名额；重新开启父开关后不自动恢复特供，用户需按名额重新申请。

## 边界与影响审查（2026-10-30）

### 必须补进实现的状态写入路径

- `accounts/patch.go` 连接变更（凭据 / Base URL / 代理）在 chat/image 域会自动落 `pending_test` 等后台检查；手动模式必须跳过该分支，否则每次改配置都会永久待检查。
- `accounts/accountsreset/runtime_reset.go` 的「重新检查 / 异常恢复」会把 `error` 重写为 `pending_test` 并投递健康检查；手动模式必须直接 `active`，不投递。
- `accountscore/writeinput.go` 的 `AccountCreationStatusInput` 默认 `pending_test`；`oauthmgmt` 创建、`aipublic` 创建、`accountstransfer` 导入（active 会 remap 为 pending_test）都必须按手动模式改为 active/disabled，不能落 pending_test。
- `authz/instance_provision.go` 与授权实例状态写入链需要同样处理；实例跟随来源账户，不允许实例单独设手动模式。
- `m11_authorized_dispatch.go`、`m11_traffic_migration.go`、批量 / 导入 / 克隆 / 公开 API 的所有状态写入口都要统一校验，避免只改主编辑页。

### 状态归一化的字段完整性

- 归一化为 `active` 时必须同时：`schedulable=1`、清空 `cooldown_until`、`cooldown_retest_*`、相关 `last_error_*`、健康失败计数 / 计划；否则会出现「状态正常但不可调度」或残留冷却。
- 归一化为 `error` 时必须保留可读原因，并清理质量隔离 enforcement / lock 运行态；手动恢复时直接回 `active`，不再进 `pending_test`。
- 归一化必须走现有账户状态变更服务，统一 bump `config_revision`、失效运行时缓存、标脏分组统计、写审计；禁止裸 UPDATE。
- ~~需要按来源区分 `temporary_unavailable` / `rate_limited`~~（2026-10-30 复审后修订：**全部 → error**。复审取证：显式策略 / 系统额度冷却落库链 `markCooldown` 与探针冷却共用同一 `cooldown_retest_generation` fence（同写 `cooldown:` 代际），fence 非空 ≠ 探针派生，原「按来源区分」判定恒不成立且会把所有冷却归一 active 覆盖用户意图；按来源区分需新增来源标记列，改动面大于统一转异常的收益，故修订为一律 `error` 保留人工恢复）。

### 其他功能边界

- **媒体域**：audio/video 已有 `SkipsConversationHealthStateMachine`，video 的 `pending_test` 还有媒体准入 / CAS 通道；audio/video 不适用该开关（无后台探测闭环）。~~建议媒体域不展示 / 不适用该开关，或单独定义媒体域规则。~~（2026-10-30 二轮复审裁决：不适用面收窄为 audio/video；**image 域适用**——图像账户存在激活检查、冷却恢复、电路/质量预检等真实后台探测，仅豁免 active 周期巡检，后端守卫现状即按 audio/video 判定，image 正常展示开关与「手动」标签。）
- **导入未验证凭据**：现有导入刻意把 `active` 重映射为 `pending_test`，原因是凭据未在本地验证。手动模式导入默认 `active` 会绕过这道安全门；建议默认 `disabled` 或导入预览显式确认后再 active。
- **用户显式策略的恢复语义**：错误策略 / 响应拦截 / 系统额度 / 手动模型检测处罚在手动模式下产生的冷却、限流、质量隔离状态没有自动恢复，只能人工「恢复正常」或临时重新开启探测；这是既有策略语义的自然结果，本开关不修改策略行为。
- **运行态建立面**：不仅要关 circuit / key-model 恢复任务，还要确认真实流量不再建立探针派生运行态；用户显式策略产生的状态属于策略语义，不拦。
- **速度优先探针索引**：`latency_degraded` 可保留请求级状态，但不要再写 `nextProbeAt` / probe-index，否则会留下无人消费的探针任务；展示层也不能把「下次探针」当账户状态。
- **展示边界**：`availabilityPresentation`、`probePresentation`、列表可用性投影、`account_list_availability_projections` 都要读取新字段并抑制过程态；否则后端仍可能吐出「待探针 / 降级」。
- **健康监控历史**：关闭后不再有新 outcome，但旧小时条 / 可用率仍在；需决定隐藏还是标注「历史数据，关闭后无新检查」。
- **正交状态**：授权到期、授权失效、账户到期、授权额度用完、时间计划停用仍是独立展示状态，不属于本次二态健康状态；不要误删。
- **零后台请求不成立**：余额自动查询 / 刷新、xAI Grok 用量刷新、OAuth token 刷新 / keepalive 仍可能访问上游；开关只保证「后台探测」归零，不保证「所有后台请求」归零。若上游封禁一切非业务请求，还需关闭余额自动查询并接受 OAuth / 用量刷新限制。

## 风险与注意事项

- 风险 1：漏掉某个后台探针家族，导致「关闭后仍有请求」。规避：候选筛选 + 派发前统一守卫 + 逐家族 Mock 请求计数验收。
- 风险 2：把开关误加到共享执行器，连手动测试也拦截。规避：共享执行器显式区分 `background` / `manual` trigger，手动路径不检查该开关。
- 风险 3：关闭时运行态/电路未清理，账户被残留状态挡住。规避：`DisableBackgroundProbe` 统一清理 + 可重试 + 审计计数。
- 风险 4：关闭时把实际不可用的账户归一化为正常，真实请求可能先失败一次。规避：关闭确认弹窗明确提示；请求级切号/重试承接；用户可手动停用。
- 风险 5：余额刷新被误纳入。规避：本计划明确不改余额查询代码与组件，测试项单独回归。
- 风险 6：手动模式下用户策略产生的冷却/限流没有自动恢复。规避：这是既有策略语义的自然结果；关闭确认弹窗与策略页说明「手动模式需人工恢复正常」，不静默。
- 风险 7：关闭账户的 `latency_degraded` 没有后台恢复探针，可能持续到 TTL 或真实流量恢复。规避：TTL 有界；不作为健康状态展示；不影响失败切号。
- 发布异常处理：加法字段默认 `1`，回滚只需回退代码；若需紧急停用，可先将账户 `background_probe_enabled` 恢复为 `1`，恢复后台探测。
