## 需求目标

- 背景：当前账户高级设置中“客户端兼容”“上游真实能力”“模型映射”“协议转换”“响应处理”边界混杂，导致用户不清楚 Codex / GPT 模型名如何转发到 DeepSeek / GLM / 通用 OpenAI-compatible 上游，也不清楚模型映射左右两侧应该如何选择。
- 目标：重构账号高级设置、模型映射和网关候选筛选，让当前账号作为上游边界，左侧 `sourceModel` 匹配客户端传入模型，右侧 `upstreamModel` 表示当前账号真实上游模型，并显式支持 OpenAI 协议档案下 `responses -> chat_completions`。
- 交付物：设计文档、计划文档、前后端类型与校验、账号高级设置交互、网关候选筛选与协议转换、响应管线边界验证、回归测试和验证记录。

- [x] 调整 `responses -> chat_completions` bridge 触发条件：由当前账号协议档案是否支持 OpenAI 协议，以及映射目标协议族共同决定。
- [x] 明确上游返回统一响应管线：非 bridge 透传不跳过 usage、审计、错误分类、账号状态和响应语义检查。

### 本次不包含

- 不做历史字段兼容、双读双写或运行时迁移逻辑；上线时由维护者按当前 schema 同步数据。
- 不做 `chat_completions -> responses`。
- 本计划不做 OpenAI Responses 与 Anthropic Messages 互转；后续 PLAN-0058 已单独立项 OpenAI Chat / Responses 到 Anthropic Messages 的显式单向桥接，反向转换仍不做。
- 不让客户端请求策略隐式启用协议转换。
- 不把通用 OpenAI 兼容供应商做成所有厂商深度优化入口；它只作为 OpenAI-compatible 兜底入口。
- 不改变 API Key / 分组授权基本模型；模型映射只能在已授权账号池内生效。

## 方案概述

- 方案原则：当前账号就是上游边界；左侧下游模型只匹配客户端请求；右侧上游模型才参与真实上游调用、账号支持、价格、错误处理和测试。
- 数据变化：模型映射需要能表达 `sourceModel`、`sourceEndpointFamily`、`upstreamModel`、`upstreamEndpointFamily` 和启用状态；不在映射行保存 source / target 供应商字段。
- 接口变化：账号保存、导入导出和前端选项接口需要返回或校验下游全局客户端模型目录、当前账号上游模型目录、通用 OpenAI 兼容账号的 OpenAI 协议模型池。
- 前端变化：账户高级设置拆清“上游连接”“上游真实能力”“客户端请求策略”“模型映射与协议转换”“错误、响应与运维策略”；模型映射表格展示下游 / 上游协议族。
- 后端变化：账号保存和导入导出按当前规则校验；网关候选筛选在已授权账号池内匹配账号映射；`responses -> chat_completions` 只在 OpenAI 协议档案下显式映射触发。
- 响应管线：上游返回必须进入统一响应管线；透传只是不改下游可见业务内容，不代表跳过审计、usage、错误分类、账号状态和响应语义检查。
- 数据处理策略：不内置历史结构兼容；如果本地数据库字段需要调整，只更新当前 schema 和当前读写逻辑。

## 风险与注意事项

- 候选筛选不能只按客户端模型目录供应商提前锁死，否则 Codex 请求 GPT 模型名无法进入 DeepSeek / GLM 账号池。
- 通用 OpenAI 兼容账号模型池要严格限制为 OpenAI 协议模型，不能把 Anthropic / Messages 模型混入。
- 右侧 `upstreamModel` 决定成本和账号质量，必须与当前账号可用模型、价格和 usage 解析保持一致。
- 响应管线不能因为“透传”跳过审计、usage、错误分类、账号冷却和语义检查。
- 发布异常处理：如果网关候选筛选异常，应禁用或回滚本次账号映射配置，保持普通 Chat / Responses 透传路径可用；数据库结构按当前 schema 修复，不加入运行时旧结构兼容。
