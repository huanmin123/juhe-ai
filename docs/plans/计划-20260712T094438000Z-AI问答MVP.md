## 需求目标

- 为登录用户提供使用自己 API Key 的站内 AI 问答工作台，并将它作为平台内置 OpenAI Chat 客户端接入现有网关。
- 模型调用必须经过现有 `/v1/chat/completions` 或 `/v1/responses` 网关和完整调度链路。
- 服务端管理最近 7 天完整成功轮次，前端以动态虚拟列表展示富文本流式回答。
- 问答以 Markdown 文本为主，并支持本轮受限内嵌图片；不引入 Agent、MCP、Skill、附件持久化或图片生成运行时。

## 方案概述

- DB service System API 进程承载 AI 问答 HTTP / SSE 路由并维持 SQLite 单写者；主进程使用独立聊天代理池隔离长连接。
- AI 问答从网关视角属于普通客户端，loopback 只是传输实现，不产生内部特权。
- 会话保存固定 `api_key_id`，服务端读取真实 Key 调用本机 `/v1/models`，并按实际账户能力选择 `/v1/chat/completions` 或 `/v1/responses`。
- 网关继续负责额度、路由策略、分组、账户、代理、切号、计费、使用记录和审计。
- standalone 新增独立 `juhe-ai-chat.sqlite3`；performance 新增独立 `juhe_chat` schema，消息表按 UTC 日分区；上下文只读取最近 7 天完整成功轮次。
- 新增按用户、按 UTC 日增量维护的容量窗口，默认每用户最近 7 天 2 GiB；发送门禁不得扫描消息明细。
- 前端使用 `@tanstack/vue-virtual` 和安全 Markdown 渲染栈，不复制参考项目的重型 Agent 结构。
- 聊天记录保留与原始审计保全保持独立，删除聊天不级联删除审计和使用记录。
- 当前项目不做旧 schema 兼容；上线前按目标业务 schema 单独完成结构同步和数据处理。

## 风险与注意事项

- loopback 网关调用必须保留真实 API Key 鉴权，内部签名元数据不能覆盖调用身份。
- 动态虚拟列表最容易在图片 / Mermaid 异步增高和 prepend 历史时跳动，必须有浏览器级回归。
- 流式回答不能逐 token 写库，最终正文与中间 buffer 都必须有字节上限。
- AI 问答新增独立聊天 schema / SQLite 文件；上线只创建或同步聊天存储，不重建无关业务、数据集、统计、上下文数据库或 Redis 数据。
- 删除聊天不会删除原始审计；若未来改变该产品承诺，需要单独立项。
- 发布异常时先关闭 AI 问答菜单和路由入口，保持现有公开网关继续服务；回滚代码不能回滚或删除已有 API Key、使用记录和审计事实。
