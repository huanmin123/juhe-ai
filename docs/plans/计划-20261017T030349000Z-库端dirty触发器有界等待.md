# PLAN-20261017T030349000Z 库端 dirty 触发器有界等待

## 基本信息

- 来源：BUG-0313 锁护航队治理扩展，统一排期批次 1-3（2026-10-17 用户批准按推荐推进，发布除外）。
- 状态：设计定稿，实施中。

## 需求目标

库端全部账户列表可用性 dirty 触发器路径的 7001001 advisory 取锁等待从无界改为有界（2s，与 Go 侧 `advisorylock.ListDirtyLockWaitTimeout` 同口径），消除资源饱和时触发器宿主事务无界等锁的最后暴露面。

现状证据（2026-10-17 取证）：

- 汇聚点唯一：`backend-go/projects/maintenance/internal/schema/pg_schema_business_tables.go` 的 `account_list_availability_mark_dirty_accounts`（函数体内 `PERFORM pg_advisory_xact_lock(7001001)`，事务中途取锁——触发器路径物理上无法首语句取锁，BUG-0237 残留面）。
- 覆盖全部 23 个触发器：业务域 18 个（accounts/proxies/groups/tags/api_keys 等变更）+ stats 域 5 个 quota crossing 触发器（`pg_schema_stats.go`，经 `account_list_availability_mark_dirty_quota_crossing` 委托汇聚）。
- 已有界与仍无界：jobs 三处首锁点（BUG-0313）与 gateway 脏标记（2026-10-17 已纳入）各自 2s 快失败，且持锁事务经触发器再入时 advisory 事务级可重入无阻塞；仍无界等锁的是**未持锁的触发器宿主事务**——管理面写操作、maintenance seed、以及 stats 聚合对 `usage_stats_*` 的逐行写（quota 触发器 FOR EACH ROW；BUG-0327 增量改造后写频更高，每次写都要过这把锁）。

## 方案（设计定稿）

汇聚点函数体内，advisory 取锁改为「保存 → 限 2s → 取锁 → 恢复」包裹：

```sql
DECLARE
  v_prev_lock_timeout text := current_setting('lock_timeout', true);
...
-- 仅本次 advisory 等待有界；恢复后宿主事务其余锁等待行为不变（零外溢）
PERFORM set_config('lock_timeout', '2s', true);
PERFORM pg_advisory_xact_lock(7001001);
PERFORM set_config('lock_timeout', COALESCE(v_prev_lock_timeout, '0'), true);
```

设计裁决与理由：

1. **包裹式而非裸设事务级超时**：`set_config(is_local=true)` 作用于事务剩余全部锁等待，裸设会把 2s 上限外溢到宿主事务后续语句（管理面写此前无任何上限，属新增行为面）。包裹+恢复把改动收敛为「仅 advisory 这一次等待有界」，零外溢。恢复取 `current_setting` 会话生效值（含 role/db 级默认），回滚忠实。
2. **不做 EXCEPTION 捕获跳过**：55P03 必须中止宿主事务——不变式「触发变更提交 ⇔ dirty 行写入」依赖同生共死；捕获跳过等于静默漂移（吞错），禁止。超时即宿主事务整体回滚，变更与标脏一起重试，自愈语义成立。
3. **可重入路径近零成本**：已持锁事务经触发器再入时 `pg_advisory_xact_lock` 无阻塞，包裹语句为 2 条无锁额外语句，可接受；不引入「先探测已持锁」的优化（pg_locks 轮询更贵）。
4. **超时值 2s** 与 `advisorylock.ListDirtyLockWaitTimeout` 同一语义族；SQL 侧为字面量 + 注释互引（与 7001001 字面量同先例）。实现时若 Sprintf 注入单源化会破坏既有静态 SQL 断言形态，则保留字面量并以测试锚定两值一致。
5. 55P03 已是 maintenance `pg_lock_retry` 的瞬时重试类 SQLSTATE（ensure-schema DDL 先例），全库口径一致：锁等待超时=快失败+可重试。

## 范围边界（非目标）

- 不改 23 个触发器的触发时机与标脏 SQL 本体。
- 不动 `EnqueueAllForRuntimeRecovery` 恢复路径（问题-0192 已拆段，另行评估）。
- 不引入任何配置项/开关（交付即生效）。
- 不处理 BUG-0237 残留的应用侧未持锁先拿行锁路径（统一排期批次 2 单独评估）。

## 执行拆解

## 验收标准

- 汇聚函数 advisory 取锁等待有界 2s，宿主事务其余锁等待行为不变。
- `--ensure-schema` 幂等重放通过，生产更新序列不变。
- 超时路径：宿主事务 55P03 整体回滚，变更与标脏同生共死（文本断言 + 代码评审保证，不引入捕获）。

## 风险与注意事项

- 触发器宿主事务（管理面写、stats 聚合写）在饱和态新增「2s 后 55P03 回滚」失败模式：与 jobs/gateway 侧用户裁决同口径（快失败可重试优于无界排队助长护航队）；管理页操作重试即可。
- `current_setting`/`set_config` 均为 PG 专用：该 SQL 仅存在于 PG schema 预置块（`Source: account-list-projection-pg-dirty-triggers`），SQLite 路径不加载，无方言影响。
