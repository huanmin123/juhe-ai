## 需求目标

- 背景：业务库数据需要同步提交保证安全，但记录库主要承载使用记录、操作日志、审计、运行日志、统计缓存和监控历史，不应阻塞管理请求或网关主链路。
- 目标：请求链路和 DB service 不直接同步写记录库；记录库记录型写入统一投递 background worker 队列，worker 作为消费端批量或分批落库。
- 交付物：操作日志队列化、worker 运行态补充、回归脚本、长期文档同步和剩余记录库维护动作清单。

## 范围边界

### 本次包含

- [x] 将操作日志从 DB service 同步写记录库改为业务提交后投递 worker 队列。
- [x] worker 增加 `operationLogQueue` 运行态和本地 flush。
- [x] 增加操作日志队列回归，验证 server / db-service 不回退本地同步写记录库。
- [x] 更新架构、SQLite 存储说明、操作日志设计和后台任务说明。

### 本次不包含

- API Key 删除后的历史使用记录 / 统计缓存清理：当前仍是提交后维护动作，后续应迁入记录库维护队列。
- 表监控页面手动清理使用记录：当前接口返回即时删除结果，改为后台队列需要补任务状态或前端提示。
- worker 内部统计、采样、清理任务：这些已经在后台进程内执行，本计划不再给 worker 自己套第二层 IPC。

## 方案概述

- 方案原则：业务库同步提交，记录库记录型写入异步投递；记录库数据允许 best-effort，业务数据不允许因为记录库失败被回滚。
- 数据变化：不新增表；新增 worker IPC 消息类型和操作日志队列运行态。
- 接口变化：对外 API 不变。
- 后端变化：`recordOperationLog()` 改为入队；`runLoggedOperation()` 改为业务库提交成功后再投递日志。
- 数据处理策略：操作日志 createdAt 在入队时固定，避免队列延迟改变操作时间。

## 决策记录

| 日期 | 决策 | 原因 | 影响 |
| --- | --- | --- | --- |
| 2026-05-18 | 业务提交后再投递操作日志 | 异步队列不再参与业务事务，事务内投递会产生回滚后残留日志风险 | `runLoggedOperation()` 先提交业务库，再入队操作日志，再执行缓存清理等 afterCommit |
| 2026-05-18 | worker 是记录库写入消费端 | 记录库写入目标是移出请求链路，不需要 worker 自己再通过 IPC 调度自己 | worker 内统计、采样、清理保持短事务直接写记录库 |

## 风险与注意事项

- 操作日志变为 best-effort 后，worker 崩溃或队列溢出可能丢失追溯记录，但不会影响业务库安全。
- 操作日志列表可能有短暂延迟，属于记录库异步落库的预期行为。
- 后续迁移记录库维护类动作时，需要给前端提供“已提交后台任务 / 最近执行结果”的清晰反馈，不能继续假装即时删除。
