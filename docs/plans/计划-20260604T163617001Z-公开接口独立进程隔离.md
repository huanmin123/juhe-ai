## 需求目标

- 背景：当前 `/__aipublic__` 公开接口由主 Web/网关进程接入口代理到 DB service，虽然业务逻辑不在主进程内执行，但入口 socket、代理并发、请求上下文和超时处理仍与主业务共享。用户明确要求公开接口独立出去，避免影响核心网关和后台管理。
- 目标：评估把公开接口调整为独立 `public-api` 进程、独立端口、独立并发和限流预算的可行性。
- 交付物：长期设计文档和关闭记录。经评估，当前改造成本和部署复杂度偏高，暂不实施代码改造。

## 方案概述

- 方案原则：公开接口是外部集成边界，不再占用主 Web/网关进程入口资源；主业务和公开接口按进程、端口、并发和反向代理规则分离。
- 数据变化：第一阶段不强制新增表；继续读取已有来源 token 表和业务索引。后续如公开接口流量升高，再新增 worker 维护的 `public_*` 对账快照表或独立公开快照 SQLite 文件。
- 接口变化：暂不调整。公开接口继续保持当前入口和路由契约。
- 后端变化：暂不新增 `public-api.ts`，暂不从 `system-api-app.ts` 移出公开路由，暂不删除 `server.ts` 的公开接口代理挂载。
- 部署变化：暂不增加第二个常驻进程和公开端口。
- 数据处理策略：维持当前 schema 和当前运行路径。

## 风险与注意事项

- 风险 1：独立端口上线后反向代理或调用方没有切换，会导致公开接口不可用。规避方式是在部署文档中明确主端口公开路径下线，并提供公开端口健康检查。
- 风险 2：公开写接口仍会访问业务库，不能做到数据库层面零影响。规避方式是独立写并发、短超时、操作日志异步投递和必要时内网白名单。
- 风险 3：来源 token 鉴权如果每次都查业务库，被扫时仍会影响 DB service。规避方式是正缓存、坏 token 负缓存和来源限频。
- 风险 4：公开统计快照滞后时调用方可能误以为无数据。规避方式是返回 `rangeReady`、`statsLagSeconds` 或快照时间，调用方自行沿用上次快照。
- 发布异常处理：如果 public 进程异常，可以只停 public 服务或移除反向代理公开路径；主后台和网关不需要回滚。
