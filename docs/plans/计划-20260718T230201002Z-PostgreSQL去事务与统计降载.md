# PLAN-20260718T230201002Z PostgreSQL 去事务与统计降载

> **For agentic workers:** REQUIRED SUB-SKILL: Use `superpowers:subagent-driven-development` (recommended) or `superpowers:executing-plans` to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**目标：** 在不删减、关闭或弱化任何现有管理、统计、额度、审计和网关功能的前提下，消除 PostgreSQL 普通查询的隐式事务开销，将统计写入改为增量、批量、低频且可重建的后台工作，使生产管理接口不再被事务往返、统计刷新和 MVCC 写放大拖入秒级。

**架构：** 普通 PostgreSQL `query`、`one`、`execute` 直接使用连接池执行一条 SQL；只有同时维护多个数据库状态且不能拆开的真实不变量才使用最小范围事务。统计页面继续读取全部现有窗口和汇总字段，但后台只处理变化范围，使用批量 SQL 合并同类写入，派生统计允许短时滞后并可从现有使用记录离线重建。

**技术栈：** Node.js 22/24、TypeScript、`pg`、PostgreSQL、PgBouncer、现有 `DatabaseClient`、stats-worker、System API 性能脚本。

## 需求目标

### 背景

- 生产累计约 `4920` 万次 `BEGIN`、`4920` 万次 `COMMIT`，并伴随约 `4800` 万次三组 `SET LOCAL`；当前普通 PostgreSQL 查询也执行 `pool.connect -> BEGIN -> SET LOCAL -> SQL -> COMMIT -> release`。
- PgBouncer 现场平均实际 SQL 约 `4.32ms`，平均事务约 `37.51ms`，说明大量时间消耗在事务和协议往返，而不是业务 SQL 本身。
- 管理接口会组合多个 repository 查询，单个页面的数十次普通读取被放大为数十个隐式事务。
- stats-worker 持续刷新用量窗口、授权窗口、分组统计和质量统计；部分统计表存在百万级反复插入、删除、更新，造成 WAL、MVCC、autovacuum、连接池和事件循环竞争。
- 现场 `stats-worker` 事件循环延迟平均约 `1.08s`、P95 约 `2.31s`；`server` 平均约 `0.76s`、P95 约 `1.76s`。管理接口内网直连仍普遍为 `0.4s` 到 `1.5s`，说明问题不在公网或反向代理。

### 目标

- 普通 PostgreSQL 读写各自只发送一条业务 SQL，不再自动开启事务，也不再为每条 SQL 发送 `SET LOCAL`。
- 显式事务只保留在账户、授权、API Key 等真实多语句不变量，以及统计“单个小批次结果与其游标”边界；禁止用一个事务包住整轮后台任务。
- 分组统计、授权统计、额度窗口、用量范围窗口和 AI 性能汇总保留当前页面、接口、字段和业务语义。
- 统计刷新按变化范围增量处理，按 key 预聚合后批量写入；在线任务不再周期性全表删除再全量重写。
- 统计派生数据可以按当前项目的性能优先原则短时滞后；发生失败时继续保留旧快照，并可通过现有离线重建命令恢复，不返回伪造空数据。
- 生产管理读接口在后台统计同时运行时达到本计划的 P95/P99 门槛，且网关额度判断、账户调度和管理 CRUD 功能不回归。

## 方案概述

### 1. 普通 SQL 直接执行

`createPostgresDatabaseClientInternal` 的普通路径统一执行：

```ts
async query<T extends object = Record<string, unknown>>(sql: string, params: readonly unknown[] = []): Promise<T[]> {
  const bound = postgresDialect.bind(sql, params)
  const result = await queryPostgres(client, bound.sql, bound.params)
  return normalizePostgresRows(result.rows) as T[]
}

async execute(sql: string, params: readonly unknown[] = []): Promise<ExecuteResult> {
  const bound = postgresDialect.bind(sql, params)
  const result = await queryPostgres(client, bound.sql, bound.params)
  return { changes: Number(result.rowCount ?? result.rows.length ?? 0) }
}
```

- 删除 `queryPostgresWithLocalTimeout`。
- 普通查询不调用 `pool.connect()`，由 `pool.query()` 自行借用并归还连接。
- `transaction()` 仍负责 `connect -> BEGIN -> SET LOCAL -> operation -> COMMIT/ROLLBACK -> release`，但调用方必须满足“两个以上数据库状态必须一起成功或一起失败”的真实不变量。
- `SET LOCAL` 只在显式事务开头执行一次，不允许为事务内每条 SQL 重复执行。
- 普通查询 timeout 不通过临时事务实现；生产使用 PostgreSQL role/database 的 `statement_timeout`、`lock_timeout` 和 PgBouncer `query_timeout`。应用保留的 timeout 配置只控制显式事务。

### 2. 统计写入先合并、后批量

- 同一批使用记录先在 Node 内按目标表唯一键合并计数、token、成本、延迟和时间字段。
- `authorization_team_usage_summary_daily`、`authorization_user_usage_summary_daily` 每张表每批最多执行若干条多行 `INSERT ... ON CONFLICT DO UPDATE`，不再为一条记录展开数十条顺序 SQL。
- `group_account_stats_dirty` 使用多行 upsert；dirty 确认删除通过 `(group_id, updated_at)` 批量条件删除，保证刷新过程中再次变脏的组不会被误确认。
- `group_account_stats` 使用批量 upsert；只删除已不存在的目标分组，不对仍存在的分组执行“先删后插”。
- 一个统计聚合小批次可以保留最小事务，以维持该批次派生结果与 cursor 一起推进；批次内不执行外部 I/O，不包含下一批、不包含窗口刷新。

分组统计目标 SQL 形态：

```sql
INSERT INTO juhe_stats.group_account_stats (
  system_account_id, group_id, total, available, active, disabled, error,
  rate_limited, current_concurrency, concurrency_limit, updated_at
)
VALUES (...), (...)
ON CONFLICT (group_id) DO UPDATE SET
  system_account_id = EXCLUDED.system_account_id,
  total = EXCLUDED.total,
  available = EXCLUDED.available,
  active = EXCLUDED.active,
  disabled = EXCLUDED.disabled,
  error = EXCLUDED.error,
  rate_limited = EXCLUDED.rate_limited,
  concurrency_limit = EXCLUDED.concurrency_limit,
  updated_at = EXCLUDED.updated_at;
```

### 3. 在线窗口只刷新变化范围

- `usage_overview_windows`：继续使用 source watermark，按最早变化日期缩小范围。
- `usage_scope_range_windows`：从 `usage_stats_daily.updated_at > previousWatermark` 得到变化的 `(system_account_id, scope_type, scope_id)`；每批只重算这些 scope 在受影响日期范围内的窗口。
- `usage_quota_hourly_windows`：按变化 scope 和已配置 `window_hours` 增量 upsert；未变化 scope 不重写。额度入口仍读取同一张表、使用同一配置和同一拒绝语义。
- `ai_performance_summary_windows`：按变化 `system_account_id` 删除并重建对应账号和全局汇总，不再每轮删除整表。
- 授权范围窗口：按变化 owner/team/user/resource key 分批刷新；未变化授权不参与本轮 SQL。
- full rebuild 不进入 `background-jobs.ts` 周期调度，只由 `maintenance:rebuild-usage-stats -- --confirm-offline` 执行。

### 4. 调度降载但功能不断

- 在线用量增量聚合继续按最多 `60s` 新鲜度运行，保证额度与今日统计持续推进。
- 热窗口触发合并：聚合期间只记录一个 pending 标记，当前刷新完成后最多补跑一轮，不按累计触发次数追跑。
- 重排行、范围和 AI 性能窗口按当前 10 到 30 分钟新鲜度目标运行；无水位变化直接跳过。
- 每个 stage 有独立运行预算；超出预算时保留旧快照和水位，下一轮从未完成边界继续，不清空页面数据。
- 各 stage 之间 `setImmediate` 让出事件循环，且同一时刻只允许一个重窗口 stage 执行。
- 调整频率只改变数据新鲜度上限，不移除任务、不减少字段、不取消页面能力。

## 性能验收阈值

### HTTP 与事件循环

- 在与生产接近的 PostgreSQL + PgBouncer + Redis 测试环境，持续 `10` 分钟管理读混合负载，并同时运行 stats-worker：
  - `GET /system-api/my-accounts`：P95 `<= 300ms`，P99 `<= 800ms`。
  - `GET /system-api/providers/models/options`：P95 `<= 250ms`，P99 `<= 600ms`。
  - `GET /system-api/my-account-status-snapshot`：P95 `<= 300ms`，P99 `<= 800ms`。
  - 其他本计划覆盖的管理读接口：P95 `<= 300ms`，P99 `<= 800ms`。
  - HTTP 错误率 `0%`；不允许以空列表、缺字段或零值响应计为成功。
- `server` 事件循环延迟 P95 `<= 250ms`，`stats-worker` P95 `<= 500ms`，且无连续三次超过 `1000ms`。

### PostgreSQL 与 PgBouncer

- 普通 management-read 请求产生的 `BEGIN/COMMIT` 数量相对发布前同流量降低 `>= 90%`。
- 代码和 SQL 采样中，普通 `SELECT/INSERT/UPDATE/DELETE` 前后不存在自动 `BEGIN + SET LOCAL + COMMIT`。
- 压测期间 `pg_stat_activity` 的 `idle in transaction` 峰值为 `0`，deadlock 增量为 `0`。
- PgBouncer `cl_waiting` 不持续大于 `0`；连接等待尖峰在一个采样周期内恢复。
- `group_account_stats`、`usage_quota_hourly_windows`、`usage_scope_range_windows` 的 statement 次数与变化 key/chunk 数相关，不再与目标表总行数或每条源记录展开数量线性增长。

### 统计功能与新鲜度

- 今日用量、额度窗口和账户/分组页面用量新鲜度：正常负载下 `<= 120s`。
- 统计首页热窗口：正常负载下 `<= 10min`。
- TopN、AI 性能、授权范围和较长范围窗口：正常负载下 `<= 30min`。
- 未变化水位的 stage 执行时间 `<= 200ms`，且不写目标窗口表。
- 统计刷新失败后上一份真实快照仍可读；恢复后无需修改页面或接口即可继续更新。
- 离线重建后，固定 fixture 的统计值与重建前基准完全一致；生产数据只要求功能恢复和新数据继续累计，不承诺已被保留策略删除的历史记录可恢复。

- 阶段 1 异常：停止发布中的当前服务，恢复上一份已验证构建并重启；本阶段无 schema 变化，不需要数据回滚。
- 阶段 2、3 异常：恢复上一构建；批量 upsert 使用原唯一键和原字段，不改变接口契约。若派生统计出现异常，先保留现场样本，再在停服/离线条件下运行重建脚本。

## 风险与注意事项

- 去掉普通隐式事务后，普通 SQL 不再获得应用侧 `SET LOCAL`；必须先验证生产 PostgreSQL role/database 和 PgBouncer timeout，避免慢查询失去上限。
- 不能机械删除所有 `transaction()`；账户创建与凭据保存、授权绑定、API Key 状态和统计小批次 cursor 等真实不变量仍需最小事务。
- 批量 SQL 受 PostgreSQL 参数数量和报文大小限制，chunk 大小必须由回归锁定，并在真实环境观察 statement duration。
- 增量窗口依赖水位和目标表唯一键；首次运行、源表截断或水位倒退必须明确记录并要求离线重建，不能在线扫完整历史。
- 统计短时滞后是允许的性能取舍，但页面功能、字段和筛选维度必须完整；额度窗口新鲜度必须满足 `120s` 门槛。
- 生产发布前后应保存 `pg_stat_statements` 和 PgBouncer 快照，不能仅凭浏览器主观感受判断成功。
