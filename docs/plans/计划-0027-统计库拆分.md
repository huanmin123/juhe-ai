## 需求目标

- 背景：当前记录库同时承载高频事实数据和统计结果。使用记录、审计、日志和采样持续写入时，可能影响统计结果查询、额度判断和统计页面响应。
- 目标：将当前记录库继续拆为统计数据集库和统计结果库，让高频写入与稳定查询隔离。
- 交付物：方案设计、方案复查评审、三库配置和 schema 拆分、repository 迁移、worker 改造、迁移 / 重建脚本、表监控适配、文档和验证记录。

## 方案概述

- 方案原则：业务库不变，记录库拆为统计数据集库和统计结果库；请求路径不跨库 join，不临时聚合明细。
- 数据变化：新增两个 SQLite 路径配置；新增 `dataset-schema.ts` 和 `stats-schema.ts`；统计结果库保存 `stats_job_state`。
- 接口变化：对外 HTTP 接口不改路径和响应结构；内部 repository 按库边界拆分。
- 前端变化：统计页面、使用记录页、日志页和表监控页面交互不变；表监控需要展示三类库。
- 后端变化：DB service 和 worker 打开三类数据库；统计 worker 跨库读写但不使用跨库事务。
- 数据处理策略：历史旧记录库停机备份后拆分；统计结果优先从数据集库重建，无法重建的历史区间明确放弃。

## 风险与注意事项

- 风险 1：跨库拆分后容易误用旧 `getRecordDatabase()`。规避方式是先迁移数据库入口，再逐个 repository 分类，最后删除或限制旧入口。
- 风险 2：统计结果写入成功但游标未推进会导致重复累加。规避方式是统计结果写入和 `stats_job_state` 推进必须在统计结果库同一事务内完成。
- 风险 3：数据集库清理早于统计处理会导致无法重建。规避方式是清理任务读取统计结果库安全水位，并保留至少最近 1 天保护窗口。
- 风险 4：表监控和部署文档仍按两库描述会误导运维。规避方式是实现完成后同步运行、部署、测试和表监控文档。
- 回滚建议：上线前保留旧记录库备份；如果三库启动或统计聚合异常，停服务后恢复旧版本代码和旧 `JUHE_AI_RECORD_DATABASE_PATH` 配置。
