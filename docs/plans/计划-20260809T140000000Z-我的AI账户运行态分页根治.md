# 我的 AI 账户运行态分页根治

## 背景与结论

2026-08-09 生产现场的 `/__aisys__/api/my-accounts` 在问题窗口约 215 次请求中，平均约 `748ms`、P95 约 `1.97s`、最大约 `3.82s`。请求耗时与本机 control upstream 基本相等，不是 Edge、TLS、PostgreSQL 锁等待、PgBouncer 等待或 Redis Stream 积压。自然请求既出现 `account-status-filter` 主导的长尾，也出现基础 `account-list` 主导的默认页；因此要同时治理基础分页和动态状态筛选，不能把问题归咎为单一 Redis 或机器负载。

当前实现为了保持状态实时性，会按排序前缀反复读取候选账户，再逐批水合 PostgreSQL 授权/额度、Redis 运行态、熔断摘要和 API Key 状态；稀疏筛选会扩展到最多 10,000 条候选。账户动态数据不能简单改为“列表只从 Redis 取”：Redis 的短暂探针状态会过期、读取失败也必须可见，且授权、来源账户、额度、过期和权限仍以 PostgreSQL 为事实来源。

根治目标是让状态/可调度筛选直接按一个可重放、可对账的 PostgreSQL 读模型索引分页；基础列表同时维持索引化的绑定读取。Redis 只保留网关热状态。读模型未知、积压或过期时必须显式不可用，不能悄悄回退到昂贵的候选扫描，也不能把未知当作可用。

## 非目标

- 不把完整账户响应、凭据或权限判断复制到 Redis。
- 不修改 `/my-accounts` 的 JSON 契约、排序、分页、权限边界或 SQLite 路径。
- 不在 API 请求链路重算全量账户，也不以 TTL 页面缓存掩盖慢查询。
- 不在本计划阶段直接发布、执行生产 DDL、重启服务或切换流量。

## 已完成：观测与隔离基础

- `GET /my-accounts` 的成功响应追加以下 `Server-Timing`：
  - `account-list-hydrate`
  - `account-status-candidate-list`
  - `account-status-candidate-hydrate`
  - `account-status-candidate-predicate`
  - `account-status-final-hydrate`
  - `account-status-final-tags`
- 这些指标只存在响应头，不写入业务数据，不改变响应 JSON。
- PostgreSQL 基础列表改为按账户利用现有索引选择最新启用分组绑定，避免先对全部绑定做窗口排序。生产只读对账 `1,376` 行无差异；同一账户域的核心查询执行样本从约 `145ms` 降至约 `61ms`。该优化不改变状态、授权或 Redis 语义。
- PostgreSQL 状态投影代码已改为按当前账户选择最新启用分组绑定，避免动态状态候选批次重复对全部绑定做窗口排序；SQLite 保留原窗口查询路径。绑定的排序、缺失绑定和授权实例语义不变，PostgreSQL 行为仍需隔离库对账。
- 分组与授权摘要的 Redis shared-cache lookup 代码已改为每批最多 `100` 个 ID 并发读取，消除页内逐项等待；Redis 读取或写入失败仍然直接失败，不回退本地缓存或旧数据，并已有行为级批量边界回归。
- 已确认不能新增第二套 Node DDL / migration 账本；读模型 schema 必须通过现有 Goose 维护入口落地。当前 checkout 缺少可验证的 Go migration catalog，因此没有创建或执行任何生产 DDL。

## 目标架构

```text
账户 / 授权 / API Key / 控制面状态写入
              │ 同事务脏标记 + generation
              ▼
PostgreSQL 投影队列 ──▶ ops-worker（租约、围栏、可重放）
              │                         │
              │                         ▼
              └──────────────▶ 账户列表可用性读模型
                                           │
GET /my-accounts ─────────────────────────┘ 一条 PostgreSQL SQL
                                           │
                  索引分页 + 当前页并发/用量/余额 overlay

Redis：只保存网关短暂探针和热状态；持久控制面写成功后才发布热状态。
```

请求 SQL 的职责严格分层：先只在 `account_list_availability_projections`、tag/search 索引上完成可见性、动态状态、筛选、排序和分页；随后只对已选中的 `pageSize + 1` 行 LEFT JOIN PostgreSQL 内的并发 overlay、当天用量、授权总用量和余额快照，并在数据库内合成 JSON。授权账户的公开 `lastUsedAt` 由授权总用量实时补齐，但分页排序继续使用旧接口的账户行排序键。它仍是一条 SQL、一次连接往返，不会对 20,000 条候选重新水合，也不会在请求链路访问 Redis、DB-service 或业务事实表。

## 开发实现与验证（未部署）

- PostgreSQL 模式已实现 durable dirty/generation/lease/fence 投影、viewer health、运行态依赖 health、runtime recovery、自然过期/时间计划/额度重置到期重投影，以及 Redis 并发到 PostgreSQL overlay 的后台同步。运行态依赖除了状态外还有默认 `15s` 的健康心跳：worker 每次成功完成真实 runtime probe 与 overlay reconcile 后才刷新；心跳过期、dirty、缺行、依赖不可用或正在重建时均返回明确 `503`，绝不回退旧的候选扫描。
- 账户、授权来源、团队额度、分组、标签、API Key 运行态、熔断、代理和搜索索引写入均会写入投影 dirty；`last_used_at` 采用原地 patch，避免高频遥测把整个 viewer 置为不可用。Redis 中已经被硬删除账户遗留的并发 dirty 事件会被安全确认并 ack；仍存在账户的 Redis 缺失或读取失败仍 fail-closed。
- 当前页的 `currentConcurrency`、`todayUsage`、授权 `lastUsedAt`、余额快照由同一条 PostgreSQL 语句在页已选中后有界 JOIN 注入。真实 PostgreSQL 影子回归覆盖自有账户和授权实例两种用量 scope，先物化、后单独写 daily/total usage、余额，验证无需重建且逐字段与旧链路相等；还覆盖运行态心跳过期 `503` 后由 maintenance 恢复。
- 在隔离开发库 `juhe_ai_sub2api_dev_account_list_projection_20260810` 完成 fresh schema、影子、HTTP `200 -> 503 -> 200`、Redis runtime recovery、授权来源时间计划、团队额度跨阈值、排序、深页、并发 overlay 与删除恢复回归。`20,000` 条首次回填在默认 `batchSize=100`、4 个 PostgreSQL worker 下单 pass 完成，最新实测 `50.9s`，无 stale claim 或 release。
- 搜索词表原有 PostgreSQL 专用索引名超过 63 字符，被名称截断后与通用索引冲突，导致 `keyword=...` 排序查询退化为 20,000 行顺序扫描和排序。改为唯一短索引名后，`EXPLAIN ANALYZE` 的默认/关键词 SQL 分别为 `2.15ms/2.89ms`；同一条 SQL 仍保留 `COLLATE "C"` 排序语义。
- `20,000` 行、`80` 并发、`30s` 的真实 PostgreSQL 压测覆盖管理列表与 options 的默认、status 稀疏/普通、schedulable、provider、group、tag、keyword、深页等 20 种筛选。零错误，端到端 P95 `160-224ms`、P99 `208-294ms`、最大 `432ms`；连接池峰值 50 条连接、waiting 79，但查询后 Node 映射 P95 仅 `0.06-0.09ms`。这是隔离开发环境的容量证据，不替代生产等价拓扑的连续验收。
- 分组列表不适合照搬账户投影：保留动态 `currentConcurrency`/`todayUsage` 语义，只把 500 个分组成员的 Redis shared-cache 从串行改为每批 100 并发。真实 scratch PG/Redis 集成压测验证 500 组冷缓存回源 `242ms`、热缓存 `60ms`，成员映射完整，测试 namespace 已 `SCAN + UNLINK` 清理。

## 后续实施门禁

1. 先恢复/定位连续的 Goose migration catalog，并以 `juhe-ai-maintenance schema-up` 作为唯一 DDL 入口；禁止新增 Node DDL、临时 SQL 或第二套 ledger。
2. 以正式 migration 重放现有读模型 schema、触发器、索引与回填；先 shadow 对账，再启用 maintenance，最后才可打开 read flag。任何时点 read flag 都不能早于完整回填和依赖 health 初始化。
3. 发布前在与生产等价的 PostgreSQL/PgBouncer 拓扑做连续压力测试。开发 `DB_POOL_MAX=50` 下的 80 并发已通过，但仍观测到 waiting 峰值 79；需要连续多轮确定受控 pool、PgBouncer transaction pooling、管理读并发上限和运行态 worker 的连接预算，不能以单次通过为由盲目扩大连接池。
4. 异常、dirty、投影缺行、运行态依赖不可用或重放未完成时返回明确 unavailable，不回退旧扫描；生产自然流量还需复核 P95/P99、503 比例、dirty age、claim lease、runtime recovery 和投影延迟。

## 当前限制

当前 checkout 仍没有可核验、连续的 Goose migration catalog，因此这些 PostgreSQL schema/trigger 代码只能作为隔离开发验证，不能安全推到生产。生产 read/maintenance flag 均保持关闭，未执行生产 DDL、回填、重启或切流。当前线上仍走既有扫描链路；开发结论不能替代生产自然流量验收。
