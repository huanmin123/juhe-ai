## 需求目标

- 背景：高性能模式可能多 Web 节点并发处理请求。上游桶避让、IP 级账号回避、IP 错误熔断和 Codex turn retry 这类短 TTL 调度状态如果在请求路径使用 Redis 分布式锁，会放大延迟，并可能因锁等待、锁残留或跨节点排队影响整体吞吐。
- 目标：请求路径短 TTL 调度状态去掉 Redis 分布式锁，接受短暂不一致，通过 TTL、时间窗口、成功信号和后台探针收敛。
- 交付物：代码调整、回归断言、长期文档和验证记录。

## 方案概述

- 方案原则：请求路径优先吞吐和可恢复性；短 TTL 调度状态允许秒级短暂不一致，不用分布式锁追求单个样本的强一致。
- 数据变化：不新增数据库字段；Redis key 仍保持短 TTL。
- 接口变化：无外部接口变化。
- 后端变化：四类网关短 TTL 状态从 `lock -> get -> mutate -> set -> release` 调整为直接 `get -> mutate -> set`；硬并发槽、限流等不可超卖状态仍使用原子操作。
- 数据处理策略：运行态可以被覆盖或丢失少量样本；状态恢复依赖 TTL、成功清理、后台探针和 generation 收敛，不把 Redis 运行态作为持久事实。

## 风险与注意事项

- 短 TTL 状态无锁后可能丢失少量并发样本；状态升级不能只按单次请求计数，必须继续依赖时间窗口、最小观察期、探针结果和成功信号。
- Redis 不可用时高性能模式不能把跨节点事实静默退回进程内 memory。
- OAuth 刷新锁仍存在，不能误认为全项目没有任何 Redis 锁调用；它不属于本次调度运行态去锁范围。
