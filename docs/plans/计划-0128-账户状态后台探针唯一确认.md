# 计划-0128 账户状态后台探针唯一确认

> 后续决策：本计划中“一次后台失败仍可调度”和“全部易失状态失败开放”已被 `PLAN-0130` 取代。最新语义是：普通用户请求仍不能改变账户级状态；但首次有效独立后台探针已确认失败后，`precheck_pending` 必须软阻断普通调度，全池软阻断时转受控半开和有界等待。

## 基本信息

- 状态：本地验证完成，等待生产发布
- 创建时间：2026-07-17
- 需求来源：生产 `huanmin` 账户池被同一来源异常请求整体隔离
- 影响范围：网关运行态、后台恢复探针、账户健康检查、账户列表状态快照、前端刷新

## 生产证据

- 同一 API Key 和来源 IP 在约两分钟内使五个实际可用账户进入 Redis `recovery_wait`，最终返回“所有上游账户正在临时隔离”。
- 多个后台恢复探针已经取得 HTTP 200 完整成功，但 `complete_success` 被错误转为异常，状态每 10 秒续期且 `attemptCount` 不推进。
- 精确清理五个 recovery state 后，相关账户立即产生连续真实成功请求，证明数据库账户并未失效。

## 不变量

1. 普通业务请求事实不能被系统自动解释为账户级状态变更；未命中用户显式策略时，业务失败只允许当前请求换号、按 API Key / IP / 会话局部回避，以及投递后台核实信号。账户所有者主动配置的账户错误策略和响应拦截策略属于明确管理意图，命中后允许按配置直接执行账户状态或运行态动作。
2. `recovery_wait` 只是内部后台任务，不是账户运行态；未执行后台探针前不得改变列表状态、全局调度资格或 Redis 状态提示。
3. 后台标准探针只按可验证事实判断，不维护状态码、错误码或错误文本白名单：完整成功、到达上游但未成功、未形成有效上游尝试。
4. 未形成有效上游尝试属于未知结论，必须丢弃判断并释放当前观察，不能累计失败、续期或标记恢复成功。
5. 普通请求失败与内部 `recovery_wait` 仍不影响调度；首次有效独立后台探针失败后，`precheck_pending` 按 `PLAN-0130` 从普通候选中软阻断。最终写入 `temporary_unavailable` 仍至少需要 5 分钟观察和 3 个独立后台轮次，确认轮次至少间隔 2 分钟。
6. 全部候选只剩 `precheck_pending` 软阻断时不再失败开放；按 `PLAN-0130` 先尝试后备分组，再使用受控半开与有界等待。
7. 只有后台恢复探针或主动健康检查的完整成功，才允许用 driver-aware 清理 memory / Redis 未完成判断；普通用户请求成功同样只记业务事实，不能直接改变账户级状态。
8. 账户列表刷新保留上一份已确认运行态，列表基础数据和新状态快照原子衔接，不能短暂显示虚假的“可调度”。
