## 需求目标

- 背景：当前大多数上游模型不原生支持 OpenAI Responses，只有 GPT / OpenAI 原生或少数 OpenAI-compatible 上游能承接 Responses。模型映射如果允许把非原生上游协议选成 `responses`，会让 UI 和运行时把不具备 Responses 能力的模型伪装成可用。用户要求先用 mockai 覆盖各种协议和能力形态，避免直接消耗真实账户排低级错误。
- 目标：建立长期协议互转矩阵，收紧模型映射右侧协议选择和保存校验；右侧 `responses` 只允许当前账号真实接口能力包含 Responses 的原生上游，其中 `responses -> responses` 是直连，`chat_completions -> responses` 是本地桥接后还原 Chat 响应形态，`messages -> responses` 禁止。后续协议转换测试必须先走 mockai，再做真实账户探针。
- 交付物：协议矩阵文档、前端 UI 限制、前后端保存校验、mockai 回归、真实账户探针计划和验证记录。

### 本次不包含

- 不把 `chat_completions -> responses` 放开给 Chat-only、Messages 或未知兼容上游；该方向只服务真实支持 Responses 的 OpenAI/GPT 原生上游，用于 Chat 客户端访问 Responses-only 模型，并必须由本地桥接把 Chat 响应形态还原。

- 不把非 Responses 上游伪装成原生 Responses。

## 方案概述

- 方案原则：区分“原生上游协议”和“网关桥接协议”。`responses` 只能在上游真实支持时作为右侧协议；其他转换目标只能落到 `chat_completions` 或 `messages`。
- 能力缺口处理：供应商 / 模型不支持的 hosted/native 能力默认返回通用 agent guidance，不作为网关 500，不伪造成功，不请求不支持的上游；客户端 agent 后续自行决定是否配置本地 MCP / 工具执行器、切换模型或移除工具。
- 数据变化：不新增 schema；收紧现有 `modelMappings` 校验。
- 接口变化：后端账户创建、编辑、导入预览、草稿测试都必须复用同一协议矩阵校验。
- 前端变化：模型映射行的左侧协议允许 `chat_completions`、`responses`、`messages`；左侧模型池按协议族切换，Chat / Responses 使用 OpenAI 协议模型池，Messages 使用 Anthropic 协议模型池；右侧协议选项根据左侧协议和账号 `supportedEndpointModes` 动态禁用；保存时给中文错误。
- 后端变化：normalize / repository 层禁止无真实 Responses 能力的 `upstreamEndpointFamily=responses`。
- 数据处理策略：不做旧映射兼容迁移；当前 schema 下发现非法映射应由用户离线清理，不在运行路径双读兜底。

## 协议互转矩阵

| 下游请求 | 上游协议 | 状态 | 说明 |
| --- | --- | --- | --- |
| Chat Completions | Chat Completions | 支持 | OpenAI-compatible 原生 Chat 或同协议模型映射 |
| Responses | Responses | 支持，但仅原生 | 只有账号真实接口能力包含 Responses 时允许；适用于 GPT / OpenAI 原生或明确支持 Responses 的 OpenAI-compatible 上游 |
| Responses | Chat Completions | 支持 | 当前 `responses -> chat_completions` bridge，面向 DeepSeek / GLM 等 Chat-only 上游 |
| Chat Completions | Responses | 支持范围内 | 仅允许账号真实接口能力包含 Responses 的 OpenAI/GPT 原生上游；本地桥接负责把 Chat 请求转为 Responses，并把 Responses 输出还原为 Chat Completion；Chat-only、Messages 或未知兼容上游仍禁止 |
| Chat Completions | Anthropic Messages | 支持 | `chat_completions -> messages` bridge |
| Responses | Anthropic Messages | 支持 | `responses -> messages` bridge |
| Anthropic Messages | Chat Completions | 支持范围内 | `messages -> chat_completions` bridge，只通过显式账号模型映射进入；不伪造 server tool / MCP / thinking 等能力 |
| Anthropic Messages | Responses | 禁止 | Anthropic 不原生支持 OpenAI Responses，当前不做反向 Responses 合成 |

## 决策记录

| 日期 | 决策 | 原因 | 影响 |
| --- | --- | --- | --- |
| 2026-06-24 | 右侧 `responses` 只允许原生 Responses 上游 | 大多数非 GPT 上游不支持 Responses；允许选择会造成运行时伪成功或低质量转换；Chat 客户端访问 Responses-only GPT 模型需要单独桥接 | UI、前端保存、后端导入和 API 保存都必须禁止非原生 Responses 上游映射；原生 `chat_completions -> responses` 必须由本地桥接还原 Chat 响应形态 |
| 2026-06-24 | mockai 先于真实账户 | 真实账户消耗额度且错误噪声大；协议字段、SSE 事件和工具格式可由 mockai 先覆盖 | 每个新增协议转换能力先补 mock，再做真实抽样 |
| 2026-06-24 | 上游能力缺口走通用 agent guidance | 上游供应商 / 模型不支持的能力不是网关服务端异常；强制兼容会导致伪成功、500 或会话中断 | 协议转换层必须返回可被任意客户端 agent 消费的 guidance，不写死客户端名称；请求非法、权限越界、状态链损坏、schema 校验或安全策略命中仍返回本地协议错误 |

## 风险与注意事项

- 如果历史数据库已有非法 `upstreamEndpointFamily=responses` 映射，本计划不在运行时代码迁移；由用户按当前 schema 离线清理。
- “Chat -> Responses” 与 “Responses -> Chat” 方向不可混淆；前者只允许真实 Responses 上游并需要本地还原 Chat 响应，后者用于 Chat-only 上游承接 Responses 客户端。
- 发布异常处理：如协议矩阵限制误伤原生 GPT Responses 账号，先检查账号 `supported_endpoint_modes` 是否包含 `responses_json` / `responses_sse`，不要放宽到所有供应商。
