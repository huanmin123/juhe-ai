## 执行规则

1. 每个批次单独建立设计与回归，不能共享一个宽 `Summary` 作为过渡终态。
2. 列表、编辑、options、secret、runtime 和 mutation result 分别定义字段白名单，并用 SQL 捕获证明没有先宽查后裁剪。
3. 写入必须有 baseline、revision / CAS、同值 no-op、动态 `SET`、关系表写入预算和按字段分类的缓存 / worker 副作用。
4. 远程搜索必须有 debounce、取消或代次 fencing；管理 target owner 必须进入缓存键和 SQL owner 条件。
5. 每批至少通过 Node/Vue typecheck、定向 HTTP/repository/竞态回归、生产构建、`git diff --check` 和隔离 Browser Network 验证。

## 非目标

- 不把所有详情请求删除；用户明确点击后、列表确实缺少数据的专用详情是正确边界。
- 不把动态默认资源 ID 写成跨用户编译期常量。
- 不在没有 revision 与关系表回归时顺手改写其他资源。
- 不包含 Go 对齐、生产部署或生产数据迁移。

## 完成标准

每一行审计项只有在“响应字段、实际 SQL、写入列、并发冲突、缓存副作用、前端 Network”六类证据同时闭合后才能从待排期改为完成。前置计划的账户列表 / 单账户编辑 / API Key 结果不能代替本计划其他资源的完成证明。
