## 需求目标

- 背景：当前后台任务如果只在 Node 主进程里用 `setInterval` 或 cron 注册，任务回调仍会占用 Web/API 进程事件循环。即使引入定时器框架，如果实际任务函数仍由主进程调用，也不能解决 Node 单线程下 Web 请求被后台批处理拖慢的问题。
- 目标：后台定时任务必须在独立 Node 进程内调度和执行，主 Web 进程只负责 HTTP/API/网关请求和必要的轻量捕获，不承担统计聚合、系统采样、OAuth 快照刷新、日志索引批量写入、审计批量落库等定时任务执行。
- 交付物：后台任务隔离架构文档、阶段计划同步、运行部署说明、后续实现与验证记录。

## 范围边界

### 本次包含

- [x] 明确主 Web 进程不得导入并执行后台任务实现，只能启动或看护后台 worker 进程。
- [x] 明确调度框架只能在后台 worker 进程内注册和触发任务，不能通过 IPC 让主进程代执行任务。
- [x] 明确请求链路产生的数据可以通过有界 IPC 或等价轻量通道交给 worker，但批量落库和聚合执行权归 worker。
- [x] 同步后端架构、核心功能、SQLite 策略、第一阶段计划、开发运行和部署文档。
- [x] 实现独立后台 worker 入口、主进程 supervisor 和进程退出清理。

- [ ] 补充类型检查、构建、运行态和性能验证记录。

### 本次不包含

- 不引入 Redis、Kafka、BullMQ、Agenda 等外部队列或分布式任务系统：第一阶段仍保持轻量本地部署。
- 不把后台任务拆成多实例分布式调度：多实例部署后再评估共享锁、任务归属和幂等边界。
- 不要求所有请求路径写库都迁移到 worker：登录会话、管理面 CRUD、网关必须立即返回所需的事务仍属于 Web 进程职责；本计划只约束后台定时、批处理和队列 flush。
- 不在本轮文档优先阶段完成代码改造：实现另按本计划执行。

## 方案概述

- 方案原则：进程隔离优先于调度语法。定时器框架只能解决注册、不可重入和调度表达，不能替代进程边界。
- 后端变化：新增独立后台 worker 入口；`server.ts` 或进程管理器只负责启动 / 看护 worker，不导入任务实现并直接执行。
- 调度变化：后台任务调度框架运行在 worker 进程内；任务函数只被 worker 入口导入，禁止主 Web 进程直接调用。
- 数据变化：第一阶段不新增外部队列表；请求链路产生的审计、使用记录和运行日志索引数据如需异步批量写入，应通过有界 IPC 或等价轻量通道进入 worker 队列。
- 部署变化：开发和生产都必须确认主 Web 进程与后台 worker 进程同时存活；常驻运行配置不能只守护 `server.js`。
- 故障策略：worker 崩溃不应带崩 Web 进程；主进程或进程管理器应记录错误并按退避重启 worker。worker 不可用时，非关键审计 / 日志索引可按队列策略丢弃，关键使用记录需按后续实现明确降级边界。

## 验收标准

- [ ] 主 Web 进程启动后不直接注册后台定时任务，不导入后台任务实现模块。
- [ ] 后台任务调度框架和任务执行函数只在独立 background worker 进程内运行。
- [ ] 统计聚合、系统采样、授权到期扫描、OAuth 快照刷新、冷却账号复测、运行日志维护和审计清理等任务均不占用 Web 进程事件循环。
- [ ] worker 崩溃不会导致 Web 进程退出；Web 进程或进程管理器能记录并重启 worker。
- [ ] 请求链路产生的审计、运行日志索引和使用记录批量 flush 不通过主进程定时器执行。
- [ ] 文档、运行说明、部署说明和验证记录同步完成。

## 风险与注意事项

- IPC 队列风险：如果主进程向 worker 发送审计或日志索引数据的通道阻塞，必须有上限和丢弃策略，不能反向阻塞请求。
- SQLite 写并发风险：主进程和 worker 进程会各自持有 SQLite 连接，必须依赖 WAL、短事务和批量写入控制锁等待。
- 任务重复风险：开发热重载、PM2 cluster 或多实例部署可能启动多个 worker；第一阶段默认单实例，后续多实例需补共享锁或显式任务归属。
- 部署风险：如果生产只守护 Web 进程而没有守护 worker，统计、OAuth 快照、清理和后台索引都会停滞。
