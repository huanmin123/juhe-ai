## 基本信息

- 状态：验证与复查中
- 创建时间：2026-07-26
- 范围：仅当前 Node 后端；不修改 Go 实现
- 前置审计：`PLAN-20260726T062111512Z`
- 目标：统一修复周期任务固定碰撞、无界单轮工作量、跨任务并发、跨部署重复执行、超时不生效和运行态不真实问题

## 实施边界

- 保持 AI 账户健康检查 `1 小时 + 账户稳定小范围错峰`，AI 健康监控继续复用探测结果，不新增账户请求。
- 模型质量定时检查保持用户配置周期，统一治理只处理 scanner、claim、并发、超时、补偿和运行态，不暗加用户不可见周期。
- 高频观测和控制任务使用稳定相位，不使用每轮随机漂移。
- 事件驱动 usage / audit / operation 等微批链路不增加人为延迟。
- PostgreSQL / Redis 验证只使用隔离命名空间、临时 schema / 数据库或独立 key prefix，不清理或覆盖远端现有业务数据。
- 审计期间已有其他并行改动的文件必须以增量补丁合并，不 reset、restore 或覆盖。

## 设计决策

1. `WorkerScheduler` 增加 `fixedRate / fixedDelay`、稳定相位、真实 timeout / abort、`coalesceOne`、失败退避、资源 lane 和完整 next-run 状态。
2. 进程内资源 lane 负责限制重统计、存储维护和外部诊断的跨 Job 并发；数据库租约负责多部署正确性，二者不能互相替代。
3. PostgreSQL 单 owner 周期任务使用短事务 `pg_try_advisory_xact_lock` 保护 TTL lease claim，并用 fencing token 防止旧 owner 晚到覆盖；不跨任务持有 session advisory lock。对象队列继续使用短事务 `FOR UPDATE SKIP LOCKED` claim。
4. SQLite 不模拟分布式租约，继续依赖单 writer / 单 replica；任务仍须保持幂等和有界执行。
5. 统计窗口、表监控、预热、代理刷新等随数据量增长的任务必须采用 cursor、时间预算、增量范围或 pair budget，错峰只作为辅助。
6. 所有锁等待和长 SQL 必须有任务级 deadline；PostgreSQL 在事务内使用 `SET LOCAL statement_timeout / lock_timeout`，不能仅依赖 `Promise.race`。

## 验收标准

- 虚拟时间两小时内，同一资源 lane 的重任务没有并发重叠，固定碰撞回归可重复。
- 相同 seed 的稳定相位可复现，不同稳定实例 ID 能分散且不超过新鲜度窗口。
- timeout 会触发 abort；长任务最多产生一次合并补跑，不形成无限 backlog。
- 两个 Node 实例竞争同一 PostgreSQL lease 时只有一个执行；未获得 lease 明确记录为 skipped。
- PostgreSQL 授权用量窗口能周期刷新，SQLite 原有范围窗口不回归。
- 系统趋势正常小时不再全删重建全部历史窗口。
- quota、overview、AI 性能摘要在线路径不得无条件全表 `DELETE`；每轮领取 scope 和窗口行数有硬上限，dirty 未清空时继续消费。
- 256 shard 表监控不执行精确 `COUNT(*)`，SQL / shard-table pair 数受配置预算约束。
- 10,000 账户预热单轮工作量和耗时受预算约束，失败账户不阻断游标推进。
- AI 健康监控不增加账户请求；模型质量用户周期和手工执行语义不变化。
- 远端验证不留下凭据、业务数据污染或未清理的隔离 key / schema。

## 回退预案

- scheduler 新能力按任务显式配置，保留旧默认语义；出现回归可逐任务撤销新选项。
- 相位、资源 lane 和租约分开提交验证，问题可按层回退。
- 增量窗口上线前保留人工全量重建入口，先做新旧结果对比。
- 远端验证使用唯一测试前缀和测试 schema；删除前先核对精确目标，只清理本轮创建对象。
- 所有生产代码修改前后保留针对性回归，不依赖远端环境作为唯一证据。
