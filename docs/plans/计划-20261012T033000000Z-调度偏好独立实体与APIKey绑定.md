## 需求目标

### 已核实的现状

- 调度偏好实际保存在 `route_strategies.config_json.normalRoutingConfig`，其模式字段是 `schedulingPreference`，取值为 `cost_first` / `speed_first`。`normal`、`weighted`、`failover`、`round_robin`、`merge` 五种策略模式均可携带它。
- `groups.scheduling_policy_json` 和授权分组的 `schedulingPolicy` 是另一套分组内调度配置；不能把它们当作本计划迁移的来源。路由模式、分组绑定、优先级和权重继续归策略路由维护。
- API Key 与策略路由按 `system_account_id` 隔离；API Key PATCH 使用 `expectedRevision`。默认 API Key 已有限制更换路由策略的规则，不能笼统写成“与路由绑定同级，所以都可随时修改”。
- 速度运行态目前含 owner、route、group、account 维度；新实体不能只替换配置 SQL 而遗漏慢样本、恢复探针和运行态查询。
- AI 问答的 `purpose=chat` 专用 Key 只承载鉴权、额度和计费，会话唯一绑定 AI 账户，不使用普通 API Key 的路由调度。

代码证据：`backend-go/projects/gateway/internal/routestrategies/config.go`、`internal/gatewayruntimecache/{sqlruntime.go,types.go}`、`internal/gatewaypreauth/preflighthelpers.go`、`internal/apikeys/{routes.go,store.go,patch.go}`、`cmd/juhe-ai-gateway/chain_dispatch.go`。这些路径均以 `backend-go/projects/gateway/` 为基准。当前功能事实以关联权威文档为准；计划不把拟议行为写成已上线事实。

### 用户目标

- 新增独立菜单“调度偏好”，提供列表和新增；系统内置一个“对话·成本优先”，不可修改、不可删除。
- 当前仅对话域提供成本优先 / 速度优先；视频、音频、图像域显式“无调度偏好”。
- 普通 API Key 同时绑定路由策略和调度偏好，两者为并列配置。路由仍按 `API Key -> 路由策略 -> 分组 -> AI 账户` 选择，偏好只影响既定路由池中的对话调度。
- 最终从策略路由移除调度偏好配置。P1 / P2 是实施分期，不新增功能开关。

### 非目标

- 不设计媒体域新调度形态，不改变现有调度算法、熔断、计费、用量和模型目录语义。
- 不迁移分组 `schedulingPolicy`，不重构策略拓扑字段。
- 不改变 AI 问答的会话账户覆盖；不因本计划给 `purpose=chat` Key 新增调度作用。

### D1 独立实体、归属与内置默认

- 新表 `scheduling_preferences`：`id`、`name`、`chat_mode`、`chat_speed_first_config_json`、`built_in`（0/1）、`enabled`（0/1）、`owner_system_account_id`、`created_at`、`updated_at`。
- 保留“系统内置一条默认”的目标，建议采用全局只读内置行：固定 ID，`built_in=1`、`owner_system_account_id=NULL`、`chat_mode=cost_first`、`enabled=1`。它作为明确例外供所有 owner 读取和绑定；其他行必须 `built_in=0` 且 owner 非空。不得把内置行挂在某个真实用户名下，再用“同 scope”过滤掉其他用户。（v2 修订：内置行名「默认调度偏好」、四域占位展示、enabled 退役——见 v2 用户裁决修订节；本条 `enabled=1` 随 v2 第 4 条作废。）
- 用户偏好名称在 owner 内唯一，采用现有资源名称归一化 / 比较规则；内置 ID 和内置身份有唯一约束。自定义行不可伪造 `built_in`、修改 owner 或覆盖固定 ID。
- 管理侧按角色和可选 owner 范围读取；用户侧只能看到自身行及全局内置行。管理员创建自定义行须明确目标 owner；绑定按 API Key 的实际 owner 校验。被授权账户 / 分组不构成跨 owner 共享偏好的许可。
- 两种存储都校验主键、owner / built-in / enabled 约束和索引。`api_keys.scheduling_preference_id` 建引用索引与外键；跨 owner 绑定由事务内校验，不能只依赖单列外键。
- 内置行由 maintenance 的 schema / seed 初始化链幂等建立；gateway / jobs 不在热路径补种。内置行缺失或结构错误是初始化失败，启动检查应报错，不能临时造一个默认对象掩盖问题。

### D2 配置形状与完整字段

`chat_mode=cost_first` 时 `chat_speed_first_config_json=NULL`；`speed_first` 保存以下对象。运行时合成为现有 `NormalRoutingConfig`，其中再加入 `schedulingPreference=chat_mode`：

```json
{
  "firstByteDeadlineMs": 30000,
  "speedFirstConfig": {
    "slowTriggerCount": 3,
    "slowWindowSeconds": 120,
    "recoverySuccessCount": 3,
    "probeIntervalSeconds": 30,
    "degradedTtlSeconds": 300,
    "maxFirstByteRetriesPerRequest": 2,
    "totalTimeDeadlineSeconds": 120,
    "compactionTotalTimeDeadlineSeconds": 300
  }
}
```

| 字段 | 默认 | 合法整数范围 |
| --- | --- | --- |
| `firstByteDeadlineMs` | 30000 | 10000..60000 毫秒 |
| `speedFirstConfig.slowTriggerCount` | 3 | 2..10 |
| `speedFirstConfig.slowWindowSeconds` | 120 | 60..600 秒 |
| `speedFirstConfig.recoverySuccessCount` | 3 | 3..10 |
| `speedFirstConfig.probeIntervalSeconds` | 30 | 10..300 秒 |
| `speedFirstConfig.degradedTtlSeconds` | 300 | 60..3600 秒 |
| `speedFirstConfig.maxFirstByteRetriesPerRequest` | 2 | 1..3 |
| `speedFirstConfig.totalTimeDeadlineSeconds` | 120 | 60..270 秒 |
| `speedFirstConfig.compactionTotalTimeDeadlineSeconds` | 300 | 300..900 秒 |

复用 / 抽取当前 Go 配置规范化能力，避免新实体另写一套默认值。缺省沿用既有默认；显式非法值、损坏 JSON 和结构错误保留校验错误，不静默降级。迁移只在规范化后比较字段与有效运行参数，不比较 JSON 键顺序或原始字节。“逐字迁移”改为“规范化参数和可观察行为等价”。旧 `speedFirstConfig.firstByteThresholdMs` 的读取别名按现行规则处理，新实体只保存 `firstByteDeadlineMs`；双字段同时出现仍拒绝。

媒体域不存占位列。是否消费偏好沿用现有请求 lane / 可重放性门控；不能仅凭账户 `capability_domain=chat` 放行图像工具或其他副作用请求。压缩请求首字豁免与总时间维度继续按既有规则执行。

### D3 API Key 绑定、清空与生命周期

新增 `api_keys.scheduling_preference_id TEXT NULL`。P1 历史 `NULL` 表示仍沿用旧策略配置；为避免与“显式清空回默认”冲突，建议新写入将默认选择持久化为内置 ID：

| 写入场景 | `schedulingPreferenceId` | 存储结果 |
| --- | --- | --- |
| 创建普通 Key | 缺失或 `null` | 固定内置 ID |
| PATCH 普通 Key | 缺失 | 保持原值，包括历史 NULL |
| PATCH 普通 Key | `null` | 固定内置 ID，即用户显式回默认 |
| 创建 / PATCH 普通 Key | 非空 ID | 同 owner 的启用偏好，或固定全局内置行 |

非法类型、空字符串、跨 owner、不存在或停用的目标拒绝写入（v2 第 4 条后「停用」分支消失，仅剩非法类型/空串/跨 owner/不存在）。偏好变更使用现有 `expectedRevision` 和事务语义；同值不更新 revision、不失效。默认普通 API Key 的路由不可换规则保留；偏好是否允许修改须独立写明，建议允许，不能由“同级”推导现有保护已取消。

`purpose=chat` Key 的列保持 NULL，EnsureChatAPIKey 不建立偏好绑定；写入口提交非空偏好 ID 拒绝，运行时不消费本配置。只改字段描述不足以保证该边界，必须覆盖内部会话路径和普通 HTTP 请求对照测试。

内置行任何业务写入口都拒绝修改 / 删除。自定义行建议允许编辑、停用、启用和删除，但新增以下引用纪律（v2 修订：停用态废除、删除改自动解绑回默认——见 v2 用户裁决修订节第 4/5 条，以下「停用」「409」条款随之作废）：

- 删除仍被 Key 引用的偏好返回 `409`，由用户先调整绑定；数据库采用 `RESTRICT`，不能静默清空引用。
- 停用被引用行是明确的行为变更：绑定保留，暂用内置成本优先；界面提交前展示受影响 Key 数和回落结果。重新启用后绑定重新生效。
- 偏好修改影响所有绑定 Key，列表 / 详情提供绑定数量；写操作记录 owner、变更字段和影响范围。
- 新偏好实体的悬空、跨 owner、损坏配置不属于正常停用：保留数据错误并中止相关请求，不回落默认掩盖问题。P1 历史 NULL 的旧策略配置仍完整保留原读取与错误语义，差异在迁移预检处理。初稿的“任何 Key 永远有效”承诺删除。

### D4 分阶段读取和失效协议

| 阶段 / 状态 | 配置来源 |
| --- | --- |
| P1，普通 Key 的历史 NULL | 完整沿用当前策略 `normalRoutingConfig` 的读取、clone、preflight 和缺省行为，不更换为新实体默认 |
| P1，有合法启用绑定 | 独立偏好合成的完整配置 |
| P1，合法绑定已停用 | 内置默认；列表保留停用绑定并显示有效来源（**v2 第 4 条作废此态**：停用废除后不存在该分支） |
| P1，显式选择系统默认 | 内置 ID 对应成本优先；不再继承旧策略 |
| P1，显式绑定的新实体引用 / 配置损坏；或 P2 配置损坏 | 显式错误，不默默改用策略或成本优先；P1 历史 NULL 的旧配置不适用此行，完整沿用原读取与错误语义 |
| P2，迁移完成 | 只读新实体；普通 Key 的 NULL 为未迁移错误，不能恢复旧源 |
| `purpose=chat`、媒体或不适用请求 | 保持现有覆盖 / lane 行为，不应用新偏好 |

偏好加载使用可区分“无绑定”和“引用错误”的读取方式（如 LEFT JOIN）；不能用 active 偏好 INNER JOIN 把整个 Key 当作不存在。有效配置进入现有 runtime 缓存，并同步 clone / sanitize、内存与 Redis 序列化、缓存版本及所有 preflight / dispatch 消费点；请求内固定同一配置快照。

API Key 绑定变化须覆盖 validation / lookup / runtime 失效，额度未变则不新增 quota 失效。偏好内容或状态变化须让所有受影响 Key 重新加载，优先用现有全局 runtime 代际和跨实例 topic，避免逐 Key N+1。必须核对 topic reason 的实际订阅条件，不能仅调用一个名为 `InvalidateGatewayRuntime` 的方法就判定生效。数据库提交后失效失败的 HTTP、操作日志和恢复行为沿用现有明确契约；不得声称回滚已经提交的数据库写入。

### D5 速度运行态隔离与可观测性

这部分是初稿遗漏的必要改造，不属于只换 SQL 来源。建议：

- P1 历史 NULL 保留原来的 `owner + route + group + accountRuntimeKey` 命名空间与状态，确保既有 Key 不因换键失去慢样本 / 降级状态。
- 新绑定的速度偏好使用 `owner + route + preferenceId + configFingerprint + group + accountRuntimeKey` 命名空间；fingerprint 只含规范化调度字段，改名不清空速度状态。
- 同路由不同偏好 / 参数不共享速度样本和恢复计数；相同路由与相同偏好配置的多个 Key 可以继续共享。成本优先不消费速度降级；一般账户健康、熔断、计费和全局并发状态不迁移到偏好维度。
- 慢样本、降级 TTL、真实恢复、后台恢复探针、body admission / 切换预留相关 scope、运行态查询必须使用同一有效身份；配置变更后旧身份不再用于新请求，迟到探针不能更新新身份。
- P1 策略 `speed-first-runtime` 只解释历史回落 scope，不把新偏好状态混成策略状态。新绑定的运行态详情按偏好 + 路由上下文查询，并保留 owner 权限、批量预算和 `runtimeAvailable=false` 语义；具体 DTO / endpoint 在开工设计门落定。
- P2 旧 scope 转新 scope 的处理必须先裁决：推荐验证等值后以 fencing 转移仍有效状态，无法可靠转移则明确短期重新采样的行为变化，不能宣称完全零变化。本项为 P2 开工门槛。

### D7 分期与迁移

P1 不回填历史 Key，只建立 schema、内置种子、新接口和读取链。P1 阶段尚未完成“策略路由只负责路由”的最终目标，不能以实体 / 菜单可用宣称整体交付。

P2 建议独立窗口执行 maintenance 一次性迁移：

1. 只读预检报告：owner / 策略 / Key 数、五种模式的有效参数、已显式绑定、历史 NULL、chat Key、坏配置和冲突。坏数据阻断对应迁移，不自动成本化。
2. 备份并冻结受影响的 Key、策略和偏好写入；确认备份可恢复后执行。线上 / 真实库执行须另获授权。
3. 按 owner 从有效策略配置生成等值偏好，成本优先绑定内置 ID；速度优先偏好建立稳定迁移映射，规范化配置 / 来源版本纳入幂等与冲突检查。
4. 仅更新 `scheduling_preference_id IS NULL` 的普通 Key；所有 P1 显式绑定（含显式内置 ID）和 `purpose=chat` 一律保留。无 Key 的策略、停用 Key / 策略也纳入清单，避免之后启用丢失配置。
5. 事务提交、重跑、部分失败恢复、计数后检和完成记录必须可验证；完成前保留 P1 读取链，完成记录不得在仍有未迁移普通 Key 时写入。P2 进程启动只读核对完成记录 / 引用完整性，未满足则失败。
6. 按 D5 处理速度运行态，再删除策略编辑器调度区块（含四域 tab 中该区块）、列表调度摘要、写接口旧参数及旧读取源；策略 `config_json` 中其他合法数据不可整列误删。
7. 回滚必须能恢复 P1 的 schema / 绑定与旧配置快照及对应二进制；P2 后产生的新绑定与新 Key 须纳入回滚预检，不能只恢复旧备份便声称无数据损失。

SQLite / PostgreSQL 都需 fresh schema + 存量加列 / 新表 + 索引 / 约束形状校验。维护入口沿用 `--ensure-schema` / `--seed`，迁移命令名及其预检、执行、后检模式在 P2 设计门定案。禁止把昂贵 Ensure、全表回填或自动迁移放到 gateway / jobs 热路径；启动守卫与 SQLite 既有 bootstrap 边界按 Go 三项目基线核对。

能力域计划的四域 tab 在 P1 保留，只作为旧策略配置入口；新绑定不读取该入口。P2 移除相关呈现时同步能力域计划的交叉引用，不能把分组和策略拓扑一同移走。
