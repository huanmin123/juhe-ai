## 验收标准

- 后台连续第 3 次临时失败时清空金额并显示“查询失败”；确定性不支持时显示“已暂停”且停止余额后台轮询；人工刷新失败不覆盖已保存金额。
- 自动刷新只处理启用、到期、当前可用的物理单 Key API Key 账户。
- 功能关闭、OAuth、多 Key 池和授权实例不展示、不查询。
- 多 Key 账户创建和编辑必须成功；如果余额查询原来开启或请求仍携带开启状态，保存结果自动收敛为关闭，不能返回余额能力错误。
- 单 Key转多 Key时清空余额调度时间并隐藏、删除旧快照；多 Key转单 Key后保持关闭，用户显式重新开启后才恢复查询。
- 五类适配器只消费明确查询接口响应，不使用兼容特征或本地数据推算余额。
- 手动刷新使用无边框 `ReloadOutlined` 图标，最长等待 15 秒且不重复并发查询。
- 新增/编辑页使用当前表单配置进行无持久化测试；列表刷新图标只同步更新当前账户单元格，不刷新整表。
- 新账户创建不等待余额探测；首次激活命中后自动开启，未命中或配置版本变化保持关闭。
- 上线后对全部系统账户执行一次游标扫描，账户配置代理时所有探测和刷新均走该代理。
- 查询结果不影响账户状态、网关调度、健康检查和本地用量统计；只更新余额快照和余额自身刷新时间。
- 列表读取无 N+1，后台单轮查询有固定上限和稳定排序。

## 2026-07-12 超时调整设计

- 现状：单账户内置适配器共同使用 8 秒总 deadline；NewAPI 可能连续请求两个接口，代理或上游响应偏慢时容易在形成有效余额前耗尽预算。
- 方案：把共享总 deadline 固定调整为 15 秒。所有候选适配器继续消费同一截止时间，不能按适配器分别获得 15 秒。
- 保持不变：后台单轮最多 100 个账户、并发 4、同账户租约 30 秒、响应体上限 256 KiB、禁止重定向、严格 JSON 解析和账户代理规则。
- 不新增系统设置或账户字段，避免为单一安全边界增加配置负担；后续只有生产证据表明 15 秒仍不足时再重新评估。
- 回归要求：静态断言总 deadline 为 15 秒；验证优先适配、回退适配和超时错误仍共享同一预算；执行余额专项回归、后端类型检查和构建。

## 2026-07-12 连续失败与人工刷新隔离设计

- 后台周期刷新把网络异常、超时、HTTP `408/429/5xx` 归为临时错误，连续第 1、2 次保留上次成功结果或显示“待重试”，第 3 次才写入真正失败；失败计数封顶为 3，任意成功清零。
- `401/403`、缺少 Base URL/API Key、自定义配置缺失或跨 Origin 等确定性错误不进行无意义重试；该旧设计由下方“能力暂停与 NewAPI 语义修正”章节替换为暂停余额后台调度。
- 连续失败元数据写入现有 `relay_balance.snapshot_json`，不新增数据库列，不触发非业务数据库重建。
- 列表人工刷新是一次即时操作：成功才持久化并更新单元格；失败只返回顶部消息，不写失败快照、不累计后台失败次数、不推进自动刷新时间。弹窗草稿测试继续保持完全无持久化。
- 前端已有成功金额在后台第 1、2 次临时失败时继续展示，并通过 tooltip 标记暂时失败次数；从未成功的账户显示“待重试（1/3 或 2/3）”。

## 2026-07-12 能力暂停与 NewAPI 语义修正

- NewAPI 的 `unlimited_quota=true` 只表示令牌本身不限额，不是用户账户余额无限；该适配器返回 `unsupported` 并继续尝试其余内置规则。
- 用户开关只表达用户意愿，后台不能自动改成关闭。全部适配器确定不支持、`401/403` 或本地配置确定错误时，把 `balance_query_next_refresh_at` 置空并保存 `unsupported` 暂停快照；`balance_query_enabled` 保持开启。
- 暂停账户不进入周期候选查询，资源占用归零。用户保存 Base URL、API Key、代理或余额配置后重新到期；列表人工刷新成功也恢复用户配置周期，失败只即时提示并保持暂停。
- 临时错误不暂停：每次失败都按账户 `intervalMinutes` 等待下一轮；第三次开始显示“查询失败”，后续计数封顶为 3 并继续周期查询，成功后清零失败序列。

## 2026-07-12 临时失败重试周期修正

- 生产发现账户停留在“待重试（2/3）”后长时间没有可见后续；只读核实 worker 正常，实际是第二次失败被固定延后 30 分钟，第三次及以后延后 60 分钟。
- 余额刷新周期是用户明确配置，临时失败只应跳过本轮并等待下一次正常查询，不应由隐藏退避覆盖为另一套周期。
- 修正后第 1、2、3 次及后续临时失败都使用账户 `intervalMinutes`；连续三次失败阈值、成功清零、人工刷新隔离和确定性暂停保持不变。
- 关联问题：`BUG-0069`。
- 上线后重新检测当前由 NewAPI `unlimited_quota=true` 形成的旧“无限”快照：其他适配器命中则保存真实结果，否则进入暂停。
- 编辑弹窗删除独立的测试查询行，把按钮放入刷新周期表单项右侧；标题帮助提示继续说明测试不保存，窄屏空间不足时按钮在同一表单项内换行右对齐。

## 2026-07-13 多 Key 优先与余额自动关闭设计

### 问题定义

- 当前余额查询首期明确只支持单 Key，但账户编辑表单在 Key 数量变为多个时只隐藏余额配置区，没有保证已保存的 `balance_query_enabled=true` 一起关闭。
- 完整编辑会在前端提示“上游余额查询仅支持单 API Key 账户”；基础编辑或直接 API 会在后端用旧余额开启状态校验最终多 Key 凭据，同样拒绝保存。
- 余额查询是辅助查询能力，多 Key 是账户凭据轮换业务能力。附属能力不能让核心账户创建、编辑和网关轮换失效。

### 决策

- 最终有效 Key 数量大于 1 时，账户保存必须成功，并自动把余额查询收敛为关闭。
- 前端负责明确提示和提交关闭状态；后端按最终合并凭据再次归一化，是所有入口的唯一事实来源。
- 自动关闭同时清空 `balance_query_next_refresh_at`。`balance_query_config_json` 保留，方便恢复单 Key 后重新开启；`relay_balance` 快照由统计写入链路幂等删除。
- 多 Key 减少为单 Key 后仍保持关闭，不能自动恢复查询。用户必须显式开启，避免历史快照或旧配置自动作用于新的凭据集合。
- 查询期间切换为多 Key 时，现有配置版本和条件写保护必须使旧查询结果失效，不能恢复快照、调度时间或余额开关。
- 不实现逐 Key 查询、余额求和、共享钱包识别或代表 Key 查询。

### 前端交互

- 单 Key 时继续展示余额查询配置。
- 最终有效 Key 数量大于 1 时，在 API Key 配置区域展示中文说明：“多 Key 账户不支持余额查询，保存后将自动关闭余额查询。”
- 不弹阻断式确认框，不要求用户先手动关闭，不再返回“仅支持单 API Key”的表单错误。
- 保存成功提示可以补充“已因多 Key 自动关闭余额查询”，但账户保存成功仍是主结果。

### 后端与存储

- 先合并并归一化最终凭据，再判断有效 Key 数量；不能使用请求里未合并的局部 credentials，也不能只依赖 `api_keys` 原始数组。
- 多 Key 时忽略请求中的余额开启意愿，把最终业务写入固定为 `balance_query_enabled=false`、`balance_query_next_refresh_at=NULL`，并保留现有余额配置 JSON。
- 业务账户状态和调度停止在同一次业务库写入中完成。统计快照删除允许通过现有 stats-writer 异步幂等执行，不引入跨库事务；列表按关闭状态立即隐藏旧快照。
- 创建、完整编辑、基础编辑、管理端、自有账户接口和直接 API 必须复用同一纯规则，避免分支行为不一致。
