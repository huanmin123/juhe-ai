# 计划-20260916T182403345Z-全链路真实AI业务场景验收

> 状态：实施中（2026-09-16 启动）。目标：上线前最低验收标准——前端管理流程 + 真实 AI 账户 + mock 故障注入 + 真实客户端，把"路由 → 分组 → 账户 → 网关链 → 用量/审计"完整串起来。

## 1. 验收目标与范围

**目标**：证明以下链路在真实组件组合下符合预期功能效果，未达标不上线。

1. **业务场景串流程**：管理面（前端 API 契约）完成 API Key → 路由策略 → 分组 → AI 账户 全套配置，真实客户端经 `/v1` 打通，管理面（usage-records / audit-logs / 账户快照）能完整归因验证。
2. **真实 AI 全链路**：真实生产账户（20 个，多 provider）真实出网调用；mock AI 注入故障，与真号混搭验证切号。
3. **机制全覆盖**：5 种路由模式、切号语义（同账户重试/跨账户切换/耗尽 503/流式已提交不拼接）、账户状态机（rate_limited 冷却、error_disabled、恢复）、普通/高并发分组、多 Key 池隔离、协议转换边界。

**非目标**：页面交互 UI 测试（维持既有约定）；压测/性能验收（另有专项）；生产写操作（生产侧全程只读）。

## 2. 环境与数据源（已取证）

| 项 | 事实 |
| --- | --- |
| 隔离实例 | acceptance harness 模式：真实 `juhe-ai-gateway` 二进制 + SQLite 六库临时目录；需要私网上游时 `JUHE_AI_ALLOW_PRIVATE_UPSTREAM_BASE_URLS=true` |
| 生产账户 | `juhe_ai_prod.juhe_business.accounts`；候选 20 个（gpt5/openai4/anthropic4/glm3/deepseek2/xai2，全 api_key 型，id 清单见测试文件内）；只读会话 `default_transaction_read_only=on` |
| 凭据解密 | `credentials_encrypted` 为 `v1:{iv}:{tag}:{ct}` AES-256-GCM（key=sha256(JUHE_AI_SECRET)）；生产 secret 经授权 kubeconfig 读 `juhe-ai-runtime` Secret，仅运行时进进程 env（`JUHE_AI_E2E_PROD_SECRET`），不落盘不入日志；导入走本地管理面 API 由本地 secret 重新加密 |
| mock AI | `backend-go/shared/platform/mockupstream`（OpenAI chat/responses，16 场景）+ 测试内侧车 middleware 做服务端场景控制；Anthropic `/v1/messages` mock 测试内补齐 |
| 真实客户端 | codex-cli 0.152.0（`CODEX_HOME` 隔离 + `exec -o`，Responses）、claude 2.1.220（`--settings` + `ANTHROPIC_BASE_URL/AUTH_TOKEN`，Messages）、opencode 1.18.5（项目级配置，chat_completions）、gemini 0.5.0（env 注入，低置信可选） |
| 成本纪律 | 真号调用 max_tokens ≤ 64、短 prompt；大批量/故障循环一律走 mock |

## 3. 测试矩阵（验收门）

### S 冒烟链（真号直通）
| # | 场景 | 断言 |
| --- | --- | --- |
| S1 | chat_completions → gpt/openai/glm/deepseek/xai 真号（流式+非流式） | 200 + 非空回复；usage-records 归因正确；`/v1/models` 含账户模型 |
| S2 | /v1/messages → anthropic 真号 | 200 + 文本；usage 归因 |
| S3 | /v1/responses → gpt 真号（codex 客户端） | codex `exec -o` 输出非空；usage `trafficSource=gateway` |
| S4 | gemini 真号（可选，低置信） | 失败则标注降级原因，不阻塞验收 |

### R 路由模式（mock 账户确定性 + 真号确认）
| # | 模式 | 场景与断言 |
| --- | --- | --- |
| R1 | normal | 2 组各 1 mock-ok 账户，固定优先序：连续请求恒命中第一组 |
| R2 | failover | 主组 mock 全 500 → 备组真号接管 200；主组恢复后流量回主组 |
| R3 | round_robin | 3 组 mock-ok，连续 6 请求轮转序列精确匹配 |
| R4 | weighted 2:1 | 12 请求按 2:1 比例分布（±1 容差） |
| R5 | normal+speed_first | mock 慢首字超 firstByteDeadlineMs → 切下一候选；审计出现首字切换事件且账户状态中性 |
| R6 | hybrid_smart | 评分超时走 fallback 档；完整链路视评分模型可用性，允许标注降级 |

### F 切号与状态
| # | 场景 | 断言 |
| --- | --- | --- |
| F1 | 同账户瞬态重试 | mock 500 一次后 ok：同账户重试成功，审计 `same_account_retry_dispatch`，无切号 |
| F2 | 跨账户切换 | 账户 A 恒 500 → B 接管；usage 两行归因（A 失败/B 成功）；A 保持 active（opaque 错误不写状态） |
| F3 | 系统额度规则 | mock 429 + insufficient quota 文本 → 账户 `rate_limited` + `cooldown_until`；冷却过期恢复 |
| F4 | 显式错误策略 | 账户 error_handling_rules 命中 → `error_disabled`；PATCH 恢复 active |
| F5 | 流式已提交断流 | mock mid_stream_close → 客户端断流，无第二账户内容拼接 |
| F6 | 多 Key 池 | 账户 2 把 key（mock 首 key 401/次 key ok）→ 同账户服务成功 |
| F7 | 候选耗尽 | 组内全 500 → 客户端 503 统一消息；各账户状态不变 |

### G 分组
| # | 场景 | 断言 |
| --- | --- | --- |
| G1 | 高并发分组排队 | 账户 concurrency_limit=1 + mock 持流，5 并发 → 全部最终成功且出现排队审计（非 503） |
| G2 | 普通组并发满 | 切组内下一账户 |
| G3 | 组内 tier 序 | superPriority 恒先；fallbackEnabled 仅在非 fallback 耗尽后派发 |

### C 真实客户端全链路
