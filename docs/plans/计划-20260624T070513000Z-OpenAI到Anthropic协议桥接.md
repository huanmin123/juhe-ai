## 需求目标

- 背景：混合智能路由或普通模型映射可能把 Codex / OpenAI-compatible 下游请求路由到 Anthropic Messages 账号。现有系统只做了 `responses -> chat_completions`，无法解决 OpenAI Chat / Responses 与 Anthropic Messages 的协议不兼容问题。
- 目标：建立长期可维护的 OpenAI Chat / Responses 到 Anthropic Messages 桥接能力，覆盖 Chat JSON、Chat SSE、Responses JSON、Responses SSE 四类入口，并接入模型映射、混合路由、usage、审计和错误处理。
- 交付物：长期设计文档、计划记录、后端桥接实现、路由与响应协议接入、mock 回归、真实账户联调记录和最终验证结果。

## 方案概述

- 方案原则：四类下游 OpenAI 形态都可以桥接到 Anthropic Messages，但只承诺明确映射的协议子集；不可映射字段受控拒绝，不静默吞掉。
- 数据变化：优先复用现有账号模型映射结构，允许 `sourceEndpointFamily = chat_completions|responses` 映射到 `upstreamEndpointFamily = messages`；如现有枚举缺失 `messages` 目标，需要按当前 schema 直接扩展。
- 接口变化：账号保存、导入导出、前端模型映射和后端校验需要允许 Anthropic v1 档案作为 OpenAI 下游桥接目标，但仍禁止 OpenAI `responses -> chat_completions` 配在 Anthropic 档案上。
- 后端变化：新增共享桥接层，接入 Anthropic provider driver、候选账号能力筛选、上游请求构造、响应协议选择、usage 解析和本地错误渲染。
- 混合路由变化：目标模型可以指向 Anthropic Messages 模型；候选分组判断从“原生承接当前请求协议”调整为“原生承接或显式桥接承接”。
- 数据处理策略：不做历史兼容分支；上线时按当前 schema 同步模型映射枚举和相关配置。

## 风险与注意事项

- OpenAI Responses 是 typed event 模型，不能用 Chat SSE handler 代替；Responses SSE 必须维护 output item 生命周期。
- Anthropic Messages 与 OpenAI Structured Outputs 不完全等价；不能把 best-effort JSON 输出包装成严格 schema 成功。
- 桥接会影响返回侧协议判断；如果仍按账号 `protocolCode=anthropic` 选择 response protocol，OpenAI 下游会收到错误格式。
- 真实上游平台可能存在模型不可用、限流、余额、SSE 不完整或第三方兼容差异；这些只能作为真实联调事实进入诊断，不能写死到桥接层。
- 发布异常处理：如果桥接路径异常，先通过关闭相关模型映射或混合目标模型规避；Anthropic native 和 OpenAI 原生 / Chat bridge 路径应保持可用。
