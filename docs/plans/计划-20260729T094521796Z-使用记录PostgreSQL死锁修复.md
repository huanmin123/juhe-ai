## 方案概述

- 现状是同一事务先插入 `juhe_usage.usage_records`，获取唯一索引相关锁后，再按批输入的 Map 迭代顺序更新 `juhe_business.accounts`。并行 worker 的输入顺序和重复投递不固定，导致同类事务获得 accounts 与 usage 唯一索引锁的顺序不同。
- 修复先在事务外汇总 `last_used_at` 与健康成功副作用。事务开始即对这两个集合的并集执行 `SELECT id ... ORDER BY id FOR NO KEY UPDATE`，然后插入 usage、再执行既有条件更新。
- 锁查询以数据库 `ORDER BY id` 为事实顺序；不存在或已删除的账户不锁定，且与既有条件更新一致。事务任一步失败仍整笔回滚，消息继续保持 pending，由现有消费者重试。

## 风险与注意事项

- 相同账户的并行 usage 批会在事务开头短暂等待，这是为消除死锁所需的可控串行化；只锁有副作用的账户，避免扩大范围。
- 账户更新的其他路径仍可能与 usage 写入竞争。该修复统一 usage 事务自身的顺序，发布后仍需观察新的死锁图是否指向其他事务链。
- 当前工作区存在大量无关变更；本计划只触及 usage repository、专项回归和关联文档，不回退或整理其他差异。
- 发布失败时回退同一 schema 下的上一已验证 release；不清理队列、Redis pending 或历史使用记录。
