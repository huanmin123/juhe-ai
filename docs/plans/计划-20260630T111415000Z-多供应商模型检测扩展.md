## 需求目标

- 背景：实施前模型检测只支持 GPT / OpenAI-compatible Responses 下的 `gpt-5.5` 和 `gpt-5.4`。用户要求新增 Anthropic、GLM 以及其他已接入供应商的模型检测，每个供应商先给 2 个最常用或当前主力模型，并参考 GPT 现有强诊断设计继续完善。
- 核心目标：把模型检测从 GPT-only 常量扩展为按供应商协议 profile 驱动的多供应商模型可信度诊断能力。
- 模型 ID 规则：所有页面、接口、历史、报告、终端日志和证据摘要都使用完整模型 ID，不显示简称。例如 Anthropic 使用 `claude-opus-4-8`、`claude-opus-4-7`，不显示 `opus-4-8`、`opus-4-7`。
- 交付物：长期设计文档、实施计划、后端 profile registry、协议专属探针、前端动态模型选项、专项回归、真实链路验证记录。

## 官方来源核对

每次实现或更新前必须重新核对官方资料，不能只凭本地旧目录：

- OpenAI / GPT：OpenAI Models、Responses、Chat Completions、Pricing、Deprecations。
- Anthropic：Anthropic Models、List Models、Model deprecations、Messages、Count Message tokens、Pricing。
- GLM：智谱模型概览、OpenAI API 兼容、HTTP API、GLM Coding Plan、Z.AI Pricing。
- DeepSeek：API Docs、List Models、Chat Completions、Thinking Mode、Context Caching、Pricing。
- Gemini：Gemini API Models、GenerateContent、StreamGenerateContent、CountTokens、Pricing。

2026-06-30 资料校准结论：官方协议资料能支撑按 profile 做模型可信度诊断，但不能支撑“物理模型身份证明”。Gemini native 必须按 `generateContent` / `streamGenerateContent` 的 `candidates[]`、`usageMetadata`、`modelVersion` 解析，短输出 token 可能被 thinking tokens 挤占，因此探针提高最小输出 token，不全局强制 `thinkingBudget=0`。Anthropic Messages 检测按 `content[]`、`model`、`usage`、`tool_use` 解析；Opus 4.7+ 相关探针不发送通用采样字段，避免官方参数约束导致误判。GLM、DeepSeek 走 OpenAI Chat-compatible 时只按 Chat Completions 字段判分，不套用 Responses 字段。

## 方案概述

### 1. 检测 profile 注册表

新增模型检测 profile registry，按供应商协议能力选择检测实现：

| profile | 适用范围 | 请求协议 | 首批模型 |
| --- | --- | --- | --- |
| `openai_responses_strong` | GPT / 通用 OpenAI-compatible Responses 账户 | `/v1/responses` | `gpt-5.5`、`gpt-5.4` |
| `openai_chat_strong` | GLM / DeepSeek / Gemini OpenAI Chat compatibility 等 Chat-only 账户 | `/v1/chat/completions` | `glm-5.2`、`glm-5.1`、`deepseek-v4-flash`、`deepseek-v4-pro` |
| `anthropic_messages_strong` | Anthropic Messages 原生账户 | `/v1/messages` | `claude-opus-4-8`、`claude-opus-4-7` |
| `gemini_native_strong` | Gemini native 账户 | Gemini v1beta | `gemini-3.5-flash`、`gemini-3.1-pro-preview` |

每个 profile 包含模型列表、默认模型、辅助模型配对、请求构造、响应解析、usage 解析、协议能力项、行为探针、评分阈值和证据摘要格式。

### 2. 协议专属探针

- OpenAI Responses：沿用现有 Responses 基础文本、SSE、结构化输出、工具调用、usage、行为指纹、长上下文、稳定性、辅助模型对照和可信对比分布相似度。
- OpenAI Chat：新增 Chat Completions JSON / SSE、严格 JSON 输出、tool calls、usage、行为指纹、长上下文、稳定性和辅助模型对照。
- Anthropic Messages：新增 Messages JSON / SSE、`/messages/count_tokens`、`tool_use`、usage、行为指纹、长上下文、稳定性和辅助模型对照。
- Gemini native：新增 `generateContent`、`streamGenerateContent`、`countTokens`、function calling、`usageMetadata`、行为指纹、长上下文、稳定性和辅助模型对照。

### 3. 模型 ID 与 UI

- 后端 options 按当前目标账户返回完整模型 ID，不返回简称。
- 前端模型下拉只展示完整 ID。
- 检测提交、历史筛选、详情抽屉和终端命令行都使用完整 ID。
- 如果 Gemini 原生返回 `models/<id>`，解析层可以识别，但 UI 与存储统一保存本地完整 ID，例如 `gemini-3.5-flash`。

### 4. 存储与兼容

- `model_check_runs.model` 从类型层面放开为字符串完整模型 ID。
- 不做旧数据兼容分支；已有 `gpt-5.5` / `gpt-5.4` 历史天然仍是合法完整 ID。
- `provider_code` 继续记录目标账户供应商；必要时在 `requestSummary` 或 `resultSummary` 中记录 `modelCheckProfile`。
- 检测项证据继续只保存脱敏、有界摘要，不保存完整探针题面或大体积响应。

## 风险与注意事项

- 黑盒 API 不能证明真实物理模型身份，只能给可信度诊断。
- 多供应商协议字段差异大，不能用 GPT Responses 的模型字段、usage 字段或工具调用结构套用到其他协议。
- Anthropic、GLM、DeepSeek、Gemini 的模型列表变化较快，每次实现或调整前必须重新核对官方来源。
- 强诊断会消耗更多 token、请求次数和额度；页面需要继续明确成本由发起用户承担。
- 真实 smoke 依赖可用上游账号和网络环境，不能把真实 Key 或敏感响应写入文档。
