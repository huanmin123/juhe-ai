# PLAN-20260727T131815566Z performance 进程指标活跃索引修复

## 目标

修复 performance 多进程拓扑中 Gateway、DB service 和后台 worker 事件循环指标随机缺失的问题，使 stats worker 每轮能够在固定开销内发现全部活跃进程并批量持久化，同时不把指标采集故障扩散到业务请求链路。

## 已确认事实

- 生产拓扑的 14 个进程都在持续写入带 20 秒 TTL 的注册项，publisher 和各进程启动入口正常。
- 当前 reader 在共享 Redis 大键空间执行 `SCAN MATCH`，但最多只读取 4 页、每页 `COUNT 64`。`COUNT` 只是提示，匹配键稀疏时 4 页无法覆盖键空间，导致本轮常常只发现 1 个进程。
- stats worker 的 IPC 补采只能访问自身管理的子进程，无法覆盖由 launchd 独立托管的 Gateway 和 DB service，因此注册表漏读会直接形成监控缺口。
- Nginx 已使用 `least_conn`，三个 Gateway 的请求分布基本均衡；本问题不能据此判断需要扩容到五个实例。

## 方案

1. 保留每进程独立 sample key 和 20 秒 TTL，避免改变退出进程自动淘汰语义。
2. publisher 用单个 Lua 命令原子执行 `SET EX`、`ZADD`、过期成员清理、基数限制和索引 TTL 刷新，把 sample key 加入独立的有序集合活跃索引；score 使用 Redis `TIME`，避免节点本地时钟偏差影响存活判断。
3. reader 使用相同 Redis 时钟在该小型索引中清理并查询最近 20 秒成员，再用一次 `MGET` 批量读取样本；禁止重新依赖共享键空间 `SCAN`。索引观测时间作为最终持久化采样时间，本地 `sampledAt` 只做 payload 合法性校验。
4. 索引本身使用短 TTL，并限制为 512 个成员，可覆盖合法最大 132 进程拓扑和滚动重叠。全部 publisher 停止后索引自动消失；reader 停摆期间 publisher 仍会清理过期成员并限制基数。
5. Redis 读取或发布失败继续按现有 fail-open 边界处理：记录监控缺测，不阻断业务请求；publisher 连续失败按 5、10、10 秒退避，上限小于 20 秒注册 lease，兼顾避免重连风暴和 Redis 恢复后的指标恢复时间，也不回退到全键空间遍历。

## 滚动升级边界

- 新 publisher 仍写现有 v2 sample key，因此旧 reader 的行为不被立即破坏。
- 新 reader 只发现已经写入活跃索引的 publisher。尚未升级的旧进程会持续缺测到该进程升级并完成首次发布，不能把这段时间误写成 20 秒 TTL。
- macOS performance 安装器必须逐个重启并健康检查 Gateway，使 Gateway 与对应 DB service 先进入新索引；最后再重启 control 及其 worker，让新 stats reader 上线。每个新进程最长一个 5 秒发布周期进入索引。
- 监控短时缺测可以接受，不能为兼容窗口保留不可靠且开销随 Redis 总键数增长的全局扫描；自定义部署器也必须遵守 publisher 先、reader 后的升级协议。
- 完整性会校验 worker 精确副本，并要求每个已租约存活的 `control/gateway:<id>` 都有同 ID 的 `db-service:<id>`。自定义 Gateway ID 没有外部期望清单，因此一组成对退出的旧 Gateway/DB service 最多可在 20 秒 lease 内暂时替代尚未出现的新 ID；这是短 TTL 监控的明确陈旧边界，不能据此改变流量路由或容量配置。

## 验证清单

- [ ] 14 个动态角色在存在大量无关 Redis key 时仍可完整读取。
- [ ] 合法最大 132 进程拓扑可完整读取，滚动重叠和实例 churn 不突破 512 成员上限。
- [ ] reader 不发送 `SCAN`，固定为索引查询和批量 `MGET`。
- [ ] 超过 20 秒的成员被清理，失效或畸形样本不返回。
- [ ] publisher 原子刷新 sample、索引成员和索引 TTL。
- [ ] Redis 统一时钟、连续失败退避和 Gateway-first/control-last 部署顺序有回归保护。
- [ ] 现有发布错峰、拓扑、批量事务和 TypeScript 检查通过。
- [ ] 多 agent 从 Redis 协议、异常边界和回归覆盖角度完成复查。

## 完成标准

- 生产同等 14 进程拓扑不再因 Redis 总键空间规模随机漏采。
- 指标读取的 Redis 命令数量和扫描范围只随活跃进程数增长，不随业务 key 总数增长。
- 代码、测试、功能文档和 bug 记录对齐，未引入请求路径依赖或持久事实语义。
