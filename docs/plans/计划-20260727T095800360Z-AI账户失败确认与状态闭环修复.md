# PLAN-20260727T095800360Z AI账户失败确认与状态闭环修复

## 目标

恢复真实网关失败、独立确认探针、账户临时不可调用、冷却复测和调度展示之间的闭环，同时保留“不按单次业务 HTTP 状态猜测账户语义”的安全边界。

## 现场与根因

- 生产 `huanmin / hubway` 在 2026-07-27 17:29 的周期健康检查已经恢复 HTTP 200，当前 `active + schedulable` 有最新成功证据，不应人工改库。
- `4ce09cc2e` 之后，generic 完整 HTTP 失败被归为 `opaque_upstream`，但质量聚合排除了该归因，因此使用记录中的连续错误无法形成质量失败确认候选。
- 周期健康和质量确认探针虽已执行，但完整 HTTP 失败被归为 `framing_complete_neutral` 后不累计阈值、不写 `temporary_unavailable`。
- OpenAI 账户健康检查新增模型目录预检后，`GET /v1/models` 被原生协议辅助判定误识别为 Anthropic 请求，在发出真实上游探针前以 `request_capability_mismatch` 短路；该失败属于本地任务失败，因此失败计数保持 0。
- AI 健康页把最近一条历史检查失败显示为“当前不可用”，同时又把持久 `active` 显示为“可调度”，造成两个不同时间维度的状态互相矛盾。
- 账户电路已经避让时，账户列表未消费 `circuitSummary`，仍可能显示纯绿色“可调度”。

## 设计边界

1. 单次业务请求失败只记录 `opaque_upstream` 诊断事实，不按状态码、错误码或正文解释限流、凭据失效或永久异常，也不直接写账户状态或共享质量。
2. gateway 的完整 opaque HTTP 失败、最终 transport failure、完整 JSON 协议失败和流式协议失败终态，每个真实请求合计最多投递一次独立健康检查；standalone 走本地 worker，performance gateway 通过 loopback HMAC 通道交给 control/ops-worker。两端按账户设置 5 分钟触发冷却，请求失败只升级低优先级周期任务，不覆盖激活或配置复检；该探针可使用健康检查队列的保留并发槽。
3. 使用固定健康模型和固定协议的受控独立探针，以协议诊断 `result.success` 判断账户可用性。完整 HTTP 失败和 transport failure 都可作为通用可用性失败，但不得派生具体错误语义。
4. 传输电路继续只消费 transport evidence；完整 framing 对传输电路保持中性，不能因为本计划改变 transport scope、generation、CAS 或升级规则。
5. 健康页明确区分“账户基础状态”和“最近检查结果”；账户列表在电路避让或验证时显示运行态标签，不把局部避让误写成整账户永久停用。

## 验收标准

- generic 上游失败会投递独立健康检查，但在探针执行前账户仍保持原状态和共享质量。
- 请求失败触发的独立确认探针成功时账户继续可调度；完整 HTTP 或 transport 确认失败时按专用阈值 1 和 CAS 写入 `temporary_unavailable`。正常周期健康仍使用配置的连续失败阈值。
- 任意 HTTP 状态码互换不改变动作类型，只影响脱敏诊断事实。
- AI 健康页显示“已启用 + 最近检查失败”等事实组合，不再把历史点称为当前状态。
- 电路避让中的账户不再显示纯绿色“可调度”。
