## 需求目标

- 背景：当前系统已经形成从 OpenAI 账户接入、账户测试、分组绑定、API Key 授权、网关调度、上游转发、响应回传、使用记录和原始审计的闭环。前置审查发现候选账号选择、响应类型判断、审计 payload 保全、请求体内存占用和队列可观测性等环节仍存在功能隐患或性能风险。
- 目标：账户创建、保存、测试和状态接口维持现状，不作为本计划治理对象；重点把调度候选、网关转发、响应分类、审计保全、请求体内存和队列可观测性收敛到可解释、可验证的链路中。
- 交付物：长期文档同步、后端调度和网关改造、必要诊断入口、测试项和验证记录。本计划已完成代码落地、自动化验证、构建验证、mock 全链路验证和本机模拟性能验证；真实上游人工验收仍按环境条件单独执行。

## 范围边界

### 本次包含

- [x] 调度候选治理：固定候选窗口改为“筛选后补齐”的有界循环，记录扫描数量、过滤原因和最终候选命中情况。
- [x] 响应类型治理：收敛 `application/octet-stream` 与 SSE / 流式响应判断，避免把普通二进制响应误判为 OpenAI 事件流。
- [x] 审计 payload 保全治理：统一 capture、IPC、worker、落库之间的截断语义，超限时保留摘要、大小、哈希、头尾片段和丢弃原因。
- [x] 请求体内存治理：为真实转发链路增加 in-flight body bytes 限制；后续按风险决定是否引入临时文件 replay 或更细粒度流式透传。
- [x] 模型匹配治理：明确模型精确匹配、别名、模型族和自定义映射之间的优先级，减少合法请求被误拒。
- [x] OAuth 刷新治理：减少请求热路径上的临近过期刷新影响，补充刷新预热、账号回避或诊断指标。
- [x] 队列和可观测性治理：补充使用记录队列、审计队列、账号调度、上游错误、响应分类的运行态指标和告警入口。

### 本次不包含

- 多节点部署、跨实例一致性和用户分片：归入 `PLAN-0037`，本计划只保证单实例当前闭环先稳定。
- 账户创建、保存、测试和状态接口治理：不做；账户管理流程维持现状。
- 运行时代码向下兼容旧 schema、旧字段或旧接口：项目规则默认按当前最优契约推进，历史数据如需处理另行提供离线脚本或 SQL。
- 引入重型外部队列、分布式缓存或独立网关集群：当前先沿用本地 DB service、background worker 和轻量进程边界。
- 全量 OpenAI API 端点白名单体系：如果后续决定限制 API Key 透传端点，再拆出独立接口契约和安全计划。
- 前端大规模信息架构重排：本计划只补必要状态、操作和诊断入口。

## 初步风险定位

| 风险点 | 当前表现 | 影响 | 后续处理方向 |
| --- | --- | --- | --- |
| 请求体完整缓冲 | 网关、文本、图片请求存在 MB 级完整 body 缓冲 | 高并发大请求时内存压力放大 | 增加 in-flight bytes 限流，评估临时文件 replay |
| 候选窗口固定 | 调度先取固定数量账号，再执行多层过滤 | 可用账号在窗口外时可能误判无账号 | 有界补齐、扫描上限和过滤原因统计 |
| 审计截断语义不一致 | capture、IPC、总消息大小各有截断阈值 | 失败证据可能被静默缩减或 hash-only | 统一摘要结构和超限原因 |
| `octet-stream` 误判流式 | 二进制类型可能进入 SSE 终止事件判断 | 非 SSE 二进制响应可能被错误处理 | 基于请求路径、上游头和有限 peek 综合判断 |
| SSE 无可见输出误伤账号 | 首段前超时、缺少终止事件或未输出前错误可能触发账号运行态副作用 | 可重试失败被误认为账号质量问题，导致短期屏蔽或流失败计数 | 只在已产生可见模型输出后应用账号级流失败副作用 |
| 超大审计摘要缺少原始 hash | 超过摘要阈值的大 body 可能只有头尾摘要、大小和结构信息 | 复盘时无法用 hash 精确关联原始请求 / 响应证据 | summary-only 摘要和 payload 引用都保留原始 body SHA256 |
| 模型匹配过窄 | 模型过滤偏精确字符串匹配 | 账号级自定义映射请求容易被误拒 | 直接模型精确匹配优先；启用的账号映射源做精确一跳匹配；不做模型族、前缀或模糊匹配 |
| OAuth 热路径刷新 | 请求准备阶段可能触发 refresh | 首个请求延迟或失败风险增加 | 已过期 / 5 秒内到期才阻塞刷新；5 到 60 秒临期 token 改为后台预热 |
| 队列背压不透明 | 使用记录、审计队列有容量边界 | 写入失败或丢弃时排障成本高 | 暴露队列长度、丢弃数、失败原因和 worker 状态 |

## 方案概述

- 方案原则：账户管理流程维持现状，先处理真实影响网关稳定性、排障能力和性能边界的运行链路问题。
- 数据变化：不涉及账户状态字段、默认值或保存路径调整；如新增诊断字段、窗口统计表或队列状态快照，按当前 schema 直接设计，不保留运行时旧结构兼容。
- 接口变化：不改管理 API 的账户保存、测试和状态接口；接口变化聚焦调度诊断、队列状态、阈值配置和模型匹配规则。
- 前端变化：不改变账户页操作流程；只在需要时补充调度失败原因、队列状态、阈值配置和审计截断说明等中文诊断信息。
- 后端变化：调整调度候选循环、响应类型判断、审计 capture 与 IPC payload、请求体限流、OAuth 刷新策略和队列诊断。
- 数据处理策略：不做账户状态数据清洗；不在 route、repository、worker 或网关热路径内写旧数据兼容分支。

## 待确认细节

- 调度候选诊断已进入审计 metadata `account_dispatch_candidate_window`；当前不新增账户页或分组页展示入口。
- 请求体 in-flight bytes 已默认按 256MB 保护；后续只需结合真实部署内存和压测结果确认是否调整生产阈值。
- API Key 透传是否继续允许宽路径，还是按 OpenAI 端点能力逐步收敛。
- 审计 payload 超限后需要保留 head-tail 字节数、hash 算法、敏感字段脱敏规则和最长保存周期。
- 模型匹配当前只支持精确下游模型和账号级显式映射源；模型族、前缀和模糊别名不进入本计划运行时规则。
- OAuth 账号当前采用 5 秒硬阻塞刷新阈值和 60 秒后台预热阈值；刷新失败只记录日志或由既有后台连续失败策略处理，不新增账号状态入口。

## 风险与注意事项

- 候选补齐会增加 DB service 查询和水合批次，但已经固定单窗口 `512` 扫描上限、最终 `256` 候选上限和审计诊断字段；如果真实流量长期触达扫描上限，应优先扩容账号分组或拆分号池，而不是放开无界扫描。
- 响应分类调整必须重点回归图片、下载、非流式 JSON 和 SSE 终止事件，避免修复二进制误判时破坏现有流式链路。
- 审计保全增强会增加存储字段和写入体积，需要明确截断阈值、脱敏规则和保留周期。
- 请求体 in-flight bytes 阈值过低会拒绝合法图片或大上下文请求，生产阈值需要结合部署规格、上游接口能力和真实压测确认；当前默认 256MB，本机模拟性能不能替代目标机器压测。
- 模型匹配治理当前刻意不做模型族、前缀或模糊别名；如后续需要自动模型路由，应拆独立计划并补计费、质量和灰度边界。
- OAuth refresh 预热如果在真实流量中频繁失败，应优先检查后台预刷新是否滞后、代理质量和 token endpoint 可用性；当前预热失败只记日志，不新增账号状态写入口。
- 队列健康快照只解决“看得见”，不改变队列处理能力；如果真实环境持续 `backlogged` 或 `degraded`，仍需要结合数据库写入耗时、worker 负载和队列阈值继续治理。
- 发布异常处理：如果实现后出现误拒或调度异常，应先关闭新增严格策略或降低阈值，保留同一当前契约下的已验证构建，不引入运行时旧结构兼容。
