## 需求目标

- 背景：PLAN-0073 已完成“用户请求只采样失败，后台探针恢复”的基础闭环，但仍存在探针语义复用 `cooldown_retest`、旧探针结果可能覆盖新状态、批量状态转换时探针缺少统一预算，以及高性能多节点下进程内 timer 不可靠的问题。
- 目标：补齐状态事件触发探针调度器设计和实现，让 standalone 与 performance 都使用同一套状态机语义；performance 模式下运行态探针状态、generation 和 due 索引必须进入 Redis runtime state，且不使用 Redis 分布式锁。
- 交付物：文档补充、探针 traffic source 拆分、探针 generation 防旧结果、调度预算 / jitter、Redis 多节点边界、回归验证。

## 方案概述

- 状态转换提交 `ProbeIntent`，探针调度器统一去重、本机预算、jitter 和执行。
- 运行态恢复探针使用 `traffic_source = runtime_recovery_probe`；持久冷却复测继续使用 `cooldown_retest`。
- 探针状态带 `generation`，真实成功、手动恢复和新状态转换都会推进 generation；旧探针结果回写前发现 generation 变化则丢弃。
- standalone 使用内存任务表和 timer；performance 使用 Redis runtime state 保存状态、Redis due index 支持任意节点 sweep，重复执行由 generation 条件写入和条件删除收敛；请求调度链路允许短暂不一致并使用短 TTL 近端缓存降低 Redis 压力。
- 探针固定使用现有账户测试健康链路；模型优先历史测试成功模型，其次供应商默认测试模型，失败现场只作为日志和状态判断依据，不进入探针请求。

## 风险与注意事项

- Redis due index 是短 TTL 运行态索引，不是持久事实；Redis 丢失后允许回到保守调度，但不能丢账务和审计事实。
- 请求调度链路允许秒级短暂不一致；不要为了实时一致性给用户请求增加分布式锁或按候选账号数量持续打 Redis。
- Redis 探针状态只保存非敏感运行态元数据；执行探针前通过 DB service 重新读取账号凭据，禁止把 API Key、OAuth token、代理密码或失败请求 payload 写入 Redis。
- 本机探针预算过小会降低恢复速度，预算过大可能放大上游压力；初始值应保守，后续根据压测调整。
- 失败请求形态不参与恢复探针；当前只避免把请求 / 能力错误误归因到账户不可用。
