## 需求目标

- 背景：用户在前端网络卡顿时连续点击创建按钮，可能导致重复创建多条业务数据；同时希望每个功能都有明确唯一键，尽量通过数据库唯一约束保证数据安全。
- 目标：设计统一幂等能力和业务唯一约束策略，避免把防重复逻辑散落在每个按钮或接口里。
- 交付物：幂等与唯一约束设计文档、计划记录、存储说明和接口契约更新；代码实现待设计确认后继续推进。

## 方案概述

- 方案原则：前端防重复只做体验，后端幂等记录负责同一次请求重放，数据库唯一约束负责最终数据安全。
- 数据变化：建议新增 `idempotency_records` 表，补充实体和关系表业务唯一索引。
- 接口变化：管理端创建类 `POST` 默认要求 `Idempotency-Key`；同 key 同请求返回第一次响应，同 key 不同请求返回 `409`。
- 前端变化：请求封装支持幂等 key，表单提交 pending 内复用同一 key，表单内容变化后生成新 key。
- 后端变化：新增幂等服务，和 `runLoggedOperation()` 或外层包装合并，确保业务写入、操作日志和幂等结果同事务提交。
- 数据处理策略：正式加唯一索引前先检查重复数据；当前预上线本地库可备份后清理或重建。

## 验收标准

- [ ] 创建类接口支持 `Idempotency-Key`，重复提交不会创建多条业务数据。
- [ ] 同 key 同请求返回第一次成功响应；同 key 不同请求返回 `409`。
- [ ] 不同 key 但命中业务唯一键时返回 `409`，由数据库约束兜底。
- [ ] 操作日志只记录首次真实成功变更，幂等重放不产生第二条日志。
- [ ] 每张表至少有主键或组合主键；实体表和关系表补齐业务唯一键或明确不适用原因。
- [ ] 前端创建 / 提交弹窗统一生成和复用幂等 key，pending 状态防连点。
- [ ] 幂等记录有保留期和清理策略，不影响高频网关主链路性能。
- [ ] 必要文档、类型、接口契约和存储说明已同步。

## 风险与注意事项

- API Key 创建响应包含明文密钥，幂等记录必须加密保存响应，不能明文落库。
- 外部调用类接口不能长事务包住网络请求，否则会放大 SQLite 写锁等待。
- 新增唯一索引前必须先检查本地库重复数据，否则建索引会失败。
- 公告、操作日志、使用记录等不能为了“每表业务唯一”强行按内容唯一，否则会误删或拦截真实事件。
- 网关侧 `Idempotency-Key` 是公开 API 透传语义，和后台管理端幂等记录暂不混用。
