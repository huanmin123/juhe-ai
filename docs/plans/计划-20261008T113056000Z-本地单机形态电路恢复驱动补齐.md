## 需求目标

- 背景：项目真实主形态是个人用户本地单机使用（SQLite + 无 Redis，`deploy/start.sh`/`start.ps1` 启动 gateway+jobs 双进程）。2026-10-08 体检确认：账户熔断运行态在 gateway 进程内（memory store），而熔断恢复职责在 jobs 的 Redis 扫描任务，本地形态下该任务 fail-closed disabled 且 gateway 进程内无替补驱动——账户熔断后永久冻结直到进程重启。同族缺口：`KeyModelMemoryRecoveryRunner` 在 gateway 内已实现但无任何装配点。
- 目标：
  1. 本地单机形态下，熔断账户（主链 protocol/model→account 电路）能被后台恢复驱动按期推进（确认/金丝雀/退避），不再冻结；恢复转换照常投影 ledger，管理页可见推进。
  2. key-model 能力熔断记忆（memory 形态）有后台恢复驱动，误判屏蔽可自愈。
  3. 本地部署文档准确描述"未配置 Redis 时的行为"，消除"补配 Redis 触发 performance 推断拒启"陷阱。
- 交付物：gateway 恢复驱动代码与测试、key-model runner 装配、权威设计文档补节、`deploy/README.md` 订正、验证记录。

## 方案概述

- 方案原则：**谁拥有运行态，谁负责恢复**。memory 形态运行态在 gateway 进程内 → 恢复驱动也在 gateway 进程内；Redis 形态运行态共享 → 恢复仍归 jobs（现状不变）。形态判定是依赖门禁（`RuntimeStateDriver != "redis"` 装配），不是功能开关（遵守"功能不设开关"）。状态机契约以 jobs `CircuitRecoveryService` 为源逐段对照，双方言 store 能力已取证对齐（ListDue/Acquire/Complete/惰性租约回收，memory 与 Redis due 语义一致）。
- 数据变化：无 schema 变化、无 env 变化（不新增任何配置项）。
- 接口变化：无对外接口变化；`newChainAccountCircuitService` 内部签名扩展（外露 store 与 mutation hook 供恢复组件装配）。
- 后端变化：`internal/gatewaycircuit/` 新增恢复 sweep + 分类器 + identity 解析；`cmd/juhe-ai-gateway/` 新增恢复组件装配（主链电路 + key-model runner），挂入 supervisor components。
- 恢复流程（对齐 jobs）：每轮 ListDue → 相位分类（SUSPECT→确认租约；OPEN/RECOVERING→canary 租约）→ 解析 identity → 账户读取与 dispatch revision 围栏 → 租约内探针（超时 unknown）→ 按 outcome 结算（framing_complete 推进/transport_failure 退避升级/unknown 中性/credential_rejected 不推进）→ mutation 经 persist hook 投影 ledger。
- 数据处理策略：无存量数据迁移；运行态为进程内 memory，重启即重来（既有语义）。

## 风险与注意事项

- 风险 1：恢复探针产生真实上游诊断流量。缓解：仅熔断 due 状态触发（ListDue 收敛），批量与并发契约对齐 jobs（sweep batch 200；轮内 worker 并发两侧装配均传探针并发预算 `JUHE_AI_JOBS_PROBE_CONCURRENCY`，默认 512/上限 5096；包级 `RecoveryDefaultConcurrency=4` 仅为零值回落，生产不可达），单机熔断账户数天然有限。
- 风险 2：sweep 与主链请求并发操作同一 store。缓解：store 级围栏（lease 互斥/generation/revision CAS）已保证单 winner，取证确认无需新锁。
- 风险 3：persist hook 未就绪（owner gate 不齐）时投影缺席。缓解：与既有装配同构——hook 为 nil 时 sweep 照常推进运行态（恢复是调度事实），仅 ledger 展示滞后，不 fail。
- 发布异常处理：恢复驱动为纯加法组件，异常时回退到上一构建即回到"冻结直到重启"现状，无数据契约影响。
