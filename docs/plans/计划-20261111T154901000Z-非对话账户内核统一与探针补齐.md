## 1. 需求目标

### 1.1 背景

非对话账户（`video` / `audio` / `image`）已经与对话账户共用同一张 `accounts` 表、同一套管理 API 和同一条 `/v1` 主链，但用户走查发现：

- 同一批内核能力在各域入口暴露不一致：有的能改但列表不显示，有的显示了但实际无效果，有的后端支持但前端挡着；
- 非对话域缺少与对话域同级的“探针”闭环，导致测试、状态机、冷却恢复、锁死、特供等功能在非对话域要么不可用、要么语义未定义；
- 前后端各自维护一份能力矩阵，已经出现 xai/qwen 图像能力漂移；
- 向量、重排、安全模型如果继续按当前方式加 `v-if` 和特判，缺口会继续放大；按 2026-11-12 最终裁决，它们拆为独立场景类型/独立账户，不新增菜单。

### 1.2 目标

1. **一套账户内核**：非对话域与对话域共用账户模型、写契约、分组/标签/代理/并发/优先级/到期/时间计划/余额/错误策略，不为域复制一套账户系统。
2. **一条请求主链**：保留现有 `/v1` 主链，用显式 `DispatchPolicy`（Conversation / Stateless / Realtime）表达差异，不另开第二条请求链路。
3. **一套场景注册表**：后端与前端消费同一份“场景能力描述”（允许能力、账户类型、探测方式、表单字段、列表列、筛选标签、状态策略），新增场景只加描述，不改散落组件。
4. **统一探针**：非对话域以“账户 + 连接 + 凭据”为单位做安全连通性探测，不要求用户选择模型或协议；D0 已裁决为是，探测覆盖人工测试、后台周期检查、激活/冷却恢复、锁死/特供依赖。
5. **入口一致**：用户能在同一位置看到并操作同一能力；不再出现“表单能改、列表不显示”“菜单能点、实际无效果”。
6. **场景类型化**：向量、重排、安全、实时拆为独立场景类型/独立账户；不新增菜单，靠单菜单「AI 账户」+ 创建时场景选择 + 列表筛选；工具场景请求走 Stateless，不继承会话亲和/缓存率/流式重试；Realtime 走 WS 专用链。

### 1.4 2026-11-12 用户裁决摘要（避免重复讨论）

1. **锁死的语义**：锁死不是缓存/会话连续性，而是“尽可能把请求留在这个账户上，把它的额度/余额用掉”。典型：低价/白嫖/限时账户（如 100 元必须一天用完）但不稳定，普通调度动不动切号。只要账户没有被判定彻底死亡，就继续用它；只有死期判死、确定性硬门（disabled/过期/模型不支持/凭据无效/余额耗尽）或 `unlock` 才切走。
2. **锁死和特供都要**：非对话域、工具/向量/重排/实时账户都要支持，与对话同语义。
3. **Realtime 探针**：技术上可行就做，不能因为“麻烦”跳过。首批 gpt（OpenAI Realtime handler 已实现）做无音频 WS 握手；Gemini Live 依赖尚未实现的 M6 协议桥，明确标注依赖而不是假装支持；其他无法安全探测的 vendor 必须给出技术原因。
4. **GPT 音频不再自动含 `realtime_session`**：Realtime 拆成独立场景/账户；音频场景只保留 TTS/转写/长音频任务。
5. **向量/重排/安全模型拆分出去**：不再塞进对话域；因为它们 Base URL/端点不同，独立成场景类型和独立 AI 账户，避免请求寻址混在一起。
6. **AI 账户菜单合并**：取消 4 个二级域菜单，只保留一个一级「AI 账户」；原「AI 账户」组内其他项（任务中心）上提为一级；创建账户时选择「场景类型」；列表增加场景类型筛选；以后新增场景只加类型，不再加菜单。本期只动 AI 账户组，其他菜单组不动。
7. **后台探针**：D0=是，媒体/工具/实时账户与对话一样走后台探针/状态机；创建后 `pending_test`，探针通过转 `active`。
8. **锁死限流边界**：D12=是，`rate_limited` / `temporary_unavailable` 在锁死窗口内继续 hold；余额/额度耗尽等确定性硬门释放。
9. **不做向后兼容（2026-11-12 追加裁决）**：非对话账户当前没有实际使用；上线时统一删除 video/audio/image/embedding/rerank/moderation/realtime 场景账户（有就删），只保留对话账户，删除后按新场景重建。因此不保留旧非对话账户的数据迁移、混合账户拆分、旧前端请求兼容和旧二进制回滚路径；schema/接口按新契约直接切换。

- 不重写 `/v1` 主链，不新增第二条 HTTP 请求链路；
- 不改变路由拓扑、分组模式、策略路由、计费口径；

- 不为每个场景新增一级/二级菜单；场景通过创建时的类型与列表筛选区分（B1）。

### 3.2 差异根因分类

| 类别 | 含义 | 涉及能力 |

| **P：探针缺失** | 没有可复用的安全探测通道，导致测试/状态机/恢复/锁死/特供无法闭环 | 人工测试（音频）、后台探测（视频/音频/部分图像）、状态机、冷却恢复、锁死、特供、待检查状态 |

### 3.3 关键结论

1. **大部分“不支持”不是内核缺失，而是探针缺失**：音频测试、音视频后台探测、状态机、冷却恢复、锁死/特供都卡在同一件事——没有一个“安全、便宜、可周期执行”的非对话探针。
2. **另一部分是入口不一致**：列表隐藏优先级/时间计划、创建态显示响应检查、矩阵漂移、批量编辑门控、测试按钮位置，都是 UI/契约层问题。
3. **媒体域不是独立链路**：它已经在同一条 `/v1` 主链上，只是通过约 10 个布尔开关切掉对话专属能力；继续加域会把开关变成 20 个。

### 3.4 规范结论：应支持 / 条件支持 / 不应支持

> 本节是“行为契约层”的结论，不是现状描述。依据是现行文档与代码事实；凡与现行文档冲突的，标为“需 D0 裁决”。

#### 3.4.1 所有域都应支持（无条件）

| 能力 | 为什么应支持 | 目标入口 |
| --- | --- | --- |
| 账户名 / API Key / Base URL | 账户身份与出站寻址，与域无关 | 创建/编辑表单 |
| 支持模型 | 账户能力边界，媒体也必须声明 | 创建/编辑表单 |
| 分组 | 路由拓扑的唯一入口，与域无关 | 创建/编辑表单 |
| 标签 / 说明 | 运维事实，与域无关 | 创建/编辑表单、列表 |
| 代理 | 出站网络事实，媒体出站同样需要 | 创建/编辑表单 |
| 并发上限 | 账户级硬保护，与域无关 | 创建/编辑表单 |
| 每分钟请求上限（RPM） | 账户级派发保护，与域无关；属于额外能力 | 创建/编辑表单 |
| 优先级 | 候选排序四元组的一部分，媒体已在消费 | 创建/编辑表单、列表 |
| 超级优先 / 降级备用 | 候选排序标记，媒体已在消费 | 创建/编辑表单、操作菜单 |
| 到期时间 | 候选硬门，与域无关 | 创建/编辑表单、列表 |
| 时间计划 | 候选闸门 `availability_schedule_gate` 对所有域生效 | 创建/编辑表单、列表 |
| 错误处理规则 | 共享失败处理链对媒体同样生效 | 创建/编辑表单 |
| 锁死（切号否决） | 目标是把请求尽可能留在指定账户上消耗额度（低价/限时/不稳定账户）；跨协议/模型/lane，媒体与工具端点同样适用；不依赖探针即可生效 | 操作菜单 + 高级配置 |

#### 3.4.2 条件支持（依赖 D0 / 供应商 / 目录数据）

| 能力 | 支持条件 | 不满足时的行为 |
| --- | --- | --- |
| 媒体人工连通性测试 | 该连接 preset 有“无副作用”探测端点（GET 不存在任务 / 空 prompt / 空体） | 明确显示“该供应商暂不支持自动探测”，不伪造成功 |
| 后台周期探测 | D0 已裁决为是；该连接 preset 有安全探测端点 | 无可探测端点时明确标记不支持，不伪造 |
| 首次激活探测（pending_test → active） | D0 已裁决为是；探测端点可用 | 无可探测端点时按手动模式处理 |
| 冷却 / 错误恢复 | D0 已裁决为是；探测端点可用 | 无可探测端点时不进入状态机 |
| 特供 | D0 已裁决为是；账户存在合法冷却 fence；特供只加速冷却复测，不改变调度 | 无冷却复测路径时不显示/不生效 |
| 后台自动探测开关 | D0 已裁决为是；媒体与对话/图像一样可开关 | 手动模式按既有二态收敛 |
| 上游余额查询 | 供应商暴露余额接口，或使用自定义 adapter（内置 adapter 只覆盖 Sub2API/NewAPI/OpenAI Billing/LiteLLM/UserBalance） | 显示“该供应商暂不支持余额查询”，不展示空开关 |
| 图像周期探测 | `images_json` 空 prompt 探测可用；否则回退到 `GET /models` 模型存在性检查 | 两者都不可用时不开放自动探测 |
| 音频长任务探测 | 优先 `audio_job_get` 查不存在任务；只有 `audio_job_create` 的账户不得 POST 创建 | 无可安全探测模式时不开放自动探测 |
| 音频转写探测 | 内置极小 WAV 真实请求；成本可接受 | 周期探测可降频或只保留人工测试 |
| 模型映射（视频创建 / 同步 TTS） | 后端已消费同族映射（`video_generation` / `tts` 族）；媒体表单按简化原则暂不开放 | 长音频任务与图像无映射面，不支持；如后续需要，仅视频/TTS 按域开放同族映射 |
| 批量编辑 | 按域字段清单实现后开放（P2） | 未实现前保持禁用，并在 UI 说明原因 |

#### 3.4.3 不应支持（必须说明原因）

| 能力 / 行为 | 适用域 | 不应支持的原因 | 现状 |
| --- | --- | --- | --- |
| 会话亲和 / 分组会话粘性 / 账户内 Key 亲和 | 全部非对话域 | 非对话请求没有会话连续性，也没有上游上下文缓存；亲和会引入无收益的粘性与错误恢复状态 | 已按《对话与非对话媒体调度分离设计》§3.2 排除 |
| 缓存率排序 / 热质量 / 速度优先 / `latency_degraded` | 全部非对话域 | 非对话没有“缓存命中”语义；这些排序只服务对话上下文复用，套用会扭曲候选顺序 | 已排除（§3.2） |
| 同账户语义重试 / 流式服务端重试 / 提交边界受限重放 | 全部非对话域 | 媒体请求在受理后重试会重复创建任务或重复计费；设计明确“受理后固定账户” | 已排除（§3.3/§4.1） |
| 跨组会话重入 / 长时间恢复等待 | 全部非对话域 | 非对话使用一次静态候选快照，失败后立即返回最终错误；等待恢复没有会话可恢复 | 已排除（§3.1/§4.1） |

| 响应检查规则（广告/语义检查） | 视频/音频/图像 | 媒体响应由媒体处理器直接渲染为产物 URL、二进制或任务对象，没有对话文本语义；文本检查会误判，且媒体错误路径已绕过 chat JSON 检查管道 | 编辑态已隐藏；创建态需修复 |
| 客户端画像 / `clientCompatibility` | 视频/音频/图像 + 工具端点 | 客户端画像是 Codex/Claude Code 等对话客户端仿真概念；媒体与工具端点出站不使用该画像 | 媒体表单已隐藏；工具端点不适用 |
| GPT `service_tier` / reasoning 覆盖 | 视频/音频/图像 + 工具端点 | 仅适用于 GPT 对话/Responses 语义，媒体/工具请求没有该字段 | 媒体表单已隐藏；工具端点不适用 |
| 批量测试 | 全部域 | 会一次性制造大量上游请求和复杂任务状态；设计已删除该入口 | 已删除 |
| 模型检测（J3b）/ 模型质量预检 | 视频/音频/图像 + 向量/重排/安全模型 | 模型检测针对对话文本模型的质量与指纹；媒体产物和工具模型的输出没有对话文本质量语义 | §16 已排除媒体域；工具模型按 mode 排除 |
| 媒体专用路由模式 / 媒体专用调度偏好 | 视频/音频/图像 | 非对话使用现有路由拓扑 + 静态候选快照；新增媒体专用模式会复制一套无会话语义的路由配置 | 设计 §6 明确不新增 |
| 媒体专用缓存 / 媒体资源存储 | 视频/音频/图像 | 非对话无缓存语义；媒体产物按零资源存储由上游 URL/任务对象承接 | 设计 §6 明确不新增 |
| 真实生成式“深度测试” | 视频/音频/图像 | 会真实计费或创建异步任务；连通性探测已能回答“Key + Base URL 是否可用” | 本期不做，走演练场/真实流量 |
| 每模型探测 | 视频/音频/图像 | 成本与复杂度随模型数线性增长；账户级连通性是本计划的契约，模型级失败由真实流量/错误策略处理 | 不做 |
| `video_create` / `audio_job_create` 的 POST 创建式探测 | 视频/音频 | 会创建真实计费任务；必须用 GET 不存在任务或空体参数校验探测 | 现行探测已是 GET/空体；计划进一步禁止 POST |
| `audio_job_create` 作为后台健康检查形态 | 音频 | 该形态会真实创建任务；应改用 `audio_job_get`。DB CHECK 允许不等于应该使用 | 写侧白名单当前包含该值；计划移除或降级为“仅记录” |
| 域原地修改（chat ↔ image 等） | 全部域 | 改域等于能力集、健康画像、统计口径同时断裂；重建账户成本低 | 现行域不可变 |
| 跨协议映射 / `generic_http` / 混合供应商 | 全部域 | 已于 2026-11-05/11-07 退役；恢复会重新引入协议桥接与不可测组合 | 不得恢复 |
| 为媒体探测新增功能开关 | 全部域 | 功能只有交付/未交付两态；开关会制造不可测的状态组合 | 项目规范禁止 |
| 另开第二条请求链路 | 全部域 | 会复制认证、配额、路由、分组、代理、错误策略、usage、audit，维护成本翻倍 | 本计划明确不做 |

#### 3.4.6 向量 / 重排 / 安全模型：同日先议归 chat，最终裁决拆分出去

2026-11-12 同日讨论出现过“归入对话域”的方案，随后用户明确：**这些场景的 Base URL/端点不同，拆分出去单独 AI 账户，避免请求寻址混在一起**。最终裁决以 §3.5 的场景类型模型为准：

- **场景类型**：`embedding` / `rerank` / `moderation` 独立，各自一个账户；
- **独立凭据与 Base URL**：向量/重排常用不同厂商或不同版本根，不能和对话账户混用；
- **请求调度**：仍然走 `Stateless`（无会话、无缓存、无流式重试）；账户场景类型不决定调度类，请求 lane 决定；
- **不新增菜单**：单菜单「AI 账户」+ 场景类型筛选覆盖（§3.5）；
- **仍不应支持**：会话亲和/缓存率/热质量/速度优先、同账户流式重放、对话响应检查、客户端画像、GPT 服务等级/思考级别；
- **仍应支持**：账户基础字段、分组/标签/代理/并发/优先级/到期/时间计划、连通性探测、锁死、特供、错误策略；余额查询按供应商接口条件支持；
- **需要新增**：请求 lane/路由、目录 mode、provider adapter、usage/计费口径、探针；`/v1/embeddings` 当前落到文本 lane、`/v1/moderations` 未注册路由、`/v1/rerank` 不存在，这些都要在 B7 一并接通。

**实现归属**：B7「向量/重排/安全模型独立场景」。

### 3.5 场景类型与单菜单（2026-11-12 新裁决）

**问题**：当前 4 个域菜单（对话/视频/音频/图像）把“账户分类”和“菜单位置”绑死；向量/重排/安全/实时再拆域就会菜单爆炸，而且不同场景的 Base URL/端点不同，混在一个对话账户里会导致请求寻址不清。

**目标**：

1. **一个一级菜单「AI 账户」**：取消对话/视频/音频/图像四个二级菜单；管理面 `/accounts`、个人面 `/my-accounts` 各一个入口。
2. **创建账户时选「场景类型」**：场景类型来自供应商能力（provider × profile × account type 的合法矩阵），只显示该供应商支持的场景。
3. **一个账户 = 一个场景类型**：账户不再混合“对话 + 向量”或“音频 + 实时”；需要多场景就建多个账户。这样 Base URL、探针、状态、调度、计费都清晰。
4. **列表增加场景类型筛选**：列表展示所有场景账户；筛选项为场景类型（对话/视频/音频/图像/向量/重排/安全/实时/...）。
5. **以后新增场景只加类型，不加菜单**：场景注册表新增一行，前端通过能力目录自动出现筛选项和创建选项。

**场景类型清单（首批）**：

| 场景类型 | 说明 | 请求形态 | 调度类 | 探针 |
| --- | --- | --- | --- | --- |
| `chat` | 对话/Responses/Messages/Gemini 对话 | JSON/SSE | Conversation | 对话挑战 |
| `video` | 视频生成与任务面 | 异步任务 | Stateless | GET 不存在任务 |
| `audio` | TTS/转写/长音频任务（**不含 Realtime**） | JSON/任务 | Stateless | TTS 空体 / task GET / WAV |
| `image` | 同步生图 | JSON | Stateless | 空 prompt |
| `embedding` | 向量 | JSON | Stateless | 空/非法 input |
| `rerank` | 重排 | JSON | Stateless | 空 query/documents |
| `moderation` | 安全模型 | JSON | Stateless | 空 input |
| `realtime` | 实时语音（WS） | WebSocket | Realtime | WS 握手（B8） |

**GPT 音频为什么自动含 `realtime_session`，以及建议**：

- 现状：OpenAI 媒体矩阵的 audio 行把 `realtime_session` 也算进 audio 允许集；2026-11-11 起“媒体默认集 = 允许集全量”，所以新建 GPT 音频账户自动带上它。
- 问题：Realtime 是 WS 连接生命周期能力，不是 TTS/转写的附带项；不是所有 GPT Key/套餐都能开 Realtime。自动包含会让账户被 Realtime 请求选中而实际不可用，也让音频表单的能力含义变糊。
- 建议（B8）：**音频场景移除 `realtime_session`；Realtime 独立成场景/账户**。需要同时用 TTS 和 Realtime 就建两个账户；不自动合并。若用户坚持一个账户，则 `realtime_session` 必须是显式 opt-in，不得默认勾选。

**数据与命名**：

- 内部沿用 `accounts.capability_domain` 列名与 API `capabilityDomain` 字段（历史名），语义改为“场景类型”；UI/文档统一叫「场景类型」，避免大规模重命名风险。
- 允许值扩展为场景注册表；**移除固定四值 CHECK**，改为文本列 + 写侧注册表校验（gateway/jobs 启动门禁检查列形状，不再检查四值枚举）。这样以后新增场景类型不需要 DDL，只改注册表。
  - 代价：DB 层不再做枚举校验，依赖“账户只能经应用写入口写入”这一现状；如有外部 SQL 直写，需要另行加约束或校验。项目当前没有外部直写账户表的通道，接受该代价。
  - **D13 追加裁决**：不做向后兼容。上线 cutover 时统一删除全部非对话账户，只保留 `capability_domain='chat'` 的账户；删除后按新场景重建。因此不需要旧非对话账户的迁移、混合账户拆分或旧二进制回滚路径；schema 迁移可以按“停旧服务 → maintenance cutover（删非对话账户、去 CHECK）→ 起新版本”单向前进。回滚只按数据库备份恢复，不支持旧二进制直接接新库。
- 现有四值 `chat/video/audio/image` 保持不变；新增 `embedding/rerank/moderation/realtime` 只影响新建账户。**不再执行 B8.1 的 audio→realtime 存量迁移**：非对话账户在 cutover 统一删除，Realtime 账户重新创建。
- 场景类型创建后不可原地修改（与现行域不可变一致）；要换场景就新建账户。

**前端路由与菜单**：

- 删除 `/accounts/{chat|video|audio|image}` 与 `/my-accounts/{chat|video|audio|image}` 路由；
- 新增 `/accounts`、`/my-accounts`，列表页从 query/筛选读取场景类型；
- 旧路径删除，不做 redirect（D13 不做向后兼容）；
- 一级菜单只保留「AI 账户」；原二级组内的其他项（如任务中心）上提为一级菜单；其他菜单组不在本期；
- 场景类型筛选同时用于统计/健康/性能页的域筛选（值域扩展，接口参数可继续叫 `domain` 或改为 `scenarioType`，以接口契约为准）。

**创建流程**：

```text
点击「创建账户」 -> 选场景类型（只列当前账号有权限、且供应商矩阵支持的）
-> 选供应商（按场景过滤） -> 填 Key/Base URL/支持模型/分组/代理
-> 创建（pending_test） -> 后台探针通过 -> active
```

**为什么这样更好**：

- 菜单不再随场景增长；
- 一个账户只承载一种请求语义，Base URL/探针/计费/状态不含糊；
- 供应商能力矩阵就是创建时的选项来源，不会出现“建了但用不了”的组合；
- 未来加向量/重排/安全/实时/更多场景，只加注册表行和 adapter，不动菜单。

```text
        ├── 场景注册表（每场景类型一行，单一来源）
        │     dispatchClasses / conversationModes / statelessModes /
        │     allowedModes / accountTypes / probePolicy / statusPolicy /
        │     testPolicy / formFields / listColumns / filterLabel
        │
        └── 一条 /v1 主链
              ├── ConversationPolicy（会话亲和、缓存率、热质量、复杂恢复）
              ├── StatelessPolicy（无亲和、静态候选、有限换号、受理后固定）
              └── RealtimePolicy（WS 生命周期，入口短路）
```

### 4.2 设计原则

1. **内核不按场景分叉**：优先级、并发、分组、代理、到期、时间计划、余额、错误策略、锁死、特供只在账户层实现一次。
2. **场景只提供描述**：某个场景支持哪些能力、用什么探针、表单显示什么、列表显示什么、筛选标签是什么，由注册表表达，不写散落 `v-if`。
3. **探针以“账户 + 连接 + 凭据”为单位**：不再要求用户为一次连通性测试选择模型/协议；内部使用账户已配置的检查模型或连接代表端点。
4. **同一能力同一入口**：能在编辑表单配置的，列表/操作菜单必须可见；显示了的能力必须真实生效，否则不显示。
5. **场景类型与调度策略解耦**：场景类型决定账户归属、创建选项、列表筛选和允许能力；请求 lane 决定 `DispatchPolicy`。对话场景账户只服务工作流对话请求；向量/重排/安全是独立场景账户，只服务各自 JSON 端点；实时是独立 WS 场景。
6. **不为未来能力复制链路**：新场景默认映射到 `StatelessPolicy`；只有 Realtime 这类连接生命周期能力单独处理。
7. **菜单不随场景增长**：所有场景共用「AI 账户」一个菜单，靠创建时的场景类型和列表筛选区分。

### 4.3 目标用户体验

- **添加账户**：选场景类型 + 供应商 → 填 Key / Base URL / 支持模型 / 分组 / 代理 → 创建；高级项按需展开（并发、优先级、特权、到期、时间计划、余额、错误策略）。向量/重排/安全/实时各自是独立场景账户，不塞进对话账户。
- **测试**：非对话/工具/实时账户只有一个“测试 Key 与 Base URL”按钮；结果展示“Key 可用 / Base URL 可达 / HTTP 400（预期拒绝）/ 认证失败 / 网络失败”，不出现协议、模型、endpoint mode 选择。实时账户用 WS 握手结果。
- **列表**：单菜单展示所有场景账户；场景类型筛选；状态、优先级、并发、时间计划、余额、标签、代理、分组与对话账户一致。
- **操作**：测试、锁死/解锁、特供、停用/启用、清理运行状态与对话账户一致；不生效的项不显示。
- **后台**：按既有全局间隔（默认 1h，可配）执行安全探测；失败按阈值进入冷却/异常，成功恢复；不真实生成产物。

## 5. 探针设计（核心）

### 5.1 探测单位与目标

- **单位**：账户（或账户实例）+ 一个健康检查连接 + 当前 Key。
- **目标**：证明“该 Key 能通过该 Base URL 完成认证并到达目标端点”。
- **不目标**：证明模型可用、证明生成成功、证明配额充足。
- **原则**：任何探测请求都不得触发真实计费任务；视频/长音频绝不 POST 创建端点。

### 5.4.1 B0 取证修正（2026-11-12 复审 blocker）

以下为复审确认的现状事实，B0 必须先按此修正 §5.2/§5.3，不得按 OpenAI 模板直接实现：

- **qwen 图像**：DashScope 原生同步接口 `POST /api/v1/services/aigc/multimodal-generation/generation`（`input.messages` + `parameters`），不是 OpenAI `images_json`；qwen base_url 是 origin，不能直拼 `/images/generations`。
- **volcengine 长音频**：查询是 `POST /api/v3/auc/bigmodel/query`，任务 ID 在请求头、业务状态在响应头 `X-Api-Status-Code`；属于 `volcengine_openspeech` preset，不是 `volcengine_ark`。不能按“GET 任务 + HTTP 状态码”实现。
- **gemini TTS**：走 `POST /v1beta/models/{model}:generateContent` + `responseModalities: AUDIO`，没有 `/tts` 端点。
- **minimax TTS**：路径是 `/t2a_v2`，不是 `/tts/create`。
- **状态码分类**：禁止只用“2xx/400/404/422 = Key 有效、401/403 = 凭据无效”。404 可能是路由不存在/WAF；volcengine 403/45000030 是缺 resource_id（不是 Key 无效），400/45001116 反而已过鉴权。§5.4 必须改成 per-vendor“状态码 + 错误码/错误体”白名单，B0 为每个组合回填“鉴权后拒绝”的样本。
- **Realtime**：`101 + session.created` 无仓库证据，现有网关只拨号透传、不消费该事件；B0 必须先做一次真实 OpenAI 握手取证（事件序列、是否需要 `OpenAI-Beta`、空连接是否计费），取证前只开人工测试，不开后台探测。
- **J1 执行引擎**：B4 不是只扩 J1 SQL 白名单。J1 实际走 `exactkeyprobe.ProbeOpenAI`，其 `images_json` 会构造真实生成请求（prompt + 1024x1024），`video_create`/`audio_job_get` 等未登记 mode 会 fail-closed。B4 必须新增连通性执行分支（`exactkeyprobe` connectivity 或复用 `accountprobe`），并加“不得真实生成/不得 POST 创建任务”的负断言。



`realtime_session` 是 WebSocket 连接生命周期能力，不是普通 HTTP 请求；但它可以有一个**无音频、无文本的安全握手探针**。用户要求技术上可行就做，不能因为麻烦跳过。

**探测方式**：

| 供应商 | 握手 | 成功判定 | 现状/备注 |
| --- | --- | --- | --- |
| OpenAI Realtime (gpt) | `wss://{host}/v1/realtime?model={model}` + `Authorization` | 101 + `session.created` | **可做**：现有 `chain_realtime.go` 已有 WS 拨号/代理/TLS 实现，可复用；连接后立即关闭，不发送 audio/text，预计无 token 计费 |
| Gemini Live (gemini native) | `wss://...BidiGenerateContent` + 最小 `setup` | `setupComplete` | **未实施**：M6 Gemini Live 协议桥本身未落地，当前 realtime handler 只支持 OpenAI Realtime；不是探针技术问题，是协议桥缺失。Realtime 场景先只开放 gpt；Gemini Live 随 M6 立项，探针随 M6 接入 |
| 其他 vendor | 按官方 WS 文档回填 | 101 + 厂商 setup 完成 | 没有官方 Realtime/WS handler 的 vendor 不开放 Realtime 场景；不硬造 |

**约束**：

- 只建立连接并完成最小 setup，不发送音频/文本/工具调用；超时 10–20s；关闭码 1000；
- 走账户代理/代理池与 TLS 配置，与真实 Realtime 请求同源；
- 人工测试不写账户状态；后台探测只写健康事实；
- 如果某供应商的 WS 握手必须创建付费会话或必须发送音频才能确认，标记“不支持自动探测”，并在 UI 显示原因——不静默跳过，也不伪造成功。

**归属**：B8「Realtime 场景与 WS 探针」。

### 5.6 探测频率与成本

- 复用全局 `accountHealthCheckIntervalHours`（默认 1h，范围 1–168），不新增场景级开关；
- 非对话/工具探测为一次轻量 GET/空体请求，成本远低于真实生成；
- 沿用 J1 的 jitter、并发上限、失败阈值、冷却退避；
- 不在真实非对话请求失败时额外派发探针（保留《对话与非对话媒体调度分离设计》§4.2 的“媒体失败不派发请求失败健康检查”），由后台周期探测负责恢复。

## 6. 生命周期 / 状态机并轨

### 6.1 目标

非对话域与对话域共用同一套账户状态机：

```text
pending_test -> active -> temporary_unavailable / rate_limited / error
     ^                                  |
     └──────── 后台探测恢复 ────────────┘
```

### 6.2 改造点

1. **移除 `SkipsConversationHealthStateMachine` 的域特判**，改为按账户实际可探测能力判定：账户有任一 probe-capable mode → 进入状态机；只有 `realtime_session` 或没有任何安全探测端点 → 保持 active-only/手动模式，并在 UI 明确“不支持自动探测”。不能因为域是 audio 就把 audio_speech 账户一起跳过。
2. **创建状态**：API Key 创建的非对话账户不再强制归一为 `active`；与对话 API Key 账户一致，默认 `pending_test`，首次激活探测通过后转 `active`。如用户显式选 `active`，按既有 `SkipInitialHealthCheck` 语义直接可调度。OAuth 创建沿用对话 OAuth 的既有语义（当前为 `active` + 跳过首检），不为媒体域单独造差异。
3. **编辑状态**：允许 `pending_test`；不再出现“选了待检查但没有探针复检”的滞留。
4. **后台自动探测开关**：移除“媒体域不适用”的 400 拒绝；音视频与对话/图像一样可开关。关闭后按既有手动模式二态收敛。
5. **冷却/错误恢复**：媒体探测成功按既有规则恢复；失败按阈值进入冷却/异常。`video_create` 的媒体准入臂（冷却到期仍可选中）保留并复核。
6. **锁死**：
   - 锁死是“尽可能把请求留在这个账户上”的切号否决门，不是优先级、不是会话亲和；目标是消耗该账户的额度/余额（典型：低价、限时、不稳定但不想换号的账户）。
   - 复用共享锁死状态机，跨协议/模型/lane 生效；媒体与工具端点同样适用。
   - 只要未达到死期且未触发硬不可用，禁止切到其他账号/分组；同账号重试、Key 轮换、电路、代理、并发硬门照常。
   - 死亡窗口由真实业务流量失败驱动；探针成功只恢复可用性，不自动解锁（与对话域一致）。
   - **D12 已裁决**：`rate_limited` / `temporary_unavailable` 在锁死窗口内继续 hold，不再释放切换；`disabled` / 过期 / 模型不支持 / 凭据无效等确定性硬门仍释放。该变更影响所有域，需同步修改锁死设计文档。
7. **特供**：探针就绪后启用；特供只影响冷却复测节奏，不改变调度排序。
8. **状态展示**：媒体域列表展示与对话域一致的状态、原因、最近检查、下次检查。

### 6.3 迁移与首跑

- 现网非对话场景账户大多为 `active`、`background_probe_enabled=1`；启用后会在一个间隔内进入首次周期探测。
- 上线前先做一次**只读/人工连通性审计**（dev + 生产抽样），确认现有非对话场景账户的 Base URL/Key 能通过新探测；避免上线后批量转异常。
- 若探测失败，按既有失败阈值处理，不立即停用；保留人工恢复入口。

### 6.4 锁死语义澄清（2026-11-12 用户纠正）

**锁死的目的不是缓存/会话连续性，而是“把这个账户的额度尽可能用掉”。** 典型场景：低价/白嫖/限时账户（例如 100 元必须一天用完），账户本身不稳定；普通调度遇到失败就切号，导致额度用不完。锁死就是尽可能把请求困在这个账户上，只要它没有被判定彻底死亡，就不切到其他账户。

> 额度消耗场景建议把死亡窗口调大（可配 30–3600s，默认 300s）；默认 5 分钟可能短于上游限流恢复时间。UI 应在锁死配置旁提示“限时额度账户可适当调大死期”。

现行契约（《AI 账户锁死调度机制设计与实现前复审》§1/§2/§4/§10）已经是这个方向：

| 维度 | 现行行为 |
| --- | --- |
| 作用点 | 切号决策处的否决门，不是更高优先级；不改候选排序 |
| 作用范围 | 跨协议、模型、lane；媒体与工具端点同样适用 |
| 普通失败 | 不切换；同账号重试、Key 轮换、电路、代理、并发硬门照常 |
| 慢首字 / `speed_first` | 不执行跨账号切换；首字计时和 270s 墙钟仍生效 |
| 分组回退 | 锁死窗口内禁止切组；死期/硬死后恢复 |
| 响应检查 `retry_next_account` | 锁死窗口内不执行换号 |
| 释放条件 | 死期到达（`DEAD_CONFIRMED`）、硬不可用（`rate_limited`、`temporary_unavailable` 等）、`unlock` |
| 探针成功 | 只恢复可用性，不自动解锁（锁状态保留） |

**D12 裁决（2026-11-12，选 A）**：现行契约把 `rate_limited` / `temporary_unavailable` 当作硬不可用并释放切换；这与“白嫖账户被限流但过一会儿还能用”的场景冲突。裁决改为：

- 锁死窗口内继续 hold 通过 `rate_limited` / `temporary_unavailable`，直到死期判死、请求墙钟交接或 `unlock`；
- `disabled` / 过期 / 模型不支持 / 凭据无效 / **余额或额度耗尽**等确定性硬门仍释放；额度耗尽不能靠 hold 恢复，必须切走或人工充值；
- 请求仍受 270s 墙钟与非终态客户端交接约束，不会无限等；客户端重试后继续读取同一锁死运行态；
- 同步修改锁死设计文档 §4/§10、状态机测试与客户端交接文案；影响所有域，不只是媒体。

**B 方案（维持现状）不采用**：它会让限时/低价额度在不稳定账户上被过早切走，违背锁死的目的。

## 7. 测试入口简化

### 7.1 目标

### 7.2 接口契约


- 存量非对话场景账户一次性审计与回填：`health_check_endpoint_mode` 不在可探测集 → 按连接派生代表 mode（如 qwen 长音频 → `audio_job_get`）；`health_check_model` 为空 → 取首个支持模型；`background_probe_enabled=0` 保持手动模式不强制翻转，但 `pending_test` 按手动模式二态收敛为 `active`，`temporary_unavailable`/`rate_limited` 按手动模式规则转 `error`，不静默探测；无可探测连接的账户标记 `probe_unsupported` 并保留人工测试；
- 多连接账户（如 volcengine ark + openspeech）按 `health_check_connection_id` 选探测连接；该连接无安全探测时回退到同账户其他 enabled 连接，仍无则标记不支持；
- OAuth 媒体账户（gemini native）使用与真实请求同源的 OAuth 认证构造；上游媒体端点不接受该 OAuth 形态时标记不支持，不硬造；
- 代理池账户的探测与真实请求同源解析代理成员，不直连；

**验收**：非对话场景账户可 `pending_test → active`；失败进入冷却/异常并可恢复；后台开关生效；对话/图像既有行为无回归。

### B5 锁死 / 特供 / 批量编辑（3–5 天）

- **D12 实现落点（复审 blocker B3）**：现行 transient 释放不在锁死门——显式/系统错误策略 cooldown 写状态后 `explicitPolicyFailure=true` 跳过锁死门，账户转 non-active 后被候选 `statusSet='active'` 排除。B5 必须先补错误策略“确定性/transient”分类轴，并裁决锁定账户 non-active 期间的候选准入（冷却 fence 保持 active，或加锁死 ENGAGED 准入臂）；额度耗尽按 `RuleID=system.upstream_insufficient_quota` / `last_error_code=system_quota_*` 释放，不能按账户状态值判断；J1 探活失败也不得提前终结锁死 hold；

- 批量编辑按场景字段清单开放（D5）；
- 列表/菜单/编辑入口一致性收尾。

**验收**：锁死/特供在非对话场景有明确行为；批量编辑字段不越场景。

### B7 向量 / 重排 / 安全模型：独立场景类型（10–15 天）

> 2026-11-12 用户最终裁决：不塞进对话域，拆分出去单独 AI 账户；原因是 Base URL/端点不同，混在一起请求寻址不清。B7 依赖 B1 的场景注册表与单菜单。

**B7.1 场景类型与账户模型**

- 场景注册表新增 `embedding` / `rerank` / `moderation`；每个账户只属于一个场景类型；
- 各 provider 词表与 `connector_registry` 的 `Domains` / mode 集按官方能力增加 `embed_content` / `rerank_json` / `moderation_json`；
- `capability_domain` 值域扩展（不再固定四值 CHECK，见 §3.5）；现有四值不变；
- 每个场景独立 Base URL/凭据/支持模型；不与 chat 账户混用；
- `health_check_endpoint_mode` 默认 = 该场景的代表 mode；`health_check_model` 从该场景支持模型中选择；
- 创建后 `pending_test`，工具端点探针通过转 `active`。

**B7.2 请求 lane 与调度**

- 新增 `LaneEmbedding` / `LaneRerank` / `LaneModeration`（或统一 `LaneUtility` + endpoint family 子类型）；修正 `/v1/embeddings` 的 endpoint family/上游路径（当前只有协议路径放行，没有专用族，容易被当 chat_completions 处理）；
- 注册 `/moderations`、`/rerank` 路由（当前 `/moderations` 只在响应校验词表出现、未在网关根注册；`/rerank` 完全不存在）；`/embeddings` 已有路由但需专用 lane/family 与 stateless 策略；
- `requestMappingSourceFamilyOf` 增加 `embedding` / `rerank` / `moderation` 族或明确返回“无映射”；不得让工具请求落到 `chat_completions` 族而误命中对话映射；
- `DispatchDomainOfLane` 将三者映射到 `StatelessDispatch`；
- 将 `StatelessMediaDispatch` 重命名为 `StatelessDispatch`（值 `stateless`），同步文档/测试/审计口径；无外部持久化契约；
- 候选过滤按请求 mode（`embed_content`/`rerank_json`/`moderation_json`）匹配账户 `supported_endpoint_modes`；
- 不产生会话亲和/组亲和/Key 亲和；不进入热质量/缓存率/速度优先/流式重试/恢复等待；
- API Key 安全策略/出站脱敏覆盖工具端点的文本输入（embedding input、rerank query/documents、moderation input），响应侧还原只对生成式文本响应生效（工具响应无占位符）。

**B7.3 协议、目录与计费**

- 对外契约先定：向量用 OpenAI `/v1/embeddings` 形态；安全模型用 OpenAI `/v1/moderations` 形态；重排没有 OpenAI 标准，推荐采用 Cohere/Jina 兼容的 `POST /v1/rerank`（`query` / `documents` / `top_n` / `return_documents` → `results[{index,relevance_score,document?}]`），厂商 adapter 归一到该形态。契约未定前不实施重排。
- 内置目录新增 embedding/rerank/moderation 行；“安全模型”按 `/v1/moderations` 形态接入；如果是对话式安全模型，按普通 chat 场景处理，不新增 mode。首批覆盖有官方 API 的厂商：
  - OpenAI：embeddings、moderations（OpenAI 无 rerank）；
  - Qwen/DashScope：embeddings、rerank；
  - Gemini：embeddings；
  - GLM/DeepSeek：按官方文档回填，未确认的不开放；
  - Anthropic/xAI：无官方 embedding/rerank/moderation 能力，明确不支持；
- 每个端点一个 adapter（路径、鉴权、请求/响应、usage/计费口径）；没有官方接口的厂商不硬造；
- 账户类型门：API Key 与 OAuth 按供应商官方能力分别验证；OAuth 不支持的组合不加入词表，写侧拒绝，不做“先放开再修”；
- 计费口径必须按厂商官方单位：embedding 按输入 token、rerank 按搜索单元/请求、moderation 按输入 token 或免费；不足的 usage 字段在 B7.3 补齐，不静默套用对话 input/output token 口径；
- 自定义模型：扩展四值 UI 分类与目录词表的映射，覆盖 `embedding/rerank/moderation`；新增值双表同步并补测试。不做无关的全量词表统一（BUG-0324 的既有映射继续保留），但自定义工具模型必须可用，不留半套。

**B7.4 探针与生命周期**

- 工具端点接入 §5 的连通性探测注册表（空/非法输入 → 400/422 = Key 有效）；
- J1 候选 SQL 的 endpoint mode 白名单增加 `embed_content` / `rerank_json` / `moderation_json`（当前不含 `embed_content`）；工具账户进入周期/激活/冷却恢复；
- 状态机、锁死、特供与 B4/B5 一致；
- 工具请求失败不触发对话流式重试；错误策略按共享失败处理链执行。

**B7.5 前端与文档**

- 单菜单「AI 账户」的场景筛选增加向量/重排/安全；创建流程可选这些场景；
- 各场景独立支持模型选择器；不与对话模型混选；

- 文档新增「向量/重排/安全场景」章节，更新模型目录、接口契约、能力域说明。

**B7 验收**：三个场景可独立创建账户；`/v1/embeddings`、`/v1/rerank`、`/v1/moderations` 走 Stateless 调度；账户可 `pending_test → active`；对话/媒体场景既有行为零回归；无安全端点的厂商明确不支持。

## 13. 风险与注意事项

1. **上游探测语义差异**：不同厂商对空 prompt/不存在任务的状态码不同；必须以真实探针回填为准，不能按状态码字面值猜测。
2. **误伤存量账户**：开启后台探测后，配置错误的媒体账户会转异常；上线前必须做连通性审计，并保留人工恢复入口。
3. **探测成本**：虽然无副作用，但仍是上游请求；沿用 J1 并发上限与频率，不做“每模型探测”。
4. **锁死语义**：锁死的目标是额度消耗（把请求尽可能留在指定账户上），不是缓存/会话；但现行契约在 `rate_limited` / `temporary_unavailable` 会释放切换，可能与“尽量不切号”冲突；D12 需裁决是否扩展到这些状态。
5. **批量编辑**：开放后必须按域字段清单校验，防止把对话专属字段写进媒体账户。
6. **移除特判的回归面**：`SkipsConversationHealthStateMachine` 被创建/PATCH/异常恢复/后台开关多处消费；必须逐点替换并补测试。
7. **无功能开关**：本期不引入“媒体探针开关”；回滚靠二进制版本与人工恢复。
8. **未来能力**：新增场景类型时，必须复用 `ScenarioProfile` 与对应调度策略（Conversation/Stateless/Realtime），不得复制媒体特判，也不新增菜单。

## 15. 验收标准

### 15.1 人工测试与入口收敛

- [x] 前后端能力矩阵来自同一来源，xai/qwen image 可创建；

- [x] 媒体表单/列表/操作菜单无域内无效项；
- [x] 时间计划/优先级/批量编辑在非对话域可见可改；
- [x] 创建后状态为 `pending_test`，后台探针通过后 `active`（D6）；
- [ ] 对话域行为零回归。

### 15.2 内核并轨

- [x] 非对话域具备 `pending_test → active → 冷却/异常 → 恢复` 状态闭环；
- [x] 后台自动探测、激活检查、冷却恢复对非对话域生效；
- [x] 锁死/特供在非对话域有明确行为；
- [x] D12：锁死窗口内 `rate_limited` / `temporary_unavailable` 继续 hold 到死期/墙钟/unlock；disabled/过期/模型不支持/凭据无效/余额耗尽等确定性硬门仍释放；
- [x] 每个可探测连接 preset 均有“无副作用”验证，且没有 POST 创建式探测；
- [x] 不具备安全探测端点的供应商明确显示“不支持自动探测”，不伪造成功。

### 15.3 单菜单与场景类型（B1）

- [x] AI 账户区域只有一个一级「AI 账户」菜单，不再有四个二级域菜单；旧四域路由删除，不做 redirect；
- [x] 创建账户第一步可选场景类型，选项来自供应商能力矩阵；
- [x] 列表可按场景类型筛选，列展示场景类型；
- [x] 一个账户只属于一个场景类型，创建后不可改；
- [x] 现有 chat/video/audio/image 账户全部可见可建，行为不变。

### 15.4 向量/重排/安全独立场景（B7）

- [ ] embedding/rerank/moderation 可独立创建账户，独立 Base URL/凭据/模型；
- [ ] `/v1/embeddings`、`/v1/rerank`、`/v1/moderations` 走 Stateless 调度，不产生会话亲和；
- [ ] 账户可 `pending_test → active`；
- [ ] 没有官方端点的厂商明确不支持，不硬造；
- [ ] 对话/媒体场景既有行为零回归。

### 15.5 Realtime 场景与 WS 探针（B8）

- [ ] GPT 音频账户不再自动含 `realtime_session`；音频与实时是独立场景账户；
- [ ] Realtime 首批只开放 gpt；账户可独立创建、WS 握手探测、`pending_test → active`；
- [ ] 探针不发送音频/文本，无 token 计费；
- [ ] Gemini Live 等未实现协议桥的 vendor 明确不开放并说明 M6 依赖；其他无法安全握手的 vendor 显示原因；
- [ ] D13 cutover 后旧非对话账户已删除、Realtime 账户按新场景重建；不保留旧非对话账户迁移路径。

### 15.6 通用
