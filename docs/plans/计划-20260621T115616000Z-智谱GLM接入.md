## 需求目标

- 背景：项目当前已有 OpenAI / GPT / Anthropic 供应商闭环，用户需要新增国产智谱 GLM，并在创建账户时像 GPT 一样区分不同接入类型。
- 目标：接入 `glm` 供应商，支持“通用 GLM API Key”和“GLM Coding Plan Key”两种账户创建入口；真实上游按官方可核验的 OpenAI Chat Completions 兼容协议落地，GLM Coding 账号只有在客户端兼容显式选择 Codex Responses 时，才通过本地通用 bridge 承接 Codex Responses 客户端。
- 交付物：供应商和协议档案种子、前后端账户创建 / 编辑 / 导入 / 测试、网关调度、模型目录、价格和 usage 统计、错误处理、恢复探活、Mock AI 回归脚本、真实烟测脚本和文档更新。

## 方案概述

- 方案原则：把“OpenAI-compatible 协议”作为协议层复用，把“智谱 GLM”作为独立供应商处理；不把 GLM 混进 GPT 账号池、GPT 价格、GPT OAuth 或 Codex Responses 策略。
- 数据变化：新增 `glm` 供应商、两套 `provider_protocol_profiles`、profile family、默认分组、GLM 模型目录和价格项；同时移除或替换 `provider_protocol_profiles(provider_code, protocol_code, protocol_version)` 这类会阻止同供应商同协议多档案的唯一约束。如果当前 schema 已支持这些字段，不新增兼容迁移分支，直接按当前 schema 写入种子和读写逻辑。
- 接口变化：账户创建 / 编辑 / 导入 / 导出 / 外部推送显式提交 `providerProtocolProfileId`；管理接口返回 GLM provider / profile / 默认能力；网关 endpoint mode 校验新增 GLM Chat-only 默认值。
- 前端变化：账户页选择 `智谱 GLM` 后展示两个接入类型，中文提示通用 Key 与 Coding Plan Key 不通用；模型选择、账号测试、日志筛选和导入示例同步补 GLM 文案。
- 后端变化：新增 GLM provider 常量、profile 常量、seed defaults、endpoint mode 默认值、模型目录加载、价格查找、账号测试默认模型、错误策略示例和回归脚本。
- 网关变化：GLM 使用 OpenAI v1 Chat Completions adapter，但供应商层保留 GLM 请求兼容、响应检查、错误策略和 usage 解析差异；Codex Responses 到 Chat Completions 的协议转换抽到 provider shared adapter，GLM Coding 只是第一批启用者，后续 DeepSeek 等供应商复用同一层。
- 数据处理策略：不做旧数据兼容；需要本地数据库同步时，由维护者按当前 schema 重新初始化或单独执行离线同步，不在运行路径挂迁移逻辑。

## 风险与注意事项

- 官方协议风险：智谱文档存在多种入口和较宽泛的 OpenAI 兼容表述；当前第一版真实上游只启用 OpenAI Chat Completions，Codex Responses 通过本地 bridge 转换，后续新增原生 Responses 或 Anthropic Messages 必须重新调研和实测。
- Bridge 限制风险：当前 Codex bridge 只覆盖流式 `/v1/responses` 主路径、function tools 和文本输出，不覆盖 namespace tools、web_search、custom tool、image generation、`/responses/compact` 或非流式 Responses。
- Schema 风险：`provider_protocol_profiles` 唯一约束已调整；已有本地数据库需要维护者按当前 schema 单独同步，不在运行时代码做兼容迁移。
- URL 风险：mock 已验证智谱官方 `/api/*/v4` Base URL 不追加 `/v1`；真实 vsllm.com 测试使用 `/v1` Base URL，因为该上游以 OpenAI-compatible 代理形式暴露。
- Key 混用风险：通用 GLM API Key 与 Coding Plan Key 不应互相假设可用；表单、导入和测试失败提示必须让用户能识别接入类型错误。
- 路由风险：`glm-5.2` 这类同名模型可能同时存在于通用和 Coding 档案；模型路由和统计展示要么使用 profile 维度，要么第一版明确由分组 / API Key 边界决定，不允许跨 profile 混绑。
- 套餐规则风险：Coding Plan 面向开发工具场景，本地中转对外开放前需要确认使用边界，不能把 Coding 号池当普通业务 API 池。
- 统计风险：Coding Plan 的本地成本估算不等同官方套餐余额；页面展示必须避免把估算成本解释为官方剩余额度。
- 恢复探测风险：健康检测和冷却复测会消耗 GLM / Coding 额度，必须使用最小请求、低输出上限和节流策略。
- 兼容风险：GLM 的 Chat 扩展字段、role 支持、`response_format`、`thinking` 和 `finish_reason` 差异只能落在 GLM 供应商层，不能污染全局 OpenAI v1 行为。
- 发布异常处理：如果上线后 GLM 转发异常，先停用 GLM 默认分组或相关账户，保留供应商种子和文档；不影响现有 OpenAI / GPT / Anthropic 账号池。
