**目标：** 在保留正常内置协议兼容、请求重试、速度优先、多 Key 隔离、周期健康保护和用户定制配置的前提下，修复已经证明会导致非成功结果清状态、默认状态不推进或依赖具体错误内容作隐式状态判断的问题。

## 需求目标

### 背景

当前真实网关请求失败后，AI 账户通常经过以下默认路径：

```text
请求级同账户确认重试
→ 重试耗尽后短暂避让
→ 后台恢复探针
→ 观察窗口与事前确认
→ 并发归零
→ temporary_unavailable
→ 交由冷却复测恢复
```

用户观察到长期上游超时仍可能反复停留在短暂避让，因此需要先证明这条完整路径是否存在断点，而不是看到某个条件分支就直接删除。

只读检查已经确认一个明确问题：

```ts
result.success || result.accountFailureEligible === false
```

运行态恢复和事前确认的部分路径使用这个条件清除状态。它会把“探针没有成功，但被分类为不计账户失败”当成恢复成功。非成功结果可以因为作用域不同而不升级账户，但不能被伪造成成功并清除已有故障状态。

同时，检查还发现多项容易被误判为缺陷、实际承担正常功能的机制。本计划必须先保护这些行为：

- 同账户确认重试用于吸收瞬时故障，重试预算耗尽后才进入账户运行态副作用。
- 探针外层异常退避用于处理任务、存储或构造故障，不能把所有异常直接归罪于账户。
- 周期健康检查不让检查模型或请求配置问题直接停用整个账户。
- OpenAI / Anthropic / Gemini 的默认 error 对象和失败事件识别用于防止 HTTP 200 内协议失败被记成成功。
- Codex `response.incomplete`、Remote Compaction 契约和 turn 级避让属于客户端兼容能力。
- 大响应与超大 SSE 事件跳过深度检查是有界内存和原样转发能力。
- 普通路由速度优先的首字 cutover 是延迟策略，不等同于上游账户故障。
- 多 Key 账户通过子 Key 派生有效可用性，设计上不要求每次 Key 变化都覆盖父账户物理状态。
- OAuth 并发刷新恢复用于避免多个请求同时刷新时误判账户失效。

因此，本计划采用“行为刻画 → 问题复现 → 最小修复 → 原功能回归”的顺序。

### 用户确认的配置边界

以下属于用户或管理员主动选择的定制行为，不纳入本次治理：

- AI 账户错误处理配置。
- AI 账户响应检查配置。
- 全局响应检查、错误处理和系统策略配置。
- 用户显式保存并启用的匹配条件、状态动作、重试动作和响应动作。

这些配置可以按自身契约消费错误码、错误类型、错误文案、供应商或客户端范围。本计划不删除相关字段、API、页面、数据表或运行能力。

### 目标

- 复现并解释“长期超时为何持续短暂避让”的真实链路。
- 只有真实成功证据才能清除已有运行态故障。
- 非成功但不应归责账户的结果保持为对应作用域错误，不升级账户，也不清状态。
- 上游失败、探针任务失败、配置问题、策略 cutover、客户端取消和旧任务失效使用结构事实区分，不使用具体错误码或文案。
- 保留请求级同账户确认重试、观察窗口、并发归零和 generation 防护。
- 保留协议错误识别、客户端兼容、大响应透传、速度优先和多 Key 派生可用性。
- 对 OAuth 的并发刷新恢复做等价结构化表达，不降低现有成功率。
- 所有修改都有“原正常功能保持不变”的回归证据。

## 判断原则

### 1. 先判断功能目的

任何准备修改的分支必须先回答：

1. 它保护的正常场景是什么。
2. 哪个现有文档或回归测试承诺了这个行为。
3. 它是否真的导致错误清状态、漏推进或错误归因。
4. 能否只替换控制依据而保持外部行为不变。

不能回答第 2、3 项时，只记录审计结论，不进入实现。

### 2. 使用正交结构事实

默认控制不强迫所有情况进入单一成功 / 失败枚举，而是记录相互独立的事实：

| 事实 | 允许值 | 用途 |
| --- | --- | --- |
| 上游执行阶段 | `not_started / started / completed` | 判断错误是否能归责具体账户 |
| 传输结果 | `completed / failed / policy_cutover / client_cancelled` | 区分真实失败和正常生命周期终止 |
| 协议结果 | `success / failure / valid_terminal / uninspected` | 表达协议成功、失败、合法非成功终态或检查省略 |
| 状态作用域 | `account / account_key / probe_task / gateway_dependency / none` | 决定更新哪个状态，不依赖错误内容 |
| 任务代次 | 当前 / 过期 | 防止旧结果覆盖新配置或新状态 |

错误状态码、错误码、类型、文案、供应商私有字段和 trace 信息继续进入诊断，但不替代上述事实。

### 3. 几个关键边界

- `response.incomplete` 可以是合法协议终态；Codex 是否重试属于已存在的客户端兼容策略，不能扩散给所有客户端。
- 大响应或 parser skipped 表示“检查省略”，不是天然失败；必须保留有界内存和原样转发。
- 探针本地配置 / 构造 / 存储失败仍然是错误，但作用域是 `probe_task`，不能当账户成功，也不能无证据升级账户。
- 真实上游请求已经发出后的连接失败、超时、截断或协议失败属于账户或 Key 作用域，不再按具体错误内容过滤。
- 同账户确认重试可以延后账户状态副作用，但每次 attempt 仍必须有审计和使用记录；预算耗尽后的最终失败必须进入统一运行态。
- 速度优先主动 cutover 属于 `policy_cutover`，保留 `latency_degraded` 逻辑，不进入账户故障状态。

## 已确认问题

### 1. 恢复探针非成功结果清状态

位置：

- `backend/src/modules/gateway/runtime/account-side-effects.service.ts`

当前多处条件：

```ts
result.success || result.accountFailureEligible === false
```

必须改成：

- 真实成功：允许按 generation 清状态。
- 上游探针失败：进入现有失败推进。
- 探针任务 / 配置错误：保留当前故障状态，安排任务重试并记录诊断；不清状态，也不累计账户失败。
- 旧 generation：丢弃结果，不修改当前状态。

这里不直接删除 `accountFailureEligible` 在人工诊断和周期健康配置保护中的用途。

### 2. OAuth 并发恢复依赖错误文案

位置：

- `backend/src/modules/openai-oauth/openai-oauth-access-token-refresh.service.ts`

`refresh_token_reused`、`invalid_grant` 文案目前用于识别“其他任务已经刷新成功”的竞争场景。竞争恢复功能必须保留，但触发条件改为：

1. 失败后重读最新凭据。
2. access token 或凭据版本已经前进且仍可用，接受最新结果。
3. refresh token generation 已变化，在统一预算内做 CAS 重试。
4. 版本没有变化且凭据不可用，按现有失败退避。

### 3. 完全缓冲 JSON 解析失败被当成“未命中检查”

位置：

- `backend/src/modules/gateway/response/non-stream-json-inspection.ts`
- `backend/src/modules/gateway/response/finalization.ts`

当响应已经声明并进入 JSON 处理、响应体也已经完整缓冲时，`JSON.parse` 失败当前会直接返回“没有检查结果”，后续仍可能只按 HTTP 2xx 记成功。

该场景与大响应检查省略不同：完整缓冲 JSON 已经有条件确认协议体无法解析，因此应作为协议失败处理，并在下游尚未提交时沿用现有重试 / 统一错误能力。不能因此删除普通 JSON 透传，也不能影响大响应有界转发。

### 4. 账户冷却复测把任务异常推进为账户长期失败

位置：

- `backend/src/modules/background/cooldown-account-retest.service.ts`

当前执行异常被转换成 `success = false + accountFailureEligible = false` 后，仍然调用 `record_cooldown_account_retest_failure`。DB service、IPC、探针构造或其他任务错误因此可能增加账户复测失败次数、延长观察窗口，最终把账户推进到 `error`。

修复边界：

- 明确上游账户复测失败：继续推进既有快速 / 慢速恢复状态机。
- 探针任务、DB service、IPC 或本地构造异常：让任务失败并按队列 / 下一周期重试，不修改账户恢复观察期。
- 不删除冷却复测、指数退避、长期复测和 PLAN-0114 的有界恢复能力。

### 5. Key 冷却复测缺少失败归属门槛

位置：

- `backend/src/modules/background/account-api-key-cooldown-retest.service.ts`

当前所有 `result.success = false` 都会调用 `record_account_api_key_failure`。配置、构造或系统故障可能被写成目标 Key 失败。

修复边界：只有明确已经进入目标 Key 上游执行并失败，才更新该 Key 运行态；任务或系统错误交给 worker 重试，不污染 Key 状态。

## 待复现疑点

以下不是已确认改造项，只有回归复现失败后才修改：

### 1. 长期超时是否真的不能升级

需要覆盖：

- 请求级确认重试开启和关闭。
- 非流式长超时、流式首包超时、首包后截断。
- standalone 与 Redis。
- 自有账户与授权实例。
- 观察窗口、事前确认、并发归零和最终 `temporary_unavailable`。

如果现有链路已经按设计推进，只补观测或文档，不改状态机。

### 2. 大响应和 parser skipped 是否错误恢复账户

必须同时保护：

- 合法大响应继续成功透传。
- 图片、base64、未知二进制和超大事件不做无界缓存。
- 检查省略不会自动伪造协议失败。

只有当“已存在故障状态被一个没有成功证据的省略检查结果清除”可以稳定复现时，才限制其作为恢复信号；不能把所有大响应改成失败。

### 3. 同账户确认重试是否吞掉最终失败

现有提前 return 属于正常确认预算。需要验证的是：

- 每次 attempt 有失败审计。
- 预算耗尽后只产生一次账户运行态失败副作用。
- 不会因为多次确认无限延后短暂避让。

### 4. 多 Key 全部不可用是否仍被派发

现有设计明确使用 Key 池派生有效可用性，不要求父账户写 `temporary_unavailable`。需要验证：

- 至少一个 Key 可用时账户正常承接。
- 全部 Key 冷却或异常时账户退出候选。
- Key 恢复成功后账户自然重新可承接。
- 新供应商只有显式声明 Key 池能力时才进入该状态机。

如果派生可用性已经正确，本计划不修改父账户状态。

### 5. `last_error_code` 是否存在无替代控制

- 账户到期优先使用正式到期时间和状态。
- OAuth 刷新异常恢复优先使用任务所有权、凭据版本和正式状态。
- tooltip、日志和审计继续使用错误码。

只有已存在正式事实可以无损替代时，才移除控制读取；不为追求形式统一破坏异常恢复。

## 方案比较

### 方案 A：行为刻画后最小修复（推荐）

- 先锁定正常内置功能。
- 复现长期超时和每个待确认疑点。
- 只修已经证明的状态错误。
- 控制依据需要调整时保持外部行为等价。

优点：直接解决真实问题，最大限度避免误删兼容、抗抖和资源保护能力。

结论：采用。

### 方案 B：删除所有具体分支

问题：会误删协议失败识别、Codex / Gemini 客户端兼容、速度优先、周期健康配置保护和 OAuth 并发恢复。

结论：不采用。

### 方案 C：只改四处成功条件

问题：虽然能修明确的错误清状态，但不能证明长期超时全链已经闭环，也无法防止 standalone / Redis 语义分叉。

结论：不单独采用；作为复现后的最小实现步骤。

## 风险与注意事项

- 最大风险不是改少，而是把正常兼容或保护机制误判成特判后删除。
- 大响应、图片、base64 和未知二进制不能为了“完整解析”重新引入无界缓冲。
- 周期健康检查和运行态恢复探针职责不同，不能因为共用测试执行器就强行使用同一种状态动作。
- 同账户确认重试期间不写账户运行态是设计行为；必须区分审计失败记录和账户状态副作用。
- 多 Key 账户整体不可承接可以由 effective availability 派生，不等于必须写父账户 `temporary_unavailable`。
- 速度优先主动放弃慢请求不是上游失败；但真实超时不能伪装成策略 cutover。
- OAuth 文案判断替换必须先有凭据版本事实，不能删除后降低并发恢复成功率。
- `oauth_token_refresh_failed` 当前承担错误状态所有权；没有等价正式字段前不得直接删除，否则 OAuth 成功可能误恢复其他异常。
- 当前工作区存在其他未完成修改；实施阶段只修改复现证明需要调整的文件。
- 不修改 schema，除非 OAuth 任务所有权确实没有可复用正式字段；若需要新字段必须重新提交用户审核。
