## 需求目标

- 背景：项目单机能力已经基本闭合，后续需要支持多节点分布式部署，让不同登录用户的数据固定落在不同节点，并通过节点选主、路由表和内部转发支撑多节点入口。
- 目标：设计并分阶段落地“无副本用户分片 + 安全选主 + 自动路由”的第一版分布式能力，保持现有轻量边界，不把首期实现扩成完整分布式数据库。
- 交付物：长期功能设计、架构总览同步、配置和存储草案、选主与路由实现、集群状态页面、验证记录和后续副本 / 迁移计划。

### 本次不包含

- 自动数据副本和自动故障接管：第一阶段不做；必须等复制日志、追平水位和旧主 fencing 设计完成后再实现。
- 自动用户迁移和重平衡：第一阶段只预留手动迁移状态和约束，不在运行路径做双写或自动搬迁。
- 跨节点统一授权：第一阶段只允许同一 home node 内授权，跨节点授权后续单独设计资源代理或授权实例复制。
- 引入 Redis、Kafka、PostgreSQL、ClickHouse 或外部分布式队列：首期继续保持轻量本地 SQLite 和节点内 worker 模型。
- 全局明细实时聚合：所有集群级统计只能读取节点预聚合摘要，不在请求链路扫描所有节点明细。
- 在线无感从单机拆分多节点：旧单机数据首期按当前节点作为 home node，再通过后续手动迁移分散。

## 方案概述

- 方案原则：默认单机不变，显式开启分布式后进入控制面选主和用户 home node 路由；leader 只管理元数据，不代理全部流量。
- 数据变化：新增 `cluster_nodes`、`cluster_terms`、`cluster_metadata_logs`、`cluster_system_account_routes`、`cluster_api_key_routes` 和 `cluster_node_summaries` 等控制面表。
- 接口变化：新增节点内部 `/__aisys__/cluster/internal/*` 接口；管理侧新增集群状态、用户路由和 API Key 路由诊断接口。
- 前端变化：新增“集群状态”管理页，展示 leader、term、节点健康、用户分布、路由版本和风险提示。
- 后端变化：新增节点配置、选主服务、metadata log、路由表、内部转发、worker lease 和集群摘要刷新。
- 数据处理策略：不在运行路径保留旧单机和新分布式双模型兼容。旧单机数据进入分布式时，先统一归属当前节点；后续用户迁移用单独离线 / 维护流程处理。

## 风险与注意事项

- 风险 1：2 节点自动选主容易脑裂。规避方式是生产默认要求 3 个投票成员，或 2 数据节点 + witness。
- 风险 2：leader 如果承载全部业务流量会成为瓶颈。规避方式是 leader 只做控制平面，业务请求按 home node 处理。
- 风险 3：无副本模式下 home node 故障会让对应用户不可用。规避方式是页面、错误码和运维文档明确该语义，副本接管后续单独设计。
- 风险 4：跨节点授权会破坏首期分片闭环。规避方式是第一阶段明确禁用，后续专项设计资源代理或授权实例复制。
- 风险 5：全局统计如果回扫所有节点明细会放大请求链路。规避方式是节点 worker 预聚合，leader 只合并摘要。
- 发布异常处理：分布式功能必须可通过配置关闭回到单机模式。已经写入分布式元数据的环境若需要回退，先停机并按当前 schema 做离线确认，不在运行路径保留双模型兼容。
