## 需求目标

- 背景：现有模型检测（J3b）全部是系统内置的确定性探针，用户无法用自己的题目验证"某个账户的模型是否被降智或替换"。需要新增一个用户自定义题库测试阶段：用户提交题目与答案，管理员审核后进入全局共享题库；检测时最多选 3 题，模型作答后与参考答案比对，答错按 31 分池扣分，从而判断该账户模型是否降智或异常。
- 目标：
  1. 全局共享的检测题库：任何用户可提交题目（标题 + 题目内容 + 判定依据），管理员审核（通过/驳回）与删除；仅"已通过"题目可被检测配置选用。
  2. 提交时自动查重：标题不得重复，题目内容与现有题目相似度过高时拒绝（需要实现相似度算法）。
  3. 检测配置（手动检测质量配置、定时检查）支持选择最多 3 道已通过题目，选择控件单输入框、选中项独占一行。
  4. 检测执行新增"题库测试"环节：排在所有现有环节最后；前面基础探针未通过（terminal 失败）时不执行。每题两跳自对比——被测模型先在独立上下文作答，再在全新隔离上下文中把自己的回答与参考答案对比并输出结构化判定；每题分值从 31 分池平均分配，判定不符扣光该题分值，结果在检测详情中逐题展示。
- 交付物：maintenance schema 变更、gateway 题库域（存储 + API + 查重算法）、检测管线题库环节、前端（入口按钮、题库弹窗、题目选择器、结果展示）、测试项与验证记录、functions 文档更新。

### 1. 题库数据模型与审核流

新表 `model_check_question_bank`（juhe_business，全局共享，跨系统账户；提交来源仅作记录字段）：

```sql
CREATE TABLE IF NOT EXISTS model_check_question_bank (
  id text PRIMARY KEY,
  title text NOT NULL,                      -- ≤100 字符
  title_norm text NOT NULL,                 -- 归一化标题（查重用，普通索引）
  question_text text NOT NULL,              -- 题目内容，≤2000 字符
  reference_answer text NOT NULL,           -- 参考答案（自对比判定依据），≤4000 字符
  key_points_json text,                     -- 评分要点（可选），JSON 数组，1..10 条、每条 ≤50 字符
  status text NOT NULL DEFAULT 'pending' CHECK (status IN ('pending', 'approved', 'rejected')),
  reject_reason text,
  created_by text NOT NULL,
  created_scope text NOT NULL,              -- 提交时所在系统账户，仅记录
  reviewed_by text,
  reviewed_at text,
  created_at text NOT NULL,
  updated_at text NOT NULL
);
-- 索引：status、created_by、title_norm
```

- 审核流：提交 → `pending`；管理员通过 → `approved`；驳回 → `rejected`（+理由）；驳回后创建者可修改重新提交（回到 `pending`）。审核用状态 CAS（`UPDATE ... WHERE status='pending'`）防并发双审。
- 权限：
  - 普通用户（自助面）：提交；列表可见 approved + 自己的提交；详情中题目全文可见，**参考答案/要点仅创建者与管理员可见**（避免题库被"喂答案"导致检测失真）。
  - 管理员（管理面）：全量列表 + 状态筛选；审核、删除（硬删除，操作写 `authsys.OperationLogSink` 审计）。
  - 创建者可撤回/删除自己的 `pending`/`rejected` 题目（决策点 D6）。
  - approved 题目锁定不可编辑；管理员可将其驳回（下架）或删除，已引用它的配置在运行时过滤（见 §4）。
- 删除不回写历史：检测结果已快照题目 id + 标题（受 sanitize 500 字符上限约束），删除后历史记录仍可读标题与判定结论。

### 2. 查重与相似度算法（提交时服务端执行）

- 归一化：NFKC → 去空白与标点 → 小写。
- 标题查重：`title_norm` 与所有 `status IN ('pending','approved')` 题目精确相等 → 拒绝（409，提示"标题与现有题目重复"）。rejected/已删除题目不占用标题。
- 内容相似度：归一化后取**字符二元组（bigram）集合，Jaccard 相似度**，与所有 pending/approved 题目比对，最大值 ≥ 0.80 → 拒绝（409，提示最相似题目的标题）。长度预过滤（长度差/较长者 > 0.5 直接跳过）控制比较量；题库规模（百级）线性扫描足够，无新依赖，Go 标准库实现。阈值 0.80 与归一化规则收敛为包内单一常量/函数，配表驱动单测。

### 4. 检测管线"题库测试"环节

- 位置：`RunSuite` 在现有全部家族（含 `usage_shape`）之后追加题库家族，quick 与 full 两分支都要插入（决策点 D4）。**仅在顶层目标套件执行**：`RunSuite` 会被可信对比递归调用（`runQuickTrustedComparison` suite.go:317、`RunTrustedComparison` suite.go:704），题库家族必须加 `Prefix==""` 顶层门禁，避免对比账户也执行题库请求、污染对比证据。此前任一 terminal 失败触发的早退（核心段 suite.go:89-147、full 段 191-193/203-205/227-229/251-253、quick 分支独立 return suite.go:179）天然跳过题库环节，transport 错误走整跑失败同理；无需新门禁，但回归测试须覆盖全部早退点。
- 运行时解析：从 policy/schedule 配置读取题目 id → 查题库取 `approved` 题目；失效 id（被删/被驳回）过滤；全部失效或未配置 → 环节整体 `skipped`（`excludedFromScoring`，不进任何分母/扣分，message 说明原因）。
- 执行：每题两次探针请求（作答 + 对比，见下）；扣分拆分按"实际执行的题数"在运行时计算：单题扣分值 = floor(31/n)，余数分给前 (31 mod n) 题 → n=1: [31]；n=2: [16,15]；n=3: [11,10,10]。
- 判定方式（用户已确认，2026-09-21）：**被测模型自对比**，不用另一个模型当裁判。每题两跳：
  1. 作答请求（上下文 A）：只发题面，不发参考答案/要点；
  2. 对比请求（上下文 B，全新独立会话）：发 题面 + 该模型自己的回答文本 + 参考答案（+可选评分要点），要求严格 JSON `{"verdict":"pass"|"fail","reason":"..."}`。
  两跳互不携带消息历史（现有探针本就是单请求无会话延续，实现以 mock 断言 payload 隔离固化）。每跳独立走现有 3 次重试（10/20/30s）契约，`max_output_tokens` 提升至 1024（包内常量）。
- 结果映射：对比判定 `pass` → `passed`；`fail` 或 **HTTP 200 但判定 JSON 解析失败** → `failed`（扣光该题扣分值；解析失败 reason 记"模型未能输出有效对比判定"——连对比都做不好的账户按质量失败处理，与 structured_output 对畸形 JSON 的现有处理一致，200 后不重试）；作答/对比请求非 200 经重试 → terminal（整跑失败，沿用现有契约，不扣分）。
- 注入风险缓解：对比请求会向被测链路发送参考答案文本，存在借题面提示注入套取他人参考答案的理论风险——审核清单增加"检查题目注入特征"一条，参考答案绝不写入证据回显。
- 模型覆盖（用户已确认，2026-09-21）：题库环节对**所有供应商/协议**生效——openai_responses / openai_chat / anthropic / gemini native 均经现有协议适配器发出（`probe.go:102-136`），两跳只是普通文本请求。判定 JSON 仅靠提示约定 + 确定性解析，**不依赖各协议的 JSON mode / 结构化输出能力**，避免能力差异造成判分不公。现行"通用测试为主、个别模型单独设计"分层不受影响：通用族（行为指纹/长上下文/稳定性/结构化/工具/交叉对照等）全模型执行；token_integrity/identity_observation 按 token 身份能力门控（suite.go:230-256）；Juice 仅对 full + openai_responses + gpt-5.6-sol/terra/luna 生效（`juice.go:24-26`），不满足条件一律 `skipped` + `excludedFromScoring` 不计分（suite.go:274-276）。
- 计分（决策点 D2，推荐扣分模型）：题库项**不进现有分母**，在 `SummarizeChecks` 现有归一化得分基础上扣减 Σ(该题扣分值 − 该题得分)，clamp [0,100]。实现要点（复审确认的两处耦合）：① 现循环只按 `MaxScore<=0||skipped` 过滤（summary.go:30），不识别 `excludedFromScoring`——题库项一律按 Kind 识别并跳过分母累加，请求失败的 warning 题同样不入分母，但需保留 `failed` 计数语义（答错的 failed 题计入 `failed++`，阻止 `likely/high_confidence` 阶梯，summary.go:35-37,108,111）；② 扣减必须紧随归一化与 Juice 罚分（summary.go:39-46）统一落点，使 modelMismatch/juice 硬短路（summary.go:49-54）与各早退路径携带的 score 一致含扣减。即环节内部总分 31 分、按题平均分配、答错扣光该题分值——单题配置时一道答错直接 −31（基础全对 100→69，低于默认阈值 70，会按现有规则触发处罚联动）。`resultSummary.customQuiz` 聚合环节小计 `{enabled, score, maxScore:31, deduction, items[]}` 供前端展示"题库测试 0/31"。
- 证据：每题一个 item（Kind=`custom_quiz`，itemKey=`custom_quiz:<questionId>`），`evidenceSummary` = `{questionTitle, verdict, reason(中文，取对比判定 reason 或解析失败说明), answerExcerpt(≤500 字符)}`，经 `sanitizeSummaryValue` 有界脱敏；**不含参考答案与要点**。

## 风险与注意事项

- 风险 1（评分语义）：扣分模型下单题误判（如关键词因措辞未命中）最多 −31 分，100→69 已低于默认处罚阈值 70，可能触发处罚联动。缓解：管理员审核把关题目可用性、判分确定性可回放、阈值/要点由提交者明确给出；若不可接受，切换 D2 备选权重模型或增加"仅诊断不计入处罚"开关（实现成本已预留）。
- 风险 2（生产形态）：当前生产为 K3s 三容器混合形态、node-runtime 现役 Web/API/网关；本计划交付 Go + 前端，生产 `/model-checks` 路径的实际可用性取决于 go-only 切流里程碑，不在本计划范围。
- 风险 3（契约钉死）：schema 语句 golden（614）、ALTER 计数（3）、`shared/contracts/j3b_model_check_schema.go` 清单、前端两个回归脚本的源码断言，任何遗漏都会导致 CI/回归失败——各阶段实现时同步更新并先读断言再改代码。
- 风险 4（平行实现漂移）：jobs 侧存在被封存的 `internal/modelcheck*` 近似复制代码，禁止在其上实现或顺手修改；一切运行时实现只在 gateway。
- 风险 5（大文件）：`ModelChecksView.vue` 已 1189 行，题库状态必须收敛在独立组件/composable，禁止继续堆入。
- 风险 6（sanitize 上限）：题目快照/回答摘录受"字符串 500 字符"脱敏上限约束，超长内容在历史记录中截断，属预期行为，前端按截断展示。
- 风险 7（提示注入）：对比请求会向被测链路发送参考答案文本，恶意题面理论上可借提示注入套取他人题目的参考答案。缓解：审核清单加入"注入特征检查"；参考答案不写入任何证据回显；题面 2000 字符上限压缩注入空间；泄漏后果有限（检测由检查发起者自选题目，套取他人参考答案无法让别人的账户"作弊过关"）。
- 发布异常处理：题库为纯新增能力，配置列为加法迁移（NULL=不启用）；异常时回滚到前一构建即可，旧构建不识别新列与新表（gateway 只校验不建表，schema 归 maintenance），不影响既有检测链路。
