## 需求目标

- 背景：旧授权入口分散在账户页和分组页，无法按团队共享，也不利于统一查看授权消耗。
- 目标：新增 `系统团队管理` 菜单，并把 AI 账户、分组、系统账户授权和团队授权统一收敛到 `授权管理` 菜单。
- 交付物：团队数据结构、统一授权数据结构、管理接口、网关鉴权与调度、授权消耗统计、团队与授权前端页面、验证记录。
- 重要前提：项目未正式上线，本地 SQLite 可重建或清洗，不考虑旧授权表历史兼容，按完整版模型实现。

## 方案概述

- 菜单变化：新增 `系统团队管理` 和 `授权管理`；账户页和分组页不再提供分散授权弹窗。
- 数据变化：新增 `system_teams`、`system_team_members`、`resource_authorizations`、`resource_authorization_sources`；本地库按新版 schema 重建或清洗。
- 授权对象：最终有效授权只绑定 `grantee_system_account_id`；团队只是批量创建 / 合并用户授权的来源。
- 授权资源：`resource_authorizations.resource_type` 支持 `account` 和 `group`。
- 调度口径：网关只校验最终用户授权；个人来源和团队来源通过来源表管理，团队来源优先，个人来源取消且不自动回退；分组授权只共享分组所有者自有账户。
- 统计口径：调用方明细归实际 API Key 所属系统账户；资源总量归真实资源所有者；授权消耗只按“资源 × 用户”聚合，团队视图只是团队成员用户消耗的筛选汇总，并排除资源归属人自用消耗。

## 验收标准

- [ ] 管理员可以创建、编辑、启停团队，并维护团队成员。
- [ ] 同一资源同一用户全生命周期只存在一条稳定的最终用户授权主记录。
- [ ] 资源所有者可以在授权管理里把自有 AI 账户或分组授权给系统账户或系统团队。
- [ ] 被授权系统账户或团队成员只能使用资源，不能编辑、删除、查看敏感凭据或继续转授权。
- [ ] 团队成员新增、移除、团队停用、系统账户停用和授权收回都能实时影响网关调度。
- [ ] 授权管理能按“资源 × 用户”展示每个被授权用户消耗；团队筛选展示成员用户用量去重汇总，且不包含资源归属人自用消耗。
- [ ] 同一用户对同一 AI 账户或分组同时拥有个人来源和团队来源时，前端列表、API 结果和调度绑定都只出现一个有效资源。
- [ ] 团队来源进入后，个人来源被取消为非生效来源，不再作为未来自动回退来源。
- [ ] 授权来源变化时，既有分组账户绑定和 API Key 分组绑定仍指向同一资源；只要最终用户授权有效就可以继续使用。
- [ ] 团队成员移除、重新加入或团队成员历史变化后，已有用户消耗仍按最终用户授权保留；团队筛选只影响当前展示范围。
- [ ] AI 账户 / 分组用量情况能展示资源全部总消耗，包含自用、所有用户授权使用。
- [ ] 使用记录页仍只展示调用方自己的明细，资源所有者不能查看被授权人的请求快照和业务内容。
- [ ] 文档、接口、类型、前端页面和验证记录同步完成。

## 风险与注意事项

- 授权穿透风险：授权资源不能被被授权人继续转授权，分组授权必须过滤非分组所有者自有账户。
- 团队动态风险：团队成员变化后，网关不能只信任 API Key 或分组绑定时的历史状态。
- 来源切换风险：如果只用单表覆盖字段实现，容易丢失来源历史或错误回退个人来源。
- 统计口径风险：授权消耗和资源真实总量必须分开聚合，避免把归属人自用算进授权消耗。
- 聚合主键风险：如果统计仍按来源或临时授权行聚合，会破坏“历史用量按最终用户授权合并”的要求。
- 隐私风险：资源所有者只能看授权聚合用量，不能看被授权人的请求快照、响应快照、客户端 IP 或 API Key 明文。
- 本地数据风险：实施时允许重建或清洗本地 SQLite，但必须避免把真实上游密钥写入文档或日志。
