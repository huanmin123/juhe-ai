# PLAN-20260729T092854040Z 多 API Key 账户健康检查与增量变更

## 目标

修正多 API Key 账户把单个 Key 的失败或新增误判为整个账户待检查的问题。账户应在至少一个此前已验证且未变更的 Key 仍可用时持续参与调度；后台账户健康检查应按 Key 池聚合，而不是依赖一次普通轮询命中。

## 业务规则

- 新增、删除、替换或重排 `api_keys` 时，按 Key 指纹比较变更前后集合。
- 若账户当前可调度，且至少保留一个变更前已处于 `active` 状态、变更后仍存在的 Key，则账户 `status`、`schedulable` 和账户级健康事实保持不变，不投递账户级健康检查。
- 新增或替换得到的新 Key 初始化为 `unverified`，在独立 Key 探测成功前不参与网关选择；其探测结果不覆盖仍健康的账户状态。
- 若全部此前正常 Key 都被移除或替换，则账户转入既有 `pending_test` 激活检查流程。
- Base URL、代理、协议能力、检查模型或检查请求形态等会影响全部 Key 的变更，仍按既有规则执行账户级检查。
- 多 Key 账户的后台健康检查固定逐 Key 探测当前可执行 Key；任一 `complete_success` 即记录账户级成功。只有没有 Key 成功时才按现有失败流程记录账户检查失败。

## 实施范围

- Key 运行态：增加未验证状态、初始化和后台探测候选支持。
- 账户 PATCH：识别 Key 集合增量，保留已有可用账户的状态并投递 Key 级探测。
- 后台检查：多 Key 候选不再通过普通轮询决定健康结果，改为固定 Key 池聚合。
- 回归：覆盖“坏 Key + 好 Key”的账户检查、增 Key 不降级、替换全部正常 Key 降级和未验证 Key 不进路由。

## 非目标

- 不改变单 Key 账户、新建账户和全局连接配置变更的激活检查规则。
- 不把完整上游 HTTP 错误自动解释为凭据失效；Key 运行态仍遵守既有来源和恢复边界。

## 验收标准

- 3 Key 账户中任一 Key 成功时，后台检查记录成功，账户不因其他 Key 失败进入不可用状态。
- 已激活账户新增 Key 后保持可调度，新 Key 在验证通过前不被选择。
- 所有既有正常 Key 被替换后，账户进入 `pending_test` 且不参与调度。
- 相关 Node 类型检查和针对性回归通过。

## 实施记录（2026-07-29）

- 已在 Key 运行态中加入 `unverified`；网关选择器将其视为不可调度，后台 Key 探测查询同时覆盖 SQLite 和 PostgreSQL。
- 管理 PATCH 和旧 `updateAccount` / `updateAccountAsync` 入口均按 Key 指纹集合判断增量。只有受 Key 池隔离支持的协议账户，且保留至少一个 `active` 的原 Key 时，才保留账户状态和账户级健康事实。
- 新增或重新加入的 Key 在账户写事务内初始化为 `unverified` 并安排立即探测；保留 Key 的运行态索引会随重排同步。全量替换、Base URL 或代理变化仍进入账户级 `pending_test`。
- 后台账户健康检查对多 Key 候选使用固定 Key 逐项探测，跳过停用 Key，并在首个成功后写入账户级成功。
