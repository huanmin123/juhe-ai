## 需求目标

- 背景：同一个 API Key 被多人共享时，某个客户端来源可能在短时间内反复触发单个账号失败。系统不能因为单个来源的样本就把账号全局冷却，也不能遇到问题就直接返回客户端。
- 目标：当前序账号出现未确认失败、后续账号完整成功时，让当前 `clientIp + API Key + 分组` 短期避让前序账号，后续请求优先自动切到其他可用账号；账号级冷却仍只由明确账号策略、流熔断或后台复测等强证据触发。
- 交付物：长期设计文档、计划文档、网关调度实现、回归脚本、验证记录和相关索引同步。

## 方案概述

### 方案原则

- 不解释状态码：默认调度不维护状态码白名单或黑名单。
- 只消费调度事实：前序账号未确认失败，后续账号完整成功，才提交当前 IP 对前序账号的短 TTL 回避。
- 不扩大账号惩罚：IP 级回避只影响候选排序，不写账号冷却或异常状态。
- 不把池子筛空：如果当前 IP 回避命中全部候选账号，则旁路回避并保留原候选列表。
- 成功才清理：当前 IP 对某账号完整成功后，清理该 IP 对该账号的回避状态。

### 后端变化

- 新增 `openai-gateway-client-ip-account-avoidance.service.ts`，维护进程内 TTL 状态和候选账号排序。
- 在 `openai-gateway-request-preflight.ts` 的本地账号屏蔽后、Codex turn 避让前应用 IP 级回避。
- 在 `fetchFirstAvailableUpstream` 内维护本请求待确认 IP 失败列表。
- 在未知失败最终 `skip_account` 后追加待确认 IP 失败；请求级错误、账号策略命中、客户端取消等不追加。
- 在完整成功响应收口时提交前序待确认 IP 失败并清理当前账号回避。

### 数据变化

- 不新增数据库字段和表。
- 新增进程内短 TTL 状态，属于易失运行态。

## 风险与注意事项

- NAT 或代理出口会让多个真实用户共享同一客户端 IP；因此 IP 级回避只能短 TTL、局部排序，不能当作用户身份或处罚依据。
- 进程内状态重启后丢失，符合轻量部署边界；横向扩容形态下每个实例只使用本实例回避状态，不承诺跨实例一致回避。
- 如果所有账号都对某 IP 被回避，系统必须旁路回避继续尝试，避免“保护机制导致无账号可用”。
- 流式已可见输出后的失败不能服务端透明重放，仍以现有流熔断和客户端策略处理。
