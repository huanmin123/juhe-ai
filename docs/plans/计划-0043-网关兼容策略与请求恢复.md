## 需求目标

- 背景：生产 `POST /v1/responses` 请求在普通 API Key `openai_standard` 账号上命中 `thinking_signature_invalid`，同一请求体在同账号原地重试多次后才 fallback 成功。根因不是本地 `JUHE_AI_SECRET` 解密失败，而是客户端携带的 Responses encrypted reasoning 状态与部分上游不兼容。
- 目标：建立可扩展的网关兼容策略层，避免把客户端、供应商、工具和错误码特例写散到主调度层；首轮保持 raw passthrough，只有明确上游兼容失败时才生成一次受控请求体变体重试。
- 交付物：长期文档、执行计划、后端策略实现、mock AI 全链路回归测试、验证记录。

## 方案概述

- 方案原则：首轮 raw passthrough，错误触发恢复；策略决策和 body/header transform 分离；请求级恢复不写账号状态；同一恢复策略只执行一次。
- 数据变化：不新增数据库字段。
- 接口变化：不新增管理 API；网关外部接口响应契约保持 OpenAI-compatible。
- 前端变化：无。
- 后端变化：新增 request feature、error classifier、compatibility policy、request recovery transform，并在 dispatch 失败处理和下一次 attempt body 构造处接入。
- 数据处理策略：无历史数据清洗；运行路径只维护当前 schema 和当前策略。

## 风险与注意事项

- 请求体恢复需要解析 JSON；必须只在触发兼容错误后执行，超过内联解析阈值时走 JSON worker，避免普通大请求首轮增加解析成本或在主线程同步解析大 body。
- 恢复策略只应记录字段存在性、数量和动作摘要，不记录 encrypted content 原文。
- 清洗 `previous_response_id` 必须区分 `function_call_output`，避免破坏工具结果提交链路。
- 发布异常处理：可通过回滚到未启用该策略的构建恢复；本次不新增数据库字段，不涉及数据回滚。
