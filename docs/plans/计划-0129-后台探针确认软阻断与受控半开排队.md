## 需求目标

### 背景

生产账号 `vsllm-胡安民-github` 在数据库仍为 `active` 时，网关运行态已经显示 `precheck_pending`，原因是独立后台探针取得真实上游 `HTTP 403 / insufficient_user_quota` 失败结果，但普通客户端请求仍继续被调度到该账号并长时间等待上游，造成多个客户端请求同时卡住。

现有首字超时、包间隔超时、同账号重试和流式兜底都发生在“请求已经选中账号并进入上游尝试”之后，无法替代账号级调度阻断。只要调度层仍持续选中已经由后台探针确认异常的账号，这些机制最多结束单个已发出的尝试，不能阻止后续请求继续排到同一个问题账号。

### 目标

- 普通客户端失败只能触发一次后台核实信号，不能直接改变账号级状态，也不能通过请求数量放大探针失败次数或延长运行态。
- 独立后台探针形成真实上游尝试且失败后，立即把账号放入网关共享运行态软阻断；数据库仍可保持 `active`，但普通客户端调度必须停止命中该账号。
- 多轮跨时间后台探针持续失败后，再写入 `temporary_unavailable`，继续使用现有冷却复测和自动恢复链路。
- 存在健康账号或后备分组时优先切换，不能为了半开或等待而拖慢本来可被救回的请求。
- 所有候选都处于软阻断时，允许受控半开；其余请求进入有界等待，等待后台探针或半开成功后重新选路。
- 单个请求从最初进入网关开始的总等待预算不超过 270 秒，重试、切号、后备分组、排队和半开不能重置预算。
- 运行态展示必须与实际调度一致，不能再出现页面显示“不可用 / 待探针确认”，调度层却仍把账号当普通候选的矛盾。
- 后台探针必须证明账号实际配置链路有效：供应商 driver、协议档案、凭据 / API Key、Base URL、代理、账号 headers / options 和 `healthCheckModel` 都必须走与真实账号请求共享的上游执行能力。

### 交付物

- 后台探针确认后的共享软阻断状态机。
- memory / Redis runtime state 一致的调度过滤。
- 单账号单租约、分组有界并发的受控半开。
- 不持久化请求 payload 的进程内有界等待协调器。
- 270 秒绝对请求截止时间与现有重试、首字和包间隔兜底的统一预算。
- 账号页准确的运行态标签、说明、下一次复核时间和调度语义。
- mock upstream、Redis 边界、状态格式化和生产候选验证记录。

## 与 PLAN-0128 的关系

本计划保留 `PLAN-0128` 的核心安全边界：

- 普通用户请求失败不能直接写账号状态。
- 用户失败信号只能原子首次创建后台核实事件，不能合并放大、改写或续期已有事件。
- 未形成真实上游尝试的探针任务失败属于未知结论，必须丢弃，不能阻断账号。
- 持久 `temporary_unavailable` 仍需跨时间多轮独立后台确认，不能由同一波客户端错误快速写入。

本计划明确修订 `PLAN-0128` 的两项调度结论：

1. “一次后台探针失败仍保持普通可调度”改为“第一次有效独立后台探针失败立即进入运行态软阻断”。
2. “全部易失运行态候选失败开放”改为“普通调度不失败开放；先后备分组，再受控半开，其余请求有界排队”。

软阻断不是持久封禁。它只阻止普通调度，并保留后台探针、主动健康检查和受控半开恢复出口，因此不会重新引入“客户端请求可以瞬间把全部账号打死”的问题。

## 核心不变量

1. 客户端失败只创建一个后台核实事件，不直接阻断、不累加账号探针失败轮次、不延长 TTL、不写数据库。
2. 只有独立后台探针真实到达上游后取得非成功、超时、连接错误或协议失败，才允许进入共享软阻断。
3. 探针执行器自身异常、DB service 超时、任务取消、无法加载账号或未发出有效上游请求属于未知，不得进入软阻断。
4. `recovery_wait` 仅代表“等待第一次独立后台核实”，不展示为账号异常，也不影响普通调度。
5. `precheck_pending` 改为“后台探针已确认异常，等待恢复复核”的软阻断语义；数据库可仍为 `active`，普通调度必须过滤。
6. 软阻断期间，账号只能被后台探针、主动健康检查或获得租约的受控半开请求访问。
7. 健康候选和后备分组永远先于半开和排队。
8. 半开失败不能增加后台确认轮次、延长健康状态 generation 或写数据库；它只结束本次租约并保持已有软阻断。
9. 半开完整成功可以清理匹配 generation 的软阻断；普通非半开用户成功仍不能修改账号级运行态。
10. 软阻断、手动恢复、后台成功、持久状态写入和账号配置变更都必须使用 generation 防止迟到结果覆盖新状态。
11. 排队不保存或复制请求 payload 到 Redis、数据库或后台队列，只保留当前 HTTP 请求生命周期和最小等待元数据。
12. 排队、重试、后备分组和半开共享一个从原始 `startedAt` 计算的绝对截止时间；总预算不能重置。
13. 客户端断开、AbortSignal 取消或响应已经结束时必须立即退出等待并释放所有本地名额。
14. 已经产生下游可见输出的流式请求不能静默拼接另一个账号；继续沿用现有客户端协议兜底边界。
15. 所有队列和并发结构必须有上限，不能为了保护客户端引入无界内存增长。

## 状态机设计

| 阶段 | 形成条件 | 存储 | 普通调度 | 恢复 / 升级 |
| --- | --- | --- | --- | --- |
| `normal` | 无异常运行态，数据库 `active` | 无运行态 | 正常参与 | 客户端失败只触发一次 `recovery_wait` |
| `recovery_wait` | 普通请求真实命中上游后失败，原子首次创建核实事件 | memory / Redis probe state | 继续参与，不展示异常 | 后台探针成功则清理；未知则丢弃；有效失败立即转 `precheck_pending` |
| `precheck_pending` | 第一次有效独立后台探针失败 | memory / Redis probe state | 从普通候选中移除 | 后台成功或半开完整成功清理；跨时间多轮失败后写 `temporary_unavailable` |
| `half_open` | 全部可恢复候选软阻断、无健康后备，且取得账号和分组租约 | 进程内短租约，绑定 runtime generation | 只允许租约持有请求 | 完整成功清理匹配软阻断；失败释放租约并继续软阻断 |
| `temporary_unavailable` | 满足既有最小观察时间、独立轮次和并发归零条件 | 数据库 | 完全不参与调度 | ops-worker 冷却复测或手动恢复 |

### 有效后台失败的定义

以下结果属于“已经形成真实上游尝试但没有完成健康成功”，允许进入软阻断：

- 上游连接超时、连接失败、TLS / EOF 等网络错误。
- 上游 HTTP 非 `2xx`，包括额度不足、限流、凭据错误和服务端错误。
- `2xx` 响应体或 SSE 协议不完整、缺少终止、失败事件、语义错误。
- 账号绑定代理、Base URL 或凭据准备完成后，真实上游发送阶段失败。

以下结果属于未知，必须清理本次核实事件而不是阻断：

- 探针任务未加载到账号或账号 generation 已变化。
- DB service、worker、队列或本地执行器自身异常，且没有形成上游尝试。
- 服务关闭、任务取消、并发门禁未取得或探针预算不足。
- 账号已经被手动恢复、修改配置或写入其他持久状态，当前探针结果已经过期。

## 后台探针与真实账号配置一致性

后台探针不通过公开 `/v1/*` 用户入口再次发起一个完整客户端请求，也不消费用户 API Key、路由策略、用户 payload 或用户选择的 model。它必须复用真实账号上游调用所使用的共享能力，并通过 `trafficSource` 明确标记为系统探针，避免被自身软阻断卡死。

必须共享的账号配置：

- 供应商 driver 和协议 profile。
- 账号类型、凭据选择和多 API Key 选择规则。
- Base URL、代理绑定和代理 profile。
- 账号 headers、供应商 options、请求映射和鉴权方式。
- 账号保存的 `healthCheckModel`。
- 上游响应协议解析和“完整成功”判定。

必须与客户端请求隔离的内容：

- 不复用失败客户端的 endpoint、stream、messages、tools、图片或其他 payload。
- 不使用用户请求 model 代替 `healthCheckModel`。
- 不参与用户 API Key 额度、路由策略、会话亲和、IP 回避和普通账号软阻断。
- 探针使用记录、日志和审计必须标记系统流量，不能伪装成用户成功或失败。

## 调度顺序

每次初始调度、等待唤醒、半开失败后的再次尝试，都必须重新执行以下顺序：

1. 重新读取当前 API Key、路由策略、分组、授权、账号数据库状态和运行态 generation。
2. 应用数据库硬过滤：`active`、`schedulable`、冷却、授权、时间计划、凭据、模型和协议能力。
3. 应用账号所有者显式配置的错误策略避让。
4. 应用后台探针确认软阻断：过滤 `precheck_pending`，保留尚未探针确认的 `recovery_wait`。
5. 如果当前分组仍有普通健康候选，按现有优先级、速度优先、权重、会话亲和和容量规则调度。
6. 如果当前分组普通候选为空，先按路由策略尝试后备分组。
7. 所有可承接分组都只有软阻断候选时，尝试取得受控半开租约。
8. 没有半开租约时进入等待；被唤醒后回到第 1 步，禁止复用入队时的账号数组。
9. 到达绝对截止时间后返回网关统一 `503 service_unavailable`，说明等待恢复超时，不透传上游敏感原文。

数据库硬不可用账号不进入本计划的恢复等待。如果候选仅剩 `disabled`、`error`、`pending_test`、`temporary_unavailable`、`rate_limited`、`schedulable = false`、授权失效或能力不匹配，应按现有规则快速失败或切后备分组。

## 受控半开设计

### 租约边界

- 同一个 `runtimeKey + generation` 同时最多一个客户端半开租约。
- 同一个分组同时最多放行有限数量的半开请求，避免账号池全部异常时瞬间把每个账号都重新打一遍。
- 半开租约只存在于当前网关进程；Redis 继续保存权威软阻断和 generation，不在 Redis 保存客户端请求或等待者。
- 半开账号必须仍满足数据库、授权、模型、协议、额度和账号硬并发约束。
- 半开请求禁止同账号原地重试；一个租约只允许一次真实上游尝试，失败后回到剩余预算内的换号 / 排队流程。
- 租约必须带 generation。后台成功、手动恢复或配置更新已经推进 generation 时，迟到的半开结果不得清理或重建状态。

### 成功边界

半开只有取得完整协议成功才算恢复：

- 非流式：`2xx`、响应体完整、协议解析成功、业务终态成功。
- 流式：上游流完整、取得有效语义输出、终止事件和终态符合协议；仅收到 headers、首字节、心跳或部分 token 不算恢复。
- 成功时清理匹配 generation 的软阻断，记录恢复事件，并按新可用容量定量唤醒等待者。

### 失败边界

- 可见输出前失败：当前请求可以在剩余 270 秒预算内尝试其他账号、后备分组或重新排队。
- 可见输出后失败：保持现有协议兜底和客户端协调策略，不静默拼接另一个账号。
- 半开失败不累计后台探针轮次、不重置 `startedAtMs`、不延长 probe state TTL、不写 `temporary_unavailable`。
- 半开失败只释放租约并进入固定的本地再尝试间隔，防止队列立即形成请求风暴；后台探针仍是失败确认的唯一权威来源。

## 等待协调器设计

### 绝对截止时间

```ts
const queueDeadlineAtMs = requestStartedAtMs + Math.min(
  270_000,
  activeGatewaySettings.streamClientTotalWaitTimeoutSeconds * 1000
)
```

- 如果现有总等待配置小于 270 秒，使用更小值。
- 如果现有配置大于 270 秒，本机制仍最多等待 270 秒。
- 每次重试、切号、切分组和重新入队都沿用同一个 `queueDeadlineAtMs`。
- 首字等待、包间隔等待和流式总寿命继续使用现有配置，但不能突破这个请求级总预算。

### 进程内等待数据

等待协调器只保存最小元数据：

```ts
interface RecoverableGatewayWaiter {
  waiterId: string
  scopeKey: string
  candidateRuntimeKeys: string[]
  enqueuedAtMs: number
  deadlineAtMs: number
  sourceKey: string
  signal?: AbortSignal
}
```

- 不保存 headers、Authorization、请求正文、messages、tools、图片或上游凭据。
- 实际 Express 请求仍停留在原 HTTP 生命周期中；协调器不复制 payload，也不把请求投递到 Redis Stream。
- scope 建议包含 `systemAccountId + apiKeyId + routeStrategyId + groupId + requestLane + requestedModel`，避免不相关模型和分组互相唤醒。
- sourceKey 使用已有 API Key / client IP 身份的安全内部标识，不写明文密钥。

### 排队和唤醒

- 同一 scope 内按 FIFO 排队，并对来源做轮转，避免同一 API Key / IP 长队独占全部恢复名额。
- 后台探针成功、主动健康成功、手动恢复、半开完整成功或账号并发释放时发布 runtimeKey 可用事件。
- 每次事件只按新释放的账号容量发放有限 permit，不广播唤醒全部请求。
- 保留一个共享 5 秒兜底巡检，补偿事件丢失；巡检由 scope 共享，不能每个请求各自建立 timer。
- 被唤醒请求只获得“重新选路资格”，不预绑定旧账号；它必须重新执行完整候选选择。
- 请求断开、AbortSignal 触发、响应结束或截止时间到达时立即从队列移除。

### 有界保护

- 等待必须发生在认证、基础请求校验和来源并发保护之后，恶意未认证请求不能进入恢复队列。
- 等待者继续占用来源并发名额，防止同一 IP / API Key 无限堆积 270 秒长连接。
- 增加进程级和 scope 级硬上限；达到上限时返回明确的本地 `503`，不能继续占用内存。
- 队列满、本地取消和客户端断开都不作为账号失败样本，也不触发新的后台探针事件。
- 队列长度、最长等待、超时、取消和来源公平性只记录统计值，不记录请求正文。

## 与现有延迟兜底的关系

| 机制 | 生效位置 | 本计划后的职责 |
| --- | --- | --- |
| 首字超时 / 速度优先切号 | 已选中账号、等待首个有效输出 | 继续救单个慢请求；不能让已确认异常账号重新进入普通候选 |
| 包间隔 / SSE 空闲超时 | 已开始流式响应 | 继续终止卡死流；可见输出前按剩余预算换号，可见输出后遵守协议边界 |
| 同账号临时重试 | 单账号失败后的短暂确认 | 普通健康账号继续按配置；软阻断半开账号禁止同账号重试 |
| 后备分组 | 当前分组不可承接 | 永远先于半开和排队 |
| 客户端总等待预算 | 整个请求生命周期 | 统一覆盖重试、切号、后备、排队和半开，最多 270 秒 |
| 后台探针 | 独立系统请求 | 唯一失败确认来源；成功可立即恢复并唤醒等待者 |

## 评审参数

以下参数除 270 秒外尚未由用户逐项确认，先使用保守推荐值写入计划，实施前可调整：

| 参数 | 推荐值 | 原因 |
| --- | --- | --- |
| 请求恢复等待硬上限 | 270 秒 | 用户已确认；覆盖排队、重试和半开总预算 |
| 单账号半开并发 | 1 | 防止异常账号被并发重新打满 |
| 单分组半开并发 | 2 | 允许两个账号并行验证，同时限制全池请求风暴 |
| 半开失败后本地再尝试间隔 | 30 秒 | 不改变后台健康状态，只控制客户端探测频率 |
| scope 等待者上限 | 256 | 防止单 API Key / 分组占用无界连接与内存 |
| 进程等待者总上限 | 2048 | 最终内存安全阀；超过时明确失败，不伪装成功 |
| 事件丢失兜底巡检 | 5 秒 | 复用现有共享巡检节奏，避免每请求 timer |

这些值不新增管理端配置项，先作为网关内部常量；只有生产压测证明需要运营可调时，再单独设计配置边界。

**核心流程伪代码：**

```ts
while (!responseFinished && Date.now() < deadlineAtMs) {
  const preflight = await prepareOpenAIGatewayDispatchContext(currentRequest)
  if (preflight.kind === 'dispatchable') return dispatch(preflight)
  if (preflight.kind === 'fallback') continue
  if (preflight.kind === 'hard_unavailable') return sendUnavailable()

  const permit = await waitCoordinator.waitForPermit({
    scope,
    candidateRuntimeKeys: preflight.softBlockedRuntimeKeys,
    deadlineAtMs,
    signal
  })
  if (!permit) return sendRecoverableWaitTimeout()
}
```

## 发布与生产验收

### 发布前

- 不修改数据库 schema，不新增运行时兼容分支。
- 检查 Redis `gateway-account-recovery` 当前状态，确认现存 `precheck_pending` 都有真实后台失败依据；如发现旧版本遗留脏状态，只精确清理该命名空间和目标 generation，不清空整个 Redis。
- 候选实例使用 mock upstream 验证：一个坏账号、一个健康账号、全部坏账号、半开成功、半开失败、客户端取消和 270 秒预算。
- 确认账号页文案和实际调度过滤一致。

### 生产验收场景

1. 对测试账号制造一个可控后台探针失败，确认数据库仍为 `active`、运行态进入软阻断。
2. 软阻断后发起新请求，确认普通 gateway attempt 对该账号为 0；只有标记为 probe 或 half-open 的尝试允许命中。
3. 同分组有健康账号时确认请求立即切走，不出现 270 秒等待。
4. 所有账号软阻断时并发发起多个请求，确认半开并发不超过设定值，其余进入等待。
5. 恢复一个账号，确认等待请求分批唤醒并重新选路，无瞬时洪峰。
6. 保持全部账号异常，确认请求最多等待 270 秒后收到统一错误，服务进程内存和事件循环无持续增长。
7. 观察至少一个完整的软阻断到持久 `temporary_unavailable`、再由冷却复测恢复的生命周期。

### 回滚边界

- 代码回滚到旧版本会重新把 `precheck_pending` 当作普通可调度，属于已知行为倒退。
- 回滚前必须先停止新实例，确认是否保留现有 soft-block state；如旧版本继续运行，需决定精确清理这些状态或接受旧版失败开放，不能让新旧语义同时在线。
- 等待队列和半开租约是进程内状态，进程重启会断开当前等待中的 HTTP 请求；本计划保护上游账号异常，不承诺跨服务重启保活客户端连接。

## 风险与注意事项

- 软阻断过早：通过“只有有效独立后台失败才阻断”和受控半开恢复降低误伤；探针任务自身故障不能阻断。
- 全池长期异常：最多等待 270 秒后仍会失败，不能伪造成功或无限挂起；这是客户端保护与资源安全之间的硬边界。
- 恶意请求占用半开：失败不进入健康确认，来源并发、FIFO 来源轮转和固定再尝试间隔限制单一来源影响。
- 长流式响应：半开必须完整成功才能恢复，可能比首字成功更慢；后台独立探针仍可提前恢复并唤醒其他请求。
- 进程内队列：符合当前单网关进程和轻量部署边界；未来如果明确支持多 Web 实例，需要另行设计跨实例 permit，不在本计划提前引入。
- 大文件风险：`account-side-effects.service.ts` 和 `routes.ts` 已较大，实施时按职责拆分，不把新状态机、队列和半开全部继续堆入原文件。
- 既有显式策略：账号所有者配置的状态动作和 TTL 不能被半开旁路；本计划只改变系统自动探针确认后的默认运行态调度。
- 使用记录：排队等待、半开尝试、后台探针和最终客户端结果必须可区分，不能把等待时间或探针流量错误计入普通成功统计。
