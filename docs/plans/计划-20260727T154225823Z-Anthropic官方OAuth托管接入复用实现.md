# PLAN-20260727T154225823Z Anthropic 官方 OAuth 托管接入复用实现

- 状态：已完成
- 完成时间：2026-07-28

## 背景

当前项目已经有完整的 OpenAI 托管 OAuth 创建 / 重新授权 / Refresh Token 换取 Access Token 链路；本计划的目标是把 Anthropic `oauth` 账户从历史上的“手工粘贴 Access Token”导入模式扩展为完整托管 OAuth 能力。

用户要求优先复用现有开源项目已经验证过的实现方式，不自行发明新流程；同时当前仓库是 Apache-2.0 项目，不能把其他项目里和订阅代理、TLS 指纹伪装、cookie / sessionKey 劫持绑定的实现原样移植。

因此本次工作聚焦在“复用现有项目内 OpenAI OAuth 的托管骨架，为 Anthropic 官方 OAuth 提供同类托管接入能力”，只迁移独立可落地、与当前架构一致的标准 OAuth code exchange / refresh token 账户接入能力。

## 目标

- 为 `anthropic` 官方协议档案补齐托管 OAuth 创建能力。
- 复用现有 OpenAI OAuth 的会话、创建、重新授权、操作日志、账户创建和前端保存流骨架。
- 让前端账户页对 OpenAI 与 Anthropic 都走“站内托管 OAuth”创建模式，而不是 Anthropic 单独保留手填 token 模式。
- 保持现有账户模型、分组、路由策略、探针、测试和网关转发边界不变。

## 范围

### 包含

- 新增 Anthropic OAuth 后端模块与系统 API 路由。
- 新增 Anthropic OAuth 前端 API 封装。
- 复用账户表单中的授权面板、保存流与重新授权逻辑。
- 调整能力矩阵：托管 OAuth 从“仅 GPT OpenAI v1”扩展到“按供应商分流”。

### 不包含

- 任何 Claude 订阅共享、Web 端 cookie 劫持、sessionKey 注入、TLS / 指纹伪装、浏览器签名模拟。
- 任何依赖非官方、不可长期维护的私有认证链路。
- 新建独立 sidecar 或把其他项目完整搬进当前仓库。

## 设计原则

- 优先镜像现有 `openai-oauth` 模块的结构、路由约定和前端调用方式。
- 供应商差异只落在 OAuth 服务实现和能力判定层，不把业务规则散落到表单和通用账户保存逻辑中。
- 不把“OAuth 账户类型”继续等同于 OpenAI；托管能力由供应商 / 协议档案共同决定。

## 任务清单

1. 审计 OpenAI OAuth 模块、前端账户保存流、重新授权流和能力矩阵。
2. 实现 Anthropic OAuth 后端模块，补齐 `auth-url`、`create-from-code`、`create-from-refresh-token`、重新授权等路由。
3. 在系统 API 中挂载 `my-anthropic-oauth` 与 `anthropic-oauth` 路由，并补齐前端 API client。
4. 调整前端能力矩阵和保存流，按供应商选择托管 OAuth API，而不是写死 `openaiOAuth`。
5. 运行定向回归并复查边界，确认没有把 OpenAI 专属假设错误带入 Anthropic。

以上任务均已完成。最终实现还补齐了派发前自动刷新、跨实例刷新锁、配置 revision CAS，以及 Anthropic OAuth 所需 beta 头；前端已通过隔离管理页验收。

## 完成标准

- Anthropic 官方档案的新建 OAuth 账户可以像 OpenAI 一样走站内授权面板。
- 新建与重新授权不再写死 OpenAI API 域。
- 现有 OpenAI OAuth 功能不回退。
- 文档、计划、代码和能力矩阵保持一致。
