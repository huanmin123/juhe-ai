### 分阶段发布顺序

用户通知上线后仍按多次发布执行，每阶段使用独立 release SHA、包校验和、验证结果和回滚点：

1. **结构准备阶段**：只执行 `000056/000057` 加法迁移并校验；旧生产代码继续运行，失败只回到匹配业务备份，不启动新代码。
2. **后端稳定性阶段**：发布账户状态、后台探针、网关 deadline / 408、多 Key、后台任务、页面 dirty outbox 和使用记录服务端缓存；临时 PostgreSQL / Redis 与主环境隔离验证后才切流。

## 核心不变量

1. 普通用户业务请求不能决定账户级持久状态；只有后台标准探针或用户显式配置的账户错误 / 响应策略可以改变状态。
2. 所有运行态枚举刷新时都以 Redis / 权威状态接口为准，空进程快照不能清空真实状态。
3. 探活开关不是 `health_check_enabled`，不能关闭系统周期健康检查。
4. 使用记录首屏缓存只服务个人作用域的“当天 + 网关请求 + 第 1 页 20 条”，key 必须包含系统账户、日期和协议版本；不再保留通用读取后响应缓存，其他查询回源数据库。
5. Redis / worker / DB service / 代理 / 公网域名故障必须分组件归因，不能统一映射为同一种错误或互相触发恢复。
6. 每个新候选必须独立完成 temporary-first、main 固定 PID/1+1+3、切回观察、临时清零和 `VERIFY_SUCCESS`，不得复用旧 release 的验收结论。

- 历史会话矩阵中的“明确遗漏”全部有代码、文档和可重复测试，或有证据充分的明确不做结论。
