# PLAN-0076 管理接口读写隔离与前台防阻塞

## 基本信息

- 编号：`PLAN-0076`
- 状态：`已完成`
- 创建时间：`2026-07-04`
- 需求来源：用户反馈本地 `AI 账户管理` 管理接口被后台 worker / SQLite 锁等待拖到秒级，并要求读请求不排队、不被后台写阻塞。
- 执行者：Codex 与并行 gpt-5.5 agents
- 关联模块：后端 / DB service / System API / SQLite / PostgreSQL 高并发模式 / 后台 worker / 管理列表 / 统计窗口 / 前端接口契约

## 需求目标

- 管理端和网关业务读请求不得被后台 worker 写入、维护任务或统计刷新无意义阻塞。
- 前端接口契约保持稳定：前端请求什么，后端仍返回对应真实数据；不通过返回空数据、删字段或弱化页面能力来掩盖性能问题。
- SQLite 单机模式下，只对写入和锁等待做必要治理；读请求不进入写队列，遇到写锁时不能长时间同步卡死 DB service 事件循环。
- PostgreSQL / 高并发模式下，读写默认依赖数据库连接池、MVCC、事务和行锁并发能力；应用层不继续用 SQLite 单写队列思维串行纯读。
- 后台 worker、网关 side effects、维护任务等非前台关键路径写入必须让位于前台业务读。

## 问题定义

- 现象：本地打开 `AI 账户管理` 时，`/accounts` 约 `1.4s`，并导致 `providers/options`、`proxies/options`、`accounts/tags` 等轻量接口在浏览器 Network 中一起显示秒级。
- 已确认根因：
  - `accounts` 列表在请求链路同步读取统计装饰字段，可能等待 stats SQLite 写锁。
  - SQLite 默认 `busy_timeout=5000ms`，同步等待会卡住 DB service 事件循环。
  - 后台 worker DB service typed operation 过去默认 high priority，可能和前台业务抢队列。
  - System API HTTP 路由虽然不走 IPC typed operation 队列，但在 DB service 进程内直接执行 repository；统一 admission、同步 SQLite 调用和认证 `touchSession` 仍会把读请求变成被动阻塞或隐藏写。
  - 连续快速请求时，认证 session 读取、账号标签等轻量读仍有路径绕过 query-only read worker；`GET /auth/me` 仍可能因为 session touch 夹带写入。
  - SQLite read worker pool 过去按 operation key 固定选子进程，同一个 URL / 同一个查询参数的 burst 会集中到同一个 read worker，出现局部排队。
  - `my-accounts` / `accounts` 列表响应装饰还会等待服务端账号运行态快照 IPC；连续点击时重复等待 runtime snapshot 会放大 80ms 到 300ms 级抖动。
- 扩展风险：
  - `groups`、`api-keys`、`stats/usage-overview`、运行日志 facets/runtime snapshot、网关 side effects 也存在读写职责混杂或装饰字段阻塞风险。
  - 高并发模式消除了 SQLite 文件级写锁，但仍可能被应用层 DB service 串行队列、连接池耗尽、行锁、Redis、实时聚合和前端 fanout 拖慢。

## 范围边界

### 本次做

- 建立 DB service typed operation 读写分类：`read`、`write`、`maintenance`、`runtime`、`ambiguous`。
- 让纯读 operation 在 PostgreSQL 模式下直接并发执行，不进入写队列。
- 让 SQLite 模式下纯读不进入写队列；写操作继续集中治理。
- 后台 worker typed DB service 请求默认低优先级；网关非关键 side effects 写入不抢前台读。
- System API HTTP 路由补显式读写元数据，避免按 HTTP 方法误判；认证 touch、操作日志、last_used 等副作用拆入低优先级写路径或合并写路径。
- 认证 session、账号标签、HEAD/GET 等通用轻量读也按真实读处理；不让每个前端请求都因为鉴权或标签下拉重新撞主线程同步 SQLite。
- 修正管理列表和统计接口中的请求链路重活：
  - `accounts` 统计装饰锁等待治理。
  - `groups` 统计 / runtime 装饰读写隔离。
  - `api-keys` usage 装饰读写隔离。
  - `stats/usage-overview` 不在请求链路临时聚合明细或日表。
  - 账号运行态快照用短 TTL / stale-while-refresh，避免连续相同列表请求重复同步等待 runtime IPC。
- 补充回归测试覆盖“后台写不堵前台读”“纯读并发”“前端契约不变”。

### 本次不做

- 不删减前端字段，不让接口返回空装饰数据作为长期方案。
- 不用 `items: []`、空 stats Map、空 usage Map 这类伪成功响应掩盖 SQLite busy、锁等待、慢查询或后台任务延迟。
- 不把前端首屏请求拆掉作为主要修复手段；前端体验和契约优先。
- 不引入运行时旧 schema 兼容或自动迁移逻辑。
- 不把 PostgreSQL 真实服务器凭据写入文档、日志或代码。

## 关键设计

### 读写隔离原则

- 纯读：
  - 不进入写队列。
  - PostgreSQL 模式直接走 async pool 并发。
  - SQLite 模式不得长时间同步等待写锁；当前通过 query-only 只读连接和 SQLite read worker pool，把 busy wait/retry 放到 worker 子进程内，避免卡死 DB service 主事件循环。
- 写入：
  - SQLite 模式继续受写队列、批次和优先级保护。
  - PostgreSQL 模式依赖事务、唯一约束、行锁和连接池；只对确有资源顺序要求的写引入 keyed 串行。
- 后台维护：
  - 默认低优先级。
  - 必须小批次、可续跑、可超时。
- 不确定读写属性的 operation：
  - 先按写处理，避免把隐藏副作用放入并发读通道。

### System API 路由分类原则

- 不只按 HTTP 方法判断读写属性，路由需要显式标注：`noDb`、`read`、`readWithSideEffect`、`write`、`longRead`。
- `GET /auth/me`、所有经过 session touch 的已认证 GET、公开接口鉴权成功后的 `last_used_at` 更新，属于读请求夹带副作用，需要拆副作用或进入低优先级写路径。
- `POST /accounts/import/preview` 是预览读，不应因为 POST 自动进写队列。
- `POST /accounts/export` 如果记录操作日志，就是读 + 写副作用；不能按纯读处理。
- `GET /audit-logs/search-hot`、`GET /runtime-logs/grep` 属于长 IO / 长查询读，需要独立并发限制和 deadline，但不能降级为空结果。

### 前端契约原则

- 管理页面已有字段保持返回。
- 如果某字段成本高，应在后端用缓存、预聚合、读通道并发或后台刷新解决。
- 只有明确是“运行态不可观测”的接口才允许返回 `available:false` 之类状态；业务数据不能无提示返回空。

### SQLite 与 PostgreSQL 差异

- SQLite：
  - 文件级写锁和同步 `node:sqlite` 调用会放大阻塞。
  - 写必须集中治理；读要避免长 busy wait 卡住事件循环。
  - 读通道必须返回真实数据或明确错误；不能因为锁忙返回空统计、空列表或缺字段。
- PostgreSQL：
  - 不存在 SQLite 同类全库文件写锁。
  - 仍需关注连接池、热点行锁、长事务和慢查询。
  - 应用层不要无意义串行纯读。

## 风险与注意事项

- 部分 GET / 读函数可能隐含写入、缓存刷新或默认数据创建，分类时必须标为 `ambiguous` 或拆出副作用。
- SQLite 纯读即使不进写队列，也可能碰到文件锁；处理方式必须是不长时间同步卡住事件循环，而不是返回假数据。
- PostgreSQL 并发不是无限并发；连接池、行锁和慢查询仍需监控。
- 前端 fanout 可以后续优化体验，但不能作为替代后端读写隔离的主方案。
- 路由和 operation 分类必须保守，发现隐藏写先标 `readWithSideEffect` / `ambiguous`，再拆副作用；不能把会写状态的请求放入纯读通道。

## 完成总结

- DB service typed operation 已有显式读写分类，SQLite 只对写入和维护任务排队，纯读不进入写队列；PostgreSQL 不套 SQLite 全局队列。
- SQLite standalone 模式下，管理端主读、账户详情 / options / 测试状态、认证 session、账号标签、系统账户 target 解析、provider 低层读、运行日志索引读、公开设置、模型目录、授权 quota 精确读、active policies、OpenAI-compatible files / vector stores 安全纯读已进入 query-only read worker 子进程；读失败返回真实错误，不返回空列表、空统计或缺字段伪成功。
- SQLite read worker 读通道已改为 least-loaded 分发，同一查询连续 burst 不再固定挤到同一个 worker；写队列和默认 keyed worker 语义不变。
- 前端管理列表 DTO 契约保持稳定，API Key 列表不返回完整密钥字段，账号 / 分组 / API Key / 策略 / 代理 / 系统账户 / 供应商 / 设置 / 运行日志 / OpenAI-compatible 读路径都用回归验证真实数据返回。
- 账号运行态快照增加短 TTL / stale-while-refresh，连续管理列表请求不会重复同步等待 runtime IPC；gateway settings 读缓存、API Key quota 缓存、任务取消状态、health / cooldown 写边界、Codex context writer pool 等 owner 明确或带副作用路径未混入 read worker，避免破坏缓存失效、运行态一致性或任务状态语义。
- 必要验证已通过：后端 typecheck、SQLite read worker、DB service 读写分类、System API 读写元数据、SQLite System API burst、SQLite worker real load、System API performance smoke、远程 PG/Redis schema 重建和 33 个 PG smoke 矩阵。
