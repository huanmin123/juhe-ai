## 需求目标

- 账户首屏、翻页、刷新和系统账户切换不再预取代理 options。
- 账户列表和基础详情直接返回有权限展示的代理最小字段，冷启动不依赖浏览器 label cache。
- 单账户和批量编辑的代理下拉首次展开、搜索或已选启用项补齐时才请求 options。
- 操作日志和公开 API 日志建立从 SQL 到前端的专用 ListItem，详情继续按 ID 加载完整内容。
- 公开 API 日志前端、Node 和 Go 默认窗口统一为 50。
- Node 生产 owner 与 Go opt-in 路径保持公开契约等价，不改变 owner manifest 或生产切流状态。
- 用 SQLite 主线程/read worker、Node/Go 真实 PostgreSQL、前端行为和浏览器网络证据完成验收。

## 范围边界

本计划包含：

- 账户列表/基础详情的代理 ID、名称、类型、启用态和不可用语义。
- `/proxies/options` 的 keyword、limit、selectedIds、字段白名单和 Node/Go 等价。
- 操作日志管理/个人列表、权限内部列、targeted/all-users 合并和详情不变。
- 公开 API 日志列表字段、50 行默认窗口、筛选、详情不变。
- 前端代理远程候选资源、身份隔离缓存、搜索 debounce、竞态和失败重试。
- 权威接口、安全、迁移、测试和计划文档同步。

本计划不包含：

- 不改变 schema、日志捕获范围、数据保留、代理管理权或账户绑定规则。
- 不实现供应商列表、策略路由计数、首页统计、响应检查策略、系统设置、Chat API Key 或模型检查 options 的后续批次。
- 不调用真实模型，不使用模型密钥。
- 不部署、不切流、不操作生产；上线等待用户通知。

## Git 同步策略

1. 设计与计划提交后 fetch/merge 最新 `origin/master`。
2. 代理、操作日志、公开 API 日志各自形成逻辑提交；每个批次后同步 master。
3. 功能分支持续推送远程，不使用 rebase 改写已推历史，不强推。
4. 最终合并前再次 fetch；若 master 变化，先在功能分支 merge 并重验。
5. 在干净 master 工作区执行非快进合并或等价可追溯合并，最终验证后推送 `origin/master`。
6. Git 合并与推送不代表部署；不领取部署计划锁，不生成发布包，不切生产流量。
