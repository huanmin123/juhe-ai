## 已确认根因

1. `account-balance-refresh` 每分钟调度，单轮最多 100 个候选、并发 4、单账户上游截止 15 秒，最坏约 375 秒；调度器只记录重入跳过，造成长期“运行中”。
2. 余额候选内部异常与任务边界异常没有分层；生产复核进一步确认，单个候选 20 秒截止会把其余候选已完成的整批任务标成 `background_job_failed`，造成 `account-balance-refresh` 状态误报。
3. 余额跨 business/stats 两库部分提交可能清空下一次刷新时间但未落暂停快照，恢复队列会每分钟重复探测。
4. 系统指标队列表是异构队列字段的固定超集，缺失字段被转成 0；`consumers` 缺失也被转成 0，导致活跃数和大量指标伪造。Redis、重试、IPC、写入池的字段并非同一语义，不能直接删除真实来源。
5. 系统指标外层和 worker 快照内层都使用 1 秒截止时间，边界延迟会把整个运行态误判为不可观测。
6. 后台任务的 success/failure 仅按 Promise 是否 reject 统计，部分失败、无候选、入队拒绝和业务摘要没有单独口径；历史失败计数又被页面当成当前异常。
7. 生产一次 DB service 拥塞同时造成统计、代理、可用性同步任务失败；另有健康检查返回数据字段类型不符导致重试耗尽。

## 阶段顺序与边界

### 阶段一：运行态和后台任务稳定性

- 队列 DTO 改为能力/来源驱动：不适用字段返回 `undefined` 并显示 `-`；修复缺失 `consumers` 的活跃计算；补齐 normal-route 恢复探针；Redis 检查失败显示明确 unavailable 行；区分 expired、dropped、flush failure 和 retry。
- 系统指标快照增加 stale/age/来源信息，拆开外层与内层超时；任务行增加执行结果、最近失败时间、运行代次/启动时间，并保留历史计数但不再把历史计数当当前异常。
- `account-balance-refresh` 改为有界批次/运行预算，返回结构化执行摘要；明确达到候选截止时间显示为“部分失败”，候选扫描、租约、数据库、IPC、持久化和未知程序异常计为整项失败；收口余额跨库暂停提交，避免确定性 unsupported 重复探测；普通 due 候选增加有界游标/诊断。
- 修复健康检查 DB service 响应的字段类型错误并补字段级诊断。
- 不改变网关协议、账号状态机、余额业务状态定义，不在本阶段引入页面缓存或 Redis/PG 拓扑调整。

阶段一实现进度（2026-07-17）：

- [x] 队列可选指标保留 N/A，活跃值按 consumers/running/writer 能力读取；固定空列收敛为“容量 / 处理”和“异常累计”。
- [x] Redis 检查失败保留异常行，网关 expired 与 dropped 分离，普通路由恢复探针队列贯通 DTO。
- [x] runtime snapshot 增加 live 来源、采集时间、年龄和 stale；外层/内层超时留出端到端余量。
- [x] 后台任务展示本进程运行次数、最近开始、最近失败及恢复状态，历史失败明确为本进程累计。
- [x] 余额任务改为 12 个候选、4 并发、45 秒运行预算、20 秒候选截止；基础设施失败进入任务失败。
- [x] 调度器增加通用部分失败结果；余额候选截止超时不再把已完成批次误报为整项失败，页面单独展示部分失败次数与原因；余额查询归一与代理配置读取/持久化边界拆开，DB/IPC/租约错误继续冒泡。
- [x] 普通 due 使用 next_refresh_at/id 复合游标越过无效前缀。
- [x] 自动余额提交使用 next_refresh_at + updated_at 代次 CAS；PostgreSQL business/stats 跨 schema 同事务提交，旧超时结果不能覆盖新一轮。
- [x] PostgreSQL JSONB 账户时间计划规范化，修复健康检查“文本字段必须是字符串”。

### 阶段二：网关与账户状态

- 网关请求解析/流式失败使用结构化内部原因分类，保留现有客户端兼容文案；客户端/网关失败不得污染账号状态。
- 先实现失败避让的结构化结果和状态迁移，再实现临时不可调用有界探活开关。
- 恢复多 API Key 运行态 DTO、指纹和编辑页展示；补回归测试。

### 阶段三：性能基线

- 先物理隔离 Redis state/queue，再移除普通 PostgreSQL 查询的隐式事务；保持额度/最小业务写入与 outbox 的可靠边界。
- 之后优化统计 worker、DB service 请求预算和后台任务降载；所有性能改动以压测和生产观测为准，不删除功能或伪造空值。

### 阶段四：页面缓存与增量更新

- 先稳定 DTO/快照/revision，再接入 IndexedDB cache-first、30 秒轻量确认、字段投影、并发竞态控制和最近 7 天预热。
- 登录、验证码、一次性凭证和权限判定不进入通用页面缓存。

## 第一阶段验收

- 现有后台队列、系统指标、余额和 runtime snapshot 回归全部通过。
- synthetic 覆盖 `undefined`/0、不同队列类型、Redis 检查失败、worker 缺失、快照过期、外层超时、任务永不结束、候选级部分失败、任务边界真实失败、跨库部分提交和 due 无效前缀。
- 本地 typecheck、build、发布包校验和启动健康通过。
- 生产临时接管发布后验证本机、内网、公网 health；观察窗口内 `account-balance-refresh` 不再持续重入，队列不适用字段不再显示伪 0，历史失败与当前异常可区分。

## 2026-07-17 生产复核补充

- 生产 `juhe-ai.worker.log` 显示，`account-balance-refresh` 一轮选择 12 个候选，其中 1 个候选达到截止时间，11 个已完成；旧实现随后抛出整项 `background_job_failed`，下一轮又恢复为完整成功。
- 该现象证明任务执行器本身仍健康，错误发生在单候选边界；因此使用通用 `partial` outcome 保留可见告警，同时不增加后台任务 `failureCount`。
- `api-key-availability-schedule-status-sync` 和 `account-availability-schedule-status-sync` 的 DB service 超时仍属于真正任务边界失败，不纳入部分失败降级。
- 回归使用真实 SQLite trigger 验证统计快照写入失败会冒泡，并用注入代理 repository 失败验证代理配置 DB 错误不会被归一成账户余额 transient。

## 回滚与反向合并

- 每阶段独立 release、独立恢复点和独立验证；任何阶段失败只回滚该阶段。
- 发布目标为 `master`；发布完成后把 `master` 反向合并到 `feature/20260706-go`，不把 feature 分支的未完成设计直接发布。
