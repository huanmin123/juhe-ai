# 网关流式性能瓶颈分析报告（2026-06-17）

## 1. 结论

本次使用本机真实 mock OpenAI 上游、临时 SQLite 数据库和真实网关处理函数，对 `/v1/responses` 流式链路做专项压测。测试不消耗真实 OpenAI 额度，结论来自 `reports/` 下的 JSON 报告和 `reports/cpu-profiles/` 下的 CPU profile。

many-events 场景固定为：`200` 个 SSE chunk、chunk 间隔 `2ms`、响应体 `4096 bytes`、模拟上游首延迟 `20ms`、并发 `100,200`。

最终采纳优化后，重复压测结果为：

| 报告 | 并发 | 成功 QPS | p95 | p99 | 事件循环 p99 | CPU/请求 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| `reports/perf-stream-many-events-final-repeat-2026-06-17.json` | 100 | `158.45` | `666.270ms` | `674.380ms` | `23.151ms` | `7.1893ms` |
| `reports/perf-stream-many-events-final-repeat-2026-06-17.json` | 200 | `133.91` | `1691.244ms` | `2017.440ms` | `41.681ms` | `8.2414ms` |

对比当前可复现的优化前参考点 `reports/perf-stream-many-events-after-usage-shard-transaction-2026-06-17.json`：

- 并发 100：成功 QPS 从 `145.32` 到 `158.45`，p95 从 `726.583ms` 到 `666.270ms`。
- 并发 200：成功 QPS 从 `144.29` 到 `133.91`，p95 从 `1430.165ms` 到 `1691.244ms`，说明高并发下仍受写出、事件循环和本机负载波动影响。
- `writev` 仍是最大热点；cork/uncork 对照已验证会明显变慢，未采纳。

因此当前结论限定为：按 `after-usage-shard-transaction` 与 `final-repeat` 两份同参报告比较，并发 100 指标改善；并发 200 指标退化且波动较大，不能把单次高点作为容量承诺。各项代码优化是否采纳主要看 CPU profile 热点下降和回归测试是否覆盖，而不是只看单次 QPS。剩余主要瓶颈仍是高频小块写出、流式主循环、响应检查/流事件解析、审计镜像和 SQLite 写入抖动。

## 6. 当前剩余瓶颈

- `writev` 仍是最大热点，说明真实瓶颈在高频小 chunk 下游写出和 Node stream/socket 层。
- `pipeUpstreamStream` 主循环仍承担读取、响应检查、流式解析、捕获、写出和终止判断，后续需要继续拆分测量。
- 高并发 200 档不稳定，最终报告不应承诺 200 并发容量；需要更长时长、多轮和生产拓扑复测。
- 审计热搜索 mirror 已降本，但审计 payload 本身仍会带来写入与捕获成本。
- CPU profile 仍显示 `JSON.parse` 总量较高，剩余来源包括终止事件、usage、URL/模块内部解析和非 fast path 事件。

## 8. 下一步建议

1. 在目标部署机器上跑 30-60 秒多轮压测，补齐真实 DB service / worker / 磁盘 / IPC 影响。
2. 继续研究小 chunk 写出策略，但不能采用已验证变慢的简单 cork/uncork；需要面向 SSE 的自适应微批，并保留首 token 体验。
3. 对审计 payload 捕获继续做策略化降本，区分排障必需字段、抽样正文和普通成功 metadata。
4. 继续扩大 fast path 到常见终止事件和 usage 事件，但必须保持失败事件、默认策略和配置策略回归覆盖。
