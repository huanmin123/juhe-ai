## 迁移顺序

1. 先收敛 P0：`account`、`system-account`、`gateway`、`db-service`。这些域决定高性能模式能否真正隔离 SQLite 和内存状态。
2. 再收敛 P1 记录与统计：audit、usage、operation/public/runtime log、record maintenance、usage stats、client-ip stats、system metrics。
3. 然后收敛 P1/P2 管理域：provider/model、proxy、group、api-key、authorization、announcement、route strategy、settings、model check。
4. 最后处理基础设施封口：`storage-repository-facade` 只能保留为 adapter 内部组合入口；业务模块不能继续直接新增引用。

## 静态守卫

- `test:storage-adapter-boundary` 固定本清单必须全部归类，避免新增未登记的数据库、Redis、队列直接调用点。
- 运行态源码禁止顶层值导入 `node:sqlite`；SQLite 只能由 standalone adapter 或 SQLite 基础设施懒加载。
- 运行态源码禁止绕过 `shared/redis-client.ts` 或 `storage/postgres-client.ts` 直接加载 `redis` / `pg` 驱动。
- 不允许为未来迁移预建只有 `planned` descriptor、没有生产消费者和真实方法实现的 runtime / adapter 骨架。
- 后续每迁移一个 Store Port，必须先固定真实消费者和契约测试，再把该业务域的直接调用点从业务模块移动到 adapter / storage infrastructure 白名单内。
