## 需求目标

- 保持 `standalone` 的轻量单机启动和 SQLite 行为不变。
- 在单台生产 Mac 的 `performance` 模式中建立 3 Gateway、2 Usage Worker、2 Log
  Worker、1 Stats Worker、1 Ops Worker 的默认多进程单元。
- 切开 Gateway、usage、日志和统计事件循环，防止旁路积压拖死 AI 会话。
- 修复 Redis producer client 超时后不自愈、usage 入队失败无持久补偿、日志放大和
  DB service 短暂不可用直接影响网关的问题。
- 提供 Nginx、launchd、健康检查、摘流、回滚和生产验证材料。

### 10 分钟高并发稳定性门禁

- [x] 先按并发阶梯寻找最高稳定档，再在该档运行不少于 10 分钟的混合真实入口负载；
  负载同时包含普通 Responses / Chat、大请求体、慢 SSE、成功审计、Usage、运行日志和
  管理端读取，不能用关闭日志或降低审计采样掩盖瓶颈。
- [x] Control 直连 `/__aisys__/health`、`/__aisys__/api/health` 和三个 Gateway 直连健康
  均为零错误、零超时、零 `503/504`，单次最大总耗时不超过 `500ms`，`p99` 不超过
  `250ms`。Nginx ingress 已承担全部正式数据面请求，但 ingress health 单列采样保留到生产
  上线窗口验证。
- [x] 使用记录、统计概览、AI 账户、审计日志和运行日志等正常管理端读取在负载期间零错误、
  零超时、零 `503/504`；每个接口 `p95 <= 500ms`、`p99 <= 1000ms`、最大耗时
  `<= 2000ms`。基线与负载期分别采样，报告延迟放大倍数。
- [x] 普通 AI 非流式请求不能因旁路积压出现数秒停顿；慢 SSE 单独统计首包时间和完整流时长，
  不能把正常长流总时长误报为卡顿。SSE 首包 `p99` 目标不超过 `500ms`、最大不超过
  `1000ms`，具体容量结论以同机 Mock AI 实测为准。
- [x] 10 分钟内所有 Node 角色持续存活且 ready，Gateway、control、DB service、Usage、Log、
  Stats 和 Ops 的事件循环、RSS、CPU、文件 I/O 都有逐秒证据；不得出现持续增长且不能回落的
  RSS、文件 backlog、Redis Stream `lag/pending` 或 PostgreSQL 锁等待。
- [x] 请求结束并进入 settle 窗口后，五类 Redis Stream 都达到 `XLEN=0`、`pending=0`、
  `lag=0`；Usage、审计和公开日志实际落库数量与稳定事件 ID 一致，PostgreSQL deadlock
  增量为 `0`；审计引用事实以 `audit_payload_refs` 为准，兼容字段 `ref_count` 固定为 `0`，
  验收后 54,409 个元数据与文件一一对应且无悬空引用、缺文件或旧孤儿。
- [x] 独立探针进程承担健康与管理面计时，不能和 Mock upstream、大包读取及数据面发压共享
  同一个 Node 事件循环，避免压测端自身停顿污染隔离结论。
