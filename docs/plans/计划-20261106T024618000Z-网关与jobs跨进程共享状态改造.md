# 网关与 jobs 跨进程共享状态改造计划

> 状态：**Tier 1 已实施（2026-11-06）：B0 共享契约包 + B1 OAuth 刷新 per-account 跨进程锁 + B2 OAuth 凭据版本投影；Tier 2 已实施：B3a 时间计划闸门版本栅栏 + B3b API Key 运行态写方序号 + B4 账户状态/冷却版本栅栏（用共享序号触发 gateway 重载 PG，不复制状态字段）；S13 OAuth 刷新失败状态已改为 gateway 只读 jobs 共享退避；B5 settings 版本已实施；B6 不做**。实施记录见 §11。
>
> 目标：把 gateway 与 jobs 之间“靠 60s 缓存过期、轮询、账户状态副作用或重复外部调用”变相传递的状态，收敛为 **Redis 共享投影/版本/锁 + PG 事实源** 的间接解耦；不引入 gateway↔jobs 直接 import、RPC 或进程看护。
>
> 关联：[代理池设计](../functions/代理池设计.md) §7.4 C7-R（本计划的首个已落地范式）、[PostgreSQL 与 Redis 高性能模式设计](../functions/PostgreSQL与Redis高性能模式设计.md)、[时间计划闸门与账户状态解耦设计](../functions/时间计划闸门与账户状态解耦设计.md)、[官方可落地OAuth账户接入设计](../functions/官方可落地OAuth账户接入设计.md)、[账号健康检测设计](../functions/账号健康检测设计.md)、[Go 三项目架构基线](../architecture/Go三项目架构基线.md)、[待办与阻塞事项](../待办与阻塞事项.md) T65/T112。

## 1. 背景与判断

### 1.1 现状

- gateway 与 jobs 是独立进程，架构基线禁止直接 import；两者只能通过 PG 稳定契约、Redis 运行态、共享文件或一次性维护输入交互。
- 现有大量状态流是 **jobs 写 PG → gateway 60s revalidate / 2min last-good 缓存**，或 **gateway 写 PG → jobs 60s settings 缓存**。这在正常情况下可用，但把“状态多久可见”绑定在缓存 TTL 上：
  - OAuth token 轮换后，gateway 最长 60s 仍可能拿旧 access token；
  - 时间计划闸门翻转依赖 jobs 10s 同步 + gateway 60s 缓存；
  - API Key 运行态/冷却变化可能在水合快照里滞后；
  - jobs 读设置也有 60s 进程内缓存，gateway 写设置后 jobs 不保证立即看到；
  - OAuth 手动/自动刷新与 jobs 定时保活没有跨进程 per-account 锁，rotation 型 refresh token 存在双打风险。
- 这些不是“业务必须慢”，而是**跨进程状态传播机制缺失**。用更短 TTL、更多轮询、账户状态副作用或调度特判去补，会牺牲性能、增加写放大或让调度语义变形。

### 1.2 判断

- Redis 作为间接共享层是合适的：两端都已依赖 Redis，且已有成熟范式（circuit 状态、key-model 状态、代理池 C7-R）。
- 但 **PG 仍是事实源**，Redis 只放小型投影、版本号或锁；不得把 token/密码/完整凭据写入 Redis。
- 本次不做“所有状态都上 Redis”的大迁移，只改**已确认有可见性/正确性代价**的域；先测量，再扩面。

### 1.3 非目标

- 不引入 gateway↔jobs 直接 RPC、pub/sub 事件总线或共享进程。
- 不把 Redis 变成业务事实源；Redis 丢失后必须能回 PG。
- 不把 token、refresh token、密码、完整凭据写入 Redis。
- 不改变账户调度算法、路由策略、分组、会话亲和或错误策略。
- 不新增 feature flag；每个域按“交付/未交付”推进。
- 不重做任务队列；媒体任务、账户测试任务等 PG 任务面不在本期。
- 不为了“统一”而迁移没有可见性问题的域。

## 3. 通用机制设计

### 3.1 三种模式

**A. 实体状态投影（entity state）**

适用于账户、API Key、代理成员等“单个实体状态变化，读者下一次请求/任务就要看到”的场景。

```text
key:   juhe-ai:{<namespace>}:state:<domain>:<entity_id>
value: 小型 JSON 或字符串（status / cooldown / gate / revision / updated_at）
TTL:   5–10 分钟，按域定义；写方每次状态变化刷新
写方:  PG 提交成功后 best-effort 写；写失败 best-effort 删除旧键，让读者回退 PG
读方:  批量 MGET/pipeline；命中且版本有效则用投影；缺失/错误回退 PG
```

**B. 粗粒度版本（coarse version）**

适用于 settings、全局配置等“读方已有 60s 缓存，只需要知道是否变化”的场景。

```text
key:   juhe-ai:{<namespace>}:version:<domain>:<scope>
value: 单调递增整数
写方:  PG 提交成功后 INCR/单调 SET
读方:  使用本地缓存前 GET/批量读；版本变化则丢弃缓存并回 PG
```

**C. 跨进程锁（lock）**

适用于 OAuth 刷新等“同一实体不能并发打外部端点”的场景。

```text
key:   juhe-ai:{<namespace>}:lock:<domain>:<entity_id>
方式:  SET NX PX；value 为随机 token；释放时 compare-and-delete
TTL:   覆盖一次外部操作的最坏时长（OAuth 刷新建议 30–60s）
失败:  拿不到锁则跳过/等待下一轮；不重复打 token 端点
```

### 3.2 契约规则

1. **PG 是事实源**：Redis 投影/版本/锁都不改变业务事实；Redis 丢键、过期、故障时必须能回 PG 或 fail-closed。
2. **不直接耦合**：jobs 不导入 gateway 内部包，gateway 不导入 jobs 内部包；键名、值形状、TTL、版本语义放在 `backend-go/shared/platform/` 的稳定契约包（建议 `crossprocessstate` 或 `staterevision`），只含 key codec/类型/常量，不含业务编排。
3. **不放秘密**：Redis 不写 access token、refresh token、密码、完整凭据、错误原文；只写状态、布尔、闸门、修订号、时间。
4. **写后投影**：PG 事务提交成功后再写 Redis；写失败不改变 PG 成功，记录告警并 best-effort 删除旧键；读者回退 PG。
5. **读时兜底**：Redis 读超时（建议 50–100ms）按缺失处理；缺失/错误回 PG；PG 也不可用时按域定义 fail-closed。
6. **批量**：同一请求/任务内按实体批量 MGET/pipeline；不允许逐账户 N 次往返。
7. **单调版本**：版本号只增不减；锁释放用 token CAS；投影值带 `updated_at`/`revision`，便于诊断乱序。
8. **无 feature flag**：每个域直接交付；未交付的域保持现状，不靠开关分流。
9. **可观测**：写失败、读回退、版本不匹配、锁竞争、锁超时均记录结构化日志/计数；不记录秘密。
10. **多实例**：Redis 是共享层；gateway 多实例通过同一键收敛；jobs 单活；锁用于跨实例互斥。

### 3.3 读者接入点

- gateway 候选/预检：按候选账户/Key 批量读投影，覆盖缓存快照中的状态字段；命中 `dead`/`gate` 关闭/冷却未过期时直接过滤，不再依赖 60s 缓存。
- gateway 运行态缓存：对 credential revision/settings version 做读前版本检查；版本变化时只重载相关账户/设置，不整组失效。
- jobs settings reader：使用 60s 缓存前检查版本；变化则回 PG。
- OAuth refresh：先拿 per-account 锁；拿不到则跳过/延后，不重复打 token 端点。

### 3.4 失败语义

| 场景 | 行为 |
| --- | --- |
| Redis 键缺失 | 回退 PG；PG 正常则继续 |
| Redis 读超时/错误 | 按缺失处理，回退 PG；记录 `state_projection_fallback` |
| Redis 写失败 | PG 成功不回滚；best-effort 删除旧键；记录 `state_projection_write_failed`；下一轮重试 |
| Redis + PG 都不可用（调度相关） | fail-closed，不直连、不按旧状态放行 |
| 锁被占用 | 跳过/延后；不重复外部调用；记录 `state_lock_contended` |
| 锁后端不可用 | 按域定义：OAuth 回退现有 PG 任务租约 + config_revision CAS（不因锁故障完全阻断），并告警；严格互斥域可 fail-closed |
| 锁持有者崩溃 | TTL 自动释放；下一轮重试 |

### 4.1 不建议改造的理由

- **S6 余额**：列表是 PG 直读，没有 60s 缓存；加 Redis 投影只会增加写放大，不会改善可见性。
- **S7 任务状态**：任务面是异步任务队列，轮询是产品语义的一部分；换成 Redis 通知需要重做任务生命周期、重试和终态回填，收益与风险不匹配。
- **S8 可用性投影**：当前无消费方；先等消费方，再决定是否需要 Redis 投影。
- **S9 模型目录**：J3b 是 gateway 进程内 owner，不存在 jobs→gateway 状态传播。
- **S10-S12**：已经是 Redis 共享、fresh PG 读或持久文件队列，不应为了“统一”而改。
- **S13 OAuth keepalive 失败状态**：已取证并实施 gateway 只读 jobs 共享退避（shared/platform/oauthfailure 固化键形状与 revision 守卫）；gateway 自身上游失败仍只记进程内 5min，不反向写 jobs 的调度账本，避免 gateway 影响 jobs 的退避/计数策略。

## 5. 分批实施计划

> 每批独立交付、独立验收；不做 feature flag。B0 是共用基座，B1 可与 B0 并行设计但依赖其锁契约。

**安全分级（推荐裁决）**

- **Tier 1（低风险，建议先做）**：B0 + B1 + B2。只影响 OAuth 刷新互斥和凭据刷新可见性；不改候选过滤、不新增调度规则；PG 任务租约/config_revision CAS 仍是兜底。
- **Tier 2（需等价性验证后再做）**：B3（API Key/闸门）→ B4（账户状态/冷却）。这两项会改变候选/preflight 读到的状态新鲜度，必须证明 Redis 路径与 PG 路径的判定完全一致；唯一允许的差异是“更早看到 PG 已提交的状态”。任何不一致即停止。
- **Tier 3（暂缓/测量）**：B5 settings 版本、B6 观察项。settings 60s 对功能影响小，先测量再决定；B6 不默认实施。

**不改变功能的硬约束**

1. 投影只做 PG 的只读加速/新鲜化，不引入新的判定字段、默认值或调度规则；同一候选的 Redis 路径与 PG 路径必须输出同一 decision。
2. Redis 缺失/读超时/错误 -> 回 PG；Redis+PG 都不可用 -> fail-closed；不得用旧 Redis 值放行。
3. 写序固定 PG 提交成功 -> Redis 投影；Redis 写失败 best-effort 删除旧键，读者回 PG；版本/updated_at 单调，防乱序覆盖。
4. 不改变现有过滤条件、优先级、冷却语义和错误策略；只替换“从哪里读同一状态”。
5. 每批必须过：单元、真实 PG/Redis 集成、失败注入、并发、dev 端到端、等价性对照；任一 mismatch 停止，不带病上线。
6. 不放 token/密码/完整凭据；不新增 gateway↔jobs 直接 import/RPC；共享包只放契约。
7. 性能门槛：每请求最多一次批量 Redis 读，50–100ms 超时；不相关请求零额外读；p99 不因新增读显著退化。

### B0：共享契约包与观测基座

- 范围：`backend-go/shared/platform/crossprocessstate`（名称待定）——key codec、域/实体常量、TTL、版本/锁原语、批量读 helper、错误分类、日志字段；只含契约，不含 gateway/jobs 业务。
- 交付：
  - `Key(domain, entity, id)` / `VersionKey(domain, scope)` / `LockKey(domain, id)`；
  - `MGetStates` / `GetVersion` / `BumpVersion` / `TryLock` / `Unlock`；
  - 50–100ms 读超时、SET NX PX 锁、token CAS 释放；
  - 单元测试 + miniredis/真实 Redis 集成测试；键空间 golden。
- 验收：gateway/jobs 均不 import 对方内部包；共享包不 import 任一项目；键 shape 测试锁定；无秘密。
- 风险：过度抽象。约束：只放 key/类型/原语，不放业务判断。

### B1：OAuth 刷新 per-account 锁（P0）

- 写方/读方：gateway `oauthmgmt` 手动/自动刷新、jobs `oauthrefresh` 定时保活。
- 契约：`...:lock:oauth-refresh:<source_account_id>`；SET NX PX 30–60s；value 随机 token；释放 compare-delete。
- 行为：锁被占用 -> 跳过本轮/延后，不重复打 token 端点；锁后端不可用 -> 回退现有 PG 任务租约 + config_revision CAS（由 CAS 兜底最坏情况），记录告警；拿到锁后仍用现有 PG CAS。
- 验收：并发 gateway+jobs 刷新同一账户，只有一个打 token 端点；失败/超时释放；锁竞争日志；现有 OAuth 回归全绿。
- 风险：锁 TTL 过短导致双打、过长导致恢复延迟；用实测刷新 P99 定 TTL，建议 60s 并保留 PG CAS 兜底。

### B2：OAuth 凭据版本（P0）

- 写方：jobs `oauthrefresh` 刷新成功、gateway `oauthmgmt` 手动/自动刷新成功后，把 `...:version:account-credentials:<account_id>` 单调推进到该次提交的 `config_revision`（`SET max`；与数据行 revision 同值，读者可检测“读到旧数据、读到新版本”的装载竞态）。
- 读方：gateway 在候选准备/运行态读取时批量检查版本；版本变化则让该账户所在 runtime/openAI-accounts 条目重载（必要时整组重载），只影响相关组/API key，不要求逐账户热替换。
- 回退：Redis 缺失/错误 -> 现有 60s 缓存或 PG 读；不因 Redis 故障阻断请求。
- 验收：jobs 刷新 -> gateway 下一次请求使用新 token；Redis 缺失 -> PG；Redis 故障 -> 旧缓存/PG 兜底；无 token 写入 Redis。
- 注意：只放 revision，不放 token；gateway 的 `auto_refresh` 与 jobs 的 keepalive 都必须 bump，避免双写不一致。

### B3：API Key 运行态 + 时间计划闸门投影（P0/P1）

- 写方：jobs `oauthrefresh/availability.go` 写 gate；jobs `accounthealth`/gateway `accountkeystates` 写 Key 运行态；gateway 请求失败写 Key 状态时同步投影。
- 键：
  - `...:state:account-gate:<account_id>` = 0/1/NULL + updated_at；
  - `...:state:api-key:<account_id>:<fingerprint>` = status/cooldown_until/next_probe_at/revision；
  - 可选 `...:version:api-key-states:<account_id>` 粗粒度版本，减少逐 Key 读。
- 读方：gateway 候选准备时批量 MGET；gate 关闭或 Key 状态非 active/冷却中 -> 过滤；Redis 缺失回 PG。
- 验收：jobs 翻 gate -> gateway 下一次请求即拦截；jobs 标记 Key 冷却 -> 下一次请求跳过；Redis 缺失/故障回 PG；无秘密。
- 注意：Key 状态写入方多（gateway/jobs），必须统一走共享 helper；PG 仍是事实源，投影只做读加速/可见性。

### B4：账户状态/冷却投影（P1）

- 写方：jobs `accounthealth/projection.go`、jobs `oauthrefresh/store.go`（`MarkAccountFailureState` / `ClearAccountFailureState`）；gateway 请求失败/恢复路径（`gatewayaccounteffects` 等现有账户状态写面）多实例投影未做。
- 键：本期落地为纯序号 `...:version:state:account:<account_id>`（INCR + TTL），不复制 status/cooldown payload；PG 仍是唯一状态事实源。
- 读方：gateway runtime 缓存命中时合并 MGET，序号变化即重载 PG 快照；候选过滤复用既有 SQL。Redis 缺失/失败回退 60s 窗口。
- 验收：jobs 写 temporary_unavailable/error/恢复 active -> gateway 正常路径下一次请求按新状态过滤；装载与写入并发时最坏 60s；Redis 故障回 PG/既有窗口。
- 注意：不要用 Redis 替代 PG 写；写序固定 PG 提交成功 -> bump 序号；bump 失败只告警，不回滚业务写。

### B5：Settings 版本（P1/P2）

- 写方：gateway settings 写路径、jobs `upstream-client-version-refresh`、其他 `system_settings` writer。
- 键：`...:version:settings:<system_account_id>` 单调递增。
- 读方：gateway settings/runtime settings 读前检查版本；jobs `jobssettings` 使用 60s 缓存前检查版本；变化则回 PG。
- 验收：gateway 写设置 -> jobs 下一次 settings 读看到；jobs 自动版本更新 -> gateway 下一次 settings 读看到；Redis 缺失/故障回 PG；无秘密。
- 注意：settings 不是每请求都读；版本检查可搭现有 runtime invalidation sync，避免新增过多 GET。

### B6：观察项（不默认实施）

- 余额快照：已有 PG 直读；只有出现实际显示延迟证据时再立项。
- 媒体/账户测试任务状态：如未来要降低 UI 轮询成本，另立“任务通知/状态键”设计，不与本计划混做。
- 账户可用性投影：等消费方出现。
- 模型目录：J3b gateway 内部，不涉及。
- 多实例租约一致性：代理池 C7-R 的 v1 单实例边界；多实例另立设计。

## 6. 验收与测试

### 6.1 通用验收

- **可见性**：jobs/gateway 写入后，读者下一次请求/任务可见；具体上界按域定义（B1/B2/B3 目标“下一次请求”；B4/B5 目标“下一次读取”）。
- **隔离**：`go-project-boundary-regression.mjs` 仍绿；gateway/jobs 无直接 import；共享包无反向依赖。
- **回退**：Redis 键缺失、读超时、写失败、Redis 整体不可用分别有测试；调度相关域在 Redis+PG 都不可用时 fail-closed。
- **无秘密**：扫描 Redis 值/日志，确认无 token/密码/完整凭据。
- **性能**：每个域最多一次批量 Redis 读；只对相关候选/Key 读；不相关请求（无该域状态）零额外读；p99 不因新增读显著退化。
- **并发**：B1 锁并发、B2/B3/B4 双写竞争、版本乱序、锁 TTL 过期均有测试。
- **兼容**：旧二进制/旧 Redis 键共存；新键缺失时行为回退现状；不要求 schema revision（除非某域需要新表，另行评审）。

### 6.2 分层测试

- 单元：key codec、版本单调、锁 CAS、TTL、回退分支。
- 集成：miniredis + 真实 Redis（若项目已有测试口径）；PG 回退用 pgtestkit。
- 端到端：dev PG/Redis 起 gateway+jobs；jobs 写状态 -> gateway 请求；gateway 写状态 -> jobs 读；Redis 断开 -> PG 兜底。
- 回归：OAuth、时间计划、API Key 轮换、账户健康、settings 各自现有包全绿。

## 7. 风险与回滚

| 风险 | 控制 |
| --- | --- |
| Redis 成为新热路径 | 批量读、50–100ms 超时、缺失回 PG；只对目标账户/Key 读 |
| 双写不一致 | PG 先写、Redis 后写；写失败删除旧键；版本单调；读侧回 PG |
| 投影旧值覆盖新值 | 版本/updated_at 单调；写方 CAS/版本；乱序丢弃 |
| 锁 TTL 不当 | 实测刷新 P99；60s 起步；PG CAS 兜底；锁竞争日志 |
| 共享包变成业务耦合 | 只放 key/类型/原语；review 时检查无业务编排 |
| Redis 故障放大 | 回退 PG；调度相关双不可用 fail-closed；熔断/告警 |
| 范围过大 | 按 B1-B5 分批；每批独立验收；B6 不默认做 |

回滚：按域回退二进制即可；Redis 键是附加投影/版本/锁，旧二进制不读即无害；PG 事实未变。若某域读侧已上线但写侧异常，先回退读侧（代码回退），不要删 PG 数据。无 feature flag。

### 11.2 实施中修正的认知

- B2 的读点修正（复审发现）：`gatewayruntimecache` 的 accounts 列表缓存（`accountsCache`）在共享缓存模式（`cacheDriver=redis`）下恒禁用，但主派发使用的是 **runtime 缓存**（`runtime.Accounts`，60s TTL、进程内、共享模式仍启用；preflight 直接用 `runtime.Accounts` 作候选）。若只挂 accounts 缓存，B2 在生产没有消费者。实现因此同时把版本快照挂到 runtime 条目与 accounts 条目：`/v1` 主路径命中 runtime 时比较版本并同步重载（复用既有 runtime 单飞），accounts 路径仅在进程缓存模式生效；accounts 缓存禁用时不读版本键，避免无消费方的每请求 Redis 往返。
- 版本号改为与 PG `config_revision` 同值（单调 `SET max`），读者可在装载数据后检测“读到旧数据、读到新版本”的竞态：快照版本大于数据行 `config_revision` 时，accounts 路径重读一次、runtime 路径直接丢弃版本快照；两路最终仍未收敛时都退回 60s 窗口（不永久禁用缓存）。这关闭了“写方在数据读与版本读之间提交”导致旧凭据被缓存 60s 的窗口，同时避免 PG 回滚/旧快照导入使版本永久领先时退化为每请求重装载。
- 50ms 读预算与 2s bump/释放预算依赖 `ContextTimeoutEnabled`：go-redis 默认关闭时会把命令 ctx 换成 Background，上下文预算不生效。OAuth 跨进程状态使用独立 Redis 客户端并显式开启该选项（gateway `chain_runtime.go`、jobs `worker_oauth_crossprocess.go`），未改其它运行态客户端语义。
- Tier 2 实现选择“**状态版本栅栏 + PG 重载**”而非计划 §B3/B4 的“状态字段 Redis 投影”：写方（jobs 闸门同步、J1 outcome 投影）在 PG 提交后只递增共享序号；gateway runtime 缓存把序号与凭据版本合并为一次 MGET，变化即用现有 `ReadGatewayRuntime`/候选 SQL 重载 PG 快照。好处是过滤/冷却/闸门/授权语义完全复用既有 PG 路径，**同一候选的 Redis 路径与 PG 路径天然输出同一 decision**（版本只决定何时重读），不需要在 gateway 复制一套状态判定；代价是变化时一次 PG 重载，但闸门翻转与账户健康状态变化频率低，且省掉状态 payload 的双写一致性与秘密边界。API Key 运行态状态（key status/cooldown/next_probe）写方在 gateway 单进程，暂未纳入。
- 状态序号是纯 `INCR`，没有可与 PG 行 revision 对值的锚点，因此不能复用 B2 的“版本领先数据 `config_revision`”竞态检测：若写方恰好在 gateway 读 PG 与读序号之间提交，该次变化最坏退回既有 60 秒窗口（不会比改造前更差），正常路径下一次请求即重载。未为此增加二次 PG 重读或全局 epoch，避免把低频状态变化放大成装载风暴；可见性契约因此表述为“通常下一次请求，装载并发时最坏 60 秒”。
- B1 的锁 TTL 采用 60s（与 token 端点预算对齐）；极端情况下锁先过期、双方并发换发时仍由 PG `config_revision` CAS 收敛，最坏结果为一次多余 token 调用，不会双写成功。
- jobs 的 OAuth 家族、健康投影与 retention 孤儿删除共用 `workerAssembly` 缓存的同一个 OAuth 跨进程 Redis 客户端（`oauthCrossProcessState` 首次构造后复用并只注册一次 closer），避免每个家族各开一个连接池；B5 的 settings 版本客户端只是在同一 Redis 客户端上派生 `<namespace>:settings` 域，不新增连接池。S13 的 gateway 读取复用 gateway 已有的 `ContextTimeoutEnabled` OAuth Redis 客户端。
- B3b 认知修正：原暂缓理由“Key 运行态写方在 gateway 单进程”与代码不符——jobs `proberepo` 的冷却复测 `RecordKeySuccess/Failure` 是同一张 `account_api_key_runtime_states` 的生产写方，jobs→gateway 最长 60s（持续失败 2min）无信号。实施复用既有 `version:state:account:<id>`，按来源+授权实例展开 bump；不新增 Key 状态 payload/键 shape，gateway 读路径零改动。相邻的 precheck `accounts.status` 写也补 bump；`DeferKeyProbe` 仅推进 `next_probe_at`，不 bump。
- B5 认知修正：gateway↔gateway 的 `system_settings` 已由 `inval` 共享版本覆盖；真实缺口是 gateway→jobs（`jobssettings` 每键 60s 且不能接总线）。版本键落在独立 `settings` 域（两端同域对齐，避免与 OAuth 域混用）；另修 peer 只在启动应用 `upstreamClientVersionOverrides` 的无界滞后：失效回调保持纯内存清缓存，upstream 覆盖重放改为单 worker 后台异步刷新（运行中触发置 dirty、完成后补跑一轮，panic 经 `safego` 兜底），避免把 `system_settings` 查询插到 runtime 读前失效同步路径，也不丢弃尾随失效。`global_settings` 品牌保持 60s 边界，不纳入本期版本键。
- 网关侧请求失败写账户冷却走既有 `inval` 共享版本总线（`chain_error_policy_effects.go` 的 `bus.Invalidate(TopicGatewayRuntime)`），不接状态序号；多实例按 inval 同步，无需重复造栅栏。
