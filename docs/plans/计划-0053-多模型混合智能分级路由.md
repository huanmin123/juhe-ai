## 需求目标

- 背景：大量请求并不需要顶级模型，用户希望一个本地 API Key 能按请求难度自动选择低价、中价或高价模型，降低平均调用成本。
- 目标：建立 API Key 级混合智能路由能力，以低价评分模型输出 `1-10` 级，再按等级选择目标模型和真实分组。
- 交付物：一次性完整功能闭环，包括长期功能设计、当前 schema、API Key 配置接口、网关评分路由、缓存亲和、成本统计、审计记录、前端配置和完整验证。

## 交付原则

- 不分阶段上线，不做“先能评分、以后再补统计 / 审计 / 前端 / 缓存亲和”的半成品。
- `routeMode = hybrid` 一旦出现在可用 UI 或可调用 API 中，必须能完成完整请求链路、成本入账、审计追踪和统计展示。
- 任务清单只表示同一版本内的工程拆解，不表示可以拆成多个可发布阶段。
- 运行路径直接按当前 schema 和当前 API 契约实现，不为旧字段、旧配置或旧 UI 流程保留兼容分支。

## 方案概述

- API Key 新增 `routeMode = normal | hybrid`。
- `normal` 维持现有行为。
- `hybrid` 使用评分模型读取完整请求上下文，输出 `1-10` 等级。
- 等级规则把等级范围映射到目标模型。
- 当前 API Key 的 active 分组绑定作为候选分组池，路由只在这个池内选择可承接目标模型的真实分组。
- 目标模型确定后，只改写请求体顶层 `model`，再进入现有账号调度。
- 同一会话维护模型和缓存亲和，避免分数小幅波动导致频繁切模型。

## 风险与注意事项

- 评分模型本身会增加固定成本；低档请求比例不足时收益会下降。
- 完整上下文评分成本可能较高；评分缓存已作为低风险优化落地，规则预判仍只能作为后续可选增强，不能替代动态评分。
- 频繁跨模型会破坏上游缓存，必须默认启用模型亲和和缓存亲和。
- 模型价格来自模型目录或用户配置，不应写死为某个平台价格。
- 运行路径不做旧结构兼容；落地时直接按当前 schema 设计。
