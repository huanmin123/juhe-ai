## 需求目标

- 背景：大量请求并不需要顶级模型，用户希望一个本地 API Key 能按请求难度自动选择低价、中价或高价模型，降低平均调用成本。
- 目标：建立 API Key 级混合智能路由能力，以低价评分模型输出 `1-10` 级，再按等级选择目标模型和真实分组。
- 交付物：一次性完整功能闭环，包括长期功能设计、当前 schema、API Key 配置接口、网关评分路由、缓存亲和、成本统计、审计记录、前端配置和完整验证。

## 交付原则

- 不分阶段上线，不做“先能评分、以后再补统计 / 审计 / 前端 / 缓存亲和”的半成品。
- `routeMode = hybrid` 一旦出现在可用 UI 或可调用 API 中，必须能完成完整请求链路、成本入账、审计追踪和统计展示。
- 任务清单只表示同一版本内的工程拆解，不表示可以拆成多个可发布阶段。
- 运行路径直接按当前 schema 和当前 API 契约实现，不为旧字段、旧配置或旧 UI 流程保留兼容分支。

## 明确不做

- 不新增混合账户。
- 不改真实账户创建和编辑流程。
- 不在所有 `200` 响应上强制做回答质量自检；后置质量评分只作为可配置增强，并且只处理 `200` 内容质量。
- 不做无声明的跨协议自动转换；目标分组必须能以原生协议承接当前请求，或具备明确设计和测试覆盖的显式桥接能力。OpenAI Chat / Responses 到 Anthropic Messages 桥接已进入 PLAN-0058。
- 不把模型价格写死到运行代码。
- 不用阶段字段参与路由；阶段只允许作为评分模型内部分析线索。
- 不做模型能力标签体系；当前先保持 `1-10` 评分、用户自定义档位、模型亲和和自动升档这一条简单主线。

## 方案概述

- API Key 新增 `routeMode = normal | hybrid`。
- `normal` 维持现有行为。
- `hybrid` 使用评分模型读取完整请求上下文，输出 `1-10` 等级。
- 评分模型不可用、调用失败或输出无效时，按用户配置的 `scoringFallbackMaxLevel` 在低档范围内从低到高寻找可用目标模型；低档无可用目标模型时返回本地可读错误。
- 等级规则把等级范围映射到目标模型；范围和目标模型都由用户配置，系统只校验启用规则覆盖 `1-10`、不重叠且不超过 `10`。
- 当前 API Key 的 active 分组绑定作为候选分组池，路由只在这个池内选择可承接目标模型的真实分组。
- 目标模型确定后，只改写请求体顶层 `model`，再进入现有账号调度。
- 同一会话维护模型和缓存亲和，避免分数小幅波动导致频繁切模型。
- 规划、执行、修复和复核都不固定高档模型；只要走混合 API Key，就按当前请求事实动态评分。
- 非 `200`、超时和连接失败继续走现有切号、重试、账号隔离和分组路由能力；只有目标模型账号池耗尽时才向更高档升级。
- `200` 响应先做基础协议校验，再按配置和触发条件进入后置质量评分；低风险短请求默认不触发，避免额外评分成本吃掉节省。
- 默认质量评分只复审低 / 中档最终目标模型，当前 `risk_based` 默认 `maxTriggerLevel = 6`；高档目标模型只在质量优先、严格输出、空响应或显式强制检查时复审，避免低价模型误判高级模型输出。
- 质量评分未通过时，默认先在原目标模型追加质量评分反馈做同档修复；同档修复仍不通过再升下一档，最多 2 次，避免无限循环。
- 质量评分触发后如果质量评分模型不可用、调用失败或输出无效，默认放行已缓冲的 `200` 目标响应并记录审计；配置为严格模式时返回可读错误。

## 风险与注意事项

- 评分模型本身会增加固定成本；低档请求比例不足时收益会下降。
- 完整上下文评分成本可能较高；评分缓存已作为低风险优化落地，规则预判仍只能作为后续可选增强，不能替代动态评分。
- 频繁跨模型会破坏上游缓存，必须默认启用模型亲和和缓存亲和。
- 后置质量评分会增加一次模型调用成本，必须按风险触发并限制重试次数；低等级、短上下文、可逆请求默认不触发。
- 质量失败后的重试不能无限循环，默认最多 `2` 次且最高不超过 `2` 次；默认第一次同档带反馈修复，第二次升档处理，并且必须记录额外成本、修复反馈、升级前后模型和失败类型。
- 评分和质量提示词不得从离线样本、项目类型、业务领域或关键词沉淀出固定规则；评测只能校准抽象维度和默认建议。
- 模型价格来自模型目录或用户配置，不应写死为某个平台价格。
- 运行路径不做旧结构兼容；落地时直接按当前 schema 设计。
