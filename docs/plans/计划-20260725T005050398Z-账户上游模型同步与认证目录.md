## 需求目标

- 背景：账户配置的本地模型目录无法反映当前上游 API Key 实际可见模型；网关还会向未认证请求公开聚合模型目录。
- 目标：账户编辑可安全地发现上游模型并与本地允许目录求交集；模型目录网关接口必须经过本地 API Key 认证；人工测试和恢复探针能以目录请求作为有界连通性预检。
- 交付物：账户模型同步接口和页面刷新入口、驱动化目录发现、认证收口、探针预检与缓存、回归测试及文档。

## 范围边界

### 本次包含

- [ ] 按供应商协议档案发现上游模型，返回本地允许目录交集。
- [ ] 在账户编辑表单的“支持模型”同行增加刷新操作，并由用户保存后生效。
- [ ] 禁止未认证访问本地网关模型目录。
- [ ] 让人工测试和后台恢复探针使用可缓存的目录预检，保留真实模型调用作为最终健康证据。
- [ ] 补齐单元 / 回归测试和长期文档。

### 本次不包含

- 自动在后台写回或删除账户的 `supportedModels`：避免静默改变健康检查模型与映射。
- 为未知上游实现无限兼容：不支持目录的账户退回既有真实模型探针。
- 将上游完整目录持久化为新的模型目录来源：本地模型目录仍是能力、价格与权限的唯一来源。

## 方案概述

- 上游目录发现按账户协议档案走既有网关 provider driver 的凭据、代理和请求头逻辑；OpenAI 兼容档案使用 `/v1/models`，Anthropic 使用 `/v1/models` 加 `anthropic-version`，Gemini 原生使用 `/v1beta/models`。
- 刷新接口仅使用已保存的账户凭据，在服务端请求上游。计算 `upstreamModelIds ∩ 本地可见供应商目录` 后，只返回当前 `supportedModels` 尚未包含的新增项；不保存账户，也不删除任何用户手动选择。
- 所有本地模型目录入口都必须先完成 Gateway API Key 认证；保留各原生协议的认证头解析，Gemini 的 `x-goog-api-key` 不被全局移除。
- 目录预检成功只证明连接、认证和目录访问；真实模型请求仍验证模型能力与额度。预检缓存按账户、实际凭据选择和协议隔离，并在短 TTL 内复用。

## 风险与注意事项

- 目录成功不代表实际模型可用，必须保留真实请求测试。
- 单账户多 Key 时，缓存不能在不同凭据之间复用。
- 目录响应和凭据不得写入账户配置或普通日志。
