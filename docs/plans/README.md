## 1. 目录目标

- 集中放置阶段计划，避免阶段范围散落在 `docs/` 根目录；已完成阶段作为归档保留，当前功能事实以架构和 functions 文档为准。
- 给每个有持续跟踪价值的需求建立稳定时间戳 ID，方便后续回看“当时为什么这样做”。
- 记录需求从方案、拆解、执行、验证到关闭的完整状态。
- 维护需求与架构文档、阶段计划、运行说明、测试验证说明、报告、bug 记录、调研文档之间的关联。
- 避免把独立测试报告正文写进计划目录，计划只记录执行过程、状态和报告链接。
- 避免需求结论散落在对话里，导致后续实现时丢失上下文。

## 2. 阶段计划与需求计划

- 阶段计划：记录阶段目标、范围、里程碑和完成标准；已完成阶段作为历史范围归档，不替代当前架构和功能文档。
- `计划-*.md`：记录阶段或单个需求的执行计划、进度、验证和完成总结，只使用 UTC 毫秒时间戳作为唯一标识。
- 阶段计划可以被多个需求计划引用；单个需求的过程记录不要直接写进阶段计划。

## 3. 什么时候需要建需求计划

建议新建计划：

- 涉及多个模块、多个文件或多阶段执行的需求。
- 影响数据结构、接口、账号调度、网关中转、权限、安全、部署或统计口径的需求。
- 用户明确要求“给方案 / 排计划 / 继续跟进 / 后面实现”的需求。
- 需要先调研、再设计、再实现、再验证的需求。
- 可能跨多次对话才能完成的需求。

可以不建计划：

- 单个错别字、单行文案、一次性小修。
- 不影响项目状态的纯问答。
- 已经有现成计划且只是补充同一需求进度。

## 4. ID 与命名

- 计划完整 ID 统一为 `PLAN-YYYYMMDDTHHmmssSSSZ`，例如 `PLAN-20260722T131530123Z`；不再分配、扫描或递增四位计划序号。
- 时间戳使用计划创建瞬间的 UTC 时间，格式为 `YYYYMMDDTHHmmssSSSZ`，精确到毫秒；生成一次后永久保持不变，后续更新不得改写。
- 时间戳就是计划唯一键。若完整 ID 或目标文件路径已存在，必须重新获取当前 UTC 时间戳后再创建，不得覆盖、复用或回收。
- 创建前必须用 `rg` 检查完整 ID 和目标文件名；索引与正文引用必须写完整 ID，Markdown 链接必须指向带时间戳的完整文件名。
- 除 `README.md` 和 `计划模板.md` 外，`docs/plans/` 下的阶段计划、需求计划和配套任务清单统一命名为 `计划-YYYYMMDDTHHmmssSSSZ-计划名称.md`。
- 历史文件已统一迁移：已有合法毫秒时间戳的文件保留原时间戳；缺少时间戳的文件使用首次入库 UTC 时间补齐，同一秒内按毫秒位确定唯一值。旧 `PLAN-NNNN` 只允许在无法无歧义迁移的历史叙述中作为旧别名保留，不得用于新文件或新引用。
- 同一需求的后续调整继续写在原计划里，不要新建近似重复计划。
- 如果一个需求拆出独立大阶段，可以保留父计划，并在父计划中链接子计划。

推荐目录结构：

```text
docs/plans/
  README.md
  计划模板.md
  计划-20260501T160541000Z-第一阶段计划.md
  计划-20260722T131530123Z-示例需求.md
  计划-20260722T132015456Z-示例任务清单.md
```

## 5. 状态定义

计划状态建议只使用这些值：

- `草稿`：已记录需求，但范围或方案还未确认。
- `待开始`：范围明确，尚未执行。
- `进行中`：正在实现、调研或验证。
- `阻塞`：依赖用户确认、外部资源、环境或上游问题。
- `待验证`：实现完成，等待测试、构建或人工验收。
- `已完成`：实现和必要验证已完成。
- `已关闭`：需求取消、合并到其他计划或不再执行。

任务清单状态建议：

- `[ ]` 未开始
- `[~]` 进行中
- `[x]` 已完成
- `[-]` 取消或不做，并说明原因
- `[!]` 阻塞，并说明阻塞点

## 6. 单个需求计划必须包含什么

每个需求计划至少包含：

- **基本信息**：计划 ID、状态、创建时间、需求来源、负责人或执行者。
- **需求目标**：要解决什么问题，最终交付什么。
- **范围边界**：本次做什么，不做什么。
- **关联文档**：涉及的架构、阶段、调研、运行、bug 或部署文档。
- **执行拆解**：可勾选的任务清单。
- **测试项**：列出必须覆盖的自动化测试、手动验证、回归场景和不适用说明。
- **进度记录**：按日期记录关键进展、决策和剩余事项。
- **验收标准**：什么情况下算完成。
- **验证记录**：跑过哪些命令、做过哪些手动验证、哪些未验证。
- **风险与注意事项**：安全、数据清洗、发布异常处理和后续扩展边界等。
- **完成总结**：最终落地内容、改动位置、验证结果和运维观察边界。

## 7. 测试项要求

每个需求计划必须包含测试项，不能只在完成时写“已验证”或“验证通过”。测试项用于提前明确本次需求要怎么证明可用，验证记录用于填写实际执行结果。

测试项至少按需覆盖：

- **命令类验证**：类型检查、构建、单元测试、接口测试或脚本运行，例如 `pnpm typecheck`、`pnpm build`。
- **功能主流程**：本次新增或修改能力的成功路径，明确入口、操作步骤和预期结果。
- **异常与边界**：必填校验、权限限制、空数据、错误响应、无可用账号、网络失败等关键失败路径。
- **回归场景**：与本次改动相邻的供应商、账户、分组、API Key、网关调度、统计或部署流程。
- **前端体验**：页面文案、空态、加载态、错误提示、表格分页、表单校验和 Ant Design Vue 中文 locale。
- **未覆盖说明**：无法执行或不适用的测试项必须写明原因、风险和后续补测条件。

测试项建议使用表格记录：测试类型、测试项、验证方式 / 命令、预期结果、状态、实际结果或备注。状态建议使用 `未执行`、`已通过`、`未通过`、`不适用`。

## 8. 关联文档规则

- 影响模块边界、数据关系、权限、安全或网关链路：同步链接并更新 `docs/architecture/架构总览.md`。
- 影响阶段范围或交付优先级：同步链接并更新 `docs/plans/` 下对应阶段计划或需求计划；当前功能事实还要同步到架构和 functions 文档。
- 影响运行、构建、部署或验证流程：同步链接并更新 `docs/develop/运行说明.md`、`docs/develop/测试与验证说明.md` 或 `docs/deploy/*`。
- 影响存储 schema 或本地数据清洗：同步链接并更新存储相关文档；运行路径只维护当前 schema，历史结构差异通过离线清洗或重建处理。
- 来自 bug 或修复问题：关联 `docs/bug/*`，必要时补充 bug 记录。
- 来自调研结论：关联对应调研文档，例如 `docs/functions/中转透传机制调研与定位修正.md`。
- 来自压测、性能分析或容量验证：关联对应 `docs/reports/*` 报告；原始 JSON、log、CPU profile 等产物继续引用仓库根目录 `reports/`。

需求计划文档只记录“本次需求怎么推进”。长期稳定结论应沉淀到架构、阶段计划、运行手册或专项调研文档，不要只留在需求计划里。

## 9. 进度维护规则

- 开始执行前，先把计划状态更新为 `进行中`。
- 每完成一个关键阶段，更新任务清单和进度记录。
- 方案发生变化时，在“决策记录”或“进度记录”里写明原因，不要只改最终结论。
- 被阻塞时写清楚阻塞原因、等待对象和下一步动作。
- 完成后必须补充测试项执行结果、验证记录和完成总结，再标记为 `已完成`。
- 需求取消或合并时标记为 `已关闭`，并说明去向。
