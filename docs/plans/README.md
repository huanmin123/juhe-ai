# 需求计划目录

> 面向 AI 和维护者。
> 这里记录每次需求的具体计划、执行进度、完成情况、关联文档、验证结果和注意事项。
> 本目录用于“过程管理和需求追踪”，不是替代架构文档、阶段计划或问题记录。

## 1. 目录目标

- 给每个有持续跟踪价值的需求建立稳定编号，方便后续回看“当时为什么这样做”。
- 记录需求从方案、拆解、执行、验证到关闭的完整状态。
- 维护需求与架构文档、阶段计划、运行手册、bug 记录、调研文档之间的关联。
- 避免需求结论散落在对话里，导致后续实现时丢失上下文。

## 2. 什么时候需要建计划

建议新建计划：

- 涉及多个模块、多个文件或多阶段执行的需求。
- 影响数据结构、接口、账号调度、网关中转、权限、安全、部署或统计口径的需求。
- 用户明确要求“给方案 / 排计划 / 继续跟进 / 后面实现”的需求。
- 需要先调研、再设计、再实现、再验证的需求。
- 可能跨多次对话才能完成的需求。

可以不建计划：

- 单个错别字、单行文案、一次性小修。
- 不影响项目状态的纯问答。
- 已经有现成计划且只是补充同一需求进度。

## 3. 编号与命名

- 编号格式统一为 `PLAN-0001`、`PLAN-0002`、`PLAN-0003`……按创建顺序递增。
- 编号只增不改，不重复使用，不回收。
- 文件名建议：`PLAN-0001-简短需求标题.md`。
- 同一需求的后续调整继续写在原计划里，不要新建近似重复计划。
- 如果一个需求拆出独立大阶段，可以保留父计划，并在父计划中链接子计划。

推荐目录结构：

```text
docs/plans/
  README.md
  PLAN-TEMPLATE.md
  PLAN-0001-xxx.md
  PLAN-0002-xxx.md
```

## 4. 状态定义

计划状态建议只使用这些值：

- `草稿`：已记录需求，但范围或方案还未确认。
- `待开始`：范围明确，尚未执行。
- `进行中`：正在实现、调研或验证。
- `阻塞`：依赖用户确认、外部资源、环境或上游问题。
- `待验证`：实现完成，等待测试、构建或人工验收。
- `已完成`：实现和必要验证已完成。
- `已关闭`：需求取消、合并到其他计划或不再执行。

任务清单状态建议：

- `[ ]` 未开始
- `[~]` 进行中
- `[x]` 已完成
- `[-]` 取消或不做，并说明原因
- `[!]` 阻塞，并说明阻塞点

## 5. 单个计划必须包含什么

每个计划至少包含：

- **基本信息**：编号、状态、创建时间、需求来源、负责人或执行者。
- **需求目标**：要解决什么问题，最终交付什么。
- **范围边界**：本次做什么，不做什么。
- **关联文档**：涉及的架构、阶段、调研、运行、bug 或部署文档。
- **执行拆解**：可勾选的任务清单。
- **进度记录**：按日期记录关键进展、决策和剩余事项。
- **验收标准**：什么情况下算完成。
- **验证记录**：跑过哪些命令、做过哪些手动验证、哪些未验证。
- **风险与注意事项**：兼容性、安全、数据迁移、回滚、后续扩展等。
- **完成总结**：最终落地内容、改动位置和后续建议。

## 6. 关联文档规则

- 影响模块边界、数据关系、权限、安全或网关链路：同步链接并更新 `docs/architecture.md`。
- 影响阶段范围或交付优先级：同步链接并更新 `docs/phase-*.md`。
- 影响运行、构建、部署或验证流程：同步链接并更新 `docs/dev-runbook.md` 或 `docs/deploy/*`。
- 影响存储 schema、迁移或数据兼容：同步链接并更新存储相关文档。
- 来自 bug 或修复问题：关联 `docs/bug/*`，必要时补充 bug 记录。
- 来自调研结论：关联对应调研文档，例如 `docs/relay-survey.md`。

计划文档只记录“本次需求怎么推进”。长期稳定结论应沉淀到架构、阶段计划、运行手册或专项调研文档，不要只留在计划里。

## 7. 进度维护规则

- 开始执行前，先把计划状态更新为 `进行中`。
- 每完成一个关键阶段，更新任务清单和进度记录。
- 方案发生变化时，在“决策记录”或“进度记录”里写明原因，不要只改最终结论。
- 被阻塞时写清楚阻塞原因、等待对象和下一步动作。
- 完成后必须补充验证记录和完成总结，再标记为 `已完成`。
- 需求取消或合并时标记为 `已关闭`，并说明去向。

## 8. 索引维护

新增计划后，在本 README 的“计划索引”中补一行。

索引建议按编号倒序或创建时间倒序维护，字段保持简洁：编号、标题、状态、创建时间、关联模块、文档链接。

## 10. 写作注意事项

- 写事实和决策，不写模糊口号。
- 每个任务要能判断完成或未完成。
- 不把敏感凭据、真实 token、用户隐私或完整上游错误敏感内容写入计划。
- 不把临时方案伪装成长期架构；长期结论必须同步到对应长期文档。
- 不把计划写成流水账，重点记录影响后续维护的关键变化。
- 文件路径、命令、字段名和接口名使用反引号，方便搜索。
