# 计划-20260904T010000000Z-账户运行态清理契约

## 1. 背景与当前事实

当前主分支 `master` 的 `HEAD` 为 `f9c1fbeac`，已完成普通路由速度优先运行态的查询、IPC、后端接口和前端展示。统一的账户运行态清理入口已在当前工作区实现，提交前仍需通过跨存储状态边界与调度回归验收。

现有恢复能力分散在多个边界：

- `clearFailureState` 清理账户持久异常字段，并在满足条件时推进 `dispatch_revision`；
- `clearGatewayAccountRuntimeAvailability` 清理网关进程内或 Redis 的账户可用性运行态；
- `clearNormalRouteLatencyDegradationForAccountBindingAsync` 清理普通路由速度优先的 `latency_degraded`；
- API Key 运行态和 API Key 瞬态失败保护分别由独立的数据库 / Redis 组件维护；
- 会话亲和、IP 级账号回避、并发槽、分组队列和 circuit 控制面各自拥有独立作用域与生命周期。

因此，现有“恢复正常”操作不能直接等同于“把账户恢复成新建账户”。

## 2. 目标

为账户管理提供一个明确、可审计、可幂等的“清理运行状态”操作，使账户在不改变业务硬约束和不打断在途请求的前提下：

1. 清理所有允许人工清理的账户级软运行态；
2. 使旧的异步探针、失败事件和旧 generation 不能覆盖清理结果；
3. 失效本地内存、Redis、DB service 和网关缓存中的相关投影；
4. 清理完成后，新的调度请求重新依据账户原有的优先级、超级优先、备用层、授权、模型能力、时间计划和额度事实计算候选。

## 3. 非目标与保护边界

以下内容不由运行态清理隐式修改：

- 手动 `disabled`、套餐过期、`lock_policy` / `lock_state`、凭据缺失或凭据无效等业务硬状态；
- 正在执行的请求、账户并发槽、全局并发槽、分组排队请求和已有队列租约；
- 账户原有的 `priority`、`superPriorityEnabled`、`fallbackEnabled`、分组绑定、模型映射、授权关系和可用时段；
- API Key 的业务 `disabled` 状态；
- 统计、使用记录、审计原文和历史故障事实。

`pending_test` / `error` 是否允许直接进入 `active` 不在默认清理语义中。默认仍应经过现有后台健康检查或显式 `force-activate` 契约，避免人工按钮绕过新账户激活门禁。

显式账户错误策略产生的冷却必须由调用方明确授权后才能清理，不能因“运行态清理”名称而自动绕过策略。

## 4. 运行态事实源与清理分类

| 状态族 | 主要事实源 | 默认动作 | 保护条件 |
| --- | --- | --- | --- |
| 账户持久异常 | `accounts.status`、`cooldown_until`、`last_error_*`、`cooldown_retest_*`、`stream_failure_*`、健康检查字段 | 复用现有 `clearFailureState` 事务语义 | 遵守过期、禁用、`pending_test` 和显式策略门禁 |
| 账户 circuit / dispatch fence | `dispatch_revision`、`account_circuit_incidents`、outbox、half-open / recovery lease | 推进 revision 使旧 generation 失效；不直接删除历史 incident | 旧 lease/result 必须被 CAS/fence 拒绝；在途 probe 不得被伪造为成功 |
| 网关账户可用性 | recovery probe、precheck、local suppression、degradation、failure storm、configured avoidance | 通过统一网关清理服务清理 | standalone 走进程内状态；performance 走 Redis；DB service 不能读取自己的假本地副本 |
| 普通路由速度优先 | `latency_degraded`，作用域为 `systemAccountId + routeStrategyId + groupId + accountRuntimeKey` | 按账户清理所有实际绑定作用域，使用现有 generation/CAS 机制 | 不能只清当前 route；不能误清其他系统账户、分组或授权实例 |
| API Key 持久运行态 | `account_api_key_runtime_states` | 将可恢复的 `error` / 冷却状态置为可重新探测状态 | 不修改 `disabled` Key；不抢占有效 `probe_claimed_until`；必须校验 `config_revision` |
| API Key 瞬态保护 | Redis transient failure guard | 按账户和 key fingerprint 精确清理 | 需要 expected generation；Redis 失败必须可见 |
| 会话亲和 | 本地索引或 Redis 会话亲和记录 | 仅在契约明确包含时按账户批量清理 | 不得用高基数无界扫描阻塞请求路径；授权实例作用域必须精确 |
| IP 级账号回避 | `clientIp + API Key + accountId` 短 TTL 状态 | 默认不随账户级清理扩大作用域；如纳入必须精确按账户清理 | 不能把 IP 回避改写成账户健康结论或账号全局冷却 |
| 并发与队列 | 本地 Map、Redis ZSET、队列和 reservation | 不清理，等待请求释放或自然过期 | 防止重复调度、容量超卖和在途请求失配 |
| 网关缓存 / 投影 | 本地 LRU、共享 Redis cache、DB service 投影 | 清理成功后按现有失效协议通知 | 不能用全量无界 flush 代替按作用域失效 |

## 5. 操作契约

当前实现使用独立的账户管理动作：

`POST /__aisys__/api/accounts/:id/runtime-reset`

请求体为严格 object，只接受配置版本，不允许客户端传入内部运行态键、锁死栅栏或选择性绕过选项：

```json
{
  "expectedConfigRevision": 12
}
```

响应至少应能区分：

- `accountId`、新的 `configRevision` / `dispatchRevision`；
- `cleared`：实际清理的状态族（账户持久异常、网关运行态、速度优先、Key 瞬态、dispatch fence 等）；
- `skipped`：因禁用、过期、锁死、显式策略、手动停调、来源不可用或健康检查门禁而保留的状态；
- `failed`：Redis、IPC 或其他后置清理失败及可重试信息；
- `dispatchEligible`：基于当前业务硬门禁重新计算后的结果，而不是简单返回 `active`。

操作必须经过资源管理权限校验、幂等保护和操作日志记录。失败不能被包装成“全部清理成功”。

## 6. 事务与时序要求

推荐顺序：

1. 在数据库事务中锁定正确的账户 / 授权实例关系，校验权限、版本和硬状态；
2. 清理允许修改的持久异常字段，推进 `dispatch_revision` / generation fence；
3. 事务提交后，调用统一 runtime coordinator 清理网关、速度优先、Key、会话和其他明确纳入的易失状态；
4. 清理动作使用 expected revision / generation / lease token，旧的异步写入必须原子拒绝；
5. 所有本地和共享缓存按现有 IPC / invalidation 协议失效；
6. 重新读取最小调度投影，确认账户是否真正可调度；
7. 返回逐项结果并写操作日志。

数据库事务不能长时间等待 Redis、HTTP 或探针完成。Redis / IPC 后置失败必须保留已提交的数据库事实，并向调用方返回部分失败，不允许自动回滚成另一种状态。

## 7. 必须验证的场景

### 正常与边界

- `temporary_unavailable` / `rate_limited` 清理后可按原优先级重新进入候选；
- `error` / `pending_test` 不绕过后台健康检查门禁；
- 过期、手动禁用、锁死和显式策略冷却不会被默认清理误改；
- 授权实例只清理指定实例，不影响同一物理凭据的其他授权实例。

### 运行态一致性

- standalone 的内存 Map、timer、waiter 与 performance 的 Redis 状态结果一致；
- 速度优先所有 route/group 作用域都被清理，其他账户和租户不受影响；
- API Key `disabled` 和有效探针租约不被抢占；
- 会话亲和、IP 回避若未纳入操作，不发生隐式清理；若纳入，必须有精确作用域回归；
- Redis 或 IPC 失败时返回部分失败，不能声称已完成。

### 并发与旧事件

- 清理与失败上报、后台探针、半开租约、账户配置更新并发时，旧 generation 结果不能覆盖清理后的状态；
- 清理期间存在在途请求时，不清并发槽、不重复派发；请求结束后槽按原 release 路径释放；
- 重复提交同一操作具备幂等结果，不重复推进无意义版本。

### 调度验收

- 清理后候选重新遵守模型匹配、超级优先、`priority`、备用层、授权、计划、额度和并发硬门禁；
- 不因清理把低优先级或备用账户提升到更高层；
- `latency_degraded` 清除只移除速度优先的短期降级信号，不伪造上游健康成功。

## 8. 实施分阶段

1. **契约冻结**：确认默认清理白名单、保护名单、是否包含会话亲和和 IP 回避、`pending_test/error` 的激活语义。
2. **后端 coordinator**：先实现统一结果模型、权限、幂等、审计和数据库 fence；不改现有自动恢复语义。
3. **运行态适配**：逐个接入网关账户运行态、速度优先、API Key；每接一类保留独立 adapter 和失败可见性。
4. **可选作用域**：在确认高基数和多实例语义后，再接会话亲和、IP 回避等独立维度。
5. **前端入口**：账户列表现有操作菜单增加“清理运行状态”一项，点击后直接提交；不增加二次确认或独立面板，仅在列表刷新后提示成功/失败。内部租约、来源 IP 或完整错误细节不暴露给普通用户。
6. **独立复审**：由未参与写入的只读复审者核对 diff、权限、状态边界、Redis/内存一致性、调度回归和文档同步。

## 9. 停止条件

出现以下任一情况时停止实现并回到 Plan，不继续扩大清理范围：

- 无法证明某个状态的权威事实源或作用域；
- Redis / 内存两种模式无法提供等价的成功/失败语义；
- 需要强行释放在途请求、并发槽或队列租约；
- 旧 generation 结果仍可能覆盖清理结果；
- 需要绕过 `disabled`、过期、锁死、授权或健康检查门禁；
- 操作结果无法区分已清理、跳过和失败。

## 10. 当前决策

本计划只冻结分析和边界，不改变当前运行逻辑。默认推荐：

- 第一阶段只清账户持久异常、账户网关运行态、速度优先 `latency_degraded`、可恢复 API Key 状态和 API Key 瞬态保护；
- 暂不默认清会话亲和和 IP 级账号回避，先通过独立作用域测试后再决定；
- 永不清并发槽、在途请求、队列租约、业务硬状态和 API Key `disabled`；
- `error` / `pending_test` 继续等待健康检查，不因人工清理直接伪造为健康账户。
