# PLAN-20260718T230201001Z 生产管理端性能优先治理实施计划

> **For agentic workers:** REQUIRED SUB-SKILL: Use `superpowers:subagent-driven-development`（推荐）或 `superpowers:executing-plans` 按子计划逐项实施；每个阶段必须经过功能完整性审查和性能门禁后才能继续。

**Goal:** 在不删减任何页面、接口、字段、统计、审计、日志或管理操作的前提下，消除生产管理页面与 System API 的秒级长尾，使 PostgreSQL、Redis、worker 和前端加载链路符合性能优先、弱一致性、允许非核心记录偶发丢失的项目定位。

**Architecture:** 方案拆成三个可独立交付的子项目：PostgreSQL 普通查询去事务与统计降载、Redis 队列隔离与后台任务降载、管理接口渐进加载与事件循环治理。主列表和核心业务事实保持同步可用；动态状态与非核心副作用使用有界异步、缓存快照、批量写和可观测降级，不通过关闭功能或返回假空数据达标。

**Tech Stack:** Node.js 22、TypeScript、Express、Vue 3、Ant Design Vue、PostgreSQL 18、PgBouncer、Redis Streams、PowerShell 7、pnpm workspace。

## 问题定义

- 生产管理接口典型耗时约 `0.4s` 到 `1.5s`，账户列表出现约 `3.99s` 到 `6.7s`，供应商选项出现约 `10s` 到 `15s`。
- Nginx `request_time` 基本等于 upstream time，公网和反向代理不是内部主瓶颈。
- PostgreSQL 普通 query / execute 固定执行 `BEGIN + SET LOCAL + SQL + COMMIT`，生产累计约 4950 万次事务包装。
- Redis state 与 queue 共享同一物理实例和 DB，大 Stream payload 与状态命令产生单线程头阻塞。
- stats-worker、ingest-worker、server 和 db-service 均存在数百毫秒到数秒事件循环 lag。
- 账户页面 options、主列表和动态快照存在串行等待与重复轮询，后端 DTO 同步补齐多组动态字段。
- 统计窗口、额度窗口、分组统计和审计维护存在高频全量或逐行写入，形成周期性资源尖峰。

## 目标与非目标

### 目标

- 管理主列表 P95 达到 `<=300ms`，P99 达到 `<=800ms`。
- 任何 options 请求不得阻塞主列表发起和首行显示。
- 普通独立 PostgreSQL SQL 不再产生自动 `BEGIN` / `COMMIT`。
- Redis state 与 queue 物理隔离，队列失败不再阻塞前台请求或触发主进程 fatal。
- 统计、审计、日志、余额和动态状态功能继续可用，只改变数据刷新与传输方式。
- 建立可重复的生产前压测、功能回归和上线观察流程。

### 非目标

- 不重写整个后端技术栈，不借本计划推进无关 Node -> Go 迁移。
- 不引入 Kafka、ClickHouse、分布式事务或新的重型基础设施。
- 不在运行路径增加旧 schema 兼容、双读双写或自动迁移。
- 不改变 API Key -> 路由策略 -> 分组 -> AI 账户的业务路由层级。
- 不修改真实上游模型请求协议和调度算法。

## 总体架构决策

### 1. 核心业务同步，附加信息渐进

- 主列表同步返回稳定身份、权限、静态调度、关联摘要和操作判定。
- 动态状态、并发、今日用量、最近使用和余额通过动态快照补齐。
- 页面保持所有字段和操作入口；渐进加载只改变请求阶段，不改变最终可见功能。

### 2. 普通 SQL 无事务，真实不变量短事务

- `DatabaseClient.query`、`one` 和单条 `execute` 直接执行 SQL。
- 账户 / 分组 / API Key / 授权等真正需要多表共同成功的写操作继续使用显式 `transaction()`。
- 统计小批结果和游标需要共同推进时保留短事务；展示性日志、审计、清理单批和单条状态写不使用额外事务。

### 3. Redis state 与 queue 隔离

- cache、state、queue 至少三个物理 Redis 进程。
- state 只承接会话、验证码、限流、并发槽和调度运行态。
- queue 承接记录型异步副作用；producer 和 consumer 使用独立连接。
- 大 payload 先落内容寻址 staging，Stream 只传引用。

### 4. 非核心副作用 best-effort

- 主请求不得等待审计、运行日志、操作日志、公开接口日志和展示性 usage 的长期重试。
- producer 采用有界内存和短 deadline，超时 / 断连 / 饱和后丢弃并计数。
- 该策略不关闭记录功能；Redis 恢复后继续正常入队和展示。

### 5. 统计保留，计算方式降载

- 所有现有统计页面、额度字段、趋势和 TopN 保留。
- 热窗口改 changed scope/date 增量，范围窗口低频刷新，分组统计批量 upsert。
- 离线全量重建只用于恢复和验证，不进入 System API 请求路径。

## 发布顺序与回退

1. 先发布观测和回归，不改变运行行为。
2. 只拆 queue Redis，观察独立收益；异常时恢复旧 URL。
3. 发布普通 SQL 去事务；异常时回滚发布包，不做 schema 回退。
4. 发布 options 解耦和动态快照；异常时逐模块回滚前后端同一发布包。
5. 发布队列 best-effort 和 payload 引用化；回退时允许丢弃新旧队列 backlog，不增加双写兼容。
6. 发布统计批量 / 增量和维护降载；异常时停对应 job，清空可重建窗口后离线重建。
7. 所有阶段稳定后更新长期架构和部署基线。

## 风险与注意事项

- “允许丢失”只适用于非核心记录和可重建统计，不授权删除业务 CRUD、权限、API Key、授权或网关核心事实。
- 动态字段短暂过期属于预期，但页面必须明确可用性，不能默认为实时。
- Redis 物理隔离需要新增端口、进程和监控，但不引入新的产品依赖。
- 去事务改动影响所有 PostgreSQL repository，必须先建立 query 边界回归并运行完整 PG smoke。
- 统计增量化不能把聚合重新放回 API 请求路径。
- 当前工作区已有与本计划无关的用户修改，实施时必须逐文件确认，不覆盖或整理无关改动。
