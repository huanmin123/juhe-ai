# 计划-20261003T065946077Z：Codex OAuth 账户模型映射消费

- 计划 ID：PLAN-20261003T065946077Z
- 状态：待开始

- 需求来源：BUG-0269 残余项（`docs/bug/问题-0269-使用记录与审计模型映射记账断线.md` 残余项登记第 1 条，:58）
- 执行者：待主代理排期指派

## 需求目标

让 Codex OAuth 账户的模型映射在请求链上真实生效，消除"记账按映射解析记录、上游请求却未改写"的两面不一致：OAuth 分支的 `ModelOverride` 接入与 api_key 分支同源的映射解析，使上游请求模型与 `upstream_model` / `model_mapping_applied` 记账一致。

## 背景（取证事实）

- `cmd/juhe-ai-gateway/chain_driver.go:312-313`：`isCodexOAuthAccount` 分支用 `canonicalAccountModel(req, account)`（supportedModels 拼写）作为 `ModelOverride`，不消费 `resolveAccountModelMapping`；同文件 api_key 分支（:281 / :341）均消费映射解析。
- Node 参照：`gpt/driver.ts` 同分支传 `modelMapping?.upstreamModel`（Node 足迹已清理，表述承自 BUG-0269 残余登记的取证结论；复核需查 git 历史）。
- 生产零可达：236 条启用映射全部在 `api_key` 账户，3 个 OAuth 账户无任何启用映射——当前该缺口无生产影响，但一旦给 OAuth 账户启用映射，运行时不会改写上游模型（失败面为上游报错），而 BUG-0269 修复后的记账会按映射解析记录，形成请求/记账不一致。

## 范围边界

### 范围内

1. OAuth 分支接入与 api_key 分支同源的映射解析：`ModelOverride` 计算改为"映射命中取映射目标（同源 `resolveAccountModelMapping` 解析链），未命中回落 `canonicalAccountModel`"，与 Node `modelMapping?.upstreamModel` 语义对齐；映射解析、候选分类与记账两侧继续共享同一实现，不允许出现"记账映射 A、实际发 B"。
2. 测试：新增 OAuth mock fixture 用例覆盖映射命中 / 未命中 / 映射目标不在 supportedModels 等关键正常、异常和边界路径；既有 OAuth 分支用例（D-151 能力解析等）不回退。

### 非目标

- 不改 api_key 分支与 gemini / anthropic 分支的映射语义。
- 不改映射的保存校验、管理面编辑与候选分类规则。
- 不处理历史存量行回溯（BUG-0269 已登记不回溯）。

## 风险与控险

- 风险：请求链行为变更——OAuth 账户启用映射后上游收到的模型名将改变，错误处理、能力过滤、探针路由均可能受影响。
- 控险：① 生产零可达现状（236 条启用映射全 api_key、OAuth 账户无启用映射）天然控险，合入即生效但无存量行为可变；② Mock 全覆盖（命中/未命中/边界）后才允许交付；③ 交付说明中明确"给 OAuth 账户启用映射即触发新行为"，供运营侧知情。
