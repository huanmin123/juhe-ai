## 需求目标

- 背景：当前账号运行态短暂避让、调度降级和事前确认容易受多 IP 高并发失败风暴影响，且部分恢复路径依赖后续用户请求触发半开，可能导致账号长时间挂在运行态屏障中。

## 方案概述

- 方案原则：真实请求只负责发现失败、短暂避让、忘记亲和和切号；后台探针负责恢复、调度降级确认和持久状态确认。
- 数据变化：不新增数据库字段；Web 本地运行态继续保存在进程内，持久冷却态沿用 `accounts.status / cooldown_until / cooldown_retest_*`。
- 接口变化：管理接口不变；账户列表继续通过 `runtimeAvailability` 展示运行态。
- 后端变化：在账号运行态副作用服务中增加后台探针调度和去重租约；调度降级必须满足时间窗口和探针结果；持久写入仍等待并发归零。
- 数据处理策略：不写运行期兼容迁移；现有本地状态为易失状态，服务重启后回到普通调度。

## 风险与注意事项

- Web 进程内运行态是易失状态，服务重启后会丢失；这是当前轻量部署边界，不能把它当作审计或账务事实。
- 后台探针本身会产生恢复探活流量，必须使用 `traffic_source = cooldown_retest` 并禁用账号状态副作用，避免污染业务统计和账号质量。
- 如果探针过于频繁，会放大上游压力；实现必须去重同一运行态键并按时间窗口退避。
- 发布异常处理：如探针异常导致误避让，可通过账户“恢复正常”清理本地运行态；持久状态仍由既有手动恢复和冷却复测处理。
