## 需求目标

- 背景：Anthropic、GPT 和 OpenAI-compatible 逻辑在网关、账号、计费、统计和前端中多处混写，后续新增供应商会继续放大维护成本。
- 目标：建立供应商驱动化标准接口，让通用层只关心认证、分组、调度、审计和记录；供应商只实现自己的协议、凭据、模型、计费和前端能力。
- 交付物：架构规范、计划文档、后端 driver registry 第一批落地、分组 profile 校验修复、受影响回归验证记录。

- 不实现新供应商真实接入：只为后续接入建立标准和第一批隔离点。

## 方案概述

- 方案原则：通用层依赖 registry，具体供应商落到独立 driver 文件；协议、供应商、客户端画像和 usage/cost/model 分开。
- 数据变化：本轮不改 schema；只修复已有 `provider_protocol_profile_id` 校验使用方式。
- 接口变化：不改外部 HTTP API；内部新增 driver 类型和 registry。
- 前端变化：本轮只记录标准，后续再切 capability adapter。
- 后端变化：新增 provider driver 骨架，账号请求能力过滤先通过 driver 判定。
- 数据处理策略：不处理旧数据；如果已有混绑数据，后续按用户要求提供离线检查 SQL。

## 风险与注意事项

- 网关请求能力过滤位于调度前，任何默认值变化都会影响跨分组 fallback。
- `providerProtocolProfileId` 修复可能暴露既有错误数据；本项目默认不在运行路径写旧数据兼容。
- 上游请求和响应拆分必须分阶段推进，避免在一次改动中同时改变 URL、header、SSE、usage 和错误副作用。
