- 背景：用户在单个账号测试和批量账号测试中观察到“显示已超过 60 秒仍未结束”“批量测试排队时间被算进等待时间”“关闭前端测试窗口后任务可能仍在后台运行”等问题；同时需要从上千到上万个账号规模重新审视全站各类测试、探测、后台复测和刷新策略。

## 当前问题摘要

| 场景 | 用户可见问题 | 当前风险 | 方案方向 |
| --- | --- | --- | --- |
| 账号单测 | 前端显示超过 60 秒仍未结束 | 排队或 worker 未消费阶段被用户误认为运行超时；如果取消请求没送达，后台仍可能继续跑；如果 worker 异常，queued 任务可能长期堆积 | 运行超时只从 `startedAt` 计时；queued 记录等待时长和最近投递 / 接收状态，超过队列等待上限后自动收口；增加 session 心跳和后端 stale 自动取消 |
| 账号批测 | 后面的账号显示排队很久，用户认为全站都在排队 | 串行消费会让后续任务等待过长；全量无边界提交又可能压垮资源；queued 无上限会在 worker 异常时越积越多 | 批量测试只做单测分批提交，默认每批最多 10 个，本批全部终态后再提交下一批；排队不计入运行超时，但超过队列等待上限要进入终态并提示后台测试 worker 长时间未接收 |
| 前端离开测试页面 | 用户切换菜单、刷新或关闭浏览器后希望后台继续，回来还能接着看 | 旧方案把前端连接中断误当成取消，临时或间断测试会被提前终止 | 增加 `testSessionId`、活动 session 查询、前端 `sessionStorage` 快照和显式停止接口 |
| 模型检测 | 强诊断请求多、耗时长 | 全量批量检测成本和时间不可控 | 默认保留强诊断；后续如做全站巡检，应另提供轻量探测入口 |
| 手动代理测试 | 多代理或多目标测试慢 | 供应商目标、出口信息目标串行时总耗时放大 | 单个代理内部目标可有限并行，但不影响账号测试链路 |
| 后台代理刷新 | 固定批量顺序检测 | 代理多时刷新周期长，旧代理状态更新滞后 | 分批滚动、可配置批量和并发，保留不可重入 |
| 冷却账号复测 | 大量账号冷却后恢复很慢 | 单 worker 串行或低并发会导致可恢复账号迟迟不恢复 | 后续单独评估，不和本次账号测试 session 治理混在一起 |
| OAuth token 刷新 | 大量 OAuth 账号临近过期时刷新慢 | 顺序刷新叠加 120 秒 token 超时会拖垮刷新窗口 | 分批并发刷新，保留账号级锁和失败计数 |
| 网关预检 / 客户端探针 | 探针耗时可能叠加到用户请求 | 没有全局保护时，异常上游可能制造大量慢探针 | 保留请求级超时和账号级抑制，必要时增加轻量并发护栏 |

## 统一设计原则

1. 排队不算运行超时但必须有队列等待上限：任务处于 `queued` 或等待 worker 接收时，只展示“等待接收 / 未开始计时”，不触发 60 秒运行超时；同时记录 `queued_at`、等待时长和最近投递 / 接收状态，超过队列等待上限后自动收口为失败或取消。
2. 运行必须有终态：任务进入 `running` 后必须有阶段超时、总超时和明确中文错误，例如“真实请求超过 60 秒未完成”。
3. 只有显式停止才取消：关闭弹窗、切换菜单、页面刷新、页面卸载、断网或心跳中断都不能取消后台任务；只有用户点击“停止测试”才取消未开始任务并尽快中断运行中任务。
4. 分批推进：批量测试不是另一套测试逻辑，只是把单个账号测试按固定批次提交；默认每批最多 10 个，等这一批全部成功、失败、取消或超时后，再提交下一批。
5. 系统级防护：账号测试 worker 默认最多同时运行 100 个任务，该值进入系统设置，防止恶意请求或异常批量把系统打满。
6. 单用户批量限量：批量入口限制单个用户本次批量每批最多 10 个账号，本批全部进入终态后才提交下一批。
7. 状态可解释：前端和日志必须区分“等待接收、运行中、取消中、已取消、运行超时、上游失败、前端已断开但后台继续、已恢复接收”。
8. 取消幂等：取消 session 或 task 可以重复调用，重复取消不报错，不产生脏状态。

## 场景方案

### 1. 账号单个测试

- 前端创建 `testSessionId`，提交单个测试任务时带上 session。
- 后端写入任务后立即返回任务 ID，任务状态为 `queued`，展示“等待接收，未开始计时”。
- worker 消费前检查任务是否已取消、session 是否仍有效、账号是否仍可访问。
- 任务进入 `running` 时写入 `startedAt`，前端只从 `startedAt` 计算运行时间。
- 单次真实请求仍按 `10s -> 20s -> 30s` 阶段等待，总运行超时 60 秒；超时返回明确结果，不无限等待。
- 用户点击“停止测试”时调用 session 取消接口；正在运行的任务设置 `cancel_requested` 并触发 AbortController。关闭弹窗只隐藏终端，任务和轮询继续。

### 2. 账号批量测试

- 批量测试使用同一个 `testSessionId`，每个账号对应一个 task，task 内部逻辑和单个账号测试完全一致。
- 前端按固定批次提交任务，默认每批最多 `10` 个；必须等当前批次全部进入终态后，才提交下一批。
- 后端账号测试 worker 使用系统设置控制并发，默认 `100`；正常批量测试不会因为单用户每批 `10` 被后端额外卡住，但恶意或异常并发会被系统级防护拦住。
- 对上千账号，也只按同一个分批策略推进，不因为数量大改成全量提交。
- 前端列表按任务 ID 增量轮询或订阅状态，不能因为某个任务慢而阻塞整批结果展示。
- 批量终止调用一次 `cancelSession(testSessionId)`，后端批量标记 session 下 `queued/running` 任务为取消或取消请求，不再由前端逐个 task 发取消请求。
- 批量测试完成后，session 进入 `completed`；后续迟到的心跳或取消请求按幂等处理。

### 3. 前端关闭、刷新、断网和异常退出

- 正常关闭弹窗：只隐藏弹窗并保留当前测试终端，不调用 session 取消接口。
- 页面切换或刷新：不发送卸载取消请求；后端 session 和 task 继续运行。
- 前端运行中可继续发送 heartbeat，用于判断浏览器端是否仍在接收，不再作为后端取消租约。
- 前端把当前 session、任务状态、终端结果和必要的脱敏账户摘要写入 `sessionStorage`，默认 12 小时过期；不写入 API Key、OAuth Token、代理密码或草稿凭据。
- 同一登录用户同一时间只允许一个 `running` session；旧 session 未结束时创建新 session 返回 `409`，前端重新打开当前测试或提示先手动停止。
- 浏览器会话丢失后不要求后端回放前端终端日志；后台任务仍继续，最终结果通过测试任务列表、使用记录、审计或对应检测结果查看。
- session 下任务全部进入终态后由前端显式完成，或在心跳停止且空闲一段时间后自动收口为 `completed`；绝不因为 heartbeat stale 把 queued/running task 改成 canceled。

### 4. 排队时间和运行时间

- `queuedAt`：任务创建或进入可消费队列的时间，只用于展示等待多久，不参与运行超时判定。
- `startedAt`：worker 真正开始测试前写入，是运行超时起点。
- `finishedAt`：任务进入成功、失败、取消或超时终态的时间。
- 前端展示建议：
  - `queued`：`等待接收，未开始计时，已等待 Ns`
  - `running`：`真实请求中，已运行 Ns，最大 60s`
  - `timeout`：`真实请求超过 60 秒未完成`
  - `canceled`：展示“用户已停止测试”或其它明确的手动 / 系统取消原因

### 5. 上千 / 上万个账号批量测试

- 上千 / 上万个账号只是容量场景，不改变批量测试策略：仍然每批最多 `10` 个，本批完成后才提交下一批。
- 系统侧默认允许较高账号测试并发 `100`；用户侧正确策略是“固定小批次 + 排队不计运行超时 + 清晰进度展示”。
- 管理员发起大量账号批测时，前端只提交当前批次，后端只保存已提交的任务，避免一次写入海量 task。
- worker 收到已经提交的 runnable task 后在系统级并发上限内尽快异步消费，默认上限 100。
- 前端必须显示总体进度：总数、等待接收、运行中、成功、失败、取消、超时。
- 大批量结果只分页读取摘要，不把所有完整结果一次性返回前端。
- 如果后端发现系统资源过载，应暂停拉取新任务，而不是把已排队任务按运行超时失败。

### 6. 模型检测

- 模型检测保持强诊断准确优先，但不应拖慢账号测试 session 的提交、取消和状态展示链路。
- 全量批量场景不默认跑强诊断完整 profile；如后续需要“全站模型可用性巡检”，应新增轻量 profile，只检查账号可调度、目标模型可请求、响应模型字段和基础协议。
- 模型检测运行时间按检测报告维度展示预计请求数和预计耗时，避免用户误认为它和账号连通性测试一样轻。
- 可信对比账户的额外消耗必须继续由用户显式选择，不自动寻找所谓官网账号。

### 7. 代理手动测试和后台代理刷新

- 单个代理内的供应商目标和出口信息目标可以有限并行，每个 HTTP 探测保留独立超时。
- 后台代理刷新继续由 worker 定时触发且不可重入，但每轮可配置 `batchSize` 和 `concurrency`；代理多时滚动刷新，不要求一轮刷新全部代理。
- 代理检测失败只更新代理质量状态，不应直接导致账号测试任务长时间等待。

### 8. 冷却账号后台复测

- 冷却复测是当前大规模账号场景的重点瓶颈之一，不能长期保持单任务串行。
- 后续如调整冷却复测，再单独确认是否需要并发策略；本计划优先处理手动账号测试体验。
- 每个账号仍保留独立退避：快速恢复失败后按 `3s -> 6s -> 12s -> 24s...` 增加 `cooldown_until`，避免同一坏账号连续占用复测资源。
- 复测请求仍走真实网关链路，候选只允许当前账号，避免复测过程悄悄切到其他账号。
- 复测结果和使用记录继续标记 `traffic_source = cooldown_retest`，不混入普通用户请求统计口径。

### 9. OAuth access token 后台刷新

- OAuth 刷新不应按账号顺序一个个等待 token endpoint，尤其是 token endpoint 最高可等待 120 秒时。
- 后续如调整 OAuth 刷新，再单独确认是否需要并发策略；本计划优先处理手动账号测试体验。
- 扫描候选仍按分页 / batch 读取，单轮不要全量加载所有 OAuth 账号。
- 连续失败计数和恢复语义保持不变：失败达到阈值标记 `oauth_token_refresh_failed`，后续刷新成功再恢复。
- 如果刷新队列积压，应优先刷新最接近过期的账号，而不是简单按创建时间顺序。

### 10. 网关预检、客户端探针和 Codex 切换探针

- 这些探针服务于真实网关请求，不能被管理面批量测试拖慢。
- 保留请求级超时、账号级短 TTL 抑制和本地错误风暴保护。
- 探针失败要写清楚是“预检失败”“客户端策略探针失败”还是“上游真实请求失败”，避免前端或日志把它误认为账号测试失败。
- 如果后续观测到高并发下探针数量过大，再增加轻量并发护栏；护栏只保护资源，不把真实用户请求排成不可解释的长队。

### 11. worker、IPC 和 DB service 资源保护

- 账号测试后端并发由系统设置控制，默认 100；任务内部仍不能开启无管理的 nested 并发。
- worker 拉取任务必须按窗口读取，不能全量读取大表或把所有任务 split 到内存。
- 所有任务状态写库使用短事务；批量取消按 session 分批更新，避免一次取消上万个任务时长时间占用 SQLite 写锁。
- DB service HTTP proxy 的 in-flight 限制属于存储保护，不应被任务系统绕过。
- 任务队列积压、运行中数、过期取消数、用户主动取消数和超时数都应暴露到后台任务状态或运行日志，便于排障。

## 建议数据结构和接口

### 任务 session

建议新增或等价实现 `account_test_sessions`：

| 字段 | 含义 |
| --- | --- |
| `id` | 测试 session ID，前端创建或后端创建均可，但必须全局唯一 |
| `scope_type` / `scope_id` | 管理侧或用户侧作用域 |
| `created_by` | 发起人 |
| `status` | `running`、`canceling`、`completed`、`canceled`、`expired` |
| `last_heartbeat_at` | 前端最后一次心跳时间 |
| `cancel_requested_at` | 用户主动取消时间 |
| `cancel_reason` | 中文取消原因或内部枚举 |
| `total_count` / `queued_count` / `running_count` / `finished_count` | 可选汇总字段，便于前端快速展示 |

建议扩展 `account_test_tasks`：

| 字段 | 含义 |
| --- | --- |
| `session_id` | 归属测试 session |
| `queued_at` | 入队时间 |
| `started_at` | worker 开始真实测试时间 |
| `finished_at` | 终态时间 |
| `cancel_requested` | 是否请求取消 |
| `cancel_reason` | 取消原因 |
| `lease_checked_at` | 最近一次 worker 检查 session 租约时间，可选 |

### 接口

建议新增接口：

- `POST /__aisys__/api/accounts/test-sessions`
- `POST /__aisys__/api/accounts/test-sessions/:sessionId/heartbeat`
- `POST /__aisys__/api/accounts/test-sessions/:sessionId/cancel`
- `GET /__aisys__/api/accounts/test-sessions/:sessionId`
- `GET /__aisys__/api/accounts/test-sessions/:sessionId/tasks`
- 用户侧同样提供 `my-accounts` 作用域接口，后端按当前登录用户收窄权限。

保留单任务取消接口作为兼容当前页面内部调用，但前端批量场景优先使用 session 取消。

### 系统设置建议

| 设置 | 默认建议 | 说明 |
| --- | --- | --- |
| `accountTestTaskConcurrency` | `100` | 账号测试 worker 系统级并发上限，建议允许 `1..1000` |
| `accountBatchTestChunkSize` | `10` | 前端批量测试每批提交数量，默认不做全量提交 |

## 风险与注意事项

- 账号测试后端默认并发上限为 100；压力控制同时依赖单用户批量每批最多 10 个、同用户 active session 互斥和手动停止。
- 取消运行中的 HTTP 请求依赖 AbortController 和底层 fetch / adapter 支持；不能中断时也必须在当前阶段超时后尽快落终态。
- 上万个任务批量取消需要分批更新，不能一次长事务锁住 SQLite。
- heartbeat 过短会放大前端和后端请求数；默认建议 `2s` 心跳、`15s` 空闲完成收口。heartbeat 不能作为任务取消依据。
- 模型强诊断成本高，不适合作为全站账号日常巡检默认策略。
- 发布异常处理：如果新 session 逻辑导致测试无法完成，可以临时关闭前端批量入口或把账号测试并发调低；存储 schema 按当前最优结构处理，不在运行时代码加入旧结构兼容。
