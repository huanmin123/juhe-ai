# GLM Coding Plan 三协议适配方案

> 计划 ID：PLAN-20260908T162203434Z  
> 状态：方案已确认，待代码实施  
> 范围：仅固化适配方案与验收边界；本计划阶段不修改运行代码、不启用新的 GLM 端点。

## 结论先行

智谱官方已经把 GLM Coding Plan 的三种接入方式拆成三个不同的 Base URL：Anthropic Message、OpenAI Chat Completion 和 OpenAI Response。当前仓库的 Go 实现只有三个 GLM 档案，覆盖 Chat Completions 与 Anthropic Messages，Responses 仅能通过显式 `responses -> chat_completions` bridge 承接，尚没有原生 GLM Responses 档案。

适配应新增独立的 `profile_glm_coding_openai_responses_v1`，绑定 `https://open.bigmodel.cn/api/v1`，使用通用 OpenAI v1 Responses adapter。不能把 `responses_json/responses_sse` 直接加入现有 Coding Chat 档案：两个官方端点不同，混用会把 `/responses` 发到 `/api/coding/paas/v4`，并使账户能力、健康检查、模型目录和审计事实失真。

## 1. 外部事实与官方定义

### 1.1 三个端点

官方[接入工具文档](https://docs.bigmodel.cn/cn/coding-plan/tool/others)表格给出的映射为：

| 官方名称 | Base URL | 本项目协议档案方向 |
| --- | --- | --- |
| Anthropic Message 协议 | `https://open.bigmodel.cn/api/anthropic` | `anthropic/v1` + Messages |
| OpenAI Chat Completion 协议 | `https://open.bigmodel.cn/api/coding/paas/v4` | `openai/v1` + Chat Completions |
| OpenAI Response 协议 | `https://open.bigmodel.cn/api/v1` | `openai/v1` + Responses |

同一页面的操作步骤主要举 Anthropic 和 OpenAI Chat，Responses 的请求字段、流式事件、usage 和工具语义没有展开。因此“端点已公布”是已核实事实，“所有 Responses 字段与模型均兼容”仍是待验证项。官方同时警告端点配置错误会导致 Coding Plan 配额不可用，端点选择不能由供应商名称或客户端画像隐式猜测。

本次证据覆盖的是 GLM Coding Plan；不能把 Coding Plan 的 `/api/v1` 端点反推为通用 GLM API `/api/paas/v4/` 也支持原生 Responses。通用档案继续按已验证的 Chat 能力运行，除非智谱另行给出对应官方资料。

### 1.2 工具侧特殊约束

- [Codex 接入文档](https://docs.bigmodel.cn/cn/coding-plan/tool/codex)明确要求使用 `https://open.bigmodel.cn/api/v1`、`wire_api = "responses"`，示例使用 `experimental_bearer_token`。这证明 Responses 是独立的原生入口，不是 Chat URL 的别名。
- [Claude Code 接入文档](https://docs.bigmodel.cn/cn/coding-plan/tool/claude)使用 `https://open.bigmodel.cn/api/anthropic` 和 `ANTHROPIC_AUTH_TOKEN`，不能套用 OpenAI Responses 身份。
- [最新模型说明](https://docs.bigmodel.cn/cn/coding-plan/latest-model)按工具区分上述三个 Base URL，并给出 `glm-5.3`、`glm-5.3-flash`、`glm-5-turbo` 等模型与上下文/effort 说明。页面没有给出本项目可直接当作完整 Responses 白名单的稳定协议矩阵。
- Coding Plan 只面向官方列出的工具/产品环境；通用 Agent 工具在负载高时可能是低优先级或尽力服务。该限制应作为产品提示和运行审计信息保存，不能臆造本地配额或限流 header。

## 2. 当前仓库事实

当前 Go seed 与网关约束只注册以下三个 GLM 档案：

| 档案 | Base URL | 当前真实 endpoint modes |
| --- | --- | --- |
| `profile_glm_general_openai_v1` | `https://open.bigmodel.cn/api/paas/v4/` | `chat_json`、`chat_sse` |
| `profile_glm_coding_openai_v1` | `https://open.bigmodel.cn/api/coding/paas/v4` | `chat_json`、`chat_sse` |
| `profile_glm_coding_anthropic_v1` | `https://open.bigmodel.cn/api/anthropic` | `messages_json`、`messages_sse` |

证据落点包括：

- `backend-go/projects/maintenance/internal/schema/pg_schema.go` 的 `provider_protocol_profiles` seed；
- `backend-go/projects/gateway/internal/accounts/endpoint_modes.go` 的 GLM 写入归一化与默认值；
- `backend-go/projects/jobs/internal/accounthealth/direct_input.go`、`modelcheckprofile/profile.go` 的主动检查白名单；
- `backend-go/projects/maintenance/internal/schema/model_catalog_data.go`、`backend-go/projects/gateway/internal/pricing/data_glm.go` 的 GLM 模型协议能力；
- `frontend/src/shared/providerProtocol.ts`、账户表单与导入协议中的三档案枚举。

现有 `Responses -> Chat Completions` bridge 是显式模型映射能力，且账号仍只保存 `chat_json/chat_sse`。它可以继续服务 Chat-only GLM，但不等价于 `/api/v1/responses` 原生能力。

## 3. 目标设计

### 3.1 独立档案与端点矩阵

| 档案 | 协议/端点族 | 默认 Base URL | 默认 modes | 备注 |
| --- | --- | --- | --- | --- |
| `profile_glm_general_openai_v1` | `openai/v1` / `chat_completions` | `/api/paas/v4/` | `chat_json`、`chat_sse` | 维持现状 |
| `profile_glm_coding_openai_v1` | `openai/v1` / `chat_completions` | `/api/coding/paas/v4` | `chat_json`、`chat_sse` | 维持现状；可显式作为 bridge 上游 |
| `profile_glm_coding_anthropic_v1` | `anthropic/v1` / `messages` | `/api/anthropic` | `messages_json`、`messages_sse` | 维持现状 |
| `profile_glm_coding_openai_responses_v1`（新增） | `openai/v1` / `responses` | `/api/v1` | `responses_json`、`responses_sse` | 原生 Responses；不启用隐式 bridge |

新增档案仍是 `providerCode=glm`、`accounts.type=api_key`、Bearer API Key。通用 `gatewayopenai` driver 可复用，但必须验证该 driver 对 GLM `/api/v1` 根地址的 URL 拼接、请求头过滤、JSON/SSE 事件和错误映射。

### 3.2 模型能力策略

模型目录的 `SupportedAPIProtocolsJSON` 是候选筛选事实，不能因为协议形状通用就把全部 GLM 模型标记为 `responses`。实施时采用两阶段：

1. 先以 `glm-5.3`、`glm-5.3-flash`、`glm-5-turbo` 作为待验证候选，不把候选写成已批准能力；
2. 使用可回放的 Mock Responses JSON/SSE，再用最小真实请求核验模型、上下文、reasoning、tool、usage 和错误语义，只有通过的模型才把 `responses` 写入目录并进入账户模型选择器。

如果官方后续给出明确白名单，以官方白名单覆盖候选清单。未知模型或仅 Chat 的模型必须在 Responses 档案候选阶段被拒绝，而不是运行时改投 Chat。

### 3.3 路由、状态与桥接边界

- 命中 Responses 档案时，`/responses` 与 `/v1/responses` 只发往 `/api/v1/responses`；不回退到 Coding Chat URL。
- 原生 Responses 的 `previous_response_id`、加密内容、压缩事件、托管工具等状态视为供应商/档案相关的不透明状态。不能在 GPT 与 GLM 之间自动换号或跨供应商迁移；换号前必须保持同一供应商、档案、模型和协议，无法满足时拒绝并保留原始错误。
- Chat-only GLM 的显式 `responses -> chat_completions` bridge 继续保留，但必须在审计和指标中与原生 Responses 分开；桥接不得伪造 `responses_json/responses_sse` 能力。
- Chat Completions 在上下文已物化且目标账号能力满足时仍可按现有策略跨供应商切换；该规则不扩展到原生 Responses。

### 3.4 Coding Plan 身份与凭据

上游鉴权使用 `Authorization: Bearer <GLM Coding Plan API Key>`；不生成 GPT/Codex 专属 header，不把 Claude 的 Anthropic header 套到 Responses。系统主动探针可复用已核验的静态 Coding 身份，但必须单独验证 Responses 端点是否需要不同的客户端标识。Coding Plan Key 与平台其他 GLM API Key 不互换，账户导入/编辑要显示明确警告。

## 4. 代码与文档影响面（实施清单）

1. **存储与 seed**：新增 Responses profile、端点族、capabilities、默认 URL 和唯一性回归；不得破坏同一供应商多 profile。
2. **网关账户契约**：扩展 GLM profile 常量、默认 modes、写入归一化、候选筛选、协议/模型兼容性和 URL 规则。
3. **后台检查**：补充 account health、人工测试、J3b 模型检查的 Responses JSON/SSE probe、默认 Base URL 和响应语义断言。
4. **模型与价格**：按通过验证的模型写入 `responses` 能力；补充 Responses generation/reasoning 参数能力，保持价格与 usage 归属为 `glm`。
5. **身份与驱动**：复用通用 OpenAI Responses adapter，补齐 GLM profile identity/header 白名单和 driver 回归，禁止 Chat 根地址误拼 `/responses`。
6. **前端与导入**：新增档案枚举、接入类型、默认检查模型、endpoint modes、导入/导出 round-trip、文案警告；未实现前不得把目标档案当成可导入值。
7. **桥接与切号防火墙**：保留显式 bridge；原生 Responses 不跨 GPT/GLM 或不同 GLM profile 换号，审计记录目标 profile、模型和实际上游 endpoint family。
8. **文档同步**：更新 GLM 接入、架构、导入协议、模型检查/测试说明和本计划的实施状态。

## 5. 验收与验证

### 必须通过

- 四档案的 profile、Base URL、protocol family、默认 modes 和导入导出枚举一致；旧三档案行为无回归。
- Mock 覆盖 Responses JSON、Responses SSE、上游错误、usage/reasoning 字段、工具字段、超时/取消和重试边界；可验证请求确实命中 `/api/v1/responses`。
- Chat 档案不能因请求 `/responses` 被误选；原生 Responses 档案不能被降级到 Chat bridge。
- GPT 原生 Responses、GLM 原生 Responses、GLM Chat bridge 的切号和审计结果符合上述防火墙；不透明状态跨供应商时明确拒绝。
- 仅通过模型能力目录允许的模型进入 Responses 候选；未验证模型给出可诊断错误。
- 文档、前端、后台探针和数据库 seed 的 profile ID 完成全局 `rg` 一致性检查。

### 实施后建议命令

在代码落地后运行受影响 Go 包的定向 `go test`，再运行账户导入/模型检查/网关 Mock 集成测试；真实 GLM 只使用最小、可撤销的 Coding Plan 测试请求，不把密钥、响应原文或私有环境资料写入仓库。

## 6. 未决问题与风险

- 官方“接入工具”页列出 Responses URL，但正文没有完整请求/流式/错误契约；需要以标准 OpenAI Responses 规范为基线，并用 Mock + 最小真实请求确认差异。
- 官方页面没有给出本项目可直接采用的 Responses 模型全量白名单，不能先行修改所有 GLM 模型的协议能力。
- `reasoning`、长上下文、tool/hosted tool、压缩和 usage 字段的实际返回可能随模型/套餐变化；未知字段应保留原始错误或标记未知，不静默降级。
- Coding Plan 的工具白名单、优先级和配额策略属于上游产品约束；本项目只做提示、可观测性和真实错误透传，不实现猜测性的本地配额算法。

## 7. 执行门禁

本计划按 `Explore -> Plan -> Work -> Critique -> Promote` 执行：仓库与官网取证已完成，当前停在 Plan。代码实施前先确认模型白名单与真实 Responses 最小样例；实施后由独立复审检查 URL、profile 能力、切号防火墙、Mock 覆盖和文档一致性，通过后再 Promote 到可用状态。
