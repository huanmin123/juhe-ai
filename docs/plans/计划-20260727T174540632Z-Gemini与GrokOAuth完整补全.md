## 需求目标

- 在现有 Anthropic / OpenAI OAuth 骨架上补齐 Gemini 与 Grok OAuth 的账户创建、令牌刷新、重新授权和网关派发闭环。
- 复用 `sub2api_source` 等参考项目已经验证的 OAuth 参数、PKCE、换码和刷新语义，不为相同流程另造协议。
- 前端沿用现有账户新增 / 编辑弹窗，按供应商显示授权回调 URL、Refresh Token 和直接 Access Token 入口。

## 范围边界

### 本次包含

- Gemini `ai_studio`、`code_assist`、`google_one` 三种 OAuth 模式：Google 授权链接、回调换码、Refresh Token 创建、手动刷新与重新授权。
- Gemini `ai_studio` 继续使用 Gemini Developer API native driver；`code_assist` / `google_one` 使用与其授权凭据匹配的 Code Assist runtime，不把内部 token 误交给 AI Studio 上游。
- Grok OAuth：xAI PKCE 授权链接、回调换码、Refresh Token 创建、手动刷新、重新授权和请求前自动刷新。
- Grok SSO Cookie 导入后启动 OAuth device flow，完成设备授权轮询并创建可刷新的 Grok OAuth 账户。
- Grok OAuth 继续落到 `profile_xai_openai_v1 + oauth`，仅承接 Responses JSON / SSE。
- 管理端和个人端 OAuth 路由、账户表单交互、专项回归与当前权威文档同步。

### 本次不包含

- Vertex AI、Google Workspace 管理授权或 Service Account JWT 等本次三种 OAuth 模式之外的 Google 身份链路。
- Grok OAuth / device flow 之外的 X 会话代理或浏览器自动化。
- 把 Grok OAuth 扩展到 Chat Completions；xAI API Key 仍可按档案能力使用 Chat / Responses。
- Go 后端实现或迁移。

## 实现约束

- Gemini OAuth 必须保存明确的授权模式；授权参数、上游 runtime、请求头和凭据刷新都按 `ai_studio`、`code_assist`、`google_one` 分支处理。
- `ai_studio` 使用 Gemini Developer API；`code_assist` / `google_one` 的内部授权凭据只能进入 Code Assist runtime，不能仅因账户类型同为 `google_oauth` 而共用 native 上游。
- Grok OAuth 使用 xAI 固定 CLI OAuth client、PKCE S256 和本地回调地址；保存并轮换 access / refresh token 及公开身份元数据。
- Grok SSO Cookie 只用于启动受控 device flow，创建成功后运行时使用 OAuth token；Cookie 不作为网关长期上游认证方式。
- Grok OAuth 上游固定为 CLI Responses 代理语义，不能继承 GPT/Codex OAuth 的 compact、attestation 或 Chat 兼容规则。
- OAuth 会话必须绑定发起账户作用域、一次性消费并有 TTL；token 交换与刷新复用账户代理且不得把 token 写入日志或错误文本。

- [ ] Gemini 可分别选择 `ai_studio`、`code_assist`、`google_one` 生成匹配的 Google 授权链接，并通过回调 URL 或 Refresh Token 创建 `google_oauth` 账户。
- [ ] `ai_studio` 账户调用 Gemini Developer API；`code_assist` / `google_one` 账户调用 Code Assist runtime，三种模式不混用 token 或上游。
- [ ] Grok 可生成 xAI PKCE 授权链接，并通过回调 URL 或 Refresh Token 创建 `oauth` 账户。
- [ ] Grok OAuth 令牌临期时可单飞刷新并持久化轮换结果。
- [ ] Grok 可通过 SSO Cookie 启动 OAuth device flow，轮询成功后创建与普通 OAuth 相同运行时语义的账户。
- [ ] Grok OAuth 只进入 `/responses`，Chat Completions 明确拒绝；xAI API Key 现有 Chat / Responses 能力不回归。
- [ ] 前端可按供应商完成授权、Refresh Token、直接 Access Token、刷新和重新授权交互。
- [ ] 文档不再把 Gemini OAuth 写成仅手工导入，也不再把 xAI 写成仅 API Key。
- [ ] Gemini 三种模式、Code Assist runtime 与 Grok SSO device flow 均有专项回归和前端交互证据。

## 风险与注意事项

- Gemini AI Studio OAuth 和 Gemini CLI Code Assist / Google One 使用不同上游与凭据语义；混用会得到无法由目标 runtime 消费的 token。
- Grok SSO Cookie 和 device flow 涉及短期会话、轮询间隔、过期与取消边界；不得把 Cookie 写入日志或长期运行凭据。
- Grok CLI OAuth 上游、client identity 和授权参数来自已验证参考实现，供应商若调整协议，需要通过专项回归重新核对。
- 当前工作树存在并行修改；本计划只追踪 Node / Vue OAuth 补全，不覆盖其他功能或 Go 迁移计划。
