## 需求目标

- 背景：原始审计日志需要保留请求链路，但单次请求 / 响应可能接近 `1MB`。多人或高频使用时，一天几万到几十万请求会产生不可承受的磁盘、SQLite、备份和查询压力。重复错误和重试风暴还会产生大量近似相同的失败记录，影响排障效率。
- 目标：把原始审计从“每条请求都复制完整原文”收敛为“成功请求只采样 10%，失败和异常链路必须保留”，通过 payload 压缩、精确去重、重复错误聚合和定期清理控制体积，同时不破坏失败链路排查能力。
- 交付物：审计日志保全策略设计文档、存储和日志文档同步、后续 schema / worker / API / 前端改造计划、验证清单。

## 方案概述

- 方案原则：完全成功请求默认只按 10% 稳定采样写入原始审计；失败、异常、客户端中断、流式中断和重试后成功链路必须写入原始审计。
- 数据变化：扩展 `audit_logs`，新增或替换 `audit_payload_refs`、`audit_payload_blobs`、`audit_error_groups`；大正文落到 `backend/data/audit/blobs/`。
- 接口变化：审计列表展示正文保留状态、采样原因、压缩收益和错误组；新增错误组列表和 payload 读取接口。
- 前端变化：审计页面增加事件视图和错误组视图，payload 区分完整原文、仅摘要、仅 hash、已过期和已丢弃。
- 后端变化：审计 worker 负责策略判定、压缩、去重、blob 写入、引用计数、错误指纹和清理；网关仍只做终态入队。
- 数据处理策略：当前预上线阶段可备份后重建或离线清洗本地库；源码不保留旧审计 payload 表兼容分支。

## 风险与注意事项

- 原始审计 payload 含凭据、prompt、文件内容和响应正文，对外分享日志、数据库或截图前必须移除。
- 去重只能按完全相同的原文 hash 复用，不能做相似文本合并。
- 错误聚合只做展示和排障摘要，不能删除底层事件。
- 成功请求未命中 10% 采样时不会有原始审计原文，排障只能依赖 `usage_records` 结构化事实和普通运行日志。
- 当前预上线阶段可通过备份后重建或离线清洗处理旧审计表；源码不保留旧结构兼容。
