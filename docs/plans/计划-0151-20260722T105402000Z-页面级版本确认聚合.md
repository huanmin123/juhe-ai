## 需求目标

- 将 `/my-accounts` 页面当前分散的 `providers.catalog`、`accounts.options`、`accounts.static` confirm 调度收敛为页面级有界批次。
- 热缓存首屏不阻塞；到确认周期时同一标签页、同一安全上下文最多发送一个常规 confirm。
- v2 冷启动和 changed reload 使用页面级 pre/post 稳定性批次，避免三个资源各自执行稳定性确认。
- mutation、scope 切换、KeepAlive deactivate 后的迟到 confirm / GET 不得推进 `confirmedAt` 或覆盖新缓存。
- `POST /data-changes/confirm` 在 DB access 与 System API rate limiter 中均使用 read 语义，同时保留 PostgreSQL session 权威鉴权和 session no-touch。
- 使用本地专项回归、真实隔离 PostgreSQL session / Redis smoke 和浏览器瀑布证明请求预算及一致性边界。

## 方案概述

- 新增独立纯 TypeScript coordinator，负责 activation、域登记、pre/post batch、deadline、token 冲突和 writeEpoch fencing。
- 新增 Vue lifecycle 适配器；受管页面只使用一个 scheduler，现有 cache controller 继续负责 IndexedDB、GET、delta 和 CAS。
- 首批 manifest 固定 `/my-accounts -> accounts.static / accounts.options / providers.catalog`。
- protocol 保持 v2，后端 confirm 契约和 Redis 单 EVAL 保持不变。
- rate limiter 读取已经解析的 System API DB access mode，显式 read POST 进入 read bucket。
- 新能力按页面配置启用；关闭后恢复原 resource controller 调度。

- 30s 周期探针按设计继续存在；KeepAlive 多页面历史双 confirm 边界已通过 activation fencing 修复并回归覆盖
- 若缓存不在 activation-hot 窗口（`confirmedAt` 超过 30s）或 confirm 返回 changed，仍会触发域 GET；这是正确性路径，不是多余 confirm

### confirm 为何保留

- confirm 是“版本探针”，用一次轻量请求判断多个页面域是否过期
- 去掉它会回到每资源各自重新拉列表/选项，成本更高
- 当前最佳形态：热缓存直接展示 + 有界聚合 confirm + 仅在 changed 时重拉

## 风险与注意事项

- 页面级批处理不能把同域不同 token 强行合并；无法合并就保持 unconfirmed。
- 新旧 scheduler 必须互斥，否则会在优化后产生双 confirm。
- mutation 发起时即推进 writeEpoch。
- 测试凭据只从用户授权文件读取并放进当前进程环境；禁止写入仓库。
- 上线必须等待用户另行通知。
