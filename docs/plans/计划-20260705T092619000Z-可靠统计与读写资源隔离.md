## 方案概述

- 统计准确性：使用记录、审计和日志事实先落 PostgreSQL；统计 worker 通过安全水位和 `stats_job_state` 游标推进，结果和游标同事务提交。
- 实时性策略：统计首页热窗口允许 10 分钟级刷新；范围窗口、授权窗口、TopN 和 AI 性能 summary 走独立低频任务，允许 10 到 30 分钟滞后。
- 读写隔离：前台读仍由 DB service 承接，后台重统计限制在 stats-worker；PG 连接通过 `application_name` 标识角色，通过 timeout 避免长查询无限占用。
- Redis 策略：Redis 不做备份，可在上线时清理；但清理前必须停服务并确认 Redis Streams pending/lag 为 0，避免丢未落库消息。
- 备份策略：常规上线只备份业务库 / 业务 schema；统计库、使用记录、审计和 Redis 不做默认全量备份。

## 风险与注意事项

- `statement_timeout` 会让过慢 SQL 明确失败；这比无限占用连接更可控，但需要在日志和压测中关注失败任务。
- PgBouncer 不接受 `statement_timeout` 等 startup parameter；应用必须使用连接后 `SET` 的实现路径。
- 如果 Redis Streams 没有 drain 就清空，会丢未落库消息；上线流程必须先停服务并检查 pending/lag。
- 统计窗口滞后会导致页面数字短时间不实时；这是本计划接受的取舍。
- 如果真实压测仍显示 `usage_scope_range_windows` 或其他窗口慢，需要继续做按 changed scope/date 增量刷新或更细粒度 staging。
