# 计划：F2–F4 最终请求接线 Build（信封统一收口）

- **状态**：待用户审核；审核通过前不改代码。
- **日期**：2026-10-11
- **目标契约**：[上游请求信封统一设计](../architecture/上游请求信封统一设计.md) §9（最终请求矩阵与接线契约，本日裁决）。
- **来源**：[信封差异与慢查询处置复核报告](../reports/信封差异与慢查询处置复核报告-2026-10-11.md) §3。
- **根治原则**（用户裁决）：彻底接通唯一构造源并删除旧构造路径，不做"八项差异逐点修补"的临时收敛。

## 1. 背景事实

- `upstreamenvelope.Build` 生产调用方为零（`rg "upstreamenvelope\.Build\(" --type go` 仅测试命中）：M1–M5 只完成辅助规则复用，最终请求构造（body 编码、适配器包装、`http.Request` 创建）仍在 F2/F3/F4 各自手里。
- F2 真实缺陷：同一请求 headers 段（`accountprobe/probe.go:528-541`）与 body 段（`applyCodexCompatibilityPayload:1413-1415`）**各生成一套随机身份**——`session-id` 头与 `client_metadata.session_id` 是两个不同 UUID；headers metadata 缺 `turn_started_at_unix_ms`。
- F2 为保持行为零变化屏蔽了 GLM profile（`buildUpstreamURL:1474` 注释自证），产生真实寻址差异：`/api/paas/v4/v1/chat/completions` vs 共享规则的 `/api/paas/v4/chat/completions`。
- F4 缺 `interactions` 的 `api-revision` 头写入路径之外的 `X-OpenAI-Internal-Codex-Responses-Lite` 等差异在 §9.1 矩阵内收口；F2 缺 `api-revision`（catalog 已固定 `2026-05-20`）。

## 3. 验收门禁（全步完成后）

- 生产调用图实际到达 `Build`（旧构造函数代码删除，非仅不调用）。
- Mock transport 捕获对比矩阵：三形态 × 三调用面结构等价，比较范围显式声明（探针内容字段除外）。
- 错误路径保留原始错误，无 fallback 掩盖。
- F1 `/v1` 不在范围内；完成后声明口径为"系统生成探针共用构造源"。

## 4. 风险与边界

- F2 面最大（multipart/图片音频/Anthropic/Interactions/三形态），W4 独立提交便于回滚定位。
- GLM 恢复消费 profile 改变 F2 对 GLM 账户的请求目标（多拼 `/v1` → 剥除）：这是 §9.2-5 裁决的寻址修正，上线后需观察 GLM 账户手动测试与探针结果。
- Code Assist `//` 折叠语义按 §9.2-7 独立验证；若验证发现某代理依赖非折叠形态，回到文档裁决再收敛。
