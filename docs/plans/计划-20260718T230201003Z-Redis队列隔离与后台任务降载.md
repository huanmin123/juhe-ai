# PLAN-20260718T230201003Z Redis 队列隔离与后台任务降载

> **给执行 Agent：** 实施时必须使用 `superpowers:subagent-driven-development`（推荐）或 `superpowers:executing-plans` 按任务逐项落地；每个任务遵循先写失败回归、再做最小实现、最后运行目标验证的顺序。

**目标：** 在不删除、关闭或弱化任何现有页面、接口、审计、日志、用量、统计及维护能力的前提下，隔离 Redis 队列流量，解除非核心记录副作用对网关和管理请求的阻塞，并降低后台维护任务造成的周期性延迟尖峰。

**架构：** 高性能模式固定使用 cache、state、queue 三个独立 Redis 资源；Redis Stream 的 producer、blocking consumer 与管理命令使用独立连接。记录功能继续完整运行，但审计、日志、用量索引等非核心副作用采用有界 best-effort：主请求只负责有限时投递，超时或过载时记录丢弃指标后继续，不用进程退出、无限重试或同步回退拖住主链路。大 payload 先写入持久数据目录中的有界引用文件，Stream 只传小引用；后台统计和清理入口全部保留，通过错峰、单飞、短批次和压力门控降低资源争抢。

**技术栈：** Node.js、TypeScript、Redis Streams、PostgreSQL、现有 `ingest-worker` / `stats-worker` / `ops-worker` / `temporary-maintenance-worker`、PowerShell 7、pnpm。

## 需求目标

- 背景：生产现场中 `JUHE_AI_REDIS_STATE_URL` 与 `JUHE_AI_REDIS_QUEUE_URL` 指向同一个 Redis 实例和 DB。审计、使用记录、运行日志及维护 Stream 的 `XADD`、`XREADGROUP`、`XAUTOCLAIM` 与网关并发、限流、会话和运行态命令竞争同一条 Redis 单线程执行链；审计消息曾达到数百 KB 至约 1.2 MB，日志中出现 `Redis XADD timed out after 1500ms` 和连接超时。后台清理与统计任务还会周期性与管理读请求争抢事件循环和 PostgreSQL。
- 目标：把 queue 流量从 cache/state 彻底隔离；让所有非核心记录投递有界、可丢、可观测且不阻塞主请求；让 Stream 单条消息保持小而稳定；让维护与重统计持续运行但不再集中制造长尾。
- 交付物：Redis 拓扑与运行配置收口、独立 producer/consumer 连接、有界 best-effort producer、payload 引用存储、维护调度降载、监控指标、回归脚本、真实环境 A/B 压测记录、部署与回退说明。

## 方案概述

### Redis 拓扑

```text
redis-cache  127.0.0.1:6379/0  -> 查询缓存、会话亲和缓存
redis-state  127.0.0.1:6380/0  -> 并发、限流、锁、探针、路由运行态
redis-queue  127.0.0.1:6381/0  -> usage/audit/operation/public/runtime/maintenance Streams
```

- 高性能模式不再接受 `JUHE_AI_ALLOW_SHARED_REDIS_URLS=true` 绕过；`assertDistinctRedisUrls` 按 canonical `host + port` 判断，协议、凭据和 DB 编号都不能把同一 Redis 进程伪装成不同物理资源。
- queue Redis 关闭与 cache/state 的共享客户端；每个进程内的 producer、blocking consumer、ACK/inspect 管理命令分别使用独立连接。
- queue Redis 的大 key、慢命令或 consumer 阻塞只影响记录副作用，不得拖慢 state Redis 的限流、并发与锁。

### 有界 best-effort producer

统一接口在 `backend/src/shared/bounded-redis-stream-producer.ts` 定义为：

```ts
export type RedisStreamProducerDropReason =
  | 'producer_overflow'
  | 'payload_reference_failed'
  | 'redis_connect_timeout'
  | 'redis_command_timeout'
  | 'redis_command_failed'

export interface BoundedRedisStreamProducerOptions<T> {
  name: string
  redisUrl: string
  maxItems: number
  maxBytes: number
  connectTimeoutMs: number
  commandTimeoutMs: number
  encode: (input: T) => Promise<string> | string
  enqueueEncoded: (encoded: string) => Promise<string>
  onDrop: (event: { reason: RedisStreamProducerDropReason; bytes: number; input: T }) => void
}

export class BoundedRedisStreamProducer<T> {
  tryEnqueue(input: T): boolean
  snapshot(): BoundedRedisStreamProducerSnapshot
  close(): Promise<void>
}
```

- `tryEnqueue` 只做有界内存入队并立即返回；Redis I/O 在 producer pump 中执行，不进入网关或管理请求 await 链。
- 默认本地上限：usage 5000 条/32 MiB，audit 256 条/32 MiB，operation/public 各 2000 条/8 MiB，runtime 沿用现有采样和上限，maintenance 1000 条/4 MiB。
- queue Redis 本机连接超时设为 300 ms、单次 `XADD` 命令预算 100 ms；超时后销毁 dedicated client、记录 drop、继续下一条，不无限重试，不触发 `scheduleProcessFatalError`。
- 功能正常时仍持续写入全部类型；只有异常和过载条目允许丢弃。

### payload 引用化与限长

`backend/src/shared/queue-payload-reference.ts` 固定以下 envelope：

```ts
export type QueuePayloadEnvelope =
  | { version: 1; kind: 'inline'; payload: string }
  | {
      version: 1
      kind: 'file_ref'
      id: string
      relativePath: string
      encoding: 'gzip'
      rawBytes: number
      storedBytes: number
      sha256: string
      createdAt: string
    }
```

- 编码后小于等于 64 KiB 时内联；超过 64 KiB 时异步 gzip 写入持久 `data/queue-payloads/<两位分片>/<id>.json.gz`，Stream 仅写 envelope。
- `RedisStreamQueue.enqueueEncoded` 对最终 XADD 字段执行 128 KiB 硬上限；超过上限直接拒绝并进入 producer drop 统计，禁止把 MB 级字符串送进 Redis。
- `readNew` / `claimPending` 解析 `file_ref` 后校验相对路径、sha256 和 rawBytes，再还原原始 JSON；成功 `XACK + XDEL` 后删除引用文件。
- 引用缺失或校验失败属于 poison message：记录原因后 ACK，不能让 consumer 永久重试卡住同一条消息。
- `temporary-maintenance-worker` 每小时清理创建时间超过 24 小时且没有活跃 Stream 消息引用的孤儿文件；单轮最多 500 个，每 50 个让出事件循环。

### 后台调度降载

- `WorkerScheduler.schedule` 增加 `jobClass: 'hot' | 'normal' | 'maintenance'`、`jitterMs`、`maxRunMs` 和 `shouldDefer`；延期计入 `deferredCount`，不记为成功或失败。
- `ingest-worker` 热写消费优先；audit hot retention 从每分钟改为每 5 分钟，data retention 从每 10 分钟改为每 30 分钟，API Key/账户清理重试从每分钟改为每 5 分钟。任务入口与数据保留目标不变。
- `stats-worker` 现有 30 分钟与 6 小时窗口保留，但初始时间至少错开 90 秒；同一时刻最多运行一个 maintenance-class 任务。
- 清理单轮只执行有限批次：审计 retained cleanup 每批不超过 100、每轮不超过 2 批、批间 25 ms；usage cleanup 每轮不超过 2 批；未清完数据留给下一轮。
- 当 queue stream lag 超过 5000、producer 本地 pending 超过 50%、或本进程事件循环 P95 超过 100 ms 时，maintenance-class 当前轮延期 60 秒；延期不删除任务。

## 发布与回退

### 发布顺序

1. 先部署 Redis queue 6381，并验证 `PING`、认证、目录权限和持久化配置。
2. 发布支持 best-effort 与引用 payload 的应用版本，但不切换 URL；本地/预发完成回归。
3. 在维护窗口停止应用，记录旧 6380 Stream pending/lag 和时间戳；不要求 drain 为零。
4. 修改生产 `JUHE_AI_REDIS_QUEUE_URL=redis://...@127.0.0.1:6381/0`，确保 cache/state 不变并移除共享放行变量。
5. 启动后完成页面、API、网关、日志、审计、用量、统计、worker 和维护入口冒烟，再进入 30 分钟 A/B。

### 回退条件

- 管理或网关主请求错误率较基线增加超过 0.5%。
- state Redis P99 仍高于 20 ms 且确认不是外部流量变化。
- 审计、用量、日志任一查询/详情入口出现契约错误、500 或持续无法写入。
- payload 引用无法被 consumer 还原，连续 5 分钟 poison/drop 比例超过入队量 1%。

### 回退动作

1. 停止应用，保留 6381 数据目录和运行日志用于排障。
2. 恢复上一已验证应用构建和上一份环境文件；如上一构建要求 queue/state 共享，则把 queue URL 临时恢复为旧值。
3. 启动并执行同一套功能冒烟；接受切换过程中 queue 消息丢失，不编写双读双写兼容。
4. 不删除 6381 引用文件和 Stream，待定位完成后再按明确路径清理。

## 风险与注意事项

- best-effort 会让过载窗口中的部分非核心记录缺失；页面功能仍存在，但记录数量可能少于实际请求数量，这是用户已确认的性能优先取舍。
- payload 引用依赖 server 与 ingest-worker 共享同一个持久 data 根目录；部署文档必须检查路径一致，不能写到 release 临时目录。
- 延长清理间隔会增加短期磁盘占用；必须通过表大小、引用文件数量和 oldest age 监控，而不是恢复高频全量清理。
- producer timeout 后必须销毁该 dedicated client，避免超时命令在后台继续堆积。
- 不能把 state Redis 故障降级为空运行态；本计划只允许记录副作用 best-effort，限流、并发和锁仍按现有明确错误契约处理。
