## 需求目标

- 多 API Key 是核心业务能力；账户变为多 Key 时保存必须成功，并在同一次业务写入中关闭余额查询、停止调度和阻止旧查询结果回写。
- 运行时账户投影保留 `service_tier_override` 与 `reasoning_effort_override`，确保 Chat、Responses、OAuth 和显式 bridge 使用账户覆盖。
- “我的使用记录”展示实际服务等级与思考级别；首字和总耗时合并为“延迟”；成本明细只解释计价模型、实际档位、计价来源、最终单价和小计。
- 审计详情区分 HTTP 客户端完成时间与后台审计完成时间；响应后的 Redis/usage/审计收尾不再占用账户并发槽。
- 大审计 payload 的摘要、base64 和 JSON 编码不得在 server 主线程形成无界同步工作；请求 body 在途 lease 保持到响应 `finish/close`。
- 模型可信度增强按 `PLAN-0095` 执行，先恢复回归门禁和官方目录，再落 Token 差分、受控 observation、预聚合基线与中文证据状态。

## 范围边界

- 不为多 Key 实现逐 Key 余额，也不因余额功能阻断多 Key 保存；恢复单 Key 后余额查询仍需人工重新开启。
- 服务等级主列表取 `billedServiceTier`，思考级别取最终上游请求的 `effectiveReasoningEffort`；空值和默认档位不制造无信息标签。
- 成本明细不能用当前目录重新解释历史费用，必须使用请求时锁定的计价事实；若现有契约缺少来源/倍率/最终单价，按当前 schema 一次补齐。
- 高性能模式的“请求时”以使用记录进入 Redis Stream 前为界，不以 consumer 最终落库时间为界；backlog 期间目录变更不得改写消息中已固化的计价事实。
- HTTP 客户端完成与审计 finalize 是两个时间点；后台收尾可以继续，但不能伪装成“返回客户端”或继续占账户并发槽。
- 审计降级必须保留大小、哈希、overflow/captureStatus 和定位元数据，不通过提高 Redis `maxmemory` 掩盖主线程序列化问题。
- 模型身份是统计证据，不用 Pro、Max、service tier 等账户权益作为真假硬证据，不读取普通用户请求正文训练标签。

## 风险与注意事项

- 使用记录 schema、计费事实和模型可信度 observation 都必须同步 SQLite/PostgreSQL，生产只使用单独审核的一次性迁移 SQL，不在运行路径写旧结构兼容。本批生产模型可信度是首次建表，迁移对象为 8 张可信度表和 11 个索引；其中 cohort 来源计数必须创建 `idx_model_trust_window_sources_cohort(cohort_key_hmac, upstream_bucket_hmac)`。生产当前不存在旧可信度表，不执行清表或删除聚合游标；只有曾试跑旧聚合的非生产环境才在停 `stats-worker` 后离线重建派生表，保留 dataset observation。
- 并发槽提前释放后，账户副作用仍需保证幂等、错误可观测和进程退出前可排空；不能简单丢弃收尾 Promise。
- 审计编码预算不能破坏 413 无正文契约，也不能让成功审计静默缺失；降级状态必须可检索、可解释。
- 模型可信度范围大，按 `PLAN-0095` 的 Task 1 至 Task 7 逐层验收；未形成独立来源稳定窗口时生产只诊断，不自动停号或改账。
- 原 `F:\sub2api-lite` 工作区存在并行开发中的未提交代码和文档，本批次只在新 worktree 实现，最终同步必须再次执行命名 stash、fast-forward、恢复和状态核验。
