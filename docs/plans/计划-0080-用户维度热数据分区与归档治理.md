## 需求目标

- 背景：生产表监控显示 `usage_record_shard_entries`、`usage_records`、`usage_scope_range_windows` 等表增长快，且索引体积明显大于表体积。当前很多索引服务低频全局筛选，但产品使用场景以用户维度为主。
- 目标：建立长期热数据治理模型，把高增长表统一收敛到“用户维度 + 日期窗口 + 分区 / shard + 归档 + 索引白名单”。
- 交付物：长期设计文档、查询契约、schema / 索引调整、SQLite 与 PG 双模式落地、归档与表监控增强、回归和压测记录。

## 方案概述

- 方案原则：高增长表先按用户和日期收敛，再做筛选；默认今天；近期在线最多 7 天；历史进入归档。
- 数据变化：拆分 raw 明细在线保留和归档保留设置；PG 高增长表改时间分区；SQLite 高增长明细使用日期 segment / shard。
- 接口变化：高增长 raw 列表接口要求 `systemAccountId` 和日期 cursor，不再返回精确全量 `total`。
- 前端变化：管理员进入高增长 raw 页面先选择用户；未选用户时只展示摘要和用户选择器。
- 后端变化：repository 禁止无用户 / 无日期窗口扫大表；统计窗口由全范围物化改为热窗口 + 按需后台生成。
- 数据处理策略：上线窗口按当前 schema 离线归档或重建旧数据；运行路径不保留旧结构兼容分支。

## 风险与注意事项

- 删除索引会改变低频筛选体验，需要前端明确日期窗口和按需诊断入口。
- PG 分区涉及主键 / 唯一约束重设计，不能在运行路径保留旧表兜底。
- 归档数据不参与常规页面查询；恢复归档必须是显式维护动作。
- 管理员全局 raw 明细能力会收紧，需用预聚合摘要和离线导出替代。
- 发布异常处理：上线前备份业务库和配置；统计域、usage shard、PG 分区和归档数据按当前 schema 离线重建或回滚到同一数据契约下的已验证构建。
