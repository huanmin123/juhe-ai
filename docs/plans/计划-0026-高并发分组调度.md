# PLAN-0026 高并发分组调度

## 基本信息

- 编号：PLAN-0026
- 状态：草稿
- 创建时间：2026-05-22
- 需求来源：用户反馈同一个 API Key 大量并发时，请求会持续打入单个可用账号，导致上游排队、超时和用户长时间无响应。
- 关联模块：分组 / AI 账户 / API Key / 网关 / 调度运行态 / 使用记录 / 文档 / 验证

## 需求目标

- 新增高并发分组设计，用于同一个 API Key 被大量用户或程序并发调用时协调账号负载。
- 保留个人分组当前轻量行为，不因高并发场景改变默认用户体验。
- 高并发分组优先尊重账号配置，包括超级优先、优先级、备用、权重和并发上限。
- 调度不默认依赖上游状态码，而是依据本地可观测体验信号分流：当前并发、分组排队、请求耗时、首段等待、近期超时和质量缓存。
- 性能优先作为实现地基：高并发策略不能在每次请求里增加额外数据库往返、扫描历史明细、复杂全局锁或无界排序。

## 范围边界

本计划当前只进入设计评审，不改代码。

后续实现范围暂定：

- 分组类型：`personal` / `high_concurrency`。
- 高并发调度策略：软并发轮转、快速优先、慢请求分流、备用账号排队启用、分组级短队列。
- 绑定级调度配置：权重、软并发覆盖、本地超级优先、本地备用。
- 网关运行态：账号当前并发、分组等待、慢请求计数、最近分配时间等单节点易失指标。
- 热路径性能约束：复用一次运行时快照，候选账号 O(n) 评分，运行态 O(1) 更新，本地队列有上限且可快速失败。
- 页面：创建 / 编辑分组时选择分组类型，高并发分组提供中文策略配置。

暂不做：

- 分布式队列、多实例共享调度态或 Redis。
- 把慢请求分流直接写成账号异常。
- 主动中断或迁移已经发往上游的请求。
- 依赖上游状态码白名单做默认账号健康判断。

## 验收标准

- 用户确认高并发分组命名、配置项、策略优先级和待复查问题。
- 实现后个人分组行为不回归。
- 实现后同 API Key 大量并发时，请求能按软并发、权重和快速优先分散到多个账号。
- 实现后高并发策略不新增每请求额外 DB 查询，调度计算保持单分组候选 O(n)，本地选号耗时达到压测目标。
- 慢请求和分组排队只影响新请求调度，不主动中断已发出的请求。
- 权重、超级优先、备用和授权账户本地配置在高并发分组中生效且作用域正确。

## 风险与注意事项

- 会话亲和与快速优先存在天然冲突，需要确认高并发分组是否默认允许达到软并发后打破亲和。
- 流式长请求可能长期占用并发槽，后续可能需要按请求类型设置不同软并发或慢请求阈值。
- 高并发实现必须先占用账号并发槽再发起上游请求，并保证所有退出路径释放，否则会在瞬时并发下继续集中打到同一个账号。
- 本地队列满、等待超时和客户端等待中断没有上游尝试，但仍需要记录为网关本地失败，便于统计和排障。
- 单节点易失运行态在重启后会丢失，这符合当前轻量边界，但后续多实例部署需要重新设计共享调度态。
- 分组繁忙对外返回 `429` 还是 `503` 需要结合客户端重试行为确认。
