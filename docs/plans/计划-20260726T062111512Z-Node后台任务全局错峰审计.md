# PLAN-20260726T062111512Z Node 后台任务全局错峰审计

## 基本信息

- 计划 ID：`PLAN-20260726T062111512Z`
- 状态：调研完成，待实施决策
- 创建时间：2026-07-26
- 需求来源：用户要求仅针对 Node 后端，全系统检查周期 Job、统计聚合和大批量任务是否需要错峰，避免集中触发形成资源尖峰
- 执行者：Codex / 项目维护者

## 需求目标

- 全量盘点 Node 后端常驻 worker、server 运行态和 DB service 中的周期任务与延迟触发器。
- 为每项任务记录角色、周期、初始延迟、单轮上限、并发、外部 I/O、目标存储、单实例与多实例语义。
- 识别启动风暴、固定相位重合、整点 / 整日集中、同一批候选同时到期、数据库写竞争和上游请求突发。
- 区分适合稳定错峰、随机抖动、事件驱动、游标小批、租约 claim 或维持现状的任务，避免一刀切加入随机延迟。
- 给出风险分级、实施分期、回退边界和可量化验证方案；本阶段不直接改变生产调度行为。

## 范围边界

### 本次包含

- `backend/src/modules/background/` 注册的全部 Node 后台任务。
- Node `server`、`worker`、`db-service` 及共享基础设施中的常驻计时器、周期维护和队列补扫。
- stats / ops / ingest 各角色的聚合、窗口刷新、清理、探针、保活、预热和重试任务。
- standalone 与 performance 两种 Node 运行模式下的单实例、多副本、锁、租约和 owner 边界。
- 现有回归、性能脚本和运行态指标对错峰改造的覆盖缺口。

### 本次不包含

- Go 后端、Go worker、Asynq 或 Go 迁移实现。
- 直接修改生产周期、批次、并发、业务状态或数据库 schema。
- 没有证据支撑的统一随机化；请求超时、短暂 retry timer 和纯 UI timer 不作为周期 Job 改造对象。
- 真实生产压测、生产部署或外部上游请求。

## 调研方法

1. 从任务注册表、`startBackgroundJobs()`、`setInterval`、自调度 `setTimeout` 和队列 retry 入口建立全集。
2. 按 worker 角色与资源类型分组，检查固定相位和共享资源冲突。
3. 对候选量可能随账户、用户、记录或表数量增长的任务，核对批次、并发、游标、让出和租约。
4. 对 performance 多副本检查 single-owner、consumer group、`SKIP LOCKED`、generation 与幂等语义。
5. 使用现有回归与静态证据交叉验证；没有真实负载证据的结论明确标注为待压测。

## 验收标准

- Node 生产常驻任务入口有可追溯全集，没有只审计 `background-jobs.ts` 的盲区。
- 每个高风险结论都包含代码位置、触发条件、负载增长维度和现有保护。
- 明确哪些任务必须错峰、哪些只需按候选到期、哪些不能随机化。
- 方案覆盖重启、多个 Node 副本、时钟漂移、任务超时、跳过 / 补跑、租约失效和监控可见性。
- 报告与计划索引已更新，且未把调研结论冒充真实生产压测结果。

## 风险与回退预案

- 错峰会增加数据新鲜度延迟，统计类任务必须先定义最大允许滞后再设置抖动范围。
- 随机抖动如果每次重启重算，会造成不可预测和测试不稳定；优先使用按任务 / 账户 ID 派生的稳定抖动。
- 多实例任务不能只靠不同启动延迟防重；需要单 owner、租约、claim 或幂等写入保证正确性。
- 高频事件驱动写队列不应人为增加秒级延迟；此类链路优先微批、背压和合并，而不是周期错峰。
