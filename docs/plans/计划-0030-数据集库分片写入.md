## 需求目标

- 背景：当前统计数据集域已经由数据集目录库和 usage shard 文件组成；数据集目录库保存审计、操作日志、运行日志索引、模型检测、清理目标和 shard 元数据，新写入的 `usage_records` 保存到多个本地 SQLite shard 文件。
- 目标：固定当前 shard 模型，让 `usage_records` 只走 usage shard 写入、查询、统计聚合、清理和重建链路；保留现有 API 响应、统计口径、额度判断和轻量部署边界。业务库必须保护，数据集目录库、usage shard 和统计结果库都允许删除重建。
- 交付物：分片设计文档、配置和 schema 方案、usage shard writer pool、明细查询适配、per-shard 统计游标、清理 / 重建 / 表监控改造、停机切换和验证记录。

## 方案概述

- 方案原则：通过多 SQLite shard 文件拆开 `usage_records` 单文件写锁；统计结果库和对外 API 响应结构保持不变。
- 数据变化：新增 usage shard root、shard count 配置、usage shard catalog、per-shard 统计游标和 writer 运行态指标；`usage_records` 从数据集目录库演进到 shard 文件。
- 接口变化：外部管理 API 和 `/v1` 网关响应不变；使用记录列表和详情内部改为 shard locator 查询。
- 前端变化：第一阶段不改变使用记录、统计、AI 性能和表监控主流程；表监控需要新增 shard 维度展示。
- 后端变化：新增 usage shard writer pool；统计 worker、记录清理、重建脚本和表监控改为 shard 感知。
- 数据处理策略：业务库是必须保护的恢复事实；数据集目录库、usage shard 和统计结果库是可重建统计域。预上线和本计划默认可以丢弃历史 usage 与历史统计，从新请求重新累计；历史数据核查只允许停机离线处理，不进入正常运行路径。

## 风险与注意事项

- 风险 1：跨 shard 列表分页实现不当会引入大范围扫描。规避方式是候选 shard 按日期窗口收敛、每个 shard 有有限查询上限，默认列表保持最近时间优先。
- 风险 2：per-shard 统计游标如果不和统计结果同事务提交，会导致重复或漏统计。规避方式是统计结果 upsert 和游标推进必须同在统计结果库事务中。
- 风险 3：usage shard 写入提速后，账号 `last_used_at` 业务库更新可能成为新的写锁来源。规避方式是把该字段改为节流合并队列。
- 风险 4：shard count 上线后直接修改会让已写入记录定位失效。规避方式是 shard count 写入 catalog 和 id / path 规则，扩容另开 rebalance 计划；历史 usage 可放弃时，不为既有记录额外维护复杂重定位。
- 风险 5：best-effort 队列仍可能在进程崩溃或队列溢出时丢 usage。规避方式是保留现有轻量默认，同时预留 durable spool 模式。
- 发布异常处理：上线前必须备份业务库和 `backend/.env`；数据集目录和统计结果库按需备份。如分片异常，停服务后恢复到同一数据契约下的已验证构建和配置。数据集目录库、usage shard 和统计结果库可清空或重建；业务库必须保留。
