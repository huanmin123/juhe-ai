## 需求目标

- 背景：三库拆分后，业务库、统计数据集库和统计结果库已经隔离，但统计数据集库内部仍是单 SQLite 文件；`usage_records`、审计、操作日志、运行日志索引等高频事实共享同一把写锁。最热的 `usage_records` 仍可能在并发请求下拖慢批量落库和统计推进。
- 目标：先把 `usage_records` 从单数据集库表演进为多 SQLite shard 文件并行写入，保留现有 API 响应、统计口径、额度判断和轻量部署边界。
- 交付物：分片设计文档、配置和 schema 方案、usage shard writer pool、明细查询适配、per-shard 统计游标、清理 / 重建 / 表监控改造、迁移和验证记录。

- 引入 Redis、Kafka、PostgreSQL、ClickHouse 或外部分布式队列：本计划继续保持单机本地 SQLite 轻量部署。

## 方案概述

- 方案原则：通过多 SQLite shard 文件拆开 `usage_records` 单文件写锁；统计结果库和对外 API 响应结构保持不变。
- 数据变化：新增 usage shard root、shard count 配置、usage shard catalog、per-shard 统计游标和 writer 运行态指标；`usage_records` 从数据集目录库迁移到 shard 文件。
- 接口变化：外部管理 API 和 `/v1` 网关响应不变；使用记录列表和详情内部改为 shard locator 查询。
- 前端变化：第一阶段不改变使用记录、统计、AI 性能和表监控主流程；表监控需要新增 shard 维度展示。
- 后端变化：新增 usage shard writer pool；统计 worker、记录清理、重建脚本和表监控改为 shard 感知。
- 数据处理策略：预上线可以丢弃统计相关历史或只保留 legacy fallback；需要历史明细时，停机后按 `created_at + hash(id)` 拆入 shard。统计结果库可以从 legacy 和 shard 输入源重建。

## 决策记录

| 日期 | 决策 | 原因 | 影响 |
| --- | --- | --- | --- |
| 2026-05-24 | 第一阶段只分片 `usage_records` | usage 是最热写入表，收益最大，且不依赖跨库外键 | 审计、操作日志、运行日志和模型检测保持现有数据集目录库 |

## 风险与注意事项

- 风险 1：跨 shard 列表分页实现不当会引入大范围扫描。规避方式是候选 shard 按日期窗口收敛、每个 shard 有有限查询上限，默认列表保持最近时间优先。
- 风险 2：per-shard 统计游标如果不和统计结果同事务提交，会导致重复或漏统计。规避方式是统计结果 upsert 和游标推进必须同在统计结果库事务中。
- 风险 3：usage shard 写入提速后，账号 `last_used_at` 业务库更新可能成为新的写锁来源。规避方式是把该字段改为节流合并队列。
- 风险 4：shard count 上线后直接修改会让旧记录定位失效。规避方式是 shard count 写入 catalog 和 id / path 规则，扩容另开 rebalance 计划。
- 风险 5：best-effort 队列仍可能在进程崩溃或队列溢出时丢 usage。规避方式是保留现有轻量默认，同时预留 durable spool 模式。
- 回滚建议：上线前备份业务库、`backend/.env` 和数据集目录；如分片异常，停服务后恢复上一版代码和配置。统计数据集 shard 和统计结果库可清空或重建；业务库必须保留。
