# 计划：AI 问答免 Key 直调内部通道（去「AI 对话 API Key」，不落使用日志）

- 状态：已实施（2026-10-24 落地，W-A/W-B/W-C 三批完成）
- 提出时间：2026-10-24
- 提出人：维护者（huanmin）
- 归属：chat 域（AI 问答）+ 网关 preauth 鉴权链 + 媒体任务归属

## 1. 背景与用户裁决

AI 问答（管理后台 my-chat 家族）当前每次为会话自动创建/自愈一个「AI 对话 API Key」（`purpose='chat'`，`EnsureChatAPIKey` 自愈链），并以它作为 Bearer 凭证驱动进程内 /v1 网关链完成对话派发。用户裁决：

1. **该 Key 整条线去掉**——AI 问答是内部自用测试工具，不再自动新建 API Key，API Key 页面不再出现；
2. **对话流量不落使用日志**——`usage_records` 完全不写（不是落 NULL 行，是零记录），用量页面不出现内部对话行；
3. **调度直接到账户**——会话绑定账户后直接钉住该账户（现有机制，保持）；
4. 调度偏好也只保留系统内置「默认调度偏好」，其余已随 2026-10-24 默认资源归一清除（已完成）。

### 已确认的架构决策（2026-10-24 用户拍板）

- **路线 A（免 Key 直调，复用网关管道）**：AI 问答不进 Key/路由/分组候选选择，但底下仍复用网关的协议转换/流式/切号管道——跨协议账户（anthropic/gemini/桥接）、工具/图片/压缩、多轮对话全部继续可用。否决了「探针式完全直连」（需重写 chat 子集 + 双轨维护，成本大）。
- 调度配置丢弃、历史悬空引用接受（默认资源归一同批裁决）。

## 2. 现状取证结论（2026-10-23/24，file:line 均为当时工作区状态）

### 2.1 Key 在 chat 域是数据归属主键（去掉它必须连带四处）

1. **鉴权注入**：5 条生成路径（`internal/chat/stream_execute.go:107`、`compaction_service.go:635`、`generation_websearch.go:96`、`generation_images.go:163`、`generation_media.go:309-313`）把 chat Key 明文放进内部请求 `authorization` Header，经 `chatGatewayExecutor.Dispatch`（cmd/juhe-ai-gateway/chain_chat.go:117-173）驱动 /v1 链。
2. **会话模型**：`chat_conversations.api_key_id`（可空列）+ `api_key_name_snapshot NOT NULL`——会话创建即绑定 chat Key（maintenance schema pg_schema_chat.go:19-20）。
3. **媒体任务归属**：`media_jobs.api_key_id NOT NULL`，归属链 `GetByIDAndAPIKey`（gatewaymedia/jobsrepo.go:234）与列表/管理面过滤全按它（经 api_keys join 推 owner）。
4. **自愈链**：`EnsureChatAPIKey`（chain_chat_keys.go:67）在会话发送时自愈补齐默认分组→默认路由→chat Key。

### 2.2 免 Key 免日志的现成先例与接缝

- **免日志先例**：deployment-smoke 旁路（gatewaypreauth/preflight.go:203-226）=「合成身份 + RecordUsage=false」——内部通道复用同一模式。
- **usage 落库路径**：chain_v1.go 装配 auditCapture/usage sink（:282-313）→ `FinalizeHandledUpstreamResponse`/`finalizeStreamFailure` → spool → jobs 落库。装配点按内部身份换 no-op sink，成功/失败/重试全路径即无记录。
- **安全先例**：`chatDispatchTarget` 用未导出 context key 保证外部 HTTP 不可伪造（chain_chat_dispatch.go:44-77）——内部身份通道同构。
- **现成接缝**：preauth 的 `req.Runtime` 预置短路（preauth.go:125-127）；preflight 的 `options.Identity` 注入分支（preflight.go:233-235，跳过 runtime 解析）与 `CandidateAccounts` 注入分支（:590-605，跳过 normal 路由策略——chat 覆盖已在消费）。

### 2.3 无 Key 下各字段的消费面结论

| 字段 | 结论 |
| --- | --- |
| `SystemAccountID` | **必须有值**（=会话 owner）：审计归属、熔断维度、分组解析（EnabledGroupIDs）全依赖 |
| `APIKeyID` | **空串全消费点容忍**：usage 列可空（orNil→NULL，不进 api_key shard 目录）、审计 BindContext 空串不覆盖、前端用量列表按 name-map 水合（NULL 无名字不报错）——且本计划下 usage 整体不落库 |
| `APIKeyRecord` | **nil 即配额/策略面整体跳过**（authorizationpreflight.go:93、107）——内部不计费不限额，语义正确 |
| 配额/限流 | 全部为按身份键的增量计数，跳过=少加，无共享计数器破坏；在途预留不 reserve 无泄漏 |
| 审计 | **保留**（待审核确认点①：区别于使用日志，audit_logs 是排障面，生产已有 5% 成功采样率治理；内部对话排障需要 trace） |
| prometheus 指标 | 保留（聚合指标非使用日志） |

### 2.4 调度直钉账户已存在

会话绑定账户（AI 问答会话账户唯一绑定设计 §5/§7）后，`chatDispatchTarget` 把候选窗口收敛为该账户单元素、绕过路由/分组候选与冷却窗口、禁用 Key 分组回退逃逸（chain_chat_dispatch.go 全链语义）。免 Key 后该机制原样保留，仅身份源改为内部通道。

## 3. 方案设计

### 3.0 实施结果（2026-10-24 已落地）

1. **AI 问答不再有「AI 对话 API Key」**：`chain_chat_keys.go` 整文件删除（`EnsureChatAPIKey` / `FindChatAPIKey` 与默认分组、默认路由自愈随文件删除）；新建 AI 问答会话不再写 `chat_conversations.api_key_id`（列保留存历史，新行为空串），`api_key_name_snapshot` 写空串；API Key 管理页面不再出现「AI 对话 API Key」；发送前置校验不再校验 Key，改为只校验会话绑定账户（数据范围内存在且启用）。
2. **对话派发改走「内部身份通道」**：进程内 `chatGatewayExecutor` 派发时注入未导出的 context 身份（会话归属系统账户 `ownerID`），`/v1` 链入口把该身份落到 `GatewayRequest.InternalOwnerSystemAccountID`；preauth 检测该字段非空即跳过 API Key 抽取/校验/认证前熔断记录/用户请求限流（客户端 IP 黑名单与认证前熔断按 ClientIP 计，内部请求无客户端 IP 故为 no-op）；preflight 改走 `options.Identity` 注入分支，不解析 API Key runtime，`APIKeyRecord == nil` 使 Key 配额与在途成本预留整体跳过（内部不计费不限额）。安全边界：该身份只能由进程内代码赋值（context key 为未导出结构体类型），不经任何 header / query / body 承载，外部 HTTP 请求无法构造；调度仍钉住会话绑定账户（`chatDispatchTarget` 机制不变，仅身份源改为内部身份字段）；生图开关载体从「gateway key 运行时视图」改为直读 `system_accounts.image_generation_enabled`（仅 active 账户生效），语义不变。
3. **对话流量零使用日志**：`GatewayRequest.SuppressUsage` 随请求置位，经 `GatewayFailureUsageContext.SuppressUsage` / `GatewayUsageContext.SuppressUsage` 投影到 `UsageRecordInput.SuppressUsage`（该字段 `json:"-"`，永不序列化，spool 落盘契约零变化）；持久化唯一闸口在 `gatewayusage.FinalizationDispatch.DispatchUsageRecord` 入口第一行丢弃抑制记录（该入口同时覆盖「正常入队 task」与「队列满溢出 spool」两条投递臂；`spooledUsageRecorder.EnqueueUsageRecord` 保留第二道保险，兜住绕过 finalization 直投 recorder 的路径）——成功、失败、重试、models 快速路径、媒体终态全部不落 `usage_records`，也不落 spool。审计日志保留（audit_logs 是排障面）；Prometheus 指标保留。
4. **media_jobs 归属改列**：新增 `owner_system_account_id text NOT NULL DEFAULT ''`（PG 与 SQLite 同构，加法式 ensure + 存量回填 `UPDATE ... FROM api_keys`）；`api_key_id` 列保留为历史审计列，不拆。归属语义分流：外部 `/v1` 媒体任务面保持 API Key 级隔离（仍用 `GetByIDAndAPIKey` / `ListByAPIKey*`）；内部通道（AI 问答）按 `owner_system_account_id` 归属（新方法 `GetByIDAndOwner` / `ListByOwner` / `ListByOwnerAndKind`）；用户面详情 `GetByOwnerAndID` 与管理面 `OwnerSystemAccountID` 过滤切到 owner 列，不再经 `api_keys` join。回填先于任何 `purpose='chat'` Key 删除执行（join 需要 Key 行在位）。

### 3.1 内部身份通道 + 免日志（gatewaypreauth + chain_v1）

1. 新增未导出 context 类型 `chatInternalIdentity{OwnerSystemAccountID string}`（cmd 层，同 chatDispatchTarget 模式，附外部不可伪造注释）。
2. `preauth.go` `ResolveGatewayRuntimeAsync` 前置分支：检测内部身份 → 跳过 Key 抽取/校验/熔断记录/用户限流，装配合成 `req.Runtime`（`APIKey=nil`，`SystemAccountID=owner`）。client IP 黑名单与认证前熔断**保留**（按 ClientIP 计，无害）。
3. **usage 全关（实施修正：结构性闸口方案，非 per-request no-op sink）**：原方案「chain_v1.go 的 auditCapture/usage sink 装配点按内部身份分支，换 no-op 实现（RecordUsage=false 语义，deployment-smoke 同款）」不可行——usage 实际有四类写入面（`gatewayusage.Service.dispatch`、`chainFinalizationUsage`、`usageDispatchAdapter`、媒体终态），其中 `engine.Usage` 与 `chainFailureDispatcher` 是进程级端口，无法按请求替换，装配点分支换不掉全部写入面。实际采用「记录自带抑制标记 + 唯一持久化闸口丢弃」的结构性方案：`GatewayRequest.SuppressUsage` 随请求置位，经 `GatewayFailureUsageContext.SuppressUsage` / `GatewayUsageContext.SuppressUsage` 投影到 `UsageRecordInput.SuppressUsage`（`json:"-"`，spool 落盘契约零变化），主闸口在 `gatewayusage.FinalizationDispatch.DispatchUsageRecord` 入口第一行丢弃——该函数有正常入队与队列满溢出 spool 两条投递臂，闸口必须在入口而非 recorder（溢出臂绕过 recorder 且标记不序列化，jobs 侧读回无法识别）——成功、失败、重试全路径零 spool 记录；`spooledUsageRecorder.EnqueueUsageRecord` 保留第二道保险；`callerTier.RecordRequest`（chain_v1.go:220-222，需 Runtime.APIKey）随 `APIKeyRecord == nil` 同步跳过。
4. preflight 调用方改传 `options.Identity{SystemAccountID: owner, APIKeyID: ""}` → `apiKeyID==""` 使 preflight.go:270 的 401 门不触发、配额段跳过（:802-812）。
5. `chain_chat_dispatch.go` 的 `chatDispatchSystemAccountID`（:244-249，原读 `req.Runtime.APIKey.SystemAccountID`）身份源改为内部身份 context。
6. 护栏测试：外部 HTTP 请求无法构造该未导出 context key（复用 `TestChatDispatchTargetFromContextRejectsExternal` 形态）。

### 3.2 chat 执行器与生成路径去 Key

1. 删除 `chain_chat_keys.go` 整文件（chatAPIKeyProvider、EnsureChatAPIKey、FindChatAPIKey、ensureDefaultGPTGroup/ensureDefaultRouteStrategies 自愈）。
2. `generation_deps.go`：删 ChatKeys 端口与 `requireOwnedApiKey`（:121-135）。
3. 5 条生成路径删 `requireOwnedApiKey` 调用与 `authorization` Header 注入；`input.apiKey` 参数族随删。
4. `chatGatewayExecutor` 携带会话 owner（WithChatDispatchAccount 同款 per-session 形态），Dispatch 注入内部身份 context。
5. 会话模型：`chat_conversations.api_key_id` **停止写入**（列保留存历史不拆 schema）；`api_key_name_snapshot` 写空串；发送预检（stream_route.go:424）改为只校验会话绑定账户存在。

### 3.3 媒体任务归属改造

1. `media_jobs` 加列 `owner_system_account_id TEXT NOT NULL DEFAULT ''`（加法式 ensure + 存量回填：`UPDATE media_jobs mj SET owner_system_account_id = ak.system_account_id FROM api_keys ak WHERE mj.api_key_id = ak.id`）。
2. `jobsrepo.go`：`GetByIDAndAPIKey`/列表/管理面过滤从 `mj.api_key_id (+ join api_keys)` 切换为 `mj.owner_system_account_id`；chat 媒体创建写 owner 列。
3. 管理面 mediajobsadmin 读面同步（B4① vendor hunks 之上小改）。

### 3.4 生产数据清理（实施阶段，停写窗口）

1. 删除生产全部 `purpose='chat'` Key（自愈链删除后不再生成；归一后现存 0+会话重建量）。
2. 既有会话行 `api_key_id` 保留原值（历史记录，不清洗）。

### 3.5 文档同步

- chat 会话设计、媒体设计文档：删除 chat Key 生命周期章节，改为「内部通道（owner+绑定账户）直接调度，不落使用日志」；`docs/architecture/架构总览.md` chat 链描述同步。

## 4. 非目标

- 不动 /v1 外部鉴权链（外部 Key 语义零变化）。
- 不拆 `chat_conversations.api_key_id` 列（历史保留）。
- 不做探针式完全直连（跨协议/工具/压缩仍走网关管道，用户已拍板路线 A）。
- 不清历史 usage/audit（此前归一批已接受的悬空引用不变）。

## 7. 风险与边界

- **preauth 安全面**：内部通道是 /v1 鉴权链的第一个大旁路（此前仅 models preauth 与 deployment-smoke 两个窄旁路）——必须用未导出 context key + 护栏测试钉死「外部不可伪造」。
- **媒体归属迁移**：存量 media_jobs 行的回填在删除任何 Key 之前执行（join 推导需要 Key 行在位），保证零悬空。
- **回滚**：代码回退提交即可；数据面仅 media_jobs 加列（加法式）与 Key 删除（备份先行）。
