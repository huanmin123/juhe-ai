## 需求目标

- 背景：`juhe-ai-public-welfare` 后续需要按 IP 消耗做公益站自己的用户维度快照和排行榜，但 `juhe-ai` 当前缺少稳定的 IP 维度统计事实层。没有 IP 统计事实层，外部接口和公益站业务都不应继续推进。
- 目标：先在 `juhe-ai` 独立完成 IP 注册、IP 预聚合、IP 运维页面和管理员封禁 / 解封能力。
- 交付物：IP 统计设计文档、存储 schema、后台 job、管理 API、系统运维页面、封禁运行态、回归测试和验证记录。外部来源 IP 聚合接口作为后续阶段接入。

## 范围边界

### 本次包含

- [ ] 设计 IP 注册表、IP 聚合表、IP 范围窗口和 IP 策略表。
- [ ] 后台 job 按 usage shard cursor 增量注册 IP 并写入 IP 统计，不在请求路径扫描明细。
- [ ] 系统管理员在“系统运维 / IP管理”查看 IP 请求次数、Token、成本、失败率、活跃天数、速度和最近使用。
- [ ] 支持筛选、排序、分页、封禁、临时封禁和解封；不提供单 IP 详情页。
- [ ] 网关请求入口读取 IP 策略运行态缓存，命中封禁时本地拒绝。
- [ ] 为后续 `juhe-ai-public-welfare` 读取 IP 聚合事实保留接口边界。

### 本次不包含

- 公益站用户和 IP 的关系映射：由 `juhe-ai-public-welfare` 自己维护。
- 公益榜排行榜、贡献榜、消耗榜、公开展示名称和快照：由公益站自己汇总。
- 公益站公网 IP 拦截、频率控制和访问限制：不属于 `juhe-ai` 本期职责。
- 地区、国家、ASN、运营商、IP 段或代理标签自动封禁：不做，避免误伤。
- 基于固定状态码或固定错误码的自动永久封禁：不做，已有 IP 级错误熔断继续保持短 TTL 易失运行态。
- 受保护外部来源 IP 聚合接口：本次只保留边界，等待 `juhe-ai-public-welfare` 对接时单独实现。

## 方案概述

- 方案原则：IP 统计先独立落地，公益站和外部接口只消费 IP 聚合事实；页面和接口不扫 `usage_records`。
- 数据变化：新增 `client_ip_registry`、`client_ip_stats_daily`、`client_ip_usage_range_windows`、`client_ip_policies`、`client_ip_policy_hits`。
- 接口变化：新增管理员 IP 统计列表、封禁和解封接口；后续新增受保护外部来源 IP 聚合接口。
- 前端变化：在管理侧“系统运维”菜单新增“IP管理”，支持列表、筛选、排序和策略操作，不展示累计详情。
- 后端变化：新增 IP 规范化、hash、bucket Set、后台增量统计 job、范围窗口刷新 job、策略缓存刷新和网关封禁判断。
- 数据处理策略：首期不做启动自动全量补历史；需要历史补齐时提供离线重建脚本，按 usage shard 游标分批处理。

## 风险与注意事项

- 风险 1：IP 维度基数高，统计写放大和索引体积可能明显增长。规避方式是首期只写 daily 和 range window，并用批处理和索引约束控制成本。
- 风险 2：启动预热 IP Set 可能拖慢 worker。当前已规避为不启动全量预热，只懒记录本进程见过的 IP，数据库唯一约束兜底。
- 风险 3：非 IPv4 来源暂不参与 IP 管理。规避方式是当前明确只识别 IPv4，后续如需扩展再重新设计统计和封禁口径。
- 风险 4：封禁共享出口 IP 可能误伤正常用户。规避方式是只支持管理员显式操作、支持临时封禁和解封。
- 风险 5：封禁运行态缓存刷新失败会造成策略滞后。规避方式是管理操作后主动刷新，并保留定时刷新兜底。
- 发布异常处理：如果上线后 IP 统计 job 压力过大，可以暂停 IP job 和封禁策略刷新，保留现有网关请求链路；如果封禁误伤，管理员可立即解封或禁用策略。
