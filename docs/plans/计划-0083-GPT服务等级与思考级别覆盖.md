## 需求目标

- 背景：GPT AI 账户目前不能统一覆盖客户端 `service_tier` 和 reasoning effort；模型目录只提供模糊的 `supportsServiceTier`，Codex `/models` 又对全部模型硬编码同一 reasoning 列表，无法正确表达 GPT-5.6 Fast、Max、Codex Ultra 和 Responses Multi-agent Beta 的边界。
- 目标：在 GPT 账户高级配置中增加默认关闭、配置后作为期望上限的服务等级和思考级别；选项按账户所选上游模型能力并集动态显示，运行时按最终上游模型能力降级；同时修正 Codex 模型能力返回，明确 Ultra 和公共 API Multi-agent 都不是 reasoning effort。
- 交付物：模型能力字段、自定义模型能力存储、账户配置与校验、前端动态表单、API Key / OAuth 网关改写、Codex `/models` 修正、审计字段、自动化回归、长期文档同步和验证记录。

## 方案概述

- 账户配置：`service_tier_override` 和 `reasoning_effort_override` 默认省略；配置后作为期望上限，运行时按最终模型能力独立降级。
- 服务等级：持久化 `default|priority|flex`；`default` 在运行时删除客户端 `service_tier`，Priority/Flex 写入对应上游值。
- 思考级别：持久化 OpenAI API wire 值 `none|minimal|low|medium|high|xhigh|max`；不允许 `ultra`。
- 模型能力：供应商模型目录增加 `supportedServiceTiers`、`supportedReasoningEfforts` 和默认 effort；前端只消费后端能力数据。
- 多模型：账户下拉选项取已知 `supportedModels` 的能力并集；未知模型不贡献选项，也不清空已知能力。
- Ultra：模型目录另存 Codex reasoning level 和 `multi_agent_version`；Sol、Terra 可声明 Ultra，Luna 不声明。Codex Ultra 由客户端主动多代理实现，wire effort 仍为 `max`。
- Responses Multi-agent Beta：公共 API 对全部 GPT-5.6 提供 `multi_agent.enabled` 托管多代理；本计划只记录边界，不加入账户 reasoning 覆盖。
- 存储：账户覆盖复用当前 provider 配置 JSON；自定义模型能力直接调整当前 schema，不写历史兼容逻辑。
- 网关：完成模型映射和目标协议确定后改写最终上游 JSON；空覆盖不触发额外 API Key JSON 解析。

## 风险与注意事项

- 模型能力会变化，必须记录来源日期并通过模型目录更新，不允许前端写死。
- Priority 响应可能被上游降级，审计和统计需要区分请求值与实际响应值。
- Priority 价格可能高于标准档，计价数据未同步时会低估成本。
- 多模型交集较严格；需要针对部分模型单独覆盖时，应后续设计按模型配置，不在本计划中做运行时静默跳过。
- Ultra 依赖 Codex 客户端主动多代理。只修正 `/models` 但不验证子代理请求、header、额度和并发链路，会形成“界面可选但行为不完整”的假支持。

- 发布异常时清空账户覆盖字段恢复客户端原始行为；schema 和代码按当前契约修复，不恢复旧字段兼容逻辑。
