### 2.3 因果链（为什么「一直失败也不切号」）

1. 渠道慢失败：每次尝试要 60~120 秒才得到失败结果。
2. 网关同账户重试预算：每次上游失败先在同账户重试（见 §3.2），3 次尝试全部烧在 kid1412-ds 上，合计 4~6 分钟。
3. 客户端耐心约 5 分钟，在第 3 次尝试中途断开（当晚 25 条 `downstream_connection_closed`）——换号永远来不及发生。
4. 账户级状态机只认探针：探针小请求通过 → 账户保持 active/可调度/优先级 0 → 下一个请求又从它开始。循环回到第 1 步。
5. 既有来源避让帮不上忙的关键时机缺口：它只在**整个请求最终失败**时确认记账（`chain_v1_loop.go:2164` `confirmClientIPAccountAvoidanceAfterFinalFailure`）；而补上慢失败直切后，多数请求会是「kid1412 烧 2 分钟 → 换 workbuddy 成功」——**最终成功 → 不记账 → 下个请求又从 kid1412 开始**，每请求重复交 2 分钟税。
6. **墙钟预算判停缺口**：270 秒总预算存在（`DefaultGatewayRequestWallBudgetMs=270_000`，routecoordination.go:16，即用户记忆中的「270 秒」）且配有主动交还客户端（client handoff）机制，但派发循环内唯一检查点（`upstreamdispatch.go:706` `reserveSameAccountRetry`）只保护同账户重试、且只对比 3 秒重试间隔——不评估新尝试自身需要的 120s 首字窗口。今晚 trace 实证：attempt 3 在 t≈228s（剩 42s）照常启动，跑至 ~300s 被客户端掐死（`downstream_connection_closed`），网关未在 270s 主动收尾。**客户端体验为「吊死到超时」，违背「快到时间应主动断开让客户端重试」的调度第一原理。**

## 4. 需求目标与非目标（v3）

### 4.1 目标（三刀，均为既有语义的加法或判停条件加强）

0. **总原则（用户裁定，2026-10-23）**：一切调度必须以「客户端请求超时（~270s 量级）内要么交付结果、要么主动给出确定性终态让客户端重试」为前提——宁可网关主动收尾，不可吊死到客户端超时。
1. **慢失败快速换号**：同账户重试只保留给快速失败（<10s）的尝试；慢失败直接轮换下一候选。把切换动作从 ~5 分钟缩进客户端耐心窗口（~2 分钟）。
2. **避让时机补全**：请求最终成功但途中有过上游归因失败尝试时，同样确认来源避让——让「对这个调用方刚失败过的号」在下个请求里沉底，不再每请求重交学费。阈值/TTL/排序/兜底/容量全部复用既有避让实现，零新增状态机。
3. **预算内启动门槛**：启动任何新上游尝试（同账户重试与跨账户轮换同规）前，剩余墙钟预算须 ≥ 一次有意义尝试的最小窗口；不足则不启动，立即走既有 `gateway_request_wall_budget_exhausted` 终态路径主动收尾；并核实/补齐普通流式路径对进行中尝试的墙钟裁剪。

### 4.2 非目标

- 不自建调用方质量台账、不做硬暂停状态机（v2 裁减，见 §6-1，含重启条件）。
- 不改探针执行链、账户级熔断/冷却语义、媒体/realtime 域、组级会话黏性、路由拓扑。
- 不改候选过滤阶段（避让是排序信号，天然无可用性风险，无需 floor 机器）。
- 不改 `temporaryUnschedulableRetryAttempts` 及探针复测行为。
- 功能不设开关：新行为随发布默认生效。

## 5. 方案设计（v5：三刀为方案本体，改动落在默认调度路径）

> **v5 修订（2026-10-23，用户裁决）**：问题属于**调度核心**，与「速度优先/成本优先」模式选择无关——修复必须落在所有 Key 默认使用的调度路径上，不得以「切到速度优先」替代（那是让乘客改乘车方式迁就车的问题）。v4 的 speed_first 盘点降级为背景知识：它证明首字截止/总时间截止的机制族在本代码库是成熟模式（实现可参照），但**不是**本计划的修复路径。**方案本体 = 三刀**（A 慢失败直切、B 避让时机补全、C 墙钟裁剪查修），时间与协调约束见 §5.4。

> 背景（非修复路径）：现有普通路由另有按 API Key 配置的 speed_first 首字截止/总时间截止机制（`preflighthelpers.go:329-355`、`chain_v1_loop.go:1876-1921`），默认 `cost_first` 不装配。它与本方案无替代关系，仅作实现参照与「不重复造轮子」的证据。

### 5.1 改动 A：慢失败快速换号

- 位置：`attemptoutcomes.go:332`（瞬态 5xx）与 `:571`（传输失败）两个同账户重试预留点。
- 变更：预留前判断该尝试耗时（与审计尝试 `duration_ms` 同源，现场可得）——**耗时 < `sameAccountRetryFastFailMaxMs`（新设置，默认 10000ms）才允许同账户重试**；慢失败直接进入换号。预算上限 `min(2, temporaryUnschedulableRetryAttempts)` 不变（快速瞬态错误立即重试同账户仍是正确行为）。
- 效果（以今晚形态）：attempt 1 慢失败（~115s）后立即切 workbuddy-ds，客户端总等待 ≈ 2 分钟而非 5 分钟。

### 5.2 改动 B：来源避让的确认时机补全

- 现状：请求结算时仅「最终失败」路径调用 `ConfirmAfterFinalFailure`（`chain_v1_loop.go:2164`）；tracker 的 `PendingFailures`（含 accountID、ErrorPhase）在请求过程中已收集，最终成功时被丢弃。
- 变更：**请求最终成功结算点**（chain 层 success settle）增加一次确认调用——tracker 内存在上游归因失败尝试时，按既有阈值（≥2）与 TTL 确认避让。语义：对这个调用方刚连续失败过 ≥2 次的号，下个请求排序沉底 5 分钟。
- 复用不改动：阈值常量、TTL（随 `defaultTemporaryUnschedulableMinutes`，上限 10 分钟）、排序（沉底且保持优先级层）、`BypassedAllAvoided` 全避让旁路（内置兜底：所有号都被避让时保持原序，等效今天的兜底行为，天然无可用性风险）、内存/Redis 双实现、5000 条容量上限、TTL 自然过期自愈（**回滚 = 回退部署，状态 ≤10 分钟自动清空**）。
- 自愈闭环：避让后该号收不到这个调用方的流量（有更优候选时）→ 不再新增失败 → TTL 过期 → 放行一个真实请求即试探（天然半开，无需租约机器）→ 成功则回归原位，失败则再次记账。

### 5.3 改动 C：墙钟预算收尾修复（普通流式路径裁剪缺口 + 启动门槛）

- 现状：270 秒墙钟预算存在（`DefaultGatewayRequestWallBudgetMs=270_000`，routecoordination.go:16）且响应层已接收 precommit 截止（`finalize.go:318`），但今晚实证 attempt 3 于 t≈228s 启动、跑至 ~300s 被客户端掐死、无主动终态——普通流式路径的进行中裁剪未生效。派发侧唯一检查点 `reserveSameAccountRetry`（`upstreamdispatch.go:706`）只对比 3s 重试间隔，不评估新尝试自身需要的时长。
- 变更两件：①**查修裁剪面**——定位普通流式路径进行中尝试未受墙钟裁剪的原因并修复，裁剪后经既有 `gateway_request_wall_budget_exhausted` 终态渲染路径（`chain_v1_loop.go:1906` `neutralRequestWallTermination` 已存在）主动收尾；②**启动门槛**——任何新尝试（同账户重试与跨账户轮换同规）启动前，剩余预算须 ≥ `gatewayAttemptStartMinWindowMs`（新设置，默认 30000ms）+ 2s 渲染保留；不足则不启动、立即终态收尾。
- 效果：任何请求要么在 270s 内交付，要么在预算内拿到确定性终态错误（早于客户端超时），客户端可立刻重试。

### 5.4 时间与协调约束（硬性注意项，实现与测试必须逐条钉住）

**时间账**（默认值下的推演，改动不得破坏）：

| 量 | 值 | 推演 |
| --- | --- | --- |
| 客户端耐心 | ~300s（今晚实证 `downstream_closed` 时刻） | 一切的上限 |
| 墙钟预算 | 270s | 终态收尾必须 ≤270s，留 30s 余量 |
| 单尝试首字超时 | 120s | 预算内最多容纳 **2 次**完整尝试（240s+终态渲染）；改动 A 保证第 1 次失败即换号，恰好用满 2 次 |
| 改动 A 门槛 | 10s | 只拦「慢失败后的同账户重试」；快失败（连接复位类）预算消耗可忽略，不进时间账 |
| 改动 C 门槛 | 30s+2s | 剩余 <32s 不再启动新尝试；与「2×120s=240s」自洽：第 2 次尝试最晚 150s 前启动，若第 1 次失败晚于 ~118s，第 2 次不启动并立即终态 |

**协调顺序**（同一请求内的机制先后，必须钉死并测试）：

1. 尝试失败 → 改动 A 判断（慢失败不预留同账户重试）→ 轮换下一候选（候选循环自身受改动 C 启动门槛约束）；
2. 请求结算（成功或失败）→ 改动 B 确认避让（依据 tracker 内本次请求的上游归因失败尝试；与改动 A 互不重复计数——A 只影响重试决策，B 只消费失败事实）；
3. 墙钟到点/不足 → 改动 C 裁剪或拒绝启动 → 既有 `gateway_request_wall_budget_exhausted` 终态路径**只渲染一次**（裁剪与启动门槛不得产生双重终态）；
4. 避让状态在**下一次请求**的候选排序时读取（`OrderAccountsByClientIPAccountAvoidanceAsync`），不在本请求循环内改排序——避免中途换序的未定义行为。

### 5.5 已知取舍（有意接受）

- **避让粒度粗于故障粒度**：v1 flash 挂了会连带该号其他模型对这个调用方沉底 5 分钟。可接受——组内其他号同样能服务那些模型，代价只是流量分布偏移；模型维度细分留作后续精化（§6-3）。
- **普通兼容客户端按 IP 分桶**：会话/设备级细分依赖统一溯源身份扩展（§6-3/6-4），本期不做。
- **实施时必核一项**：避让经客户端策略开关 `AllowClientSourceAccountAvoidance` 门控——需核实 generic 画像是否放行；若默认关闭，随本批放开（否则改动 B 对今晚这类流量不生效）。

## 10. 风险与待裁决

### 10.1 风险

- **避让误伤（flaky 号被沉底）**：阈值 ≥2 + TTL ≤10 分钟 + 排序保层 + 全避让旁路，最坏效果是「流量偏向健康号几分钟」，自愈且可观测（既有确认日志）。可接受。
- **改动面收敛**：两处加法（重试预留点耗时判断、成功结算点确认调用），不碰候选过滤/熔断/新增状态机；发布面 gateway 单进程、无 schema、无新 Redis 键空间；回滚即回退部署、状态自然过期。
- **策略开关核实**（§5.3）：若 generic 画像默认不放行避让而本批放开，属于既有机制的覆盖面扩大，需在测试项中钉住对正常号零扰动。

### 10.2 待裁决（请用户明确）

3. 改动 C 总原则确认：剩余预算不足一次有意义尝试时不启动、立即主动终态交还客户端（复用既有 `gateway_request_wall_budget_exhausted` 渲染）——是否同意。
