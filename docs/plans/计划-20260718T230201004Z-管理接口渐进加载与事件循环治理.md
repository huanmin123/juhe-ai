# PLAN-20260718T230201004Z 管理接口渐进加载与事件循环治理

> **执行要求：** 实施本计划时使用 `superpowers:subagent-driven-development` 或 `superpowers:executing-plans`，逐任务执行、逐任务验证。所有步骤使用复选框跟踪。

**目标：** 在不删除、关闭、弱化任何现有页面、字段、动态状态、余额、用量和操作入口的前提下，让管理列表先返回可交互主数据，再异步补齐动态快照与选项，并建立能定位事件循环、DB queue 和接口分段耗时的可观测链路。

**架构：** 列表请求只承担列表分页、筛选、排序及页面立即展示和操作判断所需的稳定数据；运行态、并发、今日用量、最近使用时间和余额作为真实动态快照并行加载，成功后合并到当前行，失败时保留最近一次成功值。Provider、Proxy 等 options 与列表并行，不再成为列表首包前置条件；后端以 DTO、`Server-Timing` 和 DB service queue 指标明确每一段耗时。

**技术栈：** Vue 3、TypeScript、Ant Design Vue、Express、Node.js AsyncLocalStorage、PostgreSQL / SQLite、Redis、现有 System API 与 DB service 运行指标。

## 需求目标

- 背景：生产环境已确认网络、Caddy 与 Nginx 不是管理接口主要瓶颈；管理页面首包目前会被 options、账户列表装饰、运行态、余额、用量和后台压力共同拖慢，事件循环延迟可进入秒级。
- 目标：将“页面必须等所有附加信息完成后才出现”改为“主列表先可见、真实动态数据分阶段补齐”，同时保证字段、操作、筛选语义和数据来源不被删减或伪造。
- 交付物：管理列表渐进加载代码、动态快照缓存与轮询治理、后端 DTO 与分段耗时、DB queue 观测、专项回归、压测记录、发布与回退方案。

## 不可突破的功能约束

- 不删除页面、菜单、筛选项、表格列、移动端卡片字段、余额、用量、动态状态、详情入口、编辑入口、测试入口、批量操作或刷新入口。
- 不关闭审计、统计、余额、运行态或使用记录能力来换取页面速度；相关后台写入与存储治理由同批专项计划负责，本计划只改变前台读取阶段和请求调度。
- 不返回 `0`、空字符串、空对象、空数组或“正常”状态冒充尚未取得的动态数据。
- 动态数据首次尚未成功返回时，页面显示中文真实状态，例如“正在获取”“运行态暂不可用”；已有成功值时继续展示最后成功值，并保留其 `generatedAt`。
- 快照请求失败不得清空上一次成功的状态、并发、用量、最近使用时间或余额；用户手动刷新仍可立即重试。
- 动态状态筛选、排序等依赖运行态语义的功能必须保持准确。此类查询可以显式等待所需动态投影，不能为了快而按静态字段返回错误结果。
- 不改变账户创建、编辑、删除、测试、导入、导出、批量编辑、余额刷新和授权调度的业务行为。
- 本计划的“DTO 拆分”是拆请求阶段，不是删字段；页面最终展示能力必须与实施前一致。

## 现场基线与问题链路

### 已确认基线

- 生产内网直连管理接口仍普遍需要约 `0.4s` 至 `1.5s`，账户列表存在 `2s` 至 `6s+` 尖峰，说明公网不是根因。
- `server`、`stats-worker`、`ingest-worker` 和 `db-service` 均出现事件循环延迟，单进程被阻塞时整机仍可能有空闲核心。
- `frontend/src/views/accounts/useAccountListData.ts` 的 `fetchPage` 先等待 `loadAccountOptions`，Provider / Proxy options 任一慢请求都会阻止账户列表发起或完成。
- `backend/src/modules/accounts/account-list.routes.ts` 的列表路由串行等待列表、并发水合、运行态筛选和余额水合；任何阶段抖动都会拖住完整响应。
- `frontend/src/views/accounts/accountStatusSnapshotPolling.ts` 目前成功或失败都按约 10 秒固定继续请求，失败期间没有指数退避。
- `backend/src/modules/accounts/account-status-snapshot.service.ts` 与 `backend/src/storage/account-status-snapshot.repository.ts` 已有动态快照基础，但运行态、并发、用量、授权额度等阶段缺少完整 `Server-Timing`。
- DB service 已有 `queuedRequestCount`、`oldestQueuedMs`、`lastQueueWaitMs`、`maxQueueWaitMs`、`activeConcurrentRequestCount` 等运行指标，但管理请求不能直接关联这些指标与接口耗时。

### 目标请求时序

1. 页面进入后立即发起主列表请求，不等待 Provider、Proxy 或其他 options。
2. 主列表成功后立刻渲染表格、分页、筛选结果和所有基于稳定字段的操作入口。
3. options 在独立请求通道并行加载；筛选器显示独立 loading，不阻塞列表。
4. 当前页账户 ID 确认后，并行请求运行态/用量快照和余额快照。
5. 每个快照独立成功、独立合并；某一快照失败不影响列表和其他快照。
6. 后续轮询只刷新动态快照，不重载列表，不改变分页、排序、勾选、滚动位置或编辑状态。
7. 列表条件、页码或管理范围变化时，取消旧快照并用 revision 防止旧响应覆盖新页面。

## 方案概述

### 数据和 DTO 边界

- 新增 `AccountListBaseItemDto`，承载列表首包立即展示和操作判断所需的稳定字段。它不以删除页面字段为目标，而是明确哪些字段由首包提供。
- 保留并收口 `AccountStatusSnapshotItem`，承载运行状态、可调度性、实时并发、健康状态、今日用量和最近使用时间。
- 新增 `AccountBalanceSnapshotItemDto`，承载余额查询配置状态、下一刷新时间、最后成功余额快照和快照生成时间。
- 前端新增 `AccountListRowViewModel`，由 `AccountListBaseItemDto + 最后成功状态快照 + 最后成功余额快照` 合成；表格和移动端卡片继续获得实施前全部字段。
- DTO 中的动态值必须来自真实查询或最后成功快照；没有成功值时使用显式 `loading/unavailable` 状态，不使用业务数值默认值。
- 动态状态筛选存在时，主列表服务仍调用准确的运行态筛选路径；普通无动态筛选列表走快速路径。

### 前端加载与缓存

- `useAccountListData.fetchPage` 立即发起列表，`loadAccountOptions` 改为独立、不阻塞、可复用的并行任务。
- 新增 `accountDynamicSnapshotCache.ts`，以 `viewScope + systemAccountId + accountId` 为 key 保存最后成功状态和余额快照；作用域变化不得串值。
- 列表返回后先用缓存合并当前页，再启动快照请求；快照成功后更新缓存与可见行。
- 普通刷新、筛选、分页和移动端加载更多不得先清空当前成功快照。
- 账户删除、退出登录或系统账号作用域变化时清理对应 key，避免展示已不属于当前范围的快照。

### 轮询降噪

- 成功后的基础间隔保持 PLAN-0104 的 `10 秒 +/- 1 秒`，不降低动态状态刷新能力。
- 连续失败使用 `20s -> 40s -> 80s -> 120s` 上限退避；任意成功后立即恢复 `10 秒 +/- 1 秒`。
- 浏览器 `focus` 与 `visibilitychange` 在 1 秒窗口内合并为一次刷新；已有请求在途时只记录一次 trailing refresh。
- 页面隐藏、主列表加载、没有账户 ID、组件卸载或作用域切换时停止或取消请求。
- 用户点击手动刷新时跳过失败退避并立即请求，但仍遵守同一时刻最多一个同类快照请求。

### 后端执行阶段

- `GET /accounts` / `GET /my-accounts` 普通路径只执行主列表查询并返回；不再同步等待 `applyServerAccountConcurrencyToAccountList` 和 `hydrateAccountBalances`。
- 只有请求包含依赖动态运行态的筛选或排序时，才调用 `listAccountsPageWithRuntimeStatusFilter`，并在 `Server-Timing` 标记 `account-runtime-filter`。
- `GET /accounts/status-snapshot` 保留当前 100 个 ID 上限，内部明确记录 `projection-db`、`usage-window`、`runtime-redis`、`concurrency-redis` 和 `snapshot-total`。
- 新增 `GET /accounts/balance-snapshot` 与自有账户对应路由，批量读取当前页账户的余额配置和最后成功快照，不触发真实上游余额刷新。
- 用户点击“刷新余额”继续使用现有 `POST /accounts/:id/balance/refresh`，成功后只更新对应缓存和行，不重载全表。

### 可观测性

- 新增共享 `appendServerTiming`，追加而不是覆盖现有 `Server-Timing`，避免中间件和路由互相丢指标。
- 账户列表响应至少包含 `account-list-db`、`account-runtime-filter`、`handler-total`；动态快照包含投影、用量、Redis 运行态、Redis 并发和总耗时；余额快照包含配置、快照和总耗时。
- System API 请求日志增加 `dbQueryCount`、`dbQueryMs`、`dbPoolWaitMs`、`dbQueueDepthStart`、`dbQueueDepthEnd`、`dbQueueOldestMs`、`eventLoopLagMs`。
- 诊断响应头只返回数值指标，不返回 SQL、参数、账号 ID、凭据或内部错误：`X-Juhe-Db-Queue-Depth`、`X-Juhe-Db-Queue-Oldest-Ms`、`X-Juhe-Event-Loop-Lag-Ms`。
- 慢请求阈值为 `500ms`；超过阈值记录一条结构化 `system_api_slow_request`，字段包含 route、statusCode、total、Server-Timing 分段、DB query 数、DB pool wait、queue depth 和 event-loop lag。

## 性能验收阈值

以下阈值使用生产同等 PostgreSQL / Redis 配置、20 行账户列表、已登录用户和至少 100 次只读采样；不能通过删字段、返回空数据或关闭后台功能达成。

| 指标 | 验收阈值 |
| --- | --- |
| 无动态状态筛选的账户主列表 | P50 `< 150ms`，P95 `< 300ms`，P99 `< 800ms` |
| 有动态状态筛选的账户列表 | P95 `< 500ms`，P99 `< 1000ms` |
| 100 个账户状态快照 | P95 `< 300ms`，P99 `< 800ms` |
| 100 个账户余额快照 | P95 `< 250ms`，P99 `< 700ms` |
| Provider / Proxy options | P95 `< 300ms`，且其耗时不计入列表可见时间 |
| 页面进入到主列表可交互 | P95 `< 500ms`，不等待 options 和动态快照 |
| 动态快照成功后完成合并 | 主列表后 P95 `< 500ms` |
| 请求错误率 | `< 0.1%`，不得用空成功响应降低错误率 |
| DB service queue | 管理读采样期间 `oldestQueuedMs` P95 `< 50ms`，持续超过 `200ms` 必须触发慢请求诊断 |
| db-service 事件循环 | 采样 P95 `< 100ms`，单次超过 `500ms` 必须能关联到结构化慢请求或后台任务 |
