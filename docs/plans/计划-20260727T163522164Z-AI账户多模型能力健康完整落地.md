# PLAN-20260727T163522164Z AI 账户多模型能力健康完整落地

## 目标

一次性完成 AI 账户多模型能力健康、精确隔离、恢复、整号仲裁、存储、接口和前端闭环。模型 B 被独立确认不可用时，只排除账户的 B 能力，模型 A 继续调度；单模型失败不再通过单一检查模型错误升级为整号不可用。

权威设计见 [AI 账户多模型能力健康与精确隔离设计](../functions/AI账户多模型能力健康与精确隔离设计.md)。

## 完整交付边界

本计划不按阶段实施，也不接受部分上线。以下工作域共同构成一个交付单元：

- 模型映射后的精确能力作用域与领域状态机。

- 用户失败触发、独立模型探针、5 分钟去重、账户预算和 fenced lease。
- 所有路由模式的模型能力过滤、候选切换和全池有界等待。
- 阻断、half-open、双成功恢复和整号全覆盖仲裁。
- 账户摘要、能力明细、重新检查 API、权限和前端展示。
- AI 健康监控小时聚合、诊断日志、指标和 trace。
- 离线数据切换、schema preflight、standalone / performance 验证和文档同步。

任一工作域缺失时保持“实施中”，不得启用新的生产状态写入。

## 当前问题

- 请求失败确认只携带账户 ID，丢失失败模型、模型映射目标和真实 endpoint mode。
- 请求失败触发的独立检查仍使用账户单一 `healthCheckModel`，结论与原失败能力不一致。
- 单一检查失败可以写整个账户 `temporary_unavailable`，可用模型随之退出调度。
- 单一检查成功也不能证明失败模型恢复，导致失败模型继续被命中。
- 账户标签只能显示全局可调度状态，无法解释“部分模型不可用”。

## 必须保持的边界

- 不按 HTTP 状态码、错误码或正文推断具体账户业务语义。
- 普通业务失败只切号和投递探针，不直接写模型或账户负向状态。
- 独立探针完整失败只阻断精确模型能力；任务、过期和配置故障不阻断。
- `healthCheckModel` 只作为哨兵和激活模型，请求失败确认必须使用失败请求作用域。
- 同一作用域 5 分钟内最多一次业务触发探针；阻断后由恢复调度器负责。
- 部分模型失败时账户保持可调度；只有无任何可路由能力并完成全覆盖仲裁才允许整号升级。
- 人工测试继续保持零生产状态副作用。

## 验收标准

- A、B 同账户场景中，B 被确认失败后不再接收 B 请求，A 请求不受影响。
- 请求失败探针使用 B 的真实上游模型和 endpoint mode，不再使用账户哨兵代替。
- 单账户并发失败不会造成探针风暴；5 分钟冷却、单飞、账户预算和全局容量都有自动化证据。
- 所有完整 HTTP / 协议失败只产生通用模型能力不可用，不产生具体账号错误判断。
- 部分能力失败不会写整号 `temporary_unavailable`；整号升级满足设计中的全部覆盖条件。
- 阻断能力按退避自动 half-open，并在两次独立成功后恢复；重启和多实例竞争不破坏状态。
- 前端完整展示账户持久状态和模型能力状态，且管理端与用户端权限正确。
- standalone 与 performance 测试、schema preflight、离线脚本三种模式和浏览器验收全部通过。
- 旧账户级请求失败确认路径已删除或拒绝启动，不存在双写、双判定和兼容旁路。

## 风险与控制

- 高基数：只稀疏建行、限制合法目录模型、单账户容量治理、批量读取。
- 探针成本：按需触发、5 分钟去重、账户公平预算、恢复退避，不周期扫描全部模型。
- 误杀整号：最小作用域默认、全覆盖仲裁、任一成功立即中止、在途归零。
- 误恢复：generation fencing、两次独立成功、整号恢复不清局部阻断。
- 多实例竞态：Redis fenced lease、数据库 CAS 和唯一约束三重保证。
- 上线数据风险：停服备份、dry-run、来源码精确筛选、verify 和启动 preflight。
