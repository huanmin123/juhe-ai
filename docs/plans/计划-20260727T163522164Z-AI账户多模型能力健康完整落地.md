## 目标

一次性落地 [AI 账户多模型能力健康与精确隔离设计](../functions/AI账户多模型能力健康与精确隔离设计.md)，解决“模型 B 持续失败却仍可调度”以及“B 的故障拖死仍可用模型 A”两个方向的问题。

完整交付必须同时包含最终派发描述、凭据级能力 scope、请求终态收集、独立探针、5 分钟单飞、circuit 状态机、恢复、调度过滤、PostgreSQL / Redis / Asynq 控制面、管理 API、前端、健康监控、迁移和回滚。任何单项都不能独立发布。

## 已确认的架构决策

- 模型能力层永不写入或清理 accounts.status。
- 全部能力阻断只形成 instance_all_capabilities_unavailable 派生门禁，不做全模型仲裁扫描。
- 扩展现有 account circuit scope / ledger / outbox / rebuild，不新增平行 account_capability_health 状态机。
- 长期 owner 固定为 Go + PostgreSQL + redis-state + Asynq，不新增 Node + SQLite 双套长期 adapter。
- 精确 scope 包含最终上游模型、endpoint、lane、转换路径和 credentialScopeKey。
- request_failure 旧账户哨兵路径与新能力 collector 必须互斥。
- protocol_model 子 incident 不得再通过任意 scope 计数打开父 account circuit。
- HTTP 状态码、错误码、正文和错误类型不参与能力结论。
- 同一 scope 的业务失败 admission 间隔固定为 5 分钟；每 credentialSourceAccountId 的自动 physical probe 另有跨节点 5 分钟启动门禁，其他模型只排 logical due。owner 显式重检可受控旁路，但仍受 running=1、命令限频、成本和全局预算。
- pending_test 使用 durable Catalog activation selection 轮转免费 execution Attempt，任一能力成功即可激活；单一 healthCheckModel / opaque 失败满 24 小时不得写整号 error。
- Attempt 调度必须同时满足 evidence ready、capability phase 和 Key owner；scope hold 不提升账户 dataStatus，无法定位账户的 tail 才激活全局 barrier。
- 人工测试保持零副作用；生产“重新检查”是有权限、审计和预算的独立命令。

## 当前问题

- 请求失败健康派发目前只传 accountId，复测固定 healthCheckModel，无法验证失败模型。
- 现有 request-failure health check 会把独立完整失败写到账户 temporary_unavailable。
- transport protocol_model scope 使用客户端 requestModel、缺少 endpoint，且三个不同 scope 可打开父账户电路。
- 模型映射后的最终 upstream model / endpoint / adapter route 没有统一不可变描述。
- 多 API Key 账户的能力结论没有选中 Key 维度。
- active 账户的任意业务成功会刷新账户级健康水位，可能让真正哨兵长期不跑。
- 现有健康监控只有账户哨兵三态，无法表达 unknown、部分能力阻断和全部能力派生阻断。

## 验收标准

- B 的失败探针使用真实失败 Attempt 的模型、endpoint、转换路径和 Key，不使用账户哨兵代替。
- A/B、多 Key 和授权实例测试证明局部故障不扩大。
- 请求大量失败时，5 分钟冷却、scope 单飞、物理预算和可靠任务均有自动化证据。
- control RPC / Redis / PostgreSQL 短时中断时，已经识别的失败仍由 durable handoff 重放；backlog 超标会摘流或将受影响 projection 标为 unconfirmed，不允许静默保持可调度。
- 请求失败后状态能进入 suspect / blocked / recovering，后续请求确实过滤对应 scope。
- 全部能力阻断时前端和 API 显示无可调度能力，但数据库 accounts.status 未变化。
- Redis / worker / projector 故障不会把已阻断能力误判 unknown，也不会产生风暴。
- 旧账户哨兵 request_failure 路径和 transport 子投票父级升级已删除或强制禁用。
- 所有权威文档、代码、schema、API、前端、监控和部署手册使用同一契约。

## 主要风险与控制

- **探针成本**：按 probeStrategy 明确证据强度；默认不执行付费图片 E2E。
- **误杀整号**：能力层零 accounts.status 写入口，transport 子级不投票开父级。
- **Key 误伤**：credentialScopeKey 精确隔离，Route 聚合只要一个 Key 可用就继续调度。
- **状态双写**：复用 circuit ledger / outbox；Redis provisional、PostgreSQL durable 和 readiness 责任固定。
- **请求热写**：成功 observation 节流，失败只在原子 admission winner 写持久事实。
- **旁路丢失**：gateway 先写 release 外 durable handoff，再异步提交控制面；连续 ACK 后清理，积压超标摘流，不能把日志当交付保证。
- **冷启动放行**：Redis miss 不等于 unknown，按账户 lazy-load 和 capacity sentinel 保守门禁。
- **旧数据误清**：无 provenance 一律不自动清理，allowlist 逐 ID CAS。
- **迁移双 owner**：capability_contract_version 拒绝新旧 dispatcher 混跑。
