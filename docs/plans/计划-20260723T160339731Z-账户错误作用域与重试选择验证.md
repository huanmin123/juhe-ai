## 已修复问题

1. 同一坏会话可用首错 confirmation 自证失败并把多个健康账户推进 `OPEN`。
2. 无显式账户错误策略的推理端点完整非 `2xx` 直接返回客户端，未轮换同账户好 Key 或后备账户。
3. 单分组候选为空时被误报为已尝试后备分组，跳过可恢复不可用等待。
4. 客户端中断存在被归入账户 transport failure 的事件时序窗口。
5. 多套 Mock 回归继承外部 Redis/cache 配置或使用过期 Responses 事件字段，造成非产品红灯。
6. 未知完整 HTTP 失败会写跨请求共享 Key 短避让，坏会话可误伤正常 Key。
7. 父账户电路要求全部子 scope 成功证据，但后台恢复不传 evidence，无法关闭。
8. 完整 HTTP 失败被误记为显式策略失败，污染热质量并跳过 framing-complete 收尾。
9. 同层探索 token 集合满 2048 后冻结，热点路由永久停止探索。
10. 未知完整 HTTP 失败仍会提交客户端 IP × API Key ×账户跨请求避让，同 NAT 的健康会话可能被连带重排。
11. 透传完整 HTTP 非 `2xx` 被质量生命周期当作成功；接管路径则把未知响应放入共享可靠性，都会扭曲选路。
12. 父账户恢复后未清升级证据，新的单 scope 故障可能借用旧 scope 证据立即再次升级。
13. 自动后台探针把任意完整 HTTP 业务失败当账户/Key 失败证据，仍可能写入 `temporary_unavailable` 或 `error`。
14. 图片 lane 继承文本 10 秒首字截止，并在请求已发送、完整非 `2xx` 或响应体中断后切号，存在重复生成和重复计费风险。
15. deadline 到期后的异步切换决策没有重新检查首字/读取是否已经完成，可能误杀已恢复的健康 attempt。
16. owner 状态、副作用队列、分布式 precheck 与 API Key 运行态存在迟到失败覆盖较新成功或人工硬状态的竞态。
17. `SUSPECT` 在一次独立 confirmation 失败后即 `OPEN`，两次独立网络抖动仍可误熔断；证据还需要随 control-plane 重建保持一致。
18. 同账户多 Key 固定最多尝试 2 个，第三个及后续健康 Key 可能永远无法接管。
19. 账户循环内部可绕过共享总墙钟，在最终响应保留时间内继续请求尾部账户。
20. `SUSPECT` 无新客户端流量时不进入后台 due 队列，真正死亡账户可长期占据验证中状态。
21. 10k 容量满载后新故障被伪装为 `CLOSED`，重建失败还可能永久全局阻塞。
22. `event: error` 未进入协议失败结构，普通客户端可能先收到原始错误再收到网关错误。
23. 余额 adapter 曾按 `401/403/429/5xx` 和错误文本推断确定性或瞬态语义。
24. HTTP `200` 垃圾体、失败 envelope 或缺少协议结构曾可被当成正向成功，错误清理 Key 状态并抬高热质量。
25. 多实例 Key 探针缺少数据库 claim 租约，旧 fingerprint 可堵塞固定候选窗口，迟到 worker 还可能覆盖新结果。
26. 末级低容量组把前序 binding 误认为后续 fallback，绕过 FIFO 队列并在 64 路风暴中提前返回 503。
27. personal 主组全忙时可能进入 270 秒等待，即使已有真实可承接的健康后备组；队列时限也未统一裁剪到重试预算和文本墙钟。
28. 全量电路重建未就绪时，恢复 sweep 与待投影 control-plane 事件互相等待，已加载 scope 也无法继续恢复。
29. Redis 账户 revision 清理使用无界 `HGETALL`，大账户池会把单次维护放大为全量读取。
30. GLM Mock 只写配置态 `active`、未写独立健康成功证据，并遗漏关闭 SQLite read worker pool，既形成假性 503 又使测试进程拖尾。

## 验证记录（历史基线，最终 SHA 必须重跑）

- 任意状态码与四类完整正文矩阵：12 个状态、48 个完整响应组合、12 个截断传输组合、64 路同坏会话并发，全部保持业务状态中性。
- 低容量 transport 风暴：4 个坏账户、2 个并发上限为 1 的健康账户、64 路同 session / IP 请求全部成功；健康池总并发峰值为 2，无槽泄漏或中间错误泄漏。
- 全池等待风暴：专项 Mock 连续通过，最近一次约 11.9 秒；单 scope 64 请求在 cap 8 下峰值为 8 waiter / 1 timer，多 scope 64 请求在 global cap 12 下峰值为 12 waiter / 4 timer；容量外请求快速拒绝，准入请求在 3 秒共享预算内 handoff，零上游请求且最终 waiter/timer/scope/账户并发槽全部归零。
- 多 Key：3 Key、6 个任意状态、20 路坏会话并发、5 Key 全死、66 Key 池的 64-attempt 安全截断、跨账户物理 Key 去重均通过。
- 电路：首次失败加 2 个独立 confirmation、SUSPECT 后台确认、父子 scope 恢复、同 generation 持久化 CAS、容量 sentinel、渐进重建、15 分钟退避和 10k due 压力均通过 Memory / SQLite / Redis 边界回归。
- 冷重建与父级恢复：父 account incident 与子 `protocol_model` incident 按 generation/revision 恢复；父 incident 的恢复子 scope 集合最多 64 个，超出部分不形成无界 payload；父级在 3 个通用协议成功证据后关闭且未抹掉仍故障子 scope；`SUSPECT` unknown 保持中性并按现有退避与 jitter 延后。
- Key probe：64 个旧 fingerprint、claim 互斥、租约过期接管、旧 failure / 新 success 竞态、SQLite 与隔离 PostgreSQL schema / index smoke 均通过。
- 协议成功来源：HTTP `200` 垃圾体不增加热质量、不清 Key；结构完整的 Chat、Responses、Messages、Gemini、Models、Token counting、Embeddings、Images、Interactions 才可确认成功。

## 完成标准
