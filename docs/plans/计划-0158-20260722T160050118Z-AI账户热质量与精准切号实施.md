## 方案概述

- 路由策略始终是最高业务调度层；账户层只过滤、排序和报告当前路由范围内的候选结果。
- 新增 route coordinator contract，集中消费账户可派发、临时阻断、请求内耗尽、硬耗尽和请求级 handoff。
- `GatewayRequestWallBudget`、`ServerRetryBudget` 与 `routeCoordinationBudget` 独立存在，不互相抵扣或替代。
- 短电路和热质量采用 Store Port；performance 使用 Redis 原子实现，standalone 使用有容量上限的进程内实现。
- 通用自动机制只接受本地可验证的 transport 生命周期事实；完整 HTTP 响应默认透明转发，响应语义动作只来自用户显式策略。
- 恢复使用唯一 writer、generation / dispatchRevision fencing、可重放持久交接和独立 `TransportProbeOutcome`。
- 按定稿设计新增最小持久 control-plane schema：活动 incident ledger、关闭 tombstone、`dispatchRevision` watermark 和 outbox / projector ACK；只保存有界控制事实，不保存响应状态、header、正文或热质量桶。
- schema 只描述当前完整结构；本地旧库按项目规则离线重建或清洗，不在启动和请求路径保留迁移兼容分支。

## 现状代码地图

- 请求总入口是 `backend/src/modules/gateway/routes.ts`，当前主循环同时承担 dispatch、响应处理、账户重试和分组 fallback；阶段 0 要逐步把账户层结果解释权收回 route coordinator。
- 候选准备分散在 `dispatch/candidate-filter.ts`、`dispatch/preparation.ts` 和 `dispatch/upstream-dispatch.ts`；现有普通 / 快速模式共用入口，但快速模式另有首字降级和切换路径。
- `runtime/server-retry-budget.ts` 已正确累计零可派发等待，但现有回归明确禁止整请求墙钟；本计划将保留该预算并新增独立墙钟与短协调预算。
- `runtime/account-runtime-keys.ts` 的授权实例键可以复用；请求级物理凭据、Key 指纹和协议模型尝试集合尚不存在。
- `shared/runtime-probe-state-store.ts` 已有 generation、lease、due 索引和 Redis Lua CAS，可复用原子实现结构，但旧 `recovery_wait / precheck_pending` phase 不能作为新电路语义。
- `response/downstream-commit-state.ts` 已能区分 transport 与 semantic commit；完整响应透明转发应建立在该提交边界上。
- 当前完整非 2xx 和部分 2xx 错误正文会在未获用户显式授权时切号、轮 Key 或写 suppression；这是阶段 0 首个反向回归和移除目标。
- 当前后台探针以 `AccountTestResult.success` 同时驱动持久健康和短运行态恢复，且存在按裸 `accountId` 无条件清运行态的路径；阶段 4 必须拆成业务投影与 `TransportProbeOutcome` 两个消费者并加入 fencing。
- 当前质量排序来自持久聚合 `account_quality_scores`，粒度是物理账户且不是 5/10/30 分钟热运行态；阶段 3 新建 accountRuntimeKey 维度 Store，历史分只保留展示分析用途。

## 风险与注意事项

- 路由协调、流式写出和失败归因处于网关热路径；实现必须先建立反向回归，再逐层替换，禁止一次性大改后补测试。
- Redis 脚本、内存 adapter 和后台 worker 必须保持同一状态机契约，不能让降级路径形成第二套语义。
- 热质量更新不得引入同步数据库或 IPC 等待；容量、TTL、key 基数和日志量必须有界。
- 完整响应与传输失败的边界必须由响应生命周期事实判断，不能用通用状态码 classifier 代替。
- 本计划不自动合并、不部署；完成后先报告验证和剩余风险，由用户决定后续集成与上线。
