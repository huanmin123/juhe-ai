# PLAN-0114 AI 账户临时不可调用有界恢复探活

## 基本信息

- 编号：PLAN-0114
- 状态：草稿，等待用户评审
- 创建时间：2026-07-16
- 更新时间：2026-07-16
- 需求来源：用户对话
- 执行者：AI / 维护者
- 关联模块：AI 账户 / 前端高级配置 / 管理 API / 存储 / ops-worker / 冷却复测 / 授权实例 / 文档 / 验证

## 需求目标

- 背景：部分公益上游不允许客户端在账户不可用后长期、间隔式主动探测。现有 `temporary_unavailable` 与 `rate_limited` 共用冷却复测状态机：短期按退避间隔复测，超过系统观察阈值后进入每小时一次的长期复测，持续 7 天仍失败才转为 `error`。这种长期主动请求可能触发公益上游的封禁策略。
- 目标：在 AI 账户高级配置中增加账户级“持续恢复探活”开关。关闭后，不完全取消恢复能力，而是只允许 `temporary_unavailable` 在固定 10 分钟窗口内进行有界复测；窗口届满后的最后一次复测仍失败时直接转为 `error`，停止后续自动复测。
- 交付物：账户配置字段、前后端契约、账户编辑交互、SQLite / PostgreSQL 状态机、授权实例有效配置、导入导出、操作日志、回归测试、长期文档和验证记录。

## 已确认需求

- 开关只影响持久账户状态 `temporary_unavailable` 的冷却恢复复测。
- 正常账户每 12 小时一次的周期健康检查不受影响。
- 首次激活检查、配置变化触发检查、人工账户测试和手动恢复不受影响。
- `rate_limited` 的冷却恢复与长期复测不受影响，不能因为 10 分钟限流而把账户误判为异常。
- 关闭持续探活后的恢复观察窗口固定为 10 分钟，不增加账户级时长输入框，也不复用系统“长期不可用观察阈值”。
- 开关默认开启，未主动关闭的账户保持现有恢复行为。
- 账户已处于 `temporary_unavailable` 时关闭开关，从本次保存成功时间重新开始一个完整的 10 分钟窗口，避免旧观察时间导致账户立即转为异常。

## 当前实现基线

- `ops-worker` 通过 `cooldown-account-retest` 扫描 `temporary_unavailable` 和 `rate_limited` 到期账户，并使用账户自己的 `healthCheckModel + healthCheckEndpointMode` 发起生产恢复复测。
- 冷却复测调度器默认每 3 秒扫描候选；单账户失败后按指数退避，单次等待由系统 `defaultTemporaryUnschedulableMinutes` 限制，当前默认最大 2 分钟。
- 从 `cooldown_retest_observation_started_at` 起超过 `cooldownAccountRetestMaxBackoffHours` 后进入每小时一次的长期不可用复测，当前默认阈值为 12 小时。
- 从观察开始持续 7 天仍未恢复时，账户才转为 `error`。
- 正常账户周期健康检查由独立的 `account-health-check` 任务承担，当前默认间隔为 12 小时；本计划不得把两个机制合并。

## 方案比较

### 方案 A：账户级正向布尔开关 + 复用现有冷却状态机（推荐）

- 字段使用正向语义 `temporaryUnavailableContinuousProbeEnabled`，默认 `true`。
- `true` 完全保持现有短期、长期和 7 天终态行为。
- `false` 只在 `temporary_unavailable` 下启用固定 10 分钟有界恢复分支。
- 优点：和用户需要的单个开关完全一致；数据、界面和状态流转简单；不会增加新的任务体系。
- 代价：以后如需第三种模式，需要再演进字段契约。

### 方案 B：账户级恢复策略枚举

- 使用 `temporaryUnavailableRecoveryMode = continuous | bounded`，前端仍可渲染成开关。
- 优点：以后增加 `manual_only` 等模式时更容易扩展。
- 代价：当前只有两个固定行为，枚举会增加无实际收益的校验、文档和分支。
- 结论：本轮不采用，遵循轻量和 YAGNI 原则。

### 方案 C：账户级自定义恢复时长

- 增加是否持续探活和观察分钟数两个字段。
- 优点：不同上游可配置不同窗口。
- 代价：增加用户决策成本，容易产生极短窗口或超长窗口，并偏离已确认的固定 10 分钟。
- 结论：本轮不采用。

## 推荐数据契约

### 字段

| 层级 | 字段 | 类型 | 默认值 | 含义 |
| --- | --- | --- | --- | --- |
| 数据库 | `temporary_unavailable_continuous_probe_enabled` | `INTEGER NOT NULL CHECK (... IN (0, 1))` | `1` | 是否允许 `temporary_unavailable` 进入现有长期持续恢复探活 |
| 后端领域 / API | `temporaryUnavailableContinuousProbeEnabled` | `boolean` | `true` | 账户级恢复探活策略；只影响 `temporary_unavailable` |
| 前端表单 | `temporaryUnavailableContinuousProbeEnabled` | `boolean` | `true` | 对应高级配置开关 |

- 字段不敏感，可以进入账户高级详情、导入导出和操作日志。
- 新建账户省略字段时由后端按 `true` 收口；前端默认值只用于交互，不作为业务默认值唯一来源。
- 更新账户时只有显式提交该字段才修改；严格校验必须拒绝字符串、数字和 `null`。
- 账户普通列表和轻量 options 不增加该字段，避免为仅在高级编辑中使用的配置扩大列表契约。
- 自有账户高级详情返回明确布尔值；授权实例高级详情返回来源账户的有效值并保持只读。
- 账户导出始终写出该布尔值；导入省略时使用 `true`，非法类型直接报中文校验错误。
- 外部公开账户创建契约继续不暴露该内部运行策略，使用后端默认值 `true`。

### 存储与授权实例

- 物理来源账户是该配置的所有者。
- 授权实例行按当前账户资源结构保存该字段；创建、恢复授权实例时复制来源账户值。
- 来源账户修改开关时，复用现有来源配置同步写路径更新全部未删除的有效授权实例。实例若正处于 `temporary_unavailable` 且从开启同步为关闭，也分别重置其 10 分钟观察窗口。
- 同步必须使用集合式写入和现有缓存失效机制，不能在 HTTP 路由中逐实例串行查询 / 更新；来源账户与受影响实例的 lookup 缓存及网关运行缓存都要失效。
- 如果来源账户不存在或不可用，继续按现有授权来源硬阻断处理，不用默认值掩盖来源事实。

## 状态机设计

### 持续探活开启

- `temporaryUnavailableContinuousProbeEnabled = true` 时完全保持现有行为：
  - 按现有快速 / 慢速退避复测；
  - 超过系统长期不可用观察阈值后每 1 小时复测；
  - 从观察开始持续 7 天仍失败才转为 `error`。
- 本计划不得顺手调整现有持续模式的间隔、错误码或系统设置。

### 持续探活关闭

设账户进入 `temporary_unavailable` 或在该状态下关闭开关的时间为 `T0`，固定截止时间为 `T0 + 10 分钟`：

1. 写入 `temporary_unavailable` 时原子设置 `cooldown_retest_observation_started_at = T0`，并清零本轮冷却复测失败计数。
2. 10 分钟内继续使用现有健康检查模型、请求形态和短期退避：以当前 3 秒基线起步，失败后翻倍，单次等待仍受当前最大暂停时间限制，默认最多 2 分钟。
3. 下一次计划时间不得晚于固定截止时间；计算方式为 `min(现有短期退避得到的时间, T0 + 10 分钟)`，并且有界模式不进入每小时长期复测阶段。
4. 在默认参数、worker 正常运行且队列不拥堵时，整个窗口通常不超过约 10 次复测；队列拥堵时允许次数更少，禁止为了补足次数集中补发。
5. 任意一次复测成功，继续复用现有恢复逻辑，原子清理冷却、错误和复测观察字段并恢复为可调度状态。
6. 到达截止时间后仍要执行一次最终复测；最终复测失败才转为 `error`。不得只根据墙钟到期、在没有真实探测结果时直接判异常。
7. 转为 `error` 时设置 `schedulable = false`、清空 `cooldown_until`，保留最后一次失败的状态码、trace ID 和中文排障摘要，并使用独立错误码 `cooldown_retest_limited_probe_timeout`。
8. 转为 `error` 后不再进入冷却复测候选；后续由用户修正配置并按现有恢复 / 重新检查入口处理。

### worker 延迟与重启

- 如果截止时间到达时 worker 停止、队列拥堵或没有执行槽位，账户保持 `temporary_unavailable`，不伪造“已确认异常”。
- worker 恢复后只执行一次逾期最终复测：成功则恢复，失败则转为 `error`。
- 不按错过的分钟数补发历史探针，避免服务恢复时形成请求风暴。
- 10 分钟是账户具备现有冷却复测资格时的恢复观察窗口，不是独立定时器 SLA。账户没有有效分组、已过期、授权失效或不满足现有候选条件时，不发探针，也不只因墙钟到期伪造异常；重新具备资格且截止时间已过后再执行一次最终复测。

### 配置切换

- `active / pending_test / disabled / error` 状态修改开关：只保存配置并推进 `configRevision`，不触发主动检查，也不改变当前状态。
- `rate_limited` 状态修改开关：只保存配置，限流恢复时钟和下一次复测不变。
- `temporary_unavailable` 从开启改为关闭：保存事务内将 `cooldown_retest_observation_started_at` 重置为保存时间、失败计数清零、最近复测信息清空，并按当前快速恢复初始等待把下一次复测安排到约 3 秒后，重新获得完整 10 分钟有界窗口。
- 重复保存 `false` 不重置窗口；只有真实的 `true -> false` 变化才开启新一轮 10 分钟观察。
- `temporary_unavailable` 从关闭改为开启：停止应用 10 分钟终态规则，保留当前观察起点和下一次复测时间，后续进入现有持续恢复状态机。
- 已因 10 分钟最终失败进入 `error` 后再开启开关，不自动恢复账户；避免配置保存绕过异常恢复确认。

### 旧任务与并发写保护

- 冷却复测开始时记录当前 `configRevision`、账户状态和观察起点。
- 成功或失败结果写回时必须确认账户仍是原来的冷却状态、配置版本和观察代次；配置保存、手动恢复、停用或新的状态周期已经发生时，丢弃旧结果。
- 不能让关闭开关前启动的旧探针失败结果在保存后立即把账户转为 `error`，也不能让旧成功结果覆盖用户刚执行的停用或新一轮临时不可调用状态。
- SQLite 与 PostgreSQL 使用等价的事务和条件更新语义；状态写入后继续执行账户 lookup、分组统计和网关运行缓存失效。

## 前端设计

### 入口与文案

- 位置：AI 账户新增 / 编辑弹窗 -> 高级配置，放在账户策略相关配置中，不新增页面、标签页或全局设置。
- 控件：Ant Design Vue `a-switch`，正向标签“持续恢复探活”。
- 默认：开启。
- 说明文案：

> 仅影响账户进入“临时不可调用”后的后台恢复探测。关闭后仍会在前 10 分钟按现有退避节奏有限复测，成功即恢复；10 分钟后的最终复测仍失败则标记为异常并停止复测。正常账户周期健康检查、首次激活、人工测试和限流恢复不受影响。

- 高级配置“已配置 N 项”只在该开关偏离默认值，即关闭时计入 1 项。
- 授权实例编辑页展示由来源账户同步的有效值，但控件禁用；说明该策略由来源账户所有者维护。

### 表单与保存

- 新建表单默认 `true`。
- 编辑已有账户必须等待高级详情加载后再显示 / 保存真实值，不能用前端默认值覆盖尚未加载的后端配置。
- 保存失败保留用户当前选择并显示后端中文错误。
- 开关变化不触发账户人工测试，也不改变“测试”按钮使用的模型和请求形态。

## 后端与 API 设计

- 管理侧和用户侧账户新增 / 完整更新 schema 接受布尔字段；授权实例写接口拒绝修改。
- 账户高级详情返回有效字段；普通列表、状态快照和 options 不返回。
- 账户完整更新沿用现有权限、配置版本、操作日志和缓存失效链路。
- 操作日志字段使用 `temporaryUnavailableContinuousProbeEnabled`，中文字段名使用“持续恢复探活”；只记录配置变化，不为每次后台探针额外写操作日志。
- 仅修改本开关时不投递正常账户健康检查；如果账户正在 `temporary_unavailable`，由保存事务直接调整观察时钟和下一次冷却复测。
- 冷却复测任务执行时从 DB service 重新读取账户当前配置，不把该字段缓存成长期队列快照。
- 现有 `trafficSource = cooldown_retest`、使用记录、审计和探针业务统计过滤保持不变。

## 风险与注意事项

- “关闭持续探活”仍会在前 10 分钟产生有限恢复请求，UI 文案必须避免被理解为完全零请求。
- 多个授权实例仍是独立运行个体，可能各自产生有界复测；本轮不引入跨实例探针合并。大量授权同一公益上游时仍需运维侧评估请求总量。
- 队列拥堵会减少实际探测次数并延迟最终判定；不能为了严格凑满次数而补发。
- 只用时间到期直接转异常会伪造健康事实，必须保留最终真实复测门槛。
- 配置保存与在途探针存在竞态，必须通过配置版本和观察代次守卫，不能只依赖进程内队列去重。
- 新字段影响当前 schema；按项目规则直接更新当前结构，不在运行时代码添加旧库兼容。上线前由维护者单独同步数据库结构或重建非业务环境。
- 发布异常处理：若有界模式误判，可先重新开启持续探活并按现有“恢复正常 / 重新检查”入口恢复账户；必要时回退到同一新 schema 下的上一份已验证构建，不恢复旧字段结构。
