## 需求目标

### 背景

当前模型映射唯一允许的跨协议方向是 `responses → chat_completions`（写侧 8 个 family pair、14 个请求形态）。它让 Chat-only 账户承接 Codex/Responses 会话，但 Responses 的会话生命周期无法被 Chat 上游真实承接：

- Codex 的 `/responses/compact` 走 Chat-only bridge 会被明确拒绝（`gatewaycodex/compactpreflight.go` 的 `unsupported_codex_bridge_compact`）。
- 现有 `gateway_summary_compact` 是网关自有的 `juhecmp.v2` 摘要 envelope，不是上游原生 compact，不能跨网关/跨供应商消费。
- `previous_response_id` 状态、托管工具、reasoning、include/truncation 等语义只能由网关模拟，且每个差异都要单独兜底。

2026-11-07 用户裁决：**不支持跨协议模型映射，强制客户端请求协议与实际上游协议一致**；前端两个协议下拉合并为一个；同批删除 Chat bridge / gateway summary compact 全链，不留半开状态。

### 目标

1. 映射协议强制同族：`source_endpoint_family = target_endpoint_family`；唯一例外是 Gemini 同族归一 `stream_generate_content → generate_content`。
2. 前端模型映射只保留一个协议选择；协议自动决定 source/target，两个字段仍按现有 API 契约持久化。
3. 客户端模型可跨供应商选择，但必须支持所选协议；上游模型必须是当前账户 `supportedModels` 内且支持目标协议的模型（现有规则保留并强化）。
4. 同批删除 Chat-only Responses bridge 与 gateway summary compact，以及它们依赖的 schema、env、jobs 清理任务、运行时目录和测试。
5. 存量非合规映射行在升级中删除；升级后不变量可验证。
6. 文档与代码同一次交付，不留“代码已删、文档仍写 bridge”的半成品。

## 方案概述

### 最终契约

允许的 7 个 pair（共 13 个请求形态）：

| # | source endpoint family | target endpoint family | 目标 mode |
| ---: | --- | --- | --- |
| 1 | `chat_completions` | `chat_completions` | `chat_json` / `chat_sse` |
| 2 | `responses` | `responses` | `responses_json` / `responses_sse` |
| 3 | `messages` | `messages` | `messages_json` / `messages_sse` |
| 4 | `generate_content` | `generate_content` | `generate_content_json` |
| 5 | `stream_generate_content` | `generate_content` | `generate_content_sse` |
| 6 | `video_generation` | `video_generation` | `video_create` / `video_get` / `video_content` / `video_cancel` |
| 7 | `tts` | `tts` | `audio_speech` |

不变量：

- 写侧、运行时、前端、导入、克隆、批量、`/v1/models` 并集使用同一判定；矩阵外一律中文 400。
- `sourceModel` 仍是客户端 wire 字符串，可跨供应商；后端不新增 source 目录外键（沿用 §5.1 语义），协议/目录校验落在前端选择器与导入提示；`upstreamModel` 必须是当前账户供应商目录内、账户 `supportedModels` 内且支持目标协议的模型。
- 映射一跳、不可链式；direct 与 mapping 互斥；目标失效跳过账户，不回退同账户其它模型。
- 协议等价映射（同族改名，或 Gemini `stream_generate_content → generate_content` 归一）与直接支持同权 rank 0；跨族 rank 1 机制整体删除。SQL 与 Go 的同族臂必须同时扩为 `(target = source) OR (source='stream_generate_content' AND target='generate_content')`，否则保留的 pair 5 会落 rank 2 被剔除。
- 退役后 Responses 客户端只能落到原生 Responses 账户（gpt、xai、deepseek；DeepSeek 的真实可用性需上游验证）；GLM、Gemini OpenAI Chat、火山、通义等 Chat-only 账户不再承接 Codex。

### 数据变化

- 不修改 `account_entry_mappings` 列结构；`source_endpoint_family` 与 `target_endpoint_family` 继续持久化，前端单下拉只是 UI 投影。
- schema revision 19 → 20。revision 19 已由并行的 API Key 安全策略批占用（纯 DDL 空号），本批不重排、不复用；生产当前可能仍停在 17，`maintenance upgrade` 会顺序经过 18（代理池）、19（安全策略 DDL）与 20（本批）；dry-run 必须核对三步都在计划内。
- revision 20 单一步骤（三阶段）`Destructive: true`，只在 `contract`/`all` 相执行：expand 相只推进 `schema_revision=20`、保持 `min_readable_binary_revision=19`；新二进制（`MinRequiredRevision=20`）可启动，旧二进制仍可读；contract 相执行归一/删除/删 schema 后把 min_readable 推到 20。单机发布继续使用默认 `upgrade`（all），多节点按 expand → 新二进制 → contract。
  > 实现修正（2026-11-07）：`schema_migrations.revision` 是主键且引擎按 revision 校验唯一，revision 20 只能注册 **一个 Step**，三个动作作为该 Step 内部的三个阶段（阶段 ID 写入 detail/dry-run 输出），不能注册三个同 revision 条目。以代码实现为准。
- 升级步骤 0（数据规范化，先于删除）：按 runtime 词表的反向别名表归一历史 token：`anthropic_messages`→`messages`、`gemini_generate_content`→`generate_content`、`gemini_stream_generate`→`stream_generate_content`；两侧所有已知 legacy token 都归一为现行 token（不限于 source/target 相等），避免语义同族的存量行被误删。归一前先检测唯一键 `(account_id, source_model, source_endpoint_family)` 冲突：同账户同 source_model 已存在 canonical 行时保留 canonical、删除 legacy 重复行并计入报告，禁止让 UPDATE 因唯一键失败。归一后已知 legacy token 全部落现行词表，再进入删除步骤；未知 token 计入 dry-run 报告，不静默改写。
- 升级步骤 1（Destructive）：删除规范化后仍非合规的映射行。
  ```sql
  DELETE FROM account_entry_mappings
   WHERE normalized(source_endpoint_family) <> normalized(target_endpoint_family)
     AND NOT (normalized(source_endpoint_family) = 'stream_generate_content'
              AND normalized(target_endpoint_family) = 'generate_content');
  ```
  实现时用显式 `CASE` 或临时映射表表达 `normalized()`，不得依赖运行时词表做隐式转换；dry-run 分别输出各历史别名归一数、删除数与保留数。
- 升级步骤 2（Destructive）：删除 `juhe_codex_context` schema（4 表：`codex_context_sessions`、`codex_context_responses`、`codex_context_compacts`、`codex_context_storage_cleanup_queue`；9 索引）。cleanup queue 是该 schema 的第 4 张表，不是 schema 外的独立对象。
- 删除 `JUHE_AI_CODEX_CONTEXT_ROOT` 配置注册、`datadir.CodexContextRoot`、jobs 清理任务与 mockdata 相关域。

### 接口变化

### 前端变化

- 模型映射每行只保留一个协议选择（7 个选项）：Chat Completions、Responses、Messages、Gemini GenerateContent、Gemini StreamGenerateContent、视频生成、语音合成。
- 协议选项按账户协议档案与账户实际 endpoint modes 过滤；默认协议按账户支持模式选择，不再默认 `responses → chat_completions`。
- 客户端模型候选改为跨供应商、按所选协议过滤；媒体族同样走跨供应商池（catalog 的 `supportedApiProtocols` 已含 `video` / `audio_speech` token，实施时以 `providers/endpoint_modes.go` 投影为准）。
- 上游模型候选仍来自 `form.supportedModels`，按目标协议过滤。
- source 候选池在打开弹窗/装载编辑详情时主动加载；保存前若池未就绪或加载失败，阻止保存并给出“模型目录加载失败/未就绪”的中文提示，不得沿用空池放行。
- 批量编辑同步单下拉与跨供应商 source 选择；批量当前没有协议 watcher，只需删除 disabled 协议选项写法（重置 watcher 只在单账户 `AccountStrategySection.vue`）。
- 只读展示改为单协议；历史行仍可显示两族。
