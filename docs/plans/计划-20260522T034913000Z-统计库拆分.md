## 需求目标

- 背景：早期记录域同时承载高频事实数据和统计结果。使用记录、审计、日志和采样持续写入时，可能影响统计结果查询、额度判断和统计页面响应。
- 目标：将记录域拆为统计数据集库和统计结果库，让高频写入与稳定查询隔离。
- 交付物：方案设计、方案复查评审、三库配置和 schema 拆分、repository 迁移、worker 改造、迁移 / 重建脚本、表监控适配、文档和验证记录。

## 方案概述

- 方案原则：业务库不变，记录域拆为统计数据集库和统计结果库；请求路径不跨库 join，不临时聚合明细。
- 数据变化：新增两个 SQLite 路径配置；新增 `dataset-schema.ts` 和 `stats-schema.ts`；统计结果库保存 `stats_job_state`。
- 接口变化：对外 HTTP 接口不改路径和响应结构；内部 repository 按库边界拆分。
- 前端变化：统计页面、使用记录页、日志页和表监控页面交互不变；表监控需要展示三类库。
- 后端变化：DB service 和 worker 打开三类数据库；统计 worker 跨库读写但不使用跨库事务。
- 数据处理策略：业务库必须保留；数据集库和统计结果库默认可丢弃。统计结果能从保留的 `usage_records` 重建就重建，无法重建的历史区间明确放弃并从新请求重新累计。

## 风险与注意事项

- 风险 1：跨库拆分后容易误用记录域短名入口。规避方式是删除短名入口，源码只保留 `getDatasetDatabase()` 和 `getStatsDatabase()`。
- 风险 2：统计结果写入成功但游标未推进会导致重复累加。规避方式是统计结果写入和 `stats_job_state` 推进必须在统计结果库同一事务内完成。
- 风险 3：数据集库清理早于统计处理会导致历史统计无法重建。当前口径接受统计相关历史丢弃；运行期仍通过统计结果库安全水位和最近 1 天保护窗口，避免后台清理破坏正在处理的统计批次。
- 风险 4：表监控和部署文档仍按两库描述会误导运维。规避方式是实现完成后同步运行、部署、测试和表监控文档。
- 发布异常处理：上线前必须保留业务库和 `backend/.env` 备份；历史排障明细只在离线取证时额外保留。如果三库启动或统计聚合异常，停服务后恢复业务库备份，并使用同一数据契约下的已验证构建和配置；统计数据集库 / 统计结果库可清空重建。
