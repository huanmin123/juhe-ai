## 方案概述

- 自动探测服务必须把查询结果作为显式判别联合处理：仅 `fresh`、`unlimited` 形成命中，其余状态均保持关闭。
- 余额自动刷新只处理 `active && schedulable` 的物理单 Key 账户；人工刷新保留自有账户的跨状态诊断能力。停用或不可调度账户保留用户的到期时间，恢复可调度后由 worker 补查。
- 首次激活成功把关闭且从未配置的单 Key 账户标记为“待自动探测”；内存队列只作为低延迟路径，分钟 worker 以该持久标记补偿进程重启和任务异常，确定不支持才条件清除标记，临时失败延后重试。
- 自动探测与普通余额刷新共用 `account-balance:<accountId>` 租约；租约占用只保留探测意图，不发起第二个上游请求或改写到期时间。
- 所有异步写回均以账户 ID、配置版本、当前余额配置、开关、活动/可调度候选资格和预期探测/刷新时间为条件，防止用户编辑、关闭、多 Key 收敛和时间计划变化被旧结果覆盖。
- 手动开启保存后继续清理旧快照并立即到期；页面无快照时显示待查询，周期 worker 负责生成首个正式快照，并在账户尚不可自动查询时提供准确提示。
- 测试必须直接返回 `unsupported`、`failed` 和 `pending` 快照，不再用抛异常代替所有未命中形态。

## 独立架构审查结论

本计划按 `orchestrate-model-workflow` 使用 Sol/high 只读审查（2026-07-29）。结论以当前代码、回归与长期设计为准：

- 自动刷新候选目前缺少 `active && schedulable` 门禁，导致停用/错误/待检查账户也会被周期 worker 请求上游；这与人工刷新跨状态、自动刷新受状态约束的边界冲突。
- 首次探测只使用零重试内存队列。健康检查写入成功后进程重启或队列执行异常会永久失去唯一探测机会，不能满足“首次激活后自动识别”的业务承诺。
- 复用账户表的 `balance_query_next_refresh_at` 持久化待探测事实，不新增 outbox；关闭且配置为 `{}` 的待探测记录与已开启余额刷新记录由开关和配置共同区分。内存队列继续降低首次延迟，后台小容量补偿负责可重启恢复。
- 审查中曾建议把完整 HTTP 失败排除出账户可用性阈值；该建议与 `AI账户健康状态收敛设计.md`、`AI账户检查模型与人工测试设计.md` 和已有回归冲突，已拒绝。余额的 `unsupported` 与账户健康状态机保持独立，不修改健康检查既有语义。

风险与回滚：本次新增 PostgreSQL Goose `000093` 的账户余额自动探测到期 partial index，不迁移或改写历史业务数据。旧构建可以忽略关闭状态下的探测到期时间；回滚时保留该前向兼容索引，不删除账户配置、调度时间或快照。
