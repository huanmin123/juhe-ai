## 需求目标

- 背景：网关转发本身是异步 I/O，但当前主 Web 进程仍有部分 SQLite 同步读写和流式响应全量 Buffer 累积，随着并发、长流式输出或后台写入增长，可能出现事件循环短暂被占用。
- 目标：保留 SQLite 和本地轻量部署，不引入 PostgreSQL 等第三方数据库；通过独立数据库服务进程减少 Web/API/网关主进程被同步 SQL 阻塞的概率，并把流式响应处理改为增量解析、尊重 backpressure。
- 复查目标：DB service 作为网关高频数据库访问边界，后续不再保留主 Web 进程本地降级路径；DB service 异常时由 supervisor 看护重启，请求链路返回可读错误并短暂快速失败，继续收敛流式首包预读、授权配额 IPC 和账号副作用写库的阻塞风险。
- 交付物：长期架构文档、第一阶段计划、SQLite 存储说明、本计划、后端数据库服务能力、流式转发优化和验证记录。

- [x] 新增本地数据库服务进程或等价 DB service，主 Web 进程通过异步 IPC 使用高频网关读写能力。

- [x] 保留后台 worker 执行统计、审计、运行日志索引、清理和上游探测；后台任务不回到主进程执行。
- [x] 流式响应改为增量解析 SSE 状态和 usage，避免成功流全量 `Buffer.concat`。
- [x] 处理 `res.write()` backpressure，客户端慢读时等待 `drain`。
- [x] 客户端断开时尽量关闭上游异步迭代器，释放连接和并发槽。
- [x] 复查优化一：取消 server 角色下的 DB service 本地降级；DB service 抖动时请求快速失败，避免大量同步 SQLite 压回 Web 主进程。
- [x] 复查优化二：流式首包预读改成增量解析和有限预读，避免首个输出前持续 `Buffer.concat` 与无界累积。
- [x] 复查优化三：候选账号授权配额检查从逐账号 IPC 改为批量 IPC，降低账号数较多时的线性延迟。
- [x] 复查优化四：OAuth / Codex / 账号错误状态等客户热路径副作用写库优先异步交给 DB service，当前客户请求不因这类写入失败而失败。
- [x] 复查补救：账号失败状态副作用写库失败时进入有界内存重试队列，并在 Web 主进程增加短期本地账号屏蔽，避免 DB service 抖动期间重复命中故障账号。
- [x] 复查补救：SSE 增量解析器增加单行和单事件缓冲上限，超过后仅停止网关解析，不中断客户流式响应，避免把正常长输出误判为失败。
- [x] 彻底收口系统管理 API：DB service 内部承载 `/__aisys__/api/*` 路由、登录态校验和管理面 CRUD，主 Web 进程只做流式 HTTP 代理，不再挂载管理路由或解析管理 API JSON body。

### 本次不包含

- 请求体上限调整：保持 `/v1` 网关 raw body 上限 `64mb` 不变，后续如需配置化再单独处理。
- 更换数据库：不引入 PostgreSQL、Redis、Kafka、BullMQ 等第三方存储或队列。
- 多实例全局一致性：第一阶段仍默认单实例；多实例部署需要后续设计共享锁、全局并发和队列归属。
- 多实例全局 HTTP 控制面：DB service 内部系统 API 只绑定本机，由主进程代理，不作为独立公网管理服务暴露。

## 方案概述

- 方案原则：SQLite 继续作为单文件事实存储；DB service 只隔离主 Web 事件循环，不把 SQLite 变成多写者数据库；server 角色下 DB service 异常时不再本地降级，依赖 supervisor 重启和可读错误保护主进程。
- 数据变化：不新增业务表，不修改已有字段；可能新增进程运行态和 IPC 消息类型。
- 接口变化：对外 HTTP API 和 `/v1` 协议不变。
- 后端变化：新增数据库服务进程 / IPC 客户端和 DB service 内部系统 API；主 Web 进程把 `/__aisys__/api/*` 流式代理到 DB service，网关高频读写改为异步调用；流式转发维护小窗口状态和有限诊断片段；复查阶段移除 DB service 本地降级，保留不可用快速失败窗口、配额批量检查、副作用写库异步化、有界重试、本地短期账号屏蔽和 SSE 解析器自我熔断。
- 数据处理策略：预上线阶段不做版本化迁移；如本地运行进程异常，请求链路返回可读错误并等待 supervisor 重启 DB service，通过运行态指标定位 DB service 抖动。

| 2026-05-17 | 系统管理 API 统一由 DB service 承载 | 继续让主 Web 进程挂载低频管理 CRUD 会保留同步 SQLite 路径和大量 storage 导入，边界不干净 | 主进程只保留系统 API 代理；DB service 内部监听本机随机端口并上报 ready；管理路由、登录态校验、公开设置和 CRUD 在 DB service 进程内执行 |

## 风险与注意事项

- SQLite 仍是单写者数据库；DB service 只能避免主 Web 事件循环被同步 SQL 占用，不能消除所有写锁等待。
- 如果后台 worker 与 DB service 仍各自持有 SQLite 连接，必须保持 WAL、短事务、批量上限和 busy timeout。
- 将账号错误状态写入改为异步后，需要保证网关运行态缓存及时失效或本地短期标记生效，避免短窗口内重复命中故障账号。
- 账号失败状态副作用写库需要有界重试；若 DB service 长时间不可用，内存队列无法跨进程重启保留，因此本地短期屏蔽只作为调度护栏，不替代数据库最终状态。
- SSE 解析器超限后会停止解析 usage、首 token 和终止事件；这是保护主进程内存的降级，不影响原始上游流继续转发给客户。
- 流式响应如果不保存完整成功体，审计日志的成功流完整原文捕获需要另行受采样和活跃捕获上限约束，不能无限累积。
- 回滚建议：如 DB service 引发运行问题，应优先修复 supervisor、内部 HTTP 监听、启动环境或 IPC 边界；不要把主 Web 进程本地同步 fallback 或管理 CRUD 长期带回运行路径。流式优化可退回旧 `pipeUpstreamStream` 实现。
