## 需求目标

- 背景：`PLAN-0066` 已落地 PostgreSQL + Redis 高性能模式，但代码中仍存在大量 repository 内部的 `if postgres` 分支和底层数据库句柄调用。继续按函数级分支推进会让业务层和 DB service handler 越来越难维护。
- 目标：建立业务语义级 Store Port / Adapter 方案，让业务 service、routes、DB service operation 不直接依赖 SQLite、PostgreSQL、Redis 或 SQL 方言。
- 交付物：长期设计文档、执行计划、架构入口引用、后续重构阶段和验证矩阵。

## 方案概述

- 方案原则：业务层只依赖业务语义 Port；底层由 standalone adapter 或 performance adapter 实现。
- 数据变化：本计划第一阶段不改表结构；后续如新增索引或表，只按当前 schema 直接调整，不做运行时迁移。
- 接口变化：HTTP API 不变化；后端内部从 repository 函数级分支迁移到 Store Port。
- 前端变化：无直接变化。
- 后端变化：新增 `StorageRuntime` 装配层、Port 类型、SQLite + memory adapter、PostgreSQL + Redis adapter 和静态守卫。
- 数据处理策略：不处理旧结构；需要重建或清理时写入部署 / 运维步骤，不进入运行时代码。

## 设计原则

1. **Port 表达业务语义**：接口命名使用 `findAccountForGateway()`、`listApiKeysPage()`、`enqueueUsageRecord()` 这类业务动作，不暴露 SQL、表名或 Redis key。
2. **Adapter 使用最优实现**：SQLite adapter 可以继续使用 usage shard 和单写者；PostgreSQL adapter 可以使用 schema、分区、CTE、`RETURNING` 和批量写；Redis adapter 可以使用 Lua 和 Stream consumer group。
3. **分支只在装配层**：`runtimeConfig.databaseDriver`、`cacheDriver`、`queueDriver` 只允许在 runtime composition、基础设施初始化和静态守卫中出现。
4. **无历史兼容分支**：不为旧字段、旧表、旧 API、旧路径保留运行时代码。
5. **先验证再收敛**：每迁移一个 Port，必须有 standalone 与 performance 双模式验证；高频路径必须补 smoke 或压测。

## 风险与注意事项

- 一次性改太多 repository 会带来高回归风险；必须按业务域拆小步迁移。
- Port 设计过粗会形成巨型接口；过细会导致 service 需要编排太多存储细节。每个 Port 应按业务事务和读取场景划分。
- PostgreSQL adapter 不能照搬 SQLite 查询；需要按真实 explain、索引和压测结果调整。
- Redis key、TTL 和 Stream 名称不能泄漏到业务 service；否则后续替换 Redis 或拆分实例会再次困难。
- 静态守卫开始阶段允许临时白名单，但必须随阶段推进减少，不能成为永久逃生口。
