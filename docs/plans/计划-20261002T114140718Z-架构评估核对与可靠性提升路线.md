### B. 需要修正的判断

1. **“调度解释已有基础，验证能否串起全链”**——核对结论：**当前结构上串不起来**。`DispatchDecisionSummary` 只覆盖候选准备窗口（W1b 自述 candidate-window explainability）；熔断拦截、同账户 Key 轮换、同账户重试、容量等待、热质量重排、会话 claim 均不在摘要内；同组内重派复用同一 DispatchContext 不产生新摘要；准备期终态（全抑制、配额 429、无候选 503）零摘要；审计面受审计开关门控，日志面无管理面查询。因此该项是**补建工作而非验证工作**。详见缺口清单（P3 依据）。
2. **“错误作用域与流式重试边界需要守住”**——现状好于评估估计：模型不支持（候选过滤）、单 Key 失效（Key 轮换 + `KeyScoped` 只记 Key 级）、账户异常（error policy 动作 + 熔断）、客户端错误（rethrow 不换号）在代码中确有各自作用域；流式交付后重试边界由 `DownstreamCommitState.SemanticCommitted` 双层把守（`internal/gatewayresponse/commitstate.go:9-35`、`retrydecision.go:127-142`、`chain_v1_loop.go:309-314`）。真实缺口是**可解释性**（failclass 观测分类与 error policy 动作分类两套体系无交叉引用、标签散落无统一轮次键），不是语义本身。
3. **“把部署知识转成可重复验证的结果”**——起点高于评估认知：仓库已有 `acceptance/fullchain_e2e_test.go`（真实 gateway+jobs 二进制 + mock 上游，覆盖 gateway spool → jobs drain → usage shard → catalog 注册 + 审计断言）与 `docker/single-server/deploy.sh`（md5 三点闭环 + 容器 healthy + 公网 200）。缺的是**接线**：fullchain 默认 `t.Skip`（需 `JUHE_AI_E2E_FULLCHAIN=1`）、夹具为 SQLite 六库而生产是 PG 8 schema、发布后业务闭环（一条 `/v1` 请求 → 审计 + 用量落库）仍是 runbook 人工步骤、spool 同源只靠双侧各自打印路径无自动比对。
4. **“分布式草案”**——定性不准：该文档是“后续实现和评审依据”（`:14`），被 `docs/functions/README.md:75/:191` 与 `架构总览.md:21/:37` 当作正式设计边界引用；仅“存储”“内部接口”两节自述草案粒度；plans 索引中对应计划为“待开始”。评估“暂不作下一阶段主线”的结论与项目既有立场（显式开启分布式配置后才进入）一致，予以采纳。
5. **“维护成本与轻量定义”**——项目自身已有 `PLAN-20260930T120000000Z`（全面审查清理批次，10 项过度设计与死代码，已立案待授权），本路线不重复立项，只做衔接。
