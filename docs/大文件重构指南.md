# 大文件重构指南

> 面向 AI 与维护者。
> 适用于 `juhe-ai` 中职责膨胀、难以维护或频繁改动的前端、后端、存储和脚本文件。
> 本文件只写通用拆分原则，不指定某个业务页面或某个具体模块的专属拆法。

## 1. 文件定位

- 本文件回答这些问题：
  - 什么时候应该拆大文件
  - 拆分前要先确认哪些职责
  - 前端、后端、存储、脚本分别如何保持边界
  - 哪些拆分会增加复杂度
  - 重构后如何验证行为没有变

## 2. 触发条件

- 出现以下任一情况，可以考虑重构：
  - 单文件行数明显偏大，并且包含多个职责
  - 一个页面同时承担布局、请求、表单、弹窗、格式化、批量操作
  - 一个路由文件同时承担校验、业务规则、外部请求、数据转换
  - 一个存储文件同时包含太多领域查询、转换和写入逻辑
  - 修改小需求时需要理解大量无关代码
  - 同类逻辑在多个文件中复制
  - 测试或验证只能覆盖终态，无法隔离内部规则
- 行数只是信号，不是唯一标准；职责混乱比行数更重要。

## 3. 核心原则

- 先保行为，再拆结构。
- 一次只拆一个清晰边界，不混入新功能。
- 优先拆纯函数、类型、常量、格式化、映射逻辑，再拆副作用。
- 不因为拆文件就引入复杂框架、全局状态或过度抽象。
- 对外 API、路由、字段、页面流程默认保持兼容。
- 具体业务细节的拆分计划应写在任务说明或设计文档，不写进本通用指南。

## 4. 标准流程

### 4.1 识别职责

- 拆分前先列出当前文件职责，例如：
  - 页面布局
  - 交互状态
  - 表单默认值
  - 表格列定义
  - 请求封装
  - 参数校验
  - 业务规则
  - 数据库访问
  - 对象映射
  - 外部请求
  - 错误处理
  - 日志或记录
- 标记每个职责的输入、输出和副作用。

### 4.2 决定顺序

- 低风险优先：
  - 类型
  - 常量
  - formatter
  - validator
  - mapper
  - 默认值构造
  - 表格列配置
  - API payload 构造
- 高风险后拆：
  - 数据写入
  - 外部请求
  - 凭据处理
  - 异步流程
  - 长连接或流式处理
  - 批量更新
  - 迁移或导入导出

### 4.3 落地拆分

- 先移动代码，再做行为调整。
- 拆分后立即运行最小验证。
- 如果必须改行为，要和纯重构分开说明。
- 新文件命名要表达职责，避免 `utils2`、`helperNew`、`misc`。
- 拆分过程中不要顺手重排无关代码。

## 5. 前端拆分建议

- 页面过大时优先拆：
  - 页面容器
  - 表格组件
  - 表单弹窗
  - 筛选工具栏
  - formatter
  - composable
  - 类型和常量
- 页面容器负责组合，不继续承载全部细节。
- 可复用逻辑先放在当前页面附近；跨页面稳定复用后，再上移到通用目录。
- 不要为了拆分把所有状态提前抽到全局。

## 6. 后端拆分建议

- routes 文件只负责 HTTP 边界：参数校验、调用服务、返回响应。
- service 文件负责业务流程、副作用和外部交互。
- repository 文件负责数据访问和对象转换。
- schema 文件负责表结构和兼容初始化。
- scripts 文件负责独立运行流程，不应被正常请求路径强依赖。
- 如果某一层开始承担其他层职责，优先按层拆回去。

## 7. 存储拆分建议

- 存储代码膨胀时，可以按领域或职责拆分。
- 公共能力应抽到明确命名的工具文件，例如连接、加解密、布尔转换、JSON 解析、row mapper。
- 不要把业务策略下沉到 repository。
- 新增字段时要保证旧数据兼容，不用删库作为“迁移”。

## 8. 无效拆分信号

- 文件变多了，但职责边界更难懂。
- 为单实现新增大量接口或抽象类。
- 把一个大文件拆成多个含义模糊的工具文件。
- 拆分后调用链更长，定位问题更慢。
- 重构后无法说明外部行为是否保持不变。
- 重构混入了不相关功能或样式调整。

## 9. 完成标准

- 能说明每个新文件负责什么、不负责什么。
- 对外路由、字段、页面流程保持兼容，或已明确说明行为变化。
- `pnpm typecheck` 通过，必要时 `pnpm build` 通过。
- 涉及运行行为时，按 [dev-runbook.md](dev-runbook.md) 完成对应验证。
- 如仍有大文件未拆完，说明剩余职责和下一步建议。

## 10. AI 输出要求

重构完成后建议输出：

```text
【重构目标】
- <为什么拆，拆什么边界>

【拆分结果】
- <新文件/旧文件职责变化>

【行为兼容】
- <哪些路由、字段、流程保持不变>

【验证情况】
- <typecheck/build/手动验证/未验证项>

【剩余风险】
- <仍然偏大的文件、下一步建议>
```

禁止只说：

- “已拆分”
- “结构更清晰了”
- “没有改业务逻辑”但不给验证依据
