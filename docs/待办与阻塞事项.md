## 使用规则

1. 本文只记录未完成事项。事项完成后立即删除对应条目，不保留“已完成”段落或历史记录；需要保留过程时，写入对应计划、问题或复盘文档。
2. 新增事项必须放入正确的状态分区，并至少包含：现象或目标、证据、归属、下一步、完成判定和关联文档。没有可核对证据的事项不进入本清单。
3. 事项使用稳定编号（`B`=阻塞、`C`=待确认、`T`=待办、`W`=观察、`P`=指针），跨条目引用使用编号锚点，例如 `#B1`。引用外部计划、设计或提交时提供仓库相对链接或提交哈希。
4. “完成判定”必须是可观察、可验证的结果。证据变化时更新条目；状态变化时移动到对应分区并保留原编号，避免引用失效。`W` 观察项升级为缺陷后删除本条并给档案链接；`P` 指针在对应载体了结后删除。
5. 每次修改后更新“最后核验”日期；核验只说明本清单所依据的代码、文档或提交，不代表条目已经完成。

### W11 napi.kid1412.qzz.io 渠道 `deepseek-v4.1-flash` 非流式恒回空 choices（外部上游缺陷）

- 现象 / 目标：用户账户 `kid1412-ds`（`deepseek` / `profile_deepseek_openai_v1` / `chat_json`）手动测试报 `invalid_protocol_success_response`「上游返回 HTTP 2xx，但响应中缺少所选检查协议的完成证据」。目标是确认该失败归属软件判定还是上游渠道。
- 证据（2026-10-19 实测，`curl` 直打上游 + 生产 `classifyResponse` 复算）：
  1. 探针构造形态经生产 `buildTestRequest` 核对为 `POST /v1/chat/completions`、`Accept: application/json`、body `{"model","messages","stream":false,"max_tokens":1024}`——请求无缺陷。
  2. 上游对该 `stream:false` 请求返回 **`Content-Type: text/event-stream`**，正文仅有一条 `choices: []`、`completion_tokens: 0` 的 `chat.completion.chunk` 加 `data: [DONE]`，无任何内容或 `finish_reason`。改用干净 UTF-8 body（`--data-binary` 文件）与 `hello` 极简 prompt、去掉 `stream` 字段，结果完全一致，与提示词、`max_tokens`、`max_tokens` 编码无关。
  3. 同渠道同 key 对照：`deepseek-v4-pro` / `deepseek-v4-pro-0813` / `glm-5.3-flash` / `hy3` / `mimo-v2.6-flash` 非流式均返回正常 `chat.completion` JSON 且含 `finish_reason:"stop"`；`deepseek-v4.1-flash` 流式（`stream:true`）正常返回内容与 `finish_reason:"stop"`。故障面窄到「该渠道 × 该模型 × 非流式」。
  4. 把用户贴出的真实 `responseText` 送入生产 `classifyResponse`，精确复现 `success=false` / `errorCode=invalid_protocol_success_response` / 同文案；同报文改判 `chat_sse` 亦因无内容 chunk 不判活。判定逻辑符合契约，不误判。
  5. 替代路径实测可用：`/v1/responses` 非流式（`responses_json`）中文挑战匹配返回 `29`；`chat_sse` 连跑 3 次挑战全部命中（其中 1 次 60s 未收盘，属该渠道稳定性问题）。

- 完成判定：渠道侧确认修复并以 `chat_json` 实弹测试通过；或用户裁决该渠道不再使用、相关账户改配后本条删除。
