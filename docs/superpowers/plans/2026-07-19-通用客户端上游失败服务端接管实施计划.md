# 通用客户端上游失败服务端接管 Implementation Plan
> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 在不识别通用上游具体状态码、错误类型或响应体语义的前提下，让网关对所有未提交给客户端的上游失败执行有界服务端接管：同账户短重试、当前请求排除下一 Key、下一账户、下一分组；仅当候选耗尽时才返回稳定可重试结果或精确客户端协议重试信号。图片请求沿用同一策略，只保留请求资源参数差异。

**Architecture:** 将 `fetchFirstAvailableUpstream` 的 HTTP 失败处理拆成“精确协议语义处理”和“通用不透明处理”两条路径。通用路径只读取有界诊断、完成审计/失败用量、清理当前会话亲和性，并通过请求级 Key 排除继续调度；不调用协议错误解析、失败分类、账号/Key/bucket/IP 健康惩罚或 Codex 语义持久化。只有 `response.ok` 才能提交给后续响应转发；精确客户端 profile 保留现有协议语义处理。最终无候选时复用现有 `UpstreamAttemptError`，通用客户端映射为稳定 503 retryable JSON，精确客户端映射为其协议重试信号。

**Tech Stack:** Node.js 22+, TypeScript, Express, `tsx` regression scripts, SQLite/PostgreSQL/Redis runtime drivers, existing gateway audit/usage/runtime state services.

## 2. Implement request-level opaque failure handling

- [ ] In `backend/src/modules/gateway/response/failure-dispatch.ts`, add a separate opaque-response handler next to `handleFailedUpstreamResponse`.
  - Read the body through the existing bounded reader only for diagnostics.
  - Complete the audit attempt as `success: false` and call a failure-usage recorder that does not parse protocol payloads or classify status/type.
  - Log only transport-neutral metadata and bounded diagnostic size/content; do not call `parseGatewayProtocolErrorPayload`, `classifyGatewayUpstreamFailure`, `decideAccountErrorPolicy`, account suppression, bucket failure, IP avoidance, API-Key local failure, or Codex-header semantic persistence.
  - Forget current account session affinity and return `retry` when the existing same-account retry budget permits; otherwise return `skip_account` with a request-level `tryNextApiKey` signal.
- [ ] In `backend/src/modules/gateway/usage/records.ts`, add an explicit opaque failure input/option (defaulting to existing classified behavior for exact profiles). The opaque branch must retain usage/audit records and raw bounded response snapshots but leave `errorCode`, `errorType`, and failure classification unset.
- [ ] In `backend/src/modules/gateway/dispatch/upstream-dispatch.ts`, route unsuccessful responses through the opaque handler when `interpretUpstreamResponseSemantics` is false; keep exact-profile routing unchanged. Add a request-only Key rotation signal that reuses `excludedApiKeyFingerprints` and `accountApiKeyAttemptCount` without creating `PendingAccountApiKeyFailure` or persistent Key health state.
- [ ] Change the success gate so only `response.ok` is returned as a committed upstream response. Preserve stream/protocol response handling after commit; never use generic body semantics to trigger failover.
- [ ] Run `pnpm --dir backend run typecheck` and the focused regression scripts. Expected green behavior: generic HTTP failure tries the next Key/account, exact profiles retain their current semantic failover, and opaque 200 SSE remains client-visible.

Expected result shape and dispatch boundary:

```ts
type OpaqueFailedUpstreamResponseResult = {
  action: 'retry' | 'skip_account'
  lastAttempt: UpstreamAttempt
  tryNextApiKeyForRequest: boolean
}

if (response.ok) return commitUpstreamResponse(response)
const failed = interpretUpstreamResponseSemantics
  ? await handleFailedUpstreamResponse(input)
  : await handleOpaqueFailedUpstreamResponse(input)
```

The exact implementation may reuse the existing return union, but `tryNextApiKeyForRequest` must not imply or trigger persistent API-Key failure state.
