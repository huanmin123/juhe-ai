# Redis 运行态与可靠队列隔离实施计划

> **For agentic workers:** REQUIRED SUB-SKILL: Use `superpowers:subagent-driven-development`（推荐）或 `superpowers:executing-plans`逐任务落地；每个任务先写失败回归，再做最小实现并运行目标验证。步骤使用 checkbox 跟踪。

**Goal:** 在不扩容主机、不丢失未落库 Redis Stream 消息的前提下，将 Redis cache、runtime state、reliable queue 物理隔离，消除 AOF rewrite 对调度状态的连带延迟，并让运行期 Redis 瞬时故障不再造成 Node 主进程异常退出。

**Architecture:** 保持仓库既定的 `6379 cache / 6380 state / 6381 queue` 角色。6380 state 关闭 AOF/RDB 但保持 `noeviction`；6381 queue 保留 AOF `everysec`、关闭 RDB、保持 `noeviction`。生产切换前停止 main 写入并要求六条 Stream 的 `pending=0 && lag=0`，先切 queue URL，确认消息连续性后再关闭 6380 持久化。

**Tech Stack:** Node.js 22、TypeScript、Redis 8、Redis Streams、PostgreSQL、pnpm、Docker Compose、macOS launchd、PowerShell 7、Bash。

---

## 0. 范围、证据和固定决策

### 当前证据

- 生产 `JUHE_AI_REDIS_STATE_URL` 与 `JUHE_AI_REDIS_QUEUE_URL` 当前都为 `127.0.0.1:6380/0`。
- 6379 约 12.5MB/768MB，6380 约 46.6MB/2GB，主机 16GB 内存、磁盘剩余约 347GB，无淘汰/OOM/拒绝连接证据。
- 6380 AOF 约 1.05GB；1GB rewrite 阈值仍约每 11 至 12 分钟重写，并伴随 runtime-log XADD 超时和 Node 进程恢复。
- `RedisStreamQueue` 的消息只有在消费成功后才 ACK/XDEL；未 ACK 条目不能作为普通缓存删除。

### 固定决策

- 不扩容主机；不把容量问题用更大 `maxmemory` 掩盖。
- 不直接在共享 6380 上关闭 AOF/RDB。
- 不把 state/queue 改成任何淘汰策略；state/queue 都是 `noeviction`。
- 不保留共享 URL 配置或绕过开关；三个物理 endpoint 不同是高性能模式启动硬门禁。
- 不把队列错误伪装成成功；runtime-log 等非核心 producer 使用现有有界 drop 语义并增加观测，关键 state 失败必须 fail-closed。
- 生产写操作必须单独取得正式上线确认和 `deployment-plan-lock.ps1 acquire`；本计划开发阶段不执行生产配置、进程、数据或切流操作。
