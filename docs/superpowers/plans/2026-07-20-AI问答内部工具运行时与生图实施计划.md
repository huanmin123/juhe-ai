## 1. 实施原则

1. 先建立可独立测试的工具契约和 Demo，再接入聊天路由。每完成一个阶段先运行对应回归，失败只修改一个变量后重试一次。
2. 工具执行器不拥有聊天路由、消息存储或其他工具；它只接收最小执行上下文，返回有界结构化结果或受控临时产物。
3. 上游托管工具继续由上游执行。应用只执行 Registry 中显式注册的 `diagnostic_echo` 和 `generate_image`，不会根据模型输出动态加载代码。
4. 生图统一从普通文本模型的 function call 进入；`gpt-image-2` 不再作为对话文本模型的特殊路由。图像上游请求仍经现有网关和当前会话 API Key。
5. 图片只向前端暴露一个逻辑 `assetId`；预览和原图是两个不可变对象，前端消息只使用 preview，点击和下载使用 original。

## 2. 阶段 A：契约、Schema 与 Registry

### 2.1 依赖与公共契约

- 在 `backend/package.json` 和 `pnpm-lock.yaml` 增加当前 Zod 3 兼容的 `ajv` 8 直接依赖，使用 JSON Schema 作为模型声明和服务端校验的唯一事实来源。
- 新增 `backend/src/modules/chat/tools/contracts.ts`：定义 `ChatInternalToolDefinition`、`ChatToolExecutionContext`、`ChatToolCall`、`ChatToolResult`、`ChatToolFailure`、`ChatToolLimits`、`ChatToolExecutionOwner` 和受控临时产物接口。
- 新增 `backend/src/modules/chat/tools/schema.ts`：创建 Ajv 单例、禁止未知关键字/不受支持 Schema 形态，封装有界 JSON 参数校验和错误摘要；不得把模型参数错误原样回显给用户。
- 新增 `backend/src/modules/chat/tools/registry.ts`：启动时显式注册、重复 ID/version 检查、Schema 编译、执行模式白名单和按环境过滤；未注册工具名返回稳定 `tool_not_available`。
- 新增 `backend/src/modules/chat/tools/resolver.ts`：根据环境、开发开关、模型 function calling 能力、API Key 权限、路由和图片能力返回本轮可见的应用工具；不可用工具不进入模型请求。
- 将 `backend/src/modules/chat/chat-tools.ts` 收敛为上游托管工具归一化与应用工具投影的兼容入口，删除会话路由中的绘图意图正则分支；结构图、Mermaid、SVG、图表等请求不触发应用生图工具。

### 2.2 工具实现与 Demo

- 新增 `backend/src/modules/chat/tools/executors/diagnostic-echo.ts`：只接受一个有界字符串，返回确定性 JSON；不读文件、网络、数据库、环境变量或外部凭据。
- 新增 `backend/src/modules/chat/tools/executors/index.ts`：集中注册 Demo 和后续图片执行器，不允许执行器互相导入。
- 仅当 `NODE_ENV` 为 `development` 或 `test` 且显式 `JUHE_AI_CHAT_INTERNAL_TOOLS_ENABLED=1` 时注册 `diagnostic_echo`；生产环境无论开关值如何都拒绝注册。
- 新增 `backend/src/modules/chat/tools/registry-regression.ts` 或对应 `backend/src/scripts/regression/chat-internal-tool-registry-regression.ts`，覆盖重复注册、非法 Schema、环境过滤、未注册工具和有界参数错误。

## 3. 阶段 B：协议适配与 Orchestrator

### 3.1 协议无关调用循环

- 新增 `backend/src/modules/chat/tools/protocol.ts`：将同一应用工具定义映射为 Responses function tool 和 Chat Completions function tool，并把分块参数归一化为 `{ callId, toolName, arguments, sourceOrder }`。
- Responses 适配必须保留必要的 reasoning/output items，并用 `function_call_output` 按 `call_id` 回灌；Chat Completions 适配必须保留 assistant `tool_calls` 和 `role=tool` 消息。
- 参数分块按 call ID 有界重组，禁止把完整上游响应先读入内存；调用名、JSON 参数、单次结果和事件数都应用独立上限。
- 首版请求固定 `parallel_tool_calls=false`，模型一次返回多个调用时按 `sourceOrder` 串行执行。

### 3.2 Orchestrator 与聊天流整合

- 新增 `backend/src/modules/chat/tools/orchestrator.ts`：驱动模型请求、工具事件发布、参数校验、执行、结果回灌、续答、精确去重、取消、轮次/调用数/结果字节上限和终态收敛。
- 新增 `backend/src/modules/chat/tools/chat-tool-events.ts`：把应用工具统一投影到现有 `AssistantTimeline`、SSE 和持久化 content block，显式写入 `executionOwner=application`；上游工具写 `executionOwner=upstream`，禁止重复执行。
- 改造 `backend/src/modules/chat/chat-transport.ts`：Responses 与 Chat Completions 都支持 function tool 请求和历史回灌；保持已有 hosted `web_search` 映射，工具类型不互相污染。
- 改造 `backend/src/modules/chat/chat-responses-sse.ts` 和 Chat Completions SSE 收集器：输出应用 function call 的 started/updated/completed 事件，保留源顺序、call ID、取消和 reader cancel。
- 改造 `backend/src/modules/chat/chat-generation-runner.ts`：runner 只负责生命周期、订阅、终态和持久化回调，工具循环由 Orchestrator 持有；同一 `AbortSignal` 贯穿模型、工具、临时文件和资产提交。
- 改造 `backend/src/modules/chat/chat.routes.ts`：移除 `imageGeneration` 特殊分支和 `shouldOfferChatImageGenerationTool` 绘图意图分支，改为解析本轮工具、创建 Orchestrator；保留上下文预算、accept/fail/cancel、heartbeat 和重附着边界。
- 扩展 `backend/src/modules/chat/chat-system-instructions.ts`：加入不写死具体比例的图片偏好，仅说明无明确尺寸时由模型按场景选择常规尺寸、不得无依据选择 2K/4K，明确尺寸/格式优先；不要把服务端数值限制写入系统提示词。

### 3.3 Demo 回归

- 新增 `backend/src/scripts/regression/chat-internal-tool-orchestrator-regression.ts`，用确定性假的 Responses/Chat Completions 流覆盖：无工具直接回答、单次调用、参数分块、结果回灌后续答、多调用顺序、精确重复去重、未知工具、循环上限、超时、AbortSignal 和上游 reader cancel。
- 将 `backend/package.json` 增加 `test:chat-internal-tool-registry`、`test:chat-internal-tool-orchestrator`，执行 `pnpm.cmd --dir backend run ...` 验证。
- 阶段 B 通过标准：两协议 Demo 都能看到工具开始、完成、结果回灌和最终回答；任何应用工具错误都以真实失败终态结束，不伪造成功。

## 4. 阶段 C：统一图片策略与 `generate_image`

### 4.1 图片策略模块

- 新增 `backend/src/modules/chat/chat-image-policy.ts`：定义输入优化图（WebP、最长边 1024、质量 82、1 MiB）和预览图（WebP、最长边 640、质量 78、512 KiB）两个用途档位；提供尺寸规范化、质量退避和字节上限校验。
- 输入上传改造 `backend/src/modules/chat/chat-asset-upload.ts`：后端策略为权威；合规 WebP 直接复用，其他支持格式只转一次 WebP；保留原始 MIME/尺寸/哈希用于审计和配额，不在浏览器和后端各自维护 JPEG 常量。
- 前端 `frontend/src/views/chat/composer/chatImagePreparationQueue.ts` 和图片准备模块改用后端初始化契约返回的策略，上传/粘贴统一生成 WebP；Blob URL 仅用于本地预览，发送后只传 `assetId`。
- 在 `backend/src/modules/chat/chat.routes.ts` 或初始化接口返回 `imagePolicy`，前端 `frontend/src/types/domain/chat.ts`、`frontend/src/api/domains/chat.ts` 增加类型和读取路径；策略缺失时前端不猜测新常量，显示中文失败提示。

### 4.2 `generate_image` 执行器

- 新增 `backend/src/modules/chat/tools/executors/generate-image.ts`：Schema 参数为 `prompt`、可选 `size`、可选 `quality`、可选 `output_format`，`n` 永远为 1；禁止模型传 API Key、Base URL、任意模型名、路径、外部 URL 或输出对象。
- 将 `backend/src/modules/chat/chat-image-generation-transport.ts` 收敛为 Images API 网络适配器：固定 `gpt-image-2`，使用会话绑定的 API Key 和现有网关 URL，请求 `/v1/images/generations`，支持 `webp/png/jpeg` 与受控尺寸/质量，所有响应/错误有界读取。
- 尺寸判定由执行器/策略模块完成：合法常规尺寸保留比例，最长边 1536、总像素 1,572,864、16px 倍数、最大 3:1；缺失/非法回退 1024x1024；明确 2K/4K 才进入高分辨率范围；记录 `sizeAdjusted`，不把 `auto` 交给上游。
- 默认输出格式为 WebP；用户明确 PNG/JPEG 时原图保持用户要求，不能用 WebP 覆盖明确格式；质量文案不等同于高分辨率。
- 新增 `backend/src/scripts/regression/chat-image-policy-regression.ts` 和 `chat-generate-image-tool-regression.ts`，覆盖格式/尺寸/比例/质量边界、默认 WebP、非法参数、图片输入拒绝、网关错误、取消和超大响应。

## 5. 阶段 D：双变体资产、读取缓存与下载

### 5.1 存储与事务

- 在 `backend/src/storage/schema/chat-schema.ts` 增加生成资产的 `preview_*` 字段（preview storage key、MIME、宽高、字节数、SHA-256）；当前只维护 original/preview 两变体，不引入通用变体表。
- 同步修改 `backend/src/storage/chat-assets.repository.ts` 的 row 映射、创建/提交、查找、引用和清理事务；容量账本按 original+preview 总字节计费，删除和过期同时清理两个对象。
- 扩展 `backend/src/storage/chat-asset-storage.ts`：提供变体区分的确定性 key、原子写入、流式读取、对象删除和路径边界校验；禁止把原图读入内存再转发。
- 在 `backend/src/modules/chat/chat-image-result-stream.ts` 中从原图临时文件流式生成 WebP preview，校验 MIME/尺寸/哈希/字节上限；任一 preview 编码失败则工具失败并清理未提交对象，不隐式回退 JPEG。
- 将 `backend/src/modules/chat/tools/artifact-sink.ts` 作为图片工具与仓储的唯一交界：原图和 preview 都准备成功后一次事务提交 `assistant_output` 引用；工具成功但模型续答失败时保留已提交资产事实。

### 5.2 HTTP 与前端渲染

- 修改 `backend/src/modules/chat/chat.routes.ts` 的资产 content 路由，支持 `variant=preview|original`，先校验登录、会话、资产状态、有效期和权限，再流式返回。
- 使用变体 SHA-256 作为 ETag；响应设置 `Cache-Control: private, max-age=86400, immutable`、`Content-Type`、`Content-Length`、`X-Content-Type-Options: nosniff`；`If-None-Match` 命中返回 304，不打开对象正文。
- `frontend/src/api/domains/chat.ts` 的 `chatAssetContentUrl` 增加变体参数；`frontend/src/views/chat/ChatGeneratedImage.vue` 的 `<img>` 固定 preview，打开链接和下载固定 original，下载保留 `download` 属性，复用仍只发 `assetId`。
- `frontend/src/types/domain/chat.ts` 的 `ChatAsset` 和 `output_image` 块只传逻辑资产元数据，不保存 data URL 或原图正文；恢复会话仍按同一 URL 读取，依赖浏览器缓存。
- 更新 `frontend/src/scripts/regression/chat-generated-image-regression.ts`（必要时新增）验证 preview/original URL 分离、下载链接、304 行为和 assetId 复用。

## 6. 阶段 E：整合、验证与真实验收

### 6.1 自动验证顺序

1. `pnpm.cmd --dir backend run test:chat-internal-tool-registry`
2. `pnpm.cmd --dir backend run test:chat-internal-tool-orchestrator`
3. `pnpm.cmd --dir backend run test:chat-image-policy`
4. `pnpm.cmd --dir backend run test:chat-generate-image-tool`
5. `pnpm.cmd --dir backend run test:chat-generated-asset`
6. 现有全部 backend `test:chat-*`（排除需要真实 PostgreSQL/Redis 连接的 smoke）和 frontend `test:chat-*`。
7. 后端 `pnpm.cmd --dir backend run typecheck`、runtime preflight；前端 `pnpm.cmd --dir frontend run typecheck`、`pnpm.cmd --dir frontend run build`；最后 `git diff --check`。

### 6.2 浏览器与缓存验收

- 启动新工作树本地服务，使用 Codex 内置浏览器的桌面和 390x844 视口；不使用生产 URL。
- 先用假的 Demo 场景确认 Responses/Chat Completions 的工具过程、顺序、折叠和终态工具栏。
- 再使用用户授权的本地测试账户，由普通文本模型自动调用 `generate_image`；不在对话中选择 `gpt-image-2`。
- 记录首次消息的 preview 请求、点击原图的 original 请求、下载响应和两次刷新后的 `ETag`/304；在浏览器 Network/服务端日志中确认第二次没有重新读取正文。
- 验证生成 WebP 默认格式、用户明确 PNG/JPEG 的原图格式、尺寸按场景且不无依据放大到 2K/4K、图片复用只传 assetId、原图可下载到本地。
- 真实上游失败时保留脱敏失败证据并继续验证应用失败终态、重发入口和清理；不得把失败写成真实成功。

- 变更集中在 `backend/src/modules/chat/tools/`、图片策略/资产存储、`chat-transport.ts`、`chat-generation-runner.ts`、`chat.routes.ts`、前端图片组件/API/类型及对应 regression 脚本；不顺带重构无关 Go/API Key/部署模块。
- 如果阶段 B 失败，保留 Demo 契约并回退只影响工具循环的本阶段文件，不恢复直接图像模型主流程。
- 如果真实上游失败，保留应用自动化成功路径和脱敏失败记录，不绕过网关、不读取 Codex Skill 凭据、不改生产配置。
- PDF、Word、Excel 只保留 Registry/worker 扩展边界，本计划不实现这些工具，也不引入 MCP、Skill 热加载或任意代码执行。
