# 响应检查策略渐进加载设计

## 1. 背景

响应检查策略管理页当前在首屏同时加载：

- 最多 100 条完整策略，每条包含九类 `match` 数组、备注和完整时间字段；
- 完整供应商 definitions，包含页面列表和策略表单不需要的协议档案与能力定义；
- 桌面表格把全部匹配数组展开为约 3300px 的宽表，移动卡片也重复渲染所有匹配字段。

Node repository 的管理列表使用 `SELECT *` 并为每行解析 `match_json`。查看和编辑弹窗没有详情请求，而是直接复用列表对象。因此只缩窄 HTTP 响应会破坏页面，必须同时拆分存储投影、HTTP DTO 和前端交互。

本设计承接 [全站页面 API 按需加载审计报告](../../reports/全站页面API按需加载审计报告-2026-07-20.md) 的 P1 结论，并遵循 [PLAN-0077](../../plans/计划-0077-管理接口DTO分层与渐进式加载.md) 的 overview/detail/options 分层规则。

## 2. 目标

- 首屏只读取和返回策略概览，不读取或解析 `match_json`、`notes`。
- 首屏不请求完整供应商 definitions，也不请求任何策略详情。
- 查看或编辑某条策略时，才按 ID 加载完整匹配条件与备注。
- 创建或编辑弹窗需要选择供应商时，才加载专用 provider-protocol 轻量 options。
- 列表、详情、options 在 SQLite 主线程、SQLite read worker 和 Node PostgreSQL 语义一致。
- 保持创建、更新、删除、运行时匹配、网关缓存失效和操作日志语义不变。

## 3. 范围与非目标

本批只修改 Node 后端和 Vue 前端，不修改 `backend-go/`，不切换 owner，不提交、不部署、不触碰生产。

本批不修改：

- 响应检查运行时的匹配算法、正向 matcher 校验、动作语义或优先级规则；
- 账户级响应检查规则；
- PostgreSQL / SQLite schema；
- 现有 `/providers/options` 和 `/providers/definitions` 契约；
- 网关 active policy 查询及其完整策略缓存。

## 4. HTTP 契约

### 4.1 概览列表

`GET /__aisys__/api/response-inspection-policies`

响应保持当前 envelope 和 `defaultRules` / `policies` 两组结构，但元素改为：

```ts
interface ResponseInspectionPolicyOverview {
  id: string
  defaultRule: boolean
  editable: boolean
  name: string
  enabled: boolean
  priority: number
  scopeType: 'protocol' | 'provider'
  protocolCode: 'openai' | 'anthropic' | 'gemini'
  providerCode?: string
  providerName?: string
  action: ResponseInspectionAction
  updatedAt?: string
}
```

概览严格不返回 `match`、`notes`、`createdAt`。列表继续有固定 100 条上限和稳定排序；本批不引入分页或模糊数据库搜索。前端本地搜索只基于名称、类型、层级、协议、供应商、状态、优先级和处置动作，搜索占位文案同步改为“搜索名称、协议、供应商或处置”。

### 4.2 完整详情

`GET /__aisys__/api/response-inspection-policies/:id`

```ts
interface ResponseInspectionPolicyDetail extends ResponseInspectionPolicyOverview {
  match: ResponseInspectionPolicyMatch
  notes?: string
  createdAt?: string
}
```

- 自定义策略按主键读取明确详情列；不存在返回 404。
- 内置默认规则也可按 ID 查看完整详情，`editable=false`。
- 查看和编辑共用该详情接口；迟到请求不能打开或覆盖另一条策略。

### 4.3 供应商协议轻量 options

`GET /__aisys__/api/response-inspection-policies/provider-options`

```ts
interface ResponseInspectionPolicyProviderOption {
  code: string
  name: string
  protocolCode: 'openai' | 'anthropic' | 'gemini'
}
```

- 只返回已启用供应商下已启用的 OpenAI、Anthropic、Gemini 协议档案。
- 按 `name ASC, code ASC, protocolCode ASC` 稳定排序并去重。
- 只投影 option 三字段，不复用完整 provider loader。
- 仅创建或编辑弹窗加载；只读查看不请求。
- 写接口仍使用现有后端校验确认供应商与协议匹配，不能信任 option 结果代替校验。

### 4.4 写接口

`POST /` 与 `PUT /:id` 继续接受完整 payload，并返回完整 Detail；`DELETE /:id` 保持现状。创建/更新成功后前端从返回 Detail 生成 Overview 并更新当前列表，不再立即重复请求详情；允许按统一 list revision 做一次概览确认刷新，但不能形成详情 + 列表双重阻塞链。

## 5. Node 存储边界

- 管理 overview SQL 明确投影 `id/name/enabled/priority/scope_type/protocol_code/provider_code/action/updated_at`，并以轻量 provider 名称 JOIN 或批量 lookup 返回 `providerName`。
- overview SQL 禁止 `SELECT *`、`match_json`、`notes`、`created_at`。
- detail SQL 按 ID 明确投影完整详情列，并只解析单行 `match_json`。
- gateway active policy 查询保持完整对象和既有索引，不与管理 overview mapper 合并。
- SQLite read worker 的 operation type、请求、响应和 handler 与同步/PG 路径同 DTO 契约。
- provider options 使用独立窄查询，禁止调用完整 `listProviders` / definitions loader。

## 6. 前端数据流

### 6.1 首屏

- `onMounted` 只请求 overview 列表。
- 不请求 provider definitions、provider options 或策略 detail。
- 桌面和移动列表保留：名称、默认/自定义、层级、协议、供应商、优先级、状态、处置、更新时间和操作。
- 移除全部 matcher 列、请求客户端列和备注列；这些信息在详情/编辑弹窗展示。

### 6.2 查看与编辑

- 点击查看或编辑后先进入独立 detail loading，再打开或填充弹窗。
- 详情请求以 `requestRevision + policyId` 保护；A 后点 B、关闭弹窗或页面失活后，A 的迟到响应不得提交。
- 查看默认规则只请求 detail，不请求 provider options。
- 编辑自定义策略并行或按需加载 detail 与 provider options；两者失败分别提示并允许重试，不复用旧策略表单。

### 6.3 创建

- 点击新建时加载 provider options；同一打开周期 singleflight，失败可重试。
- 页面补齐 Gemini 协议选项，使管理 UI 与当前 Node 三协议校验一致。
- 新建弹窗不请求任何策略 detail。

### 6.4 列表竞态

首屏、刷新、保存后确认和删除后确认共用同一个 list revision。旧列表响应不得覆盖更晚刷新或把已删除策略重新写回。loading 只由当前 revision 结束。

## 7. 权限与错误

- 路由沿用系统 API 的 admin 权限边界；普通用户返回 403，匿名返回现有认证错误。
- detail 不存在返回 404；options、list、detail 查询失败沿用现有中文错误模型。
- 详情或 options 失败时不打开带旧数据的表单，不清空列表，可重新点击重试。

## 8. 测试与验收

### 8.1 Node

- HTTP：overview 精确字段白名单且无 `match/notes/createdAt`；detail 完整、默认规则可查、404、权限分支；provider options 精确三字段与稳定排序。
- Query guard：overview/options SQL 无 `SELECT *`、`match_json`、`notes`、完整 provider loader；detail SQL 只读单条。
- SQLite：同步与 read worker 逐字段一致。
- PostgreSQL：真实 smoke 创建含大 matcher/notes 的策略，overview 不含详情，detail 完整，options 与 SQLite 等价，输出无 SKIP。
- 现有响应检查 runtime/gateway 回归继续通过。

### 8.2 前端

- 首屏请求矩阵：1 次 overview，0 次 detail，0 次 provider definitions/options。
- 查看、编辑、创建的详情/options 请求次数和顺序正确。
- A→B、关闭、失败重试、保存/删除与旧列表响应竞态正确。
- 桌面和移动列表不依赖 matcher/notes；详情表单仍完整显示。
- Gemini 创建/编辑能力与后端协议约束一致。

### 8.3 门禁

- Node 与前端专项回归、后端 typecheck、可运行范围内的前端 typecheck/build、`git diff --check`。
- 浏览器网络验证首屏/查看/编辑/创建；Browser/Playwright 不可用时明确记录环境限制。
- 至少两名只读 Agent 独立复核并交叉质疑，高严重度问题全部闭合。

## 9. 完成标准

- 首屏 HTTP 与 SQL 均不携带/读取完整 matcher、notes 或 provider definitions。
- 用户仍可从详情/编辑完整查看和修改所有策略字段。
- 三协议供应商选择、权限、写入校验和网关运行时语义无回归。
- 验证证据覆盖行为、HTTP、查询、SQLite worker、PG 和竞态，而非仅靠源码搜索。
