# 审计错误组列表与事件读取 Go 迁移设计

## 目标

在不接管审计捕获、payload 文件、hot search、runtime、writer、worker 和保留治理的前提下，将管理端审计错误组列表与错误组事件列表迁移到 Go opt-in 路径。实现以现行业务语义和客户端可见契约为基线，但不逐行复制 Node；内部使用 Go 原生分层、context、PostgreSQL 连接池和有界查询，并对迁移过程中确认的既有问题直接修复、记录原因和验证证据。

## 迁移原则

- 迁移的是业务事实、权限边界、客户端可见字段和仍然正确的行为，不复制 Node 事件循环、SQLite read worker、DB service、IPC 或其他运行时胶水。
- Node 只作为当前行为证据之一，不是不可修改的最终规格。发现错误、无界资源、错误语义、并发风险或 Go 中存在更清晰实现时，采用 Go 方案。
- 每项有意差异必须在本设计、PLAN-0081 或 W6 迁移记录中写明：Node 原行为、问题、Go 决策、影响范围和验证证据。没有证据的“顺手优化”不进入实现。
- 每个小块开始前、提交前和推送前 fetch 最新 `origin/master`。审计远端 Node 变更与 Go 已迁移 owner 的交集；业务契约变化同步到 Go，不适用的 Node 运行时改动记录原因。
- 远端前进后先检查文件和业务交集，再 rebase；重新执行受影响的定向与扩大验证，旧基线结果不能支撑新基线推送。

## 当前事实

Node 当前提供：

- `GET /__aisys__/api/audit-logs/error-groups`
- `GET /__aisys__/api/audit-logs/error-groups/:id/events`

错误组列表读取 `juhe_dataset.audit_error_groups`，关联系统账户、API Key、分组和账户名称；事件列表本质上是现有审计日志列表增加强制 `error_group_id` 筛选。Go 已迁移审计列表、详情和错误组详情 DTO，并已有 Goose `000069` 的错误组表、关联列和索引，但上述两条静态路由仍保持 404。

前端当前没有独立调用错误组列表或事件列表的 API 方法。本批因此只迁移后端契约，不新增页面、轮询或浏览器缓存行为。

## 范围

### 本批包含

- 管理员错误组列表、全部现有筛选、progressive pagination 和稳定排序。
- 单个错误组的审计事件列表，复用现有审计日志摘要 DTO、筛选、分页和 SQL 构造。
- 静态路由优先级、管理鉴权、读限流、120 秒请求 context、`no-store` 和通用中文依赖错误。
- store port、PostgreSQL reader、service DTO 映射、HTTP handler、router/app 既有装配和测试。
- W6、模块减法清单和 PLAN-0081 的范围与未完成门禁更新。

### 本批不包含

- `/:id/payloads/:payloadId` 原文窗口读取。
- `/search-hot` 文件扫描和 `/runtime` 进程/队列运行态。
- 审计捕获、Redis Stream / IPC、ingest writer、payload blob 文件写入、错误组聚合写入、worker 和保留清理。
- 前端页面改造、反向代理切流、生产 owner 切换、Node 路由删除或生产数据处理。
- 没有真实 `EXPLAIN` 证据的新索引。

## 方案选择

采用“扩展现有 `managementauditlogs` 纵切面，同时迁移列表和事件”的方案。

- 不新建重复模块：鉴权、DTO、列表语义和 store 已存在，拆出新模块会重复 handler、限流和 app 装配。
- 不只迁移错误组列表：列表和事件属于同一路由族，事件能够直接复用已迁移审计列表；拆成两批会重复路由与验证。
- payload、hot search 和 runtime 依赖完全不同的 owner，继续保持 Node，不因同一路由前缀扩大范围。

## Go 分层设计

### Store port

在现有 `ManagementAuditLogReader` 中增加错误组列表读取语义，输入仅包含 `path/model/statusCode/systemAccountId/apiKeyId/groupId/accountId/limit/offset`，输出为错误组摘要与 `HasMore`。port 不暴露 pgx、SQL 或 Node 类型。

事件列表不新增第二套存储查询：service 将路径参数中的错误组 ID写入现有 `ManagementAuditLogListInput.ErrorGroupID`，继续调用已经验证的审计列表 reader。

### PostgreSQL reader

错误组列表只选择错误组摘要和四类名称字段，不读取 audit event、attempt 或 payload。查询规则：

- `path` 先去除可选 HTTP method 和 query，再做精确匹配。
- `model`、四类归属 ID做精确匹配。
- `statusCode` 仅接受 `100..599` 的整数。
- 默认和最大 `pageSize=100`；单次读取 `pageSize+1`，最多暴露 1000 行窗口。
- 固定 `updated_at DESC, id DESC`，不得执行 `COUNT(*)`。

默认、path、model 和 status 过滤复用 Goose `000069` 现有索引。其他归属过滤先保持业务正确性；只有真实 PostgreSQL `EXPLAIN` 证明需要且能改善目标查询后，才单独设计索引变更。

### Service

新增错误组列表输入、列表结果和错误组摘要映射。详情与列表共用一个错误组映射 helper，避免两套字段规则漂移。

错误组事件方法复用现有审计列表 service，但强制使用路由 ID，忽略 query 中的同名筛选。未知错误组不额外查询存在性，按集合查询语义返回空列表 `200`；这不是吞错，因为调用没有请求单个错误组资源详情。

### HTTP 与路由

在动态 `/audit-logs/{id}` 前注册：

- `/audit-logs/error-groups`
- `/audit-logs/error-groups/{errorGroupId}/events`

两条路由复用现有管理端读限流和 session 鉴权；handler 继续只允许 admin / super_admin，设置 120 秒 context 和 `Cache-Control: no-store`。依赖错误只返回 `500 { message: "服务器内部错误" }`，不得回显 SQL、连接串或内部错误。

`/search-hot`、`/runtime`、payload 路径和其他未迁移子路径继续 404，避免整个 `/audit-logs/*` 前缀被误判为 Go owner。

## Node 与 Go 差异记录

- Node 的 SQLite、read worker、DB service 和 async driver 分支不迁移；Go 直接通过受 context 和连接池约束的 PostgreSQL store 读取。
- Node 事件列表通过重新调用通用 repository 形成间接复用；Go 在 service 层显式强制错误组 ID并复用同一 reader，所有权和覆盖关系更清楚。
- 不复制 Node 请求超时的 socket 写法；Go 使用 `context.WithTimeout` 向 store 传播取消。
- 如果实施时发现 Node 当前过滤、字段或错误行为存在确定问题，先写 RED 测试和差异记录，再采用 Go 修复；不得为了表面一致保留已证实缺陷。

## 并发、性能与安全

- 单次请求只执行一个错误组列表查询或一个审计事件列表查询，不启动额外 goroutine，不做逐行补数和 N+1 查询。
- 所有结果有 page/window 上界；列表不读取 payload，不执行全表内存分页或业务聚合。
- PostgreSQL 查询使用参数化占位符、稳定排序和请求 context；不存在字符串拼接注入路径。
- DTO 只返回现有审计错误组/日志摘要字段，不返回 payload、凭据、Cookie、Authorization 或内部错误。
- 本批不改变 writer、错误组聚合算法和表结构，因此不存在 Node/Go 双写。

## 测试与验收

所有生产代码遵循 RED-GREEN-REFACTOR。至少覆盖：

- service：默认/最大分页、1000 行窗口、全部筛选归一化、ECMAScript 空白、DTO 可选字段、progressive total。
- 事件：路由 ID覆盖 query、未知错误组空列表、现有审计筛选与摘要字段保持不变。
- store：摘要投影、四类名称关联、所有参数化条件、`updated_at DESC, id DESC`、`LIMIT pageSize+1`、无 `COUNT`、无 payload 表。
- HTTP/router：管理员与普通用户、read limiter 装配、120 秒 deadline、`no-store`、两条静态路由优先于详情、未迁移子路径仍 404、依赖错误不泄密。
- integration：fresh Goose schema、真实 PostgreSQL 功能 smoke 和目标索引 `EXPLAIN`；普通模式不可用可以 `SKIP`，`JUHE_AI_REQUIRE_INTEGRATION=1` 必须失败，`SKIP` 不记作真实通过。
- 收口：相关包、全量 `go test -p=1 ./...`、目标 race、`go vet -p=1 ./...`、integration-tag 编译、`go mod tidy -diff`、`git diff --check` 和独立规格/质量审查。

## Master 同步与 Node 漂移门禁

每个实现检查点执行：

1. fetch 最新 `origin/master`，记录基线 SHA。
2. 检查 Node `audit-logs.routes.ts`、read repository、query/mappers/types、schema 和前端调用变化。
3. 检查 Go 已迁移审计列表/详情与本批文件的交集。
4. 对业务变化做同步或写明不适用原因；内部 Node 运行时胶水不机械移植。
5. rebase 后重新执行受影响验证，再普通推送；禁止 force push 和带旧基线证据推送。

## 完成与删除门禁

本批完成只表示两条 Go opt-in 读路径具备可验证实现，不表示审计模块生产接管。真实 Node writer -> Go reader、查询计划、真实 listener/Cookie、反向代理精确单 owner、延迟与错误率、回滚和 Node 路由删除证据完成前，Node 实现必须保留。
