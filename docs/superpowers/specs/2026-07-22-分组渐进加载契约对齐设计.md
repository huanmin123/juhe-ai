# 分组渐进加载契约对齐设计

## 背景与目标

最新 Node 实现已经把分组页面拆成“静态列表 + 独立运行态快照 + 独立编辑详情”。Go 当前仍在列表中返回并读取 `schedulingPolicy`、`authorizationLimits`、累计 / 当日 usage、并发可用性和顶层 `runtimeSnapshot`，同时授权目标分组下拉仍返回完整分组 option，导致契约和读取成本都已经漂移。

本次只对齐以下管理端与个人端读取契约，不删除已有详情、创建、更新、删除和 account-options 能力，不新增 migration，不执行生产切流：

- `GET /__aisys__/api/groups` 与 `GET /__aisys__/api/my-groups`
- `GET /__aisys__/api/groups/status-snapshot` 与 `GET /__aisys__/api/my-groups/status-snapshot`
- `GET /__aisys__/api/authorization-options/grantee-groups` 与个人端对应路径
- `GET /__aisys__/api/groups/authorization-options` 与个人端对应路径

## 方案比较

### 方案 A：只裁剪 HTTP JSON，继续复用现有重查询

优点是改动少；缺点是列表仍读取调度策略、额度和 usage，无法满足“不在 list 回扫 usage/runtime”的性能边界，也会让未来调用方误以为已经完成渐进加载。因此不采用。

### 方案 B：专用轻量投影与独立状态快照

列表保留既有分页、owner / authorized union、owner scope、静态账户计数和授权来源摘要，但不读取或返回调度策略、额度、usage、实时并发或顶层 runtime 标记。状态快照使用专用可见性查询定位最多 100 个 group，再批量读取 `group_account_stats.current_concurrency` 与当天 usage。两个授权下拉分别使用最小 SQL 投影。该方案与最新 Node 一致，边界清晰，采用此方案。

### 方案 C：重构所有 groups/options 为统一投影框架

可以进一步减少重复 SQL，但会把 detail、account-options、route strategy options 一并卷入，扩大共享冲突和回归范围。本轮不采用。

## HTTP 与 DTO

### 分组列表

列表响应继续返回：

- 顶层 `items/total/hasMore/page/pageSize`。
- item 的静态字段：`id`、管理端可选 system account 字段、owner 字段、`name/providerCode/description/enabled/isDefault/groupType/accessType`。
- 授权摘要：`groupAuthorizationId/authorizationStatus/authorizationExpiresAt/authorizationSourceSummary`。
- 预聚合账户计数：`accountStats.total/available/active/disabled/error/rateLimited/concurrencyLimit`。
- 行动作布尔值：`canEdit/canDelete/canReturn`。

列表必须不返回 `schedulingPolicy`、`authorizationLimits`、`permissions`、`accountIds/accountCount`、`accountStats.currentConcurrency/currentConcurrencyAvailable/todayUsage/usage` 或顶层 `runtimeSnapshot`。列表请求不得读取 usage totals/daily、usage timezone、逐账户并发或 Redis runtime。

### 状态快照

新增管理端与个人端双路径，查询参数为逗号分隔 `groupIds`：

- 原始值最大 8192 字符。
- trim、去空、按首次出现去重。
- 至少 1 个，最多 100 个。
- 管理端沿用 `/groups` 的 admin-only 与可选 `systemAccountId` scope；个人端强制当前账户 scope 并忽略外部 `systemAccountId`。

响应固定为：

```json
{
  "generatedAt": "2026-07-22T00:00:00Z",
  "items": [
    {
      "id": "grp_1",
      "currentConcurrency": 3,
      "todayUsage": {
        "requestCount": 1,
        "inputTokens": 10,
        "outputTokens": 2,
        "cacheReadTokens": 0,
        "cacheReadCost": 0,
        "cacheWriteTokens": 0,
        "cacheWrite1hTokens": 0,
        "cacheWriteCost": 0,
        "thinkingTokens": 0,
        "inputImageTokens": 0,
        "outputImageTokens": 0,
        "totalTokens": 12,
        "totalCost": 0
      }
    }
  ]
}
```

不可见或不存在的 ID 直接省略。owner usage 使用 group scope；authorized usage 使用 group authorization scope。只读取预聚合表，不扫描 `usage_records`、`group_accounts` 或 Redis runtime。

### 授权下拉

- `authorization-options/grantee-groups` 严格只返回 `{id,name}`，SQL 也只投影这两列。
- `groups/authorization-options` 返回 `{id,name,canAuthorize}`。owner 行为 `true`，当前 grantee 看到的 authorized 行为 `false`；分页型 option 过滤、owner scope 与 Node 保持一致。

## 权限、限流与缓存

- 所有新路径继续受管理 API opt-in guard、只读 session 鉴权、system API IP read limiter 和 authenticated user read limiter 保护。
- 管理 `/groups/*` 只允许 admin / super_admin；个人路径强制 self scope。
- 响应继续由 system API `no-store` 中间件设置 `Cache-Control: no-store`。
- 不改变现有错误消息：缺少 status snapshot IDs 返回 Node 对齐的 400；依赖失败返回通用 500。

## 测试策略

先修改测试并确认 RED：

1. 列表 JSON 字段白名单和“usage/timezone/runtime reader 不得调用”。
2. status snapshot service 的 scope、可见性、owner/authorized usage key、空值和生成时间。
3. status snapshot HTTP 的 400/403、双路径、read limiter、no-store 和 router mount。
4. grantee-groups 严格 `{id,name}` 与 SQL 最小投影。
5. groups authorization-options 的 DTO、scope、handler、router 与 app 注入。

GREEN 后运行 groups / authorization options / store / HTTP / app 定向测试、`go vet ./...`、sqlc 生成一致性和 `git diff --check`。真实 PostgreSQL smoke 后置，不计入本轮通过声明。
