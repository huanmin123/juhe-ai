# 模型检查账户选项渐进加载设计

## 1. 背景

模型检查页面已经把历史列表、详情和运行中任务拆成各自的有界接口，账户下拉也只在展开或搜索后加载。但当前下拉仍复用通用 `/accounts/options` / `/my-accounts/options`：

- 通用 `AccountOptionSummary` 返回系统账户、owner、类型、状态、授权、到期时间和权限等模型检查不需要的字段；
- 前端取得宽 options 后再按供应商和协议 profile 过滤，后端仍会读取、组装并传输不合格候选；
- `run` 的当前可执行候选和 `history` 的历史筛选候选使用同一宽接口，只靠 `status/schedulable` 参数形成隐式差异；
- target、可信对比和历史筛选分别维护短缓存与请求代次，没有统一的身份隔离和精确 singleflight 边界。

本设计承接 [全站页面 API 按需加载审计报告](../../reports/全站页面API按需加载审计报告-2026-07-20.md) 的 P1/P2 剩余项，并遵循 [PLAN-20260704T095333001Z](../../plans/计划-20260704T095333001Z-管理接口DTO分层与渐进式加载.md) 的“用途专用 options、窄查询、后端资格过滤、前端按首次交互加载”原则。

## 2. 目标

- 为管理端和个人端提供同一个 Router 实现、两个挂载路径的模型检查专用账户 options。
- 用显式 `purpose=run|history` 区分当前可执行候选和历史筛选候选。
- HTTP 每项只返回模型检查实际需要的六个字段。
- 后端在 SQL/repository 层完成可见范围、授权额度和协议资格过滤，不先构造完整账户 Summary 再裁剪。
- 支持 `keyword` 小窗口搜索、`selectedIds` 已选项补齐和 `limit` 上限。
- 页面首屏不新增账户 options 请求；target、可信对比和历史筛选均在首次展开或确需补齐已选名称时加载。
- 同一身份和同一规范化请求使用 singleflight 与有界短缓存，同时用请求代次阻止迟到响应污染当前选择。
- SQLite 同步路径、SQLite read worker 和 Node PostgreSQL 保持等价。

## 3. 范围与非目标

本批只修改 Node 后端和 Vue 前端，不修改 `backend-go/`，不切换运行 owner，不提交、不推送、不部署、不触碰生产。

本批不修改：

- 模型检查 profile、探针、模型清单、运行结果、历史详情或 active-run 语义；
- 账户、授权或额度 schema；
- 通用 `/accounts/options`、`/my-accounts/options` 及其现有调用方；
- 模型检查运行接口的最终授权、模型、分组、凭据和网关候选校验；
- 可信对比必须同供应商、同协议 profile、同模型的最终规则。

## 4. HTTP 契约

### 4.1 共用路由

专用路由注册在现有 `modelChecksRouter`：

- 管理端：`GET /__aisys__/api/model-checks/account-options`
- 个人端：`GET /__aisys__/api/my-model-checks/account-options`

两条 URL 共用同一个 route、parser、service 和 DTO。管理端沿用现有 `requireAdmin` 挂载边界，可选 `systemAccountId`；个人端继续由 `forceSelfAccessScope` 强制当前登录用户，不能通过 query 伪造其他用户作用域。

### 4.2 请求参数

```ts
interface ModelCheckAccountOptionQuery {
  purpose: 'run' | 'history'
  keyword?: string
  selectedIds?: string[]
  limit?: number
  systemAccountId?: string // 仅管理端作用域
}
```

- `purpose` 必填，非法或缺失返回 400。
- `keyword` trim 后为空视为未提供；限制单值长度，只搜索账户名称和精确账户 ID，不搜索备注、凭据、标签或授权说明。
- `selectedIds` canonical 编码使用重复裸键，例如 `selectedIds=a&selectedIds=b`；可兼容现有 query parser 接受 bracket 数组。服务端 trim、去重并限制最多 20 个，拒绝嵌套对象、CSV/JSON 字符串、空 ID 和超长 ID。
- `limit` 默认 50，范围 1..50；非法数值返回 400，不静默扩大窗口。
- 稳定排序为名称不区分大小写升序、名称原值升序、ID 升序。
- `limit` 约束 keyword/default 窗口；合格的 `selectedIds` 作为补齐项合并、去重，因此最大响应为 `limit + 20`。
- `selectedIds` 只绕过 keyword/窗口，不绕过访问权限、purpose 资格或协议资格。不存在、不再可见或不合格的 ID 静默省略。

### 4.3 六字段响应

```ts
interface ModelCheckAccountOption {
  id: string
  name: string
  providerCode: string
  providerProtocolProfileId: string
  protocolCode: string
  protocolVersion: string
}
```

响应严格只包含以上六个字段，不返回 owner、系统账户名称、类型、状态、授权 ID、授权到期时间、权限、凭据、模型数组、分组、额度数值或运行态。

### 4.4 Purpose 语义

`purpose=run` 用于检测目标和可信对比账户：

- 候选必须在当前 AccessScope 可见；
- 必须是当前启用且可调度的账户；
- 授权账户必须处于有效授权范围，未到期、未停用，且有效授权额度未耗尽；
- `providerCode + providerProtocolProfileId` 必须命中 Node 当前模型检查支持矩阵，协议字段必须与 profile 一致；
- 可信对比的“排除目标账户、同供应商、同 profile、支持当前模型”可继续由前端用六字段即时收窄，但 POST `/run` 和 `/run/stream` 必须再次做权威校验。

`purpose=history` 仅用于历史列表账户筛选：

- 候选仍必须在当前 AccessScope 可见，并具备模型检查支持的供应商协议 profile；
- 不要求当前 active/schedulable，也不按当前授权 quota 排除，否则已停用或当前额度耗尽的账户会从历史筛选中消失；
- 已撤销授权、作用域外或其他不可见账户仍静默省略；历史行自身携带的 `targetName` 继续用于展示，不能以 options 是否仍可见决定历史记录是否显示。

options 只是候选提示，不是执行授权。账户状态、授权额度、协议 profile、模型限制、绑定分组、凭据和真实网关候选都可能在选择后变化，后端运行入口继续调用现有最终校验；前端不得因 option 曾出现而跳过错误处理。

## 5. Node 查询与存储边界

- 新增专用 `ModelCheckAccountOption` repository/query，不调用通用 `listAccountOptions*` 后再 `map/filter`，也不调用完整账户 Summary 或测试详情 loader。
- SQLite 和 PostgreSQL 均使用显式六列投影；禁止 `SELECT *`，禁止读取/解密 credentials，禁止加载模型数组、标签、统计、运行态或账户详情。
- owner、自有与授权账户的访问范围必须在 SQL 中收口。不可先读取全局候选，再由 JavaScript 按 viewer 过滤。
- `run` 的授权候选复用当前权威授权有效期、状态和 quota 口径；SQLite 所需 quota 查询/函数与 PostgreSQL JOIN 必须和现有调度资格一致。真实零额度、已超额和无额度限制不能混淆。
- 协议资格使用后端 `model-checks.profiles` / provider capability 的单一规则来源，避免复制一份容易漂移的前端常量；SQL 可先按有界 profile 集合过滤，service 仍对六字段结果做一致性断言。
- default/keyword 窗口与 selected 补齐使用固定数量批量查询或一个可证明有界的 UNION，不得按 selected ID 做 N+1。
- SQLite DB service 增加专用 read-only operation；read worker 内直接执行窄查询。同步 SQLite、read worker 和 PostgreSQL 的参数规范化、排序、去重、省略和六字段结果必须逐项一致。
- 该接口只读业务与授权/quota 事实，不引入 Redis、凭据解密、运行时探针或写操作。

## 6. 前端数据流

### 6.1 首次展开与用途资源

- 页面 mounted 仍只加载模型检查静态 options、历史 runs 和 active run；账户 options 请求数为 0。
- 检测目标下拉首次展开或远程搜索时请求 `purpose=run`。
- 可信对比只有在用户开启可信对比并首次展开/搜索时请求 `purpose=run`；收到六字段后再按当前目标、profile 和模型过滤。
- 历史账户筛选首次展开/搜索时请求 `purpose=history`。
- 历史列表行已有 `targetName` 时直接写入现有账户名称缓存，不为已知名称追加 lookup；恢复的已选 ID 缺少 label 时才用 `selectedIds` 做按需补齐。

### 6.2 Singleflight 与身份缓存

三个消费者共用一个专用 options resource：

- 对完全相同的规范化 key 只保留一个 in-flight Promise；target 和 comparison 的相同 `run` 窗口可共享结果。
- key 至少包含 API 契约版本、admin/self 路径、当前用户 ID、角色、auth revision、有效 `systemAccountId`、purpose、规范化 keyword、排序后的 selectedIds 和 limit。
- 使用短 TTL、有界 LRU 的会话内缓存；不得持久化到账户切换后仍可复用的全局存储。登出、重新登录、角色/身份 revision 或作用域变化后旧缓存不可命中。
- 失败不写缓存、不永久保留 rejected Promise；下一次展开或搜索可以重试。

### 6.3 竞态与提交所有权

- target、comparison、history 各有独立 consumer generation；共享网络请求不等于共享 UI 提交权。
- keyword A→B、scope A→B、purpose 切换、关闭下拉、重置表单、切换目标模型或用户身份时，旧 intent 立即失效。
- A→B→A 时不能复用第一次 A 的已失效 in-flight 结果提交当前 A；可命中已完成且身份一致的缓存，或创建属于新 intent 的请求。
- 只有当前 generation、身份 key、scope 和 purpose 同时匹配时才能写 options/loading/error；迟到成功或失败不能覆盖新结果、清空新 loading 或弹出过期错误。
- `selectedIds` 补齐结果与搜索窗口按 ID 合并，已选 label 不因远程搜索窗口变化而消失；服务端省略不可见/不合格 ID 时，前端清除失效选择或保留历史静态名称，行为按 run/history 分开。

## 7. 权限与安全

- 管理端保持 admin 权限；普通用户访问管理 URL 返回 403，个人 URL 只看到本人及当前仍有效的授权可见范围。
- 管理端指定 `systemAccountId` 与页面当前 scope 一致；未指定时沿用现有管理全局口径。个人端忽略或拒绝伪造 scope，不能扩大可见范围。
- 不可见、不存在、撤销授权和不合格 selected IDs 一律省略，不用 404/占位对象暴露存在性。
- 六字段均为展示与协议判断信息；接口仍沿用登录态保护和现有系统 API 缓存头，不返回 secret、credential 或 quota 数值。

## 8. 测试与验收

### 8.1 Node

- Parser/HTTP：`run/history`、缺失/非法 purpose、keyword trim/长度、limit 1/50/越界、重复裸键/bracket selectedIds、去重、20/21、嵌套/CSV/JSON/空/超长拒绝。
- DTO：每项精确六字段；默认窗口与 selected 补齐、稳定排序、去重和最大数量正确。
- 权限：管理全局/指定 owner、个人 self、自有/授权、撤销/过期授权、伪造 scope、不可见/不存在 selected ID 静默省略。
- 资格：`run` 排除 inactive、unschedulable、授权 quota 耗尽和不支持 profile；`history` 保留可见的 inactive/quota 耗尽账户但排除不支持 profile；授权无上限与真实零额度口径正确。
- 最终校验：option 返回后再停用、耗尽 quota、改变 profile/模型限制、解绑分组，POST run/stream 仍由后端拒绝。
- Query guard：显式六列、无 `SELECT *`、无 credentials/完整 Summary/统计/runtime、无按 ID N+1。
- SQLite 同步/read worker 逐字段等价；worker operation 只读且错误可传播。
- 真实 PostgreSQL smoke 覆盖 owner/authorized/quota/profile/selectedIds/排序，必须输出真实执行证据，SKIP 不计通过。
- 现有模型检查运行、可信对比、协议 profile、历史列表/详情和账户通用 options 回归继续通过。

### 8.2 前端

- 首屏账户 options 请求为 0；target、comparison、history 分别只在首次展开/搜索或缺名补齐时加载。
- 完全相同 key 并发只发一次请求；失败后可重试；短缓存命中不重复请求。
- key 隔离 admin/self、用户、角色、auth revision、owner scope、purpose、keyword、selectedIds 和 limit。
- A→B、A→B→A、scope/身份切换、关闭、重置、目标/模型变化和卸载迟到均不能污染当前状态。
- `run` 省略已选账户时清理无效运行选择；`history` 仍可依赖历史行/label cache 展示旧名称，不隐藏历史记录。
- 六字段足以驱动供应商协议、模型列表和可信对比过滤，页面不再依赖通用 `AccountOptionSummary` 的其他字段。

### 8.3 门禁与复核

- Node/前端专项回归、后端 typecheck、可运行范围内的前端 typecheck/build、`git diff --check`。
- 浏览器网络验证首屏、三类下拉、搜索、恢复筛选、切换身份和失败重试；Browser/Playwright 不可用时记录环境限制。
- 至少两名只读 Agent 分别复核权限/查询和前端竞态/缓存，并交叉质疑；高严重度问题全部闭合。

## 9. 完成标准

- 模型检查账户下拉不再调用通用账户 options，HTTP 和 SQL 都只处理六字段专用 DTO。
- 首屏不请求账户 options，三类下拉按 `run/history` 首次交互加载，精确请求可 singleflight。
- `run` 的授权 quota、调度和协议资格与当前事实一致，`history` 不因当前不可运行而丢失仍可见历史账户。
- selectedIds、不可见省略、最终运行校验、身份缓存和所有关键竞态均有行为证据。
- SQLite 同步/read worker、真实 PostgreSQL、前端和既有模型检查回归全部闭合后，才可把专项计划标记完成。
