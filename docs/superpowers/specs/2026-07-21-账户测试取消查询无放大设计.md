# 账户测试取消查询无放大设计

## 1. 问题与证据

高性能 PostgreSQL 模式下，后台账号测试出现：

```text
后台 DB service 请求超时：is_account_test_task_cancel_requested
```

当前链路是 `ops-worker -> server IPC -> DB service -> PostgreSQL`。账号测试任务在开始前、上游测试完成后、异常处理路径会查询取消状态；未取消时，`isAccountTestTaskCancelRequestedAsync` 先读任务行，再读关联 session 的取消原因，单个检查最多执行两次 SQL。账号测试 PostgreSQL 并发默认固定为 100，因此一次批量测试会把取消查询、任务状态写入和完成读取同时打入同一条 DB service / PostgreSQL 连接链路。

现有 5 秒 timeout 只限制请求等待时间，不能减少请求数量，也不能把 worker 与 server 两段等待合并成一个端到端预算。运行日志 Redis 改造已经移除一个主要压力源，但没有覆盖这条账号测试取消查询链。

## 2. 目标

- 活动账号测试取消必须在 worker 收到 cancel IPC 后立即停止，不再等待 PostgreSQL 轮询确认。
- 任务启动和任务完成必须由 PostgreSQL 条件状态转换保证，取消与完成不能互相覆盖。
- worker 重启、任务恢复和未收到 cancel IPC 时，数据库仍是取消状态的最终权威。
- 删除账号测试队列中每个任务额外的取消状态读 RPC，避免在 100 并发下形成 `O(task * check * SQL)` 放大。
- 保留现有权限、任务状态、错误语义和 PostgreSQL schema，不新增 Redis 依赖或生产锁。
- 增加能复现并发取消查询放大的回归和真实 PostgreSQL smoke。

## 3. 非目标

- 不把 `accountTestTaskConcurrency` 从 100 调大或调小来掩盖 DB service 堵塞。
- 不把取消状态迁移到 Redis、内存全局状态或运行日志文件。
- 不修改 PostgreSQL `max_connections`、PgBouncer 池或生产配置。
- 不改变真实上游模型测试的 timeout、重试和账户选择策略。
- 不部署、不操作生产数据；上线等待用户通知。

## 4. 方案比较

### 4.1 方案 A：只延长取消 RPC timeout

保留现有每任务查询，单独把取消查询 timeout 调到 10 秒或更高。

问题：只延长等待窗口，仍保留每任务多次 RPC 和两条 SQL；队列、连接池或事件循环继续拥塞时，超时会延后而不是消失。弃用。

### 4.2 方案 B：合并取消 SQL，但保留每任务轮询

把任务取消标记和 session 取消原因合并为一次 `LEFT JOIN` 查询，减少一半 SQL。

问题：仍在任务开始、结束和异常路径重复发 DB service RPC；活动任务取消本来已有 worker IPC 和 `AbortController`，继续轮询属于重复事实读取。可作为数据库 repository 的局部优化，但不能单独解决本问题。

### 4.3 方案 C：本地取消信号 + 数据库条件状态转换（推荐）

worker 运行期间以 `AbortController` 作为即时取消信号；任务 claim 在 DB service 内通过一次原子状态转换确认 queued/cancelled；任务完成通过 `UPDATE ... WHERE status='running' AND cancel_requested=false` 条件提交，返回“完成 / 已取消 / 不存在”结果。只有 worker 重启恢复、任务 claim 或条件提交失败时才依赖数据库状态。

推荐原因：消除活动任务的重复取消读 RPC，同时保留数据库在跨进程重启、竞态和最终状态上的权威性，不需要新增锁或缓存事实源。

## 5. 目标数据流

```text
cancel API
  -> PostgreSQL: cancel_requested=true / status_message
  -> worker IPC: abort task controller

worker claim
  -> DB service: mark queued -> running (同一次状态转换读取取消状态)
  -> 若已取消：直接返回 canceled，不启动上游测试

上游测试运行中
  -> worker 本地 AbortController 立即终止
  -> 不轮询 is_account_test_task_cancel_requested

测试结束
  -> DB service: 条件完成 update
  -> updated=1: completed
  -> updated=0: 读取最终状态并按 canceled / 已结束收口
```

## 6. 具体边界

### 6.1 Claim

保留 `mark_account_test_task_running` 对 queued、`cancel_requested=false` 的条件约束。PostgreSQL 实现应在一次事务或一次可验证的状态转换中完成取消判断和 running 更新；返回值不足以启动测试时，worker 直接结束任务，不再补发取消查询。

### 6.2 Live cancel

保留 `dispatchAccountTestCancel -> sendAccountTestCancelToWorker -> AbortController` 路径。worker 收到信号后立即中断上游请求和本地重试；取消 API 已经写入数据库的事实不需要被 worker 每次轮询确认。

### 6.3 Completion

完成、失败和取消必须使用条件状态转换。完成写入不能覆盖已经设置 `cancel_requested=true` 的任务；如果条件更新没有影响行，按数据库最终状态返回取消或已结束，不伪造成功。

### 6.4 Error path

原始错误已经是 DB service timeout、IPC unavailable 或任务不存在时，异常收口不得再次无界调用取消 RPC。日志保留原始错误和 task id，任务最终状态由下一次维护扫描或条件更新收口。

### 6.5 Observability

保留并使用现有 DB service runtime snapshot：pending、queued、queue wait、timeout、expired、event-loop timeout。账号测试回归额外记录每批任务的 claim、cancel、complete RPC 数量和耗时，验证取消读 RPC 不随任务数线性放大。

## 7. 兼容与回滚

- 不新增表、不新增字段、不改变现有接口 JSON 结构。
- Node standalone 继续走现有 SQLite repository 分支。
- PostgreSQL 只改账号测试任务 repository、DB service handler 类型和 worker 调度边界。
- 回滚只需恢复本次代码提交；现有任务表状态和 `cancel_requested` 字段保持兼容。

## 8. 验收标准

1. 账号测试队列源码不再为活动任务调用 `is_account_test_task_cancel_requested` 或 `read_account_test_task_cancel_message` 作为正常轮询路径。
2. claim、complete、cancel 的成功、已取消、竞态和异常路径均有回归测试。
3. 100 个并发任务的 mock/压力回归中，取消状态读 RPC 数量不再按每个阶段重复增长，且没有 DB service timeout。
4. `pnpm --filter juhe-ai-backend typecheck`、构建、账户测试任务回归、DB service 回归通过。
5. 使用测试库 `192.168.1.203` 完成 PostgreSQL 任务状态 smoke；Redis 只验证现有队列隔离不被改动。
6. 两名只读复核 Agent 完成需求、并发安全、错误收口和文档复查；不部署上线。
