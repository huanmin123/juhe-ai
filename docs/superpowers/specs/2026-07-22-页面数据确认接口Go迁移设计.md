# 页面数据确认接口 Go 迁移设计

## 目标

将前端已调用的 `POST /__aisys__/api/data-changes/confirm` 接入 Go management API。Go 直接复用现有 `redis.PageDataChangeConfirmer`、协议版本 2、Redis key 前缀、Lua confirm 快路径和 scope fingerprint，不建立第二套 token、事件或 Redis 协议。

## HTTP 与鉴权边界

- 使用现有 management Cookie 权威鉴权，允许任意已登录角色调用 `viewScope=self`。
- `viewScope=admin` 仅允许管理员；普通用户返回 `403`。
- `self` 禁止携带非空 `targetSystemAccountId`；`admin` 可省略 target 表示全局，也可指定目标系统账户。
- 请求通过读鉴权 / 读限流中间件，虽然方法为 POST 也不 touch session；System API 外层继续统一设置 `Cache-Control: no-store`。
- 请求必须使用 `application/json`（允许 charset），沿用 Node System API 的 `256kb` body 上限；请求体只允许一个 JSON 对象，拒绝未知顶层字段、未知 token 字段、尾随 JSON、非法枚举、空字符串、非整数、负数和超过 JavaScript safe integer 的序列值。
- 单次最多 32 个 domain；domain 必须来自现有协议白名单。token 可为 `null`。
- Redis confirm 或结果解析失败返回 `503`、`Retry-After: 5` 和固定中文错误，不查询 PostgreSQL 或其他业务表。

## 组件与数据流

1. `httpapi` handler 从认证上下文取得 viewer ID / role，严格解析请求并做权限校验。
2. handler 调用独立 service interface；应用层 adapter 使用 `redis.NewPageDataScope` 计算服务端 scope，再调用现有 `PageDataChangeConfirmer.Confirm`。
3. handler 用现有 `{ "data": ... }` 响应壳返回 v2 confirm 结果。
4. `app/server.go` 使用现有 state Redis 与 `RedisNamespace` 构造 confirmer；router 将该 POST 精确挂到 read auth / read rate-limit 链。

## 测试与验收

- handler 单测覆盖 self/admin、target、严格 JSON、token 字段、domain 上限、服务异常和响应 header。
- adapter 单测固定 viewer/viewScope/target 到现有 scope 计算与 confirmer 调用。
- router 单测固定路径、read auth、不 touch、no-store。
- platform Redis 既有测试继续证明旧 epoch 为 `reload`、reset sequence 变化为 `reset`、单次 Lua 和协议兼容。
- 完成目标包测试、相关回归、`go vet ./...`、差异检查和本地提交；真实 Redis smoke 后置，不作为本提交伪造证据。
