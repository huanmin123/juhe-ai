# 响应检查策略 Go 迁移设计

## 目标与边界

把管理端管理员专属的响应检查策略接口以 Go opt-in 方式迁移，覆盖 `GET/POST /response-inspection-policies` 与 `PUT/DELETE /response-inspection-policies/{id}`。Node 仍保留当前 owner，本切片不删除 Node 路由、不生产切流、不迁移网关读取逻辑，也不新增 Go migration 编号。

业务事实以 `backend/src/modules/response-inspection-policies/response-inspection-policies.routes.ts`、`backend/src/storage/response-inspection-policy.repository.ts` 和 `frontend/src/types/domain/response-inspection-policies.ts` 为准。共享表 `juhe_business.response_inspection_policies` 仅由 Node schema 创建，Go 直接读写该表；部署前必须先保证 Node schema 已初始化。

## 方案比较与选择

1. 在 HTTP handler 内直接写 SQL：文件少，但校验、事务、副作用和 HTTP 强耦合，难以测试事务提交边界。
2. 新建 module + port + PostgreSQL store：职责清晰，可用 fake store 精确证明 RED/GREEN、提交后失效和 404/冲突语义；选用此方案。
3. 从 Go migration 复制 Node 表：能让 Go 独立建库，但会产生双 schema owner 和 migration 编号冲突，本切片禁止。

## 架构

- `internal/modules/managementresponseinspectionpolicies`：定义默认规则、DTO、严格业务校验、稳定排序、100 条容量保护、CRUD orchestration、事务提交后 runtime invalidation。
- `internal/store/port/management_response_inspection_policies.go`：定义共享 DTO、事务 store 和 transactor 接口。
- `internal/store/postgres/managementresponseinspectionpolicies.go`：复用现有 PostgreSQL pool，访问 `juhe_business.response_inspection_policies` 和 provider/profile 表；不新增 driver。
- `internal/httpapi/management_response_inspection_policies.go`：admin-only、strict JSON、Node 兼容响应、错误映射和 best-effort operation log。
- `internal/httpapi/mutation_guard.go`、`router.go`、`internal/app/server.go`：加入 create/update/delete guard、opt-in 路由和生产接线。

## 契约与校验

- body 最大 `256 KiB`，只允许 `name/enabled/priority/scopeType/protocolCode/providerCode/match/action/notes`。
- `name` 为 trim 后 1..100；`enabled` 默认 `true`；`priority` 默认 `100` 且为 1..9999 整数。
- `scopeType` 仅 `protocol/provider`；`protocolCode` 仅 `openai/anthropic/gemini`。
- protocol scope 不允许非空 `providerCode`；provider scope 必须提供 1..80 的 provider code，并在同一事务里验证供应商及同协议 profile 均启用。
- match 只允许九个既有字段；每个数组最多 50 项（clientProfiles 最多 6），字符串 trim 后 1..200；client profile 必须属于前端 enum。
- `outputTextExcludes` 和 `clientProfiles` 不能单独构成命中，至少一个正向 matcher 非空。
- action 仅六个既有枚举；notes 为 null 或 trim 后最多 1000。
- GET 返回系统默认规则和管理规则；管理规则固定按 `priority ASC, updated_at DESC, id ASC`，最多 100 条。
- 不存在的 update/delete 返回 404；容量达到 100 或并发写冲突返回 400/409 的稳定中文错误。

## 一致性与副作用

- create/update/delete 在 PostgreSQL 事务中完成；update/delete 锁定目标行，create 在事务中用 advisory lock 串行化容量检查。
- 仅事务成功提交后调用现有 `InvalidateGatewayRuntime`，reason 分别为 `response_inspection_policy_created/updated/deleted`。失效失败记录结构化 warning，但不把已提交写操作改成失败。
- 操作日志在 HTTP 成功响应前 best-effort 入队，失败不回滚数据。日志不保存 matcher 原文，只保存每个 matcher 的数量摘要，固定字段数和字符串长度上限，避免敏感词与大数组进入日志。
- mutation guard 指纹包含资源 ID 与完整稳定 payload hash；matcher 原文只进入 SHA-256 指纹，不进入 key、日志或响应外字段。

### 已确认的共享 schema 漂移

Node 的 PostgreSQL provider/profile 初始化路径仍存在 `INTEGER(0/1)` 启用标记，而 Go migration catalog 定义为 `BOOLEAN`。响应策略表本身仍由 Node owner 创建，本切片不创建第二套 migration，也不借 CRUD 改写这些基础表。供应商可用性校验使用 `enabled::text IN ('true', '1')` 兼容两种既存事实；这是局部读取兼容，不是长期 schema 方案。后续 schema-owner 收敛工作应统一字段类型并移除此条件。

## 测试与验收

- module：默认规则、strict validation、provider/protocol 互斥、正向 matcher、容量/冲突、404、事务提交后失效、失败事务不失效、失效失败不覆盖提交。
- HTTP：admin-only、strict JSON、状态码/响应、mutation guard、operation log 有界无敏感原文、日志失败不覆盖成功。
- store：共享 schema SQL、稳定排序、advisory lock/`FOR UPDATE`、provider profile 校验、无 Go migration。
- app/router：handler 非 nil 时才注册，沿用管理 API auth/touch/read-write limiter。
- 本轮并发迁移最低验证：目标 package tests、目标 package `go vet`、`gofmt`、`git diff --check`。全量测试/race 和真实 PostgreSQL/Redis smoke 统一后置，不计入本切片通过。

## 自审

- 无 Node driver 复制；复用 Go pool、gateway invalidator 和 operation-log enqueue。
- 未新增 migration 编号；共享 schema 前置条件明确。
- PUT 为完整替换，未误做 PATCH。
- 失效与操作日志都在提交后，失败不会伪装为回滚。
- 日志和 mutation guard 不暴露 matcher 原文。
