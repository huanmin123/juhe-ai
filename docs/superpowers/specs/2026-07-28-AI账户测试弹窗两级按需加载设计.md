# AI 账户测试弹窗两级按需加载设计

> 契约纠正：本设计的“批量模型选项携带请求能力”部分已由 [Node 管理接口按需读写设计](2026-07-28-Node管理接口按需读写设计.md) 和 [PLAN-20260727T183737351Z](../../plans/计划-20260727T183737351Z-Node管理接口按需读写重构.md) 纠正。当前批量 `test-options` 严格只有 `{ id, name }`；请求形态始终在用户展开请求形态下拉时按当前模型定点加载。本轮只涉及 Node + Vue，未修改 Go。

## 1. 问题与目标

账户列表已经返回 `healthCheckModel` 和 `healthCheckEndpointMode`，但测试弹窗打开后仍立即请求 `test-options`，把供应商候选模型及每个模型的请求形态全部加载。该行为重复读取已经随列表返回的默认值，也让未操作下拉的用户承担目录查询、传输、解析和响应式状态成本。

本次目标固定为：打开弹窗零额外 options 请求；模型和请求形态分别在用户展开对应下拉时加载，并且请求范围不互相放大。

## 2. 已确认契约

- 弹窗初始化直接使用当前 `AccountSummary.healthCheckModel` 和 `AccountSummary.healthCheckEndpointMode`。
- 展开“选择测试模型”才调用 `GET /accounts/:id/test-options` 或个人端镜像接口，返回当前供应商作用域内严格为 `Array<{ id, name }>` 的模型窗口；搜索继续复用该接口。
- 展开“测试请求形态”时，只调用 `GET /accounts/:id/test-options/models/:modelId` 或个人端镜像接口，读取当前模型的能力。
- `test-options` 不携带 `supportedApiProtocols` 或 `testEndpointModes`。用户切换模型时只清空旧能力，直到展开请求形态下拉才读取新模型能力。
- 测试提交仍由后端重新校验模型、账户能力和请求形态；前端 options 不是授权或能力的最终事实。

## 3. 前端状态与竞态

- 模型列表请求和单模型能力请求使用独立 loading、错误、AbortController 和请求代次。
- 切换账户或关闭弹窗时同时取消两类在途请求。
- 用户选择另一个模型时取消旧模型能力请求；旧响应不得覆盖新模型的请求形态。
- 初始列表默认请求形态只表示账户保存值，不表示该模型完整能力已经加载；首次展开协议下拉定点补齐当前模型能力。
- 批量模型选项与单模型能力是不同资源，加载模型列表不能把当前模型能力标记为已加载。
- 草稿测试继续使用表单已经计算出的固定模型和请求形态，不进入自由模型/协议加载流程。

## 4. 后端与数据边界

- Node 账户列表返回两个标量字段，本次不新增 schema、列表查询或 DTO 字段；Go 未修改且不纳入本次验收。
- 现有批量模型 options 和单模型 capabilities 路由继续复用，但批量响应收窄为 `{ id, name }`，能力只由单模型接口返回。
- 管理端请求继续携带目标 `systemAccountId`；个人端继续由 self scope 固定调用者范围。

## 5. 验收与回退

- 打开管理端或个人端测试弹窗后，模型 options 和单模型 capabilities 调用次数都为 0。
- 展开模型下拉只增加一次批量 options 请求；重复展开同一窗口不重复请求。
- 直接展开请求形态下拉只增加一次当前模型 capabilities 请求，不调用批量 options。
- 批量 options 每项严格只有 `{ id, name }`；模型选择后不自动加载能力，展开请求形态下拉才读取当前模型 capabilities。
- 切账户、切模型和关闭弹窗的迟到响应均被隔离。
- 回退时可以恢复前端交互加载器，但不得恢复弹窗打开即预取，也不得从账户协议猜测已保存默认值。
