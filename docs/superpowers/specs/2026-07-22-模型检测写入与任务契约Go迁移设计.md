# 模型检测写入与任务契约 Go 迁移设计

## 目标

把 Node 模型检测的业务原理迁移为 Go 原生的可恢复任务，而不是复制 HTTP 长请求、进程内 `Map`、子进程池和 SQLite writer IPC。第一步固定 writer / job / lifecycle 契约；后续再分批实现 PostgreSQL schema、Asynq ops worker、执行器、停止控制和 SSE 观察通道。

本设计不修改并行模型检测只读分支的 router、server、reader、SQL adapter 或 schema migration。该分支的 options / history / detail 可以作为过渡只读切片；`GET /run/active` 仅用数据库 `status=running` 近似 Node 进程内状态，并固定 `stopRequested=false`，不是等价接管。writer/schema 批次必须用共享 stop intent、lease、deadline 和 stale recovery 替换该 active port/query/DTO。

## 当前事实

权威 Node 来源：

- HTTP 和 SSE：`backend/src/modules/model-checks/model-checks.routes.ts`
- 目标解析和探针编排：`backend/src/modules/model-checks/model-checks.service.ts`
- 单进程活动任务：`backend/src/modules/model-checks/model-checks-active-runs.ts`
- dataset writer：`backend/src/modules/background/background-dataset-writer.ts`
- run / item 存储：`backend/src/storage/model-checks.repository.ts`
- 三张 dataset 表：`backend/src/storage/schema/dataset-schema.ts`
- Token CPU 隔离：`backend/src/modules/model-checks/model-checks-token-worker.service.ts`

截至 `origin/master=8d9a2607b`，Go 主线没有 model-check writer、executor、job、三表 migration 或运行态 owner。并行只读分支只读取 Node 已有 PostgreSQL 事实，不代表写链已迁移。

Node 当前可观察生命周期为：

1. 校验目标、模型、profile 和可信对比账户。
2. 按当前系统账户抢占一条进程内 active run，并抢占全局诊断槽。
3. 创建 `status=running`、`level=unavailable`、`score=0`、`max_score=100` 的 run。
4. 执行完整探针套件，结束后一次性写 items；符合条件时再写 observations。
5. 把 run 终结为 `completed`、`failed` 或 `canceled`，再读取完整 detail。

`/run/stream` 的浏览器断开只停止 SSE 写出，不取消检测；显式 `/run/stop` 才取消 active execution。这个语义必须保留。非流式 `/run` 当前受 25 秒 HTTP deadline 和客户端断开影响，属于 Node 两种入口的不一致，Go 不继续保留两种任务 owner。

## Go 原生任务模型

### 持久事实和任务 owner

- PostgreSQL 的 run 是业务事实源；Asynq `ops` worker 是执行 owner；HTTP 只创建任务、观察任务或发出 stop 请求。
- 任务类型固定为 `model-check:run`，queue 为 `model-check`，由 ops worker role 消费；payload `version=1`，基础设施失败最多重试 3 次。探针业务失败由 worker 写入终态并向队列返回成功，不触发整项自动重跑；基础设施重试必须从已持久化阶段续跑，避免重复消耗上游额度。
- durable payload 统一经严格 codec 编解码：producer 先 canonicalize 再 encode，consumer 在最大 `8 KiB` 边界内拒绝未知字段、重复字段、非 canonical 标识字段、尾随 JSON 和无效版本。不能依赖 Go `json.Unmarshal` 静默忽略或覆盖额外字段来证明 Redis payload 不含凭据。
- execution deadline 不冻结拍脑袋的固定分钟数。worker 根据 profile、probe plan、单探针 timeout、内部 retry delay 和安全余量按 `probe-plan-budget-v1` 推导有界总预算；实施批次用 mock clock 和真实压测固定上下限。
- payload 只带稳定 ID、目标 / 可信对比账户 config revision、模型、profile、`probeSetVersion`、可信对比选择、trace ID 和请求时间。worker 必须使用该版本对应的 probe plan；版本在当前部署不可用时安全失败，不能静默切到新版本。
- HTTP/service 必须先使用 `NormalizeRunTaskPayload` 得到 canonical payload，再将同一份值写 run fingerprint 和 Asynq payload；不得一边保存原始空白值、一边用 trim 后的幂等键。
- API Key、Authorization、Base URL、代理密码、完整请求体和响应体禁止进入 Redis task payload。worker 在执行时按 ID 和权限事实重新解析凭据。
- public run status 第一版继续使用 `running/completed/failed/canceled`，避免与现有前端和并行 reader 冲突。Asynq pending/retry/lease 是内部状态，不伪装成新的公开 status。
- HTTP 接受任务后不持有长期 goroutine。SSE 只是 durable run 的观察者；客户端断开不取消 worker context，显式 stop、执行总 deadline、服务关闭或 worker lease 失效才触发取消。

### 写入阶段和幂等

写入阶段固定为 `create_run -> checkpoint_probe_attempts -> upsert_items -> append_observations -> finish_run`：

- `create_run` 使用稳定 run ID。重试只能复用完全相同的 canonical JSON SHA-256 请求指纹，否则返回冲突。run 与待投递 outbox 行在同一 PostgreSQL 事务写入；提交后 dispatcher 以 run ID 作为 Asynq task ID 投递并幂等标记 outbox。不得使用无法原子交接的“先 insert run 再直接 enqueue”或“先 enqueue 再 insert run”。enqueue 成功但 outbox 标记前崩溃允许重复投递，依靠 task ID、request fingerprint 和后续写阶段幂等收敛。
- worker 开始探针前必须核对目标和可信对比账户 config revision；排队期间配置变化时不得用新凭据 / endpoint 执行旧请求，应安全终结并提示重新发起。
- `checkpoint_probe_attempts` 写独立内部表 `model_check_probe_attempt_checkpoints`，不复用会被 reader 当作正式报告的 `model_check_items`。每个完成的 probe attempt 在开始下一探针前写入有界、脱敏 checkpoint，唯一键为 `(run_id, probe_key, attempt_index)`；内容只含恢复所需的状态、耗时、trace、错误摘要和有界结果，不保存凭据或原始 body。表通过 `run_id` FK cascade 随 run retention 一起删除。基础设施重试从 ledger 续跑，不重复已完成探针；worker 恰在上游响应和 checkpoint 提交之间崩溃时，正在飞行的单个探针仍可能重放，系统不虚假承诺跨外部 API exactly-once。
- `upsert_items` 在完整探针结束后一次性事务写入，保持 Node “无 partial item report” 语义；数据库必须保证每个 `(run_id, item_key)` 唯一，重试更新同一脱敏结果，不产生重复项。
- `append_observations` 使用 run / probe / round / sample 派生的确定性 ID，重复写为 no-op。
- `finish_run` 只允许 `running -> completed|failed|canceled`。相同终态重放为 no-op；不同终态不能互相覆盖。完成 / 失败 CAS 还必须同时满足 claim epoch 仍属于当前 worker、lease 未过期且 `stop_requested_at IS NULL`；stop 必须原子写 cancel intent 并优先完成 `running -> canceled` CAS，保证晚到成功不能赢过已经提交的停止请求。
- 每次 writer 都在边界执行有界脱敏。Node 的深度 4、对象 32 key、数组 20 项、字符串 500 字符是当前最低兼容边界；未来 Go DTO 可以更严格，但不能保存密钥、代理密码、原始请求或原始响应。

items transaction 失败时 run 进入 `failed`，不留下对外可见的 partial item 集合。observations 是诊断派生事实；写入失败是否使整次 run 失败在实现前通过测试固定，不能默默丢失。

### 并发、停止和恢复

- “每个 actor system account 最多一条手工模型检测”按 `ActorSystemAccountID` 建跨实例 lease；不按被检测资源 owner 建 key，也不复制 Node 进程内 `Map`。每次 claim 分配单调递增的 `claim_epoch`；续租、checkpoint、items、observations 和 finish 都必须携带并校验该 epoch。旧 worker lease 过期后即使仍在运行，也不能再提交任何写阶段。
- 全局诊断容量按上游和资源预算配置，不机械复制 Node 固定 8 槽。真正的上限来自上游并发、HTTP transport、PG pool 和 ops worker 并发。
- stop 原子写共享取消意图并尝试把仍在运行的 run CAS 为 `canceled`，worker context 同时观察取消。completed / failed CAS 必须要求没有 stop intent；终态 CAS 与 claim fencing 共同保证晚到的成功或失败不能覆盖 `canceled`。
- worker crash、进程重启或 enqueue 成功后长期无 claim 时，由有界 stale-run reconciler 按 lease/deadline 终结为 `failed`，原因码使用 `worker_lost`；不能永久停留在 `running`。
- final write 失败必须进入结构化日志、指标和 Asynq retry/dead；重试先检查已持久化 items / observations 并只补终态 CAS。不能重新覆盖已有终态，也不得因 HTTP 已断开而静默丢失。

### Token 探针

Node 为避免事件循环 CPU 阻塞，使用单 child process、16 条队列和 IPC 生成最多 2048 Token 的受控 padding。Go 不复制 child process pool：使用受任务 context 管理的普通函数或有界 goroutine，并由 ops worker 并发、CPU profile 和 execution deadline 控制。tokenizer 版本仍必须写入 observation，算法变更必须版本化。

## 主动修复 Node 问题

| Node 现状 | Go 处理 | 原因 |
| --- | --- | --- |
| active run 仅保存在单进程 `Map` | 跨实例 lease + PostgreSQL run | 多副本、重启和 stop 可见性 |
| terminal update 只有 `WHERE id=?` | `WHERE id=? AND status='running'` CAS | 防止晚到结果覆盖取消或其他终态 |
| 进程崩溃可留下永久 `running` | lease/deadline + stale reconciler | 任务可恢复且历史状态可信 |
| SSE 和非 SSE 对客户端断开的取消语义不同 | 统一 durable task；断开只停止观察 | HTTP 连接不再是任务 owner |
| writer 通过 Node IPC/SQLite 单写者分流 | Go 直接使用 PostgreSQL transaction | 删除 Node/SQLite 专用复杂度 |
| Token padding 依赖 child process pool | Go 进程内有界计算 | 无事件循环阻塞问题，减少 IPC 和进程生命周期 |
| item 表缺少 run/item key 唯一写保护 | 唯一约束 + upsert | Asynq retry 不产生重复诊断项 |

## 分批实施边界

第一批只交付：

- `internal/jobs/modelcheck` 的 task payload、校验、公开状态和终态迁移规则。
- `testdata/v1/writer-lifecycle.json` golden，记录 probe version、五个写阶段、敏感字段禁入、幂等规则和 Go 偏离原因。
- 本设计和实施计划。

后续批次依次完成：

1. Goose / sqlc / store：Node 三张公开事实表加一张 Go 内部 checkpoint 表、唯一约束、CAS terminal、作用域和脱敏。
2. Asynq enqueue / handler / worker：stable run ID、retry、deadline、lease、stop 和 stale recovery。
3. executor：目标解析、协议 profile、探针、评分、observations 和 Token 计算。
4. POST / stop / active / SSE：鉴权、限流、断线重连和观察通道。
5. 真实 PostgreSQL / Redis / Asynq / mock upstream / 前端联调和生产 owner 切流。

在第 5 步完成前，Node 继续是 writer / executor / stream / stop owner；不得删除 Node 路由、worker、schema 或测试。

## 验证门禁

- 第一批：golden contract、payload validation、terminal immutability、`go test`、`go vet`、`gofmt`、`git diff --check`。
- writer 批次：真实 PostgreSQL 证明 create/items/observations/finish 原子边界、唯一约束、CAS 和跨账户作用域。
- worker 批次：真实 Redis / Asynq 证明 retry、dead、shutdown drain、lease、stop、stale recovery 和无敏感 payload。
- HTTP/SSE 批次：断开后继续、显式 stop 后 canceled、重连观察、heartbeat、complete/error 事件边界。
- 接管批次：Node writer -> Go reader 和 Go writer -> Go reader 双向 smoke，前端真实 Go listener，单 owner、回滚和 Node 删除证据。
