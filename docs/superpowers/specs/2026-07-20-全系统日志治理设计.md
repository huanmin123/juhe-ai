# 全系统日志治理设计

## 1. 背景与目标

juhe-ai 当前同时运行 Node 主服务、worker/ingest-worker、DB service、Go HTTP 后端和多个后台任务。日志、运行时索引、审计 payload、操作日志和公开接口日志各有不同保留语义，但缺少统一的事件契约、跨进程 trace 关联、阶段计时和失败现场保全标准。

本次实现并不把所有日志合并为一张表或一个文件，而是建立统一日志底座和接入规则：

- 每个请求、后台任务、跨进程调用都能按 `traceId` / `requestId` / `jobId` 追溯。
- 每个已执行的关键阶段都有结构化 `info` 事件，不依赖相邻日志时间猜测耗时。
- 不可预知失败必须完整保留可用现场；可预知失败必须保留实际参与决策的参数。
- 记录、轮转、索引、搜索、清理和失败保底都不得阻塞业务主路径。

## 2. 统一边界

### 2.1 覆盖组件

1. Node server：网关、API Key、认证、路由、分组、AI 账户、使用记录、审计、设置和管理 API。
2. Node 子角色：worker、ingest-worker、DB service、统计/维护/模型目录后台任务。
3. Go backend：HTTP middleware、管理 API、公开 API、数据库访问、后台 worker 和外部集成。
4. 日志底座：Node Pino、Go `slog`、角色日志文件 durable spool、文件轮转、保留清理、ingest-worker 游标索引、SQLite/PostgreSQL 读取和 `rg` 搜索。Redis 只保留其他业务事实队列，不承载 runtime-log 热路径。

### 2.2 前端边界

前端不在本期采集完整用户行为、输入、响应或浏览器日志。只保留现有服务端返回的 trace 关联，并在重要错误提示中显示可查询的 trace 标识。浏览器错误采集另立项目设计。

### 2.3 语义分离

- **普通运行日志**：结构化事件、阶段、错误和运行时上下文，用于快速定位。
- **原始审计**：高权限、终态入队、容量受控的原文保全，不把原文复制到普通运行日志。
- **操作日志**：业务状态改变的谁/什么/影响谁追溯，不代替请求时间线。
- **公开接口日志**：外部来源系统调用排障，保持现有权限和保留口径。

## 3. 事件契约

### 3.1 必有字段

`time` 、`level` 、`service` 、`role` 、`event` 、`traceId` 、`requestId` 、`jobId` 、`parentId`、`outcome`、`durationMs`、`stage`、`environment`、`version` 中按语义选择出现，不用空值伪造关联。

- `service` 取 `juhe-ai-node | juhe-ai-go | juhe-ai-db-service | juhe-ai-worker` 等稳定值。
- `role` 取 `server | worker | ingest-worker | db-service | go-server | go-worker` 等稳定值。
- `event` 使用小写词法和稳定枚举，防止动态函数名导致检索失控。
- `durationMs` 只表示局部操作；累计偏移使用明确的 `startedOffsetMs` / `endedOffsetMs`，禁止把累计值重复相加。

### 3.2 时间和关联

- Node 使用 `performance.now()`，Go 使用 `time.Time` 伴随的 monotonic 部分或 `time.Since` 计时；wall clock 只用于展示和跨进程对齐。
- HTTP 入口生成 `traceId` 并传递 `requestId`；跨 HTTP、Redis stream、DB service IPC 和 worker job 必须携带父 ID。
- 不同进程之间不承诺全局写盘顺序；按 sequence/offset 重建单条请求时间线。

## 4. 失败现场原则

### 4.1 不可预知失败

未被稳定业务原因码分类、返回结构破坏、不符合契约、worker/IPC 异常、数据一致性异常和未知分支都是不可预知失败。必须保留：

- Error type/name/message/stack/code 和递归 cause 链；Go 保留 `%+v` 不可用时的类型、`errors.Is/As` 结果和原始错误摘要。
- 当前 stage、已完成 stage 摘要、请求/任务/attempt ID、父链路、结果、时间和重试状态。
- 错误时的队列长度、in-flight 字节、worker PID/role、Redis/DB service 状态、配置版本和实际决策输入。
- 单字段与单事件有界；超限时保留类型、原始大小、hash 和 `truncated` 原因，不静默删除。

### 4.2 可预知失败

已有稳定 reason code 和决策分支时，必须记录该决策实际使用的参数：请求上下文、输入阈值、当前值、候选/拒绝计数、配额/容量/并发快照、后备分支、状态码和稳定原因码。不记录不参与决策的频繁原始值。

### 4.3 敏感边界

普通运行日志和失败现场不主动扩大请求/响应正文捕获范围；字段一旦进入日志，按项目权威《安全与日志策略》的原文保留、权限、保留期和容量规则处理。本设计不新增字段名匹配脱敏；超限字段保留类型、大小、hash 和 truncation 事实。

## 5. 异步与有界日志底座

### 5.1 Node

- Pino 在主线程完成字段组装和 JSON 序列化；随后通过 Node `fs` stream 异步顺序追加完整 JSONL 到当前角色文件。文件 stream 的 I/O、backpressure、轮转和清理不由请求代码同步等待，且不使用运行日志 Redis/IPC 投递。
- Node 主日志文件是 durable spool：正常 info 不采样、不按队列策略丢行、不把“写入索引失败”当作“原始日志丢失”。进程崩溃前尚未交给文件系统的极少量缓冲仍属于进程故障边界，不能以同步 fsync 延长请求生命周期。
- `ingest-worker` 从角色文件有界追尾、解析并批量索引；业务进程不执行 runtime-log JSON 解析、hash、索引 DTO、Redis/DB 写入或 IPC line 回传。

### 5.2 Go

- 在 `slog` 之上封装有界异步 `Handler`，分离 normal、failure 和 emergency failure 通道；HTTP handler 不等待文件、Redis 或 PG。
- `context.Context` 承载 trace/request/job 关联，子 goroutine 显式传递 context，不通过全局变量传播。
- shutdown 阶段可有界 drain；normal 满载只累计 drop。failure 先使用 failure 和 emergency 预留容量；极端双 failure 通道同时饱和时不阻塞业务，只累计 `failureDropped`，并在后续 drop summary 中保留最后一条有界失败现场（不能宣称每条失败永久无损）。

### 5.3 文件、Redis、PG 与读取

- Node 文件写入使用异步 stream、单文件大小轮转和现有保留天数/最大文件数，不在请求路径执行同步写入或 fsync；原始 JSONL 文件是 runtime-log 唯一 durable spool。
- runtime-log 文件导入使用 file identity + truncation generation + byte cursor + 分块窗口，`ingest-worker` 在批次提交成功后推进游标并写 SQLite/PostgreSQL；不读整文件 `split/filter`。
- runtime-log 不使用 Redis Stream、Redis/IPC line 回传或主进程解析/hash；Redis stream 的异步传输约束只适用于使用记录、审计、操作日志、公开接口等其他事实队列。
- 运行时查询、grep、轮转清理使用 ingest/维护 worker 或子进程、有界输出和资源路径白名单。

## 6. 接入顺序

### Phase 0：契约与底座

1. 定义 Node/Go 共用 event 字段、级别、outcome、failure classification、redaction metadata 和 size limit。
2. 建立 Node timing/error 事件和角色文件 durable spool、轮转日志和保底路径。
3. 建立 Go `slog` async handler、context correlation 和 shutdown drain。
4. 对两端做队列、writer、故障和敏感字段契约回归。

### Phase 1：入口与子角色

1. Node request context、HTTP finish/close、worker/DB service IPC、runtime-log file importer 接入关联。
2. Go HTTP middleware、public API、management API、worker job 传递关联。
3. 为异步任务和跨进程消息增加 parent/job correlation，不改变业务结果。

### Phase 2：网关和关键业务

1. 网关阶段：runtime/API Key、body/JSON worker、candidate/model、健康、额度、容量、并发、fetch headers、first output、body 完成、downstream finish、audit finalize。
2. 账户、路由、分组、配额、代理、外部集成和模型目录关键决策接入可预知失败参数。
3. 使用记录、审计、操作日志依既有独立保留语义入队，不把原文复制到普通运行日志。

### Phase 3：查询、清理与运维

1. 统一事件、trace 和 stage 索引维度，补齐 Node/Go 查询返回语义。
2. 记录 Go 队列长度、normal/failure drop、最后失败现场、import lag、PG 批次耗时和 event-loop/goroutine 指标；runtime-log 不再记录 Redis pending/lag。
3. 使用测试临时 SQLite 和 `192.168.1.203` 专属 PG/Redis 资源做端到端 smoke，不写共享业务表。

## 7. 非阻塞验收

- 业务 handler 在 writer 延迟、Redis 不可用、PG 不可用、worker 退出和文件轮转失败时仍然返回原有业务结果。
- Node 原始 JSONL 主日志不采样、不按索引队列丢行；Go normal/failure/emergency 通道均有界，双 failure 通道饱和时只保证累计 drop 和最后一条有界现场。
- 文件、SQLite 和 PG 读取均使用异步、游标、分块、worker 或子进程；runtime-log 不在主请求路径整文件读取、同步聚合、Redis 投递或 IPC line 回传。
- 每条失败可以仅凭 trace/job ID重建决策现场；超限字段可确认类型/大小/hash/truncation 事实，捕获边界遵循既有日志策略。
- 默认保留期沿用现有配置；本次不执行生产上线。

## 8. 交付与分支

- 设计、计划、实现和验证在独立 worktree 进行，不改动当前 `feature/20260706-go` 工作区的用户改动。
- 开发分支基于最新 `origin/master`，每个阶段里程碑前非交互 fetch/merge 最新 master，不改写历史。
- 验证和双 Agent 复核通过后合并到 `master` 并提交推送；再在干净集成 worktree 中反向 merge 到 `feature/20260706-go` 并推送。
- 生产发布与上线时间由用户另行通知，本次不领取部署锁。

## 9. 验收门禁

1. Node/Go 结构化日志可使用同一 trace 关联，且字段契约可以作为索引输入。
2. 不可预知失败保留 Error/cause/stack 和上下文；可预知失败保留决策参数。
3. 任何 writer、worker、Redis、PG 或索引故障不影响业务 HTTP 结果，所有内存队列有界；Node 文件 spool 仍按完整 JSONL 追加，Go 极端 failure 饱和的保全口径按 5.2 执行。
4. 文件写入、轮转、导入、grep 和清理不使用主请求路径的同步整文件操作。
5. SQLite 、PostgreSQL+Redis、Node 和 Go 定向回归及非阻塞性能对照通过。
6. 文档、日志、测试和提交不含密码、token、连接串或完整 payload。
