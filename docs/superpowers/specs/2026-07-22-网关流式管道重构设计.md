# 网关流式管道重构设计

> 状态：设计稿（待多 agent 独立审查收口）  
> 编号：PLAN-0154  
> 日期：2026-07-22  
> 范围：仅设计，不改业务代码；本文件是后续实现的唯一设计权威。

## 1. 背景与问题

### 1.1 现状

网关返回侧流式能力集中在：

- `backend/src/modules/gateway/response/stream.ts`（约 67KB，主循环 / 解析 / 写出 / 失败收尾耦合）
- `finalization.ts`（流式结果到服务端重试、失败事件、审计 / usage 副作用）
- `stream-pre-commit-buffer.ts`、`downstream-commit-state.ts`、`stream-finalization-retry-decision.ts`
- 协议检查器与响应语义检查（OpenAI / Anthropic / Gemini 等）

当前链路已支持双提交边界（`transportCommitted` / `semanticCommitted`）、预提交缓冲、精确客户端协议失败解释、响应语义检查、背压等待、图像 lane 超时与零可派发账号 SSE 注释心跳。这些都是产品能力，不是可随意删减的历史包袱。

### 1.2 主要痛点

1. **热路径职责过载**：单文件同时负责上游读、SSE 半帧拼装、协议解释、预提交缓冲、写出背压、检查命中、失败事件和结果组装。
2. **双写路径风险**：预提交缓冲与直接写出并存，边界条件多，后续改动易引入“缓冲未 flush / 已写出半段仍假装未提交”。
3. **协议与编排耦合**：通用透传、精确客户端语义、响应检查策略、账号副作用决策散落在同一循环分支。
4. **高并发可观测性不足**：阶段耗时、背压等待、预提交决策、协议失败原因缺少统一结构化事件面。
5. **Go 迁移摩擦**：Node 专用闭包状态机多，接口边界不清晰，不利于映射到 Go `io.Reader` / 增量解析 / 有界队列。

### 1.3 设计目标

- 在**不删除现有业务能力**的前提下，把流式返回侧重构为可测试、可扩展、高并发友好的单管道。
- 写路径唯一、提交边界清晰、背压只等待不丢弃。
- 协议适配器完整拥有本协议语义；通用客户端保持不透明透传。
- 设计必须可迁移到 Go，不发明 Node-only 难移植结构。
- 本阶段只交付设计文档与审查结论；实现另开实施计划。

## 2. 非目标

- 不实现代码、不改 schema、不改系统设置默认值、不迁移历史配置。
- 不新增客户端双路径兼容层，不为旧字段做运行时双读双写。
- 不把请求侧调度、账户探针、额度、限流重写进本管道；管道只消费已解析的 attempt 上下文。
- 不把后台探针、软阻断、半开确认逻辑搬进 SSE 写循环。
- 不要求客户端必须 `stream=true`；非流式 JSON 路径保留，但本设计重点是流式 / 伪流式返回侧。
- 不引入完整流体重写缓冲、不按状态码/错误文案给通用路径发明业务切号。

## 3. 硬约束（验收门禁）

下列约束是实现门禁。任何实现 PR 违反任一项即视为设计未满足。

| ID | 约束 | 说明 |
| --- | --- | --- |
| H1 | 单写路径 | 只有 `DownstreamWriter` 可向客户端 socket 写字节；禁止 buffer-flush 与 direct-write 两套并行写出语义 |
| H2 | 首次语义写出即提交 | 真实协议事件 / JSON 正文 / 可见模型输出一旦写出，`semanticCommitted=true`，禁止服务端透明拼接第二账号 |
| H3 | 传输提交与语义提交分离 | SSE 注释心跳可只置 `transportCommitted`；纯 transport 失败在语义未提交时可继续服务端救回 |
| H4 | EventParser 永不写下游 | 解析器只产出帧 / 半帧状态 / 诊断；写下游只在 Writer |
| H5 | 背压只等待 | `write` 遇背压必须 await drain；禁止 drop、drop-and-continue、静默截断 |
| H6 | 禁止流式整包缓冲 | 不为常规转发拼接完整响应体；仅允许解析器有界半帧窗口 |
| H7 | 禁止二次全文改写缓冲 | 不为“事后整段替换”再缓存整条流 |
| H8 | 通用路径不发明业务失败分类 | `generic_*` 不解析上游错误语义做切号；完整上游响应按不透明透传 |
| H9 | 无客户端双路径兼容 | 新契约直接替代旧实现路径，不保留旧写路径旁路 |
| H10 | Go 可移植 | 阶段、接口、状态机可用 Go 标准库与显式结构体表达；不依赖 Node EventEmitter 生命周期技巧 |
| H11 | 能力不删减 | 见 §6 能力保全矩阵；任何删除必须先有用户显式确认 |
| H12 | 副作用不在写循环阻塞 | audit / usage / 账号运行态 / 探针投递在 attempt 终态后异步有界入队，不阻塞 SSE 写出 |

## 4. 术语

| 术语 | 定义 |
| --- | --- |
| Attempt | 一次上游账号调用尝试 |
| Transport frame | 传输层活动，如 raw chunk、SSE comment、解码后的字节片 |
| Protocol frame | 协议适配器产出的完整语义单元（事件、JSON 片段摘要、usage、error、terminal） |
| Visible semantic output | 会改变 assistant 内容、工具参数或图像输出状态的协议内容 |
| transportCommitted | 已向下游写出过传输字节（含 SSE 注释心跳或 headers 已发送后的传输写出） |
| semanticCommitted | 已向下游写出真实协议/模型语义内容，之后禁止透明换号拼接 |
| Pure transport failure | 本地可验证的连接、超时、读中断、解码损坏、未形成完整上游响应的失败 |
| Protocol-owned failure | 仅由精确客户端协议适配器或显式响应检查策略认定的协议失败帧 |
| Hold window | 解析/检查在写前对**有界未提交帧**的暂存；不是第二写路径 |

## 5. 目标架构

### 5.1 管道阶段

```text
UpstreamBodySource
  -> TransportDecoder          # gzip/br/deflate 增量解码；损坏=transport failure
  -> EventAssembler            # SSE 半帧/行拼装，有界窗口
  -> ProtocolAdapter           # 协议完整拥有：帧抽取 / 透传字节映射 / 专属失败事件
  -> FramePolicyEngine         # 响应语义检查 + 客户端策略 + 写出前决策
  -> DownstreamWriter          # 唯一写路径 + 背压 await
  -> AttemptFinalizer          # 结果组装
  -> SideEffectDispatcher      # 审计/usage/账号副作用/重试信号（写后/终态）
```

请求级编排（账号选择、同账号确认预算、分组切换、零可派发等待）仍在现有路由 / finalization / failure-dispatch 层。本管道只负责**单次 attempt 的上游返回处理**，并向编排层返回结构化 `AttemptOutcome`。

### 5.2 组件职责

#### UpstreamBodySource

- 从上游 HTTP 响应读字节流。
- 暴露 cancel、EOF、read error、byte count、first byte 时间。
- 不解析协议。

#### TransportDecoder

- 按 `content-encoding` 增量解码。
- 解码失败记为 pure transport failure。
- 过滤下游不应透传的编码头（与现有 `downstream-headers` 一致）。

#### EventAssembler

- SSE：按行/事件边界拼装；半帧只留在有界内部缓冲。
- 非 SSE 流式：按 chunk 转发，不伪造事件。
- 超大单行/单事件：遵循现有上限与“parser skipped 诊断 + raw 活动保护”语义，不因半帧静默丢连接。
- **永不调用 response.write**。

#### ProtocolAdapter（关键）

每个协议档案一个适配器（至少）：

- OpenAI v1 Chat SSE / Responses SSE
- Anthropic Messages SSE
- Gemini GenerateContent SSE / Interactions SSE
- Generic opaque passthrough（`generic_*` 默认）

适配器责任：

1. 把 assembler 事件映射为 `ProtocolFrame[]` 或 opaque `RawForwardUnit`。
2. 识别 usage、terminal、protocol error、visible output、image output。
3. 构造该协议的客户端最终失败事件字节（仅在编排层要求时由 Writer 写出）。
4. **完整拥有本协议字段路径**；禁止跨协议复用字段假设。

适配器禁止：

- 写 socket
- 改账号运行态
- 决定是否切号（只产出事实帧与建议标签，决策在 Policy / 编排层）

#### FramePolicyEngine

输入：协议帧 + 客户端策略 + 响应检查策略 + 当前 commit 状态。

输出唯一决策枚举（示意）：

```text
FORWARD                 # 立即经 Writer 写出
HOLD_FOR_INSPECTION     # 有界 hold，等待完整可判定单元
DROP_EVENT              # 仅允许策略明确且安全的独立事件删除
REWRITE_FAILURE_EVENT   # 精确客户端最终失败改写（仍经 Writer 一次写出）
REQUEST_SERVER_RETRY    # 语义未提交；关闭本 attempt，返回编排层
FAIL_TERMINAL           # 结束本响应（写失败事件或断流由客户端能力决定）
OBSERVE_ONLY            # 记录观测，不改变转发
```

#### DownstreamWriter

- 唯一写入口：`write(unit, commitKind)`。
- `commitKind`:
  - `transport`：注释心跳等 → 只 mark transportCommitted
  - `semantic`：协议/模型语义 → mark semanticCommitted
  - `header`：响应头 / status 发送
- 背压：`write` 返回 pending 时 await drain；超时/断开转为 client lifecycle 或 write failure。
- headers 只发送一次；语义提交后禁止切换到另一套 HTTP 状态重写。

#### AttemptFinalizer / SideEffectDispatcher

- 组装 `StreamPipeResult` 等价结构（兼容现有 finalization 输入面，可渐进改名）。
- 副作用：审计入队、usage 入队、IP 回避、Codex turn 记忆、后台核实投递等，全部在写循环外、终态后触发。

### 5.3 核心状态机

```text
OPEN
  ├─(write transport unit)→ TRANSPORT_OPEN
  ├─(write semantic unit)→ SEMANTIC_COMMITTED
  ├─(pure transport fail, no semantic)→ RETRYABLE_CLOSED
  ├─(protocol-owned fail + policy allows, no semantic)→ RETRYABLE_CLOSED
  ├─(client abort)→ CLIENT_ABORTED
  └─(success terminal + drain)→ SUCCESS_CLOSED

TRANSPORT_OPEN
  ├─(write semantic)→ SEMANTIC_COMMITTED
  ├─(pure transport / allowed protocol fail)→ RETRYABLE_CLOSED   # 仍无语义
  └─(cannot return non-SSE JSON into SSE)→ FAIL_TERMINAL_OR_RETRY_POLICY

SEMANTIC_COMMITTED
  ├─(continue forward)→ SEMANTIC_COMMITTED
  ├─(upstream fail / missing terminal)→ COMMITTED_FAILURE_CLOSED  # 不透明换号
  └─(success)→ SUCCESS_CLOSED
```

不变式：

1. `semanticCommitted ⇒ transportCommitted`
2. `RETRYABLE_CLOSED ⇒ !semanticCommitted`
3. 任意时刻至多一个 Writer owner
4. hold 窗口字节数有硬上限；超限必须升级为 FORWARD 或 FAIL，禁止无限积压

## 7. 失败与重试模型（与“仅 transport”要求的收口）

### 7.1 用户要求与产品能力的对齐

用户要求：**预提交默认只允许纯 transport 失败重试，业务内容失败不由网关乱分类。**  
产品已有能力：**精确客户端协议失败**与**显式响应检查策略**可在语义未提交时触发服务端重试。

收口结论（必须写入实现与测试）：

1. **Gateway core（通用默认）**  
   - 只把 pure transport failure 标为 `server_retry_candidate`。  
   - 不根据 HTTP 状态正文、错误码字符串、广告文本等自动切号。  
   - 完整上游响应（含非 2xx 与 200+error SSE）对 `generic_*` 不透明转发。

2. **Protocol-owned path（精确客户端）**  
   - 仅当客户端画像允许解释时，Adapter 可产出 `ProtocolFailure` 帧。  
   - Policy 在 `!semanticCommitted` 时可将该帧映射为 `REQUEST_SERVER_RETRY`。  
   - 这不是“网关猜业务”，而是“适配器执行已产品化的协议契约”。  
   - 能力保留：Codex / Claude Code / Gemini CLI 预提交救回与最终协议失败事件。

3. **Configured inspection path**  
   - 管理端/账户显式响应检查策略与白名单系统默认（如 compaction 契约、Gemini CLI 可重试错误）可在写前 `REQUEST_SERVER_RETRY`。  
   - 无显式策略的通用请求不进入该路径。

4. **已语义提交**  
   - 任何失败都不得透明换号拼接。  
   - 精确客户端可写协议失败事件后结束；通用客户端断流或按既有策略处理。

5. **禁止项**  
   - 不得恢复旧“错误码特征表驱动切号”为通用默认。  
   - 不得在 Adapter 内直接改账号持久状态。

### 7.2 AttemptOutcome（管道 → 编排）

```text
AttemptOutcome {
  status: success | retryable_failure | terminal_failure | client_aborted
  retryClass?: pure_transport | protocol_owned | inspection_policy
  errorCode?: string
  message?: string
  commit: { transportCommitted, semanticCommitted, downstreamBytesWritten }
  usage?: ParsedUsage
  firstTokenMs?: number
  inspection?: Decision
  uncommittedHoldBytes?: number   # 调试；成功路径应为 0
  bodyOmission?: ...
  diagnostics: { ...有界字段 }
}
```

编排层据此决定：同账号确认、切号、写最终客户端错误、投递后台核实。管道不执行切号。

## 8. 预提交 Hold 窗口（取代双写缓冲）

### 8.1 问题

现行 `stream-pre-commit-buffer` 在“缓冲整段 chunk 后 flush”和“直接写出”之间形成双路径，违反 H1。

### 8.2 新模型

- 默认流式：**判定后立即 Writer.forward**，无第二缓冲。  
- 仅当 Policy 需要“完整可判定单元”（例如 compaction 计数窗口、检查策略要求的有界事件窗）时进入 `HOLD_FOR_INSPECTION`。  
- Hold 存放的是 **ProtocolFrame / RawForwardUnit 队列**，不是第二套 socket 写实现。  
- 决策结束后，单元仍只通过 Writer 顺序写出一次，或整体丢弃并 `REQUEST_SERVER_RETRY`（仅 `!semanticCommitted`）。  
- 硬上限建议与现行同级：默认 256KiB 有界；超限策略：
  1. 若已能判定失败且未语义提交 → retry/fail  
  2. 否则强制 FORWARD 并标记诊断 `hold_window_overflow_force_forward`，同时视为可能 semantic commit  
- 图像大事件：不 hold 整图；检查只基于帧类型/有界摘要；审计省略保持。

### 8.3 与 headers 的关系

- 响应头可在首个 transport/semantic 写出前准备。  
- 一旦 headers 已发送且内容类型为 SSE，后续只能写 SSE 单元；上游改 JSON 不得拼进 SSE（继承 PLAN-0134）。

## 9. 背压、并发与资源边界

### 9.1 单请求内

- 读上游与写下游可在同一异步状态机协作；写 pending 时停止继续向下游推进，并可暂停上游读（cooperative pause）以防无界内存。  
- 禁止用无界数组堆积已读未写 chunk。  
- 上游慢 / 下游慢都只体现在 await 与超时，不丢字节。

### 9.2 多请求间

- 不引入全进程无界流式任务队列。  
- 现有入口并发、账号并发槽、lane 超时、零可派发等待预算继续约束。  
- Writer 指标：`backpressure_wait_ms`、`backpressure_wait_count`、`downstream_write_errors`。

### 9.3 取消

- 客户端 abort → 取消上游、释放并发槽、`client_aborted`，不写账号失败状态。  
- 编排层 cancel attempt → 解析器停止、Writer 不再接受新写。

## 10. 可观测性

对齐 PLAN-0146 事件 envelope，流式管道至少输出：

| 阶段 event | 关键字段 |
| --- | --- |
| `gateway_stream_attempt_started` | accountId, lane, protocol, clientProfile |
| `gateway_stream_transport_decoded` | encoding, error? |
| `gateway_stream_frame_assembled` | eventType?, size, skipped? |
| `gateway_stream_policy_decision` | decision, policyId?, retryClass? |
| `gateway_stream_write` | commitKind, bytes, backpressureWaitMs |
| `gateway_stream_commit_state` | transport, semantic, downstreamBytes |
| `gateway_stream_attempt_finished` | status, retryClass, firstTokenMs, usagePresent |

成功热路径默认 debug；失败与决策保留 info/warn。禁止在热路径同步写库。

## 11. Go 迁移映射

| Node 概念 | Go 映射 |
| --- | --- |
| UpstreamBodySource | `io.ReadCloser` + context cancel |
| TransportDecoder | streaming decompressor |
| EventAssembler | 有界 `bufio`/手写 SSE scanner |
| ProtocolAdapter | interface `Adapt(frame) ([]Frame, error)` |
| FramePolicyEngine | pure function + config snapshot |
| DownstreamWriter | `http.ResponseWriter` + `http.Flusher` + 背压/断开检测 |
| AttemptOutcome | 显式 struct，供调度层消费 |

原则：

- 解析与策略尽量纯函数，便于单测。  
- 不依赖 Node domain 特有 API。  
- SSE 不用通用黑盒库掩盖协议差异（与迁移文档一致）。

## 15. 测试与验收矩阵（实现时必须落地）

### 15.1 正确性

1. Generic SSE 原样转发失败事件，不切号。  
2. 精确客户端语义未提交协议失败 → 服务端重试/切号。  
3. 语义已提交后失败 → 不拼接，协议事件或断流。  
4. 仅 SSE 注释心跳后 transport 失败 → 仍可救回。  
5. 响应检查命中写前 retry / drop_event / observe。  
6. Codex compaction 契约失败写前换号。  
7. Anthropic terminal 后主动结束，不空等上游 EOF。  
8. 大事件超过解析上限：诊断 + 不误杀活跃流。  
9. 图像流审计省略，不写图片字节进日志。  
10. 压缩体损坏：transport failure，未提交可重试。  
11. 客户端 abort：client_aborted，无账号失败状态。  
12. 非流式 JSON 路径不被流式重构破坏（共享帧模型兼容）。

### 15.2 背压与并发

1. 下游暂停读取时上游读协作暂停，内存有界。  
2. 背压等待可观测，无 drop。  
3. 多并发 attempt 互不共享 Writer 状态。  
4. cancel 无泄漏（Node 句柄 / Go goroutine 对测在迁移阶段）。

### 15.3 门禁命令（实现阶段）

- 现有 gateway stream / retry / inspection / timeout profile 回归  
- `pnpm typecheck` / 相关 build  
- 按 PLAN-0146 方式做失败注入与慢客户端场景  

## 16. 风险与缓解

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| 误删精确客户端预提交救回 | 用户可见失败增多 | 能力矩阵 + 专项回归锁定 |
| Hold 窗口变成隐形双缓冲 | 内存与语义混乱 | H1/H6 门禁；overflow 策略固定 |
| 策略引擎过度中心化 | 协议细节泄漏 | Adapter 拥有字段；Policy 只看统一帧 |
| 一次大改难回滚 | 发布风险 | P0–P5 阶段切换；每阶段可回退 |
| 与 Go 并行开发分叉 | 双实现漂移 | 先稳定 AttemptOutcome 契约再迁 |

## 17. 明确不采纳的方案

1. 继续扩写单文件 `stream.ts` 状态机。  
2. 通用路径恢复错误码特征切号表。  
3. 完整响应体重写缓冲以支持已提交后换号。  
4. 背压时丢事件保吞吐。  
5. 为旧预提交缓冲保留长期双路径兼容。  
6. 在解析器内直接 `res.write`。  
7. 把账户持久状态机塞进 SSE 循环。
