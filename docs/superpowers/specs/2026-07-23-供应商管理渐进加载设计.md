# 供应商管理渐进加载设计

## 1. 背景与现状

供应商管理和个人模型目录共用 `ProvidersView`。当前首屏存在三类看似轻量、实际仍读取完整供应商定义的问题：

- 管理端 `GET /providers` 通过 `listProvidersForRequestAsync()` 返回完整 `ProviderDefinition[]`。仓储先读取 `providers.default_supported_models_json`，再批量读取全部协议档案、能力、账户类型和 endpoint family，最后补个人/系统默认检查模型。
- `GET /providers/options` 的 HTTP 响应已经只有 `id/code/name/enabled`，但实现仍先调用 `listProvidersAsync()` 组装完整 definitions，再在内存中过滤和映射；当前只是“响应轻”，不是“SQL 轻”。
- 个人模型目录首屏调用完整 `GET /providers/definitions`；点击某个供应商的模型目录后，页面又先按 scope 重拉整批 definitions，随后才请求 `/providers/:code/models`，造成无关供应商协议档案重复读取和串行等待。

此外，供应商模块中若干只需要判断“某个 code 是否存在且启用”的路径仍使用 `listProvidersAsync().find(...)`，一次点查触发整批协议档案组装。

本设计承接 [全站页面 API 按需加载审计报告](../../reports/全站页面API按需加载审计报告-2026-07-20.md) 的剩余 P1。它只定义 Node/Vue 的新契约与迁移边界；由于 `GET /providers` 将从完整 definition 改为 `ProviderListItem`，必须在用户确认后才能实施。

## 2. 目标

- 管理供应商首屏保留当前真实展示的账户类型、接口能力、Base URL、scoped 默认检查模型和默认支持模型，但只读取 provider base row 与每个供应商被选中的默认 protocol profile 摘要，不组装全部协议档案及 endpoint family 深对象。
- 纯筛选/选择的 `/providers/options` 使用独立窄 SQL，不再借道完整 definition loader。
- 保留 `/providers/definitions` 的完整契约，供确实依赖协议档案、账户类型和能力定义的创建/编辑表单使用。
- 新增单供应商 detail；模型目录只在点击后按 code 读取该供应商完整 definition 与模型目录。
- 只需校验启用 code 的 Node 路径使用点查/启用 code 列表，不再加载完整 definitions。
- SQLite 主线程、SQLite read worker 与 PostgreSQL 保持字段、排序、权限和错误语义一致。
- 前端所有 list/detail/models 请求具备 scope、身份、请求代次和关闭失效保护，迟到响应不得污染当前弹窗或页面。

## 3. 范围与非目标

本批只修改 Node 后端、Vue 前端、专项测试和权威文档；不修改 `backend-go/`，不提交、不推送、不部署、不触碰生产。

本批不做：

- 不修改 provider、protocol profile、模型目录或默认检查模型的数据库 schema。
- 不修改供应商驱动、协议桥接、账户凭据校验、网关调度或计费语义。
- 不新增供应商创建、启停、编辑管理接口；现有内置/种子供应商生命周期保持不变。
- 不缩窄 `/providers/definitions`，不要求依赖完整协议定义的账户表单改用轻 options。
- 不改变 `/providers/:code/models`、模型能力、模型写入和默认检查模型写入的响应 DTO。
- 不把所有 `listProvidersAsync()` 调用机械替换为 code lookup；确实需要协议档案的账户、导入、分组和运行时路径继续使用完整 loader。

## 4. HTTP 与 DTO 分层

### 4.1 管理列表：`GET /providers`

该路由继续要求 admin，并返回 `ProviderListItem[]`：

```ts
interface ProviderListItem {
  id: string
  code: string
  name: string
  parentCode?: string
  description?: string
  enabled: boolean
  accountTypes: AccountType[]
  capabilities: string[]
  baseUrl: string
  defaultHealthCheckModel: string
  defaultSupportedModels: string[]
}
```

字段白名单与当前管理表格真实可见列一致：base 字段来自 `providers`，`accountTypes/capabilities/baseUrl` 来自按现有优先级选出的默认 protocol profile，`defaultHealthCheckModel` 保持个人偏好、系统默认和 profile 默认值的现有覆盖顺序，`defaultSupportedModels` 继续解析 `providers.default_supported_models_json`。

明确不返回：

- `defaultProtocolProfileId/protocolCode/protocolVersion`；
- `systemDefaultHealthCheckModel`；
- 全部 `protocolProfiles`、单 profile description/default model 等未展示字段及 endpoint families。

排序保持 `name ASC, code ASC`，上限保持现有内置供应商边界。合法 `systemAccountId` scope 只影响每项 `defaultHealthCheckModel` 的个人偏好覆盖，其余 list 字段不随目标账户变化；目标 scope 必须继续由 admin access context 校验，不能按任意 query 读取其他用户偏好。

管理列表桌面与移动端保持现有账户类型、接口能力、Base URL、默认检查模型、默认支持模型、状态、说明和“模型目录”操作，不以渐进加载为由删除真实首屏信息。轻量化边界是“只返回这些列所需的默认 profile 摘要”，而不是缩减产品信息架构。

### 4.2 轻选项：`GET /providers/options`

现有响应形状保持不变：

```ts
interface ProviderOption {
  id: string       // 与 code 相同
  code: string
  name: string
  enabled: true
}
```

契约规则：

- 只返回启用供应商；稳定按 `name ASC, code ASC` 排序。
- SQL 直接读取 `code/name/enabled`，`id` 在 mapper 中由 `code` 生成或 SQL alias 生成。
- 不读取 `default_supported_models_json`、协议档案、能力、endpoint family、个人/系统默认检查模型。
- 不增加 `includeDisabled`、definitions 或 purpose 混合开关；需要完整定义的调用方显式使用 `/providers/definitions`。
- 个人模型目录首屏可直接使用该接口，只展示名称和操作；不再为了页面卡片读取完整 definitions。

### 4.3 完整定义：`GET /providers/definitions`

该接口保持完整 `ProviderDefinition[]` 与当前启用供应商过滤语义，继续服务于真正需要以下内容的表单和协议决策：

- 默认/全部 protocol profiles；
- account types、capabilities、endpoint families；
- base URL、默认检查模型与默认支持模型；
- system account scope 下的个人/系统默认检查模型覆盖。

本批不改变字段、排序、权限、scope 或现有调用方。测试必须证明 `/providers/options` 的 SQL 轻量化没有通过改窄 `/providers/definitions` 偷换完成标准。

### 4.4 单供应商详情：`GET /providers/:code`

新增按 code 返回一个完整 `ProviderDefinition` 的 detail：

- admin 可以读取启用或停用供应商，并可按现有 access scope 读取目标系统账户的默认检查模型偏好；
- 非 admin 只能读取启用供应商，停用或不存在统一返回 404，避免泄露不可用供应商存在性；
- 非 admin 不能通过 `systemAccountId` 越权读取其他用户偏好，scope 必须由现有 request access context 收口；
- 参数 trim 后必须满足现有 provider code 长度/字符边界，非法值返回 400；不存在返回 404；
- 返回字段与 `/providers/definitions` 的单项完全一致，不引入第二套 full definition。

静态路由 `/options`、`/definitions`、`/models/options` 必须先于 `/:code` 注册。`/:code/models`、`/:code/default-health-check-model` 等多段路由不应被 detail 捕获，并需有路由顺序回归。

### 4.5 模型目录点击时序

管理列表行只持有 `ProviderListItem`，个人模型页行只持有 `ProviderOption`。点击“模型目录/查看模型”后：

1. 立即打开弹窗并创建新的 modal generation；
2. 对当前 `providerCode + viewer + role + targetSystemAccountId` 并行请求 `GET /providers/:code` 与 `GET /providers/:code/models`；
3. detail 用于标题、协议/能力、默认检查模型、创建模型表单和默认配置；models 用于目录表格；
4. 只有 generation、code 和 scope 都仍匹配时才能写入；A→B、切换目标用户、关闭弹窗、退出登录或页面卸载均使旧 intent 失效；
5. 切换目标系统账户时重新并行加载 scoped detail/models，不重拉整批 list/definitions；
6. 单侧失败不允许沿用其他供应商或其他 scope 的旧 detail。可保留同一 code/scope 的上次成功数据并标记 refreshing，但失败态必须可见且可重试。

首屏请求矩阵固定为：

- 管理页：一次 `/providers`，零次 definitions/detail/models；
- 个人模型页：一次 `/providers/options`，零次 definitions/detail/models；
- 点击某一供应商：一次该 code 的 detail 与一次 models，可并行；不得重拉整批 `/providers` 或 `/providers/definitions`。

## 5. Node 仓储与 SQL 投影

### 5.1 独立读取原语

新增或等价实现以下窄读取，命名可按仓储现有风格调整，但职责不能合并回完整 loader：

- `listProviderListItemsAsync(systemAccountId?)`：管理可见列列表，包含默认 profile 摘要与 scoped 默认检查模型，但不包含完整 profiles；
- `listProviderOptionsAsync()`：启用供应商轻选项；
- `findProviderDefinitionAsync(code, systemAccountId?)`：单 code 完整 detail；
- `findEnabledProviderCodeAsync(code)`：只判断并返回启用 code；
- `listEnabledProviderCodesAsync()`：全供应商模型 options 等确实需要启用 code 集合时使用。

`listProvidersAsync()` 保留为完整 definition batch loader，供 `/providers/definitions` 和确实依赖协议档案的业务使用。

### 5.2 精确 SQL

管理列表第一步读取 provider base rows：

```sql
SELECT id, code, name, parent_code, description, enabled, default_supported_models_json
FROM providers
ORDER BY name ASC, code ASC
LIMIT ?
```

第二步只对这些 provider codes 批量读取按现有 `preferredDefaultProtocolProfile()` 规则选中的一条 profile。实现使用 `ROW_NUMBER() OVER (PARTITION BY provider_code ORDER BY ...)` 或严格等价的数据库侧排名，先按 enabled、Gemini native / GLM Coding OpenAI 特例、`updated_at DESC, id ASC` 排序，再只返回 `rank = 1`。投影只允许包含 profile 选择所需标识以及真实列表字段：

```sql
WITH ranked_profiles AS (
  SELECT id, provider_code, enabled, account_types_json, capabilities_json,
         base_url, default_health_check_model,
         ROW_NUMBER() OVER (
           PARTITION BY provider_code
           ORDER BY enabled DESC, preferred_profile_rank ASC, updated_at DESC, id ASC
         ) AS profile_rank
  FROM provider_protocol_profiles
  WHERE provider_code IN (...)
)
SELECT id, provider_code, enabled, account_types_json, capabilities_json,
       base_url, default_health_check_model
FROM ranked_profiles
WHERE profile_rank = 1
```

其中 `preferred_profile_rank` 是说明性占位，实际 SQL 必须用明确 `CASE` 表达现有 Gemini native 与 GLM Coding OpenAI profile ID 特例，不能依赖不存在的数据库列。最终每个 provider 最多映射一条选中 profile。随后以 provider codes 批量读取个人默认检查模型偏好和系统默认检查模型，保持 `personal -> system -> selected profile` 覆盖顺序。查询总数固定，不随供应商数量增长。

轻 options 只允许：

```sql
SELECT code, name, enabled
FROM providers
WHERE enabled = 1
ORDER BY name ASC, code ASC
LIMIT ?
```

启用 code 点查只允许：

```sql
SELECT code
FROM providers
WHERE code = ? AND enabled = 1
LIMIT 1
```

PostgreSQL 使用现有 schema qualification、placeholder dialect 和整数 enabled 语义，不把当前 INTEGER 字段误写为 boolean。list items 允许读取 `default_supported_models_json`、选中 profile 的必要数组/Base URL 和 scoped 默认检查模型表；它与 options/enabled lookup 的投影边界不同。三类读取共同禁止：

- `SELECT *`；
- 为 list item 返回或组装全部 `protocolProfiles`；
- profile families/endpoint families JOIN；
- 读取未选中 profile 的 description、protocol 深对象或其他未展示字段；
- 先调用 `listProvidersAsync()` 后在 JS 过滤/映射。

单 detail 先按 code 读取一条 provider base row，再只为该 code 读取 protocol profiles 与 families，并只查询该 code 的个人/系统默认检查模型。不能读取全部 providers 后 `.find()`，也不能为一个 detail 组装其他供应商协议档案。

### 5.3 启用 code lookup 的使用边界

在供应商模块内，下列只需“存在且启用”的校验改用 `findEnabledProviderCodeAsync()`：

- `/providers/models/options` 带 `providerCode` 的过滤校验；
- 单模型 capabilities 的供应商可用性校验；
- provider model options service 构造启用供应商 code 集合时改用 `listEnabledProviderCodesAsync()`。

只需确认“存在，允许管理停用供应商”的模型维护和默认检查模型写路径使用窄 identity/base-row lookup，不得误用 enabled lookup 改变现有行为。账户创建、导入、分组校验等需要 protocol profiles/account types/capabilities 的路径仍使用完整 definition；本批不以性能名义削弱校验。

### 5.4 SQLite worker 与 PostgreSQL

- SQLite 主线程为 list items、options、single detail、enabled code lookup 提供同步只读实现。
- read worker 增加对应有界 operation；list items 在一个 worker operation 内完成 base、选中 profile、个人偏好和系统默认的固定批量查询，禁止逐 provider/profile RPC。detail 可以在一个 worker operation 内顺序完成单 provider 的固定数量查询。
- PostgreSQL 实现逐字段等价；detail 的 profile、family、偏好读取可在 base row确认存在后并行，但任一必需查询失败时整体失败，不能返回缺字段的伪完整 definition。
- 查询次数必须与供应商数量、协议档案数量无关；list/options/code lookup 不得触发 N+1。

## 6. 缓存与失效

### 6.1 服务端

- `/providers`、`/providers/options`、`/providers/definitions`、`/providers/:code` 继续归属 `providers.catalog` page-data domain，按 route、viewer scope、role、target account 和规范化 query 分 key。
- list/options 虽然当前内容与个人 scope 无关，仍保留权限安全的 scope key，不为减少 key 数而跨身份共享可变引用。
- single detail key 必须包含 provider code 和目标系统账户；否则个人默认检查模型会串 scope。
- 内部 `findEnabledProviderCodeAsync()` 不增加独立长 TTL 内存缓存；点查足够轻，避免供应商启停/种子同步后出现第二套失效协议。
- 现有默认检查模型写入、模型目录写入和 provider catalog 变更继续发布 `providers.catalog` reset。广域失效即使会同时清除不受模型写入影响的 list/options，也优先保持单一正确失效边界。

### 6.2 前端

- list、options、definitions、detail、models 使用不同 route key；ProviderListItem 与 ProviderDefinition 不能写入同一泛型缓存槽。
- DTO 迁移时提升 list/options 资源 cache version，key 包含 viewer id、role、auth revision、target system account 和 route。
- `force` 刷新只失效当前 route/scope；收到 `providers.catalog` domain revision 变化时，相关 route 的 stale-while-revalidate 按现有 page-data 机制确认。
- 缓存命中也必须推进 modal/list generation，使更早网络响应失效；不得因复用 in-flight Promise 复活 A→B→A 的旧 intent。
- 登出、切换账号或角色变化后不能读取上一身份的 list/detail/default model。

## 7. 权限、错误与兼容边界

- `/providers` 保持 admin-only；普通用户 403，匿名沿用系统 API 认证错误。
- `/providers/options` 与 `/providers/definitions` 保持现有认证和 access scope，不因本批扩大匿名访问。
- detail 对 admin/非 admin 的停用供应商规则按 4.4 执行；目标系统账户权限由统一 access context 校验，不能依赖前端隐藏。
- `/providers/options` HTTP DTO 不变，属于兼容的查询实现优化。
- `/providers/definitions`、模型目录、capabilities 和模型写接口 DTO 不变。
- `/providers` 从 `ProviderDefinition[]` 改为 `ProviderListItem[]` 是明确的管理接口破坏性收窄；仅在用户确认后同步 Node、Vue、契约文档与回归。
- 新 detail 是新增接口。旧调用方不能被静默改成 detail 后丢失批量 definitions 需求。
- provider code 不视为 secret，但停用供应商对非 admin 仍按不可见处理；错误不得输出数据库、scope 或真实用户标识。

## 8. 测试与验收

### 8.1 Node HTTP 与查询门禁

- `/providers`：admin 成功、普通用户 403、精确 `ProviderListItem` 白名单、包含停用项、稳定排序；保留当前可见 `accountTypes/capabilities/baseUrl/defaultHealthCheckModel/defaultSupportedModels`，但无完整 profiles、families 或其他 definition 深字段。
- `/providers/options`：只返回启用项和四字段，`id === code`，稳定排序；源码/SQL 门禁证明未调用完整 loader。
- `/providers/definitions`：仍返回完整 profile、capability、account type、family、default models 与 scoped default health model。
- `/:code`：admin 启用/停用、普通用户启用、普通用户停用 404、不存在 404、非法 code 400、伪造 scope 不越权。
- 路由顺序：`options/definitions/models/options` 不被 `/:code` 捕获，现有 `/:code/models`、capabilities、默认模型与模型写路由不回归。
- Query guard：list 无 `SELECT *`、无 profile family、无完整 profile mapper，只读取每个 provider 的选中 profile及 scoped 默认模型；options/enabled lookup 无 profile/default-model 表；三者均无 `listProvidersAsync().find/filter/map`。detail 只读取目标 code。
- 验证仅需 enabled code 的模型 options/capabilities 不再构建完整 definitions，同时允许管理停用供应商的写路径语义不变。

### 8.2 SQLite、worker 与 PostgreSQL

- SQLite 主线程和 read worker 对 list/options/detail/enabled code lookup 逐字段一致。
- worker 调用次数固定，list 只批量读取选中 profile 且不产生逐 provider RPC，options 不产生任何 profile 读取，single detail 不读取其他 provider。
- 真实 PostgreSQL smoke 在事务/隔离 fixture 中创建启用与停用供应商、多个协议档案和大能力/default model JSON，证明 list 只返回被选中 profile 的可见摘要与默认支持模型，options 不读取深字段，而 detail/definitions 保持完整；结束时不输出敏感数据且不得以 SKIP 伪装成功。
- PostgreSQL INTEGER enabled predicate、排序、limit、404 与 SQLite 等价。
- 现有 provider repository driver、模型 options、模型能力、默认检查模型和 page-data change 回归继续通过。

### 8.3 前端

- 管理首屏：一次 list，零次 options/definitions/detail/models；现有表格列逐项保留，列表不读取完整 `protocolProfiles` 或 endpoint families。
- 个人模型页首屏：一次 options，零次 definitions/detail/models。
- 点击模型目录：detail 与 models 各一次并行发出，不重拉整批 providers/definitions。
- A→B、A→B→A、目标用户切换、快速关闭、刷新、登出、detail 失败、models 失败、确认缓存更新等竞态均不能覆盖当前状态或永久 loading。
- detail 成功后完整模型创建/编辑能力、默认检查模型、协议类别和模型目录展示不回归；停用供应商只在管理列表可见。
- 桌面/移动列表使用同一轻 DTO，不以空数组或空字符串伪装尚未加载的 capabilities/default models。

### 8.4 门禁与复核

- Node/前端专项回归、后端 typecheck、可运行范围内的前端 typecheck/build、`git diff --check`。
- 浏览器网络面板验证首屏和点击请求矩阵；Browser/Playwright 不可用时记录环境限制，不以源码检查代替行为证据。
- 至少两名只读 Agent 独立复核并交叉质疑 SQL 投影、权限、缓存失效、竞态、PG/worker 和兼容边界；高严重度问题全部闭合。

## 9. 完成标准

- 管理与个人模型页面首屏均不读取完整 ProviderDefinition。
- `/providers/options` 同时满足 HTTP 轻和 SQL 轻，不再通过完整 loader 裁剪。
