## 1. 背景与目标

当前 AI 问答已经具备会话、流式文本、Responses 工具事件、图片输入和富文本输出，但消息投影与上游事件不是同一条有序时间线，直接造成以下问题：

1. 用户发送后，前端等待服务端 `message.started` 才显示用户消息，缺少即时反馈。
2. `gpt-image-2` 只声明 Images 协议，聊天发送却只选择 Chat Completions 或 Responses，直接选图像模型会发生协议能力不匹配。
3. 普通 GPT 模型未声明 `image_generation` 工具，Responses 解析器也不识别 `image_generation_call`，因此自然语言生图同样不可用。
4. 正文、思考和工具分别累积并按固定组件顺序渲染，丢失真实的事件先后关系。
5. AI 消息尚未结束时已经显示时间和复制操作，过程项也没有“执行时展开、完成后折叠”的生命周期交互。
6. 代码高亮只注册少量语言，常见语言退化成普通转义文本。
7. 系统提示偏好没有完整覆盖可靠性、关键信息缺失、Mermaid、LaTeX、生图和 SVG 原型输出。

本设计以一条有序助手时间线统一正文、思考、工具和图片输出，并让直接图像模型与 Responses 托管生图最终落到同一持久化资产契约。

## 2. 范围

### 2.1 本次包含

- 用户消息发送后的本地即时投影与服务端权威消息替换。
- 助手消息有序内容块和对应站内 SSE 增量事件。
- 思考、联网搜索、其他工具与正文按真实首次出现顺序展示。
- 活跃过程自动展开、单项完成自动折叠、终态操作栏门禁。
- 直接选择 Images 协议模型生成图片。
- 普通 Responses 模型按模型目录能力声明并调用 `image_generation`。
- 生成图片作为私有聊天资产持久化、展示、下载和后续输入引用。
- 常见编程语言代码高亮。
- `chat-system-v2` 可靠性与输出偏好。
- Mermaid、LaTeX 与 fenced `svg` 原样隔离预览。
- 后端、前端、存储、Mock、真实账户和浏览器回归。

### 2.2 本次不包含

- 自建文生图模型、图片编辑器、蒙版编辑或多轮局部重绘 UI。
- Responses partial image 像素级预览；界面只展示“正在生成图片”过程，完成后一次显示最终图片。
- 任意历史消息分支、跨会话资产共享或永久图片库。
- 站内 MCP、Skill、Function Tool 执行器。
- Go 后端同步实现、生产部署或历史 schema 运行时兼容分支。

## 3. 核心决策

### 3.1 统一有序内容块

助手消息的 `content_blocks_json` 是渲染顺序的权威来源，块按 `order` 严格升序保存：

```ts
type AssistantContentBlock =
  | { type: 'output_text'; blockId: string; order: number; text: string }
  | { type: 'reasoning'; blockId: string; order: number; text: string; status: ProcessStatus }
  | { type: 'tool_call'; blockId: string; order: number; callId: string; toolType: string; status: ToolStatus; item?: JsonObject }
  | { type: 'output_image'; blockId: string; order: number; assetId: string; status: ProcessStatus; revisedPrompt?: string }
```

```ts
type ProcessStatus = 'started' | 'completed' | 'failed' | 'canceled'
type ToolStatus = 'started' | 'updated' | 'completed' | 'failed' | 'canceled'
```

- `order` 在服务端首次观察到某一内容单元时单调递增分配，后续 delta 只能更新原块，不能改变位置。
- 连续文本 delta 合并到当前 `output_text`；如果中间出现思考、工具或图片，再出现的文本必须创建新的 `output_text` 块。
- `blockId` 是站内消息块稳定标识；同一上游 `callId` 的 started、updated、completed、failed 更新原 `tool_call`，保留首次出现位置。
- 思考流按连续片段合并；被其他类型打断后再次出现时创建新的 `reasoning` 块。
- `contentText` 继续保存最终可复制正文和上下文文本，但不再决定助手渲染位置。
- 消息 failed/canceled 时，所有仍为 started/updated 的 reasoning、tool_call 和 output_image 块按同一原因终态化为 failed/canceled；已 completed 的块保持完成事实。
- 不保留旧结构的运行时双读双写；schema、类型、Mock 和当前读写逻辑一次调整到新契约。

### 3.2 站内流事件

站内 SSE 保留消息终态事件，并增加块级事件：

```text
message.started
content_block.started
content_block.delta
content_block.updated
content_block.completed
message.snapshot
message.completed | message.failed | message.canceled
```

- `content_block.started`：`{ messageId, block, eventVersion }`，其中 `block` 已包含 `blockId/order/type` 和对应初始字段。
- `content_block.delta`：`{ messageId, blockId, delta, eventVersion }`，只允许追加到 output_text/reasoning。
- `content_block.updated`：`{ messageId, blockId, patch, eventVersion }`，`patch` 是该块允许字段的浅层替换，不接受任意 JSON Patch。
- `content_block.completed`：`{ messageId, block, eventVersion }`，携带该块最终权威快照。
- `message.snapshot` 携带完整有序块，用于断线续跑和事件版本缺口修复。
- 前端只应用 `eventVersion = current + 1` 的增量；发现版本跳号时暂停应用后续 delta，等待同连接后续 snapshot，超时则触发现有 submission sync/消息刷新，不能带缺口继续拼接。
- 发送给浏览器的事件永远不包含图片 Base64，只包含私有 `assetId` 与有界元数据。
- 消息完成前的异常按现有确权逻辑收口；已形成的过程块随 failed/canceled 状态持久化，不能伪造 completed。

## 4. 用户消息即时投影

1. 用户点击发送且前端完成本地输入校验后，`PendingTurnProjection` 同时保存临时用户消息和临时助手消息，并立即插入当前会话。
2. 临时消息 ID 分别使用 `optimistic-user:${clientMessageId}` 和 `optimistic-assistant:${clientMessageId}`；二者使用独立的本地排序键，不能伪造服务端正整数 `sequenceNo`。
3. 输入框按现有规则立即清空；发送门禁、待确认和草稿恢复行为保持不变。
4. 收到 `message.started` 后，按 `clientMessageId` 原位替换为服务端 `userMessage`，并用权威 `assistantMessage` 接管临时助手投影。
5. 接受前失败时移除两条临时消息并恢复编辑器快照；已接受但终态不明时保留投影并进入现有对账流程，禁止重复发送。
6. 会话切换、消息同步和本地缓存刷新不得把当前活动轮次的临时用户/助手投影当作 `sequenceNo <= 0` 垃圾丢弃；只有收到权威 started、明确接受前失败或用户切换到其他会话后完成安全对账时才能移除。

该方案只提前展示“用户刚刚提交的本地事实”，不提前伪造服务端已接受、已计费或已生成成功。

## 5. 图像生成

### 5.1 直接图像模型

- 模型目录中 `mode=image_generation` 或仅支持 `images` 协议的模型允许出现在聊天模型选择中，但发送时进入专用 Images transport。
- `gpt-image-2` 通过本地真实 API Key 调用现有网关 `/v1/images/generations`，不能作为 `/v1/responses` 的顶层模型。
- 用户输入文本作为 `prompt`；本次不实现蒙版和编辑请求。
- 直接图像模型本次只接受文本输入；存在 `input_image` 时以稳定中文错误拒绝，不把图片静默丢弃。
- 助手时间线先创建进行中的 `tool_call(image_generation)`，上游返回后创建 `output_image` 并完成过程块。
- Images transport 必须在现有 Chat/Responses 能力拒绝之前独立分流；上游首期使用非流式 JSON，但聊天 `/stream` 路由仍包装为统一的 `message.started -> block events -> terminal` 站内 SSE，前端不直接解析 Images JSON。

### 5.2 普通 GPT 模型生图

- 模型目录明确包含 `image_generation`、本轮可走 Responses，且会话 API Key 当前路由候选存在已开启图像权限并能承接该工具的账户时，Chat transport 才在本轮工具集合中声明 `{ type: 'image_generation' }`。
- 模型目录只是静态能力来源；服务端返回给聊天页的 `effectiveTools` 必须结合 API Key、路由、候选账户、协议与图像权限计算，网关仍做最终裁决，前端不得按模型名猜测。
- 模型自行决定是否调用工具；系统提示只在用户确实要求生成位图时鼓励使用真实工具，不把普通解释请求强制转成图片。
- Responses 解析器识别 `image_generation_call` 的生命周期和最终 `result`、`revised_prompt`，按上游 `callId` 去重；多个可能携带最终结果的事件只允许第一个通过校验的结果落资产，后续重复结果忽略。
- `partial_image` 事件只用于维持调用进行态并立即丢弃其图像负载，不进入普通 64 KiB 工具事件、站内 SSE、消息快照或日志。
- 不把 `gpt-image-2` 填入 Responses 顶层 `model`；它是托管工具内部图像模型。

### 5.3 大结果与边界

- 现有 64 KiB 单 SSE 事件限制继续约束普通文本、思考和工具 JSON，但图像最终结果走独立的有界图像结果解析路径。
- 图像上游响应沿用网关图像 lane 的 64 MiB 绝对响应包络；解码后单图最多 16 MiB，每轮最多持久化 2 张生成图片，直接 Images 请求固定 `n=1`。
- 图像结果解析器增量定位 Base64 字段，按合法 Base64 边界分块解码到临时文件并同步计算字节数与 SHA-256；禁止先在内存构造完整 64 MiB JSON、完整 Base64 字符串或完整图片 Buffer。
- 用户上传图片继续沿用当前处理后 1 MiB 上限；生成图片使用独立的 16 MiB 对象读写上限，底层存储函数不得再把所有来源强制钳制为 1 MiB。
- 解析、解码、文件写入或资产提交任一步失败都清理临时对象并把图像过程标记为 failed，消息按真实结果收口。
- 浏览器、日志、站内 SSE、`content_blocks_json` 和本地缓存都不得保存图片 Base64。

## 6. 生成资产存储

生成图片复用 `chat_assets` 的所有权、会话绑定、配额、过期清理和私有读取接口，但扩展当前只面向用户上传 JPEG 的契约：

- 新增 `source_kind`：`user_upload` 或 `assistant_generated`。
- 新增消息资产引用关系，至少包含 `asset_id`、`conversation_id`、`turn_id`、`message_id`、`reference_kind` 和内容顺序；资产来源与消息引用分离，同一生成资产可以先由助手输出，后被新的用户消息作为 `input_image` 引用，不能通过覆盖单一 `turn_id/message_id` 重绑。
- 生成资产先以未提交状态预留配额并写入临时对象；完成魔数、MIME、尺寸、字节数和哈希校验后原子落盘，再由同一数据库事务写入助手资产引用、`output_image` 块并终结助手消息。
- `processed_mime_type` 扩展为实际支持的 `image/png`、`image/jpeg`、`image/webp`；用户上传仍按现有规则处理为 JPEG。
- 生成资产的 `original_*` 保存经过解码验证的供应商输出事实；`processed_*` 与同一落盘对象保持相同 MIME、尺寸、字节数和哈希。生成资产不强制重压成 JPEG，避免透明通道和细节损失；文件后缀、响应 `Content-Type` 与记录 MIME 必须一致。
- 生成资产计入现有用户资产字节数、资产数量、2 GiB 保留窗口容量和会话保留期清理。
- 资产 `expires_at` 取所有有效消息引用的最晚到期时间；删除/替换旧轮次时先删除对应引用，只有不存在未过期引用的资产才进入对象和配额回收，避免后续用户引用被源消息删除连带破坏。
- 文件系统与数据库不宣称原子事务：顺序固定为临时文件解码与校验、预留配额、原子落盘、数据库事务绑定引用并终结消息、事务成功后发送终态 SSE。取消或事务失败时不得持久化 completed output_image，并补偿删除对象、资产记录与配额；补偿失败交给未提交资产清理重试。
- 私有资产读取继续校验当前登录用户、会话归属、有效消息引用、过期时间和记录字节数；SHA-256 在写入提交前校验并作为 ETag，不在每次读取时重新扫描整图。
- 图片卡片提供预览与下载；后续作为输入时复用已有 `input_image assetId` 规则，不复制 Base64。

## 7. 前端过程与消息交互

### 7.1 有序渲染

- 助手消息只遍历有序 `contentBlocks`，不再先渲染全部 Markdown、再渲染全部工具。
- `output_text` 使用现有 Markdown 渲染器；`reasoning`、`tool_call` 使用过程组件；`output_image` 使用私有资产组件。
- 联网搜索 1、联网搜索 2 和结果正文按真实事件顺序出现，不按工具类型聚合后重排。
- 同一工具可以把多次 updated 合并为一个过程项，但不能跨不同工具 ID 合并调用次数。

### 7.2 展开与折叠

- `started/updated` 的当前过程项自动展开，并渐进追加内容。
- 单项进入 completed/failed 后自动折叠为一行摘要；用户手动展开后可以查看完整过程。
- 助手消息进入 completed/failed/canceled 时，所有仍处于展示态的过程项按终态折叠，正文和最终图片保持展开。
- 展开状态按 `messageId:blockId` 保存，只在块生命周期第一次从活跃变为终态时自动折叠；用户终态后手动展开的选择不能被其他块 delta 或快照再次覆盖。
- 新增块或块高度变化后只重新测量当前虚拟项；沿用“用户主动上滚后停止抢占”的规则。
- 流式跟随由消息 `eventVersion/renderRevision`、图片 load 和展开状态变化共同驱动；虚拟列表重测后必须保持相邻消息不重叠，并保持用户主动上滚后的锚点。

### 7.3 终态操作栏

- 助手消息状态为 `streaming` 时不渲染时间、复制和其他底部操作。
- completed/failed/canceled 才显示终态时间。
- 存在非空可复制正文时才显示复制；只有图片时提供下载，不显示无意义的正文复制。
- failed/canceled 的部分正文允许复制，但操作栏不能暗示生成成功。

## 8. 富文本输出

### 8.1 代码高亮

- 使用 highlight.js 常用语言集合并补项目需要的别名，至少覆盖 JavaScript、TypeScript、JSON、Shell、HTML、CSS、Python、Go、Java、C、C++、C#、Rust、SQL、YAML、XML、PHP 和 Ruby。
- 显式别名至少包含 `js/javascript`、`ts/typescript`、`py/python`、`sh/shell/bash`、`c++/cpp`、`c#/csharp`、`html/xml`、`yml/yaml`，别名解析在通用字符清理前完成。
- 未知或无语言标识的代码块回退为转义纯文本，不因高亮失败丢内容。
- 不引入完整语言包；构建产物大小和异步 Markdown 渲染耗时纳入回归。

### 8.2 Mermaid 与 LaTeX

- 继续使用 fenced `mermaid` 渲染流程图、时序图、状态图等；流未闭合时显示源码占位，闭合或终态后渲染。
- 行内公式使用 `$...$`，块公式使用 `$$...$$`，保持现有 KaTeX 回退行为。

### 8.3 fenced SVG

- 只有 fenced `svg` 进入预览；裸 HTML 中的 `<svg>` 仍按普通 Markdown HTML 规则处理。
- 不使用 DOMPurify 或元素/属性允许列表改写 SVG 源码。
- 原始 SVG 放入独立、隔离的 sandbox iframe `srcdoc`，不注入聊天主 DOM；允许 SVG 原型自身脚本和事件动效渲染，容器尺寸从根 `<svg>` 的 `viewBox/width/height` 读取并设置上下限。
- 预览失败时显示已转义源码和“SVG 渲染失败”，不能出现空白消息。
- 流式围栏未闭合时只展示源码；闭合后再创建预览，旧异步渲染不得覆盖新内容，重新渲染必须销毁旧 iframe。

## 9. 系统提示 `chat-system-v2`

提示词继续服从用户明确要求的语言、格式、长度和交付形态，并增加以下默认约束：

1. 以用户上下文、当前对话、可用工具或环境证据以及可靠的一般知识为依据，区分事实、合理推断、明确假设和未知。
2. 不虚构业务数据、规则、来源、工具结果或已执行操作。
3. 仅当缺失信息会实质影响正确性、安全性、成本或不可逆外部行为时暂停，并逐项列出继续所需的最少关键信息。
4. 非关键细节缺失时采用与上下文一致、可撤销的最小假设继续，明确标注假设与结论边界；可以先交付部分有效结果。
5. 用户未指定冲突格式且图形确实提升理解时，关系、流程与结构优先使用 Mermaid，数学表达使用 LaTeX。
6. 用户要求视觉原型或矢量图时可输出完整 fenced `svg`；用户要求生成位图且当前提供图像工具时优先调用真实生图能力，不用 ASCII 文本画图代替。
7. 工具能力改为显式集合，例如 `web_search`、`image_generation`，提示词和 transport 只能声明当前模型、协议与网关实际可用的工具。

`chat-system-v2` 使用新的稳定版本号和 hash；Chat Completions 与 Responses 注入同一文本，不给 API Key、路由策略、分组或 AI 账户新增用户配置项。

## 10. 测试与验收

### 10.1 后端

- 先写失败测试覆盖块顺序分配、连续文本合并、工具原位更新和快照恢复。
- 覆盖直接 Images API 与 Responses `image_generation_call` 两条路径。
