# 使用记录手动刷新设计

**状态：** 已确认

**日期：** 2026-07-18

## 1. 背景

`/my-usage-records` 和 `/usage-records` 当前通过 `usePageDataRequestCache` 保存当前查询结果，并由可见页确认调度器每 15 秒调用一次 `/data-changes/confirm`。确认结果发生变化时，页面重新加载当前查询结果。

使用记录是日志事实，当前页行内容不会因为页面停留而需要持续推送。用户明确要求改为手动刷新，避免页面持续确认和刷新。

## 2. 目标

- 两个使用记录入口都不再进行周期性自动确认或自动重载。
- 页面首次进入、筛选、排序、分页、手动刷新和已有的跨日日期切换仍能加载数据。
- 不改变使用记录 HTTP API、权限范围、查询参数、分页行为、错误提示、后端首屏热缓存或数据库查询优化。
- 不把旧的使用记录列表结果继续保存在前端 IndexedDB，避免关闭周期确认后重新进入页面仍显示不可确认的旧快照。

## 3. 非目标

- 不删除后端 `usage.records` 数据域、变更发布、首屏热缓存或分页 repository。
- 不改 `/usage-records/:id` 详情查询。
- 不改使用记录自动日期模式在部署时区跨日时切换日期范围的行为；该逻辑是日期边界维护，不是日志新鲜度轮询。
- 不处理 AI 账户列表、公告、聊天、模型检测或其他页面的动态机制。

## 4. 方案

### 4.1 页面数据流

`UsageRecordsView.vue` 保留现有 `useResponsivePagedList`，但 `fetchRecords` 直接调用现有 `usageRecordsApi.list(params)`。删除页面级 `usePageDataRequestCache` 实例、当前请求定义、周期确认间隔和缓存结果 watcher。

因此所有数据进入路径统一为：

```text
页面首次加载 / 筛选 / 排序 / 分页 / 手动刷新
                    |
                    v
          usageRecordsApi.list(params)
                    |
                    v
    后端首屏热缓存或 listUsageRecordsAsync
```

### 4.2 后端边界

后端路由仍先尝试默认个人首屏热缓存；未命中时执行现有分页查询并异步回填缓存。管理范围、带筛选条件的查询和非首屏查询继续走现有 repository 路径。前端是否使用 IndexedDB 不影响这些后端分支。

### 4.3 手动刷新与错误处理

- 桌面端和移动端现有刷新入口继续调用列表加载流程，并始终请求网络。
- 加载中状态、分页状态、筛选选项加载和现有错误提示保持不变。
- 去掉缓存后，不新增 fallback 数据，也不使用旧列表掩盖请求失败。

### 4.4 生命周期

删除页面缓存后，使用记录页面不再创建 15 秒确认定时器、focus 确认和 BroadcastChannel 页面缓存订阅。已有跨日定时器仍按当前页面激活状态管理。

## 5. 测试设计

- 先修改前端回归约束，使使用记录页面不得接入 `usePageDataRequestCache`、`usage.records` 页面确认或周期 watcher；运行回归确认现有实现失败。
- 实现直接网络加载后，运行同一回归确认约束通过。
- 保留并运行使用记录管理页回归，确认列表状态合并、筛选、分页、auto/manual 日期模式和跨日逻辑不回归。
- 运行前端类型检查和构建，确认移除导入、缓存 watcher 和请求定义后无 TypeScript/Vue 编译错误。
- 运行后端使用记录首屏热缓存回归，确认后端优化未被改动。

## 6. 验收标准

1. 两个使用记录路由源码中不再创建 `usePageDataRequestCache` 或 15 秒确认调度器。
2. 页面首次进入、筛选、排序、分页和手动刷新仍发起现有使用记录列表请求。
3. 后端使用记录 API、首屏热缓存、分页查询和权限边界的源码与回归结果不变。
4. 页面不会因为无缓存或请求失败而伪造旧数据成功。
5. 相关前端和后端回归、类型检查、构建均通过。

## 7. 发布与回退

本变更只涉及前端列表加载路径和回归约束，不需要数据库迁移或后端部署调整。回退时恢复 `UsageRecordsView.vue` 的页面缓存接入及对应回归断言即可；后端无需回退。
