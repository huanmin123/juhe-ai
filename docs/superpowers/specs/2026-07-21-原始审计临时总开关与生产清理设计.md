# 原始审计临时总开关与生产清理设计

## 1. 背景与目标

生产 Node 网关在高并发、大请求体和长流式响应场景下出现原始审计 payload 放大。现场采样显示主进程 RSS 和外部 Buffer 明显升高，事件循环延迟达到秒级，后台调度和 IPC 随之停滞。现有成功审计三项全 0 只能关闭成功请求审计，失败、异常、中断、重试后成功和早期拒绝仍会创建 capture、编码 payload、投递队列并落库，不能满足当前止血要求。

本设计增加一个部署级总开关，允许在不删除审计功能代码的前提下临时停止所有新审计。生产启用关闭状态后，清空现有生产审计数据。Go 迁移或后续容量治理完成后，可通过配置重新启用功能。

## 2. 范围与非目标

本次范围：

- 新增 `JUHE_AI_AUDIT_LOG_ENABLED` 环境变量，默认 `true`，生产配置为 `false`。
- 关闭时停止所有新审计捕获，包括成功、失败、异常、中断、重试后成功、预认证拒绝、请求体拒绝和容量降级记录。
- 关闭时不启动或使用审计 transport、server/worker IPC、Redis Stream 审计队列和审计落库队列。
- 保留历史审计列表、详情、payload 查询接口和管理员页面；运行态明确返回审计已关闭。
- 保留审计保留期清理代码，避免重新启用后出现两套生命周期逻辑。
- 生产确认关闭生效后，清空 PostgreSQL 审计表、审计 Redis Stream 和 Mac 本机 audit 文件。

明确不改：

- `usage_records`、用量统计、额度、运行日志、操作日志、公开 API 日志和模型检测记录。
- 网关请求体上限、协议转换、重试、账号调度和响应检查逻辑。
- 审计表 schema、历史查询契约和后续重新启用能力。
- Windows 开发环境和本地测试数据。

## 3. 配置契约

`RuntimeConfig.auditLog` 增加 `enabled: boolean`，由 `JUHE_AI_AUDIT_LOG_ENABLED` 读取：

| 配置值 | 行为 |
| --- | --- |
| 未配置 | `true`，保持现有环境兼容 |
| `true/1/yes/on` | 启用全部现有审计语义 |
| `false/0/no/off` | 停止所有新审计 |
| 其他值 | 启动失败并输出明确配置错误 |

成功审计热窗口、采样、保留期和正文上限仍按现有变量解析。总开关关闭时这些值只保留为配置事实，不触发捕获或落库。重新启用时无需修改代码或数据库结构。

## 4. 运行时关闭语义

### 4.1 网关捕获

`AuditCaptureContext` 继续作为调用方稳定接口，但在关闭状态下构造为轻量 no-op：

- 不登记 active capture。
- 不保存请求、上游或响应 headers/body。
- 不创建 payload summary、hash、base64 或 transport job。
- `finalize` 不生成审计记录。
- 对现有调用方返回空 capture 结果，不改变网关成功或错误响应。

### 4.2 早期拒绝与容量降级

`recordDroppedAuditCapture`、`enqueueAuditLog` 和本地批量入队入口必须在函数最前面检查总开关。这样预认证失败、图像权限拒绝、body parser 拒绝、请求体超限和容量降级等绕过正常 capture 的路径也不会生成 metadata-only 审计。

关闭行为必须集中在审计模块边界，不在每个网关调用点散布环境变量判断。

### 4.3 Transport、队列与 worker

- server 不创建审计 transport worker，不编码 Redis Stream payload。
- ingest-worker 不启动审计 Redis Stream consumer。
- 审计本地队列保持空，flush 和 shutdown drain 立即完成。
- 关闭后遗留的旧 Redis Stream 消息不自动消费，交由本次生产清理显式删除，避免旧消息在重新启用时补写。
- 其他 ingest-worker 职责继续运行，不能因审计关闭跳过使用记录、操作日志、公开 API 日志、运行日志索引或 record maintenance。

## 5. 查询与运行态

历史列表、详情、payload 和热文件搜索接口继续保留现有权限与返回契约。关闭开关不伪造 404，也不隐藏历史数据；生产数据清理后自然返回空列表。

审计 `/runtime` 响应增加或明确返回：

- `enabled: false`
- `unavailableReason: audit_disabled`
- active capture、transport 和审计队列均为零或不可用状态

该状态只描述审计子系统，不得把整个 ingest-worker 标记为不可用。

## 6. 生产发布与数据清理

代码变更属于应用 release，必须领取本机部署计划锁并使用临时服务接管流程。发布顺序：

1. 本地完成回归、类型检查、构建和 release 归档验证。
2. 在生产 `shared/backend.env` 写入 `JUHE_AI_AUDIT_LOG_ENABLED=false`。旧 release 忽略该变量，现有成功审计三项 0 继续提供回滚止血。
3. 启动支持新开关的临时 release，验证其审计 runtime 为 disabled、真实网关请求不新增任何审计记录、使用记录仍新增。
4. 切换临时服务承流，离线升级主服务，再验证主服务同样不产生审计。
5. 切回主服务并完成稳定窗口后，才执行不可恢复的数据清理。

清理前记录但不备份审计内容：

- 五张审计表行数和总大小。
- audit 文件数量和总字节数。
- 审计 Redis Stream 长度、consumer group 和 pending 数。
- 清理开始时间、当前 release 和配置状态。

清理动作：

- 在单个 PostgreSQL 事务中清空 `juhe_dataset.audit_logs`、`audit_log_attempts`、`audit_payload_refs`、`audit_payload_blobs` 和 `audit_error_groups`。不使用 `CASCADE`；若存在未预期依赖则失败并停止。
- 通过当前 release 的 runtime config 解析真实 namespace，只删除审计 Stream key，不硬编码 namespace，不触碰其他 Redis key。
- 校验 audit 根目录解析后位于 `/Users/huanmin/juhe-ai-lite/shared/data/audit`，只删除其下文件并保留目录，不跟随目录外链接。
- 删除后再次核对五张表均为 0、审计 Stream 不存在、audit 文件为 0，同时确认 `usage_records` 在清理窗口继续增长。

本次清理由用户明确授权，不生成审计内容备份，删除后不可恢复。

## 7. 回滚边界

代码回滚时旧 release 会忽略 `JUHE_AI_AUDIT_LOG_ENABLED=false`，但生产已配置的成功审计三项 0 仍会关闭成功审计；失败和异常审计会在旧 release 恢复后重新产生。应用可用性优先于审计关闭状态，出现发布故障时按标准流程回滚，不在失败 release 上继续清理数据。

数据清理没有回滚。只有临时和主 release 都已验证总开关生效、流量已稳定切回主服务后才允许执行。

## 8. 测试与验收

### 8.1 配置与单元行为

- 默认未配置时审计启用。
- 所有合法真假值解析正确，非法值启动失败。
- 开关关闭时成功和失败 capture 均不落库。
- 早期认证失败、权限拒绝、请求体超限和 dropped capture 均不入队。
- `enqueueAuditLog`、批量本地入队、Redis producer/consumer 和 transport 在关闭状态下保持零任务。
- 开关重新设为 true 后现有审计回归继续通过。

### 8.2 相邻链路

- 使用记录在审计关闭时继续落库和聚合。
- ingest/stats/ops 三个 worker 拓扑正常。
- 应用、DB service 和公网 health 为 200。
- 审计历史查询在关闭状态下仍可读取已有记录，清理后返回空列表。
- 运行态明确显示 disabled，不误报 worker 故障。

### 8.3 发布验收

- 临时和主 release 分别用真实请求验证审计表计数不增长。
- 同一请求对应的 `usage_records` 正常新增。
- 清理后 PostgreSQL、Redis 和 audit 文件三处均无审计数据。
- 稳定窗口内主进程 RSS、外部 Buffer 和事件循环延迟不再出现审计捕获造成的持续放大。
