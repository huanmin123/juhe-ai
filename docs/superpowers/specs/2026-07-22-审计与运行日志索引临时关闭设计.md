# 审计与运行日志索引临时关闭设计

## 1. 背景与目标

生产 Node 网关在高并发、大请求体和高频日志场景下出现旁路数据处理放大。原始审计会捕获、编码、排队并保存请求链路；运行日志搜索会由 ingest-worker 每秒扫描进程日志文件、解析行并写入 PostgreSQL 索引。现场已观察到主进程事件循环秒级延迟、内存升高和后台任务停滞，重启后暂时恢复。

本次以部署级开关临时停止两条非核心数据库写入链路，功能代码、schema、页面与重新启用能力保留，待 Go 迁移后重新评估。核心业务使用记录不得关闭或清理。

## 2. 范围

本次增加两个相互独立、默认启用的部署环境变量：

- `JUHE_AI_AUDIT_LOG_ENABLED`：控制全部原始审计新捕获与写入。
- `JUHE_AI_RUNTIME_LOG_INDEX_ENABLED`：控制日志文件到 `runtime_logs` 数据库搜索索引的导入。

生产把两项配置为 `false`。关闭后清空生产审计数据和运行日志数据库索引数据。

明确不改：

- `usage_records`、使用记录队列、Redis Stream、页面、统计、额度、成本和账户质量。
- Pino 正常控制台与文件日志输出、轮转和保留策略。
- 操作日志、公开 API 日志、模型检测记录。
- 网关路由、重试、协议转换、账号状态和请求体限制。
- 日志文件格式；本轮继续使用现有 Pino JSON 行格式。
- Windows 开发环境与本地数据。

## 3. 原始审计总开关

`RuntimeConfig.auditLog` 增加 `enabled: boolean`。变量未配置时为 `true`；接受 `true/1/yes/on` 与 `false/0/no/off`，其他值启动失败。

关闭时：

- `AuditCaptureContext` 为轻量 no-op，不登记 active capture，不保存 header/body，不生成 hash、摘要或最终审计记录。
- `recordDroppedAuditCapture`、`enqueueAuditLog` 与批量本地入队入口最前面返回，覆盖认证拒绝、权限拒绝、请求体拒绝和容量降级。
- server 不创建审计 transport worker，不进行 IPC 或 Redis payload 编码。
- ingest-worker 不启动审计 Redis Stream consumer；本地队列保持空，flush 与 shutdown drain 快速完成。
- 其他 ingest-worker 职责继续运行。

历史审计列表、详情、payload 和热文件搜索路由保留。`/audit-logs/runtime` 返回 `enabled=false` 和 `unavailableReason=audit_disabled`，但不能把整个 ingest-worker 标记不可用。

## 4. 运行日志数据库索引开关

`RuntimeConfig.log` 增加 `indexEnabled: boolean`，由 `JUHE_AI_RUNTIME_LOG_INDEX_ENABLED` 解析；合法值与默认值规则同审计开关。

关闭时：

- `startRuntimeLogFileImport()` 直接返回，不设置轮转文件保护 predicate，不启动发现、tail、解析、cursor 或批量入库循环。
- `runtime-log-index-maintenance` 不执行 facet 初始化、增量维护或索引保留清理。
- 正常 `logger` 输出继续写 stdout 和各角色 `.log` 文件，日志轮转与文件保留正常。
- 文件 grep 能力继续直接读取日志文件，不依赖数据库索引；数据库分页列表、详情和 facets 保留接口但清理后为空。
- `/runtime-logs/runtime` 返回 `indexEnabled=false` 和 `unavailableReason=index_disabled`；ingest-worker 的其他队列仍可用。

关闭只阻止生产自动导入。repository 的显式写函数和测试入口保留，避免移除功能或破坏重新启用回归。

## 5. JSON 日志格式结论

Pino 把字段对象序列化为 JSON 确有 CPU、字符串分配和写入字节开销，但当前更直接的额外负载来自 ingest-worker 对日志文件持续扫描、JSON 解析、批量写库和 facets 维护。本轮优先关闭数据库索引链路，不改日志格式，原因是：

- 可立即移除 tail、parse 和数据库写入开销。
- 保持现有文件排障、字段安全、fatal 诊断和工具兼容。
- 避免同时改动所有日志调用点和解析契约，降低生产止血风险。

Go 迁移后再通过压测比较结构化 JSON、固定文本和混合格式，不凭推断提前重写日志系统。

## 6. 生产发布与清理

应用按部署计划锁和 temporary-first 流程发布。先在生产 `shared/backend.env` 写入两个 `false`，再启动支持开关的 temporary release。

临时服务与主服务分别验证：

- 审计 runtime 为 `audit_disabled`，真实成功和失败请求不新增审计。
- 运行日志 runtime 为 `index_disabled`，日志文件持续增长而 `runtime_logs` 不增长。
- `usage_records` 对真实请求继续新增。
- app、DB service、公网 health 和 `1+1+3` worker 拓扑正常。

只有主服务回切、`VERIFY_SUCCESS` 和稳定观察完成后才允许清理。

审计清理：

- 单事务、无 `CASCADE` 清空 `juhe_dataset.audit_logs`、`audit_log_attempts`、`audit_payload_refs`、`audit_payload_blobs`、`audit_error_groups`。
- 通过当前 release runtime namespace 解析并只删除审计 Redis Stream key。
- 校验 `/Users/huanmin/juhe-ai-lite/shared/data/audit` 真实路径后只删除其内容并保留目录，不跟随目录外链接。

运行日志索引清理在一个 PostgreSQL 事务中、无 `CASCADE` 清空：

- `juhe_dataset.runtime_logs`
- `runtime_log_file_cursors`
- `runtime_log_facet_summary`
- `runtime_log_level_facets`
- `runtime_log_event_facets`

运行日志文件不删除。清理前只记录行数与总大小，不备份被授权清理的审计和运行日志索引内容。删除不可恢复。

## 7. 回滚边界

旧 release 会忽略新变量，因此应用回滚后审计失败记录和运行日志索引可能恢复写入；可用性优先，发生发布故障时立即回滚并停止数据清理。数据清理只在新 release 双开关已经稳定生效后执行，清理本身无回滚。

重新启用新 release 时，把对应变量设为 `true` 并重启：审计从新请求重新产生；运行日志 importer 会从空 cursor 开始读取仍在保留期内的现有日志文件，可能回填历史文件。Go 迁移前不执行重新启用；未来重新启用时应先决定是否允许回填，必要时先建立当前文件 EOF cursor。

## 8. 测试与验收

- 两个开关默认启用，合法真假值正确，非法值启动失败。
- 审计关闭时成功、失败、早期拒绝、直接 enqueue、transport 和 Redis consumer 均为零工作。
- 运行日志索引关闭时 importer 不启动、不写 cursor/日志/facets；正常日志文件仍有新增字节。
- 两个 runtime 接口明确返回 disabled，且不误报整个 ingest-worker 故障。
- 历史查询接口保留；生产清理后数据库分页结果自然为空；文件 grep 仍可搜索日志文件。
- `usage_records` 专项回归和生产真实请求均证明继续写入。
- 操作日志与公开 API 日志未被开关或清理触碰。
- 生产清理后五张审计表、审计 Stream、audit 文件内容和五张运行日志索引表均为 0。
