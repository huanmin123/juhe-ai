# 通用客户端上游失败服务端接管设计

> 状态：历史 / superseded。本文只保留决策背景，不是当前实现契约；现行边界以 [AI 账户错误语义与状态变更边界](../../functions/AI账户错误语义与状态变更边界.md) 和 [PLAN-0172](../../plans/计划-0172-20260723T160339731Z-账户错误作用域与重试选择验证.md) 为准。禁止按本文旧正文实施图片、资源创建或其他副作用请求的发送后重放。

## 1. 背景

生产图像生成请求已经通过系统账户图像权限门禁，并成功进入默认 GPT 分组，但首个上游账户返回完整 HTTP 失败响应后，网关直接把该响应交给客户端。审计显示本次请求只有一次上游尝试，并被记录为成功转发；分组内其他已验证可用账户没有获得接管机会。

当前实现把两个不同问题绑定在同一个 `interpretUpstreamResponseSemantics` 布尔值上：

- 是否读取并解释具体客户端的响应正文、错误类型和 SSE 事件；
- 完整 HTTP 请求未成功时，是否继续尝试服务端候选账户。

`generic_openai`、`generic_anthropic`、`generic_gemini` 不允许解释上游响应语义，因此现有派发器把任意已建立的 HTTP 响应都当成可交付结果。这违反项目的稳定性原则：只要服务端还有可用 Key、账户或备用分组，就不能提前把客户端暴露给单个上游账户的失败。

现有主线测试也存在契约冲突：

- `gateway-generic-upstream-opaque` 和 `gateway-upstream-semantic-policy` 固定了 generic 完整非成功 HTTP 响应直接透传；
- `codex-turn-account-switch-e2e` 已要求普通客户端在输出前失败时由服务端隐藏切号，并要求全部候选耗尽后才返回稳定的客户端可重试错误。

本设计统一上述契约，并让图像请求与普通文本请求复用同一失败接管链路。

## 2. 核心原则

1. 服务端优先救回。只要下游尚未提交不可撤回的语义内容，且仍有受当前授权和模型约束允许的候选，就继续服务端尝试。
2. 不解释未知上游语义。generic 路径不读取具体 HTTP 状态码，不解析错误类型、错误码、错误文案或供应商自定义错误结构，不据此决定账户健康或持久状态。
3. 只使用通用 HTTP 成功边界。派发器只区分本次 HTTP 请求是否成功完成，不对失败响应做细分类；这是统一传输控制，不是供应商错误语义判断。
4. 客户端画像只控制协议语义。Codex、Claude Code、Gemini CLI 等精确画像可以解释其明确协议事件；generic 客户端继续保持正文和 SSE 语义不透明。
5. 提交边界高于重试意愿。已经向客户端写出真实响应正文、模型输出、工具状态或其他不可撤回语义后，不拼接第二个账户的响应。
6. 图片不特殊化。Images API、Responses `image_generation` 与普通请求使用同一派发、失败排除、候选耗尽和客户端兜底流程；图片只使用 image lane 的并发、请求体上限和超时配置。
7. 不把单次未知失败写成账户事实。generic 完整失败响应只在当前请求内排除当前尝试，不按状态或正文修改账户持久状态、上游桶、来源熔断或模型能力。

## 3. 目标与非目标

### 3.1 目标

- generic 客户端在下游提交前收到完整 HTTP 失败响应时，继续尝试同账户允许的后续 Key、后续账户和后续分组。
- 后续账户成功时，客户端只看到最终成功响应，不看到前序账户失败。
- 全部候选耗尽后，精确客户端得到对应协议的可重试失败信号，generic 客户端得到稳定的 HTTP 客户端可重试错误。
- 失败尝试在使用记录和审计中记为失败，不确认 Key 成功、half-open 成功或会话亲和。
- 保留 generic 客户端对 `200 + JSON error`、`200 + SSE error event` 和未知成功响应正文的不透明语义。
- 统一文本、图片、OpenAI、Anthropic、Gemini 和内部辅助派发的 HTTP 成功边界。

### 3.2 非目标

- 不建立状态码、错误码、错误类型或错误文案白名单。
- 不增加图片权限错误、限流错误、余额错误或供应商错误的专属分支。
- 不根据单次 generic 失败自动禁用账户、删除支持模型或持久化负能力。
- 不在已提交响应后跨账户拼接 JSON、SSE、图片正文或工具调用。
- 不改变本地图像权限门禁、API Key 授权、额度、并发和候选模型过滤规则。
- 不在本任务中部署生产或修改生产数据。

## 4. 状态模型

网关必须分别维护以下事实，不能再用一个“是否解释语义”布尔值代替：

| 状态 | 含义 | 决策用途 |
| --- | --- | --- |
| `httpSucceeded` | 上游 HTTP 请求是否产生成功响应 | 所有客户端统一决定当前 attempt 成功或继续调度 |
| `transportCommitted` | 是否已经向下游写过 HTTP 头或 SSE 等待注释 | 限制后续输出只能保持原协议形态 |
| `semanticCommitted` | 是否已经写出真实上游正文、可见模型内容或状态改变事件 | 为 true 后禁止静默跨账户接管 |
| `interpretProtocolSemantics` | 是否允许解释明确客户端的 JSON/SSE 协议终态 | 只由精确客户端画像决定 |
| `attemptRecorded` | 当前 attempt 是否已经完成审计和使用记录 | 保证每次失败和成功只记录一次 |

`httpSucceeded` 与 `interpretProtocolSemantics` 必须独立：generic 客户端可以不解释任何错误内容，同时仍把未成功 HTTP attempt 留在服务端处理。

## 5. 请求处理流程

### 5.1 下游尚未提交时

1. 按当前路由策略、分组、模型、账户状态、并发和运行态生成候选顺序。
2. 发起当前上游 attempt，等待响应头。
3. HTTP 请求成功时进入现有响应最终化流程。
4. HTTP 请求未成功时：
   - 不向客户端复制状态、响应头或正文；
   - 对错误正文只做现有上限内的诊断捕获，不解析、不匹配、不据此分流；
   - 当前 attempt 记录为 `upstream_response` 失败；
   - 不确认 session affinity、half-open 或 Key 成功；
   - 接管顺序固定为“同账户短重试 -> 下一 Key -> 下一账户 -> 下一分组”；每一层都受现有授权、候选和统一服务端重试预算约束。
5. 任一后续 attempt 成功后，只把该成功响应交给客户端，并提交前序失败的请求内局部记录。

失败正文捕获必须有界。达到捕获上限后停止保留更多诊断内容，并主动结束当前上游响应读取；不能为切号把任意大错误正文完整读入内存。

### 5.2 transport 已提交但语义未提交时

SSE 容量等待注释可能已经写出，此时 `transportCommitted=true`、`semanticCommitted=false`。服务端仍可切换账户，但后续只能继续写合法 SSE 帧，不能退回普通 JSON。精确客户端最终耗尽时使用其协议失败事件；generic 客户端使用现有断流或通用 SSE 失败边界，不注入供应商专属事件。

### 5.3 语义已经提交时

一旦真实上游正文、文本、reasoning、工具参数、图片结果或其他可见状态已经写给客户端，当前响应不能再由第二个账户续写。网关负责：

- 结束或中断当前响应；
- 释放并发和 attempt 资源；
- 对精确客户端输出其已定义的客户端重试信号；
- 对 generic 客户端保留原协议失败或断流，让客户端执行整请求重试。

这条边界与文本、图片无关。

### 5.4 全部候选耗尽

服务端必须完成当前 Key、账户和允许的备用分组扫描，或耗尽统一服务端重试预算后，才能结束救回：

- Codex Responses、Claude Code Messages、Gemini CLI 使用各自现有稳定协议失败信号；
- generic 非流式客户端返回网关稳定 JSON 错误，状态使用当前统一服务不可用语义，错误码使用现有可重试码；
- generic 流式客户端按其下游协议和提交状态使用现有通用失败/断流边界；
- 最终响应不暴露某一个供应商的私有错误类型，也不把多个账户错误拼接给客户端。

## 6. 派发与副作用边界

### 6.1 派发器

`fetchFirstAvailableUpstream` 不再用 `interpretUpstreamResponseSemantics` 决定是否接受非成功 HTTP 响应。派发器对所有客户端统一处理 HTTP attempt 成败；客户端画像只作为后续正文/SSE 检查输入。

为避免把 generic 路径带入现有状态码/错误体策略，需要新增或抽取“opaque HTTP failure”处理边界。该边界只做：

- 有界读取和审计；
- attempt 失败记录；
- 同账户短重试预算；
- 当前请求排除和后续候选选择；
- 候选耗尽时保留最后一次 attempt 的安全诊断。

它不调用账户错误规则匹配、不解析 provider error payload，也不依据 HTTP 数字决定副作用。

### 6.2 成功确认

以下动作只能在当前 attempt 真正成功后执行：

- 记住 session affinity；
- `confirmHalfOpenSuccess()`；
- `confirmSameAccountApiKeyFailures()`；
- `recordGatewayAccountApiKeySuccess()`；
- 使用记录与审计 `success=true`；
- 成功后的来源局部回避确认和恢复。

完整转发与业务成功是不同事实。若后续仍需要观察“网关是否完成字节转发”，应使用独立字段或审计 metadata，不能复用 `success`。

### 6.3 失败副作用

generic opaque HTTP 失败可以记录：

- trace、attempt、账户、分组、耗时和 HTTP 状态摘要；
- 有界且已按现有安全规则处理的响应摘要；
- 当前请求内失败账户集合。

它不能直接触发：

- 账户持久状态变更；
- 上游桶或 IP 恶意来源熔断；
- 模型能力删除；
- 供应商错误特征规则；
- 基于状态码或正文的 Key 永久失效判断。

后台探针和明确客户端策略继续负责账户级事实确认。

## 7. 内部辅助请求

混合路由评分、质量检查等内部辅助派发不是外部透明代理，不应把非成功 HTTP 响应包装为 `outcome: success`。它们复用统一 opaque HTTP failure 接管：

- 当前评分账户失败时尝试后续允许账户；
- 全部耗尽后返回内部稳定失败，交给现有 default/fallback；
- 不解析未知供应商错误；
- 只有成功 HTTP 响应才进入评分 JSON 解析。

## 8. 图像请求

图像请求不增加任何错误识别或能力负缓存。它和文本请求的差异仅来自已有 lane 配置：

- 图像请求体上限；
- 图像首响应、流式空闲和单次 attempt 生命周期；
- 图像并发保留与候选容量排序；
- 图片正文的审计省略。

Images API 收到完整失败 HTTP 响应且下游尚未提交时，执行与 Chat、Responses 相同的服务端候选接管。成功图片一旦开始写出，不跨账户拼接或续写。

## 9. 兼容性与资源型端点

本任务修改的是统一推理派发的失败接管，不新增资源 API 的跨账户语义。已有本地 Files 和 Vector Stores 路由保持不变。对于 Uploads、Batches、Fine-tuning 等具有资源归属或创建副作用的未建模端点，候选过滤和路由能力仍按现有契约处理；本任务不借机扩展其支持范围。

如果未来正式支持资源创建端点，必须先单独设计账户归属、幂等键和后续读取固定路由，不能从本次推理请求接管规则隐式获得跨账户重放能力。

## 10. 测试策略

### 10.1 必须先失败的回归

- generic OpenAI 非流式：首个账户返回任意完整 HTTP 失败，第二账户成功；断言客户端只收到第二账户成功响应。
- generic OpenAI Images：与文本使用同一断言，仅切换模型、端点和 image lane。
- generic Anthropic、Gemini：首账户失败、后续账户成功，不解析失败正文。
- 同账户多 Key：前序 Key 失败后尝试下一 Key，再进入下一账户。
- 备用分组：当前分组耗尽后继续已授权备用分组。
- 全部候选失败：服务端耗尽后才返回稳定客户端可重试失败。
- exact client：Codex、Claude Code、Gemini CLI 已有协议语义检查和失败事件保持不变。
- `200 + JSON error`、`200 + SSE error event`：generic 仍保持不透明；精确客户端继续按现有协议边界处理。

### 10.2 副作用回归

- 失败 attempt 的 usage/audit `success=false`、`attempt_count` 准确。
- 失败 attempt 不确认 half-open，不记录 Key success，不建立 session affinity。
- 后续成功只确认最终账户成功，前序失败不被改写成成功。
- hybrid scoring/quality 非成功 HTTP 响应不能进入评分 JSON 成功路径。
- 图片成功正文继续执行审计省略，失败正文只做有界诊断捕获。

### 10.3 基线与环境

- 当前 `master` 的 `test:codex-turn-switch-e2e` 已在 generic 输出前失败场景失败，作为本任务红灯基线。
- 当前 `test:upstream-request-failure` 在账户检查模型种子校验阶段失败，属于既有测试基线问题；修复测试夹具时不得放宽业务断言。
- SQLite 测试库若因旧 schema 缺列可按项目授权删除后重建；PostgreSQL/Redis 集成测试使用测试环境和任务专属数据，不操作生产。
- 真实模型验证只在 mock、类型检查和本地/测试库回归通过后执行，并控制为最小请求；凭据只从用户指定本地文件读取，不写入仓库或日志。
