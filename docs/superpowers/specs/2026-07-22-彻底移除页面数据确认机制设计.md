# 彻底移除页面数据确认机制设计

## 1. 背景与结论

当前 page-data 机制以 `POST /data-changes/confirm`、revision token、浏览器持久缓存和写端变更发布为核心。它假设页面数据在多数确认周期内保持不变，以一次轻量版本探针替代完整业务查询。

该假设不适用于当前系统：账户余额、运行状态、用量和调度事实高频变化，且这些变化会推进 `accounts.static`、`accounts.runtime`、`accounts.options` 和统计域。实际请求经常形成“confirm -> changed -> 业务 GET”，网络往返被串行叠加，未形成稳定收益。

本次决定：**整套 page-data confirm/revision 机制退场，不保留兼容入口、空实现、旧客户端兜底或隐藏开关。页面恢复直接调用业务接口。**

## 2. 删除范围

### 2.1 前端

- 删除 `pageDataApi`、revision/domain 类型和 `/data-changes/confirm` 调用。
- 删除 IndexedDB page-data cache、resource cache、request cache、activation coordinator、manifest、generation/write epoch 和 mutation 自动失效。
- 删除页面级 30 秒 confirm scheduler、跨标签 page-data 广播和相关安全上下文围栏。
- 所有消费者恢复为直接业务请求；页面自身已有的 in-flight 去重、局部短时缓存或 KeepAlive 恢复逻辑，仅在不依赖 page-data revision 时保留。
- 手动刷新继续调用业务接口；登录/退出不再清理 page-data 存储。

### 2.2 Node 后端

- 删除 `/data-changes/confirm` 路由、domain/revision/change store、Redis EVAL 和运行时初始化。
- 删除所有 `publishAccount*PageData*`、`publishPageDataDomain*`、统计/公告 page-data 发布和写路径接线。
- 删除 DB service IPC 中的 page-data event、dirty-domain 同步和恢复协议。
- 删除 page-data dirty-domain repository、benchmark、smoke、regression 和 package scripts。
- 删除 System API 对 confirm 的 DB access/rate-limit/session 特例；普通请求继续按现有访问模式分类。

### 2.3 Go 后端

- 删除 Redis page-data publisher、app adapter、dirty-domain recovery、cache version writer 和相关测试。
- 删除管理模块及公告写接口注入的 page-data publisher；业务写入、操作日志和其他副作用保持。
- 删除 port/store 中只为 page-data dirty-domain 服务的接口和实现。

### 2.4 文档与测试

- 当前架构、功能、测试入口不再描述 page-data confirm/revision 为有效能力。
- PLAN-0115、0139、0141、0151 等历史计划保留历史正文，但在索引和文档顶部标记“机制已由 PLAN-0156-20260722T123439000Z 移除”，避免被当作当前事实。
- 删除只验证已退场机制的专项测试；相邻业务测试改为验证直接请求和正常写路径。

## 3. 明确保留的能力

以下能力名称相近，但不属于本次删除：

- 账户健康检查、后台标准探针、冷却复测和运行状态快照。
- 余额定时刷新、余额快照、用量预聚合和账户状态接口。
- repository/read-through/shared cache、网关运行态缓存、模型目录快照等独立缓存。
- 页面组件内部为了防重复点击或并发请求使用的普通 singleflight/in-flight 状态。
- 业务接口自己的分页、筛选、排序和手动刷新。

判断标准：只有依赖 page-data domain/revision/confirm/change publisher 的能力删除；独立业务事实和独立缓存不因命名含 `cache`、`snapshot` 或 `probe` 被误删。

## 4. 删除后的请求模型

```text
页面挂载 / 激活 / 手动刷新
  -> 直接调用对应业务 API
  -> 页面按现有 loading/error/superseded 规则提交结果

业务写入
  -> 写数据库 / 队列 /业务缓存失效
  -> 不再发布 page-data revision/change event
```

不新增替代协议，不引入 ETag、SSE、WebSocket 或新的版本机制。后续如需优化高频账户页面，应单独设计“静态列表 + 高频动态快照”，不能复活通用 confirm。

## 5. 数据与兼容边界

- 不保留 `/data-changes/confirm` 兼容路由，旧请求返回正常 404。
- 不读取旧 IndexedDB page-data 数据；数据库升级后浏览器会自然遗留孤立存储，但运行时代码不再访问。不得为了清理旧客户端数据保留 page-data 代码。
- Redis 中旧 page-data key 不再读写，按 TTL 自然过期；不添加生产运行时扫描或批量删除。
- 若本地 SQLite / PostgreSQL 存在只服务 dirty-domain recovery 的表，schema 和 migration catalog 应删除当前定义；既有环境的数据处理属于部署时离线事项，本次不部署。

## 6. 验证标准

- 全仓生产代码不存在 `data-changes/confirm`、`pageDataApi`、page-data domain/revision/publisher/dirty-domain 运行时引用。
- 前端页面直接调用业务 API，账户、选项、统计、授权、审计和使用记录相关回归通过。
- Node 后端和 Go 后端不再初始化、发布、恢复或存储 page-data change。
- package scripts、smoke、benchmark、测试和当前文档入口无已退场命令。
- `pnpm typecheck`、`pnpm lint`、`pnpm build`、Node 相关回归和 `go test ./...` 通过。
- 浏览器验证 `/my-accounts` 不发 confirm，只发实际业务请求；控制台无错误。
- 合并最新 master 后复验并推送 `origin/master`；不部署。
