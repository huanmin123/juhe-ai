# 授权用量渐进加载设计

## 1. 背景与现状

团队消耗明细和用户消耗明细已经只读取后台预聚合的最近 31 天范围窗口，分页也使用 `pageSize + 1` 与 1001 行上界；筛选 options 已在下拉展开或搜索时按需加载。当前剩余问题集中在一次 overview 请求仍同步完成两类职责：

- 读取当前页窗口行并补齐团队、用户、成员关系、资源和资源归属人名称；
- 读取同一 scope、日期范围和筛选条件下的汇总窗口行，再把 `summary`、`teamCount/userCount` 与分页 rows 一起返回。

因此 rows 必须等待 summary，桌面翻页和移动端 load-more 也会重复读取完全相同的 summary。用户用量当前页还需系统账户、团队、成员关系、资源和归属人多组 lookup。两个页面另有 `loadOptions/optionsLoaded/optionsLoading/loadOptionsNow` 死入口：页面从未调用它们，真实 options 已由各下拉事件独立懒加载。

本设计承接 [全站页面 API 按需加载审计报告](../../reports/全站页面API按需加载审计报告-2026-07-20.md) 的剩余 P1/P2，只定义 Node/Vue 的新契约与验收边界；必须在用户确认后实施。

## 2. 目标

- 将团队/用户授权用量拆为独立 rows 与 summary 契约，使当前页 rows 不等待 summary。
- 保留现有管理端和个人端权限、日期范围、预聚合窗口、分页上界及筛选语义。
- rows DTO 只返回当前页面真实展示或跳转所需字段，删除兼容别名和未使用状态字段。
- 同一 scope/range/filter signature 下，桌面分页和移动端 load-more 只请求 rows，不重复请求 summary。
- 当前页 lookup 只接收当前页 ID，并在依赖允许时并行执行；禁止全量读取和 N+1。
- 删除未被调用的聚合 options loader，保留各下拉现有首次展开/搜索加载。
- SQLite 同步、SQLite read worker 和 PostgreSQL 保持字段、排序、权限、空态和错误语义一致。
- Vue 用签名与请求代次隔离 rows、summary 和 options，迟到响应不得污染新 scope 或筛选条件。

## 3. 范围与非目标

本批只修改 Node 后端、Vue 前端、专项测试和权威文档；不修改 `backend-go/`，不提交、不推送、不部署、不触碰生产。

本批不做：

- 不修改 `usage_records`、授权日报表、授权范围窗口表或任何数据库 schema。
- 不在 HTTP 请求路径执行 `SUM`、`GROUP BY` 或回扫原始使用记录；rows 和 summary 都继续只读现有 range windows。
- 不改变 stats worker 的聚合、刷新周期、范围窗口发布或授权额度语义。
- 不改变日期默认值、最大 31 天、资源/团队/用户筛选口径和 1001 行分页上界。
- 不把当前页 lookup 移到前端，也不新增 Redis/长 TTL 缓存掩盖查询。
- 不预加载筛选 options；各 options 仍只在对应下拉首次展开、搜索或已选项补齐时读取。

## 4. HTTP 与 DTO 分层

### 4.1 Rows 路由

现有四条详情路由保留 URL，但响应改为 rows-only：

- 管理端：`GET /authorizations/usage/team-details`
- 个人端：`GET /my-authorizations/usage/team-details`
- 管理端：`GET /authorizations/usage/user-details`
- 个人端：`GET /my-authorizations/usage/user-details`

团队 rows 响应：

```ts
interface AuthorizationTeamUsageRowsResult {
  range: AccountUsageStatsRange
  rows: AuthorizationTeamUsageRow[]
  total: number
  page: number
  pageSize: number
  hasMore: boolean
}

interface AuthorizationTeamUsageRow {
  id: string
  teamId: string
  teamName: string
  resourceType: ResourceAuthorizationResourceType
  resourceId: string
  resourceName: string
  resourceOwnerSystemAccountId?: string
  resourceOwnerSystemAccountName?: string
  usage: AccountUsageSummary
  lastUsedAt?: string
}
```

用户 rows 响应：

```ts
interface AuthorizationUserUsageRowsResult {
  range: AccountUsageStatsRange
  rows: AuthorizationUserUsageRow[]
  total: number
  page: number
  pageSize: number
  hasMore: boolean
}

interface AuthorizationUserUsageRow {
  id: string
  systemAccountId: string
  userName: string
  username?: string
  teamNames: string[]
  resourceType: ResourceAuthorizationResourceType
  resourceId: string
  resourceName: string
  resourceOwnerSystemAccountId?: string
  resourceOwnerSystemAccountName?: string
  usage: AccountUsageSummary
  lastUsedAt?: string
}
```

`resourceType/resourceId/resourceName` 对有效 detail window 行为必填；找不到当前业务资源时 `resourceName` 返回空字符串，不能伪造旧 `accountName`。团队行删除页面未使用的 `status/accountId/accountName`，用户行删除未使用的 `accountId/accountName/sourceLabels`。`teamNames` 保留为真实展示字段：指定团队筛选时返回该团队名称，未指定团队时返回该用户当前有效团队名称集合。

rows 响应不再包含 `summary/teamCount/userCount`。`total` 继续是现有分页上界，不宣称精确全量；是否还有更多只认 `hasMore`。

### 4.2 Summary 路由

新增四条独立 summary 路由：

- 管理端：`GET /authorizations/usage/team-summary`
- 个人端：`GET /my-authorizations/usage/team-summary`
- 管理端：`GET /authorizations/usage/user-summary`
- 个人端：`GET /my-authorizations/usage/user-summary`

两类响应使用相同窄 DTO：

```ts
interface AuthorizationUsageSummaryResult {
  range: AccountUsageStatsRange
  summary: AccountUsageSummary
}
```

summary 接受与对应 rows 相同的 `systemAccountId/startDate/endDate/resourceType/resourceId/teamId/granteeSystemAccountId` 规范化参数，但不接受 `page/pageSize`。团队 summary 忽略/拒绝不适用的 `granteeSystemAccountId` 应由严格 schema 固定一种行为，推荐严格拒绝，避免缓存键和实际口径不一致。summary 只按精确窗口主键读取一条预聚合行；不存在时返回同范围的零值 summary，不执行明细聚合。

首个统计卡的“已加载团队/用户”由当前 rows 已加载数量和 `hasMore` 计算，不再把分页上界伪装成独立 summary 计数。请求、Token、成本和最后使用时间只来自 summary endpoint。

### 4.3 Scope/range/filter signature

前端为每一种 rows/summary 请求构造同一份规范化业务签名，分页不进入该签名：

```ts
type AuthorizationUsageQuerySignature = {
  kind: 'team' | 'user'
  accessMode: 'admin' | 'self'
  viewerId: string
  role: string
  authRevision: number
  effectiveOwnerSystemAccountId: string
  startDate: string
  endDate: string
  resourceType: 'all' | 'account' | 'group'
  resourceId: string
  teamId: string
  granteeSystemAccountId: string
}
```

- 值必须 trim、默认值归一化后再序列化；disabled resource group 下的 `resourceId` 必须归一为空。
- `page/pageSize` 只属于 rows request key，不属于业务 summary signature。
- viewer、role 和 auth revision 用于前端提交与缓存隔离；HTTP 仍由服务端 session/access scope 决定真实权限。
- 管理端有效 owner scope 与个人端强制 self scope 必须进入签名，不能只比较 URL query。
- 日期控件展示值必须先按后端实际 `range` 同步；后端返回范围与当前 intent 不符时不得提交。

## 5. Node 查询与 lookup 边界

### 5.1 Rows

团队/用户 rows 继续先从对应 `authorization_*_usage_range_windows` 读取 `pageSize + 1` 条，显式投影组成 `usage` 与稳定排序所需字段，不读取 summary window 行。

当前页 lookup 只使用 `takePageRows()` 后的 ID：

- 团队 rows：团队 lookup 与资源 lookup 并行；资源 lookup 完成后，再按本页唯一 owner IDs 批量读取归属人名称。
- 用户 rows：系统账户 principal、筛选团队、有效团队成员关系和资源 lookup 四组并行；资源 lookup 完成后，再批量读取本页归属人名称。
- 账户资源与分组资源 lookup 可在 repository lookup 内按各自 ID 集合并行；每组必须去重、分块并复用既有 read-through cache。
- SQLite 同步路径按相同依赖顺序执行固定批量查询；read worker 在一个 operation 内完成 rows 和本页 lookup，不能逐行 RPC。
- PostgreSQL 用 `Promise.all` 并行独立 lookup；任一必需 lookup 失败时整次 rows 失败，不能返回混合新旧名称。

查询次数只与固定 lookup 类别有关，不随 pageSize 增长；禁止在 row mapper 内查库、拉全量团队/账户/资源或回扫使用记录。

### 5.2 Summary

summary repository 只复用规范化的 access/range/filter key，并按完整主键从对应范围窗口表读取一行：

- team：`system_account_id + start_date + end_date + team_filter_id + resource_filter_type + resource_filter_id`；
- user：在上述键上增加 `grantee_filter_system_account_id`。

SQLite、worker 和 PostgreSQL 都使用显式 usage 列，不使用 `SELECT *`。summary 不执行任何团队、用户、成员、资源或归属人 lookup，也不接收分页参数。

### 5.3 Worker 与 PostgreSQL

- 将现有 overview read operation 拆为 team/user rows 与 team/user summary 四类只读 operation，或等价的严格 discriminator；worker 响应必须与主线程 DTO 逐字段一致。
- PostgreSQL 表名继续通过 dialect qualification，金额字段继续显式转换为 number，排序、空值、limit/offset 与 SQLite 一致。
- 真实 PostgreSQL smoke 必须创建/刷新可识别的团队、用户、资源和 summary window fixture，实际运行四类 admin/self 路由；缺少 PG 配置只能记录未验证，SKIP 不算通过。

## 6. Vue 数据流与竞态

### 6.1 首屏与筛选变化

首次进入或 signature 改变时，rows 与 summary 并行发出：

- rows 成功即可渲染列表并同步实际 range；不等待 summary。
- summary 使用独立 `loading/error/value`，成功后更新卡片；失败只影响卡片并提供重试，不清空已成功 rows。
- rows 失败不能让旧 signature 的 summary 显示在新筛选上；新 signature 建立时先隔离旧值，可保留视觉 stale 状态但必须明确 refreshing，不能当作新值。
- summary 重试只重发 summary；rows 重试只重发当前页 rows。

### 6.2 分页、load-more 与刷新

- 桌面换页、页大小变化和移动端 load-more 只请求 rows；只要 signature 未变，summary 请求数保持不变。
- 移动端追加必须验证 signature 和请求代次，旧筛选的下一页不能追加到新列表。
- 下拉筛选、资源归属人、日期、路由 query 或 admin/self scope 改变时重置分页并创建新 signature，再并行请求第一页 rows 与 summary。
- 显式页面刷新/下拉刷新可以同时强制刷新 rows 与 summary；普通分页和 load-more 不得借 `force` 重取 summary。
- 页面状态缓存只保存筛选、日期和分页，不持久化跨身份 summary；cache version 随 DTO 拆分提升。

rows 与 summary 各自维护 generation，提交时同时核对 generation、signature、当前 route 和身份 revision。A→B、A→B→A、管理/个人路由切换、目标 owner 切换、日期变化、卸载和登出后的迟到成功/失败均不能覆盖当前数据、loading 或错误。

### 6.3 Options 死入口删除

删除两个页面未被调用的 `optionsLoaded/optionsLoading/loadOptions/loadOptionsNow` 及其聚合错误提示。保留并验证：

- 团队、被授权用户、资源归属人和授权资源各自的 dropdown/search handler；
- selected ID 缺少 label 时的按需补齐；
- scope 或资源类型变化时只重置相关搜索窗口，不主动拉取全部 options；
- 删除 `forceOptions` 这类只为死聚合 loader 遗留的参数，除非仍有独立、可证明的现用职责。

## 7. 权限与错误语义

- 管理 routes 继续要求 admin，并由 `getRequestAccessScope(systemAccountId)` 校验全局/指定 owner；普通用户访问管理 URL 返回 403。
- 个人 routes 继续由 self 挂载强制当前登录用户，伪造 `systemAccountId` 不能扩大范围。
- rows 与 summary 必须使用同一个 access/range/filter 规范化 helper；不能出现 rows 按 self、summary 按 global 或反向串 scope。
- 无权 scope、无有效 owner 或不存在窗口时沿用现有空结果语义；非法日期、筛选形状和分页参数返回 400。
- summary 与 rows 的失败独立传播；不得吞掉数据库错误后用零值伪装成功。
- 接口不返回凭据、授权 limits、原始使用记录或未展示的用户/团队资料。

## 8. 测试与验收

### 8.1 Node HTTP、DTO 与查询

- 四条 rows 路由的 admin/self 权限、参数、分页上界、稳定排序、`hasMore` 和空态。
- team/user row 精确字段白名单；确认删除 `status/accountId/accountName/sourceLabels/summary/teamCount/userCount` 等字段。
- 四条 summary 路由只返回 `range/summary`，不接收分页，不执行 lookup；零窗口返回零 summary。
- 同一 scope/range/filter 下 rows 与 summary 数值口径一致；管理 owner、self、team、grantee、resource type/id 和日期组合不串 scope。
- Query guard 证明 rows 不读取 summary row、不回扫 `usage_records`，summary 不读取 detail rows/lookup 表；lookup 只含当前页 IDs、固定批量、无 N+1。
- PostgreSQL 独立 lookup 实际并行，错误完整传播；SQLite 同步/read worker/PostgreSQL 逐字段一致。

### 8.2 Worker 与 PostgreSQL

- 四类 read worker operation 的请求/响应、未知 discriminator、数据库错误、空页和 summary 零值回归。
- read worker 一次 rows operation 内完成固定批量 lookup，不逐行跨线程请求。
- 真实 PostgreSQL smoke 覆盖金额转换、排序、分页、团队名称、用户 principal、teamNames、资源与 owner lookup、summary 精确窗口键和权限；SKIP 不计通过。
- 既有授权用量分页、范围窗口刷新、background worker performance、repository lookup cache 和 1001 行页码门禁继续通过。

### 8.3 前端

- 首屏 rows/summary 并行；rows 先完成时立即展示，summary 迟到不阻塞表格。
- 桌面第 2 页、pageSize 变化和连续 mobile load-more 均不重取 summary；signature 改变才各发一次新 rows/summary。
- rows/summary 分别失败、分别重试，不清空对方成功数据；summary 卡片区分 loading、error、零值。
- A→B、A→B→A、路由 query、owner scope、日期、admin/self、身份 revision、卸载迟到均不污染当前数据或 loading。
- options 首屏请求仍为 0；首次展开、搜索与 selected label 补齐按需工作；源码/行为测试证明死聚合 loader 已删除。
- 团队跳转用户明细仍携带 team、resource、owner 和日期；用户页 `teamNames` 展示不回归。

### 8.4 门禁与复核

- Node/前端专项回归、后端 typecheck、可运行范围内的前端 typecheck/build、`git diff --check`。
- 浏览器 Network 验证首屏并行、分页/load-more 不重取 summary、筛选切换与失败重试；Browser/Playwright 不可用时记录环境限制。
- 至少两名只读 Agent 分别复核权限/查询/worker/PG 与前端签名/竞态/options，交叉质疑并闭合高严重度问题。

## 9. 完成标准

- 授权团队/用户 rows 与 summary 已成为独立 Node/Vue 契约，rows 可以先显示。
- rows DTO 只包含当前展示/跳转字段；summary 只读一条预聚合窗口，不再随分页重复请求。
- 当前页 lookup 有界、按依赖并行且无 N+1，SQLite worker 与 PostgreSQL 等价。
- 分页/load-more、signature 变化、身份/scope 和关键竞态均有行为证据。
- 死 options loader 已删除，现有下拉按需加载不回归。
- 专项、既有回归、真实 PostgreSQL及可用前端/浏览器门禁全部闭合后，才可标记完成。
