# 页面数据版本确认与条件读取设计

## 1. 背景与目标

当前页面缓存协议已经具备 IndexedDB、30 秒可见页确认、`unchanged / delta / reload / reset`、跨标签页协调和写后失效，但一次真实 `/my-accounts` 页面刷新仍会产生五次 `POST /data-changes/confirm`：

1. `providers.catalog` 前置确认。
2. `accounts.options` 前置确认。
3. `accounts.static` 前置确认。
4. tags GET 后的稳定性确认。
5. accounts GET 后的稳定性确认。

前三次在约 25ms 内启动，却因现有合批仅覆盖同一微任务和同一 confirm 函数上下文而没有合并。生产浏览器复用 HTTP/2 连接后，五次 confirm 的 TTFB 仍约为 `297 / 330 / 321 / 530 / 348ms`；真实 Redis store benchmark 的 confirm p95 仅约 `5-7ms`。主要成本来自每个独立 HTTP 都重复经过公网入口、server 到 DB service 代理、IP 限流、PostgreSQL session 鉴权、用户限流和 Redis，而不是 revision 计算本身。

本设计采用两层混合协议：

- 页面级协调器负责缓存展示、数据域收集、批量 confirm、跨标签页 singleflight 和 mutation fencing。
- 业务 GET 逐域升级为 revision-bearing read，在返回数据时同时返回可验证的 snapshot token，从而删除 GET 后的独立 confirm。

目标如下：

- 30 秒内热缓存立即显示，不等待网络。
- 同一安全上下文的页面激活或周期确认最多一个 confirm HTTP。
- 长期在 transactional-read domain 上实现冷启动零 confirm；本分支 v2 冷启动保留页面级 pre/post 稳定性批次。
- 变化域只读取受影响资源，不重复读取 unchanged 域。
- 业务 GET 与返回 token 必须有明确的一致性证明，禁止把 Redis 当前 token 直接拼到任意数据库结果上。
- 写成功后立即失效、patch 或按最低提交水位重读；mutation 前的迟到响应不得推进 `confirmedAt`。
- 允许 Node standalone、Node performance 和后续 Go 按能力渐进迁移，未迁移域继续使用现有协议。

## 2. 范围与非目标

### 2.1 本次范围

- 新增页面级 `PageDataActivationCoordinator`，首批接入 `/my-accounts`。
- 将 `accounts.static`、`accounts.options`、`providers.catalog` 作为 `/my-accounts` 的显式页面依赖。
- 保留现有 `/data-changes/confirm` HTTP 契约，并将其调用方式从资源级调整为页面级聚合。
- 维持 protocol v2、既有 DTO 和既有 Node / Go confirm 契约；本次不让 GET 返回 revision metadata。
- 按 activation 统一管理 pre-confirm、必要的 post-confirm、页面 lifecycle 和请求预算。
- 新增页面级 `writeEpoch` 围栏，防止 mutation、scope 切换或页面失活前的迟到 confirm / GET 覆盖新缓存。
- 修正 `/data-changes/confirm` 在 System API rate limiter 被按 HTTP POST 错分到 write bucket 的问题；它继续保留 PostgreSQL session 权威鉴权且不 touch session。
- 增加单标签请求数、冷启动、token 冲突、mutation 交错、KeepAlive 和限流分类回归。

### 2.2 非目标

- 不删除 `/data-changes/confirm`。
- 不把 confirm 改造成返回任意业务 DTO 的聚合接口。
- 不引入 WebSocket、SSE、长轮询、Kafka 或新的分布式协调系统。
- 不让 Redis、IndexedDB 或浏览器 leader 成为业务事实源或正确性单点。
- 不要求未迁移页面一次性切换协议。
- 不在本任务中执行生产部署、生产数据迁移或流量切换。

### 2.3 延期范围与准入门槛

以下内容保留为后续阶段设计，不在本分支实现：

- revision-bearing GET v3、`pageData` 响应 metadata、ETag、`200 unchanged`、304、delta/reset 的 GET transport。
- PostgreSQL / SQLite fact revision、事务内 outbox、Redis mirror watermark、`commitRevision`、`X-Min-Page-Data-Revision` 与 `revision_not_visible`。
- Go v3 handler、schema migration、全站 manifest、跨标签页 activation 聚合消息和 SSE。

只有某个 domain 同时满足以下条件，才允许进入 `transactional-read`：

1. 业务事实、domain fact revision 和 outbox 在同一写事务提交。
2. GET 在同一只读快照中读取业务数据和 fact revision；PostgreSQL 使用 `REPEATABLE READ READ ONLY`，SQLite 使用独立 deferred read snapshot。
3. revision publisher 落后、dirty、epoch/reset、日志缺口或未决 outbox 时 fail closed，不能签发 stable token。
4. 写入路径、授权 owner 解析和后台写路径已完整覆盖，且通过真实隔离 PostgreSQL / Redis 崩溃恢复与并发测试。

在上述门槛完成前，GET 不得把当前 Redis token 拼接到数据库 DTO 上，也不得标记为 `transactional`。

## 3. 核心决策

### 3.1 长期形态

```text
PageDataActivationCoordinator
  |
  +-- 热缓存 / 周期校验
  |     +-- 一次 aggregate confirm
  |            +-- unchanged -> touch cache
  |            +-- delta -> 原子 patch
  |            +-- reload/reset -> 只 GET 变化资源
  |
  +-- 冷启动 / 无 token（阶段 1）
  |     +-- 一次 aggregate pre-confirm
  |     +-- 并行业务 GET
  |     +-- 一次 aggregate post-confirm
  |            +-- baseline 与 post token 相同才写 confirmed
  |
  +-- mutation
        +-- writeEpoch fencing
        +-- affectedDomains + commitRevision
        +-- patch 或带 minimum revision 的 GET
```

页面级协调器是长期控制面。具体数据域可以选择两种 transport：

- 未迁移域：aggregate confirm + 现有业务 GET + 必要稳定性回退。
- 已迁移域：aggregate confirm 只判断是否需要读取；业务 GET 自身返回 snapshot token，不再额外 post-confirm。

本次仅实现第一种 transport。冷启动“直接 GET、零 confirm”只属于已完成 transactional-read 的后续目标；在 v2 下跳过 pre-confirm 会失去 GET 期间并发写的稳定性证明，不能以性能为由提前采用。

### 3.2 为什么不采用单一方案

只使用条件 GET 会让一个页面的多个数据域分别经过完整 HTTP 鉴权和限流，热缓存 unchanged 时请求数可能高于一次 aggregate confirm。只使用页面级 confirm 又无法独立证明多个冷启动 GET 在并发写期间取得了同一稳定事实。SSE 只能提供变化提示，不能证明缓存稳定，并会占用当前通用 DB service HTTP 代理的长连接槽位。

因此采用：

1. aggregate confirm 保留并升级为页面级控制面。
2. GET 逐域获得 snapshot token 能力。
3. SSE 只在未来出现数秒级跨会话可见性 SLO、且具备独立长连接通道时重新评估。

## 4. 页面级激活协调器

### 4.1 页面依赖清单

页面不能只依靠领域 registry 的 route 反向匹配推断依赖。首批建立显式 manifest：

```ts
interface PageDataActivationManifest {
  route: string
  domains: PageDataDomain[]
}

const myAccountsManifest = {
  route: '/my-accounts',
  domains: ['accounts.static', 'accounts.options', 'providers.catalog']
}
```

`accounts.runtime` 继续使用现有 status snapshot 轮询，不因 registry 中出现 `/my-accounts` 就自动加入静态 confirm。

### 4.2 阶段 1 激活和收集窗口

- Vue 页面 mount、KeepAlive activate、重新可见和聚焦创建 activation。
- manifest 先同步登记核心域，resource controller 可以在首次 load 前补充动态域。
- 初始收集窗口为 `50ms`，覆盖已观察到的 25ms 启动差。
- 收集窗口不能阻塞 30 秒内热缓存的展示。
- batch 发出后集合封闭；迟到资源保持 unconfirmed，不能为满足请求数目标猜测 token，也不在同一 activation 再开常规 batch。
- mutation 可提前结束收集窗口并触发高优先级 batch。

阶段 1 只在同一标签页汇总。既有 `BroadcastChannel` 按资源键的 leader 交接继续保留；跨标签页 activation 聚合是后续优化，不能把 `handled=true` 当作 follower 已获得共享 DTO 的证明。

### 4.3 安全上下文

协调 key 至少包含：

```text
viewerSystemAccountId
+ role / permission generation
+ session generation
+ viewScope
+ targetSystemAccountId
```

- 不同安全上下文不得共享 token、delta、缓存记录或 batch。
- 同一 domain、同一 token 可以去重。
- 同一 domain、不同 token 不得取最低 sequence、最高 sequence或 `null` 作为共同基线。
- v2 尚不支持 multi-cursor 时，冲突 cursor 保持 unconfirmed，不自动拆分第二个 activation confirm。

### 4.4 请求预算

| 场景 | 预算 |
| --- | --- |
| 30 秒内热缓存 | 0 个阻塞请求；到周期点最多 1 个后台 confirm |
| 过期缓存且有 baseline | 最多 1 个 aggregate confirm；changed 域再 GET |
| 冷启动或 token 缺失（v2） | 1 个 aggregate pre-confirm + 并行 GET + 最多 1 个 aggregate post-confirm |
| 冷启动或 token 缺失（transactional-read，后续） | 0 个 confirm，直接 GET |
| 单次页面激活 | 热缓存最多 1 个常规 confirm；需要稳定读取时最多 pre/post 两个批次 |
| mutation burst | 额外最多 1 个高优先级 confirm，连续写使用 10-20ms 合并窗口 |
| hidden / deactivated | 0 个周期 confirm |

“冷启动固定只有一次 confirm”不是正确性目标。v2 冷启动必须使用 pre/post 批次获得稳定证明；无法参加 post batch、confirm 失败、token 冲突或页面失活的结果可展示但必须保持 unconfirmed，不能直接写成 stable。

## 5. Revision-Bearing GET v3

### 5.1 请求契约

新客户端显式声明能力：

```http
GET /__aisys__/api/my-accounts?page=1&pageSize=20
X-Page-Data-Protocol: 3
X-Page-Data-Token: <opaque-or-encoded-token>
X-Page-Data-Accept: unchanged,delta,reset
X-Min-Page-Data-Revision: <optional-mutation-fence>
```

第一阶段不依赖真实 HTTP 304，仍使用 `200` 和响应元数据表达 `unchanged`。完整代理链验证条件头、304、浏览器和 axios 行为后，再启用：

```http
If-None-Match: W/"pd3-<validator>"
```

### 5.2 响应契约

旧客户端继续读取原有 `data`。v3 响应增加可选 `pageData`：

```json
{
  "data": {
    "items": [],
    "page": 1,
    "pageSize": 20
  },
  "pageData": {
    "protocolVersion": 3,
    "domain": "accounts.static",
    "mode": "full",
    "token": {
      "epoch": "opaque",
      "scope": "opaque",
      "sequence": 42,
      "resetSequence": 3
    },
    "representation": "opaque-query-and-schema-hash",
    "cacheable": true,
    "stability": "transactional",
    "serverTime": "2026-07-21T00:00:00.000Z"
  }
}
```

`mode` 取值：

- `full`：完整结果，可原子替换精确缓存键。
- `unchanged`：业务 DTO 可省略，客户端只 touch 当前精确 token。
- `delta`：只包含安全字段投影，必须精确匹配 base token。
- `reset`：返回完整结果并替换旧缓存，或要求客户端无条件重读。

`stability` 取值：

- `transactional`：数据和 revision 来自同一事实快照，可以写为 confirmed。
- `checked`：使用现有 revision 前后校验，只能按兼容策略写入；出现 dirty 或缺口时禁止 cache。
- `unavailable`：数据可展示，但不能推进 `confirmedAt`。

### 5.3 表示身份

ETag 和 representation hash 必须绑定：

```text
viewer + permission generation
+ viewScope + targetSystemAccountId
+ domain
+ route + normalized query + sort + page + filters
+ DTO/schema version
+ fact revision + reset revision
```

服务端根据已鉴权上下文生成 scope；客户端 token 只能作为匹配基线，不能决定身份或权限。

## 6. 数据与 Revision 一致性

### 6.1 硬门槛

禁止直接执行：

```text
业务数据库 loader 返回 data
+ 当前 Redis confirm token
= cacheable snapshot
```

这可能形成旧数据配新 token，后续长期返回 unchanged。任何域只有满足以下一种证明，才能标记 `stability=transactional`：

1. 数据和 domain fact revision 在同一 PostgreSQL / SQLite 事务快照中读取。
2. Redis 运行态数据和 revision 在同一个 Lua / MULTI 原子操作中读取。
3. 投影携带已应用的持久 outbox watermark，且服务端证明不存在 dirty、缺口或未决提交。

### 6.2 PostgreSQL 事实 revision

performance 模式新增持久事实 revision 与 outbox 契约：

```text
业务 mutation transaction
  -> 写业务事实
  -> 推进受影响 domain/scope fact revision
  -> 写 page-data outbox(eventId, factRevision, event)
  -> commit

outbox publisher
  -> 按 factRevision 镜像到 state Redis
  -> 成功后确认 outbox
```

业务 GET 在同一只读数据库快照中读取：

```text
factRevisionBefore
+ business rows
+ factRevisionAfter
```

同一事务快照内 revision 必然一致；响应 token 使用该 fact revision。Redis 只承担 aggregate confirm、delta 日志和快速镜像，不为 PostgreSQL GET 单独签发事实 token。

具体表名、scope 粒度和 transaction port 在实施细节阶段根据现有 repository transaction API 固定；设计要求是同事务事实，不要求 route 层手工拼接 SQL。

### 6.3 Standalone 与未迁移域

- Node standalone 继续使用现有 SQLite outbox / dirty generation / memory-IPC confirm。
- 未建立同事务 fact revision 的 standalone GET 不声称 `transactional`。
- 可以使用当前 pre-confirm + GET + post-confirm 的语义，但两个 confirm 应下沉到同一个 HTTP 处理链，避免重复公网往返。
- 无法证明连续性、owner 重启、epoch 变化或 dirty recovery 未完成时返回 `cacheable=false` 或 `reset`。
- Go 长期只实现 PostgreSQL + Redis 的 transactional 路径。

## 7. Delta、Reset 与稳定写入

### 7.1 Delta

只有以下条件全部满足才允许 delta：

- base token 精确匹配。
- 事件日志连续且协议版本已知。
- 权限、scope、representation 和 schema 未变化。
- 变化不影响成员、排序、筛选、分页或总数。
- 客户端可在一个 IndexedDB 事务内完成 base CAS、patch、token 更新和 `confirmedAt` 更新。

任何 CAS 失败、未知字段、日志缺口或 projection 失败都回退 full/reset。

### 7.2 Reset

以下情况必须 reset 或无条件重读：

- epoch / resetSequence 变化。
- mutation 影响权限、成员、筛选、排序、分页或 owner scope。
- outbox / Redis 镜像出现缺口或 dirty。
- schema、representation hash 或权限 generation 不匹配。
- 旧 token 无法解析或来自未支持协议版本。

## 8. Mutation Commit Fence

写请求成功响应增加：

```json
{
  "data": {},
  "pageData": {
    "affectedDomains": ["accounts.static", "accounts.options"],
    "commitRevision": "opaque-minimum-revision"
  }
}
```

前端处理顺序：

1. mutation 发起时递增相关 domain 的 `writeEpoch` 和 generation。
2. 写成功后立即 patch 可安全确定的数据，或失效对应 IndexedDB domain。
3. 广播 domain invalidation；其他标签页只标 dirty，不在隐藏状态立即拉取。
4. mutation 前发出的 confirm、GET 或 delta 即使返回 unchanged，也必须因 `writeEpoch` 不匹配而丢弃。
5. 不能 patch 的可见资源发 GET，并携带 `X-Min-Page-Data-Revision`。
6. 服务端尚未能读取到最低提交水位时返回明确的 `revision_not_visible`，客户端有界退避，不接受旧结果。

写结果不确定时保持 dirty，不伪造成功或稳定。

## 9. 跨标签页协议

- 正常情况下由 BroadcastChannel leader 汇总相同安全上下文的 activation intent。
- intent 至少包含 `activationId / requestId / scopeFingerprint / route / domains / deadline / leaderEpoch`。
- follower 只应用自己登记的 domain/cursor 结果。
- 结果必须校验 `requestId + leaderEpoch + scopeFingerprint`。
- leader 在请求发出后退出时允许重复请求；正确性不依赖严格 exactly-once。
- BroadcastChannel 不可用时每标签页独立确认，仍保持 scope、generation 和 token 门禁。
- IndexedDB 降级为标签页内存后，leader 的 handled 响应不能自动证明 follower 已获得 DTO；follower 读取不到共享记录时必须自行校验。

## 10. 错误与降级

| 情况 | 行为 |
| --- | --- |
| `401/403` | 停止应用结果，清理对应身份/权限 scope 缓存 |
| session / PG 鉴权基础设施失败 | 返回 `503`，不能伪装成未登录 |
| `429/503` | 遵循 `Retry-After`，不更新 `confirmedAt` |
| 网络超时 | 保留可展示旧缓存，保持 unconfirmed |
| revision 不可用但业务数据可读 | 返回 full + `cacheable=false` |
| delta 基线错误 / 日志缺口 | reset |
| mutation minimum revision 尚不可见 | `409 revision_not_visible`，有界重试 |
| generation / writeEpoch 不匹配 | 丢弃迟到响应 |
| 连续写导致稳定读取耗尽 | 返回可展示但不可缓存的 full，不循环重试 |

confirm 默认超时保持有界；同 activation 内不自动无界重试。失败恢复在下一周期、重新激活或用户显式刷新时进行。

## 11. 限流与鉴权语义

- `/data-changes/confirm` 在 DB access 和 System API 限流中都属于 read，不因 HTTP POST 自动进入 write bucket。
- confirm 保留 PostgreSQL session 权威鉴权，不改为 `noDb`。
- 页面级合并的主要收益是减少重复公网、代理、鉴权和限流次数，不以绕过安全中间件换性能。
- revision-bearing GET 继续经过现有 read 限流。
- 需要新增 Server-Timing：至少拆分 `server-proxy / ip-rate-limit / session-auth / user-rate-limit / page-data-revision / business-load / serialize`。

## 12. 分阶段迁移

### 阶段 1：页面级 confirm

- 新增 `/my-accounts` manifest 和 activation coordinator。
- 复用现有 confirm 请求体，将三个前置 confirm 合并为一个。
- v2 冷启动使用一个 aggregate pre-confirm、并行 GET 和至多一个 aggregate post-confirm；只有 post token 与对应 baseline 完全相同才写 confirmed。
- 热缓存确认时间仍在 30 秒内时直接展示，不新开 activation confirm；首次生命周期 tick 在下个 30 秒周期执行。
- 同域 token 冲突、late registration、post deadline、confirm 失败、deactivate 或 writeEpoch 变化时保持 unconfirmed，禁止补开第二个常规 batch。
- 本次只在单标签页聚合；现有按资源键的 BroadcastChannel leader 行为保持，跨标签页 activation 消息延期。
- 修正 POST confirm 在 System API rate limiter 中被归类为 write 的问题。
- 新增单标签请求数与竞态回归；Server-Timing 先只增加 confirm read limiter / DB service 可测分段，不承诺网络代理全链路细分。

目标：当前 `5 confirm` 降为热路径 `0-1`，需要稳定读取时最多 `1 个前置 + 1 个后置批次`；协议保持 v2，数据表、PostgreSQL outbox 和 Go 不改。

### 阶段 2：Revision-Bearing GET

- 建立按域能力表：`confirm-only / checked-read / transactional-read`。
- PostgreSQL 建立事实 revision/outbox transaction port。
- 首批迁移 `accounts.static` 和 `accounts.options`。
- 先 shadow 比较 GET snapshot token 与 aggregate confirm，不改变客户端缓存结论。
- mismatch、dirty、epoch 变化、日志缺口或 outbox backlog 时自动关闭 transactional-read 并 reset。
- shadow 稳定后灰度启用 GET 返回 token，删除对应后置 confirm。

目标：变化资源每个只需一次 GET；冷启动零 confirm。

### 阶段 3：条件读取与扩域

- 验证 Edge / WireGuard / Caddy / Nginx / server / DB service 对条件头和 304 的完整行为。
- 先启用 `200 unchanged`，再按 endpoint 启用真正 304。
- 迁移 `providers.catalog` 和其他高收益静态域。
- 未迁移域继续使用 aggregate confirm。

## 13. 可观测性

新增有界指标和日志字段：

- `pageDataActivationId`
- `pageDataRequestId`
- `viewScope`
- `domainCount`
- `cursorCount`
- `batchWindowMs`
- `confirmActionCounts`

- Server-Timing 分段。

## 14. 测试与验收

### 14.1 前端

- `/my-accounts` 三域在真实异步启动差下只产生一个 activation confirm。
- 30 秒内缓存立即显示，confirm 不阻塞首屏。
- hidden / deactivated 页面不发周期 confirm，重新激活只发一次。
- 同域同 token 去重，不同 token 不错误合并。
- mutation 前在途结果不能 touch 或覆盖 mutation 后缓存。
- 多标签 leader 正常只发一次；leader 退出、BroadcastChannel/IndexedDB 不可用时安全降级。
- 冷启动、过期缓存、confirm 失败和 revision-bearing GET 各自遵守请求预算。

### 14.2 本分支后端

- confirm 在 DB access 和 rate limiter 中均为 read。
- 单 batch 多域仍为一次 Redis EVAL，不查询业务明细库。
- 既有 dirty、epoch/reset、日志断档和未知版本语义不回退。
- 保持 protocol v2、原 DTO、现有 Node/Go confirm 夹具和无业务库 confirm 边界。

### 14.3 后续 transactional-read 门禁

- transactional GET 的数据与 fact revision 来自同一数据库快照。
- mutation、fact revision 和 outbox 在同一事务；发布失败、进程退出和恢复后不能返回假 unchanged。
- Redis 镜像落后、dirty、epoch/reset、日志断档和未知版本均安全 reset。
- `X-Min-Page-Data-Revision` 不可见时不返回旧稳定结果。
- 旧客户端忽略 `pageData` 后保持原 DTO 和权限行为。

### 14.4 本分支真实环境

- SQLite 可重建测试环境完成兼容回归。
- 使用隔离 PostgreSQL session / Redis namespace 完成三域一次 EVAL、scope、epoch/reset、dirty recovery 和完整鉴权/限流 HTTP smoke；本分支不新增数据库表。
- 浏览器验证 `/my-accounts` 冷启动、热缓存、过期缓存、写后刷新和多标签页瀑布。
- 生产只读路径不在本任务中发布；最终上线等待用户单独通知。

### 14.5 本分支完成门禁

- 当前页面的五次 confirm 在目标场景下降到设计预算。
- 没有出现 token 冲突合并、mutation 后迟到响应写回、scope 复用或冷启动假 confirmed。
- 前后端专项回归、typecheck、lint、build、Go 测试和 `git diff --check` 通过。
- 真实 Redis/PG session 隔离 smoke 通过并完成精确清理。
- 文档、v2 夹具、Node/Go 边界和回滚说明同步。

## 15. 回滚

- 所有新能力按 endpoint/domain feature capability 启用，不要求前后端原子切换。
- 新客户端缺少 v3 metadata、收到未知版本或 capability 关闭时自动回退现有 confirm/full GET。
- transactional-read 出现 mismatch、outbox backlog、dirty 或 Redis mirror 缺口时立即降为 confirm-only，并对相关域 reset。
- 页面 coordinator 可按 route 关闭，恢复原 resource controller 调度。
- 回滚不要求清理生产 IndexedDB、Redis 或数据库事实；协议版本和 epoch 不兼容时由 reset 自愈。
