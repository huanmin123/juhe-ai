# AI 问答生成续跑与本地缓存设计

> 日期：2026-07-16
> 状态：已确认（用户授权按最佳方案补全并实施）
> 范围：站内 AI 问答的生成生命周期、断线重附着、轻量一致性同步和浏览器展示缓存

## 1. 背景

当前 AI 问答把上游生成生命周期绑定在 `ChatView` 和发起请求的 HTTP/SSE 连接上：

- `/my-chat` 未使用页面缓存，切换菜单会卸载 `ChatView`。
- 页面卸载会中止前端请求。
- 后端收到响应连接关闭后会中止上游 controller，并把已接受轮次收口为 `canceled`。
- 断流确权发现助手仍为 `streaming` 时会主动调用停止。
- 每次重新进入页面都需要重新读取消息正文；会话正文增大后会给 DB service、网络和渲染造成重复压力。

因此，仅增加 `KeepAlive` 或 IndexedDB 都不能独立满足目标。`KeepAlive` 只能覆盖同一标签页内的菜单切换；IndexedDB 只能加速显示，不能阻止浏览器断开后端生成。

## 2. 目标

1. 用户切换菜单、刷新页面或关闭标签页后重新进入时，已经接受的 AI 生成继续在后端执行。
2. 页面重新进入时先从 IndexedDB 渲染可见历史，再用轻量同步接口确认权威状态。
3. 本地与服务端一致时不重复下载正文；不一致时只拉取必要增量或替换区间。
4. 显式“停止生成”仍然立即、精确地取消匹配轮次。
5. 本地缓存失败、禁用或容量不足时自动降级为现有网络加载，不阻塞发送和查看。
6. 保持当前轻量单实例边界，不为本功能引入 Redis Pub/Sub、分布式任务队列或独立事件存储。

## 3. 非目标与边界

- 不保证后端服务进程重启后继续同一次上游生成。进程重启后由现有 stale active turn 恢复逻辑把遗留轮次收口为失败或取消。
- IndexedDB 不是服务端聊天库的镜像，不保存模型 checkpoint、隐藏上下文、上游请求体或图片二进制。
- 客户端缓存不能作为模型上下文或消息写入事实来源。
- 不承诺跨浏览器、跨设备共享本地缓存。
- 不建设任意历史分支；最近轮次替换继续沿用现有语义。

## 4. 方案选择

### 4.1 仅 `KeepAlive`

优点是改动小，可解决同一标签页菜单切换。缺点是刷新、关闭标签页和 KeepAlive 淘汰后仍会断开并取消生成，不满足完整目标。

### 4.2 服务端脱离连接的 runner + IndexedDB + revision 同步（采用）

生成任务在接受后归服务端所有；HTTP/SSE 连接只是 subscriber。前端使用应用级运行态和 IndexedDB cache-first，同步时只比较服务端单调 revision 并按差异增量加载。

该方案覆盖菜单切换、刷新和关闭后重进，同时仍保持单机轻量架构。

### 4.3 持久化分布式任务

可覆盖服务重启和多实例迁移，但需要持久化事件、队列和跨实例协调，超出当前项目边界，暂不采用。

## 5. 总体架构

```text
upstream model request
        |
server-owned ChatGenerationRunner
        |-- bounded current snapshot
        |-- monotonic eventVersion
        |-- zero or more SSE subscribers
        `-- authoritative terminal DB transaction

browser ChatRuntime (app scope)
        |-- Map<conversationId, RunningTurn>
        |-- stream attach / detach
        |-- IndexedDB cache
        `-- ChatView subscriptions

IndexedDB cache -> immediate render
        |
GET sync head -> revision comparison
        |-- unchanged: no body transfer
        |-- append/status change/replace: bounded incremental fetch
        `-- active turn: attach stream snapshot + deltas
```

## 6. 服务端数据契约

### 6.1 `message_revision`

`chat_conversations` 新增：

```text
message_revision BIGINT / INTEGER NOT NULL DEFAULT 0
```

它只描述用户可见消息事实版本，不能复用 `context_revision`。以下操作必须在修改消息的同一事务内递增：

- 接受普通轮次；
- 替换最近轮次；
- 助手完成；
- 助手失败；
- 用户停止或 stale recovery 取消；
- 会改变可见消息集合的清理或删除操作。

会话标题、置顶等不影响消息正文的更新不得推进 `message_revision`。

### 6.2 轻量同步头

新增：

```http
GET /__aisys__/api/my-chat/conversations/:conversationId/sync?knownRevision=123
```

响应不包含正文：

```json
{
  "conversationId": "chat_conv_x",
  "messageRevision": 124,
  "unchanged": false,
  "serverTime": "2026-07-16T00:00:00.000Z",
  "lastSequenceNo": 20,
  "activeTurn": {
    "turnId": "turn_x",
    "assistantMessageId": "msg_x",
    "startedAt": "2026-07-16T00:00:00.000Z"
  },
  "tail": [
    {
      "id": "msg_user",
      "turnId": "turn_x",
      "sequenceNo": 19,
      "role": "user",
      "status": "completed",
      "completedAt": "2026-07-16T00:00:00.000Z",
      "expiresAt": "2026-07-19T00:00:00.000Z"
    },
    {
      "id": "msg_assistant",
      "turnId": "turn_x",
      "sequenceNo": 20,
      "role": "assistant",
      "status": "streaming",
      "completedAt": null,
      "expiresAt": "2026-07-19T00:00:00.000Z"
    }
  ]
}
```

`tail` 固定最多返回最近完整轮次的两条消息，目标响应小于 1 KiB。最后消息 ID 不能单独作为一致性依据，因为同一个助手消息 ID 会从 `streaming` 更新为终态并写入正文。

`knownRevision` 相等时仍返回 active turn 和最小 tail，供客户端恢复运行态，但不返回消息正文。

### 6.3 增量消息游标

现有 `beforeSequenceNo` 继续用于向前加载历史。新增互斥参数：

- `afterSequenceNo`：exclusive，按序号升序返回新增消息；
- `fromSequenceNo`：inclusive，按序号升序返回替换区间或同 ID 状态更新。

三类游标不能同时提交，单页上限继续为 100。正常追加使用 `afterSequenceNo`；同一助手消息终态变化使用 `fromSequenceNo=assistantSequenceNo`；最近轮次替换时先删除本地 `sequenceNo >= tail.user.sequenceNo`，再从该序号重取。

所有 revision 与消息读取都以服务端数据库为权威。客户端在同步过程中若观察到 revision 再次变化，最多重新执行一次 sync；持续变化时保留当前缓存并进入下一次短轮询，不能无限循环。

## 7. 生成生命周期与重附着

### 7.1 服务端拥有生成任务

接受轮次后创建 `ChatGenerationRunner`：

```ts
interface ChatGenerationRunner {
  ownerId: string
  conversationId: string
  turnId: string
  assistantMessageId: string
  controller: AbortController
  eventVersion: number
  snapshot: BoundedAssistantProjection
  subscribers: Map<string, ChatStreamSubscriber>
}
```

- 上游 controller 只允许显式 stop、任务 hard timeout、服务关机或内部确定性失败中止。
- `res.close` 只删除当前 subscriber，不得 abort runner。
- subscriber 写失败不得进入 runner 的业务 catch，也不得把助手消息误写成失败。
- runner 的正文、reasoning 和工具投影继续服从现有字节上限；不保存无界事件日志。
- 每次可见/过程投影变化推进 `eventVersion`，并更新有界 snapshot。
- 终态先在数据库完成 revision 事务，再发送终态事件，最后按 turnId 条件删除 registry。

同一会话仍只允许一个 runner；不同会话可以各自运行，但继续受系统现有网关、账户和全局并发控制约束。

### 7.2 重附着 SSE

新增：

```http
GET /__aisys__/api/my-chat/conversations/:conversationId/streams/:turnId
```

校验当前用户、会话、active turn 和 runner identity 后：

1. 首先发送 `message.snapshot`，包含当前 `eventVersion` 和有界助手投影；
2. 之后只发送版本更高的增量；
3. runner 已终态时不伪造内存状态，客户端回到 sync/消息增量接口；
4. active DB 状态存在但 runner 不存在时返回稳定错误，触发 stale active turn 收口，不无限等待。

客户端以 snapshot 替换当前助手投影，再应用更高版本增量，避免断线前后重复拼接。

### 7.3 显式停止

现有 stop 继续使用 `clientMessageId / turnId` 条件保护。只有用户明确点击停止时才调用；页面切换、浏览器隐藏、网络断开和普通请求异常不得自动 stop 已接受且仍在运行的轮次。

## 8. 前端运行态

### 8.1 应用级 `ChatRuntime`

运行态从 `ChatView` 移到路由外应用级单例：

```ts
Map<conversationId, RunningTurn>
```

每项记录 `clientMessageId`、`turnId`、最新 eventVersion、状态、订阅者和重连状态。`ChatView` 只订阅当前会话投影；卸载时解除 UI 订阅，不能中止生成。

`/my-chat` 同时启用 `KeepAlive`，减少普通菜单切换的重复装载，但正确性不依赖 KeepAlive。

### 8.2 恢复状态机

进入会话时：

1. 从 IndexedDB 同步读取缓存并立即渲染；
2. 请求 sync head；
3. revision 相等时不读取正文；
4. revision 不同时按 tail 选择追加、同 ID 状态更新或替换区间；
5. active turn 存在时重附着；
6. attach 失败时重新 sync，终态则读取差异，runner 缺失则等待服务端恢复收口。

`accepted + streaming` 不再自动调用 stop。只有确知提交未接受时才恢复编辑器草稿。

## 9. IndexedDB 缓存

### 9.1 模块边界

使用原生 IndexedDB，不增加 Dexie、localForage 或其他重依赖。拆分为：

- `chatLocalCache.ts`：数据库 schema、事务、容量和清理；
- `chatConversationSync.ts`：cache-first 与服务端差异同步；
- `chatGenerationRuntime.ts`：运行态、attach、subscriber 和显式 stop；
- `chatCacheBroadcast.ts`：可选的同源标签页失效通知。

页面组件不得直接操作 IndexedDB。

### 9.2 object stores

```text
conversation_heads
  key: [systemAccountId, conversationId]

messages
  key: [systemAccountId, conversationId, sequenceNo]
  index: [systemAccountId, conversationId, sequenceNo]

running_turns
  key: [systemAccountId, conversationId]
```

只保存页面可见 DTO、同步头和重连定位字段。不保存：

- API Key、OAuth token、代理密码或其他凭据；
- 图片 Blob、Base64 或原始上传文件；
- 模型 checkpoint、隐藏图片说明、reasoning 原始 payload；
- 上游请求体、审计 payload 或完整工具原始 JSON。

图片消息只保存 asset ID 和展示 metadata，内容继续走现有鉴权 URL 与浏览器 HTTP 缓存。

### 9.3 容量与淘汰

本地预算：

```text
min(256 MiB, navigator.storage.estimate().quota * 20%)
```

若 quota 不可用，使用保守的 64 MiB 软预算。缓存维护近似 UTF-8 字节，不通过扫描全部消息实时求和。

达到预算或出现 `QuotaExceededError` 时，按 `lastAccessAt` 淘汰最久未访问且满足以下条件的会话：

- 不是当前会话；
- 没有 active/running turn；
- 没有待确权提交。

服务端 `expiresAt` 与 sync 返回的 `serverTime` 用于清理默认 3 天窗口，避免依赖不准确的客户端时钟。

IndexedDB 打开、读取或写入失败只记录有界诊断并降级网络；不能阻塞发送、停止、同步或退出登录。

### 9.4 身份隔离

- 所有 key 必须包含 `systemAccountId`。
- 切换系统账户时关闭旧 runtime 订阅，不能展示旧用户缓存。
- 明确退出登录时清理该系统账户的聊天缓存。
- 404 会话删除本地对应会话；403 不删除缓存，但当前会话不再展示正文并等待重新认证。

## 10. 多标签页

`BroadcastChannel` 只发送 `{ systemAccountId, conversationId, messageRevision }` 失效提示，不传消息正文，也不作为权威锁。

多个标签页可以同时 attach 同一个 runner；每个 subscriber 有独立写入背压和生命周期。收到广播后，非发送标签页执行轻量 sync。若浏览器不支持 BroadcastChannel，则靠页面激活和短轮询同步。

## 11. 错误与竞态

- accept、replace、finalize、cancel 与 revision 递增必须同事务。
- attach 必须校验 expected turn，旧 turn 不得附着或停止新 turn。
- 终态和 stop 的迟到事件按 turnId/eventVersion 忽略。
- snapshot 必须先于增量；客户端只接受更高 eventVersion。
- IndexedDB 事务失败不得回滚服务端事实。
- 本地 revision 高于服务端时视为缓存损坏，清理该会话并重建。
- 替换轮次后本地 tail 不匹配时，从最近用户序号开始重取，不能只比较最后消息 ID。
- 服务端进程退出时先停止接受新 subscriber，再中止 runner 并按现有恢复语义落终态。

## 12. 验收

### 12.1 后端

- 接受后关闭首个 HTTP/SSE subscriber，上游继续生成并最终落库。
- 两个 subscriber attach 同一 turn，不重复请求上游。
- snapshot + eventVersion 重连不重复或遗漏正文。
- subscriber 写失败不影响 runner 和其他 subscriber。
- 显式 stop 精确取消匹配 turn，旧 stop 不影响新 turn。
- accept、replace、completed、failed、canceled 均按事务推进 `message_revision`。
- sync revision 相等不返回正文；append、同 ID 终态和 replace tail 均可区分。
- runner 缺失、服务关机和 stale active turn 有明确收口。

### 12.2 前端与 IndexedDB

- 切换其他菜单 10 秒后返回，原生成继续并显示最新增量。
- 刷新页面后先显示本地历史，再重附着生成。
- 关闭标签页后重新进入，后端仍运行时可恢复 active turn。
- revision 相等时正文接口调用次数为 0。
- 同一消息 ID 从 streaming 更新到 completed 时能正确刷新正文。
- 最近轮次替换后不会保留旧消息或旧 partial。
- IndexedDB 禁用、损坏、QuotaExceeded 时降级网络且聊天可用。
- 用户隔离、登出清理、3 天过期和 LRU 淘汰正确。
- 多标签页不会重复生成或互相停止。
- 手机端菜单切换、恢复、回到底部和输入框位置保持正常。

### 12.3 现有闭环回归

- 最近一轮编辑、显式停止、断流确权和 50 轮门禁保持原行为。
- 图片只缓存引用；上传、删除和过期资产不被 IDB 阻塞。
- 真实长会话、受控压缩、Prompt Cache usage、数据库账本和第 51 轮无写入门禁继续通过。

## 13. 实施顺序

1. 数据库 `message_revision` 与 repository 事务。
2. sync head 与增量游标。
3. server-owned runner、subscriber 解耦和 attach SSE。
4. 前端应用级 runtime 与普通菜单切换续跑。
5. IndexedDB stores、容量、cache-first 和差异同步。
6. 刷新/关闭重进、多标签、移动端和降级测试。
7. 与 50 轮、压缩、缓存及 worker 验收合并执行。

## 14. 设计自审结论

- 无 TBD、TODO 或未选择分支。
- IndexedDB 只缓存展示层，未与模型上下文混用。
- `message_revision` 与 `context_revision` 职责分离。
- 菜单切换、刷新、关闭重进和服务重启边界均已明确。
- 方案符合当前单实例轻量边界，并保留未来持久化任务扩展入口。
