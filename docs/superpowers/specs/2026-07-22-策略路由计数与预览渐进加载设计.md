# 策略路由计数与预览渐进加载设计

## 1. 背景

策略路由管理/个人列表已经拆出基础 ListItem 和最多三条分组预览，但当前基础 SQL 仍为每行执行两个相关子查询：

- `route_strategy_groups` 绑定数量；
- `api_keys` 使用数量。

主列表完成后还会按当前页 ID 执行一次带授权与分组状态 JOIN 的前三条预览查询。页面只有在这些动态字段全部返回后才展示列表。同时，当前 Vue 列表加载没有请求代次保护，翻页、筛选、切换用户或刷新时旧响应可以覆盖新状态。

本设计承接 [全站页面 API 按需加载审计报告](../../reports/全站页面API按需加载审计报告-2026-07-20.md) 的 P1 方向。由于当前 [策略路由设计](../../functions/策略路由设计.md) 仍明确要求基础列表同步返回计数和预览，本批必须先确认新契约再实施。

## 2. 目标

- 基础列表 SQL 不执行分组/API Key 计数，也不查询预览，先返回当前页静态字段。
- 当前页基础列表成功后只发一次 `list-snapshot` 请求，批量返回精确计数与前三条预览。
- snapshot 使用实时有界查询，不新增物化表、worker 预聚合或长 TTL 缓存。
- pending、失败和真实 0 三种状态在 UI 中可区分。
- 列表与 snapshot 使用同一请求代次、owner scope 和 ID signature，迟到响应不得污染新页。
- 详情接口继续同步返回完整分组绑定与精确 API Key 数，不改变编辑行为。

## 3. 范围与非目标

本批只修改 Node 后端和 Vue 前端，不修改 `backend-go/`，不切换 owner，不提交、不部署、不触碰生产。

不修改：

- 策略路由创建、更新、删除、默认保护或网关调度语义；
- API Key 只绑定策略路由的业务层级；
- 完整详情、外部公开策略路由接口或 options 契约；
- schema、索引和 page-data 持久缓存域；
- 计数排序/筛选（当前不存在）。

## 4. 基础列表契约

`GET /__aisys__/api/route-strategies` 与 `GET /__aisys__/api/my-route-strategies` 保持分页、筛选、排序和权限语义，ListItem 保留：

- `id`；
- 管理视图需要的 `systemAccountId/systemAccountName`；
- `name/description/mode/status/isDefault`；
- `normalRoutingConfig`（模式列需要显示成本优先/速度优先）；
- `createdAt/updatedAt`。

基础 ListItem 不再返回：

- `groupBindingPreview`；
- `bindingCount`；
- `apiKeyCount`。

基础 SQL 明确禁止相关 `COUNT` 子查询和预览 loader。

## 5. List Snapshot 契约

管理端：

`GET /__aisys__/api/route-strategies/list-snapshot?ids=id-a&ids=id-b`

个人端：

`GET /__aisys__/api/my-route-strategies/list-snapshot?ids=id-a&ids=id-b`

参数规则：

- canonical 编码为重复裸键 `ids=id-a&ids=id-b`；服务端也可沿用现有 query array parser 接受 bracket 数组键；
- trim、去重，至少 1 个、最多 200 个，与列表最大页大小一致；
- 每个 ID 使用现有文本长度边界；非法形状、空集合、数量或长度越界返回 400；
- 管理端可带当前列表的 `systemAccountId` 作用域；个人端强制当前登录用户并忽略/删除伪造作用域。

响应：

```ts
interface RouteStrategyListSnapshotResult {
  generatedAt: string
  items: RouteStrategyListSnapshotItem[]
}

interface RouteStrategyListSnapshotItem {
  id: string
  bindingCount: number
  apiKeyCount: number
  groupBindingPreview: RouteStrategyGroupBindingPreview[]
}
```

- 对每个可见且存在的请求 ID 返回一项，包括真实零值；不可见或不存在 ID 静默省略，不能以零值暴露存在性。
- 响应按规范化请求 ID 顺序稳定。
- `bindingCount` 统计全部绑定；`apiKeyCount` 保持当前语义，统计全部状态且 owner 匹配的 API Key。
- `groupBindingPreview` 最多三条，保持 active 优先、priority、createdAt、id 的稳定排序。
- 预览继续返回 `id/groupId/groupName/providerCode/status/groupEnabled`，并保留授权分组及授权设置对 `groupEnabled` 的现有计算。
- 路由必须注册在 `/:id` 之前，避免被详情路由捕获。

## 6. Node 查询边界

- 基础 list columns 删除两个相关 COUNT；基础 mapper 不调用 preview loader。
- snapshot 先按 AccessScope 批量筛出可见策略 ID，权限必须在 SQL 中收口，不能先查全部计数再由 JS 过滤。
- 对可见 ID 使用固定数量的 GROUP BY 聚合查询计算 binding/API Key count，禁止逐 ID 查询。
- preview 复用现有批量 ROW_NUMBER 查询及授权 JOIN，只传可见 ID。
- SQLite read worker 增加单个 snapshot operation，在 worker 内顺序执行固定数量查询。
- PostgreSQL 可在同一请求中并发 count 与 preview 批量查询，但错误必须整体失败，不返回部分成功伪装。
- 本批不增加服务端 TTL 缓存：API Key、策略绑定、分组和授权写入都会改变 snapshot，当前没有完整的跨域失效 fanout。

## 7. 前端数据流

### 7.1 统一加载代次

分页、筛选、刷新、系统账户切换、保存后和删除后都走统一 loader：

1. 创建新的 list generation，旧 list/snapshot intent 立即失效；
2. 请求基础列表；
3. 仅当前 generation 可以写入列表并结束基础 loading；
4. 基础行立即渲染；
5. 当前页非空时，以可见 ID 序列发一次 snapshot；
6. snapshot 仅在 generation、owner scope 和当前 ID 序列都一致时按 ID 合并。

AbortController 可减少浪费，但 generation 校验必须保留。

### 7.2 展示状态

- 基础列表 loading 只覆盖基础请求，snapshot 不重新遮罩整表。
- 新页 snapshot pending 时，分组和 API Key 列显示小型 loading/占位，不能显示“未绑定”或 `0`。
- snapshot ready 后，真实 0 才显示“未绑定”或 `0`。
- snapshot error 不清空基础行，不弹阻断错误；对应动态列显示“暂不可用”，工具栏刷新可重试。
- 同 scope 同 ID 的手动刷新可保留上次成功值并标记 refreshing；换页、换筛选或换 owner 不复用旧 scope 值。
- snapshot 缺少某个可见 ID 时，该行保持 unknown/error，不按 0 合并。

### 7.3 移动与删除

- 桌面和移动端使用同一 snapshot map。
- 移动追加加载若继续保留当前实现，应一次请求当前新增/可见集合，设计和回归固定请求范围，禁止逐行请求。
- 删除导致非首页变空时回退前一页或第一页后重新走统一 loader。

## 8. 权限与一致性

- 管理全局、指定 owner 与个人视图使用和基础列表相同的 AccessScope。
- 个人路由不能通过 query 获取其他用户 snapshot。
- snapshot 不改变详情、删除保护或 API Key 绑定校验中的精确计数读取。
- 分组名称、启用态与授权态按请求时事实返回；`generatedAt` 仅表示本次生成时间，不承诺跨请求事务快照。

## 9. 测试与验收

### Node

- Query guard：基础 SQLite/PG list SQL 无 `COUNT`、`api_keys`、`route_strategy_groups` 子查询，mapper 不触发 preview。
- HTTP：管理全局/指定 owner、个人伪造 scope、重复/非法/越界 IDs、不可见/不存在静默省略、路由顺序。
- Snapshot：零计数、4+ bindings、前三预览排序、授权分组 `groupEnabled`、固定查询数量、无 N+1。
- SQLite 主线程/read worker 与真实 PostgreSQL async 逐字段一致。
- 详情、分组绑定、删除保护和 API Key 现有回归继续通过。

### 前端

- 基础行先呈现，非空当前页恰好一次 snapshot，空页零次。
- pending/error/真实零显示不混淆；桌面和移动一致。
- 页 A→B、owner A→B、筛选 A→B、同页连续刷新、旧失败、卸载迟到均不能污染当前状态。
- 保存/删除后重新加载，删除空页回退正确。

### 门禁

- Node/前端专项回归、真实 PG smoke、后端 typecheck、可运行的前端 typecheck/build、`git diff --check`。
- 浏览器网络确认 list 与 snapshot 时序、请求次数和页面状态；环境不可用时明确记录。
- 至少两名只读 Agent 独立复核并交叉质疑。

## 10. 完成标准

- 基础列表可在动态计数/预览前渲染，主 SQL 不再含逐行相关计数。
- 当前页只有一个有界 snapshot 请求，后端查询数量不随策略行数增长。
- 权限、预览排序、真实零值、详情和写后行为无回归。
- 竞态、worker、PG 和浏览器证据闭合，不以源码字符串替代行为证明。
