# 代理选项与日志列表渐进加载设计

## 1. 背景

本设计延续 `PLAN-0077` 的管理接口 DTO 分层方向，修正当前 `master` 中仍未真正收窄的三个页面链路：

1. AI 账户页面把代理 options 与账户列表、供应商定义绑定加载，首屏、翻页和系统账户切换会重复请求全局代理候选。
2. 操作日志列表虽然在 route 层删除部分字段，但 repository 仍读取并组装完整 `OperationLogSummary`。
3. 公开 API 日志列表仍使用宽 `PublicApiLogSummary`，并以 100 行作为默认首屏窗口。

当前生产管理 owner 仍为 Node，但 Go 已注册账户 list/detail、proxy options、操作日志和公开 API 日志的 opt-in handler。四类接口要求 Node 正式路径与 Go opt-in 路径保持同一路由、参数、字段、权限和分页语义；本批只保证等价，不改变 owner manifest，也不触发 Go 接管。

## 2. 目标

- 账户首屏、翻页和普通刷新不再请求 `/proxies/options`。
- 账户列表和基础详情直接返回绑定代理的最小展示信息，保证冷启动、停用代理和授权实例的名称、类型、状态正确。
- 代理候选只在单账户编辑或批量编辑的代理下拉首次展开、搜索和已选启用项补齐时请求。
- 操作日志和公开 API 日志列表从 SQL、mapper、service 到前端类型均使用专用 ListItem；详情继续按 ID 加载完整内容。
- 公开 API 日志默认分页窗口统一为 50，最大值继续为 100，因为 100 仍是当前最优的显式调用上限，不作为历史兼容分支。
- 用行为、HTTP、查询和真实 PostgreSQL 证据证明改动，不把源码正则视为完成证明。

## 3. 非目标

- 不修改 schema，不做生产数据迁移。
- 不改变代理的管理权限、账号绑定规则或秘密字段存储。
- 不改变操作日志的可见范围、详情级别和 targeted/all-users 合并规则。
- 不改变公开 API 日志的捕获范围、写入队列、保留期或详情内容。
- 不调用真实模型；本批不需要模型密钥。
- 不部署、不上线；上线等待用户另行通知。

## 4. 方案选择

### 4.1 代理列表展示

考虑过两种方案：

- 账户列表返回后，再按当前页 `proxyProfileId` 请求代理 labels。实现较小，但有绑定代理的页面仍增加一次 RTT，移动分页还会产生连续补齐请求。
- 账户列表和基础详情直接投影绑定代理的最小展示字段。查询边界更明确，冷启动零额外 RTT，授权实例也可基于真实来源账户正确返回代理信息。

采用第二种。代理是账户列表已展示的关联事实，不应通过全局 options 间接水合。

### 4.2 停用代理补齐

通用 `/proxies/options` 当前允许已登录用户读取全局启用代理。若 `selectedIds` 可任意补回停用代理，会扩大为停用代理枚举入口。

因此：

- options 的普通窗口与 `selectedIds` 补齐都只返回启用代理。
- 已绑定但停用的代理名称、类型和停用态只通过用户有权访问的账户列表或基础详情返回。
- 不存在或无权访问的绑定代理继续按账户契约显示不可用状态，不从 options 猜测。

### 4.3 日志列表

采用独立 ListItem，而不是 `Omit<Summary>` 或完整 Summary 加空 payload。筛选条件可以引用不返回的列，但 SELECT 与 mapper 只构造列表实际字段。

## 5. 账户代理展示契约

### 5.1 账户 ListItem 与基础详情

在当前账户列表和基础详情 DTO 中增加：

```ts
interface AccountProxyDisplay {
  proxyProfileId?: string
  proxyProfileName?: string
  proxyProfileType?: 'http' | 'https' | 'socks5' | 'socks5h'
  proxyProfileEnabled?: boolean
  proxyProfileUnavailable?: boolean
  proxyProfileErrorMessage?: string
}
```

规则：

- 未绑定代理时四个代理身份/展示字段均省略，`proxyProfileUnavailable` 为现有语义。
- 绑定存在的代理时返回 ID、名称、类型、启用态；不返回 host、port、username、password、测试报告或连接详情。
- 授权实例使用来源账户实际绑定的代理，并按当前账户可见权限返回最小展示字段。
- 代理记录不存在时保留绑定 ID 与不可用语义；名称和类型省略，不伪造默认值。

Node SQLite/PG 与 Go opt-in PG 必须从当前页账户的代理 ID 做批量窄查询或等价索引 JOIN，不允许在 `map(row)` 中逐条查询，也不允许加载完整代理列表。

权限矩阵：

| 账户视图 | 代理启用 | 返回字段 |
| --- | --- | --- |
| admin/super_admin 管理视图 | 启用或停用 | `id/name/type/enabled` 与现有 unavailable/error 语义 |
| 普通用户自有账户 | 启用 | `id/name/type/enabled=true` |
| 普通用户自有账户 | 停用、删除或不存在 | 保留现有 `id + unavailable/error`；不返回 name/type/enabled |
| 普通用户授权实例 | 启用 | 允许返回来源账户绑定代理的 `id/name/type/enabled=true`，因为同一登录用户可从全局 enabled options 获得相同元数据 |
| 普通用户授权实例 | 停用、删除或不存在 | 保留现有 `id + unavailable/error`；不返回 name/type/enabled |

本批不改变代理管理权，也不让普通用户通过账户 DTO 获得停用代理名称、类型或停用状态。来源账户删除、授权失效或来源绑定清空时，沿用当前授权账户不可用/无绑定语义。

### 5.2 代理 options

保留 `GET /proxies/options`，参数为：

```ts
interface ProxyOptionParams {
  keyword?: string
  limit?: number
  selectedIds?: string[]
}
```

- `keyword` trim 后按现有字面前缀语义搜索。
- `limit` 默认 50，范围 `1..50`。
- 前端 canonical 编码为重复裸键：`selectedIds=id-a&selectedIds=id-b`。服务端同时识别重复裸键和常见 bracket 数组键 `selectedIds[]=id-a`；不接受 CSV、JSON 字符串或嵌套对象。
- 服务端 trim、去重并按 ID 字典序规范化，最多 20 个；每个 ID 遵循项目现有文本长度上限。缓存键使用相同规范化结果，不依赖调用方输入顺序。
- `selectedIds` 与 keyword 可以同时出现：普通搜索窗口与命中的启用已选项合并去重后，统一按 `name ASC, updated_at DESC, id ASC` 排序；补齐项不占普通窗口 limit。
- 不存在或停用的 ID 静默省略；selectedIds 形状、长度或数量越界返回 400。
- `limit` 沿用当前契约：非整数按未传处理，整数值限制在 `1..50`；本批不改变该行为。
- 响应字段固定为 `id/name/type/enabled`，其中 options 中的 `enabled` 必为 `true`。

Node SQLite、SQLite read worker、Node PG、Go service/port/PG 使用同一规范化规则和稳定排序 `name ASC, updated_at DESC, id ASC`。SQLite 使用整数布尔列；PostgreSQL 使用原生 boolean 表达式和布尔映射，禁止在 PG 路径继续使用 `enabled = 1` 或 `row.enabled === 1`。

## 6. 代理前端数据流

- 账户列表 mounted、翻页、刷新和系统账户切换不调用 `/proxies/options`；列表直接使用账户行的代理展示字段。
- 新建和编辑弹窗打开不因代理 options 阻塞；当前已选代理先用账户详情中的最小展示对象回显。
- 代理下拉首次展开才加载首窗；重复展开命中当前登录会话缓存。
- 远程搜索使用 `keyword + selectedIds`，`filter-option=false`，250ms debounce；旧请求不能覆盖新关键词或新身份状态。
- 批量编辑打开时零代理请求；只有用户启用代理字段并展开/搜索时才加载。
- 缓存键至少包含登录用户 ID、角色和端点版本；登出、身份切换或认证 revision 变化时清理。代理是全局启用资源，不按管理目标系统账户重复分片。
- 失败保留已选展示对象和最后一次成功窗口，允许再次展开重试，不得清空表单 `proxyProfileId`。
- `CachedSelect`/`ProxySelect` 显式转发 `search` 与 `dropdownVisibleChange`，已选项在 50 项裁剪后仍必须保留。

## 7. 操作日志列表契约

### 7.1 HTTP ListItem

```ts
interface OperationLogListItem {
  id: string
  traceId?: string
  actorSystemAccountId: string
  actorDisplayName?: string
  actorSystemAccountName?: string
  operationScopeSystemAccountId?: string
  operationScopeSystemAccountName?: string
  module: string
  action: string
  summary: string
  createdAt: string
}
```

列表不返回 `actorUsername`、`actorRole`、`mode`、`operationKey`、资源字段、`changes`、`metadata`、HTTP 字段、client IP、User-Agent、`detailLevel` 或 `visibilityScope`。

`detailLevel`、`visibilityScope` 和 viewer detail level 仍作为 repository/service 内部行参与权限裁剪，但不得进入 ListItem mapper 或列表 HTTP DTO。列表 SQL 允许投影这些权限内部列；SQL 门禁区分“HTTP 展示列”“权限内部列”和“仅 predicate/join 使用列”。详情接口保持当前管理员/普通用户字段契约。

### 7.2 权限不变量

- 管理列表仅 admin/super_admin 可用。
- 个人列表只包含当前用户 targeted 记录与 all_users 记录，不包含 admin_only。
- targeted/all-users 双路查询、稳定合并、去重、分页和 hasMore 语义不变。
- 普通用户传入管理筛选参数时继续忽略；不可见详情仍返回 404。
- summary/full 有效级别计算及个人详情的字段裁剪不变。

### 7.3 存储

Node 和 Go 的所有列表 SQL 使用显式列表列；详情 SQL 可使用显式完整列。Node 增加专用 mapper，Go port/service 增加列表专用 row/HTTP DTO。Go sqlc 生成文件只能通过项目生成命令更新。

## 8. 公开 API 日志列表契约

```ts
interface PublicApiLogListItem {
  id: string
  createdAt: string
  sourceName?: string
  method: string
  path: string
  success: boolean
  statusCode?: number
  durationMs?: number
  clientIp?: string
  traceId?: string
}
```

列表不返回来源引用 ID、token 元数据、测试 token 标记、query string、User-Agent、大小、capture 状态、错误详情、开始/结束时间或 request/response payload。详情保持完整契约。

Node SQLite/read worker/PG 与 Go PG 的 HTTP 返回投影均只包含上述 10 个字段。SQL 可在 WHERE/JOIN 中使用筛选列，但 mapper 不得读取或返回额外列。筛选仍可引用 trace、source、path、status、result、IP 和时间列。排序保持 `created_at DESC, id DESC`。

前端、Node 和 Go 默认 pageSize 统一为 50，最大仍为 100，pageSize + 1 判定 hasMore。前端页面缓存版本递增，避免恢复旧 100 行状态。

## 9. Node/Go 实现与 opt-in 契约矩阵

| 领域 | Node | Go | 必须一致 |
| --- | --- | --- | --- |
| 代理 options | Express route、SQLite/PG repository、SQLite worker | handler、service、port、PG/sqlc | 参数校验、字段、排序、启用过滤 |
| 账户代理展示 | account list/detail repository 和 DTO（生产 owner） | 已注册的 account list/detail opt-in handler/service/store/DTO | admin/owner/授权实例权限矩阵、nullable、不可用态 |
| 操作日志 | route、types、mapper、SQLite/PG repository、worker | handler、service、port、六条列表 SQL、mapper | 权限集合、字段、排序、详情不变 |
| 公开 API 日志 | route/types、SQLite/PG repository、worker | handler、service、port、PG store | 字段、筛选、50 行默认、详情不变 |

## 10. 错误与竞态

- options 参数错误返回现有中文 400 错误结构。
- 日志列表查询失败沿用现有错误模型，不返回部分成功伪装。
- 前端每个代理请求记录身份 scope、请求序号和关键词；关闭弹窗、切换身份或新搜索后，迟到响应只结束自己的 pending 状态，不写回当前结果。
- 详情请求竞态继续使用现有 request ID/cache 机制。

## 11. 性能证据

本批的性能结论必须基于前后对比。固定基线为 `origin/master@88c834c802aba7c303c49d52f1ebb7a5bdc91789`，前后使用同一有界 fixture、相同筛选和相同冷/热缓存状态；未压缩字节统一按 UTF-8 `JSON.stringify`/HTTP body 字节数计算，耗时至少记录 1 次冷读和 5 次热读并只作为观察值：

- 账户无绑定代理页面：首屏、翻页、刷新代理 options 请求数从 1 降为 0。
- 账户有绑定代理页面：代理展示随列表响应返回，不增加 labels RTT；记录列表响应新增字节与移除 options 响应字节的净变化。
- 操作日志：记录 20 行列表的 SQL 投影列数、未压缩响应字节和本地查询耗时；个人 targeted/all-users 结果 ID 顺序与改造前一致。
- 公开 API 日志：记录首屏 50 行 bytes/latency，以及连续加载 100 行时的总请求数、总字节和总耗时；验证第 50/51 条边界。

性能采样只作为证据，不写不稳定的绝对延迟阈值；字段、请求次数和结果集合是硬门禁。

## 12. 测试矩阵

### 12.1 代理

- Node unauth/user/admin HTTP；Go 对应 handler/service HTTP。
- keyword、limit、重复/数组 selectedIds、空值、20+1、超长、不存在和停用 ID。
- 响应精确字段白名单；损坏的 `password_encrypted` 证明 options 与账户列表展示不解密秘密。
- SQLite 主线程/read worker、Node PG、Go PG 返回一致；真实 PG 同时证明 Node 对 Goose boolean schema 可读。
- 账户列表冷启动代理名称/类型/停用态正确；授权实例使用来源账户代理。
- 账户基础详情覆盖 admin、普通用户自有、授权实例，以及启用、停用、删除/不存在代理；字段白名单与权限矩阵一致。
- 首屏/翻页/刷新零 options；单编辑/批编辑首次展开、缓存、搜索、失败重试、身份切换和迟到响应。

### 12.2 操作日志

- admin/self 精确字段白名单，详情完整或按现有权限裁剪。
- targeted-full、targeted-summary、all-users、admin-only 四类可见集合。
- self 管理筛选参数忽略、不可见详情 404、管理员路由 403。
- SQLite 主线程/read worker、Node PG、Go PG 的字段和 ID 顺序一致。
- 列表 SQL 不读取 payload/HTTP/resource 列；大 metadata sentinel 不进入列表。

### 12.3 公开 API 日志

- 默认第一页 50、第二页第 51 条，无重复遗漏，hasMore/total 正确。
- 精确字段白名单，普通用户 403，详情含完整 capture/error/payload，404 不变。
- trace、source、path、status、result、IP、时间组合筛选。
- SQLite 主线程/read worker、Node PG、Go PG nullable 与字段一致。
- 前端默认/重置 50、缓存版本、筛选回第一页、移动追加和详情按点击请求。

### 12.4 完成门禁

- 新增行为、HTTP、SQL 和真实 PG integration 测试通过。真实 PG 命令必须设置 `JUHE_AI_REQUIRE_INTEGRATION=1`，输出不得包含 `SKIP`；Go 必须运行目标 `-tags=integration` 用例，不能用普通 `go test ./...` 代替。
- PostgreSQL fixture 使用本任务唯一前缀/ID，只创建任务所需记录；`finally` 精确清理本任务记录。只有隔离测试 schema/表出现结构问题时才允许重建，禁止删除整个共享测试库或其他任务记录。
- SQLite 主线程和 read worker 使用本任务独立临时数据库文件，显式强制两条路径并逐字段比较；不得删除开发默认数据库。
- 前端竞态使用可观察真实请求次数/顺序的 composable 或组件挂载测试配合 fake timer；最终用浏览器网络面板复验首屏、翻页、展开、搜索和详情请求矩阵。源码正则和纯 helper 测试不能单独证明行为。
- `pnpm typecheck`、`pnpm lint`、`pnpm build`、`go test ./...` 通过。
- 真实测试 PostgreSQL/Redis 只用于本批需要的隔离 smoke；本批不需要 Redis 写入验证则不额外操作。
- `git diff --check` 通过。
- 至少两名只读 Agent 独立复核并交叉质疑，高严重度问题全部闭合。

## 13. 开发、同步与交付

- 功能分支从最新 `origin/master` 创建于独立 worktree。
- 设计、计划、每个逻辑批次和最终验证形成独立提交；提交前必须有对应验证证据。
- 每个逻辑批次完成后 `git fetch origin master` 并以 merge 方式同步 `origin/master`；发生冲突后重跑受影响验证。
- 功能分支推送远程作为备份和审查入口。
- 全部验证完成后，在干净的 master 集成工作区合并功能分支，重跑最终门禁。推送前再次 fetch 并确认 `origin/master` 未变化；若已前进，重新合并并重跑受影响门禁，禁止强推。
- 不构建发布包、不部署、不修改生产配置；上线等待用户通知。
