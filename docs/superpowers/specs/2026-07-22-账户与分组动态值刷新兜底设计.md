# 账户与分组动态值刷新兜底设计

## 背景

账户和分组列表已经按静态 DTO、动态快照拆分，但当前实现出现了两个断点：

- 账户列表前端不再请求 `status-snapshot`，同时 Node 列表响应会剔除动态字段，导致并发、运行可用性、冷却、最近错误、最近使用和当日用量在刷新后缺失。
- 分组列表会请求 `status-snapshot`，但 Node 分组快照读取 `group_account_stats.current_concurrency`；该统计缓存写入时固定为 `0`，无法表示 Redis 中的真实在途请求。

生产只读验证已经确认 Redis 和账户状态快照接口可用，因此本次修复落在列表与快照的组合边界，不通过轮询、重复全表查询或伪造默认值掩盖问题。

## 目标

- 页面首次加载、分页、筛选、排序和用户手动刷新后，当前已加载账户和分组的动态值能够更新。
- 列表响应已经携带完整动态值时直接使用，不重复请求快照。
- 列表响应缺少动态值时，通过当前页 ID 批量请求快照兜底。
- Redis 运行态不可用时保留同作用域上一次可信值；没有可信值时明确显示“暂不可用”，不能把未知值展示成 `0`。
- 不恢复固定周期轮询，不让动态读取污染静态页面缓存，也不在刷新路径执行逐行查询。
- Node 当前生产和 Go 渐进接管期间遵循同一前端兼容契约。

## 非目标

- 不恢复 30 秒账户状态轮询。
- 不把账户详情、凭据、模型映射等宽字段重新塞回列表 DTO。
- 不修改网关并发槽的申请、续租和释放逻辑。
- 不把 `group_account_stats.current_concurrency` 继续维护为实时事实；该字段仍可作为历史结构存在，但列表展示不再依赖它。
- 不改变使用记录、审计或运行日志开关。

## 方案比较

### 方案一：所有动态值强制内联列表

优点是一条 HTTP 请求即可完成页面加载。缺点是 Node 列表需要重新引入多组统计、授权和 Redis 查询，静态列表缓存不再稳定；Go 未完全接管时还会扩大两套实现差异。

### 方案二：所有列表无条件追加快照请求

实现简单，但 Go 或后续 Node 列表已经返回完整动态值时仍会产生重复请求，违背“能一次拿出来就直接返回”的性能要求。

### 方案三：直接值优先，快照按需兜底

列表响应同时满足“字段存在”和“对应 `runtimeSnapshot` 可用”时直接使用；否则只针对当前已加载 ID 请求快照。该方案保留静态列表缓存，同时兼容 Node 当前拆分接口和 Go 未来内联响应，是本次采用的方案。

## 数据契约

### 账户列表

动态字段集合沿用现有 `AccountStatusSnapshotItem`：

- `status`、`schedulable`、`cooldownUntil`
- 最近错误、健康检查和冷却复测字段
- 授权来源账户状态字段
- `apiKeyRuntime`
- `runtimeAvailability`、`effectiveAvailability`、`availabilityPresentation`
- `currentConcurrency`
- `lastUsedAt`、`todayUsage`

`AccountListResult.runtimeSnapshot` 继续表示列表内联动态值的可信度。当前列表没有携带完整动态字段时，前端将其视为需要快照兜底，而不是将缺失字段补成 `0`。

账户状态快照的 SQL 投影保持一次有界查询，使用统计摘要 loader，并与 Redis 运行可用性、Redis 并发槽并行读取。单次最多 100 个账户。

### 分组列表

`GroupStatusSnapshotResult` 增加：

```ts
runtimeSnapshot: {
  accountConcurrencyAvailable: boolean
}
```

每个分组快照项继续返回 `currentConcurrency` 和 `todayUsage`。`currentConcurrency` 的真实来源改为：

1. 一次读取当前分组集合的成员账户 ID。
2. 对去重后的账户 ID 批量读取 Redis 并发槽。
3. 在内存中按分组成员求和。

授权账户实例和来源账户的并发事实 ID 必须保持与网关一致。读取失败时 `accountConcurrencyAvailable=false`，数值只作为占位，前端不得当作可信 `0`。

### 直接值判定

- 账户：列表项存在所需动态字段，且列表 `runtimeSnapshot` 对应可用标记为 `true`，则跳过账户快照请求。
- 分组：列表存在 `runtimeSnapshot.accountConcurrencyAvailable=true`，且当前行 `currentConcurrencyAvailable=true`，则直接使用；否则请求分组快照。
- 当日用量等数据库动态字段缺失时，即使并发值可用，也仍需快照补齐缺失字段。

## 前端刷新流程

每次列表成功装载后执行一次动态补齐：

1. 捕获列表 revision、作用域签名和当前 ID 签名。
2. 保留列表中已经可信的动态字段。
3. 计算仍缺动态字段的 ID。
4. 按 100 个 ID 分批请求快照，最多两个批次并行。
5. 仅当 revision、作用域和 ID 签名仍一致时合并结果，防止旧请求覆盖筛选或分页后的新页面。

触发范围：

- 首次进入页面。
- 表格分页、移动端加载更多。
- 筛选、排序和作用域切换。
- 用户点击刷新或移动端下拉刷新。

不注册 timer、`visibilitychange` 或 `focus` 自动刷新。

## 降级与兜底

- Redis 并发读取失败但 SQL/统计投影成功：更新其他动态字段；并发保留同作用域同一行的上一次可信值。
- 整个快照请求失败：同作用域保留旧动态值；新行或新作用域标记不可用。
- 快照只返回部分 ID：已返回行正常合并，未返回行保留可信旧值或标记不可用。
- 切换管理目标用户、个人/管理视图或筛选作用域后，不允许复用旧作用域动态值。
- 过期响应通过 sequence、revision、作用域签名和 ID 签名共同丢弃。

## 性能约束

- 不在列表查询中新增逐账户或逐分组 SQL。
- 账户快照复用现有有界投影与批量 loader。
- 分组成员关系使用现有批量 loader；Redis 并发读取对账户 ID 去重后批量执行。
- 快照批次上限 100，前端并行上限 2。
- 列表已经携带可信动态值时不发快照请求。
- 静态页面缓存不缓存新读取到的实时并发，避免把短生命周期值当作静态事实。

## 测试设计

### 前端

- 列表动态字段完整时不请求快照。
- 列表动态字段缺失时请求一次快照并合并全部动态字段。
- 手动刷新和分页后触发一次补齐，不创建定时轮询。
- 超过 100 个 ID 时正确分批，且并行数不超过 2。
- Redis 可用性为 `false` 时保留同作用域可信并发；新作用域显示不可用。
- 旧 revision、旧作用域或旧 ID 集合的响应不能覆盖当前列表。

### 后端

- 分组快照按成员账户 Redis 并发求和，不读取统计表并发字段。
- 授权来源账户使用正确的并发事实 ID。
- Redis 不可用时显式返回 `accountConcurrencyAvailable=false`。
- 分组、账户权限边界和 100 ID 上限保持不变。
- SQL/Redis loader 均为批量调用，不出现逐行读取。

### 完整验证

- 前后端定向回归。
- `pnpm typecheck`。
- `pnpm build`。
- 浏览器验证账户和分组的首次加载、分页、筛选、手动刷新、不可用状态。
- 发布前生产只读 smoke 验证接口延迟、Redis 可用标记和实际并发值。

## 发布与回滚

- 先发布后端，使分组快照契约和实时并发来源正确；旧前端可继续消费已有字段。
- 再发布前端，启用 direct-first 与快照兜底。
- 回滚前端时后端新增 `runtimeSnapshot` 字段对旧客户端无破坏。
- 回滚后端时新前端会将缺失可用标记视为不可用并保留可信旧值，不会伪造 `0`。
