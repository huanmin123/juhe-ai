# 前端版本识别与资源恢复设计

## 1. 背景

当前前端在动态路由组件或 CSS chunk 加载失败时，会直接提示“检测到系统前端已更新”，并自动刷新页面。该流程没有读取发布提交、构建标识或服务器版本，因此服务重启、短时 502、客户端网络波动和代理链路异常也会被解释成系统升级。

生产现场已经出现“没有切换 release，但主服务异常退出后由 launchd 自动拉起”的情况。此时旧页面请求尚未加载的 chunk 可能失败，现有文案会造成错误判断。资源失败后的自动恢复本身有价值，应保留一次，但必须把“确认发生版本变化”和“普通资源失败”区分开。

## 2. 目标

- 只有服务器发布的前端 Build ID 与当前页面 Build ID 不同时，才显示“系统已更新”。
- Build ID 相同、版本清单不可用或清单格式非法时，显示中性的资源加载失败文案。
- 首次失败仍自动刷新一次，保留现有恢复能力。
- 同一路径 30 秒内再次失败时停止自动刷新，只提供手动刷新，避免循环。
- 发布包中的 Build ID 必须等于冻结的完整 Git commit，不接受短 SHA、时间戳或随机值。
- 不新增数据库、Redis、业务 API、第三方依赖或生产迁移。

## 3. 非目标

- 不监控后台是否存在新版本，不主动轮询版本。
- 不实现 Service Worker、离线缓存或多版本前端共存。
- 不改变发布切流、launchd、Nginx、Caddy 或 Edge 配置。
- 不处理主服务异常退出的 Redis 根因；最新 `master` 已有独立修复。
- 本任务只完成开发、验证与 Git 集成，不部署生产。

## 4. 方案比较

### 4.1 静态构建清单，采用

构建时将完整 Git commit 同时编译进当前页面，并输出 `frontend/dist/build-info.json`。资源加载失败后，浏览器以 `no-store` 读取 `/__aisys__/build-info.json` 并比较两端 Build ID。

优点是没有业务 API 和存储依赖，发布切换后静态清单自然跟随 release；即使版本检测失败，也能回落到中性恢复。缺点是构建脚本和静态资源缓存规则需要同步维护。

### 4.2 后端版本接口，不采用

后端读取 `RELEASE_SOURCE_COMMIT` 并返回版本。该方案增加运行时接口和发布目录读取耦合，而且主服务短时不可用时版本接口也不可用，不能改善核心故障窗口。

### 4.3 只修改文案，不采用

统一改成“资源加载失败”最简单，但无法识别真实发布，失去对旧 chunk 场景的准确反馈。

## 5. 构建标识

### 5.1 Build ID 来源

Build ID 固定为 40 位小写 Git commit：

1. 发布脚本冻结并校验 `releaseSourceCommit` 后，在执行 `pnpm build` 前设置 `VITE_JUHE_AI_BUILD_ID`。
2. 普通源码构建未显式设置环境变量时，Vite 配置从仓库根目录执行 `git rev-parse HEAD` 作为回退。
3. 非法、空白、非 40 位十六进制值或无法读取 Git commit 时必须使构建失败，禁止生成无法比较的发布包。

PowerShell 与 POSIX 发布脚本都必须使用同一完整提交；现有 `assert-release-source` 继续负责构建前后的源码漂移门禁。

### 5.2 构建产物

Vite 构建同时产生：

- 编译期常量 `__JUHE_AI_FRONTEND_BUILD_ID__`，代表当前已加载页面。
- `frontend/dist/build-info.json`，内容固定为：

```json
{"buildId":"0123456789abcdef0123456789abcdef01234567"}
```

清单只含公开提交标识，不含分支、路径、凭据、时间或环境配置。

## 6. 运行流程

### 6.1 触发入口

继续监听：

- Vite `vite:preloadError`。
- Vue Router `router.onError`。
- `unhandledrejection` 中匹配动态 import、chunk 或 CSS 资源加载失败的错误。

非资源错误仍按现有错误模型处理，不进入版本识别。

### 6.2 首次失败

同一路径超过 30 秒未自动恢复时：

1. 立即登记本次恢复，阻止并发错误重复调度。
2. 以 `cache: 'no-store'` 请求 `/__aisys__/build-info.json`，并附加时间查询参数绕过中间缓存。
3. 请求超时固定为 `1500ms`；超时、非 2xx、JSON 解析失败或 Build ID 非法都归类为“未知”。
4. 根据比较结果选择文案：
   - `changed`：标题“系统已更新”，说明“正在刷新页面以加载最新版本，请稍候。”
   - `same` 或 `unknown`：标题“页面资源加载失败”，说明“正在重新加载页面，请稍候。”
5. 两类结果都在提示展示 `900ms` 后对当前目标路由自动刷新一次。

版本识别只改变反馈语义，不阻断恢复。检测接口不可用时不得猜测发生了发布。

### 6.3 30 秒内再次失败

同一路径 30 秒内再次命中时：

- 不再自动刷新。
- 显示“页面资源加载失败”。
- 说明“自动恢复未成功，请手动刷新页面后重试。”
- 提供“刷新页面”按钮。

该状态不再声称系统更新，即使无法加载版本清单。

## 7. 缓存与服务边界

- `assets/*` 继续使用一年 immutable 缓存；文件名含内容 hash。
- `index.html`、`brand-icon.svg` 和 `build-info.json` 使用 `Cache-Control: no-cache`。
- 客户端请求额外使用 `cache: 'no-store'` 和时间查询参数。
- `build-info.json` 由现有 `express.static` 提供，不新增后端业务路由。
- 本地 Vite dev server 不要求模拟生产清单；资源恢复测试通过可注入 fetch 和构建常量验证。生产构建与本地 preview/后端静态服务验证真实清单。

## 8. 代码边界

- `frontend/vite.config.ts`：解析、校验 Build ID，注入编译常量并生成静态清单。
- `frontend/src/env.d.ts`：声明编译期常量类型。
- `frontend/src/router/frontendBuildInfo.ts`：负责清单请求、校验和 `changed/same/unknown` 分类，不包含弹窗 DOM。
- `frontend/src/router/routeLoadRecovery.ts`：根据分类展示准确文案并执行既有一次性恢复。
- `frontend/src/scripts/regression/route-load-recovery-regression.ts`：固定监听入口、版本分类、文案和防循环契约。
- `frontend/src/scripts/regression/frontend-build-info-regression.ts`：覆盖 Build ID 校验、清单比较和未知状态。
- `frontend/package.json`：登记定向回归命令。
- `scripts/package-release.ps1`、`scripts/package-release.sh`：把冻结提交显式传入前端构建。
- `backend/src/server.ts`：为 `build-info.json` 设置 `no-cache`。
- 相关功能、构建与测试文档同步更新，不改变架构模块关系。

## 9. 错误处理

- 版本清单错误只影响分类，不能形成新的未处理 Promise 拒绝。
- 版本请求超时后主动中止，禁止无界等待。
- Build ID 比较必须先规范化并严格校验，非法值返回 `unknown`，不得把格式错误当作版本变化。
- 弹窗创建失败、sessionStorage 不可用等现有浏览器边界继续保持可恢复，不引入持久全局状态。
- 自动刷新登记发生在异步版本请求之前，避免同一错误风暴并发发起请求或多次刷新。

## 10. 测试与验收

### 10.1 TDD 回归

- 先扩展回归，证明旧实现会因缺少 Build ID 比较和中性文案而失败。
- 覆盖远端 Build ID 不同、相同、请求失败、超时、非法清单。
- 覆盖首次自动刷新和 30 秒内只允许手动刷新。
- 覆盖 PowerShell/POSIX 发布脚本传入完整 commit。
- 覆盖后端对 `build-info.json` 的 `no-cache` 规则。

### 10.2 集成验证

- 前端定向回归与 typecheck。
- 后端相关静态门禁或定向回归。
- 全仓 `pnpm typecheck`、`pnpm build`。
- 构建后读取 `frontend/dist/build-info.json`，确认等于构建提交。
- 通过本地服务或 preview 验证清单响应、页面非空、控制台无新增错误，并模拟不同/相同 Build ID 的恢复提示。
- 不调用真实模型，不需要 PostgreSQL、Redis 或 SQLite 数据重建。

## 11. Git 与交付

- 在从最新 `master` 创建的独立 worktree 开发。
- 设计文档、实施计划、测试和实现按逻辑增量提交。
- 开发中在文档完成、实现完成和最终合并前分别检查远端 `master`；有新提交时先合并并重跑贴近验证。
- 全部验证通过后，将开发分支合入 `master` 并推送远端。
- 再将远端最新 `master` 合入 `feature/20260706-go`，保留该分支自身历史并推送远端。
- 不创建上线计划、不获取生产部署锁、不上传发布包、不修改生产服务；上线等待用户另行通知。
