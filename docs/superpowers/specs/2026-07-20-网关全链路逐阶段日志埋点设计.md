# 网关全链路逐阶段日志埋点设计

## 1. 背景与目标

2026-07-20 生产 trace `d75c1a65-a20a-4bc9-9893-da6ce54c587a` 显示：HTTP request context 比审计起点早 `9.003s`，审计起点到首次上游 attempt 又有 `13.017s`。现有 payload metadata 只能给出若干累计时间点，JSON worker 日志没有 `traceId`，无法把 runtime 解析、请求体接收、Redis 健康状态、配额、容量、并发槽和上游流式传输分别定量。

本次目标是为网关请求链路增加生产默认常开的逐阶段 `info` 结构化日志，使下次问题发生后能够按 `traceId` 重建完整时间线。埋点必须是 fail-open 的诊断能力：日志写入、轮转、索引、搜索或 Redis 异常都不得等待、拒绝或拖慢业务请求。

## 2. 范围

### 2.1 本次实现

- 从 `requestContextMiddleware` 开始记录，覆盖正式 audit 之前的 runtime/API Key 预解析和请求体中间件。
- 每个完成的业务阶段输出一条 `gateway.request.stage` info 日志；原始 JSONL 由当前角色文件 durable spool 保全。
- 请求完成或提前失败时输出一条 `gateway.request.timing_summary` info 日志。
- JSON worker 任务携带 `traceId`、stage 和本地 job id，使 worker 排队、执行与原请求可直接关联。
- Node 日志使用 Pino 序列化后经异步 `fs` stream 顺序追加角色 JSONL；Go 使用有界 normal/failure/emergency `slog` 通道。runtime-log 索引只由 ingest-worker 从文件 cursor 消费。
- 复用现有角色日志文件、保留天数、单文件大小和最大文件数设置。
- runtime log 导入、grep 和详情读取继续使用游标、`rg` 子进程、分块窗口和 background/ingest worker。
- 增加结构契约、时间计算、失败隔离、队列背压、轮转、索引读取和 mock 网关的定向验证。

### 2.2 本次不实现

- 不新增管理端图表、日志 UI 字段或数据库业务列。
- 不把逐阶段数据复制到 audit payload，避免为了日志可视化放大审计存储。
- 不修改路由算法、账户排序、容量或配额策略。
- 不执行生产发布、生产数据写入或生产压测。
- mock 链路能覆盖 fetch/stream 边界时不使用付费真实模型。

## 3. 方案选择

选择“生产默认常开、每阶段一条 info、角色文件 durable spool + ingest-worker 游标索引”方案。

不选择仅 debug 开关，因为问题发生后再开启会丢失现场。实现统一写入当前角色日志文件；Pino 字段组装和 JSON 序列化仍在 server 事件循环，验证报告明确记录这部分非零 CPU 成本。文件 I/O 使用 Node 异步 stream，索引元数据解析由 ingest-worker 从文件读取；runtime-log 不经 Redis 或 IPC line 回传。

## 4. 日志事件契约

### 4.1 阶段日志

统一事件名：`gateway.request.stage`；请求结束汇总事件为 `gateway.request.timing_summary`。

```json
{
  "level": "info",
  "event": "gateway.request.stage",
  "traceId": "uuid",
  "sequence": 7,
  "stage": "account.dispatch_candidates",
  "outcome": "success",
  "startedOffsetMs": 12.318,
  "endedOffsetMs": 14.207,
  "durationMs": 1.889,
  "requestLane": "responses_text",
  "trafficSource": "gateway",
  "model": "gpt-5.6-sol",
  "candidateCount": 14,
  "eligibleCount": 11
}
```

时间字段全部使用 `performance.now()` 的单调时钟差值，保留三位小数。`startedOffsetMs` 和 `endedOffsetMs` 是相对 request context 起点的偏移，`durationMs` 只是当前阶段的局部增量。字段名显式区分累计偏移和局部耗时，禁止把多个累计值相加。

`outcome` 固定为 `success | skipped | expected_failure | unexpected_failure | aborted`。可预知失败记录稳定 reason code 和决策参数；不可预知失败记录有界的原始 Error/cause/stack 现场。

### 4.2 汇总日志

统一事件名：`gateway.request.timing_summary`。它在 HTTP `finish/close` 后通过 `setImmediate` 生成客户可见时间线；audit finalize 作为 `audit.finalize` 阶段单独记录，避免把写盘或索引等待混入客户延迟。

汇总日志包含：

- `traceId`、method、规范化 path、traffic source、request lane、model、stream。
- 结果、HTTP status、account/group 内部 ID、attempt count。
- `totalDurationMs`、`preAuditDurationMs`、`preUpstreamDurationMs`、`upstreamHeadersDurationMs`、`firstOutputDurationMs`、`upstreamBodyDurationMs`、`downstreamFinishDurationMs`。
- `stageCount`、`timingLogDroppedCount`、`timingLogQueuePeakCount`、`timingLogQueuePeakBytes`。

### 4.3 捕获边界

本次 timing 事件不主动扩大普通日志捕获范围，不复制以下高体积内容：

- 客户请求体、上游请求体、上游响应体、流式 delta。
- 大型 headers、完整上游响应和重复的原始审计 payload。

字段一旦进入普通日志，按项目权威《安全与日志策略》的原文保留规则处理；本层不新增字段名匹配、字符串扫描或凭据替换。风险控制放在调用点捕获范围、权限、保留期、字段/深度/总量预算与截断标记。

### 4.4 失败日志原则

失败日志优先级高于普通阶段日志，并分为两类：

- **不可预知失败**：没有稳定业务原因码、不符合已知边界、异常类型或返回结构未被分类时，必须记录有界完整现场：`error.name`、`message`、`stack`、`code`、`cause` 递归链、当前 stage、已完成 stage 摘要、trace/request/attempt ID、HTTP 与路由上下文、队列和运行态快照及实际决策参数。这类事件以 `error` 级别进入失败预留队列。
- **可预知失败**：已有稳定 reason code 和分支契约时，必须记录该决策实际使用的参数：阈值、当前值、候选数、被拒绝数、容量/并发状态、后备决策、HTTP status、stage 耗时和稳定原因码。不记录不参与决策的频繁原始字段。

“完整现场”指可用于复现和定位的结构化上下文，受项目既有捕获范围、权限、保留期、字段深度和总量预算约束。详细错误日志必须有界，单个字段或整个事件超限时保留类型、大小、hash 和 truncation 原因，不静默删除现场。

## 5. 阶段清单

阶段名是稳定的日志契约，实现不得使用动态函数名作为 stage；当前 TypeScript 枚举位于 `backend/src/shared/request-context.ts`。

| 顺序 | stage | 起点和终点 |
| ---: | --- | --- |
| 1 | `body.admission` / `body.speed_first_admission` | Content-Length 与速度优先高并发准入 |
| 2 | `body.receive` / `body.capture` | raw body 接收、JSON 元数据与捕获完成 |
| 3 | `runtime_resolution` / `request.accepted` | runtime/API Key 解析与 handler 入口 |
| 4 | `route.group_access` | 分组权限读取 |
| 5 | `client.profile` / `protocol.bridge` | 客户画像与协议桥接决策 |
| 6 | `account.load_candidates` / `model.capability_filter` | 候选账户读取与模型能力筛选 |
| 7 | `account.session_affinity` / `account.runtime_suppression` | 会话亲和与本地抑制 |
| 8 | `account.latency_degradation` / `account.proxy_health` | 延迟降级与上游桶健康排序 |
| 9 | `account.client_ip_avoidance` / `account.codex_turn_avoidance` | 客户 IP 与 Codex turn 避让 |
| 10 | `quota.batch_decision` / `capacity.account_snapshot` | 配额 batch 与账户容量快照 |
| 11 | `capacity.client_ip_concurrency` / `account.dispatch_candidates` | IP 槽与最终候选整理 |
| 12 | `account.concurrency_acquire` | 账户并发槽等待/获取；每个真实尝试可重复出现 |
| 13 | `upstream.request_prepare` | 账户凭据选择、代理选择、header/body 构造 |
| 14 | `upstream.fetch_headers` | 单次 fetch 开始到 response headers 可用 |
| 15 | `upstream.first_output` | 派发开始到首个非 heartbeat 输出 |
| 16 | `upstream.body.completed` | headers 可用到上游 body 消费结束/失败 |
| 17 | `downstream.response.completed` / `downstream.finish` | 响应转换、写入及 HTTP finish/close |
| 18 | `audit.finalize` | 审计终态组装与异步入队 |

此外保留 `preflight.completed/rejected/failed`、`upstream.dispatch.completed/failed` 聚合阶段，用于直接定位大段耗时和失败归属。成功 mock 链路实测每个 trace 稳定出现 28 类阶段；生产前置中间件还会增加 runtime/body admission 阶段。

跳过的可选阶段仍输出 `outcome=skipped`，使缺失日志不会被误解为阶段未执行。请求在 pre-auth/body 早期拒绝时，只要汇总已完成和拒绝的阶段，不伪造后续 skipped 全链。

## 6. 主线程计时与传播

`RequestContext` 增加一个小型 `GatewayRequestTimingContext`，内部保存：

- wall clock 起点（仅用于人类时间显示）。
- monotonic 起点、当前 sequence、活动 stage token 和已完成阶段的有界摘要。
- 已投递、已丢弃、队列峰值等当前请求级计数。

当前实现对外 API 为：

```ts
logRequestStage(stage, fields?, outcome?, stageStartedAt?): void
buildRequestStageLogFields(context, stage, fields, outcome, startedAt, endedAt): Record<string, unknown>
```

调用不返回 Promise，不访问文件、Redis、DB service 或 worker result，不将日志发送失败抛回业务链路。调用方在真实边界保存 `performance.now()` 起点，因此不依赖“上一条日志”推算耗时；误传 `Date.now()` 时公共入口会回退 request monotonic 起点，避免产生万亿毫秒偏移。

## 7. 异步日志管线

### 7.1 Node 主线程与 durable spool

- Pino 在主线程完成小型事件字段组装和 JSON 序列化，随后通过当前角色的 `fs` stream 异步顺序追加完整 JSONL；这是已测量的 CPU 成本，不宣称为零。
- `logRequestStage` 不返回 Promise，不等待文件写回调、索引、Redis 或 worker ACK。Node 主日志文件不采样、不按索引队列丢 timing 行；文件系统错误通过既有错误/进程诊断路径记录，不把索引消费能力转化为请求背压。
- runtime-log 的解析、规范化、hash、索引 DTO 和持久化全部由 `ingest-worker` 从 durable spool 有界追尾完成；不做 IPC line 回传或 runtime-log Redis Stream 双写。
- 不可预知失败额外生成有界 `gateway.request.failure` error 事件；调用不等待落盘或索引确认。进程崩溃时尚未到达文件系统的缓冲属于进程故障边界，不能以同步 fsync 阻塞请求。

### 7.2 文件消费与索引 worker

- `ingest-worker` 负责批量读取角色日志文件、完整行边界、解析/规范化、批量索引、cursor 提交、轮转保护和维护指标。
- timing 事件与同角色运行日志进入 `juhe-ai.log` / `juhe-ai.worker.log` / `juhe-ai.db-service.log` 等既有角色文件，不新增 runtime-log 专用传输文件。
- 文件消费、索引或轮转异常只影响 backlog 和索引可见性，不向业务请求回传异常；原始 JSONL 文件继续作为重启后的重建来源。
- 正常关闭可在 ingest-worker shutdown 阶段做有界 drain；不在 HTTP 完成路径 await 消费或索引 flush。

### 7.3 索引与读取

- file importer 发现所有受控角色 current/rotated 文件，沿用 file identity + truncation generation + byte cursor，单轮最多读 `1 MiB/5000` 行；轮转后 offset 归零不会覆盖旧行。
- ingest-worker 提取索引所需 time/level/trace/event/message/error 元数据，主进程不执行 `JSON.parse`、hash 或逐行回传。
- runtime-log 不使用 Redis stream producer；其他事实队列仍按各自有界 in-flight count/bytes 和 command timeout 运行。
- grep 使用现有 `rg` 子进程和有界输出；不在 Node 事件循环读整个文件再 `split/filter`。
- 详情和列表仍查索引表的游标窗口，不新增实时明细聚合。

## 8. 误差、乱序和失败语义

- worker 写入的 wall-clock `time` 可能晚于业务事件；排序必须使用同 trace 的 `sequence`，时间计算使用 offset/duration，不使用写盘时间。
- 不同 trace 之间不承诺全局写盘顺序。
- 同一 stage token 只能完成一次；重复完成忽略并累加内部诊断计数，不抛错。
- worker 未就绪、已退出、队列满、写盘失败、轮转失败和索引失败都不得改变 HTTP status、账户选择或审计结果。
- 不可预知失败的主 logger.error 仅是保底通道，不得因为保底而在请求路径同步读取文件、fsync、重试 Redis 或等待 worker；其字段范围遵循项目既有日志原文策略，并受本次有界错误现场预算限制。
- 进程崩溃时允许丢失未 flush 的诊断日志；不为了“日志绝不丢”阻塞或同步 fsync 业务路径。

## 9. 配置

逐阶段 info 日志在正常 server 角色默认开启，复用 `JUHE_AI_LOG_LEVEL`、`JUHE_AI_LOG_FILE_ENABLED`、`JUHE_AI_LOG_CONSOLE_ENABLED`、目录、单文件上限、保留天数和最大文件数配置，不建立第二套 timing 开关或保留规则。

## 10. 实现边界

实际新增与调整的责任单元：

- `backend/src/shared/request-context.ts`：阶段枚举、单调计时、sequence、有界摘要和 HTTP 汇总。
- `backend/src/shared/logger.ts`：Pino 序列化后角色文件 JSONL 顺序追加、轮转和清理调度。
- `backend/src/modules/runtime-logs/runtime-log-file-import.service.ts`：file identity + truncation generation + offset 的唯一索引 consumer。
- 网关 pre-auth/body/preflight/dispatch/upstream/response 编排文件：只在真实起止边界调用 begin/complete/point，不改变业务分支。
- runtime log file import/grep 配置：识别 timing 日志文件并保留现有有界窗口。

任何已超过附近可读性上限的大文件，埋点调用只能作为两三行边界代码；时间计算和日志字段构造不得继续堆入编排大文件。

## 11. 测试与验收

### 11.1 结构与单元回归

- 单调时钟：wall clock 回拨不影响 offset/duration，嵌套和并行 stage 耗时正确。
- 契约：阶段名只能使用枚举，字段和失败现场受深度、条目、字符串及总字节预算约束。
- 生命周期：成功、pre-auth 拒绝、body 拒绝、上游失败、客户取消都生成可收口的时间线。

### 11.2 非阻塞与失败注入

- 暂停 file consumer，继续写入多角色 JSONL，验证请求完成不等待索引且原始文件完整增长；恢复后 backlog 完整追平、cursor 只在批次提交后推进。
- 注入文件 write error、长时 backpressure、rotation error、ingest-worker 退出和 cursor 提交失败，验证业务 HTTP 结果不变且 backlog 可在恢复后继续。
- 注入未分类 Error，cause 递归、stack、已完成 stage 快照和大小/截断元数据必须完整出现；注入可预知的配额/容量/并发拒绝，必须能按参数重建决策。
- 对 timing API 做高频调用并采样 event-loop delay/RSS，验证 Node 无同步文件 API、无 runtime-log Redis/DB await，Go normal/failure/emergency 队列有界并输出 drop/lastFailure 证据。
- 对 runtime log importer 构造超大 timing 文件，验证单轮读取上限、完整行 cursor、截断/轮转重置和超长行有界跳过。

### 11.3 链路验收

- SQLite + memory + mock upstream：普通 JSON、`>256 KiB` JSON worker、Responses SSE、上游失败和客户取消。
- 核对 `request_received -> runtime -> body -> candidate/model -> capacity/concurrency -> fetch headers -> first output -> body end -> downstream finish -> audit finalize` 的 trace/sequence/duration。
- PostgreSQL + Redis：使用 `192.168.1.203` 的测试资源和独立临时数据库/命名空间，验证 runtime state、角色日志文件、ingest-worker、cursor 和索引读取；确认 runtime-log Redis Stream 无新写入，不复用共享业务表容器。
- 如本地 SQLite 临时库缺少当前 schema，只删除本次测试生成的临时库并重建；PG 只重建本次专属测试库/测试 schema。
- 真实模型仅在 mock SSE 不能证明的协议边界出现时才从 `D:\模型密钥.txt` 注入，使用前另行确认付费测试必要性。

### 11.4 性能门禁

性能门禁不使用单次绝对毫秒断言，而使用同进程交错对照：

- timing 关闭/开启各至少 5 轮，固定 mock 0ms 上游、账户数和并发度。
- 报告 E2E p50/p95/p99、event-loop p99、CPU/request、RSS peak、file backlog/cursor、Go queue/drop/lastFailure 和日志字节/request；合并前历史数值不得冒充最终指标。
- 必须满足：无日志导致的 HTTP 失败，无内存队列无界增长，无 server 请求等待文件 I/O、索引、Redis/DB；Node 原始 JSONL 不采样/丢行，Go 双 failure 饱和时按有界现场规则记录。如对照显示明显恶化，不得以“日志必须完整”为理由交付，需要返回队列/consumer 设计调整。

## 13. 验收标准

1. 对一个成功或失败的网关请求，可仅用 `traceId` 和 timing 日志还原 audit 前、账户选择、fetch/first output/body、客户完成和 audit finalize 时间线。
2. 每个已执行阶段都有一条 info 结构日志，局部 `durationMs` 和累计 offset 口径明确，不需要通过相邻写盘时间猜测。
3. JSON worker 完成日志可严格关联 trace，包含 queue wait 和 worker duration，不再只能按尺寸/时间推测。
4. 日志 writer 慢、断开、满载、轮转失败和索引失败的注入测试均证明 HTTP 不等待、不失败，内存队列有界。
5. 日志读取、导入、grep、轮转和清理保持异步/子进程/游标分块，不新增整文件同步读取或请求时明细聚合。
6. SQLite+memory 定向回归、PostgreSQL+Redis 真实测试拓扑、backend typecheck/build 和性能交错对照通过。
7. 文档、代码、测试和验证报告不含密码、连接串、token 或完整 payload。
8. 改动已合并并推送到 `master` 和 `feature/20260706-go`，且没有执行生产上线。
