# 网关全链路逐阶段日志埋点设计

## 1. 背景与目标

2026-07-20 生产 trace `d75c1a65-a20a-4bc9-9893-da6ce54c587a` 显示：HTTP request context 比审计起点早 `9.003s`，审计起点到首次上游 attempt 又有 `13.017s`。现有 payload metadata 只能给出若干累计时间点，JSON worker 日志没有 `traceId`，无法把 runtime 解析、请求体接收、Redis 健康状态、配额、容量、并发槽和上游流式传输分别定量。

本次目标是为网关请求链路增加生产默认常开的逐阶段 `info` 结构化日志，使下次问题发生后能够按 `traceId` 重建完整时间线。埋点必须是 fail-open 的诊断能力：日志写入、轮转、索引、搜索或 Redis 异常都不得等待、拒绝或拖慢业务请求。

## 2. 范围

### 2.1 本次实现

- 从 `requestContextMiddleware` 开始记录，覆盖正式 audit 之前的 runtime/API Key 预解析和请求体中间件。
- 每个完成的业务阶段输出一条 `gateway_request_stage_timing` info 日志。
- 请求完成或提前失败时输出一条 `gateway_request_timing_summary` info 日志。
- JSON worker 任务携带 `traceId`、stage 和本地 job id，使 worker 排队、执行与原请求可直接关联。
- 日志生成使用专用 worker thread、有界主线程队列、有界 worker 队列和异步文件流。
- 专用日志文件复用现有保留天数、单文件大小和最大文件数设置。
- runtime log 导入、grep 和详情读取继续使用游标、`rg` 子进程、分块窗口和 background/ingest worker。
- 增加结构契约、时间计算、失败隔离、队列背压、轮转、索引读取和 mock 网关的定向验证。

### 2.2 本次不实现

- 不新增管理端图表、日志 UI 字段或数据库业务列。
- 不把逐阶段数据复制到 audit payload，避免为了日志可视化放大审计存储。
- 不修改路由算法、账户排序、容量或配额策略。
- 不执行生产发布、生产数据写入或生产压测。
- mock 链路能覆盖 fetch/stream 边界时不使用付费真实模型。

## 3. 方案选择

选择“生产默认常开、每阶段一条 info、专用异步 worker 写入”方案。

不选择仅 debug 开关，因为问题发生后再开启会丢失现场。不直接把所有阶段继续写到主 `juhe-ai.log`，因为现有 Pino JSON 序列化、`MultiDestinationLogStream`、行索引拆分和 writable 缓冲仍有一部分工作在 server 事件循环中完成；突发流量下把每个请求放大为多条主日志会增加同一个瓶颈。

## 4. 日志事件契约

### 4.1 阶段日志

统一事件名：`gateway_request_stage_timing`。

```json
{
  "level": "info",
  "event": "gateway_request_stage_timing",
  "traceId": "uuid",
  "sequence": 7,
  "stage": "candidate_window",
  "outcome": "completed",
  "startedOffsetMs": 12.318,
  "endedOffsetMs": 14.207,
  "durationMs": 1.889,
  "requestLane": "responses_text",
  "trafficSource": "gateway",
  "model": "gpt-5.6-sol",
  "candidateCount": 14,
  "eligibleCount": 11
}
```

时间字段全部使用 `performance.now()` 的单调时钟差值，保留三位小数。`startedOffsetMs` 和 `endedOffsetMs` 是相对 request context 起点的偏移，`durationMs` 只是当前阶段的局部增量。字段名显式区分累计偏移和局部耗时，禁止把多个累计值相加。

`outcome` 取值为 `completed | skipped | rejected | failed | aborted`。失败只记录稳定的错误 phase/code，不记录可能携带凭据或 payload 的原始 Error 字符串。

### 4.2 汇总日志

统一事件名：`gateway_request_timing_summary`。它在 HTTP `finish/close` 时生成客户可见时间线，在 audit finalize 完成后再生成 `gateway_request_audit_finalize_timing`，避免把 HTTP 返回后耗时混入客户延迟。

汇总日志包含：

- `traceId`、method、规范化 path、traffic source、request lane、model、stream。
- 结果、HTTP status、account/group 内部 ID、attempt count。
- `totalDurationMs`、`preAuditDurationMs`、`preUpstreamDurationMs`、`upstreamHeadersDurationMs`、`firstOutputDurationMs`、`upstreamBodyDurationMs`、`downstreamFinishDurationMs`。
- `stageCount`、`timingLogDroppedCount`、`timingLogQueuePeakCount`、`timingLogQueuePeakBytes`。

### 4.3 禁止字段

日志不得包含：

- Authorization、API Key 明文、OAuth token、Cookie、代理凭据。
- 客户请求体、上游请求体、上游响应体、流式 delta。
- 完整上游 URL 或 query string；仅允许 provider code、endpoint family 和去凭据 origin hash。
- 原始 user-agent、原始 client IP；现有请求日志如仍需要这些字段，不通过本次 timing 事件再复制。

## 5. 阶段清单

阶段名是稳定的日志契约，实现不得使用动态函数名作为 stage。

| 顺序 | stage | 起点和终点 |
| ---: | --- | --- |
| 1 | `request_received` | request context 建立时的点事件 |
| 2 | `runtime_resolution` | `preResolveGatewayRuntime` 进入到 runtime/API Key 结果确定 |
| 3 | `request_body_admission` | body admission 进入到放行/拒绝 |
| 4 | `request_body_receive` | raw parser 进入到完整 body 交给后续中间件 |
| 5 | `json_metadata_extract` | JSON worker enqueue 到 metadata result，附带 queue/worker 局部耗时 |
| 6 | `request_body_capture` | audit raw body capture 进入到完成 |
| 7 | `gateway_handler_enter` | handler 建立 audit 的点事件 |
| 8 | `client_strategy` | 客户画像/协议策略解析 |
| 9 | `candidate_window` | 分组候选窗口读取与 hydration |
| 10 | `protocol_bridge` | 协议桥接决策与请求形态确定 |
| 11 | `model_filter` | supported model/映射筛选完成 |
| 12 | `local_suppression` | 本地抑制和 precheck |
| 13 | `latency_degradation` | 普通路由首字延迟降级读取/排序 |
| 14 | `upstream_bucket_health` | Redis/memory 上游桶状态读取、half-open 选择与必要写回 |
| 15 | `client_ip_avoidance` | client IP 账户回避读取/排序 |
| 16 | `codex_turn_avoidance` | Codex turn 失败账户回避 |
| 17 | `authorization_quota` | 授权配额 batch 决策 |
| 18 | `capacity_ordering` | lane 容量刷新、busy 判定和排序 |
| 19 | `client_ip_concurrency` | 高并发组 client IP 槽申请 |
| 20 | `account_concurrency` | 账户并发槽等待/获取 |
| 21 | `upstream_request_prepare` | 账户凭据选择、代理选择、header/body 构造 |
| 22 | `upstream_fetch_headers` | fetch 开始到 response headers 可用 |
| 23 | `first_output` | fetch 开始到首个非 heartbeat 输出 |
| 24 | `upstream_body` | headers 可用到上游 body 消费结束/失败 |
| 25 | `downstream_finish` | 首次下游提交到 HTTP finish/close |
| 26 | `audit_finalize` | HTTP 完成到 audit finalize 完成 |

跳过的可选阶段仍输出 `outcome=skipped`，使缺失日志不会被误解为阶段未执行。请求在 pre-auth/body 早期拒绝时，只要汇总已完成和拒绝的阶段，不伪造后续 skipped 全链。

## 6. 主线程计时与传播

`RequestContext` 增加一个小型 `GatewayRequestTimingContext`，内部保存：

- wall clock 起点（仅用于人类时间显示）。
- monotonic 起点、当前 sequence、活动 stage token 和已完成阶段的有界摘要。
- 已投递、已丢弃、队列峰值等当前请求级计数。

对外 API 只提供：

```ts
beginGatewayRequestStage(stage, fields?): GatewayTimingStageToken
completeGatewayRequestStage(token, outcome?, fields?): void
recordGatewayRequestTimingPoint(stage, fields?): void
finalizeGatewayRequestTiming(input): void
```

`complete`/`record` 不返回 Promise，不访问文件、Redis、DB service 或 worker result，不将日志发送失败抛回业务链路。阶段 token 记录本地起点，能正确表达嵌套和并行阶段，不依赖“上一条日志”推算耗时。

## 7. 异步日志管线

### 7.1 主线程 publisher

- 当前 tick 只向有界 batch 数组追加小型可结构化对象。
- 通过 `setImmediate` 合并同 tick 事件，一次 `worker.postMessage(batch)`，不在主线程 `JSON.stringify`。
- 按 event count 和 estimated bytes 双重有界；不得依赖 V8 无界 worker message queue。
- worker 在写入完成后返回 ack，主线程才释放 in-flight 计数。
- 达到上限立即丢弃 timing 事件并计数，业务请求继续。主日志最多每 60 秒输出一条脱敏的 `gateway_timing_log_dropped` warn。

### 7.2 timing worker

- worker 负责 Pino/JSON 序列化、UTF-8 字节计数、异步写盘、backpressure/drain 和文件轮转。
- 日志文件名为 `juhe-ai.gateway-timing.log`，轮转文件使用不冲突的 timing 前缀。
- worker 自身队列也按 bytes/count 有界；文件系统持续慢或不可用时记录 drop 计数并通知 publisher，不向业务请求回传异常。
- 正常关闭可在进程 shutdown 阶段做有界 flush；不在 HTTP 完成路径 await flush。

### 7.3 索引与读取

- file importer 把 timing current file 作为第四个 active log file，沿用 file identity + byte cursor，单轮最多读 `1 MiB/5000` 行。
- Redis stream producer 继续使用有界 in-flight count/bytes 和 command timeout，投递失败丢弃索引事件而不反压 server。
- grep 使用现有 `rg` 子进程和有界输出；不在 Node 事件循环读整个文件再 `split/filter`。
- 详情和列表仍查索引表的游标窗口，不新增实时明细聚合。

## 8. 误差、乱序和失败语义

- worker 写入的 wall-clock `time` 可能晚于业务事件；排序必须使用同 trace 的 `sequence`，时间计算使用 offset/duration，不使用写盘时间。
- 不同 trace 之间不承诺全局写盘顺序。
- 同一 stage token 只能完成一次；重复完成忽略并累加内部诊断计数，不抛错。
- worker 未就绪、已退出、队列满、写盘失败、轮转失败和索引失败都不得改变 HTTP status、账户选择或审计结果。
- 进程崩溃时允许丢失未 flush 的诊断日志；不为了“日志绝不丢”阻塞或同步 fsync 业务路径。

## 9. 配置

逐阶段 info 日志在正常 server 角色默认开启。配置只用于安全门禁和测试隔离，不把日志默认变成 debug 开关：

- `JUHE_AI_GATEWAY_TIMING_LOG_ENABLED=true|false`：生产默认 `true`，测试可显式关闭。
- `JUHE_AI_GATEWAY_TIMING_LOG_MAX_IN_FLIGHT_EVENTS`、`...MAX_IN_FLIGHT_BYTES`：严格整数范围。
- 文件目录、保留天数、单文件上限和最大文件数复用 `runtimeConfig.log`，不再建第二套保留配置。

非 server 角色和不运行网关的脚本不启动 timing worker。

## 10. 实现边界

预计新增与调整的责任单元：

- `backend/src/modules/gateway/observability/request-timing.ts`：单调阶段计时、契约和 request-context 操作。
- `backend/src/modules/gateway/observability/timing-log-publisher.ts`：主线程有界 batch、worker 生命周期、ack/drop snapshot。
- `backend/src/modules/gateway/observability/timing-log-worker.ts`：序列化、异步写盘和轮转。
- `backend/src/shared/rotating-file-log-stream.ts`：从现有 logger 抽出可复用的轮转文件 stream，主 logger 保持行为不变，timing worker 复用同一边界。
- `backend/src/shared/request-context.ts`：建立 timing context，不把详细阶段数组放入 logger child fields。
- 网关 pre-auth/body/preflight/dispatch/upstream/response 编排文件：只在真实起止边界调用 begin/complete/point，不改变业务分支。
- runtime log file import/grep 配置：识别 timing 日志文件并保留现有有界窗口。

任何已超过附近可读性上限的大文件，埋点调用只能作为两三行边界代码；时间计算、日志字段构造和 publisher 不得继续堆入编排大文件。

## 11. 测试与验收

### 11.1 结构与单元回归

- 单调时钟：wall clock 回拨不影响 offset/duration，嵌套和并行 stage 耗时正确。
- 契约：阶段名只能使用枚举，字段只包含允许的 primitive/count/hash，敏感键值被拒绝。
- 生命周期：成功、pre-auth 拒绝、body 拒绝、上游失败、客户取消都生成可收口的时间线。

### 11.2 非阻塞与失败注入

- 使用不 ack 的 fake worker，验证请求完成不等待 worker，publisher 达上限后丢弃而不无界增长。
- 注入 worker exit、postMessage throw、文件 write error、长时 backpressure 和 rotation error，验证业务 HTTP 结果不变。
- 对 timing API 做高频调用并采样 event-loop delay/RSS，验证队列有界、无同步文件 API、无每条日志 Redis/DB await。
- 对 runtime log importer 构造超大 timing 文件，验证单轮读取上限、完整行 cursor、截断/轮转重置和超长行有界跳过。

### 11.3 链路验收

- SQLite + memory + mock upstream：普通 JSON、`>256 KiB` JSON worker、Responses SSE、上游失败和客户取消。
- 核对 `request_received -> runtime -> body -> candidate/model -> capacity/concurrency -> fetch headers -> first output -> body end -> downstream finish -> audit finalize` 的 trace/sequence/duration。
- PostgreSQL + Redis：使用 `192.168.1.203` 的测试资源和独立临时数据库/命名空间，验证 runtime state、runtime log Redis stream、ingest worker 和索引读取；不复用共享业务表容器。
- 如本地 SQLite 临时库缺少当前 schema，只删除本次测试生成的临时库并重建；PG 只重建本次专属测试库/测试 schema。
- 真实模型仅在 mock SSE 不能证明的协议边界出现时才从 `D:\模型密钥.txt` 注入，使用前另行确认付费测试必要性。

### 11.4 性能门禁

性能门禁不使用单次绝对毫秒断言，而使用同进程交错对照：

- timing 关闭/开启各至少 5 轮，固定 mock 0ms 上游、账户数和并发度。
- 报告 E2E p50/p95/p99、event-loop p99、CPU/request、RSS peak、timing queue peak/drop count 和日志字节/request。
- 必须满足：无日志导致的 HTTP 失败，无队列无界增长，无 server 请求等待 worker ack/write/Redis/DB，且默认档对照没有稳定性长尾恶化。如对照显示明显恶化，不得以“日志必须完整”为理由交付，需要返回 publisher/worker 设计调整。

## 13. 验收标准

1. 对一个成功或失败的网关请求，可仅用 `traceId` 和 timing 日志还原 audit 前、账户选择、fetch/first output/body、客户完成和 audit finalize 时间线。
2. 每个已执行阶段都有一条 info 结构日志，局部 `durationMs` 和累计 offset 口径明确，不需要通过相邻写盘时间猜测。
3. JSON worker 完成日志可严格关联 trace，包含 queue wait 和 worker duration，不再只能按尺寸/时间推测。
4. 日志 writer 慢、断开、满载、轮转失败和索引失败的注入测试均证明 HTTP 不等待、不失败，内存队列有界。
5. 日志读取、导入、grep、轮转和清理保持异步/子进程/游标分块，不新增整文件同步读取或请求时明细聚合。
6. SQLite+memory 定向回归、PostgreSQL+Redis 真实测试拓扑、backend typecheck/build 和性能交错对照通过。
7. 文档、代码、测试和验证报告不含密码、连接串、token 或完整 payload。
8. 改动已合并并推送到 `master` 和 `feature/20260706-go`，且没有执行生产上线。
