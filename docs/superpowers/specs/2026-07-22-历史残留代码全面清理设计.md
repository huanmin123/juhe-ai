## 2. 目标

本次工作以当前项目事实和当前正式入口为准，删除没有真实消费者的生产代码、测试代码、脚本、配置、生成物和依赖，收敛前端、Node 后端、Go 后端与构建链中的历史残留。

完成后必须满足：

1. 当前正式前端页面、Node 服务、Node worker、DB service、Go 命令、管理接口、公开接口、网关、维护脚本和发布流程保持可用。
2. 不为尚未接入的远期能力保留生产实现；仅有单元测试或历史计划、但没有正式运行入口的代码应删除。
3. 动态 worker、条件路由、维护命令、迁移文件、生成器、发布检查、备份恢复和负向防复活测试不能因普通 import 图不可达而误删。
4. TypeScript 未使用声明、孤立文件、Go 不可达包、过期测试入口和重复构建产物得到系统清理。
5. 形成可重复执行的检查门禁，降低后续再次积累死代码的概率。
6. 所有必要测试通过后合并到本地 `master` 并推送远程；不执行生产上线，上线时间等待用户另行通知。

## 3. 非目标

- 不借清理任务改变当前业务模型、权限、路由语义、错误语义或数据统计口径。
- 不把 Node 到 Go 的生产切流、生产部署或上线包含在本次范围内。
- 不主动删除当前仍由 Node 持有的生产 owner，仅因为 Go 中存在同名实现就判定 Node 为历史代码。
- 不删除仍有正式条件入口的 Go opt-in 管理接口、公开接口、worker 命令、maintenance smoke 和迁移 bridge。
- 不删除防止历史功能复活的负向契约测试；需要调整时，应把守卫迁移到新的事实边界。
- 不顺手实施与死代码清理无关的架构重写、性能优化、样式调整或兼容层新增。

## 4. “真实使用”判定

代码、脚本、配置或测试满足以下任一条件，即视为真实使用并默认保留：

1. 从 `frontend/src/main.ts`、前端 router、Node `server.ts`、`worker.ts`、`db-service.ts`、Go `cmd/*` 等正式入口可达。
2. 被 `package.json` script、Go 子命令、部署脚本、维护命令、发布 preflight 或真实 smoke 直接调用。
3. 通过 `spawn`、`fork`、Worker 文件路径、动态 import、registry、队列任务名、反射或生成清单调用。
4. 由正式环境变量、feature flag 或迁移期 opt-in 控制，且对应路由、命令或维护流程已经注册。
5. 属于数据库 migration、schema、sqlc 查询、生成器输入/输出、离线升级、备份恢复或发布验证资产。
6. 属于当前文档明确要求保留的兼容入口、重新启用能力、回滚能力或旧生产 owner。
7. 属于防止已经删除的字段、路由、worker 角色或历史功能重新出现的负向回归测试。

以下情况不单独构成真实使用：

- 仅被自身单元测试调用的生产函数或生产包。
- 仅在历史计划、历史重构记录或注释中提到，当前事实文档没有保留要求。
- 仅作为“以后可能接入”的脚手架存在，没有正式 cmd、router、worker、maintenance 或部署入口。
- 仅有同目录文件互相引用，但整个目录不在任何正式入口依赖闭包中。
- 只为了让旧回归脚本继续通过而保留、但该回归不再保护当前业务行为的实现。

“没有静态 import”只用于生成候选，不能单独作为删除证据。

## 5. 删除证据门槛

每个删除簇至少完成以下检查：

1. 静态引用：使用 `rg`、TypeScript import 图或 Go import 图确认普通消费者。
2. 动态入口：检查 Worker、fork、spawn、动态 import、文件路径、任务 registry、队列名和环境开关。
3. 命令入口：检查根、前端、后端 package scripts，Go `cmd/*`，部署、维护和 smoke 命令。
4. 文档事实：核对架构、functions、migration、develop、deploy 和当前进行中的计划。
5. Git 历史：确认替代实现已经完整落地，不存在尚未完成的接线或生产切流门禁。
6. 数据 owner：确认相关 schema、队列、定时任务、缓存和数据写 owner 不再依赖候选代码。
7. 测试语义：确认相关测试是在保护当前行为，还是只在直接调用已经脱离生产的实现。

有以下任一情况时不能直接删除：

- 候选代码负责构造仍需投递的数据，但调用链可能因重构遗漏。
- 当前功能文档仍把候选描述为正式行为。
- 生产 owner、切流、回滚或真实依赖 smoke 尚未完成。
- 删除会同时改变 API、数据或用户行为，而需求没有批准该行为变化。

这类候选先按问题修复流程判断“恢复接线”还是“正式取消”，不能把潜在缺陷伪装成垃圾清理。

## 7. 实施结构

### 7.1 第一阶段：建立失败门禁

在删除代码前先建立或启用检查，使当前死代码产生可解释的失败：

- TypeScript 未使用本地声明检查。
- 前端、Node 入口可达性检查，包含显式动态入口清单。
- Go 正式 cmd 包依赖差集检查。
- package script、维护脚本和文档入口一致性检查。

门禁必须能区分动态入口、测试 helper、migration 和 feature flag，不以简单文件名或引用次数直接判死。

### 7.2 第二阶段：前端清理

- 删除经证据确认的孤立 composable、组件、helper 和旧事件链。
- 删除未使用 import、局部函数、变量和类型。
- 对只被测试调用的 helper，确认生产实现已经内联或替代后同步调整测试。
- 调整 Vite 配置 typecheck/build/dev 链，删除 tracked `.js/.d.ts` 生成物并防止重新生成。
- 运行前端类型、构建、相关回归和浏览器 smoke。

### 7.3 第三阶段：Node 清理

- 先删除明确退役或无消费者的文件和私有函数。
- 对账户清理、Chat 初始化等疑似漏接线代码先补失败测试，决定恢复接线还是取消能力。
- 保留所有已证明的动态 worker、DB service、维护进程和 Node 当前生产 owner。
- 删除代码后同步更新 package scripts、源码契约测试和当前事实文档。

### 7.4 第四阶段：Go 清理

- 删除 9 个未进入任何正式 cmd 的业务包及其专用 port/store/test。
- 删除可达包中已被新入口替代、只被测试调用的旧 handler 和 factory。
- 保留正式 opt-in router、已注册 worker、maintenance smoke、migration、sqlc、testkit 和 Node bridge。
- 重新执行 `go list` 差集、`go test ./...`、race、vet 和 tidy diff。

### 7.5 第五阶段：脚本、依赖与文档收口

- 删除被替代的孤儿 helper、过期测试入口和不再保护当前行为的回归。
- 把仍有价值但漏挂的测试接入明确 package script，避免“无入口但实际重要”。
- 删除功能簇后重新扫描前后端依赖和 Go module，不提前删除当前仍有真实引用的依赖。
- 更新 architecture、functions、migration、develop、plans 和 refactors 中受影响的当前事实。

## 8. 子 agent 协作

设计、候选识别和最终复查使用多个并行只读审计 agent，按前端、Node、Go、测试脚本、构建依赖和文档历史分域。

实现阶段为了避免共享工作区冲突，生产代码修改按独立任务串行交给 fresh implementer agent；每个任务完成后依次执行：

1. 实现 agent 自审和定向测试。
2. 独立 spec compliance reviewer 核对范围和删除证据。
3. 独立 code quality reviewer 核对误删风险、动态入口、边界和测试质量。

不同领域的只读复核和测试分析可以并行，但多个实现 agent 不同时编辑共享文件。

## 10. 风险控制与回滚

- 所有工作在独立 worktree 和 `codex/dead-code-cleanup-20260722` 分支完成。

## 11. master 同步与集成

开发分支在以下时点 fetch 并 merge 最新 `origin/master`：

1. 候选清单冻结前。
2. 每个主要删除批次开始前。
3. 开发超过一个工作日或 master 新增约 20 个提交时。
4. 最终验证前。

每次同步要求工作树干净；同步后重新运行入口扫描、文档门禁、定向测试和基础 typecheck。master 新增调用或 owner 要求时，旧候选自动失效，必须重新审计。

最终流程：

1. feature 分支合并最新 `origin/master`。
2. 在 feature 分支完成全量验证和最终独立代码审查。
3. 检查原始 `master` 工作区的用户未提交修改，禁止覆盖、stash、restore 或 reset 用户内容。
4. 在不影响用户修改的前提下把 feature 分支合并到本地 `master`。
5. 在合并后的 master 重新执行必要验证。
6. 推送远程 `master`。
7. 不执行部署或生产切流，等待用户通知上线。

如果原始 master 的未提交修改与合并内容重叠，停止集成并报告冲突，不擅自处理用户修改。
