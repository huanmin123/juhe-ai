## 2. 问题与现场证据

生产高性能模式当前把 `JUHE_AI_REDIS_STATE_URL` 与 `JUHE_AI_REDIS_QUEUE_URL` 都指向 `127.0.0.1:6380/0`。同一 Redis 进程同时承担两类性质不同的负载：

1. 低延迟运行态：账号和 Client IP 并发租约、等待队列、限频、登录保护、分布式锁、恢复探针、会话亲和、缓存失效版本和配额快照。
2. Redis Streams 可靠队列：usage、audit、operation、public API、runtime log 和 record maintenance。

2026-07-19 只读核查得到：

| 项目 | 6379 cache | 6380 state + queue |
| --- | ---: | ---: |
| `used_memory` | 约 12.5 MB | 约 46.6 MB |
| 历史峰值 | 约 19.7 MB | 约 143.5 MB |
| `maxmemory` | 768 MB | 2 GB |
| 淘汰策略 | `allkeys-lru` | `noeviction` |
| AOF | 关闭 | 开启，`appendfsync everysec` |
| AOF 文件 | 不适用 | 约 1.05 GB，base 约 14.4 MB |
| 负载 | 约 53 ops/s | 约 631 ops/s |

主机有 16 GB 内存，磁盘剩余约 347 GB；两实例均无淘汰、拒绝连接或内存不足证据。当前问题不是 Redis 内存容量不足，而是共享进程中的 AOF 写放大和重写抖动：重写阈值从 64 MB 调到 1 GB 后，周期从约 20 至 30 秒延长为约 11 至 12 分钟，但重写期间仍出现 runtime-log XADD 超时、连接异常和主 Node 进程被 launchd 恢复。

## 3. 约束澄清

“Redis 数据允许丢失，最终事实在 PostgreSQL”只适用于 cache 和可重建的 runtime state。Redis Stream 中尚未 ACK 的消息在消费者落 PostgreSQL 前仍是唯一副本，不能按普通缓存直接丢弃。

因此以下做法明确禁止：

- 直接在当前共享 6380 上关闭 AOF 或 RDB。
- 把 state 或 queue 改为 `allkeys-lru`、`volatile-ttl` 等淘汰策略。
- 在队列未 drain 时重启、清空或迁移 6380。
- 只改大 AOF 重写阈值后宣称根因已解决。
- 通过吞掉 Redis 错误、返回假成功或删除日志/审计/用量功能换取稳定。

## 4. 目标与非目标

### 4.1 目标

- cache、runtime state、reliable queue 使用三个独立 Redis 进程。
- AOF 重写不再阻塞运行态并发、限频、锁、探针和会话操作。
- 队列保留 `noeviction + AOF everysec`，未落库消息不因切换丢失。
- runtime state 关闭 AOF/RDB，重启后由流量、PostgreSQL 和后台任务重建。
- 单次 Redis 断连、命令超时或重连错误不再升级为 Node `uncaughtException` 或立即 fatal。
- Redis 状态故障时按数据等级受控降级：关键运行态写失败时 fail-closed，非核心记录队列失败时有界失败并记录指标。
- 在现有 16 GB 主机上完成，不以扩容掩盖写放大根因。

### 4.2 非目标

- 不把 Redis 改为业务最终事实库。
- 不为旧的共享 Redis 拓扑保留长期兼容分支。
- 不在本次顺带重构所有后台任务、记录 payload 或统计链路。
- 不承诺 queue Redis 在 AOF 重写时绝对零延迟；本次先隔离影响域并建立可量化门禁。
- 不在设计阶段执行生产变更。

## 5. 目标架构

| 角色 | 端口 | 数据 | 持久化 | 淘汰策略 | 初始内存上限 |
| --- | ---: | --- | --- | --- | ---: |
| cache | 6379 | 可重建查询缓存 | `appendonly no`、`save ""` | `allkeys-lru` | 768 MB，保持不变 |
| state | 6380 | 并发租约、限频、锁、探针、临时会话、亲和等 | `appendonly no`、`save ""` | `noeviction` | 首次切换保持 2 GB；稳定观察后再评估 768 MB |
| queue | 6381 | 六类 Redis Streams 和消费组 | `appendonly yes`、`appendfsync everysec`；关闭 RDB | `noeviction` | 2 GB |

`maxmemory` 是上限而非预分配。新增 queue 的 2 GB 上限不会立即占用 2 GB 物理内存，因此当前不需要扩容主机内存。

应用固定使用三个不同 Redis 资源：

```text
JUHE_AI_REDIS_CACHE_URL -> 127.0.0.1:6379/0
JUHE_AI_REDIS_STATE_URL -> 127.0.0.1:6380/0
JUHE_AI_REDIS_QUEUE_URL -> 127.0.0.1:6381/0
JUHE_AI_ALLOW_SHARED_REDIS_URLS=false
```

生产地址判重必须按 Redis 进程资源判断。同一 host:port 即使使用不同 DB，也不算物理隔离。URL 解析必须使用规范化的 scheme、hostname 和显式/默认 port 生成物理资源键，不把 pathname/DB 纳入物理隔离判定；生产 loopback 拓扑只接受 canonical `127.0.0.1`，拒绝 `localhost`、`::1` 或未验证 DNS 别名绕过物理资源判重。

## 6. 数据与请求流

### 6.1 运行态

```text
请求 -> Node/Go 网关 -> 6380 state
                      -> 并发/限频/锁/探针结果
                      -> 成功后继续路由
                      -> 失败时关键路径返回受控 503，不放开限制
```

state 冷启动会失去当前租约、限频窗口、临时锁和亲和关系。切换必须在 main 停止承流且没有在途请求时完成；恢复后新请求重新建立状态。不能在 main 正在承流时直接重启 state。

### 6.2 可靠队列

```text
请求副作用 -> XADD 6381 queue -> consumer group -> PostgreSQL
                                             -> 成功后 XACK + XDEL
```

未 ACK 或 consumer lag 中的消息尚未落库完成。queue 切换前必须同时验证六条 Stream 的 `pending=0` 和 group `lag=0`；只检查 pending 不足以证明 drain。

## 7. AOF 与性能策略

### 7.1 state

state 不持久化，彻底消除运行态进程的 AOF fork、rewrite 和 fsync。保持 `noeviction`，内存不足必须显式 OOM 并触发告警，禁止静默删除并发租约、锁或限频状态。

### 7.2 queue

queue 继续使用 AOF everysec。RDB 与 AOF 重复保护价值有限，关闭 `save` 可减少额外 fork 和磁盘写入。AOF 重写采用分阶段调优：

1. 首次发布以当前已验证的 1 GB 最小重写阈值启动，先证明物理隔离和消息连续性。
2. 记录 30 分钟以上 AOF 增长率、rewrite duration、fork time、XADD P95/P99 和磁盘余量。
3. 只有证据证明 1 GB 仍造成 queue XADD 超时，才在保持磁盘高水位告警的前提下提高到 4 GB；不同时改变 fsync 语义。
4. 不默认启用 `no-appendfsync-on-rewrite yes`，因为它扩大异常断电时未刷盘窗口。若未来采用，必须作为单独可靠性决策。

这样先隔离 state 的延迟，再用 A/B 数据调整 queue，而不是一次改变多个变量后无法归因。

## 8. 进程稳定性与错误模型

### 8.1 初始化失败

启动时配置缺失、三个 Redis URL 共享、Redis 无法建立首次连接或 queue consumer group 无法初始化，继续 fail-fast；服务不能以错误拓扑对外提供成功健康检查。

### 8.2 运行期瞬时失败

- Redis client 的 `error` 事件必须始终有监听器，命令失败通过 Promise 返回给调用方。
- 超时包装器必须处理原命令 Promise 的后续 rejection，禁止超时后产生悬空 rejection。
- 单次 `ECONNRESET`、`Socket closed unexpectedly`、connect timeout 或 command timeout 不调用进程级 fatal。
- state 关键写失败：当前请求 fail-closed，返回受控 503 或既有错误模型；不得当作成功，也不得放宽并发、限频或锁。
- queue 非核心记录失败：按各 producer 的既有有界策略记录 drop/reason/bytes，不能改变主请求 HTTP 成功结果，也不能触发进程退出。
- 持续故障：readiness 进入 degraded/not-ready，watchdog 按既有有界策略处理；恢复连接后自动退出降级状态。

### 8.3 fatal 保留边界

真正不可恢复的配置错误、进程内部不变量破坏和数据库核心持久化损坏仍可 fatal。不能用“Redis 发生过错误”作为统一 fatal 条件。实现前必须用回归定位当前主进程退出的具体调用链，逐条移除不恰当的 fatal 升级，不改写全局 `uncaughtException` 最终兜底。

六类 queue producer 的运行期边界固定如下：

| Stream | Redis 瞬时失败（尚未 XADD） | 已 XADD 未 ACK | 重复投递验收 |
| --- | --- | --- | --- |
| usage | 最多 3 次有界重试；耗尽返回明确 enqueue failure，不调用 process fatal；调用方不得伪造已接受 | 必须继续消费，不能删除 | 以 usage record 稳定 ID / 当前 PG 写入幂等边界证明只产生一条事实 |
| audit | 最多 3 次有界重试；耗尽返回明确 enqueue failure，不调用 process fatal；调用方不得伪造已接受 | 必须继续消费，不能删除 | 以 audit event ID / 当前 repository 去重边界证明 |
| operation | 有界重试后允许 drop，记录操作日志丢弃指标，不调用 process fatal | 必须继续消费，不能删除 | 以 operation log ID 证明重放不重复落库 |
| public API | 有界重试后允许 drop，记录公开接口日志丢弃指标，不调用 process fatal | 必须继续消费，不能删除 | 以 trace/request identity 证明重放不重复落库 |
| runtime log | 现有 bounded producer drop，不调用 process fatal | 必须继续消费，不能删除 | 索引 ID 重放只保留一条索引 |
| record maintenance | 有界失败指标，由 DB/下一轮维护重建；不调用 process fatal | 必须继续消费，不能删除 | job ID / 单飞约束证明重复执行安全 |

“不丢未落库 Stream 消息”约束针对已经成功 XADD 的消息；尚未 XADD 的新增记录按上表数据损失预算处理。每一类必须在故障注入测试中分别断言：Redis 命令失败不会触发 `scheduleProcessFatalError`；usage/audit 耗尽重试时不会伪造成功；重复投递在数据库提交成功后崩溃并重新消费时不会产生重复事实。若现有稳定 ID 或唯一约束不足，先补当前 schema 下的一次性离线检查或幂等实现，再允许生产切换。

### 8.4 producer quiesce fence

fence 由 queue Redis 自身原子执行，不能只靠停止进程或观察 commandstats：

1. 新增 `backend/src/shared/redis-queue-fence.ts`，以 `juhe-ai:<namespace>:queue:fence` 为 key；发布脚本使用独立 admin client `SET key <release-token> NX` 建立 fence，token 写入发布审计。
2. 所有六类 producer 必须通过 `RedisStreamQueue.enqueue/enqueueEncoded` 的统一 Lua 路径；Lua 在同一 Redis 原子操作中先读取 fence，存在 token 则返回 `QUEUE_QUIESCED`，不存在才执行 XADD。禁止模块直接调用 XADD 绕过 fence。
3. fence owner 是 main 发布控制器；设置 fence 后，server、db-service、ingest、stats、ops 的新 producer 都被拒绝，已进入 Redis 的消息仍由 drain consumer 消费。IPC 中已排队但尚未进入 Redis 的项目按各自数据损失预算记录，不得在 fence 后继续写旧 queue。
4. drain consumer 使用独立的 one-shot 进程/launchd label，不由 main KeepAlive 管理；只允许 XREADGROUP/XAUTOCLAIM/PG commit/XACK/XDEL，不创建 producer client。drain 完成后由同一 token 执行 Redis Lua compare-and-delete（仅当当前值等于 token 才 DEL），错误 token、旧 token 或过期 owner 均不得释放 fence；失败时保留 token 和现场。
5. fence 设置后再次检查全部 consumer groups 和两段静默窗口只是验证证据，不承担禁止写入职责。所有 producer 必须有“fence 拒绝”单元回归和跨进程 smoke。

## 9. 生产迁移设计

### 9.1 前置门禁

- 用户再次明确正式上线。
- 获取 `deployment-plan-lock.ps1 acquire`，已有持有人时持续等待，不超时接管。
- 远端 deployment-change lock 和 recovery marker 均为空。
- main/temporary 发布包、环境文件、launchd plist、Redis 配置均留存哈希和可恢复副本。
- 记录 6380 的 `INFO memory/persistence/stats/commandstats`、六条 Stream 的 XLEN、pending、lag、消费组 last-delivered-id 和当前 PID/拓扑。

### 9.2 temporary 资源所有权

temporary 承流必须使用完全独立的临时资源，不得复用生产 Redis 物理进程：

- `JUHE_AI_REDIS_NAMESPACE=temporary-release-<stamp>`，且不能与生产 namespace 相同。
- `JUHE_AI_REDIS_CACHE_URL/STATE_URL/QUEUE_URL` 指向临时三 Redis（例如 16379/16380/16381），不得包含生产 6379/6380/6381。
- temporary 不启动生产 queue consumer，不读取生产 Stream；其 queue 只服务临时 PostgreSQL/临时 namespace。
- 发布前脚本必须解析 temporary `backend.env`，同时验证三个 URL、namespace、PID、端口和 PostgreSQL URL 均为临时资源。现有“复制 main env 后只改数据库/端口”的流程不足，必须在预检中阻断。

因此 temporary 可以在生产 6380 state 重启期间继续承流；它不会持有生产租约、锁、限频或亲和状态。main 切换期间的生产状态 owner 始终是 main，state 重启前后允许重建。

### 9.3 切换顺序

1. 在不接业务流量的情况下启动 6381 queue，验证端口、密码、目录、AOF、`noeviction`、launchd label 和日志完全独立。
2. 启动并验证完全隔离的 temporary 三 Redis，确认 temporary URL/namespace/consumer owner；由 temporary 接管公网。
3. 对 main 执行 producer quiesce fence：停止 server 新请求、停止所有会产生 XADD 的 worker/scheduler，保留一个有界 drain consumer；确认所有 main 子 PID、IPC producer 和 launchd KeepAlive 状态。
4. drain consumer 按六条 Stream 的全部 consumer groups 检查 `pending=0 && lag=0`。停止旧 main 全部进程后再次检查，并在两个连续观测窗口内确认 `XADD` commandstats 增量为 0；任一不满足即中止，不复制半完成 consumer group，不清理旧数据。
5. 将 main 的 queue URL 改为 6381，state URL 保持 6380，关闭 shared URL 例外；6380 暂时仍保留原持久化配置。重新启动 main，但继续由隔离 temporary 承流。
6. 验证 6381 新消息入队、消费、PostgreSQL 落库、ACK/XDEL 连续；验证 6380 无 Stream 命令增量，且六类 Stream 的重复投递回归通过。
7. 确认 queue 已由 6381 承载且 6380 无 Stream 写入后，停止 main，在 6380 通过 `launchctl bootout` 卸载旧 state daemon，原子替换配置并 `bootstrap/kickstart` 新 state daemon；验证新 PID/端口/cwd/config hash，再启动 main。此步骤会重建生产运行态，temporary 仍使用隔离 state，不受影响。
8. 完成业务 smoke、队列连续性和稳定观察后解除 quiesce、切回 main；继续观察 30 分钟，再释放 temporary。

步骤 5 与步骤 7 分开，是为了先证明 queue URL 切换正确，再改变 6380 持久化，避免两个故障变量叠加。

### 9.4 launchd 原子操作与回滚

6380/6381 为 system LaunchDaemon 时，所有变更使用以下顺序：`sudo launchctl bootout system/<label>` -> 等待 `launchctl print` 消失并确认端口/PID 已释放 -> 写入同目录临时文件并 `mv` 原子替换 plist/config -> `sudo launchctl bootstrap system <plist>` -> `sudo launchctl kickstart -k system/<label>` -> 验证 PID、端口、cwd、配置 hash 和健康检查。任一步 sudo、bootout、bootstrap、端口或 PID 校验失败，立即停止后续步骤，恢复已保存 plist/config 并按同样顺序 bootstrap；禁止让 KeepAlive 在旧配置下自动复活形成双实例。

### 9.5 回滚

- 步骤 5 前失败：停止并保留 6381，main 继续使用共享 6380，不改持久化。
- 步骤 5 后失败：**不得直接把 queue URL 恢复到 6380**。6381 是此时新的 queue 事实源；保持 main/临时修复版本继续使用 6381，先确认六条 Stream 全部落库并 drain 到 `pending=0 && lag=0`，再决定是否做经过验证的离线反向迁移。若无法 drain，保留 6381 并修复，不丢弃其 AOF。
- 步骤 7 后失败：优先继续使用 6381 queue 和新的 volatile 6380 state；不得恢复旧 state AOF，以免复活过期租约和锁。只有在 queue 已完全 drain、所有 producer 已 quiesce 且有独立迁移证据时，才允许回到旧队列拓扑。
- 任一阶段无法证明消息连续性、PID 稳定或业务 smoke 时，不切回 main。

每条回滚路径都必须执行 `deployment-plan-lock.ps1 release` 并记录 outcome=`rolled-back` 或 `cancelled`，临时 Redis/temporary 资源只在日志、queue AOF 和验证证据已归档后清理；失败现场需要保留到用户确认处置。

## 10. 观测与验收

### 10.1 必备指标

- 三实例：`used_memory/maxmemory`、peak、fragmentation、ops/s、connected clients、blocked clients、evicted keys、rejected connections、OOM。
- state：命令 P50/P95/P99、连接错误、重连、受控 503、并发/锁/限频写失败。
- queue：六条 Stream XLEN、pending、lag、oldest pending idle、XADD P95/P99、producer drop count/bytes/reason。
- AOF：current/base size、rewrite in progress、rewrite duration、fork time、last rewrite status、fsync delay。
- 进程：server/db-service/ingest/stats/ops 的 PID、launchd runs、退出码、unexpected restart、event-loop delay。

### 10.2 告警门槛

| 指标 | 告警 | 发布阻断 |
| --- | --- | --- |
| state/queue `evicted_keys` | 任意增量 | 是 |
| state/queue OOM/rejected | 任意增量 | 是 |
| 内存占比 | 60% 预警、75% 告警 | 85% 阻断 |
| queue pending/lag | 连续增长 5 分钟 | 无法回落或迁移前非零 |
| queue AOF rewrite | 超过基线 2 倍 | last status 非 ok |
| Node unexpected restart | 任意一次 | 是 |
| Redis 瞬时故障导致主请求 5xx | 超过既定错误预算 | 核心 smoke 失败 |

queue 内存达到 75% 时暂停 record-maintenance 新任务并对六类 producer 发出高水位告警；达到 85% 时 producer 在 XADD 前按各自有界策略拒绝新的非核心记录并记录 drop，保留所有已入队/未 ACK 消息，禁止通过删除 Stream 或淘汰旧 key 降压。恢复顺序是先修复消费者/数据库瓶颈并 drain 到 60% 以下，再恢复 maintenance，最后恢复其他 producer；扩容或人工迁移必须另行授权。

### 10.3 验收场景

1. 配置回归：production/performance 拒绝任何两类 URL 指向同一 host:port。
2. 角色回归：state 实例无 Stream 命令，queue 实例无运行态 key。
3. 冷启动：重启 state 后关键状态可重新建立，queue XLEN/pending/lag 不变；temporary 资源仍不受影响。
4. queue 重启：AOF 恢复后未 ACK 消息继续消费；usage、audit、operation、public-api、runtime-log、record-maintenance 分别用稳定 ID/唯一约束证明重复投递不会形成重复事实。
5. 故障注入：对六类 producer 分别注入 state/queue 短时断连，Node 无 `uncaughtException`、无 unexpected restart；关键 state 请求受控失败，queue drop 有指标。
6. AOF 重写：queue 执行 rewrite 时 state P99 不明显劣化，main PID 稳定。
7. 业务 smoke：管理登录、账号列表、网关文本/图像请求、usage/audit/operation/public/runtime/maintenance 消费与查询均通过。
8. 容量：30 分钟观察内存占比低于 60%，evicted/OOM/rejected 均无增量。

性能结论必须使用发布前后同一流量窗口或可复现压测比较；只看到错误消失不能替代延迟数据。

## 11. 实现范围

实施计划至少覆盖：

- 生产共享 Redis URL 禁止规则和回归测试。
- Redis client 运行期异常边界及 state/queue 故障注入回归。
- macOS 6381 Redis 配置、独立数据目录、launchd plist、日志和验证脚本；包含 bootout/bootstrap/kickstart 原子替换和失败回滚。
- temporary 三实例隔离、producer quiesce fence、全 consumer group Stream drain、静默窗口和固定 PID/AOF/内存门禁脚本。
- 高性能模式设计、部署指南、macOS 指南、watchdog 指南和测试说明同步。
- `PLAN-0122` 的任务、状态、验证记录和决策更新。

不在本次第一阶段实施大 payload 引用化、所有 producer 统一重写或维护任务全面降载；这些仍由 `PLAN-0122` 后续任务跟踪。第一阶段先完成物理隔离、AOF 边界和进程异常治理，降低生产风险后再用指标决定后续优化。

## 12. 完成定义

只有同时满足以下条件才能宣称本设计落地完成：

- 三个 Redis 物理进程和三个独立 URL 已在目标 macOS 生产实际验证。
- 6380 state 无 AOF/RDB，6381 queue 使用 AOF everysec 且无 RDB。
- 六条 Stream 切换前 drain、切换后落库连续性有证据。
- AOF rewrite 期间 state 延迟和 Node PID 满足门禁。
- Redis 短时断连不会导致主进程异常退出。
- 无淘汰、OOM、拒绝连接、队列持续积压或核心业务回归。
- temporary 已清理、生产 main 稳定、部署计划锁正常释放。
- 实际测试、上线、观察和回滚证据已回填计划文档。
