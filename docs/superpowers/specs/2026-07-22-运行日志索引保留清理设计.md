# 运行日志索引保留清理设计

## 目标与边界

本切片只把 PostgreSQL 运行日志索引保留清理迁移为 Go 可运行能力。Node `ingest-worker` 继续拥有运行日志文件导入、cursor 写入和 facet 增量写入，Node retention cleanup 继续拥有生产清理子域；本切片不切换生产 owner、不删除 Node、不修改 schema，也不删除原始日志文件。

清理仅在 `JUHE_AI_RUNTIME_LOG_INDEX_ENABLED=true` 时运行。保留天数读取 `sys_admin/runtimeLogIndexRetentionDays`，缺失或零值使用 14，显式值和命令覆盖必须在 1..90。一次运行固定一个 UTC cutoff，避免多批次跨越不同时间边界。

## 组件

- `internal/store/port/runtime_log_retention.go`：定义设置读取、索引批量清理和完成 cursor 批量清理的存储端口。
- `internal/modules/runtimelogretention/service.go`：负责开关、默认值、参数归一化、固定 cutoff、先索引后 cursor 的小批循环、25ms 可取消暂停和结果汇总。
- `internal/store/postgres/runtime_log_retention.go`：实现 PostgreSQL 事务、锁、稳定选删和 facet 维护。
- `internal/app/runtime_log_retention_cleanup_worker.go`：提供可直接由 CLI/supervisor 组装的一次性或周期 worker 入口；本批不改共享 CLI main。

## PostgreSQL 事务与并发

每个索引批次在单个事务中执行：

1. 先设置事务本地 `lock_timeout=25ms` 和 `statement_timeout=1s`，再用 `pg_try_advisory_xact_lock` 防止多个 Go cleaner 同时运行。advisory lock 不用于协调 Node，也不把 Node 未持有该锁误写成安全前提；拿不到时本轮 deferred。
2. 从 `runtime_logs` 中选择 `time < cutoff` 的最老行，固定 `ORDER BY time ASC, id ASC LIMIT batchSize FOR UPDATE SKIP LOCKED`，并在同一语句暂时删除、返回 `time/level/event`。空批直接提交，不触碰 facet summary，因此不会无意义地延迟 importer。
3. 确有删除后，对 `runtime_log_facet_summary(bucket_key='current')` 执行 `FOR UPDATE NOWAIT`。Node `createRuntimeLogsBatchAsync` 已核实在同一事务中先插入日志，再由 `incrementRuntimeLogFacetSnapshotsPostgres` 依次写 summary、level、event；因此 summary 行是现有双运行时都参与的串行点。Go 在取得 summary 行后才维护三类 facet；Node 已持有该行时 Go 立即回滚，Go 先取得时 Node 只在短关键区等待。
4. summary 行锁后的 Go 关键区额外受 1.5 秒 context deadline 约束。summary、level/event count 使用 `GREATEST(0, ...)`，零计数行删除；summary earliest/latest 从 cutoff 后的剩余索引重算，被删除事件的 latest 从剩余同事件索引重算。
5. advisory、summary 行或后续 facet 行发生锁竞争、保护性 statement timeout 或短关键区超时时，整个暂时删除批次回滚并返回 `ErrRuntimeLogRetentionDeferred`。service 记录 `RuntimeLogsDeferred=true`、保留此前已提交批次计数并继续完成 cursor 清理；周期 worker 下一轮重试。其他数据库错误仍作为失败返回。

旧方案的三张 facet `SHARE ROW EXCLUSIVE` 表锁会与 Node importer 的常规 `ROW EXCLUSIVE` 写锁冲突，且从选删开始覆盖整个批次，放大导入延迟。本方案不再发出任何 `LOCK TABLE`；先选删、后锁单个 summary 行，把 Node 可能等待的范围缩到 facet 维护关键区。若 Node 后续改变 summary-first 的事务顺序，必须同步更新此契约；不能仅靠 Go advisory lock 继续清理。

Node retention cleanup 当前会在取得 summary 写锁前读取 earliest/latest 边界，因此不能与 Go cleanup 并发运行；summary 行锁无法把 Node 已完成的边界读取撤销。`CleanupInput.GoExclusiveIndexCleanupOwner` 因此默认 `false` 并 fail-closed：只标记 `RuntimeLogsDeferred=true`，不调用索引删除 store，但继续独立的完成 cursor 清理。只有发布流程已经停止 Node 的 runtime-log index cleanup 子 owner、明确把该布尔值设为 `true` 后，Go 才执行索引删除。当前 app 入口未接 CLI/supervisor，也没有生产调用方设置该门禁，不构成双 owner。

完成 cursor 使用单条有界 DELETE：仅删除 `updated_at < cutoff`、`cursor_offset >= file_size` 且 `last_error_message IS NULL` 的行，按 `updated_at ASC, log_file ASC` 选取。运行中、未读完或错误 cursor 保留。

## 取消与错误

service 在每个 store 调用和批间暂停使用调用方 context。context 取消、设置读取失败、非竞争事务失败或 worker 连接失败立即返回错误；已提交批次不回滚，未提交批次由 PostgreSQL 事务回滚。锁竞争属于可观测 deferred，不作为 worker 失败，也不在同一轮自旋重试。满批且未达到 `maxBatches` 时暂停 25ms，非满批立即结束该表循环。
