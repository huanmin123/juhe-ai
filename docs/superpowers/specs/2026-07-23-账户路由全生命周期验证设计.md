# 账户路由全生命周期验证设计

## 目标

验证 Node 网关从请求进入到账户异常、切号、熔断、恢复和重新调度的完整链路，重点覆盖普通路由的质量优先与速度优先两种调度偏好。

## 生命周期断言

```text
请求接入
-> 路由策略锁定分组
-> 账户可执行性过滤
-> 质量/速度排序
-> 上游 attempt
-> 成功：记录热质量并保留调度
-> 可确认异常：单飞确认 -> SUSPECT/OPEN -> 当前请求切号
-> OPEN：新请求跳过，后台受控 HALF_OPEN 探针
-> 探针成功：RECOVERING/CLOSED -> 恢复候选
-> 恢复后请求重新参与排序
```

## 必须验证的不变量

1. `OPEN` 或无授权、无能力、不可调度账户不得被正常请求选中。
2. 同一账户的并发确认必须 singleflight/CAS，不能重复放大上游风暴。
3. 速度优先只在已选路由范围内覆盖账户偏好；确认慢账户让位给未降级可执行账户。
4. 热质量和速度样本是运行态，不得把一次偶发慢或客户端语义错误误判为永久账户死亡。
5. 恢复必须持有唯一半开租约；失败回到阻断态，成功达到阈值后才重新可调度。
6. 切号成功时客户端不应收到中间上游错误；所有候选耗尽时返回有界、脱敏、可重试终态。
7. 下游已经提交语义输出后不得跨账户拼接或重放同一请求。

## 验证层次

- Mock AI：覆盖确定性异常风暴、并发、少量健康账户和所有状态边界。
- Memory/Redis/控制面：验证本地运行态与共享运行态的一致性。
- PostgreSQL smoke：仅验证状态持久化/控制面契约，不保存真实凭据。
- 真实账户：本轮不执行异常风暴；仅在单请求、明确授权和费用可控时做最小探针。

## 通过标准

所有核心回归通过；失败账户不继续承接正常流量；可用账户能完成请求；恢复账户在满足探针阈值后重新参与；测试报告能区分 `SUSPECT`、`OPEN`、`HALF_OPEN/RECOVERING`、`CLOSED` 和客户端 handoff。
