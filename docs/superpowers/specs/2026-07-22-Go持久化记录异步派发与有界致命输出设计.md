# Go 持久化记录异步派发与有界致命输出设计

## 1. 背景

当前 Go 管理接口和公开接口在业务处理完成后，仍会在 HTTP 调用栈内读取操作日志设置并同步调用 Redis / Asynq 入队。队列依赖阻塞时，请求会额外等待最长约 5 秒；公开接口的 defer 路径同样会延迟响应完成。

Go server、worker 和 maintenance 命令在返回错误时会调用 `logging.WriteFatal`。该函数对 stderr writer 做同步写入；当 stderr、管道或宿主日志收集器永久阻塞时，即使异步 logger shutdown 已按 deadline 返回，进程仍无法到达 `os.Exit`。

这两个问题虽然发生在记录与诊断链路，但影响的是业务响应延迟、服务重启和发布可用性。本设计只处理这两个可用性问题。

## 2. 目标

1. 管理操作日志和公开接口日志的设置读取、payload 构造及 Redis / Asynq 入队不再阻塞 HTTP 响应。
2. 后台派发使用固定 worker 和有界任务通道，不按请求创建 goroutine。
3. 后台依赖失败、队列饱和或进程关闭时，允许 best-effort 记录丢失，但不得改变业务状态码、响应体或已完成的数据写入。
4. server、worker 和 maintenance 的 fatal 诊断即使遇到永久阻塞 writer，也能在固定时间内返回并继续退出。
5. 保持现有任务 payload、Asynq 队列名、重试、保留期、脱敏和 fatal 单行格式兼容。

## 3. 非目标

- 不处理运行日志文件轮转、磁盘保留、日志字节预算或日志字段内容。
- 不修正 trace/request/job/parent 字段语义或历史持久化数据。
- 不改变 operation log、public API log 的数据库 schema、查询接口或权限。
- 不调整 Redis / Asynq 部署、任务消费者、重试次数或 retention。
- 不执行生产部署、重启、切流或生产数据操作。

## 4. 当前触发链路

### 4.1 管理操作日志

```text
management handler
  -> enqueueManagementOperationLog
  -> OperationLogMaxChangesPerRecord
  -> sanitize changes
  -> operationlog.EnqueueWrite
  -> Redis / Asynq EnqueueContext
  -> handler 返回
```

设置读取和队列入队都位于请求调用栈内；`context.WithoutCancel` 还会使客户端取消无法中断这段等待。

### 4.2 公开接口日志

```text
public API shell defer
  -> 构造 request/response snapshot
  -> publicapilog.EnqueueWrite
  -> Redis / Asynq EnqueueContext
  -> defer 返回
  -> HTTP 请求结束
```

### 4.3 致命诊断

```text
command Execute 返回错误
  -> WriteFatal(stderr, err)
  -> stderr.Write
  -> 返回退出码
  -> os.Exit
```

writer 不返回时，后续步骤永远不可达。

## 5. 方案选择

采用“应用级共享有界 dispatcher + 固定 worker”的方案。

不采用每请求启动 goroutine：外部队列故障时会累计 goroutine、闭包和 payload。也不只缩短现有 5 秒 timeout：即使缩短，HTTP 仍然等待非业务依赖。

fatal 输出采用“后台写入 + 固定等待窗口”。不依赖 writer 支持 deadline，因为 `io.Writer` 没有统一的取消契约；等待窗口到期后调用方直接继续退出。

## 6. 异步持久化记录派发

### 6.1 责任边界

新增 Go 内部共享的 best-effort dispatcher，职责仅包括：

- 接收已经脱离 HTTP 生命周期的任务输入和日志关联上下文快照。
- 使用非阻塞 `TrySubmit` 写入固定容量通道。
- 由固定数量 worker 执行任务函数，并为每次外部入队建立独立 timeout context。
- 记录 accepted、completed、failed、dropped 和 pending 计数，供测试和关闭诊断读取。
- 停止接收后，在调用方提供的 shutdown context 内排空已接收任务。

dispatcher 不负责业务重试、任务去重或数据库写入；这些语义继续由现有 Asynq task 和 worker 承担。

### 6.2 默认运行参数

- operation log dispatcher：容量 256，worker 1 个。
- public API log dispatcher：容量 256，worker 1 个。
- 单次设置读取与 Asynq 入队沿用 5 秒内部 timeout。
- `TrySubmit` 不等待通道空间；满载、停止接收或依赖未配置时返回 `false`。

两个 dispatcher 分开，避免公开接口流量占满管理操作日志派发通道。固定单 worker 保持每类任务的提交顺序，并限制 Redis 故障时的并发请求数。

### 6.3 管理操作日志

`enqueueManagementOperationLog` 改为只完成以下同步步骤：

1. 判断 dispatcher 是否可用。
2. 复制 `OperationLogInput` 及当前 `logging.LogContext`。
3. 非阻塞提交后台任务并立即返回。

后台任务继续执行现有设置读取、changes 清理和 `operationlog.EnqueueWrite`。因此设置存储或 Redis / Asynq 阻塞不再延长 HTTP 请求。

任务被拒绝或后台失败时，只更新 dispatcher 统计并通过既有 logger 输出一次有界诊断；不得向 handler 返回错误，也不得回滚已完成的管理操作。

### 6.4 公开接口日志

public API shell 仍在 defer 中完成已存在的 request/response snapshot 构造，但不直接访问 Redis / Asynq。它只把不可变 input 和关联上下文交给 public dispatcher，随后立即结束请求。

后台 worker 使用捕获的 trace/request context 调用现有 `publicapilog.EnqueueWrite`，保持当前 payload 和消费者兼容。

### 6.5 生命周期

应用启动时在装配层创建 dispatcher，再注入 management operation-log options 和 public API shell。应用关闭顺序为：

1. HTTP server 停止接收新请求。
2. 两个 dispatcher 停止接受新任务。
3. 在现有 shutdown deadline 内排空已接受任务。
4. 关闭底层 Asynq client。
5. 关闭异步 logger 并返回命令错误或退出码。

shutdown context 到期时允许放弃尚未完成的记录任务；不得再次无限等待。

## 7. 有界 fatal 输出

`logging.WriteFatal` 保持现有公开调用形式和以下契约：

- 继续使用现有敏感信息清理、单行 JSON 和 4 KiB 整行上限。
- 将实际 `writer.Write` 放入单个后台 goroutine。
- 调用方最多等待 250 毫秒。
- write 完成、返回错误、panic 或等待超时都结束 `WriteFatal`；输出失败不覆盖原始命令退出码。
- 超时后不等待该 goroutine。命令入口随即返回退出码，`main` 进入 `os.Exit`，操作系统负责回收阻塞 goroutine。

该策略适用于 server、worker 和 maintenance 的所有现有入口，不为不同命令复制实现。

## 8. 错误与兼容语义

- 业务处理成功后，即使记录任务没有被接受或最终入队失败，HTTP 仍返回原业务结果。
- 业务处理失败时，记录派发同样不得覆盖原错误、状态码或响应体。
- 已被 dispatcher 接受但尚未送入 Asynq 的任务只存在于进程内存；进程崩溃允许丢失。
- Asynq 成功接收后的 retry、retention、job ID 和消费者行为保持不变。
- 不新增客户端可见字段、配置项或数据库迁移。

## 9. 测试设计

实施必须遵循 TDD，并至少覆盖：

1. 阻塞 operation-log 设置 reader 时，management handler 仍在短时间内完成响应。
2. 阻塞 operation/public Asynq client 时，HTTP handler 不等待 5 秒。
3. dispatcher 后台成功调用现有 EnqueueWrite，并保留捕获的 trace/request context。
4. 通道饱和时 `TrySubmit` 立即失败，不创建额外 worker 或 goroutine，不改变业务响应。
5. shutdown 停止新提交、排空可完成任务，并在阻塞任务下遵守 context deadline。
6. 永久阻塞 writer 下，`WriteFatal` 在 250 毫秒窗口后返回；测试结束前主动释放 writer，避免测试 goroutine 泄漏。
7. 正常 writer 仍得到一条合法、脱敏且不超过 4 KiB 的 fatal JSON。
8. server、worker、maintenance 的 `executeCommand` 在阻塞 stderr 下仍返回退出码 1。

整合门禁包括相关定向测试、`go test ./... -count=1`、`go vet ./...`、相关包 `go test -race -count=1`，以及仓库级 `pnpm typecheck` 和 `pnpm build`。

## 11. 验收标准

1. Redis / Asynq 或 operation-log 设置读取阻塞 5 秒时，management/public HTTP 响应不等待该依赖。
2. 持久化记录派发没有每请求 goroutine，后台并发由固定 worker 限制。
3. 派发失败或饱和不改变业务写入、HTTP 状态和响应体。
4. shutdown 在依赖永久阻塞时仍按 context deadline 返回。
5. fatal writer 永久阻塞时，server、worker、maintenance 命令入口仍能返回退出码并继续进程退出。
6. 正常情况下 operation/public Asynq payload、correlation、重试和消费者兼容性不变。
7. 全量 Go、race、vet、Node typecheck/build 和定向回归通过。
8. 变更不包含凭据、连接串、生产操作或部署动作。
