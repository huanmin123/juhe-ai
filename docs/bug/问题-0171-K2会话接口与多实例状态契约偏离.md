## 问题概述

- 现象：K2 Go 会话接口在 profile 回执、资料更新、错误状态、cookie 以及多实例 CAPTCHA/登录防护上与 Node 的可见结果不同。
- 期望：认证 API 应返回前端既有必需字段和最新状态；存储故障不能伪装成认证失败或退出成功；在 performance 多实例部署中，验证码和登录锁定应保持跨实例一致。
- 实际：
  1. Node `GET /auth/profile` 合并全局设置并返回必需的 `effectiveRequestLimits`；Go 只返回 `AccountSummary`，没有 settings 依赖。前端 `CurrentUserProfile` 明确把该字段定义为必需。
  2. Go `PATCH /auth/me` 成功写入后重新读取了 `updated`，却用旧的 request auth context 生成响应。因此数据库已是新名称，而响应和前端即时状态仍是旧名称；Node 用更新后的 account 返回。
  3. Go logout 忽略 `RevokeToken` 错误并返回 `loggedOut:true`；会话 middleware 将非过期类存储错误统一成 401，改密和临时令牌中的存储错误也会伪装成凭据错误。Node 等待撤销并保留服务端错误语义。
  4. Node performance 模式以 Redis 保存 CAPTCHA 与登录保护状态；Go `CaptchaService`、`LoginGuard` 使用进程内 map。负载均衡到不同实例时，A 实例签发的验证码无法在 B 验证，切换实例还可规避累积失败锁定。
  5. Bearer scheme 在 Node 中大小写不敏感而 Go 正则大小写敏感；Go 清理 session cookie 时硬编码 `SameSite=Lax` 且未继承 `Secure`/同站配置。登录保护在第十次失败先命中 IP 锁定时不会写 username 维度，和 Node 的双维度累计不同。
- 影响范围：个人资料页会出现成功后回显旧名称或缺少限制字段；数据库故障可能使客户端错误清理有效会话；多实例下验证码、爆破保护和登出行为不可靠。

## 根因与证据

- Node profile 和资料更新：`backend/src/modules/auth/auth.routes.ts` 同时读取 account/settings，并以更新后的 account 生成 `currentUserSummary`。
- Go profile 和资料更新：`backend-go/projects/gateway/internal/authsys/routes.go` 的 `getProfile` 无 settings 输入，`patchMe` 最终使用 `currentUserSummary(auth)` 而非 `updated`。
- 前端必需字段：`frontend/src/types/domain/identity.ts` 的 `CurrentUserProfile.effectiveRequestLimits`，以及 profile 页面收到成功回执后更新当前用户状态的路径。
- 会话 cookie、Bearer 与错误映射：`backend-go/projects/gateway/internal/authsys/middleware.go`、`routes.go`；Node 对照逻辑在 `auth.routes.ts` 与 `shared/http-security.ts`。
- CAPTCHA/登录防护 Go 使用内存实现：`backend-go/projects/gateway/internal/modelcheckauth/`；Node 使用 performance runtime state 的配置/服务路径。现有 K2 测试只单进程运行，不能证明跨实例等价。

## 修复与验证

- 修改点：抽取可复用的有效请求限制解析并将 settings 作为 profile 依赖；用更新后实体构建资料回执；按 Node 区分认证失败和存储故障；使 cookie/Bearer/登录 guard 完整遵循现有契约；为 performance 模式提供 Redis 共享 CAPTCHA/登录防护实现。
- 必需验证：profile/改名 golden 和前端状态回归；撤销、数据库错误和凭据竞态的故障注入；多实例 Redis CAPTCHA/锁定回放；cookie 属性与大小写 bearer 矩阵。
- 本轮已修复子项：`PATCH /auth/me` 成功回执改为使用持久化更新后的账户构建 `CurrentUserSummary`，提交 `a56b678ea`；新增改名回执回归测试，验证 `data.displayName` 返回新值。独立复审确认与 Node 回执字段和成功路径一致。临时令牌的 `Authorization` Bearer scheme 改为大小写无关，提交 `6a59481d4`；真实 HTTP 回归覆盖小写 `bearer` 访问 `/auth/me`，与 Node `/^Bearer\s+(.+)$/i` 对齐。logout 的 session 撤销失败现在返回 500 且不清除仍可能有效的 cookie，提交 `1b5907cfa`；故障注入回归覆盖失败响应、cookie 保留及原 session 仍可认证。会话查询或 touch 的存储错误不再伪装为 401，而是返回 500，提交 `8840d4c69`；故障注入覆盖 `/auth/me` middleware 的存储错误分类。logout 清 cookie 继承登录的 `SameSite`/`Secure` 配置，提交 `83dcf306f`；配置型回归覆盖 `SameSite=None; Secure`。改密前的凭据校验存储错误不再伪装为当前密码错误，提交 `93bef0939`；故障注入覆盖 500 与正常密码不匹配的原有 400 分支分离。登录时并发改密造成的 session revision 栅栏拒绝改为 Node 一致的“账号或密码已变更，请重新登录”，提交 `6afc8a4b7`；回归覆盖拒绝响应、失败计数路径与不下发 cookie。
- 其余子项仍待修复：profile settings、存储错误映射、多实例 Redis CAPTCHA/登录防护、cookie/Bearer 细节及登录保护维度等，不能因本次局部修复改变 BUG-0171 的总体待修复状态。
- 当前验证：`go test ./internal/authsys -count=1`、`go test -race ./internal/authsys -count=1`、`go vet ./internal/authsys` 和 `git diff --check` 均通过；测试使用内存 SQLite、单进程 `httptest`，不覆盖 profile settings、多实例 Redis、故障注入或真实 gateway 装配。

## 完成总结

- 结论：即使 BUG-0152 的生产入口补齐，K2 会话功能仍不能保证 Node 的接口结果与多实例安全状态一致。
- 后续建议：以真实入口的 Node/Go golden 加 Redis/故障注入集成测试作为 K2 重新验收门槛。
