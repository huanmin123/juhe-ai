- 状态：待修复
- 严重程度：P1

## 问题概述

- 现象：K2 Go 会话接口在 profile 回执、资料更新、错误状态、cookie 以及多实例 CAPTCHA/登录防护上与 Node 的可见结果不同。
- 期望：认证 API 应返回前端既有必需字段和最新状态；存储故障不能伪装成认证失败或退出成功；在 performance 多实例部署中，验证码和登录锁定应保持跨实例一致。
- 原始实际差异及当前状态：
  1. **已修复（提交 `76c352987`）**：Node `GET /auth/profile` 合并全局设置并返回必需的 `effectiveRequestLimits`；Go 已补齐 settings 读取、用户覆盖、过期回退及时区判定，并保持前端字段契约。
  2. **已修复**：Go `PATCH /auth/me` 原先用旧的 request auth context 生成响应，现已使用持久化更新后的账户返回（`a56b678ea`）。
  3. **已修复**：logout 撤销失败、会话查询/touch、改密凭据校验和临时令牌存储错误现已分别返回服务端错误，不再伪装成认证失败或退出成功（`1b5907cfa`、`8840d4c69`、`93bef0939`、`7f17f9076`）。
  4. **待修复**：Node performance 模式以 Redis 保存 CAPTCHA 与登录保护状态；Go `CaptchaService`、`LoginGuard` 使用进程内 map。负载均衡到不同实例时，A 实例签发的验证码无法在 B 验证，切换实例还可规避累积失败锁定。
  5. **已修复**：Bearer scheme 已改为大小写不敏感，session cookie 清理已继承 `SameSite`/`Secure` 配置（`6a59481d4`、`83dcf306f`）；登录保护在第十次失败即使先命中 IP 锁定也会累计 username 维度（`3c7ca413a`），与 Node 的双维度累计和 IP 优先返回一致。
- 原始影响（已修复）：个人资料页成功后回显旧名称；数据库故障使客户端错误清理有效会话；logout cookie 属性或 Bearer 大小写与 Node 不一致。
- 剩余影响：多实例下验证码和爆破保护不共享，可能通过切换实例规避。

## 根因与证据

- Node profile 和资料更新：`backend/src/modules/auth/auth.routes.ts` 同时读取 account/settings，并以更新后的 account 生成 `currentUserSummary`。
- Go profile 和资料更新：`backend-go/projects/gateway/internal/authsys/routes.go` 的 `getProfile` 已注入 settings 并计算有效请求限制；`patchMe` 最终使用 `currentUserSummary(auth)` 而非 `updated`。
- 前端必需字段：`frontend/src/types/domain/identity.ts` 的 `CurrentUserProfile.effectiveRequestLimits`，以及 profile 页面收到成功回执后更新当前用户状态的路径。
- 会话 cookie、Bearer 与错误映射：`backend-go/projects/gateway/internal/authsys/middleware.go`、`routes.go`；Node 对照逻辑在 `auth.routes.ts` 与 `shared/http-security.ts`。
- CAPTCHA/登录防护 Go 使用内存实现：`backend-go/projects/gateway/internal/modelcheckauth/`；Node 使用 performance runtime state 的配置/服务路径。现有 K2 测试只单进程运行，不能证明跨实例等价。

## 修复与验证

- 已完成修改：资料更新回执、会话/凭据/临时令牌存储错误映射、Bearer 大小写、logout cookie 属性及登录 revision 栅栏均已按 Node 对齐，具体提交和回归见下方子项记录。
- 剩余修改范围：将 CAPTCHA 与登录保护迁移为 performance 模式可共享的 Redis 状态。
- 剩余必需验证：多实例 Redis CAPTCHA/锁定回放；真实 gateway 装配验证。
- 本轮已修复子项：`GET /auth/profile` 已恢复 Node 的 `effectiveRequestLimits` 回执，提交 `76c352987`；settings 注入兼容性随后由 `29cd2a585` 固化。新增 HTTP 回归覆盖全局窗口、用户覆盖、过期回退、时区和空覆盖；raw request-limits 解析/序列化同时保留 Node 的显式字段、数值和真实日期校验语义。其余已修复子项：`PATCH /auth/me` 成功回执改为使用持久化更新后的账户构建 `CurrentUserSummary`，提交 `a56b678ea`；新增改名回执回归测试，验证 `data.displayName` 返回新值。独立复审确认与 Node 回执字段和成功路径一致。临时令牌的 `Authorization` Bearer scheme 改为大小写无关，提交 `6a59481d4`；真实 HTTP 回归覆盖小写 `bearer` 访问 `/auth/me`，与 Node `/^Bearer\s+(.+)$/i` 对齐。logout 的 session 撤销失败现在返回 500 且不清除仍可能有效的 cookie，提交 `1b5907cfa`；故障注入回归覆盖失败响应、cookie 保留及原 session 仍可认证。会话查询或 touch 的存储错误不再伪装为 401，而是返回 500，提交 `8840d4c69`；故障注入覆盖 `/auth/me` middleware 的存储错误分类。logout 清 cookie 继承登录的 `SameSite`/`Secure` 配置，提交 `83dcf306f`；配置型回归覆盖 `SameSite=None; Secure`。改密前的凭据校验存储错误不再伪装为当前密码错误，提交 `93bef0939`；故障注入覆盖 500 与正常密码不匹配的原有 400 分支分离。登录时并发改密造成的 session revision 栅栏拒绝改为 Node 一致的“账号或密码已变更，请重新登录”，提交 `6afc8a4b7`；回归覆盖拒绝响应、失败计数路径与不下发 cookie。临时令牌申请现在区分凭据/落库存储错误（500）、凭据错误或非管理员（401 并累计失败）以及 revision 栅栏拒绝（401），提交 `7f17f9076`；回归覆盖两类存储故障和非管理员第 11 次请求的 429 时序。第十次失败即使先命中 IP 锁定也会同步累计 username，提交 `3c7ca413a`；回归覆盖换 IP 后同用户名在凭据校验前得到 900 秒 username 锁定。
- 其余子项仍待修复：多实例 Redis CAPTCHA/登录防护；BUG-0171 总体仍保持待修复状态。
- 当前验证：`go test ./projects/gateway/internal/authsys -count=1`、`go test ./projects/gateway/internal/authsys -race -count=1`、`go vet ./projects/gateway/internal/authsys`、`go test ./projects/gateway/internal/modelcheckauth -race -count=1` 和 `git diff --check` 均通过；新增 profile 有效限额、过期回退和无窗口 expiresOn 测试；测试使用内存 SQLite、单进程 `httptest`，不覆盖多实例 Redis 或真实 gateway 装配。

## 完成总结

- 结论：即使 BUG-0152 的生产入口补齐，K2 会话功能仍不能保证 Node 的接口结果与多实例安全状态一致。
- 后续建议：以真实入口的 Node/Go golden 加 Redis/故障注入集成测试作为 K2 重新验收门槛。
