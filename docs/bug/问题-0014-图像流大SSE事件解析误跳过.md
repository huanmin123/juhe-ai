# BUG-0014 图像流大 SSE 事件解析误跳过

## 基本信息

- 编号：BUG-0014
- 状态：已修复
- 严重程度：P1
- 发现时间：2026-05-24
- 发现方式：用户反馈 + 生产日志分析
- 模块：后端 / 网关 / 流式转发 / 审计与使用记录
- 关联计划：无
- 关联 bug：BUG-0012
- 责任人：AI

## 问题概述

- 现象：`/v1/responses` 图像生成流中出现 `SSE 单行超过网关解析上限`，随后部分 trace 被记录为 `client_aborted / 请求已取消`。
- 期望：图像流里的大 base64 SSE 事件原样透传，解析器即使跳过当前大事件，也不能影响后续终止事件识别和成功收尾；审计、使用记录和诊断日志不保存图片字节，只保留元信息。
- 实际：流式 inspector 在单行或单事件超过内部解析上限后进入全流跳过状态，后续 `response.completed` 无法被识别，客户端在完成后关闭连接时容易被误记为取消；图像流如果被普通正文捕获，会把 base64 字节写入审计 payload，存储价值低且放大日志体积。
- 影响范围：OpenAI Responses 图像生成工具事件、Image API streaming 事件，以及任何携带大 base64 字段的 SSE 事件。

## 复现步骤

1. 使用 OpenAI-compatible 网关请求 `/v1/responses`，开启 `stream: true` 并使用 `image_generation` 工具。
2. 上游返回超过 256KB 的 `data:` 行，例如包含 `result`、`partial_image_b64` 或 `b64_json`。
3. 大事件后继续返回 `response.completed`，或 Image API 直接返回 `image_generation.completed`。

## 根因分析

- 表象：日志出现 `gateway_stream_inspector_skipped`，原因是 `SSE 单行超过网关解析上限`。
- 真实根因：图像 base64 payload 是官方协议里的正常 SSE 数据，但 inspector 把“当前事件太大无法完整解析”升级成“整条流都停止解析”，导致后续终止事件和 usage 识别丢失。
- 扩展根因：超大事件轻量识别时复用了上一条普通事件的临时 `type`，普通事件结束后没有清理 oversized 临时状态，可能把后续图像大事件误归类为上一条事件。
- 为什么会发生：原实现按文本流的小 JSON 事件设计了 256KB 单行和 512KB 单事件解析上限，没有区分主链路转发与旁路状态解析；图像流一旦携带大 base64 字段，就触发了旁路解析保护。
- 日志侧风险：审计捕获原本面向可读请求 / 响应正文，图像流里的 `partial_image_b64`、`b64_json`、`result` 属于大二进制载荷，不适合进入日志正文。

## 修复方案

- 修改点：
  - `backend/src/modules/gateway/protocols/openai-v1/stream-inspection.ts`：超大 `data:` 行或事件只标记当前 SSE event 为 oversized，记录类型摘要，随后继续解析后续事件。
  - `backend/src/modules/gateway/protocols/openai-v1/stream-inspection.ts`：为超大事件保留小尾部窗口，用于从尾部 `usage` 片段提取 token，不保存完整 base64。
  - `backend/src/modules/gateway/protocols/openai-v1/stream-events.ts`：识别 `response.image_generation_call.*`、`response.output_item.done` 中的 `image_generation_call`、`image_generation.partial_image`、`image_generation.completed`，并避免把 `partial_image_b64` / `b64_json` / `result` 当文本 token 估算。
  - `backend/src/modules/gateway/response/stream.ts`：检测到图像输出后立即清空 upstream / gateway / diagnostic body capture，后续返回 `bodyOmission` 元信息。
  - `backend/src/modules/gateway/audit/capture.service.ts`：新增审计 payload 正文省略能力；图像流只省略 upstream / gateway 响应正文并保留 client / upstream 请求证据，同时记录 `stream_body_omission` 元信息。
  - `backend/src/modules/gateway/response/finalization.ts`：图像流失败和成功路径都不再向审计和 usage 传递图像 body；失败使用记录只保留 `bodyOmission` 元信息。
  - `backend/src/scripts/regression/stream-first-output-timeout-regression.ts`：增加 Responses 大图事件后完成、Image API 大图终止事件、无 `\n\n` EOF 边界和审计不落正文回归。
- 行为影响：主转发路径仍按原始字节写出；内部解析保留安全窗口，不把完整图片响应载入审计、使用记录或诊断内存，失败审计仍保留请求正文以便定位。
- 发布异常处理：如大图事件解析异常，修正当前 SSE 解析窗口和审计省略策略；必要时停服务恢复到同一数据契约下的已验证构建。

## 下次遇到

- 先查什么：按 trace 查运行日志里的 `gateway_stream_intercept_parser_skipped`、`gateway_stream_inspector_skipped`、`recentSseEventTypes`、`terminalReceived`。
- 重点看什么：区分“主链路是否原样转发”和“旁路解析是否还能继续识别后续终止事件”。
- 如何避免误判：图像流中的大 `data:` 行是协议正常形态，不应作为上游错误或客户端错误处理；解析器只能做有限窗口解析，不能因为单个大事件永久放弃整条流；日志里看到 `stream_body_omission` 表示已按图片载荷省略正文，不是数据丢失。

## 完成总结

- 完成时间：2026-05-24
- 结论：图像 streaming 已按大 payload 事件处理，超大 SSE 不再导致整流解析失明；Responses 与 Image API 图像事件均有专项回归覆盖，日志侧省略图片响应正文并保留请求证据和正文省略元信息。
- 后续建议：若后续需要完整审计图像 payload，应另建受控对象存储或显式采样方案，不要在网关请求链路和日志路径里全量缓存 base64。
