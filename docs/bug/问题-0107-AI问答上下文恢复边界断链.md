# BUG-0107 AI 问答上下文恢复边界断链

## 基本信息

- 状态：已修复（Mock、repository 与真实模型验证）
- 严重程度：P1
- 模块：后端 / AI 问答 / 上下文 / 主动压缩 / 图片记忆
- 发现时间：2026-07-13
- 发现方式：完整验收前多代理只读审查与补充回归
- 关联计划：PLAN-0104
- 关联 bug：BUG-0106

## 问题概述

上下文主路径能完成第一次压缩，但在重复压缩、超出本地装载窗口、失败轮次、图片说明未完成、请求体接近上限和并发 usage 写回等边界下，存在丢失长期记忆、卡死会话、错过后续成功轮次或重新发送历史图片 Base64 的风险。

## 根因分析

- 第二次压缩只从旧 checkpoint 读取 `task_state`，没有重建长期记忆、工具结果和图片说明。
- 512 条消息 / 16 MiB 本地装载限制在压缩判断之前抛错，无法进入紧急压缩。
- 过滤失败助手后仍按数组相邻元素配对，导致后续成功轮次错位。
- 未完成图片说明的历史图片存在重新读取压缩图并生成 Data URL 的路径，且可能在语义未提取前被压缩掉。
- 压缩、图片说明没有业务超时；15 MiB 最终请求只拒绝，不先尝试压缩。
- usage 和 checkpoint 安装缺少完整 revision CAS；stale `compacting` claim 还可能阻塞过期清理。

## 修复方案

- 重复压缩完整恢复所有 checkpoint entry 类型，并增加第二次压缩记忆继承回归。
- 装载上限或请求体上限命中时先执行一次有界紧急压缩，再重建上下文和请求。
- 成功轮次按 `turnId` 配对，失败/取消轮次不再影响后续成功历史。
- 未完成图片说明时等待已有任务最多 1 秒，仍未完成则返回可重试错误；禁止历史图片 Base64 回流，禁止未解析图片轮次进入 checkpoint。
- 图片说明和结构化压缩分别设置 90 秒、120 秒超时。
- 每次接受轮次推进 context revision；usage 写回和 checkpoint 安装使用期望 revision CAS。
- 维护任务先恢复 stale compaction，再执行 checkpoint 清理。

## 下次遇到

- 同时构造失败轮次、超过本地行数/字节上限和未完成图片说明。
- 数据库检查 `context_revision`、`active_checkpoint_id`、entry 类型、usage 与请求体中是否出现 `data:image/`。
