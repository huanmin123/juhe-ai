# BUG-0023 分散失败未升级临时不可调用

## 基本信息

- 编号：BUG-0023
- 状态：已修复
- 严重程度：P1
- 发现时间：2026-06-13
- 发现方式：用户反馈
- 模块：后端 / 网关 / worker / 账号质量
- 关联计划：无
- 关联 bug：BUG-0020
- 责任人：AI

## 问题概述

- 现象：账户列表中多个账号长期显示“频繁失败”或“近期不稳”，但数据库持久状态仍为 `active`，没有升级为 `temporary_unavailable`。
- 期望：真实网关请求持续证明账号不可用时，应在确认后进入临时不可调用，并由后台冷却复测负责自动恢复。
- 实际：网关短窗口失败会先进入进程内短暂避让；如果失败分散在较长时间、来源单一或没有触发半开连续失败，就只会沉淀为账号质量标签，不会进入事前确认和持久状态写入。
- 影响范围：OpenAI-compatible / GPT 账号调度，特别是单用户、单 IP 或低频但持续失败的账号池。

## 复现步骤

1. 准备多个 `active` 且可调度的 GPT API Key 账户。
2. 让其中部分账户在真实网关请求中持续返回上游错误，但错误不满足 10 秒内多来源失败风暴。
3. 等待账号质量刷新后观察账户列表和数据库状态。

## 环境信息

- 分支 / 版本：本地工作区，macOS 生产实例复查。
- 数据状态：线上存在近窗口多次失败、成功率很低的 `active` 账户。
- 浏览器 / 系统 / Node 版本：macOS 部署，Node 后端。
- 是否稳定复现：是。

## 根因分析

- 表象：前端“频繁失败”标签看起来像账号状态，但状态筛选和调度仍按 `accounts.status` 判断。
- 真实根因：账号质量刷新只负责从真实请求聚合质量缓存，不负责触发持久状态确认；网关持久降级只由短窗口失败风暴、半开连续失败、账户错误策略确认、手动测试、冷却复测或人工操作触发。
- 为什么会发生：为了避免坏请求形态把账号误判为坏账号，真实网关失败先采用进程内短避让；但缺少一个跨窗口、由真实质量样本触发的后台确认机制。

## 修复方案

- 修改点：
  - `account-quality-refresh` 刷新质量缓存后，按固定批次列出近窗口频繁失败候选。
  - 新增账号质量失败确认队列，按账户所属系统账户和绑定分组上下文复用账户测试链路确认。
  - 确认成功保留正常状态；确认失败且属于账号故障时复用账户测试临时不可调用语义写入 `temporary_unavailable`。
  - 确认探针使用 `traffic_source = cooldown_retest`，不进入普通账号质量统计。
  - 为频繁失败候选查询新增 `idx_account_quality_scores_failure_precheck` 部分索引。
- 行为影响：分散但持续的真实账号失败会在后台确认后进入临时不可调用；坏请求形态导致的失败仍可能因确认成功而保持正常。
- 发布异常处理：该改动只影响后台确认和状态写入；如果生产确认探针异常增多，可先提高 `accountQualityRefreshIntervalSeconds` 或临时停止 worker 再回滚。

## 复发记录

- 2026-07-27：generic 完整 HTTP 失败改为 `opaque_upstream` 后，普通请求不再触发任何独立确认；同时独立探针的完整 HTTP 失败统一视为 `framing_complete_neutral` 且禁止写状态，导致“真实请求失败 -> 独立确认 -> temporary_unavailable”闭环失效。修复后 gateway 的 `opaque_upstream` 只负责投递按账户去重、5 分钟限频的独立健康检查，不进入共享质量或直接写状态；受控健康/质量探针的完整失败可以判定通用不可用，但传输电路仍保持 framing 中性。
- 2026-07-27 复查：补齐 standalone 投递端冷却和显式 `retry_next` 的即时确认；健康检查与质量预检改为共享账户级 single-flight 结果，质量候选改为轮转分页，避免重复探测、结果乱序和 Top 10 候选饥饿。
- 2026-07-27 端到端复查：OpenAI `GET /v1/models` 与 Anthropic 模型目录路径重叠，协议总入口已规定优先按 OpenAI 处理，但原生协议辅助判定仍把它识别为 Anthropic，导致健康检查在真实上游请求前以 `request_capability_mismatch` 短路且不累计失败。修复后辅助判定复用同一 OpenAI 路径优先级，隔离真实 gateway + mock 上游并发回归确认状态闭环恢复。

## 下次遇到

- 先查账户列表 tooltip 里的质量样本数、失败数、成功率和最后错误，再查 `accounts.status/cooldown_until` 是否真的变化。
- 重点看 worker 日志里的 `background_account_quality_refresh_completed`、`background_account_quality_failure_precheck_*`、`background_cooldown_account_retest_*`，以及网关日志里的 `gateway_account_precheck_*`。
- 不要把“频繁失败”标签直接当成持久状态；它是质量反馈，只有确认失败后才应升级到临时不可调用。
