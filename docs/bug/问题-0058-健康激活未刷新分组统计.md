## 问题概述

新账户统一先保存为 `pending_test` 和不可调度状态。健康检查成功后，账户会变为 `active` 和可调度，但原实现没有重新标记关联分组的 `group_account_stats_dirty`。

如果创建账户时产生的脏标记已经被统计 worker 消费，后续健康激活不会触发重新聚合，Node 和 Go 分组列表会继续读取陈旧的 `available=0`、`error=1`。

## 根因分析

- 账户创建状态语义调整为 `pending_test` 后，旧回归仍假设传入 `status='active'` 会直接创建可用账户。
- 健康成功写入只更新账户健康字段并清理账户 lookup，没有把状态和调度事实变化传递给分组统计失效链路。
- 分组列表遵守预聚合边界，只读取 `juhe_stats.group_account_stats`，不会在请求路径实时扫描账户表修正统计，因此缺失的 dirty 标记会持续暴露。

## 修复方案

- SQLite 健康成功在同一业务库事务内锁定并更新账户；仅当状态或 `schedulable` 实际变化时，按账户 ID 写入 `group_account_stats_dirty`。
- PostgreSQL 健康成功使用 `FOR UPDATE`、`expectedConfigRevision` 和同一事务写入 dirty；dirty 写失败时账户更新整体回滚。
- active 账户重复健康成功只刷新健康事实，不重复标记分组统计。
- 更新管理列表 fixture，显式通过健康成功激活账户，不再依赖创建入参绕过 `pending_test`。
- 补齐 worker、server、DB service、handler IPC，配置版本失配、重复成功和事务回滚回归。

## 防复发要求

- 任何影响账户状态、调度资格或分组可用性口径的写入，都必须同步检查 `group_account_stats_dirty` 失效链路。
- 预聚合列表回归必须固定“首次聚合后再改变业务事实”的顺序，避免创建时遗留 dirty 掩盖后续漏失效。
- PostgreSQL 状态写入和 dirty 标记必须保持同事务；配置版本失配不能更新账户或写 dirty。
- Node/Go 共存期要验证 Node writer 到 Go reader 的统计 freshness，不能只验证两端各自 DTO。

## 完成总结

健康激活现在会在状态或调度事实变化时可靠触发分组统计重建，Node 和 Go W5 分组列表不再长期读取激活前的预聚合值。真实 PostgreSQL writer-reader 联调仍属于生产接管门禁。
