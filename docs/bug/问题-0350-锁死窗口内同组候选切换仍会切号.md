# BUG-0350 锁死窗口内同组普通候选切换仍会切号

## 基本信息

- 编号：BUG-0350
- 状态：已修复待发布（2026-11-04）
- 严重程度：P2
- 发现时间：2026-11-03
- 发现方式：按用户要求核验「超级优先 + 锁死」组合时发现
- 模块：网关（账号派发 / 锁死门 / 链面兜底）
- 关联计划：无
- 关联 bug：无
- 责任人：网关维护者

## 问题概述

- 现象：AI 账户执行「锁死」后，账号在死亡窗口内发生真实失败，网关仍会切换到同组其他账号；锁死策略没有真正阻止切号。
- 期望：按 [AI账户锁死调度机制设计与实现前复审](../functions/AI账户锁死调度机制设计与实现前复审.md) §3.4/§10.5，锁死账号处于 `ENGAGED` 且未到死亡窗口时，真实失败后不得切换到同组其他账号或后备分组；流式请求先提交 SSE 响应头再断开（避免反向代理把 pre-commit 断开合成 502），非流式请求 Hijack+Close，客户端断连后自动重试；Hijack 不可用时才回退 503 handoff；锁状态保留，客户端重试继续；死亡窗口到期结算为 `DEAD_CONFIRMED` 后才允许切换。
- 实际：普通失败路径的锁死判断与默认分支返回相同的 `SkipAccount`，外层候选循环继续尝试同组下一个账号。临时双账号测试（已删除、未入库）结果为 `selected="a-2" err=nil failedHandlerCalls=3`：锁死账号 `a-1` 尝试 1 次 + 同账户重试 2 次后，请求成功切到 `a-2`。
- 影响范围：所有启用锁死且发生同组普通候选失败的账户；锁死功能在最主要失败路径上未生效，用户显式策略被绕过。

## 复现步骤

1. 同一分组准备两个 `active` 账户 `a-1`、`a-2`，`a-1` 开启锁死并处于 `ENGAGED`。
2. 让 `a-1` 上游返回 500（或制造已建立连接的传输失败），`a-2` 正常。
3. 发起一次 `/v1` 文本请求。
4. 观察实际结果：`a-1` 失败重试耗尽后，请求切到 `a-2` 成功返回。

## 环境信息

- 分支 / 版本：`backend-go/projects/gateway` 当前工作树，Go 网关。
- 数据状态：临时双账号测试，`BlocksCrossAccount=true` 注入 `a-1`，`a-2` 健康。
- 是否稳定复现：是（锁死门分支与默认分支同值，必然切号）。

## 根因分析

- 表象：锁死账号失败后仍换号。
- 真实根因：`internal/gatewaydispatch/attemptoutcomes.go` 的两处锁死判断（响应失败与传输失败）虽然读取了 `BlocksCrossAccount`，但命中时仍返回 `SkipAccount`，与紧随其后的默认分支返回值逐字相同；控制流没有任何变化。`dispatchSingleAccount` 将 `SkipAccount` 映射为 `attemptStopAccount`，`FetchFirstAvailableUpstream` 的候选循环继续下一个 `originalAccount`。
- 为什么会发生：锁死门只落在「是否跳过当前账号」的判定上，没有落在「是否允许跨账号切换」的决策点；后备分组与 `speed_first` 另有否决门，普通同组候选切换没有对应出口。
- 佐证：Node 历史实现同样以 `skipAccount = true; break` 结束单账户循环（`git show 488c3ac50:backend/src/modules/gateway/dispatch/upstream-dispatch.ts:1393-1398`），即该缺口在迁移前已存在；现有测试未覆盖「锁死账号失败 + 同组健康账号」场景。

## 修复方案

- 引擎新增锁死保持终态：`responseStopAccountLocked` / `errorStopAccountLocked` → `attemptStopLocked` → `dispatchResultLocked`；`FetchFirstAvailableUpstream` 命中后立即停止候选/分派段/后备遍历，返回 `AccountLockHoldError`，并按 `nextRetryAt` 释放发送租约。
- 链面 `settleDispatchError` 将 `AccountLockHoldError` 优先渲染为真·网络级断开：流式请求先提交 SSE 响应头并 flush，再 Hijack+Close，让 Caddy 把截断的流透传给客户端；非流式请求直接 Hijack+Close；Hijack 不可用时回退 503 `upstream_retryable_error`；两种路径都不进入 `switchToFallbackGroup`/耗尽切组。
- 链面 `switchToFallbackGroup` 与响应检查 `settleResponseStreamServerRetry` 增加同源锁死门；响应检查换号被拒时不写排除集、不计数、不切组。
- 完整非 2xx 现在会写入/推进锁死窗口（`RecordFailureAsync`，幂等），使 5xx 不再绕过锁死门；显式错误策略仍按原机制优先换号/结束。
- Codex compact 摘要路径经 `GatewayClientRetryError` 窄接口识别锁死保持错误，渲染 503 / `upstream_retryable_error`，与主链 handoff 契约一致。
- Key 池不可用、Key 安全上限、准备期 guidance 等候选内跳过出口增加最终锁死门；传输失败锁死路径补齐 key-model attempt 结算，避免前台许可泄漏。
- 锁死记账（`RecordFailureAsync`/`SettleDeadlineAsync`）改为 best-effort，失败只落审计，不否决既有 Key 轮换与同账号重试。
- 锁死等待继续受 §3.5.10 的 3 秒 `routeCoordinationBudget`、270 秒墙钟、取消与最终响应预留约束；单请求不硬撑 5 分钟，协调预算到即 handoff，客户端重试继续同一锁死窗口。
