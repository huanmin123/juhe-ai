> 本记录用于暂存用量统计、授权统计、非授权统计和团队统计方向的待复查问题。2026-05-05 已先修复静态复查确认的授权统计读口径问题；当前项目仍在大文件重构中，剩余统计语义和端到端数据一致性继续按本清单复查。

## 问题概述

- 现象：当前统计层已经覆盖调用方、资源归属方、授权关系、管理员全局、OAuth 快照和分组账户状态等多条线，但部分读写口径、页面展示口径和文档口径仍可能互相打架。
- 期望：授权统计和非授权统计能稳定分层：调用方看自己的调用，资源归属人看真实资源总量，授权管理看资源 × 用户的授权消耗，管理员全局看后台 global 缓存；不同维度不能误加、误读或互相替代。
- 实际：静态自查发现授权分组统计、授权详情、团队汇总、多日客户端数和统计缓存读取隔离等路径仍有待复查风险；其中 `request_count` 定义、授权分组统计、授权详情单条语义、授权 summary 读取边界、授权 scope 混合读取和失败计入授权消耗口径已完成确认或代码修正。
- 影响范围：统计概览、用量统计、授权管理用量详情、分组列表用量、AI 账户列表用量、使用记录、网关失败记录、后台统计 worker。

## 当前统计维度地图

| 维度 | 事实字段 / 缓存 scope | 预期含义 |
| --- | --- | --- |
| 调用方统计 | `usage_records.system_account_id`；`system_account` / `api_key` / `provider` / `model` / `endpoint` | API Key 所属系统账户自己的调用、模型、端点和错误统计。 |
| AI 账户真实总量 | `account_owner_system_account_id + account_id`；`scope_type = account` | 资源归属人的真实 AI 账户总消耗，包含归属人自用和所有授权使用。 |
| 分组真实总量 | `group_owner_system_account_id + group_id`；`scope_type = group` | 分组归属人的真实分组总消耗，包含归属人自用和授权分组使用。 |
| AI 账户授权消耗 | `account_owner_system_account_id + account_authorization_id`；`scope_type = account_authorization` | 某个被授权用户在某个 AI 账户上的消耗，不包含归属人自用。 |
| 分组授权消耗 | `group_owner_system_account_id + group_authorization_id`；`scope_type = group_authorization` | 某个被授权用户在某个分组上的消耗，不包含归属人自用。 |
| 管理员全局概览 | `system_account_id = global`；`scope_id = global` | 后台 worker 写入的全局缓存，不在接口请求时临时汇总事实表。 |
| OAuth 额度快照 | `account_usage_snapshots` | OpenAI OAuth 5h / 7d 上游额度快照，不属于本地 token / cost 统计。 |
| 分组账户状态 | `group_account_stats` | 账户数量、可用数、状态数和并发上限缓存，不等同于用量统计。 |

## 待复查问题

1. `request_count` 定义需要统一。
   - 位置：`docs/functions/核心功能设计.md`、`docs/functions/SQLite存储说明.md`、`backend/src/modules/gateway/openai-gateway.routes.ts`
   - 关注点：部分文档曾强调“同一请求只能写入一条 `usage_records`”，但存储说明和网关实现更接近“每次上游尝试写入”。需要明确 `request_count` 到底表示外部 API 请求、上游尝试，还是有效消耗里的上游尝试，否则失败重试会让调用方统计、资源真实总量和授权消耗一起放大。
   - 处理结果：已确认。`usage_records` 按上游请求 / 上游尝试保留事实明细；`request_count` 表示进入统计缓存的有效消耗次数。同一个客户端请求如果发生重试或切号，可以产生多条 `usage_records`，但只有成功、已拿到流式有效输出（首 token）或已有 token / cost 的记录才累计 `request_count`。

2. 授权分组列表用量可能展示成资源真实总量，而不是被授权用户自己的分组授权消耗。
   - 位置：`backend/src/storage/repositories.ts`
   - 关注点：AI 账户列表对 `access_type = authorized` 会读取 `account_authorization` 口径；分组列表当前按 `group_id` 读取 `group` 口径并填入 `accountStats.todayUsage` / `usage`。如果普通用户看到“仅可使用”的授权分组，这里可能混入归属人自用和其他被授权用户消耗。
   - 处理结果：已修复。授权分组行改为读取 `group_authorization`，自有分组行继续读取 `group` 真实总量。

3. 授权详情接口和前端弹窗存在“单条授权”与“同资源全部授权”口径混用风险。
   - 位置：`backend/src/storage/repositories.ts`、`frontend/src/views/authorizations/AuthorizationsView.vue`
   - 关注点：`GET /authorizations/:id/usage` 语义看起来是查看某条授权，但后端详情按 `resource_type + resource_id` 读取同资源所有授权；前端打开某行后又拉取同资源授权列表并把 `selectedAuthorization.usage` 替换为资源级总和。需要明确这个弹窗到底是“当前用户授权详情”还是“资源授权总览”。
   - 处理结果：已修复为“当前单条授权详情”。后端只按授权 ID 读取明细，前端不再用同资源全部授权覆盖当前弹窗总量。

4. 统计缓存读取需要继续收紧 `system_account_id + scope_type + scope_id` 三元边界。
   - 位置：`backend/src/storage/usage-summary-loaders.ts`、`backend/src/storage/repositories.ts`
   - 关注点：部分 loader 只按 `scope_type + scope_id` 读缓存，依赖 ID 全局唯一和缓存无脏数据。后续重构后建议所有资源真实总量和授权消耗读取都显式带上资源归属人的 `system_account_id`，避免导入、清洗、重建缓存或未来 ID 迁移时串口径。
   - 处理结果：已修复。summary loader 改为显式接收 `systemAccountId`、`scopeType`、`scopeId`，账户、分组和授权列表调用点均传入资源归属系统账户 ID。

5. `loadResourceAuthorizationUsageSummaries` 同时合并 `account_authorization` 和 `group_authorization`，需要按资源类型收口。
   - 位置：`backend/src/storage/repositories.ts`
   - 关注点：当前按授权 ID 同时查两类授权 scope 再合并。虽然正常情况下同一个授权 ID 只会属于一种资源类型，但如果缓存残留或导入数据异常，可能把账户授权和分组授权加到同一行。
   - 处理结果：已修复。授权列表按授权行 `resource_type` 分组读取 `account_authorization` 或 `group_authorization`，不再对同一批 ID 同时合并两类 scope。

6. 团队统计是“按团队来源分别汇总”，不是天然可相加的全局团队总量。
   - 位置：`backend/src/storage/account-usage.repository.ts`、`frontend/src/views/authorizations/authorizationFormatters.ts`
   - 关注点：同一用户如果通过多个团队来源获得同一资源，当前每个团队卡片都会包含该用户同一条稳定授权的用量。单个团队内部是用户去重汇总，但多个团队卡片之间不能直接相加；页面文案和后续报表需要避免把它当成全局去重总量。
   - 处理结果：已做页面降误导处理。授权用量弹窗文案由“团队总消耗”调整为“团队来源今日消耗”，后续报表仍需按该语义避免跨团队来源相加。

7. 未展示的客户端去重统计不再提前维护。
   - 位置：`backend/src/storage/schema.ts`、`backend/src/storage/usage-stats-writers.ts`、`frontend/src/types/domain.ts`
   - 关注点：当前页面和报表没有展示客户端去重指标，继续维护会增加统计语义、缓存重建和多日窗口解释成本。
   - 处理结果：已移除该未使用指标的 schema、写入、读取、领域类型和前端格式化逻辑；后续只有出现明确页面或报表需求时，再按真实展示口径重新设计。

8. provider / model / endpoint / error 分布目前偏调用方和管理员全局，不是资源归属方视角。
   - 位置：`backend/src/storage/usage-stats.repository.ts`、`frontend/src/views/stats/StatsView.vue`
   - 关注点：`usage_model_daily` 和 `usage_error_daily` 写入调用方与 global；资源归属人如果想看“我的资源被授权用户消耗了哪些模型 / 报了哪些错”，当前缓存并不支持。后续页面不要误把调用方概览解释成资源 owner 视角。
   - 处理结果：已确认暂不支持资源归属方模型 / 错误分布。模型和错误分布保持调用方与管理员全局视角；资源归属人只看真实资源总量和授权聚合消耗，排障找管理员处理。

9. 授权不可用、无可用上游、上游失败和成功请求需要明确是否都计入授权消耗。
   - 位置：`backend/src/modules/gateway/openai-gateway.routes.ts`
   - 关注点：分组授权可用但无上游账号时会带 `group_authorization_id` 写失败统计；分组授权不可用时只写调用方失败统计。需要确认这符合产品预期：授权不可用拦截是否算授权错误、无可用账号是否算授权消耗、上游重试失败是否按每次尝试计数。
   - 处理结果：当前口径调整为所有网关使用记录都进入 `usage_stats_*`，成功、失败、测试和后台检测统一计入请求次数；失败记录没有 token / cost 时按 0 token、0 cost 计入错误次数，便于在统计页和授权维度追踪。资源归属人自用仍不进入授权 ID 维度。
   - 追加复查：已修正 `first_token_ms` 判定，流式链路不再把任意首个字节当作首 token，而是等到 SSE 中出现有效输出 delta；该字段用于延迟展示，不再作为统计聚合过滤条件。

10. 消耗统计和排障错误统计需要分层。
    - 位置：`backend/src/storage/usage-stats-writers.ts`、`backend/src/storage/usage-stats.repository.ts`
    - 关注点：如果 `aggregateUsageStatsRecord` 过滤未形成有效上游消耗的记录，统计页会低估失败测试、无可用上游、网络异常和首包前失败。
    - 处理结果：已取消过滤，`usage_error_daily` / `usage_error_hourly` 会覆盖所有失败使用记录；token 和 cost 仍只来自真实解析到的上游用量。

11. 统计 worker 增量 upsert 不是幂等重放语义，缓存重建流程需要被明确。
    - 位置：`backend/src/storage/usage-stats.repository.ts`、`docs/functions/SQLite存储说明.md`
    - 关注点：worker 依赖游标推进并对缓存表做增量加法。如果游标被回退、状态丢失或手动重跑前未清空缓存，可能重复累计。文档里说缓存损坏可从 `usage_records` 重建，后续应补明确的清空 / 重建脚本或操作步骤。
    - 处理结果：已补统计缓存重建脚本。这个不是每次读口径调整都必须做的迁移；它是为了旧缓存已经被错误聚合、游标丢失、导入清洗或重建异常时能从事实源 `usage_records` 重新生成干净缓存。

12. OAuth 额度快照和本地 token / cost 用量必须继续保持分离。
    - 位置：`backend/src/storage/oauth-usage-loaders.ts`、`frontend/src/views/accounts/AccountUsageCell.vue`
    - 关注点：OAuth 5h / 7d 是上游窗口快照，本地 `usage_records` 是网关 token / cost 统计。额度快照已改为真实请求响应头被动更新；后续统计页和账户页不要把快照百分比加进本地用量，账户测试产生的真实模型请求仍按使用记录统计。

## 复查步骤

1. 完成当前大文件重构后，先运行类型检查和构建。
2. 准备至少 3 个系统账户：资源归属人 A、被授权用户 B、团队成员 C；准备一个团队 T，包含 B 和 C。
3. A 创建自有 AI 账户、自有分组、自有 API Key；先做一次自用调用，验证只进入 A 的调用方统计、A 的账户真实总量和 A 的分组真实总量，不进入任何授权统计。
4. A 授权 AI 账户给 B；B 通过自己的分组绑定该授权账户后调用，验证 B 的调用方统计和 B 的分组真实总量增加，A 的账户真实总量和 `account_authorization` 增加，不进入 A 的分组授权统计。
5. A 授权分组给 B；B 通过自己的 API Key 绑定授权分组后调用，验证 B 的调用方统计增加，A 的分组真实总量和 `group_authorization` 增加，命中账户的 A 账户真实总量增加，且不误写 `account_authorization`。
6. A 通过团队 T 授权账户和分组；验证 B / C 都展开为稳定用户授权 ID，个人来源被团队覆盖后历史用量仍合并到同一用户授权。
7. 如果允许同一用户来自多个团队来源，验证单个团队卡片内部去重，多个团队卡片之间不作为可相加总量展示。
8. 制造无可用账号、上游 4xx / 5xx、流式中断和重试，核对 `usage_records` 行数、`request_count`、错误统计和授权消耗是否符合“有效消耗次数”定义。
9. 分别查看账户列表、分组列表、用量统计、统计概览、授权详情、使用记录，确认调用方、资源归属方、授权关系和管理员全局四类页面没有互相借错口径。
10. 清空并重建统计缓存，验证重建后的 `usage_stats_totals`、`usage_stats_daily`、`usage_model_daily`、`usage_error_daily` 与 `usage_records` 事实源一致。

## 根因分析

- 表象：统计页面和授权页面都能显示用量，但不同页面背后的 scope 不完全一致，部分命名也无法直观看出是调用方、资源归属方还是授权方口径。
- 真实根因：新版统一授权同时引入调用者、资源所有者、稳定授权 ID、团队来源、后台缓存和全局统计，多条统计线共用 `usage_records` 和 `usage_stats_*`，读写边界需要更明确。
- 为什么会发生：当前实现集中在大文件 repository、网关路由和前端大页面中，重构前暂未完成多用户、多授权来源、失败重试和缓存重建的端到端核对。

## 修复方案

- 已完成修改点：`backend/src/storage/usage-summary-loaders.ts` 改为按 `system_account_id + scope_type + scope_id` 读取 summary 缓存；`backend/src/storage/repositories.ts` 修正账户、分组和授权列表读取口径，并将授权详情收窄为单条授权；`frontend/src/views/authorizations/AuthorizationsView.vue` 不再用资源级授权总和覆盖单条授权弹窗；后续已调整统计聚合口径，所有网关使用记录都会进入 `usage_stats_*`，失败按 0 token、0 cost 计入请求和错误次数。
- 兼容影响：本次调整改变授权分组列表和授权详情弹窗的展示数字，旧缓存表无需迁移；如果历史缓存中已存在串口径脏数据，仍建议清空并从 `usage_records` 重建统计缓存后验证。
- 回滚方式：如授权统计仍不稳定，可先隐藏授权用量详情中的团队汇总或授权分组用量展示，只保留调用方使用记录和资源真实总量。
