## 问题概述

- 现象：高性能模式下，AI 账户列表的当前并发数不稳定，甚至长时间显示 `0`，但实际网关有大量请求。
- 期望：账户页在列表加载或用户触发刷新时展示当前可见账户的 in-flight 并发快照；快照不可用时明确标记不可用，不能把默认值展示成真实 `0`，前端不得为该字段持续轮询后端。
- 实际：授权账户场景下，网关占用的 Redis 并发槽和账户列表读取的账号 ID 口径可能不一致，手动刷新页面也仍可能读到来源账号上的 `0`；旧的前端实时轮询方案会额外持续请求后端，不符合页面只按业务动作访问后端的底线。
- 影响范围：高性能模式下的管理侧 AI 账户页、用户侧我的 AI 账户页，以及定位并发槽是否准确的网关压测流程。

## 复现步骤

1. 启动 performance 模式，使用 PostgreSQL 和 Redis runtime state。
2. 打开 AI 账户列表，尤其观察被授权账户或管理员代看被授权用户账户。
3. 通过 API Key 对高并发分组持续发起请求。
4. 观察账户列表的当前并发列，可能长期停留在 `0`；即使手动刷新，如果 Redis 槽写在授权实例 ID 而列表按来源账号 ID 读取，也不会恢复正确读数。

## 环境信息

- 分支 / 版本：当前工作区
- 数据状态：performance 模式，Redis state 保存账号并发槽
- 浏览器 / 系统 / Node 版本：Windows 开发机，浏览器版本未限定
- 是否稳定复现：在页面不刷新且请求短促时稳定可见；长流式压测更容易人工确认

## 根因分析

- 表象：Redis 账号并发槽在网关请求生命周期里占用和释放，但前端看到的账户列表并发可能长期为 `0`，授权账户手动刷新也可能继续显示 `0`。
- 真实根因：授权实例和来源账号共享同一个真实上游资源，但旧实现部分网关写入路径按授权实例 ID 占用并发槽，列表和运行态快照按来源账号事实读取，导致写读 ID 不一致。
- 为什么会发生：原先没有把“并发事实账号 ID”抽成统一口径；压测脚本也没有把 Redis 并发槽和 mock 上游活跃流做对账，导致“显示长期 0”缺少专门回归门禁。后续曾短暂补过账户页轻量轮询，但该方案会持续访问后端，已按产品底线移除。

## 修复方案

- 修改点：网关并发占用、容量判断、会话亲和、运行态快照和本地屏蔽统一按来源账号 ID 作为并发事实账号 ID；账户列表加载时返回 `currentConcurrency` 与 `currentConcurrencyAvailable`；移除账户页实时并发轮询和专用轻量快照接口；高性能网关压测增加 Redis 账号并发槽采样和上游活跃流对账开关；授权账户普通更新接口禁止提交 `concurrencyLimit`，被授权人不能修改共享并发上限。
- 行为影响：授权实例和来源账号共享同一硬并发槽，账户页并发读数通过列表加载、筛选、分页、排序或用户触发刷新获取；快照不可用仍保留不可用标记，不把不可用误展示为真实 `0`，前端不再为该字段持续访问后端。
- 发布异常处理：如果 Redis state 不可用，接口应返回不可用标记或由列表原有错误路径处理；运维应优先检查 `JUHE_AI_REDIS_STATE_URL`、Redis state 发布端口和运行态 driver 配置。

## 下次遇到

- 先查什么：先看账户行 `currentConcurrencyAvailable`，再查 `JUHE_AI_RUNTIME_STATE_DRIVER` 和 Redis state 可达性。
- 重点看什么：Redis key `juhe-ai:account-concurrency-v2:<sourceAccountId>:total` 的 `ZCARD`、授权实例的 `authorizationInstanceSourceAccountId`、网关压测报告里的 `redis.accountConcurrency.maxTotal`、mock 上游 `activeStreamRequests`。
- 如何避免误判：当前并发是瞬时 in-flight，不是累计请求数；短请求可能在采样间隔之间完成，但持续活跃流不应长期显示为 `0`。授权实例必须按来源账号 ID 读写并发槽，不能只刷新前端页面排查。

## 完成总结

- 完成时间：2026-07-03

- 后续建议：真实远端 PG / Redis 栈复测时开启 `JUHE_AI_GATEWAY_LOAD_ASSERT_ACCOUNT_CONCURRENCY=1`，优先用慢 SSE mock 上游观察并发槽与列表刷新读数。
