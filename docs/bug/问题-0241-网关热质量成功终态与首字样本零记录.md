## 问题概述

- 现象：热质量存储只积累失败计数，completed_responses 恒 0、完成率恒 ≤0.5、首字 EWMA/P95 恒空。
- 期望：成功终态（completed_response）计入完成数、首字节延迟进入首字样本，热质量统计完整驱动速度优先排序。
- 实际：compareSpeed 恒 0，速度优先排序延迟维度完全中性，账户排序质量系统性退化，仅靠分钟桶过期恢复。
- 影响范围：gateway 热质量统计与账户排序（速度优先模式）；失败计数路径正常。

## 复现步骤

1. 通过网关完成若干成功请求（completed_response 终态）；
2. 查看热质量存储：completed_responses 为 0、首字样本为空；
3. compareSpeed 参与排序时恒返回 0（延迟维度中性）。

## 根因分析

- 表象：成功终态与首字样本零记录。
- 真实根因：引擎把 `HotQualityAttempt` 句柄放进 `UpstreamDispatchResult`（upstreamdispatch.go:340-366 惰性创建），但 chain 层无消费：
  - `RecordTerminal` 生产调用点仅 attemptoutcomes.go:163/:347 两处，且全在失败路径（upstream_response_failure/explicit_policy/timeout/transport），成功终态（completed_response）无发射点；
  - `MarkFirstByte` 生产调用点为 0；
  - `confirmProtocolSuccessSideEffects`（chain_v1_loop.go:897-933）只结算 Key 轮转/API Key 成功/账户锁，不触发热质量。
- 为什么会发生：句柄已创建但消费端未接线（事实）；原始接线意图待 Node 历史取证确认，暂不推断。

## 修复方案

- Node 契约已取证（git `70acc84e6^` routes.ts:1841-1865）：响应体处理完成后的统一结算点——completed_response 条件 = 2xx + 不重试 + 协议验证成功；firstByteMs 载荷表达式对所有 outcomeClass 臂统一求值。按此契约在 chain 响应终态消费句柄（`settleHotQualityTerminal`，见验证结果）。

## 验证结果

- 修复形态：
  - `HotQualityTerminal` 加 `FirstByteMs`、常量补 `completed_response`、`UpstreamDispatchResult.HotQualityAttempt` 改为接口类型；

  - 桥接 `chain_wiring_w2c.go` 透传 `FirstByteMs`；幂等由 lifecycle terminalOnce 保证。
- Node 契约依据：git 历史 `70acc84e6^` routes.ts:1841-1865——completed_response 条件 = 2xx + 不重试 + 协议验证成功；firstByteMs 对所有臂统一求值。

### 复审发现的装配层 scope 失配及修复（2026-09-30 同批次）

- 独立复审发现 blocker：热质量 attempt 写入与排序读取的 scope key 维度失配，即使终态/首字已按上节接好，生产装配写入的记录排序侧仍读不到。证据链：
  - 写侧：compose.go 装配 `newChainHotQualityLifecycleFactory`，其 `chainHotQualityLifecycleAccountOf`（chain_wiring_w2c.go）构造 `GatewayHotQualityAccountView` 只填 ID，`ProviderProtocolProfileID/ProtocolCode/ProtocolVersion` 全空；
  - `NewGatewayHotQualityAttemptLifecycle` 对空协议字段 `orDefaultString("", "")` 得 `":"`，非空通过校验 → `scope.ProtocolProfile = ":"`；
  - 读侧 `chainHotQualityAccountViewOf` → `hotQualityScopeForAccount`（runtime.go）用账户真实协议维度投影；
  - `HotQualityScopeKey` 四维精确拼接 → `":"` ≠ 真实 profile → 本批写入的 completed_response/首字样本生产排序读不到。
- 修复：引擎侧 dispatchsingle.go 早已把 `ProtocolProfile: hotQualityProtocolProfileOf(c.account)`（profile id 优先、空值回落 `protocolCode:protocolVersion`，与读侧 `orDefaultString` 投影语义一致）放进 `HotQualityLifecycleInput`，装配层此前未使用。`chainHotQualityLifecycleAccountOf` 现以 `input.ProtocolProfile` 填 `ProviderProtocolProfileID`，两侧 scope key 逐字符相等（profile-id 臂与 code:version 回落臂均覆盖）。
- 附带缺口（授权 runtimeKey，未能装配层修复，留档）：授权账户读侧 runtimeKey 为 `id:authorized:sys:grp:authz`（`GatewayAccountRuntimeKey`），写侧因 `HotQualityLifecycleInput` 只携带 `AccountID`（无 AccountAccessType/BindingSystemAccountID/BoundGroupID/AccountAuthorizationID）退化为裸 ID，授权账户的 attempt 记录排序读不到；需引擎侧扩展 input 携带绑定上下文后修复（upstreamdispatch.go 的 input 结构与 dispatchsingle.go 构造点）。
- 新增防失配回归锁（chain_wiring_w2c_test.go）：
  - `TestChainHotQualityLifecycleScopeMatchesOrderingScope`：经生产 factory 真实投影构造 lifecycle，断言写侧 scope key 与读侧排序投影（chainHotQualityAccountViewOf → hotQualityScopeForAccount 取值语义 → HotQualityScopeKey）字符串相等，并以源码 needle 锁定引擎侧 `hotQualityProtocolProfileOf` 投影契约（既有 8 个测试全用 fake lifecycle，绕过 factory 投影，本锁补上）；
  - `TestChainHotQualityLifecycleAuthorizedRuntimeKeyGap`：授权缺口行为锁（写侧裸 ID / 读侧 authorized 键），引擎 input 扩展后翻转。
- 同批次澄清 chain_v1_loop.go `settleHotQualityTerminal` 注释：RetryUpstream 中仅引擎失败路径（非 2xx 失败响应/传输错误）已在 attemptoutcomes.go 两条失败路径结算；响应期重试族（response_inspection/pre_commit_stream_failure）不经过那两条路径，attempt 终态悬挂（即下方留档第三项的准确表述）。
