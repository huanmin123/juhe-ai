## 问题概述

- 现象：部分上游中转短时间出现 502、500、缺少流式终止事件或 EOF 异常时，账号会很快进入本地短期屏蔽或累计流式失败计数，导致调度池快速避开该账号。
- 期望：未命中请求级特征规则、账号错误策略或系统明确处理策略的临时型失败，应先按同账号重试吸收波动；只有重试仍失败，或流式失败已经产生可见输出导致无法透明恢复时，才记录账号失败。
- 实际：未知非 2xx 响应没有先做同账号重试；流式失败在尚未向客户端写出 body 时也会立即触发账号流失败副作用。
- 影响范围：OpenAI 兼容网关的 `/v1/responses` 与 `/v1/chat/completions`，尤其是使用第三方中转且用户量较大时，容易把中转瞬时波动误判为账号健康问题。

## 复现步骤

1. 配置一个上游账号，模拟前几次返回 HTTP 502，随后恢复 200。
2. 使用本地网关请求 `/v1/chat/completions` 或 `/v1/responses`。
3. 观察账号是否在重试前被标记为临时不可调用或进入本地屏蔽。

## 根因分析

- 表象：账号状态没有每次失败都立刻变为 `temporary_unavailable`，但 Web 进程本地短期屏蔽和 `stream_failure_count` 会在短时间内快速生效。
- 真实根因：未知失败缺少“策略未命中后的同账号重试缓冲层”；流式失败副作用没有按可见输出区分“已经输出回答或工具参数，无法透明恢复”和“只写出 response.created、心跳或 metadata，可视为客户端可重试波动”。
- 为什么会发生：原逻辑更偏向尽快保护账号池，遇到失败就先避开当前账号；在第三方中转偶发波动频繁时，这会放大误伤。

## 修复方案

- 修改点：
  - 未命中上游错误特征规则和账号错误处理策略的未知非 2xx 失败，先按 `temporaryUnschedulableRetryAttempts` / `temporaryUnschedulableRetryIntervalSeconds` 同账号重试；兜底层不再维护状态码白名单，状态码分类由特征规则和账号错误策略负责。
  - 流式失败若尚未产生可见输出，暂不累计账号流失败计数，也不触发本地短期屏蔽；`response.created`、心跳和 metadata 不算可见输出。
  - 可见输出前的流式失败统一改写为 `upstream_retryable_error` 的 `response.failed`，包括首段前无数据、空闲超时、缺少终止事件、上游 `response.failed` 和通用 `event: error`；碎片化 SSE 只要仍有 raw chunk 到达就继续转发，不再按完整事件等待超时处理。
  - 已经产生文本、reasoning、工具参数等可见输出的流式失败仍按原流熔断逻辑计数，因为服务端不能安全重放半段流。
- 行为影响：普通非 `2xx` 上游响应统一按临时状态配置做同账号确认重试；已有流式输出后的失败仍保留保护账号池的行为。
- 发布异常处理：如流式失败处理误伤，修正当前错误策略、可见输出判断或账号副作用边界；必要时停服务恢复到同一数据契约下的已验证构建。
