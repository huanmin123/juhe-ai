# BUG-0003 管理面并发请求触发 SQLite 写锁

## 基本信息

- 编号：BUG-0003
- 状态：已修复
- 严重程度：P1
- 发现时间：2026-05-06
- 发现方式：用户反馈 traceId
- 模块：后端 / 存储 / 文档
- 关联计划：无
- 关联 bug：无
- 责任人：AI

## 问题概述

- 现象：管理面账号列表偶发返回 500，运行日志按 traceId 可看到 `database is locked`。
- 期望：管理面并发加载账号、供应商、代理、分组和系统账户时不应因为短暂 SQLite 写锁失败。
- 实际：`GET /api/accounts?sorts=priority%3Aasc` 在鉴权中间件更新登录会话活跃时间时失败。
- 影响范围：所有需要 `/api` 鉴权的管理面接口都可能受影响，账号页并发请求更容易触发。

## 复现步骤

1. 登录管理面并进入账号页。
2. 快速刷新或触发账号页并发加载多个管理面接口。
3. 用运行日志搜索 traceId `2ed274c9-0534-43a3-a842-5bc82ec949ec`。

## 环境信息

- 分支 / 版本：本地开发工作区
- 数据状态：`backend/data/juhe-ai.sqlite3`
- 浏览器 / 系统 / Node 版本：Chrome 146，Node 24.3.0
- 是否稳定复现：否，依赖并发请求和后台 worker 写入时机

## 根因分析

- 表象：账号列表请求返回 500。
- 真实根因：主进程和 background worker 各自持有 SQLite 连接，数据库虽为 WAL 模式，但连接 `busy_timeout` 为 0；同时鉴权中间件每个请求都会写 `system_sessions.last_seen_at`，账号页并发加载会制造多次不必要写入，短暂写锁会立即变成 `ERR_SQLITE_ERROR: database is locked`。
- 为什么会发生：第一阶段后台运行日志索引、审计和统计写入迁移到 worker 后，主进程仍在高频鉴权路径同步写 session，缺少 SQLite 写锁等待与写入节流。

## 修复方案

- 修改点：数据库连接初始化设置 `PRAGMA busy_timeout = 5000`；会话 `last_seen_at` 刷新改为 60 秒节流，并在 SQL 中追加旧时间条件，避免并发请求重复写同一 session。
- 行为影响：不改变登录有效期判断；`last_seen_at` 展示或清理语义从逐请求精确更新变为分钟级活跃时间。
- 发布异常处理：如会话活跃时间异常，修正当前节流逻辑并验证登录态清理；必要时停服务恢复到同一数据契约下的已验证构建。

## 下次遇到

- 先查什么：按 traceId 搜 `runtime_logs.raw_json`，看 `err.stack` 是否落在 `touchSession`、日志索引、审计落库或统计写入。
- 重点看什么：`PRAGMA busy_timeout`、是否有请求路径无条件同步写库、worker 是否有长事务批量写入。
- 如何避免误判：不要只看失败接口名称；先看栈顶写入点，区分业务查询失败和鉴权/日志等共享层副作用失败。

## 完成总结

- 完成时间：2026-05-06
- 结论：通过 SQLite 写锁等待和 session 写入节流消除了管理面并发请求下的 `database is locked`；同时修正了运行日志“文件导入 + 实时流”双路径造成的新日志重复索引。
- 后续建议：如果后续管理面并发和网关写入量继续增大，再评估把登录 session 活跃刷新改为内存批量刷新或独立轻量队列；历史重复运行日志可按需要再做一次离线清理。
