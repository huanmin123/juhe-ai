- 严重程度：P1

- 模块：后端 / 网关 / 使用记录 / PostgreSQL / SQLite / 前端

## 问题概述

- 现象：GPT 账户已经保存服务档位和思考级别覆盖，但真实派发可能仍使用客户端原值；“我的使用记录”又无法稳定展示实际档位、最终思考级别，并可能把 Priority / Flex 成本按 Default 重建。
- 期望：API Key、OAuth、Chat、Responses 和显式 bridge 都使用最终账户覆盖；compact 保持既有 reasoning 例外；使用记录保存并展示最终事实，历史成本优先读取请求时计价快照。
- 实际：账户写入层包含两个覆盖字段，但 `runtimeOpenAIAccountCredentials()` 白名单遗漏；使用记录列表投影遗漏已有 service tier 列，schema 没有 reasoning 字段和最终计价快照，成本装饰也没有传 `billedServiceTier`。
- 影响范围：GPT 上游账户覆盖、Node 使用记录 SQLite / PostgreSQL 读写、管理侧和用户侧使用记录页面。

## 根因分析

- 账户配置、加密存储、运行时凭据投影和最终请求改写属于四个独立契约；此前测试只覆盖了配置与改写函数，没有覆盖中间投影，导致已保存字段在派发前被丢弃。
- 使用记录详情使用 `SELECT *`，列表使用手写轻量列投影；新增 service tier 后只更新了 schema / mapper，没有同步两个列表投影，因此详情和列表表现不一致。
- 成本浮层按当前目录临时重建，没有把实际计费档位传入，也没有持久化请求时最终单价和档位定价来源。
- 高性能模式虽然在 PostgreSQL 写入前异步补齐快照，但补齐发生在 Redis Stream consumer 消费时；出现 backlog 后会读取未来目录，把消费时间误当成请求事实时间。
- 上游失败尝试没有 token 或成本事实，但 Redis Stream 入队前仍执行异步模型目录解析；目录缓存或数据库变慢时会直接拖延故障切换。

## 修复方案

- 运行时白名单补 `service_tier_override`、`reasoning_effort_override`，不放宽 API Key、token 等敏感字段。
- 大 JSON scanner 保持 worker 自包含，统一提取 Chat `reasoning_effort`、Responses `reasoning.effort`；客户端 body 写 requested，最终上游 body 写 effective。
- SQLite / PostgreSQL schema 新增 `requested_reasoning_effort`、`effective_reasoning_effort`、`cost_breakdown_snapshot_json`，所有列表与详情投影同步补齐 service tier、reasoning 和快照。
- 计价快照保存最终单价、各项小计、档位专用价 / 基础价倍率来源和实际倍率；写入时目录未命中也保存 `unknown` 快照和当时已有成本。上线前旧空快照只展示已落库总成本 / 缓存成本并标记来源未知，禁止用当前目录重建历史单价。
- PostgreSQL 入库固定先执行异步目录补价再生成写计划；补价未命中或异常时，写计划仍生成 `unknown` 快照，不能把新记录以空快照落库。
- `redis_stream` 路径在生成 `createdAt/id` 后、Redis 入队前异步解析目录并固化完整 `pricingModel/cost/pricingSnapshot`；目录读取失败也立即固化 `unknown` 快照。consumer 遇到已有快照必须原样写入，禁止按落库时目录再次补价。
- 没有 token、图像、音频或既有成本事实的失败记录在进入异步目录解析前直接短路；producer 与 consumer 都不得为这类记录查询目录或用未来目录补写计价模型。
- 前端模型列展示非 Default 实际档位和有效思考级别；桌面 / 移动端合并延迟；成本浮层移除模型映射解释，只展示计价事实。

## 离线数据库同步

上线前停止服务并完成备份。以下 SQL 只供一次性离线同步，不挂到应用启动、网关或 worker 路径。

PostgreSQL：

```sql
BEGIN;
ALTER TABLE juhe_usage.usage_records
  ADD COLUMN IF NOT EXISTS requested_reasoning_effort text,
  ADD COLUMN IF NOT EXISTS effective_reasoning_effort text,
  ADD COLUMN IF NOT EXISTS cost_breakdown_snapshot_json text;
COMMIT;
```

SQLite standalone：对 `JUHE_AI_USAGE_SHARD_ROOT` 下每一个现存 usage shard 停机逐库执行；新 shard 会直接使用最新 schema。

```sql
ALTER TABLE usage_records ADD COLUMN requested_reasoning_effort TEXT;
ALTER TABLE usage_records ADD COLUMN effective_reasoning_effort TEXT;
ALTER TABLE usage_records ADD COLUMN cost_breakdown_snapshot_json TEXT;
```

同步后必须用 `PRAGMA table_info(usage_records);` 或 PostgreSQL `information_schema.columns` 检查三列。旧记录无法可靠还原当时最终单价和倍率时保持快照为空，禁止用当前价格批量伪造历史快照。

## 下次遇到

- 先查账户字段是否同时经过写入规范化、加密存储、运行时凭据投影和最终请求 body 四层。
- 详情正确而列表错误时，优先对比 SQLite / PostgreSQL 的手写轻量 SELECT 列表，不要只看 mapper。
- 价格异常先看 `billed_service_tier` 与 `cost_breakdown_snapshot_json`；不能只根据客户端 `service_tier` 或当前模型目录推断历史费用。
- 新记录的快照为空就是写入契约回归；不能等未来目录补齐后再重新解释当时成本。
- Redis Stream 场景先检查消息体是否已经带 `pricingSnapshot`；只在 consumer 落库前补价仍会受 backlog 时间漂移影响。请求路径只能异步读取目录，不能为固化快照同步扫表。
- 失败尝试没有任何计费维度时应直接保留失败事实，不得为了补 `pricingModel` 等非必要字段把目录 I/O 放进故障切换链。
