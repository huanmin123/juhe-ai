## 问题概述

- 现象：生产表监控显示 `runtime_logs` 单表约 51.8 万行，表大小约 559.5 MB，索引大小约 374.2 MB，总大小约 933.8 MB，最近 1 小时增长约 1.8 万行。
- 期望：生产默认 `info` 日志只保留请求完成、失败、重试、账号避让和后台异常等运维必要事件，不让每次成功网关请求产生多条运行日志。
- 实际：成功网关链路在 `info` 级别记录上游请求开始、上游响应头、流式 pipe 开始、流式成功结束和流式进度摘要，导致运行日志索引随真实流量被多倍放大。
- 影响范围：生产运行日志文件、`runtime_logs` 索引表、运行日志 facets、dataset 库体积和后台日志写入压力。

## 复现步骤

1. 生产默认 `JUHE_AI_LOG_LEVEL=info`。
2. 持续请求 `/v1/responses` 或 `/v1/chat/completions`。
3. 查询最近 1 小时 `runtime_logs` 事件分布，可看到多个成功链路事件与 `http_request_completed` 同时增长。

## 根因分析

- 表象：`runtime_logs` 表和索引增长很快，容易误判为重复导入或 SQLite 表异常。
- 真实根因：成功网关链路的过程日志过细，并且使用 `info` 级别进入生产普通日志和运行日志索引。
- 为什么会发生：网关调试期为了排查上游请求和流式链路，保留了多条成功态过程日志；生产默认 `info` 会完整写入这些事件。运行日志索引还会保存 `raw_json` 并维护多组索引，体积会明显大于原始文本大小。

## 修复方案

- 修改点：
  - `backend/src/modules/gateway/dispatch/upstream-attempts.ts`：`gateway_upstream_request_started`、`gateway_upstream_response_received` 从 `info` 降为 `debug`。
  - `backend/src/modules/gateway/response/stream.ts`：`gateway_stream_pipe_started`、`gateway_stream_finished_success_after_terminal`、`gateway_stream_progress` 从 `info` 降为 `debug`。
  - `backend/src/modules/accounts/account-test.service.ts`：`account_diagnostic_test_retry_scheduled` 从 `info` 降为 `debug`。
  - 2026-06-23 追加收缩运行日志索引：`runtime_logs` 只保留 `time` 和 `trace_id + time` 两个查询索引，不再创建 `level + time`、`event + time`、`created_at`、`created_at + id` 四个低频筛选索引。
- 行为影响：生产默认 `info` 下不再记录高频成功过程日志；失败、异常、账号避让、请求完成和后台错误仍保持原有级别。
- 索引影响：运行日志默认最新列表和按 `traceId` 排查仍走索引；按 `level` / `event` 的管理员低频筛选会在时间索引窗口内过滤，可能比原来慢，但减少索引体积和写入放大。
- 发布异常处理：如临时需要止血但尚未发布代码，可短期把生产 `JUHE_AI_LOG_LEVEL` 调为 `warn` 并重启；这会同时隐藏正常 `info` 运行日志，只适合应急。
