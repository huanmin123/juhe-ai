# BUG-0176 系统主动请求缺少渠道身份被上游拒绝

## 问题概述

- 现象：同一 AgentRouter GLM Coding 账户通过 OpenCode 调用 `glm-5.3` 成功，但项目人工账户测试的 `chat_json` 返回 `503 upstream_retryable_error`，`chat_sse` 返回被响应检查包装后的 `401 response_inspection_matched`。
- 期望：人工账户测试、后台健康探针、主动模型检测和受控模型目录刷新使用与账户协议档案一致的上游客户端身份。
- 实际：GPT/Codex、Anthropic OAuth、Gemini Code Assist 和 Grok OAuth 的身份逻辑散落在部分调用点；GLM Coding 没有 ZCode 身份，J3b 和模型目录也没有复用已有身份规则。
- 影响范围：要求识别官方客户端的上游可能把系统主动请求拒绝或分配到错误的套餐/额度通道，而真实客户端流量仍可正常工作。

## 复现步骤

1. 使用同一已脱敏账户配置、代理和 `glm-5.3`，分别从 OpenCode 与裸 OpenAI-compatible 请求调用 `/v1/chat/completions`。
2. OpenCode 返回正常结果；裸请求返回 `401 unauthorized client detected`。
3. 在项目管理面执行人工账户测试，观察 JSON/SSE 两种测试都失败且没有模型映射。

## 环境信息

- 分支 / 版本：当前工作区；OpenCode 1.18.5；ZCode 3.11.2。
- 数据状态：使用用户当次提供的测试账户，凭据未写入仓库、文档或测试产物。
- 浏览器 / 系统 / Node 版本：Windows；本问题在 Go 系统请求链路复现。
- 是否稳定复现：身份对照稳定；上游错误外观受代理重试与响应检查影响。

## 根因分析

- 表象：项目返回通用 `503` 或包装后的 `401`，容易误判为模型不存在、Key 无效或上游临时故障。
- 真实根因：系统主动请求没有真实下游客户端身份，又缺少统一的“协议档案 -> 官方客户端静态身份”策略。AgentRouter 对请求身份有严格检查，因此同一凭据在 OpenCode 中可用而在项目探针中被拒绝。
- 为什么会发生：历史实现只在部分探针内单独补 GPT/Codex、Claude Code、Gemini CLI 和 Grok 身份；新增 GLM 档案及后续 J3b、模型目录直连没有统一复用点。另外，直接上游探针还会把仅供本地识别的 `x-juhe-client-profile` 一并发出。

## 修复方案

- 新增共享 `upstreamidentity` 策略：精确客户端绑定档案优先应用静态身份；没有精确身份的系统 API Key 请求在未提供 `User-Agent` 时使用 OpenCode 1.18.5 的最小静态 UA-only 兜底。
- GLM Coding OpenAI/Anthropic 档案应用 ZCode 3.11.2 的 `User-Agent`、`HTTP-Referer`、`X-ZCode-App-Version` 和 `X-Title`；不伪造设备、会话、签名、nonce 或 PoW。
- 人工账户测试、J1 后台探活、Gateway J3b 模型检测、jobs 遗留 J3b resolver 和模型目录刷新统一接入该策略。
- GLM Coding Anthropic 系统请求使用 `Authorization: Bearer`；通用 GLM 与其他通用 API Key 保持协议认证语义，同时按上述条件补 `User-Agent: opencode/1.18.5`。
- 普通网关流量不进入该策略，继续保留下游真实客户端身份；内部 `x-juhe-client-profile` 不再泄漏到上游。
- 不生成 `x-opencode-*`、session、project、request、client、签名、设备、nonce 或 PoW 等动态字段；余额查询仍是独立适配器。
