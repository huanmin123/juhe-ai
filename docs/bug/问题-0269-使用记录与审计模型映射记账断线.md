# 问题-0269：使用记录与审计的账号模型映射记账断线（上游模型与映射标记全空）

- 编号：BUG-0269
- 状态：已修复（2026-10-03），待发布
- 发现：用户生产报障——"我的使用记录"模型列只显示请求模型，没有橙色的 `上游 <模型>` 标签；同时怀疑"上游返回的模型与请求不一致"的红色 `上游响应 <模型>` 提示机制也失效。

## 现象

- 生产 gateway 流量（`traffic_source=gateway`）成功记录的模型列只有一个蓝色请求模型标签；映射目标模型只出现在 `upstream_response_model`（上游响应观察值），`upstream_model` 恒为 NULL。
- 生产 usage_records 全表 142,566 行 `model_mapping_applied` 全为 0（从未出现 1）；`upstream_model` 非空仅 807 行且没有任何一行与 `model` 不同（`upstream_model <> model` 行数 = 0）。
- 审计侧同病：`juhe_dataset.audit_logs` 全表 `model_mapping_applied = f`，attempt 行同样退化。
- 映射本身在请求链上是生效的：账号 `acc_1789611837269_4fcb2037`（api.shenwenai.com-glm-dsf）启用着 `glm-5.3-flash (chat_completions) -> deepseek-v4.1-flash (chat_completions)`，同一账号请求 `glm-5.3-flash` 的上游响应模型正是 `deepseek-v4.1-flash`——**只有记账/展示链路丢了映射，转发改写是好的**。

## 根因

映射记账在三条真实记账路径上都断了，且断法各不相同（BUG-0267 同族的"判定/结构在、链面消费未接"）：

1. **成功记账（主因）**：完成尝试记账的唯一生产入口是 `chainFinalizationUsage.RecordCompletedUpstreamAttempt`（`cmd/juhe-ai-gateway/chain_usage.go`），它自己拼 `gatewayusage.UsageRecordInput`，`UpstreamModel` / `PricingModel` / `ModelMappingApplied` / `ModelMappingSource` / `SourceEndpointFamily` / `UpstreamEndpointFamily` 一个都没赋值。落库侧 `nilableString/` `boolToInt` 把空串写 NULL、nil 写 0（`jobs/internal/usagewriter/rows.go`）。
   - 项目内注释早已写明"完成尝试记账走 chainFinalizationUsage 直投 recorder"（`chain_usage_wiring.go`），而 2026-09-20 的 `WithModelResolver` 收口只接进了 `gatewayusage.Service`（其 `RecordCompletedUpstreamAttempt` 在当前 Go 链**无调用方**）——接线接到了死路上。
2. **失败记账**：`gatewayusage.Service` 一侧有完整映射记账，但 4 个调用点都没有传 `SourceEndpointFamily`（`chain_ports.go` 的 `usageAttemptRecorderAdapter` 与三个 `chainFailureDispatcher` 分支）。而 `gatewayopenai.ResolveAccountModelMapping` 首道守卫就是 `sourceEndpointFamily == ""` 直接返回 nil，于是解析恒不命中：`upstreamModel` 退化为请求模型、`applied=false`。
3. **审计捕获**：`newAuditCapture`（`chain_v1_audit.go`）未设 `AuditCaptureInput.SourceEndpointFamily`，`auditModelAccounting` 拿到空 family，审计 attempt 行与 request-level 审计行的映射列同步退化。
4. **计价键走样（同源偏差）**：`chain_usage.go` 成本估算用 `firstNonEmpty(UpstreamResponseModel, RequestedModel)` 作为计价键——把上游响应观察值当成了计价模型。文档与 Node 都不是这样：`docs/functions/上游响应模型不一致审计.md` 明确 `upstream_response_model` "不是模型映射、计费、路由或失败判定机制"；`docs/functions/自定义模型与模型映射设计.md` 与 `模型价格与用量统计口径.md` 要求"发生映射按 `upstream_model`、未映射按请求模型计价"；Node `usageCostCatalogModel = pricingModel ?? upstreamModel ?? requestedModel`。旧实现是缺映射记账后拿响应模型"凑"出来的近似，映射目标与上游回显不同（供应商重路由）时直接错价。

连带丢失的同源字段（同一函数、同一批修复）：`usage_semantic` 被硬编码为 `gateway_request`（文档要求 `openai`/`anthropic`/`gemini`）、`providerProtocolProfileId` 未写、失败尝试缺 `failureAttribution`、服务层级与推理档位未透传、负 `durationMs` 未夹取。

## 修复

- `cmd/juhe-ai-gateway/chain_usage.go`：`chainFinalizationUsage` 增加按请求注入的 `requestedModel` / `sourceEndpointFamily` / 模型解析器；完成与失败两条记账都做与 Node `accountUsageModelAccounting` 等价的解析（复用运行时同一 `usageModelResolverAdapter` 与 `usageModelAccountOf` 账户投影，family 取 `requestMappingSourceFamilyOf(req)` 与派发链改写同源），落六字段；计价键改为 `pricingModel ?? upstreamModel ?? requestedModel`；成本档位对齐 Node `resolveUsageServiceTiers` 的 `billedServiceTier`（reported ?? effective ?? requested，与 jobs 冻结侧同序）；补齐 `providerCode`（账号视图优先）/ `providerProtocolProfileId` / `usage_semantic`（按协议档案）/ `failureAttribution` / 服务层级与推理档位 / `durationMs` 夹取。
- `cmd/juhe-ai-gateway/chain_v1.go`：finalization 记账实例注入 `requestModelHintOf(req)` 与 `requestMappingSourceFamilyOf(req)`。
- `cmd/juhe-ai-gateway/chain_ports.go`：4 个失败记账调用点补 `SourceEndpointFamily: requestMappingSourceFamilyOf(req/input.Req)`。
- `cmd/juhe-ai-gateway/chain_v1_audit.go`：`newAuditCapture` 注入 `SourceEndpointFamily`，审计 attempt 行与 `audit_logs` 主行恢复映射记账。

读链路与前端无需改动：`statreads` 早已 SELECT `upstream_model`/`model_mapping_applied` 并计算 `upstreamModelMismatch`，前端标签条件（`modelMappingApplied && upstreamModel`、`upstreamModelMismatch && upstreamResponseModel`）也已就位——缺的只是数据。

## 残余项（未纳入本批）

- **Codex OAuth 账户的映射在运行时未被消费（既存缺口，非本次引入）**：`isCodexOAuthAccount` 分支用 `canonicalAccountModel`（supportedModels 拼写）作为 `ModelOverride`（`chain_driver.go`），不消费映射；Node `gpt/driver.ts` 同分支传 `modelMapping?.upstreamModel`。生产当前零可达（236 条启用映射全部在 `api_key` 账户、3 个 oauth 账户无任何启用映射），但一旦给 OAuth 账户启用映射，运行时不会改写、失败面为上游报错，而本批记账会按映射解析记录 —— 需另立任务对齐（改请求链、需独立验证）。
- `usage_semantic` 解析器覆盖不全：`profile_deepseek_anthropic_v1` / `profile_glm_coding_anthropic_v1`（ProviderCode=deepseek/glm + ProtocolCode=anthropic）现解析为 `openai`，Node 为 `anthropic`（`chain_usage_wiring.go` 既有缺口，本批把该解析器扩到成功路径后影响面扩大，另立任务）。
- 成功记账的 `requestSnapshot` / `responseSnapshot` 仍未写入（读取侧已按"使用记录详情退场"退场，写入侧文档要求保留，属独立任务）。
- `chainFinalizationUsage.RecordFailedUpstreamAttempt`（无生产调用方）未同步本批的 semantic / provider / tier / 归因补齐；若后续响应管线开始调用该方法，需先补齐再启用。
- `usageDispatchAdapter.RecordGatewayFailure` 未传 `model` / `stream`、丢弃 sink 提供的 `errorCode` / `failureAttribution` / `responseSnapshot`（网关策略失败记录的展示面较弱，另行任务）。
- 历史存量行（142k）不回溯改写：`upstream_model` 保持 NULL、`model_mapping_applied` 保持 0，前端按"历史记录无新字段保持无提示"契约不猜测。
