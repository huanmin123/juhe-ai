# BUG-0263：模型检测多密钥账户凭据白名单缺失

- 状态：已修复（2026-10-02，待发布）
- 定性：Go 实现与网关主链凭据契约偏差——`modelcheckowner` 的 api_key 型凭据白名单未纳入多密钥账户必需键，多密钥账户发起模型检测在凭据解密校验阶段被整体拒绝
- 发现方式：代码取证（`modelcheckowner/business_source.go` 对照主链 `accounts/credentials_normalize.go` / `gatewaydispatch/accountpreparation.go`）

## 1. 现象

多密钥账户（≥2 把 API Key）发起模型检测时，目标解析在凭据解密校验处报 unsupported field 错误，检测无法发起。单密钥账户不受影响。

## 2. 根因

网关主链的凭据写入契约（`backend-go/projects/gateway/internal/accounts/credentials_normalize.go` `normalizeAPIKeyAccountCredentials`）对 ≥2 把 key 的账户在凭据信封中写入：

- `api_key`（恒为首把 key，单密钥与多密钥都写）；
- `api_keys`（完整 key 数组）、`api_key_strategy`（策略）、`api_key_weights`（weighted_round_robin 时的权重）。

主链消费侧（`gatewaydispatch/accountpreparation.go` `accountApiKeyEntries`）以 `api_keys` 池优先、回落单 `api_key` 的契约消费这些键。

而 `modelcheckowner/business_source.go` 的 `validateAccountCredentialFields` 对 api_key 型凭据的白名单只有 `api_key`（+common 集）。该函数按"未知字段必须 fail-closed"的既定语义逐键校验，多密钥信封中的 `api_keys`/`api_key_strategy`/`api_key_weights` 任一键出现即触发 `J3b Business credential JSON field ... is unsupported`——多密钥账户必然携带这些键，因此必然被拒。

## 3. 修复

`modelcheckowner/business_source.go` 两处，语义与主链对齐：

1. **白名单放行**：`validateAccountCredentialFields` 的 api_key 分支增加 `api_keys`、`api_key_strategy`、`api_key_weights`（common 集与 oauth/google_oauth 分支不变；未知字段依旧拒绝）。
2. **token 提取回落**：`decryptAccountCredentialMaterial` 在 api_key 字段为空且存在 `api_keys` 时，解析数组取**第一把**非空 key——检测是确定性诊断请求，取首选 key 与主链 failover 策略首选一致，不引入运行态轮转（新增 `firstAPIKeyFromPool`）。池畸形（非数组/空数组/任一元素非字符串/全空白）返回明确中文错误（`J3b Business 多密钥账户凭据 api_keys 无效：…`），不静默回落到无凭据状态。

正常路径不受影响：normalize 写入的多密钥信封恒带首把 `api_key`，token 提取优先命中该字段；`api_keys` 回落仅覆盖缺失单 key 字段的信封形态。

## 4. 验证

- 单测 `TestAPIKeyCredentialAcceptsMultiKeyEnvelope`（`business_source_test.go`）钉死契约：多密钥信封（api_key+api_keys+strategy+weights）过白名单且提取首选 key；仅池信封取池内第一把；四类畸形池（非数组/空数组/元素非字符串/全空白）均报中文错误；单密钥行为不变；无 key 信封与未知字段保持既有 fail-closed。
- `go test ./internal/modelcheckowner/ -count=1` 全绿（60.0s，ok）。
- 未做生产/PG 集成验证（待随发布验证多密钥账户手动检测可发起）。
