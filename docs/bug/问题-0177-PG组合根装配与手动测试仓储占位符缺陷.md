## 问题概述

两个既有潜伏缺陷均只在 `DatabaseDriver=postgres` 模式下触发，此前无 PG 组合根测试所以未暴露：

1. **accountbalance PG store 无法装配**：`compose_account_balance_refresh.go` 的 PG 分支注入 `PostgresPool` 但未传 `PostgresURL`，而 `accountbalance.OpenStore` 的 postgres 分支**无条件**要求非空 `PostgresURL`（即使已注入连接池，URL 仅在 nil 池直连路径使用）。结果：PG 模式 `composeSystemAPI` 恒失败（`compose gateway system api: open account-balance gateway store: account-balance postgres 缺少连接 URL`），main.go PG 业务模式无法启动。
2. **手动账号测试仓储 SQL 占位符错误**：`manualtestrepo` 全部 20 个 SQL 执行点使用 SQLite 风格 `?` 占位符，pgx 不做 `?`→`$n` 转换；PG 词法把 `?` 当操作符 token，报错位置后移（实测 `cleanupExpired` 报 `ERROR: syntax error at or near "ORDER" (SQLSTATE 42601)`）。结果：PG 模式下队列启动维护失败并持续重试，任务生命周期（mark_running/complete/fail/cancel）全部失效。

## 复现步骤

1. 对真实 PG 临时子库执行 PG 模式 `composeSystemAPI`（或 owner 全栈启动），第 1 项缺陷在装配阶段直接报缺 URL。
2. 修复第 1 项后启动 PG 模式网关，观察 `账号测试队列启动维护失败` WARN 与 sweep 循环持续重试。

## 根因分析

- 第 1 项：`OpenStore` 的校验与真实依赖不一致——`PostgresURL` 只在无注入池时需要，却对注入池路径也无条件强制；call site 侧按"已注入池"组装自然缺失 URL。
- 第 2 项：仓储按 SQLite `?` 占位符编写并自带方言值适配（`instantParam`），但从未有占位符改写层；PG 路径自 Go 迁移以来从未被真实执行过。

## 修复方案

- `accountbalance/store.go`：`PostgresURL` 非空校验移入 `PostgresPool == nil` 的直连分支（与"无注入句柄时打开专属 pgx 池"的注释契约一致）；jobs 既同时传 URL 与池，行为不变。
- `manualtestrepo/repo.go`：新增 `bindSQL` 方法（postgres 方言下 `?`→`$n`，跳过字符串字面量），并在仓储出口统一包裹全部 SQL 执行点；SQLite 模式恒等返回，行为不变。
