# BUG-0361：切号并发槽预留未消费不归还，账户并发计数长期泄漏

- 级别：P2（并发额度被逐步蚕食；未直接造成请求失败，长期可打满单账户并发）
- 状态：v2026.11.13 先上线确定性收口与存量清理（commit 6eec2018b）；根治模型已随 v2026.11.13-2 上线（2026-11-13 00:45，commit b543edcf1，gateway+jobs 同批）；30 分钟观察通过，观察期至 2026-11-20
- 登记：docs/待办与阻塞事项.md #T206

## 现象

生产管理页账户 `https://sub.vcnovb.cn-ds`（`acc_7cc3ecb0ad47e8d2`，deepseek，`concurrency_limit=20`）长期显示 `5/20`；该账户 2026-11-12 21:12:10 最后一批 12 条 SSE 请求全部成功 finalized 后，再无任何请求（审计 count=0、调度日志无 `selectedAccountId`），但页面与 Redis 计数始终为 5。

Redis 取证（DB0，键 `juhe-ai:{prod:concurrency}:gateway-account-concurrency:account-concurrency:<accountID>`）：

| 账户 | total | 最后真实请求 | 之后是否仍有 selected | 历史 release 超时 |
| --- | ---: | --- | --- | ---: |
| `acc_7cc3ecb0ad47e8d2` | 5 | 2026-11-12 21:12:10 | 否 | 2 次（11-11 06:33/16:15） |
| `acc_c339f2160fa88c75` | 16 | 2026-11-12 18:35:43 | 否 | 4 次（11-12 10:49） |
| `acc_2996788e5727408d` | 10 | 2026-11-12 19:05:28 | 否 | 0 |
| `acc_86fc2656a0a2adbc` | 1 | 2026-11-12 18:56:48 | 否 | 0 |

控制组：活跃账户 `acc_d129043d668eed46` 在请求结束后计数正常归零并删除键，证明正常释放路径有效。目标账户 21:07-21:12 的 12 条请求全部串行（真实并发峰值 1）、无切号/重试，不是泄漏来源。

## 根因

### 1. 确定性缺口：未消费的切号预留不归还（本轮修复）

`chain_v1_loop.go` 每轮派发前把 `l.speedFirstCutoverReservation` 取出到局部 `dispatchReservation` 并置字段为 nil，再作为 `PreAcquiredConcurrency` 交给引擎。引擎只在选中账户与预留目标匹配时经 `TakeForAccount` 把槽转交本轮响应链释放。

若本轮候选窗口没有该目标（调度排除集、失败/不可用代理画像、本地抑制、切号冻结目标等），引擎不会 take；而循环开头已把字段置 nil，请求级 `defer releasePendingSpeedFirstReservation()` 无法兜底，局部变量随迭代结束被 GC——目标账户上已 +1 的并发槽永久无人归还。

生产泄漏账户 `acc_2996788e5727408d` / `acc_c339f2160fa88c75` / `acc_86fc2656a0a2adbc` 的 owner 均为 `sysacc_1777763935822_2461196e`——正是生产唯一 `speed_first` 调度偏好与唯一绑定 Key（`key_1782868624489_9baeb61f`）的 owner，与「每次切号轮次给目标账户漏 +1」的路径吻合。

### 2. Redis 释放超时（有日志，偶发）

`chain_dispatch.go` 的 Release 闭包以 `context.Background()` + 3s 调用 `ReleaseAccountConcurrency`；超时打 `account concurrency Redis release failed` WARN。全量网关日志（2026-10-15 起）共 11 次，其中目标账户 2 次（11-11 06:33:04、11-11 16:15:20，均 `context deadline exceeded`），每次泄漏 1 槽。无日志的静默缺口见下。

### 3. acquire 单次往返的 at-most-once 窗口（可观测性已补）

`AcquireAccountConcurrency` 以单次 `EVAL` 完成计数与 TTL 设置。Redis 侧可能已执行成功，但客户端因超时/断连只拿到 error；该路径不构造 Release 闭包（`chain_dispatch.go`），槽无法归还，且此前无任何日志。

### 4. 放大机制：泄漏值不会被 TTL 回收

acquire 脚本每次成功都 `PEXPIRE 6h`，release 不刷新 TTL；只要账户持续有流量，key 永不过期，任何一次 +N 泄漏都被永久固化，页面表现为「一直 5/16/10」。key 只有在账户完全空闲 6 小时后才整体过期清零。这解释了为何 21:12 后 0 请求仍固定 5：5 是跨日累积的净泄漏，最后一批请求只是把 TTL 续到了 21:12。

## 修复

1. `chain_v1_speedfirst.go` 新增 `releaseUnconsumedCutoverReservation`：`Consumed()==false` 时 `Release()`（幂等）；`chain_v1_loop.go` 在每轮 `FetchFirstAvailableUpstream` 返回后立即调用。take 成功（`Consumed()==true`）时不提前释放，槽仍由 `dispatched.ReleaseConcurrency` 在响应链结束释放。
2. `chain_dispatch.go` acquire 返回 error 时补 WARN（`slot may be leaked until TTL`），把此前静默的 at-most-once 窗口纳入可观测面。
3. 回归测试 `chain_v1_speedfirst_release_test.go`：未 take 的预留被确定性释放且幂等；take 成功的预留不被提前释放、由响应链释放一次。

验证：`go test ./cmd/juhe-ai-gateway -run TestReleaseUnconsumedCutoverReservation`、`./internal/gatewayhotquality`、`./internal/gatewaydispatch -run 'Concurrency|Cutover|Reservation|Release'`、`./cmd/juhe-ai-gateway -run 'SpeedFirst|Cutover|Concurrency|AccountConcurrency'` 全绿；发布门禁 `go test ./cmd/juhe-ai-gateway -count=1 -timeout 30m` 通过。

## 根治（2026-11-13 实施，待统一发布）

单点收口只能消除「未消费预留」这一条路径；release 超时、acquire `EVAL` at-most-once、进程终止三类窗口仍依赖 6h key TTL，而 TTL 会被持续流量续期。按用户要求改为根治模型，随 gateway+jobs 同批上线：

1. **槽集合替代计数器**：Redis 并发槽改为每账户 `:slots`（总）与 `:slots:<lane>` 两个 ZSET；member = `<lane>:<token>`、score = 租约到期毫秒。当前并发 = 清理过期成员后的 `ZCARD`，释放 = 幂等 `ZREM`。不存在「+1/-1 漂移」。
2. **30m 租约 + 心跳**：槽租约 30 分钟覆盖单请求墙钟上限；realtime WS 在 20s ping 周期调用 `slot.Refresh` 续租；进程崩溃、release RPC 超时、acquire 结果不确定等全部收敛为租约到期自动回收。键级 TTL（租约 + 5m 宽限）只回收空闲账户。
3. **RPM 分离**：RPM 仍在独立 HASH（`rpm_bucket`/`rpm_count`，TTL 120s）；acquire 清理旧实现的 `total/text/image/realtime` 并发字段。
4. **jobs 同批读面**：`OverlayRedisStore.LoadSnapshots` 与 `OverlayConcurrencySource` 改为清理过期 + `ZCARD`，键 PTTL 作为 `next_reconcile_at`；gateway 与 jobs 必须同批上线，否则页面并发读数会读空。
5. **回归**：新增槽租约过期、refresh 续租/不复活、lane 隔离三组 miniredis 用例；既有 acquire/release/RPM/投影用例全部迁移到 ZSET 断言；真实 dev Redis 外部用例通过；gateway/jobs 定向包与 `cmd/juhe-ai-gateway` 全量测试通过。
6. **回滚边界**：旧二进制只读旧 HASH `total`，新代码不再维护它；回滚窗口内并发计数从头累积（短期可能放宽硬并发），RPM 不受影响。gateway 与 jobs 必须同批发布/回滚，禁止新旧二进制混跑（见《部署指南》§9.5）。
7. **复审处置（2026-11-13）**：独立复审 PASS_WITH_ISSUES，无 blocker；major「30m 租约不覆盖图片 attempt 默认 1h / 无总时限 SSE」已改为请求级自动续租（acquire 后每 20m 续租，最多 12 次≈4h；realtime 另由 WS ping 续租），超 4h 已提交 SSE 作为已知边界登记；refresh 增加 score 过期校验（过期槽不复活）、失败/槽缺失 WARN；拒绝路径 RPM 键补 TTL；空 lane 读语义与陈旧注释/文档同步。
