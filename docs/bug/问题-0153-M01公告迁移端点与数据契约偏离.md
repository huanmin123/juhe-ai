## 问题概述

- 现象：M01 提交 `81b16f8da` 新增了 `backend-go/projects/gateway/internal/announcements`，但该实现没有接入 gateway，且与仍在使用的 Node/前端公告契约存在多处可观察偏差。
- 期望：Go 接管前应完整覆盖 Node 的公开列表、公开详情、已读、管理员 CRUD、校验、revision、时间字段、操作日志和失效副作用；所有前端请求路径和返回投影保持可用。
- 实际：
  1. Node/前端使用 `/announcements/public`、`/announcements/public/:id`、`/announcements/public/read`；Go 只注册 `/my-announcements` 和 `/my-announcements/read`，没有公开详情。
  2. Go 管理列表只返回 `id/title/level/status/publishedAt/createdAt/updatedAt/editVersion`，缺少前端编辑列表契约需要的 `contentPreview/contentTruncated/updatedByName/revision`。
  3. `Store.Create` 的 SQL 只有 10 个占位符，参数却把两个 `status == "published"` 和两个 `revision` 一并传入；按列顺序会把布尔值写入 `published_at`、`created_at`，草稿的 `published_at` 也不再是 NULL。
  4. Go `PATCH` 不读取旧正文，对任何 `content` 输入都执行更新并递增 revision；Node 对相同正文视为 no-op。
  5. Go 已读和 PATCH/CREATE 校验放宽：不拒绝未知字段、空/null ID、空 PATCH、超长字段和非字符串字段；Node Zod schema 对这些情况返回 400。
  6. 操作日志没有对齐 Node 的可见范围、明细级别和完整 changes；M01 包也没有接入公告公开数据的缓存/页面失效副作用。
- 影响范围：若按现状翻转，前端公告读取会 404 或拿到不完整投影，创建/草稿时间事实会污染，幂等和 revision 冲突语义会漂移，审计记录及缓存可能与页面事实不一致。当前 Node 挂载尚未删除，因此这些偏差尚未被 Go 切换放大。

## 根因分析

- 表象：M01 提交说明写有“全路由”和测试通过，包内生命周期测试也能通过。
- 真实根因：实现只覆盖了自定义 `/my-announcements` 测试面，未以 Node 路由/前端类型作为唯一外部契约；新增 `internal/announcements` 与已有 `internal/business/announcements` 重复，且没有生产入口、owner 登记或 Node 归档闭环。
- 为什么会发生：测试夹具手工挂载 `kernel.Handler`，没有经过 `main.go` 和真实路径；断言集中在状态流转，没有覆盖投影字段、时间列、严格校验、日志副作用和前端调用方。

## 修复方案

- 修改点：先冻结 Node/前端端点矩阵和 golden，再收敛到一个公告 service/store；修正 SQL 列值、公开路径/详情、投影、字段校验、no-op revision、操作日志和缓存失效；最后在真实 gateway listener 接线后做双存储、权限、错误和回放验证。
- 行为影响：修复后 Go 才能替换 Node 公告 owner；在此之前不得摘除 Node 挂载或宣称 M01 archived。
- 发布异常处理：任何 golden 或前端端点不一致都保持 Node owner，禁止通过 Node↔Go 跨进程调用临时补洞。

### 2026-09-05：公告公开列表 limit 校验被 Go 静默回退/截断

- Node 基线：`GET /announcements/public` 通过 `publicListQuerySchema` 将 `limit` 强制转换为整数并要求 1–30；`0`、负数、非数字、浮点/非整数或大于 30 均在调用仓储前返回 400，合法值才传给 `listPublicAnnouncementsAsync`（`backend/src/modules/announcements/announcements.routes.ts`、`backend/src/storage/announcements.repository.ts`）。
- Go 实现：历史 `backend-go/projects/gateway/internal/announcements/routes.go` 使用 `parseIntOr(raw, 0)`，对空、非法和非正值直接得到 0；`Store.ListPublic` 再把 `limit<=0` 默认成 30，并把大于 30 的值截断为 30，没有返回参数错误。
- 结果偏差：`limit=0`、`limit=-1`、`limit=abc`、`limit=31` 在 Node 均为 400，Go 均返回 200；`limit=31` 虽实际查询 30 条，客户端仍会误以为请求被接受，`limit=1e1` 也会在 Go 回退到 30 而不是 Node 的 10 条。
- 结论：这是已提交 M01 公告公开读链的确定参数校验与结果边界偏差，当前仅记录，未修改 Go 代码。

### 2026-09-05：公告已读接口放宽数组/元素/未知字段校验

- Node 基线：`POST /announcements/public/read` 使用严格的 `readAnnouncementsSchema`：body 必须是只含 `announcementIds` 的对象，字段必须为字符串数组（最多 30 个），每个 ID trim 后不能为空；缺失、`null`、空字符串元素或未知字段均在写入前返回 400。空数组本身合法并返回 `count=0`（`backend/src/modules/announcements/announcements.routes.ts`、`backend/src/storage/announcements.repository.ts`）。
- Go 实现：历史 `backend-go/projects/gateway/internal/announcements/routes.go` 只检查数组长度不超过 30；JSON 缺失或 `null` 会解码为 nil 并继续调用 `Store.MarkRead`，未知字段被忽略。`Store.MarkRead` 又会 trim、丢弃空 ID 并在无有效 ID 时返回成功的 `readAt/count=0`。
- 结果偏差：`{}`、`{"announcementIds":null}`、`{"announcementIds":[""]}` 或带未知字段的请求在 Node 为 400，Go 返回 200 并可能不写任何已读记录；调用方无法据状态码区分参数错误与合法空数组。
- 结论：这是已提交 M01 公告已读写链的确定输入校验与错误状态偏差，当前仅记录，未修改 Go 代码。
- 后续建议：先修复并回放 Node/前端 golden，再重新评审，之后再进入 Node 物理归档和 owner 状态收口。
