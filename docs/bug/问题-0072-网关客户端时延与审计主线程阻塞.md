# BUG-0072 网关客户端时延与审计主线程阻塞

## 基本信息

- 编号：`BUG-0072`
- 状态：已发布并验证
- 严重程度：P1
- 发现时间：2026-07-14
- 发现方式：用户反馈 + 生产运行态采样 + 代码链路复查
- 模块：后端 / 网关 / 原始审计 / 使用记录 / 前端 / 部署
- 关联计划：`PLAN-0096`
- 关联 bug：`BUG-0012`、`BUG-0013`、`BUG-0022`

## 问题概述

- 现象：原始审计页面把审计收尾时间显示成“返回客户端”；响应写出后仍有请求排队，生产事件循环和内存会在大审计期间明显抬升。
- 期望：客户端完成、账户并发释放、使用记录耗时和后台审计完成各自使用正确时间点；大正文哈希、摘要、base64 和 JSON 编码不阻塞 server 主线程。
- 实际：审计 `ended_at/duration_ms` 包含响应后的状态写入和审计序列化，账户并发槽到整个 handler `finally` 才释放；Redis Stream 编码在 server 同步执行。
- 影响范围：流式和非流式网关请求、使用记录总耗时、原始审计列表/详情、账户并发、发布重启期间在途审计。

## 生产证据

- 生产采样中 `JSON.stringify` 是 server 事件循环热点之一；进程 RSS 约 564MB，观察峰值约 760MB。
- 抽样的 105 条审计中有 37 条正文超过 1MB，单条最大约 6.72MB，单请求最多 26 个 payload；请求正文样本达到约 3.17MB 和 14.08MB。
- 样本没有支持“Redis 内存上限是首要根因”的证据。直接提高 `maxmemory` 只能延后症状，不能消除 server 主线程的哈希、base64 与 JSON 放大。

## 根因分析

1. `audit_logs.ended_at/duration_ms` 表示审计最终固化，不是 HTTP `finish/close`，页面标签错误。
2. 使用记录在后置副作用之后读取 `Date.now()`，会把客户端已经收完响应后的时间计入总耗时。
3. 账户并发槽和请求体在途 lease 的释放边界晚于 HTTP 完成，后置副作用会压住后续请求。
4. server 直接对大 Buffer 做摘要、SHA-256、base64 和 Redis JSON 编码，形成同步 CPU 与瞬时内存放大。
5. 原 supervisor 收到 `SIGTERM` 后直接 `process.exit`，transport 队列中的审计没有有限排空机会。
6. 审计捕获在初始 preflight 之前登记，但主 handler 的 `try/catch` 从 preflight 之后才开始；preflight 抛错时没有 finalize/cancel，活动计数会永久泄漏。
7. 错误响应后的 usage 收尾是裸 `Promise`，虽然不阻塞响应，但 server 收到紧随响应的 `SIGTERM` 时无法看见或等待该任务。

## 修复方案

- 请求开始即注册共享 HTTP 完成观察器；审计写入 `http_completed_at/http_duration_ms`，使用记录也复用同一次完成时间。
- 账户并发槽与请求体 lease 在响应 `finish/close` 时幂等释放；后台状态和审计收尾继续执行但不占并发。
- server 对估算超过 256KB 的审计使用最多 2 个 worker 的有界 FIFO transport：单条输入最多 64MB、总预算 128MB、活跃预算 72MB、单任务超时 60 秒。
- transport 以 codec/base64 后字符串的实际 UTF-8 字节数执行 `4MiB` 硬校验；成功正文超过 512KB、问题链路正文超过 2MB，或多正文聚合编码将越界时，转为 `summary_only`，保留原始大小、SHA-256、前后各 256KB 与 JSON 结构摘要，不再退化为 `hash_only`。
- `/audit-logs/runtime` 暴露 transport 活跃、排队、字节、完成、失败、拒绝和待投递计数，失败/拒绝触发中文风险提示。
- server 统一接管退出信号：停止接流量，有限等待活动捕获、transport、server 投递和 ingest 审计队列，再停止 worker 与 DB service；超时必须记录剩余运行态。
- 捕获上下文增加幂等 `cancel` 和唯一活动计数释放点；初始 preflight 抛错或未产出上下文时取消，已经请求 finalize 时迟到 cancel 不得抢先丢弃审计。
- 所有错误响应的 finish 后 usage 任务进入统一 pending registry；server 关闭 HTTP 后先有限等待该 registry，再排空审计链路，未排空告警同时输出 pending 数。

## 结构同步前置

项目不在运行时做旧结构兼容。发布现有 PostgreSQL 数据库前必须离线执行并复核：

```sql
ALTER TABLE juhe_dataset.audit_logs ADD COLUMN IF NOT EXISTS http_completed_at TEXT;
ALTER TABLE juhe_dataset.audit_logs ADD COLUMN IF NOT EXISTS http_duration_ms INTEGER;
```

现有 SQLite 数据集库若继续使用，应先通过 `PRAGMA table_info(audit_logs);` 确认列不存在，再在停机窗口各执行一次：

```sql
ALTER TABLE audit_logs ADD COLUMN http_completed_at TEXT;
ALTER TABLE audit_logs ADD COLUMN http_duration_ms INTEGER;
```

未先同步结构会导致新版本审计 INSERT 失败并造成 Redis Stream 积压，因此结构检查是上线硬前置，不是可选回滚后补项。

## 下次遇到

- 先把 `HTTP finish`、上游完成、使用记录落点、审计完成和 worker 落库五个时间点分开，不从页面标签反推真实链路。
- 同时看 server event-loop、transport 运行态、Redis Stream lag/pending 和进程 RSS；不能只看 Redis `used_memory`。
- 大审计问题优先查同步 `JSON.stringify`、base64、hash 和 Buffer 复制，再判断 Redis 容量；预算必须检查最终 codec 字节，不能拿原始 Buffer 大小替代；只有持续 backlog 与真实内存压力都指向 Redis 时才评估扩容。
- 发布结构变更前先检查目标表列，再启动新代码；首批审计写入和运行态计数必须纳入 smoke。
- 审计活动计数要覆盖 preflight 抛错、返回空上下文、正常 finalize 和客户端中断；新增早退点必须明确 finalize 或 cancel，不能依赖 HTTP close 自动猜测。
- 响应后任务只做到 fire-and-forget 不等于可安全退出；必须登记 pending、提供有界等待和超时运行态。
