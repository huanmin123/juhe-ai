# BUG-0330 供应商协议档案退役导致添加账户表单空白

## 基本信息

- 编号：BUG-0330
- 状态：待验证（本机修复完成，待随下次发布上线）
- 严重程度：P1
- 发现时间：2026-10-22
- 发现方式：用户反馈（生产截图）
- 模块：前端（根因在后端供应商读面契约变更，前端未同步迁移）
- 关联计划：无
- 关联 bug：无
- 责任人：待定

## 问题概述

- 现象：生产环境「添加账户」弹窗中，点选供应商（如 DeepSeek）后，弹窗只剩供应商摘要行（名称 + 「更换」按钮）与底部按钮；账户类型选择器、API Key 输入、Base URL 等凭证区全部消失，「创建」按钮保持禁用。
- 期望：点选供应商后展示账户类型（DeepSeek 为 API Key）与完整凭证表单，可正常创建账户。
- 实际：表单主体为空，无法创建任何账户。
- 影响范围：生产环境全部对话域供应商的账户新建；编辑/克隆路径不受影响（编辑不走供应商卡片墙）。

## 复现步骤

1. 登录生产管理端，进入「我的账户 / 对话」页面。
2. 点击「添加账户」，在供应商卡片墙选择 DeepSeek。
3. 观察弹窗：步骤 1「类型与凭证」下只显示 DeepSeek 摘要行，凭证区空白，无法提交。

## 环境信息

- 分支 / 版本：生产前端 buildId `34d80ffb8`（与 HEAD 的 `frontend/src` 无差异）；后端 gateway 同批发布。
- 数据状态：`vendors` 表存在 deepseek 等九家供应商，`provider_protocol_profiles` 已随结构重建删除。
- 浏览器 / 系统 / Node 版本：不适用。
- 是否稳定复现：是（所有对话域供应商，100%）。

## 根因分析

- 表象：`AccountEditModal` 的 `#acct-sec-credential` 区域渲染为空，`AccountApiKeySection` 与 `AccountOAuthSection` 的 `v-if` 均为假；`AccountFormSelector` 的账户类型分段控件也不渲染。
- 真实根因：后端供应商读面在 B4 收尾（`3b4dd5cb9`，2026-10-19）随 `provider_protocol_profiles` 表退役，`GET /providers/{code}`、`/providers`、`/providers/definitions` 统一由 `providers.Store` 的 vendors 投影返回空形状：`protocolProfiles: []`、`accountTypes: []`、`defaultProtocolProfileId: ""`（`backend-go/projects/gateway/internal/providers/store.go` 的 `scanVendorDefinition`）。前端 `mergeAccountProviderDefinitions` 在用户选择供应商并异步加载详情后，用服务端 definition 整体覆盖 `FALLBACK_PROVIDERS` 中的内置定义，把内置的协议档案与账户类型一并抹掉；`form.type` / `form.providerProtocolProfileId` 变为空，`hasAccountType`、`isApiKeyForm` 随之为假，凭证区整块不渲染。
- 为什么会发生：B4 批次的注释只保留了 DTO 键名并假设「前端未迁移也不受影响」，但前端账户表单仍以 `protocolProfiles` 驱动账户类型与凭证组件选择；合并逻辑又基于「服务端详情一定携带完整档案」的旧契约。生产在 2026-10-22 结构重建后首次全量运行该构建，问题暴露。

## 修复方案

- 修改点：
  - `frontend/src/views/accounts/useAccountEditForm.ts` 新增 `mergeProviderDefinition`：服务端 definition 的 `protocolProfiles` 为空时，保留内置定义的 `protocolProfiles`、`accountTypes`、`defaultProtocolProfileId`、`protocolCode`、`protocolVersion`、`baseUrl`、`capabilities`，仅用服务端覆盖身份、描述、启用状态和非空默认模型；服务端返回完整档案（旧库或前端迁移完成后）仍以服务端为准。
  - `mergeAccountProviderDefinitions` 改为分别维护内置回退与已加载定义索引，避免服务端空形状覆盖本地数据。
  - `frontend/src/scripts/regression/account-provider-definitions-lazy-loading-regression.ts` 更新静态断言并新增行为断言：空形状 DeepSeek 定义合并后仍解析出 `api_key` 与 `profile_deepseek_openai_v1`；服务端完整档案仍优先。
- 行为影响：恢复 B4 前的供应商档案可用性；对话域新建账户流程恢复。媒体域（minimax / volcengine / qwen）因 `FALLBACK_PROVIDERS` 本就不含这三家，仍受同一读面退役影响，已登记为 T47。
- 发布异常处理：前端产物需随下次发布重建（`deploy.sh` 会自动检测 `frontend/` 差异并构建）；回滚时回退该提交并重新构建前端即可。

## 下次遇到

- 先查什么：`GET /providers/{code}` 实际响应中 `protocolProfiles` / `accountTypes` / `defaultProtocolProfileId` 是否为空；`FALLBACK_PROVIDERS` 是否包含当前供应商码。
- 重点看什么：`mergeAccountProviderDefinitions` 是否让服务端空形状覆盖了本地协议档案；`hasAccountType` 依赖的 `providerProtocolProfileId` 是否为空。
- 如何避免误判：不要只根据「供应商名称/图标正常显示」判断定义完整——摘要行只依赖 `code`/`name`/`enabled`，凭证区依赖 `protocolProfiles` 与 `accountTypes`。

## 完成总结

- 完成时间：2026-10-22（本机修复）
- 结论：根因是后端供应商读面按设计退役协议档案后，前端仍以服务端详情覆盖内置档案；已在前端合并层保留内置协议形状，回归脚本锁定「空形状不得清空账户类型」。
- 后续建议：前端账户表单迁移到连接预设新契约（[供应商与上游协议面重构设计](../functions/供应商与上游协议面重构设计.md) §9.3）时，删除这层兼容合并，改为直接消费 registry；媒体域三家供应商的本地回退补齐见 T47。
