# BUG-0069 余额临时失败重试等待过长

- 编号：BUG-0069
- 状态：待生产验证

- 责任人：AI

## 问题概述

- 现象：账户列表长期显示“待重试（2/3）”，用户观察不到后续第三次查询。
- 期望：临时失败只跳过本轮，按账户配置的正常余额刷新周期继续查询；连续第 3 次失败才显示真正失败。
- 实际：临时失败使用固定 15、30、60 分钟退避，第二次失败后需要等待 30 分钟，第三次及后续失败需要等待 60 分钟。
- 影响范围：所有开启余额查询且遇到网络、超时、`408/429/5xx` 或无效 JSON 等临时错误的单 API Key 账户。

## 生产证据

- 生产 `ops-worker`、主服务和 DB service 均在运行，余额任务没有停止。
- 生产账户配置 `intervalMinutes=5`，第三次失败后 `balance_query_next_refresh_at` 被写为 `lastAttemptAt + 60 分钟`。
- 同批多个启用账户均表现为连续失败计数已到 3、下一次刷新被延后 60 分钟，证明问题来自统一状态机而不是单账户数据或 worker 丢任务。

## 根因分析

- 表象：页面状态停在 2/3。
- 真实根因：`account-balance-query.service.ts` 使用 `transientRetryDelayMs()` 把失败次数映射为固定 15、30、60 分钟，没有使用账户自身 `balance_query_config_json.intervalMinutes`。
- 为什么会发生：BUG-0066 的能力暂停修复为了降低不支持账户的无效轮询，同时给临时错误引入了长退避；但确定性不支持已经会暂停调度，临时错误再使用长退避会违背“等下一次正常查询”的产品语义，并让 1 到 10 分钟的用户刷新配置失效。

## 修复方案

- 临时失败的 `next_refresh_at` 统一使用当前账户 `intervalMinutes`。
- 连续失败计数和展示语义保持不变：第 1、2 次保留旧金额或显示待重试，第 3 次才显示失败，计数封顶为 3，任意成功清零。
- 确定性不支持仍把 `next_refresh_at` 置空并暂停；人工刷新仍不累计后台失败次数。
- 不新增字段、不重建非业务数据库、不清空 Redis。

## 发布与恢复

- 普通代码发布使用 `rebuildNonBusiness=0 resetRedis=0`。
- 发布后把当前 `status=failed/pending` 且余额查询开启的账户 `balance_query_next_refresh_at` 定向调整为立即到期，让新代码接管；不修改失败计数和快照。
- 如果发布异常，回滚到上一 release；不要回滚业务数据或删除余额快照。

## 下次遇到

- 页面“待重试”长期不动时，先同时检查 snapshot 的 `lastAttemptAt`、账户 `balance_query_next_refresh_at` 和 worker scheduler 状态。
- 用户配置了刷新周期时，临时失败重试不能另建一套更长周期覆盖该配置，除非产品明确暴露并说明独立退避规则。
- 确定性不支持和临时错误要分别治理：前者暂停，后者按正常周期继续并使用连续失败阈值。
