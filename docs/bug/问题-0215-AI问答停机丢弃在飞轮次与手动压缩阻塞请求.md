# BUG-0215：AI 问答停机直接丢弃在飞轮次，手动压缩请求内同步等待执行完成

- 编号：BUG-0215
- 状态：已修复（待发布验证）
- 发现：2026-09-28，批次2 可靠性复审：SIGTERM 停机语义与压缩请求生命周期语义双双违背契约

## 现象

- 停机丢弃在飞轮次：正常 SIGTERM 停机时聊天生成 hub 不做任何排空——组合根注释宣称 "chat generation hub drain first"，但排空调用从未接进 shutdowns，在飞轮次被直接丢弃，客户端只看到连接中断，轮次终态依赖崩溃恢复事后收口。
- 手动压缩阻塞请求：`POST /conversations/:id/context/compactions` 在压缩 claim 受理后继续在请求内同步等待压缩执行完成才返回；压缩耗时与请求连接生命周期耦合——连接断开可能中断已受理的压缩，长压缩让请求长时间悬挂。

## 根因

- 排空未接线：`GenerationHub.Shutdown` 存在但没有任何调用点注册进组合根 `composed.shutdowns`；shutdowns 按 LIFO 执行，链关闭先于（本不存在的）排空，"hub 排空先于链关闭"只是注释里的宣称。
- 压缩执行与请求 context 耦合：claim 成功后压缩主体沿请求派生 context 执行、结果在 handler 内同步等待，违背"受理与执行分离"的后台任务语义。

## 修复

- 把 `hub.Shutdown(8s)` 注册进组合根 shutdowns：shutdowns 为 LIFO（后注册先执行），该注册晚于 chainShutdown / chainServices.Close，停机时 hub 排空先于网关链关闭——在飞轮次被 Abort 并有界等待（8 秒）落终态，收尾派发仍可使用在途链；窗口内未落终态的轮次由既有崩溃恢复阈值收口。
- 压缩 claim 受理后立即返回 `202`（payload status 为 `accepted` / `already_running`），压缩主体在后台执行、执行 context 与请求连接脱钩；客户端断开不中止已受理的压缩，完成事实以会话上下文状态与后续消息为准。

## 验收

- 发送中执行 SIGTERM：在飞轮次先被 Abort，8 秒内有界等待落 `canceled` 类终态（而非静默消失）；排空发生在网关链关闭之前。
- 触发手动压缩：HTTP 响应立即返回 202（`accepted` 或 `already_running`），压缩继续后台执行到终态；受理后断开客户端连接不影响压缩完成与 checkpoint 安装。

## 教训

- 停机契约不能只存在于注释：宣称 "drain first" 的顺序必须由注册位置（LIFO 语义）实际保证，没有调用点的 Shutdown 等于没有排空。
- 后台任务的受理与执行必须分离：claim 语义（受理即应答）与执行语义（脱钩后台）混在同一请求生命周期里，连接抖动就会变成任务丢失。
