## 问题概述

- 现象：M05 Go groups 仅实现基础 CRUD 和 owner 视角，Node/前端仍使用 options、授权 options、account/route-strategy options、edit-basic、return-authorization 等端点。
- 期望：分组完整迁移应覆盖所有端点、authorized 视角、统计投影、分页和严格校验，并保持删除审计与缓存失效副作用。
- 实际：
  1. Go 缺少上述端点及 `resource_authorizations` 驱动的 authorized 视角。
  2. Go 列表统计返回全零，Node 返回 `group_account_stats`、today/total usage 和 current concurrency。
  3. Node `pageSize` 最大 500 且非正数归一为 1；Go 最大 100，非正数回退 20，前端默认 500 会直接产生不同结果。
  4. Go 将 JSON `null` 可选字段按未提供处理，Node schema 对 nullable 不接受并返回 400。
  5. Go 删除日志缺少 Node 的受影响策略 targets/metadata；缓存失效差异已复核为非缺陷（历史 Go 分组读路径直接查库，未发现对应 group lookup/account-id 本地缓存）。
- 分页约束切片取证：同一迁移父提交中的 Node `normalizeGroupListOptions` 将整数 `pageSize` 归一为 `Math.min(500, Math.max(1, pageSize))`，未提供时默认 50；历史 Go `ListPage` 将 `pageSize < 1` 回退为 20，并将上限截为 100。故 `pageSize=0`、`pageSize=501` 及前端批量 500 请求会得到不同页大小、`hasMore` 和后续 offset，属于可观察结果偏离。
- 可选字段 null 校验切片取证：Node `groupSchema`/`groupPatchSchema` 的 `description`、`enabled`、`groupType`、`schedulingPolicy` 均为 optional 但非 nullable，键值为 `null` 时统一返回 400。历史 Go `createBody`/`patchBody` 对这些键的 `nil` 值直接跳过；创建请求可被错误接受，PATCH 若同时带合法字段则会忽略 null 并成功写入，改变 Node 的整包拒绝结果。
- 调度策略子字段校验切片取证：Node 路由 schema 对 `schedulingPolicy` 的五个可写字段使用 `z.number().int().min/max` 或 enum，子字段传 `null`、浮点、越界值或非法 overflow mode 会 400。历史 Go `schedulingPolicyJSON` 遇到数值子字段为 `nil` 时跳过并保留默认值；因此例如 `{"schedulingPolicy":{"defaultSoftConcurrency":null}}` 会被 Go 接受并写入默认策略，而 Node 会拒绝整次请求。其整数/范围/enum 校验本身已在 Go 实现，但 null 子值仍未对齐。
- 调度策略全局上限切片取证：历史 Node `DEFAULT_HIGH_CONCURRENCY_GROUP_SCHEDULING_POLICY` 的 `defaultSoftConcurrency`、`maxQueueSize` 与 `perApiKeyQueueLimit` 均实时读取 `runtimeConfig.concurrency.globalMax`；该值由 `JUHE_AI_CONCURRENCY_GLOBAL_MAX` 配置，默认 5000、允许范围 1–50000。历史 Go `backend-go/projects/gateway/internal/groups/scheduling.go` 仅定义常量 `defaultGlobalConcurrencyMax = 5000`，在创建/更新高并发分组时始终写入常量，且同一迁移提交的 Go 树中没有对应运行时配置读取。因此当部署将 `JUHE_AI_CONCURRENCY_GLOBAL_MAX` 设为非 5000 时，Go 的默认调度策略、队列容量和接口回显会与 Node 偏离；这是可直接观察的配置结果差异。
- 调度策略存储完整性切片取证：历史 Node `parseGroupSchedulingPolicyJson` 对高并发分组要求 `scheduling_policy_json` 为非空字符串，且必须包含完整存储字段；回归脚本将该列置为 `NULL` 或仅保留 `defaultSoftConcurrency` 时，`findGroupSummary` 均明确抛出错误，避免把损坏策略伪装成可用默认值。历史 Go `parseSchedulingPolicy` 对缺失、空值、非法 JSON 直接返回 `nil`，对缺字段 JSON 原样返回部分对象，列表/详情仍以成功响应继续返回。因而同一存储不变量被破坏时，Go 会静默成功而 Node 失败，可能让运行态继续使用不完整策略，属于错误处理和可观察结果偏离。
- 授权视角列表取证：Node `queryGroupRowsForAccess` 在非 `manageableOnly` 读取时，会将当前账户拥有的分组与 `resource_authorizations` 中授予当前账户的分组 `UNION ALL`，并返回 `accessType=authorized`、授权状态/过期时间/限额及授权设置覆盖后的字段；`findGroupRowForAccess` 对单个分组也沿用该授权查询。历史 Go `ownerClause`/`ListPage`/`FindDetail` 只按 `groups.system_account_id` 过滤并固定构造 owner 视角，未查询 `resource_authorizations`。因此被授权但非所有者的用户在 Go `/my-groups` 列表中看不到该分组，访问 `/my-groups/:id` 也会得到 404，授权状态和权限结果均丢失。
- 统计投影取证：Node `buildGroupListItems`/`buildGroupSummaries` 从 `juhe_stats.group_account_stats` 读取 total/available/active/disabled/error/rateLimited/concurrencyLimit，并补充 usage（today/total）与运行态 currentConcurrency；列表路由还通过 `hydrateGroupListPage` 返回 `generatedAt` 和最新快照。历史 Go `newListItem` 将整个 `AccountStats` 固定为零值，`FindDetail` 的 `Detail` 结构甚至没有 `accountStats` 字段，路由也不返回 `generatedAt`。前端分组表直接用 available/total、currentConcurrency 和 todayUsage 展示状态，因此有账号或实际用量的分组在 Go 页面会显示为“未绑定/0 用量”，详情响应也缺少 Node 必有的统计对象。
- 成员投影过滤切片取证：Node `loadGroupAccountIdsByGroupIds`/成员计数查询要求绑定启用、账号未删除，且满足“账号所有者等于分组所有者”或绑定的 `resource_authorizations.status` 为 active/paused/expired；因此 revoked/returned 授权账号和无有效授权的跨所有者绑定不会进入 `accountIds`/`memberCount`。历史 Go `memberCounts` 与 `groupAccountIDs` 仅 JOIN `accounts` 并检查 `group_accounts.enabled = 1`、`accounts.deleted_at IS NULL`，未 JOIN `resource_authorizations` 或校验账号/分组所有者。相同数据库下 Go 会继续展示已撤销/归还或不具有效授权的绑定，成员数和账号列表均可能偏大。
- `GET /groups/options` 端点取证：Node 路由要求 `purpose=select|account`，支持 `ids`、`keyword`、`providerCode`、`limit`、`manageableOnly`、`preferDefault`，并调用授权感知的 `listGroupOptionsAsync` 返回含 owner/authorized、权限与授权字段的选项摘要；前端 `groupsApi.options` 与 `myGroupsApi.options` 均直接调用该路径。历史 Go groups 路由只注册列表、详情和 CRUD，没有 `/groups/options` 或 `/my-groups/options`，请求只能落到未实现的路径（或被 `/{id}` 详情模式解释），无法得到 Node 的选项数据。
- `GET /groups/authorization-options` 端点取证：Node 读取同一授权感知的分组选项，并按 owner/authorized 状态计算 `canAuthorize`；前端授权编辑器通过 `groupsApi.authorizationOptions`/`myGroupsApi.authorizationOptions` 加载和补齐当前选中的分组。历史 Go 未注册 admin/self 两条路径，也没有 `canAuthorize` 计算或等价响应，因此授权表单无法加载分组候选，已保存的分组选择在选项补齐时也会请求失败。
- `GET /groups/account-options` 端点取证：Node 返回 `AccountGroupOptionSummary`，除分组/授权字段外还带 `accountIds`；所有者视角返回该分组的账号 ID，授权视角明确返回空数组以避免泄露所有者账号。前端 `groupsApi.accountOptions` 与 `myGroupsApi.accountOptions` 直接依赖此结果。历史 Go 未注册 admin/self 两条路径，既不能提供账号绑定候选，也不能执行授权视角的账号隐藏规则。
- `GET /groups/route-strategy-options` 端点取证：Node 对 admin/self 均提供路径，支持 `ids`、`keyword`、`providerCode`、`limit`，并将授权设置后的启用状态映射为 `{id,name,providerCode,enabled}`；路由策略选择器使用该结果绑定分组。历史 Go 未注册两条 route-strategy options 路径，无法返回候选或反映授权覆盖后的 `enabled` 状态。
- `GET /groups/:id/edit-basic` 端点取证：Node 与 `my-groups` 对应路径返回编辑表单所需的 `name/providerCode/description/enabled/groupType/schedulingPolicy/updatedAt`；非所有者授权视角还会合并 `group_authorization_settings` 的 enabled、groupType、schedulingPolicy 和更新时间覆盖。前端 `useScopedDomainApi` 在编辑页直接调用该专用接口。历史 Go 未注册两套 `edit-basic` 路径，`FindDetail` 不能替代该响应（字段多且包含成员/访问详情），授权用户也无法获得自己的覆盖配置。
- `POST /groups/:id/return-authorization` 端点取证：Node 与 `my-groups` 对应路径通过 `returnGroupAuthorizationForGranteeAsync` 归还当前用户获得的授权，成功返回 204；无授权或不可归还返回 404，并以 mutation guard 保证重复请求不产生重复副作用，同时记录授权 owner/grantee 双 viewer 的审计日志。历史 Go 未注册两套 return 路径，也没有归还授权的 store 调用、404 语义或审计目标，前端授权分组的“归还”操作会直接失败。
- 删除审计 targets/metadata 取证：Node `delete` 已从 store 拿到受影响策略路由，并将最多 20 个 `route_strategy` 作为 `targets` 写入日志，同时写入 `affectedRouteStrategyCount` 与样本列表 `metadata`；历史 Go `Delete` 虽计算 `AffectedRouteStrategies`，但 `authsys.OperationLogEntry` 没有 `Targets` 字段，`remove` 仅把摘要放入 `Changes`，既未持久化 targets，也未记录数量/样本 metadata。删除成功后的审计消费者无法得到 Node 的关联策略路由明细。
- 删除/停用可用性守卫切片取证：Node `loadActiveRouteStrategyGroupCountExcludingGroup` 统计策略路由剩余分组时，除所有者自有且启用的分组外，还会计入该策略路由所属账户通过 `resource_authorizations` 获得、且授权设置 `enabled` 的分组（并检查授权状态和过期时间）。历史 Go `activeBindingCountsExcludingGroup` 仅要求 `groups.system_account_id = route_strategy_groups.system_account_id`，完全排除授权分组。因此当某个被授权分组是策略路由唯一可用分组时，Go 删除/停用守卫会把剩余数量误判为 0 之外的可放行状态，可能让策略路由失去唯一可用分组。
- 删除后统计脏标记失败语义切片取证：Node PostgreSQL 的 `refreshGroupAccountStatsAfterWrite` 采用后台任务，脏标记失败只记录 `postgres_group_account_stats_dirty_mark_failed` 日志，不改变已提交删除的 204 响应；历史 Go `Delete` 在删除事务提交后同步调用 `markStatsDirty`，任何写入失败都会直接返回错误，路由因而对已删除资源返回 500。两者在统计表暂时不可写、连接中断等故障下的可观察结果不同，且 Go 已完成业务删除后还会误报请求失败。
- 删除后缓存失效复核（非缺陷）：Node 删除后会清理 `groupLookup`、`groupAccountIds` 和 gateway runtime 缓存；历史 Go 组包的 `ListPage`、`memberCounts`、`groupAccountIDs` 均直接执行 SQL，且 Go gateway 未发现同类 group lookup/account-id 缓存，因此缺少前两项失效调用不会造成已证实的陈旧读。Go 仍触发 `group_deleted` runtime invalidation，行为差异属于实现方式差异，暂不登记为 bug。
- 影响范围：分组页面缺功能或拿到错误统计/分页；非法请求被错误接受；删除后的审计关联信息不完整。缓存失效差异不构成已证实的行为问题。

## 根因与证据

- Go：`backend-go/projects/gateway/internal/groups/routes.go`、`store.go`。
- Node/前端：`backend/src/modules/groups/groups.routes.ts`、`backend/src/storage/group-summary.repository.ts`、`frontend/src/api/domains/groups.ts`。
- 当前 gateway main 未发现 groups 挂载，Node owner 仍在运行；提交没有 Node 删除或 migration-backup manifest。

## 修复与验证

- 修改点：补齐完整路由矩阵、authorized/统计查询、Node 等价分页和 null/unknown 校验，恢复删除日志 targets/metadata；接入真实 gateway 后做 SQLite/PG、前端 smoke 和 golden 回放。
- 当前验证：仅内存 SQLite 包测，未覆盖真实挂载和 PostgreSQL。
- 结论：M05 不能视为完整分组功能迁移。
