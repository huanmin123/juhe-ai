## 问题概述

- 现象：K2 提交 `c1c96f0a3` 从 Node `system-api-app.ts` 删除了 `authRouter` 和 `systemAccountsRouter` 的导入及挂载，声称由 Go `authsys` 独占这两个前缀。
- 期望：切换提交后，配置的系统 API 入口应由 Go gateway 在业务 listener 上提供会话鉴权、验证码、登录态、登出、`me`、会话撤销和 system-account CRUD 等完整能力。
- 实际：`HEAD` 的唯一 gateway 入口 `backend-go/projects/gateway/cmd/juhe-ai-gateway/main.go` 未导入或调用 `internal/authsys`，没有 `MountAuth` / `MountSystemAccounts`。该入口只启动 loopback 健康端口和 J3b model-checks 管理端口；`authsys` 仅在包内测试通过手工 `httptest` handler 暴露。Node 对应挂载已经移除，因此正式系统 API 的 K2 路由没有生产 owner。
- 影响范围：登录、验证码、会话查询/撤销、密码修改和系统账户管理不可用，管理端无法完成正常鉴权；属于切换后全局阻断。

## 复现步骤

1. 查看 `c1c96f0a3` 对 `backend/src/modules/system-api/system-api-app.ts` 的差异，确认删除了 `authRouter` 与 `systemAccountsRouter` 的导入和挂载。
2. 查看 `HEAD:backend-go/projects/gateway/cmd/juhe-ai-gateway/main.go`，确认生产入口只挂载 `/model-checks` 族路由及健康处理器，没有 `authsys` 注册或业务 listener。
3. 查看 `HEAD:migration-backup/node/final-archive/K2-session-auth.manifest.json`，确认状态为 `mount-removed-archive-pending`，并且 Node 文件仍在原路径。
4. 在配置的系统 API 前缀请求任一 K2 路径（例如登录或 system-account 列表）：Node 已无对应挂载，Go 入口也没有可达处理器。

## 根因分析

- 表象：K2 的 Go 路由包和包内测试存在，迁移看板把 K2 标为 `archived (mount-removed)`。
- 真实根因：入口翻转顺序错误，先摘除了 Node 挂载，未把 Go `authsys` 接入真实 gateway listener。测试使用手工构造的 `kernel.Handler`，没有覆盖生产 `main.go` 的启动装配。
- 为什么会发生：把“实现文件存在”和“测试 handler 可运行”误当成“唯一生产入口已接管”；manifest 自身仍标注物理归档待完成，但看板状态没有阻止该切换结果进入主线。

## 修复方案

- 修改点：后续修复必须在同一业务 listener 中注册 `authsys` 的全部路由和中间件，补齐真实启动装配、前缀和权限矩阵测试；确认 Go 入口可达后，再按完整清单物理归档 Node 并补齐正式 manifest。不得通过 Node↔Go 跨进程调用补洞。
- 行为影响：恢复 K2 全部系统 API 能力后，才允许继续其他管理切片的入口翻转。
- 发布异常处理：在 Go 入口和 golden/隔离实例验证未通过前，不得再次删除或摘除任何 Node 路由；当前不执行代码修复或生产切换。
