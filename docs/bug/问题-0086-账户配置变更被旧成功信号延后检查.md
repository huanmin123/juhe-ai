# BUG-0086 账户配置变更被旧成功信号延后检查

> 状态：已修复（待生产验证）
> 严重程度：P1
> 模块：AI 账户 / 健康检查 / PostgreSQL / SQLite / Go 公开账户

## 1. 现象

账户修改 API Key 后进入“待检查”，但下次健康复核被安排到约 12 小时后。页面可能同时显示新的待检查提示和旧配置的最近成功信号。

## 2. 触发条件

1. 账户已有历史主动检查或真实网关成功记录。
2. 修改 Key、Base URL 或其他连接配置，账户进入 `pending_test` 并清空下次检查。
3. 修改前已经在途的真实请求稍后成功，或候选扫描仍把旧成功信号当作当前配置事实。

## 3. 根因

- gateway 成功信号写回未限制 `status = active`，旧请求可覆盖新配置的待检查计划。
- PostgreSQL 候选过滤只让“从未检查过”的待检查账户绕过最近成功信号；修改配置后的账户已有历史检查时间，仍会被跳过。
- 正常检查周期默认是 12 小时加 jitter，所以故障时间表现为“约 12 小时后”，不是一小时失败退避本身失效。
- Go 公开账户更新曾只等待分钟扫描，没有在提交后立即投递 `configuration` 检查。

## 4. 修复

- SQLite、PostgreSQL 的真实成功信号只允许更新 `active` 账户。
- 两个数据库的候选过滤都让所有 `pending_test` 忽略旧成功信号；失败后的 `next_health_check_at` 仍然保留固定一小时退避。
- Go 配置更新提交后立即异步投递检查，明确停用时不请求上游。
- 健康检查结果按配置版本写回，并结构化保存最近检查 `traceId`；真实网关运行态失败同步保存错误 trace，恢复时同步清理，避免提示卡片遗留旧链路标识。
- 人工放行按 `config_revision` 做 CAS，账户更新与分组统计脏标记在同一事务提交；时段外仅保持当前 `status = disabled`，不覆盖用户允许调度的持久开关。

## 5. 验证

- `pnpm --dir backend test:account-health-check`
- `pnpm --dir backend test:account-pending-test`
- `go test ./internal/modules/publicaccounts -count=1`

回归覆盖：已有历史成功的账户修改 Key、旧成功信号延迟到达、待检查立即进入候选、一小时/24 小时收敛规则、停用配置修改不即时探测、人工强确认放行与时间计划边界。

## 6. 防复发

- 任何异步账户事实写回都必须同时校验配置版本或状态所有权，不能只按账户 ID 更新。
- SQLite 与 PostgreSQL 的候选筛选必须使用同一状态语义，并在回归中做源代码或真实数据库双分支断言。
- 不得通过“所有待检查忽略 next check”修复本问题，否则会破坏一小时失败退避并造成探测风暴。
