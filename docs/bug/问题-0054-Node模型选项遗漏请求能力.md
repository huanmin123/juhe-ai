## 问题概述

提交 `2ec3d776d` 已给模型目录、前端 `ProviderModelOption` 和账户 GPT 请求覆盖流程增加：

- `supportedServiceTiers`
- `supportedReasoningEfforts`
- `defaultReasoningEffort`

但 Node `GET /__aisys__/api/providers/models/options` 仍沿用旧投影，只返回 `providerCode`、`model` 和 `supportedApiProtocols`。生产前端因此无法从模型选项取得服务等级和思考级别能力，账户高级配置会把能力误判为空。

Go W2 已在此前按新契约返回并合并这些字段，本次审计确认 Go 不应回退；差异来自 Node 路由投影遗漏。

## 根因分析

- 模型目录事实、前端类型和长期设计已同步扩展，但 options 路由维护了独立 DTO 和手写投影。
- 去重函数只合并旧的协议能力，没有被新字段变更覆盖。
- Node `test:model-catalog` 已验证模型目录和自定义模型 CRUD 的新字段，但 options 的纯函数与 HTTP 断言仍只检查协议数组，导致回归未发现缺失。

这是跨层字段新增时只更新事实模型和消费者、漏掉轻量 DTO 投影与聚合规则的问题。

## 修复方案

- 扩展 Node `ProviderModelOption` 和 catalog 投影，返回三个请求能力字段。
- 去重时分别稳定合并 `supportedApiProtocols`、`supportedServiceTiers` 和 `supportedReasoningEfforts`。
- `defaultReasoningEffort` 只从候选默认值中选择一个仍属于合并后 reasoning 能力集合的值。
- 保持原有 `providerCode` 大小写归一、`model` 大小写敏感、首见顺序和空能力字段省略语义。
- 补纯函数和真实 HTTP options 回归，避免只验证底层模型目录。

## 防复发要求

- 新增模型能力字段时必须同时检查：事实模型、完整 catalog DTO、轻量 options DTO、去重聚合、前端类型和 HTTP 回归。
- 跨运行时审计不能机械地让 Go 向 Node 当前响应回退；需要结合最新设计、消费者和提交意图判断哪一侧发生遗漏。
- 轻量 options 接口如果被表单用作能力事实，不能只返回显示名称；所需能力字段必须由同一接口批量提供，避免前端逐模型请求或字符串猜测。

## 完成总结

Node 模型 options 已与最新前端、长期设计和 Go W2 契约对齐。当前仍未完成 W2 生产单 owner 切流与 Node 删除，但本缺陷不再阻塞生产 Node 前端读取 GPT 请求能力。
