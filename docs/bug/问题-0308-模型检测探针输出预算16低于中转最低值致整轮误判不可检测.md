# 问题-0308：模型检测探针输出预算 16 低于中转最低值致协议探针 400 整轮误判不可检测

- **日期**：2026-10-11 用户报障（carborn 账户 worldclawpro.ai/6.1s × gpt-6.1-sol）；同日修复上线
- **严重级**：P2（模型检测对该类上游全量误判"不可检测"；手动测试正常，结论互相矛盾）
- **状态**：已修复（`protocol_basic` 家族预算 16→1024；根因层修复按《上游请求信封统一设计》v3 持续推进）

## 现象与证据

用户报：carborn 的账户 worldclawpro.ai（`profile_gpt_openai_v1`，`responses_sse`）模型检测"不可检测 0/100"，但手动账户测试正常。生产 run 证据：`protocol_basic` 三次尝试全部 HTTP 400，错误原文 `max_tokens=16 is below the minimum the model provider accepts (100); raise it to at least 100`，terminalFailure 后整轮核心探针跳过 → 0/100。

## 根因

`modelcheckprobe` 的探针输出预算写死为对齐旧 Node oracle 与官方 API 最小值的小魔数：`protocol_basic` 家族 16（suite.go:118/138/789/798）、Chat 下限 64、Gemini 下限 128 等。真实中转普遍实施更高最低值（本次 100）；且 16/64 对思考模型会把 `max_output_tokens` 预算耗尽在推理上、可见回复为空（假阴性风险）。手动测试正常是因为其请求形状不携带该字段/带足预算——探针自创信封与真实流量割裂是缺陷之源。

## 修复

1. `protocol_basic` 家族（基础/流式/可信对比首探针）预算统一 `protocolBasicOutputTokens = upstreamenvelope.DefaultProbeOutputTokens(1024)`：≥ 观测最低值 100、给思考模型留推理空间、预算是上限非计费值成本可忽略。
2. 其余探针族语义预算（采样 16、token_integrity 16、身份 96/256/64 等）按设计 §4.4 原样保留（改预算影响证据可比性，须单独裁决）。
3. 回归测试 `w16g_protocol_basic_budget_test.go`：四协议 × basic 家族预算必须等于 1024。
4. 根因层（请求构造割裂）按 `docs/architecture/上游请求信封统一设计.md` v3 治理：M1 已交付 `shared/platform/upstreamenvelope` 唯一构造源（13 端点 catalog + 四鉴权策略 + 命名预算策略 + 事故 Mock 回归），F2/F3/F4/F5 的构造迁移按 M2-M5 推进。

## 教训

1. 探针请求形状必须与真实流量同界——任何"探针自己拼请求"的实现都是缺陷工厂（评审红线已入 `功能开发指导.md`）。
2. 输出预算是上限不是计费值：设过低不省钱，只会撞上游最低值限制（400）或饿死思考模型（假阴性）。
