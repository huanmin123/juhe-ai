# BUG-0354 跨协议超大 SSE 事件整流跳过致终止/失败丢失

## 基本信息

- 编号：BUG-0354
- 状态：已修复待发布（2026-11-04）
- 严重程度：P1
- 发现时间：2026-11-04
- 发现方式：BUG-0353 同源审计 + 代码路径取证
- 模块：后端 / 网关 / 流式转发 / OpenAI Chat、Anthropic、Gemini 流检查器
- 关联计划：无
- 关联 bug：BUG-0353（同源事件状态生命周期）、BUG-0014（超大 SSE 事件不应整流失明）、BUG-0314（Anthropic/Gemini 行/事件上限）
- 责任人：网关维护者

## 问题概述

- 现象：三个 inspector 在单条 SSE 行或单个事件超过解析上限时，把「当前事件无法完整解析」升级为「整条流停止解析」（`Skipped=true`）：
  - `gatewayopenai.processOversizedLine`：超大 `data:` 行且前缀无 `type`、无 `event:` 名 → `skipParsing` 整条流；
  - `gatewayanthropic` / `gatewaygemini`：单行超过 256KB 或单事件累计超过 256KB → `Skipped=true`，`pushBytes`/`Finish` 短路。
  后续 `[DONE]` / `response.completed` / `message_stop` / Gemini finish 等终止事件不再解析；管道走到 `finalizeParserSkipped` 时按 `p.completed && !FailedReceived` 收成功，超大顶层 `{"error":{...}}` 帧可能被吞成成功。
- 期望：超大事件只丢弃当前事件的完整解析，仍继续解析后续事件；若能轻量识别当前事件为顶层 error 对象或终止事件，必须置 `FailedReceived`/`TerminalReceived`；不能因为一个超大事件把整条流判成功或判失败。
- 实际：整条流 `Skipped`，后续终止/失败事件全部丢失；`finalizeParserSkipped` 的 success 口径使超大 error 帧存在静默成功风险。
- 影响范围：OpenAI Chat Completions（`/chat/completions`）与 Anthropic `/v1/messages`、Gemini native 流；Responses 的超大终止事件由 BUG-0353 修复，但未知类型超大事件仍走同一 `skipParsing`。

## 复现步骤

1. OpenAI：`NewStreamInspector` 喂入 300KB 的未知类型 `data:` 行（无 `type`、无 `event:` 名）与空行，再喂 `data: [DONE]`；修复前 `Skipped=true`、`TerminalReceived=false`。
2. Anthropic：喂入 `event: content_block_delta` + 300KB data + 空行，再喂 `event: message_stop`；修复前 `Skipped=true`、`TerminalReceived=false`。
3. Gemini：喂入 300KB `data: {"candidates":[...]}` + 空行，再喂 `data: [DONE]`；修复前 `Skipped=true`、`TerminalReceived=false`。
4. 将第 1/2/3 步的超大事件替换为顶层 `{"error":{"message":"..."}}`，修复前不置 `FailedReceived`，流按 skipped 成功收尾。
5. 修复后四类输入均应：不 `Skipped`、当前超大事件计入 summary、后续终止可识别；error 形态置 `FailedReceived=true`。

## 根因分析

- 表象：超大事件出现后 `pushBytes`/`Finish` 全部短路，后续终止事件丢失；审计可能显示成功但内容/终态不可信。
- 真实根因：把「当前 SSE 事件超过旁路解析上限」实现成了「整条流 `Skipped`」；`Skipped` 是流级终态，而超大事件只是事件级状态。OpenAI 的 oversized 分类路径已有 per-event 轻量识别，但未知类型仍回退到 `skipParsing`；Anthropic/Gemini 完全没有 per-event oversized 分类。
- 为什么会发生：行/事件上限首先是为内存有界性引入的（BUG-0314）；为保证「超大 error 帧不被误判成功」，实现选择了整条流跳过，但 `finalizeParserSkipped` 的 success 口径又把跳过当成功，形成「既丢终止又可能吞错误」的组合。
- 与 BUG-0353 的关系：两者都是「事件级状态没有按事件边界收口」的同类问题；BUG-0353 是类型字段跨事件泄漏，本 bug 是整条流状态被事件级超限触发。

## 修复方案

- 修改点：
  - `gatewayopenai/inspector.go`：`processOversizedLine` 对所有 `data:` 超大行进入 per-event oversized 模式，不再 `skipParsing`；新增逐事件 error/output 提示字段并在 `resetOversizedEventState` 清理；`flushOversizedEvent` 合并失败/终止/输出提示。
  - `gatewayanthropic/streaminspection.go`、`gatewaygemini/streaminspection.go`：新增 per-event oversized 状态；行限只丢弃当前 data/event 行直到换行，事件限只丢弃当前事件；空行按轻量分类记录 summary，后续事件继续解析；非 `data:`/`event:` 超大行保留 `Skipped`。
  - 两协议 `resetEvent` 清理全部 oversized 字段；eventName 优先；无 eventName 时从 data 前缀 4KB 内提取**顶层首键** `type`（锚定 `^\s*\{\s*"type"`，嵌套 type 不采信）。Anthropic 以 data type/eventName 驱动 `error`/`message_stop` 与 `content_block_*` 输出；Gemini 以 data type/eventName 驱动 `error`/`interaction.failed`/`interaction.completed`/`finish`/`done`/`[DONE]`、`candidates`/`finishReason` 提示与 `step.delta` 输出；`Finish()` 既有 Gemini 输出补终止语义保留。
- 行为影响：超大事件不再导致整条流失明；当前事件仍不完整解析（只保留有界前缀/尾窗），但后续终止/失败事件可正常识别。非 data/event 超大行仍按既有 `Skipped` 处理。无 schema/接口/配置变更。
- 发布异常处理：gateway-only 代码修复；回退镜像即恢复旧行为。若发布后仍出现 `gateway_stream_inspector_skipped`，按 skipReason 判断是否为非 data/event 垃圾行，再取证。

## 同源场景审计

- 见 BUG-0353「同源场景审计」；本 bug 修复后该节中「Anthropic/Gemini/OpenAI Chat 超大事件整流跳过」不再保留，改为 per-event oversized 续解析。
- BUG-0314 的「行/事件上限」内存边界保留，但超限语义从「整流 Skipped」改为「当前事件 oversized + 后续继续」。

## 已知边界（非阻塞）

- Gemini oversized `finishReason` 提示只做前 4KB 的正则键值匹配，嵌套对象中的同名字段也可能命中；触发需单事件 >256KB 且该键出现在前缀，命中后可能提前成功收尾，属窄边界。
- Anthropic/Gemini 的 data `type` 提取只接受前缀 `{` 后的顶层首键形态；`type` 不在首键的合法事件在 oversized 路径不会按 data type 分类（正常小帧完整解析不受影响，eventName 优先路径不受影响）。
- OpenAI 事件限（多行累计 >512KB）路径只扫各行前缀，不保留事件级尾窗；单行超限路径有尾窗；事件限触发行的 usage 可能丢失（既有 `wa_inspector_test.go` 已标注行为存疑，后续另立）。
- OpenAI 顶层 error 提示只检查事件首条 data 行；跨 data 行拆分的顶层 error 可能漏判（正常路径完整 JSON 解析不受影响）。
- Anthropic/Gemini oversized 失败帧只置 `ErrorMessage`，`ErrorCode` 由下游回落 `upstream_protocol_failure`。
- generic 客户端（`interpretProtocolFailures=false`）仍保留既有「有 data 证据的干净 EOF 即成功」语义；Gemini `Finish()` 在有输出且未失败时仍补记终止；本修复不改变这些既有口径，精确客户端一般按缺终止失败（Gemini 有输出例外）。

## 下次遇到

- 先查什么：`gateway_stream_inspector_skipped` 的 `reason`、`gateway_stream_completed_with_parser_skipped` 的 `success`、审计 `EventTypeCounts` 是否缺终止事件。
- 重点看什么：超大 `data:`/`event:` 行之后是否还有 `[DONE]`/`message_stop`/`finish`；超大帧前缀是否为顶层 `{"error":...}`。
- 如何避免误判：主转发始终按原始字节透传；inspector 的 oversized 只影响旁路分类，不能把整条流当成功。
