# BUG-0076 模型身份来源更新未刷新群体 peer

## 问题概述

- 现象：一个身份来源的累计特征变化后，本批账户会刷新，但同一 population、模型和 feature version 下未参与本批的其他账户仍保留旧的 LOO 距离与 paired 结果。
- 期望：任何有效身份来源更新都使同一精确 scope 的全部账户重新计算 latest；不同 population 或 feature version 不互相污染。
- 实际：只有基线版本、证据等级或独立来源数变化时才传播到群体成员。来源向量变化但这些元数据不变时，peer latest 不失效。
- 影响范围：模型身份一致性、同源塌缩和降级诊断可能暂时使用旧群体分布；当前机制仅诊断，不会自动停号或改账。

## 复现步骤

1. 在同一 `(population, requestedModel, featureVersion)` 写入五个独立来源，完成首次聚合。
2. 只更新其中三个来源的累计特征，使来源数、证据等级和 active baseline 版本保持不变。
3. 查询未参与第二批的 peer latest，再直接按当前来源事实执行 evaluate。
4. 修复前持久化距离保持 `1.011736`，实时计算已为 `2.75`。

## 根因分析

- `refreshIdentityBaselines` 只在 `refreshBaseline` 报告基线元数据变化时返回 population。
- 聚合器因此只刷新本批账户，没有把“来源累计向量变化”视为群体依赖失效。
- 影响集合只携带 population，未同时约束 requested model 和 feature version，也放大了跨版本误刷风险。
- current scope 过去由任意来源行的 `ORDER BY last_observed_at DESC` 决定；跨 scope 同毫秒时没有稳定 tie-break，重复 evaluate 可能选择不同 scope。

## 修复方案

- 每批返回所有实际触达的 `(population, requestedModel, featureVersion)`，不再依赖 baseline 是否换版。
- 精确查询每个触达 scope 的全部账户并刷新 latest，保持 population、模型和 feature version 隔离。
- current 先按 scope 聚合，以最后观测时间、scope 首次观测时间和稳定 scope 键排序；精确同毫秒时 SQLite 与 PostgreSQL 使用同一确定顺序。
- paired window 只写 current scope，不因 peer scope 重算产生额外版本行。

## 下次遇到

- 群体统计的输入向量变化时，不能只比较基线版本、来源数或证据等级；必须检查所有依赖该分布的物化 latest 是否进入失效集合。
- 影响集合必须携带完整 scope，至少包含 population、requested model 和 feature version。
- 以时间选择 current 时必须覆盖同毫秒样本，并为所有数据库方言提供一致的稳定 tie-break。
