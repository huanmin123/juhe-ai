# BUG-0136 AI 账户测试弹窗打开即加载模型目录

## 基本信息

- 编号：BUG-0136
- 状态：已修复
- 严重程度：P2
- 发现时间：2026-07-28
- 发现方式：用户反馈与浏览器 Network
- 模块：前端 / AI 账户 / 人工测试 / 按需加载
- 关联计划：PLAN-20260727T173530419Z
- 关联 bug：BUG-0125

## 问题概述

- 现象：用户只打开“测试账号连接”弹窗，没有操作模型或协议下拉，页面仍请求账户 `test-options`。
- 期望：直接使用列表行的检查模型和检查请求形态；只有展开对应下拉时才加载对应选项。
- 实际：`openTestModal()` 无条件调用批量模型 options，把供应商模型及其请求形态一起加载。
- 影响范围：管理端和个人端账户列表的单账户人工测试弹窗。

## 根因分析

- 列表契约已经完整返回 `healthCheckModel` 和 `healthCheckEndpointMode`，不是后端缺字段。
- BUG-0125 修复模型协议联动时，为了让模型选项一次携带请求形态，后续提交把批量 options 调用前移到弹窗打开阶段，覆盖了原有“首开零请求”契约。
- 回归测试也被改成断言“首开一次请求”，导致错误行为被固化；测试只验证了切换模型不追加请求，没有同时守住触发时机和请求范围。

## 修复方案

- 恢复弹窗使用列表默认值的零请求初始化。
- 模型下拉首次展开请求严格 `{ id, name }` 的批量 options；协议下拉首次展开请求当前模型 capabilities。
- 批量模型 options 不携带能力；切换模型只清理旧能力，等待用户展开协议下拉后再定点请求。
- 分离两类请求的 loading、错误、取消和迟到响应门禁。

## 下次遇到

- 先同时检查列表 DTO、弹窗初始化和下拉展开事件，不要只看 API 响应是否轻量。
- 对按需加载同时断言“未交互时请求为 0”“首次交互调用哪个接口”“相邻交互不会放大请求”。
- 批量模型选项与单模型 capabilities 必须保持不同 DTO，不得为了本地联动把能力重新塞回批量接口。

## 完成总结

已移除 `openTestModal()` 中的批量 options 预取，首开直接使用列表返回的检查模型和检查请求形态。当前模型选择器只消费 `{ id, name }` 批量目录，协议选择器只消费当前模型能力接口；两类请求保持独立缓存、失败重试、取消、迟到响应隔离以及模型切换加载态清理。最终自动化、构建与 Browser 证据由 PLAN-20260727T183737351Z 收口回填。
