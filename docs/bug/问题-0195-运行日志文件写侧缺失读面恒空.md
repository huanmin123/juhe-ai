# BUG-0195 运行日志文件写侧缺失导致运行日志读面恒空

## 基本信息

- 编号：BUG-0195
- 状态：已修复（2026-09-28，待发布生产）
- 严重程度：P2
- 发现时间：2026-09-27（生产数据面全面审计）
- 发现方式：自查（`juhe_dataset.runtime_logs` 0 行 + 日志目录恒空取证）
- 模块：网关（日志子系统）/ 后台任务（runtime log indexer）
- 关联计划：无
- 关联 bug：BUG-0193（working_dir 修复后日志目录已落持久挂载，但仍无文件产生）
- 责任人：待定

## 问题概述

- 现象：管理面运行日志读面（runtime-logs grep 家族）恒空；`juhe_dataset.runtime_logs` 0 行；`runtime_log_file_cursors` 0 行；宿主机 `data/app/logs/` 自部署起无任何文件。
- 期望：文件日志恒开（`JUHE_AI_LOG_FILE_ENABLED` 已于 2026-09-21 移除、`LogFileEnabled=true`，保留 500 文件 × 30 天），运行日志 JSONL 文件持续落盘，jobs 索引器入库，读面有数据。
- 实际：网关 slog 只挂 stdout JSONHandler（`main.go:115`），不向 `LogDir` 写任何运行日志文件；jobs 的 runtime log indexer（`runtimelog.NewIndexer`，file cursors 语义）无源可索引。
- 影响范围：运行日志页、runtime-log grep 面、`juhe_dataset.runtime_logs` 及其派生 facet 全空；日志排查能力缺失。

## 证据链

- `compose.go:538-543`：`NewRuntimeLogGrep(FileEnabled: cfg.LogFileEnabled, Directory: cfg.LogDir, ...)` —— 扫描面装配完好。
- `logreads/runtime_grep.go:328`：`os.ReadDir(g.cfg.Directory)` —— 目录恒空即无结果。
- `main.go:115`：`slog.New(slog.NewJSONHandler(os.Stdout, ...))` —— 唯一日志出口是 stdout，无文件 sink。
- jobs 侧：`main.go:601` `runtimelog.NewIndexer(runtimeConfig, runtimeStore)` + owner lease 运行中，`runtime_log_file_cursors` 0（无文件可吃）。
- 服务器取证（2026-09-27 00:1x）：`find /opt/juhe-ai/data -name '*.log' -o -name '*.jsonl'`（近 4 小时）仅命中 search-hot 的审计热数据文件，无运行日志文件。

## 根因分析

- 真实根因：Node 单体的进程内日志器同时写 stdout 与运行日志 JSONL 文件；Go 迁移只搬了 stdout handler 与"扫描/索引/保留"三个消费面，**文件写侧未移植**，且无启动校验暴露（目录恒空不报错）。
- 为什么会发生：三个消费面（grep 扫描、索引器、保留参数）都齐全，缺失的恰是唯一的生产者，属于典型的"消费面齐全掩盖生产面缺失"。

## 修复方案（已实施，2026-09-28）

- 实施前裁决：原草案「按天滚动」无任何契约依据（消费面文件名正则、清理语义、Node 归档实现、docs 权威口径全部是按大小滚动 + `<base>.<YYYYMMDDTHHMMSSZ>.<uuid>.log` 轮转名），按天实施会造成 rotated 永不清理与 EOF 竞窗丢行双重漂移，故修正为**按大小滚动**，与全部消费面零改动对齐。
- 写侧：`shared/platform/processlog` 新增 `FileSink`（append-only JSONL，`currentSize > 0 && 超阈值先轮转`，O_APPEND 单次 write 保行完整）与 `TeeWriter`（多路写入不短路，stdout 坏管道不饿死文件路）；轮转名与 Node `rotatedLogFileName` 同款；文件清理由 jobs F1 保留清理负责，写侧不删除。
- 装配：gateway `newRuntimeLogger` 三路径（LogDir 空 → disabled 事件 + stdout-only；打开失败 → unavailable 事件 + 降级；成功 → ready 事件 + `slog.NewJSONHandler(TeeWriter(stdout, sink))`），随后 `slog.SetDefault`——/v1 链与 HTTP 访问日志（原先走 slog.Default() 落 stderr 纯文本）自此 JSON 化并进文件。
- 配置：`JUHE_AI_LOG_DIR` 语义不变（未配置即禁用）；新增 `JUHE_AI_LOG_MAX_FILE_MB`（默认 100，1..1024，越界 fail-fast）对齐 Node 写侧契约；既有 `JUHE_AI_LOG_MAX_FILES`/`JUHE_AI_LOG_RETENTION_DAYS` 语义不变。
- 部署：compose 为 gateway/jobs 显式配 `JUHE_AI_LOG_DIR=/app/backend/logs`（宿主 `data/app/logs`），写侧/grep/索引器/清理三方同目录——jobs 缺省派生 `<DATA_DIR>/logs` 会与 gateway 分叉，必须显式同值。
- 范围裁决：本修复只接 gateway 写侧；jobs 进程自身日志写侧接入（Node 时代 worker 角色文件，索引器契约已支持 `juhe-ai.worker.<instance>.log`）登记为后续项。
- 验证锁：`wn_bug0195_writer_contract_test.go` 以消费面视角回放 FileSink→F1 索引器全链路（current/rotated 识别、rotated 全量索引、current 从 EOF 追新、cursor 幂等、err.message 提取、time RFC3339 可解析）。

## 完成总结

- 完成时间：2026-09-28（代码与测试、文档同步完成；生产发布待用户授权）。
- 结论：已修复。gateway 文件日志写侧按 Node 大小滚动契约实施（`shared/platform/processlog` FileSink/TeeWriter + cmd 装配三路径诊断 + `JUHE_AI_LOG_MAX_FILE_MB`），`slog.Default()` 接管使 HTTP 访问日志 JSON 化进文件；compose 显式注入 `JUHE_AI_LOG_DIR` 保证写侧/grep/索引器/清理三方同目录。
- 后续建议：jobs 进程自身日志写侧接入（`juhe-ai.worker.<instance>.log`，索引器契约已支持）；`docs/functions/SQLite存储说明.md` 中同款 rg 过时描述另行核对修正。
- 独立复审（2026-09-28，通过无 blocker）登记的非阻塞后续项：① `rotateLocked` close 失败分支可对齐 rename 失败的 best-effort 重开（当前 close 失败后文件路停供直至重启，仅影响 NFS 等边缘盘）；② 启动诊断事件只进 stdout 不落文件（有意设计，运维如需落盘另行裁决）；③ `CatchPanic` 持 bootstrap logger，切换多路后的 panic 恢复日志不进文件；④ filesink 测试未注入 os 层 rename/close/write 失败路径（实现成本高，主契约已锁）。
