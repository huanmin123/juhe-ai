- 严重程度：P1
- 发现时间：2026-07-10

- 责任人：主 agent / 维护者

## 问题概述

- 现象：Go 自定义模型新增、更新或删除已经成功写入 PostgreSQL 后，如果 Redis 网关运行时缓存失效发布失败，接口仍返回失败。
- 期望：对齐 Node 当前契约。缓存失效属于写后 best-effort 副作用，发布失败不能把已经成功且无法回滚的数据库写入误报为失败。
- 实际：旧 Go 将 invalidator 错误直接返回给 HTTP 层，调用方可能重试并触发重复创建、重复更新或删除结果误判。
- 影响范围：Go opt-in `POST/PATCH/DELETE /__aisys__/api/providers/{code}/models`。

## 复现步骤

1. 让自定义模型 store 正常完成 create、update 或 delete。
2. 注入返回错误的 `CustomProviderModelInvalidator`。
3. 旧实现返回 invalidator 错误，但数据库写入已经完成。

## 环境信息

- 分支 / 版本：`feature/20260706-go`，W3 自定义模型 CRUD Go opt-in 阶段。
- 数据状态：PostgreSQL 写入成功，Redis state 发布失败。
- 浏览器 / 系统 / Node 版本：不适用；服务层写后副作用问题。
- 是否稳定复现：是。

## 根因分析

- 表象：Redis 故障时自定义模型写接口失败。
- 真实根因：Go service 把事务外缓存失效发布当成主写入的一部分，直接传播发布错误。
- 为什么会发生：迁移自定义模型 CRUD 时复用了 invalidator 返回值，但没有同步 Node `notifyGatewayRuntimeCacheInvalidation` 的 best-effort 边界。

## 修复方案

- 修改点：
  - create、update、delete 在数据库写成功后仍调用 invalidator。
  - invalidator 错误不再改变成功写入的 service 返回值。
  - 保留更新或删除后“清理默认测试模型”失败的原有返回语义，本次不扩大到其他副作用。
  - 增加三条失败注入测试，确认 invalidator 被调用一次且错误被忽略。
- 行为影响：Redis 短暂不可用时，管理接口不再把已成功的 PostgreSQL 写入误报为失败。
- 发布异常处理：缓存失效失败期间 Node 网关可能在 TTL 或后续成功失效前短暂读取旧模型目录；应通过 Redis 监控和运行日志定位，不应依赖客户端重试数据库写入。

## 下次遇到

- 先查什么：副作用发生在事务内还是事务外，失败时主数据是否已经提交。
- 重点看什么：缓存失效、operation log、通知和异步任务是否会把已提交写入误报为失败。
- 如何避免误判：不能只看接口错误；必须同时检查数据库最终状态和调用方重试是否会产生重复写。
