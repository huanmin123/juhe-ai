# BUG-0066 NewAPI 令牌不限额误判为账户余额无限

## 现象

部分 NewAPI 账户在列表中显示“剩余：无限”，但该结果不是账户余额接口返回的真实无限余额。没有任何内置适配器能查询余额的账户仍按配置周期持续轮询，浪费后台请求资源。

## 根因

- NewAPI `/api/usage/token/` 的 `unlimited_quota=true` 表示当前令牌不受令牌额度限制，不表示用户账户或钱包余额无限。
- 解析器把令牌级权限字段直接归一化成账户级 `unlimited`，丢失了字段所属层级。
- 后台只有成功与失败状态，没有把“用户希望开启”和“当前配置没有可查询能力”分开，确定不支持后仍安排下次刷新。

## 修复

- NewAPI `unlimited_quota=true` 改为 `unsupported`，继续尝试 LiteLLM、`/user/balance` 等其余内置适配器；只有明确的账户级无限结果才返回 `unlimited`。
- 全部适配器确定不支持或发生确定性配置错误时，保持 `balance_query_enabled=1`，保存解释性 `unsupported` 快照并把 `balance_query_next_refresh_at` 置空；列表显示“已暂停”。
- 用户保存 Base URL、API Key、代理或余额配置时重新激活；列表人工刷新成功也恢复周期。人工失败或 `unsupported` 只即时提示，不写快照、不推进调度。
- 网络、超时、`408/429/5xx` 等临时错误不暂停，第三次才显示失败。原 15、30、60 分钟固定退避已被 [BUG-0069](问题-0069-余额临时失败重试等待过长.md) 修正为账户配置周期。
- 上线后重新扫描系统账户，纠正历史误判的“无限”快照。

## 验证

- 适配器回归确认 NewAPI 令牌不限额返回 `unsupported`，并继续回退到 `/user/balance`。
- 刷新状态机回归确认确定性错误保持用户开关开启且下次刷新时间为空，配置保存可以重新激活；人工失败不落库。
- 连续临时失败回归确认三次失败阈值和成功清零；重试周期当前以 [BUG-0069](问题-0069-余额临时失败重试等待过长.md) 为准。
- 前端回归确认“已暂停”文案、人工不支持不覆盖当前单元格，以及测试按钮紧凑布局。
- 本地真实组件在桌面和 390px 窄屏通过验收，无横向溢出、重叠或控制台错误。
- 生产 release `20260712-135621-balance-suspension-2c1120447` 已通过 90 秒稳定门禁：1 server、1 DB service、3 workers，PostgreSQL/Redis 可用且队列无积压。
- 未开启账户全量扫描完成：`scanned=24, enabled=7, unsupported=17, stale=0`，其中代理账户命中结果明确记录了 `proxyProfileId`。
- 首轮刷新发现 79 条历史 NewAPI `unlimited` 快照会在临时错误时按“保留上次成功值”继续显示；一次性删除这些已知错误快照并重新调度后，生产 `unlimited` 数量立即归零。

## 下次遇到

- 适配器字段必须先确认所属对象是令牌、订阅、用户还是钱包，不能只按字段名推断业务语义。
- `unlimited` 只能来自明确的账户级余额口径；权限不限额、预算缺失和接口不匹配都不能当成金额。
- 用户开关表达意愿，后台暂停表达能力状态，两者不能互相覆盖。
- 判断能力不支持前必须排除临时网络错误；只要本轮存在临时错误，就进入退避而不是永久暂停。
- 改变历史快照的业务语义时，除了修正新写入逻辑，还必须显式失效旧的错误“成功”快照；否则临时错误保留旧成功值会延续已知错误数据。
