# BUG-0116 候选缺设置被误报为网关请求体无效

## 基本信息

- 编号：BUG-0116
- 状态：已修复并完成生产验证
- 严重程度：P0
- 发现时间：2026-07-19
- 发现方式：生产临时接管后用户反馈与候选日志复核
- 模块：后端 / 网关 / PostgreSQL / 发布脚本 / macOS 生产部署
- 关联计划：PLAN-0137
- 关联 bug：无
- 责任人：当前发布任务

## 问题概述

- 现象：生产流量切到 temporary 后，Codex `/responses` 与 `/v1/responses` 请求集中返回 HTTP 400“网关请求体无效”，后台公开接口同时出现 HTTP 500。
- 期望：候选只有在系统设置、authenticated models、Codex Responses 合法 JSON、后台公开接口和新增日志都通过后才能切流；非 body-parser 异常不得被包装成客户端请求体错误。
- 实际：候选进程、`1+1+3`、双 health 和 60 秒稳定观察通过，但新版本必填的 7 个 timeout 设置没有进入部署 migration；前置 runtime 的缺设置异常又落入 raw-body error handler，被误分类为 400。
- 影响范围：temporary 承流窗口内真实网关请求无法使用；主服务未停，发现后立即原子回切 main，公网应用和 DB health 连续恢复为 `200/main`。

## 复现步骤

1. 用含新 lane timeout 设置契约的 release 启动一个从旧生产库复制、但未执行对应设置 migration 的 temporary。
2. 仅验证 `/__aisys__/health`、DB service health 和进程拓扑，均可通过。
3. 使用真实 active API Key 请求 `/v1/responses`，`preResolveGatewayRuntime` 因 `textFirstResponseTimeoutSeconds` 缺失抛错。
4. 旧注册顺序中的 `handleGatewayRawBodyError` 捕获前置 middleware 异常，返回 HTTP 400“网关请求体无效”。

## 环境信息

- 分支 / 版本：候选 `787af91b96b887fefaf1ba1efd90889bd7a71b2c`；生产回切版本 `a9794e1d79c79d341c47970505ee589b2906f858`。
- 数据状态：生产旧库保留 `stream*` 设置，但缺少新 `text*`、`image*` 和 `noAvailableAccountWaitTimeoutSeconds` 设置。
- 系统 / Node：macOS，Node `v22.22.2`，PostgreSQL 高性能模式。
- 是否稳定复现：是；temporary access log 中相同请求在 `3101` 全部快速返回 400，回切 `3001` 后恢复 200。

## 根因分析

- 表象：客户端请求体似乎无法解析。
- 真实根因一：发布期间远程 `master` 合入网关长会话设置契约，部署计划仍沿用原账户覆盖变更的空 migration，代码与生产数据契约不一致。
- 真实根因二：`express.raw` 的错误处理器作为整条前置 middleware 链之后的通用 error handler 注册，无法区分 parser 自身错误与 `preResolveGatewayRuntime` 等更早阶段错误。
- 为什么会发生：切流前门禁只覆盖 health、拓扑、结构 SQL 和窄业务查询，没有用真实 active API Key 走 authenticated models / Responses，也没有阻断“系统设置缺少字段”和 `gateway_raw_body_rejected` 日志。

## 修复方案

- 用局部 parser 包装器把 raw-body 错误处理限定在 `express.raw` 自身回调；前置 runtime 错误继续进入全局 500 边界。
- 新增离线 migration：4 个文本设置继承旧 `stream*` 值，3 个图像设置写入新默认值；旧设置保留以支持回滚旧 release。
- verify SQL 检查 7 个新设置的存在、JSON 数字类型、范围及 4 个旧回滚设置仍存在。
- temporary 验收新增真实 active API Key smoke：authenticated `/v1/models`、Codex 风格合法 JSON `/v1/responses`、DB service health 和无需登录的 `/settings/public`；同时扫描本轮日志增量并阻断缺设置、raw-body 误拒和 DB/runtime 异常。
- production 终验同样强制使用有效 API Key 验证 main 的 models、Responses、DB health 和公开设置，并校验 `X-Juhe-Active-Upstream: main`；成功标记为 `PRODUCTION_BUSINESS_SMOKE_OK`，其后继续完成 60 秒 PID、公网与日志增量观察，才允许输出 `VERIFY_SUCCESS`。
- 独立复核补齐切流脚本自身的不可绕过门禁：`switch-nginx-upstream.sh temporary` 从 3101 固定 PID 推导候选 release/stamp，在任何 Nginx 配置写入前复验 verification SHA256、`TEMP_PREFLIGHT_OK` 的 release/hash/PID/启动身份/稳定窗口/时效，以及切流瞬间的 1+1+3 和端口归属；health wait 后、首个配置写入前再次复验固定运行身份，收紧 TOCTOU 窗口。
- 日志门禁区分真实 `trafficSource=gateway` 与既有 `source=account_test` / `trafficSource=cooldown_retest` 账号复测；只豁免明确的后台复测上游失败，真实客户端 unexpected error 仍阻断。
- 发布异常处理：已在停主服务前回切 main，并以 `aborted` 模式清理候选数据库、Redis namespace、release 和日志。

## 下次遇到

- 先按 Nginx access log 的 upstream 端口对比同一请求在 main / temporary 的状态差异。
- 搜索 `gateway_raw_body_rejected` 时同时查看 `errorType`；字段为空通常表示并非 raw-body parser 自身错误。
- 新 release 增删必填系统设置时，部署 migration 和 verify 必须与最终 release commit 对比，不能沿用较早计划的空 migration。
- health 只证明进程可达；切流前必须用真实鉴权路径、关键后台读取和日志增量共同证明业务可用。
