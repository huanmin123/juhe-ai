# BUG-0001 授权管理待复查缺陷

> 本记录用于暂存统一授权、系统团队、授权分组和网关调度方向的待复查问题。当前项目正在进行大文件重构，先不直接修复；重构完成后按本清单重新验证，仍存在的问题再进入修复。
> 当前新建和编辑 API Key 可以绑定调用方自己的分组，也可以绑定有效授权给调用方的分组；授权失效后绑定配置保留但运行态不可用。

## 问题概述

- 现象：统一授权方向已经完成新版模型设计，但代码实现仍存在若干与设计不一致或待验证的缺口。
- 期望：系统团队、统一授权、授权资源绑定、授权统计和网关实时校验都符合 `PLAN-0003` 与 `系统团队与统一授权设计`。
- 实际：静态自查发现授权创建、授权列表可见性、系统团队入口、授权对象选择、资源删除清理、网关分组状态等路径仍有风险。
- 影响范围：授权管理页、系统团队页、AI 账户授权绑定、API Key 本地分组绑定、授权用量统计、网关 `/v1/*` 调度。

## 待复查问题

1. `createResourceAuthorization` 的 SQL 参数与列数量疑似不匹配，新增授权可能运行时报错。
   - 位置：`backend/src/storage/repositories.ts`
   - 关注点：`resource_authorizations` 新增和更新分支的参数顺序、参数数量、`effective_source_type` / `status` 写入是否正确。

2. 普通用户在授权管理里可能只能看到自己授权出去的记录，看不到授权给自己的记录。
   - 位置：`backend/src/storage/repositories.ts`
   - 关注点：`listResourceAuthorizations` 是否同时覆盖 `resource_owner_system_account_id = 当前用户` 和 `grantee_system_account_id = 当前用户`。

3. 系统团队管理菜单对普通用户可见，与阶段计划“仅管理员可见”不一致。
   - 位置：`frontend/src/router/index.ts`
   - 关注点：`/system-teams` 是否需要 `roles: ['admin']`；普通用户是否只通过授权页读取团队摘要。

4. 授权页复用完整系统账户列表作为授权对象选择，接口边界过宽。
   - 位置：`backend/src/modules/system-accounts/system-accounts.routes.ts`、`frontend/src/views/authorizations/AuthorizationsView.vue`
   - 关注点：是否需要独立的授权对象摘要接口，避免普通用户读取系统账户管理字段。

5. 普通用户授权给团队时，可选团队范围可能不足。
   - 位置：`backend/src/storage/repositories.ts`
   - 关注点：`listSystemTeams` 普通用户只返回自己所在团队，是否满足“统一授权管理可以读取团队摘要用于授权选择”。

6. 新增授权时前端资源选项未过滤可授权资源。
   - 位置：`frontend/src/views/authorizations/AuthorizationsView.vue`
   - 关注点：账户 / 分组选项是否应按 `permissions.canAuthorize` 或 owner 过滤，避免被授权资源被二次授权时只靠后端报错。

7. 授权账户测试可能不进入使用记录和授权统计。
   - 位置：`backend/src/modules/accounts/accounts.routes.ts`、`backend/src/modules/accounts/account-test.service.ts`
   - 关注点：如果允许被授权用户测试授权账户，是否应按一次使用动作写入调用方使用记录；否则后端应禁止授权账户测试。

8. 资源删除、停用或授权失效后，授权记录和绑定关系清理语义不够清楚。
   - 位置：`backend/src/storage/repositories.ts`
   - 关注点：删除账户 / 分组是否同步把相关授权标为不可用；`group_accounts.account_authorization_id` 是否会在授权失效后正确阻断调度且不误导页面。API Key 当前不保留授权分组绑定字段。

9. 网关调度可能未检查分组启停状态。
   - 位置：`backend/src/storage/repositories.ts`
   - 关注点：`resolveGroupUsageAccessMetadata` 和 `listOpenAIAccountsForGroup` 是否应校验 `groups.enabled = 1`。

## 复查步骤

1. 完成当前大文件重构后，先运行类型检查和构建。
2. 准备至少 3 个系统账户：资源归属人、个人被授权用户、团队成员用户。
3. 创建系统团队，覆盖新增成员、移除成员、停用团队、重新启用团队。
4. 通过授权管理分别创建 AI 账户个人授权、AI 账户团队授权、分组个人授权、分组团队授权。
5. 验证普通用户授权列表能看到“我授权出去”和“授权给我”的相关记录。
6. 验证被授权 AI 账户只能绑定到自己的同供应商分组，不能编辑、删除、看凭据或二次授权。
7. 验证授权分组不出现在 API Key 绑定选项；被授权 AI 账户只能加入调用方自己的同供应商分组，不能管理来源账户或来源分组成员。
8. 使用 API Key 调用 `/v1/models` 或 `/v1/responses`，验证网关实时拦截授权收回、团队成员移除、团队停用、系统账户停用、授权到期和分组停用。
9. 验证使用记录归调用方，授权用量按资源归属人和最终用户授权 ID 聚合，且不包含归属人自用。

## 根因分析

- 表象：授权页和网关路径存在可见性、写入、绑定、统计和调度边界不一致的风险。
- 真实根因：新版统一授权模型较复杂，当前实现集中在大文件 repository 和页面组件中，部分路径尚未经过多用户端到端验证。
- 为什么会发生：设计已从旧分散授权切到新版团队来源模型，但大文件重构尚未完成，接口边界、权限摘要、存储写入和网关实时校验还没有被完整拆分和复测。

## 修复方案

- 修改点：重构完成后再按复查结果确定，不在本记录创建时直接修改业务代码。
- 当前边界：项目按当前授权模型维护，本地库允许备份后重建或清洗；运行时代码不保留旧授权兼容分支。
- 发布异常处理：如授权链路仍不稳定，优先修正当前模型下的授权入口和资源调度；必要时停服务恢复到同一数据契约下的已验证构建。
