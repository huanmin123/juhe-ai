# BUG-0078 临时维护任务状态与过期租约未回收

## 问题概述

- 现象：生产 `background_task_runs` 长期残留 2 条 `running` 和 1 条 `queued` 临时维护任务；对应 `running` 租约早已过期，但同类新任务仍可正常完成。
- 期望：临时 worker 未启动或非正常退出后，任务状态应在明确宽限期后收口为失败；过期租约不应永久残留。
- 实际：任务只在临时 worker 正常执行到完成 / 失败处理时进入终态。fork 失败、进程被信号终止、父进程退出或整机重启会绕过终态写入；租约到期只允许后续竞争者接管，不会反向修正任务状态。
- 影响范围：后台任务页面会把历史陈旧行误认为仍在排队或运行；运维无法区分真实活跃任务和已消失进程，也会积累无用租约元数据。

## 复现步骤

1. 写入一条 `queued` 临时维护任务并让子进程始终未启动，或写入一条旧心跳 `running` 任务并让对应 lease 过期。
2. 等待超过临时任务宽限期。
3. 观察原实现没有启动或周期性 reconcile，任务状态和租约保持不变。

## 根因分析

- 表象：后台任务列表存在长期 `queued` / `running` 行和过期 lease。
- 真实根因：`background_task_runs` 与 `background_job_leases` 只有创建、心跳、正常终态写入，没有陈旧状态回收器。
- 为什么会发生：任务行在 fork 前创建；临时 worker 只有运行到自身 try/catch 才会写终态。进程级中断无法执行该逻辑，而 lease 过期本身不会更新任务行，也不会删除终态任务遗留的 lease。

## 修复方案

- 在 stats repository 增加 SQLite / PostgreSQL 同语义的事务化 reconcile：
  - `queued` 超过 10 分钟且不存在有效 lease 时，标记为 `failed`，机器原因写为 `worker_never_started`。
  - `running` 最后心跳超过 10 分钟且不存在有效 lease 时，标记为 `failed`，机器原因写为 `lease_expired_after_worker_exit`。
  - 只删除已终态或任务行不存在的过期临时 lease；近期 `running` 即使 lease 刚过期也保留租约行，使活跃 worker 下一次心跳可以原地续约。
- 在 stats-worker 注册 `background-task-run-reconcile`：启动 2 秒后首次执行，之后每 5 分钟执行，单批最多处理 500 行。
- 选择 stats-worker 是为了遵守 SQLite stats 库单写者边界；PostgreSQL 路径使用单事务和条件更新，避免与实时心跳竞争时误伤活跃任务。
- 本修复不增加 Redis / PostgreSQL 内存，不删除生产业务记录，不改变临时维护任务的正常执行流程。

## 下次遇到

- 先按 `status + updated_at` 检查 `background_task_runs`，再按 `run_id` 对照 `background_job_leases.lease_until`，不要仅凭任务状态判断 worker 仍存活。
- 同时确认对应时间窗内是否仍有同类 `completed` 记录；若持续完成，通常是历史状态未收口，不是当前队列整体卡死。
- 回收条件必须同时使用心跳宽限和有效 lease；不能直接删除所有过期 lease，也不能把所有 `running` 行批量改失败。

## 完成总结

- 完成时间：2026-07-14
- 结论：陈旧临时维护任务现在会由 stats-worker 条件化、批量、幂等地收口，活跃任务由近期心跳或有效 lease 双重保护。
- 后续建议：上线后确认原 2 条 `running` 和 1 条 `queued` 在首次 reconcile 后转为 `failed`，对应过期 lease 被删除，并继续观察新的同类任务可正常完成。
