## 问题概述

C1（切流门禁退役：BUSINESS 五证 + J3b 七证 + cutover evidence 链整体移除，owner 事实恒 auto-claim）与 C4（`JUHE_AI_SESSION_RETENTION_BATCH_SIZE` 零引用收编为常量默认 10000）落地时，cmd 包 7 处测试断言停留在退役前行为，全量跑稳定红灯：

1. `TestBusinessOwnerGateFailsClosed`（compose_test.go）：断言「Node writer 未停止必须 fail closed」——C1 后该门禁不存在。
2. `TestW1KBusinessOwnerGateArms`（w1_resolve_tail_test.go）：6 个切流语义失败臂（owner 非 gateway/交接未确认/writer 未停止/schema 未就绪/缺 epoch/缺 evidence）全部不可达。
3. `TestW1MainSessionRetentionConfig` / `TestW1ULoadSessionRetentionConfigExtraBranches` / `TestW1LoadSessionRetentionConfig`（w1_main_unit/w1_misc_pure/w1_misc）：断言自定义 BATCH_SIZE 生效、非法值报错——C4 后 env 被忽略、limit 恒 10000。
4. `TestLoadSessionRetentionConfigRejectsInvalidValues`（main_test.go）：断言非法 BATCH_SIZE 报错——同上。
5. `TestW1WOwnerJ3bFailFastArms` 的 `timezone-missing` / `j3b-host-schema` 两场景（w1_main_tail_test.go）：断言严格切流模式（J3b 七证显式配置、专属库外部预置、SCHEMA_READY 门禁）的 fail-fast——C1 后 `AutoClaimed` 恒真，专属库由组合根 `ensureJ3bDedicatedSQLiteBootstrap` 幂等自举，装配必然成功，**进程完整启动、30s 场景等待超时**（复现实证见下）。
6. `TestZeroConfigBusinessOwnerGateSemantics` / `TestZeroConfigPostgresAutoClaimFallsBackToSharedPostgresURL` 两段（zero_config_test.go）：断言「显式配置五证任一成员 → 不自动认领 + handoff 门禁保持」——C1 后残留切流语义 env 被忽略、恒自动认领，gate 只查连接性。

另含 2 处测试基建缺陷（放大了本批红灯噪音）：

- **w1 插桩二进制孤儿进程**：`%TEMP%\w1b-cov\bin\juhe-ai-gateway-cover.exe` 固定路径被先前被 kill 的测试遗留子进程锁定，后续任何 w1 场景构建失败（"being used by another process"），曾致 8 个测试集体红灯；清理孤儿进程后全部恢复。
- **场景超时无现场**：`w1bRunScenario` 超时 t.Fatalf 不带 stdout/stderr，30s 等待只留下无输出的终止，卡点不可诊断。

## 根因分析

- **行为变更与测试适配分离**：24544f44c 提交了 C1 生产代码（含 modelcheckowner 七证门禁删除），331f50752 提交 C1 收尾与 C4；两笔均未携带 cmd 包对应测试的适配（工作区遗留边界）。基线核对：e020a6d90（上一发布点）上全部用例绿。
- **24544f44c 单独存在测试构建破损**：routes.go 的 `SetLogger` 调用方入库而定义方（authorized.go 等）留在工作区——由 331f50752 补齐，无遗留问题；发布产物 deploy.sh 全量重编译自完整工作区，生产二进制不受影响。
- **机制实证（timezone-missing 场景）**：进程日志显示完整启动（`juhe-ai-gateway started` + 全部 sidecar 组件就绪）——auto-claim 自举链修复了场景构造的缺失，fail-fast 按设计不可达。stash 基线对照：e020a6d90 PASS → 引入锁定在 e020a6d90..HEAD 的 C1 批次。

## 修复方案（9 处断言对齐 + 2 处基建）

1. `TestBusinessOwnerGateFailsClosed` → `TestBusinessOwnerGateKeepsConnectionPreconditions`：断言 auto-claim 直通、退役字段不再阻断、postgres 缺业务 URL 仍 fail closed（与现实现 businessOwnerGate 仅存的两条连接性臂一致）。
2. `TestW1KBusinessOwnerGateArms`：删 6 个退役臂，保留 postgres URL / sqlite 路径两臂，新增「退役字段全部置无效值仍通过」反向断言。
3. 三处 retention 用例 + `TestLoadSessionRetentionConfigRejectsInvalidValues` → `TestLoadSessionRetentionConfigContract`：断言 interval 自定义/校验不变、BATCH_SIZE 任意残留值（合法数字/负数/零/非数字）被忽略且 limit 恒 10000。
4. `TestW1WOwnerJ3bFailFastArms`：删 `timezone-missing`/`j3b-host-schema` 两场景（注释写明 C1 后不可达的机制），保留失败点不被自举修复的三臂（retention-interval / circuit-url-invalid / circuit-meta-missing）。
5. `TestZeroConfigBusinessOwnerGateSemantics` / `TestZeroConfigPostgresAutoClaimFallsBackToSharedPostgresURL`：第三段改为「残留切流语义 env 被忽略、恒自动认领、连接性满足即放行」。
6. 基建：`w1bRunScenario` 超时 t.Fatalf 带出 stdout/stderr 现场（本批诊断依赖该增强才完成机制定位）；孤儿插桩进程经 tasklist/taskkill 清理（运维动作，无代码变更）。

## 验证结果

- 9 处改造测试 + ZeroConfig 族 + `TestW1WOwnerJ3bFailFastArms` 整族全部通过。
- cmd 包全量 `-count=1 -timeout 25m` 全绿（728s；注意默认 10m 包超时会被 w1 慢场景族顶爆 panic，全量跑必须显式提高 timeout）。
- gofmt / go vet 零告警。

## 防回归与观测性备注

- 行为契约变更（env 退役、门禁删除）交付时必须以 `go test ./cmd/... -count=1 -timeout 25m` 全绿为门禁；全量输出**禁止 head/tail 截断**——本批红灯两轮被截断漏看即此教训；`-run` 组合验证必须核对 `--- PASS` 计数与期望用例数一致（匹配不到静默跳过会造成假绿，本批诊断中亦踩过）。
- w1 插桩二进制固定路径在并行/中断场景存在文件锁竞争面：再遇 "being used by another process" 先 `tasklist | grep gateway-cover` 清孤儿，不按代码缺陷排查。
- 本批为纯测试改动，不进生产二进制，无需发版（下次任意 gateway 发布自然携带）。
