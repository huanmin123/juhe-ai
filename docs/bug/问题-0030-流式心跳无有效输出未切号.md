## 问题概述

- 现象：生产 trace `55b972ab-d34c-4608-be20-ded4bf34cb34` 的 `/v1/responses` 流式请求卡住 229 秒以上，客户端主动关闭后记录为 `client_aborted`，未在该请求内服务端隐藏切换账号。
- 期望：上游只发送 SSE 心跳 / 注释等无有效输出内容时，网关应在客户端超时前将其识别为输出前流式失败，并触发服务端隐藏重试 / 切号。
- 实际：上游在等待期间仍断续返回极小 raw chunk，刷新了“上游原始活动”时间；网关没有单独的“无有效 SSE 事件 / 无有效输出”保护，直到客户端关闭才终止，最终按 `client_aborted` 记录，无法再对已经断开的下游透明切号。
- 影响范围：所有经网关 SSE 管道转发的协议。OpenAI Responses / Codex Desktop 是本次生产样本；Anthropic Messages SSE、Gemini streamGenerateContent SSE 或其他后续协议如果上游长时间只发心跳 / 注释、不发协议有效输出 / 失败 / 终止事件，也属于同类风险。

## 根因分析

- 表象：保护机制没有切换账号。
- 真实根因：当前流式读计划把 raw upstream activity 作为活动流硬超时依据；只要上游在 `streamIdleTimeoutSeconds` 内发送任意 raw chunk，即使这些字节不形成 SSE 事件、不包含输出、不包含终止事件，也会刷新 `lastUpstreamActivityAt`。
- 为什么会发生：代码只区分“首段前无数据”和“有 raw chunk 后空闲”，没有单独统计“首个协议语义结果（可见输出 / 失败 / 终止）”的等待上限；`streamClientTotalWaitTimeoutSeconds` 是服务端隐藏重试总预算，不是单个上游流的无有效输出超时。
- 为什么没有切号：客户端关闭后流式管道抛出 abort，最终归档走 `client_aborted`；服务端隐藏切号只在流式管道返回输出前失败结果时触发，abort 分支不会对已经断开的下游继续透明重试。

## 修复方案

- 增加协议感知的无有效语义结果保护：SSE 注释 / 空心跳不能无限刷新“有效输出等待”窗口。
- 保留大事件和碎片化事件安全边界：仍允许大 SSE 事件在 raw bytes 持续到达时继续读取，避免误杀图像流或长 JSON 事件。
- 输出前命中该保护时应返回可重试的流式失败结果，而不是走客户端 abort 分支，从而复用现有服务端隐藏切号流程。
- 补专项回归：心跳-only 上游应在客户端关闭前触发服务端切号；碎片化大 SSE 事件不应误触发；客户端真实中断仍记录 `client_aborted`。
- 行为影响：所有经 `GatewayStreamInspector` 解析的 SSE 协议共用该保护；OpenAI / Anthropic / Gemini 均需提供 pending event 状态，让未闭合协议事件继续按 raw chunk 活动保护。

## 下次遇到

- 先查什么：按 trace 查运行日志 `gateway_stream_aborted` / `gateway_stream_pipe_error`，再查使用记录的 `error_code`、`duration_ms`、`account_id`、`first_token_ms`。
- 重点看什么：`chunkCount`、`totalUpstreamBytes`、`sseEventCount`、`outputReceived`、`terminalReceived`、`failedReceived`；如果 raw bytes 很少但持续刷新，优先怀疑上游心跳-only。
- 如何避免误判：不要只看“客户端关闭”或 `client_aborted` 结论；同时看该请求关闭前是否已经形成服务端可分类的输出前失败结果，以及同一 API Key 后续是否能正常触发切号。
