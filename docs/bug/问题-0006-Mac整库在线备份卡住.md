# BUG-0006 Mac 整库在线备份卡住

## 基本信息

- 编号：BUG-0006
- 状态：已修复
- 严重程度：P1
- 发现时间：2026-05-13
- 发现方式：Mac 热修部署
- 模块：部署 / 运维 / SQLite
- 关联计划：无
- 关联 bug：无
- 责任人：Codex

## 问题概述

- 现象：部署前对 Mac 生产 SQLite 执行整库 `.backup` 时长时间不结束，备份文件持续增长，影响切版节奏。
- 期望：常规部署前只备份业务相关表，避免日志、审计、用量明细、统计缓存和监控数据拖大备份。
- 实际：旧流程默认整库备份，生产库约 7.6G，在线备份在有 WAL 和活跃请求时容易耗时过长；同时 sudo 凭据没有预校验，停服务失败后仍可能进入备份阶段。
- 影响范围：Mac 部署和 schema 同步流程；主服务未损坏，但发布被阻塞并产生了临时大文件。

## 复现步骤

1. Mac 生产服务保持运行，并存在较大的 `juhe-ai.sqlite3` 和 WAL。
2. 部署脚本或手工命令执行 `sqlite3 juhe-ai.sqlite3 ".backup ..."`。
3. 备份长时间不结束，甚至在服务被 launchd 拉起后继续在线备份。

## 环境信息

- 分支 / 版本：2026-05-13 Mac 热修发布
- 数据状态：Mac 生产 SQLite 主库约 7.6G，存在活跃网关请求和 WAL
- 系统 / Node 版本：macOS LaunchDaemon 运行环境
- 是否稳定复现：在大库和高流量窗口容易复现

## 根因分析

- 表象：部署前备份卡住，临时备份目录占用数 GB 空间。
- 真实根因：常规部署备份口径过宽，把可过期或可重建的日志、审计、使用明细、统计缓存、系统监控等数据一起整库备份；同时停服务依赖 sudo，但脚本没有先验证 sudo 可用和服务已停干净。
- 为什么会发生：早期部署数据量小，整库 `.backup` 成本不明显；生产库增长后，日志/统计类表成为主要体积来源，常规发布并不需要它们。

## 修复方案

- 修改点：Mac schema 同步脚本默认只导出业务表 SQL：系统账户、全局/系统设置、供应商、代理、错误策略、AI 账户、团队、统一授权、分组、分组账户、API Key、公告和已读状态。
- 排除项：`usage_records`、`audit_*`、`operation_log*`、`runtime_logs`、`usage_*`、`stats_job_state`、`account_quality_*`、`system_metrics_*`、`system_sessions`、`account_usage_snapshots` 等日志、统计、运行态和缓存数据。
- 安全措施：执行停服务前先校验 sudo；停不干净或 3001 仍被占用时拒绝继续备份和同步表结构。
- 兼容影响：常规备份不再是完整数据库快照；如果明确要做整库迁移或灾备快照，仍需先停服务再离线 `.backup`。

## 下次遇到

- 常规部署优先使用业务表 SQL dump；整库快照只用于明确的迁移 / 覆盖 / 灾备场景。
