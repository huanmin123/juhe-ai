# BUG-0295 账户电路后台恢复不投影账本与孤儿行无回收

## 基本信息

- 编号：BUG-0295
- 状态：已修复（代码入库待发布验证；生产存量数据已于 2026-10-08 经授权结清）
- 严重程度：P1（管理面熔断状态永久冻结、账本与运行态三方漂移；实际调度未受这些孤儿行约束）
- 发现时间：2026-10-08（用户报告生产账户 `api.shenwenai.com-神影 - 克隆` 熔断验证状态自 2026-10-07 22:39 起冻结不动）
- 发现方式：生产取证（ledger / Redis DB1 主链运行态 / Redis DB2 J3b 投影三方比对）
- 模块：后端 / jobs（账户电路恢复投影）+ gateway（按账户渐进恢复装配、CAS 入参校验）
- 关联计划：无
- 关联 bug：BUG-0262（诊断请求穿透退避窗口，同链路前置修复）；BUG-0267（错误处理链路留观，与本缺陷无因果）

## 问题概述

- 现象：管理页账户列表的熔断摘要（`circuitSummary`）长期停留在 `verifying`（受控验证）与一个已过期的"下次电路检查"时间（如 2026-10-07 22:39:05.445），永不变化；生产 ledger 共 27 条非 CLOSED 事故行（SUSPECT/OPEN）停在 2026-10-05 至 10-08 之间的过去时刻，全部无人推进。
- 期望：电路作用域的恢复/退避推进（无论来自网关主链请求还是 jobs 后台恢复扫描）都按设计 §7.5 契约经可靠队列写入最小持久 incident ledger；运行态丢失后 ledger 非终态行能被恢复或结清，不产生永久孤儿。
- 实际（三条断链并存）：
  1. jobs 后台恢复扫描 `account-circuit-recovery` 对 Redis 运行态做的全部转换（acquire/complete confirmation/canary、replace_revision）**不投影回 ledger**——`worker_circuit_jobs.go` 构造 `CircuitRecoveryService` 时未传 `OnMutation`（挂点与 `observeMutation` 均已存在）。Node 原版（commit `d8bfbc2a7`）此处理线为 `onMutation: projectGatewayAccountCircuitRuntimeMutation` → 控制面 bridge → CAS 写 ledger + outbox，Go 迁移时 jobs 侧丢失。
  2. gateway 主链按账户渐进恢复（`bridge.EnsureAccountReady`/`IsAccountReady` 已实现）**未装配**进 `ServiceOptions`（`chain_wiring_w2c.go` 只挂 OnMutation 与 Logger，`isRuntimeStateReady` 默认恒 true）——Redis 运行态丢失后 ledger 非终态行不会被恢复回运行态，主链请求直接按 CLOSED 放行，ledger 行成为孤儿（设计 §125/§633 契约未闭环）。
  3. gateway CAS 写侧 `validateIncident` 强制"租约必须有 attempt 时间戳"，而 gateway 自身 bridge 的 CAS 输入从不填 attempt 字段——**主链一切带租约状态（confirmation/half_open/recovery 租约）的持久化必然入参校验失败并重试耗尽**，是 ledger 行停在无租约 SUSPECT 的另一源头。
- 影响范围：管理页熔断摘要展示（读 ledger）；ledger 事实完整性。**实际 /v1 调度不受这 27 条孤儿行约束**（运行态视角它们早已无状态＝CLOSED；管理页摘要读面亦按 dispatch_revision 围栏与 state<>'CLOSED' 过滤）。反向风险同样存在：真实活跃熔断（运行态 OPEN）可能因投影断链在 ledger 显示为 CLOSED，管理页显示比实际健康。

## 复现步骤

1. 生产查询 `juhe_business.account_circuit_incidents WHERE state<>'CLOSED'`：27 行全部 `next_transition_at_ms` 早于当前时间数小时至数天，无租约，无任何后续转换。
2. 同账户 scope 在 Redis DB1 主链 states hash 无键（主链视为 CLOSED），DB2 J3b 投影索引残留同毫秒时间戳的 SUSPECT（due 索引为 0，无恢复驱动）。
3. jobs 日志可见 `account-circuit-recovery` 任务在跑（另一账户的探针 403 退避循环 `backoffAttempt=857` 为其活跃证据），但该账户的 ledger 无对应活动行——后台扫描推进运行态而不写账本的直接实证。

## 环境信息

- 分支 / 版本：Node→Go 迁移后全部已发布版本；修复于 2026-10-08 入库（待发布）。
- 数据状态：27 条孤儿行已于 2026-10-08 结清（见「存量处置」）。
- 是否稳定复现：是（结构性缺口，任何"恢复扫描推进 + 运行态丢失"组合均复现）。

## 根因分析

- 真实根因：Node→Go 三项目拆分迁移时，账户电路控制面管道被拆成"gateway 主链投影写侧"与"jobs 只读投影侧"，jobs 恢复扫描的 mutation 投影接线在装配层丢失；gateway 侧渐进恢复 hook 装配同样未完成；CAS 入参校验与自家 bridge 输出形状矛盾（Node 原版 attempt 字段为纯 optional）。
- 为什么会发生：三项目 internal 不可互 import 的基线下，`circuitrecovery.go` 头注释声明了"通过 onMutation 将每次 mutation 投影给控制面"的契约，但装配文件未兑现；`registry.go` 对 recovery 任务的 Writes 登记只有 `runtime:account_circuit`，登记与契约的矛盾未被测试捕获。

## 修复方案

- 修改点（jobs）：
  - `internal/circuitstore/controlplane.go`：新增 ledger CAS 写侧 `CompareAndSetIncident`（锁账户行 → account_not_found / stale_dispatch_revision 围栏 → outbox dedupe 回放 → 锁 incident 行 → expected/generation CAS → 全列 upsert + 同事务 `incident_changed` outbox；44 列与 gateway 写侧逐字一致）、`Cleanup`（CLOSED 保留期到期 + 投影水位覆盖 + 无未 dispatched outbox 的物理清理）、`ListActiveIncidentsPage`（无 revision 围栏的活动行 keyset 分页，供结清扫描）。
  - `internal/opsjobs/circuitprojection.go`（新增）：薄投影器——按 scope 合并最新 mutation → CAS 投影（冲突回填重试 ≤2；终态丢弃并清 revision 缓存；`conflict 且响应无行` 时清缓存重试，防"关闭→清理→复开"永久冲突）→ 失败留 pending，由每轮恢复扫描前的 `FlushPending` 重放；无自有 timer goroutine。
  - `internal/opsjobs/orphanclose.go`（新增）：孤儿结清扫描——活跃租约跳过；PERSISTING/SHADOWED_BY_PERSISTENT 交接态跳过；运行态有键跳过；运行态缺键且超过宽限期（10 分钟）才 CAS 结清 CLOSED（对齐设计 §566"缺失键按 CLOSED 处理"的守卫链）；冲突重试前复查运行态，防同代复开竞态误清。
  - `cmd/juhe-ai-jobs/worker_circuit_jobs.go`：恢复扫描装配 `OnMutation` 投影、扫描前 `FlushPending`、维护任务尾部追加结清扫描 + Cleanup（失败记 `OutcomePartial` 不判任务失败）；projector.Close 进 closer 链。
  - `internal/jobregistry/registry.go`：两任务 Writes 登记补 `business:account_circuit_incidents` / `business:account_circuit_outbox`。
- 修改点（gateway）：
  - `cmd/juhe-ai-gateway/chain_circuit_controlplane.go`：persist hook 改 4 元组带出 bridge 实例（gate 未就绪/契约失败臂行为不变）。
  - `cmd/juhe-ai-gateway/chain_wiring_w2c.go`：`ServiceOptions` 挂 `IsRuntimeStateReady`（薄适配 `bridge.IsAccountReady`）与 `EnsureRuntimeStateReady`（直挂 `bridge.EnsureAccountReady`）——ledger → 运行态按账户渐进恢复，gate 未就绪时两 hook 为 nil 保持现状。
  - `internal/business/circuit_control_plane/store.go`：删除 attempt 时间戳与租约的双向强制耦合校验（对齐 Node 原版 attempt 纯 optional 语义；`validateIncidentTimes` 的非负与时序校验保留）——解除主链带租约状态持久化必败的矛盾。
- 行为影响：jobs 恢复扫描的恢复/退避转换对账本可见（管理页熔断状态随之推进）；主链对运行态缺失账户执行一次按账户权威查询渐进恢复（fail-closed 面仅该账户）；无 env/schema 变化。
- 存量处置（2026-10-08 已执行，用户授权）：先备份两表（`account_circuit_incidents_bak_20261008_reconcile` 40 行 / `account_circuit_outbox_bak_20261008_reconcile` 2985 行），事务内将 27 条非 CLOSED 行结清为 CLOSED（清租约与 next/open 时间、retained_until=now、`transition_id='orphan-close:'||原值`、ledger_revision+1）并同事务插入 27 条 `incident_changed` outbox 事件（dedupe `incident:orphan-close:*`）；事件被 jobs 投影消费后 DB1 主链收敛为 CLOSED 保留态（closed zset 27，5 分钟保留期后自动清理）；J3b（DB2）因 outbox 竞消费未收到事件，手动 HDEL 8 个已结清 scope 的 states/scope-runtime 残留（保留 `acc_1789972301550_e2102315/gpt-5.6-sol` 的活跃熔断行——该作用域 DB1 运行态仍 OPEN 退避中，新代码部署后由投影自然回写账本）。注意：该活跃作用域的 ledger 行在结清批次中，部署前管理页对其显示 normal 而实际熔断生效中，部署后自动纠正。

## 下次遇到

- 先查什么：管理页熔断状态与 ledger `state/next_transition_at_ms/updated_at_ms` 是否一致；不一致时核对 Redis DB1 states hash 是否存在同 scope 键（三方漂移判定）。
- 重点看什么：装配层是否兑现包内注释与 registry 登记声明的契约（`Writes` 登记是"任务写什么"的权威清单，与实际写面不一致即是缺口信号）。
- 如何避免误判：ledger 只是投影，运行态才是调度事实——"熔断卡住"先区分展示冻结与真实熔断；跨项目迁移的控制面管道，两侧装配要各自对照 Node 原版 singleton 接线清单验收。

## 完成总结

- 完成时间：2026-10-08
- 结论：三条断链（jobs 投影接线、gateway 渐进恢复装配、CAS attempt 校验矛盾）全部闭环；孤儿结清扫描作为长期对账机制落地；生产 27 条孤儿行已授权结清并验证收敛。终审（glm_5.3_max）裁决可合入，无 blocker。
- 后续建议：① 发布后观察 `account-circuit-recovery` / `account-circuit-control-plane-maintenance` 任务日志的投影与结清计数（`SkippedReopened`/`SkippedHandover` 暂未接入任务日志，需要时再接）；② `account-circuit-recovery` 偶发 `读取账户电路到期状态失败: i/o timeout`（ListDue Redis 超时）为独立问题，另行排查；③ account_not_found 行（账户已删）无自动清理路径，仅只读重扫开销，登记待办；④ jobs 写侧 `controlplane.go` 保留了一条 Node 没有的正向强制"无租约 + attempt 有值 → 拒绝"（终审发现的跨进程语义漂移点，当前不可达——两侧 bridge 均从不填 attempt），建议后续与 gateway/Node 对齐删除或补注释说明保留理由。
