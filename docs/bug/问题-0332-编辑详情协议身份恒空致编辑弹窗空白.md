## 问题概述

- 现象：生产环境打开任一已有 AI 账户的「编辑」弹窗，账户类型、凭证区与健康检查区整块空白或无法回填；列表与人工测试不受影响。
- 期望：编辑详情返回账户当前协议身份（`providerProtocolProfileId`），前端据此回填账户类型、凭证与健康检查形态。
- 实际：`GET /accounts/{id}` 的编辑详情恒返回 `providerProtocolProfileId: ""`，前端 `hasAccountType`/`isApiKeyForm` 判定为假，编辑表单渲染为空。
- 影响范围：管理端「账户编辑」的详情回显（`FindEditBasicDetail` 服务面；本修复当时未覆盖「账户克隆」读面，克隆弹窗空白由 BUG-0333 修复）；新建账户不受影响（BUG-0330/0331 已修复）。

## 复现步骤

1. 登录生产，进入「我的账户」，选择任一已有账户点击「编辑」。
2. 观察账户类型与凭证区：均为空，原账户的 API Key / Base URL / 支持模型不回显。
3. 直接请求 `GET /__aisys__/api/my-accounts/{id}`，响应 `providerProtocolProfileId` 为空字符串。

## 环境信息

- 分支 / 版本：生产 gateway 构建自 `412fafa58`（含 BUG-0330/0331 前端修复）。
- 数据状态：结构重建后的 `juhe_ai` 库，`account_connections` 为当前连接契约。
- 浏览器 / 系统 / Node 版本：不适用。
- 是否稳定复现：是（随机抽查 6 个账户全部为空）。

## 根因分析

- 表象：编辑详情 DTO 的 `providerProtocolProfileId` 恒为空，前端因此无法识别账户类型。
- 真实根因：B4（`3b4dd5cb9`）退役 `provider_protocol_profiles` 表后，`FindEditBasicDetail` 改为 `'' AS provider_protocol_profile_id` 占位，但编辑链路的读侧未迁移到新契约。账户真实协议身份此时已由 `accounts.health_check_connection_id` → `account_connections.connection_preset_code` 承载，读侧没有据此推导 legacy profile id。
- 为什么会发生：B4 先收口写侧（`connections[]`）与列表/路由投影读侧，编辑详情属于低频路径漏网；前端 BUG-0330 的合并层修复只解决「供应商定义为空」，不能补上「账户详情协议身份为空」。

## 修复方案

- 修改点：
  - `backend-go/projects/gateway/internal/accounts/list.go`：编辑详情 SELECT 增加 `accounts.health_check_connection_id` 与关联子查询 `current_health_check_preset`（`account_connections.connection_preset_code`）；扫描后经 `exactkeyprobe.ConnectionPresetProfileID` 推导 `providerProtocolProfileId`，命中时覆盖占位空值。
  - `backend-go/projects/gateway/internal/accounts/accounts_test.go`：创建账户后拉取编辑详情，断言 `providerProtocolProfileId == "profile_gpt_openai_v1"`。
- 行为影响：编辑/克隆详情恢复协议身份回显；未命中连接 preset 的账户（如历史无健康检查连接）仍返回空，前端按既有降级路径处理，不改变写侧契约。
- 发布异常处理：与 gateway 同批；回滚需回退 `list.go` 与对应镜像。

## 下次遇到

- 先查什么：编辑详情 DTO 的 `providerProtocolProfileId` 是否非空；`accounts.health_check_connection_id` 是否指向有效连接行；`account_connections.connection_preset_code` 是否在 `ConnectionPresetProfileID` 映射内。
- 重点看什么：B4 之后任何仍以 `'' AS provider_protocol_profile_id` 占位但下游需要协议身份的读路径。
- 如何避免误判：前端编辑空白既可能是供应商定义为空（BUG-0330），也可能是账户详情协议身份为空（本 bug）；分别检查 `/providers/{code}` 与 `/my-accounts/{id}`。
