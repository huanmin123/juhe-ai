## 问题概述

- 现象：彻底拆分业务库和记录库后，`pnpm test:scope` 在账号 / 分组统计路径报 `no such table: group_account_stats`。
- 期望：运行时代码严格按边界读写；`group_accounts` 只在业务库，`group_account_stats` 只在记录库。
- 实际：`loadGroupAccountStatsByGroupIds()` 仍从业务库读取 `group_account_stats`；同时 `loadGroupAccountIdsByGroupIds()` 曾误用记录库读取 `group_accounts`。
- 影响范围：分组列表、账号统计、作用域回归，以及上线后所有依赖分组账户统计缓存的页面。

## 复现步骤

1. 使用拆分后的临时业务库和记录库运行作用域回归。
2. 调用账号用量统计或分组列表聚合路径。
3. 代码从错误数据库读取表，触发 `no such table: group_account_stats`。

## 环境信息

- 分支 / 版本：2026-05-13 双库改造版本
- 数据状态：业务库和记录库已分离，运行时不做旧整库兼容。
- 系统 / Node 版本：Windows 本地 Node 22+，Mac 生产 Node 25.9.0。
- 是否稳定复现：是。

## 根因分析

- 表象：分库后统计回归超时，强制退出定位到 `group_account_stats` 表不存在。
- 真实根因：双库迁移时只迁走了大部分记录类仓库，漏掉了 `group-read-loaders.ts` 中两处共享读取函数。
- 为什么会发生：`group_accounts` 和 `group_account_stats` 命名相近，但前者是业务授权关系，后者是记录库统计缓存；如果只按模块名而不是表职责切换数据库，容易反向改错。

## 修复方案

- 修改点：`loadGroupAccountIdsByGroupIds()` 使用 `getDatabase()` 读取业务库 `group_accounts`、`groups`、`accounts`、`resource_authorizations`。
- 修改点：`loadGroupAccountStatsByGroupIds()` 使用 `getRecordDatabase()` 读取记录库 `group_account_stats`。
- 兼容影响：不兼容旧整库；旧整库拆分是历史一次性迁移动作，当前代码已固定为业务库 / 记录库分离模式，不再保留分库迁移生产入口。
- 回滚方式：回滚双库改造或恢复单库版本；不建议单独回滚该修复。
