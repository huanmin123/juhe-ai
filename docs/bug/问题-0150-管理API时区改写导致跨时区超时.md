## 问题概述

- 现象：管理 API 将绝对时间字段格式化为 `Asia/Shanghai` 的无 offset 字符串（例如 `YYYY-MM-DD HH:mm:ss.SSS`）。跨时区客户端收到后只能按本地时间或运行库默认时区解释。
- 期望：绝对时间在 API 中使用 RFC3339 UTC `Z` 或明确 offset，客户端按用户本地时区展示；后端不承担展示时区转换。
- 实际：同一瞬时值在不同时区被解释为不同时间，可能造成任务超时判断、到期判断、排序和倒计时偏移。
- 影响范围：管理 API 的账户、任务、登录资料、授权、使用记录和其他带绝对时间的列表或详情；业务日历（排班、用量统计日界线等）不属于本问题的时区迁移范围。

## 复现步骤

1. 在管理 API 响应中读取任一无 offset 的上海时间字段。
2. 在非 `Asia/Shanghai` 的浏览器或运行库中按本地时间解析该字段。
3. 比较客户端计算的超时 / 到期时间与服务端同一瞬时值，观察固定时差导致的偏移。

## 根因分析

- 表象：客户端显示的时间或超时状态与服务端不一致。
- 真实根因：管理 API 把绝对时间和展示时区耦合，丢失了 RFC3339 的 offset / UTC 信息；无 offset 字符串无法唯一表示瞬时值。
- 为什么会发生：旧契约要求统一输出上海本地格式，调用方被迫猜测时区，跨时区使用时产生固定偏移。

## 修复方案

- 修改点：统一绝对 API 时间为 RFC3339 UTC `Z` 或明确 offset；后端停止展示时区转换；Vue / 浏览器按用户本地时区展示。
- 兼容边界：所有绝对时间输入（包括历史请求或持久化值）都必须携带 RFC3339 `Z` 或明确数字 offset；上海或其他无 offset 字符串一律拒绝，不提供读取兼容。
- 业务日历：排班、可用时段、用量统计日界线和日期范围继续使用显式 IANA timezone，不改成浏览器本地时区。
- 非目标：本记录不改变数据存储结构，不涉及 backend-go、生产操作或浏览器截图验证。
