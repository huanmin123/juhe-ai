# BUG-0257：模型质量检测判定 / 处罚 / 恢复 / 调度七项一致性缺陷

- 状态：修复中（2026-10-01 契约已裁决并先行落入文档，代码实施并行进行）
- 定性：Go 迁移回归批次——`qualityDecision` 形状与两层校验语义未对齐 Node 契约，判定、处罚、恢复、调度四条链各自偏离
- 发现方式：J3B 模型质量检测专项复审（gateway `internal/modelcheckowner` 判定 / 处罚 / 恢复 / 调度链路与 Node 契约逐条对照）

## 1. 现象（七项缺陷）

1. **历史详情假达标**：run 的 `quality_decision_json` 缺少 qualityDecision v2 外部键（triggerKind / triggered / hardFailure / score / threshold / configuredAction / result / reasonCodes / beforeStatus / afterStatus / recoveryDueAt / enforcementId / generation / healthSyncResult / healthStatHour / message / decidedAt 等），详情页无法还原当次真实判定，旧记录按当前账户状态反推或字段缺失时展示出"假达标 / 假未处罚"。
2. **快速达标无法恢复**：质量隔离恢复对 `profile=quick` 的复测也要求 9 族证据 formed+trusted，quick 运行天然不形成完整证据，导致 quick 处罚的账户永远无法通过恢复检查解除隔离。
3. **硬冲突处罚被拒**：模型字段硬不匹配 / 协议硬冲突（硬失败）且分数恰好达标的运行，处罚在写入层被"分数达标"单独拒绝——硬失败应独立于分数触发处罚。
4. **恢复用错模型**：恢复检查未使用处罚持久化的 `recovery_model` 冻结快照，改按账户当前 `health_check_model` 取模型；处罚后账户改配检查模型时，恢复验证跑在与处罚不同的模型上。
5. **处罚失败阻断健康同步**：处罚写入与健康事实写入耦合在同一成败链上——处罚失败（含配置过期 stale 被当作可重试失败）时健康小时表不写入或被无限重试拖住；健康重试筛选还排除了 `unavailable` 且证据不完整的运行，导致补偿漏扫。
6. **批量租约过期结算失败**：调度器一次性领取大批量到期计划，排队等待期间租约持续消耗，轮到执行时租约已过期，结算 CAS 全部失败；大批量到期计划同时长时间阻塞恢复与健康补偿扫描。
7. **计划列表状态失真 + 构建失败无详情**：列表只有"启用 / 暂停 / 运行中"粗粒度状态，无法区分账户被删 / 已排队到期 / 正在执行；计划构建（Build）失败时不产生任何 `model_check_runs` 记录，`last_run_id` 不回写，失败无从排查。

## 2. 根因

Go 迁移（Node → Go，2026-09-05 归档清零）时 **qualityDecision 形状与两层校验语义未对齐 Node 契约**：

- `quality_decision_json` 只落了内部证据键，未落对外契约键（缺陷 1 的直接根因），下游详情 / 列表只能靠反推。
- 判定层与处罚写入层的通过条件各自实现：写入层把"分数达标"当成独立拒绝条件，没有实现"硬失败独立于分数"的合取语义（缺陷 3）。
- 恢复门槛、恢复模型、健康同步独立性、调度租约语义在迁移中被简化或各自发挥：恢复门槛未按 profile 区分（缺陷 2）、`recovery_model` 冻结识被丢弃（缺陷 4）、处罚与健康两条写入链被合成一条（缺陷 5）、租约承担了本应由执行容量承担的限流职责（缺陷 6）、列表状态与构建失败可观测性缺失（缺陷 7）。

## 3. 修复方案（契约已裁决，落 `docs/functions/模型质量定时检查与处罚恢复设计.md`）

七项缺陷对应同文档 C1-C8 契约条款与章节：

| 缺陷 | 契约 | 章节 |
| --- | --- | --- |
| 1 历史详情假达标 | C1 qualityDecision v2（camelCase 外部键 + 保留内部键；旧记录不回填不伪造，前端缺失字段显示"未记录"） | §2.6、§6.2、§8 |
| 3 硬冲突处罚被拒 | C2 判定与处罚一致性（写入层仅拒绝"分数达标且无硬失败"） | §3.2 |
| 5 处罚失败阻断健康同步 | C2 处罚与健康写入相互独立（stale 不无限重试；`healthSyncResult="pending_retry"` 分钟级重试，筛选与首发同规则） | §5.2、§7.3 |
| 4 恢复用错模型 | C2 恢复模型冻结（优先 `recovery_model`，空才回退 `health_check_model`） | §6.1、§7.2 |
| 2 快速达标无法恢复 | C3 恢复门槛按 profile 区分（quick 免 9 族证据；full 维持完整证据） | §7.2 |
| 7 构建失败无详情（及立即复测恢复新能力） | C4 立即复测恢复、C8 计划构建失败产生 failed run 并回写 `last_run_id` | §7.2.1、§7.1 |
| 6 批量租约过期结算失败 | C8 按可执行容量领取（每轮每 kind 最多 MaxConcurrency=4；租约自领取起算；结算 CAS 仅作僵尸写栅栏；恢复 / 健康补偿不被阻塞） | §7.1 |
| 7 计划列表状态失真 | C7 计划列表五态 `executionState` + `accountStatus` + `lastRunScore` | §2.3、§8 |

配套变更：C5 定时检查间隔下限 10 → 1 分钟（`interval_minutes` CHECK 放宽并随 `--ensure-schema` 幂等迁移，`recovery_interval_minutes` 维持 10..10080 不变）、C6 计划立即执行两端点（`trigger_kind` 取值域加 `schedule_now`）。接口契约同步 `docs/functions/接口契约与权限矩阵.md`；部署迁移与验证 SQL 见 `docs/deploy/部署指南.md` 与 `docker/single-server/README.md`。

## 4. 验证方式

- 定向单测（backend-go/ 下 modelcheckowner / 调度 / 恢复 / 健康同步相关包）：qualityDecision v2 字段落库形状、两层校验"分数达标 + 硬失败 → 处罚"与"分数达标且无硬失败 → 拒绝"两臂、quick / full 恢复门槛分派、`recovery_model` 优先与空回退、stale 终态（不重试）与 pending_retry 重试筛选、容量领取（租约起算点、每 kind 上限、结算栅栏）、构建失败产生 failed run。
- 隔离实例端到端：创建 `intervalMinutes=1` 计划验证约束迁移；`POST /quality-schedules/:id/run-now` 与 `run-now-batch` 受理 / 409 / 404 / 部分成功；列表 `executionState` 五态与 `lastRunScore`；触发 quality_isolate 后以 schedule_now 达标 run 验证立即复测恢复（含 manual 处罚与人工停用不被覆盖）；旧历史详情缺失字段显示"未记录"。
- 升级迁移验证（PG）：`SELECT pg_get_constraintdef(oid) FROM pg_constraint WHERE conrelid = 'business.model_quality_schedules'::regclass;` 应显示 `interval_minutes BETWEEN 1 AND 10080`；`juhe_j3b.model_check_runs` 的 trigger_kind 约束应含 `schedule_now`（完整 SQL 见 `docker/single-server/README.md`）。
