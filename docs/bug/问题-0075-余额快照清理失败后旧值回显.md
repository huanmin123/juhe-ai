# BUG-0075 余额快照清理失败后旧值回显

## 基本信息

- 编号：BUG-0075
- 状态：已修复（待生产验证）
- 严重程度：P1
- 发现时间：2026-07-14
- 发现方式：多 Key 余额修复复查
- 模块：后端 / AI 账户 / 多 Key / 余额快照 / stats-writer
- 关联 bug：BUG-0073

## 问题概述

- 现象：账户从单 Key 改成多 Key 后，业务配置已经成功自动关闭余额查询，但事务后的 stats 快照删除若失败，单账户保存路径直接吞错；用户之后恢复单 Key并重新开启余额时，旧 Key 的余额可能短暂回显。
- 期望：业务配置保存不因派生快照清理失败而回滚，但清理必须有限重试、可观测；旧快照在重试期间、重试耗尽以及进程重启后都不能重新展示。
- 影响范围：单账户保存和批量编辑后的 `relay_balance` 快照清理。

## 根因分析

- 余额配置在 business 库事务内更新，余额快照位于 stats 库，不能跨库原子提交。
- 单账户路径对 `delete_account_balance_snapshot` 使用空 `.catch()`；批量路径只记录一次汇总 warning，没有重试状态。
- 仅用进程内 pending 集合屏蔽旧快照不能覆盖进程重启；重启后必须依据持久化业务配置判断快照是否仍属于当前刷新代次。
- 余额自动刷新在瞬时失败和租约冲突 fallback 中曾直接读取裸快照：清理失败后，旧 Key 的成功金额可能被复制并按当前刷新代次重新写回，或由人工刷新接口直接返回，从而绕过列表读侧 suppression。

## 修复方案

- 新增按账户 ID 去重的轻量重试 coordinator：保存路径只同步登记清理项，首次删除和失败后的最多 3 次幂等重试全部由同一个并发为 2 的队列执行，重试间隔为 0.25 秒和 1 秒。批量 100 个账户也只登记 100 个队列项，不在请求内 `Promise.all` 并发调用 stats-writer。
- 记录首次失败、每次失败、下次重试、成功和耗尽事件；运行态暴露 pending、running、suppressed、exhausted、成功数、失败尝试数和最后错误，并接入系统指标后台任务列表。
- 重试项携带保存完成时点，删除 SQL 只清理该时点及以前的快照，避免延迟重试误删之后成功刷新的新快照。
- 进程内 suppression 保存本次清理的 `updatedBefore` 截止点；读取端同时要求 stats `next_refresh_after` 与 business `balance_query_next_refresh_at` 完全一致。截止点及以前的旧快照继续隐藏；只有后续刷新写入的快照属于当前刷新代次且 `updated_at > updatedBefore`，才立即解除 suppression 并取消尚未开始的旧清理项，避免重试耗尽后永久遮住新余额。延迟删除使用互不重叠的 `updated_at <= updatedBefore` 谓词，因此同一毫秒边界不会一边放行、一边误删。
- 多 Key 禁用会持久化 `enabled=0/next=null`，重新开启会产生新刷新点，因此进程重启后即使内存 suppression 清空，旧快照仍因代次不匹配而不展示。
- 余额刷新服务的瞬时失败复用和租约冲突 fallback 统一读取带 `next_refresh_after` 的 record，并与本次 candidate 的 `nextRefreshAt` 校验；失配时分别生成不带旧金额的 `pending` 或返回 `refreshing`，禁止把旧 Key 金额重新写成当前代次。
- 单账户和批量编辑统一走同一 coordinator，不再存在吞错或平行清理策略。

## 下次遇到

- 先确认 business 配置是否已提交，再检查 stats-writer 删除事件和“AI 账户余额旧快照清理”运行态，不要把跨库副作用失败误报成主保存失败。
- 跨库派生数据清理不能空 catch；需要幂等、有限重试、状态和读侧失效规则。
- 读侧失效不能只依赖内存标记，必须有可在进程重启后重建的持久化代次或版本事实。

## 完成总结

- 完成时间：2026-07-14
- 结论：余额快照清理已统一为不阻塞保存的有界有限重试；旧快照受 cutoff 与持久化刷新代次保护，当前代次的新快照可自动解除 suppression，待生产发布后验证真实 stats-writer 故障日志和系统指标展示。
