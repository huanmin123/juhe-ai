## 问题概述

- 现象：`TestRunStorageBootstrapSQLiteEndToEnd` 自 2026-09-28 起稳定失败：`catalog rows = 117, want 118`。
- 期望：目录种子快照演进或模型 shutdown 日期到达时，断言自动适应，不产生假失败。
- 实际：断言期望值硬编码 `118`（2026-09-23 快照口径），被测侧统计的是按当前 UTC 日期过滤 shutdown 到期后的活跃行数；`gpt-3.5-turbo-1106`（ShutdownDate=2026-09-28）到期后两侧恒差 1，测试永久失败。
- 影响范围：仅测试（产品侧 shutdown 过滤逻辑正确）；持续污染 CI 信号，掩盖真实回归。

## 复现步骤

2. 观察失败信息 `catalog rows = 117, want 118`（当日稳定复现两次确认）。

## 根因分析

- 表象：行数断言差 1。
- 真实根因：断言期望值（硬编码 118）与被测口径（seed 按当前 UTC 日期只 upsert ShutdownDate 在未来的活跃行）不对称；原注释已预见过该风险（"行跨过退役日（下一批 2026-09-28 / 2026-10-23）时需同步更新此值"），但选择了硬编码人工维护，2026-09-28 预言成真。gateway 侧同名 helper 返回 `ModelCatalogRows`（本身即活跃过滤后计数，有 `TestActiveModelCatalogSeedRowCountMatchesSeed` 锁定等式），口径对称无炸弹，未改动。
- 为什么会发生：时间依赖断言把"某日快照"写成常量，日期推进即失效。

## 修复方案

- 修改点：`projects/maintenance/cmd/juhe-ai-maintenance/storage_bootstrap_test.go` 新增 `seedActiveModelCatalogRowCount` helper——在临时期望库上重放与被测 `runStorageBootstrap` sqlite 分支完全相同的 ensure+seed 出口（同一函数、同一默认墙钟），再执行与被测断言完全同一条 `SELECT count(*) FROM provider_model_catalog` 取计数；断言改为对比该同源对称值。
- 行为影响：无产品行为变化；未来任何 shutdown 日期到达（下一批 2026-10-23）两侧同步适应，不再分叉。
- 发布异常处理：不适用（测试缺陷）。
