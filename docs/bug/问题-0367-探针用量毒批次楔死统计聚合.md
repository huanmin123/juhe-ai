# BUG-0367：探针用量毒批次楔死统计聚合（空 systemAccountId 记录整批拒绝 → 队头永久阻塞）

- 级别：P1（统计面停摆 6.5h+，业务请求不受影响）
- 状态：首轮修复已上线（2026-11-17，v2026.11.17，commit `61559089b`）；根治第二层本地已实施、待发布（见 §根治补齐）
- 关联：#T210（事故主条目，发布后核验在此收口）、#T211（告警盲区收口）

## 现象

2026-11-17 09:33 CST 起 `usage-stats-aggregation` / `client-ip-stats-aggregation` / `account-quality-refresh` 全部跳过轮次（`jobsched_run_failed`：「使用记录 ingest 队列已有 N 次写入失败且仍有待处理记录，本轮跳过统计聚合」），统计游标卡死 `usage_stats_aggregation.last_success_at=01:33Z`（9:33 CST），lag 6.5h+；gateway 侧用量落库正常（673-1465 行/时）。用户于 15:5x 发现上报（无告警推送）。

## 根因链（四步）

1. **09:33 PG 瞬时抖动**：`probeUsageWriter.resolveScope`（`jobs/cmd/juhe-ai-jobs/worker_health_usage.go`）账户查询出错时**静默返回**（注释声称「账户已删除时跳过」，代码未实现），探针用量记录以**空 `SystemAccountId`** 入队；
2. `usagewriter.NormalizeUsageRecordInput` 无 `SystemAccountId` 完整性规则（gateway 路径恒有值，缺口从未暴露）；
3. PG 写入端 `rows.go` 硬校验缺失 `systemAccountId` **整批 1000 条拒绝**，每秒重试永远失败 → 队头永久阻塞（pending 1097 条、flushFailureCount 单边爬升 74→79+）；
4. `jobs/internal/ingestgate` 粘性门控（flushFailureCount>0 且 pending）→ 全部统计聚合跳过轮次。
生产核实：全库 0 条合法空 `system_account_id` 记录；磁盘 spool 文件全部合法——毒记录仅在内存队列。

## 修复（v2026.11.17）

1. `worker_health_usage.go`：`resolveScope` 三态化——`sql.ErrNoRows`（账户已删）→ 跳过补记（nil，无告警噪音）；查询错误 → 返回错误、**不入队**（上游 warn）；解析出空 owner → 拒绝。空 owner 记录绝不再进入队列。
2. `usagespooldrain`：spool 记录准入增加 `systemAccountId` 必填校验，毒文件走既有 `.corrupt` 隔离语义（保留现场、不阻塞后续文件）。
3. 平台归一化未动（避开 ~70 测试夹具），生产方入口双闸 + PG 校验兜底。
4. 测试：探针四态脚本驱动回归（跳过/查询错误拒绝/空 owner 防御拒绝/正常入队）+ drain 毒文件用例 + t207 durable 拒绝语义保留。

验证：jobs build/vet、usagespooldrain+ingestgate+usagewriter 包全量、cmd 定向全绿；上线后 flush 失败 0、门控跳轮 0、游标从 16:33 恢复推进并追平积压、usage 正常。

## 根治补齐（第二层，2026-11-17 本地已实施，待发布）

首轮修复堵住了已知毒源（探针作用域三态化 + spool 准入校验），但事故暴露出的两个通用根因层仍开放，任何未来生产者都可能复现同类停摆：

1. **`BuildWritePlan` 整批硬校验**：单条非法记录令整批 1000 条全部拒绝，队头永久阻塞；
2. **死信复用溢出 spool 目录**：`usagespooldrain.Drainer` 扫描同一目录树，死信被当作溢出记录回放重投——合法记录遇持续写库失败（FK/约束/数据损坏）时仍会形成无终态的「失败→死信→回放→再失败」无限环（事故证据：207 批死信、163,326 条次、spool 目录每 2 分钟抖动 450–1100 个文件）。

本次改动（`shared/platform/usagewriter` + jobs/gateway 组合根）：

- `BuildWritePlanIsolated`：逐条复用 `BuildWritePlan` 的校验与构造（单一事实源），非法记录收集进 `[]RejectedRecord{Input, Reason}`，同批合法记录照常成批写入；`BuildWritePlan` 保留「首错即整批失败」的历史契约，既有调用与测试不变。
- `Writer` 新增 `WithDeadLetterSpool` + `FileDeadLetterSpool`：写计划期非法记录与重试耗尽批次统一落死信终态目录 `<DATA_DIR>/usage-record-dead-letter/<instance>/`，文件名由 `usageRecordId` 派生（重复落盘同名覆盖，幂等，重试/重启不产生副本）；该目录**不在**回放扫描范围。死信**只认**独立目录，不再回退溢出 spool（回退即恢复无限环）；未注入时按内存终态计数与有界诊断样本处理。
- jobs `worker_assembly.go` 与 gateway `chain_usage_writer.go` 同时装配溢出 spool 与死信 spool（实例子目录分别 `jobs/`、`gateway/`）。
- 观测：新增 `usage_record_rejected_invalid` 日志（`usageRecordId`/`traceId`/`trafficSource`/`reason`）；死信文件保留完整 `UsageRecordInput` JSON，人工修正后可按文件内容重新入库。
- 回归：`TestBuildWritePlanIsolatedRejectsInvalidRecord`、`TestWriterIsolatesInvalidRecordAndKeepsValidOnes`、`TestWriterDeadLetterExhaustedRetryGoesToTerminalDirectory`、`TestFileDeadLetterSpoolIsIdempotent`；删除 SQLite 时代遗留的 `TestWriterSQLiteDefaultAcceptsEmptySystemAccountID`（断言的驱动分支已退役，且 `eventually` 超时不失败使其长期空跑）。
- 验证：`usagewriter` 全包（含 `-race`）、`usagespooldrain`、`ingestgate`、statsagg、jobs/gateway cmd 定向测试全绿；shared/platform、jobs、gateway 三模块 build 通过，`go vet` 定向通过。
- 运维边界：死信目录懒创建（无死信不出现），随 `data/` 纳管属主，无自动清理；**单机备份仅 PG dump、不含 `data/` 文件域**，磁盘级故障会丢失死信文件（已知取舍）。统计聚合门禁读取的 `activeDeadLetterCount` 与出队在同一临界区记账（先解除历史门控、再计本批隔离记录），单条隔离不会造成门禁永久阻断，也不存在「已出队但门禁为 0」的放行窗口。死信目录持续不可写（磁盘满/目录被删）时批次仍按 T207-C2 语义保留重试——该边界与溢出落盘失败同款，不在本次修复范围。多节点/cluster 形态各节点死信目录需分别人工收集（jobs 只回放溢出目录）。
