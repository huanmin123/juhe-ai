## 问题概述

本轮对最近 Node 变更与已迁移 Go 自定义模型 CRUD 进行对照时发现，Node 自定义模型路由和 repository 只按 `providerCode='gpt'` 判断是否允许 `supportedServiceTiers`、`supportedReasoningEfforts` 和 `defaultReasoningEffort`，导致 GPT 图像、音频模型也能保存文本请求能力。

期望行为是请求能力只属于 GPT 文本生成模型。显式空数组或 `null` 仍可清空能力，并允许随后把模型切换为图像或音频模式。

## 根因分析

- PLAN-0083 新增请求能力字段后，Node 校验只绑定到供应商代码，没有同时绑定模型模式。
- 路由层和 repository 各自维护一份能力边界，原有回归只覆盖 GPT 与非 GPT，没有覆盖 GPT 内部的 text/image/audio 模式。

## 修复方案

- Node 路由与 repository 统一要求 `providerCode='gpt'` 且模式为空、`null` 或 `text` 时才能保存非空请求能力。
- GPT `image`、`audio` 以及非 GPT 模型提交非空请求能力统一拒绝。
- 保留显式空数组和 `null` 的清空语义，避免能力存在时直接切换模式留下脏字段。
- 增加 GPT text/image/audio、清空后切换和 repository 直接写入保护回归。

## 防复发要求

- 新增模型能力字段时必须同时检查供应商、模型模式、路由 DTO、repository 直接调用和前端消费者。
- 清空能力与切换模型模式必须作为同一组状态转换回归，不能只测创建成功。

## 完成总结

Node 已与 Go 和前端目标契约统一自定义模型请求能力适用范围。供应商定义写接口、协议档案写接口、真实 PostgreSQL smoke、生产切流和 Node 删除仍按 PLAN-0081 后续门禁推进。
