- 关联计划：`docs/migration/Node全量清零迁移总计划-20260904.md`
- 关联 bug：无

## 问题概述

- 现象：K7 mock upstream 声称覆盖 16 个场景，但 `serve` 记录的请求事实只有 Method、Path、AuthHeader；结构体中声明的 Model、StreamField 没有填充或断言。
- 期望：mock 记录并校验模型、stream 等会改变协议和路由结果的字段，才能作为 Node/Go golden 的证据。
- 实际：即使模型映射或流式标志丢失，16 场景仍可能显示通过，无法发现关键请求契约漂移。
- 影响范围：后续 AI 网关整链迁移可能在错误模型、非流式/流式切换时产生漏测。

## 根因与证据

- 文件：`backend-go/shared/platform/mockupstream/mockupstream.go` 及其测试。
- mock response 的缓存头也与 Node 流式基线不同（`Cache-Control` 缺少 `no-transform`、未设置 `X-Accel-Buffering`），是否影响具体 golden 需在接线后确认。
- 现有测试只断言场景结果，不断言完整请求快照。

## 已确认子项：Go mock 不读取 OpenAI body 的 `stream` 字段

- 对照事实：Node 的 OpenAI mock 在读取 JSON body 后以 `body.stream` 决定 Chat/Responses 是否进入 SSE；标准客户端把 `stream: true` 放在 JSON 请求体中，不要求额外 query 参数或 `Accept` 头。
- 历史 Go：`serve2` 只检查 query `stream=true` 或 `Accept` 是否包含 `text/event-stream`，完全不解析请求 body 的 `stream` 字段。对 `POST /v1/chat/completions` 的合法 `{"stream":true}` 请求，若没有这两个辅助信号，会落入非流式 JSON 分支。
- 可观察结果：同一标准 OpenAI 请求在 Node mock 返回分块 SSE（含终止 `[DONE]`），Go mock 返回单个 JSON completion；网关的流式解析、首字节/中途断流和重试测试会被错误地当成非流式成功，无法发现真实协议偏差。
- 证据范围：Node 历史 `chat-gateway-mock-ai-regression.ts` 第 866–899 行先解析 body 并断言 `body.stream`；Go 证据为提交 `020888a7c` 的 `mockupstream.go` 第 147–168 行。该结论不依赖当前未提交工作区。
- 修复门槛：优先读取并校验 JSON body 的 `stream` 布尔值，再按 Node 兼容的 header/query 规则补充协议场景；增加仅 body `stream:true/false`、header 协商和冲突组合的请求/响应 golden。

## 已确认子项：流式 `slow_first_byte` 延迟被 Go 叠加两次

- 对照事实：Node 慢首字节 mock 在请求读取完成后只创建一个定时器，延迟配置时间后写入首个响应 chunk；首字节超时阈值应据此判断。
- 历史 Go：`serve2` 在识别 `ScenarioSlowFirstByte` 时先 `time.Sleep(m.slowDelay)`；若请求进入 SSE，随后 `serveSSE` 又在写首个 chunk 前再次 `time.Sleep(slowDelay)`。流式场景实际等待约 `2 * slowDelay`，非流式场景只等待一次。
- 可观察结果：相同 `slow_first_byte` 配置下，Node 可能刚好在首字节截止内返回，Go 却因额外延迟被误判为首字节超时/传输失败；重试次数、候选切换和质量样本会因此偏离，且测试结果依赖请求是否带流式标志。
- 证据范围：Node 历史 `gateway-quality-priority-real-sample-mock-ai-regression.ts` 第 503–531 行只在 slow 分支设置一次 timer；Go 证据为提交 `020888a7c` 的 `mockupstream.go` 第 106–112、225–227 行。该结论不依赖当前未提交工作区。
- 修复门槛：让每个请求只消耗一次首字节延迟预算，并补非流式/流式、零延迟和刚好跨阈值的耗时 golden；测试需断言首字节时间而非仅状态码。

## 已确认子项：Go Mock 缺少 `/v1/responses` 端点

- 对照事实：Node 的 `chat-gateway-mock-ai-regression.ts` 将 `/v1/responses` 与 `/v1/chat/completions` 一起作为合法 POST 入口，并按 `stream` 字段返回 Responses JSON/SSE 事件；Responses 是迁移总计划 §5.1 明确要求的 OpenAI 协议面。
- 历史 Go：`backend-go/shared/platform/mockupstream/mockupstream.go` 仅对路径后缀 `/chat/completions`、`/models` 和 `/embeddings` 做分支；`/v1/responses` 会落入未知路径并返回 404。16 场景测试也只请求 Chat Completions，没有 Responses 覆盖。
- 可观察结果：任何依赖 Responses 协议的 Go 网关、探针或 golden replay 都会收到上游 404，而历史 Node Mock 会返回合法 Responses 结果；因此协议选择、Responses JSON/SSE 解码、工具事件和失败归因无法得到等价验证，甚至可能被错误记录为上游账户故障。
- 证据范围：Node 历史 `backend/src/scripts/regression/chat-gateway-mock-ai-regression.ts` 第 852–899 行；Go 迁移提交 `020888a7c` 中 `mockupstream.go` 第 147–170 行；迁移总计划 `docs/migration/Node全量清零迁移总计划-20260904.md` §5.1/§5.2。结论不依赖当前未提交工作区。
- 修复门槛：增加 `/v1/responses` 的非流式 JSON、Responses SSE、工具/结构化输出及错误场景，并将请求体 `stream`、响应头和事件序列纳入与 Node 的 golden 对照；不能用 Chat Completions 的 404 代替 Responses 行为。

## 已确认子项：Go Mock 不校验上游 HTTP method

- 对照事实：Node 的 `chat-gateway-mock-ai-regression.ts`、`account-api-key-gateway-mock-ai-regression.ts` 等历史 Mock 在进入响应逻辑前均要求 `req.method === 'POST'`；Chat/Responses/图片等上游调用使用错误方法时返回 404。该 method/path 组合属于 golden 请求契约，而不是可忽略的实现细节。
- 历史 Go：`mockupstream.serve2` 只检查 `r.URL.Path` 后缀，未检查 `r.Method`。因此 `GET /v1/chat/completions`、`GET /v1/embeddings` 等请求仍会返回 200 业务响应；现有 `mockupstream_test.go` 的 `get` helper 甚至用 GET 验证 Chat Completions 成功，掩盖了这一差异。
- 可观察结果：被测 Go 网关即使把上游请求方法错误地改成 GET，K7 Mock 仍会返回成功，测试无法发现 method 漂移；历史 Node Mock 则返回 404 并进入上游失败路径。请求三元组中的 method 由记录字段保留，但响应结果已经被错误放宽，golden 对照不能成立。
- 证据范围：Node 历史 `backend/src/scripts/regression/chat-gateway-mock-ai-regression.ts` 第 852–854 行、`account-api-key-gateway-mock-ai-regression.ts` 第 1479–1489 行；Go 迁移提交 `020888a7c` 的 `mockupstream.go` 第 95–170 行及其测试 `mockupstream_test.go` 第 10–20、31–55 行。结论不依赖当前未提交工作区。
- 修复门槛：按 OpenAI 路径定义 method 白名单（Chat/Responses/Embeddings 等 POST，Models 按 Node fixture 的实际方法单独定义），错误方法必须返回与 Node 一致的 404/错误体；测试补充错误 method 的负例，不能继续用无 method 约束的 helper 作为成功基线。

## 已确认子项：Go Mock 使用过宽的路径后缀匹配

- 对照事实：Node 的 Chat Mock 只接受精确的 `/v1/chat/completions`、`/v1/responses` 等路径；其他前缀或拼接错误的路径在入口检查处返回 404。路径是网关请求 golden 的核心字段，不能仅比较末尾资源名。
- 历史 Go：`serve2` 以 `strings.HasSuffix(r.URL.Path, "/chat/completions")`、`"/models"`、`"/embeddings"` 判断分支，未限定 `/v1/` 前缀或完整路径。`/evil/chat/completions`、`/proxy/v1/models` 等非预期路径会进入成功响应分支。
- 可观察结果：被测网关即使错误地拼接了 upstream base URL、丢失或重复 `/v1` 前缀，K7 Mock 仍可能返回 200，无法暴露 path 漂移；历史 Node Mock 会返回 404 并进入失败处理。请求记录虽保留了错误路径，但测试默认只看状态/正文时会把错误调用当成成功。
- 证据范围：Node 历史 `backend/src/scripts/regression/chat-gateway-mock-ai-regression.ts` 第 852–854 行的精确路径白名单；Go 迁移提交 `020888a7c` 的 `mockupstream.go` 第 147–158 行。结论不依赖当前未提交工作区。
- 修复门槛：为每个支持的 endpoint 建立精确 method+path 白名单（query 参数按 Node fixture 明确定义），非白名单路径统一返回 Node 等价的 404；测试补充错误前缀、重复版本前缀和尾缀路径负例。

## 已确认子项：Go 请求录制丢失 query 参数

- 对照事实：Node Mock 以 `req.url` 记录上游命中路径，包含 query；query 是上游请求三元组的一部分，且部分协议/测试场景会用它控制 `stream`、版本或其他请求语义。
- 历史 Go：`serve` 写入 `Request.Path: r.URL.Path`，只保留纯路径，查询串完全丢弃；同一请求 `/v1/chat/completions?stream=true` 与 `/v1/chat/completions` 在录制结果中得到相同 Path。
- 可观察结果：Go 网关错误地添加、删除或改写上游 query 时，`Requests()` golden 无法发现；同时 harness 自身通过 `?scenario=` 选择场景，却不会把该选择记录到请求事实，回放报告无法重建实际 URI。
- 证据范围：Node 历史 `backend/src/scripts/regression/chat-gateway-mock-ai-regression.ts` 第 854 行记录 `${req.method} ${req.url}`；Go 迁移提交 `020888a7c` 的 `mockupstream.go` 第 51–58、95–104 行。结论不依赖当前未提交工作区。
- 修复门槛：录制完整 request-target（至少保留 `Path` 与 RawQuery，或存储等价的完整 URI），并补 query 存在、重复键和编码值的 golden；场景选择参数不能覆盖真实上游 query 的记录。

## 已确认子项：Go Chat SSE 的分片与 Node 结果不一致

- 对照事实：历史 Node Chat Mock 的成功流先写一个同时包含 `delta.role=assistant` 与首段 `delta.content` 的 chunk，再写一个 `finish_reason=stop` chunk，最后发送 `[DONE]`；客户端首个数据事件即可获得可见文本。
- 历史 Go：`serveSSE` 先发送 role-only chunk，随后拆成 `MOCK`、`-`、`STREAM` 三个独立 content delta，最后才发送终止 chunk 和 `[DONE]`。流事件数、chunk 边界、正文（`MOCK-STREAM`）均与 Node fixture 不同。
- 可观察结果：即使最终拼接文本都能被解析，首个可见 token 的事件时点、事件数量、usage/响应检查的分片行为和 golden 字节序列都会偏离；依赖首 chunk 内容或按事件计数的网关重试/观测逻辑可能得到不同结果，不能把该流当作 Node 等价结果。
- 证据范围：Node 历史 `backend/src/scripts/regression/gateway-quality-priority-real-sample-mock-ai-regression.ts` 第 585–600 行（`sendSuccess`）及 `chat-gateway-mock-ai-regression.ts` 第 918–923 行；Go 迁移提交 `020888a7c` 的 `mockupstream.go` 第 198–236 行。结论不依赖当前未提交工作区。
- 修复门槛：按协议/场景分别固定 Node 的 SSE 事件顺序、字段共现、正文和终止标记；测试至少断言首 chunk 内容、事件计数、拼接正文、usage 与 `[DONE]`，不能只断言“收到 SSE”。

## 已确认子项：Go Mock 不处理客户端中途取消

- 对照事实：Node 的账号测试 Mock 在延迟响应时监听 `res.close`/请求中止，记录 abort 并取消待执行 timer；客户端中途取消会停止后续响应写入，作为 exactly-once/499 语义回归的一部分。
- 历史 Go：`serve2` 的 `ScenarioSlowFirstByte` 直接 `time.Sleep(m.slowDelay)`，`serveSSE` 逐段 `fmt.Fprint` 且忽略写入错误；两处都不检查 `r.Context().Done()`，也没有取消/记录机制。客户端关闭连接后，handler 仍会等待并继续生成剩余响应。
- 可观察结果：取消请求可能仍完成上游 Mock 的全部脚本、消耗延迟和 CPU，测试无法确认取消是否及时透传、是否停止后续 chunk 或是否发生重复/迟到写入；与 Node 的 aborted exactly-once 结果不同，可能掩盖网关取消后的资源与重试错误。
- 证据范围：Node 历史 `backend/src/scripts/regression/account-test-mock-ai-edge-regression.ts` 第 346–382 行（`observeAbort`、`res.close` 与 timer cancel）；Go 迁移提交 `020888a7c` 的 `mockupstream.go` 第 106–110、198–236 行。迁移总计划 §5.2 将“客户端中途取消（aborted exactly-once、499 语义）”列为必测项。结论不依赖当前未提交工作区。
- 修复门槛：延迟和每次写入都必须受请求 context/连接关闭驱动，记录一次 abort 并停止后续脚本；补慢首字节、流中断和非流式延迟响应的客户端取消回归，断言无迟到 chunk、无重复上游完成和稳定取消归因。

## 修复与验证

- 修改点：记录并断言 Model、StreamField、关键 headers/body，补齐流式响应头 golden；将 mock 记录纳入 G3 对照报告。
- 当前验证：现有 16 场景不能证明模型/流式字段契约，未执行真实 Node/Go replay。
- 结论：K7 当前测试 harness 覆盖不足，不能作为整链迁移验收证据。
