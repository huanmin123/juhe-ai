## 问题概述

- 现象：Go 团队更新、成员维护和统一授权写入已经成功落库后，如果授权缓存失效发布失败，接口或 worker 仍返回失败。
- 期望：对齐 Node 当前共享失效契约。业务写入成功后仍触发缓存失效，但本地 handler 或 Redis runtime state 发布失败不能覆盖已提交的业务结果。
- 实际：旧 Go 直接传播 `InvalidateAuthorizationChanged` 错误，调用方可能把已生效的团队、成员或授权变更误判为未执行并重试。
- 影响范围：
  - 团队更新、成员新增和成员移除。
  - 授权创建、普通更新、有效期更新、grant 归还、资源页归还、回收和批量到期扫描。

## 复现步骤

1. 让团队或授权 store 成功完成业务写入。
2. 注入返回错误的授权缓存 invalidator。
3. 旧实现返回 invalidator 错误，但团队、成员、grant、授权来源或运行态授权已经更新。

## 环境信息

- 分支 / 版本：`feature/20260706-go`，W4 团队与统一授权 Go opt-in 阶段。
- 数据状态：PostgreSQL 写入成功，Redis runtime state 发布失败。
- 浏览器 / 系统 / Node 版本：不适用；服务层写后副作用问题。
- 是否稳定复现：是。

## 根因分析

- 表象：Redis 故障时团队或授权写接口失败，授权到期 worker 也可能把已过期记录误报为失败。
- 真实根因：Go service 把数据库写入后的缓存失效发布当成主业务返回值的一部分。
- Node 契约：`notifyGatewayRuntimeCacheInvalidation` 和 `notifyAuthorizationQuotaCacheInvalidation` 返回 `void`；本地 handler 错误记录 warning，Redis runtime state 发布异步捕获，不回滚或覆盖业务写入。
- 为什么会发生：迁移时保留了 Go invalidator 的 `error` 返回值，但没有在团队和授权 service 层恢复 Node 的 best-effort 边界。

## 修复方案

- 团队：
  - `Update` 仅在授权来源实际变化时继续发布 `team_authorization_changed`。
  - `AddMembers` 和 `RemoveMember` 继续发布 `team_members_changed`。
  - 三条路径忽略 invalidator 返回错误，但 store、输入、冲突和未找到错误保持原语义。
- 统一授权：
  - `Create`、`Update`、`Return`、`ReturnByResource`、`Revoke` 和 `ExpireDue` 继续使用原 reason 发布失效。
  - invalidator 错误不再覆盖已成功的 grant、source、runtime authorization、stats dirty 或到期扫描结果。
- 未改变：
  - invalidator 的 topic、reason、调用位置和调用次数。
  - PostgreSQL 事务、统计脏标记、operation log 和业务校验错误。
  - Go invalidator 自身仍返回错误，其他需要强一致失败语义的调用方不被本次修改。

## 下次遇到

- 先查什么：副作用发生在数据库提交前还是提交后，失败时主数据能否回滚。
- 重点看什么：Node 调用点是 `await`、返回错误还是 `void` / 异步捕获；Go service 是否错误传播了写后通知。
- 如何避免误判：不能只看接口错误，必须检查数据库最终状态、失效 reason、调用次数和调用方重试风险。

## 完成总结

- 完成时间：2026-07-10。
- 结论：Go W4 团队和统一授权已对齐 Node 的写后 best-effort 缓存失效边界，不再把已成功业务写入误报为失败。
- 后续建议：为 Go invalidator 增加统一日志或指标装饰器，保证 best-effort 失败可以观测；真实 PG/Redis 故障注入通过前不作为生产接管证据。
