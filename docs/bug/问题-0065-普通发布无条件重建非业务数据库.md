# BUG-0065 普通发布无条件重建非业务数据库

## 现象

旧生产升级脚本每次发布都会删除并重建 `juhe_dataset`、`juhe_usage`、`juhe_stats`、`juhe_codex_context`，同时清理整个 Redis namespace。即使本次只修改前后端代码或业务表，也会丢失非业务数据库中的明细、统计、监控和上下文数据，并增加重建时间和上线负载。

## 根因

升级脚本把一次需要统计/schema 重建的历史发布动作固化成所有发布的默认步骤，没有区分业务数据库迁移、非业务 schema 迁移、统计口径重建和普通代码发布。

## 修复

- 普通发布默认保留全部非业务 schema 和 Redis 数据，只执行明确提供的业务 migration、`schema-only` 校验、release 切换和稳定验证。
- 服务器正式升级脚本增加两个默认关闭的显式参数：`重建非业务库:0|1` 和 `清理Redis命名空间:0|1`。
- 只有发布明确修改对应 schema/统计口径、迁移方案要求重建且已完成备份和临时库验证时，才传入 `1`。
- 非业务数据库与 Redis 分开授权；需要重建非业务 schema 不等于允许清空 Redis queue/state。

## 验证

- release `20260712-1043-balance-ui-d0f5e7c87` 属于代码/API/前端发布，生产切换未删除或重建任何非业务 schema，也未清空 Redis。
- 发布后 PostgreSQL、Redis、完整进程拓扑、公网前端和 90 秒稳定门禁通过，原非业务数据保留。
- 生产主机 `juhe-ai-lite/bin/upgrade-main-release.sh` 已改为两个开关默认 `0`，并通过 `bash -n`。

## 下次遇到

- 发布前先列出本次受影响的数据域；没有 schema/统计口径变化时禁止执行重建。
- 业务 migration 只作用于明确目标，不能顺带清空数据集、用量、统计或上下文 schema。
- Redis cache、runtime state 和 queue 不能作为一个整体无条件清理；确需清理时必须单独说明范围和影响。
