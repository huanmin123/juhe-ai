# BUG-0322 审计日志列表实体名称显示为空或「已删除或未知」

- 级别/状态：P2（管理面展示缺陷，不影响 /v1 业务），已修复待发布
- 报告：2026-10-16，用户在生产审计日志页发现大量空信息与「已删除或未知」，质疑"都无法被请求怎么还能进审计"

## 根因

两层叠加，均为事实确认（本地隔离环境复现）：

1. **后端读链路只返回 ID 不返回名称**：审计读链路只持有审计库句柄（`logreads/audit_reads.go` `auditLogListItemFromRow`），列表 DTO 只含 `system_account_id` / `api_key_id` / `group_id` / `account_id` 四个 ID 字段，名称字段恒为空。这不是数据缺失——ID 指向的分组/账户在业务库中存在且活跃。
2. **前端展示函数对空名称无解析路径**：分组列 `displayAuditGroupName` 依赖 `groupLabelCache`，但该缓存只在名称已在列表数据上时被填充（后端不给名 → 永远 miss）→ 回退「已删除或未知」；账户/系统账户列 `displayName` 直接显示 `-`。401 未认证行四个 ID 全空，显示 `-` 是正确语义，但与失败行混在一起造成"一堆空信息"的观感。

## 修复（前端批量解析，2026-10-16）

与账户筛选既有 label cache 模式同构，最小闭环：

- 新增 `frontend/src/views/audit-logs/auditLogEntityLabels.ts`：列表/详情数据到达后，对缓存缺失名称的分组、AI 账户、系统账户 ID 收集去重，批量调用 `groups/options`、`accounts/options`、`system-accounts/options`（均支持 `ids` 参数，≤50/次），名称写回响应式行对象（写回即重渲染）并写入 `groupLabelCache` / `accountLabelCache` / `principalLabelCache` 供后续页面命中。
- 解析不到的 ID（已删除实体）记入跳过集合，翻页不再重复请求；单元格回退「已删除或未知」。请求失败不记跳过，下次重试。
- `auditLogFormatters.ts` 新增 `displayAuditAccountName` / `displayAuditSystemAccountName`（缓存感知，与分组列 `displayAuditGroupName` 同构）；`AuditLogList.vue` 桌面/移动端与 `AuditLogDetailDrawer.vue` 概览区改用。
- `AuditLogsView.vue`：records/hotSearchRecords/detail 三个观察点接入同一 hydrator。
- API Key 列：`api_keys` 无名称解析 options 接口，保持 `-`；补齐需先扩后端契约（未包含在本次）。

## 验证

- 单测 `auditLogEntityLabels.test.ts` 5 项：批量解析写回与进缓存、同 ID 多行写回、缓存命中不发请求、跳过集合、失败重试。
- `npm run typecheck` 通过。
- 本地隔离环境（sqlite + 独立端口）真实页面验证：失败行分组列「已删除或未知」→「默认 GPT 分组」、系统账户列 →「超级管理员」；401 行（无任何 ID）保持 `-`；`accounts/options?ids=` 契约实测返回 `{id, name}`。
- 复现时的排查干扰项：本地浏览器面板被遮挡导致 rAF 停摆，`ResponsiveDataList` 的 `DeferredRender`（`deferTableMount`）永不置 ready，列表区域空白——为环境假象，非本缺陷，真实用户页面可见时原生触发，未改动产品代码。

## 后记（2026-10-16 同日范围收窄）

用户复盘后裁决：本缺陷的空行主力（401 认证失败、无可用上游账户等）根本不该进审计——「没有请求到上游的情况不再记录，网关日志里有就行」。已实施收录范围收窄（见《原始审计日志设计》保存范围节）：preauth 拦截信封路径整体删除、`flushFinalizedAudit` 对 `gateway_failed` 且零上游尝试的 finalize 不投递、媒体任务面与 realtime 签发面两个本地短路面的最小审计一并删除。空行问题从源头消除；前端名称补齐对真实上游行仍然生效（账户被删后 ID 无法回溯名称的行才回退「已删除或未知」）。
