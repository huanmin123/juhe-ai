# BUG-0339 失败健康检查去重表以请求指针为键致请求体长期驻留

## 基本信息

- 编号：BUG-0339
- 状态：已发布观察中（2026-10-31 随 v2026.10.31 发布，提交 `3bdd3e8ac`；堆趋势观察见 W42）
- 严重程度：P1（生产 gateway 活堆持续增长，容器内存告警 firing）
- 发现时间：2026-10-27 起 W42 长跑观察，2026-10-30 定位根因
- 发现方式：监控（Prometheus `go_memstats_heap_alloc_bytes` GC 后堆底持续抬升 + `AppContainerMemoryHigh` firing）
- 模块：网关 / 后端
- 关联：W42（`docs/待办与阻塞事项.md`）、BUG-0313（同族堆内存观察）

## 现象

gateway 生产进程（2026-10-29 21:2x 启动）运行 15h 后 `heap_inuse` 峰值 2010MiB、
容器工作集 2.31GiB，`go_memstats_heap_alloc_bytes` 的 GC 后堆底从 38MB 单调抬升到
1039MB；`go_memstats_heap_objects` 3.2–5.3M 无趋势（排除对象数泄漏），表现为大块
缓冲驻留。活跃时段约 +230MB/h，按此速率 4–5h 触及 GOMEMLIMIT=3072MiB 软限。上一轮
长跑（26h）实测 heap_inuse 2.67GB，同源。

## 根因

`backend-go/projects/gateway/cmd/juhe-ai-gateway/chain_request_failure_health.go` 的
`chainRequestDispatchMarks` 用 `map[*gatewaypreauth.GatewayRequest]*list.Element` +
容量 4096 的 FIFO 做「失败请求健康检查已派发」去重：

1. **键是请求指针**：以 `*GatewayRequest` 为强键把整个请求对象（含
   `Body.RawBody` 完整请求体）钉在进程堆里，直到 4096 个后续失败请求才淘汰。
2. **量级吻合**：生产 15h 内有失败尝试的请求 517 个、审计体量 1215MB（均值
   2.4MB/请求），与活堆增长 ~1GB 精确吻合；实际条目数（517）远小于容量 4096，
   FIFO 淘汰从未发生，故只增不减。
3. **移植语义错误**：Node 原语义是 per-request Symbol/WeakMap，条目随请求对象
   回收；Go 侧用进程级强键 map 是错误移植。Go 无弱引用 map，正确的移植载体是
   请求对象自身的字段（标记随请求生灭），而不是进程级表。

## 修复

- `internal/gatewaypreauth/request.go`：
  - `GatewayRequest` 新增指针字段 `failureHealthCheckMark *requestFailureHealthCheckMark`
    （`mu sync.Mutex` + `dispatched bool`），`NewGatewayRequest` 构造即初始化；
  - 新增 nil 安全的 `RequestFailureHealthCheckDispatched()` / 
    `MarkRequestFailureHealthCheckDispatched()`（零值请求经包级 `sync.Mutex` 惰性补建）；
  - 指针字段使 `gatewaydispatch/candfilters.go` 的 `clone := *req` 浅复制（model
    override）与原请求共享同一标记，保持「同一逻辑请求只派发一次」。
- `cmd/juhe-ai-gateway/chain_request_failure_health.go`：删除
  `chainRequestDispatchMarks` 类型、构造器、`marks` 字段及 FIFO 逻辑；
  `DispatchRequestFailureAccountHealthCheck` 改为读/写请求自身标记，语义不变
  （非 gateway 流量与已派发请求直接 false；排队成功（非 Rejected）才标记）；
  `newChainRequestFailureHealthDispatcher` 签名保持不变（仅组装 outbox writer）。
- 测试：
  - 新增 `cmd/juhe-ai-gateway/chain_request_failure_health_retention_test.go`：
    per-request 标记语义、**`runtime.SetFinalizer` 验证标记后请求（含 2MB RawBody）
    可被 GC（防全局强引用回归）**、浅复制共享标记；
  - `w1_misc2_test.go`（`TestW1RequestDispatchMarksLRU` →
    `TestW1RequestDispatchMarksPerRequest`）、`w1_tails_sweep_test.go`、
    `w1_misc_pure_test.go` 三处旧 marks/FIFO 用例改写为新语义；
  - `chain_failure_health_wiring_test.go` 的
    `TestChainRequestFailureHealthDispatcherThrottle` 补断言：同一请求先经
    rejecting writer（nil db，input_unavailable）派发得 false 且不置位标记，
    换健康派发器后同请求仍派发成功（「rejected 不消耗标记」由真实 PG 用例
    直接覆盖）。

## 下次遇到

- 进程级 map/缓存以对象指针为键时，先问「键对象何时被回收」：无淘汰上限或上限
  远大于实际条目量时，等价于把对象及其传递闭包（请求体、响应体）整体钉在堆里。
- Node Symbol/WeakMap 语义移植到 Go 的正确载体是请求对象自身的字段（标记随请求
  生灭），不是进程级表；浅复制场景用指针字段保持共享。
- 堆内存增长且 `heap_objects` 无趋势时，优先用审计均值体量 × 窗口条目数与活堆
  增量做量级对账，可先于 pprof 锁定驻留源。
