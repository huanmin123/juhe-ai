# BUG-0170 K2 系统账户创建与管理结果不等价

## 基本信息

- 编号：BUG-0170
- 状态：已修复（残留验证项见「修复与验证」）
- 严重程度：P1
- 发现时间：2026-09-04
- 发现方式：自查（已提交 Git 历史审计、独立复审）
- 模块：后端 / 网关 / 系统账户 / 路由 / API Key / 迁移
- 关联计划：`docs/migration/Node全量清零迁移总计划-20260904.md`
- 关联 bug：BUG-0152、BUG-0169
- 责任人：待定

## 问题概述

- 现象：K2 Go system-account CRUD 只实现账户行的核心读写，遗漏 Node 创建账户时必须同时完成的资源初始化，并改变了 null、选项、PATCH 回执、审计与缓存失效结果。
- 期望：通过系统账户接口创建、清除或更新账户后的数据库资源、管理 UI 回执、操作日志和网关运行态应与 Node 一致。
- 实际：
  1. Node 在同一事务中创建 `system_accounts`、默认 groups、默认 route strategies、默认 API keys 和 chat API key；Go `AccountStore.Create` 只插入 `system_accounts`。新建账户不会获得 Node 默认可用的路由和密钥资源。【已修复，见进度记录 2026-09-05】
  2. `requestLimits:null` 在 Go 的 PATCH 解析中仍被映射为空结构，随后不会写入 SQL `NULL`，因此无法清除已有限制；`aiAccountLimit:null` 被改写为 `0`，Node 则归一化为 SQL `NULL`。Go profile 的 raw request-limits 读取和非空写入校验已在 `76c352987` 对齐，nullable 清除已在 `e3308eb38` 修复。【已修复】
  3. 历史 Go `/system-accounts/options` 曾把 `username` 作为 `name`，在同时提供 IDs 与 keyword 时忽略 keyword，并使用任意子串匹配；Node 返回 `display_name`、叠加两个过滤条件且只做大小写不敏感的精确/前缀匹配。上述 options 差异已由 `821cc210e` 修复。【已修复】
  4. 历史 Go PATCH 最终只返回 `id/updatedAt`，导致字段 delta 全部丢失；该回执差异已由 `6bc723f2b` 补齐非 nullable 变更字段（名称、角色、状态、改密标记、图像开关、AI 账户限制和非空请求限制），显式 nullable 清除由 `e3308eb38` 补齐；操作日志 scope/viewer 已于 2026-09-05 对齐（scope 记目标账户、patch 补 admin_managed_my_resource viewer）。【已修复】
  5. Node 在 status、image-generation 和 request-limit 变更后通知 gateway runtime 与 API Key validation cache，并在后者失败时反馈标志；Go 此前没有失效依赖或调用。【已修复，见进度记录 2026-09-05】
  6. description 长度、PATCH 密码最小长度等仍比 Node schema 宽松；此处不是 Go 取消 Node 人为并发限制，而是管理数据合法性和最终持久化结果改变。【已修复，见进度记录 2026-09-05】
- 影响范围：新用户创建后无法按 Node 默认路径使用管理资源；管理页出现错误名称或陈旧行；限制清除、禁用和策略变更不能可靠传播到网关；不合法数据可能进入业务库。

## 根因与证据

- Node 创建副作用：`backend/src/storage/system-accounts.repository.ts` 的 async create 在一个 client transaction 中依次调用 `ensureDefaultBuiltInGroupsForSystemAccountAsync`、`ensureDefaultRouteStrategiesForSystemAccountAsync`、`ensureDefaultApiKeysForSystemAccountAsync`、`ensureChatApiKeyForSystemAccountAsync`。
- Go 创建：`backend-go/projects/gateway/internal/authsys/store_accounts.go` 的注释和 SQL 都表明只插入账户行，并把关联资源留给未被调用的其他 slice。【2026-09-05 起改为 `DefaultResourceEnsurer` 注入，在 create 事务内执行四个 ensure（`authsys/default_resources.go`），生产组合根必装】
- Node options：同一 repository 查询 `display_name`；Go `ListOptions` 查询 `id,username,status`。
- Go null/回执/日志/缓存代码位于 `authsys/app.go` 和 `store_accounts.go`；Node 的管理路由与 repository 在 `backend/src/modules/system-accounts/`、`backend/src/storage/system-accounts.repository.ts`。
- 当前 Go 生产入口尚未装配 K2（BUG-0152）；本记录评估的是入口修复后 Go 实现本身仍会产生的确定性差异。

## 修复与验证

- 已完成切片：`821cc210e` 对齐 `/system-accounts/options` 的 `display_name`、IDs+keyword 联合过滤、去重和精确/前缀关键词语义，并加入 HTTP 回归测试。
- 已完成切片：`6bc723f2b` 补齐 PATCH 回执的非 nullable 变更字段；`e3308eb38` 补齐显式 nullable 清除（description/aiAccountLimit/requestLimits 置 NULL、回执 delta、`apiKeyValidationCacheInvalidationFailed` 字段占位）。
- 已完成切片（2026-09-05）：创建默认资源四件套纳入同一账户创建事务（`DefaultResourceEnsurer` + `SecretSealer` 窄接口注入，对照 Node ensure 函数逐字段）；patch 后 runtime + API Key validation 双通道失效（`AccountCacheInvalidator` 窄接口接 `internal/inval`，失败置 `apiKeyValidationCacheInvalidationFailed`）；操作日志 create/patch 的 scope 记目标账户且 patch 带 admin_managed_my_resource viewer；create/patch description `max(200)`、patch password `min(4)` 按 zod 语义（UTF-16 码元）返回 400 `系统账户参数无效`。附连带修复：Patch 的 no-op 判定移到 `mustChangePassword`/`imageGenerationEnabled`/`aiAccountLimit` 字段检测之后（Node 在全部字段求值后才判 no_op，此前这三个字段单独 patch 会被静默忽略）。
- 必需验证：SQLite 与 PostgreSQL fresh/upgrade 创建账户后资源集合断言（SQLite 已由 `TestCreateSeedsDefaultResources` 覆盖；PostgreSQL 与 fresh/upgrade 集成验证待入口装配后执行）；null 清除 golden（`e3308eb38` 覆盖）；options 联合过滤；前端列表增量更新；禁用/请求限制后跨实例 runtime 与 API Key cache 行为（单元层已覆盖双通道触发与失败标志，跨实例 Redis 传播待链路装配后验证）；操作日志目标可见性（scope/viewer 已有 HTTP 回归，可见性读路径归 F4/logreads）。
- 当前验证：`authsys` 定向测试（owner gate fail-closed、advisory lock SQL 渲染断言 + SQLite 单写并发、默认资源四件套、失效双通道、校验边界、日志 scope/viewer、miniredis captcha/login-guard）全部通过 `-race`；全模块回归仅剩并行 G20 chain WIP 的既有失败。

## 完成总结

- 结论：K2 system-account 管理已补齐创建默认资源、nullable 回执、操作日志 scope/viewer、缓存失效与 schema 边界；Go 入口仍须等唯一 owner 切换证据（BUG-0152/BUG-0169 门禁）才可下掉 Node。
- 残留：PostgreSQL 模式与 fresh/upgrade 场景的资源集合、跨实例缓存传播、前端列表增量更新需在入口装配后做集成验证。
