# BUG-0254 夜间档 PG 锁超时渐进恶化（F1 索引器连续失败 / F4 retention / stats 表锁窗口）

## 基本信息

- 编号：BUG-0254
- 状态：根因主链闭环（本地复现+生产分布取证）；修复方案 1 已实施（F1/F4 容错上调），方案 3 发布纪律已写入 runbook，待随下次发布上线并观察次日备份窗口
- 严重程度：P2（可用性降级：F1 运行日志索引滞后 + F4 retention 滞后 + jobs 个别任务超时；业务流量无 ERROR、无数据损坏）
- 发现时间：2026-10-01（发布后例行巡检）
- 发现方式：生产巡检（gateway/jobs 容器日志 + PG 服务端日志取证）
- 模块：jobs `internal/runtimelog`（F1 索引器/保留清理）+ PG 锁竞争面；关联 F4 operation-log retention、jobs projection 任务族
- 关联记录：runbook 2026-09-29 23:5x「PG lock timeout 逐日上升（26:1→29:195，集中 00-09 点，受害语句集中 juhe_dataset.runtime_log_index_owner_leases 行锁）」「F4 operation log retention lock timeout 21 次」；2026-09-30 01:05 postgres 内存调优上线的观察项

## 问题概述

- 现象 1（夜间档行锁）：F1 runtime-log-indexer 连续失败（2026-10-01 06:07-06:25 实测 consecutiveFailures 41→45，每 30s 重试），错误为 `canceling statement due to lock timeout (SQLSTATE 55P03)`、CONTEXT 指向 `runtime_log_index_owner_leases` 表 tuple 行锁；该表仅 1 行（lease_key=runtime-log-index-retention），HOT 更新链物理 tuple 已到 (0,53)。
- 现象 2（表锁窗口）：2026-10-01 07:14:58-07:15:11 `juhe_stats.usage_stats_totals` 表级 AccessExclusiveLock 等待 13.8s（PG log_lock_waits 实证），与 gateway/jobs 容器重启时序吻合；同窗口并发会话 AccessShareLock 等待 7s。
- 现象 3：F4 operation-log retention 同族 55P03（06:10/06:25 各一次）；jobs `account-list-availability-projection-maintenance` 一次 context deadline exceeded（7.5s）。
- 规模：近 8 小时 PG 服务端 55P03 取消 86 次；runbook 记录 09-26→09-29 从 1 次/天升到 195 次/天，时间分布集中 00-09 点。

## 复现步骤

- 无需人工复现：生产夜间档（00-09 点）持续发生；`docker logs juhe-ai-go-jobs | grep 'runtime-log-indexer'` 观察连续失败计数。

## 环境信息

- 生产单机（103.36.63.105），PG 17（compose 内置、shared_buffers=2GB 已调优）；jobs F1 侧 PG 会话 `SET LOCAL lock_timeout='2s'`（快失败设计，55P03 为其触发形态）
- 诊断增强（2026-10-01 已上线，保留）：`ALTER SYSTEM SET log_lock_waits = on` + reload——锁等待超 1s 记录 `process X still waiting ... / blocked by process Y`，为后续诊断提供持锁者身份实证（当前日志量极小）

## 根因分析（本地复现实证 + 生产分布取证，主链闭环）

**时间分布（生产 PG 日志 2026-10-01）**：00 点 11 / 01 点 4 / 02 点 3 / 03 点 5 / **04 点 25 / 05 点 24（峰值）** / 06 点 14 / 07 点 2（衰减）；09-30 同期零记录。04:10 正是每日 pg_dump 备份窗口（runbook：备份机 192.168.1.203 主动拉整库），峰值时段与其 2 小时级时长吻合。

**本地复现（dev PG 隔离 schema，四组实验全部命中）**：
- A1：长快照读（模拟 pg_dump 的 REPEATABLE READ + ACCESS SHARE）持锁期间，`ALTER TABLE ADD COLUMN IF NOT EXISTS` 加列 DDL 等锁 3.0s 后 55P03；
- A2：**列已存在的纯 no-op `IF NOT EXISTS` 同样被阻塞**（3.0s 后 55P03）——启动/ensure-schema DDL 家族在任何长快照窗口内全部锁死；
- B：行锁未提交事务 + 一条排队 DDL → **后续普通 SELECT（ACCESS SHARE）被锁队列传导阻塞**（55P03）——解释生产 07:14 窗口 AccessShare 等待 7s 的形态；
- C：生产同款租约 upsert（`BEGIN; SET LOCAL lock_timeout='2s'; INSERT ... ON CONFLICT DO UPDATE`）在行锁被占时 2.03s 后 55P03——与 F1 失败逐字对齐。

**修正后的因果模型**（区分两个独立现象）：
1. **04-06 峰值（主因：备份 IO 放大器）**——pg_dump 不持行锁、ACCESS SHARE 也不挡 DML，单纯的整库读 IO 压力把所有事务（含持锁事务）拖慢，锁持有时间分布右移，F1 的 2s lock_timeout 语句批量超时；dump 结束即自愈（07 点衰减）。昨天（09-30）同期零发生说明 dump 时长/负载波动是触发条件（取证点：203 备份文件每日时间戳与大小对比）。
2. **07:14 表锁窗口（次因：启动 DDL × 长事务）**——容器重启时序吻合；启动链 EnsureSchema/ensure-schema 的 no-op DDL（A2 实证会被阻塞）等 AccessExclusiveLock 13.8s，其排队请求反向阻塞全表读写（B 实证传导），期间 F1/F4 的 2s lock_timeout 全部打爆。
3. **00-03 零星（背景噪声）**：正常并发下的偶发锁竞争（每小时个位数）。

已排除：F1 索引/retention 自竞争（Indexer.Run 单 goroutine 串行）；F1 重试链自发 DDL（EnsureSchema 仅进程启动执行一次，main.go:161）；maintenance 常驻；孤儿长事务（采样仅瞬态）。

## 修复方案（方案 1 已实施 2026-10-01，用户授权裁决）

1. **F1/F4 容错（已实施）**：对齐 maintenance j3a/j3b 族先例（statement 30s / lock 5s）——F1 runtimelog（statement 5s→30s、lock 2s→5s、Go 侧租约 ctx 5s→15s）与 F4 operationlog（statement 10s→30s、lock 1s→5s；Go 侧 storeOperationTimeout 10s→35s、lease keeper 续租/获取窗口 5s→15s、producer Persist/Renew ctx 10s→15s）。Go 侧预算必须大于 PG 侧超时否则先取消而失效。F1 的 release/rollback 尽力而为窗口与 F4 迁移分支宽松预算、F3 auditlog（无 lock_timeout guard，不产生 55P03）均不动。两包测试全绿。
2. **备份错峰/限速**：pg_dump 加 `--rate` 或迁离业务敏感时段；203 备份机拉取限速。
3. **发布纪律（文档化）**：避免在 04:00-07:00 备份窗口发版/重启容器（启动 DDL 会被长事务/备份快照挡住形成全表锁窗口）。
4. 观测性增强（log_lock_waits=on）保留，用于次日窗口确认 dump 会话身份与持锁时长。

## 验证结果

- 本地复现四组实验全命中（dev PG，实验代码跑后即删，未入库）。
- 生产当前窗口 55P03 归零、五容器 healthy、业务流量 ERROR=0。
- 影响面：F1 索引/F4 retention 滞后 + jobs 个别任务重试；无数据损坏、无用户可见故障。
