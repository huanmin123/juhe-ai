# BUG-0254 夜间档 PG 锁超时渐进恶化（F1 索引器连续失败 / F4 retention / stats 表锁窗口）

## 基本信息

- 编号：BUG-0254

- 严重程度：P2（可用性降级：F1 运行日志索引滞后 + F4 retention 滞后 + jobs 个别任务超时；业务流量无 ERROR、无数据损坏）
- 发现时间：2026-10-01（发布后例行巡检）
- 发现方式：生产巡检（gateway/jobs 容器日志 + PG 服务端日志取证）

- 关联记录：runbook 2026-09-29 23:5x「PG lock timeout 逐日上升（26:1→29:195，集中 00-09 点，受害语句集中 juhe_dataset.runtime_log_index_owner_leases 行锁）」「F4 operation log retention lock timeout 21 次」；2026-09-30 01:05 postgres 内存调优上线的观察项

## 问题概述

- 现象 1（夜间档行锁）：F1 runtime-log-indexer 连续失败（2026-10-01 06:07-06:25 实测 consecutiveFailures 41→45，每 30s 重试），错误为 `canceling statement due to lock timeout (SQLSTATE 55P03)`、CONTEXT 指向 `runtime_log_index_owner_leases` 表 tuple 行锁；该表仅 1 行（lease_key=runtime-log-index-retention），HOT 更新链物理 tuple 已到 (0,53)。
- 现象 2（表锁窗口）：2026-10-01 07:14:58-07:15:11 `juhe_stats.usage_stats_totals` 表级 AccessExclusiveLock 等待 13.8s（PG log_lock_waits 实证），与 gateway/jobs 容器重启时序吻合；同窗口并发会话 AccessShareLock 等待 7s。
- 现象 3：F4 operation-log retention 同族 55P03（06:10/06:25 各一次）；jobs `account-list-availability-projection-maintenance` 一次 context deadline exceeded（7.5s）。
- 规模：近 8 小时 PG 服务端 55P03 取消 86 次；runbook 记录 09-26→09-29 从 1 次/天升到 195 次/天，时间分布集中 00-09 点。

## 复现步骤

- 无需人工复现：生产夜间档（00-09 点）持续发生；`docker logs juhe-ai-go-jobs | grep 'runtime-log-indexer'` 观察连续失败计数。

## 环境信息

- 生产单机（103.36.63.105），PG 17（compose 内置、shared_buffers=2GB 已调优）；jobs F1 侧 PG 会话 `SET LOCAL lock_timeout='2s'`（快失败设计，55P03 为其触发形态）
- 诊断增强（2026-10-01 已上线，保留）：`ALTER SYSTEM SET log_lock_waits = on` + reload——锁等待超 1s 记录 `process X still waiting ... / blocked by process Y`，为后续诊断提供持锁者身份实证（当前日志量极小）

## 根因分析（部分闭环，待续）

- **已排除**：F1 索引与 retention 自竞争（Indexer.Run 为单 goroutine select 串行，不可能并发持锁）；孤儿长事务（多次采样 pg_stat_activity 长事务仅瞬态毫秒级）；maintenance ensure-schema 常驻（无今日运行记录）。
- **现象 2 机制（高度怀疑，待确认）**：容器重启窗口的启动 DDL——maintenance schema 家族含 `ALTER TABLE ADD COLUMN IF NOT EXISTS` / `DROP TRIGGER` / `CREATE INDEX`（pg_schema_stats.go 对 usage_stats_totals），此类语句即使无实际变更也需表级 AccessExclusiveLock；若 jobs/gateway 启动链对高频写表执行同族 DDL，重启窗口即锁风暴窗口（对手为正在写入的长事务，等待 10s+ 反向阻塞全部 DML）。
- **现象 1 机制（未闭环）**：夜间档 `runtime_log_index_owner_leases` 行锁的对手方身份待 log_lock_waits 积累 `ShareLock on transaction <X>` 记录后反查持锁事务语句（07:17:01 已捕获一条：process 97901 等待 transaction 16658094）。
- 待验证方向：①夜间档持锁事务的语句与所属组件（用 log_lock_waits 新记录 + pg_locks/pg_stat_activity 联查）；②启动链是否执行 stats/dataset 域 DDL（rg jobs/gateway 启动 schema 路径），若是则评估跳过（已建表时）或 CONCURRENTLY 化；③stats 每秒 projection 写入与 F1 租约 renew 的锁队列相互作用。

## 修复方案

- 待诊断后定。已上线的观测性增强（log_lock_waits=on）不回滚。

## 验证结果

- 立案待修。当前窗口（容器重启后）55P03 已归零、F1 重新 started、五容器 healthy——问题为间歇性夜间档形态。
- 影响面评估：F1 索引滞后（运行日志检索面数据延迟）+ F4 retention 滞后（旧日志清理延后）+ jobs 个别任务重试；`/v1` 业务流量 gateway ERROR=0、无数据损坏、无用户可见故障报告。
