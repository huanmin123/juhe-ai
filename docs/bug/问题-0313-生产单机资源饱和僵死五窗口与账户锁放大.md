## 分层定性：整机用户态同时僵死 = 主机资源（磁盘 I/O + CPU）饱和

窗口期内三层面同时变慢，任何一个单点故障都无法解释：

- **PG**：`SELECT version()` 跑 25s、exporter 微秒级查询跑 15–35s、连接 ping（`-- ping`）跑 1.8–5.5s（17:01 实证，16:24 窗口内）。
- **Redis**：单线程事件循环被饿——`AUTH` 341ms、`INFO` 250ms（12:20）、`eval` 3.4s（12:41）、2.2s（15:40）、710ms（17:04），慢命令时间戳与窗口精确吻合（慢命令快照 jsonl）。
- **主机**：load1 飙至 **39.7**（4 核机），尖峰精确对准窗口结束点（12:43→39.7、15:43→27.9、17:07→26.3、18:05→16.7，积压释放风暴）与部分起点（09:59→5.7、11:17→15.5）；磁盘 sda busy 峰值 89%（10:35，窗口内）。

gateway 在 15:16/16:24 窗口几乎无 500（是完全不响应而非报错）；窗口起点无外部流量激增（请求量平稳 ~100–150 行/分钟），排除被打流量。

## 放大器：advisory lock 7001001 锁护航队（convoy）

`pg_advisory_xact_lock(7001001)`（`advisorylock.AccountListDirty`，账户列表可用性投影序列化锁）在窗口内被长期持有：

- 12:21–12:41：一批 37+ 个 jobs 事务排队后同时释放（护航队释放与 12:43 load 39.7 尖峰吻合）；
- 15:15:47–15:39:56：单个 jobs 事务等锁 **1449 秒**（窗口 15:16–15:40 与之精确吻合）；
- 13:05–13:08、16–17 时档另有 47 次锁等待事件。

持锁事务期间**没有任何慢语句**——事务是在锁内被主机资源饿死（空闲等调度），不是在跑大查询。资源饱和是根因，锁排队把"一个任务慢"放大成"账户路径（gateway preflight/J1/J3b）全停"。

## 复发与根因修正（2026-10-14，重大更新）

**10-13 晚间治理后次日复发且更重**：11:51–13:48 两入口同窗不可用（探测 101 分钟；journal 持久化显示上一 boot 最后日志 **12:13**——此后连内核日志都写不出，整机冻结至用户 13:48 强制重启）；当日 ICMP 亦丢 12 点（10-13 全天 0）。exporter 全表扫修复在线但未根治——证明它只是放大器之一。

**根因修正（cAdvisor 逐容器内存历史实证）**：**内存容量不足才是本源，I/O 饱和是其症状**。

- `juhe-ai-go-gateway` RSS 从 10-13 晚 1.9GiB 爬至 **3.56GiB（11:50 达峰，与僵死开始精确吻合）**；上午反复充气至 ~3.3G 又回落（GC 周期），11:30 后最后一次爬升未能回落。
- **排除泄漏**：goroutines 全天平坦（均值 62–107、峰值 130，在文档基线内）、threads 恒 17——纯流量高峰下的 Go 堆膨胀（默认 GOGC=100 下 RSS≈2×活跃堆）。
- **并发画像（Loki 网关日志，11:20–12:20 窗口，利特尔法则）**：完成请求 650 个/小时（均值 10.8/分钟，最忙分钟 49），时长 p50=7.7s、p90=41s、**max=446s（7.4 分钟流式）**，60% 超 5s；平均并发仅 **~3.1**（最忙分钟估算 15–20 在途）——**低并发 × 单请求"又长又肥"**（每条在途流式请求累积完整响应+上下文体+快照缓冲，MB 级/个）×GC 2 倍系数 = 3.5G RSS。并发不高恰好支持 GOMEMLIMIT 方案：堆可压（GC 多跑换内存），非性能刚需。
- **每请求内存有界性核查（代码实证，回应"卡住用户滞留大数据"疑云）**：①请求体单条 ≤16MiB、全机在途 ≤256MiB 预算（`gatewaybody` admission 超出即拒）；②流式响应三协议 `StreamInspector` 均为增量解析，只存计数/用量/未完结事件（未完结行与单事件均受 256KiB 上限约束），单行/单事件超限自动 skip，**不攒完整响应**；③流式管道捕获三件套**硬上限与时长无关**（`gatewayresponse/pipe.go`：responseCapture/upstreamCapture 各 `StreamAuditCaptureBytes=1MiB` + diagnosticCapture 256KiB，`LimitedCapture` 超限丢弃标记截断）——一条 2 分钟的流式请求捕获层最多 ~2.25MiB；④非流式路径整读响应但 finalize 即释；⑤relay 为 32KB 流式缓冲；⑥审计 payload offload+快照截断；⑦路由观测 store 纯计数器。**无"卡住越久攒越多"的无界路径**：一条 2 分钟流式请求的内存足迹 ≈ 请求体 + 常数 2.25MiB。3.5G RSS 的构成 = 活跃堆 + GOGC 空隙 + Go 归还 OS 惰性（时间线 3.3G→2.06G 的放气证明可回收），冻结时 GC/scavenger 被饿死停在某点。并发预算推算：20 并发活跃堆 0.3-0.6G→RSS 0.6-1.2G（限值内无忧）；50 并发在途体撞 256MB 预算（既有保护拒绝超额）+活跃堆 ~1G→RSS 贴近 2.3G 限值（GC 加频可感知、mem_limit 3g 兜底无僵死）；已知浪费点=流式管道每 chunk 双重解析+字符串拷贝（BUG-0247 登记"大流量再优化项"），并发 50 时建议排期。**修复分级（2026-10-14 评估）**：Tier 1=消拷贝（`PushChunk` 的 `string(chunk)` 转字节级逐行扫描 + 每 chunk 双 `Snapshot()` 合一，约半天，行为零变化、三协议契约测试护航）；Tier 2=解析共享（拦截层已解析事件经 `PushParsedEvent` 喂 inspector，约一天+）——正确性边界：inspector 必须看到**最终下发字节**（加密恢复等拦截层会改写 chunk，改写路径须退回字节解析），故 Tier 2 需改写/未改写分流逻辑。触发信号：持续并发 ~50 档或 GC CPU 占比抬升，先 Tier 1 后视情况 Tier 2。
**Tier 1 落地（2026-10-14 当日）**：①三协议 `StreamInspector.PushChunk` 去整块 `string(chunk)` 拷贝，pending 行改 `[]byte` 缓冲容量跨 chunk 复用（openai 侧额外消除跨 chunk 未完结行 `string +=` 的 O(n²) 串接——长事件分片到达时原先每片全量重拼；openai 超限前缀截断/滚动尾窗、anthropic/gemini 每分段剥 `\r` 语义逐分支保形）；②快照 `PendingEvent` 判定改 `gatewayproto.HasPendingSseProtocolEventBytes` 字节前缀比较（原先 anthropic/gemini 每次 `Builder.String()` 复制整行）；③`OpenAIStreamInterceptor` pending 由 `bytes.Buffer` 改 `[]byte` + `consume` 原地前移（消除每事件一次 make+copy）；④pipe.go 每读一次的 `inspector.Snapshot()` 加 `Intercepted != nil` 守卫（nil 决策时 `handleInterceptedBeforeWrite` 直接返回，出站循环逐 chunk 快照已覆盖全部消费点；空 chunks+nil 决策时检查器状态未变，旧快照等价）。每事件一次的 `ParseSseEventText(string(...))` 保留——`RawText` 是策略匹配契约（`match.RawTextIncludes` 消费）。
**行级上限补齐（BUG-0314，2026-10-14 同日）**：Tier 1 保形复核发现 anthropic/gemini inspector 的未完结行缓冲缺行级上限（256KiB 限制只在完整 `data:` 行进入 `processLine` 后生效，持续无换行输入可无界累积，与本节"不攒完整响应"结论冲突）；已按 openai 侧 `streamInspectorMaxLineBytes` 同值补齐——`pushBytes` 在 append 前检查、超限即整流跳过（复用既有 `*_stream_event_too_large` 原因）并释放缓冲；两包新增持续无换行有界与边界红绿用例，五包全量 + `go vet`/gofmt 绿（详见 BUG-0314 文档）。
**Tier 2 证据修正（2026-10-14 深挖后定性：非纯优化，属关键路径重设计，维持不合并）**：①三个 inspector 的超限/跳过语义**只存在于字节路径**——openai 行 256KiB 前缀截断+事件 512KiB 超限分类（`appendPendingLineSegment`/`processOversizedLine`/`markOversizedEvent` 全链），anthropic/gemini 事件 256KiB→`Skipped`；`PushParsedEvent` 入口绕过全部大小记账，直喂等于改变超限行为（usage 尾窗正则回收、skip 后停解析都依赖字节路径）。②拦截器恒为 OpenAI 形状解析器（`mountResponseInspectionInterceptor` 不分 driver），双协议 inspector 走各自 `ParseSSEEventData`，共享解析需协议感知改造。③保守分流（仅小事件走事件通道）需行级字节扫描判定安全性，抵消收益。故双重解析为两层固有成本（拦截层出语义帧、inspector 出检查态，各一次 JSON 解析），仅当持续高并发实测 GC CPU 占比抬升时再立项统一解析器（须保大小语义 + 新旧等价性黄金流测试）。验证：gatewayproto/gatewayopenai/gatewayanthropic/gatewaygemini/gatewayresponse 五包 + cmd 主包全量（1174.6s ok，注意默认 10m 超时不够、需 -timeout 25m）+ cmd acceptance 全绿、`go vet` 干净。
- 8G 机算术：gateway 3.5G + PG 3.0G + 系统/其余 ≈ 7.2GiB working set → 页缓存归零 → 全部读穿透磁盘（10-13 观察的 I/O 饱和即此）→ 无 swap 可退、OOM 未及触发 → direct reclaim 风暴全员 D 状态 → 冻结。
- 客服"内存不足大量使用 swap"诊断：**方向正确、机制不准**——本机无 swap 设备（已实证），僵死机制是页缓存驱逐 + direct reclaim 活锁，非 swap 抖动。
- **排除审计日志**：F3 审计采集为有界队列（满即丢弃计数，`auditlog/producer.go`）、payload 落库 offload、请求体入口有全局在途字节预算（`gatewaybody` BodyInFlightMaxBytes）——审计路径全有界，非内存大头。

**治理（2026-10-14 当日上线）**：①4G swapfile（`/swapfile`，fstab 持久，`vm.swappiness=10` 仅作耗尽兜底——下次有现场、不再无差别冻结）；②`vm.min_free_kbytes=262144` + `vm.watermark_scale_factor=125`（提前回收防 D 状态活锁）；③gateway `GOMEMLIMIT=2300MiB`（compose 固定值，GC 封顶 RSS≈2.5G）+ `mem_limit 3g`；④jobs `mem_limit 1g`；⑤PG 有意不设限（强杀代价大于收益）；⑥采样器补内存维度（mem_avail/swap_used/psi_mem）。compose 契约已同步 `docker/single-server/README.md`「容器内存治理」节，仓库与现网 compose 逐字一致。

**观察口径**：治理后首个完整高峰日（GOMEMLIMIT 生效首个白天）无僵死窗口 + 基线 load 无显著抬升（GC 加频的 CPU 代价）即判定闭环；若 gateway 在 2.3G 限值下高峰期出现明显 GC CPU 挤占或业务延迟抬升，则升级内存（8G→16G）为最终解。

**设计评估存档（2026-10-14 用户提议"捕获缓冲内存→硬盘"）**：不采纳。捕获缓冲为请求级短命有界缓冲（≤2.25MiB/条，请求结束即释），非长期存储——耐久副本本已落盘（audit blob offload/spool/segments）；并发 50 时搬盘仅省 ~112MB（GOMEMLIMIT 预算内零头），代价是给全机最缺的磁盘 I/O 再加每流实时写（两次事故元凶即 I/O 饱和）+ 每请求盘文件生命周期管理（文件泄漏 bug 高发区）。若未来并发升级，杠杆顺序：调小 `StreamAuditCaptureBytes`（1 行常量）→ 修 BUG-0247 双重解析 → 扩内存。

## 教训（固化）

1. **监控自身的成本必须计入被监控系统的预算**：对告警数据源查询的表规模增长要有容量视角——`background_task_runs` 30 天稳态 2GB 的事实没有传导到 60s 全扫它的 queries.yaml。新增/巡检 exporter 自定义查询时，用 `pg_stat_statements` 看 mean/calls 与表规模对照。
2. **"整机同时变慢 + ICMP 正常 + 容器全 healthy"= 主机资源饱和指纹**：单看任一组件日志都会误判为该组件故障；三角取证（PG 慢日志 + Redis 慢命令 + 主机 load/PSI）交叉对时才能定性。
3. **锁护航队是资源抖动的放大器**：事务在锁内被饿死会无限期持锁（本例 24 分钟），把秒级抖动放大成 25–76 分钟账户路径全停。间歇性锁等待 + 无慢语句持锁者 = 往主机资源层找根因。
4. **事后取证对资源型故障天然无效**（瞬时采样零锁等待、慢日志只见受害者），窗口期实时采样（pg_stat_activity + blocking_pids + PSI 逐分钟）才是定案工具——本次采样器上线 3 分钟即活捉主推手。
