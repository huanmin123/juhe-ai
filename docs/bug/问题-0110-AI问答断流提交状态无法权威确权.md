# BUG-0110 AI 问答断流提交状态无法权威确权

## 基本信息

- 编号：BUG-0110
- 状态：已修复（完整回归、真实模型、断网恢复与浏览器验证）
- 严重程度：P1
- 发现时间：2026-07-14
- 发现方式：本地真实页面发送与多 Agent 复查
- 模块：前端 / 后端 / AI 问答 / 幂等 / 断流恢复
- 关联 bug：BUG-0109
- 责任人：Codex

## 问题概述

本地 AI 问答发送时出现“暂时无法确认消息是否已提交，已暂停新的发送并将在后台重试”。现场服务在请求期间没有监听，POST 和后续权威读取都未到达后端；聊天库中没有消息、幂等登记或活动轮次，因此本次实际未提交。

原保护逻辑避免未知状态下重复计费，方向正确，但只通过最近 100 条消息查找 `clientMessageId`：长预检尚未落库时可能被误判为未提交，持续确定性错误可能无限锁住输入，页面重载会丢失待确认草稿；服务重启后已经落库的 streaming 轮次若丢失进程内句柄，stop 也无法立即收口。

## 根因分析

- 本次直接原因是开发服务所在终端被关闭，worker 和 DB service 以 Windows `0xC000013A` 退出；停机窗口没有 `/stream` trace，不是模型或上游错误。
- 后端准备门禁只保存会话级 `symbol`，没有 owner 和 `clientMessageId`，无法公开 preparing 状态。
- 前端下载最近消息列表做幂等反查，既不是单一事实接口，也受 100 条窗口限制。
- 单次成功但空的消息列表会在有界轮询末尾确认“未接受”，与仍在进行的慢预检存在竞态。
- 待确认状态只在 Vue 内存中；刷新会丢失 `clientMessageId` 和已清空草稿。
- orphan streaming 只依赖较晚的维护恢复，stop 没有数据库权威兜底。
- 初版修复复查时还发现 stop 只按会话会误停新轮次、preparing 不能取消、accepted 可被后续假阴性降级、POST 前仍有未持久化窗口，且全局 sessionStorage key 会在同标签页切换账号时泄露上一账号草稿。
- 最终复查进一步发现：accept 已提交但活动流尚未登记时 stop 与原请求可能同时继续；早期 close 监听安装过晚；PostgreSQL stop 与 finalize 锁序相反；sessionStorage 不可写或 getter 抛错时仍可能发送或锁死；待确认状态的停止按钮没有可用目标；accepted 事实没有跨后台确权轮次继承；首屏外会话定向读取 5xx 后可能在 composer 不存在时清理快照。
- 加严真实图片测试后还发现，图片观察任务把用户当轮“不要转录”误当成提取规则，导致隐藏说明 OCR 丢失关键代号；旧测试可从可见助手正文回忆，因此形成假通过。

## 修复方案

- 新增 `GET /conversations/:conversationId/submissions/:clientMessageId`，返回 `preparing`、`accepted` 或 `not_found`；accepted 携带 `turnId` 和助手状态。
- 会话准备 claim 记录 owner 与 `clientMessageId`，并在长预检前登记；状态接口先查幂等表，再查进程内准备状态。
- 前端连续三次 `not_found` 且跨越 1 秒 grace 后才恢复草稿；preparing 自动确权只等待；accepted streaming 调用 stop 并持续查询到终态。
- 网络、408、425、429 和 5xx 重试，确定性 4xx 立即收口；后台轮询使用最高 15 秒的指数退避。
- 待确认请求和 Tiptap JSON 快照在 POST 前持久化，重载后继续同一 `clientMessageId` 对账。
- stop 在没有进程内句柄时通过 repository 事务校验期望 `turnId`，将匹配的孤立 streaming 助手消息原子收口为 canceled。
- stop 改为携带 `clientMessageId` / 期望 `turnId`：preparing 取消会中断当前请求等待并禁止继续进入流式上游；已启动的共享压缩任务仍按 CAS / 租约自行完成或失效，不把“停止等待”误写成物理取消底层任务。已接受轮次由 repository 事务原子条件取消；旧 turn 不会误杀新 turn，并发 stop 幂等返回。
- accepted 状态改为单调事实；`not_found` 需连续三次并跨越 1 秒，临时错误会重置负向计数；终态消息列表刷新成功前继续保持门禁。
- SSE `message.started`、持久化 `startedTurnId` 和上一轮后台确权得到的助手状态都会作为下一轮 reconcile 的初始 accepted 事实；`not_found`、preparing 和临时错误不能跨轮降级。
- 请求上下文在 POST 前写入按 `systemAccountId` 分区的 v2 sessionStorage；写入失败或浏览器禁止访问存储时本轮不发送并恢复草稿。恢复会话超出首屏 50 条时按 ID 定向加载，临时 5xx 继续保持全局门禁，只有 404 才清理；跨账号和跨会话均不恢复草稿。
- stream 路由在首个数据库等待前监听断连；accept 成功后同步登记活动流，再把上下文读取、SSE、上游请求和终态写入纳入统一 try/finally，异常不能留下孤立 streaming。
- stop 与 complete / fail / cancel 统一按“会话行 -> 助手消息行”加锁；条件更新落空重读权威终态，真实 PostgreSQL 双连接强制交错不再出现 `40P01`。
- 待确认或 preparing 状态的停止按钮从持久化请求恢复 `clientMessageId` / `turnId`，停止后继续权威确权；普通 disabled 状态不再显示无效停止按钮。
- 首屏外 pending 会话每轮后台确权前都会重新定向加载并强制选择；会话暂时不可用时，即使 submission 已是 not_found 或 terminal 也只保存事实并重试，原会话 ready 后才恢复草稿或应用消息，明确 404 才清理。
- 图片隐藏说明把用户问题和可见回答包装为不可执行参考上下文，系统指令强制客观保存所有可辨 OCR；真实测试要求首轮可见回答不含代号、历史投影含隐藏代号且不含 Data URL，下一轮仍能回忆。

## 下次遇到

- 先按 trace 判断 POST 是否真正进入后端；没有 trace 时不要把网络停机误判为上游模型失败。
- 幂等确权必须查询小型登记或专用状态接口，不能扫描最近消息窗口。
- preparing、accepted streaming、terminal 和 not_found 是不同事实，不能压成一个布尔值。
- 防重复门禁必须跨页面重载保持，且 orphan stream 要有数据库权威收口路径。
