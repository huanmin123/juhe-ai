# BUG-0034 审计保留清理单批删除长尾

## 基本信息

- 编号：BUG-0034
- 状态：已生产热修，源码已修复
- 严重程度：P2
- 发现时间：2026-07-05
- 发现方式：生产后台任务异常、PG 活动采样与 `pg_stat_statements`
- 模块：后端 / worker / 存储 / 审计
- 关联计划：无
- 关联 bug：BUG-0033
- 责任人：待定

## 问题概述

- 现象：生产后台任务页显示 `audit-hot-retention-cleanup` 多次失败，错误为 `canceling statement due to lock timeout`；数据维护 ingest 出现写入失败。PG 侧可见 `DELETE FROM juhe_dataset.audit_log_attempts WHERE audit_log_id = ANY(...)` 长时间运行。
- 期望：审计保留清理可以慢慢追赶，但不能形成大事务长尾、IO 尖峰或被误判为管理端读接口被写锁阻塞。
- 实际：`audit_log_attempts(audit_log_id, attempt_index)` 索引存在，但 `audit_payload_refs.attempt_id` 外键反查索引缺失；删除 `audit_log_attempts` 时 PostgreSQL 为维护 `audit_payload_refs.attempt_id -> audit_log_attempts.id ON DELETE SET NULL` 反复扫描 `audit_payload_refs`。
- 影响范围：后台维护吞吐、PG IO、record-maintenance Redis Stream pending、生产排障判断；当前未观察到主服务不可用。

## 复现步骤

1. 在生产高性能模式下等待审计保留清理任务运行。
2. 采样 `pg_stat_activity`。
3. 观察 `juhe-ai:worker:ingest-worker` 是否出现审计相关 `DELETE` 长事务。

## 环境信息

- 分支 / 版本：本地工作区；生产仍停留在 `20260705-214545-table-monitor-overview-hotfix`
- 数据状态：`juhe_dataset.audit_logs` 约 24 万行，`audit_payload_refs` 约 89 万行；生产 `audit_payload_refs.attempt_id` 当前全为 `NULL`，但缺少部分索引仍会导致外键触发器反查扫描。
- 是否稳定复现：取决于保留清理触发和过期数据量。

## 根因分析

- 表象：`audit_log_attempts(audit_log_id)` 已有索引，但删除仍可达到秒级甚至超时。
- 真实根因：`audit_payload_refs.attempt_id` 外键引用 `audit_log_attempts(id) ON DELETE SET NULL`，但 schema 没有为 `attempt_id` 建索引。删除父表 `audit_log_attempts` 时，PostgreSQL 外键触发器必须查引用表；缺索引导致对 `audit_payload_refs` 的反复大范围扫描。
- 证据：生产 `pg_stat_statements` 中 `DELETE FROM juhe_dataset.audit_log_attempts WHERE audit_log_id = ANY($1::text[])` 累计 `1542` 次、总耗时约 `2504569.9ms`、均值 `1624.23ms`、最大 `145083.3ms`，`shared_blks_hit=239043501`；`audit_payload_refs.attempt_id` 非空行数为 `0`，创建部分索引后探测计划命中 `Index Only Scan using idx_audit_payload_refs_attempt`。
- 次要触发：每分钟 `audit-hot-retention-cleanup` 和 `record-maintenance:audit_retained_data_cleanup` 会清理同一组审计表，旧版本还会按大批次追赶，放大锁等待与长事务窗口。

## 修复方案

- 修改点：
  - 生产在线 DDL：新增 `idx_audit_payload_refs_attempt ON juhe_dataset.audit_payload_refs(attempt_id) WHERE attempt_id IS NOT NULL`。
  - `backend/src/storage/schema/dataset-schema.ts`：补齐 `audit_payload_refs.attempt_id` 外键反查部分索引。
  - `backend/src/storage/audit-log-retention.repository.ts`：PG 审计日志保留清理单轮候选硬上限 `100`，删除子批次 `10` 个 audit id 一个短事务；错误分组清理按 `25` 条 id 分块删除。
  - `backend/src/storage/audit-log-payload-blobs.ts`：PG 审计 payload blob 元数据删除按 `25` 条 id 分块执行，避免候选 blob 较多时形成单条大 `DELETE` 长尾；文件删除继续使用异步并发上限。
  - `backend/src/modules/record-maintenance/record-maintenance-queue.service.ts`：审计保留任务限制单次 `batchSize <= 100`、`maxBatches <= 3`，满批后增加短暂停顿。
  - `backend/src/modules/background/maintenance-cleanup-jobs.ts`：PG 高性能模式跳过每分钟 `audit-hot-retention-cleanup` 直接清理，审计保留只走 record-maintenance 小批路径。
- 行为影响：统计和审计写入准确性不变；保留清理允许延后追赶，不丢数据，不提前删除未过期数据。生产已对当前 release 做 dist 热修，后续正式发布包必须包含源码修复。
- 发布异常处理：如果下版本上线后清理追赶慢，优先观察 record maintenance 队列、过期审计剩余量和 PG IO；不要回退为大事务删除。
