# BUG-0327：统计窗口全量重建周期性刷出 WAL 洪水（磁盘 I/O 风暴、PG commit 秒级卡顿）

- 状态：已修复（2026-10-17，jobs 侧交付待发布）
- 级别：P1（生产 PG 磁盘 I/O 风暴、checkpoint 失守、commit 卡 10s+，直接拖垮 /v1 与管理面尾延迟）
- 发现：2026-10-17 生产 PG 性能取证（`pg_stat_statements` + WAL 汇总 + PSI 采样 + 脏表现场核查）

## 现象（生产证据）

- WAL 体量与写频：统计窗口约 44.5 GB、323,807 次 INSERT 记录集中在两个 5 分钟周期任务；`usage_overview_*_windows` 四表的 `DELETE` mean 1736 ms，整轮"全表 DELETE + 约 36 万行重插"每 5 分钟重放一次。
- checkpoint 失守：观察窗口 425 次 checkpoint 中 378 次由 `wal` 达标（而非 `time`）触发，WAL 生成速率持续顶满 `max_wal_size`。
- 主机压力：磁盘 I/O `io_full` PSI 峰值 80–90%，呈周期性风暴形态；PG commit 观测最差 11.4 s，业务 /v1 与管理接口尾延迟同窗口劣化。
- 脏表空转：`usage_overview_dirty_scopes` 与 `ai_performance_summary_dirty_system_accounts` 生产各 53 行（≈全部账户，最老 2026-09-26）从未被消费——聚合器一直在写标记，窗口刷新侧没有任何读取方，两个任务始终走全量重建。

## 根因

结构性根因是"窗口表全量重建"与"脏标记无人消费"并存：

1. `jobs` 的 `usage-overview-windows-refresh`（5min 周期）每个执行轮在单事务内对 4 张表（`usage_overview_summary_windows` / `usage_overview_trend_windows` / `usage_model_rank_windows` / `usage_error_rank_windows`）做全表 DELETE + 全量重插（约 36 万行/轮）。
2. `ai-performance-summary-windows-refresh`（5min）对 `ai_performance_summary_windows` 全表 DELETE 后逐行单条 INSERT 约 8900 行/轮（每行一个往返，语句数放大 WAL 记录数）。
3. 聚合器已在聚合事务内写脏标记表 `usage_overview_dirty_scopes`（PK `system_account_id`）与 `ai_performance_summary_dirty_system_accounts`（PK `system_account_id`），但两表从未被窗口刷新消费；`stages_window_snapshots.go` 注释声称"PG 增量 dirty 队列是等价优化"，实为未实现（仓库内已有消费先例：`stages_quota.go` 的配额小时窗脏范围认领与按 generation CAS 删除）。

## 修复方案（文档先行，契约见《统计指标与分层聚合设计》「概览与 AI 性能窗口的脏范围增量重建」）

两个 stage 改为"天滚动全量 + 同日脏范围增量重建"，SQLite 与 PG 共用同一代码路径：

- 模式判定：`WindowRefresher` 进程内为两个 stage 各维护 `lastFullRebuildDayKey`（不持久化、无配置项）；`todayKey` 变化（含启动首轮）→ 全量重建（现有实现原样），同日 → 增量。
- 增量消费：stage 事务内读脏表全部行，空 → no-op（零 DELETE）；非空 → 逐行 `DELETE ... WHERE system_account_id = ? AND generation = ?` CAS 消费（CAS 谓词语义与 `stages_quota.go` 配额消费一致，语句形态为逐行 DELETE 而非配额的 CTE 多行 DELETE），generation 已被并发聚合推进的行保留给下轮。
- 增量重建：claimed ∩ `usage_stats_totals`（`scope_type='system_account'`）逐账户按账户 DELETE 后复用与全量相同的行构建代码 INSERT；任一 claimed 非空即重建 `global` 行。
- 孤儿清理：每个非空增量轮对目标窗口表执行反连接 DELETE（`system_account_id` 不在 totals 且不是 `global`）。
- watermark 保留：本轮结束时脏表仍有剩余（含 CAS miss）则不推进该 job 的 `stats_job_state` 水位，防 watermark-skip 把残留脏行跳过去。
- `ai_performance_summary_windows` 逐行单条 INSERT 改为经 `execOverviewWindowInsertRows` 的多行 VALUES（12 列、200 行/片），行集/行值/行序与现状一致。
- 可观测：`UsageRankStageRun` 新增 `mode=full|incremental|noop` 字段（`omitempty`，不改既有字段）。
- 离线路径不变：`statsrebuild` 首轮即全量，完成路径仍清空两张脏表（离线全量后标记失去语义）。

## 验证方式

- `backend-go/projects/jobs` 下 `go build ./... && go vet ./internal/statsagg/... ./statsrebuild/... && go test ./internal/statsagg/... ./statsrebuild/... ./cmd/juhe-ai-jobs/...` 全绿；新增 `internal/statsagg/incremental_windows_test.go` 覆盖：全量→增量对拍（增量轮窗口行集与同源数据直接全量重建排序后完全一致）、脏行 CAS 消费与 miss 保留、空脏表 no-op 零写入、天滚动回全量、totals 删账户后孤儿清理且 `global` 保留、CAS miss 残留时 watermark 不推进。
- 发布后生产核验口径：`pg_stat_statements` 中四张 overview 窗口表 DELETE 频次降至脏范围量级、WAL 日生成量显著回落、checkpoint `wal` 触发占比下降、`usage_overview_dirty_scopes` / `ai_performance_summary_dirty_system_accounts` 行数常态清空（消费即删）。

## 遗留项

- 投影域 `search_terms` 写放大（`account_list_availability_projection_search_terms`：每次 dirty claim 应用对 (viewer, account) 的名称 1..3-gram 词集全量删插约 33 行，无差异比较，2026-10-13 起 3.5 天 2230 万次 INSERT / 19.6GB WAL）是独立写放大源，另行立项。
- `wal_compression` / `max_wal_size` 等生产 PG 参数变更属高影响运维操作，需另行授权后在维护窗口实施，本修复不依赖参数调整。
