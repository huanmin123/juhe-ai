# BUG-0073 多 Key 账户被余额查询阻断

## 基本信息

- 编号：BUG-0073
- 状态：已发布并验证
- 严重程度：P1
- 发现时间：2026-07-13
- 修复时间：2026-07-14
- 模块：前端 / 后端 / AI 账户 / 多 Key / 余额查询 / 批量编辑 / ops-worker
- 关联计划：PLAN-0089、PLAN-0096
- 需求来源：Codex 会话 `019f5b7c-2b1f-7280-acd3-7e894c7efe2e`

## 问题概述

- 现象：余额查询已开启的单 Key 账户增加第二个 Key 后，完整编辑或直接 API 保存会返回“上游余额查询仅支持单 API Key 账户”；部分基础编辑虽然隐藏余额区，也可能继续携带旧开启状态。
- 期望：多 Key 是核心凭据能力。最终有效 Key 数量大于 1 时账户必须保存成功，余额查询自动关闭，调度和旧快照停止；恢复单 Key 后不能自行重新开启。
- 影响：账户内 Key 轮换无法启用，或者页面隐藏了余额配置但业务库、后台调度和旧快照仍保留开启语义。

## 根因

1. 前端 `buildAccountBalancePayload()` 在多 Key 时返回 `undefined`，没有明确提交 `balanceQueryEnabled=false`，校验仍把多 Key 当作阻断错误。
2. 路由把旧余额开启状态与新凭据组合后先做单 Key 校验，因此在 repository 写入前就拒绝保存。
3. repository 在凭据归一化之前计算余额状态，直接调用、导入或内部写入口没有最终有效凭据兜底。
4. 路由保存后会把保存前的余额配置重新覆盖到响应，后端兜底关闭时页面不能立即看到最终状态。
5. 首次余额自动探测只判断开关关闭，没有区分“从未配置”和“因多 Key 已配置关闭”，恢复单 Key 后存在再次自动开启风险。
6. 草稿“测试查询”路由调用了多 Key 能力校验但忽略返回的自动关闭决策；查询服务又允许从多 Key 池回退到旧 `api_key`，因此可能挑选一个 Key 发起本不该发生的余额请求。

## 修复

- 最终有效 Key 数按凭据归一化后的去空白、去重结果计算；多 Key 决策返回最终关闭状态，不再抛单 Key 能力错误。
- 前端完整编辑和基础编辑都明确提交关闭状态，在 API Key 区域显示中文提示，保存成功时说明自动关闭结果。
- SQLite/PostgreSQL 创建和更新 repository 在最终凭据形成后统一收敛余额状态；业务开关、调度时间和 `config_revision` 在同一次写入完成。
- 保留 `balance_query_config_json`；原配置为空时写入当前内置默认配置，作为“已配置关闭”标记，使恢复单 Key 后不会进入首次自动探测。
- 标准路由和批量编辑在业务事务提交后幂等删除 `relay_balance`；列表读取只在开关开启时附加快照，因此下一次读取立即隐藏旧余额。
- 在途查询继续使用 `configRevision + enabled + config` 条件写。账户切成多 Key 后旧 revision 不能提交业务状态或快照。
- 草稿余额测试必须消费能力校验的最终决策；多 Key 返回与保存自动关闭一致的中文原因。查询服务和候选过滤统一复用去空白、去重后的有效 Key 集合，任何直接调用也不能从旧 `api_key` 回退请求上游。

## 下次遇到

- 附属能力与核心账户凭据冲突时，先按最终归一化凭据决定附属能力状态，不能在路由层用局部请求提前拒绝核心写入。
- “隐藏配置区”不等于关闭业务状态；前端必须提交明确状态，后端仍要有唯一事实来源。
- 跨库快照清理不能放入业务事务；先让业务开关立即生效，再做可重试、幂等清理。
- 任何后台自动开启能力都必须区分“从未配置”与“用户或规则明确关闭”，否则账户形态恢复后会反向覆盖产品决策。
- 业务校验返回 decision 时，调用方必须消费最终状态；只调用不读取返回值等同于没有完成校验。外部请求服务还要保留独立硬守卫，避免内部调用绕过路由。
