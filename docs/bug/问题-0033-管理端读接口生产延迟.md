- 关联计划：无

## 问题概述

- 现象：账号、分组、API Key、策略路由列表和编辑弹窗在生产出现 `700ms` 到数秒延迟；部分请求显示 `304`，但实际仍完整执行后端查询。
- 期望：常规管理端列表和详情读接口在生产本机 / 局域网维持百毫秒级，写入、后台统计和运行态刷新不能把读接口拖到秒级。
- 实际：账号列表依赖同步运行态快照、动态 ETag 造成 304 误导、前端重复请求、DNS 慢节点和表监控快照窗口排序共同制造长尾。
- 影响范围：管理后台日常列表、详情、编辑弹窗、表监控 overview，以及用户对“写影响读”的判断。

## 复现步骤

1. 登录生产后台。
2. 打开“我的 AI 账户”“我的策略路由”等列表，观察浏览器 Network。
3. 打开编辑弹窗，观察列表、options、详情接口耗时。
4. 访问 `GET /__aisys__/api/table-monitor/overview`，观察生产 PostgreSQL 下快照查询耗时。

## 环境信息

- 分支 / 版本：`20260705-201041-runtime-filter-candidate` 之前存在多项延迟；`20260705-214545-table-monitor-overview-hotfix` 已修复表监控长尾。
- 数据状态：生产 PostgreSQL + Redis 高性能模式。
- 浏览器 / 系统 / Node 版本：Chrome / macOS server / Node 22 LTS。
- 是否稳定复现：列表和 DNS 长尾具备环境相关性；表监控 overview 旧实现稳定 `700ms+`。

## 根因分析

- 表象：用户感觉“写会影响读”，所有列表、详情、弹窗都卡。
- 真实根因：
  - 系统 API 启用动态 ETag，浏览器看到 `304`，但 Express 仍完整执行动态查询。
  - 账号列表 `status=active` 同步依赖 server 运行态快照，运行态缺失或刷新时拖慢列表。
  - 前端表格分页参数未变化时会重复触发相同请求。
  - DNS 轮询包含高延迟 edge，公网请求后端已返回但链路总耗时仍到秒级。
  - `table-monitor/overview` 在 PostgreSQL 下用窗口函数扫描并排序所有快照历史，生产 `EXPLAIN ANALYZE` 约 `715ms`。
- 为什么会发生：动态 API、运行态快照、监控快照和公网入口分别看起来“单点合理”，但叠在管理端首屏 / 弹窗链路上形成了可感知长尾；缺少生产真实读矩阵压测。

## 修复方案

- 修改点：
  - 系统 API 禁用 ETag，并统一返回 `Cache-Control: no-store`。
  - 账号运行态过滤改为只读已有快照并后台刷新，缺失快照不阻塞列表。
  - 无运行态阻断账号时跳过后置过滤，候选页按阻断数量动态收敛。
  - 前端分页参数未变化时不重复请求。
  - DNS 慢节点下线并降低劣化阈值。
  - `table-monitor/overview` 增加 30 秒短 TTL 缓存；PostgreSQL 查询改为 `GROUP BY table_keys + CROSS JOIN LATERAL latest`，使用已有 latest 索引。
- 行为影响：统计和表容量采样仍由后台写入；读接口只减少重复计算，不改变统计准确性。
- 发布异常处理：按第一档热修发布，无业务 schema 迁移；只备份 `juhe_business` 和 `backend.env`，Redis 停服后清空。

## 复发记录

- 2026-07-06 复发：用户单次请求 `GET /__aisys__/api/my-accounts?page=1&pageSize=20&groupId=grp_default_openai&status=active&sorts=priority:asc` 浏览器显示约 `1.30s`。现场拆分后确认 PostgreSQL 无锁等待，账号列表在 db-service 直连约 `90ms`，Caddy 本机 HTTPS 约 `140ms`，公网域名约 `500ms-600ms`；慢感主要来自主 `server` 同时承载 `/v1/responses` 大 JSON / SSE 网关流量和系统 API 代理，事件循环 5 分钟峰值曾到 `200ms+`，再叠加 `stats-worker` 冷范围窗口重刷抢 PG IO。
- 处理：生产将 `JUHE_AI_DB_SERVICE_HTTP_PORT` 固定到 `3002`，Caddy 对 `/__aisys__/api*` 和 `/__aipublic__*` 直连 `127.0.0.1:3002`，静态后台页面和 `/v1/*` 继续走主 `server:3001`；系统 API 不再被主网关进程事件循环排队影响。
- 处理：热用量窗口刷新补回 `usage_scope_range_windows` 的“今天结束”范围窗口；PG 高性能模式停用在线定时冷历史范围窗口重刷，避免 `usage_scope_range_windows` 这类低频统计任务每 6 小时大量 `DELETE + INSERT SELECT GROUP BY` 抢生产 IO。历史范围窗口后续应走离线重建或低峰手动维护。
- 验证：Caddy 本机 `/__aisys__/api/health` 返回 db-service 的 `Cache-Control: no-store`；Caddy 本机账号列表 5 次 `89ms-137ms`；公网域名 5 次 `523ms-580ms`，其中 TLS / 公网链路约 `220ms-250ms`；PG 活跃查询仅剩采样 psql，无锁等待。

## 下次遇到

- 先查什么：`Server-Timing`、本机 127.0.0.1、局域网、公网域名分别耗时。
- 重点看什么：动态 ETag / 304、运行态同步等待、前端重复请求、DNS edge、窗口函数扫描历史快照、主 `server` 事件循环延迟、Caddy 是否把系统 API 直连到 db-service、stats-worker 是否正在跑冷历史范围窗口重刷。
- 如何避免误判：PG MVCC 不代表应用层读写队列、后台写任务、DNS 链路和前端重复请求不会制造长尾；必须拆开后端耗时和公网总耗时。

## 完成总结

- 完成时间：2026-07-05
- 结论：管理端核心读接口生产后端已恢复百毫秒级，`table-monitor/overview` 的稳定慢查询已修复。
- 后续建议：把生产只读矩阵压测作为发布后固定验证项；表监控、统计、日志类页面继续禁止在请求链路扫描明细或历史全量窗口。
