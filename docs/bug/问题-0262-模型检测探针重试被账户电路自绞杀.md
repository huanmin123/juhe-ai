# BUG-0262：模型检测探针重试被账户电路自绞杀

- 状态：已上线（随 10-02 15:4x 发布）
- 定性：Go 实现与《模型检测设计.md》§1.2 / §230 契约偏差——探针重试预算从未生效，且探针失败证据违反"不处罚"契约把被测账户推入熔断
- 发现方式：生产用户报障「模型检测完全不能用」+ run 证据取证（2026-10-02 15:09/15:10 两次手动 run）

## 1. 现象

生产手动模型检测对慢上游账户恒定返回 `unavailable`「不可检测，目标模型链路不可检测或上游不可用」。实证 run：

- `run-a9d3c2ec963c76131042b920`（15:09，账户「神影-克隆」× gpt-5.6-sol）：`protocol_basic` 三连失败 → unavailable。
- `run-5c5c031f11563127dfdf48ee`（15:10，账户「神影-1-克隆」× gpt-6-sol）：`protocol_basic`/`responses_stream`/`usage_shape` 全 passed（**链路本身通**），但 `structured_output` 三连失败 → 终态 → unavailable。

两次 run 的 attempt 证据形态完全一致：

```json
"attempts": [
  {"durationMilliseconds": 10004, "error": "J3b probe timed out", "httpStatus": 0},
  {"durationMilliseconds": 1,    "error": "J3b upstream request failed", "httpStatus": 0},
  {"durationMilliseconds": 1,    "error": "J3b upstream request failed", "httpStatus": 0}
]
```

第一次尝试满 10 秒超时，第二、三次**1 毫秒内失败**——§1.2 契约的 20s/30s 重试预算从未执行。

## 2. 根因

探针请求经 `gateway_dispatch.ProbeAdapter` 派发，每次 attempt 携带账户电路输入（`ConfirmationEligible: true`）。因果链：

1. attempt1 发出请求，上游（reasoning 模型 × 慢中转）10 秒内未响应，attempt ctx 超时 → `client.Do` 返回 err；
2. `dispatch.go` 传输失败路径立即调 `attempt.ReportTransportFailure` → `circuit_runtime_gate.go` 的 `suspect()` → **被测账户被推入 SUSPECT 相并设置 RetryAt 退避**（按生产流量的传输失败语义结算）；
3. 2 秒重试间隔后 attempt2/3 进入 `Prepare`：`circuit_runtime_gate.go:38-41` 判定 SUSPECT 且 `RetryAt` 在未来 → **`AccountCircuitBlocked`，无 HTTP 请求，1ms 快败**；
4. `modelcheckprobe/probe.go` 错误分类把派发层/传输层错误统一包装为 `"J3b upstream request failed"`（底层 err 丢弃），三连"非 200"形成 `terminalFailure` 证据；
5. （BUG-0259 已修复的判读层正确消费该证据）→ 整 run `unavailable`。

两重契约偏差：

- **§1.2/§230 重试预算失效**：探针对被测账户的超时按普通流量语义触发熔断，再被自己触发的熔断挡死后续 attempt——10/20/30s 契约形同虚设。任何上游响应超 10 秒的账户（reasoning 模型 × 中转加成，本例 api.shenwenai.com 历史上就有 30s 级响应记录）手动检测必然 unavailable。
- **§230「不处罚」契约被违反**：设计明确「第三次仍非 200……不处罚、不质量隔离 / 降级、不写质量健康失败统计」；`suspect()` 的电路 SUSPECT 是可用性处罚（影响生产调度派发），探针失败证据不应处罚被测账户——真熔断证据应来自生产流量。

另外：BUG-0259 的 E2E 复现（tool_calling 三次尝试全部 10 秒超时）即本缺陷的同款形态；0259 修复了判读层（正确判 unavailable），本缺陷是其请求层根因，叠加后才让「完全不能用」彻底暴露。

## 3. 修复

探针请求在派发链上会被三层运行态闸门拦截，第一层闸门被探针自己的失败触发后，剩余重试全部在入口 1ms 快败。修复为诊断请求（`AccountCircuitInput.Diagnostic=true`，`ProbeAdapter` 注入）在这三层全部按中性语义结算：

1. **传输失败不 Suspect 被测账户**：`dispatch.go` 传输失败路径对 Diagnostic 请求改调 `ReportUnknown`（中性），不再 `ReportTransportFailure`→`suspect()`（推 SUSPECT + RetryAt 退避）。
2. **退避窗口穿透**：`circuit_runtime_gate.go`（+`memory_circuit_gate.go` 镜像）Prepare 对 Diagnostic 请求穿透 OPEN/SUSPECT 的 RetryAt 拦截，仍走 confirmation lease 语义（检测成功可充当电路恢复证据）——否则退避期内探针连第一个请求都发不出，而"确认被熔断账户是否恢复"正是检测用途之一。
3. **不记录 key-model FailureIntent**：`Attempt.Unknown` 名为中实际调 `RecordFailureIntent`，会把 key-model 运行态推离 CLOSED，`admitScript` 对非 CLOSED 状态直接 blocked（与电路层同构）；`dispatch.go` 传输失败路径对 Diagnostic 请求跳过该记录。
4. **错误分类透出底层错误**（BUG-0248 同款病灶）：`probe.go` `"J3b upstream request failed"` 追加底层 `err.Error()`（`ErrAccountCircuitBlocked`/`ErrAttemptBlocked` 等派发层错误从此可见）；外层 ctx `DeadlineExceeded`（内层预算未到期而外层先尽）归入 `"J3b probe timed out"` 分类。

不改动：10/20/30s 预算值与三次尝试边界（契约值）；Suspect 账户的 confirmation lease 穿透机制；`settle(false)` 的既有中性结算；0259 判读层。

## 4. 验证

- 单测：`gateway_dispatch` 三用例（Diagnostic 传输失败→电路 unknown 结算且 FailureIntent 零记录、普通请求照旧 Suspect、memory gate 退避穿透对照）；`modelcheckprobe` 两用例（传输错误透出底层错误、外层 deadline 归 timeout）。三包 `-count=1` 全绿（一次并发瞬时失败隔离复跑绿）。
- **生产实证（2026-10-02 15:2x-15:4x 三轮 gateway 发布迭代验证）**：
  - 修复前：`run-5c5c031f` attempts 形态 `10004ms 超时 / 1ms / 1ms`（错误被吞）；
  - 修复①②后：`run-c7f2577c`（神影-luna）protocol_basic **passed**（此前连 basic 都发不出），暴露第三层 `key-model admission blocked`；存量污染账户仍被历史状态挡（旧二进制残留）；
  - 三层修复齐后：`run-a4028b8b`（干净账户 api.shenwenai.com × gpt-6-sol，quick）**68 秒完整跑完**：protocol_basic/structured_output/tool_calling/usage_shape 全 passed、100 分、**level=likely（达标）**——超时探针在 20s/30s 预算内重试成功，§1.2 契约预算首次真实生效。
- 遗留观察：神影-1/神影-luna 两账户在修复上线前被旧二进制写入的存量电路/key-model 运行态需自愈（keymodelrecovery 后台恢复 + 电路 RetryAt 到期/confirmation），期间这两账户的检测可能仍报不可用，属预期过渡态，非修复缺陷。
