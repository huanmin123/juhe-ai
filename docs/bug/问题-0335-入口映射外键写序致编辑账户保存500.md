## 问题概述

- 现象：生产编辑 AI 账户保存时 `PATCH /__aisys__/api/my-accounts/{id}` 返回 500，gateway 日志：
  `accounts slice internal error — ERROR: update or delete on table "account_supported_models" violates foreign key constraint "account_entry_mappings_account_id_target_model_id_fkey" on table "account_entry_mappings" (SQLSTATE 23503)`，最近 36 小时 45 次（如 2026-10-23 13:37 多次连续失败）。
- 期望：编辑保存成功；账户入口映射（`account_entry_mappings`）与支持模型集合（`account_supported_models`）在同一事务内一致收敛。
- 实际：支持模型集合变化时，旧入口映射仍引用将被删除的 `(account_id, model_id)` 行，删除被复合外键拦截，整个 PATCH 事务回滚并 500。
- 影响范围：编辑账户保存中「支持模型集合发生变化」的请求，含两个子场景：
  - 子场景 A：PATCH 同时携带 `modelMappings`，`replaceAccountModelMappings` 排在支持模型替换之后（`patch.go:705` 先于 `patch.go:794` 执行），还没轮到映射整替换，支持模型 DELETE 已被 23503 拦截。
  - 子场景 B：PATCH 只改支持模型、未带 `modelMappings`（输入缺席，或与现值相等被 `modelMappingsEqual` 判定为未变化），旧映射悬空同样 23503，且此路径根本不会执行映射整替换。

## 复现步骤

1. 账户已有支持模型 {m1, m2}，且存在一条入口映射 target 指向 m1。
2. 管理端编辑该账户，把支持模型集合改为 {m2, m3}（m3 为目录内有效模型）。
3. 保存：`replaceAccountSupportedModels` 第一步 `DELETE FROM account_supported_models WHERE account_id = ?` 删除 m1/m2 两行，指向 m1 的映射行悬空，复合外键拒绝，PATCH 500。

## 环境信息

- 分支 / 版本：生产 gateway（Go 三项目形态，PG 业务库）。
- schema 事实：`account_entry_mappings` 复合外键 `(account_id, target_model_id) REFERENCES account_supported_models(account_id, model_id)`，无级联动作——PG 见 `backend-go/projects/maintenance/internal/schema/pg_schema_business_tables.go:976`，SQLite 见 `backend-go/projects/maintenance/internal/schema/sqlite_schema_business.go:772`；对应设计 §5.1「复合外键把 target 锁进同一账户的连接与支持模型集合」。
- 是否稳定复现：是（支持模型集合变化且存在指向被替换模型行的入口映射时 100% 失败）。

## 根因分析

- 表象：500 与 SQLSTATE 23503，错误发生在 `account_supported_models` 的 DELETE。
- 真实根因：`backend-go/projects/gateway/internal/accounts/write.go` 的 `replaceAccountSupportedModels`（修复前 1145-1167 行）语句顺序为「读 owner → DELETE account_supported_models（全删）→ 逐个解析模型名并 INSERT」。`account_entry_mappings` 的复合外键把每条入口映射的 target 锁进同一账户的支持模型集合，无级联动作；全删支持模型集合时，凡 target 指向被替换模型行的存量映射立即悬空，DELETE 被外键拒绝。PATCH 事务（`patch.go`）中支持模型替换（705 行）先于入口映射整替换（794 行）执行，且映射整替换只在显式提交且与现值不等时才发生——两个子场景都在映射得到处理之前就撞上外键。
- 为什么会发生：设计 §8 的既定原则是「依赖映射在同事务内一并解决」，不是拒绝；该写入原语在 B4 W2 落地时按「整集合替换」直觉先删后插，没有把 §5.1 复合外键的引用方向纳入写序。SQLite 测试库默认不启用外键 PRAGMA，23503 在既有测试全绿的情况下只在生产 PG 上暴露。

## 修复方案

- 修改点：仅 `backend-go/projects/gateway/internal/accounts/write.go` 的 `replaceAccountSupportedModels`，重排为：
  1. 先循环保留 `resolveEntryModelID` 把 next 模型名全部解析成 `models.id`（错误语义不变：目录外模型仍按 ValidationError 400 族拒绝；解析只读 models 表，先解析后删不影响事务原子性）。
  2. next 集合非空时，对两张表做按 next 目标集合的对称选择性删除（先映射后支持模型）：
     - `DELETE FROM account_entry_mappings WHERE account_id = ? AND target_model_id NOT IN (<nextIDs>)`；
     - `DELETE FROM account_supported_models WHERE account_id = ? AND model_id NOT IN (<nextIDs>)`。
     next 集合为空时两者退化为删除该账户全部行。占位符复用 `accountscore.Placeholders`。
  3. 随后逐行 INSERT `account_supported_models`（`insertIgnore` 分支保留；幸存行由复合主键冲突自然跳过）。
- 实现与修复契约的一处偏差（实测修正）：契约预设第 3 步「原样全删 account_supported_models」，但首轮实现按此跑场景 A 即失败（`FOREIGN KEY constraint failed`）——即使先按 `NOT IN (nextIDs)` 清理了悬空映射，全删仍会连带删除仍被保留映射引用的幸存行（如 m2），即时外键同样拒绝。因此 `account_supported_models` 的删除同样按目标集合选择性删除：复合主键 `(account_id, model_id)` 下该删除对幸存行幂等，重插由 `insertIgnore` 跳过，最终集合与全删重建完全一致；唯一差异是幸存行的 `created_at` 保留首次创建值。独立复审核实该列唯一消费点是链路装载排序（`cmd/juhe-ai-gateway/chain_accounts.go:1636` `ORDER BY asm.created_at ASC, m.upstream_model ASC`），下游均为集合成员判定/遍历、无按位取值的生产消费——旧写序下同账户行共享同一 nowISO、排序实际已按 upstream_model 退化，新写序下幸存行排前、新增行排后，排序输入变化不产生行为回归。
- 为什么按目标集合清理而不是全删映射：仍指向幸存行（next ∩ current）的映射是有效配置，全删会在「PATCH 只改支持模型、未带 modelMappings」的子场景 B 中丢失有效映射（该路径不会重写映射）。
- 注释已写明外键不变量（设计 §5.1 复合外键）、BUG-0335 生产 23503 与设计 §8「同一事务内解决依赖」原则。

## 下次遇到

- 先查什么：日志出现 `account_entry_mappings_account_id_target_model_id_fkey`（23503）时，先定位是哪条对 `account_supported_models` 或 `account_connections` 的 DELETE/UPDATE，再看同一事务内引用行的清理顺序是否先于被引用行。
- 重点看什么：任何「整集合替换」写原语（先 DELETE 后 INSERT）落在带复合外键引用的表上时，必须按目标集合做对称选择性删除或同事务内一并重写引用方；新增同类原语时在 SQLite 上显式开启外键 PRAGMA 验证。
- 如何避免误判：不要因「既有测试全绿」排除写序问题——SQLite 默认不启用外键，只有 `PRAGMA foreign_keys = ON` 的 fresh DDL 测试能暴露 23503 类缺陷。

## 完成总结
