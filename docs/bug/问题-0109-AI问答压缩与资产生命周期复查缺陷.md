## 问题概述

PLAN-0104 核心链路首次验收后，复查确认压缩认领、最近轮次替换、图片说明、附件容量和编辑器边界仍存在一组关联缺陷：压缩期间接受新轮次会违反数据库约束，重新生成仍把旧轮次发给模型，失败轮次可能进入摘要，压缩退避和租约不完整，未提交附件可无界占盘，图片说明可被旧任务覆盖，上传中断可能悬挂；前端还存在键盘删除附件未取消、混合剪贴板丢文字、未知斜杠命令吞 Enter、有序列表降级和滚动介入不完整。

期望这些派生状态都具备明确版本、租约、容量和撤销边界，后台降负不能阻塞正常对话，也不能把已经撤回或失败的内容写入模型记忆。

## 根因分析

- `context_revision`、压缩 claim 和接受轮次分别实现，缺少“新轮次原子失效旧 claim”的统一状态转换。
- 过期 checkpoint 在只读模型上下文装载中会被正确视为无效，但会话表的 `active_checkpoint_id` 和 `compacted_through_sequence` 没有同步解绑；后续 claim 继续使用旧持久游标，跳过仍在消息保留期内的有效原文。
- 替换轮次在构造上游请求后才进入事务删除，模型历史没有排除 `replaceTurnId`。
- 压缩来源最初按单条 `completed` 过滤；第一次整改虽补了配对存在性，但行/字节分页和普通模型上下文查询仍可能先计入失败用户消息或拆开超大完整轮次。
- `retry_at` 在重新 request 时被提前清空，分页进度也没有刷新 claim 租约时间。
- 图片资产只有逐行生命周期，没有用户维度预聚合占用量；说明任务也没有 claim/revision CAS。第一次整改后又发现 PostgreSQL 汇总字节仍为 `integer`，以及进程内按 assetId 去重会让旧 revision 任务吞掉新调度。
- 容量 reservation 接入保留期清理后，旧容量日桶仍按日期无条件删除；小批次同时恢复 stale turn 和删除 expired turn 时会留下尚未处理的旧 streaming 消息，下一批因日桶已不存在而永久回滚。反向只按“双零”删除又会让 PostgreSQL 已 DROP 分区对应的非零旧日桶永久积累。
- 图片说明首次加入 revision/claimId 后只防住“先 claim、后 replace、再迟到写回”，没有防住“replace 已提交、旧调度才开始 claim”。claim 未校验调度时捕获的 turn/message 绑定，会在新 revision 上认领并把旧问题语义写入新轮次。
- multipart 使用 `req.pipe(busboy)` 后只等待 Busboy 终态，源请求中断不会可靠传播。
- Tiptap 文档更新、剪贴板和滚动事件只覆盖了按钮、纯图片、滚轮/触摸等主路径，键盘和混合输入没有进入同一状态机；第一次整改只保留了混合剪贴板的文字，没有保留富文本 DOM 中的真实图文顺序，第二次整改又暴露出过滤无效图片后文件数组压缩导致的槽位错绑。

## 修复方案

- 接受新轮次时原子清除压缩 claim，并把 `compacting` 退回 `compact_pending`；压缩分页续租，成功后重置连续失败计数，失败退避到期前禁止再次 request/claim。
- 压缩 claim 先锁定会话并按当前时间验证活动 checkpoint；过期或失效时在同一事务内解绑指针、归零持久游标和进度、推进 revision，再以新 revision 建立 claim，旧 checkpoint 同步转为 superseded。只读 load 保持无副作用。
- 替换请求先校验最近完整成功轮次，所有模型历史装载显式排除旧 `turnId`，事务仍做最终并发确认。
- 普通模型上下文和压缩来源都在 SQL 层只读取完整成功轮次，行/字节分页按 pair 原子推进；单轮超过页预算时在绝对上限内整轮受控装入。attempt 只在失败落库时增加，正常打断不退避；同一会话准备阶段使用进程内排他占用，关闭预检到最终替换之间的单实例 TOCTOU。
- 真实模型偶发返回空 `currentGoal` / `recentUserIntent` 时，优先使用当前页最近用户内容、再回退旧 checkpoint 做确定性补齐；多页连续为空也按页推进最近意图，再执行完整性与摘要缩小检查，避免安全回滚后让一次可恢复格式漂移阻断压缩。
- 新增 `chat_user_asset_usage` 预聚合表，按用户限制活动图片字节和数量；`asset_bytes` 在 PostgreSQL 使用 bigint，创建与删除在同一配额锁和事务中增减，上传完成改用 `UPDATE ... RETURNING`。
- 图片说明增加 revision、claim ID 和 claimed time；重新生成会失效旧说明并递增 revision，迟到任务无法写回；进程内登记允许不同 revision 任务重叠，旧任务结束不会删除或阻止新任务。
- 图片说明 claim 进一步把调度时的 `expectedTurnId + expectedMessageId` 放入同一条条件更新：历史补全捕获原用户消息身份，当前轮捕获已接受轮次身份；旧任务在 replace 后才启动也无法认领新绑定，写回仍由 revision + claimId 做第二层 CAS。
- 容量日桶清理改为只删除“双零日桶”，或“早于窗口且该用户该日已无任何消息”的旧日桶；既保留小批次尚未结算的 reservation，也能回收 PostgreSQL DROP 分区后已无明细的账本。
- multipart 改用 stream pipeline 传播连接中断并保证临时目录清理。
- 编辑器统一清理脱离附件，保留有界 Undo/Redo 暂存并在离页删除未提交资产；混合富文本通过 DOM 顺序和未压缩文件槽位保留文字与图片，远程装饰图不消耗本地槽位；未知命令回车回到正常发送；列表使用标准四空格层级并由 Markdown 解析器验证；键盘和滚动条向上移动同样解除流式跟随。

## 下次遇到

- 任何后台派生任务都先检查 claim 是否有 revision、lease 和迟到写回 CAS。
- 后台任务如果依赖可改绑实体，claim 除 revision 外还必须校验调度时捕获的所有权身份；只校验当前 revision 不能阻止旧任务认领新版本。
- 分批清理预聚合账本时，不能只按时间删除，也不能只看账本值；必须同时证明对应明细已处理完，PostgreSQL 分区直删还要覆盖“明细已无、账本非零”的收口路径。
- “编辑并重新生成”测试必须断言实际上游请求体，而不只检查最终数据库旧行消失。
- 压缩来源必须按完整轮次测试失败、取消和序号间隙。
- 二进制资产必须同时检查单对象预算、用户预聚合配额、中断清理和数据库/文件最终一致性。
- 编辑器行为不能只测按钮；至少覆盖 Backspace/Delete、Undo/Redo、混合剪贴板、键盘滚动和滚动条拖动。

## 2026-07-17 图片上传与长会话验收补充

- 前端图片入口统一使用 Compressor.js：最长边 `1024`、JPEG `85`、透明背景填白、删除 EXIF；压缩后仍超过 `1 MiB` 时不插入编辑器。
- 后端继续用 Sharp 做权威格式、尺寸和字节校验，上传入口在读取 multipart 正文前建立账户 + 会话 reservation，创建资产后立即把 reservation 转移给数据库账本，消除并发上传的 TOCTOU。
- 单条消息前端文档边界和后端提交边界均限制最多 `5` 张；浏览器连续粘贴 6 次时只保留 5 张，第 6 次显示中文上限提示。切换会话后未提交草稿资产清理为零。
- 图片压缩改用 generation + token 状态：会话切换、clear 和卸载会物理清除旧代次 token；迟到的 Compressor 任务不能阻塞新会话，也不能向新编辑器插入图片。
- 浏览器粘贴 `3000x2000` PNG 后，数据库记录的前端上传原件为 `1024x682` JPEG、`4,888` 字节；后端处理结果为 `1024x682` JPEG、`2,390` 字节。实际消息保持“文字 -> 图片 -> 文字”顺序，跨菜单切换后流式回答继续并完成。
- 后端并发上传集成回归真实持有两阶段 reservation，验证合法第 5 张成功、第 6 张在读取大正文前拒绝，并检查临时文件和账本最终收口。

## 本地运行补充

- 当前代码首次连接旧本地聊天库时，旧表缺少上下文与资产生命周期字段，`context-status` 查询失败；本地验证库已先备份再离线同步当前 schema，运行时代码未增加旧结构兼容或自动迁移。
- System API 的 JSON 错误处理中间件此前把下游传播的普通对象错误也误报为“请求体无效”，导致页面看不到真实存储异常；现仅识别带 body-parser `type` 的解析错误，其余异常交给统一业务错误处理，并用损坏 JSON 回归锁定边界。
- `cleanup_chat_retention` 原有保留清理支持每轮 1000 条，新接入的上下文恢复与 checkpoint 清理严格限制每轮 500 条；DB handler 曾复用 1000，导致 ops-worker 每次在后续阶段失败。现保留原清理吞吐，并仅为上下文和资产阶段派生最大 500 的批次，使用临时 SQLite 直接执行 `limit: 1000` 的完整 DB service 操作验证。
