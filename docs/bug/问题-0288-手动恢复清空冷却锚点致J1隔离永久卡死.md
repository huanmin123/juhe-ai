# BUG-0288 手动恢复清空冷却锚点致 J1 隔离永久卡死

## 基本信息

- 编号：BUG-0288
- 状态：已修复（待发布验证）
- 严重程度：P1
- 发现时间：2026-10-07
- 发现方式：用户反馈
- 模块：后端 / 网关
- 关联计划：无
- 关联 bug：BUG-0282（同形根因：冷却态行锚点完整性，方向相反——0282 是预检漏写锚点，0288 是恢复只清锚点不改状态）

## 问题概述

- 现象：生产 2026-10-07 用户在账户列表对 vsllm 系列账户执行“恢复可调度 / 异常恢复”（更多菜单“恢复正常”，`PATCH {clearFailureState:true}`）后，页面仍显示“临时不可调用 / 限流中”，账户不再参与调度且永不自愈。
- 期望：人工恢复是显式确认账户可用的动作，账户应立即恢复调度（状态原子翻转），不得出现“冷却态但无冷却锚点”的中间行。
- 实际：owner 路径只清 `last_error_*` / `cooldown_until` / retest 锚点族，不改 `status`；账户停留在 `temporary_unavailable` / `rate_limited` 且锚点全空。J1 直读候选校验（jobs accounthealth `direct_input.go:168` + `scheduler.go:1183` `validCooldownFence`）要求“冷却态账户必须带完整冷却 fence”，锚点空的行被判 `direct_input_invalid` 进入隔离抑制循环，冷却复测永远够不着 → 账户永久卡死“临时不可调用”。
- 影响范围：所有经由 owner 列表恢复动作处理的冷却态账户（`temporary_unavailable` / `rate_limited`）与 `error` 账户的恢复语义；生产当前存量 3 条卡死行。不影响授权实例路径（`patchAuthorizedDispatchTx` 语义本就正确）。

## 复现步骤

1. 让一个自有账户进入 `temporary_unavailable`（或 `rate_limited`）冷却态。
2. 在账户列表“更多”菜单执行“恢复正常”（`PATCH /__aisys__/api/accounts/{id}` + `{"clearFailureState":true}`），请求成功返回 200。
3. 观察账户列表：状态仍显示“临时不可调用 / 限流中”，且该账户不再进入 J1 冷却复测候选（`direct_input_invalid` 隔离），永远无法自愈。

- 分支 / 版本：生产国内单机 Docker go-only（103.36.63.105），2026-10-07。
- 数据状态：存量 3 条“冷却态但锚点全空”卡死行（vsllm 系列）。
- 浏览器 / 系统 / Node 版本：不适用（后端缺陷，任意客户端表现一致）。
- 是否稳定复现：是。

## 根因分析

- 表象：恢复动作返回成功但账户状态不变、永不参与调度。
- 真实根因：owner 路径 `patch.go` 的 `Patch` 对 `clearFailureState` 只执行锚点清空（`last_error_*`、`cooldown_until`、健康失败计数、retest 观察族），不改写 `status`；而 J1 的 `validCooldownFence` 对冷却态候选 fail-closed——锚点不完整的行直接判 `direct_input_invalid` 隔离。两件事叠加：恢复后的行恰好落入“冷却态 + 锚点空”的非法形态，复测与恢复链路都够不着。
- 为什么会发生：Node 归档迁移时 owner 路径未对齐权威文档与授权实例语义。《AI账户健康状态收敛设计》§5 与《核心功能设计》§191 一直要求恢复语义为状态原子翻转；同仓授权实例路径 `m11_authorized_dispatch.go` 的 `patchAuthorizedDispatchTx`（约 480-488 行）已是正确先例（`clearFailure → nextStatus="active" + schedulable=true`），owner 路径迁移时只搬了锚点清空段，漏掉了状态翻转语义。

## 修复方案

- 修改点：`backend-go/projects/gateway/internal/accounts/patch.go` 三处：
  1. 混交守卫后计算恢复目标：`error → pending_test`、`temporary_unavailable / rate_limited → active`（其余状态目标为空，行为不变）；
  2. 状态机接入：恢复目标作为 `requestedStatus` 参与既有状态机（不经 `input.Status`，不触碰混交守卫）；目标为 `active` 且行内可用时间计划当前不生效时落 `disabled`（复用同包 `m11ScheduleAllowed`，对齐 `ForceActivatePending`）；套餐到期守卫（`enablesAccount` → “账户套餐已到期，不能启用或参与调度”）自动生效；
  3. `error → pending_test` 立即复检：`next_health_check_at = NULL` + 路由尾部 `DispatchAccountHealthCheck`（reason 沿用词表 `configuration`），并清掉归一化写入的“账户配置已保存，等待后台检查”错误文案（恢复即清错误标记）。
- 行为影响：恢复即恢复调度——冷却态恢复后立即 `active + schedulable`（仍受时间计划与套餐到期约束），`error` 恢复后进入不可调度的 `pending_test` 并立即投递后台激活检查；与授权实例恢复同语义。运行态归一化（`nextRuntimeState`）按目标状态自动清空冷却 / 错误 / retest 列族，恢复后不再存在“冷却态但无冷却锚点”的行。
- 发布异常处理：存量 3 条卡死行无需数据修复，发布后在账户列表对卡死账户重新点一次“恢复正常”即解卡（新语义下状态原子翻转为 `active`）。

## 下次遇到

- 先查什么：账户行的 `status` 与 `cooldown_until` / `cooldown_retest_generation` 锚点完整性是否匹配（冷却态必须有完整 fence），J1 outcome 是否出现 `direct_input_invalid`。
- 重点看什么：owner 与授权实例两条恢复路径的状态机语义是否一致（`patchAuthorizedDispatchTx` 是权威先例）；恢复类动作是否只清锚点不改状态。
- 如何避免误判：不要把“恢复成功 200”当作恢复生效的证据；以行内 `status` / `schedulable` / 锚点族的终态为准。

## 完成总结

- 完成时间：2026-10-07
