## 问题概述

- 现象：SQLite standalone 与 PG performance 两种存储模式下，统计缓存（stats 结果库 / PostgreSQL `juhe_stats`）损坏或统计口径升级后，没有任何离线重建入口。历史上承担该职责的 Node 脚本 `node backend/dist/scripts/maintenance/rebuild-usage-stats.js` 已随 Node 后端全量归档删除（`backend/dist/` 已不存在，源码只读保留在 `migration-backup/node/final-archive/backend/src/scripts/maintenance/rebuild-usage-stats.ts`）；Go 侧 `backend-go/projects/maintenance` 当前只有 schema/seed/owner manifest CLI，没有等价的统计重建命令（`rg -ln "RebuildStats|rebuildStats" backend-go` 零命中）。
- 期望：统计缓存损坏/口径升级时，有一条用户可显式执行的停服离线重建命令，从用量事实源重建统计缓存。
- 实际：文档描述的脚本不存在，无法执行；损坏的统计缓存暂无恢复做法。
- 影响范围：使用记录统计概览、AI 性能、系统指标、用量统计等所有消费统计缓存的页面与接口；两种存储模式同样受影响。

## Node 原实现参考（归档只读证据）

源码：`migration-backup/node/final-archive/backend/src/scripts/maintenance/rebuild-usage-stats.ts`（构建产物曾发布为 `backend/dist/scripts/maintenance/rebuild-usage-stats.js`）。

关键语义：

- 离线门禁：必须显式传 `--confirm-offline` 或设置 `JUHE_AI_CONFIRM_USAGE_STATS_REBUILD=1`，否则直接抛错拒绝执行（归档脚本 :52-53），防止在线误执行。
- 吞吐控制：默认每批 2000 条（`:264-265`，`--batch-size=` 可调，钳制 1..50000）、最多 1000 批（`:269-270`，`--max-batches=` 可调，钳制 1..10000），批间让出事件循环；达到单轮上限后可再次离线执行续跑。
- 两种存储模式：
  - standalone（SQLite）：从 usage shard 文件中尚未清理的 `usage_records` 重建 stats 结果库缓存；
  - performance（PostgreSQL）：从 `juhe_usage.usage_records` 重建 `juhe_stats` 缓存（`:95` 打印 "PostgreSQL schema：juhe_usage -> juhe_stats"）。
- 重建动作：清空并重建统计缓存相关表与 `stats_job_state` 游标（`:153`、`:215-220`），可选 `--refresh-rank-snapshots`。
- 明确放弃语义：usage shard / `juhe_usage.usage_records` 为空或历史记录已丢弃时，历史统计明确放弃，后续从新请求重新累计。

## 复现步骤

1. 在 standalone 或 performance 模式下使统计缓存损坏（如手工误改 stats 库、口径升级后旧缓存失效）；
2. 查阅 `docs/functions/SQLite存储说明.md` 统计重建段落并尝试执行其中历史命令；
3. 命令指向的 `backend/dist/scripts/maintenance/rebuild-usage-stats.js` 不存在，无法执行；Go maintenance 亦无等价子命令。

## 影响

- 统计缓存一旦损坏（磁盘故障、误操作、口径升级后不兼容），所有统计读取面持续报错或返回错误数据，且无恢复手段，只能接受统计长期缺失。
- 文档现行指令指向不存在的脚本，排障人员按文档操作必然失败，浪费排障时间并可能诱使现场临时手写危险 SQL。

## 建议方案

在 `backend-go/projects/maintenance` 新增 Go maintenance CLI 子命令（如 `juhe-ai-maintenance rebuild-usage-stats`），覆盖两种存储模式：

1. 离线门禁对齐 Node 语义：必须显式 `--confirm-offline` 或等价环境变量，否则拒绝执行；
2. standalone 模式：从 usage shard 中尚未清理的 `usage_records` 重建 stats 结果库；
3. performance 模式：从 `juhe_usage.usage_records` 重建 `juhe_stats`（复用 `backend-go/projects/jobs/internal/statsagg` 的聚合与 dirty scope 逻辑，避免第二套口径实现）；
4. 吞吐参数（batch size / max batches）与"达到上限可续跑"语义对齐 Node；清空并重建统计游标（`stats_job_state` 对应物）；
5. 重建动作只触碰统计结果库 / `juhe_stats`，绝不写业务库；
6. 落地后同步改写 `docs/functions/SQLite存储说明.md` 统计重建段落为现行命令。

## 验收标准

1. standalone：构造损坏/部分缺失的 stats 库 → 执行 Go CLI → 统计缓存重建成功，统计页面恢复正常读取，业务库无写入；
2. performance：构造损坏/部分缺失的 `juhe_stats` → 执行 Go CLI → 从 `juhe_usage.usage_records` 重建成功，`juhe_usage` 与业务库无写入；
3. 无 `--confirm-offline`（或未设等价环境变量）时命令拒绝执行且不产生任何副作用；
4. 缺省参数下批吞吐与 Node 默认对齐（每批 2000、最多 1000 批），上限续跑语义可用；
5. Mock 依赖（storage/聚合器接口）单测覆盖正常、中断续跑、空 usage 源（明确放弃并提示）路径；真实存储模式各跑一次端到端重建；
6. `docs/functions/SQLite存储说明.md` 统计重建段落更新为新命令用法，与实现一致。
