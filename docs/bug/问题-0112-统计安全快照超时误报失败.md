# BUG-0112 统计安全快照超时误报失败

## 基本信息

- 编号：BUG-0112
- 状态：已修复（回归与开发运行监控验证）
- 严重程度：P2
- 发现时间：2026-07-15
- 发现方式：AI 问答 20 轮真实验收期间监控发现
- 模块：后端 / stats-worker / ingest-worker / 使用记录 / 系统监控
- 关联计划：PLAN-0104
- 关联 bug：无
- 责任人：Codex

## 问题概述

- 现象：`account-quality-refresh` 周期性记录“ingest-worker 使用记录队列快照不可用”，同一开发进程 20 分钟内出现两次失败，随后又自动恢复。
- 期望：短时 worker 忙碌不应让非请求链路的统计安全检查误判失败；真正超过合理等待时间或 worker 不可用时仍必须停止推进统计游标并打印 error。
- 实际：统计安全门只等待 1000ms，而验收期间 ingest-worker 事件循环短时达到 1.1–1.3s，快照响应晚于超时边界。
- 影响范围：数据安全未受影响，安全门会跳过本轮聚合；影响账户质量统计新鲜度、后台任务成功率和错误日志信噪比。

## 复现与证据

1. 在开发环境持续进行真实多轮 AI 对话，同时读取 `/stats/system-metrics` 和增量运行日志。
2. 观察到 ingest-worker `eventLoopLagMs` 短时达到约 1225–1286ms。
3. 同期 `background_account_quality_refresh_failed` 的错误栈落在 `usageStatsAggregationSafety()`，错误为快照不可用。
4. 代码确认安全门调用 `requestIngestWorkerDrainStatus(1000)`；后续周期在 worker 延迟回落后 7ms 成功，所有队列为 0。

## 根因分析

- 统计安全门的 1000ms 固定超时低于当前开发负载下已经实际观测到的短时 ingest-worker 事件循环延迟。
- 现有 fail-closed 行为是正确的：拿不到快照时不能猜测队列为空，也不能推进统计游标。
- 问题不在安全策略，而在非请求链路的等待窗口过紧，导致可恢复的短时调度延迟被记录为任务失败。

## 修复方案

- 将 `usageStatsAggregationSafety()` 的 ingest worker 快照等待从 1000ms 调整为 3000ms。
- 不增加无限重试，不回退到伪造空快照，不绕过 `flushFailureCount` 和 backlog 安全上界。
- 超过 3 秒仍不可用时继续抛错，保留 `background_account_quality_refresh_failed` 与 `background_job_failed` error 日志。

## 下次遇到

- 同时看错误时间、worker `eventLoopLagMs`、快照请求超时和后续 `lastSuccessAt`，不要只看累计 `failureCount`。
- 快照不可用不能降级成空队列；优先校准后台等待窗口，并继续保留安全失败。
- 若 3 秒仍频繁超时，应继续分析 ingest-worker 的长任务分块与运行日志索引，而不是继续扩大超时。

## 完成总结

- 完成时间：2026-07-15
- 结论：统计安全门可容忍已观测到的短时 worker 延迟，同时继续在真正不可用时阻止游标推进并打印 error。
