# BUG-0300 J3a 过期输入清理缺索引致周期性锁风暴

## 基本信息

- 编号：BUG-0300
- 状态：已修复（2026-10-09 入库，待发布；发布后须跑一次 `--apply-j3a-proxy-latency-postgres` 建索引）
- 严重程度：P2（自愈型、/v1 业务零错误；但每 2-2.5 小时一轮跨组件锁风暴，内部健康探针 503、可观测组件重试、业务表行锁等待峰值 61.6s）
- 发现时间：2026-10-09（发布后观察期，03:52/05:2x 两波异常轮次触发深挖）
- 发现方式：生产周期观察 ERROR 构成分析 + pg_stat_statements 语句画像
- 模块：后端 / jobs / J3a 代理延迟 / shared contracts / maintenance bootstrap
- 关联计划：无
- 关联 bug：无（BUG-0299 为同窗口不同缺陷，已另案）

## 问题概述

- 现象：生产以约 2-2.5 小时为周期出现跨组件锁风暴窗口（01:23、03:52、05:2x 三波）：F1 runtime-log-indexer 与 F4 operation-log 的 owner lease 验证 55P03 锁超时 → lease 丢失 → sidecar 重启循环；J2 余额刷新轮次与 J3a 代理执行 deadline 超时；gateway `__aisys__/health` 探针 503（每波 6-10 次）。全部自愈，/v1 业务零错误。
- 期望：J3a 过期输入清理（每轮 `DELETE ... WHERE request_id IN (SELECT ... WHERE expires_at < cutoff LIMIT 1000)`，已分批）应秒级完成，不产生跨组件锁竞争。
- 实际：`proxy_latency_inputs` 的清理时间列 `expires_at` 无索引，子查询逐批全表扫宽表（payload jsonb），单条 DELETE 实测 max **21.4 秒**（avg 4.8s、calls 29）——长事务持锁期间，各组件的 lease 验证 SELECT（operation_log 13s、account_health 19s、table_monitor 9.9s）与业务表 `accounts FOR UPDATE`（等锁峰值 **61.6 秒**）排队超时。
- 影响范围：可观测与后台组件（索引/保留/余额/代理延迟）周期性降级与日志噪音；内部健康探针 503；业务 /v1 零错误但 `accounts` 行锁等待已波及业务表（未产生用户可感知错误，风险面真实存在）。

## 复现步骤

1. 生产 pg_stat_statements：`DELETE FROM juhe_jobs.proxy_latency_inputs WHERE request_id IN (SELECT ...)` max_exec_time 21.4s。
2. jobs 日志按窗口过滤：F1/F4 的 55P03 重试、J2/J3a deadline 与该 DELETE 同窗出现。
3. 表结构：`proxy_latency_inputs` 仅主键与 `unique(proxy_id, input_version)`，无 `expires_at` 索引。

## 环境信息

- 分支 / 版本：生产 `54c756c19`（2026-10-09 发布）起观察实证；缺陷自 J3a PG 化（`--apply-j3a-proxy-latency-postgres`）起即存在。
- 是否稳定复现：是（随 J3a 清理调度周期性出现；pg_stat_statements 画像确定）。

## 根因分析

- 真实根因：J3a PG schema 契约的索引清单（`J3AProxyLatencyIndexes`）只覆盖 outcomes 的两个查询索引，清理子查询的时间列 `expires_at` 无索引——批次虽已 LIMIT 1000（cleanup.go 分批正确），但子查询定位过期行是全表顺序扫（宽表含 jsonb payload），叠加锁竞争期其他事务时单条语句 21s。
- 为什么会发生：J3a 上线时只按查询路径补了 outcomes 索引，清理路径（cleanup.go 后加的限时分批）没有反向核对索引覆盖；分批解决了"事务长"，没解决"定位慢"。

## 修复方案

- 修改点（三处同源索引 + 守卫测试）：
  1. `shared/contracts/j3a_proxy_latency_schema.go`：`J3AProxyLatencyIndexes` 增 `idx_proxy_latency_inputs_expires_at`（btree on expires_at），注释挂 BUG-0300。
  2. `projects/jobs/internal/proxylatency/store.go`：sqliteSchema 与 postgresSchema 两个 DDL 段各补同名 `CREATE INDEX IF NOT EXISTS`（本地单机形态同款问题一并根治）。
  3. `projects/maintenance/internal/j3aproxylatency/bootstrap.go`：PG DDL 段补同款（`--apply-j3a-proxy-latency-postgres` 幂等创建）。
  4. `bootstrap_test.go`：索引清单守卫断言由 2 个更新为 3 个（字典序）。
- 上线要求：随发版后**必须跑一次** `docker compose run --rm maintenance --apply-j3a-proxy-latency-postgres`（ensure-schema 不含 J3a；bootstrap 对 missing index 幂等创建，报告含 index 项核对）。
- 行为影响：清理子查询变索引扫描（预期单批从 21s 降至毫秒级）；锁风暴波次消失；无 env 变化、无数据迁移（纯加法索引）。
- 未根治面：`juhe_stats` 窗口表 DELETE（max 18.5s，calls 336 avg 564ms）的 max 毛刺疑似同窗受害或存在次级索引缺口，待本修复上线后观察，若仍有独立波次再立项。
