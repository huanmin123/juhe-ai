## 问题概述

- 现象：K3 `internal/ratelimit` 的 `MemoryStore` 以单一 `entries` map 保存窗口；IP 分钟桶和突发桶传入的 key 都是 `ip+class`，没有把 `StoreName` 纳入内存 key。
- 期望：分钟窗口与突发窗口独立计数，分别执行 Node 的 60 秒和 10 秒限流。
- 实际：两个桶互相覆盖，内存驱动实际只执行一个窗口；Redis 实现虽用 `StoreName` 区分，但内存模式仍偏离 Node 的三个独立 store。
- 另有契约偏差：Go 限流存储故障使用 `http.Error` 输出 `text/plain` 和尾部换行，Node 使用 JSON 响应；故障路径的 Content-Type 和正文也不一致。
- Redis/Eval 错误在 Go 被编码为限流拒绝并返回 429，Node 对应路径返回 500/交给全局错误处理；Go 还仅按 HTTP 方法区分 read/write，无法识别 Node 的只读 POST 数据库访问模式。
- 影响范围：未配置 Redis 或测试使用内存模式时，限流阈值和 429 时机错误，可能放行过多或过早拒绝请求。

## 根因与证据

- `backend-go/projects/gateway/internal/ratelimit/memory.go` 的 map key 未包含 store 名称；`limiter.go` 的 minute/burst `BucketInput.Key` 相同。`ratelimit.go` 的失败分支直接调用 `http.Error`，RedisStore 又把 Eval 错误转换为 429。
- Node `system-api-rate-limit.middleware.ts` 使用独立 `ipMinuteStore`、`ipBurstStore`、`userMinuteStore`。
- 现有测试先触发 burst，未断言两个窗口独立存在，因此未暴露冲突。

## 修复与验证

- 修改点：让内存 key 与 Redis key 使用同一 `(StoreName, key)` 组合，并补充分钟/突发交错请求回归。
- 当前验证：`go test` 现有测试通过但未覆盖独立桶；生产 listener 也尚未接线。
- 结论：K3 内存限流行为不等价，待修复后再进行 owner 切换。
### 2026-09-05：Go 仅按 HTTP 方法分类，遗漏 Node 的只读 POST 限流语义

- Node 基线：`systemApiDbAccessModeMiddleware` 先根据“方法 + 路径”写入 `res.locals.systemApiDbAccessMode`；`methodClassFor` 对 `noDb`、`read`、`longRead` 一律返回 `read`，只有其余请求才按 GET/HEAD/OPTIONS 与非读方法区分。历史规则明确把 `POST /(?:my-)?accounts/import/preview` 标为 `read`，因此该接口使用 IP/user read 限额（`backend/src/modules/system-api/system-api-db-access.ts` 行 23-72、`backend/src/modules/system-api/system-api-rate-limit.middleware.ts` 行 345-351）。
- Go 实现：历史 `backend-go/projects/gateway/internal/ratelimit/ratelimit.go` 的 `methodClassFor` 只检查 `r.Method`，除 GET/HEAD/OPTIONS 外全部返回 `write`（行 237-244）；`Limiter.ipRateLimit`/`authenticatedRateLimit` 没有接收或读取 DB access mode 的参数，也没有路径规则表。
- 最小复现：对同一客户端连续调用 `POST /__aisys__/api/accounts/import/preview`。Node 将其计入 `ipReadPerMinute`/`ipReadBurstPer10Seconds` 与 `userReadPerMinute`；Go 将其计入对应 write 桶。在 read/write 配置不同（例如 read=100、write=2）时，第三个预览请求 Node 仍允许，Go 已返回 429。
- 结果偏差：合法的只读导入预览会被 Go 按写请求提前限流，或反过来消耗错误的配额桶；IP、用户的 `Retry-After`、429 时机和后续可用窗口均不同。该差异不是 Go 可以放宽 Node 限制，而是丢失了 Node 已明确声明的业务访问模式。
- 结论：这是已提交 K3 请求分类的确定性契约缺口，独立于内存双桶 key 冲突；修复时应把 DB access mode 作为内核/限流之间的已验证输入，至少覆盖 import preview 等只读 POST 与未标注路由的 `readWithSideEffect`/write 回放。
