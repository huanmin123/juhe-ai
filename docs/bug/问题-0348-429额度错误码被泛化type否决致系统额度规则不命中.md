- 关联计划：T92
- 关联 bug：无

## 问题概述

- 现象：生产账户「火山-ds」（`acc_0392ecf61356c079`）返回 `429 AccountQuotaExceeded`（`You have exceeded the 5-hour usage quota...`）后，同一请求连续 3 次重试同一账户，账户未被写入 `rate_limited`，后续请求继续命中该账户并反复失败；用户侧表现为「余额不足拦截没生效」。同响应体中的 `type` 为 `TooManyRequests`。
- 期望：429 命中稳定额度错误码 `AccountQuotaExceeded` 时按系统规则「上游额度不足」处理——写入 `rate_limited` + `cooldown_until`，跳过同账户 transient 重试（单 Key / 非 keyScoped 路径）并切换到下一候选。
- 实际：决策返回 `nil`，走普通上游失败路径；`isTransientSameAccountHttpStatus(429)` 触发同账户重试预算（`same_account_retry_dispatch` ×2），随后才切换账户。
- 影响范围：所有 429 响应中「稳定额度 code + 通用 type（如 `TooManyRequests`）」组合的供应商；T92 发布后火山方舟额度耗尽场景仍 100% 漏命中。403 `billing_error` 等其他形态不受影响。

## 复现步骤

1. 构造上游失败体：`{"error":{"code":"AccountQuotaExceeded","message":"You have exceeded the 5-hour usage quota...","type":"TooManyRequests"}}`。
2. 调用 `chainErrorPolicyService.Decide`（或 `accountquality.SystemInsufficientQuotaRuleMatches(429, "AccountQuotaExceeded", "TooManyRequests", ...)`）。
3. 观察返回：修复前 `nil` / `false`；修复后返回系统额度冷却决策 / `true`。

生产复现：trace `150c62ad-021a-464f-a105-90cada376d0c`——17:41:59/17:42:03/17:42:06 三次 `429 AccountQuotaExceeded` 均在同一账户，审计元数据为 `same_account_retry_dispatch`（retryNumber 1/2）+ `same_account_retry_exhausted`，且无 `account_error_policy_matched`。

规模取证：2026-11-01 17:42 至 2026-11-03 17:44（人工禁用前），该账户共 787 次 429 attempt、274 个不同请求；其中 T92 发布后的 11-03 有 162 次 429，全部未命中系统额度规则。账户凭据解密（AES v1 信封）顶层键仅 `api_key` / `base_url` / `reasoning_effort_override` / `supported_endpoint_modes`，无 `error_handling_rules` 与 `error_handling_rule_overrides`；`operation_logs` 显示 11-03 08:06 凭据变更后至 17:44 无再次凭据变更，17:44 仅改 `status` / `schedulable`，故 17:41 时系统规则未被账户覆盖抑制。

## 根因分析

- 表象：系统额度规则的 429 分支「只认稳定额度码」看起来已实现（T92 白名单含 `AccountQuotaExceeded`），单元测试也全绿。
- 真实根因：`systemQuotaRateLimitedMatch` 在检查稳定额度码之前，先用 `isRateLimitErrorIdentifier(code) || isRateLimitErrorIdentifier(typ)` 做频控否决；`TooManyRequests` 归一化后为 `toomanyrequests`，命中频控判定，直接返回 `false`，稳定额度 code 永远轮不到检查。
- 为什么会发生：T92 的回归用例没有覆盖「稳定额度 code + 通用频控 type」组合——`w1_policy_test.go` 虽有 `errorType` 字段但 429 用例全部留空，`w13_quota429_test.go` 则固定传空 type；真实响应 `code=AccountQuotaExceeded` + `type=TooManyRequests` 因此成为测试盲区。`type` 是 HTTP 状态语义的通用标识，不是频控业务码，不应否决精确命中的额度 `code`。
- 同源实现：`backend-go/shared/platform/accounttest/accountquality/quota.go`（jobs 探针共用判定）存在逐字相同的缺陷。

## 修复方案

- 修改点：
  - `backend-go/projects/gateway/cmd/juhe-ai-gateway/chain_error_policy.go` 的 `systemQuotaRateLimitedMatch`：判定顺序改为「显式频控 `code` 否决 → 稳定额度 `code`/`type` 命中 → 通用频控 `type` 否决 → 非额度标识与文本排除」。显式频控 code（`AccountRateLimitExceeded` / `rate_limit_exceeded` / `rate_limited` / `too_many_requests`）仍然优先否决，避免频控误判为额度不足。
  - `backend-go/shared/platform/accounttest/accountquality/quota.go` 同步同一契约。
  - 回归：`w1_policy_test.go`、`chain_failure_dispatch_test.go`、`accountquality/w13_quota429_test.go` 增加真实载荷（含 `type: TooManyRequests`）与「稳定额度 code + 频控 type」新翻转类的正反用例；新增链路级 `TestChainFailureDispatcherSystemQuota429GenericType`，钉住 `explicit_policy` + 账户级写入 + 审计元数据。
- 行为影响：429 稳定额度码 + 通用 `type` 组合恢复为额度规则命中，写入 `rate_limited` + `cooldown_until` 并跳过同账户 transient 重试（非 keyScoped 路径；多 Key 池隔离账户仍按既有设计走 Key 级状态与 Key 轮换）；普通 429 频控（含同样带 `type: TooManyRequests` 的频控码）行为不变。
- 发布异常处理：无需数据迁移；已处于 `active` 的受影响账户在首次命中后自动进入冷却，冷却到期由探针复测，但恢复判定必须同时确认真实请求成功（小探针 200 不能证明额度可用）。

## 下次遇到

- 先查什么：`audit_payload_refs` 中该 trace 的 `gateway_metadata` 是否有 `account_error_policy_matched`；没有则看 `same_account_retry_dispatch` 的 `retryReason`。
- 重点看什么：上游失败体的 `error.code` 与 `error.type` 实际取值，尤其是 `type` 为 `TooManyRequests` 等通用标识时，稳定额度码是否被频控否决。
- 如何避免误判：回归用例必须使用上游真实完整载荷（code + type + message），只测单一字段会把「顺序/否决」类缺陷放走。

## 已知边界

- 多 Key 池隔离账户：系统额度决策按 `keyScoped` 只写当前 Key 运行态并允许同账户换 Key，不写账户级冷却。火山方舟 5 小时计划额度是账户级语义，若未来该账户启用多 Key 池，换 Key 仍会全部 429；当前生产该账户为单 Key（凭据无 `api_keys` 数组，`account_api_key_runtime_states` 对该账户 0 行），不受影响。启用池前需另定「账户级额度码强制账户级冷却」契约。
- 429 纯文本额度错误（无稳定 `code` / `type`）仍不命中，这是设计明确的边界（429 不读文本白名单）；本次生产载荷有稳定 `code`，不属于该边界。
- jobs 侧生效面：`accountprobe` / `cooldown` 的调用点当前固定传 `errorType=""`，shared 判定顺序调整对现网 jobs 行为是契约对齐（空 type 下新旧等价）；本次事故的生效修复在 gateway。type-only 场景由 accountprobe 的 code 解析回退覆盖，`cooldown.go` 的外部构造边界属既有缺口。
- 探针恢复判据：该账户 17:42:58 的健康检查（同模型 `chat_sse`）返回 200，而 17:41-17:42 真实请求连续 429；小探针成功不能证明额度可用。发布后验收需同时观察真实请求成功，不能只以探针 200 或冷却清除判定恢复。
- 冷却时长：响应消息给出 reset 时间 21:15:56，但未提供结构化 reset 字段/头，按 api_key generic 默认 60 分钟冷却；到期探针若仍 429 会再冷却，可能产生多轮 cooldown→probe 循环（每次一个小探针），不改变账户级拦截语义。
