# BUG-0349 结构重建回迁漏写名称搜索索引致账户包含搜索失效

## 基本信息

- 编号：BUG-0349
- 状态：已修复；生产索引过渡回填（2026-11-03 23:00）；架构层已按 T119 去索引化（代码待随 T114 发布，存量派生表待退役命令清退）
- 严重程度：P2
- 发现时间：2026-11-03
- 发现方式：用户反馈（生产对话账户列表截图：搜 `k` 命中 `k40 林夕`，搜 `林` 为空）
- 模块：AI 账户列表 / 账户名称搜索 / 业务库结构重建回迁 / maintenance CLI
- 关联：BUG-0175 D-219（`rebuild-account-name-search-terms` 运维入口缺失，已随 T119 去索引化不再需要）；2026-10-22 结构重建回迁批（T55 同源）；T119 账户名称搜索去索引化

## 问题概述

- 现象：生产「对话账户」列表按账户名称搜索时，前缀关键字（`k`、`k40`）能命中 `k40 林夕`，名称中段/中文子串（`林`、`林夕`）返回空；同一账户在列表中可见且名称确实包含这些字符。
- 期望：`keyword` 按账户名称做精确/前缀/包含匹配；`林` 应命中 `k40 林夕`。
- 实际：包含匹配完全失效（仅前缀/精确可用）；所有未在 2026-10-22 之后创建或改名的存量账户都受影响。
- 影响范围：生产 1211 个未软删账户中 1144 个没有名称搜索索引；用户无法按名称中段或中文子串找到老账户，容易误判为数据丢失。

## 生产取证（2026-11-03，只读）

```sql
SELECT (SELECT count(*) FROM juhe_business.accounts WHERE deleted_at IS NULL) AS accounts,
       (SELECT count(*) FROM juhe_business.account_name_search_documents)       AS docs,
       (SELECT count(*) FROM juhe_business.account_name_search_terms)           AS terms;
-- accounts=1211, docs=67, terms=2596
```

- 无索引账户：`1144`（LEFT JOIN documents 为空）。
- `documents.updated_at` 范围：`2026-10-23T17:30:30.103Z` ~ `2026-11-03T10:23:17.793Z`——只有 10-22 回迁之后新建/改名的账户有索引。
- 目标账户：`acc_1788250742572_f6cf4e81` / `sysacc_1780019373340_6da4018e`，名称 `k40 林夕`，`status=disabled`，`capability_domain=chat`，`normalized_name` 为空、`term_count=0`。

## 根因分析

- 主列表 keyword 的包含分支依赖 `account_name_search_terms` + `account_name_search_documents`（`backend-go/projects/gateway/internal/accounts/list.go:817-840`）；精确/前缀分支直接走 `accounts.name` 范围索引，不依赖词表。索引缺失时表现正好是「前缀能中、中段不能中」。
- 增量写路径正常：账户创建（`write.go`）、改名（`patch.go`）、授权实例派生（`authz/instance_provision.go`）都在同一事务内维护词表。
- 根因：2026-10-22 生产结构重建回迁 `--import-legacy-business`（`backend-go/projects/maintenance/internal/legacybusinessimport/accounts.go`）直接 `INSERT INTO juhe_business.accounts`，整个 maintenance 模块没有写 `account_name_search_*` 的代码；回迁后也没有重建步骤。
- Go 侧没有名称搜索索引重建入口：Node 时代的 `scripts/maintenance/rebuild-account-name-search-terms.ts` 在迁移时归档，`rebuild-account-name-search-terms` 一直登记为 BUG-0175 D-219 的运维能力缺口，结构重建后无法补齐。
- 放大器：空结果时前端仍显示「还没有账户。点击「添加账户」…」，把「无匹配」呈现成「无数据」，进一步掩盖索引缺失。

## 修复方案（过渡修复，后由下方「架构层修复（T119）」取代）

> 下述词项索引/重建命令是当次故障的过渡止血方案，已于 T119 去索引化时整体删除；保留作历史记录。

- 新增共享算法 `backend-go/shared/platform/accountnamesearch`：统一 NFKC + trim 归一化与 1..3 字符词项构造，gateway 增量写入/查询与 maintenance 重建共用；匹配语义保持大小写敏感。
- maintenance 新增子命令 `rebuild-account-name-search-terms`：单事务全量重建两张索引表，幂等；正式执行强制 `--stop-write-confirmed` + `--backup-confirmed`（缺一 exit 2，不开库），`--dry-run` 只读输出账户数/存量文档数/存量词项数/缺失文档数/目标库名；事务内 `lock_timeout=2s`，停写失效时快速失败。
- `legacybusinessimport` 在账户行 INSERT 的同一事务内写该账户的 document + terms，报告新增两个计数，防止下次回迁再丢。
- gateway `statreads`（AI 健康列表）与 `authz`（授权实例派生）收敛到共享算法；前者此前只 trim 不 NFKC，全角关键字与索引不一致，属同源缺陷。
- 前端账户列表空态区分「有筛选无匹配」与「确实没有账户」。
- 契约与部署文档同步：`docs/functions/接口契约与权限矩阵.md`、`docs/functions/供应商与上游协议面重构设计.md` §10.1、`docs/deploy/部署指南.md`、`docker/single-server/README.md`、`docs/develop/测试与验证说明.md`。

## 架构层修复（T119 去索引化）

用户裁决（2026-11-03）：该派生词项层属过度设计——单用户账户量仅几十，全库 1211 行直扫毫秒级；用户维度唯一索引 `idx_accounts_owner_name_unique (system_account_id, name) WHERE deleted_at IS NULL` 与 `(system_account_id, name, id)` 查询索引已足够，全局管理员视图已有 `pg_trgm` GIN `idx_accounts_name_c_trgm_lookup` 兜底。已实施：

- gateway 列表 / options / AI 健康列表的 keyword 改为作用域内直查 `accounts.name COLLATE "C" ILIKE '%' || escaped || '%' ESCAPE '\'`（大小写不敏感，`%`/`_`/`\` 字面），删除创建/改名/软删/授权实例派生上的全部索引维护。
- jobs 可用性投影删除 `LoadSearchTerms`、投影词项写入/比对与 `search_index_complete` 列（该投影词项表从未被任何读面消费，属纯写放大）。
- schema 删除 `account_name_search_terms/documents`、`account_list_availability_projection_search_terms` 三表、9 枚索引、名称搜索 dirty 触发器与投影列；保留 `pg_trgm` 与账户名 GIN 索引。
- 删除 `rebuild-account-name-search-terms` 命令与回迁写索引；新增一次性 `drop-retired-account-name-search-index`（单事务、幂等、停写+备份确认）清退存量三表、投影列与残留触发器函数 `account_list_availability_name_search_dirty_trigger()`。
- 取舍：不再做 NFKC 归一化（全角关键字不再折叠为半角）；大小写由敏感改为 ASCII 不敏感；`%`/`_` 仍为字面。
- 生产只读 EXPLAIN 实测（2026-11-04）：全局 `name COLLATE "C" ILIKE '%林%'` 走 `idx_accounts_name_c_lookup` index-only scan，1211 行约 1.3ms；按 `system_account_id` 收敛后走 `idx_accounts_owner_all_name_c_lookup`，45 行约 0.3ms；`pg_trgm`、`gin_trgm_ops` 与 `idx_accounts_name_c_trgm_lookup` 均已在生产存在，数据量增长后可改走 GIN。
