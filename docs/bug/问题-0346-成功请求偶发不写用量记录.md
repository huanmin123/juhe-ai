# BUG-0346 成功请求偶发不写用量记录（复审结论：误报，仅剩审计可观测性缺口）

> **2026-11-03 复审结论：不是缺陷。** 原判定的「真实缺口」trace `b0ba6b29` 已证实为 AI 问答内部通道请求（`session_client_type='generic_openai'`、`session_id='cfp1-…'`），按设计抑制用量记录；真正的缺陷形态（`api_key_id` 非空 + `complete` + `attempt_count>=1` + `success` + 无用量行）近 30 天为 **0 条**。同时确认 `usage_records` 中 120,533 条 `api_key_id` 为空的行 **100% 是探针流量**（`cooldown_retest` 80,331 + `account_health_check` 40,202），与「空 key 即异常」的假设相反。唯一残留是可观测性问题（审计不记录 `suppress_usage`），见下文。

## 问题概述

- 现象：部分 trace 在审计表为 `success` / `finalized` / `complete`、`attempt_count>=1`、`final_status_code=200`，但 `usage_records` 无任何对应行。
- 期望：成功完成的上游尝试必须写一条用量记录（[模型价格与用量统计口径](../functions/模型价格与用量统计口径.md) §2「成功完成的上游尝试在写入使用记录时按同步定价目录估算」）。
- 实际：**经复审，这些「无用量行」的成功 trace 全部是内部通道请求，属设计行为**。审计不记录抑制标记，导致「设计不记账」与「意外丢记录」在数据面不可区分——这是唯一的真实问题，且只是可观测性层面。
- 影响范围：无功能性影响（无数据丢失）；仅影响事后审计的可区分性。

## 根因分析（2026-11-03 复审重写）

- 表象：审计完整但用量缺失。
- 真实结论：**不是缺陷，是内部通道按设计抑制**。证据链：
  1. trace `b0ba6b29-6b88-4179-a3b0-9f370a44d790` 的会话标注为 `session_client_type='generic_openai'`、`session_id='cfp1-…'`，属 AI 问答内部通道调用（免 API Key 直调），与 `api_key_id` 为空一致。
  2. `chain_v1.go:181-183` 对内部通道置 `req.SuppressUsage = true`；用量记录在唯一持久化闸口（`FinalizationDispatch.DispatchUsageRecord`）被丢弃。这是既定设计——内部问答不计入租户用量与成本。
  3. 排除项：不是采样（`capture_status='complete'`）；不是探针（`traffic_source='gateway'`，且探针流量本就会写用量行）。
- 「空 key 即异常」的假设被证伪：`usage_records` 中 `api_key_id` 为空的 **120,533 行全部是探针流量**（`cooldown_retest` 80,331 行 + `account_health_check` 40,202 行），`usage_gateway_empty_key` 指标为 0。空 key 在用量表里是探针的正常形态，不是丢记录的信号。
- 真正的缺陷形态（近 30 天）为 **0 条**：审计 `success` + `complete` + `attempt_count>=1` + `final_status_code=200` + `api_key_id` **非空** + 无用量行。
- 残留问题（可观测性）：审计行不记录 `suppress_usage` / `internal_channel`，事后无法仅从审计数据区分「设计抑制」与「意外丢失」。不影响业务，但会让同类排查重复发生。

## 修复方案（不需要，仅保留可观测性改进）

- **不做代码修复**：记账链路行为正确，无需改动。
- 可观测性建议（T109 跟踪，非缺陷）：审计行增加 `suppress_usage` / `internal_channel` 标记（纯加法、不改记账行为），使「按设计不记账」与「意外丢记录」在数据面可区分。上线后观察一个周期，若缺陷形态恒为 0 则彻底关闭本议题。
