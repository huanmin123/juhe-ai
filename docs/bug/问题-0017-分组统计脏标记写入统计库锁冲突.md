## 问题概述

- 现象：`cooldown-account-retest` 后台任务报 `ERR_SQLITE_ERROR: database is locked`，栈顶落在 `markGroupAccountStatsDirty`。
- 期望：冷却复测候选扫描触发过期账户清理时，即使统计结果库正在聚合写入，也不应让业务状态清理和后台调度失败。
- 实际：过期账户清理成功后同步写统计结果库 `group_account_stats_dirty`，如果统计结果库被长写事务占用，后台任务失败。
- 影响范围：账号到期自动停用、冷却复测候选扫描、分组账户统计脏缓存刷新。

## 复现步骤

1. 构造一个已到期但仍处于 `temporary_unavailable` / `rate_limited` 的 OpenAI 账户。
2. 使用另一个 SQLite 连接对统计结果库开启 `BEGIN IMMEDIATE` 写事务。
3. 调用 `listAccountsDueForCooldownRetest`，触发 `disableExpiredAccounts` 后的分组统计脏标记写入。

## 环境信息

- 分支 / 版本：本地开发工作区
- 数据状态：业务库、统计数据集库、统计结果库三库拆分
- 浏览器 / 系统 / Node 版本：Windows / Node 22.x
- 是否稳定复现：在统计结果库写锁持续超过 busy timeout 时稳定复现

## 根因分析

- 表象：冷却复测任务失败。
- 真实根因：`group_account_stats_dirty` 是业务写后的刷新队列，却写在统计结果库；统计聚合、分组统计刷新等 worker 长事务会占用统计结果库单 writer，导致业务状态变更后的脏标记写入被锁住。
- 为什么会发生：三库拆分后，分组统计结果表属于统计结果库，但刷新队列的写入时机跟业务状态提交绑定，二者归属混在一起，扩大了统计结果库写锁对业务路径的影响面。

## 修复方案

- 修改点：新增业务库 `group_account_stats_dirty` 表和索引；脏标记只写入业务库，worker 消费业务库队列后刷新统计结果库 `group_account_stats`。
- 当前边界：统计结果库只保存 `group_account_stats` 结果表；刷新队列只在业务库 `group_account_stats_dirty`，由 worker 消费后写入统计结果库。
- 发布异常处理：如脏标记刷新异常，修正当前业务库队列和统计结果刷新逻辑；业务库 `group_account_stats_dirty` 只保存可重建刷新队列，不影响核心业务事实。

## 下次遇到

- 先查什么：`background_job_failed` 的 `jobName`、栈顶 repository、当时统计结果库是否有聚合或窗口刷新任务。
- 重点看什么：业务写路径是否同步写统计结果库；刷新队列是否与业务事实同库。
- 如何避免误判：不要只调大 `busy_timeout` 或吞掉错误；先确认锁住的是业务事实提交，还是可异步消费的结果刷新队列。

## 完成总结

- 完成时间：2026-05-31
- 结论：刷新队列归回业务库后，统计结果库写锁不再阻断过期账户清理和冷却复测候选扫描。
- 后续建议：新增类似反向缓存 dirty / outbox 表时，默认跟随业务事实库，worker 再异步写结果库。
