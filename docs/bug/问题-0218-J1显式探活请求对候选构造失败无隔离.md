# BUG-0211：J1 显式探活请求对候选构造失败无隔离——单坏账户停摆全链探活

- 编号：BUG-0218（原登记 0211 与并行会话的 AI 问答系列撞号，改号让出）
- 状态：已修复（待发布）
- 发现：2026-09-28 12:10 生产巡检：jobs 3 小时 4733 条「消费账户健康探针 outbox 行失败」+ 298 条「account-health scan failed」，全部指向单一账户 `acc_f6cfe3ad185f19af`（名称 `ai.onyxaxis.org-公益`，gpt/api_key）

## 现象与影响

- 11:45~11:46 该账户上游连续请求失败，网关写入 16 条 `request_failure` outbox 行（每 2~5 秒一条）触发复测；
- J1 两处消费路径用会抛错的 `LoadAccount` 加载该账户，候选构造（`ToInput`：凭据解密/形状校验）失败 → 抛错：
  - `outbox_drain.go` `consumeProbeOutboxRow`：行保持 pending → 每周期重试 → 永不消费（毒丸行）；
  - `scheduler.go` runCycle 的 requests 循环：`return loadErr` **中断整轮 scan**（周期 inputs 的探测也在其后，未执行）；
- 结果：**J1 全账户周期探活从 11:45 停摆约 35 分钟**（outcome 时间桶 11:40=43 账户 → 11:50~12:00=0），日志每 ~7 秒刷 2 条 ERROR。
- 周期扫描路径（`LoadDueWithFailures` + suppression 抑制表）对该账户自身机制正常（其他构造失败账户被抑制），但 requests 循环的失败发生在周期 inputs 处理之前，抑制救不了。

## 根因

`consumeProbeOutboxRow` 的收敛契约注释已明确「确定性行损坏记 warn 后按已处理收敛——重试永远不会成功的失败保持 pending 只会形成毒丸」，但 `LoadAccount` 的候选构造失败（确定性、隔离结果 `Failures` 非空）未被归入该类，走了瞬态错误分支（return err）。`LoadAccountWithFailures` 隔离接口两方言 reader 均已存在，仅两处调用点未使用。

## 修复

两处调用点改隔离语义，与既有「候选缺失/不唯一时保持零值 input，由 runExplicitRequest 的 input_stale 判定落 stale 终态」完全一致：

- `outbox_drain.go`：构造失败 → WARN（requestId/accountId/失败数）+ 零值 input 继续走 `runExplicitRequest` → 行按 stale 终态结算出队；瞬态错误（transport/查询失败）保持 return err 重试。
- `scheduler.go`：同样处理；单账户构造失败不再中断整轮 scan，周期 inputs 照常执行。

## 验收

- 回归测试：fake reader 返回 Failures 非空 → drain 行被消费（不返回错误）、scan 周期 inputs 仍被处理。
- 生产止血（先行）：备份 16 条 pending 行（`/opt/juhe-ai/backup-j1-outbox-f6cfe3ad-20260928.csv`）后标记 consumed，J1 立即恢复（2 分钟内补跑 233 条 outcome / 227 个账户）。
- 发布后观察：scan failed 归零、outbox 行失败归零、无 pending 堆积。

## 遗留

- 该账户凭据/配置的坏点未定案（封套为标准 v1 格式，`ToInput` 具体失败原因需拿实际数据复现）；账户当前 `temporary_unavailable`，构造失败期间被周期路径 suppression 抑制。需要用户在管理页核对 `ai.onyxaxis.org-公益` 的凭据配置（11:45 前后是否被编辑过，updated_at=11:46:18、dispatch_revision=8）。
