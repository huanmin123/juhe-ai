## 问题概述

- 现象：Go 公开账户更新按 `apiKey`、`baseUrl` 或 `supportedModels` 字段是否出现判断连接配置变化。
- 期望：只有标准化后的 API Key 或 Base URL 实际变化才进入 `pending_test`；模型列表提交只安排下一次健康检查，不改变账户状态或清空已有健康诊断。
- 实际：重复提交相同凭据或仅提交模型列表都会把正常账户改为 `pending_test`、取消调度并清理失败状态与健康诊断。
- 影响范围：已迁移的 `POST /__aipublic__/account/update`；启用 W1b 流量后可能错误摘除正常账户。

## 根因分析

- Go 服务层把“请求字段出现”“连接配置实际变化”“需要安排健康检查”合并成同一个布尔值。
- PostgreSQL 更新语句又通过最终状态是否为 `pending_test` 同时决定健康检查排期和诊断清理，无法表达模型变更只重排检查的语义。
- Node 当前实现已经改为比较标准化后的真实连接配置，并将后台重检、检查排期和诊断重置拆成独立条件。

## 修复方案

- 解密并标准化当前与提交后的 API Key、Base URL，只在值实际变化时标记连接配置变化。
- 只有真实连接变化才强制 `pending_test`、取消调度并清理失败状态。
- 新增独立的 `ScheduleHealthCheck` 和 `ResetHealthDiagnostics` store 标志。
- `supportedModels` 只要显式提交就安排健康检查；仅真实连接变化才重置健康诊断。
- 保留凭据扩展字段、模型目录校验和当前检查模型约束。

## 下次遇到

- 更新接口中“字段出现”“值发生变化”“需要触发副作用”必须分别建模，不能复用一个 `configurationSubmitted` 标志。
- 比较加密凭据前应先解密并按写入规则标准化，不能比较随机密文或只比较 API Key 指纹。
- 健康检查排期与诊断清理是不同副作用：模型范围变化可以要求尽快检查，但不应自动抹除已有诊断。
