## 问题概述

- 现象：Go `inval.Bus.Subscribe` 返回的 unsubscribe 闭包不删除 handler；`Bus.Invalidate` 对同一 topic 1 秒内的第二次通知直接 return。
- 期望：注销后 handler 不再收到事件；同进程每次失效都立即执行并递增版本，节流只用于跨进程协调。
- 实际：重复注册或模块重载会永久保留旧 handler；快速连续的不同写操作会被抑制，缓存可能继续返回旧事实。
- 进一步事实：Go 版本号是每实例从 0 自增的 `int64`，多实例同时失效都可能写出 `version=1`；即使补上 Redis，后写覆盖和 `max` 同步也无法识别两次事件。Node 使用带时间和随机量的全局可比较字符串版本。
- 影响范围：管理写入后的页面/运行态/额度缓存可能不失效，长期运行会累积 handler 和重复副作用。

## 根因与证据

- Go：`backend-go/projects/gateway/internal/inval/inval.go` 的 `Subscribe`、`Invalidate` 与版本生成。
- Node：`backend/src/shared/gateway-cache-invalidation.ts` 本地 notify 每次执行，1 秒协调仅用于 Redis 同步。
- 当前 Go 仅有 SharedStore 接口和测试 fake，未发现生产 Redis 实现或 gateway 接线，多实例一致性也未证明。

## 修复与验证

- 修改点：实现可注销订阅、分离本地通知与跨进程节流，并补重复注册、1 秒内多次失效和 Redis 多实例测试。
- 当前验证：现有单元测试未覆盖上述时序；未执行多实例验证。
- 结论：K5 失效总线不满足 Node 的通知语义，待修复。
### 2026-09-05：Go 失效订阅者 panic 未隔离，Node 会逐 handler 捕获

- Node 基线：`runCacheInvalidators` 遍历每个 handler 时分别包裹同步调用；同步抛错只调用 `logCacheInvalidationFailure`，异步 Promise rejection 也被单独捕获，不会阻断同 topic 的其他 handler 或让请求/进程退出（`backend/src/shared/gateway-cache-invalidation.ts` 行 308-327）。异步强一致路径 `runCacheInvalidatorsAsync` 同样逐个收集错误，最终以聚合错误返回，而不是让第一个异常直接穿透。
- Go 实现：历史 `backend-go/projects/gateway/internal/inval/inval.go` 的 `Invalidate` 复制 handler 列表后直接执行 `handler(topic, reason)`，循环内没有 `recover`、错误返回值或异常隔离（行 89-113）；`Handler` 类型也被定义为无返回值函数（行 24-25）。
- 最小复现：注册两个同 topic handler，首个 handler 在收到失效通知时 panic，第二个 handler 负责清理实际 gateway cache。Node 会记录首个失败并继续调用第二个；Go 的 `Invalidate` 在首个 handler 处 panic，第二个不会执行，若调用栈未额外 recover 还会使当前 goroutine/进程异常退出。
- 结果偏差：一个缓存适配器或重复注册的旧回调异常，会阻断同 topic 的其余缓存失效；数据库已提交但网关/额度缓存继续保留旧数据，故障范围从单 handler 失败扩大为整条失效广播。该差异不是实现风格，而是 Node 明确要求的订阅者故障隔离契约缺失。
- 结论：这是已提交 K5 失效总线的确定性异常收口偏差，独立于注销不生效、1 秒节流和跨实例版本问题；修复时应在总线层对每个 handler 做 panic/错误隔离并记录，补“首个 handler panic、后续 handler 仍执行、无订阅者”回放。
