## 问题概述

- 现象：Go `inval.Bus.Subscribe` 返回的 unsubscribe 闭包不删除 handler；`Bus.Invalidate` 对同一 topic 1 秒内的第二次通知直接 return。
- 期望：注销后 handler 不再收到事件；同进程每次失效都立即执行并递增版本，节流只用于跨进程协调。
- 实际：重复注册或模块重载会永久保留旧 handler；快速连续的不同写操作会被抑制，缓存可能继续返回旧事实。
- 进一步事实：Go 版本号是每实例从 0 自增的 `int64`，多实例同时失效都可能写出 `version=1`；即使补上 Redis，后写覆盖和 `max` 同步也无法识别两次事件。Node 使用带时间和随机量的全局可比较字符串版本。
- 影响范围：管理写入后的页面/运行态/额度缓存可能不失效，长期运行会累积 handler 和重复副作用。

## 根因与证据

- Go：`backend-go/projects/gateway/internal/inval/inval.go` 的 `Subscribe`、`Invalidate` 与版本生成。
- Node：`backend/src/shared/gateway-cache-invalidation.ts` 本地 notify 每次执行，1 秒协调仅用于 Redis 同步。
- 当前 Go 仅有 SharedStore 接口和测试 fake，未发现生产 Redis 实现或 gateway 接线，多实例一致性也未证明。

## 修复与验证

- 修改点：实现可注销订阅、分离本地通知与跨进程节流，并补重复注册、1 秒内多次失效和 Redis 多实例测试。
- 当前验证：现有单元测试未覆盖上述时序；未执行多实例验证。
- 结论：K5 失效总线不满足 Node 的通知语义，待修复。
