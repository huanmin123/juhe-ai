# BUG-0019 授权配额快照跨进程失效缺失

- 发现方式：自查

- 关联计划：无
- 关联 bug：无
- 责任人：待定

## 问题概述

- 现象：授权配额限制创建、更新、撤销或过期后，server 端可能继续使用 worker 上一次推送的授权配额决策快照。
- 期望：授权配额业务写入提交后，DB service 进程内缓存、server 运行时授权配额缓存和 server 被动授权快照都应失效；新快照到达前，已标记额度限制但缺失新决策的授权应 fail-closed。
- 实际：`notifyAuthorizationQuotaCacheInvalidation` 只触发当前进程内的授权配额缓存失效；DB service 没有向 server 转发专用授权配额失效消息，server 可能短时复用旧的允许决策。
- 影响范围：DB service 模式下的授权配额检查、网关被动额度快照、授权额度限制调整后的短窗口请求。

## 复现步骤

1. 将运行角色设为 `server`，写入一个包含 `group_authorization` 和 `account_authorization` 允许决策的授权配额快照。
2. 调用 `checkGatewayAuthorizationQuotaBatchAsync`，确认命中旧快照并放行。
3. 触发 `notifyAuthorizationQuotaCacheInvalidation`。
4. 旧实现仍可能读取旧授权快照决策；修复后授权快照 entries 被清空并标记不完整，带额度限制的缺失授权决策返回拒绝。

## 根因分析

- 表象：授权配额改动后，server 请求链路短时继续按旧额度决策放行。
- 真实根因：授权配额失效器只覆盖当前进程内 `authorizationQuotaCache`，没有像网关运行时缓存一样跨 DB service IPC 通知 server；同时 server 的授权配额运行时缓存 key 没有绑定被动快照版本。
- 为什么会发生：API Key 配额快照保存的是成本，授权配额快照保存的是已计算好的允许 / 拒绝决策；限额字段变化后，旧授权决策本身会过期，必须显式让 server 端快照和运行时缓存同时失效。

## 修复方案

- 修改点：
  - DB service IPC 新增 `authorization_quota_cache_invalidate` 子进程消息。
  - DB service 注册授权配额失效器，DB service 角色向 server 转发，server 角色本地同步失效授权快照。
  - 授权配额快照缓存新增独立失效标记和版本号，只让授权决策 fail-closed，不误伤 API Key 成本快照。
  - server 授权配额运行时缓存 key 加入授权快照版本，避免快照失效后继续命中旧决策。
- 行为影响：授权限额变化后，新 worker 快照到达前，已标记额度限制但缺失新授权快照的请求会短时拒绝；未标记额度限制的授权和 API Key 成本快照不受该失效影响。
- 发布异常处理：如需回退，需同时回退 IPC 消息、快照版本和回归测试；回退期间授权限额调整后的短窗口仍可能复用旧决策。

## 复发记录

- 2026-07-10：Go `gateway-quota-snapshot-build` 开始通过 Redis runtime state 向 Node gateway 发布共享额度快照后，审计发现授权失效事件虽然已携带 `publishedAt`，Node runtime state 消费器却只调用无参数 invalidator，快照缓存改用本机收到事件时的 `Date.now()` 作为失效时刻。若 Node 晚于事件读取失效状态，而 Go 已在事件后生成新快照，新快照仍可能因“生成时间早于本机观察时间”被误判过期，触发不必要的 DB service fallback；fallback 失败时会 fail-closed。
- 本次根因修复：授权额度 invalidator metadata 新增 `publishedAt`；Node 本地通知把同一个时间写入 handler 与 Redis state，runtime state 同步把 `state.publishedAt` 继续传入快照失效器；快照缓存优先解析事件时间，非法或缺失时才回退本机时间，并保留较新的失效时间避免乱序事件回退 freshness 边界。Go runtime state payload 已有 Node 兼容 `publishedAt`，无需修改格式。
- 本次回归：先扩展 `test:gateway-quota-passive-snapshot` 并确认旧代码按预期失败，再完成修复；同时执行 `test:gateway-cache-invalidation-runtime-state` 和 backend typecheck。

## 下次遇到

- 先查什么：`notifyAuthorizationQuotaCacheInvalidation` 是否只清了当前进程，DB service 子进程消息是否覆盖 server 本地缓存和被动快照。
- 重点看什么：快照里保存的是原始成本还是最终决策；如果保存最终决策，限额字段变化必须让决策快照失效。
- 如何避免误判：不能只看 DB service 本地 `authorizationQuotaCache.clear()`；网关请求实际在 server 角色读取被动快照，跨进程失效链路必须有回归测试。涉及“事件后生成的新快照”时，必须比较事件自带时间 / 版本，不能使用消费者本机观察时间代替事件时间。

## 完成总结

- 完成时间：2026-06-02
- 结论：授权配额变更后，DB service 与 server 的缓存 / 快照失效链路已补齐；server 不再复用旧授权允许决策。
- 后续建议：新增跨进程缓存时，区分“数据成本快照”和“业务决策快照”，决策快照必须绑定版本或显式失效。
