## 问题概述

- 现象：M08 Go accounts 只实现核心列表、详情、创建、编辑、锁定族、标签和删除；Node/前端仍有高级详情、clone、runtime reset、批量、导入导出、余额/测试、模型目录、分组绑定、OAuth 重新授权等能力。
- 期望：账户功能完整迁移后，所有端点、状态机、凭据策略、删除清理、缓存/运行态和初始健康探针与 Node 结果一致，才允许归档 Node。
- 实际：
  1. Go 路由缺少上述大量端点，owner manifest 仍为 `missing`，Node `/accounts`、`/my-accounts` 仍挂载。
  2. Go 删除未撤销账户作为资源拥有者的 authorization/grant/source，未写 health tombstone outbox，也未刷新 group stats、lookup/authorization/runtime/cache。
  3. Go ENGAGED 锁配置更新始终复用旧 deadline 并清空 retry lease；Node 会按新的 death timeout 重新计算 deadline，无配置变化时保留 lease。
  4. Go create/patch 没有 Node 的凭据归一化、deprecated 字段清理、provider policy 校验和完整运行态副作用；create 也没有 dispatch 初始 health check。
  5. Go edit-basic 对凭据主动 mask，Node sanitizer 不 mask，返回结果存在产品可观察偏差（需产品确认是否有意安全加固）。
- 影响范围：账户管理页面功能缺失；删除后授权和缓存可能继续生效；锁定恢复时间/租约漂移；新建或修改账户的健康状态与网关运行态不更新。

## 根因与证据

- Go 路由：`backend-go/projects/gateway/internal/accounts/routes.go`。
- Node 路由/前端：`backend/src/modules/accounts/accounts.routes.ts`、`frontend/src/api/domains/accounts.ts`。
- 删除清理：Node `backend/src/storage/account-delete-cleanup.repository.ts`；Go `backend-go/projects/gateway/internal/accounts/delete.go`。
- 锁状态机：Node `backend/src/storage/account-lock.repository.ts`；Go `backend-go/projects/gateway/internal/accounts/lock.go`。
- 凭据与副作用：Node `account-credentials-normalization.ts`、`account-management-patch.repository.ts`、`accounts.routes.ts`；Go `write.go`、`patch.go`、`routes.go`。

## 修复与验证

- 修改点：以 Node/前端完整端点矩阵为基线拆分后续切片；先补删除授权撤销、health tombstone、缓存/运行态失效、锁状态机和凭据 golden，再补余下端点与初始探针；统一唯一 owner 后才归档 Node。
- 当前验证：Go SQLite 包内测试不能证明 PostgreSQL、Redis、worker、runtime 和前端行为；未执行真实 gateway 或浏览器验证。
- 结论：M08 是核心 CRUD 实现，不是完整账户功能迁移。

## 已核实子项

### 2026-09-05：删除资源拥有者账户未撤销授权链

- Node 基线：`backend/src/storage/account-delete-cleanup.repository.ts` 的 `deleteAccountWithRelatedCleanup` 在软删除账户前，于同一事务调用 `revokeAccountAuthorizationsForDeletedResource`（SQLite 行 145-148）；该函数筛选 `resource_type='account'` 且状态不是 `revoked/returned` 的 `resource_authorization_grants`，逐一执行撤销（行 479-492）。PostgreSQL 异步路径同样先查询该账户的 `resource_authorizations`，删除授权 grant 产生的 quota scope 绑定，并把 grant、source、authorization 状态更新为 revoked/returned（行 420-475）。
- Go 实现：历史 `backend-go/projects/gateway/internal/accounts/delete.go` 的 `Store.Delete` 仅查询账户与授权实例标识（行 35-49），随后更新 `accounts` 状态为 disabled、写 `deleted_at/deleted_by`，删除标签和名称搜索项后提交事务（行 76-101）；没有查询或更新 `resource_authorizations`、`resource_authorization_grants`、`resource_authorization_sources`，也没有清理授权 grant 产生的 quota scope 绑定。
- 结果偏差：删除一个作为资源拥有者、且仍有 active/paused 等有效授权的账户时，Go 返回 204 并将账户标记删除，但授权及其来源/grant 仍保持可用状态。授权读取、配额和被授权账户运行时仍可能把已删除账户当作有效来源；后续物理清理还会面对悬挂的授权链。Node 则在删除事务内先撤销这些关系，再提交并触发对应运行态失效。
- 结论：这是已提交 M08 的确定功能偏差，属于删除状态机和跨表副作用缺失；当前仅记录，未修改 Go 代码。

### 2026-09-05：删除账户未写入健康探针 tombstone outbox

- Node 基线：`backend/src/storage/account-delete-cleanup.repository.ts` 的 `logicallyDeleteAccounts` 在更新账户为 `disabled`、`schedulable=0` 后，按删除批次读取 `config_revision` 和 `dispatch_revision`，仅针对支持健康检查的 provider/type 调用 `reserveAndEnqueueAccountHealthJobsInputInTransaction`，写入 `kind='tombstone'`、`reason='account_deleted'` 的 health input outbox（SQLite 行 259-275）；PostgreSQL 路径同样在事务中执行异步 outbox 写入（行 307-325）。这样删除提交后，健康投影能消费带版本栅栏的 tombstone，清除该账户运行态。
- Go 实现：历史 `backend-go/projects/gateway/internal/accounts/delete.go` 的 `Store.Delete` 只更新 `accounts`、删除标签和名称搜索项，然后直接提交事务（行 76-101）；文件及 M08 账户包没有查询 `config_revision/dispatch_revision`，也没有调用 `account_health_jobs_input_outbox` 的 reserve/enqueue 入口。
- 结果偏差：已存在健康状态/运行态的账户被 Go 删除后，health worker 不会收到删除 tombstone，旧的 `account_health_current_state`、抑制/排程状态或下游运行态可能继续保留，直到其他路径偶然刷新；Node 删除事务保证该清理事件与软删除原子提交。该差异独立于授权撤销，即使没有任何授权关系也会发生。
- 结论：这是已提交 M08 的确定运行态副作用遗漏，当前仅记录，未修改 Go 代码。

### 2026-09-05：删除账户未触发缓存与网关运行态失效

- Node 基线：Node SQLite 删除事务提交后，只要确实删除了账户，就依次刷新全部分组账户统计、失效每个账户 lookup cache、失效 group-account-id cache、清空 resource-authorization lookup caches，并广播 `account_deleted` 的 gateway runtime 与 authorization quota 失效（`backend/src/storage/account-delete-cleanup.repository.ts` 行 149-157）；PostgreSQL 异步路径同样在事务提交后执行这些失效。
- Go 实现：历史 `backend-go/projects/gateway/internal/accounts/routes.go` 的 `remove` 在 `Store.Delete` 成功后只写操作日志并返回 204（行 496-543）；历史 `Store` 仅持有数据库、密钥、时钟和 ID 工厂，没有 cache invalidator、runtime invalidation bus、统计 dirty marker 或授权 lookup 清理依赖，也没有删除后的等价调用。
- 结果偏差：Go 删除后，已有账户 lookup、分组账户 ID/统计、资源授权读取及网关运行时/授权配额缓存可以继续命中删除前状态；即使数据库软删除已经提交，请求仍可能短时间选择已删除账户或旧授权来源。Node 将这些失效安排在提交后，保证读路径最终切换到删除后的状态。
- 结论：这是独立于“数据库是否删除成功”的确定副作用缺失，当前仅记录，未修改 Go 代码。

### 2026-09-05：ENGAGED 锁配置更新未按 Node 规则重算 deadline/保留 lease

- Node 基线：`backend/src/storage/account-lock.repository.ts` 的 `setAccountLockAsync` 在保留 `ENGAGED` 事件时，若 death timeout 改变，会以原 `incidentStartedAt + timeout` 重算 `deadlineAt`（行 174-181）；只有 retry/death 配置实际变化时才清除 `nextRetryAtMs`、`leaseId`、`leaseUntilMs`，两项都未变化则完整保留已有 retry lease（行 212-214）。
- Go 实现：历史 `backend-go/projects/gateway/internal/accounts/lock.go` 的 `SetLock` 只把已有 `incidentStart/deadlineAt` 原样带回，不依据新 timeout 重算 deadline（行 165-190）；其 upsert 的 `ON CONFLICT` 更新无条件将 `next_retry_at_ms`、`lease_id`、`lease_until_ms` 设为 `NULL`（行 192-210），即使 lock-config 只是重复提交相同配置也会清掉当前重试租约。
- 结果偏差：处于 `ENGAGED` 的账户修改 death timeout 后，Go 仍沿用旧死亡截止时间，可能提前或延后锁死；重复提交未变化的配置也会释放正在执行/等待中的 retry lease，改变失败重试调度。Node 对两种场景分别保持时间语义和租约语义。
- 结论：这是已提交 M08 锁状态机的确定行为偏差，当前仅记录，未修改 Go 代码。
