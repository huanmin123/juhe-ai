## 问题概述

- 现象：K2 的 Go `authsys` 即使在补齐真实入口后，仍会在高权限临时令牌、超级管理员治理和写入所有权上改变 Node 的安全结果。
- 期望：只有配置白名单来源的管理员可以申请临时访问令牌；系统账户管理接口不得创建或提升 `super_admin`；账户写入必须受唯一 owner handoff 门禁保护，并在 PostgreSQL 下串行维护至少一个 active `super_admin` 的不变量。
- 实际：
  1. 历史 Go 实现曾没有来源 IP allowlist 依赖或检查；该差异已由 `a60f47a2b` 补齐。当前实现继续对齐 Node 的严格参数契约：未知字段、显式 `null`、非对象和非整数 TTL 返回 400，同时接受 `900.0` / `9e2` 这类 JavaScript 整数语义数字。白名单拒绝仍需真实 gateway 入口 smoke 复核。
  2. 历史 Go 管理 HTTP 层曾把 `super_admin` 传入账户 Store，使现有超级管理员能够通过普通系统账户接口新增或提升超级管理员；该角色治理差异已由 `31207137d` 修复。底层 Store 仍保留 `super_admin` 供内部 seed/既有账户路径使用，不代表管理 API 可以创建或赋予该角色。
  3. Go `authsys.AccountStore` 直接执行账户写入，未持有 `OwnerGate` 或 `CheckContract`；不满足 `Confirmed`、`SchemaReady` 或 `NodeWriterStopped` 时仍不能 fail-closed。它绕过了同仓库已有 `internal/business/system_accounts` 的 handoff 约束。
  4. Node 对 PostgreSQL 系统账户角色变更使用 advisory transaction lock；Go 仅锁定目标账户行并统计其他超级管理员。并发降级最后两个 active `super_admin` 时，两个事务可各自看到对方仍有效并共同提交，最终没有可登录的超级管理员。
- 影响范围：非受信网络可取得短期高权限访问令牌；权限治理边界被扩大；切换期间可能出现 Node/Go 双写；并发管理操作可能永久锁死管理面。

## 根因与证据

- Node 临时令牌入口：`backend/src/modules/auth/auth.routes.ts` 在校验凭据前调用 `isTemporaryAccessSourceAllowed`；其配置来自 `runtimeConfig.auth.temporaryAccessIpAllowlist`。
- Go 临时令牌入口：`backend-go/projects/gateway/internal/authsys/routes.go` 已包含 allowlist 判断；`3b8497c1a` 又补齐了与 Node `.strict()` 和 JavaScript number 语义一致的请求解析。allowlist 的真实启动配置和 gateway 入口仍受 BUG-0152 约束，未在本切片宣称端到端完成。
- Node 系统账户 schema：`backend/src/modules/system-accounts/system-accounts.routes.ts` 的 create/update role 均是 `z.enum(['admin', 'user'])`；`31207137d` 使 Go 管理 HTTP 层同样拒绝 `super_admin` 和未知角色，底层 `store_accounts.go` 的内部角色集合不应与管理 API schema 混淆。
- Node 使用 `pg_advisory_xact_lock` 维护 active super-admin 不变量：`backend/src/storage/system-accounts.repository.ts`；Go `store_accounts.go` 只执行当前行 `FOR UPDATE` 和普通计数查询。
- 审计对象为 `af841ce7a094bc66fbbb0c3817ea1fc0797245f1..fbad7b341b4fc5a7ae7457668b867f6b7091213d`；没有纳入工作区未提交文件。

## 修复与验证

- 已完成切片：`a60f47a2b` 补齐临时令牌来源 allowlist；`3b8497c1a` 冻结 Node 等价的严格请求参数和 TTL 数字契约，并加入回归测试。
- 已完成切片：`31207137d` 将管理 HTTP create/PATCH 的 role 收敛为 `admin | user`，并以回归测试覆盖 `super_admin`/未知角色。
- 未完成范围：复用或等价实现带 owner gate 的系统账户 Store；PostgreSQL 使用与 Node 等价的事务级串行化策略。
- 禁止方案：不得借助 Node HTTP/IPC 调用补救，也不得以“Go 资源充足”为由放宽权限、唯一写入或一致性门禁。
- 必需验证：非白名单/白名单临时令牌 golden；系统账户 role 矩阵；owner handoff 三个拒绝分支；两个并发 role/status 修改的 PostgreSQL 测试；真实 gateway 入口 smoke。
- 当前验证：临时令牌定向测试及 `31207137d` 后的 `go test ./projects/gateway/internal/authsys -count=1 -timeout=120s`、同命令 `-race`、`go vet ./projects/gateway/internal/authsys` 和 `git diff --check` 均通过；仍未覆盖 owner handoff、PostgreSQL 并发或真实 gateway 入口。

## 完成总结

- 结论：这是 BUG-0152 入口恢复后会立即暴露的独立安全与一致性缺陷；K2 不得作为认证唯一 owner 切换。
- 后续建议：修复后以 Node/Go 路由级 golden 加 PostgreSQL 并发 fixture 复审，不以包内单元测试通过作为准入依据。
