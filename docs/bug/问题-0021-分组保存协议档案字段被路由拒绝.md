## 问题概述

- 现象：Mac 现网 `AI 分组管理` 编辑 `福利` 分组时报错 `分组参数无效`。
- 期望：前端保存分组时提交 `providerProtocolProfileId`、高并发调度策略和状态字段，后端正常通过路由校验并进入更新逻辑。
- 实际：后端 `groups.routes` 的 Zod `groupSchema` 使用 `.strict()`，但没有声明 `providerProtocolProfileId`，导致前端提交当前字段结构时在路由层被直接拒绝。
- 影响范围：管理侧和用户侧分组创建 / 编辑，只要请求体携带 `providerProtocolProfileId`，都会在旧运行包中返回 `分组参数无效`；已存在的分组数据本身不受影响。

## 复现步骤

1. 在 Mac 现网打开 `AI 分组管理`。
2. 编辑 `福利` 分组并保存。
3. 旧运行包返回 `400`，页面提示 `分组参数无效`。
4. 只要请求体包含 `providerProtocolProfileId`，即使字段值为 `profile_gpt_openai_v1`，也会被路由 strict schema 拒绝。

- 系统：macOS 服务，端口 `3001`，系统 LaunchDaemon 运行。
- 是否稳定复现：是

## 根因分析

- 表象：页面保存失败，后端返回统一错误文案 `分组参数无效`。
- 真实根因：`backend/src/modules/groups/groups.routes.ts` 的 `groupSchema` 漏掉了存储层和前端已经使用的 `providerProtocolProfileId` 字段；`.strict()` 把该字段视为未知字段，导致请求还没进入 `updateGroup`。
- 为什么会发生：供应商协议档案字段已经在 `repositories.createGroup/updateGroup`、前端分组表单和功能文档中成为当前契约，但路由层 schema 没有同步更新；错误文案又只返回笼统的 `分组参数无效`，现网容易误判为数据异常。

## 修复方案

- 修改点：
  - `backend/src/modules/groups/groups.routes.ts`：在 `groupSchema` 中增加 `providerProtocolProfileId: z.string().trim().min(1).optional()`。
  - `backend/src/scripts/regression/group-scheduling-policy-regression.ts`：补充真实 Express 路由创建 / 更新回归，覆盖前端保存分组时携带 `providerProtocolProfileId` 的请求体。
  - Mac 现网热修当前运行包 `backend/dist/modules/groups/groups.routes.js`，并重启系统 LaunchDaemon。
- 行为影响：分组创建 / 更新接口接受当前协议档案字段；具体协议档案是否有效仍由 repository 层统一校验。
- 发布异常处理：若再次出现 `分组参数无效`，先查路由 Zod schema 是否与前端请求体字段同步，再查请求体是否带了未声明字段。
