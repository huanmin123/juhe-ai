# BUG-0149：多轮生产发布停机与流程失控

## 1. 状态

整改中。发布控制器已收敛为独立 candidate、带时效和文件指纹的 preflight、原子 handover、保留旧槽和反向 switchback；仍需在下一次目标 Mac 正式发布中证明完整无感流程。

## 2. 现象与影响

最近多轮上线出现过硬停机、候选启动失败、切流后业务请求异常、服务 health 正常但浏览器不可用、生产状态与私有资料漂移，以及单次发布持续数小时。最严重的一次在 active release 已停止后继续现场修复，客户端只能进入“服务正在恢复”。

这不是单个代码缺陷，而是发布生命周期失控：慢操作进入生产关键路径，candidate 证据不完整，active 与 temporary 边界不稳定，切流、观察、回切和清理没有形成一条唯一状态机。

## 3. 已确认的故障类型

1. **先停旧服务再部署。** 同端口、同 label 原地 apply 会逐项重启 active 拓扑；任一后续问题都会直接扩大为用户停机。
2. **候选依赖和配置在现场才发现。** macOS 离线依赖、Node 版本、新设置/schema 和 F3 专用配置没有全部在启动前冻结，造成候选反复重建。
3. **health 误代替业务验收。** API base 被 Windows/MSYS 转成磁盘路径时，静态页面和 health 仍为 `200`；F3 listener `204` 也不能证明审计最终持久化成功。
4. **运行拓扑不唯一。** 历史 release、temporary 进程、LaunchDaemon 和 Nginx fragment 曾同时残留，使 owner、route 和回滚目标无法快速确认。
5. **数据与清理混入发布。** 备份、非业务数据清理、Redis 清理和旧文件删除进入同一窗口，增加时间和不可逆风险。
6. **状态资料漂移。** 私有连接快照、当前端口、release、验证结论和 checksum 曾与现场不一致，导致排障从重新取证开始。
7. **重复门禁串行执行。** 原 handover 在 preflight、切流前、切流后分别重复完整稳定观察，安全证据没有复用，增加了关键路径时间。

相关专项问题包括 [BUG-0116](问题-0116-候选缺设置被误报为网关请求体无效.md)、[BUG-0147](问题-0147-mac候选发布依赖预检缺失.md) 和 [BUG-0148](问题-0148-Windows路径转换破坏前端APIBase.md)。

## 4. 根因

- 没有强制把“构建与候选准备”和“生产切流”分成两个生命周期。
- candidate 不是唯一、长期存活且可随时接管的槽，而是临时操作过程中不断变化的对象。
- 发布完成条件偏向进程和 HTTP 状态，缺少最终 bundle、真实浏览器、数据 owner 和读回证明。
- 回滚被理解为重新部署旧版本，而不是对仍在运行的旧槽做原子路由回切。
- 每次异常都追加临时步骤，没有把步骤收敛回一个状态机和一个证据记录。

## 5. 整改

- 生产高性能拓扑只允许独立 candidate + `performance-handover-controller.sh`。
- 所有慢操作在旧槽承流期间完成；正式切流阶段禁止构建、依赖安装、schema/data 清理和现场改配置。
- preflight 将两槽与入口放在同一个稳定循环中验证，写入 5 分钟有效的 route/plan/fragment/Nginx 指纹；凭证时效在生成时冻结，后续命令不得延长。
- takeover 校验凭证后只做一次实时身份复核、原子 route 替换和一轮并行稳定观察，不重复切流前完整窗口。
- 控制器在探测前生成并校验自己的 rollback/target 快照，紧邻 route 变更再次检查 TTL 和全部指纹，只切换已验证字节。
- committed 后的正常回退统一为反向 `preflight -> switchback`；新槽已宕机时显式使用 `preflight --degraded-source -> switchback`，只证明旧槽目标和 route 身份。`recover` 只处理未提交中断。
- 旧槽在观察期内始终保留，失败不重新部署旧版本。
- 发布包以标准 JavaScript AST 解析器检查 bundle；不再使用手写词法状态机，也不以 health 代替浏览器业务页。
- 新增 [生产发布快速流程](../deploy/生产发布快速流程.md)，把目标耗时、允许动作、停止条件和证据格式固定下来。

## 6. 验收

下一次正式发布必须证明：candidate 准备失败对用户无影响；preflight 凭证过期、探测期间 TTL 跨界或 route/plan/fragment/Nginx 文件变化会拒绝 takeover；切流在目标 60–120 秒内完成 committed 稳定证明；新槽在 reload 后或 committed 后宕机时旧槽无需重启即可自动恢复或通过 degraded-source 反向回切；整个窗口没有先停 active、没有现场构建和没有清理共享数据。

在目标 Mac 完成这次正式证明前，只能说“流程和回归已整改”，不能说“无感上线已经生产验证”。
