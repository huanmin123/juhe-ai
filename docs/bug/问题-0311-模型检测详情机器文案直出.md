# 问题-0311：模型检测详情机器文案直出（题库 reason 空串、未知原因码、英文检测项消息）

## 基本信息

- 编号：BUG-0311
- 状态：已修复（2026-10-12，工作区待提交）
- 严重程度：P3（展示缺陷：判定、计分、处罚与调度均正确，三类面向用户的字段不可读）
- 发现时间：2026-10-12
- 发现方式：生产检测记录取证（详情页人工核对）
- 模块：`backend-go/projects/gateway/internal/modelcheckowner/custom_quiz.go`（reason 透出）× `frontend/src/views/model-checks/modelCheckFormatters.ts` 与 `ModelCheckRunDetailDrawer.vue`（reasonCodes 分组翻译与检测项消息）
- 关联文档：`docs/functions/模型检测设计.md`（§5.7「items[].reason 请求失败形态契约」、§15.3「reasonCodes 分类与前端翻译契约」）

## 问题概述

- 现象：生产 2026-10-12 run-b897cfd203d7a4c7ec30d4e6（快速检测，gpt 账户 × gpt-6.1-sol）整体 completed 100/100，但题库测试的「水果题」作答三次尝试全部上游超时——前两次 4.9s / 24.3s 拿到 HTTP 200 后流式零输出，被 20s / 30s 预算切断；第三次 40s 未收到响应头。整轮结论与通用族证据正常，缺陷集中在详情页三类字段：
  1. 题目 `items[].reason` 显示为 `-`——请求失败形态 reason 为空字符串，「已重试几次、每次什么结果」只留在 JSON 证据里，不进用户可见字段。
  2. 诊断依据显示 7 个「未知原因码：xxx」——`reasonCodes` 混装证据覆盖缺口码与异常码两类语义，前端只有 16 项异常码翻译，覆盖缺口码（裸族名 / `_partial` / `_evidence_insufficient` / `_not_applicable`）全部落「未知原因码」兜底。
  3. 检测项消息（`evidence.message` / `error` / `error_message`）英文原文直出（如 `J3b probe timed out`）。
- 期望：面向用户展示的证据字段必须中文并可读；证据覆盖缺口与诊断异常是两类语义，分组呈现而不是混在一个翻译表里；请求失败类证据把尝试次数与结果写进用户可见字段。
- 影响范围：模型检测详情页题库小计、诊断依据与各检测项消息展示；不涉及判定、计分、处罚与调度（本例整轮 completed、100/100、无处罚联动均为正确行为）。

## 根因分析

1. `custom_quiz.go` 请求失败形态（skipped + `excludedFromScoring`）的 `items[].reason` 写空字符串——「请求未完成 + 尝试次数」这一用户最需要的事实未进入展示字段。
2. 前端 `ModelCheckRunDetailDrawer.vue` 的 reasonCodes 翻译是单表平铺：16 项异常码 + 「未知原因码」兜底；而生成侧 `BuildTrustReport`（`modelcheckowner/trust.go`）本就把 `AggregateEvidence` 的族状态写成四形态覆盖缺口码（Missing→裸族名、Partial→`<family>_partial`、Invalid→`<family>_evidence_insufficient`、Neutral→`<family>_not_applicable`），另有 `model_response_evidence_unavailable`——这些码从未进过翻译表。快速检测是协议一致性子集，覆盖缺口码必然出现，必然显示「未知原因码」。
3. 检测项消息渲染直接取 `message`/`error`/`error_message` 原文，无三级回退、无英文错误翻译映射。

## 修复方案（三项，同批交付）

1. **后端 reason 透出**（`custom_quiz.go`）：requestFailure=true 时 `reason = 请求未完成：<原因短语>`，证据带 `retryMaxAttempts>0` 时追加 `（尝试 N/M 次）`（N=retryAttemptCount+1）；原因短语按证据 error 原文映射：`J3b probe timed out`→上游超时、`J3b probe canceled`→探针已取消、前缀 `J3b upstream request failed: `→上游请求失败：<原文>、`J3b upstream response read failed`→上游响应读取失败、前缀 `J3b upstream returned HTTP `→上游返回 HTTP <码>、`J3b upstream response exceeded limit`→上游响应超限、`J3b OAuth Codex response stream incomplete`→OAuth Codex 响应流未完成、error 为空→整条 `请求未完成`、其他→原文直出；verdict 仍为 `unavailable`（前端显示"不可判定"），不计分不扣分。契约见设计文档 §5.7。
2. **前端 reasonCodes 分组翻译**（`modelCheckFormatters.ts` + `ModelCheckRunDetailDrawer.vue`）：按机械规则分两组——「证据覆盖缺口」（后缀码/裸族名/`model_response_evidence_unavailable`，族名中文化；`detectionScope=protocol_consistency` 且有缺口时追加「本次为协议一致性子集检测，其余维度由深度检测覆盖」）与「诊断依据」（既有异常码表 + 未知码「未知原因码：xxx」兜底，组空时「未发现已知异常原因」）；后端生成逻辑不变，分类翻译是前端展示层规则。契约见设计文档 §15.3。
3. **检测项消息中文化**（`modelCheckFormatters.ts`）：`checkMessage` 按 `message` → `error` → `error_message` 三级回退取值，并按探针英文错误翻译映射表翻译：`J3b probe timed out`→探针请求超时（上游未在预算内完成响应）、`J3b probe canceled`→探针已取消、`J3b upstream request failed: X`→上游请求失败：X、`J3b upstream response read failed`→上游响应读取失败、`J3b upstream returned HTTP N`→上游返回 HTTP N、`J3b upstream response exceeded limit`→上游响应超过大小上限、`J3b OAuth Codex response stream incomplete`→OAuth Codex 响应流未完成。

涉及文件：`backend-go/projects/gateway/internal/modelcheckowner/custom_quiz.go`、`frontend/src/views/model-checks/modelCheckFormatters.ts`、`frontend/src/views/model-checks/ModelCheckRunDetailDrawer.vue`、`docs/functions/模型检测设计.md`、本文档。

## 遗留观察

- 组件级单测缺口：`ModelCheckRunDetailDrawer.vue` 的 `trustCoverageText` / `trustAnomaliesText` computed（protocol_consistency 追加说明、覆盖组空态「无」、异常组空态「未发现已知异常原因」）当前无组件级单测覆盖；现有 vitest 只覆盖格式化函数（`modelCheckFormatters.test.ts`），后续引入组件测试设施时补齐。
- 上游「HTTP 200 后流式零输出卡死」形态（前两次 4.9s/24.3s 零输出被预算切断、第三次 40s 无响应头）的重试经济学：三次尝试共约一分半才确认该题不可用，是否需要更早放弃（如零输出提前终判）未实施、另行评估——重试阶梯语义受 BUG-0287 / BUG-0292 契约约束，改动需独立裁决。
- OAuth Codex 语义失败形态的英文直出残留：`J3b OAuth Codex response must be SSE`、`J3b OAuth Codex response contains malformed SSE data` 及上游 `response.failed` 信封原文等仍按「未知原文直出」兜底（前端英文直出、后端组装为「请求未完成：<原文>」），不吞信息是既定语义；后续可作为映射补充候选。
