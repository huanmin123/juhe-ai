## 问题概述

- 现象：Gemini JSON 响应命中通用 error object 响应检查后，请求长时间不返回，最终由客户端侧超时。
- 期望：服务端拦截上游错误响应；如果策略没有要求换账号或避让账号，应立即返回网关失败，不应让客户端等待。
- 实际：`retry_no_avoidance` 命中后进入服务端重试，但候选账号集合没有变化，统一调度反复选中同一个账号。
- 影响范围：非流式响应检查命中 `retry_no_avoidance` 且当前请求没有其他候选变化时，可能出现同账号无限重试。

## 复现步骤

1. 使用 Gemini native 分组和默认响应检查策略。
2. 上游返回 HTTP 200，但 JSON body 包含 `{ "error": { "status": "UNAVAILABLE" } }`。
3. 以普通 Gemini 客户端画像请求 `generateContent`，观察请求不按预期快速收口。

## 根因分析

- 表象：客户端看到请求卡住或超时。
- 真实根因：`retry_no_avoidance` 的运行时语义是 `retryEnabled=true` 且 `accountSwitch=none`。路由层收到 `retryUpstream=true` 后重新进入统一调度，但没有把当前账号加入本轮排除集合，也没有同账号重试上限，导致候选集合和优先级不变，调度结果仍是同一个账号。
- 为什么会发生：响应检查的“重试但不避让账号”原本用于阻止坏响应写给客户端，不等于允许无限同账号重试；路由层缺少“重试是否会改变调度结果”的收口判断。

## 修复方案

- 修改点：网关路由处理 `response_inspection` 重试时，如果本次策略没有触发账号排除、换账号或运行态避让，直接调用统一失败响应收口，不再继续下一轮调度。
- 行为影响：`retry_next_account`、`avoid_account_ttl`、`avoid_upstream_bucket_ttl` 等会改变候选集合的策略仍继续服务端调度；`retry_no_avoidance` 不再无限重试。
- 发布异常处理：如果用户希望普通客户端也切账号，应把策略动作改成 `retry_next_account`，而不是依赖 `retry_no_avoidance`。

## 下次遇到

- 先查响应检查命中的 `action`、`accountSwitch`、`retryEnabled` 和路由层 `streamServerRetryExcludedAccountIds` 是否发生变化。
- 重点看重试是否改变候选集合；如果候选集合没有变化，应返回失败或使用有上限的同账号重试。
- 避免把 `retry_no_avoidance` 理解成无限服务端重试；它只表示不写账号运行态避让。
