## 问题概述

- 现象：已安装 checkpoint 的会话再次压缩时，前轮提取的 importantToolResults/imageMemories 不进入新 checkpoint。
- 期望：prior snapshot 的重要工具结果与图片语义记忆在续跑压缩中保留并累积。
- 实际：这两类条目反序列化必然失败被跳过，对应长朧行恒空，模型永久丢失该长期记忆。
- 影响范围：安装 checkpoint 后再次触发压缩的会话（恢复 pending 压缩、水位再触发）；durable_memory/task_state 为对象不受影响。

## 复现步骤

1. 会话触发上下文压缩并安装 checkpoint（checkpoint 含 tool_result/image_observation 条目）；
2. 再次触发压缩（恢复 pending 压缩或水位再触发）；
3. 新 checkpoint 的 importantToolResults/imageMemories 为空，前轮记忆丢失。

## 环境信息

- 分支 / 版本：master
- 数据状态：新 checkpoint 生成后，旧记忆无法从 checkpoint 链恢复（需依赖原始消息重新提取）
- 是否稳定复现：是（类型形态必然不匹配）

## 根因分析

- 表象：续跑压缩后长程记忆为空。
- 真实根因：`compaction_service.go` `initialSnapshot`（约 :563-567）把所有 checkpoint 条目统一 `json.Unmarshal(..., &content)` 到 `map[string]any`；而写入侧（:821-826 snapshotEntries）`tool_result`/`image_observation` 条目的 contentJSON 是数组（`json.Marshal([]map[string]any)`），数组 JSON unmarshal 到 map 必然失败 → continue → prior snapshot 的 importantToolResults/imageMemories 恒空。
- 为什么会发生：Node 原版按 content 形态直接赋值（数组保真），Go 迁移统一走 map 反序列化引入形态假设，属迁移回归。

## 修复方案

- 按 kind 分派 unmarshal 目标（数组用 `[]any`/`json.RawMessage` 保真），补"已有 checkpoint 再压缩"记忆保留测试。

## 验证结果
- `compaction_service.go` `initialSnapshot` 按 entry.kind 分派 unmarshal 目标：`tool_result`/`image_observation` 改为 `[]any`（数组保真，对应 ImportantToolResults/ImageMemories），对象 kind（durable_memory/task_state）走原 map 分支逐行未动，对齐 Node chat-context-compaction.ts:390-394 数组直接赋值语义。
- 新增 `bug0245_compaction_initial_snapshot_test.go`：写入侧 snapshotEntries → contextEntry → initialSnapshot 读回，DeepEqual 断言两类记忆数组与 prior 一致 + 对象 kind 回归不变 + 畸形数组 kind 跳过不破坏恢复。
- `go test ./projects/gateway/internal/chat/ -count=1` 全绿（48.613s）；gofmt/vet 干净。
