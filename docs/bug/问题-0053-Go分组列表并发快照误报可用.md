- 修复提交：`0eb214fd7`、`0a4c622df`

## 问题概述

Go `GET /groups` 与 `GET /my-groups` 直接返回 `group_account_stats.current_concurrency` 预聚合值，并固定声明 `runtimeSnapshot.accountConcurrencyAvailable=true`。Node 当前契约会对 owner 分组读取 Redis 实时并发；读取失败时保留原值并标记不可用。

结果是 Go 列表可能展示过期并发，同时把依赖失败误报为可靠零值；同一分组列表与详情也可能显示不同并发。

## 根因分析

早期列表迁移为避免响应暴露 `accountIds`，错误地把“不返回账户 ID”理解成“不需要服务端并发快照”。实际上 Node 会在映射轻量列表 DTO 之前使用内部 `accountIds` 读取 Redis，随后再从响应中删除账户 ID。

## 修复方案

- 新增当前页 owner 分组到账户 ID 的批量 SQL，保持启用绑定、未删除账户和有效授权实例过滤。
- 不为 authorized 分组读取或返回 owner 账户 ID。
- 账户 ID 去重后按每批最多 100 个调用现有 Redis reader，禁止 N+1。
- Redis 成功时覆盖 owner `currentConcurrency` 并设置逐项可用标记。
- Redis 失败时列表仍返回 `200`，保留预聚合并发，仅把需要快照的 owner 项和顶层快照标记为不可用。
- 整页没有任何 owner 账户时不调用 Redis，也不凭空增加逐项可用字段；顶层仍为可用。

## 防复发要求

- 轻量响应不返回内部字段，不代表服务端不能用该字段完成运行态装配。
- Redis 快照失败必须区分“零值”和“不可用”，不能静默降级成可信零。
- owner 与 authorized 的运行态语义分别测试；authorized 不能因 owner 快照实现而泄露账户 ID。

## 完成总结

Go 分组列表已对齐 Node 的实时并发覆盖、软失败和字段存在性语义。真实 PostgreSQL / Redis 和前端页面联调仍属于接管门禁。
