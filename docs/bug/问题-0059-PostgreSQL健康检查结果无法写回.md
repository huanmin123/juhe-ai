# BUG-0059 PostgreSQL 健康检查结果无法写回

## 基本信息

- 编号：BUG-0059
- 状态：已修复（生产已验证）
- 严重程度：P1
- 发现时间：2026-07-11
- 发现方式：用户反馈与生产日志排查
- 模块：后端 / worker / AI 账户 / PostgreSQL / 健康检查
- 关联计划：无
- 关联 bug：无

## 问题概述

生产环境中 `pending_test` 账户长期显示“待检查”。后台探针实际已经请求上游，但成功或失败结果都没有写入 `last_health_check_at`，账户无法激活，也无法显示失败原因。

## 根因分析

PostgreSQL 健康检查成功和失败写回 SQL 使用 `(? IS NULL OR ...)` 表达可选 CAS 守卫。`?` 转换为独立 PostgreSQL 占位符后，位于 `IS NULL` 左侧的参数没有类型上下文，数据库返回 `42P18: could not determine data type of parameter`。

任务异常又只记录“账号健康检测任务已用尽”，没有输出底层异常。失败账户的 `next_health_check_at` 无法推进，周期任务每分钟重复选中同一批旧账户，进一步阻塞新账户。

## 修复方案

- PostgreSQL 写回只为实际存在的 `expectedConfigRevision` 和 `observedAt` 动态追加 SQL 条件及参数，不再传未定型 NULL 守卫。
- 周期候选优先处理 `pending_test`，并在待检查账户内按最近更新时间倒序，保证即时投递失效时新账户也能尽快兜底。
- 队列耗尽日志保留底层异常，避免数据库写回故障被“本轮跳过”掩盖。
- PostgreSQL smoke 同时覆盖配置版本和观察时间守卫。

上线清理积压时又发现，少量从未完成后台检查的 `pending_test` 账户保留了未来的 `next_health_check_at` 和近期成功信号。候选查询现对 `pending_test + last_health_check_at IS NULL` 同时忽略遗留复检时间和普通成功信号，确保首次后台检查立即进入周期队列；人工诊断或真实流量成功不能替代后台激活检查，已有失败记录的账户仍遵守短退避时间。

## 验证记录

| 验证 | 结果 |
| --- | --- |
| 生产只回滚 SQL 复现 | 稳定返回 PostgreSQL `42P18` |
| `test:account-health-check` 红绿回归 | 通过 |
| PostgreSQL 账号探测 smoke 守卫 | 已补充，待具备测试库时执行 |
| 类型检查、正式构建 | 通过 |
| 生产状态推进 | 通过；前两轮将从未写回的待检查账户从 99 降至 61，成功账户自动激活，失败账户写入原因和 15 分钟复检时间 |
| 待检查首次调度回归 | 通过；覆盖 SQLite 行为及 PostgreSQL 候选条件 |

## 防复发要求

- PostgreSQL 可选条件不能使用无显式类型上下文的 `$n IS NULL` 参数。
- 后台任务的最终失败日志必须包含原始异常。
- 对健康检查成功和失败写回同时覆盖 PostgreSQL CAS 参数组合。
- 从未完成后台检查的待检查账户不能被遗留的未来复检时间延迟。

## 完成总结

修复后新账户保存仍立即触发检查；即时消息失效时，分钟级周期任务优先兜底待检查账户。检查失败会写入原因和退避时间，检查成功会自动激活。
