# BUG-0345 晚到写入的用量记录被统计游标越过，日/小时统计永久漏计

> **2026-11-03 处理结论：已根治待发布（revision 16）。** 机制根因是「按 `(created_at, id)` 键集游标消费」隐含假设「游标越过某行时该行已落库」，而 `created_at` 是请求终态时刻、落库是物理写入（生产实测最大晚 299,163 ms，对 5 分钟缓冲只剩 837 ms 余量）。修复把两个统计聚合器改为**消费未消费行**（`usage_records` 新增 `usage_stats_aggregated_at` / `client_ip_stats_aggregated_at` 两个消费水位列 + 部分索引），消费与记录晚到多久无关，不再依赖任何固定缓冲窗口。存量缺口（11-02 的 94 条等）属历史，不回填。

## 问题概述

- 现象：`usage_records` 的行数/错误数与 `usage_stats_daily` 对不上；差异集中在 503/429 失败行，且这些行的 `id` 内嵌时间戳（写入时刻）比 `created_at` 晚 4~5 分钟。
- 期望：每条落库的用量记录都应被两个统计聚合器各消费一次。
- 实际：聚合器按 `(created_at, id)` 键集游标推进；当某行在游标越过其 `created_at` 之后才落库，该行永远不会被读到。
- 影响范围：`usage-stats-aggregation` 的全部派生统计表（日/小时/模型/错误/延迟/账户质量/授权摘要）与 `client-ip-stats-aggregation` 的客户端 IP 日聚合；影响幅度小但永久（不可自愈）。

## 复现步骤

1. 构造一条 `created_at` 早于当前聚合游标、但晚于游标推进时刻才写入 `usage_records` 的记录。
2. 等待统计聚合轮执行（游标已越过该 `created_at`）。
3. 对比 `usage_records` 与 `usage_stats_daily` 的 `request_count`：该行只在原始表、不在统计表。

## 根因分析

- 表象：日统计 `request_count`/`error_count` 比原始表少，缺口恰好等于「写入时刻晚于统计快照」的行数（11-02 缺口 94 条 vs 晚到行 92 条，其余 2 条为 23:14:42 后写入的边界行）。
- 真实根因：`jobs/internal/statsagg/aggregate.go` 的 `AggregateUsageStatsBatch` 以
  `WHERE created_at <= safeCreatedBefore AND (created_at > cursor_created_at OR (created_at = cursor_created_at AND id > cursor_id))`
  取批，`safeCreatedBefore = now - 15s`（另与 gateway buffer 5min 取较早者，见 `ingestgate/ingestgate.go`）。游标一旦推进到 `T`，任何 `created_at <= T` 但落库晚于游标的行都不会再被选中——键集游标对「乱序到达」不设回补窗口。`clientipagg.go` 的 15 秒延迟同构，且延迟更小、更易触发。
- 为什么会发生：`created_at` 由网关在**请求终态时**写入，而 id 内嵌的时间戳取自落库时刻；两者在正常路径相差毫秒级，但**请求挂起到 wall budget 超时**时，`created_at` 是请求结束时刻，落库时刻在其后。生产实测差值集中在 268~269 秒，与 `gatewayrouting.DefaultGatewayRequestWallBudgetMs = 270_000`（270 秒）精确吻合：这些请求的上游尝试本身 300~500ms 就失败了（`duration_ms=301~414`），但请求一直重试/等待到 270 秒 wall budget 耗尽才以 `gateway_request_wall_budget_exhausted` 终态落库。
- 为什么安全窗口兜不住：15 秒 + gateway buffer 5 分钟只能覆盖「仍在队列里」的记录（通过 pending backlog 把 safeCreatedBefore 压后）；一旦记录**已经落库但落库时刻晚于游标**，任何固定窗口都只能降低概率，不能消除机制。全量实测最大延迟 299,163 ms 对 300,000 ms 窗口只剩 837 ms 余量。

## 根因修复（2026-11-03，已实施）

**方案：消费水位列（标记式消费），替代键集游标选行。**

- schema（revision 16，纯 DDL 加法）：`juhe_usage.usage_records` 新增 `usage_stats_aggregated_at` / `client_ip_stats_aggregated_at` 两列（NULL = 未被该统计消费）+ 两条部分索引 `(created_at, id) WHERE <列> IS NULL`。
- 选行：`WHERE <水位列> IS NULL AND created_at <= safeCreatedBefore ORDER BY created_at, id LIMIT n`。与 `created_at` 顺序、游标位置、记录晚到多久都无关。
- 标记：聚合写与水位标记在**同一事务**内提交（`statsagg.MarkUsageRecordsConsumed`，按 `id` 定位）；聚合失败回滚时标记一并回滚，本批下轮重新消费，不产生「已标记未聚合」的空洞。
- 存量结算（首次启用自举）：统计写入是**增量累加**，若把加列前的历史行当待消费会整体重算一遍（翻倍）。聚合器因此先探测「表内是否已有任何标记行」；没有且旧游标存在时，先把 `(created_at, id) <= 旧游标` 的行标记为已消费再正常消费。旧游标遗漏的晚到行同样被结算为已消费——历史缺口不可分辨，宁可保留已知缺口也不冒全量重复计数的风险。
- lag 口径：改为「最旧未消费记录的年龄」。旧口径取「最后消费行」的时刻，晚到行造成的积压会被读成 0，正是本 bug 被掩盖的原因。
- 下游一致性：
  - `usage-stats-consistency-check` 对账窗口上界改为「最旧未消费记录」所在小时起点（无积压时退回聚合游标），避免把部分聚合的小时计入比较面。
  - 用量记录清理（删除 Key/账户）的批次选择追加「两个水位列均已消费」过滤：扣减台账假设被删行的贡献已计入统计，未消费的行留到下一批。
  - `--rebuild-usage-stats` 在清空统计面的同一事务内把 `usage_stats_aggregated_at` 全部归零并重置游标；这是该命令对源表唯一的写（原先的「源表只读」契约按此收窄）。
- 被排除的流量来源（client-ip 的 `runtime_recovery_probe` / `cooldown_retest`）同样标记消费，否则它们会永久滞留在待消费队列里，把积压读数与清理地板一起钉死。

- 行为影响：晚到记录进入统计（此前永久漏计）；`stats_job_state.lag_seconds` 语义变为真实积压年龄；清理会推迟到两个聚合器都消费完。
- 发布异常处理：纯加法 DDL，无停写窗口、无额外命令（存量结算自动完成）。发布前 `upgrade --dry-run` 因 `dbRevision < 16` 拒绝，须先 `./deploy.sh upgrade`。这两列本身旧代码不读，但**回滚二进制会被启动门禁拒绝**（库 revision=16 > 旧二进制 15），回滚必须先恢复升级前备份或把 `schema_state.schema_revision` 降到旧二进制认识的值。
- **回滚后再升级**（revision 16 特有）：回滚期间旧代码按游标消费且不写水位，这些行重新升级后会被再消费一次（重复累加）。重新升级前必须按聚合游标补结算：

  ```sql
  SET custom.settle_at = '<回滚前最后成功时间>';
  UPDATE juhe_usage.usage_records
     SET usage_stats_aggregated_at = current_setting('custom.settle_at')
   WHERE usage_stats_aggregated_at IS NULL
     AND created_at <= (SELECT cursor_created_at FROM juhe_stats.stats_job_state
                         WHERE scope_type='global' AND scope_id='' AND job_name='usage_stats_aggregation');
  ```

  `client_ip_stats_aggregated_at` 对 `client_ip_stats_aggregation` 游标同理；执行前备份；`custom.settle_at` 未设置时 `current_setting` 会报错（不静默空跑）。只回滚不再升级时无需处理。

## 下次遇到

- 先查什么：日/小时统计与原始表对不上时，先比对「行数」再比对「token/成本」；行数差通常指向聚合漏计，金额差指向计价。
- 重点看什么：`SELECT count(*) FROM juhe_usage.usage_records WHERE usage_stats_aggregated_at IS NULL`（以及 `client_ip_stats_aggregated_at`）。稳态下只应有安全截止内的新行；持续增长说明聚合被卡住（看 `stats_job_state.lag_seconds` 与任务日志）。
- 如何避免误判：`usage_stats_daily` 同时存在 `system_account_id='global'` 与各租户行，对账必须先限定 scope，否则会把「global + 租户双份」误判为重复计数。`usage_records.id` 的第 4 段是写入时刻毫秒（`usage_<date>_sNN_<ms>_<entropy>`），与 `created_at` 的差值就是写入延迟，可用来识别晚到行。
