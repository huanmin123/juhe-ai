# BUG-0345 晚到写入的用量记录被统计游标越过，日/小时统计永久漏计

## 基本信息

- 编号：BUG-0345
- 状态：待修复
- 严重程度：P2
- 发现时间：2026-11-03
- 发现方式：自查（`usage_records` 与 `usage_stats_daily` 按日对账）
- 模块：后台任务（统计聚合游标）
- 关联计划：无
- 关联 bug：无
- 责任人：后台任务维护者

## 问题概述

- 现象：`usage_records` 的行数/错误数与 `usage_stats_daily` 对不上；差异集中在 503/429 失败行，且这些行的 `id` 内嵌时间戳（写入时刻）比 `created_at` 晚 4~5 分钟。
- 期望：每条落库的用量记录都应被统计聚合消费一次。
- 实际：聚合器按 `(created_at, id)` 键集游标推进；当某行在游标越过其 `created_at` 之后才落库（写入晚于 created_at），该行永远不会被读到。
- 影响范围：日/小时/模型/错误等全部派生统计表；影响幅度小但永久（不可自愈）。

## 复现步骤

1. 构造一条 `created_at` 早于当前聚合游标、但晚于游标推进时刻才写入 `usage_records` 的记录。
2. 等待统计聚合轮执行（游标已越过该 `created_at`）。
3. 对比 `usage_records` 与 `usage_stats_daily` 的 `request_count`：该行只在原始表、不在统计表。

## 环境信息

- 分支 / 版本：Go jobs（`backend-go/projects/jobs`），生产国内单机 Docker 现行版本。
- 数据状态：近 30 天 366 条晚到行（占 0.12%），其中失败 284 条；近 12 天按日差异：11-02 94 条、11-01 8 条、10-31 5 条、10-30 23 条、10-29 5 条、10-28 11 条、10-27 6 条、10-26 4 条、10-25 2 条。
- 是否稳定复现：是（写入延迟 > 安全窗口即触发）。

## 根因分析

- 表象：日统计 `request_count`/`error_count` 比原始表少，缺口恰好等于「写入时刻晚于统计快照」的行数（11-02 缺口 94 条 vs 晚到行 92 条，其余 2 条为 23:14:42 后写入的边界行）。
- 真实根因：`jobs/internal/statsagg/aggregate.go:77` 的 `AggregateUsageStatsBatch` 以
  `WHERE created_at <= safeCreatedBefore AND (created_at > cursor_created_at OR (created_at = cursor_created_at AND id > cursor_id))`
  取批，`safeCreatedBefore = now - 15s`（`types.go:180`，另与 gateway buffer 5min 取较早者，见 `ingestgate/ingestgate.go:156`）。游标一旦推进到 `T`，任何 `created_at <= T` 但落库晚于游标的行都不会再被选中——键集游标对「乱序到达」不设回补窗口。
- 为什么会发生：`created_at` 由网关在**请求终态时**写入（`gatewayusage/service.go` 的 `CreatedAt: time.UnixMilli(completedAtMs)`，失败路径 `completedAtMs` 取 clock 当前时刻），而 id 内嵌的时间戳取自**归一化时刻**（`usageShardRecordIDFactory.GenerateUsageRecordID` 用 `now().UnixMilli()`）；两者在正常路径相差毫秒级，但**请求本身挂起到 wall budget 超时**时，`created_at` 是请求结束时刻，落库时刻在其后。生产实测差值集中在 268~269 秒，与 `gatewayrouting.DefaultGatewayRequestWallBudgetMs = 270_000`（270 秒）精确吻合：这些请求的上游尝试本身 300~500ms 就失败了（`duration_ms=301~414`），但请求一直重试/等待到 270 秒 wall budget 耗尽才以 `gateway_request_wall_budget_exhausted` 终态落库，因此 `created_at` 落在 4.5 分钟后。
- 为什么安全窗口没兜住：15 秒 + gateway buffer 5 分钟只能覆盖「仍在队列里」的记录（通过 pending backlog 把 safeCreatedBefore 压后）；一旦记录**已经落库但落库时刻晚于游标**，任何窗口都无效。

## 生产证据

- 11-02 缺口定位：`usage_stats_daily`（scope=endpoint, system_account=global）11-02 `request_count` 25,872 vs 原始表 25,966，差 94；`error_count` 7,337 vs 7,431，差 94。
- 晚到行：11-02 共 92 条满足 `id时间戳 - created_at > 120s`（全部为 `success=0`，`endpoint='POST /v1/responses'`，租户 `sysacc_1786243931319_37dea0cf` 91 条 + `sysacc_1780629399485_5c62baf2` 1 条）。
- 延迟形态：`id时间戳 - created_at` 集中于 268~269 秒（例如 07:16:59 完成 → 07:21:29 写入），与 `DefaultGatewayRequestWallBudgetMs=270_000` 吻合；这些行的 `duration_ms` 仅 301~414ms，但审计 `duration_ms` 为 268,049~269,795ms、`attempt_count=1`、`error_code='gateway_request_wall_budget_exhausted'`——即「上游尝试快速失败、请求挂到 270 秒 wall budget 耗尽才终态」。
- 全量：近 30 天 366 条晚到（>15s），0.12%；近 12 天 150 条（>2min）。错误码分布：`gateway_request_wall_budget_exhausted` 139、`upstream_http_status` 86、空 82、`no_available_upstream_account` 30、其余 <15。
- 统计任务健康：`stats_job_state.usage_stats_aggregation` 正常推进（`lag_seconds=301`，游标持续前进），对账任务 `usage-stats-consistency-check` 已装配但只覆盖**最近窗口的小时桶**，不回溯日表历史缺口。

## 修复方案（待裁决）

- **A（推荐）**：聚合取批增加「迟到回补」通道——每轮除常规游标批次外，按 `id` 内嵌时间戳（或新增 `ingested_at` 列）扫描「落库时间 > 上次水位」的行，命中未聚合的 `(created_at, id)` 时直接聚合。实现面：`statsagg/aggregate.go` + `stats_job_state` 增列（或复用 `last_success_at`）。
- **B**：改为按「写入水位」而非 `created_at` 游标（需要新增单调递增列，改动面最大但最彻底）。
- **C**：缩小问题面——让 `created_at` 与 id 时间戳同源（都用落库时刻），使晚到行自然落在未来游标之后。代价是 `created_at` 语义从「请求完成时刻」变为「落库时刻」，会影响按时间窗口的统计口径。

裁决要点：A 改动可控且不改变 `created_at` 语义；B 最彻底但需 schema 变更；C 会改变既有时间语义。建议 A，并把「日表缺口」纳入 `usage-stats-consistency-check` 的对账范围（当前只对小时桶）。

- 行为影响：修复后晚到行进入统计；历史缺口需一次性回补（需用户授权，见待办）。
- 发布异常处理：若选 A/B 涉及 schema 变更，按部署文档同步并走迁移流程。

## 下次遇到

- 先查什么：日/小时统计与原始表对不上时，先比对「行数」再比对「token/成本」；行数差通常指向聚合漏计，金额差指向计价。
- 重点看什么：`usage_records.id` 的第 4 段是写入时刻毫秒（`usage_<date>_sNN_<ms>_<entropy>`），与 `created_at` 的差值就是写入延迟；差值 > 安全窗口即为可疑漏计行。
- 如何避免误判：`usage_stats_daily` 同时存在 `system_account_id='global'` 与各租户行，对账必须先限定 scope，否则会把「global + 租户双份」误判为重复计数。
