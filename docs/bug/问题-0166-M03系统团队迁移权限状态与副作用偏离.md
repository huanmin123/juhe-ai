## 问题概述

- 现象：M03 Go systemteams 覆盖基础 CRUD/成员接口，但没有接入 gateway，且返回 DTO、排序、历史、scope、授权 fanout、级联来源和缓存副作用与 Node 不一致。
- 期望：系统团队列表、详情、成员、历史、启停和成员变更保持 Node 的权限过滤、授权来源、审计及前端增量更新契约。
- 实际：
  1. Go 列表排序未按 Node 的 status/name 规则；成员列表缺少 id/memberCount/updatedAt 等字段；PATCH 只返回 status，前端需要的 changedFields/rowPatch/updatedAt 丢失。
  2. history 未过滤 active 成员且排序使用 created_at 而非 joined_at；管理员 `?systemAccountId` scope 被忽略，可修改无关团队。
  3. AddMembers 未调用 Node 的 authz fanout；reactivate 级联把来源写成 `system_account`/manual 而非 team；级联撤销不带真实 actor，且缺少 Node 的上限保护。
  4. 创建、修改、成员增删和状态切换未完整执行 Node 的团队 lookup、成员、资源授权缓存失效及 group stats dirty 副作用。
  5. Go reactivation 在外层事务中再开事务，SQLite/PG 的锁和提交边界尚未证明。
- 进一步确认：RemoveMember 先提交团队成员删除，再单独执行 authz revoke；撤销失败会留下成员已删除但授权仍 active 的不一致状态。AddMembers 未去重已 active ID，重复添加可能误触发成员上限。
- 版本输入切片取证：历史提交 `640470638` 的 PATCH、AddMembers、RemoveMember 路由仅检查 `expectedUpdatedAt` 非空，Store 继续按原字符串比较；Node `system-teams.routes.ts` 的三条对应 schema 共用 `rfc3339InstantSchema`，要求带 `Z`/数值 offset 的 RFC3339 并 canonicalize 为 UTC 毫秒。非法/bare 值在 Go 会进入 Store，等价 offset 也可能被误判冲突。该差异已确认，但当前 `662bd85f5` 是后续最新回退/收敛提交，按本轮边界暂不在其上实施修复。
- 成员分页/DTO 切片取证：Node `listSystemTeamMembersAsync` 只读 active 成员，按 `joined_at ASC, id ASC` 使用 `pageSize + 1` 分页，并返回 `id/memberCount/updatedAt/total/hasMore/page/pageSize`；历史 Go `members` 路由经 `FindDetail` 全量加载成员，忽略请求分页且缺少上述团队级字段，导致页码和响应契约偏离。该差异已确认，登记为独立修复切片。
- 成员历史切片取证：Node `listSystemTeamMemberHistoryAsync` 在 SQLite/PostgreSQL 均限定 `status = 'removed'`，并按 `joined_at DESC, id DESC` 稳定倒序；历史 Go `ListHistory` 仅按 `team_id` 查询，混入仍 active 的成员，且排序改为 `created_at DESC, id DESC`。因此同一团队的 history 会出现 Node 不会返回的 active 条目；当 `created_at` 与 `joined_at` 不同，条目顺序也会偏离。该差异已确认，登记为独立修复切片。
- 写操作 access scope 切片取证：历史 Go `scopeFor` 会把管理员的 `?systemAccountId` 转为 `AccessScope.FilterID`，路由也传给 `Patch`、`AddMembers`、`RemoveMember`；但三个 Store 函数体均未读取 `access`，选团队 SQL 只按团队 ID，指定账户不属于团队时仍可修改。Node 对应三条路径先用 `findSystemTeamPatchRowForAccess` 或 `findSystemTeamMemberMutationTeamAsync` 选行，在给定 scope 时要求该账户是团队 active 成员，否则统一返回 `not_found`。该越权差异已确认，登记为独立修复切片。
- 成员新增授权 fanout 切片取证：Node `addSystemTeamMembersAsync` 在同一事务内调用 `applyActiveTeamGrantsToMembersAsync`，对团队的每条 active grant 为新成员生成 `sourceType: 'team'` 的用户授权，并跳过资源 owner；任一 fanout 失败会回滚成员写入。历史 Go `AddMembers` 提交 `system_team_members` 后没有 `s.authz`/授权写入调用，只留下“由 M04 wiring 接管”的注释，且当前提交没有对应接线。因此已有团队授权时，新成员只获得成员关系而不会获得资源授权，结果与 Node 不一致。该差异已确认，登记为独立修复切片。
- 团队恢复授权状态机切片取证：Node 启用团队时在同一团队更新事务内调用 `reactivateTeamGrantSourcesAsync`，复用 `applyActiveTeamGrantsToMembersAsync`，以真实 actor、`sourceType: 'team'`、团队 ID、grant 的 remark/expiresAt/limits 重新 fanout，并跳过资源 owner。历史 Go `Patch` 已持有团队事务却调用会另开事务的 `ReactivateTeamGrants`；后者把成员构造为 `GranteeType: 'system_account'`，仅传资源 ID，固定 actor 为 `system`。因此 Go 会丢失授权字段、把 team source 写成 manual、向资源 owner 写入运行态；内层事务先提交后外层失败时，还会留下团队状态未恢复但授权已恢复的跨表不一致。该差异已确认，登记为独立修复切片。
- 团队写回执切片取证：Node PATCH 返回 `id/changedFields/rowPatch/updatedAt`，成员新增返回 `id/memberCount/updatedAt/addedMembers`，成员移除返回 `id/memberCount/updatedAt/removedMemberId`；历史 Go 分别只返回 `{status}`、`{id,addedMembers,status}`、`{id,status}`。前端 `systemTeamListMutation` 以这些缺失字段执行 revision 防回退、成员数更新和服务端排序后的局部重排，因此 Go 回执会导致成功写入后的页面状态无法按 Node 方式收敛。该差异已确认，登记为独立修复切片。
- 影响范围：团队页面增量更新异常，历史展示错误；管理员 scope 可越权；新成员无团队授权，重新启用后授权来源和缓存错误。

## 根因与证据

- Go：`backend-go/projects/gateway/internal/systemteams/routes.go`、`mutations.go`、`store.go`、`authz/team_cascade.go`。
- Node/前端：`backend/src/modules/system-teams/system-team.repository.ts`、`frontend/src/views/system-teams/*`、`systemTeamListMutation.ts`。
- 当前 gateway main 未发现 systemteams 挂载；Node system-api-app 仍挂载 `/my-teams` 与 `/system-teams`，没有 Node 归档提交。

## 修复与验证

- 修改点：按 Node/前端 DTO 和排序冻结 golden，修正 scope、history、fanout/sourceType/actor、级联上限与事务边界，补齐缓存/stats 副作用；完成真实 gateway、SQLite/PG 和前端 smoke 后再切换 owner。
- 当前验证：Go systemteams 包测试通过但未覆盖 disable→enable、scope 越权、DTO 增量和跨表副作用。
- 结论：M03 仍是部分实现，不能视为完整系统团队迁移；成员与授权一致性尚未满足。
