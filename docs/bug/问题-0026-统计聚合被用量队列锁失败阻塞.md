# BUG-0026 统计聚合被用量队列锁失败阻塞

## 问题概述

- 现象：生产统计页面无新数据或统计结果明显停滞。
- 期望：用量记录落库恢复后，统计 worker 能继续按游标增量聚合。
- 实际：使用记录队列发生 SQLite 写锁失败后，统计 worker 持续跳过聚合。
- 影响范围：用量统计、IP 统计、依赖统计结果库的趋势和汇总展示。

## 复现步骤

1. 在使用记录队列 flush 过程中模拟一次写入失败。
2. 保留失败记录并恢复写入能力。
3. 再次 flush 成功后观察队列运行态和统计聚合前置检查。

## 环境信息

- 分支 / 版本：feature/20250611-2
- 数据状态：生产业务库正常，数据集库和统计库存在历史数据但统计游标停滞。
- 浏览器 / 系统 / Node 版本：生产 Mac，Node 22。
- 是否稳定复现：在写锁冲突后稳定复现。

## 根因分析

- 表象：统计结果像是被清空或不更新。
- 真实根因：SQLite `busy_timeout` 只有 50ms，生产多 worker 并发写入数据集目录库时容易触发 `database is locked`；同时使用记录队列的 `flushFailureCount` 只增不降，统计 worker 看到失败计数大于 0 就一直跳过聚合。
- 为什么会发生：统计聚合为了避免游标越过未落库记录，会在使用记录队列积压或当前失败时主动停止；但“当前失败”被实现成了累计历史失败，导致恢复后仍被历史错误卡住。

## 修复方案

- 修改点：
  - 将 SQLite `busy_timeout` 调整为 5000ms，降低瞬时写锁冲突导致写入失败的概率。
  - 使用记录队列成功 flush 后清零 `flushFailureCount`，让统计聚合能够在队列真正恢复后继续运行。
- 行为影响：
  - 短时锁冲突时写入会等待更久，不再 50ms 内直接失败。
  - 队列健康里的 flush 失败计数表达“当前连续失败”，不再作为永久历史累计。
- 发布异常处理：
  - 如果发布后仍出现锁冲突，应继续排查长事务或高频写入来源，而不是只删除非业务库。

## 下次遇到

- 先查什么：worker 日志中的 `usage_record_queue_flush_failed`、`background_usage_stats_aggregation_failed`、`database is locked`。
- 重点看什么：`stats_job_state.updated_at` 和使用记录队列的 pending / flush failure 状态。
- 如何避免误判：统计表有数据但游标停滞时，不要先判断为前端空态或统计库丢失，应先确认 ingest 队列是否阻塞。

## 完成总结

- 完成时间：2026-06-18
- 结论：统计停滞由 SQLite 写锁失败和不可恢复的队列失败状态共同触发，已改为秒级锁等待并允许成功 flush 后恢复统计。
- 后续建议：生产发布后观察 worker 日志至少两个统计周期，确认统计游标继续前进。
