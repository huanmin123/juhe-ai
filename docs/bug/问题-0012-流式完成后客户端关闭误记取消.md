## 问题概述

- 现象：生产审计中 `asxs` 账号出现大量 `client_aborted` / “请求已取消”，但具体 trace 已经收到上游 `response.completed`。
- 期望：OpenAI SSE 已经写出成功终止事件后，客户端随后关闭连接应按成功请求收尾，不应计入失败使用记录或 `client_aborted` 审计。
- 实际：网关收到 `response.completed` 后仍等待上游 TCP EOF；Codex Desktop 在收到终止事件后关闭 SSE 连接时，网关将 `res.close` 解释成客户端中断并记录失败。
- 影响范围：OpenAI 兼容网关的 `/v1/responses` 流式请求，尤其是 Codex Desktop 等会在终止事件后主动关闭 SSE 的客户端。

## 复现步骤

1. 上游返回 `response.completed` 后短时间保持连接不主动 EOF。
2. 客户端读取到 `response.completed` 后立即关闭响应流。
3. 观察 `usage_records` 和 `audit_logs` 是否误写 `client_aborted`。

## 根因分析

- 表象：`asxs` 账号大量请求被标记为“请求已取消”。
- 真实根因：流式转发只在上游迭代器 EOF 后才按成功结束；如果客户端在 OpenAI 终止事件后先关闭 SSE，`AbortController` 会让流式读取抛取消异常，进而写入 `client_aborted`。
- 为什么会发生：代码对“客户端在响应过程中中断”和“客户端已经收到协议终止事件后收口”没有区分；审计上下文也会在 `res.close` 时无条件优先覆盖为 `client_aborted`。

## 修复方案

- 修改点：
  - 流式转发在成功写出 `response.completed` / `[DONE]` 等非失败终止事件后立即按成功收尾，不再等待上游 TCP EOF。
  - 如果客户端关闭发生在成功终止事件之后，按成功流式响应记录，不再写 `client_aborted` 使用记录。
  - 审计终态只有在请求最终未成功时才由 `clientAborted` 覆盖为 `client_aborted`。
  - 补充“终止事件后客户端关闭”的回归场景。
- 行为影响：`response.failed` 仍按流式失败处理；终止事件前的客户端关闭仍记录 `client_aborted`。
- 发布异常处理：如终止事件识别异常，修正当前流式完成判断和审计终态覆盖规则；必要时停服务恢复到同一数据契约下的已验证构建。

## 完成总结

- 完成时间：2026-05-18
- 结论：已将成功终止事件作为流式成功边界，避免 Codex Desktop 收到 `response.completed` 后关闭 SSE 被误记为失败取消。
- 复查结论：最近窗口内 100 条 `client_aborted` 里，97 条运行日志已经收到 `response.completed`，只有 3 条是真正未到终止事件的中途中断；但这些历史审计没有响应正文，无法从审计里直接回填精确 token / cost。
- 追加复查：`xuseny` 不是同类集中问题。2026-05-18 14:35 后 `xuseny` 成功 142 条，仅 1 条 `upstream_stream_idle_timeout`，没有同类批量 `client_aborted`；它唯一的 `client_aborted` 样本来自后台账号测试，日志为 `terminalReceived: false`、`sseEventCount: 0`。同窗口 `asxs` 仍有 132 条 `client_aborted`，样本日志为 `terminalReceived: true`、`response.completed: 1`，说明是完成终止事件后的收口误判。
- 修复加固：客户端关闭分支不再要求终止事件写入函数已完整返回；只要解析器已经确认上游成功终止事件且没有 `response.failed`，就按成功流式响应收尾，覆盖 terminal chunk 写入期间客户端立刻关闭的竞态。
- 后续建议：上线后观察 `asxs` 的 `client_aborted` 数量是否回落，并确认真实终止事件前取消仍能被保留。
