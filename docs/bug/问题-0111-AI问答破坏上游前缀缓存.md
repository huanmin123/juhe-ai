# BUG-0111 AI 问答破坏上游前缀缓存

## 基本信息

- 编号：BUG-0111
- 状态：已修复（完整回归与真实上游命中验证）
- 严重程度：P1
- 发现时间：2026-07-15
- 发现方式：用户成本反馈与 AI 问答请求链路静态审计
- 模块：后端 / AI 问答 / 网关 / 账户调度 / Prompt Cache / 使用记录
- 关联计划：PLAN-0104
- 关联 bug：无
- 责任人：Codex

## 问题概述

- 现象：站内 AI 问答可以完成多轮上下文和主动压缩，但没有稳定利用上游 Prompt Cache / KV Cache 的契约，不能证明重复前缀获得缓存读取价格和延迟收益。
- 期望：同一租户、API Key、会话、兼容模型和 canonical prompt 版本在连续轮次中使用稳定的 opaque cache key，保持完全一致的前缀表示，并由现有网关软亲和优先选择上次成功账户；真实 usage 能区分缓存读取、缓存写入和普通输入。
- 实际：主聊天请求没有写入 `prompt_cache_key`；因此现有网关虽然能识别该字段并执行会话软亲和，但站内聊天没有触发这个信号。Responses 当前轮纯文本按 `input_text[]` 发送，进入历史后又被折叠成普通字符串，跨轮结构不一致。
- 影响范围：长系统提示、工具定义和长会话重复前缀可能每轮重新进入普通输入计费；账号切换还可能失去上游节点或账户级缓存连续性。实际成本倍率、命中阈值和缓存保留时间取决于供应商、模型、请求长度和实时路由，不能仅凭静态审计声称固定节省十倍。

## 复现步骤

1. 创建一个使用 Responses 协议的站内 AI 问答会话，连续发送两轮纯文本。
2. 检查 `buildChatTransportRequest()` 产生的请求，确认没有 `prompt_cache_key`，也没有其他稳定会话标识进入网关的 session affinity 提取路径。
3. 对比第一轮当前用户内容和第二轮历史投影：第一轮为 `[{ type: "input_text", text: "..." }]`，第二轮同一内容变为字符串。
4. 查看上游 usage；当前链路可能记录供应商返回的缓存字段，但没有按此次会话构造证明缓存应命中的基线，也没有完成真实连续轮次命中率和计费验证。

## 根因分析

- 主聊天请求构造只发送模型、instructions、history、当前内容、工具、思考和服务等级，没有生成稳定的 `prompt_cache_key`。
- 网关已有 `prompt_cache_key` / `session_id` / `conversation_id` 等软亲和能力，但 AI 问答没有提供稳定信号，因此不能优先命中上次成功账户。
- 通用模型目录已有 `supportsPromptCaching` 等缓存事实，但 AI 问答 `ChatModelOption` 尚未消费该能力；仅凭模型名或 Responses 路径无法安全决定是否注入供应商专用字段。显式 breakpoint 还需要独立于“支持缓存”的细粒度模型能力，不能共用一个布尔值猜测。
- Responses 的当前纯文本内容保留 block 数组，历史加载时却把全部文本 block `join` 成字符串；即使语义相同，供应商看到的前缀 token / item 结构也可能不同。
- 首轮修复后的独立复查还发现：Responses 显式映射到 Chat Completions 时，桥接层重建 body 会丢失 `prompt_cache_key`。账户软亲和仍有效，但上游收不到缓存路由键。
- 当前上下文设计主要优化 token 上限和请求体大小，没有把“稳定前缀形态”作为独立不变量。动态字段、工具顺序、checkpoint 替换或图片说明替换一旦进入前缀，都会形成新的缓存边界。
- 图片隐藏说明和主动压缩本身是独立的模型请求：图片二进制、不同问答正文和不断变化的压缩 source 决定它们通常至少发生一次冷缓存。这是预期成本，不应为了追求命中而复用主会话 key 或放宽任务隔离。

## 修复实现

### 1. Capability-aware 稳定 opaque key

- 只对所有候选目录能力都明确声明 `supportsPromptCaching=true` 的模型发送 `prompt_cache_key`；未知或能力不一致的目标不发送。
- key 由服务端对版本、`systemAccountId`、`apiKeyId` 和 `conversationId` 做 SHA-256 base64url 摘要，得到稳定、不可逆的 43 字符 opaque 值；不包含可读用户信息、原始标题、凭据、具体上游账户或分组。
- key 在普通追加轮次中保持稳定；不能混入 `turnId`、`traceId`、请求时间或每轮递增的 `context_revision`。
- 模型、system instructions、工具、checkpoint 或图片 projection 改变时，请求前缀本身会自然形成新的缓存哈希边界；不需要为此新增持久化 `cache_epoch` 字段。新前缀第一次可能冷启动，后续追加轮次重新稳定。
- Anthropic 显式 breakpoint 和 Gemini explicit context cache 不套用 OpenAI 字段，后续分别由供应商驱动承接。

### 2. Prefix canonicalization

- 固定前缀顺序为 canonical instructions、稳定工具 schema、checkpoint / 历史和追加的新轮次；静态内容在前，动态内容在后。
- Responses 文本内容始终使用同一种 block 表示，不能第一轮为 `input_text[]`、下一轮变成字符串；对象字段、工具顺序和空字段处理也必须确定化。
- Responses 到 Chat Completions 的显式桥接只在原值为非空字符串时原样保留 `prompt_cache_key`，不能因协议转换丢失缓存语义。
- system prompt、工具 schema、checkpoint 和图片说明变化会改变精确前缀并产生一次合理冷启动；普通消息只在稳定尾部追加。
- 前缀规范化只消除本地可控漂移，不能伪造上游缓存命中，也不能为未知供应商硬编码统一 token 阈值、TTL 或价格倍率。

### 3. 复用现有网关账户亲和

- `prompt_cache_key` 继续进入现有 session affinity，只在同一合法候选层级内优先上次成功账户。
- 缓存亲和不得跳过授权、分组、模型能力、代理、状态、冷却、到期、额度、并发或错误策略。
- 成功率优先于缓存：亲和账户失败、不可用或短暂等待后仍无容量时，立即按现有网关规则回退其他账户；不能为了缓存命中硬绑账户或拖延故障切换。

### 4. Usage 与真实命中观测

- 使用记录必须保留上游明确返回的 OpenAI `cached_tokens`、Anthropic / compatible `cache_read` 与 `cache_write` 事实；没有字段时不推测命中。
- 专项验证按同一会话至少比较冷启动、连续追加轮次、账户亲和、checkpoint / 图片说明换代和故障回退后的 usage，分别记录普通输入、缓存读取、缓存写入、账户 ID、模型、purpose、延迟和成本。
- 自动化回归只证明 key 稳定、前缀字节/结构稳定、能力过滤和回退语义，不等于真实上游缓存命中；真实命中与账单差异必须使用官方模型单独验证。

## 供应商边界

- OpenAI Prompt Caching 使用重复前缀并支持 `prompt_cache_key` 辅助路由，命中量从 usage 的 cached token 字段观测：[OpenAI Prompt caching](https://developers.openai.com/api/docs/guides/prompt-caching)。
- Anthropic 使用自己的 `cache_control` breakpoint、缓存写入/读取 usage 和保留策略，不能把 OpenAI key 原样透传：[Anthropic Prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)。
- Gemini 同时存在 implicit caching 与 explicit cached content 语义，能力、最低输入和 TTL 由 Gemini 模型与接口决定：[Gemini Context caching](https://ai.google.dev/gemini-api/docs/caching)。

## 下次遇到

- 先同时对比“opaque key 是否稳定”和“key 对应请求前缀是否完全一致”；只有 key 相同不能保证命中。
- 先查真实 usage 的 cached / cache read / cache write，再讨论节省比例；不能用客户端估算代替供应商计费事实。
- 缓存优化不能改变网关故障回退优先级，也不能把账户亲和升级为硬绑定。
- 图片说明、结构化压缩和 checkpoint 换代是合理的冷缓存边界；重点是换代后重新稳定，而不是强求所有请求共享缓存。
