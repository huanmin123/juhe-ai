# 问题-0282：质量预检标记 temporary_unavailable 漏写冷却恢复锚点，账户永久卡死

- 编号：BUG-0282
- 状态：已修复（2026-10-04 登记并修复代码；存量数据修复与 jobs 发布另行执行）
- 影响面：生产 15 个账户（全部 `last_error_code='precheck_temporary_unavailable'` 且 `cooldown_until IS NULL`）自 2026-09-28 起陆续卡死"临时不可调用"，上游恢复后无法自动恢复，只能人工干预。

## 现象

生产账户 `api.shenwenai.com-神影-1 - 克隆`（`acc_1789614822781_30e9db9f`）2026-10-02 22:20 被"近期质量频繁失败确认"标记 `temporary_unavailable` 后，实际测试上游已恢复正常，但账户列表一直显示"临时不可调用"，超过 48 小时无任何自动恢复。

证据链（生产库 + jobs 容器）：

- 该账户 `cooldown_until` 为 NULL，`next_health_check_at` 过期近两天未再调度；
- 当天 J1 曾连续 8 次 `complete_success`（14:00–21:21 +08），上游大部分时间正常；标记后 3 秒 J1 记录唯一一条 `probe_task_failure/direct_input_invalid`，此后再无 outcome；
- `juhe_jobs.account_health_direct_input_suppressions` 存在该账户的抑制行且每 ~5 分钟刷新一次——J1 每轮都选中它（reader 对 `temporary_unavailable` 始终出候选）、构建输入时因缺冷却 fence 失败、进 5 分钟抑制循环，无限静默重复。

## 根因（Go 移植漏写恢复锚点）

`temporary_unavailable`/`rate_limited` 的恢复探测只认冷却五元 fence（J1 `direct_input.go` 的 `ToInput` 对冷却账户要求完整 `cooldown_until` + 观察起点 + generation，否则 `direct_input_invalid`；`validateDirectAccount` 还要求冷却已到期）。恢复候选按 `cooldown_until` 排序挑选。

- Node 归档实现：`mark_account_precheck_temporary_unavailable` 直接复用标准 `markAccountTemporaryUnavailableAsync` = `markAccountCooldownAsync`（写 `cooldown_until` 初始 3s 退避、`cooldown_retest_observation_started_at`、`cooldown_retest_generation`、`schedulable=1`），预检围栏只替换 CAS 条件——标记后由冷却复测正常接管（BUG-0023 的设计契约即"确认失败升级 + 冷却复测自动恢复"）。
- Go 移植版 `shared/platform/accounttest/proberepo/mutation.go` 的 `MarkPrecheckTemporaryUnavailable` 手写简化 SQL：只写 `status/last_error_*`，**漏写 `cooldown_until`、`cooldown_retest_observation_started_at`、`cooldown_retest_generation`**，也未清 `last_error_trace_id`、未保持 `schedulable=1`。

结果：precheck 标记的账户两条恢复链全部够不着——冷却复测按 `cooldown_until` 挑不到它（NULL），J1 想探它又因 fence 不完整被抑制循环永久隔离。

## 修复

- `MarkPrecheckTemporaryUnavailable` 写入与网关传输失败路径（`chain_error_policy_effects.go` markAccountCooldown 投影）同构的恢复锚点：`cooldown_until = now+3s`、`cooldown_retest_observation_started_at = now`、`cooldown_retest_generation = 'cooldown:<uuid4>'`、`schedulable = 1`、`last_error_trace_id = NULL`。
- 回归断言：`TestMarkPrecheckTemporaryUnavailableFenceOrder` 成功分支新增锚点字段写入校验（回退修复必红）。
- 存量 15 个账户通过生产数据修复补锚点（先备份 `accounts_backup_b0282_precheck`），由既有冷却复测机器自动确认恢复。

## 顺带修复（同批）

- 可观测性：`direct_input_invalid` outcome 过去只写统一文案"候选无效"，具体原因只存在于内存错误里。现 `DirectInputFailure` 增加 `Reason`（不参与 request_id 派生与去重），outcome 落具体原因，且仅在新的 fence 代次首次落库时打 `account_health_direct_input_invalid` WARN（避免 5 分钟重试刷屏）。本次三类静默卡死（BUG-0262、本 BUG、grok自建 oauth 配置缺失）均因该缺口只能靠 DB 考古发现。

- `go test -count=1 ./projects/jobs/internal/accounthealth/` 全绿。
