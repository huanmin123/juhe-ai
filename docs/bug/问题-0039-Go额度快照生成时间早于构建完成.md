# BUG-0039 Go 额度快照生成时间早于构建完成

## 基本信息

- 编号：BUG-0039
- 状态：已修复（待真实环境验证）
- 严重程度：P2
- 发现时间：2026-07-10
- 发现方式：Node 提交 `8bb00ea0a` 转 Go 契约复核
- 模块：后端 / Go / worker / 网关 / 授权额度 / Redis runtime state
- 关联计划：[PLAN-20260706T071505000Z Node 转 Go 渐进减法迁移](../plans/计划-20260706T071505000Z-Node转Go渐进减法迁移.md)
- 关联 bug：[BUG-0019 授权配额快照跨进程失效缺失](问题-0019-授权配额快照跨进程失效缺失.md)
- 责任人：主 agent / 维护者

## 问题概述

- 现象：Go gateway quota snapshot 的 `generatedAt` 使用构建入口时间，而 Node 消费端已将该字段作为构建完成后的 freshness watermark。
- 期望：统计日期、周和月窗口使用构建入口时间固定口径；`generatedAt` 在全部查询和组装完成后生成，并严格晚于构建期间发生的旧失效事件。
- 实际：旧 Go 在 `Build` 入口只取一次时间，同时用于统计窗口和最终 `generatedAt`。
- 影响范围：`gateway-quota-snapshot-build` worker 发布的授权额度快照；构建期间收到授权失效事件时，Node 网关可能把刚完成的快照判为旧数据并回退 DB service。

## 复现步骤

1. Go worker 在时间 `T1` 开始构建 quota snapshot。
2. 构建期间在 `T2 > T1` 发布 `authorization_quota_cache` 失效事件。
3. Go 在 `T3 > T2` 完成构建，但旧实现仍写 `generatedAt=T1`。
4. Node 消费端要求 `generatedAt > invalidation publishedAt`，因此拒绝该快照。

## 环境信息

- 分支 / 版本：`feature/20260706-go`，提交 `8bb00ea0a` 后的 Node 契约。
- 数据状态：Go snapshot worker 和 Node gateway 通过 Redis runtime state 共享快照与失效事件。
- 浏览器 / 系统 / Node 版本：不适用；跨运行时 freshness 时间语义问题。
- 是否稳定复现：在构建期间发生失效时稳定复现。

## 根因分析

- 表象：刚发布的新快照仍触发 DB service fallback。
- 真实根因：Go 把 snapshot 统计窗口基准时间和构建完成 watermark 合并成同一个入口时间。
- 为什么会发生：初始迁移只对齐了 `generatedAt` 字段格式，没有同步 Node 后续修复中“严格晚于 invalidation publishedAt”的消费语义。

## 修复方案

- 修改点：
  - `Build` 入口时间重命名为 `buildStartedAt`，仅用于 `statDate/statWeek/statMonth`。
  - 全部读取与组装完成后再次调用 `s.now().UTC()`，以 `buildCompletedAt` 生成 `GeneratedAt`。
  - 增加跨 UTC 日期、月份和周边界的顺序时钟测试，确认统计窗口仍固定在入口时间，watermark 使用完成时间。
- 行为影响：构建完成后的 snapshot 能正确表达 freshness，不会仅因构建期间发生过更晚的失效事件而被误判为旧数据。
- 发布异常处理：如果真实 worker 构建耗时或机器时钟异常导致 `generatedAt <= publishedAt`，Node 仍会 fail-closed 并回退 DB service；应检查跨主机时钟同步和 worker lag。

## 下次遇到

- 先查什么：时间字段代表请求开始、查询窗口、提交完成还是观察时间。
- 重点看什么：消费者是否使用严格大于比较，跨进程事件时间是否保留原始 `publishedAt`。
- 如何避免误判：字段格式一致不代表时间语义一致；必须覆盖“构建期间发生失效”的时序测试。

## 完成总结

- 完成时间：2026-07-10。

- 后续建议：真实 PG/Redis 环境增加构建中失效注入，并确认生产主机 NTP 同步。
