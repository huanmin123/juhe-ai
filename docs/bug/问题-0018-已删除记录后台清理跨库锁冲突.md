# BUG-0018 已删除记录后台清理跨库锁冲突

## 基本信息

- 编号：BUG-0018
- 状态：已修复
- 严重程度：P1
- 发现时间：2026-05-31
- 发现方式：用户追问删除场景的 `database is locked` 风险
- 模块：后端 / 存储 / worker / SQLite
- 关联计划：无
- 关联 bug：BUG-0017、BUG-0013、BUG-0003
- 责任人：待定

## 问题概述

- 现象：AI 账户或 API Key 删除后的关联记录清理，可能在统计结果库繁忙时抛出 `database is locked`，导致 record maintenance worker 记录失败并等待队列重试。
- 期望：用户删除业务资源只提交业务库事实；历史 usage、审计、模型检测和统计扣减由后台清理。统计库或 usage shard 忙时，清理目标应被标记为 blocked 并保留，下轮继续处理。
- 实际：清理函数在 dataset 事务中读取 / 写入 stats 和 usage shard；stats 写锁等待期间会扩大 dataset 事务持锁时间，锁超时后按失败抛出。
- 影响范围：已删除 AI 账户关联清理、已删除 API Key 关联清理、record maintenance worker。

## 复现步骤

1. 构造一个待清理的 AI 账户或 API Key 清理目标。
2. 使用另一个 SQLite 连接对统计结果库开启 `BEGIN IMMEDIATE` 写事务。
3. 调用 `cleanupDeletedAccountRelatedRecordData` 或 `cleanupDeletedApiKeyRelatedRecordData`。
4. 旧实现会抛出 `database is locked`；修复后返回 `hasMore = true` 和 blocked reason，并保留清理目标。

## 根因分析

- 表象：删除后清理 worker 失败。
- 真实根因：删除清理涉及三个持久域：dataset 审计 / 模型检测、usage shard 原始使用记录、stats 聚合扣减和衍生窗口。旧实现把这些动作放在一个大流程里，dataset 事务覆盖 stats 写入和 usage shard 删除，一旦 stats 单 writer 被占用，锁等待会放大到其他库。
- 为什么会发生：删除本身已异步化，但后台清理没有按库边界拆短事务，也没有把 SQLite busy 视为可重试阻塞状态。

## 修复方案

- 修改点：AI 账户和 API Key 删除关联清理拆成短事务步骤：
  - stats / usage shard 清理单独执行，失败时可幂等续跑；
  - dataset 审计和模型检测清理只在 dataset 短事务中完成；
  - 最终 stats 维度清理和衍生窗口刷新单独执行；
  - SQLite locked 转为 blocked reason，不抛出 worker 失败。
- 兼容影响：清理目标表结构不变；已有待清理目标可继续重试。
- 回滚方式：回滚代码即可；清理目标保存在 dataset 库，可由旧逻辑继续处理。

## 下次遇到

- 先查什么：`record_maintenance_queue_flush_failed`、`background_*_record_cleanup_retry_failed`、清理目标表 `last_blocked_reason / last_error_message`。
- 重点看什么：是否在一个事务里跨 dataset、stats、usage shard 多库等待；是否把可重试的 SQLite busy 当成硬失败。
- 如何避免误判：删除接口 204 不代表历史明细已物理清完；删除后的历史清理应看 dataset 清理目标队列和后台 worker 重试状态。

## 完成总结

- 完成时间：2026-05-31
- 结论：删除后关联清理按库边界拆短事务，统计库 busy 时转 blocked 重试，不再把可恢复锁竞争打成 worker 失败。
- 后续建议：新增跨库维护任务时，默认使用“登记目标 + 分库短事务 + blocked 重试”的模式，不在用户请求链路做历史明细物理清理。
