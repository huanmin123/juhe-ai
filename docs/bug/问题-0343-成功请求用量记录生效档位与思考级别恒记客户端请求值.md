# BUG-0343 成功请求用量记录 effective_service_tier / effective_reasoning_effort 恒记客户端请求值

## 基本信息

- 编号：BUG-0343
- 状态：已修复待发布
- 严重程度：P2
- 发现时间：2026-11-03
- 发现方式：自查（生产审计载荷与用量记录全量比对）
- 模块：网关（派发引擎 + 链面成功终局记账）
- 关联计划：无
- 关联 bug：无
- 责任人：网关维护者

## 问题概述

- 现象：凡派发成功的请求，用量记录的 `effective_service_tier` / `effective_reasoning_effort` 恒等于客户端请求值（requested），即使引擎最终出站体已被账户覆盖改写为其他值；失败行（引擎内部记账）反而正确。
- 期望：按 [核心功能设计](../functions/核心功能设计.md) §覆盖字段契约（:567）与 [GPT请求服务等级与思考级别覆盖设计](../functions/GPT请求服务等级与思考级别覆盖设计.md)（:225），effective 列保存「最终实际发往上游请求体中的服务等级 / 思考级别」。
- 实际：成功行的 effective==requested；与上游体不一致。
- 影响范围：Go 网关上线以来全部成功用量记录的这两列（观测与运营口径失真，不影响计费金额与 Token 数）；历史行不回填、不伪造。

## 复现步骤

1. 客户端请求顶层带 `reasoning_effort`（如 `medium`）。
2. 账户覆盖生效，引擎出站体重建为不同值（如 `max`）；触发换号重试可多次观察到同体裁荷。
3. 该请求成功后查用量记录：成功行 `effective_reasoning_effort == 客户端请求值`（期望为出站体实际值）。

## 环境信息

- 分支 / 版本：Go 网关（`backend-go/projects/gateway`），生产国内单机 Docker 现行版本。
- 数据状态：近 7 天生产全量——成功记录 109,493 条全部 effective==requested（0 条差异）；失败记录 13,217 条中 13 条 effective!=requested（失败行由引擎内部记账，读到更新后的副本，行为正确）。
- 浏览器 / 系统 / Node 版本：不适用（纯后端记账路径）。
- 是否稳定复现：是（存在账户覆盖的成功请求 100% 复现）。

## 根因分析

- 表象：成功行 effective 恒等于 requested。
- 真实根因：派发引擎与链面各持一份 usage 上下文，引擎的覆盖更新不回传链面——
  - `internal/gatewaydispatch/upstreamdispatch.go` 的 `usageContext := args.UsageContext`（修复前 :521，修复后 :528）以值拷贝取得 usage 上下文，引擎内 `dispatchsingle.go:424-426` 的 `usageContext.EffectiveServiceTier/EffectiveReasoningEffort = requestParts.*` 只更新引擎局部副本；
  - 链面成功终局 `cmd/juhe-ai-gateway/chain_v1.go` 的 `handleUpstreamResponse` 输入 `UsageContext: context.UsageContext`（链面原始副本，从未被引擎更新），成功/失败用量记录写侧（`internal/gatewayusage/service.go:345-347/:461-463`、`cmd/juhe-ai-gateway/chain_usage.go:550-552/:813-815`）都从这里取 effective 列；
  - 引擎结果结构 `UpstreamDispatchResult.EffectiveServiceTier` 已存在但全仓无消费方（Go 迁移遗漏的接线），`EffectiveReasoningEffort` 干脆没有带出字段——链面想回填也没有输入。
- 为什么会发生：Go 迁移时带出了结果字段但漏掉了「链面消费派发结果回填 usage 上下文」这一跳；失败路径因记账发生在引擎内部（读到引擎副本）而天然正确，成功路径全部失真。

### 生产证据

- 生产账户 `acc_2996788e5727408d`（tokenrhythm.studio-74bpbf，deepseek），trace `5562f4f1-5dce-4c27-adc1-0d5df5f3d7fc`：三次上游尝试（429/429/200）的 `upstream_request` 审计载荷 sha256 `b6574c581070bd8d59dcda9636676a6f73509b481d38109578bb08d71252f474` 完全相同，出站体顶层 `reasoning_effort=max`；429 失败行记录 effective=max（正确），200 成功行记录 requested=medium / effective=medium（错误）。
- 近 7 天生产全量统计：成功 109,493 条 0 条差异、失败 13,217 条中 13 条差异（即失败行正确），与「只有成功路径读链面原始副本」的根因判断精确吻合。

## 修复方案

- 修改点：
  1. `internal/gatewaydispatch/upstreamdispatch.go`：`UpstreamDispatchResult` 在 `EffectiveServiceTier` 旁新增 `EffectiveReasoningEffort`（本尝试最终出站体中的实际思考级别，`PreparedRequestParts.EffectiveReasoningEffort` 的引擎带出值）。
  2. `internal/gatewaydispatch/dispatchsingle.go`：`upstreamAttemptLoopContext` 新增 `effectiveReasoningEffort`，`runUpstreamAttemptLoop` 调用字面量从 `requestParts.EffectiveReasoningEffort` 携带（与 `effectiveServiceTier` 同源同点）。
  3. `internal/gatewaydispatch/attemptoutcomes.go`：成功分支与 ReturnResponse 分支两处 `UpstreamDispatchResult` 构造点回填 `EffectiveReasoningEffort: c.loop.effectiveReasoningEffort`。
  4. `cmd/juhe-ai-gateway/chain_v1.go`：新增包内函数 `applyDispatchedEffectiveUsageFacts`，在 `handleUpstreamResponse` 开头（`commitState == nil` 兜底之后、任何早退分支之前——媒体 job / 错误透传早退也在其内）无条件回填 `context.UsageContext` 的两列。
- 行为影响：只影响新写入的成功/失败记录的 effective 两列取值来源（改为引擎带出的出站体实际值）；回填为无条件覆盖，空串代表出站体确实没有该字段，不回落请求值。历史行不回填、不伪造。
- 发布异常处理：无 schema/配置变更；发布即生效，无需数据修复。

## 下次遇到

- 先查什么：effective 列异常先区分成功/失败记账路径——失败行由引擎内部记账（读引擎副本，覆盖生效即正确），成功行由链面终局记账（读链面原始副本）；只有成功行失真时优先怀疑「链面未消费派发结果」。
- 重点看什么：结果结构字段存在 ≠ 接线完成。`UpstreamDispatchResult.EffectiveServiceTier` 字段早已存在但全仓零消费方，是 Go 迁移遗漏的典型形态；核对「引擎带出 → 链面消费 → usage 上下文」每一跳是否有真实调用点与断言。
- 如何避免误判：不要以「429 行记录正确」推断整条链路正确——两条记账路径读的是不同副本；也不要以客户端请求体推断 effective，出站体在账户覆盖/协议改写后与请求体不同源。
- 已知边界（复审 Minor）：attempt loop 内换体的三条路径（OAuth 刷新重建 `attemptoutcomes.go` 的 `c.loop.body = rebuilt.Body`、Codex 兼容恢复体、链面 `RequestBodyOverride`）只换 body，不重算 `c.loop.effectiveServiceTier/effectiveReasoningEffort`。现有这三种恢复机制均不改写顶层 `service_tier` / `reasoning_effort` 字段（加密内容清理、凭据刷新、重放体派生），实际偏差概率极低；若未来恢复体开始改写顶层档位字段，必须同步重算 loop 的生效值。
