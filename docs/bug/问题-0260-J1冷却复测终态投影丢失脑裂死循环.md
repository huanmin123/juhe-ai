# BUG-0260：J1 冷却复测终态投影丢失脑裂死循环

- 状态：已发布（2026-10-01 23:48 jobs 单进程，md5 c96bd6ed 闭环，jobs healthy/ERROR=0，详见私有 runbook 发布记录；4 用例红绿闭环 + 独立复审六项 PASS）。
- 定性：代码缺陷（终态投影落地通道缺自愈；无契约变更，`error` 终态不被复测推翻的既有契约保持）
- 发现方式：生产巡检（2026-10-01，账户 `acc_1786071814977_bcc9bfac` 探针频率异常）
- 编号说明：任务原拟 BUG-0259 与并行批次已登记的「问题-0259-核心探针终态失败未按契约判整轮不可用」撞号，经用户裁决本问题顺延为 BUG-0260（生产止血备份表名 `accounts_backup_b0259_soulecho` 按实际执行留档，不改）。

## 1. 现象（生产实证事实链）

2026-10-01 生产巡检发现账户 `acc_1786071814977_bcc9bfac` 以约每 9 秒一发的频率被 J1 反复复测探活，自 2026-09-29 起累计 **21283 次（约 394 次/小时）**，无任何退避。其余 139 个 `temporary_unavailable` 账户复测节奏正常（约 4 次/小时，退避生效）——该形态只发生在"终态投影丢失"的单个账户上。

取证事实链：

1. 该账户冷却复测观察期超过 7 天，2026-09-29 J1 判定终态：jobs 侧 `juhe_jobs.account_health_current_state` 写入 `account_status='error'`、`error_code='cooldown_retest_observation_timeout'`（`backend-go/projects/jobs/internal/accounthealth/scheduler.go` 的 `applyCooldownDecision` 观察期超时分支产出 `cooldown_error` 投影，修复前 921-927 行）。
2. 该终态的 business 投影未落地（business `accounts` 行停留 `temporary_unavailable`；一次性 CAS 拒绝，投影面按 receipt 记 stale 后不重试）。此后脑裂：business=`temporary_unavailable` vs jobs state=`error`。
3. `nextDue` 的 split-brain 修复分支（修复前 749-758 行）条件为「business 是 `temporary_unavailable`/`rate_limited` 且 `state.AccountStatus` ≠ business status」→ 每次返回 due（`reconciliationDue`）。该分支在 789 行「`state.AccountStatus == "error"` → 不 due」的终态检查**之前**命中，对 error 终态脑裂无终局处理——每个 J1 扫描周期都放行复测。
4. 复测 outcome 落库时 `writeCurrentStateTx → updateCooldownCurrentStateTx`（`store.go:675`）的 CAS 要求 `account_status = ExpectedAccountStatus`（`temporary_unavailable`）与 state 的 `error` 永不匹配；epoch（input_version/config_revision/dispatch_revision）相同，`upsertCooldownCurrentStateEpochTx`（`store.go:739`）也不推进 → state 永卡 09-29 终态，脑裂永不自愈。
5. 结果：每 ~9 秒一发探针的死循环持续至今（巡检时点）；探针真实打到上游（终态账户被无限复测）。

## 2. 根因

两层叠加：

- **投影落地是单次尝试语义**：cooldown_error 终态投影经 outcome→投影链落 business，一次 CAS 拒绝即记 stale receipt 终结，无重试通道。business 与 jobs state 的终态一致性没有对账自愈机制。
- **`nextDue` 的 split-brain 分支没有终态概念**：该分支为「jobs state 与 business 状态不一致时强制 reconciliation」设计，放行的复测对普通脑裂（如 state=active × business=temporary）可以收敛；但 state=`error` 是终态，复测 outcome 的 state CAS 永不命中（见事实链 4），放行即死循环。终态检查（789 行）排在 split-brain 分支之后，对该形态不可达。

## 3. 影响面

- **受影响**：`jobs current_state` 为 `account_status='error'` 终态、business 行仍 `temporary_unavailable`/`rate_limited`、且 epoch 与 fence 匹配的脑裂形态——每扫描周期一发探针打到上游，state/business 永不收敛。生产实证 1 个账户（`acc_1786071814977_bcc9bfac`）。
- **不受影响**：正常退避复测（state 非 error）；`observation_timeout`/`limited_probe_timeout` 终态判定本身；state 非 error 的 split-brain（如 state=active × business=temporary 的 reconciliation、business=active × state 残留的 health 一次收敛）；error 终态不被复测推翻的语义（本修复只补投影，不"复活"账户）。

## 4. 修复契约

当 J1 发现 split-brain 形态（jobs current_state 为 `account_status='error'` 终态而 business 行仍 `temporary_unavailable`/`rate_limited`，fence 匹配、epoch 一致）时，**不再发复测探针，改为直接补落地丢失的 cooldown_error 终态投影到 business（幂等自愈）**。投影成功后 business=`error`/`schedulable=0`，账户不再构成调度候选，循环终止且两侧状态一致。

实现（`backend-go/projects/jobs/internal/accounthealth/`）：

- `scheduler.go` `nextDue`：split-brain 分支识别 `state.AccountStatus == "error"` 时返回新 kind `cooldown_terminal_reproject`（due 语义同 `reconciliationDue`）；state 非 error 的 split-brain 行为不变。
- `scheduler.go` `prepareCooldownTerminalReproject`：对该 kind **不调 `ExecuteInputProbe`**，构造携带 cooldown_error Projection 的 outcome——`TransitionKind="cooldown_error"`、`ExpectedAccountStatus=input.Eligibility.AccountStatus`、`ExpectedCooldownFence` 与 `CooldownFence=input.Cooldown`（business 现存 fence）、`error_code`/`error_message`/`status_code` 从 jobs state 行透传（保留原终态审计语义）、epoch 取当前 input、`Outcome=upstream_failure`（满足投影契约 `outcomeMatchesTransition` 对 cooldown_error 的要求）。
- 落地通道（state 一致性关键）：**不走 AppendOutcome→drain 投影链**（该链对 cooldown 投影虽保留 payload，但落地依赖 drain 消费节奏，且首次终态投影已证明一次性 CAS 拒绝后无重试），改为直调 `projection.go` 新增的 `OutcomeProjector.ProjectOutcomeNow`——与 drain 消费路径同源（`projectOutcome`）的投影事务入口，receipt 以 outcome_id 幂等、不推进 drain 游标（后续 drain 重放同一 outcome 命中 receipt 直接跳过）。投影结论（applied/stale/rejected）落定后经 `AppendOutcome` 落幂等 audit 行。
- **jobs current_state 不被改写**：state 已是 error 终态（正确状态）；该形态下 AppendOutcome 的 state CAS 永不命中（expected=temporary vs state=error）、epoch 相同不推进，state 行保持原样。
- **防放大**：request ID 仅由 账户 + input epoch + kind 派生（不含时钟，`cooldownTerminalReprojectRequestID`），同一 input_version 内同 kind 至多尝试一次；投影瞬时错误（SQL 失败等）返回 err 进入下轮重试且不落 audit 行（避免把未投影的尝试记为已处理）；fence 真失配/业务被并发编辑时投影被业务侧守卫拒绝为 stale receipt，单次有界，不形成新的高频循环。
- 组合根（`cmd/juhe-ai-jobs/main.go`）：投影面装配成功后 `SetOutcomeProjector` 回绑 runner（与 `SetProbeRequestDrain` 同款回绑模式）；投影面装配失败降级时不注入，触发时以错误显式暴露（每周期一条可见错误、无探针、无 outcome 写入），绝不静默回退复测循环。

## 5. 生产处置（止血实录，2026-10-01）

- 止血：business 行手工对齐终态——备份表 `accounts_backup_b0259_soulecho` 后，将 `accounts` 行置 `status='error'`、`schedulable=0`（语义对齐 cooldown_error 投影写入集：status/schedulable/last_error/fence 保留）。
- 验证：执行后探针循环归零（该账户不再进入 J1 调度候选），jobs state 维持 error 终态，两侧状态一致。
- 代码修复发布后，同类脑裂将由 `cooldown_terminal_reproject` 通道自愈，不再依赖人工。

## 6. 验收标准

- 脑裂+error 形态触发新 kind：不调探针（探针服务器零命中）、business 被置 `error`/`schedulable=0`、`last_error_code/message` 透传原终态审计值、cooldown fence 保持 business 现存值、`cooldown_until` 清空、jobs current_state 不变（仍 error、observed_at/error_code/fence 原样）。
- 补投影落地后循环终止：business=`error`/`schedulable=0` 不再构成候选（重复 runInput 无任务）；同一 input_version 内同 kind 只尝试一次（request_id 幂等，重复扫描不再产生新 receipt/audit 行）。
- fence 失配/epoch 前进形态不触发补投影：epoch 前走走原 `cooldown_retest` 路径；business fence 无效不 due；business fence 失配（并发编辑）时投影被守卫拒绝为 stale receipt 且单次有界、business 不被改写。
- 正常链路零回归：state 非 error 的 split-brain、正常退避复测、observation_timeout 判定、error 终态不被复测推翻——既有用例全绿。
- 测试：`internal/accounthealth` 包 `TestW260*` 4 用例红绿闭环（红态=禁用 nextDue 新分支：kind 回退 `cooldown_retest`、探针命中 1 次、business 未落地、无 receipt）；`cd backend-go/projects/jobs && go build ./...` 通过；`go test ./internal/accounthealth/ -count=1` 除 10 个预存 dev PG 环境失败（`juhe_business` 契约表缺失，基线 stash 复跑同样失败，与本修复无关）外全绿。
