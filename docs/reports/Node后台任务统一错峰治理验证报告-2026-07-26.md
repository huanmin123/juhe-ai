# Node 后台任务统一错峰治理验证报告（2026-07-26）

## 1. 范围与结论

本轮只治理 Node 后端，不修改 Go 实现。覆盖周期调度器、统计聚合与窗口、表监控、预热、系统指标、外部账户维护、日志维护、PostgreSQL 多实例租约和停机排空。

结论：核心调度、规模边界、本地回归和授权远端 PostgreSQL / Redis smoke 均已通过；测试创建的临时数据库已删除，Redis 本任务前缀最终为 0。未执行生产部署或生产流量压测。

## 2. 关键落地

- `WorkerScheduler` 支持 `fixedRate / fixedDelay`、稳定相位、`coalesceOne`、资源 lane、full-jitter 失败退避、真实 timeout / `AbortSignal`、next-run 运行态和有界 `stopAndDrain`。
- timeout 后任务若忽略取消，仍占用 running/lane 直到真实 Promise settle，避免伪取消后重入；正常停机不会再误记 timeout/failure。
- 热用量窗口从聚合后的 detached Promise 改为独立 scheduler job，进入 `stats-heavy` lane，并具备 lease、timeout、合并补跑和 drain 状态。
- PostgreSQL job lease 使用短事务 advisory xact lock 保护 claim，TTL heartbeat 和单调 fencing token 管理 owner；直连与 transaction pooling 均不持有 session lock。
- 权威写事务使用 `leaseKey + ownerId + fencingToken` 校验并 `FOR UPDATE` pin lease 行到提交，覆盖 usage cursor/桶、窗口 stage、表监控 cursor 和 Chat retention 状态推进。
- usage 首页预热复用 7 日统计窗口；fallback 最多 7 个单日 Top-512 查询，候选池 128，每轮 8 热门 + 24 轮转，PG 查询上限 1.5 秒；performance 多副本下仅 usage-worker replica 0 注册，避免最多 32 个副本重复执行同一轮预热。
- system metrics 趋势从 496 个范围全量重建改为受影响日期增量更新；同毫秒水位使用行指纹，同轮系统与进程样本合并成单个 PG 短事务。
- 256 shard 表监控的 relation、shard-table pair、目录读取和 PRAGMA 都受预算；移除常驻精确 `COUNT(*)`，retention 收敛到中央清理任务。
- Windows 网络慢采样使用 SWR 单飞缓存；performance publisher 使用稳定墙钟相位，Redis key 加入实例身份，避免多部署同 role/replica 覆盖。
- 代理、OAuth、余额使用有限并发、总预算和候选隔离；父任务取消后停止 admission，已开始 OAuth rotation 安全完成写回。
- prewarm/OAuth/runtime state 的 Redis 请求具备端到端 deadline；半开连接超时后会失效共享 client，不再无限占用任务 lane。
- model-trust 与 account-quality 已接入 `stats-online`、稳定相位、timeout/backoff、PG lease 和写事务 fencing；account-quality dirty marker 改为 CAS 清理。
- data-retention 在批次和阶段边界响应取消，Codex context 保持“当前批 storage key 删除完成后退出”的一致性尾巴。
- quota、usage overview、AI 性能摘要新增持久 dirty 表和 generation CAS。quota 每轮最多约 4096 个 `scope × window` 组合；overview 每轮 8 个账户；AI 性能摘要每轮 10 个账户，在线路径不再全表删除。
- AI 性能摘要从 30 分钟 TopN 组合任务拆成独立 5 分钟错峰任务；热 overview 与低频 overview 共用 dirty 队列，队列未清空时不受 source watermark skip 阻断。
- `production + performance` 缺少显式 `JUHE_AI_INSTANCE_ID` 时启动失败，避免跨主机 PID 碰撞覆盖 Redis 指标和重新同相。
- 日志目录维护收敛为单 owner，importer 支持停止、防重排和有界 drain。

## 4. 授权远端验证

环境：`192.168.1.203`，连接信息仅从用户指定的本地凭据文件读取，未写入源码、文档或测试产物。

隔离方式：

- 每轮创建 `codex_scheduler_smoke_<timestamp>_<random>` 唯一临时 PostgreSQL 数据库。
- schema 和默认值只应用到临时数据库。
- Redis 只使用唯一 namespace，并只扫描 `codex_scheduler_smoke:*` 测试前缀。
- `finally` 中终止临时库连接并精确 `DROP DATABASE`；不操作其他数据库或 key。

结果：

- Redis 6379 / 6380 / 6381：PING 通过；验证前后测试前缀均为 0。
- scheduled job lease PG smoke：并发 claim 只有一个 winner，token 按 `1 -> 2 -> 3` 单调推进，续租、接管、释放通过。
- usage rank / AI performance PG smoke：TopN 与 AI 性能任务独立执行，AI dirty account 局部 upsert 后同水位正确跳过。
- usage hot window PG smoke：overview dirty scope 与今日账号范围窗口正确发布，第二轮同源且无 dirty 时跳过。
- quota PG smoke：dirty scope 局部刷新、新增 37 小时配置的 keyset seed、减账归零删除均通过。
- Redis state/cache 真实回归通过，三个 Redis 角色均使用唯一测试 namespace。
- system metrics PG smoke：趋势、进程事件循环、索引计划、增量保留无关窗口和水位跳过通过。
- table monitor PG smoke：overview、表/库历史和索引计划通过。
- authorization usage range PG smoke：team/user 窗口结果与 unchanged skip 通过。
- 租约 smoke 在 PostgreSQL 直连和 6432 PgBouncer transaction-pooling 入口各通过一次。
- 最终临时数据库残留为 0，Redis 测试 key 残留为 0。

## 5. 边界与后续观察

- production performance 强制显式 `JUHE_AI_INSTANCE_ID`；非生产和 standalone 的 PID fallback 只保证本次进程生命周期内稳定。
- `AbortSignal` 是协作式取消。忽略 signal 的任务会继续占用 lane 直到 settle；这是防止并发重入的刻意语义。
- data-retention 的固定 cutoff 删除是单调、幂等操作，保留 job lease 和有界批次，不为跨 Redis/PG 原子投递引入 outbox。
- 资源 lane 只在单进程内协调；跨部署正确性仍依赖 PostgreSQL lease、对象级 claim 或明确的单 worker owner。
- 本报告证明本地回归和隔离 smoke，不代表已经完成生产部署、长时间 soak 或真实峰值容量验收。

## 6. PostgreSQL 性能规范的实际影响

本轮按 PostgreSQL 性能规范坚持：外部调用不放进事务、lease 生命周期使用短事务、本地 statement/lock timeout、keyset/有界候选、先选 relation 再取 exact size、批量写而非 per-row transaction。这样既兼容 transaction pooling，也避免为了分布式正确性制造长事务和连接占用。
