# Node 后台任务全局错峰审计报告（2026-07-26）

## 1. 执行摘要

本轮只审计 Node 后端，覆盖 `server`、`worker`、`db-service`、后台任务注册表、统计聚合、保留清理、探针、运行态采样和事件队列；没有修改生产调度或业务代码。

结论不是“给所有 Job 加随机延迟”。当前已有不少固定初始延迟，但仍存在三类问题：

1. **固定相位长期碰撞**：多个任务按相同周期和相近初始延迟运行，启动后会永久保持相位关系；多实例同时启动时也会再次同相。
2. **单轮工作量无界或近似全量**：有些任务会随账户数、日期窗口、分片数、表数或进程数放大，单纯错峰只能移动尖峰，不能消除尖峰。
3. **调度正确性与可观测性不足**：任务注册表中的 `singleOwner`、`leaseRequired` 等字段没有被调度器执行；本地 owner 调用缺少真实超时和取消；跨任务没有资源通道；部分被跳过或局部失败的任务会被记录为成功。

建议采用“**稳定相位 + 有界工作量 + 资源通道 + 多实例租约**”四层治理：

- 高频观测任务保持稳定周期，只做进程稳定相位，不做每轮随机漂移。
- 10 分钟以上的重任务采用固定完成后间隔、稳定时间窗和最多补跑一次。
- 随账户、表、分片或时间范围增长的任务必须增加游标、时间预算、增量刷新和批次上限。
- 多部署共享数据库时，重任务必须使用数据库租约、claim 或 advisory lock；错峰不能承担防重职责。
- 事件驱动队列继续使用微批和背压，不人为增加随机延迟。

需要先处理的正确性问题是：PostgreSQL 分支目前没有注册 `authorization-usage-range-windows-refresh`，这可能导致授权维度历史窗口长期不刷新。该问题独立于错峰，应作为第一阶段修复并补回归。

## 3. 当前调度模型

### 3.1 已有能力

`WorkerScheduler` 支持固定周期、固定初始延迟、立即执行和同名任务防重。一个任务仍在运行时，下一次 tick 会增加 `skippedCount`，不会并发启动同名任务。

当前只有 `workerReplicaIndex === 0` 启动后台任务，因此单个 supervisor 拓扑内不会由 usage / log worker 副本重复启动整套周期任务。

账户健康检查已经采用“1 小时基础周期 + 账户稳定小范围错峰”，应继续作为对象级到期时间的正确范例。AI 健康监控应复用这次正常探测的结果，不额外请求账户。模型质量定时检查由用户控制，保持独立，不在本轮改变其用户周期。

### 3.2 缺失能力

- 调度器只使用 `setTimeout` 后接 `setInterval`，没有稳定 jitter、固定完成后间隔、超时取消、失败退避或跨任务资源通道。
- 同名任务运行过久时只会持续丢 tick，没有“最多合并一次”的补跑语义。
- 任务 Promise 永不结束时，该任务会永久处于运行中；调度器没有 `AbortSignal` 或 `timedOut` 状态。
- 注册表的 `singleOwner`、`shardable`、`leaseRequired`、`hotspot` 目前主要是描述字段，没有被 scheduler 强制执行。
- 多套 Node 部署共享 PostgreSQL 时，固定初始延迟无法避免重复执行或同相执行。
- 当前状态缺少 `nextRunAt`、`overdueMs`、`pending`、连续失败、超时、租约 owner 和 backlog 等信息。
- worker 关闭流程会刷新队列，但没有统一停止并等待周期任务结束的 `stopBackgroundJobs()`。

## 5. 确定性碰撞与启动尖峰

### 5.1 10 分钟维护任务

当前相位会形成永久碰撞：

- `table-storage-monitor`：启动后第 3 分钟，此后每 10 分钟。
- `chat-retention-cleanup`：启动后第 3 分钟，此后每 10 分钟。
- `data-retention-cleanup`：启动后第 13 分钟，此后每 10 分钟。

因此表监控和聊天清理每轮同时运行；从第 13 分钟起，数据保留清理也加入同一相位。SQLite 的授权冷窗口在第 43 分钟还会与这组 10 分钟任务叠加。

建议先用可测试的固定槽位拆开，例如：

- 表监控：每个 10 分钟窗口约第 1分30秒。
- 聊天清理：约第 4分30秒。
- 数据保留清理：约第 7分30秒。
- 每个部署仅叠加 0～30 秒的稳定实例相位；最终槽位以虚拟时钟碰撞测试和本地负载测试为准。

### 5.2 统计任务

- 30 / 60 秒任务集中在启动后第 0、5、8、12、16 秒，虽有人工作峰，但所有副本同时启动时仍会同相。
- `usage-record-first-page-prewarm` 与 `client-ip-stats-aggregation` 都在第 8 秒相位，每 30 分钟固定相遇。
- 表监控在 3 分钟，系统趋势在 3分20秒；表监控允许等待 20 秒，两者存在临界重叠。
- performance 各进程每 5 秒同时向 Redis 发布运行态；系统采样也在第 5 秒启动且 30 秒为 5 秒整数倍，读写会长期同相。

### 5.3 重启和多部署

所有相位目前都相对于进程启动。supervisor 批量启动进程时，250ms 左右的启动间隔不足以分散数据库和 Redis 周期尖峰；多个部署在相近时间重启时也会重新同步。稳定相位必须包含可稳定配置的实例标识，不能只依赖 PID。

## 6. P0 / P1 / P2 风险

### P0：先保证正确性

1. **PostgreSQL 授权使用窗口未调度**
   - PostgreSQL 分支在注册 scope / authorization 冷窗口前提前返回。
   - hot refresh 只覆盖 overview 与 scope，不覆盖 authorization。
   - 没有找到其他生产 Node 调度入口。
   - 风险：授权团队 / 用户历史范围统计可能长期陈旧。
   - 动作：补 PostgreSQL 注册、幂等与回归；不要用错峰改造掩盖缺失任务。

2. **多部署 single-owner / lease 仅为元数据**
   - 单 supervisor 内只有 replica 0 启动任务，但多套部署共享数据库时仍会重复。
   - 动作：对重统计、清理、OAuth 刷新等任务使用数据库租约、advisory lock 或 claim + fencing。

### P1：高概率形成资源尖峰或长期饥饿

1. **系统趋势每 30 分钟全量删除重建**
   - 最近 31 天会生成 496 个任意起止日期范围。
   - standalone 约输出 39,660 行；performance 默认 14 个进程角色约输出 99,150 行。
   - 每 30 秒采样都会更新 watermark，`skipIfUnchanged` 通常无法命中。
   - 动作：只刷新受当前小时影响的窗口，封口历史窗口不动；若产品不要求任意日期范围秒开，只预生成常用窗口。

2. **使用概览窗口规模可能达到 scope × 496**
   - 最多 5000 scope 时理论摘要行约 248 万。
   - 动作：增量、游标、分段短事务，并消除 hot 与 30 分钟 overview 的重复刷新。

3. **全账户首页预热没有总预算**
   - 当前遍历全部启用系统账户，并非文档意图中的近期活跃账户。
   - 动作：只取近 7 日活跃 / 最近使用账户，持久游标，小批和总时间预算，逐账户失败隔离。

4. **表存储监控在分片场景放大**
   - Codex context 聚合会对选择表 × 全部分片执行精确 `COUNT(*)`；100 设置表 × 256 分片可达 25,600 次精确计数。
   - PostgreSQL 在挑选默认 4 张表前先读取全部 relation 大小；分区很多时依然昂贵。
   - 样本内部还清理旧表快照，与中央 retention 重复所有权。
   - 动作：去除精确 COUNT，限定 relation / shard 对预算，清理归中央 retention。

5. **共享窗口锁会静默丢刷新**
   - rank、trend、overview、scope、authorization、hot 共享一个运行标志。
   - 冲突时正常返回，scheduler 记录成功；除 hot 外没有 pending 补跑。
   - 动作：使用 `stats-heavy` 资源通道和 queue-one 合并；状态记录为 coalesced / skipped，不得记录成功。

6. **本地 owner 没有真实超时和取消**
   - stats writer owner 直接调用 handler，绕过 IPC 请求的 20 / 30 秒等待超时。
   - Promise 竞速超时也不会取消正在执行的 SQL 或上游请求。
   - 动作：调度器传递 `AbortSignal`；PostgreSQL 配合 `statement_timeout` / `lock_timeout`，SQLite 拆为可中断的小阶段。

7. **代理延迟刷新理论执行时间远大于周期**
   - 20 个代理顺序执行，每个最多 25 秒，理论可达 500 秒，周期仅 60 秒。
   - 动作：加入跨轮游标、总预算、有限并发和供应商级速率限制；纠正 hotspot 元数据。

8. **Windows 系统采样每 30 秒启动 PowerShell**
   - 网络计数通过 `Get-NetAdapter*` 获取，默认每天 2880 次子进程启动。
   - 动作：网络计数降为 60～120 秒慢采样并缓存，30 秒主样本复用；或替换为轻量原生读取。

9. **进程采样事务放大**
   - 系统样本和每个进程样本分别开启事务。
   - performance 默认约 15 个事务 / 30 秒，约 43,200 个事务 / 日。
   - 动作：一轮样本合并为一个 stats writer 批量事务。

10. **日志目录维护存在多进程重复扫描**
    - 日志流构造时会 cleanup，`startLogMaintenance` 又立即 cleanup 后每小时执行；server、db-service 和各 worker 均会启动维护。
    - 动作：共享日志目录只指定一个维护 owner，或限定进程只清理自己的文件。

### P2：调度语义、状态和运行效率改进

- usage aggregation 首轮立即运行，首次通常还会触发 hot window 链；需要 startup warm-up 和完整时间预算。
- account balance 的 45 秒预算不能取消底层请求；下一次刷新按完成时间精确顺延，批量启用可能聚集。
- client IP 聚合即使 `processed = 0` 也会调用范围刷新。
- 模型质量任务单轮可运行 10～15 分钟，scanner 会持续跳 tick；wrapper 还可能丢失局部失败结果。用户周期保持不变，只改执行队列和状态。
- 新增的模型质量健康同步补偿每分钟第 58 秒扫描最多 20 个失败 run；它属于系统幂等补偿，不改变用户设置，但注册表声明的 lease 仍需真正执行，并应把局部失败返回 scheduler。
- 手工账户测试维护每 2 秒 fire-and-forget，缺少 in-flight guard，DB service 变慢时可能重叠。
- supervisor 重启退避缺少 jitter，多实例同一故障后可能同步恢复。
- 动态 `usage_hot_window_refresh` 和部分 retry queue 未进入注册表；个别 role 元数据与实际 owner 不一致。

## 7. 不应统一加错峰的链路

以下链路以事件延迟和背压为核心，不应为了“整齐”加入秒级随机延迟：

- usage 写入：500ms / 1000 条 / 8MiB 微批。
- audit 写入：5 秒 / 500 条微批。
- operation 写入：100ms / 200 条微批。
- public API log、record maintenance、runtime log tail 等事件驱动队列。
- 用户手工触发的账户测试。

这些链路应保留微批、队列上限、背压、失败重试和可观测 backlog；如果发生峰值，优先调整批次、并发、消费配额和资源隔离。

| 类别 | 示例 | 推荐语义 |
| --- | --- | --- |
| 高频观测 / 控制 | 5～60 秒 sampler、状态同步、熔断恢复 | fixed-rate + 稳定秒槽；不做每轮随机 |
| 低频轻任务 | 小批 reconcile、expiry sweep | 稳定初始相位 + 小范围实例相位 |
| 重统计 / 存储维护 | 窗口、表监控、retention | fixed-delay + 稳定时间窗 + 资源通道 + queue-one |
| 对象到期任务 | 健康检查、余额、OAuth | 持久化 `due_at` + 对象稳定错峰 + claim |
| 用户控制周期 | 模型质量检查 | 保持用户周期；仅治理候选队列、公平性、并发和超时 |
| 事件驱动微批 | usage / audit / operation | 不加 jitter；使用微批、背压和隔离 |

### 8.2 Scheduler 能力

建议扩展而不是继续散落硬编码延迟：

- `scheduleMode: fixedRate | fixedDelay`
- `phaseOffsetMs` 和 `jitterWindowMs`，由 `jobName + workerRole + stableInstanceId` 稳定派生
- `timeoutMs`、`AbortSignal`、`timedOutCount`
- `overlapPolicy: skip | coalesceOne`，重任务默认最多合并一个尾随执行
- 失败后有界 full-jitter backoff；成功后回归正常相位
- `resourceLane`：如 `stats-heavy`、`storage-maintenance`、`external-diagnostics`
- `leaseKey` / `claim` / fencing token 用于跨部署正确性
- 运行态暴露 `nextRunAt`、`pending`、`overdueMs`、连续失败、backlog、lease owner 和上次跳过原因

稳定实例标识不能默认使用 PID；performance 部署应明确设置稳定 `JUHE_AI_INSTANCE_ID`，或持久化调度 seed。

### 8.3 资源通道

- `stats-sample`：高优先级，不能被趋势和窗口重建长期阻塞。
- `stats-heavy`：趋势、排行、overview、scope、authorization 等单并发或严格小并发。
- `storage-maintenance`：retention、表监控、日志索引等单并发并错开数据库高峰。
- `external-diagnostics`：复用当前账户诊断并发，同时限制代理、余额、OAuth 等外部 I/O 的总并发。

资源通道只控制当前部署并发；跨部署仍需数据库租约或 claim。

## 9. 分阶段实施建议

### Phase 0：正确性与事实对齐

- 补 PostgreSQL `authorization-usage-range-windows-refresh` 调度与回归。
- 对齐任务注册表与实际 owner、hotspot、动态任务和 retry queue。
- 让模型质量 wrapper、窗口锁冲突等返回真实 partial / skipped / coalesced 状态。

### Phase 1：通用调度原语

- 引入 fixed-delay、稳定相位、真实 timeout / abort、queue-one、失败退避和 next-run 状态。
- 增加稳定实例 ID 校验，避免不同部署同相。
- 为多部署重任务加入租约 / claim 契约。

### Phase 2：低风险重新排相与资源通道

- 先拆开 10 分钟表监控、聊天清理、数据 retention 的确定性碰撞。
- 将 30 分钟重统计分散到更宽时间窗，并接入 `stats-heavy`。
- performance publisher 按实例 / 角色 / 副本稳定分散到 5 秒周期内，sampler 放在 publisher 波次中点。

### Phase 3：削减单轮工作量

- 系统趋势和使用窗口增量化。
- 首页预热改近期活跃账户 + 游标 + 总预算。
- 表监控移除精确 COUNT 并限制 shard / relation 对。
- 系统指标写入合并事务，Windows 网络采集降频缓存。
- 代理刷新、OAuth、余额等改为总预算 + 游标 / claim。

### Phase 4：对象级到期错峰

- 健康检查保持当前 1h + 小范围稳定账户错峰，并作为 AI 健康监控唯一正常探测来源。
- 余额等系统控制的到期任务可使用小而有上限的对象稳定错峰，并在 UI 显示准确下次执行时间。
- 模型质量定时检查保持用户配置周期，不暗加不可见 jitter。

### Phase 5：灰度与生产观测

- 先在隔离实例运行 15 分钟和 60 分钟观测，再灰度单个部署。
- 与现有《Redis 队列隔离与后台任务降载》计划合并执行压力门禁和维护错峰，避免创建两套相互冲突的调度方案。

## 10. 验证与验收

### 10.1 自动化回归

- 虚拟时钟运行至少 2 小时，断言同一资源通道的重任务不重叠。
- 同一 seed 相位可复现，不同稳定实例 ID 能分散，延迟不超过新鲜度预算。
- 长任务 timeout 能发出 abort，最多合并一次，不产生无限 backlog。
- 失败使用有界抖动退避，成功后回归正常相位。
- 两个 Node 实例竞争同一 lease 时只有一个执行，失租后旧 owner 不能继续提交。
- worker shutdown 能停止新调度并等待 / 取消在途任务。
- PostgreSQL 授权使用窗口能按计划刷新并具有幂等回归。
- 10,000 账户预热验证单轮查询数、时间预算和游标推进。
- 256 分片表监控断言没有精确 COUNT，SQL 数量受预算约束。
- 系统趋势验证正常小时只更新受影响窗口，而非 496 范围全删重建。

### 10.2 负载与可观测门禁

- 维护窗口内管理接口 p95 相比基线退化不超过 20%。
- server / db event-loop lag p95 小于 100ms，stats / ingest worker 小于 250ms。
- 同一部署没有 `stats-heavy` 或 `storage-maintenance` 重任务并发碰撞。
- 统计新鲜度保持在各自 SLA 内，不能用错峰换取长期陈旧。
- 外部探测总并发不高于改造前配置；AI 健康监控不新增探测请求。
- 模型质量检查的用户周期、启停和手工执行语义不改变。

## 11. 回退预案

- 所有新 scheduler 能力通过独立配置开关启用，可逐任务回退到原固定周期。
- 相位调整只改调度，不改业务写入格式；出现新鲜度回归时可单任务恢复旧相位。
- 资源通道上线前保留现有同名 in-flight guard，避免回退时产生并发执行。
- 增量窗口改造需保留全量重建脚本作为人工修复路径，并对比新旧结果后再切读。
- 租约必须带 fencing 或提交前 owner 校验；不能只依赖 TTL，避免旧 owner 恢复后双写。

## 12. 最终优先级

1. 补 PostgreSQL 授权使用窗口缺失调度。
2. 实现 scheduler 的稳定相位、fixed-delay、真实超时 / 取消、queue-one 和运行态。
3. 加入 `stats-heavy` / `storage-maintenance` 通道与跨部署租约。
4. 拆开 10 分钟维护任务确定性碰撞。
5. 将系统趋势、overview、预热和表监控改为增量 / 有界执行。
6. 分散 performance publisher，合并系统指标事务并降低 Windows 网络采集成本。
7. 再处理代理、余额、OAuth 等外部 I/O 的游标、总预算和 claim。
