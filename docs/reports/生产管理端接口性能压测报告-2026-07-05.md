## 5. 关键观察

- 最初用户浏览器截图中的秒级延迟不是单一 PG 全局锁问题，而是多因素叠加：动态 ETag / 304、运行态同步等待、前端重复请求、DNS 慢节点、表监控窗口排序。
- 生产普通用户 self broad：公网 40/40 成功，整体 p95 `329.23ms`，max `402.43ms`；内网 40/40 成功，整体 p95 `148.64ms`，max `190.16ms`。
- 生产管理员 broad 修复前：内网 97/97 成功但 p95 `490.34ms`，max `1581.67ms`；慢点集中在单样本 `table-monitor/overview`、授权详情和分组详情。
- 表监控旧查询对 `table_storage_snapshots` 做窗口排序，生产约 9913 行时仍需约 `715ms`；改为 `GROUP BY table_keys + CROSS JOIN LATERAL latest` 后 `EXPLAIN ANALYZE` 约 `202ms`，上线后再叠加短 TTL 缓存。
- 公网链路仍可能偶发首包 / edge 长尾，必须用 `Server-Timing` 区分后端耗时和公网总耗时。

## 6. 边界

- 本报告中的生产 GET 压测刻意避开写接口和高成本上游调用，避免破坏生产数据或触发外部费用。
- 单样本 endpoint p95 等于 max，只能判断是否有明显秒级长尾；容量结论需另开并发压测。
- 审计保留清理写长尾没有在本轮热修中修改，原因是它涉及数据保留和审计删除语义，需单独设计分阶段、限时预算和慢批次观测。
