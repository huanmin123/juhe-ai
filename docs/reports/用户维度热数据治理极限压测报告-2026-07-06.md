# 用户维度热数据治理极限压测报告（2026-07-06）

> 历史说明：本报告记录 2026-07-06 当时的同库 `juhe_archive` 方案。该方案已于 2026-07-12 被 PLAN-0091 替换为统计安全游标后的整日分区直接 `DETACH / DROP`；下方结果仅作为历史压测证据，不代表当前运行契约。

## 1. 结论

- 通过。本轮在测试 PostgreSQL / Redis 高性能模式下，写入并查询 `500,000` 行 hot `usage_records`、`100,000` 行待归档 `usage_records`、`250,000` 行 `usage_scope_range_windows`，没有错误、死锁、Seq Scan 或阈值违规。
- 64 并发、6000 次混合查询下，整体 p95 为 `51.58ms`，p99 为 `136.27ms`；usage 查询 p95 为 `52.17ms`，range window 查询 p95 为 `50.47ms`。
- PG 整日分区归档表现稳定：`100,000` 行旧分区 detach 到 `juhe_archive` 并写入 manifest，耗时 `674.34ms`。
- 表监控全量采样表现稳定：采样 6 个逻辑库、143 张表，耗时 `181.44ms`。
- 真实入口读写混合压测通过：测试后端经 `/v1/chat/completions` 写入，后台管理端同时读取使用记录、统计窗口和表监控接口；90 秒混合阶段写入 `1,920` 次、读取 `2,984` 次，写入错误 `0`、读取错误 `0`、PG deadlocks `0`。
- 混合阶段读取 p95 为 `3583.25ms`，相对读基线 p95 `2722.41ms` 放大 `1.316x`；最慢的读接口是 `GET /usage-records today`，混合 p95 `3968.52ms`、p99 `5246.71ms`。读没有被写入拖垮，但真实入口管理端读延迟明显高于存储层直连查询，后续优化重点应放在系统 API 读链路和使用记录列表响应成本。
- 当前白名单索引仍有明显写放大：每个 10 万行 usage 日分区约 `55.80MB` 表数据、`291.99MB` 到 `293.28MB` 索引，索引 / 表大小比约 `5.23x` 到 `5.26x`。这是用户维度高频索引换查询稳定性的成本，后续如果写入量继续上升，优先继续压缩低频索引，而不是回到全局索引。

## 2. 范围

- 测试对象：`usage_records` PG 日分区写入和用户维度查询、`usage_scope_range_windows` 范围窗口查询、PG 分区归档、表监控 PG 采样。
- 覆盖链路：
  - 存储层极限压测：直接压测 PostgreSQL / Redis performance 存储层，包含 Redis PING、PG 分区创建、批量写入、并发查询、EXPLAIN 门禁、归档 manifest 和表监控采样。
  - 真实入口混合压测：启动真实后端进程、真实 Redis Stream / PG 写入、mock OpenAI 上游，通过 `/v1/chat/completions` 写入，同时通过系统后台 HTTP 接口读取使用记录、统计和表监控页面数据。
- 不覆盖内容：真实 OpenAI 上游耗时 / 额度消耗、前端渲染、线上历史数据迁移、真实生产流量混部影响。

## 5. 观察

- `usage_records` 日分区后，用户 + 日期、用户 + account、用户 + trace 前缀查询均命中分区局部索引，没有 Seq Scan。
- `usage_scope_range_windows` 在 25 万行规模下，Top scopes 查询命中 `idx_usage_scope_range_windows_account_usage_order`，lookup 命中 `idx_usage_scope_range_windows_range_lookup`。
- PG 模式下本轮压测数据没有写入 `usage_record_shard_entries`，验证了 PG 不再复制 SQLite usage catalog 明细。
- 表监控采样未实时 `COUNT(*)`，采样耗时低于 200ms，适合作为后台周期任务。
- 真实入口混合压测下，读请求没有因为写入产生错误、死锁或锁等待；混合 p95 放大 `31.6%`，说明读写资源隔离方向有效。
- 真实入口混合压测的 HTTP 层读延迟远高于存储层直连查询。主要原因包括完整系统 API 中间件、DB service HTTP 代理、成本拆解、统计窗口读取、表监控响应组装和高并发写入带来的连接竞争；这不改变分区 / 索引方案结论，但说明线上容量评估不能只看存储层 p95。
- 最大写入成本来自 `usage_records` 分区局部索引。当前查询延迟稳定，但索引体积仍是主要容量成本。

## 6. 边界

- 本次使用合成数据，不代表真实用户分布、真实模型错误分布或真实 trace 热点。
- 存储层极限压测不包含网关 HTTP、DB service IPC、ingest-worker Redis Stream 消费和前端页面渲染耗时；真实入口混合压测已覆盖网关 HTTP、DB service 和 Redis Stream，但仍不包含浏览器前端渲染。
- 真实入口混合压测使用本机 mock OpenAI 上游，不消耗真实 OpenAI 额度，也不代表真实上游慢响应、流式长连接或上游错误分布。
- 本次压测结束后脚本清理了测试分区、range window 测试行、归档 manifest 和表监控采样行。
- 线上旧数据迁移、历史索引清理和真实生产容量采样仍需在维护窗口单独执行。
