## 2. 优先修复清单

### R1 · P1 · 媒体账户状态机缺少恢复闭环（已提交）

**影响**：视频、音频账户可能从可用变为长期不可调度。

完整静态调用链确认了三条触发路径：

1. active 媒体账户修改代理、`base_url` 或有效 Key，未显式提交 `status`：`accounts/patch.go:983` 将 `connectionChanged` 落为 `pending_test`。前端 `accountSavePayload.ts:336`、`accountEditPatch.ts:32` 只在主动切换状态时提交状态，正常连接编辑会触发。
2. 媒体请求命中错误策略：`chain_error_policy.go:266` 产生 `rate_limited` / `temporary_unavailable`，`chain_error_policy_effects.go:529` 落库；冷却到期后 `chain_accounts.go:1296` 的正常候选仍要求 `active`。
3. error 账户人工清除失败：`accounts/patch.go:350` 固定恢复为 `pending_test`。

断点：新建媒体检查模式是 `audio_speech` / `video_create`，但 J1 的 PostgreSQL `jobs/internal/accounthealth/direct_input_reader.go:487`、SQLite `direct_input_reader_sqlite.go:794` 白名单都不接受这些模式。按账户立即投递也走同一查询，因此无法绕过。冷却态人工恢复仍可直接 active，所以准确结论是自动恢复断裂，并非任何人工动作均无效。

**根因判断**：能力域拆分只用“新建媒体默认 active”解决首次创建，仍复用需要对话健康检查完成的编辑、错误处罚与人工恢复状态机。

**验收**：active audio/video 修改连接后验证可调度闭环；Mock 短冷却错误，推进时钟后验证再次派发；error 人工恢复不永久停在 pending。先定媒体状态机契约再修，不能靠前端偷偷补 `status=active` 掩盖服务端状态机缺口，也不能随意新增收费媒体探针。

证据等级：完整静态调用链；本次尚未动态执行上述三条故障复现。

### R2 · P1 · 普通 ensure/SQLite 启动包含破坏性 studio 清理（未提交）

**影响**：有历史媒体工作室数据的库，在常规 schema 初始化或 SQLite 升级重启时发生数据删除。

`maintenance/internal/schema/pg_schema_business_tables.go:2481` 在普通 `--ensure-schema` 中删除 8 张 studio 表、studio API Key；`:2497` 删除 `studio_domains_json`。SQLite `schema/sqlite_schema.go:724` 重建 API Key 表时 `WHERE purpose <> 'studio'` 排除旧 Key；gateway `cmd/juhe-ai-gateway/storage_bootstrap.go:44` 每次 SQLite 启动会调用该 ensure。

这些入口没有与该删除绑定的停写、备份、核验确认。文档和 `deploy.sh:268` 仍将普通 ensure 描述为“幂等加法”。退场本身可以是需求，但“退场已同意”不能代替数据清理与恢复契约。

**修复与验收**：普通 ensure 退出破坏性清理，另设明确维护命令；先备份与停写，核对受影响表/Key 数量，再清理与后检。用历史 schema fixture 验证普通启动不丢数据、显式清理只删除目标、失败回滚可恢复。双方言要裁决一致：当前 SQLite 未删除旧 studio 表，而 PG 会删除。

### 不能宣称完全隔离的部分

1. **能力域不是请求隔离墙**。网关按 `supported_endpoint_modes` 选候选，不读 domain；存量跨域能力继续参与派发，仍共享该账户并发、冷却和账户级熔断。这是 D2/D4 的兼容裁决，不是违反当前设计的 bug，但“不同菜单相互完全无影响”并未实现。新建独立账户才能形成独立运行单元。
2. **媒体状态机仍受对话健康检查假设影响**。R1/R5 是边界未闭合的具体表现，优先从生命周期契约修复，不逐点打补丁。
3. **业务事实仍多处镜像**。供应商×域允许/默认集、健康检查白名单、前端候选、J1 读入条件分别维护；目前测试能证明部分矩阵，无法防止遗漏跨层传导。应围绕唯一能力描述或契约生成收敛，并保留行为测试。
4. **存量兼容的验证器混淆新增候选与既有事实**。R6 表明候选的分页/域过滤不能代替独立配置验证。
5. **退场清理未收口**。代码删除 studio 模块，但 API Key 前端仍保留 studio 豁免；`docs/architecture/Go三项目架构基线.md:14` 仍记 jobs studio 结算。当前 PG/SQLite 清理不一致。

文档还需回正：`docs/functions/核心功能设计.md:475` 仍称调度偏好在路由策略接口维护；`docker/single-server/README.md:133`、`docs/deploy/部署指南.md:91` 仍使用 `intervalMinutes=1` 创建示例，新建/PATCH 当前下限已为 5，历史 1 分钟只是存量兼容。

### shared 与后台修复专项

本次未确认新的高置信协议缺陷：F2/F3/F4 的最终请求均已进入 `upstreamenvelope.Build`；A/B/C 预算、URL 与 SSE 差异有明确契约。其范围是系统探针，不涵盖 `/v1` 用户请求，后者未迁入同一源不能直接算遗漏。J1 schemaReady 仅在成功提交后记忆；J3b 已先读完并关闭 rows 再写租约。成功成本回填已退出常规 ensure，批更新与 marker 同事务，扣减后 CASE 补正有对应测试。

当前 2s 锁等待仅覆盖部分 jobs 投影路径；gateway 账户脏标记 `chain_dispatch.go:969` 仍直接取锁，这是 BUG-0313 档案明示的 `/v1` 错误语义保护边界，不作为遗漏缺陷。未证实其真实 PG 等待上限和回滚行为，需补并发锁测试：超过 2s 返回 55P03、事务回滚、连接复用时 SET LOCAL 自动恢复；不能仅用 SQL 顺序 Mock 宣称等待治理生效。

## 6. 本轮复审裁决与实施补充（2026-10-14）

本轮没有把原报告中“缺口待修”或“检查通过”直接视为结论；按当前工作区源码复核后，作出以下范围裁决并落地对应修改。所有结果仍属于未提交工作区，不代表生产已部署。

- **媒体恢复范围**：audio/video 账户创建默认 active，创建和配置编辑不写 J1 健康快照、不投递对话探针；连接编辑保持媒体账户状态，人工清除 `error` 直接恢复 active。冷却恢复态准入和成功 CAS 只覆盖 `video_generation` 视频异步任务、`video_create` 视频账户及冷却已空/到期的状态；长音频 `audio_transcription` 轮询保持 active-only，同步 TTS 不走 `media_jobs`/CAS。本轮不扩展 STT 请求族或补建 `/v1/audio/jobs` 恢复语义，作为独立后续范围。
- **Studio 退场保护**：普通 ensure 保留历史 SQLite studio API Key 与表；显式 retirement 命令在写入前检查 studio Key 是否仍拥有 OpenAI-compatible files/vector-store 资源，存在时拒绝并报告计数；命令与其他 maintenance 操作互斥。该命令仍是多语句非原子清理，运行前必须停写并验证外部备份；报告为执行后结果，不是 dry-run。
- **SQLite CHECK 裁决**：PostgreSQL ensure 将 `api_keys.purpose` 扩为三值；已有 SQLite 两值 CHECK 不在普通启动时重建。保留历史 SQLite 形状并接受 PG/SQLite 约束不对称，以避免常规启动重建业务表及潜在数据损失。
- **其他补正**：host-init 的 fstab 命中改为精确首字段比较，覆盖 `/swapfile-extra` 前缀碰撞；前端基线模型映射比较 `enabled`，防止仅切换启用状态仍被当作未修改。
