# 网关阶段日志与异步写入验证报告（2026-07-21）

## 验证结论

- 网关请求已能按同一 `traceId` 重建“body 接收/捕获 -> handler -> 分组权限 -> 客户端画像/协议 -> 候选账户 -> 模型能力 -> 账号避让 -> 配额/容量 -> IP/账号并发 -> 上游准备/fetch/首输出/body -> 下游 finish -> audit finalize”的阶段时间线。
- Node 文件/控制台日志使用有界双优先级队列和独立 writer worker；批量消息、批量文件写、失败预留容量、worker ACK、关闭 drain、轮转清理和 runtime-log line 回传均有回归证据。
- Go 日志使用有界异步 `slog.Handler`，HTTP 入口统一关联 `traceId/requestId`；Node HTTP、DB service IPC、worker 和 Go HTTP 共享 `version/service/role/event` 基础字段。
- 最终 r10 的 5 秒、并发 10、mock 上游 5ms info 压测共 1,552/1,552 成功，请求中 28 类阶段全部出现；结束时 `pendingEvents=0`、`pendingBytes=0`、`normalDropped=0`、`failureDropped=0`、`destinationErrors=0`。
- 热请求本地路由链路不是当前主要耗时来源；精确 `upstream.fetch_headers` p50 17.108ms、p95 27.049ms。preflight 热路径 p50 0.445ms、p95 0.772ms，但冷启动样本仍接近 1 秒，生产慢请求应先区分冷启动、缓存构建和真实存储访问。

## 失败现场验证

使用 mock 上游错误率 100% 的单请求故障注入（r2）得到 HTTP 503。日志中保留 42 个已执行阶段，`upstream.dispatch.failed` 为 `expected_failure`、`reasonCode=upstream_accounts_exhausted`，`audit.finalize` 同样为 `expected_failure` 并保留 `statusCode=503`、`errorPhase=dispatch`、`errorCode=upstream_retryable_error`、`attemptCount=4`；汇总事件 outcome 为 `expected_failure`。未出现日志队列丢弃或 writer 错误。

未预期异常路径会同时写 `gateway.request.stage` info 和 `gateway.request.failure` error；失败现场包含 Error/cause/stack、阶段摘要、队列快照和有界截断元数据。普通日志的原文/捕获边界遵循项目既有《安全与日志策略》，本次没有新增输出层脱敏规则。

## 日志开销 A/B

使用相邻的 5 秒、并发 10 测试对比 silent 与 info。短时本机结果会受 SQLite、GC 和调度抖动影响，只用于识别数量级，不作为生产容量承诺。

info 一轮写入并索引 17,578 行；结束时队列已完全追平。同步留在业务线程上的主要成本是 Pino 字段组装/JSON 序列化，文件 I/O、控制台 I/O、轮转、目录清理和索引字段 JSON 提取由 writer worker 执行。主进程仍负责小型 line 分发、source hash 和 Redis/IPC 入队，因此“异步”指不等待 I/O/ACK，而不是零 CPU。当前 p95 增量约 2.5ms，但 QPS 与 CPU 差异说明“每阶段 info”不是零成本；后续容量规划应按目标机器、真实 PG/Redis 和真实日志盘复测。
