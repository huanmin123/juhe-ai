# 网关请求到账户选择链路耗时分析报告（2026-07-20）

## 1. 结论

本轮在 Windows 本机使用项目现有 `gateway-performance-test.ts`，启动临时 SQLite + memory 网关、临时 mock OpenAI 上游，并通过真实 `/v1/responses` 请求测量客户端到上游返回的端到端耗时。测试没有访问真实供应商，也没有写入项目正式数据库。

本轮能确认的是“账户数量与端到端延迟存在相关性”和“事件循环存在长尾”，不能仅凭端到端数据把成本归因到候选过滤、模型过滤、配额、容量排序或 SQLite/audit 某一个阶段。要回答“找到账户用了多少毫秒”，还需要业务函数内的 opt-in 分段 timer。

- 0ms mock 上游、8 个账户、并发 8：p50 `13.57ms`，p95 `16.44ms`，p99 `153.69ms`，成功 QPS `452.94`。
- 0ms mock 上游、64 个账户、并发 8：p50 `20.42ms`，p95 `26.41ms`，p99 `480.33ms`，成功 QPS `268.86`。
- 同样 8 个账户、上游固定 50ms、并发 1：端到端 p50 `62.40ms`；相对 0ms 对照增加约 `46.9ms`，这是端到端增量，不等同于可严格分解的“网关内部耗时”。并发 8 的 p95 升到 `1075.86ms`。

因此，本报告只能给出本机 mock 上游下的 E2E 基线：缓存命中、账户池较小时 p50 约十几毫秒；账户池从 8 增到 64 时出现性能恶化信号，但具体阶段和因果关系仍待分段测量。生产 PostgreSQL/Redis、真实代理和真实上游不能使用本报告数值作为 SLA。

## 2. 实际链路

请求主链路按代码调用关系为：

1. `handleOpenAIGatewayRequest` 接收请求并建立 trace、审计捕获、请求快照和客户端画像。
2. `prepareOpenAIGatewayDispatchContext` 执行 preflight。
3. `resolveGatewayRuntimeAsync` 根据 API Key 解析系统账户、路由策略/分组绑定、运行态配置和缓存账户窗口。
4. 从分组缓存取得账户候选；必要时按请求模型重新加载 model-aware candidate window。
5. 对候选账户执行请求能力过滤、支持模型/模型映射过滤。
6. 在 dispatch preparation 中执行本地抑制/运行态降级排序、授权额度判断、容量判断和调度准备。
7. `fetchFirstAvailableUpstream` 获取账户并发槽，向该账户的上游 Base URL 发请求；失败时可能继续尝试候选账户或回退分组。
8. 响应先通过非流式/流式处理完成客户端 HTTP `finish/close`；随后执行 finalization，并将 usage/audit 入队。这些后置工作可能影响后续请求的事件循环或队列压力，但不是当前客户端 `fetch` 延迟中可直接拆出的同步阶段。

关键实现位置：

- [routes.ts](/F:/sub2api-lite/backend/src/modules/gateway/routes.ts:184)：入口、preflight 和 upstream dispatch。
- [preflight.ts](/F:/sub2api-lite/backend/src/modules/gateway/request/preflight.ts:184)：API Key/runtime、分组账户窗口和候选过滤编排。
- [runtime-cache.service.ts](/F:/sub2api-lite/backend/src/modules/gateway/runtime/runtime-cache.service.ts:287)：分组账户缓存读取。
- [candidate-filter.ts](/F:/sub2api-lite/backend/src/modules/gateway/dispatch/candidate-filter.ts:33)：请求能力过滤、模型过滤和 model-aware reload。
- [preparation.ts](/F:/sub2api-lite/backend/src/modules/gateway/dispatch/preparation.ts:373)：额度与容量相关准备。
- [upstream-dispatch.ts](/F:/sub2api-lite/backend/src/modules/gateway/dispatch/upstream-dispatch.ts:134)：账户排序、并发槽和上游尝试。

| 1 | 8 | 481.29 | 12.38ms | 16.31ms | 160.22ms | 157.94ms | 0.55ms |

| 0ms | 1 | 55.63 | 15.48ms | 16.42ms | 113.58ms |

## 5. 瓶颈判断

### 已有测量证据（只到相关性层）

1. **账户数量相关的性能信号。** 1/8 账户与 64 账户的 E2E 指标不同，但具体主导函数未知；64 账户并发 1 只有 33 个样本，p99 等于该批次最大值，不能当稳定尾延迟。
2. **事件循环存在长尾。** 0ms 上游时并发 8 的事件循环 p99 为 129–158ms；这只能证明运行时长尾，不能在没有禁用对照或有效 profile 的情况下归因于 SQLite WAL、审计、usage 或 GC。
3. **上游等待影响总耗时。** 50ms mock 上游使并发 1 的端到端 p50 增加约 47ms；真实代理和供应商网络必须从网关内部开销中单独拆分。

### 尚未被本轮直接测量的项

- 路由策略多模式（混合智能、权重、故障回退、轮询）之间的单请求差异。
- 多分组 fallback、失败重试和账户切换的额外耗时。
- PostgreSQL + Redis + 独立 DB service/worker IPC 的生产拓扑成本。
- 真实代理连接建立、TLS、连接池复用和上游首字节时间。
- 精确的 preflight 子阶段耗时；当前脚本只记录客户端 `fetch` 到 `response.text()` 完成的端到端 latency、CPU、事件循环和上下游计数。
- 本轮覆盖固定模型的普通 direct filter；未覆盖不同 `supportedModels` 基数、模型映射命中、不支持模型、fallback 和 model-aware reload 等边界分支。
- 多路由模式、多分组 fallback、失败重试和账户切换的额外耗时；本轮只覆盖普通路由、单分组、固定模型。

## 6. 测试异常与边界

- 同一次基线中 `/v1/models` 在连续高频请求下全部返回 `429 authenticated_models_rate_limited`，因此本报告不把该场景作为模型列表性能结论。模型列表应使用独立低频/关闭限流的专项测试。
- CPU profile 采集命令的 PowerShell 参数传递曾产生错误文件名；profile 未作为证据，最终报告只引用 JSON 端到端结果。
- 工作区在测试期间存在用户并发编辑，曾短暂出现 `provider-model-catalog.repository.ts` 的 esbuild 语法错误；只读核对后单次重试恢复，未修改或回退用户文件。
- 2 秒短压测只能用于定位方向，不足以给生产容量承诺；长尾受本机调度、GC、杀毒软件和 SQLite WAL 波动影响。
- 代码基线为 `a6278c505cbf2d8d3514ffaaa3310eb42bd2dff4`，测试时工作区有 `232` 个变更项，无法把结果视为该 commit 的干净构建；运行时为 Node `v22.19.0`，未记录 CPU/内存/电源模式。

## 7. PG + Redis 远端对照

已在 `192.168.1.203` 安装并验证独立 queue Redis：`juhe-ai-redis-queue`、宿主机 `6381 -> 6379`、AOF everysec、512MB、noeviction、`unless-stopped`。为避免改动共享库，另建临时 PostgreSQL 数据库 `juhe_ai_gateway_perf_20260720` 并按当前仓库 schema 初始化。

压测入口实际启动了 PG + Redis + DB service + mock upstream，但 1120/1120 请求均返回 `503 没有可用的上游账户`，mock upstream 请求数为 `0`，所以这不是成功容量结果。每个请求的 audit metadata 显示：`account_dispatch_candidate_window` 的 `candidateRowCount=0`、`eligibleRowCount=0`、`finalAccountCount=0`。同时 runtime log 发现 fresh schema 缺少 `juhe_business.model_catalog_snapshot_rebuild_requests`，queue Redis 新增 backlog `1620`、pending `512`。

该结果证明当前远端“代码 + fresh schema + worker/queue”组合还未达到可压测门禁，不能把 503 延迟或 backlog 当作网关性能瓶颈。需要先对齐完整当前 schema、模型目录重建表和 worker 消费拓扑，再重复 PG+Redis 测量。

## 8. 建议的下一轮定位

1. 增加 opt-in 的请求分段 timer（默认关闭），至少记录：入口解析、runtime/API Key、分组账户缓存、能力过滤、模型过滤、额度/容量、账户槽获取、上游首字节、响应完成、usage/audit enqueue；每段只记录耗时和计数，不记录 payload/凭据。
2. 在同一进程分别跑 8/64/256 账户、1/8/32 并发，固定上游 0ms，重复 5 轮并报告 median/p95，确认候选处理是否近似线性。
3. 对比“缓存命中”和“清空 gateway runtime cache 后首请求”，确认当前约十几毫秒是否主要来自稳态缓存。
4. 使用真实生产拓扑的 PostgreSQL/Redis/DB service/worker 做同一脚本的 persistence-ready 压测，再与 SQLite+memory 结果拆分比较。
5. 先补齐有限 supportedModels、直接/映射命中、不支持模型、多路由和多分组 fixture，再决定优化优先级；任何改动都要以分段 timer 和失败/回退回归共同验收。
