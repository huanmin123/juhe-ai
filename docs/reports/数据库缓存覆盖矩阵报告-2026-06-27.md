# 数据库缓存覆盖矩阵报告（2026-06-27）

## 1. 结论

- 目前不能说“凡是用到数据库和缓存的地方都已经测试过，更不能说都已经性能测试过”。
- 高性能核心链路已经有真实 PostgreSQL / Redis 验证：System API 压测、真实网关压测、网关事实写入 readiness、Redis Streams pending 恢复、PG / PgBouncer / Redis 重启和 PG 备份恢复。
- 本轮继续补齐：SQLite DB service fallback 回归、PG schema 增量字段同步、API Key 校验 / API Key 额度 / 授权额度 / 系统设置 / 网关模型目录 / 管理端模型目录 / 响应检查策略 Redis 共享缓存源码门禁、PG usage model / error / latency / account quality 派生统计 readiness、API Key / 直接授权 / 团队授权 quota snapshot readiness、PG 审计错误分组、审计读路径、操作日志读路径、公开接口日志读路径和运行日志读路径 readiness、审计日志和操作日志 Redis Streams 持久队列、PG 模式 DB service 网关热读并发 dispatch、真实网关 100 并发复测。
- 主要缺口仍在两类：大量 repository 仍是 SQLite 同步入口或仅有功能回归；生产缓存多数 `createAppCache` 调用点仍是进程内 LRU，API Key 校验 / API Key 额度 / 授权额度 / 系统设置 / 网关模型目录 / 管理端模型目录 / 响应检查策略已具备 Redis shared cache，但包含上游凭据的网关运行态、资源 lookup 等热点仍需分级迁移。

## 2. 范围

- 测试 / 分析对象：`backend/src/storage`、`backend/src/shared`、`backend/src/modules`、`backend/src/scripts/regression`、`backend/src/scripts/performance`。
- 覆盖链路：数据库 repository、网关事实写入、统计 / 日志 / 审计、Redis cache、Redis runtime state、Redis Streams、内存队列和本地 LRU 缓存。
- 不覆盖内容：本轮不做生产迁移演练，不承诺所有 repository / 查询 / 额度派生窗口均已 PG-ready。

| P0 | 多数 `createAppCache` 生产缓存仍为内存 LRU | API Key 校验 / API Key 额度 / 授权额度 / 系统设置 / 网关模型目录 / 管理端模型目录 / 响应检查策略已具备 Redis shared cache；包含上游凭据的网关运行态、资源 lookup 等仍主要靠本地 LRU 和失效广播，多实例命中率和容量收益有限 |
| P0 | 121 个 storage 文件仍命中 SQLite 同步访问痕迹 | PG 模式下未迁移入口可能 fail-fast，或仍未经过真实 PG 行为验证 |
| P1 | 统计展示窗口 / TopN 快照仍未全量压测 | usage model / error / latency、账号质量、quota snapshot、审计错误分组、操作日志读路径、公开接口日志读路径和运行日志读路径已补 PG readiness；概览窗口、排行窗口和长期刷新仍需继续压测 |
| P1 | public / runtime log 和 record maintenance 队列仍主要是本地队列 | audit 和 operation 已迁 Redis Streams；剩余日志和维护队列仍有重启丢缓冲或高峰内存压力风险，需按积压证据分批迁移 |
| P1 | 查询 / 搜索 / 筛选 explain 未形成全量门禁 | 已有 query guard 很多，但还不是所有热点列表和筛选都有 PG explain 或慢查询阈值门禁 |
| P2 | 非核心管理端 repository 的双 driver 回归缺口 | 单次功能可用不代表大数据量、复杂筛选和跨表事务可用 |

## 8. 建议顺序

1. 先不要盲目优化已经通过的网关主链路，继续补短板。
2. 建立 PG explain / query guard 清单，优先覆盖统计页、审计页、日志页、账号列表、授权列表、API Key 列表。
3. 把高价值 `createAppCache` 调用点分级：API Key 校验、额度、授权、系统设置、网关模型目录、管理端模型目录和响应检查策略已迁 Redis shared cache；下一步只评估不含凭据的网关运行态子集和资源 lookup，代理 agent、短期重试态继续留内存。
4. 继续迁移清理任务和未覆盖查询入口，迁移一个补一个真实 PG 回归或 readiness。
5. 本地队列先不要一次性全改 Redis Streams；audit 和 operation 已完成，下一步优先评估 record maintenance、public / runtime log 队列，按真实积压、重启丢失风险和幂等成本排序。
