# 数据库缓存覆盖矩阵报告（2026-06-27）

## 1. 结论

- 目前不能说“凡是用到数据库和缓存的地方都已经测试过，更不能说都已经性能测试过”。
- 高性能核心链路已经有真实 PostgreSQL / Redis 验证：System API 压测、真实网关压测、网关事实写入 readiness、Redis Streams pending 恢复、PG / PgBouncer / Redis 重启和 PG 备份恢复。
- 本轮补齐了真实 Redis cache / runtime state driver 回归：覆盖 `SharedJsonCache`、`RuntimeStateStore`、登录失败锁定和账号并发 Redis Lua。
- 主要缺口在两类：大量 repository 仍是 SQLite 同步入口或仅有功能回归；生产缓存 34 个 `createAppCache` 调用点仍是进程内 LRU，尚未迁移到 Redis shared cache。

## 2. 范围

- 测试 / 分析对象：`backend/src/storage`、`backend/src/shared`、`backend/src/modules`、`backend/src/scripts/regression`、`backend/src/scripts/performance`。
- 覆盖链路：数据库 repository、网关事实写入、统计 / 日志 / 审计、Redis cache、Redis runtime state、Redis Streams、内存队列和本地 LRU 缓存。
- 不覆盖内容：本轮不重新执行 100 并发重压测，不修改业务 repository 适配范围，不做生产迁移演练。

## 7. 高风险未覆盖项

| 优先级 | 缺口 | 风险 |
| --- | --- | --- |
| P0 | 34 个 `createAppCache` 生产缓存仍为内存 LRU | 多实例下不是共享缓存，只能靠跨进程失效降低脏读风险，无法承担 Redis cache 的容量和命中率价值 |
| P0 | 121 个 storage 文件仍命中 SQLite 同步访问痕迹 | PG 模式下未迁移入口可能 fail-fast，或仍未经过真实 PG 行为验证 |
| P0 | 派生统计窗口未完整 PG-ready | 慢查询通常来自最慢的统计 / 筛选 / 聚合入口，不能只看网关最快路径 |
| P1 | 审计错误分组、usage model/error/latency、账号质量、额度小时窗口、quota snapshot | 会影响统计页、额度判断和后台聚合延迟 |
| P1 | audit / operation / public / runtime log 队列仍主要是本地队列 | 重启丢缓冲和高峰内存压力仍存在，暂未像 usage 一样具备 Redis Stream 恢复能力 |
| P1 | 查询 / 搜索 / 筛选 explain 未形成全量门禁 | 已有 query guard 很多，但还不是所有热点列表和筛选都有 PG explain 或慢查询阈值门禁 |
| P2 | 非核心管理端 repository 的双 driver 回归缺口 | 单次功能可用不代表大数据量、复杂筛选和跨表事务可用 |

## 8. 建议顺序

1. 先不要盲目优化已经通过的网关主链路，继续补短板。
2. 建立 PG explain / query guard 清单，优先覆盖统计页、审计页、日志页、账号列表、授权列表、API Key 列表。
3. 把高价值 `createAppCache` 调用点分级：网关运行态、额度、授权、系统设置优先；代理 agent、短期重试态继续留内存。
4. 继续迁移派生统计窗口和清理任务，迁移一个补一个真实 PG 回归或 readiness。
5. 本地队列先不要一次性全改 Redis Streams；优先评估 audit 和 record maintenance，它们对数据安全和内存压力更敏感。
