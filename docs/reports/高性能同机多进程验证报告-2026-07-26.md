# 高性能同机多进程验证报告（2026-07-26）

## 验证目标

本轮验证针对 `performance` 模式的同机多进程最小单元，重点确认 Usage / Log
多副本不是只完成配置和进程启动，而是能够真实连接隔离 Redis Stream、写入
PostgreSQL，并在单个 consumer 退出后完成 pending 接管。standalone、Nginx 摘流和
生产 Mac 切换分别使用其他回归或后续生产演练验证。

## 环境与安全边界

- 执行端：Windows 工作区，Node.js 22，当前未提交工作树。
- 依赖端：用户授权的测试 PostgreSQL、PgBouncer 和三角色 Redis 容器。
- 凭据只在测试进程内从授权文件和运行中容器读取，没有写入源码、文档、报告或原始产物。
- Redis 使用 `codex-worker-replicas-*` / `codex-runtime-log-*` 独立 namespace；数据库行使用
  本轮唯一 marker，脚本在 `finally` 中按精确 ID 清理。
- 本轮未停止或修改测试中间件服务，也未执行生产流量、付费上游请求或生产 Nginx 切换。

## 执行与结果

### Usage / Log 多副本及接管

入口：

```powershell
pnpm --filter juhe-ai-backend test:performance-worker-replicas-live-smoke
```

运行时显式启用 live-smoke 守卫、隔离 namespace，并将
`JUHE_AI_REDIS_STREAM_CLAIM_IDLE_MS` 设为 `1000`。结果：

- 2 个 Usage Worker 与 2 个 Log Worker 都在各自 consumer group 注册。
- queue fence 生效时，usage 先写入本地 durable spool；解除 fence 后成功重放 1 条。
- 共写入 4 条 usage 与 4 条 public API log；数据库主键数量精确等于稳定事件 ID 数量。
- 停止 1 个 Usage Worker 和 1 个 Log Worker 后，剩余副本继续消费新消息。
- 4 个 worker 分别以 `usage-worker:1/2`、`log-worker:1/2` 注册独立事件循环与内存样本；
  Stats 注册表读取能够返回全部四个角色，测试结束后 key 按隔离 namespace 清理。
- 被停止 Usage Worker 处于“PostgreSQL 已提交、Redis 尚未 ACK”的记录在 claim idle 后由
  另一副本接管；重复提交成为幂等 no-op，Stream 最终 `length=0`、`pending=0`。
- 命令退出码为 `0`，测试行、Stream key、fence 和临时 spool 均由脚本清理。

默认生产 claim idle 仍为 60 秒，用于避免正常长批次被过早重复认领；1 秒只用于缩短故障
接管测试。该结果证明接管语义和幂等边界，不代表生产新鲜度必须配置成 1 秒。

### Runtime Log 文件落库

入口：

```powershell
pnpm --filter juhe-ai-backend test:runtime-log-postgres-consumer-smoke
```

结果：单个隔离 JSONL 文件的 1000 行全部写入 PostgreSQL，文件 cursor 追平末尾，
`truncation_generation=0`，且没有创建已经移除的 runtime-log Redis Stream。测试行、cursor
和临时日志目录已清理。

### PostgreSQL 事务单连接安全

入口：

```powershell
pnpm --filter juhe-ai-backend test:database-client
pnpm --filter juhe-ai-backend test:postgres-query-transaction-boundary
```

结果：普通 pool query 仍可并发；显式事务借出的单连接即使被 repository helper 通过
`Promise.all` 或嵌套 transaction 同时调用，也只保持一个 active query，并在尾部查询完成后
才提交。连接在事务空闲期由服务端终止时，异步 `error` 会拒绝事务、带 error 释放坏连接，
不会升级为进程 uncaught exception。该门禁覆盖了生产旧日志中同一 DB service PID 出现的
node-postgres 并发 query warning、`idle-in-transaction timeout` 与退出链；日志本身不能证明
并发 query 是服务端 timeout 的唯一原因。

### 生产 Mac 只读预检

- 当前 release、主应用 `3001`、DB service `3002`、Nginx `3099` 以及既有三 worker 均健康，
  `3101/3102` 没有临时候选监听；磁盘和内存没有当前容量告警。
- 旧日志保留多次 runtime-log Redis timeout、DB service `idle-in-transaction timeout`、server
  IPC `EPIPE` 证据，和本次修复边界一致。
- 生产 `ops/` 仍保留两份旧发布 marker；2026-07-22 的后续成功发布证据已经明确登记为
  `historical ... recorded-and-closed`。当前 deployment lock / final verify 只阻断 `redis/`
  未闭合 marker，本轮未发现该类 Redis marker 或远端部署锁，因此这些历史文件不是当前
  发布阻断项，也不应在没有删除授权时擅自清理。

### main / temporary 双槽发布门禁

- macOS operations 回归已通过 Bash 真实调用渲染器分别生成 main 与 temporary 完整 Nginx
  主配置，而不是只检查源码字符串。main 精确包含 `3200/3211-3213`，temporary 精确包含
  `3300/3311-3313`，两份配置均监听 3099、带活动槽身份且不存在跨槽端口混入。
- 安装器发现目标槽已有 plist/run script 时，会先调用只读排空脚本；活动槽身份相同、
  安装不完整或仍有 Nginx established connection 都会拒绝覆盖。
- 退役脚本同样要求槽位已摘流且排空，只把 plist/run script 移入可恢复目录，不删除
  release、日志或共享 usage spool。
- 本地已覆盖 Bash 语法、参数负例、生成配置结构与回滚 contract。目标 Mac 的真实
  `nginx -t`、launchctl 双槽启动、graceful reload 与长流排空仍须在部署计划锁内完成动态预演。

### 隔离 Linux 10 分钟正式混合验收

最终发布候选部署到独立 Linux 验收根目录，使用独立 PostgreSQL 数据库、独立 Redis
namespace、独立审计 blob 根目录和未占用端口。既有测试实例与生产 Mac 均未停止、复用或
修改。运行拓扑为 1 Control、3 Gateway、4 DB service、2 Usage、2 Log、1 Stats、1 Ops；
资源采集在 709 秒内取得 142 个样本，每个样本都包含全部 14 个角色，三个 Gateway 的入口
请求计数均有持续正增量。

正式入口：

```powershell
pnpm --filter juhe-ai-backend test:performance-10m-acceptance
```

正式参数为 64 并发、600 秒 load、0 秒 warmup、60 秒 settle；同时覆盖普通 Responses、
Chat、Responses SSE，5K / 500K / 2M / 4M 历史请求体分布，确定性高熵 payload，以及
3–30 秒随机慢 SSE。独立控制面探针每 500ms 采样 5 个健康目标和 5 个管理接口，不与发压
或 mock upstream 共用事件循环。

结果：

- 正式请求 `6804/6804` 成功，错误率 `0`，成功 QPS `10.85`。
- Responses P95/P99/Max 为 `133.20/190.41/416.43ms`；Chat 为
  `124.20/241.81/393.11ms`。
- SSE `2288/2288` 终态和 TTFB 样本完整；TTFB P99 `262.78ms`、Max `394.44ms`，
  完整流最大约 `30.16s`，符合 3–30 秒慢流口径。
- 5K、500K、2M、4M 四档分别获得 `6123/545/102/34` 个样本，全部零错误。
- 健康探针 `6900/6900` 成功；Control 两个健康入口和三个 Gateway 直连健康的最大耗时分别为
  `31.69/17.81/15.36/18.90/22.31ms`，显著低于 `500ms` 门禁。
- 管理探针 `6900/6900` 成功；usage、统计概览、账户、审计、运行日志最大耗时分别为
  `79.20/78.96/80.83/70.66/64.43ms`，未被慢 SSE 长连接拖死。
- usage 与 audit 各 `6804` 条精确对账；settle 后 usage、audit、operation、public API、
  record maintenance 五类 Stream 均为 `length=0/pending=0/lag=0/backlog=0`。
- PostgreSQL deadlock 增量 `0`、未授予锁 `0`、未知锁等待 `0`；只观察到一次
  `2.25ms` 的 audit blob `ON CONFLICT` 短暂协调等待，单次采样且低于 `1500ms` 门禁。
- 清理前先停用测试账户和分组，再等待在途健康检查完成；退出后测试账户、分组、API Key、
  路由策略、最终 trace usage/audit/index 均为 `0`。
- 审计完整性复核覆盖 `54,409` 个 blob 元数据与同数文件、`89,988` 条引用：缺文件、尺寸
  不一致、悬空日志引用、悬空 blob 引用、5 分钟以上无引用元数据和孤儿文件均为 `0`。
  `audit_payload_refs` 是引用事实源，兼容字段 `ref_count` 固定为 `0`。
- 正式运行日志未发现 deadlock、uncaught、unhandled、fatal、panic 或最终 mock upstream
  关闭后的 `ECONNREFUSED`；验收后 5 个健康端点仍为 HTTP `200`，14 个角色仍存活。

## 暴露的问题与判断

- 初次联调按容器缺省值推断数据库名，命中了不存在的数据库；改为读取实际业务库后通过。
  正式部署必须显式配置完整 PostgreSQL URL，不能依赖镜像缺省数据库名。
- 故障 worker 在数据库提交后、ACK 前退出时，消息会保持 pending 到 claim idle；这是
  Redis Stream at-least-once 的正常恢复窗口，不是消费堵死或数据丢失。
- 前序检查曾发现测试依赖的 state / queue 凭据与运行容器漂移，且 state Redis 开启 AOF，
  与项目角色基线不一致；最新增强 smoke 使用授权文件中的 cache / queue 入口已连接成功，
  但这不等于 state 角色策略重新验收通过。角色策略 smoke 仍不能通过放宽断言掩盖基础设施
  配置问题。
- 当前工作树的模型价格 schema 已包含测试 PostgreSQL 尚未迁移的字段，usage 成本补算出现
  `42703` 后按既有降级保留原始用量，核心 4 条 usage 仍准确落库。这是发布源与 schema
  基线不一致的直接证据：不能把当前 master 工作树整体覆盖到生产旧 release，必须使用
  基于生产 commit 的隔离 hotfix，或先单独完成全量 schema 迁移验收。

## 结论与未覆盖项

真实依赖和最终 10 分钟证据已经证明：Usage / Log 多副本能够并行消费并接管 pending，
Redis 入队失败期间的 usage 能由本机 spool 幂等补写；3 个 Gateway 在普通请求、大请求体和
慢 SSE 混合压力下持续分流，Control 健康与管理读取保持低延迟，队列、数据库和审计文件在
settle/cleanup 后没有当前夹具残留。该工作树可作为安全、可回滚的生产发布候选。

仍未由本报告证明：生产 Mac 上 main/temporary 双槽的真实 `nginx -t`、launchctl 启停、
graceful reload、旧槽长流排空、生产 Redis/DB service 故障注入和完整回滚。以上操作必须在
用户明确“确认上线”后按外部上线计划执行；本轮没有修改生产 Mac，不能把候选验收写成生产
切换完成。
