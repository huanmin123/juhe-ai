# 高性能模式压测报告（2026-06-28）

## 1. 结论

- 本轮按“集中修代码，最后统一测试”的节奏收口，最新 PostgreSQL / Redis 高性能模式回归和压测均通过。
- System API 100 并发 30 秒压测通过：15078 请求全成功，错误率 0，p95 466ms，p99 568.72ms。
- 网关 128 并发 30 秒压测通过：19360 请求全成功，成功 QPS 415.7，错误率 0，p95 242.91ms，p99 302.78ms。
- PostgreSQL 未观察到死锁；压测后无残留等待锁、无残留长事务。System API 有一次瞬时 waiter 采样，但 `maxNotGrantedLocks=0`、`maxActiveQuerySeconds=0.02`，压测结束后实时检查等待锁为 0。
- Redis Streams 本轮采用“本次压测正向增量”判断积压，避免历史 pending / backlog 污染结论。网关压测期间新增正向 pending = 0，新增正向 backlog = 0，历史 backlog 净减少 828。
- 当前不建议继续盲目调主链路。后续优化应只围绕真实慢项继续：异步 operation log 搜索词写入、特定管理端复杂筛选、长周期 stats worker 和生产规格环境复测。

## 2. 范围

- 测试 / 分析对象：PostgreSQL schema / 索引、Redis shared cache、Redis runtime state、Redis Streams、System API、真实网关链路、usage / audit / operation / public logs、统计聚合和额度快照。
- 覆盖链路：本地 SQLite / memory 回归、远端 PostgreSQL / Redis smoke、System API 压测、网关压测、PG 锁 / 事务采样、Redis Stream backlog 采样。
- 不覆盖内容：生产真实规格机器容量、SQLite -> PostgreSQL 真实数据迁移演练、真实 OpenAI OAuth token endpoint、真实外部代理网络质量和应用容器 performance 模式整体验收。

## 7. 观察

- “加了 PG + Redis 仍慢”的主要原因不是数据库全局锁，而是查询计划、collation、异步事实写入和 DB service 并发边界。当前已用真实 PG explain 固定 usage / API Key / account 等热点列表不走错误索引。
- System API 管理端写请求仍会受同一账号行锁和业务更新范围影响，不能简单把所有 PATCH 无限并发。当前 100 并发下通过，且没有形成长期阻塞。
- 网关链路已经比 System API 更稳，p95 约 243ms，当前请求路径没有明显 PG 慢查询；异步 operation log 搜索词批量写入是后台慢项，但没有在本轮造成 Redis Stream 新增积压。
- 网关压测采样到一次 `maxXactAgeSeconds=10.79` 的事务年龄窗口，但同时无 lock waiters、无 not-granted locks、active query 最高 0.4s，压测后实时 PG 检查无残留事务。该现象先记录为观测项，不作为当前阻塞结论。

## 8. 边界

- 本轮报告证明当前测试栈、当前脚本参数和当前代码路径可承载 100 并发 System API 与 128 并发网关压测；新增迁移脚本源码门禁只证明离线迁移入口具备基础安全边界，不能替代真实生产数据迁移演练。
- 历史 Redis Stream pending / backlog 仍需要生产切换前清理或确认；本轮只证明新增压测没有制造新的 backlog。
- 生产上线前仍建议保留 `pg_stat_statements`、Redis Stream backlog、deadlocks、lock waiters、idle in transaction、long transaction、queue failure count 的监控。
