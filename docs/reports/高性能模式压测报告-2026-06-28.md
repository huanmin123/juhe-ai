# 高性能模式压测报告（2026-06-28）

## 1. 结论

- 本轮按“集中修代码，最后统一测试”的节奏收口，最新 PostgreSQL / Redis 高性能模式回归和压测均通过。
- System API 50 并发 30 秒补测通过：17188 请求全成功，错误率 0，QPS 410.33，p95 214.8ms，p99 305.01ms。
- 网关 64 并发 30 秒补测通过：14932 请求全成功，成功 QPS 359.73，错误率 0，p95 161.98ms，p99 261.71ms。
- PostgreSQL 未观察到死锁；System API `maxXactAgeSeconds=0.15`，网关 `maxLockWaiters=0`、`maxActiveQuerySeconds=0.29`。网关采样到周期性 `maxXactAgeSeconds=9.78`，但无 lock waiters / not-granted locks，先作为观察项。
- Redis Streams 本轮采用“本次压测正向增量”判断积压，避免历史 pending / backlog 污染结论。网关压测期间新增正向 pending = 0，新增正向 backlog = 0，历史 backlog 净减少 800。
- 当前不建议继续盲目调主链路。后续优化应只围绕真实慢项继续：异步 operation log 搜索词写入、特定管理端复杂筛选、长周期 stats worker 和生产规格环境复测。

## 7. 观察

- “加了 PG + Redis 仍慢”的主要原因不是数据库全局锁，而是查询计划、collation、异步事实写入和 DB service 并发边界。当前已用真实 PG explain 固定 usage / API Key / account 等热点列表不走错误索引。
- System API 管理端写请求仍会受同一账号行锁和业务更新范围影响，不能简单把所有 PATCH 无限并发。当前 50 并发下通过，且没有形成长期阻塞。
- 网关链路在 64 并发、50ms mock upstream 下 p95 约 162ms，当前请求路径没有明显 PG 慢查询；异步 operation log 搜索词批量写入仍是后台慢项，但没有在本轮造成 Redis Stream 新增积压。
- 网关压测采样到周期性 `maxXactAgeSeconds=9.78` 的事务年龄窗口，但同时无 lock waiters、无 not-granted locks、active query 最高 0.29s。该现象先记录为观察项，不作为当前阻塞结论；若生产看到超过 30s 或伴随锁等待，再单独优化事务边界。

## 8. 边界

- 本轮报告证明当前测试栈、当前脚本参数和当前代码路径可承载 50 并发 System API 与 64 并发网关压测；历史数据保留 / 导入不在本轮报告覆盖范围内。
- 历史 Redis Stream pending / backlog 仍需要生产切换前清理或确认；本轮只证明新增压测没有制造新的 backlog。
- 生产上线前仍建议保留 `pg_stat_statements`、Redis Stream backlog、deadlocks、lock waiters、idle in transaction、long transaction、queue failure count 的监控。
