# 后端架构与性能现状评估（2026-09-18）

> 面向 AI 与维护者。
> 本文是 Go 后端从 Node 迁移收尾后的第一轮架构与性能系统性现状评估，为后续改革计划（见 `docs/plans/` 对应 PLAN 文档）提供证据基线。
> 方法：`go list` / `rg` / `wc -l` 量化扫描 + 覆盖率账本（`go test -cover` 口径）+ 本轮覆盖率攻坚中积累的第一手实现观察。
> 所有数字为 2026-09-18 工作区实测，复核命令见文末附录。

## 1. 范围

- 对象：`backend-go/` 五模块（gateway / jobs / maintenance / shared/platform / shared/contracts）生产代码与测试代码。
- 维度：模块边界与体量、大文件与超限、包级职责（god 包）、跨包重复（复用性）、扇入耦合（扩展性）、时钟与并发模式（可测性与性能）、热路径（性能）。
- 不含前端（前端测试体系已另有 PLAN 收口）。

### 2.4 跨包重复（复用性证据）

| 重复项 | 分布 | 说明 |
| --- | --- | --- |
| `newID`（crypto/rand ID 生成） | 8 个包 | 各自实现 rand + fallback |
| `Clock`/`FixedClock` 接口 | ~10 个包 | 各自定义同名接口与注入设施，签名不一致 |
| `sanitizeRedisName` | 4 个包 | Redis 命名清洗重复实现 |
| `passiveJitterWindowMS` | 3 个包 | 节拍抖动窗口逻辑复制 |
| `parseInstant`/RFC3339 毫秒 | 3+ 个包 | 时间解析/格式化各写各的 |
| `?`→`$n` 占位符改写 | 3 处实现 | taskruns `bind()`、circuitstore `bind.go`、statsagg `dialect.go`（另有多处局部 instantParam/boolLit 方言分支） |

迁移期"每包自包含"的约定在收尾后变成了持续的重复税：同一语义（时钟、ID、命名清洗、方言占位符）有 N 份实现，行为细节已经出现漂移（如 Clock 接口签名不一致）。

`gatewayruntimecache` 被 231 处引用：运行态缓存结构是整个网关的耦合中心，任何缓存模型调整（字段、失效、并发语义）的波及面覆盖几乎所有 gateway 包。`gatewaypreauth`（198）同时被缓存、调度、公开面引用，职责边界（可用性/重试预算/预算调度）在包内有膨胀迹象。

## 3. 架构评估

### 3.1 已建立的优势（改革必须保持的基线）

1. **三项目 + go.work 边界清晰**：gateway/jobs/maintenance 互相禁止 import，shared 只放 contracts 与无业务 platform。
2. **Store Port / Adapter 收口**：业务规则统一经 Store 端口，SQLite/PG 双模式在装配层选择。
3. **供应商驱动五层模型**：协议/端点族/能力矩阵/供应商/协议档案有明确文档与白名单桥接边界。
4. **owner lease 与单 writer 边界**：各专用事实库由唯一 owner 持有。
5. **覆盖率与测试分层**：语句覆盖率 ~95% 目标已建立，后端测试分层规则成文。

### 3.2 风险清单

| 编号 | 风险 | 证据 | 影响 | 等级 |
| --- | --- | --- | --- | --- |
| A1 | 基础设施 helper 跨包重复且行为漂移 | 2.4 节 7 类重复 | 新供应商/新功能接入时复制面继续扩大；同名不同义 helper 造成隐性缺陷（本轮已实证：Clock 签名漂移、占位符 3 处实现） | P0 |
| A2 | 缓存架构成为耦合中心 | gatewayruntimecache 扇入 231 | 缓存模型演进（多节点分片、命中率优化）波及面失控 | P0 |
| A3 | god 包边界过宽 | accounts 29.8k 等 11 个逻辑包（见 2.3 注 1 的 business 反例） | 子域耦合在同一包内积累，改动半径持续扩大 | P1 |
| A4 | 4 个逻辑文件超 2000 预警线 + 2 个 DDL 数据文件超 3000 硬上限 | 2.2 节（复审修正：逻辑文件未超硬上限，属可维护性改进） | 预警线超标预示职责可再切分；DDL 数据文件超硬上限需按 schema 组拆分 | P2 |
| A5 | 时钟注入不统一，热路径退避用真实时间 | ~10 包自定义 Clock；cmd 包链路测试 559s（重试退避真实 sleep） | 可测性与测试时长恶化；重试节奏无法在测试中确定性验证 | P1 |
| A6 | 热路径 JSON 编解码密度高 | chat 61 处、accounts 47 处 json.Marshal/Unmarshal | 每请求多次编解码的分配压力，需量化基准后判定是否优化 | P2 |

### 3.3 判断（事实与推断分开）

- 事实：上述数字全部来自当前工作区实测。
- 推断：A1/A2 是"几十万行持续扩展"的最大结构性隐患——重复税随每个新功能线性增长，缓存耦合随每个新接入包线性增长；两者不先收口，后续所有优化都会被放大波及面。
- 未验证：热路径 JSON 的实际 CPU/分配占比（需 pprof 基准后判定，见 R5）；A2 的实际演进成本（需一次真实缓存改动的事后对照）。

## 4. 性能评估

1. **请求热路径**：网关链（dispatch → response → usage → cache）每请求经过多次 JSON 编解码与结构体转换；模型目录/运行态已有进程内 + Redis 两级缓存，命中率是关键变量但当前无量化基准。
2. **DB 访问**：SQLite（WAL、短事务、busy_timeout）与 PG（连接池、事务）双模式；占位符改写收敛后两模式 SQL 一致性已建立。pgpool 集中管理连接池。
3. **重试退避**：dispatch 的 recoverable-wait 用真实时钟 3s 退避（生产契约正确），但无注入点——测试只能真实睡眠，且节奏无法确定性断言。
4. **大文件读取**：架构已有 offset/cursor/stream 硬底线（架构总览成文），本轮覆盖率攻坚中未见违反。
5. **测试基础设施性能**：gateway cmd 包测试 559s（默认 10m 超时仅 40s 余量），主因是链路测试真实退避——时钟注入后预计可缩短一半以上，同时消除测试时长 flake。

## 5. 改革方向（供改革 PLAN 引用）

| 编号 | 方向 | 目标 | 对应风险 |
| --- | --- | --- | --- |
| R1 | **shared/platform 基础设施收敛**：统一 ID 生成、Clock/FixedClock、jitter、RFC3339 毫秒、`?`→`$n` 方言占位符改写、Redis 命名清洗、JSON 编码 helper 到 shared/platform，各包改为引用 | 消除 7 类重复，行为统一签名 | A1 |
| R2 | **缓存与 preauth 扇入治理**：gatewayruntimecache 按读/写/失效/并发语义拆分对外接口面；gatewaypreauth 职责边界复查 | 降低缓存演进波及面 | A2 |
| R3 | **god 包与超限文件拆分**：accounts 按子域（CRUD/导入导出/批量/测试会话/余额/时间计划）评估包级拆分；4 个预警线超标逻辑文件按大文件重构指南评估拆分；2 个超硬上限 DDL 数据文件按 schema 组拆分 | 缩小改动半径，DDL 数据文件恢复指南合格状态 | A3/A4 |
| R4 | **时钟注入统一与热路径确定性**：Clock 收敛到 shared/platform 后，dispatch 退避与链路测试注入注入点；cmd 包测试时长目标 <300s | 可测性 + 测试时长减半 | A5 |
| R5 | **热路径性能基准先行**：对 /v1 网关链与 chat 建立 pprof/bench 基准，量化 JSON 编解码与分配占比后再决定优化项 | 避免未证实的过早优化 | A6 |

### 执行约束（全部改革波次遵守）

1. 行为基线不变：对外 API、路由、字段、页面流程以当前系统模型为准。
2. 覆盖率不降：每波交付后受影响包 `go test -cover` 仍 ≥95%（未达标包沿既有缺口清单收口）。
3. 一次只拆一个清晰边界，不混入新功能（大文件重构指南）。
4. 波次并行时按最小非重叠写入范围分工（orchestrate-model-workflow）。
5. 生产缺陷随改随修，不登记不改。
