# 信封差异与慢查询处置复核报告（2026-10-11）

## 1. 结论与交付状态

本轮完成本地源码、设计和已有问题记录的复核，提出可审阅的处置方案；未修改业务代码、未访问生产、未执行 DDL、回填、数据清理或部署。以下“推荐”均是待采纳方案，不代表已经裁决或实施。

原汇报需要修正三点：

1. F2/F3/F4 尚未把最终请求构造全部接入 `upstreamenvelope.Build`。已共享的是部分 URL、Accept、认证或预算规则；调用方仍自行编码 body、包装适配器和创建 `http.Request`。只处理八处差异，不能完成“系统探针唯一构造源”的验收。
2. Codex 差异并非简单的“有无 metadata”。F2/F4 的 `codex_responses` 兼容路径会添加 `client_metadata`、`prompt_cache_key`、`include`、`reasoning.context` 等；F3 的 OAuth Codex 归一化另有规则。兼容画像与 OAuth 适配器是不同维度，必须按相同账户形态比较。
3. 慢 UPDATE 对应成功成本历史回填，而非正常分钟聚合缺少键索引。默认 30 天保留和 1 小时表监控采样已经存在；仍需处理概览读取及生产执行事实，不能据此关闭慢查询观察项。

推荐顺序：先治理反复全表回填，并保住历史扣减后成本补正的语义；并行补齐信封目标契约与真实接线；表监控先核验索引和执行计划、改窄列取最新 ID 后回表，不先改变保留期或引入预聚合。

### 3.3 推荐实施契约与验收

先在权威信封设计与相关端点/账户文档记录最终矩阵，再改代码。迁移只保留调用方的探针内容、账户选择、transport、超时、重试、评分、结算；最终 method、URL、标准/认证头、body 编码、预算字段和适配器包装统一经 `Build`。

身份作为每次请求的显式输入，由同一份身份值产生 body `client_metadata` 与相关 headers；不让两个构造阶段各随机生成一份。适配器和画像只声明不同协议语义，不能重新开一条私有最终构造路径；也不新增 feature flag。

验收必须捕获实际发送给本地 Mock transport 的请求：在相同目标、模式、适配器、画像、身份输入下，对 F2/F3/F4 比较结构化 body、URL/query 与头。提示词和探针检测内容可不同，必须明确比较字段范围。另覆盖 OAuth Codex、API Key Codex 画像、普通 API Key、Code Assist、Interactions JSON/SSE、GLM 三种 base、multipart、预算例外与错误路径。保留原始错误，不靠 fallback 消除差异。

完成标准还包括生产调用图确实到达 `Build`，且旧的最终请求构造/适配器包装实现退出；共享包单测全绿不足以替代这一门禁。F1 `/v1` 用户请求不在本设计范围内，完成后只能称“系统生成探针共用构造源”。

## 4. 分钟用量慢 UPDATE

### 4.1 已确认的来源

BUG-0307 记录的是 `UPDATE usage_stats_minute SET success_cost_usd...`，max 234 秒、5 次调用。与其匹配的本地 SQL 在 `backend-go/projects/maintenance/internal/schema/pg_schema_stats.go:2187`：

```sql
UPDATE usage_stats_minute
SET success_cost_usd = total_cost_usd
WHERE error_count = 0 AND success_cost_usd <> total_cost_usd
```

`EnsurePostgres` 在 `pg_schema.go:119` 起遍历全部 statements，没有针对该历史回填的完成标记。因此“数据已经相等时重复执行不改值”成立，但“重复执行没有扫描成本”不成立。相同回填覆盖 totals、minute、hourly、daily、weekly、monthly 六表；SQLite `ensureSQLiteStatsSuccessCostColumns` 也每次执行同一谓词。

正常 jobs 聚合在 `statsagg/upserts.go:148` 起使用主键上的 `INSERT ... ON CONFLICT ... DO UPDATE`。PG minute 表已有四列主键以及同键复合索引和 `stat_minute` 索引（`pg_schema_stats.go:207,1588,1593`）。这些索引无法直接解决上述非时间谓词的回填扫描；本轮未取得生产计划，扫描、锁等待、IO 各自占比尚不能量化。

### 4.2 推荐方案

推荐把历史回填与后续运行中的补正责任分开：历史回填默认执行一次、可恢复；运行中的变化只处理受影响行。两者一起设计和交付，不能单独增加完成标记后就删掉重复回填：

1. 对当前已满足谓词的历史行，保留既有值转换：只对 `error_count = 0` 的不相等行复制 `total_cost_usd`；混合成功/失败历史行不得臆算成功成本。这不等同已经证明一次性迁移保留所有时序行为，扣减交互见下文。
2. 使用数据库内持久完成记录，按迁移/表记录完成状态；完成后再次 `ensure-schema` 只查记录，不触碰六张事实表。不能仅以“列已经存在”判定回填完成，也不能使用进程内 Bool，因为部署会重启 maintenance。
3. 首次回填沿既有主键按稳定游标分短批；批内 cursor 与修改原子提交，失败保留原始错误，重跑从安全位置继续。避免只加 `LIMIT` 但每批仍从头扫描。
4. 新库、旧库、已有列但回填中断、已回填但没有新完成记录都必须有明确承接规则；旧已回填库最多再做一次有界核对后记录完成，不要求用户手工宣告成功。
5. 并发聚合时，不从批前读取的旧 `total_cost_usd` 写回；更新应在 SQL 里使用行锁后的当前值，并重新判定谓词。不能用跳过锁行却推进游标/完成标记的方式丢掉待迁移行。双 migration runner 必须串行收敛；短批减少单次事务时长，但不自动证明并发迁移安全。

**首次迁移还需写者协调**：未处理的历史行可能先被新失败聚合从 `error_count=0` 改成混合行，随后回填不再命中原谓词；只在 UPDATE 时重判谓词不能保住此前符合条件的历史成功成本。实施契约必须明确迁移与统计聚合/扣减写者的协调边界，例如受控维护窗口暂停相关写者，或在写路径处理旧行后再追加增量，并证明失败重跑和跨批期间不漏补。二者的运行影响不同，须在实施前选择；本报告不授权暂停生产，也不引入 feature flag。当前推荐仍是评估完整迁移与运行补正方案，不能把“批量 UPDATE + marker”直接视为已定实现。

**必须一并裁决的扣减交互**：`backend-go/projects/jobs/internal/cleanuprepo/statssubtract.go:284-343,358-389` 分别扣减 `error_count`、总成本和成功成本；删除失败记录不会扣成功成本。历史混合行可能从 `(error_count=1,total_cost=10,success_cost=0)` 变为 `(0,8,0)`；当前下次 Ensure 会补为 `(0,8,8)`，单纯完成标记则会永远留下 0。推荐在扣减链路中，针对同一事务内本次确实受影响的六表行，以扣减后的值应用等价谓词补正，不扫描整表。但补正从“下次初始化”提前到“扣减事务”改变了可见时点，须在统计/配额权威文档裁决后实施，并测试正常新聚合、历史混合行、失败记录删除、重试扣减和并发写入。不能仅由 schema 执行者自行补全。

增加精确谓词的永久部分索引可作为保留现有补正时点的替代方案；需用同一 UPDATE 的计划证明有效，并测正常聚合的索引维护成本。它仍保留部署重复回填职责，因此不是完整根治的首选；若暂不采纳扣减语义调整，应先评估此方案，不能删掉迟到补正能力。首次迁移及运行补正需要比“几行 DDL”更完整的设计，应在实施前明确范围与验收边界。

验收：新库不做无意义全扫；旧库关键成本口径不变；扣减后迟到符合谓词的行按已裁决时点得到补正；中断/失败重跑不丢行；第二次执行不再扫描六表；并发聚合不丢增量；PG/SQLite 两路径均有确定性测试，PG 的锁与性能行为再用隔离 scratch 实测。涉及初始化序列或部署契约变化时，同次同步 `docs/deploy/部署指南.md`、`docker/single-server/README.md`、`docs/deploy/linux/README.md`，成本补正同步统计与配额权威文档。

## 5. 表监控慢概览

### 5.1 已有策略与实际缺口

[表数据监控设计](../functions/表数据监控设计.md) 与 [采样粒度计划](../plans/计划-20261008T203741000Z-表监控采样粒度根治.md) 已明确默认 30 天保留、1 小时采样。无需重新裁决 90 天，也不因策略存在就认定生产旧历史已清理、磁盘已释放或概览已变快。

gateway `tablemonitor/store.go:263` 起的 PG 概览，数据库摘要使用 DISTINCT ON，表总数使用 GROUP BY，表列表以宽字段 DISTINCT ON 筛出各表最新快照，再按容量排序分页。当前不是“每次只读取一页对应的历史行”。

jobs `tablemonitor/store.go:762-764` 定义了最新快照所需的索引。但 `postgresSchemaExists`（同文件 :151）只检查三张表存在；表存在时 `ensurePostgresSchema` 直接返回，不核验索引。这是可证实的 schema 预检缺口；它不能证明生产恰好缺索引，却说明仅看 DDL 常量不能宣称生产索引齐全。

BUG-0307 的 2.2GB 是历史记录中的表容量指标。本轮没有复核 heap/index/TOAST、活行/死行及膨胀组成，不能简单用容量除行数得出“每行实际 payload 约 7KB”，也不能仅据累计耗时定量认定它放大了锁风暴。

### 5.2 推荐顺序

1. 核对目标索引的定义、有效状态、统计信息，以及快照采样/retention 执行情况。预检应验证需要的索引，缺项只在受控初始化/维护阶段补齐，不能在每次租约续约或概览请求里反复 DDL。
2. 在隔离 PostgreSQL 以接近观察项的历史量重放原概览 SELECT，保存计划和 buffer/耗时基线。UPDATE 的分析不能当只读操作在生产执行 `EXPLAIN ANALYZE`；需要真实执行的验证放 scratch。
3. 尝试把“筛选各表最新快照”改为只取 key/ID，再回表读取这些最新行；数据库摘要可用同类窄读取方式。保持搜索、总数、按容量排序、分页、NULL 排序与采样缺失的既有语义。现有最新索引可能用于减少历史宽行读取，但是否能 index-only scan、实际性能是否改善必须由计划证明。
4. 不用扩大缓存窗口、缩短 retention 或应急删历史掩盖查询问题。若索引齐全和窄读取后仍随着历史量退化，再评估由采样 owner 维护最新状态投影；这会增加写入/迁移/保留语义，届时再设计，不先引入预聚合。

验收：大历史量与空库的概览结果一致；相同采样时间的 ID tie-break、关键词、分页和 NULL 都不回归；无缓存/手动刷新的真实读取改善；retention 不破坏最后快照语义。建议性能验收目标为在同一隔离基线上，代表性概览 p95 小于 1 秒且无分钟级长尾；该目标待采纳与实测，不是本轮结果。
