# 账户域表结构与索引审计报告（2026-11-04）

> 只读审计。对象为生产 `103.36.63.105` 的 `juhe_business` schema（PostgreSQL 18）。未修改任何表、索引或数据。

## 结论

- **未发现新的跨用户读取漏洞**：账户列表 / options / AI 健康已按 `system_account_id` 先收敛，用户维度唯一索引与查询索引存在。
- 主要问题不是“缺用户 id”，而是四类：
  1. **历史备份表残留**：19 张 2026-10-24 迁移备份表，无主键、无用户索引，部分含 API Key / 授权数据；
  2. **子表外键列缺支撑索引**：删除账户/模型/API Key 时的级联与 FK 校验会扫全表；
  3. **部分用户维度列缺前导索引**：`models`、`system_sessions`、`media_jobs`；
  4. **索引冗余与 DDL 双写**：`accounts` 37 枚索引、多组近重复索引、同一张表被两个 Go 包重复建表。
- 另有两个**产品语义待裁决**项：账户名称大小写唯一性、代理配置名称全局唯一。二者都不是当前运行时缺陷，但会影响“用户维度唯一”的一致性。
- 无 P0。建议单开 T117 分批治理，先做加法索引与备份表清理，再做冗余索引回收。

## 方法与边界

- 数据源：`information_schema`、`pg_index`、`pg_constraint`、`pg_indexes`、`pg_stat_user_indexes`、`pg_stat_user_tables`、`pg_stat_database`。
- `pg_stat_database.stats_reset IS NULL`：索引扫描计数自建库以来累计，未重置；因此 `idx_scan=0` 对**建库时已存在**的索引有较强参考价值。审计后新建的索引（含 T112/T114 待发布代码新增项）时间窗更短，不能直接按 0 删除。
- 未做全量 `EXPLAIN`、慢日志关联或写路径压测；下文的 DROP 项都是**候选**，不是执行指令。
- 行数取 `pg_stat_user_tables.n_live_tup`，为统计估算值。

## 一、P1：数据卫生与真实索引缺口

### 1. 19 张 2026-10-24 备份表残留

生产 `juhe_business` 存在以下不在 HEAD schema 内的备份表：

```text
api_keys_backup_chatkey_20261024          api_keys_backup_defmerge_20261024
api_keys_bak_emptyclean_20261024          group_accounts_backup_defmerge_20261024
groups_backup_defmerge_20261024           groups_bak_emptyclean_20261024
resource_authorization_grants_bak_authwipe_20261024
resource_authorization_sources_bak_authwipe_20261024
resource_authorizations_backup_defmerge_20261024
resource_authorizations_bak_authwipe_20261024
route_strategies_backup_defmerge_20261024
route_strategies_bak_backfill_20261024
route_strategies_bak_emptyclean_20261024
route_strategy_groups_backup_defmerge_20261024
route_strategy_groups_bak_backfill_20261024
route_strategy_groups_bak_emptyclean_20261024
scheduling_preferences_backup_defmerge_20261024
system_team_members_bak_authwipe_20261024 system_teams_bak_authwipe_20261024
```

- 规模：合计约 1 MB；最大 `group_accounts_backup_defmerge_20261024` 1487 行，`api_keys_backup_defmerge_20261024` 348 行。
- 结构：19 张全部**无主键**；用户列（`system_account_id` / `grantee_system_account_id`）没有前导索引。
- 内容：包含 API Key 行、分组绑定、授权与路由策略快照；`api_keys_backup_chatkey_20261024` 属于凭据相关数据。
- 代码引用：`rg` 未发现 Go 代码读取这些表；它们不属于 `--ensure-schema` 管理面。
- 评估：这是 2026-10-24 迁移（defmerge / authwipe / emptyclean / backfill）的现场备份。当前已有整库 `pg_dump` 与旧库 `juhe_ai_old_20261022`，这些表继续留在生产业务库只会增加敏感面与 schema 噪音。
- 建议：T114/T116 发布验证通过后，逐表核对行数与迁移记录，确认无需回滚后 `DROP TABLE`；若要保留，迁到独立 archive schema/库，不留在 `juhe_business`。DROP 前先备份并走受控窗口。

### 2. `account_supported_models.model_id` 缺索引

- 现状：PK `(account_id, model_id)`；`model_id` 是 FK，但没有以 `model_id` 开头的索引。当前 7396 行。
- 影响：删除模型、校验模型引用时，PostgreSQL 需要对 `account_supported_models` 做全表扫描；行数随“账户 × 支持模型”增长，后续会明显放大。
- 建议：`CREATE INDEX ... ON account_supported_models(model_id, account_id)`（同时服务反向查询“哪些账户支持模型 X”）。

### 3. `account_list_availability_projections` 的 FK 列缺前导索引

- 现状：PK `(viewer_system_account_id, account_id)`；`account_id`、`source_account_id`、`authorization_id` 均为 FK，但没有以它们开头的索引；当前 1185 行。
- 影响：删除账户 / 授权时，级联与 FK 校验按单列扫描子表；当前规模小，账户量增长后是明确的删除慢路径。
- 建议：至少补 `(account_id)`；若 `source_account_id` / `authorization_id` 存在删除或反查路径，一并补。可先做 `CREATE INDEX` 加法，低风险。

### 4. 用户维度前导索引缺口

| 表 | 行数 | 现状 | 风险 | 建议 |
| --- | ---: | --- | --- | --- |
| `models` | 269 | 只有 PK 和 `(COALESCE(vendor_code), scope, COALESCE(system_account_id), upstream_model)` 唯一索引；个人模型查询走 `scope='personal' AND system_account_id=?` | 前导列是 vendor，owner 查询无法有效用索引，当前小表可忍，增长后变慢 | 增加 `(system_account_id, scope, vendor_code)` |
| `system_sessions` | 40 | 只有 `token_hash`、`expires_at` 索引；代码按 `system_account_id` 删会话/管理会话 | 用户会话管理、账户删除时扫全表；会话量随登录增长 | 增加 `(system_account_id, last_seen_at DESC)` |
| `media_jobs` | 0 | 只有 `account_id`、`api_key_id`、`status` 索引；repo 明确按 `owner_system_account_id` 过滤 | 当前无数据；媒体任务启用后，用户/管理列表会扫全表 | 增加 `(owner_system_account_id, created_at DESC, id DESC)` |
| `accounts` | 1211（未软删） | `authorization_instance_owner_system_account_id` 无前导索引；现有实例索引是 `(source_account_id, system_account_id, id)` | 若按“实例归属人”筛选/管理，无法直接命中 | 先确认查询路径；有则增加 `(authorization_instance_owner_system_account_id, id)` |

### 5. `openai_compatible_*` 外键索引缺口（当前 0 行，按设计会增长）

- 现状与缺口：
  - `openai_compatible_files.api_key_id`：FK 无前导索引；现有索引均以 `system_account_id` 开头。
  - `openai_compatible_vector_stores.api_key_id`：同上。
  - `openai_compatible_vector_store_files.api_key_id` / `file_id`：无前导索引（PK 是 `vector_store_id, file_id`）。
  - `openai_compatible_vector_store_chunks.vector_store_id`：无前导索引（复合索引以 `system_account_id, api_key_id` 开头）。
- 影响：删除 API Key / 文件 / vector store 时，FK 校验会扫子表；这些表设计上会承载大量 chunk/file 行，属于典型的“现在 0 行、上线后放大”的缺口。
- 建议：在功能放量前补 `(api_key_id)`、`(vector_store_id)`、`(file_id)` 支撑索引。

- 说明：`accounts` 的 37 枚索引是明确的写放大大户；上表只列了名称类与 0 扫描候选，未列 `pkey`、`system_account_concurrency`、`availability_schedule_next_check`、`super_priority`、`dispatch_priority`、`balance_*`、`health_check_due` 等高频索引。

### 7. 精确重复索引

- `account_api_key_runtime_states`：`account_api_key_runtime_states_account_fingerprint` 与 `idx_account_api_key_runtime_unique` 完全同键同谓词，**两个 DDL 所有者各建了一枚**（见第 8 条）。保留代码 upsert 依赖的 `idx_account_api_key_runtime_unique`，删除另一枚。
- `account_test_session_tasks`：PK `(session_id, task_id)` 与 `idx_account_test_session_tasks_session (session_id, task_id)` 完全重复；删除显式索引。
- `system_accounts`：`system_accounts_username_key (username)` 与 `idx_system_accounts_username_unique_lower (lower(username))` 逻辑上后者已覆盖前者的唯一性；前者仅 1 次扫描。确认没有 `ON CONFLICT (username)` 依赖后，可删除 `system_accounts_username_key`。
- T116 会随表删除 `account_name_search_terms/documents`、`account_list_availability_projection_search_terms` 上的 4 枚重复/词项索引，以及两枚 `search_index_complete` 部分索引；不在本报告重复计入。

### 8. Schema DDL 双写（同一张表两个所有者）

- `account_api_key_runtime_states` 由两处创建：
  - `backend-go/projects/maintenance/internal/schema/pg_schema_business_tables.go`（生产 schema 所有者）；
  - `backend-go/shared/platform/accounttest/proberepo/schema.go` 的 `EnsureSchema`（探针族启动自建）。
- 两者 `CREATE TABLE IF NOT EXISTS` 同形，但唯一索引名字不同，因此生产同时存在两枚同键唯一索引。新库也会按启动顺序得到两枚。
- 评估：这是 schema 所有权分散，不是单点 bug；会持续制造重复索引与漂移风险。建议明确“业务表只由 maintenance 拥有”，`proberepo.EnsureSchema` 改为只校验/不建表，或统一使用同一索引名并去掉重复 DDL。

### 9. `system_account_id` 外键一致性

- 有 FK 的用户表：`account_tags`、`account_tag_bindings`、`resource_authorizations`、`system_sessions`、`model_quality_schedules` 等。
- 无 FK 的用户表：`accounts`、`api_keys`、`groups`、`group_accounts`、`proxy_profiles`、`scheduling_preferences`、`openai_compatible_*`、`request_quota_hourly_window_scope_bindings`。
- 现状未发现系统账户硬删除路径（仅软停用），因此当前孤儿风险有限；但导入/手工 SQL 可以写入不存在的 `system_account_id`。
- 建议：裁决统一策略——
  - 方案 A：加 `FOREIGN KEY (system_account_id) REFERENCES system_accounts(id)`，用 `NOT VALID` + 窗口内 `VALIDATE`，删除行为按表选择 `RESTRICT`/`CASCADE`；
  - 方案 B：明确“系统账户只软删、不硬删”，并增加周期性孤儿检查任务。
  不要继续维持“部分有 FK、部分没有”的隐式约定。

### 10. 大小写唯一性 vs 大小写不敏感搜索

- 现状：`idx_accounts_owner_name_unique (system_account_id, name)` 是**大小写敏感**唯一；搜索是 `ILIKE`（ASCII 大小写不敏感）。
- 生产存在 1 组仅大小写不同的同名账户（`vsllm` ×2，同一 owner），说明当前允许这种并存。
- 影响：用户看到的是“两个同名账户”，搜索也无法区分；如果期望“用户维度唯一”按人类直觉成立，应改为 `(system_account_id, lower(name))` 唯一。
- 建议：先裁决语义；若改，先清理 1 组存量重复，再建 `lower(name)` 唯一索引（可先 `NOT VALID`/普通唯一索引验证）。API Key、分组、路由策略的 `name` 唯一同样大小写敏感，当前无重复，建议一并裁决。

### 11. `proxy_profiles.name` 全局唯一（已文档化，但与用户维度不一致）

- 现状：`system_account_id NOT NULL`（按用户归属），但 `idx_proxy_profiles_name_unique (name)` 是**全局唯一**；文档 `docs/functions/幂等与唯一约束设计.md:36/208` 明确“代理名称全局唯一”。
- 影响：两个用户不能使用同名代理配置；若产品预期是“每个用户自己的代理列表”，这是设计冲突。当前 `idx_proxy_profiles_system_account` 0 次扫描，说明读路径基本按全局名称，而非按 owner 列表。
- 文档漂移：文档写 `lower(name)` 唯一，实际索引是 `name`（大小写敏感）；当前无仅大小写重复。
- 建议：先确认代理是全局共享资源还是用户私有资源。全局则保留现状并删除无用的 owner 索引；用户私有则改为 `(system_account_id, name)` 唯一，并补 owner 列表索引。

### 12. 其它高索引表待跟进

- `api_keys` 15 枚、`resource_authorization_grants` 14 枚、`groups` 9 枚、`proxy_profiles` 7 枚、`system_accounts` 7 枚。

### 13. 投影读模型索引

- `account_list_availability_projection_search_terms` 及其索引随 T116 删除。
- `account_list_availability_projections.idx_..._name_trgm`（2 MB）0 次扫描；`idx_..._name_order` 与 `idx_..._name` 近似重叠。T116 后投影不再承载搜索词，建议评估删除 trigram 或 expression 索引，保留排序所需的最小集合。

## 三、P3：系统性设计债（不建议本轮动）

1. **时间戳大量使用 `text`**：`created_at` / `updated_at` / `expires_at` 多为 ISO 文本。当前依赖 ISO 字典序，查询可用；但缺少类型约束、时区语义和数据库时间运算，长期是格式漂移风险。
2. **JSON 大量使用 `text` + CHECK**：如 `payload_json`、`request_snapshot_json`、`artifact_json`；部分查询需要 `(payload_json)::jsonb` 表达式，无法直接建普通 jsonb 索引。长期应迁 `jsonb` 或拆 payload 表。
3. **`media_jobs` 单行承载 6 个 JSON 文本列**（request/artifact/error/usage/params applied/params ignored），媒体量上来后是行膨胀点；可拆 payload 侧表。
4. **`accounts` 67 列宽表**：历史字段多，读面已按列投影，暂不影响；后续可评估冷列归档。

## 四、明确不算问题（已裁决/设计如此）

- `models.system_account_id`、`scheduling_preferences.system_account_id` 可空：分别表示 builtin/global 行；不是漏用户 id。
- `resource_authorization_grants.grantee_system_account_id`、`resource_authorizations.grantee_system_account_id` 可空：团队授权使用 `grantee_team_id`；不是漏用户 id。
- `accounts.authorization_instance_owner_system_account_id` 可空：自有账户为空、授权实例才有值；符合设计。
- `schema_migrations`：不是死表，Go `upgradepipeline` 账本在用（13 行）。
- `account_name_search_*`：T116 已改为直查，待 T114 窗口退役；不再分析其索引。
- `proxy_profiles` 全局唯一：文档已裁决；仅建议确认产品意图，不作为 bug。

## 五、建议治理顺序（T117）

1. **T117a 备份表清理**（T114/T116 发布验证后）：核对 19 张表行数与迁移记录，备份后 DROP；或迁 archive schema。
2. **T117b 加法索引**（低风险）：`account_supported_models(model_id, account_id)`、`account_list_availability_projections(account_id)`、`models(system_account_id, scope, vendor_code)`、`system_sessions(system_account_id, last_seen_at DESC)`、`media_jobs(owner_system_account_id, created_at DESC, id DESC)`；`openai_compatible_*` 在功能放量前补 FK 索引。
3. **T117c 冗余索引回收**：7 天 stats + `EXPLAIN` 验证后，按 `DROP INDEX CONCURRENTLY` 回收 `accounts` 近重复与 0 扫描候选；合并 `account_api_key_runtime_states` 双唯一索引、`account_test_session_tasks` 重复索引。
4. **T117d 语义裁决**：大小写唯一性（先清 1 组重复）、代理名称全局/用户私有、`system_account_id` FK 策略。
5. **T117e 系统性债**：text 时间戳、text JSON、media_jobs payload 拆分另立计划，不在索引治理内混做。

## 六、复现口径（只读）

```sql
-- 用户列无前导索引
SELECT c.table_name FROM information_schema.columns c
WHERE c.table_schema='juhe_business' AND c.column_name LIKE '%system_account_id'
AND NOT EXISTS (SELECT 1 FROM pg_index i JOIN pg_class t ON t.oid=i.indrelid
  JOIN pg_namespace n ON n.oid=t.relnamespace JOIN pg_attribute a ON a.attrelid=t.oid AND a.attnum=i.indkey[0]
  WHERE n.nspname='juhe_business' AND t.relname=c.table_name AND a.attname=c.column_name);

-- FK 首列无前导索引
SELECT con.conrelid::regclass, a.attname FROM pg_constraint con
JOIN pg_attribute a ON a.attrelid=con.conrelid AND a.attnum=con.conkey[1]
JOIN pg_class c ON c.oid=con.conrelid JOIN pg_namespace n ON n.oid=c.relnamespace
WHERE con.contype='f' AND n.nspname='juhe_business'
AND NOT EXISTS (SELECT 1 FROM pg_index i WHERE i.indrelid=con.conrelid AND i.indisvalid AND i.indkey[0]=con.conkey[1]);

-- 索引使用率
SELECT relname, indexrelname, idx_scan FROM pg_stat_user_indexes
WHERE schemaname='juhe_business' ORDER BY idx_scan ASC;
```
