# 热路径分配画像与优化批次（2026-10-14）

## 结论

审计 profile 批次已完成 Gateway 侧五个目标的度量与决策：

1. **streamread**：流式管道处理整条 OpenAI Chat SSE 流为 31µs / 19KB / 214 allocs（含 inspector 每 chunk 快照与超限检查），无病理级分配；BUG-0247 项 4（请求体 `bytes.NewReader` 零拷贝）已在既有修复中落地。Go 1.26 定时器实现下维持现状。
2. **双快照**：管道读层冗余快照已随 BUG-0313 Tier 1 收敛（`pipe.go` 快照守卫 + inspector `pendingLine` `[]byte` 化）；每出站 chunk 的快照是进度上报、跳过日志与语义决策的必要输入。维持现状。
3. **账户克隆**：`/v1` 每请求的账户读覆盖层（可用性过滤 + 逐账户深克隆 + `CurrentConcurrency` 注入）是本次被证据支持实施优化的热点——50 账户组每次读约 122KB 垃圾。已落地切片预分配：隔离覆盖层 121,937B→65,360B（−46%），读路径 130,729B→72,936B（−44%），10 账户组 30,312B→14,408B（−52%）。
4. **OAuth body**：令牌请求体构造 `strings.NewReader(request.Body)`（字符串源零拷贝）、响应读取 `io.LimitReader` 有界（≤2MiB）、`Body` 仅一次 string 拷贝；属低频路径（令牌交换/刷新与账号接入），维持现状。
5. **派发准备链**（同批证据驱动扩展）：`PreserveGatewayAccountDispatchPriorityTiers` 泛型改指针视图（消除每账户整结构逃逸副本）+ 单次 tier 投影重构（消除按 tier 的 `map[tier][]T` append 增长）+ `buildDispatchSegments` 预分配。`PrepareDispatchAccounts` 69,968B / 125 allocs → 46,730B / 106 allocs（−33% 字节 / −15% allocs）；候选过滤维持（已预分配）。

未做（记录边界）：更激进的「缓存快照不可变契约、仅在派发选中账户时克隆单个账户」属行为契约级重构——共享缓存快照携带解密凭据，跳过每请求克隆需要全部下游消费方承诺不修改快照字段并另立文档契约，收益（50 账户约 25µs / 24KB 克隆本体）与风险不匹配，未纳入本批。派发链残项：`FilterGatewayAccountsByRequestedModel` 的两份 N 容量结果切片属过滤形态固有（结果为空列表语义）；`buildDispatchSegments` 段内账户 `append` 增长可两遍构造消除（约 6KB/次），复杂度上升暂不做；`gatewayclientip` 存在同算法手工副本且不在本画像热点，重复实现收敛为后续项。

## 背景与范围

审计复审将 streamread 开销降级为性能线索（Go 1.26 定时器 GC），并要求先度量再决定（profile 批次）。本报告覆盖四个审计目标与派发准备链扩展目标的现状度量、已实施改动、未做项及其理由。度量对象为当前工作区源码，基准环境为 Windows / i9-13900K（`-32` 即 GOMAXPROCS 32），绝对时间仅供参考，字节与 allocs 是决策依据。

## 已实施优化

均为分配削减，语义零变化：

- `internal/gatewayruntimecache/accounts.go`：
  - `applyConcurrencyOverlay`：`out := []OpenAIAccountSecret{}` → `make([]OpenAIAccountSecret, 0, len(accounts))`。账户结构体约 0.7KB，从空 append 的容量倍增会额外产生约一倍的数组复制垃圾（50 账户实测约 57KB，占覆盖层垃圾的近一半）。
  - `gatewayAccountConcurrencyAccountIDs`：`out := []string{}` → `make([]string, 0, len(accounts))`（`seen` 去重 map 语义不变）。
  - 两处均返回非 nil 空切片，`len`/JSON 序列化行为与原实现一致；`cloneOpenAIAccountsWithCurrentConcurrencyKeepAll` 原本已是预分配形态，本次对齐一致。
- `internal/gatewayproxyhealth/dispatchpriority.go`：泛型 `view` 由 `func(T)` 改 `func(*T)`（调用方 `gatewaydispatch/capacity.go` 的 `dispatchPriorityView` 与同包 `proxyhealth.go:orderResultForScope` 的闭包同步指针化，指针指向原切片元素、只读消费），消除每账户整结构逃逸副本；分组输出由 `map[tier][]T` 按 tier append 改为单次 `tierOf` 投影 + 按基准 tier 序列双重循环输出，顺序语义逐字保持（基准 tier 序列在前、未知 tier 尾部保持相对顺序）。
- `internal/gatewaydispatch/dispatchsegments.go`：`segments` 预分配 `cap = len(accounts)`（段数上限即账户数）。

## 验证

- 包测试：`gatewayruntimecache`、`gatewayproxyhealth`（含 8 连跑）、`gatewaydispatch`、`gatewayclientip` 全绿；`go build ./...` 与 `go vet` 干净。
- 链定向：`go test ./cmd/juhe-ai-gateway/ -run 'Tier|Segment|Dispatch|Capacity' -count=1` 绿（48.4s）。
- 基准前后对照见上表；`gofmt -l` 干净。
- 观察项：一次 `gatewayproxyhealth` 单跑失败（细节因输出截断丢失），随后 12 轮（含与 gatewaydispatch 组合运行）全绿未复现，判定为一次性偶发；如需可借此筛子复跑确认。

## 边界与后续

- 未度量生产真实组的账户字段规模分布与请求 QPS 加权成本；本报告的垃圾字节结论按账户数线性外推成立，绝对时间不可直接外推。
- 后续候选（按收益排序）：`FilterGatewayAccountsByRequestedModel` 结果切片形态（需过滤语义契约）、`buildDispatchSegments` 两遍构造、`gatewayclientip` 同算法副本与 gatewayproxyhealth 的收敛、派发视图 `Priority` 的 `*float64` 小对象（每账户 1 次，可用 int 字段或视图复用消除）。
- 若未来在 50+ 账户大组且高 QPS 下观察到 GC 压力，优先评估方向是「克隆按需化」（派发选中后才克隆）与「快照不可变契约」，需独立设计文档与跨包消费方审计。
