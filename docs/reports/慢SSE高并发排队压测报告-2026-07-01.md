# 慢 SSE 高并发排队压测报告（2026-07-01）

## 测试目的

验证 mock 上游在单个 SSE 请求随机持续 3-30 秒、过程中间断输出内容时，网关在 1000 并发下是否会退化成单线程、长期堵死、批量排队失败或造成 PostgreSQL / Redis 队列积压。

## 测试环境

- 代码分支：本地工作区。
- 运行入口：`pnpm --filter juhe-ai-backend test:performance-gateway-load`。
- 后端形态：真实本地 server + DB service + background worker + 本地 mock upstream。
- 中间件：`192.168.1.203` 测试环境 PostgreSQL + Redis cache + Redis state / Redis Streams。
- 场景：`responses_stream`。
- 慢 SSE：每个上游流式请求随机总时长 3000-30000ms，6 个 chunk 均匀分布发送。
- 并发：1000。
- 账号容量压测档：32 个账号，每账号 4 个并发槽，总上游槽位 128。

## 原始产物

- 高容量基线：`reports/slow-sse-1000-high-capacity.json`
- 修复前 128 槽位：`reports/slow-sse-1000-account-slots-128.json`
- 修复后 128 槽位：`reports/slow-sse-1000-account-slots-128-fixed.json`

| --- | ---: | ---: | ---: | --- | ---: | ---: | --- |

修复后 128 槽位场景的请求侧延迟符合排队预期：p50 约 79.6s，p95 约 143.2s，p99 约 152.4s。上游单条 SSE 持续时间分布仍符合 3-30 秒配置：min 约 3.18s，avg 约 16.69s，p95 约 28.98s，max 约 29.99s。

## 问题定位

高并发分组原有队列只在调度准备阶段根据本地并发快照判断是否需要等待。1000 个请求同时进入时，大量请求会在账号尚未全部显示为满载前越过准备阶段，随后在真实 Redis 账号并发槽位获取处竞争失败。

竞争失败后，旧逻辑会继续尝试所有候选账号，并为每个账号写入 `concurrency:limit` 失败记录，最后返回 503。修复前 128 槽位压测出现约 3 万条 usage record 增量和明显 Redis backlog，根因就是这些容量失败记录被批量放大。

## 修复结论

已在真实账号并发槽获取失败后补充高并发分组队列等待：

- 当带高并发调度策略的分组在 `fetchFirstAvailableUpstream` 中抢账号槽失败时，不再立即写每账号容量失败记录。
- 请求进入既有 `waitForHighConcurrencyGroupCapacity` 队列，等待账号槽释放后重新调度。
- 只有队列超时、队列满或取消时，才写入单次容量失败记录。
- 保留普通分组 / 非高并发路径原行为：账号并发满仍写失败使用记录。

修复后，128 个真实上游槽位能够承载 1000 个慢 SSE 请求，表现为按槽位排队完成，而不是批量 503 或单线程串行堵死。PostgreSQL 没有死锁和锁等待；Redis 本轮没有新增 backlog。

## 边界说明

高容量基线里的 `ECONNREFUSED` 来自本机 Windows 侧 1000 连接突发时的客户端到本地后端连接拒绝，不是上游业务调度失败；修复后的 128 槽位验证通过 `REQUEST_START_SPREAD_MS=1000` 避免该噪声干扰。

本轮没有测试多后端进程共享同一高并发队列的公平性。当前队列仍是进程内等待队列，账号槽位由 Redis 约束；如果未来部署多网关实例，需要单独验证跨实例排队公平性和唤醒策略。
