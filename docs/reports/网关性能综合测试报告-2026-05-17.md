# 网关性能综合测试报告（2026-05-17）

## 1. 测试结论

本次使用新增的 `pnpm test:perf` 对本机模拟网关链路进行性能综合测试。测试通过临时 SQLite、模拟 OpenAI 上游和真实 `/v1` 网关路由完成，不消耗真实 OpenAI 额度，不写入本地真实业务库。本文为早期临时记录类库时期的历史容量参考，当前存储口径已拆为数据集目录库、使用记录目录库、usage shard 和统计结果库。

在默认配置下，全部 9 个场景档位均执行成功，错误率均为 `0%`，使用记录队列和审计日志队列在每个档位结束后均清空。

本机模拟链路中，本轮可观察到的参考吞吐如下：

- `/v1/models`：最高成功 QPS `641.69`，并发 `25`，p95 延迟 `75.616ms`。
- `/v1/responses`：最高成功 QPS `441.45`，并发 `50`，p95 延迟 `178.828ms`。
- `/v1/chat/completions`：最高成功 QPS `482.84`，并发 `50`，p95 延迟 `163.378ms`。

以上结论只代表当前开发机、本机模拟上游、临时 SQLite 和单进程测试形态下的容量参考；生产环境仍需在目标机器、真实 DB service / worker 进程拓扑、目标磁盘和实际网络条件下复测。

## 2. 测试范围

本次覆盖：

- 网关 Bearer API Key 鉴权与运行态缓存。
- 分组授权元数据读取。
- OpenAI 账户候选选择与调度。
- `/v1/models` 本地模型列表返回。
- `/v1/responses` 非流式转发。
- `/v1/chat/completions` 非流式转发。
- 模拟上游请求、响应头复制、响应体转发。
- 使用记录队列写入当时测试用临时记录类数据库。
- 原始审计日志采样队列写入当时测试用临时记录类数据库。
- 延迟分位、QPS、错误率、事件循环延迟、CPU、内存和记录类数据增量统计。

本次不覆盖：

- 真实 OpenAI 上游耗时、限流和网络抖动。
- 真实代理链路质量。
- 生产形态的独立 DB service / background worker IPC 开销。
- 多实例部署、负载均衡或分布式场景。
- 前端页面性能。

## 6. 关键观察

### 6.1 `/v1/models`

`/v1/models` 不请求模拟上游，由网关直接返回模型列表，因此它主要反映鉴权、缓存、记录写入和本地响应能力。并发 `25` 时吞吐最高，为 `641.69 QPS`；并发 `50` 时吞吐下降到 `314.94 QPS`，p95 延迟上升到 `298.699ms`，说明在当前测试机上继续堆高并发会增加事件循环和记录写入压力。

### 6.2 `/v1/responses`

`/v1/responses` 走完整模拟上游转发链路，并发 `50` 时达到本轮最高 `441.45 QPS`，p95 延迟 `178.828ms`，错误率为 `0%`。在本机模拟上游 20ms 延迟、512 bytes 响应体条件下，该链路仍保持稳定。

### 6.3 `/v1/chat/completions`

`/v1/chat/completions` 并发 `50` 时成功 QPS 为 `482.84`，p95 延迟 `163.378ms`，错误率为 `0%`。该结果说明非流式 Chat Completions 兼容路径在本轮模拟负载下表现接近 responses，且未出现使用记录队列堆积。

### 6.4 队列与记录类数据

测试结束汇总显示：

- 临时记录类数据库 `usage_records` 总量：`20223`。
- 临时记录类数据库 `audit_logs` 总量：`1905`。
- 使用记录队列最终长度：所有档位均为 `0`。
- 审计日志队列最终长度：所有档位均为 `0`。

这说明在本轮模拟负载下，使用记录批量写入和审计采样写入能跟上请求压力，没有出现结束后队列滞留。

## 7. 容量参考

按“错误率不高于 1%，且 p95 延迟不高于 `1000ms`”作为本机模拟稳定条件，本轮所有默认档位均满足条件。

建议参考值：

| 链路 | 保守参考 QPS | 说明 |
| --- | ---: | --- |
| 模型列表 | 300 QPS | 并发 25 有更高吞吐，但并发 50 出现吞吐回落，保守取 300 |
| Responses 非流式 | 400 QPS | 并发 50 达到 441.45 QPS，保守取 400 |
| Chat Completions 非流式 | 450 QPS | 并发 50 达到 482.84 QPS，保守取 450 |

这些数值适合作为开发机模拟链路的容量参考，不应直接写入生产 SLA。

## 8. 风险与限制

- 当前测试未启动真实生产形态的独立 DB service 和 background worker，因此没有覆盖 IPC 和多进程调度开销。
- 当前测试使用本机模拟上游，网络延迟稳定且上游无真实限流；真实 OpenAI 请求的延迟和错误率会显著影响最终 QPS。
- SQLite 写入性能受磁盘、WAL、杀毒软件、系统负载和 Node 版本影响；不同机器结果会有明显差异。
- `/v1/models` 不请求上游，因此它的结果不能代表模型推理类接口能力。
- 流式 responses 场景本次未纳入默认测试；需要时可通过 `JUHE_AI_PERF_SCENARIOS=responses_stream` 单独补测。

## 9. 后续建议

1. 在目标部署机器上执行一次同样的 `pnpm test:perf`，记录真实机器基线。
2. 增加 `responses_stream` 场景专项测试，覆盖 SSE 首包、持续输出和完成事件。
3. 在生产形态下对已启动的主进程、DB service 和 background worker 做外部压测，补齐 IPC 开销和真实队列吞吐。
4. 按真实业务模型设置上游延迟，例如 `100ms`、`500ms`、`1000ms` 三档，区分网关 CPU 上限和等待型并发能力。
5. 若要形成上线容量建议，应至少补测目标机器、真实代理、真实上游、长时间 10 分钟以上稳定性和异常错误率场景。
