# 全链路请求性能审计报告（2026-07-26）

## 范围与结论

本轮只审计并交付 Node.js 网关的用户请求次数限制，以及它对客户端到上游主链路的新增开销；不处理 Go 实现，也不把历史全链路性能问题顺带扩成大范围重构。

结论：新增限制判断位于 API Key 认证后、候选账号调度前，请求路径只执行同步进程内 Map 操作、整数运算和最多四个窗口比较，不查询数据库、不等待 Redis、不扫描用量记录。100 万次纯内存基准平均 `0.765µs`，约 `1,307,896 req/s`，满足低于 `10µs` 的目标。

## 本轮实现

- 全局每分钟、日、周、月四个限制，`0` 表示无限。
- 用户覆盖支持缺失继承、`0` 无限、正整数覆盖，以及整组 `YYYY-MM-DD` 到期日。
- 到期日当天仍有效；从 `usageStatsTimezone` 下次日 `00:00` 起自动继承全局。
- 内存桶具有 2 分钟 / 2 天 / 9 天 / 35 天保留期和 500,000 默认容量，容量压力下 O(1) 淘汰最早桶。
- Redis 每秒后台批量协调，单批最多 1,024 个桶；Lua 维护实例累计值和 `__total` 差量，不做 `HVALS` 全量扫描。
- Redis 连接和命令使用 3 秒后台超时，失败指数退避最长 30 秒；故障时继续本机限制，不阻塞客户端请求。
- 超限返回 `429 user_request_limit_exceeded`，并记录丢弃请求审计；模型目录请求不计数。

执行命令：

```powershell
pnpm.cmd test:user-request-limit-performance
```

2026-07-26 本机结果：

```json
{
  "iterations": 1000000,
  "averageMicroseconds": 0.7645866,
  "requestsPerSecond": 1307896.3193966518

```

该基准只度量限制器 consume，不包含 Express、API Key runtime snapshot 读取、请求体解析、协议转换、账号选择、上游网络、SSE 和日志队列。因此它证明的是“本功能没有给主链路增加网络等待或显著 CPU 开销”，不是完整网关吞吐容量结论。

## 主链路审计边界

现有网关仍有独立于本功能的性能治理主题，包括运行时缓存 miss 的 DB service 加载、候选账号规模、协议转换、代理与上游连接、SSE 事件处理、usage / audit / runtime log 写入以及后台任务资源竞争。仓库已有专项计划与报告继续负责这些问题；本轮没有证据支持把它们与用户请求限制合并修改。

本功能保持以下边界：

- 主链路禁止 Redis / DB / HTTP await。
- Redis 只承接最终协调，不承诺多节点零超额。
- standalone 进程重启后会丢失本地计数；这是速度优先设计的已知取舍。
- Redis 后台同步失败、退出未完全排空或容量淘汰都通过指标 / 限频日志暴露，不转化为用户请求全局失败。

## 不适用范围

- Go 网关、Go system settings catalog、Go profile 契约。
- 生产多节点 Redis 高可用、真实生产流量和严格零超额配额。
- 对历史全链路热点的全面修复或容量承诺。
