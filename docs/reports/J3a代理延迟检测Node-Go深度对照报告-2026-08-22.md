# J3a 代理延迟检测 Node↔Go 深度对照报告

## 结论

本次对照确认：Go `proxylatency` 的基础探测域已经覆盖 Node 的代理 URL、凭据、SOCKS 远端 DNS、按传输模式拆分的请求头、禁止重定向、完整响应 drain、512 KiB body retention、64 KiB CONNECT response header、结果分类、lease/fence、幂等 replay 和健康状态；此前 dev 隔离 PostgreSQL/PgBouncer `6432` required smoke 也已通过并完成清理。

实现层面的三项阻断已落地，但生产切换门禁仍未关闭：

1. Node committed-outcome reader/projector 已接入，Go outcome 可按 `(stored_at,outcome_id)` 游标回写 Node `proxy_profiles` 读模型；本轮在 dev scratch 经 PgBouncer `6432` 实际验证了 reader、applied/stale CAS、receipt、cursor 与 replay，尚未验证真实 Node/Go 进程编排和重启恢复。
2. Go owner 模式下 Node 不注册 `proxy-latency-refresh`，shutdown 使用 `stopAndDrain(10_000)`；active-path-zero、旧 owner manifest、真实 handoff/rollback 仍需现场证据，故 owner gate 继续关闭。
3. Node `POST /proxies/:id/test` 在完整 gate 下走 Go loopback manual bridge，保留 `404/503 + Retry-After/200/502`、25 秒同步等待、取消、CAS stale 和 outbound fallback；本地 bridge/golden 已通过，真实进程联调尚未重跑。

数值默认值、目标排序和线级 wire golden 已有共享 manual/outcome fixture；IPv6 CONNECT authority、SOCKS wire、407/502/TLS/truncated/slow-drip 的跨 runtime 输出仍标记 `cross-runtime-unverified`，不能把本地通过扩展为生产通过。

## 6. 失败、手动与调度机制补缺

### 6.1 周期失败写回差异

Node 周期候选的非取消执行异常会写回 `testStatus=unknown`、`latency=null`、`lastTestMessage`、配置 revision 与 `lastTestedAt`，并计入 `executionFailed`；取消会向上抛出而不伪造普通候选结果。Go 对 input/claim/凭据/lease/envelope/cancel/fence 失败在 `AppendOutcome` 前返回，不产生 committed outcome；Node projector 不会为缺失 outcome 伪造 unknown。Go transport failure 则仍写代理 item `failed`。当前 projector receipt/cursor 只记录已读到的 committed outcome；Go runner 的 pre-outcome runtime error 仍仅通过 `LastError`/失败计数可观测。

### 6.2 Node 手动报告 schema

Node `ProxyTestReport` 的外部响应字段冻结为：`proxyId`、`proxyName`、`score`、`grade`、`status`、`passedCount`、`warningCount`、`failedCount`、`outboundIp?`、`outboundRegion?`、`baseLatencyMs?`、`testedAt`、`items`、`message`；每个 `ProxyTestItem` 字段为 `name`、`status`、`httpStatus?`、`latencyMs?`、`message`、`targetUrl?`。`?` 表示 Node JSON 序列化时字段为 `undefined` 则省略，不得改写为 `null`；synthetic 基础连通性 item（无 provider 或 provider 聚合）可省略 `targetUrl`，provider item 无论 passed/failed/unknown/deadline/transport 都保留 `targetUrl`，其中 unknown/deadline/transport 可省略 `httpStatus`、`latencyMs`；无可用出口或基础延迟时也省略对应 report 字段。状态枚举冻结为 `passed|warning|failed|unknown`；聚合规则为 failed>0→failed，否则 warning>0 或 passed 与 unknown 混合→warning，否则 passed>0→passed，否则 unknown；`unknown` score=0，否则 `max(0, round(100-warningCount*10-failedCount*35))`，grade 为 A(≥90)/B(≥75)/C(≥60)/D。报告包含 synthetic 基础连通性 item；provider item 使用 display name 和 base URL，Node 外部响应不携带 provider code。provider code 只能作为 bridge 内部查找元数据，不能直接添加到管理端响应。outbound 目标顺序为 `ip-api`、`ipwho.is`、`api.ip.sb`、`ipinfo.io`、`ipify`、`httpbin`，仅 200 响应尝试 JSON 解析，失败后回退；周期刷新不写 outbound。Go `Outcome` 目前没有这些管理聚合字段，因此“Go outcome -> Node report”不是直接反序列化关系，必须由 manual bridge 定义逐字段适配和 code→display-name 查找规则。

### 6.3 手动入口边界

Node 路由要求管理员权限并记录 operation log；只做 proxy 存在性检查，停用 proxy 仍可测试。诊断槽满返回 `503 + Retry-After`，测试期间对象消失返回 `404`，CAS stale (`updated=false`) 仍返回 `200` 报告，执行异常返回 `502`，槽在 finally 释放；无启用 provider 时仍可返回包含 unknown 基础 item 的 `200` 报告。Go reader 对无有效 target fail-closed。manual bridge 必须逐项保留 25 秒同步 deadline、取消、slot、鉴权、日志、stale no-op 和 outbound fallback。

### 6.4 调度器生命周期与资源占用

Node scheduler 事实为 60 秒间隔、4 分钟初始延迟、30 秒 stable phase、`coalesceOne`、`external-account-maintenance` resource lane、ops-worker 角色、60 秒 task timeout、30 秒至 10 分钟 failure backoff；默认 batch=20、candidatePoolFactor=4，candidate pool=`max(limit,limit*4)`，`targetCount=min(limit,candidates.length)`，并观察 `startedCount`、`deferredCount`、partial summary；busy lease 跳过并继续补位，周期候选还受 global concurrency、candidate deadline 与 lease grace 限制。timeout 只 abort signal，底层 task 完成前仍占用 running/lane；`stopAndDrain` 必须等待并报告 active count。Go 当前默认 BatchSize=20、InputLimit=80、candidate pool factor=4、worker concurrency=4，busy lease 跳过并继续补位并暴露 selected/target/claimed/started/processed/skipped/deferred/partial；resource lane/global governor 与跨进程 stop-and-drain 仍是未验证差异，不宣称完全 scheduler parity。
