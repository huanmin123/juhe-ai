# J3a 代理延迟检测 Node↔Go 深度对照报告

## 结论

本次对照确认：Go `proxylatency` 的基础探测域已经覆盖 Node 的代理 URL、凭据、SOCKS 远端 DNS、按传输模式拆分的请求头、禁止重定向、完整响应 drain、512 KiB body retention、64 KiB CONNECT response header、结果分类、lease/fence、幂等 replay 和健康状态；此前 dev 隔离 PostgreSQL/PgBouncer `6432` required smoke 也已通过并完成清理。

这不等于 J3a 已完成完整迁移。当前仍有三项明确阻断：

1. Node committed-outcome projector/readback 尚未接入，Go outcome 不能回写 Node `proxy_profiles` 读模型。
2. Node scheduler/business writer 尚未 drain，也没有 owner handoff、active-path-zero 和回滚证据；Go owner gate 必须保持关闭。
3. Node `POST /proxies/:id/test` 的 `404/503 + Retry-After/200/502`、25 秒同步等待和手动 outbound 字段尚无 Go bridge/readback 闭环。

数值默认值、目标排序和线级 wire golden fixture 仍需在同一 fixture 上做兼容性决策和验证；不能把当前本地 Go 通过当作跨运行时通过。

## 必须保留的迁移边界

- 不修改 Node 源码来“配合”当前 Go；Node 仍是事实源，迁移方在接线阶段按本报告同步。
- 不启用 Go owner、不停止 Node scheduler、不做双写、不增加 Node RPC/Redis fallback。
- Go 不写 Node business SQLite 或 `juhe_business.proxy_profiles`；projector 必须通过冻结的 committed outcome/cursor/receipt 协议完成。
- dev smoke 只证明 jobs schema、reader、lease、input、claim、outcome 和权限隔离；不证明 Node projector、owner handoff、manual route 或生产/L4。

## 后续阻断门禁

### P1：Node→Go→Node outcome 闭环

固定同一 proxy fixture，Node 发布 input，Go jobs 执行并提交 committed outcome，Node projector 按 `(stored_at, outcome_id)` 游标消费；覆盖 applied/stale/ignored/rejected receipt、旧 revision、重复 outcome、poison payload、重启恢复和 cursor 不丢失。未完成前保持 owner gate off。

### P2：scheduler drain 与 owner handoff

为 Node scheduler/business writer 增加停止/排空证据；确认没有活跃 Node candidate scan、DB-service 写入、queue/IPC/启动器路径后，才允许受控开启 Go owner。必须保存旧 owner manifest、回滚命令和 active-path-zero 检查，禁止先双跑。

### P3：manual bridge

实现并测试 loopback v1 encrypted input 的 404、503/Retry-After、200、502、25 秒 deadline、取消、重复 request 和 outbound 字段 readback；手动路径与周期 scheduler 分离，不引入持久队列。

### P4：兼容性证据

在同一 Node/Go fixture 上冻结 probe/candidate/run/scheduler 数值、provider target 排序、IPv6 CONNECT authority、SOCKS wire、407/502/TLS/truncated/slow-drip 线级行为；每项要有 Node 与 Go golden 输出，不能只靠源码相似。

## 6. 失败、手动与调度机制补缺

### 6.1 周期失败写回差异

Node 周期候选的非取消执行异常会写回 `testStatus=unknown`、`latency=null`、`lastTestMessage`、配置 revision 与 `lastTestedAt`，并计入 `executionFailed`；取消会向上抛出而不伪造普通候选结果。Go 对 input/claim/凭据/lease/envelope/cancel/fence 失败在 `AppendOutcome` 前返回，按契约只保留 receipt，不产生 committed outcome。Go transport failure 则仍写代理 item `failed`。这不是等价实现，P1 projector 必须决定旧 Node 状态保留、unknown 投影和 receipt 幂等规则。

### 6.2 Node 手动报告 schema

Node `ProxyTestReport` 包含 synthetic 基础连通性 item、provider display name/code、每个 target 的 `targetUrl`、HTTP status/message、latency、`baseLatencyMs`、`counts`、`score`、`grade`、总体 `message`、`testedAt`，以及可选 `outboundIp/outboundRegion`。outbound 目标顺序为 `ip-api`、`ipwho.is`、`api.ip.sb`、`ipinfo.io`、`ipify`、`httpbin`，仅 200 响应尝试 JSON 解析，失败后回退；周期刷新不写 outbound。Go `Outcome` 目前没有这些管理聚合字段，因此“Go outcome -> Node report”不是直接反序列化关系，必须由 manual bridge 定义单独的适配 schema。

### 6.3 手动入口边界

Node 路由要求管理员权限并记录 operation log；只做 proxy 存在性检查，停用 proxy 仍可测试。诊断槽满返回 `503 + Retry-After`，测试期间对象消失返回 `404`，CAS stale (`updated=false`) 仍返回 `200` 报告，执行异常返回 `502`，槽在 finally 释放；无启用 provider 时仍可返回包含 unknown 基础 item 的 `200` 报告。Go reader 对无有效 target fail-closed。manual bridge 必须逐项保留 25 秒同步 deadline、取消、slot、鉴权、日志、stale no-op 和 outbound fallback。

### 6.4 调度器生命周期与资源占用

Node scheduler 事实为 60 秒间隔、4 分钟初始延迟、30 秒 stable phase、`coalesceOne`、`external-account-maintenance` resource lane、ops-worker 角色、60 秒 task timeout、30 秒至 10 分钟 failure backoff；周期候选还受 global concurrency、candidatePoolFactor=4、candidate deadline 与 lease grace 限制。timeout 只 abort signal，底层 task 完成前仍占用 running/lane；`stopAndDrain` 必须等待并报告 active count。Go 当前为 opt-in serial cycle，没有等价 lane/global governor、deferred/partial summary 或 stop-and-drain；这属于明确差异，不是已通过的 scheduler parity。
