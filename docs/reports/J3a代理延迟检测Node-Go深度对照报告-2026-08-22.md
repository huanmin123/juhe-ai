# J3a 代理延迟检测 Node↔Go 深度对照报告

## 结论

本次对照确认：Go `proxylatency` 已独占覆盖代理 URL、凭据、SOCKS 远端 DNS、按传输模式拆分的请求头、禁止重定向、完整响应 drain、512 KiB body retention、64 KiB CONNECT response header、结果分类、lease/fence、幂等 replay、健康状态和业务结果投影；此前 dev 隔离 PostgreSQL/PgBouncer `6432` required smoke 也已通过并完成清理。

实现层面的 Go 独占接线已落地，但生产发布门禁仍未关闭：

1. Go result projector 直接按 `(stored_at,outcome_id)` 读取 committed outcome，在同一业务事务中完成 receipt、cursor、CAS 与 `proxy_profiles` 写回；Node outcome reader/projector 和 Node J3a business writer 已删除。本轮 dev scratch 经 PgBouncer `6432` 实际验证 Go projector 的 applied/stale CAS、receipt、cursor 与 replay。
2. Node J3a scheduler、旧 executor、refresh 回归入口已删除；Node 不再注册候选扫描、不再执行探测、不再写 J3a 状态。active-path-zero、真实发布 handoff、重启恢复和生产/L4 仍需现场证据。
3. Node `POST /proxies/:id/test` 仅作为管理面 Go loopback manual adapter，保留 `404/503 + Retry-After/200/502`、25 秒同步等待、取消和 CAS stale；Go 不可用时直接失败，不走 Node fallback。真实手动进程联调尚未重跑。

数值默认值、目标排序和线级 wire golden 已有共享 manual/outcome fixture；IPv6 CONNECT authority、SOCKS wire、407/502/TLS/truncated/slow-drip 的跨 runtime 输出仍标记 `cross-runtime-unverified`，不能把本地通过扩展为生产通过。

## 必须保留的迁移边界

- Node 代码已完成 J3a 删除；保留的 Node 管理路由只作为 Go manual adapter。历史 Node 机制仅作为行为 oracle，不再作为运行时 owner。
- Go owner 是唯一 J3a owner；Node 整体服务仍承担其他管理 API，但 J3a scheduler/executor 已从 Node 删除。生产发布前仍需 active-path-zero、owner manifest、重启/发布检查和 L4 证据。
- Go result projector 直接写业务 PostgreSQL `proxy_profiles`，并在同一事务中写 receipt/cursor/CAS；Node 不再拥有 J3a business writer。
- Go dev smoke 证明 jobs schema、reader、lease、input、claim、outcome、业务投影和权限隔离；本轮还验证了 Go projector 的 applied/stale/receipt/cursor/replay 事务路径；这些证据不等同 owner handoff、manual route 进程联调或生产/L4。

## 6. 失败、手动与调度机制补缺

### 6.1 周期失败写回差异

历史 Node 周期候选的非取消执行异常曾写回 `testStatus=unknown`、`latency=null`、`lastTestMessage`、配置 revision 与 `lastTestedAt`；该 executor 已删除。当前 Go 对 input/claim/凭据/lease/envelope/cancel/fence 失败在 `AppendOutcome` 前返回，不产生 committed outcome；Go transport failure 写代理 item `failed`，Go projector 只投影已提交 outcome；pre-outcome runtime error 通过 jobs health 的 `LastError`/失败计数可观测，不伪造业务 unknown。

### 6.2 Node 手动报告 schema

Node `ProxyTestReport` 的外部响应字段冻结为：`proxyId`、`proxyName`、`score`、`grade`、`status`、`passedCount`、`warningCount`、`failedCount`、`outboundIp?`、`outboundRegion?`、`baseLatencyMs?`、`testedAt`、`items`、`message`；每个 `ProxyTestItem` 字段为 `name`、`status`、`httpStatus?`、`latencyMs?`、`message`、`targetUrl?`。`?` 表示 Node JSON 序列化时字段为 `undefined` 则省略，不得改写为 `null`；synthetic 基础连通性 item（无 provider 或 provider 聚合）可省略 `targetUrl`，provider item 无论 passed/failed/unknown/deadline/transport 都保留 `targetUrl`，其中 unknown/deadline/transport 可省略 `httpStatus`、`latencyMs`；无可用出口或基础延迟时也省略对应 report 字段。状态枚举冻结为 `passed|warning|failed|unknown`；聚合规则为 failed>0→failed，否则 warning>0 或 passed 与 unknown 混合→warning，否则 passed>0→passed，否则 unknown；`unknown` score=0，否则 `max(0, round(100-warningCount*10-failedCount*35))`，grade 为 A(≥90)/B(≥75)/C(≥60)/D。报告包含 synthetic 基础连通性 item；provider item 使用 display name 和 base URL，Node 外部响应不携带 provider code。provider code 只能作为 bridge 内部查找元数据，不能直接添加到管理端响应。outbound 目标顺序为 `ip-api`、`ipwho.is`、`api.ip.sb`、`ipinfo.io`、`ipify`、`httpbin`，仅 200 响应尝试 JSON 解析，失败后回退；周期刷新不写 outbound。Go `Outcome` 目前没有这些管理聚合字段，因此“Go outcome -> Node report”不是直接反序列化关系，必须由 manual bridge 定义逐字段适配和 code→display-name 查找规则。

### 6.3 手动入口边界

Node 路由要求管理员权限并记录 operation log；只做 proxy 存在性检查，停用 proxy 仍可测试。诊断槽满返回 `503 + Retry-After`，测试期间对象消失返回 `404`，CAS stale (`updated=false`) 仍返回 `200` 报告，执行异常返回 `502`，槽在 finally 释放；无启用 provider 时仍可返回包含 unknown 基础 item 的 `200` 报告。Go reader 对无有效 target fail-closed。manual bridge 必须逐项保留 25 秒同步 deadline、取消、slot、鉴权、日志、stale no-op 和 outbound fallback。

### 6.4 调度器生命周期与资源占用

历史 Node scheduler 事实为 60 秒间隔、lane、timeout 和 failure backoff；该 scheduler 已删除。Go 当前默认 BatchSize=20、InputLimit=80、candidate pool factor=4、worker concurrency=4，busy lease 跳过并继续补位并暴露 selected/target/claimed/started/processed/skipped/deferred/partial；Go-only 调度语义以 `runner.go` 和 jobs health 为准，跨 runtime 数值 golden 仍待补齐。
