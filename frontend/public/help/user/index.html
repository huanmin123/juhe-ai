快速使用

最小可用链路是：先准备 AI 账户，再放入分组，再创建策略路由，最后创建 API Key 给客户端使用。

1

创建 AI 账户

进入“我的 AI 账户”，选择供应商和接入类型，填写上游凭据、Base URL、支持模型、并发上限和加入分组。

2

创建或选择分组

低并发个人使用选“个人分组”；同一个 API Key 会被多人或程序大量并发调用时，选“高并发分组”。

3

创建策略路由

普通路由绑定一个分组；多个分组之间需要比例、主备、轮换或模型分级时，再使用其他路由模式。

4

创建 API Key

API Key 绑定策略路由，并设置状态、额度、过期时间和时间计划。完整密钥只在创建或刷新时展示。

5

填到客户端

客户端只填本系统 Base URL 和本地 API Key。后续换上游账号、调分组或改路由时，客户端通常不用改。

如果你只是想先跑通一次调用，先用“个人分组 + 普通路由 + 一个可用 AI 账户”。确认能调用后，再加高并发、权重、回退、错误策略和模型映射。

先看一张能力图

可以把系统理解成一个“可配置的 AI 调度台”：客户端只拿一个本地 API Key，后面的分流、账号池、真实上游、错误处理和记录追踪都在后台配置。

读图方式：上面一排是请求主链路，下面三块是你排障和调优时最常用的工具。遇到问题时不要直接改所有配置，先看请求卡在哪一层。

配置方案

下面按常见目标给出推荐组合。你可以先套用方案，再按自己的账号数量、并发和成本要求微调。

目标 推荐配置 为什么这样配 验收方式
个人稳定使用 个人分组 + 普通路由 + 成本优先 + 1-3 个正常账户。 链路短、命中稳定、排障简单，适合日常聊天、代码助手和个人项目。 账号测试通过后，用客户端发一次请求，再到使用记录确认命中账号和模型。
多人共用一个 API Key 高并发分组 + 普通路由 + 多个同类账户 + 合理并发上限。 高并发分组能减少请求堆到单个账号，账号软满后优先派给更空闲账号。 并发请求时看是否仍大量命中单账号；如果频繁 429，检查分组等待时间和账号并发。
主用账号池 + 备用账号池 两个或多个分组 + 故障回退路由；第一行主用，后续备用。 主分组正常时优先主用；主分组不可承接时才切备用，主用恢复后继续回主用。 临时停用主分组或主账号，确认请求能进入备用分组。
按比例消耗多个账号池 权重调度路由 + 多个启用分组 + 权重总和不超过 100。 适合多个账号池都可用，但希望按额度、成本或质量比例分摊。 观察较长时间使用记录，确认分组命中比例接近预期。
能力相近的分组轮换 轮询路由 + 多个启用分组 + 拖拽设置顺序。 适合多个分组能力相近，希望稳定轮流作为候选起点。 连续请求后查看分组命中是否按顺序轮换。
简单任务省钱，复杂任务保质量 混合智能路由 + 低成本评分模型 + 等级到模型 / 分组映射。 先判断请求难度，再把低档请求送低成本模型，高档请求送更强模型。 抽样使用记录，确认简单请求落低档，复杂请求落高档；同时关注评分成本。
上游经常 429 账号错误处理策略：状态码 429 + 处理动作为限流 + 合理恢复策略。 明确限流错误应让账号暂停一段时间，而不是立即反复打同一个账号。 在账号测试或使用记录里确认 429 样本，再观察账号是否进入限流中并按时恢复。
客户端模型名和上游模型名不一致 账号模型别名：来源模型填客户端模型名，目标模型填上游真实模型名。 客户端不需要改模型名，系统在命中账号后改写到真实上游模型。 用客户端原模型名发请求，使用记录里确认命中目标账号且上游没有模型不存在错误。
调整配置时一次只改一层：先改账号，再改分组，再改策略路由，最后改 API Key。多个层同时改，出现问题时很难判断是哪一层导致。

配置地图

遇到问题时先定位是哪一层配置影响了请求。系统层级固定为 API Key -> 策略路由 -> 分组 -> AI 账户 -> 供应商 / 模型能力。

你想解决的问题 主要页面 重点配置 注意事项
给客户端接入 我的 API Key 名称、策略路由、运行状态、额度、过期时间、时间计划、复制 Base URL 和密钥 客户端使用本地 API Key，不是上游供应商 API Key。
决定请求去哪组账号 我的策略路由 路由模式、分组绑定、权重、主备顺序、轮询顺序、混合智能等级映射 API Key 不直接绑定分组，必须通过策略路由。
组织账号池 我的分组 所属供应商、分组类型、状态、高并发策略、说明 分组是账号池容器，不保存具体凭据。
配置真实上游 我的 AI 账户 供应商、接入类型、凭据、Base URL、支持模型、并发上限、优先级、代理、时间计划 保存前建议点击“测试”，尤其是改了凭据、Base URL 或模型后。
处理上游错误 AI 账户高级配置 账号错误处理策略、响应检查策略、账号测试、使用记录 先从使用记录或账号测试取样，再写匹配规则。
查看请求结果 我的使用记录 traceId、API Key、策略路由、分组、账号、模型、耗时、Token、错误摘要 排障时优先复制 traceId，能串起请求全链路。

API Key

API Key 是客户端访问系统的入口，负责认证、额度、过期和时间计划。它只绑定一条策略路由，不直接保存分组或账号规则。

配置项 作用 什么时候配置 常见问题
名称 用于区分不同客户端、项目或使用方。 建议写清业务名，例如“生产环境 Codex”“研发测试 Key”。 名称不影响调用，只影响后台识别。
策略路由 决定这个 API Key 的请求进入哪套路由规则。 必须选择；普通使用选择普通路由，高可用或多账号池场景选择其他模式。 修改被多个 API Key 复用的策略路由，会影响所有绑定它的 API Key。
运行状态 启用时可调用，停用后请求立即被拒绝。 临时暂停某个客户端、发现密钥泄漏或排查异常流量时停用。 如果配置了时间计划，计划边界会继续更新运行状态。
过期时间 到期后自动不可用。 给临时项目、试用用户、短期测试密钥时使用。 到期不是额度耗尽，排障时要分开看。
美元额度 限制该 API Key 的消费上限。 需要控制成本、给不同使用方分配预算时配置。 额度触顶后网关会拒绝请求，需要提升额度或换 Key。
时间计划 按时间段自动启用或停用 API Key。 只允许工作时间调用、夜间暂停、按班次开放时使用。 时间计划影响入口状态，不代表账号本身可用。
刷新密钥 生成新的完整密钥，旧密钥立即失效。 怀疑泄漏、人员变更或需要轮换密钥时使用。 刷新前确认客户端能同步更新，否则会立刻调用失败。
推荐做法：不同客户端、环境或使用方使用不同 API Key，方便单独停用、看用量和设置额度。
不要这样做：把上游供应商 API Key 填到客户端。客户端只应该使用本系统生成的本地 API Key。

策略路由

策略路由决定“一个 API Key 的请求先进入哪个分组”。如果请求命中不符合预期，优先按 API Key 绑定的策略路由排查。

通用配置

配置项 说明 使用建议
名称 在 API Key 中识别这套路由策略。 写清业务场景，例如“生产主路由”“低成本测试路由”。
说明 补充用途、适用范围或注意事项。 建议写明绑定给哪些 API Key，方便后续修改前评估影响。
路由模式 普通、混合智能、权重调度、故障回退或轮询。 不知道选哪个时先用普通路由。
状态 停用后，这套路由策略不再参与 API Key 请求调度。 停用前先确认是否还有 API Key 绑定它。
分组绑定 选择当前路由可使用的分组，并按模式配置权重、顺序或主备。 停用某一行分组后，该分组不参与当前策略调度。

路由模式怎么选

普通路由：一把钥匙进一个池

API Key > 一个分组 > 组内账号

最适合先跑通和日常稳定使用。问题也最好排查，因为请求只会先进入一个账号池。

权重调度：按比例分流

API Key
分组 A 70% 分组 B 20% 分组 C 10%

适合多个账号池都能用，但希望按额度、成本或质量比例消耗。

故障回退：主用优先，备用接管

请求 > 主分组 失败时 > 备用分组

适合主备结构清楚的场景。主分组恢复后，后续请求会继续优先主分组。

轮询路由：多个池轮流起步

A > B > C > A

适合能力相近的多个分组。轮询只决定分组起点，分组内仍会继续选号。

混合智能：先判断难度，再选模型

请求 评分模型判断 1-10 级
低档模型 中档模型 高档模型

适合明确要“简单任务省钱、复杂任务保质量”的场景。

选择口诀

一个池：普通 按比例：权重 主备：故障回退 轮着用：轮询 按难度选模型：混合智能

没有明确需求时，先用普通路由。高级路由解决具体问题，不是默认必须开启。

模式 适用场景 关键配置 误区
普通路由 一个 API Key 只需要进入一个稳定账号池。大多数个人和单项目场景优先使用。 只能绑定一个分组；可选择成本优先或速度优先。 普通路由不是“低级模式”，而是最可预测、最好排障的模式。
混合智能路由 希望按请求难度自动选择不同目标模型和分组，例如简单请求走低成本模型，复杂请求走高质量模型。 评分模型、质量偏好、等级到模型的映射、质量检查、评分缓存和模型亲和。 会增加评分成本和复杂度；没有明确分级需求时不要为了“高级”而使用。
权重调度路由 多个分组都能承接请求，希望按比例分摊流量或成本。 至少两个启用分组；每行权重 1-100；总权重不能超过 100。 权重是长期比例，不保证每几次请求都严格按比例命中。
故障回退路由 有清晰主备结构，主分组优先，主分组不可承接时再用备用分组。 第一行是主用分组；后续是备用分组；至少一个备用分组启用。 主用恢复后后续请求会继续优先主用，不是永久切到备用。
轮询路由 多个能力相近的分组需要稳定轮换，避免长期集中到一个分组。 至少两个启用分组；拖拽调整轮询顺序。 轮询只决定分组起点，分组内仍会按账号状态、并发和优先级选号。

普通路由的调度偏好

成本优先

尽量保持会话、缓存和账号命中稳定，适合长会话、缓存收益明显、对首字速度没有强要求的场景。

  • 推荐给日常对话、代码助手、固定项目。
  • 账号没有异常时，请求更倾向继续使用稳定候选。

速度优先

观察首字慢样本，确认账号近期变慢后临时后置，并通过后台探针恢复。

  • 适合多人共享、首字等待敏感、账号速度波动大的场景。
  • 不会因为一次慢请求就永久改账号状态。
速度优先字段 说明 建议
首字观察阈值 超过该秒数先记录慢样本。 过低会频繁误判，过高会降低切换敏感度。
慢速触发次数 窗口期内达到次数后，账号进入速度降级。 并发大时可适当提高，避免偶发慢样本触发。
慢速窗口期 统计连续慢速触发的时间范围。 窗口越长越保守，窗口越短越敏感。
恢复成功次数 后台探针连续达标后恢复正常排序。 设置过低可能反复切换，过高恢复会慢。
探针间隔 速度降级后后台探针的最小间隔。 不要设得太短，避免额外打扰上游。
降级租约时间 确认慢或探针失败后，临时后置持续多久。 持续慢会刷新租约，连续达标会恢复。
单请求切号次数 同一个请求在已确认首字慢后最多隐藏切换账号的次数。 用于减少慢账号导致的等待，但不应依赖它掩盖账号池不足。

混合智能路由配置

配置项 作用 建议
评分模型 先用这个模型判断请求难度和能力档位。 选成本较低、稳定、响应快的模型，不一定选最强模型。
质量偏好 在成本优先、均衡、质量优先之间选择倾向。 生产关键任务可偏质量，批量轻任务可偏成本。
评分超时 评分请求最长等待时间。 超时后按兜底最高等级继续路由，避免请求卡死。
评分失败兜底最高等级 评分模型不可用或超时时允许使用的最高等级。 越高越可能进入强模型，成本也更高。
等级路由 把评分等级 1-10 映射到目标模型和分组。 至少覆盖低档和高档；每档选择真实可承接的分组。
质量检查 对命中条件的响应做二次质量判断。 只在重要或风险场景开启，因为可能增加额外模型调用成本。
评分缓存 TTL 同类请求评分结果缓存多久。 越长越省成本，越短越贴近实时输入差异。
模型亲和 TTL 同一会话保持目标模型不频繁切换的时间。 长会话建议保守一些，避免上下文体验波动。
切换等级差 新评分与当前亲和等级差达到该值才切换模型。 用于避免小幅波动导致频繁切换。
降级确认次数 连续低评分达到次数后才降级。 避免偶发低分立刻把会话降到低档模型。

分组与高并发

分组是 AI 账户的账号池。策略路由选中分组后，系统才会在分组内按账号状态、模型、并发、优先级和运行态选择具体账户。

配置项 作用 怎么用
分组名称 用于识别账号池。 建议包含供应商、用途和环境，例如“OpenAI 生产主池”。
所属供应商 决定这个分组后续可绑定的账户范围。 同一分组内放同类供应商账号，便于模型、价格和排障口径清晰。
分组类型 个人分组按账号并发直接调度；高并发分组启用短队列、单账户软阈值和可选单 IP 并发限制。 个人自用选个人分组；共享 API Key 或高 QPS 场景选高并发分组。
说明 仅用于后台识别分组用途。 建议写清账号来源、使用方和是否允许生产流量。
状态 停用后分组不会继续承接 API Key 调度请求。 维护账号池或临时排除整组账号时使用。

个人分组和高并发分组

个人分组

适合低并发、个人使用、少量账号兜底。它更强调稳定、简单和可预测。

  • 账号少，调用量不高。
  • 希望会话尽量稳定命中同类账号。
  • 主要靠账号优先级、超级优先、备用和并发上限控制。

高并发分组

适合同一个 API Key 被多人、脚本或服务大量并发调用。它更强调减少排队等待。

  • 避免大量请求堆到同一个账号。
  • 账号软满或变慢后，新请求优先尝试更空闲账号。
  • 所有账号都硬满时，在分组短队列等待一段时间，超时返回 429。

高并发怎么分配请求

看图理解：“最大单账户排队阈值”是软分流点，“并发上限”是硬上限，“最大等待时间”决定短队列最多等多久。

高并发配置项

配置项 用户看到的含义 配置建议
最大单账户排队阈值 某个账号当前承接请求达到该值后，新请求优先切到其他账号；实际不会超过账号自己的并发上限。 默认 5 比较稳。账号很多且希望更均匀可调低；账号少且希望减少切换可调高。
最大等待时间 所有账户硬并发都满时，请求最多在分组短队列等待多久，超时后返回 429。 交互场景建议短一些，后台批处理可以适当长一些。
限制单 IP 并发 限制同一个 IP 在当前分组和 API Key 下同时占用的请求数。 多人共用同一出口 IP 时谨慎开启；主要用于防止单个来源占满分组容量。
单 IP 并发上限 开启限制后，同一 IP 同时允许多少请求进入分组调度。 默认 5；如果客户端本身会并发较多，可按真实并发需求调整。
超过限制时 “立即拒绝”会返回 429；“排队等待”会先等同 IP 请求释放，再进入分组调度。 面向实时用户选立即拒绝更清晰；后台任务可选择排队等待。
高并发分组不是无限扩容。账号自己的并发上限、状态、模型支持、授权和额度仍然是硬约束。高并发配置只能帮助更合理地分配等待和选号。

AI 账户

AI 账户是真实上游资源。这里配置的是上游凭据、Base URL、支持模型、并发上限、调度优先级、代理、错误处理和时间可用性。

基础配置

配置项 作用 使用说明
供应商 / 接入类型 决定后续表单、测试方式和可选模型范围。 先选真实上游类型，再填对应凭据。不要为了路由目的选择不匹配的供应商。
账户名称 后台识别账号。 建议写清供应商、用途、地区或套餐，例如“gpt-team-us-01”。OAuth 账户可留空自动取授权信息。
加入分组 决定这个账号放入哪个账号池。 账号必须进入分组后才能被策略路由使用。
并发上限 这个账号同一时间最多承接多少请求。 按上游套餐、账号能力和稳定性填写。高并发分组也不能突破这个硬上限。
优先级 分组内排序，小值优先，0 排在 1 前。 核心账号填较小值，普通账号填较大值。授权账号这里表示当前使用方本地分组内优先级。
账户标签 用于筛选和识别账号用途。 可按“生产”“测试”“低价”“高质量”“备用”等维度打标签。
说明 记录账号来源、限制、备注和维护信息。 建议写明套餐限制、负责人和特殊错误规则来源。

API Key 类型账户

配置项 说明 建议
API Key 真实上游密钥。支持单账号填多个上游 Key。 多个 Key 属于同一个 AI 账户池内子资源，适合上游给了多个同类 Key 的场景。
Key 轮询 多个上游 Key 按顺序轮换使用。 各 Key 能力接近时使用。
Key 权重 多个上游 Key 按权重分配。 不同 Key 额度或质量不同，想按比例消耗时使用。
Base URL 真实上游服务根地址或版本根地址。 不要填写具体接口路径，例如不要填 `/responses`、`/chat/completions`、`/messages`。
支持模型 声明这个 Base URL 实际支持的上游模型。 至少选择一个。模型映射右侧只能从这里选择。

OAuth 类型账户

OAuth 账户通过授权信息访问上游。重新授权只覆盖 OAuth Token，不会修改名称、分组、代理、并发或错误策略。

  • 支持模型仍需要声明，用于调度过滤和模型映射选择。
  • Access Token / Refresh Token 是敏感凭据，页面不会把它们当作普通说明文本展示。
  • 授权过期或刷新失败时，账号可能进入不可调度状态，需要重新授权或测试。

账户状态和操作

状态 / 标记 含义 处理方式
正常 账号可参与调度。 仍会受模型、并发、时间计划、代理和授权限制。
待检查 账号需要测试确认。 点击“测试”，确认凭据、Base URL 和模型可用后再用于生产。
停用 人工停用，不参与调度。 维护、换凭据或暂时不用时设置。
限流中 命中错误策略后按恢复策略暂停。 等待自动恢复，或确认上游已恢复后手动测试。
临时不可调用 系统恢复通道接管，稍后复测。 适合临时故障，不建议直接当成永久异常处理。
异常 账号被明确标记为异常。 检查凭据、代理、Base URL、模型和错误策略后再恢复。
超级优先 下次调度优先使用此账户。 适合短期把流量切到某个确认稳定的账号。
降级备用 仅在同分组其他可用账号都不可用或繁忙时使用。 适合成本较高、额度少或只做兜底的账号。

账户操作

账户列表里的操作会直接影响调度。不了解动作语义时，先用“测试”和“使用记录”确认，再执行停用、恢复、迁移或删除。

单个账户操作

操作 作用 什么时候用 注意事项
编辑 修改账号名称、分组、并发、优先级、凭据、模型、代理和高级策略。 新增模型、换 Base URL、调整并发、修改错误规则时使用。 更换 API Key 或 Base URL 后，先测试通过再保存到生产流量。
测试 用当前账号配置发起诊断请求。 新增账号、上游报错、代理变化、模型不通或恢复异常前使用。 测试结果可作为错误策略和响应检查规则的取样来源。
启用 / 停用 控制账号是否参与调度。 维护账号、临时下线、确认凭据错误或切走流量时使用。 待检查账户需要后台检查通过后才能参与调度。
恢复正常 清理异常、临时不可调用、限流或运行态避让。 确认上游已恢复，或错误策略误伤账号时使用。 恢复前建议先测试；否则可能恢复后又立即失败。
超级优先 让正常账号在下次调度中优先使用。 临时把流量切到确认稳定、速度快或额度充足的账号。 只有正常状态账号可以开启；高并发软满或硬满时仍可能分流。
降级备用 让账号平时不吃主流量，只在主池不可用或繁忙时兜底。 高成本账号、额度少账号、备用供应商账号适合设置。 备用不是禁用，主池不可承接时仍会使用。
迁移流量 把当前已识别且命中该账户的客户端会话短期迁到目标账户。 某个账号变慢、即将维护、需要让新请求优先切到另一个同分组可用账号。 不会打断正在输出的连接；目标不可用或不支持本次请求时仍按候选顺序降级。
刷新 OAuth 令牌 刷新 OAuth 账户令牌。 OAuth 账号令牌接近过期或刷新异常时使用。 只适用于支持 OAuth 管理的自有账户。
重新授权 重新走 OAuth 授权并覆盖 Token。 Refresh Token 失效、账号授权变化或需要重新绑定上游身份时使用。 不会修改名称、分组、代理、并发或错误策略。
克隆 基于现有账号配置创建新账号。 批量接入相同供应商、相同 Base URL、相同模型配置的账号。 克隆后仍要检查凭据、名称、分组和并发是否符合新账号。
删除 删除自有账号。 账号不再使用、凭据已废弃或清理测试数据时使用。 删除会影响绑定分组和后续调度；关联记录会按后台流程清理。
归还授权账户 从你的视图中移除被授权账户。 不再使用别人授权给你的账号时使用。 不影响授权方原账户。

迁移流量怎么选

迁移后原账户状态 含义 适用场景
不影响原账户 只把当前已识别的客户端会话迁到目标账户，不修改原账户状态。 想临时换会话命中，但不想影响新客户端正常调度。
临时不可调用 从下一次请求开始短期优先切到目标账户，原账户进入临时不可调用。 原账户短期不稳、变慢或上游维护，稍后可能恢复。
停用账户 迁移后把原账户停用。 确定原账户不应再承接流量，例如凭据风险、套餐到期或长期维护。

批量操作

操作 作用 建议
批量编辑 用同一组配置覆盖选中账号的非私有字段。 适合统一检查模型、调度、代理和错误策略；名称、分组、供应商、凭据与 Base URL 保持账户隔离。
批量恢复 对选中的异常或临时状态账号逐个恢复。 确认上游恢复后使用；不要盲目恢复未修复的异常账号。
批量启用 / 停用 批量切换账号参与调度状态。 适合维护窗口、切换账号池或清理一批不可用账号。
批量删除 删除选中的可删除账号。 删除前确认不是生产分组里仍在使用的账号。
批量操作会逐个执行，不代表同一瞬间全部成功。执行后刷新列表，确认每个账号状态和错误提示。

模型与上游接口能力

支持模型、模型别名和上游接口能力共同决定最终上游模型与协议是否匹配账号。很多“没有可用账号”都不是账号坏了，而是最终上游模型或接口形态没有匹配上。

支持模型

  • 支持模型表示这个真实上游账号能调用哪些模型。
  • 客户端请求的模型如果不在账号支持范围内，这个账号不会进入候选。
  • 如果你配置了模型别名，右侧目标模型必须来自支持模型。
  • 模型名建议使用上游真实模型名，避免大小写、后缀或别名混乱。

账号模型别名

字段 含义 使用场景
来源协议 / 来源模型 客户端请求里看到的接口类型和模型名。 客户端固定发 `gpt-4.1`，但上游真实模型叫其他名字时配置。
目标协议 / 目标模型 最终打到上游时使用的接口类型和模型名。 把客户端模型名改写成上游支持的真实模型。
启用开关 控制这条映射是否生效。 灰度测试新模型或临时停用别名时使用。
模型别名不是万能翻译器。普通账号主要用于当前供应商和当前接口范围内的模型名改写；如果页面允许选择更复杂的来源和目标组合，也必须确认映射右侧的目标模型和协议符合账号真实上游能力。

上游接口能力

上游接口能力只声明账号真实上游支持的接口形态。模型别名命中时按映射右侧的目标协议检查；未启用的最终上游接口形态不会进入该账号候选。

上游接口能力 真实上游要求
Chat Completions JSON / Streaming 真实上游使用 Chat Completions JSON / Streaming 时启用；Responses → Chat 映射按右侧 Chat 能力检查。
Responses API JSON / Streaming 真实上游原生提供 Responses JSON / Streaming 时启用；Responses → Chat 映射不要求原生 Responses 能力。
Messages API JSON / Streaming 真实上游使用 Anthropic Messages JSON / Streaming 时启用。
Count tokens / countTokens 真实上游提供对应 token 计数接口时启用。
generateContent / streamGenerateContent / embedContent 真实上游使用 Gemini native 对应接口时启用。

代理、到期和时间计划

配置项 作用 建议
代理 仅影响这个账号访问上游供应商时使用的代理。 不需要代理时留空；代理不可用会导致账号不可承接。
账户到期时间 超过这个时间后，账号不再参与调度。 套餐到期、临时账号或授权资源有明确期限时填写。
时间计划 按时间段控制账号可用性。 账号只在特定时段稳定、或需要避开高峰时使用。

错误与响应策略

错误策略处理“上游明确报错”；响应检查处理“上游返回成功状态但内容有问题”。两者都建议先观察和取样，再正式拦截或切号。

账号错误处理策略

字段 作用 说明
规则名称 识别这条规则。 建议写具体原因，例如“429 临时限流”“额度不足”。
优先级 小值先匹配，多条命中时执行最靠前规则。 更精确、更严重的规则放前面。
状态码 匹配上游 HTTP 状态码。 例如 `429, 502, 503`，只填数字。
错误码 匹配响应体里的 `error.code` 或根级 `code`。 适合稳定机器码，例如 `insufficient_quota`。
错误类型 匹配 `error.type` 或根级 `type`。 用于区分同一状态码下的不同语义。
关键词 匹配错误消息文本中的关键词。 适合上游没有稳定机器码，只能看错误文本的场景。
处理动作 命中规则后对本次请求和账号状态做什么处理。 先用“只切号”验证规则，再使用限流、临时不可调用或异常。
恢复策略 限流后什么时候自动恢复候选。 支持固定时长、每天固定时间、每周固定时间。

处理动作怎么选

动作 含义 适用场景
只切号 本次请求切到下一个账号，不改变账号状态。 不确定错误是否稳定时优先使用。
限流 按恢复策略暂停账号，到期后自动恢复。 上游明确返回 rate limit、quota reset、每日限额等。
临时不可调用 进入系统恢复通道，到期后由后台复测恢复。 临时 5xx、连接异常、账号短期不稳定。
异常 显式把账号置为异常。 凭据失效、账号被封、配置错误等需要人工修复的问题。

响应检查策略

响应检查用于识别“HTTP 成功，但内容不可接受”的情况，例如固定广告、污染文本、异常 JSON 字段、SSE 中某类事件或错误字段。

配置项 说明
规则名称 / 优先级 用于识别和排序，优先级小值先匹配。
输出文本包含 / 排除 匹配模型输出文本。包含用于识别异常内容，排除用于缩小误命中。
error.code / error.type / 错误消息 匹配响应中的错误字段，适合上游把错误包装在成功响应里。
完成原因 / 状态 匹配 finish reason 或类似状态字段。
JSON 字段路径存在 某个 JSON 字段出现就命中，适合结构化异常。
SSE 事件原文包含 匹配流式事件原文，适合流式响应里的异常事件。
处置模板 可先观察命中，也可丢弃事件、重试、避开当前账号或短期避让上游桶。
写策略前先取样：从“我的使用记录”找到失败请求，复制 traceId，再看上游状态码、响应体、错误摘要和账号测试结果。不要凭猜测写关键词，避免误伤正常响应。

授权资源

被授权的 AI 账户或分组是“可使用资源”，不是你的原始凭据副本。你可以在自己的范围内使用或绑定，但不能看到来源账号的真实凭据。

你收到授权时

  • 被授权账户需要绑定到你的分组后，才会进入你的调度链路。
  • 授权账户的优先级、超级优先和降级备用可以按你的分组本地配置，不影响授权方原账户。
  • 来源账户停用、到期、异常、授权失效或授权额度耗尽时，被授权资源也不能继续承接请求。
  • 不再使用某个授权资源时，可以执行归还；归还不删除授权方原资源。
  • 排查授权资源失败时，先看授权状态、额度、来源账户状态，再看自己的分组绑定。

你创建授权时

配置项 说明 使用建议
授权资源类型 选择授权 AI 账户或分组。 只想给对方使用某个账号时选账户；想给一组账号池能力时选分组。
授权资源 选择你自己拥有的账户或分组。 只能授权自己拥有的资源，不能把别人授权给你的资源继续授权出去。
授权对象 选择个人或团队。 个人适合明确的单个用户；团队适合一组成员统一使用。
目标分组 账户授权时，可让被授权方绑定到指定分组。 确保目标分组的供应商和使用场景匹配。
说明 记录授权目的和约束。 建议写清用途、期限、联系人和额度约定。
到期时间 到期后授权自动变为授权到期。 临时项目和测试授权建议设置，到期时间不能晚于账户到期时间。

授权状态和操作

操作 作用 注意事项
暂停 / 恢复 临时停止或恢复授权使用。 暂停不会删除授权记录，恢复后仍受资源状态和额度限制。
修改到期时间 延长、缩短或清空自动回收时间。 到期时间不能早于当前时间，也不能晚于来源账户到期时间。
回收授权 授权方收回资源使用权。 回收后被授权人不能继续使用该资源，授权记录会保留。
归还授权 被授权方主动放弃该资源。 只影响自己，不影响授权方原资源。

记录与观测

排障不要只看客户端报错。一次请求至少要看 API Key、策略路由、分组、命中账号、上游状态、耗时、Token 和 traceId。

页面 / 工具 能解决的问题 看什么字段
我的使用记录 确认请求是否进入系统、命中哪个账号、为什么失败或耗时高。 traceId、API Key、分组、账号、模型、状态码、错误摘要、耗时、Token、成本。
账号测试 确认某个账号的凭据、Base URL、代理、模型和上游接口能力是否可用。 测试接口、状态码、错误码、错误消息、响应耗时、Key 池结果。
模型检测 检查账号对某个模型或接口形态的真实表现。 检测历史、终端输出、失败原因、模型能力差异。
我的用量 / 统计 看 API Key、账号或模型的消耗趋势。 Token、成本、请求数、失败数、时间范围和资源筛选。

使用记录筛选

筛选项 用途 建议
时间范围 限定查询窗口。 排障先选问题发生前后的小窗口，避免结果过多。
请求结果 筛成功、失败或全部。 排障先看失败，再对比同时间段成功请求命中了哪些账号。
分组 定位问题是否集中在某个账号池。 高并发 429 或无可用账号时优先按分组筛。
状态码 查某类上游或本地错误。 例如查 429、500、502、503，再决定错误策略。
traceId 精确定位一次请求。 客户端报错或日志里拿到 traceId 后，优先用它查。
模型 看问题是否只出现在某个请求模型。 模型不存在、映射错误、能力不匹配时非常有用。
IP 看是否某个客户端来源集中触发错误或并发限制。 单 IP 并发保护、共享出口和异常客户端排查时使用。
请求来源 区分不同入口或调用来源。 用于判断问题是否只来自某类客户端或公开接口。

模型检测怎么用

  • 先选择 AI 账户，再选择该账户支持的完整模型 ID。
  • 默认使用快速检测做初步筛查；需要更高准确度时再开启“深度检测”。
  • 不要用模型检测代替真实业务请求；它用于确认模型能力和账号表现。
  • 可信对比只在深度检测中可用，且对比账户不能和检测目标相同。
  • 检测结果里的检测 ID、Trace ID、耗时、证据完整度和结论可用于后续排障。

请求流转

理解流转后，排障时就能知道该查哪一层。

客户端 API Key 策略路由 分组 AI 账户 真实上游 使用记录
客户端请求 客户端使用本系统 Base URL，并携带本地 API Key。
API Key 校验 检查密钥状态、额度、过期时间、时间计划和系统账户状态。
策略路由 按路由模式选择候选分组，例如普通、权重、回退或轮询。
分组选号 在分组内按模型能力、状态、并发、优先级和运行态选择账户。
请求上游 命中的 AI 账户使用自己的凭据、代理和模型配置访问真实上游。
响应处理 检查响应语义、处理流式返回、记录命中账号和错误信息。
统计审计 使用记录、成本、Token、耗时和审计信息进入后台处理。
返回客户端 客户端看到兼容协议格式的成功响应或可读错误。

排障清单

提示没有可用账号

按顺序查：API Key 是否启用，策略路由是否启用，绑定分组是否启用，分组内账号是否正常，最终上游模型和上游接口能力是否匹配，并发是否已满，代理是否可用。

请求走到不符合预期的账号

检查策略路由模式、分组顺序或权重、账号优先级、超级优先、降级备用、高并发软阈值和速度优先降级。

高并发时返回 429

看是 API Key 额度、单 IP 并发、分组短队列超时、所有账号硬并发满，还是没有可调度账号。必要时增加账号、提高账号并发或调整等待时间。

上游 429 或限额错误

从使用记录或账号测试拿到状态码和错误码，再在账号错误策略里配置限流恢复。不要直接把所有 429 都设置为异常。

模型不支持

检查客户端请求模型、账号支持模型、模型别名、上游接口能力和策略路由目标分组。模型名大小写和后缀也要一致。

响应内容异常

如果 HTTP 成功但内容有广告、污染文本或错误字段，先配置响应检查为“先观察命中”，确认样本后再改成重试或避让。

请求很慢

看使用记录中的总耗时和首段等待，再检查账号并发、代理、上游状态、普通路由速度优先配置或高并发分组阈值。

授权资源不可用

检查授权是否过期、授权额度是否用完、来源账户是否到期或停用，以及你自己的授权账户是否已绑定到可用分组。

排障顺序建议固定为：先找 traceId，再看 API Key，再看策略路由和分组，再看命中账号和上游错误，最后才调整复杂策略。
本手册只解释页面可见、可配置、可排障的内容，不展示任何账号凭据、Token 或 API Key 明文。
