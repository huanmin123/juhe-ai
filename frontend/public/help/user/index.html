先建立整体认知

产品概述：一个可控的 OpenAI 兼容入口

这一章回答三个问题：juhe-ai 是什么、它解决什么问题、边界在哪里。后面每一章都在展开这个图景的某一部分。

juhe-ai 是一个 OpenAI 兼容的中转与账号调度系统。它把手中的 AI 账号（OpenAI OAuth 账号或 OpenAI API Key 账号）收敛成一个统一入口：客户端只需要配置一次本系统的地址和一把本地 API Key，此后长期不再改动；后台账号的新增、下线、故障切换和额度控制全部在系统内完成，对客户端透明。

把账号交给 juhe-ai 之后，你得到三件事：

  1. 统一入口。客户端只面对一个 OpenAI 兼容端点（支持根路径或 /v1）。上游账号怎么换、分组怎么调，客户端配置不变；客户端持有的本地 API Key 也不携带任何上游凭据。
  2. 池化与调度。多个账号组成分组的账户池。系统在池内按优先级、并发硬上限、排队与等待规则自动选号；某个账号限流或异常时，同池其他账号自动接住请求，客户端不需要更换地址重试。
  3. 控制与观测。每把 API Key 都有运行状态、过期时间、美元额度（“n 小时美元额度”）和时间计划；每次调用产生使用记录，并沉淀为统计、用量、AI 健康、AI 性能等记录页，任何一个请求都能回答“用了什么、花了多少、为什么失败”。

适合谁

手里有多个 OpenAI 账号、需要给一个或多个客户端（SDK、IDE 插件、自动化脚本）长期稳定提供 OpenAI 兼容服务，并希望额度可控、使用可审计的个人或小团队。

产品边界

  • 它不是训练或微调平台，也不承载非生成类服务；它只做中转、调度、控制与记录。
  • 配置不能虚构上游能力：账户声明的模型与协议能力必须与真实上游一致，系统不会把上游不支持的能力“配置”出来。
  • 跨协议转换受真实协议档案约束：普通账户只表达自身真实上游协议（OpenAI v1 档案可显式声明 responses -> chat_completions 别名）；其余跨协议转换属于混合供应商账户能力，不是 API Key 或路由策略上的开关。

为什么是这五层

核心概念：一次请求经过五层

每一层只决定一件事。分层不是为了复杂，而是把“谁在调用、怎么选池、拿什么账号调上游”解耦开，改任何一层都不牵动其他层。

从客户端到真实上游，请求依次经过五层。点选下方步骤查看每层决定的单件事；前四层也可以直接打开对应配置页。

API Key 决定“谁在调用、还允许调用多少”。它只绑定一套策略路由；额度、过期时间和时间计划在这里生效。下一步：确认它绑定的是预期策略。
策略路由决定“请求采用哪种选组方式”。普通策略只有一个分组；权重、回退、轮询和合并才会处理多个分组。下一步：检查模式与分组顺序。
分组决定“账户池的供应商边界和排队规则”。一个分组只接纳同一供应商的账户。下一步：确认目标账户已加入此分组并且分组启用。
AI 账户决定“实际拿什么凭据、协议和模型去调上游”。检查通过、active、schedulable、未到期且运行态可用的账户才会进入候选。下一步：核对状态、模型、Base URL 和账户并发。
上游才是最终处理请求的一方。模型名、协议能力和错误语义必须以这里的真实能力为准；配置页不能把上游不支持的能力变出来。

分层带来了什么

身份与凭据分离客户端只持有本地 API Key，上游凭据永远不会离开系统。Key 泄露时停用这一把 Key 即可，上游账号本身不受影响。
规则复用多把 API Key 可以共享同一套策略路由；调整策略一次，所有绑定它的 Key 同时生效。也因为这个原因，改共享策略前要想清楚影响面。
供应商边界分组固定所属供应商，账户池不会混入协议不同的账户。排队、并发和故障语义都在同一协议边界内讨论，不存在隐式跨协议混排。
故障隔离账号故障在分组池内消化：候选筛选排除不可用账户，调度切到其他账号。身份层（API Key）和规则层（策略）不因单个账号异常而改变。

常见误解

API Key 不是账号Key 不保存凭据，也不直接指向某个 AI 账户；它只绑定一套策略路由。停用一把 Key 不会动到账号，删除账号也不会让 Key 失效。
策略里不存模型与凭据策略只保存“怎么选分组”的规则；模型映射和上游凭据都在账户层维护。想让某些 Key 只用特定模型，应通过分组与账户的支持模型控制，而不是在策略里配模型。
分组有供应商边界一个分组只接纳同一供应商的账户。跨供应商共享一个池不是配置技巧问题，而是架构上不存在的边界。
AI 问答不替代客户端 API Key站内 AI 问答使用系统维护的专属对话 Key，走与客户端相同的网关链路；它用于站内对话，不是客户端 Key 的验证入口。

机制视角

一次请求的完整旅程

从客户端发出请求到收到响应，网关按固定顺序经过八个阶段。理解这个顺序，排障时才能回答“请求到底停在哪一步”。

  1. 阶段 1 · 客户端发起。客户端（SDK、IDE 插件或脚本）按 OpenAI 兼容格式向本系统端点（根路径或 /v1）发起请求，请求头携带本地 API Key。从这一刻起，客户端不再关心、也无法指定实际使用哪个上游账号。证据：这次调用最终会出现在使用记录。
  2. 阶段 2 · 网关鉴权。网关先验证这把 API Key：运行状态必须是 active、未过过期时间、未超出美元额度、当前时间命中时间计划，同时还受用户级请求限制（同一用户跨所有 Key 的每分钟/日/周/月请求数）约束。任何一项不满足，请求在此终止：无效或停用的 Key 返回 401，额度用尽返回 429。证据：API Key 页面的运行状态、过期时间与美元额度。
  3. 阶段 3 · 策略选组。通过鉴权后，网关读取 Key 绑定的策略路由，按模式决定请求进入哪个分组：普通进入唯一启用分组；权重按比例分流；故障回退主用优先、备用兜底；轮询按排列顺序轮换；合并把所有绑定分组的账号合成一个池统一调度。证据：策略路由页面的模式与分组绑定。
  4. 阶段 4 · 候选筛选。进入分组后，不是所有账户都能承接这次请求。账户必须同时满足：配置状态 active、调度开关 schedulable 开启、未到期、命中账户时间计划（如有）、支持请求的模型（直接支持或命中账号模型别名）、上游接口能力覆盖本次请求形态、授权来源可用。任何一项不满足，该账户在本轮被排除。证据：AI 健康的检查结果与可调度状态。
  5. 阶段 5 · 组内调度。在候选账户中选出一个承接者：优先级小值优先；super_priority 超级优先账户排前，fallback 降级备用垫后；并发硬上限决定账户是否还有余量。高并发分组还会启用短队列与最大单账户排队阈值：所有账户占满时按最大等待时间排队，超时返回 429。证据：分组页面的并发与排队配置，以及使用记录中实际命中的账户。
  6. 阶段 6 · 上游调用。网关按账户的协议档案准备真实上游请求：账号模型别名改写上游模型名与允许的端点形态，必要时执行协议适配（如 responses -> chat_completions）；代理只影响账户到上游的网络路径；流式请求按 SSE 增量转发。证据：使用记录中的模型、耗时与状态。
  7. 阶段 7 · 结果计量。上游返回后，网关解析 usage 与计费并写入使用记录；这次结果同时成为健康与性能信号：失败进入最近错误与质量信号（账户状态变更仍由后台检查与恢复机制维护），耗时与首字样本进入性能统计。证据：使用记录、AI 健康、AI 性能。
  8. 阶段 8 · 响应返回。网关把响应按 OpenAI 兼容结构返回客户端；上游错误保留实际状态码与错误码，不做静默改写。客户端发起的重试是一条新请求，会重新经过全部八个阶段。证据：使用记录中该次调用的最终状态与成本。

从创建到承载流量

AI 账户的生命周期

账户状态不是“好/坏”两个值，而是一组有明确进入与离开条件的事实。理解状态，才能回答“为什么这个账户没有被调度”。

新建或导入的可启用账户一律先以 pending_test 创建，由后台激活检查确认“模型可用、凭据正确、协议匹配”后进入 active；人工测试结果不作为激活凭证。运行中的账户可能因故障、限流、质量问题或异常处置进入对应的运行状态；停用是人工动作，与运行状态无关。

  1. pending_test（待检查）：新建、导入或刚修改关键连接配置的账户等待后台检查；检查通过进入 active。明确接受上游可用性风险时，也可以通过“恢复正常”入口强确认放行（不适用于授权实例或已过期账户）。
  2. active（正常）：检查通过后的常态。active 是进入候选的必要条件，不保证当前一定可调度；还要同时满足 schedulable、未到期、时间计划、授权来源和运行态可用。
  3. temporary_unavailable（临时不可调用）：后台健康检测确认临时故障后进入；它是有界暂停而不是停用，恢复探针成功后回到 active。
  4. rate_limited（限流中）：真实上游账号触发限流策略后进入；复测成功后恢复。
  5. quality_isolated（质量隔离）：质量问题触发隔离后进入；复测通过后恢复。
  6. error（异常）：异常处置后的硬状态，不参与调度；排除原因后重新检查或恢复。
  7. disabled（停用）：人工停用，可以从任意状态进入；重新启用后按当前事实重新检查。
四种运行状态（temporary_unavailable、rate_limited、quality_isolated、error）是分叉，不是依次迁移：它们各自从 active 直接进入，也各自通过恢复或复测成功直接回到 active，不存在“先限流、再隔离、最后异常”的固定顺序。

检查机制：状态变化的依据

后台检查执行真实协议请求，用账户配置的检查模型验证链路。检查模型的选择原则：先选择确实被支持模型覆盖的模型，再把检查结果当作激活依据。凭据、Base URL、协议档案或关键代理等连接配置变更保存后，账户会重新交给后台复检。人工测试与模型检测是证据来源——它们区分模型不支持、上游拒绝、凭据或协议问题，但不直接改写状态；状态只由后台检查与恢复机制维护。

能力从事实中来

模型与协议的真实边界

客户端看到哪些模型、一次请求能否被承接，由“目录 + 账户支持模型 + 上游接口能力”共同决定。配置只能声明事实，不能发明能力。

可用模型从哪来

客户端请求模型列表（/models 或 /v1/models）时，网关按这把 API Key 绑定策略的启用分组合集聚合本地模型目录；站内AI 问答的模型列表也来自同一目录。而一次生成请求能否落到某个账户，取决于该账户的支持模型：请求模型被账户支持模型覆盖，或命中该账户的账号模型别名映射，这个账户才会进入候选。

账号模型别名：映射的边界

账号模型别名把“客户端协议与模型”映射到“上游协议与模型”。映射的右侧目标必须同时满足两个条件：在账户支持模型范围内，且被上游接口能力覆盖。普通账户的跨协议映射受实际协议档案限制：OpenAI v1 档案允许显式声明 responses -> chat_completions，让 Chat-only 上游承接 Responses 请求；其余跨协议、跨供应商的转换属于混合供应商账户能力，不在普通账户或路由策略里配置。

一条原则：配置不虚构上游

上游接口能力声明的是真实上游能接收的请求形态（JSON 或流式）；没有勾选的协议请求不会把该账户加入候选。支持模型、检查模型与别名目标都必须来自账户真实可用的范围——配置页不能把上游不支持的协议或模型“变出来”，检查会如实失败，而不是被绕过。

我的模型查看当前可用模型与映射；看不到预期模型时，先回到账户支持模型与分组配置检查。我的 AI 账户维护账户的支持模型、上游接口能力与账号模型别名。

按目标找操作

任务指南

四个常见任务：从零接入、批量迁移、日常使用、按症状排障。每个操作都回到前面章节的机制，知道为什么再做。

5.1 从零到第一次调用

  1. 新建分组。在我的分组确定供应商边界并选择分组类型：个人分组适合稳定低并发调用，高并发分组面向共享程序流量。先建分组，账户的“加入分组”下拉才会显示正确的候选。
  2. 添加或导入 AI 账户。在我的 AI 账户逐个填写凭据、Base URL、支持模型与上游接口能力，或按 5.2 批量导入。新账户以 pending_test 创建，此时还不能承接流量。
  3. 完成检查并设为可调度。在模型检测或账户检查确认“模型可用、凭据正确、协议匹配”，等待后台激活检查通过，并确认账户的调度开关已开启。
  4. 建立策略路由。在我的策略路由选择分组选择规则：只有一个分组时用普通模式；确实需要多分组分流或容错时，再使用权重、故障回退、轮询或合并。
  5. 建立 API Key。在我的 API Key绑定策略，按需设置美元额度、过期时间和时间计划；创建完成立即复制完整密钥，之后列表与日志不再展示明文。
  6. 客户端接入。把网关地址（根路径或 /v1）、完整 API Key 和模型名写入实际客户端；发出第一次真实调用后，到使用记录确认该次调用成功，再逐步放量。

5.2 批量导入存量账号

导入只帮你把结构化资料变成待检查账户，不会替你确认凭据真实可用。

  1. 在我的 AI 账户打开导入。普通用户只导入到自己名下；管理员可在管理账户页选择目标系统账户导入。
  2. 只粘贴 juhe-ai-account-import v1 JSON，不要粘贴 Markdown 代码块或 CSV。
  3. 先做“解析预览”，逐项处理协议档案、分组、代理引用和重复项提示。
  4. 确认导入后，不存在的分组可以按选项自动创建；同名账户可跳过。
单次请求上限约 256KB，最多 50 个账户，最多 20 个代理。普通用户不能创建新代理。即使来源写了 active，导入账户仍会以 pending_test 创建，检查通过后才可参与调度。

请根据我附上的《juhe-ai AI 账户导入协议 v1》Markdown，把下面账号数据转换为 juhe-ai-account-import v1 JSON。

要求：
1. 只输出合法 JSON，不要输出解释、Markdown 代码块或注释。
2. 顶层 type 固定为 juhe-ai-account-import，version 固定为数字 1。
3. 每个账户显式填写 name、providerCode、providerProtocolProfileId、type、status、credentials，以及 groupName 或 groupId。

5. providerProtocolProfileId 是协议档案唯一入口；不要从 base_url 或旧字段猜测档案。

7. 不确定信息放到 notes；不能判断立即可调度时 status 填 pending_test 或 disabled。

5.3 日常使用：对话、对账与授权

站内对话。AI 问答是登录用户的站内对话入口，使用系统维护的专属对话 Key，走与客户端相同的网关链路；它不替代客户端 API Key，客户端接入是否正常，以真实客户端的调用与使用记录为准。

用量对账。我的统计看自己的请求、令牌和费用总体趋势；用量统计按时间、账户与模型汇总令牌和费用，适合周期对账；使用记录定位单笔调用的账户、状态与成本。

授权与团队。授权只传递使用权，不改变资源归属。我的授权查看或管理自己可用、已发放的授权资源及其状态；我的团队查看团队成员和协作范围；团队消耗按授权团队汇总用量，用户消耗按用户核对授权用量，两者合起来覆盖团队配额对账与分配归属核对。

5.4 按症状排障

排障从证据开始：先确认请求停在第 2 章的哪个阶段，再只修改能解释当前证据的配置。

401 / 额度 / 时间边界

先看证据：API Key 的运行状态、过期时间、美元额度与时间计划。

可能原因：Key 已停用或过期；n 小时美元额度已用完（返回 429）；当前时间未命中时间计划窗口；用户级请求限制达到上限。

处置：调整额度或时间计划，或等待额度周期与时间窗口刷新后重试。

模型不存在或不支持

先看证据：客户端请求的模型名；我的模型中的可用列表。

可能原因：模型名拼写或版本不符；候选账户的支持模型未覆盖该模型；别名映射目标失效；上游接口能力未覆盖该请求形态。

处置：改用目录中可见的模型，或回到账户支持模型与账号模型别名配置修正。

没有可调度账户

先看证据：AI 健康的检查结果与可调度状态；策略绑定的分组是否启用。

可能原因：分组停用或池内没有账户；账户不满足 active、schedulable、未到期、时间计划、授权来源或运行态中的某一项。

处置：按候选条件逐项核对恢复；新账户先完成检查再承接流量。

分流结果不符

先看证据：使用记录中实际命中的分组与账户；策略路由的模式、顺序与权重。

可能原因：Key 绑定了非预期策略；对回退、轮询或权重语义的理解偏差；账户优先级影响组内选择顺序。

处置：先核对 Key 绑定；调整共享策略前确认所有绑定它的 Key 都能接受这次变化。

慢或偶发失败

先看证据：使用记录的耗时与状态；AI 性能按账户/模型看趋势。

可能原因：单次上游波动；个别账户持续变慢；高并发分组的排队等待。

处置：不要用一条慢记录调整全局配置；先缩小范围确认是普遍现象还是个别账户，再针对性处理。

配置被改

先看证据：操作日志中谁、何时、对哪类资源执行了写入。

可能原因：自己或协作成员的变更；共享策略被修改，影响所有绑定它的 Key。

处置：按日志恢复原值；需要不同规则时新建同配置策略，再绑定新的 API Key。

字段级参考

配置参考：填什么，为什么

这一章是参考层：每个条目写清楚作用、实际影响和常见误用。机制背景见前面章节。

AI 分组建立账户池与供应商边界先选供应商，再定个人/高并发
分组名称
给人识别用途，不参与调度。名称应写清使用方或场景，例如“研发共享 OpenAI”。
所属供应商
决定可加入的账户范围。分组保存 providerCode；换供应商不是改个标签，会改变账户候选边界。
个人分组
适合个人或稳定低并发调用。按账户并发直接调度，没有额外短队列策略。
高并发分组
适合共享程序流量；会启用短队列、单账户软阈值和可选的单 IP 并发限制。
最大单账户排队阈值
高并发模式才出现。到达阈值后优先选择其他账户，实际值不会高于该账户的硬并发上限。
最大等待时间
所有账户硬并发都满时允许在分组内等多久；超时返回 429。它不是上游响应超时。
限制单 IP 并发
关闭时不限制。开启后按“当前分组 + API Key + IP”限制同时占用数；超过时可立即拒绝或进入等待。
启用状态
停用分组后，绑定它的策略不会继续将请求调度到这个账户池。

先建分组再建账户的原因：账户的“加入分组”下拉只显示同一供应商的分组，避免把协议边界配乱。

AI 账户声明真实上游与可调度条件凭据、模型、并发和状态都在此层
账户名称 / 加入分组
名称用于定位；分组决定它能被哪一个账户池选择。账户的供应商必须和分组一致。
并发上限
这个账户同时承接请求的硬上限。达到后调度器会等待或尝试其他可用账户。
优先级
同一分组内小值优先，0 比 1 更靠前。它不替代策略层的分组顺序。
特权
super_priority 表示超级优先，fallback 表示降级备用；只在确实需要固定调度角色时使用。
状态
active 是进入候选的必要条件，不保证当前一定可调度；还要满足 schedulable、未到期、时间计划、授权来源和运行态均可用。pending_test 等待检查，disabled 人工停用。
API Key / 多 Key
多个 Key 可轮询或按 1-100 权重轮询；多 Key 账户不支持余额查询，保存后会自动关闭余额查询。
Base URL
填写服务根或版本根，例如 https://api.openai.com/v1；不要填 /responses、/chat/completions、/messages 这类具体接口。
支持模型
声明此 Base URL 真正可用的模型，既用于候选过滤，也是别名右侧可选模型的边界。至少选择一个。
检查模型
用来验证账户链路；先选择确实被支持模型覆盖的模型，再把检查结果当作激活依据。
上游接口能力
声明真实上游能接收的请求形态。没有勾选的协议请求不会把此账户加入候选；不能用它虚构上游能力。
账号模型别名
把“客户端协议/模型”映射到“上游协议/模型”。右侧目标必须同时满足账户支持模型和上游接口能力；普通账户的跨协议映射受实际档案限制。
代理
只影响该账户访问上游的网络路径；不会改变客户端访问本系统的地址。
服务等级 / 思考级别
只在已选模型声明支持时可用；不支持时应清空或改选模型，不能强制覆盖。

新建或导入后，先在 模型检测 / 账户检查确认“模型可用、凭据正确、协议匹配”，再将账户用于真实流量。

策略路由定义 API Key 选择分组的规则API Key 只认识策略，不直接认识账户
普通只能绑定一个启用分组，请求直接进入这个分组的账号池。
权重至少两个启用分组，按分组权重比例分流；总权重不能超过 100。
故障回退第一行是主用分组，后续是备用分组；主用恢复后仍会优先主用。
轮询至少两个启用分组，按当前排列顺序依次调度；拖动顺序会改变下一个选择次序。
合并至少两个启用分组，把所有绑定分组的账号合并成一个大池统一调度，不区分分组；拖动顺序仅决定调度平局时的基础先后。
调度偏好普通、权重、故障回退、轮询和合并五种模式共享，作用于请求所落分组内的账号调度。选“成本优先”时尽量保留当前账户缓存和会话粘黏；“速度优先”只对可重放文本观察首字慢样本，图像和副作用请求不使用这套切换。
名称 / 说明
只用于后台识别。名称建议带用途，避免在多个 API Key 之间误选共享策略。
状态
停用后，绑定该策略的 API Key 不再通过它进入分组调度。
首字截止与慢速参数
只在速度优先出现。首字截止、慢速触发次数、窗口期、恢复次数、探针间隔和降级租约一起决定“何时确认慢、何时恢复”。
分组绑定
分组是策略的唯一调度目标。修改共享策略会影响所有绑定它的 API Key；需要复制配置时，应新建同配置策略再绑定新 API Key。
API Key把调用身份接到一套策略完整密钥只在创建/刷新时展示
名称
只用于人识别；默认 API Key 和 AI 对话 API Key 的名称不可修改。
策略路由
API Key 只绑定策略路由。分组、模型和供应商选择逻辑都在策略中维护。
运行状态
只有 active 会接受调用。设置时间计划后，保存与计划边界都会直接更新这个状态。
过期时间
到达时间后不再可用；它是绝对时间边界，不受时间计划替代。
美元额度
“n 小时美元额度”可按 n 小时、每日、每周、每月设置美元上限；未开启的项目不限制。它约束的是该 Key 的调用额度。
时间计划
开启后，只在选定星期与开始/结束时间内参与调度；未命中窗口会被暂时跳过。多个窗口用于工作日/时段组合。
说明
仅作后台标记，不参与路由、额度或权限判断。

创建完成立即复制完整密钥到客户端安全配置；之后列表和日志不会再次给出完整明文。
