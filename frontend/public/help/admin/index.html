先建立整体认知

管理视角的全局：九类资源与治理原则

管理模式下的每一次保存，作用的都不是"我的配置"，而是系统范围的事实。这一章回答三个问题：管理员管理哪几类资源、每类资源的影响半径有多大、变更时用什么原则约束自己。后面每一章都在展开其中一类资源的细节。

管理员在系统里的位置。普通用户管理的是"自己名下"的资源；管理员管理的是系统范围的事实——供应商、协议档案、代理、分组、AI 账户、策略路由、API Key、授权与系统设置九类资源，并能查看全部使用记录、健康证据与日志。管理角色也可切回用户模式查看自己的资源；这里的写入会作用于所选目标系统账户或全局配置，先确认范围再保存。

九类资源与各自的影响半径

供应商
账号池、模型目录和价格目录的归属边界。调整供应商语义会影响名下全部账户的目录、计价与测试方式。
协议档案
把供应商和协议版本绑定成账户能力档案：决定账户表单、凭据类型、端点族与检查请求形态。改档案等于改一类账户的接入契约。
代理
服务器级全局运维资源，决定账户到上游的网络路径。停用或删除会立即影响所有绑定它的账户。
分组
账户集合与供应商过滤边界。停用分组或调整成员，会改变所有经策略绑定它的 API Key 的候选池。
AI 账户
真实上游凭据、模型能力、并发与运行状态。停用或异常会让所在分组少一个候选，影响每一次可能选中它的调用。
策略路由
分组选择规则：模式、顺序、权重与调度偏好。它被多把 API Key 共享，一处修改同时改变全部绑定方的行为。
API Key
调用身份、额度与时间边界。影响半径最小：只决定一个调用方能否进入网关。
授权
把账户或分组的使用权授予其他系统账户或团队。影响被授权方的可用资源与用量归属，不改变资源所有权。
系统设置
网关限流、后台任务、超时与保留期等全局运行策略。影响半径最大：保存即作用于全部用户与全部请求路径。

三条治理原则

  1. 先理解影响半径，再改配置。任何写入前先回答：这次改动落在九类资源中的哪一类、会影响谁。影响半径越大的资源（策略、分组、系统设置），越要用"新建副本再切换"而不是就地修改。
  2. 用事实验证变更，而不是只看保存成功。保存成功只说明写入成功。变更是否达到目的，要看使用记录中的实际链路、AI 健康中的检查与恢复、操作日志中的变更时间线。
  3. 警惕共享资源的多米诺效应。策略、分组与系统设置天然被多个对象共享：改一处限流会影响全部用户，改一个共享策略会影响绑定它的所有 API Key。共享资源的变更要在低峰期做、小步做，并保留回退路径。

管理前的预检

管理模式改的是系统范围事实

从基础资源到调用入口，管理动作存在一条最小顺序：供应商 / 代理 → 分组 / 账户 → 策略 → API Key。按顺序建、按顺序验证，避免入口建好了却调度不到账户。

先看写入影响。点选下方节点查看每一层被改动时会立即改变什么；图中节点可直接打开对应管理页面。

改 API Key 会立即改变某个调用身份可否进入网关。先核对目标系统账户、绑定策略、状态、额度、有效期和时间计划；它不会直接指定上游账户。
改策略会同时影响所有绑定它的 API Key。保存前在策略列表核对引用计数；需要不同规则时新建同配置策略，再把新 Key 绑定过去。
改分组会改变账户候选集合。分组会保存 providerCode，它既是账户集合，也是供应商过滤边界；先确认相关策略是否仍能选到可用账户。
改账户影响上游凭据、可用模型和并发。不必因一次请求失败直接停用；先查使用记录和健康证据，再决定检查、避让或停用。
供应商与协议档案定义真实能力边界。不能通过模型别名或接口勾选虚构不支持的协议；错误的档案会导致检查和实际请求都失败。

管理动作的最小顺序与验证点

  1. 确认基础资源。在供应商确认目标供应商存在；需要代理时先在代理管理建好。验证点：代理的最近状态与延迟检测正常，后续账户表单能选到预期供应商与代理。
  2. 建分组与 AI 账户。在AI 分组确定供应商边界与分组类型，再在AI 账户添加账户。验证点：新账户以 pending_test 创建，后台激活检查通过后进入 active；分组处于启用状态。
  3. 建策略路由。在策略路由选择路由模式并绑定分组。验证点：模式与分组数量匹配——普通模式恰好一个启用分组，权重、故障回退、轮询与合并至少两个；绑定的分组全部启用。
  4. 建 API Key。在API Key 管理绑定策略，按需设置过期时间、美元额度与时间计划。验证点：创建后立即复制完整密钥；状态、额度与时间计划符合调用方预期。
  5. 用事实验证链路。发出真实调用后核对：使用记录中的分组、账户与模型和配置一致；AI 健康无持续失败；操作日志记录了本次变更。验证点：链路每一层都落在预期对象上，且没有意外的 401 或 429。

配置资源，先建边界

AI 资源与账户生命周期

供应商决定协议档案，分组决定账户池，账户决定凭据、模型与并发。不要跳过检查就让新账户承接流量。

资源语义：供应商、协议档案与代理

供应商是账号池、模型目录和价格目录的归属边界：每个 AI 账户必须归属一个供应商，账户能声明哪些模型、按什么口径计价，都在供应商层维护。协议档案把供应商和协议版本绑定成一个能力档案，页面上以"接入类型"呈现：它决定账户表单、凭据类型（OAuth 或 API Key）、可用端点族、检查请求形态和模型映射规则。当前系统启用 OpenAI 供应商，支持 OpenAI OAuth 与 OpenAI API Key 两种账户创建方式；错误的档案会导致检查和实际请求都失败，配置不能虚构上游能力。

代理是服务器级全局运维资源，不属于任何用户的私有配置：它只决定某个账户到上游的网络路径，不改变客户端访问本系统的地址。普通用户可以读取全部已启用代理并绑定到自己的账户；管理员删除或停用代理前，先查被引用账户。

状态机：每个状态怎么进、怎么出、谁触发

账户状态不是"好/坏"两个值，而是一组有明确进入与离开条件的事实。区分谁在触发很重要：状态变化由后台系统检查与自动恢复机制维护（激活检查、周期健康检测、运行态恢复、冷却恢复）；人工测试只产生诊断证据，不作为状态变更凭证；人工动作只有停用 / 启用、"恢复正常"强确认放行，以及"重新检查"——它只重置检查窗口并交给后台确认，不直接放行。

  1. pending_test（待检查）：进入——新建、导入，或凭据、Base URL、协议档案、关键代理等连接配置变更保存后，等待后台激活检查；离开——后台检查通过进入 active。明确接受上游可用性风险时，可通过"恢复正常"强确认放行（不适用于授权实例或已过期账户，并继续服从账户时间计划）。
  2. active（正常）：进入——激活检查通过，或任一运行状态恢复成功；离开——进入某个运行状态、被人工停用，或连接配置变更后重新交给后台复检。active 是进入候选的必要条件，不保证当前可调度；还要同时满足调度开关、未到期、时间计划、授权来源和运行态可用。
  3. temporary_unavailable（临时不可调用）：进入——后台健康检测连续失败达到阈值（系统设置"健康检测连续失败阈值"，默认 3），避免网络抖动误杀；离开——恢复探针成功回到 active。暂停有上限（"临时不可调用最大暂停时间"）：先快速恢复，失败后有界退避；它是有界暂停，不是永久停用。
  4. rate_limited（限流中）：进入——真实上游账号触发限流策略；普通请求失败不会写入这个状态；离开——复测成功恢复。
  5. quality_isolated（质量隔离）：进入——质量问题触发隔离；离开——复测通过恢复。
  6. error（异常）：硬状态，不参与调度。进入——异常处置；具体原因由错误码与错误说明区分，账户状态提示会直接展示最近检查与最近错误的 traceId；离开——排除原因后重新检查或恢复。
  7. disabled（停用）：人工终态。进入——人工从任意状态停用；离开——仅人工重新启用，启用后按当前事实重新检查。停用是有意下线，不是故障；排障时不要把它和运行状态混在一起看。
人工测试与状态隔离：人工测试只生成诊断任务、使用记录和审计，成功或失败都不改写账户状态、调度开关、冷却或健康事实；账户恢复只能由后台探针的受围栏写回或独立的人工恢复操作完成。
账户与分组字段决定候选池、协议能力和并发先看供应商，再看状态和支持模型
供应商 / 协议档案
供应商是分组和账户的过滤边界；协议档案决定 OAuth/API Key 表单、接口能力和模型映射规则。
分组
只接纳同一供应商账户。个人分组直接按账户并发调度；高并发分组可设置软并发、短队列、单 IP 限制和溢出方式。
账户并发 / 优先级 / 特权
并发是账户硬上限；优先级小值优先；特权仅在明确需要超级优先或降级备用时使用。
状态与检查
pending_test 不承接流量；active 是进入候选的必要条件，不保证当前可调度；还要满足 schedulable、未到期、时间计划、授权来源和运行态均可用。disabled 是人工明确停用。
多 API Key
多个 Key 支持轮询或权重轮询，权重范围 1-100；多 Key 账户不能查询余额。
Base URL / 支持模型
Base URL 填服务根或版本根，不填具体端点；支持模型决定候选过滤及模型别名的目标范围。
接口能力 / 模型别名
只声明真实上游能处理的协议。别名的客户端侧与上游侧都必须满足当前协议档案和支持模型的限制。
代理
仅决定账户到上游的网络路径。删除或停用代理前，先查被引用账户。
分组名称 / 说明
名称与说明只用于识别，建议写业务用途、场景或限制；它们不参与调度。
分组状态
停用分组后，绑定策略不会继续把请求送入该池；重新启用即恢复候选。
响应检查策略根据真实响应匹配后执行处置先观察，再扩大处置范围
协议 / 作用层级
先选择 OpenAI、Anthropic 或 Gemini 协议；供应商层只作用于选定同协议供应商，协议层作用更广。
优先级 / 启用
优先级为 1-9999，小值先处理；停用可保留规则但不产生处置。
匹配条件
可按客户端、输出文字、结束状态、error.code、error.type、错误消息、单条 SSE 原文或 JSON 字段路径匹配；至少需要一个正向条件。
处置模板
先观察只记日志；丢事件只适合独立 SSE 垃圾事件；重试/避让账户会改变本次或后续请求的候选范围。规则不确定时先观察命中。

在 响应检查策略 新建或查看规则；验证时用 运行日志、审计日志 和 使用记录 交叉查看 traceId、命中规则和最终调用结果。

模型检测按账户和模型执行检查；先确定测试模型、协议形态和上游额度边界，结果再决定是否激活账户。响应检查策略用实际响应证据编写匹配和处置；新规则先观察命中，避免误伤正常流量。

共享策略有共享风险

策略路由与流量变更

策略决定 API Key 如何选择分组。它不保存凭据，也不替代分组内的账户并发与优先级。

策略是调控维度，账户是资源维度：策略只决定请求进入哪个分组池，池内怎么选号由账户优先级、并发硬上限与分组类型决定。每把 API Key 只绑定一条策略；策略的每一种模式都与分组绑定配合工作，点透下面的模式语义再动手。

普通恰好一个启用分组，请求直接进入该分组的账号池。
权重至少两个启用分组，按权重比例分流，所有权重总和不超过 100。
故障回退第一行主用，后续备用；主用恢复后继续优先主用。变更顺序会改变故障时的落点。
轮询至少两个启用分组，按当前排列顺序轮换。拖动顺序就是调度顺序。
合并至少两个启用分组，把所有绑定分组的账号合并成一个大池统一调度，不区分分组；拖动顺序仅决定调度平局时的基础先后。
调度偏好普通、权重、故障回退、轮询和合并五种模式共享，作用于请求所落分组内的账号调度。成本优先保留账号缓存/会话亲和；速度优先只在可重放文本的首字慢样本确认后切换。

模式选型与变更风险

  1. 普通——默认起点。规则最简单、行为最可预期，只有一个分组时是唯一选择；排障时链路也最短。
  2. 权重——按比例分流。适合灰度新账户或在多个池之间做成本分层。风险：调整权重立即改变所有绑定 Key 的分流比例；权重总和不超过 100。
  3. 故障回退——主备容灾。主用恢复后流量自动回到主用，备用只在主用不可用时承接。风险：调整顺序就改变了故障时的落点，改前先确认新顺序符合容灾预期。
  4. 轮询——按顺序均摊。适合多个等价池轮流承接。风险：拖动顺序即调度顺序，改动会立刻体现在下一个请求上。
  5. 合并——大池统一调度。适合把多组账号当一个整体提高利用率；无分组回退，用量按实际服务账号所属分组记账。代价：分组隔离在这个模式下有意失效，账号混排是预期行为而不是故障。
  6. 共性风险。模式与分组绑定是共享规则：任何调整同时作用于所有绑定该策略的 API Key。改前先在策略列表核对引用，必要时按下方共享策略变更规程操作。

调度偏好：成本优先与速度优先

调度偏好不改变策略层的分组选择，只在请求落到某个分组后影响组内账号排序（合并路由作用于合并池内）：

  • 成本优先：保留账号缓存与会话粘黏，尽量让同一会话延续同一账号，减少切换带来的上下文与缓存重建。适合按用量计费、切换成本高的场景。
  • 速度优先：只对可安全重放的文本请求观察首字慢样本，确认慢的账号在窗口内被后置；图像请求与有副作用的请求不参与这套切换，不会因为"慢"被取消或改写。首字截止与慢速参数只在速度优先出现，它们一起决定"何时确认慢、何时恢复"。
准备改共享策略时：先记录受影响 API Key 与当前分组绑定；要给新业务一套规则时，新建一个同配置的策略，再将 API Key 绑定到新策略。不要修改原策略后再绑定，以免已有流量同时变化。
策略与 API Key 接入要点从表单字段看一次完整接入名称用于识别，规则在模式与绑定里
策略名称 / 状态
名称建议带用途，避免多把 Key 之间误选共享策略；停用策略后，绑定它的 Key 不再通过它进入分组调度。
路由模式与调度偏好
模式决定怎么选分组，偏好决定所落分组内怎么选账号；两者保存后立即作用于所有绑定 Key。
分组绑定
策略真正可调度的目标集合。修改共享策略会影响所有绑定它的 API Key；需要不同规则时按上方规程新建副本。
API Key 名称
只用于后台识别，不是密钥本身；默认 API Key 与 AI 对话 API Key 的名称不可修改。
运行状态与过期时间
只有 active 状态接受调用；过期时间是绝对边界，到达后不可用，不被时间计划替代。
美元额度
可按 n 小时、日、周、月设置美元上限；额度用尽的请求返回 429。未开启的项目不限制。
时间计划
控制哪些星期和时段允许参与调度；未命中窗口的调用被暂时跳过。
完整密钥
只在创建或刷新时展示一次，之后列表与日志不再出现明文；创建后立即复制到调用方安全配置。
策略路由查看关联 API Key、模式和分组绑定。保存后用使用记录验证实际链路。API Key 管理设置 Key 的策略、状态、过期、美元额度和时间计划；完整密钥只在创建/刷新时展示。AI 分组检查供应商边界、高并发等待/单 IP 规则及启用状态。AI 账户检查账户并发、优先级、支持模型和运行态是否允许被选中。

资源与消耗分开看

授权与团队：传递使用权，不传递归属

授权决定可使用范围与归属，团队成员变化会影响后续用量归属；它不直接修改 API Key 路由。

授权的本质。授权只传递使用权，不传递管理权，也不能绕过敏感凭据隔离。被授权用户获得的是独立授权实例与使用侧调度权；来源凭据、账户归属、供应商 / 协议 / 模型 / 代理 / 并发等来源配置、授权关系本身和删除等敏感操作，仍然只属于资源归属人。

授权实例。账户授权生效后，系统为被授权用户创建独立的授权实例账户：实例有自己的状态、冷却与用量归属，被授权人分组绑定的是实例而不是原账户。归属人原账户停用、异常或删除时，授权实例保留自己的历史与本地状态，但会退出调度候选——来源可用性是实际调度的硬条件。

团队与用量归属。团队授权进入系统后同步为最终用户授权。团队成员变化影响后续用量归属：新成员加入后其消耗计入团队，移除后其后续调用不再计入；授权消耗统计不包含资源归属人自己的自用消耗。

额度与生命周期。授权可配置 n 小时、日、周、月与总美元额度，避免共享资源被超额使用；同一资源对同一被授权目标再次授权时复用原授权记录。归属人可在授权列表暂停、恢复或回收授权：暂停与过期期间被授权人仍可见但不可用，回收与归还后被授权人不可见也不可用。

授权管理先确认资源所有者、受授权对象和有效状态，再创建或调整授权范围。授权团队维护团队和成员；变更前核对影响成员与资源可见性。团队消耗按授权团队汇总用量，用于配额和费用核对。用户消耗按系统账户核对授权产生的用量和归属。

同一问题用不同证据回答

观测体系：六类证据与一条关联线索

先用使用记录定位那一次调用，再按需要用性能、健康、运行、审计和操作日志扩展证据。每类证据回答的问题不同，串起来才构成完整结论。

使用记录这次调用用了哪个账户、模型、状态、耗时和成本。
AI 健康账户是否可调度、最近检查和恢复状态。
AI 性能某账户/模型是否持续变慢，而不是只看一次长尾请求。
运行日志服务阶段、策略命中与运行异常，适合按 traceId 或策略名查。
审计日志安全和管理相关事件；按权限查看，不复制原始 payload。
操作日志谁修改过哪种资源，适合核对配置变更时间线。

traceId：把证据串起来的线索

使用记录、运行日志与审计日志携带同一个 traceId；账户状态提示会直接展示最近一次健康检查与最近一次错误的 traceId，操作日志中的人工放行也使用当前请求的 traceId。排障时从使用记录复制 traceId，再到运行日志与审计日志检索同一次请求，不要凭错误文案反查——同一个错误文案可能来自不同阶段、不同对象。

同一问题的不同证据：一次失败请求的定位路径

  1. 使用记录。先确认这次失败的调用：用了哪把 Key、绑定的策略、命中的分组与账户、最终状态与错误。多数请求问题到这一步就能定位到层。
  2. 运行日志。按 traceId 查这次请求停在哪个服务阶段、命中了哪些检查与策略，回答"网关内部发生了什么"。
  3. AI 健康。确认涉事账户是单次抖动还是持续失败，检查与恢复状态如何，决定要不要处置账户。
  4. 操作日志。确认失败发生前，是否有人改过这把 Key、这条策略、这个分组或账户的配置——先排除"变更引入"的可能，再深挖上游。
  5. 审计日志。需要完整链路证据（客户端请求、上游响应、最终返回）时使用；按权限查看，不复制原始敏感内容。
系统概览全局业务统计与状态的入口，先看趋势再下钻。用量统计按账户、模型和时间汇总令牌与费用，用于对账。AI 性能分析延迟与成功率，先缩小账户和模型范围。AI 健康查看探针与可调度状态，持续失败才进入账户处置。使用记录定位具体调用、路由和最终状态的首选页面。操作日志核对后台写入动作、操作者与结果。公开接口日志排查公开 API 调用；按最小权限处理其业务上下文。审计日志核查安全与管理事件，避免复制原始敏感内容。运行日志查看服务运行阶段，与使用记录按 traceId 交叉定位。

全局设置保存即可能影响全部用户

系统设置与日常运维

设置页按分区写入。改限流、超时、保留期或账户恢复规则前，先记录当前值、受影响请求类型与回看指标。

改设置的共同规程

  1. 记录现值与变更原因。操作日志会留下谁在何时改了什么，但不会记录你的预期；先写下来，回看时才知道"当时想解决什么"。
  2. 明确影响面。区分这次改动作用于管理面还是网关请求路径：限流影响管理操作与调用方，超时影响请求预算，保留期影响排障与审计窗口。
  3. 小步变更。一次只动一个分区的一个值；多个同时改，出了问题无法归因。
  4. 保存后回看。用 429 指标确认限流没有误伤日常操作，用后台任务与健康指标确认任务仍正常，用表监控确认保留期调整后增长趋势符合预期。
品牌、请求体与用户额度影响界面和网关入口0 表示不限额的字段必须显式确认
系统名称 / 图标路径
系统名称显示在菜单、浏览器标签和登录标题；图标默认 /__aisys__/brand-icon.svg，也可保存 256KB 内 Data URL。
文本请求体上限
1-64MB，当前默认 16MB。调大能承载更长文本上下文，也提高单请求内存压力；不等同图像请求上限。
账户电路独立确认失败次数
1-5，当前默认 2。首次 transport 失败先待确认，需要不同请求的独立失败证据；完整 HTTP 响应不计入。
用户每分钟/日/周/月请求数
限制同一系统用户跨所有 API Key 的网关请求。每个字段 0 都表示无限，达到上限后新请求返回 429。
后台接口限流保护管理面与管理写入读写限流与突发窗口需一起看
IP 读/写每分钟
保护 /__aisys__/api 的 GET/HEAD/OPTIONS 与 POST/PATCH/PUT/DELETE；0 表示无限。
IP 读/写 10 秒突发
拦截短时间集中刷新和批量提交。设得低于日常页面并发会让正常管理操作频繁 429。
登录用户读/写每分钟
在 IP 限制之外再保护同一登录账户；写限制会作用于保存、删除和批量操作。
健康检查、恢复与重试控制何时探测、何时暂时避让不要因一次网络波动就缩短全部阈值
健康检测间隔 / 错峰窗口
当前默认分别为 1 小时、10 分钟。只检测长期没有真实成功请求的正常账户，错峰避免大批账号同时打上游。
健康检测连续失败阈值
1-10，当前默认 3。达到阈值才允许进入临时不可调用，避免网络抖动误杀。
临时不可调用最大暂停时间
1-1440 分钟，当前默认 2。账户先走快速恢复，失败后退避；它不是永久停用。
安全原地重试间隔 / 次数
仅对可安全重放且响应头到达前的传输异常生效；完整 HTTP、正文中断、首字截止和副作用请求不使用。
长期不可用观察阈值
1-720 小时，当前默认 12。超过后显示长期不可用，仍保留低频复测，不把它直接改成异常状态。
文本/图像超时与保留期区分 lane，不能用一个数字覆盖全部文本和图像有独立 attempt 边界
文本首响应（流式） / 流式停顿 / 未提交寿命
只作用于文本 lane 的流式请求：等待响应头、收到内容后的空闲时间、尚无模型语义输出的单次尝试寿命。
文本非流式响应等待
只作用于文本 lane 的非流式请求；上游生成完整结果后才返回，10-3600 秒内未收到首个响应即终止当前尝试，默认 600 秒。
图像首响应 / 流式停顿 / 未提交寿命
只作用于 image lane；快速模式文本首字截止不适用于图像。
图像整请求总时限 / AI 对话生图总超时
前者约束一次通用网关图片请求的总墙钟；后者约束站内 generate_image 的完整链路。两者都是 60-86400 秒。
无可用账号等待
仅在完全没有可立即派发候选时累计；当前账号仍在执行或有可派发候选时，不会因为它到达而停止接管。
使用记录 / 运行日志索引 / 公开日志保留天数
当前默认分别为 30、14、30。缩短前确认审计、统计和排障窗口需求；运行日志索引清理不删除原始日志文件。

先缩小，再处置

风险操作与按症状排障

先缩小再处置；每一步都要有可回看的事实。管理员不应把"恢复服务"理解成先停账户或放宽全局限制——先定位证据指向的那一层，再做能被证据解释的处置。

请求异常

先看证据：使用记录确认 API Key、策略、分组和账户的实际链路；运行日志按 traceId 看服务阶段。

可能原因：Key 状态、额度或时间计划拦截；绑定策略不符预期；分组或分组内没有可调度账户。

处置：先核对链路哪一层与预期不符，只修改能解释当前证据的配置；不要跳层处置。

账户异常

先看证据：AI 健康的检查结果、账户状态与最近错误说明。

可能原因：凭据失效；模型或协议能力与上游不符；Base URL 或代理不可达；上游限流或临时故障。

处置：先查使用记录与健康证据，再决定重新检查、避让或停用；不必因一次请求失败直接停用。

性能异常

先看证据：AI 性能按账户/模型的趋势；系统指标的进程与队列。

可能原因：个别账户持续变慢；高并发分组排队等待；上游整体波动。

处置：单次慢请求不是调整全局超时的充分证据；先缩小到账户和模型，确认是普遍现象再针对性处理。

授权范围异常

先看证据：系统账户角色、授权管理的授权状态与操作日志。

可能原因：角色不对应写入受限；授权被暂停、过期或额度用尽；团队成员变化改变了可见与归属。

处置：先确认是当前模式、资源归属还是成员关系问题，再调整授权关系；不要用改资源配置的方式绕过授权边界。

改共享策略

先看证据：策略路由的关联 API Key 与当前分组绑定；操作日志确认最近变更。

可能原因：就地修改共享策略，所有绑定 Key 的行为同时改变。

处置：先记录受影响 Key 与原分组顺序；要分叉新规则时，新建一个同配置的策略，再将 API Key 绑定到新策略，原策略保持不动。

收紧限流 / 保留期

先看证据：系统设置现值；保存后的 429 指标、后台任务与排障数据。

可能原因：突发窗口低于日常页面并发；保留期短于排障与审计窗口需求。

处置：先记录现值和受影响来源，小步收紧并观察是否仍满足需要；必要时按记录恢复原值。

参考：代用户导入要点

导入把结构化来源资料变成待检查账户。管理员可以代目标系统账户执行导入，但导入不替来源确认凭据真实可用——检查通过前，导入账户不承接流量。

代用户导入时，先选择目标系统账户。导入只接受 juhe-ai-account-import v1 JSON，单次约 256KB，最多 50 个账户，最多 20 个代理；先“解析预览”再“确认导入”，来源 active 仍会创建为 pending_test。

  1. 准备来源资料。把账号资料整理为 juhe-ai-account-import v1 JSON；来源里没有的凭据、模型或账号 ID 不要补全，不确定的信息放进 notes 字段。
  2. 选择目标系统账户后执行“解析预览”。逐项处理预览提示：协议档案、分组归属、代理引用与重复项。
  3. 确认导入选项。不存在的分组可按选项自动创建，同名账户可跳过；代理引用必须指向已存在的代理，需要时先在代理管理建好。
  4. 等待后台激活检查。导入完成后账户以 pending_test 等待检查，检查通过并满足候选条件后才参与调度。
导入不是验证。即使来源写明 active，导入账户仍以 pending_test 创建；对上游可用性的最终确认，永远来自后台检查与真实调用证据。
管理页展示系统范围数据。帮助页只说明操作和边界，不公开上游密钥、OAuth token、代理密码或原始审计内容。
