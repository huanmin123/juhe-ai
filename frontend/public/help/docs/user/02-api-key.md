# API Key 与认证

> 这一篇解决：怎么创建和保管 API Key，请求里怎么把认证头写对，额度是怎么回事，以及收到 401 时先检查什么。

## 一把 API Key 是什么

API Key 是你在 juhe-ai 里的**本地钥匙**，形如 `sk-` 开头的一串字符。客户端每次请求都靠它证明"这是你发出的请求"。一把 Key 决定三件事：

| 它决定 | 说明 |
| --- | --- |
| 身份 | Key 属于你的账号，调用记录和额度都按 Key 归到你名下 |
| 额度 | 这把 Key 能用多少，由创建/管理时的额度设置决定 |
| 可用范围 | 每把 Key 只绑定一套策略路由，能用哪些模型、走哪些分组由它决定 |

同时注意 Key **不**决定什么：

| 常见误解 | 事实 |
| --- | --- |
| Key 绑定了某个上游账号 | 没有。上游是谁、账号怎么切，由后台路由决定，换上游不用换 Key |
| 在 Key 上配置能用哪些模型 | 不能。模型范围是 Key → 策略路由 → 分组 → 账户层层过滤的结果（见《核心概念：一次请求的旅程》） |
| 换一个客户端就要换一把 Key | 不必。同一把 Key 可以给多个客户端用，但按用途分 Key 更利于对账和止损 |

## 创建与保管一把 Key

入口：管理台的 [API Keys](/__aisys__/my-api-keys) 页面。

1. 创建一把新 Key，起一个能认出用途的名字（比如 `my-ide-plugin`、`my-bot`），方便以后对账和管理。
2. **Key 只在创建时完整显示一次**，立刻复制并保存到安全的地方，关掉弹窗后就再也看不到全文了。
3. 不再使用、或怀疑泄露的 Key，在列表里停用或删除（具体操作以页面为准）。停用立即生效，用它的请求会开始收到 401。

保管要点：

| 场景 | 怎么做 |
| --- | --- |
| 写代码时 | 用环境变量（如本文的 `$JUHE_AI_API_KEY`），不要把 Key 写死在源码里 |
| 用了版本管理 | 确认 `.gitignore` 生效，Key 不进仓库、不进截图和文档 |
| 发给别人协助排障 | 只发 Key 名字和前缀现象描述，**不要发 Key 全文** |
| 多个客户端 | 一把 Key 对应一个用途，泄露时只需停用那一把，也方便按用途对账（见《用量与统计》） |
| 定期整理 | 列表里用不到的 Key 及时停用，缩小泄露面 |
| 重装或迁移设备 | 先建新 Key 切换过去，验证新 Key 能用后再停用旧 Key，不要先停再换 |

## 多把 Key：按用途分

与其一把 Key 到处用，不如按用途开几把：

| 用途 | 好处 |
| --- | --- |
| IDE / 编辑器插件 | 插件配置泄露时不影响其他场景 |
| 自己写的脚本 | 脚本产生的用量一目了然 |
| 聊天客户端 | 日常聊天与工作流量分开 |
| 临时测试 | 用完就停用，不占额度 |

每把 Key 的用量都记在账上（见《用量与统计》），分得越清，对账越容易。

## 先备好环境变量，一劳永逸

本文示例统一用两个环境变量，设置一次，后面的每条 curl 都能直接照抄：

```bash
export BASE_URL="https://你的域名"
export JUHE_AI_API_KEY="sk-你的Key"
```

- Windows PowerShell 用 `$env:BASE_URL="..."` 的写法；在客户端里配置的，直接把两个值填进设置界面即可。
- Key 就是创建时保存的那串；如果找不到了，到管理台停用旧 Key 再建一把新的即可，旧 Key 立即失效。

## 请求里怎么带认证

认证只有一种方式：HTTP 请求头 `Authorization: Bearer <API Key>`。

```bash
curl -s "$BASE_URL/v1/chat/completions" \
  -H "Authorization: Bearer $JUHE_AI_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "gpt-5.4",
    "messages": [ { "role": "user", "content": "你好" } ]
  }'
```

规则逐条说清楚：

| 规则 | 说明 |
| --- | --- |
| 头的名称 | `Authorization`。没有 `x-api-key` 之类的替代头，放别的头里不会被识别 |
| `Bearer` 前缀 | 大小写不敏感，但 `Bearer` 和 Key 之间要有一个空格 |
| Key 本体 | 原样粘贴，前后不要带引号、空格或换行 |
| 放置位置 | 只放请求头。不要把 Key 放进请求体、URL 路径或查询参数 |

所有 `/v1` 协议端点都用同一套认证：对话、模型列表、图像、嵌入、语音、视频，写法完全一样，换端点只是换路径和请求体。

常见的错误写法，逐个对号：

| 写法 | 结果 |
| --- | --- |
| 只传 Key，漏掉 `Bearer ` 前缀 | 401 鉴权失败 |
| `Bearer` 和 Key 之间没有空格 | 401 鉴权失败 |
| Key 两边带了引号（`Bearer "sk-..."`） | 401 鉴权失败 |
| 把 Key 放进 `X-Api-Key` 头 | 401 鉴权失败（没有这个替代头） |
| Key 已被停用或删除后继续用 | 401 鉴权失败 |

## 额度：怎么理解这件事

理解额度的一条主线：**设置在 Key 上，消耗在记录里**。

1. 创建 Key 时（或之后）可以设置额度限制，具体数值和形式**以 [API Keys](/__aisys__/my-api-keys) 页面为准**，本文不写死。
2. 每次调用（成功或失败）都会产生一条使用记录，额度怎么扣、扣了多少，以记录为准，见《用量与统计》。
3. 额度接近上限、用尽或触发限制时的表现（如 429 类错误）与处理办法，见《错误码与排障》。

所以"我还剩多少额度"这个问题，答案永远在管理台页面上，不要靠客户端本地估算。

再补一个实用思路：把额度拆到多把 Key 上，一把出问题不影响其他——这也是按用途分 Key 的又一个好处。

## 收到 401？按顺序检查

| 顺序 | 检查点 | 怎么查 |
| --- | --- | --- |
| 1 | 请求头形状 | 是不是 `Authorization: Bearer sk-...`，`Bearer` 后有一个空格，没有多余引号 |
| 2 | Key 完整性 | 重新复制一遍，确认没少尾巴、没混入空格或换行 |
| 3 | Key 状态 | 到 [API Keys](/__aisys__/my-api-keys) 看这把 Key 是否还在、状态是否正常（可能已被停用或删除） |
| 4 | 环境变量生效 | 确认 `$JUHE_AI_API_KEY` 在发请求的那个终端/进程里真的有值（空变量会拼出 `Bearer ` 后面为空） |
| 5 | 同时是 404？ | 那多半是路径问题，见《错误码与排障》里"不带 error 信封的 404"一节 |

以上都对还 401，按《错误码与排障》继续定位。
