# 模型列表：我能用什么模型

> 这一篇解决：GET /v1/models 怎么读、模型名从哪来、为什么列表里没有你想要的模型、以及怎么快速验证一个模型真的能用。

## 一条命令拿到可用模型

```bash
curl -s "$BASE_URL/v1/models" \
  -H "Authorization: Bearer $JUHE_AI_API_KEY"
```

返回长这样：

```json
{
  "object": "list",
  "data": [
    { "id": "gpt-5.4", "object": "model", ... },
    { "id": "gemini-3.5-flash", "object": "model", ... }
  ]
}
```

要看的字段：

| 字段 | 含义 |
| --- | --- |
| `object` | `list`，表示这是一个列表 |
| `data` | 数组，每个元素是一个可用模型 |
| `data[].id` | **模型名**，直接填进请求的 `model` 字段，原样复制，不要凭印象手打 |

返回里可能还有其他描述性字段，不影响使用；核心就是拿 `data[].id`。

## 这个列表是什么

三个关键事实：

1. 它返回的是**你这把 Key 可用的模型目录**，由网关本地渲染生成，不是把某个上游的模型列表原样透传过来。
2. 不同 Key 看到的列表可以不同：因为列表跟着"Key → 策略路由 → 分组 → 账户"这条链路走（详见《核心概念：一次请求的旅程》）。
3. 模型的名字、说明和**单价**由管理员在模型目录里维护：[模型目录](/__aisys__/my-models)。想查某个模型是什么、怎么计费，去那里看。

## 模型目录和 /v1/models 什么关系

| | 模型目录（管理台） | GET /v1/models（接口） |
| --- | --- | --- |
| 谁在用 | 管理员维护，所有人可查 | 你的客户端程序化获取 |
| 内容 | 全量模型的名字、说明、单价 | **你这把 Key** 过滤后可用的模型 |
| 用途 | 查单价、查模型说明 | 拿能直接填的模型名 |

一句话：目录是"货架上有什么"，`/v1/models` 是"你这份购物卡能买什么"。

## 实时拉，还是缓存下来？

`GET /v1/models` 很轻量，但不必每次请求前都调：

| 时机 | 建议 |
| --- | --- |
| 客户端启动 / 首次配置 | 拉一次，把模型名缓存进配置 |
| 收到 `unsupported_model` 报错后 | 再拉一次，确认是不是模型名变了，再继续排障 |
| 管理员通知目录有调整后 | 重新拉一次，列表按 Key 过滤，可能真的变了 |

列表不是一成不变的：管理员在目录加模型、调整路由，你的列表都可能跟着变。

## 模型名从哪来：一层层过滤

一个模型要出现在你的列表里，得通过四层筛选：

| 层 | 这一层过滤掉什么 |
| --- | --- |
| API Key | 决定你绑定哪套策略路由，范围由此框定 |
| 策略路由 | 决定候选分组的范围 |
| 分组 | 只接纳同一供应商的账户池，跨供应商的账户进不来 |
| AI 账户 | 只留下"直接支持该模型"或"模型映射能命中"的账户 |

四层走完仍有候选账户的模型，才会出现在 `GET /v1/models` 的返回里。所以"列表"本身就是一次可用性过滤的结果——这也是它比"上游官方模型清单"更适合你的原因。

## 挑模型的两个小建议

- **按任务选类别**：对话找对话模型，画图找图像模型，向量找嵌入模型，音频找语音模型。每个模型是干什么的，以 [模型目录](/__aisys__/my-models) 里的说明为准。
- **名字永远从列表里复制**：大小写、点号、横杠都可能有讲究，手打最容易翻车。

再一个经验：把常用的几个模型全名存在自己的配置里，第一次从列表复制，之后原样复用，比每次现抄省事也更不容易错。

## 为什么列表里没有我想要的模型

| 现象 | 常见原因 | 怎么办 |
| --- | --- | --- |
| 模型完全不在列表里 | 模型目录未上架 | 找管理员确认目录 |
| 模型在目录里有，但你的列表里没有 | 你的路由链路上没有账户支持它 | 找管理员确认你的 Key 绑定的路由覆盖范围 |
| 列表里有，请求却报 503 `unsupported_model` | 模型名拼写、大小写与目录不一致（筛不到支持的账户） | 从 `data[].id` 原样复制 |
| 请求报 503 `missing_model` | 请求体里漏了 `model` 字段 | 补上再发 |
| 拿对话模型去调图像/嵌入端点 | 模型类型和端点不匹配 | 按 [模型目录](/__aisys__/my-models) 选对应类别的模型 |

其中"分组无账户支持"的报错原文是"当前分组无账户支持请求模型：X"（503 `unsupported_model`），逐字对照与完整错误信封见《错误码与排障》。

## 30 秒验证一个模型能不能用

两种办法任选：

**方法一：发一次最小请求。** 用《快速开始》第三步的 curl，把 `model` 换成你要验的名字：

```bash
curl -s "$BASE_URL/v1/chat/completions" \
  -H "Authorization: Bearer $JUHE_AI_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "要验证的模型名",
    "messages": [ { "role": "user", "content": "回复 ok" } ]
  }'
```

能正常返回 `choices` 就是通的；报错则按《错误码与排障》对号。

**方法二：不写代码。** 打开管理台的 [在线聊天](/__aisys__/my-chat) 页面，选好模型直接聊一句，现象和 API 调用一致，最适合快速肉眼验证。注意：在线聊天走的是系统维护的**专属对话 Key**（自动创建，见 [API Keys](/__aisys__/my-api-keys) 页面），与你的客户端 API Key 相互独立——它验证的是模型本身可用性，**不能替代客户端 Key 的接入验证**；客户端接入是否正常，以真实客户端调用与《用量与统计》里的使用记录为准。

上游和账户层的可用性由管理员侧持续盯守——模型可用性探测在 [模型探活](/__aisys__/my-model-checks)，上游健康在 [AI 健康](/__aisys__/my-ai-health)。你只管按列表调用；调用中遇到报错，按《错误码与排障》处理。
