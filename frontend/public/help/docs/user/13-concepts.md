# 核心概念：一次请求的旅程

> 这一篇解决：一次请求从你的客户端到真实上游要经过哪五层，每层各自决定什么、对应管理台哪个页面。

## 五层总览

路由层级固定为：**API Key → 策略路由 → 分组 → AI 账户 → 上游**。

| 层 | 它决定什么 | 管理台入口 |
| --- | --- | --- |
| 1. API Key | 你是谁、额度多少、绑定哪套策略路由 | [API Keys](/__aisys__/my-api-keys) |
| 2. 策略路由 | 怎么挑分组：普通策略只绑一个分组；权重、故障回退、轮询、混合智能属于多分组模式 | [路由策略](/__aisys__/my-route-strategies) |
| 3. 分组 | 账户池的边界：一个分组只接纳同一供应商的账户 | [分组](/__aisys__/my-groups) |
| 4. AI 账户 | 真实凭据、协议能力、支持哪些模型（含模型映射） | [AI 账户](/__aisys__/my-accounts) |
| 5. 上游 | 真正干活的 AI 服务 | —（由账户封装，你感知不到） |

记住一句话：**Key 管身份，策略管挑组，分组管池子，账户管凭据，上游管干活。**

## 逐层拆开看

### 第 1 层：API Key —— 你是谁

- 每把 Key 属于你的账号，额度、状态、绑定哪套策略路由都挂在它身上。
- 它**不**绑定具体上游账号，所以后台换上游不用你换 Key。

### 第 2 层：策略路由 —— 怎么挑分组

- Key 只绑定一套策略路由，路由决定"去哪个分组"的规则。
- 普通策略只绑一个分组，一对一；权重、故障回退、轮询、混合智能属于**多分组模式**，在候选分组之间按规则选择、故障时自动切换。

### 第 3 层：分组 —— 账户池的边界

- 分组只接纳**同一供应商**的账户池，不同供应商的账户不会混进同一个分组。
- 后面"筛账户"就发生在这个池子里，池子外的一概无份。

### 第 4 层：AI 账户 —— 真实凭据与能力

- 账户保存真实上游凭据，决定协议能力和支持的模型。
- 筛选规则：先要**直接支持该模型**的账户，再看**模型映射能否命中**；两边都不沾的出局。
- 账户还有一个硬门槛：`active`（检查通过且启用）是进入候选的必要条件，不保证当前一定可调度——限流、冷却、隔离都会临时把账户请出池子，这些由管理员侧盯守。

### 第 5 层：上游 —— 真正干活的 AI 服务

- 请求最终由选中账户的凭据发往上游。
- 上游的细节被账户封装，你的请求和响应里看不到它。

## 一次请求的六步旅程

第 1 步，出发。你的客户端带着 `Authorization: Bearer <API Key>`，把请求发到 `$BASE_URL/v1/...`。你的全部配置就这三样：Base URL、Key、模型名（见《快速开始》）。

第 2 步，验 Key。网关核对这把 Key：存在吗？状态正常吗？额度还有吗？全部通过后，取出它绑定的那套策略路由。过不了就在这里停下——这就是 401 和额度类报错的出生地。

第 3 步，挑分组。策略路由按自己的模式选分组：普通策略只有一个绑定的分组，没得挑；多分组模式则按权重、健康度、轮询顺序等规则选一个。

第 4 步，筛账户。分组在自己容纳的账户池里筛出候选账户：优先"直接支持请求模型"的账户，其次看"模型映射能否命中"。两边都不沾的账户出局。筛空了，就得到 `unsupported_model`（见《错误码与排障》）。

第 5 步，出站。从候选账户中选定一个，用它保存的真实凭据把请求发给上游。如果这一步走的是模型映射，出站的模型名会被改写成账户配置的上游模型名——**你的请求和收到的响应里，模型名都还是你发的那一个，你无感知**。

第 6 步，回程。上游返回结果，网关把响应带回来；无论成功失败，都会记一条使用记录。这笔账去哪核对，见《用量与统计》。

## 模型映射，小白版

同一个模型，在上游可能叫另一个名字。账户上可以配一张"你请求的名字 → 上游真实名字"的对照表，这就是**模型映射**。它带来的体验是：你一直用习惯的模型名，管理员在后台换上游、改映射，你的代码一行不用动。

它也解释了《模型列表》里的一个现象：能不能用某个模型，要走到"账户"这一层才见分晓——列表里没有，往往就是链路上没有账户直接支持它、映射也没命中。

想确认某个名字是不是映射出来的？映射配置在管理台的账户上；普通用户不用查配置，发一次测试请求看通不通就够。

## 卡在哪一层：报错快速归位

结合六步旅程，报错可以按层定位：

| 报错 | 卡在哪一步 | 翻哪篇 |
| --- | --- | --- |
| 401 鉴权失败 | 第 2 步之前（验 Key 没过） | 《API Key 与认证》 |
| 429 / 额度受限 | 第 2 步（额度检查） | 《错误码与排障》 |
| `unsupported_model` | 第 3-4 步（挑分组、筛账户筛空了） | 《模型列表》 |
| `missing_model` | 旅程开始前（请求体不完整） | 《对话协议 chat completions》 |
| `upstream_error` | 第 5 步（出站到上游） | 《错误码与排障》 |
| 裸 404"资源不存在" | 根本没进 `/v1` 协议层 | 《错误码与排障》 |

卡在哪一层，决定谁能解决：第 1-2 层的问题你自己查就能解决；第 3-4 层的调整权在管理员。

## 旅程中每一层，什么变了、什么没变

| 阶段 | 请求里的 `model` 名 | 使用的凭据 | 请求实际到达谁 |
| --- | --- | --- | --- |
| 你发出时 | 你写的名字 | 你的 API Key | juhe-ai 网关 |
| 账户选定后 | 命中映射则改为上游名，否则原样 | 被选中账户的真实凭据 | 真实上游服务 |
| 响应返回时 | 仍是你写的那一个 | — | 网关带回给你 |

对你始终不变的，就是 Base URL、Key、模型名三样配置。

## 常见误解，一次澄清

| 误解 | 事实 |
| --- | --- |
| 我的 Key 直连某个上游账号 | 不是。Key 只到策略路由为止，上游由分组里的账户决定 |
| 客户端可以指定走哪个分组 | 不能。分组由策略路由挑，客户端只提供模型名 |
| 模型名可以随便写别名 | 不能。以 `GET /v1/models` 返回为准；"别名"是管理员在账户上配的模型映射，不是你请求里能做的 |
| 一个分组里可以混不同供应商 | 不能。分组只接纳同一供应商的账户池 |

## 这个设计对你意味着什么

- **配置面最小**：上游可换、账户可切，客户端配置不变。
- **故障有兜底**：配了故障回退等模式的多分组策略，会在上游抖动时自动换组换账户。
- **报错能归位**：`unsupported_model` 说明卡在第 3-4 层（分组/账户筛空了），401 卡在第 2 层之前（验 Key），对号方法见《错误码与排障》。
- **天然多租户**：谁的 Key 记谁的账，用量记录自动归属到账号，你不用自己另记一本账。

五层里第 2-4 层都由管理员维护，下面入口对普通用户只作参考阅读：

- [路由策略](/__aisys__/my-route-strategies)：看你的 Key 绑定的策略怎么挑分组
- [分组](/__aisys__/my-groups)：看候选账户池的边界
- [AI 账户](/__aisys__/my-accounts)：看账户支持哪些模型、映射了哪些名字

需要新增模型、更换分组时，联系管理员，并把话说全："哪把 Key、要哪个模型"——这正好对应五层链路的定位。
