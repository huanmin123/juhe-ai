# 用量与统计

> 这一篇解决：每次调用去哪里看、怎么逐笔对账、计费按什么口径、失败请求算不算钱。

## 每次调用都会留下一条记录

两个基本事实：

1. **成功和失败的调用都会产生使用记录**——失败不是"没发生过"。
2. 每条记录能看到时间、模型、用量（token/张/秒等，按模型而定）与该次调用的计费结果，具体字段以页面展示为准。

所以"我到底调了多少、花了多少"这类问题，答案都在管理台，不在你的客户端本地估算里。

本篇余下部分就按这条主线展开：去哪看 → 怎么对账 → 计费口径 → 失败怎么办。

## 三个看数的地方

| 页面 | 适合回答的问题 |
| --- | --- |
| [统计总览](/__aisys__/my-stats) | 这段时间整体调了多少、花了多少、有没有异常起伏 |
| [用量统计](/__aisys__/my-usage-stats) | 按天、按模型等维度汇总出来的账单视角 |
| [用量记录](/__aisys__/my-usage-records) | 某一笔请求到底成没成功、计了多少——对账的终点 |

从粗到细使用：先看总览发现异常，再用统计缩小到某天/某模型，最后进用量记录逐笔核实。

## 什么时候看哪个页面

| 场景 | 去哪 |
| --- | --- |
| 只想看今天有没有异常 | [统计总览](/__aisys__/my-stats) |
| 做预算，想按模型/按天的维度 | [用量统计](/__aisys__/my-usage-stats) |
| 客户端说失败了，要核实那一笔 | [用量记录](/__aisys__/my-usage-records) |
| 想单独看某把 Key 的消耗 | 到 [用量记录](/__aisys__/my-usage-records) 按 Key 筛 |
| 核实一笔失败请求 | [用量记录](/__aisys__/my-usage-records) 看该条结果，报错按《错误码与排障》对号 |

## 三步对账

1. 从客户端侧拿到可疑的时间段和大概的请求数。
2. 到 [用量记录](/__aisys__/my-usage-records) 按时间筛选出这个区间。
3. 逐笔核对模型与用量，重点看**失败条目**的计费结果。

账对不上时，常见原因对照：

| 现象 | 常见原因 |
| --- | --- |
| 记录条数比客户端统计多 | 多把 Key / 多个客户端在用；重试过的请求每次都各自成条 |
| 有失败条目混在里面 | 失败也留记录，是否计费看该条记录的计费结果（见下文） |
| 单笔都对、总和不对 | 不同模型单价不同，汇总时不能用单一单价乘总 token |
| 某天突然多出一截 | 先去 [统计总览](/__aisys__/my-stats) 看异常从哪个时间段开始，再进记录定位 |

## 对账实例走一遍

用一个假想例子走全流程（数字仅为演示）：

1. 客户端脚本显示 14:00-14:10 之间发送了 20 次请求。
2. 到 [用量记录](/__aisys__/my-usage-records) 按这个时间段筛选，发现 21 条——比客户端记的多一条。
3. 逐条对照，多出的是一条失败记录：脚本超时后重试了一次，重试也各自成条。
4. 看这条失败记录的计费字段：算不算钱，以它记录的实际计费结果为准。
5. 结论：记录没有错账，是脚本重试造成的条数差；后续在脚本里控制重试次数。

三步对账走的就是这条路：缩小范围 → 逐条比对 → 差异逐个解释。

## 计费口径

- 计费维度**按模型而定**，不搞一刀切：

| 模型类型 | 常见计费维度 |
| --- | --- |
| 文本对话 | token（输入/输出） |
| 图像 | 按张或按 token（依模型而定） |
| 音频 / 视频 | 可能按时长（如秒） |
| 嵌入 | token |

- 各模型的**具体维度与单价来自管理台的[模型目录](/__aisys__/my-models)**，想知道数字去那里看，本文不写死。
- 想要汇总视角而不是逐笔翻，用 [用量统计](/__aisys__/my-usage-stats)。
- 单价可能随目录调整变化，别把某次看到的价格当永久事实，对账前现查一次最稳。

文本对话里输入和输出都算 token：响应里的 `usage` 字段（示例见《快速开始》）有 `prompt_tokens`（输入）、`completion_tokens`（输出）和 `total_tokens`（合计），对账时按你的单价口径选用——口径是什么，同样到 [模型目录](/__aisys__/my-models) 查。

## 失败请求算不算钱

这个问题不靠猜，靠记录：

- 系统对**每次调用**都记录实际的计费结果，所以"算不算、算多少"以 [用量记录](/__aisys__/my-usage-records) 里那一条的计费字段为准。
- 一般规律：上游已经产出的部分（比如已经生成的 token）可能计费；没碰到上游的纯失败可能不计。但不同模型、不同失败形态结果不同，**本文不替页面下结论**，逐笔看记录最可靠。
- 判断路径：到用量记录找到那笔失败请求 → 看它的计费字段 → 有疑问就把时间、模型、记录内容整理好找管理员核对。

## 对账时别踩的坑

- 客户端本地估算的 token 不等于账目：token 怎么数由上游口径决定，一切以记录为准。
- 失败条目不等于一定扣费，成功条目也不等于每个模型算法一样，逐条看记录的计费结果。
- 总览页的"今日用量"可能有统计口径与时点差异，发现对不上，直接找最终裁判——[用量记录](/__aisys__/my-usage-records)。
- 同时用了多把 Key，看总额要合并统计，看归属要按 Key 分别对。
- 时间段筛选时注意时区与"当天"的边界，差一分钟可能就跨了一条记录。

## 值得保持的自查习惯

1. 批量跑任务（比如批量画图）之后，立刻到 [用量记录](/__aisys__/my-usage-records) 确认消耗量级符合预期。
2. 新换客户端或新开 Key 之后，到用量页面确认新 Key 的调用正常入账。
3. 对某笔记录有疑问，先截图记录内容再找管理员，带完整证据比凭记忆描述快得多。
4. 每月固定日期看一眼 [用量统计](/__aisys__/my-usage-stats)，对用量趋势心里有数，异常发现得早。

## 团队与授权视角

如果你在团队场景里用，分摊与归属看这几页：

| 页面 | 看什么 |
| --- | --- |
| [团队](/__aisys__/my-teams) | 团队结构与成员 |
| [授权管理](/__aisys__/my-authorizations) | 授权关系的入口 |
| [成员用量](/__aisys__/my-authorization-user-usage) | 按用户维度看用量分摊 |
| [团队用量](/__aisys__/my-authorization-team-usage) | 按团队维度看用量汇总 |

个人用户记住主线就够：**明细看用量记录，汇总看用量统计，大盘看统计总览。**

团队页面的可见性与操作权限取决于你的角色，看不到对应入口时找管理员开通。
