# 错误码与排障

> 这一篇解决：错误的 JSON 信封长什么样、常见错误逐个对号入座、按症状快速定位该查哪里、排障时管理台哪些页面用得上。

## 错误长什么样：统一信封

`/v1` 协议路径上的失败响应，统一是这个形状：

```json
{
  "error": {
    "message": "当前分组无账户支持请求模型：gpt-5.4",
    "type": "invalid_request_error",
    "code": "unsupported_model"
  }
}
```

三个字段各管一件事：

| 字段 | 含义 |
| --- | --- |
| `error.message` | 人能读懂的原因描述，排障先看它 |
| `error.type` | 错误大类：4xx 参数类常见 `invalid_request_error`；5xx 常见 `server_error`、`service_unavailable`、`upstream_error` |
| `error.code` | 机器可读的错误码，如 `missing_model`、`unsupported_model` |

成功响应没有 `error` 字段；看到 `error` 就按本篇对号。

## 特例：一种不带 error 信封的 404

不是所有 404 都长上面那样。**非 `/v1` 的协议路径**返回 404 时是裸消息，没有 `error` 信封：

```json
{ "message": "资源不存在" }
```

| 你看到的 | 说明 | 怎么办 |
| --- | --- | --- |
| `{"error":{...}}` | 请求打进了 `/v1` 协议层，是正常的错误信封 | 按本篇逐个对号 |
| `{"message":"资源不存在"}` | 路径不对：`/v1` 前缀下拼错端点（如少个 s）、打到非 `/v1` 的路径，或把管理接口当成了 API | 核对 Base URL 与完整路径 |

## 常见错误逐个对号

### 401：鉴权失败

Key 没传对。报错指向认证环节，与模型、分组无关。

自查顺序：`Authorization: Bearer sk-...` 的形状 → Key 复制完整 → Key 状态正常（[API Keys](/__aisys__/my-api-keys) 页面）。完整清单见《API Key 与认证》。

### 503：`missing_model`（type `service_unavailable`）

请求体里没有 `model` 字段，而这把 Key 绑定分组内的账户都需要按支持模型匹配——没有模型名就没法筛账户，调度在进入路由前就停了。

修法：补上 `model`，模型名从 `GET /v1/models` 里复制（见《模型列表》）。

### 503：`unsupported_model`（type `service_unavailable`）

报错原文："当前分组无账户支持请求模型：X"。含义：你这把 Key 绑定的路由链路上，没有任何账户直接支持 X，模型映射也没命中。

自查三步：

1. 模型名是否与 `GET /v1/models` 返回的完全一致（拼写、大小写）。
2. X 在不在你的列表里——不在就是链路不覆盖。
3. 都对还报错，找管理员确认路由与目录。

详见《模型列表》与《核心概念》。

### 400：其他参数类（`invalid_request_error`）

请求体本身有问题：JSON 拼写错误、缺必填字段、字段类型不对、取值不被支持。对照对应协议篇检查请求结构：对话见《对话协议 chat completions》，流式见《流式响应 SSE 怎么读》，视频见《视频生成：从提交到取片》，图像与嵌入见《图像生成与文本嵌入》，语音见对应篇目。

### 429：速率或额度受限

请求太密集或额度触顶。等一会儿重试；持续出现就去 [API Keys](/__aisys__/my-api-keys) 与用量页面核对额度（见《用量与统计》），必要时找管理员调整。

### 5xx：`server_error` / `service_unavailable` / `upstream_error`

服务端侧的问题，具体原因以 `error.message` 为准：

```json
{
  "error": {
    "message": "（以实际返回为准）",
    "type": "upstream_error",
    "code": "..."
  }
}
```

| type | 常见含义 | 你能做什么 |
| --- | --- | --- |
| `server_error` | 网关侧内部错误 | 稍后重试；持续出现找管理员 |
| `service_unavailable` | 服务暂不可用（如当前没有可用账户） | 稍后重试 |
| `upstream_error` | 上游真实服务返回了错误，网关如实带回 | 看 `message` 判断；偶发可重试 |

## 重试的正确姿势

- 偶发 5xx、超时：直接重试一两次，多数能过。
- 429：先等再试，立刻连发只会继续撞限制。
- 重试前想一想这个操作是否已有副作用：比如异步任务（视频生成）可能已经创建，先查任务状态再决定要不要重新提交，避免重复建任务（见《视频生成：从提交到取片》）。
- 400 类参数错误**不要重试**：请求本身有问题，重发几次结果一样。

## 按症状定位

| 症状 | 先查什么 | 再看什么 |
| --- | --- | --- |
| 一直 401 | 本篇 401 清单 | 《API Key 与认证》 |
| 一调某个模型就 400 | 模型名与列表对照 | 《模型列表》 |
| 偶发 5xx、超时 | `error.message` 与 type | 本篇 5xx 与重试一节 |
| 疑似多扣钱、账对不上 | [用量记录](/__aisys__/my-usage-records) 逐笔核对 | 《用量与统计》 |
| 行为突然变了（昨天还好好的） | [操作日志](/__aisys__/my-operation-logs)：配置是不是刚被改过 | 联系管理员 |
| 某类请求全部失败、其他正常 | [AI 健康](/__aisys__/my-ai-health)：是不是特定上游出问题 | 联系管理员 |

## 排障工具箱：管理台这几个页面

| 页面 | 用它回答什么问题 |
| --- | --- |
| [用量记录](/__aisys__/my-usage-records) | 这笔请求到底成没成功、计没计费、用了多少——对账的终点 |
| [统计总览](/__aisys__/my-stats) | 整体调用量与消费的大盘，判断影响面 |
| [AI 健康](/__aisys__/my-ai-health) | 上游/账户现在正不正常 |
| [AI 性能](/__aisys__/my-ai-performance) | 延迟、成功率等趋势，判断"变慢变差"从何时开始 |
| [模型探活](/__aisys__/my-model-checks) | 模型可用性的探测结果 |
| [操作日志](/__aisys__/my-operation-logs) | 谁在什么时间改了什么配置 |

健康、性能、探活类页面由管理员维护，普通用户重点用好**用量记录**和**统计总览**这两页。

## 什么时候找管理员，带上什么

自己查过一轮还解决不了，就找管理员，一次把这些信息带全：

| 带什么 | 说明 |
| --- | --- |
| 发生时间 | 精确到分钟，方便对日志 |
| 模型名与端点 | 如 `gpt-5.4` + `/v1/chat/completions` |
| 完整报错 JSON | 信封三个字段都留着，别只截图半行 |
| 请求示例（脱敏后） | curl 或代码片段，**Key 用占位符替换，不要发 Key 全文** |
| 已经验证过什么 | 比如"模型名确认在列表里"，能省一个来回 |
