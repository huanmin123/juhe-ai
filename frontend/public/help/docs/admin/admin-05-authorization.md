# 授权、团队与接收方确认

> 这一篇解决：怎么向个人或团队发起授权、为什么接收方必须先接受、团队审批和成员确认怎么走、授权来源变化怎么处理，以及团队和个人的用量在哪看。一句话定位：授权传递使用权，不传递归属，也不替接收方做绑定决定。

## 开始之前，先确认四件事

1. 授权资源是**个人**还是**团队**目标——决定是个人 offer 还是团队 offer。
2. 团队场景先确认**团队审批人**（团队创建人）有效；审批人失效时才由管理员代行。
3. 额度方案：按 n 小时、日、周、月还是总量限制。
4. 被授权人用什么方式调用——授权给的是“可使用范围”，调用仍走被授权人自己的 API Key 与策略。

## 授权的本质：传使用权，不传归属

授权把账户或分组的使用权授予其他系统账户或团队。四条边界要记牢：

1. **先 offer，后接受。** 发起授权只产生待确认记录，不创建实例、不写分组、不进入调度。
2. **接受后再自行绑定。** 接收方接受后才创建授权实例或分组快照；账户需要接收方自己加入分组，分组需要接收方自己启用，授权方和管理员都不能代绑。
3. **只传使用权，不传管理权。** 被授权用户获得独立授权实例与使用侧调度权；来源凭据、账户归属、供应商 / 协议 / 模型 / 代理 / 并发等来源配置、授权关系本身和删除等敏感操作，仍然只属于资源归属人。
4. **不改变 API Key 路由。** 授权决定可使用范围与用量归属；被授权方自己的 API Key 绑什么策略，仍由他自己配。

## 个人授权：从发起到可用

1. 资源所有者在[授权中心](/__aisys__/authorizations)（管理侧为[统一授权](/__aisys__/authorizations)）选择“发起授权”。
2. 输入接收方的**精确用户名**；普通用户不能批量拉取全量用户列表。管理侧代资源所有者发起时，必须先选择资源所有者，并进入“待资源所有者确认”。
3. 资源所有者确认后（管理员代建场景），接收方在“收到的授权”看到 pending 来源。
4. 接收方核对授权方、来源账户、endpoint host、代理摘要、模型和额度后点击“接受”。
5. 接收方到自己的 AI 账户页把授权实例加入自己的分组；接受本身不会自动绑定。
6. 只有完成绑定后，授权实例才参与调度。

管理员不能代替资源所有者确认，也不能代替接收方接受或绑定；需要收回访问时使用“回收”，不要使用“归还”。

## 团队授权：审批 + 成员逐人确认

团队授权不是“一次性给全团队生效”：

1. 管理员在[授权团队](/__aisys__/authorization-teams)创建团队、加入成员，并确认团队创建人（团队审批人）。
2. 资源所有者按**精确团队名**发起团队 offer；管理侧代建同样先经资源所有者确认。
3. 团队审批人在“授权中心 → 团队审批”同意或拒绝。同意只代表进入成员确认流程，不代表成员已经接受。
4. 团队审批通过后，系统为每个符合条件的成员创建 pending 成员来源；每个成员必须自己接受，接受后才创建实例或分组快照。
5. 成员接受后仍需自行绑定账户或启用分组；系统不会自动加入任何成员的分组。
6. 新成员加入团队时只收到 pending 来源，不会自动继承已生效的团队授权；成员接受后才生效。
7. 团队审批人失效、缺失或与授权方为同一账户时，管理员可以代行审批并写操作日志；审批人有效时管理员不得越权代行。

团队审批通过但没有可发送成员时，授权会保持“待成员确认”直到成员出现或到期，不会立刻变成“已拒绝”。

## 来源变化与重新确认

来源账户的上游地址、代理、协议档案、连接 preset、端点模式、支持模型、模型映射、OAuth 主体或 API Key 身份指纹发生变化时：

- 相关非终态来源进入“需重新确认”，网关立即停止使用该来源；
- 接收方在授权中心看到字段级变更摘要，携带当前修订号重新确认后才恢复；
- 授权方不能替接收方重新确认，也不能通过修改来源账户绕过确认；
- 分组授权新增账户不会自动进入已接受范围，接收方需要查看范围差异、刷新范围，并对修订变化的账户逐账户重新确认。

## 生命周期动作与接收方可见性

| 动作 | 接收方看得到吗 | 还能用吗 | 说明 |
| --- | --- | --- | --- |
| 暂停 | 看得到 | 不能用 | 可由资源所有者或管理员治理触发 |
| 过期 | 看得到 | 不能用 | 到期后按规则延长或重新发起 |
| 恢复（从暂停） | 看得到 | 恢复可用 | 不自动恢复旧绑定 |
| 回收 | 来源撤销 | 不能用 | 管理员收回访问用回收，不伪装成归还 |
| 归还 | 来源归还 | 不能用 | 只能由接收方按来源操作 |
| 拒绝 | 来源拒绝 | 不能用 | 写 24h cooldown |
| 屏蔽 | 屏蔽列表 | 后续 offer 被抑制 | 接收方可以按授权方或资源屏蔽 |

> ⚠️ 回收与归还对接收方是“来源不可用”，暂停是“看得见但不可调度”。团队操作前先沟通，避免对方误判为故障。

## 管理员治理能力

- **暂停发起授权**：在[系统账户管理](/__aisys__/system-accounts)打开账户的“授权发起状态”，可暂停或解除。暂停后该账户不能创建、延长、恢复、reinvite、确认管理员代建 offer 或增加额度，只能缩短、暂停、回收。
- **查看屏蔽记录**：管理侧“统一授权 → 屏蔽记录”用于滥用调查；不展示给团队审批人。
- **团队审批代行**：只在审批人失效、缺失或与授权方同一时使用，并写操作日志。
- **不能代绑定**：管理员不得在账户、分组或路由策略页面代替接收方绑定授权实例或启用授权分组。

## 看团队与用户用量

资源与消耗分开看是有意设计：授权中心 / 统一授权页面**不展示消耗统计**，看用量去两个明细页。

| 页面 | 回答什么问题 | 典型用法 |
| --- | --- | --- |
| [授权团队](/__aisys__/authorization-teams) | 有哪些团队、每个团队有哪些成员、审批人是谁 | 维护团队和成员；变更前核对影响成员与资源可见性 |
| [团队消耗明细](/__aisys__/authorization-team-usage) | 按日期范围，每个被授权团队的消耗是多少 | 配额与费用核对；可跳转到团队成员用户消耗 |
| [用户消耗明细](/__aisys__/authorization-user-usage) | 按日期范围，每个被授权用户的消耗是多少（含被授权团队里的成员用户） | 逐人核对授权产生的用量和归属 |

对账建议的顺序：先在团队消耗页看总量是否符合预期，发现异常再进用户消耗页下钻到成员个人，最后用使用记录核对具体调用。

两个对账时容易忽略的事实：

1. 团队消耗页能**跳转到成员用户消耗**，不用重新选条件；
2. 归属人自己的自用消耗不在授权消耗统计里——发现“总量比账单小”时先核对这一点。

## 授权常见问题对照

| 现象 | 最可能原因 | 去哪看 |
| --- | --- | --- |
| 接收方看不到授权 | offer 还在待所有者确认/团队审批，或已被拒绝/回收 | 统一授权的状态和团队审批页 |
| 接收方接受了但用不了 | 还没绑定分组/启用授权分组，或来源进入需重新确认 | 授权中心“绑定”列 + 来源状态 |
| 看得到但用不了 | 授权被暂停、已过期或额度用尽 | 统一授权列表 + 授权额度配置 |
| 来源账户改了配置后突然不可用 | material change 触发 `needs_review` | 授权中心“需复核” |
| 用量归属和预期不符 | 团队成员最近有进出；或把归属人自用算进了授权消耗 | 用户消耗明细 + 授权团队成员列表 |
| 授权实例不参与调度 | 来源账户停用、异常、删除，或授权分组未启用 | 归属人原账户状态 + 授权分组启用状态 |
| 再次授权没有自动恢复旧绑定 | 新来源需要重新接受并重新绑定，这是预期行为 | 授权中心状态与绑定列 |

## 系统账户与角色：授权范围异常先查这里

[系统账户管理](/__aisys__/system-accounts)维护后台登录账号、角色、状态和初始密码；仅超级管理员可执行敏感账户写入。

排查“某人写不进 / 看不到”时，按这个顺序：

1. 确认该账号的角色是否覆盖目标操作范围；
2. 确认相关来源是否处于 `active`，是否被暂停、过期、需重新确认或额度用尽；
3. 确认团队审批人是否有效、团队成员关系最近是否变化过；
4. 确认接收方是否已完成绑定/启用。

不要用改资源配置的方式绕过授权边界——那是《风险操作与排障》里点名的高危做法。

## 附录：代用户导入要点

管理员可以**代目标系统账户**执行批量导入，把结构化来源资料变成待检查账户。导入与授权是两种不同的“把资源交付给别人”：

| | 授权 | 代用户导入 |
| --- | --- | --- |
| 交付什么 | 已有资源的使用权 | 新账户本身（装进目标系统账户名下） |
| 所有权 | 不变，仍属归属人 | 归目标系统账户 |
| 凭据 | 被授权人不可见 | 随导入资料写入 |

导入不替来源确认凭据真实可用——检查通过前，导入账户不承接流量。

### 导入的硬性约束

| 要点 | 说明 |
| --- | --- |
| 目标选择 | 先选目标系统账户，导入的账户装进谁的名下 |
| 格式 | 只接受 `juhe-ai-account-import v1` JSON；单次约 256KB，最多 50 个账户、20 个代理 |
| 来源资料 | 来源里没有的凭据、模型或账号 ID 不要补全；不确定的信息放进 notes 字段 |
| 分组 | 不存在的分组可按选项自动创建 |
| 同名账户 | 可按选项跳过 |
| 代理引用 | 必须指向已存在的代理，需要时先在[代理管理](/__aisys__/proxies)建好 |
| 激活 | 导入完成后账户以 `pending_test` 等待后台激活检查，检查通过并满足候选条件后才参与调度 |

### 导入四步

1. **准备来源资料**：整理为 `juhe-ai-account-import v1` JSON。
2. **选择目标系统账户，执行“解析预览”**：逐项处理预览提示——协议档案、分组归属、代理引用与重复项。
3. **确认导入选项**：自动建组、跳过同名等按需勾选。
4. **等待后台激活检查**：检查通过并满足候选条件后才参与调度。

> ⚠️ 导入不是验证。即使来源写明 `active`，导入账户仍以 `pending_test` 创建；对上游可用性的最终确认，永远来自后台检查与真实调用证据。
