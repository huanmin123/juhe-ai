# 授权与团队

> 这一篇解决：怎么把账户或分组的使用权授予团队成员、团队和个人的用量在哪看、授权的生命周期怎么管，以及附录——代用户导入的要点。一句话定位：授权传递使用权，不传递归属。

## 开始之前，先确认三件事

1. 授权对象是**个人**还是**团队**——决定走哪条配置路径。
2. 额度方案：按 n 小时、日、周、月还是总量限制。
3. 被授权人用什么方式调用——授权给的是"可使用范围"，调用仍走被授权人自己的 API Key 与策略。

## 授权的本质：传使用权，不传归属

授权把账户或分组的使用权授予其他系统账户或团队。三条边界要记牢：

1. **只传使用权，不传管理权。** 被授权用户获得的是独立授权实例与使用侧调度权；来源凭据、账户归属、供应商 / 协议 / 模型 / 代理 / 并发等来源配置、授权关系本身和删除等敏感操作，仍然只属于资源归属人。
2. **不能绕过敏感凭据隔离。** 被授权人看不到也拿不到来源凭据。
3. **不改变 API Key 路由。** 授权决定可使用范围与用量归属；被授权方自己的 API Key 绑什么策略，仍由他自己配。

## 授权实例：被授权人拿到的是什么

账户授权生效后，系统为被授权用户创建**独立的授权实例账户**：

| 方面 | 归属人原账户 | 被授权人的授权实例 |
| --- | --- | --- |
| 状态、冷却、用量归属 | 归属人自己的 | 实例独立维护，互不影响 |
| 分组绑定 | 绑原账户 | 绑的是实例，不是原账户 |
| 历史与本地状态 | —— | 来源不可用时实例仍保留自己的历史与本地状态 |

**来源可用性是实际调度的硬条件**：归属人原账户停用、异常或删除时，授权实例退出调度候选。

判断依据：被授权人说"我用不了"时，先看归属人原账户的状态——这不是授权配置坏了，是设计如此。

## 团队与用量归属

团队授权进入系统后同步为最终用户授权。成员变化影响的是**后续**用量归属：

| 变化 | 对用量归属的影响 |
| --- | --- |
| 新成员加入 | 加入后的消耗计入团队 |
| 成员移除 | 移除后的后续调用不再计入 |
| 归属人自用 | 授权消耗统计**不包含**资源归属人自己的自用消耗 |

移除成员不会追溯扣减历史用量；需要修正历史归属时，以消耗明细页的记录为准逐日核对。

## 团队维护的完整路径

从建团队到看消耗，四步：

1. **建团队**：在[授权团队](/__aisys__/authorization-teams)创建团队、加入成员。
2. **授权给团队**：在[统一授权](/__aisys__/authorizations)把账户或分组授权给团队，配置额度。
3. **看团队消耗**：在[团队消耗明细](/__aisys__/authorization-team-usage)按日期范围核对总量。
4. **下钻到人**：发现异常时进入[用户消耗明细](/__aisys__/authorization-user-usage)逐成员核对。

## 创建与管理授权

在[统一授权](/__aisys__/authorizations)页面操作。创建前先确认：

1. **资源所有者**是谁——授权记录挂在归属人名下；
2. **受授权对象**是哪个用户或团队；
3. **有效状态**是否符合预期——生效时间与额度。

**额度**：授权可配置 n 小时、日、周、月与总美元额度，避免共享资源被超额使用。同一资源对同一被授权目标再次授权时，复用原授权记录，不会产生重复授权。

**生命周期动作与被授权人的可见性**：

| 动作 | 被授权人看得到吗 | 还能用吗 |
| --- | --- | --- |
| 暂停 | 看得到 | 不能用 |
| 过期 | 看得到 | 不能用 |
| 恢复（从暂停） | 看得到 | 恢复可用 |
| 回收 | 看不到 | 不能用 |
| 归还 | 看不到 | 不能用 |

> ⚠️ 回收与归还对被授权人是"直接消失"，暂停是"看得见用不了"。对外部团队操作前先沟通，避免对方误判为故障来报障。

## 看团队与用户用量

资源与消耗分开看是有意设计：统一授权页面**不展示消耗统计**，看用量去两个明细页。

| 页面 | 回答什么问题 | 典型用法 |
| --- | --- | --- |
| [授权团队](/__aisys__/authorization-teams) | 有哪些团队、每个团队有哪些成员 | 维护团队和成员；变更前核对影响成员与资源可见性 |
| [团队消耗明细](/__aisys__/authorization-team-usage) | 按日期范围，每个被授权团队的消耗是多少 | 配额与费用核对；可跳转到团队成员用户消耗 |
| [用户消耗明细](/__aisys__/authorization-user-usage) | 按日期范围，每个被授权用户的消耗是多少（含被授权团队里的成员用户） | 逐人核对授权产生的用量和归属 |

对账建议的顺序：先在团队消耗页看总量是否符合预期，发现异常再进用户消耗页下钻到成员个人，最后用使用记录核对具体调用。

两个对账时容易忽略的事实：

1. 团队消耗页能**跳转到成员用户消耗**，不用重新选条件；
2. 归属人自己的自用消耗不在授权消耗统计里——发现"总量比账单小"时先核对这一点。

## 授权常见问题对照

| 现象 | 最可能原因 | 去哪看 |
| --- | --- | --- |
| 被授权人完全看不到资源 | 授权被回收 / 归还，或尚未生效 | 统一授权列表的授权状态 |
| 看得到但用不了 | 授权被暂停、已过期或额度用尽 | 统一授权列表 + 授权额度配置 |
| 用量归属和预期不符 | 团队成员最近有进出；或把归属人自用算进了授权消耗 | 用户消耗明细 + 授权团队成员列表 |
| 授权实例不参与调度 | 来源账户停用、异常或删除——来源可用性是硬条件 | 归属人原账户状态（AI 健康监控） |
| 再次授权生成新记录的期待落空 | 同一资源对同一目标再次授权复用原记录 | 属预期行为，不是重复授权失败 |

## 系统账户与角色：授权范围异常先查这里

[系统账户管理](/__aisys__/system-accounts)维护后台登录账号、角色、状态和初始密码；仅超级管理员可执行敏感账户写入。

排查"某人写不进 / 看不到"时，按这个顺序：

1. 确认该账号的角色是否覆盖目标操作范围；
2. 确认相关授权是否处于生效状态（未暂停、未过期、额度未用尽）；
3. 确认团队成员关系最近是否变化过——成员变化改变可见与归属。

不要用改资源配置的方式绕过授权边界——那是《风险操作与排障》里点名的高危做法。

## 附录：代用户导入要点

管理员可以**代目标系统账户**执行批量导入，把结构化来源资料变成待检查账户。导入与授权是两种不同的"把资源交付给别人"：

| | 授权 | 代用户导入 |
| --- | --- | --- |
| 交付什么 | 已有资源的使用权 | 新账户本身（装进目标系统账户名下） |
| 所有权 | 不变，仍属归属人 | 归目标系统账户 |
| 凭据 | 被授权人不可见 | 随导入资料写入 |

导入不替来源确认凭据真实可用——检查通过前，导入账户不承接流量。

### 导入的硬性约束

| 要点 | 说明 |
| --- | --- |
| 目标选择 | 先选目标系统账户，导入的账户装进谁的名下 |
| 格式 | 只接受 `juhe-ai-account-import v1` JSON；单次约 256KB，最多 50 个账户、20 个代理 |
| 来源资料 | 来源里没有的凭据、模型或账号 ID 不要补全；不确定的信息放进 notes 字段 |
| 分组 | 不存在的分组可按选项自动创建 |
| 同名账户 | 可按选项跳过 |
| 代理引用 | 必须指向已存在的代理，需要时先在[代理管理](/__aisys__/proxies)建好 |
| 激活 | 导入完成后账户以 `pending_test` 等待后台激活检查，检查通过并满足候选条件后才参与调度 |

### 导入四步

1. **准备来源资料**：整理为 `juhe-ai-account-import v1` JSON。
2. **选择目标系统账户，执行"解析预览"**：逐项处理预览提示——协议档案、分组归属、代理引用与重复项。
3. **确认导入选项**：自动建组、跳过同名等按需勾选。
4. **等待后台激活检查**：检查通过并满足候选条件后才参与调度。

> ⚠️ 导入不是验证。即使来源写明 `active`，导入账户仍以 `pending_test` 创建；对上游可用性的最终确认，永远来自后台检查与真实调用证据。
