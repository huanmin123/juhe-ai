# 授权、团队与使用管理

> 这一篇解决：怎么向个人或团队发起授权、接收方怎么领取、领取后能做什么不能做什么，以及团队和个人的用量在哪看。一句话定位：授权传递使用权，不传递归属；发送即达，领取即生效。

## 开始之前，先确认两件事

1. 授权资源是**个人**还是**团队**目标——个人授权产生 1 条待领取来源，团队授权按在册成员各产生 1 条。
2. 被授权人用什么方式调用——授权给的是「可使用范围」，调用仍走被授权人自己的 API Key 与策略。

## 授权的本质：传使用权，不传归属

授权把账户或分组的使用权授予其他系统账户或团队。四条边界要记牢：

1. **发送即达。** 发起授权直接送达接收方的授权中心（grant=`pending`），没有所有者确认、团队审批或成员接受等中间环节。
2. **领取即生效。** 接收方点击领取：账户授权一步完成「创建授权实例 + 绑定自己分组」（可选目标分组，缺省用默认分组）；分组授权立即生效，之后可在路由策略中引用。没有第二步绑定或启用。
3. **只传使用权，不传管理权。** 被授权用户获得独立授权实例与使用侧调度权；来源凭据、账户归属、供应商 / 协议 / 模型 / 代理等来源配置、授权关系本身和删除等敏感操作，仍然只属于资源归属人。
4. **不改变 API Key 路由。** 授权决定可使用范围与用量归属；被授权方自己的 API Key 绑什么策略，仍由他自己配。

## 个人授权：从发起到可用

1. 资源所有者在[授权中心](/__aisys__/my-authorizations)选择「发起授权」（管理员在[统一授权](/__aisys__/authorizations)代发起）。
2. 输入接收方的**精确用户名**；普通用户不能批量拉取全量用户列表。管理侧代资源所有者发起时先选择资源所有者——代建与本人发起行为完全一致，直接发送。
3. 接收方在「收到的授权」看到待领取来源，核对授权方、资源、供应商、到期时间后点击「领取」。
4. 账户授权：领取时选择（或缺省）自己的分组，实例创建并绑定一步完成，立即参与调度；分组授权：领取即生效，之后在自己的路由策略中引用该分组。

重复发起同资源同接收方：已有待领取的幂等返回，已生效/已暂停的提示已存在，历史终态记录不复活——重新发起就是一条全新授权。

## 团队授权：按成员分发

团队授权不是「一次性给全团队生效」，而是按成员逐人落地：

1. 管理员在[授权团队](/__aisys__/authorization-teams)创建团队、加入成员。
2. 资源所有者按**精确团队名**发起团队授权；系统为每个在册活跃成员（不含资源所有者自己）各生成一条待领取来源。
3. 每个成员在授权中心各自领取自己的来源；谁领取谁生效，未领取的成员不受影响。
4. 新成员加入团队后也会获得待领取来源，可再领取；成员被移出团队时其来源立即撤销、调度停止。
5. 成员拒绝或归还只影响自己的来源，不影响其他成员。

没有「团队审批」环节；团队只是分发渠道，同意权在每位成员自己手里。

## 生命周期动作

| 动作 | 谁执行 | 接收方还能用吗 | 说明 |
| --- | --- | --- | --- |
| 暂停 / 恢复 | 资源所有者 | 暂停期间不能用 | 恢复后按来源状态重新生效 |
| 延长 | 资源所有者 | 视到期情况 | 已到期（`authorization_expired`）的授权可延长恢复；曾领取的来源恢复生效，未领取的恢复为待领取 |
| 缩短到期 | 资源所有者 | 到期后不能用 | 新到期时间必须晚于当前时刻 |
| 回收 | 资源所有者 / 管理员 | 不能用 | 收回访问用回收；历史记录保留 |
| 归还 | 接收方 | 不能用 | 授权中心按来源归还；账户列表没有归还按钮 |
| 拒绝 | 接收方 | 不能用 | 待领取阶段直接拒绝 |
| 到期 | 系统 | 不能用 | 设置了有效期的授权到期自动翻转；未设置有效期的待领取来源不会过期 |

> ⚠️ 回收与归还是「来源不可用」，暂停是「看得见但不可调度」。团队操作前先沟通，避免对方误判为故障。

## 授权实例使用面

被授权账户在接收方处几乎等价自有账户使用，但有几条硬边界：

- **限频可下调、不能超过来源**：实例的并发数 / 每分钟请求数可以在账户列表行内下调，超过来源账户限值会被拒绝；来源不限时实例可自设。多个接收人共用同一源账户时，共享源账户的全局并发与每分钟请求数预算。
- **可改调度标记**：组内优先级、降级备用、超级优先可以调整，只影响自己的实例。
- **可停用/启用**：停用自己的实例只影响自己。
- **无编辑、无克隆**：来源凭据、上游地址、模型映射、代理、健康检查等来源字段全部只读跟随来源账户，不可克隆、导入、导出或转授权。
- **归还入口唯一**：账户列表无归还按钮，归还统一在授权中心按来源执行；分组授权退订保留在分组列表。

## 看团队与用户用量

资源与消耗分开看是有意设计：授权中心 / 统一授权页面**不展示消耗统计**，看用量去两个明细页。

| 页面 | 回答什么问题 | 典型用法 |
| --- | --- | --- |
| [授权团队](/__aisys__/authorization-teams) | 有哪些团队、每个团队有哪些成员 | 维护团队和成员；变更前核对影响成员与资源可见性 |
| [团队消耗明细](/__aisys__/authorization-team-usage) | 按日期范围，每个被授权团队的消耗是多少 | 配额与费用核对；可跳转到团队成员用户消耗 |
| [用户消耗明细](/__aisys__/authorization-user-usage) | 按日期范围，每个被授权用户的消耗是多少（含被授权团队里的成员用户） | 逐人核对授权产生的用量和归属 |

对账建议的顺序：先在团队消耗页看总量是否符合预期，发现异常再进用户消耗页下钻到成员个人，最后用使用记录核对具体调用。

两个对账时容易忽略的事实：

1. 团队消耗页能**跳转到成员用户消耗**，不用重新选条件；
2. 归属人自己的自用消耗不在授权消耗统计里——发现「总量比账单小」时先核对这一点。

## 授权常见问题对照

| 现象 | 最可能原因 | 去哪看 |
| --- | --- | --- |
| 接收方看不到授权 | 来源已被拒绝 / 回收，或团队授权还没展开到该成员 | 统一授权的状态与来源领取计数 |
| 接收方领取后用不了 | 源账户停用 / 异常 / 冷却 / 到期，或实例被自己停用 | 归属人原账户状态 + 授权实例状态 |
| 看得到但用不了 | 授权被暂停或已过期 | 统一授权列表状态 |
| 限频保存被拒 | 实例限频超过来源账户限值 | 来源账户的并发 / 每分钟上限 |
| 用量归属和预期不符 | 团队成员最近有进出；或把归属人自用算进了授权消耗 | 用户消耗明细 + 授权团队成员列表 |
| 再次授权没有自动恢复旧绑定 | 重新发起是全新授权，需要重新领取；这是预期行为 | 授权中心状态 |
| 想收回某人的访问 | 用「回收」，不是删除账户 | 统一授权行操作 |

## 系统账户与角色：授权范围异常先查这里

[系统账户管理](/__aisys__/system-accounts)维护后台登录账号、角色、状态和初始密码；仅超级管理员可执行敏感账户写入。

排查「某人写不进 / 看不到」时，按这个顺序：

1. 确认该账号的角色是否覆盖目标操作范围；
2. 确认相关来源是否处于生效状态，是否被暂停、过期或已归还；
3. 确认团队成员关系最近是否变化过（移除成员会立即撤销其来源）；
4. 确认接收方的实例是否被自己停用。

不要用改资源配置的方式绕过授权边界——那是《风险操作与排障》里点名的高危做法。

## 附录：代用户导入要点

管理员可以**代目标系统账户**执行批量导入，把结构化来源资料变成待检查账户。导入与授权是两种不同的「把资源交付给别人」：

| | 授权 | 代用户导入 |
| --- | --- | --- |
| 交付什么 | 已有资源的使用权 | 新账户本身（装进目标系统账户名下） |
| 所有权 | 不变，仍属归属人 | 归目标系统账户 |
| 凭据 | 被授权人不可见 | 随导入资料写入 |

导入不替来源确认凭据真实可用——检查通过前，导入账户不承接流量。

### 导入的硬性约束

| 要点 | 说明 |
| --- | --- |
| 目标选择 | 先选目标系统账户，导入的账户装进谁的名下 |
| 格式 | 只接受 `juhe-ai-account-import v1` JSON；单次约 256KB，最多 50 个账户、20 个代理 |
| 来源资料 | 来源里没有的凭据、模型或账号 ID 不要补全；不确定的信息放进 notes 字段 |
| 分组 | 不存在的分组可按选项自动创建 |
| 同名账户 | 可按选项跳过 |
| 代理引用 | 必须指向已存在的代理，需要时先在[代理管理](/__aisys__/proxies)建好 |
| 激活 | 导入完成后账户以 `pending_test` 等待后台激活检查，检查通过并满足候选条件后才参与调度 |

### 导入四步

1. **准备来源资料**：整理为 `juhe-ai-account-import v1` JSON。
2. **选择目标系统账户，执行「解析预览」**：逐项处理预览提示——协议档案、分组归属、代理引用与重复项。
3. **确认导入选项**：自动建组、跳过同名等按需勾选。
4. **等待后台激活检查**：检查通过并满足候选条件后才参与调度。

> ⚠️ 导入不是验证。即使来源写明 `active`，导入账户仍以 `pending_test` 创建；对上游可用性的最终确认，永远来自后台检查与真实调用证据。
