# AI 账户与供应商接入

> 这一篇解决：怎么创建一个 AI 账户、创建后为什么要等检查激活、七种生命周期状态各是什么意思，以及账户接不上时的常见原因。核心原则：不要跳过检查就让新账户承接流量。

## 开始之前，你需要什么

1. 明确账户归属：这个账户建在哪个**目标系统账户**名下。
2. 一份可用的上游凭据：OpenAI OAuth 授权，或 OpenAI API Key。
3. 如果上游需要走代理：代理已先建好（见下文代理边界）。

## 先理解三层边界：供应商、协议档案、代理

### 供应商：目录与计价的归属边界

供应商是账号池、模型目录和价格目录的归属边界。每个 AI 账户必须归属一个供应商；账户能声明哪些模型、按什么口径计价，都在供应商层维护。

调整供应商语义会影响名下全部账户的目录、计价与测试方式——所以供应商层的事在[供应商](/__aisys__/providers)页确认清楚，再动账户。

### 协议档案：页面上叫"接入类型"

协议档案把供应商和协议版本绑定成一个能力档案，页面上以"接入类型"呈现。它决定四件事：

- 账户表单长什么样；
- 凭据类型是 OAuth 还是 API Key；
- 可用端点族与检查请求形态；
- 模型映射规则。

当前系统启用 OpenAI 供应商，支持 **OpenAI OAuth** 与 **OpenAI API Key** 两种账户创建方式。

错误的档案会导致检查和实际请求都失败。配置不能虚构上游能力：不能通过模型别名或接口勾选声明上游不支持的协议——谎报的能力不会让请求成功，只会让检查先失败。

### 代理：账户到上游的网络路径

代理是服务器级全局运维资源，不属于任何用户的私有配置。它只决定某个账户到上游的网络路径，**不改变客户端访问本系统的地址**。

[代理管理](/__aisys__/proxies)里的代理对所有用户可见，普通用户也可以把它绑定到自己的账户。

> ⚠️ 管理员删除或停用代理前，先查被引用账户：停用或删除会立即影响所有绑定它的账户——这些账户到上游的网络路径同时断开。动手前先确认引用账户清单，并和归属人确认。

## 创建一个 AI 账户

在[AI 账户](/__aisys__/accounts)页面创建，按顺序填、按顺序核对：

| 顺序 | 做什么 | 为什么 | 判断标准 |
| --- | --- | --- | --- |
| 1 | 选目标系统账户、供应商与接入类型 | 决定账户归属、模型目录口径和表单形态 | 表单随接入类型切换（OAuth 或 API Key） |
| 2 | 填凭据与 Base URL | 凭据是调用上游的身份；Base URL 决定请求打到哪 | Base URL 填服务根或版本根，**不填具体端点** |
| 3 | 选支持模型、接口能力，按需配模型别名 | 支持模型决定候选过滤及模型别名的目标范围 | 只声明真实上游能处理的协议 |
| 4 | 设并发、优先级，按需绑定代理 | 并发是账户硬上限；优先级小值优先；代理决定到上游的路径 | 特权仅在明确需要超级优先或降级备用时使用，不默认开 |
| 5 | 保存并等待激活检查 | 新配置必须经过后台检查才能承接流量 | 创建后状态为 `pending_test` |

三个容易填错的点：

1. **Base URL**：填服务根或版本根，不填具体端点——端点族由协议档案决定，不是由 Base URL 决定。
2. **模型别名**：客户端侧与上游侧都必须满足当前协议档案和支持模型的限制，两端都要核对。
3. **多 API Key**：一个账户可以配多个 Key 轮询或权重轮询（权重范围 1-100）；注意多 Key 账户不能查询余额。

## 检查激活：从 pending_test 到 active

新账户、导入的账户，或凭据、Base URL、协议档案、关键代理等**连接配置变更**保存后，账户都会回到 `pending_test` 等待后台激活检查。**检查通过后自动进入 `active`**，这期间不需要人工干预。

### 谁在触发状态变化

区分"谁在触发"很重要，它决定了你该等还是该动：

- **后台系统**：激活检查、周期健康检测、运行态恢复、冷却恢复——状态变化由这些机制维护，你要做的是等证据。
- **人工动作**只有三种：停用 / 启用、"恢复正常"强确认放行、"重新检查"。

其中"重新检查"只重置检查窗口并交给后台确认，**不直接放行**——点了它之后账户还是要等后台结论。

### 人工测试不改写状态

人工测试只生成诊断任务、使用记录和审计，成功或失败都**不**改写账户状态、调度开关、冷却或健康事实。

账户恢复只能由两个途径完成：后台探针的受围栏写回，或独立的"恢复正常"人工操作。

### 验证激活看证据页

- [AI 健康监控](/__aisys__/ai-health)：看检查结果与恢复状态；
- [使用记录](/__aisys__/usage-records)：看激活后第一次真实调用是否命中该账户。

什么时候需要人工介入：检查持续失败且错误说明指向可修的原因（凭据过期、代理失效）——修好配置后等复检；明确接受上游可用性风险时，才用"恢复正常"强确认放行。

## 生命周期状态：每个状态怎么进、怎么出、谁触发

| 状态 | 含义 | 怎么进入 | 怎么离开 |
| --- | --- | --- | --- |
| `pending_test` | 待检查 | 新建、导入，或连接配置变更后 | 后台激活检查通过进入 `active`；或"恢复正常"强确认放行 |
| `active` | 正常 | 激活检查通过，或任一运行状态恢复成功 | 进入某个运行状态、被人工停用，或连接配置变更后重新复检 |
| `temporary_unavailable` | 临时不可调用 | 后台健康检测连续失败达到阈值（系统设置"健康检测连续失败阈值"，默认 3） | 恢复探针成功回到 `active`；暂停有上限，是有界暂停不是永久停用 |
| `rate_limited` | 限流中 | 真实上游账号触发限流策略；普通请求失败不会写入这个状态 | 复测成功恢复 |
| `quality_isolated` | 质量隔离 | 质量问题触发隔离 | 复测通过恢复 |
| `error` | 异常（硬状态，不参与调度） | 异常处置；具体原因看错误码与错误说明 | 排除原因后重新检查或恢复 |
| `disabled` | 停用（人工终态） | 人工从任意状态停用 | 仅人工重新启用，启用后按当前事实重新检查 |

读这张表的三个要点：

1. 四种运行状态（临时不可调用、限流中、质量隔离、异常）是**分叉，不是依次迁移**：恢复或复测成功后各自回到 `active`。
2. **`active` 是进入候选的必要条件，不保证当前可调度。** 还要同时满足调度开关（`schedulable`）、未到期、时间计划、授权来源和运行态可用——五项缺一不可，排查"active 却没流量"时逐项过。
3. **`disabled` 是有意下线，不是故障。** 排障时不要把它和运行状态混在一起看；`error` 状态的账户提示会直接展示最近检查与最近错误的 traceId，顺着查就能定位。

## 账户字段速查

| 字段 | 作用 | 注意 |
| --- | --- | --- |
| 供应商 / 协议档案 | 供应商是分组和账户的过滤边界；档案决定表单、接口能力和映射规则 | 改档案等于改接入契约，保存后账户回 `pending_test` |
| 并发 / 优先级 / 特权 | 并发是账户硬上限；优先级小值优先 | 特权仅在明确需要超级优先或降级备用时使用 |
| 状态与检查 | 决定账户是否进入候选 | 见上节状态机 |
| 多 API Key | 轮询或权重轮询，权重 1-100 | 多 Key 账户不能查询余额 |
| Base URL / 支持模型 | 决定请求打到哪、能服务哪些模型 | 支持模型决定候选过滤及别名目标范围 |
| 接口能力 / 模型别名 | 只声明真实上游能处理的协议 | 别名两端都受协议档案和支持模型限制 |
| 代理 | 仅决定账户到上游的网络路径 | 删除或停用代理前先查被引用账户 |
| 时间计划 | 账户自身的时间窗口约束 | 即使 `active`，窗口外也不参与调度 |

### 人工动作清单

账户相关的人工动作只有这四个，每个都有明确边界：

| 动作 | 效果 | 边界 |
| --- | --- | --- |
| 停用 / 启用 | 人工终态切换 | 停用是有意下线；启用后按当前事实重新检查 |
| 恢复正常 | 强确认放行，跳过等待 | 不适用于授权实例或已过期账户；仍服从时间计划 |
| 重新检查 | 重置检查窗口 | 交给后台确认，不直接放行 |
| 人工测试 | 生成诊断任务、使用记录和审计 | 不改写状态、调度开关、冷却或健康事实 |

## 常见接入问题

| 症状 | 最可能原因 | 去哪看 |
| --- | --- | --- |
| 一直停在 `pending_test` | 激活检查持续失败：凭据失效、Base URL 不可达、代理不通或协议档案与上游不符 | AI 健康监控的最近检查结果与错误说明 |
| 想让新账户立刻可用 | 等不及后台检查 | "恢复正常"强确认放行（不适用于授权实例或已过期账户，且仍服从账户时间计划） |
| `active` 却没被调度 | 调度开关、到期时间、时间计划、授权来源或运行态有一项不满足 | 账户详情逐项核对，再用使用记录验证 |
| 请求偶发失败就想停用 | 一次失败不构成停用依据 | 先查使用记录与健康证据，再决定重新检查、避让或停用 |
| 上游返回内容异常 | 响应不符合协议语义 | 用[响应检查策略](/__aisys__/response-inspection-policies)按真实响应证据编写匹配和处置 |
| 多 Key 账户查不到余额 | 多 Key 账户不支持余额查询 | 属预期行为，不是故障 |
| 改了连接配置后账户不可用 | 凭据、Base URL、协议档案、关键代理变更后回到 `pending_test` | 等后台激活检查，或按需强确认放行 |

### 响应检查策略：先观察，再扩大处置范围

[响应检查策略](/__aisys__/response-inspection-policies)根据真实响应匹配后执行处置，要点：

- **作用层级**：先选协议；供应商层只作用于选定同协议供应商，协议层作用更广。
- **匹配条件**：可按客户端、输出文字、结束状态、`error.code`、`error.type`、错误消息、单条 SSE 原文或 JSON 字段路径匹配；至少需要一个正向条件。
- **处置模板**：先观察只记日志；丢事件只适合独立 SSE 垃圾事件；重试/避让账户会改变本次或后续请求的候选范围。规则不确定时先观察命中。
- **优先级 / 启用**：优先级为 1-9999，小值先处理；停用可保留规则但不产生处置。

> ⚠️ 新规则先"观察"模式跑一段时间，确认命中范围无误后再启用实际处置，避免误伤正常流量。

验证方法：用[运行日志](/__aisys__/runtime-logs)（页面名"日志搜索"）、[审计日志](/__aisys__/audit-logs)和使用记录交叉查看 traceId、命中规则和最终调用结果。
