# 管理员快速上手

> 这一篇解决：第一次以管理员身份进入系统，先做什么、按什么顺序做。核心只有一句话——先理解影响半径，再改变系统范围的配置；管理模式下的每一次保存，作用的都不是"我的配置"，而是系统范围的事实。

## 开始之前，你需要什么

1. 一个**管理员账号**（角色 `super_admin` 或 `admin`），并且已经登录管理台。
2. 明确这次要接入的**上游凭据**：OpenAI OAuth 账号，或 OpenAI API Key。
3. 如果上游需要走代理：代理的地址与凭据（没有代理也可以先跑通，账户创建时可再绑）。

## 管理员和普通用户有什么不同

普通用户管理的是"自己名下"的资源：自己的账户、自己的分组、自己的 Key。管理员管理的是**系统范围的事实**，并能查看全部使用记录、健康证据与日志。

两件事从第一天起就要适应：

1. **管理视角下的写入有目标范围。** 管理角色也可以切回用户模式查看自己的资源；但在管理模式下，写入会作用于所选的目标系统账户（即某个后台登录账号名下，见《授权与团队》）或全局配置。保存前先确认"这次改动落在谁头上"。
2. **影响半径决定谨慎程度。** 同样是点一次保存，改一把 Key 只影响一个调用方，改一条共享策略影响所有绑定它的 Key，改一条系统设置影响全部用户与全部请求路径。

## 九类资源与各自的影响半径

管理员管理的资源可以归为九类。不用一次背下来，先知道"有什么、影响多大"：

| 资源 | 管什么 | 影响半径 |
| --- | --- | --- |
| 供应商 | 账号池、模型目录和价格目录的归属边界 | 调整供应商语义会影响名下全部账户的目录、计价与测试方式 |
| 协议档案 | 把供应商和协议版本绑定成账户能力档案，页面呈现为"接入类型" | 改档案等于改一类账户的接入契约 |
| 代理 | 服务器级全局运维资源，决定账户到上游的网络路径 | 停用或删除会立即影响所有绑定它的账户 |
| 分组 | 账户集合与供应商过滤边界 | 停用分组或调整成员，会改变所有经策略绑定它的 API Key 的候选池 |
| AI 账户 | 真实上游凭据、模型能力、并发与运行状态 | 停用或异常会让所在分组少一个候选，影响每一次可能选中它的调用 |
| 策略路由 | 分组选择规则：模式、顺序、权重与调度偏好 | 被多把 API Key 共享，一处修改同时改变全部绑定方的行为 |
| API Key | 调用身份、额度与时间边界 | 影响半径最小：只决定一个调用方能否进入网关 |
| 授权 | 把账户或分组的使用权授予其他系统账户或团队 | 影响被授权方的可用资源与用量归属，不改变资源所有权 |
| 系统设置 | 网关限流、后台任务、超时与保留期等全局运行策略 | 影响半径最大：保存即作用于全部用户与全部请求路径 |

九类资源在页面上的对应关系：供应商、代理、分组、账户、策略路由、API Key 在"AI 管理"菜单；授权与团队在"统一授权管理"菜单；系统设置与服务器级运维在"系统运维"菜单。找到页面，就找到了这类资源的写入入口。

## 三条治理原则

这三条贯穿全部八篇，先记住，后面每一篇都在展开其中一条：

1. **先理解影响半径，再改配置。** 任何写入前先回答：这次改动落在九类资源中的哪一类、会影响谁。影响半径越大的资源（策略、分组、系统设置），越要用"新建副本再切换"而不是就地修改。
2. **用事实验证变更，而不是只看保存成功。** 保存成功只说明写入成功。变更是否达到目的，要看[使用记录](/__aisys__/usage-records)中的实际链路、[AI 健康监控](/__aisys__/ai-health)中的检查与恢复、[操作日志](/__aisys__/operation-logs)中的变更时间线。
3. **警惕共享资源的多米诺效应。** 策略、分组与系统设置天然被多个对象共享：改一处限流会影响全部用户，改一个共享策略会影响绑定它的所有 API Key。共享资源的变更要在低峰期做、小步做，并保留回退路径。

## 第一次进入系统：先做三件确认

| 顺序 | 做什么 | 为什么 | 判断标准 |
| --- | --- | --- | --- |
| 1 | 确认登录的是管理员账号 | 普通角色看不到管理菜单，也无法写入系统范围配置 | 左侧菜单出现"AI 管理""统一授权管理""日志管理""系统运维"分组 |
| 2 | 打开[统计概览](/__aisys__/stats)看全局趋势 | 先确认系统整体是否正常：请求数、失败趋势、Token 消耗、系统性能 | 趋势与团队预期一致，没有突发的失败率上升 |
| 3 | 记住四个菜单分组的位置 | 后面所有操作都按主题落在这四组里 | 能不看文档找到[供应商](/__aisys__/providers)、[AI 账户](/__aisys__/accounts)、[策略路由](/__aisys__/route-strategies)、[系统设置](/__aisys__/settings) |

四个菜单分组的分工，先建立一个心理地图（看一遍即可，后面每篇都会回到这张地图）：

| 菜单分组 | 管什么 | 代表页面 |
| --- | --- | --- |
| AI 管理 | 供应商、代理、账户、分组、策略、Key、模型检测、用量与账户监控 | [AI 账户](/__aisys__/accounts)、[策略路由](/__aisys__/route-strategies) |
| 统一授权管理 | 授权关系、团队、授权消耗 | [统一授权](/__aisys__/authorizations) |

| 系统运维 | 设置、表监控、系统指标、IP、公告、系统账户 | [系统设置](/__aisys__/settings) |

## 第一次接入的最短路径（五步）

管理动作存在一条最小顺序：**供应商 / 代理 → 分组 / 账户 → 策略 → API Key**。按顺序建、按顺序验证，避免入口建好了却调度不到账户。

为什么是这个顺序：后面的每一层都依赖前面一层——账户要入分组，策略要绑分组，Key 要绑策略。跳步建的入口，验证时会发现"调度不到账户"，返工更多。

新手建议第一次严格按顺序走一遍，哪怕某一步"看起来可以跳过"：顺序本身就是为了保证每一步做完都有明确的验证点，出问题时也知道回退到哪一步。

五步速览：

| 步骤 | 在哪做 | 做完的判断 |
| --- | --- | --- |
| 1. 确认基础资源 | [供应商](/__aisys__/providers)、[代理管理](/__aisys__/proxies) | 代理延迟检测正常；账户表单能选到预期供应商 |
| 2. 建分组与账户 | [AI 分组](/__aisys__/groups)、[AI 账户](/__aisys__/accounts) | 账户 `pending_test` → `active`；分组启用 |
| 3. 建策略路由 | [策略路由](/__aisys__/route-strategies) | 模式与分组数量匹配；绑定分组全部启用 |
| 4. 建 API Key | [API Key 管理](/__aisys__/api-keys) | 密钥已复制；状态、额度、时间计划符合预期 |
| 5. 事实验证链路 | [使用记录](/__aisys__/usage-records)、[AI 健康监控](/__aisys__/ai-health)、[操作日志](/__aisys__/operation-logs) | 链路每层落在预期对象，无意外 401/429 |

下面逐步展开"做什么 → 为什么 → 在哪做 → 做完的判断"。

### 第 1 步：确认基础资源

- **做什么**：在[供应商](/__aisys__/providers)确认目标供应商存在；账户需要走代理时，先在[代理管理](/__aisys__/proxies)把代理建好。
- **为什么**：供应商决定账户的模型目录和计价口径；代理决定账户到上游的网络路径，晚建会让账户检查失败。
- **在哪做**：AI 管理 → 供应商；AI 管理 → 代理管理。
- **做完的判断**：代理的最近状态与延迟检测正常；后续账户表单能选到预期供应商与代理。

### 第 2 步：建分组与 AI 账户

- **做什么**：在[AI 分组](/__aisys__/groups)确定供应商边界与分组类型，再到[AI 账户](/__aisys__/accounts)添加账户。
- **为什么**：分组是账户池，只接纳同一供应商的账户；账户是真实凭据的载体，必须先有池再入池。
- **在哪做**：AI 管理 → AI 分组；AI 管理 → AI 账户。
- **做完的判断**：新账户以 `pending_test` 创建，后台激活检查通过后进入 `active`；分组处于启用状态。

### 第 3 步：建策略路由

- **做什么**：在[策略路由](/__aisys__/route-strategies)选择路由模式并绑定分组。
- **为什么**：策略决定 API Key 进入哪个分组池，没有策略的 Key 无法调度到任何账户。
- **在哪做**：AI 管理 → 策略路由。
- **做完的判断**：模式与分组数量匹配——普通模式恰好一个启用分组，权重、故障回退、轮询与合并至少两个；绑定的分组全部启用。

### 第 4 步：建 API Key

- **做什么**：在[API Key 管理](/__aisys__/api-keys)为 Key 绑定策略，按需设置过期时间、美元额度与时间计划。
- **为什么**：Key 是调用身份，把外部调用方接入你刚建好的链路。
- **在哪做**：AI 管理 → API Key 管理。
- **做完的判断**：创建后立即复制完整密钥；状态、额度与时间计划符合调用方预期。

> ⚠️ 完整密钥只在创建或刷新时展示一次，之后列表与日志不再出现明文。创建后立即复制到调用方的安全配置，不要指望以后回来再查。

### 第 5 步：用事实验证链路

发出一次真实调用后核对三处证据：

| 证据页 | 看什么 | 判断标准 |
| --- | --- | --- |
| [使用记录](/__aisys__/usage-records) | 这次调用的分组、账户与模型 | 与配置一致，没有意外的 401 或 429 |
| [AI 健康监控](/__aisys__/ai-health) | 账户的检查与恢复状态 | 无持续失败 |
| [操作日志](/__aisys__/operation-logs) | 本次变更的时间线 | 每一步建库动作都有记录，操作者与预期一致 |

链路每一层都落在预期对象上，第一次接入就完成了。

### 第一次不用做，但要知道在哪

| 事项 | 什么时候需要 | 去哪 |
| --- | --- | --- |
| 授权与团队 | 账户建好后要把使用权交给团队成员 | 《授权与团队》 |
| 模型检测 | 接入验收时验证账户模型可信度 | 《模型目录与模型检测》 |
| 系统设置 | 默认值已经够用；改动前先读规程 | 《系统设置与日常运维》 |
| 公告管理 | 有全员可见的变更要通知时 | 《系统设置与日常运维》 |
| 六类证据页 | 第一次排障之前，先知道每类证据管什么 | 《观测：日志与统计》 |

## 新手常踩的三个误区

| 误区 | 事实 |
| --- | --- |
| "保存成功"就是"变更生效" | 保存成功只说明写入成功；效果要用使用记录、AI 健康监控和操作日志里的事实确认 |
| 用"我的资源"的心态操作管理页 | 管理模式改的是系统范围事实；先确认目标系统账户与全局配置，再保存 |
| 出了问题先停账户或放宽全局限制 | 先定位证据指向的那一层，再做能被证据解释的处置——《风险操作与排障》整篇讲这件事 |

三个误区对应三篇必读：第一个误区对应《观测：日志与统计》，第二个对应本篇与《分组与路由策略》，第三个对应《风险操作与排障》。读完这四篇，日常管理的大部分场景就都有路数了。
