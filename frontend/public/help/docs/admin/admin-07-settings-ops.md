# 系统设置与日常运维

> 这一篇解决：系统设置每一项管什么、默认值是多少、改动前后的规程，以及日常巡检要看哪些页面。核心警示：设置页按分区写入，**保存即可能影响全部用户**——改限流、超时、保留期或账户恢复规则前，先记录当前值、受影响请求类型与回看指标。

## 改设置的共同规程

[系统设置](/__aisys__/settings)的任何变更都走同一套规程，四步缺一不可。

### 第 1 步：记录现值与变更原因

操作日志会留下谁在何时改了什么，但**不会记录你的预期**。先写下来三样东西：

- 原值是多少；
- 想解决什么问题；
- 预期看到什么变化。

回看时才知道"当时想解决什么"，回退时才知道"回到哪个值"。

### 第 2 步：明确影响面

区分这次改动作用于管理面还是网关请求路径：

- **限流**影响管理操作与调用方；
- **超时**影响请求预算；
- **保留期**影响排障与审计窗口。

影响面越大，越要低峰期做、越要提前告知可能受影响的调用方。

### 第 3 步：小步变更

一次只动一个分区的一个值。多个同时改，出了问题无法归因——这是排障纪律在设置域的直接应用。

### 第 4 步：保存后回看

| 看什么 | 去哪 | 判断标准 |
| --- | --- | --- |
| 429 指标 | [统计概览](/__aisys__/stats) / [使用记录](/__aisys__/usage-records) | 限流没有误伤日常操作 |
| 后台任务与健康 | [系统指标统计](/__aisys__/system-metrics-stats) / [AI 健康监控](/__aisys__/ai-health) | 任务仍正常执行 |
| 表增长趋势 | [表监控](/__aisys__/table-monitor) | 保留期调整后增长符合预期 |

## 设置分区逐项说明

### 品牌、请求体与用户额度

影响界面和网关入口。凡是"0 表示不限额"的字段，保存前必须显式确认。

| 设置项 | 范围与默认 | 说明 |
| --- | --- | --- |
| 系统名称 / 图标路径 | 图标默认 `/__aisys__/brand-icon.svg` | 系统名称显示在菜单、浏览器标签和登录标题；图标也可保存 256KB 内 Data URL |
| 文本请求体上限 | 1-64MB，默认 16MB | 调大能承载更长文本上下文，也提高单请求内存压力；不等同图像请求上限 |
| 账户电路独立确认失败次数 | 1-5，默认 2 | 首次 transport 失败先待确认，需要不同请求的独立失败证据；完整 HTTP 响应不计入 |
| 用户每分钟/日/周/月请求数 | 每项 `0` 表示无限 | 限制同一系统用户跨所有 API Key 的网关请求；达到上限后新请求返回 429 |

### 后台接口限流

保护管理面与管理写入。读写限流与突发窗口需要一起看，单独调一个没有意义。

| 设置项 | 说明 | 注意 |
| --- | --- | --- |
| IP 读/写每分钟 | 保护 `/__aisys__/api` 的 GET/HEAD/OPTIONS 与 POST/PATCH/PUT/DELETE；`0` 表示无限 | 属于管理面保护，改前先评估团队日常页面并发 |
| IP 读/写 10 秒突发 | 拦截短时间集中刷新和批量提交 | 设得低于日常页面并发，会让正常管理操作频繁 429 |
| 登录用户读/写每分钟 | 在 IP 限制之外再保护同一登录账户 | 写限制会作用于保存、删除和批量操作 |

### 健康检查、恢复与重试

控制何时探测、何时暂时避让。不要因一次网络波动就缩短全部阈值——阈值的意义就是过滤抖动。

| 设置项 | 范围与默认 | 说明 |
| --- | --- | --- |
| 健康检测间隔 / 错峰窗口 | 默认 1 小时 / 10 分钟 | 只检测长期没有真实成功请求的正常账户；错峰避免大批账号同时打上游 |
| 健康检测连续失败阈值 | 1-10，默认 3 | 达到阈值才允许进入临时不可调用，避免网络抖动误杀 |
| 临时不可调用最大暂停时间 | 1-1440 分钟，默认 2 | 账户先走快速恢复，失败后退避；它不是永久停用 |
| 安全原地重试间隔 / 次数 | —— | 仅对可安全重放且响应头到达前的传输异常生效；完整 HTTP、正文中断、首字截止和副作用请求不使用 |
| 长期不可用观察阈值 | 1-720 小时，默认 12 | 超过后显示长期不可用，仍保留低频复测，不会直接改成异常状态 |

这些阈值直接驱动账户状态机（《AI 账户与供应商接入》）：连续失败达到阈值进入 `temporary_unavailable`；恢复探针成功回到 `active`。调阈值前先想清楚它改变的是"多久进入避让"和"多久尝试恢复"。

### 文本/图像超时与保留期

文本和图像有独立的 attempt 边界，不能用一个数字覆盖全部。

**文本 lane：**

| 设置项 | 范围与默认 | 说明 |
| --- | --- | --- |
| 文本首响应（流式） | —— | 流式请求等待响应头的时间 |
| 文本流式停顿 | —— | 收到内容后的空闲时间上限 |
| 文本未提交寿命 | —— | 尚无模型语义输出的单次尝试寿命 |
| 文本非流式响应等待 | 10-3600 秒，默认 600 | 上游生成完整结果后才返回；超时未收到首个响应即终止当前尝试 |

**图像 lane：**

| 设置项 | 范围与默认 | 说明 |
| --- | --- | --- |
| 图像首响应 / 流式停顿 / 未提交寿命 | —— | 只作用于 image lane；快速模式文本首字截止不适用于图像 |
| 图像整请求总时限 | 60-86400 秒 | 约束一次通用网关图片请求的总墙钟 |
| AI 对话生图总超时 | 60-86400 秒 | 约束站内 `generate_image` 的完整链路 |
| 无可用账号等待 | —— | 仅在完全没有可立即派发候选时累计；当前账号仍在执行或有可派发候选时，不会因为它到达而停止接管 |

**保留期：**

| 设置项 | 默认 | 说明 |
| --- | --- | --- |
| 使用记录保留天数 | 30 | 排障与对账的主窗口 |
| 运行日志索引保留天数 | 14 | 索引清理不删除原始日志文件 |
| 公开日志保留天数 | 30 | 公开接口调用记录的窗口 |

> ⚠️ 保留期是排障与审计的窗口。缩短保留天数等于缩短"能查到多久以前的事实"，收紧前先确认审计需求，并记录原值以便回退。

## 系统运维菜单的其他页面

| 页面 | 管什么 | 注意 |
| --- | --- | --- |
| [表监控](/__aisys__/table-monitor) | 业务库、数据集目录库、使用记录目录库和统计结果库的表大小、行数、文件空闲空间和近期增长 | 执行维护动作前确认精确表和影响范围 |
| [系统指标统计](/__aisys__/system-metrics-stats) | Go Runtime 并发与内存趋势、gateway / jobs 双进程运行状态和后台任务执行历史 | 容量评估与异常排查的第一站 |
| [IP 管理](/__aisys__/ip-stats) | 来源 IP 的请求、Token、成本、失败率、活跃天数、封禁和白名单状态 | 规则变更会改变客户端访问结果 |
| [公开接口授权](/__aisys__/external-integration-sources) | 为外部来源后端签发来源 Token，按接口资源授权控制公开接口访问、到期和限频 | Token 创建后立即保存，之后不再展示 |
| [公告管理](/__aisys__/announcements) | 面向所有登录用户的平台公告，支持重要性标记、发布和下线 | 发布前核对受众、时间与内容，不把维护说明误发给全部用户 |
| [系统账户管理](/__aisys__/system-accounts) | 后台登录账号、角色、状态和初始密码 | 仅超级管理员可执行敏感账户写入 |

> ⚠️ IP 封禁 / 白名单和公开接口授权的 Token 都是"保存即改变访问结果"的操作：前者改变客户端能否进来，后者改变外部系统能调什么。变更前记录现值，变更后立即验证一次典型调用。

## 设置相关的症状速查

改设置前后的典型症状，先对号再动手：

| 症状 | 先查哪个设置 | 判断 |
| --- | --- | --- |
| 管理页面操作频繁 429 | 后台接口限流的 10 秒突发 | 是否低于日常页面并发 |
| 用户新请求返回 429 | 用户每分钟/日/周/月请求数；Key 美元额度 | 区分是用户级限流还是 Key 额度用尽 |
| 账户频繁进入临时不可调用 | 健康检测连续失败阈值、最大暂停时间 | 阈值是否被调得过敏感 |
| 长请求总被中途终止 | 对应 lane 的超时项 | 文本流式、非流式、图像各有独立边界 |
| 查不到较早的记录 | 三类保留天数 | 是否短于排障需要的回看期 |

## 日常巡检清单

建议按固定频率过一遍，每项都有明确判断标准。巡检发现异常时，处置动作遵循《风险操作与排障》的"先缩小再处置"。

| 频率 | 看哪 | 判断标准 | 不达标时先做什么 |
| --- | --- | --- | --- |
| 每天 | [统计概览](/__aisys__/stats) | 请求数与失败趋势无异常尖刺；错误 Top 10 无新增错误码 | 用使用记录定位异常调用，确定影响面 |
| 每天 | 429 指标 | 没有因限流误伤正常调用或管理操作 | 核对限流现值与触发来源，按记录决定是否回退 |
| 每天 | [AI 健康监控](/__aisys__/ai-health) | 无账户长期停留在运行状态 | 持续失败的账户进入处置：先查证据，再决定重新检查、避让或停用 |
| 每周 | [表监控](/__aisys__/table-monitor) | 表大小与增长趋势符合预期，磁盘空闲空间充足 | 增长异常时核对保留期设置与写入来源 |
| 每周 | [系统指标统计](/__aisys__/system-metrics-stats) | 双进程运行状态正常；后台任务执行历史无连续失败 | 任务连续失败先看任务日志，不重启进程碰运气 |
| 每周 | [操作日志](/__aisys__/operation-logs) | 变更记录都可对应到已知操作 | 出现意外写入立即核对操作者与影响范围 |

巡检的两个习惯：

1. **固定顺序。** 先全局趋势、再账户健康、再资源与变更——顺序固定才能对比出"今天哪里不一样"。
2. **异常记账。** 每次巡检发现并处置的异常，留一行记录（现象、原因、动作），下次巡检先核对是否复发。
