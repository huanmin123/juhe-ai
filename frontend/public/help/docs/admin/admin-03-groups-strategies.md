# 分组与路由策略

> 这一篇解决：分组怎么管账户池、策略路由怎么定选组规则、五种路由模式怎么选，以及改动它们之前必须知道的风险。一句话分工：分组决定"有哪些账户可选"，策略决定"请求进哪个池"。

## 开始之前，先想清楚要解决什么

| 你要解决的问题 | 大概率动哪里 |
| --- | --- |
| 新接入一批账户 | 先建分组，再入池账户（《AI 账户与供应商接入》） |
| 新业务要一套调度规则 | 新建策略路由 + 新建 API Key 绑过去 |
| 在多个池之间分配流量 | 已有策略改模式或权重（见"改共享策略的规程"） |
| 主池故障时有备用 | 故障回退模式 |

## 两层各管什么

策略是调控维度，账户是资源维度。四层职责划清楚，配置就不会互相打架：

| 层 | 管什么 | 不管什么 |
| --- | --- | --- |
| 策略路由 | 请求进入哪个分组池：模式、分组绑定、调度偏好 | 不保存凭据，也不替代分组内的账户并发与优先级 |
| 分组 | 账户集合与供应商过滤边界 | 不决定请求从哪来——那是 API Key 与策略的事 |
| 账户 | 池内怎么选号：优先级（小值优先）、并发硬上限、分组类型 | —— |
| API Key | 调用身份，**每把 Key 只绑定一条策略** | 不直接指定上游账户 |

## 分组：建池与字段

在[AI 分组](/__aisys__/groups)页面维护。每个分组绑定一个供应商，它既是账户集合，也是供应商过滤边界——**只接纳同一供应商的账户**（页面上对应"供应商"列）。

| 字段 | 说明 | 注意 |
| --- | --- | --- |
| 供应商边界 | 分组绑定的供应商决定哪些账户可入池 | 修改分组前，先确认相关策略是否仍能选到可用账户 |
| 分组类型 | 见下表 | 按池的流量形态选，不默认高并发 |
| 分组状态 | 启用 / 停用 | 停用分组后，绑定策略不会继续把请求送入该池；重新启用即恢复候选 |
| 名称 / 说明 | 只用于识别，不参与调度 | 建议写业务用途、场景或限制 |

分组类型怎么选：

| 类型 | 调度方式 | 适用 |
| --- | --- | --- |
| 个人分组 | 直接按账户并发调度 | 常规流量、小池 |
| 高并发分组 | 可设置软并发、短队列、单 IP 限制和溢出方式 | 大流量池，需要排队与防止单 IP 打满 |

**做完的判断**：分组处于启用状态；池内账户 `active` 且调度条件满足；绑定该分组的策略在[策略路由](/__aisys__/route-strategies)列表里可见。

> ⚠️ 停用分组或调整成员，会改变所有经策略绑定它的 API Key 的候选池。动手前先在策略列表核对有多少把 Key 受影响，并选择低峰期操作。

## 策略路由：五种模式

在[策略路由](/__aisys__/route-strategies)页面维护。策略决定 API Key 如何选择分组；每一种模式都与分组绑定配合工作，动手前先点透模式语义。

| 模式 | 分组数量要求 | 行为 | 典型场景与风险 |
| --- | --- | --- | --- |
| 普通 | 恰好 1 个启用分组 | 请求直接进入该分组的账号池 | 默认起点：规则最简单、行为最可预期，排障链路最短 |
| 权重 | 至少 2 个启用分组 | 按权重比例分流，所有权重总和不超过 100 | 适合灰度新账户或在多个池之间做成本分层；调整权重立即改变所有绑定 Key 的分流比例 |
| 故障回退 | 至少 2 个启用分组 | 第一行主用，后续备用；主用恢复后流量自动回到主用 | 主备容灾；调整顺序就改变了故障时的落点 |
| 轮询 | 至少 2 个启用分组 | 按当前排列顺序轮换 | 多个等价池均摊；拖动顺序即调度顺序，改动立刻体现在下一个请求 |
| 合并 | 至少 2 个启用分组 | 每次请求把各绑定分组中能服务当前请求模型的账号合并成一个候选池统一调度（直连支持，或经该账号的模型映射 / 跨协议转换承接），不要求各分组上游模型或协议一致 | 大池统一调度提高利用率；代价见下 |

**合并模式的三个代价，选型前想清楚**：

1. 分组隔离在这个模式下**有意失效**，账号混排是预期行为而不是故障；
2. 没有分组回退，用量按实际服务账号所属分组记账；
3. 不区分分组、全池平级。分组添加顺序只在两处起基础作用：调度平局时按添加顺序破平；同一个账号同时出现在多个绑定分组时，按添加顺序决定这笔用量记到哪个分组的账上。

### 模式选型的三条经验

1. **从普通模式起步。** 只有一个分组时它是唯一选择；行为可预期，排障时链路也最短。
2. **权重适合灰度。** 想让新账户先接一小部分流量，用权重而不是改分组成员。
3. **故障回退与轮询都吃顺序。** 前者顺序决定故障落点，后者顺序就是调度顺序——改顺序前先确认新顺序符合预期。

## 调度偏好：成本优先与速度优先

调度偏好是五种模式共享的配置，作用于请求所落分组内的账号调度（合并路由作用于合并池内）。它**不改变策略层的分组选择**，只在请求落到某个分组后影响组内账号排序：

一个常见误解先澄清：调度偏好改的是"组内怎么选账号"，不是"请求进哪个组"。发现流量分布不对时，该改的是模式与分组绑定；发现单个会话切换太频繁或首字太慢，才轮到调度偏好。

| 偏好 | 行为 | 适用 |
| --- | --- | --- |
| 成本优先 | 尽量让同一会话延续同一个账号（会话保持），减少切换带来的上下文与缓存重建开销 | 按用量计费、切换成本高的场景 |
| 速度优先 | 只对文本请求生效：观察"首字延迟"慢的样本，确认慢的账号在观察窗口内被暂时后置。图像请求与有副作用的请求不参与这套切换——不会因为"慢"被取消或改写 | 对首字延迟敏感的文本场景 |

速度优先的两个参数——**首字截止**与**慢速参数**——只在速度优先出现：首字截止是"等多久还没吐出第一个字就算慢"的时长阈值；慢速参数是判定后的观察窗口与后置时长（慢账号后置多久、窗口内表现好则恢复）。两者一起决定"何时确认慢、何时恢复"，具体取值以页面表单提示为准。

## 改共享策略的规程

> ⚠️ 模式与分组绑定是共享规则：任何调整同时作用于所有绑定该策略的 API Key。模式与调度偏好保存后立即生效于全部绑定方。不要在业务高峰就地修改共享策略。

标准规程，四步走：

1. **先记录**：记下受影响的 API Key 清单与当前分组绑定顺序。
2. **核对引用**：在策略列表确认这条策略被多少把 Key 绑定。
3. **新建副本**：要给新业务一套规则、或要变更规则时，新建一个同配置的策略，再把 API Key 绑定到新策略；原策略保持不动，已有流量不同时变化。不要修改原策略后再绑定。
4. **低峰期小步做**：一次只改一个维度，保留回退路径。

**做完的判断**：发一次真实调用，在[使用记录](/__aisys__/usage-records)里确认链路按新规则落到了预期分组；再观察一段时间没有意外 429 或失败。

## API Key 接入要点

在[API Key 管理](/__aisys__/api-keys)页面维护，每把 Key 绑定一条策略：

| 字段 | 说明 | 注意 |
| --- | --- | --- |
| 名称 | 只用于后台识别，不是密钥本身 | 默认 API Key 与 AI 对话 API Key 的名称不可修改 |
| 运行状态 | 只有 `active` 状态接受调用 | 停用的 Key 无法进入网关 |
| 过期时间 | 绝对边界，到达后不可用 | 不被时间计划替代 |
| 美元额度 | 可按 n 小时、日、周、月设置美元上限；额度用尽的请求返回 `429` | 未开启的项目不限制 |
| 时间计划 | 控制哪些星期和时段允许这个 Key 被使用 | 窗口外该 Key 直接不可用，请求会被拒绝（表现为鉴权/状态类错误），窗口内自动恢复 |
| 完整密钥 | 只在创建或刷新时展示一次 | 创建后立即复制到调用方安全配置 |

> ⚠️ 完整密钥只在创建或刷新时展示一次，之后列表与日志不再出现明文。刷新密钥会让旧密钥失效，先协调调用方再操作。

### Key 被拒时按什么顺序查

四个边界条件叠加生效，排查"Key 为什么被拒"按这个顺序过，先查最便宜的：

| 顺序 | 查什么 | 现象 |
| --- | --- | --- |
| 1 | 运行状态 | 非 `active` 直接不可用 |
| 2 | 过期时间 | 到达后不可用，绝对边界 |
| 3 | 美元额度 | 窗口内额度用尽，返回 `429` |
| 4 | 时间计划 | 窗口外调用被暂时跳过 |

四个条件都正常还被拒？那就不是 Key 的问题了——去使用记录看这条策略把它送进了哪个分组，再查分组内账户（《AI 账户与供应商接入》）。

## 常见配置错误对照

| 错误 | 后果 | 正确做法 |
| --- | --- | --- |
| 普通模式绑了多个分组 | 与"恰好一个启用分组"的模式约束不符，保存或调度异常 | 普通模式只绑一个；多池需求换模式 |
| 权重总和超过 100 | 权重模式约束被打破，分流比例失真 | 调整各分组权重，总和不超过 100 |
| 用合并模式却期待分组隔离 | 账号混排是合并模式的预期行为 | 需要隔离就用其他模式或拆策略 |
| Key 绑了已停用的策略 | 该 Key 不再通过它进入分组调度 | 先恢复策略或换绑 |
| 故障回退只配了主用分组 | 主用不可用时无备用可落 | 至少两个启用分组，备用在后续行 |

## 变更后的验证闭环

分组与策略的每次变更，都用同一套验证收尾：

| 证据页 | 看什么 | 判断标准 |
| --- | --- | --- |
| [使用记录](/__aisys__/usage-records) | 命中的分组、账户、模型 | 与变更后的预期一致 |
| [策略路由](/__aisys__/route-strategies) | 关联 API Key 与分组绑定 | 引用关系符合预期，没有误绑 |
| [AI 分组](/__aisys__/groups) | 分组状态与池内账户 | 启用状态、账户可调度 |
