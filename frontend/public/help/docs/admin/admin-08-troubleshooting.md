# 风险操作与排障

> 这一篇解决：哪些操作属于高危、动手前必须确认什么，以及出问题时按症状走哪条定位路径。核心纪律：**先缩小，再处置**；每一步都要有可回看的事实。管理员不应把"恢复服务"理解成先停账户或放宽全局限制——先定位证据指向的那一层，再做能被证据解释的处置。

## 开始之前：排障三问

动手处置任何异常前，先回答三个问题：

1. **影响面多大？** 一个用户、一个分组，还是全部流量——影响面决定处置的谨慎级别。
2. **最近改过什么？** 到[操作日志](/__aisys__/operation-logs)核对失败时间点附近的变更，先排除"变更引入"。
3. **证据在哪？** 至少有一条可回看的事实（一条使用记录、一张健康截图、一条日志），没有证据就没有处置。

一个例子说明三问的用法：某业务方报"对话全挂了"。影响面——只有该业务的 2 把 Key；最近变更——操作日志显示 10 分钟前有人改过它们绑定的共享策略；证据——使用记录里这两把 Key 的请求都落到了新分组，而新分组里没有支持其模型的账户。三问答完，处置动作自然收敛到"把分组绑定改回去"，而不是"停用新分组的账户"。

## 先记住：管理模式改的是系统范围事实

从基础资源到调用入口，管理动作存在一条链：供应商 / 代理 → 分组 / 账户 → 策略 → API Key。每一层被改动时会立即改变什么：

| 层 | 改了会立即改变什么 | 动手前核对 |
| --- | --- | --- |
| API Key | 某个调用身份可否进入网关 | 目标系统账户、绑定策略、状态、额度、有效期和时间计划；它不直接指定上游账户 |
| 策略路由 | 所有绑定它的 API Key 的分组选择行为 | 策略列表的引用计数；需要不同规则时新建同配置策略，再把新 Key 绑定过去 |
| 分组 | 账户候选集合 | 分组保存 `providerCode`，既是账户集合也是供应商过滤边界；确认相关策略仍能选到可用账户 |
| AI 账户 | 上游凭据、可用模型和并发 | 不必因一次请求失败直接停用；先查使用记录和健康证据，再决定检查、避让或停用 |
| 供应商 | 名下全部账户的目录、计价与测试方式 | 不能通过模型别名或接口勾选虚构不支持的协议；错误档案会让检查和实际请求都失败 |

## 高危操作清单

> ⚠️ 下面每一条操作的共同点是：影响的不只是"你正在看的那个对象"，而是所有共享它的对象。低峰期做、小步做、保留回退路径——三条缺一不可。

| 操作 | 影响 | 动手前必须确认 | 回退思路 |
| --- | --- | --- | --- |
| 停用分组 | 所有经策略绑定它的 API Key 失去这个候选池 | 有哪些策略绑定它、池内是否还有其他可用分组 | 重新启用即恢复候选 |
| 就地修改共享策略 | 所有绑定 Key 的行为同时改变 | 引用计数、受影响 Key 清单、当前分组绑定顺序 | 按记录恢复原模式与绑定顺序 |
| 停用 / 删除代理 | 所有绑定它的账户到上游的路径立即断开 | 被引用账户清单 | 重新启用代理；删除不可直接回退，先导出配置 |
| 停用 AI 账户 | 所在分组少一个候选，影响可能选中它的每次调用 | 停用理由是否有证据支撑（健康、使用记录） | 重新启用后按当前事实重新检查 |
| 收紧限流 / 缩短保留期 | 全部用户的请求路径；排障与审计窗口缩短 | 现值、受影响来源、日常并发水位 | 按记录恢复原值 |
| 删除模型 | 已绑定账户需要先解除绑定 | 哪些账户的支持模型或映射引用了它 | 先移除引用再删除，避免连锁失败 |
| 系统设置保存 | 保存即作用于全部用户与全部请求路径 | 现值与变更原因已记录、影响面已明确 | 小步改，一次一个值，按记录回退 |
| 表监控维护动作 | 直接触碰数据库表 | 精确表名与影响范围 | 动作前备份确认 |

## 处置手段从轻到重

定位到层之后，按影响半径从小到大选处置动作，能用轻的不用重的：

| 力度 | 动作 | 什么时候用 | 影响 |
| --- | --- | --- | --- |
| 轻 | 观察与取证 | 原因未明时 | 零影响：只加证据（使用记录筛选、健康时间线、traceId 检索） |
| 轻 | 重新检查 | 怀疑是暂时性失败，需要后台复核 | 只重置检查窗口，交给后台确认，不直接改状态 |
| 中 | 调整调度权重或暂缓入池 | 单个账户或单个池有问题，但服务不能断 | 改变分流比例或候选池，影响绑定方 |
| 中 | 暂停授权 | 授权资源被超用或归属争议 | 被授权人看得到但用不了，可恢复 |
| 重 | 停用账户 / 分组 / 代理 | 证据明确指向该对象且影响面已评估 | 立即改变所有共享方的候选或路径 |
| 重 | 回收授权 / 改全局设置 | 最后手段 | 全量生效，必须先记录现值 |

重的动作永远排在轻的动作之后——除非证据明确且等不起。

这张表也是沟通清单：做中、重力度动作前，把影响面和回退点同步给受影响的调用方——高危操作的沟通义务不因为赶时间而豁免。

## 按症状排障：六张卡

排障的总路数不变：先看证据，再列可能原因，最后只做能被证据解释的处置。

### 1. 请求异常

- **先看证据**：[使用记录](/__aisys__/usage-records)确认 API Key、策略、分组和账户的实际链路；[日志搜索](/__aisys__/runtime-logs)按 traceId 看服务阶段。
- **可能原因**：Key 状态、额度或时间计划拦截；绑定策略不符预期；分组或分组内没有可调度账户。
- **处置**：先核对链路哪一层与预期不符，只修改能解释当前证据的配置；不要跳层处置。
- **常见误判**：看到报错就直接改 Key 额度——先确认链路真正断在哪一层。
- **做完的判断**：同一条链路重放一次，命中对象与预期一致。

### 2. 账户异常

- **先看证据**：[AI 健康监控](/__aisys__/ai-health)的检查结果、账户状态与最近错误说明。
- **可能原因**：凭据失效；模型或协议能力与上游不符；Base URL 或代理不可达；上游限流或临时故障。
- **处置**：先查使用记录与健康证据，再决定重新检查、避让或停用；不必因一次请求失败直接停用。
- **常见误判**：把 `disabled`（人工停用）当成上游故障来处理——停用是有意下线，不是坏掉。
- **做完的判断**：账户状态变化能用检查时间线解释，而不是"重启试试"。

### 3. 性能异常

- **先看证据**：[AI 性能监控](/__aisys__/ai-performance)按账户/模型的趋势；[系统指标统计](/__aisys__/system-metrics-stats)的进程与队列。
- **可能原因**：个别账户持续变慢；高并发分组排队等待；上游整体波动。
- **处置**：单次慢请求不是调整全局超时的充分证据；先缩小到账户和模型，确认是普遍现象再针对性处理。
- **常见误判**：把一次长尾请求当成全局变慢，直接调大全局超时。
- **做完的判断**：趋势窗口内延迟与成功率回到基线，而不是只看某一次请求变快。

### 4. 授权范围异常

- **先看证据**：[系统账户管理](/__aisys__/system-accounts)的角色、[统一授权](/__aisys__/authorizations)的授权状态与[操作日志](/__aisys__/operation-logs)。
- **可能原因**：角色不对应写入受限；授权被暂停、过期或额度用尽；团队成员变化改变了可见与归属。
- **处置**：先确认是当前模式、资源归属还是成员关系问题，再调整授权关系；不要用改资源配置的方式绕过授权边界。
- **常见误判**：给用户加资源来解决看不到的问题——先查角色与授权状态。
- **做完的判断**：被授权方按预期恢复可见或可用，且没有获得超出授权范围的能力。

### 5. 改共享策略引发异常

- **先看证据**：[策略路由](/__aisys__/route-strategies)的关联 API Key 与当前分组绑定；[操作日志](/__aisys__/operation-logs)确认最近变更。
- **可能原因**：就地修改共享策略，所有绑定 Key 的行为同时改变。
- **处置**：先记录受影响 Key 与原分组顺序；要分叉新规则时，新建一个同配置的策略，再将 API Key 绑定到新策略，原策略保持不动。
- **常见误判**：以为只影响测试用的那把 Key——共享策略影响全部绑定方。

> ⚠️ 共享策略没有"小改一下"：引用计数不为 1 时，任何修改都是一次全量流量切换。按记录恢复原值后，仍要用使用记录确认流量落点回来了。

### 6. 收紧限流 / 保留期引发异常

- **先看证据**：[系统设置](/__aisys__/settings)现值；保存后的 429 指标、后台任务与排障数据。
- **可能原因**：突发窗口低于日常页面并发；保留期短于排障与审计窗口需求。
- **处置**：先记录现值和受影响来源，小步收紧并观察是否仍满足需要；必要时按记录恢复原值。
- **常见误判**：一次收紧多个分区——出问题后无法归因是哪一个值。
- **做完的判断**：429 回落到背景水平，且排障窗口仍覆盖业务需要的回看期。

### 六张卡没覆盖的症状怎么办

回到开头的排障三问，并按固定顺序取证：先[使用记录](/__aisys__/usage-records)确定"哪把 Key、哪个分组、哪个账户、什么错误"，再按《观测：日志与统计》的定位路径扩展证据。任何一次排障都建议留下记录，格式见下文"排障记录怎么留"。

## 排障纪律

五条纪律，违反任何一条都可能把小问题变成大事故：

| 纪律 | 为什么 |
| --- | --- |
| 不跳层处置 | 每一步处置都要能被证据解释；解释不了的处置先不做 |
| 人工测试不是状态变更凭证 | 测试成功不代表账户恢复，测试失败也不构成停用依据——状态只由后台检查与恢复机制维护 |
| `disabled` 不是故障 | 人工停用是有意下线；排障时把它和运行状态混在一起看会找错方向 |
| 错误文案不可反查根因 | 同一个错误文案可能来自不同阶段、不同对象；用 traceId 串证据 |
| 证据脱敏 | 引用使用记录、审计日志等内容时，不外泄密钥、token 与原始请求体 |
| 处置后必验证 | 每次处置后回到使用记录确认链路恢复预期；验证不过的处置等于没修，还可能引入新问题 |

一条总原则收尾：**"恢复服务"的正确路径是先定位、再处置**。停账户、放宽全局限制这类大半径动作，永远排在证据指向的精确动作之后。

## 排障记录怎么留

每次非平凡的处置留一份简短记录，回退和复盘都靠它：

| 记什么 | 例子 |
| --- | --- |
| 现象与影响面 | "14:00 起 A 分组 502 突增，影响 X 业务的 2 把 Key" |
| 证据 | 使用记录筛选条件、涉事 traceId、健康检查时间线 |
| 处置动作 | "把账户 a1 移出 A 分组的支持范围" |
| 回退点 | 原配置值或原分组绑定顺序 |
| 结果 | 恢复时间、是否复发 |

记录放哪由团队约定，但内容里不要出现密钥、token 或原始请求体——见上一节纪律。
