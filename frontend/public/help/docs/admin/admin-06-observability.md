# 观测：日志与统计

> 这一篇解决：六类证据各管什么、统计页面怎么用、一个失败请求怎么逐层查出结论。核心方法：先用使用记录定位那一次调用，再按需要用性能、健康、运行、审计和操作日志扩展证据——每类证据回答的问题不同，串起来才构成完整结论。

## 开始之前，先圈定范围

打开证据页之前，先手上有这三样之一，检索才有抓手：

1. 大致**时间窗口**（什么时候开始的）；
2. 涉事的 **API Key、用户或账户**（谁的影响）；
3. 最好有一条例子调用的 **traceId**（从使用记录或报错方拿到）。

三样都没有时，从[统计概览](/__aisys__/stats)开始看趋势，先找到"什么时候变坏"，再回来圈范围。

## 六类证据速查

同一问题，用不同证据回答。先记住每一类"擅长回答什么"：

| 证据 | 页面 | 回答什么问题 | 典型场景 |
| --- | --- | --- | --- |
| 使用记录 | [使用记录](/__aisys__/usage-records) | 这次调用用了哪个账户、模型、状态、耗时和成本 | 定位具体调用、路由和最终状态的首选页面 |
| AI 健康 | [AI 健康监控](/__aisys__/ai-health) | 账户是否可调度、最近检查和恢复状态 | 判断单次抖动还是持续失败 |
| AI 性能 | [AI 性能监控](/__aisys__/ai-performance) | 某账户/模型是否持续变慢，而不是只看一次长尾请求 | "变慢"投诉的取证 |
| 运行日志 | [日志搜索](/__aisys__/runtime-logs)（即运行日志） | 服务阶段、策略命中与运行异常 | 按 traceId 或策略名查网关内部发生了什么 |
| 审计日志 | [审计日志](/__aisys__/audit-logs) | 安全和管理相关事件 | 需要完整链路证据时；按权限查看，不复制原始 payload |
| 操作日志 | [操作日志](/__aisys__/operation-logs) | 谁修改过哪种资源 | 核对配置变更时间线，排除"变更引入" |

统计类页面补充全局视角：

| 页面 | 用途 |
| --- | --- |
| [统计概览](/__aisys__/stats) | 全局业务统计与状态的入口：请求数、失败趋势、Token 消耗、平均总耗时、模型分布、错误 Top 10 |
| [用量统计](/__aisys__/usage-stats) | 按账户、模型和时间汇总令牌与费用，用于对账 |
| [公开接口日志](/__aisys__/public-api-logs) | 排查外部来源系统公开接口的调用时间、耗时、状态码；按最小权限处理其业务上下文 |

## traceId：把证据串起来的线索

`traceId` 是把不同证据页串起来的唯一线索：

| 哪里能拿到 traceId | 说明 |
| --- | --- |
| 使用记录 | 每条调用记录都带 |
| 运行日志（日志搜索） | 按它检索同一次请求的内部阶段 |
| 审计日志 | 与使用记录、运行日志共用同一个 traceId |
| 账户状态提示 | 直接展示最近一次健康检查与最近一次错误的 traceId |
| 操作日志 | 人工放行记录使用当前请求的 traceId |

排障纪律：**从使用记录复制 traceId，再到运行日志与审计日志检索同一次请求**。不要凭错误文案反查——同一个错误文案可能来自不同阶段、不同对象，按文案猜会直接把排障带偏。

## 一次失败请求的定位路径

按这五步走，多数问题到第 1 步就能定位到层。每一步都回答一个明确的问题，答不出来就停在原地补证据，不要跳层。

### 第 1 步：使用记录——落在哪一层

- **做什么**：确认这次失败的调用用了哪把 Key、绑定的策略、命中的分组与账户、最终状态与错误。
- **回答的问题**：链路哪一层与预期不符——是 Key 被拦、策略选错组、组里没账户，还是账户调上游失败。
- **判断标准**：能说出"哪一层、什么现象"。多数请求问题到这一步就能定位到层。

### 第 2 步：运行日志——网关内部发生了什么

- **做什么**：在[日志搜索](/__aisys__/runtime-logs)按 traceId 查这次请求停在哪个服务阶段、命中了哪些检查与策略。
- **回答的问题**：第 1 步看到的现象，是网关哪个环节造成的。
- **判断标准**：能指出具体阶段与命中规则。

### 第 3 步：AI 健康——是抖动还是惯犯

- **做什么**：在[AI 健康监控](/__aisys__/ai-health)确认涉事账户是单次抖动还是持续失败，检查与恢复状态如何。
- **回答的问题**：要不要处置账户——单次抖动不处置，持续失败才进入处置流程。
- **判断标准**：账户的检查时间线支持"抖动"或"持续"的结论。

### 第 4 步：操作日志——是不是有人改过配置

- **做什么**：确认失败发生前，是否有人改过这把 Key、这条策略、这个分组或账户的配置。
- **回答的问题**：先排除"变更引入"的可能，再深挖上游。
- **判断标准**：失败时间点附近的变更记录都能对应到已知操作。

走完前三步已经能解决大多数问题；第 4、5 步分别用于"排除人为变更"和"取完整证据"，按需进入。

### 第 5 步：审计日志——要完整链路证据时

- **做什么**：需要完整链路证据（客户端请求、上游响应、最终返回）时使用。
- **回答的问题**：双方到底各发了什么——用于纠纷、安全事件或需要原始 payload 的场景。
- **判断标准**：按权限查看，不复制原始敏感内容。

**整体判断标准**：能用"哪一层、什么证据、什么原因"三段话描述这次失败。如果还不能，回到第 1 步换一条失败样本，不要凭印象动手。

## 症状到证据页的速查

| 症状 | 第一站 | 第二站 |
| --- | --- | --- |
| 某用户/Key 全部失败 | [使用记录](/__aisys__/usage-records) | [操作日志](/__aisys__/operation-logs) 查 Key 与策略的最近变更 |
| 偶发失败、换账户能好 | [使用记录](/__aisys__/usage-records) | [AI 健康监控](/__aisys__/ai-health) |
| 整体变慢 | [统计概览](/__aisys__/stats) 趋势 | [AI 性能监控](/__aisys__/ai-performance) 缩小账户/模型 |
| 用量对不上 | [用量统计](/__aisys__/usage-stats) | [使用记录](/__aisys__/usage-records) 核对明细 |
| 怀疑被攻击或异常调用 | [IP 管理](/__aisys__/ip-stats) | [审计日志](/__aisys__/audit-logs) |

## 统计与对账怎么用

| 场景 | 去哪 | 怎么看 |
| --- | --- | --- |
| 日常巡检 | [统计概览](/__aisys__/stats) | 按监控窗口看请求数、失败趋势、Token 消耗、平均总耗时、模型分布、错误 Top 10；先看趋势再下钻 |
| 费用对账 | [用量统计](/__aisys__/usage-stats) | 按系统账户查看每日消耗趋势，仅统计所选用户发起的调用；按账户、模型和时间汇总令牌与费用 |
| 变慢投诉 | [AI 性能监控](/__aisys__/ai-performance) | 按账户/模型看小时级趋势（含授权实例）；先缩小到账户和模型范围 |
| 账户健康复核 | [AI 健康监控](/__aisys__/ai-health) | 按账户看最近一个月逐小时的健康检查结果；持续失败才进入账户处置 |

### 什么时候用公开接口日志

公开接口日志面向的是**外部来源系统**调用本系统公开接口的场景，与 `/v1` 网关调用分开。需要核对某个外部系统的调用时间、耗时、状态码或请求摘要时用它；业务网关的问题仍以使用记录为主线。

统计读数的三条经验（配合巡检使用，见《系统设置与日常运维》的巡检清单）：

1. **先趋势后单点。** 单次长尾请求不构成结论，趋势变化才是处置依据。
2. **先缩小范围再下钻。** 从全局到账户/模型逐层收窄，避免被聚合数字误导。
3. **统计与记录互相印证。** 统计发现异常后，去使用记录找具体调用；统计是雷达，记录是证据。

### 五步之外：全局视角的补充证据

五步定位路径之外，还有两类"看面不看点"的补充：

- **AI 性能监控**：回答"是不是持续变慢"——它是趋势证据，不定位单次调用；
- **IP 管理**：来源 IP 的请求、失败率、封禁与白名单状态——怀疑异常来源时从这里进入。

## 证据的保留期

证据页能查到多久之前的事实，由系统设置的保留天数决定（当前默认值，可按需调整）：

| 证据 | 默认保留 | 说明 |
| --- | --- | --- |
| 使用记录 | 30 天 | 排障与对账的主窗口 |
| 运行日志索引 | 14 天 | 索引清理不删除原始日志文件 |
| 公开日志 | 30 天 | 公开接口调用记录 |

需要更长回看期的场景（审计、纠纷取证），在保留期内导出留档，不要指望页面一直查得到。

## 证据的边界

三类查看纪律，都是为了让证据本身保持可信：

1. **审计日志**按权限查看，不复制原始 payload 与敏感内容到外部。
2. **公开接口日志**含外部系统业务上下文，按最小权限处理。
3. 帮助与报告里引用证据时，脱敏密钥、token 与原始请求体——证据用来定位问题，不是用来传播内容的。

> ⚠️ 审计日志与公开接口日志包含原始请求响应内容。查看与引用时遵守最小权限，不得把密钥、token、代理密码或原始请求体复制到工单、文档或聊天工具里。
